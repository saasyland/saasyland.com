Os workflows ficam em `.github/workflows/`. Os workflows da aplicação (`ci.yml`, `e2e-reusable.yml` e `deploy-reusable.yml`) preparam a toolchain com a action composta `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ com a versão do Node em `.nvmrc`, um cache do Bun, `bun install --frozen-lockfile --ignore-scripts` e `bun run typegen`. Já o `remotion.yml` prepara o Node de `.nvmrc` e o npm.

| Workflow              | Gatilho                                                                                    | Jobs                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests e pushes para `main`                                                         | Verificações e cobertura, E2E no Chromium e, depois, deploy de preview, ou de produção com release |
| `e2e-full.yml`        | Pushes para `main`, o agendamento <RepositoryFact name="e2eFullSchedule" /> em UTC, manual | WebKit no push; Chromium e WebKit nas execuções agendadas e manuais                                |
| `e2e-reusable.yml`    | Chamado pelos workflows acima                                                              | Banco de dados de testes, build de testes e um projeto do Playwright                               |
| `deploy-reusable.yml` | Chamado por `ci.yml`                                                                       | Build, migrações do D1 e `wrangler deploy`                                                         |
| `remotion.yml`        | Alterações em `remotion/` ou nas suas constantes compartilhadas                            | Verifica e empacota com npm o projeto do vídeo da landing page                                     |

## Verificações

O job `verify` em `ci.yml` executa `bun run check` (tabelas de nomes de classes, verificações de i18n e de conteúdo, formatação, lint e tipos) e `bun run test:coverage` e, em seguida, envia o relatório de cobertura. O job `e2e` executa `db:reset:test` e `build:test`, instala o navegador e executa `bunx playwright test e2e/specs --project=chromium`. Execuções de E2E com falha enviam o relatório do Playwright.

## Deploys

Os deploys só são executados depois que `verify` e `e2e` passam:

| Evento                                       | Destino      | Ambiente do GitHub | URL                           |
| -------------------------------------------- | ------------ | ------------------ | ----------------------------- |
| Pull request de uma branch deste repositório | `preview`    | `Preview`          | https://preview.saasyland.com |
| Push para `main`                             | `production` | `Production`       | https://saasyland.com         |

Pull requests de forks e do Dependabot são validados, mas não recebem deploy. O preview é compartilhado: cada deploy substitui o anterior e usa o mesmo banco de dados D1, o mesmo namespace KV e o mesmo bucket R2 de preview.

`deploy-reusable.yml` verifica a existência dos secrets `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID`, executa `scripts/verify-bindings.ts`, faz o build com os valores fictícios de `.env.test`, remove o `dist/server/.dev.vars` gerado, aplica `db:migrate:<target>` e executa `vp exec wrangler deploy --config dist/server/wrangler.json`. Não executa `scripts/verify-deployment.ts`, a verificação do site no ar dos scripts `deploy:<target>`, porque a proteção contra bots da Cloudflare responde 403 às requisições dos runners de CI. Também não executa `polar:verify:<target>`, porque os ambientes do GitHub não guardam nenhum token do Polar; execute-o localmente depois de cada alteração no Polar ([Configuração do Polar](/docs/getting-started/polar-setup)). Nenhum arquivo de secrets é enviado: o Worker mantém os secrets de runtime já configurados na Cloudflare. Deploys para o mesmo destino entram em fila em vez de cancelarem uns aos outros.

O Dependabot atualiza as GitHub Actions semanalmente.

## Releases e tags [#releases-and-tags]

O site recebe deploys contínuos, então suas versões são datas, não versões semânticas. Quando um deploy de produção termina com sucesso, o job `release` do `ci.yml` marca o commit implantado com a tag `vYYYY.MM.DD` na data UTC e publica uma GitHub Release para ele. Um segundo deploy de produção no mesmo dia recebe a tag `vYYYY.MM.DD.2`, o seguinte `.3`, e assim por diante. Deploys de preview nunca recebem tag. O job `release` é o único com `contents: write`.

As notas da release são a seção daquele dia do [changelog](/docs/project/changelog), então cada mudança é descrita em um só lugar; quando o changelog não tem seção para o dia, as notas apontam para ele. `scripts/publish-release.ts` escolhe a tag e as notas com `src/lib/release.ts` e executa `gh release create`. Uma nova execução mantém a tag que o commit já tem e pula uma release que já existe.

Para voltar a produção a uma release, reverta em um pull request tudo o que veio depois da tag dela:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

O merge faz o deploy do código da tag após as verificações de sempre e o marca como uma nova release. As migrações do D1 não são revertidas, então o código mais antigo roda sobre o esquema mais novo. Toda mudança de esquema precisa funcionar com a aplicação implantada antes dela, o que torna isso seguro para a release anterior; leia as migrações intermediárias antes de voltar mais.
