---
title: "Ruoli e permessi"
description: "Definisci le dichiarazioni di permesso di un'area e i ruoli a cui le concede nel suo file di accesso e controllale nelle guardie delle route e nelle funzioni server."
---

Il controllo degli accessi usa il plugin admin di Better Auth. Ogni area definisce le dichiarazioni di permesso delle sue risorse e i ruoli a cui le concede in `src/data/<area>.access.ts`. `src/data/access.entries.ts` riunisce le aree, e `src/integrations/better-auth/auth.access.ts` costruisce da esse il controllo degli accessi di Better Auth, i ruoli e la verifica dei permessi, quindi l'integrazione di autenticazione non nomina alcuna area. I codici dei ruoli si trovano in `src/integrations/better-auth/auth.roles.ts`.

## Permessi e ruoli

```ts title="src/data/auth.access.ts"
const STATEMENTS = {
  admin: ["access"],
  settings: ["manage"],
} as const

export const AUTH_ACCESS = {
  grants: { [ROLE_CODES.ADMIN]: STATEMENTS },
  statements: STATEMENTS,
} as const satisfies AreaAccess
```

```ts title="src/integrations/better-auth/auth.access.ts"
export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...grantsOf(ROLE_CODES.ADMIN), ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole(grantsOf(ROLE_CODES.CUSTOMER)),
}
```

- `APP_STATEMENTS` in `src/data/access.ts` riunisce le dichiarazioni di tutte le aree, ordinate per risorsa, e fallisce all'avvio quando due aree dichiarano la stessa risorsa. `grantsOf(role)` riunisce ciò che ogni area concede a quel ruolo.
- L'area di autenticazione dichiara `admin` e `settings`, l'area dei prodotti `category` e `product`, l'area dei corsi `course` e `video` e l'area dei pagamenti `order`.
- I `defaultStatements` di Better Auth aggiungono le risorse `user` e `session` (ad esempio `user: ["list", "set-role", "ban", "impersonate", "delete"]` e `session: ["list", "revoke"]`).
- Ogni area concede tutte le sue dichiarazioni ad `admin`, che riceve anche le dichiarazioni di amministrazione di Better Auth; a `customer`, il ruolo predefinito dei nuovi utenti, non ne viene concessa nessuna.
- `ROLE_VALUES` tipizza la colonna `user.role` e gli schemi di ruolo in `user.zod.ts`.
- `Permission`, il tipo che accettano `authorized` e `hasPermission`, è costruito dalle dichiarazioni delle aree, quindi una dichiarazione o un'azione che nessuna area dichiara non compila.

## Dove vengono controllati i permessi

| Livello                 | Controllo                                                             |
| ----------------------- | --------------------------------------------------------------------- |
| Guardia della route     | `requireAdmin` richiede `admin: ["access"]` per tutta l'area `/admin` |
| Funzione server         | `authorized({ product: ["update"] })` su ogni operazione protetta     |
| Solo utenti autenticati | `authorized()` per le operazioni sui dati del chiamante               |
| Ovunque altrove         | `hasPermission({ permission, role })` restituisce un booleano         |

La guardia della route decide solo quali pagine vengono mostrate. Le funzioni server possono essere chiamate direttamente via RPC, quindi ognuna deve controllare il proprio permesso. Nascondere un pulsante è presentazione, non autorizzazione.

## Aggiungi un permesso

1. Aggiungi l'azione alle dichiarazioni dell'area che possiede la risorsa, ad esempio `report: ["read", "export"]` in `src/data/analytics.access.ts`. Una nuova area aggiunge il suo file e una riga a `src/data/access.entries.ts`.
2. Concedila nei `grants` dello stesso file: le aree concedono tutti i loro `STATEMENTS` a `ROLE_CODES.ADMIN`, e a un ruolo che deve ricevere meno se ne concede un sottoinsieme.
3. Richiedila nella funzione server: `.middleware([authorized({ report: ["export"] })])`.
4. Testa sia il caso consentito sia il caso `FORBIDDEN`, nel file `src/data/__test__/<area>.access.test.ts` dell'area e nei test del caso d'uso.

## Aggiungi un ruolo

1. Aggiungi il codice a `ROLE_CODES` e `ROLE_VALUES` in `auth.roles.ts`.
2. Aggiungilo a `ROLES` in `auth.access.ts` e concedigli dichiarazioni nei `grants` delle aree che può usare.
3. Aggiungi l'etichetta del ruolo a `filters.role.options` in `messages/<locale>/pages.admin.users.json` in tutte le lingue.

Il client di autenticazione (`auth.client.ts`) riceve `ac` e `ROLES`, quindi le azioni di amministrazione nel browser usano le stesse definizioni.

## Amministrazione di utenti e sessioni

I moduli di utenti e sessioni incapsulano l'API di amministrazione di Better Auth in casi d'uso, ciascuno con il proprio permesso: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` e altri. Le operazioni sui dati del chiamante, come `revokeSession`, usano `authorized()` e filtrano per `context.auth.user.id`.

In locale, `bun run db:seed:local` crea un amministratore. Su preview e in produzione, il primo amministratore viene creato da `bun run admin:grant:preview <email>` o `bun run admin:grant:production <email>`, che può eseguire solo chi ha accesso in scrittura a quel database D1, per un account che ha verificato la propria email; gli amministratori successivi si nominano in **Admin → Gestione degli utenti** con **Cambia ruolo**. Vedi [Il primo amministratore](/docs/tooling/database#the-first-admin).
