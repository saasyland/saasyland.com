Vite+ (`vite-plus`, polecenie `vp`) łączy Vite, Vitest, oxlint i oxfmt w jednym CLI, a `vite.config.ts` konfiguruje je wszystkie. `package.json` nadpisuje `vite` pakietem `@voidzero-dev/vite-plus-core` i przypina `vitest` do wersji 5.1.0. `vite-plus` również jest przypięty do dokładnej wersji; aktualizuj wszystkie trzy naraz przez `vp migrate`, a nie `bun update`. Skrypty pakietu wywołują `vp`; poza nimi używaj globalnego CLI Vite+ lub `bunx vp`.

| Polecenie         | Używane przez                                     |
| ----------------- | ------------------------------------------------- |
| `vp dev`          | `dev`                                             |
| `vp build --mode` | `build:preview`, `build:production`, `build:test` |
| `vp preview`      | `start`, `start:test`                             |
| `vp test`         | `test` i skrypty Vitest `test:*`                  |
| `vp lint`         | `lint`                                            |
| `vp fmt`          | `format`, `format:check`                          |
| `vp check`        | `check`, `check:fix`                              |
| `vp staged`       | `check:pre-commit`                                |
| `vp config`       | `prepare`, który instaluje hooki Gita             |

## Konfiguracja

`vite.config.ts` wymienia swoje wtyczki w `VITE_PLUGINS` i ładuje je leniwie, a każdy wpis importuje swój pakiet dopiero wewnątrz `load`; wtyczki dostawcy pochodzą z `src/integrations/<vendor>/<vendor>.vite.ts` (zobacz [Co uruchamiają Worker i build](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)). W Vitest ładują się tylko wpisy oznaczone `vitest`, czyli `contentIndexes()`, `repositoryFacts()` i `@vitejs/plugin-react`; poza testami zestaw wtyczek wygląda tak:

- `@cloudflare/vite-plugin`: uruchamia Workera w środowisku SSR i utrwala stan lokalny (w `.wrangler/test` dla trybu `test`, w pozostałych przypadkach w `.wrangler/state`) z `remoteBindings: false`, więc ani serwer deweloperski, ani build żadnego środowiska nie łączy się ze zdalnym bindingiem.
- `fumadocs-mdx`: kompiluje kolekcje dokumentacji i bloga.
- `saasyland:fumadocs-bundled`: zostawia `fumadocs-core` i `@fumadocs/base-ui` w bundlu serwera (`resolve.noExternal`). Ta wtyczka i `fumadocs-mdx` pochodzą z `fumadocsVitePlugins` (`src/integrations/fumadocs/fumadocs.vite.ts`).
- `contentIndexes` (`scripts/content-indexes.ts`): udostępnia `virtual:content-indexes` i `virtual:docs-search`, czyli indeksy dokumentacji, bloga i wyszukiwania, które `fumadocs.indexes.ts` buduje z `content/docs` i `content/blog`; zobacz [Fumadocs](/docs/integrations/fumadocs#content-indexes).
- `repositoryFacts` (`scripts/repository-facts.ts`): udostępnia moduł `virtual:repository-facts`, czyli liczby, wersje i ustawienia narzędzi wyświetlane na stronie głównej oraz w dokumentacji, i moduł `virtual:repository-tables`, czyli tabele, które wyświetla tylko dokumentacja; oba odczytuje z repozytorium podczas budowania. Zobacz [Tłumaczenia i treści](/docs/conventions/translations) i [Wydajność](/docs/conventions/performance#repository-tables-load-with-the-docs).
- `unused-primitives` (`scripts/unused-primitives.ts`): przed Tailwindem pomija klasy każdego prymitywu shadcn, którego nie importuje żaden kod źródłowy aplikacji; zobacz [Komponenty shadcn](/docs/ui/shadcn-components).
- `@tailwindcss/vite`: Tailwind CSS 4.
- `tanstackStart`: routing, dzielenie kodu i prerendering stron publicznych, filtrowanych przez `shouldPrerender` (`src/lib/prerender.ts`).
- `@vitejs/plugin-react`.
- `saasyland:zod-config-chunk` (`src/integrations/zod/zod.vite.ts`): w buildzie klienta umieszcza `src/integrations/zod/zod.config.ts` we własnym chunku biblioteki zod, dzięki czemu zod działa w trybie `jitless`, zanim jakikolwiek chunk zbuduje schemat, i przy Content Security Policy nigdy nie sprawdza, czy `eval` jest dostępny; zobacz [Bezpieczeństwo i utwardzanie](/docs/features/security).
- `deployedWorker` (`scripts/deployed-worker.ts`): po prerenderingu buduje Workera od nowa bez skompilowanych stron dokumentacji i bloga oraz bez tłumaczeń strony głównej i stron prawnych; zobacz [Cloudflare Workers](/docs/integrations/cloudflare-workers).
- `saasyland:polar-sdk-optional-peers`: oznacza jako zewnętrzne te opcjonalne zależności peer pakietu `@polar-sh/sdk`, które nie są zainstalowane (`build.rolldownOptions.external`); zobacz [Zależności](/docs/conventions/dependencies).

Serwer deweloperski nasłuchuje pod adresem `localhost:3000` i nie startuje, jeśli port jest zajęty. `resolve.tsconfigPaths` zapewnia alias importu `~/`. Ten sam plik zawiera sekcje `fmt`, `lint`, `staged` i `test`; zobacz [Lint i formatowanie](/docs/tooling/lint-format) oraz [Testy](/docs/tooling/testing).

`vp preview`, które uruchamiają `start`, `start:test` i prerendering, nasłuchuje pod adresem `127.0.0.1:3000`, czyli `LOCAL_SERVER` z `src/data/local-server.ts`, i ten sam adres otwiera Playwright; prerendering używa tego adresu z wolnym portem. Z `localhost` serwer nasłuchiwałby tylko pod pierwszym adresem, na który Node rozwiązuje tę nazwę, czyli `::1`, a każdy klient próbowałby najpierw `::1`, potem `127.0.0.1` i dawał każdemu adresowi tylko chwilę na odpowiedź: na obciążonym komputerze ta chwila mija, zanim klient zauważy połączenie, klient porzuca `::1`, pod `127.0.0.1` nic nie znajduje, a prerendering kończy się błędami `ETIMEDOUT ::1` i `ECONNREFUSED 127.0.0.1`.

`polarVitePlugins` w `src/integrations/polar/polar.vite.ts` zwraca wtyczkę, której hook `config` wymienia w `build.rolldownOptions.external` opcjonalne zależności peer pakietu `@polar-sh/sdk` (OpenTelemetry i `ioredis`). Nie są zainstalowane, a moduł, który je importuje, tree-shaking usuwa z Workera.

## Hooki Gita

`bun install` uruchamia `prepare`, który wywołuje `vp config --no-agent`, aby zainstalować dyspozytor hooków dla `.vite-hooks/`, a następnie `scripts/verify-git-hooks.ts`, który przerywa instalację, gdy Git nie uruchomiłby tego dyspozytora. `pre-commit` uruchamia `bun run check:pre-commit`, `prepare-commit-msg` uruchamia `scripts/commit-msg.ts`, `commit-msg` uruchamia `scripts/verify-commit-msg.ts` (zobacz [Conventional Commits](/docs/tooling/conventional-commits)), a `post-checkout` uruchamia `vp hooks enable` w kopii roboczej, która nie ma jeszcze dyspozytora, na przykład w worktree świeżo utworzonym przez `git worktree add`. `post-merge`, `post-checkout` i `post-rewrite` uruchamiają `bun install --frozen-lockfile`, gdy zmienił się `bun.lock`, więc ani pull, ani rebase, ani przełączenie gałęzi nie zostawiają nieaktualnego `node_modules`. `vp hooks status` pokazuje, czy hooki są aktywne w danym klonie repozytorium, a strona [Git i pull requesty](/docs/conventions/git-workflow#hooks-in-every-worktree) wyjaśnia, dlaczego każdy worktree potrzebuje własnego dyspozytora.

Na co dzień korzystaj ze skryptów pakietu; `vp` wywołuj bezpośrednio przy uruchomieniach punktowych, na przykład gdy formatujesz albo lintujesz wybrane ścieżki.
