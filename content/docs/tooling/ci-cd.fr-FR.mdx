Les workflows se trouvent dans `.github/workflows/`. Les workflows de l'application (`ci.yml`, `deploy.yml`, `preview.yml`, `e2e-reusable.yml` et `deploy-reusable.yml`) mettent en place la chaîne d'outils avec l'action composite `.github/actions/setup` : Bun <RepositoryFact name="bunVersion" />, Vite+ avec la version de Node de `.nvmrc` et le cache d'installation de Bun, que `setup-vp` restaure une seule fois, `bun install --frozen-lockfile --ignore-scripts` et `bun run typegen`. `remotion.yml` met plutôt en place Node depuis `.nvmrc` et npm.

| Workflow              | Déclencheur                                                                                       | Jobs                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests, groupes de la file de fusion, et appels depuis `deploy.yml`                        | Vérifications et couverture, E2E Chromium et téléversement du Worker de préversion                                                          |
| `deploy.yml`          | Pushs sur `main`                                                                                  | Les vérifications de `ci.yml`, sauf si la file de fusion les a exécutées, puis la préversion, la production et la publication de la version |
| `preview.yml`         | Manuel                                                                                            | Déploie sur la préversion partagée une branche dont les vérifications ont réussi                                                            |
| `e2e-full.yml`        | Pushs sur `main`, selon la planification <RepositoryFact name="e2eFullSchedule" /> en UTC, manuel | WebKit lors d'un push ; Chromium et WebKit lors des exécutions planifiées et manuelles                                                      |
| `e2e-reusable.yml`    | Appelé par les workflows ci-dessus                                                                | Un seul build de test, un projet Playwright sur des shards en parallèle et une seule vérification pour les deux                             |
| `deploy-reusable.yml` | Appelé par `ci.yml`, `deploy.yml` et `preview.yml`                                                | Build, puis migrations D1 et `wrangler deploy`, ou `wrangler versions upload`                                                               |
| `remotion.yml`        | Modifications de `remotion/` ou des fichiers du site qu'il importe                                | Vérifie et empaquette avec npm le projet vidéo de la page d'accueil                                                                         |

`remotion.yml` se déclenche sur les mêmes chemins pour les pull requests et les pushs : `remotion/`, le workflow lui-même et les fichiers du site que `remotion/src` importe, directement ou via d'autres fichiers du site. `src/__test__/workflows.test.ts` suit ces imports et échoue lorsqu'un fichier qu'ils atteignent ne correspond à aucun des chemins, ou qu'un chemin ne correspond à aucun des fichiers.

Les checkouts de `e2e-reusable.yml`, dont le build génère le journal des modifications et dont `content.spec.ts` le lit, de `deploy-reusable.yml`, qui construit le site, et du job `release` récupèrent tous les commits sans leurs arbres (`fetch-depth: 0` et `filter: tree:0`) : le [journal des modifications](/docs/project/changelog) date chaque entrée d'après le commit qui l'a amenée sur `main`. Par rapport à un clone superficiel, seuls les commits eux-mêmes s'ajoutent ; un clone superficiel ferait échouer la construction plutôt que de mal dater les entrées. `src/__test__/workflows.test.ts` échoue lorsqu'un de ces checkouts ne récupère plus l'historique.

## Vérifications [#checks]

Le job `verify` de `ci.yml` exécute `bun run check` (tables des noms de classes, vérifications i18n et de contenu, l'[inventaire des parcours](/docs/tooling/test-coverage#flow-coverage), formatage, lint et types) et `bun run test:coverage`, puis téléverse le rapport de couverture. Le job `e2e` appelle `e2e-reusable.yml`, qui construit une seule fois et exécute la suite sur <RepositoryFact name="e2eShards" /> runners en parallèle :

| Job                                        | Exécute                                                                                                                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `build`                                    | `db:reset:test` et `build:test`, puis téléverse `dist`, le `.wrangler/deploy` qui pointe vers la configuration de son Worker et le `.wrangler/test` rempli par le seed en un seul artefact |
| `shard`                                    | Un job par shard : télécharge ce build, installe le navigateur et lance `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>`                                            |
| `report`, nommé `Build and E2E (chromium)` | Échoue sauf si le build et chaque shard ont réussi ; si un shard a échoué, fusionne les rapports blob des shards en un seul rapport HTML et le téléverse                                   |

Les relances et les workers de Playwright restent tels que [Playwright](/docs/tooling/playwright#configuration) les décrit, sur chaque shard. Le job `report` est la seule vérification qu'exigent les règles de la branche : ajouter ou retirer un shard ne change donc le nom d'aucune vérification requise. Le build emballe aussi la liste des tags de release qu'il a lus, et chaque shard supprime tout tag créé depuis : `content.spec.ts` lit les tags de release dans Git, et une release taguée pendant que les shards attendent lui ferait attendre un changelog que le build n'a jamais rendu.

Le job `upload`, nommé `Worker upload`, appelle `deploy-reusable.yml` avec `upload: true` : il construit le Worker de préversion exactement comme le fait un déploiement et lance `wrangler versions upload`, qui l'envoie au Worker `saasyland-preview` sous forme d'une nouvelle version sans la déployer. Cloudflare vérifie ce téléversement comme il vérifie un déploiement, avec la limite de taille, le temps de démarrage, les bindings et les secrets que nomme `secrets.required` : un Worker qui passe cette vérification se déploie donc, tandis que `preview.saasyland.com` continue de servir la version déployée auparavant. Le job n'applique aucune migration et n'enregistre aucun déploiement GitHub (`deployment: false`), et il s'exécute en parallèle des téléversements des autres pull requests. La version d'une pull request reçoit l'alias `pr-<number>`, qui nomme la version dans le tableau de bord de Cloudflare ; le résumé du job affiche l'identifiant et la taille de la version, ainsi que son URL lorsque les Version URLs sont activées pour le Worker. Les pull requests provenant de forks et de Dependabot ne peuvent pas lire les identifiants Cloudflare et sautent ce job ; la file de fusion, qui le peut, téléverse leur build avant leur fusion.

Dans une pull request, `bun run check` échoue aussi tant que la pull request n'ajoute pas son [entrée au journal des modifications](/docs/conventions/git-workflow#changelog-entries), et dans la file de fusion tant que l'entrée de la pull request en file n'est pas là. La construction des jobs `e2e` et `upload`, et celle des jobs de déploiement, échoue tant que le journal afficherait sous **Non publié** une entrée qui n'est pas celle de la pull request elle-même, et dans la file de fusion et sur `main` tant qu'il en afficherait une.

## File de fusion [#merge-queue]

Le ruleset qui protège `main` exige `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)` et `Worker upload / Upload preview`, et ne fusionne les pull requests que par la file de fusion de GitHub, qui squashe chacune d'elles. `bun scripts/enqueue-pr.ts <number>` place une pull request dans la file ([Git et pull requests](/docs/conventions/git-workflow#merging)). Pour chaque pull request de la file, GitHub écrit le commit squash sur une branche nommée `gh-readonly-queue/main/pr-<number>-<commit>`, au-dessus de `main` et des pull requests qui la précèdent, et y exécute `ci.yml` pour l'événement `merge_group`. Une fois que chaque pull request d'un groupe a réussi, GitHub avance `main` jusqu'au dernier commit du groupe, celui-là même que la file a testé : un seul push amène ainsi chaque pull request du groupe sur `main` sous la forme de son propre commit squash. Une pull request qui échoue quitte la file, et celles qui la suivent sont testées de nouveau sans elle.

`ci.yml` annule le run d'une pull request lorsqu'un commit plus récent le remplace, mais jamais un run de la file, dont chaque branche a sa propre ref. Le contrôle du journal des modifications traite la branche de la file comme `main` : chaque pull request du groupe est déjà un commit squash dont le sujet se termine par son numéro, si bien qu'aucune entrée ne peut rester non publiée, et l'entrée de la pull request en file doit exister.

## Déploiements

`deploy.yml` déploie chaque push sur `main`, d'abord sur la préversion partagée, puis en production, une fois que le commit a passé toutes les vérifications qu'exige `main`. Son premier job, `tested`, exécute `scripts/tested-commit.ts`, qui lit ces vérifications dans le ruleset via l'API de GitHub et cherche une exécution réussie de chacune sur le commit poussé. Un commit arrivé par la file de fusion les a, car la file a testé ce commit précis : `deploy.yml` le déploie donc sans relancer les vérifications ; un commit arrivé sur `main` par tout autre chemin exécute d'abord les vérifications de `ci.yml`.

| Événement                           | Cible                        | Environnement GitHub         | URL                                                  |
| ----------------------------------- | ---------------------------- | ---------------------------- | ---------------------------------------------------- |
| Push sur `main`                     | `preview`, puis `production` | `Preview`, puis `Production` | https://preview.saasyland.com, https://saasyland.com |
| Exécution manuelle de `preview.yml` | `preview`                    | `Preview`                    | https://preview.saasyland.com                        |

`deploy-reusable.yml` donne à chaque environnement GitHub son URL, et `src/__test__/workflows.test.ts` échoue lorsque l'une d'elles diffère de son hôte dans `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). La préversion est partagée : chaque déploiement remplace le précédent et utilise la même base de données D1, le même espace de noms KV et les mêmes buckets R2 de préversion. Elle exécute `main` : la [suite de parcours client](/docs/tooling/playwright#journey-suite), les webhooks de la sandbox Polar et la connexion sur `preview.saasyland.com`, le seul hôte de préversion auquel Better Auth fait confiance, rencontrent ainsi tous le code que la production s'apprête à exécuter, et chaque migration atteint la base de données de préversion avant la production. Pour essayer une branche sur la préversion avant sa fusion, lancez `gh workflow run preview.yml --ref <branch>` : le workflow ne déploie la branche, migrations comprises, que si son commit a passé les vérifications qu'exige `main`, et le push suivant sur `main` y remet `main`.

`deploy-reusable.yml` vérifie la présence des secrets `CLOUDFLARE_API_TOKEN` et `CLOUDFLARE_ACCOUNT_ID`, exécute `scripts/verify-bindings.ts`, construit avec les valeurs factices de `.env.test`, supprime le fichier généré `dist/server/.dev.vars`, applique `db:migrate:<target>` et lance `vp exec wrangler deploy --config dist/server/wrangler.json`, ou, avec `upload: true`, lance `vp exec wrangler versions upload` à la place de ces deux dernières étapes. Il ne lance pas `scripts/verify-deployment.ts`, la vérification du site en ligne des scripts `deploy:<target>`, car la protection anti-bots de Cloudflare répond 403 aux requêtes des runners de CI. Il ne lance pas non plus `scripts/run-deploy-checks.ts` : la CI n'exécute donc aucune des vérifications de déploiement que les zones déclarent dans `DEPLOY_CHECKS`, car elle n'a pas de `.env.<target>` et les environnements GitHub ne contiennent que les identifiants Cloudflare. Aujourd'hui, ce sont `auth:verify`, de la zone d'authentification, et `polar:verify`, de la zone Polar ; lancez en local `bun run auth:verify:<target>` après avoir modifié un client OAuth et `bun run polar:verify:<target>` après chaque modification dans Polar ([Configurer Polar](/docs/getting-started/polar-setup)). Aucun fichier de secrets n'est téléversé : le Worker conserve les secrets d'exécution déjà définis dans Cloudflare. Les déploiements vers une même cible sont mis en file d'attente au lieu de s'annuler mutuellement, et les téléversements s'exécutent en parallèle. Un nouveau commit sur une pull request annule le run de `ci.yml` du commit précédent, que personne ne fusionnera, tandis que les runs de la file de fusion ne s'annulent jamais les uns les autres et que ceux de `deploy.yml` et de `e2e-full.yml` sur `main` se mettent en file d'attente (`concurrency` avec `queue: max`) : chaque push sur `main` est ainsi déployé.

Dependabot met à jour les GitHub Actions chaque semaine.

## Versions et tags [#releases-and-tags]

Le site est déployé en continu : ses versions sont donc des dates et non des versions sémantiques. Quand un déploiement en production réussit, le job `release` de `deploy.yml` pose le tag `vYYYY.MM.DD` à la date UTC sur le commit déployé et publie une GitHub Release correspondante. Un deuxième déploiement en production le même jour reçoit le tag `vYYYY.MM.DD.2`, le suivant `.3`, et ainsi de suite. Les déploiements en préversion ne reçoivent jamais de tag. Le job `release` est le seul à disposer de `contents: write`.

Les notes de version sont les entrées du [journal des modifications](/docs/project/changelog) que la version a livrées, celles arrivées sur `main` depuis le tag de version précédent, chacune terminée par `(#<number>)`, dont GitHub fait un lien vers sa pull request, si bien que chaque changement n'est décrit qu'à un seul endroit ; si une version n'en a livré aucune, ses notes renvoient vers le journal. `scripts/publish-release.ts` prend les notes dans `src/lib/release.ts` et lance `gh release create` avec le tag que le déploiement a choisi. Une nouvelle exécution conserve le tag que le commit possède déjà et ignore une GitHub Release qui existe déjà.

Le job du déploiement en production choisit ce tag avant de construire : `scripts/choose-release-tag.ts` applique `releaseTag` de `src/lib/release.ts` aux tags du checkout, la construction reçoit le tag dans `RELEASE_TAG`, et le job le transmet au job `release` par sa sortie `release-tag`, si bien que le déploiement et sa version partagent un seul tag. Grâce à lui, le [journal des modifications](/docs/project/changelog) relie chaque entrée à la version qui l'a livrée en premier : le plus ancien tag de version dont le commit contient le commit squash de l'entrée dans l'historique des premiers parents de `main`, que la construction lit avec les dates en un seul `git log`, ou le tag du déploiement lui-même pour les entrées qu'il apporte. Le job `release` lit le journal de la même façon, avec le tag qu'il publie, si bien que les notes d'une version sont exactement les entrées que la page relie à cette version. Les entrées fusionnées avant le premier tag de version ne renvoient vers aucune version, pas plus que, dans les constructions locales, de prévisualisation et de pull requests, les entrées qu'aucun déploiement n'a encore livrées. Deux déploiements en production ne peuvent pas choisir le même tag : `deploy.yml` n'exécute qu'un seul run du workflow à la fois (`concurrency` avec `queue: max`), si bien que le job `release` du run précédent a créé son tag avant que le déploiement suivant ne fasse le checkout du dépôt.

Pour ramener la production à une version, annulez dans une pull request tout ce qui suit son tag :

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Sa fusion déploie le code du tag après les vérifications habituelles et lui pose le tag d'une nouvelle version. Les migrations D1 ne sont pas annulées : l'ancien code s'exécute donc sur le schéma plus récent. Chaque modification du schéma doit fonctionner avec l'application déployée avant elle, ce qui rend l'opération sûre pour la version précédente ; lisez les migrations intermédiaires avant de remonter plus loin.
