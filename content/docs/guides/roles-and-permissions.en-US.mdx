title: "Roles and permissions"
description: "Declare an area's permission statements and role grants in its access file and check them in route guards and server functions."
---

Access control uses the Better Auth admin plugin. Each area declares the permission statements of its resources and the roles it grants them to in `src/data/<area>.access.ts`. `src/data/access.entries.ts` joins the areas, and `src/integrations/better-auth/auth.access.ts` builds Better Auth's access control, the roles and the permission check from them, so the auth integration names no area. The role codes live in `src/integrations/better-auth/auth.roles.ts`.

## Statements and roles

```ts title="src/data/auth.access.ts"
const STATEMENTS = {
  admin: ["access"],
  settings: ["manage"],
} as const

export const AUTH_ACCESS = {
  grants: { [ROLE_CODES.ADMIN]: STATEMENTS },
  statements: STATEMENTS,
} as const satisfies AreaAccess
```

```ts title="src/integrations/better-auth/auth.access.ts"
export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...grantsOf(ROLE_CODES.ADMIN), ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole(grantsOf(ROLE_CODES.CUSTOMER)),
}
```

- `APP_STATEMENTS` in `src/data/access.ts` joins the statements of every area, sorted by resource, and fails at startup when two areas declare the same resource. `grantsOf(role)` joins what every area grants that role.
- The auth area declares `admin` and `settings`, the products area `category` and `product`, the courses area `course` and `video`, and the payments area `order`.
- `defaultStatements` from Better Auth add the `user` and `session` resources (such as `user: ["list", "set-role", "ban", "impersonate", "delete"]` and `session: ["list", "revoke"]`).
- Every area grants all of its statements to `admin`, which also receives Better Auth's admin statements; `customer`, the default role for new users, is granted none.
- `ROLE_VALUES` types the `user.role` column and the role schemas in `user.zod.ts`.
- `Permission`, the type `authorized` and `hasPermission` take, is built from the statements the areas declare, so a statement or action that no area declares does not compile.

## Where permissions are checked

| Layer           | Check                                                                   |
| --------------- | ----------------------------------------------------------------------- |
| Route guard     | `requireAdmin` requires `admin: ["access"]` for the whole `/admin` area |
| Server function | `authorized({ product: ["update"] })` on every protected operation      |
| Signed-in only  | `authorized()` for operations on the caller's own data                  |
| Anywhere else   | `hasPermission({ permission, role })` returns a boolean                 |

The route guard only decides which pages render. Server functions are callable directly over RPC, so each one must check its own permission. Hiding a button is presentation, not authorization.

## Add a permission

1. Add the action to the statements of the area that owns the resource, for example `report: ["read", "export"]` in `src/data/analytics.access.ts`. A new area adds its file and one line to `src/data/access.entries.ts`.
2. Grant it in the same file's `grants`: the areas grant their whole `STATEMENTS` to `ROLE_CODES.ADMIN`, and a role that should get less is granted a subset.
3. Require it in the server function: `.middleware([authorized({ report: ["export"] })])`.
4. Test both the allowed and the `FORBIDDEN` case, in the area's `src/data/__test__/<area>.access.test.ts` and in the use case's tests.

## Add a role

1. Add the code to `ROLE_CODES` and `ROLE_VALUES` in `auth.roles.ts`.
2. Add it to `ROLES` in `auth.access.ts`, and grant it statements in the `grants` of the areas it may use.
3. Add the role label to `filters.role.options` in `messages/<locale>/pages.admin.users.json` for every locale.

The auth client (`auth.client.ts`) receives `ac` and `ROLES`, so admin actions in the browser use the same definitions.

## User and session administration

The user and session modules wrap the Better Auth admin API in use cases, each with its own permission: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` and more. Operations on the caller's own data, such as `revokeSession`, use `authorized()` and filter by `context.auth.user.id`.

Locally, `bun run db:seed:local` creates an admin. On preview and production, the first admin is created by `bun run admin:grant:preview <email>` or `bun run admin:grant:production <email>`, which only someone with write access to that D1 database can run, for an account that has verified its email; later admins are made in **Administration → User Management** with **Change role**. See [The first admin](/docs/tooling/database#the-first-admin).
