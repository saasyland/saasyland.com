## Configuration

`src/integrations/better-auth/auth.server.ts` creates the Better Auth instance:

- Drizzle adapter on D1, UUID v7 ids, cookie prefix `saasyland`, secure cookies outside the `development` and `test` modes, and allowed hosts per mode from `appHostsForMode`.
- Email and password, with a new account signed in at sign-up and a confirmed address required to sign in again and to receive what a confirmed address unlocks ([Email verification](/docs/features/email-verification)), passwords of <RepositoryFact name="passwordMinLength" /> to <RepositoryFact name="passwordMaxLength" /> characters with no composition rules (`auth.constraints.ts`), as OWASP and NIST SP 800-63B ask, session revocation on password reset and a "your password was changed" email after one (`onPasswordReset`). Verification and reset links work for `EMAIL_LINK_LIFETIME_HOURS` (`auth.constants.ts`), which sets both `emailVerification.expiresIn` and `resetPasswordTokenExpiresIn` and which the emails state.
- `haveIBeenPwned`, which the auth area adds in `src/data/auth.auth-plugins.ts`, refuses a new password found in the Have I Been Pwned corpus at sign-up, password reset and change, and when an admin creates a user or sets a password. Only the first five characters of the password's SHA-1 hash leave the Worker. The sign-up, reset and settings forms show `passwordCompromised` under the password field and move focus to it; the admin dialogs show it as a toast. Browser and integration tests answer the check with the provider double in `src/platform/testing/mocks/auth.providers.ts`, which reports `BREACHED_PASSWORD` from `e2e/data/accounts.ts` as breached.
- `signInNewAccount` (`auth.hooks.ts`), a `hooks.after` middleware, signs in the account a sign-up created. `enforceInputPolicy`, a `hooks.before` middleware, applies the form schemas to Better Auth's own endpoints: sign-up, password reset and change, profile and email updates, and the admin endpoints that create users or set passwords. A request posted straight to `/api/auth` gets `400 VALIDATION_ERROR` instead of skipping the rules.
- GitHub and Google social providers with account linking and encrypted OAuth tokens.
- Plugins: `admin` with the access control and roles from `auth.access.ts`, `twoFactor`, `haveIBeenPwned`, `lastLoginMethod`, which remembers the last way the browser signed in, Polar (`portal`, `webhooks`) and `tanstackStartCookies`.
- Rate limiting stored in the D1 `rate_limit` table; `/get-session`, `/sign-out` and the Polar webhook are exempt.
- An extra `timezone` user field and email change with a confirmation email.

`src/routes/api/auth.$.ts` passes every GET and POST under `/api/auth` to `auth.handler`.

## Screens

The `/auth` layout preloads the `auth.*` namespaces and places every auth page on one grid. From the `lg` breakpoint it has two halves under a shared header row: the gate panel with the headline and the assurances on the left, and the form on the right. The wordmark and the headline share a left edge, and the headline and the form start on the same line, so the form's heading stays in place as you move between auth pages. Below `lg` the gate panel is hidden, and the wordmark, the **Back to home** link and the form share one centred column as wide as the form. `AuthPending` draws the same grid while a page loads, and `e2e/specs/auth-layout.spec.ts` checks the alignment at four window sizes. Inputs, provider buttons and primary buttons share the height of the site's call-to-action buttons.

| Route                                           | Components                                | Behaviour                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/auth/sign-in`                                 | `OAuthButtons`, `SignInForm`              | Signs in with Better Auth `signIn.email`. A refusal stays above the button, with a password reset and GitHub and Google for a wrong password; an unconfirmed address gets a fresh link and moves to `/auth/verify-email` with `unverified`; an account with 2FA continues at `/auth/two-factor`. |
| `/auth/sign-up`                                 | `OAuthButtons`, `SignUpForm`              | Calls the `signUpWithPassword` server function and continues to `redirect`, or to `/auth/verify-email` when no account was created; see [Signing up with a known address](#signing-up-with-a-known-address).                                                                                     |
| `/auth/callback`                                | none                                      | `redirectAfterAuth` sends the visitor to `redirect`, or admins to `/admin` and everyone else to `/app`.                                                                                                                                                                                          |
| `/auth/verify-email`                            | `VerifyEmailForm`                         | See [Email verification](/docs/features/email-verification).                                                                                                                                                                                                                                     |
| `/auth/forgot-password`, `/auth/reset-password` | `ForgotPasswordForm`, `ResetPasswordForm` | See [Password reset](/docs/features/password-reset).                                                                                                                                                                                                                                             |
| `/auth/two-factor`                              | `TwoFactorForm`                           | See [Two-factor authentication](/docs/features/two-factor).                                                                                                                                                                                                                                      |

`SignUpForm` asks for a name of up to <RepositoryFact name="nameMaxLength" /> characters, an email and one password. The eye button shows what was typed, so there is no confirmation field, and the password field has no placeholder. `PasswordRequirements` ticks off the length rule as the visitor types and says that the breach check runs when they continue. Once the email field is left, `EmailSuggestion` offers the likely address for a misspelt domain (`suggestEmail` in `src/lib/email-suggestion.ts`, from `EMAIL_DOMAINS` in `src/data/email-domains.ts`), and pressing the suggestion fills the field in. A sign-up that creates an account signs it in and continues to `redirect`; one for an address that already has an account moves to `/auth/verify-email` with a toast that points to the inbox.

Above its form, `/auth/sign-up` shows the first entry of `SIGN_UP_INTROS` (`src/data/sign-up-intros.ts`) that applies to `redirect`, in place of its description, and `SignUpPending` draws that entry's skeleton. The auth area adds none (`AUTH_SIGN_UP_INTROS`), and the licence area adds the order summary of a tier picked on the landing page ([Licences](/docs/features/licences)).

After a successful sign-in, `finishSignIn` from `useAuthRedirect` removes the previous user's data from the query cache, clears the router cache and navigates to `/auth/callback`, keeping `redirect`. Better Auth errors returned as `?error=` on `/auth/sign-in` render the matching `auth.errors` message.

## Signing up with a known address

The sign-up screen never tells a confirmed account from an unconfirmed one (OWASP's advice against account enumeration). Better Auth answers every sign-up with the same response, `token: null` and a user, and only the account a sign-up created gets a session (`signInNewAccount`, see [Email verification](/docs/features/email-verification#signing-up)) and continues to `redirect`. For an address that already has an account, the form moves to `/auth/verify-email`, which reads "We sent an email to …. Open the link in it and you'll continue where you left off." What arrives in the inbox depends on the address:

| The address                      | What happens                                                                                                                                                                                                                       |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Has no account                   | Better Auth creates the user, `signInNewAccount` signs it in and `sendVerifyEmail` sends the verification link.                                                                                                                    |
| Belongs to a verified account    | Nothing is created. `onExistingUserSignUp` calls `sendExistingAccountEmail`: "You already have a SaaSy Land account", the sign-in methods the account has, a sign-in link that keeps `redirect`, and a link to reset the password. |
| Belongs to an unverified account | Nothing is created. `onExistingUserSignUp` sends a fresh verification link with `sendVerifyEmail`.                                                                                                                                 |

Both notices go out in the locale of the sign-up page and are limited to <RepositoryFact name="recipientEmailsPerHour" /> per address an hour. Better Auth hashes the submitted password for a known address too and runs `onExistingUserSignUp` in the background through `waitUntil`, so neither the lookup of the sign-in methods nor the email lengthens the answer. The answer for a new address differs by the rows it writes and by the session cookie that signs it in: the price of taking a buyer to the checkout without a trip to the inbox. Sign-up stays rate limited with `RATE_LIMITS.SENSITIVE`.

Signing in to an unverified account returns `EMAIL_NOT_VERIFIED`, and `emailVerification.sendOnSignIn` sends a fresh link in the locale, and with the `redirect`, of the sign-in page that the request came from. `SignInForm` moves to `/auth/verify-email?unverified=true`, which says that a new link went to the address and offers **Resend link**. A wrong password gets the usual `INVALID_EMAIL_OR_PASSWORD` and sends nothing.

## Route guards

`src/integrations/better-auth/auth.routes.ts` exports the guards used in `beforeLoad`:

- `requireSignedIn` protects `/app` and redirects to `/auth/sign-in`, with the page as `redirect`. When the browser had a session, it adds `error=SESSION_EXPIRED`, and the sign-in page says the session ended and names the page it returns to.
- `requireAdmin` protects `/admin`; a signed-in user without the `admin: ["access"]` permission goes to `/app`.
- `redirectIfSignedIn` sends signed-in users from sign-in and sign-up to `redirect`, or to their workspace.
- `redirectAfterAuth` powers `/auth/callback`.

The guards read the session through `getCurrentSessionQuery` and, when the signed-in user changes, remove the previous user's data from the query cache and keep the [public queries](/docs/conventions/data-fetching#public-queries). [Auth flows](/docs/guides/auth-flows#return-path) describes how `redirect` travels through sign-in, sign-up, OAuth and two-factor verification.

## Server functions

Server functions use the middleware from `auth.middleware.ts`: `authorized()` requires a session, `authorized({ user: ["list"] })` also checks a permission, and `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` limits calls per client IP.

```ts
export const signOutUser = createServerFn({ method: "POST" })
  .middleware([authorized()])
  .handler(({ context }) => auth.api.signOut({ headers: context.requestHeaders }))
```

There are two roles, `admin` and `customer` (the default for new users).
