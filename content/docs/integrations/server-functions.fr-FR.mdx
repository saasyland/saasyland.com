Les opérations métier se trouvent dans `src/modules/<table>/use-cases/<operation>.ts`, une opération par fichier. Chacune exporte un `createServerFn` natif avec son middleware, sa validation Zod et son handler, ainsi que les options de requête ou de mutation utilisées par les composants. Une fonction serveur qui n'appartient à aucune table va dans `src/lib` (par exemple `getStarCount` dans `src/lib/github.ts`), et une fonction utilisée par une seule route peut être définie dans le fichier de cette route (`getBlogPosts` dans `src/routes/blog.index.tsx`).

```ts
export const createCategory = createServerFn({ method: "POST" })
  .middleware([authorized({ category: ["create"] })])
  .validator((input: zod.input<typeof categoryZodSchemas.createCategory>) => categoryZodSchemas.createCategory.parse(input))
  .handler(({ data }) =>
    db
      .insert(category)
      .values({
        description: data.description ?? "",
        icon: data.icon ?? "FolderOpen",
        id: v7(),
        kind: data.kind,
        name: data.name,
        visibility: data.visibility ?? "public",
      })
      .returning()
      .get(),
  )

export const createCategoryMutation = mutationOptions({
  mutationFn: (data: Parameters<typeof createCategory>[0]["data"]) => createCategory({ data }),
  mutationKey: CATEGORY_MUTATION_KEYS.CREATE,
})
```

## Règles

- Le middleware s'exécute avant la validation et le handler. Utilisez `authorized(permission?)` pour les opérations protégées, et `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` ou `RATE_LIMITS.TOKEN` pour les opérations publiques sensibles ; voir [Better Auth](/docs/integrations/better-auth).
- Validez l'entrée avec le schéma Zod du module (`<table>.zod.ts`).
- Renvoyez directement les données et levez `AppError(ERROR_CODES.X)` depuis `src/modules/_core/constants/errors.ts` pour les échecs attendus. Les autres erreurs parviennent au client sous la forme `INTERNAL_ERROR`, si bien que les détails du fournisseur restent sur le serveur.
- Les clés de requête et de mutation sont des tuples en lecture seule dans le fichier `<table>.constants.ts` du module, et les clés de requête incluent chaque entrée qui modifie le résultat.
- Gardez les opérations atomiques avec une seule instruction SQL ou `db.batch` ; D1 ne propose pas de transactions interactives.

## Utiliser un cas d'usage

Les composants déploient les options exportées dans `useQuery`, `useSuspenseQuery` ou `useMutation`, traduisent les erreurs avec `useErrorMessage()` de `src/hooks/use-error-message.ts` et invalident les clés de requête du module après une mutation réussie :

```tsx
const deleteUser = useMutation({
  ...deleteUserMutation,
  onError: (error) => {
    toast.error(errorMessage(error))
  },
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: USER_QUERY_KEYS.ALL })
    toast.success(t("feedback.deleteSuccess"))
  },
})
```

Les loaders préchargent les mêmes options de requête dans leur `Promise.all`, de sorte que le rendu serveur et le client partagent une seule entrée de cache.
