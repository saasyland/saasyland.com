---
title: "Roles y permisos"
description: "Define en el archivo de acceso de un área sus declaraciones de permisos y los roles a los que las concede, y compruébalas en los guards de ruta y en las funciones de servidor."
---

El control de acceso usa el plugin admin de Better Auth. Cada área define en `src/areas/<area>.access.ts` las declaraciones de permisos de sus recursos y los roles a los que las concede. `src/areas/access.entries.ts` reúne las áreas, y `src/integrations/better-auth/auth.access.ts` construye a partir de ellas el control de acceso de Better Auth, los roles y la comprobación de permisos, así que la integración de autenticación no nombra ningún área. Los códigos de rol viven en `src/integrations/better-auth/auth.roles.ts`.

## Declaraciones y roles

```ts title="src/areas/auth.access.ts"
const STATEMENTS = {
  admin: ["access"],
  settings: ["manage"],
} as const

export const AUTH_ACCESS = {
  grants: { [ROLE_CODES.ADMIN]: STATEMENTS },
  statements: STATEMENTS,
} as const satisfies AreaAccess
```

```ts title="src/integrations/better-auth/auth.access.ts"
export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...grantsOf(ROLE_CODES.ADMIN), ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole(grantsOf(ROLE_CODES.CUSTOMER)),
}
```

- `APP_STATEMENTS` en `src/integrations/better-auth/auth.access.ts` reúne las declaraciones de todas las áreas, ordenadas por recurso, y falla al arrancar cuando dos áreas declaran el mismo recurso. `grantsOf(role)` reúne lo que cada área concede a ese rol.
- El área de autenticación declara `admin` y `settings`, el área de productos `category` y `product`, el área de cursos `course` y `video`, y el área de pagos `order`.
- `defaultStatements` de Better Auth añade los recursos `user` y `session` (como `user: ["list", "set-role", "ban", "impersonate", "delete"]` y `session: ["list", "revoke"]`).
- Todas las áreas conceden todas sus declaraciones a `admin`, que además recibe las declaraciones de administración de Better Auth; a `customer`, el rol por defecto de los usuarios nuevos, no se le concede ninguna.
- `ROLE_VALUES` tipa la columna `user.role` y los esquemas de rol de `user.zod.ts`.
- `Permission`, el tipo que reciben `authorized` y `hasPermission`, se construye a partir de las declaraciones que definen las áreas, así que una declaración o una acción que ningún área declara no compila.

## Dónde se comprueban los permisos

| Capa                    | Comprobación                                                        |
| ----------------------- | ------------------------------------------------------------------- |
| Guard de ruta           | `requireAdmin` exige `admin: ["access"]` para toda el área `/admin` |
| Función de servidor     | `authorized({ product: ["update"] })` en cada operación protegida   |
| Solo con sesión         | `authorized()` para operaciones sobre los datos del propio usuario  |
| En cualquier otro sitio | `hasPermission({ permission, role })` devuelve un booleano          |

El guard de ruta solo decide qué páginas se renderizan. Las funciones de servidor se pueden llamar directamente por RPC, así que cada una debe comprobar su propio permiso. Ocultar un botón es presentación, no autorización.

## Añade un permiso

1. Añade la acción a las declaraciones del área dueña del recurso, por ejemplo `report: ["read", "export"]` en `src/areas/analytics.access.ts`. Un área nueva añade su archivo y una línea a `src/areas/access.entries.ts`.
2. Concédela en los `grants` del mismo archivo: las áreas conceden todo su `STATEMENTS` a `ROLE_CODES.ADMIN`, y a un rol que deba recibir menos se le concede un subconjunto.
3. Exígela en la función de servidor: `.middleware([authorized({ report: ["export"] })])`.
4. Prueba tanto el caso permitido como el caso `FORBIDDEN`, en `src/areas/__test__/<area>.access.test.ts` del área y en las pruebas del caso de uso.

## Añade un rol

1. Añade el código a `ROLE_CODES` y `ROLE_VALUES` en `auth.roles.ts`.
2. Añádelo a `ROLES` en `auth.access.ts` y concédele declaraciones en los `grants` de las áreas que pueda usar.
3. Añade la etiqueta del rol a `filters.role.options` en `messages/<locale>/pages.admin.users.json` en todos los idiomas.

El cliente de autenticación (`auth.client.ts`) recibe `ac` y `ROLES`, así que las acciones de administración del navegador usan las mismas definiciones.

## Administración de usuarios y sesiones

Los módulos de usuarios y sesiones envuelven la API de administración de Better Auth en casos de uso, cada uno con su propio permiso: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` y otros. Las operaciones sobre los datos del propio usuario, como `revokeSession`, usan `authorized()` y filtran por `context.auth.user.id`.

En local, `bun run db:seed:local` crea un administrador. En preview y en producción, el primer administrador lo crea `bun run admin:grant:preview <email>` o `bun run admin:grant:production <email>`, que solo puede ejecutar alguien con acceso de escritura a esa base de datos D1, para una cuenta que haya verificado su correo; los administradores posteriores se crean en **Administración → Gestión de usuarios** con **Cambiar rol**. Consulta [El primer administrador](/docs/tooling/database#the-first-admin). Un administrador existente también puede invitar a una dirección nueva con el rol `admin`; consulta [Invitaciones](/docs/features/users-admin#invitations).
