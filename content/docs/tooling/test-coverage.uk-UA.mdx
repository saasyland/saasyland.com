## Покриття коду [#code-coverage]

`bun run test:coverage` запускає проєкти Vitest <RepositoryFact name="vitestProjects" /> і завершується помилкою, коли покриття рядків, інструкцій, функцій або гілок для <RepositoryFact name="coverageInclude" /> падає нижче <RepositoryFact name="coverageThreshold" unit="percent" />. Воно не враховує <RepositoryFact name="coverageExclude" />. CI запускає його на кожному pull request і кожному push у `main`, розподіливши на <RepositoryFact name="vitestShards" /> паралельних шарди, покриття яких об’єднується перед перевіркою порогів ([CI/CD](/docs/tooling/ci-cd#checks)).

Набір браузерних тестів до цього числа не входить: Playwright керує зібраним тестовим Worker, і покриття там не збирається. Повне покриття коду означає, що кожен виміряний рядок виконався в тесті, який щось перевірив. Воно не означає, що частини працюють разом через Worker, D1, браузер і провайдерів: специфікація бандла в API ліцензій для CLI надсилає лише відповіді за замовчуванням, тож запит бандла з іншою відповіддю може впасти в production, хоча кожен рядок обробника покрито. Саме це друге питання вимірює покриття сценаріїв.

## Покриття сценаріїв [#flow-coverage]

Перелік сценаріїв містить кожен сценарій сайту, робочого простору клієнта й адміністративної консолі. Кожен розділ оголошує свої сценарії в `e2e/data/<area>.flows.ts`, їх об’єднує `e2e/data/flows.entries.ts`, а типи й константи лежать у `e2e/data/flows.ts` — так само, як розділи оголошують свої сторінки й початкові дані. Сценарій має id, розділ, результат, який має перевірити тест, і один із трьох статусів:

- **покрито**: тест Playwright виконує сценарій наскрізно й перевіряє його результат. Сценарій називає специфікацію та повну назву кожного такого тесту.
- **без покриття**: функція існує, але жоден браузерний тест не виконує її наскрізно. Сценарій пояснює, чого бракує, і називає тести, які виконують його частину, та крок набору тестів шляху клієнта, який його виконує, якщо такі є.
- **треба створити**: функції ще немає, як-от створення продуктів чи зміни цін і знижок, для яких ще немає екрана. Сценарій пояснює, що є замість неї.

`bun run check` запускає `bun run check:flows`, який виводить список набору браузерних тестів через `playwright test --list` у Chromium, як їх запускають pull request, і завершується помилкою, коли:

- сценарій називає специфікацію або назву тесту, яких у наборі немає, — саме так стається, коли тест перейменовують або видаляють;
- сценарій називає тест, який пропущено;
- два сценарії мають однаковий id;
- сценарій без покриття або сценарій, який треба створити, не пояснює чому;
- сценарій називає крок, якого немає в наборі тестів шляху клієнта.

Тож покритий сценарій утрачає свій тест лише тоді, коли той самий pull request змінює його статус і записує причину.

Сьогодні сценаріїв загалом <RepositoryFact name="flows" />: покрито — <RepositoryFact name="flowsCovered" />, без покриття — <RepositoryFact name="flowsMissing" />, ще треба створити — <RepositoryFact name="flowsToBuild" />. Кількість тестів у наборі браузерних тестів — <RepositoryFact name="e2eTests" />, кількість файлів специфікацій — <RepositoryFact name="e2eSpecs" />.

Багато сценаріїв без покриття вже протестовано в межах процесу: [інтеграційні набори](/docs/architecture/testing-architecture#integration-suites) доставляють вебхуки двічі, не в тому порядку й із хибними підписами, повертають кошти й відкликають ліцензії та впираються в ліміти частоти запитів API ліцензій для CLI. Сценарій вважається покритим лише тоді, коли браузерний тест виконує його на зібраному Worker, тож доки такого тесту немає, ці сценарії вважаються сценаріями без покриття.

## Набір тестів шляху клієнта [#journey-suite]

[Набір тестів шляху клієнта](/docs/tooling/playwright#journey-suite) купує кожен план на preview у пісочниці Polar тестовою карткою Stripe, чекає, доки вебхуки видадуть ключ, користується опублікованим CLI на стількох пристроях, скільки дозволяє план, і повертає кошти за замовлення, а також підвищує план Core до Complete за доплату різниці й повертає кошти за це підвищення, щоб ліцензія знову стала планом Core. Він виконує <RepositoryFact name="flowsInJourney" /> зі сценаріїв без покриття, які таблиця сценаріїв без покриття називає в останньому стовпці. `journey.yml` має запускати його щоночі за розкладом, а запустити його можна й вручну ([CI/CD](/docs/tooling/ci-cd#journey-suite)), але жоден pull request на нього не чекає, тож ці сценарії вважаються сценаріями без покриття. Жоден запуск ще не пройшов: workflow потребує двох речей, які може налаштувати лише власник, і їх поки що немає:

1. **Секрети.** Середовище GitHub `Preview` містить `POLAR_ACCESS_TOKEN` — токен пісочниці з областями доступу `orders:read`, `refunds:write`, `benefits:read` і `license_keys:read`; `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE` і `POLAR_PRODUCT_ID_AGENCY` — продукти в пісочниці; і `RESEND_API_KEY` — ключ із повним доступом, який може читати листи, що надсилає preview. `POLAR_SERVER` дорівнює `sandbox` і не потребує секрету.
2. **Пісочниця.** Організація в пісочниці відповідає коду, що перевіряє `bun run polar:verify:preview`, а її вебхук указує на preview.

## Заплановано [#planned]

- **Мутаційне тестування.** Інструмент мутаційного тестування змінює код, що тестується, по одному оператору чи умові за раз і рахує зміни, яких не помічає жоден тест. Так вимірюється, чи тести перевіряють результати, чи лише виконують рядки. Воно почалося б із коду ліцензій, платежів, ціноутворення, доступу до курсів і автентифікації. Поки що нічого не налаштовано.
- **Покриття коду в браузері.** Збирання покриття V8, поки набір браузерних тестів запускає зібраний застосунок, показало б, до якого коду не доходить жоден браузерний тест. Про нього звітували б поруч із числом Vitest, не додаючи до нього, і без обов’язкової перевірки. Поки що нічого не налаштовано.
