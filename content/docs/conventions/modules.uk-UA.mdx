`src/modules/<table>/` існує лише для справжньої таблиці бази даних. Папка віддзеркалює схему Drizzle, тож її створення стверджує, що така таблиця існує. Код, який обслуговує функціональність без власної таблиці, розміщується деінде: серверна функція, що читає GitHub або колекцію документації, лежить у `src/lib/<topic>.ts` або в єдиному маршруті, який її використовує, а налаштування постачальника — у `src/integrations/<vendor>`.

Модулі: <RepositoryFact name="modules" />. `license` володіє двома таблицями, `license` і `revoked_license_order`. `_core` — не модуль: він містить лише основу, на якій побудовано кожен модуль, тобто коди помилок, константи HTTP, каталоги локалей, часових поясів, країн і валют, поля Zod і вхідні дані пагінації, порядку, пошуку й періоду. Константи, на яких не побудовано жодного модуля, лежать у `src/data`, а загальні допоміжні функції — у `src/lib`.

## Будова

Еталоном є `src/modules/course`. Модуль містить такі файли, усі названі за таблицею:

| Файл                         | Містить                                                                                              |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| `<table>.schema.ts`          | Таблицю Drizzle, її індекси та зв’язки                                                               |
| `<table>.constants.ts`       | Об’єкти доменних значень, їхні кортежі переліків, ключі запитів, ключі мутацій і обмеження модуля    |
| `<table>.zod.ts`             | По одній схемі вхідних даних на операцію, експортованих одним об’єктом `<table>ZodSchemas`           |
| `<table>.types.ts`           | Один інтерфейс, названий за модулем                                                                  |
| `<table>.utils.ts`           | Допоміжні функції для таблиці, чисті й безпечні для браузера, якщо вони не читають середовище Worker |
| `<table>.<concern>.ts`       | Ще один аспект таблиці, як-от `lesson.access.ts` або `video.delivery.ts`                             |
| `use-cases/<verb>-<noun>.ts` | Одну операцію, названу за її серверною функцією                                                      |
| `__test__/`                  | Тести й фікстури для наведених вище файлів                                                           |

## Схема

```ts title="src/modules/course/course.schema.ts"
export const course = sqliteTable(
  "course",
  {
    cover: text("cover"),
    icon: text("icon", { enum: COURSE_ICONS }).notNull().default(COURSE_ICON.BOOK_OPEN),
    id: text("id").primaryKey(),
    kind: text("kind", { enum: COURSE_KINDS }).notNull().default(COURSE_KIND.COURSE),
    level: text("level", { enum: COURSE_LEVELS }).notNull().default(COURSE_LEVEL.BEGINNER),
    outcomes: text("outcomes", { mode: "json" })
      .$type<LocalizedList>()
      .notNull()
      .default(sql`'{}'`),
    position: integer("position").notNull().default(0),
    prerequisites: text("prerequisites", { mode: "json" })
      .$type<LocalizedList>()
      .notNull()
      .default(sql`'{}'`),
    slug: text("slug", { length: SLUG_MAX_LENGTH }).notNull().unique(),
    status: text("status", { enum: COURSE_STATUSES }).notNull().default(COURSE_STATUS.DRAFT),
    summary: text("summary", { mode: "json" }).$type<LocalizedText>().notNull(),
    title: text("title", { mode: "json" }).$type<LocalizedText>().notNull(),
    ...timestamps(),
  },
  (table) => [index("course_status_position_idx").on(table.status, table.position)],
)
```

- Стовпці мають назви в camelCase у TypeScript і в snake_case у SQL. Ключі відсортовано, як цього вимагає лінтер, а `...timestamps()` іде останнім записом.
- `createdAt` і `updatedAt` беруться з `timestamps()` у `src/integrations/drizzle-orm/drizzle.columns.ts`: це мілісекунди, які SQLite заповнює під час вставлення, а `updatedAt` оновлюється під час кожного оновлення. Ніколи не записуйте їх вручну. `lesson_progress` потрібен лише другий, тому він бере `updatedAt: timestamps().updatedAt`. Дві таблиці не мають часових міток: `rate_limit` зберігає короткоживучі лічильники, які мають власний `expiresAt` і змінюються з кожним запитом, а `revoked_license_order` один раз записує кожне повернене замовлення Polar за його ID.
- Первинні ключі текстові. Сценарій використання, що вставляє рядок, заповнює ключ значенням UUID v7 (`v7()` з `uuid`); [таблиця-дзеркало постачальника](#tables-that-mirror-a-provider) натомість бере ідентифікатор постачальника.
- Стовпці-переліки отримують кортеж, побудований з об’єкта констант модуля, а не список літералів. Кортеж лежить поруч з об’єктом у `<table>.constants.ts`, бо його також читають схеми Zod і браузер, а цей файл нічого не імпортує з Drizzle.
- Текст, який відвідувач читає кількома мовами, — це JSON-стовпець `LocalizedText`, який валідує `localizedTextSchema` і читає `localize(text, locale)` з `src/modules/_core/utils/localized-text.ts`.
- Нову таблицю реекспортують з `src/integrations/drizzle-orm/drizzle.schemas.ts`, а її міграцію генерують командою `bun run db:generate`. Див. [Міграції бази даних](/docs/guides/database-migrations).

## Таблиці-дзеркала постачальника [#tables-that-mirror-a-provider]

`order` і `subscription` зберігають копії замовлень і підписок Polar, записані лише з даних Polar і ніколи не змінювані вручну. Таблиця-дзеркало слідує за постачальником там, де наведені вище правила кажуть інакше:

- Її первинний ключ — ідентифікатор постачальника, текстовий стовпець довжиною `POLAR_ID_MAX_LENGTH`, а стовпці мають назви полів постачальника, як-от `customer_id`, `product_id` і `subscription_id`. Наша власна таблиця, що посилається на постачальника, натомість додає до назви префікс, як `license.polar_order_id`.
- Власні часові позначки постачальника лежать поряд із `...timestamps()`. `placedAt` — момент, коли Polar створив замовлення, а `changedAt` — версія запису Polar, яку зберігає рядок: його `modified_at` або, поки запис жодного разу не змінювався, його `created_at`. `createdAt` і `updatedAt` і далі фіксують, коли D1 записала рядок.
- Стовпці-переліки отримують кортежі значень постачальника: `ORDER_STATUSES` в `order.constants.ts` перелічує `POLAR_ORDER_STATUS` з `src/integrations/polar/polar.constants.ts`, а тест типів не проходить, коли SDK називає значення, якого немає в кортежі.
- Жоден стовпець, крім `createdAt` і `updatedAt`, не має значення за замовчуванням, бо кожне значення надходить від постачальника.
- `user_id` має `ON DELETE SET NULL`: видалення облікового запису зберігає його замовлення й підписки і прибирає лише зв’язок.

`order` — ключове слово SQL. Drizzle бере в лапки кожен ідентифікатор, тож його запитам нічого не потрібно; сирий SQL називає таблицю через об’єкт схеми, як `${order}` у шаблоні `sql`, і ніколи як просто `order`.

- Кожен ключ запиту починається з префікса `ALL` модуля, тож один виклик `invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL })` оновлює все, що віддає модуль. Див. [Отримання даних і кешування](/docs/conventions/data-fetching).
- Ключі мутацій складаються з назви модуля й назви серверної функції.
- Довжини стовпців і вхідних даних отримують назву тут і є спільними для схеми та схеми Zod, як-от `VIDEO_TITLE_MAX_LENGTH` у `video.constants.ts`.
- `<MODULE>_VALIDATION_PARAMS` містить числа, які підставляються в повідомлення валідації, як-от `{ slugTooLong: { max: SLUG_MAX_LENGTH } }`.
- `scripts/repository-facts.ts` читає деякі файли констант, як-от `license.constants.ts`, поки Vite завантажує свою конфігурацію, коли аліас `~` ще не розпізнається. Такий файл імпортує інші вихідні файли за відносним шляхом, як `license.constants.ts` імпортує `POLAR_WEBHOOK_EVENT` з `../../integrations/polar/polar.constants.ts`; імпорти лише типів стираються, тож у них аліас можна залишити.

## Zod-схеми

```ts title="src/modules/chapter/chapter.zod.ts"
import * as zod from "zod"

import { localizedTextSchema, optionalLocalizedTextSchema } from "~/src/modules/_core/utils/localized-text"
import { idField } from "~/src/modules/_core/utils/zod-fields"

const chapterIdInput = zod.object({
  chapterId: idField,
})

const chapterFields = zod.object({
  summary: optionalLocalizedTextSchema,
  title: localizedTextSchema,
})

const createChapter = chapterFields.extend({ courseId: idField })

const deleteChapter = chapterIdInput

const updateChapter = chapterFields.extend(chapterIdInput.shape)

export const chapterZodSchemas = {
  createChapter,
  deleteChapter,
  updateChapter,
}
```

- `<table>.zod.ts` імпортує `* as zod from "zod"` і експортує єдиний об’єкт, ключі якого — назви операцій.
- Форми валідують дані тими самими схемами в браузері, тому `<table>.zod.ts` нічого не імпортує ні з Drizzle, ні з `.schema.ts`. Кортежі переліків і довжини беруться з `<table>.constants.ts`, який імпортує й таблиця, тож стовпець і схема спираються на одне визначення. Клієнтська збірка завершується помилкою, коли `drizzle-orm` потрапляє в браузер; див. [Тримайте ORM поза браузером](/docs/conventions/performance#keep-the-orm-out-of-the-browser).
- Жодну схему Zod не виводять із таблиці: ніщо не валідує цілий рядок під час виконання, а типи рядків в інтерфейсі модуля беруться з `$inferSelect` і `$inferInsert`.
- Поля беруться з `src/modules/_core/utils/zod-fields.ts` (`idField`, `localeField`, `slugField`) і зі спільних фрагментів у тому самому файлі; їх ніколи не оголошують заново для кожної схеми.
- Посторінкові списки повторно використовують `paginationSchema`; операції з одним записом приймають об’єкт, як-от `{ courseId }`, а не голий рядок.
- Повідомлення про помилки — це ключі перекладу (`{ message: "slugInvalid" }`), які рендеряться з простору імен `<table>.validations` модуля. Див. [Форми та таблиці](/docs/conventions/forms-and-tables).

## Інтерфейс модуля

`<table>.types.ts` експортує рівно один інтерфейс, названий за модулем, ключі якого віддзеркалюють об’єкт Zod:

```ts title="src/modules/lesson/lesson.types.ts"
export interface Lesson {
  select: typeof lesson.$inferSelect
  insert: typeof lesson.$inferInsert
  page: LessonPage
  detail: LessonPage["lesson"]
  attachment: LessonPage["lesson"]["attachments"][number]
  createLesson: zod.input<typeof lessonZodSchemas.createLesson>
  deleteLesson: zod.input<typeof lessonZodSchemas.deleteLesson>
  getLesson: zod.input<typeof lessonZodSchemas.getLesson>
  getLessonPlayback: zod.input<typeof lessonZodSchemas.getLessonPlayback>
  getLessonTitle: zod.input<typeof lessonZodSchemas.getLessonTitle>
  removeLessonVideo: zod.input<typeof lessonZodSchemas.removeLessonVideo>
  replaceLessonVideo: zod.input<typeof lessonZodSchemas.replaceLessonVideo>
  searchLessons: zod.input<typeof lessonZodSchemas.searchLessons>
  setLessonFormat: zod.input<typeof lessonZodSchemas.setLessonFormat>
  updateLesson: zod.input<typeof lessonZodSchemas.updateLesson>
}
```

Серверні функції, опції мутацій і форми типізують свої вхідні дані як `Lesson["createLesson"]`. Коли ви додаєте схему до `<table>.zod.ts`, додайте її ключ сюди в тій самій зміні. Ніколи не виводьте тип вхідних даних через `Parameters<typeof fn>[0]` і ніколи не оголошуйте локальний псевдонім чи другий інтерфейс `LessonInput`. Коли компонентам потрібна форма даних, яку повертає читання, інтерфейс теж дає їй назву, а сам тип виводиться з серверної функції: `Course["listRow"]` — це `Awaited<ReturnType<typeof getCourses>>["rows"][number]`.

## Сценарії використання

Кожен файл у `use-cases/` містить одну операцію, названу за її серверною функцією в kebab-case: `get-course-editor.ts` експортує `getCourseEditor` і `courseEditorQuery`, `update-course.ts` експортує `updateCourse` і `updateCourseMutation`. Шаблон, його middleware та помилки описано на сторінці [Серверні функції та помилки](/docs/conventions/server-functions). [Каталог модулів](/docs/reference/modules) і [матриця дозволів](/docs/reference/permissions) показують таблиці кожного модуля, його сценарії використання й виклик `authorized` кожного з них, які `collectModuleTables` у `scripts/repository-facts.ts` читає з коду під час збирання, тож новий сценарій використання з'являється там без правок, а `src/__test__/module-tables.test.ts` завершується помилкою, коли каталог пропускає файл модуля поза стандартним набором.

Сценарій використання, який виконується лише на сервері й викликається хуком Better Auth або вебхуком Polar, а не браузером, — це звичайна `async`-функція у файлі, що починається з `import "@tanstack/react-start/server-only"`, як-от `license/use-cases/grant-license.ts` і модулі надсилання листів `send-verify-email.ts`, `send-reset-password-email.ts` та `send-change-email-confirmation-email.ts`.

| `video/video.playback.ts`, `video/video.files.ts` | Підписування URL-адрес відтворення; ключі об’єктів і типи вмісту                                                   |
| `video/video.encoding.ts`                         | Варіанти роздільності, довжина сегментів і налаштування якості кодування відео                                     |
| `account/account.links.ts`                        | Посилання в листах облікового запису, побудовані з callback URL                                                    |

Файл, який ніколи не має потрапити в браузерний бандл, починається з `import "@tanstack/react-start/server-only"`, як `course.outline.ts`, `course.delivery.ts`, `course.objects.ts`, `course.transfer.ts`, `lesson.viewer.ts`, `lesson-attachment.delivery.ts`, `lesson-attachment.objects.ts`, `license.webhooks.ts`, `license.api.ts`, `license.delivery.ts`, `license.ppp.ts`, `license.upgrade-price.ts`, `order.checkout.ts`, `order.utils.ts`, `withdrawal.contracts.ts`, `account.links.ts`, `video.delivery.ts` і `license.utils.ts` (який читає ідентифікатори продуктів Polar, `POLAR_PRODUCT_IDS`, із середовища Worker). Чисті файли, як-от `lesson.access.ts` і `course.utils.ts`, нічого серверного не імпортують, тож їх можуть використовувати компоненти й тести.
