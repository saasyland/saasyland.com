Zwei Zahlen aus den letzten zwölf Monaten beschreiben den Stand der KI-gestützten Entwicklung besser als jeder Benchmark.

Die erste: **84 % der Entwickler nutzen inzwischen KI-Tools oder planen dies** in ihrem Entwicklungsprozess, nach 76 % im Vorjahr ([Stack Overflow Developer Survey 2025](https://survey.stackoverflow.co/2025/ai)).

Die zweite: In derselben Umfrage **misstrauen inzwischen mehr Entwickler aktiv der Genauigkeit von KI-Ausgaben (46 %), als ihr vertrauen (33 %)**. Nur 3 % geben an, ihr in hohem Maß zu vertrauen, und das Vertrauen in die Genauigkeit ist im Jahresvergleich gesunken statt gestiegen.

Die Nutzung stieg. Das Vertrauen sank. Die Branche hat darauf reagiert, indem sie nach einem besseren Agenten sucht. Deshalb reiht jeder Vergleichsartikel, den Sie dieses Jahr gelesen haben, elf Tools in einer Rangliste auf, die schon falsch ist, bevor Sie zu Ende gelesen haben.

Dieser Artikel vertritt eine andere These und gibt Ihnen dann eine Möglichkeit, sie an Ihrer eigenen Codebasis zu testen. Das Modell ist nicht die Variable, die Ihr Ergebnis bestimmt. **Ihr Repository ist es.** Ein Agent ist eine Schleife: vorschlagen, beobachten, korrigieren. Was er beobachtet, stammt aus Ihrer Codebasis. Wenn Ihre Codebasis einer falschen Änderung nicht schnell widersprechen kann, hat der Agent nichts, woran er sich korrigieren könnte. Also optimiert er auf das Einzige, was ihm bleibt: Plausibilität.

Das ist der ganze Mechanismus hinter dem Versagen, das alle beschreiben.

## Was ist ein KI-Coding-Agent?

Ein KI-Coding-Agent ist ein Programm, das eine Codebasis liest, eine Änderung plant, Dateien bearbeitet, Befehle ausführt und auf die Ergebnisse reagiert, ohne dass ein Mensch jeden Schritt steuert. Das unterscheidet ihn von einem Autocomplete-Assistenten: Der Agent schließt seine eigene Schleife, indem er Ihre Tests, Ihre Typprüfung und Ihren Build ausführt und sich dann anhand dessen korrigiert, was sie zurückgeben.

Dieser letzte Halbsatz ist das ganze Thema dieses Artikels. Die Obergrenze eines Agenten wird durch die Qualität und die Latenz der Signale bestimmt, die er beobachten kann. Ein Modell, das in einem Benchmark gut abschneidet, und eines, das schlecht abschneidet, erzeugen beide selbstsicheren, plausiblen, falschen Code in einem Repository, das nichts zu erwidern hat.

Irgendetwas in der Schleife signalisierte ihnen, dass alles gut lief, obwohl es das nicht tat.

### Die drei Fehlermuster

Jede Studie misst ein anderes Symptom desselben fehlenden Signals. Wer sie benennt, kann sie leichter aufspüren.

**Plausibler Drift.** Der Agent erzeugt Code, der sich korrekt liest, Ihre Namenskonventionen verwendet und das Falsche tut. Das ist die Kategorie „fast richtig“, die 45 % der Entwickler als ihr größtes Ärgernis nannten. Sie überlebt, weil nichts im Repository ihr widerspricht. Sie zu prüfen kostet mehr, als die Änderung selbst zu schreiben, denn eine falsche Antwort, die richtig aussieht, ist schwerer zurückzuweisen als eine falsche Antwort, die falsch aussieht.

**Stille Duplizierung.** Der Agent braucht eine Hilfsfunktion, findet die bereits vorhandene nicht und schreibt eine zweite. Multiplizieren Sie das mit jedem Feature, und Sie erhalten den von GitClear gemessenen Anstieg duplizierter Blöcke um 81 % gegenüber 2023. Duplizierte Blöcke sind keine Stilfrage: Die Forschung bringt geklonten Code mit **15 % bis 50 % mehr Defekten** in Verbindung. Der Agent hat sich nicht für die Duplizierung entschieden. Er konnte nicht beobachten, dass das Original existierte.

**Selbstsichere Regression.** Eine Änderung besteht alle vorhandenen Prüfungen, wird gemergt und macht etwas kaputt, das keine Prüfung abgedeckt hat. Das ist der von DORA gemessene Stabilitätsrückgang um 7,2 %, ausgedrückt als ein einzelner Vorfall. Der Output stieg, das Gate bewegte sich nicht, also erreichten pro Zeiteinheit mehr ungetestete Änderungen die Produktion.

Alle drei haben dieselbe Wurzel. Dem Agenten konnte nicht schnell genug „Nein“ gesagt werden, oder überhaupt nicht.

## Time to No: die Metrik, die die Qualität der Agentenausgabe vorhersagt

**Time to No ist die Zeit, die Ihr Repository braucht, um einem KI-Coding-Agenten zu sagen, dass seine Änderung falsch ist.** Gemessen wird ab dem Moment, in dem der Agent aufhört zu schreiben, bis zu dem Moment, in dem ein automatisiertes Signal ihm widerspricht. Ein Repository mit strikten Typen, einem Coverage-Gate und einem einzigen Prüfbefehl antwortet in Sekunden. Ein Repository ohne sie antwortet im Code-Review, in der Produktion oder nie.

Time to No ist wichtig, weil die Schleife eines Agenten so aufgebaut ist: Der Agent schlägt vor, beobachtet und korrigiert. Korrigieren kann er nur anhand von Beobachtungen, die er **innerhalb seines eigenen Laufs** erreicht. Alles, was langsamer ist, ist kein Feedback für den Agenten. Es ist Aufräumarbeit für Sie.

Hier ist die Leiter, mit den Signalen sortiert danach, wie schnell sie eintreffen.

| Signal                                   | Was es erkennt                                        | Typische Time to No       | Erreicht den Agenten? |
| ---------------------------------------- | ----------------------------------------------------- | ------------------------- | :-------------------: |
| Language Server im Editor                | Falsche Struktur, fehlendes Feld, fehlerhafter Import | Unter 1 Sekunde           |          Ja           |
| `tsc --strict`                           | Typbrüche im gesamten Projekt                         | 5 bis 30 Sekunden         |          Ja           |
| Linter und Formatter                     | Abweichungen von Konventionen, unsichere Muster       | 5 bis 20 Sekunden         |          Ja           |
| Unit- und Integrationstests              | Falsches Verhalten auf einem abgedeckten Pfad         | 30 Sekunden bis 3 Minuten |          Ja           |
| Coverage-Schwelle                        | Verhalten, das ganz ohne Test hinzugefügt wurde       | Im selben Lauf            |          Ja           |
| End-to-End-Tests in einem echten Browser | Defekter Ablauf über mehrere Schichten                | 2 bis 10 Minuten          |       Meistens        |
| CI im Pull Request                       | Alles oben Genannte, auf einer sauberen Maschine      | 5 bis 15 Minuten          |         Nein          |
| Menschliches Code-Review                 | Absicht, Design, Urteilsvermögen                      | Stunden bis Tage          |         Nein          |
| Produktion                               | Alles, was niemand geprüft hat                        | Tage bis nie              |         Nein          |

Die Grenze zwischen „Meistens“ und „Nein“ ist die entscheidende. **Der Agent lernt nur aus den Zeilen, die er innerhalb seiner eigenen Schleife erreicht.** Alles unterhalb dieser Grenze ist Feedback für Sie, nicht für ihn, und jede Stunde davon ist eine Stunde, in der Sie dafür bezahlen, Output zu prüfen, den eine Maschine kostenlos hätte zurückweisen können.

Das stellt die gesamte Tooling-Frage in ein neues Licht. Der Wechsel von einem Frontier-Agenten zum anderen verändert, wie gut die Vorschläge sind. Eine niedrigere Time to No verändert, wie viele falsche Vorschläge Sie überhaupt erreichen. Der zweite Hebel ist größer, er wirkt kumulativ, und er setzt sich nicht zurück, wenn nächsten Monat ein neues Modell erscheint.

<Callout type="warn" title="Die unbequeme Konsequenz">

Ein leistungsfähigerer Agent in einem Repository mit hoher Time to No liefert schlechtere Ergebnisse als ein weniger leistungsfähiger Agent in einem Repository mit niedriger Time to No. Er schreibt mehr Code, schneller, mit demselben Anteil falscher Antworten, und jede einzelne davon landet in Ihrer Review-Warteschlange, statt in der Schleife zu sterben.

</Callout>

### So messen Sie Ihre eigene Time to No

Sie brauchen keine Instrumentierung. Sie brauchen eine absichtlich fehlerhafte Änderung.

<Steps>

<Step>

**Wählen Sie eine echte Invariante.** Etwas, von dem Ihr Produkt tatsächlich abhängt: ein Webhook, der nicht doppelt abbuchen darf, eine Berechtigungsprüfung auf einer Admin-Route, eine Währungsumrechnung.

</Step>

<Step>

**Brechen Sie sie auf die kleinstmögliche Weise.** Kehren Sie einen Boolean um. Entfernen Sie ein `await`. Ändern Sie einen Vergleichsoperator. Brechen Sie nicht die Syntax, denn Syntaxfehler fängt alles ab, und sie beweisen nichts.

</Step>

<Step>

**Starten Sie eine Stoppuhr und führen Sie Ihren Prüfbefehl aus.** Den, den ein Agent ausführen würde. Wenn Sie keinen einzelnen Befehl haben, den ein Agent ausführen könnte, ist Ihre Time to No bereits „menschliches Review“, und Sie können die Übung hier beenden.

</Step>

<Step>

**Notieren Sie, wann etwas fehlschlägt, und was.** Nicht, wann Sie es bemerken. Sondern wann die Maschine widerspricht, mit einer Meldung, die konkret genug ist, dass ein Agent darauf reagieren könnte.

</Step>

<Step>

**Wiederholen Sie das für vier oder fünf Invarianten in verschiedenen Schichten.** Auth, Abrechnung, Datenzugriff, i18n, der Adminbereich. Die langsamste ist Ihre echte Time to No, denn in dieser Schicht richten Agenten den größten Schaden an.

</Step>

</Steps>

Die meisten Teams, die das ehrlich durchführen, finden mindestens eine Schicht, in der die Antwort „nichts ist fehlgeschlagen“ lautet. In dieser Schicht hat Ihr Agent Fiktion geschrieben.

## Die Agent-Ready Repository Scorecard

Zehn Prüfungen, bewertet mit 0, 1 oder 2 Punkten, maximal 20. Bewerten Sie Ihr eigenes Repository. Das dauert etwa fünfzehn Minuten, und das Ergebnis ist nützlicher als jeder Benchmark-Vergleich, weil es um die Codebasis geht, in der Sie tatsächlich arbeiten.

### Kontext: Findet der Agent die Wahrheit?

**1. Eine Anweisungsdatei für Agenten existiert und ist aktuell.**

`AGENTS.md` wurde im August 2025 unter Beteiligung von OpenAI, Google, Cursor und Factory als offene Spezifikation formalisiert, im Dezember 2025 an die Agentic AI Foundation der Linux Foundation übergeben und steckt heute in mehr als 60.000 öffentlichen Repositories, gelesen von über 30 Agenten.

- **0**: Keine Anweisungsdatei. Jeder Agent beginnt bei null und leitet Ihre Konventionen aus den Dateien ab, die er zufällig öffnet.
- **1**: Eine Datei existiert, aber sie besteht aus Fließtext, den der Agent interpretieren muss, oder sie hat sich von der Realität entfernt.
- **2**: Sie nennt die Befehle, die Grenzen und die Konventionen in weniger als 200 Zeilen und kann nicht veralten, weil die CI genau die Befehle ausführt, die sie nennt.

**2. Typen sind Verträge, keine Dekoration.**

- **0**: `any` ist an der Tagesordnung. Externe Daten gelangen ungeprüft ins System.
- **1**: Striktes TypeScript, aber Grenzen (HTTP-Bodys, Umgebungsvariablen, Webhook-Payloads, Datenbankzeilen) wird vertraut, statt sie zu parsen.
- **2**: Striktes TypeScript ohne `any`, dazu Schemavalidierung an jeder externen Grenze. Eine falsche Struktur scheitert am Rand, in unter einer Sekunde, mit einer Meldung, die das Feld nennt.

**3. Für jedes Muster gibt es genau ein kanonisches Beispiel.**

Agenten arbeiten durch Nachahmung des nächsten Nachbarn. Sie kopieren das Ähnlichste, das sie finden. Wenn Ihr Repository drei Arten enthält, Daten zu laden, wählt der Agent zufällig eine aus, und die Chance, dass es die gewünschte ist, liegt bei eins zu drei.

- **0**: Mehrere konkurrierende Muster für dieselbe Aufgabe, alle aktiv in Gebrauch.
- **1**: Eine dokumentierte Präferenz, die nichts durchsetzt.
- **2**: Ein implementiertes Beispiel pro Muster, sodass der nächste Nachbar immer der richtige Nachbar ist.

### Verifikation: Kann das Repository Nein sagen?

**4. Ein Befehl führt alles aus.**

- **0**: Ein README-Absatz, der Schritte in einer bestimmten Reihenfolge beschreibt.
- **1**: Mehrere Skripte, und Sie müssen wissen, welches wann auszuführen ist.
- **2**: Ein einziger Befehl, der Typen prüft, lintet, testet und berichtet und mit 0 oder 1 endet. Ein Agent kann ihn ausführen, ohne dass man ihm erklärt, wie.

**5. Coverage ist ein Gate, kein Bericht.**

- **0**: Keine Coverage-Messung.
- **1**: Coverage wird gemessen und auf einem Badge angezeigt, wegen dem niemand einen Merge blockiert.
- **2**: Eine Schwelle, die den Build fehlschlagen lässt. Neues Verhalten ohne Test kann nicht gemergt werden, also kann der Agent kein ungetestetes Verhalten hinzufügen, selbst wenn er wollte.

**6. Kritische Pfade laufen in einem echten Browser.**

- **0**: Keine End-to-End-Tests.
- **1**: Nur jsdom oder gemockte Umgebungen, die grün sind, während das Echte kaputt ist.
- **2**: Echte Browser-Engines, die Registrierung, Checkout und den Webhook-Pfad durchlaufen.

**7. Die Typprüfung kennt null Toleranz.**

- **0**: Typfehler sind normales Hintergrundrauschen.
- **1**: Fehler werden in einem Backlog verfolgt.
- **2**: Ein einziger Fehler führt zu einem Exit-Code ungleich null und blockiert den Merge. Agenten reagieren auf binäre Signale; eine Zahl, die „ein bisschen gestiegen“ ist, ist kein Signal.

### Grenzen: Kann der Agent sie einhalten?

**8. Architekturregeln werden durch Tooling durchgesetzt.**

- **0**: Konventionen existieren im Kopf eines Senior Engineers.
- **1**: In einem Wiki dokumentiert, im Review durchgesetzt.
- **2**: Eine Regel für Importgrenzen lässt den Build fehlschlagen, wenn eine Schicht dorthin greift, wo sie nicht hingehört. Der Agent lernt Ihre Architektur, indem er gegen die Wand läuft, in Sekunden, und nicht, indem er darüber liest.

**9. Gefährliche Bereiche sind ausdrücklich tabu.**

- **0**: Nichts ist gekennzeichnet. Migrationen, Secrets und Abrechnungslogik sind so leicht bearbeitbar wie eine Button-Komponente.
- **1**: Informelle Warnungen, die eine frische Agenten-Session nie gesehen hat.
- **2**: Migrationen, Secrets, Abrechnungs-Webhooks und Infrastruktur sind in der Anweisungsdatei als Bereiche benannt, die nur mit menschlichem Review geändert werden, und durch CI geschützt statt durch Hoffnung.

### Überprüfbarkeit: Kann ein Mensch es im Nachhinein prüfen?

**10. Jede Qualitätsaussage lässt sich einem Befehl zuordnen.**

- **0**: Qualitätsaussagen stehen als Adjektive im README.
- **1**: Manche Aussagen lassen sich prüfen, wenn man weiß, wo man suchen muss.
- **2**: Jede Aussage lässt sich einem Befehl zuordnen, der den Nachweis neu erzeugt. Erst das macht die Arbeit eines Agenten überhaupt prüfbar: Sie prüfen nicht, ob er sorgfältig war, sondern ob sich der Nachweis weiterhin erzeugen lässt.

    Agenten helfen auf gut abgedeckten Pfaden und driften überall sonst ab. Der Review-Aufwand steigt proportional zum Output, was den
    größten Teil des Gewinns zunichtemacht.
  </Card>
  <Card title="0 bis 10 — agentenfeindlich">
    Der Agent wird sich schnell anfühlen und falschliegen, und Sie erfahren es spät. Genau hier liegt das METR-Ergebnis.
  </Card>
</Cards>

Wenn Sie unter 11 Punkten liegen, ist die lohnendste Arbeit, die Ihnen in diesem Quartal offensteht, nicht die Bewertung von Agenten. Es sind die Prüfungen 4, 5 und 7, die drei günstigsten Wege, Tausende Sekunden Time to No zurückzukaufen.

## Die Agentenlandschaft 2026 im echten Vergleich

Zuerst die Verbreitung, denn sie ist die einzige Zahl hier mit einer belastbaren Quelle. Eine JetBrains-AI-Pulse-Umfrage unter mehr als 10.000 Entwicklern im Januar 2026 ergab, dass **74 % ein spezialisiertes KI-Entwicklungswerkzeug eingeführt hatten**. GitHub Copilot führte bei der Nutzung am Arbeitsplatz mit 29 %, Cursor und Claude Code lagen mit jeweils 18 % gleichauf.

Beachten Sie, was diese Verteilung bedeutet: Kein Werkzeug hat eine Mehrheit, die meisten Teams nutzen zwei oder drei, und der Abstand zwischen Platz eins und Platz drei ist kleiner als der zwischen einem guten und einem schlechten Repository.

<Callout type="info" title="Warum dieser Artikel keine Rangliste enthält">

Wir veröffentlichen keine Benchmark-Ranglisten, und der Grund ist nicht Diplomatie.

Die Spitzenwerte auf SWE-bench Verified und Terminal-Bench haben dieses Jahr wiederholt den Besitzer gewechselt, manchmal innerhalb desselben Monats. Jede heute veröffentlichte Tabelle mit Werten ist eine Tabelle, die einmal gestimmt hat. Schlimmer noch: Die Zahl ist für Ihre Entscheidung nahezu nutzlos. Benchmark-Aufgaben bringen einen Verifier mit, und genau der fehlt den meisten Produktions-Repositories. Ein Benchmark misst einen Agenten unter idealen Bedingungen, die Sie nicht nachgebildet haben.

Die beiden Dinge, die stabil genug sind, um darauf zu planen, sind das **Harness** (wie das Werkzeug Kontext zusammenstellt, wo es läuft, wie es um Erlaubnis fragt) und **Ihr Repository**. Genau die vergleicht dieser Abschnitt.

</Callout>

### Terminal-native Agenten

**Beispiele: Claude Code, OpenAI Codex CLI, OpenCode, Aider.**

Sie laufen als Prozess in Ihrer Shell, mit den Berechtigungen Ihrer Shell. Die Kontextzusammenstellung ist aktiv statt beiläufig: Der Agent führt `grep` aus, öffnet Dateien, führt Ihren Testbefehl aus und liest, was zurückkommt. Weil sie dort leben, wo Ihr Tooling lebt, schließen sie die Verifikationsschleife am direktesten. Wenn Sie einen einzigen Prüfbefehl haben, nutzt ein Terminal-Agent ihn, ohne dass man ihn zweimal bitten muss.

- **Am besten für:** Teams, deren Engineering-Kultur bereits im Terminal lebt, lange Änderungen über viele Dateien, Arbeit, bei der die Testsuite das wichtigste Feedback-Signal ist.
- **Das kostet Sie:** standardmäßig kein visuelles Diff-Review, die Review-Disziplin muss also von Ihnen oder von der CI kommen. Die Berechtigungsmodelle unterscheiden sich stark, und eine freizügige Konfiguration in einem Repository ohne Grenzen ist genau die Kombination, die selbstsichere Regressionen erzeugt.
- **Bemerkenswert:** Die Open-Source-Optionen in dieser Gruppe (OpenCode, Aider) lassen Ihnen die Wahl von Modell und Anbieter. Das ist wichtig, wenn Sie Vorgaben zur Datenresidenz haben oder die Kosten pro Token direkt steuern wollen.

### IDE-native Agenten

**Beispiele: Cursor, GitHub Copilot, Windsurf, Cline, JetBrains Junie.**

Sie leben im Editor und erben dessen Kontext: offene Dateien, Cursorposition, den Language Server, den Projektindex. Der Language Server ist der unterschätzte Teil. Er liefert ihnen das schnellste Signal auf der gesamten Time-to-No-Leiter, Typ-Feedback in unter einer Sekunde, ohne dass etwas ausgeführt werden muss.

- **Am besten für:** Pair-Programming im Editor-Fluss, inkrementelle Arbeit in einer Datei, die Sie ohnehin gerade lesen, Teams, die auf einen Editor standardisiert sind.
- **Das kostet Sie:** Das Kontextfenster des Editors ist nicht die Architektur Ihres Repositorys. Diese Agenten sehen, was geöffnet ist, was stille Duplizierung in einer großen Codebasis wahrscheinlicher macht, sofern Ihre Muster nicht kanonisch sind (Scorecard-Prüfung 3).
- **Bemerkenswert:** Der Vorsprung von Copilot bei der Verbreitung ist eher eine Tatsache des Unternehmenseinkaufs als eine der Fähigkeiten. Beurteilen Sie es an Ihrem eigenen Repository, nicht am Marktanteil.

### Delegierte und asynchrone Agenten

**Beispiele: Devin, Google Jules, Cloud-Task-Runner einschließlich des gehosteten Codex.**

Sie übergeben ein Issue und bekommen einen Pull Request zurück. Es gibt keine interaktive Schleife, weshalb diese Agenten von allen drei Gruppen am empfindlichsten auf die Qualität des Repositorys reagieren. Sie haben genau einen Versuch, Ihre Konventionen zu verstehen, und das einzige Korrektursignal, das ihnen zur Verfügung steht, ist das, was Ihre CI meldet.

- **Am besten für:** gut spezifizierte, abgegrenzte, repetitive Arbeit in einem Repository, das auf der Scorecard hoch abschneidet. Dependency-Updates, nachträglich ergänzte Tests, mechanische Migrationen über viele Dateien.
- **Das kostet Sie:** alles, wenn Ihr Wert niedrig ist. Ein delegierter Agent in einem agentenfeindlichen Repository ist eine Maschine zur Erzeugung plausibler Pull Requests, die ein Mensch vollständig selbst neu herleiten muss.
- **Faustregel:** Delegieren Sie nicht asynchron, bevor Sie 17 oder mehr Punkte erreichen. Das ganze Modell hängt davon ab, dass die CI in Ihrem Namen Nein sagen kann.

### Die Achsen, auf die es ankommt

| Achse                               | Warum sie über Ihr Ergebnis entscheidet                                                                    |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Wo es läuft                         | Bestimmt, welche Verifikationssignale es ohne Hilfe erreicht                                               |
| Kontextzusammenstellung             | Aktive Suche findet Ihre vorhandene Hilfsfunktion; beiläufiger Kontext oft nicht                           |
| Freigabemodell                      | Legt fest, wie viel falsche Arbeit Sie erreicht, bevor etwas widerspricht                                  |
| Wahl von Modell und Anbieter        | Wichtig für Kostenkontrolle, Datenresidenz und die Vermeidung der Abhängigkeit von einem einzigen Anbieter |
| Unterstützung für Anweisungsdateien | Unterstützung für `AGENTS.md` bedeutet, dass eine Datei jedes Werkzeug steuert, das Ihr Team nutzt         |
| Kostenstruktur                      | Preise pro Platz, pro Token und pro Aufgabe belohnen völlig unterschiedliche Workflows                     |

| ----------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |

| Editor-orientiertes Team, inkrementelle Arbeit                    | Einem IDE-nativen Agenten                         | Language-Server-Feedback in unter einer Sekunde ist die günstigste verfügbare Time to No                                                           |

Die letzte Zeile ist für einen großen Teil der Teams die ehrliche Antwort, und kein Tool-Anbieter hat einen Anreiz, sie Ihnen zu geben.

## Anweisungsdateien: Was in AGENTS.md gehört

`AGENTS.md` ist eine einfache Markdown-Datei im Stammverzeichnis Ihres Repositorys, die jedem Coding-Agenten sagt, wie er in Ihrer Codebasis arbeiten soll. Mehr als 30 Agenten lesen sie nativ, darunter Claude Code, Codex, Cursor, Copilot, Aider, Windsurf, Devin, Zed und Gemini CLI. Damit ist sie die eine Datei, deren sorgfältige Pflege sich lohnt.

| Datei                             | Gelesen von                | Wofür Sie sie nutzen                                                                    |
| --------------------------------- | -------------------------- | --------------------------------------------------------------------------------------- |
| `AGENTS.md`                       | Den meisten großen Agenten | Die einzige Quelle der Wahrheit: Befehle, Grenzen, Konventionen                         |
| `CLAUDE.md`                       | Claude Code                | Nur das, was wirklich Claude-spezifisch ist. Für den Rest verweisen Sie auf `AGENTS.md` |
| `.cursor/rules/`                  | Cursor                     | Regeln mit Editor-Geltungsbereich, pfadspezifische Überschreibungen                     |
| `.github/copilot-instructions.md` | GitHub Copilot             | Copilot-spezifische Formulierungen, wo sie abweichen                                    |

Das Fehlermuster ist hier die Duplizierung. Vier Dateien, die dieselben Konventionen beschreiben, widersprechen sich innerhalb eines Monats, und eine widersprüchliche Anweisungsdatei ist schlimmer als keine, weil der Agent der falschen mit voller Überzeugung folgt. Pflegen Sie eine einzige echte Datei und lassen Sie die anderen auf sie verweisen.

### Was tatsächlich hineingehört

Schreiben Sie auf, was ein Agent nicht durch Lesen des Codes ableiten kann, und sonst nichts.

**Hinein gehören:** der Prüfbefehl, die Definition of Done, die Architekturgrenzen und die Richtung, in die Abhängigkeiten fließen, die Bereiche, die menschliches Review erfordern, und das eine kanonische Beispiel, das für jede häufige Aufgabe kopiert werden soll.

**Weglassen sollten Sie:** alles, was das Typsystem bereits ausdrückt, Wiederholungen der Dokumentation Ihres Frameworks, angestrebte Konventionen, denen die Codebasis nicht folgt, und lange Prosa. Eine Anweisungsdatei, die nicht stimmt, ist eine Belastung.

```markdown
# AGENTS.md

## Verify before you claim done

Run `bun run check && bun run test:coverage`. It type-checks, lints, tests and enforces
100% coverage. Exit code 0 means done. Nothing else does.

## Architecture

Dependencies flow one way: presentation -> application -> domain.
The domain layer imports nothing from the other two. This is
enforced by an import boundary rule, so a violation fails the build.

## Conventions

- Strict TypeScript. No `any`, no non-null assertions.
- Validate every external boundary with a Zod schema: HTTP bodies,
  environment variables, webhook payloads.
- New behaviour needs a test in the same commit. The coverage
  gate will reject it otherwise.
- Copy the nearest existing module. There is exactly one example
  of each pattern and it is the correct one.

## Human review required (do not edit without asking)

- `drizzle/migrations/**` (destructive and irreversible)
- Stripe webhook handlers (must stay idempotent)
- Anything reading a secret or environment variable
- CI workflow files

## Useful commands

bun run dev # local dev server
bun run check && bun run test:coverage # the only gate that matters
bun run test:coverage # regenerates the coverage report
bun run check:i18n # fails on a missing translation key
```

Ungefähr vierzig Zeilen. Jede Aussage darin wird entweder durch einen Befehl durchgesetzt oder ist eine Grenze, die ein Mensch halten muss. Nichts darin kann still und leise falsch werden, ohne dass ein Build fehlschlägt.

## Der Workflow, mit dem Sie ausliefern

<Steps>

<Step>

**Lassen Sie planen, bevor geschrieben wird.** Fragen Sie nach dem Ansatz und den Dateien, die der Agent anfassen will, und lesen Sie das, bevor Sie eine Änderung freigeben. Ein falscher Plan kostet eine Nachricht zur Korrektur. Eine falsche Implementierung kostet einen Review-Zyklus. Die meisten Agenten unterstützen inzwischen einen expliziten Planungsmodus; nutzen Sie ihn für alles, was über eine Änderung an einer einzelnen Datei hinausgeht.

</Step>

<Step>

**Begrenzen Sie den Wirkungsradius.** Ein Modul, ein Feature, ein Pull Request. Agenten sind gut in der Änderung, um die Sie gebeten haben, und gleichgültig gegenüber den neunzig Dateien, die sie unterwegs angefasst haben. Ein kleiner Diff ist hier keine Stilvorliebe, sondern die einzige Möglichkeit, wie ein Mensch den Output im Tempo der Agenten noch prüfen kann.

</Step>

<Step>

**Lassen Sie ihn verifizieren, nicht behaupten.** „Fertig“ ist Exit-Code 0 Ihres Prüfbefehls, ausgeführt vom Agenten, mit für Sie sichtbarer Ausgabe. Akzeptieren Sie niemals eine Zusammenfassung als Beweis. Der METR-Befund beschreibt genau, wie es sich anfühlt, selbstsichere Zusammenfassungen zu akzeptieren: Alles liest sich wie Fortschritt.

</Step>

<Step>

**Prüfen Sie die Absicht, nicht die Syntax.** Typprüfung, Linter und Testsuite haben die Syntax bereits geprüft. Ihr Review sollte stattdessen drei Fragen stellen. Löst das das eigentliche Problem? Hat es etwas dupliziert, das schon existiert? Was hat es beschlossen, nicht zu testen?

</Step>

</Steps>

Die dritte Frage fängt am meisten ab. Fragen Sie einen Agenten, was er bewusst nicht abgedeckt hat, und er wird es Ihnen meist sagen, und zwar zutreffend. In dieser Antwort steckt Ihr nächster Vorfall.

## Was eine hohe Time to No in Geld kostet

Nehmen Sie ein bescheidenes Team, das pro Woche zehn agentengestützte Änderungen ausliefert. Angenommen, jede sechste enthält einen Defekt, den keine automatisierte Prüfung findet. Das ist vorsichtig geschätzt, gemessen an GitClears Befund, dass schon geklonter Code allein mit 15 % bis 50 % mehr Defekten einhergeht.

Das sind rund 1,7 Defekte pro Woche, die das menschliche Review oder die Produktion erreichen. Bei einem Stundensatz von 80 $ kostet ein im Review gefundener Defekt vielleicht eine Stunde, verteilt auf Reviewer und Autor. Ein Defekt, der die Produktion erreicht, kostet eine Debugging-Session, einen Fix, ein Deployment und die Unterbrechung von allem, was sonst gerade lief, und das dauert selten weniger als vier Stunden.

Gewichten Sie das mit durchschnittlich drei Stunden, und Sie geben etwa **400 $ pro Woche oder 20.000 $ pro Jahr** für Defekte aus, die ein Coverage-Gate und eine strikte Typprüfung in neunzig Sekunden kostenlos zurückgewiesen hätten, bevor ein Mensch sie je gesehen hätte.

Es geht nicht um die Genauigkeit dieser Zahl. Setzen Sie Ihren eigenen Stundensatz und Ihre eigene Defektquote ein; die Form ändert sich nicht. Die Kosten einer hohen Time to No fallen kontinuierlich an, sie wachsen mit dem Output der Agenten statt gegen ihn, und sie sind in jedem Dashboard, das Sie derzeit ansehen, unsichtbar, weil sie als normale Engineering-Arbeit erscheinen.

Deshalb ist „welcher Agent?“ die falsche Eröffnungsfrage. Ein besserer Agent vergrößert den Zähler.

## Häufig gestellte Fragen

<Accordions>

<Accordion title="Welcher KI-Coding-Agent ist 2026 der beste?">

Es gibt keinen einzelnen besten Agenten, und die ehrliche Antwort lautet, dass die Frage weniger wichtig ist, als sie klingt. Im Januar 2026 führte GitHub Copilot bei der Nutzung am Arbeitsplatz mit 29 %, Cursor und Claude Code lagen gleichauf bei 18 %. Wählen Sie nach dem passenden Harness: terminal-nativ für Arbeit über mehrere Dateien, IDE-nativ für inkrementelle Arbeit, delegiert nur dann, wenn Ihr Repository auf der Scorecard oben 17 oder mehr Punkte erreicht.

</Accordion>

<Accordion title="Machen KI-Coding-Agenten Entwickler tatsächlich schneller?">

Nicht zuverlässig, und nicht unter den Bedingungen, unter denen die meisten Teams arbeiten. Die randomisierte kontrollierte Studie von METR ergab, dass 16 erfahrene Entwickler bei echten Aufgaben in ihren eigenen ausgereiften Repositories 19 % langsamer waren, während sie glaubten, 20 % schneller zu sein. Geschwindigkeit entsteht, wenn das Repository falsche Änderungen automatisch zurückweisen kann. Ohne das steigt der Output, der Durchsatz aber nicht.

</Accordion>

<Accordion title="Warum erzeugt mein KI-Coding-Agent immer wieder Code, der fast richtig ist?">

Weil nichts in Ihrem Repository ihm widerspricht. Ein Agent optimiert auf das, was er beobachten kann, und wenn das einzige verfügbare Signal „das sieht aus wie der umgebende Code“ lautet, erzeugt er Code, der wie der umgebende Code aussieht und das Falsche tut. Für 45 % der befragten Entwickler ist das das größte Ärgernis. Senken Sie Ihre Time to No, und diese Kategorie schrumpft.

</Accordion>

<Accordion title="Was ist AGENTS.md, und brauche ich eine?">

`AGENTS.md` ist eine Markdown-Datei im Stammverzeichnis Ihres Repositorys, die Coding-Agenten Ihre Befehle, Grenzen und Konventionen mitteilt. Sie wurde im August 2025 als offene Spezifikation formalisiert, im Dezember 2025 an die Agentic AI Foundation der Linux Foundation übergeben und steckt heute in über 60.000 öffentlichen Repositories, gelesen von mehr als 30 Agenten. Ja, Sie brauchen eine, und sie sollte kurz genug sein, um wahr zu bleiben.

</Accordion>

<Accordion title="Sollte ich eine AGENTS.md und eine CLAUDE.md haben?">

Pflegen Sie eine einzige echte Datei und lassen Sie die anderen auf sie verweisen. Duplizierte Anweisungsdateien widersprechen sich innerhalb eines Monats, und ein Agent, der einer veralteten Datei folgt, folgt ihr mit voller Überzeugung. Schreiben Sie alles in `AGENTS.md` und nutzen Sie werkzeugspezifische Dateien nur für wirklich werkzeugspezifisches Verhalten.

</Accordion>

<Accordion title="Spielt 100 % Testabdeckung für KI-gestützte Entwicklung eine Rolle?">

Sie ist wichtiger als vor den Agenten, und zwar aus einem Grund, der mit der üblichen Debatte nichts zu tun hat. Eine Coverage-Schwelle, die den Build fehlschlagen lässt, ist eine Regel, die ein Agent nicht umgehen kann: Er kann kein Verhalten hinzufügen, ohne einen Test hinzuzufügen. Coverage als Badge bewirkt nichts. Coverage als Gate verwandelt einen Review-Aufwand in einen Build-Fehler, der niemanden Zeit kostet.

</Accordion>

<Accordion title="Kann ein KI-Agent mein SaaS-Boilerplate nicht einfach für mich bauen?">

Er wird es tun, und das Ergebnis wird richtig aussehen. Was er Ihnen nicht sagt, ist, welche Auth-Randfälle er übersprungen hat, welcher Webhook nicht idempotent ist oder dass die i18n-Paritätsprüfung, die er nie geschrieben hat, die fehlenden Übersetzungen gefunden hätte. Die Ausgabe eines Agenten ist nur so vertrauenswürdig wie die Prüfungen, die sie kontrolliert haben, und in einem leeren Repository gibt es keine.

</Accordion>

<Accordion title="Welcher Agent kommt mit großen Codebasen am besten zurecht?">

Die Frage läuft meist auf die Kontextzusammenstellung hinaus, nicht auf den Agenten. Agenten, die aktiv suchen (`grep` ausführen, Dateien öffnen, Imports verfolgen), finden Ihre vorhandenen Hilfsfunktionen. Agenten, die sich auf den beiläufigen Kontext des Editors verlassen, finden das, was gerade geöffnet ist. In einem großen Repository zeigt sich der Unterschied als Duplizierung, weshalb Prüfung 3 der Scorecard, ein kanonisches Beispiel pro Muster, umso wichtiger wird, je größer die Codebasis wird.

</Accordion>

<Accordion title="Wie verhindere ich, dass ein Agent Migrationen oder Secrets anfasst?">

Kennzeichnen Sie die Pfade in `AGENTS.md` als Bereiche, die nur mit menschlichem Review geändert werden, und sichern Sie das mit CI statt mit Vertrauen ab. Anweisungsdateien legen die Absicht fest; Branch-Schutz, erforderliche Reviewer für diese Pfade und ein fehlschlagender Build setzen sie durch. Jeder Bereich, in dem ein Fehler irreversibel oder teuer ist, gehört an beide Stellen.

</Accordion>

<Accordion title="Lohnt es sich, den Agenten zu wechseln, um bessere Ergebnisse zu erzielen?">

Ein Wechsel bringt Ihnen eine einmalige Veränderung der Vorschlagsqualität, die sich mit jedem neuen Modell wieder zurücksetzt. Eine niedrigere Time to No verändert, wie viele falsche Vorschläge Sie überhaupt erreichen, gilt für jeden Agenten, den Sie nutzen, und wirkt kumulativ. Machen Sie zuerst das Zweite. Wechseln Sie danach die Agenten so oft Sie wollen, denn dann ist der Preis einer falschen Wahl gering.

</Accordion>

</Accordions>
