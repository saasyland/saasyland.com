`bun run check` führt `bun run generate:cn`, `bun run check:comments`, `bun run check:i18n` und `bun run check:flows` und danach `vp check` aus, das in einem Durchgang mit oxfmt formatiert, mit oxlint lintet und mit TypeScript die Typen prüft, konfiguriert in `vite.config.ts` und `tsconfig.json`. Die CI führt denselben Befehl aus. Nichts davon ist Geschmackssache: Wenn die Werkzeuge Code akzeptieren, der gegen eine Regel auf dieser Seite verstößt, lehnt das Review ihn ab.

## Was die Werkzeuge durchsetzen

oxlint behandelt die Kategorien `correctness`, `nursery`, `pedantic`, `perf`, `style` und `suspicious` als Fehler, mit eingeschalteten typbewussten Regeln und eingeschalteter Typprüfung. Die Grenzen, die den Code am stärksten prägen:

| Regel                                   | Einstellung                                                   | Wirkung                                                                                 |
| --------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `max-lines`                             | <RepositoryFact name="maxLines" />                            | Eine Datei nach Verantwortung aufteilen, bevor sie wächst                               |
| `max-lines-per-function`                | <RepositoryFact name="maxLinesPerFunction" />                 | Komponenten und Handler bleiben klein                                                   |
| `max-statements`                        | <RepositoryFact name="maxStatements" />                       | Benannte Hilfsfunktionen extrahieren statt langer Rümpfe                                |
| `no-magic-numbers`                      | `0` und `1` erlaubt, dazu Array-Indizes und Standardwerte     | Jede andere Zahl ist eine benannte Konstante                                            |
| `id-length`                             | mindestens zwei Zeichen, außer `_`, `m` und `t`               | Bezeichner sind Wörter; `t` ist die Übersetzungsfunktion                                |
| `one-var`                               | `never`                                                       | Eine Deklaration pro Anweisung                                                          |
| `unicorn/no-null`                       | außerhalb von Tests und `src/platform/testing` aktiv          | Fehlende Werte sind `undefined`                                                         |
| `typescript/no-explicit-any`            | `error`                                                       | Kein Wert ist als `any` typisiert                                                       |
| `typescript/ban-ts-comment`             | `true` für `@ts-expect-error`, `@ts-ignore` und `@ts-nocheck` | Kein Compilerfehler wird unterdrückt, mit oder ohne Begründung                          |
| `typescript/consistent-type-assertions` | `assertionStyle: "never"`                                     | Kein `as`-Cast; `as const` und `satisfies` bleiben erlaubt                              |
| `code-style/no-comments`                | `error`                                                       | Kein Kommentar, Direktivkommentare eingeschlossen                                       |
| `code-style/no-multiline-ternary`       | `error`                                                       | Ein ternärer Ausdruck passt in eine Zeile                                               |
| `code-style/no-undefined-branch`        | `error`                                                       | Kein ternärer Ausdruck mit einem Zweig `undefined` oder `null`, kein `return undefined` |
| `code-style/no-undefined-fallback`      | `error`                                                       | Kein `?? undefined`                                                                     |
| `code-style/zod-namespace-import`       | `error`                                                       | Zod wird als `* as zod` aus `zod` importiert                                            |
| `radius/no-off-scale`                   | `error`                                                       | Jede Ecke nimmt einen Radius aus der Skala                                              |
| `type/no-off-scale`                     | `error`                                                       | Jede Textgröße ist eine Stufe der Typo-Skala                                            |
| `type/mono-for-code`                    | `error`                                                       | Die Monospace-Schrift steht nur für Code                                                |

Die Overrides sind eng und auf Dateien begrenzt: Tests und die gemeinsamen Testhelfer in `src/platform/testing` lockern `no-magic-numbers`, `no-await-in-loop`, `unicorn/no-null`, `hydration/no-clock-or-locale-in-render` und `admin-data/no-literal-data`; `src/presentation` und `src/hooks` lockern `typescript/consistent-return`; Test-Mocks lockern `require-await`; `src/routes` schaltet `sort-keys` ab, weil Routenoptionen ihrer eigenen Reihenfolge folgen (siehe [Routendateien](/docs/conventions/routes)); und die Routen, Komponenten und Datendateien des Admin-Bereichs schalten `admin-data/no-literal-data` ein (siehe [Admin-Dashboard](/docs/features/admin-dashboard#real-data-only)). Ganz `src` schaltet `radius/no-off-scale`, `type/no-off-scale` und `type/mono-for-code` ein, die Tests und `src/platform/testing` wieder abschalten, und `src/presentation/social-card.tsx` schaltet `type/no-off-scale` ab, weil Takumi die Social Card als Bild fester Größe rendert, dessen Schriftgrößen in Inline-Styles statt auf der Typo-Skala der Seite festgelegt sind (siehe [Theme](/docs/ui/theme#type-scale)).

`tsconfig.json` ergänzt die strikten Flags, die verändern, wie Code geschrieben wird: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` und `noUnusedParameters`. Ein indizierter Lesezugriff ist möglicherweise `undefined`, eine optionale Eigenschaft kann nicht explizit auf `undefined` gesetzt werden, und eine Indexsignatur wird als `record["key"]` gelesen.

Der Formatter schreibt ohne Semikolons, mit doppelten Anführungszeichen, abschließenden Kommas und einer Zeilenbreite von <RepositoryFact name="printWidth" />. Außerdem sortiert er Importe in feste Gruppen, Tailwind-Klassen in `className`- und `cn`-Aufrufen und die Skripte in `package.json` nach Namen (`sortPackageJson: { sortScripts: true }`); ordne also nichts davon von Hand, denn `vp check` schlägt fehl, wenn etwas nicht in der richtigen Reihenfolge steht. Die Befehle findest du unter [Linting und Formatierung](/docs/tooling/lint-format).

## Rendern, was der Server gerendert hat

Eine Seite wird zweimal gerendert: auf dem Server und noch einmal im Browser, wenn React das HTML hydriert. Beide Renderings müssen denselben Text ausgeben, sonst meldet React einen Hydration-Mismatch (Fehler #418) und rendert die Seite neu. Render-Code liest deshalb weder die Uhr noch die Locale der Laufzeitumgebung, die sich zwischen beiden unterscheiden: kein `new Date()` ohne Argument, kein `Date.now` und kein `toLocaleString`, `toLocaleDateString` oder `toLocaleTimeString`. Verwende einen Wert, den beide Seiten teilen:

- eine relative Zeit zählt ab dem `dataUpdatedAt` der Query, die ihre Daten gelesen hat, wie [Internationalisierung und Locales](/docs/features/internationalization) zeigt;
- ein Jahr, das die Website ausgibt, stammt aus dem Build: Der Footer beendet sein Copyright mit `REPOSITORY_FACTS.buildYear`, dem UTC-Jahr, in dem die Website gebaut wurde;
- Zahlen und Datumsangaben laufen über `useFormatter` aus use-intl, in der Locale der Seite und der Zeitzone des Benutzers;
- eine Wartezeit im Browser, etwa das Aktivierungs-Timeout von `CheckoutActivation`, ist ein Timer, der in `useEffect` startet, sodass das erste Rendering das des Servers ist.

`hydration/no-clock-or-locale-in-render`, die Regel des repository-eigenen oxlint-Plugins in `scripts/hydration-lint-plugin.ts`, setzt das in `src/hooks`, `src/presentation`, `src/providers` und `src/routes/*.tsx` durch. Dort zählt alles als Render-Code außer einer Funktion, die später läuft: ein `on…`-Event-Handler, als JSX-Prop, Objekteigenschaft oder Variable; eine `queryFn` oder `mutationFn`; und ein Callback, der an `useEffect`, `useLayoutEffect`, `useCallback`, `setTimeout`, `setInterval`, `requestAnimationFrame` oder `addEventListener` übergeben wird. Diese Listen im Plugin sind die Allowlist: Eine weitere Art verzögerter Callbacks kommt dort hinzu, mit einem Fall in `src/__test__/hydration-lint-plugin.test.ts`, niemals mit einem Disable-Kommentar.

## Keine Kommentare

Schreibe keine Kommentare: nicht in TypeScript, TSX, Tests, Skripten, Konfiguration oder CSS und auch nicht, um eine nicht offensichtliche Einschränkung zu erklären. Stattdessen trägt ein Name die Bedeutung, und die Begründung gehört in die Commit-Nachricht, den Pull Request oder diese Dokumentation.

```ts
const INCLUSIVE_END = 1
const FIRST_SEQUENCE = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

Die ersten beiden stammen aus `video.delivery.ts` und `release.ts`, die dritte aus `src/integrations/polar/polar.vite.ts`: Jede bräuchte sonst einen Kommentar.

Zwei Prüfungen setzen die Regel durch, und beide nennen die Datei, die Zeile und die Korrektur:

- `code-style/no-comments`, eine Regel des repository-eigenen oxlint-Plugins in `scripts/code-style-lint-plugin.ts`, meldet jeden Kommentar in den Dateien, die der Linter liest, im Editor und in `vp check`.
- `bun run check:comments` führt `scripts/check-comments.ts` vor dem Linter aus, in `bun run check` und im Pre-Commit-Hook. Es parst jede TypeScript-, JavaScript- und CSS-Datei, die Git verfolgt oder hinzufügen würde, mit oxc für Code und PostCSS für Styles, sodass ein `//` in einer URL oder einem regulären Ausdruck und ein `/*` in einem CSS-Glob keine Kommentare sind. Es liest, was der Linter nicht lesen kann: `e2e`, `remotion`, Deklarationsdateien, die Stylesheets und einen `/* oxlint-disable */`-Kommentar, den der Linter befolgt, bevor eine Regel ihn sieht.

Ausgenommen sind die Dateien, die `.gitattributes` als `linguist-generated` markiert, unter denen `src/routeTree.gen.ts` und `src/types/worker-configuration.d.ts` Code sind, und die `#!`-Zeile eines Skripts, die die Grammatik von JavaScript nicht als Kommentar zählt. Ein Typ, den der Compiler überall braucht, kommt in `types` in `tsconfig.json`, wie die Vitest-Globals, niemals in einen `/// <reference>`-Kommentar.

## Keine Hintertüren

Schreibe niemals `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, einen `as`-Cast oder `any`, um eine Regel zu erfüllen. Eine Regel, die anschlägt, zeigt auf ein Designproblem; ändere das Design. Die Prüfungen weisen jede davon zurück: `typescript/ban-ts-comment` die drei Compiler-Direktiven auch mit einer Beschreibung, `typescript/consistent-type-assertions` jede Assertion außer `as const`, `typescript/no-explicit-any` das `any`, und `code-style/no-comments` und `bun run check:comments` jeden Disable-Kommentar. Ein `eslint-disable`-Kommentar schaltet ohnehin nichts ab (`respectEslintDisableDirectives: false`).

- **Validieren statt behaupten.** Daten aus dem Speicher, dem Netzwerk oder einer Anfrage werden mit Zod geparst: `src/lib/github.ts` liest die zwischengespeicherte Anzahl der Sterne mit `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, was eine Zahl oder `undefined` ergibt, niemals eine Vermutung.
- **Mit einem Type Guard eingrenzen.** `isRole` in `src/integrations/better-auth/auth.roles.ts` und `isSupportedLocale` in `src/integrations/use-intl/i18n.paths.ts` machen aus einem `string` mit einer echten Prüfung eine Union.
- **Annotieren, nicht behaupten.** Gib einem Wert den Typ, den er braucht, dort, wo er deklariert wird: Die shadcn-Sidebar deklariert `SIDEBAR_MOBILE_STYLE: StyleWithCssVars`, die CSS-Eigenschaften plus ihre Custom Property `--sidebar-width`, statt das Objektliteral zu casten.
- **Prüfen, nicht umwandeln.** `as const` und `satisfies` sind erlaubt, weil sie einen Typ nie verändern: `POLAR_ORDER_STATUS` endet mit `as const satisfies Record<string, models.OrderStatus>`, sodass ein falsch geschriebener Polar-Status nicht kompiliert.
- **Umstrukturieren, wenn der Vertrag einer Bibliothek dagegenhält.** Packe einen Wert in ein Objekt, teile eine Funktion auf oder lies aus einer typisierten Quelle, statt zu casten.

## Null und undefined

Außerhalb von Tests und `src/platform/testing` ist ein fehlender Wert `undefined`, und `null` wird nie als Wert geschrieben. Der Linter erlaubt es dort, wo eine API es vorgibt: im Vergleich mit einem Wert, der `null` sein kann, etwa einer nullbaren Spalte (`entry.completedAt !== null` in `course.outline.ts`), und in einer React-DOM-Ref, die mit `useRef<HTMLElement>(null)` beginnt, weil React `ref` als `RefObject<T | null>` typisiert und es beim Unmount auf `null` zurücksetzt (`course-showcase.tsx`). Überbrücke eine API, die `null` zurückgibt, nie mit `?? undefined`; `code-style/no-undefined-fallback` lässt das scheitern. Validiere zuerst die Eingabe, damit der Aufruf nicht fehlschlagen kann, oder verwende einen Parser, der bereits `undefined` zurückgibt. Suchparameter sind der häufigste Fall, und `searchParam(schema)` in `src/lib/search-params.ts` gibt für einen fehlenden oder fehlerhaften Wert `undefined` zurück:

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Ternäre Ausdrücke und frühe Returns

Ein ternärer Ausdruck passt in eine Zeile, etwa `{t(course === undefined ? "create" : "save")}` in `course-form.tsx`. Alles, was länger ist, und jede Wahl zwischen zwei JSX-Teilen wird zu einem frühen Return, einem Paar von `&&`-Bedingungen oder einer kleinen Komponente; eine bedingte Klasse wird zu `cn("base", { "classes": condition })`. `code-style/no-multiline-ternary` lässt jeden ternären Ausdruck scheitern, der sich über mehrere Zeilen erstreckt, auch einen, den der Formatter umgebrochen hat, weil er über die Zeilenbreite hinausgewachsen ist. `src/routes/auth.reset-password.tsx` rendert seine beiden Zustände mit zwei Bedingungen:

```tsx
{hasValidToken && <ResetPasswordForm token={token} />}
{!hasValidToken && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

Funktionen kehren bei Sonderfällen früh zurück und halten den Hauptpfad ohne Einrückung, wie `hasLessonAccess` in `src/modules/lesson/lesson.access.ts`:

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.entitled
}
```

Auch kein Zweig schreibt den fehlenden Wert aus: `code-style/no-undefined-branch` lässt einen ternären Ausdruck mit einem Zweig `undefined` oder `null` und jedes `return undefined` scheitern. Schreib stattdessen, was der Code tut: Kehre aus einer Guard Clause früh zurück, lies einen Wert, der fehlen kann, mit `?.` oder mit `??` und einem echten Standardwert, gib zurück, was ein Lookup oder `find` findet, rendere JSX mit `&&` und gib dem Hook eines Vite-Plugins einen Filter, der die IDs nennt, die er behandelt, damit Rolldown ihn für keine andere ID aufruft. So liefert `scripts/repository-facts.ts` sein virtuelles Modul aus:

```ts title="scripts/repository-facts.ts"
    load: { filter: { id: exactRegex(RESOLVED_MODULE_ID) }, handler: () => moduleSource },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_MODULE_ID },
```

## Benannte Konstanten

Zahlen außer `0` und `1` erhalten einen Namen (`COURSE_STALE_MS = 60_000`, `SAVE_INTERVAL_MS = 15_000`). `0` und `1` stehen als Literale da, etwa in `.limit(1)`, `index + 1` und `toHaveBeenCalledTimes(1)`, außer sie tragen eine eigene Bedeutung: Ein Exit-Code eines Prozesses heißt `FAILURE_EXIT_CODE`, das inklusive Ende eines HTTP-Byte-Bereichs `INCLUSIVE_END`. Werte, die zur Domäne gehören, etwa Status, Arten, Zugriffsstufen, Lizenzstufen, Rollen und Ereigniswerte von Anbietern, werden einmal als `as const`-Objekt deklariert und überall über ihren Namen referenziert, auch in Tests und Fixtures:

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

Das Tupel, das eine Spalte oder ein Enum-Schema braucht, wird aus dem Objekt gebildet, nicht neu abgetippt, und steht neben ihm in den Konstanten des Moduls, die nichts aus Drizzle importieren: `course.constants.ts` deklariert `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, das sowohl `text("status", { enum: COURSE_STATUSES })` in `course.schema.ts` als auch `zod.enum(COURSE_STATUSES)` in `course.zod.ts` speist. Auch Browsercode liest die Tupel von dort: Die Preistabelle iteriert über `LICENSE_TIERS` aus `license.constants.ts`.

- Die Konstanten eines Moduls liegen in seiner `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`); die Werte eines Anbieters liegen in der `*.constants.ts` der Integration (`POLAR_ORDER_STATUS` in `polar.constants.ts`, `AUTH_PROVIDER` in `auth.constants.ts`).
- Spalten- und Eingabelängen werden einmal in den Konstanten des Moduls benannt und sowohl vom Drizzle-Schema als auch vom Zod-Schema gelesen: `PRODUCT_NAME_MAX_LENGTH` in `product.constants.ts`.
- Ein Konzept hat eine Map in einer Schreibweise: `ERROR_CODES` für Serverfehler, `AUTH_ERRORS` für die Fehlerschlüssel von Better Auth, `ROLE_CODES` für Rollen.
- Umgebungsnamen und HTTP-Statuscodes werden einmal in `src/modules/_core/constants/api.ts` deklariert: `ENVIRONMENT.PRODUCTION` in `__root.tsx` und in den Deploy-Skripten, `HTTP_STATUS.PARTIAL_CONTENT` im Medien-Handler des Workers. Keine Datei deklariert eine eigene Map für eines davon. Die einzige Ausnahme ist `vite.config.ts`, das `mode` mit dem reinen Namen vergleicht: Vite lädt es, bevor der Alias `~` aufgelöst wird, deshalb kann es `api.ts` nicht importieren.
- Eine Konstante, die nur eine Datei verwendet, bleibt in dieser Datei, unterhalb der Importe. Eine Konstante, die mehrere Dateien verwenden, kommt in ihr Modul, nach `src/data` (siehe [Dateien und Benennung](/docs/conventions/files-and-naming)) oder nach `src/modules/_core/constants`. Gib einer einzelnen Konstante nie eine eigene Datei.
- Typisierte API-Feldnamen wie `license_key_id` sind Eigenschaften, keine Werte, und bleiben Eigenschaftszugriffe.

## Hooks in Komponenten

Hook-Aufrufe mit einem einzelnen Wert kommen zuerst, dann eine Leerzeile, dann jedes destrukturierte Hook-Ergebnis, sodass die Werte, die eine Komponente zerlegt, als eigene Gruppe lesbar sind. `src/presentation/components/custom/auth/sign-in-form.tsx`:

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Eine Komponente ruft `useTranslations` einmal auf und nennt das Ergebnis `t`; den Grund dafür erklärt [Übersetzungen und Inhalte](/docs/conventions/translations).

## Namen und Importe

- Dateien und Ordner sind kebab-case; Komponenten sind PascalCase; Konstanten sind SCREAMING_SNAKE_CASE; Funktionen beginnen mit einem Verb (`resolveViewer`, `rethrowAsConflict`); Booleans lesen sich als Fragen (`isPending`, `hasLessonAccess`).
- Importe verwenden den Alias `~/src/...` und kommen aus der Datei, die das Symbol definiert; die einzige Ausnahme sind die Pfade, die jede Datei als einen Namespace importiert, `import * as ROUTES from "~/src/routes"`. Es gibt keine Barrel-Dateien, die einen Ordner re-exportieren. Re-Export-Dateien sind die Sammelpunkte mit einer Zeile `export { … } from` pro Bereich, etwa `src/routes.ts` und die Barrels `*.entries.ts` (siehe [Pfade und Navigation](/docs/conventions/routes#paths-and-navigation)), sowie `src/integrations/drizzle-orm/drizzle.schemas.ts`, weil Drizzle jede Tabelle in einem Schemaobjekt braucht.
- Zod wird auf eine Weise importiert, `import * as zod from "zod"` (oder `import type * as zod from "zod"` nur für Typen), wie es die Dokumentation von Zod 4 zeigt; `code-style/zod-namespace-import` lässt einen Default-Import, einen benannten Import und einen Unterpfad wie `zod/v4` scheitern.
- Ein Index rückt mit dem Literal um eins weiter: `lessons[index + 1]` in `course.utils.ts`. Jeder andere Versatz, auch `-1`, bekommt einen Namen: `groups.at(LAST_GROUP_INDEX)` in `robots.ts`, niemals `slice(index, -5)`.
