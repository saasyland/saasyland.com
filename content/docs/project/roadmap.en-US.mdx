Generic billing in the application, which it is built from, is live: a checkout for any Polar product, the Polar catalogue in `/admin/products`, the billing page with the account's orders, subscriptions and invoices and Polar's customer portal, and the licence built on them. ## CLI: every option in the configurator

The [configurator](/#cli) shows every option and extra of the CLI's stack package, and the CLI will generate all of them. Two more are planned and join the configurator with a release of that package: MongoDB, through Prisma, and the realtime extra. An option is enabled in the configurator, and accepted by `init`, only when a project generated with it installs, type-checks, passes its tests at <RepositoryFact name="coverageThreshold" />% coverage, builds and starts, in CI, on every change that can reach it. Until then the configurator shows it disabled and `init` refuses it with exit code <RepositoryFact name="cliExitNotAvailable" />, before any licence check.

Some answers depend on others. The API question applies only to the split and microservices architectures, and some runtimes and providers do not run on every deployment target, such as the Bun runtime on Cloudflare Workers. The configurator disables a combination the target cannot run.

The options arrive in this order:

1. Billing with Polar, with orders and customers in the generated admin console (Currently working on).
2. The subscription course extra, with courses in the generated admin console. It needs billing.
3. Billing with Stripe, and email with Plunk.
4. Prisma, first on Cloudflare D1 and then on each database as it arrives; then MongoDB through Prisma, which Drizzle cannot use.
5. Your own server with Docker: a production image that runs as a non-root user, has a health check and keeps every secret out of its layers, a Compose setup with the database and a TLS proxy, the image built and scanned in CI, and guides for upgrades and backups.
6. The split architecture: a monorepo with the web app, a Hono API and a shared contract, from which oRPC serves typed calls to the web app and a REST API with its OpenAPI description.
7. Realtime, as an extra: streaming from the server to the browser on every runtime, two-way WebSockets, with Durable Objects on Cloudflare Workers and Hono's WebSocket helpers on Node and Bun, and a live demo of both in the generated admin console.
8. Leaving email out, and leaving content out. Without email, sign-in needs a flow that sends no mail; without content, the coding conventions that a generated project's agent instructions point to must live outside the docs.
9. Postgres with Neon, Supabase or your own server; Turso; a local SQLite file.
10. Deploying to Vercel; the Bun and Deno runtimes.
11. An Elysia API, then microservices.
12. Next.js and React Router on React.
13. Solid with SolidStart and TanStack Start, Vue with Nuxt, Svelte with SvelteKit, and Angular with Analog and Angular SSR.
14. Multi-tenancy, once organizations and roles are in the application.
15. The store with sample products, the visual page builder and the visual post editor, each after the application ships the feature it generates.

### Commands and releases

- Interactive questions in a terminal. Today a terminal session answers every question you did not pass as a flag with the default, as `--yes` does.
- `status`, which shows a project's release, answers and licence.
- `change`, which runs the CLI again on an existing project with different answers: modules first, platform switches later.
- `update`, which brings a project to a newer release in one command, with a three-way merge that keeps your own edits. Update and change scenarios run every night across recent releases.
- A generated reference of every command and flag in the [CLI guide](/docs/cli), and guides for upgrading the CLI, rotating a licence key, troubleshooting, and updating or changing a project. Every command in the guide runs in CI against the CLI under test.
- A next beta that corrects the CLI's own READMEs and release documentation.
- The stable release on npm's default tag. Until then, run the CLI as <RepositoryFact name="cliPackageSpec" />. Stable ships when billing and the course extra are in, and when the nightly journey generates a project with each package manager, builds it, runs its tests and checks the licence end to end. The site then switches its commands to the default tag and publishes the release notes and a release post.

## Application

1. Prices on the site read from Polar, so that a price changes in one place.
2. Creating, editing and deleting products from the admin, through Polar; pricing models, one-time and recurring; discount codes.
3. Issuing refunds from the order page, which already shows refunds recorded in Polar; an email to the buyer when a licence is refunded or revoked; and payment disputes on the order page, with their outcome applied to the licence.
4. Moving to a lower tier from the licence page. Today it is done by email to support.
5. Dashboard metrics on real data; sign-up and checkout funnel measurement that respects privacy; an analytics screen with page views, visitors, retention and churn.
6. Turning the newsletter on and off in the customer workspace.
7. Permissions: an editor role, menus filtered by permission, and a role editor.
8. Organizations and teams, then Agency's team seats.
9. An audit log of bans, deletions and impersonation.
10. Editing the blog from the admin, in a visual editor that commits to Git through a pull request; then editing the docs.
11. The landing page built from a section registry, then the visual page designer, a pricing page, a section library and campaign pages.

## Quality and engineering

- The nightly journey suite running against the preview site and Polar's sandbox, then extended to generate a project with the CLI, build it and run its tests with each package manager.
- A browser test for every flow listed below as missing, and the flows still to build as their features ship.
- Mutation testing on the licence, payments and access code, and browser code coverage of the Playwright suite.
- Lint rules for non-null assertions and empty `catch` blocks, and guardrails for coding agents: a registry of the rules with checks, repository skills generated from the conventions with a drift check, and committed hooks.
- A boundary lint rule in generated projects, and generated projects built every night on the latest dependencies.
- Performance: the slower sections of the admin console, the products page and the billing page streamed into their skeletons, course pages cached at the edge for signed-out visitors, an A/B test of the modulepreload strip, Server-Timing on the Worker, and licence activations streamed to the page.
- Dependencies kept on their latest releases, with each patch dropped when its fix is released upstream.
- Old issues from the earlier Next.js codebase closed with a note.
