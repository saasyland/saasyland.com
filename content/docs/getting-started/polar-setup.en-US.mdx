Polar sells the three tiers at the prices checkout sends, issues their licence keys and charges the tax. The code expects a precise setup in Polar, and Polar does not warn you when the two drift apart: a product without a licence-key benefit still takes the payment but issues no key. `bun run polar:verify:<environment>` compares Polar with the code, and the deploy scripts run it before every manual deploy.

## Production and sandbox

Polar runs two separate services. Production (`polar.sh`, API `api.polar.sh`) charges real cards; the sandbox (`sandbox.polar.sh`, API `sandbox-api.polar.sh`) accepts only test cards. They share nothing: an account, organisation, token, product, discount or webhook exists in one service only, so sign up at `sandbox.polar.sh` separately and set up each service on its own.

| Environment file   | `POLAR_SERVER` | Polar organisation |
| ------------------ | -------------- | ------------------ |
| `.env.development` | `sandbox`      | Sandbox            |
| `.env.preview`     | `sandbox`      | Sandbox            |
| `.env.production`  | `production`   | Production         |

Development and preview can share one sandbox organisation, but its webhook reaches only preview: it posts to the preview host, which writes to the preview D1 database, while `bun run dev` uses a local database of its own. A test purchase made in development therefore grants no licence locally; try purchases end to end on the preview.

Never put a production token, organisation ID or product ID in `.env.development` or `.env.preview`. The sandbox API rejects a production token, and with `POLAR_SERVER=production` a test checkout would charge a real card and grant the licence in the local or preview database. `polar:verify` refuses `POLAR_SERVER=production` for development and preview, and `POLAR_SERVER=sandbox` for production.

## Organisation and token

In the sandbox, then in production:

1. Create an organisation and copy its ID from the organisation settings into `POLAR_ORGANIZATION_ID`. Give both organisations the slug in `POLAR_ORGANIZATION_SLUG` (`src/data/polar.ts`), or change the constant to their slug: the [alert and the admin list of orders that match no account](/docs/features/licences#orders-that-match-no-account) link each order to the Polar dashboard under that slug.
2. In the organisation settings, create an organisation access token with these scopes, and no others, and copy it into `POLAR_ACCESS_TOKEN`.

| Scope                     | Needed by                                                                                                                                                                                                                                                                                                                                            |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkouts:write`         | `startCheckout`, which creates the checkout with the Polar SDK (`polar.checkouts.create`)                                                                                                                                                                                                                                                            |
| `customer_sessions:write` | The customer portal link, `/api/auth/customer/portal`                                                                                                                                                                                                                                                                                                |
| `license_keys:write`      | Reading a key and its activations, activating a machine and removing an activation (`deactivateLicense` and the [CLI licence API](/docs/features/cli-licence-api)), and, for an upgrade, raising the key's activation limit and disabling the key Polar issues for the upgrade order                                                                 |
| `orders:read`             | The webhook handlers, which read the order behind a licence and the current customer of an order whose event matches no account, the upgrade price, which adds up what the customer has paid for licences, the admin order page, which reads an order and its invoice, and `orders:backfill`, which copies each order's discount and billing country |
| `organizations:read`      | `polar:verify`, which reads whether checkout localization is on, the default tax behaviour and the hosts that may embed the checkout                                                                                                                                                                                                                 |
| `products:read`           | `polar:verify`                                                                                                                                                                                                                                                                                                                                       |
| `webhooks:read`           | `polar:verify`                                                                                                                                                                                                                                                                                                                                       |

A write scope includes reading, so `license_keys:write` also covers reading keys. An organisation token already acts for its own organisation. `polar:verify` still sends `POLAR_ORGANIZATION_ID` as the `organization_id` query parameter, as the order listing for an upgrade does, so an ID of another organisation shows up as missing products.

## Products

Create one product per tier: a one-time purchase, not a subscription, with a fixed price in `DEFAULT_CURRENCY_CODE` (US dollars) equal to `TIER_PRICES` in `src/data/marketing.ts`. Copy each product's ID into its key.

| Tier     | Key                         | Price                         | Activations per key                 |
| -------- | --------------------------- | ----------------------------- | ----------------------------------- |
| Core     | `POLAR_PRODUCT_ID_CORE`     | <TierPrice tier="core" />     | <ActivationLimit tier="core" />     |
| Complete | `POLAR_PRODUCT_ID_COMPLETE` | <TierPrice tier="complete" /> | <ActivationLimit tier="complete" /> |
| Agency   | `POLAR_PRODUCT_ID_AGENCY`   | <TierPrice tier="agency" />   | <ActivationLimit tier="agency" />   |

Polar stores a price in the currency's minor units, cents for US dollars, and `polar:verify` converts `TIER_PRICES` the same way before it compares them. It ignores archived prices.

## Licence keys

Create one **License Keys** benefit per tier and attach it to that tier's product only:

- **Activations**: limited to the number in the table above, `LICENSE_ACTIVATION_LIMITS` in `src/modules/license/license.constants.ts`. Letting customers manage their activations in Polar is optional, because `/app/license` lists and removes them itself.
- **Expiration**: none. Keys never expire, as the purchase is a one-time payment.
- **Usage limit**: none.
- **Prefix**: your choice; `polar:verify` does not check it.

Each product needs exactly one licence-key benefit; other benefits beside it are fine. When Polar grants the benefit, the `benefit_grant.created` webhook stores the key on the buyer's licence.

## Consent checkbox

The buyer gives the consent to immediate supply on Polar's checkout, and this field is the only place it is asked for (see [Licences](/docs/features/licences#consent-to-immediate-supply)); Polar records it on the order. Create one custom field in the organisation and attach it to the three products:

- **Type**: checkbox.
- **Slug**: <RepositoryFact name="licenseWithdrawalConsentField" />, `LICENSE_CHECKOUT_FIELD.WITHDRAWAL_CONSENT` in `src/modules/license/license.constants.ts`. The order stores the ticked box under this key in `custom_field_data`.
- **Label**: exactly `WITHDRAWAL_CONSENT_FIELD.label` from `src/lib/polar.ts`, the English sentence built from `REFUND_TERMS.WITHDRAWAL_DAYS` that ends with a Markdown link to the production Refund Policy.
- **Name**: your choice; `WITHDRAWAL_CONSENT_FIELD.name` is the one the code suggests, and `polar:verify` does not check it.
- **Required** on each of the three products. Other fields the products ask for may stay.

`startCheckout` sends no value for the field, so the box starts empty and the buyer ticks it; Polar does not take the payment while a required box is empty. Polar keeps only the values of fields that the product asks for: before the field is attached, a checkout still works, but the order records no consent, and the [purchase confirmation](/docs/features/licences#purchase-confirmation) states the statutory right of withdrawal instead.

Creating the field and attaching it to a product need the `custom_fields:write` and `products:write` scopes, which the token above does not have. Create and attach it in the Polar dashboard, or through the API with a separate token that has them. `polar:verify` reads the attached fields from the products listing, so it needs no other scope.

## Checkout language

Polar shows its checkout in the language `startCheckout` asks for only while checkout localization is on for the organisation; otherwise every checkout opens in English. Turn it on in the organisation's settings. Polar's [checkout localization guide](https://polar.sh/docs/features/checkout/localization) calls it a feature flag, and the API returns it as `feature_settings.checkout_localization_enabled` on the organisation. `POLAR_CHECKOUT_LANGUAGES` in `src/data/polar.ts` lists the languages the code asks for, and `polar:verify` fails while localization is off.

## Tax behaviour

The pricing cards say that prices are in US dollars, that VAT is included in the EU and that sales tax is added at checkout in the US, Canada and India. Polar charges tax that way when the organisation's default tax behaviour is location-based, so set it to that in the organisation's settings. The API returns it as `default_tax_behavior` on the organisation, and `polar:verify` fails while it is not `location` (`POLAR_TAX_BEHAVIOR.LOCATION` in `src/lib/polar.ts`).

## Embedding

The buy buttons open Polar's checkout over the site in an iframe ([Licences](/docs/features/licences#the-checkout-over-the-page)), and Polar lets only the hosts its organisation lists frame its checkout. Under **Settings > Embedding**, list the hosts that `appHostsForMode` serves in each environment, without a scheme and with the port when there is one:

| Environment   | Organisation | Hosts                              |
| ------------- | ------------ | ---------------------------------- |
| `development` | Sandbox      | `localhost:3000`, `127.0.0.1:3000` |
| `preview`     | Sandbox      | `preview.saasyland.com`            |
| `production`  | Production   | `saasyland.com`                    |

An entry `*.saasyland.com` covers `preview.saasyland.com` but not `saasyland.com`. Polar adds the organisation's verified domains to the list itself. The API returns the list as `embed_hosts` on the organisation, and `polar:verify` fails while a host of the environment is missing. Until it is listed, Polar's frame stays blank on that host, and after <RepositoryFact name="checkoutOverlayGraceSeconds" unit="second" /> the button sends the buyer to Polar's checkout page instead, so buyers can still pay, a little later.

## Regional prices

Regional prices need nothing in Polar. For a buyer in a country of `PPP_TIERS` (`src/modules/license/license.pricing.ts`), whose bands take <RegionalDiscounts /> off, `startCheckout` sends the price itself: `regionalPrice` rounds the tier's price down to whole dollars, the amount the tier cards show, and the checkout carries it in `prices` as a fixed price for the tier's product that holds for that checkout only, so the product keeps its price from `TIER_PRICES`. An [upgrade](/docs/features/licences#upgrades) sends its price the same way. Discounts that an earlier setup created are no longer used, and you can delete them.

## Webhook

Create one webhook endpoint for each deployed environment, in the organisation that environment uses.

| Environment  | Organisation | URL                                                     |
| ------------ | ------------ | ------------------------------------------------------- |
| `preview`    | Sandbox      | `https://preview.saasyland.com/api/auth/polar/webhooks` |
| `production` | Production   | `https://saasyland.com/api/auth/polar/webhooks`         |

The host comes from `DEPLOYED_HOSTS` and the path from `ROUTES`. Choose the raw format, keep the endpoint enabled and subscribe it to exactly the events in `POLAR_EVENTS` (`src/data/polar-events.ts`), which joins the events every area handles (see [Payments](/docs/features/payments#webhooks)). Today the licence area handles the events in `LICENSE_WEBHOOK_EVENTS` (`src/modules/license/license.constants.ts`), and the billing area those in `src/data/billing.polar-events.ts`:

| Event                   | Licence area                                                | Billing area                         |
| ----------------------- | ----------------------------------------------------------- | ------------------------------------ |
| `benefit_grant.created` | Stores the licence key                                      |                                      |
| `benefit_grant.revoked` | Revokes the licence                                         |                                      |
| `order.created`         |                                                             | Copies the order into D1             |
| `order.paid`            | Grants the licence                                          | Updates the copy of the order        |
| `order.refunded`        | Marks the licence refunded once the order is fully refunded | Updates the copy of the order        |
| `order.updated`         |                                                             | Updates the copy of the order        |
| `subscription.created`  |                                                             | Copies the subscription into D1      |
| `subscription.updated`  |                                                             | Updates the copy of the subscription |

When an area starts to handle an event, add the event to every endpoint before you deploy that code. The code deployed until then acknowledges an event that no area handles with 200 and does nothing with it, so adding the event first is harmless, and `polar:verify` fails the deploy while an endpoint does not send every event in `POLAR_EVENTS`.

Copy the endpoint's signing secret into `POLAR_WEBHOOK_SECRET` in the same environment file. Development needs no endpoint, because Polar cannot reach `localhost`.

Never add a preview endpoint to the production organisation, or a production endpoint to the sandbox: real payments would reach preview, or test purchases would grant licences in production.

## Check the setup

```sh
bun run polar:verify:development
bun run polar:verify:preview
bun run polar:verify:production
```

Each script reads the Polar keys from `.env.<environment>` and sends only GET requests to the API that `POLAR_SERVER` names: it reads the organisation and lists its products and webhook endpoints, and changes nothing. It checks that:

- the environment file sets every Polar key, with `POLAR_SERVER=sandbox` for development and preview and `POLAR_SERVER=production` for production;
- checkout localization is on for the organisation, its default tax behaviour is location-based, and it lets every host of the environment embed its checkout;
- each `POLAR_PRODUCT_ID_*` names a product of the organisation that is neither archived nor a subscription, whose prices are fixed, in `DEFAULT_CURRENCY_CODE` and equal to `TIER_PRICES`;
- each product has exactly one licence-key benefit with the tier's limit from `LICENSE_ACTIVATION_LIMITS`, no expiration and no usage limit;
- each product requires the checkbox field <RepositoryFact name="licenseWithdrawalConsentField" /> with the label in `WITHDRAWAL_CONSENT_FIELD`;
- preview and production have an enabled raw endpoint at their webhook URL, signed with `POLAR_WEBHOOK_SECRET` and subscribed to exactly `POLAR_EVENTS`;
- no endpoint posts to the host of an environment that uses the other Polar service.

`polar:verify` is the Polar area's deploy check (`POLAR_DEPLOY_CHECKS` in `src/data/polar.deploy.ts`), so `deploy:preview` and `deploy:production` run it through `scripts/run-deploy-checks.ts`, after `scripts/verify-bindings.ts` and `scripts/prepare-deploy-secrets.ts` and before the build. CI deployments run none of the deploy checks, `polar:verify` included: `deploy-reusable.yml` has no `scripts/run-deploy-checks.ts` step, the GitHub environments hold no Polar token, and the Worker keeps the Polar secrets already set in Cloudflare. Run `polar:verify` yourself after every change in Polar.

## When it fails

The script exits with an error that lists every problem it found, one per line:

```text
Polar production does not match the code for production:
The core product (POLAR_PRODUCT_ID_CORE) has 0 licence-key benefits; it needs exactly one.
A webhook endpoint posts to https://preview.saasyland.com/api/auth/polar/webhooks, the preview host, from this Polar production organisation; remove it.
```

A failure stops the deploy before anything is built, migrated or uploaded. The script never changes Polar: fix Polar, then run it again. Each message names the key, constant or setting to fix:

- **`Set … in .env.<environment>`**: a Polar key is missing or empty, or `POLAR_SERVER` names the wrong service.
- **`rejects POLAR_ACCESS_TOKEN`**: the token is invalid, revoked or from the other service, such as a production token in `.env.preview`.
- **`lacks the … scope`**: create a token with the scopes above.
- **`names no product of the organisation`**: the product ID or `POLAR_ORGANIZATION_ID` is wrong, or belongs to the other service.
- **A price or licence key**: change it in Polar to match the code. When a business value changes on purpose, change `TIER_PRICES` or `LICENSE_ACTIVATION_LIMITS` first, then Polar.
- **`does not ask for the … checkout field`, `without requiring it`, `instead of a checkbox` or `label differs`**: create, attach or correct the [consent checkbox](#consent-checkbox). When the wording changes on purpose, change `WITHDRAWAL_CONSENT_FIELD.label` first, then the label in Polar.
- **`Checkout localization is off`**: turn on [checkout localization](#checkout-language) for the organisation.
- **`default tax behaviour is not location`**: set the organisation's [tax behaviour](#tax-behaviour) to location-based.
- **`does not let … embed its checkout`**: add the host the message names under [Settings > Embedding](#embedding).
- **A webhook endpoint**: fix the endpoint the message names, or remove an endpoint that posts to another environment's host.
