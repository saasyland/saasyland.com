Schemas liegen in den Tabellenmodulen und werden von `src/integrations/drizzle-orm/drizzle.schemas.ts` gesammelt. Migrationen sind SQL-Dateien mit Zeitstempel-Präfix in `src/integrations/drizzle-orm/migrations/`, die zusammen mit der Schemaänderung eingecheckt werden.

## Drei Datenbanken [#three-databases]

Jede Wrangler-Umgebung hat ihre eigene D1-Datenbank, und kein Skript und kein Server erreicht die Daten einer anderen Umgebung:

| Umgebung      | Datenbank                                    | Verwendet von                                         | Daten                                    |
| ------------- | -------------------------------------------- | ----------------------------------------------------- | ---------------------------------------- |
| `development` | Lokal `saasyland_local` in `.wrangler/state` | `bun run dev` und die `:local`-Skripte                | Gehören dir; `db:seed:local` befüllt sie |
| `preview`     | Remote `saasyland_com_preview`               | `preview.saasyland.com` und die `:preview`-Skripte    | Testkäufe mit der Sandbox von Polar      |
| `production`  | Remote `saasyland_com_production`            | `saasyland.com` und die `:production`-Skripte         | Kunden                                   |
| `test`        | Lokal `saasyland_test` in `.wrangler/test`   | Playwright, die isolierte Preview und `db:reset:test` | `db:seed:test` befüllt sie               |

`bun run dev` liest oder schreibt nie eine Remote-Datenbank. Jedes Binding der Umgebung `development` in `wrangler.jsonc` hat `remote: false`, das Cloudflare-Vite-Plugin läuft mit `remoteBindings: false` (`vite.config.ts`), und `src/__test__/wrangler.test.ts` schlägt fehl, wenn ein Binding der Entwicklung remote wird oder eine Datenbank, einen Namespace oder einen Bucket mit `preview` oder `production` teilt. Die anderen Bindings sind aus demselben Grund lokal:

- `CACHE` (KV) enthält nur einen Cache, den der Worker selbst wieder füllt, die Zahl der GitHub-Sterne, daher startet ein lokaler Namespace leer und funktioniert sofort.
- `MEDIA` und `BUNDLES` (R2) sind die lokalen Buckets `saasyland-local` und `saasyland-bundles-local`. Die Zeilen, die auf ihre Dateien verweisen, Videos, Lektionsmaterialien und Vorlagen-Bundles, liegen in D1, daher sähe eine lokale Datenbank mit Remote-Buckets Dateien von Preview, zu denen es keine Zeilen gibt, und hinterließe verwaiste Dateien in den Buckets von Preview.
- Better Auth speichert seine Benutzer, Sitzungen, Verifizierungstokens und Rate-Limits in D1, daher funktionieren Registrierung, Anmeldung und der Admin-Bereich lokal. E-Mails gehen weiterhin mit dem Schlüssel aus `.env.development` über Resend hinaus, und Polar-Aufrufe gehen an die Sandbox, die `POLAR_SERVER` nennt.

## Migrationen [#migrations]

1. Ändere `src/modules/<table>/<table>.schema.ts`.
2. Führe `bun run db:generate` aus und prüfe das erzeugte SQL.
3. Wende die Migration lokal mit `bun run db:migrate:local` an und führe die Tests aus; Vitest wendet jede Migration auf seine In-Memory-Datenbank an.
4. Deploye: Die Deploy-Skripte und die CI wenden die Migration auf die Preview- oder Produktionsdatenbank an, bevor der neue Worker live geht.

```sh
bun run db:generate
bun run db:migrate:local
bun run db:migrate:test
```

Weder die Installation der Abhängigkeiten noch ein Build migriert jemals eine Datenbank.

SQLite erzwingt die Länge in einem Spaltentyp wie `text(<length>)` nicht, und drizzle-kit ändert sie, indem es die Tabelle neu baut: eine neue Tabelle, jede Zeile hineinkopiert, die alte gelöscht. Deshalb gelten die Grenzen, die die Formulare und die Serverfunktionen prüfen, und eine Spalte behält die Länge, mit der sie angelegt wurde. `user.email` und `newsletter_subscriber.email` bleiben über `DECLARED_COLUMN_LENGTH` in `auth.constraints.ts` `text(<RepositoryFact name="declaredEmailColumnLength" />)` und `user.name` `text(<RepositoryFact name="declaredNameColumnLength" />)`, während eine Adresse <RepositoryFact name="emailMaxLength" /> Zeichen haben darf (`EMAIL_MAX_LENGTH`, die Pfadgrenze aus RFC 5321) und ein Name <RepositoryFact name="nameMaxLength" /> (`NAME_MAX_LENGTH`). Eine später angelegte Tabelle wie `withdrawal` deklariert `EMAIL_MAX_LENGTH` und `NAME_MAX_LENGTH` von Anfang an, sodass nichts neu gebaut werden muss. Eine erzeugte Migration, die ``CREATE TABLE `__new_`` enthält, baut eine Tabelle neu; prüfe sie, bevor du sie committest.

## Befehle

| Befehl                                                              | Datenbank                        | Macht                                                                                                                                            |
| ------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `bun run db:generate`                                               | keine                            | Eine neue Migration aus dem Schema-Diff (drizzle-kit)                                                                                            |
| `bun run db:migrate:local`                                          | Lokal `development`              | Wendet die Migrationen an                                                                                                                        |
| `bun run db:migrations:local`                                       | Lokal `development`              | Listet die noch nicht angewendeten Migrationen auf; ändert nichts                                                                                |
| `bun run db:reset:local`                                            | Lokal `development`              | Löscht `.wrangler/state/v3/d1` und wendet dann jede Migration an: eine leere Datenbank                                                           |
| `bun run db:seed:local`                                             | Lokal `development`              | Der lokale Admin, der Lehrplan, Lizenzen und eine Bestellung; siehe [Der lokale Seed](#the-local-seed)                                           |
| `bun run db:studio:local`                                           | Lokal `development`              | Drizzle Studio auf der lokalen SQLite-Datei                                                                                                      |
| `bun run admin:grant:local`                                         | Lokal `development`              | Macht ein verifiziertes Konto zum Admin; siehe [Der erste Admin](#the-first-admin)                                                               |
| `bun run db:migrate:test`                                           | Lokal `test` in `.wrangler/test` | Wendet die Migrationen an                                                                                                                        |
| `bun run db:seed:test`                                              | Lokal `test`                     | Testkonten, Lizenzen, Bestellungen, Newsletter-Abonnenten, ein Video, ein Kurs mit seinen Kapiteln und Lektionen und ein Vorlagen-Bundle der CLI |
| `bun run db:reset:test`                                             | Lokal `test`                     | Löscht `.wrangler/test` und führt dann `db:migrate:test` und `db:seed:test` aus                                                                  |
| `bun run db:migrate:preview`, `bun run db:migrate:production`       | Remote                           | Wendet die Migrationen an                                                                                                                        |
| `bun run db:migrations:preview`, `bun run db:migrations:production` | Remote                           | Listet die noch nicht angewendeten Migrationen auf; ändert nichts                                                                                |
| `bun run db:studio:preview`, `bun run db:studio:production`         | Remote                           | Drizzle Studio über die D1-HTTP-API                                                                                                              |
| `bun run db:introspect:preview`, `bun run db:introspect:production` | Remote                           | Introspektion mit drizzle-kit über die D1-HTTP-API                                                                                               |
| `bun run admin:grant:preview`, `bun run admin:grant:production`     | Remote                           | Macht ein verifiziertes Konto zum Admin; siehe [Der erste Admin](#the-first-admin)                                                               |
| `bun run courses:sync:preview`                                      | Remote `preview`                 | Kopiert die veröffentlichten Kurse der Produktion; siehe [Die Kurse nach Preview kopieren](#copying-the-courses-to-preview)                      |

`deploy:preview`, `deploy:production` und das Deployment in der CI führen `db:migrate:preview` oder `db:migrate:production` vor `wrangler deploy` aus. Kein Deployment befüllt eine Remote-Datenbank.

## Drizzle Studio

`bun run db:studio:local` führt `scripts/studio-local.ts` aus. Miniflare speichert die lokale Datenbank als eine SQLite-Datei in `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/`, benannt nach einem Hash der Datenbank-ID in `wrangler.jsonc`; das Skript ermittelt den Namen auf dieselbe Weise wie Miniflare, schlägt mit einem Hinweis fehl, wenn die Datei noch nicht existiert, und öffnet Drizzle Studio darauf mit `src/integrations/drizzle-orm/drizzle.local.config.ts`, das die Datei über `@libsql/client` liest. Studio und der Dev-Server können gleichzeitig laufen.

`bun run db:studio:preview` und `bun run db:studio:production` nutzen die D1-HTTP-API mit `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` und `CLOUDFLARE_ACCESS_TOKEN` aus `.env.preview` oder `.env.production`, über `src/integrations/drizzle-orm/drizzle.config.ts`. Jede Änderung dort ist eine Änderung an den Live-Daten dieser Umgebung.

## Der lokale Seed [#the-local-seed]

```sh
bun run db:reset:local
bun run db:seed:local
bun run dev
```

Stoppe den Dev-Server vor `db:reset:local`. `db:seed:local` (`scripts/seed-local.ts`) startet die lokalen Bindings der Umgebung `development` mit `getPlatformProxy` von Wrangler, schreibt Folgendes und kann jederzeit erneut laufen; es ändert nur, was abweicht:

- Einen Admin, <RepositoryFact name="localAdminEmail" />, mit bestätigter E-Mail-Adresse. Sein Passwort ist `LOCAL_ADMIN_PASSWORD` aus `.env.development` oder <RepositoryFact name="localAdminPassword" />, wenn es nicht gesetzt ist, und muss die Regeln der Registrierung erfüllen. Jeder Lauf setzt das Passwort neu. Verwende ein Passwort, das nur auf deinem Rechner existiert, nie eines aus der Produktion: Der Seed schreibt nur in die lokale Datenbank.
- Den Lehrplan aus `content/courses/saasy-land-courses.json`, importiert mit `planCourseImport` und `applyCourseImport` aus `src/modules/course/course.transfer.ts`, demselben Code wie **Importieren** im Admin-Bereich. Seine Lektionen haben noch kein Video und erscheinen daher als [„Wird aufgezeichnet“](/docs/features/courses#being-recorded).
- Die Titelbilder aus `content/courses/covers/`, benannt nach Slug, für die Kurse, die noch keines haben: Jede Größe kommt in den lokalen `MEDIA`-Bucket und der Kurs bekommt ihren Schlüssel, sodass der lokale Katalog wie der der Produktion aussieht.
- Die Lizenzen, die Bestellung ohne Lizenz und das Vorlagen-Bundle der CLI aus dem Test-Seed (`e2e/data/license.seed.ts`), damit das Admin-Dashboard und die Lizenzseiten Daten in echter Form haben. Ihre Kundenkonten verwenden das Passwort <RepositoryFact name="testPassword" />.

Jeder dieser Teile ist ein Element von `LOCAL_SEEDS` in `scripts/seed-local.ts` und steht in einer Datei seines eigenen Features: der Admin in `scripts/seed-local-admin.ts`, der Lehrplan und die Cover in `scripts/seed-local-courses.ts`, die Lizenzen in `e2e/data/license.seed.ts`. Eine ohne ein Feature gebaute Website hat für dieses kein Element und schreibt den Rest.

Melde dich unter http://localhost:3000/auth/sign-in mit dem Admin an und öffne `/admin/courses`, um die Kurse zu sehen.

## Kursdaten in jeder Umgebung [#course-data-in-each-environment]

- Lokal: `bun run db:seed:local` importiert den Lehrplan.
- Produktion: Ein Admin importiert `content/courses/saasy-land-courses.json` im Admin-Bereich. Melde dich als Admin an, öffne **Admin → Kurse**, wähle **Importieren**, wähle die Datei aus, führe **Datei prüfen** aus, lies den Plan und wähle dann **Importieren**. Wenn du dieselbe Datei erneut importierst, ändert sich nichts. Siehe [Import und Export](/docs/features/courses#import-and-export).
- Preview: `bun run courses:sync:preview` kopiert die veröffentlichten Kurse der Produktion, sodass Preview denselben Katalog zeigt wie die Produktion.

### Die Kurse nach Preview kopieren [#copying-the-courses-to-preview]

```sh
bunx wrangler login
bun run courses:sync:preview
```

`scripts/sync-courses.ts` erreicht D1 wie `admin:grant:*`, über `wrangler d1 execute --remote` und das gemeinsame `scripts/d1-execute.ts`. An die Produktion sendet es nur `SELECT`-Anweisungen, und Preview schreibt es in einem einzigen `--file`-Lauf. Es kopiert Zeile für Zeile, mit ihren IDs und Zeitstempeln:

- jeden veröffentlichten Kurs mit seinen Kapiteln, seinen Lektionen und deren Link-Anhängen; eine Zeile, die Preview schon hat, wird über ihre ID aktualisiert, sodass ein zweiter Lauf nichts ändert, was sich in der Produktion nicht geändert hat.

Es kopiert keine `video`-Zeilen und lässt die `video_id` jeder Lektion bei der Kopie aus: Die Dateien eines Videos liegen im `MEDIA`-Bucket der Produktion, daher beginnt eine Lektion, die für Preview neu ist, ohne Video und erscheint als [„Wird aufgezeichnet“](/docs/features/courses#being-recorded), statt beim Abspielen zu scheitern, und eine Lektion, die Preview schon hat, behält das Video, das im Lektionseditor von Preview hochgeladen wurde.

Innerhalb der kopierten Kurse löscht es die Kapitel, Lektionen und Link-Anhänge, die die Produktion nicht mehr hat, samt dem Fortschritt auf Preview in diesen Lektionen, und es löscht einen Preview-Kurs, den die Produktion nicht mehr veröffentlicht. Es kopiert keine Datei-Anhänge, deren Dateien im Bucket der Produktion liegen, und nichts außerhalb dieser Tabellen: keine Nutzer, Sitzungen, Lizenzen, Bestellungen, Abonnements, Uploads oder Fortschritte.

Es lässt `course.cover` beim Kopieren aus: Die Dateien eines Titelbilds liegen im `MEDIA`-Bucket der Produktion, deshalb hat ein Kurs, der neu in Preview ist, kein Titelbild, und ein Kurs, den Preview schon hat, behält das dort hochgeladene.

Es bricht vor dem Schreiben ab, wenn ein Preview-Kurs den Slug eines Produktionskurses mit einer anderen ID hat, etwa einer, der aus der Lehrplandatei importiert wurde; lösche diesen Kurs im Admin-Bereich von Preview und führe es dann erneut aus. Es gibt aus, was es in jeder Tabelle angelegt, aktualisiert und entfernt hat, zählt danach die Zeilen in Preview und schlägt fehl, wenn sie von denen der Produktion abweichen.

## Rabatte und Rechnungsländer älterer Bestellungen [#discounts-and-billing-countries-of-older-orders]

Die Migration `20261122143452_familiar_tusk.sql` hat der Kopie `order` den Rabatt und das Rechnungsland hinzugefügt ([Zahlungen](/docs/features/payments#orders-and-subscriptions-in-d1)). Neue Webhooks füllen sie, und eine vor der Migration kopierte Bestellung hat ein leeres `discount_amount`, bis Polar sie erneut sendet. So füllst du alle diese Bestellungen auf einmal:

```sh
bunx wrangler login
bun run orders:backfill:preview
bun run orders:backfill:production
```

`scripts/backfill-order-terms.ts` liest `POLAR_ACCESS_TOKEN` und `POLAR_SERVER` aus `.env.<environment>`, listet die Bestellungen mit leerem `discount_amount` mit `wrangler d1 execute` auf (remote für Preview und Produktion, lokal für `orders:backfill:local`) und liest jede mit `polar.orders.get` aus Polar, eine nach der anderen, wobei es so lange wartet, wie Polar verlangt, wenn es mit 429 antwortet. Es schreibt alle Bestellungen in einem einzigen `--file`-Lauf, jedes `UPDATE` beschränkt auf seine ID und auf ein leeres `discount_amount`, sodass es nie eine Kopie überschreibt, die ein Webhook inzwischen gefüllt hat, und ein zweiter Lauf nichts ändert. Es gibt aus, wie viele Bestellungen es kopiert hat, und beendet sich mit einem Fehler, solange noch eine übrig ist, etwa eine Bestellung, die Polar nicht mehr zurückgibt. Wende zuerst die Migration an.

## Der erste Admin [#the-first-admin]

Kein Endpunkt, keine Variable und kein Seed, der auf Preview oder Produktion läuft, vergibt die Rolle `admin`. Auf Preview und Produktion wird der erste Admin mit einem Skript angelegt, und das ist der einzige Weg:

```sh
bunx wrangler login
bun run admin:grant:production you@example.com
```

1. Registriere dich auf der Website mit der Adresse und öffne den Link in der Bestätigungs-E-Mail.
2. Melde dich bei Wrangler mit einem Cloudflare-Konto an, das in die D1-Datenbank der Umgebung schreiben darf.
3. Führe `bun run admin:grant:preview <email>` oder `bun run admin:grant:production <email>` aus.

`scripts/grant-admin.ts` liest das Konto mit `wrangler d1 execute --remote`, gibt es aus und lehnt eine Adresse ohne Konto, ein Konto mit unbestätigter E-Mail-Adresse und ein gesperrtes Konto ab. Danach setzt es `role` in dieser einen Zeile auf `admin`, liest das Konto erneut und gibt es aus. Ein Konto, das bereits Admin ist, bleibt unverändert.

Das ist aus drei Gründen sicher:

- Nur wer in die D1-Datenbank dieses Cloudflare-Kontos schreiben kann, kann es ausführen, mit dem eigenen `wrangler login`. Eine solche Person könnte ohnehin jede Zeile im Dashboard von Cloudflare ändern; das Skript öffnet keinen neuen Zugang.
- Es ändert eine Spalte eines einzigen Kontos, das nachgewiesen hat, dass ihm seine E-Mail-Adresse gehört.
- Die Anwendung setzt Rollen auf dem Server durch: `requireAdmin` schützt `/admin`, und jede Admin-Serverfunktion prüft ihre Berechtigung mit `authorized(...)` in `auth.middleware.ts`. Siehe [Rollen und Berechtigungen](/docs/guides/roles-and-permissions).

Weitere Admins legt ein bestehender Admin unter **Admin → Benutzerverwaltung** an: Öffne den Benutzer und dann **Rolle ändern**. `bun run admin:grant:local <email>` macht dasselbe für ein Konto, mit dem du dich lokal registriert hast. Ein bestehender Admin kann auch eine neue Adresse mit der Rolle `admin` einladen; siehe [Einladungen](/docs/features/users-admin#invitations).
