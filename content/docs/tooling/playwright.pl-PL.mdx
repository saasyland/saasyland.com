Playwright testuje zbudowaną aplikację w prawdziwych przeglądarkach. Testy działają w środowisku Wranglera `test`: lokalne D1, KV i R2 w `.wrangler/test`, fikcyjne dane dostępowe z `.env.test` i testowy punkt wejścia `src/platform/testing/worker.ts`, który przechwytuje żądania do Resend i Polara.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:journey
```

| Skrypt             | Uruchamia                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------ |
| `test:e2e:install` | Instaluje Chromium i WebKit wraz z zależnościami systemowymi                               |
| `test:e2e`         | Wszystkie testy w Chromium i WebKit                                                        |
| `test:e2e:smoke`   | `e2e/specs/smoke.spec.ts` w Chromium                                                       |
| `test:e2e:pr`      | Wszystkie testy w Chromium, tak jak uruchamia je kontrola Chromium w CI dla pull requestów |
| `test:e2e:headed`  | Wszystkie testy w widocznych oknach przeglądarek                                           |
| `test:e2e:ui`      | Tryb UI Playwrighta                                                                        |
| `test:journey`     | [Zestaw testów ścieżki klienta](#journey-suite) na preview                                 |

## Konfiguracja [#configuration]

`playwright.config.ts` uruchamia testy z `e2e/specs/`, definiuje projekty `chromium` (Desktop Chrome) i `webkit` (Desktop Safari) i używa `PLAYWRIGHT_BASE_URL` albo `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` z `src/data/local-server.ts`). Lokalnie polecenie serwera WWW uruchamia `db:reset:test`, `build:test` i `start:test`, a serwer, który już odpowiada pod tym adresem, wykorzystuje ponownie. W CI jedno zadanie przygotowuje build, każdy z <RepositoryFact name="e2eShards" /> shardów, na które podzielono testy, go rozpakowuje, a Playwright tylko uruchamia serwer ([CI/CD](/docs/tooling/ci-cd#checks)).

| -------------- | ------------------------------------------------ | --------------------------------------------- |
| Ponowienia     | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" /> |
| Workery        | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" /> |
| Ślady          | Zachowywane przy błędzie                         | Przy pierwszym ponowieniu                     |
| Nagrania wideo | Wyłączone                                        | Zachowywane przy błędzie                      |

## Uruchamianie obok innych worktree [#running-beside-other-worktrees]

Build testowy przyjmuje żądania tylko z hostów, którym ufa w trybie testowym, bo Better Auth i linki newslettera sprawdzają host żądania: `127.0.0.1:3000` i `localhost:3000` oraz `127.0.0.1` i `localhost` na portach od <RepositoryFact name="testServerFirstPort" /> do <RepositoryFact name="testServerLastPort" />, wyznaczonych przez `TEST_SERVER_PORTS` w `src/data/local-server.ts`. Na każdym innym porcie strony logowania i kursów nie działają, więc `playwright.config.ts` zatrzymuje się, zanim cokolwiek zbuduje, gdy `PLAYWRIGHT_BASE_URL` wskazuje inny host.

`PLAYWRIGHT_BASE_URL` to jedyne ustawienie, które wybiera port: Playwright otwiera ten adres i uruchamia `start:test` na jego porcie. Gdy inne worktree uruchamiają swoje testy w tym samym czasie, daj każdemu worktree własny port z zakresu. Sprawdź, czy nic na nim nie nasłuchuje, a potem uruchom na nim testy:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` nic nie wypisuje, gdy port jest wolny. Jeśli wypisze proces, weź inny port i zostaw ten serwer w spokoju: zatrzymuj tylko serwery uruchomione przez Ciebie.

Lokalnie Playwright wykorzystuje ponownie serwer, który już odpowiada pod adresem, i pomija wtedy reset bazy danych i build, więc testy nie mogą nigdy trafić na serwer innego worktree. Pilnuje tego `e2e/global-setup.ts`: przed pierwszym testem sprawdza przez `lsof` procesy nasłuchujące na porcie i przerywa przebieg, gdy któryś z nich działa w innym katalogu niż ten worktree. Serwer uruchomiony z tego worktree przechodzi sprawdzenie i jest używany taki, jaki jest, więc zatrzymaj go, gdy testy mają sprawdzić świeży build.

## Struktura

- `e2e/specs/`: testy smoke, strony głównej i jej kontrolek, nawigacji, języków, motywu, SEO, uwierzytelniania z przekierowaniami i routingiem, paneli, administracji użytkownikami, newslettera, treści, stron prawnych, cen regionalnych, ścieżki zakupu, strony licencji, API licencji CLI, programu partnerskiego, wideo, kursów, dostępu do kursów, administracji kursami, okładek, importu i materiałów kursów, pulpitu panelu administracyjnego, zamówień, produktów i urządzeń z licencją, listy wpisów bloga i ich udostępniania, Content Security Policy, odstąpienia od umowy, stopki, obwódek fokusu, pasków przewijania, webhooków licencji, opublikowanego CLI i dostępności (liczba plików: <RepositoryFact name="e2eSpecs" />).
- `e2e/pages/`: obiekty stron (page objects).
- `e2e/fixtures/`: rozszerzony fixture `test`, funkcje pomocnicze do przechwyconych e-maili, `deliverPaidOrder` w `license.ts`, który wysyła podpisany webhook `order.paid`, aby przyznać licencję, `buyLicense`, który prosi testowego Workera pod `/__test/polar/purchase` o zamówienie i jego klucz licencyjny w atrapie Polara, a potem wysyła ich podpisane `order.paid` i `benefit_grant.created`, `startedCheckouts`, który odczytuje z `/__test/polar/checkouts` płatności utworzone przez atrapę, `payCheckout`, który przez `/__test/polar/pay` testowego Workera opłaca płatność otwartą przez aplikację, z zaznaczoną zgodą, i wysyła podpisane `order.paid` i `benefit_grant.created` jej zamówienia, `accessibilityViolations` z jasnym i ciemnym schematem kolorów `COLOR_SCHEMES` w `accessibility.ts` oraz stronę płatności Polara w `polar-checkout.ts`. Atrapa Polara nadaje każdej płatności adres URL w originie strony płatności Polara, a `servePolarCheckout`, jeden z `BROWSER_DOUBLES` instalowanych przez automatyczny fixture `browserDoubles`, w każdym kontekście przeglądarki odpowiada na ten adres stroną atrapy, odczytaną z `/__test/polar/checkout` testowego Workera: strona informuje nakładkę, że się załadowała, a jej przyciski **Pay** i **Close** wysyłają `confirmed` i `success` albo `close` do `embed_origin` płatności, tak jak strona Polara. `payInCheckoutOverlay` i `closeCheckoutOverlay` je naciskają, a `refusePolarCheckoutEmbedding` serwuje stronę z `frame-ancestors 'none'`, tak jak Polar robi to dla hosta, którego jego organizacja nie wymienia. Zestaw testów ścieżki klienta ustawia opcję `browserDoublesEnabled` na `false` i płaci w prawdziwym sandboksie. `orderLicense` wysyła tylko `order.paid` takiego zakupu i zwraca `issueKey`, który później wysyła jego `benefit_grant.created`. Gdy strona atrapy jest otwarta jako samodzielna strona płatności Polara, poza ramką, jej przycisk **Pay** przenosi przeglądarkę na adres sukcesu płatności z `customer_session_token`, tak jak strona Polara, a `payOnPolarCheckoutPage` go naciska. `refundOrder`, `revokeLicenseKey`, `deliverGuestOrder` i `cutOffPolar` proszą testowego Workera pod `/__test/polar/refund`, `/__test/polar/revoke`, `/__test/polar/guest-purchase` i `/__test/polar/cut-off` o podpisany `order.refunded` zamówienia z atrapy, podpisany `benefit_grant.revoked` jego klucza, podpisany `order.paid` kupującego bez konta albo o klucz, którego żądania do Polara kończą się błędem, jakby Polar był nieosiągalny. `signUpBuyer` w `buyer.ts` rejestruje kupującego przez API, `sendToApi` w `cli-api.ts` wywołuje API licencji CLI z własnego adresu, a `EVERY_STACK_ANSWER` w `stack-answers.ts` zawiera poprawny zestaw odpowiedzi dla każdej opcji i każdego dodatku stacku.
- `e2e/data/accounts.ts`: konta z danych początkowych, administrator i klient, oraz ich hasło. `e2e/data/licenses.ts` zawiera klienta z licencją, tę licencję i po jednej licencji na każdego równoległego workera, na której spec API licencji CLI aktywuje urządzenia.
- `e2e/data/videos.ts` i `e2e/data/courses.ts`: film testowy z danych początkowych, którego pliki są w `e2e/fixtures/video/`, i kurs z danych początkowych: dwa rozdziały, pierwszy z darmowym podglądem, lekcją dla zalogowanych i płatną lekcją, drugi z trzema płatnymi lekcjami, których film jest jeszcze nagrywany.
- `e2e/data/<feature>.pages.ts` i `e2e/data/<feature>.seed.ts`: strony każdej funkcji, które odwiedzają `accessibility.spec.ts` i `workspaces.spec.ts`, oraz jej wiersze i media w testowej bazie danych; każdą listę importuje `ENTRIES` w `e2e/data/pages.ts` i `scripts/seed-test.ts`.
- `e2e/data/<feature>.flows.ts`: przepływy każdej funkcji, każdy z testem, który sprawdza go od początku do końca, albo z powodem, dla którego takiego testu brakuje, importowane przez `FLOWS` w `scripts/check-flows.ts`; zobacz [Pokrycie testami](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: globalne przygotowanie testów, które przerywa przebieg, gdy serwer na porcie testów działa z innego worktree.
- `e2e/journey/`: [zestaw testów ścieżki klienta](#journey-suite) z własną konfiguracją. `published-cli.spec.ts` uruchamia opublikowane CLI przez `runCli` z `e2e/journey/cli.ts` na testowym Workerze, więc zestaw testów przeglądarkowych potrzebuje rejestru npm.

Testowy Worker uruchamia to, co funkcje deklarują w `e2e/data/<feature>.worker.ts`; każdą listę importuje `ENTRIES` w `src/platform/testing/worker.ts`: funkcja licencji zapisuje testowe klucze licencyjne w atrapie Polara, Resend udostępnia `/__test/emails` do odczytu przechwyconych e-maili, a newsletter `/__test/newsletter` do odczytu stanu subskrybenta.

## Dostępność

`e2e/specs/accessibility.spec.ts` uruchamia [axe-core](https://github.com/dequelabs/axe-core) przez `@axe-core/playwright` na stronach publicznych, na stronach kursów, na stronie głównej dokumentacji, na każdej stronie sekcji Konwencje i na jednej stronie z każdej innej sekcji dokumentacji, we wpisie na blogu oraz w panelu administracyjnym i panelu klienta, w jasnym i ciemnym motywie. Wśród stron administracyjnych są `/admin/courses`, `/admin/courses/create` i edytor kursu z danych początkowych, które odwiedza też `e2e/specs/workspaces.spec.ts`. Test stosuje reguły WCAG 2.0, 2.1 i 2.2 na poziomach A i AA oraz dobre praktyki axe, zgłasza błąd, gdy strona nie załaduje się z kodem powodzenia, przewija stronę, aby sprawdzić też sekcje, które pojawiają się przy przewijaniu, czeka na koniec skończonych animacji i zgłasza błąd przy każdym naruszeniu, podając regułę, jej wagę i selektory elementów.

axe nie widzi ani nawigacji klawiaturą, ani układu, więc trzy pliki testów sprawdzają je w nagłówku i stopce strony: `e2e/specs/navigation.spec.ts`, że menu na telefonie przenosi fokus do siebie, zatrzymuje w sobie Tab, ustawia stronę pod spodem jako `inert` i oddaje fokus swojemu przyciskowi; `e2e/specs/footer.spec.ts`, że przy 320, 390 i 430 px w żadnym języku żadne dwa linki stopki się nie stykają ani nie wychodzą poza stopkę i że link do sekcji strony głównej jest oznaczony jako bieżący tylko w swojej sekcji; a `e2e/specs/focus-rings.spec.ts`, że przełącznik języka w stopce i przycisk palety poleceń w panelu administracyjnym rysują obwódkę fokusu przy obsłudze klawiaturą.

`e2e/specs/text-layout.spec.ts` sprawdza formularz kursu i tabele panelu administracyjnego oraz kreator polecenia na stronie głównej przy 1440, 1280, 768 i 390 px za pomocą `textLayoutProblems` z `e2e/fixtures/text-layout.ts`: żaden wiersz tekstu nie nachodzi na inny ani na ikonę, żaden nie jest ucięty bez wielokropka, żadnego wielokropek nie skraca do kilku liter, strona nigdy nie przewija się w bok, a każda karta języka w formularzu kursu jest widoczna. Tekst przewijany pod przypiętą kolumną albo pod nagłówkiem, który zostaje na miejscu, jest przez nie zasłonięty, dlatego test porównuje tekst w takich nieruchomych elementach tylko z tekstem w innych nieruchomych elementach. Osobny test otwiera każdą tabelę panelu administracyjnego po angielsku i po ukraińsku, bo ukraińskie nagłówki kolumn są najdłuższe, i kończy się błędem, gdy nagłówek nie mieści się w swojej komórce.

## Paski przewijania [#scrollbars]

`e2e/specs/scrollbars.spec.ts` uruchamia Chromium bez przełącznika `--hide-scrollbars`, który dodaje Playwright, przez `ignoreDefaultArgs` w `launchOptions`, więc Chromium rysuje klasyczne paski przewijania, które zajmują miejsce, jak w Windowsie, w Linuksie i na Macu z włączonym stałym wyświetlaniem pasków. Test sprawdza, że strona prawna, strona logowania i strona panelu administracyjnego nie przesuwają nagłówka, gdy okno rośnie, aż strona przestaje się przewijać (strona dokumentacji przewija się zawsze, bo pod jej układem na pełną wysokość okna jest jeszcze stopka strony), że otwarcie wyszukiwarki dokumentacji, wyboru języka, okna dialogowego albo menu niczego nie przesuwa, że `/admin` wypełnia okno i że okno za ciemną stroną jest ciemne w jasnym motywie. WebKit na macOS rysuje tylko nakładane paski przewijania, które nie zajmują miejsca, i żadna opcja uruchomienia tego nie zmienia, więc sprawdzenie zarezerwowanego miejsca działa tylko w Chromium. Menu strony, które poniżej `lg` zastępuje linki w nagłówku, jest sprawdzane przy 768 px: jego otwarcie i zamknięcie niczego nie przesuwa.

## Zestaw testów ścieżki klienta [#journey-suite]

`bun run test:journey` kupuje licencję i używa CLI tak jak klient, na wdrożeniu preview pod adresem `https://preview.saasyland.com`, które przyjmuje płatności w sandboksie Polara. `e2e/journey/playwright.config.ts` to osobna konfiguracja z własnym projektem Chromium i bez serwera WWW, więc nie uruchamia jej ani `test:e2e`, ani kontrole pull requestów; `journey.yml` uruchamia ją co noc i ręcznie ([CI/CD](/docs/tooling/ci-cd#journey-suite)). Każdy pakiet ma osobny test z tagiem `@core`, `@complete` lub `@agency`, testy działają równolegle, a każdy przechodzi przez te kroki:

1. **Konto.** Test zakłada konto z nowym adresem testowej skrzynki Resend, `delivered+journey-<run>-<tier>@resend.dev`, a w teście przejścia na wyższy pakiet z `upgrade` w miejscu pakietu, znajduje e-mail weryfikacyjny przez API Resend i otwiera link z tej wiadomości.
2. **Cena.** `/app/license` musi oferować pakiet w cenie dla kraju, w którym Cloudflare umieszcza runnera, tak jak podaje `/cdn-cgi/trace`: w cenie regionalnej w kraju z `PPP_TIERS`, a w pełnej cenie w każdym innym.
3. **Płatność.** Strona płatności sandboksu Polara musi się otworzyć nad `/app/license`, w ramce z `sandbox.polar.sh`, która przejmuje fokus, bez opuszczania strony, z wypełnionym adresem e-mail konta i niezaznaczoną zgodą na natychmiastowe dostarczenie; test zaznacza ją w ramce. Test płaci [kartą testową Stripe](https://docs.stripe.com/testing) z adresem rozliczeniowym w Polsce, gdzie adres rozliczeniowy to tylko kraj. Strona musi odebrać komunikaty Polara `loaded`, `confirmed` i `success` w tej kolejności, zamknąć nakładkę i pokazać aktywną licencję pod `/app?checkoutId=<id>&tier=<tier>`. Polar osadza stronę płatności w ramce tylko wtedy, gdy organizacja w sandboksie wymienia `preview.saasyland.com` w [Settings > Embedding](/docs/getting-started/polar-setup#embedding).
4. **Zamówienie i klucz.** Polar musi mieć jedno opłacone zamówienie na produkt danego pakietu, w cenie zaoferowanej przez `/app/license`, ze zgodą i językiem kupującego, potwierdzenie zakupu musi dotrzeć do skrzynki, a `/app/license` musi pokazywać klucz wydany przez webhooki, polecenia CLI i ani jednego zajętego urządzenia.
5. **CLI.** Opublikowane CLI, uruchamiane jako <RepositoryFact name="cliExec" /> tak jak polecenia z `/app/license`, łączy się z preview przez `SAASYLAND_API_URL`. `activate` zapisuje plik z danymi dostępowymi z uprawnieniami `0600`, ponowna aktywacja zachowuje to samo miejsce aktywacji, a `whoami` pokazuje urządzenie. Urządzenia CI, rozróżniane przez `SAASYLAND_CI_REPOSITORY`, zajmują pozostałe miejsca aktywacji, do <ActivationLimit tier="core" /> urządzeń w pakiecie Podstawa, <ActivationLimit tier="complete" /> w pakiecie Komplet i <ActivationLimit tier="agency" /> w pakiecie Agencja, a kolejne zostaje odrzucone z kodem `activationLimitReached`. Gdy na `/app/license` zostanie zwolnione miejsce aktywacji, dostaje je odrzucone urządzenie, a zwolnione otrzymuje `activationNotFound`. `deactivate` zwalnia pierwsze urządzenie i usuwa jego dane dostępowe.
6. **Zwrot.** Test zwraca pieniądze za zamówienie przez API sandboksu Polara i czeka, aż `/app/license` pokaże licencję jako zwróconą; wtedy `whoami` musi odpowiedzieć `licenseRefunded` i usunąć dane dostępowe.

Czwarty test, z tagiem `@upgrade`, przenosi licencję na wyższy pakiet. Kupuje pakiet Podstawa w ten sam sposób i wyczerpuje jego limit <ActivationLimit tier="core" /> urządzeń, a następne urządzenie zostaje odrzucone. Potem `/app/license?tier=complete` musi oferować pakiet Komplet w cenie dla kraju runnera pomniejszonej o koszt zamówienia pakietu Podstawa, a test płaci tę różnicę tak samo, na stronie płatności Polara nad stroną. Polar musi mieć zamówienie przejścia na wyższy pakiet na kwotę różnicy, z zamówieniem i pakietem Podstawa w `upgrade_from_order` i `upgrade_from_tier`; klucz z zamówienia pakietu Podstawa musi teraz mieć limit <ActivationLimit tier="complete" /> urządzeń z pakietu Komplet, klucz, który Polar przyznał za zamówienie przejścia, musi być wyłączony, a `/app/license` musi pokazywać pakiet Komplet z tym samym kluczem. Potem odrzucone urządzenie i następne zostają aktywowane, a kolejne zostaje odrzucone. Test zwraca pieniądze za zamówienie przejścia przez API sandboksu Polara: licencja musi znów być w pakiecie Podstawa, z tym samym kluczem i limitem pakietu Podstawa, aktywne już urządzenia dalej działają, a nowe zostaje odrzucone. Zwrot za zamówienie pakietu Podstawa kończy potem licencję.

Każde urządzenie CLI to katalog w folderze wyników testu, którego CLI używa jako katalogu domowego, a CLI działa w środowisku, w którym jest tylko `PATH`, ten katalog, pamięć podręczna npm i zmienne `SAASYLAND_*`, więc nie trafiają do niego żadne dane dostępowe zestawu. Zamówienie, które nieudany test zostawi opłacone, jest zwracane po zakończeniu testu. Konta zostają na preview, każde ze zwróconą licencją.

Zestaw odczytuje te wartości ze środowiska albo z `.env.preview`, jeśli ten plik istnieje, i bez nich zatrzymuje się przed pierwszym testem; w CI `journey.yml` odczytuje je ze środowiska `Preview` na GitHubie:

| Zmienna                                                                         | Do czego służy                                                                                                                                               |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POLAR_ACCESS_TOKEN`                                                            | Odczyt zamówień i zwroty w sandboksie oraz odczyt ich kluczy licencyjnych, z zakresami `orders:read`, `refunds:write`, `benefits:read` i `license_keys:read` |
| `POLAR_SERVER`                                                                  | Musi mieć wartość `sandbox`                                                                                                                                  |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Produkty w sandboksie, których muszą dotyczyć zamówienia                                                                                                     |
| `RESEND_API_KEY`                                                                | Odczyt e-maili weryfikacyjnych wysłanych przez preview, do czego potrzebny jest klucz z pełnym dostępem                                                      |

Na preview musi działać build z [API licencji CLI](/docs/features/cli-licence-api). Działa na nim gałąź `main`, którą `deploy.yml` wdraża tam przed produkcją; aby przetestować gałąź przed jej scaleniem, wdróż ją poleceniem `gh workflow run preview.yml --ref <branch>`, gdy jej kontrole przejdą. Sandbox musi zgadzać się z kodem, co sprawdza `bun run polar:verify:preview`. Następnie:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

`bun run test:journey --grep @core` uruchamia tylko test z tym tagiem. Raport HTML trafia do `playwright-report/journey/`, raport JSON do `playwright-report/journey.json`, a ślady, nagrania i katalogi urządzeń z nieudanych testów do `test-results/journey/`.
