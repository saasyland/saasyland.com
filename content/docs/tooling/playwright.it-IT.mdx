Playwright testa l'applicazione compilata in browser reali. La suite viene eseguita sull'ambiente Wrangler `test`: D1, KV e R2 locali in `.wrangler/test`, credenziali fittizie da `.env.test` e l'entry point di test `src/platform/testing/worker.ts`, che intercetta le richieste a Resend e Polar.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:visual
bun run test:visual:update
bun run test:journey
```

| Script               | Esegue                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------- |
| `test:e2e:install`   | Installa Chromium e WebKit con le dipendenze di sistema                                     |
| `test:e2e`           | Tutte le spec in Chromium e WebKit                                                          |
| `test:e2e:smoke`     | `e2e/specs/smoke.spec.ts` in Chromium                                                       |
| `test:e2e:pr`        | Tutte le spec in Chromium, come le esegue il controllo Chromium della CI delle pull request |
| `test:e2e:headed`    | Tutte le spec in browser visibili                                                           |
| `test:e2e:ui`        | Modalità UI di Playwright                                                                   |
| `test:visual`        | I [test visivi](#visual-tests) in Chromium dall'immagine Docker di Playwright               |
| `test:visual:update` | I test visivi, riscrivendo gli screenshot che non corrispondono più                         |
| `test:journey`       | La [suite del percorso cliente](#journey-suite) sulla preview                               |

## Configurazione [#configuration]

`playwright.config.ts` esegue le spec in `e2e/specs/`, definisce i progetti `chromium` (Desktop Chrome) e `webkit` (Desktop Safari) e usa `PLAYWRIGHT_BASE_URL` oppure `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` da `src/data/local-server.ts`). In locale il comando del web server esegue `db:reset:test`, `build:test` e `start:test`, e riutilizza un server che risponde già a quell'URL. In CI un job prepara la build, ciascuno dei <RepositoryFact name="e2eShards" /> shard che si dividono la suite la estrae, e Playwright si limita ad avviare il server ([CI/CD](/docs/tooling/ci-cd#checks)).

| Impostazione | Locale                                           | CI                                             |
| ------------ | ------------------------------------------------ | ---------------------------------------------- |
| Retry        | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" />  |
| Worker       | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" />  |
| Trace        | Conservate in caso di errore                     | Al primo retry                                 |
| Video        | Disattivati                                      | Conservati in caso di errore                   |
| Reporter     | List e HTML                                      | GitHub e blob, uniti in HTML in caso di errore |

## Eseguire la suite accanto ad altri worktree [#running-beside-other-worktrees]

La build di test accetta richieste solo dagli host di cui si fida in modalità test, perché Better Auth e i link della newsletter controllano l'host della richiesta: `127.0.0.1:3000` e `localhost:3000`, e `127.0.0.1` e `localhost` sulle porte da <RepositoryFact name="testServerFirstPort" /> a <RepositoryFact name="testServerLastPort" />, fissate da `TEST_SERVER_PORTS` in `src/data/local-server.ts`. Su qualsiasi altra porta le pagine di accesso e dei corsi falliscono, quindi `playwright.config.ts` si ferma prima di compilare qualcosa quando `PLAYWRIGHT_BASE_URL` indica un altro host.

`PLAYWRIGHT_BASE_URL` è l'unica impostazione che sceglie la porta: Playwright apre quell'URL e avvia `start:test` sulla sua porta. Quando altri worktree eseguono le loro suite nello stesso momento, dai a ogni worktree una porta tutta sua dell'intervallo. Controlla che nulla sia in ascolto su quella porta, poi eseguici la suite:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` non stampa nulla quando la porta è libera. Se stampa un processo, prendi un'altra porta e lascia stare quel server: ferma solo i server che hai avviato tu.

In locale Playwright riutilizza un server che risponde già all'URL e salta allora il reset del database e la build, quindi la suite non deve mai raggiungere il server di un altro worktree. `e2e/global-setup.ts` lo garantisce: prima del primo test cerca con `lsof` i processi in ascolto sulla porta e ferma l'esecuzione quando uno di essi gira in una directory diversa da questo worktree. Un server che hai avviato da questo worktree supera il controllo e viene riutilizzato così com'è, quindi fermalo quando la suite deve testare una build nuova.

## Struttura

- `e2e/specs/`: spec per smoke test, landing page e i suoi controlli, navigazione, locale, tema, SEO, autenticazione con i suoi reindirizzamenti e il suo routing, aree di lavoro, amministrazione degli utenti, newsletter, contenuti, pagine legali, prezzi regionali, funnel di checkout, pagina della licenza, API delle licenze della CLI, affiliati, video, corsi, accesso ai corsi, amministrazione dei corsi, copertine, importazione e materiali dei corsi, dashboard di amministrazione, ordini, prodotti e macchine delle licenze, indice del blog e condivisione degli articoli, Content Security Policy, recesso, footer, anelli di focus, barre di scorrimento, webhook delle licenze, CLI pubblicata e accessibilità (<RepositoryFact name="e2eSpecs" /> file).
- `e2e/pages/`: page object.
- `e2e/fixtures/`: la fixture `test` estesa, gli helper per le email intercettate, `deliverPaidOrder` in `license.ts`, che invia un webhook `order.paid` firmato per concedere una licenza, `buyLicense`, che chiede al Worker di test su `/__test/polar/purchase` un ordine con la sua chiave di licenza nel test double di Polar e invia i loro `order.paid` e `benefit_grant.created` firmati, `startedCheckouts`, che legge da `/__test/polar/checkouts` i checkout creati dal double, `payCheckout`, che paga un checkout aperto dall'app tramite `/__test/polar/pay` del Worker di test, con il consenso spuntato, e invia i `order.paid` e `benefit_grant.created` firmati del suo ordine, `accessibilityViolations` con i `COLOR_SCHEMES` chiaro e scuro in `accessibility.ts`, e la pagina di checkout di Polar in `polar-checkout.ts`. Il double di Polar assegna a ogni checkout un URL sull'origine del checkout di Polar, e `servePolarCheckout`, uno dei `BROWSER_DOUBLES` che la fixture automatica `browserDoubles` installa, risponde a quell'URL in ogni contesto del browser con una pagina del double, letta da `/__test/polar/checkout` del Worker di test: comunica all'overlay che è stata caricata, e i suoi pulsanti **Pay** e **Close** inviano `confirmed` e `success`, oppure `close`, all'`embed_origin` del checkout, come fa la pagina di Polar. `payInCheckoutOverlay` e `closeCheckoutOverlay` li premono, e `refusePolarCheckoutEmbedding` serve la pagina con `frame-ancestors 'none'`, come fa Polar per un host che la sua organizzazione non elenca. La suite del percorso cliente imposta l'opzione `browserDoublesEnabled` a `false` e paga sulla sandbox reale. `orderLicense` invia solo l’`order.paid` di un acquisto del genere e restituisce `issueKey`, che invia più tardi il suo `benefit_grant.created`. Aperto come la pagina di pagamento di Polar stessa, fuori da un frame, il pulsante **Pay** del double manda il browser all’URL di successo del checkout con un `customer_session_token`, come fa la pagina di Polar, e `payOnPolarCheckoutPage` lo preme. `refundOrder`, `revokeLicenseKey`, `deliverGuestOrder` e `cutOffPolar` chiedono al Worker di test su `/__test/polar/refund`, `/__test/polar/revoke`, `/__test/polar/guest-purchase` e `/__test/polar/cut-off` un `order.refunded` firmato di un ordine del double, un `benefit_grant.revoked` firmato della sua chiave, un `order.paid` firmato di un acquirente senza account o una chiave le cui richieste a Polar falliscono come se Polar non fosse raggiungibile. `signUpBuyer` in `buyer.ts` registra un acquirente tramite l’API, `sendToApi` in `cli-api.ts` chiama l’API delle licenze della CLI da un indirizzo tutto suo e `EVERY_STACK_ANSWER` in `stack-answers.ts` raccoglie un insieme valido di risposte per ogni opzione e ogni extra dello stack.
- `e2e/data/accounts.ts`: gli account creati dal seed, un admin e un cliente, e la loro password. `e2e/data/licenses.ts` contiene il cliente con licenza e la sua licenza, oltre a una licenza per ogni worker parallelo su cui la spec dell'API delle licenze della CLI attiva i dispositivi.
- `e2e/data/videos.ts` e `e2e/data/courses.ts`: il video di test creato dal seed, i cui file sono in `e2e/fixtures/video/`, e il corso creato dal seed: due capitoli, il primo con un'anteprima gratuita, una lezione per chi ha un account e una lezione a pagamento, il secondo con tre lezioni a pagamento il cui video è ancora in registrazione.
- `e2e/data/<feature>.pages.ts` e `e2e/data/<feature>.seed.ts`: le pagine di ogni funzionalità, visitate da `accessibility.spec.ts` e `workspaces.spec.ts`, e le sue righe e i suoi media nel database di test, ogni lista importata da `ENTRIES` in `e2e/data/pages.ts` e da `scripts/seed-test.ts`.
- `e2e/data/<feature>.flows.ts`: i flussi di ogni funzionalità, ognuno con il test che lo dimostra end-to-end o il motivo per cui manca, importati da `FLOWS` in `scripts/check-flows.ts`; vedi [Copertura dei test](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: il setup globale, che ferma l'esecuzione quando il server sulla porta della suite gira da un altro worktree.
- `e2e/journey/`: la [suite del percorso cliente](#journey-suite), con la sua configurazione. `published-cli.spec.ts` esegue la CLI pubblicata con `runCli` di `e2e/journey/cli.ts` contro il Worker di test, quindi la suite del browser ha bisogno del registro npm.

Il Worker di test esegue ciò che le funzionalità dichiarano in `e2e/data/<feature>.worker.ts`, ogni lista importata da `ENTRIES` in `src/platform/testing/worker.ts`: la funzionalità delle licenze inserisce le chiavi di licenza di test nel mock di Polar, Resend espone `/__test/emails` per leggere le email intercettate e la newsletter `/__test/newsletter` per leggere lo stato di un iscritto.

## Accessibilità

`e2e/specs/accessibility.spec.ts` esegue [axe-core](https://github.com/dequelabs/axe-core) tramite `@axe-core/playwright` sulle pagine pubbliche, sulle pagine dei corsi, sulla home della documentazione, su ogni pagina di Convenzioni e su una pagina di ciascuna delle altre sezioni della documentazione, su un articolo del blog e sulle aree di lavoro di amministrazione e cliente, nei temi chiaro e scuro. Le pagine di amministrazione includono `/admin/courses`, `/admin/courses/create` e l'editor del corso di test, che visita anche `e2e/specs/workspaces.spec.ts`. Applica le regole A e AA di WCAG 2.0, 2.1 e 2.2 insieme alle best practice di axe, fallisce se una pagina non si carica con uno stato di successo, scorre la pagina perché vengano controllate anche le sezioni che compaiono durante lo scorrimento, attende la fine delle animazioni finite e fallisce a ogni violazione, riportando la regola, il suo impatto e i selettori coinvolti.

axe non vede né il percorso da tastiera né il layout, quindi tre spec li verificano per l'intestazione e il footer del sito: `e2e/specs/navigation.spec.ts`, che il menu del telefono porta il focus su di sé, tiene Tab al suo interno, rende `inert` la pagina dietro e restituisce il focus al suo pulsante; `e2e/specs/footer.spec.ts`, che a <RepositoryFact name="footerPhoneWidths" /> px nessun link del footer ne tocca un altro o esce dal footer, in nessuna lingua, e che un link a una sezione della landing page è corrente solo sulla propria sezione; e `e2e/specs/focus-rings.spec.ts`, che il selettore della lingua del footer e il trigger della palette dei comandi dell'amministrazione disegnano il loro anello per la tastiera.

`e2e/specs/text-layout.spec.ts` controlla il modulo dei corsi e le tabelle dell’amministrazione e il generatore di comandi della landing page a <RepositoryFact name="textLayoutWidths" /> px con `textLayoutProblems` di `e2e/fixtures/text-layout.ts`: nessuna riga di testo si sovrappone a un’altra o a un’icona, nessuna viene tagliata senza puntini di sospensione, nessuna viene ridotta a poche lettere dai puntini, la pagina non scorre mai in orizzontale e ogni scheda di lingua del modulo dei corsi è visibile. Il testo che scorre sotto una colonna fissata o un'intestazione fissa ne resta coperto, quindi il controllo confronta il testo fisso solo con altro testo fisso. Un altro test apre ogni tabella dell'area di amministrazione in inglese e in ucraino, la lingua con le intestazioni più lunghe, e fallisce quando un'intestazione è più larga della sua cella.

## Barre di scorrimento [#scrollbars]

`e2e/specs/scrollbars.spec.ts` avvia Chromium senza l'opzione `--hide-scrollbars` di Playwright, tramite `ignoreDefaultArgs` in `launchOptions`, così Chromium disegna barre di scorrimento classiche che occupano spazio, come su Windows, su Linux e su un Mac impostato per mostrarle sempre. La spec verifica che una pagina legale, una di autenticazione e una dell'amministrazione tengano fermo il titolo quando la finestra cresce finché la pagina non scorre più (una pagina della documentazione scorre sempre, perché il footer del sito segue il suo layout alto quanto la finestra), che aprire la ricerca della documentazione, il selettore della lingua, una finestra di dialogo o un menu non sposti nulla, che `/admin` riempia la finestra e che la finestra dietro una pagina scura sia scura con il tema chiaro. WebKit su macOS disegna solo barre sovrapposte, che non occupano spazio, e nessuna opzione di avvio lo cambia, quindi il controllo dello spazio riservato gira solo in Chromium. Il menu del sito, che sostituisce i link dell'intestazione sotto `lg`, viene verificato a 768 px: aprirlo e chiuderlo non sposta nulla.

## Test visivi [#visual-tests]

`e2e/specs/visual-*.spec.ts` confrontano ciò che vede un visitatore con screenshot approvati in `e2e/specs/__screenshots__/`, quindi una modifica che manda un titolo a capo su una riga in più, aggiunge una scheda o sposta una sezione fa fallire la pull request anche quando tutti gli altri test passano. Le spec girano in un progetto Playwright a sé, `visual`, che `playwright.config.ts` definisce solo quando `PLAYWRIGHT_VISUAL_BROWSER` indica un server del browser; i progetti `chromium` e `webkit` le saltano.

```sh
bun run test:visual
bun run test:visual:update
```

| Spec                                             | Screenshot                                                                                                                                                     | Lingue e larghezze                                        |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `visual-landing.spec.ts`, `visual-facts.spec.ts` | L'intestazione, la sezione d'apertura, la griglia dei dati, i prezzi con le altre opzioni, i casi, il manifesto, la sezione finale e il footer della home page | Ogni lingua a ogni larghezza                              |
| `visual-content.spec.ts`                         | La scheda dell'autore e l'invito all'azione alla fine di un articolo del blog                                                                                  | Ogni lingua sullo smartphone, l'inglese sul desktop       |
| `visual-content.spec.ts`                         | Una pagina della documentazione                                                                                                                                | L'inglese a entrambe le larghezze, il tedesco sul desktop |
| `visual-auth.spec.ts`                            | L'intestazione di un visitatore che ha effettuato l'accesso, `/admin` e `/admin/settings`                                                                      | L'inglese a entrambe le larghezze, il tedesco sul desktop |
| `visual-billing.spec.ts`                         | `/app/billing`                                                                                                                                                 | L'inglese a entrambe le larghezze, il tedesco sul desktop |

Le lingue sono <RepositoryFact name="visualLocales" />, le larghezze <RepositoryFact name="visualWidths" /> px, e la suite conta <RepositoryFact name="visualScreenshots" /> screenshot. Sulla home page cambia soprattutto il testo, quindi le sue sezioni vengono fotografate in ogni lingua a entrambe le larghezze. Le schede sotto un articolo del blog si rompono dove le parole lunghe vanno a capo, cioè sullo smartphone, quindi vengono fotografate alla larghezza dello smartphone in ogni lingua. Le pagine dell'amministrazione e dell'area clienti prendono il layout dai componenti, non dai testi: l'inglese a entrambe le larghezze mostra il layout, e il tedesco, la lingua con le parole più lunghe, mostra le etichette che non ci stanno più.

### Gli stessi pixel a ogni esecuzione [#same-pixels-on-every-run]

- Il contesto del browser imposta `reducedMotion: "reduce"`, quindi l'entrata della sezione d'apertura, le sezioni che compaiono durante lo scorrimento e i video in loop restano fermi, e i video mostrano la loro immagine di anteprima. `toHaveScreenshot` ferma ogni altra animazione, come il nastro scorrevole dello stack, e nasconde il cursore di testo.
- Il tema è scuro e il fuso orario UTC.
- Prima del primo screenshot, `openForScreenshots` di `e2e/fixtures/visual.ts` aspetta che la pagina sia renderizzata e idratata, carica e decodifica ogni immagine, anche quelle a caricamento differito, e aspetta `document.fonts.ready`.
- `expectRegion` ritaglia una sezione dalla pagina intera nel punto in cui si trova, così l'intestazione fissa non la copre mai.
- Le maschere coprono ciò che cambia senza alcun cambiamento di layout: i dati che contano file del repository e stelle su GitHub, e gli anni della nota di copyright nel footer.
- I dati vengono dal database di test con i suoi dati iniziali. `scripts/visual-tests.ts` si ferma prima del primo test quando all'URL della suite risponde già un server, quindi Playwright reimposta il database, compila e avvia il server da sé; in CI il job scompatta la propria copia della build con i suoi dati.

### Lo stesso browser su ogni macchina [#the-same-browser-on-every-machine]

I font vengono resi in modo diverso su macOS e su Linux, e perfino tra immagini Linux diverse, quindi i test visivi non usano mai un browser della macchina su cui girano. `scripts/visual-tests.ts` avvia il server del browser di Playwright nell'immagine Docker `<RepositoryFact name="visualBrowserImage" />` per `linux/amd64`, che Docker Desktop emula sui chip Apple, ne passa l'indirizzo in `PLAYWRIGHT_VISUAL_BROWSER` ed esegue `playwright test --project=visual`. I test si collegano con `connectOptions`, il cui `exposeNetwork: "<loopback>"` permette al browser di raggiungere il server di test sull'interfaccia di loopback della macchina. Il tag dell'immagine segue la versione installata di `@playwright/test`, quindi `bun run deps:update` aggiorna insieme il browser e il runner dei test. Un portatile e la CI producono gli stessi pixel, e gli screenshot di riferimento presi in locale passano in CI. `test:visual` richiede Docker in esecuzione.

### Soglia [#threshold]

Uno screenshot fallisce quando differisce più del <RepositoryFact name="visualMaxDiffPercent" unit="percent" /> dei suoi pixel, e un pixel conta come diverso solo se il suo colore supera la soglia che Playwright applica a ogni singolo pixel. Il browser e i font sono ovunque gli stessi, quindi una pagina invariata non differisce in nessun pixel, e la sfumatura o due con cui un altro processore può arrotondare l'antialiasing resta sotto quella soglia. Uno screenshot che cambia dimensione, perché un titolo va a capo su una riga in più o si aggiunge una scheda, fallisce qualunque sia la soglia, e una sola parola aggiunta al paragrafo della sezione d'apertura cambia già più pixel di quanti la soglia ne consenta.

### Aggiornare gli screenshot di riferimento [#updating-the-baselines]

Quando una modifica al layout o al testo è voluta, esegui `bun run test:visual:update`, apri ogni PNG modificato in `e2e/specs/__screenshots__/` nel diff del tuo branch, guardalo e fanne il commit insieme alla modifica. `--update-snapshots=changed` riscrive solo gli screenshot che non corrispondono più. Quando il job `visual` fallisce in CI, carica `test-results/` come artefatto `visual-differences`, con l'immagine attesa, quella ottenuta e quella delle differenze di ogni screenshot fallito.

### In CI [#in-ci]

Il job `visual` di `e2e-reusable.yml` gira solo per Chromium, accanto agli shard: aspetta la build di test come uno shard, la scompatta ed esegue `bun run test:visual`, e il controllo `Build and E2E (chromium)` fallisce se non è passato. Gli screenshot di riferimento sono quelli di Chromium perché WebKit disegna testo e subpixel in modo diverso: servirebbero un secondo insieme di riferimenti e una seconda revisione dello stesso layout, mentre il controllo WebKit continua a verificare come si comporta WebKit.

## Suite del percorso cliente [#journey-suite]

`bun run test:journey` acquista una licenza e usa la CLI come fa un cliente, sul deployment di preview su `https://preview.saasyland.com`, che incassa i pagamenti nella sandbox di Polar. `e2e/journey/playwright.config.ts` è una configurazione a sé, con un proprio progetto Chromium e senza server web, quindi né `test:e2e` né i controlli delle pull request la eseguono; `journey.yml` la esegue ogni notte e a mano ([CI/CD](/docs/tooling/ci-cd#journey-suite)). Ogni piano è un test a sé, con il tag `@core`, `@complete` o `@agency`, i test vengono eseguiti in parallelo, e ognuno segue questi passi:

1. **Account.** Il test si registra con un nuovo indirizzo della casella di prova di Resend, `delivered+journey-<run>-<tier>@resend.dev`, o `upgrade` al posto del piano per il test dell'upgrade, trova l'email di verifica tramite l'API di Resend e ne apre il link.
2. **Prezzo.** `/app/license` deve offrire il piano al prezzo del paese in cui Cloudflare colloca il runner, come riporta `/cdn-cgi/trace`: il prezzo regionale in un paese di `PPP_TIERS`, il prezzo pieno altrove.
3. **Checkout.** Il checkout della sandbox di Polar deve aprirsi sopra `/app/license`, in un frame di `sandbox.polar.sh` che riceve il focus, senza lasciare la pagina, con l'email dell'account già compilata e il consenso alla fornitura immediata non spuntato; il test lo spunta nel frame. Il test paga con la [carta di prova di Stripe](https://docs.stripe.com/testing) e la fatturazione in Polonia, dove l'indirizzo di fatturazione è solo il paese. La pagina deve ricevere i messaggi `loaded`, `confirmed` e `success` di Polar in quest'ordine, chiudere l'overlay e mostrare la licenza attiva su `/app?checkoutId=<id>&tier=<tier>`. Polar incorpora il checkout in un frame solo finché l'organizzazione della sandbox elenca `preview.saasyland.com` in [Settings > Embedding](/docs/getting-started/polar-setup#embedding).
4. **Ordine e chiave.** Polar deve avere un solo ordine pagato per il prodotto del piano, al prezzo offerto da `/app/license`, con il consenso e la lingua dell'acquirente, la conferma dell'acquisto deve arrivare nella casella di posta e `/app/license` deve mostrare la chiave emessa dai webhook, i comandi della CLI e nessun dispositivo in uso.
5. **CLI.** La CLI pubblicata, eseguita come <RepositoryFact name="cliExec" /> al pari dei comandi di `/app/license`, comunica con la preview tramite `SAASYLAND_API_URL`. `activate` scrive il file delle credenziali con la modalità `0600`, una nuova attivazione mantiene la stessa attivazione e `whoami` mostra il dispositivo. I dispositivi di CI, distinti da `SAASYLAND_CI_REPOSITORY`, occupano le attivazioni rimanenti, fino a <ActivationLimit tier="core" /> dispositivi per Core, <ActivationLimit tier="complete" /> per Complete e <ActivationLimit tier="agency" /> per Agency, e il successivo viene rifiutato con `activationLimitReached`. Appena un'attivazione viene liberata su `/app/license`, il dispositivo rifiutato la ottiene e quello liberato riceve `activationNotFound`. `deactivate` libera il primo dispositivo e ne rimuove le credenziali.
6. **Rimborso.** Il test rimborsa l'ordine tramite l'API della sandbox di Polar e attende che `/app/license` mostri la licenza come rimborsata; a quel punto `whoami` deve rispondere `licenseRefunded` e rimuovere le credenziali.

Un quarto test, con il tag `@upgrade`, fa l'upgrade di una licenza. Acquista Core allo stesso modo e occupa i <ActivationLimit tier="core" /> dispositivi di Core, e il successivo viene rifiutato. Poi `/app/license?tier=complete` deve offrire Complete al suo prezzo per il paese del runner meno quanto è costato l'ordine Core, e il test paga questa differenza nel checkout di Polar sopra la pagina, allo stesso modo. Polar deve avere l'ordine dell'upgrade per la differenza, con l'ordine e il piano Core in `upgrade_from_order` e `upgrade_from_tier`; la chiave dell'ordine Core deve ora consentire i <ActivationLimit tier="complete" /> dispositivi di Complete, la chiave che Polar ha concesso per l'ordine dell'upgrade deve essere disattivata, e `/app/license` deve mostrare Complete con la stessa chiave. Poi il dispositivo rifiutato e il successivo si attivano, e quello dopo viene rifiutato. Il test rimborsa l'ordine dell'upgrade tramite l'API della sandbox di Polar: la licenza deve tornare Core, con la stessa chiave e il limite di Core, i dispositivi già attivati continuano a funzionare e uno nuovo viene rifiutato. Un rimborso dell'ordine Core chiude poi la licenza.

Ogni dispositivo della CLI è una directory nella cartella di output del test che la CLI usa come home, e la CLI viene eseguita senza nient'altro nel suo ambiente che `PATH`, quella home, una cache di npm e le variabili `SAASYLAND_*`, così nessuna credenziale della suite la raggiunge. Un ordine che un test fallito lascia pagato viene rimborsato alla fine del test. Gli account restano sulla preview, ciascuno con una licenza rimborsata.

La suite legge questi valori dall'ambiente, o da `.env.preview` quando il file esiste, e si ferma prima del primo test se mancano; nella CI, `journey.yml` li legge dall'ambiente GitHub `Preview`:

| Variabile                                                                       | Uso                                                                                                                                                                |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POLAR_ACCESS_TOKEN`                                                            | Leggere e rimborsare gli ordini nella sandbox e leggerne le chiavi di licenza, con gli scope `orders:read`, `refunds:write`, `benefits:read` e `license_keys:read` |
| `POLAR_SERVER`                                                                  | Deve essere `sandbox`                                                                                                                                              |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | I prodotti della sandbox a cui devono riferirsi gli ordini                                                                                                         |
| `RESEND_API_KEY`                                                                | Leggere le email di verifica inviate dalla preview, per cui serve una chiave con accesso completo                                                                  |

La preview deve eseguire una build con l'[API delle licenze della CLI](/docs/features/cli-licence-api). Esegue `main`, che `deploy.yml` vi distribuisce prima della produzione; per testare un branch prima del merge, distribuiscilo con `gh workflow run preview.yml --ref <branch>` una volta superati i suoi controlli. La sandbox deve corrispondere al codice, e lo verifica `bun run polar:verify:preview`. Poi:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

`bun run test:journey --grep @core` esegue solo il test con quel tag. Il report HTML viene scritto in `playwright-report/journey/` e un report JSON in `playwright-report/journey.json`, e le trace, i video e le directory dei dispositivi dei test falliti in `test-results/journey/`.
