Історія `main` — частина продукту: кожен pull request, злитий через squash, — це один рядок, який каже, що змінилося для людей, які користуються кодом.

## Коміти

Повідомлення комітів відповідають Conventional Commits і пишуться без емодзі; хук `prepare-commit-msg` додає емодзі відповідного типу (таблицю наведено на сторінці [Conventional commits](/docs/tooling/conventional-commits)):

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- Тема пишеться з малої літери, в наказовому способі, і каже, що зміна робить для своїх користувачів: `feat(course): reorder the catalogue from the course list`, а не `update course files`.
- Область (scope) — це модуль або розділ: `course`, `auth`, `a11y`, `deps`, `readme`.
- Тип — один із `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 і `revert` 🗑️; хук відхиляє будь-який інший. Ніколи не вводьте емодзі самостійно: хук не перевіряє тему, яка вже починається з емодзі.
- Розбивайте pull request на логічні коміти: функціональність, її документацію як `docs(<scope>)` і виправлення, знайдені дорогою.
- Ніколи не робіть коміт із `--no-verify`. Хук `pre-commit` запускає `bun run check:pre-commit`; коли він не проходить, виправляйте причину.
- Форматуйте й лінтьте лише змінені вами файли через `bunx vp fmt <files>` і `bunx vp lint --fix <files>`. Не запускайте `bun run check:fix` чи `vp check --fix` для всього репозиторію: вони переписують файли, яких ви не торкалися, зокрема спільні налаштування редактора в `.vscode/settings.json`. Якщо `.vscode/` з’являється в `git status`, відновіть його з `HEAD`.

## Жодної атрибуції ШІ

Коміти й описи pull request не містять трейлера `Co-Authored-By` для інструмента ШІ, рядка «Generated with» чи будь-якої іншої атрибуції ШІ, навіть якщо інструмент додає її за замовчуванням. GitHub зіставляє адресу з такого трейлера зі стороннім обліковим записом, який потім з’являється серед учасників репозиторію. Те саме стосується виправлень, які ви надсилаєте в upstream (див. [Залежності](/docs/conventions/dependencies)).

## Гілки та робочі дерева

- Створюйте гілку від `main`, одну гілку на pull request.
- Давайте кожній гілці власне робоче дерево Git (worktree) замість перемикання гілки в наявному checkout, щоб checkout, відкритий у редакторі чи іншому процесі, ніколи не змінювався без його відома:

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Перш ніж довіряти результатам тестів, перевірте `git branch --show-current` у каталозі, де ви тестували.
- Оновлюйте гілку pull request, зливаючи в неї `main`. Не робіть rebase гілки, яку вже надіслано, і не надсилайте її через force-push: pull request зливаються через squash, тож історія гілки ніколи не потрапляє в `main`, а force-push лише знищує історію рев’ю.

## Pull request

- **Невеликі й цільові.** Одне виправлення, одна функціональність або один рефакторинг на pull request. Велика функціональність стає стеком pull request, кожен з яких можна переглянути окремо, як це було з відео, курсами й адмінкою курсів.
- **Заголовок — це squash-коміт.** Використовуйте формат коміту; він стає темою в `main`.
- **Опис** містить `## Summary` з тим, що змінилося і чому, `## Test plan` з командами, які ви запускали, та їхніми результатами, і `## Docs` зі списком сторінок, розділів README і текстів, які ви оновили. Пишіть просто, без маркетингової мови.
- **Кожен pull request оновлює те, що він робить неточним:** README, сторінки документації в усіх локалях, [журнал змін](/docs/project/changelog) в усіх локалях і будь-які тексти сайту чи твердження лендингу, яких він стосується. Неточність, знайдена в коді, який ви не змінювали, отримує окремий pull request.

## Перевірки

CI запускає `bun run check` і `bun run test:coverage`, потім збирає тестовий Worker і запускає набір браузерних тестів у Chromium; лише коли обидва етапи проходять, він розгортає preview. Дочекайтеся й розгортання preview: це єдиний крок, який завантажує Worker у Cloudflare, і обмеження Cloudflare на завантаження вже провалювали розгортання, яке пройшло всі інші перевірки. Див. [CI/CD](/docs/tooling/ci-cd).
