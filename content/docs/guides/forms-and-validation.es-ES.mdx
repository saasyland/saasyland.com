---
title: "Formularios y validación"
description: "Crea formularios con TanStack Form, campos de shadcn y el esquema Zod del módulo que también aplica el servidor."
---

Los formularios siguen el patrón de shadcn para TanStack Form: `useForm` con el esquema Zod del módulo, render props de `form.Field`, componentes `Field` de shadcn y una mutation para el envío. La función de servidor vuelve a validar el mismo esquema, así que la comprobación en el cliente solo sirve para dar feedback.

## Ejemplo

Versión resumida de `src/presentation/components/custom/newsletter-form.tsx` (sin estilos):

```tsx
const emailSchema = newsletterSubscriberZodSchemas.subscribeToNewsletter.pick({ email: true })

export const NewsletterForm = (): JSX.Element => {
  const t = useTranslations("components.custom.newsletter-form")
  const inputId = useId()
  const errorMessage = useErrorMessage()
  const queryClient = useQueryClient()

  const subscribe = useMutation({
    ...subscribeToNewsletterMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSuccess: ({ status }) => {
      toast.success(t(status))
      return queryClient.invalidateQueries({ queryKey: NEWSLETTER_SUBSCRIBER_QUERY_KEYS.ALL })
    },
  })

  const form = useForm({
    defaultValues: { email: "" },
    listeners: { onBlur: validateOnBlur },
    onSubmit: ({ value, formApi }) => {
      subscribe.mutate(
        { email: value.email, locale: getCurrentLocale() },
        {
          onSuccess: () => {
            formApi.reset()
          },
        },
      )
    },
    validators: { onChange: emailSchema },
  })

  return (
    <form
      noValidate
      onSubmit={(event) => {
        void submitForm(event, form)
      }}
    >
      <form.Field name="email">
        {(field) => {
          const isInvalid = isFieldInvalid(field)

          return (
            <Field data-invalid={isInvalid}>
              <FieldLabel htmlFor={inputId}>{t("label")}</FieldLabel>
              <Input
                aria-describedby={`${inputId}-error`}
                aria-invalid={isInvalid}
                autoComplete="email"
                id={inputId}
                name={field.name}
                onBlur={field.handleBlur}
                onChange={(event) => {
                  field.handleChange(event.target.value)
                }}
                placeholder={t("placeholder")}
                type="email"
                value={field.state.value}
              />
              <Button isPending={subscribe.isPending} type="submit">
                {subscribe.isPending ? t("submitting") : t("button")}
              </Button>
              <div id={`${inputId}-error`}>
                {isInvalid && (
                  <ValidationFieldError
                    message={fieldErrorMessage(field.state.meta.errors)}
                    namespace="auth.validations"
                    params={AUTH_VALIDATION_PARAMS}
                  />
                )}
              </div>
            </Field>
          )
        }}
      </form.Field>
    </form>
  )
}
```

## Esquema

- Usa el esquema de `<table>.zod.ts` del módulo, o de `src/integrations/better-auth/auth.zod.ts` en los formularios de autenticación. `.pick(...)` selecciona los campos que muestra el formulario; los valores que el usuario no escribe, como el idioma, se añaden en `onSubmit`.
- `validators: { onChange: emailSchema }` es el único validador. TanStack Form lo ejecuta en cada cambio y otra vez al enviar; una copia aparte en `onSubmit` dejaría en rojo un error del envío hasta que cambiara su propio campo.
- `listeners: { onBlur: validateOnBlur }` ejecuta el mismo validador cuando un campo pierde el foco, así que un campo por el que el visitante pasa con el tabulador tiene su error en cuanto lo abandona.
- `noValidate` desactiva la validación del navegador para que los mensajes de Zod sean los únicos errores.

## Errores

- Un campo muestra su error en cuanto el visitante lo ha abandonado o ha intentado enviar, nunca mientras sigue escribiendo: `isFieldInvalid(field)` de `src/integrations/tanstack-form/form.fields.ts`, que es `field.state.meta.isBlurred && !field.state.meta.isValid`. Ese valor establece `data-invalid` en `Field`, `aria-invalid` en el input y si el error se renderiza, así que los tres cambian a la vez.
- Una vez que aparece el error, cada cambio vuelve a validar el campo, así que el error desaparece con la pulsación que corrige el valor. No uses `isTouched`: TanStack Form lo establece con la primera pulsación.
- La información en vivo que premia el progreso, como `PasswordRequirements`, lee los valores directamente y se actualiza desde la primera pulsación.
- El input siempre apunta `aria-describedby` al id de su error, `<input id>-error`, y `ValidationFieldError` renderiza ese elemento con ese id solo mientras el campo no es válido. Los navegadores ignoran una referencia a un elemento que no existe, así que el campo no tiene descripción mientras es válido.
- Los mensajes de Zod son claves de traducción, como `emailInvalid`. `fieldErrorMessage` toma el primero y `ValidationFieldError` renderiza `<namespace>.<key>` con la entrada correspondiente de `params`, por ejemplo `max` (<RepositoryFact name="emailMaxLength" />) para `emailMaxLength`. Una clave inexistente recurre a `errors.codes.VALIDATION`.
- Los formularios pasan `auth.validations`, que precargan los layouts `auth` y `admin` y que la funcionalidad del boletín añade al layout `_marketing` para su formulario, salvo los formularios de cursos de la administración, que pasan `course.validations` desde el layout `admin.courses.tsx`, el formulario de desistimiento, que pasa `withdrawal.validations` desde los layouts `_marketing` y `app`, y el formulario de los números del boletín, que pasa `newsletter-issue.validations` desde la ruta `admin.newsletter_.compose.tsx`. La ruta debe cargar el espacio de nombres que usa un formulario.
- Los errores del servidor pasan por `useErrorMessage()` en el `onError` de la mutation.

## Envío

- El `onSubmit` del formulario llama a `submitForm(event, form)` de `src/integrations/tanstack-form/form.submit.ts`. Impide el envío del navegador y llama a `form.handleSubmit()`; cuando el formulario no es válido, marca todos los campos como abandonados, de modo que se muestran todos los errores, y mueve el foco al primer control con `aria-invalid="true"`.
- Envía mediante las opciones de mutation del caso de uso expandidas en `useMutation`. `SignInForm` es la excepción: llama a `signIn.email` del cliente de Better Auth en su propio `useMutation`, y el plugin de dos factores del cliente gestiona `twoFactorRedirect`.
- `<Button isPending={mutation.isPending} type="submit">` desactiva el botón y anuncia el estado pendiente mientras dura la petición.
- El botón de envío sigue activo mientras el formulario está incompleto; solo `isPending` lo desactiva. Pulsarlo con errores muestra todos los errores y lleva el foco al primer campo no válido.
- Un error del servidor que corresponde a un solo campo, como `passwordCompromised` para una contraseña que aparece en una filtración de datos conocida, va bajo ese campo con `showFieldError(formApi, { controlId, field, message })` de `form.submit.ts` en lugar de en un toast; desaparece cuando el campo cambia.
- Restablece el formulario o navega en el `onSuccess` de la mutation e invalida las queries del módulo que cambia la mutation.

Más ejemplos: `sign-in-form.tsx`, `sign-up-form.tsx`, `reset-password-form.tsx` y `two-factor-form.tsx` en `src/presentation/components/custom/auth/`.
