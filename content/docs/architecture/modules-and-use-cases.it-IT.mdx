## Moduli

Un modulo in `src/modules/<table>` esiste solo per una tabella reale del database. Contiene:

- `<table>.schema.ts`: la tabella Drizzle, riesportata da `src/integrations/drizzle-orm/drizzle.schemas.ts`
- `<table>.zod.ts`: gli schemi di input, usati sia dai form sia dalle server function
- `<table>.constants.ts`: valori di dominio con nome come `COURSE_STATUS`, limiti delle colonne, chiavi di query e di mutazione
- `<table>.types.ts`: un’interfaccia con il nome del modulo, con i tipi di riga e il tipo di input di ogni operazione, come `Course["createCourse"]`
- `<table>.utils.ts`: quando la tabella ne ha bisogno
- `use-cases/<operation>.ts`: un'operazione per file

I moduli sono <RepositoryFact name="modules" />. `license` possiede due tabelle, `license` e `revoked_license_order`. Le costanti e gli helper condivisi si trovano in [`_core`](/docs/architecture/core). Una server function che non lavora su una tabella va in `src/lib` o nell'unica route che la usa.

## Casi d'uso

La maggior parte dei casi d'uso sono server function chiamate dal browser. Ogni file esporta la `createServerFn` e le relative opzioni di query o di mutazione:

```ts title="src/modules/course/use-cases/create-course.ts"
import { mutationOptions } from "@tanstack/react-query"
import { createServerFn } from "@tanstack/react-start"
import { v7 } from "uuid"

import { authorized } from "~/src/integrations/better-auth/auth.middleware"
import { db } from "~/src/integrations/drizzle-orm/drizzle.database"
import { rethrowAsConflict } from "~/src/integrations/drizzle-orm/drizzle.errors"

import { nextPosition } from "~/src/modules/_core/utils/ordering"
import { COURSE_MUTATION_KEYS } from "~/src/modules/course/course.constants"
import { course } from "~/src/modules/course/course.schema"
import type { Course } from "~/src/modules/course/course.types"
import { courseZodSchemas } from "~/src/modules/course/course.zod"

export const createCourse = createServerFn({ method: "POST" })
  .middleware([authorized({ course: ["create"] })])
  .validator((input: Course["createCourse"]) => courseZodSchemas.createCourse.parse(input))
  .handler(async ({ data }) => {
    const positions = await db.select({ position: course.position }).from(course)

    return db
      .insert(course)
      .values({ ...data, id: v7(), position: nextPosition(positions) })
      .returning({ id: course.id })
      .get()
      .catch(rethrowAsConflict)
  })

export const createCourseMutation = mutationOptions({
  mutationFn: (data: Course["createCourse"]) => createCourse({ data }),
  mutationKey: COURSE_MUTATION_KEYS.CREATE,
})
```

- **Il middleware** proviene da `src/integrations/better-auth/auth.middleware.ts`. `authorized()` richiede una sessione, `authorized({ course: ["create"] })` controlla anche un permesso e `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` limita le operazioni pubbliche.
- **La validazione** analizza l'input con lo schema Zod del modulo prima che venga eseguito l'handler.
- **La proprietà dei dati** deriva dalla sessione. Le operazioni sui dati del chiamante filtrano per `context.auth.user.id` e non si fidano mai di un ID utente preso dall'input.
- **Gli errori** vengono lanciati come `new AppError(ERROR_CODES.X)`. `rethrowAsConflict` trasforma un errore di vincolo di unicità, come lo slug di un corso già in uso, in `CONFLICT`. `withRequest` trasforma un errore dell'API di Better Auth in `AUTH_API_ERROR` con la chiave del messaggio dell'errore e un errore Zod in `VALIDATION`; qualsiasi altro errore viene registrato nei log e arriva al client come `INTERNAL_ERROR`.
- **Le letture** esportano invece `queryOptions`, ad esempio `getCoursesPageQuery(input)`, che restituisce `{ rows, total }` per la tabella dati.

Alcuni casi d'uso sono semplici funzioni async che vengono eseguite solo sul server e non hanno un endpoint RPC, come `send-verify-email.ts` o `grant-license.ts`. Li chiamano gli hook di Better Auth e gli handler dei webhook di Polar.

## Chiamare un caso d'uso da un componente

I componenti espandono le opzioni esportate in `useMutation`, traducono gli errori con `useErrorMessage()` e, in caso di successo, invalidano le chiavi di query del modulo:

```tsx
const t = useTranslations("pages.admin.users.actions")
const queryClient = useQueryClient()
const errorMessage = useErrorMessage()

const deleteUser = useMutation({
  ...deleteUserMutation,
  onError: (error) => {
    toast.error(errorMessage(error))
  },
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: USER_QUERY_KEYS.ALL })
    toast.success(t("feedback.deleteSuccess"))
  },
})
```
