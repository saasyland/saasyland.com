---

Better Auth зберігає користувачів, облікові записи, сесії та токени верифікації в D1 через адаптер Drizzle. Він забезпечує реєстрацію за електронною поштою й паролем, яка одразу виконує вхід нового облікового запису й відкладає на потім те, що потребує підтвердженої адреси, вхід через GitHub і Google, скидання пароля, зміну електронної пошти, двофакторну автентифікацію TOTP, керування користувачами для адміністраторів, а через свій плагін Polar — клієнтський портал і вебхуки Polar. Оформлення замовлень не належить до Better Auth: його створює `createCheckout` (`src/modules/order/order.checkout.ts`). Його HTTP API обслуговує `src/routes/api/auth.$.ts`. `auth.server.ts` і `auth.client.ts` задають `basePath` Better Auth як `ROUTES.API_AUTH_BASE` — шлях, який обслуговує цей файл, — тож сервер і клієнт у браузері беруть його з однієї константи.

## Файли

| Файл                                                   | Відповідальність                                                                                                                                                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth.server.ts`                                       | Екземпляр `betterAuth`: провайдери, плагіни `admin`, `twoFactor`, `lastLoginMethod` і `tanstackStartCookies` та всі інші плагіни, дозволені хости, обмеження частоти запитів у D1 і хуки листів               |
| `auth.client.ts`                                       | `authClient` та його методи (`signIn`, `signUp`, `signOut`, `useSession`, `twoFactor` та інші)                                                                                                                |
| `auth.routes.ts`                                       | Гарди маршрутів для `beforeLoad`                                                                                                                                                                              |
| `auth.middleware.ts`                                   | Middleware серверних функцій: `withRequest`, `authorized`, `withRateLimit` і `RATE_LIMITS`                                                                                                                    |
| `auth.access.ts`                                       | `ac`, `ROLES` і `hasPermission`, а також декларації дозволів у `APP_STATEMENTS` і їх надання ролям                                                                                                            |
| `auth.roles.ts`                                        | `ROLE_CODES`, `ROLE_VALUES`, `DEFAULT_ROLE_CODE` і `isRole`                                                                                                                                                   |

| `auth.session.ts`                                      | `getRequestSession`, серверна функція `getCurrentSession` і `getCurrentSessionQuery`                                                                                                                          |
| `auth.errors.ts`, `auth.zod.ts`, `auth.constraints.ts` | Ключі помилок, схеми форм і обмеження пароля                                                                                                                                                                  |
| `auth.hooks.ts`                                        | `enforceInputPolicy`: схеми форм, застосовані до ендпоінтів Better Auth; `signInNewAccount`: сесія для нового облікового запису; `requireVerifiedEmail`: перевірка для того, що потребує підтвердженої адреси |

## Гарди маршрутів

| Гард                 | Використовується в               | Поведінка                                                                                                   |
| -------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `requireSignedIn`    | `/app`                           | Без сесії перенаправляє на сторінку входу, передаючи відкриту сторінку як `redirect`, інакше повертає сесію |
| `requireAdmin`       | `/admin`                         | Додатково вимагає дозвіл `admin: ["access"]`, інакше перенаправляє на `/app`                                |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Надсилає користувача, який уже ввійшов, на `redirect` або, залежно від ролі, на `/admin` чи `/app`          |
| `redirectAfterAuth`  | `/auth/callback`                 | Вимагає сесію, а потім перенаправляє на `redirect` або до робочого простору відповідно до ролі              |
| `redirectIfVerified` | `/auth/verify-email`             | Надсилає сесію з підтвердженою адресою на `redirect` або, залежно від ролі, на `/admin` чи `/app`           |

Гарди завантажують сесію через кеш запитів і, коли змінюється користувач, що ввійшов, видаляють із кешу всі непублічні запити за допомогою `removeUserData` з `auth.session.ts`.

## Серверні функції

Гарди сторінок захищають лише навігацію, тому кожна захищена серверна функція повторно перевіряє викликача за допомогою middleware з `auth.middleware.ts`:

- `authorized(permission?)` вимагає сесію, за потреби перевіряє дозвіл і додає сесію до контексту як `context.auth`. Операції з власними даними викликача використовують `context.auth.user.id`, а не ідентифікатор користувача із вхідних даних.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (ліміт запитів — <RepositoryFact name="sensitiveRateLimit" /> у вікні тривалістю <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) або `RATE_LIMITS.TOKEN` (<RepositoryFact name="tokenRateLimit" /> у вікні тривалістю <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) обмежує публічну операцію для кожної клієнтської IP-адреси з `cf-connecting-ip`.
- `withRequest`, який входить до обох, зіставляє помилки з кодами `AppError`: помилки Better Auth стають `AUTH_API_ERROR` зі своїм ключем помилки, помилки Zod — `VALIDATION`, а неочікувані помилки записуються в лог і повертаються як `INTERNAL_ERROR`.

## Ролі та дозволи

`auth.roles.ts` визначає дві ролі: `admin` і `customer` (типова для нових облікових записів). `auth.access.ts` оголошує декларації дозволів кожного ресурсу в `APP_STATEMENTS`: `admin` і `settings` для адмінпанелі та її налаштувань, `product` для сторінки продуктів, яка показує каталог Polar, і для модуля продуктів, `category` для сценаріїв використання модуля категорій, яких не використовує жоден екран, `course` і `video` для курсів, а `order` — для замовлень. Він надає їх усі адміністраторам, які також отримують адміністративні декларації Better Auth, і будує з них контроль доступу та ролі. `hasPermission({ permission, role })` спільно використовують гарди, middleware та UI. Див. [Ролі та дозволи](/docs/guides/roles-and-permissions).

## Плагіни

`plugins` в `auth.server.ts` перелічує всі плагіни Better Auth у тому порядку, в якому Better Auth їх застосовує:

| Плагін                    | Що додає                                                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `admin`                   | Адміністрування користувачів і сесій з `ac` і `ROLES` з `auth.access.ts`                                                         |
| `twoFactor`               | Двофакторна автентифікація                                                                                                       |
| `lastLoginMethod`         | Cookie, яке запам'ятовує останній спосіб входу                                                                                   |
| `invitationPlugin`        | Запрошення (`src/modules/invitation/invitation.plugin.ts`)                                                                       |
| `haveIBeenPwned`          | Перевірка кожного нового пароля на витоки (`NEW_PASSWORD_PATHS`)                                                                 |
| `password-change-notice`  | `notifyPasswordChange` після зміни пароля                                                                                        |
| `license-retention`       | Хук `user.delete.before`, який відкликає ліцензію видаленого облікового запису                                                   |
| `polar`                   | Плагін Polar з порталом клієнта й вебхуками, які передають кожну подію в `handlePolarEvent` ([Платежі](/docs/features/payments)) |
| `polar-verified-customer` | `requireVerifiedEmail` перед кожним ендпоінтом під `/customer/`                                                                  |
| `tanstackStartCookies`    | Встановлює cookie Better Auth у відповідях TanStack Start і має бути останнім                                                    |

Кожен плагін записано в списку явно, тож типи Better Auth містять поля користувача й сесії, які додає кожен із них. Елемент, що називає файл можливості, як-от `revokeAccountLicense` чи `polarCore`, зникає разом із цією можливістю, як і `[ROUTES.API_AUTH_POLAR.WEBHOOKS]: false` у `rateLimit.customRules`, що звільняє доставки вебхуків Polar від обмежувача частоти запитів Better Auth.

## Листи та обмеження частоти

Хуки листів напряму викликають відправників модулів verification, account і user, оскільки автентифікації потрібні листи: `sendVerifyEmail`, `sendExistingAccountEmail`, `sendResetPasswordEmail`, `sendPasswordChangedEmail`, `sendDeleteAccountEmail` і `sendChangeEmailConfirmationEmail`. Власний обмежувач частоти Better Auth зберігає лічильники в таблиці D1 `rate_limit` з префіксом `auth:` через `consumeRateLimit` з `src/lib/rate-limit.ts`, який використовує атомарні upsert-операції й відхиляє запити, коли його сховище недоступне. `clientAddress` в `auth.middleware.ts` визначає клієнта запиту так само, як цей обмежувач: з `cf-connecting-ip`, групуючи адреси IPv6 за /64. Префікс cookie — це `APP_SLUG` із брендингу. `getRequestSession` оминає кеш cookie, тож авторизація завжди зчитує сесію з D1.
