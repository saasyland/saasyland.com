---
title: "Formularze i walidacja"
description: "Buduj formularze z TanStack Form, polami shadcn i schematem Zod modułu, który sprawdza też serwer."
---

Formularze stosują wzorzec shadcn dla TanStack Form: `useForm` ze schematem Zod modułu, render propsy `form.Field`, komponenty `Field` z shadcn i mutację, która wysyła dane. Funkcja serwerowa jeszcze raz waliduje ten sam schemat, więc sprawdzenie po stronie klienta daje tylko szybką informację zwrotną.

## Przykład

Skrócona wersja `src/presentation/components/custom/newsletter-form.tsx` (bez stylów):

```tsx
const emailSchema = newsletterSubscriberZodSchemas.subscribeToNewsletter.pick({ email: true })

export const NewsletterForm = (): JSX.Element => {
  const t = useTranslations("components.custom.newsletter-form")
  const inputId = useId()
  const errorMessage = useErrorMessage()
  const queryClient = useQueryClient()

  const subscribe = useMutation({
    ...subscribeToNewsletterMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSuccess: ({ status }) => {
      toast.success(t(status))
      return queryClient.invalidateQueries({ queryKey: NEWSLETTER_SUBSCRIBER_QUERY_KEYS.ALL })
    },
  })

  const form = useForm({
    defaultValues: { email: "" },
    listeners: { onBlur: validateOnBlur },
    onSubmit: ({ value, formApi }) => {
      subscribe.mutate(
        { email: value.email, locale: getCurrentLocale() },
        {
          onSuccess: () => {
            formApi.reset()
          },
        },
      )
    },
    validators: { onChange: emailSchema },
  })

  return (
    <form
      noValidate
      onSubmit={(event) => {
        void submitForm(event, form)
      }}
    >
      <form.Field name="email">
        {(field) => {
          const isInvalid = isFieldInvalid(field)

          return (
            <Field data-invalid={isInvalid}>
              <FieldLabel htmlFor={inputId}>{t("label")}</FieldLabel>
              <Input
                aria-describedby={`${inputId}-error`}
                aria-invalid={isInvalid}
                autoComplete="email"
                id={inputId}
                name={field.name}
                onBlur={field.handleBlur}
                onChange={(event) => {
                  field.handleChange(event.target.value)
                }}
                placeholder={t("placeholder")}
                type="email"
                value={field.state.value}
              />
              <Button isPending={subscribe.isPending} type="submit">
                {subscribe.isPending ? t("submitting") : t("button")}
              </Button>
              <div id={`${inputId}-error`}>
                {isInvalid && (
                  <ValidationFieldError
                    message={fieldErrorMessage(field.state.meta.errors)}
                    namespace="auth.validations"
                    params={AUTH_VALIDATION_PARAMS}
                  />
                )}
              </div>
            </Field>
          )
        }}
      </form.Field>
    </form>
  )
}
```

## Schemat

- Używaj schematu z `<table>.zod.ts` modułu, a w formularzach uwierzytelniania z `src/integrations/better-auth/auth.zod.ts`. `.pick(...)` wybiera pola widoczne w formularzu; wartości, których użytkownik nie wpisuje, np. język, są dodawane w `onSubmit`.
- `validators: { onChange: emailSchema }` to jedyny walidator. TanStack Form uruchamia go przy każdej zmianie i ponownie przy wysyłce; osobna kopia w `onSubmit` zostawiłaby błąd z chwili wysyłki czerwony, dopóki nie zmieniłoby się jego własne pole.
- `listeners: { onBlur: validateOnBlur }` uruchamia ten sam walidator, gdy pole traci fokus, więc pole pominięte klawiszem Tab pokazuje swój błąd, gdy tylko fokus z niego zejdzie.
- `noValidate` wyłącza walidację przeglądarki, więc jedynymi błędami są komunikaty Zod.

## Błędy

- Pole pokazuje swój błąd, gdy odwiedzający je opuścił lub spróbował wysłać formularz, a nigdy wtedy, gdy jeszcze pisze: `isFieldInvalid(field)` z `src/integrations/tanstack-form/form.fields.ts`, czyli `field.state.meta.isBlurred && !field.state.meta.isValid`. Ta wartość ustawia `data-invalid` na `Field`, `aria-invalid` na polu wejściowym i decyduje, czy błąd się renderuje, więc wszystkie trzy zmieniają się razem.
- Gdy błąd już się pojawi, każda zmiana ponownie waliduje pole, więc błąd znika przy tym naciśnięciu klawisza, które poprawia wartość. Nie używaj `isTouched`: TanStack Form ustawia je przy pierwszym naciśnięciu klawisza.
- Informacja zwrotna na żywo, która nagradza postęp, np. `PasswordRequirements`, odczytuje wartości bezpośrednio i aktualizuje się od pierwszego naciśnięcia klawisza.
- Pole zawsze ustawia `aria-describedby` na id swojego błędu, `<input id>-error`, a `ValidationFieldError` renderuje element z tym id tylko wtedy, gdy pole jest nieprawidłowe. Przeglądarki ignorują odwołanie do nieistniejącego elementu, więc prawidłowe pole nie ma opisu.
- Komunikaty Zod są kluczami tłumaczeń, np. `emailInvalid`. `fieldErrorMessage` bierze pierwszy z nich, a `ValidationFieldError` renderuje `<namespace>.<key>` z pasującym wpisem z `params`, np. `max` (<RepositoryFact name="emailMaxLength" />) dla `emailMaxLength`. Nieistniejący klucz zastępuje `errors.codes.VALIDATION`.
- Formularze przekazują `auth.validations`, które layouty `auth` i `admin` wczytują z wyprzedzeniem, a obszar newslettera dodaje do layoutu `_marketing` na potrzeby swojego formularza, z wyjątkiem formularzy kursów w panelu administracyjnym, które przekazują `course.validations` z layoutu `admin.courses.tsx`, formularza odstąpienia od umowy, który przekazuje `withdrawal.validations` z layoutów `_marketing` i `app`, oraz formularza numeru newslettera, który przekazuje `newsletter-issue.validations` z trasy `admin.newsletter_.compose.tsx`. Trasa musi wczytać przestrzeń nazw, której używa formularz.
- Błędy serwera przechodzą przez `useErrorMessage()` w `onError` mutacji.

## Wysyłka

- `onSubmit` formularza wywołuje `submitForm(event, form)` z `src/integrations/tanstack-form/form.submit.ts`. Funkcja blokuje wysyłkę przez przeglądarkę i wywołuje `form.handleSubmit()`; gdy formularz jest nieprawidłowy, oznacza wszystkie pola jako opuszczone, więc pokazują się wszystkie błędy, i przenosi fokus na pierwszą kontrolkę z `aria-invalid="true"`.
- Wysyłaj formularz przez opcje mutacji przypadku użycia rozwinięte w `useMutation`. Wyjątkiem jest `SignInForm`: wywołuje `signIn.email` klienta Better Auth we własnym `useMutation`, a `twoFactorRedirect` obsługuje wtyczka uwierzytelniania dwuskładnikowego w kliencie.
- `<Button isPending={mutation.isPending} type="submit">` wyłącza przycisk i ogłasza stan oczekiwania, dopóki trwa żądanie.
- Przycisk wysyłki pozostaje aktywny, gdy formularz jest niekompletny; wyłącza go tylko `isPending`. Naciśnięcie go mimo błędów pokazuje wszystkie błędy i przenosi fokus na pierwsze nieprawidłowe pole.
- Błąd serwera, który dotyczy jednego pola, np. `passwordCompromised` dla hasła znalezionego w znanym wycieku danych, trafia pod to pole przez `showFieldError(formApi, { controlId, field, message })` z `form.submit.ts` zamiast do toastu; znika, gdy pole się zmieni.
- Resetuj formularz lub nawiguj w `onSuccess` mutacji i unieważniaj zapytania modułu, które mutacja zmienia.

Więcej przykładów: `sign-in-form.tsx`, `sign-up-form.tsx`, `reset-password-form.tsx` i `two-factor-form.tsx` w `src/presentation/components/custom/auth/`.
