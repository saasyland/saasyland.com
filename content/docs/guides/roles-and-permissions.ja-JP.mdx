---

アクセス制御には Better Auth の admin プラグインを使います。`src/integrations/better-auth/auth.access.ts` は、すべてのリソースの権限ステートメントを `APP_STATEMENTS` で宣言してロールに付与し、そこから Better Auth のアクセス制御と権限チェックを組み立てます。これらはすべて、人がレビューする 1 つのファイルにまとまっています。ロールコードは `src/integrations/better-auth/auth.roles.ts` にあります。

## ステートメントとロール

```ts title="src/integrations/better-auth/auth.access.ts"
export const APP_STATEMENTS = {
  admin: ["access"],
  category: ["create", "read", "update", "delete"],
  course: ["create", "read", "update", "delete"],
  order: ["read", "update", "refund"],
  product: ["create", "read", "update", "delete", "publish"],
  settings: ["manage"],
  video: ["read", "delete"],
} as const

export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...APP_STATEMENTS, ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole({}),
}
```

- `APP_STATEMENTS` は、リソースごとに 1 つのステートメントをリソース順に並べます。管理画面とその設定には `admin` と `settings`、商品には `category` と `product`、コースには `course` と `video`、注文には `order` です。
- Better Auth の `defaultStatements` は、`user` と `session` のリソースを追加します（`user: ["list", "set-role", "ban", "impersonate", "delete"]` や `session: ["list", "revoke"]` など）。
- `admin` には、すべてのステートメントと Better Auth の管理者ステートメントが付与されます。新規ユーザーのデフォルトロールである `customer` には、何も付与されません。
- プロジェクトが外す機能は、そのステートメントも一緒に持っていきます。`scripts/areas.ts` が `APP_STATEMENTS.course` のようにそれらを名指しし、刈り込みのルールがオブジェクトからそれらを削除します（[テスト](/docs/conventions/testing#tests-follow-the-areas)）。
- `ROLE_VALUES` は、`user.role` カラムと `user.zod.ts` のロールのスキーマに型を与えます。
- `authorized` と `hasPermission` が受け取る型 `Permission` は `APP_STATEMENTS` から組み立てられます。そのため、そこで宣言されていないステートメントやアクションはコンパイルを通りません。

## 権限をチェックする場所

| レイヤー           | チェック                                                                  |
| ------------------ | ------------------------------------------------------------------------- |
| ルートガード       | `requireAdmin` が `/admin` 領域全体で `admin: ["access"]` を要求します    |
| サーバー関数       | 保護されたすべての操作で `authorized({ product: ["update"] })` を使います |
| サインイン済みのみ | 呼び出し元自身のデータに対する操作には `authorized()` を使います          |
| その他の場所       | `hasPermission({ permission, role })` が真偽値を返します                  |

ルートガードが決めるのは、どのページをレンダリングするかだけです。サーバー関数は RPC で直接呼び出せるため、それぞれが自分で権限をチェックする必要があります。ボタンを非表示にするのは表示上の処理であり、認可ではありません。

## 権限を追加する

1. `APP_STATEMENTS` にあるリソースのステートメントにアクションを追加するか、リソースを並び順どおりの位置に追加します。例えば `report: ["read", "export"]` です。外せる機能は、新しいリソースを `scripts/areas.ts` の自分の `names` に `APP_STATEMENTS.report` のように記載します。
2. `ROLES` で付与します。`admin` は `APP_STATEMENTS` 全体を受け取り、それより少ない権限にとどめるロールにはその一部を付与します。
3. サーバー関数でその権限を要求します：`.middleware([authorized({ report: ["export"] })])`。
4. 許可されるケースと `FORBIDDEN` のケースの両方を、`src/integrations/better-auth/__test__/auth.access.<area>.test.ts` とユースケースのテストでテストします。

## ロールを追加する

1. `auth.roles.ts` の `ROLE_CODES` と `ROLE_VALUES` にコードを追加します。
2. `auth.access.ts` の `ROLES` に、そのロールが使えるステートメントと一緒にロールを追加します。
3. すべてのロケールの `messages/<locale>/pages.admin.users.json` にある `filters.role.options` に、ロールのラベルを追加します。

認証クライアント（`auth.client.ts`）は `ac` と `ROLES` を受け取るため、ブラウザでの管理操作も同じ定義を使います。

## ユーザーとセッションの管理

user モジュールと session モジュールは、Better Auth の admin API をユースケースでラップしており、それぞれに固有の権限があります：`setUserRole`、`banUser`、`unbanUser`、`impersonateUser`、`deleteUser`、`setUserPassword`、`revokeUserSession` など。`revokeSession` のように呼び出し元自身のデータに対する操作は、`authorized()` を使い、`context.auth.user.id` で絞り込みます。

ローカルでは、`bun run db:seed:local` が管理者を作成します。プレビューと本番では、最初の管理者を `bun run admin:grant:preview <email>` または `bun run admin:grant:production <email>` で作成します。これを実行できるのはその D1 データベースへの書き込み権限を持つ人だけで、対象はメールアドレスを認証済みのアカウントです。2 人目以降の管理者は **管理画面 → ユーザー管理** の **ロールを変更** で作成します。[最初の管理者](/docs/tooling/database#the-first-admin)を参照してください。既存の管理者は、新しいアドレスを `admin` ロールで招待することもできます。[招待](/docs/features/users-admin#invitations)を参照してください。
