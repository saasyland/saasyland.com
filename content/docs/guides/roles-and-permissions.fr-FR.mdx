Le contrôle d'accès utilise le plugin admin de Better Auth. Les permissions, les rôles et la vérification des permissions se trouvent dans `src/integrations/better-auth/auth.access.ts`.

## Permissions et rôles

```ts
const APP_STATEMENTS = {
  admin: ["access"],
  category: ["create", "read", "update", "delete"],
  order: ["read", "update", "refund"],
  product: ["create", "read", "update", "delete", "publish"],
  settings: ["manage"],
} as const

export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...APP_STATEMENTS, ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole({}),
}
```

- Les `defaultStatements` de Better Auth ajoutent les ressources `user` et `session` (par exemple `user: ["list", "set-role", "ban", "impersonate", "delete"]` et `session: ["list", "revoke"]`).
- `admin` possède toutes les permissions ; `customer`, le rôle par défaut des nouveaux utilisateurs, n'en a aucune.
- `ROLE_VALUES` type la colonne `user.role` et les schémas de rôle de `user.zod.ts`.

## Où les permissions sont vérifiées

| Couche           | Vérification                                                         |
| ---------------- | -------------------------------------------------------------------- |
| Garde de route   | `requireAdmin` exige `admin: ["access"]` pour toute la zone `/admin` |
| Fonction serveur | `authorized({ product: ["update"] })` sur chaque opération protégée  |
| Connexion seule  | `authorized()` pour les opérations sur les données de l'appelant     |
| Partout ailleurs | `hasPermission({ permission, role })` renvoie un booléen             |

Le garde de route décide seulement des pages affichées. Les fonctions serveur peuvent être appelées directement via RPC : chacune doit donc vérifier sa propre permission. Masquer un bouton relève de la présentation, pas de l'autorisation.

## Ajouter une permission

1. Ajoutez l'action à `APP_STATEMENTS`, par exemple `report: ["read", "export"]`.
2. `admin` la reçoit automatiquement ; attribuez-la à d'autres rôles dans `ROLES` si nécessaire.
3. Exigez-la dans la fonction serveur : `.middleware([authorized({ report: ["export"] })])`.
4. Testez à la fois le cas autorisé et le cas `FORBIDDEN`.

## Ajouter un rôle

1. Ajoutez le code à `ROLE_CODES` et `ROLE_VALUES`.
2. Définissez ses permissions dans `ROLES`.
3. Ajoutez le libellé du rôle à `filters.role.options` dans `messages/<locale>/pages.admin.users.json` pour les neuf langues.

Le client d'authentification (`auth.client.ts`) reçoit `ac` et `ROLES` : les actions d'administration dans le navigateur utilisent donc les mêmes définitions.

## Administration des utilisateurs et des sessions

Les modules des utilisateurs et des sessions encapsulent l'API d'administration de Better Auth dans des cas d'usage, chacun avec sa propre permission : `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` et d'autres. Les opérations sur les données de l'appelant, comme `revokeSession`, utilisent `authorized()` et filtrent par `context.auth.user.id`.

Aucun administrateur n'est créé d'office en dehors de la base de test. Pour créer le premier administrateur, inscrivez-vous, vérifiez l'e-mail et définissez le `role` de cet utilisateur sur `admin` dans D1, par exemple avec `bun run db:studio:development`.
