Cada cambio se entrega con las pruebas que lo demuestran, en el mismo commit, y la cobertura se mantiene al <RepositoryFact name="coverageThreshold" unit="percent" /> en líneas, sentencias, funciones y ramas. La corrección de un bug va acompañada de una prueba que falla sin la corrección.

## Proyectos

`vite.config.ts` define tres proyectos de Vitest, que se eligen por el sufijo del archivo. Las pruebas importan su API desde `vite-plus/test` y viven en `__test__/` junto al código que cubren.

| Sufijo                 | Proyecto      | Úsalo para                                                                                                                                                                                |
| ---------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | Casos de uso, loaders, `head`, esquemas, utilidades: todo lo que se ejecuta en el servidor                                                                                                |
| `.integration.test.ts` | `integration` | Flujos de Better Auth, de pagos y de licencias, el adaptador de D1 y la carga de mensajes, con tiempos de espera de <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Componentes y páginas en jsdom                                                                                                                                                            |

`src/platform/testing/mocks/cloudflare.ts` sustituye a `cloudflare:workers` en todos los proyectos: D1 es una base de datos `node:sqlite` en memoria construida a partir de todas las migraciones del repositorio, y KV y un bucket por cada binding de R2 del entorno `test` de `wrangler.jsonc` son almacenes en memoria. `resetTestBindings()` vacía KV, el bucket y la tabla de límites de peticiones antes de cada prueba, y la función que siembra los datos de cada suite restablece las filas de las que depende. Ninguna prueba se comunica con Cloudflare, Polar, Resend ni con un proveedor de OAuth: `fetch` llega a los dobles de prueba estrictos de `mocks/resend.ts` y `mocks/polar.ts`, que validan cada petición contra los modelos de petición de los SDK y hacen fallar la prueba ante una que el proveedor rechazaría. Las pruebas comprueban lo que recibió el doble en lugar de simular un método del SDK, y las suites de autenticación ejercitan la configuración real de `auth.server.ts` a través de `auth.harness.ts`.

## Probar una función de servidor

Llámala a través de sus opciones exportadas, para que la prueba ejercite el middleware, la validación y el handler reales. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts`:

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` y `executeMutation(options, variables)` de `src/platform/testing/lib/query.ts` ejecutan las opciones en un `QueryClient` nuevo.
- La sesión sale de `createAuthSessionFixture` en `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts`; cada permiso se prueba también desde el lado que debe ser rechazado (`it("is for staff only")`).
- Los datos sembrados viven en `__test__/fixtures/` del módulo, con sus ID en objetos con nombre (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` elimina las filas que le pertenecen y las vuelve a insertar mediante Drizzle, así que cada prueba parte del mismo estado.
- En el proyecto `component`, una función de servidor se rechaza, porque jsdom hace las veces de navegador. Las pruebas de componentes le dan a una ruta los datos de su loader o simulan el `queryFn` y el `mutationFn` de las opciones que lee el componente.

## Las aserciones usan los nombres del código

- Los estados, tipos, roles y códigos de error esperados son las constantes que usa el código: `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. Una prueba nunca repite un literal de cadena del dominio, y tampoco lo hacen los datos de e2e ni el seed de pruebas: `e2e/data/courses.ts` escribe `kind: COURSE_KIND.COURSE`.
- Las pruebas de esquema son el único lugar donde se escribe un valor almacenado: `product.schema.test.ts` fija `expect(PRODUCT_STATUSES).toStrictEqual(["draft", "published", "archived"])`, así que cambiar un valor que guarda la base de datos hace fallar una prueba en lugar de exigir una migración que nadie escribió.
- La suite del navegador importa sus constantes de la aplicación (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`), así que solo puede importar archivos que cargan fuera del Worker. Los valores de Polar salen de `polar.constants.ts`, que no lee ningún entorno: `e2e/fixtures/license.ts` y el recorrido del cliente en el sandbox toman los estados del pedido de `POLAR_ORDER_STATUS`, y el pedido en sí sale de `src/platform/testing/lib/polar.ts`. Los IDs de producto de los niveles son la excepción: `POLAR_PRODUCT_IDS` lee `cloudflare:workers`, así que la suite del navegador los lee de `.env.test`.
- Las pruebas de componentes leen los textos esperados de los archivos de mensajes en inglés, como hace `admin-course-routes.component.test.tsx` con `import labels from "~/messages/en-US/pages.admin.courses.json"` y `labels.form.kinds.course`, y buscan los elementos por rol y por nombre accesible.
- Una prueba que necesita un tipo lo lee de una fuente tipada o lo comprueba en tiempo de ejecución con `toHaveProperty`; nunca hace un cast.
- Los nombres de las pruebas describen el comportamiento como una frase: «lists every course with its lesson count, drafts included».

## Cobertura

`bun run test:coverage` falla por debajo del <RepositoryFact name="coverageThreshold" unit="percent" /> en cualquiera de las cuatro métricas para `src/**/*.{ts,tsx}`. Quedan excluidos las pruebas, `__test__/`, los archivos de declaración, `src/routeTree.gen.ts`, las primitivas de shadcn y `src/platform/testing/`. El umbral se mantiene significativo:

- **Elimina las ramas que nunca pueden ejecutarse** en lugar de cubrirlas con stubs. Un `?? fallback` sobre datos que siempre están presentes, o un encadenamiento opcional sobre un valor que no puede ser `undefined`, se elimina del código fuente, no se alcanza sustituyendo un global.
- **Cubre el comportamiento real.** Los estados pendientes mantienen abierta la petición con `Promise.withResolvers()`, comprueban la interfaz pendiente, resuelven dentro de `act` y comprueban la interfaz en reposo, como hacen `expectPending` y `expectIdle` en `auth-forms.component.test.tsx`.
- **Conserva las aserciones cuando una regla aprieta.** Cuando una prueba supera `max-statements`, extrae un helper con nombre en lugar de quitar comprobaciones.
- **Carga todos los archivos de mensajes.** `i18n.messages.test.ts` carga todos los espacios de nombres de todos los idiomas, y eso es lo que cubre las líneas `import.meta.glob` de `i18n.loaders.ts`. Un archivo de mensajes nuevo queda cubierto automáticamente.

## Pruebas en una máquina ocupada

El límite de tiempo de Vitest y el margen de un segundo de `waitFor` y `findBy*` cuentan tiempo real, así que una prueba que hace trabajo que su comportamiento no necesita, o que espera a un temporizador, falla en una máquina ocupada aunque nada esté roto. El límite predeterminado se queda como está; una prueba lenta se cambia para que haga menos:

- **Una comprobación sobre muchos archivos ejecuta una prueba por archivo.** `check-content.test.ts` ejecuta `pageProblems` para cada página en inglés con `it.each(sourcePages())`, y una desviación nombra su página.
- **Lo que un componente espera con Suspense se carga antes de renderizarlo**, como hace `preloadNamespaces` con las traducciones. Cuando la prueba trata de la carga, la resuelve dentro de `act`, como hace `translations-provider.component.test.tsx`: el contenido que se reanuda fuera de `act` solo aparece después del retardo con el que React lo revela, en un temporizador real, y la prueba tiene que sondear el DOM hasta verlo.
- **Una prueba sustituye un módulo una sola vez en lugar de volver a importar el componente.** `affiliate-referral.component.test.tsx` simula `AFFILIATE_PROGRAM` una vez y le da un valor en cada prueba. Importar un componente después de `vi.resetModules()` vuelve a evaluar todo su grafo de importaciones dentro de la prueba.
- **Los fixtures que lee cada prueba se crean una vez por archivo**, como los mensajes de `getTestMessages`.
- **Un formulario se rellena con `user.paste`, salvo que sus pulsaciones sean el comportamiento que se prueba.** `fill` en `admin-course-routes.component.test.tsx` hace clic en el campo y pega; `user.type` ejecuta la validación y el renderizado del formulario una vez por carácter.
- **Una lista larga de opciones se vuelve a renderizar con poco coste.** El combobox de zonas horarias de `preferences-card.tsx` pasa sus opciones a `ComboboxList` como `items` memoizados, así que React Aria las reutiliza cuando el formulario se vuelve a renderizar.

## Las pruebas siguen a las áreas [#tests-follow-the-areas]

Las áreas cuyos archivos y rutas nombra `scripts/areas.ts` (consulta [Rutas y navegación](/docs/conventions/routes#paths-and-navigation)) también son dueñas de sus pruebas, así que la CLI `saasyland` puede dejar un área fuera de un proyecto generado junto con sus pruebas y todas las demás siguen pasando.

Un archivo de pruebas cubre un área o un archivo de código. Las páginas de administración de un área se prueban con sus esqueletos y sus migas de pan en `src/routes/__test__/admin-<area>-routes.component.test.tsx`, y sus loaders en `admin-<area>-loaders.test.ts`. La prueba de un esqueleto de layout lo renderiza con `createTestRouter(path, routeTree)` de `src/platform/testing/lib/render.tsx`, un router sobre el árbol de rutas real, y los esqueletos de los cursos se prueban en `admin/__test__/courses-pending.component.test.tsx`, porque `admin-course-routes` reconstruye las rutas de los cursos para su propio router; `admin-layout`, `admin-dashboard` y `admin-loaders` prueban la propia interfaz de administración y no nombran ningún área. Los archivos sin relación entre sí tienen cada uno su archivo de pruebas, como `background.component.test.tsx` y `wordmark.component.test.tsx`, y cada manejador de la API tiene el suyo: `src/routes/api/__test__/auth.test.ts` e `index.test.ts`. `cli.v1.test.ts` cubre los archivos de ruta de la API de licencias de la CLI, cuyo comportamiento se prueba en `src/modules/license/__test__/license.api.integration.test.ts`.

Una lista que abarca varias áreas se declara por área y la reúne un barrel:

| Lista                                  | Cada área declara                                                                                                                     | Barrel                             | La lee                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| Datos de consultas de administración   | `seed<Area>Queries` y sus factorías de filas en `src/presentation/components/custom/admin/__test__/<area>.fixtures.ts`                | `fixtures.entries.ts`              | `adminQueryClient()` en `fixtures.tsx`         |
| Etiquetas de enumeraciones             | `src/integrations/use-intl/__test__/<area>.labels.ts`                                                                                 | `labels.entries.ts`                | `enum-labels.test.ts`                          |
| Filas de D1                            | `src/integrations/drizzle-orm/__test__/<area>.rows.ts`                                                                                | `rows.entries.ts`                  | `d1.integration.test.ts`                       |
| Páginas de las pruebas en el navegador | `e2e/data/<area>.pages.ts`                                                                                                            | `e2e/data/pages.entries.ts`        | `accessibility.spec.ts` y `workspaces.spec.ts` |
| Base de datos de pruebas               | `e2e/data/<area>.seed.ts`                                                                                                             | `e2e/data/seed.entries.ts`         | `scripts/seed-test.ts`                         |
| Inventario de flujos                   | `e2e/data/<area>.flows.ts`: los flujos del área, cada uno con la prueba que lo demuestra o el motivo por el que falta                 | `e2e/data/flows.entries.ts`        | `scripts/check-flows.ts`                       |
| Consultas públicas                     | `src/integrations/better-auth/__test__/<area>.public-queries.ts`                                                                      | `public-queries.entries.ts`        | `auth.session.test.ts`                         |
| Dobles de proveedores                  | `src/platform/testing/mocks/<provider>.ts`: una lista `<PROVIDER>_PROVIDER_DOUBLES`, cada doble con `origin`, `respond` y `reset`     | `mocks/providers.entries.ts`       | `mocks/providers.ts`                           |
| Catálogo de Polar                      | `src/modules/<module>/__test__/fixtures/<area>.polar-catalogue.ts`: los productos y beneficios de clave de licencia que vende el área | `mocks/polar-catalogue.entries.ts` | `mocks/polar.ts`                               |
| Worker de pruebas                      | `e2e/data/<area>.worker.ts`: preparaciones y endpoints de prueba                                                                      | `e2e/data/worker.entries.ts`       | `src/platform/testing/worker.ts`               |

La base añade una lista vacía a los barrels que solo llenan áreas opcionales, `e2e/data/core.seed.ts`, `e2e/data/core.worker.ts`, `mocks/core.providers.ts` y `src/integrations/drizzle-orm/__test__/core.rows.ts`, de modo que un proyecto sin esas áreas sigue pasando la comprobación de tipos, y `scripts/seed-test.ts` solo ejecuta Wrangler cuando un área inserta filas. El page object de un área viene con su propia fixture: `e2e/fixtures/auth.ts` extiende el `test` de la base de `e2e/fixtures/test.ts` con `authPage`, y las specs que inician sesión importan `test` de ahí.

Las utilidades que usan varias áreas se escriben una sola vez: `renderAdmin` y `renderAdminPage` en `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` en `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` y `busyMarkup` en `src/platform/testing/lib/skeleton.tsx` y, en las pruebas en el navegador, `AuthPage.signIn`, `BasePage.leaveWhileLoading` y la fixture `pageWithoutJavaScript`. Las specs de las páginas públicas, como `accessibility.spec.ts` y `theme.spec.ts`, no inician sesión con ninguna cuenta; `workspaces.spec.ts` comprueba las páginas con sesión iniciada, su accesibilidad y su tema.

Una prueba de código compartido que necesita una entrada de las que aportan las áreas declara la suya propia en lugar de leer la de un área. `dashboard-actions.component.test.tsx` sustituye `ADMIN_DASHBOARD_ACTIONS` por una acción local de la prueba, de modo que `DashboardActions` y los marcadores de las acciones de `AdminDashboardPending` siguen cubiertos en un proyecto sin el área de pagos, que hoy declara las acciones del panel. `server.test.ts` y `vite.test.ts` hacen lo mismo con handlers del Worker y plugins de Vite locales de la prueba, y cada área prueba sus propias entradas en `src/data/__test__/<area>.worker.test.ts` y `<area>.vite.test.ts`. El código compartido que solo renderizan áreas opcionales tiene una prueba propia: `pending-blocks.component.test.tsx` cubre el esqueleto de campo que usan los esqueletos de la administración de cursos. Una prueba del control de acceso compartido solo comprueba las declaraciones del área de autenticación y las propias de Better Auth; cada área prueba lo que concede en `src/areas/__test__/<area>.access.test.ts`, y `auth.access.website.test.ts` fija los permisos de cada rol en el sitio web.

`auth-plugins.test.ts` cubre la composición de plugins con un plugin de ejemplo, así que sigue cubierta sin el plugin de Polar de la licencia, y `navigation.test.ts` comprueba los menús sin esperar ninguna entrada concreta, así que pasa con las entradas que conserve cada proyecto. `translations-provider.component.test.tsx` toma como ejemplo namespaces de la base y las pruebas de autenticación toman los datos y las rutas de la propia área de autenticación, como la lista de sesiones y `/app/settings`.

La prueba de la ruta de la licencia sustituye el `CourseUnlocks` de los cursos por una sección local de la prueba y simula su consulta del catálogo, la prueba del esqueleto de la licencia hace lo mismo con `CourseUnlocksPending`, y las pruebas de cursos sustituyen las concesiones de acceso a los cursos por `TEST_COURSE_ACCESS` (`src/modules/course/__test__/fixtures/course-access.ts`), así que las pruebas de ninguna de las dos áreas leen la otra. `license.course-access.test.ts` cubre lo que las une: la concesión de la licencia, con un snapshot de quién puede ver cada lección para un invitado, una cuenta, el equipo y cada nivel y estado de licencia.

Una prueba que fija el sitio web completo, como `navigation.website.test.ts` con el orden de cada menú, es exclusiva del sitio; las plantillas no la generan.

`scripts/areas.ts` enumera los archivos de cada área opcional como globs, los nombres que el área tiene en archivos que se quedan, como las rutas de cada área en `src/routes.ts`, y las áreas que requiere, y `bun run check:areas` comprueba que los tipos del sitio siguen pasando sin ellas. Todos los escenarios dejan fuera las áreas que solo tiene el sitio web, y cuatro de ellos dejan fuera además los cursos, las áreas de facturación, el contenido o el área de autenticación. Para cada escenario, el script borra los archivos de esas áreas y de toda área que requiera alguna de ellas, y poda los archivos que se quedan con una sola regla, la que sigue la CLI `saasyland` cuando deja fuera un área:

1. Borra los nombres que tienen las áreas retiradas, cada uno con su declaración o su propiedad de objeto.
2. Una referencia retirada es un identificador importado de un archivo borrado, el uso de un nombre retirado, como `ROUTES.COURSES` en cuanto `src/routes.ts` deja de declararlo, o una función que llama a `import()` sobre un archivo borrado. Desaparecen todos los `import` y `export … from` de un archivo borrado, y también todo import de un módulo que solo declara un archivo de declaraciones borrado, como `virtual:repository-facts`.
3. Para cada referencia retirada, borra el elemento de array más cercano dentro de su sentencia de nivel superior. Si no lo hay, borra la propiedad de objeto, el spread, el miembro de tipo o el hijo JSX más cercano sin cruzar una sentencia, y si tampoco lo hay, informa de la referencia con su archivo, línea y columna.
4. Cuando eso vacía un array que es una propiedad de un elemento de array, el elemento también desaparece, como un grupo de menú que se queda sin entradas.
5. Borra cada cadena de un array que nombra el espacio de nombres de un archivo de mensajes borrado.
6. Borra los especificadores de import y las declaraciones no exportadas, a cualquier profundidad, a las que ya nada hace referencia, y repite hasta que nada cambie.

`scripts/prune-references.ts` aplica la regla sobre los árboles sintácticos del parser oxc, y `scripts/module-bindings.ts` resuelve cada nombre hasta la declaración a la que se refiere, así que un parámetro o una variable local con el mismo nombre nunca se confunde con un import. Los archivos generados, que `.gitattributes` marca como `linguist-generated`, se copian tal cual, y la comprobación vuelve a generar el árbol de rutas. Después, el script copia a un directorio temporal los archivos que Git rastrea o añadiría, los podados en lugar de los originales, genera las tablas de nombres de clase, las colecciones de contenido mientras el área de contenido se queda y el árbol de rutas, con `scripts/generate-routes.ts`, y ejecuta `tsc --noEmit` sobre `src`, `e2e`, `scripts` y `vite.config.ts`. Un escenario falla por una referencia que la regla no puede podar y por cualquier error de tipos, y `src/__test__/check-areas.test.ts` falla cuando un glob no encaja con ningún archivo o un nombre no está declarado en su archivo. CI ejecuta un job por escenario y solo informa hasta que todos los escenarios pasen ([CI/CD](/docs/tooling/ci-cd#checks)).

## Pruebas en el navegador

Playwright ejecuta el Worker de pruebas compilado: `bun run build:test` lo compila con D1 y KV locales en `.wrangler/test`, `bun run db:reset:test` vuelve a crear esa base de datos y precarga las cuentas, el vídeo y el curso de `e2e/data`, y el punto de entrada de pruebas captura el correo saliente en `/__test/emails` para que una spec pueda seguir un enlace de verificación.

- Las specs se nombran según el flujo (`course-admin.spec.ts`, `auth-redirect.spec.ts`) y manejan la página mediante roles y nombres accesibles, con page objects en `e2e/pages/`.
- Cada spec crea los datos que modifica con valores únicos, como un slug construido a partir de `crypto.randomUUID()`, e inicia sesión desde su propia cabecera `CF-Connecting-IP`, para que las specs puedan ejecutarse en paralelo y repetirse sin chocar entre sí ni con los límites de peticiones.
- Una prueba que modifica datos precargados, como los dispositivos de una licencia, recibe registros precargados propios, uno por cada worker en paralelo, para que nunca haya dos pruebas en ejecución modificando el mismo registro. `cli-licence-api.spec.ts` activa dispositivos en la licencia que `TEST_CLI_LICENSES` de `e2e/data/licenses.ts` precarga para el `parallelIndex` de cada worker, que Playwright nunca asigna a dos workers a la vez, y su fixture `cliMachine` libera el dispositivo cuando termina la prueba, así que un reintento empieza desde la licencia precargada. La licencia `TEST_LICENSE`, que lee `license.spec.ts`, conserva solo su dispositivo precargado.
- Una spec actúa sobre una página solo cuando ha terminado `waitForAppReady()` de `e2e/pages/base-page.ts`, también tras una navegación en el cliente. El método termina cuando TanStack Router ha renderizado la URL actual, que la fixture automática `recordRenders` registra a partir del evento `onRendered` del router, porque una navegación en el cliente cambia la URL antes de que se renderice la siguiente ruta. El contenido de la ruta puede hidratarse después de ese renderizado, así que una spec que depende del estado propio de un componente, o que pulsa un enlace fuera del contenido antes de que este se haya hidratado, llama primero a `waitForHydration(element)`, que espera a que React haya hidratado el elemento y todo lo que contiene; `LandingPage.goto()` lo hace con el `main` de la página de inicio. Una spec puede abandonar una página mientras carga, como puede hacerlo un visitante, y una que recoge los errores de página de varias visitas directas abre cada visita en su propia pestaña, como hace `auth-routing.spec.ts`. Una spec que recoge errores de página abandona una página solo cuando su navegación en el cliente ya se ha renderizado: WebKit notifica como error de página una petición que la página inicia después de que la spec haya empezado a abandonarla, `Fetch API cannot load … due to access control checks.`, aunque la aplicación gestione la petición fallida.
- Una spec que debe demostrar que un texto nunca aparece, no solo que ha desaparecido al final, llama a `watchForText(text)` de `e2e/pages/base-page.ts` antes del cambio y comprueba después que el texto nunca se mostró: un `MutationObserver` en la página lo registra en cuanto se renderiza. La prueba de la mejora en `checkout-funnel.spec.ts` lo hace con el agradecimiento por el nivel anterior, y la suite de recorrido con el agradecimiento por cualquier nivel distinto del comprado.
- Cada spec falla cuando una página infringe su Content Security Policy: la fixture automática `cspViolations` de `e2e/fixtures/test.ts` registra cada evento `securitypolicyviolation` y espera que no haya ninguno cuando termina la prueba. Una spec que provoca una infracción a propósito la retira con `cspViolations.splice(0)`, como hace `content-security-policy.spec.ts`. La suite ejecuta el build de producción de `build:test`, porque el servidor de desarrollo no envía ninguna política de scripts.
- Las pull requests y la cola de fusión ejecutan todas las specs en Chromium, como hace `bun run test:e2e:pr` en local; los push a `main` y una ejecución programada semanal también ejecutan WebKit.
- Una spec que lee el portapapeles usa el fixture `readClipboard` de `e2e/fixtures/test.ts`, que concede antes de que empiece la spec los permisos del portapapeles que conoce el navegador: en Chromium `clipboard-read` y `clipboard-write`, en WebKit solo `clipboard-read`, porque WebKit no tiene permiso de escritura y deja que el clic que copia escriba en el portapapeles, como Safari.
- Una spec que realiza un flujo de principio a fin y comprueba su resultado aparece nombrada en ese flujo de `e2e/data/<area>.flows.ts`, por su archivo de spec y su título completo. `bun run check` falla cuando un flujo nombra una prueba que la suite no tiene, así que una prueba renombrada se lleva su flujo en el mismo commit, y un flujo que ninguna prueba demuestra dice por qué. Consulta [Cobertura de pruebas](/docs/tooling/test-coverage).
- Una ruta, un flujo o una corrección visual que las pruebas unitarias no pueden ver recibe una spec: los análisis de accesibilidad y las regresiones de navegación de `navigation.spec.ts` y de las specs de las áreas a las que afectan, como `content.spec.ts`, `legal.spec.ts` y `landing.spec.ts`, son ejemplos de ello. Una spec que desplaza la página la hace lo bastante alta por sí misma, como la prueba de desplazamiento de `navigation.spec.ts`, en lugar de depender de la longitud de una página. Una sección que se rellena después de cargar la página conserva su altura, así que una spec que se desplaza nunca tiene que cargarla antes: una sección que cambiaba de altura por encima del viewport movía lo que el visitante estaba leyendo, y WebKit detenía un desplazamiento suave cuando el anclaje del desplazamiento lo compensaba. Las specs del bloque de cursos en `landing.spec.ts` retienen su petición, la dejan completarse o fallar y comprueban que el bloque conserva su altura y que no se registra ningún desplazamiento del diseño.
