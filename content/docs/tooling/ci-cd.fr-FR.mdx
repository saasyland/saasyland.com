Les workflows se trouvent dans `.github/workflows/`. Les workflows de l'application (`ci.yml`, `e2e-reusable.yml` et `deploy-reusable.yml`) mettent en place la chaîne d'outils avec l'action composite `.github/actions/setup` : Bun <RepositoryFact name="bunVersion" />, Vite+ avec la version de Node de `.nvmrc`, un cache Bun, `bun install --frozen-lockfile --ignore-scripts` et `bun run typegen`. `remotion.yml` met plutôt en place Node depuis `.nvmrc` et npm.

| Workflow              | Déclencheur                                                                                       | Jobs                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests et pushs sur `main`                                                                 | Vérifications et couverture, E2E Chromium, puis déploiement en préversion, ou en production avec publication de la version |
| `e2e-full.yml`        | Pushs sur `main`, selon la planification <RepositoryFact name="e2eFullSchedule" /> en UTC, manuel | WebKit lors d'un push ; Chromium et WebKit lors des exécutions planifiées et manuelles                                     |
| `e2e-reusable.yml`    | Appelé par les workflows ci-dessus                                                                | Base de données de test, build de test et un projet Playwright                                                             |
| `deploy-reusable.yml` | Appelé par `ci.yml`                                                                               | Build, migrations D1 et `wrangler deploy`                                                                                  |
| `remotion.yml`        | Modifications de `remotion/` ou des fichiers du site qu'il importe                                | Vérifie et empaquette avec npm le projet vidéo de la page d'accueil                                                        |

`remotion.yml` se déclenche sur les mêmes chemins pour les pull requests et les pushs : `remotion/`, le workflow lui-même et les fichiers du site que `remotion/src` importe, directement ou via d'autres fichiers du site. `src/__test__/workflows.test.ts` suit ces imports et échoue lorsqu'un fichier qu'ils atteignent ne correspond à aucun des chemins, ou qu'un chemin ne correspond à aucun des fichiers.

Les checkouts qui construisent le site, dans `e2e-reusable.yml` et `deploy-reusable.yml`, et celui du job `release` récupèrent tous les commits sans leurs arbres (`fetch-depth: 0` et `filter: tree:0`) : le [journal des modifications](/docs/project/changelog) date chaque entrée d'après le commit qui l'a amenée sur `main`. Par rapport à un clone superficiel, seuls les commits eux-mêmes s'ajoutent ; un clone superficiel ferait échouer la construction plutôt que de mal dater les entrées. `src/__test__/workflows.test.ts` échoue lorsqu'un de ces checkouts ne récupère plus l'historique.

## Vérifications

Le job `verify` de `ci.yml` exécute `bun run check` (tables des noms de classes, vérifications i18n et de contenu, l'[inventaire des parcours](/docs/tooling/test-coverage#flow-coverage), formatage, lint et types) et `bun run test:coverage`, puis téléverse le rapport de couverture. Le job `e2e` exécute `db:reset:test` et `build:test`, installe le navigateur et lance `bunx playwright test e2e/specs --project=chromium`. Les exécutions E2E en échec téléversent le rapport Playwright.

Dans une pull request, `bun run check` échoue aussi tant que la pull request n'ajoute pas son [entrée au journal des modifications](/docs/conventions/git-workflow#changelog-entries).

## Déploiements

Les déploiements ne s'exécutent qu'une fois `verify` et `e2e` réussis :

| Événement                                   | Cible        | Environnement GitHub | URL                           |
| ------------------------------------------- | ------------ | -------------------- | ----------------------------- |
| Pull request depuis une branche de ce dépôt | `preview`    | `Preview`            | https://preview.saasyland.com |
| Push sur `main`                             | `production` | `Production`         | https://saasyland.com         |

`deploy-reusable.yml` donne à chaque environnement GitHub son URL, et `src/__test__/workflows.test.ts` échoue lorsque l'une d'elles diffère de son hôte dans `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Les pull requests provenant de forks et de Dependabot sont validées mais pas déployées. La préversion est partagée : chaque déploiement remplace le précédent et utilise la même base de données D1, le même espace de noms KV et les mêmes buckets R2 de préversion.

`deploy-reusable.yml` vérifie la présence des secrets `CLOUDFLARE_API_TOKEN` et `CLOUDFLARE_ACCOUNT_ID`, exécute `scripts/verify-bindings.ts`, construit avec les valeurs factices de `.env.test`, supprime le fichier généré `dist/server/.dev.vars`, applique `db:migrate:<target>` et lance `vp exec wrangler deploy --config dist/server/wrangler.json`. Il ne lance pas `scripts/verify-deployment.ts`, la vérification du site en ligne des scripts `deploy:<target>`, car la protection anti-bots de Cloudflare répond 403 aux requêtes des runners de CI. Il ne lance pas non plus `scripts/run-deploy-checks.ts` : la CI n'exécute donc aucune des vérifications de déploiement que les zones déclarent dans `DEPLOY_CHECKS`, car elle n'a pas de `.env.<target>` et les environnements GitHub ne contiennent que les identifiants Cloudflare. Aujourd'hui, ce sont `auth:verify`, de la zone d'authentification, et `polar:verify`, de la zone Polar ; lancez en local `bun run auth:verify:<target>` après avoir modifié un client OAuth et `bun run polar:verify:<target>` après chaque modification dans Polar ([Configurer Polar](/docs/getting-started/polar-setup)). Aucun fichier de secrets n'est téléversé : le Worker conserve les secrets d'exécution déjà définis dans Cloudflare. Les déploiements vers une même cible sont mis en file d'attente au lieu de s'annuler mutuellement.

Dependabot met à jour les GitHub Actions chaque semaine.

## Versions et tags [#releases-and-tags]

Le site est déployé en continu : ses versions sont donc des dates et non des versions sémantiques. Quand un déploiement en production réussit, le job `release` de `ci.yml` pose le tag `vYYYY.MM.DD` à la date UTC sur le commit déployé et publie une GitHub Release correspondante. Un deuxième déploiement en production le même jour reçoit le tag `vYYYY.MM.DD.2`, le suivant `.3`, et ainsi de suite. Les déploiements en préversion ne reçoivent jamais de tag. Le job `release` est le seul à disposer de `contents: write`.

Les notes de version sont les entrées du [journal des modifications](/docs/project/changelog) arrivées sur `main` ce jour-là, si bien que chaque changement n'est décrit qu'à un seul endroit ; si aucune n'est arrivée, les notes renvoient vers le journal. `scripts/publish-release.ts` choisit le tag et les notes avec `src/lib/release.ts` et lance `gh release create`. Une nouvelle exécution conserve le tag que le commit possède déjà et ignore une GitHub Release qui existe déjà.

Pour ramener la production à une version, annulez dans une pull request tout ce qui suit son tag :

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Sa fusion déploie le code du tag après les vérifications habituelles et lui pose le tag d'une nouvelle version. Les migrations D1 ne sont pas annulées : l'ancien code s'exécute donc sur le schéma plus récent. Chaque modification du schéma doit fonctionner avec l'application déployée avant elle, ce qui rend l'opération sûre pour la version précédente ; lisez les migrations intermédiaires avant de remonter plus loin.
