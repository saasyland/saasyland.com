---

`bun run check` exécute `bun run generate:cn`, `bun run check:comments`, `bun run check:i18n` et `bun run check:flows`, puis `vp check`, qui formate avec oxfmt, lint avec oxlint et vérifie les types avec TypeScript en une seule passe, selon la configuration de `vite.config.ts` et de `tsconfig.json`. La CI exécute la même commande. Rien ici n'est une question de goût : si les outils acceptent du code qui enfreint une règle de cette page, la revue le rejette.

## Ce que les outils imposent

oxlint traite les catégories `correctness`, `nursery`, `pedantic`, `perf`, `style` et `suspicious` comme des erreurs, avec les règles tenant compte des types et la vérification des types activées. Les limites qui façonnent le plus le code :

| Règle                                   | Réglage                                                                                   | Effet                                                                           |
| --------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `max-lines`                             | <RepositoryFact name="maxLines" />                                                        | Découpez un fichier par responsabilité avant qu'il ne grossisse                 |
| `max-lines-per-function`                | <RepositoryFact name="maxLinesPerFunction" />                                             | Les composants et les handlers restent petits                                   |
| `max-statements`                        | <RepositoryFact name="maxStatements" />                                                   | Extrayez des fonctions utilitaires nommées plutôt que d'écrire de longs corps   |
| `no-magic-numbers`                      | seuls `0` et `1` sont autorisés, ainsi que les index de tableau et les valeurs par défaut | Tout autre nombre est une constante nommée                                      |
| `id-length`                             | au moins deux caractères, sauf `_`, `m` et `t`                                            | Les identifiants sont des mots ; `t` est le traducteur                          |
| `one-var`                               | `never`                                                                                   | Une déclaration par instruction                                                 |
| `unicorn/no-null`                       | activée hors des tests et de `src/platform/testing`                                       | Les valeurs absentes sont `undefined`                                           |
| `typescript/no-explicit-any`            | `error`                                                                                   | Aucune valeur n'est typée `any`                                                 |
| `typescript/ban-ts-comment`             | `true` pour `@ts-expect-error`, `@ts-ignore` et `@ts-nocheck`                             | Aucune erreur du compilateur n'est masquée, avec ou sans raison                 |
| `typescript/consistent-type-assertions` | `assertionStyle: "never"`                                                                 | Aucune conversion `as` ; `as const` et `satisfies` restent permis               |
| `code-style/no-comments`                | `error`                                                                                   | Aucun commentaire, commentaires de directive compris                            |
| `code-style/no-multiline-ternary`       | `error`                                                                                   | Un ternaire tient sur une ligne                                                 |
| `code-style/no-undefined-branch`        | `error`                                                                                   | Aucun ternaire avec une branche `undefined` ou `null`, aucun `return undefined` |
| `code-style/no-undefined-fallback`      | `error`                                                                                   | Aucun `?? undefined`                                                            |
| `code-style/zod-namespace-import`       | `error`                                                                                   | Zod s'importe comme `* as zod` depuis `zod`                                     |
| `radius/no-off-scale`                   | `error`                                                                                   | Chaque coin prend un rayon de l'échelle                                         |
| `type/no-off-scale`                     | `error`                                                                                   | Chaque taille de texte est un palier de l'échelle typographique                 |
| `type/mono-for-code`                    | `error`                                                                                   | La police à chasse fixe est réservée au code                                    |

Les surcharges sont étroites et limitées à certains fichiers : les tests et les utilitaires de test partagés de `src/platform/testing` assouplissent `no-magic-numbers`, `no-await-in-loop`, `unicorn/no-null`, `hydration/no-clock-or-locale-in-render` et `admin-data/no-literal-data` ; `src/presentation` et `src/hooks` assouplissent `typescript/consistent-return` ; les mocks de test assouplissent `require-await` ; `src/routes` désactive `sort-keys`, car les options de route suivent leur propre ordre (voir [Fichiers de route](/docs/conventions/routes)) ; et les routes, les composants et les fichiers de données de l’administration activent `admin-data/no-literal-data` (voir [Tableau de bord d’administration](/docs/features/admin-dashboard#real-data-only)). Tout `src` active `radius/no-off-scale`, `type/no-off-scale` et `type/mono-for-code`, que les tests et `src/platform/testing` désactivent à nouveau, et `src/presentation/social-card.tsx` désactive `type/no-off-scale`, car Takumi rend la carte sociale sous forme d'image de taille fixe dont les tailles de texte sont fixées dans des styles en ligne et non sur l'échelle typographique de la page (voir [Thème](/docs/ui/theme#type-scale)).

`tsconfig.json` ajoute les options strictes qui changent la façon d'écrire le code : `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` et `noUnusedParameters`. Une lecture indexée peut valoir `undefined`, une propriété optionnelle ne peut pas recevoir `undefined` explicitement, et une signature d'index se lit sous la forme `record["key"]`.

Le formateur écrit sans points-virgules, avec des guillemets doubles, des virgules finales et une largeur de <RepositoryFact name="printWidth" />. Il trie aussi les imports en groupes fixes, les classes Tailwind dans `className` et dans les appels à `cn`, et les scripts de `package.json` par nom (`sortPackageJson: { sortScripts: true }`) : n'ordonnez donc jamais aucun d'eux à la main, car `vp check` échoue dès que l'un d'eux n'est pas dans l'ordre. Voir [Lint et formatage](/docs/tooling/lint-format) pour les commandes.

## Rendre ce que le serveur a rendu

Une page est rendue deux fois : sur le serveur, puis dans le navigateur quand React hydrate le HTML. Les deux rendus doivent afficher le même texte, sinon React signale une erreur d’hydratation (erreur #418) et rend la page à nouveau. Le code de rendu ne lit donc jamais l’horloge ni la locale de l’environnement d’exécution, qui diffèrent entre les deux : pas de `new Date()` sans argument, pas de `Date.now`, ni de `toLocaleString`, `toLocaleDateString` ou `toLocaleTimeString`. Utilisez une valeur que les deux côtés partagent :

- un temps relatif se compte à partir du `dataUpdatedAt` de la requête qui a lu ses données, comme le montre [Internationalisation et langues](/docs/features/internationalization) ;
- une année affichée par le site vient du build : le pied de page termine son copyright par `REPOSITORY_FACTS.buildYear`, l’année UTC du build du site ;
- les nombres et les dates passent par `useFormatter` de use-intl, dans la langue de la page et le fuseau horaire de l’utilisateur ;
- une attente dans le navigateur, comme le délai d’activation de `CheckoutActivation`, est un minuteur démarré dans `useEffect`, si bien que le premier rendu est celui du serveur.

`hydration/no-clock-or-locale-in-render`, la règle du plugin oxlint propre au dépôt dans `scripts/hydration-lint-plugin.ts`, l’impose dans `src/hooks`, `src/presentation`, `src/providers` et `src/routes/*.tsx`. Tout y compte comme code de rendu, sauf une fonction qui s’exécute plus tard : un gestionnaire d’événements `on…`, en prop JSX, en propriété d’objet ou en variable ; une `queryFn` ou une `mutationFn` ; et un callback passé à `useEffect`, `useLayoutEffect`, `useCallback`, `setTimeout`, `setInterval`, `requestAnimationFrame` ou `addEventListener`. Ces listes du plugin sont la liste d’autorisation : un autre type de callback différé s’y ajoute, avec un cas dans `src/__test__/hydration-lint-plugin.test.ts`, jamais par un commentaire de désactivation.

## Pas de commentaires

N'écrivez aucun commentaire : ni en TypeScript, ni en TSX, ni dans les tests, les scripts, la configuration ou le CSS, pas même pour expliquer une contrainte peu évidente. C'est un nom qui porte le sens, et le raisonnement va dans le message de commit, dans la pull request ou dans cette documentation.

```ts
const INCLUSIVE_END = 1
const FIRST_SEQUENCE = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

Les deux premières viennent de `video.delivery.ts` et de `release.ts`, la troisième de `src/data/polar.vite.ts` : chacune aurait sinon besoin d'un commentaire.

Deux vérifications imposent la règle, et toutes deux nomment le fichier, la ligne et la correction :

- `code-style/no-comments`, une règle du plugin oxlint propre au dépôt, dans `scripts/code-style-lint-plugin.ts`, signale chaque commentaire des fichiers que lit le linter, dans l'éditeur et dans `vp check`.
- `bun run check:comments` exécute `scripts/check-comments.ts` avant le linter, dans `bun run check` et dans le hook de pre-commit. Il analyse chaque fichier TypeScript, JavaScript et CSS que Git suit ou ajouterait, avec oxc pour le code et PostCSS pour les styles, si bien qu'un `//` dans une URL ou une expression régulière et un `/*` dans un glob CSS ne sont pas des commentaires. Il lit ce que le linter ne peut pas lire : `e2e`, `remotion`, les fichiers de déclaration, les feuilles de style et un commentaire `/* oxlint-disable */`, auquel le linter obéit avant qu'aucune règle ne le voie.

Les exemptions sont les fichiers que `.gitattributes` marque `linguist-generated`, parmi lesquels `src/routeTree.gen.ts` et `src/types/worker-configuration.d.ts` sont du code, et la ligne `#!` d'un script, que la grammaire de JavaScript ne compte pas comme un commentaire. Un type dont le compilateur a besoin partout va dans `types` de `tsconfig.json`, comme les globales de Vitest, jamais dans un commentaire `/// <reference>`.

## Pas d'échappatoires

N'écrivez jamais `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore` ou `@ts-nocheck`, et n'utilisez ni conversion `as` ni `any` pour faire passer une règle. Une règle qui se déclenche signale un problème de conception ; changez la conception. Les vérifications rejettent chacun d'eux : `typescript/ban-ts-comment` les trois directives du compilateur, même accompagnées d'une description, `typescript/consistent-type-assertions` toute assertion sauf `as const`, `typescript/no-explicit-any` le `any`, et `code-style/no-comments` et `bun run check:comments` tout commentaire de désactivation. De toute façon, un commentaire `eslint-disable` ne désactive rien (`respectEslintDisableDirectives: false`).

- **Validez au lieu d'affirmer.** Les données issues du stockage, du réseau ou d'une requête sont analysées avec Zod : `src/lib/github.ts` lit le nombre d'étoiles en cache avec `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, qui vaut un nombre ou `undefined`, jamais une supposition.
- **Affinez avec une garde de type.** `isRole` dans `src/integrations/better-auth/auth.roles.ts` et `isErrorCode` dans `src/hooks/use-error-message.ts` transforment une `string` en union au moyen d'une vraie vérification.
- **Annotez, n'affirmez pas.** Donnez à une valeur le type dont elle a besoin là où elle est déclarée : la barre latérale shadcn déclare `SIDEBAR_MOBILE_STYLE: StyleWithCssVars`, les propriétés CSS plus sa propriété personnalisée `--sidebar-width`, au lieu de convertir le littéral d'objet.
- **Vérifiez, ne convertissez pas.** `as const` et `satisfies` sont autorisés, car ils ne changent jamais un type : `POLAR_ORDER_STATUS` se termine par `as const satisfies Record<string, models.OrderStatus>`, si bien qu'un statut Polar mal orthographié ne compile pas.
- **Restructurez quand le contrat d'une bibliothèque vous résiste.** Enveloppez une valeur dans un objet, découpez une fonction ou lisez depuis une source typée plutôt que de convertir.

## Null et undefined

Hors des tests et de `src/platform/testing`, une valeur absente vaut `undefined`, et `null` n'est jamais écrit comme valeur. Le linter l'autorise là où une API l'impose : dans une comparaison avec une valeur qui peut être `null`, comme une colonne nullable (`entry.completedAt !== null` dans `course.outline.ts`), et dans une ref DOM de React, qui commence par `useRef<HTMLElement>(null)` parce que React type `ref` en `RefObject<T | null>` et la remet à `null` au démontage (`course-showcase.tsx`). Ne convertissez jamais le `null` renvoyé par une API avec `?? undefined` ; `code-style/no-undefined-fallback` le fait échouer. Validez d'abord l'entrée, pour que l'appel ne puisse pas échouer, ou utilisez un parseur qui renvoie déjà `undefined`. Les paramètres de recherche sont le cas le plus courant, et `searchParam(schema)` de `src/lib/search-params.ts` renvoie `undefined` pour une valeur absente ou mal formée :

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Ternaires et retours anticipés

Un ternaire tient sur une ligne, comme `{t(course === undefined ? "create" : "save")}` dans `course-form.tsx`. Tout ce qui est plus long, ainsi que tout choix entre deux morceaux de JSX, devient un retour anticipé, une paire de conditions `&&` ou un petit composant ; une classe conditionnelle devient `cn("base", { "classes": condition })`. `code-style/no-multiline-ternary` fait échouer tout ternaire qui s'étend sur plusieurs lignes, y compris celui que le formateur a coupé parce qu'il dépassait la largeur de ligne. `src/routes/auth.reset-password.tsx` affiche ses deux états avec deux conditions :

```tsx
{hasValidToken && <ResetPasswordForm token={token} />}
{!hasValidToken && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

Les fonctions retournent tôt pour les cas particuliers et gardent le chemin principal sans indentation, comme le fait `hasLessonAccess` dans `src/modules/lesson/lesson.access.ts` :

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.entitled
}
```

Aucune branche n'écrit non plus la valeur absente : `code-style/no-undefined-branch` fait échouer un ternaire dont une branche vaut `undefined` ou `null`, et chaque `return undefined`. Écrivez plutôt ce que fait le code : retournez tôt depuis une clause de garde, lisez une valeur qui peut manquer avec `?.` ou avec `??` et une vraie valeur par défaut, renvoyez ce que trouve une table de correspondance ou `find`, affichez le JSX avec `&&`, et donnez au hook d'un plugin Vite un filtre qui nomme les identifiants qu'il traite, pour que Rolldown ne l'appelle pour aucun autre. C'est ainsi que `scripts/repository-facts.ts` sert son module virtuel :

```ts title="scripts/repository-facts.ts"
    load: { filter: { id: exactRegex(RESOLVED_MODULE_ID) }, handler: () => moduleSource },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_MODULE_ID },
```

## Constantes nommées

Les nombres autres que `0` et `1` sont nommés (`COURSE_STALE_MS = 60_000`, `SAVE_INTERVAL_MS = 15_000`). `0` et `1` s'écrivent en littéraux, comme dans `.limit(1)`, `index + 1` et `toHaveBeenCalledTimes(1)`, sauf s'ils portent un sens propre : le code de sortie d'un processus s'appelle `FAILURE_EXIT_CODE`, et la fin inclusive d'une plage d'octets HTTP `INCLUSIVE_END`. Les valeurs qui appartiennent au domaine, comme les statuts, les types, les niveaux d'accès, les offres, les rôles et les valeurs d'événements des fournisseurs, sont déclarées une seule fois dans un objet `as const` et référencées par leur nom partout, y compris dans les tests et les fixtures :

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

Le tuple dont une colonne ou un schéma d'enum a besoin est construit à partir de l'objet, et non retapé, et se trouve à côté de lui dans les constantes du module, qui n'importent rien de Drizzle : `course.constants.ts` déclare `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, qui alimente à la fois `text("status", { enum: COURSE_STATUSES })` dans `course.schema.ts` et `zod.enum(COURSE_STATUSES)` dans `course.zod.ts`. Le code du navigateur y lit lui aussi les tuples : la grille tarifaire parcourt `LICENSE_TIERS` de `license.constants.ts`.

- Les constantes d'un module se trouvent dans son `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`) ; les valeurs d'un fournisseur se trouvent dans le `*.constants.ts` de l'intégration (`POLAR_ORDER_STATUS` dans `polar.constants.ts`, `AUTH_PROVIDER` dans `auth.constants.ts`).
- Les longueurs des colonnes et des entrées sont nommées une seule fois, dans les constantes du module, et lues à la fois par le schéma Drizzle et par le schéma Zod : `PRODUCT_NAME_MAX_LENGTH` dans `product.constants.ts`.
- Un concept a une seule table de correspondance, dans une seule casse : `ERROR_CODES` pour les erreurs serveur, `AUTH_ERRORS` pour les clés d'erreur de Better Auth, `ROLE_CODES` pour les rôles.
- Les noms d'environnement et les codes de statut HTTP sont déclarés une seule fois, dans `src/modules/_core/constants/api.ts` : `ENVIRONMENT.PRODUCTION` dans `__root.tsx` et les scripts de déploiement, `HTTP_STATUS.PARTIAL_CONTENT` dans le gestionnaire de médias du Worker. Aucun fichier ne déclare sa propre table de l'un ou de l'autre. La seule exception concerne les fichiers de plugins Vite comme `src/data/cloudflare.vite.ts`, qui comparent `mode` aux noms bruts : Vite les charge avant de résoudre l'alias `~`, ils ne peuvent donc pas importer `api.ts`.
- Une constante utilisée par un seul fichier reste dans ce fichier, sous les imports. Une constante utilisée par plusieurs fichiers va dans son module, dans `src/data` (voir [Fichiers et nommage](/docs/conventions/files-and-naming)) ou dans `src/modules/_core/constants`. Ne donnez jamais à une constante un fichier pour elle seule.
- Les noms de champs d'API typés comme `license_key_id` sont des propriétés, pas des valeurs, et restent des accès de propriété.

## Hooks dans les composants

Les appels de hooks qui renvoient une seule valeur viennent d'abord, puis une ligne vide, puis chaque résultat de hook déstructuré, de sorte que les valeurs qu'un composant décompose se lisent comme un groupe à part. `src/presentation/components/custom/auth/sign-in-form.tsx` :

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Un composant appelle `useTranslations` une seule fois et nomme le résultat `t` ; voir [Traductions et contenu](/docs/conventions/translations) pour savoir pourquoi.

## Noms et imports

- Les fichiers et les dossiers sont en kebab-case, les composants en PascalCase, les constantes en SCREAMING_SNAKE_CASE ; les fonctions commencent par un verbe (`resolveViewer`, `rethrowAsConflict`) ; les booléens se lisent comme des questions (`isPending`, `hasLessonAccess`).
- Les imports utilisent l'alias `~/src/...` et proviennent du fichier qui définit le symbole. Il n'y a pas de fichiers barrel qui réexportent un dossier ; le seul fichier de réexportation est `src/integrations/drizzle-orm/drizzle.schemas.ts`, car Drizzle a besoin de toutes les tables dans un seul objet de schéma.
- Zod s'importe d'une seule façon, `import * as zod from "zod"` (ou `import type * as zod from "zod"` pour les seuls types), la forme que montre la documentation de Zod 4 ; `code-style/zod-namespace-import` fait échouer un import par défaut, un import nommé et un sous-chemin comme `zod/v4`.
- Avancer un index d'une unité utilise le littéral : `lessons[index + 1]` dans `course.utils.ts`. Tout autre décalage, `-1` compris, reçoit un nom : `groups.at(LAST_GROUP_INDEX)` dans `robots.ts`, jamais `slice(index, -5)`.
