---
title: "Desplegar una preview"
description: "Aprovisione los recursos de Cloudflare y despliegue el Worker de preview."
---

El entorno `preview` despliega el Worker `saasyland-preview` en `preview.saasyland.com`. Por defecto, `development` y `preview` comparten una base de datos D1, un espacio de nombres de KV y un bucket de R2.

## Aprovisionar los recursos

```sh
bunx wrangler login
bunx wrangler d1 create saasyland_com_preview
bunx wrangler kv namespace create CACHE --env preview
bunx wrangler r2 bucket create saasyland-preview
```

En `wrangler.jsonc`, sustituya `database_id`, `database_name`, el `id` de KV y el `bucket_name` de `MEDIA` tanto en `development` como en `preview`. Conserve los nombres de binding `DB`, `CACHE` y `MEDIA` y el `migrations_dir`, y actualice los nombres de los Workers y las rutas de dominio personalizado para su cuenta. Para producción, cree recursos independientes, incluido el bucket `saasyland`, y actualice el bloque `production`. Establezca `APP_DOMAIN` en `src/presentation/branding/index.ts`. `DEPLOYED_HOSTS`, en `src/modules/_core/constants/api.ts`, deriva de él los hosts desplegados, `APP_DOMAIN` para producción y `preview.<APP_DOMAIN>` para preview, y es el único lugar en el que el código los nombra: `appHostsForMode` lo lee para obtener los hosts que aceptan Better Auth y los enlaces del boletín, y `scripts/verify-deployment.ts` les hace una petición después de un despliegue. En local, `appHostsForMode` acepta `localhost:3000` o `127.0.0.1:3000` en desarrollo, y esos más `localhost:3020` y `127.0.0.1:3020` en test. Edite `DEPLOYED_HOSTS` solo si su host de preview tiene otro nombre. Las `routes` de dominio personalizado de `wrangler.jsonc` y las URL de los entornos de `.github/workflows/deploy-reusable.yml` nombran los mismos hosts, así que manténgalos sincronizados.

## Desplegar

Rellene `.env.preview` y, a continuación, despliegue:

```sh
bun run deploy:preview
```

`deploy:preview` ejecuta `scripts/verify-bindings.ts preview`, que rechaza los bindings que faltan y los ID de marcador de posición, y después `build:preview`, que prerenderiza las páginas públicas y verifica el resultado. A continuación, `scripts/prepare-deploy-secrets.ts preview` escribe en `.wrangler/secrets.preview.json` los secretos que `wrangler.jsonc` declara para `preview`, tomados de `.env.preview`, y falla si alguno está vacío. `db:migrate:preview` aplica las migraciones nuevas antes de que `wrangler deploy` suba `dist/server/wrangler.json` con esos secretos, y por último `scripts/verify-deployment.ts preview` comprueba que responde el host de preview de `DEPLOYED_HOSTS` (https://preview.saasyland.com). `verify-bindings.ts` no comprueba que el bucket de R2 exista, porque se vincula por nombre: el despliegue falla hasta que el bucket existe. `bun run db:migrations:preview` enumera las migraciones que la base de datos de preview aún no ha aplicado.

Registre los callbacks de OAuth y el webhook de Polar para el host de preview tal como se indica en [Variables de entorno](/docs/getting-started/environment-variables).

## Despliegues automáticos

La CI despliega cada pull request procedente de una rama de este repositorio en la preview compartida, y cada push a `main` en producción, una vez superadas las comprobaciones y las pruebas en el navegador. Consulte [CI/CD](/docs/tooling/ci-cd) para conocer los secretos de GitHub necesarios.
