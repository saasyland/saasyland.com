## Cache de queries

`getRouter` crée un nouveau `QueryClient` pour chaque requête, si bien qu'aucune donnée ne fuit d'un utilisateur à l'autre côté serveur. Valeurs par défaut :

| Paramètre                            | Valeur                                                                                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `staleTime` des queries              | <RepositoryFact name="queryStaleTimeMinutes" unit="minute" />                                                                                |
| `gcTime` des queries                 | <RepositoryFact name="queryGcTimeMinutes" unit="minute" />                                                                                   |
| `defaultPreloadStaleTime` du routeur | <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />                                                                        |
| Préchargement                        | Sur intention, et les [pages de l'en-tête](/docs/conventions/performance#the-headers-pages-load-before-a-click) dès qu'une page est inactive |

Seul TanStack Query décide de ce qui est frais. `defaultPreloadStaleTime` vaut <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />, comme le demande le guide de TanStack Router pour l'utiliser avec TanStack Query, et `defaultStaleTime` garde la valeur par défaut du routeur : le routeur exécute donc les loaders d'une route à chaque préchargement et à chaque navigation, et les loaders lisent le cache des requêtes, qui ne récupère que ce qui manque ou est périmé.

Les loaders remplissent le cache avec `queryClient.query({ ...options, staleTime: "static" })` et les composants lisent les mêmes clés avec `useSuspenseQuery`. Les pages de cours et l'éditeur de cours de l'administration font exception : leurs requêtes gardent `staleTime: COURSE_STALE_MS` (<RepositoryFact name="courseStaleMinutes" unit="minute" />), car `invalidateQueries` ne recharge jamais une requête `static`, et terminer une leçon ou enregistrer une modification dans l'éditeur doit rafraîchir le programme. `setupRouterSsrQueryIntegration` sérialise le cache du serveur dans le HTML et l'hydrate dans le navigateur.

- **Les messages de traduction** sont mis en cache par locale et par namespace, avec un `staleTime` et un `gcTime` infinis.
- **La query de session** (`getCurrentSessionQuery`) a un `staleTime` de <RepositoryFact name="sessionStaleTimeMinutes" unit="minute" />. Les guards de route laissent passer une navigation avec la session en cache tant qu'elle est fraîche et la récupèrent à nouveau dès qu'elle est périmée. Une fonction serveur qui répond `UNAUTHORIZED` ou `FORBIDDEN` fait revérifier la session par `recheckRefusedSession` dans `auth.routes.ts`, et les guards s'exécutent à nouveau si elle a changé. Quand l'utilisateur connecté change, les guards suppriment toutes les queries qui ne sont pas marquées `meta: { public: true }`. Les queries publiques, comme les traductions et le nombre d'étoiles avec lequel une page prérendue a été rendue, restent en cache. Voir [Queries publiques](/docs/conventions/data-fetching#public-queries).
- **Les mutations** invalident les clés de query de leur module, par exemple `USER_QUERY_KEYS.ALL`, une fois qu'elles ont réussi.

## Prérendu [#prerendering]

`bun run build` prérend les pages publiques en parcourant les liens : landing page, pages légales, blog et documentation dans toutes les locales. Les chemins sous `/admin`, `/app`, `/auth`, `/courses`, `/newsletter` et `/api` (avec ou sans préfixe de locale) ainsi que les liens comportant une chaîne de requête ou un fragment sont exclus. Les pages de cours sont exclues parce qu'elles affichent les verrous et la progression de chaque spectateur. Le navigateur remplit le bloc des cours de la page d’accueil avec `getCourseShowcase` quand il approche de la zone visible ; la page d’accueil prérendue reste donc la même pour tous (voir [Cours](/docs/features/courses)).

Le Worker sert le HTML prérendu depuis le binding `ASSETS` avant de charger l'application. Une page prérendue ne contient aucune donnée utilisateur : elle peut donc être servie à tout le monde sans risque. Avant de l'envoyer, le Worker la réécrit avec les entrées de `DOCUMENT_REWRITES` : la tarification régionale pour un visiteur qui y a droit, et `data-session` sur `<html>` quand la requête porte le cookie de session de Better Auth, ce qui choisit le libellé **Votre compte** de l'en-tête avant l'exécution de tout script (voir [Chemins et navigation](/docs/conventions/routes#paths-and-navigation)). La marque ne vérifie que la présence du cookie, jamais la base de données ; un cookie dont la session a pris fin est effacé par la première page qui le vérifie, comme la page de connexion ou la vérification de session de l'en-tête. Chaque réponse HTML est donc envoyée avec `Cache-Control: private, no-cache` et `Vary: Cookie`, afin qu'aucun cache partagé ne stocke la page d'un visiteur pour un autre. Un cache placé devant le Worker, comme Workers Cache ou une règle de cache pour le HTML, servirait la même variante à tout le monde ; les documents ne peuvent être mis en cache que là où ces réécritures s'exécutent encore après le cache.

Le prérendu s'exécute sur un build du Worker qui contient toutes les pages. Le Worker déployé est ensuite reconstruit sans les pages compilées de la documentation et du blog, et sans les traductions que seules la landing page et les pages légales utilisent. Il n'a besoin ni des unes ni des autres : la documentation, le blog et la landing page lisent leur contenu dans des index que le build écrit dans `/assets/`, depuis le navigateur lors d'une navigation côté client, et la recherche de la documentation parcourt un index statique dans le navigateur, si bien que les navigations côté client et la recherche n'atteignent jamais le Worker (voir [Performances](/docs/conventions/performance#the-worker-holds-no-docs-or-blog-content)). Voir [Cloudflare Workers](/docs/integrations/cloudflare-workers).

## KV et D1

- **KV (`CACHE`)** stocke le nombre d'étoiles GitHub pour `src/lib/github.ts`. Un nombre d'étoiles de plus de <RepositoryFact name="starCountRefreshHours" unit="hour" /> est renvoyé immédiatement, puis rafraîchi en arrière-plan avec `waitUntil`.
- **D1 (`DB`)** stocke les sessions et les compteurs de limitation de débit. Les vérifications de session des fonctions serveur contournent le cache de cookies de Better Auth et sont mémoïsées pour le reste de la requête.
- **Le cache des Workers** conserve les fichiers vidéo que `serveMedia` lit depuis R2 sous `/media/_/<videoId>/<file>`, sans la signature, de sorte que les spectateurs d'un même point de présence partagent une seule copie en cache. Voir [Cloudflare R2](/docs/integrations/cloudflare-r2). `serveCover` garde les couvertures des cours dans un cache Workers à part, `covers`, sous leur chemin public, et les envoie avec `public, max-age=31536000, immutable`, puisque chaque nouvelle couverture reçoit un nouvel identifiant.
- Les fonctions serveur ne prennent jamais de décision de permission à partir de données en cache.
