---
title: "Como contribuir"
description: "Como propor alterações ao SaaSy Land."
---

1. Discuta alterações grandes primeiro em uma issue, aberta pelo formulário de relatório de bug ou de solicitação de funcionalidade.
2. Crie uma branch a partir de `main`.
3. Siga as [convenções](/docs/conventions) e a [arquitetura](/docs/architecture), e leia a [skill para agentes](/docs/tooling/agent-skills) correspondente antes de alterar a integração com um fornecedor. Os agentes de código começam por `AGENTS.md`, na raiz do repositório.
4. Mantenha os testes ao lado do código a que pertencem e preserve a exigência de <RepositoryFact name="coverageThreshold" unit="percent" /> de cobertura.
5. Execute as verificações abaixo.
6. Faça o commit com uma mensagem no formato de [conventional commit](/docs/tooling/conventional-commits), abra um pull request com um título no formato convencional e preencha o template dele.
7. Faça rebase da branch sobre `main` quando ela tiver conflitos, nunca faça merge de `main` nela, como descreve [Git e pull requests](/docs/conventions/git-workflow#linear-history). Quem mantém o projeto coloca o pull request verde na [fila de mesclagem](/docs/conventions/git-workflow#merging), que o testa de novo sobre `main` e o mescla.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`build:test` executa o build completo do Cloudflare, que `check` e os testes unitários não exercitam. O último comando compila e serve o Worker de teste quando nenhum servidor está rodando e executa no Chromium as specs que você indicar: execute as que cobrem o que você alterou. A CI executa todas as specs no pull request e de novo na fila de mesclagem, e o pull request só é mesclado quando essa execução está verde; `bun run test:e2e:pr` executa a suíte completa localmente da mesma forma. Execute também a suíte completa de testes no navegador no WebKit (`bun run test:e2e`) para alterações que podem se comportar de forma diferente nele. Valide separadamente as integrações reais com provedores quando alterar a configuração delas.

Quando o comportamento mudar, atualize `content/docs` em todos os locales; `bun run check:i18n` rejeita traduções ausentes, blocos de código divergentes e navegação divergente. O template do pull request traz um resumo, um plano de testes com as verificações acima e a lista da documentação atualizada; descreva nele o comportamento resultante, como você o verificou e qualquer fluxo que a mudança deixe inacabado. Uma tela administrativa só é lançada com uma fonte real para os seus dados (veja [Painel administrativo](/docs/features/admin-dashboard#real-data-only)).

`CONTRIBUTING.md`, na raiz do repositório, é a versão curta desta página, e `SUPPORT.md` indica onde obter ajuda. Todas as pessoas que participam seguem o `CODE_OF_CONDUCT.md`, o Contributor Covenant 2.1. Relate vulnerabilidades de segurança de forma privada, como descreve o `SECURITY.md`, nunca em uma issue pública.
