- Corrigé : un nouveau worktree Git reçoit ses hooks de commit. `git worktree add` installe le répartiteur de hooks du nouveau worktree par le hook `post-checkout`, si bien qu'un commit fait avant `bun install` échoue dans le hook `pre-commit` au lieu de le sauter, et `bun install` échoue quand `core.hooksPath` ne vaut pas `.vite-hooks/_` ou quand il manque un hook au répartiteur. Jusqu'ici, Git committait sans hooks, et sans prévenir, dans chaque worktree qui n'avait pas son propre répartiteur. Voir [Git et pull requests](/docs/conventions/git-workflow#hooks-in-every-worktree).
- Corrigé : [Git et pull requests](/docs/conventions/git-workflow#linear-history) ne vous dit plus de fusionner `main` dans une branche de pull request et de ne jamais faire de force-push. La page décrit l'historique linéaire que suit le projet : aucun commit de merge, même sur une branche de pull request, des branches mises à jour par un rebase sur `main`, une pull request que GitHub ne peut pas rebaser intégrée de nouveau en un seul commit, et des branches réécrites poussées avec `git push --force-with-lease`. `AGENTS.md`, `CONTRIBUTING.md` et la page [Contribuer](/docs/project/contributing) disent la même chose.
