---
title: "Come contribuire"
description: "Come proporre modifiche a SaaSy Land."
---

1. Discuti prima le modifiche importanti in una issue, aperta dal modulo di segnalazione bug o di richiesta di funzionalità.
2. Crea un branch a partire da `main`.
3. Segui le [convenzioni](/docs/conventions) e l'[architettura](/docs/architecture), e leggi la [skill per agenti](/docs/tooling/agent-skills) corrispondente prima di modificare l'integrazione di un fornitore. Gli agenti di programmazione partono da `AGENTS.md` nella radice del repository.
4. Tieni i test accanto al codice a cui appartengono e mantieni la soglia di copertura pari a <RepositoryFact name="coverageThreshold" unit="percent" />.
5. Esegui i controlli qui sotto.
6. Esegui il commit con un messaggio in formato [conventional commit](/docs/tooling/conventional-commits), apri una pull request con un titolo convenzionale e compila il suo modello.
7. Fai il rebase del branch su `main` quando entra in conflitto, mai il merge di `main` al suo interno, come spiega [Git e pull request](/docs/conventions/git-workflow#linear-history). Chi mantiene il progetto mette la pull request verde nella [coda di merge](/docs/conventions/git-workflow#merging), che la testa di nuovo sopra `main` e ne fa il merge.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`build:test` esegue la build completa di Cloudflare, che `check` e i test unitari non mettono alla prova. L'ultimo comando compila e serve il Worker di test quando non è in esecuzione alcun server ed esegue in Chromium le spec che indichi: esegui quelle che coprono ciò che hai modificato. La CI esegue ogni spec sulla pull request e di nuovo nella coda di merge, e la pull request viene unita solo quando quell'esecuzione è verde; `bun run test:e2e:pr` esegue l'intera suite in locale allo stesso modo. Esegui la suite completa di test nel browser anche in WebKit (`bun run test:e2e`) per le modifiche che lì potrebbero comportarsi diversamente. Verifica separatamente le integrazioni con i provider reali quando ne modifichi la configurazione.

Quando il comportamento cambia, aggiorna `content/docs` in tutti i locale; `bun run check:content` rifiuta traduzioni mancanti, blocchi di codice e navigazione diversi. Il modello della pull request prevede un riepilogo, un piano di test con i controlli qui sopra e l'elenco della documentazione aggiornata; descrivi lì il comportamento risultante, come l'hai verificato ed eventuali workflow che la modifica lascia incompleti. Una schermata di amministrazione viene rilasciata solo con una fonte reale per i suoi dati (vedi [Dashboard di amministrazione](/docs/features/admin-dashboard#real-data-only)).

`CONTRIBUTING.md`, nella radice del repository, è la versione breve di questa pagina, e `SUPPORT.md` indica dove trovare aiuto. Chiunque partecipi segue `CODE_OF_CONDUCT.md`, il Contributor Covenant 2.1. Segnala le vulnerabilità di sicurezza in privato, come descritto in `SECURITY.md`, mai in una issue pubblica.
