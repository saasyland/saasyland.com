Business operations live in `src/modules/<table>/use-cases/<operation>.ts`, one operation per file. Each exports a native `createServerFn` with its middleware, Zod validation and handler, plus the query or mutation options that components use. A server function that belongs to no table goes in `src/lib` (for example `getStarCount` in `src/lib/github.ts`), and one used by a single route can be defined in that route file (`getBlogPosts` in `src/routes/blog.index.tsx`).

```ts
export const createCategory = createServerFn({ method: "POST" })
  .middleware([authorized({ category: ["create"] })])
  .validator((input: zod.input<typeof categoryZodSchemas.createCategory>) => categoryZodSchemas.createCategory.parse(input))
  .handler(({ data }) =>
    db
      .insert(category)
      .values({
        description: data.description ?? "",
        icon: data.icon ?? "FolderOpen",
        id: v7(),
        kind: data.kind,
        name: data.name,
        visibility: data.visibility ?? "public",
      })
      .returning()
      .get(),
  )

export const createCategoryMutation = mutationOptions({
  mutationFn: (data: Parameters<typeof createCategory>[0]["data"]) => createCategory({ data }),
  mutationKey: CATEGORY_MUTATION_KEYS.CREATE,
})
```

## Rules

- Middleware runs before validation and the handler. Use `authorized(permission?)` for protected operations and `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` or `RATE_LIMITS.TOKEN` for sensitive public ones; see [Better Auth](/docs/integrations/better-auth).
- Validate input with the module's Zod schema (`<table>.zod.ts`).
- Return data directly and throw `AppError(ERROR_CODES.X)` from `src/modules/_core/constants/errors.ts` for expected failures. Other errors reach the client as `INTERNAL_ERROR`, so provider details stay on the server.
- Query and mutation keys are readonly tuples in the module's `<table>.constants.ts`, and query keys include every input that changes the result.
- Keep operations atomic with a single SQL statement or `db.batch`; D1 has no interactive transactions.

## Using a use case

Components spread the exported options into `useQuery`, `useSuspenseQuery` or `useMutation`, translate errors with `useErrorMessage()` from `src/hooks/use-error-message.ts` and invalidate the module's query keys after a successful mutation:

```tsx
const deleteUser = useMutation({
  ...deleteUserMutation,
  onError: (error) => {
    toast.error(errorMessage(error))
  },
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: USER_QUERY_KEYS.ALL })
    toast.success(t("feedback.deleteSuccess"))
  },
})
```

Loaders preload the same query options in their `Promise.all`, so server rendering and the client share one cache entry.
