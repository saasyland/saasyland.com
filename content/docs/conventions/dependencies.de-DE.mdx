Das Repository läuft auf dem neuesten Release jeder Abhängigkeit. Ein Upgrade, das etwas kaputt macht, wird nach vorn behoben, im Code oder upstream, niemals durch einen Rückschritt.

## Versionen der Toolchain

- Bun ist Paketmanager und Skript-Runner. `packageManager` in `package.json` (Bun <RepositoryFact name="bunVersion" />) ist die einzige Stelle, an der seine Version festgelegt wird; die CI liest sie von dort. `bun.lock` ist eingecheckt.
- Node stammt aus `.nvmrc` (<RepositoryFact name="nodeVersion" />), und `engines.node` verlangt mindestens diese Version.
- `remotion/` ist die einzige Ausnahme, mit einer eigenen npm-Toolchain, die nur installiert wird, wenn du die Videos der Landingpage bearbeitest. Sein `typescript` ist das neueste Release, das `typescript-eslint`, das die Lint-Regeln von Remotion ausführt, als Peer-Abhängigkeit akzeptiert, weil TypeScript 7 die Compiler-API, die `typescript-eslint` liest, nicht mitliefert. Die Pakete, die es mit der Website teilt, `@saasyland/stack`, `lucide-react`, `react` und `react-dom`, sind auf die niedrigste Version festgelegt, die das `package.json` der Website zulässt, weil die Videos Dateien der Website rendern, die sie importieren, und `src/data/__test__/cli.test.ts` schlägt fehl, wenn die beiden voneinander abweichen.

## Upgrades

1. Lies das Changelog und den Migrationsleitfaden der neuen Version, am besten die Fassung, die in `node_modules/<package>` mitgeliefert wird.
2. Passe den Code an die dokumentierte Verwendung der neuen Version an.
3. Prüfe in dieser Reihenfolge, und melde nichts als erledigt, bevor der letzte Schritt erfolgreich ist:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` und die Tests laufen ohne den Build von Cloudflare und TanStack Start, daher können sie erfolgreich sein, während der Build kaputt ist. Das ist bei einem einzigen Upgrade zweimal passiert: Ein neues `@polar-sh/sdk` ließ sich nicht bundeln, und ein Release von TanStack Start änderte das `modulepreload`-Markup, das `optimize-prerendered-html.ts` umschreibt. Beides zeigte sich erst in `build:test`. Nach einem Build darf `find dist/server -name '*.map'` nichts ausgeben; `upload_source_maps: false` in `wrangler.jsonc` existiert, weil der Worker mit seinen Source Maps größer ist, als Cloudflare für einen Upload akzeptiert (siehe [Cloudflare Workers](/docs/integrations/cloudflare-workers)).

Setze ein Paket nie auf ein älteres Release zurück, um einem Breaking Change auszuweichen, und füge der Anwendung nie Code hinzu, der einen Bibliotheksfehler umgeht.

## Wenn der Bug upstream liegt

Wenn die Anwendung bereits der dokumentierten Verwendung folgt und die neue Version fehlerhaft ist, behältst du die neue Version und führst die Korrektur selbst mit:

1. Belege den Bug mit einer minimalen Reproduktion außerhalb dieses Repositorys.
2. Schreibe die kleinste Änderung, die ihn im Paket behebt, entsprechend dem Fix, den du upstream vorschlagen wirst, und speichere sie mit `bun patch`. Der Patch landet in `patches/<package>@<version>.patch` und in `patchedDependencies`, und das Paket wird auf genau diese Version fixiert, damit der Patch weiterhin angewendet wird.
3. Melde den Bug upstream und öffne einen Pull Request mit dem Fix, gemäß den Beitragsregeln des jeweiligen Projekts.
4. Lösche den Patch, sobald ein Release den Fix enthält. Bevor du einen Patch behältst oder dokumentierst, prüfe mit `npm view <package> version`, ob dieses Release bereits erschienen ist.

Die aktuellen Patches:

Ein Patch ändert die Dateien eines Pakets, nicht die Versionen, die Bun dafür installiert. Wenn ein Paket eine seiner eigenen Abhängigkeiten unter dem Release fixiert, das die Anwendung verwendet, hebt stattdessen ein Eintrag unter `overrides` in `package.json` sie an:

- `"@polar-sh/sdk": "^1.3.0"`. `@polar-sh/adapter-utils` 1.1.0, das `@polar-sh/better-auth` verwendet, fixiert `@polar-sh/sdk` 1.0.2 und typisiert `webhooks({ onPayload })` des Plugins mit dieser Kopie, während das Plugin jedes Ereignis mit der Version 1.3.0 der Anwendung validiert. `handlePolarEvent` nimmt die Payload von 1.3.0 entgegen, die der Typ aus 1.0.2 nicht akzeptiert. Der Adapter importiert das SDK nur für Typen, daher ändert der Eintrag keinen gebündelten Code. Lösche ihn, sobald ein Release von `@polar-sh/adapter-utils` von `@polar-sh/sdk` 1.3.0 oder neuer abhängt (`npm view @polar-sh/adapter-utils dependencies`).

## Sicherheitshinweise

Dependabot-Warnungen decken `remotion/package-lock.json` ab, aber GitHub liest `bun.lock` nicht. Prüfe die Anwendung deshalb mit `bun audit` und das Videoprojekt mit `npm audit` in `remotion/`. Behebe einen Sicherheitshinweis mit dem neuesten Release des Pakets, das das betroffene Paket einbindet. Wenn dessen Versionsbereich das korrigierte Release bereits zulässt, genügt es, die Lockfile zu aktualisieren: `bun update` oder `npm update` in `remotion/`.

Solange kein Release des übergeordneten Pakets die Korrektur zulässt, hebt ein Eintrag unter `overrides` das betroffene Paket an, und er wird gelöscht, sobald ein Release des übergeordneten Pakets das tut. Die aktuellen Einträge:

- `package.json`: `"minimatch": "^11.0.1"`. `shadcn` erreicht `minimatch` ^10 über `ts-morph` 26 und `@ts-morph/common`, und erst `minimatch` 11.0.1 behebt GHSA-g3hv-75wg-m249. Lösche den Eintrag, wenn `shadcn` von einem `ts-morph`-Release abhängt, das [dsherret/ts-morph#1697](https://github.com/dsherret/ts-morph/pull/1697) enthält.
- `remotion/package.json`: `minimatch` ^11.0.1 unter `@typescript-eslint/typescript-estree`, für denselben Sicherheitshinweis. `@remotion/eslint-config-flat` fixiert `typescript-eslint` auf 8.71.2, dessen Parser `minimatch` ^10 verlangt. Lösche den Eintrag, wenn `@remotion/eslint-config-flat` von einem `typescript-eslint`-Release abhängt, das [typescript-eslint/typescript-eslint#13145](https://github.com/typescript-eslint/typescript-eslint/pull/13145) enthält.

`bun audit` meldet weiterhin einen Sicherheitshinweis, für den es keine Korrektur zum Übernehmen gibt:

- `esbuild` 0.18.20 (GHSA-67mh-4wv8-2f99, mittel), über `drizzle-kit` und `@esbuild-kit/esm-loader`. `drizzle-kit` 0.31.11 deklariert den Loader, importiert ihn aber nie, und der Hinweis betrifft den Entwicklungsserver von esbuild, den hier nichts startet. [drizzle-team/drizzle-orm#5304](https://github.com/drizzle-team/drizzle-orm/issues/5304) verfolgt seine Entfernung; die Release Candidates von `drizzle-kit` 1.0 hängen nicht mehr davon ab.

GitHub hat den Sicherheitshinweis zu `deepmerge` 4.3.1 (GHSA-gcqx-w48m-w2h4), das `shadcn` und `@shadcn/registry` einbanden, nach [github/advisory-database#10910](https://github.com/github/advisory-database/issues/10910) zurückgezogen, daher meldet `bun audit` ihn nicht mehr.

## Die Vite+-Einträge in package.json

```json
"vite": "npm:@voidzero-dev/vite-plus-core@8.3.8000",
"vite-plus": "1.7.0",
"vitest": "5.1.0"
```

Diese Zeilen sowie derselbe `vite`-Alias und dieselbe `vitest`-Version unter `overrides` sind genau das, was der eigene Migrator von Vite+ schreibt: `vite-plus` ist auf eine exakte Version fixiert, Bun braucht den Core als direkte `vite`-Abhängigkeit, und `vitest` ist aufgeführt, weil `@vitest/coverage-v8` und die Testtypen es brauchen. Seit `vite-plus` 1.7.0 trägt der Core die Version des Vite-Releases, das er bündelt, 8.3.8000 ist also Vite 8.3.8; `vp toolchain` zeigt die Zuordnung. Aktualisiere sie gemeinsam mit `vp migrate`, niemals mit `bun update`. Um herauszufinden, ob einer davon entfallen kann, kopiere das Projekt, führe `vp migrate` auf der Kopie aus und vergleiche das Ergebnis per Diff; entscheide es nicht durch Nachdenken. Der `minimatch`-Eintrag unter `overrides` ist die oben beschriebene Sicherheitskorrektur, und `vp migrate` lässt ihn unverändert.

`build.rolldownOptions.external`, das `src/data/polar.vite.ts` setzt, listet optionale Peer-Abhängigkeiten von `@polar-sh/sdk` auf, die nicht installiert sind und per Tree-Shaking aus dem Worker entfernt werden; siehe [Vite+](/docs/tooling/vite-plus). Entferne die Liste, wenn Polar sein Packaging korrigiert.

## Eine Abhängigkeit hinzufügen

Prüfe zuerst, ob ein Paket, das bereits in `package.json` steht, die Aufgabe erledigt, damit jeder Belang bei einer Bibliothek bleibt. Füge eine Laufzeitabhängigkeit mit `bun add` hinzu, ein Werkzeug mit `bun add --dev`, und verwende den Agent-Skill des Anbieters aus `skills-lock.json`, wenn es einen gibt (siehe [Agent-Skills](/docs/tooling/agent-skills)).
