## Données

`src/modules/category/category.schema.ts` définit la table `category` : `name`, `description`, `kind` (`category` ou `collection`), `visibility` (`public` ou `hidden`), `icon` (`Archive`, `FolderOpen` ou `Puzzle`) et les horodatages.

Cas d’usage dans `src/modules/category/use-cases`, chacun protégé par la permission `category` correspondante : `getCategories` (paginé, `kind` facultatif), `getCategory`, `createCategory`, `updateCategory` et `deleteCategory`. `createCategory` est la structure de référence d’un cas d’usage de mutation :

```ts
export const createCategory = createServerFn({ method: "POST" })
  .middleware([authorized({ category: ["create"] })])
  .validator((input: Category["createCategory"]) => categoryZodSchemas.createCategory.parse(input))
  .handler(({ data }) =>
    db
      .insert(category)
      .values({
        description: data.description ?? "",
        icon: data.icon ?? CATEGORY_ICON.FOLDER_OPEN,
        id: v7(),
        kind: data.kind,
        name: data.name,
        visibility: data.visibility ?? CATEGORY_VISIBILITY.PUBLIC,
      })
      .returning()
      .get(),
  )

export const createCategoryMutation = mutationOptions({
  mutationFn: (data: Category["createCategory"]) => createCategory({ data }),
  mutationKey: CATEGORY_MUTATION_KEYS.CREATE,
})
```

Les messages d’erreur se trouvent dans l’espace de noms `category.errors`. Aucun formulaire ne modifie encore les catégories, leurs messages Zod recevront donc un espace de noms `category.validations` avec le premier formulaire qui les affiche.

## Écran d’administration

Aucun écran ne liste, ne crée, ne modifie ni ne supprime de catégorie, et les produits n’ont pas de relation avec les catégories. `/admin/products` liste le catalogue de Polar (voir [Produits](/docs/features/products)).
