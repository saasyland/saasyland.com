SaaSy Land unterstützt neun Sprachen: `en-US` (Standard), `de-DE`, `es-ES`, `fr-FR`, `it-IT`, `ja-JP`, `pl-PL`, `pt-BR` und `uk-UA`. Englisch verwendet Pfade ohne Präfix (`/docs`); die übrigen Sprachen verwenden das vollständige Sprachpräfix (`/pl-PL/docs`). Sprachkürzel wie `/pl/docs` leiten dauerhaft auf den kanonischen Pfad um.

## Dateien

`src/integrations/use-intl/` enthält die gesamte Sprachlogik:

| Datei                | Verantwortung                                                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `i18n.config.ts`     | `I18N` mit `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, `COOKIE_NAME` und `DEFAULT_TIMEZONE`                                         |
| `i18n.messages.ts`   | `loadNamespace`, `loadPageMetadata`, `messagesQueryOptions`, `preloadNamespaces` und `ROOT_NAMESPACES`                         |
| `i18n.middleware.ts` | `resolveLocale`: kanonische Weiterleitungen und Abgleich des Sprach-Cookies für Dokument-Requests, genutzt von `src/server.ts` |
| `i18n.paths.ts`      | `localizePathname`, `deLocalizePathname`, `canonicalizePathname`, `localeLinks` und verwandte Pfad-Hilfsfunktionen             |
| `i18n.utils.ts`      | `getCurrentLocale`, `localizeUrl`, `deLocalizeUrl` und `parseLocaleCookie`                                                     |

## Namespaces

Nachrichten liegen in `messages/<locale>/<namespace>.json`, und der Dateiname ist der Namespace: `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` oder `common`. Nachrichten sind reines JSON ohne generierte Typen. Jeder Seiten-Namespace enthält `metadata.title` und `metadata.description` für den Seitenkopf.

Die Root-Route lädt die Root-Namespaces (`common`, `components.*` und `errors*`) in `beforeLoad` vor. Eine Seitenroute deklariert einen `NAMESPACE`, eine Layout-Route deklariert `NAMESPACES` für ihren Teilbaum; beide führen sie in `staticData.namespaces` auf und laden sie im Loader vor:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_landing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  staticData: { namespaces: [NAMESPACE] },
})
```

`TranslationsProvider` umschließt den Body des Dokuments und führt die Root-Namespaces mit den Namespaces jeder passenden Route in einem `IntlProvider` zusammen, sodass auch Fehler- und Not-found-Ansichten übersetzt sind. E-Mail-Namespaces lädt nur der serverseitige Anwendungsfall, der die E-Mail versendet.

## Sprache und Links

`getCurrentLocale()` ist isomorph. Auf dem Server liest die Funktion die Sprache aus der URL oder, bei `/api`- und Serverfunktions-Requests, aus dem Sprach-Cookie; im Browser liest sie die URL. Der Worker hält das Cookie mit der Seiten-URL synchron.

Das `rewrite` des Routers entfernt das Sprachpräfix aus eingehenden URLs und fügt es ausgehenden hinzu, sodass `<Link to={ROUTES.X}>` immer in der aktuellen Sprache bleibt. Verwenden Sie `localizePathname({ locale, pathname })` nur für rohe URLs: Callback-URLs von Better Auth, Links in E-Mails und von Hand gebaute `<a href>`-Elemente. Der Sprachumschalter ist ein solcher Link, sodass die Wahl einer Sprache dieselbe Seite in einem neuen Dokument lädt.

## Komponenten

Eine Komponente ruft `useTranslations` genau einmal auf und nennt die Übersetzungsfunktion `t`. i18n-ally ordnet jedes spätere `t()` nach einem weiteren `useTranslations`-Aufruf einem neuen Scope zu, und `bun run check:i18n` schlägt bei Schlüsseln fehl, die sich in ihrem Scope nicht auflösen lassen. Eine Komponente, die zwei voneinander unabhängige Namespaces benötigt, verwendet deren gemeinsamen übergeordneten Namespace oder `useTranslations()` mit vollständigen Schlüsseln.

## Prüfungen

`bun run check:i18n` führt drei Skripte aus, und `bun run check` schließt es ein:

- `scripts/check-i18n.ts`: Schlüsselgleichheit mit `en-US` und Auflösung statischer Schlüssel im jeweiligen Scope.
- `scripts/check-message-formats.ts`: Jede Nachricht lässt sich als ICU parsen und behält ihre Argumente und Rich-Text-Tags.
- `scripts/check-content.ts`: Docs- und Blog-Dateien, Navigation und Codebeispiele stimmen über alle Sprachen hinweg überein.
