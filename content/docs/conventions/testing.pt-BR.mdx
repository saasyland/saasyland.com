Toda alteração é entregue com os testes que a comprovam, no mesmo commit, e a cobertura se mantém em <RepositoryFact name="coverageThreshold" unit="percent" /> para linhas, instruções, funções e branches. A correção de um bug vem com um teste que falha sem a correção.

## Projetos

`vite.config.ts` define três projetos do Vitest, escolhidos pelo sufixo do arquivo. Os testes importam a sua API de `vite-plus/test` e ficam em `__test__/`, ao lado do código que cobrem.

| Sufixo                 | Projeto       | Use para                                                                                                                                                                                 |
| ---------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | Casos de uso, loaders, `head`, schemas, utilitários: tudo o que roda no servidor                                                                                                         |
| `.integration.test.ts` | `integration` | Fluxos do Better Auth, de pagamento e de licença, o adaptador do D1 e o carregamento de mensagens, com timeouts de <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Componentes e páginas no jsdom                                                                                                                                                           |

`src/platform/testing/mocks/cloudflare.ts` substitui `cloudflare:workers` em todos os projetos: o D1 é um banco de dados `node:sqlite` em memória criado a partir de todas as migrações versionadas, e o KV e um bucket para cada binding do R2 do ambiente `test` em `wrangler.jsonc` são armazenamentos em memória. `resetTestBindings()` esvazia o KV, o bucket e a tabela de rate limit antes de cada teste, e a função de seed de cada suíte redefine as linhas de que ela depende. Nenhum teste se comunica com o Cloudflare, o Polar, o Resend ou um provedor OAuth: o `fetch` chega aos dublês estritos em `mocks/resend.ts` e `mocks/polar.ts`, que validam cada requisição com base nos modelos de requisição dos SDKs e fazem o teste falhar diante de uma que o provedor recusaria. Os testes verificam o que o dublê recebeu em vez de fazer mock de um método do SDK, e as suítes de autenticação exercitam a configuração real de `auth.server.ts` por meio de `auth.harness.ts`.

## Testar uma server function

Chame-a pelas options que ela exporta, para que o teste exercite o middleware, a validação e o handler reais. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts`:

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` e `executeMutation(options, variables)` de `src/platform/testing/lib/query.ts` executam as options em um `QueryClient` novo.
- A sessão vem de `createAuthSessionFixture` em `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts`; toda permissão também é testada pelo lado que precisa ser recusado (`it("is for staff only")`).
- Os dados de seed ficam em `__test__/fixtures/` do módulo, com os seus IDs em objetos nomeados (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` exclui as linhas que são suas e as insere de novo pelo Drizzle, então todo teste começa do mesmo estado.
- No projeto `component`, uma server function falha, porque o jsdom faz o papel do navegador. Os testes de componentes fornecem a uma rota os dados do loader ou fazem mock de `queryFn` e `mutationFn` das options que o componente lê.

## As asserções usam os nomes do código

- Status, tipos, papéis e códigos de erro esperados são as constantes que o código usa: `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. Um teste nunca repete um literal de string do domínio, e os dados do e2e e o seed de teste também não: `e2e/data/courses.ts` escreve `kind: COURSE_KIND.COURSE`.
- Os testes de schema são o único lugar em que um valor armazenado é escrito por extenso: `product.schema.test.ts` fixa `expect(PRODUCT_STATUSES).toStrictEqual(["draft", "published", "archived"])`, de modo que mudar um valor guardado no banco faz um teste falhar em vez de exigir uma migração que ninguém escreveu.
- A suíte do navegador importa suas constantes da aplicação (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`), então só pode importar arquivos que carregam fora do Worker. O único valor de provedor que ela mesma declara é o status de pedido pago em `e2e/fixtures/polar.ts`, porque `polar.constants.ts` lê `cloudflare:workers` e é exclusivo do servidor; o pedido em si vem de `src/platform/testing/lib/polar.ts`.
- Os testes de componentes leem os textos esperados dos arquivos de mensagens em inglês, como faz `admin-course-routes.component.test.tsx` com `import labels from "~/messages/en-US/pages.admin.courses.json"` e `labels.form.kinds.course`, e encontram os elementos pelo papel e pelo nome acessível.
- Um teste que precisa de um tipo o lê de uma fonte tipada ou o verifica em tempo de execução com `toHaveProperty`; ele nunca faz cast.
- Os nomes dos testes descrevem o comportamento como uma frase: "lists every course with its lesson count, drafts included".

## Cobertura

`bun run test:coverage` falha abaixo de <RepositoryFact name="coverageThreshold" unit="percent" /> em qualquer uma das quatro métricas para `src/**/*.{ts,tsx}`. Ficam de fora os testes, `__test__/`, os arquivos de declaração, `src/routeTree.gen.ts`, os primitivos do shadcn e `src/platform/testing/`. A exigência continua significativa assim:

- **Exclua os branches que nunca podem ser executados** em vez de cobri-los com stubs. Um `?? fallback` sobre dados que estão sempre presentes, ou um optional chaining sobre um valor que não pode ser `undefined`, é removido do código-fonte, e não alcançado com o stub de um global.
- **Cubra comportamento real.** Os estados pendentes mantêm a requisição aberta com `Promise.withResolvers()`, verificam a UI pendente, resolvem dentro de `act` e verificam a UI ociosa, como fazem `expectPending` e `expectIdle` em `auth-forms.component.test.tsx`.
- **Mantenha as asserções quando uma regra apertar.** Quando um teste ultrapassa `max-statements`, extraia um helper nomeado em vez de remover verificações.
- **Carregue todos os arquivos de mensagens.** `i18n.messages.test.ts` carrega todos os namespaces de todos os locales, e é isso que cobre as linhas de `import.meta.glob` em `i18n.messages.ts`. Um arquivo de mensagens novo fica coberto por ele automaticamente.

## Os testes seguem as áreas [#tests-follow-the-areas]

As áreas que declaram os próprios caminhos e itens de menu (veja [Caminhos e navegação](/docs/conventions/routes#paths-and-navigation)) também são donas dos próprios testes, então a CLI `saasyland` pode deixar uma área de fora de um projeto gerado junto com os testes dela, e todos os outros testes continuam passando.

Um arquivo de teste cobre uma área ou um arquivo de código. As páginas de administração de uma área são testadas com os esqueletos e a trilha de navegação em `src/routes/__test__/admin-<area>-routes.component.test.tsx`, e os loaders delas em `admin-<area>-loaders.test.ts`; `admin-layout`, `admin-dashboard` e `admin-loaders` testam a própria interface de administração e não citam nenhuma área. Arquivos sem relação entre si têm cada um o seu arquivo de teste, como `background.component.test.tsx` e `wordmark.component.test.tsx`, e cada handler da API tem o seu: `src/routes/api/__test__/auth.test.ts`, `search.test.ts` e `index.test.ts`. `cli.v1.test.ts` cobre os arquivos de rota da API de licenças da CLI, cujo comportamento é testado em `src/modules/license/__test__/license.api.integration.test.ts`.

Uma lista que abrange várias áreas é declarada por área e reunida por um barrel:

| Lista                               | Cada área declara                                                                                                          | Barrel                       | Lida por                                       |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ---------------------------------------------- |
| Dados de consultas da administração | `seed<Area>Queries` e as fábricas de linhas dela em `src/presentation/components/custom/admin/__test__/<area>.fixtures.ts` | `fixtures.entries.ts`        | `adminQueryClient()` em `fixtures.tsx`         |
| Rótulos de enumerações              | `src/integrations/use-intl/__test__/<area>.labels.ts`                                                                      | `labels.entries.ts`          | `enum-labels.test.ts`                          |
| Linhas do D1                        | `src/integrations/drizzle-orm/__test__/<area>.rows.ts`                                                                     | `rows.entries.ts`            | `d1.integration.test.ts`                       |
| Páginas dos testes no navegador     | `e2e/data/<area>.pages.ts`                                                                                                 | `e2e/data/pages.entries.ts`  | `accessibility.spec.ts` e `workspaces.spec.ts` |
| Banco de dados de teste             | `e2e/data/<area>.seed.ts`                                                                                                  | `e2e/data/seed.entries.ts`   | `scripts/seed-test.ts`                         |
| Consultas públicas                  | `src/integrations/better-auth/__test__/<area>.public-queries.ts`                                                           | `public-queries.entries.ts`  | `auth.session.test.ts`                         |
| Dublês dos provedores               | `src/platform/testing/mocks/<provider>.ts`: um `origin`, `respond` e `reset`                                               | `mocks/providers.entries.ts` | `mocks/providers.ts`                           |
| Worker de testes                    | `e2e/data/<area>.worker.ts`: preparações e endpoints de teste                                                              | `e2e/data/worker.entries.ts` | `src/platform/testing/worker.ts`               |

Helpers usados por várias áreas existem uma única vez: `renderAdmin` e `renderAdminPage` em `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` em `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` e `busyMarkup` em `src/platform/testing/lib/skeleton.tsx` e, nos testes no navegador, `AuthPage.signIn`, `BasePage.leaveWhileLoading` e a fixture `pageWithoutJavaScript`. As specs das páginas públicas, como `accessibility.spec.ts` e `theme.spec.ts`, não fazem login em nenhuma conta; `workspaces.spec.ts` verifica as páginas logadas, a acessibilidade delas e o tema delas.

Um teste de código compartilhado que precisa de um item fornecido pelas áreas declara o seu próprio em vez de ler o de uma área. `dashboard-actions.component.test.tsx` substitui `ADMIN_DASHBOARD_ACTIONS` por uma ação local do teste, para que `DashboardActions` e os marcadores das ações de `AdminDashboardPending` continuem cobertos em um projeto sem a área de produtos, que hoje declara a única ação do painel. `server.test.ts`, `root.component.test.tsx` e `vite.test.ts` fazem o mesmo com handlers do Worker, componentes raiz e plugins do Vite locais do teste, e cada área testa os próprios itens em `src/data/__test__/<area>.worker.test.ts` e `<area>.vite.test.ts`. Código compartilhado que só áreas opcionais renderizam ganha um teste próprio: `pending-blocks.component.test.tsx` cobre os esqueletos de campo, de interruptor e de área de upload que os esqueletos de produtos, cursos, pagamentos e do editor de posts usam. Um teste do controle de acesso compartilhado verifica apenas as declarações da área de autenticação e as do próprio Better Auth; cada área testa o que concede em `src/data/__test__/<area>.access.test.ts`, e `access.website.test.ts` fixa as permissões de cada papel no site.

Os testes de rotas e de esqueletos da licença substituem as seções da oferta de licenças por uma seção local do teste, e os testes de cursos substituem as concessões de acesso aos cursos por `TEST_COURSE_ACCESS` (`src/modules/course/__test__/fixtures/course-access.ts`), então os testes de nenhuma das duas áreas leem a outra. `license.course-access.test.ts` cobre o que as une: a concessão da licença, com um snapshot de quem pode assistir a cada aula para um visitante, uma conta, a equipe e cada nível e status de licença.

Um teste que fixa o site inteiro, como `navigation.website.test.ts` com a ordem de cada menu, pertence só ao site; os templates não o geram.

## Testes no navegador

O Playwright executa o Worker de teste compilado: `bun run build:test` o compila com D1 e KV locais em `.wrangler/test`, `bun run db:reset:test` recria esse banco de dados e cria as contas, o vídeo e o curso de `e2e/data`, e a entrada de teste captura os e-mails enviados em `/__test/emails`, para que uma spec possa seguir um link de verificação.

- As specs levam o nome do fluxo (`course-admin.spec.ts`, `auth-redirect.spec.ts`) e conduzem a página por papéis e nomes acessíveis, com os page objects em `e2e/pages/`.
- Cada spec cria os dados que altera com valores únicos, como um slug montado a partir de `crypto.randomUUID()`, e faz login a partir do seu próprio cabeçalho `CF-Connecting-IP`, para que as specs possam rodar em paralelo e ser executadas de novo sem colidir umas com as outras nem com os rate limits.
- Uma spec age sobre uma página só depois que `waitForAppReady()` de `e2e/pages/base-page.ts` termina, inclusive após uma navegação no cliente. O método termina quando o TanStack Router renderizou a URL atual, que a fixture automática `recordRenders` registra a partir do evento `onRendered` do router, porque uma navegação no cliente muda a URL antes de a próxima rota renderizar. O conteúdo da rota pode ser hidratado depois dessa renderização, então uma spec que depende do estado próprio de um componente, ou que clica em um link fora do conteúdo antes de ele ser hidratado, chama antes `waitForHydration(element)`, que espera o React hidratar o elemento e tudo o que há nele; `LandingPage.goto()` faz isso com o `main` da landing page. Uma spec pode sair de uma página enquanto ela carrega, como um visitante pode, e uma que coleta os erros de página de várias visitas diretas abre cada visita na sua própria aba, como faz `auth-routing.spec.ts`.
- Os pull requests executam todas as specs no Chromium (`bun run test:e2e:pr`); os pushes para `main` e uma execução semanal agendada também executam o WebKit.
- Uma correção de rota, de fluxo ou visual que os testes unitários não conseguem ver ganha uma spec: as varreduras de acessibilidade e as regressões de navegação em `navigation.spec.ts` e nas specs das áreas a que se referem, como `content.spec.ts`, `legal.spec.ts` e `landing.spec.ts`, são exemplos.
