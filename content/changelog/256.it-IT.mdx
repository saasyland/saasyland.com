- Corretto: un nuovo worktree Git riceve i suoi hook di commit. `git worktree add` installa il dispatcher degli hook del nuovo worktree tramite l'hook `post-checkout`, quindi un commit fatto prima di `bun install` fallisce nell'hook `pre-commit` invece di saltarlo, e `bun install` fallisce quando `core.hooksPath` non è `.vite-hooks/_` o quando al dispatcher manca un hook. Finora Git creava commit senza hook, e senza alcun avviso, in ogni worktree che non aveva un proprio dispatcher. Vedi [Git e pull request](/docs/conventions/git-workflow#hooks-in-every-worktree).
- Corretto: [Git e pull request](/docs/conventions/git-workflow#linear-history) non ti dice più di fare il merge di `main` nel branch di una pull request e di non fare mai il force-push. Descrive la cronologia lineare che segue il progetto: nessun merge commit, nemmeno sul branch di una pull request, branch aggiornati con il rebase su `main`, una pull request di cui GitHub non riesce a fare il rebase riportata come un unico commit, e branch riscritti pubblicati con `git push --force-with-lease`. `AGENTS.md`, `CONTRIBUTING.md` e la pagina [Come contribuire](/docs/project/contributing) dicono lo stesso.
