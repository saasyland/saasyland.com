I workflow si trovano in `.github/workflows/`. I workflow dell'applicazione (`ci.yml`, `deploy.yml`, `e2e-reusable.yml` e `deploy-reusable.yml`) preparano la toolchain con l'azione composita `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ con la versione di Node in `.nvmrc` e la cache di installazione di Bun, che `setup-vp` ripristina una sola volta, `bun install --frozen-lockfile --ignore-scripts` e `bun run typegen`. `remotion.yml` invece prepara Node da `.nvmrc` e npm.

| Workflow              | Attivazione                                                                                 | Job                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull request, e chiamate da `deploy.yml`                                                    | Controlli e copertura, E2E su Chromium, poi il deploy di preview di una pull request               |
| `deploy.yml`          | Push su `main`                                                                              | I controlli di `ci.yml`, poi il deploy di produzione e la sua release                              |
| `e2e-full.yml`        | Push su `main`, la pianificazione <RepositoryFact name="e2eFullSchedule" /> in UTC, manuale | WebKit al push; Chromium e WebKit nelle esecuzioni pianificate e manuali                           |
| `e2e-reusable.yml`    | Richiamato dai workflow precedenti                                                          | Una sola build di test, un progetto Playwright su shard paralleli e un solo controllo per entrambi |
| `deploy-reusable.yml` | Richiamato da `ci.yml` e `deploy.yml`                                                       | Build, migrazioni D1 e `wrangler deploy`                                                           |
| `remotion.yml`        | Modifiche a `remotion/` o ai file del sito che importa                                      | Controlla e crea il bundle del progetto video della landing page con npm                           |

`remotion.yml` si attiva sugli stessi percorsi per le pull request e i push: `remotion/`, il workflow stesso e i file del sito che `remotion/src` importa, direttamente o tramite altri file del sito. `src/__test__/workflows.test.ts` segue queste importazioni e fallisce quando un file che raggiungono non corrisponde a nessuno dei percorsi, o un percorso non corrisponde a nessuno dei file.

I checkout di `e2e-reusable.yml`, la cui build genera il changelog e il cui `content.spec.ts` lo legge, di `deploy-reusable.yml`, che compila il sito, e del job `release` scaricano tutti i commit senza i loro alberi (`fetch-depth: 0` e `filter: tree:0`): il [changelog](/docs/project/changelog) data ogni voce in base al commit che l'ha portata su `main`. Rispetto a un clone superficiale si aggiungono solo i commit stessi; un clone superficiale farebbe fallire la build invece di datare male le voci. `src/__test__/workflows.test.ts` fallisce quando uno di questi checkout smette di scaricare la cronologia.

## Controlli [#checks]

Il job `verify` in `ci.yml` esegue `bun run check` (tabelle dei nomi delle classi, controlli di i18n e dei contenuti, l'[inventario dei flussi](/docs/tooling/test-coverage#flow-coverage), formattazione, lint e tipi) e `bun run test:coverage`, poi carica il report di copertura. Il job `e2e` richiama `e2e-reusable.yml`, che compila una sola volta ed esegue la suite su <RepositoryFact name="e2eShards" /> runner in parallelo:

| Job                                           | Esegue                                                                                                                                                     |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                       | `db:reset:test` e `build:test`, poi carica `dist` e il `.wrangler/test` popolato dal seed come un unico artefatto                                          |
| `shard`                                       | Un job per shard: scarica quella build, installa il browser ed esegue `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>`              |
| `report`, chiamato `Build and E2E (chromium)` | Fallisce a meno che la build e ogni shard siano riusciti; quando uno shard è fallito, unisce i report blob degli shard in un unico report HTML e lo carica |

I retry e i worker di Playwright restano come li descrive [Playwright](/docs/tooling/playwright#configuration), su ogni shard. Il job `report` è l'unico controllo richiesto dalle regole del branch, quindi aggiungere o rimuovere uno shard non cambia il nome di nessun controllo richiesto.

In una pull request, `bun run check` fallisce anche finché la pull request non aggiunge la propria [voce del changelog](/docs/conventions/git-workflow#changelog-entries). La build del job `e2e`, e quella dei job di deploy, fallisce finché il changelog mostrerebbe sotto **Non rilasciato** una voce che non è quella della pull request stessa, e su `main` finché ne mostrerebbe una qualsiasi.

## Deploy

I deploy vengono eseguiti solo dopo il successo di `verify` ed `e2e`, nel run di `ci.yml` per una pull request e nel run di `deploy.yml`, che richiama `ci.yml`, per un push su `main`:

| Evento                                         | Destinazione | Ambiente GitHub | URL                           |
| ---------------------------------------------- | ------------ | --------------- | ----------------------------- |
| Pull request da un branch di questo repository | `preview`    | `Preview`       | https://preview.saasyland.com |
| Push su `main`                                 | `production` | `Production`    | https://saasyland.com         |

`deploy-reusable.yml` assegna a ogni ambiente GitHub il suo URL, e `src/__test__/workflows.test.ts` fallisce quando uno differisce dal suo host in `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Le pull request provenienti da fork e da Dependabot vengono validate ma non distribuite. La preview è condivisa: ogni deploy sostituisce il precedente e usa lo stesso database D1, lo stesso namespace KV e gli stessi bucket R2 di preview.

`deploy-reusable.yml` verifica la presenza dei secret `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID`, esegue `scripts/verify-bindings.ts`, compila con i valori fittizi di `.env.test`, rimuove il file generato `dist/server/.dev.vars`, applica `db:migrate:<target>` ed esegue `vp exec wrangler deploy --config dist/server/wrangler.json`. Non esegue `scripts/verify-deployment.ts`, il controllo del sito online degli script `deploy:<target>`, perché la protezione dai bot di Cloudflare risponde 403 alle richieste dei runner di CI. Non esegue nemmeno `scripts/run-deploy-checks.ts`, quindi la CI non esegue nessuno dei controlli di deploy che le aree dichiarano in `DEPLOY_CHECKS`: nella CI non c'è alcun `.env.<target>` e gli ambienti GitHub contengono solo le credenziali di Cloudflare. Oggi sono `auth:verify` dell'area di autenticazione e `polar:verify` dell'area Polar; esegui in locale `bun run auth:verify:<target>` dopo aver modificato un client OAuth e `bun run polar:verify:<target>` dopo ogni modifica in Polar ([Configurazione di Polar](/docs/getting-started/polar-setup)). Non viene caricato alcun file di secret: il Worker mantiene i secret di runtime già impostati in Cloudflare. I deploy verso la stessa destinazione si mettono in coda invece di annullarsi a vicenda. Un nuovo commit su una pull request annulla il run di `ci.yml` del commit precedente, che nessuno unirà, mentre i run di `deploy.yml` ed `e2e-full.yml` su `main` si mettono in coda e non si annullano mai a vicenda (`concurrency` con `queue: max`), così ogni push su `main` viene testato e distribuito.

Dependabot aggiorna le GitHub Actions ogni settimana.

## Release e tag [#releases-and-tags]

Il sito viene distribuito in modo continuo, quindi le sue versioni sono date e non versioni semantiche. Quando un deploy di produzione va a buon fine, il job `release` di `deploy.yml` assegna al commit distribuito il tag `vYYYY.MM.DD` con la data UTC e pubblica una GitHub Release. Un secondo deploy di produzione nello stesso giorno riceve il tag `vYYYY.MM.DD.2`, il successivo `.3` e così via. I deploy di preview non ricevono mai un tag. Il job `release` è l'unico con `contents: write`.

Le note di rilascio sono le voci del [changelog](/docs/project/changelog) che la release ha rilasciato, quelle arrivate su `main` dal tag di release precedente, ciascuna chiusa da `(#<number>)`, che GitHub collega alla sua pull request, così ogni modifica è descritta in un solo posto; se una release non ne ha rilasciata nessuna, le sue note rimandano al changelog. `scripts/publish-release.ts` prende le note da `src/lib/release.ts` ed esegue `gh release create` con il tag scelto dal deploy. Una nuova esecuzione mantiene il tag che il commit ha già e salta una release che esiste già.

Il job del deploy in produzione sceglie quel tag prima della build: `scripts/choose-release-tag.ts` applica `releaseTag` di `src/lib/release.ts` ai tag del checkout, la build riceve il tag come `RELEASE_TAG` e il job lo passa al job `release` come output `release-tag`, così il deploy e la sua release condividono un solo tag. Con esso il [changelog](/docs/project/changelog) collega ogni voce alla release che l'ha rilasciata per prima: il tag di release più vecchio il cui commit contiene il commit squash della voce nella cronologia dei primi genitori di `main`, che la build legge insieme alle date con un solo `git log`, oppure il tag del deploy stesso per le voci che porta. Il job `release` legge il changelog allo stesso modo, con il tag che pubblica, quindi le note di una release sono esattamente le voci che la pagina collega a quella release. Le voci unite prima del primo tag di release non rimandano a nessuna release, e nelle build locali, di anteprima e delle pull request lo stesso vale per le voci che nessun deploy ha ancora rilasciato. Due deploy in produzione non possono scegliere lo stesso tag: `deploy.yml` esegue un solo run del workflow alla volta (`concurrency` con `queue: max`), quindi il job `release` del run precedente ha creato il suo tag prima che il deploy successivo faccia il checkout del repository.

Per riportare la produzione a una release, annulla in una pull request tutto ciò che viene dopo il suo tag:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Il merge distribuisce il codice del tag dopo i soliti controlli e gli assegna il tag di una nuova release. Le migrazioni D1 non vengono annullate, quindi il codice precedente gira sullo schema più recente. Ogni modifica dello schema deve funzionare con l'applicazione distribuita prima di essa, il che rende l'operazione sicura per la release precedente; leggi le migrazioni intermedie prima di tornare più indietro.
