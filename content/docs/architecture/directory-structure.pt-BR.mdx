## Regras de organização

- **Arquivos e pastas usam kebab-case.** Os testes ficam em uma pasta irmã `__test__`.
- **Rotas apenas compõem.** Um arquivo de rota define o componente de página ou de layout, `NAMESPACE` ou `NAMESPACES`, o loader e o `head`. Ele não contém widgets, diálogos nem definições de colunas.
- **Módulos são tabelas do banco de dados.** Crie `src/modules/<name>` apenas para uma tabela real. Uma server function que não trabalha com uma tabela vai para `src/lib` (por exemplo, `src/lib/github.ts`) ou, se uma única rota a usa, para o arquivo dessa rota.
- **Componentes compartilhados ficam no nível plano.** Um componente usado em várias partes do site é um único arquivo diretamente em `presentation/components/custom`.
- **Uma pasta para cada parte do site.** Componentes usados por uma única parte do site ficam em `admin/`, `app/`, `auth/`, `billing/`, `blog/`, `courses/`, `landing-page/` ou `settings/`, que contém os cards de conta que `/app/settings` e `/admin/settings` compartilham. As páginas do admin têm pasta própria, como `admin/users/`. A landing page se divide em `sections/` (um arquivo por seção da página) e `components/` (partes compartilhadas entre as seções).
- **Um widget, diálogo, formulário ou conjunto de colunas por arquivo.** Não divida um componente em um wrapper e um arquivo `-content`.
- **Sem pastas auxiliares aninhadas.** Pastas de componentes nunca contêm subpastas `components/`, `constants/`, `hooks/`, `lib/` ou `types/`, e nenhum arquivo auxiliar `.ts` fica ao lado de um componente. Uma constante usada por um único componente permanece no arquivo desse componente.
- **Constantes compartilhadas vão para `src/data`.** A pasta guarda só constantes e listas literais, sem funções, sem schemas e sem importar Zod; `src/__test__/source-layout.test.ts` falha quando um arquivo dela exporta uma função ou importa Zod. Exemplos: `MARKETING_SECTION_IDS` e as opções da CLI. O que a plataforma executa fica listado onde é executado: os handlers de requisições e as reescritas de documentos do Worker em `src/server.ts`, os plugins do Vite em `vite.config.ts` (veja [O que o Worker e o build executam](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)).
- **Todo caminho vai para `src/routes.ts`.** Todo ambiente de execução carrega esse arquivo: o navegador, o Worker, os scripts do Bun, o Playwright, o `vite.config.ts` e o projeto do Remotion. Por isso ele declara os caminhos e não importa nada (veja [Caminhos e navegação](/docs/conventions/routes#paths-and-navigation)).
- **Todo menu vai para `src/data/navigation.ts`.** Os sete menus são listas literais nesse arquivo, que importa apenas `lucide-react`, `~/src/routes` e `~/src/data/navigation.constants`, porque o projeto do Remotion lê o menu do admin tendo instalados só os pacotes do próprio Remotion.
- **As verificações do site no ar vão para `src/lib/deployment.ts`**, como `LIVE_SITE_CHECKS`, ao lado de `verifyDeployment`, que as requisita.
- **As declarações de permissão vão para `APP_STATEMENTS`, em `src/integrations/better-auth/auth.access.ts`**, para que uma pessoa revise cada mudança nelas, assim como revisa quem pode abrir as aulas pagas em `src/modules/lesson/lesson.access.ts` e a qual código chega cada evento de webhook da Polar em `src/integrations/polar/polar.webhooks.ts`.
- **Arquivos gerados não são editados à mão.** O plugin do router escreve `src/routeTree.gen.ts`, `bun run cf-typegen` escreve `src/types/worker-configuration.d.ts`, e `bun run content` e `bun run generate:cn` escrevem `.source/`.
