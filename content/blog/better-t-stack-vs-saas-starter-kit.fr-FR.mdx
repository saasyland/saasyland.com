## Commencez ici : il est très bon et vous devriez probablement l'utiliser

[Better-T-Stack](https://better-t-stack.dev/) est un CLI qui échafaude des projets TypeScript typés de bout en bout. Il est sous licence MIT, son README promet « libre et open source : pour toujours », il compte **5 636 étoiles GitHub** et il est téléchargé environ **2 476 fois par semaine** depuis npm.

La matrice d'options est la meilleure de l'écosystème, et de loin :

| Couche                              | Ce qu'il propose                                                                                                                 |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Frontend                            | React avec TanStack Router, React Router ou TanStack Start, Next.js, Nuxt, Svelte, Solid, Astro, React Native, ou aucun          |
| Backend                             | Hono, Express, Fastify, Elysia, fullstack auto-hébergé, Convex, ou aucun                                                         |
| API                                 | tRPC, oRPC, ou aucune                                                                                                            |
| Runtime                             | Bun, Node.js, Cloudflare Workers                                                                                                 |
| Base de données                     | SQLite, PostgreSQL, MySQL, MongoDB, ou aucune                                                                                    |
| ORM                                 | Drizzle, Prisma, Mongoose, ou aucun                                                                                              |
| Auth                                | Better Auth ou Clerk, en option                                                                                                  |
| Configuration de la base de données | Turso, Neon, Supabase, Prisma Postgres, MongoDB Atlas, Cloudflare D1, Docker                                                     |
| Modules complémentaires             | Turborepo, Nx, PWA, Tauri, Electrobun, Biome, Lefthook, Husky, Starlight, Fumadocs, Ultracite, Oxlint, MCP, OpenTUI, WXT, Skills |
| Exemples                            | Todo, AI                                                                                                                         |

Faire en sorte qu'autant de combinaisons produisent un projet qui passe réellement la vérification de types et s'exécute relève d'une ingénierie vraiment difficile. Il est aussi distribué sous forme de plugin Claude Code avec un serveur MCP, si bien qu'un agent peut planifier et générer une pile valide au lieu d'écrire le boilerplate à la main, ce qui est un travail réfléchi.

**Si vous construisez un prototype, un outil interne, un projet de portfolio, une application qui n'est pas un SaaS, ou tout projet où vous voulez apprendre la plomberie, arrêtez de lire et lancez `bun create better-t-stack@latest`.** Il est gratuit, il est excellent, et rien de ce qui suit ne plaide contre lui.

Le reste s'adresse à un lecteur précis : la personne qui essaie de décider si le CLI gratuit suffit pour un SaaS qu'elle compte faire payer.

## Une pile n'est pas un produit

Le README de Better-T-Stack énonce sa philosophie en quatre lignes, et la deuxième résume toute la comparaison :

> Composez votre propre pile : vous ne choisissez que les parties dont vous avez besoin, rien de plus.
> **Modèles minimaux : des squelettes dépouillés, sans aucun superflu.**
> Dépendances à jour : toujours les versions actuelles et stables par défaut.
> Libre et open source : pour toujours.

Ce n'est pas une limite que l'on cache. C'est la conception, énoncée clairement, et le projet tient exactement ce qu'il promet. La preuve se trouve dans la dernière ligne du tableau ci-dessus : les exemples fournis sont **Todo** et **AI**. Une liste de tâches et un chat. Ce sont les démonstrations canoniques que le câblage fonctionne, et ce sont les bons exemples pour un outil dont le travail est le câblage.

Donc, le cadrage honnête n'est pas « un outil gratuit auquel il manque des fonctionnalités ». C'est :

**Better-T-Stack échafaude une pile. Un kit de démarrage SaaS échafaude un produit.**

Les deux sont des outils d'échafaudage. Ils s'arrêtent à des lignes différentes. Better-T-Stack s'arrête quand le frontend peut appeler le backend et que le backend peut atteindre la base de données, avec un typage sûr, en vous laissant le choix entre neuf frontends et six backends. C'est un point d'arrêt défendable, et c'est là que la plupart des outils d'échafaudage devraient s'arrêter.

Un kit de démarrage SaaS s'arrête ailleurs : quand une personne peut s'inscrire, rejoindre une organisation, se voir attribuer un rôle, être facturée chaque mois, recevoir un e-mail à ce sujet, et être consultée par vous dans un panneau d'administration quand elle vous écrit, perdue. Tout ce qui se trouve entre ces deux lignes constitue la facture.

Voici ce qui se trouve entre `bun create better-t-stack@latest` et un produit que vous pouvez faire payer. Les estimations supposent un développeur compétent qui construit chaque élément au niveau qu'il présenterait à une entreprise cliente, et elles excluent le temps passé à décider comment le faire, qui, pour plusieurs lignes, dépasse celui de l'implémentation.

| Rôles et permissions               |      Non       | Une couche de règles d'accès que chaque requête et chaque route consulte, plus l'interface qui la reflète                                                    | 20 à 30       |
| Isolation multi-locataire          |      Non       | Appliquée au niveau des requêtes plutôt qu'à celui des vues, et testée contre un deuxième locataire                                                          | 15 à 25       |
| Facturation                        |      Non       | Pas le checkout. Prorata, montées et descentes de gamme, relances de paiement, factures, webhooks idempotents, rapprochement                                 | 25 à 40       |

À 150 $ de l'heure, cela représente **42 000 $ à 69 750 $**. Appliquez votre propre taux et le chiffre change, mais pas la conclusion. Face à un prix unique de 249 $, la comparaison est sans appel pour quiconque dont le temps a un prix.

Mais les heures sont l'argument ennuyeux, et je préfère avancer l'argument intéressant.

## La partie qui ne se compte pas en heures

Regardez quatre lignes de ce tableau : **isolation multi-locataire, rôles et permissions, idempotence des webhooks et révocation de sessions.**

Elles partagent une propriété qu'aucune des autres lignes n'a. **La mauvaise implémentation passe la revue, fonctionne en développement et fait une démo parfaite.**

Un filtre de locataire appliqué dans la couche de vue au lieu de la couche de requête fonctionne parfaitement avec un seul locataire. Il fonctionne parfaitement dans vos tests, parce que vos fixtures n'ont qu'un locataire. Il échoue le jour où les données de votre deuxième client apparaissent dans le tableau de bord de votre premier client, et ce n'est pas un rapport de bug, c'est un appel téléphonique.

Un gestionnaire de webhook sans clé d'idempotence fonctionne à chaque fois que vous le testez, parce que vous n'envoyez jamais deux fois le même événement. Stripe, si, lors des nouvelles tentatives, et quelqu'un se retrouve alors facturé deux fois ou se voit attribuer une offre deux fois.

Une vérification d'autorisation qui lit le rôle depuis la session plutôt que de le relire depuis la base de données fonctionne jusqu'au jour où quelqu'un est rétrogradé et conserve son ancienne session.

Ce ne sont pas des problèmes difficiles. Ce sont des problèmes où **l'erreur est invisible jusqu'à ce qu'elle coûte cher**, ce qui est un profil de risque complètement différent de « cela prend 40 heures ». Vous ne pouvez pas vous en sortir en achetant plus d'heures, parce que vous ne savez pas que vous en avez besoin. Vous les évitez en partant d'une fondation où quelqu'un a déjà commis l'erreur et l'a corrigée, et où un test existe désormais qui échoue si elle revient.

C'est là, plutôt que le nombre d'heures, le but d'un kit de démarrage payé.

## Ce que le côté payé ressemble concrètement

Pour être spécifique plutôt que abstrait, voici ce que signifie "déjà résolu" dans cette base de code, avec les nombres lus hors de l'exécution du test plutôt que tapé dans un fichier marketing.

**Un contrôle de couverture plutôt qu'un badge de couverture.** <RepositoryCount fact="testFiles" /> fichiers de tests et quatre seuils dans la configuration :

```ts
coverage: {
  thresholds: { branches: 100, functions: 100, lines: 100, statements: 100 },
}
```

Les branches d'erreur de la section précédente sont exactement ce qu'un contrôle de couverture des branches à 100 vous oblige à tester. C'est le mécanisme, pas le nombre.

**Des responsabilités claires et des vérifications typées.** L'application de référence publique regroupe les opérations par fonctionnalité et configure Vite+ pour vérifier à la fois les règles de lint et les types :

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

Les fichiers de routes coordonnent la navigation ; les cas d'usage des fonctionnalités vivent dans `src/modules` ; la configuration des fournisseurs vit dans `src/integrations` ; l'interface vit dans `src/presentation`. Les modules réservés au serveur gardent les bindings du Worker hors du client. La répartition des responsabilités au sein de ces dossiers est une convention à vérifier en revue, pas une restriction d'import imposée par cet extrait.

**Rigueur sans échappatoire.** `strict`, plus `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` et `verbatimModuleSyntax`. `typescript/no-explicit-any` est une erreur, et les catégories de lint sont configurées en erreur, si bien que la vérification se termine par un code de sortie en échec.

**Des fonctionnalités optionnelles, pas un modèle figé.** Le [configurateur](/#cli) pose <RepositoryCount fact="cliQuestions" /> questions et propose quatre extras : une boutique avec des produits d'exemple, un cours par abonnement, un constructeur visuel de pages et un éditeur visuel d'articles. En activer un ajoute un module. Le laisser désactivé signifie que ce code n'existe pas dans votre dépôt.

Rien de tout cela n'est une critique de Better-T-Stack. C'est une description de l'endroit où les deux produits s'arrêtent.

## Quand Better-T-Stack est la bonne réponse

Déclaré correctement, car une comparaison qui recommande toujours l'option payée est une publicité plutôt qu'une comparaison.

**Utiliser Better-T-Stack si :**

- Vous faites du prototypage, et la chose peut ne plus exister dans un mois.
- Vous apprenez, et la plomberie est le but. Construire l'authentification une fois est une formation réellement précieuse, et personne ne devrait en être dissuadé.
- Votre produit n'est pas un SaaS. Pas d'organisations, pas d'abonnements, pas d'administration. Un outil, un jeu, un tableau de bord interne, un site client.
- Vous avez déjà une bibliothèque interne pour les trois quarts ennuyeux, ce que beaucoup d'agences et d'équipes expérimentées font.
- Votre pile est en dehors de ce que n'importe quel kit payant offre. Nuxt, Svelte, Solid, Astro, React Native, Convex, tRPC. Better-T-Stack couvre tous ceux-là et aucun kit de démarrage payant ne couvre la plupart d'entre eux.
- Votre budget est vraiment nul. C'est une contrainte légitime et il n'y a aucune honte à cela. Better-T-Stack est une meilleure option gratuite que l'offre gratuite de n'importe quel produit payant.

**Envisager de payer si :**

- Vous construisez un seul produit que vous comptez facturer à des entreprises, avec des sièges, des rôles, des factures et un questionnaire de sécurité dans votre avenir.
- Vous avez déjà construit les organisations et la facturation une fois et vous vous souvenez exactement du temps qu'ont pris les parties ennuyeuses.
- Vous voulez un contrôle de tests que vous n'avez pas eu à écrire, parce qu'écrire une suite de couverture à partir de zéro est la tâche à laquelle personne n'arrive jamais.
- Vous voulez que les limites architecturales soient appliquées plutôt que prévues.
- Votre temps a un prix et 280 à 465 heures de ce temps coûtent plus de quelques centaines de dollars.

## Ils ne sont pas vraiment concurrents

La chose la plus utile que je puisse vous dire est que ce n'est pas une course à deux chevaux.

Better-T-Stack est un outil d'échafaudage pour _n'importe quel_ projet TypeScript, avec neuf frontends et six backends. Un kit de démarrage SaaS est une fondation pour _un seul type_ d'activité. Le recouvrement se limite aux dix minutes du début, pendant lesquelles les deux écrivent un projet. Ensuite, ils font des travaux différents.

L'erreur à éviter n'est pas de « choisir le gratuit ». C'est de choisir l'un ou l'autre sans savoir laquelle des deux tâches vous deviez accomplir. Un fondateur qui échafaude une belle pile typée puis passe six mois à construire les organisations et la facturation n'a pas économisé d'argent. Il a payé la facture dans une monnaie qui n'apparaît sur aucune facture.

<Accordion title={"Est-ce que Better-T-Stack inclut l'authentification ?"}>

En option, comme étape de câblage : il peut configurer Better Auth ou Clerk. Vous obtenez ainsi une connexion et une déconnexion correctement configurées. Vous n'obtenez pas les organisations, les invitations, le décompte des sièges, les actions réservées à certains rôles, la double authentification obligatoire, l'emprunt d'identité pour le support ni la révocation de sessions, qui sont autant de fonctionnalités distinctes à construire au-dessus de la bibliothèque.

</Accordion>

<Accordion title={"Lequel est le meilleur pour les agents de codage IA ?"}>

Les deux sont de bons points de départ, pour des raisons différentes. Un squelette minimal donne à un agent un contexte réduit et rien qui puisse l'embrouiller. Une fondation plus large avec des frontières imposées lui donne des exemples fonctionnels et un build qui échoue quand il dérive. La pire option est celle qu'aucun des deux ne propose : une grande base de code dont les règles n'existent que dans un readme.

</Accordion>

<Accordion title={"Combien d'heures un kit de démarrage payant fait-il réellement gagner ?"}>

Pour un SaaS multi-locataire avec facturation, rôles et administration, la fourchette détaillée dans cet article est de 280 à 465 heures de travail compétent. Pour un outil mono-utilisateur avec un seul checkout Stripe, on est plus proche de 20. Le chiffre honnête dépend entièrement de ce que vous construisez, c'est pourquoi le tableau est détaillé poste par poste plutôt que totalisé pour vous.

</Accordion>

<Accordion title={"Devrais-je simplement le construire moi-même ?"}>

Construisez-le vous-même quand la plomberie est ce que vous voulez apprendre, quand votre produit est assez atypique pour que les hypothèses d'un kit de démarrage vous gênent, ou quand votre temps n'a réellement aucun coût d'opportunité. Achetez quand vous l'avez déjà construit une fois et que vous vous souvenez exactement du temps qu'ont pris les trois quarts ennuyeux.

</Accordion>

</Accordions>
