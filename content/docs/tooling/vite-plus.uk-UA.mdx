Vite+ (`vite-plus`, команда `vp`) об'єднує Vite, Vitest, oxlint і oxfmt за одним CLI, а `vite.config.ts` налаштовує їх усі. `package.json` перевизначає `vite` на `@voidzero-dev/vite-plus-core` і фіксує `vitest` на версії 5.1.0. `vite-plus` також закріплено на точній версії; оновлюйте всі три разом через `vp migrate`, а не `bun update`. Скрипти пакета викликають `vp`; поза ними використовуйте глобальний Vite+ CLI або `bunx vp`.

| Команда           | Використовується в                                |
| ----------------- | ------------------------------------------------- |
| `vp dev`          | `dev`                                             |
| `vp build --mode` | `build:preview`, `build:production`, `build:test` |
| `vp preview`      | `start`, `start:test`                             |
| `vp test`         | `test` і скриптах Vitest `test:*`                 |
| `vp lint`         | `lint`                                            |
| `vp fmt`          | `format`, `format:check`                          |
| `vp check`        | `check`, `check:fix`                              |
| `vp staged`       | `check:pre-commit`                                |
| `vp config`       | `prepare`, який встановлює Git-хуки               |

## Конфігурація

`vite.config.ts` перелічує свої плагіни в `VITE_PLUGINS` і завантажує їх ліниво, кожен запис імпортує свій пакет усередині `load`; плагіни постачальника беруться з `src/integrations/<vendor>/<vendor>.vite.ts` (див. [Що виконують Worker і збірка](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)). Під Vitest завантажуються лише записи з позначкою `vitest`, тобто `contentIndexes()`, `repositoryFacts()` і `@vitejs/plugin-react`; в інших випадках набір такий:

- `@cloudflare/vite-plugin`: запускає Worker у середовищі SSR і зберігає локальний стан (у `.wrangler/test` для режиму `test`, в інших випадках у `.wrangler/state`), з `remoteBindings: false`, тож dev-сервер чи збірка жодного середовища не підключається до віддаленої прив'язки.
- `fumadocs-mdx`: компілює колекції документації та блогу.
- `saasyland:fumadocs-bundled`: залишає `fumadocs-core` і `@fumadocs/base-ui` у серверному бандлі (`resolve.noExternal`). Він і `fumadocs-mdx` походять із `fumadocsVitePlugins` (`src/integrations/fumadocs/fumadocs.vite.ts`).
- `contentIndexes` (`scripts/content-indexes.ts`): надає `virtual:content-indexes` і `virtual:docs-search` — індекси документації, блогу й пошуку, які `fumadocs.indexes.ts` будує з `content/docs` і `content/blog`; див. [Fumadocs](/docs/integrations/fumadocs#content-indexes).
- `repositoryFacts` (`scripts/repository-facts.ts`): надає модуль `virtual:repository-facts`: кількості, версії та налаштування інструментів, які виводять головна сторінка й документація, прочитані з репозиторію під час збірки; див. [Переклади та контент](/docs/conventions/translations).
- `unused-primitives` (`scripts/unused-primitives.ts`): перед Tailwind пропускає класи кожного примітиву shadcn, який не імпортує жоден вихідний код застосунку; див. [Компоненти shadcn](/docs/ui/shadcn-components).
- `@tailwindcss/vite`: Tailwind CSS 4.
- `tanstackStart`: маршрутизація, розділення коду та попередній рендеринг публічних сторінок, відфільтрований `shouldPrerender` (`src/lib/prerender.ts`).
- `@vitejs/plugin-react`.
- `saasyland:zod-config-chunk` (`src/integrations/zod/zod.vite.ts`): у клієнтській збірці кладе `src/integrations/zod/zod.config.ts` у власний чанк zod, тож zod працює в режимі `jitless` ще до того, як будь-який чанк створить схему, і під Content Security Policy ніколи не перевіряє, чи доступний `eval`; див. [Безпека та посилення захисту](/docs/features/security).
- `deployedWorker` (`scripts/deployed-worker.ts`): після попереднього рендерингу заново збирає Worker без скомпільованих сторінок документації та блогу і без перекладів лендингу та юридичних сторінок; див. [Cloudflare Workers](/docs/integrations/cloudflare-workers).
- `saasyland:polar-sdk-optional-peers`: позначає як зовнішні не встановлені необов’язкові peer-залежності `@polar-sh/sdk` (`build.rolldownOptions.external`); див. [Залежності](/docs/conventions/dependencies).

Dev-сервер слухає `localhost:3000` і завершується з помилкою, якщо порт зайнятий. `resolve.tsconfigPaths` надає псевдонім імпорту `~/`. Той самий файл містить секції `fmt`, `lint`, `staged` і `test`; див. [Лінтинг і форматування](/docs/tooling/lint-format) і [Тестування](/docs/tooling/testing).

`vp preview`, який запускають `start`, `start:test` і пререндеринг, слухає `127.0.0.1:3000`, адресу `LOCAL_SERVER` з `src/data/local-server.ts`, і Playwright відкриває цю адресу; пререндеринг використовує ту саму адресу з вільним портом. З `localhost` сервер слухав би лише першу адресу, до якої Node розв'язує це ім'я, `::1`, а кожен клієнт пробував би спершу `::1`, потім `127.0.0.1` і давав би кожній адресі лише короткий час на відповідь: на завантаженій машині цей час спливає раніше, ніж клієнт помічає з'єднання, клієнт полишає `::1`, на `127.0.0.1` нічого не знаходить, і пререндеринг зупиняється з `ETIMEDOUT ::1` і `ECONNREFUSED 127.0.0.1`.

`polarVitePlugins` у `src/integrations/polar/polar.vite.ts` повертає плагін, хук `config` якого перелічує в `build.rolldownOptions.external` необов'язкові peer-залежності `@polar-sh/sdk` (OpenTelemetry та `ioredis`). Їх не встановлено, а модуль, який їх імпортує, вилучається з Worker завдяки tree-shaking.

## Git-хуки

`bun install` запускає `prepare`, який викликає `vp config --no-agent`, щоб встановити диспетчер хуків для `.vite-hooks/`, а потім `scripts/verify-git-hooks.ts`, який завершує встановлення помилкою, якщо Git не запускав би цей диспетчер. `pre-commit` запускає `bun run check:pre-commit`, `prepare-commit-msg` запускає `scripts/commit-msg.ts`, а `commit-msg` запускає `scripts/verify-commit-msg.ts` (див. [Conventional commits](/docs/tooling/conventional-commits)), а `post-checkout` запускає `vp hooks enable` у checkout, де ще немає диспетчера, наприклад у робочому дереві, яке щойно створила команда `git worktree add`. `post-merge`, `post-checkout` і `post-rewrite` запускають `bun install --frozen-lockfile`, коли змінився `bun.lock`, тож pull, rebase чи перемикання гілки ніколи не залишають `node_modules` застарілим. `vp hooks status` показує, чи активні хуки в клоні, а [Git і pull request](/docs/conventions/git-workflow#hooks-in-every-worktree) пояснює, чому кожному робочому дереву потрібен власний диспетчер.

Надавайте перевагу скриптам пакета; викликайте `vp` напряму для цільових запусків, наприклад для форматування чи лінтингу конкретних шляхів.
