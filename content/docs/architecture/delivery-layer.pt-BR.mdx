## Arquivos de rota

As rotas são arquivos planos em `src/routes`. Os pontos viram segmentos de caminho:

| Arquivo                           | URL                | Observações                                     |
| --------------------------------- | ------------------ | ----------------------------------------------- |
| `__root.tsx`                      | todas as páginas   | Shell do documento e namespaces raiz            |
| `_site.tsx`                       | nenhuma            | Layout sem caminho com o cabeçalho do site      |
| `_site._marketing.tsx`            | nenhuma            | Layout sem caminho para as páginas de marketing |
| `_site._marketing.terms.tsx`      | `/terms`           | Página dentro do layout de marketing            |
| `admin.tsx`                       | `/admin`           | Layout com o guard `requireAdmin`               |
| `admin.users.all.tsx`             | `/admin/users/all` | Página dentro do layout do admin                |
| `_site._marketing.blog.index.tsx` | `/blog`            | Página índice do layout `blog`                  |
| `_site.docs.$.tsx`                | `/docs/*`          | Rota splat para as páginas da documentação      |
| `api/auth.$.ts`                   | `/api/auth/*`      | Handler HTTP, sem componente                    |

Os IDs em `createFileRoute("…")` são literais de string mantidos pelo gerador de rotas, que também escreve `src/routeTree.gen.ts`. Arquivos em pastas `__test__` são ignorados. Toda URL tem uma constante em `ROUTES` (`src/routes.ts`), e os links usam `<Link to={ROUTES.X}>`.

## Rotas de página

Uma rota de página define um componente `<Name>Page`, uma constante `NAMESPACE` logo acima de `export const Route` e um loader que carrega os metadados da página e o namespace em um único `Promise.all`:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.TERMS),
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Dados extras entram no mesmo `Promise.all`, por exemplo `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` em `admin.users.all.tsx`. `pageHead`, de `src/lib/seo.ts`, monta as tags de título, descrição, canonical, `hreflang`, Open Graph e imagem social a partir do `metadata` do loader; veja [Busca e prévias em redes sociais](/docs/features/seo).

## Rotas de layout

Uma rota de layout define um componente `<Name>Layout`, um array `NAMESPACES` e, nas áreas protegidas, um guard em `beforeLoad`. Os seus `NAMESPACES` nomeiam todos os namespaces de que as suas páginas precisam, inclusive os de outras funcionalidades, e um parâmetro de busca é validado pelas páginas que o leem, como as páginas de licença `/app` e `/app/license` fazem com `tier`:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "pages.license", "timezones"] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Os guards `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn`, `redirectIfVerified` e `redirectAfterAuth` vêm de `src/integrations/better-auth/auth.routes.ts`.

## Esqueletos de carregamento

A maioria das navegações termina antes que qualquer UI de carregamento apareça: os links pré-carregam a sua rota no hover e no toque, e as páginas públicas são pré-renderizadas. Quando uma navegação não terminou depois de `defaultPendingMs`, <RepositoryFact name="navigationPendingMs" unit="millisecond" />, o router mostra o esqueleto da rota e, como `defaultPendingMinMs` é <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, o remove assim que a página fica pronta. Isso acontece com uma conexão lenta ou na primeira requisição a um novo isolate do Worker (veja [Desempenho](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

Não há componente de carregamento padrão. Cada rota de layout e de página define o seu próprio `pendingComponent`. As páginas da documentação são desenhadas dentro do layout da documentação: `_site.docs.index.tsx` e `_site.docs.$.tsx` mostram `DocsIndexPending` e `DocsPagePending`, o artigo e o seu sumário ao lado da barra lateral, e o layout `docs` mostra `DocsPending` quando alguém entra na documentação vindo de outro lugar. Cada esqueleto reproduz a página que substitui:

- **Esqueletos de página**, como `SignInPending` e `LegalPending`, ficam no arquivo de esqueletos da funcionalidade e marcam o seu elemento raiz com `aria-busy="true"`. Os arquivos são `custom/auth/auth-pending.tsx`, os arquivos de administração em `custom/admin/` (`admin-pending.tsx` para o layout, um arquivo `<feature>-pending.tsx` por funcionalidade, como `products-pending.tsx`, e blocos compartilhados em `pending-blocks.tsx`), os arquivos do app do cliente em `custom/app/` (`app-pending.tsx` para o layout, `auth-pending.tsx` e `license-pending.tsx`, e o cabeçalho de página que compartilham em `pending-blocks.tsx`), os arquivos do layout público na raiz de `custom/` (`marketing-pending.tsx` para o layout, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` e `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` e `custom/docs-pending.tsx`.
- **Esqueletos de layout**, como `AuthPending` e `MarketingPending`, renderizam a moldura do layout e, dentro dela, o `pendingComponent` da primeira rota abaixo do layout que corresponde ao caminho atual e define um, que `usePagePending` em `src/hooks/use-page-pending.ts` lê da árvore de rotas. Por isso, entrar em uma área vindo de outro lugar mostra a página certa, e um esqueleto de layout um nível abaixo, como `AdminUsersPending`, faz o mesmo com as suas próprias páginas. Os elementos da moldura que não precisam de dados, como `Wordmark` e `PageFrame`, são renderizados de verdade, e o cabeçalho do site continua na tela, porque o layout `_site`, que o renderiza, não tem loader pelo qual esperar.
- **Placeholders de texto** são barras `Skeleton` com o token tipográfico do elemento real mais `h-lh scale-y-70`, de modo que cada barra preenche exatamente uma caixa de linha. Os blocos usam as alturas e os raios reais. As listas tiram o seu comprimento das mesmas constantes da UI, como `OAUTH_PROVIDERS` e `AUTH_ASSURANCES` em `src/data/auth.ts`.

Ao adicionar uma página, adicione o esqueleto dela ao arquivo de esqueletos da funcionalidade e defina-o como `pendingComponent` da rota; os esqueletos de layout o encontram ali.

## Outros aspectos das rotas

- **Search params** são processados por `validateSearch` na rota, por exemplo o parâmetro `tab` de `/app/settings`. O schema é um `zod.object` montado com os helpers de `src/lib/search-params.ts`: `searchText()` e `searchFlag()` resultam em `undefined` para um valor ausente, vazio ou malformado, e `searchChoice(choices, fallback)` resulta no fallback. `searchParam(schema)` resulta em `undefined`, a menos que o valor siga outro schema do zod, como o token da newsletter.
- **Server functions de uma única rota** podem ser definidas no arquivo da rota com `createServerFn`.
- **Conteúdo gerado no build**: os loaders da documentação, do blog e da landing leem os índices de conteúdo de `virtual:content-indexes`, arquivos em `/assets/`, então não precisam de nenhuma server function e rodam no navegador em uma navegação no cliente (veja [Fumadocs](/docs/integrations/fumadocs#content-indexes)).
- **Endpoints HTTP** ficam em `src/routes/api`. Veja [Handlers HTTP do TanStack Start](/docs/architecture/api-layer).

## Router

`src/router.tsx` exporta `getRouter`, que cria um novo `QueryClient` e um novo router a cada requisição. Ele configura:

- os componentes padrão de erro e de página não encontrada, vindos de `presentation/components/custom`, e nenhum componente de carregamento padrão (veja [Esqueletos de carregamento](#esqueletos-de-carregamento))
- pré-carregamento por intenção e um `defaultPreloadStaleTime` de <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />, de modo que é o TanStack Query, e não o roteador, que decide se uma página pré-carregada ou visitada de novo busca algo outra vez (veja [Cache e SSR](/docs/architecture/caching-and-ssr) e [Desempenho](/docs/conventions/performance#the-headers-pages-load-before-a-click))
- um `rewrite` que remove o prefixo de locale das URLs recebidas e o adiciona de volta aos links gerados
- a integração das queries com o SSR por meio de `setupRouterSsrQueryIntegration`

## Depois de um deploy [#after-a-deploy]

Cada deploy substitui os assets estáticos do Worker, e o Vite dá a cada arquivo um nome baseado no conteúdo, então uma aba aberta antes de um deploy pede chunks de rota que não existem mais. O TanStack Start coloca o componente e o loader de cada rota em chunks próprios. O TanStack Router recarrega a página quando o chunk de um componente não carrega (`lazyRouteComponent`), mas o router-core carrega o chunk de um loader com `lazyFn`, que entrega a importação que falhou à rota como erro do loader. Um clique em **Blog** numa aba assim falhava no chunk do loader do layout do blog e mostrava a página de erro.

`DefaultError`, o componente de erro padrão do router, agora se recupera disso. `isStaleBuildError`, em `src/lib/stale-build.ts`, reconhece um erro que indica que a página executa código que um deploy mais recente removeu:

- uma importação dinâmica que falhou, que `isModuleNotFoundError` do router-core reconhece no Chromium, no Firefox e no Safari;
- um arquivo que o Vite não conseguiu pré-carregar para um chunk, como a folha de estilos dele, que o Vite informa com um evento `vite:preloadError`. A rota raiz escuta esse evento enquanto a aplicação está aberta (`listenForStaleBuilds`).

Diante de um erro assim, `DefaultError` carrega como página nova o endereço para o qual o visitante navegou, com `router.navigate({ href, reloadDocument: true, replace: true })`, então o visitante chega à página em que clicou, já servida pelo novo deploy; até o navegador sair da página, o componente mostra um `main` vazio e marcado como ocupado no lugar da mensagem de erro. `claimReload` permite uma recarga dessas por destino e build. Ele grava o destino em `sessionStorage` junto com a URL do script de entrada da página, que muda a cada deploy que altera um arquivo carregado pelo navegador, porque cada chunk é alcançado a partir da entrada pelo nome baseado no conteúdo. Uma segunda falha para o mesmo destino no mesmo build mostra a página de erro, então um arquivo que realmente falta não consegue fazer a página recarregar sem parar, e o próximo deploy ganha uma recarga própria. Quando o navegador recusa o armazenamento de sessão, nada é recarregado.

O Safari cancela os arquivos que uma página ainda está carregando assim que o visitante começa a sair dela, então um chunk ou uma folha de estilo a caminho falha como se um deploy o tivesse removido. Por isso `listenForStaleBuilds` também registra quando a página recebe `beforeunload`, e `DefaultError` espera com `whenPageStays` até que um `pageshow`, `pointerdown` ou `keydown` mostre que o visitante ficou antes de carregar a página de novo. Um visitante que sai chega à página que pediu em vez de ser mandado de volta para a que deixava, e quem volta à página ou fica nela recebe o recarregamento nesse momento. `stale-build.spec.ts` segura o código da rota de uma lição, sai para a política de privacidade, cancela o código e verifica que a política de privacidade abre e que a lição não é pedida de novo.

Um pré-carregamento que falhou não consome nada. Passar o ponteiro sobre um link pré-carrega a rota dele, como o cabeçalho faz com os próprios links assim que uma página fica ociosa; se isso falhar, nenhum componente de erro aparece, e o router busca o chunk de novo quando o visitante clica. `e2e/specs/stale-build.spec.ts` ativa a economia de dados, para que o cabeçalho não carregue o blog antes, tira os chunks do blog de uma página aberta e verifica que um clique, também depois de um pré-carregamento que falhou ao passar o ponteiro, chega ao blog depois de uma recarga, e que uma página cujos chunks continuam faltando mostra a página de erro depois de duas recargas, uma de `DefaultError` e uma de `lazyRouteComponent`.
