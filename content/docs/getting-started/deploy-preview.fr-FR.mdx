---
title: "Déployer une préversion"
description: "Provisionner les ressources Cloudflare et déployer le Worker de préversion."
---

L'environnement `preview` déploie le Worker `saasyland-preview` sur `preview.saasyland.com`. Par défaut, `development` et `preview` partagent une base de données D1, un espace de noms KV et un bucket R2.

## Provisionner les ressources

```sh
bunx wrangler login
bunx wrangler d1 create saasyland_com_preview
bunx wrangler kv namespace create CACHE --env preview
bunx wrangler r2 bucket create saasyland-preview
```

Dans `wrangler.jsonc`, remplacez `database_id`, `database_name`, l'`id` KV et le `bucket_name` de `MEDIA` sous `development` et sous `preview`. Conservez les noms de binding `DB`, `CACHE` et `MEDIA` ainsi que `migrations_dir`, et adaptez les noms des Workers et les routes de domaine personnalisé à votre compte. Pour la production, créez des ressources distinctes, y compris le bucket `saasyland`, et mettez à jour le bloc `production`. Définissez `APP_DOMAIN` dans `src/presentation/branding/index.ts`. `DEPLOYED_HOSTS`, dans `src/modules/_core/constants/api.ts`, en déduit les hôtes déployés, `APP_DOMAIN` pour la production et `preview.<APP_DOMAIN>` pour la préversion, et c'est le seul endroit où le code les nomme : `appHostsForMode` le lit pour les hôtes qu'acceptent Better Auth et les liens de la newsletter, et `scripts/verify-deployment.ts` les interroge après un déploiement. En local, `appHostsForMode` accepte `localhost:3000` ou `127.0.0.1:3000` en développement, et ceux-ci plus `localhost:3020` et `127.0.0.1:3020` en test. Ne modifiez `DEPLOYED_HOSTS` que si votre hôte de préversion porte un autre nom. Les `routes` de domaine personnalisé de `wrangler.jsonc` et les URL d'environnement de `.github/workflows/deploy-reusable.yml` nomment les mêmes hôtes : gardez-les synchronisés.

## Déployer

Remplissez `.env.preview` et mettez en place la sandbox Polar comme décrit dans [Configurer Polar](/docs/getting-started/polar-setup), puis déployez :

```sh
bun run deploy:preview
```

`deploy:preview` exécute `scripts/verify-bindings.ts preview`, qui rejette les bindings manquants et les identifiants fictifs, puis `polar:verify:preview`, qui compare l'organisation Polar de `.env.preview` avec le code, puis `build:preview`, qui prérend les pages publiques et vérifie le résultat. `scripts/prepare-deploy-secrets.ts preview` écrit ensuite dans `.wrangler/secrets.preview.json` les secrets que `wrangler.jsonc` déclare pour `preview`, lus depuis `.env.preview`, et échoue si l'un d'eux est vide. `db:migrate:preview` applique les nouvelles migrations avant que `wrangler deploy` ne téléverse `dist/server/wrangler.json` avec ces secrets, et `scripts/verify-deployment.ts preview` vérifie enfin que l'hôte de préversion de `DEPLOYED_HOSTS` (https://preview.saasyland.com) répond. `verify-bindings.ts` ne vérifie pas que le bucket R2 existe, car il est lié par son nom : le déploiement échoue tant qu'il n'existe pas. `bun run db:migrations:preview` liste les migrations que la base de données de préversion n'a pas encore appliquées.

Enregistrez les callbacks OAuth pour l'hôte de préversion, comme indiqué dans [Variables d'environnement](/docs/getting-started/environment-variables).

## Déploiements automatiques

La CI déploie chaque pull request provenant d'une branche de ce dépôt sur la préversion partagée, et chaque push sur `main` en production, une fois les vérifications et les tests dans le navigateur réussis. Voir [CI/CD](/docs/tooling/ci-cd) pour les secrets GitHub requis.
