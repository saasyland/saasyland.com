## Implemented

- **Sessions**: Better Auth sessions in D1, cookie prefix `saasyland`, secure cookies outside local modes, allowed hosts per mode, and `cf-connecting-ip` as the client address. The client session never contains the token.
- **Accounts**: required email verification, sessions revoked on password reset, optional TOTP with backup codes, verification identifiers stored hashed and OAuth tokens encrypted.
- **Authorization**: `requireSignedIn` and `requireAdmin` on routes; `authorized(permission)` on server functions with the roles that `auth.access.ts` builds from the areas' access files.
- **Rate limits**: the Better Auth limiter and the `withRateLimit` middleware share the D1 `rate_limit` table. `RATE_LIMITS.SENSITIVE` allows <RepositoryFact name="sensitiveRateLimit" /> calls and `RATE_LIMITS.TOKEN` <RepositoryFact name="tokenRateLimit" /> calls per <RepositoryFact name="rateLimitWindowSeconds" unit="second" /> per client and action. Verification, password reset and newsletter confirmation emails are also limited to <RepositoryFact name="recipientEmailsPerHour" /> of each kind per address per hour (`withinRecipientRateLimit`, keyed on a SHA-256 hash of the address); over the limit the email is skipped silently. The [CLI licence API](/docs/features/cli-licence-api) counts its requests per address and per licence key in the same table.
- **Errors**: the request middleware turns failures into `AppError` codes (`src/modules/_core/constants/errors.ts`), so clients never receive raw server messages; components show them with `useErrorMessage`.
- **Webhooks and forms**: Polar webhooks are verified with `POLAR_WEBHOOK_SECRET`; a newsletter subscription (`subscribeToNewsletter`) is accepted only on the build mode's hosts from `appHostsForMode`, over HTTPS or, in development and test, HTTP (`newsletterRequestOrigin`).
- **Better Auth input**: `enforceInputPolicy` in `auth.hooks.ts` applies the form schemas to every Better Auth endpoint that accepts a password, name, email or image, so requests sent straight to `/api/auth` meet the same rules; a failing request gets `400` with `VALIDATION_ERROR`.
- **Media**: video files stay in a private R2 bucket. The Worker serves them only under `/media/` paths signed with an HMAC key derived from `AUTH_SECRET` and valid for at least <RepositoryFact name="signedMediaHours" unit="hour" />. `getVideoPlayback` issues them to callers with `video: ["read"]`; `getLessonPlayback` issues them for a published lesson once `hasLessonAccess` allows the viewer, so guests receive them for free previews, signed-in users for account lessons, Complete or Agency licence holders for paid lessons and admins for every lesson; a wrong or expired signature gets `403`.
- **CLI template bundles**: each release's bundle stays in the private `BUNDLES` bucket. The CLI licence API signs a `/bundles/` URL, valid for <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, only for an active licence and an activation of the calling machine, with an HMAC key that HKDF derives from `AUTH_SECRET` for bundles alone; a wrong or expired signature gets `403`. See [CLI licence API](/docs/features/cli-licence-api#template-bundles).
- **Headers**: every response from the Worker carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, a `Permissions-Policy` that turns off camera, microphone, geolocation and topics, and a Content Security Policy that blocks framing, `<base>` changes and plugins (`base-uri 'none'`, `frame-ancestors 'none'`, `object-src 'none'`). HTTPS responses add `Strict-Transport-Security`. They are defined once, as `SECURITY_HEADERS` and `HTTPS_SECURITY_HEADERS` in `src/modules/_core/constants/api.ts`, and `src/server.ts` sets them on every Worker response, replacing any value the response or a `public/_headers` rule already set. Files served without the Worker (`/assets/*`, `/fonts/*`, `/robots.txt`, `/llms.txt`) get the same headers from the `/*` rule in `public/_headers`, a static file the platform reads before any code runs; `src/__test__/server.test.ts` fails when that rule and the constants differ.
- **Scripts**: a page runs only the scripts it was served with. Its Content Security Policy follows Google's strict CSP: `script-src` with a nonce or with hashes, `'strict-dynamic'` so that those scripts can load the rest, such as route chunks and the Affonso pixel, and `'unsafe-inline' https:` as fallbacks that browsers with nonce and hash support ignore. A page the Worker renders gets the policy in its header: `src/server.ts` creates a nonce for every response, sends `renderedPagePolicy(nonce)` from `src/lib/content-security-policy.ts`, and passes the nonce to TanStack Start as the request context's `nonce`, which `getRouter` gives to the router, so it is on every script the router, React and `ThemeScript` render. A prerendered page is the same file for every visitor and cannot carry a nonce, so `scripts/secure-prerendered-html.ts` runs after `optimize-prerendered-html.ts` in every build: `securePrerenderedPage` in `src/lib/prerendered-policy.ts` loads the entry module from a small inline script instead of a `<script src>`, hashes every inline script, and writes the policy into a `<meta http-equiv="Content-Security-Policy">` tag right after the charset. Framing stays in the header, because browsers ignore `frame-ancestors` in a meta tag. The browser runs zod `jitless` (`src/integrations/zod/zod.config.ts`, kept in zod's own chunk), so zod never probes for `eval`. The dev server sends only the header policy, because Vite's inline scripts carry no nonce; the browser suite runs a production build and fails any spec in which a page reports a violation.

## Not implemented

- Content Security Policy directives for styles, images, media, fonts and connections, Trusted Types, and reports of violations: the policy restricts scripts, plugins, base URLs and framing.
- An audit log, including for bans, deletions and impersonation.
- Bot protection or CAPTCHA on public forms.
- An impersonation screen ([Impersonation](/docs/features/impersonation)).
