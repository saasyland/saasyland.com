## Requisição de página

1. **Canonicalização do locale.** `src/server.ts` chama `resolveLocale` para as requisições de documento `GET` e `HEAD` fora de `/api` e `/_serverFn`. Um prefixo só de idioma ou do locale padrão (`/pl/docs`, `/en-US/docs`) é redirecionado com `308` para a forma canônica (`/pl-PL/docs`, `/docs`). Quando o locale da URL difere do cookie de locale, o cookie é atualizado na resposta.
2. **Assets estáticos primeiro.** O Worker pede o caminho ao binding `ASSETS`. Páginas pré-renderizadas e arquivos estáticos são retornados sem alteração. Só quando recebe um `404` ele carrega o handler do TanStack Start com um `import()` dinâmico.
3. **Roteamento.** `getRouter` cria um novo router e um novo `QueryClient`. O `rewrite` do router remove o prefixo de locale, então `/pl-PL/docs` corresponde às rotas de `/docs`.
4. **O `beforeLoad` da raiz** pré-carrega os namespaces de tradução raiz (`common`, `components.*`, `errors*`).
5. **Guards.** Funções `beforeLoad` de layouts, como `requireAdmin`, carregam a query de sessão e redirecionam quando o acesso não é permitido.
6. **Loaders** rodam em paralelo. Cada um pré-carrega seus namespaces, os metadados da página e as queries no `QueryClient` da requisição.
7. **Renderização.** O shell raiz renderiza `<html lang dir>` e envolve o body no `TranslationsProvider`. O cache de queries é serializado no HTML para que o navegador não busque os mesmos dados de novo.
8. **Headers da resposta.** Em respostas HTML, o Worker adiciona um header `Link` de preload para a folha de estilos e as fontes do locale, define o cookie de locale quando necessário e aplica os atributos de preços regionais quando o header `cf-ipcountry` dá direito a um desconto. Em seguida, toda resposta que o Worker retorna recebe os headers de segurança (`SECURITY_HEADERS` em `src/server.ts`, mais `Strict-Transport-Security` sobre HTTPS), a menos que ela já os defina.
9. **Hidratação.** O navegador faz a hidratação com o cache serializado. As navegações seguintes executam os guards e os loaders no navegador e buscam os dados por meio de server functions.

## Chamada de server function

1. O navegador chama a server function, que o build substituiu por uma requisição RPC para `/_serverFn/…`. O Worker pula o tratamento de locale nesse caminho. A URL não tem prefixo de locale, então `getCurrentLocale()` retorna `en-US` no servidor; uma server function que precisa do locale o recebe como entrada.
2. O middleware roda na ordem declarada. `withRequest` captura os headers da requisição e normaliza os erros, `withRateLimit` contabiliza a tentativa no D1 e `authorized` carrega a sessão e verifica a permissão.
3. O validator analisa a entrada com o schema Zod do módulo.
4. O handler consulta o D1 ou chama um provedor e retorna dados simples.
5. O componente recebe os dados ou um código de `AppError`. Em caso de sucesso, ele invalida as chaves de query do módulo; em caso de falha, exibe `useErrorMessage()(error)`.

```text
GET /pl-PL/admin/users/all
  src/server.ts        resolveLocale, ASSETS lookup, TanStack Start handler
  router rewrite       /admin/users/all
  __root beforeLoad    root namespaces
  /admin beforeLoad    requireAdmin
  loaders              metadata, namespaces, queries
  SSR                  HTML with serialized query cache
  src/server.ts        Link header, locale cookie, regional pricing, security headers

POST /_serverFn/…
  withRequest → withRateLimit → authorized → validator → handler → data or AppError
```

## Requisição de mídia

`src/server.ts` verifica o caminho antes de qualquer outra coisa. Uma requisição em `/media/` vai para `serveMedia` (`src/modules/video/video.delivery.ts`), carregado com um `import()` dinâmico, e pula o tratamento de locale, a consulta a `ASSETS` e o TanStack Start. `serveMedia` verifica a assinatura e a expiração no caminho e depois responde a partir do cache do Workers ou do R2, incluindo requisições `Range`. A resposta recebe os mesmos cabeçalhos de segurança que todas as outras. Veja [Cloudflare R2](/docs/integrations/cloudflare-r2).
