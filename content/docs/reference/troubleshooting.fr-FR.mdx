## Base de données

**`no such table` dans `bun run dev`.** La base de développement locale n'a pas été migrée. Exécutez `bun run db:migrate:local`, ou `bun run db:reset:local` et `bun run db:seed:local` pour une base neuve et initialisée.

**`no such table` dans Playwright.** Les tests navigateur utilisent leur propre base locale. Exécutez `bun run db:reset:test`, ou laissez Playwright démarrer l'application, ce qui l'exécute.

**Les tables de Vitest ne sont pas à jour.** Le mock D1 applique chaque fichier SQL de `src/integrations/drizzle-orm/migrations` au démarrage. Après une modification du schéma, générez une migration avec `bun run db:generate`.

## Serveur de développement

**Le serveur de développement ne démarre pas.** Il écoute sur `localhost:3000` avec `strictPort` et échoue donc si le port est déjà occupé. Arrêtez l'autre processus.

**La connexion ou OAuth échoue.** Vérifiez `AUTH_SECRET` et les identifiants du client OAuth dans le fichier d'environnement, ainsi que l'URL de callback du fournisseur, qui doit pointer vers <RepositoryFact name="oauthCallbackPath" /> sur l'hôte que vous utilisez. Better Auth n'accepte que les hôtes configurés pour le mode de build : `localhost:3000` et `127.0.0.1:3000` en développement.

**Il manque un binding ou un secret dans les types du Worker.** Exécutez `bun run cf-typegen` après avoir modifié `wrangler.jsonc` : il type chaque binding et chaque secret de `secrets.required`. Une valeur que Wrangler ne peut pas déduire, comme une variable que seul `test` définit, va dans le `src/types/<feature>.d.ts` de la fonctionnalité.

**Les classes `text-*` personnalisées disparaissent lors de la fusion.** `cn` dépend de tables générées à partir de `src/lib/cn.config.ts`. `bun run dev`, `bun run check` et les builds les régénèrent ; exécutez `bun run generate:cn` si `.source/cn-tables.ts` est absent.

## Traductions

**`No messages/<locale>/<namespace>.json`.** Une route déclare un namespace qui n'a pas de fichier pour cette locale. Créez le fichier dans chaque locale.

**Une clé s'affiche sous la forme de son chemin, ou `check:i18n` signale une clé manquante.** La clé manque dans une locale, ou le composant la lit en dehors de la portée de son appel à `useTranslations`. Utilisez un seul `useTranslations` par composant et exécutez `bun run check:i18n`.

## Documentation

**Une page de documentation renvoie une erreur 404.** Le fichier doit s'appeler `<page>.<locale>.mdx` et figurer dans `pages` du fichier `meta.<locale>.json` du dossier. Exécutez `bun run content` pour régénérer `.source`.

**`check-content.ts` échoue.** Il compare chaque locale à en-US. `Changed code examples` signifie qu'un bloc de code diffère de celui de la version anglaise ; les blocs de code doivent être identiques. `Untranslated English paragraph` signifie qu'un paragraphe a été copié sans être traduit. `Missing <file>` signifie qu'un fichier de locale n'existe pas. `leaves out … from the English page` et `adds …, which the English page does not have` signifient qu'une traduction a perdu ou ajouté du code en ligne, un composant ou l'une de ses props, ou un lien vers une autre page ; recopiez-le tel que la page anglaise le contient. `has … table rows where the English page has …` signifie qu'un tableau a perdu ou gagné une ligne. `links to … instead of …` signifie qu'un lien interne serait redirigé ou nomme une locale ; écrivez le chemin que propose le message.

**`check-message-formats.ts` échoue.** `changed the path or command …` signifie qu'une traduction a modifié un chemin de fichier ou une commande du message anglais ; laissez-le tel quel ou passez-le en argument ICU depuis `REPOSITORY_FACTS`. `unexpected Markdown code` signifie qu'une traduction a ajouté des accents graves, qu'un message affiche tels quels. `uses “Sie” where de-DE addresses the reader as “du”` signifie qu'une traduction s'adresse au lecteur dans une forme que sa langue n'utilise pas ; réécrivez la phrase dans la [forme d'adresse](/docs/conventions/translations#one-form-of-address) de la langue. `check-content.ts` signale la même chose pour une page de documentation, un article de blog ou une entrée du changelog.

## Tests et déploiement

**`test:coverage` échoue.** La couverture doit atteindre <RepositoryFact name="coverageThreshold" unit="percent" /> pour les lignes, les instructions, les fonctions et les branches. Le rapport dans `coverage/` liste les lignes non couvertes.

**Le déploiement s'arrête à `verify-bindings.ts`.** L'environnement cible dans `wrangler.jsonc` n'a pas un binding que l'environnement `development` déclare (`DB`, `CACHE`, `MEDIA` ou `BUNDLES`), contient encore des identifiants D1 ou KV provisoires ou, pour la production, partage une ressource avec la preview. Créez les ressources dans Cloudflare et remplacez les identifiants.

**Le déploiement s'arrête à `prepare-deploy-secrets.ts`.** Une clé listée dans `secrets.required` de l'environnement est absente, vide ou un espace réservé dans `.env.<environment>`. `Set …` nomme les clés absentes ou vides, et `Replace the placeholders …` celles qui contiennent une valeur entre crochets, comme `[UPDATE]`, ou un mot comme `TODO` ou `changeme` ; aucun des deux n'affiche de valeur. [Scripts du projet](/docs/tooling/scripts) liste tous les espaces réservés qu'il refuse. Placez les vraies valeurs dans le fichier et relancez le déploiement.

**Le déploiement s'arrête à `auth:verify`.** Un identifiant client OAuth de `.env.<environment>` n'a pas le format de son fournisseur, qui refuserait donc la connexion. L'erreur nomme la variable, le fichier et le fournisseur sans afficher la valeur, par exemple `AUTH_GOOGLE_CLIENT_ID in .env.production is not a Google OAuth client ID.` Copiez l'identifiant client depuis la console du fournisseur (pour Google, voir l'entrée `invalid_client` ci-dessous) et lancez `bun run auth:verify:<environment>` pour le vérifier de nouveau.

**Le déploiement s'arrête à `polar:verify`.** Polar ne correspond pas au code : une clé de `.env.<environment>` est absente ou désigne le mauvais service Polar, le jeton est rejeté ou il lui manque un scope, ou bien la localisation du paiement ou le comportement fiscal de l'organisation, un produit, un prix, une clé de licence ou un webhook diffère de ce qu'attend le code. L'erreur liste chaque problème ; [Configurer Polar](/docs/getting-started/polar-setup) explique chaque message. `bun run polar:verify:<environment>` relance la vérification.

**Le déploiement s'arrête à `verify-deployment.ts`.** Le Worker est déployé, mais un chemin vérifié n'a pas répondu `200` avec le type de contenu attendu, ou une connexion n'a pas atteint son fournisseur comme prévu. L'erreur liste chaque requête et ce qui ne va pas ; ouvrez l'URL et consultez les journaux du Worker dans Cloudflare. Une ligne qui se termine par `client_id is not a Google OAuth client ID.` signifie que le Worker n'a pas de véritable identifiant client pour ce fournisseur ; voir l'entrée suivante. `bun scripts/verify-deployment.ts <preview|production>` relance la vérification.

**Google répond `Error 401: invalid_client` et `The OAuth client was not found.`** Le Worker a envoyé à Google un identifiant client que Google ne connaît pas. `bun run deploy:<environment>` refuse un espace réservé ou une valeur d'un autre format dans `AUTH_GOOGLE_CLIENT_ID` avant le build (voir `prepare-deploy-secrets.ts` et `auth:verify` ci-dessus) ; un secret du Worker qui en contient un a donc été défini autrement, par exemple avec `wrangler secret put`. Un identifiant client au format de Google que Google ne connaît pas appartient à un client supprimé ou à un client d'un autre projet Google Cloud. Pour corriger :

1. Dans la console Google Cloud, ouvrez **Google Auth Platform → Clients** et créez un client de type **Web application**, ou ouvrez celui que vous voulez utiliser. Son identifiant client se termine par `.apps.googleusercontent.com`.
2. Ajoutez `https://<host>` à **Authorized JavaScript origins** et <RepositoryFact name="googleCallbackUrl" /> à **Authorized redirect URIs** pour chaque hôte sur lequel vous déployez ; Google peut mettre quelques minutes à les appliquer.
3. Dans **Google Auth Platform → Audience**, sélectionnez **Publish app** pour que tout compte Google puisse se connecter, et pas seulement les utilisateurs de test.
4. Placez l'identifiant et le secret du client dans `AUTH_GOOGLE_CLIENT_ID` et `AUTH_GOOGLE_CLIENT_SECRET` de `.env.<environment>` et lancez `bun run deploy:<environment>`, qui vérifie l'identifiant client avant le build, envoie les deux secrets du Worker et vérifie de nouveau la connexion.

**Un build avec prérendu échoue.** La sortie du build indique la première URL en échec. Ouvrez cette page avec `bun run dev` pour voir l'erreur.
