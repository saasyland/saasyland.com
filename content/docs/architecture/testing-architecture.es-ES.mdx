## Proyectos de Vitest

`vp test` ejecuta Vitest a través de Vite+ con tres proyectos definidos en `vite.config.ts`. Las pruebas viven en una carpeta `__test__` junto al código que cubren e importan las APIs de pruebas desde `vite-plus/test`.

| Proyecto      | Entorno | Patrón de archivo       |
| ------------- | ------- | ----------------------- |
| `node`        | Node    | `*.test.ts`             |
| `integration` | Node    | `*.integration.test.ts` |
| `component`   | jsdom   | `*.component.test.tsx`  |

Ninguna prueba contacta con una cuenta real de Cloudflare ni con un proveedor real:

- D1 es una base de datos SQLite en memoria que ejecuta las migraciones del repositorio, y KV es un mapa en memoria. KV y los contadores de límite de peticiones se reinician antes de cada prueba.
- `createServerFn` se sustituye para que una función de servidor se ejecute en el mismo proceso pasando por su middleware y su validador reales.
- Las pruebas de componentes renderizan con un `QueryClient` y un router reales.
- Las peticiones de correo, OAuth y pagos están mockeadas.

## Cobertura

`bun run test:coverage` exige un 100 % de líneas, sentencias, funciones y ramas en todo `src`. Se excluyen las primitivas de shadcn, `src/platform/testing`, los archivos generados y las declaraciones de tipos. Cubre el comportamiento real y elimina las ramas que nunca pueden ejecutarse, en lugar de simular globales para llegar a ellas.

## Pruebas de navegador

Las specs de Playwright viven en `e2e/specs`, con los page objects en `e2e/pages` y los fixtures en `e2e/fixtures`. Se ejecutan contra un build similar al de producción que usa el entorno `test` de Wrangler: D1 y KV locales en `.wrangler/test`, secretos ficticios de `.env.test` y un Worker de pruebas que captura los correos salientes para que una spec pueda seguir un enlace de verificación real. En local, Playwright aplica las migraciones, carga los datos iniciales, hace el build y arranca la aplicación por sí mismo. La suite se ejecuta en Chromium y WebKit.

## CI

`.github/workflows/ci.yml` se ejecuta en las pull requests y en los push a `main`:

1. `bun run check`: formato, lint, comprobación de tipos y `check:i18n`
2. `bun run test:coverage`
3. Un build de pruebas y la suite de Playwright en Chromium
4. Un despliegue de preview para las pull requests, o un despliegue a producción para `main`
