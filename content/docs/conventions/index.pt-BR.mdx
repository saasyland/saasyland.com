Estas páginas são o padrão de código deste repositório. Elas descrevem como o código é escrito aqui, não como poderia ser escrito, e cada regra cita os arquivos que a seguem. A maioria das regras é garantida por um comando: `bun run check` (formatação, lint, tipos, traduções e estrutura da documentação), `bun run test:coverage` (a exigência de <RepositoryFact name="coverageThreshold" unit="percent" />) ou a suíte end-to-end. As demais são cobradas na revisão, e cada página diz quais.

Quando estiver em dúvida sobre como escrever algo, encontre o exemplo existente mais próximo do mesmo tipo, leia-o e copie a forma dele. Consistência vale mais do que uma ideia localmente melhor: uma segunda maneira de fazer a mesma coisa obriga todo leitor posterior, humano ou agente, a aprender as duas.

## Regras sem exceções

Violar uma delas faz uma alteração ser rejeitada, por melhor que ela seja em todo o resto.

1. Nenhum comentário em código, testes, scripts, configuração ou CSS. Veja [Estilo de código](/docs/conventions/code-style).
2. Nada de `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, casts com `as` ou `any` para passar por uma regra. Corrija a causa.
3. Nada de ternários de várias linhas nem de `?? undefined`. Fora dos testes e de `src/platform/testing`, `null` só é escrito onde uma API o define: na comparação com um valor que pode ser `null` e em uma ref de DOM do React (`useRef<HTMLElement>(null)`). Veja [Estilo de código](/docs/conventions/code-style).
4. Status, tipos, planos, papéis e outros valores de domínio são constantes nomeadas, nunca literais de string repetidos, inclusive nos testes. Os testes de schema são o único lugar em que um valor armazenado é escrito por extenso. Veja [Testes](/docs/conventions/testing).
5. Uma pasta em `src/modules` só existe para uma tabela do banco de dados. Veja [Módulos](/docs/conventions/modules).
6. Todo texto exibido ao usuário existe em todos os locales, assim como toda página da documentação. Os números mostrados no site são medidos ou declarados uma única vez em `src/data`, nunca digitados. Veja [Traduções e conteúdo](/docs/conventions/translations).
7. A cobertura se mantém em <RepositoryFact name="coverageThreshold" unit="percent" /> para linhas, instruções, funções e branches. Veja [Testes](/docs/conventions/testing).
8. Uma alteração atualiza o README, a documentação e os textos do site que ela torna imprecisos, no mesmo pull request.
9. Commits e pull requests não levam nenhuma atribuição a IA nem trailer `Co-Authored-By`. Veja [Git e pull requests](/docs/conventions/git-workflow).

## Definição de pronto

Uma alteração está pronta quando estes comandos passam, nesta ordem, na branch que você está prestes a enviar:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` e os testes não exercitam o build do Cloudflare: uma atualização de dependência já passou nos dois enquanto o build de produção estava quebrado. Execute `build:test` em toda alteração, e a suíte de navegador em tudo o que não for documentação. Antes de fazer o commit, leia o seu próprio diff em busca de comentários, literais de string que deveriam ser constantes e textos ou documentação que a alteração tornou incorretos.
