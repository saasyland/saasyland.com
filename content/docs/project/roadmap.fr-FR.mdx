## CLI : chaque option du configurateur

Le [configurateur](/#cli) affiche chaque option et chaque extra que SaaSy Land générera, et la CLI les générera tous. Une option n’est activée dans le configurateur, et acceptée par `init`, que lorsqu’un projet généré avec elle s’installe, passe la vérification des types, réussit ses tests à <RepositoryFact name="coverageThreshold" /> % de couverture, se construit et démarre, en CI, à chaque modification susceptible de l’atteindre. D’ici là, le configurateur l’affiche désactivée et `init` la refuse avec le code de sortie <RepositoryFact name="cliExitNotAvailable" />, avant toute vérification de licence.

Certaines réponses dépendent d’autres. La question de l’API ne concerne que les architectures API séparée et microservices, et certains environnements d’exécution et fournisseurs ne tournent pas sur toutes les cibles de déploiement, comme l’environnement d’exécution Bun sur Cloudflare Workers. Le configurateur désactive toute combinaison que la cible ne peut pas exécuter.

Les options arrivent dans cet ordre :

1. La facturation avec Polar, avec les commandes et les clients dans la console d’administration générée. Elle attend la facturation générique de l’application (En cours).
2. L’extra Cours par abonnement, avec les cours dans la console d’administration générée. Il a besoin de la facturation.
3. La facturation avec Stripe, et l’e-mail avec Plunk.
4. Se passer de l’e-mail, et se passer du contenu. Sans e-mail, la connexion a besoin d’un parcours qui n’envoie aucun message ; sans contenu, les conventions de code vers lesquelles renvoient les instructions pour agents d’un projet généré doivent se trouver en dehors de la documentation.
5. Postgres avec Neon, Supabase ou votre propre serveur ; Turso ; un fichier SQLite local ; Prisma.
6. Le déploiement sur Vercel, ou sur votre propre serveur avec une image Docker de production et une configuration Compose ; les environnements d’exécution Bun et Deno.
7. L’architecture API séparée, avec une API Hono ou Elysia, puis les microservices.
8. Le temps réel, en extra : le streaming du serveur vers le navigateur sur chaque environnement d’exécution, les WebSockets bidirectionnels et une démo en direct des deux dans la console d’administration générée.
9. Next.js et React Router sur React.
10. Solid avec SolidStart et TanStack Start, Vue avec Nuxt, Svelte avec SvelteKit, et Angular avec Analog et Angular SSR.
11. L’option Multitenant, une fois que les organisations et les rôles seront dans l’application.
12. La boutique avec des produits d’exemple, le constructeur de pages visuel et l’éditeur visuel de publication, chacun après que l’application aura livré la fonctionnalité qu’il génère.

### Commandes et versions

- Des questions interactives dans un terminal. Aujourd’hui, une session de terminal répond par la valeur par défaut à chaque question que vous n’avez pas passée en flag, comme le fait `--yes`.
- `status`, qui affiche la version, les réponses et la licence d’un projet.
- `change`, qui relance la CLI sur un projet existant avec d’autres réponses : les modules d’abord, les changements de plateforme ensuite.
- `update`, qui fait passer un projet à une version plus récente en une seule commande, avec une fusion à trois voies qui conserve vos propres modifications. Des scénarios de mise à jour et de changement tournent chaque nuit sur les versions récentes.
- Une référence générée de chaque commande et de chaque flag dans le [guide de la CLI](/docs/cli), et des guides pour mettre à jour la CLI, renouveler une clé de licence, résoudre les problèmes, et mettre à jour ou modifier un projet. Chaque commande du guide s’exécute en CI contre la CLI testée.
- Une prochaine bêta qui corrige les README de la CLI elle-même et sa documentation de version.
- La version stable sur le tag par défaut de npm. D’ici là, lancez la CLI avec <RepositoryFact name="cliPackageSpec" />. La version stable sortira quand la facturation et l’extra de cours seront là, et quand la suite de parcours client nocturne générera un projet avec chaque gestionnaire de paquets, le construira, exécutera ses tests et vérifiera la licence de bout en bout. Le site passera alors ses commandes sur le tag par défaut et publiera les notes de version et un article de sortie.

## Application

1. La facturation générique (En cours) : la page de facturation avec les factures et le portail client, puis la licence par-dessus.
2. Les prix du site lus depuis Polar, pour qu’un prix ne change qu’à un seul endroit.
3. Créer, modifier et supprimer des produits depuis l’administration, via Polar ; les modèles de tarification, ponctuels et récurrents ; les codes de réduction.
4. Émettre des remboursements depuis la page de la commande, qui affiche déjà les remboursements enregistrés dans Polar ; un e-mail à l’acheteur quand une licence est remboursée ou révoquée ; et les litiges de paiement sur la page de la commande, avec leur issue appliquée à la licence.
5. Passer à une offre inférieure depuis la page de la licence. Aujourd’hui, cela se fait par e-mail au support.
6. Des métriques de tableau de bord sur des données réelles ; une mesure de l’entonnoir d’inscription et de paiement respectueuse de la vie privée ; un écran d’analytique avec les pages vues, les visiteurs, la rétention et l’attrition.
7. La newsletter : une liste d’abonnés avec export CSV, l’envoi des numéros depuis l’administration, et l’activation ou la désactivation de la newsletter dans l’espace client.
8. Les permissions : un rôle de rédacteur, des menus filtrés selon les permissions et un éditeur de rôles.
9. Les organisations et les équipes, puis les places d’équipe d’Agency.
10. Un profil de l’espace de travail dans les paramètres de l’administration : nom, e-mail de support, adresse et logo.
11. Un journal d’audit des bannissements, des suppressions et des emprunts d’identité.
12. La modification du blog depuis l’administration, dans un éditeur visuel qui commite dans Git via une pull request ; puis la modification de la documentation.
13. La page d’accueil construite à partir d’un registre de sections, puis le concepteur visuel de pages, une page de tarifs, une bibliothèque de sections et des pages de campagne.
14. L’ouverture du programme d’affiliation.
15. Apple Pay et Google Pay dans le checkout intégré, que Polar doit activer pour les checkouts intégrés.

## Qualité et ingénierie

- La suite de tests du navigateur WebKit comme vérification obligatoire.
- La suite de parcours client nocturne exécutée contre le site de preview et la sandbox de Polar, puis étendue pour générer un projet avec la CLI, le construire et exécuter ses tests avec chaque gestionnaire de paquets.
- Un test dans le navigateur pour chaque parcours listé plus bas comme manquant, et pour les parcours encore à construire à mesure que leurs fonctionnalités sont livrées.
- Des tests de mutation sur le code des licences, des paiements et des accès, et la couverture de code dans le navigateur de la suite Playwright.
- Les exclusions du contrôle de couverture, les primitives shadcn et les utilitaires de test, indiquées sur la page de couverture des tests.
- Des règles de lint pour les assertions non nulles et les blocs `catch` vides, et des garde-fous pour les agents de codage : un registre des règles avec leurs vérifications, des skills du dépôt générées à partir des conventions avec un contrôle de dérive, et des hooks versionnés dans le dépôt.
- Une règle de lint sur les frontières entre modules dans les projets générés, et des projets générés construits chaque nuit sur les dernières dépendances.
- Performance : un test A/B de la suppression des indications modulepreload, Server-Timing sur le Worker, et les activations de licence diffusées en continu vers la page.
- Des dépendances maintenues sur leurs dernières versions, chaque patch étant retiré dès que son correctif sort en amont.
- Les anciennes issues de la précédente base de code Next.js fermées avec une note.
