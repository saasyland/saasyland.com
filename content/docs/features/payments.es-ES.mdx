Los pagos pasan por Polar con el plugin `@polar-sh/better-auth`, que el área de Polar añade a Better Auth en `src/data/polar.auth-plugins.ts`:

```ts
export const POLAR_AUTH_PLUGINS = [
  {
    plugin: polar({
      client: polarCore,
      use: [portal(), webhooks({ onPayload: handlePolarEvent, secret: env.POLAR_WEBHOOK_SECRET })],
    }),
    rateLimitExemptPaths: [ROUTES.API_AUTH_POLAR.WEBHOOKS],
  },
] as const satisfies readonly AuthPluginEntry[]
```

El plugin añade el portal de cliente y los webhooks, que quedan exentos del limitador de frecuencia de Better Auth, pero ningún pago: su `checkout()` crearía un pago solo con el ID de la cuenta, de modo que Polar volvería a pedir su correo a un comprador con la sesión iniciada. Better Auth no cierra ninguna ruta por HTTP, así que `src/data/__test__/polar.auth-plugins.integration.test.ts` comprueba que la ruta de pago del plugin responde 404 y falla en cuanto se añade `checkout()` al plugin. Un área que vende crea sus pagos con el SDK de Polar tras sus propias comprobaciones, como hace `startCheckout` del área de licencias (consulta [Licencias](/docs/features/licences)).

`src/integrations/polar/polar.config.ts` crea `polarCore` a partir de `POLAR_ACCESS_TOKEN` y `POLAR_SERVER`, que es el que usa el plugin, y `polar`, los servicios de pagos, descuentos, claves de licencia y pedidos construidos sobre él. `POLAR_ORGANIZATION_ID` acota a la organización cada llamada a Polar que nombra una organización; [Entorno y bindings](/docs/reference/environment) las enumera. `src/integrations/polar/polar.constants.ts` contiene los valores propios de Polar, `POLAR_ORDER_STATUS`, `POLAR_LICENSE_KEY_STATUS`, `POLAR_WEBHOOK_EVENT` y `POLAR_CHECKOUT_ID_PLACEHOLDER`, cada uno comprobado con los tipos del SDK; no lee ningún entorno, así que también lo importan el navegador y la suite del navegador. Las rutas del área de Polar, `API_AUTH_POLAR` y `API_AUTH_CUSTOMER_PORTAL`, están en `src/data/polar.routes.ts`. [Configuración de Polar](/docs/getting-started/polar-setup) describe los productos, las claves de licencia, los descuentos, el webhook y el token que este código espera en Polar, y `bun run polar:verify:<environment>` los comprueba.

## Webhooks [#webhooks]

Polar envía los eventos a `/api/auth/polar/webhooks`. El plugin verifica la firma con `POLAR_WEBHOOK_SECRET` y pasa cada evento a `handlePolarEvent`, en `src/data/polar-events.ts`. Un área que reacciona a los eventos de Polar declara una lista en `src/data/<area>.polar-events.ts` y la añade a `src/data/polar-events.entries.ts`. Cada entrada indica los eventos que gestiona y la función que los gestiona:

```ts
export interface PolarEventHandler {
  readonly events: readonly models.WebhookEventType[]
  readonly handle: (event: webhooks.WebhookPayload) => Promise<void>
}
```

- `handlePolarEvent` ejecuta a la vez el `handle` de cada entrada que incluye el tipo del evento y espera a que terminen todos.
- Cuando uno falla, el plugin responde 500 y Polar vuelve a entregar el evento más tarde, así que cada handler debe poder ejecutarse dos veces con el mismo evento sin causar problemas. Polar desactiva un endpoint que falla una y otra vez, y `polar:verify` informa de un endpoint desactivado.
- Un evento que no incluye ninguna entrada se confirma y no va a ninguna parte.
- `POLAR_EVENTS` reúne los eventos de todas las entradas, ordenados y sin repetir. El endpoint de webhook en Polar debe enviar exactamente esos, y `polar:verify` los compara.
- El área de Polar añade una lista vacía en `src/data/polar.polar-events.ts`, para que el barrel nunca esté vacío. Hoy solo el área de licencias gestiona eventos, en `src/data/license.polar-events.ts`; consulta [Licencias](/docs/features/licences#webhooks-and-licences).

`polar:verify` se ejecuta en Bun, fuera del Worker, y lee `POLAR_EVENTS`, así que `src/data/polar-events.ts` y cada `<area>.polar-events.ts` no importan código de servidor. El `handle` de un área carga sus handlers cuando llega un evento:

```ts
const { licenseWebhookHandlers } = await import("~/src/modules/license/license.webhooks")
```

`src/data/__test__/polar-events.test.ts` importa `src/data/polar-events.ts` en Bun y falla cuando esa importación llega al entorno de ejecución del Worker.

## Portal de cliente

`ROUTES.API_AUTH_CUSTOMER_PORTAL` (`/api/auth/customer/portal`) abre el portal de cliente de Polar de la cuenta con sesión iniciada. La tarjeta de la licencia de `/app/license` enlaza a él.

## Pantalla de administración (demostración)

`/admin/payments` muestra `RefundStats` y un `DataTable` de reembolsos sobre `ADMIN_PAYMENT_ROWS` de `src/data/admin-payments.ts`; sus botones no están conectados. El área de pagos define las declaraciones de permisos `order` (`read`, `update`, `refund`) en `src/data/payments.access.ts`, pero ningún caso de uso lee pedidos ni reembolsos.
