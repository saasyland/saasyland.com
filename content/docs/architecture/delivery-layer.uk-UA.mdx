## Файли маршрутів

Маршрути — це пласкі файли в `src/routes`. Крапки стають сегментами шляху:

| Файл                              | URL                | Примітки                                    |
| --------------------------------- | ------------------ | ------------------------------------------- |
| `__root.tsx`                      | усі сторінки       | Оболонка документа й кореневі простори імен |
| `_site.tsx`                       | немає              | Макет без шляху із заголовком сайту         |
| `_site._marketing.tsx`            | немає              | Макет без шляху для маркетингових сторінок  |
| `_site._marketing.terms.tsx`      | `/terms`           | Сторінка всередині маркетингового макета    |
| `admin.tsx`                       | `/admin`           | Макет із guard-функцією `requireAdmin`      |
| `admin.users.all.tsx`             | `/admin/users/all` | Сторінка всередині макета адмін-панелі      |
| `_site._marketing.blog.index.tsx` | `/blog`            | Індексна сторінка макета `blog`             |
| `_site.docs.$.tsx`                | `/docs/*`          | Splat-маршрут для сторінок документації     |
| `api/auth.$.ts`                   | `/api/auth/*`      | HTTP-обробник без компонента                |

Ідентифікатори `createFileRoute("…")` — це рядкові літерали, які підтримує генератор роутера; він також записує `src/routeTree.gen.ts`. Файли в папках `__test__` ігноруються. Кожна URL-адреса має константу в `ROUTES` (`src/routes.ts`), а посилання використовують `<Link to={ROUTES.X}>`.

## Маршрути сторінок

Маршрут сторінки визначає компонент `<Name>Page`, константу `NAMESPACE` безпосередньо над `export const Route` і loader-функцію, яка завантажує метадані сторінки та простір імен в одному `Promise.all`:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Додаткові дані потрапляють у той самий `Promise.all`, наприклад `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` в `admin.users.all.tsx`. `pageHead` із `src/lib/seo.ts` будує теги title, description, canonical, `hreflang`, Open Graph і зображення для соцмереж з `metadata`, яку повертає loader-функція; див. [Пошук і попередній перегляд у соцмережах](/docs/features/seo).

## Маршрути макетів

Маршрут макета визначає компонент `<Name>Layout`, масив `NAMESPACES` і, для захищених розділів, guard-функцію в `beforeLoad`. Його `NAMESPACES` закінчуються просторами імен, які до нього додають інші розділи, а параметр пошуку валідують сторінки, що його читають, як це роблять сторінки ліцензії `/app` і `/app/license` з `tier`:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "timezones", ...layoutNamespaces("/app")] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Guard-функції `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn`, `redirectIfVerified` і `redirectAfterAuth` надходять із `src/integrations/better-auth/auth.routes.ts`.

## Скелетони завантаження [#loading-skeletons]

Більшість переходів завершується ще до появи будь-якого інтерфейсу очікування: посилання попередньо завантажують свій маршрут під час наведення й дотику, а публічні сторінки попередньо відрендерені. Коли перехід не завершився за `defaultPendingMs`, <RepositoryFact name="navigationPendingMs" unit="millisecond" />, роутер показує скелетон маршруту, а оскільки `defaultPendingMinMs` дорівнює <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, прибирає його, щойно сторінка готова. Так буває на повільному з'єднанні або під час першого запиту до нового ізолята Worker (див. [Продуктивність](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

Типового компонента очікування немає. Кожен маршрут макета й сторінки задає власний `pendingComponent`. Сторінки документації малюються всередині макета документації: `_site.docs.index.tsx` і `_site.docs.$.tsx` показують `DocsIndexPending` і `DocsPagePending` — статтю та її зміст поруч із бічною панеллю, а макет `docs` показує `DocsPending`, коли хтось заходить у документацію з іншого місця. Кожен скелетон відтворює сторінку, яку заміщує:

- **Скелетони сторінок**, як-от `SignInPending` і `LegalPending`, розміщено у файлі скелетонів зони; вони позначають свій кореневий елемент атрибутом `aria-busy="true"`. Це файли `custom/auth/auth-pending.tsx`, файли адмін-панелі в `custom/admin/` (`admin-pending.tsx` для макета, по одному файлу `<area>-pending.tsx` на кожну зону, як-от `products-pending.tsx`, та спільні блоки в `pending-blocks.tsx`), файли застосунку клієнта в `custom/app/` (`app-pending.tsx` для макета, `auth-pending.tsx` і `license-pending.tsx`, а також спільний для них заголовок сторінки в `pending-blocks.tsx`), файли публічного макета на верхньому рівні `custom/` (`marketing-pending.tsx` для макета, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` і `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` і `custom/docs-pending.tsx`.
- **Скелетони макетів**, як-от `AuthPending` і `MarketingPending`, рендерять каркас макета, а всередині нього — `pendingComponent` першого маршруту під макетом, який відповідає поточному шляху й задає його; `usePagePending` у `src/hooks/use-page-pending.ts` читає його з дерева маршрутів. Тому під час переходу в зону з іншого місця показується правильна сторінка, а скелетон макета на рівень нижче, як-от `AdminUsersPending`, робить те саме для своїх сторінок. Елементи каркаса, яким не потрібні дані, як-от `Wordmark` і `PageFrame`, рендеряться по-справжньому, а заголовок сайту залишається на екрані, бо макет `_site`, який його рендерить, не має loader-функції, на яку треба чекати.
- **Текстові заповнювачі** — це смуги `Skeleton` з типографічним токеном справжнього елемента плюс `h-lh scale-y-70`, тож кожна смуга заповнює рівно один рядковий блок (line box). Блоки мають справжні висоти й радіуси заокруглення. Списки беруть свою довжину з тих самих констант, що й UI, як-от `OAUTH_PROVIDERS` і `AUTH_ASSURANCES` у `src/data/auth.ts`.

Коли додаєте сторінку, додайте її скелетон до файлу скелетонів зони та задайте як `pendingComponent` маршруту; скелетони макетів знаходять його там.

## Інші аспекти маршрутів

- **Параметри рядка запиту** розбирає `validateSearch` у маршруті, наприклад параметр `tab` для `/admin/products`. Схема — це `zod.object`, побудований з допоміжних функцій у `src/lib/search-params.ts`: `searchText()` і `searchFlag()` дають `undefined`, коли значення немає, воно порожнє чи некоректне, а `searchChoice(choices, fallback)` дає резервне значення. `searchParam(schema)` дає `undefined`, якщо значення не відповідає іншій zod-схемі, наприклад токену розсилки.
- **Серверні функції одного маршруту** можна визначити у файлі маршруту через `createServerFn`.
- **Вміст, зібраний під час збірки**: loader-и документації, блогу й лендингу читають індекси вмісту з `virtual:content-indexes`, тобто файли в `/assets/`, тож їм не потрібна серверна функція і під час навігації на клієнті вони виконуються в браузері (див. [Fumadocs](/docs/integrations/fumadocs#content-indexes)).
- **HTTP-ендпоінти** лежать у `src/routes/api`. Див. [HTTP-обробники TanStack Start](/docs/architecture/api-layer).

## Роутер

`src/router.tsx` експортує `getRouter`, який для кожного запиту створює новий `QueryClient` і роутер. Він налаштовує:

- типові компоненти помилки та «не знайдено» з `presentation/components/custom`, але без типового компонента очікування (див. [Скелетони завантаження](#loading-skeletons))
- попереднє завантаження за наміром користувача й типовий час застарівання даних (<RepositoryFact name="routerStaleTimeMinutes" unit="minute" />), однаковий для завантажених і попередньо завантажених сторінок, тож сторінка, яку `Navigation` попередньо завантажує для заголовка, щойно сторінка простоює, ще свіжа в момент кліку (див. [Продуктивність](/docs/conventions/performance#the-headers-pages-load-before-a-click))
- `rewrite`, який прибирає префікс локалі з вхідних URL-адрес і додає його назад до згенерованих посилань
- інтеграцію запитів із SSR через `setupRouterSsrQueryIntegration`

## Після розгортання [#after-a-deploy]

Кожне розгортання замінює статичні ресурси Worker, а Vite називає кожен файл за його вмістом, тож вкладка, відкрита до розгортання, запитує чанки маршрутів, яких уже не існує. TanStack Start виносить компонент і loader кожного маршруту в окремі чанки. TanStack Router перезавантажує сторінку, коли чанк компонента не вдається завантажити (`lazyRouteComponent`), але чанк loader router-core завантажує через `lazyFn`, яка передає невдалий імпорт маршруту як помилку його loader. Клік на **Blog** у такій вкладці падав на чанку loader макета блогу й показував сторінку помилки.

`DefaultError`, типовий компонент помилки роутера, тепер із цим справляється. `isStaleBuildError` у `src/lib/stale-build.ts` розпізнає помилку, яка означає, що сторінка виконує код, який видалило новіше розгортання:

- невдалий динамічний імпорт, який `isModuleNotFoundError` з router-core розпізнає в Chromium, Firefox і Safari;
- файл, який Vite не зміг попередньо завантажити для чанка, наприклад його таблицю стилів; Vite повідомляє про нього подією `vite:preloadError`. Кореневий маршрут слухає цю подію, поки застосунок відкритий (`listenForStaleBuilds`).

За такої помилки `DefaultError` завантажує адресу, на яку перейшов відвідувач, як нову сторінку через `router.navigate({ href, reloadDocument: true, replace: true })`, тож відвідувач потрапляє на сторінку, на яку натиснув, уже з нового розгортання; поки браузер не залишить сторінку, компонент показує порожній `main`, позначений як зайнятий, замість повідомлення про помилку. `claimReload` дозволяє одне таке перезавантаження для кожного призначення й збірки. Він записує призначення в `sessionStorage` разом з URL вхідного скрипту сторінки, який змінюється з кожним розгортанням, що змінює файл, який завантажує браузер, бо до кожного чанка веде шлях від вхідного скрипту через його назву на основі вмісту. Друга невдача для того самого призначення в тій самій збірці показує сторінку помилки, тож файл, якого справді бракує, не може змусити сторінку перезавантажуватися без кінця, а наступне розгортання отримує власне перезавантаження. Коли браузер відмовляє в доступі до сховища сесії, нічого не перезавантажується.

Safari скасовує файли, які сторінка ще завантажує, щойно відвідувач починає її залишати, тож чанк або таблиця стилів, що були в дорозі, завершуються помилкою, ніби їх видалило розгортання. Тому `listenForStaleBuilds` також зазначає, коли сторінка отримує `beforeunload`, а `DefaultError` чекає через `whenPageStays`, доки `pageshow`, `pointerdown` або `keydown` не покаже, що відвідувач залишився, перш ніж завантажити сторінку знову. Відвідувач, який іде, потрапляє на сторінку, яку запросив, замість того щоб повернутися на ту, яку залишав, а той, хто повертається на сторінку або залишається на ній, отримує перезавантаження тоді. `stale-build.spec.ts` затримує таблицю стилів відеоплеєра на уроці, переходить до політики конфіденційності, скасовує таблицю стилів і перевіряє, що політика конфіденційності відкривається, а урок не запитується знову.

Невдале попереднє завантаження нічого не витрачає. Наведення вказівника на посилання попередньо завантажує його маршрут, як це робить заголовок для своїх посилань, щойно сторінка простоює; якщо це не вдається, жоден компонент помилки не з'являється, а роутер знову запитує чанк, коли відвідувач натискає. `e2e/specs/stale-build.spec.ts` вмикає заощадження даних, щоб заголовок не завантажив блог заздалегідь, прибирає чанки блогу з відкритої сторінки й перевіряє, що клік, зокрема після невдалого попереднього завантаження під час наведення, потрапляє на блог після одного перезавантаження, а сторінка, чиїх чанків і далі бракує, показує сторінку помилки після двох перезавантажень, одного від `DefaultError` і одного від `lazyRouteComponent`.
