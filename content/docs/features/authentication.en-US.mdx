## Configuration

`src/integrations/better-auth/auth.server.ts` creates the Better Auth instance:

- Drizzle adapter on D1, UUID v7 ids, cookie prefix `saasyland`, secure cookies outside the `development` and `test` modes, and allowed hosts per mode from `appHostsForMode`.
- Email and password with required email verification, passwords of 8 to 1024 characters with an uppercase letter and a special character (`auth.constraints.ts`) and session revocation on password reset.
- `enforceInputPolicy` (`auth.hooks.ts`), a `hooks.before` middleware, applies the form schemas to Better Auth's own endpoints: sign-up, password reset and change, profile and email updates, and the admin endpoints that create users or set passwords. A request posted straight to `/api/auth` gets `400 VALIDATION_ERROR` instead of skipping the rules.
- GitHub and Google social providers with account linking and encrypted OAuth tokens.
- Plugins: `admin` with the roles from `auth.access.ts`, `twoFactor`, Polar (`checkout`, `portal`, `webhooks`) and `tanstackStartCookies`.
- Rate limiting stored in the D1 `rate_limit` table; `/get-session`, `/sign-out` and the Polar webhook are exempt.
- An extra `timezone` user field and email change with a confirmation email.

`src/routes/api/auth.$.ts` passes every GET and POST under `/api/auth` to `auth.handler`.

## Screens

The `/auth` layout preloads the `auth.*` namespaces and renders the gate panel next to the form.

| Route                                           | Components                                | Behaviour                                                                                                                                         |
| ----------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/auth/sign-in`                                 | `OAuthButtons`, `SignInForm`              | Signs in with Better Auth `signIn.email`. An unverified email moves to `/auth/verify-email`; an account with 2FA continues at `/auth/two-factor`. |
| `/auth/sign-up`                                 | `OAuthButtons`, `SignUpForm`              | Calls the `signUpWithPassword` server function, then moves to `/auth/verify-email`.                                                               |
| `/auth/callback`                                | none                                      | `redirectAfterAuth` sends the visitor to `redirect`, or admins to `/admin` and everyone else to `/app`.                                           |
| `/auth/verify-email`                            | `VerifyEmailForm`                         | See [Email verification](/docs/features/email-verification).                                                                                      |
| `/auth/forgot-password`, `/auth/reset-password` | `ForgotPasswordForm`, `ResetPasswordForm` | See [Password reset](/docs/features/password-reset).                                                                                              |
| `/auth/two-factor`                              | `TwoFactorForm`                           | See [Two-factor authentication](/docs/features/two-factor).                                                                                       |

After a successful sign-in, `finishSignIn` from `useAuthRedirect` clears the query and router caches and navigates to `/auth/callback`, keeping `redirect`. Better Auth errors returned as `?error=` on `/auth/sign-in` render the matching `auth.errors` message.

## Route guards

`src/integrations/better-auth/auth.routes.ts` exports the guards used in `beforeLoad`:

- `requireSignedIn` protects `/app` and redirects to `/auth/sign-in`, with the page as `redirect`.
- `requireAdmin` protects `/admin`; a signed-in user without the `admin: ["access"]` permission goes to `/app`.
- `redirectIfSignedIn` sends signed-in users from sign-in and sign-up to `redirect`, or to their workspace.
- `redirectAfterAuth` powers `/auth/callback`.

The guards read the session through `getCurrentSessionQuery` and clear the query cache when the signed-in user changes. [Auth flows](/docs/guides/auth-flows#return-path) describes how `redirect` travels through sign-in, sign-up, OAuth and two-factor verification.

## Server functions

Server functions use the middleware from `auth.middleware.ts`: `authorized()` requires a session, `authorized({ user: ["list"] })` also checks a permission, and `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` limits calls per client IP.

```ts
export const signOutUser = createServerFn({ method: "POST" })
  .middleware([authorized()])
  .handler(({ context }) => auth.api.signOut({ headers: context.requestHeaders }))
```

There are two roles, `admin` and `customer` (the default for new users).
