Jede Drittanbieter-Bibliothek und jeder Dienst, der eingerichtet werden muss, besitzt einen eigenen Ordner unter `src/integrations`. Die Dateien heißen `<prefix>.<concern>.ts`, wobei das Präfix der Kurzname des Anbieters ist.

| `better-auth`    | `auth.server`, `auth.client`, `auth.access`, `auth.roles`, `auth.middleware`, `auth.routes`, `auth.session`, `auth.errors`, `auth.hooks`, `auth.zod`, `auth.constraints`, `auth.constants` | Auth-Konfiguration, Rollen, Middleware für Server Functions, Route-Guards, Session-Query, Provider-IDs                                                                   |

## Was keine Integration ist

- Die Anzahl der GitHub-Sterne ist eine Server Function in `src/lib/github.ts`, gecacht in KV.
- Rate Limiting ist `src/lib/rate-limit.ts` und basiert auf der Tabelle `rate_limit`.
- Cloudflare-Bindings brauchen keinen Adapter. Servercode liest sie aus `env` in `cloudflare:workers`.

## Geschäftslogik bleibt in Modulen

Eine Integration konfiguriert einen Anbieter. Entscheidungen über Anwendungsdaten gehören in das Modul, dem die Tabelle gehört:

- Das Polar-Plugin, eines der `plugins` in `src/integrations/better-auth/auth.server.ts`, prüft Webhook-Signaturen mit `POLAR_WEBHOOK_SECRET` und übergibt jedes Ereignis an `handlePolarEvent` in `src/integrations/polar/polar.webhooks.ts`. Diese Funktion reicht es an jedes Element von `POLAR_EVENT_HANDLERS` weiter, das das Ereignis aufführt; das Element der Lizenz ruft die `licenseWebhookHandlers` in `src/modules/license/license.webhooks.ts` auf, die wiederum die Lizenz-Use-Cases aufrufen, und die Elemente der Bestellungen und Abonnements rufen `recordOrder` und `recordSubscription` auf. Auch die Produkt-IDs der Lizenzstufen, `POLAR_PRODUCT_IDS`, gehören zum Lizenzbereich; sie liegen in `src/modules/license/license.utils.ts`.
- Die E-Mail-Hooks von Better Auth rufen `sendVerifyEmail`, `sendExistingAccountEmail`, `sendResetPasswordEmail`, `sendPasswordChangedEmail`, `sendDeleteAccountEmail` und `sendChangeEmailConfirmationEmail` aus den Modulen verification, account und user direkt auf.
- Ein Use Case versendet eine E-Mail in der Locale, die sein Aufrufer übergibt (die Bestätigungs-E-Mail liest sie aus der Callback-URL): Er lädt den Namespace des Templates, rendert das Template und ruft `sendEmail` auf:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await sendEmail({
  idempotency: { purpose: VERIFICATION_EMAIL_PURPOSE.VERIFY_EMAIL, token: crypto.randomUUID() },
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```
