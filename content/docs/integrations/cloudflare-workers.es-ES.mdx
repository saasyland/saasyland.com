La aplicación se ejecuta como un único Cloudflare Worker. `@cloudflare/vite-plugin` lo compila y `CLOUDFLARE_ENV` selecciona el entorno de Wrangler. `wrangler.jsonc` establece `main` en `./src/server.ts`, activa `nodejs_compat` y la observabilidad, y sirve los archivos estáticos mediante el binding `ASSETS`. El Worker se ejecuta primero en todas las rutas excepto `/assets/*`, `/fonts/*`, `/robots.txt` y `/llms.txt`. Los source maps no se suben (`upload_source_maps` es `false`), porque el Worker y sus source maps superan juntos el tamaño que Cloudflare acepta en una sola subida.

| Entorno       | Worker                  | D1, KV y R2                           | Dominio                 |
| ------------- | ----------------------- | ------------------------------------- | ----------------------- |
| `development` | `saasyland-development` | Recursos locales en `.wrangler/state` | `localhost:3000`        |
| `preview`     | `saasyland-preview`     | Recursos de preview                   | `preview.saasyland.com` |
| `production`  | `saasyland`             | Recursos de producción                | `saasyland.com`         |
| `test`        | `saasyland-test`        | Recursos locales en `.wrangler/test`  | `127.0.0.1:3000`        |

Todos los entornos vinculan D1 como `DB`, KV como `CACHE` y R2 como `MEDIA` y `BUNDLES`, y enumeran sus secretos obligatorios. `AFFONSO_PROGRAM_ID`, que necesita el seguimiento de referidos de afiliados, es una variable normal en `vars`, definida en `production` y, con un ID ficticio, en `test`. El seguimiento solo funciona cuando el Worker tiene el ID y el programa está abierto: hoy `AFFILIATE_PROGRAM` vale <RepositoryFact name="affiliateProgram" /> ([Abrir el programa](/docs/features/affiliates#opening-the-programme)). El entorno `test` usa `src/platform/testing/worker.ts` como punto de entrada; intercepta las solicitudes a Resend y a Polar y expone endpoints exclusivos de pruebas para Playwright.

## Flujo de una solicitud

`src/server.ts` gestiona todas las solicitudes:

1. Una ruta que reclama un área va, antes que nada, al handler de peticiones de esa área. El área de cursos reclama `/media/` y la pasa a `serveMedia`, que sirve archivos de vídeo firmados desde la caché de Workers o desde R2 (consulta [Cloudflare R2](/docs/integrations/cloudflare-r2)), y el área de licencias reclama `/bundles/` y la pasa a `serveBundle`, que sirve desde R2 los bundles de plantillas firmados de la CLI (consulta [API de licencias de la CLI](/docs/features/cli-licence-api#template-bundles)). De los pasos siguientes, solo se les aplican las cabeceras de seguridad.
2. `resolveLocale` de `i18n.middleware.ts` examina las solicitudes de documentos `GET` y `HEAD` fuera de `/api` y `/_serverFn`. Redirige los alias de idioma y las rutas de idioma no canónicas con el estado 308 e indica cuándo la cookie de idioma no coincide con el idioma de la URL.
3. Las solicitudes `GET` y `HEAD` fuera de `/api` y `/_serverFn` se sirven primero desde `ASSETS`, lo que cubre las páginas prerenderizadas. Un 404 pasa al handler de TanStack Start.
4. Cuando hay que actualizar la cookie de idioma, el Worker la añade a la respuesta. Las respuestas HTML reciben además una cabecera `Link` de precarga para las fuentes del idioma, que Cloudflare envía como Early Hints (consulta Ajustes de la zona más abajo).
5. Las respuestas HTML pasan por los handlers de documentos de las áreas. El del área de licencias añade los precios regionales: cuando el país de `cf-ipcountry` cumple los requisitos para un descuento por paridad de poder adquisitivo, un `HTMLRewriter` añade los atributos del descuento a `<html>` y la respuesta pasa a ser `private, no-cache`.
6. Cada respuesta, incluidas las redirecciones, las llamadas a la API y los archivos multimedia, recibe las cabeceras de seguridad de [Seguridad y endurecimiento](/docs/features/security), y cada respuesta HTML, renderizada o prerenderizada, recibe una política de scripts con un nonce propio, que Cloudflare también entrega a los scripts que inyecta. Los archivos que no pasan por el Worker reciben el mismo conjunto de `public/_headers`.

`src/server.ts` no nombra ningún área: cada área declara sus handlers de peticiones y de documentos en `src/data/<area>.worker.ts`, y `src/data/worker.entries.ts` los reúne (consulta [Lo que aportan las áreas](/docs/architecture/platform-layer#what-the-areas-add)).

## Ajustes de la zona

Dos ajustes de la zona afectan a todas las páginas. Ambos están en **Speed** > **Settings** > **Content Optimization** del panel de Cloudflare:

- **Early Hints**: activado. Cloudflare guarda la cabecera `Link` de la última respuesta de una página y la envía como respuesta `103 Early Hints` mientras el Worker prepara la siguiente respuesta para la misma URL, de modo que el navegador empieza antes a descargar las fuentes. La cabecera solo nombra las fuentes, porque Cloudflare también la reenvía después de un despliegue; consulta [Rendimiento](/docs/conventions/performance).
- **Speed Brain**: desactivado. Añade una cabecera `Speculation-Rules` que pide a Chromium precargar un enlace que el visitante está a punto de abrir, pero Cloudflare se niega a precargar una URL que ejecuta un Worker, y aquí todas las páginas lo hacen (`run_worker_first`), así que cada precarga falla con `503` y `cf-speculation-refused: prefetch refused: disabled for worker requests`. Cloudflare también indica que no admite políticas con `'strict-dynamic'` y nonces, como esta. Desactivarlo no cuesta nada: TanStack Router ya carga el código y los datos de un enlace bajo el puntero (`defaultPreload: "intent"`) y los de cada enlace de la cabecera en cuanto una página queda inactiva, y lo abre sin pedir un documento nuevo. En el plan Free, Speed Brain está activado por defecto.

## Despliegue

`bun run deploy:preview` y `bun run deploy:production` ejecutan `scripts/verify-bindings.ts`, que rechaza los bindings que faltan y los ID de D1 y KV de marcador de posición, después `scripts/prepare-deploy-secrets.ts`, que rechaza un valor vacío o de marcador de posición entre los secretos que declara `wrangler.jsonc`, después `scripts/run-deploy-checks.ts`, que ejecuta la comprobación de despliegue de cada área, hoy `auth:verify:<environment>`, que comprueba el formato de los identificadores de cliente OAuth, y `polar:verify:<environment>`, que compara con el código la organización de Polar del entorno, y después la compilación correspondiente, las migraciones de D1 del entorno, `wrangler deploy` de `dist/server/wrangler.json` con esos secretos y `scripts/verify-deployment.ts`, que comprueba el sitio desplegado. Los buckets `MEDIA` se vinculan por nombre y deben existir antes del primer despliegue; créalos con `wrangler r2 bucket create`. Las compilaciones prerenderizan las páginas públicas y ejecutan `scripts/verify-build.ts` y `scripts/optimize-prerendered-html.ts`. Consulta [Desplegar una preview](/docs/getting-started/deploy-preview), [Scripts del proyecto](/docs/tooling/scripts) y [CI/CD](/docs/tooling/ci-cd).

Cada build compila el Worker dos veces. El primer Worker contiene todas las páginas y prerenderiza las públicas. Después del prerenderizado, `scripts/deployed-worker.ts` vuelve a compilar el Worker que se despliega sin lo que solo necesita el prerenderizado: cada importación de una página compilada de la documentación o del blog se resuelve a un único módulo que lanza un error, y se omiten las traducciones que solo usan la landing y las páginas legales. Las páginas prerenderizadas se sirven desde `ASSETS`, y las navegaciones en el cliente leen los índices de la documentación y del blog y renderizan el MDX desde los chunks del navegador, así que el Worker desplegado nunca lee el contenido. `scripts/verify-build.ts` hace fallar el build si una página de la documentación o una entrada publicada del blog no se prerenderizó, y si algún archivo del Worker desplegado contiene un módulo de la documentación o del blog.
