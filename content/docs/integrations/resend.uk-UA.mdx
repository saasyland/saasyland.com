`src/integrations/resend/resend.config.ts` експортує `resendClient`, який створює клієнт Resend з `RESEND_API_KEY` під час кожного надсилання листа: SDK Resend викидає помилку без ключа, тож збірці, попередньо відрендереній сторінці чи запиту, що не надсилає листів, ключ не потрібен. `resend.utils.ts` експортує `sendEmail` — єдину функцію, яка надсилає листи. `from` типово дорівнює `RESEND_EMAIL_FROM`, обов'язкова опція `idempotency` вказує призначення листа й токен, що його ініціював, а `sendEmail` перетворює їх на ключ `${purpose}/${sha256Hex(token)}`, який не дає Resend надіслати повторений запит двічі й не перевищує ліміт Resend у 256 символів, а помилка Resend викидається як виняток. Обидва файли призначені лише для сервера. Кожен модуль, що надсилає листи, називає свої призначення у власному `<module>.constants.ts`, як-от `VERIFICATION_EMAIL_PURPOSE` у `verification.constants.ts`, а `email-purposes.test.ts` не проходить, коли два модулі використовують те саме призначення. Сценарії використання передають ту саму назву як `kind` ліміту на одержувача.

## Шаблони та сценарії використання

Шаблони в `src/presentation/emails/` — це компоненти React Email, що містять лише розмітку. Кожен експортує константу `*_NAMESPACE`, отримує `locale` і `messages` як пропси та перекладає за допомогою `createTranslator` з use-intl. Сценарій використання, який надсилає лист, отримує локаль від свого викликача (лист підтвердження читає її з callback-URL), завантажує повідомлення, рендерить шаблон і викликає `sendEmail`:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await sendEmail({
  idempotency: { purpose: VERIFICATION_EMAIL_PURPOSE.VERIFY_EMAIL, token: crypto.randomUUID() },
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

Better Auth викликає перші п'ять сценаріїв використання напряму зі своїх хуків в `auth.server.ts`. Сповіщення про розсилку надходить власникові сайту англійською після підтвердження підписки. Обробник `order.paid` розділу ліцензій надсилає підтвердження покупки мовою, збереженою в замовленні, а для замовлення ліцензії, клієнт якого не відповідає жодному обліковому запису, — власникові сайту англійською сповіщення про таке замовлення. На заяву про відмову від договору надсилається підтвердження отримання мовою сторінки, з якої її надіслано, а власник сайту отримує сповіщення англійською. Посилання в листах будуються за допомогою `localizePathname`, тож вони відкриваються в локалі листа. `createInvitation` і `resendInvitation` надсилають запрошення мовою, яку для нього вибрав адміністратор.

Сценарії використання для підтвердження адреси, скидання пароля, наявного облікового запису й підтвердження розсилки спершу викликають `withinRecipientRateLimit` з `src/lib/rate-limit.ts`: ліміт листів кожного типу на адресу за годину — <RepositoryFact name="recipientEmailsPerHour" />, з ключем за хешем SHA-256 адреси. Понад ліміт вони пропускають лист без помилки. `sendInvitationEmail` перевіряє те саме обмеження, але після його перевищення завершується помилкою `TOO_MANY_REQUESTS`, тож адміністратор бачить помилку.

## Тестування

Vitest мокає виклики постачальника. У тестовому Worker для Playwright запити до API Resend перехоплюються замість надсилання, а `/__test/emails?to=<address>` повертає перехоплені листи.
