Todos los archivos de `src/routes` tienen la misma forma, así que quien conoce uno los conoce todos. Un archivo de ruta compone: declara lo que necesita la página y coloca componentes. Los widgets, formularios, diálogos y columnas de tabla viven en `src/presentation/components/custom`.

## Rutas de página

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        onReorder={({ offset, row }) => move.mutateAsync({ courseId: row.id, offset })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        search={t("table.search")}
        selectable
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.ADMIN_COURSES),
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **El componente** es una `const` local llamada `<Name>Page`, definida en primer lugar. El marcado pequeño que solo usa esta página puede ir encima como componentes locales, como hacen `CourseProgress` y `StartLink` en `_site._marketing.courses.$course.index.tsx`; cualquier cosa con sus propios datos, mutación o estado va a un archivo de componente.
- **Un espacio de nombres.** `const NAMESPACE = "pages.<feature>.<page>"` va justo encima de `export const Route` y se usa en `loadPageMetadata`, `preloadNamespaces` y `staticData`. Todo lo demás que necesite la página lo declara su layout.
- **Un solo `Promise.all`.** El loader inicia todo el trabajo a la vez: los metadatos de la página, el espacio de nombres y cada consulta que leen los componentes. Devuelve `{ locale, metadata }` para `head`. Nunca esperes a que termine una de estas tareas antes de iniciar la siguiente.
- **`head: pageHead(ROUTES.X)`** construye el título, la descripción, la URL canónica y las URL alternativas a partir de los metadatos del archivo del espacio de nombres.
- **Las rutas de URL salen de `ROUTES`**, en `src/routes.ts`, que reúne las rutas de todas las áreas (consulta [Rutas y navegación](#paths-and-navigation)); nunca escribas una ruta como literal.

Una página cuyo título sale de un registro espera ese registro y construye su head a partir de los datos del loader, como hace `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  head: ({ loaderData }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  pendingComponent: AdminCourseEditorPending,
})
```

## Rutas de layout

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Un layout declara `const NAMESPACES = [...] as const` encima de `export const Route` y lo precarga. Cuando no tiene ninguno, omite la opción; no existe `namespaces: []`.
- Un layout nombra en sus `NAMESPACES`, como cadenas sin más, todos los namespaces que necesitan sus páginas y sus componentes, incluidos los de otras funcionalidades. `/app` enumera `pages.license`, `pages.withdrawal` y `withdrawal.validations`, porque su resumen muestra la tarjeta de licencia y la oferta y su página de licencia muestra la tarjeta de desistimiento; `/admin/users` enumera `pages.admin.customers`, `pages.admin.orders` y `pages.admin.users.license`; y `/_site/_marketing` y `/_site/docs` enumeran `auth.validations`, porque sus pies muestran el formulario del boletín, y el layout de marketing, también `withdrawal.validations`. Al dejar fuera una funcionalidad se borran sus archivos de mensajes, y la regla de poda borra cada cadena que nombra uno de ellos ([Pruebas](/docs/conventions/testing#tests-follow-the-features)).
- El componente, cuando el layout renderiza uno, se llama `<Name>Layout` y coloca un `<Outlet />`.
- Una guarda va en el `beforeLoad` del layout que es dueño del área: `beforeLoad: requireAdmin` en `admin.tsx`, `requireSignedIn` en `app.tsx`, ambos layouts del área de autenticación. Las guardas solo deciden la navegación; cada función de servidor sigue comprobando su propio permiso.

## Orden de las opciones

`sort-keys` está desactivada en `src/routes` porque TanStack Router infiere los tipos en el orden de declaración: los tipos de una opción salen de las opciones que tiene encima. Las opciones van en orden alfabético, salvo aquellas a través de las que el router infiere tipos, que siguen el orden de su guía de carga de datos: `validateSearch` primero, antes de todo lo que lee los parámetros de búsqueda, luego `loaderDeps`, `context`, `beforeLoad` y `loader`, y `head`, `headers` y `scripts` después de `loader`, porque leen sus datos. Así `head` recibe el tipo que devuelve el loader tal cual, sin ningún tipo escrito a mano, y `code-style/route-option-order` hace fallar una ruta que declara estas opciones en otro orden:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Nunca escribas en línea un array o un objeto de datos dentro de `createFileRoute`; decláralo encima como una constante.

## Parámetros de búsqueda

`validateSearch` es un `zod.object` construido con los helpers de `src/lib/search-params.ts`:

| Helper                            | Valor cuando el parámetro falta o está mal formado | Uso                                            |
| --------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| `searchText()`                    | `undefined`                                        | Tokens, correos electrónicos, códigos de error |
| `searchFlag()`                    | `undefined`                                        | Booleanos                                      |
| `searchParam(schema)`             | `undefined`                                        | Cualquier otro esquema, como una ruta          |
| `searchChoice(choices, fallback)` | `fallback`                                         | Una pestaña o una vista                        |

Un texto ausente se queda en `undefined`, así que un valor por defecto nunca se cuela en una URL que construye el router. Un parámetro `searchChoice` va acompañado de `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, que elimina el valor por defecto de la URL. Una página a la que otro sitio devuelve a los visitantes declara además `search: { middlewares: [onlyDeclaredSearch(schema)] }` con su propio esquema, como hacen `/app` y `/app/license` para el pago de Polar: el router construye entonces su dirección solo con los parámetros declarados, y el servidor redirige una dirección que lleva cualquier otro parámetro a la misma dirección sin él, antes de que una comprobación o la página lo lean. Nunca escribas a mano comprobaciones `typeof search["x"] === "string"`; añade un helper cuando haga falta un nuevo tipo de campo. Cuando un hijo necesita un parámetro que la página ha validado como presente, la página estrecha su tipo y se lo pasa, como `auth.reset-password.tsx` pasa `token` a `ResetPasswordForm`. Las páginas que leen los mismos parámetros comparten un esquema en el `.zod.ts` del módulo que leen, que también parsean sus esqueletos, como hacen `/app/license` y la parte del resumen que aporta el área de licencias con `licenseSearchSchema` (`src/modules/license/license.zod.ts`).

## Esqueletos

La navegación debe sentirse instantánea, así que cada ruta que renderiza una página tiene un `pendingComponent` que la reproduce: la misma disposición, las mismas tarjetas y el mismo número de filas.

- Los esqueletos viven en el archivo pending del área (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) y usan `Skeleton` de shadcn.
- Los esqueletos están en el script de entrada de cada página, así que un esqueleto importa `Skeleton`, las primitivas de shadcn, otros esqueletos y las constantes que fijan sus longitudes, nunca un formulario ni el archivo que lo contiene; `pending-imports.test.ts` falla cuando alguno llega a `@tanstack/react-form` (consulta [Rendimiento](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Un marcador de texto lleva el token tipográfico real más `h-lh scale-y-70`, para que tenga la altura de la línea que sustituye: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- La longitud de las listas sale de las constantes que usa la página: `DataGridPending` en `data-grid-pending.tsx` dibuja por defecto `DEFAULT_PAGE_SIZE` filas, el tamaño de página de todas las tablas de administración.
- El esqueleto de un layout renderiza el `pendingComponent` de la primera ruta coincidente por debajo del layout que define uno, que `usePagePending(layout)` de `src/hooks/use-page-pending.ts` lee del árbol de rutas: `AdminPending`, `AppPending`, `AuthPending` y `MarketingPending` en sus layouts, y `AdminUsersPending` y `AdminCourseSectionPending` un nivel más abajo. Por eso, la ruta de una página es el único lugar que nombra su esqueleto, sea cual sea el layout que lo muestre; `/admin/users`, que redirige a `/admin/users/all`, fija el esqueleto de esa página.
- No hay un `defaultPendingComponent` para todo el router. `src/router.tsx` fija `defaultPendingMs` en <RepositoryFact name="navigationPendingMs" unit="millisecond" /> y `defaultPendingMinMs` en <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, ambos de `src/data/navigation.constants.ts`: una navegación que no ha terminado pasado el primero muestra el esqueleto de la ruta, y el esqueleto desaparece en cuanto la página está lista, sin quedarse ni un momento más. Las rutas mantienen estos valores; consulta [Rendimiento](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) para ver las mediciones que los respaldan.
- Las páginas de la documentación dibujan sus esqueletos dentro del layout de la documentación: `DocsIndexPending` y `DocsPagePending` ocupan las áreas de la cuadrícula del artículo y de la tabla de contenidos de Fumadocs, así que una navegación entre páginas de la documentación mantiene la barra lateral en pantalla. El componente de la página renderiza el MDX en su propio `<Suspense key={path}>`, así que la barra lateral funciona antes de que cargue el chunk MDX de la página, y una navegación reemplaza el HTML del servidor de la página anterior en lugar de hidratarlo con los datos de la siguiente.

## Enlaces

- Los enlaces del router reciben una constante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, o un patrón de ruta con `params` para las rutas dinámicas. `LinkButton` y `SidebarMenuLink` de shadcn reciben `to` de la misma manera, y `AnchorButton` recibe un `href` para una dirección fuera del árbol de rutas.
- Nunca añadas el prefijo de idioma a un enlace del router; lo añade la reescritura del router. Una URL completa en el idioma actual, para un valor que sale del router como cadena, se obtiene de `router.buildLocation({ ... }).publicHref`, que es como `use-auth-redirect.ts` construye sus enlaces de inicio de sesión. `localizePathname` es para las URL que se construyen fuera de un contexto de router o para otro idioma: correos, destinos de redirección de Better Auth, enlaces dentro de MDX y el selector de idioma.

## Rutas y navegación [#paths-and-navigation]

Cada ruta y cada entrada de menú se escribe una sola vez, en una sola lista, y una funcionalidad que se puede dejar fuera, como los cursos, los productos o las páginas legales, entra en esa lista como un elemento que nombra su propia ruta. Al dejar fuera la funcionalidad se borran sus archivos y sus nombres, y con ellos cada elemento que nombra alguno, así que las listas no necesitan un archivo por funcionalidad ni un barrel. Así es como la CLI `saasyland` monta un proyecto a partir de capas de plantillas. Solo `scripts/features.ts`, que la aplicación nunca carga, enumera las funcionalidades opcionales con sus archivos y las rutas que les pertenecen, para que `bun run check:features` pueda comprobar el sitio sin cada una de ellas ([Pruebas](/docs/conventions/testing#tests-follow-the-features)).

| Qué                                                  | Se declara en                                                                                                                                                                                                              | Se lee de                                                                                                        |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Rutas                                                | `src/routes.ts`: un `export const` por ruta                                                                                                                                                                                | `import * as ROUTES from "~/src/routes"`                                                                         |
| Rutas renderizadas en cada petición                  | `REQUEST_RENDERED_ROUTES` en `src/routes.ts`                                                                                                                                                                               | `isRequestRenderedRoute` en `src/routes.ts`                                                                      |
| Entradas de menú                                     | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` y `FOOTER_NAVIGATION` en `src/data/navigation.ts`, en el orden en que se muestran | Las barras laterales, la cabecera, el pie, la paleta de comandos y el panel                                      |
| Namespaces de layout                                 | `NAMESPACES` en la ruta de layout                                                                                                                                                                                          | El loader del layout y `staticData`                                                                              |
| Listas de la administración y del espacio de trabajo | `DASHBOARD_STATS`, `DASHBOARD_PANELS`, `COMMAND_SEARCHES`, `USER_TABS`, `USER_PROFILE_SECTIONS` y `ACCOUNT_DELETION_NOTICES`, cada una en el componente que la renderiza                                                   | Ese componente, su esqueleto y la ruta que carga sus datos                                                       |
| Comprobaciones del sitio publicado                   | `LIVE_SITE_CHECKS` en `src/lib/deployment.ts`                                                                                                                                                                              | `verifyDeployment` ([Plataforma y pruebas](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)) |

`src/routes.ts` declara todas las rutas y no importa nada, porque lo cargan todos los entornos de ejecución: el navegador, el Worker en cada arranque en frío, los scripts de Bun, Playwright, `vite.config.ts` y el proyecto de Remotion. Cada archivo lo importa como un único espacio de nombres, `import * as ROUTES from "~/src/routes"`, así que cada ruta conserva su tipo literal y `<Link to={ROUTES.COURSES}>` se sigue comprobando contra el árbol de rutas. Una ruta construida a partir de otra, como `BLOG_FEED` a partir de `BLOG`, va detrás de aquella de la que se construye.

El Worker y la compilación llevan sus listas igual: `REQUEST_HANDLERS` y `DOCUMENT_REWRITES` en `src/server.ts` y `VITE_PLUGINS` en `vite.config.ts` también son listas literales, en las que una funcionalidad opcional entra como un elemento.

`src/data/navigation.ts` contiene los siete menús como listas literales, cada entrada con su página en `to`, la clave completa de su mensaje en `label` y, en la consola de administración y el espacio de trabajo, su icono de `lucide-react`. El menú de administración agrupa sus entradas bajo un grupo de la barra lateral, con `key` de `ADMIN_NAVIGATION_GROUP`, y el pie, sus enlaces bajo una columna, con `key` de `FOOTER_COLUMN`. El archivo solo importa `lucide-react`, `~/src/routes` y `~/src/data/navigation.constants`, porque el proyecto de Remotion lee el menú de administración y su job de CI solo instala los paquetes propios de Remotion; `src/__test__/source-layout.test.ts` falla cuando importa cualquier otra cosa. La consola de administración y el espacio de trabajo de clientes solo existen con inicio de sesión, así que sus entradas nombran las rutas del área de autenticación y desaparecen con ella, igual que **Iniciar sesión** en la cabecera y en el pie:

```ts title="src/data/navigation.ts"
export const HEADER_NAVIGATION: readonly SiteEntry[] = [
  { hash: MARKETING_SECTION_IDS.PRICING, label: "navigation.core.header.pricing", to: ROUTES.HOME },
  { label: "navigation.courses.header.courses", to: ROUTES.COURSES },
  { label: "navigation.content.header.blog", to: ROUTES.BLOG },
  { label: "navigation.content.header.docs", to: ROUTES.DOCS },
  { label: "navigation.auth.header.signIn", signedIn: { label: "navigation.auth.header.account" }, to: ROUTES.SIGN_IN },
]
```

Un sitio creado sin la funcionalidad de cursos no tiene `ROUTES.COURSES`, así que la regla de poda borra la entrada **Cursos** de la cabecera, y un grupo o una columna que se quede vacío desaparece con ella, como la columna legal del pie en un sitio sin las páginas legales.

Una entrada de la cabecera o del pie de página puede nombrar una etiqueta `signedIn` que sustituye la suya para un visitante con sesión iniciada, y su enlace lleva entonces a su espacio de trabajo: `/admin` para una cuenta con acceso de administración, `/app` para todas las demás. `Navigation`, `MobileMenu` y `Footer` leen los dos menús de `useSiteNavigation` (`src/hooks/use-site-navigation.ts`), que apunta las entradas `signedIn` al espacio de trabajo en cuanto lo conoce y, si no, devuelve las listas sin cambios. Toma el espacio de trabajo del único hook de su `WORKSPACE_HOOKS`, `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`), que lo decide a partir del rol de la sesión con `hasPermission` y el permiso `admin: ["access"]` que comprueba `requireAdmin`; un proyecto sin inicio de sesión no tiene ningún hook, así que sus menús quedan sin cambios.

La etiqueta se elige antes de que se ejecute ningún script. `SiteEntryLabel` (`src/presentation/components/custom/site-entry-label.tsx`) renderiza las dos etiquetas de una entrada así, y la variante `signed-in` de `globals.css` muestra **Tu cuenta** en lugar de **Iniciar sesión** en cuanto `<html>` lleva `data-session`. Solo ocupa espacio la etiqueta visible, de modo que el enlace mide lo que su propio texto en todos los idiomas y tiene la misma separación que los demás enlaces de la cabecera. El Worker pone ese atributo en cada página HTML que devuelve a una petición que lleva la cookie de sesión de Better Auth (`markSession`, consulta [Caché y SSR](/docs/architecture/caching-and-ssr#prerendering)), así que una página prerenderizada llega ya con la etiqueta correcta y ningún enlace se mueve mientras la página carga. Mientras no se conoce la sesión, el enlace lleva a `/auth/sign-in`, que envía a un visitante con sesión iniciada a su espacio de trabajo y muestra el formulario a cualquier otro. Tras la hidratación, `useVisitorWorkspace` pide la sesión solo en una página que el Worker ha marcado, apunta el enlace al espacio de trabajo y mantiene la marca al día con la sesión: la quita cuando la sesión que hay detrás de la cookie ha terminado y la pone cuando el visitante inicia sesión sin recargar la página. Un navegador sin sesión no pide nada, aunque conserve la cookie de Better Auth con el último método de inicio de sesión, que sobrevive al cierre de sesión para que la página de inicio de sesión pueda marcar el método como **Usado la última vez**. Cada menú da a sus enlaces como clave su posición en la lista, así que React cambia el mismo enlace en lugar de sustituirlo, y una pulsación que empieza mientras se carga la sesión llega igualmente a él. Hasta que una parte de la página se ha hidratado, `useVisitorWorkspace` no devuelve nada, porque `useHydrated` responde con el valor del servidor mientras React hidrata: un pie de página que se hidrata después de que llegue la sesión muestra el mismo HTML que el servidor y cambia después, en lugar de romper la hidratación.

Cada entrada del panel de administración abre una pantalla que funciona con datos reales, y la página de inicio las cuenta todas. Una pantalla cuyos datos aún no tienen origen no recibe ninguna entrada (consulta [Panel de administración](/docs/features/admin-dashboard#real-data-only)).

La barra lateral de la app de clientes contiene la entrada **Licencia** de la venta de licencias y la entrada **Facturación** del área de facturación, y sus recursos, la **Documentación** del contenido, encima de la dirección de soporte. La base solo necesita `/` y `/api`, y **Precios** en la cabecera, la única entrada con `hash`, que enlaza con la sección de precios de `/`.

Una estadística del panel en `DASHBOARD_STATS` tiene un `prefetch`, que ejecuta el loader de `/admin`, y un hook `useValue`, al que `DashboardStats` llama para leer el número.

`APP_STATEMENTS`, en `auth.access.ts`, define las declaraciones de permisos, una por recurso, y `scripts/features.ts` nombra las declaraciones de una funcionalidad que se puede omitir, como `APP_STATEMENTS.course`, para que omitirla las borre (consulta [Roles y permisos](/docs/guides/roles-and-permissions)).

Las listas de `src/data/navigation.ts` tienen un tipo declarado de `src/data/navigation.constants.ts`, como `IconEntry` o `SiteEntry`, así que una lista cuyas entradas deja fuera un proyecto, como las acciones del panel sin el área de pagos, es una lista vacía que sigue pasando la comprobación de tipos. `navigation.test.ts` comprueba que el `to` de cada entrada es una ruta del árbol de rutas y que ningún menú nombra dos veces una página o una etiqueta.

El `label` de una entrada es la clave completa de su mensaje, como `navigation.courses.admin.courses`, y el mensaje vive en el archivo de la funcionalidad dueña de la página, `messages/<locale>/navigation.<feature>.json`, así que al dejar fuera la funcionalidad se borran con ella sus etiquetas. Un componente lo renderiza con `t(entry.label)` de `useTranslations()`. Una sección de administración etiqueta sus subpáginas para las migas de pan en el `breadcrumbs` de su entrada, del segmento de la ruta a la clave, como `create` a `navigation.courses.breadcrumbs.create`. Una pestaña de la gestión de usuarios, una búsqueda de la paleta de comandos y una estadística del panel también nombran la clave completa de su etiqueta, como `navigation.team.userTabs.invitations`, `navigation.auth.search.users` y `dashboard.courses.learners`, y un panel del dashboard lee sus textos bajo su `key` en `dashboard.<feature>.json`. Los dos tipos de archivo son espacios de nombres raíz, así que cualquier menú puede etiquetar cualquier entrada. Lo que pertenece al propio menú se queda en su espacio de nombres: `groups.<group>` en `pages.admin.sidebar`, `columns.<column>` en `components.custom.footer` y la llamada a la acción, el botón del menú y el enlace de salto de la cabecera en `components.custom.navigation`. `navigation.test.ts` falla cuando a una entrada, a una variante con sesión iniciada, a una miga de pan, a una pestaña de la gestión de usuarios o a una búsqueda de la paleta de comandos le falta el mensaje en algún locale, y `admin-dashboard.component.test.tsx`, cuando le falta a una estadística.

Las páginas que se renderizan en el Worker en cada solicitud, como `/admin`, `/auth` o `/courses`, figuran en `REQUEST_RENDERED_ROUTES`, en `src/routes.ts`. El plugin de TanStack Start en `vite.config.ts` las excluye del prerenderizado con `shouldPrerender` (`src/lib/prerender.ts`), que llama a `isRequestRenderedRoute`, así que tampoco están en el sitemap de las páginas, y `buildPageHead` les asigna la tarjeta del sitio salvo que la ruta pase una imagen propia. Renderizarse en cada solicitud no deja una página fuera de los resultados de búsqueda: las páginas de los cursos figuran en un sitemap que el Worker escribe desde D1 (consulta [Búsqueda y vistas previas en redes sociales](/docs/features/seo#course-sitemap)). Vite no resuelve el alias `~` mientras carga su propia configuración, así que `prerender.ts` importa `src/routes.ts` por ruta relativa.
