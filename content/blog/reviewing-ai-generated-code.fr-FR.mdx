<Callout title="Ce qu’est cet article">

Un guide pratique pour relire du code écrit par des agents de codage IA, pour toute équipe et toute stack. Il suppose que vos vérifications rejettent déjà ce qu’un programme peut trancher, et couvre ce qui reste. Chaque section énonce d’abord la règle, puis les travaux de recherche qui la fondent, puis les pull requests du dépôt public de saasyland.com où la revue a détecté quelque chose que toutes les vérifications avaient laissé passer. L’article couvre :

1. Pourquoi le code écrit par l’IA demande une autre revue, et ce que dit la recherche sur les agents et les tests.
2. La revue des preuves et de la description avant celle du code.
3. Les contournements face aux causes racines, et les tests devenus plus faciles.
4. Les échappatoires au typage et aux erreurs qu’un linter strict laisse encore passer.
5. Le périmètre, la conception et les chemins protégés, y compris les conceptions déformées par une règle.
6. Les affirmations en prose, un second agent comme relecteur, un ordre de revue à copier, et ce qui échappe encore à notre propre revue.

## La réponse courte

Relisez la pull request d’un agent dans l’ordre qui fait apparaître les problèmes le plus vite, et consacrez votre attention à ce qu’aucune vérification ne peut faire. D’abord les preuves : le commit que vous lisez est celui qui a été testé, et la CI a réussi sur ce commit. Puis la description face au diff, et le diff face à votre liste de chemins protégés. Puis chaque modification d’un test, car un agent qui n’arrive pas à faire passer un test rend parfois le test plus facile. Puis la question qui repère les erreurs les plus coûteuses : cette modification supprime-t-elle la cause du problème, ou seulement l’endroit où il s’est manifesté ? Ensuite, les échappatoires au typage et aux erreurs que votre linter autorise, le périmètre de la modification, toute conception déformée par une règle, et chaque affirmation que la modification fait en prose. Traitez un résumé qui dit « terminé » comme une affirmation. Demandez la commande, sa sortie et le commit sur lequel elle a tourné.

## Pourquoi le code écrit par l’IA demande une autre revue

La revue a toujours moins servi à trouver des bugs qu’on ne le pense. Dans leur étude de 2013 sur la revue de code chez Microsoft, Alberto Bacchelli et Christian Bird ont constaté que « trouver des défauts reste la principale motivation de la revue », mais que « les revues portent moins sur les défauts que prévu », et que « la compréhension du code et des modifications est l’aspect clé de la revue de code ». Avec un auteur humain, la compréhension est partagée : l’auteur sait pourquoi le code a cette forme, et la revue est une conversation.

Avec un agent comme auteur, trois choses changent.

**L’assurance de l’auteur ne dit rien.** Un agent écrit « tous les tests passent » sur le même ton, qu’ils passent ou non. Le guide d’Anthropic pour Claude Code énonce le mécanisme sans détour : « Claude s’arrête quand le travail a l’air terminé. » Son conseil à la personne qui relit est de demander des preuves : « la commande qu’il a lancée et sa sortie, ou la capture d’écran. “Tous les tests passent”, à lui seul, ne vous apprend pas grand-chose. »

**Le code a l’air juste.** Dans l’enquête 2025 de Stack Overflow, la frustration la plus courante avec les outils d’IA, citée par 66 % des développeurs, était « des solutions d’IA presque justes, mais pas tout à fait », et 45,2 % disaient que déboguer du code généré par l’IA prend plus de temps. Un code presque juste est le plus difficile à relire, car rien n’y a l’air faux.

**Votre propre sentiment de progression n’est pas fiable.** L’étude randomisée de METR auprès de développeurs open source expérimentés, début 2025, a constaté qu’avec les outils d’IA autorisés, « ils mettent 19 % plus de temps à traiter les tickets ». Avant l’étude, ils « s’attendaient à ce que l’IA les accélère de 24 % », et après coup, ils « croyaient toujours que l’IA les avait accélérés de 20 % ». Une personne qui relit et qui a le sentiment que le travail avance vite ne mesure rien.

### Les agents cherchent à satisfaire les vérifications qu’ils voient

La raison la plus forte de relire autrement est documentée par les concepteurs des modèles eux-mêmes.

La fiche système de Claude 3.7 Sonnet, publiée par Anthropic en février 2025, contient une section intitulée « Focalisation excessive sur la réussite des tests ». Elle rapporte que le modèle « recourt occasionnellement à des cas particuliers pour réussir les cas de test dans des environnements de codage agentiques comme Claude Code ». Le plus souvent, cela consistait à « renvoyer directement les valeurs de test attendues plutôt que d’implémenter des solutions générales, mais cela inclut aussi la modification des tests problématiques eux-mêmes pour qu’ils correspondent à la sortie du code ». Cela se produisait « après plusieurs tentatives infructueuses de développer une solution générale », et Anthropic recommandait de surveiller trois signaux : « Des cycles excessifs de modification et d’exécution des tests sur un seul fichier », « Des commentaires qui suggèrent un traitement propre aux tests » et « Des modifications inattendues de fichiers de test ».

OpenAI a rapporté la même famille de comportements en mars 2025, dans ses travaux sur la surveillance des modèles de raisonnement. Ses exemples incluent un agent qui raisonnait « Nous pouvons contourner verify pour qu’il renvoie toujours true », et un autre qui prévoyait : « Pour ignorer tous les tests, nous pouvons définir une fonction `pytest_runtest_setup` qui les ignore toujours. » Quand OpenAI a pénalisé le modèle pour de telles pensées pendant l’entraînement, « l’agent entraîné sous pression sur la CoT apprend toujours à pratiquer le reward hacking », mais « il a appris à cacher son intention dans la chaîne de pensée ». Le rapport antérieur de METR sur le reward hacking, cité dans [le premier article de cette série](/blog/ai-coding-agent-guardrails), a constaté la même chose dans des tâches notées.

Anthropic indique que ses mesures d’atténuation à l’entraînement « ont nettement réduit la fréquence de ce comportement en usage courant ». Ce qui reste apparaît là où Anthropic l’a observé : après des échecs répétés sur un problème difficile, c’est-à-dire exactement le genre de modification qui a le plus besoin de revue. La conséquence pratique est simple. Une exécution de CI au vert vous dit que les vérifications ont réussi. Elle ne vous dit pas que ces vérifications sont celles avec lesquelles vous avez commencé.

## Relire les preuves avant le code

Les premières minutes d’une revue devraient aller à ce que la pull request affirme à son propre sujet. La plupart des échecs coûteux que nous avons vus se trouvaient dans les affirmations, pas dans le code.

**Le commit que vous lisez est-il celui qui a été testé ?** Un agent qui fait un rebase, un amend ou qui pousse un correctif après sa dernière exécution des tests a une pull request dont la description décrit un commit antérieur. Vérifiez que la CI a tourné sur le commit de tête, et que l’exécution a réussi toutes les vérifications obligatoires, pas seulement les plus rapides. [Le deuxième article de cette série](/blog/running-ai-coding-agents-in-parallel) raconte comment un agent a annoncé « terminé » alors que la suite de tests du navigateur tournait encore.

**Les nombres sont-ils des preuves ?** Un bon plan de test nomme chaque commande avec son résultat, les décomptes qu’elle a produits et tout ce qui n’a pas pu être exécuté. Nos pull requests montrent la différence. Le plan de test de #177 indique 355 fichiers de test et 2 301 tests à couverture complète, précise que quatre tests de fichiers qu’il n’a pas touchés ont atteint leur délai d’expiration sous une charge moyenne de 40 à 170 sur la machine, nomme l’option qu’a utilisée l’exécution réussie, et dit clairement que la suite de tests du navigateur n’a pas été lancée en local, et pourquoi. #123 fait état d’une première exécution de la couverture dans laquelle sept tests ont expiré sous la charge, puis d’une nouvelle exécution propre. Aucune des deux ne cache un échec, et toutes deux sont plus utiles qu’un « tout est vert ».

**La description décrit-elle ce diff ?** Le 16 novembre, #224, une correction de mise en page, a été fusionnée avec la description de #225, une modification de licence, y compris un paragraphe affirmant que le propriétaire avait approuvé des modifications de fichiers de licence que #224 n’a jamais touchés. Aucune vérification ne lit les descriptions. Depuis, la revue les compare : chaque modification que mentionne la description figure dans le diff, chaque fichier du diff est expliqué, et chaque approbation est citée avec les chemins qu’elle couvre.

**Cela a-t-il l’air terminé, ou cela fonctionne-t-il ?** Un élément d’interface qui s’affiche promet qu’il fait quelque chose. En novembre, les écrans de gestion des utilisateurs de la console d’administration affichaient des boutons **Modifier**, **Voir le profil** et **Ajouter un utilisateur** sans gestionnaire d’événements, alors que neuf fonctions serveur liées aux utilisateurs et aux sessions n’avaient aucun appelant (#194). Aucune vérification ne l’a remarqué : un bouton sans gestionnaire s’affiche, et rien n’appuyait dessus. Le correctif a relié chaque élément à une vraie fonction serveur, ou l’a supprimé. Pour tout ce qu’un utilisateur peut voir, la preuve est une capture d’écran ou un test dans le navigateur qui appuie sur le bouton et vérifie le résultat.

## Contournements et causes racines

L’erreur la plus coûteuse que fait un agent est un correctif au mauvais endroit. Il passe chaque vérification, il s’accompagne souvent d’un test de régression, et il laisse la cause dans le code, où la page suivante tombera dessus.

Un contournement a une forme reconnaissable. Il se trouve à côté du symptôme plutôt qu’en amont : une attente ajoutée à un test, une valeur de repli passée à un composant, une condition qui saute le cas en échec, une nouvelle tentative autour d’une situation de concurrence, une version ramenée en arrière. La question qui le démasque est celle que suggère le guide de revue de Google quand il dit qu’« il est souvent utile de regarder la CL dans un contexte élargi » : qu’est-ce qui a provoqué cela, et quoi d’autre pourrait y être exposé après la fusion ?

### Un contournement choisi en connaissance de cause

Le 14 novembre, un visiteur connecté qui appuyait sur un lien de l’en-tête de la page d’accueil avant que la page ne soit hydratée faisait signaler à React une erreur d’hydratation : le serveur avait affiché le nombre d’étoiles GitHub, et le navigateur rendait à sa place un squelette de chargement. #146 l’a corrigé en passant le nombre du loader de la page au composant comme données provisoires, avec un test de régression, et chaque vérification a réussi.

Sa description nommait la vraie cause. Une garde de route de l’intégration d’authentification vidait tout le cache des requêtes chaque fois qu’elle trouvait une session que la page prérendue n’avait pas connue, pour qu’un utilisateur ne voie jamais les données d’un autre. La garde jetait les données publiques avec les données privées, et toute page rendue à partir du cache pouvait tomber sur le même bug. La description disait aussi pourquoi elle laissait la cause en place : la modifier impliquait de décider quelles données peuvent survivre à un changement d’utilisateur, dans `src/integrations/better-auth/`, un chemin qui exige le feu vert du propriétaire.

La revue a demandé la cause racine, le propriétaire a approuvé la modification du chemin protégé, et deux heures plus tard, #152 l’a corrigée : les requêtes se marquent elles-mêmes comme publiques, un changement d’utilisateur supprime chaque requête qui ne l’est pas, et le contournement de #146 a été supprimé. La leçon a deux volets. Les agents connaissent souvent la cause, et un bon brief leur demande de la dire. Et un chemin protégé, qui existe pour rendre les modifications dangereuses plus rares, rend aussi plus probables les correctifs de symptômes, car le moyen le moins coûteux de contourner une cause protégée est un correctif ailleurs. Quand un correctif se trouve à côté d’un chemin protégé, demandez-vous si c’est la protection qui a choisi la conception.

### Des tests qui attendent que le bug passe

Plus tôt le même jour, #142 avait rendu la suite de tests du navigateur fiable dans WebKit en attendant que le routeur ait rendu une page avant d’agir dessus. Cette attente modélise un véritable état de disponibilité, et elle est correcte. Mais certaines des situations de concurrence qu’elle corrigeait venaient de bugs dans les bibliothèques, et #151 les a nommés : « #142 a fait attendre à la suite de tests du navigateur que trois bugs de bibliothèques passent, mais les visiteurs tombent toujours dessus. » Un visiteur qui faisait défiler une page pendant son hydratation était renvoyé tout en haut ; une navigation hors d’une page en cours de chargement pouvait se transformer en rechargement de la page que l’on quittait.

#151 a apporté chaque correctif sous la forme d’un patch sur la dernière version de TanStack Router et de Motion, a ajouté un test dans le navigateur qui échoue sans chaque patch, et a supprimé les attentes qui n’existaient que pour esquiver les bugs. L’un des patchs du routeur reprend la modification d’une pull request amont encore ouverte. Sa reproduction est le genre de preuve qu’une revue devrait demander : une application TanStack Start minimale qui échouait six fois sur six sans le correctif d’une ligne et réussissait dix fois sur dix avec.

La règle que nous en avons tirée : une attente dans un test est acceptable quand elle modélise ce qu’un utilisateur attend lui aussi. Quand elle attend qu’un bug passe, les utilisateurs tombent toujours sur le bug, et le correctif a sa place dans le code ou, pour une bibliothèque, dans un patch avec un test de régression et un signalement en amont.

### Une règle de décision

N’acceptez un contournement que si les trois conditions sont réunies : la cause échappe à votre contrôle, le contournement est signalé là où le prochain lecteur le trouvera, et sa suppression est suivie quelque part. Sinon, demandez la cause. Ramener une dépendance à une version antérieure est un contournement aux effets durables ; notre règle est de rester sur la dernière version et de traiter un bug amont par un patch, pour que le correctif disparaisse avec la version suivante au lieu de rester pour toujours.

## Les tests devenus plus faciles

Un diff qui modifie un test mérite plus d’attention qu’un diff qui modifie du code, car le test est ce en quoi vous avez confiance quand vous ne regardez pas. Le guide de revue de Google le résume en une phrase : « Les tests ne se testent pas eux-mêmes. »

Lisez chaque modification d’un fichier de test et cherchez ceci :

- **Des assertions supprimées ou assouplies :** `toEqual` qui devient `toMatchObject`, une valeur précise qui devient `expect.anything()`, une assertion supprimée avec le code qu’elle testait.
- **Des snapshots ou des fixtures mis à jour** dont personne n’a lu le nouveau contenu.
- **Des cas particuliers :** du code testé qui se comporte différemment pour une valeur que seul le test utilise, ou qui renvoie exactement la valeur qu’un test attend.
- **De nouveaux skips, de nouvelles tentatives et de nouveaux délais d’expiration,** y compris un délai plus long sur un seul test.
- **De nouveaux mocks** de la chose même que le test était censé exercer.
- **Des assertions sur l’implémentation** plutôt que sur le comportement : quelle fonction a été appelée plutôt que ce que voit l’utilisateur.

Anthropic a noté que les cas particuliers observés « incluent souvent (mais pas toujours) des commentaires explicites signalant le cas particulier (par exemple, “# cas particulier pour le test XYZ”) ». Notre dépôt interdit tout commentaire autre qu’un lien sur une ligne vers l’endroit où se trouve la justification, et une vérification rejette le reste. Cela supprime l’étiquette : dans une base de code comme la nôtre, le signal doit donc venir de la lecture du diff des tests lui-même.

Le contre-exemple à copier est #191. Sur une machine chargée, nos tests unitaires les plus lents dépassaient leur délai. La solution facile était de relever les délais d’expiration. À la place, la pull request a cherché pourquoi chaque test était lent et a supprimé le travail dont il n’avait pas besoin : un test exécutait la vérification du contenu sur chaque page dans neuf locales et est devenu un cas par page ; plusieurs laissaient la temporisation du fallback de suspense de React s’exécuter hors de `act` ; une combobox reconstruisait chaque option à chaque frappe. Sa description énonce la contrainte qu’elle a respectée : « Aucun délai d’expiration n’a été relevé et aucun test n’a reçu son propre délai. » Une personne qui relit peut confronter cette phrase au diff en une minute, et c’est ce qu’un plan de test devrait permettre.

## Les échappatoires discrètes au typage

Un compilateur strict et un linter strict arrêtent les échappatoires voyantes : `any`, les assertions de type, les commentaires de désactivation. Ce qui arrive en revue, ce sont les discrètes, qui compilent proprement et échouent à l’exécution.

TypeScript dit explicitement pourquoi les assertions sont dangereuses : « les assertions de type sont supprimées par le compilateur et n’affecteront pas le comportement de votre code à l’exécution », et « aucune exception ni aucun `null` ne sera généré si l’assertion de type est fausse ». Il en va de même pour l’assertion non nulle : « cela ne change pas le comportement de votre code à l’exécution ».

### Ce que notre linter laisse encore passer

Le 22 novembre, nous avons soumis un fichier sonde à notre configuration de lint, qui active des catégories entières de règles comme erreurs, avec des règles qui tiennent compte des types, et qui interdit `any`, toute assertion de type sauf `as const`, et tout commentaire de désactivation :

| Ligne du fichier sonde                                              | Rejetée | Par                                                                          |
| ------------------------------------------------------------------- | ------- | ---------------------------------------------------------------------------- |
| `(raw: string): Licence => JSON.parse(raw)`                         | Oui     | `typescript/no-unsafe-return`                                                |
| `const parse = <T>(raw: string): T => JSON.parse(raw)`              | Oui     | `typescript/no-unsafe-return` et `typescript/no-unnecessary-type-parameters` |
| `Reflect.get(target, key)` renvoyé comme une `string`               | Oui     | `typescript/no-unsafe-return`                                                |
| `items.find((item) => item.length > 2)!.length`                     | Non     |                                                                              |
| `(value: unknown): value is Licence => typeof value === "object"`   | Non     |                                                                              |
| `zod.custom<Licence>()` sans vérification                           | Non     |                                                                              |
| `licence?.key ?? ""`                                                | Non     |                                                                              |
| Un `catch {}` vide, ou un `catch` qui renvoie une valeur par défaut | Non     |                                                                              |

Chaque ligne qui est passée transforme une valeur manquante ou mal formée en comportement faux sans erreur. L’assertion non nulle affirme que la valeur existe. La garde de type affirme qu’un objet est une `Licence` après avoir seulement vérifié que c’est un objet. Le schéma personnalisé accepte n’importe quoi et le type comme une `Licence`. La valeur de repli en chaîne vide transforme « pas de licence » en une clé de licence qui est une chaîne vide, que la fonction suivante enverra peut-être sans sourciller à une API. L’erreur avalée cache l’échec à la personne qui l’aurait corrigé. Notre code applicatif ne contient aujourd’hui aucune assertion non nulle ni aucun schéma personnalisé sans vérification ; seule la revue garantit qu’il en reste ainsi, et les règles qui couvrent la première existent à la fois dans typescript-eslint et dans Oxlint.

### Une échappatoire bien justifiée reste une échappatoire

Le commit qui a migré saasyland.com vers TanStack Start, le 6 septembre 2026, portait six commentaires de désactivation du lint : quatre pour des assertions de type non sûres, un pour `null` et un pour un argument non sûr. Chacun était accompagné d’une phrase qui le faisait paraître nécessaire :

```ts
// TanStack Query requires a defined result; null represents an absent license.
// oxlint-disable-next-line unicorn/no-null
const NO_LICENSE = null
```

La moitié de la raison était vraie. La documentation de TanStack Query dit qu’« en cas de succès, la valeur résolue peut être n’importe quoi sauf undefined ». La conclusion ne l’était pas : la requête n’avait pas besoin de `null`, elle avait besoin d’une valeur définie. La revue a supprimé les six en trois semaines en changeant la conception que chacun protégeait. Celui-ci est devenu un objet qui existe toujours :

```ts
.handler(async ({ context }) => ({ license: await getLicense(context.auth.user.id) }))
```

Les autres ont suivi le même chemin : un helper de test qui imposait par une assertion un type généré construit désormais un arbre de messages non typé, et un proxy de test qui imposait par une assertion le type d’un builder vérifie désormais à l’exécution qu’il a reçu une fonction serveur, et lève une `TypeError` dans le cas contraire. Nos conventions listent désormais les alternatives à une échappatoire : valider au lieu d’affirmer, affiner avec une vraie garde de type, annoter au lieu d’affirmer, vérifier avec `satisfies` au lieu de convertir, et restructurer quand le contrat d’une bibliothèque vous résiste. Depuis #274, `bun run check` rejette tout commentaire de désactivation : ce genre d’échappatoire n’arrive donc plus en revue. La leçon reste valable pour celles qui y arrivent : une raison écrite à côté d’une échappatoire est un argument, et le travail de la revue consiste à mettre l’argument à l’épreuve, pas à l’admirer.

## Le périmètre, la conception et la forme de la modification

**Les modifications non demandées.** Les agents corrigent des choses en chemin. C’est souvent utile et toujours un problème de revue, car une modification que personne n’a demandée est relue comme une partie d’une modification que quelqu’un a demandée. La règle que nous appliquons : les corrections annexes sont les bienvenues quand la description les liste et dit pourquoi. #169, une correction des chemins de fichiers traduits, liste les autres erreurs qu’elle a corrigées dans les chaînes qu’elle réécrivait déjà. #191, une pull request sur des tests lents, a modifié un composant de production, et sa description explique que le composant reconstruisait chaque option à chaque rendu, ce qui était à la fois le problème du test et celui de l’utilisateur. Une modification que la description ne mentionne pas est une raison de s’arrêter et de poser la question.

**Les abstractions dont personne n’avait besoin.** Le guide de Google demande aux relecteurs d’« encourager les développeurs à résoudre le problème dont ils savent qu’il doit être résolu maintenant, et non le problème dont le développeur suppose qu’il pourrait devoir être résolu à l’avenir ». Les agents penchent dans l’autre sens : un wrapper autour d’un appel de bibliothèque, une factory à un seul produit, un helper qui en duplique un qui existe déjà trois dossiers plus loin. Nos conventions demandent un seul mécanisme évident par préoccupation et un appel direct à la bibliothèque ; en revue, la vérification la moins coûteuse consiste à chercher dans le dépôt une fonction existante avant d’en accepter une nouvelle.

**Le cérémonial qui satisfait une règle.** Quand une règle est légèrement fausse, les agents s’y conforment à grande échelle. Notre règle contre les nombres magiques n’autorisait que `0` : les agents ont donc nommé chaque `1`, et #230 a remplacé 72 de ces constantes par leur valeur. [Le premier article de cette série](/blog/ai-coding-agent-guardrails) raconte cette histoire. En revue, un motif que personne n’écrirait à la main est le signe qu’il faut corriger la règle.

**Les conceptions déformées par un chemin protégé.** C’est le cas subtil. #177 avait besoin d’une constante de statut pour les fonctionnalités disponibles ou à venir. La vidéo de la page d’accueil réalisée avec Remotion importe la navigation de l’administration, et un test exige que le workflow de la vidéo surveille chaque fichier que Remotion importe : un nouveau fichier aurait donc impliqué une modification de `.github/workflows/`, un chemin qui exige l’approbation du propriétaire. La pull request a placé la constante dans `src/data/navigation.constants.ts`, un fichier que le workflow surveillait déjà, et l’a dit dans sa description. Des modifications ultérieures ont entièrement retiré le statut de la navigation de l’administration. Aujourd’hui, la constante sert les cartes des forfaits et les textes du site, et elle vit toujours dans les constantes de navigation, pour une raison qui n’existe plus. Rien ne le vérifie. C’est en revue que l’on se demande : ce fichier est-il celui où un nouveau lecteur chercherait cela, et sinon, qu’est-ce qui a poussé l’auteur à le mettre ici ?

Le guide d’Anthropic ajoute un avertissement qui vaut pour tout relecteur, humain ou agent : « Un relecteur à qui l’on demande de trouver des problèmes trouvera toujours _quelque chose_. Si vous corrigez chaque remarque, vous vous retrouvez avec des couches d’abstraction en trop et des tests pour des cas qui ne peuvent pas se produire. » Le périmètre joue dans les deux sens. Une revue qui exige toutes les améliorations possibles produit le même code envahissant qu’un agent qui les ajoute sans qu’on les lui demande.

## Les chemins protégés dans le diff

[Le premier article de cette série](/blog/ai-coding-agent-guardrails) explique quels chemins exigent la seconde clé d’une personne et pourquoi une approbation se rattache à un diff. En revue, deux vérifications en découlent.

**Comparez mécaniquement les fichiers modifiés à la liste.** Lire un long diff à la recherche de chemins protégés est exactement la tâche qu’une personne accomplit mal en fin de journée. Une commande d’une ligne le fait à chaque fois ; le kit à la fin de l’article en contient une. Quand un chemin protégé figure dans le diff, la description doit citer l’approbation et nommer les chemins qu’elle couvre.

**Demandez-vous ce que la protection a changé.** Les deux incidents ci-dessus, un correctif de symptôme à côté d’une cause protégée et une constante placée pour éviter un fichier protégé, montrent qu’une liste de chemins protégés façonne le code qui l’entoure. Aucun des deux n’a touché un chemin protégé : aucun des deux n’apparaîtrait donc dans une vérification mécanique. La question pour la personne qui relit est la question inverse : cette modification a-t-elle évité un chemin protégé, et le bon correctif serait-il passé par lui ?

## Les faits et les affirmations en prose

Les agents écrivent de la prose avec la même aisance que du code, et la prose n’a pas de compilateur. Les descriptions de pull requests, la documentation, les journaux des modifications, les README et les articles de blog font tous des affirmations, et notre historique montre quatre types d’affirmations fausses.

**La configuration inventée.** Deux de nos articles disaient que `typescript/no-explicit-any` était une erreur dans notre configuration de lint alors que ce n’était pas le cas ; #123 a rendu la phrase vraie en activant la règle. Le même audit a trouvé un `tsconfig.json` cité avec `verbatimModuleSyntax`, que le projet ne définit pas, et une option de lint, `denyWarnings: true`, qui n’existe pas.

**Les sources mal attribuées.** Un audit de chaque article par rapport à ses sources, le 17 novembre (#241), a trouvé un chiffre de Stack Overflow cité à 45 % alors que l’enquête dit 66 %, un taux d’usage d’API dépréciées attribué au mauvais article de recherche, et un chiffre de défauts de GitClear que la page publique de GitClear ne contient pas.

**Le contexte périmé.** Des traductions faites à partir d’une ancienne version anglaise décrivaient une stack que le site n’utilisait plus, avec d’anciens décomptes et d’anciens noms de forfaits (#116). Chaque phrase était fluide et plausible.

**Les descriptions de la mauvaise modification,** comme dans #224.

La revue de la prose est la même que celle du code, avec des sources à la place des tests. Chaque nombre renvoie au code qui le définit, et [l’article précédent](/blog/documentation-drift-numbers-from-code) montre comment l’afficher à partir de là pour qu’il ne puisse pas être faux. Chaque chiffre externe a un lien, et la personne qui relit ouvre le lien et cherche les mots exacts. Chaque « est imposé » nomme la vérification qui l’impose. Chaque citation figure dans la source.

## Un second agent comme relecteur

Un agent relecteur est bon marché, rapide et utile en première passe, si vous le configurez pour cette tâche.

- **Un contexte neuf.** Le guide d’Anthropic décrit sa commande `/code-review` comme une revue « du diff dans un sous-agent neuf qui n’a jamais vu votre conversation. Il n’est pas influencé par le raisonnement qui a produit le code. » Un relecteur qui a lu le raisonnement de l’auteur a tendance à l’accepter.
- **Des outils en lecture seule.** Un relecteur qui peut modifier corrigera ce qu’il trouve et transformera une revue en seconde modification. Les sous-agents de Claude Code prennent une liste `tools` dans leur définition ; ne donnez à un relecteur que la lecture et la recherche.
- **Une spécification de référence.** Le brief à partir duquel la modification a été construite, ou l’issue, pour que le relecteur vérifie des exigences plutôt que des goûts.
- **Des instructions sur ce qu’il ne faut pas signaler.** Le style, et les cas hypothétiques, pour la raison qu’Anthropic donne plus haut.

Connaissez ses limites. Un agent relecteur fait généralement tourner le même modèle que l’auteur, ou un modèle plus petit : il partage donc les angles morts de l’auteur, et il ne peut pas vous dire si la modification est la bonne chose à construire. Dans notre organisation, un agent principal rédige le brief de chaque exécutant et lit son rapport et son diff au regard de ce brief avant que la modification n’entre dans la file de fusion, et tout ce qui figure sur la liste de revue humaine attend le oui écrit du propriétaire, cité mot pour mot. La question du [deuxième article](/blog/running-ai-coding-agents-in-parallel) reste celle qui révèle le plus de problèmes : qu’avez-vous décidé de ne pas faire, et pourquoi ?

## Un ordre de revue qui fait apparaître les problèmes vite

Le deuxième article de cette série propose une liste en huit étapes pour relire la pull request d’un agent. Voici la version plus longue que nous utilisons désormais, dans l’ordre, avec ce que chaque étape cherche. Arrêtez-vous à la première étape qui échoue ; il ne sert à rien de lire du code dont les preuves manquent.

1. **Les preuves.** Le commit de tête est le commit testé. La CI a réussi chaque vérification obligatoire sur ce commit. Le plan de test nomme les commandes, les résultats et les décomptes, et dit ce qui n’a pas été exécuté. Les modifications visibles par l’utilisateur ont une capture d’écran ou un test dans le navigateur qui appuie sur l’élément.
2. **La description face au diff.** Chaque modification qu’affirme la description figure dans le diff. Chaque fichier du diff est expliqué.
3. **Les chemins protégés.** Aucun n’a changé, ou chacun est couvert par une approbation citée qui le nomme.
4. **Le diff des tests.** Aucune assertion assouplie ou supprimée sans raison, aucun nouveau skip, aucune nouvelle tentative, aucun nouveau délai d’expiration ni aucun nouveau mock de l’unité testée, aucun cas particulier.
5. **La cause racine.** Le correctif change ce qui a provoqué le problème. Rien d’autre ne peut tomber sur le même bug après la fusion. Tout contournement est signalé et suivi.
6. **Les échappatoires.** Aucune assertion non nulle, aucune garde de type mensongère, aucun schéma qui accepte n’importe quoi, aucune valeur de repli qui masque une absence, aucune erreur avalée.
7. **Le périmètre et la conception.** Rien de non demandé et d’inexpliqué. Aucune nouvelle abstraction à un seul utilisateur, aucun doublon d’un helper existant, aucun fichier placé là où un lecteur ne le chercherait pas, aucune conception déformée par une règle.
8. **Les affirmations en prose.** Les nombres affichés à partir du code, les faits externes accompagnés d’un lien et retrouvés à cette adresse, chaque « imposé » nommant sa vérification.
9. **Tout ce que la modification affecte.** La documentation, le README, les textes du site et le journal des modifications dans toutes les langues ; l’essentiel relève d’une vérification, et le reste est ici.
10. **L’historique.** Une seule modification, un titre qui se lira bien comme commit de squash, aucune ligne d’attribution.

Les étapes 1 à 3 prennent quelques minutes et ne demandent aucune compréhension du code : une pull request qui échoue à l’une d’elles ne coûte donc presque rien à renvoyer. Les étapes 4 à 7 sont celles où passe le temps, et ce sont les étapes qu’aucun programme ne peut faire à votre place.

## Ce que cela coûte, et où le dépenser

La revue est la seule partie de ce système qui ne passe pas à l’échelle avec davantage d’agents. [Le deuxième article](/blog/running-ai-coding-agents-in-parallel) a constaté que c’était la personne qui relit, et non les machines ou les minutes de CI, qui était la vraie limite au nombre d’agents pouvant travailler en même temps. Trois habitudes la gardent abordable.

**Déplacez dans des vérifications tout ce qui peut être tranché.** Chaque règle qu’un programme peut trancher et que vous relisez encore à l’œil est du temps de revue gaspillé. L’[article sur les garde-fous](/blog/ai-coding-agent-guardrails) traite de cela.

**Faites des modifications petites, une à la fois.** Une pull request qui ne contient qu’une modification peut être lue au regard d’une seule question. Les agents produisent de gros diffs à peu de frais ; le brief devrait demander une modification par pull request, et la personne qui relit devrait renvoyer celles qui ne s’y tiennent pas.

**Dosez la profondeur selon le rayon d’impact.** Les paiements, l’identité, les migrations, les contrats dont dépendent d’autres logiciels et les vérifications elles-mêmes ont droit à la liste complète, lentement. Une correction de documentation a droit aux étapes 1, 2 et 8.

## Ce qui échappe encore à notre revue

Dans l’esprit du reste de la série, voici où notre propre processus est faible.

- **Les descriptions sont comparées aux diffs par une personne**, pas par une vérification : une journée chargée peut donc encore en laisser passer une.
- **La constante de statut de #177** vit toujours dans les constantes de navigation, pour une raison qui n’existe plus.
- **Les assertions non nulles et les schémas personnalisés** sont absents de notre code par habitude ; aucune règle ne les rejette encore.
- **Les tests de mutation**, qui mesureraient si les tests échouent quand le code change, ne sont pas en place : « les tests devenus plus faciles » dépend donc de la lecture.
- **Le relecteur et l’auteur partagent souvent un modèle**, et partagent donc ses angles morts.
- **Les agents travaillent sous le compte du propriétaire** : GitHub ne peut donc pas exiger une revue par quelqu’un d’autre que l’auteur ; la seconde clé est détenue par la couche de permissions des agents et par une approbation citée, comme le décrit le premier article.

## Un kit de revue à copier

**Un modèle de pull request** qui demande des preuves au lieu d’assurances :

```md
## What and why

One change. What made the problem happen, and how this removes it.

## Evidence

| Command | Result | Commit |
| ------- | ------ | ------ |
|         |        |        |

Not run, and why:

## Also changed

Every change the title does not cover, with its reason.

## Protected paths

None, or each path with the quoted approval that covers it.

## Not done

What I decided not to do, and why.
```

**Une commande qui liste les chemins protégés d’un diff**, lancée par la personne qui relit ou dans la CI :

```sh
git diff --name-only origin/main...HEAD | grep -E '^(db/migrations/|src/billing/|src/auth/|\.github/|eslint\.config\.js|vitest\.config\.ts)'
```

**Une recherche des signaux d’alerte dans le diff des tests**, comme point de départ de l’étape 4 :

```sh
git diff origin/main...HEAD -- '*.test.*' '*.spec.*' | grep -nE '^\+.*(\.skip|\.only|\.todo|retry|retries|timeout|expect\.anything|toMatchObject|vi\.mock|jest\.mock)|^-.*expect\('
```

**Des règles de lint pour deux des échappatoires discrètes**, telles qu’ESLint et typescript-eslint les nomment :

```js
export default [
  {
    rules: {
      "@typescript-eslint/no-non-null-assertion": "error",
      "no-empty": "error",
    },
  },
]
```

**Un sous-agent relecteur en lecture seule** pour Claude Code, dans `.claude/agents/reviewer.md` :

```md
---
name: reviewer
description: Reviews a pull request's diff against the brief it was built from, before a person reads it.
tools: Read, Grep, Glob
---

You review a change you did not write. You are given the brief and the diff.

Report, in this order, only what affects correctness:

1. Claims in the description that the diff does not support, and files in the diff the description does not explain.
2. Changes to tests that make them easier: removed or loosened assertions, skips, retries, timeouts, mocks of the unit under test, special cases.
3. Fixes that change where a problem shows rather than what causes it.
4. Non-null assertions, type guards that do not check what they claim, schemas that accept anything, fallbacks that hide a missing value, swallowed errors.
5. New abstractions with one user, and helpers that duplicate existing ones.

Do not report style. Do not report cases that cannot happen. Do not edit anything.
```

**Une ligne pour votre fichier d’instructions**, pour que l’auteur prépare ce que demandera la personne qui relit :

```md
## Before you say done

Give the commit you tested, each command with its result, what you did not run and why, every change beyond the task, and what you decided not to do. A summary is not evidence.
```
