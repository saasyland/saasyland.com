## Реалізовано

- **Сесії**: сесії Better Auth у D1, префікс cookie `saasyland`, захищені cookie поза локальними режимами, дозволені хости для кожного режиму та `cf-connecting-ip` як адреса клієнта. Клієнтська сесія ніколи не містить токена.
- **Облікові записи**: обов’язкове підтвердження пошти, відкликання сесій після скидання пароля, необов’язковий TOTP з резервними кодами, ідентифікатори підтвердження зберігаються як хеші, токени OAuth зашифровано.
- **Авторизація**: `requireSignedIn` і `requireAdmin` на маршрутах; `authorized(permission)` у серверних функціях із ролями з `auth.access.ts`.
- **Обмеження запитів**: обмежувач Better Auth і middleware `withRateLimit` спільно використовують таблицю `rate_limit` у D1. `RATE_LIMITS.SENSITIVE` дозволяє 3 виклики, а `RATE_LIMITS.TOKEN` — 5 викликів за 60 секунд для кожного клієнта й дії. Листи підтвердження адреси, скидання пароля й підтвердження розсилки також обмежено трьома листами кожного типу на адресу за годину (`withinRecipientRateLimit`, з ключем за хешем SHA-256 адреси); понад ліміт лист мовчки пропускається.
- **Помилки**: middleware запитів перетворює збої на коди `AppError` (`src/modules/_core/constants/errors.ts`), тож клієнти ніколи не отримують «сирих» повідомлень сервера; компоненти показують їх через `useErrorMessage`.
- **Вебхуки й форми**: вебхуки Polar перевіряються за допомогою `POLAR_WEBHOOK_SECRET`; підписка на розсилку (`subscribeToNewsletter`) приймається лише на хостах режиму збірки з `appHostsForMode`, через HTTPS або, у режимах розробки й тестування, через HTTP (`newsletterRequestOrigin`).
- **Вхідні дані Better Auth**: `enforceInputPolicy` в `auth.hooks.ts` застосовує схеми форм до кожного ендпоінта Better Auth, який приймає пароль, ім’я, адресу пошти чи зображення, тож запити, надіслані безпосередньо на `/api/auth`, дотримуються тих самих правил; запит, що не пройшов перевірку, отримує `400` з `VALIDATION_ERROR`.
- **Медіафайли**: відеофайли зберігаються в приватному бакеті R2. Worker віддає їх лише за шляхами `/media/`, підписаними ключем HMAC, виведеним з `AUTH_SECRET`, які діють щонайменше шість годин. `getVideoPlayback` видає такі шляхи тим, хто має `video: ["read"]`; `getLessonPlayback` видає їх для опублікованого уроку, щойно `hasLessonAccess` допускає глядача, тож гості отримують їх для безкоштовних переглядів, користувачі, які увійшли, — для уроків для акаунтів, власники ліцензії Complete або Agency — для платних уроків, а адміністратори — для кожного уроку; неправильний або прострочений підпис отримує `403`.
- **Заголовки**: кожна відповідь від Worker має `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, `Permissions-Policy`, що вимикає камеру, мікрофон, геолокацію й topics, і Content Security Policy, яка забороняє вбудовування у фрейми, зміну `<base>` і плагіни. HTTPS-відповіді додатково мають `Strict-Transport-Security`. Worker задає їх у `src/server.ts`, якщо відповідь не має власних. Файли, що віддаються без Worker (`/assets/*`, `/fonts/*`, `/robots.txt`, `/llms.txt`), отримують лише заголовки з `public/_headers`: Content Security Policy, `Referrer-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options` і `X-Frame-Options`, без `Cross-Origin-Opener-Policy` і `Permissions-Policy`.

## Не реалізовано

- Content Security Policy, що обмежує скрипти й стилі: попередньо відрендерені сторінки потребували б хешу кожного вбудованого скрипта на кожній сторінці.
- Журнал аудиту, зокрема для блокувань, видалень і входу від імені інших користувачів.
- Захист від ботів або CAPTCHA в публічних формах.
- Екран входу від імені користувача ([Вхід від імені користувача](/docs/features/impersonation)).
