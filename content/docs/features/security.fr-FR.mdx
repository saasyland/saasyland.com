## Mis en œuvre

- **Sessions** : sessions Better Auth dans D1, préfixe de cookie `saasyland`, cookies sécurisés hors des modes locaux, hôtes autorisés par mode et `cf-connecting-ip` comme adresse du client. La session côté client ne contient jamais le jeton.
- **Comptes** : vérification obligatoire de l’e-mail, sessions révoquées lors d’une réinitialisation du mot de passe, TOTP facultatif avec codes de secours, identifiants de vérification stockés sous forme de hachage et jetons OAuth chiffrés.
- **Autorisation** : `requireSignedIn` et `requireAdmin` sur les routes ; `authorized(permission)` sur les fonctions serveur avec les rôles de `auth.access.ts`.
- **Limites de débit** : le limiteur de Better Auth et le middleware `withRateLimit` partagent la table `rate_limit` de D1. `RATE_LIMITS.SENSITIVE` autorise 3 appels et `RATE_LIMITS.TOKEN` 5 appels par tranche de 60 secondes, par client et par action. Les e-mails de vérification, de réinitialisation du mot de passe et de confirmation de newsletter sont aussi limités à trois de chaque type par adresse et par heure (`withinRecipientRateLimit`, avec pour clé un hachage SHA-256 de l’adresse) ; au-delà de la limite, l’e-mail est ignoré silencieusement.
- **Erreurs** : le middleware de requête transforme les échecs en codes `AppError` (`src/modules/_core/constants/errors.ts`), si bien que les clients ne reçoivent jamais de messages bruts du serveur ; les composants les affichent avec `useErrorMessage`.
- **Webhooks et formulaires** : les webhooks Polar sont vérifiés avec `POLAR_WEBHOOK_SECRET` ; une inscription à la newsletter (`subscribeToNewsletter`) n’est acceptée que sur les hôtes du mode de build issus de `appHostsForMode`, en HTTPS ou, en développement et en test, en HTTP (`newsletterRequestOrigin`).
- **Entrées Better Auth** : `enforceInputPolicy` dans `auth.hooks.ts` applique les schémas des formulaires à chaque endpoint Better Auth qui accepte un mot de passe, un nom, un e-mail ou une image, de sorte que les requêtes envoyées directement à `/api/auth` respectent les mêmes règles ; une requête non conforme reçoit `400` avec `VALIDATION_ERROR`.
- **Médias** : les fichiers vidéo restent dans un bucket R2 privé. Le Worker ne les sert que sous des chemins `/media/` signés avec une clé HMAC dérivée de `AUTH_SECRET` et valables au moins six heures. `getVideoPlayback` les émet pour les appelants qui ont `video: ["read"]` ; `getLessonPlayback` les émet pour une leçon publiée dès que `hasLessonAccess` autorise le spectateur : les invités les reçoivent donc pour les aperçus gratuits, les utilisateurs connectés pour les leçons réservées aux comptes, les détenteurs d’une licence Complete ou Agency pour les leçons payantes et les administrateurs pour toutes les leçons ; une signature erronée ou expirée reçoit `403`.
- **En-têtes** : chaque réponse du Worker porte `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, une `Permissions-Policy` qui désactive caméra, micro, géolocalisation et topics, et une Content Security Policy qui bloque l’intégration en cadre, les changements de `<base>` et les plugins. Les réponses HTTPS ajoutent `Strict-Transport-Security`. Le Worker les définit dans `src/server.ts` sauf si la réponse a déjà les siens. Les fichiers servis sans le Worker (`/assets/*`, `/fonts/*`, `/robots.txt`, `/llms.txt`) ne reçoivent que les en-têtes de `public/_headers` : la Content Security Policy, `Referrer-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options` et `X-Frame-Options`, sans `Cross-Origin-Opener-Policy` ni `Permissions-Policy`.

## Non mis en œuvre

- Une Content Security Policy qui restreint scripts et styles : les pages prérendues demanderaient un hash pour chaque script en ligne de chaque page.
- Un journal d’audit, y compris pour les bannissements, les suppressions et les usurpations.
- Une protection anti-bots ou un CAPTCHA sur les formulaires publics.
- Un écran d’usurpation d’identité ([Usurpation d’identité](/docs/features/impersonation)).
