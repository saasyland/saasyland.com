アプリケーションは 1 つの Cloudflare Worker として動作します。`@cloudflare/vite-plugin` がビルドを行い、`CLOUDFLARE_ENV` で Wrangler の環境を選択します。`wrangler.jsonc` は `main` を `./src/server.ts` に設定し、`nodejs_compat` とオブザーバビリティを有効にし、静的ファイルを `ASSETS` バインディング経由で配信します。`/assets/*`、`/fonts/*`、`/robots.txt`、`/llms.txt` を除くすべてのパスで、最初に Worker が実行されます。ソースマップはアップロードしません（`upload_source_maps` は `false`）。Worker とソースマップを合わせると、Cloudflare が 1 回のアップロードで受け付けるサイズを超えるためです。

| 環境          | Worker                  | D1、KV、R2                             | ドメイン                |
| ------------- | ----------------------- | -------------------------------------- | ----------------------- |
| `development` | `saasyland-development` | `.wrangler/state` 内のローカルリソース | `localhost:3000`        |
| `preview`     | `saasyland-preview`     | プレビュー用リソース                   | `preview.saasyland.com` |
| `production`  | `saasyland`             | 本番用リソース                         | `saasyland.com`         |
| `test`        | `saasyland-test`        | `.wrangler/test` 内のローカルリソース  | `127.0.0.1:3000`        |

どの環境も D1 を `DB`、KV を `CACHE`、R2 を `MEDIA` と `BUNDLES` としてバインドし、必要なシークレットを列挙します。アフィリエイトの紹介トラッキングに必要な `AFFONSO_PROGRAM_ID` は `vars` の下の通常の変数で、`production` と、ダミー ID で `test` に設定されています。トラッキングが動作するのは、Worker にこの ID があり、かつプログラムが開始している場合だけです。現在の `AFFILIATE_PROGRAM` は <RepositoryFact name="affiliateProgram" /> です（[プログラムの開始](/docs/features/affiliates#opening-the-programme)）。`test` 環境は `src/platform/testing/worker.ts` をエントリーとして使います。このエントリーは Resend と Polar へのリクエストを横取りし、Playwright 用のテスト専用エンドポイントを公開します。

## リクエストの流れ

`src/server.ts` がすべてのリクエストを処理します。

1. `REQUEST_HANDLERS` のエントリーが受け持つパスは、ほかの何よりも先にそのハンドラーに渡されます。コースは `/media/` を受け持ち、コースのカバー画像を `serveCover` に、レッスンの資料を `serveAttachment` に、署名済みの動画ファイルを `serveMedia` に渡します。いずれも R2 から読み出し、カバー画像と動画は Workers のキャッシュを通します（[Cloudflare R2](/docs/integrations/cloudflare-r2) を参照）。ライセンスは `/bundles/` を受け持ち、`serveBundle` に渡します。`serveBundle` は CLI の署名済みのテンプレートバンドルを R2 から配信します（[CLI ライセンス API](/docs/features/cli-licence-api#template-bundles) を参照）。以下の手順のうち、これらに適用されるのはセキュリティヘッダーだけです。
2. `i18n.middleware.ts` の `resolveLocale` が、`/api` と `/_serverFn` 以外への `GET` と `HEAD` のドキュメントリクエストを検査します。言語エイリアスと正規でないロケールパスをステータス 308 でリダイレクトし、ロケール Cookie が URL のロケールと異なる場合はそれを通知します。
3. `/api` と `/_serverFn` 以外への `GET` と `HEAD` のリクエストは、まず `ASSETS` から配信されます。プリレンダリングされたページもここに含まれます。404 の場合は TanStack Start のハンドラーに処理が移ります。
4. ロケール Cookie の更新が必要な場合、Worker はそれをレスポンスに追加します。HTML レスポンスには、そのロケールのフォントに対する `Link` プリロードヘッダーも付与され、Cloudflare はこれを Early Hints として送ります（後述の「ゾーンの設定」を参照）。
5. HTML レスポンスは `DOCUMENT_REWRITES` を通ります。ライセンスの `rewritePppOffer` は地域別の価格を適用します。`cf-ipcountry` の国が購買力に基づく割引の対象である場合、`HTMLRewriter` が `<html>` に割引の属性を追加し、レスポンスは `private, no-cache` になります。
6. リダイレクト、API 呼び出し、メディアファイルを含むすべてのレスポンスに、[セキュリティと堅牢化](/docs/features/security) のセキュリティヘッダーを付け、レンダリングされたものもプリレンダリングされたものも含め、すべての HTML レスポンスには、そのレスポンス専用の nonce を持つスクリプトのポリシーも付けます。Cloudflare も、自身が挿入するスクリプトにこの nonce を付けます。Worker を経由しないファイルには、`public/_headers` から同じセットが付きます。

`src/server.ts` は、リクエストハンドラーを `REQUEST_HANDLERS` に、ドキュメントの書き換えを `DOCUMENT_REWRITES` に並べます。機能は、それぞれのリストに自身のモジュールを指す 1 つの要素として加わります（[Worker とビルドが実行するもの](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)を参照）。

## ゾーンの設定

ゾーンの 2 つの設定がすべてのページに影響します。どちらも Cloudflare ダッシュボードの **Speed** > **Settings** > **Content Optimization** にあります。

- **Early Hints**: オン。Cloudflare はページの直前のレスポンスの `Link` ヘッダーを保存し、Worker が同じ URL への次のレスポンスを用意している間に、それを `103 Early Hints` レスポンスとして送ります。そのためブラウザーはフォントのダウンロードを早く始められます。Cloudflare はデプロイ後にもこのヘッダーを送り直すので、ヘッダーにはフォントだけを並べます。[パフォーマンス](/docs/conventions/performance)を参照してください。
- **Speed Brain**: オフ。訪問者がこれから開くリンクを Chromium にプリフェッチさせる `Speculation-Rules` ヘッダーを追加しますが、Cloudflare は Worker を実行する URL のプリフェッチを拒否します。このサイトではすべてのページがそうなので（`run_worker_first`）、プリフェッチはどれも `503` と `cf-speculation-refused: prefetch refused: disabled for worker requests` で失敗します。また Cloudflare は、このサイトのように `'strict-dynamic'` と nonce を使うポリシーには対応しないとしています。オフにしても失うものはありません。TanStack Router は、ポインターの下にあるリンクのコードとデータを（`defaultPreload: "intent"`）、ページがアイドルになった後はヘッダーのすべてのリンクのコードとデータも、すでに読み込み、新しいドキュメントを要求せずにそのページを開きます。Free プランでは Speed Brain は既定でオンです。

## デプロイ

`bun run deploy:preview` と `bun run deploy:production` は、まずバインディングの欠落とプレースホルダーのままの D1 と KV の ID を拒否する `scripts/verify-bindings.ts` を実行し、次に `wrangler.jsonc` が宣言するシークレットの中に空の値やプレースホルダーの値があれば拒否する `scripts/prepare-deploy-secrets.ts` を、さらに各エリアのデプロイ前チェック（現在は OAuth クライアント ID の形式を確認する `auth:verify:<environment>` と、その環境の Polar の組織をコードと比較する `polar:verify:<environment>`）を実行する `scripts/run-deploy-checks.ts` を実行し、続いて対応するビルド、その環境の D1 マイグレーション、それらのシークレットを使った `dist/server/wrangler.json` の `wrangler deploy`、そして稼働中のサイトを確認する `scripts/verify-deployment.ts` を実行します。R2 バケット（`MEDIA` と `BUNDLES`）は名前でバインドされるため、最初のデプロイの前に存在している必要があります。`wrangler r2 bucket create` で作成してください。ビルドは公開ページをプリレンダリングし、`scripts/verify-build.ts` と `scripts/optimize-prerendered-html.ts` を実行します。[プレビューをデプロイする](/docs/getting-started/deploy-preview)、[プロジェクトのスクリプト](/docs/tooling/scripts)、[CI/CD](/docs/tooling/ci-cd) を参照してください。

ビルドのたびに Worker を 2 回コンパイルします。最初の Worker にはすべてのページが含まれ、公開ページをプリレンダリングします。プリレンダリングの後、`scripts/deployed-worker.ts` が、プリレンダリングにしか使わないものを除いてデプロイ用の Worker を再ビルドします。コンパイル済みのドキュメントやブログのページのインポートはすべて、例外を投げる 1 つのモジュールに解決され、ランディングと法務の各ページだけが使う翻訳も除外されます。プリレンダリング済みのページは `ASSETS` から返され、クライアント側のナビゲーションはドキュメントとブログのインデックスを読み、ブラウザ用チャンクから MDX をレンダリングするため、デプロイされた Worker がコンテンツを読むことはありません。ドキュメントのページまたは公開済みのブログ記事がプリレンダリングされていない場合や、デプロイされた Worker のいずれかのファイルがドキュメントやブログのモジュールを含む場合、`scripts/verify-build.ts` がビルドを失敗させます。
