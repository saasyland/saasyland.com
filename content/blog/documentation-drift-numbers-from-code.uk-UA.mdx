faq:
  - question: Що таке дрейф документації?
    answer: >-
      Розрив, що виникає між тим, що кажуть документація, маркетингові тексти чи README, і тим, що
      робить код, бо одне з них змінилося, а інше ні. Він починається тієї миті, коли факт існує у
      двох місцях: число, вписане на сторінку вручну, — це копія того, що знає код, і ніщо не тримає
      копію узгодженою, коли код змінюється.
  - question: Чому ШІ-агенти для програмування посилюють дрейф документації?
    answer: >-
      Бо вони множать копії. Агент, який пише сторінку, копіює число, яке побачив на іншій сторінці,
      агент-перекладач копіює його в кожну мову, а кілька агентів, що працюють паралельно, копіюють
      кожен свою версію. На saasyland.com кількості, вписані вручну на лендингу, ставали хибними за
      кілька тижнів, а переклади, зроблені зі старішої англійської сторінки, описували стек, яким
      сайт уже не користувався.
  - question: Як тримати числа в документації узгодженими з кодом?
    answer: >-
      Не вписуйте їх вручну. Вимірюйте кількості під час збірки й надавайте їх сторінкам як модуль,
      імпортуйте значення, які оголошує код, як-от ціни й ліміти, з файлу, що їх оголошує, і виводьте
      і те, і інше через компонент, який форматує їх для мови читача. Тоді сторінка показує те, що
      виміряла збірка, кожною мовою, і нікому не треба її редагувати.
  - question: Що ніколи не слід вписувати вручну в документацію чи маркетингові тексти?
    answer: >-
      Усе, на що може відповісти код: кількості, ціни, ліміти, версії, шляхи до файлів, команди,
      прапорці, списки підтримуваних варіантів і те, чи доступна функція. Вписуйте лише те, чого код
      знати не може: пояснення, причини, оцінки й датовані факти про зовнішній світ із посиланням на
      їхнє джерело.
  - question: Як не дати прикладам коду в документації застаріти?
    answer: >-
      Або запускайте їх, як це роблять тести документації в Rust, або перевіряйте їх за вихідним
      кодом. На saasyland.com блок коду, заголовком якого є шлях у репозиторії, має бути точним
      фрагментом цього файлу, і перевірка контенту провалює CI, коли файл змінюється, а фрагмент
      йому більше не відповідає.
  - question: Як показувати функції, які ще не вийшли, і не перебільшувати?
    answer: >-
      Дайте кожній функції статус у коді, доступна чи готується, і пишіть кожне речення, яке від
      нього залежить, як повідомлення з обома версіями. Тоді сторінка показує версію, що відповідає
      статусу, а зміна однієї константи пересуває кожне речення кожною мовою одночасно. Там, де
      статус залежить від того, що код справді робить, виводьте його з цього коду, а не задавайте
      вручну.
  - question: Як двом репозиторіям узгоджуватися щодо спільних значень?
    answer: >-
      Покладіть спільні значення в один пакет, який імпортують обидва, решту пов’яжіть на рівні
      типів, щоб зміна з одного боку не компілювалася з іншого, і протестуйте опубліковану пару
      наскрізно. Пакет контракту прибирає більшість дрейфу між репозиторіями; він не прибирає
      розбіжності версій між розгортаннями, які його використовують.
  - question: Що таке реєстр тверджень?
    answer: >-
      Файл, що перелічує кожну обіцянку, яку ваш сайт, документація й дописи дають про продукт,
      кожну з тестом, який її доводить, зміною, яка її доведе, або позначкою, що сьогодні вона
      хибна. Перевірка провалюється, коли доведене твердження вказує на тест, якого вже немає, тож
      обіцянка не може непомітно втратити свій доказ.
  - question: Чи варте виведення значень документації з коду своєї ціни?
    answer: >-
      Для сайту кількома мовами — майже завжди: одне хибне число коштує по виправленню на кожну
      мову, а вписане вручну значення стає хибним щоразу, коли змінюється код. Для однієї сторінки,
      яка наводить два числа, досить тесту, що порівнює сторінку з кодом. Ціна реальна: крок збірки,
      компоненти й перевірки, які треба підтримувати, і текст, написаний так, щоб значення могло
      змінитися, не ламаючи речення.

Практичний посібник про те, як тримати документацію, маркетингові тексти й дописи в блозі правдивими, коли код змінюється щодня, а більшість слів пишуть ШІ-агенти. Він підходить для будь-якого стеку. Кожен розділ спершу дає правило, а потім показує, як його застосовує saasyland.com, з його справжніми файлами, pull request і помилками, через які кожне правило стало потрібним. У ньому:

1. Що таке дрейф документації і чому агенти роблять його швидшим і ширшим.
2. Шість видів тверджень на сайті і де живе істина кожного з них.
3. Вимірювання під час збірки й виведення значень через компоненти замість вписування вручну.
4. Перевірка того, що мусить лишатися вписаним вручну, як-от фрагментів коду й довідкових таблиць.
5. Статуси замість граматичних часів для того, що ще не вийшло, і похідні числа, які не можуть зрости самі.
6. Один контракт між двома репозиторіями, реєстр тверджень, еталонний diff, зовнішні факти, витрати, прогалини й стартовий набір.

## Коротка відповідь

Кожен факт на сторінці повинен мати рівно одне джерело, і сторінка повинна виводити його звідти. Розкладіть те, що каже ваш сайт, за видами. Кількості, що стосуються вашого коду, вимірює збірка. Значення, які встановлює бізнес, як-от ціни й ліміти, оголошують один раз у коді й імпортують. Числа, похідні від них, обчислюють, і обчислюють обережно. Те, чи працює функція, — це статус у коді, і кожне речення, що від нього залежить, має версію для кожного статусу. Обіцянки щодо поведінки перелічують разом із тестом, який їх доводить. Факти про зовнішній світ мають дату й посилання. Усе, що мусить лишатися вписаним вручну, як-от фрагмент коду чи довідкову таблицю, порівнює з кодом перевірка, яка провалює CI. Тоді єдине, у чому людина чи агент ще може помилитися, — це текст навколо значень, і саме для цього існує рев’ю.

## Що таке дрейф документації і чому агенти його посилюють

Дрейф документації — це розрив між тим, що кажуть ваші слова, і тим, що робить ваш код. Для нього не потрібно, щоб хтось помилився. Сторінка, яка каже «12 інтеграцій», була правдивою того дня, коли її написали; код отримав тринадцяту, сторінка ні, і тепер вона хибна. Причина не в недбалості, а в дублюванні: той самий факт живе у двох місцях, і лише одне з них підтримує те, що його змінює.

Dave Thomas і Andy Hunt сформулювали цей принцип у _The Pragmatic Programmer_: «Кожна частина знання повинна мати єдине, однозначне, авторитетне представлення в системі». Вони прямо кажуть, що документація теж підпадає під нього. Їхній тест на порушення звучить так: «коли має змінитися якийсь один аспект коду, чи доводиться вам вносити цю зміну в кількох місцях і в кількох різних форматах? Чи доводиться вам змінювати код і документацію …? Якщо так, ваш код не DRY».

Посібник Google з документації дає операційну версію: «Змінюйте документацію в тому самому CL, що й код». Це правило працює, коли людина, яка змінює код, знає кожну сторінку, що його згадує. Воно перестає працювати в масштабі, а масштаб приносять ШІ-агенти для програмування.

### Три способи, якими агенти множать копії

**Швидкість.** Агент пише сторінку документації за кілька хвилин і вписує ті числа, які бачить. Якщо інша сторінка каже 176 тестових файлів, нова сторінка теж скаже 176. Кожна сторінка, яку агент пише з інших сторінок, успадковує їхні помилки й додає ще одну копію.

**Мови.** saasyland.com публікується <RepositoryFact name="languages" /> мовами. Вписане вручну число існує по разу в кожній мові, а агенти-перекладачі працюють із тим англійським текстом, який їм дали. 12 листопада 2026 року ми виявили, що перекладені дописи в блозі було зроблено зі старішої англійської версії: вони описували стек Next.js, Bun, Elysia і Neon, яким сайт уже не користувався, 54 мови, 141 тестовий файл і 472 тести (#116). Кожен переклад був внутрішньо узгодженим, гладким і хибним.

**Паралельні сесії.** Кілька агентів, що працюють одночасно, копіюють кожен ту версію факту, яка була правдивою на початку його сесії. Два pull request, які обидва згадують кількість, можуть злитися в будь-якому порядку, і перемагає другий, байдуже, чи його число новіше.

Агенти також перекладають те, чого перекладати не можна, бо для перекладача число чи шлях усередині речення виглядає як текст. Наш аудит узгодженості 15 листопада виявив, що список доказів на лендингу показував `bun run テスト` японською і `src/intégrations/` французькою (#169). На демонстраційному екрані цін в адмінці ціни було вписано вручну в повідомлення кожної мови, і перекладачі їх сконвертували: польська сторінка показувала 129 zł, бразильська — 58 реалів, а німецька — 58 €, поруч із ціною в доларах $290 (#169). Дві локалі переклали саму контактну адресу електронної пошти (#132). Кожен із цих випадків був реченням, що містило значення, і значення сприйняли як частину речення.

### Як виглядав наш власний дрейф

Лендинг saasyland.com колись казав, що кожне число на ньому згенеровано з цього публічного репозиторію. 12 листопада такими були лише два: кількість зірок на GitHub і мажорна версія React. Решту вписали вручну у файли повідомлень, і вони задрейфували (#115):

| Твердження на сторінці                   | Що було в репозиторії |
| ---------------------------------------- | --------------------- |
| 176 тестових файлів                      | 221                   |
| 8 наборів Playwright                     | 12                    |
| 13 розділів адмінки, а деінде — «десять» | 9                     |
| «Дванадцять» запитань CLI                | 13                    |

Жодне з них не було брехнею, коли його вписували. Кожне було знімком, який код уже залишив позаду. У цьому й суть: дрейф не виправиш більшою уважністю, бо копія правильна до того дня, коли вона вже ні, і ніщо не каже вам, котрий це день.

## Шість видів тверджень і де живе істина кожного з них

Перш ніж щось будувати, розкладіть те, що каже ваш сайт. Кожен вид має інше джерело істини й потребує іншого механізму.

| Вид         | Приклад                                     | Джерело істини                     | Механізм                                     | Що провалюється, коли воно дрейфує                         |
| ----------- | ------------------------------------------- | ---------------------------------- | -------------------------------------------- | ---------------------------------------------------------- |
| Виміряні    | Кількість тестів, сторінок чи мов           | Репозиторій                        | Рахує збірка                                 | Дрейфувати нічому: збірка виводить сьогоднішню кількість   |
| Оголошені   | Ціна, ліміт плану, строк повернення коштів  | Одна константа в коді              | Імпортують і форматують для локалі           | Тест, що порівнює зовнішні системи з константою            |
| Похідні     | Заощаджені години, ціна, виражена в годинах | Формула над оголошеними значеннями | Обчислюють у коді, обережно округлюють       | Тест, що твердження досі справджується                     |
| Статус      | Чи функція доступна, чи готується           | Одна константа статусу на функцію  | Повідомлення з версією для кожного статусу   | Тест, що рендерить обидві версії                           |
| Поведінкові | «Повернення коштів припиняє дію ліцензії»   | Поведінка коду                     | Тест, названий поруч із твердженням          | Перевірка, що кожне доведене твердження досі має свій тест |
| Зовнішні    | Результат опитування, ціна конкурента       | Чужа сторінка                      | Датоване цитування, яке перевіряють повторно | Нічого автоматичного; дата повторної перевірки             |

Із таблиці випливають два правила. По-перше, кожен вид, крім останнього, можна змусити провалювати перевірку, коли він дрейфує, тож саме останньому виду належить ваша увага під час рев’ю. По-друге, механізм залежить від виду, а не від того, де з’являється твердження: та сама ціна трапляється на картці цін, у дописі в блозі, у відповіді FAQ і в meta description сторінки, і кожному з цих місць потрібне те саме джерело.

## Вимірюйте під час збірки

Кількість, що стосується вашого репозиторію, має обчислювати збірка, яка публікує сторінку, з тих самих файлів, яких стосується ця кількість. Більшість бандлерів мають для цього місце. API плагінів Vite називає його віртуальним модулем: «Віртуальні модулі дають змогу передавати у вихідні файли інформацію, доступну під час збірки, за допомогою звичайного синтаксису імпорту ESM». Плагін обчислює значення, коли починається збірка, і будь-яка сторінка імпортує їх, як звичайний модуль.

Наш плагін — це `scripts/repository-facts.ts`, який надає `virtual:repository-facts`. Він рахує тестові файли, специфікації Playwright і UI-компоненти за glob-шаблонами, отримує список браузерних тестів, запитуючи його в Playwright, і читає налаштування із самих файлів інструментів: поріг покриття, ліміти лінтера й ширину рядків форматера з `vite.config.ts`, версію Node з `.nvmrc`, версію Bun з `package.json`, кількість шардів CI з файлів workflow. Кілька його рядків показують, наскільки прямі ці вимірювання:

```ts title="scripts/repository-facts.ts"
    e2eShards: readShards(E2E_WORKFLOW),
    e2eSpecs: countFiles(`${e2eSpecsPath}/*.spec.ts`),
    e2eSpecsPath,
    e2eTests: browserTests.length,
```

Сам плагін займає приблизно двадцять рядків: він будує вихідний код модуля в хуку Vite `config` і віддає його під розв’язаним id, що починається з `\0`, як показує посібник Vite з плагінів для віртуальних модулів.

```ts title="scripts/repository-facts.ts"
    enforce: "pre",
    load: { filter: { id: exactRegex(RESOLVED_MODULE_ID) }, handler: () => moduleSource },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_MODULE_ID },
```

Довіру до нього забезпечують три проєктні рішення.

**Вимірюйте те, чого стосується твердження, а не замінник.** Наша перша версія рахувала розділи адмінки за підписами бічної панелі, бо підрахунок самої бічної панелі затягнув би на лендинг 3,7 КБ стиснутого gzip коду адмінки (#115). Тест тримав підписи рівними бічній панелі. Згодом кількість змінила значення: лендинг стверджував, що розділи адмінки працюють, а п’ять з одинадцяти показували демонстраційні дані. Тож кожен пункт меню адмінки отримав статус, факт рахував лише робочі, і число впало з 11 до 6 (#177). Потім демонстраційні екрани взагалі видалили (#259). Тепер факт показує <RepositoryFact name="adminSections" />, і він рахує кожен пункт, бо кожен пункт — робочий екран.

**Відхиляйте конфігурацію, яку документація не може описати.** Сторінка, яка каже «покриття тримається на рівні 100%», припускає один поріг. Якщо хтось встановить для гілок 95, а для рядків 100, речення стане двозначним. Наш плагін валідує схемою конфігурацію, яку читає, і схема відхиляє чотири різні пороги:

```ts title="scripts/repository-facts.ts"
const thresholdsSchema = zod
  .object({ branches: zod.number(), functions: zod.number(), lines: zod.number(), statements: zod.number() })
  .refine(
    ({ branches, functions, lines, statements }) => [branches, functions, statements].every((threshold) => threshold === lines),
    "The docs state one coverage threshold for all four metrics",
  )
```

Збірка провалюється з цим повідомленням, і людина чи агент, що змінили поріг, мусять вирішити, що повинна казати документація. Це перевірка форми факту, а не лише його значення.

**Шляхи й команди — теж факти.** Речення, яке каже читачам відкрити `coverage/coverage-summary.json` чи запустити `bun run test:coverage`, містить два значення, якими володіє код. Починаючи з #169, лендинг бере їх із того самого модуля: шлях до підсумку — з `reportsDirectory` у конфігурації Vite, каталог специфікацій — з `testDir` у Playwright, команди — з `package.json`. Тест перевіряє, що кожен наведений шлях існує і кожна команда є скриптом. Жоден перекладач уже не перетворить їх на `bun run テスト`, бо переклад їх ніколи не містить.

## Виводьте значення через компоненти, а не рядки

Щойно значення існує в коді, виводьте його через один компонент і ніколи не вписуйте вручну його результат. У нашій документації й блозі цей компонент — `<RepositoryFact>`. У MDX `<RepositoryFact name="testFiles" />` виводить <RepositoryFact name="testFiles" />, `<RepositoryFact name="e2eTests" />` — <RepositoryFact name="e2eTests" />, а `<RepositoryFact name="coverageThreshold" unit="percent" />` — <RepositoryFact name="coverageThreshold" unit="percent" />, відформатовані для мови сторінки, яку ви читаєте. Усе правило форматування вміщується в десяток рядків:

```tsx title="src/presentation/components/custom/repository-fact.tsx"
const FactValue = ({ unit, value }: { readonly unit?: keyof typeof UNIT_FORMATS | undefined; readonly value: Value }): JSX.Element => {
  const format = useFormatter()

  if (typeof value === "number") {
    return <>{format.number(value, unit && UNIT_FORMATS[unit])}</>
  }

  if (typeof value === "string") {
    return <code>{value}</code>
  }

  return <>{format.list(value.map((item) => <code key={item}>{item}</code>))}</>
}
```

Число форматується з роздільниками локалі, а з `unit` — ще й зі словом локалі для секунд, годин, днів чи відсотків, у правильній формі множини. Рядок виводиться як код, бо кожен рядковий факт — це шлях, команда чи ідентифікатор, які мають виглядати однаково кожною мовою. Список стає списком коду в оформленні локалі: «a, b and c» англійською, «a, b et c» французькою.

Таблиці отримують те саме. `<RepositoryTable>` виводить рядки, які будує код, під назвами стовпців, які перекладає сторінка: декларації дозволів кожної ролі, типи комітів та їхні емодзі, регіональні множники цін із їхніми країнами, форми звертання, яких кожна мова не повинна використовувати. Таблиця, вписана вручну <RepositoryFact name="languages" /> мовами, — це <RepositoryFact name="languages" /> копій структури даних; таблиця, виведена зі структури, — одна.

Три місця не можуть рендерити компонент, і кожному потрібна власна відповідь:

- **Файли повідомлень.** Тексти інтерфейсу живуть у повідомленнях JSON, а не в MDX. Значення потрапляють у них як аргументи ICU, як у `{testFiles, number} test files`, а компонент, що рендерить повідомлення, передає йому модуль фактів. Порада ICU стосується кожного такого повідомлення: «пишіть повні речення в їхніх підповідомленнях», бо речення, склеєне з фрагментів, перекладач не може переставити.
- **Frontmatter.** Заголовок, опис і FAQ допису — це YAML, який живить head сторінки, стрічку й структуровані дані. Заголовки й відповіді FAQ наших дописів — це повідомлення ICU, які `formatPostText` форматує з фактами, тож відповідь FAQ може містити кількість мов. Meta description не може, тож його пишуть без чисел.
- **Блоки коду.** Блок коду копіюється байт у байт. Йому потрібен наступний механізм.

Результат видно в нашій історії. Коли #137 замінив кожне вписане вручну значення в документації, лише в блозі вже було 81 використання ранішої версії компонента, яке треба було перейменувати, а документація отримала виведені з коду значення для лімітів частоти запитів, покриття, лімітів лінтера, тайм-аутів, налаштувань кодування відео, строків дії підписаних URL-адрес, інтервалів опитування, розмірів сторінок, цін, версій, повторних спроб і розкладів, кожне з яких раніше вписували вручну дев’ятьма мовами.

## Коли значення мусить лишатися вписаним вручну, перевіряйте його

Деякий текст мусить містити саме значення: фрагмент коду, таблицю маршрутів, список змінних середовища. Для такого тексту правило одне: порівнюйте сторінку з кодом перевіркою, яка провалюється.

**Запускайте приклади або порівнюйте їх із вихідним кодом.** Rust вбудовує це у свій інструмент документації: «rustdoc підтримує виконання прикладів із вашої документації як тестів. Це гарантує, що приклади у вашій документації актуальні й працюють». Для сайту на TypeScript виконати кожен фрагмент складніше, тож ми натомість порівнюємо. Блок коду, заголовком якого є шлях у репозиторії, має бути точним фрагментом цього файлу:

```ts title="scripts/check-content.ts"
const quotedSourceProblems = ({ label, target }: Translation): string[] =>
  [...target.matchAll(QUOTED_SOURCE_PATTERN)].flatMap(({ groups }) => {
    const path = groups?.["path"] ?? ""
    const file = join(REPOSITORY_DIR, path)

    if (existsSync(file) && readFileSync(file, "utf8").includes(groups?.["code"] ?? "")) {
      return []
    }

    return [`A code block in ${label} is not an excerpt of ${path}`]
  })
```

Кожен блок коду із заголовком у цій статті перевіряється саме так, усіма <RepositoryFact name="languages" /> мовами, на кожному pull request. Якщо хтось змінить один із файлів, процитованих вище, `bun run check` назве цей допис і провалюватиметься, доки фрагмент не оновлять.

**Генеруйте довідкові таблиці або порівнюйте їх.** Довідник маршрутів, сторінка скриптів і таблиця змінних середовища — це списки, які код уже містить. Наша перевірка контенту провалюється, коли сторінка маршрутів дає константі маршруту неправильний шлях, коли сторінка скриптів пропускає скрипт із `package.json` або перелічує такий, якого немає, і коли таблиці середовища пропускають секрет, оголошений у `wrangler.jsonc`. Вона також провалюється, коли сторінка документації називає локальний хост чи піддомен, якого не дозволяє жоден режим збірки.

**Тримайте переклади в структурі англійської сторінки.** Переклад повинен мати ті самі фрагменти вбудованого коду, ті самі компоненти з тими самими props, ті самі посилання й ту саму кількість рядків таблиць, що й англійська сторінка. Саме ця перевірка назавжди покінчила з перекладеними командами й шляхами: перекладач, людина чи агент, може переформулювати кожне речення, але не може змінити жодного символу між зворотними апострофами.

**Перевіряйте зовнішні системи за кодом перед розгортанням.** Ціни оголошено в `TIER_PRICES`; платіжний провайдер тримає власну копію у своєму каталозі продуктів, і розбіжність там означала б, що з покупця стягують одну ціну, а сторінка показує іншу. Наше розгортання запускає `polar:verify` перед збіркою, і воно провалюється, коли ціна продукту в Polar відрізняється від константи або його ліцензійні ключі дозволяють іншу кількість пристроїв, ніж `LICENSE_ACTIVATION_LIMITS`. Повідомлення про помилку називає константу, тож той, хто його читає, знає, котра сторона є джерелом.

## Статуси, а не граматичні часи

Найважче тримати правдивими твердження про майбутнє. «Генерує ваше виставлення рахунків» хибне, доки функція не вийде, правдиве після, і кожне речення, яке це каже, має змінитися того самого дня. Текст справляється з цим погано: речення в майбутньому часі лишаються в майбутньому часі й після виходу функції, а речення в теперішньому часі пишуть заздалегідь, бо так вони звучать краще.

Виправлення — зробити доступність значенням у коді. Кожна функція отримує статус, а кожне речення, що від нього залежить, — це повідомлення з однією версією на статус.

У нас два статуси, `FEATURE_STATUS.AVAILABLE` і `FEATURE_STATUS.ARRIVING`. Функції кожного тарифу перелічено в `TIER_FEATURES` з їхнім статусом, а картки цін групують їх під **Доступно зараз** і **Готується**, тож жодна мова не вписує статус вручну. Коли CLI ще не вмів генерувати проєкти, цей факт жив у тексті: одинадцять повідомлень дев’ятьма мовами. #189 переніс його в одну константу, `CLI_GENERATION`, і перетворив кожне з цих повідомлень на ICU select:

```json title="messages/en-US/components.custom.pricing.json"
      "tagline": "{generation, select, available {The CLI and the generated source with its tests.} other {The CLI now, the generated source and tests as they arrive.}}",
```

ICU описує цей механізм як використання «аргументу „select“ для вибору підповідомлень за фіксованим набором ключових слів». Кожна версія — повне речення, тож кожна мова може написати його по-своєму. Тест рендерить кожне таке речення з обома статусами кожною мовою, тож версія, якої сьогодні ніхто не бачить, усе одно має бути правильною, а інший тест провалюється, коли мова пише «готується» поза select, куди статус не може дійти.

20 листопада CLI отримав генерацію проєктів, і #251 перемкнув константу на available. Кожен select перемкнувся сам, кожною мовою: перший екран, конфігуратор, FAQ, слогани цін, робочий простір клієнта. Той самий pull request усе одно мусив вручну оновити текст у десяти дописах блогу, у документації й у README, бо ці речення описували генерацію так, що select до них не доходив. Урок: пропускайте кожне речення про функцію, яка ще не вийшла, через статус від того дня, коли ви його пишете, зокрема й речення в довгих текстах.

### Виводьте статус там, де можете

Статус, заданий вручну, все одно можна задати зарано. Там, де сам код знає, чи працює функція, виводьте статус із цього знання. Наш CLI публікує, які відповіді підтримують його шаблони, а вебсайт виводить із цього статус виставлення рахунків:

```ts title="src/data/marketing.ts"
const TEMPLATES_GENERATE_BILLING = CLI_TEMPLATE_SUPPORT.choices.billing.some((option) => option !== NONE)

export const BILLING_GENERATION: FeatureStatus = TEMPLATES_GENERATE_BILLING ? CLI_GENERATION : FEATURE_STATUS.ARRIVING
```

Коли `CLI_GENERATION` перемкнувся, виставлення рахунків лишилося під **Готується**, бо жоден шаблон його ще не генерував (#233). Нікому не треба було пам’ятати, що виставлення рахунків — виняток; його перемістить випуск шаблонів, який генеруватиме виставлення рахунків.

### Пишіть речення, які посилаються на джерело

Деякі твердження — це списки, які зростатимуть. «Генерує TanStack Start, Cloudflare, D1, Drizzle, Better Auth і Resend» правдиве для одного випуску й неповне для наступного. #233 переписав такі речення так, щоб вони називали джерело, а не переказували його: генерація записує «варіанти, які ви можете обрати в конфігураторі», а конфігуратор вмикає саме ті варіанти, які підтримують шаблони. Речення лишається правдивим, коли список зростає, а сам список живе в одному місці.

## Похідні числа: округлюйте вниз, обмежуйте зверху й показуйте рядки

Маркетингові числа часто похідні: заощаджені години, заощаджені гроші, час до першого розгортання. Їх найлегше роздути й найважче перевірити, тож тут діють три правила.

1. **Обчислюйте їх у коді з розписаних вхідних даних**, щоб кожне вхідне значення можна було прочитати й оскаржити.
2. **Округлюйте в бік, невигідний для читача**, і обмежуйте заголовне число зверху, щоб твердження не могло зрости саме, коли додають рядок.
3. **Публікуйте рядки** скрізь, де заголовне число з’являється в розгорнутому вигляді.

Наше твердження про «фору», тобто години роботи senior-розробника, які заощаджує згенерований проєкт, з #184 дотримується всіх трьох. `HEAD_START_ROWS` у `src/data/head-start.ts` перелічує кожну частину типового проєкту, яку генерують шаблони, шар шаблонів, у якому вона постачається, і нижню й верхню оцінки годин, які вона забрала б вручну. Виставлення рахунків, організації, мультитенантність і демонстраційна комерція рядка не мають, бо жоден шаблон їх ще не генерує. Сьогодні рядки в сумі дають від <RepositoryFact name="headStartLowHours" /> до <RepositoryFact name="headStartHighHours" /> годин, а заголовне число бере нижню межу:

```ts title="src/data/head-start.ts"
export const HEAD_START_HOURS = Math.min(
  HEAD_START_CLAIM_MAX_HOURS,
  Math.floor(HEAD_START_LOW_HOURS / HEAD_START_ROUNDING_HOURS) * HEAD_START_ROUNDING_HOURS,
)
```

Заголовне число виводить <RepositoryFact name="headStartHours" />. Верхня межа — це число, яке сайт уже стверджував до появи рядків, тож розпис міг лише підтвердити твердження або знизити його. Якщо рядок видалити, цифра впаде, і нікому не доведеться редагувати сторінку. Дописи, що її обговорюють, виводять кожен рядок з його оцінкою, тож читач, який не згоден з оцінкою, бачить, з якою саме і наскільки.

Те саме стосується будь-якої цифри, похідної від ціни. Твердження, що Core коштує менше ніж <RepositoryFact name="corePriceInHours" unit="hour" /> роботи senior-розробника, — це `CORE_PRICE_IN_HOURS`, обчислене з ціни й ілюстративної погодинної ставки, оголошеної поруч, і тест провалюється, якщо ціна колись перестане вкладатися в цю кількість годин. #132 прибрав кожну суму, похідну від цін, яку вписали в текст вручну, як-от різницю між двома тарифами, бо вписана вручну різниця стає хибною того дня, коли змінюється будь-яка з цін.

## Один контракт між двома репозиторіями

Дрейф між двома репозиторіями — та сама проблема на більшій відстані. _The Pragmatic Programmer_ називає це дублюванням представлення: «ваш код мусить мати знання, яке також присутнє в зовнішній речі … Змініть його на одному кінці — і зламається інший».

SaaSy Land має два репозиторії: цей вебсайт, який продає ліцензії й обслуговує API ліцензій, і приватний CLI, який запускають клієнти. Обом потрібні ті самі тарифи, маршрути API, коди помилок, ліміти, коди виходу й список варіантів стеку. Це знання живе в одному пакеті, `@saasyland/stack`, опублікованому в npm за ліцензією MIT. CLI його збирає; вебсайт імпортує.

Скільки імпортувати — це компроміс, і в нас його вирішило вимірювання. Реекспорт констант тарифів пакета під час виконання поклав би в JavaScript лендингу чанк на 12 072 байти, 4 493 байти після gzip, бо пакет не оголошував, що не має побічних ефектів, і tree-shaking нічого не міг прибрати (#160). Вебсайт тримає власні назви тарифів і пов’язує їх із контрактом на рівні типів, що нічого не коштує під час виконання:

```ts title="src/modules/license/license.constants.ts"
export const LICENSE_TIER = {
  AGENCY: "agency",
  COMPLETE: "complete",
  CORE: "core",
} as const satisfies Record<string, Api["tier"]>
```

Тариф, доданий чи видалений з будь-якого боку, не компілюється на вебсайті, а тест порівнює значення. Починаючи з #244, конфігуратор на лендингу теж читає запитання, варіанти й правила стеку з пакета, тож вебсайт не тримає копії матриці.

Спільний контракт прибирає дубльоване знання. Він не прибирає розбіжності версій між розгортаннями. 20 листопада опублікований CLI надіслав поле, яке вебсайт у продакшні, що досі працював на попередній версії контракту, відхилив. Обидва репозиторії проходили кожен тест проти версії, яку закріпили. [Перший допис цієї серії](/blog/ai-coding-agent-guardrails) розповідає цю історію; правило, яке з неї вийшло: зміна контракту починає працювати на сервері раніше, ніж випускають клієнт, який її використовує.

### Дрейф, який ми знайшли, поки це писали

Власний README пакета — така сама сторінка, як будь-яка інша, і дрейфує так само. README, опублікований разом із `@saasyland/stack` 0.1.0-beta.5, досі каже: «Конфігуратор на saasyland.com тримає власну копію матриці». Це було правдою до #244, злитого 20 листопада, який цю копію прибрав. npm робить такий дрейф липким: «Файл `README.md` оновиться на сторінці пакета лише тоді, коли ви опублікуєте нову версію свого пакета». README, який описує інший репозиторій, — це копія факту, яким володіє той репозиторій, і виправлення полягає в тому, щоб казати лише те, що робить сам пакет.

## Реєстр тверджень для того, що може довести тест

Деякі твердження стосуються поведінки: «ліцензії, за які повернули кошти, перестають працювати», «CLI записує лише ті варіанти, які ви обрали», «кожен рядок перекладено». Код не може їх вивести. Тест може їх довести, а реєстр може пов’язати кожне твердження з його тестом.

Репозиторій CLI веде такий реєстр. Його `docs/acceptance.md` перелічує кожну обіцянку, яку saasyland.com, його документація, юридичні сторінки й дописи, а також власні README CLI дають про CLI і проєкти, які він генерує. Кожен рядок має стабільний id, точні слова твердження, кожне місце, яке його робить, рівень тестів, що його доводить, і клітинку доказу в одному з трьох станів:

- **Доведено:** один чи кілька тестів, кожен названо за файлом і назвою.
- **Заплановано:** pull request, який додасть доказ.
- **Відкрито:** твердження сьогодні хибне або недоказове, і рядок каже, що мало б змінитися: продукт чи текст.

`bun run check` провалюється, коли доведене твердження називає тестовий файл чи назву тесту, яких не існує, коли заплановане твердження не називає запланованого pull request або коли два твердження мають однаковий id. Твердження, доведене тестом у репозиторії вебсайту, перевіряють проти вебсайту на закріпленому коміті тим самим завданням CI, яке запускає описаний нижче еталонний diff. Pull request, який додає тест для запланованого твердження, у тому самому коміті замінює заплановану клітинку цим тестом, а pull request, який змінює поведінку CLI, перевіряє рядки, що її описують.

Відкритий рядок — найкорисніший різновид. Він фіксує речення, яке каже текст, а продукт ще не робить, там, де його бачить кожен pull request, і має закінчитися рішенням: створити функцію або переформулювати текст.

Вебсайт має власний реєстр для одного виду тверджень. Кожен сценарій користувача й адміністратора перелічено в `e2e/data/<area>.flows.ts` разом із браузерним тестом, який виконує його наскрізно, або причиною, чому такого тесту ще немає, і `bun run check` провалюється, коли сценарій називає тест, якого вже немає (#253). Сторінка документації про [покриття тестами](/docs/tooling/test-coverage) виводить перелік: сьогодні сценаріїв загалом <RepositoryFact name="flows" />, із них покрито <RepositoryFact name="flowsCovered" />, без браузерного тесту <RepositoryFact name="flowsMissing" />, а <RepositoryFact name="flowsToBuild" /> — це функції, які ще треба створити. Той самий pull request зробив твердження про покриття точними: «100% покриття тестами» стало «100% покриття коду», бо це число вимірює рядки, які виконують модульні, інтеграційні й компонентні тести, а не сценарії, доведені в браузері. Одне запитання в розділі FAQ цю зміну оминуло, і його змінили 22 листопада.

### Чого реєстр не ловить

Реєстр перевіряє докази, а не твердження. Перевірка, яка читає лише клітинки з доказами, ніколи не порівнює слова рядка зі сторінкою, на яку він посилається, тож рядок може й далі цитувати речення після того, як текст переформулювали або прибрали. Якщо ви ведете реєстр, нехай перевірка читає і місця, на які посилаються рядки, а не лише названі в них тести, і видаляйте рядок, щойно його твердження зникає із сайту.

## Еталонний diff: згенерований результат проти справжнього продукту

Продукт, який генерує код, має ще одне твердження, яке треба тримати: згенерований проєкт — це те, що показує маркетинг. Репозиторій CLI порівнює їх напряму. Його скрипт `golden` генерує еталонний стек із шаблонів точно так, як це зробив би `init`, отримує вебсайт на закріпленому коміті й порівнює два дерева файл за файлом: ідентичні, навмисно змінені, різні чи відсутні. Закомічений список називає кожну навмисну відмінність із причиною, як-от юридичні сторінки, які є власним зобов’язанням клієнта й не генеруються. Звіт запускається на кожному pull request. Він поки що не блокує злиття; запланована зміна зробить його обов’язковим бар’єром із нічним звітом про дрейф.

Власні документи згенерованого проєкту тримають на тому самому рівні. Тести генерують стеки, не встановлюючи їх, і читають їхні README, `AGENTS.md` і workflow CI: ці документи не можуть називати скрипт, якого бракує в згенерованому `package.json`, змінну середовища, якої проєкт не визначає, шлях, якого він не містить і не створює, і жодної версії — версії вони лишають файлам, що їх закріплюють. Тож документація шаблону може казати лише те, що правдиве для стеку, який її містить.

## Зовнішні факти: датуйте, цитуйте, перевіряйте повторно

Факти про зовнішній світ неможливо вивести з вашого коду, і вони дрейфують найшвидше: ціни, результати опитувань, функції конкурентів, поведінка інструмента після його наступного випуску. Чесними їх тримають три правила.

1. **Цитуйте першоджерело** з посиланням і наводьте цитату, а не переказ числа.
2. **Датуйте кожну перевірку.** Наші дописи починаються рядком «Остання перевірка» й закінчуються приміткою про те, коли прочитано джерела.
3. **Перевіряйте повторно за розкладом** і оновлюйте дату `updated` допису, коли факт змінюється.

Повторна перевірка знаходить більше, ніж ви очікуєте. 17 листопада ми звірили кожен допис з його джерелами (#241). Статистику Stack Overflow процитували як 45%, тоді як опитування каже 66%; 45% було другим пунктом того самого списку. Частку використання застарілих API від 25 до 38% приписали не тій статті. Цифри дефектів, приписаної GitClear, на публічній сторінці GitClear не було взагалі. Ціни й кількості в конкурентів змінилися. Агенти написали ці речення впевнено, і вони пройшли кожну нашу перевірку, бо жодна перевірка не читає опитувань.

Комерційна причина дбати про це виходить за межі довіри. У Сполучених Штатах настанови FTC для рекламодавців кажуть, що «рекламодавці повинні мати докази на підтвердження своїх тверджень» і що «закон вимагає, щоб рекламодавці мали докази ще до виходу реклами». Сторінка продукту, яка виводить свої твердження з коду й перелічує поведінкові твердження з їхніми тестами, має ці докази за самою своєю побудовою.

## Скільки це коштує

Ніщо з цього не безкоштовне, і витрати варто знати ще до початку.

**Крок збірки й компоненти, які треба підтримувати.** Плагін фактів, компоненти, правила форматування та їхні тести — такий самий код, як будь-який інший. Вони потребують рев’ю і ламаються так, як не ламається вписаний вручну текст: факт, що читає файл, якого збірка не може знайти, зупиняє збірку.

**Розмір бандла, якщо ви неуважні.** Імпорт значення може імпортувати весь його модуль. Двічі очевидний спосіб поділитися значенням затягнув би на лендинг код, який йому не потрібен: 3,7 КБ коду адмінки, щоб порахувати розділи адмінки (#115), і 12 КБ матриці стеку й схем контракту, щоб поділитися трьома назвами тарифів (#160). Вимірюйте бандл, коли імпортуєте значення в публічну сторінку, і віддавайте перевагу зв’язкам на рівні типів або вузьким модулям.

**Текст, який витримує зміни.** Речення, що виводить число, має читатися правильно з будь-яким числом: «1 test file» і «221 test files», а також польською, де форм множини більше, ніж в англійській. Ми пишемо такі речення через множину ICU або перефразовуємо їх так, щоб число стояло окремо, а деяка граматика опирається: виведене число не завжди може прийняти відмінок, якого потребує речення німецькою чи польською, тож речення переписують навколо нього.

**Frontmatter без чисел.** Meta description і анонси не можуть виконувати код, тож вони описують, а не рахують. Це трохи коштує в пошукових сніпетах.

**Великі зміни, один раз.** Заміна вписаних вручну значень зачепила 643 файли в #137, бо кожне значення існувало дев’ятьма мовами. Зробити це рано набагато дешевше, ніж пізно.

Що це дає: кількості, ціни, ліміти, версії й кількість мов, які наша документація й дописи наводять про saasyland.com, виводяться з коду кожною мовою, а зміна в коді, яка зробила б процитований фрагмент чи довідкову таблицю хибними, провалює CI з назвою сторінки.

## Що досі дрейфує

Дечого описані вище механізми не досягають, і саме там досі з’являються помилки.

- **Текст без значення.** Які браузери запускаються на pull request, а які лише на `main`, — це факт про workflow CI без жодного числа, і лендинг подавав його хибно кожною мовою до #115. Таке речення ловить лише рев’ю або тест, який читає workflow.
- **Історичні числа.** Ця стаття навмисно вписує числа на кшталт 176, 221 і 643: вони описують, яким був репозиторій певного дня, і кожне прив’язане до pull request. Вони не дрейфують, бо це твердження про минуле. Числа в теперішньому часі виводяться з коду.
- **Значення в повідомленнях без аргументів.** Перевірка повідомлень порівнює аргументи перекладу з англійськими, але не шукає чисел у повідомленні, яке аргументів не має. Поки писалася ця стаття, ми знайшли одне таке: слоган поруч із формою входу вписував свою цифру покриття кожною мовою.
- **Документи поза збіркою,** як-от README пакета, опублікований в npm, які змінюються, лише коли хтось публікує нову версію.
- **Зовнішні факти** між повторними перевірками.

## Стартовий набір, який можна скопіювати

Ці частини підходять для більшості сайтів на TypeScript, зібраних за допомогою Vite. Це мінімальні версії описаного вище; адаптуйте назви.

**Плагін фактів**, який вимірює під час збірки й надає віртуальний модуль:

```ts
import { globSync, readFileSync } from "node:fs"
import type { Plugin } from "vite"
import { exactRegex } from "vite/rolldown/pluginutils"

const MODULE_ID = "virtual:facts"
const RESOLVED_ID = `\0${MODULE_ID}`

const collectFacts = () => ({
  testFiles: globSync("src/**/*.test.{ts,tsx}").length,
  nodeVersion: readFileSync(".nvmrc", "utf8").trim(),
})

export const facts = (): Plugin => ({
  name: "facts",
  resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_ID },
  load: { filter: { id: exactRegex(RESOLVED_ID) }, handler: () => `export default ${JSON.stringify(collectFacts())}` },
})
```

**Компонент**, який виводить факт для локалі сторінки, а код — як код:

```tsx
import facts from "virtual:facts"

export const Fact = ({ name, locale }: { name: keyof typeof facts; locale: string }) => {
  const value = facts[name]

  return typeof value === "number" ? <>{new Intl.NumberFormat(locale).format(value)}</> : <code>{value}</code>
}
```

**Статус і повідомлення з обома версіями**, а також тест, що рендерить обидві:

```ts
export const FEATURE_STATUS = { ARRIVING: "arriving", AVAILABLE: "available" } as const

export const BILLING = FEATURE_STATUS.ARRIVING
```

```json
{
  "billing": "{billing, select, available {Billing is wired in.} other {Billing is arriving in a later release.}}"
}
```

**Перевірка фрагментів** для блоків коду із заголовком-шляхом, яку слід запускати в CI:

````ts
import { readFileSync } from "node:fs"

const TITLED_BLOCK = /^```\w*\s+title="(?<path>[^"]+)"\n(?<code>[\s\S]*?)^```$/gmu

export const excerptProblems = (page: string, source: string): string[] =>
  [...source.matchAll(TITLED_BLOCK)].flatMap(({ groups }) =>
    readFileSync(groups?.path ?? "", "utf8").includes(groups?.code ?? "") ? [] : [`${page}: not an excerpt of ${groups?.path}`],
  )
````

**Реєстр тверджень** у вигляді таблиці у вашому репозиторії з перевіркою, що тест кожного доведеного рядка існує:

```md
| ID        | Claim                            | Where                | Proof                                                   |
| --------- | -------------------------------- | -------------------- | ------------------------------------------------------- |
| CLAIM-001 | "Refunded licences stop working" | pricing page, FAQ q4 | `test/licence.test.ts` › "a refund revokes the licence" |
| CLAIM-002 | "Exports to CSV"                 | features page        | Planned: the export pull request                        |
| CLAIM-003 | "Works offline"                  | landing page hero    | Open: no offline mode exists; reword or build it        |
```

**Правило рев’ю** для всього іншого, у вашому файлі інструкцій:

```md
## Numbers and claims

- Never type a count, price, limit, version, path or command into docs, copy or messages: print it from code.
- Every sentence about a feature that has not shipped goes through its status.
- Every external fact has a link to its primary source and the date it was checked.
```
