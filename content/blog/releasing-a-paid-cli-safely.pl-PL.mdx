faq:
  - question: Czym jest publikacja etapowa w npm?
    answer: >-
      Krokiem zatwierdzenia między CI a publicznym rejestrem. CI uruchamia npm stage publish, które
      nie wymaga drugiego składnika, a wersja czeka w npm na zatwierdzenie z dist-tagiem ustalonym
      już na tym etapie. Staje się publiczna dopiero wtedy, gdy zatwierdzi ją opiekun pakietu, na
      npmjs.com albo poleceniem npm stage approve, a npm w obu przypadkach wymaga uwierzytelniania
      dwuskładnikowego. Odrzucona wersja zostaje usunięta bez publikacji.
  - question: Publikować z CI przez zaufanego wydawcę czy tokenem npm?
    answer: >-
      Przez zaufanego wydawcę. CI wymienia krótkotrwały token OIDC z GitHub Actions albo GitLaba na
      dane uwierzytelniające do publikacji, więc nie ma długotrwałego tokena, który trzeba by
      przechowywać, rotować i chronić przed wyciekiem. Uprawnienie id-token write daj tylko zadaniu,
      które publikuje. Jeśli chcesz też, żeby wydania zatwierdzał człowiek, pozwól zaufanemu wydawcy
      tylko wystawiać wersje do zatwierdzenia. W ustawieniach pakietu wymagaj uwierzytelniania
      dwuskładnikowego i zabroń publikacji tokenami.
  - question: Czy publikacja przez zaufanego wydawcę daje pakietowi poświadczenie pochodzenia?
    answer: >-
      Tylko z publicznego repozytorium. npm automatycznie generuje poświadczenia pochodzenia przy
      publikacji przez zaufanego wydawcę, gdy publiczne są zarówno repozytorium źródłowe, jak i
      pakiet, a dla prywatnych repozytoriów ich nie generuje. Pakiet zbudowany z prywatnego
      repozytorium wciąż ma podpis rejestru npm, który weryfikuje npm audit signatures, ale nie ma
      poświadczenia pochodzenia.
  - question: Kiedy workflow wydania powinien tworzyć tagi Gita i GitHub Releases?
    answer: >-
      Gdy rejestr już udostępnia wersję, a nie wtedy, gdy CI ją wystawia albo publikuje. Wystawiona
      wersja może zostać odrzucona, zastąpiona albo po prostu nigdy niezatwierdzona, a wtedy tag i
      Release opisują pakiet, którego nikt nie może zainstalować. Najpierw sprawdź w rejestrze
      dokładnie tę wersję, zadbaj o to, żeby zadanie można było bezpiecznie uruchamiać dowolną
      liczbę razy, i uruchamiaj je ponownie po każdym zatwierdzeniu.
  - question: Jak sprawić, żeby CLI pobierało dokładnie te pliki, z którymi je wydano?
    answer: >-
      Przypnij w publikowanym kodzie skrót zawartości, a nie skompresowanego pliku, i zapisz go
      wtedy, gdy powstaje wersja. Prześlij plik, zanim pakiet będzie można zainstalować, niech
      serwer odpowiada rozmiarem i skrótem, które przechowuje, i odrzucaj każde pobranie, którego
      rozmiar albo skrót różni się od odpowiedzi serwera albo od przypiętego skrótu, zanim cokolwiek
      z niego odczytasz.
  - question: Czy pusty changeset może zablokować wydanie?
    answer: >-
      Tak. Akcja Changesets uznaje, że nie ma nic do zrobienia, gdy każdy oczekujący changeset jest
      pusty, nawet jeśli na gałęzi jest wersja, której npm jeszcze nie ma. Przytrafiło się to nam,
      gdy pusty changeset trafił na gałąź po zbudowaniu pull requesta z nową wersją, a ten pull
      request scalono bez przebudowania. Scalaj pull request z nową wersją tylko wtedy, gdy
      zbudowano go z najnowszego commita gałęzi.
  - question: Co zrobić, gdy opublikowana wersja w npm jest zepsuta?
    answer: >-
      Oznacz ją jako przestarzałą z komunikatem, który podaje poprawioną wersję, a poprawkę wydaj
      jako nową wersję poprawkową zwykłym procesem. Nie cofaj publikacji: npm nigdy nie pozwala
      ponownie użyć tej samej nazwy i wersji, a każdy projekt, który przypiął tę wersję, przestaje
      działać. Wersję, która jest tylko wystawiona do zatwierdzenia, można zamiast tego odrzucić.
  - question: Czy agenci AI powinni móc publikować pakiety?
    answer: >-
      Mogą robić wszystko aż do rejestru: changesety, pull requesty z nową wersją, zmiany w
      workflowach poddane przeglądowi, informacje o wydaniu, weryfikację i zapis wydania. Krok,
      którego nie da się cofnąć, powinien wymagać składnika, którego nie ma żaden agent, na przykład
      zatwierdzenia wystawionej wersji przez opiekuna pakietu uwierzytelnianiem dwuskładnikowym, a
      nigdzie nie powinno być tokena publikacji, którego agent mógłby użyć.

## Krótka odpowiedź

Traktuj wydanie jako jedyny krok, który nie jest scaleniem. Wszystko przed rejestrem da się zautomatyzować i powtórzyć: nadanie wersji na podstawie changesetów, build, jednokrotne spakowanie, uruchomienie zbudowanego programu na każdej obsługiwanej platformie i przesłanie wszystkiego, co CLI będzie pobierać. Krok, którego nie da się cofnąć, czyli pojawienie się wersji w npm, dostaje drugi klucz, którego nie ma żaden workflow. Wystawiaj wydanie do zatwierdzenia z CI przez zaufanego wydawcę w npm (trusted publishing), który zamiast zapisanego tokena używa krótkotrwałego tokena OIDC, a wystawioną wersję niech zatwierdza opiekun pakietu uwierzytelnianiem dwuskładnikowym. Wszystko, co CLI pobiera w czasie działania, przypnij skrótem zawartości i sprawdzaj względem dwóch źródeł. Tagi Gita i GitHub Releases twórz dopiero wtedy, gdy npm udostępnia wersję, bo wystawiona wersja może nigdy nie zostać opublikowana. I uważaj na chwile, w których narzędzie do wydań uznaje według własnych reguł, że nie ma nic do zrobienia: pusty changeset sprawił kiedyś, że jedna z naszych wersji beta w ogóle nie została wystawiona, choć wszystkie zadania były zielone.

## Dlaczego wydanie to nie scalenie

Scalenie można cofnąć kolejnym scaleniem. Wydania nie, z trzech powodów.

**Numer wersji jest zajęty na zawsze.** Zasady npm dotyczące cofania publikacji nie zostawiają złudzeń: „Gdy `package@version` zostanie raz użyte, nie można go już nigdy użyć ponownie”. I dalej: „Dotyczy to nawet pakietu, którego publikację cofnięto”. Samo cofnięcie publikacji jest dozwolone w ciągu pierwszych 72 godzin tylko wtedy, gdy żaden inny pakiet w rejestrze nie zależy od Twojego, a później tylko na surowszych warunkach; we wszystkich pozostałych przypadkach npm zaleca oznaczenie wersji jako przestarzałej. Złe wydanie naprawia się nową wersją, a zła wersja zostaje w rejestrze dla każdego, kto ją przypiął.

**Klienci opierają na nim swoje skrypty.** Publiczny interfejs CLI jest szerszy niż eksporty biblioteki: to jego polecenia, flagi i wartości domyślne, kody wyjścia, wynik przeznaczony dla programów, pliki, które zapisuje, i środowiska uruchomieniowe, w których startuje. Zmieniona wartość domyślna albo nowy kod wyjścia psuje zadanie CI, którego nigdy nie zobaczysz.

**Płatne CLI ma więcej niż jedną ruchomą część.** Nasze sprawdza licencję w saasyland.com przy każdym tworzeniu projektu i przez API licencji serwisu pobiera szablony, z których generuje projekt, w jednej paczce na wydanie. Wydanie to pakiet w npm plus paczka szablonów w magazynie obiektów plus kontrakt z serwerem. Te trzy elementy muszą się zgadzać od pierwszej minuty, w której klient może zainstalować wersję.

Agenci AI zmieniają to, gdzie leży ryzyko. W odwracalnych częściach są szybcy i dokładni: piszą changesety, pilnują, żeby pull request z nową wersją był aktualny, edytują workflowy, piszą informacje o wydaniu w <RepositoryFact name="languages" /> językach, a potem sprawdzają rejestr. W części nieodwracalnej są dokładnie tak samo pewni siebie jak we wszystkim innym. Dlatego zasada projektowa tego wpisu jest prosta: niech agenci robią wszystko aż do rejestru, niech każdy krok przed nim da się bezpiecznie uruchomić dwa razy, a jedyny krok, który nie jest ani odwracalny, ani powtarzalny, niech wymaga klucza w rękach człowieka.

Kilka słów o naszym układzie, żeby łatwiej było przełożyć go na Twój. CLI SaaSy Land to trzy pakiety npm, `saasyland`, `create-saasyland` i `@saasyland/stack`, wydawane z prywatnego repozytorium na GitHubie za pomocą Changesets 3 i GitHub Actions. Według stanu na 25 listopada 2026 wersje zapoznawcze wychodzą w tagu <RepositoryFact name="cliReleaseChannel" /> w npm, najnowsza to 0.1.0-beta.5 z 20 listopada, a klienci uruchamiają <RepositoryFact name="cliPackageSpec" />; w `latest` wciąż jest wydanie zastępcze `0.0.0`, które zarezerwowało nazwy. Agenci to sesje Claude Code: agent prowadzący i wykonawcy, dla których przygotowuje briefy, i to oni odpowiadają za CLI od początku do końca. Gdy właściciel im je przekazał, poprosił o „wersjonowanie, listę zmian i wszystko tak profesjonalnie, jak się da”, wydawane „partiami, które naprawdę mają sens”. Każdą publikację zatwierdza sam.

## Cały proces w jednej tabeli

Każdy wiersz to krok wydania: co się w nim uruchamia, co może coś zapisać i co go zatrzymuje. Dalsza część wpisu omawia wiersze w kolejności, w jakiej mogą zawieść.

| Krok                           | Co się uruchamia                                                                    | Co może zapisać                       | Co go zatrzymuje                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------- | ------------------------------------- | --------------------------------------------------------------------------------- |
| Pull request                   | CI na Linuksie i kontrola changesetów                                               | Nic poza pull requestem               | Dowolna kontrola albo zmiana w publikowanym pakiecie bez changesetu               |
| Pull request z nową wersją     | `changeset version`, a potem przypięcie szablonów                                   | Własną gałąź i własny pull request    | Recenzent, który znajdzie zły numer wersji albo notatkę niezrozumiałą dla klienta |
| Scalenie do `main` albo `beta` | Wybór trybu: nowa wersja, publikacja albo nic                                       | Nic                                   | Brak czegokolwiek do opublikowania                                                |
| Pakowanie                      | Formatowanie, lint, typy, testy przy pełnym pokryciu, testy dymne, `changeset pack` | Artefakt ze spakowanymi pakietami     | Każdy błąd                                                                        |
| Zbudowane programy             | Dziewięć zadań: Linux, macOS i Windows, na każdym trzy wersje Node, do tego Bun     | Nic                                   | Dowolne z dziewięciu                                                              |
| Wystawienie                    | Weryfikacja i przesłanie paczki szablonów, potem `npm stage publish`                | Magazyn szablonów i wystawioną wersję | Paczka inna niż przypięta albo odrzucona wymiana tokenów                          |
| Zatwierdzenie                  | Opiekun pakietu, z uwierzytelnianiem dwuskładnikowym                                | Publiczną wersję i jej dist-tag       | Jakikolwiek problem z wystawioną wersją                                           |
| Zapis wydania                  | Najpierw pytanie do npm, potem tagi Gita i GitHub Releases                          | Tagi i Releases                       | Wersja, której npm jeszcze nie udostępnia                                         |
| Po wydaniu                     | Instalacja z npm w czystym katalogu i informacje o wydaniu w serwisie               | Serwis                                | Nieudana kontrola zainstalowanej wersji                                           |

## Wersjonowanie, na którym klient może polegać

### Zapisz, co w CLI łamie zgodność

Wersjonowanie semantyczne pomaga tylko wtedy, gdy masz na piśmie, co jest Twoim publicznym interfejsem. Nasze zasady wydań wymieniają, co w CLI łamie zgodność:

- usunięcie polecenia, flagi albo wartości flagi, zmiana ich nazwy albo zmiana wartości domyślnej;
- inny kod wyjścia w tej samej sytuacji;
- usunięcie pola z wyniku `--json`, zmiana jego nazwy albo typu, przy czym nowe pole nie łamie zgodności;
- zmiana w manifeście projektu, której starsze CLI nie potrafi odczytać;
- wyższa minimalna wersja Node;
- usunięty albo zmieniony eksport współdzielonego pakietu;
- zmiana, którą za łamiącą zgodność uznają własne reguły API licencji.

Przed 1.0 zmiana drugiej liczby w numerze wersji oznacza nowe funkcje albo zmianę łamiącą zgodność, a zmiana trzeciej – tylko poprawki. API licencji stosuje tę samą dyscyplinę na własnej granicy. W ramach `v1` serwis może dodać pole odpowiedzi, endpoint albo kod błędu, a CLI ignoruje pola, których nie zna; wszystko inne wymaga `v2` udostępnianego obok `v1` tak długo, jak wywołuje je jakaś obsługiwana wersja CLI. [Pierwszy wpis z tej serii](/blog/ai-coding-agent-guardrails) opisuje, jak opublikowane CLI wysyłało pole, którego działający serwis jeszcze nie przyjmował, i dlaczego zmiana kontraktu trafia teraz najpierw na serwer.

### Changeset to informacja o wydaniu dla klientów

Każdy pull request, który zmienia publikowany pakiet, dodaje changeset, a CI odrzuca pull request, który tego nie robi: `changeset status --since=origin/<base>` kończy się błędem, gdy pakiet zmienił się bez changesetu. Ważniejsza reguła dotyczy treści. Changeset to informacja o wydaniu dla klienta: jedno albo dwa proste zdania o tym, co się dla niego zmienia i co musi zrobić, z poleceniami i flagami zapisanymi tak, jak je wpisuje. „Poprawka błędu w parserze flag” nic klientowi nie mówi. Tak wygląda notatka do 0.1.0-beta.5 w publicznych [informacjach o wydaniach](/docs/cli/releases):

> **Zmiana łamiąca zgodność:** opcja `--billing lemonsqueezy` została usunięta, ponieważ Lemon Squeezy kończy działalność: od 16 listopada 2026 nie przyjmuje nowych rejestracji, a 31 marca 2027 zostanie zamknięte. `--billing polar` i `--billing stripe` pozostają wartościami, które `--billing` zna, ale `init` nadal odrzuca obie z kodem <RepositoryFact name="cliExitNotAvailable" />, bo wygenerowane projekty nie mają jeszcze płatności. `init --billing lemonsqueezy` kończy teraz działanie z kodem <RepositoryFact name="cliExitUsage" />, jak każda inna wartość, której `--billing` nie zna.

To, jak zapiszesz regułę, decyduje o tym, co produkują agenci. Agent, któremu każe się tylko „dodać changeset”, zwykle pisze „Refaktoryzacja parsera flag”. Agent, który wie, że changeset to tekst, który klient przeczyta na liście zmian, pisze notatkę taką jak powyżej. Zmiana, której klienci nie mogą zauważyć, na przykład refaktoryzacja albo nowy test, dostaje pusty changeset. Ta furtka jest źródłem drugiego incydentu w tym wpisie.

### Jedna wersja dla pakietów wydawanych razem

Trzy pakiety tworzą w Changesets grupę o stałej wersji, w której „wszystkie pakiety z grupy dostają nową wersję i są publikowane razem, nawet gdy nie ma w nich zmian”. Dlatego `saasyland@0.1.0-beta.5` zawsze wychodzi razem z `@saasyland/stack@0.1.0-beta.5`, a klient, zgłoszenie błędu i odpowiedź pomocy technicznej posługują się jednym numerem. Koszt widać na liście zmian: pakiet, który sam nie ma nic do powiedzenia, i tak dostaje wydanie, a informacje o wydaniach w naszym serwisie wypisują dla niego „Brak zmian w tym wydaniu.”, zamiast zostawiać lukę, która wygląda na przeoczenie.

### Wydawaj partiami i nie spiesz się ze scaleniem pull requesta z nową wersją

Changesets utrzymuje otwarty pull request Version Packages i przebudowuje go, gdy scalane są kolejne changesety. To ten pull request decyduje o wydaniu: jego scalenie jest decyzją o wydaniu. Wydajemy spójnymi partiami, nigdy po jednym wydaniu na pull request. Na `main` pull request Version Packages dla 0.1.0 jest otwarty od 14 listopada, a 25 listopada zawierał 24 changesety; zostanie scalony, gdy stabilna partia będzie kompletna i opisana w dokumentacji.

Wersje zapoznawcze wychodzą z gałęzi `beta` w trybie wydań przedpremierowych Changesets (pre mode). Jego dokumentacja ostrzega, że „wydania przedpremierowe są bardzo skomplikowane!” i że „błędy mogą doprowadzić repozytorium i publikację do stanu, który bardzo trudno naprawić”. Oba zdania się u nas sprawdziły, jak zobaczysz niżej. Jeśli korzystasz z tego trybu, trzymaj go na osobnej gałęzi, utrzymuj liniową historię tej gałęzi, żeby tagi wydań wskazywały historię, którą da się przeczytać, i przenoś na nią zmiany z `main` w sposób, który da się przejrzeć. My przenosimy commity z `main` przez cherry-pick na gałąź utworzoną z `beta` i scalamy ją przez squash, więc `beta` nigdy nie dostaje commita scalającego.

### README w npm jest częścią wydania

Do pierwszego stabilnego wydania w `latest` jest wydanie zastępcze, więc README, które każe uruchomić `npx saasyland init`, uruchamia wydanie zastępcze, w którym nie działa żadne polecenie. W 0.1.0-beta.1 spakowane pliki README robiły dokładnie to, a polecenia `create` bez tagu też trafiały na `latest`. Teraz test dymny czyta README w każdym spakowanym pakiecie i kończy się błędem, gdy polecenie podaje któryś z pakietów bez dist-tagu albo z innym dist-tagiem. Dist-tag, którego oczekują testy, jest zadeklarowany w jednym miejscu, a jego zmiana to jeden z kroków pierwszego stabilnego wydania. Z tego samego powodu [przewodnik po CLI](/docs/cli) w naszym serwisie wypisuje swoje polecenia z jednej stałej, <RepositoryFact name="cliPackageSpec" />.

## Publikacja etapowa: człowiek trzyma klucz w samym rejestrze

### Czym jest publikacja etapowa

Publikacja etapowa w npm (staged publishing) „dodaje krok zatwierdzenia, zanim pakiety pojawią się publicznie w rejestrze npm”. CI uruchamia `npm stage publish`, które „nie wymaga 2FA”, i w ten sposób wystawia wersję do zatwierdzenia, a wersja czeka w npm, aż zatwierdzi ją opiekun pakietu: „Weryfikacja 2FA będzie wymagana niezależnie od tego, czy zatwierdzasz pakiet w CLI, czy na npmjs.com”. Odrzucenie wystawionej wersji też wymaga drugiego składnika. Dist-tag ustala się w chwili wystawienia: „Tag jest niezmienną właściwością wystawionego pakietu”. Publikacja etapowa wymaga npm 11.15.0 lub nowszego; nasze zadanie wystawiające używa npm dołączonego do Node 26.13.1, czyli npm 11.20.0, i wypisuje w podsumowaniu wersję npm, którą wystawiło wydanie.

npm stopniowo przestawia na ten model wszystkich. Jego lista zmian z września 2026 mówi, że „npm planuje na styczeń 2027 usunięcie bezpośredniej publikacji przez tokeny omijające 2FA”, a jako drogę migracji dla automatyzacji, która nie może jeszcze przejść na zaufanego wydawcę, proponuje tokeny, które mogą tylko wystawiać wersje do zatwierdzenia. Nasze przebiegi wystawiające zapisują w logu komunikat npm: „npm tokens that bypass 2FA are being restricted for account changes and direct publishing.”

### Dlaczego klucz jest w npm, a nie w CI

GitHub potrafi przez środowiska wstrzymać zadanie, dopóki nie zatwierdzi go recenzent, a przewodnik Changesets sugeruje „utworzenie środowiska z wymaganymi recenzentami, którzy zatwierdzają uruchomienie zadania publikacji”. My umieściliśmy klucz w npm, z dwóch powodów. Chroni on samą nieodwracalną rzecz: cokolwiek zrobi workflow i cokolwiek scali agent, nic nie staje się publiczne, dopóki opiekun pakietu nie zatwierdzi dokładnie tej wystawionej wersji. Opiera się też na drugim składniku uwierzytelniania opiekuna w npm, którego nie może mieć żaden workflow, agent ani token GitHuba. Zatwierdzenie w CI chroni zadanie, a gdy już zostanie udzielone, to zadanie może opublikować wszystko, co zbudowało. Do tego GitHub oferuje wymaganych recenzentów w prywatnych repozytoriach tylko w planach Enterprise, więc dla wielu zespołów rejestr jest jedynym miejscem, w którym taka blokada jest w ogóle dostępna.

### Changesets jeszcze nie wystawia wersji, więc wystawiaj według jego planu

Przewodnik Changesets mówi wprost: „Na razie publikacja etapowa nie działa z Changesets, więc na tę chwilę używaj zamiast niej zaufanego wydawcy”. Ogłoszenie wersji 3 zapowiada publikację etapową w „następnej aktualizacji z nowymi funkcjami”. Do tego czasu akcja publikująca Changesets uruchamia `npm publish`, które zaufany wydawca z prawem tylko do wystawiania odrzuca. Dlatego nasze zadanie wystawiające robi to, co zrobiłaby akcja, ze zmienionym jednym poleceniem. Czyta plan publikacji, który `changeset pack` zapisuje obok spakowanych pakietów, i wystawia każdy pakiet z dostępem i dist-tagiem wybranymi przez Changesets: `beta` w trybie wydań przedpremierowych, `latest` w pozostałych przypadkach.

Dla każdego pakietu z tego planu zadanie najpierw pyta npm, przez publiczne `npm view`, które nie potrzebuje danych uwierzytelniających, czy rejestr udostępnia już dokładnie tę wersję. Jeśli nie, uruchamia `npm stage publish` na spakowanym pakiecie z dostępem i dist-tagiem z planu oraz z flagą `--json` i odczytuje identyfikator wystawienia z odpowiedzi npm. Każdy pakiet kończy się dokładnie jednym z trzech wyników i właśnie dlatego zadanie można bezpiecznie uruchomić ponownie, a to ważne, bo zadanie wydania to właśnie to, które najbardziej chcesz uruchomić jeszcze raz, gdy zawiedzie runner:

- **Już w npm:** pakiet zostaje pominięty. Ani push do `main` po wydaniu, ani ponowne uruchomienie nie próbuje publikować drugi raz.
- **Wystawiony przez wcześniejszy przebieg:** npm odpowiada kodem 409, a zadanie to zgłasza i idzie dalej. Token zaufanego wydawcy może wystawiać i publikować, ale npm podaje, że „krótkotrwałe tokeny nie mogą uruchamiać podpoleceń `npm stage`”, więc zadanie nie może wypisać wystawionych wersji, żeby znaleźć wcześniejszy identyfikator; jego podsumowanie mówi osobie zatwierdzającej, gdzie go szukać.
- **Cokolwiek innego:** zadanie zatrzymuje się przed następnym pakietem.

Podsumowanie zadania to lista rzeczy do zrobienia dla osoby zatwierdzającej: jeden wiersz na pakiet, z jego wersją, dist-tagiem, identyfikatorem wystawienia i dokładnym poleceniem, które go zatwierdza. Trzy pakiety to jedno wydanie, więc zatwierdza się wszystkie trzy razem. Zestaw do wydań na końcu tego wpisu zawiera ogólną wersję tego zadania, napisaną na podstawie dokumentacji npm, dla repozytorium bez Changesets.

### Co zapisuje rejestr

W przypadku wersji 0.1.0-beta.5 metadane npm podają, że opublikowało ją GitHub Actions przez zaufanego wydawcę, i wskazują opiekuna, który ją zatwierdził. Wystawiono ją 20 listopada o 11:25 UTC, a publiczna stała się o 11:44. Ten zapis to ślad audytowy: który workflow wytworzył bajty i która osoba je wypuściła.

## Zaufany wydawca: żadnego tokena, który mógłby wyciec

### Krótkotrwałe dane uwierzytelniające, tylko w jednym zadaniu

Publikacja przez zaufanego wydawcę (trusted publishing) pozwala CI publikować „przy użyciu krótkotrwałych tokenów podpisanych kryptograficznie”, uzyskanych przez OIDC dostawcy CI zamiast zapisanego tokena npm. Wymaga npm 11.5.1 i Node 22.14.0 lub nowszych, a na GitHubie „kluczowym wymaganiem jest uprawnienie id-token: write”. Po stronie npm zaufany wydawca wskazuje organizację albo użytkownika GitHuba, repozytorium, plik workflow i opcjonalnie środowisko. Dwa kolejne ustawienia zamykają pozostałe furtki:

- **Zaufany wydawca może tylko wystawiać.** W CLI npm to `npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish`, bez `--allow-publish`. Dokumentacja npm mówi, że dla zaufanego wydawcy „`npm stage publish` jest zawsze dozwolone”, a bezpośrednia publikacja i zmiany dist-tagów to osobne opcje, wyłączone, dopóki nie włączy ich opiekun pakietu.
- **Prawo publikacji wymaga uwierzytelniania dwuskładnikowego i zabrania tokenów.** npm zaznacza, że to ustawienie „dotyczy tylko tradycyjnego uwierzytelniania tokenami”, więc zaufany wydawca dalej działa, a żaden token, gdziekolwiek zapisany, nie może publikować.

Zaufanego wydawcę konfiguruje się w ustawieniach pakietu na npmjs.com, więc nowa nazwa pakietu kosztuje jeden ręczny krok: właściciel sam publikuje wydanie zastępcze `0.0.0`, z uwierzytelnianiem dwuskładnikowym, a potem dodaje zaufanego wydawcę i ustawienie dostępu. Dlatego w `latest` jest dziś `0.0.0`.

Po stronie GitHuba workflow zaczyna się od `permissions: {}`, a każde zadanie prosi o to, czego potrzebuje. Przewodnik Changesets ujmuje to prosto: „upewnij się, że `id-token: write` jest ustawione tylko w zadaniu, które musi publikować”.

| Zadanie                                            | Uprawnienia                                                | Po co                                                          |
| -------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| Wybór trybu wydania                                | `contents: read`                                           | Czyta oczekujące changesety                                    |
| Otwieranie pull requesta z nową wersją             | `contents`, `pull-requests` i `actions` do zapisu          | Wypycha gałąź wydania, otwiera pull request, uruchamia jego CI |
| Budowanie, weryfikacja i pakowanie                 | `contents: read`                                           | Buduje, testuje i pakuje                                       |
| Uruchamianie zbudowanych programów, dziewięć zadań | `contents: read`                                           | Buduje i uruchamia programy                                    |
| Wystawianie w npm                                  | `contents: read` i `id-token: write`, chronione środowisko | Wymienia w npm token OIDC i przesyła paczkę szablonów          |
| Tworzenie tagów i Releases                         | `contents: write`                                          | Tworzy tagi i Releases                                         |

Zadanie wystawiające jako jedyne może poprosić o token OIDC i jako jedyne korzysta z chronionego środowiska. To środowisko przechowuje dane uwierzytelniające do magazynu szablonów, a wdrażać do niego mogą tylko gałęzie wydań. GitHub udostępnia sekrety środowiska „tylko zadaniom workflow, które korzystają z tego środowiska”, więc żadne inne zadanie ani żaden przebieg workflow z innej gałęzi nie może ich odczytać.

### Token w kopii roboczej też jest uprawnieniem

`actions/checkout` zostawia token zadania w lokalnej konfiguracji Gita, „żeby uruchamiać uwierzytelnione polecenia Gita”, chyba że ustawisz `persist-credentials: false`. Ustawiliśmy tę opcję na false w każdym zadaniu i pierwszy pull request Version Packages nigdy się nie otworzył: gdy Changesets wypychało gałąź wydania, Git zgłosił „could not read Username for 'https://github.com'”. Poprawka oddała token temu jednemu zadaniu, jedynemu, które coś wypycha. Zasada najmniejszych uprawnień dotyczy każdego zadania z osobna, a nie jednego ustawienia powielonego w całym pliku.

### Błąd, którego npm nie potrafił wyjaśnić

Pierwsza beta trafiła do npm dwanaście godzin po scaleniu jej pull requesta z nową wersją. 14 listopada o 06:18 UTC zadanie wystawiające zakończyło się błędem zgłoszonym przez samo npm:

```text
npm error code ENEEDAUTH
npm error need auth This command requires you to be logged in to https://registry.npmjs.org/
```

Komunikat każe się zalogować. Prawdziwym powodem była nieudana wymiana tokena OIDC, a npm zapisuje ten powód na poziomie verbose, w logu debugowania na runnerze, który znika razem z zadaniem. Zmieniliśmy zadanie wystawiające tak, żeby przy każdym niepowodzeniu przesyłało `~/.npm/_logs/` jako artefakt, a log z następnego niepowodzenia wskazał przyczynę: npm nie znalazł zaufanego wydawcy, który pasowałby do repozytorium, workflow i środowiska przebiegu. Dokumentacja npm ostrzega właśnie przed tym: „npm nie weryfikuje konfiguracji zaufanego wydawcy, gdy ją zapisujesz” oraz „Wszystkie pola rozróżniają wielkość liter i muszą się dokładnie zgadzać”. Gdy ustawienia na npmjs.com zgodziły się z workflow, ponowne uruchomienie nieudanego zadania wystawiło 0.1.0-beta.0 o 18:24, a właściciel zatwierdził tę wersję cztery minuty później.

Ta lekcja wykracza poza npm. Gdy zawodzi warstwa uwierzytelniania, jej komunikat o błędzie zwykle opisuje ostatni sposób, jaki wypróbowała, a nie krok, który zawiódł pierwszy. Zachowuj log debugowania narzędzia z każdego nieudanego zadania wydania, z krótkim czasem przechowywania, i przeczytaj go, zanim cokolwiek zmienisz.

### Poświadczenie pochodzenia wymaga publicznego repozytorium

W publicznym repozytorium zaufany wydawca daje poświadczenie pochodzenia (provenance) bez dodatkowej pracy: npm „automatycznie generuje i publikuje poświadczenia pochodzenia”, ale tylko gdy „publikujesz z publicznego repozytorium” i „publikujesz publiczny pakiet”, a „generowanie poświadczeń pochodzenia nie jest obsługiwane w prywatnych repozytoriach”. Nasze CLI jest komercyjne, a jego repozytorium prywatne, więc jego pakiety nie mają poświadczenia pochodzenia. Mają za to podpis rejestru npm, który każdy może sprawdzić: w czystym katalogu z zainstalowanym `saasyland@0.1.0-beta.5` polecenie `npm audit signatures` zgłasza „1 package has a verified registry signature”. Jeśli Twój kod źródłowy jest publiczny, włącz poświadczenie pochodzenia i powiedz użytkownikom, jak je weryfikować. Jeśli jest prywatny, napisz to wprost, zamiast pozwalać, żeby słowo „zaufany” sugerowało gwarancję, której nie masz.

## Przypnij wszystko, co pobiera CLI

### Szablony są częścią wydania, ale nie pakietu

`saasyland init` generuje projekt z szablonów, których nie zawiera. Po sprawdzeniu licencji pobiera przez API licencji serwisu paczkę szablonów własnego wydania. Dzięki temu płatne szablony nie trafiają do publicznego pakietu w npm, ale każde wydanie dostaje drugi artefakt, o którym npm nic nie wie. Wynikają z tego dwie reguły: paczka, którą dostaje klient, musi być dokładnie tą, z którą wydanie przetestowano, i musi istnieć, zanim ktokolwiek będzie mógł wydanie zainstalować.

### Skrót zawartości, a nie kompresji

Paczka jest budowana deterministycznie: warstwy są posortowane według identyfikatora, pliki według ścieżki, klucze mają stałą kolejność, a z systemu plików nie zapisuje się nic poza zawartością każdego pliku i jego bitem wykonywalności. Jej skrót to SHA-256 JSON-u w archiwum, a nie bajtów gzipa, bo Node i Bun kompresują ten sam JSON do różnych bajtów. Gdy to zmierzyliśmy, skróty archiwów się różniły, a skróty zawartości nie. Skrót skompresowanego pliku identyfikuje kompresor; przestałby się zgadzać przy pierwszej aktualizacji zlib w którymś środowisku uruchomieniowym, a klient usłyszałby, że pobrany plik jest uszkodzony.

### Przypinaj przy nadawaniu wersji, weryfikuj przed przesłaniem, przesyłaj przed wystawieniem

Przypięty skrót zapisuje się w pull requeście Version Packages. Skrypt wersji uruchamia `changeset version`, potem buduje paczkę nowej wersji i dodaje jej skrót do pliku przypiętych skrótów w CLI, więc recenzent widzi zmianę numeru wersji i przypięty skrót obok siebie, a wydanie ma skrót we własnym kodzie. Przypinanie odmawia zmiany skrótu, który jest już przypięty. Każde CLI zawiera też skróty wszystkich wcześniejszych wydań, bo `update`, gdy się pojawi, będzie odtwarzać wydanie, z którego utworzono projekt, jako bazę swojego scalenia.

W chwili wydania zadanie wystawiające przebudowuje paczkę i kończy się błędem, jeśli jej skrót różni się od przypiętego. Potem przesyła archiwum, ze skrótem w metadanych obiektu, do magazynu, z którego czyta API licencji, i odczytuje z powrotem każdy obiekt: jego rozmiar, typ zawartości, metadane i skrót zawartości. Dopiero wtedy cokolwiek wystawia w npm, bo opublikowane CLI nigdy nie może prosić o paczkę, której nie ma. Przesyłanie odrzuca każde archiwum, które nie jest przypiętą paczką, więc ponowne uruchomienie nigdy nie zmieni tego, co udostępnia wydanie.

### Sprawdzaj dwa razy, względem dwóch źródeł

Serwis odpowiada na żądanie paczki krótkotrwałym podpisanym adresem URL, ważnym przez <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, oraz rozmiarem i skrótem paczki, które odczytuje z nagłówka zapisanego obiektu, nie otwierając archiwum:

```ts title="src/modules/license/license.api.ts"
const storedBundle = async (version: string): Promise<StoredBundle> => {
  const key = bundleObjectKey(version)
  const object = await env.BUNDLES.head(key)

  if (object === null) {
    return { error: { code: API_ERROR.VERSION_NOT_FOUND, version }, success: false }
  }

  const metadata = bundleMetadataSchema.safeParse(object.customMetadata)

  if (!metadata.success) {
    throw new Error(`${key} has no ${BUNDLE_METADATA.SHA256} digest in its custom metadata`, { cause: metadata.error })
  }

  return { bundle: { sha256: metadata.data[BUNDLE_METADATA.SHA256], size: object.size }, success: true }
}
```

Obiekt bez skrótu nie jest udostępniany: API odpowiada `serviceUnavailable`, a log wskazuje ten obiekt. Następnie CLI pobiera archiwum, czyta nie więcej niż zapowiedziany rozmiar i odrzuca je, jeśli jego rozmiar i skrót nie zgadzają się z odpowiedzią API, a skrót także z przypiętym skrótem wkompilowanym w wydanie. Niezgodność kończy działanie z kodem <RepositoryFact name="cliExitProtocol" /> i niczego nie zapisuje; nawet poprawnie pobrana paczka trafia do katalogu projektu za jednym razem, więc przerwane uruchomienie niczego po sobie nie zostawia.

Po co oba sprawdzenia? Skrót z API chroni pobieranie. Przypięty skrót chroni wydanie przed jego własnym serwerem: cokolwiek leży w magazynie pod kluczem danej wersji, opublikowane CLI uruchomi tylko szablony, z którymi przetestowano jego wydanie. Każde źródło sprawdza drugie i żadnemu nie ufa się w pojedynkę. Dokumentacja serwisu opisuje w całości endpoint i reguły publikowania paczek na stronie [API licencji CLI](/docs/features/cli-licence-api#publishing-bundles).

### Reguła ogólna

Wszystko, co Twoje CLI pobiera w czasie działania, czy to szablony, schematy, pliki binarne, czy lista wtyczek, jest częścią wydania. Wersjonuj to razem z wydaniem, przypnij skrótem zawartości w publikowanym kodzie, prześlij, zanim pakiet będzie można zainstalować, i przechowuj każdą wersję, o którą wciąż może poprosić obsługiwane wydanie.

## Zbuduj raz, potem testuj to, co wydajesz

### Spakuj raz i wystaw te same bajty

Zadanie pakujące uruchamia kontrole formatowania, lintera i typów, testy przy pełnym pokryciu i testy dymne, a potem `changeset pack` zapisuje spakowane pakiety i plan publikacji do artefaktu. Zadanie wystawiające pobiera ten artefakt; nigdy niczego nie buduje. Bajty, które npm dostaje do zatwierdzenia, to bajty wytworzone przez tamto zadanie.

### Pakowanie, które przepuściło składnię monorepo

0.1.0-beta.1 trafiło do npm z zapisami `catalog:` w `devDependencies` wszystkich trzech pakietów, w sumie z sześcioma takimi wpisami, co rejestr wciąż pokazuje. W monorepo zarządzanym przez Buna wspólne wersje zapisuje się jako `catalog:`. Changesets 3 pakuje tylko przez npm, pnpm albo Yarn, a w monorepo z Bunem wracało do `npm pack`, które kopiuje te zapisy do spakowanego `package.json` bez rozwiązywania. Nic się nie zepsuło, bo nikt nie instaluje zależności deweloperskich CLI. Ten sam wyciek w `dependencies` zepsułby każdą instalację wydania.

Poprawka przyczyny zawiera łatkę na Changesets zrobioną przez `bun patch`, dzięki której pakowanie idzie przez `bun pm pack`; to polecenie zapisuje wersję, na którą rozwiązuje się każdy zapis, i odmawia spakowania pakietu, którego zapisu nie umie rozwiązać. Łatka to część odpowiedzialna za pakowanie z otwartego pull requesta, który dodaje obsługę Buna do Changesets, [changesets/changesets#2334](https://github.com/changesets/changesets/pull/2334), i zniknie, gdy ta zmiana trafi do wydania Changesets. Tego, żeby błąd nie wrócił, pilnuje test: testy dymne pakują każdy publikowany pakiet tym samym poleceniem co wydanie i kończą się błędem na każdym `catalog:` albo `workspace:` pozostawionym w dowolnym polu zależności. Testuj spakowany pakiet, a nie kod w repozytorium. Funkcje monorepo Twojego menedżera pakietów są niewidoczne dla testu, który działa na kodzie źródłowym.

### Wystawiaj dopiero po testach na każdej platformie

Klienci uruchamiają CLI pod Node i Bunem, na Linuksie, macOS i Windows. Pull requesty uruchamiają zbudowany program tylko na Linuksie, żeby oszczędzać minuty; przebieg wydania sprawdza każdą platformę, na dokładnie tym commicie, który ma zaraz wystawić. Dziewięć zadań buduje pakiety i uruchamia programy pod Node 22.12.0, 24 i 26 na każdym systemie, a na każdym runnerze także pod Bunem.

Dziewięć zadań to jedna macierz, trzy systemy razy trzy wersje Node, począwszy od najstarszej wersji Node, którą obsługuje CLI. Dwa ustawienia zamieniają tę macierz w blokadę. Zadanie wystawiające wymienia w `needs` zarówno zadanie pakujące, jak i macierz, i nie ma własnego `if:`, więc GitHub je pomija, jeśli którekolwiek z nich nie zakończyło się powodzeniem; warunek taki jak `if: always()` w zadaniu wystawiającym po cichu by to zniweczył. Do tego macierz ustawia `fail-fast: false`, więc niepowodzenie jednego wariantu nie anuluje pozostałych, a przebieg pokazuje każdą platformę, na której coś się zepsuło, a nie tylko pierwszą.

Blokada, która jeszcze nigdy na Twoich oczach niczego nie zatrzymała, to nadzieja, a nie blokada. Zanim jej zaufaliśmy, uruchomiliśmy prawdziwy workflow wydania na tymczasowej gałęzi, z commita równoważnego scalonemu pull requestowi Version Packages, z jednym wariantem celowo zepsutym: Windows pod Node 26. Wszystkie pozostałe zadania przeszły, a zadanie wystawiające zostało pominięte, gdy tylko skończył się ostatni wariant. Ta próba nie mogłaby niczego opublikować, nawet gdyby blokada była błędna, bo środowisko, którego potrzebuje zadanie wystawiające, pozwala wdrażać tylko z gałęzi wydań; po wszystkim npm wymieniał te same wersje co wcześniej i nie pojawił się żaden tag ani Release.

Przeniesienie przebiegów na macOS i Windows z każdego scalenia na samo wydanie zmniejszyło liczbę płatnych minut scalenia do `main` o jedną trzecią do połowy, według pomiaru, który zrobiliśmy przy tej zmianie, kosztem płaconym raz na wydanie. To, czego ta blokada nie robi, wymienia lista pod koniec wpisu: uruchamia `--version` i `--help`, a nie pełne generowanie projektu, i buduje na każdym runnerze, zamiast instalować wystawiony spakowany pakiet.

## Zapisuj wydanie dopiero wtedy, gdy istnieje

### Nieopublikowane 0.1.0-beta.3

Nasz pierwszy workflow wydania tworzył tagi Gita i GitHub Releases zaraz po wystawieniu. Powód był taki, że gdy opiekun pakietu zatwierdza wystawioną wersję, npm nie wysyła żadnego zdarzenia, które mogłoby uruchomić workflow. Tagi pojawiały się więc w chwili wystawienia wersji, a nie jej publikacji. Historia wydań pokazuje, co to oznaczało, w UTC:

| Wersja       | Scalenie pull requesta z nową wersją | Utworzenie GitHub Releases | Udostępnienie w npm |
| ------------ | ------------------------------------ | -------------------------- | ------------------- |
| 0.1.0-beta.0 | 14 listopada, 06:17                  | 14 listopada, 18:24        | 14 listopada, 18:28 |
| 0.1.0-beta.1 | 14 listopada, 18:38                  | 14 listopada, 18:40        | 14 listopada, 23:08 |
| 0.1.0-beta.2 | 15 listopada, 22:52                  | 15 listopada, 22:55        | 15 listopada, 23:32 |
| 0.1.0-beta.3 | 17 listopada, 14:23                  | 17 listopada, 14:26        | Nigdy               |
| 0.1.0-beta.4 | 20 listopada, 09:49                  | 20 listopada, 09:51        | 20 listopada, 10:11 |
| 0.1.0-beta.5 | 20 listopada, 11:18                  | 20 listopada, 11:45        | 20 listopada, 11:44 |

0.1.0-beta.3 wystawiono 17 listopada i trzy dni później wciąż czekało na zatwierdzenie, gdy powstała i została wystawiona kolejna beta, zawierająca wszystkie jego zmiany i jeszcze jedną. Właściciel zatwierdził 0.1.0-beta.4. 0.1.0-beta.3 nigdy nie trafiło do npm, a `npm view saasyland versions` wymienia 0.1.0-beta.2, a zaraz po nim 0.1.0-beta.4. Repozytorium miało jednak dla niego trzy tagi i trzy GitHub Releases, które opisywały pakiety, których nikt nie mógł zainstalować. Nawet przy czterech wersjach beta, które tą drogą trafiły do npm, Releases pojawiały się pierwsze, od czterech minut do czterech i pół godziny wcześniej. Workflow miał rację we wszystkim poza jedną rzeczą, której nie mógł wiedzieć: czy i kiedy człowiek zatwierdzi wydanie.

### Najpierw zapytaj npm, potem taguj

Przenieśliśmy tagi i Releases do osobnego zadania, które najpierw pyta rejestr. Dla każdego publikowanego pakietu sprawdza trzy rzeczy: czy `CHANGELOG.md` pakietu ma sekcję dla wersji z kopii roboczej, a taką sekcję zapisuje tylko pull request Version Packages; czy npm udostępnia dokładnie tę wersję, przez publiczne `npm view`, które nie potrzebuje tokena; i czy tag już istnieje. Dopiero gdy każdy pakiet przejdzie pierwsze dwa sprawdzenia, a jakiegoś tagu brakuje, uruchamia `changeset git-tag` przez akcję Changesets, która wypycha tagi i tworzy Release z każdego wpisu na liście zmian. W przeciwnym razie niczego nie zapisuje, a jego podsumowanie mówi dlaczego.

Oba sprawdzenia są celowo proste. Wersja liczy się jako udostępniona tylko wtedy, gdy `npm view` wypisze dokładnie tę wersję, więc brakująca wersja, błąd sieci i nieoczekiwana odpowiedź liczą się tak samo jak wersja nieudostępniona i żaden tag nie powstaje. Tag liczy się jako istniejący tylko wtedy, gdy Git znajdzie jego pełną referencję, więc gałąź o tej samej nazwie nie może się pod niego podszyć. Zestaw do wydań na końcu tego wpisu zawiera ogólną wersję tego sprawdzenia dla pojedynczego pakietu.

Zadanie uruchamia się na trzy sposoby: zaraz po wystawieniu, kiedy zwykle zastaje wersję wciąż czekającą na zatwierdzenie; ręcznie, co agent prowadzący robi, gdy tylko właściciel zatwierdzi wydanie; i raz dziennie jako zabezpieczenie awaryjne. Jego przebiegi na jednej gałęzi należą do wspólnej grupy współbieżności i czekają w kolejce, zamiast nakładać się na siebie, więc dwa przebiegi nigdy nie tagują jednocześnie, a zadanie najpierw pobiera wszystkie tagi, więc tworzy tylko to, czego brakuje, i można je uruchamiać dowolną liczbę razy.

0.1.0-beta.5 było pierwszym wydaniem, które przez nie przeszło. Zadanie zapisu w przebiegu wydania uruchomiło się o 11:25 UTC i stwierdziło, że npm jeszcze nie udostępnia wersji. npm udostępnił ją o 11:44:37; agent prowadzący uruchomił workflow zapisu wydania o 11:45:27, a trzy Releases pojawiły się o 11:45:51.

### Harmonogram to siatka bezpieczeństwa, a nie krok

Codzienne zabezpieczenie nauczyło nas dwóch rzeczy o zdarzeniu `schedule` w GitHubie. Po pierwsze, „workflowy uruchamiane według harmonogramu działają na najnowszym commicie domyślnej gałęzi”, a tagi wersji beta muszą wskazywać commit na `beta`. Dlatego zadanie uruchamiane z harmonogramu samo niczego nie taguje: odczytuje gałęzie z wyzwalacza workflow wydania i na każdej z nich uruchamia workflow zapisu wydania przez `workflow_dispatch`, żeby każdy przebieg tagował własną gałąź. Po drugie, harmonogram jest przybliżony. GitHub pisze, że zdarzenie „może być opóźnione w okresach dużego obciążenia” i że „część zadań w kolejce może zostać porzucona”. Nasz harmonogram jest ustawiony na wczesny ranek UTC, a od 21 do 24 listopada przebieg startował mniej więcej osiem do jedenastu godzin później. Zadanie z harmonogramu może wyłapać to, o czym zapomniał człowiek. Nigdy nie powinno być krokiem, na który czeka wydanie.

### Oznaczaj to, czego nigdy nie wydano

Tagi i Releases 0.1.0-beta.3 zostają na miejscu: ich usunięcie wymazałoby zapis tego, co zbudowano i wystawiono. Zamiast tego lista zmian każdego pakietu mówi teraz pod nagłówkiem 0.1.0-beta.3: „Nieopublikowane w npm: 0.1.0-beta.4 zastąpiło tę wersję, zanim została zatwierdzona, a każda zmiana poniżej trafiła do 0.1.0-beta.4”. Trzy GitHub Releases mają w tytułach dopisek „(not published)”, czyli „nieopublikowane”, a [informacje o wydaniach](/docs/cli/releases) w serwisie mówią to samo. Zasady wydań zyskały też nową regułę: zatwierdź albo odrzuć wystawione wydanie, zanim zostanie scalony kolejny pull request Version Packages.

## Pusty changeset, który zablokował wydanie

[Pierwszy wpis z tej serii](/blog/ai-coding-agent-guardrails) opisuje tę historię krótko, jako przykład agenta, który spełnia literę kontroli. Oto pełny przebieg zdarzeń, bo pokazuje rodzaj awarii łatwy do przeoczenia: narzędzie do wydań uznaje, zgodnie z własnymi regułami, że nie ma nic do zrobienia.

### Trzy scalenia w 81 sekund

Wszystko wydarzyło się na `beta` 20 listopada, w UTC:

1. **11:17:12.** Pull request przeniósł dwa commity z `main`. Jego przebieg wydania otworzył pull request Version Packages dla 0.1.0-beta.5.
2. **11:18:06.** Scalono pull request, który dodawał notatkę „Nieopublikowane w npm” do trzech list zmian. Edycja listy zmian liczy się jako zmiana pakietu, więc kontrola changesetów zażądała changesetu, a pull request dodał pusty, dokładnie tak, jak zasady wydań nakazywały przy zmianie, której klienci nie mogą zauważyć.
3. **11:18:33.** Scalono pull request z nową wersją, 27 sekund później. Zbudowano go przed scaleniem poprawki list zmian, więc nie uwzględnił pustego changesetu.
4. **11:19.** Przebieg wydania na tym commicie scalającym wybrał tryb i pominął wszystkie pozostałe zadania. 0.1.0-beta.5 dostało na `beta` swój numer wersji, ale nie zostało wystawione, a wszystkie zadania były zielone.

Tymczasem przebieg wydania dla commita scalającego poprawkę list zmian, czekający w kolejce za pozostałymi, otworzył drugi pull request Version Packages z commita, który był już nieaktualny; zamknięto go bez scalania.

### Dlaczego wybrany tryb to „none”

`changesets/action/select-mode` zwraca jeden z trzech trybów: version, publish albo none. Oto ta decyzja w jego publicznym kodzie źródłowym w wersji v2.1.2, sformatowana według zasad tego serwisu:

```ts
if (changesets.length > 0) {
  const hasNonEmptyChangesets = changesets.some((changeset) => changeset.releases.length > 0)
  if (hasNonEmptyChangesets) {
    return { mode: "version" }
  }
  return { mode: "none" }
}
```

Jeśli czeka jakikolwiek changeset, a wszystkie są puste, tryb to `none`, a plan publikacji, który wykryłby, że 0.1.0-beta.5 brakuje w npm, w ogóle nie zostaje obliczony. Według własnych zasad akcji to rozsądne: pusty changeset znaczy „nie wydawaj niczego”. W połączeniu z pull requestem z nową wersją scalonym przed przebudowaniem oznaczało to wydanie, które dostało numer, ale nigdy nie trafiło do npm.

### Poprawka i reguły

Kolejny pull request usunął pusty changeset pięć minut później. Następny przebieg wybrał `publish`, wystawił 0.1.0-beta.5 o 11:25, a właściciel zatwierdził je o 11:44. Nasze zasady mówią teraz, że puste changesety należą wyłącznie do `main`, a zmiana wprowadzona bezpośrednio na `beta`, której klienci nie mogą zauważyć, na przykład poprawka listy zmian, nie ma changesetu, a jej nieprzechodząca kontrola changesetów to jedyne dozwolone niepowodzenie.

Dwie reguły sprawdzą się w każdym zespole:

- **Scalaj pull request z nową wersją tylko wtedy, gdy zbudowano go z najnowszego commita gałęzi.** Jeśli po jego ostatniej aktualizacji cokolwiek zostało scalone, poczekaj, aż workflow wydania go przebuduje.
- **Traktuj „nie ma nic do zrobienia” jako wynik, który trzeba sprawdzić.** Przebieg wydania, który uznaje, że nie ma nic do zrobienia, choć w rejestrze brakuje wersji z gałęzi, zakończył się porażką, nawet jeśli każde zadanie jest zielone.

Pierwszą regułę mamy na piśmie, a drugiej nie mamy jeszcze w postaci kontroli. Do tego nasza spisana reguła o pustych changesetach obejmuje gałąź, na której to się stało, a sam mechanizm nie zależy od trybu wydań przedpremierowych: ten sam wyścig na `main` zostawiłby ten sam oczekujący pusty changeset.

## CI dla pull requesta, z którego wydajesz

### GitHub nie uruchamia workflowów dla pushy własnego tokena

Zadanie wersjonujące wypycha gałąź Version Packages tokenem `GITHUB_TOKEN` workflow, a dokumentacja GitHuba mówi, że „zdarzenia wywołane przez `GITHUB_TOKEN` nie utworzą nowego przebiegu workflow”, z jednym wyjątkiem, który ma tu znaczenie: „zdarzenia `workflow_dispatch` i `repository_dispatch` zawsze tworzą przebiegi workflow”. Dlatego pull request, z którego mieliśmy zaraz wydawać, nie pokazywał żadnych kontroli; żeby jeden z takich pull requestów w ogóle dostał przebieg, agent ręcznie go zamknął i otworzył ponownie. Poprawka zostawia domyślny token i sama uruchamia CI. Zaraz po tym, jak Changesets otworzy albo zaktualizuje pull request z nową wersją, to samo zadanie odczytuje gałąź tego pull requesta i uruchamia na niej workflow CI poleceniem `gh workflow run`. To działa, bo workflow CI przyjmuje zarówno `pull_request`, jak i `workflow_dispatch`.

Zadanie dostaje `actions: write` dla tego jednego wywołania, a przebiegi kontroli są przypisane do najnowszego commita gałęzi, więc widać je w pull requeście. Token aplikacji GitHub też uruchomiłby CI, ale wymaga aplikacji i kolejnego sekretu; to rozwiązanie nie wymaga żadnego z nich.

### Ustawiaj przebiegi wydania w kolejce, nigdy ich nie zastępuj

Grupy współbieżności w GitHub Actions trzymały kiedyś tylko jeden oczekujący przebieg: „Jeśli do grupy trafił inny przebieg, oczekujący przebieg był anulowany i zastępowany”. W workflow wydania to błąd, bo z trzech szybkich pushy do `beta` środkowy by przepadł. Od maja 2026 `queue: max` pozwala grupie „ustawiać w kolejce wiele oczekujących przebiegów i przetwarzać je po kolei”, do 100 przebiegów, gdy `cancel-in-progress` ma wartość false.

Ogólny przykład, na podstawie dokumentacji GitHuba o współbieżności, dla workflow wydania, który nigdy nie może zgubić przebiegu:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false
  queue: max
```

Nasz workflow wydania działa właśnie tak, więc każdy push do gałęzi wydania dostaje własny, pełny przebieg, po kolei. Sekwencja z pustym changesetem pokazuje drugą stronę tej gwarancji: przebieg z kolejki decyduje na podstawie własnego commita, nawet jeśli w chwili, gdy rusza, ten commit jest już nieaktualny. Kolejka zachowuje każdy przebieg; nie sprawia, że decyzja starego przebiegu staje się aktualna.

## Kto trzyma który klucz

Agenci prowadzą wydanie; właściciel trzyma to, czego nie da się cofnąć.

| Czynność                                         | Agenci                                                             | Właściciel                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Changesety i pull request z nową wersją          | Piszą je, przeglądają notatki i scalają, gdy partia jest kompletna | Nic                                                                                   |
| Workflowy wydań                                  | Piszą zmianę i dowodzą, że działa, na przykład próbnym przebiegiem | Zatwierdza zacytowanym „tak” każdą zmianę w plikach, które decydują, co trafia do npm |
| Build, testy, pakowanie i wystawienie            | Nic: robi to CI na commicie scalającym                             | Nic                                                                                   |
| Zatwierdzenie albo odrzucenie wystawionej wersji | Przekazują dokładne identyfikatory wystawień                       | Zatwierdza albo odrzuca z uwierzytelnianiem dwuskładnikowym                           |
| Tagi i GitHub Releases                           | Uruchamiają workflow zapisu wydania zaraz po zatwierdzeniu         | Nic                                                                                   |
| Nowa nazwa pakietu                               | Przygotowują ją na `main` i spisują dokładne kroki                 | Publikuje wydanie zastępcze i konfiguruje zaufanego wydawcę                           |
| Zła wersja                                       | Piszą komunikat o przestarzałej wersji i poprawkę                  | Uruchamia `npm deprecate` z uwierzytelnianiem dwuskładnikowym                         |
| Informacje o wydaniu i weryfikacja               | Instalują z npm w czystym katalogu, piszą notatki w każdym języku  | Przegląda                                                                             |

Workflow wydania, konfiguracja Changesets i pola pakietów, które decydują o tym, co trafia do npm, są w repozytorium CLI na liście wymagającej przeglądu przez człowieka, więc każdy pull request, który je zmienia, na przykład ten, który zmienił sposób zapisywania wydań, cytuje pisemną zgodę właściciela. Ten sam plik instrukcji każe agentom nigdy nie publikować i nigdy nie uruchamiać `npm trust`. Żaden agent nie ma też danych uwierzytelniających npm, bo takie nie istnieją: każdy pakiet zabrania publikacji tokenami, a jedyną zautomatyzowaną tożsamością, która może wystawiać wersje, jest sam workflow wydania.

Weryfikacja nie kończy się na wydaniu. Testy ścieżek użytkownika w serwisie uruchamiają się według harmonogramu <RepositoryFact name="journeySchedule" /> w UTC: kupują licencję w każdym pakiecie w sandboksie Polara na wdrożeniu podglądowym, a potem prowadzą opublikowane CLI, prosto z npm, przez aktywację, limity urządzeń, dezaktywację i zwrot pieniędzy, który kończy licencję:

```ts title="e2e/journey/cli.ts"
const child = spawn("env", ["-i", ...variables, PACKAGE_MANAGER.NPM.exec, "--yes", CLI_PACKAGE_SPEC, ...inputs, "--json"], { cwd: home })
```

To ta sama zasada, od której zaczął się ten wpis. Agenci mogą robić wszystko, co jest odwracalne albo co wyłapie późniejszy krok. Kroki, które nie są ani jednym, ani drugim, trzyma człowiek, przez składnik uwierzytelniania, którego agenci nie mogą mieć.

## Gdy wydanie jest złe

Wersja w npm zostaje na zawsze, więc wycofanie oznacza ruch naprzód.

- **Oznacz jako przestarzałą, potem wydaj poprawkę.** `npm deprecate` z komunikatem, który wskazuje poprawkę, na przykład „Psuje init w systemie Windows. Użyj wersji 1.4.1 lub nowszej”, uruchamiane przez właściciela z uwierzytelnianiem dwuskładnikowym. Poprawka przechodzi przez ten sam proces co każde wydanie. Poprawkę bezpieczeństwa albo poprawkę błędu, który powoduje utratę danych, wydaje się od razu, bez czekania na jej partię.
- **Nigdy nie cofaj publikacji.** Psuje to każdy projekt i skrypt, który przypiął tę wersję, a numeru wersji nie da się już nigdy użyć ponownie.
- **Odrzuć to, co jest tylko wystawione.** `npm stage reject <stage id>` usuwa wystawioną wersję bez publikacji, również z uwierzytelnianiem dwuskładnikowym.
- **Pamiętaj o odrzuconej wersji.** Odrzucona wersja wciąż jest wersją w repozytorium i wciąż brakuje jej w npm, więc następny push bez oczekującego changesetu wystawi ją ponownie. Zanim zrobisz cokolwiek innego, scal poprawkę razem z jej changesetem.

## Czego wciąż nam brakuje

W duchu całej serii: oto miejsca, w których nasz własny proces wydań jest słaby.

- **Brak poświadczenia pochodzenia.** Repozytorium jest prywatne, więc pakiety mają podpis rejestru npm i żadnego poświadczenia pochodzenia.
- **Jeszcze brak stabilnego kanału.** `latest` to wciąż wydanie zastępcze, a każde publikowane przez nas polecenie podaje tag <RepositoryFact name="cliReleaseChannel" />. Pierwsze stabilne wydanie musi jednocześnie zmienić pliki README, testy, które je sprawdzają, i polecenia w serwisie.
- **Płytka kontrola na wielu platformach.** Na macOS i Windows wydanie sprawdza `--version` i `--help` pod każdym środowiskiem uruchomieniowym, a nie pełne `init`, i buduje na każdym runnerze, zamiast instalować spakowany pakiet, który zostanie wystawiony.
- **Zatwierdzenie opiera się na podsumowaniu.** `npm stage download` pobiera wystawiony pakiet „do lokalnego sprawdzenia” bez drugiego składnika, więc osoba zatwierdzająca mogłaby przed zatwierdzeniem zainstalować i uruchomić dokładnie te bajty. Jeszcze tego nie robimy.
- **Brak alarmu przy „nie ma nic do zrobienia”.** Przebieg wydania, który uznaje, że nie ma nic do zrobienia, choć w npm brakuje wersji z gałęzi, nie zgłasza żadnego błędu.
- **Spóźniona siatka bezpieczeństwa.** Przebieg zapisu wydania uruchamiany z harmonogramu startuje wiele godzin po czasie, więc agent prowadzący uruchamia go ręcznie po każdym zatwierdzeniu.
- **Jedna osoba zatwierdzająca.** 0.1.0-beta.3 czekało na zatwierdzenie trzy dni i zostało zastąpione. Wydanie, które zależy od drugiego składnika jednej osoby, posuwa się w tempie tej osoby.
- **Brak przebiegu na działającym API przed wydaniem.** [Pierwszy wpis](/blog/ai-coding-agent-guardrails) opisuje barierę, której potrzebujemy: uruchamianie w CI opublikowanego CLI na produkcji przed każdym wydaniem. Wymaga to klucza licencyjnego jako sekretu CI, czyli zmiany wymagającej przeglądu przez człowieka, która czeka na właściciela.

## Zestaw do wydań, gotowy do skopiowania

**Lista kontrolna wydania**, po kolei:

1. Partia jest scalona, a ostatni przebieg CI na gałęzi wydania jest zielony.
2. Każdy changeset czyta się jak notatkę dla klienta, a numer wersji jest właściwy.
3. Pull request z nową wersją przebudowano po ostatnim scaleniu, a jego kontrole są zielone.
4. Dokumentacja, której potrzebuje wydanie, jest już opublikowana, a każda zmiana kontraktu, który czyta serwer, jest już na serwerze wdrożona.
5. Żadne wcześniejsze wystawione wydanie nie czeka na zatwierdzenie.
6. Scal pull request z nową wersją.
7. Spakuj raz; uruchom zbudowany program na każdym obsługiwanym systemie i w każdym środowisku uruchomieniowym; wystaw wydanie tylko wtedy, gdy wszystko przeszło.
8. Prześlij i odczytaj z powrotem wszystko, co CLI będzie pobierać, i sprawdź to z przypiętym skrótem, zanim wystawisz wydanie.
9. Zatwierdź każdy pakiet wydania z uwierzytelnianiem dwuskładnikowym albo odrzuć wydanie.
10. Utwórz tagi i Releases, gdy rejestr udostępnia każdy pakiet wydania.
11. Zainstaluj wydanie z rejestru w czystym katalogu i uruchom CLI.
12. Opublikuj informacje o wydaniu i oznacz wszystko, co wystawiono, ale nigdy nie opublikowano.

**Zadanie wystawiające**, ogólny przykład napisany na podstawie dokumentacji npm dla repozytorium bez Changesets, a nie własny workflow CLI. Nie potrzebuje tokena i można je bezpiecznie uruchomić ponownie. Zakłada zadanie `pack`, które przesyła spakowane pakiety jako artefakt o nazwie `tarballs`, środowisko o nazwie `release` i zaufanego wydawcę na npmjs.com, który wskazuje ten plik workflow, to środowisko i uprawnienie tylko do wystawiania. Każda akcja jest w nim przypięta do commita wydania, z tagiem za nim, bo tag można przesunąć, a zadanie wydania to ostatnie miejsce, w którym powinien działać kod, którego nikt nie przejrzał:

```yaml
stage:
  needs: pack
  runs-on: ubuntu-latest
  environment: release
  permissions:
    contents: read
    id-token: write
  steps:
    - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
      with:
        node-version: 26
    - uses: actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2
      with:
        name: tarballs
    - name: Stage every tarball npm does not serve yet
      shell: bash
      run: |
        for tarball in *.tgz; do
          manifest=$(tar -xOzf "$tarball" package/package.json)
          name=$(jq -r .name <<< "$manifest")
          version=$(jq -r .version <<< "$manifest")
          if [ "$(npm view "$name@$version" version 2> /dev/null)" = "$version" ]; then
            echo "$name@$version is already on npm" >> "$GITHUB_STEP_SUMMARY"
          elif staged=$(npm stage publish "$tarball" --access public --tag latest --json); then
            echo "$name@$version staged as $(jq -r --arg name "$name" '.[$name].stageId' <<< "$staged")" >> "$GITHUB_STEP_SUMMARY"
          elif [ "$(jq -r '.error.code' <<< "$staged")" = E409 ]; then
            echo "$name@$version was staged by an earlier run" >> "$GITHUB_STEP_SUMMARY"
          else
            exit 1
          fi
        done
    - name: Keep npm's logs when staging fails
      if: failure()
      uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
      with:
        name: npm-logs
        path: ~/.npm/_logs/
        retention-days: 7
```

**Zaufany wydawca, który może tylko wystawiać**, konfigurowany raz dla każdego pakietu przez opiekuna z uwierzytelnianiem dwuskładnikowym:

```sh
npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish
```

**Tagi tylko dla tego, co udostępnia npm**, ogólny przykład dla pojedynczego pakietu, do bezpiecznego uruchamiania dowolną liczbę razy, na przykład po każdym zatwierdzeniu:

```sh
name=$(jq -r .name package.json)
version=$(jq -r .version package.json)
if [ "$(npm view "$name@$version" version 2> /dev/null)" != "$version" ]; then
  echo "npm does not serve $name@$version yet, so nothing is tagged"
  exit 0
fi
if git rev-parse -q --verify "refs/tags/v$version" > /dev/null; then
  exit 0
fi
git tag "v$version"
git push origin "v$version"
gh release create "v$version" --verify-tag --notes-file release-notes.md
```

**Pobranie sprawdzane względem serwera i przypiętego skrótu**, zanim cokolwiek je odczyta, ogólny przykład w TypeScripcie dla Node:

```ts
import { createHash } from "node:crypto"
import { gunzipSync } from "node:zlib"

const MAX_CONTENT_BYTES = 256 * 1024 * 1024

interface BundleAnswer {
  readonly sha256: string
  readonly size: number
}

export const verifiedContent = (archive: Buffer, answer: BundleAnswer, pinned: string): Buffer => {
  if (archive.length !== answer.size) {
    throw new Error(`Expected ${answer.size} bytes and received ${archive.length}`)
  }

  const content = gunzipSync(archive, { maxOutputLength: MAX_CONTENT_BYTES })
  const digest = createHash("sha256").update(content).digest("hex")

  if (digest !== answer.sha256 || digest !== pinned) {
    throw new Error("The download is not the bundle this release was tested with")
  }

  return content
}
```

**Reguły wydań do Twojego pliku z instrukcjami**, żeby agenci przygotowywali to, co zatwierdzi właściciel:

```md
## Releases

- Never run npm publish, npm unpublish, npm stage approve or npm stage reject. CI stages releases, and a maintainer approves them with 2FA.
- Every change to a published package adds a changeset written for customers: what changes for them and what they have to do.
- Merge a version pull request only when it was built from the branch's current head, and never while a staged release awaits approval.
- After an approval, start the records workflow, install the release from npm in a clean directory and run it before announcing anything.
- Label a version that was staged and never published in its changelog and its GitHub Release. Never delete its tag.
```
