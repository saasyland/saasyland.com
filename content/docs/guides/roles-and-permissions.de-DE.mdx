Die Zugriffskontrolle nutzt das Admin-Plugin von Better Auth. `src/integrations/better-auth/auth.access.ts` deklariert die Berechtigungs-Statements aller Ressourcen in `APP_STATEMENTS`, gewährt sie den Rollen und baut daraus die Zugriffskontrolle von Better Auth und die Berechtigungsprüfung auf, in einer einzigen Datei, die ein Mensch prüft. Die Rollencodes liegen in `src/integrations/better-auth/auth.roles.ts`.

## Statements und Rollen

```ts title="src/integrations/better-auth/auth.access.ts"
export const APP_STATEMENTS = {
  admin: ["access"],
  category: ["create", "read", "update", "delete"],
  course: ["create", "read", "update", "delete"],
  order: ["read", "update", "refund"],
  product: ["create", "read", "update", "delete", "publish"],
  settings: ["manage"],
  video: ["read", "delete"],
} as const

export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...APP_STATEMENTS, ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole({}),
}
```

- `APP_STATEMENTS` führt ein Statement pro Ressource auf, nach Ressource sortiert: `admin` und `settings` für die Admin-Konsole und ihre Einstellungen, `category` und `product` für die Produkte, `course` und `video` für die Kurse und `order` für die Bestellungen.
- `defaultStatements` von Better Auth fügen die Ressourcen `user` und `session` hinzu (etwa `user: ["list", "set-role", "ban", "impersonate", "delete"]` und `session: ["list", "revoke"]`).
- Der Rolle `admin` werden alle Statements und die Admin-Statements von Better Auth gewährt; der Rolle `customer`, der Standardrolle für neue Benutzer, wird keines gewährt.
- Ein Feature, das ein Projekt weglässt, nimmt seine Statements mit: `scripts/areas.ts` nennt sie, etwa `APP_STATEMENTS.course`, und die Bereinigungsregel löscht sie aus dem Objekt ([Testen](/docs/conventions/testing#tests-follow-the-areas)).
- `ROLE_VALUES` typisiert die Spalte `user.role` und die Rollenschemas in `user.zod.ts`.
- `Permission`, der Typ, den `authorized` und `hasPermission` annehmen, wird aus `APP_STATEMENTS` gebildet, sodass ein Statement oder eine Aktion, die dort nicht deklariert ist, nicht kompiliert.

## Wo Berechtigungen geprüft werden

| Schicht         | Prüfung                                                                       |
| --------------- | ----------------------------------------------------------------------------- |
| Route-Guard     | `requireAdmin` verlangt `admin: ["access"]` für den gesamten `/admin`-Bereich |
| Server-Funktion | `authorized({ product: ["update"] })` auf jeder geschützten Operation         |
| Nur angemeldet  | `authorized()` für Operationen auf den eigenen Daten des Aufrufers            |
| Überall sonst   | `hasPermission({ permission, role })` gibt einen booleschen Wert zurück       |

Der Route-Guard entscheidet nur, welche Seiten gerendert werden. Server-Funktionen sind direkt per RPC aufrufbar, daher muss jede ihre eigene Berechtigung prüfen. Einen Button auszublenden ist Darstellung, keine Autorisierung.

## Berechtigung hinzufügen

1. Die Aktion zum Statement der Ressource in `APP_STATEMENTS` hinzufügen oder die Ressource an ihrer sortierten Stelle ergänzen, zum Beispiel `report: ["read", "export"]`. Ein Feature, das wegfallen kann, nennt eine neue Ressource in seinen `names` in `scripts/areas.ts`, etwa `APP_STATEMENTS.report`.
2. Sie in `ROLES` gewähren: `admin` erhält das gesamte `APP_STATEMENTS`, und einer Rolle, die weniger erhalten soll, wird eine Teilmenge gewährt.
3. In der Server-Funktion verlangen: `.middleware([authorized({ report: ["export"] })])`.
4. Sowohl den erlaubten als auch den `FORBIDDEN`-Fall testen, in `src/integrations/better-auth/__test__/auth.access.<area>.test.ts` und in den Tests des Use Cases.

## Rolle hinzufügen

1. Den Code zu `ROLE_CODES` und `ROLE_VALUES` in `auth.roles.ts` hinzufügen.
2. Die Rolle mit den Statements, die sie nutzen darf, zu `ROLES` in `auth.access.ts` hinzufügen.
3. Die Rollenbeschriftung zu `filters.role.options` in `messages/<locale>/pages.admin.users.json` für jede Locale hinzufügen.

Der Auth-Client (`auth.client.ts`) erhält `ac` und `ROLES`, sodass Admin-Aktionen im Browser dieselben Definitionen verwenden.

## Benutzer- und Session-Verwaltung

Die Module für Benutzer und Sessions kapseln die Admin-API von Better Auth in Use Cases, jeder mit eigener Berechtigung: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` und weitere. Operationen auf den eigenen Daten des Aufrufers, etwa `revokeSession`, verwenden `authorized()` und filtern nach `context.auth.user.id`.

Lokal legt `bun run db:seed:local` einen Admin an. Auf Preview und Produktion legt `bun run admin:grant:preview <email>` oder `bun run admin:grant:production <email>` den ersten Admin an, für ein Konto, das seine E-Mail-Adresse verifiziert hat; ausführen kann das nur, wer Schreibzugriff auf die D1-Datenbank dieser Umgebung hat. Weitere Admins entstehen unter **Admin → Benutzerverwaltung** mit **Rolle ändern**. Siehe [Der erste Admin](/docs/tooling/database#the-first-admin). Ein bestehender Admin kann auch eine neue Adresse mit der Rolle `admin` einladen; siehe [Einladungen](/docs/features/users-admin#invitations).
