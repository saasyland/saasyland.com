Chaque règle de cette page est issue d'une mesure, et plusieurs ont remplacé une correction intuitive qui aggravait les choses. Ne modifiez le code qui sous-tend l'une d'elles qu'avec une nouvelle mesure qui fait mieux.

## Mesurez avant d'affirmer

- Comparez le build précédent et le nouveau build sur la même page, avec au moins cinq exécutions de Lighthouse pour chacun, en les alternant, et comparez les médianes. Une seule exécution ne prouve rien : environ une exécution sur cinq est une valeur aberrante due au bruit de la machine.
- Ne jugez pas une modification sur une seule exécution de PageSpeed Insights. Le même déploiement obtient des scores très différents selon la vitesse de la machine qui exécute le test, ce que Lighthouse indique sous le nom `benchmarkIndex`.
- Mesurez un build de production (`bun run build:test`, puis `bun run start:test`) servi en HTTP/2 avec compression. En HTTP/1.1 local sans compression, la simulation réseau de Lighthouse modélise des connexions et des tailles de transfert que la production n'a jamais.
- Un diagnostic Lighthouse n'est pas un score. Une indication « forced reflow » ou « properly size images » peut être fausse pour la page, comme le montrent les sections ci-dessous ; vérifiez les métriques notées avant d'y donner suite.

## Gardez petit le graphe de démarrage du Worker

`src/server.ts` s'exécute pour chaque requête HTML (`run_worker_first` dans `wrangler.jsonc`), et tout ce qu'il importe statiquement est évalué à chaque démarrage à froid. Lui et les handlers du Worker qu'apportent les zones n'importent que des constantes et des utilitaires purs, et chargent le reste lorsqu'une requête en a besoin :

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

Un seul import statique d'un nom d'en-tête depuis un module qui importait aussi le client Polar a un jour ajouté environ 1,4 Mo de SDK à chaque démarrage à froid, et le premier octet de la page d'accueil mettait jusqu'à 1,4 seconde à arriver. C'est pourquoi `COUNTRY_HEADER` et `IP_ADDRESS_HEADER` se trouvent dans `src/modules/_core/constants/api.ts`, qui n'importe rien de lourd. Avant d'ajouter un import statique à `server.ts` ou à un `<area>.worker.ts`, suivez sa chaîne d'imports : tout ce qui atteint `polar`, `drizzle-orm` ou `resend` est une régression. `scripts/verify-build.ts` le vérifie à chaque build : il suit les imports statiques du point d'entrée du Worker déployé, `dist/server/index.js`, et échoue lorsqu'ils atteignent du code issu de `@polar-sh`, `drizzle-orm` ou `resend` dans le bundle, ou qu'ils totalisent plus de `BOOT_CLOSURE_MAX_BYTES`.

## Gardez l'ORM hors du navigateur [#keep-the-orm-out-of-the-browser]

Drizzle ne s'exécute que dans le Worker. Le navigateur a besoin des schémas Zod d'un module pour ses formulaires et de ses tuples d'enum pour ses listes déroulantes : les deux se trouvent donc dans des fichiers qui n'importent rien de Drizzle, `<table>.zod.ts` et `<table>.constants.ts` (voir [Modules](/docs/conventions/modules)). Un import du navigateur qui atteint un `<table>.schema.ts` exécute `sqliteTable(...)`, un appel que le bundler doit conserver, et entraîne `drizzle-orm` avec lui.

`<table>.zod.ts` construisait autrefois aussi des schémas `insert`, `select` et `update` à partir des tables avec `drizzle-zod`, et rien ne les lisait à l'exécution. `drizzle-zod` retient tout l'espace de noms de zod, si bien que le bundler conservait aussi chaque locale de zod, son convertisseur JSON Schema et son compilateur. Les squelettes de chargement de `/admin` et `/app` importaient `PreferencesCardPending` de `preferences-card.tsx`, qui importait `user.zod.ts`, et les composants de chargement échappent au découpage du code : tout cela se chargeait donc sur chaque page. Déplacer les tuples dans les constantes et supprimer ces schémas a retiré environ 75 Kio de JavaScript compressé avec gzip de chaque page. Les tailles ci-dessous totalisent tous les scripts que charge chaque page, compressés avec gzip, d'après la sortie de `bun run build:test` :

| Page           | Avant     | Après     |
| -------------- | --------- | --------- |
| `/`            | 526,2 Kio | 450,7 Kio |
| `/docs/<page>` | 612,1 Kio | 536,5 Kio |
| `/blog`        | 487,2 Kio | 411,7 Kio |
| `/app`         | 496,6 Kio | 421,0 Kio |
| `/admin`       | 515,0 Kio | 439,4 Kio |

`src/data/tanstack.vite.ts` interdit `drizzle-orm` à l'environnement client grâce à la protection des imports de TanStack Start :

```ts title="src/data/tanstack.vite.ts"
const SERVER_ONLY_PACKAGES = [/^drizzle-orm(?:\/|$)/u]
```

Un build dans lequel un import de ce paquet survit au tree shaking échoue et affiche la chaîne d'imports qui mène de la route au fichier qui a atteint Drizzle. Rompez la chaîne là où elle commence : importez le tuple depuis les constantes du module, ou déplacez le code dans une fonction serveur. Les imports qui ne portent que sur des types sont effacés et ne comptent jamais.

## Charger les messages quand une page en a besoin [#load-messages-when-a-page-needs-them]

La première page qu'ouvre un visiteur ne charge aucun fichier de messages dans le navigateur : la route racine et les routes correspondantes préchargent leurs namespaces dans le cache de queries côté serveur, et TanStack Start envoie ce cache avec le HTML. Le navigateur ne charge un namespace que lorsqu'une navigation ultérieure en demande un que le cache ne contient pas encore.

`import.meta.glob` donne à chaque fichier de messages son propre chunk, mais la table qui associe chaque fichier à son chunk, et qui nomme chaque namespace de chaque locale, est livrée dans le module qui appelle le glob. Ce module était `i18n.messages.ts`, que la route racine importe, et il contenait cette table deux fois, une fois pour les messages et une fois pour les métadonnées de page, si bien que chaque page chargeait environ 240 Kio de loaders, 21 Kio compressés avec gzip. La table vit désormais seule dans `i18n.loaders.ts`, et `loadNamespace` l'importe la première fois qu'il charge un namespace :

```ts title="src/integrations/use-intl/i18n.messages.ts"
const { MESSAGE_LOADERS } = await import("~/src/integrations/use-intl/i18n.loaders")
```

`loadPageMetadata` lit `metadata` dans le namespace de la page au lieu d'une seconde table, si bien que le head d'une page et ses messages viennent du même chunk. Le navigateur récupère `i18n.loaders.ts`, environ 11 Kio compressés avec gzip, avec le premier namespace qu'il charge, lors d'une navigation ou du survol qui en précharge un. Les namespaces racine sont toujours trouvés par nom de fichier dans `i18n.messages.ts`, et les clés de ce glob coûtent environ 2 Kio compressés avec gzip. Tous les scripts que charge chaque page, compressés avec gzip, d'après la sortie de `bun run build:test` :

| Page           | Avant     | Après     |
| -------------- | --------- | --------- |
| `/`            | 462,9 Kio | 442,3 Kio |
| `/docs/<page>` | 553,5 Kio | 532,9 Kio |
| `/blog`        | 424,6 Kio | 404,0 Kio |
| `/app`         | 430,4 Kio | 409,7 Kio |
| `/admin`       | 452,8 Kio | 432,2 Kio |

Chargez les messages uniquement via `loadNamespace`, et n'ajoutez jamais d'`import.meta.glob` sur `messages/` à un module que la route racine importe. `scripts/verify-build.ts` suit les imports statiques du script d'entrée du navigateur et fait échouer le build lorsqu'ils contiennent le loader d'un namespace de page.

## Les pages prérendues chargent d'abord le CSS et les polices

Les pages publiques sont prérendues et n'ont besoin d'aucun JavaScript pour leur premier affichage. TanStack Start émet une indication `modulepreload` pour chaque chunk dont une page peut avoir besoin, plus d'une centaine sur la page d'accueil, et sur un réseau mobile simulé elles entrent en concurrence avec la feuille de style et les polices. `scripts/optimize-prerendered-html.ts`, qu'exécute chaque script de build, supprime toutes les indications de dépendances et ne conserve que celle du script d'entrée de la page, avec `fetchpriority="low"` :

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

Supprimer les indications a réduit le First Contentful Paint d'environ un tiers ; conserver l'indication d'entrée en basse priorité a réduit le First Contentful Paint mobile de 375 ms supplémentaires. Ne rajoutez jamais d'indications de préchargement, ni pour les dépendances ni pour les chunks de route. Le script fait échouer le build lorsqu'il ne trouve aucune indication à supprimer ou aucune à conserver : un changement dans la sortie du build est ainsi détecté au lieu d'annuler silencieusement cette optimisation.

La politique de scripts préserve cet ordre. `scripts/secure-prerendered-html.ts` s'exécute après l'optimiseur et remplace le `<script type="module">` de l'entrée par un chargeur en ligne, au même endroit de la page, qui y crée le même script de module. L'indication d'entrée dans le head continue de lancer le téléchargement en basse priorité, et le module s'exécute toujours lorsque l'analyseur atteint la fin du body. Un chargeur qui appelle `import()` serait plus court, mais Chromium bloque un import dynamique depuis un script autorisé par un hachage.

`robots.txt` et `llms.txt` sont des fichiers statiques de `public/` qui contournent le Worker (`"!/robots.txt", "!/llms.txt"` dans `run_worker_first`). Lighthouse récupère les deux avec un délai d'expiration de deux secondes, et une réponse lente du Worker faisait échouer ses audits SEO et de préparation aux agents.

## Les fournisseurs n'enveloppent jamais l'outlet d'une route

TanStack Router enveloppe les outlets de route dans des frontières Suspense, et React hydrate ces frontières plus tard, par petites tranches. Un fournisseur de contexte placé au-dessus d'elles et dont la valeur change juste après l'hydratation oblige React à hydrater d'un coup tout ce qui se trouve en dessous :

- `ThemeProvider` autour de toute l'application transformait l'hydratation de la page d'accueil en une seule tâche de 200 ms qui bloquait les saisies. Monté autour de ses deux consommateurs, le `Toaster` et le `ThemeSwitch` de la documentation, il a fait passer le Total Blocking Time d'environ 150 ms à moins de 10 ms.
- `MotionProvider` au-dessus de l'outlet d'une route publie un nouveau contexte lorsque ses fonctionnalités d'animation ont fini de se charger. Sur un article de blog, cette mise à jour arrivait pendant que la page chargeait encore son contenu : React se rabattait sur le rendu côté client, et la mise en page se décalait.

Avant d'ajouter un fournisseur à `__root.tsx` ou à un layout, vérifiez si sa valeur peut changer après l'hydratation. Si c'est le cas, montez-le à côté des composants qui le lisent, sous chaque `<Outlet />` de route. Les emplacements sont listés dans [Composants et styles](/docs/conventions/components).

## Les squelettes restent dans le script d'entrée [#skeletons-stay-in-the-entry-script]

TanStack Router ne sépare pas `pendingComponent` dans un chunk à part par défaut, et `src/data/tanstack.vite.ts` conserve ce réglage, si bien que chaque squelette se trouve dans le script d'entrée et s'affiche dès qu'une navigation dépasse `pendingMs`. Les séparer a été mesuré puis écarté :

- Les squelettes de layout `AdminPending`, `AppPending` et `MarketingPending` dessinent le squelette de la page à partir de `PAGE_SKELETONS`, qui importe les squelettes de toutes les zones, et le routeur charge les composants de chargement des routes correspondantes avant l'hydratation de la page. `/`, `/app` et `/admin` chargeaient toujours chaque squelette, désormais dans des chunks à part, et grossissaient de 3,5 à 6,5 Kio compressés avec gzip ; seules les pages dont le layout a son propre squelette, comme `/docs` et `/blog`, s'allégeaient.
- Un squelette séparé doit être chargé avant de pouvoir s'afficher. Dans Chromium sans interface, avec 400 ms de latence ajoutée et 200 Kio/s, une navigation côté client de `/` vers `/blog` affichait le blog après 2 290 ms au lieu de 1 390 ms, derrière un squelette dont le build non séparé n'avait jamais eu besoin ; avec 150 ms de latence, elle prenait 800 ms au lieu de 640 ms.

Comme chaque page charge chaque squelette, un squelette importe `Skeleton`, les primitives shadcn, d'autres squelettes et les constantes qui fixent ses longueurs, jamais un formulaire. `PreferencesCardPending` était exporté par `preferences-card.tsx`, si bien que les squelettes de `/admin` et `/app` mettaient le formulaire des préférences, TanStack Form, la liste des fuseaux horaires et les schémas utilisateur dans le script d'entrée de chaque page ; il a désormais son propre fichier, `preferences-card-pending.tsx`. Tous les scripts que charge chaque page, compressés avec gzip, d'après la sortie de `bun run build:test` :

| Page           | Avant     | Après     |
| -------------- | --------- | --------- |
| `/`            | 463,0 Kio | 451,9 Kio |
| `/docs/<page>` | 553,6 Kio | 527,3 Kio |
| `/blog`        | 424,7 Kio | 413,6 Kio |
| `/app`         | 430,4 Kio | 404,1 Kio |
| `/admin`       | 452,9 Kio | 427,7 Kio |

`/` et `/blog` économisent moins parce que leurs layouts affichent le formulaire de la newsletter, qui a de toute façon besoin de TanStack Form. `pending-imports.test.ts` suit les imports de chaque `*-pending.tsx` et échoue lorsque l'un d'eux atteint `@tanstack/react-form`. Les panneaux du tableau de bord d'administration et les sections de l'aperçu client associent toujours chaque squelette à son composant dans la liste de la zone, si bien que ces composants se chargent avec les squelettes.

## Un seul build Tailwind

Seul `src/presentation/styles/globals.css` exécute Tailwind. Les feuilles de style des routes, comme `docs.css` et `typeset.css`, sont du CSS simple, et les styles propres à Fumadocs arrivent via `globals.css` :

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

Un second build Tailwind dans la feuille de style d'une route a un jour livré ses propres `.hidden`, `.rounded-md` et variables de thème. Les couches de cascade de même nom fusionnent d'une feuille de style à l'autre, et React ne retire jamais une feuille de style qu'il a insérée avec `precedence` : après une visite de la documentation, la page d'accueil perdait sa mise en page responsive et ses polices jusqu'au rechargement. Le test de bout en bout « landing keeps its responsive styles after visiting the docs » de `e2e/specs/landing.spec.ts` protège contre ce problème. Tout ce qui a besoin de Tailwind passe par `globals.css`.

## Médias

- **Boucles de la page d'accueil.** Chaque `src/presentation/assets/motion/<name>.webm` a une affiche `<name>.webp` exactement aux dimensions de la vidéo, pour que le passage de l'affiche à la vidéo ne produise pas de gain de netteté visible. Ces dimensions sont `LANDING_VIDEO_SIZES` dans `src/data/landing-videos.ts`, que lisent à la fois les compositions Remotion et `ConceptLoop`. Les largeurs plus petites sont des fichiers distincts, `<name>-<width>.webp`, proposés via le `srcSet` de l'affiche. `landing-videos.test.ts` échoue lorsque la taille d'une affiche diffère de celle de sa composition ou de la largeur indiquée dans son nom de fichier. Ne réduisez jamais l'affiche en taille réelle ; pour l'alléger, réencodez-la aux mêmes dimensions. Les vidéos se chargent avec `preload="none"`, ne sont lues que tant qu'un quart de leur surface est visible et ne sont jamais lues pour les lecteurs qui préfèrent des animations réduites.
- **La visite du cours** dans `course-showcase.tsx` n'est pas une boucle. Son `<video>` n'est rendu qu'après que le visiteur a appuyé sur lecture : jusque-là, la page ne charge que l'affiche, un `<picture>` avec des sources AVIF et WebP aux 1600 pixels de la vidéo et à 800. La vidéo elle-même est servie en WebM avec un repli en MP4.
- **Les vidéos des cours** sont encodées à l'avance en HLS adaptatif et servies depuis R2 avec le cache des Workers. Voir [Vidéos](/docs/features/videos).
- **Vidéo pilotée par le défilement.** Le site n'en contient aucune aujourd'hui. Une vidéo dont le temps suit la position de défilement doit être encodée en all-intra (chaque image est une image clé, `keyint=1`) : un encodage normal effectue un déplacement en environ 200 ms, un encodage all-intra en environ 3 ms, et aucun lissage en JavaScript ne permet de piloter fluidement une vidéo qui met 200 ms à se positionner.

## Apparition au défilement

`Reveal` (`src/presentation/components/custom/landing-page/components/reveal.tsx`) fait apparaître en fondu les sections de la page d'accueil lorsqu'elles entrent dans la zone d'affichage. Il partage un seul `IntersectionObserver` entre toutes les instances, détermine dès le premier callback de l'observateur si un élément commence sous la ligne de flottaison, et écrit directement des attributs `data-reveal`, sans état React ni nouveau rendu. Une version qui conservait la visibilité dans un état React doublait le Total Blocking Time, car chaque section était rendue à nouveau et la page calculait deux fois sa mise en page. Ne le remettez pas dans un état, et ne le remplacez pas sans comparaison.

Deux autres optimisations ont été mesurées et rejetées : `content-visibility: auto` sur les sections de la page d'accueil, qui cassait les liens internes vers les sections plus bas dans la page, et le chargement différé du formulaire de newsletter, qui obtenait un score identique ou moins bon que son rendu direct.

## Le contenu qui arrive plus tard garde sa taille

Une page prérendue s'affiche avant qu'aucun script ne s'exécute : une section qui se remplit ensuite doit donc tenir dans la place qu'on lui a donnée. Le bloc des cours de la page d'accueil en est une : il lit les cours publiés quand le défilement l'approche, et son espace réservé supposait auparavant deux cours de six leçons chacun, si bien que le bloc grandissait ou rétrécissait à l'arrivée des cours et déplaçait tout ce qui se trouvait dessous de cent pixels ou plus. Ses colonnes contiennent désormais un ensemble fixe de lignes uniques, l'espace réservé dessine les mêmes lignes et ses messages s'inscrivent dans un cadre de la taille d'une colonne, si bien que chaque état a la même hauteur à toutes les largeurs (voir [Cours](/docs/features/courses)). Le nombre d'étoiles de la page d'accueil fait de même avec un squelette aussi haut que le nombre. Écrire les cours dans le HTML prérendu n'est pas une option : le build n'a pas la base de données de production, et rendre la page d'accueil dans le Worker à chaque requête ferait perdre le temps jusqu'au premier octet que le prérendu fait gagner.
