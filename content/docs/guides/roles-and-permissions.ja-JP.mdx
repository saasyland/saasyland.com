---

アクセス制御には Better Auth の admin プラグインを使います。各エリアは、自分のリソースの権限ステートメントと、それを付与するロールを `src/data/<area>.access.ts` で宣言します。`src/data/access.entries.ts` がエリアをまとめ、`src/integrations/better-auth/auth.access.ts` がそこから Better Auth のアクセス制御、ロール、権限チェックを組み立てるため、認証のインテグレーションはどのエリアも名指ししません。ロールコードは `src/integrations/better-auth/auth.roles.ts` にあります。

## ステートメントとロール

```ts title="src/data/auth.access.ts"
const STATEMENTS = {
  admin: ["access"],
  settings: ["manage"],
} as const

export const AUTH_ACCESS = {
  grants: { [ROLE_CODES.ADMIN]: STATEMENTS },
  statements: STATEMENTS,
} as const satisfies AreaAccess
```

```ts title="src/integrations/better-auth/auth.access.ts"
export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...grantsOf(ROLE_CODES.ADMIN), ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole(grantsOf(ROLE_CODES.CUSTOMER)),
}
```

- `src/data/access.ts` の `APP_STATEMENTS` は、すべてのエリアのステートメントをリソース順にまとめ、2 つのエリアが同じリソースを宣言すると起動時に失敗します。`grantsOf(role)` は、すべてのエリアがそのロールに付与するものをまとめます。
- 認証エリアは `admin` と `settings`、商品エリアは `category` と `product`、コースエリアは `course` と `video`、決済エリアは `order` を宣言します。
- Better Auth の `defaultStatements` は、`user` と `session` のリソースを追加します（`user: ["list", "set-role", "ban", "impersonate", "delete"]` や `session: ["list", "revoke"]` など）。
- すべてのエリアは自分のステートメントをすべて `admin` に付与し、このロールには Better Auth の管理者ステートメントも付与されます。新規ユーザーのデフォルトロールである `customer` には、何も付与されません。
- `ROLE_VALUES` は、`user.role` カラムと `user.zod.ts` のロールのスキーマに型を与えます。
- `authorized` と `hasPermission` が受け取る型 `Permission` は、エリアが宣言するステートメントから組み立てられます。そのため、どのエリアも宣言していないステートメントやアクションはコンパイルを通りません。

## 権限をチェックする場所

| レイヤー           | チェック                                                                  |
| ------------------ | ------------------------------------------------------------------------- |
| ルートガード       | `requireAdmin` が `/admin` 領域全体で `admin: ["access"]` を要求します    |
| サーバー関数       | 保護されたすべての操作で `authorized({ product: ["update"] })` を使います |
| サインイン済みのみ | 呼び出し元自身のデータに対する操作には `authorized()` を使います          |
| その他の場所       | `hasPermission({ permission, role })` が真偽値を返します                  |

ルートガードが決めるのは、どのページをレンダリングするかだけです。サーバー関数は RPC で直接呼び出せるため、それぞれが自分で権限をチェックする必要があります。ボタンを非表示にするのは表示上の処理であり、認可ではありません。

## 権限を追加する

1. リソースを所有するエリアのステートメントにアクションを追加します。例えば `src/data/analytics.access.ts` の `report: ["read", "export"]` です。新しいエリアは、自分のファイルと、`src/data/access.entries.ts` への 1 行を追加します。
2. 同じファイルの `grants` で付与します。エリアは `STATEMENTS` 全体を `ROLE_CODES.ADMIN` に付与し、それより少ない権限にとどめるロールにはその一部を付与します。
3. サーバー関数でその権限を要求します：`.middleware([authorized({ report: ["export"] })])`。
4. 許可されるケースと `FORBIDDEN` のケースの両方を、エリアの `src/data/__test__/<area>.access.test.ts` とユースケースのテストでテストします。

## ロールを追加する

1. `auth.roles.ts` の `ROLE_CODES` と `ROLE_VALUES` にコードを追加します。
2. `auth.access.ts` の `ROLES` にロールを追加し、そのロールが使えるエリアの `grants` でステートメントを付与します。
3. すべてのロケールの `messages/<locale>/pages.admin.users.json` にある `filters.role.options` に、ロールのラベルを追加します。

認証クライアント（`auth.client.ts`）は `ac` と `ROLES` を受け取るため、ブラウザでの管理操作も同じ定義を使います。

## ユーザーとセッションの管理

user モジュールと session モジュールは、Better Auth の admin API をユースケースでラップしており、それぞれに固有の権限があります：`setUserRole`、`banUser`、`unbanUser`、`impersonateUser`、`deleteUser`、`setUserPassword`、`revokeUserSession` など。`revokeSession` のように呼び出し元自身のデータに対する操作は、`authorized()` を使い、`context.auth.user.id` で絞り込みます。

ローカルでは、`bun run db:seed:local` が管理者を作成します。プレビューと本番では、最初の管理者を `bun run admin:grant:preview <email>` または `bun run admin:grant:production <email>` で作成します。これを実行できるのはその D1 データベースへの書き込み権限を持つ人だけで、対象はメールアドレスを認証済みのアカウントです。2 人目以降の管理者は **管理画面 → ユーザー管理** の **ロールを変更** で作成します。[最初の管理者](/docs/tooling/database#the-first-admin)を参照してください。
