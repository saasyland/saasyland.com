Diese Seiten sind der Coding-Standard dieses Repositorys. Sie beschreiben, wie hier Code geschrieben wird, nicht, wie er geschrieben werden könnte, und jede Regel nennt die Dateien, die ihr folgen. Die meisten Regeln setzt ein Befehl durch: `bun run check` (Formatierung, Lint, Typen, Übersetzungen und Struktur der Dokumentation), `bun run test:coverage` (die 100-%-Hürde) oder die End-to-End-Suite. Die übrigen sichert das Review, und jede Seite sagt, welche das sind.

Wenn Sie unsicher sind, wie Sie etwas schreiben sollen, suchen Sie das nächstliegende vorhandene Beispiel derselben Art, lesen Sie es und übernehmen Sie seine Form. Konsistenz ist mehr wert als eine lokal bessere Idee: Ein zweiter Weg, dasselbe zu tun, zwingt jeden späteren Leser, ob Mensch oder Agent, beide zu lernen.

## Referenzimplementierung

Die Kursfunktion ist der neueste Code im Repository und die Form, an der Sie sich orientieren. Sie umfasst ein Tabellenmodul, öffentliche und Admin-Routen, Formulare, Dialoge, eine Datentabelle, Skeletons und Tests.

| Art                               | Vorlage                                                                |
| --------------------------------- | ---------------------------------------------------------------------- |
| Tabellenmodul                     | `src/modules/course/`, daneben `chapter`, `lesson` und `video`         |
| Lesezugriff mit Query-Optionen    | `src/modules/course/use-cases/get-course-editor.ts`                    |
| Paginierte Liste für eine Tabelle | `src/modules/course/use-cases/get-courses.ts`                          |
| Mutation mit Mutation-Optionen    | `src/modules/course/use-cases/update-course.ts`                        |
| Layout-Route                      | `src/routes/admin.courses.tsx`                                         |
| Seitenroute mit Datentabelle      | `src/routes/admin.courses.index.tsx`                                   |
| Seitenroute mit Parameter         | `src/routes/admin.courses.$courseId.tsx`                               |
| Formular                          | `src/presentation/components/custom/admin/courses/course-form.tsx`     |
| Dialog mit Formular               | `src/presentation/components/custom/admin/courses/chapter-dialog.tsx`  |
| Tabellenspalten                   | `src/presentation/components/custom/admin/courses/course-columns.tsx`  |
| Routen-Skeletons                  | `src/presentation/components/custom/admin/content-pending.tsx`         |
| Tests für Server Functions        | `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts` |
| Browsertests                      | `e2e/specs/course-admin.spec.ts`                                       |

## Regeln ohne Ausnahme

Wer gegen eine dieser Regeln verstößt, bekommt die Änderung abgelehnt, ganz gleich, was sie sonst gut macht.

1. Keine Kommentare in Code, Tests, Skripten, Konfiguration oder CSS. Siehe [Codestil](/docs/conventions/code-style).
2. Kein `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, keine `as`-Casts und kein `any`, um an einer Regel vorbeizukommen. Beheben Sie die Ursache.
3. Keine mehrzeiligen ternären Ausdrücke und kein `?? undefined`. Außerhalb von Tests und `src/platform/testing` steht `null` nur dort, wo eine API es vorgibt: im Vergleich mit einem Wert, der `null` sein kann, und in einer React-DOM-Ref (`useRef<HTMLElement>(null)`). Siehe [Codestil](/docs/conventions/code-style).
4. Status, Arten, Stufen, Rollen und andere Domänenwerte sind benannte Konstanten, niemals wiederholte String-Literale, auch nicht in Tests. Schematests sind der einzige Ort, an dem ein gespeicherter Wert ausgeschrieben wird. Siehe [Testen](/docs/conventions/testing).
5. Einen Ordner in `src/modules` gibt es nur für eine Datenbanktabelle. Siehe [Module](/docs/conventions/modules).
6. Jeder Text, den Nutzer sehen, existiert in allen neun Locales, ebenso jede Dokumentationsseite. Zahlen auf der Website werden gemessen, nie von Hand eingetragen. Siehe [Übersetzungen und Inhalte](/docs/conventions/translations).
7. Die Testabdeckung bleibt bei 100 % für Zeilen, Anweisungen, Funktionen und Verzweigungen. Siehe [Testen](/docs/conventions/testing).
8. Eine Änderung aktualisiert im selben Pull Request die README, die Dokumentation und die Website-Texte, die durch sie ungenau werden.
9. Commits und Pull Requests enthalten keine KI-Attribution und keinen `Co-Authored-By`-Trailer. Siehe [Git und Pull Requests](/docs/conventions/git-workflow).

## Definition of Done

Eine Änderung ist fertig, wenn diese Befehle in dieser Reihenfolge erfolgreich durchlaufen, und zwar in dem Branch, den Sie gleich pushen:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` und die Tests prüfen den Cloudflare-Build nicht: Ein Upgrade einer Abhängigkeit hat einmal beide bestanden, während der Produktions-Build kaputt war. Führen Sie `build:test` bei jeder Änderung aus und die Browser-Suite bei allem, was nicht nur Dokumentation ist. Lesen Sie vor dem Commit Ihren eigenen Diff auf Kommentare, auf String-Literale, die Konstanten sein sollten, und auf Texte oder Dokumentation, die durch die Änderung falsch geworden sind.
