## Worker とバインディング

`wrangler.jsonc` は、`src/server.ts` を Worker のエントリーとして設定します。Worker は次のバインディングを受け取ります。

| バインディング | 種類            | 用途                                                                                                                                                                              |
| -------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DB`           | D1 データベース | セッションとレート制限のカウンターを含む、すべてのテーブル                                                                                                                        |
| `CACHE`        | KV 名前空間     | GitHub のスター数                                                                                                                                                                 |
| `MEDIA`        | R2 バケット     | 動画、レッスンの資料、コースのカバー画像。`serveMedia`、`serveAttachment`、`serveCover` が `/media/` 配下で配信。事業者のロゴは `serveBusinessLogo` が `/media/logos/` 配下で配信 |
| `BUNDLES`      | R2 バケット     | CLI のテンプレートバンドル。`serveBundle` が `/bundles/` 配下で配信                                                                                                               |
| `ASSETS`       | 静的アセット    | プリレンダリング済みのページと `public` のファイル                                                                                                                                |

`/assets/*`、`/fonts/*`、`/robots.txt`、`/llms.txt` へのリクエストは、Worker を実行せずに静的アセットから返されます。サーバーコードは、バインディング、シークレット、`waitUntil` を `cloudflare:workers` から読み取ります。`src/server.ts` は、返すすべてのレスポンスにセキュリティヘッダーを追加します。Worker を経由せずに配信されるファイルには、`public/_headers` のサブセットが付きます（[セキュリティと堅牢化](/docs/features/security)）。

## Worker とビルドが実行するもの [#what-the-worker-and-the-build-run]

Worker と Vite のビルドは、それぞれ自分のリストを、それを実行するファイルの中に持ちます。機能は、その機能自身の識別子を指す 1 つの要素としてリストに加わるため、機能を外すと、その要素も機能のファイルと一緒に消えます。ルートルート、タイムゾーン、公開サイトのチェックは、パスやメニューと同じように、使うものを直接名指しします（[パスとナビゲーション](/docs/conventions/routes#paths-and-navigation)を参照）。

| リスト              | ファイル         | 実行                                                                                   |
| ------------------- | ---------------- | -------------------------------------------------------------------------------------- |
| `REQUEST_HANDLERS`  | `src/server.ts`  | Worker が、ロケールのミドルウェア、静的アセット、TanStack Start より前に実行します     |
| `DOCUMENT_REWRITES` | `src/server.ts`  | Worker が、返すすべての HTML ページに対して実行します                                  |
| `VITE_PLUGINS`      | `vite.config.ts` | `vp dev` と `vp build` が実行し、`vitest` が指定されたエントリーは Vitest も実行します |

リクエストハンドラーは `pathPrefix` を受け持ち、その配下のすべてのリクエストに応答します。`/media/covers/` のコースのカバー画像は `serveCover`、`/sitemap-courses.xml` のコースのサイトマップは `serveCourseSitemap`、`/media/downloads/` のレッスンの資料は `serveAttachment`、それ以外の `/media/` は `serveMedia`、`/bundles/` のテンプレートバンドルは `serveBundle` が返します。Worker は、パスがそのプレフィックスで始まる最初のハンドラーを使うため、狭いプレフィックスは、それを含むプレフィックスより前に置きます。ドキュメントの書き換えは、Worker が返すすべての HTML ページをそのロケールとリクエストとともに受け取り、送信するページを返します。地域別価格に対して `src/modules/license/license.pricing.ts` の `rewritePppOffer` が、ヘッダーのアカウントリンクに対して `src/modules/session/session.rewrite.ts` の `markSession` が行っているのがこれです。`src/server.ts` はプレフィックスと書き換えを静的にインポートするため、これらはコールドスタートのたびに評価されます。そのため `src/server.ts` がインポートするのは定数と純粋なヘルパーだけで、各ハンドラーは自分のモジュールを動的 `import()` で読み込みます（[パフォーマンス](/docs/conventions/performance)を参照）。

`serveBusinessLogo`（`src/modules/business-profile/business-profile.delivery.ts`）は `/media/logos/` 配下の事業者のロゴに応答し、コースの `/media/` ハンドラーより前に置かれます。

Vite プラグインのエントリーには、プラグインのパッケージをインポートしてそのプラグインを返す `load` と、Vitest でも読み込むかどうかを示す `vitest` があります。エントリーはリストの順に実行されます。Cloudflare、Fumadocs、コンテンツのインデックス、リポジトリの情報、Tailwind CSS、TanStack Start、React、zod のチャンク、デプロイする Worker、Polar SDK の任意のピア依存関係の順です。ベンダーのプラグインはベンダーと一緒に `src/integrations/<vendor>/<vendor>.vite.ts` に置きます。`fumadocsVitePlugins`、`zodVitePlugins`、`polarVitePlugins` がそれです。Vite は `~` エイリアスを解決する前に設定を読み込むため、`vite.config.ts` と、`src/lib/prerender.ts` の `shouldPrerender` をはじめとする、それがインポートするファイルは、`.ts` 拡張子付きの相対パスでインポートします。また、`vp lint` と `vp fmt` がプラグインのパッケージを読み込まないように、各エントリーはそのパッケージを `load` の中でインポートします。

`src/routes/__root.tsx` はアウトレットの隣に `AffiliateReferral` を描画します。これは、アフィリエイトプログラムが開いていて、訪問に紹介パラメーターが付いているときだけ Affonso のスクリプトを読み込みます（[アフィリエイトプログラム](/docs/features/affiliates)）。`TranslationsProvider` は、`TIME_ZONE_HOOKS` の最初のフックである `useSessionTimeZone`（`src/hooks/use-session-time-zone.ts`）のタイムゾーンで日付をフォーマットします。このフックは、ルートガードが読み込んだセッションからサインイン中のユーザーのタイムゾーンを返し、セッションがなければ `UTC` を返します。サインインのないプロジェクトにはフックがなく、その場合もプロバイダーは `UTC` を使います。`useSiteNavigation` は、ヘッダーとフッター用の訪問者のワークスペースを、`WORKSPACE_HOOKS` にある唯一のフック `useVisitorWorkspace` から受け取ります。`getRouter` は失敗したクエリとミューテーションをすべて `QUERY_ERROR_HANDLERS` の各ハンドラー、つまり認証機能の `recheckRefusedSession` に渡します。`useErrorMessage` は、エラーのメッセージを翻訳する名前空間を `ERROR_NAMESPACES` で引きます。この Map は、認証機能の `AUTH_ERRORS` をコアの `ERROR_CODES` と並べて展開したものです。サインインがなければ、メニューは並べたとおりのままで、失敗したリクエストは何も確認し直さず、メッセージは `ERROR_CODES` だけから引かれます。フッターの著作権表示は `APP_FOUNDED_YEAR` から `REPOSITORY_FACTS.buildYear` までで、同じ年は一度だけ表示するため、`REPOSITORY_FACTS` のないプロジェクトは創業年だけを表示します。いずれも、機能自身のファイルを名指しする 1 つの要素または 1 つの JSX 要素なので、その機能を外すとファイルと一緒に消えます。

デプロイ前チェックは `<name>:verify:<environment>` という名前のパッケージスクリプトで、機能が自身のスクリプトの 1 つとして `package.json` に追加します。`bun scripts/run-deploy-checks.ts preview` は、名前が `:verify:preview` で終わるスクリプトをすべて実行します。現在は認証機能の `auth:verify:preview` と Polar の機能の `polar:verify:preview` です。そのため、これらの機能のいずれかがないプロジェクトには、その機能のスクリプトもチェックもありません。空のシークレットやプレースホルダーのシークレットに対するチェックは、どの機能も宣言しません。デプロイ前チェックの前に `scripts/prepare-deploy-secrets.ts` が実行され、`wrangler.jsonc` が宣言するすべてのシークレットの中からそうした値を拒否するからです。

公開サイトのチェックは、デプロイ後にリクエストするパスと、そのパスが返すべきコンテンツタイプを指定します。ステータスは常に `200` です。チェックは `src/lib/deployment.ts` の `LIVE_SITE_CHECKS` に並び、デプロイ後に `scripts/verify-deployment.ts` がリクエストします。対象はトップページ、`robots.txt`、`security.txt`、サイトマップインデックスとページのサイトマップ、サイトカード、組織のロゴ、`/api`、セッションのエンドポイント、各プロバイダーでのサインイン、ブログのフィード、そしてリクエストごとに D1 から描画される `/courses` とコースのサイトマップです。`post` を持つチェックは、代わりにサイト自身のオリジンから JSON の本文を送り、JSON の応答を `findProblems` に渡します。`src/lib/auth.ts` の `signInPost` はこの方法で `OAUTH_PROVIDERS` の各プロバイダーのサインインを開始し、認可 URL がプロバイダーのホスト上にない場合、`client_id` が別の形式の場合、`redirect_uri` がデプロイ先のドメインに戻らない場合に拒否します（[OAuth プロバイダー](/docs/features/oauth)）。チェックは自分の機能のパスまたはヘルパーを名指しするため、その機能がないプロジェクトにはそのチェックもありません。

複数の機能が項目を追加する 3 つのリストは、それを実行するファイルの中にあり、どのリストの変更も人がレビューします。コースアクセスは `src/modules/lesson/lesson.access.ts` の `COURSE_ACCESS_GRANTS` で、唯一の要素はライセンスの付与です（[コース](/docs/features/courses)）。Better Auth のプラグインは `src/integrations/better-auth/auth.server.ts` の `plugins` で、`haveIBeenPwned` による漏洩チェック、ライセンスの `license-retention` フック、Polar プラグインが含まれます（[Better Auth](/docs/integrations/better-auth)）。Polar の各 Webhook イベントが届くコードは `src/integrations/polar/polar.webhooks.ts` の `POLAR_EVENT_HANDLERS` で、注文のコピー、サブスクリプションのコピー、ライセンスにそれぞれ 1 つずつ要素があります（[決済](/docs/features/payments)）。各要素はその機能のファイルを指すので、その機能がないプロジェクトではその要素が外れ、どの機能も、依存していない別の機能をインポートしません。ライセンスの機能はこのサイトにしかなく、常にコースの機能と一緒に含まれるので、自分のページのうちコースの機能が受け持つ部分は、リストを定義せずに直接インポートします。購入案内の最後に表示するロックされたコース（[顧客アプリ](/docs/features/customer-app)）、ライセンスが開いた最初の有料レッスンのタイトル（[ユーザー（管理）](/docs/features/users-admin#profile)）、購入確認に載せるコースへのリンク（[ライセンス](/docs/features/licences#purchase-confirmation)）です。

管理画面と顧客ワークスペースのリストは、それぞれを描画するコンポーネントの中にあり、ほかの機能は自分の識別子を指す要素としてそこに加わります。ユーザー管理のタブは `USER_TABS`、ユーザーのプロフィールのカードは `USER_PROFILE_SECTIONS`（[ユーザー（管理）](/docs/features/users-admin)）、ダッシュボードの統計とパネルは `DASHBOARD_STATS` と `DASHBOARD_PANELS`、コマンドパレットの検索は `COMMAND_SEARCHES`（[管理ダッシュボード](/docs/features/admin-dashboard)）、アカウント削除の案内は `ACCOUNT_DELETION_NOTICES`（[設定](/docs/features/settings#delete-account)）です。1 つの機能だけが追加するものは、リストを使わずに直接描画します。ワークスペースの **講座** 項目の横に表示するコースの進捗（[顧客アプリ](/docs/features/customer-app)）、概要ページのライセンスのセクション、登録フォームの下の同意の一文（[法務ページ](/docs/features/legal-pages)）、顧客テーブルの **端末** 列（[注文と顧客](/docs/features/orders#customers)）です。登録ページは、導入文と自分の説明文のどちらを表示するかを選ぶため、ライセンスの注文概要だけを項目に持つ導入文のリストを残しています（[ライセンス](/docs/features/licences)）。機能を外すと、そのファイルを指すリストの要素、プロパティ、JSX 要素がすべて削除されます。

メールを送る各モジュールは、`VERIFICATION_EMAIL_PURPOSE` のように、メールの目的の名前を自分の `<module>.constants.ts` に定義します（[Resend](/docs/integrations/resend)）。

## 環境

`wrangler.jsonc` は 4 つの環境を定義します。`vp dev` と `vp build` で使う環境は `CLOUDFLARE_ENV` で選択します。

| 環境          | バインディング                            | 使用箇所                                        |
| ------------- | ----------------------------------------- | ----------------------------------------------- |
| `development` | `.wrangler/state` 内のローカル D1、KV、R2 | `bun run dev`                                   |
| `preview`     | プレビュー用 D1、KV、R2                   | `bun run build:preview`、`deploy:preview`       |
| `production`  | 本番用 D1、KV、R2                         | `bun run build:production`、`deploy:production` |
| `test`        | `.wrangler/test` 内のローカル D1、KV、R2  | `bun run build:test`、Playwright                |

各環境は、必要なシークレットを `secrets.required` に列挙します。値は対応する `.env.<environment>` ファイルから取得され、デプロイスクリプトは空の値やプレースホルダーの値を拒否したうえで、宣言されたキーを `.wrangler/secrets.<environment>.json` に書き出し、そのファイルを `--secrets-file` で Wrangler に渡します。`test` 環境は、エントリーとして `src/platform/testing/worker.ts` を使い、`.env.test` にコミットされたダミー値を使います。`AFFONSO_PROGRAM_ID` は公開情報なので、シークレットではなく `vars` の下の通常の Worker 変数です。`production` は SaaSy Land のプログラム ID を、`test` はダミー ID を設定しています。1 つのモジュールのシークレットはまとめて、`.env.example`（`test` では `.env.test`）と同じ順序で並びます。そのため、機能はシークレットを 1 つのまとまりとして追加できます。`src/__test__/wrangler.test.ts` は名前を順序どおりに比較し、異なると失敗します。まとまりの間の空行は読みやすさのためだけのもので、フォーマッターが削除することもあるため、テストは空行を比較しません。

機能のバインディングも独立したブロックになります。R2 バケットは機能のもので、`MEDIA` はコースの、`BUNDLES` はライセンス販売の機能のものです。そのため、各環境で `r2_buckets` は最後に置かれて機能ごとに 1 つのエントリーを持ち、ある機能のないプロジェクトではそのエントリーがありません。`wrangler.test.ts` は、`development` と異なる D1 データベース、KV 名前空間、R2 バケットをバインドする環境があるとき、`development` のバインディングがリモートのとき、`development` が `preview` または `production` とリソースを共有するときにも失敗し、`scripts/verify-bindings.ts` はどのバインディングも名指しせずに、対象環境が宣言するすべてのバインディングをチェックします。

## 型

- `src/types/worker-configuration.d.ts` は `bun run cf-typegen` が `wrangler.jsonc` の `development` 環境から生成し、`DB`、`CACHE`、`MEDIA`、`BUNDLES` のバインディングと `secrets.required` のすべてのシークレットを含む `Cloudflare.Env` を宣言します。`src/types/bindings.d.ts` は、Wrangler が出力しない `ASSETS` を追加します。
- 機能が `src/types/<feature>.d.ts` で宣言するのは、Wrangler が導き出せないものだけです。`affiliates.d.ts` は `production` と `test` だけが設定する省略可能な `AFFONSO_PROGRAM_ID` 変数、`polar.d.ts` は `POLAR_SERVER` の 2 つの値、`repository-facts.d.ts` は `virtual:repository-facts` モジュール、`content-indexes.d.ts` は `virtual:content-indexes` モジュールを宣言します。`use-intl.d.ts` は use-intl のメッセージとフォーマットの型を登録します。
- `src/types/router.d.ts` は、ルーターの型と `staticData.namespaces` ルートオプションを登録します。

## テストランタイムの配線

`src/platform/testing` には、特定の機能に属させることができないものだけを置きます。

- `setup.ts`：jest-dom のマッチャー、各テスト前のバインディングのリセット、サーバー関数をプロセス内で実行するための `createServerFn` の置き換え
- `mocks/cloudflare.ts`：チェックイン済みのマイグレーションを実行するインメモリ SQLite の D1、インメモリの KV、`wrangler.jsonc` の `test` 環境にある R2 バインディングごとのインメモリのバケット、テストからフラッシュできる `waitUntil`
- `mocks/cache.ts`：`createEdgeCache`。メディア配信のテストで使う Workers のキャッシュのスタブ
- `mocks/resend.ts`、`mocks/polar.ts`、`mocks/auth.providers.ts`: Resend と Polar の API、Have I Been Pwned の範囲 API の厳密なテストダブル。それぞれプロバイダーのダブルのリスト（`RESEND_PROVIDER_DOUBLES`、`POLAR_PROVIDER_DOUBLES`、`AUTH_PROVIDER_DOUBLES`）に入っています。`mocks/providers.ts` の `DOUBLES` が各リストをインポートし、すべてのテストとブラウザーテスト用の Worker で `fetch` をそれらに振り向け、リセットします
- `mocks/wrksz-themes.ts`：テーマライブラリの代替実装
- `lib/`：サーバー関数の RPC ブリッジ、レンダリング用ヘルパー、リクエスト URL 用ヘルパー、クエリランナー、Polar のモデルと署名付きの Webhook
- `worker.ts`: ブラウザーテスト用の Worker のエントリー。プロバイダーのダブルをインストールし、各機能が `e2e/data/<feature>.worker.ts` で宣言するセットアップとテスト用エンドポイントを実行します。各リストは `ENTRIES` がインポートします。ライセンス機能は Polar のダブルにテスト用のライセンスキーを登録し、Resend は配信したメールを、ニュースレターは購読者の状態を公開します

各スイートでの使われ方は、[テストと CI](/docs/architecture/testing-architecture)を参照してください。
