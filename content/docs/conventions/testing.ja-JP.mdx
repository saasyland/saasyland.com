すべての変更は、それを証明するテストと一緒に同じコミットで出荷し、カバレッジは行、ステートメント、関数、分岐のすべてで <RepositoryFact name="coverageThreshold" unit="percent" /> を維持します。バグ修正には、その修正がなければ失敗するテストを付けます。

## プロジェクト

`vite.config.ts` は 3 つの Vitest プロジェクトを定義しており、ファイルのサフィックスによってどれかが選ばれます。テストは API を `vite-plus/test` からインポートし、対象のコードの隣の `__test__/` に置きます。

| サフィックス           | プロジェクト  | 用途                                                                                                                                                             |
| ---------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | ユースケース、ローダー、`head`、スキーマ、ユーティリティなど、サーバー上で実行されるものすべて                                                                   |
| `.integration.test.ts` | `integration` | Better Auth、決済、ライセンスのフロー、D1 アダプター、メッセージの読み込み。タイムアウトは <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | jsdom 上のコンポーネントとページ                                                                                                                                 |

`src/platform/testing/mocks/cloudflare.ts` は、すべてのプロジェクトで `cloudflare:workers` を置き換えます。D1 はチェックイン済みのすべてのマイグレーションから構築したインメモリの `node:sqlite` データベースで、KV と、`wrangler.jsonc` の `test` 環境にある R2 バインディングごとのバケットはインメモリのストアです。`resetTestBindings()` は各テストの前に KV、バケット、レート制限のテーブルを空にし、各スイートのシード関数は、そのスイートが依存する行をリセットします。Cloudflare、Polar、Resend、OAuth プロバイダーと通信するテストはありません。`fetch` は `mocks/resend.ts` と `mocks/polar.ts` の厳密なテストダブルに届き、テストダブルはすべてのリクエストを SDK のリクエストモデルに照らして検証し、プロバイダーが拒否するリクエストがあればテストを失敗させます。テストは SDK のメソッドをモックするのではなく、テストダブルが受け取った内容をアサートし、認証のスイートは `auth.harness.ts` を通じて本物の `auth.server.ts` の設定を動かします。

## サーバー関数のテスト

サーバー関数は、エクスポートされたオプションを通して呼び出します。そうすることで、テストが本物のミドルウェア、バリデーション、ハンドラーを実行します。`src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts` の例です。

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `src/platform/testing/lib/query.ts` の `executeQuery(options)` と `executeMutation(options, variables)` は、新しい `QueryClient` でオプションを実行します。
- セッションは `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts` の `createAuthSessionFixture` から作ります。すべての権限は、拒否されなければならない側からもテストします（`it("is for staff only")`）。
- シードデータはモジュールの `__test__/fixtures/` に置き、その ID は名前付きのオブジェクト（`IDS`、`LESSON_IDS`、`USERS`）にまとめます。`seedCatalogue()` は自分が所有する行を削除し、Drizzle を通して挿入し直すため、すべてのテストは同じ状態から始まります。
- `component` プロジェクトでは jsdom がブラウザーにあたるため、サーバー関数は reject されます。コンポーネントのテストでは、ルートにローダーのデータを与えるか、コンポーネントが読み取るオプションの `queryFn` と `mutationFn` をモックします。

## アサーションではコードの名前を使う

- 期待するステータス、種別、ロール、エラーコードには、コードが使う定数を使います（`COURSE_STATUS.DRAFT`、`ROLE_CODES.ADMIN`、`rejects.toThrow(ERROR_CODES.FORBIDDEN)`）。テストでドメインの文字列リテラルを繰り返すことはなく、e2e のデータやテストのシードも同様です。`e2e/data/courses.ts` は `kind: COURSE_KIND.COURSE` と書いています。
- 保存される値をそのまま書くのは、スキーマのテストだけです。`license.schema.test.ts` は `expect(LICENSE_STATUSES).toStrictEqual(["active", "revoked", "refunded"])` で値を固定しているため、データベースに保存される値を変えると、誰も書いていないマイグレーションが必要になる代わりにテストが失敗します。
- ブラウザーテストのスイートは定数をアプリケーションからインポートします（`LICENSE_TIER`、`ROLE_CODES`、`I18N.SUPPORTED_LOCALES`）。そのため、インポートできるのは Worker の外で読み込めるファイルだけです。Polar の値は、環境を読み取らない `polar.constants.ts` から取得します。`e2e/fixtures/license.ts` と Polar サンドボックスを使うジャーニースイートは注文ステータスを `POLAR_ORDER_STATUS` から取得し、注文そのものは `src/platform/testing/lib/polar.ts` から取得します。例外はプランの商品 ID です。`POLAR_PRODUCT_IDS` は `cloudflare:workers` を読み込むため、ブラウザーテストのスイートはそれらを `.env.test` から読み取ります。
- コンポーネントのテストは、期待する文言を英語のメッセージファイルから読み取り、要素はロールとアクセシブルな名前で探します。`admin-course-routes.component.test.tsx` では `import labels from "~/messages/en-US/pages.admin.courses.json"` と `labels.form.kinds.course` を使っています。
- 型が必要なテストは、型付きのソースから読み取るか、`toHaveProperty` で実行時にチェックします。キャストは決して使いません。
- テスト名は振る舞いを文として説明します（「lists every course with its lesson count, drafts included」）。

## カバレッジ

`bun run test:coverage` は、`src/**/*.{ts,tsx}` について 4 つの指標のいずれかが <RepositoryFact name="coverageThreshold" unit="percent" /> を下回ると失敗します。テスト、`__test__/`、型宣言ファイル、`src/routeTree.gen.ts`、shadcn のプリミティブ、`src/platform/testing/` は対象外です。このゲートを意味のあるものに保つため、次のことを守ります。

- **決して実行されない分岐は削除する。** スタブでカバーしてはいけません。常に存在するデータに対する `?? fallback` や、`undefined` になりえない値に対するオプショナルチェーンは、グローバルをスタブして到達させるのではなく、ソースから削除します。
- **実際の振る舞いをカバーする。** 処理中の状態は、`auth-forms.component.test.tsx` の `expectPending` と `expectIdle` のように、`Promise.withResolvers()` でリクエストを保留したまま処理中の UI をアサートし、`act` の中で解決してから待機中の UI をアサートします。
- **ルールに引っかかってもアサーションは残す。** テストが `max-statements` を超えたら、チェックを削らずに名前付きのヘルパーに切り出します。
- **すべてのメッセージファイルを読み込む。** `i18n.messages.test.ts` はすべてのロケールのすべての名前空間を読み込み、これによって `i18n.loaders.ts` の `import.meta.glob` の行がカバーされます。新しいメッセージファイルも自動的にカバーされます。

## 負荷の高いマシンでのテスト

Vitest のタイムアウトと `waitFor`・`findBy*` の 1 秒の猶予は実時間で数えるため、振る舞いに必要のない処理をするテストやタイマーを待つテストは、何も壊れていなくても負荷の高いマシンで失敗します。既定のタイムアウトはそのままにし、遅いテストは処理を減らすように直します。

- **多数のファイルにまたがるチェックはファイルごとに 1 つのテストにします。** `check-content.test.ts` は `it.each(sourcePages())` で英語の各ページについて `pageProblems` を実行し、差分があればそのページ名を示します。
- **コンポーネントが Suspense で待つものは描画の前に読み込みます。** 翻訳では `preloadNamespaces` がこれを行います。読み込みそのものを確かめるテストでは、`translations-provider.component.test.tsx` のように `act` の中で解決します。`act` の外で再開したコンテンツは、React が表示を遅らせたあと、実際のタイマーで初めて現れるため、テストはそれをポーリングすることになります。
- **コンポーネントを読み込み直さず、モジュールを一度だけ置き換えます。** `affiliate-referral.component.test.tsx` は `AFFILIATE_PROGRAM` を一度だけモックし、各テストで値を設定します。`vi.resetModules()` のあとにコンポーネントを読み込み直すと、そのインポートグラフ全体がテストの中で評価し直されます。
- **すべてのテストが読むフィクスチャはファイルごとに一度だけ作ります。** `getTestMessages` のメッセージがその例です。
- **キー入力そのものを確かめるのでなければ、フォームには `user.paste` で入力します。** `admin-course-routes.component.test.tsx` の `fill` はフィールドをクリックして貼り付けます。`user.type` は 1 文字ごとにフォームの検証と描画を実行します。
- **長い選択肢のリストは安く再描画できるようにします。** `preferences-card.tsx` のタイムゾーンのコンボボックスは選択肢をメモ化した `items` として `ComboboxList` に渡すので、フォームが再描画されても React Aria はそれを再利用します。

## テストは機能に従う [#tests-follow-the-features]

`scripts/features.ts` がファイルとパスを挙げる機能は（[パスとナビゲーション](/docs/conventions/routes#paths-and-navigation)を参照）、テストも自分で持ちます。そのため `saasyland` CLI は、生成するプロジェクトから機能をそのテストごと外せて、残るテストはすべて通り続けます。

1 つのテストファイルが扱うのは 1 つの機能か 1 つのソースファイルです。機能の管理画面のページは、スケルトンとパンくずリストも含めて `src/routes/__test__/admin-<feature>-routes.component.test.tsx` でテストし、ローダーは `admin-<feature>-loaders.test.ts` でテストします。レイアウトのスケルトンのテストでは、実際のルートツリーを使うルーターである `src/platform/testing/lib/render.tsx` の `createTestRouter(path, routeTree)` でレイアウトのスケルトンを描画します。コースのスケルトンは、`admin-course-routes` が独自のルーター用にコースのルートを組み直すため、`admin/__test__/courses-pending.component.test.tsx` でテストします。`admin-layout`、`admin-dashboard`、`admin-loaders` は管理画面そのものをテストし、どの機能の名前も出しません。互いに関係のないファイルにはそれぞれテストファイルを用意し（`background.component.test.tsx` や `wordmark.component.test.tsx` など）、API ハンドラーにもそれぞれ 1 つずつ用意します（`src/routes/api/__test__/auth.test.ts`、`index.test.ts`）。`cli.v1.test.ts` は CLI ライセンス API のルートファイルを対象とし、その動作は `src/modules/license/__test__/license.api.integration.test.ts` でテストします。

複数の機能にまたがるリストにはバレルがありません。各機能は自分の分を専用のファイルで宣言し、そのリストを読む唯一のファイルが各ファイルをインポートして 1 つのリテラルのリストに書き出します。機能を外すとそのファイルが消え、インポートとともに要素も消えます。

| 一覧                       | 各機能が宣言するもの                                                                                                          | 並べる側                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 管理画面のクエリデータ     | `src/presentation/components/custom/admin/__test__/<feature>.fixtures.ts` の `seed<Feature>Queries` と行のファクトリー        | `fixtures.tsx` の `adminQueryClient()`                                      |
| 列挙値のラベル             | `src/integrations/use-intl/__test__/<feature>.labels.ts`                                                                      | `enum-labels.test.ts` の `ENUM_LABELS`（コアのラベルはその場に書きます）    |
| D1 の行                    | `src/integrations/drizzle-orm/__test__/<feature>.rows.ts`                                                                     | `d1.integration.test.ts`                                                    |
| ブラウザーテストのページ   | `e2e/data/<feature>.pages.ts`                                                                                                 | `e2e/data/pages.ts` の `ENTRIES`（ホームページはその場に書きます）          |
| テスト用データベース       | `e2e/data/<feature>.seed.ts`                                                                                                  | `scripts/seed-test.ts`                                                      |
| フロー一覧                 | `e2e/data/<feature>.flows.ts` の、その機能のフロー（それぞれに、それを証明するテスト、またはテストがない理由）                | `scripts/check-flows.ts` の `FLOWS`                                         |
| 公開クエリ                 | 専用のソースファイルにある `public: true` のクエリ                                                                            | `auth.session.test.ts` の `PUBLIC_QUERIES`（クエリごとに 1 つのプロパティ） |
| プロバイダーのテストダブル | `src/platform/testing/mocks/<provider>.ts` の `<PROVIDER>_PROVIDER_DOUBLES` リスト（各ダブルは `origin`、`respond`、`reset`） | `mocks/providers.ts` の `DOUBLES`                                           |
| Polar のカタログ           | `src/modules/<module>/__test__/fixtures/<feature>.polar-catalogue.ts` の、その機能が販売する商品とライセンスキーの特典        | `mocks/polar.ts` の `CATALOGUES`                                            |
| テスト用 Worker            | `e2e/data/<feature>.worker.ts` のセットアップとテスト用エンドポイント                                                         | `src/platform/testing/worker.ts` の `ENTRIES`                               |

コアのために空のリストを宣言するファイルはありません。どのプロジェクトにもある項目は、`e2e/data/pages.ts` のホームページのようにリストそのものに書きます。`scripts/seed-test.ts` は、機能が行を投入するときだけ Wrangler を実行します。機能のページオブジェクトには専用のフィクスチャが付きます。`e2e/fixtures/auth.ts` は `e2e/fixtures/test.ts` のコアの `test` を `authPage` で拡張し、サインインするスペックはそこから `test` をインポートします。機能のメール用ヘルパーも、`e2e/fixtures/license-emails.ts` や `e2e/fixtures/invitation-emails.ts` のように専用のフィクスチャファイルに置き、共有の `getSentEmails`、`latestEmail`、`linkTo` は `e2e/fixtures/emails.ts` にあります。機能のブラウザー用ダブルは、`servePolarCheckout` のように `e2e/fixtures/test.ts` の `BROWSER_DOUBLES` に加わります。

複数の機能が使うヘルパーは 1 か所にだけ書きます。`src/presentation/components/custom/admin/__test__/fixtures.tsx` の `renderAdmin` と `renderAdminPage`、`src/routes/__test__/fixtures/admin-router.ts` の `loadAsAdmin`、`src/platform/testing/lib/skeleton.tsx` の `markupOf` と `busyMarkup`、そしてブラウザーテストの `AuthPage.signIn`、`BasePage.leaveWhileLoading`、`pageWithoutJavaScript` フィクスチャです。`accessibility.spec.ts` や `theme.spec.ts` のような公開ページのスペックは、どのアカウントでもサインインしません。サインイン後のページと、そのアクセシビリティとテーマは `workspaces.spec.ts` がチェックします。

機能が提供する項目を必要とする共有コードのテストは、機能が宣言した項目を読むのではなく、テスト専用の項目を宣言します。`dashboard-actions.component.test.tsx` は `ADMIN_DASHBOARD_ACTIONS` をテスト専用のアクションに置き換えるため、現在ダッシュボードのアクションを宣言している決済の機能がないプロジェクトでも、`DashboardActions` と `AdminDashboardPending` のアクションのプレースホルダーはカバーされたままです。`server.test.ts` は、各リクエストハンドラーのファイルを配信し、各ドキュメントの書き換えを Worker に通すテストを、その機能自身のモジュールを名指しして行うため、機能を外せばそのテストも消えます。`vite-config.test.ts` は `VITE_PLUGINS` を順序どおりに読み込み、ベンダーのプラグインはその隣でテストします（例: `zod.vite.test.ts`）。オプションの機能だけが描画する共有コードには、専用のテストを用意します。`pending-blocks.component.test.tsx` は、コース管理のスケルトンが使うフィールドのスケルトンをカバーします。`auth.access.test.ts` は各ロールに付与されるものをチェックし、各機能は自分のステートメントを `auth.access.courses.test.ts` のような `auth.access.<feature>.test.ts` でチェックします。`auth.access.website.test.ts` は、このサイトにおけるすべてのロールの権限を固定します。

`auth.server.test.ts` は Better Auth のすべてのプラグインの ID を順番どおりに列挙します。`navigation.test.ts` は特定の項目を期待せずにメニューをチェックするため、プロジェクトがどの項目を残しても通ります。`translations-provider.component.test.tsx` はコアの名前空間を例に使い、認証のテストはセッション一覧や `/app/settings` のような認証の機能自身のデータとパスを例に使います。

ライセンスのルートのテストはコースの `CourseUnlocks` をテスト内のセクションに、そのカタログのクエリをモックに置き換え、ライセンスのスケルトンのテストは `CourseUnlocksPending` で同じことを行い、コースのテストは `lesson.access.ts` のコースアクセスの付与を `withTestCourseAccess` で `TEST_COURSE_ACCESS`（`src/modules/course/__test__/fixtures/course-access.ts`）に置き換えるので、どちらの機能のテストももう一方を読みません。両者をつなぐ部分は `src/modules/lesson/__test__/lesson.access.license.test.ts` がテストします。ライセンスの付与と、ゲスト、アカウント、スタッフ、すべてのライセンスのティアとステータスについて、誰がどのレッスンを視聴できるかのスナップショットです。

`navigation.website.test.ts` のようにサイト全体を固定するテスト（すべてのメニューの順序を確認します）はこのサイト専用で、テンプレートは生成しません。

`scripts/features.ts` は、オプションの各機能のファイルを glob で、残るファイルの中でその機能が持つ名前（`src/routes.ts` にある各機能のパスなど）と、その機能が必要とする機能を挙げます。`bun run check:features` は、それらを外してもサイトが動くことをチェックします。1 つのシナリオはウェブサイトにしかない機能だけを外し、ほかの各シナリオはそれに加えてコース、課金の機能、コンテンツ、認証の機能のどれかを外します。スクリプトはシナリオごとに、それらの機能と、そのどれかを必要とするすべての機能のファイルを削除し、残るファイルを 1 つのルールで刈り込みます。`saasyland` CLI が機能を外すときに従うのと同じルールです。

1. 外した機能が持つ名前を、それぞれの宣言またはオブジェクトのプロパティごと削除します。
2. 外された参照とは、削除されたファイルからインポートした識別子、外された名前の使用（たとえば `src/routes.ts` が宣言しなくなった `ROUTES.COURSES`）、削除されたファイルに対して `import()` を呼ぶ関数、または削除されたモジュールを指す `vi.mock`、`vi.doMock`、`vi.unmock`、`vi.doUnmock` のことです。削除されたファイルの `import` と `export … from` はすべて消え、削除された宣言ファイルだけが宣言するモジュール（たとえば `virtual:repository-facts`）のインポートも消えます。
3. 外された参照がテストのコールバック、つまりどの形（`.each`、`.skip`、`.only` など）の `it` や `test`、または Playwright の `test.step` の中にあるときは、そのテスト全体を削除します。それ以外の外された参照については、次の単位のうち削除できるいちばん近いものを削除します。関数、クラス、`return` 文、条件、エクスポートは丸ごと削除しないので、それらにしか囲まれていない参照はファイル、行、列とともに報告します。
   - トップレベルの文の中でいちばん近い配列要素。なければ、文をまたがずにいちばん近いオブジェクトのプロパティ、スプレッド、型のメンバー、JSX の子要素。
   - 参照を囲む式文。モジュール、`describe`、`beforeEach` などのフックの直下にあれば削除し、それ以外の関数の中では、外側から参照しているものがすべて削除されるときだけ削除します。
   - 参照を囲む変数の宣言子。値が関数でもクラスでもなく、初期化子が参照するものがすべて削除されるときに限ります。宣言子が束縛する名前もそのとき外された名前になり、その使用がすべて同じルールで削除できるときだけ宣言子を削除します。メニュー項目から `signedInDestination(entry, workspace)` が組み立てるリンクのように、残るコードにも依存する値は残して報告します。変えるべきなのは刈り込みではなく設計だからです。
   - 参照を囲むフックまたは `describe`。
4. その結果、配列要素のプロパティである配列が空になったときは、その要素も削除します。項目がなくなったメニューのグループがその例です。`.each` のテーブルが空になったテスト、コールバックが空になったテスト、ステップ、フック、`describe`、テストが 1 つも残らない `describe`、本体が空になったループとコールバック（コールバックはそれを囲む単位ごと）も同じように削除します。関数や条件の本体が空になってしまう場合は文を残し、その中の参照を報告します。
5. 削除されたメッセージファイルの名前空間を指す、配列内の文字列要素を削除します。
6. どこからも参照されなくなったインポート指定子、エクスポートされていない宣言（深さは問いません）、配列の分割代入パターンの要素を削除し（後ろに残る要素があるときは穴を残します）、何も変わらなくなるまで繰り返します。テストが 1 つも残らない `*.test.*` や `*.spec.*` のファイルはまるごと削除します。

`scripts/prune-references.ts` は oxc パーサーの構文木にこのルールを適用し、`scripts/module-bindings.ts` はそれぞれの名前を参照先の宣言に解決します。そのため、同じ名前の引数やローカル変数をインポートと取り違えることはありません。`scripts/test-cases.ts` は、ファイルが `it`、`test`、`describe`、フック、`vi` としてインポートしたもの（ローカル名は問いません）の呼び出しから、テスト、グループ、フック、モックを見つけます。`scripts/prune-units.ts` は各参照を囲む単位を選び、`scripts/prune-edits.ts` は削除を書き込みます。削除した文の前後の空きのうち広いほうを残すので、文のまとまりの間の空行は消えません。`.gitattributes` が `linguist-generated` とする生成ファイルはそのままコピーし、ルートツリーはチェックが生成し直します。続いてスクリプトは、Git が追跡している、または追加しようとしているファイルを、刈り込んだものは元のファイルの代わりにして一時ディレクトリにコピーし、刈り込んだファイルを `vp fmt` で整形し、クラス名のテーブル、コンテンツの機能が残る場合はコンテンツのコレクション、`scripts/generate-routes.ts` でルートツリーを生成してから、`src`、`e2e`、`scripts`、`vite.config.ts` に対して `tsc --noEmit` を実行し、残ったメッセージに `check:i18n` をかけます。ルールで刈り込めない参照が残るか、型エラーか翻訳エラーが 1 つでもあればシナリオは失敗します。glob がどのファイルにも一致しないときや、名前がそのファイルで宣言されていないときは `src/__test__/check-features.test.ts` が失敗します。ルールで刈り込めない参照は、[ディレクトリ構成](/docs/architecture/directory-structure)が示す場所にコードを置くことで直し、刈り込みに例外を加えることはしません。CI はシナリオごとに 1 つのジョブを実行し、失敗したシナリオは実行全体を失敗させます（[CI/CD](/docs/tooling/ci-cd#checks)）。

## ブラウザーテスト

Playwright は、ビルド済みのテスト用 Worker に対して実行されます。`bun run build:test` は `.wrangler/test` 配下のローカルの D1 と KV を使ってそれをビルドし、`bun run db:reset:test` はそのデータベースを作り直して、`e2e/data` のアカウント、動画、コースをシードします。テスト用のエントリーは送信メールを `/__test/emails` でキャプチャするため、スペックは確認リンクをたどることができます。

- スペックはフローにちなんで命名し（`course-admin.spec.ts`、`auth-redirect.spec.ts`）、`e2e/pages/` のページオブジェクトを使って、ロールとアクセシブルな名前でページを操作します。
- 各スペックは、`crypto.randomUUID()` から作ったスラッグのような一意の値で、自分が変更するデータを作成し、独自の `CF-Connecting-IP` ヘッダーでサインインします。そのため、スペックは互いに衝突したりレート制限に引っかかったりすることなく、並列に実行でき、再実行もできます。
- シードされたデータ（ライセンスの端末など）を変更するテストは、並列ワーカーごとに 1 つずつ専用のシードレコードを使うので、実行中の 2 つのテストが同じレコードを変更することはありません。`cli-licence-api.spec.ts` は、`e2e/data/licenses.ts` の `TEST_CLI_LICENSES` が各ワーカーの `parallelIndex` に対してシードするライセンスで端末をアクティベートします。Playwright はこの番号を同時に 2 つのワーカーに割り当てません。`cliMachine` フィクスチャはテストの終了時に端末を解放するので、リトライはシードされたライセンスから始まります。`license.spec.ts` が読む `TEST_LICENSE` には、シードされた端末だけが残ります。
- スペックは、クライアント側のナビゲーションの後も含めて、`e2e/pages/base-page.ts` の `waitForAppReady()` が返ってからページを操作します。このメソッドは TanStack Router が現在の URL をレンダリングした時点で返ります。それを記録するのは、ルーターの `onRendered` イベントを購読する自動フィクスチャ `recordRenders` です。クライアント側のナビゲーションでは、次のルートがレンダリングされる前に URL が変わるためです。ルートのコンテンツはそのレンダリングの後にハイドレーションされることがあります。そのため、コンポーネント自身の状態に依存するスペックや、コンテンツがハイドレーションされる前にコンテンツ外のリンクを押すスペックは、先に `waitForHydration(element)` を呼び出します。これは React が要素とその中のすべてをハイドレーションするまで待ちます。`LandingPage.goto()` はランディングページの `main` に対してこれを行います。スペックは訪問者と同じように、読み込み中のページを離れてもかまいません。複数の直接アクセスにわたってページのエラーを集めるスペックは、`auth-routing.spec.ts` のように、アクセスごとに別のタブを開くか、`workspaces.spec.ts` のように、各ページのネットワークが落ち着くのを待ってから (`page.waitForLoadState("networkidle")`) 離れます。サイドバーのバッジや動画のセグメントのように、ページはハイドレーションの後で初めて送るリクエストを持つからです。ページのエラーを集めるスペックは、クライアント側のナビゲーションがレンダリングされてからページを離れます。スペックがページを離れ始めた後にページが開始したリクエストを、WebKit はアプリがその失敗を処理していてもページのエラー `Fetch API cannot load … due to access control checks.` として報告するためです。
- テキストが最後に消えていることだけでなく、一度も表示されないことを示す必要があるスペックは、変化の前に `e2e/pages/base-page.ts` の `watchForText(text)` を呼び出し、その後でテキストが一度も表示されなかったことを確認します。ページ内の `MutationObserver` が、レンダリングされた瞬間にそれを記録します。`checkout-funnel.spec.ts` のアップグレードのテストは以前のプランへのお礼について、ジャーニースイートは購入したプラン以外のお礼についてこれを行います。
- ページが Content Security Policy に違反すると、どのスペックも失敗します。自動フィクスチャ `cspViolations`（`e2e/fixtures/test.ts`）が `securitypolicyviolation` イベントをすべて記録し、テストの終了時に何も記録されていないことを期待します。意図的に違反を起こすスペックは、それを `cspViolations.splice(0)` で取り出します。`content-security-policy.spec.ts` がその例です。スイートが `build:test` の本番ビルドに対して実行されるのは、開発サーバーがスクリプトのポリシーを送らないためです。
- プルリクエストとマージキューでは、すべてのスペックを Chromium と WebKit で実行します。ローカルでは `bun run test:e2e:pr` が Chromium で、`bun run test:e2e` が両方で実行します。`main` へのプッシュでは WebKit でもう一度、週次のスケジュールでは両方で実行します。
- クリップボードを読むスペックは `e2e/fixtures/test.ts` の `readClipboard` フィクスチャを使います。このフィクスチャはスペックの開始前に、ブラウザーが知っているクリップボードの権限を付与します。Chromium では `clipboard-read` と `clipboard-write`、WebKit では `clipboard-read` だけです。WebKit には書き込みの権限がなく、Safari と同じく、コピーするクリックでクリップボードに書き込めるからです。
- 署名が必要なテスト用エンドポイントは、`test` ビルドが読み込む `.env.test` のダミーのシークレットを使ってテスト用 Worker の中で署名するため、スペックがシークレットを持つことはありません。`e2e/data/courses.worker.ts` の `/__test/media/signed-paths` は、動画のストリームとレッスンのダウンロードに、現在の時刻とすでに過ぎた有効期限でそれぞれ署名します。`e2e/data/billing.worker.ts` の `/__test/polar/billing-purchase` は、後から届く `subscription.updated` を含む Polar の注文とサブスクリプションのイベントに、テスト用の Webhook シークレットで署名します。
- リクエストの順序に依存するスペックは、`page.route` でリクエストを保留するか破棄します。`header-session.spec.ts` は訪問者が **Your account** を押す間ヘッダーのセッション確認を保留し、`course-progress.spec.ts` のレッスン完了のテストはそれを破棄します。こうすることで、最初に成功するセッション確認は、レッスンがすでにページに表示されている状態でのルートガードのプリロードになります。
- フローをエンドツーエンドで実行してその結果をアサートするスペックは、`e2e/data/<feature>.flows.ts` のそのフローに、スペックファイルと完全なタイトルで記載されます。スイートにないテストをフローが挙げていると `bun run check` が失敗するため、テストの名前を変えるときは同じコミットでフローも書き換え、どのテストも証明していないフローにはその理由を書きます。[テストカバレッジ](/docs/tooling/test-coverage)を参照してください。
- ユニットテストでは検出できないルート、フロー、見た目の修正にはスペックを用意します。アクセシビリティのスキャンや、`navigation.spec.ts` と、`content.spec.ts`、`legal.spec.ts`、`landing.spec.ts` のように対象の機能のスペックにあるナビゲーションの退行テストがその例です。スクロールするスペックは、`navigation.spec.ts` のスクロールのテストのように、ページの長さに頼らず自分でページを十分な高さにします。ページの読み込み後に中身が入るセクションは高さを保つため、スクロールするスペックがそれを先に読み込む必要はありません。ビューポートより上のセクションの高さが変わると訪問者が読んでいた内容が動き、スクロールアンカリングがそれを補正すると WebKit はスムーズスクロールを止めていました。`landing.spec.ts` のコースブロックのスペックは、そのリクエストを止めておき、成功または失敗させてから、ブロックが高さを保ち、レイアウトのずれが報告されないことを確かめます。
