## CLI: every option in the configurator

The [configurator](/#cli) shows every option and extra that SaaSy Land will generate, and the CLI will generate all of them. An option is enabled in the configurator, and accepted by `init`, only when a project generated with it installs, type-checks, passes its tests at <RepositoryFact name="coverageThreshold" />% coverage, builds and starts, in CI, on every change that can reach it. Until then the configurator shows it disabled and `init` refuses it with exit code <RepositoryFact name="cliExitNotAvailable" />, before any licence check.

Some answers depend on others. The API question applies only to the split and microservices architectures, and some runtimes and providers do not run on every deployment target, such as the Bun runtime on Cloudflare Workers. The configurator disables a combination the target cannot run.

The options arrive in this order:

1. Billing with Polar, with orders and customers in the generated admin console. It waits on generic billing in the application (Next).
2. The subscription course extra, with courses in the generated admin console. It needs billing.
3. Billing with Stripe, and email with Plunk.
4. Leaving email out, and leaving content out. Without email, sign-in needs a flow that sends no mail; without content, the coding conventions that a generated project's agent instructions point to must live outside the docs.
5. Postgres with Neon, Supabase or your own server; Turso; a local SQLite file; Prisma.
6. Deploying to Vercel or your own server; the Bun and Deno runtimes.
7. The split architecture with a Hono or Elysia API, then microservices.
8. Next.js and React Router on React.
9. Solid with SolidStart and TanStack Start, Vue with Nuxt, Svelte with SvelteKit, and Angular with Analog and Angular SSR.
10. Multi-tenancy, once organizations and roles are in the application.
11. The store with sample products, the visual page builder and the visual post editor, each after the application ships the feature it generates.

### Commands and releases

- Interactive questions in a terminal. Today a terminal session answers every question you did not pass as a flag with the default, as `--yes` does.
- `status`, which shows a project's release, answers and licence.
- `change`, which runs the CLI again on an existing project with different answers: modules first, platform switches later.
- `update`, which brings a project to a newer release in one command, with a three-way merge that keeps your own edits. Update and change scenarios run every night across recent releases.
- A generated reference of every command and flag in the [CLI guide](/docs/cli), and guides for upgrading the CLI, rotating a licence key, troubleshooting, and updating or changing a project. Every command in the guide runs in CI against the CLI under test.
- A next beta that corrects the CLI's own READMEs and release documentation.
- The stable release on npm's default tag. Until then, run the CLI as <RepositoryFact name="cliPackageSpec" />. Stable ships when billing and the course extra are in, and when the nightly journey generates a project with each package manager, builds it, runs its tests and checks the licence end to end. The site then switches its commands to the default tag and publishes the release notes and a release post.

## Application

1. Generic billing: the Polar customer portal and the licence on top of it.
2. Prices on the site read from Polar, so that a price changes in one place.
3. Creating, editing and deleting products from the admin, through Polar; pricing models, one-time and recurring; discount codes.
4. Issuing refunds from the order page, which already shows refunds recorded in Polar; an email to the buyer when a licence is refunded or revoked; and payment disputes on the order page, with their outcome applied to the licence.
5. Moving to a lower tier from the licence page. Today it is done by email to support.
6. Dashboard metrics on real data; sign-up and checkout funnel measurement that respects privacy; an analytics screen with page views, visitors, retention and churn.
7. The newsletter: a subscriber list with CSV export, sending issues from the admin, and turning the newsletter on and off in the customer workspace.
8. Permissions: an editor role, menus filtered by permission, and a role editor.
9. Organizations and teams, then Agency's team seats.
10. A workspace profile in the admin settings: name, support email, address and logo.
11. An audit log of bans, deletions and impersonation.
12. Editing the blog from the admin, in a visual editor that commits to Git through a pull request; then editing the docs.
13. The landing page built from a section registry, then the visual page designer, a pricing page, a section library and campaign pages.
14. The affiliate programme opens.
15. Apple Pay and Google Pay in the embedded checkout, which Polar has to enable for embedded checkouts.
