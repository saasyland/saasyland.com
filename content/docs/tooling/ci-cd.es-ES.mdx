Los flujos de trabajo se encuentran en `.github/workflows/`. Los flujos de trabajo de la aplicación (`ci.yml`, `deploy.yml`, `e2e-reusable.yml` y `deploy-reusable.yml`) configuran la cadena de herramientas con la acción compuesta `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ con la versión de Node de `.nvmrc` y la caché de instalación de Bun, que `setup-vp` restaura una sola vez, `bun install --frozen-lockfile --ignore-scripts` y `bun run typegen`. `remotion.yml`, en cambio, configura Node desde `.nvmrc` y npm.

| Flujo de trabajo      | Disparador                                                                                | Jobs                                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests y llamadas desde `deploy.yml`                                               | Comprobaciones y cobertura, E2E en Chromium y después el despliegue a preview de una pull request                 |
| `deploy.yml`          | Pushes a `main`                                                                           | Las comprobaciones de `ci.yml` y después el despliegue a producción con la publicación de su versión              |
| `e2e-full.yml`        | Pushes a `main`, la programación <RepositoryFact name="e2eFullSchedule" /> en UTC, manual | WebKit en cada push; Chromium y WebKit en las ejecuciones programadas y manuales                                  |
| `e2e-reusable.yml`    | Invocado por los flujos de trabajo anteriores                                             | Una sola compilación de pruebas, un proyecto de Playwright en shards paralelos y una sola comprobación para ambos |
| `deploy-reusable.yml` | Invocado por `ci.yml` y `deploy.yml`                                                      | Compilación, migraciones de D1 y `wrangler deploy`                                                                |
| `remotion.yml`        | Cambios en `remotion/` o en los archivos del sitio web que importa                        | Comprueba y empaqueta con npm el proyecto de vídeo de la página de inicio                                         |

`remotion.yml` se ejecuta con las mismas rutas en las pull requests y en los pushes: `remotion/`, el propio flujo de trabajo y los archivos del sitio web que importa `remotion/src`, directamente o a través de otros archivos del sitio web. `src/__test__/workflows.test.ts` sigue esas importaciones y falla cuando un archivo al que llegan no coincide con ninguna de las rutas, o una ruta no coincide con ninguno de los archivos.

Los checkouts de `e2e-reusable.yml`, cuya compilación renderiza el registro de cambios y cuyo `content.spec.ts` lo lee, de `deploy-reusable.yml`, que compila el sitio, y del job `release` descargan todos los commits sin sus árboles (`fetch-depth: 0` y `filter: tree:0`): el [registro de cambios](/docs/project/changelog) fecha cada entrada por el commit que la llevó a `main`. Frente a un clon superficial solo se añaden los propios commits; con un clon superficial la compilación fallaría en lugar de fechar mal las entradas. `src/__test__/workflows.test.ts` falla cuando uno de esos checkouts deja de descargar el historial.

## Comprobaciones [#checks]

El job `verify` de `ci.yml` ejecuta `bun run check` (tablas de nombres de clase, comprobaciones de i18n y de contenido, el [inventario de flujos](/docs/tooling/test-coverage#flow-coverage), formato, lint y tipos) y `bun run test:coverage`, y después sube el informe de cobertura. El job `e2e` invoca `e2e-reusable.yml`, que compila una sola vez y ejecuta la suite en <RepositoryFact name="e2eShards" /> runners en paralelo:

| Job                                          | Ejecuta                                                                                                                                                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                      | `db:reset:test` y `build:test`, y después sube `dist` y el `.wrangler/test` sembrado como un solo artefacto                                                                |
| `shard`                                      | Un job por shard: descarga esa compilación, instala el navegador y ejecuta `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>`                         |
| `report`, llamado `Build and E2E (chromium)` | Falla salvo que la compilación y todos los shards se hayan superado; cuando un shard ha fallado, combina los informes blob de los shards en un solo informe HTML y lo sube |

Los reintentos y los workers propios de Playwright se mantienen como los describe [Playwright](/docs/tooling/playwright#configuration), en cada shard. El job `report` es la única comprobación que exigen las reglas de la rama, así que añadir o quitar un shard no cambia el nombre de ninguna comprobación obligatoria.

En una pull request, `bun run check` también falla hasta que la pull request añade su [entrada del registro de cambios](/docs/conventions/git-workflow#changelog-entries). La compilación del job `e2e`, y la de los jobs de despliegue, falla mientras el registro de cambios fuera a mostrar en **Sin publicar** una entrada que no sea la de la propia pull request, y en `main` mientras fuera a mostrar cualquiera.

## Despliegues

Los despliegues solo se ejecutan después de que `verify` y `e2e` se superen, en la ejecución de `ci.yml` para una pull request y en la ejecución de `deploy.yml`, que invoca `ci.yml`, para un push a `main`:

| Evento                                          | Destino      | Entorno de GitHub | URL                           |
| ----------------------------------------------- | ------------ | ----------------- | ----------------------------- |
| Pull request desde una rama de este repositorio | `preview`    | `Preview`         | https://preview.saasyland.com |
| Push a `main`                                   | `production` | `Production`      | https://saasyland.com         |

`deploy-reusable.yml` asigna a cada entorno de GitHub su URL, y `src/__test__/workflows.test.ts` falla cuando una no coincide con su host en `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Las pull requests desde forks y de Dependabot se validan, pero no se despliegan. La preview es compartida: cada despliegue sustituye al anterior y usa la misma base de datos D1, el mismo espacio de nombres de KV y los mismos buckets de R2 de preview.

`deploy-reusable.yml` comprueba que existan los secretos `CLOUDFLARE_API_TOKEN` y `CLOUDFLARE_ACCOUNT_ID`, ejecuta `scripts/verify-bindings.ts`, compila con los valores ficticios de `.env.test`, elimina el `dist/server/.dev.vars` generado, aplica `db:migrate:<target>` y ejecuta `vp exec wrangler deploy --config dist/server/wrangler.json`. No ejecuta `scripts/verify-deployment.ts`, la comprobación del sitio desplegado de los scripts `deploy:<target>`, porque la protección contra bots de Cloudflare responde con 403 a las peticiones de los runners de CI. Tampoco ejecuta `scripts/run-deploy-checks.ts`, así que la CI no ejecuta ninguna de las comprobaciones de despliegue que las áreas declaran en `DEPLOY_CHECKS`: en la CI no hay ningún `.env.<target>` y los entornos de GitHub solo guardan las credenciales de Cloudflare. Hoy son `auth:verify`, del área de autenticación, y `polar:verify`, del área de Polar; ejecuta en local `bun run auth:verify:<target>` después de cambiar un cliente OAuth y `bun run polar:verify:<target>` después de cada cambio en Polar ([Configuración de Polar](/docs/getting-started/polar-setup)). No se sube ningún archivo de secretos: el Worker conserva los secretos de ejecución ya configurados en Cloudflare. Los despliegues al mismo destino se ponen en cola en lugar de cancelarse entre sí. Un nuevo commit en una pull request cancela la ejecución de `ci.yml` del commit anterior, que nadie va a fusionar, mientras que las ejecuciones de `deploy.yml` y `e2e-full.yml` en `main` se ponen en cola y nunca se cancelan entre sí (`concurrency` con `queue: max`), así que cada push a `main` se prueba y se despliega.

Dependabot actualiza las GitHub Actions semanalmente.

## Versiones y etiquetas [#releases-and-tags]

El sitio se despliega de forma continua, así que sus versiones son fechas, no versiones semánticas. Cuando un despliegue a producción termina con éxito, el job `release` de `deploy.yml` etiqueta el commit desplegado como `vYYYY.MM.DD` con la fecha UTC y publica una GitHub Release para él. Un segundo despliegue a producción el mismo día recibe la etiqueta `vYYYY.MM.DD.2`, el siguiente `.3`, y así sucesivamente. Los despliegues a preview nunca se etiquetan. El job `release` es el único con `contents: write`.

Las notas de la versión son las entradas del [registro de cambios](/docs/project/changelog) que publicó la versión, las que llegaron a `main` desde la etiqueta de versión anterior, cada una terminada en `(#<number>)`, que GitHub enlaza a su pull request, de modo que cada cambio se describe en un solo lugar; si una versión no publicó ninguna, sus notas enlazan al registro de cambios. `scripts/publish-release.ts` toma las notas de `src/lib/release.ts` y ejecuta `gh release create` con la etiqueta que eligió el despliegue. Una nueva ejecución conserva la etiqueta que ya tiene el commit y omite la GitHub Release si ya existe.

El job del despliegue a producción elige esa etiqueta antes de compilar: `scripts/choose-release-tag.ts` aplica `releaseTag` de `src/lib/release.ts` a las etiquetas del checkout, la compilación recibe la etiqueta como `RELEASE_TAG` y el job se la pasa al job `release` como su salida `release-tag`, de modo que el despliegue y su versión comparten una etiqueta. Con ella, el [registro de cambios](/docs/project/changelog) enlaza cada entrada a la versión que la publicó por primera vez: la etiqueta de versión más antigua cuyo commit contiene el commit squash de la entrada en el historial de primeros padres de `main`, que la compilación lee junto con las fechas en un solo `git log`, o la propia etiqueta del despliegue para las entradas que trae. El job `release` lee el registro de cambios de la misma manera, con la etiqueta que publica, así que las notas de una versión son exactamente las entradas que la página enlaza a esa versión. Las entradas fusionadas antes de la primera etiqueta de versión no enlazan a ninguna versión, y en las compilaciones locales, de vista previa y de pull requests tampoco las entradas que ningún despliegue ha publicado aún. Dos despliegues a producción no pueden elegir la misma etiqueta: `deploy.yml` ejecuta una sola ejecución del workflow a la vez (`concurrency` con `queue: max`), así que el job `release` de la ejecución anterior ya ha creado su etiqueta cuando el siguiente despliegue hace checkout del repositorio.

Para devolver producción a una versión, revierte en una pull request todo lo posterior a su etiqueta:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Al fusionarla, el código etiquetado se despliega tras las comprobaciones habituales y se etiqueta como una nueva versión. Las migraciones de D1 no se revierten, así que el código anterior se ejecuta sobre el esquema más reciente. Cada cambio de esquema debe funcionar con la aplicación desplegada antes que él, lo que hace que esto sea seguro para la versión anterior; lee las migraciones intermedias antes de retroceder más.
