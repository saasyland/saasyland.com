このページのルールはどれも計測から生まれたもので、いくつかは、かえって状況を悪化させた直感的な修正を置き換えたものです。これらのルールの背後にあるコードを変更するのは、それを上回る新しい計測結果がある場合だけにしてください。

## 主張する前に計測する

- 同じページで以前のビルドと新しいビルドを比較します。それぞれ少なくとも 5 回ずつ交互に Lighthouse を実行し、中央値を比較します。1 回の実行では何も証明できません。マシンのノイズにより、およそ 5 回に 1 回は外れ値が出ます。
- PageSpeed Insights の 1 回の実行で変更を判断してはいけません。同じデプロイでも、テストを実行するマシンの速度によってスコアは大きく変わります。Lighthouse はその速度を `benchmarkIndex` として報告します。
- 本番ビルド（`bun run build:test` の後に `bun run start:test`）を、圧縮を有効にした HTTP/2 で配信して計測します。圧縮なしの素のローカル HTTP/1.1 では、Lighthouse のネットワークシミュレーションが、本番では決して起こらない接続と転送サイズを前提に計算してしまいます。
- Lighthouse の診断はスコアではありません。以下のセクションで示すように、「強制リフロー」や「適切なサイズの画像」のようなヒントが、そのページにとっては誤りである場合があります。対応する前に、スコアに反映される指標を確認してください。

## Worker の起動グラフを小さく保つ

`src/server.ts` はすべての HTML リクエストで実行され（`wrangler.jsonc` の `run_worker_first`）、静的にインポートしたものはすべて、コールドスタートのたびに評価されます。そのため、このファイルと各エリアが追加する Worker ハンドラーは、定数と純粋なヘルパーだけをインポートし、それ以外はリクエストが必要としたときに読み込みます。

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

以前、Polar のクライアントもインポートしていたモジュールからヘッダー名を 1 つ静的にインポートしただけで、約 1.4 MB の SDK がすべてのコールドスタートに読み込まれ、ランディングページの最初の 1 バイトが届くまでに最大 1.4 秒かかったことがあります。`COUNTRY_HEADER` と `IP_ADDRESS_HEADER` が、重いものを何もインポートしない `src/modules/_core/constants/api.ts` にあるのはそのためです。`server.ts` や `<area>.worker.ts` に静的インポートを追加する前に、そのインポートの連鎖をたどってください。`polar`、`drizzle-orm`、`resend` に到達するものはすべて退行です。`scripts/verify-build.ts` はビルドのたびにこれを確認します。デプロイされる Worker のエントリーである `dist/server/index.js` の静的インポートをたどり、それらが `@polar-sh`、`drizzle-orm`、`resend` からバンドルされたコードに到達した場合や、合計が `BOOT_CLOSURE_MAX_BYTES` を超えた場合に失敗します。

## ルートツリーを軽く保つ [#keep-the-route-tree-light]

Worker は、プリレンダリング済みのページでも静的ファイルでもないすべてのリクエストを TanStack Start に渡し、Start はほかの何よりも先にルートツリーを読み込みます。これはレンダリングするページの場合も、サーバー関数の呼び出しの場合も同じです。ルートツリーとは、`src/routeTree.gen.ts` と、ルートファイルが静的にインポートするすべてのモジュールのことで、`/api/search` のようなサーバールートのハンドラーも含みます。Worker のアイソレートは、そのような最初のリクエストでこれを評価し、サーバー関数は最初の呼び出しで自分のチャンクを読み込みます。どちらも訪問者がクライアント側のナビゲーションを待っている間に起こるため、それらがインポートするものはすべて、新しいアイソレートでの待ち時間の一部になります。

以前は、ドキュメントとブログのコレクションを最初からすべて読み込んでいました。`.source/server.ts` は、すべてのロケールのすべてのドキュメントページとブログ記事のコンパイル済み MDX をインポートしていました。これは各ページの見出しと検索用テキストを含む 1,305 個のモジュールです。さらに Lucide アイコンプラグインが、ドキュメントの meta ファイルが名前を挙げる数個のアイコンのために、アイコンセット全体を追加していました。ドキュメントのレイアウト、ドキュメントのページ、ランディングページ、ブログはサーバー関数を通じてこのソースを読み、`/api/search` はこれを静的にインポートしていたため、ソースがルートツリーに入っていました。saasyland.com では、`/` から `/docs` へのクライアント側のナビゲーションが 2 つのサーバー関数を待つ時間は、新しいアイソレートで約 1.3 秒、ウォームなアイソレートで約 25 ms でした。ランディングページとブログも、最初のナビゲーションで同じだけの時間がかかっていました。

- `fumadocs.config.ts` は両方のコレクションを `async` にします。ソースは各ページのフロントマターを保持し、リクエストがページの見出しや検索用テキストを必要とするときに、`page.data.load()` がそのページのコンパイル済み MDX をインポートします。ページツリーと `getDocsPage` はフロントマターだけを読みます。ランディングページは表示する記事を、ブログの一覧は 1 つのロケールの記事を、ブログ記事のページはその記事自体を、`/api/search` は最初のリクエストですべてのページを読み込みます。
- `/api/search` はハンドラーの中で `fumadocs.search.ts` をインポートするため、検索インデックスはルートツリーに入りません。
- `fumadocs.icons.ts` は meta ファイルが名前を挙げるアイコンだけをインポートします。meta ファイルがインポートされていないアイコンを指定した場合や、どの meta ファイルも指定していないアイコンがインポートされている場合、`fumadocs.icons.test.ts` は失敗します。

サイズは、`bun run build:test` の Worker で各部分が静的にインポートするものの合計です。時間は、ノート PC で交互に 5 回ずつ実行した中央値です。

| 指標                                                                                              | 変更前                     | 変更後                   |
| ------------------------------------------------------------------------------------------------- | -------------------------- | ------------------------ |
| ルートツリー（すべてのサーバーリクエストが読み込む）                                              | 1,635 モジュール、21.7 MiB | 296 モジュール、4.9 MiB  |
| ドキュメントのページツリーと `getDocsPage`（それぞれのインポートを含む）                          | 1,402 モジュール、16.9 MiB | 41 モジュール、1.3 MiB   |
| `dist/server` 内の JavaScript                                                                     | 4,275 ファイル、28.0 MiB   | 2,953 ファイル、26.8 MiB |
| Node でのルートツリーの評価                                                                       | 554 ms                     | 162 ms                   |
| Node での Fumadocs のソースの評価                                                                 | 375 ms                     | 24 ms                    |
| 新しい `vp preview` の Worker で、`/` から `/docs` の見出しが表示されるまでの最初のナビゲーション | 260 ms                     | 198 ms                   |

`scripts/verify-build.ts` は、ルートツリーと `dist/server` 内のすべてのサーバー関数の静的インポートをたどり、それらがコンパイル済みのドキュメントページやブログのページに到達するとビルドを失敗させます。ルートツリーがまだ読み込むものの大部分、約 3 MiB は Better Auth とそれがインポートするモジュールで、`/api/auth/$`、認証ページの検索パラメーターのスキーマ、CLI のライセンス API がこれを静的にインポートしています。

## 遅いナビゲーションはすぐにスケルトンを表示する [#a-slow-navigation-shows-its-skeleton-at-once]

`src/router.tsx` は、`src/data/navigation.constants.ts` の値を使って、`defaultPendingMs` を <RepositoryFact name="navigationPendingMs" unit="millisecond" /> に、`defaultPendingMinMs` を <RepositoryFact name="navigationPendingMinMs" unit="millisecond" /> に設定します。TanStack Router のデフォルトである 1 秒と 0.5 秒のままでは、遅いナビゲーションは丸 1 秒間、新しいアドレス以外に何も表示しませんでした。新しいアイソレートで **ドキュメント** を最初にクリックすると約 1.6 秒かかり、ドキュメントのスケルトンは 1 秒後にようやく表示されるか、まったく表示されませんでした。また、ルートに `pendingMs: Number.POSITIVE_INFINITY` が設定されていたドキュメントページ間のクリックでは、待っている間ずっと前のページが表示されたままでした。

- 遅延時間内に完了するナビゲーションは、次のページの準備ができるまで前のページを表示し続け、スケルトンを表示することはありません。saasyland.com では、ルーターがホバー時にプリロードしたページや、すでに読み込んだページへのナビゲーションは、クリックから 40〜115 ms で完了しました。ウォーム状態の Worker でセクションを初めて訪れる場合は、リクエストごとに 40 ms のレイテンシを加え、リンクにホバーせずにローカルで測定すると 184〜314 ms でした。遅延時間はどちらよりも長いため、どちらのナビゲーションでもスケルトンは表示されません。
- 遅延時間を過ぎてもまだ読み込み中のナビゲーションは、読み込みが続いている間だけルートのスケルトンを表示します。`defaultPendingMinMs` は <RepositoryFact name="navigationPendingMinMs" unit="millisecond" /> なので、ルーターはスケルトンを画面に留めておくことはせず、ページの準備ができた時点で取り除きます。
- ドキュメントのページには独自のスケルトン `DocsIndexPending` と `DocsPagePending` があり、サイドバーの横の記事と目次を埋めます。そのため、ドキュメントページ間の遅いナビゲーションでは、前のページをそのまま残すのではなく、次のページの形が表示されます。

`e2e/specs/content.spec.ts` は、`/docs` へのナビゲーションとドキュメントページ間のナビゲーションのサーバー関数を保留し、サーバー関数が応答するまで、それぞれがスケルトンを表示し、2 つ目ではサイドバーも表示することを確認します。

## ORM をブラウザーに入れない [#keep-the-orm-out-of-the-browser]

Drizzle は Worker の中だけで動きます。ブラウザーには、フォームのためにモジュールの Zod スキーマが、セレクトフィールドのために enum のタプルが必要です。そのため、どちらも Drizzle から何もインポートしないファイル、`<table>.zod.ts` と `<table>.constants.ts` に置きます（[モジュール](/docs/conventions/modules)を参照）。ブラウザー側のインポートが `<table>.schema.ts` に到達すると `sqliteTable(...)` が実行されます。バンドラーはこの呼び出しを取り除けないため、`drizzle-orm` も一緒に読み込まれます。

以前の `<table>.zod.ts` は、`drizzle-zod` を使ってテーブルから `insert`、`select`、`update` のスキーマも組み立てていましたが、実行時にそれらを読むものはありませんでした。`drizzle-zod` は zod の名前空間全体を保持するため、バンドラーは zod のすべてのロケール、JSON Schema への変換器、コンパイラーまで残していました。`/admin` と `/app` の読み込み中のスケルトンは `preferences-card.tsx` から `PreferencesCardPending` をインポートしていて、このファイルは `user.zod.ts` をインポートしていました。ペンディングコンポーネントはコード分割されないため、これらすべてがすべてのページで読み込まれていました。タプルを定数に移し、これらのスキーマを削除したことで、すべてのページで gzip 圧縮後の JavaScript が約 75 KiB 減りました。以下のサイズは、各ページが読み込むすべてのスクリプトを gzip で圧縮した合計で、`bun run build:test` の出力から取ったものです。

| ページ         | 変更前    | 変更後    |
| -------------- | --------- | --------- |
| `/`            | 526.2 KiB | 450.7 KiB |
| `/docs/<page>` | 612.1 KiB | 536.5 KiB |
| `/blog`        | 487.2 KiB | 411.7 KiB |
| `/app`         | 496.6 KiB | 421.0 KiB |
| `/admin`       | 515.0 KiB | 439.4 KiB |

`src/data/tanstack.vite.ts` は、TanStack Start のインポート保護によって、クライアント環境での `drizzle-orm` のインポートを禁止しています。

```ts title="src/data/tanstack.vite.ts"
const SERVER_ONLY_PACKAGES = [/^drizzle-orm(?:\/|$)/u]
```

そのインポートがツリーシェイキング後も残るビルドは失敗し、ルートから Drizzle に到達したファイルまでのインポートの連鎖を出力します。連鎖はその起点で断ち切ってください。タプルはモジュールの定数からインポートするか、コードをサーバー関数に移します。型のみのインポートは消去されるため、対象になりません。

## メッセージはページが必要とするときに読み込む [#load-messages-when-a-page-needs-them]

訪問者が最初に開くページは、ブラウザーでメッセージファイルを 1 つも読み込みません。root ルートとマッチしたルートがサーバー上で名前空間をクエリキャッシュにプリロードし、TanStack Start がそのキャッシュを HTML と一緒に送るからです。ブラウザーが名前空間を読み込むのは、後のナビゲーションでキャッシュにまだない名前空間が必要になったときだけです。

`import.meta.glob` はメッセージファイルごとに専用のチャンクを作りますが、各ファイルからチャンクへの対応表は、すべてのロケールのすべての名前空間を含み、glob を呼び出すモジュールに入ります。そのモジュールは root ルートがインポートする `i18n.messages.ts` で、メッセージ用とページメタデータ用に対応表を 2 つ持っていたため、どのページも約 240 KiB、gzip 圧縮後で 21 KiB のローダーを読み込んでいました。対応表は現在 `i18n.loaders.ts` に単独で置かれ、`loadNamespace` が最初に名前空間を読み込むときにインポートします。

```ts title="src/integrations/use-intl/i18n.messages.ts"
const { MESSAGE_LOADERS } = await import("~/src/integrations/use-intl/i18n.loaders")
```

`loadPageMetadata` は 2 つ目の対応表ではなくページの名前空間から `metadata` を読むため、ページの head とメッセージは同じチャンクから来ます。ブラウザーは `i18n.loaders.ts`（gzip 圧縮後で約 11 KiB）を、ナビゲーション時またはホバーによるプリロード時に、最初に読み込む名前空間と一緒に取得します。root 名前空間は引き続き `i18n.messages.ts` でファイル名から見つけられ、その glob のキーは gzip 圧縮後で約 2 KiB です。各ページが読み込むすべてのスクリプトの gzip 圧縮後のサイズ（`bun run build:test` の出力より）：

| ページ         | 変更前    | 変更後    |
| -------------- | --------- | --------- |
| `/`            | 462.9 KiB | 442.3 KiB |
| `/docs/<page>` | 553.5 KiB | 532.9 KiB |
| `/blog`        | 424.6 KiB | 404.0 KiB |
| `/app`         | 430.4 KiB | 409.7 KiB |
| `/admin`       | 452.8 KiB | 432.2 KiB |

メッセージは `loadNamespace` 経由でのみ読み込み、root ルートがインポートするモジュールに `messages/` を対象とする `import.meta.glob` を追加してはいけません。`scripts/verify-build.ts` はブラウザーのエントリースクリプトの静的インポートをたどり、ページ名前空間のローダーが含まれているとビルドを失敗させます。

## プリレンダリングされたページは CSS とフォントを先に読み込む

公開ページはプリレンダリングされており、最初の描画に JavaScript を必要としません。TanStack Start は、ページが必要としうるすべてのチャンクに対して `modulepreload` ヒントを出力し、ランディングページではその数が 100 を超えます。シミュレートされたモバイルネットワークでは、これらがスタイルシートやフォントと帯域を奪い合います。すべてのビルドスクリプトが実行する `scripts/optimize-prerendered-html.ts` は、依存関係のヒントをすべて削除し、ページ自身のエントリースクリプトのヒントだけを `fetchpriority="low"` で残します。

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

ヒントを削除したことで First Contentful Paint は約 3 分の 1 短くなり、エントリーのヒントを低い優先度で残したことで、モバイルの First Contentful Paint がさらに 375 ms 短くなりました。依存関係のものでもルートのチャンクのものでも、プリロードヒントを戻してはいけません。このスクリプトは、削除するヒントや残すヒントが見つからない場合にビルドを失敗させます。そのため、ビルド出力が変わっても、この最適化が気づかないうちに元に戻ることはなく、確実に検出されます。

TanStack Start は現在すべてのヒントを `fetchpriority="low"` で出力するため、2026 年 11 月にランディングページでこのルールを測り直しました。各バリアントで交互に 5 回ずつ実行しています。156 個のヒントをすべて残すと、ブラウザーはページのチャンクを 11 回ではなく 1 回の波で取得し、CLI コンフィギュレーターのハイドレーションはデスクトップで 250 ms、スロットリングしたスマートフォンで 315 ms 早まりましたが、First Contentful Paint はデスクトップで 68 ms、モバイルで 77 ms 遅くなりました。ヒントは引き続き削除します。

スクリプトのポリシーもこの順序を保ちます。Worker は、すべてのプリレンダリングされたページを `withNonce` に通してストリーミングします。この `HTMLRewriter` は、エントリーの `<script type="module">` とそのヒントにレスポンスの nonce を追加するだけで、ほかには何も変更しません。そのため、head にあるヒントは引き続き低い優先度でダウンロードを開始し、モジュールも引き続き、パーサーが body の終わりに達した時点で実行されます。書き換えはストリーミングで行われるので、バイトを溜め込むことはありません。ただし、HTML レスポンスには `ETag` が付かないため、ブラウザーはページを再検証せずに、もう一度ダウンロードします。

`robots.txt` と `llms.txt` は `public/` にある静的ファイルで、Worker を経由しません（`run_worker_first` の `"!/robots.txt", "!/llms.txt"`）。Lighthouse はどちらも 2 秒のタイムアウトで取得するため、Worker の応答が遅いと SEO とエージェント対応の監査で不合格になっていました。

## Early Hints にはデプロイ後も残るファイルだけを並べる

HTML レスポンスに付く Worker の `Link` ヘッダーには、ロケールのフォントだけを並べます。Cloudflare はこのヘッダーを URL ごとに保存し、その URL への次のリクエストに Worker が応答する前に `103 Early Hints` レスポンスとして送ります。保存されたコピーはデプロイ後も残ります。Vite はスタイルシートに内容から決まる名前を付けるので、CSS が少しでも変わるデプロイの後は、ヒントに載ったスタイルシートはもう存在しないファイルです。ブラウザーは 404 をダウンロードし、結局は HTML から新しいスタイルシートを見つけます。`public/fonts` のファイルは、デプロイをまたいでも同じ名前のままです。

saasyland.com で Chromium を使い、3 ページでバリアントごとに 15 回ずつ交互に実行し、エッジの実際の Early Hints のタイミングで測定しました。フォントをヒントに載せると、First Contentful Paint は 168–208 ms から 144–164 ms に下がりました。スタイルシートのヒントは、URL が最新のときはさらに 12–28 ms 短縮しましたが、デプロイで置き換わった後は何も短縮しませんでした。デプロイの 25 分後、Early Hints を受け取ったサイトマップの 91 ページのうち 67 ページが、まだ前のスタイルシートをヒントに載せていました。スタイルシートの `<link>` はどのページでも最初の 1 キロバイトにあるので、ブラウザーは HTML の最初のバイトでそれを見つけます。ヒントには、デプロイ後も URL が変わらないファイルだけを載せてください。

## プロバイダーはルートの outlet を包まない

TanStack Router はルートの outlet を Suspense 境界で包み、React はそれらの境界を後から小さな単位で少しずつハイドレーションします。その上にあるコンテキストプロバイダーの値がハイドレーション直後に変わると、React はその下にあるすべてを一度にハイドレーションせざるを得なくなります。

- アプリケーション全体を包む `ThemeProvider` によって、ランディングページのハイドレーションが、入力をブロックする 200 ms の 1 つのタスクになっていました。利用する 2 つのコンポーネント、`Toaster` とドキュメントの `ThemeSwitch` の周りにマウントしたところ、Total Blocking Time は約 150 ms から 10 ms 未満になりました。
- ルートの outlet の上にある `MotionProvider` は、アニメーション機能の読み込みが終わると新しいコンテキストを公開します。ブログ記事では、ページがまだコンテンツを読み込んでいる最中にその更新が届き、React がクライアントレンダリングにフォールバックして、レイアウトがずれました。

`__root.tsx` やレイアウトにプロバイダーを追加する前に、その値がハイドレーション後に変わりうるかを確認してください。変わりうる場合は、すべてのルートの `<Outlet />` より下で、それを読み取るコンポーネントのそばにマウントします。配置の一覧は[コンポーネントとスタイリング](/docs/conventions/components)にあります。

## ハイドレーションが重いウィジェットには専用の境界を与える [#a-widget-that-is-heavy-to-hydrate-gets-its-own-boundary]

ランディングページの CLI コンフィギュレーターは 40 個の React Aria ボタンを描画し、それぞれが押下、ホバー、フォーカスのフックを持ちます。ページの残りと一緒にハイドレーションすると、それらのエフェクトによってページのハイドレーションを締めくくるコミットが Lighthouse のデスクトップのスロットリングで 70〜100 ms のタスクになり、Total Blocking Time が 101 ms から 147 ms に上がりました。`CliSection` は `CliConfigurator` を、決してサスペンドしない `Suspense` 境界で包みます。React はこのような境界をページの残りの後に単独でハイドレーションし、別のコミットで確定するため、長いタスクはなくなり、Total Blocking Time は 100 ms になりました。First Contentful Paint と Largest Contentful Paint は変わりません。コンフィギュレーター自体のハイドレーションは約 50 ms 遅くなります。ほかのウィジェットに専用の境界を与えるのは、比較で同じ長いタスクが確認できたときだけにしてください。

## スケルトンはエントリースクリプトに残す [#skeletons-stay-in-the-entry-script]

TanStack Router はデフォルトでは `pendingComponent` を専用のチャンクに分割せず、`src/data/tanstack.vite.ts` もこのデフォルトを保っています。そのため、すべてのスケルトンはエントリースクリプトに含まれ、ナビゲーションが `pendingMs` を超えた瞬間に表示されます。分割は計測したうえで採用しませんでした。

- レイアウトのスケルトン `AdminPending`、`AppPending`、`MarketingPending` は、すべてのエリアのスケルトンをインポートする `PAGE_SKELETONS` からページのスケルトンを描画し、ルーターはページのハイドレーション前に、マッチしたルートの読み込み中コンポーネントを読み込みます。`/`、`/app`、`/admin` は分割後も、専用のチャンクとしてすべてのスケルトンを読み込み、gzip 圧縮後で 3.5〜6.5 KiB 増えました。軽くなったのは、`/docs` や `/blog` のように、レイアウトが独自のスケルトンを持つページだけでした。
- 分割したスケルトンは、読み込まれるまで表示できません。ヘッドレス Chromium で 400 ms の遅延と 200 KiB/s を加えると、`/` から `/blog` へのクライアント側のナビゲーションでブログが表示されるまで 1,390 ms ではなく 2,290 ms かかり、その間、分割しないビルドでは一度も必要なかったスケルトンが表示されました。遅延が 150 ms の場合は 640 ms ではなく 800 ms でした。

すべてのページがすべてのスケルトンを読み込むため、スケルトンがインポートするのは `Skeleton`、shadcn のプリミティブ、他のスケルトン、長さを決める定数だけで、フォームは決してインポートしません。`PreferencesCardPending` は `preferences-card.tsx` からエクスポートされていたため、`/admin` と `/app` のスケルトンが、設定フォーム、TanStack Form、タイムゾーンの一覧、ユーザーのスキーマをすべてのページのエントリースクリプトに持ち込んでいました。現在は専用のファイル `preferences-card-pending.tsx` にあります。各ページが読み込むすべてのスクリプトの gzip 圧縮後のサイズ（`bun run build:test` の出力より）：

| ページ         | 変更前    | 変更後    |
| -------------- | --------- | --------- |
| `/`            | 463.0 KiB | 451.9 KiB |
| `/docs/<page>` | 553.6 KiB | 527.3 KiB |
| `/blog`        | 424.7 KiB | 413.6 KiB |
| `/app`         | 430.4 KiB | 404.1 KiB |
| `/admin`       | 452.9 KiB | 427.7 KiB |

`/` と `/blog` の削減量が小さいのは、レイアウトがニュースレターのフォームを描画しており、いずれにしても TanStack Form が必要だからです。`pending-imports.test.ts` はすべての `*-pending.tsx` のインポートをたどり、いずれかが `@tanstack/react-form` に到達するとテストを失敗させます。管理ダッシュボードのパネルと顧客向け概要のセクションは、エリアのリストで今もスケルトンとコンポーネントを組にしているため、それらのコンポーネントはスケルトンと一緒に読み込まれます。ライセンスの購入案内もそうしたセクションの 1 つなので、その購入ダイアログは、開いたときに同意フォーム `checkout-consent.tsx` を `lazy` で読み込みます。

## Tailwind のビルドは 1 つ

Tailwind を実行するのは `src/presentation/styles/globals.css` だけです。`docs.css` や `typeset.css` のようなルートのスタイルシートは素の CSS で、Fumadocs 自身のスタイルは `globals.css` を通して読み込みます。

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

以前、ルートのスタイルシートで 2 つ目の Tailwind ビルドを行った結果、独自の `.hidden`、`.rounded-md`、テーマ変数が出力されたことがあります。同じ名前のカスケードレイヤーはスタイルシートをまたいでマージされ、React は `precedence` 付きで挿入したスタイルシートを決して削除しません。そのため、ドキュメントを一度訪れると、ランディングページはリロードするまでレスポンシブなレイアウトとフォントを失いました。`e2e/specs/landing.spec.ts` の E2E テスト「landing keeps its responsive styles after visiting the docs」がこれを防いでいます。Tailwind が必要なものはすべて `globals.css` を通します。

## メディア

- **ランディングページのループ動画。** 各 `src/presentation/assets/motion/<name>.webm` には、動画とまったく同じ寸法のポスター `<name>.webp` があるため、ポスターから動画に切り替わるときに画像が目に見えて鮮明になることはありません。寸法は `src/data/landing-videos.ts` の `LANDING_VIDEO_SIZES` で、Remotion のコンポジションと `ConceptLoop` の両方がこれを読み取ります。より小さい幅は別ファイルの `<name>-<width>.webp` で、ポスターの `srcSet` を通して提供します。ポスターのサイズがそのコンポジションやファイル名の幅と異なると、`landing-videos.test.ts` が失敗します。フルサイズのポスターを縮小してはいけません。軽くしたい場合は、同じ寸法で再エンコードします。動画は `preload="none"` で読み込み、4 分の 1 が表示されている間だけ再生し、モーションを減らす設定の読者には決して再生しません。
- **コースツアー**（`course-showcase.tsx`）はループ動画ではありません。`<video>` は訪問者が再生を押してから初めてレンダリングされるため、それまでページが読み込むのはポスターだけです。ポスターは、動画と同じ 1600 ピクセル幅と 800 ピクセル幅の AVIF と WebP のソースを持つ `<picture>` です。動画そのものは WebM で配信し、MP4 をフォールバックにしています。
- **コースの動画**は、事前にアダプティブ HLS にエンコードし、Workers のキャッシュを使って R2 から配信します。[動画](/docs/features/videos)を参照してください。
- **スクロールに連動する動画。** 現在のサイトにはありません。再生位置がスクロール位置に追従する動画は、オールイントラ（すべてのフレームをキーフレームにする、`keyint=1`）でエンコードしなければなりません。通常のエンコードではシークに約 200 ms かかりますが、オールイントラでは約 3 ms です。200 ms かかるシークは、JavaScript でどれだけ滑らかにしてもスクラブ再生にはなりません。

## スクロールで表示する

`Reveal`（`src/presentation/components/custom/landing-page/components/reveal.tsx`）は、ランディングページのセクションがビューポートに入るとフェードインさせます。すべてのインスタンスで 1 つの `IntersectionObserver` を共有し、オブザーバーの最初のコールバックで要素がファーストビューより下から始まるかを判断し、React の状態も再レンダリングも使わずに `data-reveal` 属性を直接書き込みます。表示状態を React の状態に保持していたバージョンでは、すべてのセクションが再レンダリングされてページのレイアウトが 2 回行われたため、Total Blocking Time が 2 倍になりました。状態に戻してはいけません。また、比較せずに置き換えてもいけません。

ほかに 2 つの最適化を計測し、不採用にしました。ランディングページのセクションに `content-visibility: auto` を指定する方法は、ページ下部のセクションへのページ内リンクを壊しました。ニュースレターのフォームを遅延読み込みする方法は、直接描画する場合と同じか、より悪いスコアでした。

## 後から届く内容は大きさを保つ

プリレンダリングされたページはスクリプトが動く前に描画されるため、後から中身が入るセクションは、与えられた場所に収まらなければなりません。ランディングページのコースブロックがその一つです。スクロールで近づくと公開済みのコースを読み込みますが、以前のプレースホルダーは 6 レッスンのコースが 2 つあると見込んでいたため、コースが届くとブロックが伸び縮みし、その下のすべてを 100 ピクセル以上動かしていました。現在は各列が決まった数の 1 行の項目を持ち、プレースホルダーは同じ行を描き、メッセージは列と同じ大きさの枠に表示されるため、どの状態でもどの画面幅でも高さが同じです（[コース](/docs/features/courses) を参照）。ランディングページのスター数も、数字と同じ高さのスケルトンで同じようにしています。コースをプリレンダリングされた HTML に書き込むことはできません。ビルドには本番のデータベースがなく、リクエストのたびに Worker でランディングページをレンダリングすれば、プリレンダリングで短縮した最初の 1 バイトまでの時間を失うためです。
