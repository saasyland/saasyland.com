## Реалізовано

- **Сесії**: сесії Better Auth у D1, префікс cookie `saasyland`, захищені cookie поза локальними режимами, дозволені хости для кожного режиму та `cf-connecting-ip` як адреса клієнта. Клієнтська сесія ніколи не містить токена.
- **Облікові записи**: обов’язкове підтвердження пошти, відкликання сесій після скидання пароля, необов’язковий TOTP з резервними кодами, ідентифікатори підтвердження зберігаються як хеші, токени OAuth зашифровано.
- **Авторизація**: `requireSignedIn` і `requireAdmin` на маршрутах; `authorized(permission)` у серверних функціях із ролями, які `auth.access.ts` будує з файлів доступу розділів.
- **Обмеження запитів**: обмежувач Better Auth і middleware `withRateLimit` спільно використовують таблицю `rate_limit` у D1. `RATE_LIMITS.SENSITIVE` обмежує кількість викликів до <RepositoryFact name="sensitiveRateLimit" />, а `RATE_LIMITS.TOKEN` — до <RepositoryFact name="tokenRateLimit" /> у вікні тривалістю <RepositoryFact name="rateLimitWindowSeconds" unit="second" /> для кожного клієнта й дії. Кількість листів підтвердження адреси, скидання пароля й підтвердження розсилки також обмежено до <RepositoryFact name="recipientEmailsPerHour" /> кожного типу на адресу за годину (`withinRecipientRateLimit`, з ключем за хешем SHA-256 адреси); понад ліміт лист мовчки пропускається. [API ліцензій для CLI](/docs/features/cli-licence-api) рахує свої запити за адресою та за ліцензійним ключем у тій самій таблиці.
- **Помилки**: middleware запитів перетворює збої на коди `AppError` (`src/modules/_core/constants/errors.ts`), тож клієнти ніколи не отримують «сирих» повідомлень сервера; компоненти показують їх через `useErrorMessage`.
- **Вебхуки й форми**: вебхуки Polar перевіряються за допомогою `POLAR_WEBHOOK_SECRET`; підписка на розсилку (`subscribeToNewsletter`) приймається лише на хостах режиму збірки з `appHostsForMode`, через HTTPS або, у режимах розробки й тестування, через HTTP (`newsletterRequestOrigin`).
- **Вхідні дані Better Auth**: `enforceInputPolicy` в `auth.hooks.ts` застосовує схеми форм до кожного ендпоінта Better Auth, який приймає пароль, ім’я, адресу пошти чи зображення, тож запити, надіслані безпосередньо на `/api/auth`, дотримуються тих самих правил; запит, що не пройшов перевірку, отримує `400` з `VALIDATION_ERROR`.
- **Медіафайли**: відеофайли зберігаються в приватному бакеті R2. Worker віддає їх лише за шляхами `/media/`, підписаними ключем HMAC, виведеним з `AUTH_SECRET`; строк дії цих шляхів — щонайменше <RepositoryFact name="signedMediaHours" unit="hour" />. `getVideoPlayback` видає такі шляхи тим, хто має `video: ["read"]`; `getLessonPlayback` видає їх для опублікованого уроку, щойно `hasLessonAccess` допускає глядача, тож гості отримують їх для безкоштовних переглядів, користувачі, які увійшли, — для уроків для акаунтів, власники ліцензії Complete або Agency — для платних уроків, а адміністратори — для кожного уроку; неправильний або прострочений підпис отримує `403`.
- **Бандли шаблонів CLI**: бандл кожного випуску зберігається в приватному бакеті `BUNDLES`. API ліцензій для CLI підписує URL-адресу `/bundles/`, дійсну протягом <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, лише для активної ліцензії та активації пристрою, що надсилає запит, ключем HMAC, який HKDF виводить з `AUTH_SECRET` лише для бандлів; неправильний або прострочений підпис отримує `403`. Див. [API ліцензій для CLI](/docs/features/cli-licence-api#template-bundles).
- **Заголовки**: кожна відповідь від Worker має `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, `Permissions-Policy`, що вимикає камеру, мікрофон, геолокацію й topics, і Content Security Policy, яка забороняє вбудовування у фрейми, зміну `<base>` і плагіни (`base-uri 'none'`, `frame-ancestors 'none'`, `object-src 'none'`). HTTPS-відповіді додатково мають `Strict-Transport-Security`. Їх визначено один раз, як `SECURITY_HEADERS` і `HTTPS_SECURITY_HEADERS` у `src/modules/_core/constants/api.ts`, а `src/server.ts` задає їх для кожної відповіді Worker, замінюючи будь-яке значення, яке вже задала відповідь або правило з `public/_headers`. Файли, що віддаються без Worker (`/assets/*`, `/fonts/*`, `/robots.txt`, `/llms.txt`), отримують ті самі заголовки з правила `/*` у `public/_headers` — статичного файлу, який платформа читає ще до запуску будь-якого коду; `src/__test__/server.test.ts` завершується помилкою, коли це правило й константи розходяться.
- **Скрипти**: сторінка виконує лише ті скрипти, з якими її віддано. Її Content Security Policy відповідає strict CSP від Google: `script-src` з nonce або з хешами, `'strict-dynamic'`, щоб ці скрипти могли завантажити решту, як-от чанки маршрутів і піксель Affonso, і `'unsafe-inline' https:` як запасні варіанти, які браузери з підтримкою nonce і хешів ігнорують. Сторінка, яку рендерить Worker, отримує політику в заголовку: `src/server.ts` створює nonce для кожної відповіді, надсилає `renderedPagePolicy(nonce)` з `src/lib/content-security-policy.ts` і передає nonce в TanStack Start як `nonce` контексту запиту, який `getRouter` передає роутеру, тож nonce є на кожному скрипті, який рендерять роутер, React і `ThemeScript`. Попередньо відрендерена сторінка — це той самий файл для кожного відвідувача, і вона не може мати nonce, тому `scripts/secure-prerendered-html.ts` запускається після `optimize-prerendered-html.ts` у кожній збірці: `securePrerenderedPage` у `src/lib/prerendered-policy.ts` завантажує вхідний модуль з невеликого вбудованого скрипта замість `<script src>`, обчислює хеш кожного вбудованого скрипта й записує політику в тег `<meta http-equiv="Content-Security-Policy">` одразу після charset. Заборона вбудовування у фрейми залишається в заголовку, бо браузери ігнорують `frame-ancestors` у метатегу. Браузер запускає zod у режимі `jitless` (`src/integrations/zod/zod.config.ts`, що лежить у власному чанку zod), тож zod ніколи не перевіряє, чи доступний `eval`. Сервер розробки надсилає лише політику в заголовку, бо вбудовані скрипти Vite не мають nonce; браузерний набір запускає продакшн-збірку й завершує помилкою кожну специфікацію, у якій сторінка повідомляє про порушення.

## Не реалізовано

- Директиви Content Security Policy для стилів, зображень, медіа, шрифтів і з’єднань, Trusted Types і звіти про порушення: політика обмежує скрипти, плагіни, базові URL-адреси та вбудовування у фрейми.
- Журнал аудиту, зокрема для блокувань, видалень і входу від імені інших користувачів.
- Захист від ботів або CAPTCHA в публічних формах.
