---

Vite+ は Vitest（`vp test`）を 3 つのプロジェクトで実行します。テストは対象のコードの隣にある `__test__` フォルダーに置き、API は `vite-plus/test` からインポートします。

| プロジェクト  | ファイル                         | 環境  |
| ------------- | -------------------------------- | ----- |
| `node`        | `__test__/*.test.ts(x)`          | Node  |
| `integration` | `__test__/*.integration.test.ts` | Node  |
| `component`   | `__test__/*.component.test.tsx`  | jsdom |

テストには、ソースファイルに合わせた名前を付けます。`category.zod.ts` は `__test__/category.zod.test.ts` でカバーします。

## コマンド

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
```

`bun test` ではなく `bun run test` を使ってください。プロジェクト、環境、セットアップファイルを読み込むのは Vitest だけです。

## カバレッジゲート

`bun run test:coverage` は、`src` 配下のアプリケーションコードについて、行、ステートメント、関数、分岐のいずれかが **100%** を下回ると失敗します。テスト、`src/platform/testing`、shadcn のプリミティブ、生成されたファイルは除外されます。実際の振る舞いをカバーし、決して実行されない分岐は、グローバルをスタブして到達させるのではなく削除してください。レポートは `coverage/` に出力されます。

## テストランタイム

- `src/platform/testing/setup.ts` は、jest-dom のマッチャーを登録し、各テストの前にバインディングをリセットし、すべての `createServerFn` を `withTestRpc` 経由で実行します。そのため、呼び出しは実際のミドルウェアとバリデーターを通ります。これは `node` と `integration` プロジェクトでの動作です。`component` プロジェクトでは jsdom がブラウザにあたるため、サーバー関数は失敗します。
- `cloudflare:workers` は `src/platform/testing/mocks/cloudflare.ts` に解決されます。D1 はチェックイン済みのすべてのマイグレーションを適用したインメモリの SQLite データベース、KV と `MEDIA` の R2 バケットはインメモリのマップで、`flushWaitUntil()` はバックグラウンドタスクの完了を待ちます。`mocks/cache.ts` の `createEdgeCache()` は Workers のキャッシュをスタブします。
- `.env.test` はダミーの認証情報を提供します。`fetch` は Resend と Polar の厳密なテストダブル（`mocks/resend.ts`、`mocks/polar.ts`）に届き、それ以外のホストへのリクエストはマシンがオフラインであるかのように失敗するため、マシンの外には何も送信されません。プロバイダーが拒否するリクエストは、テストを失敗させます。
- `src/platform/testing/lib/render.tsx` の `renderWithRouter` は、実際のルーターと `QueryClient` を使ってコンポーネントをレンダリングします。

## ユースケースをテストする

`src/modules/category/use-cases/__test__/create-category.test.ts` から抜粋したものです。

```ts
import { describe, expect, it, vi } from "vite-plus/test"

import { executeMutation } from "~/src/platform/testing/lib/query"

import { createAuthSessionFixture } from "~/src/integrations/better-auth/__test__/fixtures/auth.session.fixture"
import { ROLE_CODES } from "~/src/integrations/better-auth/auth.access"
import type { auth } from "~/src/integrations/better-auth/auth.server"
import * as authServer from "~/src/integrations/better-auth/auth.server"

import { ERROR_CODES } from "~/src/modules/_core/constants/errors"
import { CATEGORY_KIND } from "~/src/modules/category/category.constants"
import { createCategoryMutation } from "~/src/modules/category/use-cases/create-category"

const getSessionMock = vi.hoisted(() => vi.fn<(typeof auth.api)["getSession"]>())

vi.mock(import("@tanstack/react-start/server-only"), () => ({}))

describe("create-category", () => {
  it("returns a domain error when the caller is not an admin", async () => {
    vi.spyOn(authServer.auth.api, "getSession").mockImplementation(getSessionMock)
    getSessionMock.mockResolvedValue(
      createAuthSessionFixture({ role: ROLE_CODES.CUSTOMER, userId: "01900000-0000-7000-8000-000000000001" }),
    )

    await expect(executeMutation(createCategoryMutation, { kind: CATEGORY_KIND.CATEGORY, name: "SaaS Plans" })).rejects.toThrow(
      ERROR_CODES.FORBIDDEN,
    )
  })
})
```

ユースケースのすべての結果をテストします。成功、それぞれの `AppError` コード、セッションがない場合、権限がない場合です。ドメイン値とエラーコードは、文字列を繰り返し書かず、定数（`CATEGORY_KIND`、`ERROR_CODES`）から取得します。

## Resend と Polar を相手にテストする

Resend や Polar の SDK はモックしないでください。リクエストを送信するコードを呼び出し、テストダブルが受け取った内容をアサートします。`mocks/resend.ts` の `getSentEmails(recipient)` は、配信されたメールを、レンダリングされた HTML と冪等性キーとともに返します。`mocks/polar.ts` は購入セッション、注文、ライセンスキーを保持し、その関数が購入を先に進めます。`payPolarCheckout`、`grantPolarLicenseKey`、`refundPolarOrder`、`revokePolarLicenseKey`、`activatePolarLicenseKey` です。`src/modules/license/__test__/license-purchase.integration.test.ts` から抜粋したものです。

```ts
const buyer = await signUpAndVerify()
const order = await paidOrder(buyer, LICENSE_TIER.COMPLETE)

expect(await deliver(POLAR_WEBHOOK_EVENT.ORDER_PAID, order)).toBe(HTTP_STATUS.OK)
expect(await currentLicense(buyer)).toMatchObject({ status: LICENSE_STATUS.ACTIVE, tier: LICENSE_TIER.COMPLETE })
```

`paidOrder` は本物の `startCheckout` で購入セッションを開始し、テストダブルの中で支払いを済ませます。`deliver` は `lib/polar.ts` の `signedPolarWebhook` でイベントに署名し、Better Auth の Polar エンドポイントに POST して、レスポンスのステータスを返します。そのため、署名の検証、プラグイン、`license.webhooks.ts` のハンドラーがすべて実行されます。プロバイダーの障害をアプリがどう扱うかをテストするには、`resend.utils.test.ts` と同じように、1 つのリクエストだけにプロバイダーのエラーで応答します（`vi.spyOn(globalThis, "fetch").mockResolvedValueOnce(Response.json(error, { status }))`）。

## 認証フローをテストする

認証のスイートは、`auth.server.ts` の本物の `auth` に対して実行されます。`src/integrations/better-auth/__test__/fixtures/auth.harness.ts` は、訪問者と同じ手順でアカウントを作成します。`signUp`、`verifyEmail`（配信されたメール内のトークンをたどり、それによって開始されたセッションを返します）、`signIn`、`signUpAndVerify` です。`browserHeaders()` はリクエストごとに専用の `CF-Connecting-IP` を付けるため、あるテストが別のテストの許容回数を使い切ることなく、本番環境と同じように Better Auth のレート制限が適用されます。Better Auth がバックグラウンドで送信するメールを読む前に、`flushWaitUntil()` を await してください。

## コンポーネントをテストする

コンポーネントのテストは、`messages/en-US` の実際のメッセージを使ってレンダリングし、ミューテーションオプションを提供するユースケースのモジュールをモックして、Testing Library と `userEvent` で UI を操作します。処理中の状態をテストするには、`Promise.withResolvers()` でモックしたリクエストを保留したままにして処理中の UI をアサートし、その後 `act` 内で解決してアイドル状態の UI をアサートします。時間をおいて変化するコンポーネントは、実際の時間を待つのではなく、フェイクタイマー（`vi.useFakeTimers()` のあと、`act` 内で `vi.advanceTimersByTimeAsync`）でテストします。また、ルートのテストの `QueryClient` はローダーが取得したデータを新鮮な状態に保つ（`staleTime: Infinity`）ため、マシンのレンダリング速度によってクエリの実行回数が変わることはありません。`userEvent.setup({ delay: null })` は、キー入力の間に実際のタイマーを挟まずに UI を操作します。完全な例は `src/presentation/components/custom/__test__/newsletter-form.component.test.tsx` です。ルートのテストではルートにローダーデータを渡し、ローダー自体は `node` テストで `getRouter()` を通して検証します。`src/routes/__test__/marketing-routes.component.test.tsx` と `marketing-loaders.test.ts` がその両側の例です。

## ブラウザテスト

Playwright のスペックは `e2e/specs` に、ページオブジェクトは `e2e/pages` に、フィクスチャは `e2e/fixtures` にあります。これらは、`.wrangler/test` にあるローカルの D1、KV、R2、そして `e2e/data/accounts.ts` のシード済みアカウントを使い、ビルド済みのテスト用アプリケーションに対して実行されます。ローカルでは、Playwright がそのアプリケーションのマイグレーション、シード、ビルド、起動を自ら行います。

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:ui
```

テスト用の Worker は同じ Resend と Polar のテストダブルをインストールし、送信されたメールを記録するため、スペックは `/__test/emails?to=<address>` から認証リンクを読み取れます。`e2e/fixtures/polar.ts` の `deliverPaidOrder` は、統合テストのスイートのイベントと同じように署名した、完全な `order.paid` イベントを POST します。

## プッシュする前に

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`build:test` はユニットテストでは検証されない Cloudflare の完全なビルドを実行し、`test:e2e:pr` はプルリクエストの CI と同じく、すべてのスペックを Chromium で実行します。

CI は、すべてのプルリクエストと `main` へのプッシュでチェック、カバレッジ、Chromium のブラウザスイートを実行し、WebKit のスイートは毎週と `main` へのプッシュ時に実行します。
