description: "The MEDIA and BUNDLES buckets: private storage for videos, lesson materials and course covers, and the CLI's template bundles, all served by the Worker."

Every environment binds an R2 bucket as `MEDIA` in `wrangler.jsonc`: `saasyland` in production, `saasyland-preview` for preview, a local `saasyland-local` bucket for `bun run dev` and a local `saasyland-test` bucket for the test build. The buckets are private: public access and the `r2.dev` URL stay off, and every read goes through the Worker. The licence area binds a second bucket, `BUNDLES`, for the CLI's template bundles (see [Template bundles](#template-bundles)).

## Object layout

Each video's files sit under `videos/<videoId>/`, where `videoId` is the `video` row's id. `videoObjectKey` and `videoDirectory` in `src/modules/video/video.files.ts` build the keys, and `mediaContentType` lists the only file names that may be uploaded or served, with their media types. Anything else is refused.

Each uploaded lesson material sits under `attachments/<attachmentId>/<fileName>`, where `attachmentId` is the `lesson_attachment` row's id and `fileName` is the uploaded name reduced to letters, digits, dots, hyphens and underscores. `attachmentObjectKey` and `attachmentContentType` in `src/modules/lesson-attachment/lesson-attachment.files.ts` build the key and give the media type of the <RepositoryFact name="attachmentFileTypes" /> extensions that may be uploaded or served.

Each course cover sits under `covers/<courseId>/<coverId>.<extension>` at full size, with each smaller size beside it as `<coverId>-<width>.<extension>`. `coverObjectKey` and `coverVariantKey` in `src/modules/course/course.cover.ts` build the keys, and `coverContentType` gives the media type of a stored cover, WebP or JPEG.

## Signed delivery

The player never sees a bucket key. A server function calls `createPlayback` (`src/modules/video/video.playback.ts`), which returns paths of the form:

```text
/media/<expiry>.<signature>/<videoId>/master.m3u8
```

- `expiry` is a Unix time in base 36, at least <RepositoryFact name="signedMediaHours" unit="hour" /> ahead and rounded up to the hour, so links issued within the same hour are identical and stay cacheable in the browser.
- `signature` is an HMAC-SHA-256 of `<videoId>.<expiry>` with a key derived from `AUTH_SECRET` by HKDF, so no extra secret is needed and the key is used for nothing else.
- Playlists refer to renditions, segments and captions by relative paths, so one signed prefix covers the whole stream.

`src/server.ts` sends every `/media/` request to one of the courses' entries of `REQUEST_HANDLERS` before the locale middleware and TanStack Start, and adds the usual security headers. They load `serveCover` for `/media/covers/`, `serveAttachment` for `/media/downloads/` and `serveMedia` (`src/modules/video/video.delivery.ts`) for every other path, each with a dynamic `import()`. `serveMedia`:

- accepts only `GET` and `HEAD` (`405` otherwise);
- returns `404` for a path that is not a listed media file and `403` for an expired or wrong signature;
- answers `Range` requests with `206` and `Content-Range`, and `416` for a range outside the file;
- serves whole files from the Workers cache when it can. Files are stored there under `/media/_/<videoId>/<file>`, without the signature, so every viewer shares one cached copy per edge location. Responses to the browser are `private, max-age=86400, immutable`.

Signed paths work as bearer links until they expire: anyone holding one can play that video. Checking who may watch happens when the path is issued.

Lesson materials use the same scheme under `/media/downloads/<expiry>.<signature>/<attachmentId>/<fileName>`, with a key of their own and a lifetime of at least <RepositoryFact name="signedDownloadHours" unit="hour" />. `getLesson` signs them only for a viewer who may open the lesson. `serveAttachment` (`src/modules/lesson-attachment/lesson-attachment.delivery.ts`) receives the requests under `/media/downloads/` from the `/media/` handler in place of `serveMedia`, accepts only `GET` and `HEAD`, answers `403` for an expired or wrong signature and `404` for a file that is not there, and serves the file with `Content-Disposition: attachment` and `Cache-Control: private, no-store`.

Course covers are public and unsigned, under `/media/covers/<courseId>/<file>`, because the catalogue, the course pages and the landing page show them to every visitor. `serveCover` (`src/modules/course/course.delivery.ts`) accepts only `GET` and `HEAD` (`405` otherwise), answers `404` for a path that names no cover and for a file that is not there, serves the cover with `Cache-Control: public, max-age=31536000, immutable` and keeps a copy in the Workers cache `covers`. Every new cover gets a new id, so no cached copy goes stale; see [Course covers](/docs/features/courses#course-covers).

The business logo is public and unsigned too, under `/media/logos/<file>`: the R2 key is `logos/<logoId>.<extension>`, built by `logoObjectKey` in `src/modules/business-profile/business-profile.logo.ts`, and `logoContentType` gives its media type, WebP or PNG. `serveBusinessLogo` serves it with the same rules and keeps a copy in the Workers cache `logos`; `src/server.ts` lists its handler before the courses' ones, so `/media/logos/` never reaches them. See [Settings](/docs/features/settings#business-profile).

## Uploads

The Worker does not accept video uploads. `scripts/publish-video.ts` writes to the bucket with `wrangler r2 bulk put --remote`, using your `bunx wrangler login`; see [Videos](/docs/features/videos). Deleting a video from the admin lists the prefix and deletes the objects page by page through the binding.

Lesson materials and course covers are the two uploads the Worker accepts. `uploadLessonAttachment` takes a file of up to <RepositoryFact name="attachmentMaxMegabytes" /> MB from an admin and writes it through the binding. Deleting a material, or the lesson, chapter or course it belongs to, deletes its object; see [Courses](/docs/features/courses#materials). `uploadCourseCover` takes the sizes of a cover from an admin, each of up to <RepositoryFact name="courseCoverMaxMegabytes" /> MB, and replacing or removing the cover, or deleting the course, deletes its files.

## Template bundles

Every environment binds the licence area's `BUNDLES` bucket as well:

<RepositoryTable columns={["Environment", "Bucket"]} name="cliBundleBuckets" />

It holds one object per release of the CLI, the release's template bundle under <RepositoryFact name="cliBundleKey" />, which the CLI repository's release uploads with the SHA-256 of its content as the custom metadata <RepositoryFact name="cliBundleDigestMetadata" />; the Worker never writes to it, and reads that digest with `head()` instead of the archive. The [CLI licence API](/docs/features/cli-licence-api#template-bundles) signs <RepositoryFact name="cliBundleUrlPath" /> URLs the way `/media/` paths are signed, with a key of its own and a lifetime of <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, and `serveBundle` (`src/modules/license/license.delivery.ts`) streams the object without caching it. [Publishing bundles](/docs/features/cli-licence-api#publishing-bundles) lists the key, the content type and the buckets a release uploads to.

## Tests

In Vitest, `cloudflare:workers` resolves to `src/platform/testing/mocks/cloudflare.ts`, which provides an in-memory bucket for each R2 binding of the `test` environment, `MEDIA` and `BUNDLES`, with `get` (including ranges), `head`, `put` of text, bytes or a file with custom metadata, `delete` and paged `list`. `src/platform/testing/mocks/cache.ts` stubs the Workers cache. The test build uses the local `saasyland-test` and `saasyland-bundles-test` buckets under `.wrangler/test`.
