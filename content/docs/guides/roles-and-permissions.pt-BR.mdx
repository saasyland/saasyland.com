O controle de acesso usa o plugin admin do Better Auth. `src/integrations/better-auth/auth.access.ts` define as declarações de permissão de cada recurso em `APP_STATEMENTS`, as concede aos papéis e monta a partir delas o controle de acesso do Better Auth e a verificação de permissão, em um único arquivo que uma pessoa revisa. Os códigos de papel ficam em `src/integrations/better-auth/auth.roles.ts`.

## Declarações e papéis

```ts title="src/integrations/better-auth/auth.access.ts"
export const APP_STATEMENTS = {
  admin: ["access"],
  category: ["create", "read", "update", "delete"],
  course: ["create", "read", "update", "delete"],
  order: ["read", "update", "refund"],
  product: ["create", "read", "update", "delete", "publish"],
  settings: ["manage"],
  video: ["read", "delete"],
} as const

export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...APP_STATEMENTS, ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole({}),
}
```

- `APP_STATEMENTS` lista uma declaração por recurso, em ordem de recurso: `admin` e `settings` para o console de administração e as suas configurações, `category` e `product` para os produtos, `course` e `video` para os cursos, e `order` para os pedidos.
- Os `defaultStatements` do Better Auth adicionam os recursos `user` e `session` (como `user: ["list", "set-role", "ban", "impersonate", "delete"]` e `session: ["list", "revoke"]`).
- `admin` recebe todas as declarações e as declarações de administração do Better Auth; `customer`, o papel padrão de novos usuários, não recebe nenhuma.
- Uma funcionalidade que um projeto deixa de fora leva junto as suas declarações: `scripts/features.ts` as nomeia, como `APP_STATEMENTS.course`, e a regra de poda as apaga do objeto ([Testes](/docs/conventions/testing#tests-follow-the-features)).
- `ROLE_VALUES` tipa a coluna `user.role` e os schemas de papel em `user.zod.ts`.
- `Permission`, o tipo que `authorized` e `hasPermission` recebem, é montado a partir de `APP_STATEMENTS`, então uma declaração ou ação que ele não declara não compila.

## Onde as permissões são verificadas

| Camada                  | Verificação                                                        |
| ----------------------- | ------------------------------------------------------------------ |
| Guard de rota           | `requireAdmin` exige `admin: ["access"]` para toda a área `/admin` |
| Função de servidor      | `authorized({ product: ["update"] })` em toda operação protegida   |
| Apenas logado           | `authorized()` para operações sobre os dados de quem chama         |
| Em qualquer outro lugar | `hasPermission({ permission, role })` retorna um booleano          |

O guard de rota só decide quais páginas são renderizadas. As funções de servidor podem ser chamadas diretamente por RPC, então cada uma precisa verificar sua própria permissão. Esconder um botão é apresentação, não autorização.

## Adicione uma permissão

1. Adicione a ação à declaração do recurso em `APP_STATEMENTS`, ou adicione o recurso na posição que lhe cabe na ordem, por exemplo `report: ["read", "export"]`. Uma funcionalidade que pode ficar de fora nomeia um recurso novo nos seus `names` em `scripts/features.ts`, como `APP_STATEMENTS.report`.
2. Conceda-a em `ROLES`: `admin` recebe todo o `APP_STATEMENTS`, e um papel que deve receber menos ganha um subconjunto.
3. Exija-a na função de servidor: `.middleware([authorized({ report: ["export"] })])`.
4. Teste tanto o caso permitido quanto o caso `FORBIDDEN`, em `src/integrations/better-auth/__test__/auth.access.<feature>.test.ts` e nos testes do caso de uso.

## Adicione um papel

1. Adicione o código a `ROLE_CODES` e `ROLE_VALUES` em `auth.roles.ts`.
2. Adicione-o a `ROLES` em `auth.access.ts` com as declarações que ele pode usar.
3. Adicione o rótulo do papel a `filters.role.options` em `messages/<locale>/pages.admin.users.json` em todos os idiomas.

O cliente de autenticação (`auth.client.ts`) recebe `ac` e `ROLES`, então as ações de administração no navegador usam as mesmas definições.

## Administração de usuários e sessões

Os módulos de usuários e de sessões envolvem a API de administração do Better Auth em casos de uso, cada um com sua própria permissão: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` e outros. Operações sobre os dados de quem chama, como `revokeSession`, usam `authorized()` e filtram por `context.auth.user.id`.

Localmente, `bun run db:seed:local` cria um administrador. No preview e na produção, o primeiro administrador é criado por `bun run admin:grant:preview <email>` ou `bun run admin:grant:production <email>`, que só quem tem acesso de escrita a esse banco de dados D1 pode executar, para uma conta que já verificou o e-mail; os administradores seguintes são criados em **Administração → Gerenciamento de usuários** com **Alterar função**. Veja [O primeiro administrador](/docs/tooling/database#the-first-admin). Um administrador existente também pode convidar um novo endereço com o papel `admin`; veja [Convites](/docs/features/users-admin#invitations).
