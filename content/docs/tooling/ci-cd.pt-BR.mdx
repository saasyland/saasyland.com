Os workflows ficam em `.github/workflows/`. Os workflows da aplicação (`ci.yml`, `e2e-reusable.yml` e `deploy-reusable.yml`) preparam a toolchain com a action composta `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ com a versão do Node em `.nvmrc`, um cache do Bun, `bun install --frozen-lockfile --ignore-scripts` e `bun run typegen`. Já o `remotion.yml` prepara o Node de `.nvmrc` e o npm.

| Workflow              | Gatilho                                                                                    | Jobs                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests e pushes para `main`                                                         | Verificações e cobertura, E2E no Chromium e, depois, deploy de preview, ou de produção com release |
| `e2e-full.yml`        | Pushes para `main`, o agendamento <RepositoryFact name="e2eFullSchedule" /> em UTC, manual | WebKit no push; Chromium e WebKit nas execuções agendadas e manuais                                |
| `e2e-reusable.yml`    | Chamado pelos workflows acima                                                              | Banco de dados de testes, build de testes e um projeto do Playwright                               |
| `deploy-reusable.yml` | Chamado por `ci.yml`                                                                       | Build, migrações do D1 e `wrangler deploy`                                                         |
| `remotion.yml`        | Alterações em `remotion/` ou nos arquivos do site que ele importa                          | Verifica e empacota com npm o projeto do vídeo da landing page                                     |

`remotion.yml` é acionado pelos mesmos caminhos em pull requests e pushes: `remotion/`, o próprio workflow e os arquivos do site que `remotion/src` importa, diretamente ou por meio de outros arquivos do site. `src/__test__/workflows.test.ts` segue essas importações e falha quando um arquivo alcançado não corresponde a nenhum dos caminhos ou quando um caminho não corresponde a nenhum dos arquivos.

Os checkouts que fazem o build do site, em `e2e-reusable.yml` e `deploy-reusable.yml`, e o do job `release` buscam todos os commits sem as suas árvores (`fetch-depth: 0` e `filter: tree:0`): o [changelog](/docs/project/changelog) data cada entrada pelo commit que a levou à `main`. Em relação a um clone raso, só os próprios commits são acrescentados; com um clone raso o build falharia em vez de datar as entradas errado. `src/__test__/workflows.test.ts` falha quando um desses checkouts deixa de buscar o histórico.

## Verificações

O job `verify` em `ci.yml` executa `bun run check` (tabelas de nomes de classes, verificações de i18n e de conteúdo, o [inventário de fluxos](/docs/tooling/test-coverage#flow-coverage), formatação, lint e tipos) e `bun run test:coverage` e, em seguida, envia o relatório de cobertura. O job `e2e` executa `db:reset:test` e `build:test`, instala o navegador e executa `bunx playwright test e2e/specs --project=chromium`. Execuções de E2E com falha enviam o relatório do Playwright.

Em um pull request, `bun run check` também falha até que o pull request adicione a sua [entrada do changelog](/docs/conventions/git-workflow#changelog-entries).

## Deploys

Os deploys só são executados depois que `verify` e `e2e` passam:

| Evento                                       | Destino      | Ambiente do GitHub | URL                           |
| -------------------------------------------- | ------------ | ------------------ | ----------------------------- |
| Pull request de uma branch deste repositório | `preview`    | `Preview`          | https://preview.saasyland.com |
| Push para `main`                             | `production` | `Production`       | https://saasyland.com         |

`deploy-reusable.yml` atribui a cada ambiente do GitHub a sua URL, e `src/__test__/workflows.test.ts` falha quando uma delas difere do host do ambiente em `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Pull requests de forks e do Dependabot são validados, mas não recebem deploy. O preview é compartilhado: cada deploy substitui o anterior e usa o mesmo banco de dados D1, o mesmo namespace KV e os mesmos buckets R2 de preview.

`deploy-reusable.yml` verifica a existência dos secrets `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID`, executa `scripts/verify-bindings.ts`, faz o build com os valores fictícios de `.env.test`, remove o `dist/server/.dev.vars` gerado, aplica `db:migrate:<target>` e executa `vp exec wrangler deploy --config dist/server/wrangler.json`. Não executa `scripts/verify-deployment.ts`, a verificação do site no ar dos scripts `deploy:<target>`, porque a proteção contra bots da Cloudflare responde 403 às requisições dos runners de CI. Também não executa `scripts/run-deploy-checks.ts`, então a CI não executa nenhuma das verificações de deploy que as áreas declaram em `DEPLOY_CHECKS`: não há `.env.<target>` na CI, e os ambientes do GitHub guardam só as credenciais da Cloudflare. Hoje são `auth:verify`, da área de autenticação, e `polar:verify`, da área do Polar; execute localmente `bun run auth:verify:<target>` depois de alterar um cliente OAuth e `bun run polar:verify:<target>` depois de cada alteração no Polar ([Configuração do Polar](/docs/getting-started/polar-setup)). Nenhum arquivo de secrets é enviado: o Worker mantém os secrets de runtime já configurados na Cloudflare. Deploys para o mesmo destino entram em fila em vez de cancelarem uns aos outros.

O Dependabot atualiza as GitHub Actions semanalmente.

## Releases e tags [#releases-and-tags]

O site recebe deploys contínuos, então suas versões são datas, não versões semânticas. Quando um deploy de produção termina com sucesso, o job `release` do `ci.yml` marca o commit implantado com a tag `vYYYY.MM.DD` na data UTC e publica uma GitHub Release para ele. Um segundo deploy de produção no mesmo dia recebe a tag `vYYYY.MM.DD.2`, o seguinte `.3`, e assim por diante. Deploys de preview nunca recebem tag. O job `release` é o único com `contents: write`.

As notas da release são as entradas do [changelog](/docs/project/changelog) que chegaram à `main` naquele dia, então cada mudança é descrita em um só lugar; quando nenhuma chegou, as notas apontam para o changelog. `scripts/publish-release.ts` escolhe a tag e as notas com `src/lib/release.ts` e executa `gh release create`. Uma nova execução mantém a tag que o commit já tem e pula uma release que já existe.

Para voltar a produção a uma release, reverta em um pull request tudo o que veio depois da tag dela:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

O merge faz o deploy do código da tag após as verificações de sempre e o marca como uma nova release. As migrações do D1 não são revertidas, então o código mais antigo roda sobre o esquema mais novo. Toda mudança de esquema precisa funcionar com a aplicação implantada antes dela, o que torna isso seguro para a release anterior; leia as migrações intermediárias antes de voltar mais.
