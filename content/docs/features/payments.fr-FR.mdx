Les paiements passent par Polar avec le plugin `@polar-sh/better-auth`, que la zone Polar ajoute à Better Auth dans `src/data/polar.auth-plugins.ts` :

```ts
export const POLAR_AUTH_PLUGINS = [
  {
    plugin: polar({
      client: polarCore,
      use: [portal(), webhooks({ onPayload: handlePolarEvent, secret: env.POLAR_WEBHOOK_SECRET })],
    }),
    rateLimitExemptPaths: [ROUTES.API_AUTH_POLAR.WEBHOOKS],
  },
] as const satisfies readonly AuthPluginEntry[]
```

Le plugin ajoute le portail client et les webhooks, exemptés du limiteur de débit de Better Auth, mais aucun paiement : son `checkout()` créerait un paiement avec le seul identifiant du compte, si bien que Polar redemanderait son e-mail à un acheteur connecté. Better Auth ne ferme aucun chemin en HTTP : `src/data/__test__/polar.auth-plugins.integration.test.ts` vérifie donc que le chemin de paiement du plugin répond 404, et échoue dès que `checkout()` est ajouté au plugin. Une zone qui vend crée ses paiements avec le SDK Polar après ses propres vérifications, comme le fait `startCheckout` dans la zone des licences (voir [Licences](/docs/features/licences)).

`src/integrations/polar/polar.config.ts` crée `polarCore` à partir de `POLAR_ACCESS_TOKEN` et `POLAR_SERVER`, que le plugin utilise, ainsi que `polar`, les services de paiements, de remises, de clés de licence et de commandes construits dessus. `POLAR_ORGANIZATION_ID` restreint à l’organisation chaque appel à Polar qui nomme une organisation ; [Environnement et bindings](/docs/reference/environment) les énumère. `src/integrations/polar/polar.constants.ts` contient les valeurs propres à Polar, `POLAR_ORDER_STATUS`, `POLAR_LICENSE_KEY_STATUS`, `POLAR_WEBHOOK_EVENT` et `POLAR_CHECKOUT_ID_PLACEHOLDER`, chacune vérifiée par rapport aux types du SDK ; il ne lit aucun environnement, si bien que le navigateur et la suite du navigateur l’importent aussi. Les chemins de la zone Polar, `API_AUTH_POLAR` et `API_AUTH_CUSTOMER_PORTAL`, se trouvent dans `src/data/polar.routes.ts`. [Configurer Polar](/docs/getting-started/polar-setup) décrit les produits, les clés de licence, les remises, le webhook et le jeton que ce code attend dans Polar, et `bun run polar:verify:<environment>` les vérifie.

## Webhooks [#webhooks]

Polar envoie ses événements à `/api/auth/polar/webhooks`. Le plugin vérifie leur signature avec `POLAR_WEBHOOK_SECRET` et transmet chaque événement à `handlePolarEvent` dans `src/data/polar-events.ts`. Une zone qui réagit aux événements Polar déclare une liste dans `src/data/<area>.polar-events.ts` et l’ajoute à `src/data/polar-events.entries.ts`. Chaque entrée nomme les événements qu’elle traite et la fonction qui les traite :

```ts
export interface PolarEventHandler {
  readonly events: readonly models.WebhookEventType[]
  readonly handle: (event: webhooks.WebhookPayload) => Promise<void>
}
```

- `handlePolarEvent` exécute en même temps le `handle` de chaque entrée qui liste le type de l’événement, et attend qu’ils aient tous terminé.
- Lorsque l’un d’eux échoue, le plugin répond 500 et Polar renvoie l’événement plus tard : chaque handler doit donc pouvoir s’exécuter deux fois pour le même événement sans conséquence. Polar désactive un point de terminaison qui continue d’échouer, et `polar:verify` signale un point de terminaison désactivé.
- Un événement qu’aucune entrée ne liste est acquitté et ne va nulle part.
- `POLAR_EVENTS` réunit les événements de toutes les entrées, triés et chacun une seule fois. Le point de terminaison du webhook dans Polar doit envoyer exactement ceux-là, et `polar:verify` les compare.
- La zone Polar ajoute une liste vide dans `src/data/polar.polar-events.ts`, si bien que le barrel n’est jamais vide. Aujourd’hui, seule la zone des licences traite des événements, dans `src/data/license.polar-events.ts` ; voir [Licences](/docs/features/licences#webhooks-and-licences).

`polar:verify` s’exécute dans Bun, hors du Worker, et lit `POLAR_EVENTS` : `src/data/polar-events.ts` et chaque `<area>.polar-events.ts` n’importent donc aucun code serveur. Le `handle` d’une zone charge ses handlers à l’arrivée d’un événement :

```ts
const { licenseWebhookHandlers } = await import("~/src/modules/license/license.webhooks")
```

`src/data/__test__/polar-events.test.ts` importe `src/data/polar-events.ts` dans Bun et échoue lorsque cet import atteint le runtime du Worker.

## Portail client

`ROUTES.API_AUTH_CUSTOMER_PORTAL` (`/api/auth/customer/portal`) ouvre le portail client Polar du compte connecté. La carte de licence de `/app/license` y renvoie.

## Écran d’administration (démo)

`/admin/payments` affiche `RefundStats` et un `DataTable` de remboursements sur `ADMIN_PAYMENT_ROWS` de `src/data/admin-payments.ts` ; ses boutons ne sont pas branchés. La zone des paiements définit les déclarations de permission `order` (`read`, `update`, `refund`) dans `src/data/payments.access.ts`, mais aucun cas d’usage ne lit de commandes ni de remboursements.
