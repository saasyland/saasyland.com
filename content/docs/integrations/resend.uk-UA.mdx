`src/integrations/resend/resend.config.ts` створює клієнт Resend з `RESEND_API_KEY`. `resend.utils.ts` експортує `sendEmail` — єдину функцію, яка надсилає листи. `from` типово дорівнює `RESEND_EMAIL_FROM`, обов'язкова опція `idempotency` вказує призначення листа й токен, що його ініціював, а `sendEmail` перетворює їх на ключ `<purpose>/<SHA-256 токена>`, який не дає Resend надіслати повторений запит двічі й не перевищує ліміт Resend у 256 символів, а помилка Resend викидається як виняток. Обидва файли призначені лише для сервера. `resend.constants.ts` дає назву кожному призначенню в `EMAIL_PURPOSE`, а сценарії використання передають ту саму назву як `kind` ліміту на одержувача.

## Шаблони та сценарії використання

Шаблони в `src/presentation/emails/` — це компоненти React Email, що містять лише розмітку. Кожен експортує константу `*_NAMESPACE`, отримує `locale` і `messages` як пропси та перекладає за допомогою `createTranslator` з use-intl. Сценарій використання, який надсилає лист, отримує локаль від свого викликача (лист підтвердження читає її з callback-URL), завантажує повідомлення, рендерить шаблон і викликає `sendEmail`:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await sendEmail({
  idempotency: { purpose: EMAIL_PURPOSE.VERIFY_EMAIL, token },
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

| Шаблон                                | Простір імен                             | Надсилає                                                                     |
| ------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------- |
| `verify-email.tsx`                    | `emails.verify-email`                    | `modules/verification/use-cases/send-verify-email.ts`                        |
| `reset-password-email.tsx`            | `emails.reset-password-email`            | `modules/verification/use-cases/send-reset-password-email.ts`                |
| `change-email-confirmation-email.tsx` | `emails.change-email-confirmation-email` | `modules/account/use-cases/send-change-email-confirmation-email.ts`          |
| `newsletter-confirmation-email.tsx`   | `emails.newsletter-confirmation-email`   | `modules/newsletter-subscriber/use-cases/subscribe-to-newsletter.ts`         |
| `newsletter-notification-email.tsx`   | `emails.newsletter-notification-email`   | `modules/newsletter-subscriber/use-cases/confirm-newsletter-subscription.ts` |

Better Auth викликає перші три сценарії використання зі своїх хуків в `auth.server.ts`. Сповіщення про розсилку надходить власникові сайту англійською після підтвердження підписки. Посилання в листах будуються за допомогою `localizePathname`, тож вони відкриваються в локалі листа.

Сценарії використання для підтвердження адреси, скидання пароля й підтвердження розсилки спершу викликають `withinRecipientRateLimit` з `src/lib/rate-limit.ts`: щонайбільше три листи кожного типу на адресу за годину, з ключем за хешем SHA-256 адреси. Понад ліміт вони пропускають лист без помилки.

## Тестування

Vitest мокає виклики постачальника. У тестовому Worker для Playwright запити до API Resend перехоплюються замість надсилання, а `/__test/emails?to=<address>` повертає перехоплені листи.
