---
title: "Forms and validation"
description: "Build forms with TanStack Form, shadcn fields and the module Zod schema that the server also enforces."
---

Forms follow the shadcn TanStack Form pattern: `useForm` with the module's Zod schema, `form.Field` render props, shadcn `Field` components and a mutation for submission. The server function validates the same schema again, so the client check is for feedback only.

## Example

Condensed from `src/presentation/components/custom/newsletter-form.tsx` (styling removed):

```tsx
const emailSchema = newsletterSubscriberZodSchemas.subscribeToNewsletter.pick({ email: true })

export const NewsletterForm = (): JSX.Element => {
  const t = useTranslations("components.custom.newsletter-form")
  const inputId = useId()
  const errorMessage = useErrorMessage()
  const queryClient = useQueryClient()

  const subscribe = useMutation({
    ...subscribeToNewsletterMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSuccess: ({ status }) => {
      toast.success(t(status))
      return queryClient.invalidateQueries({ queryKey: NEWSLETTER_SUBSCRIBER_QUERY_KEYS.ALL })
    },
  })

  const form = useForm({
    defaultValues: { email: "" },
    listeners: { onBlur: validateOnBlur },
    onSubmit: ({ value, formApi }) => {
      subscribe.mutate(
        { email: value.email, locale: getCurrentLocale() },
        {
          onSuccess: () => {
            formApi.reset()
          },
        },
      )
    },
    validators: { onChange: emailSchema },
  })

  return (
    <form
      noValidate
      onSubmit={(event) => {
        void submitForm(event, form)
      }}
    >
      <form.Field name="email">
        {(field) => {
          const isInvalid = isFieldInvalid(field)

          return (
            <Field data-invalid={isInvalid}>
              <FieldLabel htmlFor={inputId}>{t("label")}</FieldLabel>
              <Input
                aria-describedby={`${inputId}-error`}
                aria-invalid={isInvalid}
                autoComplete="email"
                id={inputId}
                name={field.name}
                onBlur={field.handleBlur}
                onChange={(event) => {
                  field.handleChange(event.target.value)
                }}
                placeholder={t("placeholder")}
                type="email"
                value={field.state.value}
              />
              <Button isPending={subscribe.isPending} type="submit">
                {subscribe.isPending ? t("submitting") : t("button")}
              </Button>
              <div id={`${inputId}-error`}>
                {isInvalid && (
                  <ValidationFieldError
                    message={fieldErrorMessage(field.state.meta.errors)}
                    namespace="auth.validations"
                    params={AUTH_VALIDATION_PARAMS}
                  />
                )}
              </div>
            </Field>
          )
        }}
      </form.Field>
    </form>
  )
}
```

## Schema

- Use the schema from the module's `<table>.zod.ts`, or from `src/integrations/better-auth/auth.zod.ts` for auth forms. `.pick(...)` selects the fields the form shows; values the user does not type, such as the locale, are added in `onSubmit`.
- `validators: { onChange: emailSchema }` is the only validator. TanStack Form runs it on every change and again on submit; a separate `onSubmit` copy would leave a submit-time error red until its own field changed.
- `listeners: { onBlur: validateOnBlur }` runs the same validator when a field loses focus, so a field the visitor tabbed through has its error as soon as they leave it.
- `noValidate` turns off browser validation so the Zod messages are the only errors.

## Errors

- A field shows its error once the visitor has left it or tried to submit, never while they are still typing: `isFieldInvalid(field)` from `src/integrations/tanstack-form/form.fields.ts`, which is `field.state.meta.isBlurred && !field.state.meta.isValid`. The value sets `data-invalid` on `Field`, `aria-invalid` on the input and whether the error renders, so all three change together.
- After the error shows, every change revalidates the field, so the error clears on the keystroke that fixes the value. Do not use `isTouched`: TanStack Form sets it on the first keystroke.
- Live feedback that rewards progress, such as `PasswordRequirements`, reads the values directly and updates from the first keystroke.
- The input always sets `aria-describedby` to its error's id, `<input id>-error`, and `ValidationFieldError` renders that element with the id only while the field is invalid. Browsers ignore a reference to a missing element, so the field has no description while it is valid.
- Zod messages are translation keys, such as `emailInvalid`. `fieldErrorMessage` takes the first one, and `ValidationFieldError` renders `<namespace>.<key>` with the matching entry from `params`, for example `max` (<RepositoryFact name="emailMaxLength" />) for `emailMaxLength`. A key that does not exist falls back to `errors.codes.VALIDATION`.
- The forms pass `auth.validations`, which the `auth` and `admin` layouts preload and the newsletter feature adds to the `_marketing` layout for its form, except the admin course forms, which pass `course.validations` from the `admin.courses.tsx` layout, the withdrawal form, which passes `withdrawal.validations` from the `_marketing` and `app` layouts, and the newsletter issue form, which passes `newsletter-issue.validations` from the `admin.newsletter_.compose.tsx` route. The route must load the namespace a form uses.
- Server errors go through `useErrorMessage()` in the mutation's `onError`.

## Submission

- The form's `onSubmit` calls `submitForm(event, form)` from `src/integrations/tanstack-form/form.submit.ts`. It prevents the browser's submission and calls `form.handleSubmit()`; when the form is invalid it marks every field as left, so all errors show, and moves focus to the first control with `aria-invalid="true"`.
- Submit through the use case's mutation options spread into `useMutation`. `SignInForm` is the exception: it calls the Better Auth client's `signIn.email` in its own `useMutation`, and the client's two-factor plugin handles `twoFactorRedirect`.
- `<Button isPending={mutation.isPending} type="submit">` disables the button and announces the pending state while the request runs.
- The submit button stays enabled while the form is incomplete; only `isPending` disables it. Pressing it with mistakes shows every error and focuses the first invalid field.
- A server error that belongs to one field, such as `passwordCompromised` for a password found in a known data breach, goes under that field with `showFieldError(formApi, { controlId, field, message })` from `form.submit.ts` instead of a toast; it clears when the field changes.
- Reset the form or navigate in the mutation's `onSuccess`, and invalidate the module queries the mutation changes.

More examples: `sign-in-form.tsx`, `sign-up-form.tsx`, `reset-password-form.tsx` and `two-factor-form.tsx` in `src/presentation/components/custom/auth/`.
