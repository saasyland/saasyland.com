Jede Regel auf dieser Seite stammt aus einer Messung, und mehrere haben eine intuitive Lösung ersetzt, die es schlimmer gemacht hat. Ändern Sie den Code hinter einer dieser Regeln nur mit einer neuen Messung, die sie übertrifft.

## Erst messen, dann behaupten

- Vergleichen Sie den vorherigen und den neuen Build auf derselben Seite mit mindestens fünf Lighthouse-Läufen pro Build, abwechselnd ausgeführt, und vergleichen Sie die Mediane. Ein einzelner Lauf beweist nichts: Etwa jeder fünfte Lauf ist ein Ausreißer, verursacht durch Rauschen auf der Maschine.
- Beurteilen Sie eine Änderung nicht anhand eines einzigen Laufs von PageSpeed Insights. Dasselbe Deployment erzielt je nach Geschwindigkeit der Maschine, die den Test ausführt, sehr unterschiedliche Werte; diese Geschwindigkeit meldet Lighthouse als `benchmarkIndex`.
- Messen Sie einen Produktions-Build (`bun run build:test`, dann `bun run start:test`), ausgeliefert über HTTP/2 mit Komprimierung. Über einfaches lokales HTTP/1.1 ohne Komprimierung modelliert die Netzwerksimulation von Lighthouse Verbindungen und Übertragungsgrößen, die es in Produktion nie gibt.
- Eine Lighthouse-Diagnose ist kein Score. Ein Hinweis wie „forced reflow“ oder „properly size images“ kann für die Seite falsch sein, wie die folgenden Abschnitte zeigen; prüfen Sie die bewerteten Metriken, bevor Sie danach handeln.

## Den Boot-Graph des Workers klein halten

`src/server.ts` läuft bei jeder HTML-Anfrage (`run_worker_first` in `wrangler.jsonc`), und alles, was es statisch importiert, wird bei jedem Kaltstart ausgewertet. Die Datei und die Worker-Handler, die die Bereiche beitragen, importieren nur Konstanten und reine Hilfsfunktionen und laden den Rest, wenn eine Anfrage ihn braucht:

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

Ein einziger statischer Import eines Header-Namens aus einem Modul, das auch den Polar-Client importierte, zog einmal etwa 1,4 MB SDK in jeden Kaltstart, und das erste Byte der Landingpage brauchte bis zu 1,4 Sekunden. Deshalb liegen `COUNTRY_HEADER` und `IP_ADDRESS_HEADER` in `src/modules/_core/constants/api.ts`, das nichts Schweres importiert. Bevor Sie `server.ts` oder einer `<area>.worker.ts` einen statischen Import hinzufügen, verfolgen Sie dessen Importkette: Alles, was `polar`, `drizzle-orm` oder `resend` erreicht, ist eine Regression. `scripts/verify-build.ts` prüft das bei jedem Build: Es verfolgt die statischen Importe des Einstiegspunkts des deployten Workers, `dist/server/index.js`, und schlägt fehl, wenn sie Code erreichen, der aus `@polar-sh`, `drizzle-orm` oder `resend` gebündelt wurde, oder zusammen mehr als `BOOT_CLOSURE_MAX_BYTES` ergeben.

## Das ORM aus dem Browser heraushalten [#keep-the-orm-out-of-the-browser]

Drizzle läuft nur im Worker. Der Browser braucht die Zod-Schemas eines Moduls für seine Formulare und dessen Enum-Tupel für seine Auswahlfelder, deshalb liegen beide in Dateien, die nichts aus Drizzle importieren: `<table>.zod.ts` und `<table>.constants.ts` (siehe [Module](/docs/conventions/modules)). Ein Browser-Import, der eine `<table>.schema.ts` erreicht, führt `sqliteTable(...)` aus, einen Aufruf, den der Bundler behalten muss, und bringt `drizzle-orm` mit.

`<table>.zod.ts` erzeugte früher außerdem mit `drizzle-zod` die Schemas `insert`, `select` und `update` aus den Tabellen, und zur Laufzeit las sie nichts. `drizzle-zod` hält den gesamten Zod-Namespace fest, sodass der Bundler auch jede Zod-Locale, den JSON-Schema-Konverter von Zod und seinen Compiler behielt. Die Pending-Skeletons von `/admin` und `/app` importierten `PreferencesCardPending` aus `preferences-card.tsx`, das `user.zod.ts` importierte, und Pending-Komponenten werden nicht in eigene Chunks aufgeteilt, sodass all das auf jeder Seite geladen wurde. Die Tupel in die Konstanten zu verschieben und diese Schemas zu löschen, hat jede Seite um etwa 75 KiB gzip-komprimiertes JavaScript verkleinert. Die Größen unten umfassen jedes Skript, das die jeweilige Seite lädt, gzip-komprimiert, laut Ausgabe von `bun run build:test`:

| Seite          | Vorher    | Nachher   |
| -------------- | --------- | --------- |
| `/`            | 526,2 KiB | 450,7 KiB |
| `/docs/<page>` | 612,1 KiB | 536,5 KiB |
| `/blog`        | 487,2 KiB | 411,7 KiB |
| `/app`         | 496,6 KiB | 421,0 KiB |
| `/admin`       | 515,0 KiB | 439,4 KiB |

`src/data/tanstack.vite.ts` verweigert `drizzle-orm` der Client-Umgebung über den Importschutz von TanStack Start:

```ts title="src/data/tanstack.vite.ts"
const SERVER_ONLY_PACKAGES = [/^drizzle-orm(?:\/|$)/u]
```

Ein Build, in dem ein Import davon das Tree-Shaking übersteht, schlägt fehl und gibt die Importkette von der Route bis zu der Datei aus, die Drizzle erreicht hat. Unterbrechen Sie die Kette dort, wo sie beginnt: Importieren Sie das Tupel aus den Konstanten des Moduls, oder verschieben Sie den Code in eine Server Function. Reine Typ-Importe werden entfernt und zählen nie.

## Nachrichten laden, wenn eine Seite sie braucht [#load-messages-when-a-page-needs-them]

Die erste Seite, die ein Besucher öffnet, lädt im Browser keine Nachrichtendatei: Die Root-Route und die passenden Routen laden ihre Namespaces auf dem Server in den Query-Cache vor, und TanStack Start schickt diesen Cache mit dem HTML. Der Browser lädt einen Namespace erst, wenn eine spätere Navigation einen braucht, den der Cache noch nicht enthält.

`import.meta.glob` gibt jeder Nachrichtendatei einen eigenen Chunk, aber die Zuordnung jeder Datei zu ihrem Chunk, die jeden Namespace in jeder Locale nennt, landet in dem Modul, das den Glob aufruft. Dieses Modul war `i18n.messages.ts`, das die Root-Route importiert, und es enthielt die Zuordnung doppelt, einmal für die Nachrichten und einmal für die Seiten-Metadaten, sodass jede Seite etwa 240 KiB Loader lud, 21 KiB gzip-komprimiert. Die Zuordnung liegt jetzt allein in `i18n.loaders.ts`, und `loadNamespace` importiert sie, wenn es zum ersten Mal einen Namespace lädt:

```ts title="src/integrations/use-intl/i18n.messages.ts"
const { MESSAGE_LOADERS } = await import("~/src/integrations/use-intl/i18n.loaders")
```

`loadPageMetadata` liest `metadata` aus dem Namespace der Seite statt aus einer zweiten Zuordnung, sodass der Head einer Seite und ihre Nachrichten aus einem Chunk kommen. Der Browser holt `i18n.loaders.ts`, etwa 11 KiB gzip-komprimiert, mit dem ersten Namespace, den er lädt, bei einer Navigation oder beim Hovern, das eine vorlädt. Die Root-Namespaces werden weiterhin in `i18n.messages.ts` am Dateinamen erkannt, und die Schlüssel dieses Globs kosten etwa 2 KiB gzip-komprimiert. Jedes Skript, das die jeweilige Seite lädt, gzip-komprimiert, laut Ausgabe von `bun run build:test`:

| Seite          | Vorher    | Nachher   |
| -------------- | --------- | --------- |
| `/`            | 462,9 KiB | 442,3 KiB |
| `/docs/<page>` | 553,5 KiB | 532,9 KiB |
| `/blog`        | 424,6 KiB | 404,0 KiB |
| `/app`         | 430,4 KiB | 409,7 KiB |
| `/admin`       | 452,8 KiB | 432,2 KiB |

Laden Sie Nachrichten nur über `loadNamespace`, und fügen Sie nie ein `import.meta.glob` über `messages/` in ein Modul ein, das die Root-Route importiert. `scripts/verify-build.ts` folgt den statischen Importen des Einstiegsskripts im Browser und lässt den Build fehlschlagen, wenn sie den Loader eines Seiten-Namespace enthalten.

## Vorgerenderte Seiten laden zuerst CSS und Schriften

Öffentliche Seiten werden vorgerendert und brauchen für ihren ersten Paint kein JavaScript. TanStack Start erzeugt einen `modulepreload`-Hinweis für jeden Chunk, den eine Seite brauchen könnte, auf der Landingpage mehr als hundert, und in einem simulierten Mobilfunknetz konkurrieren sie mit dem Stylesheet und den Schriften. `scripts/optimize-prerendered-html.ts`, das jedes Build-Skript ausführt, entfernt jeden Hinweis auf Abhängigkeiten und behält nur den Hinweis auf das eigene Entry-Skript der Seite, mit `fetchpriority="low"`:

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

Das Entfernen der Hinweise senkte den First Contentful Paint um etwa ein Drittel; den Entry-Hinweis mit niedriger Priorität zu behalten, senkte den mobilen First Contentful Paint um weitere 375 ms. Fügen Sie nie wieder Preload-Hinweise hinzu, weder für Abhängigkeiten noch für Routen-Chunks. Das Skript lässt den Build fehlschlagen, wenn es keinen Hinweis zum Entfernen oder keinen zum Behalten findet, sodass eine Änderung der Build-Ausgabe auffällt, statt dies stillschweigend rückgängig zu machen.

Die Skript-Richtlinie behält diese Reihenfolge bei. `scripts/secure-prerendered-html.ts` läuft nach dem Optimierer und ersetzt das `<script type="module">` des Entry-Moduls an derselben Stelle der Seite durch einen Inline-Loader, der dort dasselbe Modul-Skript erzeugt. Der Entry-Hinweis im Head startet den Download weiterhin mit niedriger Priorität, und das Modul läuft weiterhin, sobald der Parser das Ende des Body erreicht. Ein Loader, der `import()` aufruft, wäre kürzer, aber Chromium blockiert einen dynamischen Import aus einem Skript, das ein Hash zulässt.

`robots.txt` und `llms.txt` sind statische Dateien in `public/`, die den Worker umgehen (`"!/robots.txt", "!/llms.txt"` in `run_worker_first`). Lighthouse ruft beide mit einem Timeout von zwei Sekunden ab, und eine langsame Antwort des Workers ließ die Audits von Lighthouse für SEO und Agent-Readiness fehlschlagen.

## Provider umschließen nie ein Routen-Outlet

TanStack Router umschließt Routen-Outlets mit Suspense-Boundaries, und React hydriert diese Boundaries später, in kleinen Stücken. Ein Context-Provider darüber, dessen Wert sich direkt nach der Hydration ändert, zwingt React, alles darunter auf einmal zu hydrieren:

- `ThemeProvider` um die gesamte Anwendung machte die Hydration der Landingpage zu einer einzigen Aufgabe von 200 ms, die Eingaben blockierte. Nachdem er nur noch um seine beiden Nutzer herum eingebunden wurde, den `Toaster` und den `ThemeSwitch` der Dokumentation, sank die Total Blocking Time von etwa 150 ms auf unter 10 ms.
- `MotionProvider` über einem Routen-Outlet veröffentlicht einen neuen Context, wenn seine Animationsfunktionen fertig geladen sind. Bei einem Blogbeitrag traf diese Aktualisierung ein, während die Seite noch ihren Inhalt lud; React wich auf clientseitiges Rendern aus, und das Layout verschob sich.

Bevor Sie `__root.tsx` oder einem Layout einen Provider hinzufügen, prüfen Sie, ob sich sein Wert nach der Hydration ändern kann. Wenn ja, binden Sie ihn neben den Komponenten ein, die ihn lesen, unterhalb jedes Routen-`<Outlet />`. Die Platzierungen sind unter [Komponenten und Styling](/docs/conventions/components) aufgeführt.

## Skeletons bleiben im Einstiegsskript [#skeletons-stay-in-the-entry-script]

TanStack Router teilt `pendingComponent` standardmäßig nicht in einen eigenen Chunk auf, und `src/data/tanstack.vite.ts` behält diese Voreinstellung bei, sodass jedes Skeleton im Einstiegsskript liegt und erscheint, sobald eine Navigation `pendingMs` überschreitet. Sie aufzuteilen wurde gemessen und verworfen:

- Die Layout-Skeletons `AdminPending`, `AppPending` und `MarketingPending` zeichnen das Seiten-Skeleton aus `PAGE_SKELETONS`, das die Skeletons aller Bereiche importiert, und der Router lädt die Pending-Komponenten der passenden Routen, bevor die Seite hydriert. `/`, `/app` und `/admin` luden weiterhin jedes Skeleton, nun in eigenen Chunks, und wurden um 3,5 bis 6,5 KiB gzip-komprimiert größer; leichter wurden nur Seiten, deren Layout ein eigenes Skeleton hat, etwa `/docs` und `/blog`.
- Ein aufgeteiltes Skeleton muss geladen sein, bevor es erscheinen kann. In Headless-Chromium mit 400 ms zusätzlicher Latenz und 200 KiB/s zeigte eine clientseitige Navigation von `/` zu `/blog` den Blog nach 2.290 ms statt nach 1.390 ms, hinter einem Skeleton, das der Build ohne Aufteilung nie brauchte; mit 150 ms Latenz dauerte sie 800 ms statt 640 ms.

Weil jede Seite jedes Skeleton lädt, importiert ein Skeleton `Skeleton`, die shadcn-Primitive, andere Skeletons und die Konstanten, die seine Längen bestimmen, nie ein Formular. `PreferencesCardPending` wurde aus `preferences-card.tsx` exportiert, sodass die Skeletons von `/admin` und `/app` das Einstellungsformular, TanStack Form, die Zeitzonenliste und die Benutzer-Schemas in das Einstiegsskript jeder Seite brachten; es hat jetzt eine eigene Datei, `preferences-card-pending.tsx`. Jedes Skript, das die jeweilige Seite lädt, gzip-komprimiert, laut Ausgabe von `bun run build:test`:

| Seite          | Vorher    | Nachher   |
| -------------- | --------- | --------- |
| `/`            | 463,0 KiB | 451,9 KiB |
| `/docs/<page>` | 553,6 KiB | 527,3 KiB |
| `/blog`        | 424,7 KiB | 413,6 KiB |
| `/app`         | 430,4 KiB | 404,1 KiB |
| `/admin`       | 452,9 KiB | 427,7 KiB |

`/` und `/blog` sparen weniger, weil ihre Layouts das Newsletter-Formular rendern, das TanStack Form ohnehin braucht. `pending-imports.test.ts` folgt den Importen jeder `*-pending.tsx` und schlägt fehl, wenn eine davon `@tanstack/react-form` erreicht. Die Panels des Admin-Dashboards und die Abschnitte der Kundenübersicht koppeln jedes Skeleton weiterhin in der Liste des Bereichs an seine Komponente, sodass diese Komponenten mit den Skeletons geladen werden.

## Ein einziger Tailwind-Build

Nur `src/presentation/styles/globals.css` führt Tailwind aus. Routen-Stylesheets wie `docs.css` und `typeset.css` sind einfaches CSS, und die eigenen Styles von Fumadocs kommen über `globals.css` herein:

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

Ein zweiter Tailwind-Build in einem Routen-Stylesheet lieferte einmal seine eigenen `.hidden`, `.rounded-md` und Theme-Variablen aus. Gleichnamige Cascade Layers werden über Stylesheets hinweg zusammengeführt, und React entfernt nie ein Stylesheet, das es mit `precedence` eingefügt hat, sodass die Landingpage nach einem Besuch der Dokumentation ihr responsives Layout und ihre Schriften bis zum Neuladen verlor. Der End-to-End-Test "landing keeps its responsive styles after visiting the docs" in `e2e/specs/landing.spec.ts` sichert das ab. Alles, was Tailwind braucht, läuft über `globals.css`.

## Medien

- **Landing-Loops.** Jede `src/presentation/assets/motion/<name>.webm` hat ein Posterbild `<name>.webp` mit genau den Abmessungen des Videos, damit der Übergang vom Posterbild zum Video nicht sichtbar schärfer wird. Die Abmessungen sind `LANDING_VIDEO_SIZES` in `src/data/landing-videos.ts`, die sowohl die Remotion-Kompositionen als auch `ConceptLoop` lesen. Kleinere Breiten sind eigene Dateien, `<name>-<width>.webp`, angeboten über das `srcSet` des Posterbilds. `landing-videos.test.ts` schlägt fehl, wenn die Größe eines Posterbilds von seiner Komposition oder von der Breite in seinem Dateinamen abweicht. Verkleinern Sie nie das Posterbild in voller Größe; um es leichter zu machen, kodieren Sie es in denselben Abmessungen neu. Die Videos laden mit `preload="none"`, spielen nur, solange ein Viertel davon sichtbar ist, und spielen nie für Leser, die reduzierte Bewegung bevorzugen.
- **Die Kurstour** in `course-showcase.tsx` ist keine Schleife. Ihr `<video>` wird erst gerendert, wenn jemand auf Abspielen drückt, sodass die Seite bis dahin nur das Posterbild lädt: ein `<picture>` mit AVIF- und WebP-Quellen in den 1600 Pixeln des Videos und in 800 Pixeln. Das Video selbst wird als WebM mit MP4 als Ausweichformat ausgeliefert.
- **Kursvideos** werden vorab in adaptives HLS kodiert und mit dem Workers-Cache aus R2 ausgeliefert. Siehe [Videos](/docs/features/videos).
- **Per Scrollen gesteuertes Video.** Die Website hat derzeit keines. Ein Video, dessen Zeit der Scrollposition folgt, muss all-intra kodiert sein (jeder Frame ein Keyframe, `keyint=1`): Bei einer normalen Kodierung dauert ein Sprung etwa 200 ms, bei einer all-intra-Kodierung etwa 3 ms, und keine noch so starke Glättung in JavaScript macht aus einem Sprung von 200 ms ein flüssiges Scrubbing.

## Einblenden beim Scrollen

`Reveal` (`src/presentation/components/custom/landing-page/components/reveal.tsx`) blendet Abschnitte der Landingpage ein, wenn sie in den Viewport kommen. Es teilt einen `IntersectionObserver` zwischen allen Instanzen, entscheidet anhand des ersten Callbacks des Observers, ob ein Element unterhalb des sichtbaren Bereichs beginnt, und schreibt `data-reveal`-Attribute direkt, ohne React-State und ohne erneutes Rendern. Eine Version, die die Sichtbarkeit in React-State hielt, verdoppelte die Total Blocking Time, weil jeder Abschnitt neu renderte und die Seite zweimal das Layout berechnete. Verlagern Sie es nicht zurück in State, und ersetzen Sie es nicht ohne Vergleichsmessung.

Zwei weitere Optimierungen wurden gemessen und verworfen: `content-visibility: auto` auf Abschnitten der Landingpage, was seiteninterne Links zu weiter unten liegenden Abschnitten kaputt machte, und das verzögerte Laden des Newsletter-Formulars, das gleich gut oder schlechter abschnitt, als es direkt zu rendern.

## Später geladene Inhalte behalten ihre Größe

Eine vorgerenderte Seite wird gezeichnet, bevor ein Skript läuft, also muss ein Abschnitt, der sich danach füllt, in den Platz passen, den er bekommen hat. Der Kursblock der Landingpage ist ein solcher Abschnitt: Er liest die veröffentlichten Kurse, sobald er in die Nähe gescrollt wird, und sein Platzhalter nahm früher zwei Kurse mit je sechs Lektionen an, sodass der Block beim Eintreffen der Kurse wuchs oder schrumpfte und alles darunter um hundert Pixel und mehr verschob. Seine Spalten haben jetzt eine feste Folge einzeiliger Zeilen, der Platzhalter zeichnet dieselben Zeilen, und seine Hinweise stehen in einem Rahmen von der Größe einer Spalte, sodass jeder Zustand bei jeder Breite dieselbe Höhe hat (siehe [Kurse](/docs/features/courses)). Die Sternanzahl auf der Landingpage macht es genauso, mit einem Skeleton so hoch wie die Zahl. Die Kurse ins vorgerenderte HTML zu schreiben, ist keine Option: Der Build hat keine Produktionsdatenbank, und die Landingpage bei jeder Anfrage im Worker zu rendern, würde die Zeit bis zum ersten Byte wieder hergeben, die das Vorrendern spart.
