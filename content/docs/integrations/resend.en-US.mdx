`src/integrations/resend/resend.config.ts` creates the Resend client from `RESEND_API_KEY`. `resend.utils.ts` exports `sendEmail`, the only function that sends email. `from` defaults to `RESEND_EMAIL_FROM`, the required `idempotency` option names the email's purpose and the token that triggered it, and `sendEmail` turns them into the key `<purpose>/<SHA-256 of the token>`, which stops Resend from sending a retried request twice and stays within Resend's 256-character limit, and a Resend error is thrown. Both files are server-only. `resend.constants.ts` names every purpose in `EMAIL_PURPOSE`, and the use cases pass the same name as the `kind` of the per-recipient limit.

## Templates and use cases

Templates in `src/presentation/emails/` are React Email components with markup only. Each exports a `*_NAMESPACE` constant, receives `locale` and `messages` as props and translates with use-intl `createTranslator`. The use case that sends an email receives the locale from its caller (the verification email reads it from the callback URL), loads the messages, renders the template and calls `sendEmail`:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await sendEmail({
  idempotency: { purpose: EMAIL_PURPOSE.VERIFY_EMAIL, token },
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

| Template                              | Namespace                                | Sent by                                                                      |
| ------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------- |
| `verify-email.tsx`                    | `emails.verify-email`                    | `modules/verification/use-cases/send-verify-email.ts`                        |
| `reset-password-email.tsx`            | `emails.reset-password-email`            | `modules/verification/use-cases/send-reset-password-email.ts`                |
| `change-email-confirmation-email.tsx` | `emails.change-email-confirmation-email` | `modules/account/use-cases/send-change-email-confirmation-email.ts`          |
| `newsletter-confirmation-email.tsx`   | `emails.newsletter-confirmation-email`   | `modules/newsletter-subscriber/use-cases/subscribe-to-newsletter.ts`         |
| `newsletter-notification-email.tsx`   | `emails.newsletter-notification-email`   | `modules/newsletter-subscriber/use-cases/confirm-newsletter-subscription.ts` |

Better Auth calls the first three use cases from its hooks in `auth.server.ts`. The newsletter notification goes to the site owner in English after a subscription is confirmed. Links inside emails are built with `localizePathname`, so they open in the email's locale.

The verification, password reset and newsletter confirmation use cases first call `withinRecipientRateLimit` from `src/lib/rate-limit.ts`: at most three emails of each kind per address per hour, keyed on a SHA-256 hash of the address. Over the limit they skip the email without an error.

## Testing

Vitest mocks provider calls. In the Playwright test Worker, requests to the Resend API are captured instead of sent, and `/__test/emails?to=<address>` returns the captured emails.
