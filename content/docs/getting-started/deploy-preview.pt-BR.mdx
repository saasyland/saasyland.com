---
title: "Deploy de um preview"
description: "Provisione os recursos da Cloudflare e faça o deploy do Worker de preview."
---

O ambiente `preview` faz o deploy do Worker `saasyland-preview` em `preview.saasyland.com`. Por padrão, `development` e `preview` compartilham um banco de dados D1, um namespace KV e um bucket R2.

## Provisionar os recursos

```sh
bunx wrangler login
bunx wrangler d1 create saasyland_com_preview
bunx wrangler kv namespace create CACHE --env preview
bunx wrangler r2 bucket create saasyland-preview
```

Em `wrangler.jsonc`, substitua `database_id`, `database_name`, o `id` do KV e o `bucket_name` de `MEDIA` tanto em `development` quanto em `preview`. Mantenha os nomes de binding `DB`, `CACHE` e `MEDIA` e o `migrations_dir`, e atualize os nomes dos Workers e as rotas de domínio personalizado para a sua conta. Para produção, crie recursos separados, incluindo o bucket `saasyland`, e atualize o bloco `production`. Defina `APP_DOMAIN` em `src/presentation/branding/index.ts`. `DEPLOYED_HOSTS`, em `src/modules/_core/constants/api.ts`, deriva dele os hosts de deploy, `APP_DOMAIN` para produção e `preview.<APP_DOMAIN>` para preview, e é o único lugar em que o código os nomeia: `appHostsForMode` o lê para obter os hosts que o Better Auth e os links da newsletter aceitam, e `scripts/verify-deployment.ts` faz requisições a eles depois de um deploy. Localmente, `appHostsForMode` aceita `localhost:3000` ou `127.0.0.1:3000` em desenvolvimento e, em teste, esses mais `localhost:3020` e `127.0.0.1:3020`. Edite `DEPLOYED_HOSTS` apenas se o seu host de preview tiver outro nome. As `routes` de domínio personalizado em `wrangler.jsonc` e as URLs de ambiente em `.github/workflows/deploy-reusable.yml` nomeiam os mesmos hosts, então mantenha-os em sincronia.

## Deploy

Preencha `.env.preview`, configure o sandbox do Polar como descrito em [Configuração do Polar](/docs/getting-started/polar-setup) e, em seguida, faça o deploy:

```sh
bun run deploy:preview
```

`deploy:preview` executa `scripts/verify-bindings.ts preview`, que rejeita bindings ausentes e IDs de placeholder, depois `polar:verify:preview`, que compara a organização do Polar em `.env.preview` com o código, e então `build:preview`, que pré-renderiza as páginas públicas e verifica a saída. Em seguida, `scripts/prepare-deploy-secrets.ts preview` grava em `.wrangler/secrets.preview.json` os secrets que o `wrangler.jsonc` declara para `preview`, lidos de `.env.preview`, e falha se algum estiver vazio. `db:migrate:preview` aplica as novas migrações antes que o `wrangler deploy` envie `dist/server/wrangler.json` com esses secrets e, por fim, `scripts/verify-deployment.ts preview` verifica se o host de preview de `DEPLOYED_HOSTS` (https://preview.saasyland.com) responde. `verify-bindings.ts` não verifica se o bucket R2 existe, porque ele é vinculado pelo nome: o deploy falha até que ele exista. `bun run db:migrations:preview` lista as migrações que o banco de dados de preview ainda não aplicou.

Registre os callbacks de OAuth para o host de preview, conforme listado em [Variáveis de ambiente](/docs/getting-started/environment-variables).

## Deploys automáticos

A CI faz o deploy de todo pull request de uma branch deste repositório no preview compartilhado, e de todo push para `main` em produção, depois que as verificações e os testes no navegador passam. Veja [CI/CD](/docs/tooling/ci-cd) para os secrets do GitHub necessários.
