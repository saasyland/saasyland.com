## Datenbank

**`no such table` bei `bun run dev`.** Die lokale Entwicklungsdatenbank ist nicht migriert. Führe `bun run db:migrate:local` aus, oder `bun run db:reset:local` und `bun run db:seed:local` für eine frische, befüllte Datenbank.

**`no such table` in Playwright.** Browsertests nutzen eine eigene lokale Datenbank. Führe `bun run db:reset:test` aus oder lass Playwright die App starten, das diesen Befehl ausführt.

**Die Vitest-Tabellen sind veraltet.** Der D1-Mock wendet beim Start jede SQL-Datei in `src/integrations/drizzle-orm/migrations` an. Erzeuge nach einer Schemaänderung eine Migration mit `bun run db:generate`.

## Entwicklungsserver

**Der Dev-Server startet nicht.** Er lauscht mit `strictPort` auf `localhost:3000` und schlägt daher fehl, wenn der Port belegt ist. Beende den anderen Prozess.

**Die Anmeldung oder OAuth schlägt fehl.** Prüfe `AUTH_SECRET` und die OAuth-Client-Zugangsdaten in der Umgebungsdatei und ob die Callback-URL des Providers auf <RepositoryFact name="oauthCallbackPath" /> auf dem Host zeigt, den du verwendest. Better Auth akzeptiert nur die Hosts, die für den Build-Modus konfiguriert sind: in der Entwicklung `localhost:3000` und `127.0.0.1:3000`.

**In den Worker-Typen fehlt ein Binding oder Secret.** Führe nach Änderungen an `wrangler.jsonc` den Befehl `bun run cf-typegen` aus: Er typisiert jedes Binding und jedes Secret aus `secrets.required`. Einen Wert, den Wrangler nicht ableiten kann, etwa eine Variable, die nur `test` setzt, deklariert der Bereich in seiner `src/types/<area>.d.ts`.

**Eigene `text-*`-Klassen verschwinden beim Zusammenführen.** `cn` hängt von Tabellen ab, die aus `src/lib/cn.config.ts` generiert werden. `bun run dev`, `bun run check` und die Builds erzeugen sie neu; führe `bun run generate:cn` aus, wenn `.source/cn-tables.ts` fehlt.

## Übersetzungen

**`No messages/<locale>/<namespace>.json`.** Eine Route deklariert einen Namespace, für den es in dieser Locale keine Datei gibt. Lege die Datei in jeder Locale an.

**Ein Key wird als sein Pfad gerendert, oder `check:i18n` meldet einen fehlenden Key.** Der Key fehlt in einer Locale, oder die Komponente liest ihn außerhalb des Scopes ihres `useTranslations`-Aufrufs. Verwende nur einen `useTranslations`-Aufruf pro Komponente und führe `bun run check:i18n` aus.

## Dokumentation

**Eine Doku-Seite liefert 404.** Die Datei muss `<page>.<locale>.mdx` heißen und in `pages` der `meta.<locale>.json` ihres Ordners aufgeführt sein. Führe `bun run content` aus, um `.source` neu zu erzeugen.

**`check-content.ts` schlägt fehl.** Das Skript vergleicht jede Locale mit en-US. `Changed code examples` bedeutet, dass ein Codeblock vom englischen abweicht; Codeblöcke müssen identisch sein. `Untranslated English paragraph` bedeutet, dass ein Absatz unübersetzt kopiert wurde. `Missing <file>` bedeutet, dass eine Locale-Datei fehlt. `leaves out … from the English page` und `adds …, which the English page does not have` bedeuten, dass eine Übersetzung Inline-Code, eine Komponente oder eine ihrer Props oder einen Link auf eine andere Seite verloren oder hinzugefügt hat; übernimm sie so, wie die englische Seite sie hat. `has … table rows where the English page has …` bedeutet, dass einer Tabelle eine Zeile fehlt oder eine hinzugekommen ist. `links to … instead of …` bedeutet einen internen Link, den die Website umleiten würde oder der eine Locale nennt; schreibe den Pfad, den die Meldung vorschlägt.

**`check-message-formats.ts` schlägt fehl.** `changed the path or command …` bedeutet, dass eine Übersetzung einen Dateipfad oder einen Befehl der englischen Nachricht verändert hat; lass ihn unverändert oder übergib ihn als ICU-Argument aus `REPOSITORY_FACTS`. `unexpected Markdown code` bedeutet, dass eine Übersetzung Backticks hinzugefügt hat, die eine Nachricht unverändert ausgibt. `uses “Sie” where de-DE addresses the reader as “du”` bedeutet, dass eine Übersetzung die Leser in einer Form anspricht, die ihre Locale nicht verwendet; formuliere den Satz in der [Anrede](/docs/conventions/translations#one-form-of-address) der Locale um. `check-content.ts` meldet dasselbe für eine Docs-Seite, einen Blogbeitrag oder einen Changelog-Eintrag.

## Tests und Deployment

**`test:coverage` schlägt fehl.** Die Testabdeckung muss für Zeilen, Anweisungen, Funktionen und Branches <RepositoryFact name="coverageThreshold" unit="percent" /> betragen. Der Bericht in `coverage/` listet die nicht abgedeckten Zeilen auf.

**Das Deployment bricht bei `verify-bindings.ts` ab.** Der Zielumgebung in `wrangler.jsonc` fehlt ein Binding, das die Umgebung `development` deklariert (`DB`, `CACHE`, `MEDIA` oder `BUNDLES`), sie enthält noch Platzhalter-IDs für D1 oder KV, oder sie teilt als Produktionsumgebung eine Ressource mit Preview. Lege die Ressourcen in Cloudflare an und ersetze die IDs.

**Das Deployment bricht bei `prepare-deploy-secrets.ts` ab.** Ein Schlüssel aus `secrets.required` der Umgebung fehlt in `.env.<environment>`, ist leer oder ein Platzhalter. `Set …` nennt die Schlüssel, die fehlen oder leer sind, und `Replace the placeholders …` die Schlüssel, die einen Wert in Klammern wie `[UPDATE]` oder ein Wort wie `TODO` oder `changeme` enthalten; keine der beiden Meldungen gibt einen Wert aus. [Projektskripte](/docs/tooling/scripts) listet jeden Platzhalter auf, den das Skript ablehnt. Trage die echten Werte in die Datei ein und starte das Deployment erneut.

**Das Deployment bricht bei `auth:verify` ab.** Eine OAuth-Client-ID in `.env.<environment>` hat nicht das Format ihres Anbieters, daher würde der Anbieter die Anmeldung ablehnen. Die Fehlermeldung nennt die Variable, die Datei und den Anbieter, ohne den Wert auszugeben, etwa `AUTH_GOOGLE_CLIENT_ID in .env.production is not a Google OAuth client ID.` Kopiere die Client-ID aus der Konsole des Anbieters (für Google siehe den Eintrag zu `invalid_client` weiter unten) und führe `bun run auth:verify:<environment>` aus, um sie erneut zu prüfen.

**Das Deployment bricht bei `polar:verify` ab.** Polar stimmt nicht mit dem Code überein: Ein Schlüssel in `.env.<environment>` fehlt oder nennt den falschen Polar-Dienst, das Token wird abgelehnt oder ihm fehlt ein Scope, oder die Checkout-Lokalisierung oder das Steuerverhalten der Organisation, ein Produkt, ein Preis, ein Lizenzschlüssel oder ein Webhook weicht von dem ab, was der Code erwartet. Die Fehlermeldung listet jedes Problem auf; [Polar-Einrichtung](/docs/getting-started/polar-setup) erklärt jede Meldung. `bun run polar:verify:<environment>` führt die Prüfung erneut aus.

**Das Deployment bricht bei `verify-deployment.ts` ab.** Der Worker ist deployt, aber ein geprüfter Pfad hat nicht mit `200` und dem erwarteten Inhaltstyp geantwortet, oder eine Anmeldung hat ihren Anbieter nicht wie vorgesehen erreicht. Die Fehlermeldung listet jede Anfrage und das Problem auf; öffne die URL und lies die Worker-Logs in Cloudflare. Endet eine Zeile auf `client_id is not a Google OAuth client ID.`, hat der Worker für diesen Anbieter keine echte Client-ID; siehe den nächsten Eintrag. `bun scripts/verify-deployment.ts <preview|production>` führt die Prüfung erneut aus.

**Google antwortet mit `Error 401: invalid_client` und `The OAuth client was not found.`** Der Worker hat Google eine Client-ID geschickt, die Google nicht kennt. `bun run deploy:<environment>` lehnt einen Platzhalter oder einen Wert in einem anderen Format in `AUTH_GOOGLE_CLIENT_ID` vor dem Build ab (siehe `prepare-deploy-secrets.ts` und `auth:verify` oben), ein Worker-Secret mit einem solchen Wert wurde also auf anderem Weg gesetzt, etwa mit `wrangler secret put`. Eine Client-ID in Googles Format, die Google nicht kennt, gehört zu einem gelöschten Client oder zu einem Client in einem anderen Google-Cloud-Projekt. So behebst du es:

1. Öffne in der Google Cloud Console **Google Auth Platform → Clients** und lege einen Client vom Typ **Web application** an, oder öffne den, den du verwenden willst. Seine Client-ID endet auf `.apps.googleusercontent.com`.
2. Trage für jeden Host, auf den du deployst, `https://<host>` unter **Authorized JavaScript origins** und <RepositoryFact name="googleCallbackUrl" /> unter **Authorized redirect URIs** ein; Google kann einige Minuten brauchen, bis sie gelten.
3. Wähle unter **Google Auth Platform → Audience** die Option **Publish app**, damit sich jedes Google-Konto anmelden kann und nicht nur die Testnutzer.
4. Trage Client-ID und Secret in `AUTH_GOOGLE_CLIENT_ID` und `AUTH_GOOGLE_CLIENT_SECRET` in `.env.<environment>` ein und führe `bun run deploy:<environment>` aus; das prüft die Client-ID vor dem Build, lädt beide Worker-Secrets hoch und prüft die Anmeldung erneut.

**Ein Prerender-Build schlägt fehl.** Die Build-Ausgabe nennt die erste URL, die fehlgeschlagen ist. Öffne diese Seite mit `bun run dev`, um den Fehler zu sehen.
