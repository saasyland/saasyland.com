`src/integrations/better-auth/auth.access.ts` define as declarações de permissão em `APP_STATEMENTS`, as concede aos papéis e monta a partir delas o controle de acesso do Better Auth (veja [Papéis e permissões](/docs/guides/roles-and-permissions)). As mesmas definições são usadas pelo servidor (`authorized`, guards de rota) e pelo cliente do Better Auth.

## Papéis

| Papel   | Código     | Permissões                                                                                                             |
| ------- | ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| Admin   | `admin`    | Todas as declarações da aplicação listadas abaixo, mais as declarações de admin do Better Auth para `user` e `session` |
| Cliente | `customer` | Nenhuma. Clientes podem chamar funções de servidor que exigem apenas uma sessão.                                       |

Novos usuários recebem `customer` (`DEFAULT_ROLE_CODE` em `auth.roles.ts`).

## Onde as permissões são verificadas

Cada caso de uso de `src/modules/*/use-cases/` pela chamada `authorized` que executa; `authorized()` exige uma sessão e nenhuma permissão:

<RepositoryTable name="permissionChecks" columns={["Middleware", "Casos de uso"]} />

As funções de servidor sem `authorized` executam `withRequest` ou `withRateLimit` e não precisam de sessão: <RepositoryFact name="publicUseCases" />. Fora dos casos de uso, `requireAdmin` no layout `/admin` e o redirecionamento após o login verificam `admin: ["access"]` com `hasPermission`, e `resolveViewer` (`lesson.viewer.ts`) deixa quem tem `course: ["read"]` assistir a toda aula e baixar seus materiais, seja qual for o nível de acesso da aula.

<RepositoryFact name="uncheckedStatements" /> estão declarados, mas ainda não são verificados por nenhuma função de servidor.

## Verificando uma permissão

As funções de servidor usam o middleware, por exemplo `authorized({ category: ["read"] })`. O restante do código chama `hasPermission`, como fazem os guards de rota:

```ts
const isAdmin = (role: string | null | undefined): boolean => hasPermission({ permission: { admin: ["access"] }, role })

export const requireAdmin = async (context: ProtectedRouteContext) => {
  const result = await requireSignedIn(context)
  if (!isAdmin(result.session.user.role)) {
    throw redirect({ replace: true, to: ROUTES.APP.INDEX })
  }
  return result
}
```
