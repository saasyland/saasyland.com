faq:
  - question: Що таке staged publishing у npm?
    answer: >-
      Це етап схвалення між CI і публічним реєстром. CI запускає npm stage publish, що не вимагає
      другого фактора, і версія чекає в зоні staging із тим dist-тегом, з яким її туди поставили.
      Публічною вона стає лише тоді, коли її схвалить супровідник, на npmjs.com або командою npm
      stage approve, і в обох випадках npm вимагає двофакторної автентифікації. Відхилену версію
      видаляють, так і не опублікувавши.
  - question: Публікувати з CI через trusted publishing чи з токеном npm?
    answer: >-
      Через trusted publishing. CI обмінює короткоживучий токен OIDC від GitHub Actions або GitLab
      на облікові дані для публікації, тож немає довгоживучого токена, який треба зберігати,
      ротувати і який може витекти. Дайте дозвіл id-token write лише завданню, що публікує, обмежте
      довіреного видавця самим staging, якщо вам також потрібне схвалення, і налаштуйте пакет так,
      щоб він вимагав двофакторної автентифікації й забороняв токени.
  - question: Чи дає trusted publishing моєму пакету атестації походження?
    answer: >-
      Лише з публічного репозиторію. npm автоматично генерує атестації походження (provenance) для
      trusted publishing, коли і вихідний репозиторій, і пакет публічні, а для приватних
      репозиторіїв не генерує. Пакет, зібраний із приватного репозиторію, усе одно має підпис
      реєстру npm, який перевіряє npm audit signatures, але не має атестацій походження.
  - question: Коли workflow релізу має створювати теги Git і GitHub Releases?
    answer: >-
      Після того, як реєстр почав віддавати версію, а не тоді, коли CI ставить її в staging чи
      публікує. Версію в staging можуть відхилити, замінити новішою або просто ніколи не схвалити, і
      тоді тег і Release описують пакет, якого ніхто не може встановити. Спершу перевірте в реєстрі
      точну версію, зробіть завдання безпечним для скількох завгодно запусків і запускайте його
      знову після кожного схвалення.
  - question: Як CLI може переконатися, що завантажує саме ті файли, з якими його випустили?
    answer: >-
      Закріпіть у коді, який ви публікуєте, дайджест вмісту, а не стисненого файлу, і записуйте це
      закріплення тоді, коли створюється версія. Вивантажте файл, перш ніж пакет можна буде
      встановити, нехай сервер відповідає розміром і дайджестом, які він зберігає, і відхиляйте
      будь-яке завантаження, розмір чи дайджест якого відрізняється від відповіді сервера або від
      закріпленого, ще до того, як щось із нього прочитати.
  - question: Чи може порожній changeset заблокувати реліз?
    answer: >-
      Так. Action Changesets не вибирає жодної роботи, коли кожен changeset в очікуванні порожній,
      навіть якщо гілка містить версію, якої в npm ще немає. З нами це сталося, коли порожній
      changeset потрапив у гілку вже після того, як зібрали pull request версії, а pull request
      версії злили, не перебудувавши. Зливайте pull request версії лише тоді, коли його зібрано з
      поточного head гілки.
  - question: Що робити, коли опублікована версія в npm зламана?
    answer: >-
      Позначте її як застарілу з повідомленням, яке називає виправлену версію, і випустіть
      виправлення як новий патч звичайним конвеєром. Не знімайте її з публікації: npm ніколи не
      дозволяє використати назву й версію вдруге, і кожен проєкт, який закріпив цю версію,
      зламається. Версію, яка лише стоїть у staging, можна натомість відхилити.
  - question: Чи варто дозволяти ШІ-агентам публікувати пакети?
    answer: >-
      Вони можуть робити все аж до реєстру: changeset, pull request версій, зміни workflow під
      рев’ю, нотатки до випусків, перевірку й записи після релізу. Крок, який не можна скасувати,
      має вимагати фактора, якого немає в жодного агента, як-от двофакторного схвалення версії в
      staging супровідником, і ніде не має бути токена публікації, яким міг би скористатися агент.

## Коротка відповідь

Ставтеся до релізу як до єдиного кроку, що не є злиттям. Усе до реєстру можна автоматизувати й повторити: версіонування з changeset, збірку, одноразове пакування, запуск зібраної програми на кожній платформі, яку ви підтримуєте, вивантаження всього, що завантажуватиме CLI. Крок, який не можна скасувати, — поява версії в npm — отримує другий ключ, якого немає в жодного workflow. Ставте реліз у staging із CI через trusted publishing у npm, який використовує короткоживучий токен OIDC замість збереженого, і нехай супровідник схвалює версію в staging із двофакторною автентифікацією. Закріплюйте за вмістом усе, що CLI отримує під час виконання, і звіряйте це з двома джерелами. Створюйте теги Git і GitHub Releases лише після того, як npm почав віддавати версію, бо версію в staging можуть так і не опублікувати. І стежте за моментами, коли інструмент релізу за власними правилами вирішує, що робити нічого: одного разу порожній changeset узагалі не дав поставити одну з наших бет у staging, і кожне завдання при цьому було зеленим.

## Чому реліз — це не злиття

Злиття можна скасувати іншим злиттям. Реліз — ні, і на це є три причини.

**Номер версії витрачено.** Політика npm щодо зняття з публікації (unpublish) категорична: «Щойно `package@version` використано, ви вже ніколи не зможете використати його знову». І далі: «Це так, навіть якщо цей пакет знято з публікації». Саме зняття з публікації дозволене в перші 72 години лише тоді, коли від вашого пакета не залежить жоден інший пакет у реєстрі, а пізніше — лише за суворіших умов; для всього іншого npm радить позначати версію як застарілу (deprecate). Поганий реліз виправляють уперед, новою версією, а погана версія лишається в реєстрі для всіх, хто її закріпив.

**Клієнти пишуть під нього скрипти.** Публічний інтерфейс CLI ширший за експорти бібліотеки: його команди, прапорці й значення за замовчуванням, коди виходу, машинозчитуваний вивід, файли, які він записує, і середовища виконання, у яких він запускається. Змінене значення за замовчуванням чи новий код виходу ламає завдання CI, якого ви ніколи не побачите.

**Платний CLI має більше ніж одну рухому частину.** Наш перевіряє ліцензію на saasyland.com щоразу, коли створює проєкт, і завантажує шаблони, з яких генерує проєкт, — один бандл на реліз — через API ліцензій вебсайту. Реліз — це пакет у npm, плюс бандл шаблонів у сховищі, плюс контракт із сервером. Усі три мають узгоджуватися з першої хвилини, коли клієнт може встановити версію.

ШІ-агенти змінюють те, де зосереджено ризик. Вони швидкі й ретельні в оборотних частинах: пишуть changeset, тримають pull request версії актуальним, редагують workflow, пишуть нотатки до випусків <RepositoryFact name="languages" /> мовами, перевіряють реєстр після релізу. У незворотній частині вони рівно так само впевнені, як і в усьому іншому. Тож принцип цього допису простий: дайте агентам робити все аж до реєстру, зробіть кожен крок перед ним безпечним для повторного запуску й поставте ключ у руках людини на єдиний крок, який не є ні оборотним, ні повторюваним.

Кілька слів про налаштування, щоб ви могли зіставити його зі своїм. CLI SaaSy Land — це три пакети npm, `saasyland`, `create-saasyland` і `@saasyland/stack`, які випускаються з приватного репозиторію на GitHub за допомогою Changesets 3 і GitHub Actions. Станом на 25 листопада 2026 року попередні версії виходять у тезі <RepositoryFact name="cliReleaseChannel" /> в npm, остання з них — 0.1.0-beta.5 від 20 листопада, а клієнти запускають <RepositoryFact name="cliPackageSpec" />; `latest` досі містить заглушку `0.0.0`, яка зарезервувала назви. Агенти — це сесії Claude Code: головний агент і виконавці, яким він пише брифи, і вони повністю відповідають за CLI. Коли власник передав його їм, він попросив «версіонування, журнал змін і все інше настільки професійно, наскільки можливо», з релізами «партіями, які справді мають сенс». Він схвалює кожну публікацію.

## Конвеєр одним поглядом

Кожен рядок — це крок релізу, те, що цей крок може кудись записати, і те, що його зупиняє. Решта допису проходить рядками в тому порядку, у якому вони можуть зламатися.

| -------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------- |

| Злиття в `main` або `beta` | Вибирається режим: version, publish або none                                        | Нічого                              | Немає чого публікувати                                                                 |

## Версіонування, на яке може покластися клієнт

### Запишіть, що для CLI означає несумісна зміна

Семантичне версіонування допомагає лише тоді, коли ви записали, що саме є вашим публічним інтерфейсом. Наша політика релізів перелічує, що вважається несумісною зміною для CLI:

- команду, прапорець чи значення прапорця прибрано або перейменовано, або змінено значення за замовчуванням;
- інший код виходу в тій самій ситуації;
- поле виводу `--json` прибрано, перейменовано або змінено його тип, тоді як нове поле несумісною зміною не є;
- зміна маніфесту проєкту, якої не може прочитати старіший CLI;
- вища мінімальна версія Node;
- прибраний або змінений експорт спільного пакета;
- зміна, яку власні правила API ліцензій називають несумісною.

До 1.0 мінорна версія несе нові функції або несумісну зміну, а патч — лише виправлення. API ліцензій дотримується тієї самої дисципліни на власній межі. У межах `v1` вебсайт може додати поле відповіді, ендпоінт чи код помилки, а CLI ігнорує поля, яких не знає; усе інше вимагає `v2`, яку обслуговують поруч із `v1`, доки її викликає хоч один підтримуваний CLI. [Перший допис цієї серії](/blog/ai-coding-agent-guardrails) розповідає, як опублікований CLI надсилав поле, якого робочий вебсайт ще не приймав, і чому зміна контракту тепер спершу виходить на сервері.

### Changeset — це нотатка до випуску для клієнтів

Кожен pull request, що змінює опублікований пакет, додає changeset, а CI відхиляє той, що не додає: `changeset status --since=origin/<base>` падає, коли пакет змінився без нього. Важливіше правило стосується вмісту. Changeset — це нотатка до випуску для клієнта: одне-два прості речення про те, що для нього змінюється і що він має зробити, з командами й прапорцями, записаними так, як він їх набирає. «Виправлено помилку в парсері прапорців» нічого не каже клієнту. Ось нотатка до 0.1.0-beta.5 у тому вигляді, у якому її виводять журнал змін, опублікований разом із пакетом у npm, і публічні [нотатки до випусків](/docs/cli/releases):

> **Несумісна зміна:** `--billing lemonsqueezy` більше немає, бо Lemon Squeezy закривається: він не приймає нових реєстрацій із 16 листопада 2026 року й припиняє роботу 31 березня 2027 року. `--billing polar` і `--billing stripe` залишаються, а `init --billing lemonsqueezy` тепер завершується з кодом <RepositoryFact name="cliExitUsage" />, як і будь-яке інше значення, якого `--billing` не має.

Те, як сформульовано правило, визначає, що створюють агенти. Якщо агенту сказати лише «додати changeset», він зазвичай пише «Рефакторинг парсера прапорців». Якщо сказати йому, що changeset — це те, що клієнт читає в журналі змін, він пише нотатку, наведену вище. Зміна, якої клієнти не можуть помітити, як-от рефакторинг чи новий тест, отримує порожній changeset. Саме цей запасний вихід став джерелом другого інциденту в цьому дописі.

### Одна версія для пакетів, що виходять разом

Три пакети утворюють фіксовану групу Changesets, у якій «усі пакети групи отримують підвищення версії й публікуються разом, навіть коли змін немає». Тож `saasyland@0.1.0-beta.5` завжди виходить разом із `@saasyland/stack@0.1.0-beta.5`, і клієнту, звіту про помилку та відповіді підтримки потрібен один номер. Ціну видно в журналі змін: пакет, якому нічого сказати про себе, однаково отримує реліз, і нотатки до випусків на нашому вебсайті виводять для нього «У цьому випуску змін немає.», щоб не лишати прогалини, схожої на недогляд.

### Випускайте релізи партіями й притримуйте pull request версії

Changesets тримає відкритим pull request Version Packages і перебудовує його в міру того, як зливаються changeset. Цей pull request — бар’єр релізу: злити його означає ухвалити рішення про реліз. Ми випускаємо релізи цілісними партіями, ніколи не по одному на pull request. У `main` pull request Version Packages для 0.1.0 відкритий із 14 листопада й 25 листопада містив 24 changeset; його зіллють, коли стабільна партія буде повною й задокументованою.

Попередні версії виходять із гілки `beta` в режимі пререлізу Changesets. Його документація попереджає, що «Пререлізи дуже складні!» і що «Помилки можуть призвести до станів репозиторію й публікації, які дуже важко виправити». Обидва речення для нас справдилися, як ви побачите далі. Якщо ви користуєтеся режимом пререлізу, тримайте його в окремій гілці, тримайте історію цієї гілки лінійною, щоб теги релізів вказували на історію, яку можна прочитати, і переносьте зміни з `main` так, щоб їх можна було переглянути. Ми переносимо коміти з `main` через cherry-pick у гілку, створену від `beta`, і зливаємо її через squash, тож `beta` ніколи не отримує коміту злиття.

### README в npm — частина релізу

До першого стабільного релізу `latest` — це заглушка, тож README, який пропонує `npx saasyland init`, запускає заглушку, де не працює жодна команда. У 0.1.0-beta.1 запаковані README робили саме це, а команди `create` без тегу теж підтягували `latest`. Тепер smoke-тест читає README всередині кожного запакованого tarball і падає, коли команда називає один із пакетів без dist-тегу або з іншим. Dist-тег, якого очікують тести, оголошено один раз, а його зміна — це крок першого стабільного релізу. Власний [посібник із CLI](/docs/cli) на вебсайті виводить свої команди з однієї константи, <RepositoryFact name="cliPackageSpec" />, із тієї самої причини.

## Staged publishing: ключ людини — у реєстрі

### Що таке staging

Staged publishing у npm «додає етап схвалення, перш ніж пакети з’являться в реєстрі npm». CI запускає `npm stage publish`, що «не вимагає 2FA», і версія чекає в зоні staging, доки її не схвалить супровідник: «Перевірку 2FA буде запитано незалежно від того, схвалюєте ви пакет у CLI чи на npmjs.com». Відхилення версії в staging теж вимагає другого фактора. Dist-тег фіксується тоді, коли версію ставлять у staging: «Тег — незмінна властивість пакета в staging». Staging вимагає npm 11.15.0 або новішого; наше завдання staging використовує npm, що постачається з Node 26.13.1, тобто npm 11.20.0, і виводить у своєму підсумку версію npm, якою ставило пакети в staging.

npm спрямовує всіх у цей бік. Його журнал змін за вересень 2026 року каже, що «npm планує в січні 2027 року прибрати пряму публікацію через токени, які обходять 2FA», і пропонує токени лише для staging як шлях міграції для автоматизації, яка ще не може перейти на trusted publishing. Наші запуски staging записують у лог повідомлення npm: «Токени npm, які обходять 2FA, обмежуються для змін облікового запису й прямої публікації».

### Чому бар’єр стоїть у npm, а не в CI

GitHub може змусити завдання чекати на рецензента через середовища (environments), а посібник Changesets пропонує «створити середовище з обов’язковими рецензентами, які схвалюють запуск завдання публікації». Ми натомість поставили ключ у npm, і на це дві причини. Він захищає саму незворотну річ: що б не зробив workflow і що б не злив агент, ніщо не стає публічним, доки супровідник не схвалить саме цю версію в staging. І він спирається на другий фактор супровідника в npm, якого не може мати жоден workflow, агент чи токен GitHub. Схвалення в CI захищає завдання, і щойно його надано, це завдання може опублікувати все, що зібрало. До того ж GitHub пропонує обов’язкових рецензентів для приватних репозиторіїв лише в тарифах Enterprise, тож для багатьох команд реєстр — єдине місце, де такий бар’єр узагалі доступний.

### Changesets ще не вміє staging, тож ставте в staging за його планом

Посібник Changesets каже прямо: «Наразі Staged Publishing не працює з Changesets, тому поки що слід використовувати Trusted Publishing». Його оголошення про v3 каже, що staging з’явиться в «наступному оновленні функцій». А доти його action публікації запускає `npm publish`, і довірений видавець, якому дозволено лише staging, таку публікацію відхиляє. Тож наше завдання staging робить те, що зробив би action, лише з однією зміненою командою. Воно читає план публікації, який `changeset pack` записує поруч із tarball, і ставить кожен пакет у staging із тим доступом і dist-тегом, які вибрав Changesets: `beta` в режимі пререлізу, `latest` в інших випадках.

Для кожного пакета з цього плану завдання спершу запитує npm через публічний `npm view`, якому не потрібні облікові дані, чи реєстр уже віддає саме цю версію. Якщо ні, воно запускає `npm stage publish` для запакованого tarball із доступом і dist-тегом із плану та прапорцем `--json` і бере id у staging з відповіді npm. Кожен пакет завершується рівно одним із трьох результатів, і саме це робить завдання безпечним для повторного запуску, а це важливо, бо завдання релізу — саме те, яке найбільше хочеться перезапустити після збою раннера:

- **Уже в npm:** пакет пропускається. Push у `main` після релізу чи повторний запуск не намагається опублікувати вдруге.
- **Поставлено в staging попереднім запуском:** npm відповідає кодом 409, а завдання повідомляє про це й іде далі. Токен trusted publishing може ставити в staging і публікувати, але npm каже, що «Короткоживучі токени не можуть запускати підкоманди `npm stage`», тож завдання не може переглянути список staging, щоб знайти попередній id; його підсумок підказує тому, хто схвалює, де шукати.
- **Будь-що інше:** завдання зупиняється перед наступним пакетом.

Підсумок завдання — це робочий список того, хто схвалює: по рядку на пакет, з його версією, dist-тегом, id у staging і точною командою, яка його схвалює. Три пакети — це один реліз, тож усі три схвалюють разом. Набір для релізу наприкінці цього допису містить загальну версію цього завдання, написану за документацією npm, для репозиторію без Changesets.

### Що записує реєстр

Для 0.1.0-beta.5 метадані npm називають видавцем GitHub Actions — через довіреного видавця — і називають супровідника, який схвалив версію. Її поставили в staging об 11:25 UTC 20 листопада, а публічною вона стала об 11:44. Цей запис і є журналом аудиту: який workflow створив байти і яка людина їх випустила.

## Trusted publishing: жодного токена, який може витекти

### Короткоживучі облікові дані лише в одному завданні

Trusted publishing дає CI змогу публікувати, «використовуючи короткоживучі, криптографічно підписані токени», які отримують через OIDC провайдера CI замість збереженого токена npm. Він вимагає npm 11.5.1 і Node 22.14.0 або новіших, а на GitHub «Критична вимога — дозвіл id-token: write». На боці npm довірений видавець (trusted publisher) називає організацію чи користувача GitHub, репозиторій, файл workflow і, за бажанням, середовище. Ще два налаштування зачиняють решту дверей:

- **Довірений видавець може ставити в staging і нічого більше.** У CLI npm це `npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish` без `--allow-publish`. Для довіреного видавця, як каже документація npm, «`npm stage publish` дозволено завжди», а пряма публікація й зміни dist-тегів — окремі опції, вимкнені, доки супровідник їх не ввімкне.
- **Доступ до публікації вимагає двофакторної автентифікації й забороняє токени.** npm зазначає, що це «впливає лише на традиційну автентифікацію токенами», тож довірений видавець і далі працює, тоді як жоден токен, хоч би де його зберігали, не може публікувати.

Довіреного видавця налаштовують у параметрах пакета на npmjs.com, тож нова назва пакета коштує одного ручного кроку: власник вручну публікує заглушку `0.0.0` із двофакторною автентифікацією, а потім додає довіреного видавця й налаштування доступу. Ось чому `latest` сьогодні містить `0.0.0`.

На боці GitHub workflow починається з `permissions: {}`, і кожне завдання просить те, що йому потрібно. Посібник Changesets каже це прямо: «переконайтеся, що `id-token: write` задано лише для завдання, якому треба публікувати».

| Завдання                                    | Дозволи                                                   | Навіщо                                                          |
| ------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------- |
| Вибір режиму релізу                         | `contents: read`                                          | Читає changeset в очікуванні                                    |
| Відкриття pull request версії               | `contents`, `pull-requests` і `actions` на запис          | Надсилає гілку релізу, відкриває pull request, запускає його CI |
| Збірка, перевірка й пакування               | `contents: read`                                          | Збирає, тестує й пакує                                          |
| Запуск зібраних bin-файлів, дев’ять завдань | `contents: read`                                          | Збирає й запускає bin-файли                                     |
| Staging у npm                               | `contents: read` і `id-token: write`, захищене середовище | Обмінює токен OIDC з npm і вивантажує бандл шаблонів            |
| Створення тегів і Releases                  | `contents: write`                                         | Створює теги й Releases                                         |

Завдання staging — єдине, яке може запитати токен OIDC, і єдине, що використовує захищене середовище. Це середовище зберігає облікові дані сховища шаблонів, і розгортати в нього можуть лише гілки релізів. GitHub робить секрети середовища «доступними лише для завдань workflow, які використовують це середовище», тож жодне інше завдання й жоден запуск workflow з будь-якої іншої гілки не можуть їх прочитати.

### Токен у checkout — теж дозвіл

`actions/checkout` зберігає токен завдання в локальній конфігурації Git, «щоб виконувати автентифіковані команди git», якщо не задати `persist-credentials: false`. Ми задали false в кожному завданні, і перший pull request Version Packages так і не відкрився: коли Changesets надсилав гілку релізу, Git повідомив «could not read Username for 'https://github.com'», тобто не зміг прочитати ім’я користувача. Виправлення повернуло токен цьому одному завданню, єдиному, що робить push. Принцип найменших привілеїв — властивість кожного завдання, а не одне налаштування, скопійоване по всьому файлу.

### Збій, якого npm не зміг пояснити

Перша бета потрапила в npm через дванадцять годин після злиття її pull request версії. 14 листопада о 06:18 UTC завдання staging упало з власною помилкою npm:

```text
npm error code ENEEDAUTH
npm error need auth This command requires you to be logged in to https://registry.npmjs.org/
```

Повідомлення каже вам увійти. Справжньою причиною був збій обміну токена OIDC, і npm записує цю причину на рівні verbose, у лог налагодження на раннері, який видаляється разом із завданням. Ми налаштували завдання staging так, щоб після кожного збою воно вивантажувало `~/.npm/_logs/` як артефакт, і лог наступного збою назвав причину: npm не знайшов довіреного видавця, який відповідав би репозиторію, workflow і середовищу запуску. Документація npm попереджає саме про це: «npm не перевіряє конфігурацію вашого довіреного видавця, коли ви її зберігаєте», і «Усі поля чутливі до регістру й мають бути точними». Щойно налаштування на npmjs.com почали відповідати workflow, повторний запуск невдалого завдання поставив 0.1.0-beta.0 у staging о 18:24, а власник схвалив її через чотири хвилини.

Урок ширший за npm. Коли шар автентифікації ламається, його повідомлення про помилку зазвичай описує запасний варіант, який він спробував останнім, а не крок, що зламався першим. Зберігайте лог налагодження інструмента з кожного невдалого завдання релізу, з коротким терміном зберігання, і читайте його, перш ніж щось змінювати.

### Атестації походження потребують публічного репозиторію

У публічному репозиторії trusted publishing дає вам атестації походження (provenance) безкоштовно: npm «автоматично генерує й публікує атестації походження», але лише тоді, коли ви «Публікуєте з публічного репозиторію» і «Публікуєте публічний пакет», а «Генерація атестацій походження не підтримується для приватних репозиторіїв». Наш CLI комерційний, а його репозиторій приватний, тож його пакети не мають атестацій походження. Натомість вони мають підпис реєстру npm, який може перевірити будь-хто: у чистому каталозі з установленим `saasyland@0.1.0-beta.5` команда `npm audit signatures` повідомляє «1 package has a verified registry signature», тобто що один пакет має перевірений підпис реєстру. Якщо ваш вихідний код публічний, увімкніть атестації походження й розкажіть користувачам, як їх перевіряти. Якщо приватний, так і скажіть, а не дозволяйте словам «trusted publishing» натякати на гарантію, якої у вас немає.

## Закріпіть усе, що завантажує CLI

### Шаблони — частина релізу, але не пакета

`saasyland init` генерує проєкт із шаблонів, яких сам не містить. Після перевірки ліцензії він завантажує бандл шаблонів свого релізу через API ліцензій вебсайту. Це тримає платні шаблони поза публічним tarball у npm і дає кожному релізу другий артефакт, про який npm нічого не знає. Звідси два правила: бандл, який отримує клієнт, має бути саме тим, з яким реліз тестували, і він має існувати раніше, ніж хтось зможе встановити реліз.

### Обчислюйте дайджест вмісту, а не стиснення

Бандл збирається детерміновано: шари впорядковано за id, файли — за шляхом, ключі — у фіксованому порядку, і з файлової системи не записано нічого, крім вмісту кожного файлу та його біта виконання. Його дайджест — це SHA-256 JSON усередині архіву, а не байтів gzip, бо Node і Bun стискають той самий JSON у різні байти. Коли ми це виміряли, дайджести архівів різнилися, а дайджести вмісту — ні. Дайджест стисненого файлу ідентифікує компресор; він зламався б, щойно середовище виконання оновило б свій zlib, і клієнту сказали б, що його завантаження пошкоджене.

### Закріплюйте під час версіонування, перевіряйте перед вивантаженням, вивантажуйте перед staging

Закріплення записують у pull request Version Packages. Скрипт версії запускає `changeset version`, потім збирає бандл нової версії й додає його дайджест до файлу закріплених дайджестів усередині CLI, тож рецензент бачить підвищення версії й закріплення поруч, а реліз несе дайджест у власному коді. Закріплення відмовляється змінювати дайджест, який уже закріплено. Кожен CLI також несе закріплені дайджести всіх попередніх релізів, бо `update`, коли з’явиться, знову генеруватиме реліз, з якого створено проєкт, як базу для свого злиття.

Під час релізу завдання staging знову збирає бандл і падає, якщо його дайджест не збігається із закріпленим. Потім воно вивантажує архів, із дайджестом у метаданих об’єкта, у сховище, яке читає API ліцензій, і читає кожен об’єкт назад: розмір, тип вмісту, метадані й дайджест вмісту. Лише після цього воно щось ставить у staging у npm, бо опублікований CLI ніколи не має запитувати бандл, якого немає. Вивантаження відхиляє будь-який архів, що не є закріпленим бандлом, тож повторний запуск ніколи не змінить того, що віддає реліз.

### Перевіряйте двічі, за двома джерелами

Вебсайт відповідає на запит бандла короткоживучою підписаною URL-адресою, дійсною протягом <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, а також розміром і дайджестом бандла, які він читає із заголовка збереженого об’єкта, не відкриваючи архіву:

```ts title="src/modules/license/license.api.ts"
const storedBundle = async (version: string): Promise<StoredBundle> => {
  const key = bundleObjectKey(version)
  const object = await env.BUNDLES.head(key)

  if (object === null) {
    return { error: { code: API_ERROR.VERSION_NOT_FOUND, version }, success: false }
  }

  const metadata = bundleMetadataSchema.safeParse(object.customMetadata)

  if (!metadata.success) {
    throw new Error(`${key} has no ${BUNDLE_METADATA.SHA256} digest in its custom metadata`, { cause: metadata.error })
  }

  return { bundle: { sha256: metadata.data[BUNDLE_METADATA.SHA256], size: object.size }, success: true }
}
```

Об’єкт без дайджесту не віддається: API відповідає `serviceUnavailable`, а лог називає об’єкт. Потім CLI завантажує архів, читає не більше оголошеного розміру й відхиляє його, хіба що розмір і дайджест збігаються з відповіддю API, а дайджест — ще й із закріпленим, вкомпільованим у реліз. Розбіжність завершується з кодом <RepositoryFact name="cliExitProtocol" /> і нічого не записує; навіть правильне завантаження записується в каталог проєкту за один раз, тож перерваний запуск нічого по собі не лишає.

Навіщо обидві перевірки? Дайджест від API захищає завантаження. Закріплення захищає реліз від його ж сервера: хоч би що лежало в сховищі під ключем версії, опублікований CLI запускає лише ті шаблони, з якими тестували його реліз. Кожне джерело перевіряє інше, і жодному не довіряють окремо. Документація вебсайту повністю описує ендпоінт і правила публікації бандлів у розділі [API ліцензій для CLI](/docs/features/cli-licence-api#publishing-bundles).

### Загальне правило

Усе, що ваш CLI отримує під час виконання, — шаблони, схеми, бінарні файли чи список плагінів — є частиною релізу. Версіонуйте це разом із релізом, закріплюйте за вмістом у коді, який публікуєте, вивантажуйте, перш ніж пакет можна буде встановити, і зберігайте кожну версію, яку ще може запитати підтримуваний реліз.

## Зберіть один раз, а потім тестуйте те, що постачаєте

### Пакуйте один раз і ставте в staging саме ці байти

Завдання пакування запускає перевірки форматування, лінтера й типів, тести з повним покриттям і smoke-тести, а потім `changeset pack` записує tarball і план публікації в артефакт. Завдання staging завантажує цей артефакт; воно ніколи нічого не збирає. Байти, які npm ставить у staging, — це байти, які створило те завдання.

### Пакувальник, через який просочився синтаксис робочого простору

0.1.0-beta.1 потрапила в npm зі специфікаторами `catalog:` у `devDependencies` усіх трьох пакетів, загалом шість записів, як досі показує реєстр. Робочий простір Bun записує спільні версії як `catalog:`. Changesets 3 пакує лише з npm, pnpm або Yarn, а в робочому просторі Bun він переходив на `npm pack`, який копіює ці специфікатори в запакований `package.json` нерозв’язаними. Нічого не зламалося, бо ніхто не встановлює залежності розробки CLI. Такий самий витік у `dependencies` зламав би кожне встановлення релізу.

Виправлення першопричини містить `bun patch` для Changesets, що пакує через `bun pm pack`, а той записує версію, до якої розв’язується кожен специфікатор, і відмовляється пакувати той, якого не може розв’язати. Патч — це та половина відкритого upstream pull request [changesets/changesets#2334](https://github.com/changesets/changesets/pull/2334), яка стосується пакування; сам pull request додає Bun до Changesets, і патч приберуть, коли реліз міститиме цю зміну. Виправленим це тримає тест: smoke-тести пакують кожен опублікований пакет власною командою релізу й падають на будь-якому `catalog:` чи `workspace:`, що лишився в будь-якому полі залежностей. Тестуйте tarball, а не робочий простір. Функції робочих просторів вашого менеджера пакетів невидимі для тесту, який працює з вихідного коду.

### Бар’єр перед staging на кожній платформі

Клієнти запускають CLI під Node і Bun, на Linux, macOS і Windows. Pull request запускають зібрану програму лише на Linux, щоб заощадити хвилини; запуск релізу перевіряє кожну платформу, на тому самому коміті, який от-от поставить у staging. Дев’ять завдань збирають пакети й запускають bin-файли під Node 22.12.0, 24 і 26 на кожній системі, а також під Bun на кожному раннері.

Дев’ять завдань — це одна матриця: три системи на три версії Node, починаючи з найстарішої версії Node, яку підтримує CLI. Два налаштування перетворюють цю матрицю на бар’єр. Завдання staging перелічує в `needs` і завдання пакування, і матрицю та не має власного `if:`, тож GitHub пропускає його, якщо хоч одне з них не завершилося успішно; умова на кшталт `if: always()` у завданні staging непомітно звела б це нанівець. А матриця задає `fail-fast: false`, тож збій в одній комбінації не скасовує решти, і запуск показує кожну платформу, що зламалася, а не лише першу.

Бар’єр, який ви жодного разу не бачили закритим, — це надія, а не бар’єр. Перш ніж довіритися цьому, ми запустили справжній workflow релізу в тимчасовій гілці, з коміту, рівнозначного злитому pull request Version Packages, і з однією комбінацією, яку навмисно змусили впасти: Windows під Node 26. Усі інші завдання пройшли, а завдання staging пропустили, щойно завершилася остання комбінація. Пробний запуск не зміг би нічого опублікувати, навіть якби бар’єр був хибним, бо середовище, якого потребує завдання staging, дозволяє розгортання лише з гілок релізів; після цього npm показував ті самі версії, що й раніше, і не з’явилося жодного тегу чи Release.

Перенесення запусків на macOS і Windows з кожного злиття на сам реліз скоротило оплачувані хвилини злиття в `main` на третину–половину, за нашим вимірюванням, зробленим під час цієї зміни, ціною, яку платять раз на реліз. Чого бар’єр не робить, перелічено ближче до кінця цього допису: він запускає `--version` і `--help`, а не повну генерацію проєкту, і збирає на кожному раннері замість того, щоб установлювати tarball зі staging.

### Спершу запитайте npm, потім ставте тег

Ми перенесли теги й Releases в окреме завдання, яке спершу запитує реєстр. Для кожного опублікованого пакета воно перевіряє три речі: що `CHANGELOG.md` пакета має розділ для версії з checkout, який пише лише pull request Version Packages; що npm віддає саме цю версію, через публічний `npm view`, якому не потрібен токен; і чи вже існує тег. Лише коли кожен пакет проходить дві перші перевірки й тегу бракує, воно запускає `changeset git-tag` через action Changesets, який надсилає теги й створює Release з кожного запису журналу змін. Інакше воно нічого не записує, а його підсумок пояснює чому.

Обидві перевірки навмисно прості. Версія вважається такою, яку npm віддає, лише тоді, коли `npm view` виводить саме цю версію, тож і відсутня версія, і мережева помилка, і неочікувана відповідь означають, що версію не віддають, і жоден тег не створюється. Тег вважається наявним лише тоді, коли Git знаходить його повне посилання (ref), тож гілка з такою самою назвою не може видати себе за нього. Набір для релізу наприкінці цього допису містить загальну версію цієї перевірки для одного пакета.

Завдання запускається трьома способами: одразу після staging, коли воно зазвичай бачить, що версія ще чекає; вручну, що головний агент робить, щойно власник схвалює реліз; і раз на день як запасний варіант. Його запуски в одній гілці мають спільну групу паралельності й стають у чергу, а не перекриваються, тож два запуски ніколи не ставлять теги одночасно, а ще воно спершу отримує всі теги, тож створює лише те, чого бракує, і його можна запускати скільки завгодно разів.

0.1.0-beta.5 стала першим релізом, що пройшов через нього. Завдання записів у її запуску релізу виконалося об 11:25 UTC і з’ясувало, що npm версію ще не віддає. npm почав віддавати її об 11:44:37; головний агент запустив workflow записів об 11:45:27, а три Releases з’явилися об 11:45:51.

### Розклад — це страхувальна сітка, а не крок

Щоденний запасний запуск навчив нас двох речей про подію `schedule` у GitHub. По-перше, «Заплановані workflow запускаються на останньому коміті гілки за замовчуванням», а теги бети мають вказувати на коміт у `beta`. Тож заплановане завдання саме тегів не ставить: воно читає гілки з власного тригера workflow релізу й запускає workflow записів на кожній із них через `workflow_dispatch`, щоб кожен запуск ставив теги у своїй гілці. По-друге, розклад приблизний. GitHub каже, що подія «може затримуватися в періоди високого навантаження» і що «деякі завдання в черзі можуть бути відкинуті». Наш запуск заплановано на ранні ранкові години за UTC, і з 21 по 24 листопада він стартував приблизно на вісім–одинадцять годин пізніше. Заплановане завдання може підхопити те, про що людина забула. Воно ніколи не має бути кроком, на який чекає реліз.

## Порожній changeset, який заблокував реліз

[Перший допис цієї серії](/blog/ai-coding-agent-guardrails) коротко розповідає цю історію як приклад агента, що виконує перевірку за буквою. Ось повна послідовність, бо вона показує клас збоїв, який легко пропустити: інструмент релізу, що вирішує, цілком правильно за власними правилами, що робити нічого.

### Три злиття за 81 секунду

Усе сталося в `beta` 20 листопада, за UTC:

1. **11:17:12.** Pull request переніс два коміти з `main`. Його запуск релізу відкрив pull request Version Packages для 0.1.0-beta.5.
2. **11:18:06.** Злили pull request, який додавав до трьох журналів змін нотатку «Не опубліковано в npm». Правка журналу змін вважається зміною пакета, тож перевірка changeset вимагала changeset, і pull request додав порожній, точно як приписувала політика релізів для зміни, якої клієнти не можуть помітити.
3. **11:18:33.** Pull request версії злили через 27 секунд. Його зібрали ще до злиття виправлення журналів змін, тож порожнього changeset він не поглинув.
4. **11:19.** Запуск релізу на цьому коміті злиття вибрав режим і пропустив усі інші завдання. 0.1.0-beta.5 отримала версію в `beta`, але в staging не потрапила, і кожне завдання було зеленим.

Тим часом запуск релізу на коміті злиття виправлення журналів змін, що стояв у черзі за іншими, відкрив другий pull request Version Packages з коміту, який уже став історією; його закрили без злиття.

### Чому режимом був «none»

`changesets/action/select-mode` повертає один із трьох режимів: version, publish або none. Ось це рішення в його публічному вихідному коді у v2.1.2, у форматуванні цього сайту:

```ts
if (changesets.length > 0) {
  const hasNonEmptyChangesets = changesets.some((changeset) => changeset.releases.length > 0)
  if (hasNonEmptyChangesets) {
    return { mode: "version" }
  }
  return { mode: "none" }
}
```

Якщо хоч один changeset очікує і всі вони порожні, режимом стає `none`, і план публікації, який виявив би, що 0.1.0-beta.5 в npm немає, так і не обчислюється. За власною логікою action це розумно: порожній changeset означає «нічого не випускати». У поєднанні з pull request версії, який злили, не перебудувавши, це дало реліз, який створили, але так і не випустили.

### Виправлення й правила

Ще один pull request прибрав порожній changeset через п’ять хвилин. Наступний запуск вибрав `publish`, поставив 0.1.0-beta.5 у staging об 11:25, а власник схвалив її об 11:44. Наша політика тепер каже, що порожнім changeset місце лише в `main`, а зміна, зроблена безпосередньо в `beta`, якої клієнти не можуть помітити, як-от виправлення журналу змін, не має changeset, і її невдала перевірка changeset — єдиний дозволений збій.

Два правила підходять будь-якій команді:

- **Зливайте pull request версії лише тоді, коли його зібрано з поточного head гілки.** Якщо після його останнього оновлення щось злили, зачекайте, доки workflow релізу його перебудує.
- **Ставтеся до «немає що робити» як до результату, який треба перевірити.** Запуск релізу, який не вибирає жодної роботи, коли версії з гілки немає в реєстрі, зазнав невдачі, навіть якщо кожне завдання зелене.

Перше правило в нас записане, а друге ще не стало перевіркою. І наше записане правило про порожні changeset стосується гілки, де це сталося, тоді як сам механізм від режиму пререлізу не залежить: така сама гонка в `main` лишила б той самий порожній changeset в очікуванні.

## CI для pull request, з якого ви випускаєте реліз

### GitHub не запускає workflow на push власного токена

Завдання версії надсилає гілку Version Packages з `GITHUB_TOKEN` workflow, а документація GitHub каже, що «події, запущені через `GITHUB_TOKEN`, не створюють нового запуску workflow», з одним винятком, який тут важливий: «події `workflow_dispatch` і `repository_dispatch` завжди створюють запуски workflow». Тож pull request, який ми от-от мали випустити, не показував жодних перевірок; щоб отримати запуск на одному з них, агент вручну закрив його й відкрив знову. Виправлення лишає токен за замовчуванням і запускає CI саме. Одразу після того, як Changesets відкриває або оновлює pull request версії, те саме завдання визначає гілку цього pull request і запускає на ній workflow CI командою `gh workflow run`; це працює, бо workflow CI приймає не лише `pull_request`, а й `workflow_dispatch`.

Завдання отримує `actions: write` для цього єдиного виклику, а запуски перевірок прив’язуються до head-коміту гілки, тож їх видно в pull request. Токен GitHub App теж запустив би CI, але для нього потрібні застосунок і ще один секрет; тут не потрібно ні того, ні іншого.

### Ставте запуски релізу в чергу, а не замінюйте їх

Групи паралельності (concurrency groups) у GitHub Actions раніше тримали лише один запуск в очікуванні: «Якщо до групи входив інший запуск, запуск в очікуванні скасовувався й замінювався». Для workflow релізу це хибно, бо три швидкі push у `beta` відкинули б середній. Із травня 2026 року `queue: max` дає групі змогу «ставити в чергу кілька запусків в очікуванні й обробляти їх послідовно», до 100, коли `cancel-in-progress` має значення false.

Загальний приклад за документацією GitHub про паралельність — для workflow релізу, який ніколи не має втрачати запуски:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false
  queue: max
```

Наш workflow релізу працює саме так, тож кожен push у гілку релізу отримує власний повний запуск, по черзі. Історія з порожнім changeset показує інший бік цієї гарантії: запуск із черги ухвалює рішення за власним комітом, навіть коли цей коміт на момент запуску вже став історією. Черга зберігає кожен запуск; вона не робить рішення старого запуску актуальним.

## У кого який ключ

Агенти ведуть реліз; власник тримає те, що не можна скасувати.

| Робота                                   | Агенти                                                            | Власник                                                                             |
| ---------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Changeset і pull request версії          | Пишуть їх, перевіряють нотатки й зливають, коли партія повна      | Нічого                                                                              |
| Workflow релізів                         | Пишуть зміну й доводять її, наприклад пробним запуском            | Схвалює кожну зміну у файлах, що визначають, що потрапляє в npm, процитованим «так» |
| Збірка, тести, пакування й staging       | Нічого: це робить CI на коміті злиття                             | Нічого                                                                              |
| Схвалення чи відхилення версії в staging | Передають точні id у staging                                      | Схвалює або відхиляє з двофакторною автентифікацією                                 |
| Теги й GitHub Releases                   | Запускають workflow записів одразу після схвалення                | Нічого                                                                              |
| Нова назва пакета                        | Готують її в `main` і записують точні кроки                       | Публікує заглушку й налаштовує для неї довіреного видавця                           |
| Погана версія                            | Пишуть повідомлення про застарілість і виправлення                | Запускає `npm deprecate` із двофакторною автентифікацією                            |
| Нотатки до випусків і перевірка          | Встановлюють із npm у чистий каталог, пишуть нотатки всіма мовами | Переглядає                                                                          |

Workflow релізу, конфігурація Changesets і поля пакетів, які визначають, що потрапляє в npm, є в списку для рев’ю людиною в репозиторії CLI, тож кожен pull request, що їх змінює, як-от той, що змінив спосіб запису релізів, цитує письмову згоду власника. Той самий файл інструкцій каже агентам ніколи не публікувати й не запускати `npm trust`. І жоден агент не має облікових даних npm, бо їх не існує: кожен пакет забороняє публікацію токенами, а єдине, що може автоматично ставити в staging, — це сам workflow релізу.

Перевірка не закінчується релізом. Набір тестів шляху клієнта на вебсайті працює за розкладом <RepositoryFact name="journeySchedule" /> в UTC: він купує кожен тариф у пісочниці Polar на preview-розгортанні, а потім проводить опублікований CLI, прямо з npm, через активацію, ліміти пристроїв, деактивацію й повернення коштів, яке завершує ліцензію:

```ts title="e2e/journey/cli.ts"
const child = spawn("env", ["-i", ...variables, PACKAGE_MANAGER.NPM.exec, "--yes", CLI_PACKAGE_SPEC, ...inputs, "--json"], { cwd: home })
```

Принцип той самий, з якого почався цей допис. Агенти можуть робити все, що оборотне або що впіймає пізніший крок. Людина тримає кроки, які не є ні тим, ні іншим, через фактор, якого агенти мати не можуть.

## Коли реліз невдалий

Версія в npm лишається назавжди, тож відкат означає рух уперед.

- **Позначте як застарілу, потім випустіть патч.** `npm deprecate` із повідомленням, яке називає виправлення, наприклад «Ламає init у Windows. Використовуйте 1.4.1 або новішу», запускає власник із двофакторною автентифікацією. Виправлення проходить тим самим конвеєром, що й будь-який реліз. Виправлення безпеки чи втрати даних випускають одразу, не чекаючи його партії.
- **Ніколи не знімайте з публікації.** Це ламає кожен проєкт і скрипт, що закріпив версію, а номер версії вже ніколи не можна буде використати.
- **Відхиляйте те, що лише стоїть у staging.** `npm stage reject <stage id>` прибирає версію зі staging, не публікуючи її, знову з двофакторною автентифікацією.
- **Пам’ятайте про версію, яку відхилили.** Відхилена версія досі є версією в репозиторії й досі відсутня в npm, тож наступний push без changeset в очікуванні знову поставить її в staging. Спершу злийте виправлення з його changeset, а вже потім усе інше.

## Чого нам досі бракує

У дусі решти серії — ось де наш власний процес релізів слабкий.

- **Немає атестацій походження.** Репозиторій приватний, тож пакети мають підпис реєстру npm і не мають атестацій походження.
- **Ще немає стабільного каналу.** `latest` досі заглушка, і кожна команда, яку ми публікуємо, називає тег <RepositoryFact name="cliReleaseChannel" />. Перший стабільний реліз має одночасно змінити README, тести, що їх перевіряють, і команди на вебсайті.
- **Поверхневий кросплатформний бар’єр.** На macOS і Windows реліз перевіряє `--version` і `--help` під кожним середовищем виконання, а не повний `init`, і збирає на кожному раннері замість того, щоб установлювати tarball, який піде в staging.
- **Схвалення спирається на підсумок.** `npm stage download` у npm завантажує tarball зі staging «для локального огляду» без другого фактора, тож той, хто схвалює, міг би встановити й запустити саме ці байти перед схваленням. Ми ще цього не робимо.
- **Немає тривоги на «немає що робити».** Запуск релізу, який не вибирає жодної роботи, коли версії з гілки немає в npm, нічого не валить.
- **Запізніла страхувальна сітка.** Запланований запуск записів стартує на години пізніше, ніж має, тож головний агент запускає його вручну після кожного схвалення.
- **Схвалює лише одна людина.** 0.1.0-beta.3 три дні чекала на схвалення й була замінена. Реліз, що залежить від другого фактора однієї людини, рухається в темпі цієї людини.
- **Немає запуску проти робочого API перед релізом.** [Перший допис](/blog/ai-coding-agent-guardrails) описує запобіжник, який ми хочемо: запуск опублікованого CLI проти продакшну в CI перед кожним релізом. Для нього потрібен ліцензійний ключ як секрет CI, а це зміна для рев’ю людиною, яка чекає на власника.

## Набір для релізу, який можна скопіювати

**Чекліст релізу**, по черзі:

1. Партію злито, і останній запуск CI у гілці релізу зелений.
2. Кожен changeset читається як нотатка для клієнта, і підвищення версії правильне.
3. Pull request версії перебудовано після останнього злиття, і його перевірки зелені.
4. Документація, потрібна релізу, уже опублікована, а будь-яку зміну контракту, який читає сервер, уже розгорнуто на сервері.
5. Жоден реліз у staging більше не чекає на схвалення.
6. Злийте pull request версії.
7. Запакуйте один раз; запустіть зібрану програму на кожній системі й у кожному середовищі виконання, які ви підтримуєте; ставте в staging, лише якщо все це пройшло.
8. Вивантажте й прочитайте назад усе, що завантажуватиме CLI, і звірте із закріпленим дайджестом, перш ніж ставити в staging.
9. Схваліть кожен пакет релізу з двофакторною автентифікацією або відхиліть реліз.
10. Створіть теги й Releases, щойно реєстр почне віддавати кожен пакет релізу.
11. Встановіть із реєстру в чистий каталог і запустіть CLI.
12. Опублікуйте нотатки до випусків і позначте все, що ставили в staging, але так і не опублікували.

**Завдання staging** — загальний приклад, написаний за документацією npm для репозиторію без Changesets, а не власний workflow CLI. Йому не потрібен токен, і його безпечно запускати повторно. Воно передбачає завдання `pack`, яке вивантажує tarball як артефакт із назвою `tarballs`, середовище з назвою `release` і довіреного видавця на npmjs.com, який називає цей файл workflow, це середовище й дозвіл лише на staging. Кожну дію в ньому закріплено за комітом релізу, з тегом після нього, бо тег можна перемістити, а завдання релізу — останнє місце, де варто запускати код, який ви не переглянули:

```yaml
stage:
  needs: pack
  runs-on: ubuntu-latest
  environment: release
  permissions:
    contents: read
    id-token: write
  steps:
    - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
      with:
        node-version: 26
    - uses: actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2
      with:
        name: tarballs
    - name: Stage every tarball npm does not serve yet
      shell: bash
      run: |
        for tarball in *.tgz; do
          manifest=$(tar -xOzf "$tarball" package/package.json)
          name=$(jq -r .name <<< "$manifest")
          version=$(jq -r .version <<< "$manifest")
          if [ "$(npm view "$name@$version" version 2> /dev/null)" = "$version" ]; then
            echo "$name@$version is already on npm" >> "$GITHUB_STEP_SUMMARY"
          elif staged=$(npm stage publish "$tarball" --access public --tag latest --json); then
            echo "$name@$version staged as $(jq -r --arg name "$name" '.[$name].stageId' <<< "$staged")" >> "$GITHUB_STEP_SUMMARY"
          elif [ "$(jq -r '.error.code' <<< "$staged")" = E409 ]; then
            echo "$name@$version was staged by an earlier run" >> "$GITHUB_STEP_SUMMARY"
          else
            exit 1
          fi
        done
    - name: Keep npm's logs when staging fails
      if: failure()
      uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
      with:
        name: npm-logs
        path: ~/.npm/_logs/
        retention-days: 7
```

**Довірений видавець, якому дозволено лише staging**, — налаштовується один раз для кожного пакета супровідником із двофакторною автентифікацією:

```sh
npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish
```

**Теги лише для того, що віддає npm**, — загальний приклад для одного пакета, який безпечно запускати скільки завгодно разів, наприклад після кожного схвалення:

```sh
name=$(jq -r .name package.json)
version=$(jq -r .version package.json)
if [ "$(npm view "$name@$version" version 2> /dev/null)" != "$version" ]; then
  echo "npm does not serve $name@$version yet, so nothing is tagged"
  exit 0
fi
if git rev-parse -q --verify "refs/tags/v$version" > /dev/null; then
  exit 0
fi
git tag "v$version"
git push origin "v$version"
gh release create "v$version" --verify-tag --notes-file release-notes.md
```

**Завантаження, яке звіряють із сервером і закріпленим дайджестом**, ще до того, як щось його прочитає, — загальний приклад на TypeScript для Node:

```ts
import { createHash } from "node:crypto"
import { gunzipSync } from "node:zlib"

const MAX_CONTENT_BYTES = 256 * 1024 * 1024

interface BundleAnswer {
  readonly sha256: string
  readonly size: number
}

export const verifiedContent = (archive: Buffer, answer: BundleAnswer, pinned: string): Buffer => {
  if (archive.length !== answer.size) {
    throw new Error(`Expected ${answer.size} bytes and received ${archive.length}`)
  }

  const content = gunzipSync(archive, { maxOutputLength: MAX_CONTENT_BYTES })
  const digest = createHash("sha256").update(content).digest("hex")

  if (digest !== answer.sha256 || digest !== pinned) {
    throw new Error("The download is not the bundle this release was tested with")
  }

  return content
}
```

**Правила релізу для вашого файлу інструкцій**, щоб агенти готували те, що схвалить власник:

```md
## Releases

- Never run npm publish, npm unpublish, npm stage approve or npm stage reject. CI stages releases, and a maintainer approves them with 2FA.
- Every change to a published package adds a changeset written for customers: what changes for them and what they have to do.
- Merge a version pull request only when it was built from the branch's current head, and never while a staged release awaits approval.
- After an approval, start the records workflow, install the release from npm in a clean directory and run it before announcing anything.
- Label a version that was staged and never published in its changelog and its GitHub Release. Never delete its tag.
```
