Playwright tests the built application in real browsers. The suite runs against the `test` Wrangler environment: local D1, KV and R2 in `.wrangler/test`, dummy credentials from `.env.test` and the test entry `src/platform/testing/worker.ts`, which intercepts Resend and Polar requests.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:journey
```

| Script             | Runs                                                                      |
| ------------------ | ------------------------------------------------------------------------- |
| `test:e2e:install` | Installs Chromium and WebKit with system dependencies                     |
| `test:e2e`         | All specs in Chromium and WebKit                                          |
| `test:e2e:smoke`   | `e2e/specs/smoke.spec.ts` in Chromium                                     |
| `test:e2e:pr`      | All specs in Chromium, as the Chromium check of pull request CI runs them |
| `test:e2e:headed`  | All specs in visible browsers                                             |
| `test:e2e:ui`      | Playwright UI mode                                                        |
| `test:journey`     | The [journey suite](#journey-suite) against preview                       |

## Configuration

`playwright.config.ts` runs the specs in `e2e/specs/`, defines the `chromium` (Desktop Chrome) and `webkit` (Desktop Safari) projects and uses `PLAYWRIGHT_BASE_URL` or `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` from `src/data/local-server.ts`). Locally the web server command runs `db:reset:test`, `build:test` and `start:test`, and reuses a server that already answers at that URL. In CI one job prepares the build, each of the <RepositoryFact name="e2eShards" /> shards that share the suite unpacks it, and Playwright only starts the server ([CI/CD](/docs/tooling/ci-cd#checks)).

| Setting  | Local                                            | CI                                            |
| -------- | ------------------------------------------------ | --------------------------------------------- |
| Retries  | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" /> |
| Workers  | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" /> |
| Traces   | Kept on failure                                  | On first retry                                |
| Videos   | Off                                              | Kept on failure                               |
| Reporter | List and HTML                                    | GitHub and blob, merged into HTML on failure  |

## Running beside other worktrees

The test build accepts requests only from the hosts it trusts in test mode, because Better Auth and the newsletter links check the request's host: `127.0.0.1:3000` and `localhost:3000`, and `127.0.0.1` and `localhost` on ports <RepositoryFact name="testServerFirstPort" /> to <RepositoryFact name="testServerLastPort" />, set by `TEST_SERVER_PORTS` in `src/data/local-server.ts`. On any other port the sign-in and course pages fail, so `playwright.config.ts` stops before it builds anything when `PLAYWRIGHT_BASE_URL` names another host.

`PLAYWRIGHT_BASE_URL` is the one setting that chooses the port: Playwright opens that URL and starts `start:test` on its port. When other worktrees run their suites at the same time, give each worktree its own port from the range. Check that nothing listens on it, then run the suite there:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` prints nothing when the port is free. If it prints a process, take another port and leave that server alone: stop only the servers you started.

Locally Playwright reuses a server that already answers at the URL and then skips the database reset and the build, so the suite must never reach another worktree's server. `e2e/global-setup.ts` makes sure of it: before the first test it looks up the processes listening on the port with `lsof` and stops the run when one of them runs in another directory than this worktree. A server you started from this worktree passes and is reused as it is, so stop it when the suite should test a fresh build.

## Layout

- `e2e/specs/`: specs for smoke checks, the landing page and its controls, navigation, locales, theme, SEO, auth with its redirects and routing, workspaces, user administration, newsletter, content, legal pages, regional pricing, the checkout funnel, the licence page, the CLI licence API, affiliates, videos, courses, course access, course administration, course covers, imports and materials, the admin dashboard, orders, products and licence machines, the blog index and sharing, the content security policy, withdrawal, the footer, focus rings, scrollbars, licence webhooks, the published CLI and accessibility (<RepositoryFact name="e2eSpecs" /> files).
- `e2e/pages/`: page objects.
- `e2e/fixtures/`: the extended `test` fixture, helpers for captured emails, `deliverPaidOrder` in `license.ts`, which posts a signed `order.paid` webhook to grant a licence, `buyLicense`, which asks the test Worker's `/__test/polar/purchase` for an order and its licence key in the Polar test double and posts their signed `order.paid` and `benefit_grant.created`, `startedCheckouts`, which reads the checkouts the double created from `/__test/polar/checkouts`, `payCheckout`, which pays a checkout the app opened through the test Worker's `/__test/polar/pay`, with the consent ticked, and posts the signed `order.paid` and `benefit_grant.created` of its order, `accessibilityViolations` with the light and dark `COLOR_SCHEMES` in `accessibility.ts`, and Polar's checkout page in `polar-checkout.ts`. The Polar double gives each checkout a URL on Polar's checkout origin, and `servePolarCheckout`, one of the `BROWSER_DOUBLES` that the automatic `browserDoubles` fixture installs, answers that URL in every browser context with a page of the double, read from the test Worker's `/__test/polar/checkout`: it tells the overlay it has loaded, and its **Pay** and **Close** buttons send `confirmed` and `success`, or `close`, to the checkout's `embed_origin`, as Polar's page does. `payInCheckoutOverlay` and `closeCheckoutOverlay` press them, and `refusePolarCheckoutEmbedding` serves the page with `frame-ancestors 'none'`, as Polar does for a host its organisation does not list. The journey suite sets the `browserDoublesEnabled` option to `false` and pays on the real sandbox. `orderLicense` posts only the `order.paid` of such a purchase and returns `issueKey`, which posts its `benefit_grant.created` later. Opened as Polar's own checkout page, outside a frame, the double's **Pay** sends the browser to the checkout's success URL with a `customer_session_token`, as Polar's page does, and `payOnPolarCheckoutPage` presses it. `refundOrder`, `revokeLicenseKey`, `deliverGuestOrder` and `cutOffPolar` ask the test Worker's `/__test/polar/refund`, `/__test/polar/revoke`, `/__test/polar/guest-purchase` and `/__test/polar/cut-off` for a signed `order.refunded` of an order in the double, a signed `benefit_grant.revoked` of its key, a signed `order.paid` of a buyer without an account, or a key whose requests to Polar fail as if Polar could not be reached. `signUpBuyer` in `buyer.ts` signs a buyer up through the API, `sendToApi` in `cli-api.ts` calls the CLI licence API from an address of its own, and `EVERY_STACK_ANSWER` in `stack-answers.ts` holds a legal set of answers for every option and extra of the stack.
- `e2e/data/accounts.ts`: the seeded accounts, an admin and a customer, and their password. `e2e/data/licenses.ts` holds the customer with a licence and that licence, and a licence for each parallel worker that the CLI licence API spec activates machines on.
- `e2e/data/videos.ts` and `e2e/data/courses.ts`: the seeded test video, whose files are in `e2e/fixtures/video/`, and the seeded course: two chapters, the first with a free preview, an account lesson and a paid lesson, the second with three paid lessons whose video is still being recorded.
- `e2e/data/<feature>.pages.ts` and `e2e/data/<feature>.seed.ts`: each feature's pages, which `accessibility.spec.ts` and `workspaces.spec.ts` visit, and its rows and media in the test database, each list imported by `ENTRIES` in `e2e/data/pages.ts` and by `scripts/seed-test.ts`.
- `e2e/data/<feature>.flows.ts`: each feature's flows, each with the test that proves it end to end or the reason it is missing, imported by `FLOWS` in `scripts/check-flows.ts`; see [Test coverage](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: the global setup, which stops the run when the server on the suite's port runs from another worktree.
- `e2e/journey/`: the [journey suite](#journey-suite), with its own configuration. `published-cli.spec.ts` runs the published CLI with `runCli` from `e2e/journey/cli.ts` against the test Worker, so the browser suite needs the npm registry.

The test Worker runs what the features declare in `e2e/data/<feature>.worker.ts`, each list imported by `ENTRIES` in `src/platform/testing/worker.ts`: the licence feature seeds the test licence keys in the Polar double, Resend exposes `/__test/emails` to read the captured emails and the newsletter feature `/__test/newsletter` to read a subscriber's state.

## Accessibility

`e2e/specs/accessibility.spec.ts` runs [axe-core](https://github.com/dequelabs/axe-core) through `@axe-core/playwright` on the public pages, the course pages, the docs home, every Conventions page and one page from each other docs section, a blog post, and the admin and customer workspaces in the light and dark themes. The admin pages include `/admin/courses`, `/admin/courses/create` and the seeded course's editor, which `e2e/specs/workspaces.spec.ts` also visits. It applies the WCAG 2.0, 2.1 and 2.2 A and AA rules plus axe's best practices, fails when a page does not load with a successful status, scrolls through the page so sections that reveal on scroll are checked too, waits for finite animations to finish, and fails on any violation, listing the rule, its impact and the affected selectors.

axe cannot see keyboard flow or layout, so three specs check them for the site's header and footer: `e2e/specs/navigation.spec.ts` that the phone menu moves focus into itself, keeps Tab inside, makes the page behind `inert` and returns focus to its button; `e2e/specs/footer.spec.ts` that no two footer links touch or leave the footer at <RepositoryFact name="footerPhoneWidths" /> px in any locale, and that a link to a landing section is current only on its own section; and `e2e/specs/focus-rings.spec.ts` that the footer's language switcher and the admin command palette's trigger draw their ring for the keyboard.

`e2e/specs/text-layout.spec.ts` checks the admin course form, the admin tables and the landing page's command builder at <RepositoryFact name="textLayoutWidths" /> px with `textLayoutProblems` from `e2e/fixtures/text-layout.ts`: no line of text overlaps another line or an icon, none is cut off without an ellipsis, none is shortened by an ellipsis to a few letters, the page never scrolls sideways, and every locale tab of the course form is in view. Text that scrolls under a pinned column or a sticky header is covered by it, so the check compares sticky text only with other sticky text. Another test opens every admin grid in every locale at the width of a phone, where no column takes the room left over, and fails when a header label is wider than its cell.

## Scrollbars

`e2e/specs/scrollbars.spec.ts` starts Chromium without Playwright's `--hide-scrollbars` switch, through `ignoreDefaultArgs` in `launchOptions`, so Chromium draws classic scrollbars that take room, as on Windows, on Linux and on a Mac set to always show scroll bars. The spec checks that a legal page, an auth page and an admin page keep their heading in place when the window grows until the page no longer scrolls (a docs page always scrolls, because the site footer follows its full-height layout), that opening the docs search, the language select, a dialog or a menu moves nothing, that `/admin` fills the window and that the window behind a dark page is dark in the light theme. WebKit on macOS draws only overlay scrollbars, which take no room, and no launch option changes that, so the check for the reserved room runs in Chromium only. The site menu, which replaces the header links below `lg`, is checked at 768 px: opening and closing it moves nothing.

## Journey suite

`bun run test:journey` buys a licence and uses the CLI the way a customer does, on the preview deployment at `https://preview.saasyland.com`, which takes payments in the Polar sandbox. `e2e/journey/playwright.config.ts` is a configuration of its own, with a Chromium project and no web server, so `test:e2e` and the pull request checks never run it; `journey.yml` runs it every night and by hand ([CI/CD](/docs/tooling/ci-cd#journey-suite)). Each tier is a test of its own, tagged `@core`, `@complete` or `@agency`, the tests run in parallel, and each one goes through these steps:

1. **Account.** The test signs up with a new address of Resend's test inbox, `delivered+journey-<run>-<tier>@resend.dev`, or `upgrade` in place of the tier for the upgrade test, finds the verification email through the Resend API and opens its link.
2. **Price.** `/app/license` must offer the tier at the price for the country that Cloudflare places the runner in, as `/cdn-cgi/trace` reports it: the regional price in a country of `PPP_TIERS`, the full price anywhere else.
3. **Checkout.** The Polar sandbox checkout must open over `/app/license`, in a frame from `sandbox.polar.sh` that takes the focus, without leaving the page, with the account's email filled in and the consent to immediate supply unticked; the test ticks it in the frame. The test pays with [Stripe's test card](https://docs.stripe.com/testing), billed to Poland, where the billing address is only the country. The page must receive Polar's `loaded`, `confirmed` and `success` messages in that order, close the overlay and show the active licence at `/app?checkoutId=<id>&tier=<tier>`. Polar frames the checkout only while the sandbox organisation lists `preview.saasyland.com` under [Settings > Embedding](/docs/getting-started/polar-setup#embedding).
4. **Order and key.** Polar must hold one paid order for the tier's product, at the price `/app/license` offered, with the consent and the buyer's language, the purchase confirmation must reach the inbox, and `/app/license` must show the key that the webhooks issued, the CLI commands and no machine in use.
5. **CLI.** The published CLI, run as <RepositoryFact name="cliExec" /> like the commands on `/app/license`, talks to preview through `SAASYLAND_API_URL`. `activate` writes the credentials file with mode `0600`, activating again keeps the same slot, and `whoami` shows the machine. CI machines, told apart by `SAASYLAND_CI_REPOSITORY`, take the remaining slots, up to <ActivationLimit tier="core" /> machines for Core, <ActivationLimit tier="complete" /> for Complete and <ActivationLimit tier="agency" /> for Agency, and the next one is refused with `activationLimitReached`. Once a slot is freed on `/app/license`, the refused machine gets it and the freed one is told `activationNotFound`. `deactivate` frees the first machine and removes its credentials.
6. **Refund.** The test refunds the order through the Polar sandbox API and waits until `/app/license` shows the licence as refunded; `whoami` must then answer `licenseRefunded` and remove the credentials.

A fourth test, tagged `@upgrade`, upgrades a licence. It buys Core the same way and fills Core's <ActivationLimit tier="core" /> machines, and the next one is refused. `/app/license?tier=complete` must then offer Complete at its price for the runner's country less what the Core order cost, and the test pays that difference in Polar's checkout over the page, the same way. Polar must hold the upgrade order at the difference, with the Core order and tier in `upgrade_from_order` and `upgrade_from_tier`; the Core order's key must now allow Complete's <ActivationLimit tier="complete" /> machines, the key Polar granted for the upgrade order must be disabled, and `/app/license` must show Complete with the same key. The refused machine and the next one then activate, and the one after is refused. The test refunds the upgrade order through the Polar sandbox API: the licence must be Core again, with the same key and Core's limit, the machines already active keep working and a new one is refused. A refund of the Core order then ends the licence.

Every CLI machine is a directory in the test's output folder that the CLI uses as its home, and the CLI runs with nothing in its environment but `PATH`, that home, an npm cache and the `SAASYLAND_*` variables, so none of the suite's credentials reach it. An order that a failed test leaves paid is refunded when the test ends. The accounts stay on preview, each with a refunded licence.

The suite reads these values from the environment, or from `.env.preview` when the file exists, and stops before the first test without them; in CI, `journey.yml` reads them from the GitHub environment `Preview`:

| Variable                                                                        | Used for                                                                                                                                                                |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | Reading and refunding the orders in the sandbox and reading their licence keys, with the `orders:read`, `refunds:write`, `benefits:read` and `license_keys:read` scopes |
| `POLAR_SERVER`                                                                  | Must be `sandbox`                                                                                                                                                       |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | The sandbox products the orders must be for                                                                                                                             |
| `RESEND_API_KEY`                                                                | Reading the verification emails that preview sent, which takes a full-access key                                                                                        |

Preview must run a build with the [CLI licence API](/docs/features/cli-licence-api). It runs `main`, which `deploy.yml` deploys there before production; to test a branch before it merges, deploy it with `gh workflow run preview.yml --ref <branch>` once its checks have passed. The sandbox must match the code, which `bun run polar:verify:preview` checks. Then:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

`bun run test:journey --grep @core` runs only the test with that tag. The HTML report is written to `playwright-report/journey/` and a JSON report to `playwright-report/journey.json`, and the traces, videos and machine directories of failed tests to `test-results/journey/`.
