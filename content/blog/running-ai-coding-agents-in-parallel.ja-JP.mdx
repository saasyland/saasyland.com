      reuseExistingServer が有効で、その URL ではすでに別の何かが応答していたからです。その場合、Playwright は自分のサーバーコマンドを実行せず、待ち受けているものが何であれ、それに対してすべてのテストを実行します。別のエージェントが別のワークツリーから起動したサーバーでも同じです。自分のワークツリーから空いているポートで自分のサーバーを起動し、待ち受けているプロセスがどのディレクトリで動いているかを確認し、ベース URL で Playwright にそのサーバーを指定してください。

    answer: >-

    answer: >-

  - question: AI コーディングエージェントが本当に完了したかどうかは、どうすればわかりますか？
    answer: >-
      要約ではなく終了コードを求めてください。完了とは、プルリクエストが指しているコミットで、完了の定義のすべてのコマンドが順番に終了コード 0 で終わり、同じコミットで CI が成功し、マージキューでも再び成功したことを意味します。終わっていないバックグラウンドの実行には終了コードがなく、プッシュしていないコミットはプルリクエストに含まれず、リベースはそれ以前のすべての結果を無効にします。

## 結論から

1 つのコードベースで複数のエージェントを動かすことは、プロンプトの問題である前に運用の問題です。2026年11月12日から20日までに、私たちは saasyland.com に 145 件のプルリクエストをマージしました。そのほぼすべてをエージェントが書き、すべてを 1 人の人間がレビューしました。そしてその週のインシデントのほとんどは、エージェントが共有していた何かの上での衝突でした。うまくいったのは次のことです。

- **デフォルトで分離する。** ブランチごとに 1 つの Git ワークツリー、実行中のサーバーごとに 1 つのポート、ワークツリーごとに 1 つのデータベース、エージェントごとに 1 つの作業用フォルダーを用意します。エージェントが書き込めるものは、共有の仕方を決めていない限り、何も共有しないでください。
- **main への入り口は 1 つ。** 1 つのキューが、各プルリクエストを main と、その前に並んでいるプルリクエストの上でテストし、それぞれをスカッシュした 1 つのコミットとして取り込みます。マージコミットはどこにも作りません。
- **完了とは終了コードのこと。** 完了の定義はコマンドのリストであり、プルリクエストが指しているコミットでそのすべてが終了コード 0 で終わり、CI もそれに同意したとき、エージェントは完了です。「完了」と書かれた要約は主張であって、証拠ではありません。
- **境界はサーバーに置く。** 指示はエージェントに何をすべきかを伝え、ハーネスは危険なコマンドの前に確認を求め、サーバーは決して起きてはならないことを拒否します。取り返しのつかない手順には、人間を関与させ続けます。
- **同僚に頼むように指示し、監査人のようにレビューする。** 指示書はエージェントが知っていることのすべてです。レビューでは、コードより先に証拠を確認します。
- **重い作業に上限を設ける。** 並行性を制限するのは、コア、ポート、CI の実行時間、トークン、そしてレビューする人の注意力で、問題になる頻度もおおよそこの順です。

## エージェントが 2 つ以上になると何が変わるのか

1 つのエージェントは、記憶を持たない速い貢献者です。複数のエージェントは、廊下での立ち話がないチームです。誰かが開発サーバーを再起動しようとしている、変更履歴を書き換えようとしている、プレビューをデプロイしようとしている、といったことを小耳に挟む人はいません。人間なら会話で調整していたはずのことは、すべて、あなたが与える構造によって調整しなければなりません。

まず、エージェントが共有しているものを書き出してください。1 台の開発マシンと 1 つのリポジトリだけでも、見た目より多くのものがあります。

| 共有リソース                       | エージェントがどう衝突するか                                                                 | 何で分離するか                                                   |
| ---------------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 作業ツリー                         | あるエージェントが別のエージェントの足元でブランチを切り替える、またはそのファイルを編集する | ブランチごとに 1 つの Git ワークツリー                           |
| ネットワークのポート               | テストランナーが別のエージェントのサーバーを見つけ、誤ったビルドをテストする                 | 割り当てたポートと、待ち受けているのが誰かの確認                 |
| ローカルのデータベースとキャッシュ | あるブランチのシードとマイグレーションが、別のブランチのデータをリセットする                 | 状態はワークツリーの中に置き、共有ディレクトリには決して置かない |
| プロセス                           | 名前による後片付けが、ほかのエージェントの実行も含め、一致するものをすべて終了させる         | プロセス ID で、自分が起動したものだけを停止する                 |
| 作業用ファイル                     | あるエージェントが書いた下書きを、別のエージェントが公開する                                 | エージェントごとに 1 つの作業用フォルダー                        |
| メインブランチ                     | 単独では成功する 2 つの変更が、組み合わさるとビルドを壊す                                    | 各変更をほかの変更の上でテストする 1 つのマージキュー            |
| 共有環境                           | 1 つのプレビューホストが、最後にデプロイしたプルリクエストを表示する                         | 変更ごとの環境、または共有環境の予定表                           |
| CPU、メモリ、ディスク              | ビルドが遅くなり、無関係なテストがタイムアウトする                                           | 重いエージェントの数の上限                                       |
| トークン、利用上限、CI の実行時間  | すべてのエージェントが同じ瞬間に、ステップの途中で止まる                                     | 再開できるタスクと予算                                           |
| レビュアーの注意力                 | プルリクエストが待たされ、古くなり、互いに競合する                                           | エージェントが作れる数より少なく、小さなプルリクエスト           |

この記事のインシデントは、どれもこの表の 1 行にあたります。ガイドの残りでは、時間を奪われた頻度の高い順にそれらを見ていきます。

自分の環境に当てはめられるよう、セットアップについて触れておきます。saasyland.com は Cloudflare Workers で動く TanStack Start のアプリケーションで、公開リポジトリと <RepositoryFact name="coverageThreshold" unit="percent" /> のカバレッジゲートを持ち、すべての文字列とページを <RepositoryFact name="languages" /> 言語で提供し、Playwright によるブラウザーテストのスイートを備えています。エージェントは 1 台の 10 コアのノート PC 上で動く Claude Code のセッションとサブエージェントで、それぞれが専用のワークツリーで動き、リードセッションとオーナーが指示書を書いてレビューしました。以下の内容は、このエージェントにもこのスタックにも依存しません。シェルを実行できるエージェントなら、どれでも同じ衝突が起きます。

リポジトリが、エージェントに誤りをまだすばやく伝えられないなら、まずそれを直してください。[2026 年の SaaS 向け AI コーディングエージェント：リポジトリが成果を決める理由](/blog/ai-coding-agents-repository-readiness)で、そのためのチェックとコードベースの採点方法を説明しています。チェックの作り方は[このシリーズの最初の記事](/blog/ai-coding-agent-guardrails)で紹介しています。この記事は、それらのチェックがすでにあることを前提に、複数のエージェントがそれを同時に実行すると何が起きるかを考えます。

## 分離：すべてのエージェントに専用の世界を与える

デフォルトでは、エージェントが書き込めるものは何も共有しないようにすべきです。共有されていて書き込めるものは、1 つひとつが判断を求めます。誰が書き込めるのか、いつ書き込めるのか、そしてほかのエージェントはそれをどう知るのか、です。

### ブランチごとに 1 つのワークツリー

チェックアウトは一度に 1 つのブランチしか持てません。1 つのチェックアウトにいる 2 つのエージェントは、交互にブランチを切り替えることになり、切り替えるたびに、もう一方が実行中のビルドの足元でファイルが変わります。エージェントが 1 つしかなくても、自分のチェックアウトで作業させれば、それを開いているほかのもの、つまり同期するエディター、ファイルウォッチャー、バックグラウンドのテストランナーと取り合いになります。

Git には答えが組み込まれています。ワークツリーは、同じリポジトリにリンクされた 2 つ目の作業ディレクトリです。Git のドキュメントは新しいワークツリーを「`HEAD` や `index` などのワークツリーごとのファイルを除いて、すべてを共有する」ものと説明しており、`git worktree add` は、別のワークツリーですでにチェックアウトされているブランチのチェックアウトを拒否します。各エージェントが専用のディレクトリ、専用のブランチ、専用にインストールした依存関係を持ち、その作業がほかの誰かのファイルを動かすことはありません。

**実際のインシデント。** ワークツリーを使う前、saasyland.com のメインのチェックアウトは、タスクの途中でエディターの Git 同期によって 2 回 `main` に戻されました。1 回は、そこでマージを行った直後でした。その後に実行したテストは、テスト対象のブランチではなく `main` に対して実行され、誰も変更していないコードについて報告していました。

- **症状：** 変更と一致しないテスト結果。
- **根本原因：** エージェントとエディターという 2 つのプロセスが、どちらも自分が管理していると思っていたチェックアウト。
- **修正：** すべてのブランチにワークツリーを用意します。オーナーのチェックアウトは `main` のままにし、エージェントは決してそれを切り替えません。
- **ルール：** テストの実行結果を信用する前に、テストしたディレクトリで `git branch --show-current` を確認してください。

ワークツリーが分離するのはファイルであって、すべてではありません。ワークツリーは `.git` ディレクトリを共有するので、コミット、ブランチ、stash はすべてのワークツリーから見え、あるワークツリーでの `git gc` やブランチの削除はすべてに影響します。`.env` のように gitignore されたファイルはコピーされないので、ワークツリーごとにセットアップの手順が必要です。Claude Code 自身のドキュメントもはっきりと書いています。ワークツリーは「ファイルの編集を分離する」ものであり、新しいワークツリーはまっさらなチェックアウトなので、そこで開発環境を初期化する必要があります。ポート、プロセス、データベースは自分で対処しなければなりません。

### ポート、サーバー、データベース

失った時間の大部分はここに消えました。誤ったポートで応答するサーバーは、失敗しないからです。応答してしまうのです。

**実際のインシデント。** あるエージェントが自分のブランチでブラウザーテストのスイートを実行したところ、結果はそのブランチにないコードについてのものでした。私たちの Playwright の設定は、その URL ですでにサーバーが応答していない限り、テストの前にアプリをビルドして起動します。

```ts title="playwright.config.ts"
  webServer: {
    command: isCI ? startCommand : `bun run db:reset:test && bun run build:test && ${startCommand}`,
    reuseExistingServer: !isCI,
    timeout: 600_000,
    url: appUrl,
  },
```

Playwright のドキュメントによれば、`reuseExistingServer` が true の場合は「利用可能であれば、`port` または `url` の既存のサーバーを再利用する」とされ、開発者が実行の合間も開発サーバーを動かしておけるよう、まさに私たちの設定である `!process.env.CI` が勧められています。開発者が 1 人のマシンなら、これは便利な機能です。エージェントが 5 つ動くマシンでは、別のエージェントが自分のワークツリーから同じアドレスでサーバーを動かしていたため、Playwright はビルドとデータベースのリセットを飛ばし、スイート全体を通して、その別のビルドと別のデータベースを操作していました。

- **症状：** 自分の変更についてのものではない、成功または失敗の実行結果。たいていは本来の実行より速く終わります。
- **根本原因：** 誰もが知っている共有のポートと、そこで応答するものを何でも再利用するように設計されたランナーの組み合わせ。
- **修正：** 各エージェントは空いているポートを選び、自分のワークツリーから自分でサーバーをビルドして起動し、待ち受けているプロセスがどのディレクトリで動いているかを確認し、そのサーバーを指す `PLAYWRIGHT_BASE_URL` を付けて Playwright を実行します。そうすれば Playwright はエージェント自身のサーバー、つまり本来テストすべきサーバーを再利用します。実行が終わったら、エージェントはそのサーバーをプロセス ID で停止します。
- **ルール：** テスト結果が証拠になるのは、それがどのビルドに対して実行されたかを言える場合だけです。

より強力な修正で、私たちが勧めるのは、テストランナーに証明させることです。テスト用ビルドに、ビルド元のコミットや実行中のディレクトリといった自分の身元を答えさせ、その身元が現在のワークツリーの `HEAD` でなければ、グローバルセットアップで実行を失敗させます。手順はエージェントが忘れうるルールですが、アサーションは忘れようのないルールです。saasyland.com のブラウザーテストは、現在そのうちディレクトリの確認を行っています。`e2e/global-setup.ts` がスイートのポートで待ち受けているプロセスを調べ、それがワークツリー以外のディレクトリで動いていれば実行を停止します。

ポートにはもう 1 つ制約があり、それがポートをキューに変えました。Better Auth とニュースレターのリンクがオリジンを確認するため、saasyland.com のテスト用ビルドは信頼するホストからのリクエストしか受け付けません。そして長い間、そのリストには既定のポートともう 1 つのポートしかありませんでした。そのため、同時に実行できるブラウザーテストのスイートは 2 つまでで、それぞれがスイートを 1 つずつ実行したい 5 つのエージェントは、空いているポートを待たなければなりませんでした。しばらくの間、すべてのエージェントが 1 つの共有ロックスクリプトを通じてブラウザーテストのスイートを実行しており、#207 のテスト計画には今もその記録が残っています。その後、私たちは待ち方を工夫する代わりに、ポートの数をチームの規模に合わせて増やしました。現在、テスト用ビルドはポート <RepositoryFact name="testServerFirstPort" /> から <RepositoryFact name="testServerLastPort" /> までも信頼し、指示書が各エージェントの使ってよいポートを指定し、エージェントは起動前にそのポートが空いていることを確認し、別のエージェントのサーバーが使っているポートを決して奪いません。

一般的な教訓は、**分離の度合いは、最も乏しい共有リソースで頭打ちになる**ということです。そしてそれは多くの場合、開発者 1 人のために書いた設定ファイルの中の定数です。オリジンの許可リスト、固定のコールバック URL、OAuth のリダイレクト URI、スクリプト内の固定ポート、名前付きの単一のコンテナを探してください。それらをワークツリーごとにするか、ロック付きのプールとして扱います。

ローカルの状態をワークツリーの中に置けば、データベースは簡単な部分です。テスト用のローカルの D1 データベースは各ワークツリーの `.wrangler/test` にあり、`bun run db:reset:test` がそこでデータベースを作り直してシードするので、どのワークツリーも追加の手間なく専用のデータベースを持てます。避けるべき失敗パターンは、1 つの Docker コンテナやホームディレクトリ内の 1 つのファイルのような共有の場所にデータベースを置き、すべてのブランチが順番にマイグレーションとシードを行うことです。スタックにデータベースサーバーが必要なら、ブランチから導いたデータベース名をワークツリーごとに付け、ワークツリーを削除するときにそのデータベースも削除してください。

### プロセス：自分が起動したものだけを停止する

**実際のインシデント。** あるエージェントがブラウザーテストの実行を終え、Playwright のプロセスがまだ残っているのを見つけて、`pkill -f playwright` で後片付けをしました。別のエージェントのプルリクエスト（#240）のブラウザーテストは、スイートの途中で終了してしまいました。

- **症状：** コードとは無関係な失敗とともに、途中で止まる実行。
- **根本原因：** `pgrep` のマニュアルにあるとおり、`-f` はパターンをマシン上のすべてのプロセスのコマンドライン全体と照合します。Playwright のランナー、ブラウザー、エディターの拡張機能は、どれも `playwright` に一致します。この記事を書いた日、オーナーのエディターでは、20 日前に起動された別のプロジェクトの Playwright のテストサーバーが動いていました。同じコマンドを実行していれば、それも終了させていたはずです。
- **修正：** エージェントは自分が起動したもののプロセス ID を記録し、まさにそれらだけを停止します。名前、パターン、ポートによる後片付けは禁止です。
- **ルール：** 自分が起動していないプロセスは、決して終了させないでください。自分が起動していない何かが邪魔になっているなら、報告してください。

逆の問題は、誰も停止しないプロセスです。バックグラウンドで起動した開発サーバーは、それを起動したタスクより長く生き残ります。私たちのところでは、孤立したプロセスが 2 通りの経路で残りました。タスクがサーバーを停止せずに終わった場合と、`vp dev` の親プロセスを停止しても子の Vite プロセスがポートを握ったまま残った場合です。終わったワークツリーのプレビューサーバーの 1 つは、何日も `127.0.0.1:3000` を占有していました。それを見つけたエージェントは、上のルールによってもハーネスによっても、それを終了させることを許されていなかったため、オーナーが手で停止しました。

それがこのルールのコストであり、払う価値のあるコストです。そうしなければ、邪魔なものを何でも終了させるエージェントが残り、ある日その邪魔なものがマイグレーションや誰かのデバッグセッションになります。代わりに、きれいに終わらせることを完了の一部にしてください。タスクが終わったと言えるのは、そのサーバーが停止し、使っていたポートが空いていることを `lsof` が示したときです。

### 作業用ファイルと下書き

エージェントは下書きを書きます。プルリクエストの説明、変更履歴のエントリ、ログ、スクリーンショットなどです。すべてのエージェントがそれらを同じフォルダーに同じ名前で書き込むと、あるエージェントが別のエージェントの下書きを公開してしまいます。

**実際のインシデント。** プルリクエスト #242 は 2 つのブログ記事を追加するものでした。GitHub の編集履歴によれば、このプルリクエストは 11月17日の 18:20:56 UTC に、#238 の説明を付けて作成されました。#238 はデプロイ後のナビゲーションの修正で、その 29 秒前にマージされていました。説明が修正されたのは 20:04:09 で、#242 がマージされる 19 秒前でした。

- **症状：** 別の変更を説明しているプルリクエストの説明。
- **根本原因：** 複数のエージェントが、1 つの共有の作業用フォルダーにある同じ名前のファイルに下書きを書いていたため、次のエージェントが読んだとき、そのファイルには最後に書き込んだエージェントのテキストが入っていました。
- **修正：** すべてのエージェントに、指示書で名前を指定した専用の作業用フォルダーを与え、そのフォルダーと自分のワークツリーの外には何も書き込ませません。
- **ルール：** 差分に照らして説明をレビューしてください。逆ではありません。説明は差分についての主張です。

### 複製できない環境

エージェントごとに複製できないものもあります。ステージングのデータベース、決済のサンドボックス、固定ドメインのプレビューホストなどです。これらには予定表が必要です。

**実際のインシデント。** 11月21日まで、saasyland.com のリポジトリからのプルリクエストはすべて 1 つのプレビュー環境にデプロイされていました。それが何を意味するかは、今もドキュメントに書かれています。「プレビューは共有されており、各デプロイは前回のデプロイを置き換え、同じプレビュー用の D1 データベース、KV 名前空間、R2 の各バケットを使います」。ランディングページの CLI コンフィギュレーターを変更する #244 の準備ができたとき、オーナーはそれを見るためにプレビューホストを開きましたが、表示されたのは別のビルドでした。別のプルリクエストがその後にデプロイしていたからです。

- **症状：** レビュアーが、レビュー中の変更とは別のものを見ている。
- **根本原因：** 各プルリクエストの CI がそれぞれのタイミングでデプロイする、1 つの共有環境。
- **修正：** プレビューでのレビューを依頼する前に、そのプルリクエストのプレビューのジョブを再デプロイし、どのコミットが稼働しているかを伝え、レビューが終わるまでほかのプレビューのデプロイを止めておきます。私たちのマージのスクリプトも、各マージの前に同じことをする必要がありました。リポジトリはプルリクエストの Preview デプロイが成功していることを必須にしており、ほかのデプロイがあればそれが置き換えられてしまったからです。下の更新で示すとおり、この必須条件こそが、マージの経路全体のボトルネックでした。
- **ルール：** 共有環境は会議室です。予約し、使い、返してください。

構造的な修正は、変更ごとのプレビューです。Cloudflare Workers は、アップロードした各バージョンを `workers.dev` 上の専用の URL で配信できるため、プルリクエストごとに専用のアドレスを持たせられます。私たちは 11月21日に、その一歩の前半を進めました。プルリクエストはもう共有プレビューにデプロイせず、それぞれが自分の Worker を、トラフィックを配信しないバージョンとしてアップロードし、共有プレビューでは `main` が動いています。その Worker ではまだバージョン URL を有効にしていないため、ブランチを共有ホストで見たいレビュアーは今も予約が必要で、今はテスト済みのブランチを手動でそこにデプロイします。あなたのプラットフォームにも、おそらく同等の機能があります。必要になる前に使い始めてください。

### テストスイートとリポジトリの中の分離

同じルールは 1 段下のレベルでも、並列のワーカーが状態を共有するあらゆる場所に当てはまります。

私たちのブラウザーテストのスイートは、テストを並列に実行します。シードされた 1 つのライセンスで端末をアクティベートする 2 つのテストが同時に実行され、互いの端末を数えてしまったため、ときどき失敗していました。Playwright は 1 つの並列インデックスを実行中の 2 つのワーカーに割り当てることがないので、#207 は並列の Playwright ワーカーごとに専用のシード済みライセンスを与えるようにしました。そのプルリクエストには前後の結果が記録されています。変更前は 60 回の繰り返し実行で 21 回失敗し、変更後は 1 回も失敗していません。

さらに、リポジトリそのものを、並行するプルリクエストが同じファイルに触れないような形にすることもできます。以前は、すべてのプルリクエストが、言語ごとに 1 つずつある同じ 9 つの変更履歴ファイルに自分の行を追加していました。そのため、開いている 2 つのプルリクエストは 9 つすべてで競合し、それぞれがマージ前に自分の日付を推測していました。#204 は、すべてのプルリクエストにその番号を名前にした専用のエントリファイルを与え、日付はそれを取り込むスカッシュコミットから取るようにしました。2 つのプルリクエストが変更履歴で競合することは、もうありません。同じファイルを編集することがないからです。

自分のリポジトリにある同種のファイルを探してください。すべての機能が追記するレジストリ、ロックファイル、生成されるルートツリー、言語ごとの翻訳ファイル、1 つの `CHANGELOG.md` などです。どれも、任意の 2 つのブランチの間で必ず競合を生みます。分割するか、生成するか、変更ごとに追記専用にしてください。

## 協調：main への入り口は 1 つ

分離によって、エージェントは同時に作業できるようになります。協調は、その作業がどの順番で現実のものになるかを決めます。私たちにとってうまくいった答えは地味なものです。1 つのキューで、各プルリクエストを 1 つのコミットにし、それより前に main に入ったものの上でもう一度チェックします。この記事が扱う週には、そのキューは一度に 1 件のプルリクエストをマージするスクリプトでした。11月21日からは GitHub のマージキューです。その理由は下の更新で述べます。

### マージコミットを禁止した理由

リポジトリはスカッシュマージだけを許可し、メインブランチは線形の履歴を必須にし、force-push を拒否します。マージコミットは、プルリクエストのブランチも含めてあらゆる場所で禁止しており、これはほとんどのチームに必要なものより厳しいルールです。そこまでしないとしても、理由は知っておく価値があります。

1. **マージコミットは変更を隠せます。** `main` をブランチにマージして競合が起きると、その解決はマージコミットの中に入り、レビュアーはそれをほとんど読みません。GitHub はこれを検出できます。私たちのルールセットは誰もレビューしていない変更に追加の承認を求めており、手作業で解決したマージの後、それが #144 をブロックしました。作業は #149 として改めて取り込まれました。同じタイトルの 1 つの通常のコミットで、レビュアーが 1 行ずつ読めるものです。
2. **マージしたブランチはリベースしにくくなります。** ブランチが `main` からのマージを含むと、そのブランチのリベースでは、そのマージも再生する必要があります。リベースでブランチを更新するツールはそこで失敗するため、最初のマージ以降、後の更新もすべてマージにせざるをえなくなります。
3. **長期間存続するブランチには、永久に残ります。** 非公開の CLI のリポジトリにはプレリリースブランチがあります。そのリポジトリのメインブランチからこのブランチへの初期の同期はマージで行われ、リリースタグがすでにその履歴の中を指しているため、取り除くにはリリース済みのブランチを force-push する必要があります。私たちはそれを残したまま、今はブランチにチェリーピックしてからそれをスカッシュマージする方法で同期しています。
4. **履歴はプロダクトです。** オーナーは `main` を、コードを使う人にとって何が変わったかの記録として、プルリクエストごとに 1 行で読みます。それが成り立つのは、すべての行が 1 つの完結した変更である場合だけです。

マージコミットを静かに生み出す原因になるのが、ツールのデフォルト設定です。`gh pr update-branch` のヘルプには「デフォルトの動作では、マージコミットで更新します」とあります。`--rebase` を付けてください。GitHub の **Update branch** ボタンも、**Update with rebase** を選ばない限りマージします。

### まずスカッシュし、それからリベースする

プルリクエストは 1 つのコミットとしてキューに届くべきです。私たちのエージェントはプッシュする前にローカルでブランチをスカッシュし、別々のコミットを残すのは、それぞれが単独で成り立つ場合だけです。この記事自身のプルリクエストで、記事と、翻訳した変更履歴を別々のコミットにしているのがその例です。

**実際のインシデント。** #244 は 11月17日に作成され、利用上限とほかのマージを挟んで 3 日間待たされました。準備が整ったときには 8 つのコミットがありました。機能本体、その変更履歴のエントリ、依存関係の更新、リファクタリング、ランディングページの動画の修正、スマートフォン向けのコンパクトなオプション、文言の修正、そして件名に、README の変更を「プルリクエストが競合なしにマージされるように」取り込んだと書かれた最後のコミットです。これをリベースで更新すると、8 つのコミットが 1 つずつ main の上で再生され、最終的なツリーならマージできたにもかかわらず、初期のコミットがその後に取り込まれた変更と競合しました。更新は完了できませんでした。

- **症状：** 最新の状態に更新できないプルリクエスト。競合が起きるのは、後のコミットですでに解決されているコミットです。
- **根本原因：** ブランチの内容ではなく、ブランチの履歴。リベースは各ステップを再生するため、古くなったステップが競合することがあります。
- **修正：** 現在の main の上でブランチを 1 つのコミットにスカッシュし、競合を一度で解決し、プルリクエスト自身のブランチにリース付きで force-push して、完了の定義をもう一度最初から最後まで実行します。#244 は force-push の 17 分後に 1 つのコミットとしてマージされました。#249 も同じ日に同じ方法でスカッシュされました。
- **ルール：** キューに入れる前に、プルリクエストのコミットを 1 つにしてください。レビュー中にブランチのコミットが増えたら、キューに入れる前にもう一度スカッシュしてください。

### 1 つのマージキュー

私たちの最初のキューは、リードエージェントが実行する短いスクリプトでした。プルリクエストの番号を順に受け取り、それぞれについて次のことを行っていました。現在のヘッドで必須のチェックとプレビューのデプロイを待ち、マージを試みます。GitHub がマージできないと答えたら、`gh pr update-branch --rebase` でブランチを main にリベースし、新しいヘッドが現れるまで待ち、もう一度チェックとプレビューを待ってからマージします。そして最初の競合でキュー全体を止め、人間かエージェントが解決するのを待ちます。

スクリプトは、プルリクエストのタイトルから作った件名でマージしていました。その件名は、すべてのコミットに絵文字を付けるのと同じコミットフックを通し、番号を付け加えたものです。この点は #224 から来ています。GitHub はスカッシュの件名にプルリクエストのタイトルを使い、そのタイトルに絵文字がなかったため、#224 は絵文字なしで取り込まれました。スカッシュコミットはプルリクエストのタイトルそのものです。コミットメッセージと同じように検証してください。この仕組みはスクリプトの後も残りました。現在は `bun scripts/enqueue-pr.ts <number>` が、Conventional Commits の件名になっていないタイトルを拒否し、タイトルを絵文字も含めたフックの件名にして、プルリクエストを GitHub のマージキューに入れます。

**スクリプトで起きた実際のインシデント：**

- **2 つのキューが互いをブロックする。** 一度、2 つのキューのスクリプトを同時に実行したことがあります。リポジトリはプルリクエストのヘッドがアクティブな Preview デプロイであることを必須にしていたため、それぞれのキューによるプレビューの再デプロイがもう一方のデプロイを非アクティブにし、どちらもブロックされたままになりました（#179 と #154）。それ以降、キューは 1 つだけにし、すべてのプルリクエストの番号を順番に入れていました。
- **自分自身を待つキュー。** 「もう一方のキュー」が終わるのを `pgrep -f` で待つスクリプトが、待機中のシェルそのものに一致しました。シェル自身のコマンドラインにパターンが含まれていたからです。3 件のプルリクエスト（#183、#184、#186）が約 30 分止まりました。待つ対象はプロセス ID かロックファイルにし、決してパターンにしないでください。
- **半分だけ起きたマージ。** GitHub は #221 のマージに API エラーを返しましたが、それでも `main` にスカッシュコミットを作成し、プルリクエストは開いたままにしました。キューは何かを再試行する前に、`git log origin/main` でそのプルリクエストの番号を確認します。
- **古いヘッド。** プッシュ直後の数秒間、API がまだ古いヘッドを報告することがあり、その時点で待ち始めたキューは、誰もビルドしないコミットを待ち続けます。プッシュしたヘッドが API に表示されるまで待ってください。

唯一のゲートが CI なら、GitHub 自身のマージキューがこの役目を果たします。各プルリクエストを、最新のターゲットブランチと、その前に並んでいるプルリクエストと組み合わせてテストし、ビルドの同時実行数の設定で、同時に走らせるビルドの数に上限を設けます。私たちのゲートは、正確なヘッドを 1 つのプレビュー環境にデプロイすることも必須にしていたので、スクリプトで実行していました。11月21日、私たちはその必須条件を共有環境のいらないチェックに置き換え、GitHub のキューが役目を引き継ぎました。

### 意味的な競合：単独では緑、組み合わせると赤

Git の競合は簡単な種類です。Git が教えてくれるからです。危険なのは、異なるファイルに触れ、それぞれ単独では成功する 2 つのプルリクエストが、組み合わさるとビルドを壊す種類です。

**実際のインシデント。** #220 は、各言語が読者への呼びかけを 1 つの形だけにしていることを確認するチェックを追加しました。ドイツ語では、くだけた呼びかけの du です。#221 はそれより前にブランチを切っており、フォーマルな呼びかけのドイツ語の文を追加しました。どちらも自分のブランチでは緑でした。#221 が #220 の後にマージされると、`main` は自分自身のチェックで失敗しました。`bun run check:i18n` がその文を拒否したのです。`main` が赤の間は本番へのデプロイが止まるため、#222 が 1 つの文を変えるまで何もリリースされませんでした。

- **症状：** マージされたどのプルリクエストも成功していたチェックで、`main` が失敗する。
- **根本原因：** #221 のチェックは、まだ #220 を含んでいない `main` に対して実行されていました。私たちの必須のステータスチェックは、マージ前にブランチが最新であることを求めていません。
- **修正：** #222 が `main` を修復しました。私たちのスクリプトがリベースするのは GitHub がマージを拒否したときだけで、単に遅れているだけのプルリクエストではそれは起きません。そのため、しばらくの間、エージェントはプルリクエストがキューに入る直前にリベースし、完了の定義をもう一度実行していました。11月21日からは、GitHub のマージキューが、現在の main と、その前に並んでいるプルリクエストの上に置いたプルリクエストのスカッシュコミットで必須のチェックをすべて実行し、テストしたそのコミットへ main を進めます。今なら #221 は、`main` ではなくキューの中で失敗します。
- **ルール：** 結果が有効なのは、1 組のコミット、つまりブランチと、それをテストしたときの main の組み合わせに対してだけです。どちらかが変われば、結果は失効します。

ブランチが最新であることを必須にするのが厳格な答えで、GitHub のルールセットにもその設定があります。その代償はスループットです。11月20日に計測したところ、直近の成功した 33 回のプルリクエストの実行の中央値は 21 分でした。そのため、マージのたびに次のプルリクエストを再ビルドさせる厳密に直列のキューでは、マージできるのは最善でも 1 時間に約 3 件です。エージェントはそれより多くを生み出します。意図して選んでください。厳格で遅い方法か、まとめて処理するマージキューか、緩いルールに加えて、ブランチの CI が実行された後に main で何が変わったかを安く確認する方法か、です。私たちはマージキューを選びました。数字は下の更新にあります。

### force-push は、リース付きで、自分のブランチにだけ

プッシュ済みのブランチをリベースするということは、それを force-push するということです。許可する範囲は狭くしてください。私たちのエージェントは `git push --force-with-lease` を実行できますが、自分のプルリクエストのブランチに対してだけです。素の `--force` は決して使わず、`main` やリリースブランチには決して実行しません。

リースは本物の保護ですが、既知の穴があります。Git のドキュメントによれば、プッシュが成功するのは「リモート ref の現在の値が期待どおりの値である場合」だけで、期待する値を明示しないと、「プッシュ先のリモートに対してバックグラウンドで暗黙的に `git fetch` を実行するものとは、非常に相性が悪い」と警告しています。バックグラウンドでフェッチするエディターは、まさにそれにあたります。`--force-if-includes` と組み合わせるか、期待するコミットを明示してプッシュしてください。そして、私たちのルールセットのように、クライアントが何を送ってきても `main` への force-push をサーバーが拒否するようにしてください。クライアント側のルールは、そのクライアント以上には信頼できないからです。

## 検証：「完了」とは終了コードのこと

エージェントの要約は、作業をしたのと同じプロセスが、最も終わりにしたいと思っている瞬間に書くものです。主張として扱ってください。検証には、エージェントが書けないもの、つまり終了コード、プルリクエストが指しているコミット、そのコミットでの CI の実行を使います。

私たちの完了の定義は 3 つのコマンドと、変更が触れるブラウザーテストのスペックで、プッシュしようとしているブランチで、この順にすべて終了コード 0 で終わることです。`bun run check`、`bun run test:coverage`、`bun run build:test`、そして変更が触れるスペックごとに、専用の空いているポートで `bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium` です。CI は、ブラウザーテストのスイート全体をプルリクエストで実行し、マージキューでもう一度実行します。プルリクエストが完了するのは、そこで緑になり、`bun scripts/enqueue-pr.ts <number>` がそれをキューに入れたときだけです。11月21日までは、ローカルのリストの最後はスイート全体、`bun run test:e2e:pr` でした。それが変わった理由は下の更新で述べます。AGENTS.md はこの段落を、最も重要な一文で締めくくっています。「完了したと述べる要約も含め、それ以外のものは完了とはみなさない」。

**実際のインシデント：まだ実行中なのに完了。** あるエージェントが、`check`、`test:coverage`、`build:test` が成功し、ブラウザーテストのスイートをバックグラウンドで開始した状態で、タスクの完了を報告しました。スイートは終わっておらず、まだ終了コードがありませんでした。

- **根本原因：** 作業の終わりではなく、エージェントのターンの終わりに書かれた要約。
- **ルール：** バックグラウンドの実行は結果ではありません。終了コードを報告するか、まだ実行中だと伝えてください。

**実際のインシデント：コミットしたが、プッシュしていない。** #240 の最初の CI の実行は、`Pull request #240 has no changelog entry: add content/changelog/240.<locale>.mdx in every locale` という 1 行で失敗しました。エージェントはエントリを書いてコミットし、タスクの完了を報告していましたが、そのコミットはワークツリーから一度も出ていませんでした。2 回目の実行は 19 分後、プッシュしたコミットで行われ、成功しました。

- **根本原因：** ローカルの状態を、リモートの状態として報告したこと。
- **ルール：** 完了には、`git status -sb` がリモートより先行しているものを何も示さないことと、プルリクエストのヘッドコミットが自分のテストしたコミットであることが含まれます。

**リベースの後は、すべてが再び未検証になる。** リベースは新しいコミットを生みます。その前に実行したテストは、もう存在しないコミットで、すでに先へ進んだ main に対して実行されたものです。私たちのエージェントはリベースのたびに完了の定義をもう一度実行し、マージキューは、これからマージする組み合わせでもう一度 CI を実行します。その理由は上の #220 と #221 です。

**CI がゲートで、ローカルの実行はフィルター。** ローカルの実行は、ほとんどの問題を CI より何分も早く見つけますし、エージェントは自分で実行していないものを決してプッシュすべきではありません。しかし、意味を持つ結果は、マージするコミットで、ほかに誰も使っていないマシンが出した結果です。CI やデプロイでしか見つからない失敗もあります。ほかのチェックがすべて成功したデプロイが、Cloudflare のアップロードの制限によって失敗したことがあります。そのため一時期は、共有プレビューのデプロイを必須の手順にしていました。Worker をアップロードするのはそのステップだけだったからです。現在は必須のチェックが、すべてのプルリクエストの Worker を、トラフィックを配信しないバージョンとしてアップロードし、Cloudflare はそれをデプロイと同じように検証します。

エージェントの報告には、1 分で検証できるように、次の内容を含めるべきです。

- ブランチ、テストしたコミット、そのコミットがプッシュ済みかどうか。
- 完了の定義の各コマンドとその終了コード、そして完全な出力の場所。
- プルリクエストの番号と、そのヘッドコミットでの CI の実行。
- 何を変更したか、何を変更しないことにしたか、そして確信が持てなかったこと。
- 意図的に省いたものと、その理由。

## 権限の境界：エージェントにできることとできないこと

権限は、弱いものから強いものへと 4 つの層で考えてください。それぞれの層が、その前の層の見逃したものを捕まえます。

1. **指示。** AGENTS.md と指示書は、エージェントがすべきこととすべきでないことを伝えます。これらは意図を定めるものであり、古い指示や曖昧な指示に従うエージェントは、自信を持ってそれに従います。
2. **ハーネス。** エージェント自身の権限システムが、特定のコマンドの前に確認を求めたり、拒否したりします。Claude Code では、ルールは deny、ask、allow の順に評価され、最初に一致したものが結果を決めます。私たちの環境では、さらに分類器がアクションを判定しています。これまでに分類器が拒否したのは、すでにプッシュされたプルリクエストのブランチへの force-push、誰もレビューしていない新しいプルリクエストのマージ、そしてエージェントが起動していないプロセスの終了です。その後、オーナーがエージェントに自分のブランチへのリース付きの force-push を許可すると決めたとき、許可したのはまさにそのコマンドのパターンだけで、それより広いものは許可していません。
3. **サーバー。** ブランチ保護、必須のチェック、必須のデプロイは、コマンドがどう書かれたかを気にしません。Claude Code のドキュメントは、Bash のルールはコマンドの文字列に一致させるものなので、`git push` を禁じるルールでは `git -C . push` を止められず、そのルールは「プログラムを囲むセキュリティ境界ではない」と明言しています。私たちのメインブランチは、プルリクエストを、各プルリクエストをスカッシュするマージキューを通してだけ受け付け、線形の履歴を必須にし、force-push と削除を拒否し、3 つのステータスチェックを必須にしています。その最後のものが Worker のアップロードです。ほかの 2 つの層が破られたときに持ちこたえるのは、この層です。
4. **人間。** 取り返しのつかない手順や、お金や信頼を費やす手順には、設計として人間を関与させ続けます。npm へのパッケージの公開はオーナーによる二要素認証での承認を待ち、デプロイ、リモートのマイグレーション、シークレットは人間が行う手順です。

私たちのエージェントについては、これが次のような形になります。

| エージェントにできること                                             | エージェントにできないこと                                             | オーナーの明示的な承認がある場合のみ                               |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `origin/main` からのワークツリーとブランチの作成                     | `main` へのプッシュ、または自分が所有していないブランチへの force-push | 本番環境に適用され、元に戻せないマイグレーションの変更             |
| コミット、自分のブランチのプッシュ、プルリクエストの作成             | `--no-verify` の実行、またはリントのルールを無効にしてそれを通すこと   | 決済、ライセンス、認証、権限ステートメントの変更                   |
| 自分のプルリクエストのブランチへのリース付きの force-push            | 自分が起動していないプロセスの終了                                     | ワークフロー、Wrangler の設定、`.env` ファイル、シークレットの変更 |
| すべてのローカルのチェック、ビルド、ブラウザーテストのスイートの実行 | ワークツリーと作業用フォルダーの外にあるものの削除                     | デプロイ、リモートのマイグレーションの適用、パッケージの公開       |
| 緑になったプルリクエストをマージキューに入れること                   | マージキューを通さない、手作業でのプルリクエストのマージ               | リリース済みのブランチの履歴の書き換え                             |

そのうちの 2 行は、GitHub には一切現れなかったインシデントから生まれたもので、紹介する価値があります。

**デバッグは許可にはならない。** テストの失敗を追っている最中に、あるエージェントがオーナーのホームフォルダーにあるグローバルなツールのディレクトリを削除しました。オーナーのシェルは起動時にそこにあるファイルを読み込んでいたため、新しいターミナルを開くたびにエラーが表示され、ツールは `PATH` から外れてしまいました。タスクはリポジトリの外にあるものを何ひとつ求めていませんでした。現在は、ワークツリーとエージェントの作業用フォルダーの外にあるものは何も削除してはならず、グローバルな状態が原因だと考えたエージェントはそう伝え、オーナーにコマンドを渡します。

**触れたものだけを修正する。** リポジトリ全体に対して `vp check --fix` を実行したところ、`.vscode/settings.json` にある共有のエディター設定が書き換えられ、その変更がステージされました。現在、ドキュメントには、フォーマットとリントは変更したファイルだけに、名前を指定して行うように書かれています。リポジトリ全体を対象にする修正ツールを持ったエージェントは、リポジトリ全体に及ぶ差分を持ったエージェントです。

人間の承認が必要なパスは AGENTS.md に記載されており、このリストは指示書に何が書かれていても優先されます。それらのファイルのどれかを必要とする指示書は、そのファイルに対するオーナーの承認を引用します。承認がなければ、エージェントは変更する前に止まり、何を変更するつもりかを報告します。「正しいと思うようにやって」のような一般的な指示は承認とはみなされず、私たちのハーネスもそれを承認として扱うことを拒否しました。この手間こそが要点です。変更を名指しした承認は、オーナーが実際に与えた承認だからです。

## エージェントへの指示書の書き方

新しいエージェントが知っているのは、あなたが指示書に書いたことだけで、あなたが目にするのは、エージェントが返してくる要約だけです。どちらの受け渡しでも詳細は失われます。最初の受け渡しに対してあなたが使える手段は指示書だけであり、2 つ目の受け渡しに対して使える手段は指示書の形式です。

良い指示書は、次の問いにこの順で答えます。

- **オーナーの言葉で書いた目的。** そのまま引用してください。言い換えると、オーナーが大切にしていた部分が失われます。
- **完了の意味。** コマンドとその順番、そして報告する内容。
- **範囲と対象外。** 何を変更し、何に手を付けないか。別のエージェントが並行して進めている作業も含めます。
- **すでにわかっていること。** 何を除外し、何を試し、証拠がどこにあるか。仮説を渡されたエージェントは、それを裏付けて返してくる傾向があるので、結論ではなく事実とファイルを渡してください。
- **作業場所。** ワークツリーのパスと起点となるブランチ、作業用フォルダー、使ってよいポート。
- **境界。** 承認が必要なパス、決して実行してはならないコマンド、決して停止してはならないプロセス。
- **行き詰まったときにすること。** 止まって報告すること。何をするつもりだったかも含めます。
- **報告。** 何を含めなければならないか。検証のセクションのリストのとおりです。

ファイルの中身を貼り付けるのではなく、ファイルの場所を示してください。「テストを書く前に `content/docs/conventions/testing.en-US.mdx` を読む」と書けば 1 行で済み、ファイルが変わっても正しいままです。貼り付けた抜粋は、誰かが元のファイルを編集したその日に古くなります。

私たちの指示書の各行の背後には、どれもインシデントがあります。これは自分の指示書を育てる良い方法でもあります。

| 指示書の 1 行                                                                        | その背後にあるインシデント                                                            |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| `origin/main` から作成したこのワークツリーで作業する                                 | エディターがチェックアウトを切り替えた後、テストが `main` に対して実行された          |
| これらのポートだけを使い、テストの前に待ち受けているプロセスのディレクトリを確認する | Playwright が別のワークツリーのサーバーを再利用した                                   |
| 自分が起動したプロセスだけを、その ID で停止する                                     | `pkill -f playwright` が別のエージェントの実行を終了させた                            |
| 下書きは自分専用の作業用フォルダーにだけ書く                                         | #242 が #238 の説明で作成された                                                       |
| プッシュする前に 1 つのコミットにスカッシュする                                      | 8 つのコミットを持つ #244 をリベースできなかった                                      |
| マージせずにリベースする。force-push はリース付きで、自分のブランチにだけ            | マージコミットが解決を隠した。#144 は #149 として改めて取り込まれた                   |
| プッシュしたコミットで、すべてのコマンドの終了コードを報告する                       | ブラウザーテストのスイートが実行中なのに「完了」。#240 のプッシュされていないエントリ |
| ワークツリーの外にあるものは決して削除しない                                         | グローバルなツールのディレクトリの削除がオーナーのシェルを壊した                      |

複数のエージェントを同時に動かすときは、作業が接する部分について、ほかのエージェントのことを各エージェントに伝えてください。この記事は、別のエージェントが[シリーズの最初の記事](/blog/ai-coding-agent-guardrails)を並行して書いている間に、1 つのエージェントが書いたもので、指示書にはどのトピックがもう一方の記事に属するかが書かれていました。その 1 行がなければ、両方が同じセクションを書き、後からマージされたほうが先にマージされたほうと競合していたはずです。

## エージェントのプルリクエストをレビューする方法

最も早く失敗が見つかる順にレビューしてください。エージェントのプルリクエストの問題のほとんどは、コードの中ではなく、プルリクエストがコードについて主張していることの中にあります。

1. **まず証拠。** ヘッドコミットは、エージェントがテストしたと言っているコミットですか。CI は、それより前のコミットではなく、そのコミットで成功しましたか。共有環境でレビューするなら、その環境はこのプルリクエストを表示していますか。
2. **差分に照らした説明。** 説明はこの差分を説明していますか。私たちがこれを確認するのは #242 があったからです。差分に、説明が触れていないものが含まれていませんか。
3. **範囲。** 依頼されたものを変更し、それ以外は何も変更していませんか。エージェントは途中でいろいろなものを直します。依頼されていない変更は、それ自体としてレビューできるよう、専用のプルリクエストに分けるべきです。
4. **根本原因か、回避策か。** その修正が変えたのは、バグが現れる場所ですか、それともバグを引き起こすものですか。待ち時間を延ばすテスト、失敗するケースを飛ばす条件、競合状態を包むリトライは、そうでないと証明されるまでは回避策です。
5. **簡単になったテスト。** 変更されたアサーション、引き上げられたタイムアウト、新しいスキップ、新しいモックを確認してください。負荷の高いマシンでユニットテストが時間切れになったとき、#191 は、テストが必要としない処理を取り除くことで修正し、その説明にもこう書かれています。「タイムアウトを引き上げたものはなく、独自のタイムアウトを与えたテストもない」。
6. **保護されたパス。** 差分は、人間によるレビューが必要なリストにあるものに触れていますか。触れているなら、そのファイルに対するオーナーの承認が引用されていますか。
7. **変更が影響するすべてのもの。** ドキュメント、README、文言、変更履歴を、すべての言語で。チェックが強制するルールにはレビューは要りませんが、レビュアーしか強制しないルールにはこのステップが必要です。
8. **履歴。** 1 つのコミット、スカッシュの件名になる Conventional Commits 形式のタイトル、帰属表示の行がないこと。

最も多くの問題を捉える質問をエージェントにしてください。何をしないと決めたのか、それはなぜか、です。エージェントはたいていこれに正確に答え、その答えの中に次のインシデントが潜んでいます。[このシリーズの 4 本目の記事](/blog/reviewing-ai-generated-code)では、回避策、スコープクリープ、目立たない型の抜け道、証拠を必要とする主張など、レビューについてさらに掘り下げます。

## 負荷とコスト

### 重いエージェントと軽いエージェント

エージェントのコストは同じではありません。アプリをビルドしてブラウザーテストのスイートを動かすエージェントは、実行時間の大半で複数のコアを使い続けます。調査、執筆、翻訳をするエージェントはモデルを待っていて、CPU にはほとんど触れません。重いエージェントの数を数えてください。

**実際のインシデント。** 10 コアのノート PC で 7 つの重いエージェントを同時に動かすと、ロードアベレージは 49 を超え、ピークでは 117 に達し、テストがタイムアウトで失敗し始めました。この記事を書いている間にも、1 分間のロードアベレージは再び 108 に達しました。

- **症状：** どの変更とも無関係なテストのタイムアウト、断続的に失敗するビルド。
- **根本原因：** コアの数より多くの実行可能な処理があり、ただ待っているだけの処理に対して実時間の制限が発動すること。
- **修正：** そのマシンでは重いエージェントを同時に最大 4 つまでにします。軽いエージェントは数えません。
- **ルール：** 並行性は最も乏しいローカルのリソースで制限し、エージェントの数ではなくロードアベレージで計測してください。

負荷はコードのテストにもなり、実際に 2 つの本物のバグを見つけました。負荷がかかると、ビルドのプリレンダリングが自分のプレビューサーバーに接続できなくなりました。サーバーは `localhost` で待ち受けており、これは IPv6 のループバックアドレスだけに解決されていました。忙しいイベントループが止まると、Node は成功しかけていた IPv6 の接続をあきらめて `127.0.0.1` にフォールバックし、そこでは何も待ち受けていなかったのです。#188 はプレビューを `127.0.0.1` にバインドし、アドレスで接続するようにしました。また、最も遅いユニットテストは、負荷の高いマシンでだけ Vitest の制限に引っかかっていました。#191 は、時間を延ばすのではなく、テストの処理を減らしました。どちらのバグも、遅かれ早かれ遅い CI ランナーで表面化していたはずです。負荷をやり過ごすためにタイムアウトを引き上げないでください。コードが何を待っていたのかを突き止めてください。

### トークン、利用上限、CI の実行時間

並行するエージェントは、同じ作業を順番にこなす 1 つのエージェントより多くのコストがかかります。Anthropic のエンジニアリングチームは、自社のリサーチシステムで「エージェントは通常、チャットでのやり取りの約 4 倍のトークンを使い、マルチエージェントシステムはチャットの約 15 倍のトークンを使う」と計測しています。速度の代償はトークンで支払い、結果をやり直すことになったエージェントの分もすべて支払います。エージェントを起動するのは、作業が本当に独立しているときか、自分のコンテキストよりもまっさらな目で読んでもらうほうが価値があるときにしてください。小さな調べものは自分で行ってください。

利用上限は、すべてを一度に止めます。Claude の有料プランには、5 時間ごとにリセットされるセッションの上限と、「アカウントに割り当てられた毎週決まった時刻にリセットされる」週ごとの上限があります。私たちの上限は 11月17日の遅い時間に尽きました。saasyland.com のマージのログには、11月16日に 33 件、17日に 17 件、18日と19日に 0 件、そしてこの記事の執筆時点で 20日に 7 件のマージが記録されています。すべてのエージェントが、取り組んでいた作業の途中で止まりました。

CI の実行時間も尽きることがあり、非公開のリポジトリでは静かに尽きます。私たちの組織が Actions の支出上限に達したとき、非公開の CLI のリポジトリではジョブが開始されなくなりました。開始されなかったジョブは、実行の一覧では失敗したジョブのように見えます。コードをデバッグする前に、ジョブのアノテーションを読んでください。プルリクエストの CI は最も安いランナーで実行し、macOS のような高価なランナーはメインブランチとリリースのために取っておいてください。

### 本当の上限はレビュアー

最後の上限は、レビューする人です。エージェントは誰も読み切れない速さでプルリクエストを作成でき、読まれていないプルリクエストは進捗ではありません。古くなっていき、先にマージされるすべてのものと競合する在庫です。#244 は 3 日間待たされ、作り直しが必要になりました。エージェントの適切な数とは、その出力を同じ日のうちに注意深くレビューできる数です。

### すべてのタスクを再開できるようにする

利用上限は、この週で最も役に立つ習慣を教えてくれました。タスクは、その場にいなかった誰かがディスクから再開できなければなりません。状態を保持するのは 3 つの場所です。

- **ブランチ。** エージェントは、ステップがうまくいった時点で、まだ終わっていなくてもブランチにコミットします。コミットのあるワークツリーは、エージェントが生き残れない事態にも耐えて残ります。
- **プルリクエスト。** 説明には、計画、判断、検証の結果を書きます。早めに作成し、計画が変わったら更新してください。
- **台帳。** 1 つのファイルに、オーナーからの未完了の依頼をすべて、その状態、ブランチまたはプルリクエスト、次のステップとともに記録し、何かが変わった瞬間に更新します。11月20日に上限がリセットされたとき、作業はこのファイルから再開しました。キューに入っていたプルリクエストがマージされ、#244 がリベースされ、止まっていたエージェントは、それぞれのブランチと、どこで止まったかのメモを渡されて再起動しました。

### リリースにも同じ規律が必要

プロセスについての教訓が 2 つ、CLI のリリースから得られました。CLI は、同じエージェントと同じルールで運用している、別の非公開リポジトリです。ここではプロセスだけを説明します。リリースパイプラインそのものは、このシリーズの後の記事で扱います。

- **リリースは、それが存在するようになってから記録する。** リリースのワークフローは以前、オーナーが公開を承認する前の、npm にバージョンをステージした時点で、Git のタグと GitHub Releases を作成していました。ステージしたバージョンの 1 つが公開されなかったため、3 つの GitHub Releases が、npm が一度も配信しなかったパッケージを説明することになりました。現在は、npm がそのバージョンを配信した後に別の実行がタグとリリースを書き込み、公開されなかったバージョンにはその旨のラベルが付いています。
- **書き手より先に読み手をリリースする。** CLI とウェブサイトが契約を共有している場合、その変更は、それを送るクライアントより先にサーバーに届かなければなりません。ある CLI のリリースが送った応答を、まだ以前のバージョンの契約のままだったウェブサイトのライセンス API が拒否しました。公開済みの CLI を本番環境に対して確かめる私たち自身のエンドツーエンドのチェックがそれを見つけ、同じ日のうちにウェブサイトの更新で修正されました。現在、契約の変更はまずウェブサイトでリリースします。

### ボトルネックは共有環境だった

`main` のルールセットは、各プルリクエストが `Preview` 環境へのデプロイに成功していることを必須にしており、その環境は 1 つのホストでした。別のプルリクエストがデプロイすると、GitHub は前のデプロイを非アクティブにし、ルールはそれを数えなくなりました。そのため、緑で準備のできたプルリクエストは、隣のプルリクエストがデプロイした瞬間にマージする権利を失いました。そこで私たちのスクリプトは、各プルリクエストのプレビューをマージの直前に、1 件ずつしか通さないデプロイのキューで再デプロイしており、準備のできた 2 つのプルリクエストが同時にマージ可能になることはありませんでした。各マージはプレビューのデプロイを待ち、それは計測した実行では 3.6〜5.3 分かかりました。そして GitHub にマージを拒否されたプルリクエストはリベースされ、プルリクエストの実行全体をもう一度支払いました。

テストも遅かったのですが、作業を直列にしていたのはテストではありませんでした。#275 より前の 11月21日の、成功した 12 回のプルリクエストの実行では、ブラウザーテストのスイートは 1 台のランナーで 13.6〜19.3 分かかり、実行全体は 18.1〜23.9 分、中央値は 21.5 分でした。スイートを半分にすれば、直列のキューの 1 回ごとの番は短くなったでしょう。しかし、準備のできた 2 つのプルリクエストを同じ 5 分の間にマージできるようにはならなかったはずです。

### すぐにできた修正：デプロイの代わりにチェックを

最初の変更では、コードに一切触れませんでした。15:15 UTC に、ルールセットで必須だった `Preview` のデプロイが、プレビューのデプロイのジョブ `Deploy preview / Deploy preview` の必須のステータスチェックに変わりました。ステータスチェックはコミットに属し、別のプルリクエストのデプロイがそれを失敗させることはできないため、準備のできたプルリクエストが互いの順番を奪うことはなくなりました。プレビューホストは共有のままで、そのデプロイも 1 つずつ順に実行されていましたが、誰かがデプロイしたせいで、一度成功したものをもう一度成功させる必要はなくなりました。

### ブラウザーテストのスイートのシャーディング（#275）

#275 は、1 つのブラウザーのジョブを、1 つのビルドと 4 個のシャードに分けました。1 つのジョブがテスト用のデータベースにシードし、`build:test` を実行し、ビルドをそのデータベースとともにアーティファクトとしてアップロードします。各シャードはそれをダウンロードし、Playwright の `--shard` オプションと blob レポーターで、スペックのうち自分の分を実行します。最後のジョブは今も `Build and E2E (chromium)` という名前で、ビルドとすべてのシャードが成功したときだけ成功し、どれかが失敗したときは、シャードのレポートを 1 つの HTML レポートにまとめます。必須のチェックの名前が変わらなかったので、ルールセットの変更は必要ありませんでした。

同じプルリクエストで、小さなコストも 2 つ解消しました。以前は 1 つのブランチの実行が互いの後ろに並んでおり、上の 12 回のうち 3 回は、最初のジョブが始まる前に、同じブランチの古い実行を 13〜15 分待っていました。現在は、新しいコミットが、置き換える前のコミットの実行をキャンセルします。そして、依存関係のキャッシュの 2 回目の復元もなくなりました。プルリクエストの計測では、ジョブごとに約 40 秒かかっていたものです。#275 の後、ビルドは 3.4〜4.7 分、各シャードはさらに 3.2〜5.6 分かかり、最後にまだプレビューのデプロイが残っていたプルリクエストの実行は 13.4〜14.7 分でした。

シャーディングは無料ではありません。各シャードがツールチェーンとブラウザーをもう一度セットアップするため、1 回の実行が使うランナーの時間は以前より増えます。GitHub の標準ランナーを使う公開リポジトリなら、その時間に費用はかかりません。非公開のリポジトリなら、数えておいてください。

### インシデント：ビルドとシャードの間に付いたリリースタグ（#278）

1 つのジョブを複数に分けたことで、1 つのジョブでは起こりえなかった競合状態が生まれました。変更履歴のスペック `content.spec.ts` は、ビルドした変更履歴を Git のリリースタグと比べます。ビルドとテストが 1 つのジョブで動いていたときは、両者は 1 つのチェックアウトを読んでいました。#275 の後は、数分ずれた別々のチェックアウトを読むようになりました。

#273 の実行では、ビルドのジョブが 16:40 UTC にリポジトリをチェックアウトしました。16:44:03 に、#275 のデプロイがリリース `v2026.11.21.9` を公開しました。シャードは 20 秒後に始まり、ビルドした変更履歴が一度も見ていないタグをフェッチし、3 番目のシャードが失敗しました。スペックは `v2026.11.21.9` にリンクした項目を期待しましたが、それは数分前にビルドされたページの知らないリリースでした。

- **症状：** 変更が触れていないコンテンツについてのテストが 1 つのシャードで失敗し、同じコミットが後で成功する。
- **根本原因：** 同じ変化する状態、つまりリポジトリのタグを、異なる瞬間に読むジョブ。1 つのジョブなら 1 つのスナップショットを読んでいましたが、5 つのジョブは 5 つを読みました。
- **修正：** #278 では、ビルドが読んだタグをソートしたリストをビルドと一緒に詰め、各シャードは Playwright が始まる前に、それ以降に作られたタグをすべて削除します。こうして両者が同じ履歴を読みます。スペック、そのリトライ、ビルドは変わっていません。#278 は #275 の 49 分後にマージされました。
- **ルール：** ジョブを分けるときは、実行中に変わりうる、そのジョブが読むものをすべて書き出し、そのスナップショットをアーティファクトと一緒に後のジョブに渡してください。

### GitHub のマージキューと Worker のアップロード（#277）

#277 は、スクリプトと共有プレビューのチェックを一緒に置き換えました。

- **マージキュー。** プルリクエストは今、GitHub のマージキューを通してだけ `main` に入ります。キューは、スカッシュする、すべてのエントリの成功を必須にする、最大 5 つのエントリを同時にビルドする、1〜5 件をまとめてマージする、グループがそろうのを最大 5 分待つ、という設定です。GitHub は各エントリについて、`main` と、その前に並んでいるエントリの上のブランチにスカッシュコミットを書き、そこで必須のチェックを実行し、テストしたそのコミットへ `main` を進めます。失敗したプルリクエストはキューから外れ、その後ろのものは、それを除いてもう一度テストされます。これこそ #220 と #221 に必要だったチェックです。前に並んでいるすべてのものの上で成功しない限り、何も `main` に入りません。
- **デプロイの代わりに Worker のアップロード。** 必須のチェック `Worker upload / Upload preview` は、デプロイと同じようにプレビューの Worker をビルドし、`wrangler versions upload --preview-alias pr-<number>` を実行します。Cloudflare は、サイズ、起動時間、バインディング、必須のシークレットをデプロイのときと同じように確認しますが、そのバージョンはトラフィックを配信しません。`preview.saasyland.com` はそれまで配信していたものを配信し続け、マイグレーションは実行されず、異なるプルリクエストのアップロードは並んで実行されます。準備のできたプルリクエストが共有するものは、もう何もありません。
- **キューを信頼するデプロイ。** `main` へのプッシュでは、最初のジョブが `main` の必須のチェックを読み、プッシュされたコミットでそれぞれの成功した実行を探します。キューがテストしたコミットは、そのまま共有プレビューへ進み（今はそこで `main` が動いています）、続いて本番に進みます。キューを通らなかったコミットは、まずすべてのチェックを実行します。
- **マージのための 1 つのコマンド。** `bun scripts/enqueue-pr.ts <number>` はタイトルを確認し、スカッシュコミットに残る絵文字をタイトルに付け、自動マージを有効にします。これで、チェックが成功したときにプルリクエストがキューに入ります。
- **短くなったローカルの完了の定義。** CI は今、すべてのプルリクエストについて、ほかに誰も使っていないランナーで、プルリクエストとキューの 2 回、ブラウザーテストのスイート全体を実行します。そこでエージェントは、ほかのエージェントと共有するノート PC でスイート全体を実行する代わりに、`check`、`test:coverage`、`build:test`、そして変更が触れるスペックを、自分のポートで実行します。

プルリクエストの実行は今、同時に始まる 3 つのジョブ、つまりカバレッジ付きのチェック、テスト用のビルド、Worker のアップロードと、それに続くシャードでできており、新しいワークフローでの最初の 5 回の実行では 7.7〜9.8 分かかりました。今いちばん長いジョブは、カバレッジ付きの単体テストです。#277 のキューの実行では 7 分 21 秒かかり、11月20日の 3 分 44 秒と比べて長くなっています。次に見るべきところはそこです。

### 多くのエージェントを動かすすべてのチームへの教訓

- **作業を速くする前に、共有リソースを探す。** 目に見えるコストはテストの時間でした。本当のコストは、準備のできたすべての変更が独り占めする必要のある、1 つの環境でした。テストを速くすれば直列のキューの 1 回ごとの番が短くなります。共有の必須条件をなくせば、キューそのものがなくなります。
- **世界の性質ではなく、コミットの性質を必須にする。** デプロイの状態は、ほかの誰かのデプロイによって奪われることがあります。コミットのチェックは奪われません。隣の作業が無効にできる必須条件は、どれも並行作業を直列の作業に変えます。
- **デプロイせずに、変更がデプロイできることを証明する。** プラットフォームが検証し、トラフィックを配信しないアップロードは、共有のデプロイが与えていた保証を、何も共有せずに与えます。
- **組み合わせはキューにテストさせる。** エージェントは、単独では成功する小さな変更を数多く生み出します。リスクは組み合わせにあり、組み合わせを見られるのは、各変更をその前に並んだ変更の上でテストするキューだけです。
- **ジョブを分けるときは、それが読むもののスナップショットを取る。** 並列のジョブは、タグ、デフォルトブランチ、レジストリ、時計を異なる瞬間に読みます。最初のジョブが読んだものを、ほかのジョブに渡してください。
- **信頼する経路を、速い経路にする。** 私たちのデプロイは、キューがまさにそのコミットで実行したものを何も再実行しません。キューを迂回したものは、すべてのチェックの代価をもう一度支払います。
- **実行のデータから、ジョブの単位で計測する。** 実行の所要時間には、最初のジョブの前に待った時間が含まれますが、ジョブの時間には含まれません。その 2 つの差こそ、私たちの時間の多くが消えていた場所でした。

## プレイブック

合うものをコピーしてください。各部分は Git、シェル、GitHub のようなホスティングを前提にしています。コマンドは自分のスタックのものに置き換えてください。

### 分離のセットアップ

現在の main から作る、ブランチごとに 1 つのワークツリーです。

```sh
git fetch origin
git worktree add ../wt-fix-locale -b fix/locale-links origin/main
cd ../wt-fix-locale
bun install --frozen-lockfile
git branch --show-current
```

自分のサーバーで、確認したポートを使い、終わったらプロセス ID で停止するブラウザーテストの実行です。

```sh
PORT=3020
if lsof -nP -iTCP:"$PORT" -sTCP:LISTEN; then echo "port $PORT is taken"; exit 1; fi
bun run db:reset:test
bun run build:test
bun run start:test --port "$PORT" > server.log 2>&1 &
SERVER_PID=$!
until curl -fsS "http://127.0.0.1:$PORT" > /dev/null; do sleep 1; done
LISTENER=$(lsof -nP -iTCP:"$PORT" -sTCP:LISTEN -t | head -1)
test "$(lsof -a -p "$LISTENER" -d cwd -Fn | sed -n 's/^n//p')" = "$(pwd -P)" || exit 1
PLAYWRIGHT_BASE_URL="http://127.0.0.1:$PORT" bun run test:e2e:pr
echo "exit code $?"
kill "$LISTENER" "$SERVER_PID"
```

各エージェントの環境のチェックリストです。

- 現在の `origin/main` から作成した専用のワークツリーとブランチがあり、あなたのチェックアウトは決して使わない
- 依存関係がワークツリーにインストールされ、gitignore 対象のセットアップファイルがコピーされている
- ローカルのデータベースとキャッシュがワークツリーの中にある
- ポートは指示書で割り当てられ、使う前に確認され、待ち受けているプロセスのディレクトリが検証されている
- 下書き、ログ、スクリーンショットのための専用の作業用フォルダーがある
- 最後にプロセスを ID で停止し、ポートが空いている

### 数行で書けるマージキュー

ホスティングにマージキューがあり、ゲートが CI だけなら、ホスティングのキューを使ってください。私たちも今はそうしており、プルリクエストをキューに入れるのは `gh pr merge <number> --auto --squash` という 1 つのコマンドです。下のスクリプトは、ホスティングのキューが実行できないゲートのためのものです。1 つのキューで、一度に 1 件のプルリクエストを、指定した順に処理し、最初の問題で止まります。

```sh
set -euo pipefail
for pr in "$@"; do
  head=$(gh pr view "$pr" --json headRefOid --jq .headRefOid)
  behind=$(gh api "repos/{owner}/{repo}/compare/main...$head" --jq .behind_by)
  if [ "$behind" -gt 0 ]; then
    gh pr update-branch "$pr" --rebase
    while [ "$(gh pr view "$pr" --json headRefOid --jq .headRefOid)" = "$head" ]; do sleep 15; done
    sleep 30
  fi
  gh pr checks "$pr" --watch --required --fail-fast
  gh pr merge "$pr" --squash --subject "$(gh pr view "$pr" --json title --jq .title) (#$pr)"
done
```

ゲートに必要なものを追加してください。必須のデプロイを待つ処理、タイトルがコミットの件名として有効かどうかのチェック、再試行の前の `git log origin/main` の確認などです。実行するインスタンスは 1 つだけにし、決して 2 つにしないでください。

### 指示書のテンプレート

各項目を埋めてください。省略してよいものはありません。

- **目的：** 何を達成するか、そしてその理由。オーナーの言葉を引用する。
- **完了：** 完了の定義のコマンドとその順番、そして各コマンドがプッシュしたコミットで終了コード 0 で終わらなければならないこと。
- **範囲：** 何を変更するか。何を変更しないか。ほかのエージェントが並行して何をしていて、どの部分がそのエージェントのものか。
- **既知の事実：** 何を除外したか、何を試したか、どのファイルと実行に証拠があるか。
- **作業場所：** ワークツリーのパス、ブランチとその起点、作業用フォルダー、ポート。
- **境界：** 承認が必要なパスと、承認があればその引用。決して実行してはならないコマンド。決して停止してはならないプロセス。
- **行き詰まったとき：** 止まり、何をするつもりで、それはなぜかを報告する。
- **報告：** ブランチとコミット、プッシュ済みかどうか。各コマンドとその終了コードとログ。プルリクエストの番号と CI の実行。何を変更したか、何をなぜ省いたか、何に確信が持てなかったか。

### レビューのチェックリスト

- ヘッドコミットがエージェントのテストしたコミットであり、CI がそのコミットで成功している
- レビューに使う環境が、このプルリクエストを表示している
- 説明が差分と一致し、差分に説明が触れていないものが含まれていない
- 変更が範囲内にとどまっている。それ以外のものは別のプルリクエストにする
- 修正が、症状の現れる場所ではなく原因に対処している
- どのテストも簡単になっていない。弱められたアサーション、引き上げられたタイムアウト、新しいスキップ、説明のないモックがない
- 保護されたパスが、引用された承認なしに変更されていない
- ドキュメント、README、文言、変更履歴がすべての言語で更新されている
- コミットが 1 つで、タイトルが Conventional Commits 形式で、帰属表示の行がない
- エージェントが何をしないと決めたかを尋ね、その答えを読んだ

### 運用者のチェックリスト

- 重いエージェントの数をコアの数で制限し、次のエージェントを起動する前にロードアベレージを確認している
- 準備のできたすべてのプルリクエストを順番に入れた、1 つのマージキューが動いている
- 共有環境をレビューの前に予約し、終わったら解放している
- 台帳に、未完了のタスクがすべて、状態、ブランチ、次のステップとともに記載されている
- どのエージェントのタスクも、そのブランチ、プルリクエスト、台帳から再開できる
- 孤立したサーバーと古いワークツリーを、それを起動した人が片付けている
- プルリクエストを準備ができたその日にレビューしている。そうしなければエージェントの速度が落ちる
