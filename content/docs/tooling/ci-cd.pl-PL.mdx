Workflowy znajdują się w `.github/workflows/`. Workflowy aplikacji (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `e2e-reusable.yml` i `deploy-reusable.yml`) konfigurują zestaw narzędzi za pomocą akcji złożonej `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ z wersją Node z `.nvmrc` i cache instalacji Buna, który `setup-vp` przywraca jeden raz, `bun install --frozen-lockfile --ignore-scripts` i `bun run typegen`. `remotion.yml` konfiguruje zamiast tego Node z `.nvmrc` i npm.

| Workflow              | Wyzwalacz                                                                             | Zadania                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requesty, grupy kolejki scalania i wywołania z `deploy.yml`                      | Kontrole, testy z pokryciem na równoległych shardach, E2E w Chromium i przesłanie Workera preview    |
| `deploy.yml`          | Pushe do `main`                                                                       | Kontrole z `ci.yml`, chyba że uruchomiła je kolejka scalania, następnie preview, produkcja i wydanie |
| `preview.yml`         | Ręcznie                                                                               | Wdraża gałąź, której kontrole przeszły, do współdzielonego środowiska preview                        |
| `e2e-full.yml`        | Pushe do `main`, harmonogram <RepositoryFact name="e2eFullSchedule" /> w UTC, ręcznie | WebKit przy pushu; Chromium i WebKit przy uruchomieniach z harmonogramu i ręcznych                   |
| `journey.yml`         | Harmonogram <RepositoryFact name="journeySchedule" /> w UTC, ręcznie                  | [Zestaw testów ścieżki klienta](#journey-suite) na wspólnym preview, w sandboksie Polar              |
| `e2e-reusable.yml`    | Wywoływany przez powyższe workflowy                                                   | Jeden testowy build, jeden projekt Playwright na równoległych shardach i jedna kontrola dla obu      |
| `deploy-reusable.yml` | Wywoływany przez `ci.yml`, `deploy.yml` i `preview.yml`                               | Build, następnie migracje D1 i `wrangler deploy` albo `wrangler versions upload`                     |
| `remotion.yml`        | Zmiany w `remotion/` lub w plikach witryny, które importuje                           | Sprawdza i pakuje projekt wideo strony głównej za pomocą npm                                         |

`remotion.yml` uruchamia się przy pull requestach i pushach dla tych samych ścieżek: `remotion/`, samego workflowu oraz plików witryny, które importuje `remotion/src`, bezpośrednio lub przez inne pliki witryny. `src/__test__/workflows.test.ts` śledzi te importy i kończy się błędem, gdy osiągnięty przez nie plik nie pasuje do żadnej ze ścieżek albo ścieżka nie pasuje do żadnego z plików.

Checkouty w `e2e-reusable.yml`, którego build renderuje historię zmian i którego `content.spec.ts` ją odczytuje, w `deploy-reusable.yml`, który buduje witrynę, oraz w zadaniu `release` pobierają wszystkie commity bez ich drzew (`fetch-depth: 0` i `filter: tree:0`): [historia zmian](/docs/project/changelog) datuje każdy wpis commitem, który wprowadził go do `main`. W porównaniu z płytkim klonem dochodzą tylko same commity; przy płytkim klonie build kończy się błędem, zamiast błędnie datować wpisy. `src/__test__/workflows.test.ts` kończy się błędem, gdy któryś z tych checkoutów przestaje pobierać historię.

## Kontrole [#checks]

Za wymaganą kontrolą `Format, lint, types, i18n, tests` stoją trzy zadania w `ci.yml`:

| Zadanie                                               | Uruchamia                                                                                                                                                                                                                                                |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                               | `bun run check`: tablice nazw klas, kontrole i18n i treści, [spis przepływów](/docs/tooling/test-coverage#flow-coverage), formatowanie, lint i typy                                                                                                      |
| `test`                                                | Jedno zadanie na shard, <RepositoryFact name="vitestShards" /> równolegle: `bun run test:coverage --shard=<n>/<total>` z reporterem blob Vitesta, a następnie przesyła raport blob sharda z jego pokryciem                                               |
| `verify`, o nazwie `Format, lint, types, i18n, tests` | Gdy każdy shard przejdzie, pobiera raporty blob i uruchamia `bun run test:coverage --merge-reports`, które scala pokrycie i egzekwuje progi, a następnie przesyła raport pokrycia; kończy się błędem, jeśli nie przeszły `check`, każdy shard i scalenie |

Shard nie sprawdza żadnego progu, bo mierzy tylko kod, do którego docierają jego własne testy; progi z `vite.config.ts` obowiązują raz, dla scalonego pokrycia wszystkich shardów, tak jak przy lokalnym `bun run test:coverage`. Zadanie `verify` jest jedyną kontrolą wymaganą przez reguły gałęzi, więc dodanie lub usunięcie sharda nie zmienia nazwy żadnej wymaganej kontroli.

Zadanie `e2e` wywołuje `e2e-reusable.yml`, który buduje aplikację raz i uruchamia zestaw testów równolegle na <RepositoryFact name="e2eShards" /> runnerach:

| Zadanie                                       | Uruchamia                                                                                                                                                                                               |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                       | `db:reset:test` i `build:test`, a następnie przesyła `dist`, wskazujący konfigurację Workera `.wrangler/deploy` i wypełniony danymi testowymi `.wrangler/test` jako jeden artefakt                      |
| `shard`                                       | Jedno zadanie na shard, uruchamiane razem z buildem: instaluje przeglądarkę, czeka na przesłanie buildu, pobiera go i uruchamia `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>` |
| `report`, o nazwie `Build and E2E (chromium)` | Kończy się błędem, jeśli build lub którykolwiek shard nie zakończył się powodzeniem; gdy shard zakończył się błędem, scala raporty blob shardów w jeden raport HTML i go przesyła                       |

Shardy nie czekają na zakończenie całego zadania `build` (`needs`): startują razem z nim i konfigurują zestaw narzędzi oraz przeglądarkę, gdy on buduje. Potem `scripts/wait-for-job.ts` co kilka sekund pyta API GitHuba o zadanie `build` tego samego uruchomienia, aż jego krok `Upload the test build` zakończy się sukcesem, a shard pobiera artefakt. Skrypt wysyła ETag poprzedniej odpowiedzi, a GitHub nie wlicza niezmienionej odpowiedzi do limitu żądań tokenu. Nieudany krok buildu albo build, który kończy się bez przesłania, w ciągu kilku sekund kończy niepowodzeniem każdy shard, z nazwą nieudanego kroku i linkiem do buildu, a shard, który czeka dłużej niż limit skryptu, kończy się błędem, który to mówi. Odczyt zadań uruchomienia wymaga `actions: read`, o które prosi tylko zadanie `shard`: `ci.yml`, `e2e-full.yml` i zadanie `checks` w `deploy.yml` przyznają je workflowom, które wywołują, a każde inne zadanie zachowuje `contents: read`.

Własne ponowienia i workery Playwright pozostają na każdym shardzie takie, jak opisuje je [Playwright](/docs/tooling/playwright#configuration). Zadanie `report` jest jedyną kontrolą, której wymagają reguły gałęzi, więc dodanie lub usunięcie sharda nie zmienia nazwy żadnej wymaganej kontroli. Build pakuje też listę tagów wydań, które odczytał, a każdy shard usuwa każdy tag utworzony od tego czasu: `content.spec.ts` czyta tagi wydań z Gita, a wydanie otagowane, gdy shardy czekają, kazałoby mu oczekiwać changelogu, którego build nigdy nie wyrenderował.

Zadanie `upload`, o nazwie `Worker upload`, wywołuje `deploy-reusable.yml` z `upload: true`: buduje Workera preview dokładnie tak jak wdrożenie i uruchamia `wrangler versions upload`, które przesyła go do Workera `saasyland-preview` jako nową wersję, nie wdrażając jej. Cloudflare sprawdza przesłaną wersję tak samo jak wdrożenie, czyli limit rozmiaru, czas uruchamiania, bindingi i sekrety wymienione w `secrets.required`, więc Worker, który przejdzie tę kontrolę, da się wdrożyć, podczas gdy `preview.saasyland.com` nadal serwuje wcześniej wdrożoną wersję. Zadanie nie stosuje żadnej migracji i nie rejestruje wdrożenia GitHub (`deployment: false`), a działa równolegle z przesyłaniem z innych pull requestów. Wersja pull requesta dostaje alias `pr-<number>`, który nazywa wersję w panelu Cloudflare; podsumowanie zadania wypisuje identyfikator i rozmiar wersji oraz jej URL, gdy dla Workera są włączone Version URLs, a dla `saasyland-preview` obecnie nie są. Pull requesty z forków i od Dependabota nie mogą odczytać danych uwierzytelniających Cloudflare i pomijają to zadanie; kolejka scalania, która może je odczytać, przesyła ich build, zanim zostaną scalone.

W pull requeście `bun run check` kończy się też błędem, dopóki pull request nie doda swojego [wpisu w historii zmian](/docs/conventions/git-workflow#changelog-entries), a w kolejce scalania, dopóki nie ma wpisu pull requesta z kolejki. Build w jobach `e2e` i `upload` oraz w jobach wdrożenia kończy się błędem, dopóki historia zmian pokazywałaby w sekcji **Niewydane** wpis inny niż wpis samego pull requesta, a w kolejce scalania i na `main`, dopóki pokazywałaby jakikolwiek.

## Kolejka scalania [#merge-queue]

Ruleset, który chroni `main`, wymaga kontroli `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)` i `Worker upload / Upload preview` i przyjmuje pull requesty wyłącznie przez kolejkę scalania GitHuba (merge queue), która łączy każdy z nich w jeden commit squash. `bun scripts/enqueue-pr.ts <number>` umieszcza pull request w kolejce ([Git i pull requesty](/docs/conventions/git-workflow#merging)). Dla każdego pull requesta w kolejce GitHub zapisuje commit squash na gałęzi o nazwie `gh-readonly-queue/main/pr-<number>-<commit>`, na szczycie `main` i pull requestów przed nim, i uruchamia na niej `ci.yml` dla zdarzenia `merge_group`. Gdy każdy pull request z grupy przejdzie, GitHub przesuwa `main` na ostatni commit grupy, dokładnie ten, który przetestowała kolejka, więc jeden push wprowadza do `main` każdy pull request z grupy jako osobny commit squash. Pull request, który nie przejdzie, opuszcza kolejkę, a te za nim są testowane ponownie bez niego.

`ci.yml` anuluje przebieg pull requesta, gdy zastępuje go nowszy commit, ale nigdy przebiegu kolejki, której każda gałąź ma własną referencję. Kontrola historii zmian traktuje gałąź kolejki jak `main`: każdy pull request z grupy jest już commitem squash, którego temat kończy się jego numerem, więc żaden wpis nie może być niewydany, a wpis samego pull requesta z kolejki musi istnieć.

## Wdrożenia

`deploy.yml` wdraża każdy push do `main`, najpierw do współdzielonego środowiska preview, a potem na produkcję, gdy commit przejdzie wszystkie kontrole, których wymaga `main`. Jego pierwsze zadanie, `tested`, uruchamia `scripts/tested-commit.ts`, który odczytuje te kontrole z rulesetu przez API GitHuba i szuka udanego przebiegu każdej z nich na wypchniętym commicie. Commit, który przeszedł przez kolejkę scalania, je ma, bo kolejka przetestowała właśnie ten commit, więc `deploy.yml` wdraża go bez ponownego uruchamiania kontroli; commit, który trafił do `main` w inny sposób, najpierw przechodzi kontrole z `ci.yml`.

| Zdarzenie                         | Cel                               | Środowisko GitHub                 | URL                                                  |
| --------------------------------- | --------------------------------- | --------------------------------- | ---------------------------------------------------- |
| Push do `main`                    | `preview`, następnie `production` | `Preview`, następnie `Production` | https://preview.saasyland.com, https://saasyland.com |
| Ręczne uruchomienie `preview.yml` | `preview`                         | `Preview`                         | https://preview.saasyland.com                        |

`deploy-reusable.yml` nadaje każdemu środowisku GitHub jego URL, a `src/__test__/workflows.test.ts` kończy się błędem, gdy któryś z nich różni się od hosta środowiska w `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Środowisko preview jest współdzielone: każde wdrożenie zastępuje poprzednie i używa tej samej bazy D1, przestrzeni nazw KV i bucketów R2 środowiska preview. Działa na nim `main`, więc [zestaw testów ścieżki klienta](/docs/tooling/playwright#journey-suite), webhooki sandboksa Polar i logowanie na `preview.saasyland.com`, jedynym hoście preview, któremu ufa Better Auth, trafiają na kod, który produkcja zaraz uruchomi, a każda migracja dociera do bazy preview przed produkcją. Aby wypróbować tam gałąź przed jej scaleniem, uruchom `gh workflow run preview.yml --ref <branch>`: wdraża ono gałąź, razem z migracjami, tylko wtedy, gdy jej commit przeszedł kontrole wymagane przez `main`, a następny push do `main` przywraca tam `main`.

`deploy-reusable.yml` sprawdza obecność sekretów `CLOUDFLARE_API_TOKEN` i `CLOUDFLARE_ACCOUNT_ID`, uruchamia `scripts/verify-bindings.ts`, buduje aplikację z fikcyjnymi wartościami z `.env.test`, usuwa wygenerowany `dist/server/.dev.vars`, stosuje `db:migrate:<target>` i uruchamia `vp exec wrangler deploy --config dist/server/wrangler.json` albo, z `upload: true`, uruchamia `vp exec wrangler versions upload` zamiast dwóch ostatnich kroków. Nie uruchamia `scripts/verify-deployment.ts`, czyli sprawdzenia działającej witryny ze skryptów `deploy:<target>`, ponieważ ochrona Cloudflare przed botami odpowiada kodem 403 na żądania z runnerów CI. Nie uruchamia też `scripts/run-deploy-checks.ts`, więc CI nie wykonuje żadnego ze sprawdzeń przed wdrożeniem, które obszary deklarują w `DEPLOY_CHECKS`: w CI nie ma pliku `.env.<target>`, a środowiska GitHub przechowują tylko dane uwierzytelniające Cloudflare oraz, w `Preview`, ustawienia sandboksa [zestawu testów ścieżki klienta](#journey-suite). Obecnie są to `auth:verify` z obszaru uwierzytelniania i `polar:verify` z obszaru Polar; uruchamiaj lokalnie `bun run auth:verify:<target>` po zmianie klienta OAuth i `bun run polar:verify:<target>` po każdej zmianie w Polar ([Konfiguracja Polar](/docs/getting-started/polar-setup)). Żaden plik sekretów nie jest przesyłany: Worker zachowuje sekrety środowiska uruchomieniowego ustawione już w Cloudflare. Wdrożenia do tego samego celu czekają w kolejce, zamiast wzajemnie się anulować, a przesyłania działają równolegle. Nowy commit w pull requeście anuluje przebieg `ci.yml` dla poprzedniego commita, którego nikt nie scali, natomiast przebiegi kolejki scalania nigdy nie anulują się nawzajem, a przebiegi `deploy.yml` i `e2e-full.yml` na `main` czekają w kolejce (`concurrency` z `queue: max`), więc każdy push do `main` zostaje wdrożony.

Dependabot co tydzień aktualizuje akcje GitHub Actions.

## Zestaw testów ścieżki klienta [#journey-suite]

`journey.yml` uruchamia `bun run test:journey`, czyli [zestaw testów ścieżki klienta](/docs/tooling/playwright#journey-suite), na `https://preview.saasyland.com` według harmonogramu <RepositoryFact name="journeySchedule" /> w UTC i po ręcznym uruchomieniu:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` przyjmuje wartość `all`, `core`, `complete`, `agency` lub `upgrade`; każda wartość poza `all` uruchamia tylko test z tym tagiem. Zadanie odczytuje te sekrety ze środowiska GitHub `Preview`, nie rejestrując wdrożenia (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` i `RESEND_API_KEY`. Ustawia `POLAR_SERVER` na `sandbox`, jedyną wartość, którą zestaw akceptuje, a zestaw tworzy klienta Polar dla sandboksa, więc workflow nie może dotrzeć do produkcyjnego Polar. Uruchomienia ustawiają się w kolejce i nigdy nie anulują się nawzajem, bo anulowane uruchomienie zostawiłoby swoje zamówienia opłacone. Zadanie zapisuje wynik i czas każdego testu oraz błąd każdego nieudanego testu w podsumowaniu uruchomienia i przesyła raport HTML, `playwright-report/journey.json` oraz ślady, nagrania i katalogi maszyn nieudanych testów jako artefakt `journey-report`.

Workflow nie uruchamia się po każdym wdrożeniu `main`. Każde uruchomienie zakłada na preview konto na każdy test, opłaca i zwraca jego zamówienia w sandboksie Polar i wysyła e-maile weryfikacyjne oraz potwierdzenia zakupu przez konto Resend, które preview dzieli z produkcją. W pracowity dzień `main` jest wdrażany wiele razy, więc uruchomienie po każdym wdrożeniu zwielokrotniłoby te e-maile wobec limitów wysyłki, od których zależą e-maile produkcji, i niczego by nie zatrzymało: produkcja jest wdrażana zaraz po preview, cokolwiek znajdzie ścieżka. Nocne uruchomienie wykrywa zepsuty zakup w ciągu doby. Uruchom je ręcznie po zmianie płatności, licencji lub API licencji CLI oraz po `gh workflow run preview.yml --ref <branch>`, aby przetestować gałąź przed scaleniem.

## Wydania i tagi [#releases-and-tags]

Witryna jest wdrażana w sposób ciągły, więc jej wersjami są daty, a nie wersje semantyczne. Gdy wdrożenie produkcyjne zakończy się sukcesem, zadanie `release` w `deploy.yml` oznacza wdrożony commit tagiem `vYYYY.MM.DD` z datą UTC i publikuje dla niego GitHub Release. Drugie wdrożenie produkcyjne tego samego dnia dostaje tag `vYYYY.MM.DD.2`, kolejne `.3` i tak dalej. Wdrożenia preview nigdy nie dostają tagu. Zadanie `release` jako jedyne ma `contents: write`.

Notatki do wydania to wpisy z [historii zmian](/docs/project/changelog), które dostarczyło wydanie, czyli te, które trafiły do `main` od poprzedniego tagu wydania, każdy zakończony `(#<number>)`, co GitHub zamienia w link do jego pull requesta, więc każda zmiana jest opisana w jednym miejscu; gdy wydanie nie dostarczyło żadnego, jego notatki zawierają link do historii zmian. `scripts/publish-release.ts` bierze notatki z `src/lib/release.ts` i uruchamia `gh release create` z tagiem wybranym przez wdrożenie. Ponowne uruchomienie zachowuje tag, który commit już ma, i pomija wydanie, które już istnieje.

Job wdrożenia produkcyjnego wybiera ten tag przed buildem: `scripts/choose-release-tag.ts` stosuje `releaseTag` z `src/lib/release.ts` do tagów checkoutu, build dostaje tag jako `RELEASE_TAG`, a job przekazuje go jobowi `release` jako swoje wyjście `release-tag`, więc wdrożenie i jego wydanie mają jeden tag. Dzięki temu [historia zmian](/docs/project/changelog) linkuje każdy wpis do wydania, które dostarczyło go jako pierwsze: do najstarszego tagu wydania, którego commit zawiera commit squash wpisu w historii pierwszych rodziców `main`, odczytywanej przez build razem z datami w jednym `git log`, albo do własnego tagu wdrożenia dla wpisów, które ono wnosi. Job `release` czyta historię zmian tak samo, z tagiem, który publikuje, więc notatki wydania to dokładnie te wpisy, które strona linkuje do tego wydania. Wpisy scalone przed pierwszym tagiem wydania nie linkują do żadnego wydania, podobnie jak w buildach lokalnych, podglądu i pull requestów wpisy, których żadne wdrożenie jeszcze nie dostarczyło. Dwa wdrożenia produkcyjne nie mogą wybrać tego samego tagu: `deploy.yml` uruchamia naraz tylko jeden przebieg workflow (`concurrency` z `queue: max`), więc job `release` poprzedniego przebiegu utworzył już swój tag, zanim kolejne wdrożenie zrobi checkout repozytorium.

Aby przywrócić produkcję do wybranego wydania, wycofaj w pull requeście wszystko, co nastąpiło po jego tagu:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Po scaleniu kod z tagu zostaje wdrożony po zwykłych kontrolach i oznaczony jako nowe wydanie. Migracje D1 nie są wycofywane, więc starszy kod działa na nowszym schemacie. Każda zmiana schematu musi działać z aplikacją wdrożoną przed nią, dlatego powrót do poprzedniego wydania jest bezpieczny; zanim cofniesz się dalej, przeczytaj migracje dodane w międzyczasie.
