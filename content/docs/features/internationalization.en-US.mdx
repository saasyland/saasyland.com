## Locales

`I18N` in `src/integrations/use-intl/i18n.config.ts` defines `en-US` (default), `de-DE`, `es-ES`, `fr-FR`, `it-IT`, `ja-JP`, `pl-PL`, `pt-BR` and `uk-UA`, the cookie `saasyland.com_locale`, the default time zone `UTC` and the named date formats `FORMATS`.

## URLs

The default locale has no prefix; every other locale is a path prefix, for example `/docs` and `/pl-PL/docs`. For document requests the Worker (`resolveLocale` in `i18n.middleware.ts`) redirects non-canonical paths with a 308: `/en-US/docs` becomes `/docs` and `/pl/docs` becomes `/pl-PL/docs`. `/api` and `/_serverFn` paths never carry a prefix.

The router `rewrite` in `src/router.tsx` removes the prefix from incoming URLs and adds it to outgoing ones, so routes and links use plain paths: `<Link to={ROUTES.SIGN_IN}>`. Raw URLs in the current locale, such as Better Auth `callbackURL` and `errorCallbackURL`, come from `router.buildLocation(...).publicHref`; `localizePathname({ locale, pathname })` builds a URL for a given locale, such as the locale switcher's links and links in emails. `AriaProvider` localizes the `href` of React Aria components.

## Locale cookie

When the locale in a document URL differs from the cookie, the Worker sets the cookie on the response; no code chooses a locale from it. `getCurrentLocale()` works on both sides and reads the URL path, falling back to `en-US`. `/api` and server-function URLs have no prefix, so on the server it returns `en-US` for them. Emails get their locale from the flow instead: auth emails from its `callbackURL`, the newsletter confirmation from the `locale` the form sends.

## Messages

Messages are `messages/<locale>/<namespace>.json`; the file name is the namespace, for example `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` or `common`. Every page namespace has `metadata.title` and `metadata.description`.

- Root namespaces (`common`, `components.*`, `errors*`) are preloaded in the root `beforeLoad`.
- A layout declares `NAMESPACES`, a page declares `NAMESPACE`. Both go into `staticData.namespaces` and are preloaded by the loader:

```ts
loader: async ({ context }) => {
  const locale = getCurrentLocale()
  const [metadata] = await Promise.all([
    loadPageMetadata({ locale, namespace: NAMESPACE }),
    preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
  ])
  return { locale, metadata }
},
```

- `TranslationsProvider` wraps the document body and merges the root namespaces with the namespaces of the matched routes into one `IntlProvider`, so error screens are translated too.
- Emails load their namespace on the server with `loadNamespace`.

## Components

Each component calls `useTranslations` once and names the translator `t`. A component that needs two namespaces uses their common parent or `useTranslations()` with full keys.

## Dates, numbers and time zones

Dates and numbers are formatted with use-intl's `useFormatter` (`format.dateTime`, `format.number`, `format.relativeTime`, `format.list`). The locale decides the conventions: the order of day and month, the 12- or 24-hour clock and the separators. The time zone is the only display preference a user stores.

`TranslationsProvider` gives `IntlProvider` two more values:

- `timeZone`: the `timezone` of the signed-in user from the current session query, or `I18N.DEFAULT_TIMEZONE` (`UTC`) without a session. The provider reads the session that the `/app`, `/admin` and auth route guards load and never fetches it itself, so prerendered public pages are the same for every visitor and hydrate unchanged. When the session query changes, for example after the user saves a new zone in [Settings](/docs/features/settings), every date re-renders.
- `formats`: `I18N.FORMATS`, the named date formats. `src/types/use-intl.d.ts` registers their names with use-intl, so an unknown name fails the type check.

| Name            | English example           | Use                                                                                                         |
| --------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `date`          | Nov 14, 2026              | The day of an instant in the reader's zone, in tables                                                       |
| `dateTime`      | Nov 14, 2026, 3:04 PM UTC | An instant with its time and the zone abbreviation: licence activations and account dates in the admin      |
| `calendarDate`  | Nov 14, 2026              | A date without a time, such as a blog post's date. It is formatted in UTC, so it never moves to another day |
| `calendarDay`   | November 14               | Day labels of the admin analytics chart                                                                     |
| `calendarMonth` | Nov                       | Month labels of the admin dashboard chart                                                                   |

A call can override one option of a named format: `format.dateTime(new Date(post.date), "calendarDate", { month: "long" })`. Admin tables show other users' dates in the viewer's own zone with the abbreviation, so a column reads and sorts in one zone; the user's zone has a column of its own.

## Switching language

`locale-switcher.tsx` has two language controls. `LocaleSwitcher`, in the marketing footer, is a `<details>` menu with a plain link per locale to the current path in that locale, so it works before hydration. `LocaleSelect`, in the docs and customer app sidebars, is a select field styled like `ThemeSwitch` that opens the same URL. Either way, choosing a language loads a new document, and the query string and hash are not carried over. Polish and Ukrainian pages also preload the Latin Extended and Cyrillic font subsets ([Fonts and branding](/docs/ui/fonts-and-branding)).

## Checks

`bun run check:i18n` checks key parity across locales, resolves static keys in their `useTranslations` scope, validates ICU message syntax and checks docs and blog content parity.
