Os workflows ficam em `.github/workflows/`. Os workflows da aplicação (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `updates.yml`, `e2e-reusable.yml` e `deploy-reusable.yml`) preparam a toolchain com a action composta `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ com a versão do Node em `.nvmrc` e o cache de instalação do Bun, que o `setup-vp` restaura uma única vez, `bun install --frozen-lockfile --ignore-scripts` e `bun run typegen`. Já o `remotion.yml` prepara o Node de `.nvmrc` e o npm.

| Workflow              | Gatilho                                                                                    | Jobs                                                                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests, grupos da fila de mesclagem e chamadas do `deploy.yml`                      | Verificações, testes com cobertura em shards paralelos, checagem de tipos sem cada área opcional, E2E no Chromium e o upload do Worker de preview |
| `deploy.yml`          | Pushes para `main`                                                                         | As verificações do `ci.yml`, a menos que a fila de mesclagem já as tenha executado, e depois preview, produção e a release                        |
| `preview.yml`         | Manual                                                                                     | Faz o deploy no preview compartilhado de uma branch cujas verificações passaram                                                                   |
| `e2e-full.yml`        | Pushes para `main`, o agendamento <RepositoryFact name="e2eFullSchedule" /> em UTC, manual | WebKit no push; Chromium e WebKit nas execuções agendadas e manuais                                                                               |
| `journey.yml`         | O agendamento <RepositoryFact name="journeySchedule" /> em UTC, manual                     | A [suíte da jornada do cliente](#journey-suite) contra o preview compartilhado, no sandbox do Polar                                               |
| `updates.yml`         | O agendamento <RepositoryFact name="updatesSchedule" /> em UTC, manual                     | Abre, atualiza ou fecha a [issue de atualizações](#updates)                                                                                       |
| `e2e-reusable.yml`    | Chamado pelos workflows acima                                                              | Um único build de testes, um projeto do Playwright em shards paralelos e uma única verificação para ambos                                         |
| `deploy-reusable.yml` | Chamado por `ci.yml`, `deploy.yml` e `preview.yml`                                         | Build e depois migrações do D1 e `wrangler deploy`, ou `wrangler versions upload`                                                                 |
| `remotion.yml`        | Alterações em `remotion/` ou nos arquivos do site que ele importa                          | Verifica e empacota com npm o projeto do vídeo da landing page                                                                                    |

`remotion.yml` é acionado pelos mesmos caminhos em pull requests e pushes: `remotion/`, o próprio workflow e os arquivos do site que `remotion/src` importa, diretamente ou por meio de outros arquivos do site. `src/__test__/workflows.test.ts` segue essas importações e falha quando um arquivo alcançado não corresponde a nenhum dos caminhos ou quando um caminho não corresponde a nenhum dos arquivos.

Os checkouts em `e2e-reusable.yml`, cujo build renderiza o changelog e cujo `content.spec.ts` o lê, em `deploy-reusable.yml`, que faz o build do site, e no job `release` buscam todos os commits sem as suas árvores (`fetch-depth: 0` e `filter: tree:0`): o [changelog](/docs/project/changelog) data cada entrada pelo commit que a levou à `main`. Em relação a um clone raso, só os próprios commits são acrescentados; com um clone raso o build falharia em vez de datar as entradas errado. `src/__test__/workflows.test.ts` falha quando um desses checkouts deixa de buscar o histórico.

## Verificações [#checks]

Três jobs em `ci.yml` estão por trás da verificação obrigatória `Format, lint, types, i18n, tests`:

| Job                                                  | Executa                                                                                                                                                                                                                                                            |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `check`                                              | `bun run check`: tabelas de nomes de classes, verificações de i18n e de conteúdo, o [inventário de fluxos](/docs/tooling/test-coverage#flow-coverage), as [skills para agentes](/docs/tooling/agent-skills#drift-checks), formatação, lint e tipos                 |
| `test`                                               | Um job por shard, <RepositoryFact name="vitestShards" /> em paralelo: `bun run test:coverage --shard=<n>/<total>` com o reporter blob do Vitest e, em seguida, envia o relatório blob do shard com a sua cobertura                                                 |
| `verify`, chamado `Format, lint, types, i18n, tests` | Quando todos os shards passam, baixa os relatórios blob e executa `bun run test:coverage --merge-reports`, que mescla a cobertura e aplica os limites, e depois envia o relatório de cobertura; falha a menos que `check`, cada shard e a mesclagem tenham passado |

Um shard não verifica nenhum limite, porque mede apenas o código que os seus próprios testes alcançam; os limites de `vite.config.ts` valem uma vez, para a cobertura mesclada de todos os shards, como em um `bun run test:coverage` local. O job `verify` é a única verificação que as regras da branch exigem, então adicionar ou remover um shard não muda o nome de nenhuma verificação obrigatória.

O job `features` roda `bun run check:features <scenario>` uma vez para cada cenário de `scripts/features.ts`, em paralelo. Ele apaga as funcionalidades do cenário, poda o que os arquivos que ficam nomeiam delas, formata os arquivos podados, verifica os tipos do restante e confere as traduções ([Testes](/docs/conventions/testing#tests-follow-the-features)). Um cenário com uma referência que não pode ser podada, um erro de tipo ou um erro de tradução faz o job falhar e, com ele, a execução.

O job `e2e` chama `e2e-reusable.yml`, que faz o build uma única vez e executa a suíte em <RepositoryFact name="e2eShards" /> runners em paralelo:

| Job                                          | Executa                                                                                                                                                                                         |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                      | `db:reset:test` e `build:test` e, em seguida, envia `dist`, o `.wrangler/deploy` que aponta para a configuração do Worker e o `.wrangler/test` já populado pelo seed como um único artefato     |
| `shard`                                      | Um job por shard, iniciado junto com o build: instala o navegador, espera o upload do build, baixa esse build e executa `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>` |
| `report`, chamado `Build and E2E (chromium)` | Falha a menos que o build e todos os shards tenham passado; quando um shard falhou, mescla os relatórios blob dos shards em um único relatório HTML e o envia                                   |

Os shards não esperam o job `build` inteiro terminar (`needs`): começam junto com ele e preparam a toolchain e o navegador enquanto ele compila. Depois, `scripts/download-artifact.ts` consulta a API do GitHub a cada poucos segundos sobre o job `build` da execução, até que o passo `Upload the test build` dele tenha dado certo. Um passo que deu certo não significa que o GitHub já liste o artefato dele, e um download nesse intervalo falha com `Artifact not found`, então o script consulta depois os artefatos da execução até que o GitHub liste `test-worker-<browser>` enviado desde o início do build, e depois baixa ele mesmo esse artefato e o confere com o digest SHA-256 que o GitHub registrou. Um artefato listado ainda pode responder `Not Found` por um instante, então o script pergunta de novo até que o GitHub sirva o arquivo inteiro, e nenhum outro passo o pede nesse meio-tempo. O script envia o ETag da resposta anterior, e o GitHub não conta uma resposta sem mudanças no limite de requisições do token. Um passo do build que falha, ou um build que termina sem o upload, faz todos os shards falharem em poucos segundos, com o passo que falhou e um link para o build, e um shard que espera além do limite do script falha com um erro que diz se falta o passo, a listagem ou o download. Ler os jobs e os artefatos da execução exige `actions: read`, que só o job `shard` pede: `ci.yml`, `e2e-full.yml` e o job `checks` de `deploy.yml` concedem essa permissão aos workflows que chamam, e todos os outros jobs ficam com `contents: read`.

As novas tentativas e os workers do próprio Playwright continuam como o [Playwright](/docs/tooling/playwright#configuration) os descreve, em cada shard. O job `report` é a única verificação que as regras da branch exigem, então adicionar ou remover um shard não muda o nome de nenhuma verificação obrigatória. O build também empacota a lista de tags de release que leu, e cada shard apaga qualquer tag criada desde então: `content.spec.ts` lê as tags de release do Git, e uma release marcada enquanto os shards esperam o faria esperar um changelog que o build nunca renderizou.

O job `upload`, chamado `Worker upload`, chama `deploy-reusable.yml` com `upload: true`: faz o build do Worker de preview exatamente como um deploy faz e executa `wrangler versions upload`, que o envia ao Worker `saasyland-preview` como uma nova versão sem fazer o deploy dela. A Cloudflare verifica o upload como verifica um deploy (o limite de tamanho, o tempo de inicialização, os bindings e os secrets que `secrets.required` lista), então o deploy de um Worker que passa nesta verificação funciona, enquanto `preview.saasyland.com` continua servindo a versão que recebeu deploy antes. O job não aplica nenhuma migração nem registra nenhum deployment do GitHub (`deployment: false`), e roda em paralelo com os uploads de outros pull requests. A versão de um pull request recebe o alias `pr-<number>`, que dá nome à versão no painel da Cloudflare; o resumo do job mostra o ID e o tamanho da versão, e a URL dela quando as Version URLs estão ativadas para o Worker, o que hoje não acontece com o `saasyland-preview`. Pull requests de forks e do Dependabot não conseguem ler as credenciais da Cloudflare e pulam o job; a fila de mesclagem, que consegue, envia o build deles antes de serem mesclados.

Em um pull request, `bun run check` também falha até que o pull request adicione a sua [entrada do changelog](/docs/conventions/git-workflow#changelog-entries), e na fila de mesclagem até que a entrada do pull request enfileirado exista. O build dos jobs `e2e` e `upload`, e o dos jobs de deploy, falha enquanto o changelog listaria em **Não lançado** uma entrada que não seja a do próprio pull request, e na fila de mesclagem e na `main` enquanto listaria qualquer uma.

## Fila de mesclagem [#merge-queue]

O ruleset que protege `main` exige `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)` e `Worker upload / Upload preview`, e só mescla pull requests pela fila de mesclagem do GitHub, que faz squash de cada um. `bun scripts/enqueue-pr.ts <number>` coloca um pull request na fila ([Git e pull requests](/docs/conventions/git-workflow#merging)). Para cada pull request na fila, o GitHub escreve o commit squash em uma branch chamada `gh-readonly-queue/main/pr-<number>-<commit>`, sobre a `main` e os pull requests à frente dele, e executa nela o `ci.yml` para o evento `merge_group`. Quando todos os pull requests de um grupo passam, o GitHub move a `main` para o último commit do grupo, exatamente o commit que a fila testou, de modo que um único push leva cada pull request do grupo à `main` como o seu próprio commit squash. Um pull request que falha sai da fila, e os que estão atrás dele são testados de novo sem ele.

O ruleset também tem `copilot_code_review` com `review_on_push: true`, mas, em 22 de novembro de 2026, o GitHub Copilot não revisou nenhum pull request desde o #70, então os pull requests não recebem revisão automática. Uma revisão seria apenas consultiva: o ruleset não exige nenhuma aprovação nem nenhuma thread de revisão resolvida, então um pull request espera apenas pelos três checks acima.

O `ci.yml` cancela a execução de um pull request quando um commit mais novo a substitui, mas nunca uma execução da fila, cujas branches têm cada uma a sua própria ref. A verificação do changelog trata a branch da fila como a `main`: cada pull request do grupo já é um commit squash cujo assunto termina com o seu número, então nenhuma entrada pode ficar sem lançamento, e a entrada do próprio pull request enfileirado precisa existir.

## Deploys

O `deploy.yml` faz o deploy de todo push para `main`, primeiro no preview compartilhado e depois em produção, quando o commit passou em todas as verificações que a `main` exige. O primeiro job dele, `tested`, executa `scripts/tested-commit.ts`, que lê essas verificações do ruleset pela API do GitHub e procura uma execução bem-sucedida de cada uma no commit enviado. Um commit que veio pela fila de mesclagem as tem, porque a fila testou exatamente esse commit, então o `deploy.yml` faz o deploy dele sem executar as verificações de novo; um commit que chegou à `main` de qualquer outra forma executa primeiro as verificações do `ci.yml`.

| Evento                           | Destino                        | Ambiente do GitHub             | URL                                                  |
| -------------------------------- | ------------------------------ | ------------------------------ | ---------------------------------------------------- |
| Push para `main`                 | `preview`, depois `production` | `Preview`, depois `Production` | https://preview.saasyland.com, https://saasyland.com |
| Execução manual do `preview.yml` | `preview`                      | `Preview`                      | https://preview.saasyland.com                        |

`deploy-reusable.yml` atribui a cada ambiente do GitHub a sua URL, e `src/__test__/workflows.test.ts` falha quando uma delas difere do host do ambiente em `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). O preview é compartilhado: cada deploy substitui o anterior e usa o mesmo banco de dados D1, o mesmo namespace KV e os mesmos buckets R2 de preview. Ele roda a `main`, então a [suíte da jornada do cliente](/docs/tooling/playwright#journey-suite), os webhooks do sandbox da Polar e o login em `preview.saasyland.com`, o único host de preview em que o Better Auth confia, encontram o código que a produção está prestes a rodar, e toda migração chega ao banco de dados de preview antes da produção. Para testar uma branch ali antes de ela ser mesclada, execute `gh workflow run preview.yml --ref <branch>`: ele faz o deploy da branch, com as migrações, só quando o commit dela passou nas verificações que a `main` exige, e o próximo push para `main` coloca a `main` de volta.

`deploy-reusable.yml` verifica a existência dos secrets `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID`, executa `scripts/verify-bindings.ts`, faz o build com os valores fictícios de `.env.test`, remove o `dist/server/.dev.vars` gerado, aplica `db:migrate:<target>` e executa `vp exec wrangler deploy --config dist/server/wrangler.json` ou, com `upload: true`, executa `vp exec wrangler versions upload` no lugar das duas últimas etapas. Não executa `scripts/verify-deployment.ts`, a verificação do site no ar dos scripts `deploy:<target>`, porque a proteção contra bots da Cloudflare responde 403 às requisições dos runners de CI. Também não executa `scripts/run-deploy-checks.ts`, então a CI não executa nenhuma das verificações de deploy, ou seja, dos scripts `<name>:verify:<environment>` do `package.json`: não há `.env.<target>` na CI, e os ambientes do GitHub guardam só as credenciais da Cloudflare, além das configurações do sandbox da [suíte da jornada do cliente](#journey-suite) em `Preview`. Hoje são `auth:verify`, da área de autenticação, e `polar:verify`, da área da Polar; execute localmente `bun run auth:verify:<target>` depois de alterar um cliente OAuth e `bun run polar:verify:<target>` depois de cada alteração na Polar ([Configuração da Polar](/docs/getting-started/polar-setup)). Nenhum arquivo de secrets é enviado: o Worker mantém os secrets de runtime já configurados na Cloudflare. Deploys para o mesmo destino entram em fila em vez de cancelarem uns aos outros, e os uploads rodam em paralelo. Um novo commit em um pull request cancela a execução do `ci.yml` do commit anterior, que ninguém vai mesclar, enquanto as execuções da fila de mesclagem nunca cancelam umas às outras e as do `deploy.yml` e do `e2e-full.yml` na `main` entram em fila (`concurrency` com `queue: max`), então todo push para a `main` recebe deploy.

O Dependabot atualiza as GitHub Actions semanalmente.

## Suíte da jornada do cliente [#journey-suite]

`journey.yml` executa `bun run test:journey`, a [suíte da jornada do cliente](/docs/tooling/playwright#journey-suite), contra `https://preview.saasyland.com` no agendamento <RepositoryFact name="journeySchedule" /> em UTC e quando alguém o inicia manualmente:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` é `all`, `core`, `complete`, `agency` ou `upgrade`; qualquer valor diferente de `all` executa só o teste com essa tag. O job lê estes secrets do ambiente `Preview` do GitHub sem registrar um deploy (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` e `RESEND_API_KEY`. Ele define `POLAR_SERVER` como `sandbox`, o único valor que a suíte aceita, e a suíte cria o cliente do Polar para o sandbox, então o workflow não consegue chegar ao Polar de produção. As execuções entram em fila e nunca cancelam umas às outras, porque uma execução cancelada deixaria os pedidos dela pagos. O job escreve o resultado e a duração de cada teste, e o erro de cada teste que falhou, no resumo da execução, e faz upload do relatório HTML, de `playwright-report/journey.json` e dos traces, vídeos e diretórios de máquina dos testes que falharam como o artefato `journey-report`.

O workflow não roda depois de cada deploy de `main`. Cada execução cadastra uma conta por teste no preview, paga e reembolsa os pedidos delas no sandbox do Polar e envia os e-mails de verificação e as confirmações de compra pela conta do Resend que o preview compartilha com a produção. `main` recebe deploy muitas vezes num dia movimentado, então uma execução depois de cada deploy multiplicaria esses e-mails diante dos limites de envio de que os e-mails da produção dependem, e não impediria nada: a produção recebe o deploy logo depois do preview, seja o que for que a jornada encontre. Cada execução cobre a compra inteira: o cadastro com a verificação do e-mail, um pagamento no sandbox para cada plano, a chave que a Polar emite, a CLI publicada nos dispositivos do plano, o upgrade de Core para Complete e os reembolsos. Ela ainda não está verde: nenhuma execução passou, porque os secrets do workflow não estão configurados, então por enquanto ela não verifica nenhuma compra. Inicie-a manualmente depois de uma mudança em pagamentos, licenças ou na API de licenças da CLI, e depois de `gh workflow run preview.yml --ref <branch>` para testar uma branch antes do merge.

## Atualizações [#updates]

`updates.yml` procura atualizações de dependências e de skills para agentes no agendamento <RepositoryFact name="updatesSchedule" /> em UTC e quando iniciado manualmente. O primeiro passo, `bun scripts/report-updates.ts find`, pergunta ao registro do npm a versão mais recente de cada dependência direta e executa `bun run skills:update` no checkout do runner, do qual nada é commitado, para ver quais skills mudaram na origem. O segundo passo, `bun scripts/report-updates.ts issue`, mantém uma única issue, <RepositoryFact name="updatesIssueTitle" />: abre a issue quando há atualizações, reescreve nas execuções seguintes e fecha quando tudo está em dia. A issue lista cada pacote desatualizado, marcado como movido por `bun run deps:update` ou fixado, e cada skill com os commits entre os quais ela mudaria.

O workflow só pode ler o repositório e escrever issues, e só o segundo passo recebe o token. Ele não abre pull requests, porque o GitHub não inicia nenhum workflow para um pull request aberto pelo próprio token do workflow, então as verificações dele nunca rodariam; execute `bun run deps:update` em uma branch no lugar disso.

## Releases e tags [#releases-and-tags]

O site recebe deploys contínuos, então suas versões são datas, não versões semânticas. Quando um deploy de produção termina com sucesso, o job `release` do `deploy.yml` marca o commit implantado com a tag `vYYYY.MM.DD` na data UTC e publica uma GitHub Release para ele. Um segundo deploy de produção no mesmo dia recebe a tag `vYYYY.MM.DD.2`, o seguinte `.3`, e assim por diante. Deploys de preview nunca recebem tag. O job `release` é o único com `contents: write`.

As notas da release são as entradas do [changelog](/docs/project/changelog) que a release entregou, as que chegaram à `main` desde a tag de release anterior, cada uma terminada em `(#<number>)`, que o GitHub transforma em link para o seu pull request, então cada mudança é descrita em um só lugar; quando uma release não entregou nenhuma, as suas notas apontam para o changelog. `scripts/publish-release.ts` pega as notas de `releaseNotes`, em `src/lib/changelog.ts`, o único elemento de `RELEASE_NOTES`, e executa `gh release create` com a tag que o deploy escolheu, então um projeto sem o changelog publica as releases sem notas. Uma nova execução mantém a tag que o commit já tem e pula uma release que já existe.

O job do deploy de produção escolhe essa tag antes do build: `scripts/choose-release-tag.ts` aplica `releaseTag` de `src/lib/release.ts` às tags do checkout, o build recebe a tag como `RELEASE_TAG` e o job a repassa ao job `release` como a sua saída `release-tag`, então o deploy e a sua release compartilham uma tag. Com ela, o [changelog](/docs/project/changelog) liga cada entrada à release que a entregou primeiro: a tag de release mais antiga cujo commit contém o commit squash da entrada no histórico de primeiros pais da `main`, que o build lê junto com as datas em um único `git log`, ou a própria tag do deploy para as entradas que ele traz. O job `release` lê o changelog da mesma forma, com a tag que publica, então as notas de uma release são exatamente as entradas que a página liga a essa release. Entradas mescladas antes da primeira tag de release não apontam para nenhuma release, nem, nos builds locais, de preview e de pull requests, as entradas que nenhum deploy entregou ainda. Dois deploys de produção não podem escolher a mesma tag: `deploy.yml` roda uma única execução do workflow de cada vez (`concurrency` com `queue: max`), então o job `release` da execução anterior já criou a sua tag quando o próximo deploy faz o checkout do repositório.

Para voltar a produção a uma release, reverta em um pull request tudo o que veio depois da tag dela:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

O merge faz o deploy do código da tag após as verificações de sempre e o marca como uma nova release. As migrações do D1 não são revertidas, então o código mais antigo roda sobre o esquema mais novo. Toda mudança de esquema precisa funcionar com a aplicação implantada antes dela, o que torna isso seguro para a release anterior; leia as migrações intermediárias antes de voltar mais.
