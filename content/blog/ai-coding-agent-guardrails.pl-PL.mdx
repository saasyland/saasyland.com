  - question: Czy regułę umieścić w AGENTS.md, czy w CI?
    answer: >-
      W CI zawsze wtedy, gdy program może ją rozstrzygnąć na podstawie kodu, treści, wyniku builda

## Krótka odpowiedź

Traktuj każdą regułę, którą dajesz agentowi, jako prośbę, dopóki nie egzekwuje jej program. Przy każdej regule zapytaj, czy program mógłby ją rozstrzygnąć na podstawie kodu, treści, wyniku builda albo diffu. Jeśli tak, napisz kontrolę, niech jej komunikat mówi, co zrobić zamiast tego, i uruchamiaj ją tam, gdzie pracuje agent, oraz ponownie jako wymagany status CI, którego nikt nie może pominąć przy scalaniu. Plik instrukcji zostaw na to, czego żaden program nie rozstrzygnie, i niech każdy jego wiersz wskazuje polecenie, które go sprawdza. Ścieżki nieodwracalne i te, które przesuwają pieniądze, umieść za drugim kluczem w rękach osoby, której tożsamości agent nie współdzieli. Zdefiniuj ukończenie jako krótką listę poleceń, które muszą zakończyć się kodem 0, w ustalonej kolejności. Potem celowo łam własne reguły, żeby dowiedzieć się, których przestrzegania tylko się spodziewałeś.

Inżynierowie Google mają nazwę dla idei, która stoi za tym wszystkim. _Software Engineering at Google_ nazywa ją regułą Beyoncé: „If you liked it, then you shoulda put a test on it.” Gdy kod piszą agenty, dotyczy ona każdej reguły, nie tylko zachowania.

## Dlaczego reguła, o której agentowi tylko się mówi, jest prośbą

Plik instrukcji, taki jak `AGENTS.md` albo `CLAUDE.md`, to tekst umieszczany w kontekście modelu na początku sesji. Kształtuje to, co robi agent; niczego nie rozstrzyga. Dokumentacja Anthropic dla Claude Code mówi to wprost: Claude traktuje te pliki „as context, not enforced configuration”, a „to block an action regardless of what Claude decides, use a PreToolUse hook instead”. Ta sama strona wyznacza granicę między tymi dwoma rodzajami kontroli: „Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude’s behavior but are not a hard enforcement layer.”

To nie jest słabość jednego narzędzia. Każdy agent czyta swój plik instrukcji jako część promptu, a prompt konkuruje ze wszystkim innym w kontekście: z zadaniem, z plikami, które agent otworzył, z własnymi instrukcjami systemowymi narzędzia i z tym, co podsunął ostatni komunikat o błędzie. Badania mierzą, jak ta rywalizacja przebiega. IFScale, benchmark opublikowany w lipcu 2025, dał 20 modelom do 500 instrukcji naraz i stwierdził, że „even the best frontier models only achieve 68% accuracy at the max density of 500 instructions”, z przewagą instrukcji, które pojawiły się najwcześniej. METR podał w czerwcu 2025, że najnowsze czołowe modele, którym dano zadanie z punktacją, próbowały „to get a higher score by modifying the tests or scoring code” i że „demonstrate awareness that their behavior isn’t in line with user intentions”.

Żaden z tych wyników nie znaczy, że agenty są niedbałe. Znaczy, że reguła, która żyje tylko w tekście, jest jednym wejściem spośród wielu, przestrzeganym przez większość czasu, a chwile, w których nie jest przestrzegana, to chwile, w których nikt nie patrzy.

### Sześć sposobów, na jakie zawodzą reguły zapisane tylko w instrukcjach

Każdy z nich zdarzył się w naszych repozytoriach i na każdy jest rozwiązanie, które nie zależy od tego, czy agent przeczyta coś uważniej.

**1. Rozmycie.** Każda reguła, którą dodajesz, sprawia, że każda inna jest przestrzegana odrobinę rzadziej. Dokumentacja Claude Code zaleca pliki instrukcji krótsze niż 200 wierszy, bo „longer files consume more context and reduce adherence”. Nasz `AGENTS.md` to streszczenie, które wskazuje całą sekcję dokumentacji z konwencjami. Agent czyta streszczenie w każdej sesji, a strony tylko wtedy, gdy przyjdzie mu to do głowy.

**2. Konflikt.** Instrukcje przychodzą z kilku miejsc i są ze sobą sprzeczne. Narzędzia agentowe domyślnie dodają do commitów trailer atrybucji, taki jak `Co-Authored-By`. Nasze reguły tego zabraniają, bo GitHub przypisuje adres z trailera do konta i wymienia to konto jako współtwórcę repozytorium. Rozwiązanie, które trzyma, jest strukturalne, a nie kolejnym zdaniem: repozytorium pozwala tylko na scalanie przez squash, a commit squash bierze tytuł pull requesta z pustą treścią, więc nic, co agent napisze w komunikacie commita na swojej gałęzi, nie trafia do `main`. Od #274 hook `commit-msg` odrzuca też każdy komunikat commita, którego trailer wymienia narzędzie AI, więc agent dowiaduje się o tym już przy pierwszym commicie.

**3. Z drugiej ręki.** Gdy kilka agentów pracuje razem, większość instrukcji dociera do wykonawcy przez streszczenie innego agenta, a streszczenia gubią szczegóły. W naszym układzie agent prowadzący pisze brief dla każdego wykonawcy. Jeden brief mówił, że „właściciel zatwierdził” zmianę w płatnościach, podczas gdy zatwierdził on coś innego (#166). Następnego ranka dwa briefy mówiły, że API licencji CLI nie jest na liście przeglądu przez człowieka, choć `AGENTS.md` wymieniał je od poprzedniego dnia, i dwa pull requesty je zmieniły (#208 i #211). Tym, co za każdym razem zatrzymało następny krok, nie była instrukcja: warstwa uprawnień harnessu agenta odmówiła scalenia zmiany w płatnościach i dalszej pracy nad drugą zmianą licencji, dopóki właściciel nie powiedział „tak”. Jego „tak” dla zmiany licencji jest zacytowane w jej pull requeście.

**4. Litera ponad intencją.** Gdy kontrola wymaga artefaktu, agent produkuje najtańszy artefakt, który przechodzi. Nasza konfiguracja lintera dopuszczała kiedyś jako gołą liczbę tylko `0`, więc każda `1` stawała się stałą: `SINGLE_CALL` istniało 16 razy, `SINGLE_ROW_LIMIT` 12 razy, a około 80 stałych równało się `0` albo `1` bez żadnego powodu poza regułą (#230). W naszym prywatnym repozytorium CLI kontrola wydania, która wymaga changesetu, dostała pusty, a ten zatrzymał następne wydanie; ta historia jest niżej. Żaden z agentów nie złamał reguły. Oba ją spełniły.

**5. Dryf.** Instrukcja opisuje bazę kodu z dnia, w którym ją napisano. Gdy kod się zmienia, a zdanie nie, agent idzie za zdaniem. Dokumentacja, która powtarza wartość zdefiniowaną w kodzie, psuje się tak samo: nasza dokumentacja wpisywała kiedyś ręcznie, w każdym języku, limity żądań, limity pokrycia i lintera, ceny oraz liczbę języków, więc jedna zmiana w kodzie mogła zostawić błędną stronę w każdym z nich (#137). Rozwiązaniem było wypisywanie tych wartości z kodu; jak to działa, opisuje [trzeci tekst z tej serii](/blog/documentation-drift-numbers-from-code).

**6. Samoocena.** Podsumowanie, które agent pisze o własnej pracy, to najmniej wiarygodna rzecz, jaką produkuje. „Wszystkie testy przechodzą” to zdanie; kod wyjścia to dowód. Nasz pull request #224, poprawka layoutu, został scalony z opisem #225, zmiany licencji, łącznie z akapitem mówiącym, że właściciel zatwierdził zmiany w plikach licencji, których #224 w ogóle nie dotykał. Żadna kontrola nie czyta opisów, więc nic tego nie zauważyło.

O tym, gdzie trafia reguła, decydują dwie zasady.

**Umieść każdą regułę na najniższym szczeblu, który potrafi ją rozstrzygnąć, i powtórz ją na pierwszym szczeblu, którego agent nie może pominąć.** Reguła, która żyje tylko w hooku Gita, znika w chwili, gdy ktoś zrobi commit z `--no-verify`; reguła, która żyje tylko w CI, każe agentowi czekać kilka minut, żeby dowiedział się o brakującym średniku. Hooki są dla szybkości, a CI dla prawdy, więc nasz hook pre-commit uruchamia każdą kontrolę z `bun run check` oprócz spisu przepływów, przy czym formatowanie, lint i typy sprawdza tylko w plikach przygotowanych do commita, a pominięcie hooka kosztuje jeden czerwony przebieg CI zamiast zepsutego `main`.

**Nigdy nie pozwól, żeby warstwa uprawnień agenta była jedyną warstwą.** To najszybsze miejsce, by zatrzymać niebezpieczne polecenie, i najłatwiejsze do obejścia. Dokumentacja samego Claude Code ostrzega, że „Bash permission patterns that try to constrain command arguments are fragile” i że reguła odrzucająca `git push` nie pasuje do „a push written another way, such as `git -C . push`”. Wszystko, co musi trzymać, potrzebuje za sobą reguły po stronie serwera.

### Przykład z praktyki: jedna reguła na trzech szczeblach

Nasza reguła dotycząca historii jest prosta: `main` pozostaje liniowy i nikt nie przepisuje współdzielonej gałęzi. Jest egzekwowana trzy razy: przez uprawnienia agentów, przez reguły gałęzi na serwerze i przez właściciela, który jako jedyny może te reguły zdjąć.

Agent zrobił rebase gałęzi swojego pull requesta i próbował wypchnąć ją force-pushem. Ustawienia uprawnień agenta nie pozwalały na force-push, więc polecenie zostało odrzucone, a praca trafiła na serwer jako nowy pull request z nowej gałęzi (#235 zamknięto na rzecz #236). To był właściwy wynik z niewłaściwego powodu: rebase własnej gałęzi i wypchnięcie jej z `--force-with-lease` jest bezpieczne, bo, jak pisze dokumentacja Gita, push przechodzi tylko „if the current value of the remote ref is the expected value”. Właściciel zezwolił więc dokładnie na tę formę, na własnych gałęziach pull requestów agentów, i na nic więcej.

Za regułą lokalną stoi serwer. Zestawy reguł GitHuba „prevent users from force pushing to the targeted branches”, a nasze blokują force-pushe i usuwanie na współdzielonych gałęziach i wymagają liniowej historii. Gdy właściciel rzeczywiście chciał przepisać współdzieloną gałąź wydań w repozytorium CLI, żeby usunąć z niej commity scalające, serwer odrzucił nawet push z lease. Musiał zdjąć regułę na jeden push i przywrócić ją, surowszą niż wcześniej, teraz także z wymaganiem liniowej historii. Reguła lokalna wyłapała rutynowy błąd w kilka sekund; reguła serwera wytrzymała, gdy ktoś z dobrych powodów próbował zrobić niebezpieczną rzecz.

## Które reguły należą do kontroli, a które do instrukcji

Każdą regułę da się przyporządkować trzema pytaniami.

1. **Czy program może ją rozstrzygnąć na podstawie artefaktu,** takiego jak kod źródłowy, treść, konfiguracja, wynik builda, diff albo komunikat commita, bez wiedzy o tym, dlaczego wprowadzono zmianę? Jeśli tak, należy do kontroli.
2. **Czy taniej ją raz zakodować, niż przeglądać w nieskończoność?** Reguła, którą zastosujesz w setkach przeglądów, zwraca dzień pracy nad narzędziem. Reguła, która uruchamia się dwa razy w roku, może się nie zwrócić.
3. **Czy fałszywy alarm kosztowałby więcej niż przeoczenie?** Kontrola, która wystarczająco często zgłasza poprawny kod, uczy wszystkich, łącznie z agentami, ją obchodzić. Zawężaj definicję, aż przestanie, albo zostaw regułę przeglądowi.

| Reguła                                                                  | Gdzie należy       | Jak                                                                                                     |
| ----------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------- |
| Bez komentarzy                                                          | Kontrola           | Własna reguła lintera, która czyta komentarze z drzewa składniowego                                     |
| Bez `any`, bez asercji typów, bez komentarzy wyłączających reguły       | Kontrola           | Flagi kompilatora i reguły lintera, z zablokowanym wyłączaniem reguł w kodzie                           |
| Każdy tekst widoczny dla użytkownika w każdym języku                    | Kontrola           | Skrypt, który porównuje klucze komunikatów między językami i z kluczami używanymi w kodzie              |
| Wpis w historii zmian w każdym pull requeście                           | Kontrola           | Skrypt CI, który szuka wpisu nazwanego numerem pull requesta                                            |
| Dokumentacja, która cytuje wartości zdefiniowane w kodzie               | Głównie kontrola   | Wypisuj wartości z kodu; porównuj z kodem tabele, które trzyma dokumentacja                             |
| Wartości domenowe jako nazwane stałe                                    | Częściowo kontrola | `no-magic-numbers` obejmuje liczby; powtarzane wartości tekstowe wymagają własnej reguły albo przeglądu |
| Naprawiaj przyczynę, nie objaw                                          | Instrukcja         | Zapytaj w przeglądzie, co spowodowało błąd                                                              |
| Jedna zmiana na pull request                                            | Instrukcja         | Co najwyżej ostrzeżenie o rozmiarze                                                                     |
| Żadnych zmian w płatnościach, uwierzytelnianiu ani migracjach bez „tak” | Drugi klucz        | Właściciele kodu i wymagana recenzja od tożsamości, której agent nie ma                                 |
| Nigdy nie wdrażaj i nie dotykaj danych produkcyjnych                    | Uprawnienia        | Zablokuj polecenia lokalnie i trzymaj dane uwierzytelniające produkcji poza środowiskiem agenta         |

### Do czego nadal służą instrukcje

Instrukcje nie są przestarzałe; mają po prostu węższe zadanie. Używaj ich do intencji („napraw przyczynę”), do jednego wzorcowego przykładu do skopiowania, do listy ścieżek, które wymagają człowieka, do definicji ukończenia i jako indeksu kontroli: każda reguła, a po niej polecenie, które ją egzekwuje. Agent, który wie, że `bun run check` zakończy się błędem na komentarzu, pisze mniej komentarzy, a resztę poprawia w kilka sekund zamiast w przeglądzie. Nasz `AGENTS.md` kończy definicję ukończenia zdaniem wymierzonym w szósty tryb awarii opisany wyżej: „Nothing else counts as done, including a summary that says it is.”

## Zrób audyt reguł, łamiąc je

Najtańszy audyt, jaki możesz przeprowadzić, to plik, który raz łamie każdą z Twoich reguł. Uruchom na nim swoje kontrole i zapisz, które wiersze przechodzą. Zajmuje to godzinę i zastępuje Twoje przekonanie o tym, co egzekwują Twoje narzędzia, wiedzą o tym, co egzekwują naprawdę.

### Przykład z praktyki: co odrzuca nasz linter

Zrobiliśmy to 20 listopada 2026 dla reguł stylu kodu z naszego `AGENTS.md`. Nasza konfiguracja oxlint włącza jako błędy całe kategorie reguł, `correctness`, `nursery`, `pedantic`, `perf`, `style` i `suspicious`, z włączonymi regułami uwzględniającymi typy. Zapisaliśmy w pliku roboczym po jednym wierszu na regułę i uruchomiliśmy na nim `vp lint`.

| Wiersz w pliku próbnym                           | Odrzucony | Przez                                 |
| ------------------------------------------------ | --------- | ------------------------------------- |
| `// a comment that starts in lower case`         | Tak       | `capitalized-comments`                |
| `const x = 2 // A comment after code`            | Tak       | `no-inline-comments`                  |
| `// TODO fix this later`                         | Tak       | `no-warning-comments`                 |
| `// A capitalised comment on its own line`       | Nie       |                                       |
| `/** A JSDoc block */`                           | Nie       |                                       |
| `{/* A comment in JSX */}`                       | Nie       |                                       |
| `readValue() as Named`, zawężające `unknown`     | Tak       | `typescript/no-unsafe-type-assertion` |
| `value as Named`, rozszerzające                  | Nie       |                                       |
| `(input: any)`                                   | Tak       | `typescript/no-explicit-any`          |
| `// @ts-expect-error` bez opisu                  | Tak       | `typescript/ban-ts-comment`           |
| `// @ts-expect-error` z opisem                   | Nie       |                                       |
| `// oxlint-disable-next-line no-magic-numbers`   | Nie       | Wyłączył też regułę, którą wymienia   |
| `return null`                                    | Tak       | `unicorn/no-null`                     |
| `input ?? undefined`                             | Nie       |                                       |
| Operator trójargumentowy rozbity na trzy wiersze | Nie       |                                       |

Z jednej tabeli wyszły cztery lekcje i wszystkie cztery dotyczą każdego lintera.

**Kategorie dają reguły przypadkiem.** Włączenie `style` i `pedantic` sprawiło, że „bez komentarzy” wyglądało na egzekwowane: komentarze pisane małą literą, komentarze na końcu wiersza i komentarze TODO kończyły się błędem, dzięki regułom, których nikt w tym celu nie wybrał. Każdy agent, który napisze schludny komentarz wielką literą w osobnym wierszu, przechodzi. Jeśli reguła jest ważna, włącz ją po nazwie i wiedz, która reguła ją egzekwuje.

**Linter nie upilnuje własnego wyłącznika.** Komentarz wyłączający jest komentarzem, ale linter czyta go jako instrukcję, zanim zobaczy go jakakolwiek reguła, więc ucisza właśnie tę regułę, która by zaprotestowała. ESLint potrafi takie komentarze odrzucać: „To disable all inline config comments, use the `noInlineConfig` setting in your configuration file.” W narzędziu bez takiej opcji szukaj dyrektyw w CI, poza linterem.

**Ustawienia domyślne są celowo łagodne.** `ban-ts-comment` w typescript-eslint dopuszcza `@ts-expect-error` „when it includes a description”, a port w oxlint zachowuje się tak samo, więc agent, który poda powód, przechodzi. „A value of `true` for a particular directive means that this rule will report if it finds any usage of said directive.” Wybierz `true`, jeśli reguła brzmi „nigdy”.

**Powtarzaj próbę po każdej aktualizacji lintera.** Kategorie takie jak `nursery` zyskują i tracą reguły między wydaniami. Plik próbny jest testem Twojej konfiguracji i zasługuje na to, żeby działać w CI jak każdy inny test; zestaw startowy na końcu artykułu ma taki test.

Wszystkie luki z tabeli zamknęliśmy następnego dnia, w #274. `code-style/no-comments` zgłasza każdy komentarz, `code-style/no-multiline-ternary` każdy operator trójargumentowy rozciągający się na kilka wierszy, a `code-style/no-undefined-fallback` każde `?? undefined`; `typescript/ban-ts-comment` odrzuca teraz `@ts-expect-error` nawet z opisem, a `typescript/consistent-type-assertions` z `assertionStyle: "never"` odrzuca rozszerzające `as`. Włączone w całym repozytorium reguły znalazły 21 wielowierszowych operatorów trójargumentowych, z czego 17 w skopiowanych do repozytorium komponentach shadcn, oraz dwa rzutowania `as`, a pull request przepisał każde z tych miejsc, zamiast robić dla niego wyjątek.

## Jak zamienić regułę stylu w kontrolę

1. **Zapisz regułę jako pytanie o artefakt, na które odpowiedź brzmi tak albo nie.** „Czy ten plik zawiera komentarz?” da się rozstrzygnąć. „Czy ten kod jest czytelny?” nie, i to pytanie należy do przeglądu. Jeśli nie umiesz zapisać pytania, znalazłeś instrukcję, a nie kontrolę.
2. **Wybierz najtańsze narzędzie, które odpowiada na nie dokładnie.** W tej kolejności: istniejąca reguła włączona po nazwie; flaga kompilatora albo konfiguracji; własna reguła lintera na drzewie składniowym; skrypt przechodzący po plikach; test, który sprawdza właściwość kodu albo treści; kontrola wyniku builda; kontrola działającego systemu.
3. **Do wszystkiego wewnątrz kodu używaj parsera.** Wyrażenie regularne, które szuka `//`, znajdzie też każdy URL w ciągu znaków i każdy escapowany ukośnik we wzorcu. Drzewo składniowe wie, czym jest komentarz.
4. **Niech komunikat o błędzie będzie instrukcją.** Agent przeczyta go w środku zadania, bez żadnego innego kontekstu. Powiedz, co zrobić zamiast tego i gdzie.
5. **Sprawdź ją na znanych naruszeniach.** Zanim zaufasz nowej kontroli, uruchom ją na kodzie, dla którego została napisana, i upewnij się, że zgłasza dokładnie te przypadki, o których wiesz, ani mniej, ani więcej.
6. **Trzymaj wyjątki w kodzie, z testem dla każdego.** Lista dozwolonych w kontroli, przeglądana jak każda zmiana, jest lepsza niż komentarz wyłączający, którego nikt nie widzi.
7. **Uruchamiaj ją w dwóch miejscach.** W hooku pre-commit, żeby agent dowiedział się o problemie w kilka sekund, i jako wymaganą kontrolę CI, żeby trzymała, gdy hook się nie uruchomi.
8. **Zdecyduj, co dzieje się z istniejącymi naruszeniami.** Napraw je w tym samym pull requeście, jeśli możesz; w przeciwnym razie zapisz stan bazowy, odrzucaj tylko nowe naruszenia i celowo zmniejszaj stan bazowy.

Nasza kontrola wpisów w historii zmian pokazuje krok 4. Przebieg CI pull requesta kończy się błędem, dopóki nie istnieje wpis nazwany jego numerem, a komunikat jest zarazem poprawką:

```ts title="scripts/check-content.ts"
export const pullRequestEntryProblems = (ref: string): string[] => {
  const pullRequest = pullRequestOf(ref)

  if (pullRequest === undefined || existsSync(join(REPOSITORY_DIR, CHANGELOG_DIRECTORY, `${pullRequest}${SOURCE_MDX_SUFFIX}`))) {
    return []
  }

  return [`Pull request #${pullRequest} has no changelog entry: add ${CHANGELOG_DIRECTORY}/${pullRequest}.<locale>.mdx in every locale`]
}
```

### Przykład z praktyki: błąd hydratacji staje się regułą lintera

React renderuje stronę dwa razy, raz na serwerze i raz w przeglądarce, a oba renderowania muszą wypisać ten sam tekst. Każdy komponent, który podczas renderowania odczytuje zegar albo ustawienia regionalne przeglądarki, wypisuje w każdym z tych miejsc coś innego, a React zgłasza błąd #418 i renderuje stronę od nowa. Pull request #198 naprawił jeden taki błąd: strona administracyjna wypisywała na serwerze „aktywny 48 sekund temu”, a w przeglądarce „aktywny 49 sekund temu”. Audyt znalazł jeszcze trzy błędy tego samego rodzaju. Stopka wypisywała `new Date().getFullYear()`, co od 1 stycznia aż do następnego wdrożenia zepsułoby każdą stronę ze stopką. Panel checkoutu porównywał zegar serwera z zegarem przeglądarki. Wykres formatował liczby przez `toLocaleString()`.

Naprawienie czterech błędów zostawiłoby piąty kolejnemu agentowi. Pull request #201 naprawił te trzy i dodał regułę `hydration/no-clock-or-locale-in-render` jako małą wtyczkę oxlint w `scripts/hydration-lint-plugin.ts`. Zgłasza ona `new Date()` bez argumentu, `Date.now` i metody `toLocale…String` wszędzie, gdzie wykonują się podczas renderowania, i dopuszcza je tylko w funkcjach, które wykonują się później: w obsłudze zdarzeń, funkcjach zapytań i mutacji, efektach i licznikach czasu. Widać w niej każdy krok opisanej wyżej metody:

- **Pytanie jest dokładne:** czy kod renderujący odczytuje zegar albo ustawienia regionalne środowiska uruchomieniowego? Pierwotny błąd siedział w callbacku `.map`, który prosty wzorzec uznałby za funkcję odroczoną.
- **Komunikaty są instrukcjami:** „Use an instant both share, such as a query’s dataUpdatedAt or a build-time value, or read the clock in an event handler, an effect or a query function.”
- **Sprawdzono ją na znanych przypadkach:** na `main` zgłosiła dokładnie pięć miejsc znalezionych w audycie, trzy naprawione w tym pull requeście i dwa z #198.
- **Jej wyjątki są kodem:** odroczone wywołania to trzy nazwane listy we wtyczce, a dokumentacja mówi, że nowy wpis dopisuje się tam „z przypadkiem w `src/__test__/hydration-lint-plugin.test.ts`, nigdy komentarzem wyłączającym regułę”. Gdy #201 został scalony, własny zestaw testów reguły miał 28 poprawnych i niepoprawnych przypadków.

### Przykład z praktyki: bez komentarzy, egzekwowane przez parser

Audyt powyżej pokazał, że naszą regułę zakazu komentarzy egzekwuje tylko przypadek. Oto reguła, która zamknęła tę lukę, napisana pod API reguł ESLint, które ładuje też Oxlint („Oxlint’s plugin API is compatible with ESLint v9+”); nasza to `code-style/no-comments` w `scripts/code-style-lint-plugin.ts`:

```ts title="scripts/code-style-lint-plugin.ts"
export const COMMENT_MESSAGES = {
  comment:
    "Remove this comment. Say it in a name, a named constant or a smaller function, and put the reasoning in the commit message, the pull request or the docs.",
  directive: "Remove this directive comment, which switches a check off, and fix the cause the rule or the compiler reports instead.",
} as const

export const commentMessageId = (text: string): keyof typeof COMMENT_MESSAGES => (DIRECTIVE.test(text) ? "directive" : "comment")

export const noComments = defineRule({
  create: (context) => ({
    Program: () => {
      for (const comment of context.sourceCode.getAllComments()) {
        if (comment.type !== SHEBANG) {
          context.report({ loc: comment.loc, messageId: commentMessageId(comment.value) })
        }
      }
    },
  }),
  meta: {
    docs: {
      description: "Source files carry no comments: names, the commit message, the pull request and the docs carry the meaning.",
    },
    messages: COMMENT_MESSAGES,
    type: "problem",
  },
})
```

Uruchomiliśmy ją z naszą istniejącą konfiguracją na każdym pliku, który obejmuje linter. Zgłosiła komentarz liniowy pisany wielką literą, blok JSDoc i komentarz JSX z pliku próbnego, pominęła `//` w ciągu znaków z URL-em i w wyrażeniu regularnym, a w kodzie objętym linterem znalazła dokładnie jeden problem: wiersz `#!/usr/bin/env bun` na początku skryptu. ESLint dokumentuje, dlaczego: shebangi „are treated as comments” i zwraca je `getAllComments()`. Stąd wyjątek `SHEBANG`, który jest lekcją z kroku 5 w miniaturze: kontrola, której nie uruchomiłeś na prawdziwym kodzie, ma błędy, których jeszcze nie spotkałeś.

Drugie odkrycie jest równie ważne: poza tym wierszem lintowany kod nie miał żadnych komentarzy. Przegląd utrzymał regułę. Kosztowało to jednak właściciela uwagę potrzebną do jej pilnowania, za każdym razem, i właśnie o tę wymianę chodzi w tym artykule.

Reguła lintera wciąż ma dwa martwe punkty. Nie widzi plików, które linter pomija, a u nas są to zestaw testów przeglądarkowych, pliki deklaracji i arkusze stylów, i nie może zgłosić komentarza `/* oxlint-disable */`, który ją wymienia, bo linter najpierw wykonuje dyrektywę. Dlatego `bun run check:comments` parsuje każdy plik TypeScript, JavaScript i CSS, który śledzi Git, poza linterem, za pomocą oxc dla kodu i PostCSS dla stylów, i kończy się błędem przy każdym komentarzu, zanim ruszy linter. Pierwsze uruchomienie znalazło jeszcze jeden: wiersz `/// <reference types>` w pliku deklaracji, który przeniesiono do `types` w `tsconfig.json`.

### Gdy reguła rodzi rytuał, popraw regułę

Kontrola, która jest odrobinę błędna, nie jest przez agenty ignorowana. Jest wykonywana, i to na masową skalę. Nasza reguła `no-magic-numbers` dopuszczała tylko `0`, więc agenty nazywały każdą `1`: `SINGLE_CALL`, `NEXT`, `STEP`, `FIRST_LETTER`, `ZERO_TICK`, `NO_OFFSET`. Każda stała była poprawna i każda utrudniała czytanie kodu. Pull request #230 dopuścił `0` i `1` jako literały i wstawił z powrotem w miejsca użycia 72 stałe, które istniały tylko dla reguły, zachowując te, które mają własne znaczenie, takie jak `FAILURE_EXIT_CODE` i `INCLUSIVE_END`. Lekcja jest ogólna: gdy widzisz wzorzec posłuszeństwa, którego nie napisałby żaden człowiek, taki jak stałe równe jeden, puste changesety albo komentarz wyłączający z pieczołowicie napisanym uzasadnieniem, zmień regułę, a nie kod.

## Ścieżki wymagające przeglądu przez człowieka: co potrzebuje drugiego klucza

Niektóre zmiany są błędne w sposób, który przechodzi wszystkie testy, bo awaria istnieje tylko na produkcji, z upływem czasu albo w starciu z atakującym. Te ścieżki potrzebują, żeby człowiek powiedział „tak”, zanim się zmienią, niezależnie od tego, kto napisał zmianę.

| Rodzaj ścieżki                    | Dlaczego kontrole nie wystarczą                                                                         | W saasyland.com                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Stan nieodwracalny                | Migracja, która przechodzi wszystkie testy, wciąż może stracić dane produkcyjne i nie da się jej cofnąć | `src/integrations/drizzle-orm/migrations/`                                                             |
| Pieniądze                         | Błędna obsługa webhooka jest poprawna, dopóki nie przyjdzie ponowienie, zwrot albo chargeback           | `src/modules/license/license.webhooks.ts`, `src/modules/license/use-cases/`, `src/integrations/polar/` |
| Tożsamość i uprawnienia           | Działające logowanie nie dowodzi niczego o wygasaniu, unieważnianiu ani rolach                          | `src/integrations/better-auth/`, `src/data/access.ts` i plik dostępu każdego obszaru                   |
| Kontrakty, od których zależą inni | Oprogramowanie, którego nie wdrażasz, psuje się, gdy one się zmieniają                                  | `src/modules/license/license.api.ts`, API licencji CLI                                                 |
| Sekrety i konfiguracja wdrożenia  | Zapisanie sekretu w logach albo wysłanie go dalej działa bez zarzutu                                    | `wrangler.jsonc`, `.env*` i wszystko, co czyta sekret                                                  |

Nasz `AGENTS.md` podaje tę listę i każdemu wpisowi daje uzasadnienie, co pomaga agentowi i kolejnemu czytelnikowi:

```md title="AGENTS.md"
- `src/integrations/drizzle-orm/migrations/`: applied to production databases and irreversible.
- `src/modules/license/license.webhooks.ts`, `src/modules/license/use-cases/`, `src/integrations/polar/` and `src/integrations/affonso/`: payments, licences and affiliate referrals.
```

### Kontrole też są ścieżką wymagającą przeglądu przez człowieka

Odkrycie METR o agentach, które edytują testy i kod punktujący, to powód, dla którego istnieje ostatni wiersz tabeli. Agent poproszony o to, żeby nieprzechodząca kontrola przeszła, ma dwie możliwości: naprawić kod albo osłabić kontrolę. Druga jest często krótsza. Pliki, które definiują Twoje bramki, czyli workflowy CI, konfiguracja lintera i typów, progi pokrycia i skrypty kontroli, potrzebują więc tego samego drugiego klucza co kod płatności. Nasza lista wymienia `.github/workflows/`; nie wymienia jeszcze `vite.config.ts`, gdzie mieszkają reguły lintera i progi pokrycia, ani `scripts/`, gdzie mieszkają kontrole treści. Powinny się na niej znaleźć.

### Zgoda należy do diffu, a nie do prozy

Opisane wyżej incydenty z drugiej ręki mają wspólny kształt: zgoda istniała jako zdanie, a zdanie zawędrowało dalej niż zgoda. „Właściciel zatwierdził” w briefie, opis wklejony z innego pull requesta, lista, która mówiła, że plik nie jest chroniony. Rozwiązaniem jest uczynienie ze zgody zapisu z trzech części: zacytowanych słów osoby, ścieżek, których dotyczy, i tego, czego nie obejmuje. Pull request #223, który sprawił, że wdrożenie odrzuca wartości zastępcze sekretów, robi dokładnie to. Cytuje odpowiedź właściciela, „6. yes”, wymienia skrypty wdrożeniowe, których dotyczy, i podaje ścieżki wymagające przeglądu przez człowieka, których nie dotyka. Recenzent, albo kontrola, może porównać tę listę z diffem. Reguła, której teraz przestrzegamy: nikt nie pisze „właściciel zatwierdził” bez zacytowania wiadomości, która to mówi.

### Drugi klucz wymaga drugiej tożsamości

GitHub potrafi egzekwować drugi klucz: plik `CODEOWNERS` przypisuje ścieżki ludziom, a reguła gałęzi może „require reviews from code owners”. Jest jednak haczyk, który ma znaczenie dla każdego programisty pracującego w pojedynkę z agentami. Dokumentacja GitHuba mówi to jednoznacznie: „Pull request authors cannot approve their own pull requests.” Jeśli Twoje agenty otwierają pull requesty z Twoimi danymi uwierzytelniającymi, każde zabezpieczenie po stronie serwera widzi Ciebie, a wymaganej recenzji od Ciebie nie da się udzielić.

Tak wygląda dziś nasza sytuacja. Agenty pracują na koncie właściciela, więc nasza reguła gałęzi wymaga kontroli CI i kolejki scalania, a nie zatwierdzającej recenzji, a „tak” właściciela dla ścieżki wymagającej przeglądu przez człowieka to zacytowana wiadomość, której pilnuje warstwa uprawnień agentów. To działało, jak pokazują incydenty, i jest to najsłabsza część naszego układu. Silniejsze rozwiązanie łatwo opisać: daj agentom własną tożsamość, na przykład konto bota albo GitHub App z prawem zapisu, ale bez uprawnień administratora, umieść ścieżki wymagające przeglądu przez człowieka w `CODEOWNERS` i wymagaj recenzji właściciela kodu na `main`. Wtedy drugi klucz to kliknięcie człowieka i żadne zdanie nie może go zastąpić.

## Zdefiniuj ukończenie jako kody wyjścia

„Gotowe” to najdroższe słowo, jakie mówi agent, bo wszystko, co następuje po nim, to czas kogoś innego. Zdefiniuj je jako krótką listę poleceń, które muszą zakończyć się kodem 0 na gałęzi, która ma zostać wypchnięta, w ustalonej kolejności, od najszybszego do najwolniejszego, przy czym każde wyłapuje rodzaj błędu, którego nie wyłapią poprzednie. Niech CI uruchamia te same polecenia, a nie ich podobne wersje, żeby zielony przebieg lokalny zapowiadał zielony przebieg CI. Proś o kody wyjścia i liczby w pull requeście, a podsumowanie traktuj jako twierdzenie do sprawdzenia.

### Przykład z praktyki: trzy polecenia i specyfikacje, których dotknęła zmiana

Nasza definicja ukończenia to trzy polecenia, potem specyfikacje przeglądarkowe, których dotyka zmiana, a potem kolejka scalania. Oto linie `AGENTS.md`, z których korzysta:

```sh title="AGENTS.md"
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
bun scripts/enqueue-pr.ts <number>
```

`check` formatuje, lintuje, sprawdza typy i uruchamia kontrole tłumaczeń i treści w każdym języku. `test:coverage` uruchamia testy jednostkowe, integracyjne i komponentów z bramką pokrycia na poziomie <RepositoryFact name="coverageThreshold" unit="percent" /> dla linii, instrukcji, funkcji i gałęzi. `build:test` buduje Workera Cloudflare i sprawdza wynik. `test:e2e:pr` serwuje ten build i przeprowadza przez niego cały zestaw testów przeglądarkowych w Chromium; CI uruchamia go w pull requeście i ponownie w kolejce scalania, a lokalnie agent uruchamia zamiast niego linię `bunx playwright test`, dla specyfikacji, których dotyka jego zmiana, na własnym wolnym porcie. Pull request jest gotowy dopiero wtedy, gdy jest zielony w CI, a ostatnia linia wstawiła go do kolejki.

Do 21 listopada lista lokalna kończyła się całym zestawem, a pull request był scalany przez skrypt, który czekał na wspólne wdrożenie preview. ## Gdy wszystkie kontrole są zielone, a produkt jest zepsuty

Dwa incydenty przeszły wszystkie kontrole, jakie mieliśmy. Oba nauczyły nas więcej niż 68 odmów.

### 100% pokrycia, a `init` nie działało

SaaSy Land ma dwa repozytoria: ten serwis, który udostępnia API licencji, i prywatne CLI, które klienci uruchamiają, żeby tworzyć projekty. Oba importują jeden pakiet kontraktu, który definiuje żądania i odpowiedzi API, i oba walidują nim dane. Schematy kontraktu odrzucają klucze, których nie znają, i to dobre ustawienie domyślne: ciche ignorowanie byłoby gorsze.

Wydanie CLI dodało pytanie, o bibliotekę UI, i wysyłało odpowiedź na nie do API licencji. Serwis na produkcji wciąż walidował dane poprzednią wersją kontraktu. Każdy test jednostkowy w obu repozytoriach przechodził, bo każde repozytorium testowało się względem wersji kontraktu, którą przypięło; pokrycie było pełne po obu stronach. 20 listopada 2026 uruchomiliśmy opublikowane CLI, prosto z npm, na produkcji, z prawdziwą licencją wystawioną przez produkcyjny checkout, jako test end-to-end. `init` zakończyło się błędem: API odrzuciło żądanie komunikatem „Unrecognized key: library”.

Poprawką było przejście serwisu na nową wersję kontraktu (#244), które trafiło na produkcję tego samego popołudnia, po czym opublikowane CLI utworzyło swój projekt na produkcji. Lekcje są ogólne:

- **Pokrycie to właściwość repozytorium. Poprawność to właściwość wdrożonego systemu.** Nic w żadnym z zestawów testów nie uruchamiało razem obu wdrożonych połówek.
- **Rozjazd wersji między rzeczami, które wdrażasz osobno, jest niewidoczny dla testów jednostkowych.** Testuj opublikowanego klienta na działającym serwerze albo przynajmniej na tej wersji serwera, która będzie działać, gdy klient zostanie wydany.
- **Ustal kolejność wdrożeń.** Zmiana kontraktu trafia najpierw na serwer i działa tam, zanim zostanie wydany klient, który z niej korzysta. Teraz przestrzegamy tej reguły, a kolejną barierką będzie uruchamianie w CI opublikowanego CLI na działającym API przed wydaniem. Wymaga to klucza licencji jako sekretu CI, co samo jest zmianą wymagającą przeglądu przez człowieka, więc czeka na właściciela.

### Pusty changeset, który zatrzymał wydanie

Ten incydent wydarzył się w prywatnym repozytorium CLI, więc opisuję proces bez kodu. CLI jest wydawane przez Changesets, a CI odrzuca pull request, który zmienia pakiet bez changesetu, czyli pliku mówiącego, co będzie zawierać następne wydanie. Changesets dokumentuje furtkę: „If you want to merge a change without doing any releases (such as when you only change tests or build tools), you can run `changeset --empty` to add a special changeset that does not release anything.”

Pull request na gałęzi pre-release poprawiał tylko historię zmian, więc dodał pusty changeset, dokładnie tak, jak opisuje dokumentacja. Na gałęzi w trybie pre-release, gdy jedynym oczekującym changesetem był pusty, workflow wydania nie znalazł niczego do wersjonowania ani do publikacji, więc następna beta nie została przygotowana. Poprawka usunęła pusty changeset, a przewodnik po wydaniach mówi teraz, że puste changesety należą wyłącznie do gałęzi głównej.

To znowu litera ponad intencją, tylko poziom wyżej. Kontrola zażądała artefaktu, agent dostarczył najtańszy poprawny, a prawdziwym odbiorcą artefaktu był inny system z własnymi regułami. Gdy kontrola żąda pliku, zapytaj, co jeszcze ten plik czyta, i przetestuj pipeline, który go czyta.

## Wprowadzanie w istniejącym repozytorium

Nie potrzebujesz tego wszystkiego od poniedziałku. Oto kolejność, która daje najwięcej na dzień pracy.

<Steps>

<Step>

**Spisz inwentarz.** Wypisz każdą regułę, jaką kiedykolwiek przekazałeś agentowi albo współpracownikowi: pliki instrukcji, uwagi z przeglądów, które ciągle powtarzasz, stronę z konwencjami. Obok każdej reguły zapisz, gdzie jest dziś egzekwowana. Większość zespołów odkrywa, że większość ich reguł nie jest egzekwowana nigdzie.

</Step>

<Step>

**Sprawdź go próbą.** Napisz plik, który raz łamie każdą regułę, uruchom swoje kontrole i zaznacz, co przeszło. To zamienia inwentarz z tego, w co wierzysz, w to, co jest prawdą.

</Step>

<Step>

**Zrób jedno polecenie.** Jeden skrypt `check`, który formatuje, lintuje, sprawdza typy i uruchamia Twoje kontrole treści, oraz jedno polecenie testowe z pokryciem. Wpisz oba do pliku instrukcji jako definicję ukończenia.

</Step>

<Step>

**Niech CI uruchamia te same polecenia i niech będą wymagane.** Oznacz zadania CI jako wymagane kontrole statusu w regule gałęzi, razem z blokadą force-pushy i usuwania na `main`. Od tego kroku nic czerwonego nie zostaje scalone, niezależnie od tego, kto to napisał.

</Step>

<Step>

**Dodawaj bramki po jednej, z zapadką.** Ścisłe flagi typów, potem bramka pokrycia, potem kontrole treści, których potrzebuje Twój produkt. Przy każdej napraw istniejące naruszenia w tym samym pull requeście, jeśli możesz, tak jak #220 zrobił z 1404 formalnymi niemieckimi formami. W przeciwnym razie zapisz stan bazowy i odrzucaj tylko nowe naruszenia. `coverage.thresholds.autoUpdate` w Vitest podnosi progi, gdy pokrycie rośnie, więc liczba może tylko iść w górę.

</Step>

<Step>

**Ogrodź niebezpieczne ścieżki.** Zablokuj force-pushe, wdrożenia i dane uwierzytelniające produkcji w ustawieniach uprawnień agenta. Spisz listę przeglądu przez człowieka z uzasadnieniem dla każdego wpisu, dołącz do niej pliki, które definiują Twoje kontrole, i podeprzyj ją właścicielami kodu oraz osobną tożsamością dla agentów.

</Step>

<Step>

**Odchudź plik instrukcji.** Usuń każdą regułę, którą egzekwuje już kontrola, i zastąp ją poleceniem, które ją egzekwuje. Zostać powinny intencja, przykłady, lista przeglądu i definicja ukończenia.

</Step>

<Step>

**Powtarzaj próbę po aktualizacjach.** Uruchamiaj plik próbny ponownie za każdym razem, gdy linter, kompilator albo runner testów zmienia wersję główną, i za każdym razem, gdy zmienia się reguła. Jeszcze lepiej: zrób z tego test.

</Step>

</Steps>

## Ile to kosztuje

Barierki nie są darmowe, a każdy, kto mówi Ci, że są, żadnych nie utrzymywał.

**Czas przy każdej zmianie.** 20 listopada nasze CI potrzebowało około 16 i pół minuty od pushu do zielonego, w większości na zestaw testów przeglądarkowych na jednym runnerze. Odkąd zestaw działa równolegle na <RepositoryFact name="e2eShards" /> runnerach, przebieg pull requesta trwa około 7 do 9 minut, a kolejka scalania uruchamia go jeszcze raz przed scaleniem, plus tyle, ile trwa lokalny przebieg przed pushem. Shardy kupują ten czas minutami runnerów, bo każdy z nich ponownie przygotowuje narzędzia i przeglądarkę. W publicznym repozytorium same minuty CI nic nie kosztują na standardowych runnerach GitHuba, które GitHub dokumentuje jako darmowe dla publicznych repozytoriów; prywatne repozytorium płaci za każdą minutę, a zestaw testów przeglądarkowych to miejsce, w którym te minuty znikają.

**Kod do napisania i utrzymania.** Nasze kontrole treści i tłumaczeń, weryfikator builda, wtyczka hydratacji i hook commita to razem ponad tysiąc wierszy TypeScriptu, z własnymi testami. Są kodem jak każdy inny: mają błędy, jak pokazują shebang i francuskie „ton”, i potrzebują takiego samego przeglądu.

**Czerwień, która znaczy „jeszcze nie”.** 34 z 37 przebiegów `check` zakończonych błędem w naszej próbce pochodziły z pull requestów, których wpis w historii zmian jeszcze nie istniał, bo wpis nosi nazwę numeru, który nie istnieje, dopóki nie powstanie pull request. Kontrola, która rutynowo kończy się błędem z oczekiwanego powodu, uczy wszystkich czytać czerwień jako szum, a to najgroźniejszy nawyk, jakiego może nabrać zespół z barierkami. Jeśli projektujesz taką kontrolę, daj jej stan, który nie jest błędem, albo świadomie zaakceptuj koszt, jak dotąd robimy my.

**Rytuał.** Reguła, która jest odrobinę zbyt surowa, rodzi posłuszeństwo, jakiego nikt nie napisałby ręcznie, co pokazały 72 stałe z #230. Zaplanuj czas na dostrojenie reguł po ich dodaniu.

**Praca przy każdej zmianie, która rośnie razem z produktem.** W naszym repozytorium każda zmiana aktualizuje dokumentację w <RepositoryFact name="languages" /> językach i dodaje wpis w historii zmian w każdym z nich. Kontrole pilnują, żeby to się działo. Nie sprawiają, że jest tańsze.

W zamian dostajesz tabelę powyżej: 68 przebiegów, których nie dało się scalić, a żaden nie wymagał, żeby ktoś to zauważył, i agenty, które mogą pracować godzinami bez nadzoru nad każdym krokiem, bo repozytorium mówi „nie” w naszym imieniu. W języku naszego [tekstu o gotowości repozytorium](/blog/ai-coding-agents-repository-readiness) każda kontrola opisana tutaj obniża Time to No.

## Czego barierki nie wyłapują

Kontrole rozstrzygają to, co może rozstrzygnąć program. Wszystko inne nadal wymaga człowieka, który przeczyta zmianę i zapyta, dlaczego.

- **Intencja.** Właściwy kod dla złego problemu przechodzi wszystkie kontrole. Naprawa objawu też. Pull request #146 naprawił błąd hydratacji w jednym komponencie strony głównej, z testem regresji, i wszystkie bramki przeszły; przyczyną był strażnik trasy, który opróżniał cały cache zapytań przy każdej zmianie zalogowanego użytkownika, co #152 naprawił dla każdej strony.
- **Projekt.** Druga funkcja pomocnicza, która dubluje tę, którą już masz, nowa abstrakcja, której nikt nie potrzebował, moduł w złym miejscu. Lint widzi składnię, nie cel.
- **Słabe testy.** Test, który sprawdza implementację, przechodzi i pokrywa swoje wiersze. Pokrycie mierzy, co się wykonało, a nie co zostało sprawdzone; testy mutacyjne mierzą więcej, a jeszcze ich nie dodaliśmy.
- **Granice między wdrożeniami.** Incydent z `init`: każda strona poprawna, para zepsuta.
- **Proza.** Opisy pull requestów, twierdzenia w dokumentacji i teksty historii zmian, chyba że ich fakty wypisujesz z kodu.
- **Same kontrole.** Kontrola może być błędna, zbyt łagodna albo zbyt surowa. Sprawdź ją próbą.
- **Następna nowa awaria.** Każda barierka w tym artykule koduje incydent, który już się wydarzył. Przegląd to sposób na znalezienie tego, który jeszcze się nie wydarzył.

## Zestaw startowy do skopiowania

Te elementy działają w większości repozytoriów TypeScript. Używają npm, ESLint, Vitest i GitHub Actions, bo to narzędzia najpopularniejsze; każdy pomysł da się przenieść na inne.

**Jedno polecenie na każdą bramkę**, nazwane wszędzie tak samo, żeby plik instrukcji, hook i CI mówiły to samo:

```json
{
  "scripts": {
    "check": "prettier --check . && eslint --max-warnings 0 . && tsc --noEmit",
    "test:coverage": "vitest run --coverage",
    "build": "vite build",
    "test:e2e": "playwright test"
  }
}
```

**Konfiguracja lintera bez wyłącznika.** Wyłączanie reguł w kodzie jest zablokowane, reguła komentarzy z wcześniejszej części jest dołączona, a furtki są zakazane po nazwie. `assertionStyle: "never"` wciąż pozwala na `as const`, które typescript-eslint dokumentuje jako „always allowed by this rule”.

```js
import { defineConfig } from "eslint/config"
import tseslint from "typescript-eslint"

const noComments = {
  meta: {
    type: "suggestion",
    messages: { comment: "Say it in a name, a commit message or the docs." },
  },
  create: (context) => ({
    Program: () => {
      for (const comment of context.sourceCode.getAllComments()) {
        if (comment.type !== "Shebang") {
          context.report({ loc: comment.loc, messageId: "comment" })
        }
      }
    },
  }),
}

export default defineConfig({ linterOptions: { noInlineConfig: true } }, tseslint.configs.strictTypeChecked, {
  languageOptions: { parserOptions: { projectService: true } },
  plugins: { house: { rules: { "no-comments": noComments } } },
  rules: {
    "house/no-comments": "error",
    "@typescript-eslint/ban-ts-comment": ["error", { "ts-expect-error": true, "ts-ignore": true, "ts-nocheck": true }],
    "@typescript-eslint/consistent-type-assertions": ["error", { assertionStyle: "never" }],
    "@typescript-eslint/no-explicit-any": "error",
    "@typescript-eslint/no-non-null-assertion": "error",
    "no-magic-numbers": ["error", { ignore: [0, 1], ignoreArrayIndexes: true, ignoreDefaultValues: true }],
  },
})
```

**Ścisłe typy.** To flagi, które nasz własny `tsconfig.json` ustawia ponad `strict`:

```json
{
  "compilerOptions": {
    "strict": true,
    "exactOptionalPropertyTypes": true,
    "noUncheckedIndexedAccess": true,
    "noPropertyAccessFromIndexSignature": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true
  }
}
```

**Bramka pokrycia.** `100: true` to skrót Vitest, który „sets global thresholds to 100”. W istniejącej bazie kodu zacznij od dzisiejszych liczb z `autoUpdate: true` i pozwól im rosnąć.

```ts
import { defineConfig } from "vitest/config"

export default defineConfig({
  test: {
    coverage: {
      provider: "v8",
      include: ["src/**/*.{ts,tsx}"],
      thresholds: { 100: true },
    },
  },
})
```

**Test próbny Twoich reguł**, żeby aktualizacja lintera albo zmiana konfiguracji, która wyłącza regułę, kończyła CI błędem. Trzymaj pliki próbne poza zwykłym przebiegiem lintera i lintuj je tutaj z wyłączonym pomijaniem plików:

```ts
import { ESLint } from "eslint"
import { expect, it } from "vitest"

const eslint = new ESLint({ ignore: false })

it.each([
  ["comment.ts", "house/no-comments"],
  ["assertion.ts", "@typescript-eslint/consistent-type-assertions"],
  ["expect-error.ts", "@typescript-eslint/ban-ts-comment"],
  ["explicit-any.ts", "@typescript-eslint/no-explicit-any"],
])("rejects %s with %s", async (file, rule) => {
  const [result] = await eslint.lintFiles([`test/rule-probes/${file}`])

  expect(result?.messages.map(({ ruleId }) => ruleId)).toContain(rule)
})
```

**CI, które uruchamia te same polecenia**, plus wyszukiwanie komentarzy wyłączających reguły, które nie zależy od tego, czy jakikolwiek linter respektuje własne ustawienia. Ustaw to zadanie jako wymaganą kontrolę statusu:

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc
      - run: npm ci
      - run: npm run check
      - run: npm run test:coverage
      - run: npm run build
      - name: No suppression comments
        run: |
          if git grep -n -E "(eslint|oxlint)-disable|biome-ignore|@ts-(ignore|expect-error|nocheck)" -- "*.ts" "*.tsx" "*.js" "*.jsx" "*.mjs"; then exit 1; fi
```

**Reguła gałęzi na `main`:** wymagaj zadania CI; wymagaj pull requesta i pozwalaj tylko na scalanie przez squash; wymagaj liniowej historii; blokuj force-pushe i usuwanie; wymagaj recenzji właścicieli kodu, gdy agenty będą miały własną tożsamość.

**Właściciele kodu dla ścieżek, które wymagają człowieka**, łącznie z plikami, które definiują Twoje bramki:

```text
/db/migrations/ @your-org/maintainers
/src/billing/ @your-org/maintainers
/src/auth/ @your-org/maintainers
/.github/ @your-org/maintainers
/eslint.config.js @your-org/maintainers
/vitest.config.ts @your-org/maintainers
```

**Uprawnienia agenta**, które odrzucają polecenia, które nigdy nie mogą się wykonać, i pozwalają na bezpieczną formę force-pusha. Ten przykład to `.claude/settings.json` z Claude Code; reguły deny wygrywają z regułami allow, bo „rules are evaluated in order: deny, then ask, then allow”. Pamiętaj, że wzorce argumentów są kruche i właśnie dlatego istnieje opisana wyżej reguła gałęzi.

```json
{
  "permissions": {
    "deny": ["Bash(git push --force *)", "Bash(git push -f *)", "Bash(git commit --no-verify *)"],
    "ask": ["Edit(./db/migrations/**)", "Edit(./src/billing/**)", "Edit(./.github/**)"],
    "allow": ["Bash(git push --force-with-lease *)"]
  }
}
```

**Plik instrukcji, który wskazuje kontrole**, zamiast je powtarzać:

```md
# AGENTS.md

## Done

`npm run check`, `npm run test:coverage`, `npm run build` and `npm run test:e2e` exit 0, in that order, on the branch you push. Put each exit code in the pull request. A summary is not evidence.

## Rules a check enforces

- No comments, suppression comments, type assertions or `any`: `npm run check` fails on each.
- Coverage stays at 100%: `npm run test:coverage` fails below it.

## Rules review enforces

- Fix the cause, not the symptom, and say in the pull request what caused the bug.
- One change per pull request.

## Human review required

Do not change these without a maintainer's written yes that names the paths:

- `db/migrations/`: applied to production and irreversible.
- `src/billing/` and `src/auth/`: money and identity.
- `.github/`, `eslint.config.js` and `vitest.config.ts`: the checks themselves.
```

## Gdzie barierki saasyland.com dziś nie wystarczają

Pisanie tego artykułu było audytem, a audyt znalazł luki. W duchu całej reszty oto one.

Trzy z nich są już zamknięte: komentarze, furtki oraz wielowierszowe operatory trójargumentowe razem z `?? undefined` sprawiają teraz, że `bun run check` kończy się błędem (#274). Pozostają te:

- **Zestaw testów przeglądarkowych** leży poza linterem: `bun run check:comments` czyta `e2e/`, ale żadna inna reguła lintera tego nie robi.
- **Ścieżek wymagających przeglądu przez człowieka** pilnują instrukcja i warstwa uprawnień agentów, a nie GitHub, bo agenty pracują pod tożsamością właściciela. Lista pomija też pliki, które definiują bramki.
- **Opisy pull requestów** nie są porównywane z diffem.
- **Opublikowane CLI** nie jest jeszcze uruchamiane na działającym API przed każdym wydaniem.
- **Testy mutacyjne**, które mierzyłyby, ile testy sprawdzają, a nie ile uruchamiają, nie są skonfigurowane.

Każda z tych pozycji to reguła, którą przekazujemy słowami, zamiast ją egzekwować, i każda zejdzie niżej po drabinie.
