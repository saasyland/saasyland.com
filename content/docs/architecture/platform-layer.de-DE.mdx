## Worker und Bindings

`wrangler.jsonc` legt `src/server.ts` als Einstiegspunkt des Workers fest. Der Worker erhält vier Bindings:

| Binding  | Typ              | Verwendet für                                                    |
| -------- | ---------------- | ---------------------------------------------------------------- |
| `DB`     | D1-Datenbank     | Alle Tabellen, einschließlich Sessions und Rate-Limit-Zählern    |
| `CACHE`  | KV-Namespace     | Die Anzahl der GitHub-Sterne und die regionalen Checkout-Rabatte |
| `MEDIA`  | R2-Bucket        | Videodateien, ausgeliefert von `serveMedia` unter `/media/`      |
| `ASSETS` | Statische Assets | Vorgerenderte Seiten und Dateien aus `public`                    |

Requests an `/assets/*`, `/fonts/*`, `/robots.txt` und `/llms.txt` werden aus den statischen Assets bedient, ohne dass der Worker läuft. Servercode liest Bindings, Secrets und `waitUntil` aus `cloudflare:workers`. `src/server.ts` fügt jeder Antwort, die es zurückgibt, die Sicherheits-Header hinzu; Dateien, die ohne den Worker ausgeliefert werden, erhalten die Teilmenge aus `public/_headers` ([Sicherheit und Härtung](/docs/features/security)).

## Umgebungen

`wrangler.jsonc` definiert vier Umgebungen. `CLOUDFLARE_ENV` wählt eine davon für `vp dev` und `vp build` aus.

| Umgebung      | Bindings                                                 | Verwendet von                                   |
| ------------- | -------------------------------------------------------- | ----------------------------------------------- |
| `development` | Remote-Preview-D1, -KV und -R2                           | `bun run dev`                                   |
| `preview`     | Preview-D1, -KV und -R2                                  | `bun run build:preview`, `deploy:preview`       |
| `production`  | Produktions-D1, -KV und -R2                              | `bun run build:production`, `deploy:production` |
| `test`        | Lokale D1, lokaler KV und lokales R2 in `.wrangler/test` | `bun run build:test`, Playwright                |

Jede Umgebung listet ihre benötigten Secrets unter `secrets.required` auf. Die Werte stammen aus der passenden Datei `.env.<environment>`; die Deploy-Skripte übergeben sie mit `--secrets-file` an Wrangler. Die Umgebung `test` verwendet `src/platform/testing/worker.ts` als Einstiegspunkt und die eingecheckten Dummy-Werte aus `.env.test`.

## Typen

- `src/types/bindings.d.ts` deklariert `Cloudflare.Env`: die Bindings und jedes Secret, das der Worker liest. Die drei `CLOUDFLARE_*`-Secrets sind nicht deklariert, weil nur drizzle-kit sie liest, und zwar aus `process.env`.
- `src/types/worker-configuration.d.ts` wird von `bun run cf-typegen` generiert.
- `src/types/router.d.ts` registriert den Router-Typ und die Routenoption `staticData.namespaces`.

## Verdrahtung der Testlaufzeit

`src/platform/testing` enthält nur, was zu keinem einzelnen Feature gehören kann:

- `setup.ts`: jest-dom-Matcher, ein Zurücksetzen der Bindings vor jedem Test und der Ersatz für `createServerFn`, der Server Functions im selben Prozess ausführt
- `mocks/cloudflare.ts`: eine D1 auf Basis von SQLite im Arbeitsspeicher, die die eingecheckten Migrationen ausführt, ein KV im Arbeitsspeicher, ein `MEDIA`-Bucket im Arbeitsspeicher und ein `waitUntil`, das Tests flushen können
- `mocks/cache.ts`: `createEdgeCache`, ein Stub des Workers-Cache für die Tests der Medienauslieferung
- `mocks/providers.ts`: Abfangen von fetch-Aufrufen an Resend und Polar in Browsertests, einschließlich mitgeschnittener E-Mails
- `mocks/wrksz-themes.ts`: ein Ersatz für die Theme-Bibliothek
- `lib/`: die RPC-Brücke für Server Functions, Render-Helfer, Helfer für Request-URLs und Query-Runner
- `worker.ts`: der Worker-Einstiegspunkt für Browsertests, der ausgehende E-Mails mitschneidet

Wie die Testsuiten diese Bausteine nutzen, beschreibt [Tests und CI](/docs/architecture/testing-architecture).
