Форми дотримуються шаблону shadcn для TanStack Form: `useForm` зі схемою Zod модуля, render props `form.Field`, компоненти `Field` із shadcn і мутація для надсилання. Серверна функція ще раз валідує ту саму схему, тож перевірка на клієнті потрібна лише для зворотного зв'язку.

## Приклад

Скорочена версія `src/presentation/components/custom/newsletter-form.tsx` (без стилів):

```tsx
const emailSchema = newsletterSubscriberZodSchemas.subscribeToNewsletter.pick({ email: true })

export const NewsletterForm = (): JSX.Element => {
  const t = useTranslations("components.custom.newsletter-form")
  const inputId = useId()
  const errorMessage = useErrorMessage()
  const queryClient = useQueryClient()

  const subscribe = useMutation({
    ...subscribeToNewsletterMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSuccess: ({ status }) => {
      toast.success(t(status))
      return queryClient.invalidateQueries({ queryKey: NEWSLETTER_SUBSCRIBER_QUERY_KEYS.ALL })
    },
  })

  const form = useForm({
    defaultValues: { email: "" },
    listeners: { onBlur: validateOnBlur },
    onSubmit: ({ value, formApi }) => {
      subscribe.mutate(
        { email: value.email, locale: getCurrentLocale() },
        {
          onSuccess: () => {
            formApi.reset()
          },
        },
      )
    },
    validators: { onChange: emailSchema },
  })

  return (
    <form
      noValidate
      onSubmit={(event) => {
        void submitForm(event, form)
      }}
    >
      <form.Field name="email">
        {(field) => {
          const isInvalid = isFieldInvalid(field)

          return (
            <Field data-invalid={isInvalid}>
              <FieldLabel htmlFor={inputId}>{t("label")}</FieldLabel>
              <Input
                aria-describedby={`${inputId}-error`}
                aria-invalid={isInvalid}
                autoComplete="email"
                id={inputId}
                name={field.name}
                onBlur={field.handleBlur}
                onChange={(event) => {
                  field.handleChange(event.target.value)
                }}
                placeholder={t("placeholder")}
                type="email"
                value={field.state.value}
              />
              <Button isPending={subscribe.isPending} type="submit">
                {subscribe.isPending ? t("submitting") : t("button")}
              </Button>
              <div id={`${inputId}-error`}>
                {isInvalid && (
                  <ValidationFieldError
                    message={fieldErrorMessage(field.state.meta.errors)}
                    namespace="auth.validations"
                    params={AUTH_VALIDATION_PARAMS}
                  />
                )}
              </div>
            </Field>
          )
        }}
      </form.Field>
    </form>
  )
}
```

## Схема

- Використовуйте схему з `<table>.zod.ts` модуля, а для форм автентифікації — з `src/integrations/better-auth/auth.zod.ts`. `.pick(...)` вибирає поля, які показує форма; значення, яких користувач не вводить, наприклад мова, додаються в `onSubmit`.
- `validators: { onChange: emailSchema }` — єдиний валідатор. TanStack Form запускає його під час кожної зміни й ще раз під час надсилання; окрема копія для `onSubmit` залишала б помилку, отриману під час надсилання, як-от `passwordsMustMatch`, червоною, доки не зміниться її власне поле.
- `listeners: { onBlur: validateOnBlur }` запускає той самий валідатор, коли поле втрачає фокус, тож поле, яке відвідувач пройшов клавішею Tab, отримує свою помилку, щойно відвідувач його залишає.
- `noValidate` вимикає валідацію браузера, тож єдиними помилками лишаються повідомлення Zod.

## Помилки

- Поле показує свою помилку, щойно відвідувач залишив його або спробував надіслати форму, і ніколи — поки він ще вводить текст: `isFieldInvalid(field)` з `src/integrations/tanstack-form/form.fields.ts`, тобто `field.state.meta.isBlurred && !field.state.meta.isValid`. Це значення встановлює `data-invalid` на `Field`, `aria-invalid` на полі введення й визначає, чи рендериться помилка, тож усі три змінюються разом.
- Після того як помилка з'явилася, кожна зміна повторно валідує поле, тож помилка зникає з тим натисканням клавіші, яке виправляє значення. Не використовуйте `isTouched`: TanStack Form встановлює його з першим натисканням клавіші.
- Живий зворотний зв'язок, що заохочує прогрес, як-от `PasswordRequirements`, читає значення безпосередньо й оновлюється з першого натискання клавіші.
- Поле завжди вказує в `aria-describedby` id своєї помилки, `<input id>-error`, а `ValidationFieldError` рендерить елемент із цим id лише поки поле некоректне. Браузери ігнорують посилання на відсутній елемент, тож коректне поле не має опису.
- Повідомлення Zod — це ключі перекладу, наприклад `emailInvalid`. `fieldErrorMessage` бере перше з них, а `ValidationFieldError` рендерить `<namespace>.<key>` з відповідним записом із `params`, наприклад `{ max: 64 }` для `emailMaxLength`. Для неіснуючого ключа використовується `errors.codes.VALIDATION`.
- Форми передають `auth.validations`, який заздалегідь завантажують layout `auth` і `admin` і який розділ розсилки додає до layout `_marketing` для своєї форми, крім форм курсів в адмінпанелі, які передають `course.validations` з layout `admin.courses.tsx`. Маршрут має завантажити простір імен, який використовує форма. У `messages/` також є простір імен `<table>.validations` для інших модулів, наприклад `user.validations`, але жодна форма чи маршрут їх не завантажує.
- Помилки сервера проходять через `useErrorMessage()` в `onError` мутації.

## Надсилання

- `onSubmit` форми викликає `submitForm(event, form)` з `src/integrations/tanstack-form/form.submit.ts`. Він запобігає надсиланню браузером і викликає `form.handleSubmit()`; якщо форма некоректна, він позначає кожне поле як залишене, тож з'являються всі помилки, і переводить фокус на перший елемент керування з `aria-invalid="true"`.
- Надсилайте форму через параметри мутації сценарію використання, розгорнуті в `useMutation`. Виняток — `SignInForm`: вона викликає `signIn.email` клієнта Better Auth у власному `useMutation`, а двофакторний плагін клієнта обробляє `twoFactorRedirect`.
- `<Button isPending={mutation.isPending} type="submit">` блокує кнопку й повідомляє про стан очікування, поки триває запит.
- Кнопка надсилання залишається активною, поки форму не заповнено; вимикає її лише `isPending`. Натискання на неї з помилками показує всі помилки й переводить фокус на перше некоректне поле.
- Помилка сервера, що стосується одного поля, як-от `passwordCompromised` для пароля, знайденого у відомому витоку даних, показується під цим полем через `showFieldError(formApi, { controlId, field, message })` з `form.submit.ts`, а не сповіщенням; вона зникає, коли поле змінюється.
- Скидайте форму або переходьте на іншу сторінку в `onSuccess` мутації та інвалідуйте запити модуля, які змінює мутація.
