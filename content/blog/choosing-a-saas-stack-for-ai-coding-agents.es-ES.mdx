El consejo que todo el mundo da sobre cómo elegir un stack para agentes de programación de IA es que lo popular es mejor, porque los modelos lo han visto más. Suena obviamente cierto. Lo era. En 2026 se ha invertido en parte, y la prueba es un archivo que Next.js escribe por sí solo en tu proyecto.

Ejecuta `next dev` en Next.js 16 y escribirá esto en tu `AGENTS.md`, sin que nadie se lo pida:

```markdown
# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all
differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/`
before writing any code. Heed deprecation notices.
```

El framework de React más popular del mundo incluye ahora una advertencia para los agentes de programación: lo que recuerdan sobre él es incorrecto. No es una crítica a Next.js. Es una respuesta honesta a un problema real, y es la declaración más clara de lo que significa de verdad elegir un stack en 2026.

Este artículo trata de ese problema y de qué hacer con él. No es una lista de la compra. Las listas se quedan obsoletas, y una lista no puede decirte qué hacer con la biblioteca que ya usas y que no aparece en ella.

## ¿Qué hace realmente un stack por un agente de programación de IA?

Un stack no hace que un agente acierte. Cambia **cuántos programas erróneos se pueden expresar**. Cada elección de biblioteca reduce o amplía el espacio del código que compila pero es incorrecto. Ese es todo el mecanismo, y es la razón por la que «apto para agentes» es una propiedad que se puede comprobar y no una sensación.

Piensa en el mismo error en dos bases de código. Un agente interpreta una columna de la base de datos como una cadena cuando es una marca de tiempo.

Con un constructor de consultas tipado, el error no se puede expresar. El código no compila, el agente ve el error dentro de su propia ejecución y lo corrige. Coste: unos dos segundos.

Con una consulta en bruto que devuelve `any`, el error compila, supera la revisión porque se lee bien y produce una fecha incorrecta en un correo de facturación seis semanas después. Coste: un incidente.

El mismo modelo. El mismo prompt. El mismo error. El stack decidió si era un error de compilación o un incidente.

## La brecha de actualidad, y por qué lo popular dejó de ser un indicador

Este es el argumento que todos esgrimen: las bibliotecas populares aparecen más a menudo en los datos de entrenamiento, así que los modelos las escriben con más precisión. La primera mitad es cierta. La segunda depende ahora por completo de algo que el argumento ignora: **lo rápido que cambia la biblioteca**.

**La brecha de actualidad es la distancia entre la API que recuerda un modelo y la API que de verdad usas en producción.** El volumen de datos de entrenamiento te dice con cuánta seguridad escribirá un modelo código para una biblioteca. La brecha de actualidad te dice si esa seguridad está justificada. Son magnitudes distintas y, en los frameworks que cambian deprisa, ahora apuntan en direcciones opuestas.

La investigación al respecto es inequívoca. Un estudio de ocho bibliotecas muy utilizadas midió **tasas de uso de API obsoletas de entre el 25 % y el 38 %** en código generado por modelos, y las atribuyó a un conocimiento paramétrico desfasado y a la ausencia de una vista en vivo de cómo es la API hoy ([APILOT, arXiv](https://arxiv.org/pdf/2409.16526)). Los trabajos sobre API en evolución describen el mismo fallo como un conflicto de conocimiento: el modelo no adivina, recuerda con seguridad una versión que ya no existe ([When LLMs Lag Behind, arXiv](https://arxiv.org/html/2604.09515v1)).

Esto produce una clasificación contraintuitiva. Ordenadas según cuántos problemas causa la memoria del modelo:

| Perfil de la biblioteca                                          | Volumen de entrenamiento | Cambios en la API | Efecto neto en el resultado del agente                     |
| ---------------------------------------------------------------- | ------------------------ | ----------------- | ---------------------------------------------------------- |
| Popular y estable (React, PostgreSQL, Tailwind)                  | Alto                     | Pocos             | **El mejor.** La memoria es amplia y sigue siendo correcta |
| Pequeña y estable (Zod, la mayoría de utilidades especializadas) | Menor                    | Pocos             | **Bueno.** Menos memoria, pero lo que hay es correcto      |
| Popular y cambiante (un framework a mitad de una versión mayor)  | Alto                     | Muchos            | **El peor.** Seguro de sí mismo, fluido y erróneo          |
| Pequeña y cambiante                                              | Bajo                     | Muchos            | Malo, pero el agente matiza en lugar de afirmar            |

La celda inferior derecha es la interesante. Cuando un modelo sabe poco de una biblioteca, tiende a matizar, buscar o leer el código fuente. Cuando sabe mucho de la _versión anterior_ de una biblioteca, afirma. **La seguridad está calibrada con el volumen de entrenamiento, no con la corrección**, así que el peor caso es mucho volumen más muchos cambios: un agente que escribe código obsoleto con fluidez y nunca muestra dudas.

Ese es exactamente el caso del que advierte Next.js en el bloque anterior. Es el framework de React con el que más se ha entrenado a los modelos, y ha introducido suficientes cambios como para que su proveedor considerara justificado imprimir una advertencia para los agentes.

### Qué hacer al respecto

No puedes arreglar la memoria de un modelo, pero sí puedes hacer que sus errores salgan baratos:

- **Prioriza la estabilidad sobre la popularidad cuando entren en conflicto.** Una API estable desde hace cinco años que el modelo recuerda a medias es mejor que una API reescrita que recuerda mal por completo.
- **Deja que el compilador detecte la deriva de versiones.** Los errores por API obsoletas solo salen caros en las fronteras sin tipos. Este es el verdadero argumento a favor de los tipos de extremo a extremo, y es más sólido que el habitual.
- **Fija la versión de la documentación que lee el agente y guárdala junto al código.** El propio consejo de Next es leer la guía de `node_modules`, no la web. La documentación local coincide con tu versión instalada; un artículo de blog de 2024, no.
- **Trata las dependencias nuevas como no fiables.** Lo veremos más abajo, porque es un problema de seguridad y no solo de corrección.

## El Agent Stack Test

Cuatro preguntas por dependencia, puntuadas con 0, 1 o 2, hasta 8 puntos. Se aplica a bibliotecas que no existían cuando se escribió esto, y esa es precisamente la ventaja de un test frente a una lista.

### 1. Restricción: ¿un mal uso puede impedir la compilación?

- **0**: La biblioteca devuelve `any`, o la configuración se basa en claves de texto, o los errores solo aparecen en tiempo de ejecución.
- **1**: Los tipos existen pero son orientativos; una llamada incorrecta sigue compilando con una conversión de tipo.
- **2**: Un mal uso es un error de tipos. Los programas erróneos no se pueden expresar.

### 2. Convergencia: ¿hay una única forma obvia de hacer el trabajo?

Los agentes trabajan por imitación, así que una biblioteca con seis API equivalentes te da una probabilidad entre seis de que use la que ya utiliza tu base de código.

- **0**: Muchos enfoques equivalentes, todos habituales en la práctica y todos presentes en los datos de entrenamiento.
- **1**: Una forma recomendada, más alternativas heredadas de uso generalizado.
- **2**: Una sola forma, y las alternativas han desaparecido en lugar de estar marcadas como obsoletas.

### 3. Verificabilidad: ¿puede el agente demostrar por sí mismo que funciona?

- **0**: La corrección solo la puede observar una persona mirando la aplicación en ejecución.
- **1**: Se puede probar, pero la configuración es lo bastante manual como para que el agente no la haga.
- **2**: La cubre un comando que el agente ya ejecuta.

### 4. Actualidad: ¿está al día lo que el modelo recuerda de ella?

- **0**: Cambios de versión mayor en el último año, con API públicas renombradas o eliminadas.
- **1**: Cambios menores recientes, o la documentación con la que aprendió el modelo es ahora incorrecta en algunos puntos.
- **2**: La API pública lleva estable el tiempo suficiente para que el código recordado siga funcionando, o la biblioteca incluye documentación legible por máquina junto a la versión instalada.

**Cómo leer la puntuación.** De 7 a 8 es una dependencia que se puede confiar a un agente sin supervisión. De 4 a 6 significa que funciona con una frontera de tipos o una prueba a su alrededor. Con 3 o menos, o la envuelves en una interfaz que controles, o aceptas que una persona escriba cada punto de llamada.

El test trata deliberadamente de la _forma_ de una dependencia, no de su calidad. Bibliotecas excelentes puntúan mal aquí (una gran biblioteca a mitad de una reescritura saca un 0 en actualidad), y otras del montón puntúan bien. Esto mide la idoneidad para agentes, no el mérito.

## El test aplicado, capa por capa

Lo que sigue es el stack que distribuimos, puntuado con honestidad, incluido lo que cuesta. Tus respuestas pueden ser otras; lo transferible es el razonamiento.

### Lenguaje: TypeScript, estricto, sin vías de escape

**Puntuación: 8/8.** Es la elección de la que depende todo lo demás de la lista.

El modo estricto es el mínimo, no el objetivo. Las propiedades que importan para los agentes son las que la gente suele desactivar: nada de `any` implícito, nada de acceso por índice sin comprobar, nada de aserciones de no nulo. Cada uno de esos flags convierte toda una clase de resultados del agente, seguros pero erróneos, de una sorpresa en tiempo de ejecución en un subrayado rojo que el agente ve antes de terminar su turno.

La versión importa menos que la configuración. Un TypeScript reciente configurado de forma laxa es peor para trabajar con agentes que uno más antiguo configurado de forma estricta.

### Runtime y framework: Cloudflare Workers, TanStack Start, React

**Puntuación: 6/8.** Restricción 2, convergencia 1, verificabilidad 2, actualidad 1.

Este es el punto débil, dicho con honestidad, y es el mismo del que advierte Next.js. El núcleo de React lleva estable el tiempo suficiente para que la memoria del modelo sea fiable. La capa de framework que lo rodea no, y el punto de actualidad le pasa factura.

La aplicación pública actual usa React con TanStack Start sobre Cloudflare Workers. Bun y Vite+ proporcionan la cadena de herramientas local. Los agentes deben leer la documentación de los paquetes instalados y las skills oficiales de TanStack Start y Cloudflare, con versión fijada, antes de modificar código del framework o del despliegue.

La convergencia pierde un punto porque los loaders de ruta, las funciones de servidor, la caché de consultas y los endpoints HTTP normales tienen responsabilidades distintas. Este repositorio muestra dónde va cada cosa: los archivos de ruta coordinan la navegación, los casos de uso de cada funcionalidad se encargan de las operaciones y las integraciones con proveedores se encargan de la configuración de cada servicio.

### Capa de API: funciones de servidor de TanStack Start, tipadas de extremo a extremo

**Puntuación: 7/8.**

La propiedad que importa no es el framework, sino que los tipos de entrada y salida de un handler sean visibles para quien lo llama. Cuando cambia la forma de una ruta, todos los puntos de llamada que pasan a ser incorrectos dejan de compilar.

El consejo de la competencia suele nombrar bibliotecas RPC concretas. Eso es una implementación de la propiedad, no la propiedad en sí. Sirve cualquier enfoque en el que cambiar un endpoint rompa la compilación en sus puntos de llamada. Lo que no sirve es un simple `fetch` a una ruta JSON tipada a mano en el punto de llamada, porque es una frontera en la que una suposición errónea del agente compila sin problemas, llega a producción y la descubre un cliente.

**Las fronteras de API sin tipos son donde sobreviven los errores de los agentes.**

### Base de datos: Drizzle sobre Cloudflare D1

**Puntuación: 8/8.**

El esquema es TypeScript, así que es a la vez el origen de las migraciones y el de los tipos, y no hay un segundo artefacto que pueda desincronizarse. Una consulta que hace referencia a una columna inexistente es un error de compilación, no un 500.

Dos propiedades importan más allá del tipado. Las consultas de Drizzle se parecen a SQL, así que el conocimiento de SQL que ya existe se aprovecha. Cloudflare D1 usa la semántica de SQLite, así que los agentes deben seguir el adaptador de D1 y la documentación instalada en lugar de copiar consultas específicas de Postgres. Las migraciones versionadas y los bindings locales aislados permiten revisar los cambios antes de cualquier operación remota.

### Validación: Zod en la frontera de las peticiones

**Puntuación: 8/8.** Es la capa que la mayoría de stacks se saltan y la que antes se amortiza.

Los tipos describen lo que crees. Los esquemas lo comprueban. Cada punto por el que entran datos en el proceso (cuerpos HTTP, variables de entorno, payloads de webhooks, respuestas de terceros, columnas JSON de la base de datos) es un punto en el que el sistema de tipos confía en una promesa que nadie ha verificado.

En esta aplicación, Zod parsea las entradas de las funciones de servidor, los parámetros de búsqueda de las rutas y los valores de los formularios, y el SDK de Polar verifica y parsea los payloads de los webhooks. Los bindings de entorno los tipa Wrangler en lugar de parsearlos, así que son la frontera en la que todavía se confía sin verificar.

En el trabajo con agentes esto importa más que en el trabajo humano. Una persona que escribe una integración tiende a desconfiar del payload porque ya se ha quemado antes. Un agente escribe el camino feliz con total seguridad, porque el camino feliz es lo que contienen sobre todo sus datos de entrenamiento. Un esquema en la frontera convierte ese optimismo en un error capturado con un mensaje que nombra el campo.

### Autenticación: Better Auth, en tu repositorio

**Puntuación: 7/8.**

La propiedad relevante para los agentes es que la implementación es código fuente tuyo y no una llamada opaca a un servicio alojado. Un agente puede leer cómo se emite una sesión, seguir el token hasta donde se verifica y ampliarlo de una forma que puedes revisar en un diff.

La autenticación alojada puntúa peor aquí por una razón estructural, independiente del argumento del precio: la mitad importante de la lógica está detrás de una frontera de API que el agente no puede leer, así que cualquier pregunta sobre su comportamiento acaba en una suposición o en una consulta a la documentación, y cualquier personalización se convierte en una integración en lugar de en un cambio.

El punto que pierde es el de actualidad. Es una biblioteca que cambia deprisa en un ecosistema que aún se está consolidando, así que la memoria del modelo sobre su API no es fiable. Es un buen ejemplo del test haciendo su trabajo: una biblioteca puede ser la elección correcta y aun así puntuar mal en un eje, y saber en cuál te indica dónde poner la protección.

### Estilos: Tailwind

**Puntuación: 7/8.**

La razón que se suele dar es el volumen de datos de entrenamiento. La mejor razón es estructural: los estilos están en el elemento al que dan estilo, así que **no hay un segundo archivo que el agente tenga que acordarse de abrir**. Una hoja de estilos en otro directorio es una obligación de sincronización, y el fallo típico de los agentes no es que den mal estilo, sino que actualizan solo uno de los dos sitios.

Esto se generaliza más allá de los estilos. El mismo argumento favorece las pruebas y los tipos situados junto al código, y va en contra de cualquier patrón en el que un cambio deba replicarse en un sitio que el agente no tiene motivo para mirar.

### Internacionalización: use-intl con una comprobación de paridad

**Puntuación: 7/8**, y se gana su sitio aquí por una razón que en realidad no tiene que ver con la i18n.

Las traducciones son el fallo silencioso por excelencia. Un agente añade una funcionalidad, escribe los textos en inglés, y a los demás idiomas les faltan ahora claves. Nada se rompe. Las pruebas pasan. El error llega precisamente a los clientes que no pueden notificarlo con claridad.

La solución no es una biblioteca mejor, sino que `bun run check:i18n` haga fallar la CI cuando falta una clave. Cualquier parte de tu sistema con esa forma (presente en un sitio, ausente sin avisar en otro) necesita el mismo tratamiento, y mientras no lo tenga será invisible para tu agente y para ti.

### Pagos y correo electrónico: Polar, Resend

**Puntuación: 6/8** y **7/8**.

Las integraciones de pago pierden puntos por convergencia, no por calidad. Esta aplicación usa el checkout de Polar y webhooks verificados, con la gestión de compras y claves de licencia en los casos de uso de cada funcionalidad. Sigue esa implementación y el comportamiento de reintentos que documenta el proveedor. Resend envía desde el Worker las plantillas de correo localizadas.

Los webhooks merecen su propia advertencia, y la tienen más abajo.

### Pruebas: Vitest y Playwright

**Puntuación: 8/8**, y es la capa que hace útiles todas las demás puntuaciones.

Lo importante no es la cobertura como número. Es que `bun run check && bun run test:coverage` existe, termina con 0 o 1, y un agente puede ejecutarlo sin que nadie le diga cómo. Todo lo que hay por encima de esta línea trata de reducir lo que un agente puede expresar. Esta línea trata de detectar lo que aun así se ha colado.

## El número de dependencias es superficie para el agente

Cada dependencia es una API que el modelo podría recordar mal. Eso reformula el argumento habitual de las «demasiadas dependencias», que suele girar en torno al tamaño del bundle y la cadena de suministro, y lo convierte también en un argumento de corrección.

Las dependencias de runtime figuran en `package.json`. Lo que importa no es cuántas hay, sino su forma: casi todas están tipadas de extremo a extremo o envueltas en una frontera que controlamos, así que una suposición errónea sobre ellas falla al compilar en lugar de fallar en producción.

Ahora hay un segundo motivo para tener cuidado, y es de seguridad. Se midió que los modelos de vanguardia publicados entre octubre de 2025 y marzo de 2026 alucinaban nombres de paquetes con tasas de entre el **4,62 % y el 6,10 %** ([arXiv](https://arxiv.org/pdf/2605.17062)). Los atacantes registran esos nombres inventados en registros públicos y esperan, un ataque llamado **slopsquatting** ([Mend](https://www.mend.io/blog/the-hallucinated-package-attack-slopsquatting/)).

La regla práctica: **una dependencia añadida por un agente es una pull request sin revisar de un desconocido.** Comprueba que el paquete existe, que su nombre es el que esperabas y no uno casi idéntico, y que de verdad lo necesitabas. Los lockfiles y un paso de revisión para los cambios en `package.json` cubren la mayor parte de la exposición con un esfuerzo casi nulo.

## Lo que los agentes nunca deberían controlar solos

Algunas partes de un SaaS comparten una propiedad: **la versión incorrecta parece correcta, pasa las pruebas, funciona bien en las demos y solo falla en condiciones que tu batería de pruebas no reproduce.** Es esa propiedad, y no la dificultad, lo que hace que no sea seguro delegarlas.

| Superficie                        | Por qué la versión incorrecta supera la revisión                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| Gestión de sesiones y tokens      | Un inicio de sesión que funciona no demuestra nada sobre caducidad, rotación o revocación |
| Webhooks de pago                  | Un handler no idempotente es correcto hasta que llega el reintento                        |
| Migraciones de base de datos      | La reversibilidad y la pérdida de datos son invisibles hasta el rollback                  |
| Aislamiento entre tenants         | La consulta es correcta para el tenant de prueba e incorrecta para el segundo             |
| Cualquier cosa que lea un secreto | Registrar un token en los logs es un cambio de una línea que funciona perfectamente       |

El webhook es el caso más claro. Stripe reintenta ante cualquier respuesta que no sea 2xx, así que un handler que cobra correctamente en la primera entrega y vuelve a cobrar en el reintento supera todas las pruebas que se le ocurrirían a un agente, porque escribir esa prueba exige conocer ya el modo de fallo. No es un límite de la capacidad del modelo. Es que las pruebas que escribe un agente reflejan los modos de fallo de sus datos de entrenamiento, y los errores de idempotencia están infrarrepresentados en ellos en relación con lo a menudo que cuestan dinero real.

Marca estas rutas en `AGENTS.md` como de revisión exclusivamente humana y respáldalo con revisores obligatorios, para que la intención se haga cumplir en lugar de darse por supuesta.

## Preguntas frecuentes

<Accordions>

<Accordion title="¿Cuál es el mejor stack tecnológico para agentes de programación de IA en 2026?">

TypeScript de extremo a extremo, con una capa de base de datos tipada, validación de esquemas en cada frontera externa, una autenticación que vive en tu repositorio y un único comando que comprueba los tipos, pasa el linter y ejecuta las pruebas. Las bibliotecas concretas importan mucho menos que el hecho de que usarlas mal impida compilar. Antes de adoptar cualquier candidata, puntúala según restricción, convergencia, verificabilidad y actualidad.

</Accordion>

<Accordion title="¿Elegir un framework popular ayuda a los agentes de programación de IA?">

Menos que antes, y a veces nada. La popularidad da a un modelo más datos de entrenamiento, pero solo sobre la versión con la que se entrenó. Un framework que publica cambios incompatibles más deprisa de lo que se reentrenan los modelos produce código seguro de sí mismo, fluido y erróneo. En cuanto una biblioteca cambia rápido, la estabilidad importa más que el volumen.

</Accordion>

<Accordion title="¿Por qué mi agente escribe código con API que ya no existen?">

Porque recuerda la versión con la que se entrenó. Una investigación midió tasas de uso de API obsoletas de entre el 25 % y el 38 % en ocho bibliotecas muy utilizadas, y las atribuyó a un conocimiento paramétrico desfasado y a no tener una vista en vivo de cómo es la API hoy. Tu comprobador de tipos es la corrección más barata para esto, y por eso el problema sobrevive en las fronteras sin tipos.

</Accordion>

<Accordion title="¿Debería dejar que un agente de IA elija mis dependencias?">

No sin comprobar que cada paquete existe. Los modelos de vanguardia publicados entre octubre de 2025 y marzo de 2026 alucinaron nombres de paquetes con tasas de entre el 4,62 % y el 6,10 %, y ahora los atacantes registran esos nombres inventados en registros públicos, un ataque llamado slopsquatting. Trata cualquier dependencia nueva que añada un agente como una pull request sin revisar de un desconocido.

</Accordion>

<Accordion title="¿Un monorepo es mejor para los agentes de programación de IA?">

Solo si las fronteras las impone el tooling en lugar de describirlas un README. Un monorepo cuyas fronteras entre paquetes hacen fallar la compilación cuando se cruzan enseña tu arquitectura a un agente en segundos. Un monorepo que se mantiene unido por convención le da al agente más sitios en los que poner el código correcto en el paquete equivocado.

</Accordion>

<Accordion title="¿Qué partes de un SaaS no debería escribir nunca un agente por su cuenta?">

Cualquier cosa en la que un error de apariencia plausible sea caro y silencioso: la gestión de sesiones y tokens, los webhooks de pago, las migraciones de base de datos, el aislamiento entre tenants y cualquier cosa que lea un secreto. Todas comparten una propiedad: la versión incorrecta pasa las pruebas y funciona bien en las demos, y solo falla en condiciones que tu batería de pruebas no reproduce.

</Accordion>

<Accordion title="¿Necesito tRPC u oRPC para tener una API apta para agentes?">

Necesitas tipos que crucen la frontera de red; la biblioteca concreta es secundaria. Sirve cualquier enfoque en el que un cliente que llama a un endpoint modificado deje de compilar. Lo que no funciona es un simple fetch a una ruta JSON sin tipos, porque es una frontera en la que una suposición errónea compila sin problemas y llega a producción.

</Accordion>

<Accordion title="¿Cuántas dependencias son demasiadas en una base de código asistida por agentes?">

Cuenta superficies, no paquetes. Cada dependencia es una API que el modelo puede recordar mal, así que la pregunta es cuántas de ellas son críticas, poco conocidas y no están comprobadas. Una dependencia cubierta por tipos estrictos y una prueba cuesta poco. Una que devuelve datos sin tipos a tu lógica de negocio cuesta en cada cambio futuro.

</Accordion>

<Accordion title="¿Tailwind ayuda de verdad a los agentes de programación de IA?">

Sí, por una razón estructural y no estética. Los estilos están en el elemento al que dan estilo, así que no hay un segundo archivo que el agente tenga que acordarse de abrir y actualizar. El mismo argumento favorece las pruebas y los tipos situados junto al código, y va en contra de cualquier patrón en el que un cambio deba replicarse en un archivo que el agente no tiene motivo para abrir.

</Accordion>

<Accordion title="¿Debería cambiar de stack para que mi agente funcione mejor?">

Casi nunca. El coste de la migración es seguro y la ganancia es limitada, mientras que añadir tipos estrictos, validación en las fronteras y un único comando de verificación a tu stack actual es barato y surte efecto de inmediato. Cambia de stack cuando ya fueras a cambiarlo de todos modos, y deja que la idoneidad para agentes sea un criterio de desempate y no el motivo.

</Accordion>
