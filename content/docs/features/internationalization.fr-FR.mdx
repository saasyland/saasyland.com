## Langues

`I18N` dans `src/integrations/use-intl/i18n.config.ts` définit `en-US` (par défaut), `de-DE`, `es-ES`, `fr-FR`, `it-IT`, `ja-JP`, `pl-PL`, `pt-BR` et `uk-UA`, le cookie `saasyland.com_locale`, le fuseau horaire par défaut `UTC` et les formats de date nommés `FORMATS`.

## URL

La langue par défaut n’a pas de préfixe ; toute autre langue est un préfixe de chemin, par exemple `/docs` et `/pl-PL/docs`. Pour les requêtes de document, le Worker (`resolveLocale` dans `i18n.middleware.ts`) redirige les chemins non canoniques avec un 308 : `/en-US/docs` devient `/docs` et `/pl/docs` devient `/pl-PL/docs`. Les chemins `/api` et `/_serverFn` n’ont jamais de préfixe.

Le `rewrite` du routeur dans `src/router.tsx` retire le préfixe des URL entrantes et l’ajoute aux URL sortantes : les routes et les liens utilisent donc des chemins simples, comme `<Link to={ROUTES.SIGN_IN}>`. Les URL brutes dans la langue courante, comme `callbackURL` et `errorCallbackURL` de Better Auth, proviennent de `router.buildLocation(...).publicHref` ; `localizePathname({ locale, pathname })` construit une URL pour une langue donnée, comme les liens du sélecteur de langue et les liens dans les e-mails. `AriaProvider` localise le `href` des composants React Aria.

## Cookie de langue

Lorsque la langue de l’URL d’un document diffère du cookie, le Worker définit le cookie dans la réponse ; aucun code ne choisit une langue à partir de celui-ci. `getCurrentLocale()` fonctionne des deux côtés et lit le chemin de l’URL, avec `en-US` comme repli. Les URL de `/api` et des fonctions serveur n’ont pas de préfixe, donc côté serveur il renvoie `en-US` pour elles. Les e-mails obtiennent plutôt leur langue du parcours : les e-mails d’authentification depuis son `callbackURL`, la confirmation de newsletter depuis la `locale` envoyée par le formulaire.

## Messages

Les messages sont des fichiers `messages/<locale>/<namespace>.json` ; le nom du fichier est l’espace de noms, par exemple `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` ou `common`. Chaque espace de noms de page contient `metadata.title` et `metadata.description`.

- Les espaces de noms racine (`common`, `components.*`, `errors*`) sont préchargés dans le `beforeLoad` racine.
- Un layout déclare `NAMESPACES`, une page déclare `NAMESPACE`. Les deux vont dans `staticData.namespaces` et sont préchargés par le loader :

```ts
loader: async ({ context }) => {
  const locale = getCurrentLocale()
  const [metadata] = await Promise.all([
    loadPageMetadata({ locale, namespace: NAMESPACE }),
    preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
  ])
  return { locale, metadata }
},
```

- `TranslationsProvider` enveloppe le corps du document et fusionne les espaces de noms racine avec ceux des routes correspondantes dans un seul `IntlProvider` : les écrans d’erreur sont donc traduits eux aussi.
- Les e-mails chargent leur espace de noms côté serveur avec `loadNamespace`.

## Composants

Chaque composant appelle `useTranslations` une seule fois et nomme le traducteur `t`. Un composant qui a besoin de deux espaces de noms utilise leur parent commun ou `useTranslations()` avec des clés complètes.

## Dates, nombres et fuseaux horaires

Les dates et les nombres sont formatés avec `useFormatter` de use-intl (`format.dateTime`, `format.number`, `format.relativeTime`, `format.list`). La langue détermine les conventions : l’ordre du jour et du mois, l’horloge sur 12 ou 24 heures et les séparateurs. Le fuseau horaire est la seule préférence d’affichage qu’un utilisateur enregistre.

`TranslationsProvider` transmet deux valeurs supplémentaires à `IntlProvider` :

- `timeZone` : le champ `timezone` de l’utilisateur connecté, issu de la requête de session courante, ou `I18N.DEFAULT_TIMEZONE` (`UTC`) sans session. Le provider lit la session que chargent les gardes des routes `/app`, `/admin` et d’authentification, et ne la récupère jamais lui-même : les pages publiques prérendues sont donc identiques pour chaque visiteur et s’hydratent sans changement. Lorsque la requête de session change, par exemple après que l’utilisateur a enregistré un nouveau fuseau dans les [Paramètres](/docs/features/settings), chaque date est de nouveau rendue.
- `formats` : `I18N.FORMATS`, les formats de date nommés. `src/types/use-intl.d.ts` déclare leurs noms auprès de use-intl, si bien qu’un nom inconnu fait échouer la vérification des types.

| Nom             | Exemple (anglais)         | Usage                                                                                                                     |
| --------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `date`          | Nov 14, 2026              | Le jour d’un instant dans le fuseau du lecteur, dans les tableaux                                                         |
| `dateTime`      | Nov 14, 2026, 3:04 PM UTC | Un instant avec son heure et l’abréviation du fuseau : activations de licence et dates des comptes dans l’administration  |
| `calendarDate`  | Nov 14, 2026              | Une date sans heure, comme la date d’un article de blog. Elle est formatée en UTC et ne passe donc jamais à un autre jour |
| `calendarDay`   | November 14               | Libellés des jours du graphique d’analyse de l’administration                                                             |
| `calendarMonth` | Nov                       | Libellés des mois du graphique du tableau de bord de l’administration                                                     |

Un appel peut remplacer une option d’un format nommé : `format.dateTime(new Date(post.date), "calendarDate", { month: "long" })`. Les tableaux de l’administration affichent les dates des autres utilisateurs dans le fuseau propre à la personne qui les consulte, avec son abréviation, afin qu’une colonne se lise et se trie dans un seul fuseau ; le fuseau de l’utilisateur a sa propre colonne.

## Changer de langue

`locale-switcher.tsx` propose deux sélecteurs de langue. `LocaleSwitcher`, dans le pied de page marketing, est un menu `<details>` avec un lien simple par langue vers le chemin courant dans cette langue : il fonctionne donc avant l’hydratation. `LocaleSelect`, dans les barres latérales de la documentation et de l’application client, est un champ de sélection qui reprend le style de `ThemeSwitch` et ouvre la même URL. Dans les deux cas, choisir une langue charge un nouveau document, et la chaîne de requête et le fragment ne sont pas conservés. Les pages en polonais et en ukrainien préchargent aussi les sous-ensembles de polices latin étendu et cyrillique ([Polices et identité visuelle](/docs/ui/fonts-and-branding)).

## Vérifications

`bun run check:i18n` vérifie la parité des clés entre les langues, résout les clés statiques dans la portée de leur `useTranslations`, valide la syntaxe des messages ICU et vérifie la parité du contenu de la documentation et du blog.
