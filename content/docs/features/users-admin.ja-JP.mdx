## ルート

`src/routes/admin.users.tsx` はレイアウトで、リンク形式のタブは `src/data/user-tabs.ts` の `USER_TABS` です。これは各エリアの `src/data/<area>.user-tabs.ts` を `order` の順にまとめます。タブはパスとページのスケルトンを指定し、エリアの `navigation.<area>.json` にあるタブのラベルはパンくずリストでもそのページの名前になります。認証エリアは **全ユーザー** を、決済のエリアは **顧客** を追加します（[注文と顧客](/docs/features/orders#customers)を参照）。`/admin/users` は `/admin/users/all` へリダイレクトします。どのタブもページタイトルは `pages.admin.users` から取ります。

| ルート                   | 内容                                                                               |
| ------------------------ | ---------------------------------------------------------------------------------- |
| `/admin/users/all`       | 稼働中のユーザーテーブル                                                           |
| `/admin/users/customers` | Polar のすべての顧客と、そのアカウント、注文、返金後の支払額                       |
| `/admin/users/$userId`   | ユーザーのプロフィール: アカウントの詳細、セッション、ほかのエリアが追加するカード |

## すべてのユーザー

```tsx
<DataTable columns={userColumns} options={{ query: getUsersPageQuery, selectable: true }} />
```

- `getUsersPageQuery` はサーバー関数 `getUsers`（`src/modules/user/use-cases/get-users.ts`、権限 `user: ["list"]`）を呼び出します。ページネーションと並べ替えはサーバー側で行い、名前、ロール、ステータス、メール確認、2FA、タイムゾーン、作成日時と更新日時で並べ替えられます。
- ステータスは列ではありません。`getUserStatus`（`user.utils.ts`）が `banned` と `emailVerified` から `banned`、`pending`、`active` を導き、サーバーは同じ SQL の `case` 式で並べ替えます。`UserStatusBadge`（`user-status-badge.tsx`）がテーブルとプロフィールでステータスを表示します。
- `userColumns` は `src/presentation/components/custom/admin/users/user-columns.tsx` にあり、各ユーザーの名前はそのユーザーのプロフィールへリンクします。作成日時と更新日時は `common.dateTime` メッセージを使い、閲覧者自身のタイムゾーンで略称付きで表示されるため、どちらの列も 1 つのタイムゾーンで表示され、並べ替えられます。各ユーザーのタイムゾーンは独立した列で表示されます。

**ユーザーを追加** は `CreateUserDialog`（`create-user-dialog.tsx`）を開きます。これは `userZodSchemas.createUser` で検証する TanStack Form のフォームで、名前、メールアドレス、初期パスワード、ロールを入力します。`createUser`（`user: ["create"]`。ロールについては Better Auth が `user: ["set-role"]` もチェックします）を呼び出し、新しいユーザーのプロフィールを開きます。Better Auth はメールアドレスが未確認の状態でアカウントを作成するため、最初のサインインで `/auth/verify-email` に移動し、そこで確認リンクが送信されます。

## プロフィール [#profile]

`src/routes/admin.users.$userId.tsx` は、ユーザー、そのセッション、ほかのエリアのカードのデータを同時に読み込み、ページのタイトルをユーザーの名前にします。存在しないユーザーの場合は Not Found ページになります。

- `getUserQuery` はユーザーの行を読み取ります（`get-user.ts`、`user: ["get"]`）。`UserDetails`（`user-details.tsx`）は、ロール、ステータス、メール確認、二要素認証、タイムゾーン、作成日時と更新日時を `ADMIN_USER_DETAILS`（`src/data/admin.ts`）の順に表示し、`AdminUserProfilePending` も同じ順序に従います。
- `listUserSessionsQuery` はユーザーの有効なセッションを、トークンを除いて新しい順に一覧表示します（`list-user-sessions.ts`、`session: ["list"]`）。`UserSessions`（`user-sessions.tsx`）は各デバイスとそのアクティビティを表示し、`revokeUserSession` で 1 つのセッションを、確認のうえ `revokeUserSessions` ですべてのセッションを失効させます（どちらも `session: ["revoke"]`）。`revokeUserSession` はセッションの ID を受け取り、サーバー側でそのトークンを調べます。これは `revokeSession` が管理者自身のセッションに対して行うのと同じです。
- ほかのエリアは、アカウントの詳細の下に表示するカードを `src/data/<area>.user-profile.ts` で追加し、`src/data/user-profile.entries.ts` がそれらを `USER_PROFILE_SECTIONS`（`src/data/user-profile.ts`）にまとめます。セクションは、カード、`AdminUserProfilePending` も描画するそのスケルトン、そしてページがそのユーザーについて読み込むデータを指定します。認証エリアは何も追加しません。ライセンスのエリアは `UserLicense`（`user-license.tsx`）を追加します。これは `userLicenseQuery`（`get-user-license.ts`、`user: ["get"]`）を読み取り、プラン、ステータス、購入日時、即時提供への同意、最初のアクティベーション、最初のテンプレートのダウンロード、そして有効なライセンスの場合は返金できるかどうかを表示します。返金できるかどうかは、リクエストの時点でサーバーが判断します（[ライセンス](/docs/features/licences#records-and-refunds)を参照）。その下には `UserWithdrawals`（`user-withdrawals.tsx`）があり、`userWithdrawalsQuery`（`get-user-withdrawals.ts`、`user: ["get"]`）を読み取って、アカウントの撤回の意思表示を新しい順に一覧にします。入力された氏名、メールアドレス、注文番号、購入者の特定方法、意思表示が届いた時点の返金条件、受領確認をメールで送信したかどうかを表示します（[ライセンス](/docs/features/licences#withdrawal-function)を参照）。これらの文言は `pages.admin.users.license` にあり、ライセンスのエリアが `src/data/license.namespaces.ts` でレイアウトに追加します。
- 決済のエリアは `UserOrders`（アカウントの注文と通貨ごとの返金後の支払額）を追加し、ライセンスカードには `LICENSE_ACTIVATION_LIMITS` によるパッケージの端末の上限が表示されます（[注文と顧客](/docs/features/orders#customers)を参照）。

ヘッダーには、ユーザーの名前とメールアドレス、そしてテーブルの行と同じアクションメニューが表示されます。

## アクション

`UserActions`（`row-actions.tsx`）はユーザーごとのメニューで、テーブルの最後の列（`UserRowActions`）とプロフィールにあります。

| 項目                           | 開くもの                 | サーバー関数                                  |
| ------------------------------ | ------------------------ | --------------------------------------------- |
| **ユーザーを編集する**         | `EditUserDialog`         | `updateUser`（`user: ["update"]`）、名前のみ  |
| **ロールを変更**               | ロールのサブメニュー     | `setUserRole`（`user: ["set-role"]`）         |
| **パスワードをリセットする**   | `ResetPasswordDialog`    | `setUserPassword`（`user: ["set-password"]`） |
| **このユーザーとしてログイン** | なし、そのままサインイン | `impersonateUser`（`user: ["impersonate"]`）  |
| **ユーザーを利用停止**         | `BanUserDialog`（確認）  | `banUser`（`user: ["ban"]`）                  |
| **利用停止を解除**             | なし                     | `unbanUser`（`user: ["ban"]`）                |
| **ユーザーを削除する**         | `DeleteUserDialog`       | `deleteUser`（`user: ["delete"]`）            |

- サインイン中の管理者自身の行には **ロールを変更**、**ユーザーを利用停止**、**ユーザーを削除する** がないため、管理者が自分自身を締め出すことはありません。いずれにしても、Better Auth は呼び出し元自身の利用停止や削除を拒否します。
- **このユーザーとしてログイン** は、管理者でも利用停止中でもないユーザーにだけ表示されます。Better Auth は `user: ["impersonate-admins"]` がなければ管理者へのなりすましを拒否し（この権限はどのロールにもありません）、利用停止中のユーザーにはセッションを与えません。[なりすまし](/docs/features/impersonation)を参照してください。
- プロフィールを開いているユーザーを削除すると、`/admin/users/all` に戻ります。
- 成功するたびに `USER_QUERY_KEYS.ALL`（セッションの場合は `SESSION_QUERY_KEYS.USER`）を無効化してトーストを表示し、権限不足を含むエラーは `useErrorMessage` を通して表示します。いずれかのアクションの実行中は、メニューボタンが無効になります。

各サーバー関数は `auth.middleware.ts` の `authorized(...)` で自身の権限をチェックします。`user` と `session` のステートメントは Better Auth の `defaultStatements` で、`admin` ロールは Better Auth の `adminAc` を持つため、`src/data/auth.access.ts` は `admin` と `settings` だけを宣言します。`/admin` のガードは `admin: ["access"]` を持つロールだけを通します。

## 招待とロール

招待テーブルはありません。ロールは `auth.roles.ts` の `admin` と `customer` で、ユーザーごとに **ロールを変更** で設定します。テーブルとユースケースが裏付けるまで、管理画面に招待やロールの編集画面はありません。
