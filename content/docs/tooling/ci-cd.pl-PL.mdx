Workflowy leżą w `.github/workflows/`. Workflowy aplikacji (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `updates.yml`, `e2e-reusable.yml` i `deploy-reusable.yml`) przygotowują narzędzia akcją złożoną `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ z wersją Node z `.nvmrc` i cache instalacji Buna, który `setup-vp` przywraca jeden raz, `bun install --frozen-lockfile --ignore-scripts` i `bun run typegen`. `remotion.yml` instaluje zamiast tego Node z `.nvmrc` i npm.

| Workflow              | Wyzwalacz                                                                             | Zadania                                                                                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requesty, grupy kolejki scalania i wywołania z `deploy.yml`                      | Kontrole, testy z pokryciem na równoległych shardach, sprawdzanie typów bez każdego z opcjonalnych obszarów, E2E w Chromium i w WebKit oraz przesłanie Workera preview |
| `deploy.yml`          | Pushe do `main`                                                                       | Kontrole z `ci.yml`, o ile nie uruchomiła ich kolejka scalania, potem preview, produkcja i wydanie                                                                     |
| `preview.yml`         | Ręcznie                                                                               | Wdraża na wspólne preview gałąź, której kontrole przeszły                                                                                                              |
| `e2e-full.yml`        | Pushe do `main`, harmonogram <RepositoryFact name="e2eFullSchedule" /> w UTC, ręcznie | WebKit przy pushu, tak jak w każdym pull requeście; Chromium i WebKit przy uruchomieniach z harmonogramu i ręcznych                                                    |
| `journey.yml`         | Harmonogram <RepositoryFact name="journeySchedule" /> w UTC, ręcznie                  | [Zestaw testów ścieżki klienta](#journey-suite) na wspólnym preview, w sandboksie Polara                                                                               |
| `updates.yml`         | Harmonogram <RepositoryFact name="updatesSchedule" /> w UTC, ręcznie                  | Otwiera, aktualizuje albo zamyka [zgłoszenie z aktualizacjami](#updates)                                                                                               |
| `e2e-reusable.yml`    | Wywoływany przez powyższe workflowy                                                   | Jeden build testowy, jeden projekt Playwrighta na równoległych shardach i jedna kontrola dla obu                                                                       |
| `deploy-reusable.yml` | Wywoływany przez `ci.yml`, `deploy.yml` i `preview.yml`                               | Build, potem migracje D1 i `wrangler deploy` albo `wrangler versions upload`                                                                                           |
| `remotion.yml`        | Zmiany w `remotion/` albo w plikach strony, które importuje                           | Sprawdza i pakuje przez npm projekt wideo ze strony głównej                                                                                                            |

`remotion.yml` uruchamia się przy pull requestach i pushach dla tych samych ścieżek: `remotion/`, samego workflowu i plików strony, które `remotion/src` importuje bezpośrednio albo przez inne pliki strony. `src/__test__/workflows.test.ts` śledzi te importy i kończy się błędem, gdy plik, do którego prowadzą, nie pasuje do żadnej ze ścieżek albo ścieżka nie pasuje do żadnego pliku.

Pobieranie repozytorium w `e2e-reusable.yml`, którego build renderuje listę zmian, a `content.spec.ts` ją odczytuje, w `deploy-reusable.yml`, który buduje stronę, i w zadaniu `release` ściąga wszystkie commity bez ich drzew (`fetch-depth: 0` i `filter: tree:0`), ponieważ [lista zmian](/docs/project/changelog) datuje każdy wpis datą commita, który wprowadził go do `main`. W porównaniu z płytkim klonem dochodzą tylko same commity, a przy płytkim klonie build kończy się błędem, zamiast przypisać wpisom złe daty. `src/__test__/workflows.test.ts` kończy się błędem, gdy któreś z tych pobrań przestaje ściągać historię.

Każda akcja z innego repozytorium, także z `actions/*`, jest przypięta do pełnego SHA commita wydania, a tag wydania stoi za nim w komentarzu: `uses: <owner>/<repo>@<commit> # <tag>`. Workflow uruchamia więc dokładnie kod tego wydania, nawet jeśli jego tag zostanie później przesunięty. `src/__test__/workflows.test.ts` kończy się błędem, gdy `uses:` w `.github/workflows/` lub `.github/actions/` wskazuje tag albo gałąź zamiast commita, nie ma tagu wydania za commitem albo przypina dwa wydania jednego repozytorium. `bun run deps:update` przenosi każdą akcję na najnowsze wydanie i przepisuje razem commit i tag ([Zależności](/docs/conventions/dependencies#upgrading)), więc akcje aktualizują się na tej samej gałęzi co pakiety.

## Kontrole [#checks]

Za wymaganą kontrolą `Format, lint, types, i18n, tests`, którą zgłasza zadanie `verify`, stoją zadania `check`, `test` i `features` w `ci.yml`:

| Zadanie                                               | Uruchamia                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                               | `bun run check`: tablice nazw klas, kontrole i18n i treści, [spis przepływów](/docs/tooling/test-coverage#flow-coverage), [umiejętności agentów](/docs/tooling/agent-skills#drift-checks), formatowanie, lint i typy                                                                        |
| `test`                                                | Jedno zadanie na shard, <RepositoryFact name="vitestShards" /> równolegle: `bun run test:coverage --shard=<n>/<total>` z reporterem blob Vitesta, a potem przesyła raport blob sharda razem z jego pokryciem                                                                                |
| `verify`, o nazwie `Format, lint, types, i18n, tests` | Gdy przejdą wszystkie shardy, pobiera raporty blob i uruchamia `bun run test:coverage --merge-reports`, które scala pokrycie i sprawdza progi, a potem przesyła raport pokrycia; kończy się błędem, jeśli nie przeszły `check`, każdy shard, scalenie i każdy scenariusz zadania `features` |

Shard nie sprawdza żadnego progu, bo mierzy tylko kod, do którego docierają jego własne testy; progi z `vite.config.ts` są sprawdzane raz, na scalonym pokryciu wszystkich shardów, tak jak przy lokalnym `bun run test:coverage`. Spośród tych zadań tylko `verify` jest kontrolą, której wymagają reguły gałęzi, więc dodanie albo usunięcie sharda lub scenariusza nie zmienia nazwy żadnej wymaganej kontroli.

Zadanie `features` uruchamia `bun run check:features <scenario>` raz dla każdego scenariusza z `scripts/features.ts`, równolegle. Usuwa funkcje scenariusza, czyści pliki, które zostają, z odwołań do nich, formatuje oczyszczone pliki, a potem sprawdza typy reszty i jej tłumaczenia ([Testy](/docs/conventions/testing#tests-follow-the-features)). Scenariusz, w którym zostaje odwołanie niemożliwe do usunięcia, błąd typów albo błąd tłumaczeń, kończy swoje zadanie błędem, a z nim wymaganą kontrolę `Format, lint, types, i18n, tests`.

Zadania `e2e` i `e2e-webkit` wywołują `e2e-reusable.yml`, pierwsze z `browser: chromium`, drugie z `browser: webkit`. Każde wywołanie buduje aplikację raz i uruchamia testy w swojej przeglądarce równolegle na <RepositoryFact name="e2eShards" /> runnerach:

| Zadanie                                        | Uruchamia                                                                                                                                                                                                |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                        | `db:reset:test` i `build:test`, a potem przesyła jako jeden artefakt `dist`, wskaźnik `.wrangler/deploy` do konfiguracji jego Workera i wypełniony danymi testowymi `.wrangler/test`                     |
| `shard`                                        | Jedno zadanie na shard, uruchamiane razem z buildem: instaluje przeglądarkę, czeka na przesłanie buildu, pobiera go i uruchamia `bunx playwright test e2e/specs --project=<browser> --shard=<n>/<total>` |
| `report`, o nazwie `Build and E2E (<browser>)` | Kończy się błędem, jeśli build albo którykolwiek shard nie przeszedł; gdy shard nie przeszedł, scala raporty blob shardów w jeden raport HTML i go przesyła                                              |

Shardy nie czekają na koniec całego zadania `build` (`needs`): startują razem z nim i przygotowują narzędzia oraz przeglądarkę, gdy ono buduje. Potem `scripts/download-artifact.ts` co kilka sekund pyta API GitHuba o zadanie `build` tego samego uruchomienia, aż jego krok `Upload the test build` zakończy się powodzeniem. Udany krok nie znaczy jeszcze, że GitHub wymienia jego artefakt, a pobieranie w tym okienku kończy się błędem `Artifact not found`, więc skrypt pyta potem o artefakty uruchomienia, aż GitHub wymieni `test-worker-<browser>` przesłany od startu buildu, po czym sam pobiera ten artefakt i porównuje go ze skrótem SHA-256 zapisanym przez GitHuba. Wymieniony artefakt może jeszcze przez chwilę odpowiadać `Not Found`, więc skrypt pyta ponownie, aż GitHub wyda całe archiwum, a w międzyczasie żaden inny krok go nie pobiera. Skrypt wysyła ETag poprzedniej odpowiedzi, a GitHub nie wlicza niezmienionej odpowiedzi do limitu żądań tokenu. Nieudany krok buildu albo build, który kończy się bez przesłania artefaktu, w ciągu kilku sekund oblewa każdy shard, z nazwą nieudanego kroku i linkiem do buildu, a shard, który czeka dłużej niż limit skryptu, kończy się błędem, który mówi, czy brakuje kroku, pozycji na liście czy pobrania. Odczyt zadań i artefaktów uruchomienia wymaga `actions: read`, o które prosi tylko zadanie `shard`: `ci.yml`, `e2e-full.yml` i zadanie `checks` w `deploy.yml` przyznają je wywoływanym workflowom, a każde inne zadanie zostaje przy `contents: read`.

Ponowienia i workery samego Playwrighta zostają na każdym shardzie takie, jak opisuje je strona [Playwright](/docs/tooling/playwright#configuration). Zadanie `report` każdej przeglądarki to jedyna kontrola tej przeglądarki, której wymagają reguły gałęzi, więc dodanie albo usunięcie sharda nie zmienia nazwy żadnej wymaganej kontroli. Build pakuje też listę tagów wydań, które odczytał, a każdy shard usuwa każdy tag utworzony od tamtej chwili: `content.spec.ts` odczytuje tagi wydań z Gita, a wydanie otagowane w czasie, gdy shardy czekają, kazałoby mu oczekiwać listy zmian, której build nigdy nie wyrenderował.

Zadanie `upload`, o nazwie `Worker upload`, wywołuje `deploy-reusable.yml` z `upload: true`: buduje Workera preview dokładnie tak jak przy wdrożeniu i uruchamia `wrangler versions upload`, które przesyła go do Workera `saasyland-preview` jako nową wersję, ale jej nie wdraża. Cloudflare sprawdza przesłaną wersję tak samo jak wdrożenie: limit rozmiaru, czas uruchamiania, bindingi i sekrety wymienione w `secrets.required`, więc Workera, który przejdzie tę kontrolę, da się wdrożyć, a `preview.saasyland.com` dalej serwuje wcześniej wdrożoną wersję. Zadanie nie stosuje żadnej migracji i nie rejestruje wdrożenia na GitHubie (`deployment: false`), a działa równolegle z przesyłaniem z innych pull requestów. Wersja z pull requesta dostaje alias `pr-<number>`, pod którym widać ją w panelu Cloudflare; podsumowanie zadania podaje identyfikator i rozmiar wersji oraz jej URL, gdy Worker ma włączone Version URLs, a `saasyland-preview` dziś ich nie ma. Pull requesty z forków i od Dependabota nie mają dostępu do danych logowania do Cloudflare i pomijają to zadanie; kolejka scalania, która ma do nich dostęp, przesyła ich build przed scaleniem.

W pull requeście `bun run check` kończy się też błędem, dopóki pull request nie doda swojego [wpisu na liście zmian](/docs/conventions/git-workflow#changelog-entries), a w kolejce scalania – dopóki nie ma wpisu pull requesta z kolejki. Build w zadaniach `e2e` i `upload` oraz w zadaniach wdrożenia kończy się błędem, jeśli lista zmian pokazałaby w sekcji **Niewydane** wpis inny niż wpis samego pull requesta, a w kolejce scalania i na `main` – jeśli pokazałaby tam jakikolwiek wpis.

## Kolejka scalania [#merge-queue]

Zestaw reguł, który chroni `main`, wymaga kontroli `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)`, `Build and E2E / Build and E2E (webkit)` i `Worker upload / Upload preview` i scala pull requesty wyłącznie przez kolejkę scalania GitHuba (merge queue), która każdy z nich łączy w jeden commit metodą squash. `bun scripts/enqueue-pr.ts <number>` dodaje pull request do kolejki ([Git i pull requesty](/docs/conventions/git-workflow#merging)). Dla każdego pull requesta w kolejce GitHub zapisuje commit po squashu na gałęzi `gh-readonly-queue/main/pr-<number>-<commit>`, na bazie `main` i pull requestów, które czekają przed nim, i uruchamia na niej `ci.yml` dla zdarzenia `merge_group`. Gdy każdy pull request z grupy przejdzie, GitHub przesuwa `main` na ostatni commit grupy, dokładnie ten, który przetestowała kolejka, więc jeden push wprowadza do `main` każdy pull request z grupy jako osobny commit po squashu. Pull request, który nie przejdzie, wypada z kolejki, a te za nim są testowane ponownie już bez niego.

Ruleset ma też regułę `copilot_code_review` z `review_on_push: true`, ale według stanu na 22 listopada 2026 GitHub Copilot nie przejrzał żadnego pull requesta od #70, więc pull requesty nie przechodzą automatycznego przeglądu. Taki przegląd byłby zresztą tylko doradczy: ruleset nie wymaga zatwierdzenia przez recenzenta ani rozwiązania wątków przeglądu, więc pull request czeka wyłącznie na cztery powyższe kontrole.

`ci.yml` anuluje przebieg dla pull requesta, gdy zastępuje go nowszy commit, ale nigdy przebiegu kolejki, bo każda jej gałąź ma własną referencję. Kontrola listy zmian traktuje gałąź kolejki jak `main`: każdy pull request z grupy jest już commitem po squashu, którego temat kończy się jego numerem, więc żaden wpis nie może być niewydany, a wpis samego pull requesta z kolejki musi istnieć.

## Wdrożenia

`deploy.yml` wdraża każdy push do `main`, najpierw na wspólne preview, a potem na produkcję, gdy commit przejdzie wszystkie kontrole, których wymaga `main`. Jego pierwsze zadanie, `tested`, uruchamia `scripts/tested-commit.ts`, który odczytuje te kontrole z zestawu reguł przez API GitHuba i szuka udanego przebiegu każdej z nich na wypchniętym commicie. Commit, który przeszedł przez kolejkę scalania, je ma, bo kolejka przetestowała właśnie ten commit, więc `deploy.yml` wdraża go bez ponownego uruchamiania kontroli; commit, który trafił do `main` inną drogą, najpierw przechodzi kontrole z `ci.yml`.

| Zdarzenie                         | Cel                               | Środowisko na GitHubie            | URL                                                  |
| --------------------------------- | --------------------------------- | --------------------------------- | ---------------------------------------------------- |
| Push do `main`                    | `preview`, następnie `production` | `Preview`, następnie `Production` | https://preview.saasyland.com, https://saasyland.com |
| Ręczne uruchomienie `preview.yml` | `preview`                         | `Preview`                         | https://preview.saasyland.com                        |

`deploy-reusable.yml` nadaje każdemu środowisku na GitHubie jego URL, a `src/__test__/workflows.test.ts` kończy się błędem, gdy któryś z nich różni się od hosta środowiska w `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Preview jest wspólne: każde wdrożenie zastępuje poprzednie i używa tej samej bazy D1, przestrzeni nazw KV i bucketów R2 środowiska preview. Działa na nim `main`, więc [zestaw testów ścieżki klienta](/docs/tooling/playwright#journey-suite), webhooki z sandboksa Polara i logowanie na `preview.saasyland.com`, jedynym hoście preview, któremu ufa Better Auth, trafiają na kod, który za chwilę uruchomi produkcja, a każda migracja dociera do bazy preview przed produkcją. Aby wypróbować tam gałąź przed jej scaleniem, uruchom `gh workflow run preview.yml --ref <branch>`: polecenie wdraża gałąź razem z migracjami tylko wtedy, gdy jej commit przeszedł kontrole wymagane przez `main`, a następny push do `main` przywraca tam `main`.

`deploy-reusable.yml` sprawdza, czy są sekrety `CLOUDFLARE_API_TOKEN` i `CLOUDFLARE_ACCOUNT_ID`, uruchamia `scripts/verify-bindings.ts`, buduje aplikację z fikcyjnymi wartościami z `.env.test`, usuwa wygenerowany `dist/server/.dev.vars`, stosuje `db:migrate:<target>` i uruchamia `vp exec wrangler deploy --config dist/server/wrangler.json`, a z `upload: true` w miejsce dwóch ostatnich kroków uruchamia `vp exec wrangler versions upload`. Nie uruchamia `scripts/verify-deployment.ts`, czyli sprawdzenia działającej strony ze skryptów `deploy:<target>`, ponieważ ochrona Cloudflare przed botami odpowiada kodem 403 na żądania z runnerów CI. Nie uruchamia też `scripts/run-deploy-checks.ts`, więc CI nie wykonuje żadnej z kontroli wdrożenia, czyli żadnego ze skryptów `<name>:verify:<environment>` z `package.json`: w CI nie ma pliku `.env.<target>`, a środowiska na GitHubie przechowują tylko dane logowania do Cloudflare i, w `Preview`, ustawienia sandboksa dla [zestawu testów ścieżki klienta](#journey-suite). Dziś są to `auth:verify` z obszaru uwierzytelniania i `polar:verify` z obszaru Polara; uruchamiaj lokalnie `bun run auth:verify:<target>` po zmianie klienta OAuth i `bun run polar:verify:<target>` po każdej zmianie w Polarze ([Konfiguracja Polara](/docs/getting-started/polar-setup)). Żaden plik sekretów nie jest przesyłany: Worker zachowuje sekrety środowiska uruchomieniowego, które są już ustawione w Cloudflare. Wdrożenia na ten sam cel czekają w kolejce, zamiast się wzajemnie anulować, a przesyłania działają równolegle. Nowy commit w pull requeście anuluje przebieg `ci.yml` dla poprzedniego commita, którego i tak nikt nie scali, natomiast przebiegi kolejki scalania nigdy się nawzajem nie anulują, a przebiegi `deploy.yml` i `e2e-full.yml` na `main` czekają w kolejce (`concurrency` z `queue: max`), więc każdy push do `main` zostaje wdrożony.

## Zestaw testów ścieżki klienta [#journey-suite]

`journey.yml` uruchamia `bun run test:journey`, czyli [zestaw testów ścieżki klienta](/docs/tooling/playwright#journey-suite), na `https://preview.saasyland.com` według harmonogramu <RepositoryFact name="journeySchedule" /> w UTC i po ręcznym uruchomieniu:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` przyjmuje wartość `all`, `core`, `complete`, `agency` albo `upgrade`; każda wartość poza `all` uruchamia tylko test z tym tagiem. Zadanie odczytuje te sekrety ze środowiska `Preview` na GitHubie, nie rejestrując wdrożenia (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` i `RESEND_API_KEY`. Ustawia `POLAR_SERVER` na `sandbox`, jedyną wartość, którą przyjmuje zestaw, a zestaw tworzy klienta Polara dla sandboksa, więc workflow nie może sięgnąć do produkcyjnego Polara. Uruchomienia czekają w kolejce i nigdy się nawzajem nie anulują, bo anulowane uruchomienie zostawiłoby opłacone zamówienia. Zadanie zapisuje w podsumowaniu uruchomienia wynik i czas każdego testu oraz błąd każdego nieudanego testu, a raport HTML, `playwright-report/journey.json` oraz ślady, nagrania i katalogi urządzeń z nieudanych testów przesyła jako artefakt `journey-report`.

Workflow nie uruchamia się po każdym wdrożeniu `main`. Każde uruchomienie zakłada na preview konto dla każdego testu, opłaca i zwraca jego zamówienia w sandboksie Polara oraz wysyła e-maile weryfikacyjne i potwierdzenia zakupu przez konto Resend, które preview dzieli z produkcją. W intensywny dzień `main` jest wdrażany wiele razy, więc uruchomienie po każdym wdrożeniu mnożyłoby te e-maile przy limitach wysyłki, od których zależą e-maile z produkcji, i niczego by nie zatrzymało: produkcja jest wdrażana zaraz po preview, cokolwiek wykażą testy ścieżki. Każde uruchomienie obejmuje cały zakup: rejestrację z potwierdzeniem adresu e-mail, płatność w sandboksie za każdy pakiet, klucz wydany przez Polara, opublikowane CLI na urządzeniach pakietu, przejście z pakietu Podstawa na Komplet i zwroty. Nie świeci jeszcze na zielono: żadne uruchomienie nie przeszło, bo sekrety nie są ustawione, więc na razie nie sprawdza żadnego zakupu. Uruchom je ręcznie po zmianie płatności, licencji albo API licencji CLI oraz po `gh workflow run preview.yml --ref <branch>`, aby przetestować gałąź przed scaleniem.

## Aktualizacje [#updates]

`updates.yml` szuka aktualizacji zależności i umiejętności agentów według harmonogramu <RepositoryFact name="updatesSchedule" /> w UTC i po ręcznym uruchomieniu. Pierwszy krok, `bun scripts/report-updates.ts find`, pyta rejestr npm o najnowsze wydanie każdej bezpośredniej zależności i uruchamia `bun run skills:update` w kopii repozytorium na runnerze, z której nic nie trafia do commita, aby sprawdzić, które umiejętności zmieniły się w źródle. Drugi krok, `bun scripts/report-updates.ts issue`, prowadzi jedno zgłoszenie, <RepositoryFact name="updatesIssueTitle" />: otwiera je, gdy są aktualizacje, przepisuje przy kolejnych uruchomieniach i zamyka, gdy wszystko jest aktualne. Zgłoszenie wymienia każdy nieaktualny pakiet, z oznaczeniem, czy przesunie go `bun run deps:update`, czy jest przypięty, i każdą umiejętność z commitami, między którymi by się przesunęła. Pierwszy krok czyta też przez `git ls-remote`, które nie wymaga tokena, tagi wydań repozytorium każdej przypiętej akcji, a zgłoszenie wymienia każdą akcję przypiętą do wydania starszego niż najnowsze.

Workflow może tylko czytać repozytorium i tworzyć zgłoszenia, a token dostaje wyłącznie drugi krok. Nie otwiera pull requestów, bo GitHub nie uruchamia żadnego workflowu dla pull requesta otwartego tokenem samego workflowu, więc jego kontrole nigdy by się nie wykonały; zamiast tego uruchom `bun run deps:update` na osobnej gałęzi.

## Wydania i tagi [#releases-and-tags]

Strona jest wdrażana w sposób ciągły, więc jej wersje to daty, a nie numery wersji semantycznych. Gdy wdrożenie produkcyjne się powiedzie, zadanie `release` w `deploy.yml` oznacza wdrożony commit tagiem `vYYYY.MM.DD` z datą UTC i publikuje dla niego GitHub Release. Drugie wdrożenie produkcyjne tego samego dnia dostaje tag `vYYYY.MM.DD.2`, kolejne `.3` i tak dalej. Wdrożenia preview nigdy nie dostają tagu. Zadanie `release` jako jedyne ma `contents: write`.

Informacje o wydaniu to wpisy z [listy zmian](/docs/project/changelog), które weszły do wydania, czyli te, które trafiły do `main` od poprzedniego tagu wydania, każdy zakończony `(#<number>)`, co GitHub zamienia w link do pull requesta, więc każda zmiana jest opisana w jednym miejscu; gdy w wydaniu nie ma żadnego wpisu, informacje o nim zawierają link do listy zmian. `scripts/publish-release.ts` bierze te informacje z `releaseNotes` w `src/lib/changelog.ts`, jedynego elementu swojej listy `RELEASE_NOTES`, i uruchamia `gh release create` z tagiem wybranym przez wdrożenie, więc projekt bez listy zmian publikuje wydania bez informacji o wydaniu. Ponowne uruchomienie zachowuje tag, który commit już ma, i pomija wydanie, które już istnieje.

Zadanie wdrożenia produkcyjnego wybiera ten tag przed buildem: `scripts/choose-release-tag.ts` stosuje `releaseTag` z `src/lib/release.ts` do tagów pobranego repozytorium, build dostaje tag jako `RELEASE_TAG`, a zadanie przekazuje go zadaniu `release` jako swoje wyjście `release-tag`, więc wdrożenie i jego wydanie mają jeden tag. Dzięki temu [lista zmian](/docs/project/changelog) łączy każdy wpis z pierwszym wydaniem, które go zawierało: z najstarszym tagiem wydania, którego commit zawiera commit wpisu po squashu w historii pierwszych rodziców `main`, którą build odczytuje razem z datami jednym `git log`, albo z własnym tagiem wdrożenia dla wpisów, które ono wnosi. Zadanie `release` czyta listę zmian tak samo, z tagiem, który publikuje, więc informacje o wydaniu to dokładnie te wpisy, które strona łączy z tym wydaniem. Wpisy scalone przed pierwszym tagiem wydania nie są połączone z żadnym wydaniem, podobnie jak w buildach lokalnych, preview i pull requestów wpisy, których żadne wdrożenie jeszcze nie wydało. Dwa wdrożenia produkcyjne nie mogą wybrać tego samego tagu: `deploy.yml` uruchamia naraz tylko jeden przebieg workflowu (`concurrency` z `queue: max`), więc zadanie `release` poprzedniego przebiegu utworzyło już swój tag, zanim kolejne wdrożenie pobierze repozytorium.

Aby przywrócić na produkcji wybrane wydanie, wycofaj w pull requeście wszystko, co przyszło po jego tagu:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Po scaleniu kod z tagu zostaje wdrożony po zwykłych kontrolach i oznaczony jako nowe wydanie. Migracje D1 nie są wycofywane, więc starszy kod działa na nowszym schemacie. Każda zmiana schematu musi działać z aplikacją wdrożoną przed nią, dlatego powrót do poprzedniego wydania jest bezpieczny; zanim cofniesz się dalej, przeczytaj migracje dodane w międzyczasie.
