---
title: "File di route"
description: "L'unica forma di una route di pagina e di una route di layout: NAMESPACE o NAMESPACES, un loader con un solo Promise.all, uno scheletro che rispecchia la pagina, schemi di ricerca e link."
---

Ogni file in `src/routes` ha la stessa forma, quindi chi ne conosce uno li conosce tutti. Un file di route compone: dichiara ciò di cui la pagina ha bisogno e posiziona i componenti. Widget, form, finestre di dialogo e colonne delle tabelle si trovano in `src/presentation/components/custom`.

## Route di pagina

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        onReorder={({ offset, row }) => move.mutateAsync({ courseId: row.id, offset })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        search={t("table.search")}
        selectable
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Il componente** è una `const` locale chiamata `<Name>Page`, definita per prima. Piccoli frammenti di markup usati solo da questa pagina possono stare sopra di essa come componenti locali, come fanno `CourseProgress` e `StartLink` in `_site._marketing.courses.$course.index.tsx`; tutto ciò che ha dati, mutation o stato propri va in un file di componente.
- **Un solo namespace.** `const NAMESPACE = "pages.<area>.<page>"` sta subito sopra `export const Route` ed è usato in `loadPageMetadata`, `preloadNamespaces` e `staticData`. Tutto il resto di cui la pagina ha bisogno lo dichiara il suo layout.
- **Un solo `Promise.all`.** Il loader avvia tutto il lavoro in una volta: i metadati della pagina, il namespace e ogni query che i componenti leggono. Restituisce `{ locale, metadata }` per `head`. Non attendere mai uno di questi prima di avviare il successivo.
- **`head: pageHead(ROUTES.X)`** costruisce titolo, descrizione, URL canonico e alternative a partire dai metadati del file del namespace.
- **I percorsi provengono da `ROUTES`** in `src/routes.ts`, che riunisce i percorsi di tutte le aree (vedi [Percorsi e navigazione](#paths-and-navigation)); non scrivere mai un percorso letterale.

Una pagina il cui titolo proviene da un record attende quel record e costruisce il proprio head dai dati del loader, come fa `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Route di layout

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Un layout dichiara `const NAMESPACES = [...] as const` sopra `export const Route` e lo precarica. Quando non ne ha, omette l'opzione; non esiste `namespaces: []`.
- Un layout indica nei suoi `NAMESPACES`, come semplici stringhe, ogni namespace di cui hanno bisogno le sue pagine e i loro componenti, compresi quelli di altre funzionalità. `/app` elenca `pages.license`, `pages.withdrawal` e `withdrawal.validations`, perché la sua panoramica mostra la scheda e l'offerta della licenza e la sua pagina della licenza mostra la scheda del recesso; `/admin/users` elenca `pages.admin.customers`, `pages.admin.orders` e `pages.admin.users.license`; e `/_site/_marketing` e `/_site/docs` elencano `auth.validations`, perché i loro footer mostrano il modulo della newsletter, e il layout di marketing anche `withdrawal.validations`. Escludere una funzionalità elimina i suoi file di messaggi, e la regola di potatura elimina ogni stringa che ne nomina uno ([Test](/docs/conventions/testing#tests-follow-the-areas)).
- Il componente, quando il layout ne rende uno, si chiama `<Name>Layout` e posiziona un `<Outlet />`.
- Una guard va in `beforeLoad` sul layout che possiede l'area: `beforeLoad: requireAdmin` in `admin.tsx`, `requireSignedIn` in `app.tsx`, entrambi layout dell'area di autenticazione. Le guard decidono solo la navigazione; ogni server function controlla comunque il proprio permesso.

## Ordine delle opzioni

`sort-keys` è disattivata in `src/routes` perché TanStack Router inferisce i tipi nell'ordine di dichiarazione. Le opzioni sono in ordine alfabetico, tranne `validateSearch`, che viene per prima, prima di qualsiasi cosa legga la ricerca:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Non scrivere mai un array o un oggetto di dati direttamente dentro `createFileRoute`; dichiaralo come costante sopra.

## Parametri di ricerca

`validateSearch` è uno `zod.object` costruito con gli helper di `src/lib/search-params.ts`:

| Helper                            | Valore quando il parametro manca o è malformato | Uso                                      |
| --------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| `searchText()`                    | `undefined`                                     | Token, email, codici di errore           |
| `searchFlag()`                    | `undefined`                                     | Booleani                                 |
| `searchParam(schema)`             | `undefined`                                     | Qualsiasi altro schema, come un percorso |
| `searchChoice(choices, fallback)` | `fallback`                                      | Una scheda o una vista                   |

Il testo assente resta `undefined`, quindi un valore predefinito non finisce mai in un URL costruito dal router. Un parametro `searchChoice` è abbinato a `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, che rimuove il valore predefinito dall'URL. Una pagina a cui un altro sito rimanda i visitatori dichiara anche `search: { middlewares: [onlyDeclaredSearch(schema)] }` con il proprio schema, come fanno `/app` e `/app/license` per il checkout di Polar: il router costruisce allora il suo indirizzo con i soli parametri dichiarati, e il server reindirizza un indirizzo che porta un altro parametro allo stesso indirizzo senza di esso, prima che un controllo o la pagina lo leggano. Non scrivere mai a mano controlli come `typeof search["x"] === "string"`; aggiungi un helper quando serve un nuovo tipo di campo. Quando un componente figlio ha bisogno di un parametro che la pagina ha già verificato come presente, la pagina ne restringe il tipo e lo passa in basso, come `auth.reset-password.tsx` passa `token` a `ResetPasswordForm`. Le pagine che leggono gli stessi parametri condividono uno schema nel `.zod.ts` del modulo che leggono, che analizzano anche i loro scheletri, come fanno `/app/license` e la parte della panoramica aggiunta dall'area della licenza con `licenseSearchSchema` (`src/modules/license/license.zod.ts`).

## Scheletri

La navigazione deve sembrare istantanea, quindi ogni route che rende una pagina ha un `pendingComponent` che la rispecchia: lo stesso layout, le stesse card e lo stesso numero di righe.

- Gli scheletri si trovano nel file pending dell'area (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) e usano `Skeleton` di shadcn.
- Gli scheletri sono nello script di ingresso di ogni pagina, quindi uno scheletro importa `Skeleton`, le primitive shadcn, altri scheletri e le costanti che ne fissano le lunghezze, mai un form o il file che lo contiene; `pending-imports.test.ts` fallisce quando uno raggiunge `@tanstack/react-form` (vedi [Prestazioni](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Un segnaposto di testo riceve il vero token tipografico più `h-lh scale-y-70`, così ha l'altezza della riga che sostituisce: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- La lunghezza degli elenchi proviene dalle costanti che usa la pagina: `DataGridPending` in `data-grid-pending.tsx` disegna per impostazione predefinita `DEFAULT_PAGE_SIZE` righe, la dimensione di pagina di ogni tabella dell'amministrazione.
- Lo scheletro di un layout renderizza il `pendingComponent` della prima route sotto il layout che corrisponde al percorso corrente e ne definisce uno, che `usePagePending(layout)` in `src/hooks/use-page-pending.ts` legge dall'albero delle route: `AdminPending`, `AppPending`, `AuthPending` e `MarketingPending` per i loro layout, e `AdminUsersPending` e `AdminCourseSectionPending` un livello più in basso. La route di una pagina è quindi l'unico punto che nomina il suo scheletro, qualunque sia il layout che lo mostra; `/admin/users`, che reindirizza a `/admin/users/all`, imposta lo scheletro di quella pagina.
- Non esiste un `defaultPendingComponent` valido per tutto il router. `src/router.tsx` imposta `defaultPendingMs` a <RepositoryFact name="navigationPendingMs" unit="millisecond" /> e `defaultPendingMinMs` a <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, entrambi da `src/data/navigation.constants.ts`: una navigazione non ancora terminata dopo il primo mostra lo scheletro della route, e lo scheletro sparisce non appena la pagina è pronta, senza restare un istante di più. Le route mantengono questi valori; vedi [Prestazioni](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) per le misurazioni su cui si basano.
- Le pagine della documentazione disegnano i loro scheletri dentro il layout della documentazione: `DocsIndexPending` e `DocsPagePending` riempiono le aree della griglia dell'articolo e dell'indice dei contenuti di Fumadocs, così una navigazione tra pagine della documentazione mantiene la barra laterale sullo schermo. Il componente della pagina renderizza l'MDX in un proprio `<Suspense key={path}>`, così la barra laterale funziona prima che il chunk MDX della pagina sia caricato, e una navigazione sostituisce l'HTML del server della pagina precedente invece di idratarlo con i dati della successiva.

## Link

- I link del router ricevono una costante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, oppure un pattern di route con `params` per i percorsi dinamici. `LinkButton` e `SidebarMenuLink` di shadcn ricevono `to` allo stesso modo, e `AnchorButton` riceve un `href` per un indirizzo fuori dall’albero delle route.
- Non aggiungere mai il prefisso del locale a un link del router; lo aggiunge la riscrittura del router. Un URL completo nel locale corrente, per un valore che esce dal router come stringa, proviene da `router.buildLocation({ ... }).publicHref`, come fa `use-auth-redirect.ts` per costruire i suoi link di accesso. `localizePathname` serve per gli URL costruiti fuori dal contesto di un router o per un altro locale: email, destinazioni di reindirizzamento di Better Auth, link dentro l'MDX e il selettore della lingua.

## Percorsi e navigazione [#paths-and-navigation]

Ogni percorso e ogni voce di menu si scrive una sola volta, in un'unica lista, e una funzionalità che si può escludere, come i corsi, i prodotti o le pagine legali, entra in quella lista come un elemento che nomina il proprio percorso. Escludere la funzionalità elimina i suoi file e i suoi nomi, e con essi ogni elemento che ne nomina uno, quindi le liste non hanno bisogno di un file per funzionalità né di un barrel. È così che la CLI `saasyland` compone un progetto a partire da layer di template. Solo `scripts/areas.ts`, che l'applicazione non carica mai, elenca le aree opzionali con i loro file e i percorsi che possiedono, così che `bun run check:areas` possa controllare i tipi del sito senza ciascuna di esse ([Test](/docs/conventions/testing#tests-follow-the-areas)).

| Cosa                                | Dichiarato in                                                                                                                                                                                                            | Letto da                                                                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Percorsi                            | `src/routes.ts`: un `export const` per percorso                                                                                                                                                                          | `import * as ROUTES from "~/src/routes"`                                                                       |
| Percorsi non elencati               | `UNLISTED_ROUTES` in `src/routes.ts`                                                                                                                                                                                     | `isUnlistedRoute` in `src/routes.ts`                                                                           |
| Voci di menu                        | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` e `FOOTER_NAVIGATION` in `src/data/navigation.ts`, nell'ordine in cui compaiono | Le barre laterali, l'intestazione, il footer, la palette dei comandi e la dashboard                            |
| Namespace dei layout                | `NAMESPACES` nella route del layout                                                                                                                                                                                      | Il loader del layout e `staticData`                                                                            |
| Liste dell'admin e dell'app clienti | `DASHBOARD_STATS`, `DASHBOARD_PANELS`, `COMMAND_SEARCHES`, `USER_TABS`, `USER_PROFILE_SECTIONS` e `ACCOUNT_DELETION_NOTICES`, ciascuna nel componente che la renderizza                                                  | Quel componente, il suo scheletro e la route che carica i suoi dati                                            |
| Controlli del sito online           | `LIVE_SITE_CHECKS` in `src/lib/deployment.ts`                                                                                                                                                                            | `verifyDeployment` ([Piattaforma e test](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)) |

`src/routes.ts` dichiara ogni percorso e non importa nulla, perché lo carica ogni runtime: il browser, il Worker a ogni avvio a freddo, gli script Bun, Playwright, `vite.config.ts` e il progetto Remotion. Ogni file lo importa come un unico namespace, `import * as ROUTES from "~/src/routes"`, così ogni percorso mantiene il suo tipo letterale e `<Link to={ROUTES.COURSES}>` resta verificato rispetto all'albero delle route. Un percorso costruito a partire da un altro, come `BLOG_FEED` da `BLOG`, segue quello da cui è costruito.

Le liste a cui un'area aggiunge ancora voci in un file a sé, gli handler del Worker e i plugin di Vite, mantengono per ora i loro barrel. Un barrel contiene solo righe `export { … } from`, una per file di area e ordinate per modulo, come `src/integrations/drizzle-orm/drizzle.schemas.ts`.

`src/data/navigation.ts` contiene i sette menu come liste letterali, ogni voce con la sua pagina in `to`, la chiave completa del suo messaggio in `label` e, nella console di amministrazione e nell'app clienti, la sua icona di `lucide-react`. Il menu dell'admin raggruppa le sue voci sotto un gruppo della sidebar, con `key` da `ADMIN_NAVIGATION_GROUP`, e il footer i suoi link sotto una colonna, con `key` da `FOOTER_COLUMN`. Il file importa solo `lucide-react`, `~/src/routes` e `~/src/data/navigation.constants`, perché il progetto Remotion legge il menu dell'admin e il suo job di CI installa solo i pacchetti propri di Remotion; `src/__test__/source-layout.test.ts` fallisce quando importa qualsiasi altra cosa. La console di amministrazione e l'app clienti esistono solo con l'accesso, quindi le loro voci nominano i percorsi dell'area di autenticazione e spariscono con essa, come **Accedi** nell'intestazione e nel footer:

```ts title="src/data/navigation.ts"
export const HEADER_NAVIGATION: readonly SiteEntry[] = [
  { hash: MARKETING_SECTION_IDS.PRICING, label: "navigation.core.header.pricing", to: ROUTES.HOME },
  { label: "navigation.courses.header.courses", to: ROUTES.COURSES },
  { label: "navigation.content.header.blog", to: ROUTES.BLOG },
  { label: "navigation.content.header.docs", to: ROUTES.DOCS },
  { label: "navigation.auth.header.signIn", signedIn: { label: "navigation.auth.header.account" }, to: ROUTES.SIGN_IN },
]
```

Un progetto senza i corsi non ha `ROUTES.COURSES`, quindi la regola di potatura elimina la voce **Corsi** dell'intestazione, e un gruppo o una colonna che resta vuota sparisce con essa, come la colonna legale del footer in un progetto senza le pagine legali.

Una voce dell’intestazione o del piè di pagina può indicare un’etichetta `signedIn` che sostituisce la sua per un visitatore che ha effettuato l’accesso, e il suo link porta allora all’area di lavoro del visitatore: `/admin` per un account con accesso di amministrazione, `/app` per tutti gli altri. `Navigation`, `MobileMenu` e `Footer` leggono entrambi i menu da `useSiteNavigation` (`src/hooks/use-site-navigation.ts`), che mette al loro posto le voci `signedIn` appena conosce l’area di lavoro del visitatore e altrimenti restituisce le liste invariate. Prende l’area di lavoro dall’unico hook del suo `WORKSPACE_HOOKS`, `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`), che lo decide dal ruolo della sessione con `hasPermission` e il permesso `admin: ["access"]` che controlla `requireAdmin`; un progetto senza accesso non ha alcun hook, quindi i suoi menu restano invariati. Le pagine pubbliche sono prerenderizzate, quindi il loro HTML mostra **Accedi**; dopo l’idratazione, un browser che ha il cookie di Better Auth con l’ultimo metodo di accesso usato chiede la sua sessione, e l’intestazione, il suo menu mobile e il piè di pagina mostrano **Il tuo account** al suo posto, già con il link all’area giusta. Ogni menu usa come chiave dei suoi link la loro posizione nell’elenco, così React modifica lo stesso link invece di sostituirlo, e una pressione iniziata su **Accedi** mentre la sessione si carica apre comunque l’area. Un browser che non ha mai effettuato l’accesso non chiede nulla. Finché una parte della pagina non è idratata, `useVisitorWorkspace` non restituisce nulla, anche se il browser ha già la sessione, perché `useHydrated` risponde con il valore del server mentre React idrata: un footer che si idrata dopo l'arrivo della sessione mostra lo stesso **Accedi** dell'HTML e cambia dopo, invece di rompere l'idratazione.

Ogni voce dell’admin apre una schermata che funziona con dati reali, e la landing page le conta tutte. Una schermata i cui dati non hanno ancora una fonte non riceve alcuna voce (vedi [Dashboard di amministrazione](/docs/features/admin-dashboard#real-data-only)).

La barra laterale dell'app clienti contiene la voce **Licenza** della vendita delle licenze, e le sue risorse la voce **Documentazione** dei contenuti, sopra l'indirizzo del supporto. La base ha bisogno solo di `/` e `/api`, e di **Prezzi** nell'intestazione, l'unica voce con un `hash`, che porta alla sezione dei prezzi di `/`.

Una statistica della dashboard in `DASHBOARD_STATS` ha un `prefetch`, che il loader di `/admin` esegue, e un hook `useValue`, che `DashboardStats` chiama per leggere il numero.

`APP_STATEMENTS` in `auth.access.ts` contiene le dichiarazioni di permesso, una per risorsa, e `scripts/areas.ts` nomina le dichiarazioni di una funzionalità che si può escludere, come `APP_STATEMENTS.course`, così che escluderla le elimini (vedi [Ruoli e permessi](/docs/guides/roles-and-permissions)).

Le liste di `src/data/navigation.ts` hanno un tipo dichiarato da `src/data/navigation.constants.ts`, come `IconEntry` o `SiteEntry`, quindi una lista le cui voci un progetto esclude, come le azioni della dashboard senza l'area dei pagamenti, è una lista vuota che supera comunque il controllo dei tipi. `navigation.test.ts` verifica che il `to` di ogni voce sia un percorso dell'albero delle route e che nessun menu nomini due volte una pagina o un'etichetta.

Il `label` di una voce è la chiave completa del suo messaggio, come `navigation.courses.admin.courses`, e il messaggio si trova nel file della funzionalità a cui appartiene la pagina, `messages/<locale>/navigation.<area>.json`, quindi escludere la funzionalità elimina con essa le sue etichette. Un componente lo renderizza con `t(entry.label)` da `useTranslations()`. Una sezione dell'admin definisce le etichette delle sue sottopagine per le breadcrumb nel `breadcrumbs` della sua voce, dal segmento del percorso alla chiave, come `create` verso `navigation.courses.breadcrumbs.create`. Anche una scheda della gestione utenti, una ricerca della palette dei comandi e una statistica della dashboard indicano la chiave completa della loro etichetta, come `navigation.team.userTabs.invitations`, `navigation.auth.search.users` e `dashboard.courses.learners`, e un pannello della dashboard legge i suoi testi sotto la sua `key` in `dashboard.<area>.json`. Entrambi i tipi di file sono namespace radice, quindi ogni menu può mostrare l'etichetta di qualsiasi voce. Ciò che appartiene al menu stesso resta nel suo namespace: `groups.<group>` in `pages.admin.sidebar`, `columns.<column>` in `components.custom.footer` e la call to action, il pulsante del menu e il link di salto dell'intestazione in `components.custom.navigation`. `navigation.test.ts` fallisce quando a una voce, a una variante per chi ha effettuato l'accesso, a una breadcrumb, a una scheda della gestione utenti o a una ricerca della palette dei comandi manca il messaggio in un locale, e `admin-dashboard.component.test.tsx` quando manca a una statistica.

Le pagine che vengono renderizzate dal Worker a ogni richiesta, come `/admin`, `/auth` o `/courses`, sono elencate in `UNLISTED_ROUTES` in `src/routes.ts`. Il plugin di TanStack Start in `vite.config.ts` le esclude dal prerendering con `shouldPrerender` (`src/lib/prerender.ts`), che chiama `isUnlistedRoute`, e `buildPageHead` assegna loro la card del sito invece di una card della pagina (vedi [Motori di ricerca e anteprime social](/docs/features/seo)). Vite non risolve l'alias `~` mentre carica la propria configurazione, quindi `prerender.ts` importa `src/routes.ts` con un percorso relativo.
