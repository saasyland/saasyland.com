Un'email ha tre parti: un modello in `src/presentation/emails/`, un namespace di messaggi in `messages/<locale>/emails.<name>.json` e il caso d'uso che carica i messaggi, genera il modello e lo invia. La pagina [Resend](/docs/integrations/resend) elenca ogni modello con il caso d'uso che lo invia.

## Modello

Un modello contiene solo markup ed esporta il proprio namespace. Traduce con `createTranslator` di `use-intl` perché viene reso fuori dal contesto React. Ogni modello viene reso dentro `EmailLayout`, di `src/presentation/emails/email-layout.tsx`, che imposta una volta per tutti la lingua, il testo di anteprima, Tailwind e il contenitore centrato. `src/presentation/emails/verify-email.tsx`:

```tsx title="src/presentation/emails/verify-email.tsx"
import type { JSX } from "react"

import { Button, Heading, Section, Text } from "react-email"
import { createTranslator } from "use-intl"

import { EMAIL_LINK_LIFETIME_HOURS } from "~/src/integrations/better-auth/auth.constants"
import type { SupportedLocale } from "~/src/integrations/use-intl/i18n.config"

import type emailMessages from "~/messages/en-US/emails.verify-email.json"
import { APP_NAME } from "~/src/presentation/branding"
import { EmailBrandHeader } from "~/src/presentation/emails/email-brand-header"
import { EmailFallbackLink } from "~/src/presentation/emails/email-fallback-link"
import { EmailLayout } from "~/src/presentation/emails/email-layout"

export const VERIFY_EMAIL_NAMESPACE = "emails.verify-email"

interface VerifyEmailProps {
  readonly locale: SupportedLocale
  readonly messages: typeof emailMessages
  readonly name: string
  readonly verifyUrl: string
}

export const VerifyEmail = ({ messages, locale, name, verifyUrl }: Readonly<VerifyEmailProps>): JSX.Element => {
  const t = createTranslator({ locale, messages: { emails: { "verify-email": messages } }, namespace: "emails.verify-email" })

  return (
    <EmailLayout lang={locale} preview={t("preview", { appName: APP_NAME })}>
      <EmailBrandHeader />
      <Section>
        <Heading className="m-0 mb-4 text-2xl font-bold">{t("heading")}</Heading>
        <Text className="m-0 mb-6 text-base text-neutral-600">{t("body", { name })}</Text>
        <Button href={verifyUrl} className="box-border rounded-md bg-neutral-900 px-5 py-3 text-center text-base text-white no-underline">
          {t("button")}
        </Button>
        <Text className="mt-6 mb-0 text-base text-neutral-600">{t("expiry", { hours: EMAIL_LINK_LIFETIME_HOURS })}</Text>
        <EmailFallbackLink label={t("fallback")} url={verifyUrl} />
        <Text className="mt-6 text-sm text-neutral-500">{t("footer")}</Text>
      </Section>
    </EmailLayout>
  )
}
```

## Messaggi

Crea `messages/<locale>/emails.<name>.json` in tutte le lingue. Includi una chiave `subject`; il caso d'uso la traduce separatamente dal corpo.

```json title="messages/en-US/emails.verify-email.json"
{
  "subject": "Verify your email address",
  "preview": "Verify your email for {appName}",
  "heading": "Verify your email",
  "body": "Hi {name}, thanks for signing up. Confirm your email address to finish setting up your account.",
  "button": "Verify email",
  "expiry": "The link works for {hours, plural, one {# hour} other {# hours}}.",
  "fallback": "If the button does not work, copy this link into your browser:",
  "footer": "If you did not create an account, you can safely ignore this email."
}
```

Le route non precaricano mai i namespace delle email; li carica sul server il caso d'uso che invia il messaggio.

## Invio

Il caso d'uso ricava la lingua dall'URL di callback che riceve, controlla il limite per destinatario, carica i messaggi, costruisce link assoluti con `localizePathname` e chiama `sendEmail`. `src/modules/verification/use-cases/send-verify-email.ts`:

```ts title="src/modules/verification/use-cases/send-verify-email.ts"
export const sendVerifyEmail = async ({
  callbackURL,
  token,
  user,
}: {
  callbackURL: string
  token: string
  user: { email: string; name: string }
}): Promise<void> => {
  if (!(await withinRecipientRateLimit({ kind: VERIFICATION_EMAIL_PURPOSE.VERIFY_EMAIL, recipient: user.email }))) {
    console.warn("[email] verification email not sent: the recipient reached the hourly limit")
    return
  }

  const callback = new URL(callbackURL, getRequest().url)
  const locale = extractLocaleFromPath(callback.pathname) ?? I18N.DEFAULT_LOCALE
  const verifyUrl = new URL(localizePathname({ locale, pathname: ROUTES.AUTH.VERIFY_EMAIL }), getRequest().url)
  verifyUrl.search = callback.search
  verifyUrl.searchParams.set("token", token)

  const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })

  await sendEmail({
    idempotency: { purpose: VERIFICATION_EMAIL_PURPOSE.VERIFY_EMAIL, token: crypto.randomUUID() },
    react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
    subject: createTranslator({ locale, messages })("subject"),
    to: user.email,
  })
}
```

`sendEmail` (`src/integrations/resend/resend.utils.ts`) invia tramite Resend da `RESEND_EMAIL_FROM` a meno che non venga indicato `from`, passa la chiave di idempotenza in modo che un nuovo tentativo non invii mai due volte e genera un errore quando Resend ne restituisce uno.

L'email di verifica usa una chiave nuova a ogni invio, `crypto.randomUUID()`, come le email di account esistente e di password cambiata: Better Auth firma i suoi token di verifica con timestamp al secondo, quindi una registrazione e un accesso nello stesso secondo portano lo stesso token e Resend tratterebbe la seconda email come un nuovo tentativo della prima.

## Chi invia cosa

- Gli hook di Better Auth in `src/integrations/better-auth/auth.server.ts` chiamano direttamente i casi d'uso: `sendVerifyEmail` per `emailVerification.sendVerificationEmail` e per le registrazioni ripetute di account non verificati, `sendExistingAccountEmail` per le registrazioni ripetute di account verificati, `sendResetPasswordEmail` per `emailAndPassword.sendResetPassword`, `sendPasswordChangedEmail` per `emailAndPassword.onPasswordReset`, `sendChangeEmailConfirmationEmail` per `user.changeEmail` e `sendDeleteAccountEmail` per `user.deleteUser.sendDeleteAccountVerification`.
- Le richieste di Better Auth arrivano su `/api/auth` senza prefisso di lingua, quindi gli hook ricavano la lingua dell'email dal `callbackURL` del flusso, un percorso di pagina localizzato, con `extractLocaleFromCallbackURL` o `extractLocaleFromPath` di `src/integrations/use-intl/i18n.paths.ts`. L'inglese è la lingua di riserva.
- I casi d'uso della newsletter inviano da soli le email di conferma e di notifica, ad esempio `subscribeToNewsletter`.
- L'handler del webhook `onOrderPaid` della funzionalità delle licenze chiama `sendPurchaseConfirmationEmail` dopo aver assegnato la licenza. L'email prende la lingua da `metadata.locale` dell'ordine, i link dall'host che ha ricevuto il webhook e il token di idempotenza dall'ID dell'ordine Polar, e un invio fallito fa fallire l'handler, così Polar ritenta.
- Se un ordine di licenza pagato non corrisponde a nessun account, `onOrderPaid` non assegna nulla e chiama `sendUnmatchedOrderAlert`, che avvisa il proprietario del sito in inglese.
- `recordWithdrawal`, chiamato da `submitWithdrawal`, invia l'avviso di ricevimento di una dichiarazione di recesso nella lingua della pagina da cui è stata inviata e la notifica del recesso al proprietario del sito in inglese. Un invio fallito finisce nei log e non fa fallire la dichiarazione.
- `createInvitation` e `resendInvitation` chiamano `sendInvitationEmail` con la lingua scelta dall’amministratore, salvata nell’invito. Il token di idempotenza è il token del link, quindi ogni nuovo link è una nuova email, e oltre il limite per destinatario l’invio fallisce con `TOO_MANY_REQUESTS` invece di saltare l’email.
- `sendVerifyEmail`, `sendResetPasswordEmail`, `sendExistingAccountEmail` e `subscribeToNewsletter` chiamano `withinRecipientRateLimit` (`src/lib/rate-limit.ts`) prima dell'invio: al massimo <RepositoryFact name="recipientEmailsPerHour" /> email di un tipo per indirizzo all'ora, con chiave basata su un hash SHA-256 dell'indirizzo. Oltre il limite registrano un avviso e non inviano nulla. Aggiungi lo stesso controllo a ogni email che un visitatore può attivare senza un account.

## Aggiungi un'email

1. Aggiungi il modello in `src/presentation/emails/<name>.tsx` con il suo `<NAME>_NAMESPACE` esportato.
2. Aggiungi `messages/<locale>/emails.<name>.json` in tutte le lingue.
3. Dai un nome al suo scopo nell'oggetto `<MODULE>_EMAIL_PURPOSE` del `<module>.constants.ts` del modulo mittente, che `email-purposes.test.ts` confronta con gli scopi di tutti gli altri moduli, e invialo dal caso d'uso a cui appartiene l'azione, passando `idempotency: { purpose, token }` con il token o l'id del record che lo attiva.
4. Testa il modello in `src/presentation/emails/__test__/` e il caso d'uso con `sendEmail` simulato.

Credenziali Resend: `RESEND_API_KEY` e `RESEND_EMAIL_FROM`. I test non contattano mai Resend.
