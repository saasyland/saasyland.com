## ルートファイル

ルートは `src/routes` 内のフラットなファイルです。ドットはパスセグメントになります。

| ファイル                          | URL                | 備考                                       |
| --------------------------------- | ------------------ | ------------------------------------------ |
| `__root.tsx`                      | すべてのページ     | ドキュメントシェルと root 名前空間         |
| `_site.tsx`                       | なし               | サイトヘッダー付きのパスなしレイアウト     |
| `_site._marketing.tsx`            | なし               | マーケティングページ用のパスなしレイアウト |
| `_site._marketing.terms.tsx`      | `/terms`           | マーケティングレイアウト内のページ         |
| `admin.tsx`                       | `/admin`           | `requireAdmin` ガード付きのレイアウト      |
| `admin.users.all.tsx`             | `/admin/users/all` | 管理画面レイアウト内のページ               |
| `_site._marketing.blog.index.tsx` | `/blog`            | `blog` レイアウトのインデックスページ      |
| `_site.docs.$.tsx`                | `/docs/*`          | ドキュメントページ用のスプラットルート     |
| `api/auth.$.ts`                   | `/api/auth/*`      | HTTP ハンドラー（コンポーネントなし）      |

`createFileRoute("…")` の ID は、ルータージェネレーターが管理する文字列リテラルです。ジェネレーターは `src/routeTree.gen.ts` も書き出します。`__test__` フォルダー内のファイルは無視されます。すべての URL には `ROUTES`（`src/routes.ts`）に定数があり、リンクには `<Link to={ROUTES.X}>` を使います。

## ページルート

ページルートは、`<Name>Page` コンポーネント、`export const Route` の直上に置く `NAMESPACE` 定数、そしてページのメタデータと名前空間を 1 つの `Promise.all` で読み込むローダーを定義します。

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

追加のデータも同じ `Promise.all` に入れます。たとえば `admin.users.all.tsx` では `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` を追加しています。`src/lib/seo.ts` の `pageHead` は、ローダーの `metadata` からタイトル、説明、canonical、`hreflang`、Open Graph、ソーシャル画像の各タグを生成します。[検索エンジンとソーシャルプレビュー](/docs/features/seo)を参照してください。

## レイアウトルート

レイアウトルートは、`<Name>Layout` コンポーネント、`NAMESPACES` 配列、そして保護されたエリアでは `beforeLoad` 内のガードを定義します。その `NAMESPACES` には、ほかの機能のものも含め、配下のページが必要とするすべての名前空間を挙げます。検索パラメーターは、ライセンスのページ `/app` と `/app/license` が `tier` で行っているように、それを読むページで検証します。

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "pages.license", "timezones"] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

ガードの `requireSignedIn`、`requireAdmin`、`redirectIfSignedIn`、`redirectIfVerified`、`redirectAfterAuth` は `src/integrations/better-auth/auth.routes.ts` で提供されています。

## 読み込み中のスケルトン [#loading-skeletons]

ほとんどのナビゲーションは、ペンディング UI が表示される前に完了します。リンクはホバー時とタッチ時にルートをプリロードし、公開ページはプリレンダリング済みです。ナビゲーションが `defaultPendingMs` の <RepositoryFact name="navigationPendingMs" unit="millisecond" /> を過ぎても完了しない場合、ルーターはルートのスケルトンを表示します。`defaultPendingMinMs` は <RepositoryFact name="navigationPendingMinMs" unit="millisecond" /> なので、ページの準備ができた時点でスケルトンを取り除きます。これが起こるのは、低速な回線のときや、新しい Worker アイソレートへの最初のリクエストのときです（[パフォーマンス](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) を参照）。

デフォルトのペンディングコンポーネントはありません。すべてのレイアウトルートとページルートが独自の `pendingComponent` を設定します。docs のページは docs レイアウトの内側に描画されます。`_site.docs.index.tsx` と `_site.docs.$.tsx` は、サイドバーの横に記事とその目次を描く `DocsIndexPending` と `DocsPagePending` を表示し、`docs` レイアウトは、別の場所から docs に入ったときに `DocsPending` を表示します。各スケルトンは自分が代わりに表示されるページの見た目をそのまま再現します。

- **ページスケルトン**（`SignInPending` や `LegalPending` など）は、エリアのペンディングファイルに置かれ、最上位の要素に `aria-busy="true"` を付けます。対象のファイルは `custom/auth/auth-pending.tsx`、`custom/admin/` 内の管理画面用ファイル（レイアウト用の `admin-pending.tsx`、エリアごとに 1 つずつの `<area>-pending.tsx`（`products-pending.tsx` など）、共有ブロックをまとめた `pending-blocks.tsx`）、`custom/app/` 内の顧客アプリ用ファイル（レイアウト用の `app-pending.tsx`、`auth-pending.tsx`、`license-pending.tsx`、それらが共有するページヘッダーをまとめた `pending-blocks.tsx`）、`custom/` 直下の公開レイアウト用ファイル（レイアウト用の `marketing-pending.tsx`、`core-pending.tsx`、`legal-pending.tsx`、`license-pending.tsx`、`newsletter-pending.tsx`）、`custom/blog/blog-pending.tsx`、`custom/courses/courses-pending.tsx`、`custom/docs-pending.tsx` です。
- **レイアウトスケルトン**（`AuthPending` や `MarketingPending` など）は、レイアウトの外枠を描画し、その中に `pendingComponent` を描画します。描画するのは、現在のパスでレイアウトより下にあるルートのうち、`pendingComponent` を持つ最初のルートのもので、`src/hooks/use-page-pending.ts` の `usePagePending` がルートツリーから読み取ります。そのため、別の場所からエリアに入ったときも正しいページが表示されます。`AdminUsersPending` のように 1 階層下にあるレイアウトスケルトンも、自分のページに対して同じことをします。`Wordmark` や `PageFrame` など、データを必要としない外枠の要素は本物がそのまま描画されます。サイトヘッダーも画面に表示されたままです。ヘッダーを描画する `_site` レイアウトには、待つべきローダーがないためです。
- **テキストのプレースホルダー**は、実際の要素のタイプトークンに `h-lh scale-y-70` を加えた `Skeleton` バーです。これにより、各バーがちょうど 1 つのラインボックスを埋めます。ボックスには実際の高さと角丸の半径を使います。リストの長さは、`src/data/auth.ts` の `OAUTH_PROVIDERS` や `AUTH_ASSURANCES` など、UI と同じ定数から取ります。

ページを追加するときは、そのスケルトンをエリアのペンディングファイルに追加し、ルートの `pendingComponent` に設定します。レイアウトスケルトンはそこからスケルトンを見つけます。

## ルートに関するその他の事項

- **検索パラメーター**は、ルート内の `validateSearch` でパースします。例として、`/admin/products` の `tab` パラメーターがあります。スキーマは `src/lib/search-params.ts` のヘルパーで組み立てた `zod.object` です。`searchText()` と `searchFlag()` は値が欠けている、空である、または不正な形式である場合に `undefined` を返し、`searchChoice(choices, fallback)` はその場合にフォールバック値を返します。`searchParam(schema)` は、値がニュースレターのトークンなど任意の zod スキーマに一致しない限り `undefined` を返します。
- **単一ルート用のサーバー関数**は、ルートファイル内で `createServerFn` を使って定義できます。
- **ビルド時に作るコンテンツ**: ドキュメント、ブログ、ランディングのローダーは、`virtual:content-indexes` からコンテンツのインデックスを読みます。これは `/assets/` 配下のファイルなので、サーバー関数は要らず、クライアント側のナビゲーションではブラウザーで実行されます（[Fumadocs](/docs/integrations/fumadocs#content-indexes) を参照）。
- **HTTP エンドポイント**は `src/routes/api` に置きます。詳しくは [TanStack Start の HTTP ハンドラー](/docs/architecture/api-layer)を参照してください。

## ルーター

`src/router.tsx` がエクスポートする `getRouter` は、リクエストごとに新しい `QueryClient` とルーターを作成し、次の設定を行います。

- `presentation/components/custom` のデフォルトのエラーと not-found の各コンポーネント。デフォルトのペンディングコンポーネントは設定しません（[読み込み中のスケルトン](#loading-skeletons)を参照）
- インテント時のプリロードと、読み込んだページにもプリロードしたページにも共通の <RepositoryFact name="routerStaleTimeMinutes" unit="minute" />のデフォルト stale time。ページがアイドルになると `Navigation` がヘッダーのためにプリロードするページは、クリックされた時点でもまだ新しいままです（[パフォーマンス](/docs/conventions/performance#the-headers-pages-load-before-a-click)を参照）
- 受信した URL からロケールプレフィックスを取り除き、生成するリンクには付け直す `rewrite`
- `setupRouterSsrQueryIntegration` による SSR クエリ統合

## デプロイの後 [#after-a-deploy]

デプロイのたびに Worker の静的アセットは置き換わり、Vite は各ファイルに内容に基づく名前を付けるため、デプロイ前に開いたタブはもう存在しないルートのチャンクを要求します。TanStack Start は各ルートのコンポーネントとローダーをそれぞれ別のチャンクに分けます。TanStack Router はコンポーネントのチャンクを読み込めないとページを再読み込みします（`lazyRouteComponent`）が、ローダーのチャンクは router-core が `lazyFn` で読み込み、失敗したインポートをそのままローダーのエラーとしてルートに渡します。そのため、このようなタブで **Blog** をクリックすると、ブログのレイアウトのローダーのチャンクで失敗し、エラーページが表示されていました。

ルーターのデフォルトのエラーコンポーネントである `DefaultError` が、これに対処するようになりました。`src/lib/stale-build.ts` の `isStaleBuildError` は、新しいデプロイが削除したコードをページが実行していることを示すエラーを判別します。

- 失敗した動的インポート。router-core の `isModuleNotFoundError` が Chromium、Firefox、Safari で判別します。
- チャンクのために Vite がプリロードできなかったファイル（スタイルシートなど）。Vite はこれを `vite:preloadError` イベントで通知します。ルートルートはアプリケーションが開いている間このイベントを監視します（`listenForStaleBuilds`）。

このようなエラーの場合、`DefaultError` は訪問者が移動しようとしたアドレスを `router.navigate({ href, reloadDocument: true, replace: true })` で新しいページとして読み込むため、訪問者はクリックしたページに新しいデプロイの内容でたどり着きます。ブラウザーがページを離れるまでは、エラーメッセージの代わりに処理中を示す空の `main` を表示します。`claimReload` は、このような再読み込みを宛先とビルドごとに 1 回だけ許可します。宛先は、ページのエントリースクリプトの URL と一緒に `sessionStorage` に記録されます。すべてのチャンクはエントリーから内容に基づく名前でたどられるため、この URL はブラウザーが読み込むファイルを変えるデプロイのたびに変わります。同じビルドで同じ宛先が再び失敗するとエラーページを表示するので、本当に存在しないファイルがページを延々と再読み込みさせることはなく、次のデプロイでは改めて 1 回の再読み込みが許可されます。ブラウザーがセッションストレージを拒否した場合は、何も再読み込みしません。

Safari は、訪問者がページを離れ始めた時点で、そのページがまだ読み込んでいるファイルを取り消します。そのため、読み込み途中のチャンクやスタイルシートは、デプロイで削除されたときと同じように失敗します。そこで `listenForStaleBuilds` はページが `beforeunload` を受け取ったことも記録し、`DefaultError` はページを読み込み直す前に、`pageshow`、`pointerdown`、`keydown` のいずれかで訪問者がとどまったと分かるまで `whenPageStays` で待ちます。離れる訪問者は、離れようとしたページに戻されることなく求めたページに着き、ページに戻ってきた訪問者やとどまった訪問者はその時点で読み込み直しを受けます。`stale-build.spec.ts` はレッスンで動画プレーヤーのスタイルシートを止めたままプライバシーポリシーへ移動し、スタイルシートを取り消して、プライバシーポリシーが開き、レッスンが再び要求されないことを確かめます。

失敗したプリロードは何も消費しません。リンクにポインターを重ねるとルーターはそのルートをプリロードし、ヘッダーもページがアイドルになると自分のリンクについて同じことをしますが、それが失敗してもエラーコンポーネントは表示されず、訪問者がクリックしたときにルーターがチャンクをもう一度取得します。`e2e/specs/stale-build.spec.ts` は、ヘッダーが先にブログを読み込まないようにデータセーバーを有効にしてから、開いているページからブログのチャンクを取り除き、クリックが、ポインターを重ねたときのプリロードが失敗した後でも、1 回の再読み込みでブログにたどり着くこと、そしてチャンクが欠けたままのページは 2 回の再読み込み（`DefaultError` による 1 回と `lazyRouteComponent` による 1 回）の後にエラーページを表示することを確認します。
