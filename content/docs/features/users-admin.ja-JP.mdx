## ルート

`src/routes/admin.users.tsx` はレイアウトで、リンク形式のタブは `src/areas/browser.ts` の `userTabs` です。これは各エリアの `src/areas/<area>.ts` を `order` の順にまとめます。タブはパスを指定し、そのページのルートは `AdminUsersPending` がタブの下に描画するスケルトンを設定します。エリアの `navigation.<area>.json` にあるタブのラベルはパンくずリストでもそのページの名前になります。認証エリアは **全ユーザー** と **招待** を、決済のエリアは **顧客** を追加します（[注文と顧客](/docs/features/orders#customers)を参照）。`/admin/users` は `/admin/users/all` へリダイレクトします。どのタブもページタイトルは `pages.admin.users` から取ります。

| ルート                     | 内容                                                                               |
| -------------------------- | ---------------------------------------------------------------------------------- |
| `/admin/users/all`         | すべてのアカウントを表示するデータグリッド、検索と絞り込みはサーバー側             |
| `/admin/users/customers`   | Polar のすべての顧客と、そのアカウント、注文、返金後の支払額                       |
| `/admin/users/invitations` | 未承諾の招待と、**ユーザーを招待する**、**再送信**、**取り消す**                   |
| `/admin/users/$userId`     | ユーザーのプロフィール: アカウントの詳細、セッション、ほかのエリアが追加するカード |

## すべてのユーザー

```tsx
<DataGrid
  columns={columns}
  empty={t("empty")}
  id={USER_GRID_ID}
  label={t("label")}
  query={(request) => getUsersPageQuery(userZodSchemas.getUsers.parse(request))}
  rowActions={UserRowActions}
  search={t("search")}
  selectable
/>
```

- `getUsersPageQuery` はサーバー関数 `getUsers`（`src/modules/user/use-cases/get-users.ts`、権限 `user: ["list"]`）を呼び出します。`userZodSchemas.getUsers` がグリッドのリクエストを検証し、ページネーション、並べ替え、検索、すべての絞り込みはサーバー側で行います。
- 検索は名前とメールアドレスを対象にします。絞り込みは、ユーザーをテキストで、ロールとステータスを複数選択で、メール確認と 2FA をはい・いいえで、タイムゾーンを複数選択で、作成日時と更新日時を日の範囲で指定します。
- ステータスは列ではありません。`getUserStatus`（`user.utils.ts`）が `banned` と `emailVerified` から `banned`、`pending`、`active` を導き、サーバーは同じ SQL の `case` 式で並べ替えと絞り込みを行います。`UserStatusBadge`（`user-status-badge.tsx`）がテーブルとプロフィールでステータスを表示します。
- `useUserColumns` は `src/presentation/components/custom/admin/users/user-columns.tsx` にあり、各ユーザーの名前はそのユーザーのプロフィールへリンクし、ユーザー列は左端に固定されます。最初に表示されるのはユーザー、ロール、ステータス、メール確認、作成日時で、2FA、タイムゾーン、更新日時は「列」メニューから表示できます。作成日時と更新日時は `common.dateTime` メッセージを使い、閲覧者自身のタイムゾーンで略称付きで表示されるため、どちらの列も 1 つのタイムゾーンで表示され、並べ替えられます。
- 各行の末尾には、グリッドの `rowActions` として `UserRowActions` が右端に固定されて表示されます。CSV はユーザーを `name <email>` の形式で書き出し、ロール、ステータス、はい・いいえはテーブルの表示どおりに書き出します。

**ユーザーを追加** は `CreateUserDialog`（`create-user-dialog.tsx`）を開きます。これは `userZodSchemas.createUser` で検証する TanStack Form のフォームで、名前、メールアドレス、初期パスワード、ロールを入力します。`createUser`（`user: ["create"]`。ロールについては Better Auth が `user: ["set-role"]` もチェックします）を呼び出し、新しいユーザーのプロフィールを開きます。Better Auth はメールアドレスが未確認の状態でアカウントを作成するため、最初のサインインで `/auth/verify-email` に移動し、そこで確認リンクが送信されます。

## プロフィール [#profile]

`src/routes/admin.users.$userId.tsx` は、ユーザー、そのセッション、ほかのエリアのカードのデータを同時に読み込み、ページのタイトルをユーザーの名前にします。存在しないユーザーの場合は Not Found ページになります。

- `getUserQuery` はユーザーの行を読み取ります（`get-user.ts`、`user: ["get"]`）。`UserDetails`（`user-details.tsx`）は、ロール、ステータス、メール確認、二要素認証、タイムゾーン、作成日時と更新日時を `ADMIN_USER_DETAILS`（`src/data/admin.ts`）の順に表示し、`AdminUserProfilePending` も同じ順序に従います。
- `listUserSessionsQuery` はユーザーの有効なセッションを、トークンを除いて新しい順に一覧表示します（`list-user-sessions.ts`、`session: ["list"]`）。`UserSessions`（`user-sessions.tsx`）は各デバイスとそのアクティビティを表示し、`revokeUserSession` で 1 つのセッションを、確認のうえ `revokeUserSessions` ですべてのセッションを失効させます（どちらも `session: ["revoke"]`）。`revokeUserSession` はセッションの ID を受け取り、サーバー側でそのトークンを調べます。これは `revokeSession` が管理者自身のセッションに対して行うのと同じです。
- ほかのエリアは、アカウントの詳細の下に表示するカードを `src/areas/<area>.ts` で追加し、`src/areas/browser.entries.ts` がそれらを `BROWSER_AREAS`（`src/areas/browser.ts`）にまとめます。セクションは、カード、`AdminUserProfilePending` も描画するそのスケルトン、そしてページがそのユーザーについて読み込むデータを指定します。認証エリアは何も追加しません。ライセンスのエリアは `UserLicense`（`user-license.tsx`）を追加します。これは `userLicenseQuery`（`get-user-license.ts`、`user: ["get"]`）を読み取り、プラン、ステータス、購入日時、即時提供への同意、最初のアクティベーション、最初のテンプレートのダウンロード、最初に開いた有料レッスン、そして有効なライセンスの場合は返金できるかどうかを表示します。返金できるかどうかは、リクエストの時点でサーバーが判断します（[ライセンス](/docs/features/licences#records-and-refunds)を参照）。その下には `UserWithdrawals`（`user-withdrawals.tsx`）があり、`userWithdrawalsQuery`（`get-user-withdrawals.ts`、`user: ["get"]`）を読み取って、アカウントの撤回の意思表示を新しい順に一覧にします。入力された氏名、メールアドレス、注文番号、購入者の特定方法、意思表示が届いた時点の返金条件、受領確認をメールで送信したかどうかを表示します（[ライセンス](/docs/features/licences#withdrawal-function)を参照）。これらの文言は `pages.admin.users.license` にあり、ライセンスのエリアが `src/areas/license.ts` でレイアウトに追加します。
- ライセンスカードには、`LICENSE_ACTIVATION_LIMITS` によるパッケージの端末の上限と、**使用中の端末** の下に、キーが Polar で有効化した端末が表示されます。Polar の上限に対する台数と、各端末のラベル、システム、有効化日時です。`userActivationsQuery`（`get-user-activations.ts`、`user: ["get"]`）は、`polar.licenseKeys.get` で一度に最大 <RepositoryFact name="defaultPageSize" /> 件のアカウントについてそれらを読み取ります。各リクエストのタイムアウトは <RepositoryFact name="licenseActivationsTimeoutSeconds" unit="second" />で、応答は <RepositoryFact name="licenseActivationsStaleMinutes" unit="minute" />保持します。キーのないライセンスでは Polar がまだキーを発行していないことを伝え、Polar が応答しないキーではカードの残りを表示したまま Polar に接続できなかったことを伝えます。
- 最初に開いた有料レッスンでは、日時の下にレッスンとそのコースが表示されます。ライセンスのエリアは、コースのエリアの `OpenedLessonName` でタイトルを表示し、`lessonTitleQuery`（`get-lesson-title.ts`、`course: ["read"]`）で読み込むので、ライセンスのモジュールはコースのテーブルを読みません。その後削除されたレッスンの場合、行には日時だけが表示されます。
- 決済のエリアは `UserOrders`（アカウントの注文と通貨ごとの返金後の支払額）を追加します（[注文と顧客](/docs/features/orders#customers)を参照）。

ヘッダーには、ユーザーの名前とメールアドレス、そしてテーブルの行と同じアクションメニューが表示されます。

## アクション

`UserActions`（`row-actions.tsx`）はユーザーごとのメニューで、テーブルの最後の列（`UserRowActions`）とプロフィールにあります。

| 項目                           | 開くもの                 | サーバー関数                                  |
| ------------------------------ | ------------------------ | --------------------------------------------- |
| **ユーザーを編集する**         | `EditUserDialog`         | `updateUser`（`user: ["update"]`）、名前のみ  |
| **ロールを変更**               | ロールのサブメニュー     | `setUserRole`（`user: ["set-role"]`）         |
| **パスワードをリセットする**   | `ResetPasswordDialog`    | `setUserPassword`（`user: ["set-password"]`） |
| **このユーザーとしてログイン** | なし、そのままサインイン | `impersonateUser`（`user: ["impersonate"]`）  |
| **ユーザーを利用停止**         | `BanUserDialog`（確認）  | `banUser`（`user: ["ban"]`）                  |
| **利用停止を解除**             | なし                     | `unbanUser`（`user: ["ban"]`）                |
| **ユーザーを削除する**         | `DeleteUserDialog`       | `deleteUser`（`user: ["delete"]`）            |

- サインイン中の管理者自身の行には **ロールを変更**、**ユーザーを利用停止**、**ユーザーを削除する** がないため、管理者が自分自身を締め出すことはありません。いずれにしても、Better Auth は呼び出し元自身の利用停止や削除を拒否します。
- **このユーザーとしてログイン** は、管理者でも利用停止中でもないユーザーにだけ表示されます。Better Auth は `user: ["impersonate-admins"]` がなければ管理者へのなりすましを拒否し（この権限はどのロールにもありません）、利用停止中のユーザーにはセッションを与えません。[なりすまし](/docs/features/impersonation)を参照してください。
- プロフィールを開いているユーザーを削除すると、`/admin/users/all` に戻ります。
- 成功するたびに `USER_QUERY_KEYS.ALL`（セッションの場合は `SESSION_QUERY_KEYS.USER`）を無効化してトーストを表示し、権限不足を含むエラーは `useErrorMessage` を通して表示します。いずれかのアクションの実行中は、メニューボタンが無効になります。

各サーバー関数は `auth.middleware.ts` の `authorized(...)` で自身の権限をチェックします。`user` と `session` のステートメントは Better Auth の `defaultStatements` で、`admin` ロールは Better Auth の `adminAc` を持つため、`src/areas/auth.access.ts` は `admin` と `settings` だけを宣言します。`/admin` のガードは `admin: ["access"]` を持つロールだけを通します。

## 招待 [#invitations]

`/admin/users/invitations` の **ユーザーを招待する** は `InviteUserDialog`（`invite-user-dialog.tsx`）を開きます。これは `invitationZodSchemas.createInvitation` で検証する TanStack Form のフォームで、メールアドレス、`auth.roles.ts` の `ROLE_VALUES` から選ぶロール、メールの言語を入力します。メールの言語の初期値は管理者自身の言語です。`createInvitation`（`src/modules/invitation/use-cases/create-invitation.ts`、権限 `user: ["create"]`、`INVITATION_RATE_LIMIT` でレート制限）は、すでにアカウントか未承諾の招待があるアドレスを `CONFLICT` で拒否し、招待を保存して、`sendInvitationEmail` でリンクをメールで送信します。メールを送信できなかった場合、招待は再び削除されます。

`invitation` テーブルには、誰が誰を招待し、その招待がどうなったかが記録されます。

| 列                           | 内容                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| `email`、`role`、`locale`    | 小文字にした招待先のアドレス、アカウントに付与するロール、メールの言語                       |
| `token_hash`                 | リンクのトークンの SHA-256 ハッシュ。トークン自体はメールにしか含まれません                  |
| `invited_by`、`created_at`   | 招待した管理者とその日時                                                                     |
| `sent_at`、`expires_at`      | 最後のリンクを送信した日時と、リンクが使えなくなる日時（その `INVITATION_LIFETIME_DAYS` 後） |
| `accepted_by`、`accepted_at` | 招待を承諾したアカウントとその日時                                                           |
| `revoked_by`、`revoked_at`   | 招待を取り消した管理者とその日時                                                             |

ユーザーへの外部キーは `ON DELETE SET NULL` なので、記録はそこに記載されたアカウントより長く残ります。`accepted_at` と `revoked_at` が空の行に限った `email` の部分ユニークインデックスにより、アドレスごとに未承諾の招待は 1 件だけになります。

このタブは、`listInvitations`（`user: ["list"]`）で未承諾の招待を、保留中のものもリンクの期限が切れたものも含めて、`useInvitationColumns`（`invitation-columns.tsx`）を使った `DataGrid` に一覧表示します。このグリッドはブラウザー内で、メールアドレスと招待者で検索し、メールアドレス、ロール、ステータス、招待者、送信日、有効期限の日で絞り込みます。`InvitationRowActions` は各行の末尾に、**再送信** と **取り消す** を含むメニューを表示します。**再送信**（`resendInvitation`、招待と同じレート制限）は新しいリンクを送信します。新しいリンクはトークンを置き換え、有効期間を最初から数え直すため、以前のリンクは使えなくなります。**取り消す**（`revokeInvitation`）は最初に確認を求め、その後に管理者と日時を記録します。以後、リンクを開くと招待が取り消されたことが表示されます。

リンクは `/auth/invite?token=…`（`src/routes/auth.invite.tsx`）を開きます。`getInvitation` は招待先のアドレス、ロール、リンクのステータス（`INVITATION_STATUS`）を返し、ページには次のいずれかが表示されます。

- **保留中で、サインインしていない場合:** アドレス、名前、パスワードを表示します。`acceptInvitation`（トークンの利用と同じレート制限）はこれらを使い、Better Auth の `createUser` で、ロールを付与し、アドレスを確認済みにしたアカウントを作成してから、訪問者をサインインさせ、ロールに応じて `/admin` または `/app` を開きます。パスワードには、管理者が作成する新しいユーザーと同じポリシーと Have I Been Pwned のチェックが適用されます。**Google で続行** または **GitHub で続行** を使うと、サインインした状態で同じページに戻ります。
- **保留中で、招待先のアドレスでサインインしている場合:** **招待を承諾する** を表示します。`claimInvitation`（サインイン必須、トークンの利用と同じレート制限）がアカウントにロールと確認済みのアドレスを与えます。
- **保留中で、別のアドレスでサインインしている場合:** 両方のアドレスと **ログアウト** を表示します。
- **期限切れ、取り消し済み、承諾済み、または不明な場合:** 何が起きたかと、サインインする方法を表示します。

承諾の処理は、招待が未承諾でリンクの期限が切れていない間だけ招待を承諾済みにするため、1 つのリンクで作成できるアカウントは 1 つだけです。ロール自体は `admin` と `customer` で、後からユーザーごとに **ロールを変更** で設定します。
