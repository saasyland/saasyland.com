title: "Routendateien"

Jede Datei in `src/routes` hat dieselbe Form, sodass ein Leser, der eine kennt, alle kennt. Eine Routendatei setzt zusammen: Sie deklariert, was die Seite braucht, und platziert Komponenten. Widgets, Formulare, Dialoge und Tabellenspalten liegen in `src/presentation/components/custom`.

## Seitenrouten

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const columns = useCourseColumns()

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        rowActionsSize={COURSE_COLUMN_SIZES.actions}
        search={t("table.search")}
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Die Komponente** ist eine lokale `const` namens `<Name>Page` und wird zuerst definiert. Kleines Markup, das nur diese Seite verwendet, darf als lokale Komponente darüber stehen, wie `CourseProgress` und `StartLink` in `_site._marketing.courses.$course.index.tsx`; alles mit eigenen Daten, einer Mutation oder eigenem Zustand kommt in eine Komponentendatei.
- **Ein Namespace.** `const NAMESPACE = "pages.<area>.<page>"` steht direkt über `export const Route` und wird in `loadPageMetadata`, `preloadNamespaces` und `staticData` verwendet. Alles andere, was die Seite braucht, deklariert ihr Layout.
- **Ein `Promise.all`.** Der Loader startet alle Arbeiten gleichzeitig: Seitenmetadaten, den Namespace und jede Query, die die Komponenten lesen. Er gibt `{ locale, metadata }` für `head` zurück. Warte nie auf eine davon, bevor du die nächste startest.
- **`head: pageHead(ROUTES.X)`** baut Titel, Beschreibung, kanonische URL und Sprachalternativen aus den Metadaten in der Namespace-Datei.
- **Pfade stammen aus `ROUTES`** in `src/routes.ts`, das die Pfade aller Bereiche zusammenführt (siehe [Pfade und Navigation](#paths-and-navigation)); schreibe nie ein Pfadliteral.

Eine Seite, deren Titel aus einem Datensatz stammt, wartet auf diesen Datensatz und baut ihren Head aus den Loader-Daten, wie `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Layout-Routen

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Ein Layout deklariert `const NAMESPACES = [...] as const` über `export const Route` und lädt sie vor. Hat es keine, lässt es die Option weg; ein `namespaces: []` gibt es nicht.
- Einen Namespace, den eine Komponente eines anderen Bereichs im Layout braucht, fügt dieser Bereich in `src/areas/<area>.ts` hinzu, das das Layout über seine Routen-ID benennt, und das Layout übernimmt `...layoutNamespaces("/app")` per Spread in seine `NAMESPACES`. Der Lizenzbereich fügt `pages.license`, `pages.withdrawal` und `withdrawal.validations` zu `/app` hinzu, dessen Übersicht die Lizenzkarte und das Angebot und dessen Lizenzseite die Widerrufskarte zeigt, außerdem `withdrawal.validations` zu `/_site/_marketing` und `pages.admin.users.license` zu `/admin/users`; der Zahlungsbereich fügt `pages.admin.customers` und `pages.admin.orders` zu `/admin/users` hinzu; und der Newsletter-Bereich fügt `/_site/_marketing` und `/_site/docs`, deren Footer das Newsletter-Formular zeigen, `auth.validations` hinzu. `browser.test.tsx` prüft beim Kompilieren, dass jedes Layout, das ein Bereich nennt, eine Routen-ID ist.
- Die Komponente, sofern das Layout eine rendert, heißt `<Name>Layout` und platziert ein `<Outlet />`.
- Ein Guard gehört in `beforeLoad` des Layouts, dem der Bereich gehört: `beforeLoad: requireAdmin` in `admin.tsx`, `requireSignedIn` in `app.tsx`, beides Layouts des Auth-Bereichs. Guards entscheiden nur über die Navigation; jede Server Function prüft trotzdem ihre eigene Berechtigung.

## Reihenfolge der Optionen

`sort-keys` ist in `src/routes` abgeschaltet, weil TanStack Router Typen in der Reihenfolge der Deklaration ableitet. Optionen sind alphabetisch sortiert, außer dass `validateSearch` als Erstes kommt, vor allen Optionen, die die Suchparameter lesen:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Schreibe nie ein Array oder Objekt mit Daten inline in `createFileRoute`; deklariere es darüber als Konstante.

## Suchparameter

`validateSearch` ist ein `zod.object`, gebaut aus den Helfern in `src/lib/search-params.ts`:

| Helfer                            | Wert, wenn der Parameter fehlt oder fehlerhaft ist | Verwendung                           |
| --------------------------------- | -------------------------------------------------- | ------------------------------------ |
| `searchText()`                    | `undefined`                                        | Tokens, E-Mail-Adressen, Fehlercodes |
| `searchFlag()`                    | `undefined`                                        | Booleans                             |
| `searchParam(schema)`             | `undefined`                                        | Jedes andere Schema, etwa ein Pfad   |
| `searchChoice(choices, fallback)` | `fallback`                                         | Ein Tab oder eine Ansicht            |

Fehlender Text bleibt `undefined`, sodass ein Standardwert nie in eine URL gelangt, die der Router baut. Ein `searchChoice`-Parameter wird mit `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }` kombiniert, das den Standardwert aus der URL entfernt. Eine Seite, auf die eine andere Website Besucher zurückschickt, deklariert außerdem `search: { middlewares: [onlyDeclaredSearch(schema)] }` mit ihrem eigenen Schema, so wie `/app` und `/app/license` für den Checkout von Polar: Der Router baut ihre Adresse dann nur mit den deklarierten Parametern, und der Server leitet eine Adresse mit einem anderen Parameter auf dieselbe Adresse ohne ihn weiter, bevor eine Prüfung oder die Seite ihn liest. Schreibe nie von Hand Prüfungen wie `typeof search["x"] === "string"`; ergänze einen Helfer, wenn eine neue Art von Feld nötig ist. Braucht eine Kindkomponente einen Parameter, dessen Vorhandensein die Seite validiert hat, grenzt die Seite ihn ein und reicht ihn weiter, so wie `auth.reset-password.tsx` `token` an `ResetPasswordForm` übergibt. Seiten, die dieselben Parameter lesen, teilen sich ein Schema in `src/data`, das auch ihre Skeletons parsen, so wie `/app/license` und der Teil der Übersicht, den der Lizenzbereich beiträgt, mit `licenseSearchSchema` (`src/data/license.ts`).

## Skeletons

Navigation muss sich sofort anfühlen, daher hat jede Route, die eine Seite rendert, eine `pendingComponent`, die sie spiegelt: dasselbe Layout, dieselben Karten und dieselbe Anzahl an Zeilen.

- Skeletons liegen in der Pending-Datei des Bereichs (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) und verwenden `Skeleton` von shadcn.
- Skeletons liegen im Einstiegsskript jeder Seite, daher importiert ein Skeleton `Skeleton`, die shadcn-Primitive, andere Skeletons und die Konstanten, die seine Längen bestimmen, nie ein Formular oder die Datei, die eines enthält; `pending-imports.test.ts` schlägt fehl, wenn eines `@tanstack/react-form` erreicht (siehe [Performance](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Ein Textplatzhalter erhält das echte Typografie-Token plus `h-lh scale-y-70`, sodass er die Höhe der Zeile hat, die er ersetzt: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- Listenlängen stammen aus den Konstanten, die die Seite verwendet: `DataGridPending` in `data-grid-pending.tsx` zeichnet standardmäßig `DEFAULT_PAGE_SIZE` Zeilen, die Seitengröße jeder Admin-Tabelle.
- Ein Layout-Skeleton rendert die `pendingComponent` der ersten Route unterhalb seines Layouts, die für den aktuellen Pfad eine hat; `usePagePending(layout)` in `src/hooks/use-page-pending.ts` liest sie aus dem Routenbaum. So arbeiten `AdminPending`, `AppPending`, `AuthPending` und `MarketingPending` für ihre Layouts und `AdminUsersPending` und `AdminCourseSectionPending` eine Ebene tiefer. Die Route einer Seite ist deshalb die einzige Stelle, die ihr Skeleton nennt, egal welches Layout es zeigt; `/admin/users`, das zu `/admin/users/all` weiterleitet, setzt das Skeleton dieser Seite.
- Es gibt keine routerweite `defaultPendingComponent`. `src/router.tsx` setzt `defaultPendingMs` auf <RepositoryFact name="navigationPendingMs" unit="millisecond" /> und `defaultPendingMinMs` auf <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, beide aus `src/data/navigation.constants.ts`: Eine Navigation, die bis dahin nicht abgeschlossen ist, zeigt das Skeleton der Route, und das Skeleton verschwindet, sobald die Seite bereit ist, ohne länger stehen zu bleiben. Routen behalten diese Werte bei; die Messungen dahinter stehen unter [Performance](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once).
- Die Docs-Seiten zeichnen ihre Skeletons innerhalb des Docs-Layouts: `DocsIndexPending` und `DocsPagePending` füllen die Grid-Bereiche des Artikels und des Inhaltsverzeichnisses von Fumadocs, sodass eine Navigation zwischen Docs-Seiten die Seitenleiste auf dem Bildschirm hält. Die Seitenkomponente rendert das MDX in einer eigenen `<Suspense key={path}>`, sodass die Seitenleiste funktioniert, bevor der MDX-Chunk der Seite geladen ist, und eine Navigation das Server-HTML der vorherigen Seite ersetzt, statt es mit den Daten der nächsten Seite zu hydrieren.

## Links

- Router-Links erhalten eine Konstante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>` oder ein Routenmuster mit `params` für dynamische Pfade. `LinkButton` und `SidebarMenuLink` von shadcn erhalten `to` auf dieselbe Weise, und `AnchorButton` erhält ein `href` für eine Adresse außerhalb des Routenbaums.
- Füge einem Router-Link nie das Locale-Präfix hinzu; das Rewrite des Routers ergänzt es. Eine vollständige URL in der aktuellen Locale, für einen Wert, der den Router als String verlässt, kommt aus `router.buildLocation({ ... }).publicHref`, so wie `use-auth-redirect.ts` seine Anmeldelinks baut. `localizePathname` ist für URLs gedacht, die außerhalb eines Router-Kontexts oder für eine andere Locale gebaut werden: E-Mails, Weiterleitungsziele von Better Auth, Links in MDX und der Sprachumschalter.

## Pfade und Navigation [#paths-and-navigation]

Keine Datei der Anwendung listet alle Bereiche auf. Jeder Bereich, etwa die Kurse, die Produkte oder die Rechtstexte, deklariert seine eigenen Pfade, Menüeinträge samt ihren Beschriftungen, Seiten-Skeletons und Berechtigungen, und ein Barrel führt sie zusammen. Ein Bereich kommt also mit seinen eigenen Dateien hinzu oder fällt mit ihnen weg. So setzt die `saasyland`-CLI ein Projekt aus Template-Layern zusammen. Nur `scripts/areas.ts`, das die Anwendung nie lädt, listet die optionalen Bereiche mit ihren Dateien auf, damit `bun run check:areas` die Typen der Website ohne jeden von ihnen prüfen kann ([Testen](/docs/conventions/testing#tests-follow-the-areas)).

| Was                               | Jeder Bereich deklariert                                                        | Barrel                            | Gelesen aus                                                                                                                                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pfade                             | `src/areas/<area>.shared.ts`: ein `export const` pro Pfad                       | `src/routes.ts`                   | `import * as ROUTES from "~/src/routes"`                                                                                                                                                     |
| Menüeinträge                      | `src/areas/<area>.navigation.ts`: `entries` in einem Objekt `<AREA>_NAVIGATION` | `src/areas/navigation.entries.ts` | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` und `FOOTER_NAVIGATION` in `src/data/navigation.ts` |
| Dashboard-Statistiken und -Panels | `src/data/<area>.dashboard.ts`: eine Liste `<AREA>_DASHBOARD`                   | `src/data/dashboard.entries.ts`   | `ADMIN_DASHBOARD_STATS` und `ADMIN_DASHBOARD_PANELS` in `src/data/dashboard.ts`                                                                                                              |
| Berechtigungen                    | `src/areas/<area>.access.ts`: ein Objekt `<AREA>_ACCESS`                        | `src/areas/access.entries.ts`     | `APP_STATEMENTS` und `grantsOf` in `src/integrations/better-auth/auth.access.ts`                                                                                                             |
| Nicht gelistete Pfade             | `src/areas/<area>.shared.ts`: `unlisted` in einem Objekt `<AREA>_SHARED`        | `src/areas/shared.entries.ts`     | `UNLISTED_ROUTES` und `isUnlistedRoute` in `src/areas/shared.ts`                                                                                                                             |
| Layout-Namespaces                 | `src/areas/<area>.ts`: `layoutNamespaces` in einem Objekt `<AREA>_BROWSER`      | `src/areas/browser.entries.ts`    | `layoutNamespaces(layout)` in `src/areas/browser.ts`                                                                                                                                         |

Ein Barrel enthält nur Zeilen der Form `export { … } from`, eine pro Bereichsdatei und nach Modul sortiert, wie `src/integrations/drizzle-orm/drizzle.schemas.ts`. Ein Barrel, das nur optionale Bereiche füllen, bekommt außerdem eine Datei vom Kern, etwa `src/areas/core.ts`, die nur den Namen des Kerns enthält, sodass ein Projekt ohne diese Bereiche weiterhin Typprüfung und Lint besteht. Das Barrel der Pfade ist `src/routes.ts` selbst, und jede Datei importiert es als einen Namespace, `import * as ROUTES from "~/src/routes"`, sodass jeder Pfad seinen Literaltyp behält und `<Link to={ROUTES.COURSES}>` weiterhin gegen den Routenbaum geprüft wird:

```ts title="src/routes.ts"
export { API, HOME } from "./areas/core.shared.ts"
export { ADMIN_COURSES, ADMIN_COURSES_CREATE, COURSES } from "./areas/courses.shared.ts"
```

Ein Menüeintrag gibt mit `placement` (`NAVIGATION_PLACEMENT` in `src/data/navigation.constants.ts`) an, wo er erscheint: in der Admin-Sidebar, in den Schaltflächen über dem Dashboard, in den Schnellaktionen der Befehlspalette, in der Seitenleiste des Kundenbereichs und ihren Ressourcen, im öffentlichen Header oder im Footer. Sein `order` sortiert ihn zwischen die Einträge der anderen Bereiche, sodass keine Liste von der Reihenfolge der Dateien abhängt. Admin-Einträge nennen außerdem ihre Sidebar-Gruppe (`group`), Footer-Links ihre Spalte (`column`); `ADMIN_NAVIGATION_GROUPS` und `FOOTER_COLUMNS` legen die Reihenfolge der Gruppen und Spalten fest, und eine Gruppe oder Spalte, die kein Bereich füllt, entfällt. Die Admin-Konsole und der Kundenbereich existieren nur mit Anmeldung, deshalb gehören sie dem Auth-Bereich: ihre Pfade `/admin`, `/admin/settings`, `/app` und `/app/settings`, ihre Einträge für Dashboard, Übersicht, Einstellungen und Benutzerverwaltung sowie **Anmelden** im Header und im Footer:

Ein Header- oder Footer-Eintrag kann eine `signedIn`-Beschriftung nennen, die seine eigene für einen angemeldeten Besucher ersetzt, und sein Link führt dann zu dessen Arbeitsbereich: `/admin` für ein Konto mit Admin-Zugriff, `/app` für alle anderen. `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`) entscheidet anhand der Rolle in der Sitzung mit `hasPermission` und der Berechtigung `admin: ["access"]`, die `requireAdmin` prüft. Die öffentlichen Seiten sind vorgerendert, ihr HTML zeigt daher **Anmelden**; nach der Hydration fragt ein Browser, der das Cookie von Better Auth mit der zuletzt verwendeten Anmeldemethode hat, nach seiner Sitzung, und Header, mobiles Menü und Footer zeigen an dieser Stelle **Dein Konto**, gleich mit dem Link zum richtigen Arbeitsbereich. Ein Browser, der sich nie angemeldet hat, fragt nichts ab. Bis ein Teil der Seite hydriert ist, liefert `useVisitorWorkspace` nichts, auch wenn der Browser die Sitzung schon hat, weil `useHydrated` während der Hydrierung durch React den Wert des Servers liefert: Ein Footer, der erst nach dem Eintreffen der Sitzung hydriert, rendert dasselbe **Anmelden** wie das HTML und wechselt danach, statt die Hydrierung zu brechen.

Jeder Admin-Eintrag öffnet eine Ansicht, die mit echten Daten arbeitet, und die Landingpage zählt sie alle. Eine Ansicht, deren Daten noch keine Quelle haben, bekommt keinen Eintrag (siehe [Admin-Dashboard](/docs/features/admin-dashboard#real-data-only)).

Der Lizenzbereich fügt der Seitenleiste des Kundenbereichs seinen Eintrag **Lizenz** hinzu, und der Inhaltsbereich fügt ihren Ressourcen über der Support-Adresse **Dokumentation** hinzu. Der Kernbereich deklariert nur `/` und `/api` sowie im Header **Preise**, den einzigen Eintrag mit `hash`, der zum Preisabschnitt von `/` führt.

Eine Dashboard-Statistik hat ein `prefetch`, das der Loader von `/admin` ausführt, und einen Hook `useValue`, den `DashboardStats` aufruft, um die Zahl zu lesen.

Die Access-Datei eines Bereichs deklariert die Berechtigungs-Statements seiner Ressourcen und die Rollen, denen er sie gewährt. `auth.access.ts` baut die Zugriffskontrolle von Better Auth aus `APP_STATEMENTS` und jede Rolle aus `grantsOf(role)` auf, sodass die Auth-Integration keinen Bereich nennt, und `APP_STATEMENTS` schlägt fehl, wenn zwei Bereiche dieselbe Ressource deklarieren (siehe [Rollen und Berechtigungen](/docs/guides/roles-and-permissions)).

Die Listen in `src/data/navigation.ts` haben einen deklarierten Typ, `NavigationEntry`, statt der Typen der Einträge, die die Bereiche gerade deklarieren. Eine Platzierung, die kein Bereich füllt, etwa die Dashboard-Aktionen in einem Projekt ohne den Zahlungsbereich, ist deshalb eine leere Liste, die trotzdem die Typprüfung besteht. `navigation.test.ts` prüft beim Kompilieren, dass das `to` jedes Eintrags, den ein Bereich deklariert, ein Pfad des Routenbaums ist (`FileRouteTypes["to"]` aus `src/routeTree.gen.ts`).

Ein Eintrag erhält seinen Bereich (`area`) aus dem `name` des Objekts `<AREA>_NAVIGATION` seines Bereichs, und der Bereich beschriftet ihn in seiner eigenen Nachrichtendatei: `<placement>.<key>` in `messages/<locale>/navigation.<area>.json`, etwa `admin.courses` und `header.courses` in `navigation.courses.json`. Eine Dashboard-Statistik wird über ihren `key` in `dashboard.<area>.json` beschriftet, und ein Admin-Abschnitt beschriftet seine Unterseiten für die Breadcrumbs unter `breadcrumbs.<segment>` in seiner `navigation.<area>.json`, etwa `breadcrumbs.create`; ein Tab der Benutzerverwaltung wird unter `userTabs.<key>` beschriftet, was den Tab und seine Seite in den Breadcrumbs benennt, und ein Dashboard-Panel hält seine Texte unter seinem `key` in `dashboard.<area>.json`. Beide Arten von Dateien sind Root-Namespaces, sodass jedes Menü jeden Eintrag beschriften kann, und `useNavigationLabel` in `src/hooks/use-navigation-label.ts` liefert die Beschriftung eines Eintrags. Was zum Menü selbst gehört, bleibt in dessen Namespace: `groups.<group>` in `pages.admin.sidebar`, `columns.<column>` in `components.custom.footer` und der Call-to-Action, der Menü-Button und der Skip-Link des Headers in `components.custom.navigation`. `enum-labels.test.ts` schlägt fehl, wenn einem Eintrag oder einer Statistik in einer Locale die Beschriftung fehlt.

Ein Bereich, dessen Seiten der Worker bei jedem Request rendert, etwa `/admin`, `/auth` oder `/courses`, listet diese Pfade im Feld `unlisted` seines Objekts `<AREA>_SHARED` in `src/areas/<area>.shared.ts` auf. Das TanStack-Start-Plugin in `src/data/tanstack.vite.ts` nimmt sie mit `isUnlistedRoute` vom Prerendering aus, und `buildPageHead` gibt ihnen die Karte der Website statt einer Seitenkarte (siehe [Suche und Social-Media-Vorschauen](/docs/features/seo)). Vite löst den Alias `~` nicht auf, während es seine eigene Konfiguration lädt, deshalb importiert jede Datei in `src/areas`, die es lädt, `shared.ts`, `shared.entries.ts` und jede `<area>.shared.ts`, über relative Pfade. Der Worker-Einstieg, `vite.config.ts` und das Remotion-Projekt erreichen über `ROUTES` jede gemeinsame Datei, deshalb enthält eine gemeinsame Datei Pfade und nichts, was eine Abhängigkeit nachzieht. Live-Checks sind eine eigene Dateiart, `src/areas/<area>.live.ts`, weil nur die Prüfung nach dem Deployment und die Dokumentation sie laden. Auch die Menüeinträge sind eine eigene, reine Dateiart, `src/areas/<area>.navigation.ts`, die `src/areas/navigation.entries.ts` zusammenführt und `src/data/navigation.ts` liest, weil das Remotion-Projekt das Admin-Menü liest und sein CI-Job nur die eigenen Pakete von Remotion installiert, sodass es die Browser-Datei eines Bereichs, `src/areas/<area>.ts`, nicht laden kann, die Code von Router, TanStack Query und Server-Funktionen importiert.
