## Worker y bindings

`wrangler.jsonc` define `src/server.ts` como punto de entrada del Worker. El Worker recibe cuatro bindings:

| Binding  | Tipo               | Uso                                                                               |
| -------- | ------------------ | --------------------------------------------------------------------------------- |
| `DB`     | Base de datos D1   | Todas las tablas, incluidas las sesiones y los contadores de límite de peticiones |
| `CACHE`  | Namespace de KV    | El número de estrellas de GitHub y los descuentos regionales del checkout         |
| `MEDIA`  | Bucket de R2       | Archivos de vídeo, servidos por `serveMedia` bajo `/media/`                       |
| `ASSETS` | Recursos estáticos | Páginas prerenderizadas y archivos de `public`                                    |

Las peticiones a `/assets/*`, `/fonts/*`, `/robots.txt` y `/llms.txt` se sirven desde los recursos estáticos sin ejecutar el Worker. El código de servidor lee los bindings, los secretos y `waitUntil` de `cloudflare:workers`. `src/server.ts` añade las cabeceras de seguridad a cada respuesta que devuelve; los archivos que se sirven sin el Worker reciben el subconjunto de `public/_headers` ([Seguridad y endurecimiento](/docs/features/security)).

## Lo que aportan las áreas [#what-the-areas-add]

Ningún archivo de la plataforma nombra un área. Cada área, como los cursos o la venta de licencias, aporta en sus propios archivos lo que necesita en el Worker, la ruta raíz, la compilación de Vite y el despliegue, y un barrel los reúne, igual que las rutas y los menús (consulte [Rutas y navegación](/docs/conventions/routes#paths-and-navigation)):

| Qué                          | Cada área declara                                               | Barrel                       | Lo usa                                                                                        |
| ---------------------------- | --------------------------------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------- |
| Handlers del Worker          | `src/data/<area>.worker.ts`: una lista `<AREA>_WORKER_HANDLERS` | `src/data/worker.entries.ts` | `DOCUMENT_HANDLERS` y `REQUEST_HANDLERS` en `src/data/worker.ts`, que ejecuta `src/server.ts` |
| Componentes raíz             | `src/data/<area>.root.ts`: una lista `<AREA>_ROOT_COMPONENTS`   | `src/data/root.entries.ts`   | `ROOT_COMPONENTS` en `src/data/root.ts`, que `src/routes/__root.tsx` monta junto al outlet    |
| Plugins de Vite              | `src/data/<area>.vite.ts`: una lista `<AREA>_VITE_PLUGINS`      | `src/data/vite.entries.ts`   | `vitePlugins` en `src/data/vite.ts`, que carga `vite.config.ts`                               |
| Comprobaciones de despliegue | `src/data/<area>.deploy.ts`: una lista `<AREA>_DEPLOY_CHECKS`   | `src/data/deploy.entries.ts` | `DEPLOY_CHECKS` en `src/data/deploy.ts`, que ejecuta `scripts/run-deploy-checks.ts`           |

Un handler de peticiones reclama un `pathPrefix` y responde a todas las peticiones bajo él antes del middleware de locale, los recursos estáticos y TanStack Start, como hace el handler del área de cursos con `/media/`. Un handler de documentos recibe cada página HTML que devuelve el Worker, con su locale y la petición, y devuelve la página que se enviará, como hacen los precios regionales del área de licencias. `src/server.ts` importa los handlers de forma estática, así que se evalúan en cada arranque en frío: un archivo de handlers solo importa constantes y utilidades puras y carga lo que pese más con un `import()` dinámico (consulte [Rendimiento](/docs/conventions/performance)).

Una entrada de plugins de Vite tiene un `order`, que sitúa sus plugins entre los de las demás áreas, y `vitest`, que indica si también se cargan con Vitest. Vite carga su configuración antes de que se resuelva el alias `~`, así que `vite.ts`, `vite.entries.ts` y cada `<area>.vite.ts` importan por ruta relativa con la extensión `.ts`, y una entrada importa su paquete de plugins dentro de su función `plugins`, para que `vp lint` y `vp fmt` nunca lo carguen.

Una comprobación de despliegue nombra un script del paquete con una variante por entorno desplegado. El área de Polar declara `polar:verify`, así que `bun scripts/run-deploy-checks.ts preview` ejecuta `bun run polar:verify:preview`.

## Entornos

`wrangler.jsonc` define cuatro entornos. `CLOUDFLARE_ENV` selecciona uno para `vp dev` y `vp build`.

| Entorno       | Bindings                                | Lo usa                                          |
| ------------- | --------------------------------------- | ----------------------------------------------- |
| `development` | D1, KV y R2 de preview remotos          | `bun run dev`                                   |
| `preview`     | D1, KV y R2 de preview                  | `bun run build:preview`, `deploy:preview`       |
| `production`  | D1, KV y R2 de producción               | `bun run build:production`, `deploy:production` |
| `test`        | D1, KV y R2 locales en `.wrangler/test` | `bun run build:test`, Playwright                |

Cada entorno enumera sus secretos obligatorios en `secrets.required`. Los valores salen del archivo `.env.<environment>` correspondiente; los scripts de despliegue escriben las claves declaradas en `.wrangler/secrets.<environment>.json` y pasan ese archivo a Wrangler con `--secrets-file`. El entorno `test` usa `src/platform/testing/worker.ts` como punto de entrada y los valores ficticios versionados en `.env.test`. `AFFONSO_PROGRAM_ID` es público, así que es una variable de Worker normal en `vars` y no un secreto; solo `test` lo define. Los secretos de un módulo forman un bloque, separado del siguiente por una línea en blanco, en el orden de `.env.example`, y de `.env.test` para `test`, de modo que un área aporta sus secretos como un solo bloque; `src/__test__/wrangler.test.ts` falla cuando los bloques de los dos archivos no coinciden.

## Tipos

- `src/types/worker-configuration.d.ts` lo genera `bun run cf-typegen` a partir del entorno `development` de `wrangler.jsonc` y declara `Cloudflare.Env`: los bindings `DB`, `CACHE` y `MEDIA` y todos los secretos de `secrets.required`. `src/types/bindings.d.ts` añade `ASSETS`, que Wrangler omite.
- Un área declara en `src/types/<area>.d.ts` solo lo que Wrangler no puede derivar: `affiliates.d.ts`, la variable opcional `AFFONSO_PROGRAM_ID`, que solo define `test`; `polar.d.ts`, los dos valores de `POLAR_SERVER`, y `repository-facts.d.ts`, el módulo `virtual:repository-facts`.
- `src/types/router.d.ts` registra el tipo del router y la opción de ruta `staticData.namespaces`.

## Infraestructura del runtime de pruebas

`src/platform/testing` contiene solo lo que no puede pertenecer a una única funcionalidad:

- `setup.ts`: los matchers de jest-dom, el reinicio de los bindings antes de cada prueba y el sustituto de `createServerFn` que ejecuta las funciones de servidor en el mismo proceso
- `mocks/cloudflare.ts`: un D1 en memoria sobre SQLite que ejecuta las migraciones del repositorio, un KV en memoria, un bucket `MEDIA` en memoria y un `waitUntil` que las pruebas pueden vaciar
- `mocks/cache.ts`: `createEdgeCache`, un sustituto de la caché de Workers para las pruebas de entrega de medios
- `mocks/resend.ts` y `mocks/polar.ts`: dobles de prueba estrictos de las API de Resend y Polar, y `mocks/providers.ts`, que dirige `fetch` hacia ellos en cada prueba y en el Worker de las pruebas de navegador
- `mocks/wrksz-themes.ts`: un sustituto de la librería de temas
- `lib/`: el puente RPC de las funciones de servidor, utilidades de renderizado, utilidades para las URL de las peticiones, ejecutores de consultas y modelos de Polar con webhooks firmados
- `worker.ts`: el punto de entrada del Worker para las pruebas de navegador, que instala los dobles de los proveedores y expone el correo entregado

Consulta [Pruebas y CI](/docs/architecture/testing-architecture) para ver cómo los usan las suites.
