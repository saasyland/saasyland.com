Historia `main` jest częścią produktu: każdy pull request scalony przez squash to jeden wiersz, który mówi, co zmieniło się dla osób korzystających z kodu.

## Commity

Komunikaty commitów są zgodne z Conventional Commits i pisze się je bez emoji; hook `prepare-commit-msg` dodaje emoji odpowiadające typowi (tabelę znajdziesz na stronie [Konwencjonalne commity](/docs/tooling/conventional-commits)):

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- Temat jest pisany małymi literami, w trybie rozkazującym, i mówi, co zmiana daje jej użytkownikom: `feat(course): reorder the catalogue from the course list`, a nie `update course files`.
- Zakresem jest moduł lub obszar: `course`, `auth`, `a11y`, `deps`, `readme`.
- Typem jest `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 lub `revert` 🗑️; hook odrzuca każdy inny. Nigdy nie wpisuj emoji samodzielnie: hook nie sprawdza tematu, który już się od niego zaczyna.
- Dziel pull request na logiczne commity: funkcję, jej dokumentację jako `docs(<scope>)` oraz poprawki znalezione po drodze.
- Nigdy nie commituj z `--no-verify`. Hook `pre-commit` uruchamia `bun run check:pre-commit`; gdy kończy się błędem, usuń przyczynę.
- Formatuj i lintuj tylko pliki, które zmieniłeś, przez `bunx vp fmt <files>` i `bunx vp lint --fix <files>`. Nie uruchamiaj `bun run check:fix` ani `vp check --fix` na całym repozytorium: przepisują pliki, których nie dotykałeś, w tym współdzielone ustawienia edytora w `.vscode/settings.json`. Jeśli `.vscode/` pojawi się w `git status`, przywróć go z `HEAD`.

## Bez atrybucji AI

Commity i opisy pull requestów nie zawierają trailera `Co-Authored-By` dla narzędzia AI, wiersza „Generated with” ani żadnej innej atrybucji AI, nawet jeśli narzędzie dodaje ją domyślnie. GitHub przypisuje adres z takiego trailera do niezwiązanego konta, które następnie pojawia się jako współtwórca repozytorium. To samo dotyczy poprawek zgłaszanych do projektów źródłowych (zobacz [Zależności](/docs/conventions/dependencies)).

## Gałęzie i worktree

- Twórz gałąź od `main`, jedną gałąź na pull request.
- Każdej gałęzi daj własny worktree Gita zamiast przełączać gałąź w istniejącym checkoucie, aby nigdy nie zmienić checkoutu, który ma otwarty edytor lub inny proces:

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Zanim zaufasz wynikom testów, sprawdź `git branch --show-current` w katalogu, w którym testowałeś.

### Hooki w każdym worktree [#hooks-in-every-worktree]

Git odczytuje `core.hooksPath` z konfiguracji, którą współdzielą wszystkie worktree repozytorium, a Vite+ ustawia w niej ścieżkę względną `.vite-hooks/_`, więc Git uruchamia dyspozytor hooków tego worktree, w którym tworzysz commit. Dyspozytor jest generowany i nigdy nie trafia do commita, dlatego każdy worktree potrzebuje własnego, a tam, gdzie go brakuje, Git bez ostrzeżenia pomija hooki. Instalują go dwa kroki:

- `git worktree add` uruchamia hook `post-checkout` checkoutu, z którego wywołujesz polecenie, a `.vite-hooks/post-checkout` instaluje dyspozytor nowego worktree poleceniem `vp hooks enable`. Commit utworzony przed `bun install` kończy się wtedy błędem w hooku `pre-commit`, zamiast go pominąć.
- `bun install` uruchamia `prepare`, który odświeża dyspozytor poleceniem `vp config --no-agent`, a potem uruchamia `scripts/verify-git-hooks.ts`. Instalacja kończy się błędem, gdy `core.hooksPath` ma inną wartość niż `.vite-hooks/_` albo gdy w dyspozytorze brakuje hooka z `.vite-hooks/`, a komunikat błędu podaje polecenie, które to naprawia.

Nigdy nie ustawiaj `core.hooksPath` na inną wartość i nigdy nie przekazuj Gitowi `-c core.hooksPath`. Dopóki to ustawienie zawierało bezwzględną ścieżkę do dyspozytora głównego checkoutu, `vp config` nie instalował dyspozytora w pozostałych worktree, a gdy następne `bun install` w głównym checkoucie przywróciło ścieżkę względną, commity w tych worktree powstawały bez hooków. `vp hooks status` pokazuje, czy hooki są aktywne w danym worktree.

## Liniowa historia [#linear-history]

Ruleset, który chroni `main` na GitHubie, wymaga liniowej historii, przyjmuje tylko scalanie przez squash i odrzuca force-push, więc każdy pull request trafia do `main` jako jeden commit. Gałęzie pull requestów również pozostają liniowe:

- Nigdy nie twórz commita scalającego, ani na `main`, ani na gałęzi pull requesta: nie scalaj `main` do gałęzi i nie rozwiązuj konfliktów w commicie scalającym.
- Aktualizuj gałąź, robiąc jej rebase na `main`, poleceniem `gh pr update-branch --rebase` albo poleceniami `git fetch origin` i `git rebase origin/main`.
- Gdy GitHub nie może zrobić rebase’u pull requesta z kilkoma commitami, wprowadź go ponownie jako jeden commit na szczycie `main`: połącz gałąź w jeden commit na jej bazie scalania, a potem zrób rebase tego commita, dzięki czemu każdy konflikt rozwiązujesz tylko raz:

```sh
git fetch origin
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -m "feat(course): reorder the catalogue from the course list"
git rebase origin/main
git push --force-with-lease
```

- Wypychaj przepisaną gałąź poleceniem `git push --force-with-lease` i tylko własną gałąź pull requesta. Nigdy nie rób force-pusha na `main` ani na gałąź innej osoby i nigdy nie używaj zwykłego `--force`, który nadpisuje commity wypchnięte od Twojego ostatniego fetcha.

## Pull requesty

- **Małe i ukierunkowane.** Jedna poprawka, jedna funkcja lub jeden refaktoring na pull request. Duża funkcja staje się stosem pull requestów, z których każdy da się przejrzeć osobno, tak jak powstawały wideo, kursy i administracja kursami.
- **Tytuł jest commitem squash.** Używaj formatu commitów; tytuł staje się tematem na `main`.
- **Opis** zawiera `## Summary` z tym, co się zmieniło i dlaczego, `## Test plan` z uruchomionymi poleceniami i ich wynikami oraz listę `## Docs` ze zaktualizowanymi stronami, sekcjami README i tekstami. Pisz go prosto, bez języka marketingowego.
- **Każdy pull request aktualizuje to, co czyni nieaktualnym:** README, strony dokumentacji we wszystkich językach oraz wszelkie teksty serwisu i deklaracje na stronie głównej, których dotyczy, a do tego dodaje własny [wpis w historii zmian](#changelog-entries). Nieścisłość znaleziona w kodzie, którego nie zmieniałeś, dostaje własny pull request.

## Wpisy w historii zmian [#changelog-entries]

Każdy pull request dodaje własny wpis do [historii zmian](/docs/project/changelog), dzięki czemu pull requesty otwarte równolegle nigdy nie edytują tego samego pliku.

- **Nazwij go numerem pull requesta.** Otwórz pull request, a potem dodaj `content/changelog/<number>.<locale>.mdx` we wszystkich językach: listę punktowaną bez frontmattera opisującą, co zmienia się dla osób korzystających z kodu, z linkami do stron dokumentacji, których dotyczy.
- **Nigdy nie wpisuj daty.** Strona historii zmian i informacje o wydaniu biorą dzień każdego wpisu z historii Gita: dzień (UTC) commita squash, którego temat GitHub kończy na `(#<number>)`. Dopóki pull request nie zostanie scalony, jego wpis jest wymieniony w sekcji **Niewydane**.
- **CI to sprawdza.** W pull requeście `bun run check` kończy się błędem, dopóki brakuje `content/changelog/<number>.en-US.mdx`, a `check:i18n` porównuje z nim każde tłumaczenie tak jak stronę dokumentacji. Błędem kończy się też plik nazwany ani numerem pull requesta, ani pełnym hashem commita: nieliczne zmiany, które trafiły do `main` bez pull requesta, noszą nazwę swojego commita.

## Kontrole

CI uruchamia `bun run check` i `bun run test:coverage`, następnie buduje testowego Workera i uruchamia zestaw testów przeglądarkowych w Chromium; wdrożenie preview następuje dopiero wtedy, gdy oba przejdą. Poczekaj także na wdrożenie preview: to jedyny krok, który przesyła Workera do Cloudflare, a limity przesyłania Cloudflare zablokowały już wdrożenie, które przeszło wszystkie inne kontrole. Zobacz [CI/CD](/docs/tooling/ci-cd).
