Workflows liegen in `.github/workflows/`. Die Anwendungs-Workflows (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `e2e-reusable.yml` und `deploy-reusable.yml`) richten die Toolchain mit der Composite Action `.github/actions/setup` ein: Bun <RepositoryFact name="bunVersion" />, Vite+ mit der Node-Version aus `.nvmrc` und dem Installations-Cache von Bun, den `setup-vp` einmal wiederherstellt, `bun install --frozen-lockfile --ignore-scripts` und `bun run typegen`. `remotion.yml` richtet stattdessen Node aus `.nvmrc` und npm ein.

| Workflow              | Auslöser                                                                                       | Jobs                                                                                                                  |
| --------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull Requests, Merge-Gruppen und Aufrufe aus `deploy.yml`                                      | Prüfungen, Tests mit Abdeckung auf parallelen Shards, E2E in Chromium und der Upload des Preview-Workers              |
| `deploy.yml`          | Pushes auf `main`                                                                              | Die Prüfungen von `ci.yml`, sofern die Merge Queue sie nicht ausgeführt hat, dann Preview, Produktion und das Release |
| `preview.yml`         | Manuell                                                                                        | Deployt einen Branch, dessen Prüfungen bestanden sind, in die gemeinsame Preview                                      |
| `e2e-full.yml`        | Pushes auf `main`, nach dem Zeitplan <RepositoryFact name="e2eFullSchedule" /> in UTC, manuell | WebKit bei Push; Chromium und WebKit bei geplanten und manuellen Läufen                                               |
| `journey.yml`         | Nach dem Zeitplan <RepositoryFact name="journeySchedule" /> in UTC, manuell                    | Die [Journey-Suite](#journey-suite) gegen die gemeinsame Preview, in der Polar-Sandbox                                |
| `e2e-reusable.yml`    | Von den obigen Workflows aufgerufen                                                            | Ein Test-Build, ein Playwright-Projekt auf parallelen Shards und eine Prüfung für beide                               |
| `deploy-reusable.yml` | Von `ci.yml`, `deploy.yml` und `preview.yml` aufgerufen                                        | Build, dann D1-Migrationen und `wrangler deploy` oder `wrangler versions upload`                                      |
| `remotion.yml`        | Änderungen an `remotion/` oder an den Dateien der Website, die es importiert                   | Prüft und bündelt das Videoprojekt der Landingpage mit npm                                                            |

`remotion.yml` reagiert bei Pull Requests und Pushes auf dieselben Pfade: `remotion/`, den Workflow selbst und die Dateien der Website, die `remotion/src` importiert, direkt oder über andere Dateien der Website. `src/__test__/workflows.test.ts` folgt diesen Imports und schlägt fehl, wenn eine erreichte Datei zu keinem der Pfade passt oder ein Pfad zu keiner der Dateien.

Die Checkouts in `e2e-reusable.yml`, dessen Build den Changelog rendert und dessen `content.spec.ts` ihn liest, in `deploy-reusable.yml`, der die Website baut, und im Job `release` holen jeden Commit ohne seine Trees (`fetch-depth: 0` und `filter: tree:0`): Der [Changelog](/docs/project/changelog) datiert jeden Eintrag nach dem Commit, der ihn nach `main` gebracht hat. Gegenüber einem Shallow Clone kommen nur die Commits selbst hinzu; ein Shallow Clone ließe den Build fehlschlagen, statt die Einträge falsch zu datieren. `src/__test__/workflows.test.ts` schlägt fehl, wenn einer dieser Checkouts die Historie nicht mehr holt.

## Prüfungen [#checks]

Hinter der erforderlichen Prüfung `Format, lint, types, i18n, tests` stehen drei Jobs in `ci.yml`:

| Job                                                  | Führt aus                                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                              | `bun run check`: Klassennamen-Tabellen, i18n- und Inhaltsprüfungen, das [Ablaufinventar](/docs/tooling/test-coverage#flow-coverage), Formatierung, Linting und Typen                                                                                                                                                            |
| `test`                                               | Ein Job pro Shard, <RepositoryFact name="vitestShards" /> parallel: `bun run test:coverage --shard=<n>/<total>` mit dem Blob-Reporter von Vitest, danach lädt er den Blob-Bericht des Shards mit seiner Abdeckung hoch                                                                                                          |
| `verify`, benannt `Format, lint, types, i18n, tests` | Sobald jeder Shard bestanden hat, lädt er die Blob-Berichte herunter und führt `bun run test:coverage --merge-reports` aus, das die Abdeckung zusammenführt und die Schwellenwerte durchsetzt, und lädt dann den Abdeckungsbericht hoch; schlägt fehl, sofern nicht `check`, jeder Shard und das Zusammenführen bestanden haben |

Ein Shard prüft keinen Schwellenwert, weil er nur den Code misst, den seine eigenen Tests erreichen; die Schwellenwerte aus `vite.config.ts` gelten einmal, für die zusammengeführte Abdeckung aller Shards, so wie bei einem lokalen `bun run test:coverage`. Der Job `verify` ist die eine Prüfung, die die Branch-Regeln verlangen, daher ändert das Hinzufügen oder Entfernen eines Shards keinen Namen einer erforderlichen Prüfung.

Der Job `e2e` ruft `e2e-reusable.yml` auf; dieser Workflow baut einmal und führt die Suite parallel auf <RepositoryFact name="e2eShards" /> Runnern aus:

| Job                                                | Führt aus                                                                                                                                                                                                        |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                            | `db:reset:test` und `build:test`, lädt dann `dist`, den Verweis `.wrangler/deploy` auf seine Worker-Konfiguration und das per Seed befüllte `.wrangler/test` als ein Artefakt hoch                               |
| `shard`                                            | Ein Job pro Shard, gestartet neben dem Build: installiert den Browser, wartet auf den Upload des Builds, lädt ihn herunter und führt `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>` aus |
| `report`, mit dem Namen `Build and E2E (chromium)` | Schlägt fehl, wenn der Build oder ein Shard nicht erfolgreich war; ist ein Shard fehlgeschlagen, führt er die Blob-Berichte der Shards zu einem HTML-Bericht zusammen und lädt ihn hoch                          |

Die Shards warten nicht auf den ganzen Job `build` (`needs`): Sie starten mit ihm und richten die Toolchain und den Browser ein, während er baut. Danach fragt `scripts/wait-for-job.ts` alle paar Sekunden über die API von GitHub den Job `build` des Laufs ab, bis dessen Schritt `Upload the test build` erfolgreich war, und der Shard lädt das Artefakt herunter. Das Skript sendet das ETag der vorigen Antwort mit, und GitHub rechnet eine unveränderte Antwort nicht auf das Rate Limit des Tokens an. Ein fehlgeschlagener Schritt des Builds oder ein Build, der ohne seinen Upload endet, lässt jeden Shard binnen Sekunden fehlschlagen, mit dem fehlgeschlagenen Schritt und einem Link zum Build, und ein Shard, der länger als das Limit des Skripts wartet, schlägt mit einer Fehlermeldung fehl, die das sagt. Die Jobs des Laufs zu lesen erfordert `actions: read`, das nur der Job `shard` anfordert: `ci.yml`, `e2e-full.yml` und der Job `checks` von `deploy.yml` gewähren es den Workflows, die sie aufrufen, und jeder andere Job behält `contents: read`.

Die eigenen Wiederholungen und Worker von Playwright bleiben auf jedem Shard so, wie [Playwright](/docs/tooling/playwright#configuration) sie beschreibt. Der Job `report` ist die einzige Prüfung, die die Branch-Regeln verlangen; das Hinzufügen oder Entfernen eines Shards ändert also keinen Namen einer erforderlichen Prüfung. Der Build packt außerdem die Liste der Release-Tags ein, die er gelesen hat, und jeder Shard löscht jeden seither angelegten Tag: `content.spec.ts` liest die Release-Tags aus Git, und ein Release, das getaggt wird, während die Shards warten, ließe es ein Changelog erwarten, das der Build nie gerendert hat.

Der Job `upload` mit dem Namen `Worker upload` ruft `deploy-reusable.yml` mit `upload: true` auf: Er baut den Preview-Worker genau so wie ein Deployment und führt `wrangler versions upload` aus, das ihn als neue Version an den Worker `saasyland-preview` sendet, ohne sie zu deployen. Cloudflare prüft den Upload wie ein Deployment, also das Größenlimit, die Startzeit, die Bindings und die Secrets, die `secrets.required` nennt, sodass sich ein Worker, der diese Prüfung besteht, deployen lässt, während `preview.saasyland.com` weiter die zuvor deployte Version ausliefert. Der Job wendet keine Migration an und legt kein GitHub-Deployment an (`deployment: false`), und er läuft parallel zu den Uploads anderer Pull Requests. Die Version eines Pull Requests erhält den Alias `pr-<number>`, der die Version im Dashboard von Cloudflare benennt; die Zusammenfassung des Jobs gibt die ID und die Größe der Version aus und ihre URL, wenn Version URLs für den Worker aktiviert sind, was sie für `saasyland-preview` derzeit nicht sind. Pull Requests aus Forks und von Dependabot können die Cloudflare-Zugangsdaten nicht lesen und überspringen den Job; die Merge Queue, die sie lesen kann, lädt ihren Build hoch, bevor sie gemergt werden.

In einem Pull Request schlägt `bun run check` außerdem fehl, bis der Pull Request seinen [Changelog-Eintrag](/docs/conventions/git-workflow#changelog-entries) hinzufügt, und in der Merge Queue, bis der Eintrag des eingereihten Pull Requests vorhanden ist. Der Build in den Jobs `e2e` und `upload` und in den Deploy-Jobs schlägt fehl, solange der Changelog einen Eintrag unter **Unveröffentlicht** aufführen würde, der nicht der des Pull Requests selbst ist, und in der Merge Queue und auf `main`, solange er überhaupt einen aufführen würde.

## Merge Queue [#merge-queue]

Das Ruleset, das `main` schützt, verlangt `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)` und `Worker upload / Upload preview` und lässt Pull Requests nur über die Merge Queue von GitHub zu, die jeden einzelnen zu einem Squash-Commit zusammenfasst. `bun scripts/enqueue-pr.ts <number>` stellt einen Pull Request in die Queue ([Git und Pull Requests](/docs/conventions/git-workflow#merging)). Für jeden Pull Request in der Queue schreibt GitHub den Squash-Commit auf einen Branch namens `gh-readonly-queue/main/pr-<number>-<commit>`, auf `main` und den Pull Requests vor ihm, und führt darauf `ci.yml` für das Ereignis `merge_group` aus. Sobald jeder Pull Request einer Gruppe bestanden hat, setzt GitHub `main` auf den letzten Commit der Gruppe, genau den Commit, den die Queue getestet hat, sodass ein einziger Push jeden Pull Request der Gruppe als eigenen Squash-Commit in `main` bringt. Ein Pull Request, der fehlschlägt, verlässt die Queue, und die Pull Requests hinter ihm werden ohne ihn erneut getestet.

`ci.yml` bricht den Lauf eines Pull Requests ab, wenn ein neuerer Commit ihn ersetzt, aber nie einen Lauf der Queue, deren Branches jeweils eine eigene Ref haben. Die Changelog-Prüfung behandelt den Branch der Queue wie `main`: Jeder Pull Request der Gruppe ist bereits ein Squash-Commit, dessen Betreff mit seiner Nummer endet, also darf kein Eintrag unveröffentlicht sein, und der eigene Eintrag des eingereihten Pull Requests muss vorhanden sein.

## Deployments

`deploy.yml` deployt jeden Push auf `main`, zuerst in die gemeinsame Preview und danach in die Produktion, sobald der Commit jede Prüfung bestanden hat, die `main` verlangt. Sein erster Job, `tested`, führt `scripts/tested-commit.ts` aus, das diese Prüfungen über die API von GitHub aus dem Ruleset liest und für jede einen erfolgreichen Lauf auf dem gepushten Commit sucht. Ein Commit, der über die Merge Queue kam, hat sie, weil die Queue genau diesen Commit getestet hat, also deployt `deploy.yml` ihn, ohne die Prüfungen erneut auszuführen; ein Commit, der auf anderem Weg in `main` gelangt ist, durchläuft zuerst die Prüfungen von `ci.yml`.

| Ereignis                         | Ziel                         | GitHub-Umgebung              | URL                                                  |
| -------------------------------- | ---------------------------- | ---------------------------- | ---------------------------------------------------- |
| Push auf `main`                  | `preview`, dann `production` | `Preview`, dann `Production` | https://preview.saasyland.com, https://saasyland.com |
| Manueller Lauf von `preview.yml` | `preview`                    | `Preview`                    | https://preview.saasyland.com                        |

`deploy-reusable.yml` gibt jeder GitHub-Umgebung ihre URL, und `src/__test__/workflows.test.ts` schlägt fehl, wenn eine davon vom Host der Umgebung in `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`) abweicht. Die Preview ist gemeinsam genutzt: Jedes Deployment ersetzt das vorherige und verwendet dieselbe Preview-D1-Datenbank, denselben KV-Namespace und dieselben R2-Buckets. Auf ihr läuft `main`, sodass die [Journey-Suite](/docs/tooling/playwright#journey-suite), die Webhooks der Polar-Sandbox und die Anmeldung auf `preview.saasyland.com`, dem einzigen Preview-Host, dem Better Auth vertraut, alle auf den Code treffen, den die Produktion als Nächstes ausführt, und jede Migration die Preview-Datenbank vor der Produktion erreicht. Um dort einen Branch vor dem Merge auszuprobieren, führe `gh workflow run preview.yml --ref <branch>` aus: Es deployt den Branch samt Migrationen nur, wenn sein Commit die Prüfungen bestanden hat, die `main` verlangt, und der nächste Push auf `main` stellt `main` wieder her.

`deploy-reusable.yml` prüft, ob die Secrets `CLOUDFLARE_API_TOKEN` und `CLOUDFLARE_ACCOUNT_ID` vorhanden sind, führt `scripts/verify-bindings.ts` aus, baut mit den Platzhalterwerten aus `.env.test`, entfernt die erzeugte `dist/server/.dev.vars`, wendet `db:migrate:<target>` an und führt `vp exec wrangler deploy --config dist/server/wrangler.json` aus oder führt, mit `upload: true`, anstelle der letzten beiden Schritte `vp exec wrangler versions upload` aus. `scripts/verify-deployment.ts`, die Prüfung der Live-Website aus den `deploy:<target>`-Skripten, läuft hier nicht, weil der Bot-Schutz von Cloudflare Anfragen von CI-Runnern mit 403 beantwortet. Auch `scripts/run-deploy-checks.ts` läuft hier nicht. CI führt also keinen der Deploy-Checks aus, die die Bereiche in `DEPLOY_CHECKS` deklarieren: In CI gibt es keine `.env.<target>`, und die GitHub-Umgebungen enthalten nur die Cloudflare-Zugangsdaten, dazu in `Preview` die Sandbox-Einstellungen der [Journey-Suite](#journey-suite). Derzeit sind das `auth:verify` aus dem Auth-Bereich und `polar:verify` aus dem Polar-Bereich; führe `bun run auth:verify:<target>` lokal aus, nachdem du einen OAuth-Client geändert hast, und `bun run polar:verify:<target>` nach jeder Änderung in Polar ([Polar-Einrichtung](/docs/getting-started/polar-setup)). Es wird keine Secrets-Datei hochgeladen: Der Worker behält die Laufzeit-Secrets, die bereits in Cloudflare gesetzt sind. Deployments auf dasselbe Ziel werden in eine Warteschlange gestellt, statt sich gegenseitig abzubrechen, und Uploads laufen parallel. Ein neuer Commit in einem Pull Request bricht den Lauf von `ci.yml` für den vorherigen Commit ab, den niemand mergen wird, während die Läufe der Merge Queue einander nie abbrechen und die von `deploy.yml` und `e2e-full.yml` auf `main` in eine Warteschlange gestellt werden (`concurrency` mit `queue: max`), sodass jeder Push auf `main` deployt wird.

Dependabot aktualisiert die GitHub Actions wöchentlich.

## Journey-Suite [#journey-suite]

`journey.yml` führt `bun run test:journey` aus, die [Journey-Suite](/docs/tooling/playwright#journey-suite), gegen `https://preview.saasyland.com`, nach dem Zeitplan <RepositoryFact name="journeySchedule" /> in UTC und wenn jemand ihn von Hand startet:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` ist `all`, `core`, `complete`, `agency` oder `upgrade`; jeder Wert außer `all` führt nur den Test mit diesem Tag aus. Der Job liest diese Secrets der GitHub-Umgebung `Preview`, ohne ein Deployment zu erfassen (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` und `RESEND_API_KEY`. Er setzt `POLAR_SERVER` auf `sandbox`, den einzigen Wert, den die Suite akzeptiert, und die Suite baut ihren Polar-Client für die Sandbox, sodass der Workflow das produktive Polar nicht erreichen kann. Läufe reihen sich ein und brechen einander nie ab, denn ein abgebrochener Lauf ließe seine Bestellungen bezahlt. Der Job schreibt das Ergebnis und die Dauer jedes Tests und den Fehler jedes fehlgeschlagenen Tests in die Zusammenfassung des Laufs und lädt den HTML-Bericht, `playwright-report/journey.json` und die Traces, Videos und Maschinenverzeichnisse der fehlgeschlagenen Tests als Artefakt `journey-report` hoch.

Der Workflow läuft nicht nach jedem Deployment von `main`. Jeder Lauf registriert auf Preview ein Konto pro Test, bezahlt und erstattet dessen Bestellungen in der Polar-Sandbox und sendet ihre Bestätigungs-E-Mails und Kaufbestätigungen über das Resend-Konto, das Preview mit der Produktion teilt. `main` wird an einem vollen Tag viele Male deployt, ein Lauf nach jedem Deployment würde diese E-Mails also gegen die Sendelimits vervielfachen, von denen die E-Mails der Produktion abhängen, und er würde nichts aufhalten: Die Produktion wird direkt nach der Preview deployt, was immer die Journey findet. Der nächtliche Lauf findet einen kaputten Kauf innerhalb eines Tages. Starte ihn von Hand nach einer Änderung an Zahlungen, Lizenzen oder der CLI-Lizenz-API und nach `gh workflow run preview.yml --ref <branch>`, um einen Branch vor dem Merge zu testen.

## Releases und Tags [#releases-and-tags]

Die Website wird kontinuierlich deployt, deshalb sind ihre Versionen Datumsangaben statt semantischer Versionen. Wenn ein Deployment in Produktion erfolgreich war, versieht der Job `release` in `deploy.yml` den deployten Commit mit dem Tag `vYYYY.MM.DD` nach dem UTC-Datum und veröffentlicht dazu ein GitHub Release. Ein zweites Deployment in Produktion am selben Tag erhält den Tag `vYYYY.MM.DD.2`, das nächste `.3` und so weiter. Preview-Deployments erhalten nie einen Tag. Der Job `release` ist der einzige Job mit `contents: write`.

Die Release Notes sind die Einträge im [Changelog](/docs/project/changelog), die das Release ausgeliefert hat, also die seit dem vorherigen Release-Tag in `main` angekommenen, jeweils mit `(#<number>)` am Ende, das GitHub auf den Pull Request verlinkt, sodass jede Änderung an genau einer Stelle beschrieben ist; hat ein Release keinen ausgeliefert, verlinken seine Notes auf den Changelog. `scripts/publish-release.ts` nimmt die Notes aus `src/lib/release.ts` und führt `gh release create` mit dem Tag aus, den das Deployment gewählt hat. Ein erneuter Lauf behält den Tag, den der Commit bereits hat, und überspringt ein bereits vorhandenes Release.

Der Job des Produktions-Deployments wählt diesen Tag vor dem Build: `scripts/choose-release-tag.ts` wendet `releaseTag` aus `src/lib/release.ts` auf die Tags des Checkouts an, der Build erhält den Tag als `RELEASE_TAG`, und der Job gibt ihn als Output `release-tag` an den Job `release` weiter, sodass Deployment und Release denselben Tag tragen. Damit verlinkt der [Changelog](/docs/project/changelog) jeden Eintrag auf das Release, das ihn als erstes ausgeliefert hat: den frühesten Release-Tag, dessen Commit den Squash-Commit des Eintrags in der First-Parent-Historie von `main` enthält, die der Build zusammen mit den Daten in einem einzigen `git log` liest, oder den eigenen Tag des Deployments für die Einträge, die es mitbringt. Der Job `release` liest den Changelog genauso, mit dem Tag, den er veröffentlicht, sodass die Notes eines Release genau die Einträge sind, die die Seite auf dieses Release verlinkt. Einträge, die vor dem ersten Release-Tag gemergt wurden, verlinken auf kein Release, ebenso in lokalen Builds, Preview-Builds und Builds von Pull Requests die Einträge, die noch kein Deployment ausgeliefert hat. Zwei Produktions-Deployments können nicht denselben Tag wählen: `deploy.yml` führt jeweils nur einen Workflow-Lauf aus (`concurrency` mit `queue: max`), sodass der Job `release` des vorherigen Laufs seinen Tag erstellt hat, bevor das nächste Deployment das Repository auscheckt.

Um die Produktion auf ein Release zurückzusetzen, mach in einem Pull Request alles nach seinem Tag rückgängig:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Nach dem Merge wird der Code des Tags mit den üblichen Prüfungen deployt und als neues Release getaggt. D1-Migrationen werden nicht zurückgenommen, der ältere Code läuft also auf dem neueren Schema. Jede Schemaänderung muss mit der Anwendung funktionieren, die vor ihr deployt wurde; das macht diesen Weg für das vorherige Release sicher. Lies die Migrationen dazwischen, bevor du weiter zurückgehst.
