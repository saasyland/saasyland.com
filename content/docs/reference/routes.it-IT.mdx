Ogni percorso ha una costante in `ROUTES`, dichiarata in `src/routes.ts`, che non importa nulla (vedi [Percorsi e navigazione](/docs/conventions/routes#paths-and-navigation)). I link usano la costante, ad esempio `<Link to={ROUTES.SIGN_IN}>`, e il router aggiunge il prefisso del locale. Ogni pagina elencata qui sotto viene servita anche con ciascun prefisso di locale non predefinito, ad esempio `/pl-PL/terms`.

## Pagine pubbliche

Queste pagine si trovano nel layout `_site`, che mostra l'intestazione del sito. Tutte, a parte la documentazione, si trovano anche nel layout `_marketing` (cornice della pagina e footer), il layout della documentazione mostra da sé lo stesso footer, e il blog e la documentazione hanno layout propri al loro interno. Sono tutte prerenderizzate, tranne le pagine della newsletter.

| ----------------------------- | ------------------------ | -------------------------------------------------------------- |
| `/`                           | `HOME`                   | `_site._marketing.index.tsx`                                   |
| `/licence`                    | `LICENCE`                | `_site._marketing.licence.tsx`                                 |
| `/privacy`                    | `PRIVACY`                | `_site._marketing.privacy.tsx`                                 |
| `/terms`                      | `TERMS`                  | `_site._marketing.terms.tsx`                                   |
| `/refunds`                    | `REFUNDS`                | `_site._marketing.refunds.tsx`                                 |
| `/withdrawal`                 | `WITHDRAWAL`             | `_site._marketing.withdrawal.tsx`                              |
| `/affiliates`                 | `AFFILIATES`             | `_site._marketing.affiliates.tsx`                              |
| `/newsletter/confirm`         | `NEWSLETTER_CONFIRM`     | `_site._marketing.newsletter.confirm.tsx`                      |
| `/newsletter/unsubscribe`     | `NEWSLETTER_UNSUBSCRIBE` | `_site._marketing.newsletter.unsubscribe.tsx`                  |
| `/blog`                       | `BLOG`                   | `_site._marketing.blog.tsx`, `_site._marketing.blog.index.tsx` |
| `/blog/rss.xml`               | `BLOG_FEED`              | nessuno                                                        |
| `/blog/page/*`                | nessuna                  | `_site._marketing.blog.page.$page.tsx`                         |

`/*` è ogni indirizzo che nessun’altra route riconosce: `_site._marketing.$.tsx` lancia `notFound()`, quindi il server risponde 404 con la pagina non trovata, renderizzata a ogni richiesta (vedi [Pagina non trovata](/docs/features/landing-page#not-found-page)).

`/blog/rss.xml` non ha un file di route: `scripts/generate-seo-files.ts` scrive il feed di ogni lingua dopo la build (vedi [Feed RSS](/docs/features/blog#feed)).

## Corsi

Il layout `/courses` (`_site._marketing.courses.tsx`) si trova nei layout `_site` e `_marketing`, come il blog, e non ha guard: il server controlla il livello di accesso di ogni lezione (vedi [Corsi](/docs/features/courses)). Queste pagine leggono D1 a ogni richiesta e non vengono prerenderizzate. `/sitemap-courses.xml` non ha un file di rotta: risponde un handler delle richieste in `src/server.ts`, a partire da D1 (vedi [Sitemap dei corsi](/docs/features/seo#course-sitemap)).

| Percorso                     | Costante          | File di route                                                        |
| ---------------------------- | ----------------- | -------------------------------------------------------------------- |
| `/courses`                   | `COURSES`         | `_site._marketing.courses.tsx`, `_site._marketing.courses.index.tsx` |
| `/courses/<course>`          | nessuna           | `_site._marketing.courses.$course.index.tsx`                         |
| `/courses/<course>/<lesson>` | nessuna           | `_site._marketing.courses.$course.$lesson.tsx`                       |
| `/sitemap-courses.xml`       | `COURSES_SITEMAP` | nessuno                                                              |

## API

I percorsi API non vengono mai localizzati.

| Percorso                                     | Costante        | File di route                                                                                                                                      |
| -------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api`                                       | `API`           | `api/index.ts`                                                                                                                                     |
| `/api/auth/*`                                | `API_AUTH_BASE` | `api/auth.$.ts`                                                                                                                                    |
| <RepositoryFact name="cliApiBasePath" />`/*` | nessuna         | `api/cli.v1.license.ts`, `api/cli.v1.activations.ts`, `api/cli.v1.activations.$activationId.ts`, `api/cli.v1.activations.$activationId.bundles.ts` |

I percorsi dell'API delle licenze della CLI vengono dal suo contratto, `API_BASE_PATH` e `API_ROUTE` in `@saasyland/stack/api`, e `src/routes/api/__test__/cli.v1.test.ts` verifica che il router invii ciascuno di essi al proprio file di route (vedi [API delle licenze della CLI](/docs/features/cli-licence-api)).

`ROUTES.API_AUTH` elenca i percorsi degli endpoint propri di Better Auth e di quelli dei suoi plugin di amministrazione e di autenticazione a due fattori, relativi a `/api/auth`; `auth.server.ts` li usa per escludere alcuni endpoint dal rate limiting, e `INPUT_POLICY` in `auth.hooks.ts` per validare gli endpoint che accettano una password, un nome, un'email o un'immagine. `ROUTES.API_AUTH_POLAR` elenca i webhook del plugin Polar, che `auth.server.ts` esclude dal rate limiting, e, come `API_AUTH_CUSTOMER_PORTAL`, sparisce insieme all'area Polar. `API_AUTH_CUSTOMER_PORTAL` e `API_AUTH_VERIFY_EMAIL` sono percorsi completi di endpoint di Better Auth, costruiti a partire da `API_AUTH_BASE`. `AUTH` e `NEWSLETTER` non hanno una pagina propria; insieme ad `ADMIN`, `APP`, `API` e `COURSES` identificano le aree che non vengono mai prerenderizzate (`REQUEST_RENDERED_ROUTES` in `src/routes.ts`, che `isRequestRenderedRoute` legge), e `verify-build.ts` fa fallire una build che ha prerenderizzato una pagina sotto uno di essi.

## Media

`/media/<expiry>.<signature>/<videoId>/<file>` serve i file video firmati. Non ha una costante in `ROUTES` né un file di route: `src/server.ts` lo passa a `serveMedia` prima del middleware del locale, quindi non viene mai localizzato. Vedi [Cloudflare R2](/docs/integrations/cloudflare-r2).

`/media/covers/<courseId>/<file>` serve le copertine pubbliche dei corsi tramite `serveCover`, e `/media/downloads/<expiry>.<signature>/<attachmentId>/<fileName>` i materiali firmati delle lezioni tramite `serveAttachment`. L’handler di `/media/` dell’area dei corsi li manda lì, quindi neanche loro vengono mai localizzati. Vedi [Copertine dei corsi](/docs/features/courses#course-covers).

<RepositoryFact name="cliBundleUrlPath" /> serve allo stesso modo i bundle di template firmati della CLI, tramite `serveBundle`, e prende il
suo prefisso da `BUNDLE_PATH_PREFIX` in `license.constants.ts`. Vedi [API delle licenze della
CLI](/docs/features/cli-licence-api#template-bundles).
