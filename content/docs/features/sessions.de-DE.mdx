---

Sitzungen liegen in der D1-Tabelle `session` (`src/modules/session/session.schema.ts`). `auth.session.ts` liest sie mit `getRequestSession`, pro Anfrage memoisiert, und stellt Routen und Komponenten `getCurrentSessionQuery` bereit. Die clientseitige Kopie enthält nie das Sitzungstoken.

Jede Sitzung speichert außerdem `country`, ein zusätzliches Feld von Better Auth, das der Datenbank-Hook `session.create.before` in `auth.server.ts` aus dem Header `cf-ipcountry` füllt, den Cloudflare jeder Anfrage hinzufügt (`COUNTRY_HEADER`). Nur ein Code aus dem Katalog `COUNTRIES` wird übernommen, sodass das Feld bei Tor-Adressen (`T1`) und unbekannten Adressen (`XX`) leer bleibt. Browser und Betriebssystem stammen aus dem User-Agent: `sessionDevice` in `src/modules/session/session.utils.ts` erkennt die gängigen Browser und Systeme am Namen und unterscheidet Smartphones von Tablets.

## Anwendungsfälle

| Anwendungsfall                            | Middleware                       | Verwendet von  |
| ----------------------------------------- | -------------------------------- | -------------- |
| `getActiveSessions`                       | angemeldet                       | `SessionsCard` |
| `revokeSession`                           | angemeldet; nur eigene Sitzungen | `SessionRow`   |
| `revokeOtherSessions`                     | angemeldet                       | `SessionsCard` |
| `listUserSessions`                        | `session: ["list"]`              | `UserSessions` |
| `revokeUserSession`, `revokeUserSessions` | `session: ["revoke"]`            | `UserSessions` |

`getActiveSessions` liefert die nicht abgelaufenen Sitzungen des aktuellen Benutzers, die neuesten zuerst, und lässt die Sitzungen von Identitätswechseln weg. `listUserSessions` liefert die nicht abgelaufenen Sitzungen eines anderen Benutzers aus `listUserSessions` von Better Auth, die neuesten zuerst und ohne ihre Tokens, die Sitzungen von Identitätswechseln eingeschlossen. `revokeUserSession` nimmt eine Sitzungs-ID entgegen und sucht ihr Token auf dem Server heraus, sodass kein Token den Browser erreicht.

## Benutzeroberfläche

Der Tab **Sicherheit** von `/app/settings` und `/admin/settings` rendert `SessionsCard` (`src/presentation/components/custom/settings/sessions-card.tsx`), mit diesem Browser zuerst. Jede `SessionRow` nennt Browser und System, etwa „Firefox unter Windows“, markiert **Dieses Gerät** und zeigt das Land, die IP-Adresse, wann die Sitzung zuletzt aktiv war und wann sie sich angemeldet hat. Jede andere Zeile hat **Abmelden**, dessen zugänglicher Name das Gerät nennt, und die Karte endet mit **Andere Geräte abmelden**, solange es ein anderes gibt. Wer das Passwort ändert oder festlegt, meldet damit ebenfalls jede andere Sitzung ab, und die Liste wird aktualisiert.

Das Profil eines Benutzers in `/admin/users` rendert `UserSessions` (`src/presentation/components/custom/admin/users/user-sessions.tsx`): für jede Sitzung das Gerät, aus demselben `useSessionDeviceName`, wann die Anmeldung erfolgte und wann sie zuletzt aktiv war, eine Schaltfläche, die sie widerruft, und nach einer Bestätigung eine Schaltfläche, die den Benutzer überall abmeldet. Siehe [Benutzer (Admin)](/docs/features/users-admin).

## Zwischengespeicherte Daten und das angemeldete Konto [#cached-data-and-the-signed-in-account]

Jede Query, die nicht als öffentlich markiert ist, gehört dem Konto, das beim Laden angemeldet war ([Öffentliche Queries](/docs/conventions/data-fetching#public-queries)). `auth.routes.ts` merkt sich dieses Konto für jeden Query-Cache. `getRouter()` reicht jede Änderung des Caches an `recordUserDataOwner` weiter, das das Konto aus der ersten Sitzung übernimmt, die der Cache enthält, ganz gleich, ob der Server sie in die Seite gerendert, ein Routen-Guard sie geladen oder der Header sie abgefragt hat. Jeder Routen-Guard vergleicht die Sitzung, die er lädt, mit diesem Eintrag. Weichen beide voneinander ab, entfernt der Guard mit `removeUserData` die Queries und Mutationen des bisherigen Kontos, speichert die neue Sitzung und merkt sich das neue Konto. Ein nicht angemeldeter Besucher zählt als eigenes Konto. Anmelden, Abmelden und ein Kontowechsel leeren den Cache also jeweils, während eine Prüfung, die dasselbe Konto findet, alles behält, was die Seite geladen hat, etwa eine Lektion, die der Lernende gerade als abgeschlossen markiert hat.

Der Eintrag liegt neben dem Cache und nicht in der Sitzungs-Query. Er nennt deshalb weiterhin das bisherige Konto, wenn eine Komponente die Sitzung erneut abruft und dabei ein anderes Konto findet oder wenn die Sitzungs-Query den Cache verlässt. Der nächste Guard entfernt dann die Daten des bisherigen Kontos.
