Workflows liegen in `.github/workflows/`. Die Anwendungs-Workflows (`ci.yml`, `e2e-reusable.yml` und `deploy-reusable.yml`) richten die Toolchain mit der Composite Action `.github/actions/setup` ein: Bun <RepositoryFact name="bunVersion" />, Vite+ mit der Node-Version aus `.nvmrc`, ein Bun-Cache, `bun install --frozen-lockfile --ignore-scripts` und `bun run typegen`. `remotion.yml` richtet stattdessen Node aus `.nvmrc` und npm ein.

| Workflow              | Auslöser                                                                                       | Jobs                                                                                                    |
| --------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull Requests und Pushes auf `main`                                                            | Prüfungen und Testabdeckung, E2E in Chromium, dann Deployment in Preview oder in Produktion mit Release |
| `e2e-full.yml`        | Pushes auf `main`, nach dem Zeitplan <RepositoryFact name="e2eFullSchedule" /> in UTC, manuell | WebKit bei Push; Chromium und WebKit bei geplanten und manuellen Läufen                                 |
| `e2e-reusable.yml`    | Von den obigen Workflows aufgerufen                                                            | Testdatenbank, Test-Build und ein Playwright-Projekt                                                    |
| `deploy-reusable.yml` | Von `ci.yml` aufgerufen                                                                        | Build, D1-Migrationen und `wrangler deploy`                                                             |
| `remotion.yml`        | Änderungen an `remotion/` oder an den Dateien der Website, die es importiert                   | Prüft und bündelt das Videoprojekt der Landingpage mit npm                                              |

`remotion.yml` reagiert bei Pull Requests und Pushes auf dieselben Pfade: `remotion/`, den Workflow selbst und die Dateien der Website, die `remotion/src` importiert, direkt oder über andere Dateien der Website. `src/__test__/workflows.test.ts` folgt diesen Imports und schlägt fehl, wenn eine erreichte Datei zu keinem der Pfade passt oder ein Pfad zu keiner der Dateien.

Die Checkouts, die die Website bauen, in `e2e-reusable.yml` und `deploy-reusable.yml`, und der Checkout des Jobs `release` holen jeden Commit ohne seine Trees (`fetch-depth: 0` und `filter: tree:0`): Der [Changelog](/docs/project/changelog) datiert jeden Eintrag nach dem Commit, der ihn nach `main` gebracht hat. Gegenüber einem Shallow Clone kommen nur die Commits selbst hinzu; ein Shallow Clone ließe den Build fehlschlagen, statt die Einträge falsch zu datieren. `src/__test__/workflows.test.ts` schlägt fehl, wenn einer dieser Checkouts die Historie nicht mehr holt.

## Prüfungen

Der Job `verify` in `ci.yml` führt `bun run check` (Klassennamen-Tabellen, i18n- und Inhaltsprüfungen, das [Ablaufinventar](/docs/tooling/test-coverage#flow-coverage), Formatierung, Linting und Typen) und `bun run test:coverage` aus und lädt anschließend den Abdeckungsbericht hoch. Der Job `e2e` führt `db:reset:test` und `build:test` aus, installiert den Browser und startet `bunx playwright test e2e/specs --project=chromium`. Bei fehlgeschlagenen E2E-Läufen wird der Playwright-Bericht hochgeladen.

In einem Pull Request schlägt `bun run check` außerdem fehl, bis der Pull Request seinen [Changelog-Eintrag](/docs/conventions/git-workflow#changelog-entries) hinzufügt. Der Build im Job `e2e` und in den Deploy-Jobs schlägt fehl, solange der Changelog einen Eintrag unter **Unveröffentlicht** aufführen würde, der nicht der des Pull Requests selbst ist, und auf `main`, solange er überhaupt einen aufführen würde.

## Deployments

Deployments laufen erst, nachdem `verify` und `e2e` erfolgreich waren:

| Ereignis                                           | Ziel         | GitHub-Umgebung | URL                           |
| -------------------------------------------------- | ------------ | --------------- | ----------------------------- |
| Pull Request von einem Branch in diesem Repository | `preview`    | `Preview`       | https://preview.saasyland.com |
| Push auf `main`                                    | `production` | `Production`    | https://saasyland.com         |

`deploy-reusable.yml` gibt jeder GitHub-Umgebung ihre URL, und `src/__test__/workflows.test.ts` schlägt fehl, wenn eine davon vom Host der Umgebung in `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`) abweicht. Pull Requests aus Forks und von Dependabot werden validiert, aber nicht deployt. Die Preview ist gemeinsam genutzt: Jedes Deployment ersetzt das vorherige und verwendet dieselbe Preview-D1-Datenbank, denselben KV-Namespace und dieselben R2-Buckets.

`deploy-reusable.yml` prüft, ob die Secrets `CLOUDFLARE_API_TOKEN` und `CLOUDFLARE_ACCOUNT_ID` vorhanden sind, führt `scripts/verify-bindings.ts` aus, baut mit den Platzhalterwerten aus `.env.test`, entfernt die erzeugte `dist/server/.dev.vars`, wendet `db:migrate:<target>` an und führt `vp exec wrangler deploy --config dist/server/wrangler.json` aus. `scripts/verify-deployment.ts`, die Prüfung der Live-Website aus den `deploy:<target>`-Skripten, läuft hier nicht, weil der Bot-Schutz von Cloudflare Anfragen von CI-Runnern mit 403 beantwortet. Auch `scripts/run-deploy-checks.ts` läuft hier nicht. CI führt also keinen der Deploy-Checks aus, die die Bereiche in `DEPLOY_CHECKS` deklarieren: In CI gibt es keine `.env.<target>`, und die GitHub-Umgebungen enthalten nur die Cloudflare-Zugangsdaten. Derzeit sind das `auth:verify` aus dem Auth-Bereich und `polar:verify` aus dem Polar-Bereich; führe `bun run auth:verify:<target>` lokal aus, nachdem du einen OAuth-Client geändert hast, und `bun run polar:verify:<target>` nach jeder Änderung in Polar ([Polar-Einrichtung](/docs/getting-started/polar-setup)). Es wird keine Secrets-Datei hochgeladen: Der Worker behält die Laufzeit-Secrets, die bereits in Cloudflare gesetzt sind. Deployments auf dasselbe Ziel werden in eine Warteschlange gestellt, statt sich gegenseitig abzubrechen.

Dependabot aktualisiert die GitHub Actions wöchentlich.

## Releases und Tags [#releases-and-tags]

Die Website wird kontinuierlich deployt, deshalb sind ihre Versionen Datumsangaben statt semantischer Versionen. Wenn ein Deployment in Produktion erfolgreich war, versieht der Job `release` in `ci.yml` den deployten Commit mit dem Tag `vYYYY.MM.DD` nach dem UTC-Datum und veröffentlicht dazu ein GitHub Release. Ein zweites Deployment in Produktion am selben Tag erhält den Tag `vYYYY.MM.DD.2`, das nächste `.3` und so weiter. Preview-Deployments erhalten nie einen Tag. Der Job `release` ist der einzige Job mit `contents: write`.

Die Release Notes sind die Einträge im [Changelog](/docs/project/changelog), die das Release ausgeliefert hat, also die seit dem vorherigen Release-Tag in `main` angekommenen, jeweils mit `(#<number>)` am Ende, das GitHub auf den Pull Request verlinkt, sodass jede Änderung an genau einer Stelle beschrieben ist; hat ein Release keinen ausgeliefert, verlinken seine Notes auf den Changelog. `scripts/publish-release.ts` nimmt die Notes aus `src/lib/release.ts` und führt `gh release create` mit dem Tag aus, den das Deployment gewählt hat. Ein erneuter Lauf behält den Tag, den der Commit bereits hat, und überspringt ein bereits vorhandenes Release.

Der Job des Produktions-Deployments wählt diesen Tag vor dem Build: `scripts/choose-release-tag.ts` wendet `releaseTag` aus `src/lib/release.ts` auf die Tags des Checkouts an, der Build erhält den Tag als `RELEASE_TAG`, und der Job gibt ihn als Output `release-tag` an den Job `release` weiter, sodass Deployment und Release denselben Tag tragen. Damit verlinkt der [Changelog](/docs/project/changelog) jeden Eintrag auf das Release, das ihn als erstes ausgeliefert hat: den frühesten Release-Tag, dessen Commit den Squash-Commit des Eintrags in der First-Parent-Historie von `main` enthält, die der Build zusammen mit den Daten in einem einzigen `git log` liest, oder den eigenen Tag des Deployments für die Einträge, die es mitbringt. Der Job `release` liest den Changelog genauso, mit dem Tag, den er veröffentlicht, sodass die Notes eines Release genau die Einträge sind, die die Seite auf dieses Release verlinkt. Einträge, die vor dem ersten Release-Tag gemergt wurden, verlinken auf kein Release, ebenso in lokalen Builds, Preview-Builds und Builds von Pull Requests die Einträge, die noch kein Deployment ausgeliefert hat. Zwei Produktions-Deployments können nicht denselben Tag wählen: `ci.yml` führt pro Ref jeweils nur einen Workflow-Lauf aus (`concurrency` mit `queue: max`), sodass der Job `release` des vorherigen Laufs seinen Tag erstellt hat, bevor das nächste Deployment das Repository auscheckt.

Um die Produktion auf ein Release zurückzusetzen, mach in einem Pull Request alles nach seinem Tag rückgängig:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Nach dem Merge wird der Code des Tags mit den üblichen Prüfungen deployt und als neues Release getaggt. D1-Migrationen werden nicht zurückgenommen, der ältere Code läuft also auf dem neueren Schema. Jede Schemaänderung muss mit der Anwendung funktionieren, die vor ihr deployt wurde; das macht diesen Weg für das vorherige Release sicher. Lies die Migrationen dazwischen, bevor du weiter zurückgehst.
