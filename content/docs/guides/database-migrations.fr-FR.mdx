---
title: "Migrations de base de données"
description: "Modifiez un schéma Drizzle, générez la migration SQL et appliquez-la à chaque base D1."
---

Cloudflare D1 (SQLite) est la base de données de l'application. Les schémas des modules utilisent `drizzle-orm/sqlite-core`, `src/integrations/drizzle-orm/drizzle.schemas.ts` les rassemble et drizzle-kit écrit les migrations dans `src/integrations/drizzle-orm/migrations/` avec un préfixe d'horodatage.

## Déroulement

1. Modifiez `<table>.schema.ts`. Pour une nouvelle table, exportez-la aussi depuis `drizzle.schemas.ts`.
2. Générez le SQL :

```sh
bun run db:generate
```

3. Relisez le fichier généré et commitez-le avec la modification du schéma.
4. Appliquez-le à la base avec laquelle vous travaillez. `deploy:preview`, `deploy:production` et la CI l'appliquent à la base de l'aperçu ou à celle de production avant de déployer.

## Commandes

| Commande                        | Base de données                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| `bun run db:migrate:local`      | Base de développement locale dans `.wrangler/state`, utilisée par `bun run dev`      |
| `bun run db:reset:local`        | Supprime la base de développement locale, puis la migre à nouveau                    |
| `bun run db:migrate:test`       | Base de test locale dans `.wrangler/test`, utilisée par Playwright et l'aperçu isolé |
| `bun run db:reset:test`         | Supprime `.wrangler/test`, puis migre la base de test locale et y applique le seed   |
| `bun run db:migrate:preview`    | Base distante de l'aperçu                                                            |
| `bun run db:migrate:production` | Base distante de production                                                          |

`bun run db:migrations:local`, `db:migrations:preview` et `db:migrations:production` listent les migrations qu'une base n'a pas encore appliquées. `bun run db:studio:local` ouvre Drizzle Studio sur le fichier de la base locale. `db:studio:preview` et `db:studio:production` l'ouvrent sur une base distante, et les scripts `db:introspect:*` l'inspectent, tous deux via l'API HTTP de D1 avec `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` et `CLOUDFLARE_ACCESS_TOKEN` issus du fichier d'environnement correspondant. Voir [Base de données](/docs/tooling/database).

## Conventions de schéma

- Les dates sont des `integer(..., { mode: "timestamp_ms" })` avec la valeur par défaut `(unixepoch() * 1000)`. Les tables obtiennent `createdAt` et `updatedAt` avec `...timestamps()` de `src/integrations/drizzle-orm/drizzle.columns.ts`.
- Les booléens sont des `integer(..., { mode: "boolean" })`.
- Les index, contraintes d'unicité, clés étrangères et relations restent dans le fichier de schéma.
- D1 n'a pas de transactions interactives. Gardez une opération atomique avec une seule instruction SQL ou `db.batch([...])`, comme le font `getUsers` et le limiteur de requêtes.

## Tests

Le binding D1 de test applique chaque fichier SQL du dossier des migrations à une base SQLite en mémoire : les tests qui utilisent D1 s'exécutent donc contre le schéma migré. `src/integrations/drizzle-orm/__test__/` vérifie que le schéma, ses index et ses clés étrangères se matérialisent. Son `migrations.test.ts` limite la migration qui ajoute les tables `order` et `subscription` à des instructions `CREATE` pour ces tables et leurs index, et vérifie, sur une base migrée jusqu'à la migration qui la précède, que chaque table et chaque index existant auparavant restent tels quels. Il limite la migration qui ajoute les enregistrements de la licence à trois instructions `ALTER TABLE … ADD` de colonnes pouvant être nulles, et vérifie que toutes les autres tables, tous les index et une licence existante restent tels quels, avec les nouvelles colonnes vides. Il limite la migration qui ajoute le contenu des cours à une instruction `CREATE TABLE` et une instruction `CREATE INDEX` pour `lesson_attachment`, suivies uniquement d'instructions `ALTER TABLE … ADD` de colonnes avec une valeur par défaut, et vérifie que toutes les autres tables et tous les autres index, ainsi qu'un cours, un chapitre, une leçon et une vidéo existants, restent tels quels avec les nouvelles colonnes à leur valeur par défaut, et que supprimer une leçon supprime ses ressources. Voir [Écrire des tests](/docs/guides/writing-tests).

## Données PostgreSQL existantes

Ces migrations créent uniquement le schéma SQLite. Transférer les données d'une ancienne installation PostgreSQL exige un export et un import distincts et relus.
