Zahlungen laufen über Polar mit dem Plugin `@polar-sh/better-auth`, das der Polar-Bereich in `src/data/polar.auth-plugins.ts` zu Better Auth hinzufügt:

```ts title="src/data/polar.auth-plugins.ts"
export const POLAR_AUTH_PLUGINS = [
  {
    plugin: polar({
      client: polarCore,
      use: [portal(), webhooks({ onPayload: handlePolarEvent, secret: env.POLAR_WEBHOOK_SECRET })],
    }),
    rateLimitExemptPaths: [ROUTES.API_AUTH_POLAR.WEBHOOKS],
  },
  {
    plugin: {
      hooks: {
        before: [
          {
            handler: requireVerifiedEmail,
            matcher: ({ path }) => path?.startsWith(ROUTES.API_AUTH_POLAR.CUSTOMER) === true,
          },
        ],
      },
      id: "polar-verified-customer",
    },
    rateLimitExemptPaths: [],
  },
] as const satisfies readonly AuthPluginEntry[]
```

Das Plugin fügt das Kundenportal und die Webhooks hinzu, die von der Ratenbegrenzung von Better Auth ausgenommen sind, aber keinen Checkout: Sein `checkout()` würde einen Checkout nur mit der ID des Kontos erstellen, sodass Polar einen angemeldeten Käufer erneut nach seiner E-Mail-Adresse fragen würde. Better Auth sperrt keinen Pfad für HTTP, daher prüft `src/data/__test__/polar.auth-plugins.integration.test.ts`, dass der Checkout-Pfad des Plugins mit 404 antwortet, und schlägt fehl, sobald dem Plugin `checkout()` hinzugefügt wird. Ein Bereich, der verkauft, erstellt seine Checkouts nach seinen eigenen Prüfungen mit dem Polar-SDK, so wie es `startCheckout` im Lizenzbereich tut (siehe [Lizenzen](/docs/features/licences)).

Der zweite Eintrag, `polar-verified-customer`, ist ein eigenes Plugin, das `requireVerifiedEmail` (`auth.hooks.ts`) vor jedem Endpunkt unter `/customer/` ausführt, sodass das Kundenportal mit `403 EMAIL_NOT_VERIFIED` antwortet, bis die Adresse des Kontos bestätigt ist ([E-Mail-Bestätigung](/docs/features/email-verification)).

`src/integrations/polar/polar.config.ts` erstellt aus `POLAR_ACCESS_TOKEN` und `POLAR_SERVER` den Client `polarCore`, den das Plugin verwendet, sowie `polar`, die darauf aufbauenden Dienste für Checkouts, Lizenzschlüssel und Bestellungen. `POLAR_ORGANIZATION_ID` grenzt jeden Polar-Aufruf, der eine Organisation nennt, auf die Organisation ein; [Umgebung und Bindings](/docs/reference/environment) listet sie auf. `src/integrations/polar/polar.constants.ts` enthält die eigenen Werte von Polar: `POLAR_ORDER_STATUS`, `POLAR_SUBSCRIPTION_STATUS`, `POLAR_RECURRING_INTERVAL`, `POLAR_LICENSE_KEY_STATUS` und `POLAR_WEBHOOK_EVENT`, jeweils gegen die Typen des SDK geprüft, `POLAR_CHECKOUT_ID_PLACEHOLDER`, `POLAR_CUSTOMER_SESSION_TOKEN_PARAM` sowie `POLAR_ID_MAX_LENGTH`, die Länge jeder Spalte, die eine Polar-ID enthält. Die Datei liest keine Umgebung, daher importieren auch der Browser und die Browser-Suite sie. Die Pfade des Polar-Bereichs, `API_AUTH_POLAR` und `API_AUTH_CUSTOMER_PORTAL`, liegen in `src/areas/polar.shared.ts`. [Polar-Einrichtung](/docs/getting-started/polar-setup) beschreibt die Produkte, Lizenzschlüssel, die Zustimmungs-Checkbox, das Steuerverhalten, den Webhook und das Token, die dieser Code in Polar erwartet, und `bun run polar:verify:<environment>` prüft sie.

## Webhooks [#webhooks]

Polar sendet die Ereignisse an `/api/auth/polar/webhooks`. Das Plugin verifiziert die Signatur mit `POLAR_WEBHOOK_SECRET` und übergibt jedes Ereignis an `handlePolarEvent` in `src/data/polar-events.ts`. Ein Bereich, der auf Polar-Ereignisse reagiert, deklariert eine Liste in `src/data/<area>.polar-events.ts` und trägt sie in `src/data/polar-events.entries.ts` ein. Jeder Eintrag nennt die Ereignisse, die er verarbeitet, und die Funktion, die sie verarbeitet:

```ts
export interface PolarEventHandler {
  readonly events: readonly models.WebhookEventType[]
  readonly handle: (event: webhooks.WebhookPayload) => Promise<void>
}
```

- `handlePolarEvent` führt das `handle` jedes Eintrags aus, der den Typ des Ereignisses aufführt, alle gleichzeitig, und wartet auf alle.
- Schlägt einer davon fehl, wartet `handlePolarEvent` trotzdem, bis die anderen fertig sind, damit kein Bereich mitten in seinen Schreibvorgängen abbricht, und lehnt dann mit einem `AggregateError` aller Fehler ab. Das Plugin antwortet mit 500, und Polar stellt das Ereignis später erneut zu. Deshalb muss jeder Handler gefahrlos zweimal für dasselbe Ereignis laufen können. Polar deaktiviert einen Endpunkt, der immer wieder fehlschlägt, und `polar:verify` meldet einen deaktivierten Endpunkt.
- Ein Ereignis, das kein Eintrag aufführt, wird bestätigt und geht nirgendwohin.
- `POLAR_EVENTS` führt die Ereignisse aller Einträge zusammen, sortiert und jedes nur einmal. Der Webhook-Endpunkt in Polar muss genau diese senden, und `polar:verify` vergleicht sie.
- Der Polar-Bereich trägt in `src/data/polar.polar-events.ts` eine leere Liste bei, sodass das Barrel nie leer ist. Der Abrechnungsbereich kopiert Bestellungen und Abonnements in `src/data/billing.polar-events.ts` nach D1 (siehe [Die Kopien schreiben](#writing-the-copies)), und der Lizenzbereich vergibt und widerruft Lizenzen in `src/data/license.polar-events.ts` (siehe [Lizenzen](/docs/features/licences#webhooks-and-licences)).

`polar:verify` läuft in Bun, außerhalb des Workers, und liest `POLAR_EVENTS`, daher importieren `src/data/polar-events.ts` und jede `<area>.polar-events.ts` keinen Servercode. Das `handle` eines Bereichs lädt seine Handler erst, wenn ein Ereignis eintrifft:

```ts
const { licenseWebhookHandlers } = await import("~/src/modules/license/license.webhooks")
```

`src/data/__test__/polar-events.test.ts` importiert `src/data/polar-events.ts` in Bun und schlägt fehl, wenn dieser Import die Laufzeit des Workers erreicht.

## Bestellungen und Abonnements in D1 [#orders-and-subscriptions-in-d1]

Der Polar-Bereich hält Kopien der Bestellungen und Abonnements von Polar in zwei D1-Tabellen, `order` (`src/modules/order/`) und `subscription` (`src/modules/subscription/`), damit Listen, Suchen und Zugriffsprüfungen sie mit SQL lesen können und weiter funktionieren, während Polar langsam ist. Polar bleibt die Quelle: Jede Zeile ist der Datensatz von Polar unter der ID von Polar, wird nur aus den Webhooks von Polar geschrieben und nie von Hand bearbeitet. [Module](/docs/conventions/modules#tables-that-mirror-a-provider) nennt die Regeln, denen jede solche Spiegeltabelle folgt.

| Tabelle        | Spalten                                                                                                                                                                                                                                                                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `order`        | `id`, `user_id`, `customer_id`, `product_id`, `subscription_id`, `status` (`ORDER_STATUSES`), `currency`, `total_amount`, `refunded_amount`, `invoice_number`, `discount_id`, `discount_code`, `discount_name`, `discount_amount`, `billing_country`, `description`, `placed_at`, `changed_at`      |
| `subscription` | `id`, `user_id`, `customer_id`, `product_id`, `product_name`, `status` (`SUBSCRIPTION_STATUSES`), `amount`, `currency`, `recurring_interval` (`SUBSCRIPTION_RECURRING_INTERVALS`), `recurring_interval_count`, `current_period_end`, `cancel_at_period_end`, `started_at`, `ended_at`, `changed_at` |

- `id`, `customer_id`, `product_id` und `subscription_id` sind IDs von Polar, und jede von Polar kopierte Spalte trägt den Feldnamen von Polar. `subscription_id` hat keinen Fremdschlüssel, weil die Ereignisse von Polar in beliebiger Reihenfolge eintreffen können.
- `user_id` verknüpft das Konto und bleibt bei einem Kunden ohne Konto leer. Wird ein Konto gelöscht, bleiben seine Bestellungen und Abonnements erhalten, und ihr `user_id` wird geleert (`ON DELETE SET NULL`).
- Beträge stehen in der kleinsten Einheit der Währung, so wie Polar sie sendet. `description` ist das, was mit der Bestellung gekauft wurde, so wie Polar es in Rechnung gestellt hat, und `product_name` der Name des Produkts des Abonnements, so wie Polar ihn zuletzt gemeldet hat.
- `discount_id`, `discount_code` und `discount_name` sind der Rabatt, den Polar angewendet hat, aus `discount_id` und `discount` der Bestellung, und `discount_amount` ist, was er von der Zwischensumme abgezogen hat; `billing_country` ist das Land der Rechnungsadresse der Bestellung als ISO-3166-1-Alpha-2-Code. Sie sind leer bei einer Bestellung ohne Rabatt oder ohne Rechnungsadresse, und `discount_amount` ist nur bei einer Bestellung leer, die kopiert wurde, bevor es diese Spalten gab (siehe [Bestellungen und Kunden](/docs/features/orders#discounts-and-billing-countries-of-older-orders)).
- `placed_at` ist der Zeitpunkt, zu dem Polar die Bestellung angelegt hat. `changed_at` ist die Version des Polar-Datensatzes, die die Zeile enthält: das `modified_at` von Polar oder, bei einem nie geänderten Datensatz, das `created_at` von Polar. Die eigenen Spalten `created_at` und `updated_at` der Zeile halten fest, wann D1 sie geschrieben hat.
- Die Indizes dienen den Listen, für die es diese Kopien gibt: `order_user_placed_at_idx` den Bestellungen eines Kontos und `order_status_placed_at_idx` den Bestellungen mit einem bestimmten Status, beide nach dem Zeitpunkt der Bestellung; `subscription_user_status_idx` den Abonnements eines Kontos nach Status und `subscription_status_current_period_end_idx` den Abonnements mit einem bestimmten Status nach dem Ende ihres Zeitraums.
- `status` enthält den Wert von Polar unverändert, auch `trial_ended`, das Polar setzt, wenn eine Testphase ohne Zahlung endet. Noch gewährt nichts Zugang anhand des Status eines Abonnements; eine Prüfung, die das tut, zählt nur `trialing` und `active` als laufendes Abonnement, sodass `trial_ended`, `past_due` und die übrigen Status nie als eines gelten.

### Die Kopien schreiben [#writing-the-copies]

`src/data/billing.polar-events.ts` fügt den Polar-Ereignissen zwei Einträge hinzu (siehe [Webhooks](#webhooks)), und jeder lädt seinen Use Case, wenn ein Ereignis eintrifft:

| Ereignisse                                                       | Use Case                                                                            |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `order.created`, `order.updated`, `order.paid`, `order.refunded` | `recordOrder` in `src/modules/order/use-cases/record-order.ts`                      |
| `subscription.created`, `subscription.updated`                   | `recordSubscription` in `src/modules/subscription/use-cases/record-subscription.ts` |

- Jeder Use Case nimmt den Datensatz von Polar, `models.Order` oder `models.Subscription`, und schreibt ihn in einer einzigen Anweisung: einem Insert unter der ID von Polar, der eine bereits vorhandene Zeile nur dann aktualisiert, wenn ihr gespeichertes `changed_at` nicht später liegt als das des Datensatzes. Eine neuere Version wird übernommen, eine ältere, die verspätet eintrifft, ändert nichts, und dieselbe Version wird, zweimal zugestellt, mit denselben Werten erneut geschrieben. Von zwei verschiedenen Zuständen mit demselben `modified_at` bleibt der zuletzt geschriebene, bis Polar den Datensatz erneut ändert.
- `recordOrder` übernimmt Rabatt und Rechnungsland aus `polarOrderTerms` (`src/modules/order/order.polar.ts`), das auch `scripts/backfill-order-terms.ts` verwendet. Eine spätere Version ohne Rechnungsadresse behält das bereits kopierte Land.
- Dieselbe Anweisung füllt `user_id` über `polarCustomerAccount` in `src/integrations/polar/polar.customers.ts`: das Konto, dessen ID die `external_id` des Kunden ist, die der verkaufende Bereich beim Checkout setzt, so wie es `startCheckout` im Lizenzbereich tut. Sie bleibt leer, wenn der Kunde keine `external_id` hat oder kein Konto diese ID trägt, etwa weil das Konto gelöscht wurde.
- Auch der Lizenzbereich verarbeitet `order.paid` und `order.refunded`. Die Kopie übernimmt sie ebenfalls und hält so die Zahlung und die Rückerstattung fest, ob Polar dafür zusätzlich `order.updated` sendet oder nicht. `handlePolarEvent` führt beide Bereiche gleichzeitig aus; schlägt die Kopie fehl, antwortet die Zustellung mit 500, und der erneute Versuch von Polar wiederholt beide Schreibvorgänge, ohne zu ändern, was einer von ihnen bereits geschrieben hat.
- Das Admin-Dashboard liest die Kopien der Bestellungen, um die bezahlten Lizenzbestellungen ohne Lizenz aufzulisten (siehe [Lizenzen](/docs/features/licences#orders-that-match-no-account)) und den Umsatz zu summieren (siehe [Umsatz im Dashboard](#revenue-on-the-dashboard)); die Kopien der Abonnements liest noch keine Seite.

## Kundenportal

`ROUTES.API_AUTH_CUSTOMER_PORTAL` (`/api/auth/customer/portal`) öffnet das Polar-Kundenportal des angemeldeten Kontos. Die Lizenzkarte auf `/app/license` verlinkt darauf.

## Umsatz im Dashboard [#revenue-on-the-dashboard]

Der Zahlungsbereich deklariert die Berechtigungs-Statements für `order` (`read`, `update`, `refund`) in `src/data/payments.access.ts` und fügt dem Dashboard in `src/data/payments.dashboard.ts` das Panel **Umsatz** hinzu. Seine Query, `getRevenue` in `src/modules/order/use-cases/get-revenue.ts`, prüft `order: ["read"]` und summiert die Kopien der bezahlten Bestellungen eines Zeitraums pro Währung, abzüglich der Erstattungen; [Admin-Dashboard](/docs/features/admin-dashboard#revenue) beschreibt, was sie zählt. `get-unlicensed-orders` im Lizenzbereich prüft ebenfalls `order: ["read"]`. [Bestellungen und Kunden](/docs/features/orders) beschreibt die Admin-Ansichten, die die Kopien lesen. Noch aktualisiert oder erstattet kein Anwendungsfall Bestellungen: Erstattungen und Auszahlungen werden in Polar erledigt.
