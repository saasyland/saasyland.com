## Módulos

Um módulo em `src/modules/<table>` existe apenas para uma tabela real do banco de dados. Ele contém:

- `<table>.schema.ts`: a tabela Drizzle, reexportada por `src/integrations/drizzle-orm/drizzle.schemas.ts`
- `<table>.zod.ts`: os schemas de entrada, usados tanto pelos formulários quanto pelas funções de servidor
- `<table>.constants.ts`: valores de domínio nomeados como `COURSE_STATUS`, limites de colunas, chaves de query e de mutation
- `<table>.types.ts`: uma interface com o nome do módulo, com os tipos de linha e o tipo de entrada de cada operação, como `Course["createCourse"]`
- `<table>.utils.ts`: quando a tabela precisa deles
- `use-cases/<operation>.ts`: uma operação por arquivo

Os módulos são <RepositoryFact name="modules" />. `license` é dono de duas tabelas, `license` e `revoked_license_order`. Constantes e helpers compartilhados ficam em [`_core`](/docs/architecture/core). Uma função de servidor que não trabalha com uma tabela pertence a `src/lib` ou à única rota que a usa.

## Casos de uso

A maioria dos casos de uso são funções de servidor chamadas pelo navegador. Cada arquivo exporta o `createServerFn` e as respectivas query ou mutation options:

```ts title="src/modules/course/use-cases/create-course.ts"
import { mutationOptions } from "@tanstack/react-query"
import { createServerFn } from "@tanstack/react-start"
import { v7 } from "uuid"

import { authorized } from "~/src/integrations/better-auth/auth.middleware"
import { db } from "~/src/integrations/drizzle-orm/drizzle.database"
import { rethrowAsConflict } from "~/src/integrations/drizzle-orm/drizzle.errors"

import { nextPosition } from "~/src/modules/_core/utils/ordering"
import { COURSE_MUTATION_KEYS } from "~/src/modules/course/course.constants"
import { course } from "~/src/modules/course/course.schema"
import type { Course } from "~/src/modules/course/course.types"
import { courseZodSchemas } from "~/src/modules/course/course.zod"

export const createCourse = createServerFn({ method: "POST" })
  .middleware([authorized({ course: ["create"] })])
  .validator((input: Course["createCourse"]) => courseZodSchemas.createCourse.parse(input))
  .handler(async ({ data }) => {
    const positions = await db.select({ position: course.position }).from(course)

    return db
      .insert(course)
      .values({ ...data, id: v7(), position: nextPosition(positions) })
      .returning({ id: course.id })
      .get()
      .catch(rethrowAsConflict)
  })

export const createCourseMutation = mutationOptions({
  mutationFn: (data: Course["createCourse"]) => createCourse({ data }),
  mutationKey: COURSE_MUTATION_KEYS.CREATE,
})
```

- **O middleware** vem de `src/integrations/better-auth/auth.middleware.ts`. `authorized()` exige uma sessão, `authorized({ course: ["create"] })` também verifica uma permissão e `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` limita as operações públicas.
- **A validação** analisa a entrada com o schema Zod do módulo antes de o handler rodar.
- **A titularidade** vem da sessão. Operações sobre os dados do próprio chamador filtram por `context.auth.user.id` e nunca confiam em um ID de usuário vindo da entrada.
- **Os erros** são lançados como `new AppError(ERROR_CODES.X)`. `rethrowAsConflict` transforma um erro de restrição de unicidade, como o slug de um curso que já está em uso, em `CONFLICT`. `withRequest` transforma um erro de API do Better Auth em `AUTH_API_ERROR`, com a chave de mensagem do erro, e um erro do Zod em `VALIDATION`; qualquer outro erro é registrado em log e chega ao cliente como `INTERNAL_ERROR`.
- **As leituras** exportam `queryOptions` no lugar, por exemplo `getCoursesPageQuery(input)`, que resolve `{ rows, total }` para a tabela de dados.

Alguns casos de uso são funções assíncronas comuns que rodam apenas no servidor e não têm endpoint RPC, como `send-verify-email.ts` ou `grant-license.ts`. Quem os chama são os hooks do Better Auth e os handlers de webhooks da Polar.

## Chamando um caso de uso a partir de um componente

Os componentes passam as options exportadas para `useMutation` com spread, traduzem os erros com `useErrorMessage()` e invalidam as chaves de query do módulo em caso de sucesso:

```tsx
const t = useTranslations("pages.admin.users.actions")
const queryClient = useQueryClient()
const errorMessage = useErrorMessage()

const deleteUser = useMutation({
  ...deleteUserMutation,
  onError: (error) => {
    toast.error(errorMessage(error))
  },
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: USER_QUERY_KEYS.ALL })
    toast.success(t("feedback.deleteSuccess"))
  },
})
```
