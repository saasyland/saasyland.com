Vite+ esegue Vitest (`vp test`) in tre progetti. I test si trovano in una cartella `__test__` accanto al codice che coprono e importano le API da `vite-plus/test`.

| Progetto      | File                             | Ambiente |
| ------------- | -------------------------------- | -------- |
| `node`        | `__test__/*.test.ts(x)`          | Node     |
| `integration` | `__test__/*.integration.test.ts` | Node     |
| `component`   | `__test__/*.component.test.tsx`  | jsdom    |

Dai a ogni test il nome del suo file sorgente: `category.zod.ts` è coperto da `__test__/category.zod.test.ts`.

## Comandi

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
```

Usa `bun run test` e non `bun test`: solo Vitest carica i progetti, gli ambienti e il file di configurazione.

## Soglia di copertura

`bun run test:coverage` fallisce quando la copertura di righe, istruzioni, funzioni e rami del codice applicativo in `src` è inferiore a **<RepositoryFact name="coverageThreshold" unit="percent" />**. Sono esclusi i test, `src/platform/testing`, le primitive shadcn e i file generati. Copri il comportamento reale ed elimina i rami che non possono mai essere eseguiti invece di sostituire variabili globali per raggiungerli. I report vengono scritti in `coverage/`.

## Ambiente di test

- `src/platform/testing/setup.ts` registra i matcher di jest-dom, reimposta i binding prima di ogni test e fa passare ogni `createServerFn` attraverso `withTestRpc`, così le chiamate eseguono il vero middleware e il vero validatore. Questo vale per i progetti `node` e `integration`. Nel progetto `component` una funzione server fallisce, perché jsdom è il browser.
- `cloudflare:workers` punta a `src/platform/testing/mocks/cloudflare.ts`. D1 è un database SQLite in memoria con tutte le migrazioni del repository applicate, KV e il bucket R2 `MEDIA` sono mappe in memoria e `flushWaitUntil()` attende le attività in background. `createEdgeCache()` di `mocks/cache.ts` fa da stub della cache di Workers.
- `.env.test` fornisce credenziali fittizie. `fetch` raggiunge test double rigorosi di Resend e Polar (`mocks/resend.ts`, `mocks/polar.ts`) e qualsiasi altro host fallisce come se la macchina fosse offline, quindi nulla la lascia. Una richiesta che il provider rifiuterebbe fa fallire il test.
- `renderWithRouter` di `src/platform/testing/lib/render.tsx` mostra i componenti con un vero router e un vero `QueryClient`.

## Testa un caso d'uso

Versione ridotta di `src/modules/category/use-cases/__test__/create-category.test.ts`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"

import { executeMutation } from "~/src/platform/testing/lib/query"

import { createAuthSessionFixture } from "~/src/integrations/better-auth/__test__/fixtures/auth.session.fixture"
import { ROLE_CODES } from "~/src/integrations/better-auth/auth.access"
import type { auth } from "~/src/integrations/better-auth/auth.server"
import * as authServer from "~/src/integrations/better-auth/auth.server"

import { ERROR_CODES } from "~/src/modules/_core/constants/errors"
import { CATEGORY_KIND } from "~/src/modules/category/category.constants"
import { createCategoryMutation } from "~/src/modules/category/use-cases/create-category"

const getSessionMock = vi.hoisted(() => vi.fn<(typeof auth.api)["getSession"]>())

vi.mock(import("@tanstack/react-start/server-only"), () => ({}))

describe("create-category", () => {
  it("returns a domain error when the caller is not an admin", async () => {
    vi.spyOn(authServer.auth.api, "getSession").mockImplementation(getSessionMock)
    getSessionMock.mockResolvedValue(
      createAuthSessionFixture({ role: ROLE_CODES.CUSTOMER, userId: "01900000-0000-7000-8000-000000000001" }),
    )

    await expect(executeMutation(createCategoryMutation, { kind: CATEGORY_KIND.CATEGORY, name: "SaaS Plans" })).rejects.toThrow(
      ERROR_CODES.FORBIDDEN,
    )
  })
})
```

Testa ogni esito di un caso d'uso: successo, ogni codice di `AppError`, sessione mancante e permesso mancante. I valori di dominio e i codici di errore provengono dalle loro costanti (`CATEGORY_KIND`, `ERROR_CODES`), mai da stringhe ripetute.

## Testa con Resend e Polar

Non simulare l'SDK di Resend o di Polar. Chiama il codice che invia la richiesta e verifica ciò che ha ricevuto il test double. `getSentEmails(recipient)` di `mocks/resend.ts` restituisce le email consegnate con il loro HTML renderizzato e la loro chiave di idempotenza; `mocks/polar.ts` conserva checkout, ordini e chiavi di licenza, e le sue funzioni fanno avanzare un acquisto: `payPolarCheckout`, `grantPolarLicenseKey`, `refundPolarOrder`, `revokePolarLicenseKey` e `activatePolarLicenseKey`. Versione ridotta di `src/modules/license/__test__/license-purchase.integration.test.ts`:

```ts
const buyer = await signUpAndVerify()
const order = await paidOrder(buyer, LICENSE_TIER.COMPLETE)

expect(await deliver(LICENSE_WEBHOOK_EVENTS.onOrderPaid, order)).toBe(HTTP_STATUS.OK)
expect(await currentLicense(buyer)).toMatchObject({ status: LICENSE_STATUS.ACTIVE, tier: LICENSE_TIER.COMPLETE })
```

`paidOrder` avvia il checkout tramite il vero `startCheckout` e lo paga nel test double. `deliver` firma l'evento con `signedPolarWebhook` di `lib/polar.ts`, lo invia con una POST all'endpoint Polar di Better Auth e restituisce lo stato della risposta, così vengono eseguiti la verifica della firma, il plugin e gli handler in `license.webhooks.ts`. Per testare come l'applicazione gestisce un errore del provider, rispondi a una singola richiesta con l'errore del provider, come fa `resend.utils.test.ts`: `vi.spyOn(globalThis, "fetch").mockResolvedValueOnce(Response.json(error, { status }))`.

## Testa un flusso di autenticazione

Le suite di autenticazione vengono eseguite sul vero `auth` di `auth.server.ts`. `src/integrations/better-auth/__test__/fixtures/auth.harness.ts` crea gli account come fa un visitatore: `signUp`, `verifyEmail` (che segue il token nell'email consegnata e restituisce la sessione che apre), `signIn` e `signUpAndVerify`. `browserHeaders()` dà a ogni richiesta il proprio `CF-Connecting-IP`, così i rate limit di Better Auth si applicano come in produzione senza che un test esaurisca la quota di un altro. Attendi `flushWaitUntil()` prima di leggere un'email che Better Auth invia in background.

## Testa un componente

I test dei componenti usano i messaggi reali di `messages/en-US`, simulano il modulo del caso d'uso che fornisce le opzioni di mutation e pilotano l'interfaccia con Testing Library e `userEvent`. Per gli stati di attesa, tieni aperta la richiesta simulata con `Promise.withResolvers()`, verifica l'interfaccia in attesa, poi risolvila dentro `act` e verifica l'interfaccia a riposo. Un componente che cambia dopo un ritardo si testa con i fake timer (`vi.useFakeTimers()`, poi `vi.advanceTimersByTimeAsync` dentro `act`), mai aspettando il tempo reale, e il `QueryClient` di un test di route mantiene freschi i dati recuperati dal suo loader (`staleTime: Infinity`), così la velocità di rendering della macchina non cambia mai quante volte viene eseguita una query. `userEvent.setup({ delay: null })` pilota l'interfaccia senza un timer reale tra una battuta e l'altra. `src/presentation/components/custom/__test__/newsletter-form.component.test.tsx` è un esempio completo. Un test di route fornisce alla route i dati del loader, e un test `node` copre il loader tramite `getRouter()`: `src/routes/__test__/marketing-routes.component.test.tsx` e `marketing-loaders.test.ts` sono le due metà.

## Test nel browser

Le specifiche Playwright si trovano in `e2e/specs`, con i page object in `e2e/pages` e le fixture in `e2e/fixtures`. Vengono eseguite sull'applicazione di test compilata, con D1, KV e R2 locali in `.wrangler/test` e gli account di prova di `e2e/data/accounts.ts`. In locale, Playwright esegue da solo migrazione, popolamento, build e avvio di questa applicazione.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:ui
```

Il Worker di test installa gli stessi test double di Resend e Polar e registra le email inviate, così una specifica può leggere il link di verifica da `/__test/emails?to=<address>`. `deliverPaidOrder` in `e2e/fixtures/polar.ts` invia un evento `order.paid` completo, firmato come gli eventi delle suite di integrazione.

## Prima del push

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`build:test` esegue la build Cloudflare completa, che i test unitari non coprono, e `test:e2e:pr` esegue ogni specifica su Chromium, come fa la CI delle pull request.

La CI esegue i controlli, la copertura e la suite browser su Chromium a ogni pull request e a ogni push su `main`, e WebKit ogni settimana e a ogni push su `main`.
