## Worker and bindings

`wrangler.jsonc` sets `src/server.ts` as the Worker entry. The Worker receives these bindings:

| Binding   | Type          | Used for                                                              |
| --------- | ------------- | --------------------------------------------------------------------- |
| `DB`      | D1 database   | All tables, including sessions and rate-limit counters                |
| `CACHE`   | KV namespace  | The GitHub star count and the regional checkout discounts             |
| `MEDIA`   | R2 bucket     | Video files, served by `serveMedia` under `/media/`                   |
| `BUNDLES` | R2 bucket     | The CLI's template bundles, served by `serveBundle` under `/bundles/` |
| `ASSETS`  | Static assets | Prerendered pages and files from `public`                             |

Requests for `/assets/*`, `/fonts/*`, `/robots.txt` and `/llms.txt` are served from static assets without running the Worker. Server code reads bindings, secrets and `waitUntil` from `cloudflare:workers`. `src/server.ts` adds the security headers to every response it returns; files served without the Worker get the subset in `public/_headers` ([Security and hardening](/docs/features/security)).

## What the areas add

No platform file names an area. Each area, such as the courses or the licence sales, adds what it needs to the Worker, the root route, the Vite build and the deploy in files of its own, and a barrel joins them, as the paths and menus are joined (see [Paths and navigation](/docs/conventions/routes#paths-and-navigation)):

| What             | Each area declares                                             | Barrel                          | Used by                                                                                                  |
| ---------------- | -------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Worker handlers  | `src/data/<area>.worker.ts`: one `<AREA>_WORKER_HANDLERS` list | `src/data/worker.entries.ts`    | `DOCUMENT_HANDLERS` and `REQUEST_HANDLERS` in `src/data/worker.ts`, which `src/server.ts` runs           |
| Root components  | `src/data/<area>.root.ts`: one `<AREA>_ROOT_COMPONENTS` list   | `src/data/root.entries.ts`      | `ROOT_COMPONENTS` in `src/data/root.ts`, which `src/routes/__root.tsx` mounts beside the outlet          |
| Time zone        | `src/data/<area>.time-zone.ts`: one `<AREA>_TIME_ZONES` list   | `src/data/time-zone.entries.ts` | `TIME_ZONE_SOURCES` in `src/data/time-zone.ts`, whose first zone `TranslationsProvider` formats dates in |
| Vite plugins     | `src/data/<area>.vite.ts`: one `<AREA>_VITE_PLUGINS` list      | `src/data/vite.entries.ts`      | `vitePlugins` in `src/data/vite.ts`, which `vite.config.ts` loads                                        |
| Deploy checks    | `src/data/<area>.deploy.ts`: one `<AREA>_DEPLOY_CHECKS` list   | `src/data/deploy.entries.ts`    | `DEPLOY_CHECKS` in `src/data/deploy.ts`, which `scripts/run-deploy-checks.ts` runs                       |
| Live site checks | `src/data/<area>.live.ts`: one `<AREA>_LIVE_CHECKS` list       | `src/data/live.entries.ts`      | `LIVE_SITE_CHECKS` in `src/data/live.ts`, which `scripts/verify-deployment.ts` requests after a deploy   |

A request handler claims a `pathPrefix` and answers every request under it before the locale middleware, the static assets and TanStack Start, as the courses area's handler does for `/media/` and the licence area's for `/bundles/`. A document handler receives every HTML page the Worker returns, with its locale and the request, and returns the page to send, as the licence area's regional pricing does. `src/server.ts` imports the handlers statically, so they are evaluated on every cold start: a handler file imports only constants and pure helpers and loads anything larger with a dynamic `import()` (see [Performance](/docs/conventions/performance)).

A Vite plugin entry has an `order`, which places its plugins among those of the other areas, and `vitest`, which says whether they also load under Vitest. Vite loads its configuration before the `~` alias resolves, so `vite.ts`, `vite.entries.ts` and every `<area>.vite.ts` import by relative path with the `.ts` extension, and an entry imports its plugin package inside its `plugins` function, so that `vp lint` and `vp fmt` never load it.

A time zone source is a hook that returns the zone to format dates in. The auth area's returns the signed-in user's zone from the session that the route guards loaded, or `UTC`; without a source, `TranslationsProvider` uses `UTC` as well.

A deploy check names a package script with one variant per deployed environment. The auth area declares `auth:verify` and the Polar area `polar:verify`, so `bun scripts/run-deploy-checks.ts preview` runs `bun run auth:verify:preview` and `bun run polar:verify:preview`. No area declares a check for an empty or placeholder secret: `scripts/prepare-deploy-secrets.ts` runs before the deploy checks and refuses one among all the secrets that `wrangler.jsonc` declares.

A live site check names a path and the status and content type it must answer with after a deploy. The core checks the home page, `robots.txt`, the sitemap, the site card and `/api`, the auth area the session endpoint, and the courses area `/courses`, which renders from D1 on every request. A check with a `post` sends its JSON body from the site's own origin instead and hands the JSON answer to `findProblems`: the auth area starts the sign-in with every provider in `OAUTH_PROVIDERS` this way and refuses an authorize URL that is not on the provider's host, carries a `client_id` in another format or has a `redirect_uri` that does not return to the deployed domain ([OAuth providers](/docs/features/oauth)).

An area can also define a list of its own that other areas add to in the same way. The courses area defines course access in `src/data/course-access.ts`, and the licence area grants it in `src/data/license.course-access.ts` ([Courses](/docs/features/courses)); the licence area defines the sections of its offer in `src/data/license-offer.ts`, and the courses area adds the locked courses in `src/data/courses.license-offer.ts` ([Customer app](/docs/features/customer-app)). The auth area defines the plugins and emails that other areas add to Better Auth ([Better Auth](/docs/integrations/better-auth)): the polar area adds the Polar plugin and Resend the auth emails. The polar area defines the Polar webhook events in `src/data/polar-events.ts`, and the licence area and the billing area add the events they handle in `src/data/license.polar-events.ts` and `src/data/billing.polar-events.ts` ([Payments](/docs/features/payments)). The auth area also defines the user management tabs in `src/data/user-tabs.ts`, which hold its own **All users** tab today ([Users (admin)](/docs/features/users-admin)), and the notices under the sign-up form in `src/data/sign-up-notices.ts`, to which the legal area adds the consent line ([Legal pages](/docs/features/legal-pages)), the customer app's overview in `src/data/app-overview.ts`, to which the licence area adds its section and the search params it reads ([Customer app](/docs/features/customer-app)), and the cards of a user's profile in the admin in `src/data/user-profile.ts`, to which the licence area adds the licence ([Users (admin)](/docs/features/users-admin)). A project without one of the areas leaves out the list that area defines together with what the others add to it, so no area imports another that does not depend on it.

The core adds an empty list to each barrel that only optional areas fill: `src/data/core.worker.ts`, `core.root.ts`, `core.time-zone.ts`, `core.deploy.ts` and `core.namespaces.ts`, so a project without those areas still type-checks and lints, and the auth area adds an empty `AUTH_AUTH_PLUGINS` to its plugin list, an empty `AUTH_SIGN_UP_NOTICES` to its sign-up notices, an empty `AUTH_APP_OVERVIEW` to the overview and an empty `AUTH_USER_PROFILE` to the user profile, and the polar area an empty `POLAR_POLAR_EVENTS` to its webhook events. The areas that send email name the purposes of their emails in `src/data/<area>.email-purposes.ts`, which `src/data/email-purposes.entries.ts` joins into `EMAIL_PURPOSE` ([Resend](/docs/integrations/resend)).

## Environments

`wrangler.jsonc` defines four environments. `CLOUDFLARE_ENV` selects one for `vp dev` and `vp build`.

| Environment   | Bindings                                 | Used by                                         |
| ------------- | ---------------------------------------- | ----------------------------------------------- |
| `development` | Local D1, KV and R2 in `.wrangler/state` | `bun run dev`                                   |
| `preview`     | Preview D1, KV and R2                    | `bun run build:preview`, `deploy:preview`       |
| `production`  | Production D1, KV and R2                 | `bun run build:production`, `deploy:production` |
| `test`        | Local D1, KV and R2 in `.wrangler/test`  | `bun run build:test`, Playwright                |

Each environment lists its required secrets under `secrets.required`. Values come from the matching `.env.<environment>` file; the deploy scripts refuse an empty or placeholder value and write the declared keys to `.wrangler/secrets.<environment>.json` and pass that file to Wrangler with `--secrets-file`. The `test` environment uses `src/platform/testing/worker.ts` as its entry and the committed dummy values in `.env.test`. `AFFONSO_PROGRAM_ID` is public, so it is a plain Worker variable under `vars` rather than a secret; `production` sets SaaSy Land's own programme ID and `test` a dummy one. The secrets of one module stay together, in the order of `.env.example`, and of `.env.test` for `test`, so an area contributes its secrets as one group; `src/__test__/wrangler.test.ts` compares the names in order and fails when they differ. A blank line between two groups is only for reading, since a formatter may remove it, so the test ignores it.

An area's bindings form a block of their own as well. The R2 buckets belong to areas, `MEDIA` to the courses and `BUNDLES` to the licence sales, so `r2_buckets` comes last in each environment, with one entry per area, and a project without an area leaves its entry out. `wrangler.test.ts` also fails when an environment binds other D1 databases, KV namespaces or R2 buckets than `development`, when a `development` binding is remote, and when `development` shares a resource with `preview` or `production`, and `scripts/verify-bindings.ts` checks every binding the target environment declares without naming any.

## Types

- `src/types/worker-configuration.d.ts` is generated by `bun run cf-typegen` from the `development` environment of `wrangler.jsonc` and declares `Cloudflare.Env`: the `DB`, `CACHE`, `MEDIA` and `BUNDLES` bindings and every secret in `secrets.required`. `src/types/bindings.d.ts` adds `ASSETS`, which Wrangler leaves out.
- An area declares in `src/types/<area>.d.ts` only what Wrangler cannot derive: `affiliates.d.ts` the optional `AFFONSO_PROGRAM_ID` variable, which only `production` and `test` set, `polar.d.ts` the two values of `POLAR_SERVER`, and `repository-facts.d.ts` the `virtual:repository-facts` module.
- `src/types/router.d.ts` registers the router type and the `staticData.namespaces` route option.

## Test runtime wiring

`src/platform/testing` holds only what cannot belong to one feature:

- `setup.ts`: jest-dom matchers, a binding reset before each test, and the `createServerFn` replacement that runs server functions in-process
- `mocks/cloudflare.ts`: an in-memory SQLite D1 that runs the checked-in migrations, an in-memory KV, an in-memory bucket for each R2 binding of the `test` environment in `wrangler.jsonc` and a `waitUntil` that tests can flush
- `mocks/cache.ts`: `createEdgeCache`, a stub of the Workers cache for the media delivery tests
- `mocks/resend.ts` and `mocks/polar.ts`: strict doubles of the Resend and Polar APIs, each in a list of its area's doubles (`RESEND_PROVIDER_DOUBLES`, `POLAR_PROVIDER_DOUBLES`) that `mocks/providers.entries.ts` joins with the core's empty `CORE_PROVIDER_DOUBLES`, and `mocks/providers.ts`, which routes `fetch` to them and resets them in every test and in the browser test Worker
- `mocks/wrksz-themes.ts`: a replacement for the theme library
- `lib/`: the server-function RPC bridge, render helpers, request URL helpers, query runners, and Polar models with signed webhooks
- `worker.ts`: the Worker entry for browser tests, which installs the provider doubles and runs the set-up and test endpoints the areas declare in `e2e/data/<area>.worker.ts` (`worker.entries.ts`): the licence area seeds the test licence key in the Polar double, Resend exposes the delivered email and the newsletter a subscriber's state

See [Testing and CI](/docs/architecture/testing-architecture) for how the suites use them.
