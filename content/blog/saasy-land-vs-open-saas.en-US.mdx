## What Open SaaS does well

Open SaaS is the free SaaS starter most developers have already heard of, and it earns that.

**It is free and popular.** It is MIT licensed, and its repository had **16,427 stars** on GitHub on 25 November 2026. A large community has used it, so most questions you will have are already answered in its issues or on Wasp’s Discord.

**It ships more features today.** Email sign-in with verification, with Google, GitHub and Discord ready to switch on. Background and cron jobs, through Wasp’s jobs on PgBoss. File uploads to AWS S3. An admin dashboard with analytics from Plausible or Google Analytics. An OpenAI demo app. A docs site and a blog on Astro Starlight. Payments with Stripe, Lemon Squeezy, Polar or Paddle, chosen in one file.

**It deploys in one command.** `wasp deploy` puts the database, the server and the client on Fly.io or Railway, there is a one-click Railway template, and you can deploy by hand to any other host.

**It speaks to coding agents.** The template has an `AGENTS.md` and a `CLAUDE.md`, agent skills in `.agents` and `.claude`, LLM-friendly docs through `llms.txt`, and the repository describes a Claude Code plugin.

**Wasp does a lot of work for you.** Its README describes it as a framework that "abstracts away complex full-stack features like auth, background jobs, RPC, email sending, end-to-end type safety, single-command deployment, and more". If you want those decisions made and maintained by someone else, that is exactly what you are getting.

If your question is "what is the fastest free way to a working SaaS with payments, jobs and uploads", Open SaaS is a very good answer, and you should not feel you need anything else.

## The real difference: a framework underneath, or none

Both products give you React code you can read and change. The difference is what that code stands on.

**Open SaaS stands on Wasp.** You declare your app in `main.wasp.ts`: its routes, its auth methods, its jobs, its email sender, its operations. The Wasp CLI reads that declaration and builds and runs the app, with React in the browser and Node.js and Prisma on the server. That is how Open SaaS gets auth, jobs and one-command deploys in so few lines. It also means your app depends on Wasp: on its release cadence, on its upgrades between versions, and on its CLI. Open SaaS’s own tests guide asks you to set `WASP_VERSION` in CI to match the version your project uses. Wasp’s README says it is in beta, "with most features fully developed and functioning well".

None of that is a flaw. It is a trade, and for many projects a good one: you give up some control over the plumbing and get a lot of plumbing for free.

**SaaSy Land stands on nothing of its own.** The CLI writes ordinary code for the stack you chose: today TanStack Start, React and Vite+, Better Auth, Drizzle with Cloudflare D1, Resend and use-intl. There is no SaaSy Land runtime, no SaaSy Land package your app imports and no configuration language of ours to learn. Delete the CLI the day after you generate, and the project still installs, builds, tests and deploys, because every line of it is yours.

The cost of that choice is also real. Whatever Wasp would have written for you, the CLI must write into your project as code you then own: today that is auth, email, the admin console, docs and a blog, the tests and the CI workflow, but not yet billing, jobs or uploads. And "the stack you choose" is, today, one stack. The [roadmap](/docs/project/roadmap) lists the rest in the order they arrive: Polar billing and Plunk email, Stripe, your own server with Docker, Prisma, a split API, realtime and MongoDB, then Postgres, Vercel, Next.js, React Router, Solid, Vue with Nuxt, Svelte with SvelteKit, and Angular with Analog or Angular SSR. Each option is enabled only when a project generated with it installs, type-checks, passes its tests, builds and starts in CI.

## What each one gives your coding agent

Most new code in a SaaS today is written by an agent, so this is the question that decides the most hours.

Open SaaS gives an agent **context**. Its `AGENTS.md` tells the agent to read the Open SaaS and Wasp documentation through their `llms.txt` indexes before it starts, the template carries agent skills such as a guided tour, and Wasp’s single config file gives the agent an overview of the whole app in one place. That makes an agent faster at writing Wasp code that looks right.

SaaSy Land gives an agent **consequences**. A generated project has an `AGENTS.md` and a README that describe the stack you chose, and a CI workflow that runs the check and the tests with coverage, then the browser suite, on every pull request. This site, the reference the templates are cut from, fails the merge below <RepositoryFact name="coverageThreshold" />% coverage of statements, branches, functions and lines across <RepositoryFact name="testFiles" /> test files, runs <RepositoryFact name="e2eTests" /> browser tests, refuses an `any` or a disabled lint rule, and fails CI when a translation is missing in any of its <RepositoryFact name="languages" /> languages.

Instructions and checks are not rivals; both repositories have instructions. The difference shows on the day the agent ignores them. An instruction an agent skipped is found by a reviewer, or by a customer. A check an agent broke is found by the pull request, before anything merges. We wrote about that difference in [the guardrails that make a wrong change fail](/blog/ai-coding-agent-guardrails).

## Tests

Open SaaS includes Playwright end-to-end tests in its `e2e-tests` directory, four spec files on 25 November 2026, covering the landing page, the pricing page, the auth redirects and the demo app. Its repository runs them on every pull request, and its tests guide explains how to copy that workflow into your own project, because the template does not come with one.

That is a sensible starting point, and more than many paid starters ship. It is a different claim from a coverage gate. An end-to-end suite proves that the paths someone wrote a test for work today. A coverage gate refuses to merge a branch that no test runs, which is where error handling, webhook signatures and permission checks hide. For a human who tests by hand before every release, the difference is small. For an agent opening ten pull requests a day, it is most of the difference.

## Payments, and the Lemon Squeezy question

Open SaaS supports four payment providers: Stripe, Lemon Squeezy, Polar and Paddle. You pick one in `src/payment/paymentProcessor.ts` and its client counterpart, then delete the other providers’ folders, environment variables and packages, as its payments guide describes. Three of the four are merchants of record, which handle sales tax for you.

One of them is closing. Lemon Squeezy closed new store sign-ups on 16 November 2026 and stops processing payments on 31 March 2027; its announcement recommends Stripe’s Managed Payments for businesses in a supported country. On 25 November 2026 Open SaaS still lists Lemon Squeezy in its README and its payments guide. If you start on Open SaaS now, pick Stripe, Polar or Paddle.

SaaSy Land’s generated projects have no billing on 25 November 2026. This site sells its own licences through Polar, and billing with Polar, then with Stripe, is first on the roadmap. If you need payments in your first week and do not want to write them, that alone is a reason to choose Open SaaS today.

## Updates

Open SaaS is candid about updates: its documentation advises against merging later template changes into an app you have already started, because your code will have diverged, and suggests copying the specific fixes you need by hand. That is honest, and it is how most free templates work in practice.

SaaSy Land records the release and your answers in `saasyland.json` in every generated project, so it can regenerate the same project from a newer release. The `update` command that would merge that into your project is on the roadmap and not available yet. Today, neither product updates your project for you.

## What each one costs

Open SaaS costs nothing, and the services it connects to bill you directly.

SaaSy Land has a free entry too: the complete source of saasyland.com, with its auth, customer workspace, admin console, Polar checkout and coverage gate, is public under the MIT licence. You can read all of it, run it and build on it without paying. ## Choose Open SaaS when

- You want to spend nothing, and an MIT licence is what you need.
- You need background jobs, file uploads or payments in your first week, without writing them.
- You are happy to build on Wasp and follow its releases, and you like declaring your app in one config file.
- You want to deploy to Fly.io or Railway with one command, on PostgreSQL.
- Your product is in one language, or you will add translations yourself.

## Choose SaaSy Land when

- You want plain code with no framework of ours underneath, so nothing stands between your project and its stack’s own releases.
- Most of your code is written by coding agents, and you want checks that fail the pull request when one of them breaks something, not only instructions it may skip.
- You sell in more than one language, and want every string, date and price translated from the first day, with CI failing on a missing key.
- You deploy to Cloudflare Workers with D1 today, or you will wait for the stack you want as it arrives on the roadmap.
- You build for clients and want a licence that says so: Agency covers unlimited client projects.

And if you are not sure yet, start with the free part: read this site’s source, run its tests, and see whether that is the codebase you want your agent working in.
