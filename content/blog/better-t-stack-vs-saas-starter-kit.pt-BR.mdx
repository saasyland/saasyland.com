## Comece aqui: ele é muito bom e você provavelmente deveria usá-lo

O [Better-T-Stack](https://better-t-stack.dev/) é uma CLI para gerar projetos TypeScript com segurança de tipos de ponta a ponta. Tem licença MIT, o README promete “gratuito e open source: para sempre”, tem **5.636 estrelas no GitHub** e é baixado cerca de **2.476 vezes por semana** no npm.

A matriz de opções é a melhor do ecossistema, e com folga:

| Camada                | O que oferece                                                                                                                    |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Frontend              | React com TanStack Router, React Router ou TanStack Start, Next.js, Nuxt, Svelte, Solid, Astro, React Native ou nenhum           |
| Backend               | Hono, Express, Fastify, Elysia, fullstack auto-hospedado, Convex ou nenhum                                                       |
| API                   | tRPC, oRPC ou nenhuma                                                                                                            |
| Runtime               | Bun, Node.js, Cloudflare Workers                                                                                                 |
| Banco de dados        | SQLite, PostgreSQL, MySQL, MongoDB ou nenhum                                                                                     |
| ORM                   | Drizzle, Prisma, Mongoose ou nenhum                                                                                              |
| Autenticação          | Better Auth ou Clerk, opcional                                                                                                   |
| Configuração do banco | Turso, Neon, Supabase, Prisma Postgres, MongoDB Atlas, Cloudflare D1, Docker                                                     |
| Complementos          | Turborepo, Nx, PWA, Tauri, Electrobun, Biome, Lefthook, Husky, Starlight, Fumadocs, Ultracite, Oxlint, MCP, OpenTUI, WXT, Skills |
| Exemplos              | Todo, AI                                                                                                                         |

Fazer tantas combinações produzirem um projeto que realmente passa na verificação de tipos e roda é engenharia de verdade, e difícil. Ele também é distribuído como plugin do Claude Code com um servidor MCP, para que um agente possa planejar e gerar um stack válido em vez de escrever boilerplate à mão, o que é um trabalho bem pensado.

**Se você está construindo um protótipo, uma ferramenta interna, um projeto de portfólio, um app que não é SaaS ou qualquer coisa em que queira aprender a infraestrutura, pare de ler e execute `bun create better-t-stack@latest`.** É gratuito, é excelente, e nada abaixo argumenta contra ele.

O restante é para um leitor específico: quem está tentando decidir se a CLI gratuita basta para um SaaS pelo qual pretende cobrar.

## Um stack não é um produto

O README do Better-T-Stack apresenta sua filosofia em quatro linhas, e a segunda resume toda a comparação:

> Monte seu próprio stack: você escolhe só as partes de que precisa, nada além disso.
> **Templates mínimos: estruturas iniciais enxutas, sem nada de excesso.**
> Dependências atualizadas: sempre versões atuais e estáveis por padrão.
> Gratuito e open source: para sempre.

Isso não é uma limitação escondida. É o design, dito com clareza, e o projeto entrega exatamente o que promete. A prova está na última linha da tabela acima: os exemplos incluídos são **Todo** e **AI**. Uma lista de tarefas e um chat. Essas são as demonstrações canônicas de que a integração funciona, e são os exemplos certos para uma ferramenta cujo trabalho é integrar.

Então o enquadramento honesto não é “ferramenta gratuita com recursos faltando”. É:

**O Better-T-Stack gera um stack. Um kit inicial SaaS gera um produto.**

Os dois são geradores. Eles param em linhas diferentes. O Better-T-Stack para quando o frontend consegue chamar o backend e o backend consegue acessar o banco de dados, com segurança de tipos, com nove frontends e seis backends à sua escolha. É um ponto defensável para parar, e é onde a maioria dos geradores deveria parar.

Um kit inicial SaaS para em outro lugar: quando uma pessoa consegue se cadastrar, entrar em uma organização, receber um papel, ser cobrada mensalmente, receber um e-mail sobre isso e ser consultada por você em um painel administrativo quando escrever confusa. Tudo entre essas duas linhas é a conta.

Eis o que fica entre `bun create better-t-stack@latest` e um produto pelo qual você pode cobrar. As estimativas consideram um desenvolvedor competente construindo cada item no padrão que apresentaria a uma empresa pagante e não incluem o tempo gasto decidindo como fazer, que em várias linhas é maior que a implementação.

A US$ 150 por hora, isso dá **US$ 42.000 a US$ 69.750**. Coloque a sua própria taxa e o número muda, mas a conclusão não. Contra um preço único de US$ 249, a comparação não é difícil para ninguém cujo tempo tenha preço.

Mas as horas são o argumento chato, e prefiro apresentar o interessante.

## A parte que não se mede em horas

Observe quatro linhas dessa tabela: **isolamento multitenant, papéis e permissões, idempotência de webhooks e revogação de sessões.**

Elas compartilham uma propriedade que nenhuma das outras linhas tem. **A implementação errada passa na revisão, funciona em desenvolvimento e se sai bem na demonstração.**

Um filtro de tenant aplicado na camada de visualização em vez da camada de consultas funciona perfeitamente com um tenant. Funciona perfeitamente nos seus testes, porque seus fixtures têm um tenant. Falha no dia em que os dados do seu segundo cliente aparecem no dashboard do primeiro, e isso não é um relatório de bug, é um telefonema.

Um handler de webhook sem chave de idempotência funciona todas as vezes que você testa, porque você nunca envia o mesmo evento duas vezes. A Stripe envia, em uma nova tentativa, e então alguém foi cobrado duas vezes ou recebeu um plano duas vezes.

Uma verificação de permissão que lê o papel da sessão em vez de relê-lo do banco de dados funciona até alguém ser rebaixado e manter a sessão antiga.

Esses não são problemas difíceis. São problemas em que **errar é invisível até ficar caro**, o que é um perfil de risco completamente diferente de “isto leva 40 horas”. Você não consegue sair deles comprando mais horas, porque não sabe que precisa delas. Você os evita partindo de uma fundação em que alguém já cometeu o erro e o corrigiu, e em que agora existe um teste que falha se ele voltar.

É para isso, e não pela contagem de horas, que um kit inicial pago realmente serve.

## Como é o lado pago, concretamente

Para ser específico em vez de abstrato, eis o que “já resolvido” significa nesta base de código, com os números lidos da execução dos testes, e não digitados em um arquivo de marketing.

**Um gate de cobertura, e não um selo de cobertura.** <RepositoryCount fact="testFiles" /> arquivos de teste e quatro limites na configuração:

```ts
coverage: {
  thresholds: { branches: 100, functions: 100, lines: 100, statements: 100 },
}
```

Os ramos de erro da seção anterior são exatamente o que um gate de cobertura de ramificações em 100 obriga você a testar. Esse é o mecanismo, não o número.

**Responsabilidades claras e verificações tipadas.** O aplicativo de referência público agrupa as operações por funcionalidade e configura o Vite+ para verificar tanto as regras de lint quanto os tipos:

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

Os arquivos de rota coordenam a navegação; os casos de uso das funcionalidades ficam em `src/modules`; a configuração de fornecedores fica em `src/integrations`; a interface fica em `src/presentation`. Módulos exclusivos do servidor mantêm os bindings do Worker fora do cliente. A responsabilidade dentro dessas pastas é uma convenção a ser revisada, e não uma restrição de importação aplicada por este trecho.

**Rigor sem válvula de escape.** `strict`, mais `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` e `verbatimModuleSyntax`. `typescript/no-explicit-any` é um erro, e as categorias de lint estão configuradas como erros, então a verificação termina com um código de saída de falha.

**Recursos opcionais, não um template fixo.** O [configurador](/#cli) faz <RepositoryCount fact="cliQuestions" /> perguntas e oferece quatro extras: uma loja com produtos de exemplo, um curso por assinatura, um construtor visual de páginas e um editor visual de posts. Ativar um deles adiciona um módulo. Deixá-lo desativado significa que esse código não existe no seu repositório.

Nada disso é uma crítica ao Better-T-Stack. É uma descrição de onde os dois produtos param.

## Quando o Better-T-Stack é a resposta certa

Dito direito, porque uma comparação que sempre recomenda a opção paga é um anúncio, e não uma comparação.

**Use o Better-T-Stack se:**

- Você está prototipando, e a coisa pode não existir daqui a um mês.
- Você está aprendendo, e a infraestrutura é o objetivo. Construir autenticação uma vez é uma formação realmente valiosa, e ninguém deveria ser convencido a desistir disso.
- Seu produto não é um SaaS. Sem organizações, sem assinaturas, sem painel administrativo. Uma ferramenta, um jogo, um dashboard interno, um site para cliente.
- Você já tem uma biblioteca interna para os três quartos chatos, como muitas agências e equipes experientes têm.
- Seu stack está fora do que qualquer kit pago oferece. Nuxt, Svelte, Solid, Astro, React Native, Convex, tRPC. O Better-T-Stack cobre todos esses, e nenhum kit inicial pago cobre a maioria deles.
- Seu orçamento é realmente zero. É uma restrição legítima e não há vergonha nisso. O Better-T-Stack é uma opção gratuita melhor do que o plano gratuito de qualquer produto pago.

**Considere pagar se:**

- Você está construindo um produto pelo qual pretende cobrar de empresas, com assentos, papéis, faturas e um questionário de segurança no seu futuro.
- Você já construiu organizações e cobrança uma vez e lembra exatamente quanto tempo as partes chatas levaram.
- Você quer um gate de testes que não precisou escrever, porque escrever uma suíte de cobertura do zero é o item a que ninguém nunca chega.
- Você quer as fronteiras arquiteturais aplicadas, e não apenas pretendidas.
- Seu tempo tem preço, e 280 a 465 horas dele custam mais do que algumas centenas de dólares.

## Eles não são realmente concorrentes

A coisa mais útil que posso dizer é que esta não é uma disputa entre dois cavalos.

O Better-T-Stack é um gerador para _qualquer_ projeto TypeScript, com nove frontends e seis backends. Um kit inicial SaaS é uma fundação para _um tipo_ de negócio. A sobreposição são os dez minutos iniciais em que os dois escrevem um projeto. Depois disso, fazem trabalhos diferentes.

O erro a evitar não é “escolher o gratuito”. É escolher qualquer um dos dois sem saber de qual dos dois trabalhos você precisava. Um fundador que gera um belo stack com segurança de tipos e depois passa seis meses construindo organizações e cobrança não economizou dinheiro. Ele pagou a conta na moeda que não aparece em nenhuma fatura.
