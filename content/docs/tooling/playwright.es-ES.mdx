Playwright prueba la aplicación compilada en navegadores reales. La suite se ejecuta contra el entorno de Wrangler `test`: D1, KV y R2 locales en `.wrangler/test`, credenciales ficticias de `.env.test` y el punto de entrada de pruebas `src/platform/testing/worker.ts`, que intercepta las solicitudes a Resend y a Polar.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:visual
bun run test:visual:update
bun run test:journey
```

| Script               | Ejecuta                                                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| `test:e2e:install`   | Instala Chromium y WebKit con las dependencias del sistema                                          |
| `test:e2e`           | Todas las specs en Chromium y WebKit                                                                |
| `test:e2e:smoke`     | `e2e/specs/smoke.spec.ts` en Chromium                                                               |
| `test:e2e:pr`        | Todas las specs en Chromium, como las ejecuta la comprobación de Chromium de la CI de pull requests |
| `test:e2e:headed`    | Todas las specs en navegadores visibles                                                             |
| `test:e2e:ui`        | Modo UI de Playwright                                                                               |
| `test:visual`        | Las [pruebas visuales](#visual-tests) en Chromium desde la imagen de Docker de Playwright           |
| `test:visual:update` | Las pruebas visuales, reescribiendo las capturas que ya no coinciden                                |
| `test:journey`       | La [suite del recorrido del cliente](#journey-suite) contra preview                                 |

## Configuración [#configuration]

`playwright.config.ts` ejecuta las specs de `e2e/specs/`, define los proyectos `chromium` (Desktop Chrome) y `webkit` (Desktop Safari) y usa `PLAYWRIGHT_BASE_URL` o `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` de `src/data/local-server.ts`). En local, el comando del servidor web ejecuta `db:reset:test`, `build:test` y `start:test`, y reutiliza un servidor que ya responda en esa URL. En CI, un job prepara la compilación, cada uno de los <RepositoryFact name="e2eShards" /> shards que se reparten la suite la desempaqueta y Playwright solo inicia el servidor ([CI/CD](/docs/tooling/ci-cd#checks)).

| Ajuste     | Local                                            | CI                                            |
| ---------- | ------------------------------------------------ | --------------------------------------------- |
| Reintentos | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" /> |
| Workers    | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" /> |
| Trazas     | Se conservan si falla                            | En el primer reintento                        |
| Vídeos     | Desactivados                                     | Se conservan si falla                         |
| Reporter   | Lista y HTML                                     | GitHub y blob, combinados en HTML si falla    |

## Ejecutar junto a otros worktrees [#running-beside-other-worktrees]

La build de pruebas solo acepta peticiones de los hosts en los que confía en modo de pruebas, porque Better Auth y los enlaces del boletín comprueban el host de la petición: `127.0.0.1:3000` y `localhost:3000`, y `127.0.0.1` y `localhost` en los puertos <RepositoryFact name="testServerFirstPort" /> a <RepositoryFact name="testServerLastPort" />, definidos por `TEST_SERVER_PORTS` en `src/data/local-server.ts`. En cualquier otro puerto fallan las páginas de inicio de sesión y de cursos, por eso `playwright.config.ts` se detiene antes de compilar nada cuando `PLAYWRIGHT_BASE_URL` indica otro host.

`PLAYWRIGHT_BASE_URL` es el único ajuste que elige el puerto: Playwright abre esa URL e inicia `start:test` en su puerto. Cuando otros worktrees ejecutan sus suites al mismo tiempo, da a cada worktree su propio puerto del rango. Comprueba que nada escucha en él y ejecuta la suite allí:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` no imprime nada cuando el puerto está libre. Si imprime un proceso, elige otro puerto y no toques ese servidor: detén solo los servidores que iniciaste tú.

En local, Playwright reutiliza un servidor que ya responde en la URL y entonces se salta el reinicio de la base de datos y la compilación, de modo que la suite nunca debe llegar al servidor de otro worktree. `e2e/global-setup.ts` lo garantiza: antes de la primera prueba busca con `lsof` los procesos que escuchan en el puerto y detiene la ejecución cuando alguno se ejecuta en un directorio distinto de este worktree. Un servidor que iniciaste desde este worktree pasa la comprobación y se reutiliza tal cual; detenlo cuando la suite deba probar una compilación nueva.

## Estructura

- `e2e/specs/`: specs de comprobaciones smoke, la página de inicio y sus controles, navegación, idiomas, tema, SEO, autenticación con sus redirecciones y su enrutamiento, espacios de trabajo, administración de usuarios, newsletter, contenido, páginas legales, precios regionales, el embudo de pago, la página de licencia, la API de licencias de la CLI, afiliados, vídeos, cursos, acceso a cursos, administración de cursos, portadas, importación y materiales de los cursos, panel de administración, pedidos, productos y máquinas de las licencias, índice del blog y compartir entradas, Content Security Policy, desistimiento, pie de página, anillos de foco, barras de desplazamiento, webhooks de licencias, CLI publicada y accesibilidad (<RepositoryFact name="e2eSpecs" /> archivos).
- `e2e/pages/`: page objects.
- `e2e/fixtures/`: la fixture `test` extendida, utilidades para los correos capturados, `deliverPaidOrder` en `license.ts`, que envía un webhook `order.paid` firmado para conceder una licencia, `buyLicense`, que pide al Worker de pruebas en `/__test/polar/purchase` un pedido con su clave de licencia en el doble de pruebas de Polar y envía sus `order.paid` y `benefit_grant.created` firmados, `startedCheckouts`, que lee de `/__test/polar/checkouts` los pagos que creó el doble, `payCheckout`, que completa un pago que abrió la aplicación a través de `/__test/polar/pay` del Worker de pruebas, con el consentimiento marcado, y envía los `order.paid` y `benefit_grant.created` firmados de su pedido, `accessibilityViolations` con los `COLOR_SCHEMES` claro y oscuro en `accessibility.ts`, y la página de pago de Polar en `polar-checkout.ts`. El doble de Polar da a cada pago una URL en el origen del pago de Polar, y `servePolarCheckout`, uno de los `BROWSER_DOUBLES` que instala la fixture automática `browserDoubles`, responde a esa URL en cada contexto del navegador con una página del doble, leída de `/__test/polar/checkout` del Worker de pruebas: indica a la capa superpuesta que se ha cargado, y sus botones **Pay** y **Close** envían `confirmed` y `success`, o `close`, al `embed_origin` del pago, como hace la página de Polar. `payInCheckoutOverlay` y `closeCheckoutOverlay` los pulsan, y `refusePolarCheckoutEmbedding` sirve la página con `frame-ancestors 'none'`, como hace Polar con un host que su organización no incluye en la lista. La suite del recorrido del cliente pone la opción `browserDoublesEnabled` en `false` y paga en el sandbox real. `orderLicense` envía solo el `order.paid` de una compra así y devuelve `issueKey`, que envía después su `benefit_grant.created`. Abierto como la propia página de pago de Polar, fuera de un marco, el botón **Pay** del doble lleva al navegador a la URL de éxito del pago con un `customer_session_token`, como hace la página de Polar, y `payOnPolarCheckoutPage` lo pulsa. `refundOrder`, `revokeLicenseKey`, `deliverGuestOrder` y `cutOffPolar` piden al Worker de pruebas en `/__test/polar/refund`, `/__test/polar/revoke`, `/__test/polar/guest-purchase` y `/__test/polar/cut-off` un `order.refunded` firmado de un pedido del doble, un `benefit_grant.revoked` firmado de su clave, un `order.paid` firmado de un comprador sin cuenta o una clave cuyas peticiones a Polar fallan como si Polar no respondiera. `signUpBuyer` en `buyer.ts` registra a un comprador por la API, `sendToApi` en `cli-api.ts` llama a la API de licencias de la CLI desde una dirección propia y `EVERY_STACK_ANSWER` en `stack-answers.ts` reúne un conjunto válido de respuestas para cada opción y cada extra del stack.
- `e2e/data/accounts.ts`: las cuentas precargadas, un administrador y un cliente, y su contraseña. `e2e/data/licenses.ts` contiene el cliente con licencia y esa licencia, además de una licencia por cada worker en paralelo, en la que la spec de la API de licencias de la CLI activa dispositivos.
- `e2e/data/videos.ts` y `e2e/data/courses.ts`: el vídeo de prueba precargado, cuyos archivos están en `e2e/fixtures/video/`, y el curso precargado: dos capítulos, el primero con una vista previa gratuita, una lección para cuentas y una lección de pago, y el segundo con tres lecciones de pago cuyo vídeo aún se está grabando.
- `e2e/data/<feature>.pages.ts` y `e2e/data/<feature>.seed.ts`: las páginas de cada funcionalidad, que visitan `accessibility.spec.ts` y `workspaces.spec.ts`, y sus filas y archivos multimedia en la base de datos de pruebas, cada lista importada por `ENTRIES` en `e2e/data/pages.ts` y por `scripts/seed-test.ts`.
- `e2e/data/<feature>.flows.ts`: los flujos de cada funcionalidad, cada uno con la prueba que lo demuestra de principio a fin o el motivo por el que falta, importados por `FLOWS` en `scripts/check-flows.ts`; consulta [Cobertura de pruebas](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: la configuración global, que detiene la ejecución cuando el servidor del puerto de la suite se ejecuta desde otro worktree.
- `e2e/journey/`: la [suite del recorrido del cliente](#journey-suite), con su propia configuración. `published-cli.spec.ts` ejecuta la CLI publicada con `runCli` de `e2e/journey/cli.ts` contra el Worker de pruebas, así que la suite del navegador necesita el registro de npm.

El Worker de pruebas ejecuta lo que las funcionalidades declaran en `e2e/data/<feature>.worker.ts`, cada lista importada por `ENTRIES` en `src/platform/testing/worker.ts`: la funcionalidad de licencias siembra las claves de licencia de prueba en el doble de Polar, Resend expone `/__test/emails` para leer los correos capturados y la del boletín, `/__test/newsletter` para leer el estado de un suscriptor.

## Accesibilidad

`e2e/specs/accessibility.spec.ts` ejecuta [axe-core](https://github.com/dequelabs/axe-core) mediante `@axe-core/playwright` en las páginas públicas, las páginas de cursos, la portada de la documentación, todas las páginas de Convenciones y una página de cada una de las demás secciones de la documentación, una entrada del blog y los espacios de trabajo de administración y de cliente con los temas claro y oscuro. Las páginas de administración incluyen `/admin/courses`, `/admin/courses/create` y el editor del curso sembrado, que `e2e/specs/workspaces.spec.ts` también visita. Aplica las reglas A y AA de WCAG 2.0, 2.1 y 2.2 junto con las buenas prácticas de axe, falla si una página no se carga con un estado de éxito, recorre la página con scroll para que también se revisen las secciones que aparecen al desplazarse, espera a que terminen las animaciones finitas y falla ante cualquier infracción, indicando la regla, su impacto y los selectores afectados.

axe no ve el recorrido del teclado ni el diseño, así que tres specs los comprueban en la cabecera y el pie de página del sitio: `e2e/specs/navigation.spec.ts`, que el menú del móvil lleva el foco a sí mismo, mantiene Tab dentro, deja la página de detrás `inert` y devuelve el foco a su botón; `e2e/specs/footer.spec.ts`, que a <RepositoryFact name="footerPhoneWidths" /> px ningún par de enlaces del pie se toca ni se sale del pie en ningún idioma, y que un enlace a una sección de la página de inicio solo es el actual en su propia sección; y `e2e/specs/focus-rings.spec.ts`, que el selector de idioma del pie y el disparador de la paleta de comandos del panel de administración dibujan su anillo para el teclado.

`e2e/specs/text-layout.spec.ts` comprueba el formulario de cursos y las tablas de la administración y el generador de comandos de la página de inicio a <RepositoryFact name="textLayoutWidths" /> px con `textLayoutProblems` de `e2e/fixtures/text-layout.ts`: ninguna línea de texto se solapa con otra ni con un icono, ninguna se corta sin puntos suspensivos, ninguna queda reducida a unas pocas letras por los puntos suspensivos, la página nunca se desplaza en horizontal y todas las pestañas de idioma del formulario de cursos están a la vista. El texto que se desplaza por debajo de una columna fijada o de una cabecera fija queda tapado por ella, así que la comprobación compara el texto fijo solo con otro texto fijo. Otra prueba abre cada tabla del panel de administración en inglés y en ucraniano, el idioma con los encabezados más largos, y falla cuando un encabezado es más ancho que su celda.

## Barras de desplazamiento [#scrollbars]

`e2e/specs/scrollbars.spec.ts` inicia Chromium sin el modificador `--hide-scrollbars` de Playwright, mediante `ignoreDefaultArgs` en `launchOptions`, así que Chromium dibuja barras de desplazamiento clásicas que ocupan espacio, como en Windows, en Linux y en un Mac configurado para mostrarlas siempre. La spec comprueba que una página legal, una de autenticación y una del panel de administración mantienen su encabezado en su sitio cuando la ventana crece hasta que la página deja de desplazarse (una página de la documentación siempre se desplaza, porque el pie del sitio sigue a su layout de toda la altura de la ventana), que abrir la búsqueda de la documentación, el selector de idioma, un diálogo o un menú no mueve nada, que `/admin` ocupa la ventana y que la ventana detrás de una página oscura es oscura con el tema claro. WebKit en macOS solo dibuja barras superpuestas, que no ocupan espacio, y ninguna opción de arranque lo cambia, así que la comprobación del espacio reservado solo se ejecuta en Chromium. El menú del sitio, que sustituye a los enlaces de la cabecera por debajo de `lg`, se comprueba a 768 px: abrirlo y cerrarlo no mueve nada.

## Pruebas visuales [#visual-tests]

`e2e/specs/visual-*.spec.ts` comparan lo que ve un visitante con capturas de pantalla aprobadas en `e2e/specs/__screenshots__/`, así que un cambio que pasa un título a otra línea, añade una tarjeta o mueve una sección hace fallar la pull request aunque pasen todas las demás pruebas. Las specs se ejecutan en su propio proyecto de Playwright, `visual`, que `playwright.config.ts` solo define cuando `PLAYWRIGHT_VISUAL_BROWSER` indica un servidor de navegador; los proyectos `chromium` y `webkit` las omiten.

```sh
bun run test:visual
bun run test:visual:update
```

| Spec                                             | Capturas                                                                                                                                                                    | Idiomas y anchos                                      |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `visual-landing.spec.ts`, `visual-facts.spec.ts` | La cabecera, la sección de apertura, la cuadrícula de datos, los precios con las demás opciones, los casos, el manifiesto, la sección final y el pie de la página de inicio | Cada idioma en cada ancho                             |
| `visual-content.spec.ts`                         | La tarjeta del autor y la llamada a la acción al final de un artículo del blog                                                                                              | Cada idioma en el móvil, el inglés en el escritorio   |
| `visual-content.spec.ts`                         | Una página de la documentación                                                                                                                                              | El inglés en ambos anchos, el alemán en el escritorio |
| `visual-auth.spec.ts`                            | La cabecera de un visitante con sesión iniciada, `/admin` y `/admin/settings`                                                                                               | El inglés en ambos anchos, el alemán en el escritorio |
| `visual-billing.spec.ts`                         | `/app/billing`                                                                                                                                                              | El inglés en ambos anchos, el alemán en el escritorio |

Los idiomas son <RepositoryFact name="visualLocales" />, los anchos <RepositoryFact name="visualWidths" /> px, y la suite reúne <RepositoryFact name="visualScreenshots" /> capturas. En la página de inicio lo que cambia es sobre todo el texto, así que sus secciones se capturan en cada idioma en ambos anchos. Las tarjetas bajo un artículo del blog se rompen donde las palabras largas saltan de línea, en el móvil, así que se capturan con el ancho del móvil en cada idioma. Las páginas de la administración y del área de cliente toman su diseño de los componentes, no de los textos: el inglés en ambos anchos muestra el diseño, y el alemán, el idioma con las palabras más largas, muestra las etiquetas que dejan de caber.

### Los mismos píxeles en cada ejecución [#same-pixels-on-every-run]

- El contexto del navegador fija `reducedMotion: "reduce"`, así que la entrada de la sección de apertura, las secciones que aparecen al desplazarse y los vídeos en bucle se quedan quietos, y los vídeos muestran su imagen de portada. `toHaveScreenshot` detiene cualquier otra animación, como la cinta de la stack, y oculta el cursor de texto.
- El tema es oscuro y la zona horaria UTC.
- Antes de la primera captura, `openForScreenshots` de `e2e/fixtures/visual.ts` espera a que la página se renderice e hidrate, carga y decodifica cada imagen, también las de carga diferida, y espera a `document.fonts.ready`.
- `expectRegion` recorta una sección de la página completa en el lugar que ocupa, de modo que la cabecera fija nunca la tapa.
- Las máscaras cubren lo que cambia sin ningún cambio de diseño: los datos que cuentan archivos del repositorio y estrellas de GitHub, y los años del aviso de copyright del pie.
- Los datos salen de la base de datos de pruebas con sus datos iniciales. `scripts/visual-tests.ts` se detiene antes de la primera prueba cuando ya responde un servidor en la URL de la suite, así que Playwright restablece la base de datos, compila y arranca el servidor por sí mismo; en la CI, el job desempaqueta su propia copia del build con sus datos.

### El mismo navegador en cada máquina [#the-same-browser-on-every-machine]

Las fuentes se ven distintas en macOS y en Linux, e incluso entre imágenes de Linux, así que las pruebas visuales nunca usan un navegador de la máquina que las ejecuta. `scripts/visual-tests.ts` arranca el servidor de navegador de Playwright en la imagen de Docker `<RepositoryFact name="visualBrowserImage" />` para `linux/amd64`, que Docker Desktop emula en los chips de Apple, pasa su dirección en `PLAYWRIGHT_VISUAL_BROWSER` y ejecuta `playwright test --project=visual`. Las pruebas se conectan con `connectOptions`, y su `exposeNetwork: "<loopback>"` permite al navegador llegar al servidor de pruebas en la interfaz de loopback de la máquina. La etiqueta de la imagen sigue a la versión instalada de `@playwright/test`, así que `bun run deps:update` actualiza a la vez el navegador y el ejecutor de pruebas. Un portátil y la CI producen los mismos píxeles, de modo que las capturas de referencia tomadas en local pasan en la CI. `test:visual` necesita Docker en marcha.

### Umbral [#threshold]

Una captura falla cuando difieren más del <RepositoryFact name="visualMaxDiffPercent" unit="percent" /> de sus píxeles, y un píxel solo cuenta como distinto si su color supera el umbral que Playwright aplica a cada píxel. El navegador y sus fuentes son los mismos en todas partes, así que una página sin cambios no difiere en ningún píxel, y el tono o dos en que otro procesador puede redondear el suavizado de bordes queda por debajo de ese umbral. Una captura cuyo tamaño cambia, porque un título pasa a otra línea o se añade una tarjeta, falla sea cual sea el umbral, y una sola palabra añadida al párrafo de la sección de apertura ya cambia más píxeles de los que permite el umbral.

### Actualizar las capturas de referencia [#updating-the-baselines]

Cuando un cambio en el diseño o en el texto es intencionado, ejecuta `bun run test:visual:update`, abre cada PNG modificado de `e2e/specs/__screenshots__/` en el diff de tu rama, revísalo y haz commit de él junto con el cambio. `--update-snapshots=changed` solo reescribe las capturas que ya no coinciden. Cuando el job `visual` falla en la CI, sube `test-results/` como artefacto `visual-differences`, con la imagen esperada, la obtenida y la de diferencias de cada captura que falló.

### En la CI [#in-ci]

El job `visual` de `e2e-reusable.yml` solo se ejecuta para Chromium, junto a los shards: espera el build de pruebas como un shard, lo desempaqueta y ejecuta `bun run test:visual`, y la comprobación `Build and E2E (chromium)` falla si no pasó. Las capturas de referencia son las de Chromium porque WebKit dibuja el texto y los subpíxeles de otra manera: necesitaría un segundo juego de capturas y una segunda revisión del mismo diseño, mientras que la comprobación de WebKit sigue probando cómo se comporta WebKit.

## Suite del recorrido del cliente [#journey-suite]

`bun run test:journey` compra una licencia y usa la CLI como lo hace un cliente, en el despliegue de preview en `https://preview.saasyland.com`, que cobra en el sandbox de Polar. `e2e/journey/playwright.config.ts` es una configuración propia, con su propio proyecto de Chromium y sin servidor web, así que ni `test:e2e` ni las comprobaciones de las pull requests la ejecutan; `journey.yml` la ejecuta cada noche y a mano ([CI/CD](/docs/tooling/ci-cd#journey-suite)). Cada nivel es una prueba propia, con la etiqueta `@core`, `@complete` o `@agency`, las pruebas se ejecutan en paralelo y cada una sigue estos pasos:

1. **Cuenta.** La prueba se registra con una dirección nueva de la bandeja de pruebas de Resend, `delivered+journey-<run>-<tier>@resend.dev`, o `upgrade` en lugar del nivel en la prueba de la subida de nivel, encuentra el correo de verificación a través de la API de Resend y abre su enlace.
2. **Precio.** `/app/license` debe ofrecer el nivel al precio del país en el que Cloudflare sitúa al runner, según indica `/cdn-cgi/trace`: el precio regional en un país de `PPP_TIERS` y el precio completo en cualquier otro.
3. **Pago.** El checkout del sandbox de Polar debe abrirse sobre `/app/license`, en un marco de `sandbox.polar.sh` que recibe el foco, sin salir de la página, con el correo de la cuenta ya rellenado y el consentimiento al suministro inmediato sin marcar; la prueba lo marca en el marco. La prueba paga con la [tarjeta de prueba de Stripe](https://docs.stripe.com/testing) y facturación en Polonia, donde la dirección de facturación es solo el país. La página debe recibir los mensajes `loaded`, `confirmed` y `success` de Polar en ese orden, cerrar la capa superpuesta y mostrar la licencia activa en `/app?checkoutId=<id>&tier=<tier>`. Polar solo muestra el checkout en un marco mientras la organización del sandbox incluya `preview.saasyland.com` en [Settings > Embedding](/docs/getting-started/polar-setup#embedding).
4. **Pedido y clave.** Polar debe tener un único pedido pagado del producto del nivel, al precio que ofreció `/app/license`, con el consentimiento y el idioma del comprador, la confirmación de compra debe llegar a la bandeja de entrada, y `/app/license` debe mostrar la clave que emitieron los webhooks, los comandos de la CLI y ningún dispositivo en uso.
5. **CLI.** La CLI publicada, ejecutada como <RepositoryFact name="cliExec" /> igual que los comandos de `/app/license`, se comunica con preview mediante `SAASYLAND_API_URL`. `activate` escribe el archivo de credenciales con el modo `0600`, volver a activar conserva la misma activación y `whoami` muestra el dispositivo. Los dispositivos de CI, que `SAASYLAND_CI_REPOSITORY` distingue, ocupan las activaciones restantes, hasta <ActivationLimit tier="core" /> dispositivos en Core, <ActivationLimit tier="complete" /> en Complete y <ActivationLimit tier="agency" /> en Agency, y el siguiente se rechaza con `activationLimitReached`. En cuanto se libera una activación en `/app/license`, el dispositivo rechazado la obtiene y el liberado recibe `activationNotFound`. `deactivate` libera el primer dispositivo y elimina sus credenciales.
6. **Reembolso.** La prueba reembolsa el pedido mediante la API del sandbox de Polar y espera hasta que `/app/license` muestre la licencia como reembolsada; entonces `whoami` debe responder `licenseRefunded` y eliminar las credenciales.

Una cuarta prueba, con la etiqueta `@upgrade`, sube una licencia de nivel. Compra Core de la misma forma y ocupa los <ActivationLimit tier="core" /> dispositivos de Core, y el siguiente se rechaza. Después, `/app/license?tier=complete` debe ofrecer Complete a su precio para el país del runner menos lo que costó el pedido de Core, y la prueba paga esa diferencia en el checkout de Polar superpuesto a la página, de la misma forma. Polar debe tener el pedido de la subida de nivel por la diferencia, con el pedido y el nivel de Core en `upgrade_from_order` y `upgrade_from_tier`; la clave del pedido de Core debe permitir ahora los <ActivationLimit tier="complete" /> dispositivos de Complete, la clave que Polar concedió por el pedido de la subida de nivel debe estar desactivada y `/app/license` debe mostrar Complete con la misma clave. Después se activan el dispositivo rechazado y el siguiente, y el que viene detrás se rechaza. La prueba reembolsa el pedido de la subida de nivel a través de la API del sandbox de Polar: la licencia debe volver a ser Core, con la misma clave y el límite de Core, los dispositivos ya activados siguen funcionando y uno nuevo se rechaza. Un reembolso del pedido de Core termina después la licencia.

Cada dispositivo de la CLI es un directorio en la carpeta de salida de la prueba que la CLI usa como su directorio personal, y la CLI se ejecuta sin nada en su entorno salvo `PATH`, ese directorio, una caché de npm y las variables `SAASYLAND_*`, de modo que ninguna credencial de la suite llega a ella. Un pedido que una prueba fallida deja pagado se reembolsa cuando termina la prueba. Las cuentas quedan en preview, cada una con una licencia reembolsada.

La suite lee estos valores del entorno, o de `.env.preview` cuando el archivo existe, y se detiene antes de la primera prueba si faltan; en CI, `journey.yml` los lee del entorno `Preview` de GitHub:

| Variable                                                                        | Para qué                                                                                                                                                        |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | Leer y reembolsar los pedidos en el sandbox y leer sus claves de licencia, con los scopes `orders:read`, `refunds:write`, `benefits:read` y `license_keys:read` |
| `POLAR_SERVER`                                                                  | Debe ser `sandbox`                                                                                                                                              |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Los productos del sandbox a los que deben corresponder los pedidos                                                                                              |
| `RESEND_API_KEY`                                                                | Leer los correos de verificación que envió preview, para lo que hace falta una clave con acceso completo                                                        |

Preview debe ejecutar un build con la [API de licencias de la CLI](/docs/features/cli-licence-api). Preview ejecuta `main`, que `deploy.yml` despliega allí antes que en producción; para probar una rama antes de que se fusione, despliégala con `gh workflow run preview.yml --ref <branch>` una vez superadas sus comprobaciones. El sandbox debe coincidir con el código, lo que comprueba `bun run polar:verify:preview`. Después:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

`bun run test:journey --grep @core` ejecuta solo la prueba con esa etiqueta. El informe HTML se escribe en `playwright-report/journey/` y un informe JSON en `playwright-report/journey.json`, y las trazas, los vídeos y los directorios de dispositivos de las pruebas fallidas en `test-results/journey/`.
