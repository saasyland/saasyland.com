## Worker とバインディング

`wrangler.jsonc` は、`src/server.ts` を Worker のエントリーとして設定します。Worker は次のバインディングを受け取ります。

| バインディング | 種類            | 用途                                                                |
| -------------- | --------------- | ------------------------------------------------------------------- |
| `DB`           | D1 データベース | セッションとレート制限のカウンターを含む、すべてのテーブル          |
| `CACHE`        | KV 名前空間     | GitHub のスター数とチェックアウトの地域割引                         |
| `MEDIA`        | R2 バケット     | 動画ファイル。`serveMedia` が `/media/` 配下で配信                  |
| `BUNDLES`      | R2 バケット     | CLI のテンプレートバンドル。`serveBundle` が `/bundles/` 配下で配信 |
| `ASSETS`       | 静的アセット    | プリレンダリング済みのページと `public` のファイル                  |

`/assets/*`、`/fonts/*`、`/robots.txt`、`/llms.txt` へのリクエストは、Worker を実行せずに静的アセットから返されます。サーバーコードは、バインディング、シークレット、`waitUntil` を `cloudflare:workers` から読み取ります。`src/server.ts` は、返すすべてのレスポンスにセキュリティヘッダーを追加します。Worker を経由せずに配信されるファイルには、`public/_headers` のサブセットが付きます（[セキュリティと堅牢化](/docs/features/security)）。

## エリアが追加するもの [#what-the-areas-add]

プラットフォームのファイルはどのエリアも名指ししません。コースやライセンス販売といった各エリアが、Worker、ルートルート、Vite のビルド、デプロイに必要なものを自分のファイルで追加し、パスやメニューと同じようにバレルがそれらをまとめます（[パスとナビゲーション](/docs/conventions/routes#paths-and-navigation)を参照）。

| 対象                 | 各エリアが宣言するもの                                              | バレル                          | 使う側                                                                                                                    |
| -------------------- | ------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Worker ハンドラー    | `src/data/<area>.worker.ts`: `<AREA>_WORKER_HANDLERS` のリスト 1 つ | `src/data/worker.entries.ts`    | `src/data/worker.ts` の `DOCUMENT_HANDLERS` と `REQUEST_HANDLERS`。`src/server.ts` が実行します                           |
| ルートコンポーネント | `src/data/<area>.root.ts`: `<AREA>_ROOT_COMPONENTS` のリスト 1 つ   | `src/data/root.entries.ts`      | `src/data/root.ts` の `ROOT_COMPONENTS`。`src/routes/__root.tsx` がアウトレットの隣にマウントします                       |
| タイムゾーン         | `src/data/<area>.time-zone.ts`: `<AREA>_TIME_ZONES` のリスト 1 つ   | `src/data/time-zone.entries.ts` | `src/data/time-zone.ts` の `TIME_ZONE_SOURCES`。`TranslationsProvider` はその最初のタイムゾーンで日付をフォーマットします |
| Vite プラグイン      | `src/data/<area>.vite.ts`: `<AREA>_VITE_PLUGINS` のリスト 1 つ      | `src/data/vite.entries.ts`      | `src/data/vite.ts` の `vitePlugins`。`vite.config.ts` が読み込みます                                                      |
| デプロイ前チェック   | `src/data/<area>.deploy.ts`: `<AREA>_DEPLOY_CHECKS` のリスト 1 つ   | `src/data/deploy.entries.ts`    | `src/data/deploy.ts` の `DEPLOY_CHECKS`。`scripts/run-deploy-checks.ts` が実行します                                      |
| 公開サイトのチェック | `src/data/<area>.live.ts`: `<AREA>_LIVE_CHECKS` のリスト 1 つ       | `src/data/live.entries.ts`      | `src/data/live.ts` の `LIVE_SITE_CHECKS`。デプロイ後に `scripts/verify-deployment.ts` がリクエストします                  |

リクエストハンドラーは `pathPrefix` を受け持ち、その配下のすべてのリクエストに、ロケールのミドルウェア、静的アセット、TanStack Start より先に応答します。コースのエリアのハンドラーが `/media/` に対して、ライセンスのエリアのハンドラーが `/bundles/` に対して行っているのがこれです。ドキュメントハンドラーは、Worker が返すすべての HTML ページをそのロケールとリクエストとともに受け取り、送信するページを返します。ライセンスのエリアの地域別価格がこれにあたります。`src/server.ts` はハンドラーを静的にインポートするため、ハンドラーはコールドスタートのたびに評価されます。そのためハンドラーのファイルがインポートするのは定数と純粋なヘルパーだけで、それより大きなものは動的 `import()` で読み込みます（[パフォーマンス](/docs/conventions/performance)を参照）。

Vite プラグインのエントリーには、ほかのエリアのプラグインの中での位置を決める `order` と、Vitest でも読み込むかどうかを示す `vitest` があります。Vite は `~` エイリアスを解決する前に設定を読み込むため、`vite.ts`、`vite.entries.ts`、各 `<area>.vite.ts` は `.ts` 拡張子付きの相対パスでインポートします。また、`vp lint` と `vp fmt` がプラグインのパッケージを読み込まないように、エントリーはそのパッケージを `plugins` 関数の中でインポートします。

タイムゾーンのソースは、日付のフォーマットに使うタイムゾーンを返すフックです。認証のエリアのソースは、ルートガードが読み込んだセッションからサインイン中のユーザーのタイムゾーンを返し、セッションがなければ `UTC` を返します。ソースがない場合も、`TranslationsProvider` は `UTC` を使います。

デプロイ前チェックは、デプロイ先の環境ごとに 1 つずつバリエーションを持つパッケージスクリプトを指定します。認証エリアは `auth:verify` を、Polar のエリアは `polar:verify` を宣言しているので、`bun scripts/run-deploy-checks.ts preview` は `bun run auth:verify:preview` と `bun run polar:verify:preview` を実行します。空のシークレットやプレースホルダーのシークレットに対するチェックは、どのエリアも宣言しません。デプロイ前チェックの前に `scripts/prepare-deploy-secrets.ts` が実行され、`wrangler.jsonc` が宣言するすべてのシークレットの中からそうした値を拒否するからです。

公開サイトのチェックは、デプロイ後にリクエストするパスと、そのパスが返すべきステータスとコンテンツタイプを指定します。コアはトップページ、`robots.txt`、サイトマップ、サイトカード、`/api` を、認証のエリアはセッションのエンドポイントを、コースのエリアはリクエストごとに D1 から描画される `/courses` をチェックします。`post` を持つチェックは、代わりにサイト自身のオリジンから JSON の本文を送り、JSON の応答を `findProblems` に渡します。認証のエリアはこの方法で `OAUTH_PROVIDERS` の各プロバイダーのサインインを開始し、認可 URL がプロバイダーのホスト上にない場合、`client_id` が別の形式の場合、`redirect_uri` がデプロイ先のドメインに戻らない場合に拒否します（[OAuth プロバイダー](/docs/features/oauth)）。

エリアは、ほかのエリアが同じ方法で項目を追加する独自のリストを定義することもできます。コースのエリアは `src/data/course-access.ts` でコースアクセスを定義し、ライセンスのエリアが `src/data/license.course-access.ts` でそれを与えます（[コース](/docs/features/courses)）。ライセンスのエリアは `src/data/license-offer.ts` で購入案内のセクションを定義し、コースのエリアが `src/data/courses.license-offer.ts` でロックされたコースを追加します（[顧客アプリ](/docs/features/customer-app)）。認証のエリアは、ほかのエリアが Better Auth に追加するプラグインとメールを定義します（[Better Auth](/docs/integrations/better-auth)）。Polar のエリアは Polar プラグインを、Resend は認証のメールを追加します。Polar のエリアは `src/data/polar-events.ts` で Polar の Webhook イベントを定義し、ライセンスのエリアと請求のエリアが `src/data/license.polar-events.ts` と `src/data/billing.polar-events.ts` でそれぞれが処理するイベントを追加します（[決済](/docs/features/payments)）。認証のエリアは、ユーザー管理のタブも `src/data/user-tabs.ts` で定義し、チームのエリアがそこに招待とロールを追加します（[ユーザー（管理）](/docs/features/users-admin)）。登録フォームの下に置く案内も `src/data/sign-up-notices.ts` で定義し、法的情報のエリアがそこに同意の一文を追加します（[法務ページ](/docs/features/legal-pages)）。顧客アプリの概要ページも `src/data/app-overview.ts` で定義し、ライセンスのエリアがそこに自分のセクションと、そのセクションが読み取る検索パラメーターを追加します（[顧客アプリ](/docs/features/customer-app)）。いずれかのエリアがないプロジェクトでは、そのエリアが定義するリストと、ほかのエリアがそこに追加するものが一緒に外れるので、どのエリアも、依存していない別のエリアをインポートしません。

任意のエリアだけが中身を入れるバレルには、コアが空のリストを追加します。`src/data/core.worker.ts`、`core.root.ts`、`core.time-zone.ts`、`core.deploy.ts`、`core.namespaces.ts` です。これにより、それらのエリアがないプロジェクトでも型チェックと lint が通ります。認証のエリアも、自分のプラグインのリストに空の `AUTH_AUTH_PLUGINS` を、登録の案内に空の `AUTH_SIGN_UP_NOTICES` を、概要ページに空の `AUTH_APP_OVERVIEW` を追加し、Polar のエリアは自分の Webhook イベントに空の `POLAR_POLAR_EVENTS` を追加します。メールを送るエリアは、メールの目的の名前を `src/data/<area>.email-purposes.ts` に定義し、`src/data/email-purposes.entries.ts` がそれらを `EMAIL_PURPOSE` にまとめます（[Resend](/docs/integrations/resend)）。

## 環境

`wrangler.jsonc` は 4 つの環境を定義します。`vp dev` と `vp build` で使う環境は `CLOUDFLARE_ENV` で選択します。

| 環境          | バインディング                           | 使用箇所                                        |
| ------------- | ---------------------------------------- | ----------------------------------------------- |
| `development` | リモートのプレビュー用 D1、KV、R2        | `bun run dev`                                   |
| `preview`     | プレビュー用 D1、KV、R2                  | `bun run build:preview`、`deploy:preview`       |
| `production`  | 本番用 D1、KV、R2                        | `bun run build:production`、`deploy:production` |
| `test`        | `.wrangler/test` 内のローカル D1、KV、R2 | `bun run build:test`、Playwright                |

各環境は、必要なシークレットを `secrets.required` に列挙します。値は対応する `.env.<environment>` ファイルから取得され、デプロイスクリプトは空の値やプレースホルダーの値を拒否したうえで、宣言されたキーを `.wrangler/secrets.<environment>.json` に書き出し、そのファイルを `--secrets-file` で Wrangler に渡します。`test` 環境は、エントリーとして `src/platform/testing/worker.ts` を使い、`.env.test` にコミットされたダミー値を使います。`AFFONSO_PROGRAM_ID` は公開情報なので、シークレットではなく `vars` の下の通常の Worker 変数です。設定しているのは `test` だけです。1 つのモジュールのシークレットはまとめて、`.env.example`（`test` では `.env.test`）と同じ順序で並びます。そのため、エリアはシークレットを 1 つのまとまりとして追加できます。`src/__test__/wrangler.test.ts` は名前を順序どおりに比較し、異なると失敗します。まとまりの間の空行は読みやすさのためだけのもので、フォーマッターが削除することもあるため、テストは空行を比較しません。

エリアのバインディングも独立したブロックになります。R2 バケットはエリアのもので、`MEDIA` はコースの、`BUNDLES` はライセンス販売のエリアのものです。そのため、各環境で `r2_buckets` は最後に置かれてエリアごとに 1 つのエントリーを持ち、あるエリアのないプロジェクトではそのエントリーがありません。`wrangler.test.ts` は、`development` と異なる D1 データベース、KV 名前空間、R2 バケットをバインドする環境があっても失敗し、`scripts/verify-bindings.ts` はどのバインディングも名指しせずに、対象環境が宣言するすべてのバインディングをチェックします。

## 型

- `src/types/worker-configuration.d.ts` は `bun run cf-typegen` が `wrangler.jsonc` の `development` 環境から生成し、`DB`、`CACHE`、`MEDIA`、`BUNDLES` のバインディングと `secrets.required` のすべてのシークレットを含む `Cloudflare.Env` を宣言します。`src/types/bindings.d.ts` は、Wrangler が出力しない `ASSETS` を追加します。
- エリアが `src/types/<area>.d.ts` で宣言するのは、Wrangler が導き出せないものだけです。`affiliates.d.ts` は `test` だけが設定する省略可能な `AFFONSO_PROGRAM_ID` 変数、`polar.d.ts` は `POLAR_SERVER` の 2 つの値、`repository-facts.d.ts` は `virtual:repository-facts` モジュールを宣言します。
- `src/types/router.d.ts` は、ルーターの型と `staticData.namespaces` ルートオプションを登録します。

## テストランタイムの配線

`src/platform/testing` には、特定の機能に属させることができないものだけを置きます。

- `setup.ts`：jest-dom のマッチャー、各テスト前のバインディングのリセット、サーバー関数をプロセス内で実行するための `createServerFn` の置き換え
- `mocks/cloudflare.ts`：チェックイン済みのマイグレーションを実行するインメモリ SQLite の D1、インメモリの KV、`wrangler.jsonc` の `test` 環境にある R2 バインディングごとのインメモリのバケット、テストからフラッシュできる `waitUntil`
- `mocks/cache.ts`：`createEdgeCache`。メディア配信のテストで使う Workers のキャッシュのスタブ
- `mocks/resend.ts` と `mocks/polar.ts`：Resend と Polar の API の厳密なテストダブル。それぞれエリアのダブルのリスト（`RESEND_PROVIDER_DOUBLES`、`POLAR_PROVIDER_DOUBLES`）に入っており、`mocks/providers.entries.ts` がコアの空の `CORE_PROVIDER_DOUBLES` と一緒にまとめます。あわせて、すべてのテストとブラウザテスト用の Worker で `fetch` をそれらに振り向け、それらをリセットする `mocks/providers.ts`
- `mocks/wrksz-themes.ts`：テーマライブラリの代替実装
- `lib/`：サーバー関数の RPC ブリッジ、レンダリング用ヘルパー、リクエスト URL 用ヘルパー、クエリランナー、Polar のモデルと署名付きの Webhook
- `worker.ts`：ブラウザテスト用の Worker エントリー。プロバイダーのテストダブルをインストールし、各エリアが `e2e/data/<area>.worker.ts`（`worker.entries.ts`）で宣言するセットアップとテスト用エンドポイントを実行します。ライセンスのエリアは Polar のテストダブルにテスト用のライセンスキーを登録し、Resend は配信されたメールを、ニュースレターは購読者の状態を公開します

各スイートでの使われ方は、[テストと CI](/docs/architecture/testing-architecture)を参照してください。
