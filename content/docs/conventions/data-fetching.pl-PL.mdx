Dane trafiają na ekran przez TanStack Query. Przypadek użycia eksportuje swoje opcje obok funkcji serwerowej, a loader trasy, komponent i test używają tych samych opcji, więc już z samej konstrukcji korzystają z jednego wpisu w cache.

## Opcje zapytań

```ts
export const courseEditorQuery = (input: Course["getCourseEditor"]) =>
  queryOptions({
    queryFn: () => getCourseEditor({ data: input }),
    queryKey: [...COURSE_QUERY_KEYS.EDITOR, input.courseId],
    staleTime: COURSE_STALE_MS,
  })
```

| Rodzaj odczytu                   | Eksport                                                                    | Przykład                                         |
| -------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------ |
| Przyjmuje dane wejściowe         | Funkcja zwracająca opcje, nazwana `<noun>Query`                            | `courseEditorQuery(input)`, `courseQuery(input)` |
| Nie przyjmuje danych wejściowych | Stała nazwana `<noun>Query`                                                | `currentLicenseQuery`                            |
| Lista stronicowana dla tabeli    | `get<Things>PageQuery(input)` oraz pierwsza strona jako `get<Things>Query` | `getOrdersPageQuery`, `getOrdersQuery`           |

## Klucze zapytań

Klucz zaczyna się od prefiksu modułu z `<table>.constants.ts`, potem następuje operacja, a potem każdy parametr wejściowy, który wpływa na wynik:

```ts
queryKey: [...COURSE_QUERY_KEYS.CATALOGUE, input.locale]
queryKey: [...COURSE_QUERY_KEYS.DETAIL, input.locale, input.slug]
queryKey: [...COURSE_QUERY_KEYS.LIST, courseZodSchemas.getCourses.parse(input)]
```

Klucz listy przechowuje sparsowane dane wejściowe, więc `getCoursesPageQuery()` i `getCoursesPageQuery({ pageIndex: 0, pageSize: 10 })` trafiają do tego samego wpisu. Język należy do klucza zawsze wtedy, gdy serwer lokalizuje wynik. Nigdy nie wpisuj klucza bezpośrednio w komponencie: odczytaj go z opcji, a do unieważniania z obiektu `<MODULE>_QUERY_KEYS`.

## Publiczne zapytania [#public-queries]

Zapytanie, którego wynik jest taki sam dla każdego odwiedzającego, niezależnie od tego, kto jest zalogowany, deklaruje `meta: { public: true }`:

```ts title="src/lib/github.ts"
export const starCountQuery = queryOptions({
  gcTime: STAR_COUNT_REFRESH_AFTER_MS,
  meta: { public: true },
  queryFn: () => getStarCount(),
  queryKey: ["github", "stars"],
  staleTime: starCountStaleTime(import.meta.env.MODE),
})
```

Tłumaczenia (`messagesQueryOptions`) i liczba gwiazdek na GitHubie (`starCountQuery`) są publiczne. Każde inne zapytanie należy do zalogowanego użytkownika. Gdy użytkownik się zmienia, `removeUserData` w `auth.session.ts` usuwa te zapytania i wszystkie mutacje, a publiczne zachowuje, więc następny użytkownik nigdy nie zobaczy danych poprzedniego, a prerenderowana strona zachowuje dane, z którymi ją wyrenderowano: flaga jest częścią każdego zapytania, które serwer dehydratuje do strony. Zapytanie bez tej flagi zostaje pobrane ponownie dla następnego użytkownika, co kosztuje jedno żądanie, ale nigdy nie prowadzi do wycieku danych, więc oznaczaj zapytanie jako publiczne tylko wtedy, gdy jego funkcja serwerowa nigdy nie odczytuje sesji. `auth.session.test.ts` wykonuje każde publiczne zapytanie i kończy się błędem, jeśli któreś z nich odczytuje sesję albo jeśli plik źródłowy deklaruje publiczne zapytanie, którego test nie wykonuje. Test wymienia je w `PUBLIC_QUERIES`, a kluczem każdego wpisu jest plik źródłowy, który deklaruje dane zapytanie.

## Świeżość

`getRouter()` w `src/router.tsx` tworzy jeden `QueryClient` na żądanie z czasami cache z `src/integrations/tanstack-query/query.cache.ts`. Router ustawia `defaultPreloadStaleTime` na `ROUTER_PRELOAD_STALE_TIME_MS` i zostawia domyślne `defaultStaleTime`, więc o świeżości danych decydują wyłącznie te czasy cache:

```ts
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      gcTime: QUERY_GC_TIME_MS,
      staleTime: QUERY_STALE_TIME_MS,
    },
  },
})
```

Zapytanie, które potrzebuje innej świeżości, ustawia `staleTime` nazwaną stałą, która mówi dlaczego: `PLAYBACK_STALE_MS` (godzina, w granicach czasu życia podpisanego adresu URL odtwarzania), `STAR_COUNT_REFRESH_AFTER_MS` dla liczby gwiazdek na GitHubie (w buildzie testowym `starCountStaleTime` zamienia ją na `Infinity`), `Infinity` dla komunikatów tłumaczeń, które zmieniają się tylko przy wdrożeniu. Nigdy nie twórz `QueryClient` na poziomie modułu; na serwerze współdzieliłby dane jednego użytkownika z kolejnym żądaniem.

## Loadery pobierają z wyprzedzeniem, komponenty odczytują

Loader strony pobiera z wyprzedzeniem zapytania, które odczytują jego komponenty: te, których potrzebuje pierwsza część odpowiedzi, w jednym `Promise.all` opisanym na stronie [Pliki tras](/docs/conventions/routes), a pozostałe bez czekania na nie, tak aby docierały strumieniowo ([Sekcje przesyłane strumieniowo](/docs/conventions/routes#streamed-sections)). Z `src/routes/app.license.tsx`:

```ts
context.queryClient.query({ ...currentLicenseQuery, staleTime: "static" })
```

`staleTime: "static"` sprawia, że loader zwraca dane z cache, zamiast pobierać je ponownie. Komponent odczytuje następnie te same opcje i stosuje własny `staleTime` zapytania:

```tsx
const { license } = useSuspenseQuery(currentLicenseQuery).data
```

Dzięki temu strona, której dane są już w cache, renderuje się od razu po przejściu, a nieaktualne dane odświeżają się w tle, zamiast wstrzymywać nawigację.

Odczyt `"static"` ignoruje też unieważnianie: zwraca dane z cache nawet po tym, jak mutacja je unieważniła, a świeże dane docierają dopiero wtedy, gdy komponent pobierze je ponownie. Dlatego loader czeka na zapytanie z jego własnym `staleTime`, gdy strona nie może pokazać danych sprzed ostatniej akcji odwiedzającego albo gdy loader sam potrzebuje danych, do tytułu lub do odpowiedzi 404. Tak robią strony kursów i edytor kursów w panelu administracyjnym, bo po ukończeniu lekcji lub zapisaniu edytora następny ekran musi pokazać zaktualizowany program:

```ts
context.queryClient.query(courseQuery({ locale, slug: params.course })).catch(rethrowAsNotFound)
```

- Używaj `useSuspenseQuery` dla danych pobranych z wyprzedzeniem przez loader, a `useQuery` tylko dla danych, które mogą dotrzeć później bez blokowania strony, jak liczba gwiazdek w `proof-section.tsx`. Zapytanie, które loader przesyła strumieniowo, zawsze odczytuje się przez `useSuspenseQuery` wewnątrz granicy `Suspense`; odczytane przez `useQuery` renderowałoby się na serwerze bez danych, a w przeglądarce z danymi.
- Nie pobieraj danych w `useEffect` i nie przekazuj wyników zapytań w dół przez właściwości: każdy komponent wywołuje opcje, których potrzebuje.
- `DataGrid` otrzymuje funkcję, która z jego żądania tworzy opcje, `query={(request) => getOrdersPageQuery(orderZodSchemas.getOrders.parse(request))}`, i sam wykonuje zapytanie.

## Mutacje i unieważnianie

Komponent rozwija opcje mutacji w `useMutation` operatorem spread i dodaje tylko własne callbacki. Po udanym zapisie unieważnia prefiks modułu, a następnie pokazuje komunikat:

```tsx
const update = useMutation({
  ...updateCourseMutation,
  onError,
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL })
    toast.success(t("saved"))
  },
})
```

- Unieważniaj najwęższy prefiks, który obejmuje każdy ekran pokazujący zmienione dane. Mutacje rozdziałów i lekcji unieważniają `COURSE_QUERY_KEYS.ALL`, ponieważ pokazują je edytor kursu i publiczne strony kursów. `useLessonProgress` unieważnia tylko `COURSE_QUERY_KEYS.DETAIL` i tylko wtedy, gdy lekcja zostanie ukończona.
- Czekaj na zakończenie unieważniania, zanim przejdziesz na inną stronę lub zamkniesz okno dialogowe, aby następny ekran wyrenderował świeże dane.
- Błędy przechodzą przez `useErrorMessage()`; zobacz [Funkcje serwerowe i błędy](/docs/conventions/server-functions).
- Nigdy nie aktualizuj cache ręcznie, żeby upozorować wynik. Jedynym wyjątkiem jest sesja: gdy zmienia się zalogowany użytkownik, `loadRouteSession` w `auth.routes.ts` usuwa dane poprzedniego użytkownika za pomocą `removeUserData` i zapisuje nową sesję, więc żadne prywatne dane nie przetrwają wylogowania ani zmiany konta. Zobacz [Publiczne zapytania](#public-queries).
