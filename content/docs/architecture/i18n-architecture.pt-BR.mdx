## Locales e URLs

O SaaSy Land atende <RepositoryFact name="languages" /> locales, <RepositoryFact name="supportedLocales" />, com `en-US` como padrão. O locale padrão não tem prefixo (`/docs`); todos os outros usam a tag completa (`/pl-PL/docs`). O Worker redireciona prefixos só de idioma e prefixos do locale padrão, como `/pl/docs` ou `/en-US/docs`, para a URL canônica.

`getCurrentLocale()` é isomórfica e lê o locale do caminho da URL nos dois lados, recorrendo a `en-US` quando o caminho não tem prefixo de locale. As URLs de `/api` e de server functions nunca têm um, então no servidor ela retorna `en-US` para essas requisições. O Worker mantém o cookie de locale sincronizado com a URL da página, mas nenhum código escolhe um locale a partir do cookie. Server functions que retornam conteúdo localizado recebem o locale como entrada, e os e-mails de autenticação o leem do `callbackURL` do fluxo.

## Mensagens

As traduções ficam em `messages/<locale>/<namespace>.json`. O nome do arquivo é o namespace, por exemplo `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` ou `common`. Namespaces com pontos são mesclados em uma única árvore de mensagens, então `useTranslations("pages.admin.users")` lê `pages.admin.users.json`. Todo namespace de página tem `metadata.title` e `metadata.description` para as tags de head. As mensagens são JSON puro, sem tipos gerados.

## Carregamento

- **Namespaces raiz** (`common`, `components.*`, `errors*`) são pré-carregados no `beforeLoad` da raiz.
- **Rotas de página** declaram `const NAMESPACE = "pages.x"`, pré-carregam esse namespace no loader e o listam em `staticData.namespaces`.
- **Rotas de layout** declaram `const NAMESPACES = [...] as const` e fazem o mesmo.
- **`TranslationsProvider`** envolve o body do documento no shell raiz. Ele combina os namespaces raiz com os `staticData.namespaces` das rotas correspondentes e passa o resultado para o `IntlProvider`, de modo que toda tela, inclusive as telas de erro, seja traduzida.
- **E-mails** carregam seu namespace no servidor com `loadNamespace`, dentro do caso de uso que os envia.

## Links

Os links do router não precisam de tratamento de locale: `<Link to={ROUTES.SIGN_IN}>` recebe o prefixo pelo `rewrite` do router. Uma URL bruta no locale atual, como um `callbackURL` do Better Auth, também vem do router, que aplica o mesmo rewrite e serializa os parâmetros de busca (`useAuthRedirect` em `src/hooks/use-auth-redirect.ts`):

```ts
const { publicHref: callbackURL } = router.buildLocation({ search: { redirect }, to: ROUTES.AUTH_CALLBACK })
```

`localizePathname({ locale, pathname })` monta uma URL para um locale específico: os links do seletor de idioma e os links em e-mails, que o servidor monta sem router.

O seletor de idioma renderiza um link simples para o mesmo caminho em cada locale, então trocar de idioma carrega um novo documento.

## Traduções nos componentes

Um componente chama `useTranslations` exatamente uma vez e chama o tradutor de `t`. O i18n-ally redefine o escopo de toda chamada a `t()` que vem depois de uma nova chamada a `useTranslations`, e `bun run check:i18n` falha quando uma chave não se resolve no seu escopo. Um componente que precisa de dois namespaces não relacionados usa o pai comum deles ou `useTranslations()` com as chaves completas.

`bun run check:i18n` executa três scripts: `check-i18n.ts` (paridade de chaves entre os locales, resolução das chaves por escopo e chaves que nenhum arquivo do código-fonte renderiza), `check-message-formats.ts` (sintaxe das mensagens ICU) e `check-content.ts` (paridade da documentação e do blog entre os locales).
