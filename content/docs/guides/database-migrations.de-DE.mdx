---
title: "Datenbankmigrationen"
description: "Ein Drizzle-Schema ändern, die SQL-Migration generieren und auf jede D1-Datenbank anwenden."
---

Cloudflare D1 (SQLite) ist die Anwendungsdatenbank. Modulschemas verwenden `drizzle-orm/sqlite-core`, `src/integrations/drizzle-orm/drizzle.schemas.ts` sammelt sie, und drizzle-kit schreibt Migrationen mit Zeitstempel-Präfix nach `src/integrations/drizzle-orm/migrations/`.

## Ablauf

1. `<table>.schema.ts` ändern. Eine neue Tabelle zusätzlich aus `drizzle.schemas.ts` exportieren.
2. Das SQL generieren:

```sh
bun run db:generate
```

3. Die generierte Datei prüfen und zusammen mit der Schemaänderung committen.
4. Sie auf die Datenbank anwenden, mit der gearbeitet wird. `deploy:preview`, `deploy:production` und die CI wenden sie vor dem Deployment auf die Preview- oder Produktionsdatenbank an.

## Befehle

| Befehl                          | Datenbank                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------- |
| `bun run db:migrate:local`      | Lokale Entwicklungsdatenbank in `.wrangler/state`, genutzt von `bun run dev`                |
| `bun run db:reset:local`        | Löscht die lokale Entwicklungsdatenbank und migriert sie anschließend neu                   |
| `bun run db:migrate:test`       | Lokale Testdatenbank in `.wrangler/test`, genutzt von Playwright und der isolierten Preview |
| `bun run db:reset:test`         | Löscht `.wrangler/test` und migriert und befüllt die lokale Testdatenbank anschließend neu  |
| `bun run db:migrate:preview`    | Remote-Preview-Datenbank                                                                    |
| `bun run db:migrate:production` | Remote-Produktionsdatenbank                                                                 |

`bun run db:migrations:local`, `db:migrations:preview` und `db:migrations:production` listen die Migrationen auf, die eine Datenbank noch nicht angewendet hat. `bun run db:studio:local` öffnet Drizzle Studio auf der lokalen Datenbankdatei. `db:studio:preview` und `db:studio:production` öffnen es auf einer Remote-Datenbank, und die `db:introspect:*`-Skripte introspektieren sie, beide über die D1-HTTP-API mit `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` und `CLOUDFLARE_ACCESS_TOKEN` aus der passenden Umgebungsdatei. Siehe [Datenbank](/docs/tooling/database).

## Schema-Konventionen

- Datumswerte sind `integer(..., { mode: "timestamp_ms" })` mit dem Standardwert `(unixepoch() * 1000)`. Tabellen erhalten `createdAt` und `updatedAt` über `...timestamps()` aus `src/integrations/drizzle-orm/drizzle.columns.ts`.
- Boolesche Werte sind `integer(..., { mode: "boolean" })`.
- Indizes, Unique-Constraints, Fremdschlüssel und Relationen bleiben in der Schemadatei.
- D1 kennt keine interaktiven Transaktionen. Eine Operation mit einer einzigen SQL-Anweisung oder `db.batch([...])` atomar halten, wie es `getUsers` und der Rate-Limiter tun.

## Tests

Das Test-D1-Binding wendet jede SQL-Datei im Migrationsordner auf eine In-Memory-SQLite-Datenbank an, sodass D1-gestützte Tests gegen das migrierte Schema laufen. `src/integrations/drizzle-orm/__test__/` prüft, dass das Schema, seine Indizes und seine Fremdschlüssel tatsächlich angelegt werden. Das dortige `migrations.test.ts` beschränkt die Migration, die die Tabellen `order` und `subscription` hinzufügt, auf `CREATE`-Anweisungen für diese Tabellen und ihre Indizes und prüft auf einer Datenbank, die bis zur vorhergehenden Migration migriert ist, dass jede frühere Tabelle und jeder frühere Index unverändert bleibt. Die Migration, die die Lizenznachweise hinzufügt, beschränkt es auf drei `ALTER TABLE … ADD`-Anweisungen für Spalten, die NULL zulassen, und prüft, dass jede andere Tabelle, jeder Index und eine bestehende Lizenz unverändert bleiben und die neuen Spalten leer sind. Die Migration, die die Kursinhalte hinzufügt, beschränkt es auf ein `CREATE TABLE` und ein `CREATE INDEX` für `lesson_attachment`, auf die nur `ALTER TABLE … ADD`-Anweisungen für Spalten mit Standardwerten folgen, und prüft, dass jede andere Tabelle, jeder andere Index sowie ein bestehender Kurs, ein bestehendes Kapitel, eine bestehende Lektion und ein bestehendes Video unverändert bleiben und die neuen Spalten ihre Standardwerte haben und dass das Löschen einer Lektion ihre Materialien löscht. Die Migration, die die erste kostenpflichtige Lektion erfasst, beschränkt es auf zwei `ALTER TABLE … ADD`-Anweisungen für Spalten von `license`, die NULL zulassen, und prüft, dass jede andere Tabelle, jeder Index und eine bestehende Lizenz unverändert bleiben und die neuen Spalten leer sind. Siehe [Tests schreiben](/docs/guides/writing-tests).

## Bestehende PostgreSQL-Daten

Diese Migrationen erzeugen nur das SQLite-Schema. Das Übertragen von Daten aus einer früheren PostgreSQL-Installation erfordert einen separaten, geprüften Export und Import.
