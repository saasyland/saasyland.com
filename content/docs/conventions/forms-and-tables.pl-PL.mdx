Formularze i tabele to dwa miejsca, w których ręcznie pisane warianty mnożą się najszybciej. Każde z nich buduje się w jeden sposób, zaczerpnięty z przewodników samych dostawców, a nie wymyślony tutaj.

## Formularze

Każdy formularz stosuje [przewodnik shadcn dla TanStack Form](https://ui.shadcn.com/docs/forms/tanstack-form): `useForm` z `@tanstack/react-form`, schemat Zod modułu jako walidator oraz `Field`, `FieldLabel`, `Input`, `Textarea` lub `Select` z shadcn. `src/presentation/components/custom/admin/courses/course-form.tsx`:

```tsx
const form = useForm({
  defaultValues: course === undefined ? NEW_COURSE : toValues(course),
  listeners: { onBlur: validateOnBlur },
  onSubmit: ({ value }) => {
    if (course === undefined) {
      create.mutate(value)
      return
    }
    update.mutate({ ...value, courseId: course.id })
  },
  validators: { onChange: courseZodSchemas.createCourse },
})

return (
  <form
    noValidate
    onSubmit={(event) => {
      void submitForm(event, form)
    }}
  >
```

- **Schemat formularza to schemat serwera.** Walidatorem jest ten sam `courseZodSchemas.createCourse`, którym parsuje dane funkcja serwerowa, lub jego `.pick(...)`, tak jak w `chapter-dialog.tsx` z `chapterZodSchemas.updateChapter.pick({ title: true })`. Nigdy nie pisz drugiego schematu tylko dla formularza.
- **Jeden walidator, `onChange`.** TanStack Form uruchamia go przy każdej zmianie i ponownie przy wysyłce. Nie dodawaj jego kopii w `onSubmit`: błąd z walidatora wysyłki znika dopiero wtedy, gdy zmieni się jego własne pole, więc błąd obejmujący kilka pól, taki jak `passwordsMustMatch`, pozostawał czerwony po poprawieniu drugiego pola.
- **Waliduj pole, które odwiedzający opuszcza.** `listeners: { onBlur: validateOnBlur }` uruchamia ten sam walidator, gdy pole traci fokus, więc pole, przez które odwiedzający tylko przeszedł, dostaje swój błąd właśnie w tej chwili, a nie przy późniejszym naciśnięciu klawisza w innym polu.
- **Wysyłaj przez `submitForm`.** `submitForm(event, form)` z `src/integrations/tanstack-form/form.submit.ts` zatrzymuje wbudowaną wysyłkę przeglądarki i wywołuje `form.handleSubmit()`. Gdy formularz jest nieprawidłowy, oznacza wszystkie pola jako opuszczone, więc wszystkie błędy pojawiają się naraz, i przenosi fokus na pierwszą kontrolkę z `aria-invalid="true"`.
- **`noValidate`.** Wbudowana walidacja przeglądarki jest wyłączona, więc każdy komunikat pochodzi ze schematu i jest przetłumaczony.
- **Wartości domyślne są typowane przez interfejs modułu**, jako `NEW_COURSE: Course["createCourse"]`.
- **Wysyłaj przez mutację.** `onSubmit` wywołuje `mutate` z opcji mutacji, a przycisk wysyłki pokazuje stan oczekiwania: `<Button isPending={create.isPending || update.isPending} type="submit">`.

### Kiedy pojawiają się błędy

Błędy stosują zasadę „nagradzaj wcześnie, karz późno”:

- Gdy odwiedzający pisze w polu, pole nie pokazuje błędu i nie ma `aria-invalid`, nawet jeśli wartość nie jest jeszcze prawidłowa.
- Gdy odwiedzający opuści pole albo spróbuje wysłać formularz, pole pokazuje swój błąd.
- Od tej chwili pole jest walidowane ponownie przy każdej zmianie, więc błąd znika przy tym naciśnięciu klawisza, które poprawia wartość.
- Informacja zwrotna nagradzająca postęp, taka jak lista wymagań hasła, aktualizuje się od pierwszego naciśnięcia klawisza: to nie jest błąd.
- Błędy serwera, takie jak adres e-mail, który jest już zarejestrowany, pokazuje toast.

`isFieldInvalid(field)` z `src/integrations/tanstack-form/form.fields.ts` to jedyne miejsce, które o tym decyduje: `field.state.meta.isBlurred && !field.state.meta.isValid`. Nie kopiuj sprawdzenia `isTouched` z przewodnika shadcn: TanStack Form ustawia `isTouched` przy pierwszym naciśnięciu klawisza, przez co wpisane do połowy hasło robiło się czerwone.

### Pola

Każde pole to `Field` z shadcn, którego stan nieprawidłowości pochodzi z `isFieldInvalid`. Z `course-fields.tsx`:

```tsx
<Field data-invalid={isFieldInvalid(field)}>
  <FieldLabel htmlFor={id}>{label}</FieldLabel>
  <Input
    aria-describedby={`${id}-error`}
    aria-invalid={isFieldInvalid(field)}
    className={cn({ "font-mono": isCode })}
    id={id}
    lang={lang}
    name={field.name}
    onBlur={field.handleBlur}
    onChange={(event) => {
      field.handleChange(event.target.value)
    }}
    value={field.state.value ?? ""}
  />
  <FieldMessage field={field} id={id} />
</Field>
```

- `data-invalid`, `aria-invalid` i element błędu odczytują `isFieldInvalid(field)`, więc czytnik ekranu ogłasza, że pole jest nieprawidłowe, dokładnie wtedy, gdy pojawia się błąd, a nigdy wtedy, gdy odwiedzający jeszcze pisze.
- Każda kontrolka wywołuje `field.handleBlur` w `onBlur`; selektor plików wywołuje go po wybraniu pliku.
- Pole wejściowe zawsze kieruje `aria-describedby` na ID swojego błędu. Element błędu renderuje się tylko wtedy, gdy pole jest nieprawidłowe, a odwołanie do nieistniejącego elementu niczego nie opisuje.
- Błędy renderuje `ValidationFieldError` z `custom/validation-field-error.tsx`. Komunikaty Zod są kluczami tłumaczeń, więc wyszukuje je w przestrzeni nazw `<table>.validations` modułu i interpoluje liczby z `<MODULE>_VALIDATION_PARAMS`:

```tsx
<ValidationFieldError
  id={`${id}-error`}
  message={fieldErrorMessage(field.state.meta.errors)}
  namespace="course.validations"
  params={COURSE_VALIDATION_PARAMS}
/>
```

- Żadnych ręcznie pisanych elementów `<input>`, `<label>` ani `<button>` i żadnego komponentu opakowującego jedno pole dla jednego formularza. Komponent pola współdzielony przez kilka formularzy jednego obszaru znajduje się w jednym pliku, tak jak `CourseTextField`, `CourseTextAreaField` i `CourseOptionField` dla formularzy kursu, rozdziału i lekcji.
- Błędy serwera pokazuje `toast.error(errorMessage(error))`, a sukces przetłumaczony `toast.success`.

### Przyciski wysyłki pozostają aktywne

Przycisk wysyłki nigdy nie jest wyłączany dlatego, że formularz jest niekompletny: żadnego `isDisabled`, `disabled` ani `aria-disabled`, gdy brakuje wartości lub są nieprawidłowe. Przygaszony przycisk nie mówi, co jest nie tak, a GOV.UK, NN/g i Adrian Roselli odradzają takie rozwiązanie. Naciśnięcie go mimo błędów to zwykła próba wysyłki: `submitForm` pokazuje wszystkie błędy i przenosi fokus na pierwsze nieprawidłowe pole. Przycisk wyłącza tylko `isPending`, dopóki trwa żądanie.

Komponent `Button` z shadcn ustawia `preventFocusOnPress` na przycisku z `type="submit"`, więc naciśnięcie go myszą lub palcem zostawia fokus w edytowanym polu. Inaczej błąd, który pojawia się po opuszczeniu tego pola, przesunąłby przycisk, zanim naciśnięcie się skończy, i naciśnięcie niczego by nie wysłało.

### Błędy serwera przy polu

Gdy serwer odrzuca jedno pole, błąd należy pokazać pod tym polem, a nie w toaście. Formularze rejestracji, resetowania hasła i hasła w ustawieniach robią tak w przypadku hasła znalezionego w znanym wycieku danych, z `onError` mutacji w `onSubmit`. Z `sign-up-form.tsx`:

```tsx
onError: (error) => {
  if (error.message === AUTH_ERRORS.PASSWORD_COMPROMISED) {
    showFieldError(formApi, { controlId: "sign-up-password", field: "password", message: error.message })
    return
  }
  toast.error(errorMessage(error))
},
```

- `showFieldError` z `src/integrations/tanstack-form/form.submit.ts` zapisuje klucz komunikatu jako błąd wysyłki pola, oznacza pole jako opuszczone, aby `isFieldInvalid` je pokazało, i przenosi fokus na kontrolkę.
- Klucz jest wyszukiwany jak każdy inny komunikat walidacji, więc potrzebuje wpisu w przestrzeni nazw walidacji pola, tutaj `auth.validations.passwordCompromised`.
- Błąd znika przy następnej zmianie tego pola, a wszystkie pozostałe błędy serwera nadal są toastami.

Najmniejszym kompletnym przykładem jest `src/presentation/components/custom/newsletter-form.tsx`; [przewodnik po formularzach](/docs/guides/forms-and-validation) pokazuje krok po kroku, jak go zbudować.

## Tabele

Każda tabela to generyczny `DataTable` z `src/presentation/components/custom/data-table.tsx`, używany bezpośrednio na stronie:

```tsx
<DataTable columns={courseColumns} options={{ query: ({ pageIndex, pageSize }) => getCoursesPageQuery({ pageIndex, pageSize }) }} />
```

Jego właściwości to cały interfejs:

| Właściwość | Zawartość                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------- |
| `columns`  | Zestaw kolumn z `<entity>-columns.tsx`                                                                              |
| `data`     | Wiersze już obecne w pamięci, dla tabeli stronicowanej po stronie klienta                                           |
| `options`  | `query` (ze stanu strony tworzy opcje zapytania, do stronicowania po stronie serwera), `selectable`, `initialState` |
| `filters`  | Kontrolki wyszukiwania i wyboru powiązane z ID kolumn                                                               |

`DataTable` jest wzorowany na [tabeli danych React Aria z shadcn](https://ui.shadcn.com/docs/components/aria/data-table): `tableFeatures` i `useTable` z TanStack Table v9, renderowane prymitywami tabeli shadcn. Stronicowanie, sortowanie, filtrowanie, zaznaczanie, wiersze ładowania i pasek paginacji znajdują się w jego wnętrzu. Nie pisz osobnego komponentu tabeli, nagłówka, wiersza ani paginacji dla jednej strony i nie dodawaj opcji, której żadna strona jeszcze nie używa.

### Kolumny

Zestaw kolumn znajduje się w `custom/<area>/<entity>-columns.tsx` i jest budowany przez `createColumnHelper<DataTableFeatures, Row>()`, gdzie typ wiersza pochodzi z interfejsu modułu (`Course["listRow"]`):

```tsx
export const courseColumns = columnHelper.columns([
  columnHelper.accessor("title", { cell: TitleCell, enableSorting: false, header: () => <CourseHeader id="course" /> }),
  columnHelper.accessor("kind", { cell: KindCell, enableSorting: false, header: () => <CourseHeader id="kind" /> }),
  columnHelper.accessor("status", { cell: StatusCell, enableSorting: false, header: () => <CourseHeader id="status" /> }),
  columnHelper.accessor("lessons", { cell: LessonsCell, enableSorting: false, header: () => <CourseHeader id="lessons" /> }),
  columnHelper.accessor("updatedAt", { cell: UpdatedCell, enableSorting: false, header: () => <CourseHeader id="updated" /> }),
  columnHelper.display({ cell: ActionsCell, header: DataTableActionsHeader, id: "actions" }),
])
```

- Każda komórka to mały komponent w tym samym pliku, który sam odczytuje swoje tłumaczenia (`KindCell`, `StatusCell`), a w przypadku akcji także własne mutacje (`ActionsCell`).
- Etykiety nagłówków pochodzą z komponentu nagłówka, który odczytuje przestrzeń nazw strony, nigdy z tekstów w definicji kolumny.
- Kolumna akcji używa `DataTableActionsHeader`, który podaje czytnikom ekranu nazwę kolumny.
- Akcje złożone wyłącznie z ikony mają `aria-label`, który nazywa wiersz: `t("actions.edit", { title })`.
