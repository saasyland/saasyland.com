Eine E-Mail besteht aus drei Teilen: einer Vorlage in `src/presentation/emails/`, einem Message-Namespace in `messages/<locale>/emails.<name>.json` und dem Use Case, der die Messages lädt, die Vorlage rendert und die E-Mail versendet. Die Seite [Resend](/docs/integrations/resend) listet jede Vorlage mit dem Use Case auf, der sie versendet.

## Vorlage

Eine Vorlage enthält nur Markup und exportiert ihren Namespace. Sie übersetzt mit `createTranslator` aus `use-intl`, weil sie außerhalb des React-Kontexts rendert. Jede Vorlage rendert in `EmailLayout` aus `src/presentation/emails/email-layout.tsx`, das Sprache, Vorschautext, Tailwind und den zentrierten Container einmal für alle festlegt. `src/presentation/emails/verify-email.tsx`:

```tsx title="src/presentation/emails/verify-email.tsx"
import type { JSX } from "react"

import { Button, Heading, Section, Text } from "react-email"
import { createTranslator } from "use-intl"

import { EMAIL_LINK_LIFETIME_HOURS } from "~/src/integrations/better-auth/auth.constants"
import type { SupportedLocale } from "~/src/integrations/use-intl/i18n.config"

import type emailMessages from "~/messages/en-US/emails.verify-email.json"
import { APP_NAME } from "~/src/presentation/branding"
import { EmailBrandHeader } from "~/src/presentation/emails/email-brand-header"
import { EmailFallbackLink } from "~/src/presentation/emails/email-fallback-link"
import { EmailLayout } from "~/src/presentation/emails/email-layout"

export const VERIFY_EMAIL_NAMESPACE = "emails.verify-email"

interface VerifyEmailProps {
  readonly locale: SupportedLocale
  readonly messages: typeof emailMessages
  readonly name: string
  readonly verifyUrl: string
}

export const VerifyEmail = ({ messages, locale, name, verifyUrl }: Readonly<VerifyEmailProps>): JSX.Element => {
  const t = createTranslator({ locale, messages: { emails: { "verify-email": messages } }, namespace: "emails.verify-email" })

  return (
    <EmailLayout lang={locale} preview={t("preview", { appName: APP_NAME })}>
      <EmailBrandHeader />
      <Section>
        <Heading className="m-0 mb-4 text-2xl font-bold">{t("heading")}</Heading>
        <Text className="m-0 mb-6 text-base text-neutral-600">{t("body", { name })}</Text>
        <Button href={verifyUrl} className="box-border rounded-md bg-neutral-900 px-5 py-3 text-center text-base text-white no-underline">
          {t("button")}
        </Button>
        <Text className="mt-6 mb-0 text-base text-neutral-600">{t("expiry", { hours: EMAIL_LINK_LIFETIME_HOURS })}</Text>
        <EmailFallbackLink label={t("fallback")} url={verifyUrl} />
        <Text className="mt-6 text-sm text-neutral-500">{t("footer")}</Text>
      </Section>
    </EmailLayout>
  )
}
```

## Messages

`messages/<locale>/emails.<name>.json` in jeder Locale anlegen. Einen Schlüssel `subject` aufnehmen; der Use Case übersetzt ihn getrennt vom Inhalt.

```json title="messages/en-US/emails.verify-email.json"
{
  "subject": "Verify your email address",
  "preview": "Verify your email for {appName}",
  "heading": "Verify your email",
  "body": "Hi {name}, thanks for signing up. Confirm your email address to finish setting up your account.",
  "button": "Verify email",
  "expiry": "The link works for {hours, plural, one {# hour} other {# hours}}.",
  "fallback": "If the button does not work, copy this link into your browser:",
  "footer": "If you did not create an account, you can safely ignore this email."
}
```

E-Mail-Namespaces werden nie von Routen vorgeladen; der versendende Use Case lädt sie auf dem Server.

## Versand

Der Use Case entnimmt die Locale der Callback-URL, die er erhält, prüft das Limit pro Empfänger, lädt die Messages, baut absolute Links mit `localizePathname` und ruft `sendEmail` auf. `src/modules/verification/use-cases/send-verify-email.ts`:

```ts title="src/modules/verification/use-cases/send-verify-email.ts"
export const sendVerifyEmail = async ({
  callbackURL,
  token,
  user,
}: {
  callbackURL: string
  token: string
  user: { email: string; name: string }
}): Promise<void> => {
  if (!(await withinRecipientRateLimit({ kind: VERIFICATION_EMAIL_PURPOSE.VERIFY_EMAIL, recipient: user.email }))) {
    console.warn("[email] verification email not sent: the recipient reached the hourly limit")
    return
  }

  const callback = new URL(callbackURL, getRequest().url)
  const locale = extractLocaleFromPath(callback.pathname) ?? I18N.DEFAULT_LOCALE
  const verifyUrl = new URL(localizePathname({ locale, pathname: ROUTES.VERIFY_EMAIL }), getRequest().url)
  verifyUrl.search = callback.search
  verifyUrl.searchParams.set("token", token)

  const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })

  await sendEmail({
    idempotency: { purpose: VERIFICATION_EMAIL_PURPOSE.VERIFY_EMAIL, token: crypto.randomUUID() },
    react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
    subject: createTranslator({ locale, messages })("subject"),
    to: user.email,
  })
}
```

`sendEmail` (`src/integrations/resend/resend.utils.ts`) versendet über Resend mit dem Absender `RESEND_EMAIL_FROM`, sofern kein `from` angegeben ist, übergibt den Idempotenzschlüssel, damit ein erneuter Versuch nie doppelt sendet, und wirft einen Fehler, wenn Resend einen Fehler zurückgibt.

Die Bestätigungs-E-Mail bekommt bei jedem Versand einen eigenen Schlüssel aus `crypto.randomUUID()`, wie die E-Mails zu einem bestehenden Konto und zu einem geänderten Passwort: Better Auth signiert seine Bestätigungstokens mit sekundengenauen Zeitstempeln, sodass eine Registrierung und eine Anmeldung in derselben Sekunde dasselbe Token tragen und Resend die zweite E-Mail als Wiederholung der ersten behandeln würde.

## Wer was versendet

- Better-Auth-Hooks in `src/integrations/better-auth/auth.server.ts` rufen die Use Cases direkt auf: `sendVerifyEmail` für `emailVerification.sendVerificationEmail` und wiederholte Registrierungen nicht verifizierter Konten, `sendExistingAccountEmail` für wiederholte Registrierungen verifizierter Konten, `sendResetPasswordEmail` für `emailAndPassword.sendResetPassword`, `sendPasswordChangedEmail` für `emailAndPassword.onPasswordReset`, `sendChangeEmailConfirmationEmail` für `user.changeEmail` und `sendDeleteAccountEmail` für `user.deleteUser.sendDeleteAccountVerification`.
- Better-Auth-Requests kommen ohne Locale-Präfix bei `/api/auth` an, daher ermitteln die Hooks die Locale der E-Mail aus der `callbackURL` des Ablaufs, einem lokalisierten Seitenpfad, mit `extractLocaleFromCallbackURL` oder `extractLocaleFromPath` aus `src/integrations/use-intl/i18n.paths.ts`. Fallback ist Englisch.
- Die Newsletter-Use-Cases versenden die Bestätigungs- und Benachrichtigungs-E-Mails des Newsletters selbst, zum Beispiel `subscribeToNewsletter`.
- Der Webhook-Handler `onOrderPaid` des Lizenzbereichs ruft `sendPurchaseConfirmationEmail` auf, nachdem er die Lizenz vergeben hat. Die E-Mail nimmt ihre Locale aus `metadata.locale` der Bestellung, ihre Links vom Host, der den Webhook empfangen hat, und ihr Idempotenz-Token aus der Polar-Bestell-ID, und ein fehlgeschlagener Versand lässt den Handler fehlschlagen, damit Polar es erneut versucht.
- Passt eine bezahlte Lizenzbestellung zu keinem Konto, vergibt `onOrderPaid` nichts und ruft `sendUnmatchedOrderAlert` auf, das den Betreiber der Website auf Englisch warnt.
- `recordWithdrawal`, das `submitWithdrawal` aufruft, sendet die Eingangsbestätigung einer Widerrufserklärung in der Sprache der Seite, von der sie gesendet wurde, und die Benachrichtigung über den Widerruf auf Englisch an den Betreiber der Website. Ein fehlgeschlagener Versand wird protokolliert und lässt die Erklärung nicht scheitern.
- `createInvitation` und `resendInvitation` rufen `sendInvitationEmail` mit der Sprache auf, die der Admin gewählt hat und die an der Einladung gespeichert ist. Das Idempotenz-Token ist das Token des Links, daher ist jeder neue Link eine neue E-Mail, und über dem Limit pro Empfänger schlägt der Versand mit `TOO_MANY_REQUESTS` fehl, statt die E-Mail auszulassen.
- `sendVerifyEmail`, `sendResetPasswordEmail`, `sendExistingAccountEmail` und `subscribeToNewsletter` rufen vor dem Versand `withinRecipientRateLimit` (`src/lib/rate-limit.ts`) auf: höchstens <RepositoryFact name="recipientEmailsPerHour" /> E-Mails einer Art pro Adresse und Stunde, mit einem SHA-256-Hash der Adresse als Schlüssel. Über dem Limit loggen sie eine Warnung und versenden nichts. Füge dieselbe Prüfung zu jeder E-Mail hinzu, die ein Besucher ohne Konto auslösen kann.

## E-Mail hinzufügen

1. Die Vorlage mit ihrem exportierten `<NAME>_NAMESPACE` in `src/presentation/emails/<name>.tsx` anlegen.
2. `messages/<locale>/emails.<name>.json` in jeder Locale hinzufügen.
3. Den Zweck im Objekt `<MODULE>_EMAIL_PURPOSE` in `<module>.constants.ts` des versendenden Moduls benennen, das `email-purposes.test.ts` mit den Zwecken aller anderen Module abgleicht, und die E-Mail aus dem Use Case versenden, dem die Aktion gehört, mit `idempotency: { purpose, token }` und dem auslösenden Token oder der ID des auslösenden Datensatzes.
4. Die Vorlage in `src/presentation/emails/__test__/` testen und den Use Case mit gemocktem `sendEmail`.

Resend-Zugangsdaten: `RESEND_API_KEY` und `RESEND_EMAIL_FROM`. Tests kontaktieren Resend nie.
