title: "Testen"
description: "Zu welchem Vitest-Projekt ein Test gehört, wie Server Functions gegen ein D1 im Arbeitsspeicher getestet werden, die Praxis der Testabdeckung, benannte Konstanten in Assertions und die Browser-Suite."
---

Jede Änderung wird im selben Commit mit den Tests ausgeliefert, die sie belegen, und die Testabdeckung bleibt bei <RepositoryFact name="coverageThreshold" unit="percent" /> für Zeilen, Anweisungen, Funktionen und Verzweigungen. Ein Bugfix kommt mit einem Test, der ohne den Fix fehlschlägt.

## Projekte

`vite.config.ts` definiert drei Vitest-Projekte, ausgewählt über das Dateisuffix. Tests importieren ihre API aus `vite-plus/test` und liegen in `__test__/` neben dem Code, den sie abdecken.

| Suffix                 | Projekt       | Verwenden für                                                                                                                                                                         |
| ---------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | Use Cases, Loader, `head`, Schemas, Hilfsfunktionen: alles, was auf dem Server läuft                                                                                                  |
| `.integration.test.ts` | `integration` | Abläufe von Better Auth, Zahlungen und Lizenzen, den D1-Adapter und das Laden von Nachrichten, mit Timeouts von <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Komponenten und Seiten in jsdom                                                                                                                                                       |

`src/platform/testing/mocks/cloudflare.ts` ersetzt `cloudflare:workers` in jedem Projekt: D1 ist eine `node:sqlite`-Datenbank im Arbeitsspeicher, aufgebaut aus jeder eingecheckten Migration, KV und ein Bucket für jedes R2-Binding der Umgebung `test` in `wrangler.jsonc` sind Speicher im Arbeitsspeicher. `resetTestBindings()` leert vor jedem Test KV, den Bucket und die Rate-Limit-Tabelle, und die Seed-Funktion jeder Suite setzt die Zeilen zurück, von denen sie abhängt. Kein Test spricht mit Cloudflare, Polar, Resend oder einem OAuth-Anbieter: `fetch` erreicht die strikten Test-Doubles in `mocks/resend.ts` und `mocks/polar.ts`, die jede Anfrage gegen die Request-Modelle der SDKs validieren und den Test bei einer Anfrage scheitern lassen, die der Anbieter ablehnen würde. Tests prüfen, was das Double empfangen hat, statt eine SDK-Methode zu mocken, und Auth-Suites steuern die echte Konfiguration aus `auth.server.ts` über `auth.harness.ts`.

## Eine Server Function testen

Rufen Sie sie über ihre exportierten Optionen auf, damit der Test die echte Middleware, Validierung und den echten Handler durchläuft. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts`:

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` und `executeMutation(options, variables)` aus `src/platform/testing/lib/query.ts` führen die Optionen in einem frischen `QueryClient` aus.
- Die Session stammt aus `createAuthSessionFixture` in `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts`; jede Berechtigung wird auch von der Seite getestet, die abgewiesen werden muss (`it("is for staff only")`).
- Seed-Daten liegen in `__test__/fixtures/` des Moduls, mit ihren IDs in benannten Objekten (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` löscht die Zeilen, die ihm gehören, und fügt sie über Drizzle erneut ein, sodass jeder Test vom selben Zustand ausgeht.
- Im Projekt `component` schlägt eine Server Function fehl, weil jsdom für den Browser steht. Komponententests geben einer Route ihre Loader-Daten oder mocken `queryFn` und `mutationFn` der Optionen, die die Komponente liest.

## Assertions verwenden die Namen des Codes

- Erwartete Status, Arten, Rollen und Fehlercodes sind die Konstanten, die der Code verwendet: `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. Ein Test wiederholt nie ein String-Literal der Domäne, und ebenso wenig tun das die E2E-Daten oder der Test-Seed: `e2e/data/courses.ts` schreibt `kind: COURSE_KIND.COURSE`.
- Schematests sind der einzige Ort, an dem ein gespeicherter Wert ausgeschrieben wird: `product.schema.test.ts` legt `expect(PRODUCT_STATUSES).toStrictEqual(["draft", "published", "archived"])` fest, sodass eine Änderung an einem Wert in der Datenbank einen Test scheitern lässt, statt eine Migration zu erfordern, die niemand geschrieben hat.
- Die Browser-Suite importiert ihre Konstanten aus der Anwendung (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`) und kann deshalb nur Dateien importieren, die außerhalb des Workers laden. Die Werte von Polar kommen aus `polar.constants.ts`, das keine Umgebung liest: `e2e/fixtures/polar.ts` und die Journey-Suite in der Sandbox nehmen die Bestellstatus aus `POLAR_ORDER_STATUS`, und die Bestellung selbst stammt aus `src/platform/testing/lib/polar.ts`. Die Produkt-IDs der Stufen sind die Ausnahme: `POLAR_PRODUCT_IDS` liest `cloudflare:workers`, daher liest die Browser-Suite sie aus `.env.test`.
- Komponententests lesen erwartete Texte aus den englischen Nachrichtendateien, wie `admin-course-routes.component.test.tsx` mit `import labels from "~/messages/en-US/pages.admin.courses.json"` und `labels.form.kinds.course`, und finden Elemente über Rolle und zugänglichen Namen.
- Ein Test, der einen Typ braucht, liest ihn aus einer typisierten Quelle oder prüft ihn zur Laufzeit mit `toHaveProperty`; er castet nie.
- Testnamen beschreiben Verhalten als Satz: "lists every course with its lesson count, drafts included".

## Testabdeckung

`bun run test:coverage` schlägt fehl, wenn eine der vier Metriken für `src/**/*.{ts,tsx}` unter <RepositoryFact name="coverageThreshold" unit="percent" /> liegt. Ausgenommen sind Tests, `__test__/`, Deklarationsdateien, `src/routeTree.gen.ts`, die shadcn-Primitive und `src/platform/testing/`. Die Hürde bleibt aussagekräftig:

- **Löschen Sie Verzweigungen, die nie ausgeführt werden können**, statt sie mit Stubs abzudecken. Ein `?? fallback` auf Daten, die immer vorhanden sind, oder ein Optional Chaining auf einem Wert, der nicht `undefined` sein kann, wird aus dem Quellcode entfernt, nicht durch das Stubben eines globalen Objekts erreicht.
- **Decken Sie echtes Verhalten ab.** Ladezustände halten die Anfrage mit `Promise.withResolvers()` offen, prüfen die Lade-UI, lösen innerhalb von `act` auf und prüfen die Ruhe-UI, wie es `expectPending` und `expectIdle` in `auth-forms.component.test.tsx` tun.
- **Behalten Sie Assertions, wenn eine Regel greift.** Überschreitet ein Test `max-statements`, extrahieren Sie einen benannten Helfer, statt Prüfungen wegzulassen.
- **Laden Sie jede Nachrichtendatei.** `i18n.messages.test.ts` lädt jeden Namespace jeder Locale; das deckt die `import.meta.glob`-Zeilen in `i18n.messages.ts` ab. Eine neue Nachrichtendatei wird dadurch automatisch abgedeckt.

## Tests folgen den Bereichen [#tests-follow-the-areas]

Die Bereiche, die ihre eigenen Pfade und Menüeinträge deklarieren (siehe [Pfade und Navigation](/docs/conventions/routes#paths-and-navigation)), besitzen auch ihre Tests. So kann die `saasyland`-CLI einen Bereich samt seinen Tests aus einem generierten Projekt weglassen, und alle übrigen Tests laufen weiter durch.

Eine Testdatei deckt einen Bereich oder eine Quelldatei ab. Die Admin-Seiten eines Bereichs werden mit ihren Skeletons und Breadcrumbs in `src/routes/__test__/admin-<area>-routes.component.test.tsx` getestet, ihre Loader in `admin-<area>-loaders.test.ts`; `admin-layout`, `admin-dashboard` und `admin-loaders` testen die Admin-Oberfläche selbst und nennen keinen Bereich. Voneinander unabhängige Dateien bekommen je eine eigene Testdatei, etwa `background.component.test.tsx` und `wordmark.component.test.tsx`, und jeder API-Handler hat seine eigene: `src/routes/api/__test__/auth.test.ts`, `search.test.ts` und `index.test.ts`. `cli.v1.test.ts` deckt die Routendateien der CLI-Lizenz-API ab; ihr Verhalten wird in `src/modules/license/__test__/license.api.integration.test.ts` getestet.

Eine Liste, die sich über die Bereiche erstreckt, wird pro Bereich deklariert und von einem Barrel zusammengeführt:

| Liste                     | Jeder Bereich deklariert                                                                                                                         | Barrel                             | Gelesen von                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------ |
| Abfragedaten des Admins   | `seed<Area>Queries` und seine Zeilen-Factories in `src/presentation/components/custom/admin/__test__/<area>.fixtures.ts`                         | `fixtures.entries.ts`              | `adminQueryClient()` in `fixtures.tsx`           |
| Enum-Beschriftungen       | `src/integrations/use-intl/__test__/<area>.labels.ts`                                                                                            | `labels.entries.ts`                | `enum-labels.test.ts`                            |
| D1-Zeilen                 | `src/integrations/drizzle-orm/__test__/<area>.rows.ts`                                                                                           | `rows.entries.ts`                  | `d1.integration.test.ts`                         |
| Seiten der Browsertests   | `e2e/data/<area>.pages.ts`                                                                                                                       | `e2e/data/pages.entries.ts`        | `accessibility.spec.ts` und `workspaces.spec.ts` |
| Testdatenbank             | `e2e/data/<area>.seed.ts`                                                                                                                        | `e2e/data/seed.entries.ts`         | `scripts/seed-test.ts`                           |
| Öffentliche Abfragen      | `src/integrations/better-auth/__test__/<area>.public-queries.ts`                                                                                 | `public-queries.entries.ts`        | `auth.session.test.ts`                           |
| Test-Doubles der Anbieter | `src/platform/testing/mocks/<provider>.ts`: eine Liste `<PROVIDER>_PROVIDER_DOUBLES`, jedes Double mit `origin`, `respond` und `reset`           | `mocks/providers.entries.ts`       | `mocks/providers.ts`                             |
| Polar-Katalog             | `src/modules/<module>/__test__/fixtures/<area>.polar-catalogue.ts`: die Produkte, Rabatte und Lizenzschlüssel-Benefits, die der Bereich verkauft | `mocks/polar-catalogue.entries.ts` | `mocks/polar.ts`                                 |
| Test-Worker               | `e2e/data/<area>.worker.ts`: Set-ups und Testendpunkte                                                                                           | `e2e/data/worker.entries.ts`       | `src/platform/testing/worker.ts`                 |

Der Kern trägt zu den Barrels, die nur optionale Bereiche füllen, eine leere Liste bei, `e2e/data/core.seed.ts`, `e2e/data/core.worker.ts`, `mocks/core.providers.ts` und `src/integrations/drizzle-orm/__test__/core.rows.ts`, sodass ein Projekt ohne diese Bereiche weiterhin die Typprüfung besteht, und `scripts/seed-test.ts` startet Wrangler nur, wenn ein Bereich Zeilen anlegt. Das Page Object eines Bereichs kommt mit einer eigenen Fixture: `e2e/fixtures/auth.ts` erweitert das `test` des Kerns aus `e2e/fixtures/test.ts` um `authPage`, und die Specs, die sich anmelden, importieren `test` von dort.

Hilfsfunktionen, die mehrere Bereiche nutzen, gibt es nur einmal: `renderAdmin` und `renderAdminPage` in `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` in `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` und `busyMarkup` in `src/platform/testing/lib/skeleton.tsx` sowie in den Browsertests `AuthPage.signIn`, `BasePage.leaveWhileLoading` und die Fixture `pageWithoutJavaScript`. Die Specs öffentlicher Seiten wie `accessibility.spec.ts` und `theme.spec.ts` melden sich bei keinem Konto an; `workspaces.spec.ts` prüft die Seiten nach der Anmeldung, ihre Barrierefreiheit und ihr Theme.

Ein Test von gemeinsamem Code, der einen Eintrag braucht, den die Bereiche beisteuern, deklariert einen eigenen, statt den eines Bereichs zu lesen. `dashboard-actions.component.test.tsx` ersetzt `ADMIN_DASHBOARD_ACTIONS` durch eine testlokale Aktion, sodass `DashboardActions` und die Aktions-Platzhalter von `AdminDashboardPending` auch in einem Projekt ohne den Produktbereich abgedeckt bleiben, der heute die einzige Dashboard-Aktion deklariert. `server.test.ts`, `root.component.test.tsx` und `vite.test.ts` machen es mit testlokalen Worker-Handlern, Root-Komponenten und Vite-Plugins ebenso, und jeder Bereich testet seine eigenen Einträge in `src/data/__test__/<area>.worker.test.ts` und `<area>.vite.test.ts`. Gemeinsamer Code, den nur optionale Bereiche rendern, bekommt einen eigenen Test: `pending-blocks.component.test.tsx` deckt die Skeletons für Felder, Schalter und Upload-Zonen ab, die die Skeletons der Produkte, der Kurse, der Zahlungen und des Beitragseditors verwenden. Ein Test der gemeinsamen Zugriffskontrolle prüft nur die Statements des Auth-Bereichs und die von Better Auth selbst; jeder Bereich testet die Berechtigungen, die er gewährt, in `src/data/__test__/<area>.access.test.ts`, und `access.website.test.ts` schreibt die Berechtigungen jeder Rolle auf der Website fest.

`auth-plugins.test.ts` deckt die Plugin-Zusammenstellung mit einem Beispiel-Plugin ab, sodass sie auch ohne das Polar-Plugin der Lizenz abgedeckt bleibt, und `navigation.test.ts` erwartet nur die Admin-Gruppen und Footer-Spalten, die Einträge haben. `translations-provider.component.test.tsx` nimmt Namespaces des Kerns als Beispiele, die Auth-Tests nehmen die eigenen Daten und Pfade des Auth-Bereichs, etwa die Sitzungsliste und `/app/settings`, und `media-upload-zone.component.test.tsx` prüft, dass die Upload-Zone der Produkte und des Beitragseditors den Rahmen ihres Skeletons zeichnet.

Die Routen- und Skeleton-Tests der Lizenz ersetzen die Abschnitte des Lizenzangebots durch einen testlokalen, und die Kurstests ersetzen die Kurszugangsfreigaben durch `TEST_COURSE_ACCESS` (`src/modules/course/__test__/fixtures/course-access.ts`), sodass die Tests keines der beiden Bereiche den anderen lesen. `license.course-access.test.ts` deckt ab, was sie verbindet: die Freigabe der Lizenz, mit einem Snapshot dessen, wer welche Lektion ansehen darf, für einen Gast, ein Konto, das Team und jede Lizenzstufe und jeden Lizenzstatus.

Ein Test, der die gesamte Website festschreibt, etwa `navigation.website.test.ts` mit der Reihenfolge jedes Menüs, gehört nur zur Website; die Templates erzeugen ihn nicht.

## Browsertests

Playwright führt den gebauten Test-Worker aus: `bun run build:test` kompiliert ihn mit lokalem D1 und KV unter `.wrangler/test`, `bun run db:reset:test` erstellt diese Datenbank neu und legt die Konten, das Video und den Kurs in `e2e/data` an, und der Test-Einstiegspunkt fängt ausgehende E-Mails unter `/__test/emails` ab, damit eine Spec einem Verifizierungslink folgen kann.

- Specs sind nach dem Ablauf benannt (`course-admin.spec.ts`, `auth-redirect.spec.ts`) und steuern die Seite über Rollen und zugängliche Namen, mit Page Objects in `e2e/pages/`.
- Jede Spec legt die Daten, die sie ändert, mit eindeutigen Werten an, etwa einem Slug aus `crypto.randomUUID()`, und meldet sich mit ihrem eigenen Header `CF-Connecting-IP` an, sodass Specs parallel laufen und erneut ausgeführt werden können, ohne miteinander oder mit Rate Limits zu kollidieren.
- Eine Spec interagiert mit einer Seite erst, wenn `waitForAppReady()` aus `e2e/pages/base-page.ts` zurückgekehrt ist, auch nach clientseitigen Navigationen. Die Methode kehrt zurück, sobald TanStack Router die aktuelle URL gerendert hat, was die automatische Fixture `recordRenders` aus dem Router-Ereignis `onRendered` aufzeichnet, denn eine clientseitige Navigation ändert die URL, bevor die nächste Route rendert. Routeninhalte können erst nach diesem Rendern hydrieren. Eine Spec, die vom eigenen Zustand einer Komponente abhängt oder einen Link außerhalb des Inhalts drückt, bevor dieser hydriert ist, ruft deshalb zuerst `waitForHydration(element)` auf, das wartet, bis React das Element und alles darin hydriert hat; `LandingPage.goto()` tut das für `main` der Landingpage. Eine Spec darf eine Seite verlassen, während sie lädt, wie es auch Besucher tun, und eine Spec, die Seitenfehler über mehrere direkte Aufrufe sammelt, öffnet jeden Aufruf in einem eigenen Tab, wie `auth-routing.spec.ts`. Eine Spec, die Seitenfehler sammelt, verlässt eine Seite erst, wenn deren clientseitige Navigation gerendert ist: WebKit meldet eine Anfrage, die die Seite startet, nachdem die Spec sie zu verlassen begonnen hat, als Seitenfehler, `Fetch API cannot load … due to access control checks.`, obwohl die App die fehlgeschlagene Anfrage behandelt.
- Pull Requests führen jede Spec in Chromium aus (`bun run test:e2e:pr`); Pushes auf `main` und ein wöchentlicher Zeitplan führen zusätzlich WebKit aus.
- Eine Korrektur an einer Route, einem Ablauf oder der Darstellung, die Unit-Tests nicht sehen können, bekommt eine Spec: Die Barrierefreiheitsscans und die Navigationsregressionen in `navigation.spec.ts` und in den Specs der Bereiche, die sie betreffen, etwa `content.spec.ts`, `legal.spec.ts` und `landing.spec.ts`, sind Beispiele. Eine Spec, die scrollt, macht die Seite selbst hoch genug, wie der Scroll-Test in `navigation.spec.ts`, statt sich auf die Länge einer Seite zu verlassen. Eine Spec, die prüft, wo ein sanftes Scrollen endet, lädt vorher die Abschnitte, die sich auf dem Weg nachträglich füllen, wie der Logo-Test in `landing-controls.spec.ts` den Kursblock: WebKit bricht ein sanftes Scrollen ab, wenn die Scroll-Verankerung einen Abschnitt oberhalb des Viewports ausgleicht, dessen Höhe sich währenddessen ändert.
