Payments run through Polar with the `@polar-sh/better-auth` plugin, which the polar area adds to Better Auth in `src/data/polar.auth-plugins.ts`:

```ts
export const POLAR_AUTH_PLUGINS = [
  {
    disabledPaths: [],
    plugin: polar({
      client: polarCore,
      use: [portal(), webhooks({ onPayload: handlePolarEvent, secret: env.POLAR_WEBHOOK_SECRET })],
    }),
    rateLimitExemptPaths: [ROUTES.API_AUTH_POLAR.WEBHOOKS],
  },
] as const satisfies readonly AuthPluginEntry[]
```

The plugin adds the customer portal and the webhooks, which are exempt from Better Auth's rate limiter, and no checkout: its `checkout()` would create a checkout with the account's ID alone, so Polar would ask a signed-in buyer for their email again. An area that sells creates its checkouts with the Polar SDK after its own checks, as the licence area's `startCheckout` does (see [Licences](/docs/features/licences)).

`src/integrations/polar/polar.config.ts` creates `polarCore` from `POLAR_ACCESS_TOKEN` and `POLAR_SERVER`, which the plugin uses, and `polar`, the checkouts, discounts, licence keys and orders services built on it. `POLAR_ORGANIZATION_ID` scopes every Polar call that names an organisation; [Environment and bindings](/docs/reference/environment) lists them. `src/integrations/polar/polar.constants.ts` holds Polar's own values, `POLAR_ORDER_STATUS`, `POLAR_LICENSE_KEY_STATUS`, `POLAR_WEBHOOK_EVENT` and `POLAR_CHECKOUT_ID_PLACEHOLDER`, each checked against the SDK's types; it reads no environment, so the browser and the browser suite import it too. The polar area's paths, `API_AUTH_POLAR` and `API_AUTH_CUSTOMER_PORTAL`, are in `src/data/polar.routes.ts`. [Polar setup](/docs/getting-started/polar-setup) describes the products, licence keys, discounts, webhook and token this code expects in Polar, and `bun run polar:verify:<environment>` checks them.

## Webhooks

Polar posts to `/api/auth/polar/webhooks`. The plugin verifies the signature with `POLAR_WEBHOOK_SECRET` and passes each event to `handlePolarEvent` in `src/data/polar-events.ts`. An area that reacts to Polar events declares a list in `src/data/<area>.polar-events.ts` and adds it to `src/data/polar-events.entries.ts`. Each entry names the events it handles and the function that handles them:

```ts
export interface PolarEventHandler {
  readonly events: readonly models.WebhookEventType[]
  readonly handle: (event: webhooks.WebhookPayload) => Promise<void>
}
```

- `handlePolarEvent` runs the `handle` of every entry that lists the event's type, all at once, and waits for all of them.
- When one rejects, the plugin answers 500 and Polar delivers the event again later, so each handler must be safe to run twice for the same event. Polar disables an endpoint that keeps failing, and `polar:verify` reports a disabled endpoint.
- An event that no entry lists is acknowledged and goes nowhere.
- `POLAR_EVENTS` joins the events of every entry, sorted and each once. The webhook endpoint in Polar must send exactly these, and `polar:verify` compares them.
- The polar area adds an empty list in `src/data/polar.polar-events.ts`, so the barrel is never empty. Today only the licence area handles events, in `src/data/license.polar-events.ts`; see [Licences](/docs/features/licences#webhooks-and-licences).

`polar:verify` runs in Bun, outside the Worker, and reads `POLAR_EVENTS`, so `src/data/polar-events.ts` and every `<area>.polar-events.ts` import no server code. An area's `handle` loads its handlers when an event arrives:

```ts
const { licenseWebhookHandlers } = await import("~/src/modules/license/license.webhooks")
```

`src/data/__test__/polar-events.test.ts` imports `src/data/polar-events.ts` in Bun and fails when that import reaches the Worker's runtime.

## Customer portal

`ROUTES.API_AUTH_CUSTOMER_PORTAL` (`/api/auth/customer/portal`) opens the Polar customer portal of the signed-in account. The licence card on `/app/license` links to it.

## Admin screen (demo)

`/admin/payments` renders `RefundStats` and a refunds `DataTable` over `ADMIN_PAYMENT_ROWS` from `src/data/admin-payments.ts`; its buttons are not wired. The payments area declares the `order` permission statements (`read`, `update`, `refund`) in `src/data/payments.access.ts`, but no use case reads orders or refunds.
