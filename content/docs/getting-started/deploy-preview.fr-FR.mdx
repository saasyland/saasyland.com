---
title: "Déployer une préversion"
description: "Provisionner les ressources Cloudflare et déployer le Worker de préversion."
---

L'environnement `preview` déploie le Worker `saasyland-preview` sur `preview.saasyland.com`. Il dispose de sa propre base de données D1, de son propre espace de noms KV et de deux buckets R2 ; `development` utilise des ressources locales et ne partage rien avec lui.

## Provisionner les ressources

```sh
bunx wrangler login
bunx wrangler d1 create saasyland_com_preview
bunx wrangler kv namespace create CACHE --env preview
bunx wrangler r2 bucket create saasyland-preview
bunx wrangler r2 bucket create saasyland-bundles-preview
```

Dans `wrangler.jsonc`, remplacez `database_id`, `database_name`, l'`id` KV et le `bucket_name` de `MEDIA` et de `BUNDLES` sous `preview` ; le bloc `development` nomme des ressources locales et ne demande aucune modification. Conservez les noms de binding `DB`, `CACHE`, `MEDIA` et `BUNDLES` ainsi que `migrations_dir`, et adaptez les noms des Workers et les routes de domaine personnalisé à votre compte. Pour la production, créez des ressources distinctes, y compris les buckets `saasyland` et `saasyland-bundles`, et mettez à jour le bloc `production`. `BUNDLES` contient les bundles de modèles des versions de la CLI, que la publication du dépôt de la CLI téléverse dans le bucket de préversion et dans celui de production ; voir [Publier les bundles](/docs/features/cli-licence-api#publishing-bundles). Définissez `APP_DOMAIN` dans `src/presentation/branding/index.ts`. `DEPLOYED_HOSTS`, dans `src/modules/_core/constants/api.ts`, en déduit les hôtes déployés, `APP_DOMAIN` pour la production et `preview.<APP_DOMAIN>` pour la préversion, et c'est le seul endroit où le code les nomme : `appHostsForMode` le lit pour les hôtes qu'acceptent Better Auth et les liens de la newsletter, et `scripts/verify-deployment.ts` les interroge après un déploiement. En local, `appHostsForMode` accepte `localhost:3000` ou `127.0.0.1:3000` en développement, et en test ceux-ci plus `localhost` et `127.0.0.1` sur les ports <RepositoryFact name="testServerFirstPort" /> à <RepositoryFact name="testServerLastPort" />. Ne modifiez `DEPLOYED_HOSTS` que si votre hôte de préversion porte un autre nom. Les `routes` de domaine personnalisé de `wrangler.jsonc` et les URL d'environnement de `.github/workflows/deploy-reusable.yml` nomment les mêmes hôtes : gardez-les synchronisés.

## Déployer

Remplissez `.env.preview` et mettez en place la sandbox Polar comme décrit dans [Configurer Polar](/docs/getting-started/polar-setup), puis déployez :

```sh
bun run deploy:preview
```

`deploy:preview` exécute `scripts/verify-bindings.ts preview`, qui rejette les bindings manquants et les identifiants fictifs, puis `scripts/prepare-deploy-secrets.ts preview`, qui écrit dans `.wrangler/secrets.preview.json` les secrets que `wrangler.jsonc` déclare pour `preview`, lus depuis `.env.preview`, et échoue si l'un d'eux est vide ou un espace réservé comme `[UPDATE]`. `scripts/run-deploy-checks.ts preview` exécute ensuite la vérification de déploiement de chaque fonctionnalité, aujourd'hui `auth:verify:preview`, qui vérifie que les identifiants client OAuth de `.env.preview` ont le format de leurs fournisseurs, et `polar:verify:preview`, qui compare l'organisation Polar de `.env.preview` avec le code. `build:preview` prérend ensuite les pages publiques et vérifie le résultat. `db:migrate:preview` applique les nouvelles migrations avant que `wrangler deploy` ne téléverse `dist/server/wrangler.json` avec ces secrets, et `scripts/verify-deployment.ts preview` vérifie enfin que l'hôte de préversion de `DEPLOYED_HOSTS` (`https://preview.saasyland.com`) répond et que la connexion avec chaque fournisseur OAuth atteint ce fournisseur avec un identifiant client à son format et revient sur l'hôte de préversion. `verify-bindings.ts` ne vérifie pas que les buckets R2 existent, car ils sont liés par leur nom : le déploiement échoue tant qu'ils n'existent pas. `bun run db:migrations:preview` liste les migrations que la base de données de préversion n'a pas encore appliquées.

Enregistrez les callbacks OAuth pour l'hôte de préversion, comme indiqué dans [Variables d'environnement](/docs/getting-started/environment-variables).

## Déploiements automatiques

La CI déploie chaque push sur `main` sur la préversion partagée, puis en production, une fois que les vérifications et les tests dans le navigateur ont réussi dans la file de fusion ou dans ce run. Le workflow `Preview` déploie à la demande une branche sur la préversion partagée. Voir [CI/CD](/docs/tooling/ci-cd) pour les secrets GitHub requis.
