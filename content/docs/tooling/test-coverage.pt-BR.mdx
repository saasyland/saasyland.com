## Cobertura de código [#code-coverage]

`bun run test:coverage` executa os projetos do Vitest <RepositoryFact name="vitestProjects" /> e falha quando linhas, instruções, funções ou branches ficam abaixo de <RepositoryFact name="coverageThreshold" unit="percent" /> de <RepositoryFact name="coverageInclude" />. Ele deixa de fora <RepositoryFact name="coverageExclude" />. A CI o executa em todo pull request e em todo push para `main`.

A suíte de navegador não conta para esse número: o Playwright conduz o Worker de testes gerado pelo build, e nenhuma cobertura é coletada ali. Cobertura de código total significa que cada linha medida rodou sob um teste que verificou alguma coisa. Não significa que as partes funcionam juntas através do Worker, do D1, do navegador e dos provedores: a spec de bundles da API de licenças da CLI envia só as respostas padrão, então uma requisição de bundle com outra resposta poderia falhar em produção mesmo com cada linha do handler coberta. A cobertura de fluxos mede essa segunda questão.

## Cobertura de fluxos [#flow-coverage]

O inventário de fluxos lista cada fluxo do site, do workspace do cliente e do console de administração. Cada área declara os seus fluxos em `e2e/data/<area>.flows.ts`, reunidos por `e2e/data/flows.entries.ts`, com os tipos e as constantes em `e2e/data/flows.ts`, assim como as áreas declaram as suas páginas e os seus dados de seed. Um fluxo tem um id, uma área, o resultado que um teste precisa verificar e um de três status:

- **coberto**: um teste do Playwright executa o fluxo de ponta a ponta e verifica o resultado. O fluxo cita a spec e o título completo de cada um desses testes.
- **sem cobertura**: o recurso existe, mas nenhum teste no navegador executa o fluxo de ponta a ponta. O fluxo diz o que falta e cita os testes que fazem uma parte dele e a etapa da jornada que o executa, se houver.
- **a construir**: o recurso ainda não existe, como as telas de administração de produtos, preços e descontos, que mostram dados de exemplo. O fluxo diz o que ocupa o lugar dele.

`bun run check` executa `bun run check:flows`, que lista a suíte de navegador com `playwright test --list` no Chromium, como os pull requests a executam, e falha quando:

- um fluxo cita uma spec ou um título de teste que a suíte não tem, que é o que acontece ao renomear ou apagar o teste;
- um fluxo cita um teste que é pulado;
- dois fluxos compartilham um id;
- um fluxo sem cobertura ou um fluxo a construir não diz por quê;
- um fluxo cita uma etapa que a suíte da jornada do cliente não tem.

Assim, um fluxo coberto só perde o seu teste quando o mesmo pull request muda o status dele e registra o motivo.

A suíte de navegador tem <RepositoryFact name="e2eTests" /> testes em <RepositoryFact name="e2eSpecs" /> arquivos de spec.

## Suíte da jornada do cliente [#journey-suite]

A [suíte da jornada do cliente](/docs/tooling/playwright#journey-suite) compra cada plano no preview, no sandbox da Polar, com o cartão de teste da Stripe, espera os webhooks emitirem a chave, usa a CLI publicada em tantos dispositivos quanto o plano permite e reembolsa o pedido; além disso, faz o upgrade do Core para o Complete pela diferença e reembolsa o upgrade para voltar ao Core. Ela executa <RepositoryFact name="flowsInJourney" /> dos fluxos sem cobertura, que a tabela de fluxos sem cobertura cita na última coluna, mas nenhum workflow de CI a executa, então esses fluxos contam como sem cobertura. Executá-la na CI exige três passos que só o proprietário pode dar:

1. **Secrets.** O ambiente `Preview` do GitHub guarda `POLAR_ACCESS_TOKEN`, um token do sandbox com os escopos `orders:read`, `refunds:write`, `benefits:read` e `license_keys:read`; `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE` e `POLAR_PRODUCT_ID_AGENCY`, os produtos do sandbox; e `RESEND_API_KEY`, uma chave com acesso total que pode ler os e-mails que o preview envia. `POLAR_SERVER` é `sandbox` e não precisa de secret.
2. **Sandbox.** A organização do sandbox corresponde ao código, o que `bun run polar:verify:preview` verifica, e o webhook dela aponta para o preview.
3. **Workflow.** Um job executa `bun run test:journey` com o Chromium instalado depois do job **Deploy preview** do `deploy.yml`, que faz o deploy da `main` no preview antes da produção. Neste repositório, workflows precisam da revisão de uma pessoa, então o job é proposto em vez de adicionado.

## Planejado [#planned]

- **Testes de mutação.** Uma ferramenta de mutação altera o código sob teste, um operador ou uma condição de cada vez, e conta as alterações que nenhum teste percebe. Ela mede se os testes verificam resultados ou só executam linhas. Começaria pelo código de licenças, pagamentos, preços, acesso aos cursos e autenticação. Nada está configurado ainda.
- **Cobertura de código no navegador.** Coletar a cobertura do V8 enquanto a suíte de navegador executa a aplicação compilada mostraria qual código nenhum teste no navegador alcança. Ela seria informada ao lado do número do Vitest, sem ser somada a ele, e sem gate. Nada está configurado ainda.
