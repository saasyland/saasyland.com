Jede Regel auf dieser Seite stammt aus einer Messung, und mehrere haben eine intuitive Lösung ersetzt, die es schlimmer gemacht hat. Ändere den Code hinter einer dieser Regeln nur mit einer neuen Messung, die sie übertrifft.

## Erst messen, dann behaupten

- Vergleiche den vorherigen und den neuen Build auf derselben Seite mit mindestens fünf Lighthouse-Läufen pro Build, abwechselnd ausgeführt, und vergleiche die Mediane. Ein einzelner Lauf beweist nichts: Etwa jeder fünfte Lauf ist ein Ausreißer, verursacht durch Rauschen auf der Maschine.
- Beurteile eine Änderung nicht anhand eines einzigen Laufs von PageSpeed Insights. Dasselbe Deployment erzielt je nach Geschwindigkeit der Maschine, die den Test ausführt, sehr unterschiedliche Werte; diese Geschwindigkeit meldet Lighthouse als `benchmarkIndex`.
- Miss einen Produktions-Build (`bun run build:test`, dann `bun run start:test`), ausgeliefert über HTTP/2 mit Komprimierung. Über einfaches lokales HTTP/1.1 ohne Komprimierung modelliert die Netzwerksimulation von Lighthouse Verbindungen und Übertragungsgrößen, die es in Produktion nie gibt.
- Eine Lighthouse-Diagnose ist kein Score. Ein Hinweis wie „forced reflow“ oder „properly size images“ kann für die Seite falsch sein, wie die folgenden Abschnitte zeigen; prüfe die bewerteten Metriken, bevor du danach handelst.

## Den Boot-Graph des Workers klein halten

`src/server.ts` läuft bei jeder HTML-Anfrage (`run_worker_first` in `wrangler.jsonc`), und alles, was es statisch importiert, wird bei jedem Kaltstart ausgewertet. Die Datei und die Worker-Handler, die die Bereiche beitragen, importieren nur Konstanten und reine Hilfsfunktionen und laden den Rest, wenn eine Anfrage ihn braucht:

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

Ein einziger statischer Import eines Header-Namens aus einem Modul, das auch den Polar-Client importierte, zog einmal etwa 1,4 MB SDK in jeden Kaltstart, und das erste Byte der Landingpage brauchte bis zu 1,4 Sekunden. Deshalb liegen `COUNTRY_HEADER` und `IP_ADDRESS_HEADER` in `src/modules/_core/constants/api.ts`, das nichts Schweres importiert. Bevor du `server.ts` oder einem Modul, das er importiert, einen statischen Import hinzufügst, verfolge dessen Importkette: Alles, was `polar`, `drizzle-orm` oder `resend` erreicht, ist eine Regression. `scripts/verify-build.ts` prüft das bei jedem Build: Es verfolgt die statischen Importe des Einstiegspunkts des deployten Workers, `dist/server/index.js`, und schlägt fehl, wenn sie Code erreichen, der aus `@polar-sh`, `drizzle-orm` oder `resend` gebündelt wurde, oder zusammen mehr als `BOOT_CLOSURE_MAX_BYTES` ergeben. Die Pfade gehören zu diesen statischen Importen, deshalb deklariert `src/routes.ts` sie und importiert nichts.

## Den Routenbaum leicht halten [#keep-the-route-tree-light]

Der Worker übergibt jede Anfrage, die weder eine vorgerenderte Seite noch eine statische Datei ist, an TanStack Start, und Start lädt vor allem anderen den Routenbaum, für den Aufruf einer Server Function ebenso wie für eine Seite, die es rendert: `src/routeTree.gen.ts` und jedes Modul, das die Routendateien statisch importieren, einschließlich der Handler von Server-Routen wie `/api/auth/$`. Ein Worker-Isolate wertet ihn bei seiner ersten solchen Anfrage aus, und eine Server Function lädt ihren eigenen Chunk bei ihrem ersten Aufruf. Beides geschieht, während ein Besucher auf eine clientseitige Navigation wartet, deshalb gehört alles, was sie importieren, auf einem neuen Isolate zur Wartezeit.

Die Collections von Dokumentation und Blog wurden früher vollständig im Voraus geladen: `.source/server.ts` importierte das kompilierte MDX jeder Docs-Seite und jedes Blogbeitrags in jeder Locale, 1.305 Module mit den Überschriften und dem Suchtext jeder Seite, und das Lucide-Icons-Plugin fügte für die wenigen Icons, die die Meta-Dateien der Dokumentation nennen, den gesamten Icon-Satz hinzu. Das Docs-Layout, die Docs-Seiten, die Landingpage und der Blog lasen diese Quelle über ihre Server Functions, und `/api/search` importierte sie statisch, wodurch sie im Routenbaum landete. Auf saasyland.com wartete eine clientseitige Navigation von `/` zu `/docs` auf einem neuen Isolate etwa 1,3 Sekunden auf ihre beiden Server Functions, auf einem warmen etwa 25 ms; die Landingpage und der Blog zahlten bei ihrer ersten Navigation dasselbe.

Die Collections wurden `async`, sodass die Quelle das Frontmatter jeder Seite behielt und das kompilierte MDX einer Seite erst importierte, wenn eine Anfrage deren Überschriften oder Suchtext brauchte, und `/api/search` importierte seinen Index in seinem Handler. Der nächste Abschnitt hat die Inhalte ganz aus dem Worker genommen. `fumadocs.icons.ts` importiert nur die Icons, die die Meta-Dateien nennen, und `fumadocs.icons.test.ts` schlägt fehl, wenn eine Meta-Datei ein Icon nennt, das die Datei nicht importiert, oder wenn sie eines importiert, das keine Meta-Datei nennt.

Die Größen geben an, was jeder Teil im Worker von `bun run build:test` statisch importiert, und die Zeiten sind der Median aus fünf verschränkten Läufen auf einem Laptop:

| Messung                                                                                          | Vorher                  | Nachher                 |
| ------------------------------------------------------------------------------------------------ | ----------------------- | ----------------------- |
| Der Routenbaum, den jede Serveranfrage lädt                                                      | 1.635 Module, 21,7 MiB  | 296 Module, 4,9 MiB     |
| Der Seitenbaum der Dokumentation und `getDocsPage`, jeweils mit ihren Importen                   | 1.402 Module, 16,9 MiB  | 41 Module, 1,3 MiB      |
| JavaScript in `dist/server`                                                                      | 4.275 Dateien, 28,0 MiB | 2.953 Dateien, 26,8 MiB |
| Auswertung des Routenbaums in Node                                                               | 554 ms                  | 162 ms                  |

Das meiste, was der Routenbaum noch lädt, etwa 3 MiB, sind Better Auth und die Module, die es importiert; `/api/auth/$`, das Suchschema der Auth-Seiten und die Lizenz-API der CLI importieren sie statisch.

## Der Worker enthält keine Inhalte von Dokumentation und Blog [#the-worker-holds-no-docs-or-blog-content]

Nach der obigen Änderung bündelte der Worker Dokumentation und Blog weiterhin: das kompilierte MDX von 1.305 Seiten, etwa 14,6 MiB eines Uploads von 27,5 MiB, behalten für `/api/search`, für die Inhaltsverzeichnisse und Lesezeiten der Blogbeiträge und neben dem Frontmatter, das die Server Functions der Dokumentation, des Blogs und der Landingpage lasen. Eine Anfrage auf einem neuen Isolate wartete 1 bis 2 Sekunden, bevor überhaupt Code lief, eine clientseitige Navigation durch die Dokumentation auf saasyland.com dauerte auf einem neuen Isolate 1,3 bis 2,0 Sekunden und auf einem warmen etwa 270 ms, und eine Suche in der Dokumentation dauerte 9 bis 18 Sekunden.

Jeder Build macht die Inhalte jetzt zu Daten, die die App als statische Dateien importiert. `scripts/content-indexes.ts`, ein Vite-Plugin, lädt `fumadocs.indexes.ts` mit dem Module Runner von Vite; diese Datei liest `content/docs` und `content/blog` mit den Schemas der Collections und dem `loader` von Fumadocs und baut für jede Locale:

- den Docs-Index: den Seitenbaum und die Seiten nach Slug, jeweils mit Titel, Beschreibung, Abschnitt und MDX-Datei;
- den Blog-Index: die veröffentlichten Beiträge, die neuesten zuerst, mit Frontmatter, Inhaltsverzeichnis und Lesezeit;
- den Suchindex: die exportierte Suchdatenbank von Fumadocs über die Docs-Seiten, die der Build nach `/assets/search-index-<locale>-<hash>.json` schreibt.

`loadDocsIndex` und `loadBlogIndex` aus `virtual:content-indexes` importieren den Docs- oder Blog-Index einer Locale, jeweils einen eigenen Chunk unter `/assets/`. Das Docs-Layout und die Docs-Seiten, der Blog, seine Beiträge und die Landingpage lesen sie in ihren Loadern, die bei einer clientseitigen Navigation im Browser und beim Prerendering auf dem Server laufen, und das kompilierte MDX einer Seite kommt wie bisher aus ihrem Browser-Chunk. `run_worker_first` überlässt `/assets/*` den statischen Assets von Cloudflare, sodass eine clientseitige Navigation durch die Dokumentation oder den Blog überhaupt keinen Worker anfragt. Die Suche der Dokumentation lädt bei der ersten Suchanfrage den Index ihrer Locale herunter und durchsucht ihn im Browser (siehe [Dokumentationsseite](/docs/features/docs-site#search)); `/api/search` gibt es nicht mehr.

Der deployte Worker liefert jede Docs-Seite und jeden Blogbeitrag vorgerendert aus, daher löst `scripts/deployed-worker.ts` jeden Import einer kompilierten Seite in ein einziges Modul auf, das einen Fehler wirft, und der Build kompiliert keine dieser Seiten. `scripts/verify-build.ts` lässt den Build fehlschlagen, wenn eine Datei des deployten Workers ein Modul der Dokumentation oder des Blogs enthält, wenn eine Locale keinen Suchindex hat oder wenn der Index einer Locale nicht genau die Docs-Seiten dieser Locale unter ihren Titeln enthält.

Die Größen stammen aus dem Worker von `bun run build:test`, die Zeiten aus dem Preview-Deployment, gemessen mit Headless-Chromium, jede Stichprobe auf einem neuen Isolate und anhand ihres `cf-ray` den Logs des Workers zugeordnet:

| --------------------------------------------------------------------------------------------------- | -------------------------------------- | -------------------------------------- |
| Upload des Workers, `wrangler deploy --dry-run`                                                     | 30.115 KiB, 7.201 KiB gzip-komprimiert | 13.465 KiB, 3.148 KiB gzip-komprimiert |
| Dateien in `dist/server`                                                                            | 3.021                                  | 1.590                                  |
| Kompilierte Seiten von Dokumentation und Blog im deployten Worker                                   | 1.341                                  | keine                                  |

`e2e/specs/content.spec.ts` prüft, dass clientseitige Navigationen durch die Dokumentation und den Blog nichts als statische Dateien anfragen und dass die Suche der Dokumentation den Index der Locale der Seite erst herunterlädt, wenn jemand sucht.

## Eine langsame Navigation zeigt ihr Skeleton sofort [#a-slow-navigation-shows-its-skeleton-at-once]

`src/router.tsx` setzt `defaultPendingMs` auf <RepositoryFact name="navigationPendingMs" unit="millisecond" /> und `defaultPendingMinMs` auf <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, aus `src/data/navigation.constants.ts`. Mit den Standardwerten von TanStack Router, einer Sekunde und einer halben Sekunde, zeigte eine langsame Navigation eine volle Sekunde lang nichts außer einer neuen Adresse: Ein erster Klick auf **Dokumentation** auf einem neuen Isolate dauerte etwa 1,6 Sekunden und zeigte das Skeleton der Dokumentation erst nach einer Sekunde oder gar nicht, und ein Klick von einer Docs-Seite zu einer anderen, deren Routen `pendingMs: Number.POSITIVE_INFINITY` hatten, behielt die vorherige Seite während der gesamten Wartezeit.

- Eine Navigation, die innerhalb der Verzögerung abgeschlossen ist, behält die vorherige Seite, bis die nächste bereit ist, und zeigt nie ein Skeleton. Auf saasyland.com war eine Navigation zu einer Seite, die der Router beim Hovern vorab oder bereits geladen hatte, 40 bis 115 ms nach dem Klick abgeschlossen. Ein erster Besuch eines Bereichs auf einem warmen Worker dauerte, lokal gemessen mit 40 ms Latenz pro Anfrage und ohne Hovern über den Link, 184 bis 314 ms; die Verzögerung liegt über beiden Werten, sodass keine dieser Navigationen ein Skeleton zeigt.
- Eine Navigation, die nach der Verzögerung noch lädt, zeigt das Skeleton ihrer Route genau so lange, wie sie noch lädt: `defaultPendingMinMs` beträgt <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, also entfernt der Router das Skeleton, sobald die Seite bereit ist, statt es auf dem Bildschirm festzuhalten.
- Die Docs-Seiten haben eigene Skeletons, `DocsIndexPending` und `DocsPagePending`, die den Artikel und das Inhaltsverzeichnis neben der Seitenleiste füllen, sodass eine langsame Navigation zwischen Docs-Seiten die Form der nächsten Seite zeigt, statt die vorherige stehen zu lassen.

`e2e/specs/content.spec.ts` hält den Docs-Index einer Navigation zu `/docs` und das kompilierte MDX einer Navigation zwischen Docs-Seiten zurück und prüft, dass jede ihr Skeleton zeigt, die zweite auch die Seitenleiste, bis sie eintreffen. Diese Tests schalten zuerst den Datensparmodus ein, damit der Header die Dokumentation nicht schon vor dem Klick lädt.

## Pro Anfrage gerenderte Seiten streamen ihre langsamen Abschnitte [#request-rendered-pages-stream-their-slow-sections]

Die Admin-Konsole, der Kundenbereich und die Kursseiten werden für jede Anfrage auf dem Worker gerendert. Ihre Loader warteten früher auf jede Query, sodass nichts den Worker verließ, bevor die langsamste geantwortet hatte; auf `/admin` und `/admin/products` war das der Produktkatalog von Polar, ein Aufruf der API von Polar bei jedem Seitenaufruf. Jeder Loader wartet jetzt nur auf das, was der erste Teil der Antwort braucht, startet den Rest, ohne darauf zu warten, und jeder langsame Abschnitt wird in derselben Antwort in sein Skeleton gestreamt ([Gestreamte Abschnitte](/docs/conventions/routes#streamed-sections)):

- `/admin` wartet auf die neuesten Konten, die sein `DataGrid` mit `useQuery` liest. Jede Statistik und jedes Panel wird in einer eigenen Grenze gestreamt, sodass nur die Zahl der Produkte auf Polar wartet.
- `/admin/products` streamt sein Grid.
- `/app/billing` streamt seine Bestellungen und Abonnements und den Button zum Kundenportal von Polar, der von ihnen abhängt.
- Eine Lektion streamt ihren Player: Sobald der Loader weiß, dass die Lektion abgespielt werden kann, beginnt er, den Stream zu signieren, ohne darauf zu warten, sodass Titel, Text und Inhaltsverzeichnis den Worker verlassen, bevor der signierte Stream existiert, und der Player füllt sein Skeleton.

Gemessen auf Builds von `bun run build:test`, ausgeliefert von `bun run start:test`, mit dem User-Agent eines Browsers und per Cookie angemeldet, in 3 abwechselnden Runden mit je 10 Anfragen pro Seite und Build. Der Test-Build beantwortet Anfragen an Polar aus einem Test-Double im Speicher; für diese Läufe wartete es vor jeder Antwort 300 ms, um den Roundtrip zur API von Polar nachzubilden. D1 ist im Test-Build lokal. Das erste Byte ist die Zeit bis zum Eintreffen der Header der Antwort, die TanStack Start mit dem ersten Teil der Seite sendet; jede Zelle ist der Median der Mediane der drei Runden:

| Seite             | Erstes Byte vorher | Erstes Byte nachher | Ganze Seite vorher | Ganze Seite nachher |
| ----------------- | ------------------ | ------------------- | ------------------ | ------------------- |
| `/admin`          | 403 ms             | 83 ms               | 419 ms             | 327 ms              |
| `/admin/products` | 361 ms             | 43 ms               | 370 ms             | 367 ms              |
| `/app/billing`    | 30 ms              | 28 ms               | 36 ms              | 35 ms               |
| Eine Lektion      | 38 ms              | 35 ms               | 45 ms              | 44 ms               |

`/app/billing` und die Lektion lesen nur D1, das hier lokal ist, deshalb zeigen diese Läufe für sie keinen Unterschied; auf Cloudflare wartet ihr erstes Byte nicht mehr auf die Queries, die jetzt gestreamt werden. Ohne die Verzögerung brauchte jede Seite vorher und nachher gleich lang, innerhalb der Streuung der Läufe. Die vollständig geladenen Seiten sind bei 1440 und 390 Pixeln Breite auf Englisch und Deutsch pixelgenau identisch, und jedes Skeleton nimmt die Größe des Abschnitts ein, der es ersetzt.

Ein Crawler erhält die ganze Seite in seiner ersten Antwort: TanStack Start wartet auf jeden Abschnitt, bevor es eine Anfrage beantwortet, deren User-Agent `isbot` erkennt. `isbot` zählt auch `curl` und das `fetch` von Bun und Node zu den Crawlern, deshalb muss ein Skript, das das Streaming misst, den User-Agent eines Browsers senden.

`src/routes/__test__/admin-products-loaders.test.ts` prüft, dass `/admin` und `/admin/products` rendern, während der Katalog von Polar noch lädt, und `app-billing-routes.component.test.tsx` und `lesson-routes.component.test.tsx`, dass der Zahlungsverlauf und der Player ihre Skeletons halten, während ihre Daten gestreamt werden.

## Die Seiten des Headers laden vor dem Klick [#the-headers-pages-load-before-a-click]

`defaultPreload: "intent"` lädt Code und Daten eines Links erst, wenn der Mauszeiger `defaultPreloadDelay` lang darauf geruht hat, also <RepositoryFact name="navigationPreloadDelayMs" unit="millisecond" /> (`NAVIGATION_PRELOAD_DELAY_MS` in `src/data/navigation.constants.ts`), und diese Zeit gibt ihm weder ein schneller Klick noch ein Tippen auf dem Telefon noch die Tastatur. Nachdem der Routenbaum leichter geworden war, dauerte eine clientseitige Navigation von `/` bis zur Überschrift von `/docs` auf saasyland.com auf einem warmen Worker-Isolate 255 bis 283 ms und auf einem neuen 1,3 bis 2,0 Sekunden, weil die beiden Server Functions der Dokumentation 1,1 bis 2,0 Sekunden auf den Start des Isolates warteten.

Deshalb lädt `Navigation` die Seite jedes Eintrags von `HEADER_NAVIGATION` über TanStack Router vorab, sobald die angezeigte Seite im Leerlauf ist. So startet ein neues Isolate vor dem Klick, und der Klick findet Code und Daten der Seite im Cache des Routers. Es ruft in einem Effekt für jeden Eintrag `router.preloadRoute` auf und plant die Aufrufe mit `preloadWhenIdle`:

```ts title="src/lib/idle-preload.ts"
const schedule = (preload: () => void, signal: AbortSignal): void => {
  if (dataSaverSchema.safeParse(navigator).success) {
    return
  }
  if (document.readyState === "complete") {
    whenIdle(preload, signal)
    return
  }
  globalThis.addEventListener(
    "load",
    () => {
      whenIdle(preload, signal)
    },
    { once: true, signal },
  )
}
```

- `preloadWhenIdle` (`src/lib/idle-preload.ts`) wartet auf das Ereignis `load` und dann auf `requestIdleCallback`, sodass das Vorabladen nie mit den eigenen Anfragen der Seite, ihrem Largest Contentful Paint oder ihrer Hydration konkurriert. Safari hat kein `requestIdleCallback`, dort wartet es <RepositoryFact name="idleFallbackDelayMs" unit="millisecond" /> nach `load`. Es gibt die Funktion zurück, die das Warten abbricht; der Effekt ruft sie auf, wenn der Header vorher verschwindet oder die Seite wechselt.
- Für Besucher, die den Datensparmodus eingeschaltet haben (`navigator.connection.saveData`), lädt es nichts vorab.
- Der Effekt hängt von `shownPath` ab, dem Pfad der angezeigten Seite aus `resolvedLocation` des Routers, deshalb lädt der Header erneut vorab, sobald die nächste Seite im Leerlauf ist, und hält seine Seiten frisch, während jemand die Website durchstöbert. Eine Seite, deren Daten noch frisch sind, wird nicht erneut geladen. Die Seite, mit der ein Besuch beginnt, wurde beim Build gerendert, deshalb hält der Router ihre Daten für veraltet und lädt sie erneut, wenn der Header sie zum ersten Mal von einer anderen Seite aus vorab lädt.
- `preload="viewport"` von TanStack Router an den Links des Headers würde beginnen, sobald ein Link im Viewport ist, und der fixierte Header ist es immer, also würde es mit der Hydration konkurrieren; außerdem liegen die Links auf dem Telefon im Menü, das sie erst rendert, wenn es sich öffnet.
- Nur die Links des Headers laden auf diese Weise vorab. Jeder andere Link, etwa die Hunderte in der Seitenleiste der Dokumentation, behält `defaultPreload: "intent"`.
- Sobald die Session den Konto-Link auf den Bereich des Besuchers zeigen lässt, `/admin` oder `/app`, lädt dieser Eintrag nur seinen Code, mit `router.loadRouteChunk` für jede Route, die er trifft. Das Vorabladen der Seite führte den Guard und den Loader dieses Bereichs aus: für einen Admin das ganze Dashboard samt Katalog von Polar, auf jeder Seite, die er aufrief. Ein Eintrag, dessen Seite die in `HEADER_NAVIGATION` deklarierte ist, **Anmelden** eingeschlossen, lädt weiterhin seine Daten. Gemessen auf einem Build von `bun run build:test` sanken die Anfragen an Server Functions, die eine angemeldete Seite gestellt hatte, bis sie im Leerlauf war, auf `/` für einen Admin von 12 auf 2 und für einen Kunden von 4 auf 2.

`src/router.tsx` setzt `defaultPreloadStaleTime` auf <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />, den Wert aus dem Leitfaden von TanStack Router für TanStack Query, und lässt `defaultStaleTime` beim Standardwert des Routers, sodass allein TanStack Query entscheidet, was frisch ist: Ein Klick nach einem Preload führt die Loader der Seite erneut aus, und sie lesen, was der Preload in den Query-Cache gelegt hat. Früher hielt der Router vorab geladene Seiten für die Stale-Time der Queries, weil die Loader von Dokumentation und Blog Server Functions außerhalb von TanStack Query aufriefen; inzwischen importieren sie die beim Build erzeugten Indizes, die der Browser nach dem ersten Laden behält, und das ist nicht mehr nötig. Auf einem Build von `bun run build:test` lösten das Überfahren eines Links und der anschließende Klick mit beiden Einstellungen dieselben Aufrufe von Server Functions aus, für Kurs-, Blog-, Dokumentations- und Admin-Seiten gleichermaßen: einen oder zwei beim ersten Überfahren, je nach den Queries der Seite, und keinen beim zweiten Überfahren, beim Klick oder auf dem Rückweg.

Gemessen auf preview.saasyland.com mit einem frischen Browser pro Lauf, der jeweils `/` lädt, wartet, bis das Netzwerk ruhig ist, und zwei Sekunden länger, und dann auf **Dokumentation** klickt. Cloudflare verteilt die Anfragen eines Browsers auf mehrere Isolates, deshalb traf vor der Änderung der größte Teil der Läufe auf ein neues. Jede Zelle nennt den Median und in Klammern die Spanne:

| Messung                                                                                                                 | Vorher                 | Nachher        |
| ----------------------------------------------------------------------------------------------------------------------- | ---------------------- | -------------- |
| Vom Klick bis zur Überschrift der Dokumentation, wenn eine Server Function der Dokumentation auf ein neues Isolate traf | 1.287 ms (1.116–2.137) | 87 ms (67–145) |
| Vom Klick bis zur Überschrift der Dokumentation, wenn beide auf warme Isolates trafen                                   | 194 ms (177–208)       | 96 ms (91–101) |
| Anfragen an Server Functions, auf die der Klick wartet                                                                  | 2                      | 0              |

Die Startseite ist nicht langsamer geworden. Lighthouse auf `/`, auf einem Build von `bun run build:test` hinter einem HTTP/2-Proxy mit Kompression, Median aus 13 Läufen je Build, die Hälfte davon in jeder Reihenfolge:

| Messung                           | Vorher   | Nachher  |
| --------------------------------- | -------- | -------- |
| Largest Contentful Paint, mobil   | 1.546 ms | 1.538 ms |
| Total Blocking Time, mobil        | 12 ms    | 12 ms    |
| Largest Contentful Paint, Desktop | 729 ms   | 728 ms   |
| Total Blocking Time, Desktop      | 137 ms   | 136 ms   |

`e2e/specs/navigation.spec.ts` wartet, bis das Vorabladen des Headers auf `/` und auf `/docs` abgeschlossen ist, hält jede Server Function zurück und klickt auf jeden Link des Headers, auf dem Desktop und im Telefonmenü; jede Seite öffnet sich trotzdem. Außerdem prüft es, dass für Besucher mit eingeschaltetem Datensparmodus vor einem Klick nichts geladen wird.

Die eigene Standardverzögerung von TanStack Router beträgt 50 ms. Auf einem Build von `bun run build:test` mit 40 ms zusätzlicher Latenz, wobei der Zeiger vor dem Drücken 75 oder 150 ms auf einem Eintrag der Seitenleiste der Admin-Konsole ruhte, mit 20 Klicks pro Zelle, erreichte der Klick die Seite im Median nach 37 ms mit 50 ms und nach 40 bis 46 ms mit der aktuellen Verzögerung, innerhalb der Streuung der Läufe (12 bis 122 ms), während ein Zeiger, der mit 75 ms pro Eintrag die Seitenleiste hinunterfuhr, ohne zu drücken, mit 50 ms 8 Anfragen an Server Functions auslöste und mit der aktuellen Verzögerung 2. Die Verzögerung bleibt, wie sie ist.

## Loader bleiben im Chunk ihrer Route [#loaders-stay-in-their-routes-chunk]

`vite.config.ts` lagert den Loader jeder Route in einen eigenen Chunk aus, zusammen mit ihrer Komponente, Fehlerkomponente und Not-found-Komponente, während TanStack Router den Loader standardmäßig im Routenbaum lässt. Dort macht er eine Navigation, die nichts vorab geladen hat, also ein Tippen oder einen Klick ohne Verweilen auf dem Link, um einen Roundtrip schneller, legt aber jeden Loader und alles, was er importiert, in das Einstiegsskript. ## Guards verwenden die zwischengespeicherte Session [#guards-reuse-the-cached-session]

TanStack Router führt das `beforeLoad` eines Layouts bei jeder Navigation darunter aus und startet die Loader erst, wenn es fertig ist. `requireSignedIn` und `requireAdmin` lasen `getCurrentSessionQuery` bisher mit `staleTime: 0`, also wartete jeder Klick in `/app` und `/admin`, auch zurück auf eine schon geöffnete Seite, auf eine Session-Anfrage, bevor die eigenen Anfragen der Seite beginnen konnten. Auf saasyland.com dauerte diese Anfrage 60 bis 70 ms von jedem 190 bis 300 ms langen Klick in der Admin-Seitenleiste.

Die Guards lesen die Session jetzt mit ihrer eigenen Stale Time, `SESSION_STALE_TIME_MS` (<RepositoryFact name="sessionStaleTimeMinutes" unit="minute" />): Eine frische Session lässt die Navigation ohne Anfrage durch, eine veraltete wird neu geladen, bevor die Seite lädt. Guards entscheiden nur, was der Besucher sieht; jede Server Function prüft weiterhin die Session ihrer eigenen Anfrage (siehe [Authentifizierung und Sicherheit](/docs/architecture/security-model)). Damit eine beendete Session trotzdem sofort auffällt, gibt `getRouter` seinem `QueryCache` und seinem `MutationCache` ein gemeinsames `onError`, das jeden Fehler an jeden Handler in `QUERY_ERROR_HANDLERS` weitergibt; der einzige ist `recheckRefusedSession` aus dem Auth-Bereich. Antwortet eine Server Function mit `UNAUTHORIZED` oder `FORBIDDEN`, lädt `recheckRefusedSession` die Session in einen eigenen Cache-Eintrag; haben sich Nutzer oder Rolle geändert, markiert es die zwischengespeicherte Session als veraltet und führt die Guards mit `router.invalidate()` erneut aus, die den Besucher mit dem Hinweis auf die beendete Session zur Anmeldung schicken oder einen früheren Admin nach `/app`. Eine unveränderte Session lässt die Seite in Ruhe, sodass eine Ablehnung nie in eine Schleife gerät.

Gemessen auf einem Build von `bun run build:test`, ausgeliefert von `bun run start:test`, in Chromium mit 40 ms zusätzlicher Latenz pro Anfrage, angemeldet als der geseedete Admin, in 2 abwechselnden Runden mit je 5 Läufen pro Build. Jeder Lauf öffnete `/admin` und dann jeden Eintrag der Seitenleiste zweimal, wobei der Zeiger vor dem Drücken 250 ms auf dem Eintrag ruhte; ein Klick wird vom Drücken bis zum ersten Frame gemessen, nachdem der Router die Seite gerendert hat. ## Der Header kennt die Session vor seinen Skripten [#the-header-knows-the-session-before-its-scripts]

Jede öffentliche Seite ist vorgerendert, ihr HTML kann also nicht wissen, wer sie liest. Der Link **Anmelden** im Header wurde erst zu **Dein Konto**, nachdem die Seite ihre Skripte geladen, hydriert und nach der Session gefragt hatte, und die breitere Beschriftung schob dann **Preise**, **Kurse**, **Blog** und **Dokumentation** zur Seite. Ein Browser, der sich je angemeldet hatte, fragte bei jedem Seitenaufruf nach der Session, weil das Cookie von Better Auth mit der zuletzt verwendeten Anmeldemethode darüber entschied, und dieses Cookie überdauert die Abmeldung.

Jetzt entscheidet der Worker über die Beschriftung, bevor das HTML ihn verlässt. `markSession` setzt `data-session` auf `<html>`, wenn der Request das Session-Cookie mitbringt; es prüft nur, ob das Cookie vorhanden ist, nie die Datenbank. Der Link enthält beide Beschriftungen, und CSS blendet nur die ein, die die Markierung auswählt, sodass der Link so breit ist wie die Beschriftung, die er zeigt, und denselben Abstand zu seinen Nachbarn hat wie jeder andere Header-Link. Die Session-Anfrage läuft nur auf einer markierten Seite, und ein Cookie, dessen Session beendet ist, wird schon von dieser ersten Anfrage gelöscht, sodass die nächste Seite unmarkiert bleibt (siehe [Pfade und Navigation](/docs/conventions/routes#paths-and-navigation) und [Caching und SSR](/docs/architecture/caching-and-ssr#prerendering)). Im Pull Request mit dieser Änderung, #405, wuchs der Kaltstart des Workers um 702 Bytes auf 38.292.

## Das ORM aus dem Browser heraushalten [#keep-the-orm-out-of-the-browser]

Drizzle läuft nur im Worker. Der Browser braucht die Zod-Schemas eines Moduls für seine Formulare und dessen Enum-Tupel für seine Auswahlfelder, deshalb liegen beide in Dateien, die nichts aus Drizzle importieren: `<table>.zod.ts` und `<table>.constants.ts` (siehe [Module](/docs/conventions/modules)). Ein Browser-Import, der eine `<table>.schema.ts` erreicht, führt `sqliteTable(...)` aus, einen Aufruf, den der Bundler behalten muss, und bringt `drizzle-orm` mit.

`<table>.zod.ts` erzeugte früher außerdem mit `drizzle-zod` die Schemas `insert`, `select` und `update` aus den Tabellen, und zur Laufzeit las sie nichts. `drizzle-zod` hält den gesamten Zod-Namespace fest, sodass der Bundler auch jede Zod-Locale, den JSON-Schema-Konverter von Zod und seinen Compiler behielt. Die Pending-Skeletons von `/admin` und `/app` importierten `PreferencesCardPending` aus `preferences-card.tsx`, das `user.zod.ts` importierte, und Pending-Komponenten werden nicht in eigene Chunks aufgeteilt, sodass all das auf jeder Seite geladen wurde. Die Tupel in die Konstanten zu verschieben und diese Schemas zu löschen, hat jede Seite um etwa 75 KiB gzip-komprimiertes JavaScript verkleinert. | `/docs/<page>` | 612,1 KiB | 536,5 KiB |
| `/blog`        | 487,2 KiB | 411,7 KiB |
| `/app`         | 496,6 KiB | 421,0 KiB |
| `/admin`       | 515,0 KiB | 439,4 KiB |

`vite.config.ts` verweigert `drizzle-orm` der Client-Umgebung über den Importschutz von TanStack Start:

## Nachrichten laden, wenn eine Seite sie braucht [#load-messages-when-a-page-needs-them]

Die erste Seite, die ein Besucher öffnet, lädt im Browser keine Nachrichtendatei: Die Root-Route und die passenden Routen laden ihre Namespaces auf dem Server in den Query-Cache vor, und TanStack Start schickt diesen Cache mit dem HTML. Der Browser lädt einen Namespace erst, wenn eine spätere Navigation einen braucht, den der Cache noch nicht enthält.

`import.meta.glob` gibt jeder Nachrichtendatei einen eigenen Chunk, aber die Zuordnung jeder Datei zu ihrem Chunk, die jeden Namespace in jeder Locale nennt, landet in dem Modul, das den Glob aufruft. Dieses Modul war `i18n.messages.ts`, das die Root-Route importiert, und es enthielt die Zuordnung doppelt, einmal für die Nachrichten und einmal für die Seiten-Metadaten, sodass jede Seite etwa 240 KiB Loader lud, 21 KiB gzip-komprimiert. Die Zuordnung liegt jetzt allein in `i18n.loaders.ts`, und `loadNamespace` importiert sie, wenn es zum ersten Mal einen Namespace lädt:

```ts title="src/integrations/use-intl/i18n.messages.ts"
const { MESSAGE_LOADERS } = await import("~/src/integrations/use-intl/i18n.loaders")
```

`loadPageMetadata` liest `metadata` aus dem Namespace der Seite statt aus einer zweiten Zuordnung, sodass der Head einer Seite und ihre Nachrichten aus einem Chunk kommen. Der Browser holt `i18n.loaders.ts`, etwa 11 KiB gzip-komprimiert, mit dem ersten Namespace, den er lädt, bei einer Navigation oder beim Hovern, das eine vorlädt. Die Root-Namespaces werden weiterhin in `i18n.messages.ts` am Dateinamen erkannt, und die Schlüssel dieses Globs kosten etwa 2 KiB gzip-komprimiert. Jedes Skript, das die jeweilige Seite lädt, gzip-komprimiert, laut Ausgabe von `bun run build:test`:

| `/docs/<page>` | 553,5 KiB | 532,9 KiB |
| `/blog`        | 424,6 KiB | 404,0 KiB |

## Vorgerenderte Seiten laden zuerst CSS und Schriften

Öffentliche Seiten werden vorgerendert und brauchen für ihren ersten Paint kein JavaScript. TanStack Start erzeugt einen `modulepreload`-Hinweis für jeden Chunk, den eine Seite brauchen könnte, auf der Landingpage mehr als hundert, und in einem simulierten Mobilfunknetz konkurrieren sie mit dem Stylesheet und den Schriften. `scripts/optimize-prerendered-html.ts`, das jedes Build-Skript ausführt, entfernt jeden Hinweis auf Abhängigkeiten und behält nur den Hinweis auf das eigene Entry-Skript der Seite, mit `fetchpriority="low"`:

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

Das Entfernen der Hinweise senkte den First Contentful Paint um etwa ein Drittel; den Entry-Hinweis mit niedriger Priorität zu behalten, senkte den mobilen First Contentful Paint um weitere 375 ms. Füge nie wieder Preload-Hinweise hinzu, weder für Abhängigkeiten noch für Routen-Chunks. Das Skript lässt den Build fehlschlagen, wenn es keinen Hinweis zum Entfernen oder keinen zum Behalten findet, sodass eine Änderung der Build-Ausgabe auffällt, statt dies stillschweigend rückgängig zu machen.

TanStack Start gibt inzwischen jeden Hinweis mit `fetchpriority="low"` aus, deshalb wurde die Regel im November 2026 auf der Landingpage neu gemessen, fünf abwechselnde Läufe je Variante. Mit allen 156 Hinweisen lud der Browser die Chunks der Seite in einer Welle statt in elf und hydrierte den CLI-Konfigurator auf dem Desktop 250 ms und auf einem gedrosselten Smartphone 315 ms früher, aber der First Contentful Paint kam auf dem Desktop 68 ms und mobil 77 ms später. Die Hinweise bleiben entfernt.

Die Skript-Richtlinie behält diese Reihenfolge bei. Der Worker streamt jede vorgerenderte Seite durch `withNonce`, einen `HTMLRewriter`, der die Nonce der Antwort dem `<script type="module">` des Entry-Moduls und seinem Hinweis hinzufügt und sonst nichts ändert, sodass der Hinweis im Head den Download weiterhin mit niedriger Priorität startet und das Modul weiterhin läuft, sobald der Parser das Ende des Body erreicht. Das Umschreiben geschieht im Stream und hält daher kein Byte zurück, aber HTML-Antworten tragen kein `ETag`, deshalb lädt ein Browser eine Seite erneut herunter, statt sie zu revalidieren.

`robots.txt` und `llms.txt` sind statische Dateien in `public/`, die den Worker umgehen (`"!/robots.txt", "!/llms.txt"` in `run_worker_first`). Lighthouse ruft beide mit einem Timeout von zwei Sekunden ab, und eine langsame Antwort des Workers ließ die Audits von Lighthouse für SEO und Agent-Readiness fehlschlagen.

## Early Hints nennen nur Dateien, die ein Deployment überdauern

Der `Link`-Header des Workers auf HTML-Antworten nennt die Schriften der Locale und sonst nichts. Cloudflare speichert den Header pro URL und sendet ihn als `103 Early Hints`-Antwort, bevor der Worker die nächste Anfrage an diese URL beantwortet, und die gespeicherte Kopie übersteht ein Deployment. Vite benennt das Stylesheet nach seinem Inhalt, daher ist ein angekündigtes Stylesheet nach einem Deployment, das irgendein CSS ändert, eine Datei, die es nicht mehr gibt: Der Browser lädt einen 404 und findet das neue Stylesheet ohnehin im HTML. Die Dateien in `public/fonts` behalten ihre Namen von einem Deployment zum nächsten.

Gemessen auf saasyland.com mit Chromium, 15 verschränkte Läufe pro Variante auf drei Seiten, mit dem tatsächlichen Early-Hints-Timing der Edge: Die Ankündigung der Schriften senkte den First Contentful Paint von 168–208 ms auf 144–164 ms. Eine Ankündigung des Stylesheets sparte weitere 12–28 ms, wenn seine URL aktuell war, und nichts, wenn ein Deployment sie ersetzt hatte; 25 Minuten nach einem Deployment kündigten 67 der 91 Sitemap-Seiten, die Early Hints erhielten, noch das vorherige Stylesheet an. Das `<link>` des Stylesheets steht im ersten Kilobyte jeder Seite, sodass der Browser es mit den ersten Bytes des HTML findet. Kündige nur Dateien an, deren URLs ein Deployment überdauern.

## Provider umschließen nie ein Routen-Outlet

TanStack Router umschließt Routen-Outlets mit Suspense-Boundaries, und React hydriert diese Boundaries später, in kleinen Stücken. Ein Context-Provider darüber, dessen Wert sich direkt nach der Hydration ändert, zwingt React, alles darunter auf einmal zu hydrieren:

- `ThemeProvider` um die gesamte Anwendung machte die Hydration der Landingpage zu einer einzigen Aufgabe von 200 ms, die Eingaben blockierte. Nachdem er nur noch um seine beiden Nutzer herum eingebunden wurde, den `Toaster` und den `ThemeSwitch` der Dokumentation, sank die Total Blocking Time von etwa 150 ms auf unter 10 ms.
- `MotionProvider` über einem Routen-Outlet veröffentlicht einen neuen Context, wenn seine Animationsfunktionen fertig geladen sind. Bei einem Blogbeitrag traf diese Aktualisierung ein, während die Seite noch ihren Inhalt lud; React wich auf clientseitiges Rendern aus, und das Layout verschob sich.

Bevor du `__root.tsx` oder einem Layout einen Provider hinzufügst, prüfe, ob sich sein Wert nach der Hydration ändern kann. Wenn ja, binde ihn neben den Komponenten ein, die ihn lesen, unterhalb jedes Routen-`<Outlet />`. Die Platzierungen sind unter [Komponenten und Styling](/docs/conventions/components) aufgeführt.

## Ein Widget, das teuer zu hydrieren ist, bekommt eine eigene Boundary [#a-widget-that-is-heavy-to-hydrate-gets-its-own-boundary]

Der CLI-Konfigurator auf der Landingpage rendert vierzig React-Aria-Buttons, jeder mit eigenen Hooks für Drücken, Hover und Fokus. Zusammen mit dem Rest der Seite hydriert, machten ihre Effekte den Commit, der die Hydration der Seite abschließt, unter der Desktop-Drosselung von Lighthouse zu einer Aufgabe von 70–100 ms, die die Total Blocking Time von 101 auf 147 ms hob. `CliSection` umschließt `CliConfigurator` mit einer `Suspense`-Boundary, die nie suspendiert. React hydriert eine solche Boundary für sich, nach dem Rest der Seite, und committet sie getrennt, sodass die lange Aufgabe verschwindet und die Total Blocking Time 100 ms beträgt, bei unverändertem First Contentful Paint und Largest Contentful Paint. Der Konfigurator selbst hydriert etwa 50 ms später. Gib einem anderen Widget nur dann eine eigene Boundary, wenn ein Vergleich dieselbe lange Aufgabe zeigt.

## Ein Abschnitt mit Bedienelementen lädt mit seiner Seite [#a-section-with-controls-loads-with-its-page]

Bevor React eine Seite hydriert, lädt der Router die Chunks der passenden Routen: `hydrate` in `@tanstack/router-core` wartet auf die Komponente und die Pending-Komponente jeder Route. Eine Komponente, die eine Seite mit Reacts `lazy` oder mit `lazyRouteComponent` nennt, gehört nicht dazu, also wird ihr Chunk bei einem vollständigen Laden erst angefragt, wenn React sie während der Hydration erreicht. Bis dieser Chunk ankommt, behält React die nächste `Suspense`-Boundary als HTML des Servers und verwirft jeden Klick darauf; es spielt den Klick nicht nach, wenn die Boundary hydriert ist. Die Panels des Admin-Dashboards wurden so geladen, und die ihnen nächste Boundary war die der Route, also ignorierte das ganze Dashboard unter dem Layout der Konsole Klicks, bis die Chunks der Panels ankamen. Auch der Kursplayer wurde so geladen, in einer eigenen Boundary, also tat sein Play-Button nichts, bis der Chunk des Players ankam.

Ein Teil mit einem Button, einem Link, einem Feld oder einer Tabelle wird deshalb von der Seite importiert, die ihn rendert, und nur ein Teil, der keinen Klick annimmt, lädt verzögert, in einer eigenen `Suspense`-Boundary. `source-layout.test.ts` folgt jedem Modul, das eine Datei unter `src/presentation` oder `src/routes` über `lazy` oder `lazyRouteComponent` lädt, und schlägt fehl, wenn eines React Aria, den Router, TanStack Form, TanStack Table oder den Videoplayer erreicht. Zeichnet ein Skeleton seine Teile aus einer Liste, enthält diese Liste nur, was Skeleton und Loader brauchen: `DASHBOARD_PANELS` in `panels-pending.tsx` nennt den `key`, das Skeleton und den `prefetch` jedes Panels, und `panels.tsx` ordnet jedem Schlüssel sein Panel in einem `Record` zu, dessen Typ diese Schlüssel vorgeben, sodass ein Panel ohne Eintrag oder ein Eintrag ohne Panel die Typprüfung nicht besteht. Das Skeleton der Kursseiten nimmt das Skeleton des Players aus `player-pending.tsx`. Die Komponente des Dashboards importiert `panels.tsx` und die der Lektion den Player, also kommen ihre Bedienelemente mit dem eigenen Chunk der Seite an, vor der Hydration, und die Skeletons bleiben so leicht wie zuvor.

Nur die Zeichnung der Diagramme des Dashboards lädt weiterhin verzögert. Mit Recharts im Chunk des Dashboards wertete der Browser es vor der Hydration aus, in derselben langen Aufgabe wie den Code des Dashboards, und ein vollständiges Laden von `/admin` blockierte den Hauptthread 98 ms länger als mit der Zeichnung in einem eigenen Chunk (Chromium bei 6-facher CPU-Drosselung, Mediane aus sechs abwechselnden Ladevorgängen). `TimeSeriesChart` rendert jetzt die Tabelle seiner Werte mit dem Panel und lädt die Balken, `TimeSeriesBars` in `time-series-bars.tsx`, mit `lazyRouteComponent` in einer eigenen Boundary, und der Loader des Dashboards lädt sie mit den Daten vor. Die Zeitraum-Buttons und die Währungs-Tabs wirken vom ersten Moment an; eine Zeichnung, die noch nicht angekommen ist, folgt einem Klick, sobald ihr Chunk da ist.

Der Test „a press on a dashboard panel right after a full load hydrates the console takes effect, however late the scripts arrive“ in `e2e/specs/admin-dashboard.spec.ts` verlangsamt jedes Skript, lädt `/admin`, klickt im Umsatz-Panel auf 12 Monate, sobald die Seitenleiste der Konsole hydriert ist, und prüft, dass das Panel umschaltet. Mit den verzögert geladenen Panels schlug er fehl, jetzt besteht er. Unten stehen das Einstiegsskript mit seinen statischen Importen, gzip-komprimiert, aus der Ausgabe von `bun run build:test`; das Desktop-Preset von Lighthouse bei 7-facher CPU-Drosselung, Mediane aus fünf abwechselnden Läufen; und die Zeit, die die langen Aufgaben, die Chromium bei einem vollständigen Laden mit 6-facher CPU-Drosselung aufzeichnete, den Hauptthread blockierten, Mediane aus zwölf Ladevorgängen von `/admin` und sieben einer Lektion. Die Simulation von Lighthouse meldet für `/admin` eine höhere Total Blocking Time, während die langen Aufgaben, die Chromium aufzeichnet, den Hauptthread kürzer blockieren:

## Ein einziger Tailwind-Build

Nur `src/presentation/styles/globals.css` führt Tailwind aus. Routen-Stylesheets wie `docs.css` und `typeset.css` sind einfaches CSS, und die eigenen Styles von Fumadocs kommen über `globals.css` herein:

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

Ein zweiter Tailwind-Build in einem Routen-Stylesheet lieferte einmal seine eigenen `.hidden`, `.rounded-md` und Theme-Variablen aus. Gleichnamige Cascade Layers werden über Stylesheets hinweg zusammengeführt, und React entfernt nie ein Stylesheet, das es mit `precedence` eingefügt hat, sodass die Landingpage nach einem Besuch der Dokumentation ihr responsives Layout und ihre Schriften bis zum Neuladen verlor. Der End-to-End-Test "landing keeps its responsive styles after visiting the docs" in `e2e/specs/landing.spec.ts` sichert das ab. Alles, was Tailwind braucht, läuft über `globals.css`.

## Medien

- **Landing-Loops.** Jede `src/presentation/assets/motion/<name>.webm` hat ein Posterbild `<name>.webp` mit genau den Abmessungen des Videos, damit der Übergang vom Posterbild zum Video nicht sichtbar schärfer wird. Die Abmessungen sind `LANDING_VIDEO_SIZES` in `src/data/landing-videos.ts`, die sowohl die Remotion-Kompositionen als auch `ConceptLoop` lesen. Kleinere Breiten sind eigene Dateien, `<name>-<width>.webp`, angeboten über das `srcSet` des Posterbilds. `landing-videos.test.ts` schlägt fehl, wenn die Größe eines Posterbilds von seiner Komposition oder von der Breite in seinem Dateinamen abweicht. Verkleinere nie das Posterbild in voller Größe; um es leichter zu machen, kodiere es in denselben Abmessungen neu. Die Videos laden mit `preload="none"`, spielen nur, solange ein Viertel davon sichtbar ist, und spielen nie für Leser, die reduzierte Bewegung bevorzugen. Die Schleife im Hero gleitet nach oben, ohne einzublenden (`--rise-opacity: 1` an ihrem `animate-rise`), weil ihr Poster auf einem Desktop-Bildschirm das größte Element über dem Falz ist und ein Poster, das aus der Transparenz einblendet, erst als gezeichnet gilt, wenn die Einblendung beginnt.
- **Die Kurstour** in `course-showcase.tsx` ist keine Schleife. Ihr `<video>` wird erst gerendert, wenn jemand auf Abspielen drückt, sodass die Seite bis dahin nur das Posterbild lädt: ein `<picture>` mit AVIF- und WebP-Quellen in den 1600 Pixeln des Videos und in 800 Pixeln. Das Video selbst wird als WebM mit MP4 als Ausweichformat ausgeliefert.
- **Kursvideos** werden vorab in adaptives HLS kodiert und mit dem Workers-Cache aus R2 ausgeliefert. Siehe [Videos](/docs/features/videos).
- **Per Scrollen gesteuertes Video.** Die Website hat derzeit keines. Ein Video, dessen Zeit der Scrollposition folgt, muss all-intra kodiert sein (jeder Frame ein Keyframe, `keyint=1`): Bei einer normalen Kodierung dauert ein Sprung etwa 200 ms, bei einer all-intra-Kodierung etwa 3 ms, und keine noch so starke Glättung in JavaScript macht aus einem Sprung von 200 ms ein flüssiges Scrubbing.

## Einblenden beim Scrollen

`Reveal` (`src/presentation/components/custom/landing-page/components/reveal.tsx`) blendet Abschnitte der Landingpage ein, wenn sie in den Viewport kommen. Es teilt einen `IntersectionObserver` zwischen allen Instanzen, entscheidet anhand des ersten Callbacks des Observers, ob ein Element unterhalb des sichtbaren Bereichs beginnt, und schreibt `data-reveal`-Attribute direkt, ohne React-State und ohne erneutes Rendern. Eine Version, die die Sichtbarkeit in React-State hielt, verdoppelte die Total Blocking Time, weil jeder Abschnitt neu renderte und die Seite zweimal das Layout berechnete. Verlagere es nicht zurück in State, und ersetze es nicht ohne Vergleichsmessung.

Zwei weitere Optimierungen wurden gemessen und verworfen: `content-visibility: auto` auf Abschnitten der Landingpage, was seiteninterne Links zu weiter unten liegenden Abschnitten kaputt machte, und das verzögerte Laden des Newsletter-Formulars, das gleich gut oder schlechter abschnitt, als es direkt zu rendern.

## Später geladene Inhalte behalten ihre Größe

Eine vorgerenderte Seite wird gezeichnet, bevor ein Skript läuft, also muss ein Abschnitt, der sich danach füllt, in den Platz passen, den er bekommen hat. Der Kursblock der Landingpage ist ein solcher Abschnitt: Er liest die veröffentlichten Kurse, sobald er in die Nähe gescrollt wird, und sein Platzhalter nahm früher zwei Kurse mit je sechs Lektionen an, sodass der Block beim Eintreffen der Kurse wuchs oder schrumpfte und alles darunter um hundert Pixel und mehr verschob. Seine Spalten haben jetzt eine feste Folge einzeiliger Zeilen, der Platzhalter zeichnet dieselben Zeilen, und seine Hinweise stehen in einem Rahmen von der Größe einer Spalte, sodass jeder Zustand bei jeder Breite dieselbe Höhe hat (siehe [Kurse](/docs/features/courses)). Die Sternanzahl auf der Landingpage macht es genauso, mit einem Skeleton so hoch wie die Zahl. Die Kurse ins vorgerenderte HTML zu schreiben, ist keine Option: Der Build hat keine Produktionsdatenbank, und die Landingpage bei jeder Anfrage im Worker zu rendern, würde die Zeit bis zum ersten Byte wieder hergeben, die das Vorrendern spart.
