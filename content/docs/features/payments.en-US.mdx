Payments run through Polar with the `@polar-sh/better-auth` plugin, which the polar area adds to Better Auth in `src/data/polar.auth-plugins.ts`:

```ts
export const POLAR_AUTH_PLUGINS = [
  {
    plugin: polar({
      client: polarCore,
      use: [portal(), webhooks({ onPayload: handlePolarEvent, secret: env.POLAR_WEBHOOK_SECRET })],
    }),
    rateLimitExemptPaths: [ROUTES.API_AUTH_POLAR.WEBHOOKS],
  },
] as const satisfies readonly AuthPluginEntry[]
```

The plugin adds the customer portal and the webhooks, which are exempt from Better Auth's rate limiter, and no checkout: its `checkout()` would create a checkout with the account's ID alone, so Polar would ask a signed-in buyer for their email again. Better Auth closes no path to HTTP, so `src/data/__test__/polar.auth-plugins.integration.test.ts` checks that the plugin's checkout path answers 404 and fails once `checkout()` is added to the plugin. An area that sells creates its checkouts with the Polar SDK after its own checks, as the licence area's `startCheckout` does (see [Licences](/docs/features/licences)).

`src/integrations/polar/polar.config.ts` creates `polarCore` from `POLAR_ACCESS_TOKEN` and `POLAR_SERVER`, which the plugin uses, and `polar`, the checkouts, licence keys and orders services built on it. `POLAR_ORGANIZATION_ID` scopes every Polar call that names an organisation; [Environment and bindings](/docs/reference/environment) lists them. `src/integrations/polar/polar.constants.ts` holds Polar's own values: `POLAR_ORDER_STATUS`, `POLAR_SUBSCRIPTION_STATUS`, `POLAR_RECURRING_INTERVAL`, `POLAR_LICENSE_KEY_STATUS` and `POLAR_WEBHOOK_EVENT`, each checked against the SDK's types, `POLAR_CHECKOUT_ID_PLACEHOLDER`, `POLAR_CUSTOMER_SESSION_TOKEN_PARAM`, and `POLAR_ID_MAX_LENGTH`, the length of every column that holds a Polar ID. It reads no environment, so the browser and the browser suite import it too. The polar area's paths, `API_AUTH_POLAR` and `API_AUTH_CUSTOMER_PORTAL`, are in `src/data/polar.routes.ts`. [Polar setup](/docs/getting-started/polar-setup) describes the products, licence keys, consent checkbox, tax behaviour, webhook and token this code expects in Polar, and `bun run polar:verify:<environment>` checks them.

## Webhooks

Polar posts to `/api/auth/polar/webhooks`. The plugin verifies the signature with `POLAR_WEBHOOK_SECRET` and passes each event to `handlePolarEvent` in `src/data/polar-events.ts`. An area that reacts to Polar events declares a list in `src/data/<area>.polar-events.ts` and adds it to `src/data/polar-events.entries.ts`. Each entry names the events it handles and the function that handles them:

```ts
export interface PolarEventHandler {
  readonly events: readonly models.WebhookEventType[]
  readonly handle: (event: webhooks.WebhookPayload) => Promise<void>
}
```

- `handlePolarEvent` runs the `handle` of every entry that lists the event's type, all at once, and waits for all of them.
- When one rejects, `handlePolarEvent` still waits for the others to finish, so no area stops halfway through its writes, and then rejects with an `AggregateError` of every failure. The plugin answers 500 and Polar delivers the event again later, so each handler must be safe to run twice for the same event. Polar disables an endpoint that keeps failing, and `polar:verify` reports a disabled endpoint.
- An event that no entry lists is acknowledged and goes nowhere.
- `POLAR_EVENTS` joins the events of every entry, sorted and each once. The webhook endpoint in Polar must send exactly these, and `polar:verify` compares them.
- The polar area adds an empty list in `src/data/polar.polar-events.ts`, so the barrel is never empty. The billing area copies orders and subscriptions into D1 in `src/data/billing.polar-events.ts` (see [Writing the copies](#writing-the-copies)), and the licence area grants and revokes licences in `src/data/license.polar-events.ts` (see [Licences](/docs/features/licences#webhooks-and-licences)).

`polar:verify` runs in Bun, outside the Worker, and reads `POLAR_EVENTS`, so `src/data/polar-events.ts` and every `<area>.polar-events.ts` import no server code. An area's `handle` loads its handlers when an event arrives:

```ts
const { licenseWebhookHandlers } = await import("~/src/modules/license/license.webhooks")
```

`src/data/__test__/polar-events.test.ts` imports `src/data/polar-events.ts` in Bun and fails when that import reaches the Worker's runtime.

## Orders and subscriptions in D1

The polar area keeps copies of Polar's orders and subscriptions in two D1 tables, `order` (`src/modules/order/`) and `subscription` (`src/modules/subscription/`), so that lists, searches and access checks can read them with SQL and keep working while Polar is slow. Polar stays the source: each row is Polar's record under Polar's ID, written only from Polar's webhooks and never edited by hand. [Modules](/docs/conventions/modules#tables-that-mirror-a-provider) gives the rules every such mirror table follows.

| Table          | Columns                                                                                                                                                                                                                                                                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `order`        | `id`, `user_id`, `customer_id`, `product_id`, `subscription_id`, `status` (`ORDER_STATUSES`), `currency`, `total_amount`, `refunded_amount`, `invoice_number`, `description`, `placed_at`, `changed_at`                                                                                             |
| `subscription` | `id`, `user_id`, `customer_id`, `product_id`, `product_name`, `status` (`SUBSCRIPTION_STATUSES`), `amount`, `currency`, `recurring_interval` (`SUBSCRIPTION_RECURRING_INTERVALS`), `recurring_interval_count`, `current_period_end`, `cancel_at_period_end`, `started_at`, `ended_at`, `changed_at` |

- `id`, `customer_id`, `product_id` and `subscription_id` are Polar's IDs, and every column copied from Polar takes Polar's field name. `subscription_id` has no foreign key, because Polar's events can arrive in any order.
- `user_id` links the account and stays empty for a customer without one. Deleting an account keeps its orders and subscriptions and empties their `user_id` (`ON DELETE SET NULL`).
- Amounts are in the currency's minor units, as Polar sends them. `description` is what the order bought, as Polar invoiced it, and `product_name` the name of the subscription's product as Polar last reported it.
- `placed_at` is when Polar created the order. `changed_at` is the version of Polar's record that the row holds: Polar's `modified_at`, or Polar's `created_at` for a record that never changed. The row's own `created_at` and `updated_at` record when D1 wrote it.
- The indexes serve the lists these copies exist for: `order_user_placed_at_idx` an account's orders and `order_status_placed_at_idx` the orders of a status, both by when they were placed; `subscription_user_status_idx` an account's subscriptions by status and `subscription_status_current_period_end_idx` the subscriptions of a status by the end of their period.
- `status` holds Polar's value as it is, `trial_ended` included, which Polar sets when a trial ends without a payment. Nothing grants access from a subscription's status yet; a check that does counts only `trialing` and `active` as a running subscription, so `trial_ended`, `past_due` and the other statuses never pass for one.

### Writing the copies

`src/data/billing.polar-events.ts` adds two entries to the Polar events (see [Webhooks](#webhooks)), and each loads its use case when an event arrives:

| Events                                                           | Use case                                                                            |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `order.created`, `order.updated`, `order.paid`, `order.refunded` | `recordOrder` in `src/modules/order/use-cases/record-order.ts`                      |
| `subscription.created`, `subscription.updated`                   | `recordSubscription` in `src/modules/subscription/use-cases/record-subscription.ts` |

- Each use case takes Polar's record, `models.Order` or `models.Subscription`, and writes it in one statement: an insert under Polar's ID that, when the row already exists, updates it only if the stored `changed_at` is not later than the record's. A newer version applies, an older one that arrives late changes nothing, and the same version delivered twice is written again with the same values. Of two different states with the same `modified_at`, the one written last stays until Polar changes the record again.
- The same statement fills `user_id` through `polarCustomerAccount` in `src/integrations/polar/polar.customers.ts`: the account whose ID is the customer's `external_id`, which the area that sells sets at checkout, as the licence area's `startCheckout` does. It stays empty when the customer has no `external_id` or when no account has that ID, for instance because the account was deleted.
- The licence area handles `order.paid` and `order.refunded` too. The copy takes them as well, so it holds the payment and the refund whether or not Polar also sends `order.updated` for them. `handlePolarEvent` runs both areas at once; when the copy fails, the delivery answers 500, and Polar's retry repeats both writes without changing what one of them already wrote.
- The admin dashboard reads the order copies to list the paid licence orders that have no licence (see [Licences](/docs/features/licences#orders-that-match-no-account)) and to total the revenue (see [Revenue on the dashboard](#revenue-on-the-dashboard)); no page reads the subscription copies yet.

## Customer portal

`ROUTES.API_AUTH_CUSTOMER_PORTAL` (`/api/auth/customer/portal`) opens the Polar customer portal of the signed-in account. The licence card on `/app/license` links to it.

## Revenue on the dashboard

The payments area declares the `order` permission statements (`read`, `update`, `refund`) in `src/data/payments.access.ts` and adds the **Revenue** panel to the dashboard in `src/data/payments.dashboard.ts`. Its query, `getRevenue` in `src/modules/order/use-cases/get-revenue.ts`, checks `order: ["read"]` and totals the paid order copies of a period per currency, refunds subtracted; [Admin dashboard](/docs/features/admin-dashboard#revenue) describes what it counts. The licence area's `get-unlicensed-orders` checks `order: ["read"]` too. [Orders and customers](/docs/features/orders) describes the admin screens that read the copies. No use case updates or refunds orders yet: refunds and payouts are done in Polar.
