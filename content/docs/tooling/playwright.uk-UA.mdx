Playwright тестує зібраний застосунок у справжніх браузерах. Набір тестів працює із середовищем Wrangler `test`: локальні D1, KV і R2 у `.wrangler/test`, фіктивні облікові дані з `.env.test` і тестова точка входу `src/platform/testing/worker.ts`, яка перехоплює запити до Resend і Polar.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:journey
```

| Скрипт             | Що запускає                                                   |
| ------------------ | ------------------------------------------------------------- |
| `test:e2e:install` | Встановлює Chromium і WebKit разом із системними залежностями |
| `test:e2e`         | Усі специфікації в Chromium і WebKit                          |
| `test:e2e:smoke`   | `e2e/specs/smoke.spec.ts` у Chromium                          |
| `test:e2e:pr`      | Усі специфікації в Chromium, як у CI для pull request         |
| `test:e2e:headed`  | Усі специфікації у видимих браузерах                          |
| `test:e2e:ui`      | Режим UI Playwright                                           |
| `test:journey`     | [Набір тестів шляху клієнта](#journey-suite) на preview       |

## Конфігурація [#configuration]

`playwright.config.ts` запускає специфікації з `e2e/specs/`, визначає проєкти `chromium` (Desktop Chrome) і `webkit` (Desktop Safari) та використовує `PLAYWRIGHT_BASE_URL` або `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` з `src/data/local-server.ts`). Локально команда вебсервера запускає `db:reset:test`, `build:test` і `start:test` та повторно використовує сервер, який уже відповідає за цією адресою. У CI збірку готує одне завдання, кожен із <RepositoryFact name="e2eShards" /> шардів, між якими розподілено набір тестів, розпаковує її, а Playwright лише запускає сервер ([CI/CD](/docs/tooling/ci-cd#checks)).

| Параметр   | Локально                                         | CI                                               |
| ---------- | ------------------------------------------------ | ------------------------------------------------ |
| Повтори    | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" />    |
| Воркери    | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" />    |
| Трасування | Зберігаються при збої                            | Під час першого повтору                          |
| Відео      | Вимкнено                                         | Зберігаються при збої                            |
| Звіт       | List і HTML                                      | GitHub і blob, який при збої об'єднується в HTML |

## Запуск поряд з іншими worktree [#running-beside-other-worktrees]

Тестова збірка приймає запити лише від хостів, яким довіряє в режимі тестування, бо Better Auth і посилання розсилки перевіряють хост запиту: `127.0.0.1:3000` і `localhost:3000`, а також `127.0.0.1` і `localhost` на портах від <RepositoryFact name="testServerFirstPort" /> до <RepositoryFact name="testServerLastPort" />, які задає `TEST_SERVER_PORTS` у `src/data/local-server.ts`. На будь-якому іншому порту сторінки входу й курсів не працюють, тому `playwright.config.ts` зупиняється ще до збірки, коли `PLAYWRIGHT_BASE_URL` вказує інший хост.

`PLAYWRIGHT_BASE_URL` — єдине налаштування, що обирає порт: Playwright відкриває цю адресу й запускає `start:test` на її порту. Коли інші worktree одночасно запускають свої набори тестів, дайте кожному worktree власний порт із діапазону. Перевірте, що на ньому ніщо не слухає, і запустіть набір там:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` нічого не виводить, коли порт вільний. Якщо він виводить процес, візьміть інший порт і не чіпайте цей сервер: зупиняйте лише сервери, які запустили ви.

Локально Playwright повторно використовує сервер, який уже відповідає за адресою, і тоді пропускає скидання бази даних і збірку, тож набір ніколи не повинен потрапити на сервер іншого worktree. Це гарантує `e2e/global-setup.ts`: перед першим тестом він знаходить через `lsof` процеси, що слухають порт, і зупиняє запуск, коли якийсь із них працює в іншому каталозі, ніж цей worktree. Сервер, який ви запустили з цього worktree, проходить перевірку й використовується як є, тож зупиніть його, коли набір має перевірити свіжу збірку.

## Структура

- `e2e/specs/`: специфікації для smoke-перевірок, лендингу та його елементів керування, навігації, локалей, теми, SEO, автентифікації з її переадресаціями й маршрутизацією, робочих просторів, адміністрування користувачів, розсилки, контенту, юридичних сторінок, регіональних цін, воронки оплати, сторінки ліцензії, API ліцензій для CLI, партнерської програми, відео, курсів, доступу до курсів, адміністрування курсів, футера, кілець фокусу, смуг прокручування і доступності (файлів: <RepositoryFact name="e2eSpecs" />).
- `e2e/pages/`: об'єкти сторінок (page objects).
- `e2e/fixtures/`: розширена фікстура `test`, помічники для перехоплених листів, `deliverPaidOrder` у `license.ts`, який надсилає підписаний вебхук `order.paid`, щоб видати ліцензію, `buyLicense`, який просить тестовий Worker за адресою `/__test/polar/purchase` про замовлення з ліцензійним ключем у тестовому дублері Polar і надсилає їхні підписані `order.paid` і `benefit_grant.created`, `startedCheckouts`, який читає з `/__test/polar/checkouts` оплати, створені дублером, `payCheckout`, який оплачує відкриту застосунком оплату через `/__test/polar/pay` тестового Worker з позначеною згодою й надсилає підписані `order.paid` і `benefit_grant.created` її замовлення, `accessibilityViolations` зі світлою й темною схемами `COLOR_SCHEMES` в `accessibility.ts` і сторінка оплати Polar у `polar-checkout.ts`. Дублер Polar дає кожній оплаті URL-адресу на походженні оплати Polar, а фікстура `polarCheckout` у кожному контексті браузера відповідає на цю адресу сторінкою дублера, прочитаною з `/__test/polar/checkout` тестового Worker: вона повідомляє накладці, що завантажилася, а її кнопки **Pay** і **Close** надсилають `confirmed` і `success` або `close` до `embed_origin` оплати, як це робить сторінка Polar. `payInCheckoutOverlay` і `closeCheckoutOverlay` натискають їх, а `refusePolarCheckoutEmbedding` віддає сторінку з `frame-ancestors 'none'`, як Polar робить для хоста, якого не перелічує його організація. Набір тестів шляху клієнта встановлює опцію `polarCheckoutDouble` у `false` і платить у справжній пісочниці. `orderLicense` надсилає лише `order.paid` такої покупки й повертає `issueKey`, який пізніше надсилає її `benefit_grant.created`. Відкрита як власна сторінка оплати Polar, поза фреймом, кнопка **Pay** дубля спрямовує браузер на адресу успіху оплати з `customer_session_token`, як це робить сторінка Polar, а `payOnPolarCheckoutPage` її натискає.
- `e2e/data/accounts.ts`: засіяні облікові записи (адміністратора й клієнта) та їхній пароль. Клієнт із ліцензією, сама ліцензія та ліцензії, на яких специфікація API ліцензій для CLI активує пристрої, по одній на кожен паралельний воркер, — у `e2e/data/licenses.ts`.
- `e2e/data/videos.ts` і `e2e/data/courses.ts`: засіяне тестове відео, файли якого лежать у `e2e/fixtures/video/`, і засіяний курс: один розділ із безкоштовним переглядом, уроком для акаунтів і двома платними уроками, один з яких без відео.
- `e2e/data/<area>.pages.ts` і `e2e/data/<area>.seed.ts`: сторінки кожного розділу, які відвідують `accessibility.spec.ts` і `workspaces.spec.ts`, а також його рядки й медіафайли в тестовій базі даних, які об’єднують `pages.entries.ts` і `seed.entries.ts`.
- `e2e/data/<area>.flows.ts`: сценарії кожного розділу, кожен із тестом, який доводить його наскрізно, або з причиною, чому такого тесту немає; їх об’єднує `flows.entries.ts`. Див. [Покриття тестами](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: глобальне налаштування, яке зупиняє запуск, коли сервер на порту набору працює з іншого worktree.
- `e2e/journey/`: [набір тестів шляху клієнта](#journey-suite) з власною конфігурацією.

Тестовий Worker запускає те, що розділи оголошують у `e2e/data/<area>.worker.ts` і що об'єднує `worker.entries.ts`: розділ ліцензій додає тестові ліцензійні ключі в мок Polar, Resend відкриває `/__test/emails` для читання перехоплених листів, а розділ розсилки — `/__test/newsletter` для читання стану підписника.

## Доступність

`e2e/specs/accessibility.spec.ts` запускає [axe-core](https://github.com/dequelabs/axe-core) через `@axe-core/playwright` на публічних сторінках, на сторінках курсів, на головній сторінці документації, на кожній сторінці розділу «Конвенції» та на одній сторінці з кожного іншого розділу документації, у записі блогу і в робочих просторах адміністратора й клієнта у світлій і темній темах. Сторінки адмінпанелі охоплюють `/admin/courses`, `/admin/courses/create` і редактор тестового курсу, які також відвідує `e2e/specs/workspaces.spec.ts`. Специфікація застосовує правила рівнів A та AA з WCAG 2.0, 2.1 і 2.2, а також найкращі практики axe, падає, якщо сторінка не завантажується з успішним статусом, прокручує сторінку, щоб перевірити й розділи, що з'являються під час прокручування, чекає завершення скінченних анімацій і падає за будь-якого порушення, вказуючи правило, його вплив і відповідні селектори.

axe не бачить ні проходу клавіатурою, ні макета, тож три специфікації перевіряють їх для заголовка й футера сайту: `e2e/specs/navigation.spec.ts` — що меню на телефоні переводить фокус на себе, тримає Tab усередині, робить сторінку позаду `inert` і повертає фокус на свою кнопку; `e2e/specs/footer.spec.ts` — що на 320, 390 і 430 px жодною мовою два посилання футера не торкаються одне одного й не виходять за межі футера, а посилання на розділ головної сторінки є поточним лише на своєму розділі; і `e2e/specs/focus-rings.spec.ts` — що перемикач мови у футері й тригер палітри команд в адмінці малюють своє кільце для клавіатури.

`e2e/specs/text-layout.spec.ts` перевіряє форму курсу й таблиці адмінпанелі та конструктор команди на головній сторінці за 1440, 1280, 768 і 390 px за допомогою `textLayoutProblems` з `e2e/fixtures/text-layout.ts`: жоден рядок тексту не накладається на інший чи на іконку, жоден не обрізаний без трьох крапок, жоден не скорочений трьома крапками до кількох літер, сторінка ніколи не прокручується вбік, і кожна вкладка мови у формі курсу видима.

## Смуги прокручування [#scrollbars]

`e2e/specs/scrollbars.spec.ts` запускає Chromium без перемикача `--hide-scrollbars` від Playwright через `ignoreDefaultArgs` у `launchOptions`, тож Chromium малює класичні смуги прокручування, які займають місце, як у Windows, у Linux і на Mac, де смуги показуються завжди. Spec перевіряє, що юридична сторінка, сторінка автентифікації та сторінка адмінпанелі тримають заголовок на місці, коли вікно росте, доки сторінка не перестане прокручуватися (сторінка документації прокручується завжди, бо після її макета на всю висоту вікна йде футер сайту), що відкриття пошуку документації, вибору мови, діалогу чи меню нічого не зсуває, що `/admin` заповнює вікно і що вікно за темною сторінкою темне у світлій темі. WebKit на macOS малює лише накладні смуги прокручування, які не займають місця, і жоден параметр запуску цього не змінює, тож перевірка зарезервованого місця працює лише в Chromium. Меню сайту, яке нижче `lg` замінює посилання заголовка, перевіряється на 768 px: його відкриття й закриття нічого не зсуває.

## Набір тестів шляху клієнта [#journey-suite]

`bun run test:journey` купує ліцензію та користується CLI так, як це робить клієнт, на preview-розгортанні за адресою `https://preview.saasyland.com`, яке приймає платежі в пісочниці Polar. `e2e/journey/playwright.config.ts` — окрема конфігурація з власним проєктом Chromium і без вебсервера, тому ні `test:e2e`, ні перевірки pull request її не запускають; поки що її не запускає й жоден workflow, а сторінка [Покриття тестами](/docs/tooling/test-coverage#journey-suite) перелічує, що потрібно, щоб запускати її в CI. Кожен план — окремий тест, тести виконуються паралельно, і кожен проходить такі кроки:

1. **Обліковий запис.** Тест реєструється з новою адресою тестової скриньки Resend, `delivered+journey-<run>-<tier>@resend.dev`, а в тесті підвищення плану — з `upgrade` замість плану, знаходить лист підтвердження через API Resend і відкриває посилання з нього.
2. **Ціна.** `/app/license` має пропонувати план за ціною для країни, у якій Cloudflare розташовує runner, як повідомляє `/cdn-cgi/trace`: за регіональною ціною в країні з `PPP_TIERS` і за повною ціною в будь-якій іншій.
3. **Оплата.** Checkout пісочниці Polar має відкритися поверх `/app/license`, не залишаючи сторінки, у фреймі з `sandbox.polar.sh`, який отримує фокус, з уже заповненою адресою електронної пошти облікового запису й не відміченою згодою на негайне надання; тест відмічає її у фреймі. Тест платить [тестовою карткою Stripe](https://docs.stripe.com/testing) з адресою для рахунку в Польщі, де ця адреса складається лише з країни. Сторінка має отримати повідомлення Polar `loaded`, `confirmed` і `success` саме в такому порядку, закрити накладку й показати активну ліцензію на `/app?checkoutId=<id>&tier=<tier>`. Polar вбудовує оплату у фрейм лише тоді, коли організація в пісочниці перелічує `preview.saasyland.com` у [Settings > Embedding](/docs/getting-started/polar-setup#embedding).
4. **Замовлення та ключ.** У Polar має бути одне оплачене замовлення на продукт плану за ціною, яку пропонувала `/app/license`, зі згодою та мовою покупця, підтвердження покупки має надійти до поштової скриньки, а `/app/license` має показувати ключ, який видали вебхуки, команди CLI й жодного зайнятого пристрою.
5. **CLI.** Опублікований CLI, який запускається як <RepositoryFact name="cliExec" />, так само як команди на `/app/license`, звертається до preview через `SAASYLAND_API_URL`. `activate` записує файл облікових даних із режимом `0600`, повторна активація зберігає те саме місце, а `whoami` показує пристрій. CI-пристрої, які розрізняє `SAASYLAND_CI_REPOSITORY`, займають решту місць, до <ActivationLimit tier="core" /> пристроїв у плані Core, <ActivationLimit tier="complete" /> у плані Complete і <ActivationLimit tier="agency" /> у плані Agency, а наступний отримує відмову з `activationLimitReached`. Щойно на `/app/license` звільняють місце, його отримує пристрій, якому відмовили, а звільнений отримує `activationNotFound`. `deactivate` звільняє перший пристрій і видаляє його облікові дані.
6. **Повернення коштів.** Тест повертає кошти за замовлення через API пісочниці Polar і чекає, доки `/app/license` покаже ліцензію як повернену; після цього `whoami` має відповісти `licenseRefunded` і видалити облікові дані.

Четвертий тест підвищує план ліцензії. Він так само купує план Core і займає <ActivationLimit tier="core" /> пристрої плану Core, а наступний відхиляється. Потім `/app/license?tier=complete` має пропонувати план Complete за його ціною для країни runner-а мінус вартість замовлення Core, і тест так само сплачує цю різницю в оформленні замовлення Polar поверх сторінки. Polar має містити замовлення підвищення на суму різниці, із замовленням і планом Core в `upgrade_from_order` і `upgrade_from_tier`; ключ замовлення Core тепер має дозволяти <ActivationLimit tier="complete" /> пристроїв плану Complete, ключ, який Polar надав за замовлення підвищення, має бути вимкнений, а `/app/license` має показувати план Complete з тим самим ключем. Потім відхилений пристрій і наступний активуються, а ще наступний відхиляється. Тест повертає кошти за замовлення підвищення через API пісочниці Polar: ліцензія має знову бути планом Core, з тим самим ключем і лімітом Core, уже активовані пристрої працюють далі, а новий відхиляється. Повернення коштів за замовлення Core потім завершує ліцензію.

Кожен пристрій CLI — це каталог у теці результатів тесту, який CLI використовує як домашній каталог, а CLI працює із середовищем, де є лише `PATH`, цей каталог, кеш npm і змінні `SAASYLAND_*`, тож жодні облікові дані набору до нього не потрапляють. Замовлення, яке невдалий тест залишає оплаченим, повертається після завершення тесту. Облікові записи залишаються на preview, кожен із поверненою ліцензією.

Набір читає ці значення із середовища або з `.env.preview`, якщо файл існує, і без них зупиняється перед першим тестом:

| Змінна                                                                          | Для чого                                                                                                                                                                         |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | Читання замовлень і повернення коштів у пісочниці та читання їхніх ліцензійних ключів, з областями доступу `orders:read`, `refunds:write`, `benefits:read` і `license_keys:read` |
| `POLAR_SERVER`                                                                  | Має дорівнювати `sandbox`                                                                                                                                                        |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Продукти в пісочниці, яких мають стосуватися замовлення                                                                                                                          |
| `RESEND_API_KEY`                                                                | Читання листів підтвердження, які надіслав preview; для цього потрібен ключ із повним доступом                                                                                   |

На preview має працювати збірка з [API ліцензій для CLI](/docs/features/cli-licence-api). Там працює `main`, який `deploy.yml` розгортає туди перед production; щоб протестувати гілку до злиття, розгорніть її командою `gh workflow run preview.yml --ref <branch>`, щойно її перевірки пройдуть. Пісочниця має відповідати коду, що перевіряє `bun run polar:verify:preview`. Далі:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

Звіт записується в `playwright-report/journey/`, а трейси, відео й каталоги пристроїв невдалих тестів — у `test-results/journey/`.
