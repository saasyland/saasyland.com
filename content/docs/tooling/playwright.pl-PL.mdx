Playwright testuje zbudowaną aplikację w prawdziwych przeglądarkach. Zestaw testów działa w środowisku Wranglera `test`: lokalne D1, KV i R2 w `.wrangler/test`, fikcyjne dane uwierzytelniające z `.env.test` i testowy punkt wejścia `src/platform/testing/worker.ts`, który przechwytuje żądania do Resend i Polar.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:journey
```

| Skrypt             | Uruchamia                                                          |
| ------------------ | ------------------------------------------------------------------ |
| `test:e2e:install` | Instaluje Chromium i WebKit wraz z zależnościami systemowymi       |
| `test:e2e`         | Wszystkie specyfikacje w Chromium i WebKit                         |
| `test:e2e:smoke`   | `e2e/specs/smoke.spec.ts` w Chromium                               |
| `test:e2e:pr`      | Wszystkie specyfikacje w Chromium, tak jak w CI dla pull requestów |
| `test:e2e:headed`  | Wszystkie specyfikacje w widocznych przeglądarkach                 |
| `test:e2e:ui`      | Tryb UI Playwright                                                 |
| `test:journey`     | [Zestaw testów ścieżki klienta](#journey-suite) na preview         |

## Konfiguracja [#configuration]

`playwright.config.ts` uruchamia specyfikacje z `e2e/specs/`, definiuje projekty `chromium` (Desktop Chrome) i `webkit` (Desktop Safari) i używa `PLAYWRIGHT_BASE_URL` lub `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` z `src/data/local-server.ts`). Lokalnie polecenie serwera WWW uruchamia `db:reset:test`, `build:test` i `start:test` oraz ponownie wykorzystuje serwer, który już odpowiada pod tym adresem. W CI jedno zadanie przygotowuje build, każdy z <RepositoryFact name="e2eShards" /> shardów, między które podzielony jest zestaw testów, rozpakowuje go, a Playwright jedynie uruchamia serwer ([CI/CD](/docs/tooling/ci-cd#checks)).

| Ustawienie     | Lokalnie                                         | CI                                            |
| -------------- | ------------------------------------------------ | --------------------------------------------- |
| Ponowienia     | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" /> |
| Workery        | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" /> |
| Ślady (traces) | Zachowywane przy błędzie                         | Przy pierwszym ponowieniu                     |
| Nagrania wideo | Wyłączone                                        | Zachowywane przy błędzie                      |
| Reporter       | Lista i HTML                                     | GitHub i blob, scalane do HTML przy błędzie   |

## Uruchamianie obok innych worktree [#running-beside-other-worktrees]

Build testowy przyjmuje żądania tylko z hostów, którym ufa w trybie testowym, bo Better Auth i linki newslettera sprawdzają host żądania: `127.0.0.1:3000` i `localhost:3000` oraz `127.0.0.1` i `localhost` na portach od <RepositoryFact name="testServerFirstPort" /> do <RepositoryFact name="testServerLastPort" />, wyznaczonych przez `TEST_SERVER_PORTS` w `src/data/local-server.ts`. Na każdym innym porcie strony logowania i kursów kończą się błędem, więc `playwright.config.ts` zatrzymuje się, zanim cokolwiek zbuduje, gdy `PLAYWRIGHT_BASE_URL` wskazuje inny host.

`PLAYWRIGHT_BASE_URL` to jedyne ustawienie, które wybiera port: Playwright otwiera ten adres i uruchamia `start:test` na jego porcie. Gdy inne worktree uruchamiają swoje testy w tym samym czasie, każde worktree dostaje własny port z zakresu. Sprawdź, że nic na nim nie nasłuchuje, a potem uruchom na nim testy:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` nic nie wypisuje, gdy port jest wolny. Jeśli wypisze proces, weź inny port i zostaw ten serwer w spokoju: zatrzymuj tylko serwery uruchomione przez Ciebie.

Lokalnie Playwright ponownie wykorzystuje serwer, który już odpowiada pod adresem, i pomija wtedy reset bazy danych i build, więc testy nigdy nie mogą trafić na serwer innego worktree. Pilnuje tego `e2e/global-setup.ts`: przed pierwszym testem sprawdza przez `lsof` procesy nasłuchujące na porcie i przerywa przebieg, gdy któryś z nich działa w innym katalogu niż to worktree. Serwer uruchomiony przez Ciebie z tego worktree przechodzi sprawdzenie i jest wykorzystywany taki, jaki jest, więc zatrzymaj go, gdy testy mają sprawdzić świeży build.

## Struktura

- `e2e/specs/`: specyfikacje testów smoke, strony głównej i jej kontrolek, nawigacji, języków, motywu, SEO, uwierzytelniania z jego przekierowaniami i routingiem, obszarów roboczych, administracji użytkownikami, newslettera, treści, stron prawnych, cen regionalnych, ścieżki zakupu, strony licencji, API licencji CLI, programu partnerskiego, wideo, kursów, dostępu do kursów, administracji kursami, stopki, obramowań fokusu, pasków przewijania i dostępności (liczba plików: <RepositoryFact name="e2eSpecs" />).
- `e2e/pages/`: obiekty stron (page objects).
- `e2e/fixtures/`: rozszerzony fixture `test`, funkcje pomocnicze do obsługi przechwyconych e-maili, `deliverPaidOrder` w `license.ts`, który wysyła podpisany webhook `order.paid`, aby przyznać licencję, `buyLicense`, który prosi testowy Worker pod `/__test/polar/purchase` o zamówienie z kluczem licencyjnym w dublerze testowym Polar i wysyła ich podpisane `order.paid` i `benefit_grant.created`, `startedCheckouts`, który odczytuje z `/__test/polar/checkouts` płatności utworzone przez dublera, `payCheckout`, który opłaca płatność otwartą przez aplikację przez `/__test/polar/pay` testowego Workera, z zaznaczoną zgodą, i wysyła podpisane `order.paid` i `benefit_grant.created` jej zamówienia, oraz `accessibilityViolations` z jasnym i ciemnym schematem kolorów (`COLOR_SCHEMES`) w `accessibility.ts`.
- `e2e/data/accounts.ts`: wstępnie utworzone konta, administratora i klienta, oraz ich hasło. Klient z licencją, jego licencja oraz licencje, na których specyfikacja API licencji CLI aktywuje maszyny, po jednej na każdy równoległy worker, są w `e2e/data/licenses.ts`.
- `e2e/data/videos.ts` i `e2e/data/courses.ts`: wstępnie utworzony film testowy, którego pliki są w `e2e/fixtures/video/`, oraz wstępnie utworzony kurs: jeden rozdział z darmowym podglądem, lekcją dla zalogowanych i dwiema płatnymi lekcjami, z których jedna nie ma filmu.
- `e2e/data/<area>.pages.ts` i `e2e/data/<area>.seed.ts`: strony każdego obszaru, które odwiedzają `accessibility.spec.ts` i `workspaces.spec.ts`, oraz jego wiersze i media w testowej bazie danych, łączone przez `pages.entries.ts` i `seed.entries.ts`.
- `e2e/data/<area>.flows.ts`: przepływy każdego obszaru, każdy z testem, który potwierdza go end-to-end, albo z powodem, dla którego testu brakuje, łączone przez `flows.entries.ts`; zobacz [Pokrycie testami](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: globalny setup, który przerywa przebieg, gdy serwer na porcie testów działa z innego worktree.
- `e2e/journey/`: [zestaw testów ścieżki klienta](#journey-suite) z własną konfiguracją.

Testowy Worker uruchamia to, co obszary deklarują w `e2e/data/<area>.worker.ts`, połączone przez `worker.entries.ts`: obszar licencji zapisuje testowe klucze licencyjne w dublerze Polar, Resend udostępnia `/__test/emails` do odczytu przechwyconych e-maili, a obszar newslettera `/__test/newsletter` do odczytu stanu subskrybenta.

## Dostępność

`e2e/specs/accessibility.spec.ts` uruchamia [axe-core](https://github.com/dequelabs/axe-core) przez `@axe-core/playwright` na stronach publicznych, na stronach kursów, na stronie głównej dokumentacji, na każdej stronie sekcji Konwencje i na jednej stronie z każdej pozostałej sekcji dokumentacji, we wpisie na blogu oraz w obszarach roboczych administratora i klienta, w jasnym i ciemnym motywie. Strony administracji obejmują `/admin/courses`, `/admin/courses/create` i edytor wstępnie utworzonego kursu, które odwiedza też `e2e/specs/workspaces.spec.ts`. Stosuje reguły WCAG 2.0, 2.1 i 2.2 na poziomach A i AA oraz dobre praktyki axe, kończy się niepowodzeniem, gdy strona nie wczyta się ze statusem powodzenia, przewija stronę, aby sprawdzić też sekcje pojawiające się przy przewijaniu, czeka na zakończenie skończonych animacji i kończy się niepowodzeniem przy każdym naruszeniu, podając regułę, jej wagę i selektory elementów.

axe nie widzi ani przebiegu klawiatury, ani układu, więc trzy specyfikacje sprawdzają je w nagłówku i stopce witryny: `e2e/specs/navigation.spec.ts`, że menu na telefonie przenosi fokus do siebie, zatrzymuje Tab w środku, czyni stronę pod spodem `inert` i oddaje fokus swojemu przyciskowi; `e2e/specs/footer.spec.ts`, że przy 320, 390 i 430 px w żadnym języku żadne dwa linki stopki się nie stykają ani nie wychodzą poza stopkę oraz że link do sekcji strony głównej jest bieżący tylko na swojej sekcji; a `e2e/specs/focus-rings.spec.ts`, że przełącznik języka w stopce i wyzwalacz palety poleceń w panelu administracyjnym rysują swoje obramowanie dla klawiatury.

## Paski przewijania [#scrollbars]

`e2e/specs/scrollbars.spec.ts` uruchamia Chromium bez przełącznika `--hide-scrollbars` Playwrighta, przez `ignoreDefaultArgs` w `launchOptions`, więc Chromium rysuje klasyczne paski przewijania, które zajmują miejsce, jak w Windows, w Linuksie i na Macu ustawionym tak, by zawsze je pokazywał. Spec sprawdza, że strona prawna, strona uwierzytelniania i strona panelu administracyjnego trzymają nagłówek w miejscu, gdy okno rośnie, aż strona przestaje się przewijać (strona dokumentacji przewija się zawsze, bo po jej layoucie na całą wysokość okna następuje stopka witryny), że otwarcie wyszukiwarki dokumentacji, wyboru języka, okna dialogowego lub menu niczego nie przesuwa, że `/admin` wypełnia okno i że okno za ciemną stroną jest ciemne w jasnym motywie. WebKit na macOS rysuje tylko nakładkowe paski przewijania, które nie zajmują miejsca, i żadna opcja uruchomienia tego nie zmienia, więc sprawdzenie zarezerwowanego miejsca działa tylko w Chromium. Menu witryny, które poniżej `lg` zastępuje linki nagłówka, jest sprawdzane przy 768 px: jego otwarcie i zamknięcie niczego nie przesuwa.

## Zestaw testów ścieżki klienta [#journey-suite]

`bun run test:journey` kupuje licencję i używa CLI tak jak klient, na wdrożeniu preview pod adresem `https://preview.saasyland.com`, które przyjmuje płatności w sandboksie Polar. `e2e/journey/playwright.config.ts` to osobna konfiguracja z własnym projektem Chromium i bez serwera WWW, więc ani `test:e2e`, ani kontrole pull requestów jej nie uruchamiają i na razie nie uruchamia jej żaden workflow: [Pokrycie testami](/docs/tooling/test-coverage#journey-suite) wymienia, czego potrzeba, żeby uruchamiać ją w CI. Każdy plan to osobny test, testy działają równolegle, a każdy przechodzi przez te kroki:

1. **Konto.** Test rejestruje się nowym adresem testowej skrzynki Resend, `delivered+journey-<run>-<tier>@resend.dev`, a w teście przejścia na wyższy plan z `upgrade` zamiast planu, znajduje e-mail weryfikacyjny przez API Resend i otwiera zawarty w nim link.
2. **Cena.** `/app/license` musi oferować plan w cenie dla kraju, w którym Cloudflare umieszcza runnera, tak jak podaje `/cdn-cgi/trace`: w cenie regionalnej w kraju z `PPP_TIERS`, a w pełnej cenie w każdym innym.
3. **Płatność.** Checkout sandboksu Polar musi się otworzyć z wypełnionym adresem e-mail konta i niezaznaczoną zgodą na natychmiastowe dostarczenie; test zaznacza ją na stronie Polar. Test płaci [kartą testową Stripe](https://docs.stripe.com/testing), z adresem rozliczeniowym w Polsce, gdzie adres rozliczeniowy to tylko kraj.
4. **Zamówienie i klucz.** Polar musi mieć jedno opłacone zamówienie na produkt danego planu, w cenie zaoferowanej na `/app/license`, ze zgodą i językiem kupującego, potwierdzenie zakupu musi dotrzeć do skrzynki, a `/app/license` musi pokazywać klucz wydany przez webhooki, polecenia CLI i brak używanych maszyn.
5. **CLI.** Opublikowane CLI, uruchamiane jako <RepositoryFact name="cliExec" /> tak jak polecenia z `/app/license`, komunikuje się z preview przez `SAASYLAND_API_URL`. `activate` zapisuje plik z danymi uwierzytelniającymi z trybem `0600`, ponowna aktywacja zachowuje to samo miejsce, a `whoami` pokazuje maszynę. Maszyny CI, rozróżniane przez `SAASYLAND_CI_REPOSITORY`, zajmują pozostałe miejsca, do <ActivationLimit tier="core" /> maszyn w planie Podstawa, <ActivationLimit tier="complete" /> w planie Komplet i <ActivationLimit tier="agency" /> w planie Agencja, a kolejna zostaje odrzucona z kodem `activationLimitReached`. Gdy na `/app/license` zostanie zwolnione miejsce, dostaje je odrzucona maszyna, a zwolniona otrzymuje `activationNotFound`. `deactivate` zwalnia pierwszą maszynę i usuwa jej dane uwierzytelniające.
6. **Zwrot.** Test zwraca pieniądze za zamówienie przez API sandboksu Polar i czeka, aż `/app/license` pokaże licencję jako zwróconą; wtedy `whoami` musi odpowiedzieć `licenseRefunded` i usunąć dane uwierzytelniające.

Czwarty test przenosi licencję na wyższy plan. Kupuje plan Podstawa w ten sam sposób i zajmuje <ActivationLimit tier="core" /> maszyny planu Podstawa, a następna zostaje odrzucona. Potem `/app/license?tier=complete` musi oferować plan Komplet w cenie dla kraju runnera pomniejszonej o koszt zamówienia planu Podstawa, a test płaci tę różnicę w checkoucie Polar. Polar musi mieć zamówienie przejścia na wyższy plan na kwotę różnicy, z zamówieniem i planem Podstawa w `upgrade_from_order` i `upgrade_from_tier`; klucz zamówienia planu Podstawa musi teraz dopuszczać <ActivationLimit tier="complete" /> maszyn planu Komplet, klucz, który Polar przyznał za zamówienie przejścia, musi być wyłączony, a `/app/license` musi pokazywać plan Komplet z tym samym kluczem. Potem odrzucona maszyna i następna zostają aktywowane, a kolejna zostaje odrzucona. Test zwraca pieniądze za zamówienie przejścia przez API sandboksu Polar: licencja musi znów być planem Podstawa, z tym samym kluczem i limitem planu Podstawa, już aktywowane maszyny dalej działają, a nowa zostaje odrzucona. Zwrot za zamówienie planu Podstawa kończy potem licencję.

Każda maszyna CLI to katalog w folderze wyników testu, którego CLI używa jako katalogu domowego, a CLI działa ze środowiskiem zawierającym wyłącznie `PATH`, ten katalog, pamięć podręczną npm i zmienne `SAASYLAND_*`, więc nie trafiają do niego żadne dane uwierzytelniające zestawu. Zamówienie, które nieudany test zostawi opłacone, zostaje zwrócone po zakończeniu testu. Konta zostają na preview, każde ze zwróconą licencją.

Zestaw odczytuje te wartości ze środowiska albo z `.env.preview`, jeśli plik istnieje, i bez nich zatrzymuje się przed pierwszym testem:

| Zmienna                                                                         | Do czego służy                                                                                                                                               |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POLAR_ACCESS_TOKEN`                                                            | Odczyt zamówień i zwroty w sandboksie oraz odczyt ich kluczy licencyjnych, z zakresami `orders:read`, `refunds:write`, `benefits:read` i `license_keys:read` |
| `POLAR_SERVER`                                                                  | Musi mieć wartość `sandbox`                                                                                                                                  |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Produkty w sandboksie, których muszą dotyczyć zamówienia                                                                                                     |
| `RESEND_API_KEY`                                                                | Odczyt e-maili weryfikacyjnych wysłanych przez preview, do czego potrzebny jest klucz z pełnym dostępem                                                      |

Na preview musi działać build z [API licencji CLI](/docs/features/cli-licence-api): pull request wdraża tam swoją gałąź w jobie **Deploy preview**. Sandbox musi zgadzać się z kodem, co sprawdza `bun run polar:verify:preview`. Następnie:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

Raport trafia do `playwright-report/journey/`, a ślady, nagrania i katalogi maszyn nieudanych testów do `test-results/journey/`.
