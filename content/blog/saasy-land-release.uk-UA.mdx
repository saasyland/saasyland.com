## Що таке SaaSy Land?

SaaSy Land — це комерційний стартовий набір для SaaS на React. CLI ставить запитання щодо конфігурації та генерує лише ті модулі, які ви обрали: автентифікацію у вашій власній базі даних, платежі, транзакційну пошту, адмінпанель, інтернаціоналізацію та візуальний конструктор сторінок. Ви отримуєте тестові файли (<RepositoryFact name="testFiles" />) і обов’язкову перевірку покриття, яка вже їх контролює, тож отриманий код перевірений, а не просто наявний.

Вихідний код публічного сайту поширюється за ліцензією MIT; окремий CLI і приватні шаблони є пропрієтарними. Придбайте ліцензію, увійдіть на saasyland.com і отримайте ключ, потрібний для встановлення та використання CLI. Онлайн-перевірка ліцензії стосується CLI. Згенеровані застосунки можна редагувати й розгортати за комерційною ліцензією, і для них не потрібен ключ під час виконання. Ліцензія сайту не надає прав на торговельну марку SaaSy Land.

## Оберіть стек, виконайте одну команду

CLI — це не шаблон, який ви завантажуєте, а потім із ним боретеся. Він запитує, що ви будуєте, і генерує саме це, тож той самий інструмент створює і побічний проєкт з одним тенантом, і багатотенантний продукт із merchant of record.

```bash
bunx saasyland@latest init my-app \
  --framework tanstack \
  --tenancy multi \
  --billing polar \
  --content mdx \
  --email resend
```

Деякі з варіантів, із навмисно нудними прапорцями, щоб команда працювала, коли її вставляють у скрипт, а не в промпт:

| Запитання      | Варіанти                                          | Чому це запитання                                                                                                                                    |
| -------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Фреймворк      | `tanstack`, `next`, `react-router`                | Підтримуються всі три; оберіть той, який ваша команда вже знає                                                                                       |
| Тенанти        | `single`, `multi`                                 | Якщо додати організації згодом, доведеться змінити кожен уже написаний запит                                                                         |
| Автентифікація | `better-auth`, `--no-auth`                        | Better Auth у вашій власній базі даних або жодних облікових записів для інструмента, якому вони не потрібні                                          |
| Пошта          | `resend`, `plunk`, `--no-email`                   | Транзакційна пошта, вбудована в сценарії автентифікації, або жодної                                                                                  |
| Платежі        | `polar`, `stripe`, `lemonsqueezy`, `--no-billing` | Polar і Lemon Squeezy є merchant of record і беруть на себе ПДВ у ЄС і податок із продажів у США. Stripe — ні. Засновник ухвалює це рішення один раз |
| Контент        | `mdx`, `--no-content`                             | Блог і документація або нічого з цього                                                                                                               |

Змініть відповідь — і команда зміниться разом із нею. Запустіть її знову для наступного проєкту: відповіді змінюються, а CLI і довічні оновлення — ні.

### Чому обов’язкова перевірка покриття сьогодні важливіша, ніж на момент запуску

Коли вийшла версія 2.0, показник покриття був аргументом якості. Відтоді він став аргументом пропускної здатності, адже велику частку коду, який додають до кодових баз SaaS, тепер пише агент.

У [Stack Overflow Developer Survey 2025](https://survey.stackoverflow.co/2025/ai) 84% розробників повідомили, що використовують або планують використовувати інструменти ШІ, а найчастіше згадуваним розчаруванням, яке назвали 45%, був результат ШІ, що «майже правильний, але не зовсім». Поріг, який блокує злиття, — найдешевша доступна відповідь на це: агент не може додати поведінку, не додавши тест, а все, що він зламає, виявляється в pull request, а не в клієнта.

Ми докладно писали про це в статтях [чому якість роботи агента визначає ваш репозиторій](/blog/ai-coding-agents-repository-readiness) і [як обрати стек для ШІ-агентів програмування](/blog/choosing-a-saas-stack-for-ai-coding-agents). Коротко: цей репозиторій набирає 17 із 20 балів за нашою власною шкалою готовності — завдяки побудові, а не зусиллям.

## Перевірте кожне твердження до оплати

Жодних відгуків, бо в цитаті нічого перевірити. Кожне число про кодову базу на цій сторінці вимірюється в публічному репозиторії сайту, і ось де перевірити кожне твердження.

| Твердження                                                                                | Де перевірити                                                                                                          |
| ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 100% покриття тестами                                                                     | `coverage/coverage-summary.json`, генерує `bun run test:coverage`                                                      |
| Обов’язкове, а не лише у звіті                                                            | `.github/workflows/ci.yml`, на кожному pull request і push до main                                                     |
| Справжні браузери, а не jsdom                                                             | `e2e/specs`, набори Playwright (<RepositoryFact name="e2eSpecs" />), Chromium на кожному pull request і WebKit на main |
| Мови (<RepositoryFact name="languages" />), валюти (<RepositoryFact name="currencies" />) | `messages/` і `src/modules/_core/constants`, перевіряє `bun run check:i18n`                                            |
| Суворі типи, нуль `any`                                                                   | `bun run check`, включно із суворою перевіркою типів                                                                   |
| Компоненти у вашому репозиторії (<RepositoryFact name="uiComponents" />)                  | `src/presentation/components/shadcn`, редагований вихідний код                                                         |

<Accordion title={"Що таке SaaSy Land?"}>

SaaSy Land — це готовий до продакшну стартовий набір для SaaS на React. CLI ставить запитання щодо конфігурації та генерує лише те, що ви обрали: автентифікацію у вашій власній базі даних, платежі, транзакційну пошту, адмінпанель, інтернаціоналізацію (мови: <RepositoryFact name="languages" />) і візуальний конструктор сторінок, а також тестові файли (<RepositoryFact name="testFiles" />) і обов’язкову перевірку покриття на 100%, які вже працюють у CI. Один платіж від <TierPrice tier="core" />, без плати за користувача.

<Accordion title={"Скільки коштує SaaSy Land?"}>

Три тарифи з одноразовою оплатою. Core коштує <TierPrice tier="core" /> і містить пропрієтарний CLI і редагований вихідний код згенерованого застосунку, кожен модуль, який може згенерувати CLI, повний набір тестів і довічні оновлення основи. Agency коштує <TierPrice tier="agency" /> і додає необмежену кількість клієнтських проєктів, місця для команди в курсі та на reactprojects.com, приватний канал у Discord з автором, 60-хвилинну консультацію з архітектури та файли Figma для конструктора сторінок. </Accordion>

<Accordion title={"Чи справді SaaSy Land має 100% покриття тестами?"}>

Так, для інструкцій, гілок, функцій і рядків, і це обов’язкова перевірка, а не значок. Файли Vitest (<RepositoryFact name="testFiles" />) плюс набори Playwright (<RepositoryFact name="e2eSpecs" />) у справжніх браузерах, Chromium на кожному pull request і WebKit на main, а поріг перевіряється на кожному pull request через `.github/workflows/ci.yml`. Виконайте `bun run test:coverage` у репозиторії, і звіт згенерується заново.

</Accordion>

<Accordion title={"Який стек використовує SaaSy Land 2.0?"}>

Публічний еталонний застосунок використовує TanStack Start і React 19 на Cloudflare Workers, типізовані серверні функції, Better Auth, Drizzle з Cloudflare D1, Zod, Polar, Resend, use-intl, Tailwind CSS 4, shadcn/ui і Fumadocs. Bun і Vite+ відповідають за розробку, перевірки, тести та збірки. Конфігуратор CLI пропонує доступні альтернативи для згенерованих проєктів.

</Accordion>

<Accordion title={"Чому Better Auth, а не Clerk чи Auth0?"}>

Володіння і маржа. Хмарна автентифікація бере плату за кожного активного користувача на місяць, тому ваші витрати зростають саме тоді, коли мав би зростати дохід. Better Auth живе у вашій кодовій базі та вашій базі даних, а отже ваші користувачі — це рядки, якими володієте ви, логіка автентифікації — це вихідний код, який можна читати й розширювати, і немає ліцензійної плати за автентифікацію кожного користувача; витрати на хостинг і базу даних, як і раніше, залежать від використання.

</Accordion>

<Accordion title={"Чи можна використовувати SaaSy Land для клієнтських проєктів?"}>

Тариф Agency за <TierPrice tier="agency" /> охоплює необмежену кількість клієнтських проєктів і готовий до використання під власним брендом, тож ви можете постачати його стільком клієнтам, скільком виставляєте рахунки. </Accordion>

<Accordion title={"Чи обов’язково використовувати кожну частину?"}>

Ні. CLI ставить запитання щодо конфігурації та генерує лише те, що ви обрали, тож автентифікацію, платежі, пошту й контент можна вимкнути прапорцем `--no-auth`, `--no-billing`, `--no-email` або `--no-content`.
