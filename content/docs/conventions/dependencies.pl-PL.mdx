Repozytorium działa na najnowszym wydaniu każdej zależności. Aktualizację, która coś psuje, naprawia się do przodu, w kodzie lub w projekcie źródłowym, nigdy przez cofnięcie się.

## Wersje narzędzi

- Bun jest menedżerem pakietów i narzędziem do uruchamiania skryptów. `packageManager` w `package.json` (Bun <RepositoryFact name="bunVersion" />) to jedyne miejsce, w którym ustawia się jego wersję; CI odczytuje ją stamtąd. `bun.lock` jest zapisany w repozytorium.
- Node pochodzi z `.nvmrc` (<RepositoryFact name="nodeVersion" />), a `engines.node` wymaga co najmniej tej wersji.
- Jedynym wyjątkiem jest `remotion/`, z własnym zestawem narzędzi npm, instalowanym tylko przy edycji filmów strony głównej.

## Aktualizacja

1. Przeczytaj changelog i przewodnik migracji nowej wersji, najlepiej kopię dostarczoną w `node_modules/<package>`.
2. Zmień kod tak, by odpowiadał udokumentowanemu użyciu nowej wersji.
3. Weryfikuj w tej kolejności i nie zgłaszaj niczego jako ukończonego, zanim ostatni krok nie przejdzie:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` i testy działają bez buildu Cloudflare i TanStack Start, więc mogą przejść, gdy build jest zepsuty. Zdarzyło się to dwa razy podczas jednej aktualizacji: nowego `@polar-sh/sdk` nie dało się zbundlować, a wydanie TanStack Start zmieniło znaczniki `modulepreload`, które przepisuje `optimize-prerendered-html.ts`. Oba problemy ujawniły się dopiero w `build:test`. Po buildzie `find dist/server -name '*.map'` nie może niczego wypisać; `upload_source_maps: false` w `wrangler.jsonc` istnieje, ponieważ Worker z mapami źródeł jest większy, niż Cloudflare przyjmuje przy przesyłaniu (zobacz [Cloudflare Workers](/docs/integrations/cloudflare-workers)).

Nigdy nie przypinaj pakietu do starszego wydania, aby uniknąć zmiany niekompatybilnej wstecz, i nigdy nie dodawaj do aplikacji kodu, który obchodzi błąd biblioteki.

## Gdy błąd leży w projekcie źródłowym

Gdy aplikacja już stosuje udokumentowane użycie, a nowa wersja działa błędnie, zachowaj nową wersję i utrzymuj poprawkę:

1. Udowodnij błąd minimalną reprodukcją poza tym repozytorium.
2. Napisz najmniejszą zmianę, która naprawia go w pakiecie, odzwierciedlającą poprawkę, którą zaproponujesz w projekcie źródłowym, i zapisz ją przez `bun patch`. Patch trafia do `patches/<package>@<version>.patch` i do `patchedDependencies`, a pakiet zostaje przypięty do tej dokładnej wersji, żeby patch nadal się nakładał.
3. Zgłoś błąd w projekcie źródłowym i otwórz pull request z poprawką, zgodnie z zasadami współtworzenia tego projektu.
4. Usuń patch, gdy tylko poprawka trafi do wydania. Zanim zachowasz lub udokumentujesz patch, sprawdź poleceniem `npm view <package> version`, czy to wydanie już się ukazało.

Obecne patche to `patches/@videojs%2Futils@10.3.0.patch`, który naprawia adresy URL miniatur storyboardu w odtwarzaczu wideo (razem z nim `@videojs/react` jest przypięty do wersji 10.3.0), `patches/@fumadocs%2Fbase-ui@16.19.0.patch`, dzięki któremu bloki kodu bez tytułu nie są nienazwanymi punktami orientacyjnymi typu region (`@fumadocs/base-ui` jest przypięty do wersji 16.19.0) oraz `patches/fumadocs-core@16.19.0.patch`, dzięki któremu `usePathname` w adapterze TanStack zwraca stronę, którą router pokazuje, gdy ładuje się następna (`fumadocs-core` jest przypięty do wersji 16.19.0). W ten sam sposób utrzymywano patch do `fumadocs-mdx` 15.6.0 i usunięto go, gdy wersja 15.6.1 dostarczyła poprawkę z projektu źródłowego.

## Ostrzeżenia o podatnościach

Alerty Dependabota obejmują `remotion/package-lock.json`, ale GitHub nie czyta `bun.lock`, więc sprawdzaj aplikację przez `bun audit`, a projekt wideo przez `npm audit` w `remotion/`. Usuwaj podatność najnowszym wydaniem pakietu, który wciąga podatny pakiet. Jeśli zakres wersji tego pakietu już dopuszcza poprawione wydanie, wystarczy odświeżyć lockfile: `bun update` albo `npm update` w `remotion/`.

Dopóki żadne wydanie pakietu nadrzędnego nie dopuszcza poprawki, wpis w `overrides` podnosi wersję podatnego pakietu i zostaje usunięty, gdy tylko zrobi to wydanie pakietu nadrzędnego. Obecne wpisy:

- `package.json`: `"minimatch": "^11.0.1"`. `shadcn` dociera do `minimatch` ^10 przez `ts-morph` 26 i `@ts-morph/common`, a GHSA-g3hv-75wg-m249 naprawia dopiero `minimatch` 11.0.1. Usuń go, gdy `shadcn` będzie zależał od wydania `ts-morph` zawierającego [dsherret/ts-morph#1697](https://github.com/dsherret/ts-morph/pull/1697).
- `remotion/package.json`: `minimatch` ^11.0.1 pod `@typescript-eslint/typescript-estree`, z powodu tego samego ostrzeżenia. `@remotion/eslint-config-flat` przypina `typescript-eslint` do wersji 8.71.2, której parser wymaga `minimatch` ^10. Usuń go, gdy `@remotion/eslint-config-flat` będzie zależał od wydania `typescript-eslint` zawierającego [typescript-eslint/typescript-eslint#13145](https://github.com/typescript-eslint/typescript-eslint/pull/13145).

`bun audit` nadal zgłasza dwa ostrzeżenia, dla których nie ma poprawki do wdrożenia:

- `deepmerge` 4.3.1 (GHSA-gcqx-w48m-w2h4, niska), przez `shadcn` i `@shadcn/registry`. Poprawione wydanie nie istnieje, jego CVE odrzucono jako nieopisujące podatności, a [github/advisory-database#10910](https://github.com/github/advisory-database/issues/10910) prosi GitHub o wycofanie ostrzeżenia.
- `esbuild` 0.18.20 (GHSA-67mh-4wv8-2f99, umiarkowana), przez `drizzle-kit` i `@esbuild-kit/esm-loader`. `drizzle-kit` 0.31.11 deklaruje ten loader, ale nigdy go nie importuje, a ostrzeżenie dotyczy serwera deweloperskiego esbuild, którego nic tutaj nie uruchamia. [drizzle-team/drizzle-orm#5304](https://github.com/drizzle-team/drizzle-orm/issues/5304) śledzi jego usunięcie; wersje release candidate `drizzle-kit` 1.0 już od niego nie zależą.

## Wpisy Vite+ w package.json

```json
"vite": "npm:@voidzero-dev/vite-plus-core@1.6.0",
"vite-plus": "1.6.0",
"vitest": "5.1.0"
```

Te wiersze oraz ten sam alias `vite` i wersja `vitest` w `overrides` to dokładnie to, co zapisuje migrator Vite+: `vite-plus` jest przypięty do dokładnej wersji, Bun potrzebuje rdzenia jako bezpośredniej zależności `vite`, a `vitest` jest wymieniony, ponieważ potrzebują go `@vitest/coverage-v8` i typy testów. Aktualizuj je razem przez `vp migrate`, nigdy przez `bun update`. Aby sprawdzić, czy któryś z nich można usunąć, skopiuj projekt, uruchom `vp migrate` na kopii i porównaj wynik; nie rozstrzygaj tego rozumowaniem. Wpis `minimatch` w `overrides` to opisana wyżej poprawka bezpieczeństwa i `vp migrate` zostawia go bez zmian.

`build.rolldownOptions.external` w `vite.config.ts` wymienia opcjonalne zależności peer `@polar-sh/sdk`, które nie są zainstalowane i są usuwane z Workera przez tree-shaking; zobacz [Vite+](/docs/tooling/vite-plus). Usuń tę listę, gdy Polar naprawi swoje pakowanie.

## Dodawanie zależności

Najpierw sprawdź, czy zadania nie wykonuje już pakiet obecny w `package.json`, aby każde zagadnienie miało jedną bibliotekę. Zależność runtime dodawaj przez `bun add`, narzędzie przez `bun add --dev`, a jeśli istnieje umiejętność agenta danego dostawcy w `skills-lock.json`, korzystaj z niej (zobacz [Umiejętności agentów](/docs/tooling/agent-skills)).
