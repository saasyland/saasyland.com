`src/routes` のファイルはすべて同じ形をしているため、1 つを知っていればすべてがわかります。ルートファイルは組み立てを担い、ページに必要なものを宣言してコンポーネントを配置します。ウィジェット、フォーム、ダイアログ、テーブルのカラムは `src/presentation/components/custom` に置きます。

## ページルート

`src/routes/admin.courses.index.tsx` の例です。

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        onReorder={({ offset, row }) => move.mutateAsync({ courseId: row.id, offset })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        search={t("table.search")}
        selectable
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.ADMIN_COURSES),
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **コンポーネント**は `<Name>Page` という名前のローカルな `const` で、最初に定義します。このページだけで使う小さなマークアップは、`_site._marketing.courses.$course.index.tsx` の `CourseProgress` や `StartLink` のように、ローカルなコンポーネントとしてその上に置いてもかまいません。独自のデータ、ミューテーション、状態を持つものはすべてコンポーネントファイルに置きます。
- **名前空間は 1 つ。** `const NAMESPACE = "pages.<feature>.<page>"` は `export const Route` の直上に置き、`loadPageMetadata`、`preloadNamespaces`、`staticData` で使います。ページが必要とするその他の名前空間は、レイアウトが宣言します。
- **`Promise.all` は 1 つ。** ローダーは、ページのメタデータ、名前空間、コンポーネントが読み取るすべてのクエリを一度に開始し、`head` のために `{ locale, metadata }` を返します。どれかを await してから次を開始してはいけません。
- **`head: pageHead(ROUTES.X)`** は、名前空間ファイルのメタデータからタイトル、説明、正規 URL、代替リンクを組み立てます。
- **パスは `src/routes.ts` の `ROUTES` から取得します。** `ROUTES` はすべてのエリアのパスをまとめたものです（[パスとナビゲーション](#paths-and-navigation)を参照）。 パスのリテラルを書いてはいけません。

タイトルがレコードから決まるページは、`admin.courses.$courseId.tsx` のように、そのレコードを await し、ローダーのデータから head を組み立てます。

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  head: ({ loaderData }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  pendingComponent: AdminCourseEditorPending,
})
```

## レイアウトルート

`src/routes/admin.courses.tsx` の例です。

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- レイアウトは `export const Route` の上で `const NAMESPACES = [...] as const` を宣言し、それをプリロードします。名前空間がない場合はオプションごと省略し、`namespaces: []` とは書きません。
- レイアウトは、配下のページとそのコンポーネントが必要とするすべての名前空間を、ほかの機能のものも含めて、`NAMESPACES` にただの文字列として挙げます。`/app` は、概要にライセンスカードと購入案内を、ライセンスページに撤回のカードを表示するため、`pages.license`、`pages.withdrawal`、`withdrawal.validations` を挙げます。`/admin/users` は `pages.admin.customers`、`pages.admin.orders`、`pages.admin.users.license` を挙げます。`/_site/_marketing` と `/_site/docs` は、フッターにニュースレターのフォームを表示するため `auth.validations` を挙げ、マーケティングのレイアウトはさらに `withdrawal.validations` も挙げます。機能を外すとそのメッセージファイルが削除され、刈り込みのルールがそれらを指す文字列をそれぞれ削除します（[テスト](/docs/conventions/testing#tests-follow-the-features)）。
- レイアウトがコンポーネントを描画する場合、その名前は `<Name>Layout` とし、`<Outlet />` を配置します。
- ガードは、そのエリアを所有するレイアウトの `beforeLoad` に置きます。`admin.tsx` では `beforeLoad: requireAdmin`、`app.tsx` では `requireSignedIn` で、どちらも認証のエリアのレイアウトです。ガードが決めるのはナビゲーションだけで、各サーバー関数は引き続き自分で権限をチェックします。

## オプションの順序

TanStack Router は宣言順に型を推論し、各オプションの型はそれより上のオプションから決まるため、`src/routes` では `sort-keys` を無効にしています。オプションはアルファベット順に並べますが、ルーターが型を推論する経路になるオプションだけは、データ読み込みのガイドが示す順に並べます。`validateSearch` を先頭に置いて検索パラメーターを読み取るどのオプションよりも前にし、続けて `loaderDeps`、`context`、`beforeLoad`、`loader` の順に置き、`head`、`headers`、`scripts` は `loader` のデータを読むので `loader` の後に置きます。こうすると `head` は手書きの型なしで loader の戻り値の型をそのまま受け取り、これらのオプションを別の順で宣言したルートは `code-style/route-option-order` で失敗します。

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

`createFileRoute` の中にデータの配列やオブジェクトを直接書いてはいけません。その上で定数として宣言します。

## 検索パラメーター

`validateSearch` は、`src/lib/search-params.ts` のヘルパーで組み立てた `zod.object` です。

| ヘルパー                          | パラメーターがない、または不正な場合の値 | 用途                                   |
| --------------------------------- | ---------------------------------------- | -------------------------------------- |
| `searchText()`                    | `undefined`                              | トークン、メールアドレス、エラーコード |
| `searchFlag()`                    | `undefined`                              | 真偽値                                 |
| `searchParam(schema)`             | `undefined`                              | パスなど、その他のスキーマ             |
| `searchChoice(choices, fallback)` | `fallback`                               | タブやビュー                           |

テキストがない場合は `undefined` のままなので、ルーターが組み立てる URL にデフォルト値が紛れ込むことはありません。`searchChoice` のパラメーターには `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }` を組み合わせ、URL からデフォルト値を取り除きます。ほかのサイトが訪問者を戻すページは、`/app` と `/app/license` が Polar のチェックアウトのためにしているように、自分のスキーマで `search: { middlewares: [onlyDeclaredSearch(schema)] }` も宣言します。するとルーターは宣言したパラメーターだけでアドレスを組み立て、サーバーはほかのパラメーターを含むアドレスを、それを除いた同じアドレスへリダイレクトします。これはガードやページがそのパラメーターを読む前に行われます。`typeof search["x"] === "string"` のようなチェックを手書きしてはいけません。新しい種類のフィールドが必要になったら、ヘルパーを追加します。ページが存在を検証したパラメーターを子が必要とする場合は、`auth.reset-password.tsx` が `token` を `ResetPasswordForm` に渡しているように、ページが型を絞り込んでから下に渡します。同じパラメーターを読み取るページは、読み取るモジュールの `.zod.ts` にある 1 つのスキーマを共有し、そのスケルトンも同じスキーマでパースします。`/app/license` と、ライセンスのエリアが概要ページに追加する部分が `licenseSearchSchema`（`src/modules/license/license.zod.ts`）を共有しているのがその例です。

## スケルトン

ナビゲーションは一瞬で終わるように感じられなければなりません。そのため、ページを描画するすべてのルートは、そのページを再現する `pendingComponent` を持ちます。レイアウトも、カードも、行数も同じです。

- スケルトンはエリアのペンディングファイル（`admin/products-pending.tsx`、`courses/courses-pending.tsx`）に置き、shadcn の `Skeleton` を使います。
- スケルトンはすべてのページのエントリースクリプトに含まれるため、スケルトンがインポートするのは `Skeleton`、shadcn のプリミティブ、他のスケルトン、長さを決める定数だけで、フォームやフォームを含むファイルは決してインポートしません。いずれかが `@tanstack/react-form` に到達すると `pending-imports.test.ts` が失敗します（[パフォーマンス](/docs/conventions/performance#skeletons-stay-in-the-entry-script)を参照）。
- テキストのプレースホルダーには、実際のタイポグラフィのトークンに `h-lh scale-y-70` を加え、置き換える行と同じ高さにします（`<Skeleton className="h-lh w-28 scale-y-70 text-label" />`）。
- リストの長さは、ページが使う定数から取ります。`data-grid-pending.tsx` の `DataGridPending` は、既定で、すべての管理画面のテーブルのページサイズである `DEFAULT_PAGE_SIZE` 行を描画します。
- レイアウトのスケルトンは、現在のパスでそのレイアウトより下にあるルートのうち、`pendingComponent` を持つ最初のルートの `pendingComponent` を描画します。これは `src/hooks/use-page-pending.ts` の `usePagePending(layout)` がルートツリーから読み取ります。`AdminPending`、`AppPending`、`AuthPending`、`MarketingPending` はそれぞれのレイアウトで、`AdminUsersPending` と `AdminCourseSectionPending` はその 1 階層下でこれを行います。そのため、どのレイアウトが表示する場合でも、ページのスケルトンを指定するのはそのページのルートだけです。`/admin/users` は `/admin/users/all` へリダイレクトするため、リダイレクト先のページのスケルトンを設定します。
- ルーター全体の `defaultPendingComponent` はありません。`src/router.tsx` は、どちらも `src/data/navigation.constants.ts` の値を使って、`defaultPendingMs` を <RepositoryFact name="navigationPendingMs" unit="millisecond" /> に、`defaultPendingMinMs` を <RepositoryFact name="navigationPendingMinMs" unit="millisecond" /> に設定します。前者の時間までに完了しないナビゲーションはルートのスケルトンを表示し、スケルトンはページの準備ができた時点で消え、それ以上表示され続けることはありません。各ルートはこれらの値をそのまま使います。その根拠となる計測については [パフォーマンス](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) を参照してください。
- ドキュメントのページは、スケルトンをドキュメントのレイアウトの内側に描画します。`DocsIndexPending` と `DocsPagePending` は Fumadocs の記事と目次のグリッド領域を埋めるため、ドキュメントのページ間のナビゲーションでもサイドバーは画面に表示されたままです。ページコンポーネントは MDX を専用の `<Suspense key={path}>` でレンダリングします。そのため、ページの MDX チャンクが読み込まれる前でもサイドバーが動作し、ナビゲーションでは前のページのサーバー HTML を次のページのデータでハイドレートせずに置き換えます。

## リンク

- ルーターのリンクには定数を渡します。`<Link to={ROUTES.COURSES}>`、`<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`、あるいは動的なパスであれば `params` 付きのルートパターンです。shadcn の `LinkButton` と `SidebarMenuLink` も同じように `to` を受け取り、ルートツリーの外のアドレスには `AnchorButton` が `href` を受け取ります。
- ルーターのリンクにロケールプレフィックスを付けてはいけません。ルーターの rewrite が付けます。文字列としてルーターの外に出る値のために現在のロケールの完全な URL が必要な場合は、`use-auth-redirect.ts` がサインインのリンクを組み立てるときのように、`router.buildLocation({ ... }).publicHref` から取得します。`localizePathname` は、ルーターのコンテキストの外で組み立てる URL や、別のロケールの URL に使います。メール、Better Auth のリダイレクト先、MDX 内のリンク、言語切り替えがこれにあたります。

## パスとナビゲーション [#paths-and-navigation]

各パスと各メニュー項目は、1 つのリストに一度だけ書きます。コース、商品、法務ページのように外せる機能は、自分のパスを名指しする 1 つの要素としてそのリストに加わります。機能を外すとそのファイルと名前が削除され、それとともにそれらを名指しする要素もすべて削除されるため、リストには機能ごとのファイルもバレルも要りません。`saasyland` CLI はこの仕組みでテンプレートのレイヤーからプロジェクトを組み立てます。アプリケーションが読み込まない `scripts/features.ts` だけが、オプションの機能をそのファイルと持っているパスとともに列挙しており、`bun run check:features` はそれを使って機能を 1 つずつ外したサイトをチェックします（[テスト](/docs/conventions/testing#tests-follow-the-features)）。

| 対象                             | 宣言する場所                                                                                                                                                                                                      | 読み取り元                                                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| パス                             | `src/routes.ts`：パスごとに 1 つの `export const`                                                                                                                                                                 | `import * as ROUTES from "~/src/routes"`                                                                              |
| リクエストごとに描画するパス     | `src/routes.ts` の `REQUEST_RENDERED_ROUTES`                                                                                                                                                                      | `src/routes.ts` の `isRequestRenderedRoute`                                                                           |
| メニュー項目                     | `src/data/navigation.ts` の `ADMIN_NAVIGATION`、`ADMIN_COMMAND_ACTIONS`、`ADMIN_DASHBOARD_ACTIONS`、`APP_NAVIGATION`、`APP_RESOURCE_NAVIGATION`、`HEADER_NAVIGATION`、`FOOTER_NAVIGATION`（表示する順に並べます） | サイドバー、ヘッダー、フッター、コマンドパレット、ダッシュボード                                                      |
| レイアウトの名前空間             | レイアウトルートの `NAMESPACES`                                                                                                                                                                                   | レイアウトのローダーと `staticData`                                                                                   |
| 管理画面とワークスペースのリスト | `DASHBOARD_STATS`、`DASHBOARD_PANELS`、`COMMAND_SEARCHES`、`USER_TABS`、`USER_PROFILE_SECTIONS`、`ACCOUNT_DELETION_NOTICES`（いずれも、それを描画するコンポーネントの中）                                         | そのコンポーネント、そのスケルトン、データを読み込むルート                                                            |
| 公開サイトのチェック             | `src/lib/deployment.ts` の `LIVE_SITE_CHECKS`                                                                                                                                                                     | `verifyDeployment`（[プラットフォームとテスト](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)） |

`src/routes.ts` はすべてのパスを宣言し、何もインポートしません。ブラウザー、コールドスタートごとの Worker、Bun のスクリプト、Playwright、`vite.config.ts`、Remotion プロジェクトのすべての実行環境が読み込むからです。どのファイルもこれを 1 つの名前空間としてインポートします（`import * as ROUTES from "~/src/routes"`）。そのため各パスはリテラル型を保ち、`<Link to={ROUTES.COURSES}>` は引き続きルートツリーに対して型検査されます。`BLOG` から組み立てる `BLOG_FEED` のように、ほかのパスから組み立てるパスは、元になるパスの後に置きます。

Worker とビルドのリストも同じです。`src/server.ts` の `REQUEST_HANDLERS` と `DOCUMENT_REWRITES`、`vite.config.ts` の `VITE_PLUGINS` もリテラルのリストで、オプションの機能はそこに 1 つの要素として加わります。

`src/data/navigation.ts` は 7 つのメニューをリテラルのリストとして持ちます。各項目は `to` にそのページを、`label` にメッセージの完全なキーを持ち、管理画面とワークスペースでは `lucide-react` のアイコンも持ちます。管理画面のメニューは項目をサイドバーのグループ（`ADMIN_NAVIGATION_GROUP` の `key`）の下にまとめ、フッターはリンクを列（`FOOTER_COLUMN` の `key`）の下にまとめます。このファイルがインポートするのは `lucide-react`、`~/src/routes`、`~/src/data/navigation.constants` だけです。Remotion プロジェクトが管理画面のメニューを読み込み、その CI ジョブは Remotion 自身のパッケージしかインストールしないからです。ほかのものをインポートすると `src/__test__/source-layout.test.ts` が失敗します。管理画面と顧客ワークスペースはサインインがあって初めて存在するため、それらの項目は認証のエリアのパスを名指しし、エリアと一緒に消えます。ヘッダーとフッターの **ログイン** も同じです。

```ts title="src/data/navigation.ts"
export const HEADER_NAVIGATION: readonly SiteEntry[] = [
  { hash: MARKETING_SECTION_IDS.PRICING, label: "navigation.core.header.pricing", to: ROUTES.HOME },
  { label: "navigation.courses.header.courses", to: ROUTES.COURSES },
  { label: "navigation.content.header.blog", to: ROUTES.BLOG },
  { label: "navigation.content.header.docs", to: ROUTES.DOCS },
  { label: "navigation.auth.header.signIn", signedIn: { label: "navigation.auth.header.account" }, to: ROUTES.SIGN_IN },
]
```

コースの機能を外してビルドしたサイトには `ROUTES.COURSES` がないため、刈り込みのルールがヘッダーの **講座** 項目を削除し、それによって空になったグループや列も一緒に削除されます。法務ページのないサイトで、フッターの法的情報の列が消えるのと同じです。

ヘッダーやフッターのエントリは、サインイン済みの訪問者向けに自分のラベルを置き換える `signedIn` ラベルを指定でき、そのリンクは訪問者のワークスペースに向かいます。管理者権限を持つアカウントは `/admin`、それ以外は `/app` です。`Navigation`、`MobileMenu`、`Footer` は、両方のメニューを `useSiteNavigation`（`src/hooks/use-site-navigation.ts`）から読みます。このフックはワークスペースがわかると `signedIn` のエントリのリンク先をそこに向け、わからなければリストをそのまま返します。ワークスペースは `WORKSPACE_HOOKS` にある唯一のフック `useVisitorWorkspace`（`src/hooks/use-visitor-workspace.ts`）から受け取ります。このフックが、セッションのロールから `hasPermission` と、`requireAdmin` が確認する `admin: ["access"]` 権限で決めます。サインインのないプロジェクトにはフックがないため、メニューはそのままです。

ラベルはスクリプトが動く前に決まります。`SiteEntryLabel`（`src/presentation/components/custom/site-entry-label.tsx`）は、こうしたエントリの両方のラベルを描画しますが、場所を取るのは表示中のラベルだけです。そのため、どの言語でもリンクの幅はそのラベルの文字の幅になり、ヘッダーのほかのリンクと同じ間隔で並びます。`<html>` に `data-session` が付くと、`globals.css` の `signed-in` バリアントが **ログイン** の代わりに **マイアカウント** を表示します。Worker は、Better Auth のセッション Cookie を持つリクエストに返すすべての HTML ページにこの属性を設定します（`markSession`、[キャッシュと SSR](/docs/architecture/caching-and-ssr#prerendering) を参照）。そのため、プリレンダリングされたページも最初から正しいラベルで届き、読み込み中にリンクが動くことはありません。セッションがわかるまで、リンクの行き先は `/auth/sign-in` です。このページはサインイン済みの訪問者をワークスペースへ送り、それ以外の人にはフォームを表示します。ハイドレーション後、`useVisitorWorkspace` は Worker が印を付けたページでだけセッションを問い合わせ、リンクをワークスペースに向け、印をセッションと一致させ続けます。Cookie の背後にあるセッションが終わっていれば印を外し、訪問者がリロードせずにサインインすれば印を付けます。サインアウトしたブラウザは何も問い合わせません。Better Auth の前回使用したサインイン方法の Cookie はそのブラウザに残っていますが、この Cookie はサインインページがその方法に **前回使用** と表示できるよう、サインアウト後も残るものです。各メニューはリンクのキーにリストでの位置を使うため、React はリンクを置き換えずに同じリンクを書き換え、セッションの読み込み中に始まった押下もそのリンクに届きます。ページの一部がハイドレートされるまで、`useVisitorWorkspace` は何も返しません。React のハイドレーション中は `useHydrated` がサーバーの値を返すためです。セッションが届いた後にハイドレートされるフッターもサーバーと同じ HTML を描画し、その後で切り替わるので、ハイドレーションが壊れません。

管理画面のエントリはすべて、実データで動作する画面を開きます。ランディングページはそれらをすべて数えます。データの取得元がまだない画面には、エントリがありません（[管理ダッシュボード](/docs/features/admin-dashboard#real-data-only)を参照）。

顧客向けアプリのサイドバーにはライセンスの **ライセンス** 項目と課金の **お支払い** 項目があり、そのリソース欄には、サポートの連絡先の上にコンテンツの **ドキュメント** があります。コアに必要なのは `/` と `/api`、そしてヘッダーの **料金** だけです。**料金** は `hash` を持つ唯一の項目で、`/` の料金セクションへリンクします。

`DASHBOARD_STATS` のダッシュボードの統計には、`/admin` のローダーが実行する `prefetch` と、`DashboardStats` が数値を読み取るために呼び出す `useValue` フックがあります。

`auth.access.ts` の `APP_STATEMENTS` は権限ステートメントをリソースごとに 1 つずつ宣言します。`scripts/features.ts` は、外せる機能のステートメントを `APP_STATEMENTS.course` のように名指しするので、その機能を外すとステートメントも削除されます（[ロールと権限](/docs/guides/roles-and-permissions)を参照）。

`src/data/navigation.ts` のリストには、`IconEntry` や `SiteEntry` のような、`src/data/navigation.constants.ts` で宣言された型が付いています。そのため、決済エリアのないプロジェクトのダッシュボードアクションのように、プロジェクトが項目を外したリストは空のリストになり、それでも型チェックを通ります。`navigation.test.ts` は、すべての項目の `to` がルートツリーのパスであること、そしてどのメニューも同じページやラベルを 2 回指定していないことをチェックします。

項目の `label` はメッセージの完全なキーで（`navigation.courses.admin.courses` など）、メッセージはそのページを所有する機能のファイル `messages/<locale>/navigation.<feature>.json` にあります。そのため、機能を外すとそのラベルも一緒に消えます。コンポーネントは `useTranslations()` の `t(entry.label)` でラベルを描画します。管理画面のセクションは、パンくずリストに表示するサブページのラベルを、項目の `breadcrumbs` にパスのセグメントからキーへの対応として置きます（`create` から `navigation.courses.breadcrumbs.create` など）。ユーザー管理のタブ、コマンドパレットの検索、ダッシュボードの統計も、`navigation.team.userTabs.invitations`、`navigation.auth.search.users`、`dashboard.courses.learners` のように、ラベルの完全なキーを指定します。ダッシュボードのパネルは、`dashboard.<feature>.json` の自分の `key` の下にある文言を読み取ります。どちらの種類のファイルも root 名前空間なので、どのメニューもすべての項目にラベルを付けられます。メニュー自体に属するものは、そのメニューの名前空間に残ります。`pages.admin.sidebar` の `groups.<group>`、`components.custom.footer` の `columns.<column>`、`components.custom.navigation` のヘッダーの行動喚起ボタン、メニューボタン、スキップリンクです。いずれかのロケールで項目、サインイン時の別ラベル、パンくずリスト、ユーザー管理のタブ、コマンドパレットの検索のメッセージが欠けていると `navigation.test.ts` が失敗し、統計のラベルが欠けていると `admin-dashboard.component.test.tsx` が失敗します。

`/admin`、`/auth`、`/courses` のように、リクエストごとに Worker 上でレンダリングされるページは、`src/routes.ts` の `REQUEST_RENDERED_ROUTES` に列挙します。`vite.config.ts` の TanStack Start プラグインは、`isRequestRenderedRoute` を呼び出す `shouldPrerender`（`src/lib/prerender.ts`）でそれらをプリレンダリングから除外するため、それらはページのサイトマップにも載りません。`buildPageHead` は、ルートが独自の画像を渡さない限り、サイトカードを割り当てます。リクエストごとにレンダリングされても、ページが検索結果から外れるわけではありません。コースのページは、Worker が D1 から書き出すサイトマップに載ります（[検索エンジンとソーシャルプレビュー](/docs/features/seo#course-sitemap)を参照）。Vite は自身の設定を読み込む間 `~` エイリアスを解決しないため、`prerender.ts` は `src/routes.ts` を相対パスでインポートします。
