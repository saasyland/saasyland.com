title: "Lint i formatowanie"
description: "oxlint i oxfmt uruchamiane przez Vite+ oraz skrypty kontrolne."
---

Vite+ uruchamia oxfmt do formatowania i oxlint do lintowania; oba narzędzia są skonfigurowane w sekcjach `fmt` i `lint` pliku `vite.config.ts`. `bun run check` to kontrola jakości, którą uruchamia CI:

```sh
bun run check
```

Uruchamia `generate:cn`, `check:comments`, `check:i18n`, `check:content`, `check:flows`, `check:skills` i `vp check`, który sprawdza formatowanie, reguły lintera i typy w całym projekcie. Aby uruchomić tylko jedno narzędzie, użyj `bun run lint`, `bun run format` lub `bun run format:check`.

## Formatowanie

- Bez średników, podwójne cudzysłowy, przecinki końcowe i końce linii LF; szerokość wcięcia w spacjach: <RepositoryFact name="tabWidth" />, szerokość wiersza: <RepositoryFact name="printWidth" />.
- Importy są układane w stałych grupach: tylko serwerowe, `cloudflare:workers`, React, pakiety zewnętrzne, następnie foldery `~/src` (platforma, providery, integracje, moduły, trasy, hooki, dane i motyw, typy, lib, branding, komponenty shadcn, komponenty własne, style), a na końcu importy względne.
- Klasy Tailwinda są sortowane w `className` oraz w wywołaniach `cn`, `cva`, `clsx` i `tw`.

## Lintowanie

- Kategorie `correctness`, `nursery`, `pedantic`, `perf`, `style` i `suspicious` są zgłaszane jako błędy.
- Włączone są reguły uwzględniające typy oraz sprawdzanie typów (`typeAware` i `typeCheck`).
- Najważniejsze limity: <RepositoryFact name="maxLines" /> wierszy w pliku, <RepositoryFact name="maxLinesPerFunction" /> wierszy w funkcji, <RepositoryFact name="maxStatements" /> instrukcji w funkcji, żadnych magicznych liczb poza `0` i `1`, żadnego jawnego `any` (`typescript/no-explicit-any`) i identyfikatory co najmniej dwuznakowe, z wyjątkiem `_`, `m` i `t`.
- Wyjątki w konfiguracji łagodzą kilka reguł dla testów, kodu warstwy prezentacji i hooków, mocków testowych oraz plików tras.
- `jsPlugins` ładuje własne wtyczki oxlint repozytorium: `scripts/code-style-lint-plugin.ts`, której reguły `code-style/no-comments`, `code-style/no-multiline-ternary`, `code-style/no-undefined-branch`, `code-style/no-undefined-fallback`, `code-style/route-option-order` i `code-style/zod-namespace-import` odrzucają każdy komentarz poza jednowierszowym linkiem, każdy operator trójargumentowy zapisany w kilku wierszach, każdy operator trójargumentowy z gałęzią `undefined` lub `null`, każde `return undefined` i każde `?? undefined`, każdą opcję trasy zadeklarowaną poza kolejnością, w jakiej TanStack Router wywodzi typy (zobacz [Pliki tras](/docs/conventions/routes)), oraz każdy import Zod inny niż `import * as zod from "zod"` (zobacz [Styl kodu](/docs/conventions/code-style)), `scripts/hydration-lint-plugin.ts`, której reguła `hydration/no-clock-or-locale-in-render` nie pozwala, aby kod renderujący odczytywał zegar albo ustawienia regionalne środowiska uruchomieniowego (zobacz [Styl kodu](/docs/conventions/code-style)), `scripts/admin-data-lint-plugin.ts`, której reguła `admin-data/no-literal-data` nie dopuszcza danych demonstracyjnych do kodu panelu administracyjnego (zobacz [Panel administracyjny](/docs/features/admin-dashboard#real-data-only)), oraz `scripts/radius-lint-plugin.ts`, której reguła `radius/no-off-scale` pilnuje, aby każdy narożnik miał promień ze skali zaokrągleń (zobacz [Motyw](/docs/ui/theme#corner-radius)). `scripts/type-lint-plugin.ts` dodaje `type/no-off-scale` i `type/mono-for-code`, które pilnują, aby każdy rozmiar tekstu pochodził ze skali typograficznej, a krój o stałej szerokości był używany tylko w kodzie (zobacz [Motyw](/docs/ui/theme#type-scale)).
- Obejścia są zakazane z nazwy: `typescript/ban-ts-comment` odrzuca `@ts-expect-error`, `@ts-ignore` i `@ts-nocheck` nawet z opisem, `typescript/consistent-type-assertions` z `assertionStyle: "never"` odrzuca każdą asercję typu poza `as const`, a `respectEslintDisableDirectives: false` sprawia, że komentarz `eslint-disable` niczego nie wyłącza. `code-style/no-comments` zastępuje `capitalized-comments`, `no-inline-comments` i `no-warning-comments`: kategorie je włączają, ale każda z nich widziała tylko część komentarzy, więc te trzy reguły są wyłączone.

Oba narzędzia ignorują pliki generowane i zewnętrzne: pliki deklaracji, `src/routeTree.gen.ts`, migracje, `.source`, `dist`, `coverage`, `e2e`, `remotion`, foldery agentów i wyniki Playwrighta. `scripts/` jest formatowany i lintowany tak samo jak `src/`. `bun run check:comments` czyta także to, co pomija linter: `e2e`, `remotion`, pliki deklaracji, arkusze stylów i workflowy YAML.

Formatter sortuje też `package.json`, w tym jego `scripts` alfabetycznie (`sortPackageJson: { sortScripts: true }`), więc `vp check` kończy się błędem, gdy któryś skrypt stoi nie na swoim miejscu.

Usuwaj przyczynę błędu lintera. Nie dodawaj komentarzy wyłączających reguły, `@ts-expect-error` ani rzutowań `as` tylko po to, żeby reguła przeszła. Komentarz wyłączający jest komentarzem, a linter wykonuje go, zanim jakakolwiek reguła zobaczy kod, więc `bun run check:comments`, które działa poza linterem, odrzuca taki komentarz wszędzie, gdzie się pojawi.

## Naprawianie

Hook pre-commit uruchamia `bun run check:pre-commit`; jego krok `vp staged` uruchamia `vp check --fix` wyłącznie na plikach przygotowanych do commita. `bun run check:fix` stosuje poprawki w całym repozytorium i może przepisać pliki spoza Twoich zmian, więc przed commitem przejrzyj jego diff. Aby poprawić tylko własne zmiany, przekaż ich ścieżki do `vp` (globalnego CLI Vite+ lub `bunx vp`):

```sh
vp fmt src/routes/admin.users.all.tsx
vp lint --fix src/routes/admin.users.all.tsx
```
