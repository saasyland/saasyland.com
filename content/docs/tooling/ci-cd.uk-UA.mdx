Workflow-файли розміщено в `.github/workflows/`. Workflow-файли застосунку (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `updates.yml`, `e2e-reusable.yml` і `deploy-reusable.yml`) налаштовують інструментарій через складену дію `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ з версією Node з `.nvmrc` і кешем встановлення Bun, який `setup-vp` відновлює один раз, `bun install --frozen-lockfile --ignore-scripts` і `bun run typegen`. Натомість `remotion.yml` налаштовує Node з `.nvmrc` і npm.

| Workflow              | Тригер                                                                              | Завдання                                                                                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull request, групи черги злиття й виклики з `deploy.yml`                           | Перевірки, тести з покриттям на паралельних шардах, перевірка типів без кожного необов’язкового розділу, E2E у Chromium і WebKit та завантаження Worker для preview |
| `deploy.yml`          | Push у `main`                                                                       | Перевірки `ci.yml`, якщо їх не запускала черга злиття, потім preview, production і реліз                                                                            |
| `preview.yml`         | Вручну                                                                              | Розгортає в спільний preview гілку, перевірки якої пройшли                                                                                                          |
| `e2e-full.yml`        | Push у `main`, за розкладом <RepositoryFact name="e2eFullSchedule" /> в UTC, вручну | WebKit при push, як і в кожному pull request; Chromium і WebKit за розкладом і при ручному запуску                                                                  |
| `journey.yml`         | За розкладом <RepositoryFact name="journeySchedule" /> в UTC, вручну                | [Набір тестів шляху клієнта](#journey-suite) на спільному preview, у пісочниці Polar                                                                                |
| `updates.yml`         | За розкладом <RepositoryFact name="updatesSchedule" /> в UTC, вручну                | Відкриває, оновлює або закриває [issue з оновленнями](#updates)                                                                                                     |
| `e2e-reusable.yml`    | Викликається наведеними вище workflow                                               | Одна тестова збірка, один проєкт Playwright на паралельних шардах і одна перевірка для обох                                                                         |
| `deploy-reusable.yml` | Викликається з `ci.yml`, `deploy.yml` і `preview.yml`                               | Збірка, потім міграції D1 і `wrangler deploy` або `wrangler versions upload`                                                                                        |
| `remotion.yml`        | Зміни в `remotion/` або у файлах сайту, які він імпортує                            | Перевіряє та пакує проєкт відео для лендингу за допомогою npm                                                                                                       |

`remotion.yml` запускається для pull request і push за тими самими шляхами: `remotion/`, сам workflow і файли сайту, які імпортує `remotion/src`, напряму або через інші файли сайту. `src/__test__/workflows.test.ts` іде за цими імпортами й не проходить, коли знайдений через них файл не відповідає жодному зі шляхів або шлях не відповідає жодному з файлів.

Checkout-и в `e2e-reusable.yml`, де збірка генерує журнал змін, а `content.spec.ts` читає його, у `deploy-reusable.yml`, що збирає сайт, а також у завданні `release` завантажують усі коміти без їхніх дерев (`fetch-depth: 0` і `filter: tree:0`): [журнал змін](/docs/project/changelog) датує кожен запис комітом, який приніс його в `main`. Порівняно з неглибоким клоном додаються лише самі коміти; з неглибоким клоном збірка завершилася б помилкою, а не датувала б записи неправильно. `src/__test__/workflows.test.ts` не проходить, коли один із цих checkout-ів перестає завантажувати історію.

## Перевірки [#checks]

За обов’язковою перевіркою `Format, lint, types, i18n, tests`, про яку звітує завдання `verify`, стоять завдання `check`, `test` і `features` в `ci.yml`:

| Завдання                                              | Запускає                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                               | `bun run check`: таблиці імен класів, перевірки i18n і контенту, [перелік сценаріїв](/docs/tooling/test-coverage#flow-coverage), [навички агентів](/docs/tooling/agent-skills#drift-checks), форматування, лінтинг і типи                                                                     |
| `test`                                                | Одне завдання на шард, <RepositoryFact name="vitestShards" /> паралельно: `bun run test:coverage --shard=<n>/<total>` з blob-репортером Vitest, а потім завантажує blob-звіт шарду з його покриттям                                                                                           |
| `verify`, з назвою `Format, lint, types, i18n, tests` | Коли всі шарди пройшли, завантажує blob-звіти й запускає `bun run test:coverage --merge-reports`, що об’єднує покриття й застосовує пороги, а потім завантажує звіт про покриття; завершується помилкою, якщо не пройшли `check`, кожен шард, об’єднання й кожен сценарій завдання `features` |

Шард не перевіряє жодного порогу, бо вимірює лише код, до якого доходять його власні тести; пороги з `vite.config.ts` застосовуються один раз, до об’єднаного покриття всіх шардів, так само як у локальному `bun run test:coverage`. З цих завдань лише `verify` є перевіркою, якої вимагають правила гілки, тож додавання чи вилучення шарду або сценарію не змінює назви жодної обов’язкової перевірки.

Завдання `features` запускає `bun run check:features <scenario>` один раз для кожного сценарію з `scripts/features.ts`, паралельно. Воно видаляє можливості сценарію, прибирає з файлів, які лишаються, посилання на них, форматує очищені файли, а тоді перевіряє типи решти та її переклади ([Тестування](/docs/conventions/testing#tests-follow-the-features)). Сценарій, у якому лишається посилання, яке не вдається прибрати, помилка типів або помилка перекладу, завершує своє завдання помилкою, а з ним і обов’язкову перевірку `Format, lint, types, i18n, tests`.

Завдання `e2e` і `e2e-webkit` викликають `e2e-reusable.yml`, перше з `browser: chromium`, друге з `browser: webkit`. Кожен виклик один раз виконує збірку й запускає набір тестів у своєму браузері паралельно на <RepositoryFact name="e2eShards" /> раннерах:

| Завдання                                      | Що виконує                                                                                                                                                                                           |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                       | `db:reset:test` і `build:test`, потім завантажує `dist`, вказівник `.wrangler/deploy` на конфігурацію його Worker і `.wrangler/test` із засіяними даними як один артефакт                            |
| `shard`                                       | Одне завдання на шард, що стартує поряд зі збіркою: встановлює браузер, чекає на завантаження збірки, отримує її і запускає `bunx playwright test e2e/specs --project=<browser> --shard=<n>/<total>` |
| `report` з назвою `Build and E2E (<browser>)` | Завершується помилкою, якщо не пройшла збірка або будь-який шард; коли шард не пройшов, об'єднує blob-звіти шардів в один HTML-звіт і завантажує його                                                |

Шарди не чекають на завершення всього завдання `build` (`needs`): вони стартують разом із ним і налаштовують інструментарій та браузер, поки воно збирає. Потім `scripts/download-artifact.ts` що кілька секунд запитує в API GitHub завдання `build` того самого запуску, доки його крок `Upload the test build` не завершиться успішно. Успішний крок ще не означає, що GitHub уже показує його артефакт у списку, а завантаження в цьому проміжку падає з `Artifact not found`, тож далі скрипт запитує артефакти запуску, доки GitHub не покаже `test-worker-<browser>`, завантажений від початку збірки, а потім сам завантажує цей артефакт і звіряє його з дайджестом SHA-256, який записав GitHub. Артефакт зі списку ще якусь мить може відповідати `Not Found`, тож скрипт запитує знову, доки GitHub не віддасть увесь архів, і жоден інший крок не запитує його тим часом. Скрипт надсилає ETag попередньої відповіді, а GitHub не зараховує незмінну відповідь до ліміту запитів токена. Невдалий крок збірки або збірка, що завершилася без завантаження, за кілька секунд валить кожен шард, з назвою невдалого кроку і посиланням на збірку, а шард, що чекає довше за ліміт скрипта, завершується помилкою, яка каже, чого бракує: кроку, списку чи завантаження. Щоб читати завдання й артефакти запуску, потрібен `actions: read`, і просить його лише завдання `shard`: `ci.yml`, `e2e-full.yml` і завдання `checks` у `deploy.yml` надають його workflow-файлам, які викликають, а кожне інше завдання зберігає `contents: read`.

Власні повтори й воркери Playwright на кожному шарді лишаються такими, як їх описує [Playwright](/docs/tooling/playwright#configuration). Завдання `report` кожного браузера — єдина перевірка цього браузера, якої вимагають правила гілки, тож додавання чи вилучення шарда не змінює жодної назви обов'язкової перевірки. Збірка також пакує список тегів релізів, які вона прочитала, а кожен шард видаляє будь-який тег, створений відтоді: `content.spec.ts` читає теги релізів із Git, і реліз, позначений тегом, поки шарди чекають, змусив би його очікувати changelog, якого збірка ніколи не рендерила.

Завдання `upload` з назвою `Worker upload` викликає `deploy-reusable.yml` з `upload: true`: воно збирає Worker для preview точно так, як це робить розгортання, і запускає `wrangler versions upload`, що надсилає його у Worker `saasyland-preview` як нову версію, не розгортаючи її. Cloudflare перевіряє завантаження так само, як розгортання: обмеження розміру, час запуску, прив'язки та секрети, які називає `secrets.required`, тож Worker, що пройшов цю перевірку, розгорнеться, а `preview.saasyland.com` тим часом і далі обслуговує версію, розгорнуту раніше. Завдання не застосовує міграцій і не записує розгортання GitHub (`deployment: false`), а виконується паралельно із завантаженнями інших pull request. Версія pull request отримує псевдонім `pr-<number>`, яким вона позначена в дашборді Cloudflare; підсумок завдання показує ID і розмір версії, а також її URL, коли для Worker увімкнено Version URLs, а для `saasyland-preview` їх зараз не ввімкнено. Pull request із форків і від Dependabot не можуть прочитати облікові дані Cloudflare й пропускають це завдання; черга злиття, яка може їх прочитати, завантажує їхню збірку перед злиттям.

У pull request `bun run check` також завершується помилкою, доки pull request не додасть власний [запис журналу змін](/docs/conventions/git-workflow#changelog-entries), а в черзі злиття — доки немає запису pull request, що стоїть у черзі. Збірка в завданнях `e2e` і `upload`, а також у завданнях розгортання, завершується помилкою, доки журнал змін показував би в розділі **Ще не випущено** запис, що не є записом самого pull request, а в черзі злиття й у `main` — доки показував би будь-який.

## Черга злиття [#merge-queue]

Ruleset, що захищає `main`, вимагає `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)`, `Build and E2E / Build and E2E (webkit)` і `Worker upload / Upload preview` та зливає pull request лише через чергу злиття GitHub, яка робить squash кожного з них. `bun scripts/enqueue-pr.ts <number>` ставить pull request у чергу ([Git і pull request](/docs/conventions/git-workflow#merging)). Для кожного pull request у черзі GitHub записує squash-коміт у гілку з назвою `gh-readonly-queue/main/pr-<number>-<commit>` поверх `main` і pull request, що стоять перед ним, і запускає на ній `ci.yml` для події `merge_group`. Щойно кожен pull request групи пройде, GitHub переміщує `main` на останній коміт групи, той самий коміт, який протестувала черга, тож один push приносить у `main` кожен pull request групи як окремий squash-коміт. Pull request, який не пройшов, виходить із черги, а ті, що стоять за ним, тестуються знову вже без нього.

Ruleset також містить `copilot_code_review` з `review_on_push: true`, але станом на 22 листопада 2026 року GitHub Copilot не переглянув жодного pull request від #70, тож pull request не отримують автоматичного рев’ю. Рев’ю було б лише дорадчим: ruleset не вимагає жодного схвалення й жодного розв’язаного треду рев’ю, тож pull request чекає лише на чотири перевірки вище.

`ci.yml` скасовує запуск pull request, коли його замінює новіший коміт, але ніколи не скасовує запуск черги, адже кожна її гілка має власний ref. Перевірка журналу змін вважає гілку черги гілкою `main`: кожен pull request групи вже є squash-комітом, тема якого завершується його номером, тож жоден запис не може бути невипущеним, а власний запис pull request у черзі має існувати.

## Розгортання

`deploy.yml` розгортає кожен push у `main`, спершу в спільний preview, а потім у production, щойно коміт пройшов усі перевірки, яких вимагає `main`. Його перше завдання, `tested`, запускає `scripts/tested-commit.ts`, який читає ці перевірки з ruleset через API GitHub і шукає успішний запуск кожної з них на надісланому коміті. Коміт, що пройшов через чергу злиття, їх має, бо черга протестувала саме цей коміт, тож `deploy.yml` розгортає його, не запускаючи перевірки знову; коміт, що потрапив у `main` іншим шляхом, спершу проходить перевірки `ci.yml`.

| Подія                       | Ціль                          | Середовище GitHub             | URL                                                  |
| --------------------------- | ----------------------------- | ----------------------------- | ---------------------------------------------------- |
| Push у `main`               | `preview`, потім `production` | `Preview`, потім `Production` | https://preview.saasyland.com, https://saasyland.com |
| Ручний запуск `preview.yml` | `preview`                     | `Preview`                     | https://preview.saasyland.com                        |

`deploy-reusable.yml` задає кожному середовищу GitHub його URL, а `src/__test__/workflows.test.ts` не проходить, коли якийсь із них відрізняється від хоста середовища в `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Preview спільний: кожне розгортання замінює попереднє й використовує ту саму базу даних D1, простір імен KV і бакети R2 для preview. На ньому працює `main`, тож [набір тестів шляху клієнта](/docs/tooling/playwright#journey-suite), вебхуки пісочниці Polar і вхід на `preview.saasyland.com`, єдиний preview-хост, якому довіряє Better Auth, мають справу з кодом, який ось-ось запустить production, а кожна міграція потрапляє в базу даних preview раніше, ніж у production. Щоб випробувати там гілку до злиття, запустіть `gh workflow run preview.yml --ref <branch>`: команда розгортає гілку разом із міграціями лише тоді, коли її коміт пройшов перевірки, яких вимагає `main`, а наступний push у `main` повертає туди `main`.

`deploy-reusable.yml` перевіряє наявність секретів `CLOUDFLARE_API_TOKEN` і `CLOUDFLARE_ACCOUNT_ID`, запускає `scripts/verify-bindings.ts`, виконує збірку з фіктивними значеннями з `.env.test`, видаляє згенерований `dist/server/.dev.vars`, застосовує `db:migrate:<target>` і запускає `vp exec wrangler deploy --config dist/server/wrangler.json` або, з `upload: true`, запускає `vp exec wrangler versions upload` замість двох останніх кроків. `scripts/verify-deployment.ts`, перевірка розгорнутого сайту зі скриптів `deploy:<target>`, тут не запускається, бо захист Cloudflare від ботів відповідає 403 на запити з раннерів CI. `scripts/run-deploy-checks.ts` тут теж не запускається, тож CI не виконує жодної з перевірок перед розгортанням, тобто скриптів `<name>:verify:<environment>` у `package.json`: у CI немає `.env.<target>`, а середовища GitHub містять лише облікові дані Cloudflare і, у `Preview`, налаштування пісочниці для [набору тестів шляху клієнта](#journey-suite). Зараз це `auth:verify` із розділу автентифікації та `polar:verify` із розділу Polar; запускайте локально `bun run auth:verify:<target>` після зміни клієнта OAuth і `bun run polar:verify:<target>` після кожної зміни в Polar ([Налаштування Polar](/docs/getting-started/polar-setup)). Файл секретів не завантажується: Worker зберігає секрети середовища виконання, уже задані в Cloudflare. Розгортання в ту саму ціль стають у чергу, а не скасовують одне одного, а завантаження виконуються паралельно. Новий коміт у pull request скасовує запуск `ci.yml` для попереднього коміту, який ніхто не зливатиме, тоді як запуски черги злиття ніколи не скасовують один одного, а запуски `deploy.yml` і `e2e-full.yml` у `main` стають у чергу (`concurrency` з `queue: max`), тож кожен push у `main` розгортається.

Dependabot щотижня оновлює GitHub Actions.

## Набір тестів шляху клієнта [#journey-suite]

`journey.yml` запускає `bun run test:journey`, тобто [набір тестів шляху клієнта](/docs/tooling/playwright#journey-suite), на `https://preview.saasyland.com` за розкладом <RepositoryFact name="journeySchedule" /> в UTC і тоді, коли його запускають вручну:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` має значення `all`, `core`, `complete`, `agency` або `upgrade`; будь-яке значення, крім `all`, запускає лише тест із цим тегом. Завдання читає ці секрети середовища GitHub `Preview`, не фіксуючи розгортання (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` і `RESEND_API_KEY`. Воно встановлює `POLAR_SERVER` у `sandbox`, єдине значення, яке приймає набір, а набір створює свій клієнт Polar для пісочниці, тож workflow не може дістатися до продакшн-Polar. Запуски стають у чергу й ніколи не скасовують один одного, бо скасований запуск залишив би свої замовлення оплаченими. Завдання записує результат і тривалість кожного тесту та помилку кожного невдалого тесту в підсумок запуску і завантажує HTML-звіт, `playwright-report/journey.json` та трасування, відео й каталоги машин невдалих тестів як артефакт `journey-report`.

Workflow не запускається після кожного розгортання `main`. Кожен запуск реєструє на preview обліковий запис на кожен тест, оплачує й повертає його замовлення в пісочниці Polar і надсилає листи підтвердження адреси та підтвердження покупки через обліковий запис Resend, який preview ділить із продакшном. У насичений день `main` розгортається багато разів, тож запуск після кожного розгортання помножив би ці листи на тлі лімітів надсилання, від яких залежать листи продакшну, і нічого б не зупинив: продакшн розгортається одразу після preview, хоч би що знайшов шлях клієнта. Кожен запуск охоплює всю покупку: реєстрацію з підтвердженням адреси, оплату в пісочниці за кожен план, ключ, який видає Polar, опублікований CLI на пристроях плану, перехід із Core на Complete і повернення коштів. Зеленим він ще не став: жоден запуск не пройшов, бо секретів не задано, тож поки що він не перевіряє жодної покупки. Запускайте його вручну після змін у платежах, ліцензіях або API ліцензій CLI, а також після `gh workflow run preview.yml --ref <branch>`, щоб перевірити гілку до злиття.

## Оновлення [#updates]

`updates.yml` шукає оновлення залежностей і навичок агентів за розкладом <RepositoryFact name="updatesSchedule" /> в UTC і під час запуску вручну. Перший крок, `bun scripts/report-updates.ts find`, запитує в реєстрі npm найновіший реліз кожної прямої залежності й запускає `bun run skills:update` у checkout раннера, з якого нічого не комітиться, щоб побачити, які навички змінилися в джерелі. Другий крок, `bun scripts/report-updates.ts issue`, веде одне issue, <RepositoryFact name="updatesIssueTitle" />: відкриває його, коли є оновлення, переписує під час наступних запусків і закриває, щойно все актуальне. Issue перелічує кожен застарілий пакет із позначкою, чи його зсуває `bun run deps:update`, чи він зафіксований, і кожну навичку з комітами, між якими вона перейшла б.

Workflow може лише читати репозиторій і писати issues, і токен отримує тільки другий крок. Він не відкриває pull request, бо GitHub не запускає жодного workflow для pull request, відкритого власним токеном workflow, тож його перевірки ніколи б не виконалися; натомість запустіть `bun run deps:update` у гілці.

## Релізи й теги [#releases-and-tags]

Сайт розгортається безперервно, тож його версії — це дати, а не семантичні версії. Коли розгортання production завершується успішно, завдання `release` у `deploy.yml` позначає розгорнутий коміт тегом `vYYYY.MM.DD` з датою за UTC і публікує для нього GitHub Release. Друге розгортання production того самого дня отримує тег `vYYYY.MM.DD.2`, наступне — `.3` і так далі. Розгортання preview ніколи не отримують тегів. Завдання `release` — єдине з `contents: write`.

Нотатки до релізу — це записи [журналу змін](/docs/project/changelog), які доставив реліз, тобто ті, що потрапили в `main` після попереднього тегу релізу, і кожен із них завершується `(#<number>)`, що GitHub перетворює на посилання на його pull request, тож кожну зміну описано в одному місці; якщо реліз не доставив жодного, його нотатки містять посилання на журнал змін. `scripts/publish-release.ts` бере нотатки з `releaseNotes` у `src/lib/changelog.ts`, єдиного елемента `RELEASE_NOTES`, і запускає `gh release create` з тегом, який вибрало розгортання, тож проєкт без журналу змін публікує релізи без нотаток. Повторний запуск залишає тег, який коміт уже має, і пропускає реліз, що вже існує.

Завдання розгортання в production вибирає цей тег перед збіркою: `scripts/choose-release-tag.ts` застосовує `releaseTag` із `src/lib/release.ts` до тегів checkout, збірка отримує тег як `RELEASE_TAG`, а завдання передає його завданню `release` як свій вихід `release-tag`, тож розгортання і його реліз мають один тег. Завдяки цьому [журнал змін](/docs/project/changelog) посилається з кожного запису на реліз, який першим його доставив: на найстаріший тег релізу, коміт якого містить squash-коміт запису в історії перших батьків `main`, яку збірка читає разом із датами одним `git log`, або на власний тег розгортання для записів, які воно приносить. Завдання `release` читає журнал змін так само, з тегом, який публікує, тож нотатки релізу — це саме ті записи, які сторінка пов'язує з цим релізом. Записи, злиті до першого тегу релізу, не посилаються на жоден реліз, як і в локальних збірках, збірках preview і pull request записи, яких ще не доставило жодне розгортання. Два розгортання в production не можуть вибрати той самий тег: `deploy.yml` запускає водночас лише один запуск workflow (`concurrency` з `queue: max`), тож завдання `release` попереднього запуску вже створило свій тег, коли наступне розгортання робить checkout репозиторію.

Щоб повернути production до релізу, скасуйте в pull request усе, що йде після його тегу:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Після злиття код із тегу розгортається після звичайних перевірок і позначається як новий реліз. Міграції D1 не скасовуються, тож старіший код працює з новішою схемою. Кожна зміна схеми має працювати із застосунком, розгорнутим перед нею, тому повернення до попереднього релізу безпечне; перш ніж повертатися далі, перегляньте міграції між ними.
