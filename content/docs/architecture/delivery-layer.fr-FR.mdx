## Fichiers de route

Les routes sont des fichiers à plat dans `src/routes`. Les points deviennent des segments de chemin :

| Fichier                           | URL                | Remarques                                   |
| --------------------------------- | ------------------ | ------------------------------------------- |
| `__root.tsx`                      | toutes les pages   | Shell du document et namespaces racine      |
| `_site.tsx`                       | aucune             | Layout sans chemin avec l'en-tête du site   |
| `_site._marketing.tsx`            | aucune             | Layout sans chemin pour les pages marketing |
| `_site._marketing.terms.tsx`      | `/terms`           | Page à l'intérieur du layout marketing      |
| `admin.tsx`                       | `/admin`           | Layout avec le guard `requireAdmin`         |
| `admin.users.all.tsx`             | `/admin/users/all` | Page à l'intérieur du layout admin          |
| `_site._marketing.blog.index.tsx` | `/blog`            | Page d'index du layout `blog`               |
| `_site.docs.$.tsx`                | `/docs/*`          | Route splat pour les pages de documentation |
| `api/auth.$.ts`                   | `/api/auth/*`      | Handler HTTP, sans composant                |

Les identifiants passés à `createFileRoute("…")` sont des littéraux de chaîne maintenus par le générateur du routeur, qui écrit aussi `src/routeTree.gen.ts`. Les fichiers des dossiers `__test__` sont ignorés. Chaque URL a une constante dans `ROUTES` (`src/routes.ts`), et les liens utilisent `<Link to={ROUTES.X}>`.

## Routes de page

Une route de page définit un composant `<Name>Page`, une constante `NAMESPACE` juste au-dessus de `export const Route`, et un loader qui charge les métadonnées de la page et le namespace dans un seul `Promise.all` :

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.TERMS),
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Les données supplémentaires vont dans le même `Promise.all`, par exemple `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` dans `admin.users.all.tsx`. `pageHead` de `src/lib/seo.ts` construit les balises de titre, de description, d'URL canonique, `hreflang`, Open Graph et d'image de partage à partir des `metadata` renvoyées par le loader ; voir [Référencement et aperçus sociaux](/docs/features/seo).

## Routes de layout

Une route de layout définit un composant `<Name>Layout`, un tableau `NAMESPACES` et, pour les zones protégées, un guard dans `beforeLoad`. Ses `NAMESPACES` nomment chaque namespace dont ses pages ont besoin, y compris ceux d'autres fonctionnalités, et un paramètre de recherche est validé par les pages qui le lisent, comme le font les pages de licence `/app` et `/app/license` avec `tier` :

```tsx title="src/routes/app.tsx"
const NAMESPACES = [
  "auth.dates",
  "auth.errors",
  "auth.form",
  "auth.security",
  "auth.session",
  "auth.validations",
  "countries",
  "pages.app.sidebar",
  "pages.license",
  "pages.withdrawal",
  "timezones",
  "withdrawal.validations",
] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Les guards `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn`, `redirectIfVerified` et `redirectAfterAuth` proviennent de `src/integrations/better-auth/auth.routes.ts`.

## Squelettes de chargement

La plupart des navigations se terminent avant qu'une interface d'attente n'apparaisse : les liens préchargent leur route au survol et au toucher, et les pages publiques sont prérendues. Lorsqu'une navigation n'est pas terminée après `defaultPendingMs`, <RepositoryFact name="navigationPendingMs" unit="millisecond" />, le routeur affiche le squelette de la route et, comme `defaultPendingMinMs` vaut <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, le retire dès que la page est prête. Cela arrive avec une connexion lente ou lors de la première requête adressée à un nouvel isolat du Worker (voir [Performances](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

Il n'y a pas de composant de chargement par défaut. Chaque route de layout et de page définit son propre `pendingComponent`. Les pages de la documentation sont dessinées dans le layout de la documentation : `_site.docs.index.tsx` et `_site.docs.$.tsx` affichent `DocsIndexPending` et `DocsPagePending`, l'article et sa table des matières à côté de la barre latérale, et le layout `docs` affiche `DocsPending` lorsque quelqu'un arrive dans la documentation depuis une autre page. Chaque squelette reproduit la page qu'il remplace :

- **Les squelettes de page**, comme `SignInPending` et `LegalPending`, se trouvent dans le fichier de squelettes de la fonctionnalité et marquent leur élément racine avec `aria-busy="true"`. Ces fichiers sont `custom/auth/auth-pending.tsx`, les fichiers d'administration dans `custom/admin/` (`admin-pending.tsx` pour le layout, un fichier `<feature>-pending.tsx` par fonctionnalité, comme `products-pending.tsx`, et des blocs partagés dans `pending-blocks.tsx`), les fichiers de l'espace client dans `custom/app/` (`app-pending.tsx` pour le layout, `auth-pending.tsx` et `license-pending.tsx`, ainsi que l'en-tête de page qu'ils partagent dans `pending-blocks.tsx`), les fichiers du layout public à la racine de `custom/` (`marketing-pending.tsx` pour le layout, `core-pending.tsx`, `legal-pending.tsx`, `newsletter-pending.tsx` et `withdrawal-pending.tsx`), `custom/billing/billing-pending.tsx`, `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` et `custom/docs-pending.tsx`.
- **Les squelettes de layout**, comme `AuthPending` et `MarketingPending`, affichent le cadre du layout et, à l'intérieur, le `pendingComponent` de la première route sous le layout qui correspond au chemin courant et en définit un, que `usePagePending` de `src/hooks/use-page-pending.ts` lit dans l'arbre des routes. Quand on arrive dans une zone depuis une autre partie du site, c'est donc la bonne page qui s'affiche, et un squelette de layout situé un niveau plus bas, comme `AdminUsersPending`, fait de même pour ses propres pages. Les éléments du cadre qui n'ont pas besoin de données, comme `Wordmark` et `PageFrame`, sont réellement rendus, et l'en-tête du site reste à l'écran, car le layout `_site` qui l'affiche n'a pas de loader à attendre.
- **Les espaces réservés de texte** sont des barres `Skeleton` qui portent le jeton typographique de l'élément réel plus `h-lh scale-y-70`, de sorte que chaque barre remplit exactement une boîte de ligne. Les blocs reprennent les hauteurs et les rayons réels. Les listes tirent leur longueur des mêmes constantes que l'interface, comme `OAUTH_PROVIDERS` et `AUTH_ASSURANCES` dans `src/data/auth.ts`.

Quand vous ajoutez une page, ajoutez son squelette au fichier de squelettes de la fonctionnalité et définissez-le comme `pendingComponent` de la route ; les squelettes de layout l'y trouvent.

## Autres aspects des routes

- **Les paramètres de recherche** sont analysés par `validateSearch` dans la route, par exemple le paramètre `tab` de `/app/settings`. Le schéma est un `zod.object` construit à partir des utilitaires de `src/lib/search-params.ts` : `searchText()` et `searchFlag()` donnent `undefined` pour une valeur absente, vide ou mal formée, et `searchChoice(choices, fallback)` donne la valeur de repli. `searchParam(schema)` donne `undefined` sauf si la valeur respecte un autre schéma zod, comme le jeton de la newsletter.
- **Les fonctions serveur propres à une seule route** peuvent être définies dans le fichier de route avec `createServerFn`.
- **Le contenu produit au build** : les loaders de la documentation, du blog et de la landing page lisent les index de contenu depuis `virtual:content-indexes`, des fichiers sous `/assets/` ; ils n'ont donc besoin d'aucune fonction serveur et s'exécutent dans le navigateur lors d'une navigation côté client (voir [Fumadocs](/docs/integrations/fumadocs#content-indexes)).
- **Les endpoints HTTP** se trouvent dans `src/routes/api`. Voir [Handlers HTTP de TanStack Start](/docs/architecture/api-layer).

## Routeur

`src/router.tsx` exporte `getRouter`, qui crée un nouveau `QueryClient` et un nouveau routeur pour chaque requête. Il définit :

- les composants par défaut d'erreur et de page introuvable, issus de `presentation/components/custom`, et aucun composant de chargement par défaut (voir [Squelettes de chargement](#squelettes-de-chargement))
- le préchargement à l'intention et un `defaultPreloadStaleTime` de <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />, si bien que c'est TanStack Query, et non le routeur, qui décide si une page préchargée ou revisitée récupère encore quelque chose (voir [Cache et SSR](/docs/architecture/caching-and-ssr) et [Performances](/docs/conventions/performance#the-headers-pages-load-before-a-click))
- un `rewrite` qui retire le préfixe de locale des URL entrantes et le rajoute aux liens générés
- l'intégration SSR des queries via `setupRouterSsrQueryIntegration`

## Après un déploiement [#after-a-deploy]

Chaque déploiement remplace les assets statiques du Worker, et Vite nomme chaque fichier d'après son contenu : un onglet ouvert avant un déploiement demande donc des chunks de route qui n'existent plus. TanStack Start place le composant et le loader de chaque route dans des chunks distincts. TanStack Router recharge la page quand le chunk d'un composant ne se charge pas (`lazyRouteComponent`), mais router-core charge le chunk d'un loader avec `lazyFn`, qui transmet l'import échoué à la route comme erreur de son loader. Un clic sur **Blog** dans un tel onglet échouait sur le chunk du loader du layout du blog et affichait la page d'erreur.

`DefaultError`, le composant d'erreur par défaut du routeur, s'en remet désormais. `isStaleBuildError` dans `src/lib/stale-build.ts` reconnaît une erreur qui signifie que la page exécute du code qu'un déploiement plus récent a supprimé :

- un import dynamique échoué, que `isModuleNotFoundError` de router-core reconnaît dans Chromium, Firefox et Safari ;
- un fichier que Vite n'a pas pu précharger pour un chunk, comme sa feuille de style, que Vite signale par un événement `vite:preloadError`. La route racine écoute cet événement tant que l'application est ouverte (`listenForStaleBuilds`).

Pour une telle erreur, `DefaultError` charge comme une nouvelle page l'adresse vers laquelle le visiteur a navigué, avec `router.navigate({ href, reloadDocument: true, replace: true })` : le visiteur arrive ainsi sur la page qu'il a cliquée, servie par le nouveau déploiement. Jusqu'à ce que le navigateur quitte la page, le composant affiche un `main` vide et marqué comme occupé au lieu du message d'erreur. `claimReload` autorise un seul rechargement de ce type par destination et par build. Il enregistre la destination dans `sessionStorage` avec l'URL du script d'entrée de la page, qui change à chaque déploiement modifiant un fichier que charge le navigateur, car chaque chunk est atteint depuis l'entrée par son nom dérivé du contenu. Un second échec pour la même destination dans le même build affiche la page d'erreur : un fichier réellement manquant ne peut donc pas faire recharger la page sans fin, et le déploiement suivant obtient son propre rechargement. Si le navigateur refuse le stockage de session, rien n'est rechargé.

Safari annule les fichiers qu'une page charge encore dès que le visiteur commence à la quitter : un chunk ou une feuille de style en cours de chargement échoue alors comme si un déploiement l'avait supprimé. `listenForStaleBuilds` note donc aussi le moment où la page reçoit `beforeunload`, et `DefaultError` attend avec `whenPageStays` qu'un `pageshow`, un `pointerdown` ou un `keydown` montre que le visiteur est resté avant de recharger la page. Un visiteur qui s'en va arrive sur la page qu'il a demandée au lieu d'être renvoyé sur celle qu'il quittait, et celui qui revient sur la page ou y reste obtient alors le rechargement. `stale-build.spec.ts` retient le code de la route d'une leçon, part vers la politique de confidentialité, annule le code et vérifie que la politique de confidentialité s'ouvre et que la leçon n'est pas redemandée.

Un préchargement échoué ne consomme rien. Le survol d'un lien précharge sa route, comme le fait l'en-tête pour ses propres liens dès qu'une page est inactive ; si cela échoue, aucun composant d'erreur ne s'affiche, et le routeur redemande le chunk lors du clic. `e2e/specs/stale-build.spec.ts` active l'économiseur de données, pour que l'en-tête ne charge pas le blog avant, retire les chunks du blog d'une page ouverte et vérifie qu'un clic, y compris après un survol dont le préchargement a échoué, arrive sur le blog après un rechargement, et qu'une page dont les chunks manquent toujours affiche la page d'erreur après deux rechargements, l'un par `DefaultError` et l'autre par `lazyRouteComponent`.
