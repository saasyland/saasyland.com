## Commencez ici: il est très bon et vous devriez probablement l'utiliser

[Better-T-Stack](https://better-t-stack.dev/) est un CLI pour les projets d'échafaudage de bout en bout de type sûr TypeScript. Il est MIT sous licence, son README promet "libre et open source: pour toujours," il a **5 636 GitHub étoiles** et il est tiré à peu près **2,476 fois par semaine** à partir de npm.

La matrice des options est la meilleure de l'écosystème, et elle n'est pas proche:

Obtenir que de nombreuses combinaisons pour produire un projet qui effectivement type-checks et runs est vraiment une ingénierie difficile. Il est aussi livré en tant que plugin Claude Code avec un serveur MCP, de sorte qu'un agent peut planifier et générer une pile valide plutôt que de rouler à la main plaque de chaudière, qui est un travail réfléchi.

**Si vous construisez un prototype, un outil interne, un projet de portefeuille, une application non-SaaS, ou tout ce que vous voulez apprendre la plomberie, arrêtez de lire et exécutez `bun create better-t-stack@latest`.** Il est libre, il est excellent, et rien ci-dessous ne s'y oppose.

Le reste est pour un lecteur spécifique: la personne qui essaie de décider si le CLI gratuit est suffisant pour un SaaS ils ont l'intention de facturer de l'argent pour.

## Une pile n'est pas un produit

Le README de Better-T-Stack énonce sa philosophie en quatre lignes, et le second est la comparaison complète:

> Roulez votre propre pile : vous ne choisissez que les pièces dont vous avez besoin, rien de plus.
> **Modèles minimums: échafaudages à os nus avec ballon zéro.**
> Dernières dépendances : utilisez toujours les versions actuelles et stables par défaut.
> Source libre et ouverte : pour toujours.

Ce n'est pas une limitation qui est cachée. C'est la conception, dit clairement, et le projet donne exactement ce qu'il promet. La preuve se trouve à la dernière ligne du tableau ci-dessus: les exemples expédiés sont: **Todo** et **IA**C'est vrai. Une liste de todo et un chat. Ce sont les démonstrations canoniques que le câblage fonctionne, et ils sont les bons exemples pour un outil dont le travail est le câblage.

Donc, le cadrage honnête n'est pas « un outil gratuit qui manque des fonctionnalités ». C'est :

**Better-T-Stack échafaude une pile. Un kit de démarrage SaaS échafaude un produit.**

Les deux sont des échafaudages. Ils s'arrêtent à différentes lignes. Better-T-Stack s'arrête lorsque le frontend peut appeler le backend et le backend peut atteindre la base de données en toute sécurité, avec votre choix de neuf frontends et six backends. C'est un endroit défendable pour s'arrêter, et c'est là que la plupart des échafaudiers devraient s'arrêter.

Un démarreur SaaS s'arrête ailleurs : quand une personne peut s'inscrire, rejoindre une organisation, se voir attribuer un rôle, être facturé mensuellement, recevoir un email à ce sujet, et être regardé par vous dans un panneau d'administration quand ils écrivent dans confus. Tout entre ces deux lignes est le projet de loi.

## La partie qui n'est pas des heures

Regardez quatre rangées dans ce tableau : **isolement multi-tenus, rôles et permissions, idempotency webhook, et révocation de session.**

Ils partagent une propriété qu'aucune des autres rangées n'ont. **La mauvaise mise en œuvre passe examen, fonctionne dans le développement, et les démos correctement.**

Un filtre de locataire appliqué dans la couche de vue au lieu de la couche de requête fonctionne parfaitement avec un seul locataire. Il fonctionne parfaitement dans vos tests, parce que vos installations ont un locataire. Il échoue le jour où les données de votre deuxième client apparaissent dans le tableau de bord de votre premier client, et ce n'est pas un rapport de bogue, c'est un appel téléphonique.

Un gestionnaire de webhook sans clé idempotency fonctionne à chaque fois que vous le testez, parce que vous n'envoyez jamais le même événement deux fois. Stripe ne, en réessayer, et puis quelqu'un a été chargé deux fois ou accordé un plan deux fois.

Une vérification d'autorisation qui lit le rôle de la session plutôt que de le relire à partir de la base de données fonctionne jusqu'à ce que quelqu'un soit démodé et garde son ancienne session.

Ce ne sont pas des problèmes difficiles. Ce sont des problèmes où **être mal est invisible jusqu'à ce qu'il soit cher**, qui est un profil de risque complètement différent de "cela prend 40 heures."Vous ne pouvez pas acheter votre sortie d'eux avec plus d'heures, parce que vous ne savez pas que vous avez besoin des heures. Vous les évitez en commençant par une fondation où quelqu'un a déjà fait l'erreur et l'a réparée, et où un test existe maintenant qui échoue s'il revient.

C'est là, plutôt que le nombre d'heures, le but d'un kit de démarrage payé.

## Ce que le côté payé ressemble concrètement

Pour être spécifique plutôt que abstrait, voici ce que signifie "déjà résolu" dans cette base de code, avec les nombres lus hors de l'exécution du test plutôt que tapé dans un fichier marketing.

**Une porte de couverture plutôt qu'un badge de couverture.** 141 dossiers d'essai, 472 tests et quatre seuils dans la configuration:

```ts
coverage: {
  thresholds: { branches: 100, functions: 100, lines: 100, statements: 100 },
}
```

Les branches d'erreur dans la section précédente sont exactement ce qu'une porte de couverture de branche à 100 vous oblige à tester. C'est le mécanisme, pas le nombre.

**Architecture le compilateur est d'accord avec.** Trois règles de lint rendent les limites du module exécutable :

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

Vous ne pouvez pas mettre une requête de base de données dans un composant React. La construction échoue et vous dit pourquoi.

**Stricté sans trappe d'évacuation.** `strict`Plus `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` et `verbatimModuleSyntax`. `typescript/no-explicit-any` est une erreur, et le linter fonctionne avec `denyWarnings: true`, donc il n'y a aucun avertissement que vous pouvez apprendre à ignorer.

**Caractéristiques optionnelles, pas un modèle fixe.** Les [configurateur](/#cli) pose douze questions et offre quatre extras: un magasin avec des exemples de produits, un cours d'abonnement, un concepteur de page visuelle et un éditeur de poste visuel. Allumer un sur ajoute un module. Le laisser en dehors signifie que le code n'existe pas dans votre dépôt.

Rien de tout cela n'est une critique de Better-T-Stack. C'est une description de l'endroit où les deux produits s'arrêtent.

## Quand Better-T-Stack est la bonne réponse

Déclaré correctement, car une comparaison qui recommande toujours l'option payée est une publicité plutôt qu'une comparaison.

**Utiliser Better-T-Stack si:**

- Vous êtes prototypage, et la chose peut ne pas exister en un mois.
- Vous apprenez, et la plomberie est le but. La construction d'une fois est une éducation vraiment précieuse et personne ne doit en être démantelé.
- Votre produit n'est pas un SaaS. Pas d'organisations, pas d'abonnements, pas de admin. Un outil, un jeu, un tableau de bord interne, un site client.
- Vous avez déjà une bibliothèque interne pour les trois quarts ennuyeux, ce que beaucoup d'agences et d'équipes expérimentées font.
- Votre pile est en dehors de ce que n'importe quel kit payant offre. Nuxt, Svelte, Solid, Astro, React Native, Convex, tRPC. Better-T-Stack couvre tous ceux et aucun démarreur payé ne couvre la plupart d'entre eux.
- Votre budget est vraiment nul. C'est une contrainte légitime et il n'y a pas de honte en elle. Better-T-Stack est une meilleure option gratuite que n'importe quel produit payé de niveau libre.

**Envisager de payer si :**

- Vous construisez un produit pour lequel vous comptez facturer des sièges, des rôles, des factures et un questionnaire de sécurité à l'avenir.
- Vous avez déjà construit des organisations et la facturation une fois et rappelez-vous exactement combien de temps les pièces ennuyeuses ont pris.
- Vous voulez une porte de test que vous n'aviez pas à écrire, parce que l'écriture d'une suite de couverture de zéro est l'élément auquel personne n'arrive jamais.
- Vous voulez que les limites architecturales soient appliquées plutôt que prévues.
- Votre temps a un prix et de 280 à 465 heures de cela coûte plus de quelques centaines de dollars.

## Ils ne sont pas vraiment concurrents

La chose la plus utile que je puisse vous dire est que ce n'est pas une course à deux chevaux.

Better-T-Stack est un échafaudage pour _toutes les_ TypeScript projet, sur neuf frontends et six backends. Un kit de démarrage SaaS est une base pour _un seul genre_ d'affaires. Le chevauchement est les dix minutes au début où les deux écrivent un projet. Après cela, ils font des travaux différents.

L'erreur à éviter n'est pas de "choisir le libre". C'est choisir l'un ou l'autre sans savoir lequel des deux emplois dont vous aviez besoin. Un fondateur qui échafaude une belle pile sans danger de type, puis passe six mois à construire des organisations et à facturer n'a pas économisé de l'argent. Ils ont payé la facture dans la monnaie qui n'apparaît pas sur une facture.

La pire option est celle que ni l'un ni l'autre n'offre : une grande base de codes dont les règles n'existent que dans une lecture.

</Accordion>

<Accordion title={"Combien d'heures un kit de démarrage payé économise-t-il réellement?"}>

Pour un multi-locataire SaaS avec facturation, rôles et un administrateur, la plage détaillée dans cet article est de 280 à 465 heures de travail compétent. Pour un outil mono-utilisateur avec une commande Stripe, il est proche de 20. Le nombre d'honnêtes dépend entièrement de ce que vous construisez, c'est pourquoi le tableau est détaillé plutôt que totalisé pour vous.

</Accordion>

<Accordion title={"Devrais-je le construire moi-même ?"}>

Construisez-le vous-même quand la plomberie est ce que vous voulez apprendre, quand votre produit est assez étrange que les hypothèses d'un débutant vous combattraient, ou quand votre temps n'a vraiment pas de coût d'opportunité. Achetez quand vous l'avez déjà construit une fois et rappelez-vous exactement combien de temps les trois quarts ennuyeux ont pris.

</Accordion>
