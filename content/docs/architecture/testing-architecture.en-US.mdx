## Vitest projects

`vp test` runs Vitest through Vite+ with three projects defined in `vite.config.ts`. Tests live in a `__test__` folder next to the code they cover and import test APIs from `vite-plus/test`.

| Project       | Environment | File pattern            |
| ------------- | ----------- | ----------------------- |
| `node`        | Node        | `*.test.ts`             |
| `integration` | Node        | `*.integration.test.ts` |
| `component`   | jsdom       | `*.component.test.tsx`  |

No test contacts a real Cloudflare account or provider:

- D1 is an in-memory SQLite database that runs the checked-in migrations, and KV and the `MEDIA` and `BUNDLES` R2 buckets are in-memory maps. KV, the buckets and the rate-limit counters reset before each test, and `createEdgeCache` stubs the Workers cache.
- `createServerFn` is replaced so a server function runs in-process through its real middleware and validator. That holds in the `node` and `integration` projects. In the `component` project a server function rejects, because jsdom is the browser.
- Component tests render with a real `QueryClient` and router.
- `fetch` reaches strict doubles of Resend and Polar instead of the network, and any other host fails as if the machine were offline.

## Provider doubles

`src/platform/testing/setup.ts` replaces `fetch` before every test, so the app's own Resend and Polar SDK clients send their real requests to `src/platform/testing/mocks/resend.ts` and `src/platform/testing/mocks/polar.ts`.

- They check what the provider checks: the API key or access token, the endpoint and method, and the body or query, with strict Zod schemas typed against the SDKs' own request models (`EmailApiOptions`, `models.CheckoutCreate`, `models.LicenseKeyDeactivate`). Polar's double also refuses a product the organization does not have, and a checkout price for another product or below Polar's smallest price.
- They answer as the provider answers: Resend replays a repeated `Idempotency-Key` instead of sending twice and answers 409 when the key comes back with a different email; Polar returns complete `models.Checkout`, `models.Order` and `models.LicenseKeyWithActivations` objects and a 404 for an order or key it does not hold.
- Polar's double serves the products and licence-key benefits that the areas seed, each from `__test__/fixtures/<area>.polar-catalogue.ts` in its module, joined by `src/platform/testing/mocks/polar-catalogue.entries.ts`. A product is an ID, a name, a price in minor units with its currency and a recurring interval, or none for a one-time purchase. The double seeds the catalogue again whenever it resets, so a product that a test adds with `seedPolarCatalogue`, such as a monthly plan, is gone in the next test.
- The licence area's catalogue comes from the code: a product for each tier with its ID in `POLAR_PRODUCT_IDS` and its price in `TIER_PRICES`, and a licence-key benefit for each with its activation limit in `LICENSE_ACTIVATION_LIMITS`. A checkout may carry its own fixed price for its product in `prices`, which the order then charges.
- A request the provider would refuse or an endpoint the app does not call is recorded, and a shared `afterEach` fails the test, even when the app caught the error.

## Integration suites

`*.integration.test.ts` files exercise whole server-side flows against the in-memory D1 and the provider doubles:

- The Better Auth suites run against the real `auth` from `auth.server.ts`, its plugins, hooks, rate limits and email senders included. `__test__/fixtures/auth.harness.ts` signs up, verifies and signs in with the headers a browser sends and reads each token from the email the Resend double delivered.
- `license-purchase.integration.test.ts` covers payments and licences: checkout creation (the tier, the whole-dollar regional price by country, the consent and the language, the referral metadata, refusal with an active licence), upgrades (the price less what was paid, the checkout for the difference, the tier and activation limit moved on the same key, the upgrade order's own key disabled, and a refunded upgrade put back), then signed `order.paid`, `benefit_grant.created`, `order.refunded` (partial and full) and `benefit_grant.revoked` webhooks through Better Auth's Polar endpoint, delivered out of order, twice and with bad signatures, the purchase confirmation email, and the licence activations listing and deactivation.
- `license.api.integration.test.ts` covers the [CLI licence API](/docs/features/cli-licence-api): every endpoint against D1 and the Polar double, for licences bought through the real webhook handlers, with a machine's activation reused, the activation limit, refunded and revoked licences, the rate limits per address and per key, and Polar outages. It reads every answer with the contract's `readApiResponse`, and `e2e/specs/cli-licence-api.spec.ts` calls the built Worker the way the CLI does.

## Coverage

`bun run test:coverage` enforces <RepositoryFact name="coverageThreshold" unit="percent" /> for lines, statements, functions and branches across `src`. The shadcn primitives, `src/platform/testing`, generated files and type declarations are excluded. Cover real behavior, and delete branches that can never run instead of stubbing globals to reach them.

## Browser tests

Playwright specs live in `e2e/specs`, with page objects in `e2e/pages` and fixtures in `e2e/fixtures`. They run against a production-like build that uses the `test` Wrangler environment: local D1, KV and R2 in `.wrangler/test`, dummy secrets from `.env.test`, and a test Worker that installs the same Resend and Polar doubles and exposes the delivered email so a spec can follow a real verification link. `e2e/fixtures/license.ts` delivers a paid order signed exactly as the integration suites sign theirs. Locally, Playwright migrates, seeds, builds and starts the app itself. The suite runs in Chromium and WebKit.

The journey suite in `e2e/journey/` is the exception: it runs by hand against the preview deployment, with real email, the Polar sandbox and the published CLI. See [Journey suite](/docs/tooling/playwright#journey-suite).

The integration suites above test many flows in-process that no browser test performs yet, such as webhooks delivered twice or out of order. [Test coverage](/docs/tooling/test-coverage) counts a flow as covered only when a browser test performs it against the built Worker, and lists the rest with what is missing.

## CI

`.github/workflows/ci.yml` runs on pull requests, and `.github/workflows/deploy.yml` runs it for each push to `main`:

1. `bun run check`: formatting, lint, type checks, `check:i18n` and `check:flows`
2. `bun run test:coverage`
3. One test build, then the Playwright suite in Chromium on <RepositoryFact name="e2eShards" /> shards in parallel
4. A preview deployment for pull requests, or a production deployment for `main`
