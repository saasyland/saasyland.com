---
title: "Moduli e validazione"
description: "Crea moduli con TanStack Form, i campi shadcn e lo schema Zod del modulo applicato anche dal server."
---

I moduli seguono il pattern shadcn per TanStack Form: `useForm` con lo schema Zod del modulo, render prop di `form.Field`, componenti `Field` di shadcn e una mutation per l'invio. La funzione server valida di nuovo lo stesso schema, quindi il controllo lato client serve solo a dare riscontro all'utente.

## Esempio

Versione ridotta di `src/presentation/components/custom/newsletter-form.tsx` (senza stili):

```tsx
const emailSchema = newsletterSubscriberZodSchemas.subscribeToNewsletter.pick({ email: true })

export const NewsletterForm = (): JSX.Element => {
  const t = useTranslations("components.custom.newsletter-form")
  const inputId = useId()
  const errorMessage = useErrorMessage()
  const queryClient = useQueryClient()

  const subscribe = useMutation({
    ...subscribeToNewsletterMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSuccess: ({ status }) => {
      toast.success(t(status))
      return queryClient.invalidateQueries({ queryKey: NEWSLETTER_SUBSCRIBER_QUERY_KEYS.ALL })
    },
  })

  const form = useForm({
    defaultValues: { email: "" },
    listeners: { onBlur: validateOnBlur },
    onSubmit: ({ value, formApi }) => {
      subscribe.mutate(
        { email: value.email, locale: getCurrentLocale() },
        {
          onSuccess: () => {
            formApi.reset()
          },
        },
      )
    },
    validators: { onChange: emailSchema },
  })

  return (
    <form
      noValidate
      onSubmit={(event) => {
        void submitForm(event, form)
      }}
    >
      <form.Field name="email">
        {(field) => {
          const isInvalid = isFieldInvalid(field)

          return (
            <Field data-invalid={isInvalid}>
              <FieldLabel htmlFor={inputId}>{t("label")}</FieldLabel>
              <Input
                aria-describedby={`${inputId}-error`}
                aria-invalid={isInvalid}
                autoComplete="email"
                id={inputId}
                name={field.name}
                onBlur={field.handleBlur}
                onChange={(event) => {
                  field.handleChange(event.target.value)
                }}
                placeholder={t("placeholder")}
                type="email"
                value={field.state.value}
              />
              <Button isPending={subscribe.isPending} type="submit">
                {subscribe.isPending ? t("submitting") : t("button")}
              </Button>
              <div id={`${inputId}-error`}>
                {isInvalid && (
                  <ValidationFieldError
                    message={fieldErrorMessage(field.state.meta.errors)}
                    namespace="auth.validations"
                    params={AUTH_VALIDATION_PARAMS}
                  />
                )}
              </div>
            </Field>
          )
        }}
      </form.Field>
    </form>
  )
}
```

## Schema

- Usa lo schema di `<table>.zod.ts` del modulo, oppure di `src/integrations/better-auth/auth.zod.ts` per i moduli di autenticazione. `.pick(...)` seleziona i campi mostrati dal modulo; i valori che l'utente non digita, come la lingua, vengono aggiunti in `onSubmit`.
- `validators: { onChange: emailSchema }` è l'unico validatore. TanStack Form lo esegue a ogni modifica e di nuovo all'invio; una copia separata in `onSubmit` lascerebbe rosso un errore dell'invio finché non cambia il suo stesso campo.
- `listeners: { onBlur: validateOnBlur }` esegue lo stesso validatore quando un campo perde il focus, così un campo attraversato dal visitatore con il tasto Tab mostra il suo errore non appena lo lascia.
- `noValidate` disattiva la validazione del browser, così gli unici errori sono i messaggi Zod.

## Errori

- Un campo mostra il suo errore quando il visitatore lo ha lasciato o ha provato a inviare, mai mentre sta ancora scrivendo: `isFieldInvalid(field)` da `src/integrations/tanstack-form/form.fields.ts`, che è `field.state.meta.isBlurred && !field.state.meta.isValid`. Questo valore imposta `data-invalid` su `Field`, `aria-invalid` sull'input e se l'errore viene reso, quindi tutti e tre cambiano insieme.
- Dopo che l'errore è comparso, ogni modifica valida di nuovo il campo, quindi l'errore scompare al tasto che corregge il valore. Non usare `isTouched`: TanStack Form lo imposta al primo tasto premuto.
- Il riscontro in tempo reale che premia i progressi, come `PasswordRequirements`, legge direttamente i valori e si aggiorna fin dal primo tasto premuto.
- L'input imposta sempre `aria-describedby` sull'id del proprio errore, `<input id>-error`, e `ValidationFieldError` rende quell'elemento con quell'id solo finché il campo non è valido. I browser ignorano un riferimento a un elemento assente, quindi un campo valido non ha descrizione.
- I messaggi Zod sono chiavi di traduzione, come `emailInvalid`. `fieldErrorMessage` prende il primo e `ValidationFieldError` mostra `<namespace>.<key>` con la voce corrispondente di `params`, ad esempio `max` (<RepositoryFact name="emailMaxLength" />) per `emailMaxLength`. Una chiave inesistente ripiega su `errors.codes.VALIDATION`.
- I form passano `auth.validations`, che i layout `auth` e `admin` precaricano e che l'area della newsletter aggiunge al layout `_marketing` per il suo form, tranne i form dei corsi dell'amministrazione, che passano `course.validations` dal layout `admin.courses.tsx`. La route deve caricare il namespace usato da un form. `messages/` contiene anche un namespace `<table>.validations` per gli altri moduli, come `user.validations`, ma nessun form o route li carica.
- Gli errori del server passano per `useErrorMessage()` nell'`onError` della mutation.

## Invio

- L'`onSubmit` del modulo chiama `submitForm(event, form)` da `src/integrations/tanstack-form/form.submit.ts`. Impedisce l'invio del browser e chiama `form.handleSubmit()`; quando il modulo non è valido, segna ogni campo come lasciato, così compaiono tutti gli errori, e sposta il focus sul primo controllo con `aria-invalid="true"`.
- Invia tramite le opzioni di mutation del caso d'uso espanse in `useMutation`. `SignInForm` è l'eccezione: chiama `signIn.email` del client Better Auth in un proprio `useMutation`, e il plugin a due fattori del client gestisce `twoFactorRedirect`.
- `<Button isPending={mutation.isPending} type="submit">` disattiva il pulsante e annuncia lo stato di attesa mentre la richiesta è in corso.
- Il pulsante di invio resta attivo mentre il modulo è incompleto; solo `isPending` lo disattiva. Premerlo con degli errori mostra tutti gli errori e sposta il focus sul primo campo non valido.
- Un errore del server che riguarda un solo campo, come `passwordCompromised` per una password trovata in una violazione di dati nota, va sotto quel campo con `showFieldError(formApi, { controlId, field, message })` da `form.submit.ts` invece che in un toast; scompare quando il campo cambia.
- Reimposta il modulo o naviga nell'`onSuccess` della mutation e invalida le query del modulo che la mutation modifica.

Altri esempi: `sign-in-form.tsx`, `sign-up-form.tsx`, `reset-password-form.tsx` e `two-factor-form.tsx` in `src/presentation/components/custom/auth/`.
