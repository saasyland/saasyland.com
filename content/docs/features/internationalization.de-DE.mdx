## Locales

`I18N` in `src/integrations/use-intl/i18n.config.ts` definiert die <RepositoryFact name="languages" /> Locales <RepositoryFact name="supportedLocales" /> mit `en-US` als Standard, das Cookie `saasyland.com_locale`, die Standardzeitzone `UTC` und die benannten Datumsformate `FORMATS`.

## URLs

Die Standard-Locale hat kein Präfix; jede andere Locale ist ein Pfadpräfix, zum Beispiel `/docs` und `/pl-PL/docs`. Bei Dokumentanfragen leitet der Worker (`resolveLocale` in `i18n.middleware.ts`) nicht kanonische Pfade mit einem 308 weiter: Aus `/en-US/docs` wird `/docs` und aus `/pl/docs` wird `/pl-PL/docs`. Pfade unter `/api` und `/_serverFn` tragen nie ein Präfix.

Das Router-`rewrite` in `src/router.tsx` entfernt das Präfix aus eingehenden URLs und fügt es ausgehenden hinzu, sodass Routen und Links einfache Pfade verwenden: `<Link to={ROUTES.SIGN_IN}>`. Rohe URLs in der aktuellen Locale, etwa `callbackURL` und `errorCallbackURL` von Better Auth, kommen aus `router.buildLocation(...).publicHref`; `localizePathname({ locale, pathname })` baut eine URL für eine bestimmte Locale, etwa die Links der Sprachauswahl und Links in E-Mails. `AriaProvider` lokalisiert das `href` von React-Aria-Komponenten.

## Locale-Cookie

Weicht die Locale in einer Dokument-URL vom Cookie ab, setzt der Worker das Cookie in der Antwort; kein Code wählt eine Locale anhand des Cookies. `getCurrentLocale()` funktioniert auf beiden Seiten und liest den URL-Pfad, mit `en-US` als Fallback. `/api`- und Serverfunktions-URLs haben kein Präfix, daher gibt die Funktion für sie auf dem Server `en-US` zurück. E-Mails erhalten ihre Locale stattdessen aus dem Ablauf: Auth-E-Mails aus dessen `callbackURL`, die Newsletter-Bestätigung aus der `locale`, die das Formular sendet.

## Meldungen

Meldungen liegen in `messages/<locale>/<namespace>.json`; der Dateiname ist der Namespace, zum Beispiel `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` oder `common`. Jeder Seiten-Namespace enthält `metadata.title` und `metadata.description`.

- Die Root-Namespaces (`common`, `components.*`, `errors*`) werden im Root-`beforeLoad` vorab geladen.
- Ein Layout deklariert `NAMESPACES`, eine Seite `NAMESPACE`. Beide landen in `staticData.namespaces` und werden vom Loader vorab geladen:

```ts
loader: async ({ context }) => {
  const locale = getCurrentLocale()
  const [metadata] = await Promise.all([
    loadPageMetadata({ locale, namespace: NAMESPACE }),
    preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
  ])
  return { locale, metadata }
},
```

- `TranslationsProvider` umschließt den Body des Dokuments und führt die Root-Namespaces mit den Namespaces der passenden Routen in einem `IntlProvider` zusammen, sodass auch Fehleransichten übersetzt sind.
- E-Mails laden ihren Namespace auf dem Server mit `loadNamespace`.

## Komponenten

Jede Komponente ruft `useTranslations` einmal auf und nennt den Übersetzer `t`. Eine Komponente, die zwei Namespaces benötigt, verwendet deren gemeinsamen übergeordneten Namespace oder `useTranslations()` mit vollständigen Schlüsseln.

## Datumsangaben, Zahlen und Zeitzonen

Datumsangaben und Zahlen werden mit `useFormatter` von use-intl formatiert (`format.dateTime`, `format.number`, `format.relativeTime`, `format.list`). Die Locale bestimmt die Konventionen: die Reihenfolge von Tag und Monat, die 12- oder 24-Stunden-Uhr und die Trennzeichen. Die Zeitzone ist die einzige Anzeigepräferenz, die ein Benutzer speichert.

`TranslationsProvider` übergibt `IntlProvider` zwei weitere Werte:

- `timeZone`: die `timezone` des angemeldeten Benutzers aus der aktuellen Session-Query oder ohne Session `I18N.DEFAULT_TIMEZONE` (`UTC`). `useSessionTimeZone` (`src/hooks/use-session-time-zone.ts`) liefert sie als einzigen Hook von `TIME_ZONE_HOOKS` in `translations-provider.tsx` (siehe [Plattform und Tests](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)), liest die Session, die die Route-Guards von `/app`, `/admin` und den Auth-Routen laden, und ruft sie nie selbst ab, sodass vorgerenderte öffentliche Seiten für jeden Besucher gleich sind und unverändert hydrieren. Ändert sich die Session-Query, etwa nachdem der Benutzer in den [Einstellungen](/docs/features/settings) eine neue Zeitzone gespeichert hat, wird jedes Datum neu gerendert.
- `formats`: `I18N.FORMATS`, die benannten Datumsformate. `src/types/use-intl.d.ts` registriert ihre Namen bei use-intl, sodass ein unbekannter Name die Typprüfung nicht besteht.

| Name            | Beispiel (Englisch) | Verwendung                                                                                                                               |
| --------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `date`          | Nov 14, 2026        | Der Tag eines Zeitpunkts in der Zeitzone des Lesers, in Tabellen                                                                         |
| `time`          | 3:04 PM UTC         | Die Uhrzeit eines Zeitpunkts mit Zonenkürzel, die `common.dateTime` an sein `date` anfügt                                                |
| `calendarDate`  | Nov 14, 2026        | Ein Datum ohne Uhrzeit, etwa das Datum eines Blogbeitrags. Es wird in UTC formatiert und verschiebt sich daher nie auf einen anderen Tag |
| `calendarMonth` | Nov                 | Die Tages- und Monatsbeschriftungen der Diagramme im Admin-Dashboard, die `day` oder `year` hinzufügen                                   |

Ein benanntes Format enthält ein Datum oder eine Uhrzeit, nie beides. Engines verbinden die beiden unterschiedlich: Safari gibt „Nov 14, 2026 at 3:04 PM UTC“ aus, wo der Server „Nov 14, 2026, 3:04 PM UTC“ ausgibt, sodass ein Format mit beidem in Safari einen anderen Text renderte, als der Server gesendet hatte, und React einen Hydration-Mismatch meldete. Ein Datum mit Uhrzeit ist die Nachricht `common.dateTime`, `{value, date, date}, {value, time, time}` (auf Japanisch ohne Komma), etwa `t("common.dateTime", { value: createdAt })`, und jede Engine gibt beide Teile gleich aus. Lizenzaktivierungen und die Kontodaten im Adminbereich verwenden sie. `i18n.config.test.ts` schlägt fehl, wenn ein benanntes Format Datums- und Uhrzeitfelder mischt, und prüft, dass die Nachricht in jeder Locale und jeder Zeitzone ausgibt, was die Engine des Servers ausgibt.

Eine relative Zeit, etwa „active 9 seconds ago“ bei einer Session, zählt ab dem Moment, in dem ihre Daten gelesen wurden: `format.relativeTime(session.updatedAt, dataUpdatedAt)`, mit dem `dataUpdatedAt` der Query, die die Session geliefert hat. Der Server schickt diesen Moment mit der Query an den Browser, sodass beide denselben Text ausgeben, unabhängig von Uhrzeit, Zeitzone und der Uhr des Besuchers. Ab `new Date()` gezählt, nahm sie den Zeitpunkt, zu dem der Server die Seite renderte, und einen späteren auf der eigenen Uhr des Browsers, sodass das Profil eines Benutzers im Adminbereich auf dem Server „active 9 seconds ago“ und im Browser „active 10 seconds ago“ ausgab und React einen Hydration-Mismatch meldete.

Ein Aufruf kann eine Option eines benannten Formats überschreiben: `format.dateTime(new Date(post.date), "calendarDate", { month: "long" })`. Admin-Tabellen zeigen die Datumsangaben anderer Benutzer in der eigenen Zeitzone des Betrachters mit deren Kürzel, sodass eine Spalte in einer einzigen Zeitzone gelesen und sortiert wird; die Zeitzone des Benutzers hat eine eigene Spalte.

## Sprache wechseln

`locale-switcher.tsx` enthält zwei Sprachauswahlen. `LocaleSwitcher` im Marketing-Footer ist ein `<details>`-Menü mit einem einfachen Link pro Locale auf den aktuellen Pfad in dieser Locale und funktioniert daher schon vor der Hydration. `LocaleSelect` in den Seitenleisten der Dokumentation und der Kunden-App ist ein Auswahlfeld im Stil von `ThemeSwitch`, das dieselbe URL öffnet. In beiden Fällen lädt die Wahl einer Sprache ein neues Dokument, und Query-String und Hash werden nicht übernommen. Polnische und ukrainische Seiten laden zusätzlich die Schrift-Subsets Latin Extended und Cyrillic vorab ([Schriften und Branding](/docs/ui/fonts-and-branding)). Ein Druck auf eine Sprache lässt den Fokus, wo er ist (`onMouseDown` verhindert den Wechsel), sodass das Menü, das sich schließt, sobald der Fokus es verlässt, offen bleibt, bis Safari, das beim Druck auf einen Link nichts fokussiert, dem Link folgt.

## Prüfungen

`bun run check:i18n` prüft die Meldungen: die Schlüsselparität zwischen den Locales, statische Schlüssel in ihrem `useTranslations`-Scope, Schlüssel, die keine Quelldatei rendert, die ICU-Syntax und Anreden, die die Locale nicht verwendet. `bun run check:content` prüft Dokumentation, Blog und Changelog: die Parität der Inhalte, identische Codeblöcke und die Anrede.
