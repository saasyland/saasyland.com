O histórico de `main` faz parte do produto: cada pull request mesclado com squash é uma linha que diz o que mudou para as pessoas que usam o código.

## Commits

As mensagens de commit seguem o Conventional Commits, escritas sem emoji; o hook `prepare-commit-msg` adiciona o emoji do tipo (veja [Conventional commits](/docs/tooling/conventional-commits) para a tabela):

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- O assunto é em minúsculas, no imperativo, e diz o que a alteração faz para os seus usuários: `feat(course): reorder the catalogue from the course list`, não `update course files`.
- O escopo é o módulo ou a funcionalidade: `course`, `auth`, `a11y`, `deps`, `readme`.
- O tipo é um de `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 e `revert` 🗑️; o hook rejeita qualquer outro. Nunca digite o emoji você mesmo: o hook não verifica um assunto que já começa com um emoji.
- Divida um pull request em commits lógicos: o recurso, a sua documentação como `docs(<scope>)` e as correções encontradas no caminho.
- Nunca faça commit com `--no-verify`. O hook `pre-commit` executa `bun run check:pre-commit`; quando ele falhar, corrija a causa.
- Formate e aplique o lint apenas nos arquivos que você alterou, com `bunx vp fmt <files>` e `bunx vp lint --fix <files>`. Não execute `bun run check:fix` nem `vp check --fix` sobre o repositório inteiro: eles reescrevem arquivos que você não tocou, incluindo as configurações compartilhadas do editor em `.vscode/settings.json`. Se `.vscode/` aparecer em `git status`, restaure-o a partir de `HEAD`.

## Nenhuma atribuição a IA

Os commits e as descrições de pull requests não levam trailer `Co-Authored-By` de uma ferramenta de IA, nenhuma linha "Generated with" nem qualquer outra atribuição a IA, mesmo quando uma ferramenta a adiciona por padrão. O GitHub associa o endereço desse trailer a uma conta sem relação com o projeto, que passa então a aparecer como colaboradora do repositório. O hook `commit-msg` rejeita uma mensagem de commit que contenha uma dessas atribuições e indica a linha a remover (veja [Conventional commits](/docs/tooling/conventional-commits)). O mesmo vale para as correções enviadas upstream (veja [Dependências](/docs/conventions/dependencies)).

## Branches e worktrees

- Crie a branch a partir de `main`, uma branch por pull request.
- Dê a cada branch a sua própria worktree do Git em vez de trocar a branch de um checkout, para que um checkout que um editor ou outro processo tem aberto nunca seja alterado por baixo dele:

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Antes de confiar em uma execução de testes, verifique `git branch --show-current` no diretório que você testou.

### Hooks em cada worktree [#hooks-in-every-worktree]

O Git lê `core.hooksPath` da configuração que todas as worktrees de um repositório compartilham, e o Vite+ define o valor como o caminho relativo `.vite-hooks/_`, então o Git executa o dispatcher de hooks da worktree em que você faz o commit. O dispatcher é gerado e nunca entra em um commit, por isso cada worktree precisa do seu, e onde ele falta o Git pula os hooks sem nenhum aviso. Dois passos o instalam:

- `git worktree add` executa o hook `post-checkout` do checkout em que você roda o comando, e `.vite-hooks/post-checkout` instala o dispatcher da nova worktree com `vp hooks enable`. Assim, um commit feito antes de `bun install` falha no hook `pre-commit` em vez de pulá-lo.
- `bun install` executa `prepare`, que renova o dispatcher com `vp config --no-agent` e depois executa `scripts/verify-git-hooks.ts`. A instalação falha quando `core.hooksPath` não é `.vite-hooks/_` ou quando falta ao dispatcher um hook de `.vite-hooks/`, e o erro mostra o comando que corrige o problema.

Nunca defina `core.hooksPath` com outro valor e nunca passe `-c core.hooksPath` ao Git. Enquanto essa configuração guardava o caminho absoluto do dispatcher do checkout principal, `vp config` não instalou dispatcher nas outras worktrees, e quando o `bun install` seguinte no checkout principal restaurou o caminho relativo, os commits nessas worktrees foram feitos sem hooks. `vp hooks status` mostra se os hooks estão ativos em uma worktree.

## Histórico linear [#linear-history]

O ruleset que protege `main` no GitHub exige um histórico linear, aceita pull requests apenas pela fila de mesclagem, que faz squash de cada um, e recusa force-push, então cada pull request chega a `main` como um único commit. As branches dos pull requests também ficam lineares:

- Nunca crie um commit de merge, nem em `main` nem na branch de um pull request: não faça merge de `main` em uma branch e não resolva conflitos em um commit de merge.
- Atualize uma branch fazendo rebase sobre `main`, com `gh pr update-branch --rebase` ou com `git fetch origin` e `git rebase origin/main`, quando ela tiver conflitos com `main`. Um pull request sem conflitos não precisa de rebase para ser mesclado: a fila de mesclagem o testa sobre a `main` mais recente.
- Quando o GitHub não consegue fazer rebase de um pull request com vários commits, integre-o de novo como um único commit sobre `main`: junte a branch em um commit na base de merge dela e depois faça rebase desse commit, para resolver cada conflito uma única vez:

```sh
git fetch origin
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -m "feat(course): reorder the catalogue from the course list"
git rebase origin/main
git push --force-with-lease
```

- Envie uma branch reescrita com `git push --force-with-lease`, e apenas a branch do seu próprio pull request. Nunca dê force-push em `main` nem na branch de outra pessoa, e nunca use um `--force` simples, que sobrescreve commits enviados desde o seu último fetch.

## Pull requests

- **Pequenos e focados.** Uma correção, um recurso ou uma refatoração por pull request. Um recurso grande vira uma pilha de pull requests, cada um revisável por si só, como foram os vídeos, os cursos e a administração de cursos.
- **O título é o commit do squash.** Use o formato de commit sem o emoji; ele se torna o assunto em `main`, que o GitHub termina com `(#<number>)`. `scripts/enqueue-pr.ts` adiciona o emoji que o hook de commit adicionaria quando coloca o pull request na fila de mesclagem.
- **A descrição** tem um `## Summary` do que mudou e por quê, um `## Test plan` com os comandos que você executou e os seus resultados, e uma lista `## Docs` das páginas, seções do README e textos que você atualizou. Escreva de forma simples, sem linguagem de marketing.
- **Sem revisão automática.** O ruleset de `main` tem a regra `copilot_code_review` com `review_on_push: true`, mas, em 22 de novembro de 2026, o GitHub Copilot não revisou nenhum pull request desde o #70, então os pull requests não recebem revisão automática. Mesmo uma revisão seria apenas consultiva: não aprovaria nem bloquearia nada, porque o ruleset não exige nenhuma aprovação.
- **Todo pull request atualiza o que ele torna impreciso:** o README, as páginas da documentação em todos os locales e qualquer texto do site ou afirmação da landing page que ele afete, e adiciona a sua [entrada do changelog](#changelog-entries). Uma imprecisão encontrada em código que você não alterou ganha o seu próprio pull request. O README não pode imprimir valores do código, então `src/__test__/readme.test.ts` o lê: cada versão, porta, contagem e limite que ele informa deve ser igual ao valor que o código ou `REPOSITORY_FACTS` guarda, qualquer outro número falha, a menos que seja uma data ou um dos fatos externos que o teste lista, cada comando `bun run` deve nomear um script de `package.json`, e cada arquivo, rota e regra de lint que ele nomeia deve existir.

## Mesclagem [#merging]

Um pull request só chega à `main` pela fila de mesclagem do GitHub. Quando as verificações dele estiverem verdes e a entrada do changelog estiver incluída, coloque-o na fila com o número dele:

```sh
bun scripts/enqueue-pr.ts 280
```

O script falha com um título que não segue o formato de commit, troca o título pelo assunto que o hook de commit escreveria, com o emoji, e executa `gh pr merge --auto --squash`, que adiciona o pull request à fila assim que as verificações dele passam. A fila testa cada pull request sobre a `main` e sobre os pull requests à frente dele, com as verificações que o pull request executou, faz o build de vários ao mesmo tempo e integra juntos os pull requests de um grupo quando todos eles passam, então ninguém precisa fazer rebase de um pull request pronto para mesclá-lo. Um pull request que falha na fila sai dela; corrija-o e coloque-o na fila de novo. Nunca mescle um pull request manualmente nem por fora da fila: a execução da fila é a que testou o commit que chega à `main`, e o `deploy.yml` executa de novo todas as verificações para um commit que passou por fora dela.

## Entradas do changelog [#changelog-entries]

Todo pull request adiciona a sua própria entrada ao [changelog](/docs/project/changelog), de modo que pull requests abertos ao mesmo tempo nunca editam o mesmo arquivo.

- **Dê a ela o número do pull request.** Abra o pull request e depois adicione `content/changelog/<number>.<locale>.mdx` em todos os locales: uma lista com marcadores, sem frontmatter, do que mudou para quem usa o código, com links para as páginas da documentação afetadas.
- **Nunca escreva uma data nem o número do pull request.** A página do changelog tira o dia de cada entrada, e as notas de versão a sua release, do histórico do Git: o dia, em UTC, do commit squash cujo assunto o GitHub termina com `(#<number>)`. Até o pull request ser mesclado, a entrada aparece em **Não lançado**. O número vem do nome do arquivo: a página termina cada item de uma entrada com um link para o seu pull request, ou para o seu commit no caso de uma entrada com o nome de um commit, e as notas de versão terminam cada item com `(#<number>)`, que o GitHub transforma em link. Depois do deploy, a página também liga cada entrada à [release](/docs/tooling/ci-cd#releases-and-tags) que a entregou primeiro.
- **A CI verifica.** Em um pull request, `bun run check` falha enquanto `content/changelog/<number>.en-US.mdx` não existir, e `check:content` compara cada tradução com ele como faz com uma página da documentação. Um arquivo nomeado sem o número de um pull request nem o hash completo de um commit também falha: as poucas mudanças que chegaram à `main` sem pull request levam o nome do seu commit.
- **Só a sua própria entrada pode ficar sem lançamento.** Na CI, o build do site falha enquanto o changelog listaria em **Não lançado** uma entrada que não deveria estar ali: em um pull request para a `main`, qualquer entrada que não seja a do próprio pull request, e na fila de mesclagem e na `main`, qualquer entrada. Uma branch da fila de mesclagem já contém o commit squash de cada pull request do seu grupo, então cada uma das entradas deles tem o seu dia. Um build local, que não tem `GITHUB_REF`, lista todas as entradas não mescladas. Isso pega uma entrada que sobrevive ao seu pull request: `content/changelog/219.<locale>.mdx` ficou para trás quando o #219 foi fechado sem ser mesclado, repetia a entrada do #220 e aparecia em **Não lançado** em produção até o #254 removê-la.

## Verificações

A CI executa `bun run check` e `bun run test:coverage`, verifica o site sem cada funcionalidade opcional com `bun run check:features`, em um job por cenário de `scripts/features.ts`, compila o Worker de teste e executa a suíte de navegador no Chromium e no WebKit, e envia o Worker de preview ao Cloudflare como uma versão que não recebe tráfego. Esse upload é a verificação de que o Cloudflare aceita o Worker: os limites de upload do Cloudflare já fizeram falhar um deploy que tinha passado em todas as outras verificações. A fila de mesclagem executa de novo as mesmas verificações no pull request junto com a `main` e os pull requests à frente dele. Veja [CI/CD](/docs/tooling/ci-cd).
