## Regras de organização

- **Arquivos e pastas usam kebab-case.** Os testes ficam em uma pasta irmã `__test__`.
- **Rotas apenas compõem.** Um arquivo de rota define o componente de página ou de layout, `NAMESPACE` ou `NAMESPACES`, o loader e o `head`. Ele não contém widgets, diálogos nem definições de colunas.
- **Módulos são tabelas do banco de dados.** Crie `src/modules/<name>` apenas para uma tabela real. Uma server function que não trabalha com uma tabela vai para `src/lib` (por exemplo, `src/lib/github.ts`) ou, se uma única rota a usa, para o arquivo dessa rota.
- **Componentes compartilhados ficam no nível plano.** Um componente usado em várias áreas é um único arquivo diretamente em `presentation/components/custom`.
- **Pastas de área e de página.** Componentes usados por uma única área ficam em `admin/`, `app/`, `auth/`, `blog/`, `courses/`, `landing-page/` ou `settings/`, que contém os cards de conta que `/app/settings` e `/admin/settings` compartilham. As páginas do admin têm pasta própria, como `admin/users/`. A landing page se divide em `sections/` (um arquivo por seção da página) e `components/` (partes compartilhadas entre as seções).
- **Um widget, diálogo, formulário ou conjunto de colunas por arquivo.** Não divida um componente em um wrapper e um arquivo `-content`.
- **Sem pastas auxiliares aninhadas.** Pastas de componentes nunca contêm subpastas `components/`, `constants/`, `hooks/`, `lib/` ou `types/`, e nenhum arquivo auxiliar `.ts` fica ao lado de um componente. Uma constante usada por um único componente permanece no arquivo desse componente.
- **Dados compartilhados vão para `src/data`.** Exemplos: `MARKETING_SECTION_IDS` e as opções da CLI. As áreas também declaram ali o que adicionam à plataforma: handlers do Worker e plugins do Vite (veja [O que as áreas adicionam](/docs/architecture/platform-layer#what-the-areas-add)).
- **Os caminhos de cada área vão para `src/areas/<area>.shared.ts`.** Todo ambiente de execução carrega esse arquivo: o navegador, o Worker, os scripts do Bun, o Playwright e o `vite.config.ts`. Por isso ele só contém constantes e importa por caminho relativo, e `src/routes.ts` reúne os caminhos de todas as áreas (veja [Caminhos e navegação](/docs/conventions/routes#paths-and-navigation)). As verificações do site no ar são um tipo de arquivo próprio, `src/areas/<area>.live.ts`, porque só a verificação depois do deploy e a documentação as carregam. O que uma área adiciona às páginas, como os seus namespaces de layout, o seu fuso horário, os seus componentes raiz e os seus itens no painel administrativo e no espaço de trabalho do cliente, vai no seu arquivo de navegador, `src/areas/<area>.ts`, um objeto `<AREA>_BROWSER` que só o navegador e a renderização no servidor carregam. Os itens de menu também são um tipo de arquivo próprio e puro, `src/areas/<area>.navigation.ts`, que `src/areas/navigation.entries.ts` reúne e `src/data/navigation.ts` lê, porque o projeto do Remotion lê o menu do admin e o seu job de CI só instala os pacotes do próprio Remotion, então ele não consegue carregar o arquivo de navegador de uma área, `src/areas/<area>.ts`, que importa código do router, do TanStack Query e de server functions. As declarações de permissão vão para um arquivo próprio, `src/areas/<area>.access.ts`, para que uma pessoa revise cada mudança nelas.
- **Arquivos gerados não são editados à mão.** O plugin do router escreve `src/routeTree.gen.ts`, `bun run cf-typegen` escreve `src/types/worker-configuration.d.ts`, e `bun run content` e `bun run generate:cn` escrevem `.source/`.
