Os workflows ficam em `.github/workflows/`. Os workflows da aplicação (`ci.yml`, `deploy.yml`, `e2e-reusable.yml` e `deploy-reusable.yml`) preparam a toolchain com a action composta `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ com a versão do Node em `.nvmrc` e o cache de instalação do Bun, que o `setup-vp` restaura uma única vez, `bun install --frozen-lockfile --ignore-scripts` e `bun run typegen`. Já o `remotion.yml` prepara o Node de `.nvmrc` e o npm.

| Workflow              | Gatilho                                                                                    | Jobs                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests e chamadas do `deploy.yml`                                                   | Verificações e cobertura, E2E no Chromium e, depois, o deploy de preview de um pull request               |
| `deploy.yml`          | Pushes para `main`                                                                         | As verificações do `ci.yml` e, depois, o deploy de produção e a sua release                               |
| `e2e-full.yml`        | Pushes para `main`, o agendamento <RepositoryFact name="e2eFullSchedule" /> em UTC, manual | WebKit no push; Chromium e WebKit nas execuções agendadas e manuais                                       |
| `e2e-reusable.yml`    | Chamado pelos workflows acima                                                              | Um único build de testes, um projeto do Playwright em shards paralelos e uma única verificação para ambos |
| `deploy-reusable.yml` | Chamado por `ci.yml` e `deploy.yml`                                                        | Build, migrações do D1 e `wrangler deploy`                                                                |
| `remotion.yml`        | Alterações em `remotion/` ou nos arquivos do site que ele importa                          | Verifica e empacota com npm o projeto do vídeo da landing page                                            |

`remotion.yml` é acionado pelos mesmos caminhos em pull requests e pushes: `remotion/`, o próprio workflow e os arquivos do site que `remotion/src` importa, diretamente ou por meio de outros arquivos do site. `src/__test__/workflows.test.ts` segue essas importações e falha quando um arquivo alcançado não corresponde a nenhum dos caminhos ou quando um caminho não corresponde a nenhum dos arquivos.

Os checkouts em `e2e-reusable.yml`, cujo build renderiza o changelog e cujo `content.spec.ts` o lê, em `deploy-reusable.yml`, que faz o build do site, e no job `release` buscam todos os commits sem as suas árvores (`fetch-depth: 0` e `filter: tree:0`): o [changelog](/docs/project/changelog) data cada entrada pelo commit que a levou à `main`. Em relação a um clone raso, só os próprios commits são acrescentados; com um clone raso o build falharia em vez de datar as entradas errado. `src/__test__/workflows.test.ts` falha quando um desses checkouts deixa de buscar o histórico.

## Verificações [#checks]

O job `verify` em `ci.yml` executa `bun run check` (tabelas de nomes de classes, verificações de i18n e de conteúdo, o [inventário de fluxos](/docs/tooling/test-coverage#flow-coverage), formatação, lint e tipos) e `bun run test:coverage` e, em seguida, envia o relatório de cobertura. O job `e2e` chama `e2e-reusable.yml`, que faz o build uma única vez e executa a suíte em <RepositoryFact name="e2eShards" /> runners em paralelo:

| Job                                          | Executa                                                                                                                                                       |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                      | `db:reset:test` e `build:test` e, em seguida, envia `dist` e o `.wrangler/test` já populado pelo seed como um único artefato                                  |
| `shard`                                      | Um job por shard: baixa esse build, instala o navegador e executa `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>`                     |
| `report`, chamado `Build and E2E (chromium)` | Falha a menos que o build e todos os shards tenham passado; quando um shard falhou, mescla os relatórios blob dos shards em um único relatório HTML e o envia |

As novas tentativas e os workers do próprio Playwright continuam como o [Playwright](/docs/tooling/playwright#configuration) os descreve, em cada shard. O job `report` é a única verificação que as regras da branch exigem, então adicionar ou remover um shard não muda o nome de nenhuma verificação obrigatória.

Em um pull request, `bun run check` também falha até que o pull request adicione a sua [entrada do changelog](/docs/conventions/git-workflow#changelog-entries). O build do job `e2e`, e o dos jobs de deploy, falha enquanto o changelog listaria em **Não lançado** uma entrada que não seja a do próprio pull request, e na `main` enquanto listaria qualquer uma.

## Deploys

Os deploys só são executados depois que `verify` e `e2e` passam, na execução do `ci.yml` para um pull request e na execução do `deploy.yml`, que chama o `ci.yml`, para um push para `main`:

| Evento                                       | Destino      | Ambiente do GitHub | URL                           |
| -------------------------------------------- | ------------ | ------------------ | ----------------------------- |
| Pull request de uma branch deste repositório | `preview`    | `Preview`          | https://preview.saasyland.com |
| Push para `main`                             | `production` | `Production`       | https://saasyland.com         |

`deploy-reusable.yml` atribui a cada ambiente do GitHub a sua URL, e `src/__test__/workflows.test.ts` falha quando uma delas difere do host do ambiente em `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Pull requests de forks e do Dependabot são validados, mas não recebem deploy. O preview é compartilhado: cada deploy substitui o anterior e usa o mesmo banco de dados D1, o mesmo namespace KV e os mesmos buckets R2 de preview.

`deploy-reusable.yml` verifica a existência dos secrets `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID`, executa `scripts/verify-bindings.ts`, faz o build com os valores fictícios de `.env.test`, remove o `dist/server/.dev.vars` gerado, aplica `db:migrate:<target>` e executa `vp exec wrangler deploy --config dist/server/wrangler.json`. Não executa `scripts/verify-deployment.ts`, a verificação do site no ar dos scripts `deploy:<target>`, porque a proteção contra bots da Cloudflare responde 403 às requisições dos runners de CI. Também não executa `scripts/run-deploy-checks.ts`, então a CI não executa nenhuma das verificações de deploy que as áreas declaram em `DEPLOY_CHECKS`: não há `.env.<target>` na CI, e os ambientes do GitHub guardam só as credenciais da Cloudflare. Hoje são `auth:verify`, da área de autenticação, e `polar:verify`, da área da Polar; execute localmente `bun run auth:verify:<target>` depois de alterar um cliente OAuth e `bun run polar:verify:<target>` depois de cada alteração na Polar ([Configuração da Polar](/docs/getting-started/polar-setup)). Nenhum arquivo de secrets é enviado: o Worker mantém os secrets de runtime já configurados na Cloudflare. Deploys para o mesmo destino entram em fila em vez de cancelarem uns aos outros. Um novo commit em um pull request cancela a execução do `ci.yml` do commit anterior, que ninguém vai mesclar, enquanto as execuções do `deploy.yml` e do `e2e-full.yml` na `main` entram em fila e nunca cancelam umas às outras (`concurrency` com `queue: max`), então todo push para a `main` é testado e recebe deploy.

O Dependabot atualiza as GitHub Actions semanalmente.

## Releases e tags [#releases-and-tags]

O site recebe deploys contínuos, então suas versões são datas, não versões semânticas. Quando um deploy de produção termina com sucesso, o job `release` do `deploy.yml` marca o commit implantado com a tag `vYYYY.MM.DD` na data UTC e publica uma GitHub Release para ele. Um segundo deploy de produção no mesmo dia recebe a tag `vYYYY.MM.DD.2`, o seguinte `.3`, e assim por diante. Deploys de preview nunca recebem tag. O job `release` é o único com `contents: write`.

As notas da release são as entradas do [changelog](/docs/project/changelog) que a release entregou, as que chegaram à `main` desde a tag de release anterior, cada uma terminada em `(#<number>)`, que o GitHub transforma em link para o seu pull request, então cada mudança é descrita em um só lugar; quando uma release não entregou nenhuma, as suas notas apontam para o changelog. `scripts/publish-release.ts` pega as notas de `src/lib/release.ts` e executa `gh release create` com a tag que o deploy escolheu. Uma nova execução mantém a tag que o commit já tem e pula uma release que já existe.

O job do deploy de produção escolhe essa tag antes do build: `scripts/choose-release-tag.ts` aplica `releaseTag` de `src/lib/release.ts` às tags do checkout, o build recebe a tag como `RELEASE_TAG` e o job a repassa ao job `release` como a sua saída `release-tag`, então o deploy e a sua release compartilham uma tag. Com ela, o [changelog](/docs/project/changelog) liga cada entrada à release que a entregou primeiro: a tag de release mais antiga cujo commit contém o commit squash da entrada no histórico de primeiros pais da `main`, que o build lê junto com as datas em um único `git log`, ou a própria tag do deploy para as entradas que ele traz. O job `release` lê o changelog da mesma forma, com a tag que publica, então as notas de uma release são exatamente as entradas que a página liga a essa release. Entradas mescladas antes da primeira tag de release não apontam para nenhuma release, nem, nos builds locais, de preview e de pull requests, as entradas que nenhum deploy entregou ainda. Dois deploys de produção não podem escolher a mesma tag: `deploy.yml` roda uma única execução do workflow de cada vez (`concurrency` com `queue: max`), então o job `release` da execução anterior já criou a sua tag quando o próximo deploy faz o checkout do repositório.

Para voltar a produção a uma release, reverta em um pull request tudo o que veio depois da tag dela:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

O merge faz o deploy do código da tag após as verificações de sempre e o marca como uma nova release. As migrações do D1 não são revertidas, então o código mais antigo roda sobre o esquema mais novo. Toda mudança de esquema precisa funcionar com a aplicação implantada antes dela, o que torna isso seguro para a release anterior; leia as migrações intermediárias antes de voltar mais.
