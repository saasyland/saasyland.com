---
title: "Contribuir"
description: "Cómo proponer cambios en SaaSy Land."
---

1. Comenta primero los cambios importantes en un issue, abierto desde el formulario de informe de error o de solicitud de funcionalidad.
2. Crea una rama a partir de `main`.
3. Sigue las [convenciones](/docs/conventions) y la [arquitectura](/docs/architecture), y lee la [skill para agentes](/docs/tooling/agent-skills) correspondiente antes de modificar una integración con un proveedor. Los agentes de programación parten de `AGENTS.md`, en la raíz del repositorio.
4. Mantén las pruebas junto a su propietario y respeta el umbral de cobertura del <RepositoryFact name="coverageThreshold" unit="percent" />.
5. Ejecuta las comprobaciones siguientes.
6. Haz commit con un mensaje de [commit convencional](/docs/tooling/conventional-commits), abre una pull request con un título convencional y rellena su plantilla.
7. Haz rebase de la rama sobre `main` cuando entre en conflicto, nunca fusiones `main` en ella, como explica [Git y pull requests](/docs/conventions/git-workflow#linear-history). Quien mantiene el proyecto pone la pull request en verde en la [cola de fusión](/docs/conventions/git-workflow#merging), que vuelve a probarla sobre `main` y la fusiona.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`build:test` ejecuta el build completo de Cloudflare, que `check` y las pruebas unitarias no ejercitan. El último comando compila y sirve el Worker de pruebas cuando no hay ningún servidor en marcha y ejecuta en Chromium las specs que nombras: ejecuta las que cubren lo que has cambiado. La CI ejecuta todas las specs en la pull request y de nuevo en la cola de fusión, y la pull request solo se fusiona cuando esa ejecución está en verde; `bun run test:e2e:pr` ejecuta la suite completa en local de la misma manera. Ejecuta también la suite completa de pruebas en el navegador en WebKit (`bun run test:e2e`) para los cambios que puedan comportarse de forma distinta allí. Valida por separado las integraciones con proveedores reales cuando cambie su configuración.

Cuando cambie el comportamiento, actualiza `content/docs` en todos los idiomas; `bun run check:i18n` rechaza las traducciones que faltan y los bloques de código y la navegación que difieren. La plantilla de la pull request incluye un resumen, un plan de pruebas con las comprobaciones anteriores y una lista de la documentación actualizada; describe en ella el comportamiento resultante, cómo lo has verificado y cualquier flujo que el cambio deje sin terminar. Una pantalla de administración solo se publica con un origen real para sus datos (consulta [Panel de administración](/docs/features/admin-dashboard#real-data-only)).

`CONTRIBUTING.md`, en la raíz del repositorio, es la versión breve de esta página, y `SUPPORT.md` indica dónde obtener ayuda. Todas las personas que participan siguen `CODE_OF_CONDUCT.md`, el Contributor Covenant 2.1. Informa de las vulnerabilidades de seguridad de forma privada, como describe `SECURITY.md`, nunca en un issue público.
