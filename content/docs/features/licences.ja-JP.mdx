ライセンスのエリアは、Polar のエリアのプラグインと Webhook（[決済](/docs/features/payments)）を土台に、プラン `core`、`complete`、`agency` を Polar の商品として販売します。`src/modules/license/license.utils.ts` の `POLAR_PRODUCT_IDS` はプランを `POLAR_PRODUCT_ID_CORE`、`POLAR_PRODUCT_ID_COMPLETE`、`POLAR_PRODUCT_ID_AGENCY` に対応付け、`licenseTierForProduct` は同じ対応付けから商品のプランを読み取ります。[Polar の設定](/docs/getting-started/polar-setup)では、各プランが Polar で必要とする商品、ライセンスキー、同意のチェックボックスを説明しています。

## 購入

有効なライセンスを持たないサインイン済みユーザーには、`/app` と `/app/license` に `LicenseOffer` が表示されます。ランディングページのプランのカード（`PricingTiers`。[ランディングページ](/docs/features/landing-page)を参照）にプランごとの `CheckoutButton` を付けたもので、地域価格のチェックボックスと、購入で視聴できるようになるコースのレッスンも表示されます。

### 即時提供への同意 [#consent-to-immediate-supply]

購入者は、支払いの直前に Polar のチェックアウトページで 1 回だけ同意します。Polar のすべてのライセンスの商品は、チェックボックスのフィールド <RepositoryFact name="licenseWithdrawalConsentField" /> を必須にしています（[Polar のセットアップ](/docs/getting-started/polar-setup#consent-checkbox)）。そのラベルは即時提供を求め、ライセンスキーの発行で提供が始まった時点で <RepositoryFact name="refundWithdrawalDays" unit="day" />の撤回権を失うことを了承する内容です。`startCheckout` は `custom_field_data` を送らないため、ボックスは空の状態で始まり、チェックを入れられるのは購入者だけです。ボックスが空のままでは Polar は支払いを受け付けません。購入者が支払うときに Polar がフィールドを商品と照合し、必須のチェックボックスには `true` しか受け付けないためです。Polar はチェックの入ったボックスを注文に保存し、[購入確認](#purchase-confirmation)メールがそれを耐久性のある媒体で確認します。これが、EU でデジタルコンテンツの撤回権を消滅させる条件、つまり購入者の事前の明示的な同意、了承、そして確認です。

`CheckoutButton`（`src/presentation/components/custom/app/checkout.tsx`）は、押されるとすぐに独自のダイアログなしで購入を開始し、Polar のチェックアウトをページの上に開き（[ページに重ねて開くチェックアウト](#the-checkout-over-the-page)）、それが開くまでほかのプランのボタンを無効にします。同じファイルの `CheckoutNotice` は、プランのカードの下と選んだプランの下で、Polar が Merchant of Record であり支払いページで同意を求めること、プロジェクトを生成するか有料レッスンを開くまでは <RepositoryFact name="refundWithdrawalDays" unit="day" />の間は全額返金を受けられることを事前に伝え、返金ポリシー、利用規約、商用ライセンスにリンクします。

### 購入の開始 [#starting-the-checkout]

`startCheckout`（`src/modules/license/use-cases/start-checkout.ts`）は `{ locale, returnPath, tier }` を受け取ります。`returnPath` は購入者がボタンを押したページで、サイト内にとどまるよう `callbackPathSchema` で検証します。リクエストのオリジンは `trustedRequestOrigin`（`src/lib/request-origin.ts`）で読み取ります。この関数は、ビルドモードについて `appHostsForMode` が挙げていないホストや、開発とテスト以外での平文の HTTP を `FORBIDDEN` で拒否します。そのうえで次の処理を行います。

1. アカウントにすでに同じプランか上位プランの `active` なライセンスがある場合は、チェックアウトの代わりに `{ alreadyActive: true }` を返します。ボタンは `pages.license` の `buy.alreadyActive` を表示してライセンスを再取得するため、購入後も開いたままだったページはライセンスの表示に切り替わります。
2. `buyerTierPrice`（`license.ppp.ts`）でプランの価格を決めます。`TIER_PRICES` の金額に、`regional_pricing` Cookie が `off` でない限り `PPP_TIERS` にある `cf-ipcountry` の国の倍率を掛け、`regionalPrice`（`license.pricing.ts`）でドル未満を切り捨てます。`regionalPrice` は、プランのカードが価格の表示に使うのと同じ関数です。有効なライセンスのプランがより下位のアカウントでは、代わりに[アップグレード](#upgrades)の価格になります。
3. `polar.checkouts.create` でプランの Polar チェックアウトを作成します。チェックアウトはアカウントに紐付け（`external_customer_id`）、そのメールアドレスと名前（`customer_email`、`customer_name`）を入力済みにするため、チェックアウトのフォームはそれらが入った状態で開きます。さらに、`cf-connecting-ip` から得た購入者の IP アドレス（`customer_ip_address`。Better Auth の `getIP` で読み取り）、無効にした割引コード、`TIER_PRICES` と異なる場合にこのチェックアウトに限って有効なプランの商品の固定価格として `prices` に入れた手順 2 の価格、`metadata` の `locale`（`LICENSE_CHECKOUT_METADATA`）に入れた購入者の言語（アップグレードでは `upgrade_from_order` と `upgrade_from_tier` に入れたアップグレード元の注文とプランも。訪問者がアフィリエイトリンクから来た場合はアフィリエイトの紹介情報も。[アフィリエイトプログラム](/docs/features/affiliates)を参照）、`polarCheckoutLanguage` で決めた Polar のページの言語を入れた `locale`、Polar が戻るボタンを表示するよう `return_url` にした `returnPath` のページ、購入者の言語での成功 URL `/app?checkoutId={CHECKOUT_ID}&tier=<tier>`（`localizePathname`）、そしてチェックアウトをフレームに表示してそのメッセージを受け取れる唯一のページとして `embed_origin` に入れたリクエストのオリジンを渡します。Polar はメタデータと購入者が与えた同意を注文にコピーし、`{CHECKOUT_ID}`（`POLAR_CHECKOUT_ID_PLACEHOLDER`）をチェックアウト ID に置き換えます。
4. チェックアウトの ID と URL を返し、`CheckoutButton` がそれをページの上に開きます。

返金済み（`refunded`）または取り消し済み（`revoked`）のライセンスがあっても、新しい購入はできます。

`POLAR_CHECKOUT_LANGUAGES`（`src/data/polar.ts`）は、サイトの各言語を Polar のチェックアウトが翻訳されている言語に対応付けます。対応する言語がない場合、`polarCheckoutLanguage` は英語である `POLAR_CHECKOUT_DEFAULT_LANGUAGE` を使い、その言語では `isPolarCheckoutTranslated` によって `CheckoutNotice` が支払いページは英語で開くことを書き添えます。Polar がその言語でページを表示するのは、組織でチェックアウトのローカライズがオンになっている間だけで、`polar:verify` がこれを確認します（[Polar のセットアップ](/docs/getting-started/polar-setup#checkout-language)）。

### ページに重ねて開くチェックアウト [#the-checkout-over-the-page]

`openCheckoutOverlay`（`src/lib/checkout-overlay.ts`）は、購入者がいるページの上にオーバーレイで Polar のチェックアウトを表示します。`@polar-sh/checkout/embed` の `PolarEmbedCheckout` はチェックアウトが始まったときに初めてインポートするため、購入者がボタンを押す前に Polar のスクリプトを読み込むページはありません。ページがそれをエントリースクリプトとして、または静的インポートで読み込むと、`scripts/verify-build.ts` がビルドを失敗させます。`PolarEmbedCheckout.create` はサイトで解決済みのテーマで Polar のフレームをページに追加し、チェックアウトを読み込んだと Polar が伝えると、オーバーレイは次のように動作します。

- `pages.license` の `buy.overlay` でフレームに名前を付け、フォーカスをフレームの中に移して、ページのほかの部分を `inert` にします。これにより、キーボードとスクリーンリーダーはチェックアウトの中にとどまります。
- 支払い前の `close` では、チェックアウトを閉じてページを元に戻します。購入者は元の場所にとどまり、ボタンは再び押せる状態でフォーカスを受け取ります。
- `success`、または Polar の `confirmed` の後の `close` では、Polar のスクリプトにリダイレクトさせずにチェックアウトを閉じ、`CheckoutButton` がページを再読み込みせずにその場で `/app?checkoutId=<id>&tier=<tier>` に移動します。これは、Polar のチェックアウトページが戻る先と同じ成功 URL です（[支払い後](#after-payment)）。

ボタンは、押されてからオーバーレイが開くまで `buy.pending` を表示します。オーバーレイを開けない場合、ボタンはブラウザーを同じチェックアウトの Polar のチェックアウトページに移動させ、その `return_url` と成功 URL がこれまでどおり購入者を戻します。オーバーレイを開けないのは、スクリプトの読み込みに失敗したとき、Polar のフレームが現れないとき、またはフレームは読み込まれたものの、チェックアウトの準備ができたことを Polar が <RepositoryFact name="checkoutOverlayGraceSeconds" unit="second" />以内（`CHECKOUT_OVERLAY_GRACE_MS`）に伝えないときです。最後の例は、組織が挙げていないホストからのフレーム表示を Polar が拒否する場合です（[Polar のセットアップ](/docs/getting-started/polar-setup#embedding)）。

ページの Content Security Policy がフレームとして許可するのは、Polar のチェックアウトだけです。`documentPolicy` は、`POLAR_SERVER` に対して `polarCheckoutOrigin`（`src/data/polar.ts`）が返すオリジン、つまり本番では `https://polar.sh`、サンドボックスでは `https://sandbox.polar.sh` を `frame-src` に追加します（[セキュリティ](/docs/features/security)）。

### アップグレード [#upgrades]

アカウントが持つライセンスは 1 つだけで、所有者は差額を支払ってライセンスを上位のプランに移します。`LicenseCard` は、ライセンスのプランより上位の各プランについて `/app/license?tier=<tier>` にリンクします（`license.upgrades.ts` の `higherTiers`）。有効なライセンスがあり、`tier` がそれより上位のプランの場合、`/app` と `/app/license` は `UpgradeOffer`（`src/presentation/components/custom/app/upgrade-offer.tsx`）を表示します。支払う金額、その内訳、アップグレードの前と後にキーで有効化できる端末数、そして `CheckoutButton` とその下の `CheckoutNotice` です。`upgradePriceQuery`（`get-upgrade-price.ts`）は、金額を `upgradePrice`（`license.upgrade-price.ts`）から読み取ります。

- この購入者にとっての上位プランの価格。`buyerTierPrice` から求め、地域価格を含みます。
- そこからクレジットを差し引きます。クレジットは、`polar.orders.list` で一覧取得した Polar の顧客の、`DEFAULT_CURRENCY_CODE` 建ての支払い済みまたは一部返金済みのライセンス注文すべてについて、請求した価格（`subtotal_amount` から `discount_amount` を引いた額）から、`refunded_amount` と、価格が税込みだった場合はあわせて返金された `refunded_tax_amount` を引いた額です。`net_amount` では EU の価格に含まれる VAT が抜け、購入者が支払った額より少なく差し引くことになります。
- 残りが Polar の米ドルでの最低価格である `POLAR_MINIMUM_PRICE_AMOUNT`（`polar.constants.ts`）未満なら、無料になります。Polar は無料のチェックアウトは受け付けますが、それより小さい価格は受け付けないためです。

`startCheckout` は上位プランの商品に対してその金額を請求し、`metadata` にライセンスの注文とプランを記します。有効でないライセンスや、まだ Polar の注文やキーがないライセンスはアップグレードできず、購入も拒否されたままです。下位プランへの変更は、引き続きサポートを通じて行います。

アップグレードの注文が支払われると、`onOrderPaid` は `grantLicense` の代わりに `upgradeLicense`（`use-cases/upgrade-license.ts`）を呼び出します。ライセンスが `upgrade_from_order` の注文でまだ有効な間は、`polar.licenseKeys.update` でライセンスの Polar キーのアクティベーション数の上限を新しいプランの `LICENSE_ACTIVATION_LIMITS` に引き上げ、新しいプランを設定します。そのため、キー、そのアクティベーション、最初の注文とその記録はそのまま残ります。Polar はアップグレードの注文にも独自のキーを付与しますが、`onBenefitGrantCreated` がそれを Polar で無効にするため、顧客が持つキーは 1 つのままです。その間にライセンスが返金、取り消し、または置き換えられていたアップグレードの注文は、独立したライセンスとして付与されます。アップグレードの注文が全額返金されると `revertLicenseUpgrade` が呼ばれ、ライセンスがまだアップグレード後のプランである間は、以前のプランとアクティベーション数の上限に戻します。最初の注文の返金では、これまでどおりライセンスを取り消します。

### サインアップ前に選んだプラン

ランディングページの各プランのボタンは `/auth/sign-up?redirect=/app?tier=<tier>` にリンクします。戻り先のパスはサインアップ、メール認証、サインインを経ても保持され（`useAuthRedirect`）、すでにサインインしている訪問者はそのまま戻り先に移動します。`licenseSearchSchema`（`src/data/license.ts`。`searchParam` で構築）は、`/app/license` で、またライセンスのエリアが概要ページに追加するパラメーターとして `/app` で、`tier` を `LICENSE_TIER` と照合します。`/app` と `/app/license` はどちらも購入案内の上に `ChosenTier` を表示します。プラン、その地域価格、**決済に進む** ボタンが含まれ、このボタンも同じ購入を開始し、その下に `CheckoutNotice` を表示します。プランが選ばれている場合、購入案内はプランのカードを **パッケージを比較** の折りたたみ表示（`license-offer.tsx` の `ComparedTiers`）にまとめるため、目に入るのは選んだプランのボタンになります。ロックされた有料レッスンは、サインイン済みの視聴者を `/app/license?tier=complete`（Core の所有者にはそこで[アップグレード](#upgrades)が表示されます）に、ゲストをサインアップにリンクし、サインアップ後は同じページに戻ります。アカウントが必要なレッスンはサインインにリンクします（[コース](/docs/features/courses)）。

サインアップページの時点でプランが示されます。ライセンスのエリアは `src/data/license.sign-up-intros.ts` で `SignUpOrderSummary`（`custom/app/sign-up-order-summary.tsx`）を `SIGN_UP_INTROS` に追加し、`redirectTierSchema`（`src/data/license.ts`）がロケールの接頭辞の有無にかかわらず `/app` または `/app/license` への `redirect` から `LICENSE_TIER` を読み取ると、ページは説明文の代わりにこれを表示します。概要には、プラン名と `TIER_PRICES` の金額、訪問者がいま `PURCHASE_STEP` のどのステップにいるか（アカウント作成の次に Polar での支払い）、そして未使用の購入なら `REFUND_TERMS.WITHDRAWAL_DAYS` 日以内に全額返金されることが、返金ポリシーへのリンク付きで表示されます。サインアップページには地域別価格の選択肢がないため、概要には定価が表示され、訪問者が辞退していなければ決済時に地域別の割引が適用されます。`SignUpPending` は同じリダイレクトに対して `SignUpOrderSummaryPending` を描画し、それ以外の `redirect` では説明文がそのまま表示されます。

### 支払い後 [#after-payment]

支払いが終わると、購入者は `/app?checkoutId=<id>&tier=<tier>` にいます。ページに重ねて開いた Polar のチェックアウトが支払いを報告すると `CheckoutButton` がそこに移動し、オーバーレイを開けなかった場合は Polar のチェックアウトページがそこに戻します。どちらの場合も、通常は `order.paid` Webhook がライセンスを付与するより前です。`checkoutId` があり、ライセンスがまだ有効でない間、ページはプランのカードを隠して `CheckoutActivation` を表示します。このコンポーネントは <RepositoryFact name="activationPollSeconds" unit="second" />ごと（`ACTIVATION_POLL_MS`）に `currentLicenseQuery` を再取得します。

- ライセンスが有効になると購入者にお礼を表示し、`triggerConfetti`（`src/lib/confetti.ts`。動きを減らす設定の訪問者には何も描きません）でお祝いして[最初のステップ](#first-steps)を表示し、その下にライセンスが表示されます。
- <RepositoryFact name="activationTimeoutSeconds" unit="second" />
  （`ACTIVATION_TIMEOUT_MS`）たってもライセンスがない場合は再取得を止め、Polar
  がまだ支払いを確認していないことを伝えます。あわせて、サポートのメールアドレス、問い合わせ用の番号としての購入セッション
  ID、**もう一度確認** ボタンを表示します。

UUID ではない `checkoutId` は無視されます。

`tier` は、成功 URL でもオーバーレイからの遷移でも、そのチェックアウトで購入したプランを示します。アップグレードのライセンスは下位のプランですでに有効なので、`CheckoutActivation` はライセンスがそのプランになるまで（`license.upgrades.ts` の `hasReachedTier`）確認を続け、そうなって初めて購入者にお礼を表示します。表示するのはライセンスの新しいプランで、以前のプランではありません。それまでページは最初のステップも `UpgradeOffer` も表示しません。`tier` のない戻りでは、有効なライセンスを購入とみなします。

Polar のチェックアウトページは、成功 URL に `customer_session_token`（`POLAR_CUSTOMER_SESSION_TOKEN_PARAM`）を付け加えます。これは購入者の Polar のカスタマーポータルを開くトークンです。`/app` と `/app/license` は自分が宣言した検索パラメーターだけを残す（`src/lib/search-params.ts` の `onlyDeclaredSearch`）ため、サーバーはそのアドレスに対し、トークンを除いた同じアドレスへのリダイレクトで応答します。これはサインインのガードやページがトークンを目にする前に行われます。トークンがアドレスバーに残ることも、サインインの `redirect`、確認メール、ページのリクエストに入ることもなく、サイトがトークンを読むこともありません。

### 最初のステップ [#first-steps]

`GetStarted`（`src/presentation/components/custom/app/get-started.tsx`）は、アクティベーションのパネルの下と概要ページに、有効なライセンスで最初のプロジェクトに至るまでのステップを表示します。完了済みの購入、ライセンスキー、`CLI_SETUP_LINES`（`src/data/cli.ts`）のコマンド <RepositoryFact name="cliSetupCommands" /> を、それぞれコピーボタン付きで並べ、進捗バーを添えます。キーのステップはそこでキーをコピーするか有効化すると完了し、有効化のステップはライセンスに `activated_at` が入ると、プロジェクトのステップは `delivered_at` が入ると完了します（[記録と返金](#records-and-refunds)）。プロジェクトのステップは、返金ポリシーではプロジェクトの生成が最初の利用にあたることを伝えます。アドレスが確認されるまで、キーのステップはキーの代わりに確認リンクの送信先を表示します。`licenseKeySetupQuery`（`get-current-license-key.ts`）は、確認済みのアドレスのキーを発行中は <RepositoryFact name="licenseKeyPollSeconds" unit="second" />ごとに再取得します。`licenseSetupQuery`（`get-current-license.ts`）は、キーの発行中は <RepositoryFact name="licenseKeyPollSeconds" unit="second" />ごと、未完了のステップがある間は <RepositoryFact name="licenseSetupPollSeconds" unit="second" />ごとにライセンスを再取得し、すべてのステップが完了すると止まります。

## Webhook とライセンス [#webhooks-and-licences]

`src/data/license.polar-events.ts` は、`LICENSE_WEBHOOK_EVENTS`（`license.constants.ts`）に列挙されたイベントでライセンスのエリアを Polar のイベントに追加し（[決済](/docs/features/payments#webhooks)を参照）、そのうち注文のイベントには `POLAR_WEBHOOK_EVENT` の値を使います。このファイルの `handle` は、各イベントを `licenseWebhookHandlers` の同じ名前のハンドラーに渡します。`licenseWebhookHandlers` は `Record<keyof typeof LICENSE_WEBHOOK_EVENTS, unknown>` を満たすため、イベントのないハンドラーや、ハンドラーのないイベントがあるとコンパイルが通りません。`licenseWebhookHandlers`（`src/modules/license/license.webhooks.ts`）は Polar の顧客の `external_id` でユーザーを特定します。イベントには Polar がイベントを作成した時点で記録していた顧客が含まれ、再配信でも同じ内容が送られます。そのため、その `external_id` がどのアカウントも指していない場合、`onOrderPaid` と `onBenefitGrantCreated` は `polar.orders.get` で注文を読み直し、注文の現在の顧客で照合します。このアプリにアカウントがない顧客のイベントは、アカウントが必要な場合はログに記録したうえで受領し、Polar が再送しないようにします。

- `onOrderPaid` → `grantLicense`: 購入した商品のプランと、即時提供への購入者の同意（[記録と返金](#records-and-refunds)を参照）で、ユーザーの唯一のライセンスを作成または更新します。新しい購入が古い購入を置き換えます。メタデータに `upgrade_from_order` がある注文は代わりに `upgradeLicense` に渡り、アップグレード元のライセンスがもう有効でない場合にだけ付与されます（[アップグレード](#upgrades)）。続いて `sendPurchaseConfirmationEmail` が購入を確認します（[購入確認](#purchase-confirmation)を参照）。送信に失敗するとハンドラーも失敗するため、Polar がイベントを再送します。ライセンスではない商品の注文はログに記録するだけです。顧客がどのアカウントにも対応しないライセンスの注文は、ログに記録したうえで通知します（[アカウントに対応しない注文](#orders-that-match-no-account)を参照）。
- `onBenefitGrantCreated` → `attachLicenseKey`: Polar のライセンスキーをライセンスに保存します。ライセンスが元のキーを保ったアップグレードの注文では、代わりに注文自体のキーを Polar で無効にします（`POLAR_LICENSE_KEY_STATUS.DISABLED`）。支払い済みの注文がまだ記録されていない間は失敗させ、Polar に再送させます。返金済みの注文やライセンスではない商品のキーは受領します。
- `onOrderRefunded` → ステータス `refunded` で `revokeLicense`。注文が全額返金された場合のみで、一部返金ではライセンスを維持します。アップグレードの注文では、まず `revertLicenseUpgrade` が以前のプランとアクティベーション数の上限に戻します。
- `onBenefitGrantRevoked` → ステータス `revoked` で `revokeLicense`。

`revokeLicense` は、その注文で購入したライセンスのステータスを設定し、注文を `revoked_license_order` に記録して、遅れて届いた Webhook が再び付与できないようにします。`refunded` を置き換えることはありません。Polar は返金された注文の特典も取り消し、2 つのイベントはどちらの順序でも届く可能性があるためです。[CLI ライセンス API](/docs/features/cli-licence-api) は、このステータスに応じて `licenseRefunded` または `licenseRevoked` を返します。

## 記録と返金 [#records-and-refunds]

`license` 行は、現在の購入について 4 つの記録を保持します。いずれも、そのできごとが起こるまでは空のままです。

| 列                                     | 記録する内容                                                                                             | 書き込み元                                                                                                    |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `withdrawal_consent_at`                | 購入者がチェックアウトで即時提供に同意し、撤回権を失うことを了承した日時。注文が作成された時刻を使います | `order.paid` を受けた `grantLicense`                                                                          |
| `activated_at`                         | いずれかの端末でのキーの最初のアクティベーション                                                         | [CLI ライセンス API](/docs/features/cli-licence-api#records-of-use)                                           |
| `delivered_at`                         | CLI がそのキーで初めてテンプレートをダウンロードした日時                                                 | [CLI ライセンス API](/docs/features/cli-licence-api#records-of-use)                                           |
| `lesson_opened_at`、`opened_lesson_id` | ライセンスで解放される有料レッスンを購入者が初めて開いた日時と、そのレッスンの ID                        | ライセンスの[コースアクセス](/docs/features/courses#access-levels)を通じた `getLesson` と `getLessonPlayback` |

購入者は Polar のチェックアウトで必須のチェックボックスにチェックを入れて同意します（[即時提供への同意](#consent-to-immediate-supply)）。同意は注文に `custom_field_data.<slug>` として保存されます。スラッグは <RepositoryFact name="licenseWithdrawalConsentField" />（`license.constants.ts` の `LICENSE_CHECKOUT_FIELD`）です。`src/lib/polar.ts` の `WITHDRAWAL_CONSENT_FIELD` はフィールドの名前、タイプ、英語のラベルを保持し、このフィールドを必須にしていない商品がある間は `polar:verify` が失敗します（[Polar の設定](/docs/getting-started/polar-setup#consent-checkbox)を参照）。`onOrderPaid` は Zod でこのフィールドを検証し、値が `true` の場合にだけ同意を記録します。返金後の購入など、同じアカウントの新しい注文は、同意をその注文自身の同意で置き換え、`activated_at`、`delivered_at`、`lesson_opened_at`、`opened_lesson_id` を空にします。そのため、記録は常に現在の購入を表します。これらの記録が導入される前に購入されたライセンスには、その当時の記録はありません。

`refundEligibility`（`src/modules/license/license.refunds.ts`）は、購入時刻、同意、最初のダウンロード、最初の有料レッスン、現在時刻だけから結果を求める純粋関数です。期間は購入から <RepositoryFact name="refundWithdrawalDays" unit="day" />で、この数値を宣言する唯一の場所である `src/data/refunds.ts` の `REFUND_TERMS.WITHDRAWAL_DAYS` で定められています。戻り値は `REFUND_ELIGIBILITY` のいずれか 1 つの種類です。

| 種類                  | 条件                                                                                                             | 含む値          |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------- |
| `refundable`          | 期間内で、購入者が同意しており、CLI がまだテンプレートをダウンロードしておらず、有料レッスンも開かれていない場合 | `until`         |
| `statutoryWithdrawal` | 期間内で、同意が記録されていないため、使用の有無にかかわらず法定の撤回権が適用される場合                         | `until`         |
| `used`                | 期間内で、購入者が同意しており、CLI がすでにテンプレートをダウンロードしたか、有料レッスンが開かれた場合         | `usedAt`、`via` |
| `expired`             | 期間が終了した場合                                                                                               | `endedAt`       |

`used` の購入は、2 つの最初の使用のうち早い方を `usedAt` として、それがどちらだったかを `via` として持ちます。値は `FIRST_USE.TEMPLATES` または `FIRST_USE.LESSON`（`license.constants.ts`）です。管理者は、ユーザーのプロフィールで記録と、その結果を説明する文を確認できます。[ユーザー（管理）](/docs/features/users-admin#profile)を参照してください。

アカウントを削除しても、ライセンスの行は、[プライバシーポリシー](/privacy)が返金と決済の紛争のために保存する購入と提供の記録として残ります。`user_id` は `ON DELETE SET NULL` なので、キー、4つの記録、Polar の識別子はアカウントなしで残ります。Better Auth がユーザーを削除する前に、ライセンスのエリアが `src/data/license.auth-plugins.ts` で追加するデータベースフック `user.delete.before` である `revokeAccountLicense`（`src/modules/license/use-cases/revoke-account-license.ts`）が、`active` のライセンスを `revoked` にするので、そのキーは CLI で使えなくなります。`refunded` のライセンスはそのステータスのままです。このフックは、顧客がアカウントを削除したときと、管理者がユーザーを削除したときに実行されます。

## 購入確認 [#purchase-confirmation]

`grantLicense` の後、`onOrderPaid` は、同意に必要な永続的な媒体での確認を購入者に送ります。`sendPurchaseConfirmationEmail`（`src/modules/license/use-cases/send-purchase-confirmation-email.ts`）は `PurchaseConfirmationEmail`（`src/presentation/emails/purchase-confirmation-email.tsx`、名前空間 `emails.purchase-confirmation-email`）をレンダリングし、購入したアカウントのアドレスに送信します。

- **言語**: 注文の `metadata.locale` を `localeField` で検証して使います。サイトが対応する言語を持たない注文には英語を使います。
- **注文**: 請求書番号（注文にまだ請求書番号がない場合は Polar の注文 ID）、注文日、その言語の料金カードと同じ名前で示すプラン、そして注文の通貨での `total_amount` です。`total_amount` は `fromMinorUnits` で補助単位から変換します。
- **撤回権**: `custom_field_data` に同意が含まれている場合、メールは、購入者が即時提供を求め、撤回権を失うことを了承したことを改めて示し、そのためこの注文には撤回権が適用されないことを伝えます。同意がない場合、メールは、購入者が注文日から <RepositoryFact name="refundWithdrawalDays" unit="day" />以内に撤回できることを伝えます。
- **返金**: 初回使用前の全額返金の期限 `refundDeadline`（`license.refunds.ts`）です。購入時刻に `REFUND_TERMS.WITHDRAWAL_DAYS` を加えた日付で、`refundEligibility` が使うのと同じ日付です。返金ポリシーのとおり、全額返金には CLI でプロジェクトを生成しておらず、有料レッスンも開いていないことが必要です。
- **リンク**: メールの言語のライセンスページ、[CLI ガイド](/docs/cli)、利用規約、商用ライセンス、返金ポリシー、[撤回機能](#withdrawal-function)です。撤回機能へは、撤回権と返金についての文からリンクします。リンク先は Webhook を受け取ったホストです。ボタンの下には、メールクライアントがボタンを隠す読者のために、`EmailFallbackLink` がライセンスページのアドレスを書き出します。
- **はじめに**: 注文の下のブロックです。キーがあるライセンスページへのボタン、`CLI_SETUP_LINES` のコマンド <RepositoryFact name="cliSetupCommands" />、CLI ガイドへのリンクを含み、コースを利用できる購入者（`holdsCourseAccess`）にはコースへのリンク（名前空間 `purchase-email.courses`）も含みます。
- **ブランド**: 認証のメールと同じく、`EmailBrandHeader` がメールの上にサイト名を置きます。

日付は UTC で表示します。冪等性キーは `LICENSE_EMAIL_PURPOSE.PURCHASE_CONFIRMATION`（`license.constants.ts`）と Polar の注文 ID の組み合わせなので、Polar が `order.paid` を何度配信しても、Resend が送るメールは注文ごとに 1 通です。また、メールは注文だけから組み立てるため、再配信でも同じリクエストが送られます。アカウントやプランに対応しない注文には、確認メールを送りません。アカウントのないライセンスの注文については、代わりにサイト宛てにアラートを送ります（[アカウントに対応しない注文](#orders-that-match-no-account)を参照）。[トランザクションメール](/docs/features/email)を参照してください。

## アカウントに対応しない注文 [#orders-that-match-no-account]

`startCheckout` はすべての購入セッションをサインイン中のアカウントに結び付けます。そのため、注文がどのアカウントにも対応しないのは、Polar のダッシュボードで作成した購入リンクなど、`startCheckout` が作成していない購入セッションで支払われた場合か、購入セッションの開始から支払いまでの間にアカウントが削除された場合だけです。購入者は支払いを済ませているのにライセンスを持っていないため、サイトはその注文を通知し、ライセンスが付与されるまで一覧に表示します。

### アラート

`onOrderPaid` はこのような注文をログに記録し、`sendUnmatchedOrderAlert`（`src/modules/license/use-cases/send-unmatched-order-alert.ts`）に渡します。この関数は `UnmatchedOrderAlertEmail`（`src/presentation/emails/unmatched-order-alert-email.tsx`、名前空間 `emails.unmatched-order-alert-email`）を `I18N.DEFAULT_LOCALE` で、`NOTIFICATIONS_EMAIL` から `CONTACT_EMAIL` に送信します。メールには次の内容が記載されます。

- Polar の注文 ID と注文日（UTC）
- プランと、注文の通貨での `total_amount`
- イベントに含まれる顧客のメールアドレスと名前。含まれていない場合はその旨
- Polar のダッシュボードで注文を開くリンク。`polarOrderUrl`（`src/modules/license/license.utils.ts`）が、`POLAR_DASHBOARD_HOSTS` のうち `POLAR_SERVER` に対応するホスト、`POLAR_ORGANIZATION_SLUG`（どちらも `src/data/polar.ts`）、注文 ID から組み立てます
- [注文を復旧する](#recovering-an-order)手順

冪等性キーは `LICENSE_EMAIL_PURPOSE.UNMATCHED_ORDER_ALERT`（`license.constants.ts`）と Polar の注文 ID の組み合わせです。Resend はキーを 24 時間保持するため、その間に同じ注文が何度配信されても、アラートは 1 通だけ送られます。それ以降の再配信では、注文がまだどのアカウントにも対応していなければ、改めてアラートを送ります。アラートを送信できない場合はハンドラーが失敗するため、Polar がイベントを再送します。

### 管理画面の一覧

ライセンスのエリアは、`src/data/license.dashboard.ts` で `UnlicensedOrders`（`src/presentation/components/custom/admin/license/unlicensed-orders.tsx`）を[管理ダッシュボード](/docs/features/admin-dashboard)のパネルに追加し、ダッシュボードのローダーがそのクエリをプリフェッチします。`unlicensedOrdersQuery`（`src/modules/license/use-cases/get-unlicensed-orders.ts`）は `order: ["read"]` をチェックし、[Polar の注文のコピー](/docs/features/payments#orders-and-subscriptions-in-d1)のうち、次の条件をすべて満たすものを新しい順に一覧表示します。

- ステータスが `paid` であること
- `product_id` が `POLAR_PRODUCT_IDS` に含まれること
- どのライセンスの `polar_order_id` でもないこと
- `revoked_license_order` に含まれないこと

パネルは `DataGrid`（`unlicensed-order-columns.tsx` の `useUnlicensedOrderColumns`）です。各行には、Polar の注文を新しいタブで開く注文 ID、日時、Polar の顧客 ID、補助単位から変換した金額が表示され、グリッドは注文、日付、顧客、金額で絞り込めます。該当する注文がない場合、グリッドには、支払い済みのライセンス注文にはすべてライセンスがあることが表示されます。一覧には、`order.paid` の配信がまだ成功していない注文や、削除されたアカウントの注文（ライセンスもアカウントとともに削除されたもの）も含まれます。

### 注文の復旧 [#recovering-an-order]

1. 管理画面のユーザー管理で購入者のアカウントを探すか、**ユーザーを追加する** を使い、アラートに記載されたメールアドレスでアカウントを作成します（[ユーザー（管理）](/docs/features/users-admin)を参照）。アカウントの ID は、プロフィールのアドレス `/admin/users/<ID>` の最後の部分です。
2. アラートまたは管理画面の一覧から Polar で注文を開き、続いてその顧客を開きます。顧客のメニューで **Edit Customer** を選び、**External ID** にアカウントの ID を設定して **Save Customer** を選びます。API を使う場合は、`customers:write` を持つトークンで `PATCH /v1/customers/{id}` に `external_id` を送ります。Polar は外部 ID を一度設定すると保持し続け、組織内で一意であることを求めます。そのため、この方法が使えるのは、顧客に外部 ID がまだなく、アカウントに別の Polar の顧客がない場合だけです。それ以外の場合は、Polar で注文を返金し、サインインした状態でもう一度購入するよう購入者に依頼します。
3. Polar の Webhook の設定でエンドポイントの配信履歴を開き、その注文の `order.paid` イベントを見つけて **Redeliver** を選びます。続いて、`benefit_grant.created` イベントでも同じ操作をします。`onOrderPaid` がライセンスを付与してアカウントのアドレスに購入確認メールを送り、`onBenefitGrantCreated` がライセンスキーを保存します。`benefit_grant.created` が先に届いた場合は、ライセンスができるまで失敗し、Polar が再試行します。その後、注文は管理画面の一覧から消えます。

Polar がイベントを再配信できるのは、そのイベントのペイロードを保持している間だけです。Polar のサーバーはペイロードを 90 日後にアーカイブします。

## 撤回機能 [#withdrawal-function]

消費者権利指令（2011/83/EU）の第 11a 条は、指令 (EU) 2023/2673 によって追加され、2026 年 6 月 19 日から適用されます。この条は、ウェブサイトで契約を締結する事業者に、そのサイトで撤回機能を提供することを求めています。撤回機能とは、「ここで契約を撤回する」と表示され、目立つように配置され、撤回期間中いつでも利用できる操作要素で、オンラインの撤回の意思表示を開きます。消費者はそこで氏名、契約、確認の送信先となる電子アドレスを入力または確認し、「撤回を確定する」とだけ表示された操作要素で送信します。事業者はその後、意思表示の内容と送信日時を記載した受領確認を、永続的な媒体で、不当な遅滞なく送ります。期間の終了前に送信された意思表示は、期限内に権利を行使したものとなります。

### 設置場所

- `/withdrawal`（`ROUTES.WITHDRAWAL`、`_site._marketing.withdrawal.tsx`、名前空間 `pages.withdrawal`）は、サインインしていなくても使える、プリレンダリングされた公開ページです。すべてのページのフッターが **ここで契約を撤回する**（`src/data/license.navigation.ts` の `LICENSE_NAVIGATION`）としてこのページにリンクし、返金ポリシー、利用規約、購入確認メールもリンクします。
- `WithdrawalCard`（`src/presentation/components/custom/app/withdrawal-card.tsx`）は、`/app/license` の有効なライセンスの下にあります。プラン、注文番号、購入日を示し、撤回権または初回利用前の全額返金がまだ適用されるかどうか、あるいは購入がいつ、どのように初めて利用されたかを、サーバーの時刻での `refundEligibility` に基づいて伝えます。また、**ここで契約を撤回する** で、アカウントの氏名、メールアドレス、注文番号が入力済みの意思表示をダイアログで開きます。意思表示の後は、それを受領した日時を表示します。

どちらも `WithdrawalForm`（`src/presentation/components/custom/withdrawal-form.tsx`）を使います。フォームには、意思表示の文、氏名、受領確認の送信先メールアドレス、注文番号があり、`withdrawalZodSchemas.submitWithdrawal` と `withdrawal.validations` のメッセージで検証されます。送信ボタンは **撤回を確定する** です。権利がもう適用されないことを理由に、フォームが意思表示を拒むことはありません。その判断は後で行います。意思表示を受け付けると、フォームは受付内容の表示に替わります。表示するのは、意思表示、受領した日時、受領確認をメールで送信したかどうかです。

### 送信

`submitWithdrawal`（`src/modules/withdrawal/use-cases/submit-withdrawal.ts`）は `withRateLimit("submit-withdrawal", RATE_LIMITS.SENSITIVE)` を実行し（クライアントごとに 1 分あたり <RepositoryFact name="sensitiveRateLimit" /> 件の意思表示まで）、セッションがあれば読み取ります。`matchContract`（`src/modules/withdrawal/withdrawal.contracts.ts`）は、現在の注文が入力された番号を持つ有効なライセンスを探します。番号は Polar の注文 ID でも請求書番号でもよく、大文字と小文字は区別しません。サインイン中のアカウントがそのライセンスを所有している場合、または入力されたメールアドレスがそのアカウントのものである場合、意思表示はそのライセンスに属します。続いて `recordWithdrawal`（`record-withdrawal.ts`、サーバー専用）が次の処理を行います。

1. 意思表示を、一致したライセンスのその時点の返金条件、または `unmatched` とともに `withdrawal` テーブルに保存します。
2. `WithdrawalAcknowledgementEmail`（名前空間 `emails.withdrawal-acknowledgement-email`）を、入力されたアドレスにページの言語で送ります。内容は意思表示、氏名、注文番号、アドレス、送信日時で、送信はアドレスあたり 1 時間に <RepositoryFact name="recipientEmailsPerHour" /> 通までです。Resend が受け付けた日時を `acknowledged_at` に記録します。
3. `WithdrawalNotificationEmail`（名前空間 `emails.withdrawal-notification-email`）を `I18N.DEFAULT_LOCALE` で、`NOTIFICATIONS_EMAIL` から `CONTACT_EMAIL` に送ります。内容は意思表示、購入者の特定方法、ライセンス、返金条件、受領確認を送信したかどうか、返金の期限（受領から <RepositoryFact name="refundReimbursementDays" unit="day" />後、`REFUND_TERMS.REIMBURSEMENT_DAYS`）、管理画面のアカウントと Polar の注文へのリンクです。

送信できなかったメールはログに記録され、意思表示はそのまま残ります。その場合、受付内容の表示は受領確認がこれから届くことを伝え、通知には受領確認が送信されていないことが記載されます。冪等性キーは `WITHDRAWAL_EMAIL_PURPOSE`（`withdrawal.constants.ts`）の `WITHDRAWAL_ACKNOWLEDGEMENT` と `WITHDRAWAL_NOTIFICATION` と撤回の ID の組み合わせです。

自動的に返金や取り消しが行われることはなく、返金するかどうかはオーナーが判断します。撤回を受け入れるには、Polar で注文を返金します。すると `order.refunded` がライセンスを返金済みにし、そのキーを取り消します（[Webhook とライセンス](#webhooks-and-licences)を参照）。そのうえで購入者に返信してください。

### withdrawal テーブル

| 列                                        | 保持する内容                                                                                                                                                                |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                      | UUID v7                                                                                                                                                                     |
| `name`、`email`、`reference`              | 購入者が入力したとおりの氏名、受領確認の送信先メールアドレス、注文番号                                                                                                      |
| `locale`                                  | ページの言語。受領確認はこの言語を使います                                                                                                                                  |
| `channel`                                 | 購入者がサインインしていた場合は `account`、そうでない場合は `public`（`WITHDRAWAL_CHANNEL`）                                                                               |
| `user_id`、`license_id`、`polar_order_id` | 一致したアカウント、ライセンス、Polar の注文。一致しない場合は、サインインしていた購入者のアカウント。`ON DELETE SET NULL` により、いずれかが削除されても意思表示は残ります |
| `eligibility`                             | 意思表示が届いた時点の返金条件。`REFUND_ELIGIBILITY` の種類のいずれか、または `unmatched`（`WITHDRAWAL_ELIGIBILITY`）                                                       |
| `acknowledged_at`                         | Resend が受領確認を受け付けた日時。受領確認が未送信の間は空です                                                                                                             |
| `created_at`                              | 意思表示を受領した日時。受領確認に記載される日時です                                                                                                                        |

管理画面のユーザープロフィールには、アカウントの意思表示が新しい順に表示されます。[ユーザー（管理）](/docs/features/users-admin#profile)を参照してください。

## 顧客向け画面

`/app/license` は `LicenseCard` を表示します。有効なライセンスでは、プラン、キー、`CLI_KEY_LINES` のコマンド（キーの有効化、プロジェクトの生成、端末の表示と解放）をそれぞれコピーボタン付きで、キーの発行中は `licenseKeySetupQuery` がキーの到着時にキーと置き換える行を、さらに `/api/auth/customer/portal` の Polar カスタマーポータルへのリンク、上位の各プランへの **…にアップグレード** リンク（[アップグレード](#upgrades)）、下位プランへの変更の連絡先となるサポートのメールアドレスを表示します。キーとポータルはアドレスが確認されるまで表示されません（[メール確認](/docs/features/email-verification#what-waits-for-the-confirmed-address)を参照）。返金済みまたは取り消されたライセンスでは、キー、コマンド、端末を表示せず、ステータス、その下の購入案内へのリンク、サポートへのリンクを表示します。キーのある有効なライセンスの下には `LicenseActivations` を表示します。`LicenseActivations` は Polar 上のキーのアクティベーションを一覧表示し、`deactivateLicense` で個別に解除します。Polar がそのアクティベーションをもう保持していない場合、`deactivateLicense` は `NOT_FOUND` を返します。CLI は [CLI ライセンス API](/docs/features/cli-licence-api) を通じてアクティベーションを追加、削除します。Polar は各プランのライセンスキーの特典に設定されたアクティベーション数の上限を強制します。この上限は `LICENSE_ACTIVATION_LIMITS` と一致している必要があり、Core は <ActivationLimit tier="core" />、Complete は <ActivationLimit tier="complete" />、Agency は <ActivationLimit tier="agency" /> です。[顧客アプリ](/docs/features/customer-app)を参照してください。
