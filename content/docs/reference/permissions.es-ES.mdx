Cada área define sus declaraciones de permisos y los roles a los que las concede en `src/areas/<area>.access.ts`, y `src/integrations/better-auth/auth.access.ts` construye a partir de ellas el control de acceso de Better Auth y los roles (consulta [Roles y permisos](/docs/guides/roles-and-permissions)). Las mismas definiciones las usan el servidor (`authorized`, los guards de ruta) y el cliente de Better Auth.

## Roles

| Rol           | Código     | Permisos                                                                                                                                                                                 |
| ------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Administrador | `admin`    | Todas las declaraciones de la aplicación que aparecen abajo, que cada área concede a los administradores, más las declaraciones de administración de Better Auth para `user` y `session` |
| Cliente       | `customer` | Ninguno. Los clientes pueden llamar a las funciones de servidor que solo exigen una sesión.                                                                                              |

Los usuarios nuevos reciben `customer` (`DEFAULT_ROLE_CODE` en `auth.roles.ts`).

## Comprobar un permiso

Las funciones de servidor usan el middleware, por ejemplo `authorized({ category: ["read"] })`. El resto del código llama a `hasPermission`, como hacen los guards de ruta:

```ts
const isAdmin = (role: string | null | undefined): boolean => hasPermission({ permission: { admin: ["access"] }, role })

export const requireAdmin = async (context: ProtectedRouteContext) => {
  const result = await requireSignedIn(context)
  if (!isAdmin(result.session.user.role)) {
    throw redirect({ replace: true, to: ROUTES.APP })
  }
  return result
}
```
