Each rule on this page came from a measurement, and several replaced an intuitive fix that made things worse. Change the code behind one of them only with a new measurement that beats it.

## Measure before you claim

- Compare the previous build and the new build on the same page, at least five Lighthouse runs each, interleaved, and compare medians. One run proves nothing: about one run in five is an outlier from machine noise.
- Do not judge a change on one PageSpeed Insights run. The same deployment scores very differently depending on the speed of the machine that runs the test, which Lighthouse reports as `benchmarkIndex`.
- Measure a production build (`bun run build:test`, then `bun run start:test`) served over HTTP/2 with compression. Over plain local HTTP/1.1 without compression, Lighthouse's network simulation models connections and transfer sizes that production never has.
- A Lighthouse diagnostic is not a score. A "forced reflow" or "properly size images" hint can be wrong for the page, as the sections below show; check the scored metrics before acting on it.

## Keep the Worker's boot graph small

`src/server.ts` runs for every HTML request (`run_worker_first` in `wrangler.jsonc`), and everything it imports statically is evaluated on every cold start. It and the Worker handlers that the features add import only constants and pure helpers, and load the rest when a request needs it:

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

One static import of a header name from a module that also imported the Polar client once pulled about 1.4 MB of SDK into every cold start, and the first byte of the landing page took up to 1.4 seconds. That is why `COUNTRY_HEADER` and `IP_ADDRESS_HEADER` live in `src/modules/_core/constants/api.ts`, which imports nothing heavy. Before adding a static import to `server.ts` or to a module it imports, follow its import chain: anything that reaches `polar`, `drizzle-orm` or `resend` is a regression. `scripts/verify-build.ts` checks it on every build: it follows the static imports of the deployed Worker's entry, `dist/server/index.js`, and fails when they reach code bundled from `@polar-sh`, `drizzle-orm` or `resend`, or add up to more than `BOOT_CLOSURE_MAX_BYTES`. The paths are part of that closure, so `src/routes.ts` declares them and imports nothing.

## Keep the route tree light

The Worker hands every request that is neither a prerendered page nor a static file to TanStack Start, and Start loads the route tree before it does anything else, for a server function call as much as for a page it renders: `src/routeTree.gen.ts` and every module the route files import statically, including the handlers of server routes such as `/api/auth/$`. A Worker isolate evaluates it on its first such request, and a server function loads its own chunk on its first call. Both happen while a visitor waits for a client navigation, so everything they import is part of the wait on a new isolate.

The docs and blog collections used to be eager: `.source/server.ts` imported the compiled MDX of every docs page and blog post in every locale, 1,305 modules with each page's headings and search text, and the Lucide icons plugin added the whole icon set for the few icons the docs meta files name. The docs layout, the docs pages, the landing page and the blog read that source through their server functions, and `/api/search` imported it statically, which put it in the route tree. On saasyland.com, a client navigation from `/` to `/docs` waited about 1.3 seconds for its two server functions on a new isolate, and about 25 ms on a warm one; the landing page and the blog paid the same on their first navigation.

The collections became `async`, so the source kept each page's frontmatter and imported a page's compiled MDX only when a request needed its headings or search text, and `/api/search` imported its index in its handler. The next section took the content out of the Worker altogether. `fumadocs.icons.ts` imports only the icons the meta files name, and `fumadocs.icons.test.ts` fails when a meta file names an icon it does not import or it imports one that no meta file names.

The sizes are what each part imports statically in the `bun run build:test` Worker, and the times are the median of five interleaved runs on a laptop:

## The Worker holds no docs or blog content

After the change above, the Worker still bundled the docs and blog: the compiled MDX of 1,305 pages, about 14.6 MiB of a 27.5 MiB upload, kept for `/api/search`, for the tables of contents and reading times of blog posts, and beside the frontmatter that the server functions of the docs, the blog and the landing page read. A request on a new isolate waited 1 to 2 seconds before any code ran, a client navigation through the docs on saasyland.com took 1.3 to 2.0 seconds on a new isolate and about 270 ms on a warm one, and a docs search took 9 to 18 seconds.

Every build now turns the content into data the app imports as static files. `scripts/content-indexes.ts`, a Vite plugin, loads `fumadocs.indexes.ts` with Vite's module runner, which reads `content/docs` and `content/blog` with the collection schemas and Fumadocs' `loader` and builds, for each locale:

- the docs index: the page tree, and the pages by slug with their title, description, section and MDX file;
- the blog index: the published posts, newest first, with their frontmatter, table of contents and reading time;
- the search index: Fumadocs' exported search database of the docs pages, which the build writes to `/assets/search-index-<locale>-<hash>.json`.

`loadDocsIndex` and `loadBlogIndex` from `virtual:content-indexes` import a locale's docs or blog index, a chunk of its own under `/assets/`. The docs layout and pages, the blog, its posts and the landing page read them in their loaders, which run in the browser on a client navigation and on the server while prerendering, and a page's compiled MDX comes from its browser chunk as before. `run_worker_first` leaves `/assets/*` to Cloudflare's static assets, so a client navigation through the docs or the blog requests no Worker at all. The docs search downloads its locale's index on the first query and searches it in the browser (see [Docs site](/docs/features/docs-site#search)); `/api/search` is gone.

The deployed Worker serves every docs page and blog post prerendered, so `scripts/deployed-worker.ts` resolves every import of a compiled page to one module that throws, and the build compiles none of them. `scripts/verify-build.ts` fails the build when any file of the deployed Worker holds a docs or blog module, when a locale has no search index, or when a locale's index does not hold exactly that locale's docs pages under their titles.

## A slow navigation shows its skeleton at once

`src/router.tsx` sets `defaultPendingMs` to <RepositoryFact name="navigationPendingMs" unit="millisecond" /> and `defaultPendingMinMs` to <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, from `src/data/navigation.constants.ts`. With TanStack Router's defaults, one second and half a second, a slow navigation showed nothing but a new address for a full second: a first click on **Docs** on a new isolate took about 1.6 seconds and showed the docs skeleton only after one second or not at all, and a click from one docs page to another, whose routes had `pendingMs: Number.POSITIVE_INFINITY`, kept the previous page for the whole wait.

- A navigation that finishes within the delay keeps the previous page until the next one is ready and never shows a skeleton. On saasyland.com, a navigation to a page the router had preloaded on hover or already loaded finished 40 to 115 ms after the click. A first visit to a section on a warm Worker, measured locally with 40 ms of latency per request and without hovering the link, took 184 to 314 ms; the delay is above both, so neither shows a skeleton.
- A navigation that is still loading after the delay shows its route's skeleton for exactly as long as it keeps loading: `defaultPendingMinMs` is <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, so the router removes the skeleton the moment the page is ready instead of holding it on screen.
- The docs pages have skeletons of their own, `DocsIndexPending` and `DocsPagePending`, which fill the article and table of contents beside the sidebar, so a slow navigation between docs pages shows the shape of the next page instead of leaving the previous one in place.

`e2e/specs/content.spec.ts` holds the docs index of a navigation to `/docs` and the compiled MDX of one between docs pages and checks that each shows its skeleton, and the sidebar in the second, until they arrive. These tests turn on data saver first, so the header does not load the docs before the click.

## Request-rendered pages stream their slow sections

The admin console, the workspace and the course pages render on the Worker for each request. Their loaders used to await every query, so nothing left the Worker until the slowest one had answered; on `/admin` and `/admin/products` that was Polar's product catalogue, a call to Polar's API on every view. Each loader now awaits only what the first flush needs and starts the rest without awaiting it, and each slow section streams into its skeleton in the same response ([Streamed sections](/docs/conventions/routes#streamed-sections)):

- `/admin` awaits the newest accounts, which its `DataGrid` reads with `useQuery`. Each statistic and each panel streams in its own boundary, so only the product count waits for Polar.
- `/admin/products` streams its grid.
- `/app/billing` streams its orders and subscriptions, and the button to Polar's customer portal, which depends on them.
- A lesson streams its player: once the loader knows the lesson can be played, it starts signing the stream without waiting for it, so the title, the text and the contents leave the Worker before the signed stream exists, and the player fills its skeleton.

Measured on `bun run build:test` builds served by `bun run start:test`, with a browser's user agent and signed in by cookie, in 3 interleaved rounds of 10 requests per page and build. The test build answers Polar from an in-memory double; for these runs it waited 300 ms before each answer, to stand in for the round trip to Polar's API. D1 is local in the test build. The first byte is the time until the response's headers arrive, which TanStack Start sends with the first part of the page; each cell is the median of the three rounds' medians:

| Page              | First byte before | First byte after | Whole page before | Whole page after |
| ----------------- | ----------------- | ---------------- | ----------------- | ---------------- |
| `/admin`          | 403 ms            | 83 ms            | 419 ms            | 327 ms           |
| `/admin/products` | 361 ms            | 43 ms            | 370 ms            | 367 ms           |
| `/app/billing`    | 30 ms             | 28 ms            | 36 ms             | 35 ms            |
| A lesson          | 38 ms             | 35 ms            | 45 ms             | 44 ms            |

`/app/billing` and the lesson read only D1, which is local here, so these runs show no difference for them; on Cloudflare, their first byte no longer waits for the queries that now stream. Without the delay, every page took the same time before and after, within the spread of the runs. The fully loaded pages are identical, pixel for pixel, at 1440 and 390 pixels wide in English and German, and each skeleton takes the size of the section that replaces it.

A crawler gets the whole page in its first response, with every section in place: TanStack Start waits for every section before it answers a request whose user agent `isbot` recognises, and the router-core patch keeps the router from reading React's stream before then ([Dependencies](/docs/conventions/dependencies)). `isbot` also counts `curl` and the `fetch` of Bun and Node as crawlers, so a script that measures streaming has to send a browser's user agent.

`src/routes/__test__/admin-products-loaders.test.ts` checks that `/admin` and `/admin/products` render while the Polar catalogue is still loading, and `app-billing-routes.component.test.tsx` and `lesson-routes.component.test.tsx` that the billing history and the player hold their skeletons while their data streams.

## The header's pages load before a click

`defaultPreload: "intent"` loads the code and data of a link only once the pointer has rested on it for `defaultPreloadDelay`, <RepositoryFact name="navigationPreloadDelayMs" unit="millisecond" /> (`NAVIGATION_PRELOAD_DELAY_MS` in `src/data/navigation.constants.ts`), which a quick click, a tap on a phone and a keyboard never give it. After the route tree was made lighter, a client navigation from `/` to the heading of `/docs` on saasyland.com took 255 to 283 ms on a warm Worker isolate and 1.3 to 2.0 seconds on a new one, because the two docs server functions waited 1.1 to 2.0 seconds for the isolate to start.

`Navigation` therefore preloads the page of every `HEADER_NAVIGATION` entry through TanStack Router once the page on screen is idle, so a new isolate starts before the click and the click finds the page's code and data in the router's cache. It calls `router.preloadRoute` for each entry in an effect and schedules the calls with `preloadWhenIdle`:

```ts title="src/lib/idle-preload.ts"
const schedule = (preload: () => void, signal: AbortSignal): void => {
  if (dataSaverSchema.safeParse(navigator).success) {
    return
  }
  if (document.readyState === "complete") {
    whenIdle(preload, signal)
    return
  }
  globalThis.addEventListener(
    "load",
    () => {
      whenIdle(preload, signal)
    },
    { once: true, signal },
  )
}
```

- `preloadWhenIdle` (`src/lib/idle-preload.ts`) waits for the `load` event and then for `requestIdleCallback`, so the preloads never compete with the page's own requests, its Largest Contentful Paint or its hydration. Safari has no `requestIdleCallback`, so there it waits <RepositoryFact name="idleFallbackDelayMs" unit="millisecond" /> after `load`. It returns the function that cancels the wait, which the effect calls when the header unmounts or the page changes first.
- It preloads nothing for a visitor who has turned on data saver (`navigator.connection.saveData`).
- The effect depends on `shownPath`, the path of the page on screen from the router's `resolvedLocation`, so the header preloads again once the next page is idle and keeps its pages fresh while someone browses. A page whose data is still fresh is not loaded again. The page a visit starts on was rendered at build time, so the router counts its data as stale and loads it again the first time the header preloads it from another page.
- TanStack Router's `preload="viewport"` on the header's links would start as soon as a link is in the viewport, which the fixed header always is, so it would compete with hydration; and on a phone the links sit in the menu, which renders them only when it opens.
- Only the header's links preload this way. Every other link, such as the hundreds in the docs sidebar, keeps `defaultPreload: "intent"`.
- Once the session points the account link at the visitor's workspace, `/admin` or `/app`, that entry loads only its code, with `router.loadRouteChunk` for each route it matches. Preloading the page ran the workspace's guard and its loader: for an admin, the whole dashboard, Polar's catalogue included, on every page they viewed. An entry whose page is the one `HEADER_NAVIGATION` declares, **Sign in** included, still loads its data. Measured on a `bun run build:test` build, the server function requests a signed-in page made by the time it was idle fell from 12 to 2 on `/` for an admin and from 4 to 2 for a customer.

`src/router.tsx` sets `defaultPreloadStaleTime` to <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />, the value TanStack Router's guide to TanStack Query gives, and leaves `defaultStaleTime` at the router's default, so TanStack Query alone decides what is fresh: a click after a preload runs the page's loaders again, and they read what the preload put in the query cache. The router used to keep preloaded pages for the query stale time, because the docs and blog loaders called server functions outside TanStack Query; they now import the build-time indexes, which the browser keeps once it has loaded them, so that is no longer needed. On a `bun run build:test` build, hovering a link and then clicking it made the same server function calls with either setting, for the course, blog, docs and admin console pages alike: one or two on the first hover, depending on the page's queries, and none on a second hover, on the click or on the way back.

Measured on preview.saasyland.com with a fresh browser per run, each loading `/`, waiting until the network was quiet and two seconds more, then clicking **Docs**. Cloudflare spreads the requests of one browser over several isolates, so most runs before the change met a new one. Each cell gives the median and, in brackets, the range:

## Loaders stay in their route's chunk

`vite.config.ts` splits each route's loader into a chunk of its own, with its component, error component and not-found component, while TanStack Router's default keeps the loader in the route tree. Keeping it there makes a navigation that nothing preloaded, a tap or a click with no rest on the link, one round trip faster, but it puts every loader and what it imports in the entry script. Measured on `bun run build:test` builds, in Chromium with data saver on and 150 ms of added latency per request, in interleaved rounds of 4 clicks per build, 8 to 12 clicks per cell, with the size of every script each page loads, gzipped:

| Measure                                         | Loaders split | Loaders in the route tree |
| ----------------------------------------------- | ------------- | ------------------------- |
| JavaScript on `/`                               | 530.5 KiB     | 644.5 KiB                 |
| JavaScript on `/admin`                          | 644.6 KiB     | 762.5 KiB                 |
| Click from `/` to `/courses`, nothing preloaded | 649 ms        | 508 ms                    |
| Click in the admin sidebar, nothing preloaded   | 515 ms        | 355 ms                    |

Every page would load about 115 KiB more to save one round trip on the clicks that preloading misses, and the header's pages are preloaded already, so the loaders stay split.

## Guards reuse the cached session

TanStack Router runs a layout's `beforeLoad` on every navigation below it and starts the loaders only once it has finished. `requireSignedIn` and `requireAdmin` used to read `getCurrentSessionQuery` with `staleTime: 0`, so every click in `/app` and `/admin`, even back to a page already open, waited for a session request before the page's own requests could start. On saasyland.com that request took 60 to 70 ms of each 190 to 300 ms click in the admin sidebar.

The guards now read the session with its own stale time, `SESSION_STALE_TIME_MS` (<RepositoryFact name="sessionStaleTimeMinutes" unit="minute" />): a fresh session lets the navigation through without a request, and a stale one is fetched again before the page loads. Guards only decide what the visitor sees; every server function still checks the session of its own request (see [Authentication and security](/docs/architecture/security-model)). So that an ended session is still noticed at once, `getRouter` gives its `QueryCache` and `MutationCache` one `onError`, which passes every failure to each handler in `QUERY_ERROR_HANDLERS`; the auth feature's `recheckRefusedSession` is the only one. When a server function answers `UNAUTHORIZED` or `FORBIDDEN`, `recheckRefusedSession` fetches the session into a cache entry of its own; if the user or the role changed, it marks the cached session stale and runs the guards again with `router.invalidate()`, which sends the visitor to sign-in with the notice that the session ended, or a former admin to `/app`. An unchanged session leaves the page alone, so a refusal can never loop.

Measured on a `bun run build:test` build served by `bun run start:test`, in Chromium with 40 ms of added latency per request, signed in as the seeded admin, in 2 interleaved rounds of 5 runs per build. Each run opened `/admin` and then every sidebar entry twice, the pointer resting on the entry for 250 ms before the press; a click is timed from the press to the first frame after the router rendered the page. Each cell gives the median over every entry and, in brackets, the range:

| Measure                                           | Before                       | After                           |
| ------------------------------------------------- | ---------------------------- | ------------------------------- |
| From the press to the page, first visit           | 209 ms (83–1,206)            | 156 ms (41–647)                 |
| From the press to the page, return visit          | 68 ms (49–406)               | 18 ms (11–56)                   |
| Session requests per click                        | 1, 2 for **User Management** | none while the session is fresh |
| Server function requests a return visit waits for | 1–2                          | 0                               |

`e2e/specs/admin-navigation.spec.ts` checks that every console page opens a second time without a request, and that a session ended elsewhere leads to sign-in at the first server function that refuses it.

## The header knows the session before its scripts

Every public page is prerendered, so its HTML cannot know who is reading it. The header's **Sign in** link used to turn into **Your account** only after the page had loaded its scripts, hydrated and asked for the session, and the wider label then pushed **Pricing**, **Courses**, **Blog** and **Docs** sideways. A browser that had ever signed in asked for the session on every page view, because the gate was Better Auth's last-used sign-in method cookie, which outlives sign-out.

The Worker now decides the label before the HTML leaves it. `markSession` sets `data-session` on `<html>` when the request carries the session cookie; it reads only the cookie's presence, never the database. The link holds both labels and CSS displays only the one the mark selects, so the link is as wide as the label it shows and sits as far from its neighbours as every other header link. The session request runs only on a marked page, and a cookie whose session has ended is cleared by that first request, so the next page is unmarked (see [Paths and navigation](/docs/conventions/routes#paths-and-navigation) and [Caching and SSR](/docs/architecture/caching-and-ssr#prerendering)). In #405, the pull request that made this change, the Worker's cold start grew by 702 bytes, to 38,292.

Measured on `bun run build:test` builds served by `vp preview` on one machine, in Chromium at 1440 by 900 with data saver on, so that only the session request reaches a server function. The two builds ran in 2 interleaved rounds of 2 runs on `/`, `/docs` and `/blog` each, 12 page views per cell. A label is correct from the first frame that shows the header with the right text; the median comes first and the range in brackets:

| Measure                                                    | Before                    | After                             |
| ---------------------------------------------------------- | ------------------------- | --------------------------------- |
| Signed in: label correct, normal CPU                       | 684 ms (438–2,863)        | 69 ms (52–101), the first frame   |
| Signed in: label correct, CPU slowed 4 times               | 1,206 ms (1,021–1,753)    | 162 ms (114–391), the first frame |
| Signed in: header links that move                          | 4 in every page view      | none                              |
| Signed in: layout shift                                    | 0.0004 in every page view | 0                                 |
| Session requests per page view, signed out after a sign-in | 1                         | 0                                 |
| Session requests per page view, signed in                  | 1                         | 1                                 |
| Session requests per page view, session ended elsewhere    | 1 on every page view      | 1 on the first, then 0            |

A browser whose session ended elsewhere now sees **Your account** until the check answers, 405 ms (292–611) at normal speed, and then **Sign in**: the label tells the truth as soon as it is known, and the links before it move once, on that one page view, by the difference between the widths of the two labels. Lighthouse 13 on `/`, behind an HTTP/2 proxy with Brotli, desktop preset at 7 times CPU slowdown, 4 runs per cell, medians, the 2 runs of a load spike left out: with the session cookie, First Contentful Paint 453 ms before and 403 ms after, Largest Contentful Paint 871 and 867 ms, Total Blocking Time 218 and 226 ms, Cumulative Layout Shift 0 in both; without it, and on the mobile preset, every metric stayed within the spread of the runs.

`e2e/specs/header-session.spec.ts` checks, in Chromium and WebKit, that a page shows the right label before any script runs, that no header link moves while a signed-out or a signed-in page loads and that the account link sits as far from its neighbours as the other links, in English and in Polish, that a signed-out browser asks for no session, that an ended session turns the label back to **Sign in**, laid out as on any signed-out page, and asks no more, and that a press on **Your account** lands on the workspace, before the scripts run or while the session loads.

## React Aria links preload like router links

`defaultPreload: "intent"` belongs to TanStack Router's `<Link>`. The sidebars, `LinkButton` and the other link buttons were React Aria `Link`s that navigate through React Aria's `RouterProvider`, so resting the pointer on them loaded nothing and a click waited for the page's code and server functions. `LinkButton` is now `createLink(AnchorButton)` and `SidebarMenuLink` is `createLink(SidebarMenuButton)`, which TanStack Router documents for React Aria Components: they take `to`, with `params` and `search`, and preload on intent, on focus and on touch like `<Link>`. `AnchorButton` stays for addresses outside the route tree. `TabsLink`, the tabs of `/admin/users`, calls `router.preloadRoute` when the pointer rests on a tab or it takes focus, and a result of `AdminCommandPalette` does the same when the pointer rests on it.

| ---------------------------------------- | --------------- | ------------- |
| From the press to the page, first visit  | 128 ms (38–270) | 34 ms (16–91) |
| From the press to the page, return visit | 16 ms (14–34)   | 16 ms (9–33)  |

## Keep the ORM out of the browser

Drizzle runs only in the Worker. The browser needs a module's Zod schemas for its forms and its enum tuples for its selects, so both live in files that import nothing from Drizzle: `<table>.zod.ts` and `<table>.constants.ts` (see [Modules](/docs/conventions/modules)). A browser import that reaches a `<table>.schema.ts` runs `sqliteTable(...)`, a call the bundler has to keep, and brings `drizzle-orm` with it.

`<table>.zod.ts` once also built `insert`, `select` and `update` schemas from the tables with `drizzle-zod`, and nothing read them at runtime. `drizzle-zod` holds on to the whole zod namespace, so the bundler also kept every zod locale, its JSON Schema converter and its compiler. The `/admin` and `/app` pending skeletons imported `PreferencesCardPending` from `preferences-card.tsx`, which imported `user.zod.ts`, and pending components are not code-split, so all of it loaded on every page. Moving the tuples to the constants and deleting those schemas took about 75 KiB of gzipped JavaScript off every page. ```ts title="vite.config.ts"


A build in which an import of it survives tree-shaking fails and prints the chain of imports from the route to the file that reached Drizzle. Break the chain where it starts: import the tuple from the module's constants, or move the code into a server function. Type-only imports are erased and never count.

## Load messages when a page needs them

The first page a visitor opens loads no message file in the browser: the root route and the matched routes preload their namespaces into the query cache on the server, and TanStack Start sends that cache with the HTML. The browser loads a namespace only when a later navigation needs one that the cache does not hold yet.

`import.meta.glob` gives every message file a chunk of its own, but the map from each file to its chunk, which names every namespace in every locale, ships in the module that calls the glob. That module was `i18n.messages.ts`, which the root route imports, and it held the map twice, once for the messages and once for the page metadata, so every page loaded about 240 KiB of loaders, 21 KiB gzipped. The map now lives on its own in `i18n.loaders.ts`, and `loadNamespace` imports it the first time it loads a namespace:

```ts title="src/integrations/use-intl/i18n.messages.ts"
const { MESSAGE_LOADERS } = await import("~/src/integrations/use-intl/i18n.loaders")
```

`loadPageMetadata` reads `metadata` from the page's namespace instead of from a second map, so a page's head and its messages come from one chunk. The browser fetches `i18n.loaders.ts`, about 11 KiB gzipped, with the first namespace it loads, on a navigation or on the hover that preloads one. The root namespaces are still found by file name in `i18n.messages.ts`, and that glob's keys cost about 2 KiB gzipped. Every script each page loads, gzipped, from the `bun run build:test` output:

## Repository tables load with the docs

`REPOSITORY_FACTS` (`src/lib/repository-facts.ts`) is in every page's entry script, because the landing page prints its counts. The `repositoryFacts` plugin used to serve those counts and every table the docs print with `<RepositoryTable>`, such as the endpoints of the CLI licence API, the seeded accounts and the user flows, as one module, `virtual:repository-facts`. Rolldown puts a whole module into one chunk, so every page loaded the tables too. The plugin now serves the counts as `virtual:repository-facts` and the tables as `virtual:repository-tables`, which only `repository-fact.tsx`, the MDX components of the docs, imports. `scripts/verify-build.ts` fails the build when the static imports of the browser's entry script reach them. That took 25.7 KiB gzipped out of the entry script, but Lighthouse measured no change on `/`, because the header preloads the docs' code once the page is idle (see [The header's pages load before a click](#the-headers-pages-load-before-a-click)).

That preload is where the cost was. `repository-fact.tsx` printed the Polish terms that the glossary check leaves to the reader from `POLISH_GLOSSARY` in `src/lib/glossary-terms.ts`, which compiles a pattern for every term of both glossaries when it loads and searches every preferred term with each. Every page ran that when the header preloaded the docs: under Lighthouse's mobile throttling it was one task of about two seconds right after the page loaded. The plugin now builds the glossary tables and those terms when a build first imports `virtual:repository-tables`, so no browser loads `glossary-terms.ts`. The plugin runs before Vite resolves the `~` alias, so `glossary-terms.ts` imports the glossaries by relative path, as `src/lib/prerender.ts` imports `src/routes.ts`.

Three other ways to make the landing page lighter were measured and left out:

- **Fewer chunks.** The landing page loads 277 scripts, 216 of them under 2 KiB, because Rolldown gives each set of modules that the entry script shares with the lazy routes a chunk of its own. A chunk group for every module that the entry script imports statically cut the entry's files from 161 to 3, but a module's static imports name every module that a barrel file re-exports, used or not, so the entry grew from 415.3 KiB to 509.8 KiB gzipped, and the median Largest Contentful Paint went from 2,101 ms to 2,586 ms. A group that sorts modules by the routes that use them (`entriesAware`) and merges the sets under 16 KiB left 87 files and 1,023.9 KiB gzipped.
- **An SVG sprite.** The 122 icons inlined in the HTML are 52 KB of it, but only 1.8 KB with brotli, because they repeat. A sprite would save at most that and add a request.
- **Fewer messages in the HTML.** TanStack Start hands the query cache to the browser in a script of 93 KB, 14.1 KB with brotli. It holds the page's own locale only: the namespaces that the root route and the landing page load, which hydration needs, and the GitHub star count. The landing page does not render every root namespace, but every component reads its own namespace on any page (see [Translations and content](/docs/conventions/translations)), so loading fewer would change that convention.

## Prerendered pages load CSS and fonts first

Public pages are prerendered and need no JavaScript for their first paint. TanStack Start emits a `modulepreload` hint for every chunk a page may need, more than a hundred on the landing page, and under a simulated mobile network they compete with the stylesheet and fonts. `scripts/optimize-prerendered-html.ts`, which every build script runs, removes every dependency hint and keeps only the page's own entry script hint, at `fetchpriority="low"`:

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

Removing the hints cut First Contentful Paint by about a third; keeping the entry hint at low priority cut mobile First Contentful Paint by another 375 ms. Never add preload hints back, for dependencies or for route chunks. The script fails the build when it finds no hint to strip or none to keep, so a change in the build output is caught rather than silently undoing this.

TanStack Start now emits every hint with `fetchpriority="low"`, so the rule was measured again in November 2026 on the landing page, five interleaved runs per variant. Keeping all 156 hints let the browser fetch the page's chunks in one wave instead of eleven and hydrated the CLI configurator 250 ms sooner on desktop and 315 ms sooner on a throttled phone, but First Contentful Paint came 68 ms later on desktop and 77 ms later on mobile. The hints stay stripped.

The script policy keeps this order. The Worker streams every prerendered page through `withNonce`, an `HTMLRewriter` that adds the response's nonce to the entry's `<script type="module">` and to its hint and changes nothing else, so the hint in the head still starts the download at low priority and the module still runs when the parser reaches the end of the body. The rewrite streams, so it holds back no byte, but HTML responses carry no `ETag`, so a browser downloads a page again instead of revalidating it.

`robots.txt` and `llms.txt` are static files in `public/` that bypass the Worker (`"!/robots.txt", "!/llms.txt"` in `run_worker_first`). Lighthouse fetches both with a two-second timeout, and a slow Worker response failed its SEO and agent-readiness audits.

## Early Hints name only files that outlive a deploy

The Worker's `Link` header on HTML responses names the locale's fonts and nothing else. Cloudflare stores the header per URL and sends it as a `103 Early Hints` response before the Worker answers the next request for that URL, and the stored copy survives a deploy. Vite names the stylesheet after its content, so after a deploy that changes any CSS, a hinted stylesheet is a file that no longer exists: the browser downloads a 404 and finds the new stylesheet in the HTML anyway. The files in `public/fonts` keep their names from one deploy to the next.

Measured on saasyland.com with Chromium, 15 interleaved runs per variant on three pages, with the edge's own Early Hints timing: hinting the fonts brought First Contentful Paint from 168–208 ms down to 144–164 ms. A stylesheet hint saved another 12–28 ms when its URL was current and nothing when a deploy had replaced it, and 25 minutes after a deploy, 67 of the 91 sitemap pages that got Early Hints still hinted the previous stylesheet. The stylesheet's `<link>` sits in the first kilobyte of every page, so the browser finds it with the first bytes of HTML. Hint only files whose URLs outlive a deploy.

## Providers never wrap a route outlet

TanStack Router wraps route outlets in Suspense boundaries, and React hydrates those boundaries later, in small slices. A context provider above them whose value changes right after hydration forces React to hydrate everything below it at once:

- `ThemeProvider` around the whole application turned the landing page's hydration into one 200 ms task that blocked input. Mounted around its two consumers, the `Toaster` and the docs `ThemeSwitch`, Total Blocking Time went from about 150 ms to under 10 ms.
- `MotionProvider` above a route outlet publishes a new context when its animation features finish loading. On a blog post that update arrived while the page was still loading its content, React fell back to client rendering, and the layout shifted.

Before adding a provider to `__root.tsx` or a layout, check whether its value can change after hydration. If it can, mount it next to the components that read it, below every route `<Outlet />`. The placements are listed in [Components and styling](/docs/conventions/components).

## A widget that is heavy to hydrate gets its own boundary

The CLI configurator on the landing page renders forty React Aria buttons, each with its own press, hover and focus hooks. Hydrated with the rest of the page, their effects made the commit that ends the page's hydration a 70–100 ms task under Lighthouse's desktop throttling, which raised Total Blocking Time from 101 to 147 ms. `CliSection` wraps `CliConfigurator` in a `Suspense` boundary that never suspends. React hydrates such a boundary on its own, after the rest of the page, and commits it separately, so the long task is gone and Total Blocking Time is 100 ms, with First Contentful Paint and Largest Contentful Paint unchanged. The configurator itself hydrates about 50 ms later. Give another widget a boundary of its own only when a comparison shows the same long task.

## A section with controls loads with its page

Before React hydrates a page, the router loads the chunks of the routes it matched: `hydrate` in `@tanstack/router-core` waits for each route's component and pending component. A component that a page names with React's `lazy` or with `lazyRouteComponent` is not one of them, so on a full load its chunk is requested only when React reaches it during hydration. Until that chunk arrives, React keeps the nearest `Suspense` boundary as the server's HTML and drops every press on it; it does not replay the press once the boundary hydrates. The admin dashboard's panels were loaded that way, and the boundary nearest to them was the route's own, so the whole dashboard below the console's layout ignored clicks until the panels' chunks arrived. The course player was loaded that way too, inside a boundary of its own, so its play button did nothing until the player's chunk arrived.

A part with a button, a link, a field or a table is therefore imported by the page that renders it, and only a part that takes no press loads lazily, inside a `Suspense` boundary of its own. `source-layout.test.ts` follows every module that a file under `src/presentation` or `src/routes` loads through `lazy` or `lazyRouteComponent`, and fails when one reaches React Aria, the router, TanStack Form, TanStack Table or the video player. When a skeleton draws its parts from a list, that list holds only what the skeleton and the loader need: `DASHBOARD_PANELS` in `panels-pending.tsx` names each panel's `key`, skeleton and `prefetch`, and `panels.tsx` gives each key its panel in a `Record` typed by those keys, so a panel without an entry, or an entry without a panel, fails the type check. The course pages' skeleton takes the player's skeleton from `player-pending.tsx`. The dashboard's component imports `panels.tsx` and the lesson's imports the player, so their controls arrive with the page's own chunk, before hydration, and the skeletons stay as light as before.

Only the drawing of the dashboard's charts stays lazy. With Recharts in the dashboard's chunk, the browser evaluated it before hydration, in the same long task as the dashboard's code, and a full load of `/admin` blocked the main thread for 98 ms more than with the drawing in a chunk of its own (Chromium at 6× CPU, medians of six interleaved loads). `TimeSeriesChart` now renders the table of its values with the panel and loads the bars, `TimeSeriesBars` in `time-series-bars.tsx`, with `lazyRouteComponent` inside a boundary of their own, and the dashboard's loader preloads them with the data. The range buttons and the currency tabs work from the first moment; a drawing that has not arrived yet follows a press as soon as its chunk does.

## One Tailwind build

Only `src/presentation/styles/globals.css` runs Tailwind. Route stylesheets such as `docs.css` and `typeset.css` are plain CSS, and Fumadocs' own styles come in through `globals.css`:

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

A second Tailwind build in a route stylesheet once shipped its own `.hidden`, `.rounded-md` and theme variables. Same-named cascade layers merge across stylesheets, and React never removes a stylesheet it inserted with `precedence`, so after one visit to the docs the landing page lost its responsive layout and fonts until a reload. The end-to-end test "landing keeps its responsive styles after visiting the docs" in `e2e/specs/landing.spec.ts` guards this. Anything that needs Tailwind goes through `globals.css`.

## Media

- **Landing loops.** Each `src/presentation/assets/motion/<name>.webm` has a poster `<name>.webp` with exactly the video's dimensions, so the hand-over from poster to video does not visibly sharpen. The dimensions are `LANDING_VIDEO_SIZES` in `src/data/landing-videos.ts`, which both the Remotion compositions and `ConceptLoop` read. Smaller widths are separate files, `<name>-<width>.webp`, offered through the poster's `srcSet`. `landing-videos.test.ts` fails when a poster's size differs from its composition or from the width in its file name. Never shrink the full-size poster; to make it lighter, re-encode it at the same dimensions. The videos load with `preload="none"`, play only while a quarter of them is visible and never play for readers who prefer reduced motion. The hero's loop slides up without fading in (`--rise-opacity: 1` on its `animate-rise`), because on a desktop screen its poster is the largest element above the fold, and a poster that fades in from transparent only counts as painted once the fade starts.
- **The course tour** in `course-showcase.tsx` is not a loop. Its `<video>` is rendered only after the visitor presses play, so until then the page loads just the poster: a `<picture>` with AVIF and WebP sources at the video's 1600 pixels and at 800. The video itself ships as WebM with an MP4 fallback.
- **Course videos** are encoded ahead of time to adaptive HLS and served from R2 with the Workers cache. See [Videos](/docs/features/videos).
- **Scroll-scrubbed video.** The site has none today. A video whose time follows the scroll position must be encoded all-intra (every frame a keyframe, `keyint=1`): a normal encode seeks in about 200 ms, an all-intra one in about 3 ms, and no amount of smoothing in JavaScript makes a 200 ms seek scrub.

## Reveal on scroll

`Reveal` (`src/presentation/components/custom/landing-page/components/reveal.tsx`) fades landing sections in as they enter the viewport. It shares one `IntersectionObserver` between every instance, decides from the observer's first callback whether an element starts below the fold, and writes `data-reveal` attributes directly, with no React state and no re-render. A version that kept the visibility in React state doubled Total Blocking Time, because every section re-rendered and the page laid out twice. Do not move it back into state, and do not replace it without a comparison.

Two other optimisations were measured and rejected: `content-visibility: auto` on landing sections, which broke in-page links to sections further down, and loading the newsletter form lazily, which scored the same or worse than rendering it directly.

## Content that arrives later keeps its size

A prerendered page paints before any script runs, so a section that fills in afterwards has to fit the space it was given. The landing page's course block is one: it reads the published courses once it scrolls near, and its placeholder used to guess two courses of six lessons each, so the block grew or shrank when the courses arrived and moved everything below it by a hundred pixels or more. Its columns now hold a fixed set of single lines, the placeholder draws the same lines, and its messages sit in a frame the size of a column, so every state has the same height at every width (see [Courses](/docs/features/courses)). The star count on the landing page does the same with a skeleton as tall as the number. Printing the courses into the prerendered HTML is not an option: the build has no production database, and rendering the landing page in the Worker on every request would give back the time to first byte that prerendering saves.

The docs keep the column of their table of contents the same way. The table of contents comes after the article in the HTML, so an empty element ahead of the article, `#nd-toc-column`, reserves its column, and the article has its final width and place in every frame the browser draws, before the table of contents has arrived (see [Docs site](/docs/features/docs-site)).
