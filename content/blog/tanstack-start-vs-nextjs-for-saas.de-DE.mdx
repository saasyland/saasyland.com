<Callout title="Was dieser Artikel ist">

Ein Vergleich von TanStack Start und Next.js für alle, die gerade ein SaaS bauen wollen, geschrieben von einem Team, das sich zwischen beiden entscheiden musste. Er behandelt:

1. Wo beide Frameworks im November 2026 stehen, nach TanStack Start 1.0 und Next.js 16.
2. Den Unterschied, aus dem alles andere folgt: was standardmäßig auf dem Server läuft.
3. Routing, Typsicherheit und Server Functions, einschließlich der Sicherheitsvorfälle, die beide hatten.
4. Hosting auf Vercel, auf einem Node-Server und auf Cloudflare Workers, und was jede dieser Optionen kostet.
5. Was ein SaaS braucht und keines der beiden Frameworks mitbringt, und wo jedes davon die bessere Wahl ist.

</Callout>

_Zuletzt geprüft am 20. November 2026. Jede Aussage über TanStack Start, Next.js, Vercel und Cloudflare stammt aus deren eigener Dokumentation, ihren Blogs, Bedingungen und Sicherheitshinweisen oder aus der npm-Registry und ist unten verlinkt. Jede Zahl über SaaSy Land wird aus seinem Code ausgegeben. Wir verkaufen ein Produkt, das auf TanStack Start aufbaut, also gewichte unsere Schlussfolgerungen entsprechend; die Quellen stehen da, damit du uns nichts davon einfach glauben musst._

## Die kurze Antwort

**Wähle Next.js**, wenn deine öffentlichen Seiten genauso wichtig sind wie deine App: Marketing, Dokumentation und Inhalte, die auf dem Server gerendert, gecacht und revalidiert werden sollen, mit optimierten Bildern, alles eingebaut. Wähle es auch, wenn dein Team es schon kennt, wenn du das größte Ökosystem und den größten Bewerberpool im React-Umfeld willst oder wenn du auf Vercel hosten willst.

**Wähle TanStack Start**, wenn der größte Teil deines Produkts hinter einer Anmeldung liegt und aus Dashboards, Tabellen, Formularen und Filtern besteht, wo typisierte Routen und typisierte Suchparameter Fehler abfangen, bevor sie ausgeliefert werden. Wähle es auch, wenn du Server Functions willst, ohne Server Components zu deinem Komponentenmodell zu machen, oder wenn du auf Cloudflare Workers deployst, das TanStack als offiziellen Hosting-Partner führt.

Beide können heute ein SaaS in Produktion betreiben. Der Rest dieses Artikels liefert die Details hinter diesen zwei Absätzen.

## Wo beide Frameworks im November 2026 stehen

**TanStack Start ist stabil.** TanStack hat am 13. Oktober 2026 verkündet, dass TanStack Start 1.0 endlich stabil ist („TanStack Start 1.0 is finally stable“). Das stabile Release wurde als Version 1.169 von `@tanstack/react-start` veröffentlicht, nicht als 1.0.0, und der Migrationsleitfaden von TanStack nennt 1.169 das erste stabile Release („the first stable release“); eine frühere Versionsnummer ist also ein Release Candidate. Vergleiche, die vor Oktober geschrieben wurden, beschreiben ein Framework, das noch nicht stabil war.

**Next.js ist bei Version 16.** Next.js 16 hat Turbopack zum Standard-Bundler gemacht, `middleware.ts` durch `proxy.ts` ersetzt, das in der Node.js-Runtime läuft, die Integration des React Compilers stabil gemacht und Cache Components mit der Direktive `"use cache"` eingeführt. Next.js 16.2 hat die Adapter-API im März 2026 stabil gemacht. Seit 16.4 haben neue Apps, die mit `create-next-app` angelegt werden, Cache Components standardmäßig aktiviert, und laut Next.js wird dieses Modell in Next.js 17 zum Standard („will become the default in Next.js 17“). Am 20. November 2026 war 16.4.6 das neueste Release auf npm.

**Der offizielle Vergleich ist ungewöhnlich fair.** Die eigene Vergleichsseite von TanStack, am 11. September 2026 gegen Next.js 16.3 geprüft, sagt, dass Self-Hosting von Next.js Bildoptimierung und die Konfiguration von ISR einschließt und diese Funktionen nicht als Vercel-exklusiv bezeichnet werden sollten („those features should not be labeled Vercel-only“), und dass die Seite keinen Sieger bei der Performance kürt („does not establish a performance winner“). Jeder Artikel, der dir erzählt, TanStack Start sei schneller oder Next.js funktioniere nur auf Vercel, geht weiter als TanStack selbst.

## Der Unterschied, aus dem alles andere folgt: was auf dem Server läuft

**Next.js beginnt auf dem Server.** Im App Router sind Layouts und Seiten standardmäßig Server Components („layouts and pages are Server Components“). Eine Komponente lädt ihre Daten dort, wo sie rendert, liefert für sich selbst kein JavaScript aus, und die interaktiven Teile markierst du mit `"use client"`. Mutationen sind Server Functions, die eine Client-Komponente wie eine lokale Funktion aufruft. Für eine inhaltsreiche Seite ist das ein echter Vorteil: Weniger JavaScript erreicht den Browser, und das Laden der Daten steht direkt neben dem Markup, das sie verwendet.

**TanStack Start beginnt mit gewöhnlichem React.** Seiten sind Client-Komponenten, die TanStack Start für die erste Anfrage auf dem Server rendert und im Browser hydratisiert. Daten kommen über Route-Loader, und Code, der nur auf dem Server laufen darf, lebt in Server Functions, die mit `createServerFn` erstellt werden; laut Dokumentation laufen sie auf dem Server, lassen sich aber nahtlos aus Client-Code aufrufen („run on the server but can be invoked from client code seamlessly“). Du kannst das Server-Rendering mit Selective SSR pro Route abschalten oder eine Single-Page-App ausliefern, die trotzdem Server Functions aufruft. Server Components gibt es, aber als Experiment: Laut Dokumentation sind sie standardmäßig nicht aktiviert („are not enabled by default“), und in der Ankündigung von 1.0 schrieb Tanner Linsley, er habe beschlossen, sie auf tanstack.com nicht mehr zu verwenden („decided to stop using it on tanstack.com“).

**Was das für ein SaaS bedeutet.** Der größte Teil eines SaaS liegt hinter der Anmeldung: Tabellen, Filter, Formulare und Einstellungen, wo die Seite ohnehin interaktiv ist und der Browser den größten Teil des Zustands schon hält. Genau dort kostet dich das Modell von TanStack Start am wenigsten. Die Marketing-Website, die Dokumentation und der Blog sind das Gegenteil: größtenteils statisch, von Suchmaschinen gelesen und mit dem Server-First-Modell von Next.js besser bedient. Welche Hälfte deines Produkts größer ist, ist die erste Frage, die du beantworten musst.

## Routing und Typsicherheit

**TanStack Router typisiert jede Route.** Er leitet die Typen, die er bekommt, vollständig ab und reicht sie beharrlich durch das gesamte Routing („fully infers the types it’s provided and tenaciously pipes them through the entire routing experience“): Ein Link auf eine Route, die nicht existiert, ein fehlender Pfadparameter oder ein falscher Suchparameter lassen die Typprüfung scheitern. Suchparameter werden pro Route mit `validateSearch` validiert und typisiert, und das zählt in einem SaaS, in dem Filter, Sortierung, Paginierung und Tabs in die URL gehören, damit sich eine Ansicht teilen und neu laden lässt.

**Auch Next.js hat typisierte Routen, mit anderem Umfang.** Über die optionale Einstellung `typedRoutes` kann Next.js Links statisch typisieren, um Tippfehler und andere Fehler bei der Verwendung von `next/link` zu verhindern, und der eigene Vergleich von TanStack warnt, es sei ungenau, das nur als IDE-Hinweise zu beschreiben („describing it as only IDE hints is inaccurate“). Suchparameter erreichen eine Seite allerdings als Strings, die du selbst oder mit einer Bibliothek parst und validierst.

Das ist der Grund für TanStack Start, den wir am häufigsten hören, und es ist der Grund, aus dem wir uns dafür entschieden haben: In einer App mit Dutzenden filterbarer Tabellen ist die URL Zustand, und dass der Compiler sie prüft, macht sich bezahlt.

## Server Functions und die Sicherheitsgrenze

Beide Frameworks lassen eine Client-Komponente eine Funktion aufrufen, die auf dem Server läuft, und in beiden ist sie ein HTTP-Endpunkt, den jeder aufrufen kann. Die Dokumentation von Next.js sagt es unmissverständlich: Server Functions sind über direkte POST-Requests erreichbar, nicht nur über die Oberfläche deiner Anwendung, also prüfe Authentifizierung und Autorisierung immer innerhalb jeder einzelnen Server Function. Dasselbe gilt für `createServerFn` von TanStack Start, und seine Middleware ist der Ort, an den diese Prüfung gehört.

Drei Vorfälle zeigen, warum die Prüfung in jede Funktion gehört und nicht an den Rand der App:

- **CVE-2025-29927, März 2025.** In Next.js ließen sich Autorisierungsprüfungen innerhalb einer Next.js-Anwendung umgehen, wenn die Prüfung in der Middleware stattfand („if the authorization check occurs in middleware“). Die Lücke wurde als kritisch eingestuft, betraf Releases ab 11.1.4 und wurde in 12.3.5, 13.5.9, 14.2.25 und 15.2.3 behoben. Laut dem Postmortem von Vercel waren selbst gehostete Apps mit `next start` und `output: 'standalone'` betroffen, Apps auf Vercel, Netlify und Cloudflare Workers dagegen nicht.
- **CVE-2025-55182, Dezember 2025.** React hat eine Schwachstelle in React Server Components offengelegt, die Remote Code Execution ohne Authentifizierung erlaubt („an unauthenticated remote code execution vulnerability in React Server Components“), bewertet mit CVSS 10.0. Sie betraf jedes Framework und jeden Bundler mit Unterstützung für Server Components, darunter `next`, `react-router` und `@vitejs/plugin-rsc`; in Next.js waren App-Router-Apps auf 15.x und 16.x betroffen, Pages-Router-Apps nicht. TanStack Start stand nicht auf der Liste, weil Server Components dort optional sind, aber sein experimentelles Setup nutzt `@vitejs/plugin-rsc`.
- **CVE-2026-102989, September 2026.** TanStack hat eine kritische Reflected-XSS-Schwachstelle in der Verarbeitung der Antworten von Server Functions in TanStack Start offengelegt („a critical reflected cross-site scripting (XSS) vulnerability in TanStack Start’s server-function response handling“), die `@tanstack/react-start` ab 1.143.12 betraf und in 1.168.60 behoben wurde.

Keines der beiden Frameworks ist immun, und ein jüngeres hatte weniger Zeit, angegriffen zu werden. Was ein SaaS schützt, ist eine Autorisierungsprüfung in jeder Server Function und die Gewohnheit, innerhalb weniger Tage zu aktualisieren. In saasyland.com führt jede Server Function die passende Middleware aus `auth.middleware.ts` aus, `authorized(...)` für einen angemeldeten Nutzer oder eine Berechtigung, und die [Konvention für Server Functions](/docs/conventions/server-functions) erklärt, warum ein Routen-Guard nie als Autorisierung gilt.

## Hosting: Vercel, ein Node-Server oder Cloudflare Workers

### Next.js

**Next.js läuft überall, wo Node.js läuft.** Laut seinem Deployment-Leitfaden braucht eine Plattform einen Node.js-Server, mehr nicht: Ein einziger Prozess mit `next start` beherrscht jede Funktion von Next.js korrekt. Seit Next.js 16.2 ist die Adapter-API stabil, entwickelt gemeinsam mit OpenNext, Netlify, Cloudflare, AWS Amplify und Google Cloud, und die Dokumentation führt zwei verifizierte Adapter auf, für Vercel und Bun, während Cloudflare und Netlify an ihren eigenen arbeiten.

**Self-Hosting mit mehr als einer Instanz erfordert Konfiguration.** Der Cache, den ISR und Cache Components nutzen, liegt im lokalen Dateisystem (also auf der Festplatte) jeder einzelnen Next.js-Serverinstanz, und ein Aufruf von `revalidateTag()` auf einer Instanz invalidiert nur den Cache dieser Instanz; mehrere Instanzen brauchen also einen gemeinsamen Cache-Handler. Sie brauchen außerdem denselben `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`, sonst sehen Nutzer nach einem Deploy Fehler wie „Failed to find Server Action“.

**Vercel ist der bequemste Weg, und ein SaaS braucht Pro.** Laut den Bedingungen von Vercel darfst du die Dienste im Hobby-Tarif nur für private oder nicht kommerzielle Zwecke nutzen („you shall only use the Services under a Hobby plan for your personal or non-commercial use“), ein Produkt, für das du Geld verlangst, gehört also auf Pro. Pro kostet eine monatliche Plattformgebühr von 20 $, die einen Seat zum Deployen und 20 $ Nutzungsguthaben enthält; weitere kostenpflichtige Seats kosten je 20 $ im Monat, Seats zum Ansehen sind kostenlos, und Nutzung über das Guthaben hinaus wird nach Verbrauch abgerechnet.

**Auf Cloudflare Workers läuft Next.js über eine Nachimplementierung oder einen Adapter.** Cloudflare empfiehlt vinext als Standardweg, um Next.js-Anwendungen auf Cloudflare Workers zu betreiben („recommends vinext as the default way to run Next.js applications on Cloudflare Workers“). vinext ist ein Vite-Plugin, das die API von Next.js nachimplementiert, und die Dokumentation von Cloudflare sagt, vinext sei in der Beta („vinext is in beta“); seine eigene README beantwortet die Frage nach dem Einsatz in Produktion mit „You can, with caution“, also mit Vorsicht, und fügt hinzu, OpenNext sei die sicherere Wahl („OpenNext is the safer choice“), wenn du einen ausgereiften Weg brauchst, Next.js außerhalb von Vercel zu betreiben. Der Cloudflare-Adapter von OpenNext unterstützt alle Minor- und Patch-Versionen von Next.js 16.

### TanStack Start

**TanStack Start ist eine Vite-Anwendung und wird auch so deployt.** Sein Hosting-Leitfaden empfiehlt drei offizielle Hosting-Partner, Cloudflare, Netlify und Railway, und führt Vercel, einen Node-Server, Bun und weitere über Nitro auf. Auf Cloudflare baut es mit dem eigenen Vite-Plugin von Cloudflare, die App ist also ein Worker, mit D1, KV und R2 als gewöhnlichen Bindings statt über einen Adapter, der die Runtime eines anderen Frameworks übersetzt.

**Was du aufgibst, ist das eingebaute Caching.** Die ISR von TanStack Start nutzt Standard-HTTP-Cache-Header, die mit jedem CDN funktionieren („leverages standard HTTP cache headers that work with any CDN“): Du setzt die Header, und dein CDN erledigt den Rest. Das ist leichter zu durchschauen, und es ist zugleich Arbeit, die Next.js dir abnimmt.

saasyland.com läuft auf einem Cloudflare Worker mit D1 über Drizzle, KV und R2, und die [Dokumentation zu Cloudflare Workers](/docs/integrations/cloudflare-workers) zeigt, wie.

## Was ein SaaS braucht und keines der beiden Frameworks mitbringt

Ein Framework ist der kleinste Teil eines SaaS. Weder TanStack Start noch Next.js liefert Anmeldung, Abrechnung, Transaktions-E-Mails, einen Admin-Bereich oder die Tests, die all das am Laufen halten, und die verbleibenden Lücken unterscheiden sich nur leicht:

- **Sprachen.** Der App Router von Next.js hat kein eingebautes internationalisiertes Routing: Sein Leitfaden verschachtelt jede Seite unter einem Ordner `app/[lang]`, leitet in `proxy.js` nach Sprache weiter und verweist auf Bibliotheken wie next-intl. TanStack Router bietet Bausteine wie optionale Pfadparameter und das Umschreiben von Routen, mit Beispielen auf Basis von Paraglide. So oder so wählst du eine Bibliothek und bindest sie selbst ein.
- **Bilder.** Next.js hat `next/image` und `next/font`. TanStack Start überlässt Bilder CSS, einem Bilddienst oder deinem Host.
- **Authentifizierung.** Beide werden von Better Auth, Clerk und den anderen Bibliotheken unterstützt; wir vergleichen sie in [Better Auth vs. Clerk vs. Auth.js](/blog/better-auth-vs-clerk-vs-authjs).
- **Abrechnung.** Keines der beiden Frameworks nimmt Zahlungen entgegen. Polar, Stripe und Lemon Squeezy werden in [Polar vs. Stripe vs. Lemon Squeezy](/blog/polar-vs-stripe-vs-lemon-squeezy) verglichen.

Diese Liste, dazu eine Admin-Konsole, E-Mail, eine Testsuite und Dokumentation, ist genau das, wofür ein Starter-Kit da ist, und es ist dieselbe Arbeit, egal welches Framework darunter liegt.

## Ökosystem, Recruiting und KI-Coding-Agenten

**Next.js ist weit größer.** In der Woche vom 12. bis 18. November 2026 zählte die Download-Statistik von npm 99.343.684 Downloads von `next` und 14.088.042 von `@tanstack/react-start`. Mehr Entwickler kennen Next.js, mehr Anbieter dokumentieren es zuerst, und mehr Starter-Kits bauen darauf auf. Das ist ein echter Vorteil, wenn du Leute einstellst, wenn du nach einer Fehlermeldung suchst und wenn du einen Dienst integrierst.

**TanStack Start profitiert von TanStack.** TanStack Query, Router, Table und Form sind auch für sich allein weit verbreitet, sodass vieles in einer TanStack-Start-App jedem vertraut ist, der sie schon genutzt hat, und die Dienste, die ein SaaS braucht, dokumentieren TanStack Start zunehmend: Better Auth und Clerk haben beide Anleitungen dafür.

**Für Coding-Agenten sind beide Frameworks neu.** Next.js 16 hat die Middleware umbenannt und das Caching geändert; das stabile Release von TanStack Start hat `.inputValidator()` in `.validator()` umbenannt und setzt Vite 8 voraus. Wofür du dich auch entscheidest, gib deinen Agenten die aktuelle Dokumentation, statt dich auf das zu verlassen, was sie im Training gelernt haben; darüber haben wir in [Die Wahl eines SaaS-Stacks für KI-Coding-Agenten](/blog/choosing-a-saas-stack-for-ai-coding-agents) geschrieben.

## Wann Next.js die bessere Wahl ist

- **Deine öffentlichen Seiten tragen das Geschäft.** Eine Content-Website, ein Marktplatz mit Tausenden indexierbarer Seiten oder eine Dokumentation, die Anmeldungen bringt, profitiert von Server Components, ISR, Cache Components und Bildoptimierung, ohne dass du sie selbst zusammensetzen musst.
- **Du willst Server Components als dein Modell.** Sie sind der Kern des App Routers und in TanStack Start experimentell.
- **Dein Team kennt Next.js schon.** Der eigene Vergleich von TanStack sagt, ein anderes Routing-Modell sei für sich genommen kein Grund, eine gesunde Anwendung neu zu schreiben („a different routing model is not, by itself, a reason to rewrite a healthy application“), und dieselbe Überlegung gilt für die Erfahrung eines Teams.
- **Du hostest auf Vercel.** Preview-Deployments, Caching und Bildoptimierung funktionieren ohne Konfiguration, und Pro kostet zum Einstieg 20 $ im Monat.
- **Du brauchst das breiteste Ökosystem.** Mehr Integrationen, Beispiele, Starter-Kits und Entwickler, die du einstellen kannst.

## Wann TanStack Start die bessere Wahl ist

- **Dein Produkt liegt größtenteils hinter einer Anmeldung.** Dashboards, Tabellen und Formulare gewinnen mehr durch typisierte Routen, validierte Suchparameter und explizite Loader als durch Server Components.
- **Du willst ein Client-First-Denkmodell.** Server Functions und Middleware geben dir Servercode, ohne die Grenze zwischen Server und Client zum Teil jeder Komponente zu machen.
- **Du deployst auf Cloudflare Workers oder willst die Wahl zwischen mehreren Hosts.** Cloudflare ist offizieller Hosting-Partner, und der Build ist der von Vite.
- **Du willst, dass sich das Framework aus deinem Caching heraushält.** HTTP-Cache-Header und dein CDN statt eines Framework-Caches, den du pro Instanz konfigurierst.

## Warum SaaSy Land auf TanStack Start aufbaut

saasyland.com ist ein SaaS genau der ersten Art: ein Kundenbereich, eine Admin-Konsole mit Datentabellen, eine Lizenz-API, ein Checkout, ein Blog und Dokumentation in <RepositoryFact name="languages" /> Sprachen. Bis September 2026 lief es mit Next.js 16 auf Vercel; der Umstieg auf TanStack Start auf Cloudflare Workers ist in seiner öffentlichen Historie nachvollziehbar. Wir haben uns für TanStack Start mit React <RepositoryFact name="reactMajor" />, Vite+ und Cloudflare Workers entschieden, aus vier Gründen, die du in seinem öffentlichen Quellcode nachlesen kannst:

1. **Typisierte URLs.** Eine Route, die Suchparameter liest, validiert sie mit Zod in `validateSearch`, sodass ein Filter, eine Seitennummer oder ein Tab in der URL beim Parsen geprüft und überall, wo er gelesen wird, typisiert ist. Die [Konvention für Routen](/docs/conventions/routes) zeigt die eine Form, die jede Routendatei hat.
2. **Server Functions mit expliziter Middleware.** Jede Server Function validiert ihre Eingabe mit dem Zod-Schema ihres Moduls und führt die passende Autorisierungs-Middleware aus, also genau die Prüfung, für die die Vorfälle oben sprechen.
3. **Workers als Plattform, nicht als Ziel.** Der Worker, D1, KV und R2 sind die Runtime der Anwendung, ohne Adapter zwischen Framework und Plattform.
4. **Eine Toolchain.** Vite+ betreibt den Dev-Server, den Build, Vitest und die Linter aus einer einzigen `vite.config.ts`, und der Merge scheitert unter <RepositoryFact name="coverageThreshold" /> % Abdeckung von Anweisungen, Verzweigungen, Funktionen und Zeilen.

Die Kosten sind real. Wir haben keine Server Components, also hydratisiert jede Komponente auf unseren Marketingseiten im Browser, auch die Teile, die sich nie ändern, und die [Performance-Konvention](/docs/conventions/performance) hält fest, was wir stattdessen messen und einsparen. Wir haben kein `next/image`, also bereiten wir unsere Bilder und Video-Poster selbst vor. Und wir folgen einem jüngeren Framework dicht auf den Fersen: Sein stabiles Release hat APIs geändert, die wir nutzen, und wir bleiben auf seinem neuesten Release.

Die CLI von SaaSy Land ist in der Beta. Sie aktiviert deine Lizenz und generiert TanStack-Start-Projekte für Cloudflare Workers, und der [Konfigurator](/#cli) führt Next.js als Option, die noch kommt. Ganz saasyland.com ist unter der MIT-Lizenz öffentlich, sodass du die TanStack-Start-App, aus der der Generator Projekte schreibt, lesen kannst, bevor du kaufst.
