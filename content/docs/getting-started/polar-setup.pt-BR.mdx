A Polar vende os três planos pelos preços que o checkout envia, emite as chaves de licença deles e cobra os impostos. O código espera uma configuração precisa na Polar, e a Polar não avisa quando os dois divergem: um produto sem um benefício de chave de licença continua recebendo o pagamento, mas não emite nenhuma chave. `bun run polar:verify:<environment>` compara a Polar com o código, e os scripts de deploy o executam antes de todo deploy manual.

## Produção e sandbox

A Polar mantém dois serviços separados. A produção (`polar.sh`, API `api.polar.sh`) cobra cartões reais; o sandbox (`sandbox.polar.sh`, API `sandbox-api.polar.sh`) aceita apenas cartões de teste. Eles não compartilham nada: uma conta, organização, token, produto, desconto ou webhook existe em um único serviço, então crie uma conta em `sandbox.polar.sh` à parte e configure cada serviço de forma independente.

| Arquivo de ambiente | `POLAR_SERVER` | Organização da Polar |
| ------------------- | -------------- | -------------------- |
| `.env.development`  | `sandbox`      | Sandbox              |
| `.env.preview`      | `sandbox`      | Sandbox              |
| `.env.production`   | `production`   | Produção             |

Desenvolvimento e preview podem compartilhar uma organização do sandbox, assim como compartilham um banco de dados D1: o webhook dela envia eventos para o host de preview, e uma compra de teste feita em desenvolvimento chega ao banco de dados compartilhado por meio dele.

Nunca coloque um token, um ID de organização ou um ID de produto de produção em `.env.development` ou `.env.preview`. A API do sandbox rejeita um token de produção e, com `POLAR_SERVER=production`, um checkout de teste cobraria um cartão real e concederia a licença no banco de dados local ou de preview. `polar:verify` recusa `POLAR_SERVER=production` para desenvolvimento e preview, e `POLAR_SERVER=sandbox` para produção.

## Organização e token

No sandbox e, depois, na produção:

1. Crie uma organização e copie o ID dela, nas configurações da organização, para `POLAR_ORGANIZATION_ID`. Dê às duas organizações o slug de `POLAR_ORGANIZATION_SLUG` (`src/data/polar.ts`), ou mude a constante para o slug delas: o [alerta e a lista do admin de pedidos sem conta correspondente](/docs/features/licences#orders-that-match-no-account) apontam cada pedido para o painel da Polar com esse slug.
2. Nas configurações da organização, crie um token de acesso da organização com estes escopos, e nenhum outro, e copie-o para `POLAR_ACCESS_TOKEN`.

| Escopo                    | Usado por                                                                                                                                                                                                                                                                                 |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkouts:write`         | `startCheckout`, que cria o checkout por meio do plugin da Polar para o Better Auth                                                                                                                                                                                                       |
| `customer_sessions:write` | O link do portal do cliente, `/api/auth/customer/portal`                                                                                                                                                                                                                                  |
| `license_keys:write`      | Ler uma chave e as ativações dela, ativar um dispositivo e remover uma ativação (`deactivateLicense` e a [API de licenças da CLI](/docs/features/cli-licence-api)) e, num upgrade, aumentar o limite de ativações da chave e desativar a chave que a Polar emite para o pedido de upgrade |
| `orders:read`             | Os handlers de webhook, que leem o pedido por trás de uma licença e o cliente atual de um pedido cujo evento não corresponde a nenhuma conta, e o preço do upgrade, que soma o que o cliente pagou por licenças                                                                           |
| `organizations:read`      | `polar:verify`, que lê se a localização do checkout está ativada e o comportamento fiscal padrão                                                                                                                                                                                          |
| `products:read`           | `polar:verify`                                                                                                                                                                                                                                                                            |
| `webhooks:read`           | `polar:verify`                                                                                                                                                                                                                                                                            |

Um escopo de escrita inclui a leitura, então `license_keys:write` também cobre a leitura de chaves. Um token de organização já age em nome da própria organização. Ainda assim, `polar:verify` envia `POLAR_ORGANIZATION_ID` como o parâmetro de consulta `organization_id`, como faz a listagem de pedidos de um upgrade, então um ID de outra organização aparece como produtos ausentes.

## Produtos

Crie um produto por plano: uma compra única, não uma assinatura, com um preço fixo em `DEFAULT_CURRENCY_CODE` (dólares americanos) igual a `TIER_PRICES` em `src/data/marketing.ts`. Copie o ID de cada produto para a chave correspondente.

| Plano    | Chave                       | Preço                         | Ativações por chave                 |
| -------- | --------------------------- | ----------------------------- | ----------------------------------- |
| Core     | `POLAR_PRODUCT_ID_CORE`     | <TierPrice tier="core" />     | <ActivationLimit tier="core" />     |
| Complete | `POLAR_PRODUCT_ID_COMPLETE` | <TierPrice tier="complete" /> | <ActivationLimit tier="complete" /> |
| Agency   | `POLAR_PRODUCT_ID_AGENCY`   | <TierPrice tier="agency" />   | <ActivationLimit tier="agency" />   |

A Polar guarda um preço na menor unidade da moeda, centavos no caso do dólar americano, e `polar:verify` converte `TIER_PRICES` da mesma forma antes de compará-los. Ele ignora preços arquivados.

## Chaves de licença

Crie um benefício do tipo **License Keys** por plano e associe-o apenas ao produto desse plano:

- **Ativações**: limitadas ao número da tabela acima, `LICENSE_ACTIVATION_LIMITS` em `src/modules/license/license.constants.ts`. Permitir que os clientes gerenciem as próprias ativações na Polar é opcional, porque `/app/license` já as lista e remove por conta própria.
- **Expiração**: nenhuma. As chaves nunca expiram, já que a compra é um pagamento único.
- **Limite de uso**: nenhum.
- **Prefixo**: à sua escolha; `polar:verify` não o verifica.

Cada produto precisa de exatamente um benefício de chave de licença; outros benefícios ao lado dele não são problema. Quando a Polar concede o benefício, o webhook `benefit_grant.created` grava a chave na licença do comprador.

## Caixa de consentimento [#consent-checkbox]

O comprador dá o consentimento ao fornecimento imediato no checkout da Polar, e esse campo é o único lugar onde ele é pedido (veja [Licenças](/docs/features/licences#consent-to-immediate-supply)); a Polar o registra no pedido. Crie um campo personalizado na organização e associe-o aos três produtos:

- **Tipo**: caixa de seleção.
- **Slug**: <RepositoryFact name="licenseWithdrawalConsentField" />, `LICENSE_CHECKOUT_FIELD.WITHDRAWAL_CONSENT` em `src/modules/license/license.constants.ts`. O pedido guarda a caixa marcada sob essa chave em `custom_field_data`.
- **Rótulo**: exatamente `WITHDRAWAL_CONSENT_FIELD.label` de `src/lib/polar.ts`, a frase em inglês montada a partir de `REFUND_TERMS.WITHDRAWAL_DAYS` que termina com um link em Markdown para a Política de Reembolso de produção.
- **Nome**: à sua escolha; `WITHDRAWAL_CONSENT_FIELD.name` é o que o código sugere, e `polar:verify` não o verifica.
- **Obrigatório** em cada um dos três produtos. Outros campos que os produtos pedem podem continuar.

`startCheckout` não envia nenhum valor para o campo, então a caixa começa vazia e o comprador a marca; a Polar não aceita o pagamento enquanto uma caixa obrigatória estiver vazia. A Polar só guarda os valores dos campos que o produto pede: antes de o campo ser associado, o checkout continua funcionando, mas o pedido não registra nenhum consentimento, e a [confirmação da compra](/docs/features/licences#purchase-confirmation) informa, em vez disso, o direito de desistência previsto em lei.

Criar o campo e associá-lo a um produto exige os escopos `custom_fields:write` e `products:write`, que o token acima não tem. Crie e associe o campo no painel da Polar ou pela API, com um token à parte que tenha esses escopos. `polar:verify` lê os campos associados na listagem de produtos, então não precisa de nenhum outro escopo.

## Idioma do checkout [#checkout-language]

A Polar só mostra o checkout no idioma que `startCheckout` pede enquanto a localização do checkout estiver ativada na organização; caso contrário, todo checkout abre em inglês. Ative-a nas configurações da organização. O [guia de localização do checkout](https://polar.sh/docs/features/checkout/localization) da Polar a chama de feature flag, e a API a retorna como `feature_settings.checkout_localization_enabled` na organização. `POLAR_CHECKOUT_LANGUAGES` em `src/data/polar.ts` lista os idiomas que o código pede, e `polar:verify` falha enquanto a localização estiver desativada.

## Comportamento fiscal [#tax-behaviour]

Os cards de preços dizem que os preços estão em dólares americanos, que o IVA está incluído na UE e que o imposto sobre vendas é adicionado no checkout nos Estados Unidos, no Canadá e na Índia. A Polar cobra os impostos dessa forma quando o comportamento fiscal padrão da organização é baseado na localização, então defina-o assim nas configurações da organização. A API o retorna como `default_tax_behavior` na organização, e `polar:verify` falha enquanto ele não for `location` (`POLAR_TAX_BEHAVIOR.LOCATION` em `src/lib/polar.ts`).

## Preços regionais [#regional-prices]

Os preços regionais não precisam de nada na Polar. Para um comprador em um país de `PPP_TIERS` (`src/modules/license/license.pricing.ts`), cujas faixas abatem <RegionalDiscounts />, `startCheckout` envia o próprio preço: `regionalPrice` arredonda o preço do plano para baixo em dólares inteiros, o valor que os cards de planos mostram, e o checkout o leva em `prices` como um preço fixo para o produto do plano que vale só para esse checkout, de modo que o produto mantém o preço de `TIER_PRICES`. Um [upgrade](/docs/features/licences#upgrades) envia o preço dele da mesma forma. Os descontos criados por uma configuração anterior não são mais usados, e você pode excluí-los.

## Webhook

Crie um endpoint de webhook para cada ambiente com deploy, na organização que esse ambiente usa.

| Ambiente     | Organização | URL                                                     |
| ------------ | ----------- | ------------------------------------------------------- |
| `preview`    | Sandbox     | `https://preview.saasyland.com/api/auth/polar/webhooks` |
| `production` | Produção    | `https://saasyland.com/api/auth/polar/webhooks`         |

O host vem de `DEPLOYED_HOSTS` e o caminho, de `ROUTES`. Escolha o formato raw, mantenha o endpoint ativado e inscreva-o exatamente nos eventos de `POLAR_EVENTS` (`src/data/polar-events.ts`), que reúne os eventos que todas as áreas tratam (veja [Pagamentos](/docs/features/payments#webhooks)). Hoje a área de licenças trata os eventos de `LICENSE_WEBHOOK_EVENTS` (`src/modules/license/license.constants.ts`), e a área de cobrança, os de `src/data/billing.polar-events.ts`:

| Evento                  | Área de licenças                                                            | Área de cobrança               |
| ----------------------- | --------------------------------------------------------------------------- | ------------------------------ |
| `benefit_grant.created` | Grava a chave de licença                                                    |                                |
| `benefit_grant.revoked` | Revoga a licença                                                            |                                |
| `order.created`         |                                                                             | Copia o pedido para o D1       |
| `order.paid`            | Concede a licença                                                           | Atualiza a cópia do pedido     |
| `order.refunded`        | Marca a licença como reembolsada quando o pedido é reembolsado por completo | Atualiza a cópia do pedido     |
| `order.updated`         |                                                                             | Atualiza a cópia do pedido     |
| `subscription.created`  |                                                                             | Copia a assinatura para o D1   |
| `subscription.updated`  |                                                                             | Atualiza a cópia da assinatura |

Quando uma área começar a tratar um evento, adicione o evento a cada endpoint antes de fazer o deploy desse código. O código implantado até lá responde 200 a um evento que nenhuma área trata e não faz nada com ele, então adicionar o evento antes não causa problema, e o `polar:verify` faz o deploy falhar enquanto um endpoint não enviar todos os eventos de `POLAR_EVENTS`.

Copie o secret de assinatura do endpoint para `POLAR_WEBHOOK_SECRET` no mesmo arquivo de ambiente. O desenvolvimento não precisa de endpoint, porque a Polar não consegue alcançar `localhost`.

Nunca adicione um endpoint de preview à organização de produção, nem um endpoint de produção ao sandbox: pagamentos reais chegariam ao preview, ou compras de teste concederiam licenças em produção.

## Verificar a configuração

```sh
bun run polar:verify:development
bun run polar:verify:preview
bun run polar:verify:production
```

Cada script lê as chaves da Polar de `.env.<environment>` e envia apenas requisições GET à API que `POLAR_SERVER` indica: lê a organização e lista os produtos e os endpoints de webhook dela, e não altera nada. Ele verifica se:

- o arquivo de ambiente define todas as chaves da Polar, com `POLAR_SERVER=sandbox` para desenvolvimento e preview e `POLAR_SERVER=production` para produção;
- a localização do checkout está ativada na organização, e o comportamento fiscal padrão dela é baseado na localização;
- cada `POLAR_PRODUCT_ID_*` indica um produto da organização que não está arquivado nem é uma assinatura, com preços fixos, em `DEFAULT_CURRENCY_CODE` e iguais a `TIER_PRICES`;
- cada produto tem exatamente um benefício de chave de licença com o limite do plano definido em `LICENSE_ACTIVATION_LIMITS`, sem expiração e sem limite de uso;
- cada produto exige o campo de caixa de seleção <RepositoryFact name="licenseWithdrawalConsentField" /> com o rótulo de `WITHDRAWAL_CONSENT_FIELD`;
- preview e produção têm um endpoint raw ativado na respectiva URL de webhook, assinado com `POLAR_WEBHOOK_SECRET` e inscrito exatamente em `POLAR_EVENTS`;
- nenhum endpoint envia eventos para o host de um ambiente que usa o outro serviço da Polar.

`polar:verify` é a verificação de deploy da área da Polar (`POLAR_DEPLOY_CHECKS` em `src/data/polar.deploy.ts`), então `deploy:preview` e `deploy:production` o executam por meio de `scripts/run-deploy-checks.ts`, depois de `scripts/verify-bindings.ts` e `scripts/prepare-deploy-secrets.ts` e antes do build. Os deploys da CI não executam nenhuma verificação de deploy, nem mesmo `polar:verify`: `deploy-reusable.yml` não tem nenhuma etapa para `scripts/run-deploy-checks.ts`, os ambientes do GitHub não guardam nenhum token da Polar, e o Worker mantém os secrets da Polar já configurados na Cloudflare. Execute `polar:verify` você mesmo depois de cada alteração na Polar.

## Em caso de falha

O script termina com um erro que lista cada problema encontrado, um por linha:

```text
Polar production does not match the code for production:
The core product (POLAR_PRODUCT_ID_CORE) has 0 licence-key benefits; it needs exactly one.
A webhook endpoint posts to https://preview.saasyland.com/api/auth/polar/webhooks, the preview host, from this Polar production organisation; remove it.
```

Uma falha interrompe o deploy antes de qualquer build, migração ou envio. O script nunca altera a Polar: corrija a Polar e execute-o de novo. Cada mensagem indica a chave, a constante ou a configuração a corrigir:

- **`Set … in .env.<environment>`**: uma chave da Polar está ausente ou vazia, ou `POLAR_SERVER` indica o serviço errado.
- **`rejects POLAR_ACCESS_TOKEN`**: o token é inválido, foi revogado ou é do outro serviço, como um token de produção em `.env.preview`.
- **`lacks the … scope`**: crie um token com os escopos acima.
- **`names no product of the organisation`**: o ID do produto ou `POLAR_ORGANIZATION_ID` está errado ou pertence ao outro serviço.
- **Um preço ou uma chave de licença**: altere-o na Polar para que corresponda ao código. Quando um valor de negócio muda de propósito, altere primeiro `TIER_PRICES` ou `LICENSE_ACTIVATION_LIMITS` e, depois, a Polar.
- **`does not ask for the … checkout field`, `without requiring it`, `instead of a checkbox` ou `label differs`**: crie, associe ou corrija a [caixa de consentimento](#consent-checkbox). Quando o texto muda de propósito, altere primeiro `WITHDRAWAL_CONSENT_FIELD.label` e, depois, o rótulo na Polar.
- **`Checkout localization is off`**: ative a [localização do checkout](#checkout-language) na organização.
- **`default tax behaviour is not location`**: defina o [comportamento fiscal](#tax-behaviour) da organização como baseado na localização.
- **Um endpoint de webhook**: corrija o endpoint que a mensagem indica ou remova um endpoint que envia eventos para o host de outro ambiente.
