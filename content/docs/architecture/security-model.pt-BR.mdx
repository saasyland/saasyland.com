## Duas camadas de controle de acesso

**Guards de rota** em `src/integrations/better-auth/auth.routes.ts` rodam em `beforeLoad` e redirecionam:

| Guard                | Usado por                      | Comportamento                                                                                        |
| -------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `requireSignedIn`    | Layout de `/app`               | Redireciona para o login quando não há sessão, mantendo a página como `redirect`                     |
| `requireAdmin`       | Layout de `/admin`             | Também exige a permissão `admin: ["access"]`; caso contrário, redireciona para `/app`                |
| `redirectIfSignedIn` | Páginas de login e de cadastro | Envia o usuário autenticado para `redirect` ou para a área de trabalho dele                          |
| `redirectAfterAuth`  | `/auth/callback`               | Envia o usuário para `redirect` ou, conforme o papel, para `/admin` ou `/app` depois da autenticação |

Os guards só decidem o que o usuário vê. Quem protege os dados é o **middleware das server functions**, em `auth.middleware.ts`, porque qualquer server function pode ser chamada sem passar pela sua página:

- `authorized()` carrega a sessão da requisição e lança `UNAUTHORIZED` quando não há sessão.
- `authorized({ user: ["ban"] })` também verifica as permissões do papel definidas em `auth.access.ts` e lança `FORBIDDEN`.
- O handler recebe a sessão como `context.auth`. Operações sobre os dados do próprio chamador usam `context.auth.user.id`, nunca um ID de usuário vindo da entrada.

## Sessões

- O Better Auth armazena as sessões no D1 e usa o prefixo de cookie `saasyland`, com cookies seguros fora dos builds de desenvolvimento e de teste.
- `getRequestSession` ignora o cache de cookie e memoiza a sessão pelo restante da requisição.
- A sessão enviada ao navegador não inclui o token.
- `tanstackStartCookies` é o último plugin do Better Auth, para que os cookies definidos durante uma server function cheguem à resposta.
- Os hosts permitidos são fixos por modo de build: `saasyland.com` em produção, `preview.saasyland.com` em preview, `localhost:3000` e `127.0.0.1:3000` em desenvolvimento e, em teste, também `localhost:3020` e `127.0.0.1:3020`.

O Better Auth também cuida da verificação de e-mail (obrigatória antes do login), da redefinição de senha (que revoga as sessões existentes), do OAuth com GitHub e Google (com os tokens criptografados em repouso), da autenticação de dois fatores e da personificação de usuários pelo admin. Os identificadores de verificação são armazenados como hash.

## Rate limits

`withRateLimit(kind, limit)` conta as tentativas por operação e por IP do cliente (`cf-connecting-ip`) na tabela `rate_limit`, com um único batch atômico do D1. `RATE_LIMITS.SENSITIVE` permite <RepositoryFact name="sensitiveRateLimit" /> tentativas e `RATE_LIMITS.TOKEN` permite <RepositoryFact name="tokenRateLimit" /> a cada <RepositoryFact name="rateLimitWindowSeconds" unit="second" />. Se o armazenamento dos contadores falhar, a requisição é recusada. O rate limiter do próprio Better Auth usa a mesma tabela com o prefixo de chave `auth:`; leituras de sessão, logout e webhooks do Polar ficam isentos.

Os e-mails que um visitante pode disparar têm um segundo limite. `withinRecipientRateLimit` permite <RepositoryFact name="recipientEmailsPerHour" /> e-mails de cada tipo (verificação, redefinição de senha e confirmação da newsletter) por endereço por hora, com a chave em um hash SHA-256 do endereço, e descarta o e-mail silenciosamente além disso.

## Headers da resposta

`src/server.ts` define `SECURITY_HEADERS` (uma Content Security Policy, `Cross-Origin-Opener-Policy`, `Permissions-Policy`, `Referrer-Policy`, `X-Content-Type-Options` e `X-Frame-Options`) em toda resposta que o Worker retorna, mais `HTTPS_SECURITY_HEADERS` (`Strict-Transport-Security`) sobre HTTPS, e substitui qualquer valor que a resposta ou uma regra de `public/_headers` já tenha definido. As duas constantes ficam em `src/modules/_core/constants/api.ts`. Os arquivos servidos sem o Worker recebem os mesmos headers da regra `/*` de `public/_headers`, e `src/__test__/server.test.ts` falha quando essa regra e as constantes divergem. Veja [Segurança e hardening](/docs/features/security).

## Links de mídia

Os arquivos de vídeo ficam em um bucket R2 privado. `getVideoPlayback` exige `video: ["read"]`, e `getLessonPlayback` o nível de acesso da aula, antes de assinar um caminho, e a assinatura é um HMAC-SHA-256 com uma chave derivada de `AUTH_SECRET` por HKDF. `serveMedia` responde `403` para uma assinatura errada ou expirada. Um caminho assinado funciona como um link de portador até expirar, pelo menos <RepositoryFact name="signedMediaHours" unit="hour" /> depois de emitido, então quem o tiver pode reproduzir aquele vídeo. Veja [Cloudflare R2](/docs/integrations/cloudflare-r2).

## Erros e entrada

- Server functions que recebem entrada a analisam com um schema Zod antes de o handler rodar.
- Os endpoints do próprio Better Auth seguem as mesmas regras dos formulários: `enforceInputPolicy` em `auth.hooks.ts` roda antes de todo endpoint que aceita uma senha, um nome, um e-mail ou uma imagem e responde `400` com `VALIDATION_ERROR` quando o body não passa no schema.
- `withRequest` transforma erros inesperados em `INTERNAL_ERROR` e registra o erro original no servidor, para que detalhes internos nunca cheguem ao cliente.
- Os webhooks do Polar são verificados com `POLAR_WEBHOOK_SECRET` antes de qualquer alteração de licença.
- Os secrets são lidos de `cloudflare:workers` apenas por código de servidor: módulos exclusivos do servidor, handlers de server functions e helpers que só eles importam. `scripts/verify-build.ts` faz o build falhar quando um asset do cliente importa `cloudflare:workers`.
- As áreas privadas (`/admin`, `/app`, `/auth`, `/newsletter`) nunca são pré-renderizadas, nem as páginas de cursos, que mostram os bloqueios e o progresso de cada espectador.
