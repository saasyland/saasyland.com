## Vitest のプロジェクト

`vp test` は Vite+ を通じて Vitest を実行し、`vite.config.ts` で定義された 3 つのプロジェクトを使います。テストは対象コードの隣にある `__test__` フォルダーに置き、テスト用の API は `vite-plus/test` からインポートします。

| プロジェクト  | 環境  | ファイルパターン                                 |
| ------------- | ----- | ------------------------------------------------ |
| `node`        | Node  | `*.test.ts` と `*.test.tsx`（下の 2 種類を除く） |
| `integration` | Node  | `*.integration.test.ts`                          |
| `component`   | jsdom | `*.component.test.tsx`                           |

実際の Cloudflare アカウントやプロバイダーに接続するテストはありません。

- D1 は、チェックイン済みのマイグレーションを実行するインメモリの SQLite データベースで、KV、および `MEDIA` と `BUNDLES` の R2 バケットはインメモリのマップです。KV、各バケット、レート制限のカウンターは各テストの前にリセットされ、`createEdgeCache` が Workers のキャッシュをスタブします。
- `createServerFn` が置き換えられているため、サーバー関数は本物のミドルウェアとバリデーターを通って、プロセス内で実行されます。これは `node` と `integration` プロジェクトでの動作です。`component` プロジェクトでは jsdom がブラウザにあたるため、サーバー関数は失敗します。
- コンポーネントテストは、本物の `QueryClient` とルーターを使ってレンダリングします。
- `fetch` はネットワークではなく Resend と Polar の厳密なテストダブルに届き、それ以外のホストへのリクエストは、マシンがオフラインであるかのように失敗します。

## プロバイダーのテストダブル

`src/platform/testing/setup.ts` は各テストの前に `fetch` を置き換えます。そのため、アプリ自身の Resend と Polar の SDK クライアントは、本物のリクエストを `src/platform/testing/mocks/resend.ts` と `src/platform/testing/mocks/polar.ts` に送信します。

- プロバイダーと同じ項目をチェックします。API キーまたはアクセストークン、エンドポイントとメソッド、ボディまたはクエリを、SDK 自身のリクエストモデル（`EmailApiOptions`、`models.CheckoutCreate`、`models.LicenseKeyDeactivate`）に合わせて型付けした厳密な Zod スキーマで検証します。Polar のテストダブルは、組織に存在しない商品も、別の商品に付けたチェックアウト価格や Polar の最低価格を下回るチェックアウト価格も拒否します。
- プロバイダーと同じように応答します。Resend は、同じ `Idempotency-Key` が繰り返されると二重に送信せずに最初の結果を返し、そのキーが別のメールとともに再び届くと 409 を返します。Polar は完全な `models.Checkout`、`models.Order`、`models.LicenseKeyWithActivations` オブジェクトを返し、保持していない注文やキーには 404 を返します。
- Polar のダブルは、各機能が販売する商品とライセンスキー特典を提供します。それぞれのモジュールの `__test__/fixtures/<feature>.polar-catalogue.ts` にあり、`src/platform/testing/mocks/polar.ts` の `CATALOGUES` がインポートします。商品は ID、名前、通貨の最小単位で表した価格とその通貨、請求間隔からなり、買い切りの商品には請求間隔がありません。テストダブルはリセットのたびにカタログを投入し直すため、テストが `seedPolarCatalogue` で追加した月額プランなどの商品は、次のテストには残りません。
- ライセンスの機能のカタログはコードから作られます。プランごとの商品は ID を `POLAR_PRODUCT_IDS`、価格を `TIER_PRICES` から取り、商品ごとのライセンスキーの特典はアクティベーション数の上限を `LICENSE_ACTIVATION_LIMITS` から取ります。チェックアウトは `prices` に商品の固定価格を独自に指定でき、注文ではその価格が請求されます。
- プロバイダーが拒否するリクエストや、アプリが呼び出さないエンドポイントへのリクエストは記録され、アプリがそのエラーを捕捉した場合でも、共通の `afterEach` がテストを失敗させます。

## 統合テストのスイート [#integration-suites]

`*.integration.test.ts` ファイルは、インメモリの D1 とプロバイダーのテストダブルを相手に、サーバー側のフロー全体を検証します。

- Better Auth のスイートは、`auth.server.ts` の本物の `auth` に対して実行され、そのプラグイン、フック、レート制限、メール送信処理もすべて含まれます。`__test__/fixtures/auth.harness.ts` は、ブラウザが送るのと同じヘッダーでサインアップ、メール認証、サインインを行い、各トークンを Resend のテストダブルが配信したメールから読み取ります。
- `license-purchase.integration.test.ts` は決済とライセンスをカバーします。購入セッションの作成（プラン、国ごとの、ドル未満を切り捨てた地域価格、同意と言語、紹介情報のメタデータ、有効なライセンスがある場合の拒否）、アップグレード（支払い済みの額を差し引いた価格、差額の購入セッション、同じキーでのプランとアクティベーション数の上限の変更、アップグレードの注文自体のキーの無効化、返金されたアップグレードの巻き戻し）、続いて Better Auth の Polar エンドポイントを通る署名付きの `order.paid`、`benefit_grant.created`、`order.refunded`（一部返金と全額返金）、`benefit_grant.revoked` Webhook（順序の入れ替わり、二重配信、不正な署名を含む）、購入確認メール、そしてライセンスのアクティベーションの一覧表示と解除です。
- `license.api.integration.test.ts` は [CLI ライセンス API](/docs/features/cli-licence-api) をカバーします。本物の Webhook ハンドラーを通じて購入したライセンスについて、D1 と Polar のテストダブルを相手にすべてのエンドポイントを検証し、端末のアクティベーションの再利用、アクティベーション数の上限、返金済みと取り消し済みのライセンス、アドレスごととキーごとのレート制限、Polar の障害を扱います。すべてのレスポンスをコントラクトの `readApiResponse` で読み取り、`e2e/specs/cli-licence-api.spec.ts` は CLI と同じ方法でビルド済みの Worker を呼び出します。

## カバレッジ

`bun run test:coverage` は、`src` 全体で行、ステートメント、関数、分岐のカバレッジを <RepositoryFact name="coverageThreshold" unit="percent" /> にすることを必須とします。shadcn のプリミティブ、`src/platform/testing`、生成ファイル、型宣言は対象外です。実際の振る舞いをカバーしてください。決して実行されない分岐は、グローバルをスタブして到達させるのではなく、削除します。

## ブラウザテスト

Playwright のスペックは `e2e/specs` に、ページオブジェクトは `e2e/pages` に、フィクスチャは `e2e/fixtures` に置きます。スペックは、`test` Wrangler 環境を使う本番相当のビルドに対して実行されます。この環境では、`.wrangler/test` 内のローカル D1、KV、R2、`.env.test` のダミーシークレット、そして同じ Resend と Polar のテストダブルをインストールし、配信されたメールを公開するテスト用 Worker を使います。そのため、スペックは実際の認証リンクをたどることができます。`e2e/fixtures/license.ts` は、統合テストのスイートとまったく同じ方法で署名した支払い済みの注文を配信します。ローカルでは、Playwright がマイグレーション、シード投入、ビルド、アプリの起動を自動で行います。スイートは Chromium と WebKit で実行されます。

`e2e/journey/` のジャーニースイートは例外で、`journey.yml` が毎晩と手動でプレビューデプロイに対して実行し、実際のメール、Polar のサンドボックス、公開済みの CLI を使います。[ジャーニースイート](/docs/tooling/playwright#journey-suite)を参照してください。

上記の統合テストのスイートは、Webhook の二重配信や順序が入れ替わった配信など、まだどのブラウザーテストも実行していない多くのフローをプロセス内でテストしています。[テストカバレッジ](/docs/tooling/test-coverage)は、ブラウザーテストがビルドした Worker に対してフローを実行した場合にのみ、そのフローをカバー済みと数え、残りのフローは不足しているものとともに一覧にします。

```sh
bun run test

bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:journey
```

## CI

`.github/workflows/ci.yml` はプルリクエストとマージキューのグループで実行され、マージキューがテストしていないコミットが `main` に push されたときは `.github/workflows/deploy.yml` がそれを実行します。

1. `bun run check`：フォーマット、lint、型チェック、`check:comments`、`check:i18n`, `check:content`、`check:flows`
2. <RepositoryFact name="vitestShards" /> 個のシャードで並列に実行する `bun run
   test:coverage`。最後のジョブがそのカバレッジを統合し、しきい値と照合します
3. ブラウザーごとに 1 回のテストビルドの後、Chromium と WebKit の Playwright スイートをそれぞれ <RepositoryFact name="e2eShards" /> 個のシャードで並列に実行
4. トラフィックを処理しないバージョンとしてのプレビュー用 Worker のアップロード、`main` ではさらにプレビュー環境と本番環境へのデプロイ
