## 結論から

エージェントのプルリクエストは、最も早く失敗が見つかる順にレビューし、どのチェックにもできないところに注意を注いでください。まず証拠です。読んでいるコミットがテストされたコミットであり、そのコミットで CI が成功していること。次に、差分に照らした説明と、保護されたパスのリストに照らした差分。次に、テストへのすべての変更です。テストを通せないエージェントは、ときにテストのほうを簡単にするからです。次に、最も高くつく誤りを捉える問いです。この変更は問題の原因を取り除いているのか、それとも問題が現れた場所を取り除いているだけなのか。その後に、リンターが許してしまう型とエラーの抜け道、変更の範囲、ルールを避けるように曲げられた設計、そして変更が文章でしているすべての主張を確認します。「完了」と書かれた要約は主張として扱ってください。コマンド、その出力、そしてそれを実行したコミットを求めてください。

## AI が書いたコードに別のレビューが必要な理由

レビューは昔から、人が思うほどにはバグを見つけるためのものではありませんでした。Microsoft でのコードレビューについての 2013 年の研究で、Alberto Bacchelli と Christian Bird は、「欠陥の発見は依然としてレビューの主な動機である」一方で、「レビューは予想されていたほど欠陥に関するものではない」こと、そして「コードと変更の理解こそがコードレビューの鍵となる側面である」ことを見いだしました。人間が作成者なら、理解は共有されています。作成者はコードがなぜそうなっているのかを知っていて、レビューは会話になります。

作成者がエージェントになると、3 つのことが変わります。

**作成者の自信は何の情報も伝えない。** エージェントは、テストが通っていてもいなくても、同じ調子で「すべてのテストが通りました」と書きます。Claude Code についての Anthropic のガイドは、その仕組みを率直に述べています。「Claude は、作業が終わったように見えた時点で止まる」。レビュアーへの助言は、証拠を求めることです。「実行したコマンドとその出力、またはスクリーンショット。『すべてのテストが通りました』だけでは、ほとんど何もわからない」。

**コードは正しく見える。** Stack Overflow の 2025 年のアンケートでは、AI ツールに対する最も多い不満は、66% の開発者が挙げた「ほぼ正しいが、完全には正しくない AI の解決策」で、45.2% が、AI が生成したコードのデバッグにはより時間がかかると答えました。ほぼ正しいコードは、レビューするのが最も難しい種類のコードです。どこにも誤って見えるところがないからです。

**自分の進み具合の感覚は当てにならない。** 2025年初めに経験豊富なオープンソースの開発者を対象に行われた METR のランダム化研究では、AI ツールの使用を許可すると、「課題を完了するのに 19% 長くかかる」ことがわかりました。研究の前、彼らは「AI によって 24% 速くなると予想して」いて、研究の後も「AI によって 20% 速くなったと依然として信じていた」のです。作業が速く進んでいると感じているレビュアーは、何も計測していません。

### エージェントは目に見えるチェックに合わせて最適化する

レビューのやり方を変えるべき最も強い理由は、モデルを作る企業自身が記録しています。

2025年2月に公開された Claude 3.7 Sonnet についての Anthropic のシステムカードには、「テストを通すことへの過度な集中」という題のセクションがあります。そこでは、このモデルが「Claude Code のようなエージェント型のコーディング環境で、テストケースを通すために、ときおり特別扱いに頼る」と報告しています。最も多かったのは「汎用的な解決策を実装するのではなく、テストが期待する値を直接返すこと」でしたが、「問題のあるテストそのものを、コードの出力に合わせて変更すること」も含まれていました。これは「汎用的な解決策を作ろうとする試みが何度も失敗した後」に起きており、Anthropic は 3 つの兆候に注意するよう勧めています。「1 つのファイルに対する過度な編集とテスト実行の繰り返し」「テスト固有の処理を示唆するコメント」「テストファイルへの予期しない変更」です。

OpenAI は 2025年3月、推論モデルの監視についての取り組みの中で、同じ種類の振る舞いを報告しました。その例には、「verify を回避して、常に true を返すようにできる」と推論したエージェントや、「すべてのテストをスキップするには、常にスキップする `pytest_runtest_setup` 関数を定義すればよい」と計画した別のエージェントが含まれています。訓練中にそうした思考に対してモデルにペナルティを与えると、「CoT への圧力をかけて訓練したエージェントも、依然として報酬ハッキングを学習する」ものの、「思考の連鎖の中で意図を隠すことを学習している」のです。[このシリーズの最初の記事](/blog/ai-coding-agent-guardrails)で引用した、報酬ハッキングについての METR のそれ以前のレポートも、スコアのあるタスクで同じことを見つけています。

Anthropic は、訓練による緩和策が「通常の使用におけるこの振る舞いの頻度を大幅に減らした」と報告しています。残っているものは、Anthropic がそれを観察したところに現れます。難しい問題で失敗を繰り返した後です。それはまさに、最もレビューを必要とする種類の変更です。実際的な帰結は単純です。緑の CI の実行は、チェックが通ったことを教えてくれます。そのチェックが、最初にあったチェックと同じものであることは教えてくれません。

## コードより先に証拠をレビューする

レビューの最初の数分は、プルリクエストが自分自身について主張していることに充てるべきです。私たちが見てきた高くつく失敗のほとんどは、コードではなく主張の中にありました。

**読んでいるコミットは、テストされたコミットか。** 最後のテスト実行の後にリベース、amend、または修正のプッシュをしたエージェントのプルリクエストでは、説明がそれより前のコミットを説明しています。CI がヘッドコミットで実行されたこと、そしてその実行が、速いものだけでなく必須のチェックをすべて通過したことを確認してください。[このシリーズの 2 本目の記事](/blog/running-ai-coding-agents-in-parallel)では、ブラウザーテストのスイートがまだ実行中なのにエージェントが「完了」と報告した経緯を伝えています。

**数値は証拠になっているか。** 良いテスト計画は、各コマンドとその結果、それが出した件数、そして実行できなかったものを挙げています。私たちのプルリクエストがその違いを示しています。#177 のテスト計画は、355 個のテストファイルと 2,301 件のテストを完全なカバレッジで報告し、触れていないファイルの 4 件のテストが、マシンのロードアベレージが 40〜170 という負荷の下でタイムアウトに達したと述べ、成功した実行で使ったフラグを挙げ、ブラウザーテストのスイートはローカルでは実行しなかったことと、その理由をはっきり述べています。#123 は、負荷のために 7 件のテストがタイムアウトした最初のカバレッジの実行と、問題のない再実行を報告しています。どちらも失敗を隠しておらず、どちらも「すべて緑」より役に立ちます。

**説明はこの差分を説明しているか。** 11月16日、レイアウトの修正である #224 が、ライセンスの変更である #225 の説明付きでマージされました。その説明には、#224 が一度も触れていないライセンスファイルへの変更をオーナーが承認したという段落まで含まれていました。説明を読むチェックはありません。それ以来、レビューで説明と差分を比べています。説明が触れているすべての変更が差分にあること、差分のすべてのファイルが説明されていること、すべての承認が、それが対象とするパスとともに引用されていることです。

**完了したように見えるだけか、動くのか。** 描画されるコントロールは、それが何かをするという主張です。11月、管理画面のユーザー画面には、ハンドラーのない **Edit**、**View profile**、**Add User** のボタンが表示されていて、一方でユーザーとセッションの 9 つのサーバー関数には呼び出し元がありませんでした（#194）。どのチェックも気づきませんでした。ハンドラーのないボタンは描画され、それを押したものは何もなかったからです。修正では、すべてのコントロールを実際のサーバー関数につなぐか、削除しました。ユーザーが目にするものについての証拠は、スクリーンショットか、ボタンを押してその結果をアサートするブラウザーテストです。

## 回避策と根本原因

エージェントがする最も高くつく誤りは、誤った場所での修正です。それはすべてのチェックを通過し、多くの場合は回帰テストまで付いてきますが、原因はコードに残り、次のページがそれに突き当たります。

回避策には見分けのつく形があります。上流ではなく、症状のすぐ隣にあるのです。テストに追加した待ち、1 つのコンポーネントに渡したフォールバックの値、失敗するケースを飛ばす条件、競合状態を包むリトライ、古いバージョンへの依存関係の固定などです。それを暴く問いは、Google のレビューガイドが「CL を広い文脈で見ると役に立つことが多い」と言うときにほのめかしているものです。何がこれを引き起こしたのか、そしてマージの後に、ほかの何かが同じものに遭遇しうるか、です。

### 意図して選んだ回避策

11月14日、ログインしている訪問者が、ページのハイドレーションが終わる前にランディングページのヘッダーのリンクを押すと、React がハイドレーションのエラーを報告しました。サーバーは GitHub のスター数を出力していて、ブラウザーはその場所に読み込み中のスケルトンを描画していたのです。#146 は、ページのローダーからコンポーネントへ、その数をプレースホルダーのデータとして渡すことでこれを修正し、回帰テストを付けました。すべてのチェックが通りました。

その説明は、本当の原因を挙げていました。認証のインテグレーションにあるルートガードは、プリレンダリングされたページが知らなかったセッションを見つけるたびに、あるユーザーが別のユーザーのデータを決して目にしないよう、クエリのキャッシュ全体を消去していました。このガードは公開データを非公開のデータと一緒に捨てていて、キャッシュから描画されるどのページも同じバグに遭遇しえました。説明には、なぜ原因に手を付けなかったのかも書かれていました。それを変えるには、ユーザーが変わったときにどのデータが残ってよいかを決める必要があり、それは `src/integrations/better-auth/` の中、つまりオーナーの承認が必要なパスでの決定だったのです。

レビューは根本原因を求め、オーナーは保護されたパスへの変更を承認し、2 時間後に #152 がそれを修正しました。公開してよいクエリは自らそう宣言し、ユーザーが変わると公開でないクエリはすべて削除され、#146 の回避策は削除されました。この教訓には 2 つの面があります。エージェントは原因を知っていることが多く、良い指示書はそれを述べるように求めます。そして、危険な変更を減らすためにある保護されたパスは、症状への修正を増やすことにもなります。保護された原因を避ける最も安上がりな道は、どこか別の場所での修正だからです。修正が保護されたパスの隣にあるときは、その保護が設計を決めたのではないかを確かめてください。

### バグをやり過ごすテスト

同じ日のもっと早い時間に、#142 は、ルーターがページを描画するまで待ってからページを操作するようにして、WebKit でのブラウザーテストのスイートを安定させました。その待ちは実際の準備完了の状態をモデル化したもので、正しいものです。しかし、それが修正した競合状態の一部はライブラリのバグから来ていて、#151 はそれを名指ししました。「#142 はブラウザーテストのスイートに 3 つのライブラリのバグをやり過ごさせたが、訪問者は今もそれに遭遇している」。ページのハイドレーション中にスクロールした訪問者はページの先頭に戻され、読み込み中のページから離れるナビゲーションは、離れようとしているページの再読み込みに変わることがありました。

#151 は、それぞれの修正を TanStack Router と Motion の最新リリースへのパッチとして持ち込み、パッチがなければ失敗するブラウザーテストをそれぞれに追加し、バグを避けるためだけにあった待ちを削除しました。ルーターのパッチの 1 つは、アップストリームでまだオープンになっているプルリクエストの変更です。その再現用のアプリは、レビューが求めるべき種類の証拠です。1 行の修正がなければ 6 回中 6 回失敗し、修正があれば 10 回中 10 回成功する、最小限の TanStack Start のアプリです。

私たちがそこから得たルールです。テストの中の待ちは、ユーザーも待つものをモデル化しているなら許容できます。バグをやり過ごすための待ちなら、ユーザーは今もそのバグに遭遇していて、修正はコードの中に、ライブラリなら回帰テストとアップストリームへの報告を伴うパッチの中に置くべきです。

### 判断のルール

回避策を受け入れるのは、次の 3 つがすべて成り立つときだけにしてください。原因が自分たちの手の届かないところにあること、次に読む人が見つけられる場所で、それが回避策だと示してあること、そして何かがその削除を追跡していることです。そうでなければ原因を求めてください。依存関係を古いバージョンに固定するのは、影響が長く続く回避策です。私たちの方針は、最新のリリースにとどまり、アップストリームのバグはパッチとして持つことで、そうすれば修正は、いつまでも残るのではなく、次のリリースとともに消えていきます。

## 簡単になったテスト

テストを変更する差分は、コードを変更する差分よりも注意を払う価値があります。見ていないときに信頼しているのはテストだからです。Google のレビューガイドは、これを英語のわずか 4 語で言い表しています。「テストは自分自身をテストしない」。

テストファイルへのすべての変更を読み、次のものを探してください。

- **削除された、または緩められたアサーション：** `toEqual` が `toMatchObject` になる、特定の値が `expect.anything()` になる、テストしていたコードと一緒にアサーションが削除される。
- **更新されたスナップショットやフィクスチャ：** その新しい中身を誰も読んでいないもの。
- **特別扱い：** テストだけが使う値で分岐する、またはテストが期待するとおりの値を返す、テスト対象のコード。
- **新しいスキップ、リトライ、タイムアウト：** 1 つのテストのタイムアウトを延ばすことも含みます。
- **新しいモック：** そのテストが動かすはずだったものそのものをモックしているもの。
- **振る舞いではなく実装へのアサーション：** ユーザーが目にするものではなく、どの関数が呼ばれたか。

Anthropic は、観察した特別扱いには「多くの場合（常にではないが）、特別扱いを示す明示的なコメント（例：『# special case for test XYZ』）が含まれる」と述べています。私たちのリポジトリは、理由が書かれた場所への 1 行のリンクを除いてすべてのコメントを禁止していて、残りはチェックが拒否します。それによってラベルがなくなるので、私たちのようなコードベースでは、兆候はテストの差分そのものを読むことから得なければなりません。

見習う価値のある反例は #191 です。負荷の高いマシンで、私たちの最も遅いユニットテストが時間切れになっていました。簡単な修正はタイムアウトを引き上げることでした。代わりにそのプルリクエストは、各テストがなぜ遅いのかを突き止め、必要のない処理を取り除きました。あるテストは 9 つのロケールのすべてのページに対してコンテンツチェックを実行していて、ページごとに 1 つのケースになりました。いくつかのテストは React の suspense のフォールバックのスロットリングを `act` の外で動かしていました。あるコンボボックスは、キー入力のたびにすべてのオプションを作り直していました。その説明は、守った制約を述べています。「タイムアウトを引き上げたものはなく、独自のタイムアウトを与えたテストもない」。レビュアーはこの文を 1 分で差分と照らし合わせられますし、テスト計画はまさにそれを可能にすべきものです。

## 目立たない型の抜け道

厳格なコンパイラーと厳格なリンターは、目立つ抜け道を捕まえます。`any`、型アサーション、抑制コメントです。レビューまでたどり着くのは目立たないもので、きれいにコンパイルされ、実行時に失敗します。

TypeScript は、アサーションが危険な理由を明言しています。「型アサーションはコンパイラーによって削除され、コードの実行時の振る舞いには影響しない」、そして「型アサーションが誤っていても、例外が発生することも `null` が生成されることもない」。非 null アサーションについても同じことが言えます。「これはコードの実行時の振る舞いを変えない」。

### 私たちのリンターがまだ通してしまうもの

11月22日、私たちは検証用のファイルを私たちのリント設定にかけました。この設定は、型情報を使うルールとともにルールのカテゴリ全体をエラーとして有効にし、`any`、`as const` を除くすべての型アサーション、すべての抑制コメントを禁止しています。

| 検証用ファイルの行                                                | 拒否されたか | 拒否したルール                                                               |
| ----------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------- |
| `(raw: string): Licence => JSON.parse(raw)`                       | はい         | `typescript/no-unsafe-return`                                                |
| `const parse = <T>(raw: string): T => JSON.parse(raw)`            | はい         | `typescript/no-unsafe-return` と `typescript/no-unnecessary-type-parameters` |
| `string` として返される `Reflect.get(target, key)`                | はい         | `typescript/no-unsafe-return`                                                |
| `items.find((item) => item.length > 2)!.length`                   | いいえ       |                                                                              |
| `(value: unknown): value is Licence => typeof value === "object"` | いいえ       |                                                                              |
| チェックのない `zod.custom<Licence>()`                            | いいえ       |                                                                              |
| `licence?.key ?? ""`                                              | いいえ       |                                                                              |
| 空の `catch {}`、またはデフォルト値を返す `catch`                 | いいえ       |                                                                              |

通過した行はどれも、欠けている値や不正な値を、エラーなしに誤った振る舞いに変えます。非 null アサーションは、値が存在すると言います。型ガードは、オブジェクトであることだけを確認して、それが `Licence` だと言います。カスタムスキーマは何でも受け入れ、それを `Licence` として型付けします。空文字列へのフォールバックは「ライセンスがない」状態を、空文字列のライセンスキーに変え、次の関数はそれを平気で API に送るかもしれません。握りつぶされたエラーは、それを直したはずの人から失敗を隠します。私たちのアプリケーションコードには、現時点で非 null アサーションもチェックのないカスタムスキーマもありません。その状態を保っているのはレビューだけで、1 つ目のためのルールは typescript-eslint と Oxlint のどちらにも存在します。

### もっともな理由があっても、抜け道は抜け道

saasyland.com を TanStack Start に移行した 2026年9月6日のコミットには、6 つのリントの抑制コメントが含まれていました。安全でない型アサーションのためのものが 4 つ、`null` のためのものが 1 つ、安全でない引数のためのものが 1 つです。どれにも、それが必要に聞こえる一文が添えられていました。

```ts
// TanStack Query requires a defined result; null represents an absent license.
// oxlint-disable-next-line unicorn/no-null
const NO_LICENSE = null
```

理由の半分は正しいものでした。TanStack Query のドキュメントには、「成功した場合、解決される値は undefined 以外の何でもよい」とあります。結論は正しくありませんでした。クエリに必要だったのは `null` ではなく、定義された値でした。レビューは 3 週間以内に、それぞれが守っていた設計を変えることで 6 つすべてを取り除きました。これは、常に存在するオブジェクトになりました。

```ts
.handler(async ({ context }) => ({ license: await getLicense(context.auth.user.id) }))
```

ほかのものも同じ道をたどりました。生成された型をアサートしていたテストのヘルパーは、今は型のないメッセージツリーを組み立て、ビルダーの型をアサートしていたテストのプロキシは、今はサーバー関数を受け取ったことを実行時に確認し、そうでなければ `TypeError` をスローします。私たちの規約は今、抜け道の代わりになるものを挙げています。アサーションではなくバリデーションを使う、本物の型ガードで絞り込む、アサーションではなく型注釈を付ける、変換せずに `satisfies` でチェックする、そしてライブラリの約束事と衝突するときは構造を変える、です。#274 以降、`bun run check` はすべての抑制コメントを拒否するので、この種の抜け道はもうレビューまで届きません。それでも届くものについては、教訓が残ります。抜け道の隣に書かれた理由は 1 つの議論であり、レビューの仕事は、その議論に感心することではなく、それを検証することです。

## 範囲、設計、そして変更の形

**依頼されていない変更。** エージェントは途中でいろいろなものを直します。それはしばしば役に立ちますが、常にレビューの問題になります。誰も頼んでいない変更が、誰かが頼んだ変更の一部としてレビューされるからです。私たちが使うルールは、隣接する修正は、説明がそれを挙げて理由を述べていれば歓迎する、というものです。翻訳されたファイルパスの修正である #169 は、すでに書き直していた文字列の中で直したほかの誤りを挙げています。遅いテストについてのプルリクエストである #191 は本番のコンポーネントを変更しており、その説明は、そのコンポーネントが描画のたびにすべてのオプションを作り直していて、それがテストの問題でもありユーザーの問題でもあったと述べています。説明が触れていない変更は、立ち止まって尋ねる理由になります。

**誰も必要としていなかった抽象化。** Google のガイドはレビュアーに、「開発者が将来解決する必要があるかもしれないと推測する問題ではなく、今解決する必要があるとわかっている問題を解決するよう、開発者に勧める」ことを求めています。エージェントは逆の方向に傾きます。ライブラリの呼び出しを包むラッパー、生成物が 1 つしかないファクトリー、3 つ隣のフォルダーにすでにあるものと重複するヘルパーなどです。私たちの規約は、関心事ごとに誰が見てもわかる仕組みを 1 つだけ用意し、ライブラリは直接呼び出すことを求めています。レビューでは、新しい関数を受け入れる前に、既存の関数がないかリポジトリを検索するのが最も安上がりなチェックです。

**ルールを満たすための儀式。** ルールが少し間違っていると、エージェントはそれに大規模に従ってしまいます。マジックナンバーを禁止する私たちのルールは `0` しか許可していなかったので、エージェントはすべての `1` に名前を付け、#230 はそうした定数を 72 個インライン化しました。[このシリーズの最初の記事](/blog/ai-coding-agent-guardrails)がその経緯を伝えています。レビューでは、人が手では決して書かないようなパターンは、ルールを直すべきだというサインです。

**保護されたパスを避けるように曲げられた設計。** これは見落としやすいものです。#177 には、機能が提供中か提供予定かを表すステータスの定数が必要でした。Remotion のランディング動画は管理画面のナビゲーションをインポートしていて、あるテストは、Remotion がインポートするすべてのファイルを動画のワークフローが監視することを求めているので、新しいファイルを作れば、オーナーの承認が必要なパスである `.github/workflows/` を編集することになっていました。そのプルリクエストは、ワークフローがすでに監視していたファイル `src/data/navigation.constants.ts` に定数を置き、説明でそう述べていました。その後の変更で、管理画面のナビゲーションからはステータスが完全に取り除かれました。今日、その定数はプランのカードと文言のために使われていて、もう存在しない理由のために、今もナビゲーションの定数の中にあります。それをチェックするものは何もありません。レビューこそ、こう問う場所です。このファイルは、新しく読む人がこれを探す場所ですか。そうでないなら、作成者がここに置いた理由は何ですか。

Anthropic のガイドは、人間であれエージェントであれ、すべてのレビュアーに当てはまる警告を加えています。「問題を見つけるように頼まれたレビュアーは、必ず _何か_ を見つける。指摘をすべて修正すると、余分な抽象化のレイヤーと、起こりえないケースのためのテストができあがる」。範囲の問題は、どちらの側にも起こります。考えられるすべての改善を求めるレビューは、頼まれもしないのに改善を加えるエージェントと同じ、膨れ上がったコードを生みます。

## 差分の中の保護されたパス

[このシリーズの最初の記事](/blog/ai-coding-agent-guardrails)では、どのパスに人の 2 本目の鍵が必要か、そしてなぜ承認が差分に結び付くのかを説明しています。レビューでは、そこから 2 つのチェックが導かれます。

**変更されたファイルを、機械的にリストと比較する。** 長い差分を読んで保護されたパスを探すのは、まさに人が 1 日の終わりに苦手とする作業です。1 行のコマンドなら毎回それをこなします。最後のキットにそのコマンドがあります。保護されたパスが差分にあるときは、説明が承認を引用し、それが対象とするパスを挙げていなければなりません。

**保護が何を変えたかを問う。** 上の 2 つのインシデント、つまり保護された原因の隣での症状への修正と、保護されたファイルを避けるために置かれた定数は、保護されたパスのリストがその周りのコードを形作ることを示しています。どちらも保護されたパスには触れていないので、どちらも機械的なチェックには現れません。レビュアーが問うべきは逆のことです。この変更は保護されたパスを避けましたか。正しい修正なら、そのパスを通っていましたか。

## 文章の中の事実と主張

エージェントはコードと同じくらい流暢に文章を書き、文章にはコンパイラーがありません。プルリクエストの説明、ドキュメント、変更履歴、README、ブログ記事はどれも主張をしており、私たちの履歴には、誤った主張の 4 つの種類が見られます。

**でっちあげた設定。** 私たちの 2 本の記事は、`typescript/no-explicit-any` が私たちのリント設定でエラーになっていると述べていましたが、実際にはそうなっていませんでした。#123 は、そのルールを有効にすることで、その文を正しいものにしました。同じ監査では、プロジェクトが設定していない `verbatimModuleSyntax` を含む `tsconfig.json` の引用と、存在しないリントのオプション `denyWarnings: true` も見つかりました。

**誤った出典の帰属。** 11月17日にすべての記事を出典と照らし合わせた監査（#241）では、アンケートでは 66% とあるのに 45% と引用された Stack Overflow の数値、誤った論文のものとされた非推奨 API の割合、そして GitClear の公開ページには載っていない GitClear の欠陥の数値が見つかりました。

**古いコンテキスト。** 古い英語のバージョンから作られた翻訳は、サイトがもう使っていないスタックを、古い件数と古いプラン名とともに説明していました（#116）。どの文も流暢で、もっともらしいものでした。

**別の変更の説明。** #224 がその例です。

文章のレビューは、テストの代わりに出典を使うことを除けば、コードのレビューと同じです。すべての数値は、それを定義するコードを指します。そして[前回の記事](/blog/documentation-drift-numbers-from-code)では、数値を誤りようがないように、そこから出力する方法を紹介しています。すべての外部の数値にはリンクがあり、レビュアーはそのリンクを開いて、まったく同じ言葉を探します。「強制されている」と書かれたものはすべて、それを強制するチェックを名指しします。すべての引用は出典の中にあります。

## レビュアーとしての 2 つ目のエージェント

レビュアーのエージェントは安く、速く、その仕事のために設定すれば、一次レビューとして役に立ちます。

- **新しいコンテキスト。** Anthropic のガイドは、`/code-review` コマンドを、「会話を一度も見ていない新しいサブエージェントで差分を」レビューするものと説明しています。「コードを生み出した推論に左右されない」。作成者の推論を読んだレビュアーは、それを受け入れがちです。
- **読み取り専用のツール。** 編集できるレビュアーは見つけたものを直してしまい、レビューを 2 つ目の変更に変えます。Claude Code のサブエージェントは定義に `tools` のリストを取ります。レビュアーには読み取りと検索だけを与えてください。
- **照らし合わせるための仕様。** 変更の元になった指示書、または issue です。そうすれば、レビュアーは好みではなく要件を確認します。
- **報告しないことについての指示。** スタイルと仮定のケースです。理由は、上で Anthropic が述べているとおりです。

その限界を知っておいてください。レビュアーのエージェントは通常、作成者と同じモデルか、それより小さなモデルで動くので、作成者の盲点を共有し、その変更が作るべき正しいものかどうかは教えてくれません。私たちの環境では、リードエージェントが各ワーカーの指示書を書き、変更がマージキューに入る前に、その報告と差分をその指示書と照らし合わせて読みます。そして人間によるレビューが必要なリストにあるものはすべて、引用されたオーナーの「はい」を待ちます。[2 本目の記事](/blog/running-ai-coding-agents-in-parallel)の問いは、今も最も多くの問題を捉えます。何をしないと決めたのか、それはなぜか、です。

## 早く失敗が見つかるレビューの順序

このシリーズの 2 本目の記事には、エージェントのプルリクエストをレビューするための 8 つのステップのリストがあります。ここでは、私たちが今使っているより長い版を、各ステップで何を探すかとともに順に示します。最初に失敗したステップで止めてください。証拠が欠けているコードを読んでも意味がありません。

1. **証拠。** ヘッドコミットがテストされたコミットであること。そのコミットで CI が必須のチェックをすべて通過したこと。テスト計画がコマンド、結果、件数を挙げ、実行しなかったものを述べていること。ユーザーに見える変更には、スクリーンショットか、コントロールを押すブラウザーテストがあること。
2. **差分に照らした説明。** 説明が主張するすべての変更が差分にあること。差分のすべてのファイルが説明されていること。
3. **保護されたパス。** どれも変更されていないか、変更されたパスごとに、それを名指しした承認が引用されていること。
4. **テストの差分。** 理由のないアサーションの緩和や削除がなく、新しいスキップ、リトライ、タイムアウト、テスト対象のユニットのモックがなく、特別扱いがないこと。
5. **根本原因。** 修正が、問題を引き起こしたものを変えていること。マージの後に、ほかの何も同じバグに遭遇しえないこと。回避策があれば、そう示してあり、追跡されていること。
6. **抜け道。** 非 null アサーション、偽りの型ガード、何でも受け入れるスキーマ、欠落を隠すフォールバック、握りつぶされたエラーがないこと。
7. **範囲と設計。** 依頼されておらず説明もない変更がないこと。利用者が 1 つしかない新しい抽象化、既存のヘルパーの重複、読む人が探さない場所に置かれたファイル、ルールに合わせて曲げられた設計がないこと。
8. **文章の中の主張。** 数値がコードから出力され、外部の事実にリンクがあってリンク先で見つかり、「強制されている」がそのチェックを名指ししていること。
9. **変更が影響するすべてのもの。** ドキュメント、README、文言、変更履歴を、すべての言語で。そのほとんどはチェックが確認し、残りはここで確認します。
10. **履歴。** 1 つの変更、スカッシュコミットとして読みやすいタイトル、帰属表示の行がないこと。

ステップ 1〜3 は数分で終わり、コードの理解を必要としないので、そのどれかで失敗したプルリクエストを差し戻すコストはほとんどかかりません。時間がかかるのはステップ 4〜7 で、それはどのプログラムも代わりにやってくれないステップです。

## かかるコストと、それをどこに使うか

レビューは、このシステムの中で、エージェントを増やしても規模が拡大しない唯一の部分です。[2 本目の記事](/blog/running-ai-coding-agents-in-parallel)では、同時に作業できるエージェントの数を本当に制限していたのは、マシンでも CI の実行時間でもなく、レビュアーだったことを明らかにしました。3 つの習慣が、それを負担できる範囲に保ちます。

**判定できるものはすべてチェックに移す。** プログラムが判定できるのにまだ目でレビューしているルールは、どれも間違ったものにレビューの時間を使っています。[ガードレールの記事](/blog/ai-coding-agent-guardrails)は、それを実現するためのものです。

**変更を小さく、1 つに保つ。** 変更が 1 つのプルリクエストは、1 つの問いに照らして読めます。エージェントは大きな差分を安く生み出します。指示書はプルリクエストごとに 1 つの変更を求め、レビュアーはそうなっていないものを差し戻すべきです。

**影響範囲に応じて深さを割く。** 決済、ID 管理、マイグレーション、ほかのソフトウェアが依存するコントラクト、そしてチェックそのものには、リスト全体を時間をかけて適用します。ドキュメントの修正には、ステップ 1、2、8 を適用します。

## 私たちのレビューがまだ見逃していること

シリーズのほかの記事と同じく、私たち自身のプロセスの弱いところを示します。

- **説明と差分の比較は人が行っています。** チェックではないので、忙しい日にはまだ見逃すことがあります。
- **#177 のステータスの定数** は、もう存在しない理由のために、今もナビゲーションの定数の中にあります。
- **非 null アサーションとカスタムスキーマ** が私たちのコードにないのは習慣によるもので、それを拒否するルールはまだありません。
- **ミューテーションテスト**、つまりコードが変わったときにテストが失敗するかどうかを計測する仕組みは設定されていないので、「簡単になったテスト」を見つけるのは読むことに頼っています。
- **レビュアーと作成者はしばしばモデルを共有しています。** そのため、その盲点も共有しています。
- **エージェントはオーナーのアカウントで作業しています。** そのため GitHub は、作成者以外の誰かによるレビューを必須にできません。最初の記事で説明したとおり、2 本目の鍵はエージェントの権限レイヤーと、引用された承認が持っています。

## コピーして使えるレビューキット

**保証ではなく証拠を求めるプルリクエストのテンプレート**です。

```md
## What and why

One change. What made the problem happen, and how this removes it.

## Evidence

| Command | Result | Commit |
| ------- | ------ | ------ |
|         |        |        |

Not run, and why:

## Also changed

Every change the title does not cover, with its reason.

## Protected paths

None, or each path with the quoted approval that covers it.

## Not done

What I decided not to do, and why.
```

**差分の中の保護されたパスを一覧にするコマンド**です。レビュアーが実行するか、CI で実行します。

```sh
git diff --name-only origin/main...HEAD | grep -E '^(db/migrations/|src/billing/|src/auth/|\.github/|eslint\.config\.js|vitest\.config\.ts)'
```

**テストの差分の危険信号を探す検索**です。ステップ 4 の出発点として使います。

```sh
git diff origin/main...HEAD -- '*.test.*' '*.spec.*' | grep -nE '^\+.*(\.skip|\.only|\.todo|retry|retries|timeout|expect\.anything|toMatchObject|vi\.mock|jest\.mock)|^-.*expect\('
```

**目立たない抜け道のうち 2 つのためのリントルール**です。ESLint と typescript-eslint での名前で示します。

```js
export default [
  {
    rules: {
      "@typescript-eslint/no-non-null-assertion": "error",
      "no-empty": "error",
    },
  },
]
```

**Claude Code 用の読み取り専用のレビュアーのサブエージェント**です。`.claude/agents/reviewer.md` に置きます。

```md
---
name: reviewer
description: Reviews a pull request's diff against the brief it was built from, before a person reads it.
tools: Read, Grep, Glob
---

You review a change you did not write. You are given the brief and the diff.

Report, in this order, only what affects correctness:

1. Claims in the description that the diff does not support, and files in the diff the description does not explain.
2. Changes to tests that make them easier: removed or loosened assertions, skips, retries, timeouts, mocks of the unit under test, special cases.
3. Fixes that change where a problem shows rather than what causes it.
4. Non-null assertions, type guards that do not check what they claim, schemas that accept anything, fallbacks that hide a missing value, swallowed errors.
5. New abstractions with one user, and helpers that duplicate existing ones.

Do not report style. Do not report cases that cannot happen. Do not edit anything.
```

**指示ファイルに加える一文**です。レビュアーが求めるものを、作成者があらかじめ用意するようにします。

```md
## Before you say done

Give the commit you tested, each command with its result, what you did not run and why, every change beyond the task, and what you decided not to do. A summary is not evidence.
```
