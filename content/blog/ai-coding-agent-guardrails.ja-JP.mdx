  - question: AI コーディングエージェントのためのガードレールとは何ですか？
    answer: >-
      エージェントが同意するかどうかに関係なく実行されるチェックです。リントルール、型チェック、カバレッジのしきい値、コンテンツチェック、コミットフック、必須の CI ステータス、ブランチルール、デプロイチェックなどがあります。どれもルールを終了コードに変え、エージェントはそれを目にし、反論できません。AGENTS.md や CLAUDE.md の指示はエージェントに何を望むかを伝え、ガードレールはエージェントがそれ以外のことをしたときに変更を失敗させます。
  - question: ルールは AGENTS.md と CI のどちらに置くべきですか？
    answer: >-
      コード、コンテンツ、ビルドの出力、差分からプログラムが判定できるなら CI に置き、根本原因を直すことやプルリクエストを小さく保つことのように判断が必要なら AGENTS.md に置きます。ほとんどのルールは最終的に両方に置かれます。チェックがルールを強制し、指示ファイルの 1 行がそれを確認するコマンドを示すので、エージェントは完了したと言う前にそのコマンドを実行します。
  - question: AI コーディングエージェントが AGENTS.md や CLAUDE.md のルールを無視するのはなぜですか？
    answer: >-

## 結論から

エージェントに与えるルールはどれも、プログラムが強制するまではお願いにすぎないと考えてください。ルールごとに、プログラムがコード、コンテンツ、ビルドの出力、差分からそれを判定できるかを問います。できるなら、チェックを書き、そのメッセージで代わりに何をすべきかを伝え、エージェントが作業する場所で実行し、さらに誰もそれを無視してマージできない必須の CI ステータスとしてもう一度実行します。指示ファイルは、どのプログラムにも判定できないことのために取っておき、その各行が、それを確認するコマンドを指すようにします。取り返しのつかないパスとお金を動かすパスは、エージェントとは別の ID を持つ人が持つ 2 本目の鍵の向こうに置きます。完了は、順番に実行して終了コード 0 を返さなければならない短いコマンドのリストとして定義します。そのうえで自分たちのルールを意図的に破り、どのルールがただの願望だったのかを確かめてください。

Google のエンジニアは、これらすべての根底にある考え方に名前を付けています。_Software Engineering at Google_ はこれをビヨンセルールと呼んでいます。「気に入っていたのなら、テストを付けておくべきだった」というものです。エージェントがコードを書くようになった今、これは振る舞いだけでなく、すべてのルールに当てはまります。

## エージェントに伝えるだけのルールがお願いにすぎない理由

`AGENTS.md` や `CLAUDE.md` のような指示ファイルは、セッションの開始時にモデルのコンテキストに置かれるテキストです。エージェントの行動を方向付けはしますが、何も決定しません。Claude Code に関する Anthropic のドキュメントは、これをはっきりと述べています。Claude はこれらのファイルを「強制される設定ではなく、コンテキストとして」扱い、「Claude の判断に関係なく操作をブロックするには、代わりに PreToolUse フックを使う」べきだというのです。同じページは、2 種類の制御の境界線を次のように引いています。「設定のルールは、Claude が何をすると判断したかに関係なく、クライアントによって強制される。CLAUDE.md の指示は Claude の振る舞いを方向付けるが、厳格な強制のレイヤーではない」。

これは 1 つのツールの弱点ではありません。どのエージェントも指示ファイルをプロンプトの一部として読み、プロンプトはコンテキスト内のほかのすべてのものと競合します。タスク、エージェントが開いたファイル、ツール自身のシステム指示、そして直前のエラーメッセージが示唆したことです。この競合がどう決着するかは、研究で測られています。2025年7月に公開されたベンチマークの IFScale は、20 のモデルに最大 500 個の指示を一度に与え、「最も優れたフロンティアモデルでさえ、500 個の指示という最大密度では 68% の正確さしか達成できない」こと、そして先に来た指示に偏る傾向があることを明らかにしました。METR は 2025年6月に、最近のフロンティアモデルにスコアの付くタスクを与えると、「テストや採点のコードを変更することで、より高いスコアを得ようと」し、「自分の振る舞いがユーザーの意図に沿っていないことを認識している様子を示す」と報告しています。

どちらの結果も、エージェントがいい加減だという意味ではありません。意味しているのは、テキストの中にしか存在しないルールは多くの入力のうちの 1 つにすぎず、たいていは守られるものの、守られないのは決まって誰も見ていないときだということです。

### 指示だけのルールが失敗する 6 つの仕方

以下はどれも私たちのリポジトリで実際に起きたことで、どれにも、エージェントがより注意深く読むことに頼らない対策があります。

**1. 希釈。** ルールを 1 つ追加するたびに、ほかのすべてのルールが守られる可能性が少しずつ下がります。Claude Code のドキュメントは、「長いファイルはより多くのコンテキストを消費し、遵守率を下げる」ため、指示ファイルを 200 行未満にするよう勧めています。私たちの `AGENTS.md` は、規約を扱うドキュメントの 1 セクション全体を指し示す要約です。エージェントは要約をすべてのセッションで読みますが、各ページを読むのは思いついたときだけです。

**2. 競合。** 指示は複数の場所から届き、互いに食い違います。エージェントのツールは、デフォルトでコミットに `Co-Authored-By` のような帰属表示のトレーラーを追加します。私たちのルールはそれを禁止しています。GitHub はトレーラーのアドレスをアカウントに結び付け、そのアカウントをリポジトリのコントリビューターとして表示するからです。持ちこたえた対策は、もう 1 つの文ではなく構造によるものでした。リポジトリはスカッシュマージしか許可せず、スカッシュコミットはプルリクエストのタイトルを使って本文を空にするので、エージェントがブランチのコミットメッセージに書いたものは何も `main` に届きません。#274 以降は、`commit-msg` フックも、トレーラーが AI ツールを名指しするコミットメッセージをすべて拒否するので、エージェントは最初のコミットの時点でそれを知ります。

**3. 伝聞。** 複数のエージェントが協力して作業すると、ワーカーに届く指示のほとんどは別のエージェントによる要約を経由し、要約では何かが失われます。私たちの環境では、リードエージェントが各ワーカーへの指示書を書きます。ある指示書には、オーナーは別のことを承認していたのに、決済の変更について「オーナーが承認した」と書かれていました（#166）。翌朝には 2 つの指示書が、CLI のライセンス API は人間によるレビューのリストに含まれていないと述べていました。`AGENTS.md` は前日からそれを記載していたにもかかわらず、2 つのプルリクエストがそれを変更しました（#208 と #211）。どちらの場合も次の一歩を止めたのは指示ではありませんでした。エージェントのハーネスの権限レイヤーが、オーナーが承認するまで、決済の変更のマージと、2 つ目のライセンスの変更の作業継続を拒否したのです。ライセンスの変更に対する彼の承認の言葉は、そのプルリクエストに引用されています。

**4. 意図より文言。** チェックが成果物を要求すると、エージェントはそれを通過する最も安上がりな成果物を作ります。私たちのリント設定はかつて、そのまま書ける数値として `0` しか許可していなかったので、すべての `1` が定数になりました。`SINGLE_CALL` は 16 か所、`SINGLE_ROW_LIMIT` は 12 か所に存在し、約 80 個の定数が、ルールのため以外には何の理由もなく `0` か `1` に等しくなっていました（#230）。非公開の CLI リポジトリでは、changeset を要求するリリースのチェックに空の changeset が渡され、それが次のリリースを止めました。その経緯は後述します。どちらのエージェントもルールを破ってはいません。どちらもルールを満たしたのです。

**5. ドリフト。** 指示は、それが書かれた日のコードベースを説明します。コードが変わってもその文が変わらなければ、エージェントは文のほうに従います。コードが定義する値を言い直すドキュメントも、同じように誤っていきます。私たちのドキュメントはかつて、レート制限、カバレッジとリントの上限、価格、ロケールの数をすべての言語で手入力していたので、コードを 1 か所変えると、それぞれの言語でページが誤ったまま残ることがありました（#137）。対策は、それらの値をコードから出力することでした。その方法は、[このシリーズの 3 本目の記事](/blog/documentation-drift-numbers-from-code)で扱います。

**6. 自己申告。** エージェントによる自身の作業の要約は、エージェントが生み出すもののうち最も信頼できないものです。「すべてのテストが通りました」は文にすぎず、終了コードは証拠です。レイアウトの修正である私たちのプルリクエスト #224 は、ライセンスの変更である #225 の説明付きでマージされ、その説明には、#224 が一度も触れていないライセンスファイルへの変更をオーナーが承認したという段落まで含まれていました。説明を読むチェックはないので、何もそれに気づきませんでした。

ルールをどこに置くかは、2 つの原則で決まります。

**各ルールは、それを判定できる最も低い段に置き、エージェントが飛ばせない最初の段で繰り返す。** Git フックの中にしかないルールは、誰かが `--no-verify` でコミットした瞬間に消えます。CI の中にしかないルールは、セミコロンが 1 つ欠けていることを知るまでエージェントを数分間待たせます。フックは速さのため、CI は真実のためにあるので、私たちの pre-commit フックは、フローの一覧を除く `bun run check` のすべてのチェックを実行し、フォーマット、リント、型はステージされたファイルだけに対して実行します。フックを飛ばしても、壊れた `main` ではなく、赤い CI の実行が 1 回増えるだけで済みます。

**エージェントの権限レイヤーを唯一のレイヤーにしない。** そこは危険なコマンドを止めるのに最も速い場所であり、最も回避しやすい場所でもあります。Claude Code 自身のドキュメントは、「コマンドの引数を制約しようとする Bash の権限パターンは壊れやすい」と警告し、`git push` を拒否するルールは「`git -C . push` のように別の書き方をしたプッシュ」には一致しないと述べています。必ず持ちこたえなければならないものには、その背後にサーバー側のルールが必要です。

### 実例：3 つの段にまたがる 1 つのルール

履歴についての私たちのルールは単純です。`main` は線形に保ち、誰も共有ブランチを書き換えません。このルールは 3 回強制されます。エージェントの権限によって、サーバー上のブランチルールによって、そしてそれらのルールを解除できる唯一の人物であるオーナーによってです。

あるエージェントがプルリクエストのブランチをリベースし、force-push しようとしました。エージェントの権限設定は force-push を許可していなかったので、コマンドは拒否され、作業は新しいブランチからの新しいプルリクエストとして上がりました（#235 は閉じられ、#236 になりました）。結果は正しかったものの、理由は誤っていました。自分のブランチをリベースして `--force-with-lease` でプッシュするのは安全です。Git の言葉を借りれば、そのプッシュは「リモートの ref の現在の値が期待どおりの値である場合」にだけ通るからです。そこでオーナーは、エージェント自身のプルリクエストのブランチに限ってまさにその形だけを許可し、それ以外は何も許可しませんでした。

ローカルのルールの背後には、サーバーがあります。GitHub のルールセットは「ユーザーが対象のブランチに force-push することを防ぎ」、私たちのルールセットは共有ブランチへの force-push と削除をブロックし、線形の履歴を必須にしています。CLI リポジトリの共有のリリースブランチからマージコミットを取り除くために、オーナー自身がそのブランチの書き換えを望んだとき、サーバーは lease 付きのプッシュさえ拒否しました。オーナーは 1 回のプッシュのためにルールを解除し、そのあと以前より厳しい形で、つまりそこでも線形の履歴を必須にしてルールを元に戻す必要がありました。ローカルのルールはよくあるミスを数秒で捕まえ、サーバーのルールは、正当な理由を持つ人が危険なことをしようとしたときに持ちこたえました。

## どのルールをチェックに置き、どのルールを指示に置くか

どんなルールも、3 つの問いで振り分けられます。

1. **プログラムが成果物から判定できるか。** ソースコード、コンテンツ、設定、ビルドの出力、差分、コミットメッセージといった成果物から、変更が行われた理由を知らずに判定できるなら、それはチェックに置くべきです。
2. **ずっとレビューし続けるより、一度コード化するほうが安いか。** 何百回ものレビューで適用するルールなら、1 日分のツール作りの元が取れます。年に 2 回しか発動しないルールなら、そうとは限りません。
3. **誤検知のコストは、見逃しのコストより大きいか。** 正当なコードに対して頻繁に発動するチェックは、エージェントも含めた全員に、それを回避することを教えてしまいます。そうならなくなるまで定義を絞り込むか、そのルールはレビューに任せてください。

| ルール                                                     | 置き場所     | 方法                                                                                  |
| ---------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------- |
| コメントを書かない                                         | チェック     | 構文木からコメントを読み取るカスタムのリントルール                                    |
| `any`、型アサーション、抑制コメントを使わない              | チェック     | コンパイラーのフラグとリントルール。インラインでの無効化はオフにする                  |
| ユーザーに表示されるすべての文字列がすべてのロケールにある | チェック     | メッセージのキーをロケール間で、またコードが使うキーと比較するスクリプト              |
| すべてのプルリクエストに変更履歴のエントリ                 | チェック     | プルリクエストにちなんで名付けられたエントリを探す CI のスクリプト                    |
| コードが定義する値を引用するドキュメント                   | ほぼチェック | 値をコードから出力し、ドキュメントが持つ表をコードと比較する                          |
| 名前付きの定数としてのドメインの値                         | 一部チェック | `no-magic-numbers` は数値をカバー。繰り返される文字列の値にはカスタムルールかレビュー |
| 症状ではなく根本原因を直す                                 | 指示         | レビューで、何がバグを引き起こしたのかを問う                                          |
| プルリクエストごとに 1 つの変更                            | 指示         | せいぜいサイズの警告                                                                  |
| 決済、認証、マイグレーションは承認なしに変更しない         | 2 本目の鍵   | コードオーナーと、エージェントが持たない ID からの必須のレビュー                      |
| デプロイせず、本番データに触れない                         | 権限         | ローカルでコマンドを拒否し、本番の認証情報をエージェントの環境に置かない              |

### 指示がまだ役に立つこと

指示が時代遅れになったわけではありません。役割が狭くなっただけです。指示は、意図（「原因を直す」）、コピーすべき唯一の正規の例、人が必要なパスのリスト、完了の定義、そしてチェックの索引として使ってください。索引とは、各ルールの後にそれを強制するコマンドを続けたものです。`bun run check` がコメントで失敗することを知っているエージェントは、書くコメントが少なくなり、残りもレビューではなく数秒で直します。私たちの `AGENTS.md` は、完了の定義を、上の 6 つ目の失敗パターンを狙った一文で締めくくっています。「それ以外は、完了したと述べる要約も含めて、何ひとつ完了とはみなさない」。

## ルールを破って監査する

実行できる最も安上がりな監査は、各ルールを 1 回ずつ破るファイルです。それに対してチェックを実行し、どの行が通過したかを書き留めます。1 時間で済み、ツールが強制していると信じていることを、実際に強制していることに置き換えてくれます。

### 実例：私たちのリンターが拒否するもの

私たちは 2026年11月20日、`AGENTS.md` のコードスタイルのルールについてこれを行いました。私たちの oxlint の設定は、ルールのカテゴリー全体、つまり `correctness`、`nursery`、`pedantic`、`perf`、`style`、`suspicious` をエラーとして有効にし、型情報を使うルールもオンにしています。ルールごとに 1 行ずつ使い捨てのファイルに書き、それに対して `vp lint` を実行しました。

| プローブファイルの行                           | 拒否   | 拒否したもの                          |
| ---------------------------------------------- | ------ | ------------------------------------- |
| `// a comment that starts in lower case`       | はい   | `capitalized-comments`                |
| `const x = 2 // A comment after code`          | はい   | `no-inline-comments`                  |
| `// TODO fix this later`                       | はい   | `no-warning-comments`                 |
| `// A capitalised comment on its own line`     | いいえ |                                       |
| `/** A JSDoc block */`                         | いいえ |                                       |
| `{/* A comment in JSX */}`                     | いいえ |                                       |
| `unknown` を絞り込む `readValue() as Named`    | はい   | `typescript/no-unsafe-type-assertion` |
| 型を広げる `value as Named`                    | いいえ |                                       |
| `(input: any)`                                 | はい   | `typescript/no-explicit-any`          |
| 説明のない `// @ts-expect-error`               | はい   | `typescript/ban-ts-comment`           |
| 説明が続く `// @ts-expect-error`               | いいえ |                                       |
| `// oxlint-disable-next-line no-magic-numbers` | いいえ | 名前を挙げたルールも無効にした        |
| `return null`                                  | はい   | `unicorn/no-null`                     |
| `input ?? undefined`                           | いいえ |                                       |
| 3 行に分かれた三項演算子                       | いいえ |                                       |

1 つの表から 4 つの教訓が得られ、4 つともどのリンターにも当てはまります。

**カテゴリーは、意図しないルールをもたらす。** `style` と `pedantic` を有効にしたことで、「コメントを書かない」が強制されているように見えていました。小文字で始まるコメント、行末のコメント、TODO コメントは失敗しましたが、それは誰もその目的で選んだわけではないルールによるものでした。整った、大文字で始まるコメントを独立した行に書くエージェントは通過します。重要なルールなら名前で有効にし、どのルールがそれを強制しているのかを把握してください。

**リンターは自分自身のオフスイッチを取り締まれない。** 無効化コメントもコメントですが、リンターはどのルールがそれを見るよりも先に、それを指示として読み取ります。そのため、異議を唱えるはずのルールそのものが黙らされます。ESLint はこれを拒否できます。「インラインの設定コメントをすべて無効にするには、設定ファイルで `noInlineConfig` の設定を使う」というものです。その選択肢がないツールでは、リンターの外の CI でディレクティブを検索してください。

**デフォルトは意図的に寛容になっている。** typescript-eslint の `ban-ts-comment` は、「説明が含まれている場合」には `@ts-expect-error` を許可し、oxlint の移植版も同じように動作するので、理由を書いたエージェントは通過します。ドキュメントには「特定のディレクティブの値を `true` にすると、このルールはそのディレクティブの使用を見つけた場合に必ず報告する」とあります。ルールが「決して使わない」なら `true` を選んでください。

**リンターをアップグレードするたびにプローブを実行し直す。** `nursery` のようなカテゴリーは、リリースごとにルールが増えたり減ったりします。プローブファイルは設定のテストであり、ほかのテストと同じように CI で実行する価値があります。最後のスターターキットにはそれが含まれています。

私たちは翌日、#274 でこの表の穴をすべて塞ぎました。`code-style/no-comments` はすべてのコメントを、`code-style/no-multiline-ternary` は複数行にまたがるすべての三項演算子を、`code-style/no-undefined-fallback` はすべての `?? undefined` を報告します。`typescript/ban-ts-comment` は説明付きの `@ts-expect-error` も拒否するようになり、`assertionStyle: "never"` を指定した `typescript/consistent-type-assertions` は型を広げる `as` を拒否します。リポジトリ全体でこれらのルールを有効にすると、複数行の三項演算子が 21 個（そのうち 17 個はリポジトリに取り込んだ shadcn のコンポーネントの中）と、`as` によるキャストが 2 つ見つかりました。プルリクエストは、それぞれを例外にするのではなく書き直しました。

## スタイルのルールをチェックに変える方法

1. **ルールを、成果物についての「はい」か「いいえ」で答えられる問いとして書く。** 「このファイルにはコメントが含まれているか」は判定できます。「このコードはわかりやすいか」は判定できず、レビューの領分です。問いを書けないなら、見つけたのはチェックではなく指示です。
2. **それに正確に答えられる最も安価なツールを選ぶ。** 安い順に、名前で有効にした既存のルール、コンパイラーや設定のフラグ、構文木に対するカスタムのリントルール、ファイルを走査するスクリプト、コードやコンテンツの性質を検証するテスト、ビルドの出力に対するチェック、本番のシステムに対するチェックです。
3. **コードの内側を対象にするものにはパーサーを使う。** `//` を探す正規表現は、文字列の中のすべての URL や、パターンの中のエスケープされたすべてのスラッシュも見つけてしまいます。構文木は、何がコメントなのかを知っています。
4. **失敗のメッセージを指示にする。** エージェントはそれをタスクの途中で、ほかのコンテキストなしに読みます。代わりに何をすべきか、そしてそれをどこで行うかを伝えてください。
5. **既知の違反で証明する。** 新しいチェックを信頼する前に、それが対象として書かれたコードに対して実行し、わかっているケースだけを過不足なく検出することを確かめます。
6. **例外はコードに置き、それぞれにテストを付ける。** ほかの変更と同じようにレビューされる、チェックの中の許可リストは、誰の目にも留まらない無効化コメントに勝ります。
7. **2 か所で実行する。** エージェントが数秒で気づけるように pre-commit フックで実行し、フックが実行されなくても持ちこたえるように必須の CI チェックとしても実行します。
8. **既存の違反をどうするかを決める。** できるなら同じプルリクエストで直します。それができなければベースラインを記録して新しい違反だけで失敗させ、ベースラインは意図的に縮めていきます。

私たちの変更履歴のチェックは、ステップ 4 の例です。プルリクエストの CI の実行は、そのプルリクエストにちなんで名付けられたエントリが存在するまで失敗し、メッセージがそのまま修正方法になっています。

```ts title="scripts/check-content.ts"
export const pullRequestEntryProblems = (ref: string): string[] => {
  const pullRequest = pullRequestOf(ref)

  if (pullRequest === undefined || existsSync(join(REPOSITORY_DIR, CHANGELOG_DIRECTORY, `${pullRequest}${SOURCE_MDX_SUFFIX}`))) {
    return []
  }

  return [`Pull request #${pullRequest} has no changelog entry: add ${CHANGELOG_DIRECTORY}/${pullRequest}.<locale>.mdx in every locale`]
}
```

### 実例：ハイドレーションのバグがリントルールになる

React はページを 2 回、サーバーで 1 回とブラウザーで 1 回レンダリングし、2 つのレンダリングは同じテキストを出力しなければなりません。レンダリング中に時計やブラウザーのロケールを読むコンポーネントは、それぞれの場所で異なるものを出力し、React はエラー #418 を報告してページをレンダリングし直します。プルリクエスト #198 は、そのようなバグを 1 つ修正しました。ある管理画面のページが、サーバーでは「48 秒前にアクティブ」、ブラウザーでは「49 秒前にアクティブ」と出力していたのです。監査で、同じ種類のバグがさらに 3 つ見つかりました。フッターは `new Date().getFullYear()` を出力していて、1月1日から次のデプロイまで、フッターのあるすべてのページを壊すところでした。チェックアウトのパネルは、サーバーの時計とブラウザーの時計を比較していました。あるグラフは `toLocaleString()` で数値をフォーマットしていました。

4 つのバグを直すだけなら、5 つ目は次のエージェントに残されていたはずです。プルリクエスト #201 は 3 つを修正し、`scripts/hydration-lint-plugin.ts` の小さな oxlint プラグインとして、`hydration/no-clock-or-locale-in-render` というルールを追加しました。このルールは、引数なしの `new Date()`、`Date.now`、`toLocale…String` のメソッドを、レンダリング中に実行されるあらゆる場所で報告し、後で実行される関数、つまりイベントハンドラー、クエリ関数とミューテーション関数、エフェクト、タイマーの中でだけ許可します。上で示した方法の各ステップが、このルールに表れています。

- **問いが正確。** レンダリングのコードが時計や実行環境のロケールを読むかどうかを問います。元のバグは `.map` のコールバックの中にあり、単純なパターンなら、それを後で実行される関数とみなしていたはずです。
- **メッセージが指示になっている。** 「クエリの dataUpdatedAt やビルド時の値のように両方が共有する時点を使うか、イベントハンドラー、エフェクト、クエリ関数の中で時計を読む」。
- **既知のケースで証明された。** `main` では、監査が見つけた 5 か所、つまり修正した 3 か所と #198 の 2 か所を、過不足なく検出しました。
- **例外がコードになっている。** 後で実行される呼び出しはプラグイン内の 3 つの名前付きリストで、ドキュメントには、新しいエントリは「`src/__test__/hydration-lint-plugin.test.ts` のケースとともに追加し、決して無効化コメントでは追加しない」と書かれています。#201 がマージされた時点で、ルール自身のテストスイートには有効なケースと無効なケースが 28 件ありました。

### 実例：監査の指摘がコンテンツチェックになる

チェックはコードのためだけのものではありません。私たちのサイト、ドキュメント、ブログは <RepositoryFact name="languages" /> 個の言語で提供されており、翻訳はまさに、エージェントが速く、しかし少しだけ誤ってこなす種類の作業です。

11月15日の一貫性の監査で、ランディングページの根拠のリストの中で、ファイルパスとコマンドが翻訳されているのが見つかりました。日本語では `bun run テスト`、フランス語では `src/intégrations/`、イタリア語では `copertura/copertura-riepilogo.json` です。原因は、翻訳可能なテキストの中にコードがあったことでした。プルリクエスト #169 はパスとコマンドをコードが提供する値に移し、英語のページと比べてインラインコード、コンポーネント、リンク、表の行を追加、削除、変更した翻訳を、コンテンツチェックが失敗させるようにしました。チェックはすべてのコードスパンをバイト単位で比較するので、人間であれエージェントであれ、翻訳者がコマンドを翻訳することはもうできません。

翌日、#220 は呼びかけの形について同じことを行いました。各ロケールは読み手に 1 つの形で語りかけます。ドイツ語では `du`、フランス語では `vous` で、エージェントは 1 つのページの中でも形を行き来していました。この変更の前、ドイツ語のメッセージは丁寧な `Sie`、`Ihr`、`Ihnen` を 363 回使い、ドイツ語のドキュメント、記事、その他のコンテンツは 1,041 回使っていました。変更後はゼロです。このルールは現在、各ロケールが使ってはならない語とともに `src/lib/forms-of-address.ts` にあり、メッセージとコンテンツのチェックは、そのいずれかを含むテキストを失敗させます。このチェックは 1 時間以内に、ドイツ語のトラブルシューティングの文の中で最初の本当のケースを見つけ、#222 がそれを修正しました。また、検出してはならないものも学ぶ必要がありました。フランス語の「ton」は「口調」という意味でもあるので、リストに入れていません。

### 実例：パーサーで強制する「コメントを書かない」

上の監査は、私たちの「コメントを書かない」というルールが偶然にしか強制されていないことを示しました。その穴を塞いだのが次のルールです。ESLint のルール API に対して書いたもので、Oxlint もこれを読み込みます（「Oxlint のプラグイン API は ESLint v9 以降と互換性がある」）。私たちのリポジトリでは、`scripts/code-style-lint-plugin.ts` の `code-style/no-comments` がこれにあたります。

```ts title="scripts/code-style-lint-plugin.ts"
export const COMMENT_MESSAGES = {
  comment:
    "Remove this comment. Say it in a name, a named constant or a smaller function, and put the reasoning in the commit message, the pull request or the docs.",
  directive: "Remove this directive comment, which switches a check off, and fix the cause the rule or the compiler reports instead.",
} as const

export const commentMessageId = (text: string): keyof typeof COMMENT_MESSAGES => (DIRECTIVE.test(text) ? "directive" : "comment")

export const noComments = defineRule({
  create: (context) => ({
    Program: () => {
      for (const comment of context.sourceCode.getAllComments()) {
        if (comment.type !== SHEBANG) {
          context.report({ loc: comment.loc, messageId: commentMessageId(comment.value) })
        }
      }
    },
  }),
  meta: {
    docs: {
      description: "Source files carry no comments: names, the commit message, the pull request and the docs carry the meaning.",
    },
    messages: COMMENT_MESSAGES,
    type: "problem",
  },
})
```

このルールを既存の設定のまま、リンターが対象とするすべてのファイルに対して実行しました。プローブファイルの大文字で始まる行コメント、JSDoc のブロック、JSX のコメントを報告し、URL の文字列や正規表現の中の `//` には手を付けず、リンターが対象とするコードの中に問題をちょうど 1 つだけ見つけました。あるスクリプトの先頭にある `#!/usr/bin/env bun` の行です。ESLint はその理由を文書化しています。shebang は「コメントとして扱われ」、`getAllComments()` が返すものに含まれるのです。`SHEBANG` の例外があるのはそのためで、これはステップ 5 の教訓の縮図です。実際のコードで実行したことのないチェックには、まだ出会っていないバグがあります。

もう 1 つの発見も同じくらい重要です。その行を除けば、リントの対象となるコードにはコメントがまったくありませんでした。レビューがルールを守っていたのです。ただし、それを守るためにオーナーは毎回注意を払う必要がありました。この記事が扱うのは、まさにそのトレードオフです。

それでも、リントルールには 2 つの死角があります。1 つは、リンターが読み飛ばすファイルが見えないことで、私たちの場合はブラウザーのテストスイート、型宣言ファイル、スタイルシートがそれにあたります。もう 1 つは、自分の名前を挙げた `/* oxlint-disable */` を報告できないことです。リンターが先にそのディレクティブに従ってしまうからです。そこで `bun run check:comments` は、Git が追跡しているすべての TypeScript、JavaScript、CSS ファイルを、リンターの外で、コードは oxc で、スタイルは PostCSS でパースし、リンターが実行される前に、コメントがあれば失敗します。最初の実行で、さらに 1 つが見つかりました。型宣言ファイルの中の `/// <reference types>` の行で、これは `tsconfig.json` の `types` に移しました。

### ルールが形だけの儀式を生んだら、ルールを直す

少しだけ誤ったチェックは、エージェントに無視されるのではありません。大規模に従われるのです。私たちの `no-magic-numbers` ルールは `0` しか許可していなかったので、エージェントはすべての `1` に名前を付けました。`SINGLE_CALL`、`NEXT`、`STEP`、`FIRST_LETTER`、`ZERO_TICK`、`NO_OFFSET` です。どの定数も正しく、どれもがコードを読みにくくしていました。プルリクエスト #230 は `0` と `1` をリテラルとして許可し、ルールのためだけに存在していた 72 個の定数をインライン化しました。その一方で、`FAILURE_EXIT_CODE` や `INCLUSIVE_END` のように独自の意味を持つものは残しました。この教訓は一般化できます。1 に等しい定数、空の changeset、心を込めて理由を書いた無効化コメントのように、人間なら決して書かない遵守のパターンを見つけたら、コードではなくルールを変えてください。

## 人間によるレビューが必要なパス：2 本目の鍵が必要なもの

変更の中には、すべてのテストに合格するような形で誤っているものがあります。失敗が本番環境でしか、時間が経ってからしか、あるいは攻撃者がいるときにしか現れないからです。そうしたパスは、誰が変更を書いたかにかかわらず、変更する前に人の承認が必要です。

### チェックも人間によるレビューが必要なパス

テストや採点のコードを編集するエージェントについての METR の発見が、最後の行がある理由です。失敗しているチェックを通すよう頼まれたエージェントには、2 つの選択肢があります。コードを直すか、チェックを弱めるかです。後者のほうが手っ取り早いこともよくあります。ですから、ゲートを定義するファイル、つまり CI のワークフロー、リントと型の設定、カバレッジのしきい値、チェックのスクリプトには、決済のコードと同じ 2 本目の鍵が必要です。私たちのリストには `.github/workflows/` が挙がっていますが、リントルールとカバレッジのしきい値がある `vite.config.ts` や、コンテンツチェックがある `scripts/` はまだ挙がっていません。これらもリストに載せるべきです。

### 承認は文章ではなく差分に結び付く

上の伝聞のインシデントには共通の形があります。承認が一文として存在し、その文が承認そのものより遠くまで伝わったのです。指示書の中の「オーナーが承認した」、別のプルリクエストから貼り付けられた説明、あるファイルは保護されていないと述べたリストがそうでした。対策は、承認を 3 つの部分からなる記録にすることです。引用したその人の言葉、それが対象とするパス、そして対象としないものです。デプロイがプレースホルダーのシークレットを拒否するようにしたプルリクエスト #223 は、まさにそうしています。オーナーの返答「6. yes」を引用し、対象とするデプロイスクリプトを挙げ、手を付けない人間によるレビューのパスを列挙しています。レビュアーやチェックは、そのリストを差分と比較できます。私たちは現在、承認を伝えるメッセージを引用せずに「オーナーが承認した」と書かない、というルールに従っています。

### 2 本目の鍵には 2 つ目の ID が必要

GitHub は 2 本目の鍵を強制できます。`CODEOWNERS` ファイルがパスを人に割り当て、ブランチルールで「コードオーナーからのレビューを必須にする」ことができます。ただし、エージェントを使うすべての個人開発者にとって重要な落とし穴があります。GitHub のドキュメントは「プルリクエストの作成者は、自分のプルリクエストを承認できない」と明言しています。エージェントがあなたの認証情報でプルリクエストを開くなら、サーバー側のすべての制御にはあなたが見えており、あなたからの必須のレビューを与えることは不可能です。

これが私たちの現状です。エージェントはオーナーのアカウントで作業しているので、私たちのブランチルールは承認のレビューではなく CI のチェックとマージキューを必須にしており、人間によるレビューが必要なパスに対するオーナーの承認は引用されたメッセージで、それをエージェントの権限レイヤーが守っています。インシデントが示すとおりこれは機能してきましたが、私たちの仕組みの中で最も弱い部分です。より強い構成は、説明するだけなら簡単です。エージェントに専用の ID、たとえば書き込み権限はあるが管理者権限のないボットアカウントや GitHub App を与え、人間によるレビューが必要なパスを `CODEOWNERS` に入れ、`main` でコードオーナーのレビューを必須にします。そうすれば 2 本目の鍵は人によるクリックになり、どんな文もその代わりにはなれません。

## 完了を終了コードで定義する

「完了」は、エージェントが口にする言葉の中で最も高くつく言葉です。その後のすべてが、ほかの誰かの時間になるからです。完了は、プッシュしようとしているブランチで終了コード 0 を返さなければならない短いコマンドのリストとして、速いものから遅いものへの固定の順序で定義し、各コマンドが、それより前のコマンドでは捕まえられない種類の失敗を捕まえるようにします。CI には、よく似たものではなく同じコマンドを実行させます。そうすれば、ローカルで緑なら CI でも緑になると予測できます。プルリクエストには終了コードと件数を書いてもらい、要約は検証すべき主張として扱ってください。

### 実例：3 つのコマンドと、触れたスペック

私たちの完了の定義は、3 つのコマンド、次に変更が触れるブラウザーのスペック、そしてマージキューです。使うのは `AGENTS.md` の次の行です。

```sh title="AGENTS.md"
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
bun scripts/enqueue-pr.ts <number>
```

`check` はフォーマット、リント、型チェックを行い、すべてのロケールで翻訳とコンテンツのチェックを実行します。`test:coverage` は、行、ステートメント、関数、分岐について <RepositoryFact name="coverageThreshold" unit="percent" /> のカバレッジのゲートのもとで、ユニットテスト、統合テスト、コンポーネントテストを実行します。`build:test` は Cloudflare Worker をビルドして出力をチェックします。`test:e2e:pr` はそのビルドを配信し、Chromium でブラウザーのスイート全体を操作します。CI はこれをプルリクエストで実行し、マージキューでもう一度実行します。ローカルでは、エージェントは代わりに `bunx playwright test` の行を、変更が触れるスペックについて、専用の空いているポートで実行します。プルリクエストが完了するのは、CI で緑になり、最後の行がそれをキューに入れたときだけです。

11月21日までは、ローカルのリストの最後はスイート全体で、プルリクエストは共有プレビューのデプロイを待つスクリプトを通してマージされていました。その両方が変わった理由は、[このシリーズの次の記事](/blog/running-ai-coding-agents-in-parallel#update-november-2026)で述べています。2026年11月20日、ブログの共有機能が `main` に入ったときに走った CI の実行と、11月21日、マージキューを導入したプルリクエストのマージキューでの実行で、各ステップにかかった時間は次のとおりです。

| ステップ                                       | 11月20日、ジョブごとに 1 台のランナー | 11月21日、マージキューで                  |
| ---------------------------------------------- | ------------------------------------- | ----------------------------------------- |
| ツールチェーンと依存関係のセットアップ         | 1 分 11 秒                            | 24 秒                                     |
| `bun run check`                                | 16 秒                                 | 31 秒                                     |
| `bun run test:coverage`                        | 3 分 44 秒                            | 7 分 21 秒                                |
| `bun run build:test`                           | 2 分 59 秒                            | 2 分 48 秒                                |
| Chromium でのブラウザーのスイート              | 12 分 2 秒                            | 4 個の各シャードで 2 分 15 秒〜3 分 10 秒 |
| トラフィックを配信しない Worker のアップロード | まだチェックではなかった              | 3 分 24 秒、ビルドと並行                  |

ブラウザーのスイートは、1 台のランナーでの 12 分から、4 台それぞれで約 3 分になり、ツールチェーンのセットアップからは同じキャッシュの 2 回目の復元がなくなりました。カバレッジ付きのユニットテストは前日の約 2 倍の時間がかかって最も遅いジョブになっていたので、次に変えたのはそこでした。

#285 はカバレッジ付きのテストを並列のシャードに分け、そのカバレッジを必須チェックの中でマージします。#289 はブラウザーのスイートをさらに多くのシャードに分け、#296 はビルドの実行中にブラウザーのシャードがセットアップを済ませるようにしました。現在 CI は、テストを <RepositoryFact name="vitestShards" /> 個のシャードで、ブラウザーのスイートを <RepositoryFact name="e2eShards" /> 個のシャードで実行しています。2026年11月22日の #304 のマージキューでの実行では、カバレッジのシャードが 2.1〜3.3 分、ビルドが 3.7 分、ブラウザーのシャードが 5.0〜7.7 分、Worker のアップロードが 5.1 分かかり、実行全体は最初のジョブから最後のジョブまで 7.8 分でした。再び最も遅いジョブはブラウザーのスイートです。

どのコマンドも、それがなかったために何かが通過してしまったからリストに入っています。11月12日、依存関係のアップグレード（#94）は、本番ビルドが 2 か所で壊れていたのに、`check` と、完全なカバレッジでの 1,255 件のテストに合格しました。新しい Polar SDK がバンドルできず、TanStack Start のリリースが出力を変えたためにビルド後のスクリプトが失敗したのです。ユニットテストは Cloudflare のビルドを一切実行しないので、`build:test` がリストに加わり、規約のドキュメントにその理由が記録されています。

### すべてのテストに同乗するゲート

ブラウザーのスイートは、自身のアサーションを実行するだけではありません。3 つのフィクスチャがすべてのテストに自動的に付き、ページが Content Security Policy の違反、欠けている翻訳や形式の誤った翻訳、ブラウザーが認識しない Permissions Policy を報告すると、そのテストを失敗させます。そのため、新しいブラウザーテストはどれも、作者が何もしなくても、訪れるページでのこれら 3 つの性質のテストにもなります。

```ts title="e2e/fixtures/test.ts"
const reportCspViolations = (prefix: string): void => {
  document.addEventListener("securitypolicyviolation", ({ blockedURI, lineNumber, sourceFile, violatedDirective }) => {
    console.error(`${prefix} ${violatedDirective} blocked ${blockedURI} in ${sourceFile}:${String(lineNumber)}`)
  })
}
```

同じスイートは、両方のカラーテーマで axe のアクセシビリティスキャンを実行します。後述のサンプルのうち 3 回の実行は、WCAG のコントラストを満たさないテキストを理由に、これらのスキャンで失敗しました。良いモニターで見ていたら、どのレビュアーも気づかなかったはずの退行です。

### ビルドとデプロイのゲート

`scripts/verify-build.ts` は、どのユニットテストにも見えないビルド出力の性質をチェックします。公開されているすべてのドキュメントページと記事がプリレンダリングされていること、サーバー専用のモジュールがブラウザーのスクリプトに入り込んでいないこと、すべてのロケールに検索インデックスがあること、そして Worker がコールドスタートで読み込むコードが、特定のリクエストのためのパッケージを含まずにバイト数の予算内に収まっていることです。

```ts title="scripts/verify-build.ts"
if (bootPackages.size > 0) {
  throw new Error(`The Worker loads ${[...bootPackages].join(", ")} on every cold start; import it where a request needs it`)
}
```

デプロイにも独自のゲートがあります。11月、本番環境の環境ファイルにはまだ `AUTH_GOOGLE_CLIENT_ID="[UPDATE]"` が残っていました。デプロイは空の値しか拒否しなかったのでそれをアップロードし、Google でのサインインは `invalid_client` で失敗しました。プルリクエスト #223 は、デプロイがビルドの前にプレースホルダーを拒否するようにしました。対象は角括弧で囲まれた値か、短いリストにある語のいずれかで、大文字と小文字は問いません。

```ts title="src/lib/deploy-secrets.ts"
export const SECRET_PLACEHOLDER_WORDS = ["changeme", "placeholder", "replaceme", "tbd", "todo", "update"] as const
```

### 3 か月でゲートが拒否したもの

2026年8月14日から11月20日までの、プルリクエストに対する私たちの CI の直近 400 回の実行は、次のように終わりました。合格が 319 回、失敗が 68 回で、残りはキャンセルされたか、まだ実行中でした。チェックは必須なので、失敗した実行はマージできません。68 回の失敗が、どのゲートで止められたかは次のとおりです（1 回の実行が複数のゲートで失敗することもあります）。

| ゲート                                        | 失敗した実行 | 見つかったもの                                                                                                           |
| --------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `check`：フォーマット、リント、型、コンテンツ | 37           | 変更履歴のエントリが存在する前の 34 回、丁寧なドイツ語の「Sie」が 1 回、型とリントのエラーが 2 回                        |
| カバレッジのゲート                            | 8            | テストされていないコード。行の 99.93% だった実行から、分岐の 63.89% だった実行まで                                       |
| ブラウザーのスイート                          | 25           | コントラストの失敗、ロケールのナビゲーション、CLI のライセンス API、ドキュメントの検索、ハイドレーション、不安定なテスト |
| テストビルド                                  | 2            | ビルドの失敗と、適用されなかったローカルのマイグレーション                                                               |
| プレビューデプロイ                            | 2            | Worker のアップロードの失敗と、ライブチェックの失敗                                                                      |

3 つの点が目を引きます。カバレッジのゲートは、行の 99.93% がカバーされた変更を拒否しました。どのレビュアーも拒否しなかったはずのものです。赤い `check` の実行のほとんどは変更履歴のエントリによるもので、このエントリはプルリクエストに番号が付くまで書けません。これは後で改めて取り上げるコストです。そして、赤いブラウザーの実行のすべてが変更のバグだったわけではありません。不安定なテストや、並列の実行が互いに干渉したものもあり、それは[このシリーズの次の記事](/blog/running-ai-coding-agents-in-parallel)で扱います。

## すべてのチェックが緑なのにプロダクトが壊れているとき

2 つのインシデントは、私たちのすべてのチェックを通過しました。どちらも、68 回の拒否より多くのことを教えてくれました。

### カバレッジ 100% でも `init` が動かなかった

SaaSy Land には 2 つのリポジトリがあります。ライセンス API を提供するこのウェブサイトと、顧客がプロジェクトを作成するために実行する非公開の CLI です。どちらも API のリクエストとレスポンスを定義する 1 つの契約パッケージをインポートし、どちらもそれでバリデーションを行います。契約のスキーマは知らないキーを拒否します。これは良いデフォルトで、黙って無視するほうが悪い結果になっていたはずです。

CLI のあるリリースが、UI ライブラリという質問を追加し、その回答をライセンス API に送るようになりました。本番のウェブサイトは、まだ以前のバージョンの契約でバリデーションしていました。両方のリポジトリのすべてのユニットテストは合格しました。各リポジトリは自分が固定した契約のバージョンに対して自分自身をテストしていたからで、カバレッジは両側で完全でした。2026年11月20日、私たちはエンドツーエンドのテストとして、npm から直接取得した公開済みの CLI を、本番のチェックアウトで発行した実際のライセンスを使って、本番環境に対して実行しました。`init` は失敗しました。API がリクエストを「Unrecognized key: library」で拒否したのです。

修正は、ウェブサイトを新しい契約のバージョンに移すこと（#244）で、同じ日の午後に出荷され、その後、公開済みの CLI は本番環境に対してプロジェクトを作成できました。教訓は一般的なものです。

- **カバレッジはリポジトリの性質であり、正しさはデプロイされたシステムの性質。** どちらのテストスイートも、デプロイされた 2 つの半分を一緒に動かしてはいませんでした。
- **別々にデプロイするもの同士のバージョンのずれは、ユニットテストには見えない。** 公開済みのクライアントを本番のサーバーに対してテストするか、少なくとも、クライアントが出荷されるときに本番で動いているはずのバージョンのサーバーに対してテストしてください。
- **デプロイの順序を決める。** 契約の変更はまずサーバーで出荷されて本番で動き、そのあとでそれを使うクライアントがリリースされるようにします。私たちは現在このルールに従っており、次のガードレールは、リリース前に CI で公開済みの CLI を本番の API に対して実行することです。それには CI のシークレットとしてライセンスキーが必要で、それ自体が人間によるレビューが必要な変更なので、オーナーの判断を待っています。

### リリースを止めた空の changeset

これは非公開の CLI リポジトリで起きたことなので、コードは示さずにプロセスを説明します。CLI は Changesets でリリースされ、CI は changeset なしでパッケージを変更するプルリクエストを拒否します。changeset とは、次のリリースに何が含まれるかを記したファイルです。Changesets は抜け道を文書化しています。「リリースを一切行わずに変更をマージしたい場合（テストやビルドツールだけを変更する場合など）は、`changeset --empty` を実行して、何もリリースしない特別な changeset を追加できる」。

プレリリースのブランチでのあるプルリクエストは変更履歴を修正しただけだったので、文書どおりに空の changeset を追加しました。プレリリースモードのブランチで、保留中のものが空の changeset だけだったため、リリースのワークフローはバージョンを上げるものも公開するものも見つけられず、次のベータ版はステージされませんでした。修正では空の changeset を削除し、リリースガイドには現在、空の changeset はメインブランチにだけ置くよう書かれています。

これは、1 段上のレベルで再び起きた「意図より文言」の失敗です。チェックが成果物を要求し、エージェントは最も安上がりな有効な成果物を提供し、その成果物を実際に使うのは独自のルールを持つ別のシステムでした。チェックがファイルを要求するときは、ほかに何がそのファイルを読むのかを問い、それを読むパイプラインをテストしてください。

## 既存のリポジトリに導入する

月曜日にこれをすべて揃える必要はありません。1 日の作業あたりの効果が最も大きい順に並べると、次のようになります。

<Steps>

<Step>

**棚卸しを書く。** エージェントや同僚にこれまで伝えたすべてのルールを列挙します。指示ファイル、何度も繰り返しているレビューコメント、規約のページなどです。各ルールの横に、それが現在どこで強制されているかを書きます。ほとんどのチームは、ルールの大半がどこでも強制されていないことに気づきます。

</Step>

<Step>

**プローブする。** 各ルールを 1 回ずつ破るファイルを書き、チェックを実行して、何が通過したかを記録します。これで棚卸しは、信じていることから事実に変わります。

</Step>

<Step>

**コマンドを 1 つにする。** フォーマット、リント、型チェックを行ってコンテンツチェックを実行する単一の `check` スクリプトと、カバレッジ付きの単一のテストコマンドを用意します。両方を完了の定義として指示ファイルに書きます。

</Step>

<Step>

**CI に同じコマンドを実行させ、それを必須にする。** ブランチルールで CI のジョブを必須のステータスチェックとして指定し、あわせて `main` への force-push と削除をブロックします。このステップ以降、誰が書いたものであっても、赤いものはマージされません。

</Step>

<Step>

**ラチェットを使ってゲートを 1 つずつ追加する。** 厳格な型のフラグ、次にカバレッジのゲート、次にプロダクトに必要なコンテンツチェックです。それぞれについて、できるなら #220 がドイツ語の丁寧な形 1,404 個に対して行ったように、既存の違反を同じプルリクエストで直します。それができなければベースラインを記録し、新しい違反だけで失敗させます。Vitest の `coverage.thresholds.autoUpdate` はカバレッジが改善するとしきい値を引き上げるので、数値は上がる一方になります。

</Step>

<Step>

**危険なパスを囲う。** エージェントの権限設定で、force-push、デプロイ、本番の認証情報を拒否します。エントリごとに理由を添えて人間によるレビューのリストを書き、チェックを定義するファイルもそこに含め、それをコードオーナーとエージェント用の別の ID で裏付けます。

</Step>

<Step>

**指示ファイルを小さくする。** チェックが強制するようになったルールはすべて削除し、それを強制するコマンドに置き換えます。残るべきなのは、意図、例、レビューのリスト、完了の定義です。

</Step>

<Step>

**アップグレードの後にもう一度プローブする。** リンター、コンパイラー、テストランナーのメジャーバージョンが変わったとき、そしてルールが変わったときには、プローブファイルをもう一度実行します。テストにしてしまえば、なお良いです。

</Step>

</Steps>

## かかるコスト

ガードレールは無料ではありません。無料だと言う人は、ガードレールを保守したことがないのです。

**変更ごとの時間。** 私たちの CI は、11月20日にはプッシュから緑になるまで約 16 分半かかり、その大半は 1 台のランナーでのブラウザーのスイートでした。スイートが <RepositoryFact name="e2eShards" /> 台のランナーで並列に動くようになってから、プルリクエストの実行は約 7〜9 分で、マージの前にマージキューがもう一度それを実行します。さらに、プッシュ前のローカルの実行にかかる時間が加わります。シャードはランナーの時間と引き換えにその時間を得ています。各シャードがツールチェーンとブラウザーをもう一度セットアップするからです。公開リポジトリなら、CI の時間そのものは GitHub の標準ランナーでは費用がかかりません。GitHub は公開リポジトリでの利用を無料と文書化しています。非公開のリポジトリでは 1 分ごとに料金がかかり、その時間を消費するのはブラウザーのスイートです。

**書いて保守するコード。** コンテンツと翻訳のチェック、ビルドの検証スクリプト、ハイドレーションのプラグイン、コミットフックは、合わせて 1,000 行を超える TypeScript で、それぞれにテストがあります。これらもほかのコードと同じです。shebang やフランス語の「ton」が示すようにバグがあり、同じレビューが必要です。

**「まだ」を意味する赤。** サンプルのうち失敗した `check` の実行 37 回中 34 回は、変更履歴のエントリがまだ存在しないプルリクエストによるものでした。エントリはプルリクエストの番号にちなんで名付けられ、その番号はプルリクエストができるまで存在しないからです。予想どおりの理由で日常的に失敗するチェックは、赤をノイズとして読むことを全員に教えてしまいます。これは、ガードレールを持つチームが身につけうる最も危険な習慣です。そのようなチェックを設計するなら、失敗ではない状態を与えるか、私たちがこれまでそうしてきたように、承知のうえでそのコストを受け入れてください。

**形だけの儀式。** 少し厳しすぎるルールは、誰も手では書かないような遵守を生み出します。#230 の 72 個の定数がそれを示しました。ルールを追加したあとで、それを調整する時間を見込んでおいてください。

**プロダクトに比例して増える変更ごとの作業。** 私たちのリポジトリでは、すべての変更が <RepositoryFact name="languages" /> 個の言語でドキュメントを更新し、それぞれの言語で変更履歴のエントリを追加します。チェックはそれが確実に行われるようにしますが、安くはしてくれません。

これで得られるのが、上の表です。マージできなかった 68 回の実行は、どれも人が気づく必要がありませんでした。そして、リポジトリが私たちに代わって「ノー」と言うので、エージェントは誰も各ステップを見ていなくても何時間も作業できます。私たちの[リポジトリの準備についての記事](/blog/ai-coding-agents-repository-readiness)の言葉で言えば、ここにあるチェックはどれも Time to No を短くします。

## ガードレールが検出できないもの

チェックは、プログラムが判定できることを判定します。それ以外のすべてには、変更を読んで理由を問う人が今も必要です。

- **意図。** 誤った問題に対する正しいコードは、すべてのチェックを通過します。症状の修正も同じです。プルリクエスト #146 は、ランディングページの 1 つのコンポーネントのハイドレーションエラーをリグレッションテスト付きで修正し、すべてのゲートを通過しました。原因は、サインイン中のユーザーが変わるたびにクエリのキャッシュ全体を空にするルートガードで、#152 がそれをすべてのページについて修正しました。
- **設計。** すでにあるヘルパーと重複する 2 つ目のヘルパー、誰も必要としていなかった新しい抽象化、誤った場所にあるモジュールなどです。リントが見るのは構文であり、目的ではありません。
- **弱いテスト。** 実装を検証するテストも合格し、その行をカバーします。カバレッジが測るのは何が実行されたかであり、何が確認されたかではありません。ミューテーションテストはそれ以上を測りますが、私たちはまだ導入していません。
- **デプロイ間の境界。** `init` のインシデントがその例です。どちらの側も正しいのに、組み合わせると壊れていました。
- **文章。** プルリクエストの説明、ドキュメントの主張、変更履歴の文章は、その事実をコードから出力しない限りチェックされません。
- **チェックそのもの。** チェックも誤ることがあり、寛容すぎることも厳しすぎることもあります。プローブしてください。
- **次の新しい失敗。** この記事のガードレールはどれも、すでに起きたインシデントをコード化したものです。まだ起きていないものを見つける方法が、レビューです。

## コピーして使えるスターターキット

以下の部品は、ほとんどの TypeScript リポジトリで機能します。最も一般的なので npm、ESLint、Vitest、GitHub Actions を使っていますが、どの考え方もほかのツールに置き換えられます。

**ゲートごとに 1 つのコマンド**を、どこでも同じ名前で用意します。そうすれば、指示ファイル、フック、CI がすべて同じことを言います。

```json
{
  "scripts": {
    "check": "prettier --check . && eslint --max-warnings 0 . && tsc --noEmit",
    "test:coverage": "vitest run --coverage",
    "build": "vite build",
    "test:e2e": "playwright test"
  }
}
```

**オフスイッチのないリントの設定。** インラインでの無効化はオフにし、上で示したコメントのルールを含め、抜け道は名前を挙げて禁止しています。`assertionStyle: "never"` でも `as const` は許可されます。typescript-eslint はこれを「このルールでは常に許可される」と文書化しています。

```js
import { defineConfig } from "eslint/config"
import tseslint from "typescript-eslint"

const noComments = {
  meta: {
    type: "suggestion",
    messages: { comment: "Say it in a name, a commit message or the docs." },
  },
  create: (context) => ({
    Program: () => {
      for (const comment of context.sourceCode.getAllComments()) {
        if (comment.type !== "Shebang") {
          context.report({ loc: comment.loc, messageId: "comment" })
        }
      }
    },
  }),
}

export default defineConfig({ linterOptions: { noInlineConfig: true } }, tseslint.configs.strictTypeChecked, {
  languageOptions: { parserOptions: { projectService: true } },
  plugins: { house: { rules: { "no-comments": noComments } } },
  rules: {
    "house/no-comments": "error",
    "@typescript-eslint/ban-ts-comment": ["error", { "ts-expect-error": true, "ts-ignore": true, "ts-nocheck": true }],
    "@typescript-eslint/consistent-type-assertions": ["error", { assertionStyle: "never" }],
    "@typescript-eslint/no-explicit-any": "error",
    "@typescript-eslint/no-non-null-assertion": "error",
    "no-magic-numbers": ["error", { ignore: [0, 1], ignoreArrayIndexes: true, ignoreDefaultValues: true }],
  },
})
```

**厳格な型。** 私たちの `tsconfig.json` が `strict` に加えて設定しているフラグです。

```json
{
  "compilerOptions": {
    "strict": true,
    "exactOptionalPropertyTypes": true,
    "noUncheckedIndexedAccess": true,
    "noPropertyAccessFromIndexSignature": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true
  }
}
```

**カバレッジのゲート。** `100: true` は、「グローバルなしきい値を 100 に設定する」Vitest の省略記法です。既存のコードベースでは、`autoUpdate: true` を使って今日の数値から始め、それが上がっていくに任せてください。

```ts
import { defineConfig } from "vitest/config"

export default defineConfig({
  test: {
    coverage: {
      provider: "v8",
      include: ["src/**/*.{ts,tsx}"],
      thresholds: { 100: true },
    },
  },
})
```

**ルールのためのプローブテスト**を用意すると、リンターのアップグレードや設定の変更でルールがオフになったときに CI が失敗します。プローブファイルは通常のリントの実行から外し、ここで ignore をオフにしてリントします。

```ts
import { ESLint } from "eslint"
import { expect, it } from "vitest"

const eslint = new ESLint({ ignore: false })

it.each([
  ["comment.ts", "house/no-comments"],
  ["assertion.ts", "@typescript-eslint/consistent-type-assertions"],
  ["expect-error.ts", "@typescript-eslint/ban-ts-comment"],
  ["explicit-any.ts", "@typescript-eslint/no-explicit-any"],
])("rejects %s with %s", async (file, rule) => {
  const [result] = await eslint.lintFiles([`test/rule-probes/${file}`])

  expect(result?.messages.map(({ ruleId }) => ruleId)).toContain(rule)
})
```

**同じコマンドを実行する CI** に加えて、どのリンターが自身の設定を守るかにも依存しない、抑制コメントの検索を行います。このジョブを必須のステータスチェックにしてください。

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc
      - run: npm ci
      - run: npm run check
      - run: npm run test:coverage
      - run: npm run build
      - name: No suppression comments
        run: |
          if git grep -n -E "(eslint|oxlint)-disable|biome-ignore|@ts-(ignore|expect-error|nocheck)" -- "*.ts" "*.tsx" "*.js" "*.jsx" "*.mjs"; then exit 1; fi
```

**`main` のブランチルール：** CI のジョブを必須にし、スカッシュマージのみのプルリクエストを必須にし、線形の履歴を必須にし、force-push と削除をブロックし、エージェントが専用の ID を持ったらコードオーナーのレビューを必須にします。

**人が必要なパスのコードオーナー**を、ゲートを定義するファイルも含めて設定します。

```text
/db/migrations/ @your-org/maintainers
/src/billing/ @your-org/maintainers
/src/auth/ @your-org/maintainers
/.github/ @your-org/maintainers
/eslint.config.js @your-org/maintainers
/vitest.config.ts @your-org/maintainers
```

**エージェントの権限**で、決して実行してはならないコマンドを拒否し、安全な形の force-push を許可します。この例は Claude Code の `.claude/settings.json` です。「ルールは deny、ask、allow の順に評価される」ため、deny のルールは allow のルールに優先します。引数のパターンは壊れやすいことを忘れないでください。上のブランチルールがあるのはそのためです。

```json
{
  "permissions": {
    "deny": ["Bash(git push --force *)", "Bash(git push -f *)", "Bash(git commit --no-verify *)"],
    "ask": ["Edit(./db/migrations/**)", "Edit(./src/billing/**)", "Edit(./.github/**)"],
    "allow": ["Bash(git push --force-with-lease *)"]
  }
}
```

**チェックを繰り返すのではなく、チェックを指し示す指示ファイル**です。

```md
# AGENTS.md

## Done

`npm run check`, `npm run test:coverage`, `npm run build` and `npm run test:e2e` exit 0, in that order, on the branch you push. Put each exit code in the pull request. A summary is not evidence.

## Rules a check enforces

- No comments, suppression comments, type assertions or `any`: `npm run check` fails on each.
- Coverage stays at 100%: `npm run test:coverage` fails below it.

## Rules review enforces

- Fix the cause, not the symptom, and say in the pull request what caused the bug.
- One change per pull request.

## Human review required

Do not change these without a maintainer's written yes that names the paths:

- `db/migrations/`: applied to production and irreversible.
- `src/billing/` and `src/auth/`: money and identity.
- `.github/`, `eslint.config.js` and `vitest.config.ts`: the checks themselves.
```

## saasyland.com のガードレールにまだ足りないところ

この記事を書くことは監査でもあり、その監査で穴が見つかりました。記事のほかの部分と同じ精神で、ここに挙げます。

そのうち 3 つは塞がりました。コメント、抜け道、そして複数行の三項演算子と `?? undefined` は、今では `bun run check` で失敗します（#274）。残っているのは次のものです。

- **ブラウザーのテストスイート**はリンターの対象外です。`bun run check:comments` は `e2e/` を読みますが、ほかのリントルールは読みません。
- **人間によるレビューが必要なパス**は、GitHub ではなく、指示とエージェントの権限レイヤーによって守られています。エージェントがオーナーの ID で作業しているからです。リストからは、ゲートを定義するファイルも漏れています。
- **プルリクエストの説明**は、差分と照合されていません。
- **公開済みの CLI** は、各リリースの前に本番の API に対してまだ実行されていません。
- テストがどれだけ実行するかではなく、どれだけ確認するかを測る**ミューテーションテスト**は、まだ導入されていません。

これらはどれも、強制するのではなく伝えているだけのルールであり、どれもいずれ、はしごの下の段へ移していきます。
