Execute os scripts a partir da raiz do repositório com `bun run <script>`. Os scripts que chamam o Wrangler, e o `db:generate`, que chama o drizzle-kit, os executam via `vp exec`, que pega o binário de `node_modules/.bin`, então sempre usam as versões travadas no `bun.lock`.

## Desenvolvimento e build

| Script             | Executa                                                                                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dev`              | `generate:cn`, `content` e `vp dev` no ambiente `development` em http://localhost:3000                                                                                         |
| `build`            | O mesmo que `build:preview`                                                                                                                                                    |
| `build:preview`    | Limpa `dist`, `generate:cn`, `content`, `vp build` para `preview`, `scripts/verify-build.ts preview`, `scripts/optimize-prerendered-html.ts` e `scripts/generate-seo-files.ts` |
| `build:production` | As mesmas etapas para `production`                                                                                                                                             |
| `build:test`       | As mesmas etapas para o ambiente `test`                                                                                                                                        |
| `start`            | `vp preview` do build mais recente em http://127.0.0.1:3000                                                                                                                    |
| `start:test`       | `vp preview` do build de testes                                                                                                                                                |

`verify-build.ts` verifica se `.wrangler/deploy/config.json` aponta para `dist/server/wrangler.json` e se esse arquivo faz o deploy do Worker que o `wrangler.jsonc` define para o ambiente e, em seguida, o idioma do documento, os links canônicos e alternativos da página inicial e das páginas legais localizadas, as fontes, que aliases de locale e as páginas sob os caminhos não listados das áreas não foram pré-renderizados, que todas as páginas da documentação e todos os posts publicados do blog foram pré-renderizados, que nenhum asset do cliente importa `cloudflare:workers`, que os imports estáticos do script de entrada do navegador não contêm o loader das mensagens de nenhum namespace de página e que o código que o Worker carrega em um cold start continua pequeno: os imports estáticos de `dist/server/index.js` não podem chegar a `@polar-sh`, `drizzle-orm` ou `resend` e devem somar no máximo `BOOT_CLOSURE_MAX_BYTES` (veja [Desempenho](/docs/conventions/performance)). `optimize-prerendered-html.ts` remove das páginas pré-renderizadas as dicas `modulepreload` de dependências e mantém a dica da entrada com baixa prioridade. `generate-seo-files.ts` grava o `sitemap.xml` e o feed do blog em cada idioma, e renderiza um card social para cada página pré-renderizada e o logotipo da organização, tudo a partir dos metadados das próprias páginas; veja [Busca e prévias em redes sociais](/docs/features/seo).

## Deploy

| Script              | Executa                                                                                                                                                                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deploy:preview`    | `scripts/verify-bindings.ts preview`, `scripts/prepare-deploy-secrets.ts preview`, `scripts/run-deploy-checks.ts preview`, `build:preview`, `db:migrate:preview`, `wrangler deploy` de `dist/server/wrangler.json` e `scripts/verify-deployment.ts preview` |
| `deploy:production` | As mesmas etapas para `production`                                                                                                                                                                                                                          |

- `verify-bindings.ts` falha quando falta ao ambiente um binding que `development` declara (aqui `DB`, `CACHE`, `MEDIA` e `BUNDLES`) ou ainda tem um ID de D1 ou KV de placeholder, e quando a produção compartilha com o preview o banco de dados, o namespace ou o bucket.
- `prepare-deploy-secrets.ts` lê de `.env.<environment>` as chaves listadas em `secrets.required` do ambiente, falha quando alguma está ausente, vazia ou é um placeholder, e grava apenas essas chaves em `.wrangler/secrets.<environment>.json`. Um placeholder é um valor entre colchetes (<RepositoryFact name="secretPlaceholderBrackets" />), como `[UPDATE]`, ou uma das palavras <RepositoryFact name="secretPlaceholderWords" />, em maiúsculas ou minúsculas e com ou sem espaços, hífens ou sublinhados. O erro informa as chaves sem mostrar os valores delas. Ele lê os nomes do `wrangler.jsonc`, então cobre os secrets de todas as áreas sem nomear nenhuma. As outras variáveis do arquivo não são enviadas.
- `run-deploy-checks.ts` executa `bun run <check>:<environment>` para cada verificação de deploy que uma área declara em `src/data/<area>.deploy.ts` e interrompe o deploy antes do build quando uma falha. Hoje são `auth:verify`, da área de autenticação, que falha a menos que <RepositoryFact name="oauthClientIdVariables" /> em `.env.<environment>` tragam cada um um client ID no formato do seu provedor (os formatos que `verify-deployment.ts` aplica depois do deploy), e `polar:verify`, da área do Polar, que falha quando a organização do Polar em `.env.<environment>` não corresponde ao código.
- As migrações rodam depois do build e antes do deploy, então um build com falha nunca toca o banco de dados e o novo Worker nunca inicia com um schema antigo.
- O deploy executa `env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.<environment>.json`. A configuração gerada pelo build já aponta para um único ambiente; um `CLOUDFLARE_ENV` que tenha ficado no shell faria o Wrangler procurar uma seção de ambiente que esse arquivo não tem.
- `verify-deployment.ts` faz requisições a <RepositoryFact name="liveSiteCheckPaths" /> no domínio do ambiente e falha a menos que cada um responda `200` com o tipo de conteúdo esperado. Em <RepositoryFact name="socialSignInPath" />, ele inicia, como o navegador faz, o login com cada provedor da página de login, <RepositoryFact name="oauthProviderIds" />, e falha a menos que a URL de autorização que recebe esteja no host do próprio provedor e traga um `client_id` no formato desse provedor e um `redirect_uri` igual a <RepositoryFact name="oauthCallbackPath" /> no mesmo domínio. O erro nomeia o provedor e o problema sem mostrar o valor. Ele executa de novo uma verificação que falha até <RepositoryFact name="liveSiteCheckRetries" /> vezes, com <RepositoryFact name="liveSiteCheckRetrySeconds" unit="second" /> de intervalo, e não altera nada além do estado OAuth e do contador de tentativas de curta duração no D1 que um clique em um botão de login também deixa. `bun scripts/verify-deployment.ts <preview|production>` verifica um site no ar de forma independente.

## Geração e manutenção

| Script           | Executa                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| `content`        | `fumadocs-mdx`: gera `.source/` a partir de `content/`                                                  |
| `generate:cn`    | Gera as tabelas de mesclagem de classes em `.source/cn-tables.ts` a partir de `src/lib/cn.config.ts`    |
| `cf-typegen`     | `wrangler types` para `development`: gera novamente `src/types/worker-configuration.d.ts`               |
| `typegen`        | `cf-typegen`, `generate:cn` e `content`                                                                 |
| `skills:sync`    | `scripts/sync-skills.ts`: restaura as skills para agentes a partir de `skills-lock.json`                |
| `clean`          | Remove `.source`, `.tanstack`, `.wrangler`, `dist`, `coverage`, a saída do Playwright e `*.tsbuildinfo` |
| `clean:deep`     | `clean` e `node_modules`                                                                                |
| `clean:hardcore` | `clean:deep`, `bun.lock` e `skills-lock.json`                                                           |
| `prepare`        | Executado na instalação: `vp config --no-agent` (hooks do Git), `generate:cn` e `content`               |

`clean` apaga `.wrangler`, incluindo os bancos de dados locais de desenvolvimento e de testes e os arquivos de secrets gravados pelos scripts de deploy, então exporte antes os dados locais que quiser manter.
