faq:
  - question: Cloudflare Workers で SaaS 全体を動かせますか？
    answer: >-
      データが D1 の形に合うなら動かせます。saasyland.com は、ページ、サーバー関数、サインイン、ライセンス API、Webhook、動画配信を 1 つの Worker で動かし、ユーザー、セッション、ライセンス、コースを D1 に、キャッシュを KV に、非公開のファイルを R2 に置いています。最初に確認すべき上限は、D1 のデータベースあたり 10 GB という容量、データベースごとに一度に 1 つのクエリしか処理しないこと、そしてコードが判断している間、開いたままにできるトランザクションがないことです。
  - question: Cloudflare D1 はトランザクションに対応していますか？
    answer: >-
      バッチとしてのみ対応しています。D1 はステートメントを自動コミットモードで実行し、ドキュメントには、バッチにまとめたステートメントは SQL トランザクションであると書かれています。ステートメントは順に実行されてコミットされ、1 つでも失敗するとバッチ全体がロールバックされます。トランザクションを開いて読み取り、コードの中で判断し、あとでコミットすることはできないため、読み取り・判断・書き込みの処理は 1 つの SQL ステートメントか 1 つのバッチにする必要があります。
  - question: Cloudflare D1 の上限は何ですか？
    answer: >-
      Workers Paid では、データベースあたり 10 GB、アカウントあたり 1 TB、Worker の呼び出し 1 回あたり 1,000 クエリです。Workers Free では、データベースあたり 500 MB、クエリは 50 回です。どちらのプランでも、行、文字列、BLOB は最大 2 MB、ステートメントは最大 100 KB で、1 つのクエリにバインドできるパラメーターは最大 100 個、実行時間は最大 30 秒です。また、各データベースはクエリを一度に 1 つずつ処理します。
  - question: セッションやレート制限を Workers KV に保存すべきですか？
    answer: >-
      いいえ。KV は結果整合性です。Cloudflare によれば、変更がほかのロケーションで見えるようになるまでに最大 60 秒、あるいはそれ以上かかることがあり、存在しないキーの検索結果もキャッシュされ、アトミックな操作が必要な場面には KV は向いていません。1 つのキーが受け付ける書き込みは 1 秒に 1 回です。セッション、カウンター、アクセスを決めるものはすべて D1 か Durable Objects に置き、KV は 1 分前のものでも構わないデータのキャッシュに使ってください。
  - question: Cloudflare Workers ではどのようにレート制限すべきですか？
    answer: >-
      制限をどれだけ正確にする必要があるかによります。Workers の Rate Limiting バインディングは近似的なもので、カウントは結果整合性であり、Cloudflare のロケーションごとに別々に適用されます。すべてのロケーションにわたる 1 つの厳密な制限には、Cloudflare は Durable Objects を勧めています。saasyland.com はカウンターを D1 に置いています。D1 は正確で、すべてのアイソレートで共有されますが、その代わりに数えるリクエストごとに 1 行の書き込みが発生します。KV はカウンターには向かないツールです。
  - question: Cloudflare Workers で SaaS を動かすにはいくらかかりますか？
    answer: >-
      Workers Paid は月額 $5 で、1,000 万リクエスト、3,000 万 CPU ミリ秒、D1 の読み取り 250 億行と書き込み 5,000 万行、D1 のストレージ 5 GB、KV の読み取り 1,000 万回と書き込み 100 万回が含まれます。R2 では毎月、ストレージ 10 GB、Class A 操作 100 万回、Class B 操作 1,000 万回が無料で、それを超えるストレージは 1 GB・月あたり $0.015 です。エグレス料金はかかりません。静的アセットへのリクエストは無料です。
  - question: R2 から非公開の動画やファイルをどう配信しますか？
    answer: >-
      Worker を通すか署名付き URL を使い、公開バケットからは決して配信しません。saasyland.com は、視聴者がそのレッスンを視聴できることを確認してから、有効期限と HMAC でパスに署名します。Worker はその署名を検証し、範囲リクエストに応答し、ファイル全体を各データセンターの Workers のキャッシュに保持します。Worker を経由しない代わりの方法が R2 の署名付き URL で、有効期間は最大 7 日、使えるのは S3 API のドメインだけです。
  - question: デプロイ時に D1 のマイグレーションはどのように適用されますか？
    answer: >-
      新しいコードが公開される前に適用されます。デプロイは、drizzle-kit が生成した SQL ファイルを wrangler d1 migrations apply で適用し、このコマンドは適用した各マイグレーションを d1_migrations テーブルに記録します。Worker をデプロイするのはその後です。短い間、以前の Worker が新しいスキーマに対して動くため、どのマイグレーションも、その前にデプロイされたコードで動作する必要があります。
  - question: D1 のマイグレーションで、外部キーを持つテーブルを作り直せますか？
    answer: >-
      できますが、外部キーを無効にする方法ではできません。D1 はすべてのクエリとマイグレーションで外部キーを強制し、各クエリは暗黙のトランザクションの中で実行されるため、よく使われる PRAGMA foreign_keys による切り替えは役に立ちません。D1 のドキュメントは、トランザクションの終了時に制約を確認する PRAGMA defer_foreign_keys と、事前に違反を見つける PRAGMA foreign_key_check を案内しています。
  - question: Cloudflare Worker はどれくらいの大きさにできますか？
    answer: >-
      2026年9月4日以降は、すべてのプランで非圧縮 64 MiB で、圧縮後のサイズの上限はありません。それ以前は、Free で圧縮後 3 MB、Paid で 10 MB でした。グローバルスコープは 1 秒以内に実行を終える必要があります。それでもサイズは時間に響きます。新しいアイソレートは最初のリクエストの前にスクリプト全体を読み込む必要があるため、saasyland.com はドキュメントとブログのコンテンツを Worker の外に移し、アップロードのサイズを半分以下にしました。

## 結論から

D1、KV、R2 を備えた Cloudflare Workers は、本番の SaaS を支えられます。saasyland.com は、マーケティングページ、ドキュメント、ブログ、サインイン、顧客ワークスペース、管理コンソール、ライセンス API、決済の Webhook、コースの動画を 1 つの Worker から配信しています。このプラットフォームでは、いくつかの習慣が報われ、それを欠くと痛い目にあいます。

- **D1 は SQLite で、各データベースは一度に 1 つのクエリにしか応答しません。** Workers Paid では 1 つのデータベースに最大 10 GB を保存でき、コードが判断している間に開いたままにしておけるトランザクションはありません。読み取り・判断・書き込みの処理はすべて、1 つのステートメントか 1 回の `batch()` として書いてください。
- **KV はデータベースではなくキャッシュです。** 結果整合性なので、セッション、カウンター、権限は D1 か Durable Objects に置きます。
- **R2 にはエグレス料金がありません**。そのため、各ファイルを誰が読めるかを自分で管理する仕組みが決める限り、動画やダウンロードの置き場所に適しています。
- **Worker のサイズはそのままレイテンシーになります。** 新しいアイソレートは応答する前にスクリプト全体を読み込むので、バンドルしたものはコールドリクエストの最初の 1 バイトに表れます。
- **マイグレーションは、それを必要とするコードより先に実行されます。** スキーマの変更はどれも、まだ稼働しているリリースで動作しなければなりません。

このガイドの残りでは、この 5 つの文をルールに落とし込み、それぞれを本番環境で示します。

## Workers が SaaS に合う場合と合わない場合

プラットフォームの機能一覧からではなく、プロダクトの形から考え始めてください。Workers がよく合うのは次のような場合です。

- **データがリレーショナルで、規模がほどほど。** ユーザー、アカウント、サブスクリプション、ライセンス、設定、コンテンツのメタデータは SQLite に無理なく収まり、データベースあたり 10 GB はその種の行にとってかなりの量です。
- **ほとんどのリクエストが短い。** ページのレンダリング、API 呼び出しへの応答、Webhook の検証、URL への署名にかかる CPU 時間は数ミリ秒で、Workers が課金するのも、アイソレートが得意とするのもまさにそれです。
- **トラフィックがグローバル、または急増する。** サイズを決めるべきサーバーはなく、アイドル時間ではなくリクエストごとに支払います。
- **ファイルが大きく、頻繁に読まれる。** 動画、ダウンロード、ビルド成果物は、R2 ではストレージと操作の料金がかかるだけで、帯域幅の料金は一切かかりません。

合わないのは次のような場合です。

- **データに 1 つの大きな共有データベースが必要。** 10 GB を超えると、D1 ではデータを複数のデータベースに分ける必要があります。これはもともとテナントごとに分かれているデータには向きますが、すべてのクエリが結合する 1 つのデータセットには向きません。
- **書き込みに、1 つのデータベースでの長いトランザクションや高い並行性が必要。** ほかのサービスを呼び出している間ロックを保持しなければならない処理や、シングルスレッドのデータベース 1 つでは吸収できない書き込みレートは、データベースサーバーのほうが扱いやすくなります。Cloudflare が既存のデータベースのためのグローバルなコネクションプーリングとクエリキャッシュと説明する Hyperdrive を使えば、すでに運用しているデータベースを Worker から使えます。
- **処理が長い、または CPU を大量に使う。** Workers Paid では 1 つのリクエストが使える CPU 時間は最大 5 分、メモリはアイソレートあたり 128 MB なので、動画のエンコードや大きなバッチジョブはほかの場所で行うか、分割して Queues で処理します。Cloudflare は Queues を、メッセージを「確実な配信で」送受信するものと説明しています。

saasyland.com は最初の種類のプロダクトです。ほどほどのリレーショナルデータ、短いリクエスト、頻繁に読まれる大きなファイルがあります。唯一の重い処理であるコースの動画のエンコードは、アップロードの後に、Worker の外にある FFmpeg を備えたマシンで実行します。

## データの種類ごとにふさわしい場所に置く

このプラットフォームでのミスの多くは、別の整合性モデルのために作られたプロダクトに何かを保存することから生じます。次の表は、どの SaaS でも私たちがもう一度下すであろう判断です。

| データ                                                                          | 置き場所               | 理由                                                                                   |
| ------------------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------- |
| ユーザー、セッション、注文、ライセンス、権限など、アクセスを決めるものすべて    | D1                     | リレーショナルで、一貫性があり、クエリでき、ほかのデータと結合できる                   |
| 高い書き込みレートのもとでも正確でなければならないカウンターと協調処理          | Durable Objects        | 強い整合性のストレージを持つ、世界で一意のオブジェクトで、協調処理のために作られている |
| 遅いサードパーティの応答のコピー、設定、フィーチャーフラグ                      | KV                     | どこでも読み取りが速く、1 分程度古くても誰も困らない                                   |
| 動画、ダウンロード、アップロード、ビルド成果物、バックアップ                    | R2                     | 大きなオブジェクト、エグレス料金なし、デフォルトで非公開                               |
| プリレンダリング済みの HTML、ハッシュ付きのスクリプトとスタイル、フォント、画像 | Workers の静的アセット | 静的アセットへのリクエストは無料で無制限                                               |
| 1 つのデータセンター内で再利用するレスポンス                                    | Workers の Cache API   | 速いがローカルで、Cloudflare によればその内容はほかのデータセンターに複製されない      |

その背景にあるルールは次のとおりです。アクセスを決めるものは一貫性のある場所に保存し、大きなものは R2 に置き、ビルド時に計算できるものは静的アセットにし、KV には捨てて取得し直せるものだけを置きます。

### 実例：saasyland.com のバインディング

saasyland.com は、`wrangler.jsonc` で宣言した次のバインディングでこの表に従っています。

| バインディング | プロダクト             | 保持するもの                                                                                 | コード内の場所                                                                |
| -------------- | ---------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `ASSETS`       | Workers の静的アセット | ビルドで生成されたプリレンダリング済みのページ、スクリプト、スタイル、フォント、画像         | `src/server.ts`                                                               |
| `DB`           | D1                     | ユーザー、セッション、ライセンス、Polar の注文のコピー、コース、動画、レート制限のカウンター | `src/integrations/drizzle-orm/` と `src/modules/`                             |
| `CACHE`        | KV                     | ほかのサービスの API からの 1 つのキャッシュ済みの応答                                       | `src/lib/github.ts`                                                           |
| `MEDIA`        | R2                     | コースの動画とカバー画像、レッスンの資料                                                     | `src/modules/video/`、`src/modules/course/`、`src/modules/lesson-attachment/` |
| `BUNDLES`      | R2                     | CLI の各リリースのテンプレートバンドル                                                       | `src/modules/license/`                                                        |

Durable Object はまだありません。レート制限のセクションで示すとおり、このサイトが持つカウンターはすべて D1 にあります。

## バインディング、環境、シークレット

Worker の設定ファイルはシステム全体の地図であり、コードとして扱う価値があります。

**やるべきこと：**

- **ステージごとに専用のリソースを用意する。** 本番環境は、データベース、名前空間、バケットを決してプレビューと共有すべきではありません。マイグレーションを実行したりテストデータを削除したりするプレビューのデプロイが、顧客のデータに触れられてはいけません。
- **完全にローカルのリソースで動く環境を 1 つ用意する。** ブラウザーテストには、ネットワークアクセスや認証情報なしで数秒でリセットできるデータベース、キャッシュ、バケットが必要です。
- **各環境に必要なシークレットを宣言し**、どれかが欠けている、空である、または `[UPDATE]` のようなプレースホルダーである間はデプロイを拒否します。
- **ビルドの前に設定を確認する。** 欠けたバインディングやプレースホルダーの ID は、デプロイが失敗した後よりも、10 分かかるビルドの前に見つけるほうが安上がりです。

**やってはいけないこと：**

- **シークレットをグローバルスコープで読み取ったり**、ビルドに焼き込んだりしないでください。リクエストの中で環境から読み取れば、ローテーションしたシークレットが再ビルドなしで有効になります。
- **異なるものを 1 つの鍵で署名しない。** R2 のセクションで示すように、1 つのシークレットから用途ごとに鍵を導出すれば、ある種類のファイルの署名を別の種類に流用されることはありません。
- **手で入力した ID が正しいことを当てにしない。** デプロイが見ている値と比較してください。

### 実例：4 つの環境と 2 つのデプロイ前チェック

`wrangler.jsonc` は、同じバインディングを持つ環境を定義しています。`production`、`preview`、`bun run dev` のために専用のローカルの D1 データベース、KV 名前空間、バケットをバインドする `development`、そしてブラウザーテストのスイートのために `.wrangler/test` 配下にローカルの D1 データベース、KV 名前空間、バケットを置く `test` です。各環境は必要なシークレットを列挙しています。どのデプロイの前にも、`scripts/verify-bindings.ts` は、環境にバインディングが欠けている場合、D1 や KV の ID がプレースホルダーのままの場合、本番環境がデータベース、名前空間、バケットをプレビューと共有している場合に失敗し、`scripts/prepare-deploy-secrets.ts` は、必要なシークレットが欠けている、空である、またはプレースホルダーである場合に、値を表示せずにキーの名前を挙げて失敗します。

2 つ目のチェックは、[#223](https://github.com/saasyland/saasyland.com/pull/223) に記録した実際のミスから生まれました。本番のシークレットファイルに Google OAuth のクライアント ID として `[UPDATE]` が残ったままで、当時のチェックは空の値しか拒否しなかったためデプロイがそれをアップロードし、Google でのサインインが `invalid_client` で失敗しました。修正は 2 層で行いました。ローカルからのデプロイのたびに各プロバイダーでサインインを開始し、送られる先の URL を検証する稼働中のサイトのチェックと、ビルドが始まる前のプレースホルダーの値の拒否です。どちらの層も単独でこのミスを見つけられたはずで、2 つ合わせれば二重に見つけられます。

## どのリクエストで Worker を実行するかを決める

Workers では、静的アセットへのリクエストは無料で無制限で、Worker を実行するリクエストには課金されます。そのため、アーキテクチャ上の最初の判断はルーティングに関するものになります。そもそもどのパスをコードに届けるべきか、です。

コードにしか追加できないものがレスポンスに必要な場合は、Worker を先に実行します。

- **レスポンスごとに変わるヘッダー**。たとえば新しい nonce を持つ Content Security Policy です。
- **訪問者ごとの書き換え**。たとえば地域別の価格やロケールのリダイレクトです。
- 公開されていないファイルの前に置く**アクセス制御**。

ハッシュ付きのスクリプトとスタイル、フォント、`robots.txt` のように、レスポンスが誰にとっても同じなら、アセットストアに直接応答させます。1 つ落とし穴があります。Cloudflare のドキュメントによれば、`_headers` ファイルのヘッダーは「Worker のコードが生成したレスポンスには適用されない」のです。セキュリティヘッダーをアセットストアのルールと Worker の 2 か所で設定するなら、1 つの定数にまとめ、両者が一致することをテストしてください。

### 実例：すべてのページで意図的に Worker を実行する

saasyland.com は、誰にとっても同じファイルを除くすべてのパスの前で Worker を実行しています。

```jsonc title="wrangler.jsonc"
  "assets": {
    "directory": "./public",
    "binding": "ASSETS",
    "html_handling": "drop-trailing-slash",
    "run_worker_first": ["/*", "!/assets/*", "!/fonts/*", "!/robots.txt", "!/llms.txt"],
  },
```

そのうえで、`src/server.ts` はリクエストを次の順に処理します。

1. エリアのリクエストハンドラーが、自分の受け持つパスを引き受けます。コースのエリアは `/media/` を、ライセンスのエリアは `/bundles/` を受け持ちます。
2. 正規でないロケールパスはリダイレクトされます。
3. `GET` と `HEAD` のリクエストは、すべてのプリレンダリング済みページを保持する `ASSETS` から探され、見つからなかったものだけが TanStack Start に届きます。
4. プリレンダリングされたものもレンダリングされたものも含め、すべての HTML レスポンスは Content Security Policy のためのそのレスポンス専用の nonce を受け取り、`private, no-cache` として送られます。すべてのレスポンスにセキュリティヘッダーが付きます。
5. 訪問者の国が対象である場合、ライセンスのエリアのドキュメントハンドラーが、地域別の価格に合わせてページを書き換えます。

理由は手順 4 と 5 です。静的なページは新しい nonce を持てず、訪問者の国を知ることもできません。nonce の側については [Cloudflare Workers での nonce を使った Content Security Policy](/blog/content-security-policy-nonces-cloudflare-workers) で詳しく説明しています。Worker を経由しないファイルには `public/_headers` から同じセキュリティヘッダーが付き、このファイルとコード内の定数が異なると `src/__test__/server.test.ts` が失敗します。その代償はページビューと画像ごとに課金されるリクエストで、コストのセクションでこれを数字にしています。

## コールドパスを短く保つ

Worker はアイソレートの中で動きます。Cloudflare によれば、アイソレートは「コンテナや仮想マシン上の Node プロセスよりも約 100 倍速く起動できる」ものです。これはアイソレートについては正しいのですが、新しいアイソレートでも、最初のリクエストを処理する前にスクリプト全体を読み込む必要があります。上限のページははっきりと、「バンドルが大きく、グローバルスコープの初期化コードが重いほど、起動時間は長くなる」と書いています。2026年9月4日以降、サイズの上限はすべてのプランで非圧縮 64 MiB なので、大きな Worker もデプロイはできます。ただ起動が遅くなるだけです。さらに、アイソレートは破棄されます。Cloudflare によれば 2 つのリクエストが同じアイソレートに届く保証はないため、トラフィックがほどほどのサイトでは一日中コールドスタートが発生します。

ここから導かれるルールは次のとおりです。

1. **エントリーが静的にインポートするコードを予算として扱う。** エントリーファイルがインポートするものと、それらのファイルがインポートするものはすべて、最初のリクエストの前に評価されます。定数と小さなヘルパーだけにとどめてください。
2. **重いコードは、リクエストが必要とする場所でインポートする。** ハンドラーの中で `await import()` によって読み込む決済 SDK、データベースクライアント、メールライブラリは、それを呼び出さないリクエストでは何のコストもかかりません。
3. **フレームワークが最初に読み込むものに注意する。** すべてのルートモジュールをインポートするルーターや、すべてのコンテンツをインポートする検索ルートは、そのコードをすべてのコールドリクエストに載せてしまいます。
4. **コンテンツをスクリプトの外に出す。** 誰にとっても同じページは静的アセットとしてプリレンダリングでき、ビルド時にしか変わらないデータは静的ファイルとして書き出してブラウザーで読めます。
5. **アップロードと起動を計測する。** Cloudflare の上限のページは、非圧縮の `Total Upload` を確認するために `wrangler deploy --outdir bundled/ --dry-run` を勧め、グローバルスコープの CPU プロファイルを取る `wrangler check startup` を挙げ、デプロイ時に Wrangler が `startup_time_ms` を報告するとしています。
6. **コールドリクエストは実際のデプロイで計測する。** ローカルのサーバーが、エッジのアイソレートと同じようにコールドスタートすることはありません。

### 実例：コールドパスを半分にした 2 つのプルリクエスト

**ルートツリーはコンテンツをインポートしなくなりました。** TanStack Start は、サーバー関数の呼び出しも含め、どのリクエストを処理する前にもルートツリーを読み込みます。2026年11月17日にマージされた [#236](https://github.com/saasyland/saasyland.com/pull/236) より前は、ルートツリーがドキュメントの検索をインポートしており、その検索がすべての言語のすべてのドキュメントページとブログ記事のコンパイル済み MDX をインポートしていました。各ページの MDX はリクエストが必要としたときだけ、検索のコードは誰かが検索したときだけ読み込むようにしたことで、ルートツリーは 1,635 モジュール・21.7 MiB から 296 モジュール・4.9 MiB になり、プレビューデプロイでは、新しいアイソレートでの最初のサーバー関数が中央値で 481 ms から 341 ms になりました。

**Worker はコンテンツをまったく保持しなくなりました。** 2026年11月20日にマージされた [#239](https://github.com/saasyland/saasyland.com/pull/239) は、ドキュメント、ブログ、検索インデックスを、ビルドが `/assets/` 配下に書き出すファイルに変えます。すべてのドキュメントページとブログ記事はプリレンダリングされ、クライアント側のナビゲーションはブラウザーでそれらのインデックスを読み、デプロイされる Worker はコンパイル済みページのインポートをすべて例外を投げるモジュールに解決し、いずれかのページのコンテンツが Worker に入り込むとビルドが失敗します。アップロードは 30,115 KiB から 13,465 KiB になり、プレビューデプロイの新しいアイソレートでは、ハンドラーが実行されるまでの待ち時間が中央値で 934 ms から 561 ms に、最初の 1 バイトまでの時間が 1,145 ms から 676 ms に下がりました。ドキュメント内のナビゲーションでは、今では Worker へのリクエストが一切発生しません。また、各アイソレートがインデックスを作っている間、最初のクエリに 7〜16 秒かかっていたドキュメントの検索は、今では 2 秒未満で応答します。

計測からわかったのは、数字が動いたのはリクエストが評価するコードではなく（こちらはほぼ変わりませんでした）、Cloudflare が新しいアイソレートに読み込まなければならないスクリプトのサイズのほうだったということです。起動時に実行されるのは小さなエントリーだけなので、Wrangler が報告した Worker の起動時間は 2 ms でした。待ち時間は、新しいアイソレートにスクリプトを読み込むことから生じていました。どのビルドのどのアイソレートが応答したかを確かめるため、各コールドサンプルを `cf-ray` ヘッダーで `wrangler tail` と照合しました。

## D1：エッジの SQLite として設計する

D1 は、Cloudflare のストレージ、レプリケーション、API で包まれた SQLite です。それを前提に設計すれば快適なデータベースですが、Postgres のつもりで設計すると手こずります。

### データベースの形を知る

2 つの性質が、ほかのすべてを決めます。

**各データベースは一度に 1 つのクエリを処理します。** Cloudflare のドキュメントには、「個々の D1 データベースは本質的にシングルスレッド」であり、「最大スループットはクエリの所要時間に直接関係する」とあります。1 ms で終わるクエリなら 1 秒間に多くを処理できますが、テーブルを 200 ms かけてスキャンするクエリは、その 200 ms の間ほかのすべてのクエリを止めます。ここでは、コネクションプールを持つサーバーよりも、インデックスを使う短いクエリと少ないラウンドトリップが重要になります。

**スケールは、大きなデータベースではなく、データベースの数で得ます。** D1 は「複数の小さな（10 GB の）データベースにわたる水平スケールアウトを前提に設計されて」おり、Workers Paid には最初の 100,000 個のデータベースが含まれます。データがもともとテナントごとに分かれているなら、テナントごとに 1 つのデータベースという設計はサポートされており、それぞれが自分専用のスレッドを持ちます。1 つの共有データセットなら、10 GB を超える日のための計画を、その日が来る前に立ててください。

読み取りもスケールアウトできます。D1 のリードレプリケーションはレプリカからクエリに応答し、「リードレプリカに追加のストレージ料金やコンピューティング料金はかからない」のですが、これは Sessions API を通じてしか機能しません。「リードレプリケーションを使うには、D1 Sessions API を使う必要がある」とされ、この API は「セッション内のすべてのクエリについて逐次一貫性」を保ちます。セッションがなければ、すべてのクエリはプライマリに送られます。

### インタラクティブなトランザクションなしでのアトミックな書き込み

D1 はステートメントを自動コミットモードで実行し、「バッチにまとめたステートメントは SQL トランザクション」です。`batch()` はステートメントを順に実行し、1 つが失敗すると、D1 は「シーケンス全体を中止またはロールバック」します。できないのは、トランザクションを開き、行を JavaScript に読み込んで判断し、あとでコミットすることです。アトミックでなければならない判断は、すべて SQL の中で行う必要があります。ほぼすべてのケースは、次の 5 つのパターンでまかなえます。

1. **条件付きの 1 つのステートメント。** アップサート、または条件がルールそのものになっている `UPDATE … WHERE` は、判断と書き込みを 1 ステップで行います。どちらに転んだかは、変更された行数を読めばわかります。
2. **審判としての制約。** 同時に行われた 2 つの挿入のどちらが勝つかは一意インデックスが決めます。負けた挿入のエラーは、クラッシュさせずに、きれいな `409 Conflict` に変換します。
3. **`INSERT … SELECT … WHERE`。** クエリが条件を満たすと判断した場合にだけ行を挿入する処理を、1 つのステートメントで行います。
4. **複数のステートメントにはバッチ。** 2 つの書き込みを一緒に行わなければならないときは 1 つのバッチとして送り、それらと一貫していなければならない読み取りも同じバッチに加えます。
5. **順不同で届くイベントにはバージョン。** Webhook は再試行され、互いを追い越します。イベント自身のタイムスタンプかバージョンを保存し、それが新しい場合にだけ書き込むようにします。

ほかのデータベースでは自然に感じられるパターン、つまり行を読み、コードで確認してから書き込むという方法は避けてください。2 つのリクエストが、どちらかが書き込む前に両方とも古い行を読む可能性があります。

### 実例：4 つのアトミックな書き込み

**上限を超えられないカウンター。** レートリミッターは、リクエストを上限ごとに 1 つのアップサートで数えます。`setWhere` の条件によって、すでに上限を超えたリクエストはデータベースが数えることを拒否するので、同じクライアントを同じ瞬間に数える 2 つのアイソレートが、両方とも上限をすり抜けることはありません。

```ts title="src/lib/rate-limit.ts"
const upsertCounter = (insert: CounterInsert, input: RateLimitInput, now: Date) => {
  const expired = lte(rateLimit.expiresAt, now)

  return insert
    .onConflictDoUpdate({
      set: {
        attempts: sql`case when ${expired} then 1 else ${rateLimit.attempts} + 1 end`,
        expiresAt: sql`case when ${expired} then ${windowEnd(input, now).getTime()} else ${rateLimit.expiresAt} end`,
      },
      setWhere: not(refuses(input, now)),
      target: rateLimit.key,
    })
    .returning({ resetsAt: rateLimit.expiresAt })
}
```

**前にしか進まない Webhook のコピー。** saasyland.com は Polar のすべての注文のコピーを保持しています。Polar は、注文を作成したイベントより先に更新を届けることも、同じものを 2 回届けることもあるので、アップサートは少なくとも同じくらい新しいコピーでしか行を上書きしません。

```ts title="src/modules/order/use-cases/record-order.ts"
export const recordOrder = async (polarOrder: models.Order): Promise<void> => {
  const copy = {
    changedAt: new Date(polarOrder.modified_at ?? polarOrder.created_at),
    checkoutId: polarOrder.checkout_id,
    currency: polarOrder.currency,
    customerId: polarOrder.customer_id,
    description: polarOrder.description,
    invoiceNumber: polarOrder.invoice_number,
    placedAt: new Date(polarOrder.created_at),
    productId: polarOrder.product_id,
    refundedAmount: polarOrder.refunded_amount,
    status: polarOrder.status,
    subscriptionId: polarOrder.subscription_id,
    totalAmount: polarOrder.total_amount,
    userId: polarCustomerAccount(polarOrder.customer),
    ...polarOrderTerms(polarOrder),
  }

  await db
    .insert(order)
    .values({ id: polarOrder.id, ...copy })
    .onConflictDoUpdate({ set: copy, setWhere: lte(order.changedAt, copy.changedAt), target: order.id })
}
```

**遅れて届いた付与では取り消せない返金。** 注文が返金されると、1 つのバッチの中で、ライセンスが取り消され、その注文が挿入専用のテーブルに記録されます。ライセンスを付与するイベントが返金の後に届いた場合、付与の処理はその行を見つけて何もしません。

```ts title="src/modules/license/use-cases/revoke-license.ts"
export const revokeLicense = async ({ polarOrderId, status, userId }: RevokeLicenseInput): Promise<void> => {
  const matchingOrder = and(eq(license.userId, userId), eq(license.polarOrderId, polarOrderId), ne(license.status, LICENSE_STATUS.REFUNDED))
  await db.batch([
    db.insert(revokedLicenseOrder).values({ polarOrderId, userId }).onConflictDoNothing(),
    db.update(license).set({ status }).where(matchingOrder),
  ])
}
```

**審判としての一意制約。** 2 人の管理者が同じスラッグを同時に作成しうる場面では、挿入はそのまま実行され、一意インデックスが判断します。`rethrowAsConflict` は、負けた側のエラーをアプリケーションの `CONFLICT` コードに変換します。

```ts title="src/integrations/drizzle-orm/drizzle.errors.ts"
export const rethrowAsConflict = (error: unknown): never => {
  if (isUniqueViolation(error)) {
    throw new AppError(ERROR_CODES.CONFLICT)
  }

  throw error
}
```

### 少ないラウンドトリップ、小さなステートメント

どのクエリも Worker からデータベースへのラウンドトリップであり、D1 ではデータベースの唯一のスレッドも占有します。次の 3 つのルールで、その両方のコストを抑えられます。

- **リクエストに必要な読み取りをバッチにまとめる。** ページング付きのテーブルにはページと合計件数が必要なので、両方を 1 回の `batch()` で送ります。saasyland.com の管理画面の一覧はまさにそうしており、CLI ライセンス API はライセンスの検索と 2 つのレート制限のカウンターを 1 つのバッチとして送るので、リクエストを受け付けるのにかかる D1 への往復は 1 回だけです。
- **呼び出しあたりとクエリあたりの上限に注意する。** Worker の 1 回の呼び出しで実行できるクエリは Workers Paid で 1,000 回、Free で 50 回で、1 つのクエリにバインドできるパラメーターは最大 100 個なので、カラムが 10 個のテーブルへの複数行の挿入では 1 つのステートメントに 10 行しか入りません。一括インポートは小さな挿入のバッチになります。
- **長い処理を 1 つのクエリに詰め込まない。** クエリの実行時間は最大 30 秒です。大きなテーブルのバックフィルは、ステートメントごとに上限のある範囲だけを処理すべきです。saasyland.com のレートリミッターも、テーブル全体を一掃するのではなく、リクエストごとに決まった数までの期限切れカウンターを削除しています。

### インデックスとクエリのコスト

D1 は読み取った行と書き込んだ行に課金し、「読み取り行数は、各行のサイズにかかわらず、クエリが読み取った（スキャンした）行の数を測る」ものです。インデックスのないクエリは毎回テーブルをスキャンし、お金とデータベースの唯一のスレッドの両方を消費します。クエリの結果は、そのクエリが何をしたかを教えてくれます。結果の `meta` には、「このクエリが読み取った（スキャンした）行の数」である `rows_read` と、`rows_written` が含まれます。推測する前に、最も頻繁に実行されるクエリについてこれらをログに記録してください。

インデックスもただではありません。「書き込みがインデックス付きのカラムを含む場合、インデックスによって書き込み行が 1 行追加される」からです。Cloudflare 自身は、読み取り行数の削減が「ほぼすべてのケースで」それを相殺すると助言していますが、カウンターのテーブルのようにリクエストのたびに書き込まれるテーブルでは、両方を数えてください。

### 実例：1 つのスキーマ、1 つのデータベース

`src/integrations/drizzle-orm/drizzle.database.ts` が `env.DB` の上にサーバー専用の Drizzle クライアントを作り、各テーブルは `src/modules/<table>/` に専用のモジュールを持ち、そこにスキーマ、Zod スキーマ、ユースケースがあります。ID は UUID v7 の文字列です。ただし、Polar の注文とサブスクリプションを Polar 自身の ID のままコピーするテーブルは例外です。日付はミリ秒単位の整数です。Better Auth は、ユーザー、セッション、アカウント、検証トークン、二要素認証のシークレットを Drizzle アダプターを通じて同じデータベースに書き込むため、管理コンソールはそれらをほかのテーブルと同じようにライセンスや注文と結合できます。このサイトのデータベースは環境ごとに 1 つです。データはテナントごとではなく共有のもので、10 GB にはほど遠いからです。

## ダウンタイムのないマイグレーション

Workers では、デプロイはコードについてはアトミックですが、データについてはそうではありません。新しい Worker は古い Worker を一度に置き換えますが、データベースは前か後に別のステップでマイグレーションされます。前を選び、そのうえで、まだ稼働しているリリースがそれに対して動けるように、すべてのマイグレーションを書いてください。

**ルール：**

- **マイグレーションはスキーマから生成し、SQL をレビューし、両方を一緒にコミットする。** マイグレーションは本番環境に対して一度だけ実行されるコードです。コードと同じように読んでください。
- **マイグレーションは、それを使うコードをデプロイする前に**、同じパイプラインの中で適用します。そうすれば、リリースが自分より古いスキーマに対して動くことはありません。
- **拡張してから縮小する。** あるリリースで NULL を許容するカラム、テーブル、インデックスを追加し、それを読み書きするコードをリリースし、古い形は後のリリースで削除します。名前の変更は、複数のリリースにわたる追加、バックフィル、切り替え、削除です。
- **実行済みのマイグレーションは決して編集しない。** Wrangler は適用したファイルを記録しており、変更したファイルを再び実行することはありません。代わりに新しいマイグレーションを書いてください。
- **バックフィルは小分けにする。** 30 秒というクエリの上限と単一のスレッドのどちらを考えても、1 回の大きな更新より多数の小さな更新のほうが適しています。
- **テーブルを作り直すときは外部キーに注意する。** SQLite は、カラムの定義の一部を、新しいテーブルを作成して行をコピーし、入れ替えることで変更します。D1 によれば、「D1 はデフォルトで、すべてのクエリとマイグレーションにおいて外部キー制約が有効であることを強制する」うえ、各クエリは暗黙のトランザクションの中で実行されるため、外部キーを無効にしても役に立ちません。D1 のドキュメントは、トランザクションの終了時に制約を確認する `PRAGMA defer_foreign_keys = on` と、事前に違反を見つける `PRAGMA foreign_key_check` を案内しています。テーブルを作り直すマイグレーションが生成されたら、この点を念頭に置いて読んでください。
- **CI ですべてのマイグレーションを空のデータベースからテストする。** そうすれば、自分のマシンでしか動かないマイグレーションは、本番環境に届く前に失敗します。
- **ロールバックは必要になる前に計画する。** コードのロールバックは簡単ですが、データのロールバックはそうではありません。D1 の Time Travel は、データベースを過去の時点に復元します。Workers Paid では最大 30 日前まで、Free では 7 日前までです。これはデータを壊したマイグレーションへの対処法であって、カラムを追加しただけのマイグレーションへの対処法ではありません。

### 実例：パイプラインと追加のみの変更

saasyland.com では、スキーマはテーブルのモジュールにあります。`bun run db:generate` はスキーマの変更を `src/integrations/drizzle-orm/migrations/` 内のタイムスタンプで始まる SQL ファイルに変換し、このファイルは変更と一緒にコミットされます。Vitest は、統合テストを実行する前に、すべてのマイグレーションをインメモリの SQLite データベースに適用します。Wrangler はそれらを D1 に適用し、適用した各ファイルを `d1_migrations` テーブルに記録するので、デプロイは新しいものだけを実行します。

```json title="package.json"
    "db:migrate:production": "vp exec wrangler d1 migrations apply DB --env production --remote",
```

プルリクエストはプレビューの Worker の新しいバージョンをデプロイせずにアップロードし、Cloudflare はそれをデプロイと同じように検査します。`main` へのマージは共有のプレビューを、続いて本番環境をデプロイします。どちらのデプロイも同じ手順を実行します。バインディングを確認し、ビルドし、その環境のマイグレーションを適用してから、`wrangler deploy` を実行します。データベースが先に変わるので、短い間、まだ稼働している Worker が新しいスキーマに対して動きます。ライセンスの配信記録を追加したマイグレーションは、これに耐えられる種類の変更を示しています。以前のリリースが単に無視する、NULL を許容する 3 つのカラムです。冒頭は次のとおりです。

```sql title="src/integrations/drizzle-orm/migrations/20261116195637_great_blazing_skull.sql"
ALTER TABLE `license` ADD `activated_at` integer;--> statement-breakpoint
ALTER TABLE `license` ADD `delivered_at` integer;--> statement-breakpoint
```

同じルールがロールバックも安全にします。本番環境はプルリクエストでコードを元に戻すことでロールバックし、マイグレーションは元に戻さないので、古いコードは、すでに互換性のあった新しいスキーマに対して動きます。[CI/CD のページ](/docs/tooling/ci-cd)は、これをすべての変更に対するルールとして定めています。スキーマの変更はどれも、その前にデプロイされたアプリケーションで動作しなければならない、というものです。

## KV：記憶の長いキャッシュ

KV はどこでも読み取りが速い一方、全体の値が揃うまでには時間がかかります。Cloudflare のドキュメントには、「変更がほかのグローバルネットワークのロケーションで見えるようになるまでに、最大 60 秒、あるいはそれ以上かかることがある」こと、「キーが存在しないことを示す否定的な検索結果もキャッシュされるため、同じ遅延が生じる」こと、そして「アトミックな操作のサポートが必要なアプリケーションには、KV は理想的ではない」ことが書かれています。1 つのキーが受け付ける書き込みは 1 秒に 1 回で、読み取った値を読み手の近くにどれだけキャッシュしておくかを決める `cacheTtl` は 30 秒未満にできません。

そのため KV は、一部のデータには最適ですが、それ以外には危険です。

**適した用途：** 遅いサードパーティの応答のコピー、手で変更する設定やフィーチャーフラグ、ときどき作り直す事前計算済みのデータです。

**適さない用途：** セッション（取り消されたセッションが別の都市でまだ 1 分間使えるのはセキュリティのバグです）、カウンター（2 つのロケーションが同じ古い値を増やすと更新が失われます）、アクセスを決めるもの、キーあたり 1 秒に 1 回を超えて書き込むものです。Better Auth の Cloudflare ガイドも、自身のデータについて同じ結論に達しています。KV は「`secondaryStorage` の契約を満たせない」というものです。

**うまくいくパターン：**

- **取得時刻を値の中に保存する。** 有効期限だけに頼るのではなく、データと一緒に `fetchedAt` を保持すれば、読み手はそのまま返すか、返してからバックグラウンドで更新するか、先に取得し直すかを判断できます。
- **`waitUntil` でバックグラウンドで更新する。** 訪問者はキャッシュされた値をすぐに受け取り、更新はレスポンスの後、`waitUntil()` が許す 30 秒以内に完了します。
- **読み取り時に検証する。** 古いリリースが書き込んだ値や、失敗したリリースが中途半端に書き込んだ値は、信頼せずに存在しないものとして扱うべきです。
- **完全な値だけを書き込む。** 更新が途中で失敗したら、不完全な一覧を保存せず、古いエントリーを残します。
- **リクエストの間で Worker のメモリに何も保持しない。** Cloudflare はいつでもアイソレートを破棄でき、2 つのリクエストが同じアイソレートに届く保証はないので、モジュールレベルのキャッシュは、ときどきしか機能しないキャッシュです。

### 実例：捨てられる 1 つのエントリー

saasyland.com の `CACHE` 名前空間が保持するエントリーはちょうど 1 つ、サイトに表示する GitHub のスター数で、<RepositoryFact name="starCountRefreshHours" unit="hour" />が過ぎると更新されます。

このエントリーは値を取得時刻とともに保存し、読み取る側はそれを Zod で検証し、存在しないエントリーや不正なエントリーは取得し直します。古くなったスター数はそのまま返して、バックグラウンドで更新します。

```ts title="src/lib/github.ts"
export const getStarCount = createServerFn({ method: "GET" }).handler(async () => {
  const cached = cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data

  if (cached === undefined) {
    return fetchStarCount()
  }

  if (Date.now() - cached.fetchedAt >= STAR_COUNT_REFRESH_AFTER_MS) {
    waitUntil(fetchStarCount())
  }

  return cached.count
})
```

セッション、レート制限、ライセンス、そのほかアクセスを決めるものはすべて D1 にあります。

## R2：Worker の奥にある非公開のファイル

R2 は大きなオブジェクトをエグレス料金なしで保存するので、動画やダウンロードの経済性が変わります。請求額はストレージと操作の分だけで、視聴時間の分は一切ありません。設計上の問題は、どの訪問者がどのオブジェクトを読めるかを誰が決めるかです。

**バケットは非公開にする。** 販売するものや個人的なものについては、パブリックアクセスと `r2.dev` の URL を無効のままにしておくべきです。そのうえで、アクセスを許可する方法を選びます。

| 方法                    | 仕組み                                                                                                                                  | 選ぶべき場合                                                                                                           |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Worker が署名したパス   | コードが有効期限付きでパスに署名し、Worker が署名を確認してバインディング経由でオブジェクトを読む                                       | 自分のドメイン、エッジでのキャッシュ、範囲リクエストの処理、独自のヘッダー、そして読み取りのたびのチェックが欲しい場合 |
| R2 の署名付き URL       | R2 の API 認証情報で署名された URL で、`GET`、`HEAD`、`PUT`、`DELETE` に「1 秒から 7 日まで」有効。クライアントは R2 と直接やり取りする | アップロードやダウンロードで Worker を経由させたくない場合。ただし「カスタムドメインでは使えない」点に注意             |
| 読み取りのたびに Worker | Worker がリクエストごとにセッションを確認し、オブジェクトをストリーミングする                                                           | ファイルが小さく少ない場合、またはアクセス権が刻々と変わる場合                                                         |

どれを選んでも、どちらの種類の URL もベアラートークンです。R2 のドキュメントは「署名付き URL をベアラートークンとして扱う」よう求めており、署名済みパスも同じで、持っている人なら誰でも期限が切れるまで使えます。誰が読めるかは URL を発行するときに確認し、有効期限は短くし、署名済み URL の全体を決してログに記録しないでください。

**上手な署名：**

- **重要なものすべてに対して HMAC を使う：** オブジェクト、有効期限、そのほか変わってはならないものすべてです。
- **1 つのシークレットから HKDF で用途ごとに鍵を導出し**、動画の署名をダウンロードの署名として流用できないようにします。
- **有効期限は 1 時間などの決まった単位に切り上げ**、その単位のうちに発行された URL が同一になり、キャッシュが再利用できるようにします。
- プレーヤーが多数のファイルを取得する場合は、**ファイルごとではなくプレフィックスに署名します**。セグメントを相対パスで参照する HLS のプレイリストなら、署名済みの 1 つのプレフィックスでストリーム全体をカバーできます。

**上手な配信：**

- **`Range` リクエストに `206` で応答する。** プレーヤーやダウンロードマネージャーはこれに依存しています。
- **ファイル全体を署名なしのキーでエッジにキャッシュし**、すべての視聴者が 1 つのコピーを共有するようにします。ただし、Workers の Cache API はローカルです。Cloudflare によれば「キャッシュの内容は、元のデータセンターの外には複製されない」うえ、`cache.put` は「階層型キャッシュと互換性がない」ので、各データセンターは各ファイルを R2 から一度ずつ読み込みます。

**上手なアップロード：**

- Worker へのリクエストボディは Free と Pro のプランで 100 MB、Business で 200 MB に制限されているので、大きなアップロードはこの上限より小さいパートに分けて R2 に送ります。Worker を通すマルチパートアップロードにするか、署名付きの `PUT` やツールで R2 に直接送ります。
- **重い処理は Worker の外で行う。** リクエストの中での動画のエンコードは Worker の CPU とメモリの上限では手が届かないので、アップロードの後に、それができるマシンで行います。
- **オブジェクトについて後で知る必要があることは、書き込むときにカスタムメタデータとして保存し**、後のリクエストがオブジェクトを読まずに `head()` から応答できるようにします。

### 実例：コースの動画と CLI のバンドル

saasyland.com は、コースの動画とカバー画像、レッスンの資料を `MEDIA` に、CLI のテンプレートバンドルを `BUNDLES` に置いており、どちらも非公開です。管理者がレッスンの録画をレッスンエディターにドロップすると、ブラウザーはそれを Worker 経由で R2 のマルチパートアップロードに <RepositoryFact name="videoUploadPartMegabytes" /> MB ずつのパートとして送り、各パートはセッションに照らして確認されます。アップロードの後、FFmpeg を備えたマシンがそれをアダプティブ HLS にエンコードします。最大 <RepositoryFact name="videoTopRendition" /> のレンディション、<RepositoryFact name="videoSegmentSeconds" unit="second" />のセグメント、ポスター、シークプレビュー用のストーリーボード、言語ごとの字幕を作り、ストリームを Wrangler でアップロードします。D1 のレッスンは `video` テーブルの行を指し、動画がプレースホルダーとしてマークされたレッスンは、再生される代わりに収録中として表示されます。

訪問者がレッスンを開くと、`getLessonPlayback` が D1 からレッスンを読み込み、`hasLessonAccess` でこの視聴者がそれを視聴できることを確認し、そのうえで初めてパスに署名します。

```ts title="src/modules/video/video.playback.ts"
export const createPlayback = async ({ now, secret, video }: PlaybackGrant) => {
  const expires = signedExpiry({ now, ttlSeconds: PLAYBACK_TTL_SECONDS })
  const signature = await signHmac({ info: SIGNING_INFO, message: signedMessage({ expires, videoId: video.id }), secret })
  const base = `${MEDIA_PATH_PREFIX}/${expires}.${signature}/${video.id}`

  return {
    captions: video.captionLocales.map((locale) => ({ locale, src: `${base}/captions/${locale}.vtt` })),
    poster: `${base}/${VIDEO_FILES.POSTER}`,
    posterSmall: `${base}/${VIDEO_FILES.POSTER_SMALL}`,
    src: `${base}/${VIDEO_FILES.MASTER_PLAYLIST}`,
    storyboard: `${base}/${VIDEO_FILES.STORYBOARD_TRACK}`,
  }
}
```

署名は、HKDF が動画の再生専用に認証シークレットから導出した鍵による HMAC-SHA-256 です。有効期限は少なくとも <RepositoryFact name="signedMediaHours" unit="hour" />先で、1 時間単位に切り上げられます。`serveMedia` はメソッド、ファイル名、署名を確認し、`Range` リクエストには R2 から直接 `206` で応答し、ファイル全体を署名を含まないキーで Workers のキャッシュに保持します。レッスンの資料も `/media/downloads/` の下で同じ方式を使い、専用の鍵と、少なくとも <RepositoryFact name="signedDownloadHours" unit="hour" />有効なリンクを持ちます。Worker が受け付けるアップロードは資料、コースのカバー画像、レッスンの録画で、いずれも管理者からのものです。上限は資料 1 件あたり <RepositoryFact name="attachmentMaxMegabytes" /> MB、カバー画像のサイズごとに <RepositoryFact name="courseCoverMaxMegabytes" /> MB、録画 1 本あたり <RepositoryFact name="videoUploadMaxGigabytes" /> GB です。カバー画像は公開されており、`serveCover` が `/media/covers/` の下で署名なしに配信し、新しいカバー画像には毎回新しい ID が付くため、1 年間キャッシュできます。

バンドルはメタデータのルールを示しています。CLI の各リリースは、内容の SHA-256 を R2 のカスタムメタデータとして付けてテンプレートバンドルをアップロードし、ライセンス API はバンドルのリクエストに対して、そのダイジェストを `head()` で読み取り、<RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />有効なダウンロード URL に署名します。2026年11月17日にマージされた [#208](https://github.com/saasyland/saasyland.com/pull/208) より前は、Worker がリクエストのたびにアーカイブをダウンロードし、展開し、ハッシュを計算しており、ローカルでの計測では 1.7 MB のバンドルで約 31 ms の CPU 時間がかかっていました。メタデータを読むようにしたことで、バンドルのサイズにかかわらず約 3 ms になりました。

## アイソレートをまたいで機能するレート制限

レート制限の質は、そのカウンターの質で決まります。1 つのクライアントからのリクエストは、多くのロケーションの多くのアイソレートに届くので、メモリ上のカウンターでは何も数えられません。カウントを保持できる場所は 4 つあります。

| 選択肢                                  | 正確さ                                                                                  | コストとトレードオフ                                                                                   |
| --------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Workers の Rate Limiting バインディング | 近似的：カウントは「Cloudflare のロケーションごとに別々に適用される」                   | 管理するストレージは不要。ウィンドウは 10 秒か 60 秒のみ                                               |
| D1 のカウンター                         | 1 つのデータベースが判断するので、正確で共有される                                      | 数えるリクエストごとに 1 行、インデックスがあれば 2 行の書き込みが発生し、データベースのスレッドを使う |
| Durable Objects                         | 正確。「すべてのロケーションにわたる 1 つの厳密な制限が必要」な場合の Cloudflare の答え | 運用するプロダクトが 1 つ増える。まさにこの種の協調処理のために作られている                            |
| KV                                      | 不適切：結果整合性で、キーあたり 1 秒に 1 回の書き込み                                  | 制限しようとしている負荷のもとで更新が失われる                                                         |

**どれにも当てはまるルール：**

- **信頼できるものをキーにする。** Cloudflare では、クライアントのアドレスは `cf-connecting-ip` ヘッダーです。ネットワークではなく人に付いて回る制限には、アカウント、API キー、メールアドレスを加えます。
- **保存する識別子はハッシュ化する。** メールアドレスをキーにしたカウンターが、アドレスそのものを含む必要はありません。
- **可能なら、処理と同じラウンドトリップで数える。** そうすれば、制限によるレイテンシーの増加はありません。
- **ストアが停止したときにどうなるかを決める。** フェイルクローズでは、処理できたはずのトラフィックを拒否します。フェイルオープンでは、まさに最も弱っているときに攻撃者を通してしまいます。エンドポイントごとに選び、それを書き残してください。
- **後片付けは上限のあるステップで行い**、トラフィックとともに大きくなる一掃処理は決して使いません。

### 実例：D1 のカウンターとフェイルクローズ

saasyland.com は、すべてのカウンターを 1 つの `rate_limit` テーブルに置いており、これを Better Auth のリミッター、サーバー関数のミドルウェア、CLI ライセンス API が共有しています。クライアントとアクションごとに <RepositoryFact name="rateLimitWindowSeconds" unit="second" />あたり、機密性の高い操作は <RepositoryFact name="sensitiveRateLimit" /> 回、トークンの引き換えは <RepositoryFact name="tokenRateLimit" /> 回まで許可され、確認メールとリセットメールは、アドレスの SHA-256 ハッシュをキーとして、種類ごとにアドレスあたり 1 時間に <RepositoryFact name="recipientEmailsPerHour" /> 通までに制限されます。数える各リクエストは上で示したアップサートで、拒否を見つける読み取りと、上限のある件数の期限切れカウンターの削除と一緒に 1 つのバッチとして送られます。D1 に到達できない場合、リミッターは拒否します。

```ts title="src/lib/rate-limit.ts"
export const consumeRateLimit = async (input: RateLimitInput): Promise<RateLimitDecision> => {
  try {
    return await countRequest(input)
  } catch (error) {
    console.error("Rate-limit storage unavailable", error)
    return { allowed: false, retryAfter: input.windowSeconds }
  }
}
```

サインイン、パスワードのリセット、ライセンスの有効化では、フェイルクローズが正しいデフォルトです。拒否されたリクエストのコストは再試行で済みますが、受け付けたリクエストのコストはアカウントそのものになりかねないからです。D1 での正確なカウンターの代償は書き込みです。数えるリクエストごとに 2 行を書き込むとすると、Workers Paid に含まれる 5,000 万行で、最初の 1 ドルの追加料金が発生するまでに月におよそ 2,500 万件のリクエストを数えられます。制限にそれ以上が必要な場合や、1 つのデータベースが受け持つべき量を超える毎秒の書き込みが必要な場合は、Durable Objects が次の一歩です。

## デプロイ、検証、監視

Workers でのデプロイは数秒で終わるので、その前後の手順を省きたくなります。以下の各手順は、saasyland.com 自身のデプロイで実行されています。

1. ビルドの前に**設定とシークレットを確認する**：バインディングがそろっていること、プレースホルダーの ID がないこと、本番環境がプレビューとリソースを共有していないこと、必要なシークレットがすべて設定されていること。
2. **ビルドし、ビルドを確認する：** コールドパスの予算、プリレンダリングすべきページがすべてプリレンダリングされていること、サーバー専用のコードがブラウザーに届いていないこと。
3. **対象のデータベースをマイグレーションする。**
4. **デプロイする。**
5. 実際のリクエストで**稼働中のサイトを確認する**：ページが応答すること、サインインが正しい OAuth クライアントにリダイレクトすること、ヘッダーが期待どおりであること。

プレビューも、専用のリソースに対して同じパイプラインで実行してください。そして、自分の死角を知っておいてください。saasyland.com では、Cloudflare のボット対策が CI ランナーからのリクエストに `403` で応答するため、稼働中のサイトのチェックはローカルからのデプロイで実行し、CI からのデプロイではそれ以外のすべてを実行します。

**ログ。** Workers Logs を使うには、設定で `observability` を有効にする必要があります。Cloudflare はログを Free で 3 日間、Paid で 7 日間保持し、Paid には月 2,000 万件のログイベントが含まれ、それを超えると 100 万件あたり $0.60 がかかります。2026年12月1日からは Cloudflare Observability の料金体系に移行します。`head_sampling_rate` を使えば、リクエストの多い Worker でも一部のリクエストだけを残せます。リクエストの `cf-ray`、ユーザー ID、注文 ID など、インシデントを突き合わせるのに必要な識別子をログに記録し、シークレット、署名済み URL、メールアドレスの全体は決して記録しないでください。

### 実例：デプロイスクリプト

ローカルからの本番デプロイは、パイプライン全体を 1 つのスクリプトにつなげ、最初に失敗した手順で止まります。

```json title="package.json"
    "deploy:production": "bun scripts/verify-bindings.ts production && bun scripts/prepare-deploy-secrets.ts production && bun scripts/run-deploy-checks.ts production && bun run build:production && bun run db:migrate:production && env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.production.json && bun scripts/verify-deployment.ts production",
```

1 つのトレードオフは意図的なものです。`wrangler.jsonc` は `upload_source_maps` を `false` にしています。かつて Worker とソースマップを合わせると、Cloudflare が 1 回のアップロードで受け付けるサイズを超えたからです。本番環境のスタックトレースはバンドルされたコードを指しており、Worker が小さくなった後も、ソースマップはまだ有効に戻していません。

## 重要な上限

SaaS が最初に直面する上限を、2026年11月20日時点の Cloudflare の上限のページからまとめました。

| --------------------------------------------------- | ------------- | ----------------------------- |
| D1 のデータベースのサイズ                           | 500 MB        | 10 GB                         |
| アカウントあたりの D1 のストレージ                  | 5 GB          | 1 TB                          |
| Worker の呼び出し 1 回あたりの D1 のクエリ          | 50            | 1,000                         |
| D1 の行、文字列、BLOB                               | 2 MB          | 2 MB                          |

## コスト

2026年11月20日時点の Cloudflare の料金です。

| プロダクト    | 含まれるもの                                                    | それを超える分                                                                      |
| ------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Workers Paid  | 月額 $5：1,000 万リクエストと 3,000 万 CPU ミリ秒               | 100 万リクエストあたり $0.30、100 万 CPU ミリ秒あたり $0.02                         |
| 静的アセット  | すべてのプランで、すべてのリクエスト                            | 無料                                                                                |
| D1            | 毎月、読み取り 250 億行、書き込み 5,000 万行、5 GB              | 読み取り 100 万行あたり $0.001、書き込み 100 万行あたり $1.00、1 GB・月あたり $0.75 |
| KV            | 毎月、読み取り 1,000 万回、書き込み・削除・一覧 100 万回、1 GB  | 読み取り 100 万回あたり $0.50、書き込み 100 万回あたり $5.00、1 GB・月あたり $0.50  |
| R2 Standard   | 10 GB・月、毎月 Class A 操作 100 万回と Class B 操作 1,000 万回 | 1 GB・月あたり $0.015、Class A 100 万回あたり $4.50、Class B 100 万回あたり $0.36   |
| R2 のエグレス | 無料                                                            | 無料                                                                                |

D1 は独自のエグレス料金やコンピューティング料金を請求しません。

saasyland.com のトラフィックは公開していないので、私たちの請求書の代わりに、Worker へのリクエストが月 100 万回の場合の計算を示します。このサイトのように作られたサイトでは、すべてのページと画像が Worker を実行し、スクリプト、スタイル、フォントは実行しないので、これは 100 万ページビュー未満にあたります。

- **Workers：** 100 万リクエストは含まれる量の 10 分の 1 で、3,000 万 CPU ミリ秒は 1 リクエストあたり平均 30 ms をまかないます。
- **D1：** リクエストあたり 1,000 行を読み取り 10 行を書き込むとしても、読み取りは 10 億行で含まれる量の 4%、書き込みは 1,000 万行でその 5 分の 1 です。
- **KV：** リクエストあたり最大 1 回の読み取りなら、含まれる読み取りの 10 分の 1 です。書き込みは更新間隔ごとにおよそ 1 回しか発生しません。
- **R2：** 最初の 10 GB は無料で、100 GB の動画ライブラリは、どれだけ視聴されても保存費用は月 $1.35 です。

つまり、その月の請求額は $5 に、無料の 10 GB を超える R2 のストレージ代を加えた額です。トラフィックが 10 倍になっても 1,000 万リクエストの枠に収まります。最初に増えるのは、含まれる量を超えると 100 万ミリ秒あたり $0.02 の CPU 時間と、100 万行あたり $1.00 の D1 の書き込みです。これが、リクエストを短く保ち、書き込みを慎重に行う実際的な理由であり、成長するにつれて、リクエストのたびに書き込むレートリミッターを見直す価値がある理由です。

## そのまま使えるチェックリスト

**設定と環境**

- すべてのステージが専用の D1 データベース、KV 名前空間、バケットを持ち、本番環境はプレビューと何も共有していない
- テスト用に、ローカルのリソースだけで動く環境が 1 つある
- 各環境が必要なシークレットを宣言し、デプロイは空の値やプレースホルダーの値を拒否する
- 用途の異なる鍵は、1 つのシークレットから別々に導出されている

**リクエストの経路**

- ハッシュ付きのアセット、フォント、そのほか誰にとっても同じファイルは Worker を経由しない
- Worker と `_headers` が設定するヘッダーは 1 つのソースから来ており、一致することがテストされている
- レスポンスごとのデータを含む HTML は `private` で、共有キャッシュには決して保存されない

**コールドスタート**

- エントリーの静的インポートは予算として扱われ、ビルドで確認されている
- SDK、データベースクライアント、メールライブラリは、リクエストが必要とする場所でインポートされている
- ビルド時にしか変わらないコンテンツは、Worker にバンドルせず、プリレンダリングするか静的ファイルとして書き出している
- コールドリクエストはローカルではなく、デプロイ先で計測している

**D1**

- 読み取り・判断・書き込みはすべて、1 つのステートメントか 1 つのバッチになっている
- 一意制約が競合を裁き、そのエラーは `500` ではなく `409` になる
- Webhook のコピーは新しい場合にだけ書き込まれ、取り消しは遅れて届くイベントが確認する記録を残す
- 頻繁に実行されるクエリにはインデックスがあり、その `rows_read` を確認済み
- 複数行の挿入は 100 個というパラメーターの上限を守っている
- 10 GB を超えたときの計画が、たとえ「テナントごとに 1 つのデータベース」だけであっても書き残されている

**マイグレーション**

- マイグレーションは生成され、レビューされ、コードと一緒にコミットされている
- パイプラインはデプロイの前にマイグレーションを行う
- どのマイグレーションも直前のリリースで動作し、名前の変更や削除は複数のリリースにわたって行う
- テーブルの作り直しでは、外部キーを無効にするのではなく `PRAGMA defer_foreign_keys` を使う
- CI がすべてのマイグレーションを空のデータベースに適用する
- Time Travel の使い方を、必要になる日より前に知っている

**KV、R2、レート制限**

- KV には、アクセスを決めるものも、キーあたり 1 秒に 1 回を超えて書き込むものも置いていない
- キャッシュした値は取得時刻を持ち、読み取り時に検証される
- バケットは非公開で、アクセスは URL の発行時に判断され、URL には有効期限がある
- 大きなアップロードは、リクエストボディの上限より小さいパートに分けて R2 に送る
- リクエストが必要とするオブジェクトの情報は、カスタムメタデータとして保存されている
- 各レート制限には、求められる正確さに合ったストアがあり、フェイルオープンかフェイルクローズかの判断が書き残されている

**デプロイと運用**

- 設定のチェック、ビルドのチェック、マイグレーション、デプロイ、稼働中のサイトのチェックがこの順に実行される
- Workers Logs が有効で、必要に応じてサンプリングされ、識別子を記録し、シークレットや署名済み URL は決して記録しない

SaaSy Land の CLI は npm の <RepositoryFact name="cliReleaseChannel" /> タグで公開されています。ライセンスを有効化し、コンフィギュレーターが現在選べるようにしているスタック、つまり Cloudflare Workers 上の React と TanStack Start を書き出します。ほかのフレームワークは[ロードマップ](/docs/project/roadmap)に載っています。現在書き出せるオプションと提供予定のオプションは[コンフィギュレーター](/#cli)で確認できます。ここで説明した Worker は MIT ライセンスで公開されており、[Cloudflare Workers](/docs/integrations/cloudflare-workers)、[D1](/docs/integrations/cloudflare-d1)、[KV](/docs/integrations/cloudflare-kv)、[R2](/docs/integrations/cloudflare-r2) のページがそのすべての部分を説明しています。
