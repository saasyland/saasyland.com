Das Repository läuft auf dem neuesten Release jeder Abhängigkeit. Ein Upgrade, das etwas kaputt macht, wird nach vorn behoben, im Code oder upstream, niemals durch einen Rückschritt.

## Versionen der Toolchain [#upgrading]

Aktualisiere die Abhängigkeiten, die Agent-Skills und die GitHub Actions mit einem Befehl, auf einem eigenen Branch:

```sh
bun run deps:update
```

`scripts/update-dependencies.ts` führt in dieser Reihenfolge aus:

1. `vp migrate` aus dem neuesten Vite+-Release, wenn es neuer ist als das `vite-plus` in `package.json`; das bewegt `vite-plus`, den `vite`-Alias und `vitest` gemeinsam;
2. `bun update --latest` für jede Abhängigkeit, die mit einem `^`- oder `~`-Bereich angegeben ist; das bringt sie auf ihr neuestes Release, auch auf eine neue Major-Version, und behält den Bereich bei;
3. `bun run skills:update`, das die [Agent-Skills](/docs/tooling/agent-skills) auf die neuesten Commits ihrer Quellen bringt und die Versionen der Pakete festhält, die sie beschreiben;
4. `scripts/github-actions.ts`, das mit `git ls-remote` die Release-Tags des Repositorys jeder Action in `.github/workflows/` und `.github/actions/` liest, das neueste stabile Release nimmt, einem annotierten Tag bis zu seinem Commit folgt und jedes `uses:` auf diesen Commit und Tag umschreibt ([CI/CD](/docs/tooling/ci-cd)).

Exakte Pins lässt es unverändert, weil jeder einen Grund auf dieser Seite hat, und am Ende nennt es jedes fixierte Paket, für das es ein neueres Release gibt. `bun run check` schlägt fehl, solange sich ein Paket, das ein Skill beschreibt, seit dem letzten `skills:update` bewegt hat, sodass Abhängigkeiten und Skills nicht auseinanderlaufen können. Jede Woche listet der Workflow `updates.yml` die verfügbaren Updates in einem GitHub-Issue auf; siehe [CI/CD](/docs/tooling/ci-cd#updates).

Danach für jedes Paket, das sich bewegt hat:

- Bun ist Paketmanager und Skript-Runner. `packageManager` in `package.json` (Bun <RepositoryFact name="bunVersion" />) ist die einzige Stelle, an der seine Version festgelegt wird; die CI liest sie von dort. `bun.lock` ist eingecheckt.
- Node stammt aus `.nvmrc` (<RepositoryFact name="nodeVersion" />), und `engines.node` verlangt mindestens diese Version.
- `remotion/` ist die einzige Ausnahme, mit einer eigenen npm-Toolchain, die nur installiert wird, wenn du die Videos der Landingpage bearbeitest. Sein `typescript` ist das neueste Release, das `typescript-eslint`, das die Lint-Regeln von Remotion ausführt, als Peer-Abhängigkeit akzeptiert, weil TypeScript 7 die Compiler-API, die `typescript-eslint` liest, nicht mitliefert. Die Pakete, die es mit der Website teilt, `@saasyland/stack`, `lucide-react`, `react` und `react-dom`, sind auf die niedrigste Version festgelegt, die das `package.json` der Website zulässt, weil die Videos Dateien der Website rendern, die sie importieren, und `src/data/__test__/cli.test.ts` schlägt fehl, wenn die beiden voneinander abweichen.

## Upgrades

1. Lies das Changelog und den Migrationsleitfaden der neuen Version, am besten die Fassung, die in `node_modules/<package>` mitgeliefert wird.
2. Passe den Code an die dokumentierte Verwendung der neuen Version an.
3. Prüfe in dieser Reihenfolge, und melde nichts als erledigt, bevor der letzte Schritt erfolgreich ist:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` und die Tests laufen ohne den Build von Cloudflare und TanStack Start, daher können sie erfolgreich sein, während der Build kaputt ist. Das ist bei einem einzigen Upgrade zweimal passiert: Ein neues `@polar-sh/sdk` ließ sich nicht bundeln, und ein Release von TanStack Start änderte das `modulepreload`-Markup, das `optimize-prerendered-html.ts` umschreibt. Beides zeigte sich erst in `build:test`. Nach einem Build darf `find dist/server -name '*.map'` nichts ausgeben; `upload_source_maps: false` in `wrangler.jsonc` existiert, weil der Worker mit seinen Source-Maps größer ist, als Cloudflare für einen Upload akzeptiert (siehe [Cloudflare Workers](/docs/integrations/cloudflare-workers)).

Setze ein Paket nie auf ein älteres Release zurück, um einem Breaking Change auszuweichen, und füge der Anwendung nie Code hinzu, der einen Bibliotheksfehler umgeht.

## Wenn der Bug upstream liegt [#when-the-bug-is-upstream]

Wenn die Anwendung bereits der dokumentierten Verwendung folgt und die neue Version fehlerhaft ist, behältst du die neue Version und führst die Korrektur selbst mit:

1. Belege den Bug mit einer minimalen Reproduktion außerhalb dieses Repositorys.
2. Schreibe die kleinste Änderung, die ihn im Paket behebt, entsprechend dem Fix, den du upstream vorschlagen wirst, und speichere sie mit `bun patch`. Der Patch landet in `patches/<package>@<version>.patch` und in `patchedDependencies`, und das Paket wird auf genau diese Version fixiert, damit der Patch weiterhin angewendet wird.
3. Melde den Bug upstream und öffne einen Pull-Request mit dem Fix, gemäß den Beitragsregeln des jeweiligen Projekts.
4. Lösche den Patch, sobald ein Release den Fix enthält. Bevor du einen Patch behältst oder dokumentierst, prüfe mit `npm view <package> version`, ob dieses Release bereits erschienen ist.

Die aktuellen Patches:

- `patches/@tanstack%2Frouter-core@1.171.39.patch` enthält zwei Korrekturen. Es verhindert, dass das erste Rendern des Routers nach der Hydration das Fenster wieder nach oben scrollt; der Fehler ist upstream als [TanStack/router#8933](https://github.com/TanStack/router/issues/8933) gemeldet und wird so behoben, wie es [TanStack/router#8934](https://github.com/TanStack/router/pull/8934) vorschlägt. - `patches/@tanstack%2Freact-router@1.170.46.patch` verhindert, dass `lazyRouteComponent` eine Seite neu lädt, deren Routen-Chunk der Browser abgebrochen hat, weil der Besucher die Seite verlässt. - `patches/framer-motion@14.14.0.patch` sorgt dafür, dass `LazyMotion` ein Feature-Bundle ignoriert, das nicht geladen werden kann, statt die Ablehnung unbehandelt zu lassen. `motion` ist damit auf 14.14.0 fixiert. Es ist die in [better-auth/better-auth#12873](https://github.com/better-auth/better-auth/pull/12873) vorgeschlagene Korrektur.
- `patches/playwright-core@1.65.1.patch` lässt den WebKit-Treiber von Playwright einer Cross-Site-Navigation zu einer Seite folgen, die `Cross-Origin-Opener-Policy` sendet, etwa der Rückkehr vom gehosteten Checkout von Polar in den Kundenbereich: Der WebKit-Build von Playwright 1.65 legt für den Wechsel eine zweite provisorische Seite an, bevor er die erste zerstört, und der Treiber verwirft nun die erste, statt an einer Assertion in `WKPage._onTargetCreated` zu scheitern. `@playwright/test` ist damit auf 1.65.1 fixiert. Der Fehler ist upstream als [microsoft/playwright#44254](https://github.com/microsoft/playwright/issues/44254) gemeldet, das Playwright als erledigt geschlossen hat; noch enthält kein stabiles Release nach 1.65.1 die Korrektur, also bleibt der Patch, bis eines erscheint.
- `patches/fumadocs-core@16.19.7.patch` lässt `useMediaQuery` seinen Wert nach dem Einhängen der Komponente in einer Transition setzen, statt ihn mit `useSyncExternalStore` zu lesen. `SidebarProvider` von Fumadocs liest darüber `(width < 768px)`, das während der Hydration `null` ist und auf einem Smartphone gleich danach `true`. `useSyncExternalStore` übernahm diese Änderung in einem synchronen Rendern, das den Docs-Artikel erreichte, während sein MDX noch lud, sodass React das `<main>` des Servers verwarf und neu zeichnete, mit einem leeren Bild dazwischen; in einer Transition wartet React stattdessen auf den Artikel. `fumadocs-core` ist damit auf 16.19.7 fixiert. `e2e/specs/content-chrome.spec.ts` prüft, dass eine Docs-Seite ihr `<main>` behält, während ihr MDX verspätet ankommt.

`@tanstack/router-core` ist eine direkte Abhängigkeit, weil `src/lib/stale-build.ts` daraus `isModuleNotFoundError` importiert, und auf 1.171.39 fixiert, damit sein Patch weiter greift. `@tanstack/react-router` ist auf 1.170.46 und `@tanstack/react-start` auf 1.169.7 fixiert, weil beide genau von den gepatchten TanStack-Versionen abhängen. Ein Patch für `fumadocs-mdx` 15.6.0 wurde auf dieselbe Weise mitgeführt und entfernt, als 15.6.1 den Upstream-Fix auslieferte, ebenso die Patches für `@fumadocs/base-ui` und `fumadocs-core` 16.19.2, als 16.19.3 deren Fixes auslieferte. Der Patch für `@videojs/utils` 10.4.0 entfiel, als 10.5.0 dessen Fix auslieferte. Ein Patch, der dem Docs-Layout von Fumadocs einen Slot `skipToContent` gab, wurde entfernt, als Fumadocs den Slot ablehnte; jetzt blendet `globals.css` den Link von Fumadocs aus, und der eigene Skip-Link der Website führt zum Artikel der Dokumentation (siehe [Dokumentationsseite](/docs/features/docs-site)).

Projekte, die `saasyland init` schreibt, bringen eigene Kopien der Patches mit, die ihr Stack braucht, in ihrem eigenen Ordner `patches/` und in `patchedDependencies`, und jedes gepatchte Paket ist auf die gepatchte Version fixiert: Die Templates für TanStack Start fügen die Patches für `@tanstack/router-core` und `@tanstack/react-router` hinzu, und jedes Projekt erhält den Patch für `framer-motion`. Die Patches für `router-core` und `framer-motion` sind dieselben Dateien wie hier. Der Patch für `react-router` im Projekt ist allein der in TanStack/router#8830 vorgeschlagene Fix, ohne die Erweiterung dieser Website für einen Chunk, der erst nach `beforeunload` zu laden beginnt. Die Patches für `better-auth` und `playwright-core` bleiben hier: Ein erzeugtes Projekt nutzt weder das Plugin `haveIBeenPwned` noch den WebKit-Test dieser Website für den Checkout von Polar. Sobald ein Release einen Fix enthält, löscht ein Projekt den Patch und seinen Eintrag in `patchedDependencies` und wechselt auf dieses Release, so wie diese Website (siehe [SaaSy Land CLI](/docs/cli#create-a-project)). Der `fumadocs-core`-Patch ist noch nicht in den Vorlagen.

Ein Patch ändert die Dateien eines Pakets, nicht die Versionen, die Bun dafür installiert. Wenn ein Paket eine seiner eigenen Abhängigkeiten unter dem Release fixiert, das die Anwendung verwendet, und die Typen der beiden Kopien nicht zusammenpassen, hebt stattdessen ein Eintrag unter `overrides` in `package.json` sie an. Derzeit ist keiner nötig. `@polar-sh/adapter-utils` 1.1.1, das `@polar-sh/better-auth` verwendet, fixiert `@polar-sh/sdk` 1.3.1, daher installiert Bun diese Kopie neben der Version 1.3.2 der Anwendung. Der Adapter importiert das SDK nur, um `webhooks({ onPayload })` des Plugins zu typisieren, und `handlePolarEvent`, das die Payload von 1.3.2 entgegennimmt, akzeptiert die von 1.3.1, weil 1.3.2 Typen nur erweitert, etwa um `trial_ended` unter den Abo-Status. Ändert ein späteres SDK-Release eine Payload so, dass die Kopie des Adapters sie nicht akzeptiert, schlägt `bun run check` bei `handlePolarEvent` fehl; dann hebt ein Eintrag für `@polar-sh/sdk` unter `overrides` die Kopie des Adapters an, bis ein Release von `@polar-sh/adapter-utils` von diesem SDK abhängt (`npm view @polar-sh/adapter-utils dependencies`).

## Sicherheitshinweise [#security-advisories]

`bun run deps:audit` führt `bun audit` für die Produktionsabhängigkeiten im Job `check` jedes Pull-Requests und jeder Merge-Gruppe aus und jede Woche erneut in `updates.yml` ([CI/CD](/docs/tooling/ci-cd#checks)). Es schlägt bei einem Sicherheitshinweis des Schweregrads <RepositoryFact name="auditBlockingSeverities" /> fehl, den keine gültige Ausnahme abdeckt, und gibt niedrigere aus, ohne fehlzuschlagen.

Dependabot-Warnungen decken `remotion/package-lock.json` ab, aber GitHub liest `bun.lock` nicht. Prüfe die Anwendung deshalb mit `bun audit` und das Videoprojekt mit `npm audit` in `remotion/`. Behebe einen Sicherheitshinweis mit dem neuesten Release des Pakets, das das betroffene Paket einbindet. Wenn dessen Versionsbereich das korrigierte Release bereits zulässt, genügt es, die Lockfile zu aktualisieren: `bun update` oder `npm update` in `remotion/`.

Solange kein Release des übergeordneten Pakets die Korrektur zulässt, hebt ein Eintrag unter `overrides` das betroffene Paket an, und er wird gelöscht, sobald ein Release des übergeordneten Pakets das tut. Die aktuellen Einträge:

- `package.json`: `"minimatch": "^11.0.1"`. `shadcn` erreicht `minimatch` ^10 über `ts-morph` 26 und `@ts-morph/common`, und erst `minimatch` 11.0.1 behebt GHSA-g3hv-75wg-m249. Lösche den Eintrag, wenn `shadcn` von einem `ts-morph`-Release abhängt, das [dsherret/ts-morph#1697](https://github.com/dsherret/ts-morph/pull/1697) enthält.
- `remotion/package.json`: `minimatch` ^11.0.1 unter `@typescript-eslint/typescript-estree`, für denselben Sicherheitshinweis. `@remotion/eslint-config-flat` fixiert `typescript-eslint` auf 8.71.2, dessen Parser `minimatch` ^10 verlangt. Lösche den Eintrag, wenn `@remotion/eslint-config-flat` von einem `typescript-eslint`-Release abhängt, das [typescript-eslint/typescript-eslint#13145](https://github.com/typescript-eslint/typescript-eslint/pull/13145) enthält.

`bun audit` meldet weiterhin einen Sicherheitshinweis, für den es keine Korrektur zum Übernehmen gibt:

- `esbuild` 0.18.20 (GHSA-67mh-4wv8-2f99, mittel), über `drizzle-kit` und `@esbuild-kit/esm-loader`. `drizzle-kit` 0.31.11 deklariert den Loader, importiert ihn aber nie, und der Hinweis betrifft den Entwicklungsserver von esbuild, den hier nichts startet. [drizzle-team/drizzle-orm#5304](https://github.com/drizzle-team/drizzle-orm/issues/5304) verfolgt seine Entfernung; die Release Candidates von `drizzle-kit` 1.0 hängen nicht mehr davon ab.

GitHub hat den Sicherheitshinweis zu `deepmerge` 4.3.1 (GHSA-gcqx-w48m-w2h4), das `shadcn` und `@shadcn/registry` einbanden, nach [github/advisory-database#10910](https://github.com/github/advisory-database/issues/10910) zurückgezogen, daher meldet `bun audit` ihn nicht mehr.

### Ausnahmen [#audit-exceptions]

Ein Sicherheitshinweis, für den es noch keine Korrektur gibt, meist in einem transitiven Paket, erhält eine Ausnahme in `AUDIT_EXCEPTIONS` (`src/data/dependency-audit.ts`), der einzigen Liste dafür, eingetragen in einem eigenen Pull-Request und geprüft wie jede andere Änderung. Jeder Eintrag nennt den GitHub-Sicherheitshinweis (`advisory`) und das Paket (`package`), begründet, warum der Hinweis bis zu einer Korrektur hingenommen wird (`reason`), und trägt das Datum der Prüfung (`reviewedOn`), das Enddatum der Ausnahme (`expiresOn`) und einen Link auf das Upstream-Issue oder den Pull-Request, der die Korrektur verfolgt (`tracking`). Der Scan schlägt bei einer Ausnahme fehl,

- die abgelaufen ist: prüfe sie mit neuen Daten erneut oder entferne sie;
- die länger als <RepositoryFact name="auditExceptionMaxDays" unit="day" /> nach ihrer Prüfung gilt oder deren Prüfdatum in der Zukunft liegt;
- die zu keinem gemeldeten hohen oder kritischen Sicherheitshinweis mehr passt, damit keine ihren Grund überdauert.

Jeder Sicherheitshinweis, den eine Ausnahme erlaubt, wird in jedem Lauf als Warnung ausgegeben, sodass keine Ausnahme still bleibt, und `dependency-audit.test.ts` prüft die Felder jedes Eintrags. Der Pull-Request, der die Korrektur übernimmt, entfernt den Eintrag.

## Die Vite+-Einträge in package.json

```json
"vite": "npm:@voidzero-dev/vite-plus-core@8.3.8000",
"vite-plus": "1.7.0",
"vitest": "5.1.0"
```

Diese Zeilen sowie derselbe `vite`-Alias und dieselbe `vitest`-Version unter `overrides` sind genau das, was der eigene Migrator von Vite+ schreibt: `vite-plus` ist auf eine exakte Version fixiert, Bun braucht den Core als direkte `vite`-Abhängigkeit, und `vitest` ist aufgeführt, weil `@vitest/coverage-v8` und die Testtypen es brauchen. Seit `vite-plus` 1.7.0 trägt der Core die Version des Vite-Releases, das er bündelt, 8.3.8000 ist also Vite 8.3.8; `vp toolchain` zeigt die Zuordnung. Aktualisiere sie gemeinsam mit `vp migrate`, niemals mit `bun update`. Um herauszufinden, ob einer davon entfallen kann, kopiere das Projekt, führe `vp migrate` auf der Kopie aus und vergleiche das Ergebnis per Diff; entscheide es nicht durch Nachdenken. Der `minimatch`-Eintrag unter `overrides` ist die oben beschriebene Sicherheitskorrektur, und `vp migrate` lässt ihn unverändert.

`build.rolldownOptions.external`, das `src/integrations/polar/polar.vite.ts` setzt, listet optionale Peer-Abhängigkeiten von `@polar-sh/sdk` auf, die nicht installiert sind und per Tree-Shaking aus dem Worker entfernt werden; siehe [Vite+](/docs/tooling/vite-plus). Entferne die Liste, wenn Polar sein Packaging korrigiert.

## Eine Abhängigkeit hinzufügen

Prüfe zuerst, ob ein Paket, das bereits in `package.json` steht, die Aufgabe erledigt, damit jeder Belang bei einer Bibliothek bleibt. Füge eine Laufzeitabhängigkeit mit `bun add` hinzu, ein Werkzeug mit `bun add --dev`, und verwende den Agent-Skill des Anbieters aus `skills-lock.json`, wenn es einen gibt (siehe [Agent-Skills](/docs/tooling/agent-skills)). Beschreibt ein Skill eines Anbieters das neue Paket, trage das Paket bei seiner Quelle in `SKILL_SOURCES` (`src/data/skills.ts`) ein und führe `bun run skills:update` aus.
