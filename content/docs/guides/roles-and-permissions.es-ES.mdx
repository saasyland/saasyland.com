El control de acceso usa el plugin admin de Better Auth. `src/integrations/better-auth/auth.access.ts` define las declaraciones de permisos de cada recurso en `APP_STATEMENTS`, las concede a los roles y construye a partir de ellas el control de acceso de Better Auth y la comprobación de permisos, en un solo archivo que revisa una persona. Los códigos de rol viven en `src/integrations/better-auth/auth.roles.ts`.

## Declaraciones y roles

```ts title="src/integrations/better-auth/auth.access.ts"
export const APP_STATEMENTS = {
  admin: ["access"],
  category: ["create", "read", "update", "delete"],
  course: ["create", "read", "update", "delete"],
  order: ["read", "update", "refund"],
  product: ["create", "read", "update", "delete", "publish"],
  settings: ["manage"],
  video: ["read", "delete"],
} as const

export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...APP_STATEMENTS, ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole({}),
}
```

- `APP_STATEMENTS` enumera una declaración por recurso, por orden de recurso: `admin` y `settings` para la consola de administración y sus ajustes, `category` y `product` para los productos, `course` y `video` para los cursos, y `order` para los pedidos.
- `defaultStatements` de Better Auth añade los recursos `user` y `session` (como `user: ["list", "set-role", "ban", "impersonate", "delete"]` y `session: ["list", "revoke"]`).
- A `admin` se le conceden todas las declaraciones y las declaraciones de administración de Better Auth; a `customer`, el rol por defecto de los usuarios nuevos, no se le concede ninguna.
- Una funcionalidad que un proyecto omite se lleva sus declaraciones: `scripts/features.ts` las nombra, como `APP_STATEMENTS.course`, y la regla de poda las borra del objeto ([Pruebas](/docs/conventions/testing#tests-follow-the-features)).
- `ROLE_VALUES` tipa la columna `user.role` y los esquemas de rol de `user.zod.ts`.
- `Permission`, el tipo que reciben `authorized` y `hasPermission`, se construye a partir de `APP_STATEMENTS`, así que una declaración o una acción que no declare no compila.

## Dónde se comprueban los permisos

| Capa                    | Comprobación                                                        |
| ----------------------- | ------------------------------------------------------------------- |
| Guard de ruta           | `requireAdmin` exige `admin: ["access"]` para toda el área `/admin` |
| Función de servidor     | `authorized({ product: ["update"] })` en cada operación protegida   |
| Solo con sesión         | `authorized()` para operaciones sobre los datos del propio usuario  |
| En cualquier otro sitio | `hasPermission({ permission, role })` devuelve un booleano          |

El guard de ruta solo decide qué páginas se renderizan. Las funciones de servidor se pueden llamar directamente por RPC, así que cada una debe comprobar su propio permiso. Ocultar un botón es presentación, no autorización.

## Añade un permiso

1. Añade la acción a la declaración del recurso en `APP_STATEMENTS`, o añade el recurso en el lugar que le corresponde por orden, por ejemplo `report: ["read", "export"]`. Una funcionalidad que se puede omitir nombra un recurso nuevo en sus `names` de `scripts/features.ts`, como `APP_STATEMENTS.report`.
2. Concédela en `ROLES`: `admin` recibe todo `APP_STATEMENTS`, y a un rol que deba recibir menos se le concede un subconjunto.
3. Exígela en la función de servidor: `.middleware([authorized({ report: ["export"] })])`.
4. Prueba tanto el caso permitido como el caso `FORBIDDEN`, en `src/integrations/better-auth/__test__/auth.access.<feature>.test.ts` y en las pruebas del caso de uso.

## Añade un rol

1. Añade el código a `ROLE_CODES` y `ROLE_VALUES` en `auth.roles.ts`.
2. Añádelo a `ROLES` en `auth.access.ts` con las declaraciones que pueda usar.
3. Añade la etiqueta del rol a `filters.role.options` en `messages/<locale>/pages.admin.users.json` en todos los idiomas.

El cliente de autenticación (`auth.client.ts`) recibe `ac` y `ROLES`, así que las acciones de administración del navegador usan las mismas definiciones.

## Administración de usuarios y sesiones

Los módulos de usuarios y sesiones envuelven la API de administración de Better Auth en casos de uso, cada uno con su propio permiso: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` y otros. Las operaciones sobre los datos del propio usuario, como `revokeSession`, usan `authorized()` y filtran por `context.auth.user.id`.

En local, `bun run db:seed:local` crea un administrador. En preview y en producción, el primer administrador lo crea `bun run admin:grant:preview <email>` o `bun run admin:grant:production <email>`, que solo puede ejecutar alguien con acceso de escritura a esa base de datos D1, para una cuenta que haya verificado su correo; los administradores posteriores se crean en **Administración → Gestión de usuarios** con **Cambiar rol**. Consulta [El primer administrador](/docs/tooling/database#the-first-admin). Un administrador existente también puede invitar a una dirección nueva con el rol `admin`; consulta [Invitaciones](/docs/features/users-admin#invitations).
