`wrangler.jsonc` define cuatro entornos. `CLOUDFLARE_ENV` selecciona uno para el servidor de desarrollo y las compilaciones, y cada uno lee los secretos de su propio archivo de entorno:

| Entorno       | Seleccionado por                            | Bindings                                 | Secretos de        |
| ------------- | ------------------------------------------- | ---------------------------------------- | ------------------ |
| `development` | `bun run dev`                               | D1, KV y R2 locales en `.wrangler/state` | `.env.development` |
| `preview`     | `build:preview`, `deploy:preview`           | D1, KV y R2 de preview                   | `.env.preview`     |
| `production`  | `build:production`, `deploy:production`     | D1, KV y R2 de producción                | `.env.production`  |
| `test`        | `build:test`, `start:test`, `db:reset:test` | D1, KV y R2 locales en `.wrangler/test`  | `.env.test`        |

Git ignora `.env.development`, `.env.preview` y `.env.production`; `.env.example` enumera sus claves. `.env.test` está incluido en el repositorio y solo contiene valores ficticios. Los scripts de despliegue solo suben las claves enumeradas en `secrets.required` del entorno, leídas del archivo correspondiente.

## Secretos

Cada entorno enumera sus secretos en `secrets.required`: las claves de Better Auth, OAuth, Resend y Polar, además de `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` y `CLOUDFLARE_ACCESS_TOKEN` para las herramientas de Drizzle (el entorno `test` omite estos tres). Consulta [Variables de entorno](/docs/getting-started/environment-variables) para conocer cada clave.

`AFFONSO_PROGRAM_ID`, el ID público del programa de Affonso que necesita el seguimiento de referidos de afiliados, es una variable de Worker en `vars`, no un secreto, así que no está en `.env.example` ni en `secrets.required`. Defínelo solo para el entorno que recibe pagos reales; `production` define el ID de programa de SaaSy Land y `test`, un ID ficticio para las pruebas en el navegador. El seguimiento solo funciona cuando el Worker tiene el ID y el programa está abierto: hoy `AFFILIATE_PROGRAM` vale <RepositoryFact name="affiliateProgram" /> ([Abrir el programa](/docs/features/affiliates#opening-the-programme)).

El código del servidor lee los secretos con `import { env } from "cloudflare:workers"`. Nada usa una variable `VITE_`, y ninguna puede contener un secreto, porque Vite las expone al navegador. `scripts/verify-build.ts` hace fallar la compilación cuando un recurso del cliente importa `cloudflare:workers`. El dominio canónico procede de `APP_DOMAIN` en `src/presentation/branding/index.ts`, no de una variable de entorno.

## Bindings

| Binding   | Tipo               | Uso                                                                   |
| --------- | ------------------ | --------------------------------------------------------------------- |
| `DB`      | D1                 | Base de datos de la aplicación, sesiones y límites de frecuencia      |
| `CACHE`   | KV                 | Recuento de estrellas de GitHub                                       |
| `MEDIA`   | R2                 | Archivos de vídeo, servidos a través de `/media/`                     |
| `BUNDLES` | R2                 | Los bundles de plantillas de la CLI, servidos a través de `/bundles/` |
| `ASSETS`  | Recursos estáticos | Páginas prerenderizadas, fuentes y archivos públicos                  |

El desarrollo solo usa bindings locales, por lo que `bun run dev` nunca toca los datos de preview ni de producción; [Base de datos](/docs/tooling/database#three-databases) explica por qué cada binding es local. Los cursos son los mismos en todos los entornos: `bun run db:seed:local` importa el temario en local y `bun run courses:sync:preview` copia los cursos publicados de producción a preview ([Datos de cursos en cada entorno](/docs/tooling/database#course-data-in-each-environment)). Ejecuta `bun run cf-typegen` después de cambiar los bindings para regenerar `src/types/worker-configuration.d.ts`.

## Pruebas

Vitest carga `.env.test` mediante `test.env` y resuelve `cloudflare:workers` como `src/platform/testing/mocks/cloudflare.ts`, que proporciona en memoria D1, KV y un bucket por cada binding de R2; `src/platform/testing/mocks/cache.ts` simula la caché de Workers. Playwright usa el entorno `test` y su punto de entrada `src/platform/testing/worker.ts`. Ninguno de los dos necesita credenciales reales.
