## Routendateien

Routen sind flache Dateien in `src/routes`. Punkte werden zu Pfadsegmenten:

| Datei                             | URL                | Hinweise                                |
| --------------------------------- | ------------------ | --------------------------------------- |
| `__root.tsx`                      | alle Seiten        | Dokument-Shell und Root-Namespaces      |
| `_site.tsx`                       | keine              | Pfadloses Layout mit dem Website-Header |
| `_site._marketing.tsx`            | keine              | Pfadloses Layout für Marketingseiten    |
| `_site._marketing.terms.tsx`      | `/terms`           | Seite innerhalb des Marketing-Layouts   |
| `admin.tsx`                       | `/admin`           | Layout mit dem Guard `requireAdmin`     |
| `admin.users.all.tsx`             | `/admin/users/all` | Seite innerhalb des Admin-Layouts       |
| `_site._marketing.blog.index.tsx` | `/blog`            | Indexseite des `blog`-Layouts           |
| `_site.docs.$.tsx`                | `/docs/*`          | Splat-Route für Dokumentationsseiten    |
| `api/auth.$.ts`                   | `/api/auth/*`      | HTTP-Handler, keine Komponente          |

Die IDs in `createFileRoute("…")` sind String-Literale, die der Router-Generator pflegt; er schreibt auch `src/routeTree.gen.ts`. Dateien in `__test__`-Ordnern werden ignoriert. Jede URL hat eine Konstante in `ROUTES` (`src/routes.ts`), und Links verwenden `<Link to={ROUTES.X}>`.

## Seitenrouten

Eine Seitenroute definiert eine Komponente `<Name>Page`, eine Konstante `NAMESPACE` direkt über `export const Route` und einen Loader, der die Seitenmetadaten und den Namespace in einem einzigen `Promise.all` lädt:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Zusätzliche Daten kommen in dasselbe `Promise.all`, zum Beispiel `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` in `admin.users.all.tsx`. `pageHead` aus `src/lib/seo.ts` erzeugt aus den `metadata` des Loaders den Titel, die Beschreibung, den Canonical-Link sowie die Tags für `hreflang`, Open Graph und das Vorschaubild; siehe [Suche und Social-Media-Vorschauen](/docs/features/seo).

## Layout-Routen

Eine Layout-Route definiert eine Komponente `<Name>Layout`, ein Array `NAMESPACES` und für geschützte Bereiche einen Guard in `beforeLoad`. Ihre `NAMESPACES` enden mit den Namespaces, die andere Bereiche ihr hinzufügen, und ein Suchparameter wird von den Seiten validiert, die ihn lesen, so wie es die Lizenzseiten `/app` und `/app/license` mit `tier` tun:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "timezones", ...layoutNamespaces("/app")] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Die Guards `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn`, `redirectIfVerified` und `redirectAfterAuth` stammen aus `src/integrations/better-auth/auth.routes.ts`.

## Lade-Skeletons

Die meisten Navigationen sind abgeschlossen, bevor überhaupt eine Pending-UI erscheint: Links laden ihre Route bei Hover und Touch vorab, und öffentliche Seiten sind vorgerendert. Ist eine Navigation nach `defaultPendingMs`, <RepositoryFact name="navigationPendingMs" unit="millisecond" />, nicht abgeschlossen, zeigt der Router das Skeleton der Route, und weil `defaultPendingMinMs` <RepositoryFact name="navigationPendingMinMs" unit="millisecond" /> beträgt, entfernt er es, sobald die Seite bereit ist. Das passiert bei einer langsamen Verbindung oder bei der ersten Anfrage an ein neues Worker-Isolate (siehe [Performance](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

Es gibt keine Standardkomponente für Pending. Jede Layout- und Seitenroute legt ihre eigene `pendingComponent` fest. Die Docs-Seiten werden innerhalb des Docs-Layouts gezeichnet: `_site.docs.index.tsx` und `_site.docs.$.tsx` zeigen `DocsIndexPending` und `DocsPagePending`, den Artikel und sein Inhaltsverzeichnis neben der Seitenleiste, und das `docs`-Layout zeigt `DocsPending`, wenn jemand die Dokumentation von anderswo aus betritt. Jedes Skeleton bildet die Seite nach, die es vertritt:

- **Seiten-Skeletons** wie `SignInPending` und `LegalPending` liegen in der Pending-Datei des Bereichs und kennzeichnen ihr Wurzelelement mit `aria-busy="true"`. Die Dateien sind `custom/auth/auth-pending.tsx`, die Admin-Dateien in `custom/admin/` (`admin-pending.tsx` für das Layout, eine Datei `<area>-pending.tsx` pro Bereich, etwa `products-pending.tsx`, und gemeinsame Bausteine in `pending-blocks.tsx`), die Dateien der Kunden-App in `custom/app/` (`app-pending.tsx` für das Layout, `auth-pending.tsx` und `license-pending.tsx` sowie der gemeinsame Seitenkopf in `pending-blocks.tsx`), die Dateien des öffentlichen Layouts direkt in `custom/` (`marketing-pending.tsx` für das Layout, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` und `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` und `custom/docs-pending.tsx`.
- **Layout-Skeletons** wie `AuthPending` und `MarketingPending` rendern den Rahmen des Layouts und darin die `pendingComponent` der ersten Route unterhalb des Layouts, die für den aktuellen Pfad eine hat; `usePagePending` in `src/hooks/use-page-pending.ts` liest sie aus dem Routenbaum. Wer von woanders in einen Bereich wechselt, sieht deshalb gleich die richtige Seite, und ein Layout-Skeleton eine Ebene tiefer, etwa `AdminUsersPending`, macht dasselbe für seine eigenen Seiten. Rahmenelemente, die keine Daten benötigen, etwa `Wordmark` und `PageFrame`, werden echt gerendert, und der Website-Header bleibt sichtbar, weil das Layout `_site`, das ihn rendert, keinen Loader hat, auf den es warten müsste.
- **Textplatzhalter** sind `Skeleton`-Balken mit dem Schrift-Token des echten Elements plus `h-lh scale-y-70`, sodass jeder Balken genau eine Zeilenbox füllt. Boxen verwenden die echten Höhen und Radien. Listen beziehen ihre Länge aus denselben Konstanten wie die UI, etwa `OAUTH_PROVIDERS` und `AUTH_ASSURANCES` in `src/data/auth.ts`.

Wenn du eine Seite hinzufügst, ergänze ihr Skeleton in der Pending-Datei des Bereichs und setze es als `pendingComponent` der Route; dort finden es die Layout-Skeletons.

## Weitere Aspekte von Routen

- **Suchparameter** werden in der Route mit `validateSearch` geparst, zum Beispiel der Parameter `tab` von `/admin/products`. Das Schema ist ein `zod.object` aus den Hilfsfunktionen in `src/lib/search-params.ts`: `searchText()` und `searchFlag()` liefern `undefined` für einen fehlenden, leeren oder fehlerhaften Wert, und `searchChoice(choices, fallback)` liefert den Fallback. `searchParam(schema)` liefert `undefined`, sofern der Wert nicht zu einem anderen zod-Schema passt, etwa zum Newsletter-Token.
- **Server Functions für eine einzelne Route** dürfen mit `createServerFn` in der Routendatei definiert werden.
- **Inhalte aus dem Build**: Die Loader von Doku, Blog und Landingpage lesen die Inhaltsindizes aus `virtual:content-indexes`, Dateien unter `/assets/`, daher brauchen sie keine Server Function und laufen bei einer clientseitigen Navigation im Browser (siehe [Fumadocs](/docs/integrations/fumadocs#content-indexes)).
- **HTTP-Endpunkte** liegen in `src/routes/api`. Siehe [HTTP-Handler in TanStack Start](/docs/architecture/api-layer).

## Router

`src/router.tsx` exportiert `getRouter`, das für jeden Request einen neuen `QueryClient` und einen neuen Router erstellt. Dabei wird Folgendes festgelegt:

- Standardkomponenten für Fehler und Not Found aus `presentation/components/custom`, aber keine Standardkomponente für Pending (siehe [Lade-Skeletons](#lade-skeletons))
- Preloading bei Intent und eine Standard-Stale-Time von <RepositoryFact name="routerStaleTimeMinutes" unit="minute" /> für geladene wie für vorab geladene Seiten, sodass eine Seite, die `Navigation` für den Header vorab lädt, sobald eine Seite im Leerlauf ist, beim Klick noch frisch ist (siehe [Performance](/docs/conventions/performance#the-headers-pages-load-before-a-click))
- ein `rewrite`, das das Locale-Präfix aus eingehenden URLs entfernt und es in generierten Links wieder hinzufügt
- die SSR-Query-Integration über `setupRouterSsrQueryIntegration`

## Nach einem Deployment [#after-a-deploy]

Jedes Deployment ersetzt die statischen Assets des Workers, und Vite benennt jede Datei nach ihrem Inhalt, sodass ein Tab, der vor einem Deployment geöffnet wurde, Routen-Chunks anfordert, die es nicht mehr gibt. TanStack Start legt die Komponente und den Loader jeder Route in eigene Chunks. TanStack Router lädt die Seite neu, wenn der Chunk einer Komponente nicht geladen werden kann (`lazyRouteComponent`), aber router-core lädt den Chunk eines Loaders mit `lazyFn`, das den fehlgeschlagenen Import als Fehler des Loaders an die Route weitergibt. Ein Klick auf **Blog** in einem solchen Tab scheiterte am Loader-Chunk des Blog-Layouts und zeigte die Fehlerseite.

`DefaultError`, die Standard-Fehlerkomponente des Routers, fängt das jetzt ab. `isStaleBuildError` in `src/lib/stale-build.ts` erkennt einen Fehler, der bedeutet, dass die Seite Code ausführt, den ein neueres Deployment entfernt hat:

- einen fehlgeschlagenen dynamischen Import, den `isModuleNotFoundError` aus router-core in Chromium, Firefox und Safari erkennt;
- eine Datei, die Vite für einen Chunk nicht vorladen konnte, etwa sein Stylesheet; Vite meldet sie mit einem Event `vite:preloadError`. Die Root-Route hört auf dieses Event, solange die Anwendung geöffnet ist (`listenForStaleBuilds`).

Bei einem solchen Fehler lädt `DefaultError` die Adresse, zu der der Besucher navigiert ist, mit `router.navigate({ href, reloadDocument: true, replace: true })` als neue Seite, sodass er auf der angeklickten Seite landet, ausgeliefert vom neuen Deployment; bis der Browser die Seite verlässt, rendert die Komponente statt der Fehlermeldung ein leeres, als beschäftigt markiertes `main`. `claimReload` erlaubt ein solches Neuladen pro Ziel und Build. Es speichert das Ziel in `sessionStorage` zusammen mit der URL des Entry-Skripts der Seite, die sich mit jedem Deployment ändert, das eine vom Browser geladene Datei ändert, weil jeder Chunk vom Entry aus über seinen inhaltsbasierten Namen erreicht wird. Ein zweiter Fehler für dasselbe Ziel im selben Build zeigt die Fehlerseite, sodass eine Datei, die wirklich fehlt, die Seite nicht endlos neu laden lässt, und das nächste Deployment bekommt ein eigenes Neuladen. Verweigert der Browser den Session Storage, wird nichts neu geladen.

Safari bricht die Dateien, die eine Seite noch lädt, ab, sobald der Besucher sie zu verlassen beginnt, sodass ein Chunk oder Stylesheet, das unterwegs war, fehlschlägt, als hätte ein Deployment es entfernt. `listenForStaleBuilds` merkt sich deshalb auch, wann die Seite `beforeunload` erhält, und `DefaultError` wartet mit `whenPageStays`, bis ein `pageshow`, `pointerdown` oder `keydown` zeigt, dass der Besucher geblieben ist, bevor es die Seite neu lädt. Ein Besucher, der geht, erreicht die Seite, die er aufgerufen hat, statt auf die verlassene Seite zurückgeschickt zu werden, und wer zur Seite zurückkehrt oder auf ihr bleibt, bekommt dann das Neuladen. `stale-build.spec.ts` hält auf einer Lektion das Stylesheet des Videoplayers zurück, wechselt zur Datenschutzerklärung, bricht das Stylesheet ab und prüft, dass die Datenschutzerklärung öffnet und die Lektion nicht erneut angefragt wird.

Ein fehlgeschlagenes Preload beansprucht nichts. Fährt ein Besucher mit dem Zeiger über einen Link, lädt der Router dessen Route vor, wie es der Header für seine eigenen Links tut, sobald eine Seite im Leerlauf ist; schlägt das fehl, rendert keine Fehlerkomponente, und der Router lädt den Chunk beim Klick erneut. `e2e/specs/stale-build.spec.ts` schaltet den Datensparmodus ein, damit der Header den Blog nicht vorher lädt, entfernt die Chunks des Blogs aus einer geöffneten Seite und prüft, dass ein Klick, auch nach einem fehlgeschlagenen Preload beim Überfahren, nach einem Neuladen auf dem Blog landet und dass eine Seite, deren Chunks weiter fehlen, nach zwei Neuladevorgängen die Fehlerseite zeigt, einem durch `DefaultError` und einem durch `lazyRouteComponent`.
