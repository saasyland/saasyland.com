title: "Archivos de ruta"
description: "La única forma de una ruta de página y de una ruta de layout: NAMESPACE o NAMESPACES, un loader con un solo Promise.all, un esqueleto que reproduce la página, esquemas de búsqueda y enlaces."
---

Todos los archivos de `src/routes` tienen la misma forma, así que quien conoce uno los conoce todos. Un archivo de ruta compone: declara lo que necesita la página y coloca componentes. Los widgets, formularios, diálogos y columnas de tabla viven en `src/presentation/components/custom`.

## Rutas de página

`src/routes/admin.courses.index.tsx`:

```tsx
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <div className="flex flex-col gap-4 sm:flex-row sm:items-end sm:justify-between">
        <div>
          <h1 className="text-statement font-semibold text-foreground">{t("title")}</h1>
          <p className="text-sm text-muted-foreground">{t("description")}</p>
        </div>
        <LinkButton className="h-9 gap-2" href={ROUTES.ADMIN_COURSES_CREATE} size="sm">
          <PlusCircle aria-hidden className="size-4" />
          {t("actions.create")}
        </LinkButton>
      </div>

      <DataTable columns={courseColumns} options={{ query: ({ pageIndex, pageSize }) => getCoursesPageQuery({ pageIndex, pageSize }) }} />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **El componente** es una `const` local llamada `<Name>Page`, definida en primer lugar. El marcado pequeño que solo usa esta página puede ir encima como componentes locales, como hacen `CourseProgress` y `StartLink` en `courses.$course.index.tsx`; cualquier cosa con sus propios datos, mutación o estado va a un archivo de componente.
- **Un espacio de nombres.** `const NAMESPACE = "pages.<area>.<page>"` va justo encima de `export const Route` y se usa en `loadPageMetadata`, `preloadNamespaces` y `staticData`. Todo lo demás que necesite la página lo declara su layout.
- **Un solo `Promise.all`.** El loader inicia todo el trabajo a la vez: los metadatos de la página, el espacio de nombres y cada consulta que leen los componentes. Devuelve `{ locale, metadata }` para `head`. Nunca esperes a que termine una de estas tareas antes de iniciar la siguiente.
- **`head: pageHead(ROUTES.X)`** construye el título, la descripción, la URL canónica y las URL alternativas a partir de los metadatos del archivo del espacio de nombres.
- **Las rutas de URL salen de `ROUTES`**, en `src/routes.ts`, que reúne las rutas de todas las áreas (consulta [Rutas y navegación](#paths-and-navigation)); nunca escribas una ruta como literal.

Una página cuyo título sale de un registro espera ese registro y construye su head a partir de los datos del loader, como hace `admin.courses.$courseId.tsx`:

```tsx
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Rutas de layout

`src/routes/admin.courses.tsx`:

```tsx
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Un layout declara `const NAMESPACES = [...] as const` encima de `export const Route` y lo precarga. Cuando no tiene ninguno, omite la opción; no existe `namespaces: []`.
- El componente, cuando el layout renderiza uno, se llama `<Name>Layout` y coloca un `<Outlet />`.
- Una guarda va en el `beforeLoad` del layout que es dueño del área: `beforeLoad: requireAdmin` en `admin.tsx`, `requireSignedIn` en `app.tsx`. Las guardas solo deciden la navegación; cada función de servidor sigue comprobando su propio permiso.

## Orden de las opciones

`sort-keys` está desactivada en `src/routes` porque TanStack Router infiere los tipos en el orden de declaración. Las opciones van en orden alfabético, salvo `validateSearch`, que va primero, antes de todo lo que lee los parámetros de búsqueda:

```tsx
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: zod.object({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Nunca escribas en línea un array o un objeto de datos dentro de `createFileRoute`; decláralo encima como una constante.

## Parámetros de búsqueda

`validateSearch` es un `zod.object` construido con los helpers de `src/lib/search-params.ts`:

| Helper                            | Valor cuando el parámetro falta o está mal formado | Uso                                            |
| --------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| `searchText()`                    | `undefined`                                        | Tokens, correos electrónicos, códigos de error |
| `searchFlag()`                    | `undefined`                                        | Booleanos                                      |
| `searchParam(schema)`             | `undefined`                                        | Cualquier otro esquema, como una ruta          |
| `searchChoice(choices, fallback)` | `fallback`                                         | Una pestaña o una vista                        |

Un texto ausente se queda en `undefined`, así que un valor por defecto nunca se cuela en una URL que construye el router. Un parámetro `searchChoice` va acompañado de `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, que elimina el valor por defecto de la URL. Nunca escribas a mano comprobaciones `typeof search["x"] === "string"`; añade un helper cuando haga falta un nuevo tipo de campo. Cuando un hijo necesita un parámetro que la página ha validado como presente, la página estrecha su tipo y se lo pasa, como `auth.reset-password.tsx` pasa `token` a `ResetPasswordForm`. Un layout valida los parámetros que lee toda su área, como hace `app.tsx` con `validateSearch: appSearchSchema`; el esquema vive en `src/data/app.ts` porque el esqueleto del layout parsea los mismos parámetros.

## Esqueletos

La navegación debe sentirse instantánea, así que cada ruta que renderiza una página tiene un `pendingComponent` que la reproduce: la misma disposición, las mismas tarjetas y el mismo número de filas.

- Los esqueletos viven en el archivo pending del área (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) y usan `Skeleton` de shadcn.
- Un marcador de texto lleva el token tipográfico real más `h-lh scale-y-70`, para que tenga la altura de la línea que sustituye: `<Skeleton className="h-lh w-28 scale-y-70 font-mono text-label" />`.
- La longitud de las listas sale de las constantes que usa la página: `PAGE_ROWS` en `admin/pending-blocks.tsx` tiene `DEFAULT_PAGE_SIZE` filas, el tamaño de página de todas las tablas de administración.
- El esqueleto de un layout elige de un mapa el esqueleto de página que corresponde a la ruta actual, como hacen `AdminPending`, `AppPending` y `MarketingPending` con `PAGE_SKELETONS` y `AdminCourseSectionPending` con `COURSE_PAGES` en `admin/courses-pending.tsx`. Cada área añade sus páginas a `PAGE_SKELETONS` en `src/data/<area>.skeletons.ts` (consulta [Rutas y navegación](#paths-and-navigation)); una página de un layout que pertenece a una sola área, como la sección de un curso, se añade al mapa propio de ese layout.
- No hay un `defaultPendingComponent` para todo el router, y `pendingMs` mantiene el valor por defecto de TanStack. Las rutas de la documentación son la única excepción: `pendingMs: Number.POSITIVE_INFINITY` y `wrapInSuspense: false`. El componente de la página se hidrata con el layout de la documentación y renderiza el MDX en su propio `<Suspense key={path}>`, así que la barra lateral funciona antes de que cargue el chunk MDX de la página, y una navegación reemplaza el HTML del servidor de la página anterior en lugar de hidratarlo con los datos de la siguiente.

## Enlaces

- Los enlaces del router reciben una constante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, o un patrón de ruta con `params` para las rutas dinámicas. `LinkButton` de shadcn recibe un `href`.
- Nunca añadas el prefijo de idioma a un enlace del router; lo añade la reescritura del router. Una URL completa en el idioma actual, para un valor que sale del router como cadena, se obtiene de `router.buildLocation({ ... }).publicHref`, que es como `use-auth-redirect.ts` construye sus enlaces de inicio de sesión. `localizePathname` es para las URL que se construyen fuera de un contexto de router o para otro idioma: correos, destinos de redirección de Better Auth, enlaces dentro de MDX y el selector de idioma.

## Rutas y navegación [#paths-and-navigation]

Ningún archivo enumera todas las áreas de la aplicación. Cada área, como los cursos, los productos o las páginas legales, declara sus propias rutas, sus entradas de menú con sus etiquetas, sus esqueletos de página y sus permisos, y un barrel los reúne, así que un área se añade o se deja fuera con sus propios archivos. Así es como la CLI `saasyland` monta un proyecto a partir de capas de plantillas.

| Qué                    | Cada área declara                                               | Barrel                           | Se lee de                                                                                                                             |
| ---------------------- | --------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Rutas                  | `src/data/<area>.routes.ts`: un `export const` por ruta         | `src/data/routes.entries.ts`     | `ROUTES` en `src/routes.ts`                                                                                                           |
| Entradas de menú       | `src/data/<area>.navigation.ts`: una lista `<AREA>_NAVIGATION`  | `src/data/navigation.entries.ts` | `ADMIN_NAVIGATION`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `NAVIGATION_PAGES` y `FOOTER_NAVIGATION` en `src/data/navigation.ts` |
| Estadísticas del panel | `src/data/<area>.dashboard.ts`: una lista `<AREA>_DASHBOARD`    | `src/data/dashboard.entries.ts`  | `ADMIN_DASHBOARD_STATS` en `src/data/dashboard.ts`                                                                                    |
| Esqueletos de página   | `src/data/<area>.skeletons.ts`: una lista `<AREA>_SKELETONS`    | `src/data/skeletons.entries.ts`  | `PAGE_SKELETONS` en `src/data/skeletons.ts`                                                                                           |
| Permisos               | `src/data/<area>.access.ts`: un objeto `<AREA>_ACCESS`          | `src/data/access.entries.ts`     | `APP_STATEMENTS` y `grantsOf` en `src/data/access.ts`                                                                                 |
| Rutas no listadas      | `src/data/<area>.routes.ts`: una lista `<AREA>_UNLISTED_ROUTES` | `src/data/unlisted.entries.ts`   | `UNLISTED_ROUTES` y `isUnlistedRoute` en `src/data/unlisted.ts`                                                                       |

Un barrel solo contiene líneas `export { … } from`, una por archivo de área y ordenadas por módulo, como `src/integrations/drizzle-orm/drizzle.schemas.ts`. `src/routes.ts` reexporta las rutas como un único espacio de nombres, así que cada ruta conserva su tipo literal y `<Link to={ROUTES.COURSES}>` se sigue comprobando contra el árbol de rutas:

```ts title="src/routes.ts"
export * as ROUTES from "~/src/data/routes.entries"
```

Una entrada de menú indica dónde aparece con `placement` (`NAVIGATION_PLACEMENT` en `src/data/navigation.constants.ts`): la barra lateral de administración, los botones sobre el panel, la barra lateral de la app de clientes, la cabecera pública o el pie. Su `order` la ordena entre las entradas de las demás áreas, de modo que ninguna lista depende del orden de los archivos. Las entradas de administración indican además su grupo de la barra lateral (`group`), y los enlaces del pie su columna (`column`); `ADMIN_NAVIGATION_GROUPS` y `FOOTER_COLUMNS` fijan el orden de grupos y columnas, y el que ninguna área rellena se omite. El área base, que tiene todo proyecto, añade dos entradas de administración y dos entradas a la barra lateral de la app de clientes:

```ts title="src/data/core.navigation.ts"
const AREA = "core"

export const CORE_NAVIGATION = [
  {
    area: AREA,
    group: ADMIN_NAVIGATION_GROUP.OVERVIEW,
    icon: Home,
    key: "dashboard",
    order: 10,
    placement: NAVIGATION_PLACEMENT.ADMIN,
    to: ROUTES.ADMIN,
  },
  {
    area: AREA,
    group: ADMIN_NAVIGATION_GROUP.ADMINISTRATION,
    icon: Settings,
    key: "settings",
    order: 30,
    placement: NAVIGATION_PLACEMENT.ADMIN,
    to: ROUTES.ADMIN_SETTINGS,
  },
  { area: AREA, icon: Home, key: "overview", order: 10, placement: NAVIGATION_PLACEMENT.APP, to: ROUTES.APP },
  { area: AREA, icon: Settings, key: "settings", order: 30, placement: NAVIGATION_PLACEMENT.APP, to: ROUTES.APP_SETTINGS },
] as const satisfies readonly NavigationEntry[]
```

Una estadística del panel tiene un `prefetch`, que ejecuta el loader de `/admin`, y un hook `useValue`, al que `DashboardStats` llama para leer el número.

Un esqueleto de página une el `to` de la página con su `pendingComponent`, el mismo esqueleto que fija la ruta de la página. Los esqueletos de layout `AdminPending`, `AppPending` y `MarketingPending` dibujan el de la ruta actual cuando alguien entra en su layout desde otra parte. Un área declara los esqueletos de todas sus páginas, sea cual sea el layout que las muestre: el área de licencias declara `/app`, `/app/license` y `/premium`, y el área legal sus cinco páginas públicas.

El archivo de acceso de un área define las declaraciones de permisos de sus recursos y los roles a los que las concede. `auth.access.ts` construye el control de acceso de Better Auth a partir de `APP_STATEMENTS` y cada rol a partir de `grantsOf(role)`, así que la integración de autenticación no nombra ningún área, y `APP_STATEMENTS` falla cuando dos áreas declaran el mismo recurso (consulta [Roles y permisos](/docs/guides/roles-and-permissions)).

Las listas de `src/data/navigation.ts` y `PAGE_SKELETONS` tienen tipos declarados, `NavigationEntry` y `PageSkeleton`, en lugar de los tipos de las entradas que declaren las áreas en cada momento, así que una ubicación que ningún área llena, como las acciones del panel en un proyecto sin el área de productos, es una lista vacía que sigue pasando la comprobación de tipos. `navigation.test.ts` y `skeletons.test.ts` comprueban al compilar que el `to` de cada entrada y de cada esqueleto que declara un área es una ruta del árbol de rutas (`FileRouteTypes["to"]` de `src/routeTree.gen.ts`).

Una entrada indica su `area`, y el área la etiqueta en su propio archivo de mensajes: `<placement>.<key>` en `messages/<locale>/navigation.<area>.json`, como `admin.courses` y `header.courses` en `navigation.courses.json`. Una estadística del panel se etiqueta por su `key` en `dashboard.<area>.json`, y una sección de administración etiqueta sus subpáginas para las migas de pan bajo `breadcrumbs.<segment>` en su `navigation.<area>.json`, como `breadcrumbs.create`. Los dos tipos de archivo son espacios de nombres raíz, así que cualquier menú puede etiquetar cualquier entrada, y `useNavigationLabel` en `src/hooks/use-navigation-label.ts` devuelve la etiqueta de una entrada. Lo que pertenece al propio menú se queda en su espacio de nombres: `groups.<group>` en `pages.admin.sidebar`, `columns.<column>` en `components.custom.footer` y las secciones de la página de inicio en `components.custom.navigation`. `enum-labels.test.ts` falla cuando a una entrada o a una estadística le falta la etiqueta en algún locale.

Un área cuyas páginas se renderizan en el Worker en cada solicitud, como `/admin`, `/auth` o `/courses`, enumera esas rutas en `<AREA>_UNLISTED_ROUTES`. `vite.config.ts` las excluye del prerenderizado con `isUnlistedRoute`, y `buildPageHead` les asigna la tarjeta del sitio en lugar de una tarjeta de página (consulta [Búsqueda y vistas previas en redes sociales](/docs/features/seo)). Vite no resuelve el alias `~` mientras carga su propia configuración, así que `unlisted.entries.ts` y `unlisted.ts` importan por ruta relativa los archivos de área.
