description: "Де розміщуються тести, як працюють проєкти Vitest і тестові прив'язки, обов'язкове 100% покриття та Playwright."
---

Vite+ запускає Vitest (`vp test`) у трьох проєктах. Тести лежать у теці `__test__` поруч із кодом, який вони перевіряють, і імпортують API з `vite-plus/test`.

| Проєкт        | Файли                            | Середовище |
| ------------- | -------------------------------- | ---------- |
| `node`        | `__test__/*.test.ts(x)`          | Node       |
| `integration` | `__test__/*.integration.test.ts` | Node       |
| `component`   | `__test__/*.component.test.tsx`  | jsdom      |

Називайте тест за вихідним файлом: `category.zod.ts` покриває `__test__/category.zod.test.ts`.

## Команди

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
```

Використовуйте `bun run test`, а не `bun test`: лише Vitest завантажує проєкти, середовища й файл налаштувань.

## Обов'язкове покриття

`bun run test:coverage` завершується помилкою, якщо покриття рядків, інструкцій, функцій і гілок коду застосунку в `src` нижче за **100%**. Тести, `src/platform/testing`, примітиви shadcn і згенеровані файли виключено. Покривайте реальну поведінку й видаляйте гілки, які ніколи не виконуються, замість підміни глобальних об'єктів, щоб до них дістатися. Звіти записуються в `coverage/`.

## Середовище тестів

- `src/platform/testing/setup.ts` реєструє matchers jest-dom, скидає прив'язки перед кожним тестом і пропускає кожен `createServerFn` через `withTestRpc`, тож виклики виконують справжні middleware і валідатор. Це стосується проєктів `node` та `integration`. У проєкті `component` серверна функція завершується помилкою, бо jsdom є браузером.
- `cloudflare:workers` вказує на `src/platform/testing/mocks/cloudflare.ts`. D1 — це база SQLite в пам'яті із застосованими всіма міграціями з репозиторію, KV і бакет R2 `MEDIA` — мапи в пам'яті, а `flushWaitUntil()` чекає на фонові завдання. `createEdgeCache()` з `mocks/cache.ts` підміняє кеш Workers.
- `.env.test` надає фіктивні облікові дані. `fetch` потрапляє до строгих дублерів Resend і Polar (`mocks/resend.ts`, `mocks/polar.ts`), а запит до будь-якого іншого хоста завершується помилкою, наче машина офлайн, тож ніщо її не залишає. Запит, який провайдер відхилив би, провалює тест.
- `renderWithRouter` з `src/platform/testing/lib/render.tsx` рендерить компоненти зі справжнім роутером і `QueryClient`.

## Протестуйте сценарій використання

Скорочена версія `src/modules/category/use-cases/__test__/create-category.test.ts`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"

import { executeMutation } from "~/src/platform/testing/lib/query"

import { createAuthSessionFixture } from "~/src/integrations/better-auth/__test__/fixtures/auth.session.fixture"
import { ROLE_CODES } from "~/src/integrations/better-auth/auth.access"
import type { auth } from "~/src/integrations/better-auth/auth.server"
import * as authServer from "~/src/integrations/better-auth/auth.server"

import { ERROR_CODES } from "~/src/modules/_core/constants/errors"
import { CATEGORY_KIND } from "~/src/modules/category/category.constants"
import { createCategoryMutation } from "~/src/modules/category/use-cases/create-category"

const getSessionMock = vi.hoisted(() => vi.fn<(typeof auth.api)["getSession"]>())

vi.mock(import("@tanstack/react-start/server-only"), () => ({}))

describe("create-category", () => {
  it("returns a domain error when the caller is not an admin", async () => {
    vi.spyOn(authServer.auth.api, "getSession").mockImplementation(getSessionMock)
    getSessionMock.mockResolvedValue(
      createAuthSessionFixture({ role: ROLE_CODES.CUSTOMER, userId: "01900000-0000-7000-8000-000000000001" }),
    )

    await expect(executeMutation(createCategoryMutation, { kind: CATEGORY_KIND.CATEGORY, name: "SaaS Plans" })).rejects.toThrow(
      ERROR_CODES.FORBIDDEN,
    )
  })
})
```

Перевіряйте кожен результат сценарію використання: успіх, кожен код `AppError`, відсутню сесію й відсутній дозвіл. Доменні значення й коди помилок беруться з їхніх констант (`CATEGORY_KIND`, `ERROR_CODES`), а не з повторюваних рядків.

## Протестуйте роботу з Resend і Polar

Не мокайте SDK Resend чи Polar. Викличте код, який надсилає запит, і перевірте, що отримав дублер. `getSentEmails(recipient)` з `mocks/resend.ts` повертає доставлені листи з їхнім відрендереним HTML і ключем ідемпотентності; `mocks/polar.ts` зберігає сеанси оплати, замовлення й ліцензійні ключі, а його функції просувають покупку далі: `payPolarCheckout`, `grantPolarLicenseKey`, `refundPolarOrder`, `revokePolarLicenseKey` і `activatePolarLicenseKey`. Скорочена версія `src/modules/license/__test__/license-purchase.integration.test.ts`:

```ts
const buyer = await signUpAndVerify()
const order = await paidOrder(buyer, LICENSE_TIER.COMPLETE)

expect(await deliver(POLAR_WEBHOOK_EVENT.ORDER_PAID, order)).toBe(HTTP_STATUS.OK)
expect(await currentLicense(buyer)).toMatchObject({ status: LICENSE_STATUS.ACTIVE, tier: LICENSE_TIER.COMPLETE })
```

`paidOrder` створює сеанс оплати через справжній `startCheckout` і оплачує його в дублері. `deliver` підписує подію через `signedPolarWebhook` з `lib/polar.ts`, надсилає її на кінцеву точку Polar у Better Auth і повертає статус відповіді, тож виконуються і перевірка підпису, і плагін, і обробники в `license.webhooks.ts`. Щоб перевірити, як застосунок обробляє збій провайдера, дайте на один запит відповідь з помилкою провайдера, як це робить `resend.utils.test.ts`: `vi.spyOn(globalThis, "fetch").mockResolvedValueOnce(Response.json(error, { status }))`.

## Протестуйте процес автентифікації

Набори автентифікації працюють зі справжнім `auth` з `auth.server.ts`. `src/integrations/better-auth/__test__/fixtures/auth.harness.ts` створює облікові записи так само, як це робить відвідувач: `signUp`, `verifyEmail` (переходить за токеном з доставленого листа й повертає сесію, яку він відкриває), `signIn` і `signUpAndVerify`. `browserHeaders()` дає кожному запиту власний `CF-Connecting-IP`, тож обмеження частоти запитів Better Auth діють як у production, і жоден тест не вичерпує ліміт іншого. Перш ніж читати лист, який Better Auth надсилає у фоні, дочекайтеся `flushWaitUntil()` через `await`.

## Протестуйте компонент

Тести компонентів рендерять зі справжніми повідомленнями з `messages/en-US`, мокають модуль сценарію використання, який надає параметри мутації, і керують інтерфейсом через Testing Library та `userEvent`. Для станів очікування тримайте замоканий запит відкритим через `Promise.withResolvers()`, перевірте інтерфейс очікування, потім розв'яжіть запит усередині `act` і перевірте інтерфейс у стані спокою. Компонент, який змінюється із затримкою, тестують фейковими таймерами (`vi.useFakeTimers()`, потім `vi.advanceTimersByTimeAsync` усередині `act`), ніколи не чекаючи реального часу, а `QueryClient` у тесті маршруту тримає дані, отримані loader, свіжими (`staleTime: Infinity`), тож швидкість рендерингу на машині ніколи не змінює того, скільки разів виконується запит. `userEvent.setup({ delay: null })` керує інтерфейсом без справжнього таймера між натисканнями клавіш. Повний приклад — `src/presentation/components/custom/__test__/newsletter-form.component.test.tsx`. Тест маршруту передає маршруту дані loader, а тест `node` покриває loader через `getRouter()`: `src/routes/__test__/marketing-routes.component.test.tsx` і `marketing-loaders.test.ts` є двома половинами.

## Браузерні тести

Специфікації Playwright розміщено в `e2e/specs`, об'єкти сторінок — у `e2e/pages`, а фікстури — в `e2e/fixtures`. Вони працюють зі зібраним тестовим застосунком із локальними D1, KV і R2 у `.wrangler/test` та тестовими обліковими записами з `e2e/data/accounts.ts`. Локально Playwright сам застосовує міграції, наповнює базу, збирає й запускає цей застосунок.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:ui
```

Тестовий Worker встановлює ті самі дублери Resend і Polar і зберігає надіслані листи, тож специфікація може прочитати посилання підтвердження з `/__test/emails?to=<address>`. `deliverPaidOrder` у `e2e/fixtures/polar.ts` надсилає повну подію `order.paid`, підписану так само, як події інтеграційних наборів.

## Перед push

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`build:test` запускає повну збірку Cloudflare, якої модульні тести не перевіряють, а `test:e2e:pr` запускає всі специфікації в Chromium, як це робить CI для pull request.

CI запускає перевірки, покриття й браузерний набір у Chromium для кожного pull request і кожного push у `main`, а WebKit — щотижня та під час push у `main`.
