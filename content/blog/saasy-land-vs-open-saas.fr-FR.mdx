## Ce qu’Open SaaS fait bien

Open SaaS est le kit de démarrage SaaS gratuit dont la plupart des développeurs ont déjà entendu parler, et il le mérite.

**Il est gratuit et populaire.** Il est sous licence MIT, et son dépôt comptait **16 427 étoiles** sur GitHub le 25 novembre 2026. Une large communauté l’a utilisé, si bien que la plupart des questions que vous vous poserez ont déjà une réponse dans ses issues ou sur le Discord de Wasp.

**Il offre plus de fonctionnalités aujourd’hui.** La connexion par e-mail avec vérification, et Google, GitHub et Discord prêts à être activés. Les tâches en arrière-plan et les tâches cron, via les jobs de Wasp sur PgBoss. L’envoi de fichiers vers AWS S3. Un tableau de bord d’administration avec les statistiques de Plausible ou de Google Analytics. Une application de démonstration OpenAI. Un site de documentation et un blog sur Astro Starlight. Les paiements avec Stripe, Lemon Squeezy, Polar ou Paddle, choisis dans un seul fichier.

**Il se déploie en une commande.** `wasp deploy` envoie la base de données, le serveur et le client sur Fly.io ou Railway, il existe un template Railway en un clic, et vous pouvez déployer à la main sur n’importe quel autre hébergeur.

**Il s’adresse aux agents de codage.** Le template contient un `AGENTS.md` et un `CLAUDE.md`, des skills pour agents dans `.agents` et `.claude`, une documentation adaptée aux LLM via `llms.txt`, et le dépôt décrit un plugin Claude Code.

**Wasp fait beaucoup de travail pour vous.** Son README le décrit comme un framework qui « masque la complexité de fonctionnalités full-stack comme l’authentification, les tâches en arrière-plan, le RPC, l’envoi d’e-mails, la sûreté des types de bout en bout, le déploiement en une seule commande, et plus encore ». Si vous voulez que ces décisions soient prises et maintenues par quelqu’un d’autre, c’est exactement ce que vous obtenez.

Si votre question est « quel est le moyen gratuit le plus rapide d’arriver à un SaaS qui fonctionne, avec paiements, tâches et envoi de fichiers ? », Open SaaS est une très bonne réponse, et vous n’avez aucune raison de penser qu’il vous faut autre chose.

## La vraie différence : un framework en dessous, ou aucun

Les deux produits vous donnent du code React que vous pouvez lire et modifier. La différence, c’est ce sur quoi ce code repose.

**Open SaaS repose sur Wasp.** Vous déclarez votre application dans `main.wasp.ts` : ses routes, ses méthodes d’authentification, ses tâches, son expéditeur d’e-mails, ses opérations. La CLI de Wasp lit cette déclaration, puis construit et exécute l’application, avec React dans le navigateur, et Node.js et Prisma sur le serveur. C’est ainsi qu’Open SaaS obtient l’authentification, les tâches et le déploiement en une commande en si peu de lignes. Cela signifie aussi que votre application dépend de Wasp : de son rythme de publication, de ses mises à niveau entre versions et de sa CLI. Le guide des tests d’Open SaaS vous demande lui-même de définir `WASP_VERSION` dans la CI pour qu’elle corresponde à la version qu’utilise votre projet. Le README de Wasp indique qu’il est en bêta, « la plupart des fonctionnalités étant entièrement développées et fonctionnant bien ».

Rien de tout cela n’est un défaut. C’est un compromis, et pour beaucoup de projets un bon : vous cédez une part du contrôle sur la tuyauterie, et vous obtenez beaucoup de tuyauterie gratuitement.

**SaaSy Land ne repose sur rien qui lui appartienne.** La CLI écrit du code ordinaire pour la stack que vous avez choisie : aujourd’hui TanStack Start, React et Vite+, Better Auth, Drizzle avec Cloudflare D1, Resend et use-intl. Il n’y a pas de runtime SaaSy Land, pas de paquet SaaSy Land que votre application importe et pas de langage de configuration maison à apprendre. Supprimez la CLI le lendemain de la génération : le projet s’installe, se construit, se teste et se déploie toujours, parce que chacune de ses lignes vous appartient.

Ce choix a lui aussi un coût bien réel. Tout ce que Wasp aurait écrit pour vous, la CLI doit l’écrire dans votre projet, sous forme de code qui vous appartient ensuite : aujourd’hui, ce sont l’authentification, l’e-mail, la console d’administration, la documentation et un blog, les tests et le workflow CI, mais pas encore la facturation, les tâches ni l’envoi de fichiers. Et « la stack de votre choix », c’est aujourd’hui une seule stack. La [feuille de route](/docs/project/roadmap) liste le reste dans l’ordre d’arrivée : la facturation avec Polar et l’e-mail avec Plunk, Stripe, votre propre serveur avec Docker, Prisma, une API séparée, le temps réel et MongoDB, puis Postgres, Vercel, Next.js, React Router, Solid, Vue avec Nuxt, Svelte avec SvelteKit, et Angular avec Analog ou Angular SSR. Chaque option n’est activée que lorsqu’un projet généré avec elle s’installe, passe la vérification des types, réussit ses tests, se construit et démarre en CI.

## Ce que chacun apporte à votre agent de codage

L’essentiel du nouveau code d’un SaaS est aujourd’hui écrit par un agent : c’est donc la question dont dépendent le plus d’heures de travail.

Open SaaS donne à un agent du **contexte**. Son `AGENTS.md` demande à l’agent de lire la documentation d’Open SaaS et de Wasp via leurs index `llms.txt` avant de commencer, le template embarque des skills pour agents comme une visite guidée, et le fichier de configuration unique de Wasp donne à l’agent une vue d’ensemble de toute l’application en un seul endroit. L’agent écrit ainsi plus vite du code Wasp qui a l’air juste.

SaaSy Land donne à un agent des **conséquences**. Un projet généré a un `AGENTS.md` et un README qui décrivent la stack choisie, et un workflow CI qui lance la vérification et les tests avec couverture, puis la suite de tests dans le navigateur, à chaque pull request. Ce site, la référence dont les templates sont tirés, bloque la fusion sous <RepositoryFact name="coverageThreshold" /> % de couverture des instructions, des branches, des fonctions et des lignes sur <RepositoryFact name="testFiles" /> fichiers de test, exécute <RepositoryFact name="e2eTests" /> tests de bout en bout dans le navigateur, refuse un `any` ou une règle de lint désactivée, et fait échouer la CI quand une traduction manque dans l’une de ses <RepositoryFact name="languages" /> langues.

Les instructions et les vérifications ne sont pas rivales ; les deux dépôts ont des instructions. La différence apparaît le jour où l’agent les ignore. Une instruction qu’un agent a sautée, c’est un relecteur qui la découvre, ou un client. Une vérification qu’un agent a cassée, c’est la pull request qui la révèle, avant toute fusion. Nous avons écrit sur cette différence dans [les garde-fous qui font échouer une mauvaise modification](/blog/ai-coding-agent-guardrails).

## Tests

Open SaaS inclut des tests de bout en bout Playwright dans son répertoire `e2e-tests` : quatre fichiers de spécifications au 25 novembre 2026, qui couvrent la page d’accueil, la page des tarifs, les redirections d’authentification et l’application de démonstration. Son dépôt les exécute à chaque pull request, et son guide des tests explique comment copier ce workflow dans votre propre projet, car le template n’en fournit pas.

C’est un point de départ raisonnable, et plus que ce que livrent beaucoup de kits payants. Mais ce n’est pas la même promesse qu’un seuil de couverture. Une suite de bout en bout prouve que les parcours pour lesquels quelqu’un a écrit un test fonctionnent aujourd’hui. Un seuil de couverture refuse la fusion tant qu’une branche du code n’est exécutée par aucun test, et c’est là que se cachent la gestion des erreurs, les signatures de webhooks et les contrôles de permissions. Pour un humain qui teste à la main avant chaque version, la différence est mince. Pour un agent qui ouvre dix pull requests par jour, c’est presque toute la différence.

## Les paiements, et la question de Lemon Squeezy

Open SaaS prend en charge quatre prestataires de paiement : Stripe, Lemon Squeezy, Polar et Paddle. Vous en choisissez un dans `src/payment/paymentProcessor.ts` et dans son équivalent côté client, puis vous supprimez les dossiers, les variables d’environnement et les paquets des autres prestataires, comme le décrit son guide des paiements. Trois des quatre sont des Merchants of Record, qui gèrent les taxes sur les ventes à votre place.

L’un d’eux ferme. Lemon Squeezy a fermé l’inscription de nouvelles boutiques le 16 novembre 2026 et cessera de traiter les paiements le 31 mars 2027 ; son annonce recommande Managed Payments de Stripe aux entreprises situées dans un pays pris en charge. Au 25 novembre 2026, Open SaaS mentionne toujours Lemon Squeezy dans son README et dans son guide des paiements. Si vous démarrez sur Open SaaS maintenant, choisissez Stripe, Polar ou Paddle.

Les projets générés par SaaSy Land n’ont pas de facturation au 25 novembre 2026. Ce site vend ses propres licences via Polar, et la facturation avec Polar, puis avec Stripe, est en tête de la feuille de route. Si vous avez besoin des paiements dès la première semaine et ne voulez pas les écrire, c’est à lui seul une raison de choisir Open SaaS aujourd’hui.

## Mises à jour

Open SaaS est franc sur les mises à jour : sa documentation déconseille de fusionner les modifications ultérieures du template dans une application déjà commencée, parce que votre code aura divergé, et suggère de recopier à la main les correctifs précis dont vous avez besoin. C’est honnête, et c’est ainsi que fonctionnent en pratique la plupart des templates gratuits.

SaaSy Land enregistre la version et vos réponses dans `saasyland.json` dans chaque projet généré, afin de pouvoir régénérer le même projet à partir d’une version plus récente. La commande `update` qui fusionnerait cela dans votre projet figure sur la feuille de route et n’est pas encore disponible. Aujourd’hui, aucun des deux produits ne met à jour votre projet à votre place.

## Ce que coûte chacun

Open SaaS ne coûte rien, et les services auxquels il se connecte vous facturent directement.

SaaSy Land a aussi une porte d’entrée gratuite : le code source complet de saasyland.com, avec son authentification, son espace client, sa console d’administration, son paiement Polar et son seuil de couverture, est public sous licence MIT. Vous pouvez tout lire, l’exécuter et construire dessus sans payer. Ce que vous payez, c’est le générateur : Core à <TierPrice tier="core" />, Complete à <TierPrice tier="complete" /> et Agency à <TierPrice tier="agency" />, chacun en paiement unique avec les mises à jour à vie du socle. Core et Complete couvrent vos propres produits ; Agency y ajoute un nombre illimité de projets clients, en marque blanche, avec un appel d’architecture de <RepositoryFact name="callMinutes" /> minutes. Chaque clé fonctionne sur <ActivationLimit tier="core" />, <ActivationLimit tier="complete" /> ou <ActivationLimit tier="agency" /> machines à la fois.

## Quand choisir Open SaaS

- Vous ne voulez rien dépenser, et une licence MIT est ce qu’il vous faut.
- Vous avez besoin de tâches en arrière-plan, d’envoi de fichiers ou de paiements dès la première semaine, sans les écrire.
- Construire sur Wasp et suivre ses versions ne vous dérange pas, et vous aimez déclarer votre application dans un seul fichier de configuration.
- Vous voulez déployer en une commande sur Fly.io ou Railway, avec PostgreSQL.
- Votre produit est dans une seule langue, ou vous ajouterez les traductions vous-même.

## Quand choisir SaaSy Land

- Vous voulez du code standard sans framework maison en dessous, pour que rien ne s’interpose entre votre projet et les versions de sa propre stack.
- La majeure partie de votre code est écrite par des agents de codage, et vous voulez des vérifications qui font échouer la pull request quand l’un d’eux casse quelque chose, pas seulement des instructions qu’il risque de sauter.
- Vous vendez dans plus d’une langue et voulez que chaque texte, chaque date et chaque prix soient traduits dès le premier jour, avec une CI qui échoue sur une clé manquante.
- Vous déployez aujourd’hui sur Cloudflare Workers avec D1, ou vous attendrez que la stack que vous voulez arrive sur la feuille de route.
- Vous travaillez pour des clients et voulez une licence qui le prévoit : Agency couvre un nombre illimité de projets clients.

Et si vous hésitez encore, commencez par la partie gratuite : lisez le code source de ce site, lancez ses tests, et voyez si c’est la base de code dans laquelle vous voulez que votre agent travaille.
