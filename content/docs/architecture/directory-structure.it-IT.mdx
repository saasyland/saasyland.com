## Regole di posizionamento

- **File e cartelle usano il kebab-case.** I test si trovano in una cartella `__test__` adiacente.
- **Le route si limitano a comporre.** Un file di route definisce il componente di pagina o di layout, `NAMESPACE` o `NAMESPACES`, il loader e `head`. Non contiene widget, dialog né definizioni di colonne.
- **I moduli sono tabelle del database.** Crea `src/modules/<name>` solo per una tabella reale. Una server function che non lavora su una tabella va in `src/lib` (ad esempio `src/lib/github.ts`) oppure, se la usa una sola route, nel file di quella route.
- **I componenti condivisi sono piatti.** Un componente usato in più aree è un singolo file direttamente in `presentation/components/custom`.
- **Cartelle di area e di pagina.** I componenti usati da una sola area si trovano in `admin/`, `app/`, `auth/`, `blog/`, `courses/`, `landing-page/` o `settings/`, che contiene le card dell’account condivise da `/app/settings` e `/admin/settings`. Le pagine admin hanno una propria cartella, come `admin/users/`. La landing page è suddivisa in `sections/` (un file per ogni sezione della pagina) e `components/` (le parti condivise dalle sezioni).
- **Un widget, dialog, form o set di colonne per file.** Non dividere un componente in un wrapper e in un file `-content`.
- **Nessuna cartella di helper annidata.** Le cartelle dei componenti non contengono mai sottocartelle `components/`, `constants/`, `hooks/`, `lib/` o `types/`, e nessun file helper `.ts` sta accanto a un componente. Una costante usata da un solo componente resta nel file di quel componente.
- **I dati condivisi vanno in `src/data`.** Esempi: `MARKETING_SECTION_IDS` e le opzioni della CLI. Lì le aree dichiarano anche ciò che aggiungono alla piattaforma: handler del Worker e plugin di Vite (vedi [Cosa aggiungono le aree](/docs/architecture/platform-layer#what-the-areas-add)).
- **I percorsi di ogni area vanno in `src/areas/<area>.shared.ts`.** Ogni runtime carica quel file: il browser, il Worker, gli script Bun, Playwright e `vite.config.ts`. Per questo contiene solo costanti e importa con percorsi relativi, e `src/routes.ts` riunisce i percorsi di tutte le aree (vedi [Percorsi e navigazione](/docs/conventions/routes#paths-and-navigation)). I controlli del sito online sono un tipo di file a sé, `src/areas/<area>.live.ts`, perché li caricano solo la verifica dopo il deploy e la documentazione. Ciò che un'area aggiunge alle pagine, come i namespace dei layout, il fuso orario, i componenti radice e le sue voci nella console di amministrazione e nello spazio di lavoro del cliente, va nel suo file del browser, `src/areas/<area>.ts`, un oggetto `<AREA>_BROWSER` che caricano solo il browser e il rendering sul server. Anche le voci di menu sono un tipo di file a sé e puro, `src/areas/<area>.navigation.ts`, che `src/areas/navigation.entries.ts` riunisce e `src/data/navigation.ts` legge, perché il progetto Remotion legge il menu dell'admin e il suo job di CI installa solo i pacchetti propri di Remotion, quindi non può caricare il file del browser di un'area, `src/areas/<area>.ts`, che importa codice del router, di TanStack Query e delle server function. Le sue dichiarazioni di permesso vanno in un file a sé, `src/areas/<area>.access.ts`, così che una persona revisioni ogni loro modifica.
- **I file generati non si modificano a mano.** Il plugin del router scrive `src/routeTree.gen.ts`, `bun run cf-typegen` scrive `src/types/worker-configuration.d.ts`, mentre `bun run content` e `bun run generate:cn` scrivono `.source/`.
