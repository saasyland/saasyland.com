Toda alteração é entregue com os testes que a comprovam, no mesmo commit, e a cobertura se mantém em <RepositoryFact name="coverageThreshold" unit="percent" /> para linhas, instruções, funções e branches. A correção de um bug vem com um teste que falha sem a correção.

## Projetos

`vite.config.ts` define três projetos do Vitest, escolhidos pelo sufixo do arquivo. Os testes importam a sua API de `vite-plus/test` e ficam em `__test__/`, ao lado do código que cobrem.

| Sufixo                 | Projeto       | Use para                                                                                                                                                                                 |
| ---------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | Casos de uso, loaders, `head`, schemas, utilitários: tudo o que roda no servidor                                                                                                         |
| `.integration.test.ts` | `integration` | Fluxos do Better Auth, de pagamento e de licença, o adaptador do D1 e o carregamento de mensagens, com timeouts de <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Componentes e páginas no jsdom                                                                                                                                                           |

`src/platform/testing/mocks/cloudflare.ts` substitui `cloudflare:workers` em todos os projetos: o D1 é um banco de dados `node:sqlite` em memória criado a partir de todas as migrações versionadas, e o KV e um bucket para cada binding do R2 do ambiente `test` em `wrangler.jsonc` são armazenamentos em memória. `resetTestBindings()` esvazia o KV, o bucket e a tabela de rate limit antes de cada teste, e a função de seed de cada suíte redefine as linhas de que ela depende. Nenhum teste se comunica com o Cloudflare, a Polar, o Resend ou um provedor OAuth: o `fetch` chega aos dublês estritos em `mocks/resend.ts` e `mocks/polar.ts`, que validam cada requisição com base nos modelos de requisição dos SDKs e fazem o teste falhar diante de uma que o provedor recusaria. Os testes verificam o que o dublê recebeu em vez de fazer mock de um método do SDK, e as suítes de autenticação exercitam a configuração real de `auth.server.ts` por meio de `auth.harness.ts`.

## Testar uma server function

Chame-a pelas options que ela exporta, para que o teste exercite o middleware, a validação e o handler reais. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts`:

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` e `executeMutation(options, variables)` de `src/platform/testing/lib/query.ts` executam as options em um `QueryClient` novo.
- A sessão vem de `createAuthSessionFixture` em `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts`; toda permissão também é testada pelo lado que precisa ser recusado (`it("is for staff only")`).
- Os dados de seed ficam em `__test__/fixtures/` do módulo, com os seus IDs em objetos nomeados (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` exclui as linhas que são suas e as insere de novo pelo Drizzle, então todo teste começa do mesmo estado.
- No projeto `component`, uma server function falha, porque o jsdom faz o papel do navegador. Os testes de componentes fornecem a uma rota os dados do loader ou fazem mock de `queryFn` e `mutationFn` das options que o componente lê.

## As asserções usam os nomes do código

- Status, tipos, papéis e códigos de erro esperados são as constantes que o código usa: `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. Um teste nunca repete um literal de string do domínio, e os dados do e2e e o seed de teste também não: `e2e/data/courses.ts` escreve `kind: COURSE_KIND.COURSE`.
- Os testes de schema são o único lugar em que um valor armazenado é escrito por extenso: `license.schema.test.ts` fixa `expect(LICENSE_STATUSES).toStrictEqual(["active", "revoked", "refunded"])`, de modo que mudar um valor guardado no banco faz um teste falhar em vez de exigir uma migração que ninguém escreveu.
- A suíte do navegador importa suas constantes da aplicação (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`), então só pode importar arquivos que carregam fora do Worker. Os valores da Polar vêm de `polar.constants.ts`, que não lê nenhuma variável de ambiente: `e2e/fixtures/license.ts` e a jornada no sandbox tiram os status de pedido de `POLAR_ORDER_STATUS`, e o pedido em si vem de `src/platform/testing/lib/polar.ts`. Os IDs de produto dos planos são a exceção: `POLAR_PRODUCT_IDS` lê `cloudflare:workers`, então a suíte do navegador os lê de `.env.test`.
- Os testes de componentes leem os textos esperados dos arquivos de mensagens em inglês, como faz `admin-course-routes.component.test.tsx` com `import labels from "~/messages/en-US/pages.admin.courses.json"` e `labels.form.kinds.course`, e encontram os elementos pelo papel e pelo nome acessível.
- Um teste que precisa de um tipo o lê de uma fonte tipada ou o verifica em tempo de execução com `toHaveProperty`; ele nunca faz cast.
- Os nomes dos testes descrevem o comportamento como uma frase: "lists every course with its lesson count, drafts included".

## Cobertura

`bun run test:coverage` falha abaixo de <RepositoryFact name="coverageThreshold" unit="percent" /> em qualquer uma das quatro métricas para `src/**/*.{ts,tsx}`. Ficam de fora os testes, `__test__/`, os arquivos de declaração, `src/routeTree.gen.ts`, os primitivos do shadcn e `src/platform/testing/`. A exigência continua significativa assim:

- **Exclua os branches que nunca podem ser executados** em vez de cobri-los com stubs. Um `?? fallback` sobre dados que estão sempre presentes, ou um optional chaining sobre um valor que não pode ser `undefined`, é removido do código-fonte, e não alcançado com o stub de um global.
- **Cubra comportamento real.** Os estados pendentes mantêm a requisição aberta com `Promise.withResolvers()`, verificam a UI pendente, resolvem dentro de `act` e verificam a UI ociosa, como fazem `expectPending` e `expectIdle` em `auth-forms.component.test.tsx`.
- **Mantenha as asserções quando uma regra apertar.** Quando um teste ultrapassa `max-statements`, extraia um helper nomeado em vez de remover verificações.
- **Carregue todos os arquivos de mensagens.** `i18n.messages.test.ts` carrega todos os namespaces de todos os locales, e é isso que cobre as linhas de `import.meta.glob` em `i18n.loaders.ts`. Um arquivo de mensagens novo fica coberto por ele automaticamente.

## Testes em uma máquina sobrecarregada

O limite de tempo do Vitest e a margem de um segundo de `waitFor` e `findBy*` contam tempo real, então um teste que faz trabalho de que seu comportamento não precisa, ou que espera um timer, falha em uma máquina sobrecarregada mesmo sem nada quebrado. O limite padrão continua como está; um teste lento é alterado para fazer menos:

- **Uma verificação sobre muitos arquivos roda um teste por arquivo.** `check-content.test.ts` roda `pageProblems` para cada página em inglês com `it.each(sourcePages())`, e uma divergência informa a sua página.
- **O que um componente espera com Suspense é carregado antes de renderizá-lo**, como `preloadNamespaces` faz com as traduções. Quando o teste trata do próprio carregamento, ele o resolve dentro de `act`, como `translations-provider.component.test.tsx`: o conteúdo que retoma fora de `act` só aparece depois do atraso com que o React o revela, em um timer real, e o teste precisa consultar o DOM até vê-lo.
- **Um teste substitui um módulo uma única vez em vez de importar o componente de novo.** `affiliate-referral.component.test.tsx` simula `AFFILIATE_PROGRAM` uma vez e o define em cada teste. Importar um componente depois de `vi.resetModules()` avalia de novo todo o seu grafo de imports dentro do teste.
- **As fixtures que todo teste lê são criadas uma vez por arquivo**, como as mensagens de `getTestMessages`.
- **Um formulário é preenchido com `user.paste`, a menos que as teclas sejam o comportamento testado.** `fill` em `admin-course-routes.component.test.tsx` clica no campo e cola; `user.type` executa a validação e a renderização do formulário a cada caractere.
- **Uma lista longa de opções é barata de renderizar de novo.** O combobox de fusos horários de `preferences-card.tsx` passa suas opções para `ComboboxList` como `items` memoizados, então o React Aria as reutiliza quando o formulário renderiza de novo.

## Os testes seguem as funcionalidades [#tests-follow-the-features]

As funcionalidades cujos arquivos e caminhos `scripts/features.ts` nomeia (veja [Caminhos e navegação](/docs/conventions/routes#paths-and-navigation)) também são donas dos seus testes, então a CLI `saasyland` pode deixar uma funcionalidade fora de um projeto gerado junto com os testes dela, enquanto todos os outros testes continuam passando.

Um arquivo de teste cobre uma funcionalidade ou um arquivo de código. As páginas de administração de uma funcionalidade são testadas com os esqueletos e a trilha de navegação em `src/routes/__test__/admin-<feature>-routes.component.test.tsx`, e os loaders delas em `admin-<feature>-loaders.test.ts`. O teste de um esqueleto de layout o renderiza com `createTestRouter(path, routeTree)` de `src/platform/testing/lib/render.tsx`, um router sobre a árvore de rotas real, e os esqueletos dos cursos são testados em `admin/__test__/courses-pending.component.test.tsx`, porque `admin-course-routes` reconstrói as rotas dos cursos para o seu próprio router; `admin-layout`, `admin-dashboard` e `admin-loaders` testam a própria interface de administração e não citam nenhuma funcionalidade. Arquivos sem relação entre si têm cada um o seu arquivo de teste, como `background.component.test.tsx` e `wordmark.component.test.tsx`, e cada handler da API tem o seu: `src/routes/api/__test__/auth.test.ts` e `index.test.ts`. `cli.v1.test.ts` cobre os arquivos de rota da API de licenças da CLI, cujo comportamento é testado em `src/modules/license/__test__/license.api.integration.test.ts`.

Uma lista que abrange várias funcionalidades não tem barrel: cada funcionalidade declara a sua parte em um arquivo próprio, e o único arquivo que lê a lista importa cada parte e as escreve em uma lista literal, então deixar uma funcionalidade de fora apaga o arquivo dela e, com o import, o elemento dela:

| Lista                               | Cada funcionalidade declara                                                                                                                    | Listada por                                                                 |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Dados de consultas da administração | `seed<Feature>Queries` e as fábricas de linhas dela em `src/presentation/components/custom/admin/__test__/<feature>.fixtures.ts`               | `adminQueryClient()` em `fixtures.tsx`                                      |
| Rótulos de enumerações              | `src/integrations/use-intl/__test__/<feature>.labels.ts`                                                                                       | `ENUM_LABELS` em `enum-labels.test.ts`, com os rótulos da base escritos ali |
| Linhas do D1                        | `src/integrations/drizzle-orm/__test__/<feature>.rows.ts`                                                                                      | `d1.integration.test.ts`                                                    |
| Páginas dos testes no navegador     | `e2e/data/<feature>.pages.ts`                                                                                                                  | `ENTRIES` em `e2e/data/pages.ts`, com as páginas iniciais escritas ali      |
| Banco de dados de teste             | `e2e/data/<feature>.seed.ts`                                                                                                                   | `scripts/seed-test.ts`                                                      |
| Inventário de fluxos                | `e2e/data/<feature>.flows.ts`: os fluxos da funcionalidade, cada um com o teste que o prova ou o motivo pelo qual ele falta                    | `FLOWS` em `scripts/check-flows.ts`                                         |
| Consultas públicas                  | uma consulta com `public: true` no próprio arquivo de código                                                                                   | `PUBLIC_QUERIES` em `auth.session.test.ts`, uma propriedade por consulta    |
| Dublês dos provedores               | `src/platform/testing/mocks/<provider>.ts`: uma lista `<PROVIDER>_PROVIDER_DOUBLES`, cada dublê com `origin`, `respond` e `reset`              | `DOUBLES` em `mocks/providers.ts`                                           |
| Catálogo da Polar                   | `src/modules/<module>/__test__/fixtures/<feature>.polar-catalogue.ts`: os produtos e benefícios de chave de licença que a funcionalidade vende | `CATALOGUES` em `mocks/polar.ts`                                            |
| Worker de testes                    | `e2e/data/<feature>.worker.ts`: preparações e endpoints de teste                                                                               | `ENTRIES` em `src/platform/testing/worker.ts`                               |

Nenhum arquivo declara uma lista vazia para a base: um item que todo projeto tem é escrito na própria lista, como as páginas iniciais em `e2e/data/pages.ts`, e `scripts/seed-test.ts` só roda o Wrangler quando uma funcionalidade semeia linhas. O page object de uma funcionalidade vem com uma fixture própria: `e2e/fixtures/auth.ts` estende o `test` base de `e2e/fixtures/test.ts` com `authPage`, e as specs que fazem login importam `test` dali. Os helpers de e-mail de uma funcionalidade também ficam em um arquivo de fixtures próprio, como `e2e/fixtures/license-emails.ts` e `e2e/fixtures/invitation-emails.ts`, ao lado dos compartilhados `getSentEmails`, `latestEmail` e `linkTo` de `e2e/fixtures/emails.ts`, e o dublê de navegador de uma funcionalidade entra em `BROWSER_DOUBLES` em `e2e/fixtures/test.ts`, como `servePolarCheckout`.

Helpers usados por várias funcionalidades existem uma única vez: `renderAdmin` e `renderAdminPage` em `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` em `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` e `busyMarkup` em `src/platform/testing/lib/skeleton.tsx` e, nos testes no navegador, `AuthPage.signIn`, `BasePage.leaveWhileLoading` e a fixture `pageWithoutJavaScript`. As specs das páginas públicas, como `accessibility.spec.ts` e `theme.spec.ts`, não fazem login em nenhuma conta; `workspaces.spec.ts` verifica as páginas logadas, a acessibilidade delas e o tema delas.

Um teste de código compartilhado que precisa de um item fornecido pelas funcionalidades declara o seu próprio em vez de ler o de uma funcionalidade. `dashboard-actions.component.test.tsx` substitui `ADMIN_DASHBOARD_ACTIONS` por uma ação local do teste, para que `DashboardActions` e os marcadores das ações de `AdminDashboardPending` continuem cobertos em um projeto sem a funcionalidade de pagamentos, que hoje declara as ações do painel. `server.test.ts` serve os arquivos de cada handler de requisição e passa cada reescrita de documento pelo Worker em um teste que nomeia o módulo próprio da funcionalidade, de modo que deixar a funcionalidade de fora apaga o teste, `vite-config.test.ts` carrega `VITE_PLUGINS` na ordem deles, e os plugins de um fornecedor são testados ao lado, como em `zod.vite.test.ts`. Código compartilhado que só funcionalidades opcionais renderizam ganha um teste próprio: `pending-blocks.component.test.tsx` cobre o esqueleto de campo que os esqueletos da administração de cursos usam. `auth.access.test.ts` verifica o que cada papel recebe, cada funcionalidade verifica as próprias declarações em `auth.access.<feature>.test.ts`, como `auth.access.courses.test.ts`, e `auth.access.website.test.ts` fixa as permissões de cada papel no site.

`auth.server.test.ts` lista em ordem o id de cada plugin do Better Auth, e `navigation.test.ts` verifica os menus sem esperar nenhum item específico, então passa com quaisquer itens que um projeto mantenha. `translations-provider.component.test.tsx` usa namespaces da base como exemplo e os testes de autenticação usam os dados e os caminhos da própria funcionalidade de autenticação, como a lista de sessões e `/app/settings`.

O teste de rota da licença substitui o `CourseUnlocks` dos cursos por uma seção local do teste e faz mock da sua query do catálogo, o teste de esqueleto da licença faz o mesmo com `CourseUnlocksPending`, e os testes de cursos substituem as concessões de acesso aos cursos de `lesson.access.ts` por `TEST_COURSE_ACCESS` através de `withTestCourseAccess` (`src/modules/course/__test__/fixtures/course-access.ts`), então os testes de nenhuma das duas funcionalidades leem a outra. `src/modules/lesson/__test__/lesson.access.license.test.ts` cobre o que as une: a concessão da licença, com um snapshot de quem pode assistir a cada aula para um visitante, uma conta, a equipe e cada nível e status de licença.

Um teste que fixa o site inteiro, como `navigation.website.test.ts` com a ordem de cada menu, pertence só ao site; os templates não o geram.

`scripts/features.ts` lista como globs os arquivos de cada funcionalidade opcional, os nomes que a funcionalidade tem em arquivos que ficam, como os caminhos dela em `src/routes.ts`, e as funcionalidades de que ela depende, e `bun run check:features` verifica que o site continua funcionando sem elas. Um cenário deixa de fora apenas as funcionalidades que só o site tem; cada um dos outros deixa de fora também os cursos, as funcionalidades de cobrança, o conteúdo ou a autenticação. Para cada cenário, o script apaga os arquivos dessas funcionalidades e de toda funcionalidade que depende de alguma delas, e depois poda os arquivos que ficam com uma única regra, a mesma que a CLI `saasyland` segue quando deixa uma funcionalidade de fora:

1. Apaga os nomes que as funcionalidades removidas têm, cada um com sua declaração ou propriedade de objeto.
2. Uma referência removida é um identificador importado de um arquivo apagado, o uso de um nome removido, como `ROUTES.COURSES` assim que `src/routes.ts` deixa de declará-lo, uma função que chama `import()` sobre um arquivo apagado, ou um `vi.mock`, `vi.doMock`, `vi.unmock` ou `vi.doUnmock` que nomeia um módulo apagado. Todo `import` e `export … from` de um arquivo apagado sai, e também todo import de um módulo que só um arquivo de declarações apagado declara, como `virtual:repository-facts`.
3. Uma referência removida no callback de um teste, isto é, um `it` ou um `test` em qualquer forma, como `.each`, `.skip` ou `.only`, ou um `test.step` do Playwright, leva o teste inteiro com ela. Para qualquer outra referência removida, apaga a mais próxima destas unidades que pode sair; uma função, uma classe, uma instrução `return`, uma condição ou um export nunca sai inteiro, então informa com arquivo, linha e coluna uma referência que só um deles envolve:
   - o elemento de array mais próximo dentro da sua instrução de nível superior ou, se não houver, a propriedade de objeto, o spread, o membro de tipo ou o filho JSX mais próximo, sem atravessar uma instrução;
   - a instrução de expressão em volta, no nível superior de um módulo, de um `describe` ou de um hook como `beforeEach`, e dentro de qualquer outra função só quando sai tudo o que ela nomeia de fora de si;
   - o declarador de variável em volta, quando o valor não é uma função nem uma classe e sai tudo o que o inicializador nomeia; os nomes que ele vincula passam então a ser nomes removidos também, e o declarador só sai se cada uso deles sair pela mesma regra. Um valor que também depende de código que fica, como o link que `signedInDestination(entry, workspace)` monta a partir de um item de menu, fica e é informado, porque o que precisa mudar é o design, não a poda;
   - o hook ou o `describe` em volta.
4. Quando isso esvazia um array que é propriedade de um elemento de array, o elemento também sai, como um grupo de menu que fica sem itens. Do mesmo jeito saem um teste cuja tabela `.each` fica vazia, um teste, passo, hook ou `describe` cujo callback fica vazio, um `describe` que fica sem nenhum teste e um laço ou callback com o corpo vazio, o callback junto com a unidade em volta. Se o corpo de uma função ou de uma condição ficasse vazio, as instruções ficam e as referências nelas são informadas.
5. Apaga cada string de um array que nomeia o namespace de um arquivo de mensagens apagado.
6. Apaga os especificadores de import, as declarações não exportadas, em qualquer nível, e os elementos de um padrão de desestruturação de array que nada mais referencia, deixando um buraco antes de um elemento que fica, e repete até nada mudar. Um arquivo `*.test.*` ou `*.spec.*` que fica sem nenhum teste é apagado inteiro.

`scripts/prune-references.ts` aplica a regra às árvores sintáticas do parser oxc, e `scripts/module-bindings.ts` resolve cada nome até a declaração a que ele se refere, então um parâmetro ou uma variável local com o mesmo nome nunca é confundido com um import. `scripts/test-cases.ts` reconhece os testes, grupos, hooks e mocks pelas chamadas ao que um arquivo importa como `it`, `test`, `describe`, um hook ou `vi`, com qualquer nome local, `scripts/prune-units.ts` escolhe a unidade em volta de cada referência, e `scripts/prune-edits.ts` grava as remoções mantendo o maior dos dois espaços em volta de uma instrução apagada, para a linha em branco entre grupos de instruções não sumir. Os arquivos gerados, que o `.gitattributes` marca como `linguist-generated`, são copiados como estão, e a checagem gera a árvore de rotas de novo. Depois, o script copia para um diretório temporário os arquivos que o Git rastreia ou adicionaria, os podados no lugar dos originais, formata os arquivos podados com `vp fmt`, gera as tabelas de nomes de classes, as coleções de conteúdo enquanto a funcionalidade de conteúdo fica e a árvore de rotas, com `scripts/generate-routes.ts`, roda `tsc --noEmit` sobre `src`, `e2e`, `scripts` e `vite.config.ts` e, por fim, `check:i18n` sobre as mensagens que restam. Um cenário falha por uma referência que a regra não consegue podar, por qualquer erro de tipo e por qualquer erro de tradução, e `src/__test__/check-features.test.ts` falha quando um glob não corresponde a nenhum arquivo ou um nome não está declarado no seu arquivo. Uma referência que a regra não consegue podar se corrige pondo o código onde a [estrutura de diretórios](/docs/architecture/directory-structure) manda, nunca com uma exceção na poda. A CI roda um job por cenário, e um cenário que falha faz a execução falhar ([CI/CD](/docs/tooling/ci-cd#checks)).

## Testes no navegador

O Playwright executa o Worker de teste compilado: `bun run build:test` o compila com D1 e KV locais em `.wrangler/test`, `bun run db:reset:test` recria esse banco de dados e cria as contas, o vídeo e o curso de `e2e/data`, e a entrada de teste captura os e-mails enviados em `/__test/emails`, para que uma spec possa seguir um link de verificação.

- As specs levam o nome do fluxo (`course-admin.spec.ts`, `auth-redirect.spec.ts`) e conduzem a página por papéis e nomes acessíveis, com os page objects em `e2e/pages/`.
- Cada spec cria os dados que altera com valores únicos, como um slug montado a partir de `crypto.randomUUID()`, e faz login a partir do seu próprio cabeçalho `CF-Connecting-IP`, para que as specs possam rodar em paralelo e ser executadas de novo sem colidir umas com as outras nem com os rate limits.
- Um teste que altera dados criados pelo seed, como os dispositivos de uma licença, recebe registros próprios criados pelo seed, um para cada worker paralelo, para que dois testes em execução nunca alterem o mesmo registro. `cli-licence-api.spec.ts` ativa dispositivos na licença que `TEST_CLI_LICENSES`, em `e2e/data/licenses.ts`, cria para o `parallelIndex` de cada worker, que o Playwright nunca atribui a dois workers ao mesmo tempo, e sua fixture `cliMachine` libera o dispositivo quando o teste termina, então uma nova tentativa começa da licença criada pelo seed. A licença `TEST_LICENSE`, que `license.spec.ts` lê, mantém apenas o dispositivo criado pelo seed.
- Uma spec age sobre uma página só depois que `waitForAppReady()` de `e2e/pages/base-page.ts` termina, inclusive após uma navegação no cliente. O método termina quando o TanStack Router renderizou a URL atual, que a fixture automática `recordRenders` registra a partir do evento `onRendered` do router, porque uma navegação no cliente muda a URL antes de a próxima rota renderizar. O conteúdo da rota pode ser hidratado depois dessa renderização, então uma spec que depende do estado próprio de um componente, ou que clica em um link fora do conteúdo antes de ele ser hidratado, chama antes `waitForHydration(element)`, que espera o React hidratar o elemento e tudo o que há nele; `LandingPage.goto()` faz isso com o `main` da landing page. Uma spec pode sair de uma página enquanto ela carrega, como um visitante pode, e uma que coleta os erros de página de várias visitas diretas abre cada visita na sua própria aba, como faz `auth-routing.spec.ts`, ou sai de cada página só depois que a rede dela fica ociosa (`page.waitForLoadState("networkidle")`), como faz `workspaces.spec.ts`, porque uma página dispara algumas requisições só depois da hidratação, como um selo na barra lateral ou os segmentos de um vídeo. Uma spec que coleta erros de página só sai de uma página depois que a navegação no cliente foi renderizada: o WebKit relata como erro de página uma requisição que a página inicia depois que a spec começou a sair dela, `Fetch API cannot load … due to access control checks.`, mesmo que o app trate a requisição que falhou.
- Uma spec que precisa provar que um texto nunca aparece, e não só que sumiu no fim, chama `watchForText(text)` de `e2e/pages/base-page.ts` antes da mudança e confere depois que o texto nunca apareceu: um `MutationObserver` na página o registra no momento em que é renderizado. O teste do upgrade em `checkout-funnel.spec.ts` faz isso com o agradecimento pelo plano antigo, e a suíte de jornada com o agradecimento por qualquer plano que não seja o comprado.
- Toda spec falha quando uma página viola a sua Content Security Policy: a fixture automática `cspViolations` de `e2e/fixtures/test.ts` registra cada evento `securitypolicyviolation` e espera que não haja nenhum quando o teste termina. Uma spec que provoca uma violação de propósito a retira com `cspViolations.splice(0)`, como faz `content-security-policy.spec.ts`. A suíte executa o build de produção de `build:test`, porque o servidor de desenvolvimento não envia nenhuma política de scripts.
- Os pull requests e a fila de mesclagem executam todas as specs no Chromium e no WebKit; localmente, `bun run test:e2e:pr` as executa no Chromium e `bun run test:e2e` nos dois. Os pushes para `main` executam o WebKit de novo, e uma execução semanal agendada executa os dois.
- Uma spec que lê a área de transferência usa o fixture `readClipboard` de `e2e/fixtures/test.ts`, que concede antes de a spec começar as permissões da área de transferência que o navegador conhece: no Chromium `clipboard-read` e `clipboard-write`, no WebKit só `clipboard-read`, porque o WebKit não tem permissão de escrita e deixa o clique que copia escrever na área de transferência, como o Safari.
- Uma spec que executa um fluxo de ponta a ponta e verifica o resultado dele é citada por esse fluxo em `e2e/data/<feature>.flows.ts`, pelo arquivo da spec e pelo título completo. `bun run check` falha quando um fluxo cita um teste que a suíte não tem, então um teste renomeado leva o seu fluxo junto no mesmo commit, e um fluxo que nenhum teste prova diz por quê. Veja [Cobertura de testes](/docs/tooling/test-coverage).
- Uma correção de rota, de fluxo ou visual que os testes unitários não conseguem ver ganha uma spec: as varreduras de acessibilidade e as regressões de navegação em `navigation.spec.ts` e nas specs das funcionalidades a que se referem, como `content.spec.ts`, `legal.spec.ts` e `landing.spec.ts`, são exemplos. Uma spec que rola a página a deixa alta o bastante por conta própria, como faz o teste de rolagem em `navigation.spec.ts`, em vez de depender do comprimento de uma página. Uma seção que se preenche depois que a página carrega mantém a altura, então uma spec que rola a página nunca precisa carregá-la antes: uma seção que mudava de altura acima da viewport movia o que o visitante estava lendo, e o WebKit interrompia uma rolagem suave quando a ancoragem de rolagem compensava isso. As specs do bloco de cursos em `landing.spec.ts` seguram a requisição dele, deixam que ela dê certo ou falhe e verificam que o bloco mantém a altura e que nenhum deslocamento de layout é relatado.
