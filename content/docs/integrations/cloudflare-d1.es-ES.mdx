Cloudflare D1 (SQLite) es la base de datos de la aplicación, vinculada como `DB`. `src/integrations/drizzle-orm/` la conecta con Drizzle:

| Archivo               | Propósito                                                                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `drizzle.database.ts` | `db` exclusivo del servidor, creado con `drizzle(env.DB, { schema })`                                                                       |
| `drizzle.schemas.ts`  | Reexporta el esquema de cada tabla y sus relaciones                                                                                         |
| `drizzle.config.ts`   | drizzle-kit: dialecto SQLite, driver `d1-http`, migraciones con prefijo de marca de tiempo en `migrations/`                                 |
| `drizzle.errors.ts`   | `rethrowAsConflict`, que convierte un error de restricción única en `AppError(ERROR_CODES.CONFLICT)` y vuelve a lanzar cualquier otro error |
| `drizzle.columns.ts`  | `timestamps()`, las columnas `createdAt` y `updatedAt` que cada tabla con marcas de tiempo incorpora a su esquema                           |

## Tablas

Cada tabla pertenece a un módulo en `src/modules/<table>/` con `<table>.schema.ts` (`drizzle-orm/sqlite-core`), más `.zod.ts`, `.constants.ts`, `.types.ts` y `use-cases/` cuando la tabla tiene operaciones y `.utils.ts` cuando necesita funciones auxiliares. Los módulos son `account`, `category`, `chapter`, `course`, `lesson`, `lesson-attachment`, `lesson-progress`, `license`, `newsletter-subscriber`, `order`, `product`, `rate-limit`, `session`, `subscription`, `two-factor`, `user`, `verification`, `video` y `withdrawal`. `rate-limit` solo contiene su esquema, `order` y `subscription` por ahora solo contienen sus esquemas, constantes y tipos, y `license` también es propietario de `revoked_license_order`. El código que no es propietario de una tabla no tiene módulo.

Los esquemas siguen las mismas convenciones:

- Los ID son cadenas UUID v7, salvo en `order` y `subscription`, que copian los registros de Polar con los ID de Polar (consulta [Módulos](/docs/conventions/modules#tables-that-mirror-a-provider)).
- Las fechas son columnas `integer` en modo `timestamp_ms`, con `unixepoch() * 1000` como valor predeterminado. `...timestamps()` añade así `createdAt` y `updatedAt`, y `updatedAt` se vuelve a sellar en cada actualización.
- Los booleanos son columnas `integer` en modo `boolean`.
- Las relaciones, los índices, las restricciones de unicidad y las claves foráneas se declaran en el esquema.

## Escrituras atómicas

D1 no tiene transacciones interactivas. Mantén una operación atómica con una única sentencia, como un upsert con `onConflictDoUpdate`, o agrupa sentencias con `db.batch`. Los casos de uso de listas paginadas obtienen una página y su total en un único batch (`src/modules/category/use-cases/get-categories.ts`):

```ts
const filter = data.kind && eq(category.kind, data.kind)
const [rows, totals] = await db.batch([
  db
    .select()
    .from(category)
    .where(filter)
    .orderBy(desc(category.createdAt), desc(category.id))
    .limit(data.pageSize)
    .offset(data.pageIndex * data.pageSize),
  db.select({ total: count() }).from(category).where(filter),
])
return { rows, total: totals.reduce((sum, row) => sum + row.total, 0) }
```

El limitador de frecuencia de `src/lib/rate-limit.ts` lee los contadores que rechazan una petición, elimina un número acotado de contadores caducados y cuenta la petición con un upsert atómico por límite, todo en un único batch, de modo que las instancias del Worker comparten los mismos límites y una petición rechazada no escribe nada. `rateLimitBatch` devuelve estas sentencias para que quien lo llame añada su propia consulta al mismo batch; la API de licencias de la CLI añade la consulta de la licencia.

## Migraciones

Las migraciones son archivos SQL en `src/integrations/drizzle-orm/migrations/`, generados con `bun run db:generate` y aplicados con Wrangler. Vitest las ejecuta contra una base de datos SQLite en memoria. Consulta [Base de datos](/docs/tooling/database) para ver los comandos.
