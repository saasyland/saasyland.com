`bun run check` executa `bun run generate:cn`, `bun run check:comments`, `bun run check:i18n`, `bun run check:content`, `bun run check:flows` e `bun run check:skills` e depois `vp check`, que formata com o oxfmt, aplica o lint com o oxlint e faz a checagem de tipos com o TypeScript em uma única passada, com a configuração de `vite.config.ts` e `tsconfig.json`. A CI executa o mesmo comando. Nada aqui é questão de gosto: se as ferramentas aceitarem um código que viola uma regra desta página, a revisão o rejeita.

## O que as ferramentas garantem

O oxlint executa as categorias `correctness`, `nursery`, `pedantic`, `perf`, `style` e `suspicious` como erros, com as regras com reconhecimento de tipos e a checagem de tipos ativadas. Os limites que mais moldam o código:

| Regra                                   | Configuração                                                               | Efeito                                                                          |
| --------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `max-lines`                             | <RepositoryFact name="maxLines" />                                         | Divida um arquivo por responsabilidade antes que ele cresça                     |
| `max-lines-per-function`                | <RepositoryFact name="maxLinesPerFunction" />                              | Componentes e handlers continuam pequenos                                       |
| `max-statements`                        | <RepositoryFact name="maxStatements" />                                    | Extraia helpers nomeados em vez de escrever corpos longos                       |
| `no-magic-numbers`                      | apenas `0` e `1` são permitidos, além de índices de array e valores padrão | Todo outro número é uma constante nomeada                                       |
| `id-length`                             | pelo menos dois caracteres, exceto `_`, `m` e `t`                          | Identificadores são palavras; `t` é o tradutor                                  |
| `one-var`                               | `never`                                                                    | Uma declaração por instrução                                                    |
| `unicorn/no-null`                       | ativada fora dos testes e de `src/platform/testing`                        | Valores ausentes são `undefined`                                                |
| `typescript/no-explicit-any`            | `error`                                                                    | Nenhum valor é tipado como `any`                                                |
| `typescript/ban-ts-comment`             | `true` para `@ts-expect-error`, `@ts-ignore` e `@ts-nocheck`               | Nenhum erro do compilador é suprimido, com ou sem um motivo                     |
| `typescript/consistent-type-assertions` | `assertionStyle: "never"`                                                  | Nenhum cast com `as`; `as const` e `satisfies` continuam permitidos             |
| `code-style/no-comments`                | `error`                                                                    | Nenhum comentário além de um link de uma linha, e nunca uma diretiva            |
| `code-style/no-multiline-ternary`       | `error`                                                                    | Um ternário cabe em uma linha                                                   |
| `code-style/no-undefined-branch`        | `error`                                                                    | Nada de ternário com um ramo `undefined` ou `null` nem de `return undefined`    |
| `code-style/no-undefined-fallback`      | `error`                                                                    | Nada de `?? undefined`                                                          |
| `code-style/route-option-order`         | `error` em `src/routes`                                                    | As opções de rota pelas quais os tipos passam seguem a ordem do TanStack Router |
| `code-style/zod-namespace-import`       | `error`                                                                    | Zod é importado como `* as zod` de `zod`                                        |
| `radius/no-off-scale`                   | `error`                                                                    | Cada canto usa um raio da escala                                                |
| `type/no-off-scale`                     | `error`                                                                    | Cada tamanho de texto é um degrau da escala tipográfica                         |
| `type/mono-for-code`                    | `error`                                                                    | A fonte monoespaçada é só para código                                           |

Os overrides são restritos e valem por arquivo: os testes e os helpers de teste compartilhados em `src/platform/testing` relaxam `no-magic-numbers`, `no-await-in-loop`, `unicorn/no-null`, `hydration/no-clock-or-locale-in-render` e `admin-data/no-literal-data`; `src/presentation` e `src/hooks` relaxam `typescript/consistent-return`; os mocks de teste relaxam `require-await`; `src/routes` desativa `sort-keys`, porque as opções de rota seguem uma ordem própria (veja [Arquivos de rota](/docs/conventions/routes)); e as rotas, os componentes e os arquivos de dados do admin ativam `admin-data/no-literal-data` (veja [Painel administrativo](/docs/features/admin-dashboard#real-data-only)). Todo o `src` ativa `radius/no-off-scale`, `type/no-off-scale` e `type/mono-for-code`, que os testes e `src/platform/testing` desativam de novo, e `src/presentation/social-card.tsx` desativa `type/no-off-scale`, porque o Takumi renderiza o card social como uma imagem de tamanho fixo, com os tamanhos de texto definidos em estilos inline e não na escala tipográfica da página (veja [Tema](/docs/ui/theme#type-scale)).

`tsconfig.json` adiciona as flags estritas que mudam a forma de escrever código: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` e `noUnusedParameters`. Uma leitura indexada pode ser `undefined`, uma propriedade opcional não pode receber `undefined` explicitamente, e uma assinatura de índice é lida como `record["key"]`.

O formatador imprime sem ponto e vírgula, com aspas duplas, vírgulas finais e largura de <RepositoryFact name="printWidth" />. Ele também ordena os imports em grupos fixos, as classes do Tailwind em `className` e nas chamadas a `cn`, e os scripts do `package.json` pelo nome (`sortPackageJson: { sortScripts: true }`), então nunca ordene nenhum deles à mão: `vp check` falha quando um deles está fora de ordem. Veja [Lint e formatação](/docs/tooling/lint-format) para os comandos.

## Renderizar o que o servidor renderizou

Uma página renderiza duas vezes: no servidor e de novo no navegador, quando o React hidrata o HTML. As duas renderizações precisam imprimir o mesmo texto; senão, o React relata um erro de hidratação (erro #418) e renderiza a página de novo. Por isso o código de renderização nunca lê o relógio nem o locale do ambiente de execução, que diferem entre os dois: nada de `new Date()` sem argumento, de `Date.now` nem de `toLocaleString`, `toLocaleDateString` ou `toLocaleTimeString`. Use um valor que os dois lados compartilham:

- um tempo relativo conta a partir do `dataUpdatedAt` da query que leu os dados, como mostra [Internacionalização e idiomas](/docs/features/internationalization);
- um ano que o site imprime vem da build: o rodapé termina o copyright em `REPOSITORY_FACTS.buildYear`, o ano UTC em que o site foi construído;
- números e datas passam por `useFormatter` do use-intl, no idioma da página e no fuso horário do usuário;
- uma espera no navegador, como o tempo limite de ativação de `CheckoutActivation`, é um timer iniciado em `useEffect`, então a primeira renderização é a do servidor.

`hydration/no-clock-or-locale-in-render`, a regra do plugin próprio de oxlint do repositório em `scripts/hydration-lint-plugin.ts`, aplica isso em `src/hooks`, `src/presentation`, `src/providers` e `src/routes/*.tsx`. Ali tudo conta como código de renderização, exceto uma função que roda depois: um handler de evento `on…`, como prop de JSX, propriedade de objeto ou variável; uma `queryFn` ou `mutationFn`; e um callback passado a `useEffect`, `useLayoutEffect`, `useCallback`, `setTimeout`, `setInterval`, `requestAnimationFrame` ou `addEventListener`. Essas listas no plugin são a lista de permissões: outro tipo de callback adiado entra ali, com um caso em `src/__test__/hydration-lint-plugin.test.ts`, nunca com um comentário de desativação.

## Comentários [#comments]

Por padrão, não escreva comentários: nem em TypeScript, TSX, testes, scripts, configuração, CSS ou workflows. Um nome carrega o significado, e o raciocínio vai para a mensagem de commit, o pull request ou esta documentação.

```ts
const INCLUSIVE_END = 1
const FIRST_SEQUENCE = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

As duas primeiras vêm de `video.delivery.ts` e `release.ts`, a terceira de `src/integrations/polar/polar.vite.ts`: sem esses nomes, cada uma precisaria de um comentário.

Um comentário só se justifica quando quem lê o código precisa mesmo saber onde está o motivo, e mesmo assim ele aponta para lá em vez de explicar. As verificações aceitam duas formas e nada mais:

- Um comentário de link: uma linha cujo conteúdo é um link para onde está o motivo, depois de no máximo <RepositoryFact name="linkCommentWords" /> palavras. O link é uma URL `https://`, como uma página de documentação, o README ou o roadmap no GitHub ou uma issue ou um pull request upstream, ou um caminho da documentação deste site que começa com `/docs/`: `// https://github.com/TanStack/router/issues/8933` ou `// See /docs/conventions/code-style#comments`. Um comentário de bloco ou de JSX segue a mesma forma de uma linha, e nenhum outro comentário pode ficar na linha de cima ou na de baixo.
- Uma tag de versão em um workflow: uma linha `uses:` de YAML que fixa uma action em um SHA de commit de 40 caracteres termina com a tag com que esse commit foi lançado, `# v4` ou `# v7.0.0`. Um arquivo YAML não aceita nenhum outro comentário.

Todo o resto falha: uma explicação, um banner, um `TODO`, código comentado, uma segunda linha, texto depois do link e um comentário de diretiva, mesmo que termine com um link.

Duas verificações garantem a regra, e as duas indicam o arquivo, a linha e a correção:

- `code-style/no-comments`, uma regra do plugin de oxlint do repositório em `scripts/code-style-lint-plugin.ts`, relata todo comentário que não seja um comentário de link nos arquivos que o linter lê, no editor e em `vp check`.
- `bun run check:comments` executa `scripts/check-comments.ts` antes do linter, em `bun run check` e no hook de pre-commit. Ele analisa todo arquivo TypeScript, JavaScript, CSS e YAML que o Git rastreia ou adicionaria, com o oxc para o código, o PostCSS para os estilos e o pacote `yaml` para o YAML, então um `//` em uma URL ou em uma expressão regular, um `/*` em um glob de CSS e um `#` em uma string de YAML não são comentários. Ele lê o que o linter não consegue ler: `e2e`, `remotion`, os arquivos de declaração, as folhas de estilo, os workflows e um comentário `/* oxlint-disable */`, que o linter obedece antes que qualquer regra o veja.

As isenções são os arquivos que `.gitattributes` marca como `linguist-generated`, dos quais `src/routeTree.gen.ts` e `src/types/worker-configuration.d.ts` são código, e a linha `#!` de um script, que a gramática do JavaScript não conta como comentário. Um tipo de que o compilador precisa em todo lugar vai para `types` em `tsconfig.json`, como os globais do Vitest, nunca para um comentário `/// <reference>`.

## Nada de válvulas de escape

Nunca escreva `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, um cast com `as` ou `any` para fazer uma regra passar. Uma regra que dispara está apontando para um problema de design; mude o design. As verificações rejeitam cada uma delas: `typescript/ban-ts-comment` rejeita as três diretivas do compilador mesmo com uma descrição, `typescript/consistent-type-assertions` toda asserção, exceto `as const`, `typescript/no-explicit-any` o `any`, e `code-style/no-comments` e `bun run check:comments` todo comentário de desativação. Para começo de conversa, um comentário `eslint-disable` não desativa nada (`respectEslintDisableDirectives: false`).

- **Valide em vez de fazer asserções.** Dados vindos do armazenamento, da rede ou de uma requisição são analisados com o Zod: `src/lib/github.ts` lê a contagem de estrelas em cache com `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, que é um número ou `undefined`, nunca um palpite.
- **Restrinja com um type guard.** `isRole` em `src/integrations/better-auth/auth.roles.ts` e `isSupportedLocale` em `src/integrations/use-intl/i18n.paths.ts` transformam uma `string` em uma união com uma verificação real.
- **Anote, não faça asserções.** Dê a um valor o tipo de que ele precisa onde ele é declarado: a sidebar do shadcn declara `SIDEBAR_MOBILE_STYLE: StyleWithCssVars`, as propriedades CSS mais a sua propriedade customizada `--sidebar-width`, em vez de fazer um cast do objeto literal.
- **Verifique, não converta.** `as const` e `satisfies` são permitidos porque nunca mudam um tipo: `POLAR_ORDER_STATUS` termina em `as const satisfies Record<string, models.OrderStatus>`, então um status da Polar escrito errado não compila.
- **Reestruture quando o contrato de uma biblioteca resistir.** Envolva um valor em um objeto, divida uma função ou leia de uma fonte tipada em vez de fazer um cast.

## Null e undefined

Fora dos testes e de `src/platform/testing`, um valor ausente é `undefined`, e `null` nunca é escrito como valor. O linter o permite onde uma API o define: na comparação com um valor que pode ser `null`, como uma coluna anulável (`entry.completedAt !== null` em `course.outline.ts`), e em uma ref de DOM do React, que começa como `useRef<HTMLElement>(null)` porque o React tipa `ref` como `RefObject<T | null>` e a volta para `null` ao desmontar (`course-showcase.tsx`). Nunca faça a ponte de uma API que retorna `null` com `?? undefined`; `code-style/no-undefined-fallback` faz isso falhar. Valide a entrada primeiro, para que a chamada não possa falhar, ou use um parser que já retorna `undefined`. Os search params são o caso mais comum, e `searchParam(schema)` em `src/lib/search-params.ts` retorna `undefined` para um valor ausente ou malformado:

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Ternários e retornos antecipados

Um ternário cabe em uma linha, como `{t(course === undefined ? "create" : "save")}` em `course-form.tsx`. Qualquer coisa mais longa, e toda escolha entre dois trechos de JSX, vira um retorno antecipado, um par de condições `&&` ou um componente pequeno; uma classe condicional vira `cn("base", { "classes": condition })`. `code-style/no-multiline-ternary` faz falhar todo ternário que ocupa mais de uma linha, inclusive um que o formatador quebrou porque passou da largura de linha. `src/routes/auth.reset-password.tsx` renderiza seus dois estados com duas condições:

```tsx
{hasValidToken && <ResetPasswordForm token={token} />}
{!hasValidToken && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

As funções retornam cedo nos casos especiais e mantêm o caminho principal sem indentação extra, como faz `hasLessonAccess` em `src/modules/lesson/lesson.access.ts`:

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.entitled
}
```

Nenhum ramo escreve por extenso o valor ausente: `code-style/no-undefined-branch` faz falhar um ternário com um ramo `undefined` ou `null` e todo `return undefined`. Escreva no lugar o que o código faz: retorne cedo de uma cláusula de guarda, leia um valor que pode faltar com `?.` ou com `??` e um valor padrão de verdade, retorne o que uma tabela de consulta ou `find` encontra, renderize o JSX com `&&` e dê ao hook de um plugin do Vite um filtro que nomeie os ids que ele trata, para que o Rolldown não o chame para nenhum outro id. É assim que `scripts/repository-facts.ts` serve os seus módulos virtuais:

```ts title="scripts/repository-facts.ts"
    load: { filter: { id: RESOLVED_MODULE_IDS }, handler: (id) => sources.get(id) },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: MODULE_IDS }, handler: (id) => `${RESOLVED}${id}` },
```

## Constantes nomeadas

Números diferentes de `0` e `1` têm nome (`COURSE_STALE_MS = 60_000`, `LESSON_PROGRESS_SAVE_INTERVAL_MS = 15_000`). `0` e `1` são escritos como literais, como em `.limit(1)`, `index + 1` e `toHaveBeenCalledTimes(1)`, a menos que tenham um significado próprio: o código de saída de um processo é `FAILURE_EXIT_CODE`, e o fim inclusivo de um intervalo de bytes HTTP é `INCLUSIVE_END`. Valores que pertencem ao domínio, como status, tipos, níveis de acesso, planos, papéis e valores de eventos de provedores, são declarados uma única vez como um objeto `as const` e referenciados pelo nome em todo lugar, inclusive nos testes e nas fixtures:

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

A tupla de que uma coluna ou um schema de enum precisa é montada a partir do objeto, não digitada de novo, e fica ao lado dele nas constantes do módulo, que não importam nada do Drizzle: `course.constants.ts` declara `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, que alimenta tanto `text("status", { enum: COURSE_STATUSES })` em `course.schema.ts` quanto `zod.enum(COURSE_STATUSES)` em `course.zod.ts`. O código do navegador também lê as tuplas de lá: a tabela de preços percorre `LICENSE_TIERS` de `license.constants.ts`.

- As constantes de um módulo ficam no seu `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`); os valores de um provedor ficam no `*.constants.ts` da integração (`POLAR_ORDER_STATUS` em `polar.constants.ts`, `AUTH_PROVIDER` em `auth.constants.ts`).
- Os comprimentos de colunas e de entradas são nomeados uma única vez, nas constantes do módulo, e lidos tanto pelo schema do Drizzle quanto pelo schema do Zod: `VIDEO_TITLE_MAX_LENGTH` em `video.constants.ts`.
- Um conceito tem um único mapa, em uma única convenção de caixa: `ERROR_CODES` para erros do servidor, `AUTH_ERRORS` para chaves de erro do Better Auth, `ROLE_CODES` para papéis.
- Nomes de ambiente e códigos de status HTTP são declarados uma única vez, em `src/modules/_core/constants/api.ts`: `ENVIRONMENT.PRODUCTION` em `__root.tsx` e nos scripts de deploy, `HTTP_STATUS.PARTIAL_CONTENT` no handler de mídia do Worker. Nenhum arquivo declara um mapa próprio de nenhum dos dois. A única exceção é `vite.config.ts`, que compara `mode` com o nome puro: o Vite o carrega antes de resolver o alias `~`, então ele não pode importar `api.ts`.
- Uma constante usada por um único arquivo fica nesse arquivo, abaixo dos imports. Uma constante usada por vários arquivos vai para o seu módulo, para `src/data` (veja [Arquivos e nomenclatura](/docs/conventions/files-and-naming)) ou para `src/modules/_core/constants`. Nunca dê a uma constante um arquivo só para ela.
- Nomes de campos de APIs tipadas, como `license_key_id`, são propriedades, não valores, e continuam como acesso a propriedade.

## Hooks em componentes

As chamadas de hooks que retornam um único valor vêm primeiro, depois uma linha em branco e, em seguida, cada resultado de hook desestruturado, para que os valores que um componente desmembra sejam lidos como um grupo próprio. `src/presentation/components/custom/auth/sign-in-form.tsx`:

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Um componente chama `useTranslations` uma vez e dá ao resultado o nome `t`; veja [Traduções e conteúdo](/docs/conventions/translations) para entender o porquê.

## Nomes e imports

- Arquivos e pastas usam kebab-case; componentes usam PascalCase; constantes usam SCREAMING_SNAKE_CASE; funções começam com um verbo (`resolveViewer`, `rethrowAsConflict`); booleanos se leem como perguntas (`isPending`, `hasLessonAccess`).
- Os imports usam o alias `~/src/...` e vêm do arquivo que define o símbolo, inclusive os caminhos: `import { ROUTES } from "~/src/routes"`. Não há barrel files: nenhum arquivo reexporta uma pasta nem junta as listas de vários arquivos, e `src/routes.ts` declara os caminhos ele mesmo. Fora as primitivas do shadcn em `src/presentation/components/shadcn/`, algumas das quais reexportam as partes que envolvem, só estes arquivos reexportam: `src/integrations/drizzle-orm/drizzle.schemas.ts`, porque o Drizzle precisa de todas as tabelas em um único objeto de schema; `src/modules/license/license.utils.ts`, que reexporta `orderCurrencySchema` e `polarOrderUrl` para o código de licenças; e `src/integrations/motion/motion.features.ts`, que reexporta `domMax` como o pacote de recursos que o `LazyMotion` carrega.
- Zod é importado de um só jeito, `import * as zod from "zod"` (ou `import type * as zod from "zod"` só para tipos), a forma que a documentação do Zod 4 mostra; `code-style/zod-namespace-import` faz falhar uma importação padrão, uma importação nomeada e um subcaminho como `zod/v4`.
- Avançar um índice em um usa o literal: `lessons[index + 1]` em `course.utils.ts`. Qualquer outro deslocamento, inclusive `-1`, ganha um nome: `groups.at(LAST_GROUP_INDEX)` em `robots.ts`, nunca `slice(index, -5)`.
