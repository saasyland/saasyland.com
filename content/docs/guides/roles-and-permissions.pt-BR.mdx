title: "Papéis e permissões"
description: "Defina no arquivo de acesso de uma área as declarações de permissão dela e os papéis aos quais as concede, e verifique-as nos guards de rota e nas funções de servidor."
---

O controle de acesso usa o plugin admin do Better Auth. Cada área define em `src/data/<area>.access.ts` as declarações de permissão dos seus recursos e os papéis aos quais as concede. `src/data/access.entries.ts` reúne as áreas, e `src/integrations/better-auth/auth.access.ts` monta a partir delas o controle de acesso do Better Auth, os papéis e a verificação de permissão, de modo que a integração de autenticação não cita nenhuma área. Os códigos de papel ficam em `src/integrations/better-auth/auth.roles.ts`.

## Declarações e papéis

```ts title="src/data/auth.access.ts"
const STATEMENTS = {
  admin: ["access"],
  settings: ["manage"],
} as const

export const AUTH_ACCESS = {
  grants: { [ROLE_CODES.ADMIN]: STATEMENTS },
  statements: STATEMENTS,
} as const satisfies AreaAccess
```

```ts title="src/integrations/better-auth/auth.access.ts"
export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...grantsOf(ROLE_CODES.ADMIN), ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole(grantsOf(ROLE_CODES.CUSTOMER)),
}
```

- `APP_STATEMENTS` em `src/data/access.ts` reúne as declarações de todas as áreas, ordenadas por recurso, e falha na inicialização quando duas áreas declaram o mesmo recurso. `grantsOf(role)` reúne o que cada área concede a esse papel.
- A área de autenticação declara `admin` e `settings`, a área de produtos `category` e `product`, a área de cursos `course` e `video`, e a área de pagamentos `order`.
- Os `defaultStatements` do Better Auth adicionam os recursos `user` e `session` (como `user: ["list", "set-role", "ban", "impersonate", "delete"]` e `session: ["list", "revoke"]`).
- Todas as áreas concedem todas as suas declarações a `admin`, que também recebe as declarações de administração do Better Auth; `customer`, o papel padrão de novos usuários, não recebe nenhuma.
- `ROLE_VALUES` tipa a coluna `user.role` e os schemas de papel em `user.zod.ts`.
- `Permission`, o tipo que `authorized` e `hasPermission` recebem, é montado a partir das declarações que as áreas fazem, então uma declaração ou ação que nenhuma área declara não compila.

## Onde as permissões são verificadas

| Camada                  | Verificação                                                        |
| ----------------------- | ------------------------------------------------------------------ |
| Guard de rota           | `requireAdmin` exige `admin: ["access"]` para toda a área `/admin` |
| Função de servidor      | `authorized({ product: ["update"] })` em toda operação protegida   |
| Apenas logado           | `authorized()` para operações sobre os dados de quem chama         |
| Em qualquer outro lugar | `hasPermission({ permission, role })` retorna um booleano          |

O guard de rota só decide quais páginas são renderizadas. As funções de servidor podem ser chamadas diretamente por RPC, então cada uma precisa verificar sua própria permissão. Esconder um botão é apresentação, não autorização.

## Adicione uma permissão

1. Adicione a ação às declarações da área dona do recurso, por exemplo `report: ["read", "export"]` em `src/data/analytics.access.ts`. Uma área nova adiciona o seu arquivo e uma linha a `src/data/access.entries.ts`.
2. Conceda-a nos `grants` do mesmo arquivo: as áreas concedem todo o seu `STATEMENTS` a `ROLE_CODES.ADMIN`, e um papel que deve receber menos ganha um subconjunto.
3. Exija-a na função de servidor: `.middleware([authorized({ report: ["export"] })])`.
4. Teste tanto o caso permitido quanto o caso `FORBIDDEN`, no `src/data/__test__/<area>.access.test.ts` da área e nos testes do caso de uso.

## Adicione um papel

1. Adicione o código a `ROLE_CODES` e `ROLE_VALUES` em `auth.roles.ts`.
2. Adicione-o a `ROLES` em `auth.access.ts` e conceda-lhe declarações nos `grants` das áreas que ele pode usar.
3. Adicione o rótulo do papel a `filters.role.options` em `messages/<locale>/pages.admin.users.json` em todos os idiomas.

O cliente de autenticação (`auth.client.ts`) recebe `ac` e `ROLES`, então as ações de administração no navegador usam as mesmas definições.

## Administração de usuários e sessões

Os módulos de usuários e de sessões envolvem a API de administração do Better Auth em casos de uso, cada um com sua própria permissão: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` e outros. Operações sobre os dados de quem chama, como `revokeSession`, usam `authorized()` e filtram por `context.auth.user.id`.

Localmente, `bun run db:seed:local` cria um administrador. No preview e na produção, o primeiro administrador é criado por `bun run admin:grant:preview <email>` ou `bun run admin:grant:production <email>`, que só quem tem acesso de escrita a esse banco de dados D1 pode executar, para uma conta que já verificou o e-mail; os administradores seguintes são criados em **Administração → Gerenciamento de usuários** com **Alterar função**. Veja [O primeiro administrador](/docs/tooling/database#the-first-admin).
