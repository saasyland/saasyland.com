Workflowy znajdują się w `.github/workflows/`. Workflowy aplikacji (`ci.yml`, `e2e-reusable.yml` i `deploy-reusable.yml`) konfigurują zestaw narzędzi za pomocą akcji złożonej `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ z wersją Node z `.nvmrc`, cache Buna, `bun install --frozen-lockfile --ignore-scripts` i `bun run typegen`. `remotion.yml` konfiguruje zamiast tego Node z `.nvmrc` i npm.

| Workflow              | Wyzwalacz                                                                             | Zadania                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requesty i pushe do `main`                                                       | Kontrole i pokrycie, E2E w Chromium, następnie wdrożenie preview albo produkcyjne z wydaniem |
| `e2e-full.yml`        | Pushe do `main`, harmonogram <RepositoryFact name="e2eFullSchedule" /> w UTC, ręcznie | WebKit przy pushu; Chromium i WebKit przy uruchomieniach z harmonogramu i ręcznych           |
| `e2e-reusable.yml`    | Wywoływany przez powyższe workflowy                                                   | Testowa baza danych, testowy build i jeden projekt Playwright                                |
| `deploy-reusable.yml` | Wywoływany przez `ci.yml`                                                             | Build, migracje D1 i `wrangler deploy`                                                       |
| `remotion.yml`        | Zmiany w `remotion/` lub w plikach witryny, które importuje                           | Sprawdza i pakuje projekt wideo strony głównej za pomocą npm                                 |

`remotion.yml` uruchamia się przy pull requestach i pushach dla tych samych ścieżek: `remotion/`, samego workflowu oraz plików witryny, które importuje `remotion/src`, bezpośrednio lub przez inne pliki witryny. `src/__test__/workflows.test.ts` śledzi te importy i kończy się błędem, gdy osiągnięty przez nie plik nie pasuje do żadnej ze ścieżek albo ścieżka nie pasuje do żadnego z plików.

Checkouty, które budują witrynę, w `e2e-reusable.yml` i `deploy-reusable.yml`, oraz checkout zadania `release` pobierają wszystkie commity bez ich drzew (`fetch-depth: 0` i `filter: tree:0`): [historia zmian](/docs/project/changelog) datuje każdy wpis commitem, który wprowadził go do `main`. W porównaniu z płytkim klonem dochodzą tylko same commity; przy płytkim klonie build kończy się błędem, zamiast błędnie datować wpisy. `src/__test__/workflows.test.ts` kończy się błędem, gdy któryś z tych checkoutów przestaje pobierać historię.

## Kontrole

Zadanie `verify` w `ci.yml` uruchamia `bun run check` (tablice nazw klas, kontrole i18n i treści, [spis przepływów](/docs/tooling/test-coverage#flow-coverage), formatowanie, lint i typy) oraz `bun run test:coverage`, a następnie przesyła raport pokrycia. Zadanie `e2e` uruchamia `db:reset:test` i `build:test`, instaluje przeglądarkę i uruchamia `bunx playwright test e2e/specs --project=chromium`. Nieudane przebiegi E2E przesyłają raport Playwright.

W pull requeście `bun run check` kończy się też błędem, dopóki pull request nie doda swojego [wpisu w historii zmian](/docs/conventions/git-workflow#changelog-entries). Build w jobie `e2e` i w jobach wdrożenia kończy się błędem, dopóki historia zmian pokazywałaby w sekcji **Niewydane** wpis inny niż wpis samego pull requesta, a na `main`, dopóki pokazywałaby jakikolwiek.

## Wdrożenia

Wdrożenia uruchamiają się dopiero po pomyślnym zakończeniu `verify` i `e2e`:

| Zdarzenie                                | Cel          | Środowisko GitHub | URL                           |
| ---------------------------------------- | ------------ | ----------------- | ----------------------------- |
| Pull request z gałęzi w tym repozytorium | `preview`    | `Preview`         | https://preview.saasyland.com |
| Push do `main`                           | `production` | `Production`      | https://saasyland.com         |

`deploy-reusable.yml` nadaje każdemu środowisku GitHub jego URL, a `src/__test__/workflows.test.ts` kończy się błędem, gdy któryś z nich różni się od hosta środowiska w `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Pull requesty z forków i od Dependabota są walidowane, ale nie są wdrażane. Środowisko preview jest współdzielone: każde wdrożenie zastępuje poprzednie i używa tej samej bazy D1, przestrzeni nazw KV i bucketów R2 środowiska preview.

`deploy-reusable.yml` sprawdza obecność sekretów `CLOUDFLARE_API_TOKEN` i `CLOUDFLARE_ACCOUNT_ID`, uruchamia `scripts/verify-bindings.ts`, buduje aplikację z fikcyjnymi wartościami z `.env.test`, usuwa wygenerowany `dist/server/.dev.vars`, stosuje `db:migrate:<target>` i uruchamia `vp exec wrangler deploy --config dist/server/wrangler.json`. Nie uruchamia `scripts/verify-deployment.ts`, czyli sprawdzenia działającej witryny ze skryptów `deploy:<target>`, ponieważ ochrona Cloudflare przed botami odpowiada kodem 403 na żądania z runnerów CI. Nie uruchamia też `scripts/run-deploy-checks.ts`, więc CI nie wykonuje żadnego ze sprawdzeń przed wdrożeniem, które obszary deklarują w `DEPLOY_CHECKS`: w CI nie ma pliku `.env.<target>`, a środowiska GitHub przechowują tylko dane uwierzytelniające Cloudflare. Obecnie są to `auth:verify` z obszaru uwierzytelniania i `polar:verify` z obszaru Polar; uruchamiaj lokalnie `bun run auth:verify:<target>` po zmianie klienta OAuth i `bun run polar:verify:<target>` po każdej zmianie w Polar ([Konfiguracja Polar](/docs/getting-started/polar-setup)). Żaden plik sekretów nie jest przesyłany: Worker zachowuje sekrety środowiska uruchomieniowego ustawione już w Cloudflare. Wdrożenia do tego samego celu czekają w kolejce, zamiast wzajemnie się anulować.

Dependabot co tydzień aktualizuje akcje GitHub Actions.

## Wydania i tagi [#releases-and-tags]

Witryna jest wdrażana w sposób ciągły, więc jej wersjami są daty, a nie wersje semantyczne. Gdy wdrożenie produkcyjne zakończy się sukcesem, zadanie `release` w `ci.yml` oznacza wdrożony commit tagiem `vYYYY.MM.DD` z datą UTC i publikuje dla niego GitHub Release. Drugie wdrożenie produkcyjne tego samego dnia dostaje tag `vYYYY.MM.DD.2`, kolejne `.3` i tak dalej. Wdrożenia preview nigdy nie dostają tagu. Zadanie `release` jako jedyne ma `contents: write`.

Notatki do wydania to wpisy z [historii zmian](/docs/project/changelog), które dostarczyło wydanie, czyli te, które trafiły do `main` od poprzedniego tagu wydania, każdy zakończony `(#<number>)`, co GitHub zamienia w link do jego pull requesta, więc każda zmiana jest opisana w jednym miejscu; gdy wydanie nie dostarczyło żadnego, jego notatki zawierają link do historii zmian. `scripts/publish-release.ts` bierze notatki z `src/lib/release.ts` i uruchamia `gh release create` z tagiem wybranym przez wdrożenie. Ponowne uruchomienie zachowuje tag, który commit już ma, i pomija wydanie, które już istnieje.

Job wdrożenia produkcyjnego wybiera ten tag przed buildem: `scripts/choose-release-tag.ts` stosuje `releaseTag` z `src/lib/release.ts` do tagów checkoutu, build dostaje tag jako `RELEASE_TAG`, a job przekazuje go jobowi `release` jako swoje wyjście `release-tag`, więc wdrożenie i jego wydanie mają jeden tag. Dzięki temu [historia zmian](/docs/project/changelog) linkuje każdy wpis do wydania, które dostarczyło go jako pierwsze: do najstarszego tagu wydania, którego commit zawiera commit squash wpisu w historii pierwszych rodziców `main`, odczytywanej przez build razem z datami w jednym `git log`, albo do własnego tagu wdrożenia dla wpisów, które ono wnosi. Job `release` czyta historię zmian tak samo, z tagiem, który publikuje, więc notatki wydania to dokładnie te wpisy, które strona linkuje do tego wydania. Wpisy scalone przed pierwszym tagiem wydania nie linkują do żadnego wydania, podobnie jak w buildach lokalnych, podglądu i pull requestów wpisy, których żadne wdrożenie jeszcze nie dostarczyło. Dwa wdrożenia produkcyjne nie mogą wybrać tego samego tagu: `ci.yml` uruchamia naraz tylko jeden przebieg workflow na ref (`concurrency` z `queue: max`), więc job `release` poprzedniego przebiegu utworzył już swój tag, zanim kolejne wdrożenie zrobi checkout repozytorium.

Aby przywrócić produkcję do wybranego wydania, wycofaj w pull requeście wszystko, co nastąpiło po jego tagu:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Po scaleniu kod z tagu zostaje wdrożony po zwykłych kontrolach i oznaczony jako nowe wydanie. Migracje D1 nie są wycofywane, więc starszy kod działa na nowszym schemacie. Każda zmiana schematu musi działać z aplikacją wdrożoną przed nią, dlatego powrót do poprzedniego wydania jest bezpieczny; zanim cofniesz się dalej, przeczytaj migracje dodane w międzyczasie.
