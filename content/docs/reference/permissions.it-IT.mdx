Ogni area dichiara i propri statement dei permessi e i ruoli a cui li concede in `src/data/<area>.access.ts`, e `src/integrations/better-auth/auth.access.ts` costruisce da essi il controllo degli accessi di Better Auth e i ruoli (vedi [Ruoli e permessi](/docs/guides/roles-and-permissions)). Le stesse definizioni vengono usate dal server (`authorized`, guard delle route) e dal client di Better Auth.

## Ruoli

| Ruolo   | Codice     | Permessi                                                                                                                                              |
| ------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin   | `admin`    | Tutti gli statement dell'applicazione elencati sotto, che ogni area concede agli admin, più gli statement admin di Better Auth per `user` e `session` |
| Cliente | `customer` | Nessuno. I clienti possono chiamare le server function che richiedono solo una sessione.                                                              |

I nuovi utenti ricevono il ruolo `customer` (`DEFAULT_ROLE_CODE` in `auth.roles.ts`).

## Controllare un permesso

Le server function usano il middleware, ad esempio `authorized({ category: ["read"] })`. Il resto del codice chiama `hasPermission`, come fanno le guard delle route:

```ts
const isAdmin = (role: string | null | undefined): boolean => hasPermission({ permission: { admin: ["access"] }, role })

export const requireAdmin = async (context: ProtectedRouteContext) => {
  const result = await requireSignedIn(context)
  if (!isAdmin(result.session.user.role)) {
    throw redirect({ replace: true, to: ROUTES.APP })
  }
  return result
}
```
