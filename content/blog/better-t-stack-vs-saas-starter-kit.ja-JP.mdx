## まずはここから：非常に優れたツールなので、おそらく使うべきです

[Better-T-Stack](https://better-t-stack.dev/) は、エンドツーエンドで型安全な TypeScript プロジェクトをスキャフォールドするための CLI です。MIT ライセンスで、README では「無料かつオープンソース：永久に」と約束しており、**GitHub スターは 5,636**、npm からは週に約 **2,476 回**取得されています。

選択肢のマトリクスはエコシステムで最高であり、他を大きく引き離しています。

| バックエンド               | Hono、Express、Fastify、Elysia、セルフホストのフルスタック、Convex、またはなし                                                              |

| ランタイム                 | Bun、Node.js、Cloudflare Workers                                                                                                            |

| 認証                       | Better Auth または Clerk（オプション）                                                                                                      |

これだけ多くの組み合わせから、実際に型チェックを通って動作するプロジェクトを生成するのは、本当に難しいエンジニアリングです。さらに MCP サーバー付きの Claude Code プラグインとしても提供されているため、エージェントはボイラープレートを手書きする代わりに、有効なスタックを計画して生成できます。よく考えられた仕事です。

**プロトタイプ、社内ツール、ポートフォリオ用のプロジェクト、SaaS 以外のアプリ、あるいは配管部分を学びたいものを作っているなら、ここで読むのをやめて `bun create better-t-stack@latest` を実行してください。** 無料で、優れていて、以下の内容にもそれに反対する主張は何もありません。

ここから先は、ある特定の読者のための内容です。お金を取るつもりの SaaS に、無料の CLI で十分かどうかを判断しようとしている人です。

## スタックはプロダクトではない

Better-T-Stack の README は、その哲学を 4 行で述べています。そして 2 行目が、この比較のすべてです。

> 自分だけのスタックを組む：必要な部分だけを選び、余計なものは何もない。
> **最小限のテンプレート：肥大化ゼロの、必要最小限のスキャフォールド。**
> 最新の依存関係：デフォルトで常に最新の安定版を使う。
> 無料かつオープンソース：永久に。

これは隠された制約ではありません。はっきりと表明された設計であり、プロジェクトは約束したことを正確に実現しています。その証拠は上の表の最後の行にあります。同梱のサンプルは **Todo** と **AI** です。ToDo リストとチャットです。これらは配線が機能していることを示す定番のデモであり、配線を仕事とするツールにとって正しいサンプルです。

したがって、正直な捉え方は「無料ツールには機能が足りない」ではありません。こうです。

**Better-T-Stack はスタックをスキャフォールドします。SaaS スターターキットはプロダクトをスキャフォールドします。**

どちらもスキャフォールダーです。止まる地点が違うだけです。Better-T-Stack は、9 種類のフロントエンドと 6 種類のバックエンドから選んだ構成で、フロントエンドがバックエンドを呼び出せ、バックエンドがデータベースに型安全に到達できた時点で止まります。それは十分に正当な止まりどころであり、ほとんどのスキャフォールダーはそこで止まるべきです。

SaaS スターターキットは別の地点で止まります。ユーザーがサインアップし、組織に参加し、ロールを割り当てられ、毎月課金され、そのことについてメールを受け取り、困って問い合わせてきたときには、あなたが管理画面でその人の状況を確認できる時点です。その 2 本の線の間にあるものすべてが、請求書です。

## 項目別の請求書

| 項目                           | Better-T-Stack | 「完成」が実際に意味すること                                                                                 | 時間         |
| ------------------------------ | :------------: | ------------------------------------------------------------------------------------------------------------ | ------------ |
| 型安全なスタックの配線         |      あり      | フロントエンド、API、ランタイム、データベース、ORM が型レベルで一致していること                              | 0            |
| 認証ライブラリの設定           |   オプション   | Better Auth または Clerk のセットアップ：サインイン、サインアウト、セッション                                | 0            |
| 組織と招待                     |      なし      | スキーマ、招待トークン、有効期限、シート数の管理、所有権の移譲、メンバーが抜ける場合の処理                   | 25〜40       |
| ロールと権限                   |      なし      | すべてのクエリとルートが参照するポリシー層と、それを反映する UI                                              | 20〜30       |
| マルチテナントの分離           |      なし      | ビュー層ではなくクエリ層で強制され、2 つ目のテナントに対してテストされていること                             | 15〜25       |

| トランザクションメール         |      なし      | テンプレート、プレビュー、ロケールごとの文面、到達率、配信停止、法令遵守                                     | 15〜25       |

| サンプルのコマースまたはコース |      なし      | 販売するものそのものの、シードデータ付きで動作するリファレンス実装                                           | 30〜60       |

時給 150 ドルなら、**42,000〜69,750 ドル**になります。自分の時給を当てはめれば数字は変わりますが、結論は変わりません。<TierPrice tier="core" /> の買い切り価格と比べれば、時間に価値がある人にとって迷う余地はありません。

とはいえ、時間の話は退屈な論点です。もっと興味深い論点のほうをお話ししたいと思います。

## 時間では測れない部分

この表の 4 つの行に注目してください。**マルチテナントの分離、ロールと権限、Webhook の冪等性、そしてセッションの取り消し**です。

これらには、他のどの行にもない共通の性質があります。**誤った実装でもレビューを通り、開発環境では動作し、デモも正しく動く**のです。

クエリ層ではなくビュー層に適用されたテナントフィルターは、テナントが 1 つのうちは完璧に動作します。テストでも完璧に動作します。フィクスチャにはテナントが 1 つしかないからです。それが破綻するのは、2 社目の顧客のデータが 1 社目の顧客のダッシュボードに表示された日です。それはバグ報告ではなく、電話がかかってくる事態です。

冪等性キーのない Webhook ハンドラーは、テストするたびに毎回動作します。同じイベントを 2 回送ることがないからです。しかし Stripe はリトライ時に同じイベントを送ってきます。そして誰かが 2 回課金されたり、プランが 2 回付与されたりします。

ロールをデータベースから読み直すのではなくセッションから読み取る権限チェックは、誰かが降格されたのに古いセッションを持ち続けるまでは動作します。

これらは難しい問題ではありません。**間違っていても、高くつくまでは目に見えない**問題であり、「これには 40 時間かかる」とはまったく異なるリスクの性質を持っています。時間を多くかけても解決できません。その時間が必要だと気づけないからです。これを避ける方法は、誰かがすでにその間違いを犯して修正し、再発すれば失敗するテストが今は存在している基盤から始めることです。

時間数ではなく、これこそが有料のスターターキットが本当に存在する理由です。

## 有料側の具体的な中身

抽象論ではなく具体的に示すため、このコードベースで「すでに解決済み」が何を意味するかを紹介します。数字はマーケティング用のファイルに手入力したものではなく、テストの実行結果から読み取ったものです。

**カバレッジバッジではなく、カバレッジゲート。** <RepositoryFact name="testFiles" /> 個のテストファイルと、設定ファイル内の 4 つのしきい値です。

```ts
coverage: {
  thresholds: { branches: 100, functions: 100, lines: 100, statements: 100 },
}
```

前のセクションで挙げたエラーブランチこそ、100 に設定したブランチカバレッジゲートがテストを強制するものです。重要なのは数字ではなく、この仕組みです。

**明確な責任範囲と型付きのチェック。** 公開リファレンスアプリは処理を機能ごとにまとめ、Vite+ で lint ルールと型の両方をチェックするよう設定しています。

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

ルートファイルはナビゲーションを調整し、機能のユースケースは `src/modules` に、ベンダーのセットアップは `src/integrations` に、UI は `src/presentation` に置かれます。サーバー専用モジュールは、Worker のバインディングをクライアントに持ち込ませません。これらのフォルダ内での責任範囲はレビューで確認する規約であり、このスニペットによって強制されるインポート制限ではありません。

**逃げ道のない厳格さ。** `strict` に加えて、`exactOptionalPropertyTypes`、`noUncheckedIndexedAccess`、`noPropertyAccessFromIndexSignature`、`noImplicitReturns`。`typescript/no-explicit-any` はエラーであり、lint のカテゴリもエラーとして設定されているため、チェックは失敗の終了コードを返します。

**固定のテンプレートではなく、オプション機能。** [コンフィギュレーター](/#cli) は <RepositoryFact name="cliQuestions" /> 個の質問を行い、<RepositoryFact name="cliExtras" /> 個の追加機能を提供します。サンプル商品付きのストア、サブスクリプション型のコース、ビジュアルページビルダー、ビジュアル投稿エディターです。どれかを有効にすると、モジュールが追加されます。無効のままにすれば、そのコードはリポジトリに存在しません。

ここに書いたことは、どれも Better-T-Stack への批判ではありません。2 つのプロダクトがそれぞれどこで止まるかを説明しているだけです。

## Better-T-Stack が正解になる場合

きちんと述べておきます。常に有料の選択肢を勧める比較は、比較ではなく広告だからです。

**次の場合は Better-T-Stack を使ってください。**

- プロトタイプを作っていて、1 か月後にはそれが存在しないかもしれない。
- 学習中で、配管部分こそが目的である。認証を一度自分で作ることは本当に価値のある学びであり、誰もそれを思いとどまらせるべきではありません。
- プロダクトが SaaS ではない。組織もサブスクリプションも管理画面もない。ツール、ゲーム、社内ダッシュボード、クライアントのサイトなど。
- 退屈な 4 分の 3 のための社内ライブラリをすでに持っている。多くの制作会社や経験豊富なチームがそうです。
- スタックが、どの有料キットの対象範囲にも入っていない。Nuxt、Svelte、Solid、Astro、React Native、Convex、tRPC。Better-T-Stack はそのすべてに対応していますが、有料のスターターキットはそのほとんどに対応していません。
- 予算が本当にゼロである。それは正当な制約であり、何も恥じることはありません。Better-T-Stack は、どの有料プロダクトの無料プランよりも優れた無料の選択肢です。

**次の場合は、お金を払うことを検討してください。**

- 企業から料金を取るつもりのプロダクトを 1 つ作っていて、将来シート、ロール、請求書、セキュリティ質問票が待っている。
- 組織と課金を一度作ったことがあり、退屈な部分にどれだけ時間がかかったかを正確に覚えている。
- 自分で書かずに済むテストゲートがほしい。カバレッジスイートをゼロから書くのは、誰も手を付けられずに終わる項目だからです。
- 型付きのチェックとサーバー専用の境界でビルドを失敗させ、それ以外のアーキテクチャも記憶任せにせず書き残しておきたい。
- 自分の時間に価値があり、その 280〜465 時間は数百ドルより高くつく。

## 実はライバルではない

私が伝えられる最も有益なことは、これが二者択一の競争ではないということです。

Better-T-Stack は、9 種類のフロントエンドと 6 種類のバックエンドにわたる、_あらゆる_ TypeScript プロジェクトのためのスキャフォールダーです。SaaS スターターキットは、_ある 1 種類の_ ビジネスのための基盤です。両者が重なるのは、どちらもプロジェクトを書き出す最初の 10 分間だけです。その後は、それぞれ別の仕事をしています。

避けるべき間違いは「無料のほうを選ぶこと」ではありません。2 つの仕事のどちらが必要なのかを知らないまま、どちらかを選ぶことです。美しく型安全なスタックをスキャフォールドしたあと、6 か月かけて組織と課金を作る創業者は、お金を節約したわけではありません。請求書には現れない通貨で、その代金を支払ったのです。

## よくある質問

<Accordions>

<Accordion title="Better-T-Stack は無料ですか？">

はい。MIT ライセンスで、README では「無料かつオープンソース：永久に」と約束しています。執筆時点で GitHub スターは 5,636、npm の週間ダウンロード数は約 2,476 です。この記事には、これを使うべきではないという主張は一切ありません。読者の多くにとっては、これが正しい選択です。

</Accordion>

<Accordion title="Better-T-Stack は実際に何をスキャフォールドするのですか？">

スタックです。フロントエンドは React、Next.js、Nuxt、Svelte、Solid、Astro、React Native から、バックエンドは Hono、Express、Fastify、Elysia、Convex から選べます。さらに tRPC か oRPC、Bun、Node、Cloudflare Workers のいずれか、SQLite、Postgres、MySQL、MongoDB のいずれか、Drizzle、Prisma、Mongoose のいずれかを選び、オプションで Better Auth か Clerk を追加できます。これらを正しく型安全に結び付けてくれます。これは本物の、そして難しい仕事です。

</Accordion>

<Accordion title="Better-T-Stack に含まれていないものは何ですか？">

課金、トランザクションメール、管理画面、ロールと権限、マルチテナンシー、国際化、コンポーネントライブラリ、テストスイートです。これは見落としではなく、設計によるものです。プロジェクトが掲げる哲学は「最小限のテンプレート：肥大化ゼロの、必要最小限のスキャフォールド」であり、同梱されているサンプルは Todo アプリと AI チャットだけです。

</Accordion>

<Accordion title="無料の CLI があるのに、有料の SaaS ボイラープレートを買う価値はありますか？">

それが省いてくれる作業が、本来なら自分でやるはずの作業である場合に限ります。認証フローを作るのが好きな場合、プロダクトに課金が不要な場合、あるいはそのすべてに対応する社内ライブラリがすでにある場合は、無料の CLI のほうが明らかに優れています。組織、ロール、Webhook、管理画面を 3 度目に作り直すことになるなら、200 時間以上に対して数百ドルという比較は迷うまでもありません。

</Accordion>

<Accordion title="スキャフォールドしたプロジェクトに課金を追加するには、どれくらい時間がかかりますか？">

チェックアウトなら半日で済みます。課金には 25〜40 時間かかります。チェックアウトは簡単な 1 割にすぎず、残りは日割り計算、アップグレード、ダウングレード、督促、請求書履歴、冪等な Webhook 処理、そして受け取れなかった Webhook を拾い上げる照合ジョブだからです。最初の支払いを受け取れることと、確実に課金できることは同じではありません。

</Accordion>

<Accordion title="Better-T-Stack と有料のスターターキットを併用できますか？">

同じプロジェクトで併用しても意味はありません。どちらも基盤を生成するもので、基盤は 1 つしか持てないからです。両者が向いているプロジェクトは異なります。多くの開発者は、プロトタイプや社内ツールには無料のスキャフォールダーを、収益を上げなければならないプロダクトには有料の基盤を使っています。これは矛盾ではなく、理にかなった使い分けです。

</Accordion>

<Accordion title="Better-T-Stack に認証は含まれていますか？">

オプションとして、配線のステップの一つとして含まれています。Better Auth か Clerk をセットアップできます。これでサインインとサインアウトが正しく設定された状態になります。しかし、組織、招待、シート数の管理、ロールによるアクションの制限、二要素認証の強制、サポートのためのなりすまし、セッションの取り消しは得られません。これらはいずれも、ライブラリの上に構築する別の機能です。

</Accordion>

<Accordion title="AI コーディングエージェントにはどちらが向いていますか？">

理由は異なりますが、どちらも良い出発点です。最小限のスキャフォールドは、エージェントに小さなコンテキストを与え、混乱の元になるものがありません。境界が強制された大きめの基盤は、動作するお手本と、エージェントが逸脱したときに失敗するビルドを与えます。最悪なのは、どちらも提供しない選択肢、つまりルールが readme の中にしか存在しない大規模なコードベースです。

</Accordion>

<Accordion title="有料のスターターキットは、実際に何時間を節約してくれますか？">

課金、ロール、管理画面を備えたマルチテナント SaaS なら、この記事で項目別に見積もった範囲は、有能な開発者の作業で 280〜465 時間です。Stripe のチェックアウトが 1 つあるだけのシングルユーザー向けツールなら、20 時間に近くなります。正直な数字は何を作るかに完全に左右されます。だからこそ、表では合計を示すのではなく項目別にしています。

</Accordion>

<Accordion title="自分で作るべきでしょうか？">

学びたいのがまさにその配管部分である場合、スターターキットの前提とぶつかるほどプロダクトが特殊な場合、あるいは自分の時間に本当に機会費用がない場合は、自分で作ってください。すでに一度作ったことがあり、退屈な 4 分の 3 にどれだけ時間がかかったかを正確に覚えているなら、購入してください。

</Accordion>

</Accordions>
