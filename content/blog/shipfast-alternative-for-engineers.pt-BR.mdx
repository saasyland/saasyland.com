## A diferença que não é uma característica

Tabelas de recursos são a forma mais fraca de comparação, porque qualquer um pode adicionar uma linha. Aqui está a diferença que não pode ser adicionada a uma tabela por um concorrente na próxima semana, porque é uma propriedade de como o código é mantido juntos.

**Nesta base de códigos, a arquitetura é executável.** Não está documentado. Executado, pela linter, em cada compromisso.

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

Há três dessas regras. Código de domínio não pode importar React, Em seguida, o ORM, infraestrutura ou código de aplicação. O código de aplicação não pode importar infraestrutura. Código de apresentação não pode importar Drizzle ou entrar na infraestrutura de um módulo, e deve chamar um caso de uso de aplicativos em vez disso.

A consequência vale a pena dizer claramente. **Você não pode acidentalmente colocar um banco de dados em um componente React.** Você não pode: a construção falha com uma mensagem que diz o porquê. Um novo contribuinte aprende a arquitetura no tempo que leva para ler um erro. Assim como um agente codificador, que é cada vez mais a mesma declaração.

Cada kit de iniciação tem um diagrama de arquitetura em sua leitura. Muito poucos têm um que o compilador concorda. Seis meses depois, essa é a diferença entre uma base de código que ainda tem a forma que você projetou e uma que se tornou silenciosamente uma pasta de arquivos.

A documentação pública não tem página para testes. Suas seções são Tutoriais, Recursos, Componentes, Segurança, Implantação e Extras. Isso é consistente com o propósito declarado do produto, que é a velocidade para primeiro implantar em vez de manutenção de longo prazo, mas isso significa que a rede de segurança de regressão é algo que você constrói antes de sua segunda característica.

</Accordion>

<Accordion title={"Sim. ShipFast Apoiar multi-dotação ou organizações?"}>

A documentação não tem página para multi-dotação, organizações, equipes ou controle de acesso baseado em papéis. Para um único operador que é bom. Para qualquer coisa vendida para uma empresa é o maior item do trabalho restante, porque o isolamento de inquilinos tem que ser forçado na camada de consulta em vez de adicionado na camada de UI uma vez que os clientes existem.

</Accordion>

<Accordion title={"Por que usar MongoDB é importante para uma SaaS Caldeira?"}>

Porque os objetos... SaaS Os usuários pertencem a organizações, organizações possuem assinaturas, assinaturas produzem faturas, faturas itens de linha de referência, um modelo de loja de documentos que com o nível de aplicação junta e nenhuma chave estrangeira, então integridade referencial torna-se um código que você tem que escrever e manter correto ao invés de uma propriedade que o banco de dados garante.

</Accordion>

<Accordion title={"É um kit de partida de $249 vale a pena quando ShipFast Custa $199?"}>

Os 50 dólares não são a decisão. Ambos os preços são um erro de arredondamento contra o trabalho. A decisão é qual o conjunto de problemas que você prefere possuir: por US$199 você possui aluguel, papéis, o administrador, a suíte de teste e o modelo de dados reescrever; em US$249 aqueles chegam escritos e cobertos. Preço a diferença em suas próprias horas e a comparação deixa de ser sobre o preço.

</Accordion>

<Accordion title={"Posso migrar um existente? ShipFast Projeto?"}>

Sim, e o caminho honesto não é uma migração. Andar em um novo projeto, portar sua lógica de negócios para os limites do módulo, e mover seus dados com um script único. As partes que valem a pena manter são seu código de domínio e sua cópia. As peças que você está substituindo, a fiação, o encanamento de faturamento e o modelo de dados, são as peças que um kit de arranque deveria lhe dar de qualquer maneira.

</Accordion>

<Accordion title={"Quantos clientes tem? ShipFast Tem?"}>

Sua página inicial diz 8.393 fabricantes na época da escrita, ao lado de um desconto que conta para baixo contra os primeiros 8.400 clientes. Essa é a verdadeira validação da oferta e deve ser levada a sério. Mede quantas pessoas queriam um começo rápido, o que é uma pergunta diferente de quantos desses projetos ainda estavam sendo mantidos um ano depois.

</Accordion>

<Accordion title={"O que a arquitetura imposta pela linter realmente significa?"}>

Que os limites são executáveis ao invés de descritos. Nesta base de códigos, o código de domínio não pode importar React, Next, Drizzle ou infraestrutura; o código de aplicação não pode importar infraestrutura; código de apresentação não pode importar o ORM. São regras de fiapo que falham na construção, então uma violação arquitetônica é um cheque vermelho em vez de um parágrafo em um readme que ninguém lê.

</Accordion>

<Accordion title={"Devo comprar uma caldeira ou começar do próximo aplicativo?"}>

Comece do zero quando o encanamento é o que você quer aprender, ou quando seu produto é estranho o suficiente para que as suposições de um iniciante lutem contra você. Compre quando o trabalho entre uma pasta vazia e sua primeira linha genuinamente nova é trabalho que você já fez antes e prefere não fazer de novo. Quase ninguém foi pago por sua implementação.

</Accordion>
