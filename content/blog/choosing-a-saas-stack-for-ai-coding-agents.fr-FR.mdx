C'était vrai. En 2026, c'est en partie inversé, et la preuve est un fichier que Next.js écrit tout seul dans votre projet.

# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all
differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/`
before writing any code. Heed deprecation notices.

Le framework React le plus populaire au monde avertit désormais les agents de codage que ce dont ils se souviennent à son sujet est faux. Ce n'est pas une critique de Next.js. ## Que fait réellement une pile pour un agent de codage IA ?

Une pile ne rend pas un agent correct. Elle change **le nombre de programmes erronés qu'il est possible d'exprimer**. Chaque choix de bibliothèque réduit ou élargit l'espace du code qui compile mais qui est faux. C'est tout le mécanisme, et c'est pourquoi « adapté aux agents » est une propriété que l'on peut tester plutôt qu'une impression.

Prenons la même erreur dans deux bases de code. Un agent lit une colonne de base de données comme une chaîne alors qu'il s'agit d'un horodatage.

Avec un query builder typé, l'erreur n'est pas exprimable. Le code ne compile pas, l'agent voit l'erreur pendant sa propre exécution et la corrige. Temps perdu : environ deux secondes.

Avec une requête brute qui renvoie `any`, l'erreur compile, passe la relecture parce que le code a l'air correct, et produit une date erronée dans un e-mail de facturation six semaines plus tard. Temps perdu : un incident.

Même modèle. Même prompt. Même erreur. C'est la pile qui a décidé s'il s'agissait d'une erreur de compilation ou d'un incident.

## L'écart d'actualité, et pourquoi la popularité a cessé d'être un indicateur

Voici l'argument que tout le monde avance : les bibliothèques populaires apparaissent plus souvent dans les données d'entraînement, donc les modèles les écrivent plus précisément. La première moitié est vraie. La seconde dépend désormais entièrement d'un élément que l'argument ignore : **la vitesse à laquelle la bibliothèque change**.

**L'écart d'actualité est la distance entre l'API dont un modèle se souvient et l'API que vous livrez réellement.** Le volume de données d'entraînement vous dit avec quelle assurance un modèle écrira du code pour une bibliothèque. L'écart d'actualité vous dit si cette assurance est justifiée. Ce sont deux grandeurs différentes et, pour les frameworks qui évoluent vite, elles pointent désormais dans des directions opposées.

La recherche sur ce sujet est sans ambiguïté. Une étude portant sur huit bibliothèques largement utilisées a mesuré **des taux d'utilisation d'API obsolètes de 25 % à 38 %** dans le code généré par les modèles, et les attribue à des connaissances paramétriques périmées et à l'absence de toute vue en direct sur ce qu'est l'API aujourd'hui ([APILOT, arXiv](https://arxiv.org/pdf/2409.16526)). Des travaux sur les API qui évoluent décrivent le même échec comme un conflit de connaissances : le modèle ne devine pas, il se souvient avec assurance d'une version qui n'existe plus ([When LLMs Lag Behind, arXiv](https://arxiv.org/html/2604.09515v1)).

Il en résulte un classement contre-intuitif. Trié selon l'ampleur des problèmes que cause la mémoire du modèle :

| Profil de bibliothèque                                                          | Volume d'entraînement | Évolution de l'API | Effet net sur le code de l'agent                           |
| ------------------------------------------------------------------------------- | --------------------- | ------------------ | ---------------------------------------------------------- |
| Populaire et stable (React, PostgreSQL, Tailwind)                               | Élevé                 | Faible             | **Le meilleur.** La mémoire est vaste et toujours correcte |
| Petite et stable (Zod, la plupart des utilitaires ciblés)                       | Plus faible           | Faible             | **Bon.** Moins de mémoire, mais ce qui existe est juste    |
| Populaire et en évolution rapide (un framework au milieu d'une version majeure) | Élevé                 | Élevé              | **Le pire.** Assuré, fluide et faux                        |
| Petite et en évolution rapide                                                   | Faible                | Élevé              | Mauvais, mais l'agent reste prudent au lieu d'affirmer     |

La cellule en bas à droite est la plus intéressante. Lorsqu'un modèle sait peu de choses sur une bibliothèque, il a tendance à rester prudent, à chercher ou à lire la source. Lorsqu'il en sait beaucoup sur la _version précédente_ d'une bibliothèque, il affirme. **L'assurance est calibrée sur le volume d'entraînement, pas sur l'exactitude**, donc le pire cas est un volume élevé combiné à une forte évolution : un agent qui écrit couramment du code obsolète et ne signale jamais le moindre doute.

C'est exactement le cas contre lequel Next.js met en garde dans le bloc ci-dessus. C'est le framework React sur lequel les modèles ont été le plus entraînés, et il a suffisamment changé pour que son éditeur juge nécessaire d'imprimer un avertissement à l'intention des agents.

### Que faire ?

Vous ne pouvez pas corriger la mémoire d'un modèle, mais vous pouvez rendre ses erreurs peu coûteuses :

- **Préférez la stabilité à la popularité lorsqu'elles s'opposent.** Une API stable depuis cinq ans dont le modèle se souvient à moitié vaut mieux qu'une API réécrite dont il se souvient entièrement de travers.
- **Laissez le compilateur détecter la dérive de version.** Les erreurs d'API obsolètes ne coûtent cher qu'aux frontières non typées. C'est le véritable argument en faveur des types de bout en bout, et il est plus fort que l'argument habituel.
- **Épinglez et embarquez la documentation que l'agent lit.** Next.js conseille lui-même de lire le guide dans `node_modules`, pas sur le web. La documentation locale correspond à votre version installée ; un article de blog de 2024, non.
- **Traitez les nouvelles dépendances comme non fiables.** Nous y revenons plus bas, car c'est un problème de sécurité et pas seulement d'exactitude.

## Le test Agent Stack

Quatre questions par dépendance, notées 0, 1 ou 2, soit 8 points. Il s'applique aux bibliothèques qui n'existaient pas au moment de la rédaction, ce qui est tout l'intérêt d'un test par rapport à une liste.

### 1. Contrainte : une mauvaise utilisation peut-elle empêcher la compilation ?

- **0** : La bibliothèque renvoie `any`, ou la configuration repose sur des clés en chaînes, ou les erreurs n'apparaissent qu'à l'exécution.
- **1** : Les types existent mais sont indicatifs ; un appel erroné compile toujours avec un cast.
- **2** : Une mauvaise utilisation est une erreur de type. Les programmes erronés ne sont pas exprimables.

### 2. Convergence : existe-t-il une façon évidente de faire le travail ?

Les agents travaillent par imitation, donc une bibliothèque avec six API équivalentes vous donne une chance sur six de tomber sur celle que votre base de code utilise déjà.

- **0** : Beaucoup d'approches équivalentes, toutes courantes dans la nature et toutes présentes dans les données d'entraînement.
- **1** : Une façon recommandée, plus des alternatives historiques largement utilisées.
- **2** : Une seule façon, et les alternatives ont disparu au lieu d'être simplement dépréciées.

### 3. Vérifiabilité : l'agent peut-il prouver lui-même que cela fonctionne ?

- **0** : L'exactitude n'est observable que par un humain qui regarde l'application en cours d'exécution.
- **1** : Testable, mais la mise en place est suffisamment manuelle pour que l'agent ne la fasse pas.
- **2** : Une commande que l'agent exécute déjà le couvre.

### 4. Actualité : la mémoire du modèle est-elle à jour ?

- **0** : Changements de version majeure au cours de la dernière année, avec des API publiques renommées ou supprimées.
- **1** : Changements mineurs récents, ou la documentation dont le modèle a appris est désormais fausse par endroits.
- **2** : L'API publique est stable depuis assez longtemps pour que le code mémorisé fonctionne encore, ou la bibliothèque livre une documentation lisible par machine avec la version installée.

**Lire le score.** De 7 à 8, c'est une dépendance que l'on peut confier à un agent sans supervision. De 4 à 6, elle fonctionne avec une frontière de types ou un test autour. À 3 ou moins, soit vous l'enveloppez dans une interface qui vous appartient, soit vous acceptez qu'un humain écrive chaque site d'appel.

Le test porte délibérément sur la _forme_ d'une dépendance plutôt que sur sa qualité. D'excellentes bibliothèques obtiennent ici de mauvais scores (une très bonne bibliothèque en pleine réécriture obtient 0 en actualité), et des bibliothèques banales obtiennent de bons scores. Il mesure l'adéquation aux agents, pas le mérite.

## Appliquer le test, couche par couche

Voici la pile que nous livrons, notée honnêtement, y compris là où elle a un coût. Vos réponses peuvent différer ; c'est le raisonnement qui est transposable.

### Langage : TypeScript, strict, sans échappatoire

**Note : 8/8.** C'est le choix dont dépend tout le reste de la liste.

Le mode strict est le plancher, pas l'objectif. Les propriétés qui comptent pour les agents sont celles que l'on désactive habituellement : pas de `any` implicite, pas d'accès non vérifié aux index, pas d'assertions non nulles. Chacune de ces options transforme toute une catégorie de code d'agent sûr de lui mais faux, qui aurait été une surprise à l'exécution, en un soulignement rouge que l'agent voit avant de terminer son tour.

La version compte moins que la configuration. Un TypeScript récent configuré de façon laxiste est pire pour le travail d'un agent qu'une version plus ancienne configurée strictement.

### Environnement d'exécution et framework : Cloudflare Workers, TanStack Start, React

**Note : 6/8.** Contrainte 2, convergence 1, vérifiabilité 2, actualité 1.

C'est, honnêtement, le point faible, et c'est le même que celui contre lequel Next.js met en garde. Le cœur de React est stable depuis assez longtemps pour que la mémoire des modèles soit fiable. La couche framework qui l'entoure ne l'a pas été, et elle perd le point d'actualité.

L'application publique actuelle utilise React avec TanStack Start sur Cloudflare Workers. Bun et Vite+ fournissent la chaîne d'outils locale. Les agents doivent lire la documentation des paquets installés ainsi que les skills officiels épinglés de TanStack Start et de Cloudflare avant de modifier le code du framework ou du déploiement.

La convergence perd un point parce que les loaders de route, les fonctions serveur, la mise en cache des requêtes et les endpoints HTTP ordinaires ont des responsabilités différentes. Ce dépôt montre où chacun a sa place : les fichiers de route coordonnent la navigation, les cas d'usage des fonctionnalités portent les opérations, et les intégrations de fournisseurs portent la configuration des services.

### Couche API : fonctions serveur TanStack Start, typées de bout en bout

**Note : 7/8.**

La propriété qui compte n'est pas le framework, c'est que les types d'entrée et de sortie d'un handler soient visibles pour l'appelant. Lorsque la forme d'une route change, chaque site d'appel devenu incorrect cesse de compiler.

Les conseils des concurrents citent généralement des bibliothèques RPC précises. C'est une implémentation de la propriété, pas la propriété elle-même. Toute approche dans laquelle modifier un endpoint casse le build à ses sites d'appel convient. Ce qui ne convient pas, c'est un simple `fetch` vers une route JSON typée à la main au site d'appel, car c'est une frontière où l'hypothèse erronée d'un agent compile proprement, part en production et est découverte par un client.

**Les frontières d'API non typées sont l'endroit où les erreurs des agents survivent.**

### Base de données : Drizzle sur Cloudflare D1

**Note : 8/8.**

Le schéma est en TypeScript : il est donc à la fois la source des migrations et la source des types, et il n'existe pas de second artefact qui puisse diverger. Une requête qui fait référence à une colonne inexistante est une erreur de compilation, pas une erreur 500.

Deux propriétés comptent au-delà du typage. Les requêtes Drizzle ressemblent à du SQL, donc les connaissances SQL existantes se transposent. Cloudflare D1 utilise la sémantique de SQLite, donc les agents doivent suivre l'adaptateur D1 et la documentation installée au lieu de copier des requêtes propres à Postgres. Les migrations versionnées et les bindings locaux isolés permettent de relire les changements avant toute opération distante.

### Validation : Zod à la frontière des requêtes

**Note : 8/8.** C'est la couche que la plupart des piles omettent, et celle qui est rentabilisée le plus vite.

Les types décrivent ce que vous croyez. Les schémas le vérifient. Chaque point d'entrée des données dans le processus (corps HTTP, variables d'environnement, payloads de webhooks, réponses de tiers, colonnes JSON de la base de données) est un endroit où le système de types fait confiance à une promesse que personne n'a vérifiée.

Dans cette application, Zod parse les entrées des fonctions serveur, les paramètres de recherche des routes et les valeurs des formulaires, et le SDK Polar vérifie et parse les payloads des webhooks. Les bindings d'environnement sont typés par Wrangler plutôt que parsés, si bien qu'ils restent la frontière que l'on croit encore sur parole.

Pour le travail d'un agent, cela compte davantage que pour celui d'un humain. Un humain qui écrit une intégration a tendance à se méfier du payload parce qu'il s'est déjà brûlé les doigts. Un agent écrit le cas nominal avec une confiance totale, parce que c'est surtout le cas nominal que contiennent ses données d'entraînement. Un schéma à la périphérie transforme cet optimisme en erreur interceptée, avec un message qui nomme le champ.

### Auth : Better Auth, dans votre dépôt

**Note : 7/8.**

La propriété qui compte pour un agent est que l'implémentation est du code source qui vous appartient plutôt qu'un appel hébergé opaque. Un agent peut lire comment une session est émise, suivre le jeton jusqu'à l'endroit où il est vérifié, et l'étendre d'une manière que vous pouvez relire dans un diff.

L'authentification hébergée obtient ici un moins bon score pour une raison structurelle, indépendante de l'argument du prix : la moitié importante de la logique se trouve derrière une frontière d'API que l'agent ne peut pas lire, donc toute question sur le comportement se termine par une supposition ou une recherche dans la documentation, et toute personnalisation devient une intégration plutôt qu'une modification.

Le point qu'elle perd est celui de l'actualité. C'est une bibliothèque qui évolue vite dans un écosystème encore en consolidation, donc la mémoire que les modèles ont de son API n'est pas fiable. C'est un bon exemple du test qui fait son travail : une bibliothèque peut être le bon choix tout en obtenant un mauvais score sur un axe, et savoir lequel vous indique où placer le garde-fou.

### Styles : Tailwind

**Note : 7/8.**

La raison habituellement avancée est le volume de données d'entraînement. La meilleure raison est structurelle : les styles se trouvent sur l'élément qu'ils mettent en forme, donc **il n'y a pas de second fichier que l'agent doit penser à ouvrir**. Une feuille de style dans un autre répertoire est une obligation de synchronisation, et le mode d'échec des agents n'est pas de mal styliser, c'est de ne mettre à jour qu'un seul des deux endroits.

Cela va au-delà des styles. Le même argument plaide pour des tests colocalisés et des types colocalisés, et contre tout schéma dans lequel un changement doit être répercuté à un endroit que l'agent n'a aucune raison de consulter.

### Internationalisation : use-intl avec un contrôle de parité

**Note : 7/8**, et elle mérite sa place ici pour une raison qui ne concerne pas vraiment l'i18n.

Les traductions sont l'archétype de l'échec silencieux. Un agent ajoute une fonctionnalité, écrit les chaînes en anglais, et il manque désormais des clés dans les autres langues. Rien ne plante. Les tests passent. Le bug atteint précisément les clients qui ne peuvent pas le signaler clairement.

La solution n'est pas une meilleure bibliothèque, c'est que `bun run check:i18n` fasse échouer la CI sur une clé manquante. Toute partie de votre système qui a cette forme (présente à un endroit, silencieusement absente à un autre) a besoin du même traitement et, tant qu'elle ne l'a pas, elle reste invisible pour votre agent comme pour vous.

### Paiements et e-mails : Polar, Resend

**Note : 6/8** et **7/8**.

Les intégrations de paiement perdent des points sur la convergence plutôt que sur la qualité. Cette application utilise le checkout Polar et des webhooks vérifiés, avec la gestion des achats et des clés de licence dans les cas d'usage des fonctionnalités. Suivez cette implémentation et le comportement de nouvelle tentative documenté par le fournisseur. Resend envoie les modèles d'e-mails localisés depuis le Worker.

Les webhooks méritent leur propre avertissement, et en reçoivent un plus bas.

### Tests : Vitest et Playwright

**Note : 8/8**, et c'est la couche qui rend toutes les autres notes exploitables.

L'enjeu n'est pas la couverture en tant que chiffre. C'est que `bun run check && bun run test:coverage` existe, se termine avec 0 ou 1, et qu'un agent puisse l'exécuter sans qu'on lui explique comment. Tout ce qui se trouve au-dessus de cette ligne vise à réduire ce qu'un agent peut exprimer. Cette ligne-ci vise à intercepter ce qui est passé malgré tout.

## Le nombre de dépendances est une surface d'exposition pour l'agent

Chaque dépendance est une API dont le modèle peut se souvenir de travers. Cela transforme l'argument habituel du « trop de dépendances », qui porte normalement sur la taille du bundle et la chaîne d'approvisionnement, en un argument d'exactitude également.

Les dépendances d'exécution sont listées dans `package.json`. Ce qui compte, ce n'est pas leur nombre mais leur forme : presque toutes sont soit typées de bout en bout, soit enveloppées derrière une frontière qui nous appartient, donc une hypothèse erronée à leur sujet empêche la compilation au lieu d'échouer en production.

Il existe désormais une seconde raison d'être prudent, et elle relève de la sécurité. Des mesures montrent que les modèles de pointe publiés entre octobre 2025 et mars 2026 hallucinent des noms de paquets à des taux compris entre **4,62 % et 6,10 %** ([arXiv](https://arxiv.org/pdf/2605.17062)). Des attaquants enregistrent ces noms inventés sur les registres publics et attendent, une attaque appelée **slopsquatting** ([Mend](https://www.mend.io/blog/the-hallucinated-package-attack-slopsquatting/)).

La règle pratique : **une dépendance ajoutée par un agent est une pull request non relue venant d'un inconnu.** Vérifiez que le paquet existe, que son nom est bien celui que vous attendiez et pas une variante approchante, et que vous en aviez réellement besoin. Les lockfiles et une étape de relecture des modifications de `package.json` couvrent l'essentiel de l'exposition pour un effort quasi nul.

## Ce que les agents ne devraient jamais gérer seuls

Certaines parties d'un SaaS partagent une propriété : **la mauvaise version a l'air juste, passe les tests, fonctionne en démo, et n'échoue que dans des conditions que votre suite de tests ne reproduit pas.** C'est cette propriété, et non la difficulté, qui rend leur délégation risquée.

| Surface                            | Pourquoi la mauvaise version passe la relecture                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| Gestion des sessions et des jetons | Une connexion qui fonctionne ne prouve rien sur l'expiration, la rotation ou la révocation |
| Webhooks de paiement               | Un handler non idempotent est correct jusqu'à l'arrivée de la nouvelle tentative           |
| Migrations de base de données      | La réversibilité et la perte de données restent invisibles jusqu'au rollback               |
| Isolation des locataires           | La requête est juste pour le locataire de test et fausse pour le second                    |
| Tout ce qui lit un secret          | Journaliser un jeton est une modification d'une ligne qui fonctionne parfaitement          |

Le webhook est le cas le plus parlant. Stripe renvoie l'événement en cas de réponse non 2xx, donc un handler qui débite correctement à la première livraison et débite à nouveau lors de la nouvelle tentative passe tous les tests qu'un agent penserait à écrire, car écrire ce test suppose de connaître déjà le mode de défaillance. Ce n'est pas une limite des capacités du modèle. C'est que la suite de tests qu'écrit un agent reflète les modes de défaillance présents dans ses données d'entraînement, et les bugs d'idempotence y sont sous-représentés par rapport à la fréquence à laquelle ils coûtent de l'argent réel.

Marquez ces chemins dans `AGENTS.md` comme relevant uniquement d'une relecture humaine, et appuyez cela sur des relecteurs obligatoires, afin que l'intention soit imposée plutôt que supposée respectée.

## La pile, et où la vérifier

Chaque affirmation ci-dessous correspond à une commande du dépôt public du site, plutôt qu'à un adjectif sur une page.

## Foire aux questions

<Accordions>

<Accordion title={"Quelle est la meilleure pile technique pour les agents de codage AI en 2026 ?"}>

TypeScript de bout en bout, avec une couche de base de données typée, une validation par schéma à chaque frontière externe, une authentification qui vit dans votre dépôt et une seule commande qui vérifie les types, lance le linter et exécute les tests. Les bibliothèques précises comptent bien moins que le fait qu'une mauvaise utilisation empêche la compilation. Notez chaque candidat sur la contrainte, la convergence, la vérifiabilité et l'actualité avant de l'adopter.

</Accordion>

<Accordion title={"Le choix d'un framework populaire aide-t-il les agents de codage de l'IA ?"}>

Moins qu'avant, et parfois pas du tout. La popularité donne à un modèle davantage de données d'entraînement, mais seulement sur la version sur laquelle il a été entraîné. Un framework qui publie des changements incompatibles plus vite que les modèles ne sont réentraînés produit un code assuré, fluide et faux. Dès qu'une bibliothèque évolue vite, la stabilité compte davantage que le volume.

</Accordion>

<Accordion title={"Pourquoi mon agent écrit-il du code en utilisant des API qui n'existent plus ?"}>

Parce qu'il se souvient de la version sur laquelle il a été entraîné. Des travaux de recherche ont mesuré des taux d'utilisation d'API obsolètes de 25 % à 38 % sur huit bibliothèques largement utilisées, attribués à des connaissances paramétriques périmées et à l'absence de vue en direct sur ce qu'est l'API aujourd'hui. Votre vérificateur de types est la correction la moins coûteuse, et c'est pourquoi le problème survit aux frontières non typées.

</Accordion>

<Accordion title={"Devrais-je laisser un agent d'IA choisir mes dépendances ?"}>

Pas sans vérifier que chaque paquet existe. Les modèles de pointe publiés entre octobre 2025 et mars 2026 ont halluciné des noms de paquets à des taux compris entre 4,62 % et 6,10 %, et des attaquants enregistrent désormais ces noms inventés sur les registres publics, une attaque appelée slopsquatting. Traitez toute nouvelle dépendance ajoutée par un agent comme une pull request non relue venant d'un inconnu.

</Accordion>

<Accordion title={"Un monorepo est-il mieux pour les agents de codage de l'IA ?"}>

Seulement si les frontières sont imposées par l'outillage plutôt que décrites dans un readme. Un monorepo dont les frontières entre paquets font échouer le build lorsqu'elles sont franchies enseigne votre architecture à un agent en quelques secondes. Un monorepo qui ne tient que par convention donne à l'agent davantage d'endroits où mettre le bon code dans le mauvais paquet.

</Accordion>

<Accordion title={"Quelles parties d'un SaaS un agent ne devrait-il jamais écrire seul ?"}>

Tout domaine où une erreur d'apparence plausible est à la fois coûteuse et silencieuse : la gestion des sessions et des jetons, les webhooks de paiement, les migrations de base de données, l'isolation des locataires et tout ce qui lit un secret. Ces éléments partagent une propriété : la mauvaise version passe les tests et les démos sans problème, et n'échoue que dans des conditions que votre suite de tests ne reproduit pas.

</Accordion>

<Accordion title={"Ai-je besoin de tRPC ou d'oRPC pour une API adaptée aux agents ?"}>

Vous avez besoin de types qui traversent la frontière réseau ; la bibliothèque précise est secondaire. Toute approche dans laquelle un client qui appelle un endpoint modifié ne compile plus fera l'affaire. Ce qui ne fonctionne pas, c'est un simple fetch vers une route JSON non typée, car c'est une frontière où une hypothèse erronée compile proprement et atteint la production.

</Accordion>

<Accordion title={"Combien de dépendances sont trop nombreuses pour une base de code assistée par un agent ?"}>

Comptez les surfaces plutôt que les paquets. Chaque dépendance est une API dont le modèle peut se souvenir de travers, donc la question est de savoir combien d'entre elles sont structurantes, peu familières et non vérifiées. Une dépendance couverte par des types stricts et un test coûte peu. Une dépendance qui renvoie des données non typées dans votre logique métier coûte à chaque changement futur.

</Accordion>

<Accordion title={"Est-ce que Tailwind aide réellement les agents de codage de l'IA ?"}>

Oui, pour une raison structurelle plutôt que stylistique. Les styles se trouvent sur l'élément qu'ils mettent en forme, donc il n'y a pas de second fichier que l'agent doit penser à ouvrir et à mettre à jour. Le même argument plaide pour des tests colocalisés et des types colocalisés, et contre tout schéma dans lequel un changement doit être répercuté dans un fichier que l'agent n'a aucune raison d'ouvrir.

</Accordion>

<Accordion title={"Devrais-je changer de pile pour que mon agent fonctionne mieux ?"}>

Presque jamais. Le coût d'une migration est certain et le gain est limité, alors qu'ajouter des types stricts, une validation aux frontières et une commande de vérification unique à votre pile existante coûte peu et s'applique immédiatement. Changez de pile quand vous alliez le faire de toute façon, et faites de l'adéquation aux agents un critère de départage plutôt que la raison.

</Accordion>

</Accordions>
