Daten gelangen über TanStack Query auf einen Bildschirm. Ein Use-Case exportiert seine Optionen neben seiner Serverfunktion, und der Routen-Loader, die Komponente und der Test verwenden alle dieselben Optionen, sodass sie konstruktionsbedingt einen Cache-Eintrag teilen.

## Query-Optionen

```ts
export const courseEditorQuery = (input: Course["getCourseEditor"]) =>
  queryOptions({
    queryFn: () => getCourseEditor({ data: input }),
    queryKey: [...COURSE_QUERY_KEYS.EDITOR, input.courseId],
    staleTime: COURSE_STALE_MS,
  })
```

| Art des Lesezugriffs              | Export                                                                   | Beispiel                                         |
| --------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| Erhält eine Eingabe               | Eine Funktion, die Optionen zurückgibt, benannt `<noun>Query`            | `courseEditorQuery(input)`, `courseQuery(input)` |
| Erhält keine Eingabe              | Eine Konstante namens `<noun>Query`                                      | `currentLicenseQuery`                            |
| Paginierte Liste für eine Tabelle | `get<Things>PageQuery(input)` und die erste Seite als `get<Things>Query` | `getOrdersPageQuery`, `getOrdersQuery`           |

## Query-Keys

Ein Key beginnt mit dem Präfix des Moduls aus `<table>.constants.ts`, dann folgt die Operation, dann jede Eingabe, die das Ergebnis verändert:

```ts
queryKey: [...COURSE_QUERY_KEYS.CATALOGUE, input.locale]
queryKey: [...COURSE_QUERY_KEYS.DETAIL, input.locale, input.slug]
queryKey: [...COURSE_QUERY_KEYS.LIST, courseZodSchemas.getCourses.parse(input)]
```

Der Listen-Key speichert die geparste Eingabe, sodass `getCoursesPageQuery()` und `getCoursesPageQuery({ pageIndex: 0, pageSize: 10 })` auf denselben Eintrag führen. Eine Locale gehört immer dann in den Key, wenn der Server das Ergebnis lokalisiert. Schreibe einen Key nie inline in eine Komponente: Lies ihn aus den Optionen oder, zum Invalidieren, aus dem Objekt `<MODULE>_QUERY_KEYS`.

## Öffentliche Queries [#public-queries]

Eine Query, deren Ergebnis für jeden Besucher gleich ist, egal wer angemeldet ist, deklariert `meta: { public: true }`:

```ts title="src/lib/github.ts"
export const starCountQuery = queryOptions({
  gcTime: STAR_COUNT_REFRESH_AFTER_MS,
  meta: { public: true },
  queryFn: () => getStarCount(),
  queryKey: ["github", "stars"],
  staleTime: STAR_COUNT_REFRESH_AFTER_MS,
})
```

Die Übersetzungen (`messagesQueryOptions`) und die Anzahl der GitHub-Sterne (`starCountQuery`) sind öffentlich. Jede andere Query gehört dem angemeldeten Nutzer. Wechselt der Nutzer, entfernt `removeUserData` in `auth.session.ts` diese Queries und jede Mutation und behält die öffentlichen, sodass der nächste Nutzer nie die Daten des vorherigen sieht und eine vorgerenderte Seite die Daten behält, mit denen sie gerendert wurde: Das Flag reist mit jeder Query mit, die der Server in die Seite dehydriert. Eine Query ohne das Flag wird für den nächsten Nutzer neu geladen, was eine Anfrage kostet, aber nie Daten preisgibt; markiere eine Query deshalb nur dann als öffentlich, wenn ihre Serverfunktion nie die Session liest. `auth.session.test.ts` führt jede öffentliche Query aus und schlägt fehl, wenn eine davon die Session liest oder wenn eine Quelldatei eine öffentliche Query deklariert, die der Test nicht ausführt. Der Test führt sie in `PUBLIC_QUERIES` auf, jeweils unter der Quelldatei, die die Query deklariert.

## Aktualität

`getRouter()` in `src/router.tsx` erstellt pro Anfrage einen `QueryClient` mit den Cache-Zeiten aus `src/integrations/tanstack-query/query.cache.ts`. Der Router setzt `defaultPreloadStaleTime` auf `ROUTER_PRELOAD_STALE_TIME_MS` und lässt `defaultStaleTime` beim Standardwert, sodass allein diese Cache-Zeiten bestimmen, was frisch ist:

```ts
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      gcTime: QUERY_GC_TIME_MS,
      staleTime: QUERY_STALE_TIME_MS,
    },
  },
})
```

Eine Query, die eine andere Aktualität braucht, setzt `staleTime` mit einer benannten Konstante, die den Grund nennt: `PLAYBACK_STALE_MS` (eine Stunde, innerhalb der Lebensdauer einer signierten Wiedergabe-URL), `STAR_COUNT_REFRESH_AFTER_MS` für die Anzahl der GitHub-Sterne, `Infinity` für Übersetzungsnachrichten, die sich nur mit einem Deployment ändern. Erstelle nie einen `QueryClient` auf Modulebene; auf dem Server würde er die Daten eines Nutzers mit der nächsten Anfrage teilen.

## Loader laden vor, Komponenten lesen

Ein Seiten-Loader lädt die Queries vor, die seine Komponenten lesen: die, die der erste Teil der Antwort braucht, innerhalb des einen `Promise.all`, das unter [Routendateien](/docs/conventions/routes) beschrieben ist, und die übrigen, ohne auf sie zu warten, sodass sie gestreamt werden ([Gestreamte Abschnitte](/docs/conventions/routes#streamed-sections)). Aus `src/routes/app.license.tsx`:

```ts
context.queryClient.query({ ...currentLicenseQuery, staleTime: "static" })
```

`staleTime: "static"` lässt den Loader vorhandene Daten aus dem Cache zurückgeben, statt sie neu zu laden. Die Komponente liest anschließend dieselben Optionen und wendet die eigene `staleTime` der Query an:

```tsx
const { license } = useSuspenseQuery(currentLicenseQuery).data
```

Eine Navigation zu einer Seite, deren Daten bereits im Cache liegen, rendert also sofort, und veraltete Daten werden im Hintergrund aktualisiert, statt die Navigation aufzuhalten.

Ein `"static"`-Lesezugriff ignoriert außerdem die Invalidierung: Er gibt Daten aus dem Cache zurück, selbst nachdem eine Mutation sie invalidiert hat, und die frischen Daten kommen erst an, wenn die Komponente neu lädt. Deshalb wartet ein Loader stattdessen auf die Query mit ihrer eigenen `staleTime`, wenn die Seite nie Daten zeigen darf, die älter sind als etwas, das der Besucher gerade getan hat, oder wenn der Loader die Daten selbst braucht, für den Titel oder um mit 404 zu antworten. Die Kursseiten und der Kurseditor im Admin tun das, weil das Abschließen einer Lektion oder das Speichern im Editor auf dem nächsten Bildschirm den aktualisierten Lehrplan zeigen muss:

```ts
context.queryClient.query(courseQuery({ locale, slug: params.course })).catch(rethrowAsNotFound)
```

- Verwende `useSuspenseQuery` für Daten, die der Loader vorgeladen hat, und `useQuery` nur für Daten, die später eintreffen dürfen, ohne die Seite zu blockieren, etwa die Anzahl der Sterne in `proof-section.tsx`. Eine Query, die der Loader streamt, wird immer mit `useSuspenseQuery` innerhalb einer `Suspense`-Grenze gelesen; mit `useQuery` gelesen, würde sie auf dem Server ohne ihre Daten rendern und im Browser mit ihnen.
- Lade keine Daten in `useEffect`, und reiche Query-Ergebnisse nicht als Props weiter: Jede Komponente ruft die Optionen auf, die sie braucht.
- Ein `DataGrid` erhält eine Funktion, die seine Anfrage auf Optionen abbildet, `query={(request) => getOrdersPageQuery(orderZodSchemas.getOrders.parse(request))}`, und führt die Query selbst aus.

## Mutationen und Invalidierung

Eine Komponente übernimmt die Mutation-Optionen per Spread in `useMutation` und ergänzt nur ihre eigenen Callbacks. Nach einem erfolgreichen Schreibzugriff invalidiert sie das Präfix des Moduls und gibt dann Rückmeldung:

```tsx
const update = useMutation({
  ...updateCourseMutation,
  onError,
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL })
    toast.success(t("saved"))
  },
})
```

- Invalidiere das engste Präfix, das jeden Bildschirm abdeckt, der die geänderten Daten zeigt. Mutationen von Kapiteln und Lektionen invalidieren `COURSE_QUERY_KEYS.ALL`, weil der Kurseditor und die öffentlichen Kursseiten sie anzeigen. `useLessonProgress` invalidiert nur `COURSE_QUERY_KEYS.DETAIL`, und nur, wenn eine Lektion abgeschlossen wird.
- Warte auf die Invalidierung, bevor du wegnavigierst oder einen Dialog schließen, damit der nächste Bildschirm frische Daten rendert.
- Fehler laufen über `useErrorMessage()`; siehe [Serverfunktionen und Fehler](/docs/conventions/server-functions).
- Aktualisiere den Cache nie von Hand, um ein Ergebnis vorzutäuschen. Die einzige Ausnahme ist die Session: Wechselt der angemeldete Nutzer, entfernt `loadRouteSession` in `auth.routes.ts` mit `removeUserData` die Daten des vorherigen Nutzers und speichert die neue Session, damit keine privaten Daten eine Abmeldung oder einen Kontowechsel überdauern. Siehe [Öffentliche Queries](#public-queries).
