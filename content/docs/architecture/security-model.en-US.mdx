## Two layers of access control

**Route guards** in `src/integrations/better-auth/auth.routes.ts` run in `beforeLoad` and redirect:

| Guard                | Used by                   | Behavior                                                                             |
| -------------------- | ------------------------- | ------------------------------------------------------------------------------------ |
| `requireSignedIn`    | `/app` layout             | Redirects to sign-in without a session, keeping the page as `redirect`               |
| `requireAdmin`       | `/admin` layout           | Also requires the `admin: ["access"]` permission, otherwise redirects to `/app`      |
| `redirectIfSignedIn` | Sign-in and sign-up pages | Sends a signed-in user to `redirect`, or to their workspace                          |
| `redirectAfterAuth`  | `/auth/callback`          | Sends the user to `redirect`, or to `/admin` or `/app` by role, after authentication |

Guards only decide what the user sees. **Server function middleware** in `auth.middleware.ts` protects the data, because any server function can be called without its page:

- `authorized()` loads the session for the request and throws `UNAUTHORIZED` without one.
- `authorized({ user: ["ban"] })` also checks the role's permissions from `auth.access.ts` and throws `FORBIDDEN`.
- The handler receives the session as `context.auth`. Operations on the caller's own data use `context.auth.user.id`, never a user ID from the input.

## Sessions

- Better Auth stores sessions in D1 and uses the `saasyland` cookie prefix, with secure cookies outside development and test builds.
- `getRequestSession` bypasses the cookie cache and memoizes the session for the rest of the request.
- The session sent to the browser has its token removed.
- `tanstackStartCookies` is the last Better Auth plugin, so cookies set during a server function reach the response.
- Allowed hosts are fixed per build mode: `saasyland.com` in production, `preview.saasyland.com` in preview, `localhost:3000` and `127.0.0.1:3000` in development, and in test also `localhost:3020` and `127.0.0.1:3020`.

Better Auth also handles email verification (required before sign-in), password reset (which revokes existing sessions), OAuth with GitHub and Google (tokens encrypted at rest), two-factor authentication and admin impersonation. Verification identifiers are stored hashed.

## Rate limits

`withRateLimit(kind, limit)` counts attempts per operation and client IP (`cf-connecting-ip`) in the `rate_limit` table with a single atomic D1 batch. `RATE_LIMITS.SENSITIVE` allows <RepositoryFact name="sensitiveRateLimit" /> attempts and `RATE_LIMITS.TOKEN` allows <RepositoryFact name="tokenRateLimit" /> per <RepositoryFact name="rateLimitWindowSeconds" unit="second" />. If the counter storage fails, the request is refused. Better Auth's own rate limiter uses the same table with an `auth:` key prefix; session reads, sign-out and Polar webhooks are exempt.

Emails a visitor can trigger have a second limit. `withinRecipientRateLimit` allows <RepositoryFact name="recipientEmailsPerHour" /> emails of each kind (verification, password reset and newsletter confirmation) per address per hour, keyed on a SHA-256 hash of the address, and skips the email silently beyond that.

## Response headers

`src/server.ts` sets `SECURITY_HEADERS` (a Content Security Policy, `Cross-Origin-Opener-Policy`, `Permissions-Policy`, `Referrer-Policy`, `X-Content-Type-Options` and `X-Frame-Options`) on every response the Worker returns, plus `HTTPS_SECURITY_HEADERS` (`Strict-Transport-Security`) over HTTPS, and replaces any value the response or a `public/_headers` rule already set. Both constants live in `src/modules/_core/constants/api.ts`. Files served without the Worker get the same headers from the `/*` rule in `public/_headers`, and `src/__test__/server.test.ts` fails when that rule and the constants differ. See [Security and hardening](/docs/features/security).

## Media links

Video files stay in a private R2 bucket. `getVideoPlayback` requires `video: ["read"]`, and `getLessonPlayback` the lesson's access level, before they sign a path, and the signature is an HMAC-SHA-256 with a key derived from `AUTH_SECRET` by HKDF. `serveMedia` answers `403` for a wrong or expired signature. A signed path works as a bearer link until it expires, at least <RepositoryFact name="signedMediaHours" unit="hour" /> after it is issued, so whoever holds it can play that video. See [Cloudflare R2](/docs/integrations/cloudflare-r2).

## Errors and input

- Server functions that take input parse it with a Zod schema before the handler runs.
- Better Auth's own endpoints follow the same rules as the forms: `enforceInputPolicy` in `auth.hooks.ts` runs before every endpoint that accepts a password, name, email or image and answers `400` with `VALIDATION_ERROR` when the body fails its schema.
- `withRequest` turns unexpected errors into `INTERNAL_ERROR` and logs the original on the server, so internal details never reach the client.
- Polar webhooks are verified with `POLAR_WEBHOOK_SECRET` before any licence changes.
- Secrets are read from `cloudflare:workers` only by server code: server-only modules, server function handlers and helpers that only they import. `scripts/verify-build.ts` fails the build when a client asset imports `cloudflare:workers`.
- Private areas (`/admin`, `/app`, `/auth`, `/newsletter`) are never prerendered, and neither are the course pages, which show each viewer's locks and progress.
