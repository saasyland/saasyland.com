title: "Lint i formatowanie"
description: "oxlint i oxfmt uruchamiane przez Vite+ oraz skrypty kontrolne."
---

Vite+ uruchamia oxfmt do formatowania i oxlint do lintowania; oba narzędzia są skonfigurowane w sekcjach `fmt` i `lint` pliku `vite.config.ts`. `bun run check` to bramka jakości, którą uruchamia CI:

```sh
bun run check
```

Uruchamia on `generate:cn`, `check:comments`, `check:i18n`, `check:flows` i `vp check`, który sprawdza formatowanie, stosuje reguły lintera i sprawdza typy w projekcie. Aby uruchomić tylko jedno narzędzie, użyj `bun run lint`, `bun run format` lub `bun run format:check`.

## Formatowanie

- Bez średników, podwójne cudzysłowy, przecinki końcowe i końce linii LF; szerokość wcięcia w spacjach: <RepositoryFact name="tabWidth" />, szerokość wiersza: <RepositoryFact name="printWidth" />.
- Importy są sortowane w stałe grupy: tylko serwerowe, `cloudflare:workers`, React, pakiety zewnętrzne, następnie obszary `~/src` (platforma, providery, integracje, moduły, trasy, hooki, dane i motyw, typy, lib, branding, komponenty shadcn, komponenty własne, style), a na końcu importy względne.
- Klasy Tailwind są sortowane w `className` oraz w wywołaniach `cn`, `cva`, `clsx` i `tw`.

## Lintowanie

- Kategorie `correctness`, `nursery`, `pedantic`, `perf`, `style` i `suspicious` są zgłaszane jako błędy.
- Włączone są reguły uwzględniające typy oraz sprawdzanie typów (`typeAware` i `typeCheck`).
- Najważniejsze limity: maksymalna liczba linii w pliku (<RepositoryFact name="maxLines" />), linii w funkcji (<RepositoryFact name="maxLinesPerFunction" />) i instrukcji w funkcji (<RepositoryFact name="maxStatements" />), brak magicznych liczb poza `0` i `1`, brak jawnego `any` (`typescript/no-explicit-any`) oraz identyfikatory o długości co najmniej dwóch znaków z wyjątkiem `_`, `m` i `t`.
- Nadpisania łagodzą kilka reguł dla testów, kodu warstwy prezentacji i hooków, mocków testowych oraz plików tras.
- `jsPlugins` ładuje własne wtyczki oxlint repozytorium: `scripts/code-style-lint-plugin.ts`, której reguły `code-style/no-comments`, `code-style/no-multiline-ternary` i `code-style/no-undefined-fallback` odrzucają każdy komentarz, każdy operator trójargumentowy rozciągający się na kilka wierszy i każde `?? undefined` (zobacz [Styl kodu](/docs/conventions/code-style)), `scripts/hydration-lint-plugin.ts`, której reguła `hydration/no-clock-or-locale-in-render` nie pozwala kodowi renderującemu odczytywać zegara ani języka środowiska uruchomieniowego (zobacz [Styl kodu](/docs/conventions/code-style)), `scripts/admin-data-lint-plugin.ts`, której reguła `admin-data/no-literal-data` nie dopuszcza danych demonstracyjnych do kodu panelu administracyjnego (zobacz [Panel administracyjny](/docs/features/admin-dashboard#real-data-only)), oraz `scripts/radius-lint-plugin.ts`, której reguła `radius/no-off-scale` trzyma każdy narożnik na skali zaokrągleń (zobacz [Motyw](/docs/ui/theme#corner-radius)).
- Furtki są zakazane imiennie: `typescript/ban-ts-comment` odrzuca `@ts-expect-error`, `@ts-ignore` i `@ts-nocheck` nawet z opisem, `typescript/consistent-type-assertions` z `assertionStyle: "never"` odrzuca każdą asercję typu poza `as const`, a `respectEslintDisableDirectives: false` sprawia, że komentarz `eslint-disable` niczego nie wyłącza. `code-style/no-comments` zastępuje `capitalized-comments`, `no-inline-comments` i `no-warning-comments`, które włączają kategorie i z których każda widziała tylko część komentarzy, więc te trzy są wyłączone.

Oba narzędzia ignorują pliki generowane i zewnętrzne: pliki deklaracji, `src/routeTree.gen.ts`, migracje, `.source`, `dist`, `coverage`, `e2e`, `remotion`, foldery agentów i wyniki Playwright. `scripts/` jest formatowany i lintowany tak samo jak `src/`. `bun run check:comments` czyta także to, co pomija linter: `e2e`, `remotion`, pliki deklaracji i arkusze stylów.

Formatter sortuje też `package.json`, w tym jego `scripts` alfabetycznie (`sortPackageJson: { sortScripts: true }`), więc `vp check` kończy się błędem, gdy skrypt jest nie na swoim miejscu.

Usuwaj przyczynę błędu lintera. Nie dodawaj komentarzy wyłączających reguły, `@ts-expect-error` ani rzutowań `as` tylko po to, by spełnić regułę. Komentarz wyłączający jest komentarzem, a linter podporządkowuje się mu, zanim zobaczy go jakakolwiek reguła, więc polecenie `bun run check:comments`, działające poza linterem, odrzuca go wszędzie, gdzie się znajdzie.

## Naprawianie

Hook pre-commit uruchamia `bun run check:pre-commit`; jego krok `vp staged` uruchamia `vp check --fix` wyłącznie na plikach dodanych do stagingu. `bun run check:fix` stosuje poprawki w całym repozytorium i może przepisać pliki spoza Twoich zmian, więc przed commitem przejrzyj jego diff. Aby poprawić tylko własne zmiany, przekaż ich ścieżki do `vp` (globalnego CLI Vite+ lub `bunx vp`):

```sh
vp fmt src/routes/admin.users.all.tsx
vp lint --fix src/routes/admin.users.all.tsx
```
