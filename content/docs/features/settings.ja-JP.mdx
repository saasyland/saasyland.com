`src/routes/app.settings.tsx` と `src/routes/admin.settings.tsx` は、`SETTINGS_TABS`（`src/data/auth.ts`）から **一般** と **セキュリティ** の 2 つのタブを表示します。タブは `tab` 検索パラメーターで表し、`settingsSearchSchema` が検証して、既定のタブのときはアドレスから省きます。そのため、OAuth のリンクは `?tab=security` に戻ってきます。カードは `src/presentation/components/custom/settings` にあり、`/app` と `/admin` のレイアウトが読み込む `auth.security` 名前空間を共有して、顧客と管理者の両方に使われます。最後に **アカウントを削除** があるのは、顧客の一般タブだけです。どちらのローダーもセッション一覧（`getActiveSessionsQuery`）とサインイン方法（`listAccountsQuery`）をプリロードし、`/app/settings` はさらにアカウント削除の案内の読み込みも実行します。

| タブ         | `/app/settings`                                                          | `/admin/settings`                                                        |
| ------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 一般         | `PreferencesCard`、`EmailCard`、`DeleteAccountCard`                      | `PreferencesCard`、`EmailCard`                                           |
| セキュリティ | `PasswordCard`、`TwoFactorCard`、`ConnectedAccountsCard`、`SessionsCard` | `PasswordCard`、`TwoFactorCard`、`ConnectedAccountsCard`、`SessionsCard` |

## 環境設定

`PreferencesCard`（`src/presentation/components/custom/preferences-card.tsx`）は、サインイン中のユーザーのタイムゾーンを編集します。これはアカウントに保存される唯一の表示設定です。保存済みのタイムゾーンは現在のセッションクエリから読み取ります。

- 検索可能なコンボボックスが、`TIMEZONE_CODES`（`src/modules/user/user.constants.ts`、`TIMEZONES` から派生）のすべてのタイムゾーンを、`timezones` 名前空間での名前で一覧表示します。この名前空間は `/admin` と `/app` のレイアウトが読み込みます。
- **このブラウザから検出** は、ブラウザーが報告するタイムゾーンを選択します。タイムゾーンは `Intl.DateTimeFormat` が解決した形で比較するため、`Asia/Calcutta` のようなエイリアスからでも `Asia/Kolkata` が見つかります。一覧にないタイムゾーンの場合はメッセージを表示し、現在の選択を維持します。
- **環境設定を保存** は `updatePreferences`（`src/modules/user/use-cases/update-preferences.ts`、サインイン必須）を呼び出します。このユースケースは `userZodSchemas.updatePreferences` でタイムゾーンを検証し、Better Auth の `updateUser` を通じて保存します。その後、カードは現在のセッションクエリを無効化し、`TranslationsProvider` がすべての日付を新しいタイムゾーンで表示します（[国際化とロケール](/docs/features/internationalization)）。

言語は保存されません。言語は URL 内のロケールで、`LocaleSelect` で切り替えます。日付の順序、12 時間制か 24 時間制か、数値の区切り文字もロケールで決まります。

## メールアドレス

`EmailCard` はアドレスとその確認状況を表示し、**メールアドレスを変更** で `ChangeEmailForm`（`custom/auth/change-email-form.tsx`）を開きます。これはメール確認のバナーと同じフォームで、`changeEmail`（サインイン必須、レート制限）を呼び出します。確認済みのアドレスは 2 段階で変わります。まず Better Auth が現在のアドレスに確認リンク（`ChangeEmailConfirmationEmail`）を送り、そのリンクが開かれると新しいアドレスに確認リンクを送ります。このリンクを開くと変更が保存されます。どちらのリンクも、変更を始めたページに戻ります。未確認のアドレスはすぐに変わり、新しい確認リンクが届きます。新しいアドレスにすでにアカウントがある場合、Better Auth は何も送らず、ほかのアドレスと同じように応答します。そのため、トーストは、そのアドレスが使える場合はリンクを送信中であると伝えます。

## パスワード

`PasswordCard` はサインイン方法を読み取ります。パスワードがあれば現在のパスワードと新しいパスワードを入力させ、`changePassword`（サインイン必須、レート制限）を呼び出します。このユースケースは、ほかのセッションを必ずすべてサインアウトさせます。GitHub または Google だけでサインインするアカウントには、代わりに **パスワードを設定** が表示され、`setPassword`（サインイン必須、レート制限）を呼び出します。これは Better Auth のサーバー専用の `setPassword` を実行してから `revokeOtherSessions` を実行します。どちらのフォームも長さのルールに `PasswordRequirements` でチェックを付け、既知のデータ漏洩に含まれるパスワードは入力欄の下に示し、最後にアカウントへ `PasswordChangedEmail` を送ります。変更のときは `password-change-notice` フックが、新しいパスワードのときは `setPassword` が送信します。

## 二要素認証

`TwoFactorCard` は TOTP が有効かどうかを表示し、`TwoFactorDialog` を開いて、有効化、無効化、新しいバックアップコードの作成を行います。いずれも現在のパスワードを入力してから進みます。パスワードのないアカウントには、先にパスワードを設定するよう案内します。2 つ目の要素が守るのは、パスワードによるサインインだからです。[二要素認証](/docs/features/two-factor)を参照してください。

## 連携アカウント

`ConnectedAccountsCard` は `OAUTH_PROVIDERS` の GitHub と Google を、それぞれを連携した日付とともに一覧表示します。**連携する** はブラウザーから Better Auth の `linkSocial` を呼び出します。これはプロバイダーを経由して `?tab=security` に戻ってきます。失敗した場合は `?error=` 付きで戻り、カードにその `auth.errors` のメッセージを表示します。Better Auth は、プロバイダー側のアドレスがアカウントのアドレスと異なるアカウントも連携します（`accountLinking.allowDifferentEmails`）。連携を始めるのはサインイン中の所有者本人だからです。**連携を解除** は、アカウントの行 ID を渡して `unlinkAccount`（サインイン必須、レート制限）を呼び出します。カードがこれを表示するのは、アカウントにほかのサインイン方法がある間だけで、Better Auth もいずれにせよ最後の 1 つの連携解除を拒否します。プロバイダーでしかサインインできないアカウントには、先にパスワードを設定するか別のアカウントを連携するよう案内します。

## セッション

`SessionsCard` は、サインインしているブラウザーを、このブラウザーを先頭にして一覧表示します。[セッション](/docs/features/sessions)を参照してください。

## アカウントの削除 [#delete-account]

`DeleteAccountCard` は、削除によって消えるもの、つまりプロフィール、サインイン方法、二要素認証の設定、コースの進捗を一覧表示し、続けて `ACCOUNT_DELETION_NOTICES` の案内を表示します。このリストは `custom/settings/delete-account-card.tsx` がカードの隣で宣言します。各案内は、コンポーネントと、2 つの設定ページがその案内のために読み込むデータを指定し、どの案内も自分が属するエリアのコンポーネントを指すので、そのエリアがないプロジェクトにはその案内がありません。最初に表示されるのは法的情報のエリアの `AccountDeletionRecords` で、決済記録や税務記録、ライセンスとその提供記録は、プライバシーポリシーに記載のとおり、アカウントとの紐付けを外したうえで保存されることを伝えます。続いてライセンスのエリアの `LicenseDeletionNotice` が、アカウントが有効なライセンスを持つ間に表示され、ライセンスはアカウントの削除とともに終了すること、キーが使えなくなること、削除しても返金されないこと、撤回機能を先に使うことを伝えます。

**アカウントを削除** は現在のパスワードを求めるダイアログを開き（パスワードのないアカウントでは何も求めません）、`requestAccountDeletion`（サインイン必須、レート制限）を呼び出します。Better Auth がパスワードを確認して `sendDeleteAccountVerification` を呼び出し、`sendDeleteAccountEmail` が `/app/settings/delete-account?token=…` へのリンクをページの言語でメール送信します。リンクは `EMAIL_LINK_LIFETIME_HOURS` の間有効です。そのページ（`src/routes/app.settings_.delete-account.tsx`）は `/app` のサインインの内側にあり、削除の影響をもう一度示して、**アカウントを削除する** が押されたときにだけアカウントを削除します。`confirmAccountDeletion`（サインイン必須、トークンとしてレート制限）がトークンを Better Auth の `deleteUser` に渡し、`deleteUser` がユーザーとそのセッションを削除して Cookie を失効させます。その後ページはクエリキャッシュからアカウントのデータを削除し、ホームページへ移動して削除したことを伝えます。別の場所で開いたリンクは先にサインインを求め、トークンのないページは設定へ戻る道を示します。リンクを開いただけでは何も起こらないため、リンクをたどるメールスキャナーがアカウントを削除することはありません。

ユーザーを削除すると、そのセッション、サインイン方法、二要素認証の行、コースの進捗も連鎖して削除されます。ライセンス、Polar の注文とサブスクリプションのコピー、および撤回の意思表示は、[プライバシーポリシー](/privacy)のとおり、ユーザーを外したまま行が残り、有効なライセンスは先に取り消されます（[ライセンス](/docs/features/licences#records-and-refunds)）。

## スケルトン

`preferences-card-pending.tsx` の `PreferencesCardPending` と、`custom/settings/settings-pending.tsx` の `SettingsTabsPending`、`EmailCardPending`、`DeleteAccountCardPending` が、`AdminSettingsPending`、`AppSettingsPending`、`AppDeleteAccountPending` を描画します。すべてのページがスケルトンを読み込み、カードのファイルにはフォームがあるため、これらは専用のファイルに置いています（[パフォーマンス](/docs/conventions/performance#skeletons-stay-in-the-entry-script)を参照）。スケルトンが描画するのは一般タブです。
