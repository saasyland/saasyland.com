Better Auth stores users, accounts, sessions and verification tokens in D1 through the Drizzle adapter. It provides email and password sign-up that signs a new account in at once and saves what needs a confirmed address for later, GitHub and Google sign-in, password reset, email change, TOTP two-factor authentication, admin user management and, through its Polar plugin, the Polar customer portal and webhooks. Checkouts are not part of Better Auth: they are created by `createCheckout` (`src/modules/order/order.checkout.ts`). Its HTTP API is served by `src/routes/api/auth.$.ts`. `auth.server.ts` and `auth.client.ts` set Better Auth's `basePath` to `ROUTES.API.AUTH.BASE`, the path that file serves, so the server and the browser client take it from one constant.

| `auth.access.ts`                                       | `ac`, `ROLES` and `hasPermission`, and the permission statements in `APP_STATEMENTS` and their grants                                                                                                 |
| `auth.roles.ts`                                        | `ROLE_CODES`, `ROLE_VALUES`, `DEFAULT_ROLE_CODE` and `isRole`                                                                                                                                         |
| `auth.constants.ts`                                    | `AUTH_PROVIDER`: the ids of the email and password provider (`credential`) and the OAuth providers; `LOGIN_METHOD` and `LAST_LOGIN_METHOD_COOKIE` for the **Last used** badge                         |
| `auth.session.ts`                                      | `getRequestSession`, the `getCurrentSession` server function and `getCurrentSessionQuery`                                                                                                             |

## Route guards

| Guard                | Used by                          | Behaviour                                                                                    |
| -------------------- | -------------------------------- | -------------------------------------------------------------------------------------------- |
| `requireSignedIn`    | `/app`                           | Redirects to sign-in without a session, with the page as `redirect`, and returns the session |
| `requireAdmin`       | `/admin`                         | Also requires the `admin: ["access"]` permission, otherwise redirects to `/app`              |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Sends a signed-in user to `redirect`, or to `/admin` or `/app` by role                       |
| `redirectAfterAuth`  | `/auth/callback`                 | Requires a session, then redirects to `redirect` or to the workspace for the role            |
| `redirectIfVerified` | `/auth/verify-email`             | Sends a session with a confirmed address to `redirect`, or to `/admin` or `/app` by role     |

The guards load the session through the query cache and, when the signed-in user changes, remove every cached query that is not public with `removeUserData` from `auth.session.ts`. [Sessions](/docs/features/sessions#cached-data-and-the-signed-in-account) explains how they know whose data the cache holds.

## Server functions

Page guards only protect navigation, so every protected server function checks the caller again with middleware from `auth.middleware.ts`:

- `authorized(permission?)` requires a session, optionally checks a permission, and adds the session to the context as `context.auth`. Operations on the caller's own data use `context.auth.user.id`, never a user ID from the input.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (<RepositoryFact name="sensitiveRateLimit" /> requests per <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) or `RATE_LIMITS.TOKEN` (<RepositoryFact name="tokenRateLimit" /> per <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) limits a public operation per client IP from `cf-connecting-ip`.
- `withRequest`, which both include, maps errors to `AppError` codes: Better Auth errors become `AUTH_API_ERROR` with their error key, Zod errors become `VALIDATION`, and unexpected errors are logged and returned as `INTERNAL_ERROR`.

## Roles and permissions

`auth.roles.ts` defines two roles: `admin` and `customer` (the default for new accounts). `auth.access.ts` declares the statements of every resource in `APP_STATEMENTS`: `admin` and `settings` for the admin console and its settings, `product` for the products page, which lists the Polar catalogue, and for the product module, `category` for the category module's use cases, which no screen uses, `course` and `video` for the courses, and `order` for the orders. It grants them all to admins, who also receive Better Auth's admin statements, and builds the access control and the roles from them. `hasPermission({ permission, role })` is shared by guards, middleware and the UI. See [Roles and permissions](/docs/guides/roles-and-permissions).

## Plugins

`plugins` in `auth.server.ts` lists every Better Auth plugin, in the order Better Auth applies them:

| Plugin                    | What it adds                                                                                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `admin`                   | User and session administration with `ac` and `ROLES` from `auth.access.ts`                                                                   |
| `twoFactor`               | Two-factor authentication                                                                                                                     |
| `lastLoginMethod`         | The cookie that remembers the last sign-in method                                                                                             |
| `invitationPlugin`        | Invitations (`src/modules/invitation/invitation.plugin.ts`)                                                                                   |
| `haveIBeenPwned`          | The breach check of every new password (`NEW_PASSWORD_PATHS`)                                                                                 |
| `password-change-notice`  | `notifyPasswordChange` after a password change                                                                                                |
| `license-retention`       | The `user.delete.before` hook that revokes a deleted account's licence                                                                        |
| `polar`                   | The Polar plugin with the customer portal and the webhooks, which hand each event to `handlePolarEvent` ([Payments](/docs/features/payments)) |
| `polar-verified-customer` | `requireVerifiedEmail` before every `/customer/` endpoint                                                                                     |
| `tanstackStartCookies`    | Sets Better Auth's cookies on TanStack Start's responses, and must come last                                                                  |

Every plugin is written out in the list, so Better Auth's types include the user and session fields each one adds. An element that names a feature's file, such as `revokeAccountLicense` or `polarCore`, leaves with that feature, and so does `[ROUTES.API.AUTH.POLAR.WEBHOOKS]: false` in `rateLimit.customRules`, which keeps Polar's deliveries out of Better Auth's rate limiter.

## Email and rate limits

The email hooks call the senders of the verification, account and user modules directly, because auth needs email: `sendVerifyEmail`, `sendExistingAccountEmail`, `sendResetPasswordEmail`, `sendPasswordChangedEmail`, `sendDeleteAccountEmail` and `sendChangeEmailConfirmationEmail`. Better Auth's own rate limiter stores its counters in the D1 `rate_limit` table under an `auth:` prefix through `consumeRateLimit` from `src/lib/rate-limit.ts`, which uses atomic upserts and rejects requests when its storage is unavailable. `clientAddress` in `auth.middleware.ts` resolves a request's client the way that limiter does, from `cf-connecting-ip` with IPv6 addresses grouped by /64. The cookie prefix is `APP_SLUG` from the branding. `getRequestSession` bypasses the cookie cache, so authorization always reads the session from D1.
