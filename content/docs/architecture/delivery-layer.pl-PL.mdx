## Pliki tras

Trasy to płaskie pliki w `src/routes`. Kropki stają się segmentami ścieżki:

| Plik                              | URL                | Uwagi                                       |
| --------------------------------- | ------------------ | ------------------------------------------- |
| `__root.tsx`                      | wszystkie strony   | Rama dokumentu i główne przestrzenie nazw   |
| `_site.tsx`                       | brak               | Layout bez ścieżki z nagłówkiem witryny     |
| `_site._marketing.tsx`            | brak               | Layout bez ścieżki dla stron marketingowych |
| `_site._marketing.terms.tsx`      | `/terms`           | Strona w layoucie marketingowym             |
| `admin.tsx`                       | `/admin`           | Layout z guardem `requireAdmin`             |
| `admin.users.all.tsx`             | `/admin/users/all` | Strona w layoucie panelu administracyjnego  |
| `_site._marketing.blog.index.tsx` | `/blog`            | Strona indeksowa layoutu `blog`             |
| `_site.docs.$.tsx`                | `/docs/*`          | Trasa splat dla stron dokumentacji          |
| `api/auth.$.ts`                   | `/api/auth/*`      | Handler HTTP bez komponentu                 |

Identyfikatory w `createFileRoute("…")` to literały tekstowe utrzymywane przez generator routera, który zapisuje też `src/routeTree.gen.ts`. Pliki w folderach `__test__` są ignorowane. Każdy URL ma stałą w `ROUTES` (`src/routes.ts`), a linki używają `<Link to={ROUTES.X}>`.

## Trasy stron

Trasa strony definiuje komponent `<Name>Page`, stałą `NAMESPACE` bezpośrednio nad `export const Route` oraz loader, który ładuje metadane strony i przestrzeń nazw w jednym `Promise.all`:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.TERMS),
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Dodatkowe dane trafiają do tego samego `Promise.all`, na przykład `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` w `admin.users.all.tsx`. `pageHead` z `src/lib/seo.ts` buduje na podstawie `metadata` z loadera znaczniki tytułu, opisu, adresu kanonicznego, `hreflang`, Open Graph i obrazu podglądu; zobacz [Podglądy w wyszukiwarkach i mediach społecznościowych](/docs/features/seo).

## Trasy layoutów

Trasa layoutu definiuje komponent `<Name>Layout`, tablicę `NAMESPACES`, a w przypadku obszarów chronionych także guard w `beforeLoad`. Jej `NAMESPACES` wymieniają każdą przestrzeń nazw, której potrzebują jej strony, także przestrzenie nazw innych funkcji, a parametr adresu URL walidują strony, które go odczytują, tak jak strony licencji `/app` i `/app/license` robią to z `tier`:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "pages.license", "timezones"] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Guardy `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn`, `redirectIfVerified` i `redirectAfterAuth` pochodzą z `src/integrations/better-auth/auth.routes.ts`.

## Szkielety ładowania [#loading-skeletons]

Większość nawigacji kończy się, zanim pojawi się jakikolwiek stan ładowania: linki wstępnie ładują swoją trasę po najechaniu kursorem i dotknięciu, a strony publiczne są prerenderowane. Gdy nawigacja nie skończy się po `defaultPendingMs`, czyli <RepositoryFact name="navigationPendingMs" unit="millisecond" />, router pokazuje szkielet trasy, a ponieważ `defaultPendingMinMs` wynosi <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, usuwa go w chwili, gdy strona jest gotowa. Dzieje się tak przy wolnym połączeniu albo przy pierwszym żądaniu do nowego izolatu Workera (zobacz [Wydajność](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

Nie ma domyślnego komponentu ładowania. Każda trasa layoutu i strony ustawia własny `pendingComponent`. Strony dokumentacji są rysowane wewnątrz layoutu dokumentacji: `_site.docs.index.tsx` i `_site.docs.$.tsx` pokazują `DocsIndexPending` i `DocsPagePending`, czyli artykuł i jego spis treści obok paska bocznego, a layout `docs` pokazuje `DocsPending`, gdy ktoś wchodzi do dokumentacji z innego miejsca. Każdy szkielet odwzorowuje stronę, którą zastępuje:

- **Szkielety stron**, takie jak `SignInPending` i `LegalPending`, znajdują się w pliku szkieletów danej funkcji i oznaczają swój element główny atrybutem `aria-busy="true"`. Są to pliki `custom/auth/auth-pending.tsx`, pliki panelu administracyjnego w `custom/admin/` (`admin-pending.tsx` dla layoutu, po jednym pliku `<feature>-pending.tsx` na każdą funkcję, np. `products-pending.tsx`, i wspólne bloki w `pending-blocks.tsx`), pliki aplikacji klienta w `custom/app/` (`app-pending.tsx` dla layoutu, `auth-pending.tsx` i `license-pending.tsx` oraz wspólny dla nich nagłówek strony w `pending-blocks.tsx`), pliki layoutu publicznego bezpośrednio w `custom/` (`marketing-pending.tsx` dla layoutu, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` i `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` i `custom/docs-pending.tsx`.
- **Szkielety layoutów**, takie jak `AuthPending` i `MarketingPending`, renderują ramę layoutu, a w niej `pendingComponent` pierwszej trasy poniżej layoutu, która pasuje do bieżącej ścieżki i go ustawia; `usePagePending` w `src/hooks/use-page-pending.ts` odczytuje go z drzewa tras. Dzięki temu po wejściu do obszaru z innego miejsca widać właściwą stronę, a szkielet layoutu o poziom niżej, taki jak `AdminUsersPending`, robi to samo dla swoich stron. Elementy ramy, które nie potrzebują danych, takie jak `Wordmark` i `PageFrame`, renderują się naprawdę, a nagłówek witryny zostaje na ekranie, bo renderujący go layout `_site` nie ma loadera, na który musiałby czekać.
- **Placeholdery tekstu** to paski `Skeleton` z tokenem typograficznym prawdziwego elementu oraz `h-lh scale-y-70`, dzięki czemu każdy pasek wypełnia dokładnie jedną linię tekstu (line box). Bloki mają prawdziwe wysokości i promienie zaokrągleń. Listy biorą swoją długość z tych samych stałych co UI, np. `OAUTH_PROVIDERS` i `AUTH_ASSURANCES` w `src/data/auth.ts`.

Gdy dodajesz stronę, dodaj jej szkielet do pliku szkieletów funkcji i ustaw go jako `pendingComponent` trasy; tam znajdą go szkielety layoutów.

## Inne aspekty tras

- **Parametry adresu URL** są parsowane przez `validateSearch` w trasie, na przykład parametr `tab` w `/app/settings`. Schemat to `zod.object` zbudowany z funkcji pomocniczych z `src/lib/search-params.ts`: `searchText()` i `searchFlag()` zwracają `undefined` dla brakującej, pustej lub nieprawidłowej wartości, a `searchChoice(choices, fallback)` zwraca wartość zapasową. `searchParam(schema)` zwraca `undefined`, chyba że wartość pasuje do innego schematu zod, np. tokenu newslettera.
- **Funkcje serwerowe używane przez jedną trasę** można zdefiniować w pliku trasy za pomocą `createServerFn`.
- **Treść generowana podczas budowania**: loadery dokumentacji, bloga i strony głównej czytają indeksy treści z `virtual:content-indexes`, czyli z plików pod `/assets/`, więc nie potrzebują funkcji serwerowej i przy nawigacji po stronie klienta działają w przeglądarce (zobacz [Fumadocs](/docs/integrations/fumadocs#content-indexes)).
- **Endpointy HTTP** znajdują się w `src/routes/api`. Zobacz [Handlery HTTP w TanStack Start](/docs/architecture/api-layer).

## Router

`src/router.tsx` eksportuje `getRouter`, który dla każdego żądania tworzy nowy `QueryClient` i router. Konfiguruje:

- domyślne komponenty błędu i nieznalezionej strony z `presentation/components/custom`, bez domyślnego komponentu ładowania (zobacz [Szkielety ładowania](#loading-skeletons))
- wstępne ładowanie po wskazaniu linku i `defaultPreloadStaleTime` równe <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />, więc to TanStack Query, a nie router, decyduje, czy wstępnie załadowana albo ponownie odwiedzona strona pobiera coś jeszcze raz (zobacz [Cache i SSR](/docs/architecture/caching-and-ssr) oraz [Wydajność](/docs/conventions/performance#the-headers-pages-load-before-a-click))
- `rewrite`, który usuwa prefiks języka z przychodzących adresów URL i dodaje go z powrotem do generowanych linków
- integrację zapytań z SSR przez `setupRouterSsrQueryIntegration`

## Po wdrożeniu [#after-a-deploy]

Każde wdrożenie zastępuje statyczne zasoby Workera, a Vite nazywa każdy plik według jego zawartości, więc karta otwarta przed wdrożeniem prosi o chunki tras, których już nie ma. TanStack Start umieszcza komponent i loader każdej trasy w osobnych chunkach. TanStack Router przeładowuje stronę, gdy nie uda się załadować chunka komponentu (`lazyRouteComponent`), ale chunk loadera router-core ładuje przez `lazyFn`, które przekazuje nieudany import trasie jako błąd jej loadera. Kliknięcie **Blog** w takiej karcie kończyło się błędem na chunku loadera layoutu bloga i stroną błędu.

`DefaultError`, domyślny komponent błędu routera, radzi sobie z tą sytuacją. `isStaleBuildError` w `src/lib/stale-build.ts` rozpoznaje błąd, który oznacza, że strona wykonuje kod usunięty przez nowsze wdrożenie:

- nieudany import dynamiczny, który `isModuleNotFoundError` z router-core rozpoznaje w Chromium, Firefoksie i Safari;
- plik, którego Vite nie zdołał wstępnie załadować dla chunka, na przykład jego arkusz stylów; Vite zgłasza go zdarzeniem `vite:preloadError`. Trasa główna nasłuchuje tego zdarzenia, dopóki aplikacja jest otwarta (`listenForStaleBuilds`).

Przy takim błędzie `DefaultError` ładuje adres, do którego przeszedł odwiedzający, jako nową stronę przez `router.navigate({ href, reloadDocument: true, replace: true })`, więc odwiedzający trafia na klikniętą stronę, już z nowego wdrożenia; dopóki przeglądarka nie opuści strony, komponent zamiast komunikatu o błędzie renderuje pusty `main` oznaczony jako zajęty. `claimReload` pozwala na jedno takie przeładowanie dla każdego celu i builda. Zapisuje cel w `sessionStorage` razem z URL-em skryptu wejściowego strony, który zmienia się przy każdym wdrożeniu zmieniającym plik ładowany przez przeglądarkę, bo każdy chunk jest wczytywany ze skryptu wejściowego pod nazwą zawierającą hash jego zawartości. Drugi błąd dla tego samego celu w tym samym buildzie pokazuje stronę błędu, więc plik, którego naprawdę brakuje, nie może przeładowywać strony bez końca, a następne wdrożenie dostaje własne przeładowanie. Gdy przeglądarka odmawia dostępu do pamięci sesji, nic się nie przeładowuje.

Safari anuluje pliki, które strona jeszcze wczytuje, gdy tylko odwiedzający zaczyna ją opuszczać, więc chunk lub arkusz stylów w drodze kończy się błędem, jakby usunęło go wdrożenie. Dlatego `listenForStaleBuilds` odnotowuje też, kiedy strona otrzymuje `beforeunload`, a `DefaultError` czeka przez `whenPageStays`, aż `pageshow`, `pointerdown` lub `keydown` pokaże, że odwiedzający został, zanim ponownie załaduje stronę. Odwiedzający, który wychodzi, trafia na stronę, o którą prosił, zamiast wracać na tę, którą opuszczał, a ten, kto wraca na stronę lub na niej zostaje, dostaje wtedy przeładowanie. `stale-build.spec.ts` wstrzymuje kod trasy lekcji, przechodzi do polityki prywatności, anuluje ten kod i sprawdza, że polityka prywatności się otwiera, a lekcja nie jest pobierana ponownie.

Nieudane wstępne ładowanie nie wykorzystuje przeładowania. Najechanie kursorem na link wstępnie ładuje jego trasę, tak jak nagłówek robi to ze swoimi linkami, gdy strona jest bezczynna; gdy to się nie uda, nie renderuje się żaden komponent błędu, a router pobiera chunk ponownie, gdy odwiedzający kliknie. `e2e/specs/stale-build.spec.ts` włącza oszczędzanie danych, żeby nagłówek nie załadował wcześniej bloga, usuwa chunki bloga z otwartej strony i sprawdza, że kliknięcie, także po nieudanym wstępnym ładowaniu przy najechaniu, trafia na bloga po jednym przeładowaniu, a strona, której chunków nadal brakuje, pokazuje stronę błędu po dwóch przeładowaniach, jednym przez `DefaultError` i jednym przez `lazyRouteComponent`.
