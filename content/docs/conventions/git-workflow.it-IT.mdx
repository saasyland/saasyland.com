La cronologia di `main` fa parte del prodotto: ogni pull request unita con squash merge è una riga che dice cosa è cambiato per chi usa il codice.

## Commit

I messaggi di commit seguono Conventional Commits, scritti senza emoji; l'hook `prepare-commit-msg` aggiunge l'emoji del tipo (vedi [Conventional commits](/docs/tooling/conventional-commits) per la tabella):

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- L'oggetto è in minuscolo, all'imperativo, e dice cosa fa la modifica per i suoi utenti: `feat(course): reorder the catalogue from the course list`, non `update course files`.
- Lo scope è il modulo o l'area: `course`, `auth`, `a11y`, `deps`, `readme`.
- Il tipo è uno tra `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 e `revert` 🗑️; l'hook rifiuta qualsiasi altro tipo. Non scrivere mai l'emoji a mano: l'hook non controlla un oggetto che inizia già con un'emoji.
- Dividi una pull request in commit logici: la funzionalità, la sua documentazione come `docs(<scope>)`, e le correzioni trovate lungo il percorso.
- Non eseguire mai un commit con `--no-verify`. L'hook `pre-commit` esegue `bun run check:pre-commit`; quando fallisce, correggi la causa.
- Formatta e analizza con il linter solo i file che hai modificato, con `bunx vp fmt <files>` e `bunx vp lint --fix <files>`. Non eseguire `bun run check:fix` o `vp check --fix` sull'intero repository: riscrivono file che non hai toccato, comprese le impostazioni condivise dell'editor in `.vscode/settings.json`. Se `.vscode/` compare in `git status`, ripristinala da `HEAD`.

## Nessuna attribuzione all'IA

I commit e le descrizioni delle pull request non riportano alcun trailer `Co-Authored-By` per uno strumento di IA, nessuna riga "Generated with" e nessun'altra attribuzione all'IA, anche quando uno strumento la aggiunge per impostazione predefinita. GitHub associa l'indirizzo di un trailer di questo tipo a un account estraneo, che compare poi tra i contributori del repository. L'hook `commit-msg` rifiuta un messaggio di commit che contiene un'attribuzione di questo tipo e indica la riga da rimuovere (vedi [Conventional commits](/docs/tooling/conventional-commits)). Lo stesso vale per le correzioni proposte upstream (vedi [Dipendenze](/docs/conventions/dependencies)).

## Branch e worktree

- Crea un branch a partire da `main`, un branch per pull request.
- Assegna a ogni branch il proprio worktree Git invece di cambiare il branch di un checkout, così un checkout aperto da un editor o da un altro processo non viene mai modificato mentre è in uso:

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Prima di fidarti dell'esito di un test, controlla `git branch --show-current` nella cartella in cui hai eseguito i test.

### Gli hook in ogni worktree [#hooks-in-every-worktree]

Git legge `core.hooksPath` dalla configurazione condivisa da tutti i worktree di un repository, e Vite+ lo imposta sul percorso relativo `.vite-hooks/_`, quindi Git esegue il dispatcher degli hook del worktree in cui fai il commit. Il dispatcher è generato e non entra mai in un commit, perciò ogni worktree ha bisogno del proprio, e dove manca Git salta gli hook senza alcun avviso. Due passaggi lo installano:

- `git worktree add` esegue l'hook `post-checkout` del checkout da cui lanci il comando, e `.vite-hooks/post-checkout` installa il dispatcher del nuovo worktree con `vp hooks enable`. Un commit fatto prima di `bun install` fallisce quindi nell'hook `pre-commit` invece di saltarlo.
- `bun install` esegue `prepare`, che aggiorna il dispatcher con `vp config --no-agent` e poi esegue `scripts/verify-git-hooks.ts`. L'installazione fallisce quando `core.hooksPath` non è `.vite-hooks/_` o quando al dispatcher manca un hook di `.vite-hooks/`, e l'errore mostra il comando che lo ripara.

Non impostare mai `core.hooksPath` su un altro valore e non passare mai `-c core.hooksPath` a Git. Finché conteneva il percorso assoluto del dispatcher del checkout principale, `vp config` non ha installato alcun dispatcher negli altri worktree, e quando il successivo `bun install` nel checkout principale ha ripristinato il percorso relativo, i commit in quei worktree sono stati creati senza hook. `vp hooks status` indica se gli hook sono attivi in un worktree.

## Cronologia lineare [#linear-history]

Il ruleset che protegge `main` su GitHub richiede una cronologia lineare, accetta le pull request solo attraverso la coda di merge, che fa lo squash di ciascuna, e rifiuta i force-push, quindi ogni pull request arriva su `main` come un unico commit. Anche i branch delle pull request restano lineari:

- Non creare mai un merge commit, né su `main` né sul branch di una pull request: non fare il merge di `main` in un branch e non risolvere conflitti in un merge commit.
- Aggiorna un branch facendo il rebase su `main`, con `gh pr update-branch --rebase` oppure con `git fetch origin` e `git rebase origin/main`, quando entra in conflitto con `main`. Una pull request senza conflitti non ha bisogno di alcun rebase per il merge: la coda di merge la testa sopra l'ultima versione di `main`.
- Quando GitHub non riesce a fare il rebase di una pull request con più commit, riportala come un unico commit sopra `main`: riduci il branch a un solo commit sulla sua merge base, poi fai il rebase di quel commit, così risolvi ogni conflitto una sola volta:

```sh
git fetch origin
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -m "feat(course): reorder the catalogue from the course list"
git rebase origin/main
git push --force-with-lease
```

- Pubblica un branch riscritto con `git push --force-with-lease`, e solo il tuo branch di pull request. Non fare mai il force-push di `main` o del branch di un'altra persona, e non usare mai un semplice `--force`, che sovrascrive i commit pubblicati dopo il tuo ultimo fetch.

## Pull request

- **Piccole e mirate.** Una correzione, una funzionalità o un refactoring per pull request. Una funzionalità grande diventa una serie di pull request, ognuna revisionabile da sola, come è stato per i video, i corsi e l'amministrazione dei corsi.
- **Il titolo è il commit di squash.** Usa il formato dei commit senza l'emoji; diventa l'oggetto su `main`, che GitHub chiude con `(#<number>)`. `scripts/enqueue-pr.ts` aggiunge l'emoji che aggiungerebbe l'hook di commit quando mette la pull request nella coda di merge.
- **La descrizione** contiene un `## Summary` di cosa è cambiato e perché, un `## Test plan` con i comandi che hai eseguito e i loro risultati, e un elenco `## Docs` delle pagine, delle sezioni del README e dei testi che hai aggiornato. Scrivila in modo semplice, senza linguaggio di marketing.
- **Nessuna revisione automatica.** Il ruleset di `main` contiene la regola `copilot_code_review` con `review_on_push: true`, ma al 22 novembre 2026 GitHub Copilot non ha revisionato alcuna pull request dalla #70, quindi le pull request non ricevono alcuna revisione automatica. Anche una revisione sarebbe solo consultiva: non approverebbe e non bloccherebbe nulla, perché il ruleset non richiede alcuna approvazione.
- **Ogni pull request aggiorna ciò che rende inesatto:** il README, le pagine della documentazione in tutti i locale e qualsiasi testo del sito o affermazione della landing page che tocca, e aggiunge la propria [voce del changelog](#changelog-entries). Le inesattezze trovate in codice che non hai modificato richiedono una pull request a parte. Il README non può stampare valori dal codice, quindi lo legge `src/__test__/readme.test.ts`: ogni versione, porta, conteggio e soglia che indica deve essere uguale al valore del codice o di `REPOSITORY_FACTS`, ogni altro numero fallisce a meno che non sia una data o uno dei fatti esterni elencati dal test, ogni comando `bun run` deve nominare uno script di `package.json`, e ogni file, route e regola di lint che nomina deve esistere.

## Merge [#merging]

Una pull request arriva su `main` solo attraverso la coda di merge di GitHub. Quando i suoi controlli sono verdi e la sua voce del changelog è presente, mettila in coda con il suo numero:

```sh
bun scripts/enqueue-pr.ts 280
```

Lo script fallisce su un titolo che non segue il formato dei commit, imposta come titolo l'oggetto che scriverebbe l'hook di commit, emoji compresa, ed esegue `gh pr merge --auto --squash`, che aggiunge la pull request alla coda non appena i suoi controlli passano. La coda testa ogni pull request sopra `main` e sopra le pull request che la precedono, con i controlli che la pull request ha eseguito, ne compila diverse alla volta e porta su `main` un gruppo di pull request tutte insieme quando ciascuna è passata, così nessuno deve fare il rebase di una pull request pronta per unirla. Una pull request che fallisce nella coda ne esce; correggila e rimettila in coda. Non fare mai il merge di una pull request a mano o scavalcando la coda: è l'esecuzione della coda ad aver testato il commit che arriva su `main`, e `deploy.yml` riesegue tutti i controlli per un commit che l'ha saltata.

## Voci del changelog [#changelog-entries]

Ogni pull request aggiunge la propria voce al [changelog](/docs/project/changelog), così le pull request aperte in parallelo non modificano mai lo stesso file.

- **Dalle il nome della pull request.** Apri la pull request, poi aggiungi `content/changelog/<number>.<locale>.mdx` in tutti i locale: un elenco puntato, senza frontmatter, di ciò che cambia per chi usa il codice, con i link alle pagine della documentazione interessate.
- **Non scrivere mai una data né il numero della pull request.** La pagina del changelog ricava il giorno di ogni voce, e le note di rilascio la sua release, dalla cronologia Git: il giorno, in UTC, del commit squash il cui oggetto GitHub chiude con `(#<number>)`. Finché la pull request non è unita, la sua voce compare sotto **Non rilasciato**. Il numero lo ricavano dal nome del file: la pagina chiude ogni punto di una voce con un link alla sua pull request, o al suo commit per una voce che porta il nome di un commit, e le note di rilascio chiudono ogni punto con `(#<number>)`, che GitHub trasforma in link. Una volta distribuita, la pagina collega anche ogni voce alla [release](/docs/tooling/ci-cd#releases-and-tags) che l'ha rilasciata per prima.
- **La CI lo controlla.** In una pull request, `bun run check` fallisce finché manca `content/changelog/<number>.en-US.mdx`, e `check:content` confronta ogni traduzione con questo file come fa con una pagina della documentazione. Fallisce anche un file che non porta né il numero di una pull request né l'hash completo di un commit: le poche modifiche arrivate su `main` senza pull request portano il nome del loro commit.
- **Solo la tua voce può restare non rilasciata.** In CI, la build del sito fallisce finché il changelog mostrerebbe sotto **Non rilasciato** una voce che non dovrebbe esserci: in una pull request verso `main`, qualsiasi voce tranne quella della pull request stessa, e nella coda di merge e su `main`, qualsiasi voce. Un branch della coda di merge contiene già il commit squash di ogni pull request del suo gruppo, quindi ognuna delle loro voci ha il suo giorno. Una build locale, che non ha `GITHUB_REF`, mostra tutte le voci non unite. Così emerge una voce sopravvissuta alla sua pull request: `content/changelog/219.<locale>.mdx` è rimasto indietro quando #219 è stata chiusa senza unirla, ripeteva la voce di #220 ed è comparso sotto **Non rilasciato** in produzione finché #254 non l'ha rimosso.

## Controlli

La CI esegue `bun run check` e `bun run test:coverage`, compila il Worker di test ed esegue la suite nel browser in Chromium, e carica il Worker di preview su Cloudflare come versione che non riceve traffico. Quel caricamento è il controllo che Cloudflare accetta il Worker: i suoi limiti di caricamento hanno fatto fallire un deploy che aveva superato tutti gli altri controlli. La coda di merge esegue di nuovo gli stessi controlli sulla pull request insieme a `main` e alle pull request che la precedono. Vedi [CI/CD](/docs/tooling/ci-cd).
