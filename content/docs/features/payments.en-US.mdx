Payments run through Polar with the `@polar-sh/better-auth` plugin, which `plugins` in `src/integrations/better-auth/auth.server.ts` lists with a plugin of its own after it:

```ts title="src/integrations/better-auth/auth.server.ts"
    polar({
      client: polarCore,
      use: [portal(), webhooks({ onPayload: handlePolarEvent, secret: env.POLAR_WEBHOOK_SECRET })],
    }),
    {
      hooks: {
        before: [
          {
            handler: requireVerifiedEmail,
            matcher: ({ path }) => path?.startsWith(ROUTES.API_AUTH_POLAR.CUSTOMER) === true,
          },
        ],
      },
      id: "polar-verified-customer",
    },
```

The plugin adds the customer portal and the webhooks, which `[ROUTES.API_AUTH_POLAR.WEBHOOKS]: false` in `rateLimit.customRules` exempts from Better Auth's rate limiter, and no checkout: its `checkout()` would create a checkout with the account's ID alone, so Polar would ask a signed-in buyer for their email again. Better Auth closes no path to HTTP, so `src/integrations/better-auth/__test__/auth.server.polar.integration.test.ts` checks that the plugin's checkout path answers 404 and fails once `checkout()` is added to the plugin. Checkouts start in the order module instead, with the Polar SDK (see [Checkout](#checkout)).

The second element, `polar-verified-customer`, is a plugin of its own that runs `requireVerifiedEmail` (`auth.hooks.ts`) before every `/customer/` endpoint, so the customer portal answers `403 EMAIL_NOT_VERIFIED` until the account's address is confirmed ([Email verification](/docs/features/email-verification)).

`src/integrations/polar/polar.config.ts` creates `polarCore` from `POLAR_ACCESS_TOKEN` and `POLAR_SERVER`, which the plugin uses, and `polar`, the checkouts, licence keys and orders services built on it. `POLAR_ORGANIZATION_ID` scopes every Polar call that names an organisation; [Environment and bindings](/docs/reference/environment) lists them. `src/integrations/polar/polar.constants.ts` holds Polar's own values: `POLAR_ORDER_STATUS`, `POLAR_SUBSCRIPTION_STATUS`, `POLAR_RECURRING_INTERVAL`, `POLAR_LICENSE_KEY_STATUS` and `POLAR_WEBHOOK_EVENT`, each checked against the SDK's types, `POLAR_CHECKOUT_ID_PLACEHOLDER`, `POLAR_CUSTOMER_SESSION_TOKEN_PARAM`, and `POLAR_ID_MAX_LENGTH`, the length of every column that holds a Polar ID. It reads no environment, so the browser and the browser suite import it too. Polar's paths, `API_AUTH_POLAR` and `API_AUTH_CUSTOMER_PORTAL`, are in `src/routes.ts`. [Polar setup](/docs/getting-started/polar-setup) describes the products, licence keys, consent checkbox, tax behaviour, webhook and token this code expects in Polar, and `bun run polar:verify:<environment>` checks them.

## Checkout

`createCheckout` in `src/modules/order/order.checkout.ts` creates every checkout the site starts, with `polar.checkouts.create`. It takes the signed-in account from the server function's context and `{ locale, productId, returnPath, successPath }`, and:

1. reads the origin of the request with `trustedRequestOrigin` (`src/lib/request-origin.ts`), which refuses with `FORBIDDEN` a host that `appHostsForMode` does not list for the build mode, or plain HTTP outside development and test, and names it as `embed_origin`, the only page that may frame the checkout and receive its messages, so that `openCheckoutOverlay` (`src/lib/checkout-overlay.ts`) can show it over the page ([The checkout over the page](/docs/features/licences#the-checkout-over-the-page));
2. ties the checkout to the account (`external_customer_id`) and fills in its email and name (`customer_email`, `customer_name`), so the checkout form opens with them, and the buyer's IP address from `cf-connecting-ip` (`customer_ip_address`, read with Better Auth's `getIP`);
3. opens Polar's page in the language `polarCheckoutLanguage` gives for `locale`, and writes `locale` itself into `metadata` under `ORDER_CHECKOUT_METADATA.LOCALE` (`order.constants.ts`), next to the affiliate referral when the visitor came through an affiliate link ([Affiliate programme](/docs/features/affiliates)). Polar copies the metadata onto the order;
4. passes `returnPath` as `return_url`, so Polar shows a back button to it, and `successPath` in the buyer's language (`localizePathname`) as the success URL, with `checkoutId={CHECKOUT_ID}` before the path's own search params. Polar replaces `{CHECKOUT_ID}` (`POLAR_CHECKOUT_ID_PLACEHOLDER`) with the checkout ID;
5. lets the buyer enter Polar's discount codes and charges the product's price in Polar, unless the caller passes its own terms (`allow_discount_codes`, `metadata` and `prices`), and returns `{ checkoutId, url }`.

`startCheckout` in `src/modules/order/use-cases/start-checkout.ts` is the server function that starts a checkout for any Polar product. Its input, `orderZodSchemas.startCheckout` (`Order["startCheckout"]`), takes the product's Polar ID as a UUID, and both paths validated with `callbackPathSchema`, so that they stay on the site. It runs `authorized()`, so only a signed-in account buys, and refuses with `FORBIDDEN`, without asking Polar, a product that a feature sells through a checkout of its own: `hasOwnCheckout` reads `PRODUCTS_WITH_OWN_CHECKOUT`, whose one element is the licence's `POLAR_PRODUCT_IDS`. The licence's own `startCheckout` checks the account's licence, prices the tier and then calls `createCheckout` with its terms ([Licences](/docs/features/licences#starting-the-checkout)). No page of this site offers another product yet.

Both server functions run `withRateLimit(CHECKOUT_RATE_LIMIT_KIND, CHECKOUT_RATE_LIMIT)` before `authorized()`, which allows <RepositoryFact name="checkoutsPerMinute" /> checkouts a minute per client, whichever of the two starts them: each one is a request to Polar's API with the organisation's token, whose rate limit every buyer shares.

## Webhooks

Polar posts to `/api/auth/polar/webhooks`. The plugin verifies the signature with `POLAR_WEBHOOK_SECRET` and passes each event to `handlePolarEvent` in `src/integrations/polar/polar.webhooks.ts`. `POLAR_EVENT_HANDLERS` in the same file lists the code each event reaches, and each element names the events it handles and the function that handles them:

```ts title="src/integrations/polar/polar.webhooks.ts"
export interface PolarEventHandler {
  readonly events: readonly models.WebhookEventType[]
  readonly handle: (event: webhooks.WebhookPayload) => Promise<void>
}
```

- `handlePolarEvent` runs the `handle` of every element that lists the event's type, all at once, and waits for all of them.
- When one rejects, `handlePolarEvent` still waits for the others to finish, so no handler stops halfway through its writes, and then rejects with an `AggregateError` of every failure. The plugin answers 500 and Polar delivers the event again later, so each handler must be safe to run twice for the same event. Polar disables an endpoint that keeps failing, and `polar:verify` reports a disabled endpoint.
- An event that no element lists is acknowledged and goes nowhere.
- `POLAR_EVENTS` joins the events of every element, sorted and each once. The webhook endpoint in Polar must send exactly these, and `polar:verify` compares them.
- The first two elements copy orders and subscriptions into D1 for the events in `ORDER_WEBHOOK_EVENTS` (`order.constants.ts`) and `SUBSCRIPTION_WEBHOOK_EVENTS` (`subscription.constants.ts`) (see [Writing the copies](#writing-the-copies)), and the third grants and revokes licences for those in `LICENSE_WEBHOOK_EVENTS` (see [Licences](/docs/features/licences#webhooks-and-licences)). A project without the licence or without the order copies loses the element that names their files.

`polar:verify` runs in Bun, outside the Worker, and reads `POLAR_EVENTS`, so `polar.webhooks.ts` imports only constants. A handler loads its code when an event arrives:

```ts title="src/integrations/polar/polar.webhooks.ts"
const { licenseWebhookHandlers } = await import("~/src/modules/license/license.webhooks")
```

`src/integrations/polar/__test__/polar.webhooks.test.ts` imports `polar.webhooks.ts` in Bun and fails when that import reaches the Worker's runtime.

## Orders and subscriptions in D1

The polar area keeps copies of Polar's orders and subscriptions in two D1 tables, `order` (`src/modules/order/`) and `subscription` (`src/modules/subscription/`), so that lists, searches and access checks can read them with SQL and keep working while Polar is slow. Polar stays the source: each row is Polar's record under Polar's ID, written only from Polar's webhooks and never edited by hand. [Modules](/docs/conventions/modules#tables-that-mirror-a-provider) gives the rules every such mirror table follows.

| Table          | Columns                                                                                                                                                                                                                                                                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `order`        | `id`, `user_id`, `customer_id`, `product_id`, `subscription_id`, `status` (`ORDER_STATUSES`), `currency`, `total_amount`, `refunded_amount`, `invoice_number`, `discount_id`, `discount_code`, `discount_name`, `discount_amount`, `billing_country`, `description`, `placed_at`, `changed_at`      |
| `subscription` | `id`, `user_id`, `customer_id`, `product_id`, `product_name`, `status` (`SUBSCRIPTION_STATUSES`), `amount`, `currency`, `recurring_interval` (`SUBSCRIPTION_RECURRING_INTERVALS`), `recurring_interval_count`, `current_period_end`, `cancel_at_period_end`, `started_at`, `ended_at`, `changed_at` |

- `id`, `customer_id`, `product_id` and `subscription_id` are Polar's IDs, and every column copied from Polar takes Polar's field name. `subscription_id` has no foreign key, because Polar's events can arrive in any order.
- `user_id` links the account and stays empty for a customer without one. Deleting an account keeps its orders and subscriptions and empties their `user_id` (`ON DELETE SET NULL`).
- Amounts are in the currency's minor units, as Polar sends them. `description` is what the order bought, as Polar invoiced it, and `product_name` the name of the subscription's product as Polar last reported it.
- `discount_id`, `discount_code` and `discount_name` are the discount Polar applied, from the order's `discount_id` and its `discount`, and `discount_amount` what it took off the subtotal; `billing_country` is the country of the order's billing address, as an ISO 3166-1 alpha-2 code. They are empty for an order without a discount or a billing address, and `discount_amount` is empty only for an order copied before these columns existed (see [Orders and customers](/docs/features/orders#discounts-and-billing-countries-of-older-orders)).
- `placed_at` is when Polar created the order. `changed_at` is the version of Polar's record that the row holds: Polar's `modified_at`, or Polar's `created_at` for a record that never changed. The row's own `created_at` and `updated_at` record when D1 wrote it.
- The indexes serve the lists these copies exist for: `order_user_placed_at_idx` an account's orders and `order_status_placed_at_idx` the orders of a status, both by when they were placed; `subscription_user_status_idx` an account's subscriptions by status and `subscription_status_current_period_end_idx` the subscriptions of a status by the end of their period.
- `status` holds Polar's value as it is, `trial_ended` included, which Polar sets when a trial ends without a payment. Nothing grants access from a subscription's status yet; a check that does counts only `trialing` and `active` as a running subscription, so `trial_ended`, `past_due` and the other statuses never pass for one.

### Writing the copies

The first two elements of `POLAR_EVENT_HANDLERS` (see [Webhooks](#webhooks)) each load their use case when an event arrives:

| Events                                                           | Use case                                                                            |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `order.created`, `order.updated`, `order.paid`, `order.refunded` | `recordOrder` in `src/modules/order/use-cases/record-order.ts`                      |
| `subscription.created`, `subscription.updated`                   | `recordSubscription` in `src/modules/subscription/use-cases/record-subscription.ts` |

- Each use case takes Polar's record, `models.Order` or `models.Subscription`, and writes it in one statement: an insert under Polar's ID that, when the row already exists, updates it only if the stored `changed_at` is not later than the record's. A newer version applies, an older one that arrives late changes nothing, and the same version delivered twice is written again with the same values. Of two different states with the same `modified_at`, the one written last stays until Polar changes the record again.
- `recordOrder` takes the discount and the billing country from `polarOrderTerms` (`src/modules/order/order.polar.ts`), which `scripts/backfill-order-terms.ts` uses too. A later version without a billing address keeps the country already copied.
- The same statement fills `user_id` through `polarCustomerAccount` in `src/integrations/polar/polar.customers.ts`: the account whose ID is the customer's `external_id`, which `createCheckout` sets on every checkout ([Checkout](#checkout)). It stays empty when the customer has no `external_id` or when no account has that ID, for instance because the account was deleted.
- The licence handles `order.paid` and `order.refunded` too. The copy takes them as well, so it holds the payment and the refund whether or not Polar also sends `order.updated` for them. `handlePolarEvent` runs both handlers at once; when the copy fails, the delivery answers 500, and Polar's retry repeats both writes without changing what one of them already wrote.
- The admin dashboard reads the order copies to list the paid licence orders that have no licence (see [Licences](/docs/features/licences#orders-that-match-no-account)) and to total the revenue (see [Revenue on the dashboard](#revenue-on-the-dashboard)); no page reads the subscription copies yet.

## Customer portal

`ROUTES.API_AUTH_CUSTOMER_PORTAL` (`/api/auth/customer/portal`) opens the Polar customer portal of the signed-in account. The licence card on `/app/license` links to it.

## Revenue on the dashboard

The `order` permission statement (`read`, `update`, `refund`) is in `APP_STATEMENTS` (`src/integrations/better-auth/auth.access.ts`), and the payments area adds the **Revenue** panel to the dashboard as an entry of `DASHBOARD_PANELS` (`custom/admin/dashboard/panels.tsx`). Its query, `getRevenue` in `src/modules/order/use-cases/get-revenue.ts`, checks `order: ["read"]` and totals the paid order copies of a period per currency, refunds subtracted; [Admin dashboard](/docs/features/admin-dashboard#revenue) describes what it counts. The licence area's `get-unlicensed-orders` checks `order: ["read"]` too. [Orders and customers](/docs/features/orders) describes the admin screens that read the copies. No use case updates or refunds orders yet: refunds and payouts are done in Polar.
