---
title: "Moduli"
description: "Un modulo è una tabella del database: il suo schema, le costanti, gli schemi Zod, l'interfaccia dei tipi, i casi d'uso e i pochi file dedicati di cui una tabella può avere bisogno."
---

`src/modules/<table>/` esiste solo per una tabella reale del database. La cartella rispecchia lo schema Drizzle, quindi crearne una equivale ad affermare che esiste una tabella. Il codice che serve una funzionalità senza una tabella propria va altrove: una server function che legge da GitHub o dalla raccolta della documentazione si trova in `src/lib/<topic>.ts` o nell'unica route che la usa, e la configurazione di un fornitore si trova in `src/integrations/<vendor>`.

I moduli sono `account`, `category`, `chapter`, `course`, `lesson`, `lesson-progress`, `license`, `newsletter-subscriber`, `order`, `product`, `rate-limit`, `session`, `subscription`, `two-factor`, `user`, `verification` e `video`. `license` possiede due tabelle, `license` e `revoked_license_order`. `_core` non è un modulo: contiene i codici di errore, i cataloghi e i campi Zod che tutti i moduli condividono.

## Anatomia

`src/modules/course` è il riferimento. Un modulo contiene questi file, tutti con il nome della tabella:

| File                         | Contiene                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `<table>.schema.ts`          | La tabella Drizzle, i suoi indici e le relazioni                                                           |
| `<table>.constants.ts`       | Oggetti dei valori di dominio, le loro tuple enum, chiavi di query, chiavi di mutation e limiti del modulo |
| `<table>.zod.ts`             | Uno schema di input per operazione, esportati come un unico oggetto `<table>ZodSchemas`                    |
| `<table>.types.ts`           | Un'interfaccia con il nome del modulo                                                                      |
| `<table>.utils.ts`           | Helper per la tabella, puri e sicuri nel browser a meno che non leggano l'ambiente del Worker              |
| `<table>.<concern>.ts`       | Un ulteriore aspetto della tabella, come `lesson.access.ts` o `video.delivery.ts`                          |
| `use-cases/<verb>-<noun>.ts` | Un'operazione, con il nome della sua server function                                                       |
| `__test__/`                  | Test e fixture per i file precedenti                                                                       |

## Schema

```ts
export const course = sqliteTable(
  "course",
  {
    id: text("id").primaryKey(),
    kind: text("kind", { enum: COURSE_KINDS }).notNull().default(COURSE_KIND.COURSE),
    position: integer("position").notNull().default(0),
    slug: text("slug", { length: SLUG_MAX_LENGTH }).notNull().unique(),
    status: text("status", { enum: COURSE_STATUSES }).notNull().default(COURSE_STATUS.DRAFT),
    summary: text("summary", { mode: "json" }).$type<LocalizedText>().notNull(),
    title: text("title", { mode: "json" }).$type<LocalizedText>().notNull(),
    ...timestamps(),
  },
  (table) => [index("course_status_position_idx").on(table.status, table.position)],
)
```

- Le colonne sono in camelCase in TypeScript e in snake_case in SQL. Le chiavi sono ordinate, come richiede il linter, con `...timestamps()` come ultima voce.
- `createdAt` e `updatedAt` provengono da `timestamps()` in `src/integrations/drizzle-orm/drizzle.columns.ts`: millisecondi, riempiti da SQLite all'inserimento, con `updatedAt` aggiornato a ogni modifica. Non scriverli mai a mano. `lesson_progress` ha bisogno solo del secondo, quindi usa `updatedAt: timestamps().updatedAt`. Due tabelle non hanno timestamp: `rate_limit` contiene contatori di breve durata che hanno un proprio `expiresAt` e cambiano a ogni richiesta, e `revoked_license_order` registra una sola volta ogni ordine Polar rimborsato, tramite il suo ID.
- Le chiavi primarie sono testuali. Un caso d'uso che inserisce una riga riempie la chiave con un UUID v7 (`v7()` da `uuid`); una [tabella specchio di un provider](#tables-that-mirror-a-provider) prende invece l'ID del provider.
- Le colonne enum ricevono una tupla costruita dall'oggetto costante del modulo, mai un elenco di letterali. La tupla sta accanto all'oggetto in `<table>.constants.ts`, perché la leggono anche gli schemi Zod e il browser, e quel file non importa nulla da Drizzle.
- Il testo che un visitatore legge in più lingue è una colonna JSON `LocalizedText`, validata da `localizedTextSchema` e letta con `localize(text, locale)` da `src/modules/_core/utils/localized-text.ts`.
- Una nuova tabella viene riesportata da `src/integrations/drizzle-orm/drizzle.schemas.ts`, e la sua migrazione viene generata con `bun run db:generate`. Vedi [Migrazioni del database](/docs/guides/database-migrations).

## Tabelle specchio di un provider [#tables-that-mirror-a-provider]

`order` e `subscription` contengono copie degli ordini e degli abbonamenti di Polar, scritte solo a partire dai dati di Polar e mai modificate a mano. Una tabella specchio segue il provider dove le regole precedenti non lo farebbero:

- La sua chiave primaria è l'ID del provider, una colonna di testo di lunghezza `POLAR_ID_MAX_LENGTH`, e le sue colonne prendono i nomi dei campi del provider, come `customer_id`, `product_id` e `subscription_id`. Una nostra tabella che punta al provider antepone invece un prefisso al nome, come fa `license.polar_order_id`.
- Gli istanti propri del provider stanno accanto a `...timestamps()`. `placedAt` indica quando Polar ha creato l'ordine, e `changedAt` la versione del record di Polar contenuta nella riga: il suo `modified_at`, oppure il suo `created_at` finché non è mai cambiato. `createdAt` e `updatedAt` registrano comunque quando D1 ha scritto la riga.
- Le colonne enum ricevono tuple dei valori del provider: `ORDER_STATUSES` in `order.constants.ts` elenca `POLAR_ORDER_STATUS` da `src/integrations/polar/polar.constants.ts`, e un test dei tipi fallisce quando l'SDK nomina un valore che manca nella tupla.
- Nessuna colonna ha un valore predefinito oltre a `createdAt` e `updatedAt`, perché ogni valore arriva dal provider.
- `user_id` è `ON DELETE SET NULL`: eliminare un account conserva i suoi ordini e abbonamenti e rimuove solo il collegamento.

`order` è una parola chiave SQL. Drizzle mette tra virgolette ogni identificatore, quindi le sue query non richiedono altro; l'SQL grezzo nomina la tabella tramite l'oggetto dello schema, come `${order}` dentro un template `sql`, mai come un semplice `order`.

## Costanti

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const

export const COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const

export const COURSE_STALE_MS = 60_000

export const COURSE_SHOWCASE = {
  COURSES: 2,
  LESSONS: 6,
} as const

export const COURSE_QUERY_KEYS = {
  ALL: ["course"],
  CATALOGUE: ["course", "catalogue"],
  DETAIL: ["course", "detail"],
  EDITOR: ["course", "getCourseEditor"],
  LIST: ["course", "getCourses"],
  SHOWCASE: ["course", "showcase"],
} as const

export const COURSE_MUTATION_KEYS = {
  CREATE: ["course", "createCourse"],
  DELETE: ["course", "deleteCourse"],
  MOVE: ["course", "moveCourse"],
  UPDATE: ["course", "updateCourse"],
} as const
```

- Ogni chiave di query inizia con il prefisso `ALL` del modulo, quindi un solo `invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL })` aggiorna tutto ciò che il modulo fornisce. Vedi [Recupero dei dati e caching](/docs/conventions/data-fetching).
- Le chiavi di mutation sono il nome del modulo e il nome della server function.
- Le lunghezze delle colonne e degli input ricevono un nome qui e sono condivise dallo schema e dallo schema Zod, come `PRODUCT_NAME_MAX_LENGTH` in `product.constants.ts`.
- `<MODULE>_VALIDATION_PARAMS` contiene i numeri che i messaggi di validazione interpolano, come `{ slugTooLong: { max: SLUG_MAX_LENGTH } }`.
- `scripts/repository-facts.ts` legge alcuni file di costanti, come `license.constants.ts`, mentre Vite carica la sua configurazione, quando l'alias `~` non si risolve ancora. Un file del genere importa gli altri file sorgente con un percorso relativo, come `license.constants.ts` importa `POLAR_WEBHOOK_EVENT` da `../../integrations/polar/polar.constants.ts`; gli import di soli tipi vengono rimossi e possono mantenere l'alias.

## Schemi Zod

```ts title="src/modules/course/course.zod.ts"
import zod from "zod/v4"

import { MOVE_DIRECTIONS } from "~/src/modules/_core/constants/ordering"
import { localizedTextSchema } from "~/src/modules/_core/utils/localized-text"
import { paginationSchema } from "~/src/modules/_core/utils/pagination"
import { idField, localeField, slugField } from "~/src/modules/_core/utils/zod-fields"
import { COURSE_KINDS, COURSE_STATUSES } from "~/src/modules/course/course.constants"

const courseIdInput = zod.object({
  courseId: idField,
})

const courseFields = zod.object({
  kind: zod.enum(COURSE_KINDS),
  slug: slugField,
  status: zod.enum(COURSE_STATUSES),
  summary: localizedTextSchema,
  title: localizedTextSchema,
})

const createCourse = courseFields

const deleteCourse = courseIdInput

const getCatalogue = zod.object({
  locale: localeField,
})

const getCourse = zod.object({
  locale: localeField,
  slug: slugField,
})

const getCourseEditor = courseIdInput

const getCourseShowcase = zod.object({
  locale: localeField,
})

const getCourses = paginationSchema

const moveCourse = courseIdInput.extend({ direction: zod.enum(MOVE_DIRECTIONS) })

const updateCourse = courseFields.extend(courseIdInput.shape)

export const courseZodSchemas = {
  createCourse,
  deleteCourse,
  getCatalogue,
  getCourse,
  getCourseEditor,
  getCourseShowcase,
  getCourses,
  moveCourse,
  updateCourse,
}
```

- `<table>.zod.ts` importa `zod from "zod/v4"` ed esporta un unico oggetto le cui chiavi sono i nomi delle operazioni.
- I form validano con gli stessi schemi nel browser, quindi `<table>.zod.ts` non importa nulla da Drizzle né da un `.schema.ts`. Le tuple enum e le lunghezze vengono da `<table>.constants.ts`, importato anche dalla tabella, così la colonna e lo schema condividono un'unica definizione. La build client fallisce quando `drizzle-orm` arriva nel browser; vedi [Tieni l'ORM fuori dal browser](/docs/conventions/performance#keep-the-orm-out-of-the-browser).
- Nessuno schema Zod è derivato dalla tabella: nulla valida una riga intera a runtime, e i tipi delle righe nell'interfaccia del modulo vengono da `$inferSelect` e `$inferInsert`.
- I campi provengono da `src/modules/_core/utils/zod-fields.ts` (`idField`, `localeField`, `slugField`) e da frammenti condivisi nello stesso file, mai dichiarati di nuovo per ogni schema.
- Gli elenchi paginati riusano `paginationSchema`; le operazioni su un singolo record ricevono un oggetto come `{ courseId }`, mai una stringa semplice.
- I messaggi di errore sono chiavi di traduzione (`{ message: "slugInvalid" }`), rese dal namespace `<table>.validations` del modulo. Vedi [Form e tabelle](/docs/conventions/forms-and-tables).

## L'interfaccia del modulo

`<table>.types.ts` esporta esattamente un'interfaccia, con il nome del modulo, le cui chiavi rispecchiano l'oggetto Zod:

```ts
export interface Lesson {
  select: typeof lesson.$inferSelect
  insert: typeof lesson.$inferInsert
  createLesson: zod.input<typeof lessonZodSchemas.createLesson>
  deleteLesson: zod.input<typeof lessonZodSchemas.deleteLesson>
  getLessonPlayback: zod.input<typeof lessonZodSchemas.getLessonPlayback>
  moveLesson: zod.input<typeof lessonZodSchemas.moveLesson>
  updateLesson: zod.input<typeof lessonZodSchemas.updateLesson>
}
```

Server function, opzioni di mutation e form tipizzano il proprio input come `Lesson["createLesson"]`. Quando aggiungi uno schema a `<table>.zod.ts`, aggiungi qui la sua chiave nella stessa modifica. Non ricavare mai un tipo di input con `Parameters<typeof fn>[0]`, e non dichiarare mai un alias locale o una seconda interfaccia `LessonInput`. Quando i componenti hanno bisogno della forma restituita da una lettura, anche questa ha un nome nell'interfaccia, ricavato dalla server function: `Course["listRow"]` è `Awaited<ReturnType<typeof getCourses>>["rows"][number]`.

## Casi d'uso

Ogni file in `use-cases/` contiene un'operazione, con il nome della sua server function in kebab-case: `get-course-editor.ts` esporta `getCourseEditor` e `courseEditorQuery`, `update-course.ts` esporta `updateCourse` e `updateCourseMutation`. Il pattern, il suo middleware e i suoi errori sono descritti in [Server function ed errori](/docs/conventions/server-functions).

Un caso d'uso che viene eseguito solo sul server, chiamato da un hook di Better Auth o da un webhook di Polar anziché dal browser, è una semplice funzione `async` in un file che inizia con `import "@tanstack/react-start/server-only"`, come `license/use-cases/grant-license.ts` e i mittenti delle email `send-verify-email.ts`, `send-reset-password-email.ts` e `send-change-email-confirmation-email.ts`.

## File dedicati

Quando una tabella ha bisogno di logica che non è né un caso d'uso né un helper puro, riceve un file per ogni aspetto, chiamato `<table>.<concern>.ts`:

| File                                                    | Aspetto                                                                                |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `lesson/lesson.access.ts`                               | Chi può guardare una lezione; puro, usato sul server e nei test                        |
| `lesson/lesson.viewer.ts`                               | Risolve sul server lo spettatore che ha effettuato l'accesso e il suo accesso ai corsi |
| `license/license.webhooks.ts`                           | Handler dei webhook di Polar, chiamati da `license.polar-events.ts`                    |
| `license/license.api.ts`                                | Gli handler dell'API delle licenze della CLI, serviti da `src/routes/api/cli.v1.*.ts`  |
| `license/license.bundles.ts`                            | Firma degli URL dei bundle di template della CLI; chiavi dei loro oggetti              |
| `license/license.delivery.ts`                           | L'handler del Worker per le richieste `/bundles/` firmate                              |
| `license/license.ppp.ts`                                | Sconti di prezzo regionali per il checkout                                             |
| `license/license.pricing.ts`                            | Fasce dei prezzi regionali e cookie di rinuncia; puro                                  |
| `newsletter-subscriber/newsletter-subscriber.server.ts` | Controlli delle richieste solo lato server                                             |
| `video/video.delivery.ts`                               | L'handler del Worker per le richieste `/media/` firmate                                |
| `video/video.playback.ts`, `video/video.files.ts`       | Firma degli URL di riproduzione; chiavi degli oggetti e content type                   |

Un file che non deve mai finire nel bundle del browser inizia con `import "@tanstack/react-start/server-only"`, come fanno `lesson.viewer.ts`, `license.webhooks.ts`, `license.api.ts`, `license.delivery.ts`, `newsletter-subscriber.server.ts`, `video.delivery.ts` e `license.utils.ts` (che legge gli ID dei prodotti Polar, `POLAR_PRODUCT_IDS`, dall'ambiente del Worker). I file puri come `lesson.access.ts` e `course.utils.ts` non importano nulla di lato server, quindi componenti e test possono usarli.
