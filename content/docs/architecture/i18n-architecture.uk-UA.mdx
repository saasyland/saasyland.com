## Локалі та URL-адреси

Кількість локалей, які обслуговує SaaSy Land: <RepositoryFact name="languages" />. Це <RepositoryFact name="supportedLocales" />, а типова з них — `en-US`. Типова локаль не має префікса (`/docs`); кожна інша локаль використовує свій повний тег (`/pl-PL/docs`). Worker перенаправляє префікси, що містять лише мову, і префікси типової локалі, як-от `/pl/docs` чи `/en-US/docs`, на канонічну URL-адресу.

`getCurrentLocale()` — ізоморфна функція, яка з обох боків читає локаль зі шляху URL і повертає `en-US`, коли шлях не має префікса локалі. URL-адреси `/api` і серверних функцій ніколи його не мають, тож на сервері для таких запитів вона повертає `en-US`. Worker синхронізує cookie локалі з URL-адресою сторінки, але жоден код не вибирає локаль за cookie. Серверні функції, які повертають локалізований вміст, отримують локаль як вхідний параметр, а листи автентифікації читають її з `callbackURL` сценарію.

## Повідомлення

Переклади лежать у `messages/<locale>/<namespace>.json`. Назва файлу — це простір імен, наприклад `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` або `common`. Простори імен із крапками об'єднуються в одне дерево повідомлень, тож `useTranslations("pages.admin.users")` читає `pages.admin.users.json`. Кожен простір імен сторінки має `metadata.title` і `metadata.description` для тегів head. Повідомлення — це звичайний JSON без згенерованих типів.

## Завантаження

- **Кореневі простори імен** (`common`, `components.*`, `errors*`) попередньо завантажуються в кореневому `beforeLoad`.
- **Маршрути сторінок** оголошують `const NAMESPACE = "pages.x"`, попередньо завантажують його в loader-функції та вказують у `staticData.namespaces`.
- **Маршрути макетів** оголошують `const NAMESPACES = [...] as const` і роблять те саме.
- **`TranslationsProvider`** обгортає тіло документа в кореневій оболонці. Він поєднує кореневі простори імен зі `staticData.namespaces` зіставлених маршрутів і передає результат в `IntlProvider`, тож перекладено кожен екран, включно з екранами помилок.
- **Листи** завантажують свій простір імен на сервері через `loadNamespace` у сценарії використання, який їх надсилає.

## Посилання

Посиланням роутера не потрібна обробка локалі: `<Link to={ROUTES.SIGN_IN}>` отримує префікс від `rewrite` роутера. Сира URL-адреса в поточній локалі, як-от `callbackURL` для Better Auth, теж надходить від роутера, який застосовує той самий rewrite і серіалізує параметри пошуку (`useAuthRedirect` у `src/hooks/use-auth-redirect.ts`):

```ts
const { publicHref: callbackURL } = router.buildLocation({ search: { redirect }, to: ROUTES.AUTH_CALLBACK })
```

`localizePathname({ locale, pathname })` будує URL-адресу для заданої локалі: посилання перемикача локалі й посилання в листах, які сервер будує без роутера.

Перемикач локалі рендерить звичайне посилання на той самий шлях у кожній локалі, тож зміна мови завантажує новий документ.

## Переклади в компонентах

Компонент викликає `useTranslations` рівно один раз і називає функцію перекладу `t`. Після кожного наступного виклику `useTranslations` i18n-ally змінює область усіх подальших викликів `t()`, а `bun run check:i18n` завершується помилкою на ключах, які не розв'язуються у своїй області. Компонент, якому потрібні два непов'язані простори імен, використовує їхній спільний батьківський простір імен або `useTranslations()` з повними ключами.

`bun run check:i18n` запускає три скрипти: `check-i18n.ts` (паритет ключів між локалями, розв'язання ключів у їхній області та ключі, які не рендерить жоден файл вихідного коду), `check-message-formats.ts` (синтаксис повідомлень ICU) і `check-content.ts` (паритет документації та блогу між локалями).
