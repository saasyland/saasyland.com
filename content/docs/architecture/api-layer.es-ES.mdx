---
title: "Handlers HTTP de TanStack Start"
description: "Los endpoints HTTP bajo /api y cuándo conviene añadir uno en lugar de una función de servidor."
---

Las operaciones propias de la aplicación son funciones de servidor. Los handlers HTTP existen solo donde algo ajeno al cliente RPC de la aplicación llama a una URL: el cliente de navegador de Better Auth, los proveedores OAuth, los webhooks de Polar y el buscador de la documentación.

| Archivo                    | Ruta          | Métodos   | Gestiona                                                                                                                                                     |
| -------------------------- | ------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `src/routes/api/index.ts`  | `/api`        | GET       | Una respuesta de estado en JSON `{ runtime: "cloudflare-workers" }`                                                                                          |
| `src/routes/api/auth.$.ts` | `/api/auth/*` | GET, POST | Todos los endpoints de Better Auth, incluidos los callbacks de OAuth, la verificación de correo, el portal de clientes de Polar y `/api/auth/polar/webhooks` |
| `src/routes/api/search.ts` | `/api/search` | GET       | La búsqueda de Fumadocs en la documentación                                                                                                                  |

Un handler se declara con `server.handlers` en `createFileRoute`. Recibe la `Request` estándar de la Web y devuelve una `Response`:

```ts
import { createFileRoute } from "@tanstack/react-router"

import { auth } from "~/src/integrations/better-auth/auth.server"

export const Route = createFileRoute("/api/auth/$")({
  server: { handlers: { GET: ({ request }) => auth.handler(request), POST: ({ request }) => auth.handler(request) } },
})
```

## Reglas

- No añadas un endpoint REST para una operación a la que solo llama esta aplicación. Escribe en su lugar un caso de uso con `createServerFn`, que obtiene entrada tipada, middleware y opciones de consulta.
- Un handler valida su entrada y comprueba los permisos por su cuenta. El middleware de las funciones de servidor (`authorized`, `withRateLimit`) no se ejecuta en los handlers.
- La verificación específica de cada proveedor se queda en su integración. Las firmas de los webhooks de Polar las verifica el plugin de Polar dentro de Better Auth, no un handler propio.
- Las rutas de `/api` nunca se localizan, nunca se prerenderizan y quedan fuera de la gestión del locale que hace el Worker.
