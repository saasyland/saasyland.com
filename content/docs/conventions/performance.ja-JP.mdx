このページのルールはどれも計測から生まれたもので、いくつかは、かえって状況を悪化させた直感的な修正を置き換えたものです。これらのルールの背後にあるコードを変更するのは、それを上回る新しい計測結果がある場合だけにしてください。

## 主張する前に計測する

- 同じページで以前のビルドと新しいビルドを比較します。それぞれ少なくとも 5 回ずつ交互に Lighthouse を実行し、中央値を比較します。1 回の実行では何も証明できません。マシンのノイズにより、およそ 5 回に 1 回は外れ値が出ます。
- PageSpeed Insights の 1 回の実行で変更を判断してはいけません。同じデプロイでも、テストを実行するマシンの速度によってスコアは大きく変わります。Lighthouse はその速度を `benchmarkIndex` として報告します。
- 本番ビルド（`bun run build:test` の後に `bun run start:test`）を、圧縮を有効にした HTTP/2 で配信して計測します。圧縮なしの素のローカル HTTP/1.1 では、Lighthouse のネットワークシミュレーションが、本番では決して起こらない接続と転送サイズを前提に計算してしまいます。
- Lighthouse の診断はスコアではありません。以下のセクションで示すように、「強制リフロー」や「適切なサイズの画像」のようなヒントが、そのページにとっては誤りである場合があります。対応する前に、スコアに反映される指標を確認してください。

## Worker の起動グラフを小さく保つ

`src/server.ts` はすべての HTML リクエストで実行され（`wrangler.jsonc` の `run_worker_first`）、静的にインポートしたものはすべて、コールドスタートのたびに評価されます。そのため、定数と純粋なヘルパーだけをインポートし、それ以外はリクエストが必要としたときに読み込みます。

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

以前、Polar のクライアントもインポートしていたモジュールからヘッダー名を 1 つ静的にインポートしただけで、約 1.4 MB の SDK がすべてのコールドスタートに読み込まれ、ランディングページの最初の 1 バイトが届くまでに最大 1.4 秒かかったことがあります。`COUNTRY_HEADER` と `IP_ADDRESS_HEADER` が、重いものを何もインポートしない `src/modules/_core/constants/api.ts` にあるのはそのためです。`server.ts` に静的インポートを追加する前に、そのインポートの連鎖をたどってください。`polar`、`drizzle-orm`、`resend` に到達するものはすべて退行です。

## プリレンダリングされたページは CSS とフォントを先に読み込む

公開ページはプリレンダリングされており、最初の描画に JavaScript を必要としません。TanStack Start は、ページが必要としうるすべてのチャンクに対して `modulepreload` ヒントを出力し、ランディングページではその数が 100 を超えます。シミュレートされたモバイルネットワークでは、これらがスタイルシートやフォントと帯域を奪い合います。すべてのビルドスクリプトが実行する `scripts/optimize-prerendered-html.ts` は、依存関係のヒントをすべて削除し、ページ自身のエントリースクリプトのヒントだけを `fetchpriority="low"` で残します。

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

ヒントを削除したことで First Contentful Paint は約 3 分の 1 短くなり、エントリーのヒントを低い優先度で残したことで、モバイルの First Contentful Paint がさらに 375 ms 短くなりました。依存関係のものでもルートのチャンクのものでも、プリロードヒントを戻してはいけません。このスクリプトは、削除するヒントや残すヒントが見つからない場合にビルドを失敗させます。そのため、ビルド出力が変わっても、この最適化が気づかないうちに元に戻ることはなく、確実に検出されます。

`robots.txt` と `llms.txt` は `public/` にある静的ファイルで、Worker を経由しません（`run_worker_first` の `"!/robots.txt", "!/llms.txt"`）。Lighthouse はどちらも 2 秒のタイムアウトで取得するため、Worker の応答が遅いと SEO とエージェント対応の監査で不合格になっていました。

## プロバイダーはルートの outlet を包まない

TanStack Router はルートの outlet を Suspense 境界で包み、React はそれらの境界を後から小さな単位で少しずつハイドレーションします。その上にあるコンテキストプロバイダーの値がハイドレーション直後に変わると、React はその下にあるすべてを一度にハイドレーションせざるを得なくなります。

- アプリケーション全体を包む `ThemeProvider` によって、ランディングページのハイドレーションが、入力をブロックする 200 ms の 1 つのタスクになっていました。利用する 2 つのコンポーネント、`Toaster` とドキュメントの `ThemeSwitch` の周りにマウントしたところ、Total Blocking Time は約 150 ms から 10 ms 未満になりました。
- ルートの outlet の上にある `MotionProvider` は、アニメーション機能の読み込みが終わると新しいコンテキストを公開します。ブログ記事では、ページがまだコンテンツを読み込んでいる最中にその更新が届き、React がクライアントレンダリングにフォールバックして、レイアウトがずれました。

`__root.tsx` やレイアウトにプロバイダーを追加する前に、その値がハイドレーション後に変わりうるかを確認してください。変わりうる場合は、すべてのルートの `<Outlet />` より下で、それを読み取るコンポーネントのそばにマウントします。配置の一覧は[コンポーネントとスタイリング](/docs/conventions/components)にあります。

## Tailwind のビルドは 1 つ

Tailwind を実行するのは `src/presentation/styles/globals.css` だけです。`docs.css` や `typeset.css` のようなルートのスタイルシートは素の CSS で、Fumadocs 自身のスタイルは `globals.css` を通して読み込みます。

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

以前、ルートのスタイルシートで 2 つ目の Tailwind ビルドを行った結果、独自の `.hidden`、`.rounded-md`、テーマ変数が出力されたことがあります。同じ名前のカスケードレイヤーはスタイルシートをまたいでマージされ、React は `precedence` 付きで挿入したスタイルシートを決して削除しません。そのため、ドキュメントを一度訪れると、ランディングページはリロードするまでレスポンシブなレイアウトとフォントを失いました。`e2e/specs/navigation.spec.ts` の E2E テスト「landing keeps its responsive styles after visiting the docs」がこれを防いでいます。Tailwind が必要なものはすべて `globals.css` を通します。

## メディア

- **ランディングページのループ動画。** 各 `src/presentation/assets/motion/<name>.webm` には、動画とまったく同じ寸法（`concept-loop.tsx` の `LOOPS` の `size`）のポスター `<name>.webp` があるため、ポスターから動画に切り替わるときに画像が目に見えて鮮明になることはありません。より小さい幅は別ファイルの `<name>-<width>.webp` で、ポスターの `srcSet` を通して提供します。フルサイズのポスターを縮小してはいけません。軽くしたい場合は、同じ寸法で再エンコードします。動画は `preload="none"` で読み込み、4 分の 1 が表示されている間だけ再生し、モーションを減らす設定の読者には決して再生しません。
- **コースツアー**（`course-showcase.tsx`）はループ動画ではありません。`<video>` は訪問者が再生を押してから初めてレンダリングされるため、それまでページが読み込むのはポスターだけです。ポスターは、動画と同じ 1600 ピクセル幅と 800 ピクセル幅の AVIF と WebP のソースを持つ `<picture>` です。動画そのものは WebM で配信し、MP4 をフォールバックにしています。
- **コースの動画**は、事前にアダプティブ HLS にエンコードし、Workers のキャッシュを使って R2 から配信します。[動画](/docs/features/videos)を参照してください。
- **スクロールに連動する動画。** 現在のサイトにはありません。再生位置がスクロール位置に追従する動画は、オールイントラ（すべてのフレームをキーフレームにする、`keyint=1`）でエンコードしなければなりません。通常のエンコードではシークに約 200 ms かかりますが、オールイントラでは約 3 ms です。200 ms かかるシークは、JavaScript でどれだけ滑らかにしてもスクラブ再生にはなりません。

## スクロールで表示する

`Reveal`（`src/presentation/components/custom/landing-page/components/reveal.tsx`）は、ランディングページのセクションがビューポートに入るとフェードインさせます。すべてのインスタンスで 1 つの `IntersectionObserver` を共有し、オブザーバーの最初のコールバックで要素がファーストビューより下から始まるかを判断し、React の状態も再レンダリングも使わずに `data-reveal` 属性を直接書き込みます。表示状態を React の状態に保持していたバージョンでは、すべてのセクションが再レンダリングされてページのレイアウトが 2 回行われたため、Total Blocking Time が 2 倍になりました。状態に戻してはいけません。また、比較せずに置き換えてもいけません。

ほかに 2 つの最適化を計測し、不採用にしました。ランディングページのセクションに `content-visibility: auto` を指定する方法は、ページ下部のセクションへのページ内リンクを壊しました。ニュースレターのフォームを遅延読み込みする方法は、直接描画する場合と同じか、より悪いスコアでした。
