Ejecuta los scripts desde la raíz del repositorio con `bun run <script>`. Los scripts que llaman a Wrangler, y `db:generate`, que llama a drizzle-kit, los ejecutan mediante `vp exec`, que toma el binario de `node_modules/.bin`, así que siempre usan las versiones fijadas en `bun.lock`.

## Desarrollo y compilación

| Script             | Ejecuta                                                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dev`              | `generate:cn`, `content` y `vp dev` en el entorno `development` en http://localhost:3000                                                                                        |
| `build`            | Lo mismo que `build:preview`                                                                                                                                                    |
| `build:preview`    | Limpia `dist`, `generate:cn`, `content`, `vp build` para `preview`, `scripts/verify-build.ts preview`, `scripts/optimize-prerendered-html.ts` y `scripts/generate-seo-files.ts` |
| `build:production` | Los mismos pasos para `production`                                                                                                                                              |
| `build:test`       | Los mismos pasos para el entorno `test`                                                                                                                                         |
| `start`            | `vp preview` de la última compilación en http://127.0.0.1:3000                                                                                                                  |
| `start:test`       | `vp preview` de la compilación de pruebas                                                                                                                                       |

`verify-build.ts` comprueba que `.wrangler/deploy/config.json` apunta a `dist/server/wrangler.json` y que este archivo despliega el Worker que `wrangler.jsonc` indica para el entorno, y después el idioma del documento, los enlaces canónicos y alternativos de la página de inicio y de las páginas legales localizadas, las fuentes, que los alias de idioma y las páginas bajo las rutas no listadas de las áreas no se hayan prerenderizado, que todas las páginas de la documentación y las entradas publicadas del blog se hayan prerenderizado, que ningún recurso del cliente importe `cloudflare:workers`, que los imports estáticos del script de entrada del navegador no contengan el loader de los mensajes de ningún namespace de página, que el embed del pago de Polar esté en un único recurso del cliente que solo carga `import()`, cuando un comprador inicia un pago, y que el código que el Worker carga en un arranque en frío siga siendo pequeño: las importaciones estáticas de `dist/server/index.js` no deben llegar a `@polar-sh`, `drizzle-orm` ni `resend`, y deben sumar como máximo `BOOT_CLOSURE_MAX_BYTES` (consulta [Rendimiento](/docs/conventions/performance)). `optimize-prerendered-html.ts` elimina de las páginas prerenderizadas las indicaciones `modulepreload` de las dependencias y mantiene la indicación del punto de entrada con prioridad baja. `generate-seo-files.ts` escribe `sitemap.xml` y el feed del blog en cada idioma, y renderiza una tarjeta social para cada página prerenderizada y el logotipo de la organización, todo a partir de los metadatos de las propias páginas; consulta [Búsqueda y vistas previas en redes sociales](/docs/features/seo).

## Despliegue

| Script              | Ejecuta                                                                                                                                                                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deploy:preview`    | `scripts/verify-bindings.ts preview`, `scripts/prepare-deploy-secrets.ts preview`, `scripts/run-deploy-checks.ts preview`, `build:preview`, `db:migrate:preview`, `wrangler deploy` de `dist/server/wrangler.json` y `scripts/verify-deployment.ts preview` |
| `deploy:production` | Los mismos pasos para `production`                                                                                                                                                                                                                          |

- `verify-bindings.ts` falla cuando al entorno le falta un binding que declara `development` (aquí `DB`, `CACHE`, `MEDIA` y `BUNDLES`) o todavía tiene un ID de D1 o KV de marcador de posición, y cuando producción comparte con preview su base de datos, su espacio de nombres o su bucket.
- `prepare-deploy-secrets.ts` lee de `.env.<environment>` las claves enumeradas en `secrets.required` del entorno, falla cuando alguna falta, está vacía o es un marcador de posición, y escribe solo esas claves en `.wrangler/secrets.<environment>.json`. Un marcador de posición es un valor entre corchetes (<RepositoryFact name="secretPlaceholderBrackets" />), como `[UPDATE]`, o una de las palabras <RepositoryFact name="secretPlaceholderWords" />, en mayúsculas o minúsculas y con o sin espacios, guiones o guiones bajos. El error indica las claves sin mostrar sus valores. Lee los nombres de `wrangler.jsonc`, así que cubre los secretos de todas las áreas sin nombrar ninguna. Las demás variables del archivo no se suben.
- `run-deploy-checks.ts` ejecuta `bun run <check>:<environment>` para cada comprobación de despliegue que un área declara en `src/data/<area>.deploy.ts`, y detiene el despliegue antes de la compilación cuando una falla. Hoy son `auth:verify`, del área de autenticación, que falla a menos que <RepositoryFact name="oauthClientIdVariables" /> de `.env.<environment>` contengan cada uno un identificador de cliente con el formato de su proveedor (los formatos que `verify-deployment.ts` aplica después del despliegue), y `polar:verify`, del área de Polar, que falla cuando la organización de Polar de `.env.<environment>` no coincide con el código.
- Las migraciones se ejecutan después de la compilación y antes del despliegue, así que una compilación fallida nunca toca la base de datos y el nuevo Worker nunca arranca con un esquema anterior.
- El despliegue ejecuta `env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.<environment>.json`. La configuración compilada ya apunta a un único entorno; un `CLOUDFLARE_ENV` que quede en la shell haría que Wrangler buscara una sección de entorno que ese archivo no tiene.
- `verify-deployment.ts` solicita <RepositoryFact name="liveSiteCheckPaths" /> en el dominio del entorno y falla a menos que cada ruta responda `200` con el tipo de contenido esperado. En <RepositoryFact name="socialSignInPath" /> comienza, como lo hace el navegador, el inicio de sesión con cada proveedor de la página de inicio de sesión, <RepositoryFact name="oauthProviderIds" />, y falla a menos que la URL de autorización que recibe esté en el host del propio proveedor y lleve un `client_id` con el formato de ese proveedor y un `redirect_uri` igual a <RepositoryFact name="oauthCallbackPath" /> en el mismo dominio. El error nombra el proveedor y lo que falla sin mostrar el valor. Vuelve a ejecutar una comprobación que falla hasta <RepositoryFact name="liveSiteCheckRetries" /> veces, con <RepositoryFact name="liveSiteCheckRetrySeconds" unit="second" /> de intervalo, y no modifica nada salvo el estado OAuth y el contador de intentos de corta duración en D1 que también deja un clic en un botón de inicio de sesión. `bun scripts/verify-deployment.ts <preview|production>` comprueba de forma independiente un sitio desplegado.

## Generación y mantenimiento

| Script           | Ejecuta                                                                                                                                                                                                                                                                                        |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `content`        | `fumadocs-mdx`: genera `.source/` a partir de `content/`                                                                                                                                                                                                                                       |
| `generate:cn`    | Genera las tablas de fusión de clases en `.source/cn-tables.ts` a partir de `src/lib/cn.config.ts`                                                                                                                                                                                             |
| `cf-typegen`     | `wrangler types` para `development`: regenera `src/types/worker-configuration.d.ts`                                                                                                                                                                                                            |
| `typegen`        | `cf-typegen`, `generate:cn` y `content`                                                                                                                                                                                                                                                        |
| `deps:update`    | `scripts/update-dependencies.ts`: `vp migrate` para un Vite+ más reciente, `bun update --latest` para cada dependencia con rango y después `skills:update`; nombra los paquetes fijados que tienen una versión más reciente; consulta [Dependencias](/docs/conventions/dependencies#upgrading) |
| `skills:sync`    | `scripts/sync-skills.ts`: restaura las skills para agentes a partir de `skills-lock.json`                                                                                                                                                                                                      |
| `skills:update`  | `scripts/sync-skills.ts update`: lleva cada skill para agentes de `skills-lock.json` a su último commit de origen, y registra en `skills-packages.json` las versiones de los paquetes que documentan las skills                                                                                |
| `clean`          | Elimina `.source`, `.tanstack`, `.wrangler`, `dist`, `coverage`, la salida de Playwright y `*.tsbuildinfo`                                                                                                                                                                                     |
| `clean:deep`     | `clean` y `node_modules`                                                                                                                                                                                                                                                                       |
| `clean:hardcore` | `clean:deep`, `bun.lock` y `skills-lock.json`                                                                                                                                                                                                                                                  |
| `prepare`        | Se ejecuta durante la instalación: `vp config --no-agent` (hooks de Git), `scripts/verify-git-hooks.ts`, `generate:cn` y `content`                                                                                                                                                             |

`clean` elimina `.wrangler`, incluidas las bases de datos locales de desarrollo y de pruebas y los archivos de secretos que escriben los scripts de despliegue, así que exporta antes los datos locales que quieras conservar.
