Jede Änderung wird im selben Commit mit den Tests ausgeliefert, die sie belegen, und die Testabdeckung bleibt bei <RepositoryFact name="coverageThreshold" unit="percent" /> für Zeilen, Anweisungen, Funktionen und Verzweigungen. Ein Bugfix kommt mit einem Test, der ohne den Fix fehlschlägt.

## Projekte

`vite.config.ts` definiert drei Vitest-Projekte, ausgewählt über das Dateisuffix. Tests importieren ihre API aus `vite-plus/test` und liegen in `__test__/` neben dem Code, den sie abdecken.

| Suffix                 | Projekt       | Verwenden für                                                                                                                                                                         |
| ---------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | Use Cases, Loader, `head`, Schemas, Hilfsfunktionen: alles, was auf dem Server läuft                                                                                                  |
| `.integration.test.ts` | `integration` | Abläufe von Better Auth, Zahlungen und Lizenzen, den D1-Adapter und das Laden von Nachrichten, mit Timeouts von <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Komponenten und Seiten in jsdom                                                                                                                                                       |

`src/platform/testing/mocks/cloudflare.ts` ersetzt `cloudflare:workers` in jedem Projekt: D1 ist eine `node:sqlite`-Datenbank im Arbeitsspeicher, aufgebaut aus jeder eingecheckten Migration, KV und ein Bucket für jedes R2-Binding der Umgebung `test` in `wrangler.jsonc` sind Speicher im Arbeitsspeicher. `resetTestBindings()` leert vor jedem Test KV, den Bucket und die Rate-Limit-Tabelle, und die Seed-Funktion jeder Suite setzt die Zeilen zurück, von denen sie abhängt. Kein Test spricht mit Cloudflare, Polar, Resend oder einem OAuth-Anbieter: `fetch` erreicht die strikten Test-Doubles in `mocks/resend.ts` und `mocks/polar.ts`, die jede Anfrage gegen die Request-Modelle der SDKs validieren und den Test bei einer Anfrage scheitern lassen, die der Anbieter ablehnen würde. Tests prüfen, was das Double empfangen hat, statt eine SDK-Methode zu mocken, und Auth-Suites steuern die echte Konfiguration aus `auth.server.ts` über `auth.harness.ts`.

## Eine Server Function testen

Rufe sie über ihre exportierten Optionen auf, damit der Test die echte Middleware, Validierung und den echten Handler durchläuft. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts`:

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` und `executeMutation(options, variables)` aus `src/platform/testing/lib/query.ts` führen die Optionen in einem frischen `QueryClient` aus.
- Die Session stammt aus `createAuthSessionFixture` in `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts`; jede Berechtigung wird auch von der Seite getestet, die abgewiesen werden muss (`it("is for staff only")`).
- Seed-Daten liegen in `__test__/fixtures/` des Moduls, mit ihren IDs in benannten Objekten (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` löscht die Zeilen, die ihm gehören, und fügt sie über Drizzle erneut ein, sodass jeder Test vom selben Zustand ausgeht.
- Im Projekt `component` schlägt eine Server Function fehl, weil jsdom für den Browser steht. Komponententests geben einer Route ihre Loader-Daten oder mocken `queryFn` und `mutationFn` der Optionen, die die Komponente liest.

## Assertions verwenden die Namen des Codes

- Erwartete Status, Arten, Rollen und Fehlercodes sind die Konstanten, die der Code verwendet: `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. Ein Test wiederholt nie ein String-Literal der Domäne, und ebenso wenig tun das die E2E-Daten oder der Test-Seed: `e2e/data/courses.ts` schreibt `kind: COURSE_KIND.COURSE`.
- Schematests sind der einzige Ort, an dem ein gespeicherter Wert ausgeschrieben wird: `product.schema.test.ts` legt `expect(PRODUCT_STATUSES).toStrictEqual(["draft", "published", "archived"])` fest, sodass eine Änderung an einem Wert in der Datenbank einen Test scheitern lässt, statt eine Migration zu erfordern, die niemand geschrieben hat.
- Die Browser-Suite importiert ihre Konstanten aus der Anwendung (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`) und kann deshalb nur Dateien importieren, die außerhalb des Workers laden. Die Werte von Polar kommen aus `polar.constants.ts`, das keine Umgebung liest: `e2e/fixtures/license.ts` und die Journey-Suite in der Sandbox nehmen die Bestellstatus aus `POLAR_ORDER_STATUS`, und die Bestellung selbst stammt aus `src/platform/testing/lib/polar.ts`. Die Produkt-IDs der Stufen sind die Ausnahme: `POLAR_PRODUCT_IDS` liest `cloudflare:workers`, daher liest die Browser-Suite sie aus `.env.test`.
- Komponententests lesen erwartete Texte aus den englischen Nachrichtendateien, wie `admin-course-routes.component.test.tsx` mit `import labels from "~/messages/en-US/pages.admin.courses.json"` und `labels.form.kinds.course`, und finden Elemente über Rolle und zugänglichen Namen.
- Ein Test, der einen Typ braucht, liest ihn aus einer typisierten Quelle oder prüft ihn zur Laufzeit mit `toHaveProperty`; er castet nie.
- Testnamen beschreiben Verhalten als Satz: "lists every course with its lesson count, drafts included".

## Testabdeckung

`bun run test:coverage` schlägt fehl, wenn eine der vier Metriken für `src/**/*.{ts,tsx}` unter <RepositoryFact name="coverageThreshold" unit="percent" /> liegt. Ausgenommen sind Tests, `__test__/`, Deklarationsdateien, `src/routeTree.gen.ts`, die shadcn-Primitive und `src/platform/testing/`. Die Hürde bleibt aussagekräftig:

- **Lösche Verzweigungen, die nie ausgeführt werden können**, statt sie mit Stubs abzudecken. Ein `?? fallback` auf Daten, die immer vorhanden sind, oder ein Optional Chaining auf einem Wert, der nicht `undefined` sein kann, wird aus dem Quellcode entfernt, nicht durch das Stubben eines globalen Objekts erreicht.
- **Decke echtes Verhalten ab.** Ladezustände halten die Anfrage mit `Promise.withResolvers()` offen, prüfen die Lade-UI, lösen innerhalb von `act` auf und prüfen die Ruhe-UI, wie es `expectPending` und `expectIdle` in `auth-forms.component.test.tsx` tun.
- **Behalte Assertions, wenn eine Regel greift.** Überschreitet ein Test `max-statements`, extrahiere einen benannten Helfer, statt Prüfungen wegzulassen.
- **Lade jede Nachrichtendatei.** `i18n.messages.test.ts` lädt jeden Namespace jeder Locale; das deckt die `import.meta.glob`-Zeilen in `i18n.loaders.ts` ab. Eine neue Nachrichtendatei wird dadurch automatisch abgedeckt.

## Tests auf einem ausgelasteten Rechner

Das Zeitlimit von Vitest und das Budget von einer Sekunde für `waitFor` und `findBy*` messen Echtzeit. Ein Test, der mehr Arbeit erledigt, als sein Verhalten braucht, oder auf einen Timer wartet, schlägt daher auf einem ausgelasteten Rechner fehl, obwohl nichts kaputt ist. Das Standardlimit bleibt, wie es ist; ein langsamer Test wird so umgebaut, dass er weniger tut:

- **Eine Prüfung über viele Dateien läuft als ein Test pro Datei.** `check-content.test.ts` führt `pageProblems` mit `it.each(sourcePages())` für jede englische Seite aus, und eine Abweichung nennt ihre Seite.
- **Was eine Komponente per Suspense lädt, wird vor dem Rendern geladen**, wie es `preloadNamespaces` für Übersetzungen tut. Geht es im Test um das Laden selbst, löst der Test es innerhalb von `act` auf, wie `translations-provider.component.test.tsx`: Inhalt, der außerhalb von `act` fortgesetzt wird, erscheint erst nach der Drosselung, mit der React ihn einblendet, auf einem echten Timer, und der Test muss danach pollen.
- **Ein Test ersetzt ein Modul einmal, statt die Komponente erneut zu importieren.** `affiliate-referral.component.test.tsx` mockt `AFFILIATE_PROGRAM` einmal und setzt es in jedem Test. Wer eine Komponente nach `vi.resetModules()` erneut importiert, wertet ihren gesamten Importgraphen innerhalb des Tests neu aus.
- **Fixtures, die jeder Test liest, werden einmal pro Datei erzeugt**, etwa die Nachrichten aus `getTestMessages`.
- **Ein Formular wird mit `user.paste` ausgefüllt, sofern nicht seine Tastenanschläge das getestete Verhalten sind.** `fill` in `admin-course-routes.component.test.tsx` klickt in das Feld und fügt ein; `user.type` führt die Validierung und das Rendern des Formulars für jedes Zeichen aus.
- **Eine lange Optionsliste lässt sich günstig neu rendern.** Die Zeitzonen-Combobox in `preferences-card.tsx` übergibt ihre Optionen als memoisierte `items` an `ComboboxList`, sodass React Aria sie wiederverwendet, wenn das Formular neu rendert.

## Tests folgen den Features [#tests-follow-the-features]

Die Features, deren Dateien und Pfade `scripts/features.ts` nennt (siehe [Pfade und Navigation](/docs/conventions/routes#paths-and-navigation)), besitzen auch ihre Tests, sodass die CLI `saasyland` ein Feature samt seinen Tests aus einem generierten Projekt weglassen kann, während jeder verbleibende Test weiter besteht.

Eine Testdatei deckt ein Feature oder eine Quelldatei ab. Die Admin-Seiten eines Features werden mit ihren Skeletons und Breadcrumbs in `src/routes/__test__/admin-<feature>-routes.component.test.tsx` getestet, ihre Loader in `admin-<feature>-loaders.test.ts`. Ein Test eines Layout-Skeletons rendert es mit `createTestRouter(path, routeTree)` aus `src/platform/testing/lib/render.tsx`, einem Router auf dem echten Routenbaum, und die Kurs-Skeletons werden in `admin/__test__/courses-pending.component.test.tsx` getestet, weil `admin-course-routes` die Kursrouten für seinen eigenen Router neu aufbaut; `admin-layout`, `admin-dashboard` und `admin-loaders` testen die Admin-Oberfläche selbst und nennen kein Feature. Voneinander unabhängige Dateien bekommen je eine eigene Testdatei, etwa `background.component.test.tsx` und `wordmark.component.test.tsx`, und jeder API-Handler hat seine eigene: `src/routes/api/__test__/auth.test.ts` und `index.test.ts`. `cli.v1.test.ts` deckt die Routendateien der CLI-Lizenz-API ab; ihr Verhalten wird in `src/modules/license/__test__/license.api.integration.test.ts` getestet.

Eine Liste, die mehrere Features umfasst, hat kein Barrel: Jedes Feature deklariert seinen Teil in einer eigenen Datei, und die eine Datei, die die Liste liest, importiert jeden Teil und schreibt sie in einer literalen Liste aus, sodass das Weglassen eines Features seine Datei löscht und mit dem Import auch sein Element:

| Liste                     | Jedes Feature deklariert                                                                                                                   | Aufgeführt von                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Abfragedaten des Admins   | `seed<Feature>Queries` und seine Zeilen-Factories in `src/presentation/components/custom/admin/__test__/<feature>.fixtures.ts`             | `adminQueryClient()` in `fixtures.tsx`                                            |
| Enum-Beschriftungen       | `src/integrations/use-intl/__test__/<feature>.labels.ts`                                                                                   | `ENUM_LABELS` in `enum-labels.test.ts`, die Beschriftungen des Kerns direkt darin |
| D1-Zeilen                 | `src/integrations/drizzle-orm/__test__/<feature>.rows.ts`                                                                                  | `d1.integration.test.ts`                                                          |
| Seiten der Browsertests   | `e2e/data/<feature>.pages.ts`                                                                                                              | `ENTRIES` in `e2e/data/pages.ts`, die Startseiten direkt darin                    |
| Testdatenbank             | `e2e/data/<feature>.seed.ts`                                                                                                               | `scripts/seed-test.ts`                                                            |
| Ablaufinventar            | `e2e/data/<feature>.flows.ts`: die Abläufe des Features, jeder mit dem Test, der ihn beweist, oder dem Grund, warum er fehlt               | `FLOWS` in `scripts/check-flows.ts`                                               |
| Öffentliche Abfragen      | eine Abfrage mit `public: true` in ihrer eigenen Quelldatei                                                                                | `PUBLIC_QUERIES` in `auth.session.test.ts`, eine Eigenschaft pro Abfrage          |
| Test-Doubles der Anbieter | `src/platform/testing/mocks/<provider>.ts`: eine Liste `<PROVIDER>_PROVIDER_DOUBLES`, jedes Double mit `origin`, `respond` und `reset`     | `DOUBLES` in `mocks/providers.ts`                                                 |
| Polar-Katalog             | `src/modules/<module>/__test__/fixtures/<feature>.polar-catalogue.ts`: die Produkte und Lizenzschlüssel-Benefits, die das Feature verkauft | `CATALOGUES` in `mocks/polar.ts`                                                  |
| Test-Worker               | `e2e/data/<feature>.worker.ts`: Set-ups und Testendpunkte                                                                                  | `ENTRIES` in `src/platform/testing/worker.ts`                                     |

Keine Datei deklariert eine leere Liste für den Kern: Ein Eintrag, den jedes Projekt hat, steht direkt in der Liste, so wie die Startseiten in `e2e/data/pages.ts`, und `scripts/seed-test.ts` führt Wrangler nur aus, wenn ein Feature Zeilen einspielt. Das Page Object eines Features bringt eine eigene Fixture mit: `e2e/fixtures/auth.ts` erweitert den Kern-`test` aus `e2e/fixtures/test.ts` um `authPage`, und die Specs, die sich anmelden, importieren `test` von dort. Auch die E-Mail-Hilfsfunktionen eines Features liegen in einer eigenen Fixture-Datei, etwa `e2e/fixtures/license-emails.ts` und `e2e/fixtures/invitation-emails.ts`, neben den gemeinsamen `getSentEmails`, `latestEmail` und `linkTo` in `e2e/fixtures/emails.ts`, und das Browser-Double eines Features kommt als Element in `BROWSER_DOUBLES` in `e2e/fixtures/test.ts`, wie `servePolarCheckout`.

Hilfsfunktionen, die mehrere Features nutzen, gibt es nur einmal: `renderAdmin` und `renderAdminPage` in `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` in `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` und `busyMarkup` in `src/platform/testing/lib/skeleton.tsx` sowie in den Browsertests `AuthPage.signIn`, `BasePage.leaveWhileLoading` und die Fixture `pageWithoutJavaScript`. Die Specs öffentlicher Seiten wie `accessibility.spec.ts` und `theme.spec.ts` melden sich bei keinem Konto an; `workspaces.spec.ts` prüft die Seiten nach der Anmeldung, ihre Barrierefreiheit und ihr Theme.

Ein Test von gemeinsamem Code, der einen Eintrag braucht, den die Features beisteuern, deklariert einen eigenen, statt den eines Features zu lesen. `dashboard-actions.component.test.tsx` ersetzt `ADMIN_DASHBOARD_ACTIONS` durch eine testlokale Aktion, sodass `DashboardActions` und die Aktions-Platzhalter von `AdminDashboardPending` auch in einem Projekt ohne das Zahlungs-Feature abgedeckt bleiben, der heute die Dashboard-Aktionen deklariert. `server.test.ts` stellt die Dateien jedes Request-Handlers bereit und führt jede Dokument-Umschreibung durch den Worker, in einem Test, der das eigene Modul des Features nennt, sodass das Weglassen des Features den Test löscht, `vite-config.test.ts` lädt `VITE_PLUGINS` in ihrer Reihenfolge, und die Plugins eines Anbieters werden daneben getestet, etwa in `zod.vite.test.ts`. Gemeinsamer Code, den nur optionale Features rendern, bekommt einen eigenen Test: `pending-blocks.component.test.tsx` deckt das Feld-Skeleton ab, das die Skeletons der Kursverwaltung verwenden. `auth.access.test.ts` prüft, was jeder Rolle gewährt wird, jedes Feature prüft seine eigenen Statements in `auth.access.<feature>.test.ts`, etwa `auth.access.courses.test.ts`, und `auth.access.website.test.ts` schreibt die Berechtigungen jeder Rolle auf der Website fest.

`auth.server.test.ts` führt die ID jedes Better-Auth-Plugins der Reihe nach auf, und `navigation.test.ts` prüft die Menüs, ohne einen bestimmten Eintrag zu erwarten, und besteht daher mit jeder Auswahl an Einträgen, die ein Projekt behält. `translations-provider.component.test.tsx` nimmt Namespaces des Kerns als Beispiele, und die Auth-Tests nehmen die eigenen Daten und Pfade des Auth-Features, etwa die Sitzungsliste und `/app/settings`.

Der Routentest der Lizenz ersetzt `CourseUnlocks` aus dem Kurs-Feature durch einen testlokalen Abschnitt und dessen Katalog-Query durch einen Mock, der Skeleton-Test der Lizenz macht dasselbe mit `CourseUnlocksPending`, und die Kurstests ersetzen die Kurszugangsfreigaben von `lesson.access.ts` über `withTestCourseAccess` durch `TEST_COURSE_ACCESS` (`src/modules/course/__test__/fixtures/course-access.ts`), sodass die Tests keines der beiden Features den anderen lesen. `src/modules/lesson/__test__/lesson.access.license.test.ts` deckt ab, was sie verbindet: die Freigabe der Lizenz, mit einem Snapshot dessen, wer welche Lektion ansehen darf, für einen Gast, ein Konto, das Team und jede Lizenzstufe und jeden Lizenzstatus.

Ein Test, der die gesamte Website festschreibt, etwa `navigation.website.test.ts` mit der Reihenfolge jedes Menüs, gehört nur zur Website; die Templates erzeugen ihn nicht.

`scripts/features.ts` listet die Dateien jedes optionalen Features als Globs auf, die Namen, die das Feature in verbleibenden Dateien besitzt, etwa die Pfade jedes Features in `src/routes.ts`, und die Features, die es voraussetzt, und `bun run check:features` prüft, dass die Website ohne sie weiter funktioniert. Jedes Szenario lässt die Features weg, die nur die Website hat, und vier davon lassen außerdem die Kurse, die Abrechnungs-Features, die Inhalte oder das Auth-Feature weg. Für jedes Szenario löscht das Skript die Dateien dieser Features und jedes Features, das eines davon voraussetzt, und bereinigt die verbleibenden Dateien dann mit einer Regel, derselben, der die CLI `saasyland` folgt, wenn sie ein Feature weglässt:

1. Es löscht die Namen, die die entfernten Features besitzen, jeweils mit ihrer Deklaration oder Objekteigenschaft.
2. Ein entfernter Verweis ist ein Bezeichner, der aus einer gelöschten Datei importiert wird, die Verwendung eines entfernten Namens, etwa `ROUTES.COURSES`, sobald `src/routes.ts` ihn nicht mehr deklariert, eine Funktion, die `import()` auf eine gelöschte Datei aufruft, oder ein `vi.mock`, `vi.doMock`, `vi.unmock` oder `vi.doUnmock`, das ein gelöschtes Modul nennt. Jedes `import` und jedes `export … from` einer gelöschten Datei fällt weg, ebenso jeder Import eines Moduls, das nur eine gelöschte Deklarationsdatei deklariert, etwa `virtual:repository-facts`.
3. Steht ein entfernter Verweis im Callback eines Tests, also eines `it` oder `test` in jeder Form, etwa `.each`, `.skip` oder `.only`, oder eines Playwright-`test.step`, fällt der ganze Test weg. Für jeden anderen entfernten Verweis löscht es die nächstgelegene dieser Einheiten, die wegfallen kann; eine Funktion, eine Klasse, eine `return`-Anweisung, eine Bedingung oder ein Export fällt nie als Ganzes weg, daher meldet es einen Verweis, den nur eines davon umschließt, mit Datei, Zeile und Spalte:
   - das nächstgelegene Array-Element innerhalb seiner Anweisung auf oberster Ebene, sonst die nächstgelegene Objekteigenschaft, den Spread, das Typ-Member oder das JSX-Kind, ohne eine Anweisung zu überschreiten;
   - die umgebende Ausdrucksanweisung, wenn sie auf oberster Ebene eines Moduls, eines `describe` oder eines Hooks wie `beforeEach` steht, und in jeder anderen Funktion nur, wenn alles wegfällt, was sie von außerhalb nennt;
   - den umgebenden Variablen-Deklarator, wenn sein Wert weder eine Funktion noch eine Klasse ist und alles wegfällt, was sein Initialisierer nennt; die Namen, die er bindet, sind dann ebenfalls entfernte Namen, und der Deklarator fällt nur weg, wenn jede ihrer Verwendungen nach derselben Regel wegfällt. Ein Wert, der auch auf verbleibenden Code zurückgreift, etwa der Link, den `signedInDestination(entry, workspace)` aus einem Menüeintrag baut, bleibt und wird gemeldet, denn ändern muss sich der Entwurf, nicht die Bereinigung;
   - den umgebenden Hook oder das umgebende `describe`.
4. Leert das ein Array, das eine Eigenschaft eines Array-Elements ist, fällt auch das Element weg, so wie eine Menügruppe ohne Einträge. Ebenso fallen ein Test weg, dessen `.each`-Tabelle es leert, ein Test, ein Schritt, ein Hook oder ein `describe`, dessen Callback es leert, ein `describe` ohne verbleibenden Test und eine Schleife oder ein Callback mit leerem Rumpf, der Callback samt der umgebenden Einheit. Würde es den Rumpf einer Funktion oder einer Bedingung leeren, bleiben die Anweisungen stehen, und es meldet die Verweise darin.
5. Es löscht jedes String-Element eines Arrays, das den Namespace einer gelöschten Nachrichtendatei nennt.
6. Es löscht die Import-Specifier, die nicht exportierten Deklarationen, auf jeder Ebene, und die Elemente eines Array-Destrukturierungsmusters, auf die nichts mehr verweist, wobei vor einem verbleibenden Element eine Lücke bleibt, und wiederholt das, bis sich nichts mehr ändert. Eine `*.test.*`- oder `*.spec.*`-Datei, in der kein Test mehr steht, löscht es ganz.

`scripts/prune-references.ts` wendet die Regel auf die Syntaxbäume des oxc-Parsers an, und `scripts/module-bindings.ts` löst jeden Namen zu der Deklaration auf, auf die er verweist, sodass ein Parameter oder eine lokale Variable gleichen Namens nie für einen Import gehalten wird. `scripts/test-cases.ts` erkennt Tests, Gruppen, Hooks und Mocks an den Aufrufen dessen, was eine Datei als `it`, `test`, `describe`, Hook oder `vi` importiert, unter jedem lokalen Namen, `scripts/prune-units.ts` wählt die Einheit um jeden Verweis, und `scripts/prune-edits.ts` schreibt die Löschungen und behält den breiteren der beiden Abstände um eine gelöschte Anweisung, sodass die Leerzeile zwischen Gruppen von Anweisungen erhalten bleibt. Generierte Dateien, die `.gitattributes` als `linguist-generated` markiert, werden unverändert kopiert, und den Routenbaum erzeugt die Prüfung neu. Danach kopiert das Skript die Dateien, die Git verfolgt oder hinzufügen würde, in ein temporäres Verzeichnis, die bereinigten anstelle der ursprünglichen, formatiert die bereinigten Dateien mit `vp fmt`, erzeugt die Klassennamen-Tabellen, die Content-Sammlungen, solange das Content-Feature bleibt, und mit `scripts/generate-routes.ts` den Routenbaum, führt `tsc --noEmit` über `src`, `e2e`, `scripts` und `vite.config.ts` aus und prüft mit `check:i18n` die verbleibenden Nachrichten. Ein Szenario scheitert an einem Verweis, den die Regel nicht entfernen kann, an jedem Typfehler und an jedem Übersetzungsfehler, und `src/__test__/check-features.test.ts` schlägt fehl, wenn ein Glob keine Datei trifft oder ein Name in seiner Datei nicht deklariert ist. Ein Verweis, den die Regel nicht entfernen kann, wird behoben, indem der Code dorthin kommt, wo die [Verzeichnisstruktur](/docs/architecture/directory-structure) ihn vorsieht, nie durch eine Ausnahme im Bereinigungsskript. CI führt einen Job pro Szenario aus, und ein fehlschlagendes Szenario lässt den Lauf fehlschlagen ([CI/CD](/docs/tooling/ci-cd#checks)).

## Browsertests

Playwright führt den gebauten Test-Worker aus: `bun run build:test` kompiliert ihn mit lokalem D1 und KV unter `.wrangler/test`, `bun run db:reset:test` erstellt diese Datenbank neu und legt die Konten, das Video und den Kurs in `e2e/data` an, und der Test-Einstiegspunkt fängt ausgehende E-Mails unter `/__test/emails` ab, damit eine Spec einem Verifizierungslink folgen kann.

- Specs sind nach dem Ablauf benannt (`course-admin.spec.ts`, `auth-redirect.spec.ts`) und steuern die Seite über Rollen und zugängliche Namen, mit Page Objects in `e2e/pages/`.
- Jede Spec legt die Daten, die sie ändert, mit eindeutigen Werten an, etwa einem Slug aus `crypto.randomUUID()`, und meldet sich mit ihrem eigenen Header `CF-Connecting-IP` an, sodass Specs parallel laufen und erneut ausgeführt werden können, ohne miteinander oder mit Rate Limits zu kollidieren.
- Ein Test, der per Seed angelegte Daten ändert, etwa die Geräte einer Lizenz, bekommt eigene per Seed angelegte Datensätze, einen für jeden parallelen Worker, sodass nie zwei laufende Tests denselben Datensatz ändern. `cli-licence-api.spec.ts` aktiviert Geräte auf der Lizenz, die `TEST_CLI_LICENSES` in `e2e/data/licenses.ts` für den `parallelIndex` des jeweiligen Workers anlegt, den Playwright nie zwei Workern gleichzeitig gibt, und die Fixture `cliMachine` gibt das Gerät frei, wenn der Test endet, sodass eine Wiederholung mit der Lizenz aus dem Seed beginnt. Die Lizenz `TEST_LICENSE`, die `license.spec.ts` liest, behält nur ihr per Seed angelegtes Gerät.
- Eine Spec interagiert mit einer Seite erst, wenn `waitForAppReady()` aus `e2e/pages/base-page.ts` zurückgekehrt ist, auch nach clientseitigen Navigationen. Die Methode kehrt zurück, sobald TanStack Router die aktuelle URL gerendert hat, was die automatische Fixture `recordRenders` aus dem Router-Ereignis `onRendered` aufzeichnet, denn eine clientseitige Navigation ändert die URL, bevor die nächste Route rendert. Routeninhalte können erst nach diesem Rendern hydrieren. Eine Spec, die vom eigenen Zustand einer Komponente abhängt oder einen Link außerhalb des Inhalts drückt, bevor dieser hydriert ist, ruft deshalb zuerst `waitForHydration(element)` auf, das wartet, bis React das Element und alles darin hydriert hat; `LandingPage.goto()` tut das für `main` der Landingpage. Eine Spec darf eine Seite verlassen, während sie lädt, wie es auch Besucher tun, und eine Spec, die Seitenfehler über mehrere direkte Aufrufe sammelt, öffnet jeden Aufruf in einem eigenen Tab, wie `auth-routing.spec.ts`, oder verlässt jede Seite erst, wenn ihr Netzwerk ruht (`page.waitForLoadState("networkidle")`), wie `workspaces.spec.ts`, weil eine Seite manche Anfragen erst nach der Hydration startet, etwa ein Badge in der Seitenleiste oder die Segmente eines Videos. Eine Spec, die Seitenfehler sammelt, verlässt eine Seite erst, wenn deren clientseitige Navigation gerendert ist: WebKit meldet eine Anfrage, die die Seite startet, nachdem die Spec sie zu verlassen begonnen hat, als Seitenfehler, `Fetch API cannot load … due to access control checks.`, obwohl die App die fehlgeschlagene Anfrage behandelt.
- Eine Spec, die beweisen muss, dass ein Text nie erscheint, nicht nur, dass er am Ende verschwunden ist, ruft vor der Änderung `watchForText(text)` aus `e2e/pages/base-page.ts` auf und prüft danach, dass der Text nie zu sehen war: Ein `MutationObserver` in der Seite hält ihn fest, sobald er gerendert wird. Der Upgrade-Test in `checkout-funnel.spec.ts` macht das für den Dank für die alte Stufe, die Journey-Suite für den Dank für jede andere Stufe als die gekaufte.
- Jede Spec schlägt fehl, wenn eine Seite gegen ihre Content Security Policy verstößt: Die automatische Fixture `cspViolations` in `e2e/fixtures/test.ts` protokolliert jedes Ereignis `securitypolicyviolation` und erwartet am Ende des Tests keines. Eine Spec, die absichtlich einen Verstoß auslöst, entnimmt ihn mit `cspViolations.splice(0)`, wie `content-security-policy.spec.ts`. Die Suite führt den Produktions-Build von `build:test` aus, weil der Dev-Server keine Skript-Richtlinie sendet.
- Pull Requests und die Merge Queue führen jede Spec in Chromium und in WebKit aus; lokal führt `bun run test:e2e:pr` sie in Chromium aus und `bun run test:e2e` in beiden. Pushes auf `main` führen WebKit noch einmal aus, ein wöchentlicher Zeitplan beide.
- Eine Spec, die die Zwischenablage liest, nimmt die Fixture `readClipboard` aus `e2e/fixtures/test.ts`, die vor dem Start der Spec die Berechtigungen für die Zwischenablage erteilt, die der Browser kennt: Chromium `clipboard-read` und `clipboard-write`, WebKit nur `clipboard-read`, denn WebKit hat keine Schreibberechtigung und lässt den Klick, der kopiert, in die Zwischenablage schreiben, wie Safari.
- Eine Spec, die einen Ablauf End-to-End durchläuft und sein Ergebnis prüft, wird von diesem Ablauf in `e2e/data/<feature>.flows.ts` mit ihrer Spec-Datei und ihrem vollständigen Titel genannt. `bun run check` schlägt fehl, wenn ein Ablauf einen Test nennt, den die Suite nicht hat; ein umbenannter Test nimmt seinen Ablauf also im selben Commit mit, und ein Ablauf, den kein Test beweist, sagt, warum. Siehe [Testabdeckung](/docs/tooling/test-coverage).
- Eine Korrektur an einer Route, einem Ablauf oder der Darstellung, die Unit-Tests nicht sehen können, bekommt eine Spec: Die Barrierefreiheitsscans und die Navigationsregressionen in `navigation.spec.ts` und in den Specs der Features, die sie betreffen, etwa `content.spec.ts`, `legal.spec.ts` und `landing.spec.ts`, sind Beispiele. Eine Spec, die scrollt, macht die Seite selbst hoch genug, wie der Scroll-Test in `navigation.spec.ts`, statt sich auf die Länge einer Seite zu verlassen. Ein Abschnitt, der sich nach dem Laden der Seite füllt, behält seine Höhe, sodass eine Spec, die scrollt, ihn nie vorher laden muss: Ein Abschnitt, dessen Höhe sich oberhalb des Viewports änderte, verschob, was der Besucher gerade las, und WebKit brach ein sanftes Scrollen ab, wenn die Scroll-Verankerung das ausglich. Die Specs des Kursblocks in `landing.spec.ts` halten seine Anfrage an, lassen sie gelingen oder fehlschlagen und prüfen, dass der Block seine Höhe behält und keine Layoutverschiebung gemeldet wird.
