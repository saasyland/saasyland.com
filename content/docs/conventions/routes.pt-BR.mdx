title: "Arquivos de rota"
description: "A forma única de uma rota de página e de uma rota de layout: NAMESPACE ou NAMESPACES, um loader com um único Promise.all, um esqueleto que reproduz a página, schemas de busca e links."
---

Todo arquivo em `src/routes` tem a mesma forma, então quem conhece um conhece todos. Um arquivo de rota compõe: ele declara do que a página precisa e posiciona os componentes. Widgets, formulários, diálogos e colunas de tabela ficam em `src/presentation/components/custom`.

## Rotas de página

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const columns = useCourseColumns()

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        rowActionsSize={COURSE_COLUMN_SIZES.actions}
        search={t("table.search")}
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **O componente** é uma `const` local chamada `<Name>Page`, definida primeiro. Uma marcação pequena usada apenas por esta página pode ficar acima dele como componentes locais, como `CourseProgress` e `StartLink` em `_site._marketing.courses.$course.index.tsx`; tudo o que tem dados, mutation ou estado próprios vai para um arquivo de componente.
- **Um namespace.** `const NAMESPACE = "pages.<area>.<page>"` fica logo acima de `export const Route` e é usado em `loadPageMetadata`, `preloadNamespaces` e `staticData`. Todo o resto de que a página precisa é declarado pelo seu layout.
- **Um `Promise.all`.** O loader inicia todo o trabalho de uma vez: os metadados da página, o namespace e todas as queries que os componentes leem. Ele retorna `{ locale, metadata }` para `head`. Nunca aguarde um deles antes de iniciar o próximo.
- **`head: pageHead(ROUTES.X)`** monta o título, a descrição, a URL canônica e os links alternativos a partir dos metadados do arquivo de namespace.
- **Os caminhos vêm de `ROUTES`**, em `src/routes.ts`, que reúne os caminhos de todas as áreas (veja [Caminhos e navegação](#paths-and-navigation)); nunca escreva um literal de caminho.

Uma página cujo título vem de um registro aguarda esse registro e monta o seu head a partir dos dados do loader, como faz `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Rotas de layout

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Um layout declara `const NAMESPACES = [...] as const` acima de `export const Route` e os pré-carrega. Quando não tem nenhum, ele omite a opção; não existe `namespaces: []`.
- Um namespace de que um componente de outra área precisa no layout é adicionado por essa área em `src/data/<area>.namespaces.ts`, que nomeia o layout pelo seu id de rota, e o layout espalha `...layoutNamespaces("/app")` nos seus `NAMESPACES`. A área de licenças adiciona `pages.license`, `pages.withdrawal` e `withdrawal.validations` a `/app`, cuja visão geral mostra o card da licença e a oferta e cuja página de licença mostra o card de desistência, `withdrawal.validations` a `/_site/_marketing` e `pages.admin.users.license` a `/admin/users`; a área de pagamentos adiciona `pages.admin.customers` e `pages.admin.orders` a `/admin/users`; e a área da newsletter adiciona `auth.validations` a `/_site/_marketing` e `/_site/docs`, cujos rodapés mostram o formulário da newsletter. `namespaces.test.ts` verifica em tempo de compilação que todo layout que uma área nomeia é um id de rota.
- O componente, quando o layout renderiza um, se chama `<Name>Layout` e posiciona um `<Outlet />`.
- Um guard vai em `beforeLoad`, no layout que é dono da área: `beforeLoad: requireAdmin` em `admin.tsx`, `requireSignedIn` em `app.tsx`, ambos layouts da área de autenticação. Os guards decidem apenas a navegação; toda server function continua verificando a sua própria permissão.

## Ordem das opções

`sort-keys` fica desativado em `src/routes` porque o TanStack Router infere os tipos na ordem de declaração. As opções ficam em ordem alfabética, exceto `validateSearch`, que vem primeiro, antes de tudo o que lê os search params:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Nunca escreva um array ou um objeto de dados diretamente dentro de `createFileRoute`; declare-o como uma constante acima.

## Search params

`validateSearch` é um `zod.object` montado com os helpers de `src/lib/search-params.ts`:

| Helper                            | Valor quando o parâmetro está ausente ou malformado | Uso                                    |
| --------------------------------- | --------------------------------------------------- | -------------------------------------- |
| `searchText()`                    | `undefined`                                         | Tokens, e-mails, códigos de erro       |
| `searchFlag()`                    | `undefined`                                         | Booleanos                              |
| `searchParam(schema)`             | `undefined`                                         | Qualquer outro schema, como um caminho |
| `searchChoice(choices, fallback)` | `fallback`                                          | Uma aba ou uma visualização            |

Um texto ausente continua `undefined`, então um valor padrão nunca vaza para uma URL que o router monta. Um parâmetro `searchChoice` vem acompanhado de `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, que remove o valor padrão da URL. Uma página para a qual outro site devolve os visitantes declara também `search: { middlewares: [onlyDeclaredSearch(schema)] }` com o próprio schema, como `/app` e `/app/license` fazem para o checkout da Polar: o router passa a montar o endereço só com os parâmetros declarados, e o servidor redireciona um endereço com qualquer outro parâmetro para o mesmo endereço sem ele, antes que uma verificação ou a página o leiam. Nunca escreva à mão verificações como `typeof search["x"] === "string"`; adicione um helper quando for necessário um novo tipo de campo. Quando um filho precisa de um parâmetro que a página validou como presente, a página o restringe e o repassa, como `auth.reset-password.tsx` repassa `token` para `ResetPasswordForm`. Páginas que leem os mesmos parâmetros compartilham um schema em `src/data`, que os seus esqueletos também analisam, como fazem `/app/license` e a parte da visão geral que a área de licenças adiciona com `licenseSearchSchema` (`src/data/license.ts`).

## Esqueletos

A navegação precisa parecer instantânea, então toda rota que renderiza uma página tem um `pendingComponent` que a reproduz: o mesmo layout, os mesmos cards e o mesmo número de linhas.

- Os esqueletos ficam no arquivo de esqueletos da área (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) e usam o `Skeleton` do shadcn.
- Os esqueletos ficam no script de entrada de toda página, então um esqueleto importa `Skeleton`, as primitivas do shadcn, outros esqueletos e as constantes que definem os seus comprimentos, nunca um formulário nem o arquivo que contém um; `pending-imports.test.ts` falha quando algum chega a `@tanstack/react-form` (veja [Desempenho](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Um placeholder de texto recebe o token tipográfico real mais `h-lh scale-y-70`, para ter a altura da linha que substitui: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- O comprimento das listas vem das constantes que a página usa: `DataGridPending` em `data-grid-pending.tsx` desenha por padrão `DEFAULT_PAGE_SIZE` linhas, o tamanho de página de todas as tabelas da administração.
- Um esqueleto de layout renderiza o `pendingComponent` da primeira rota abaixo do layout que corresponde ao caminho atual e define um, que `usePagePending(layout)` em `src/hooks/use-page-pending.ts` lê da árvore de rotas: `AdminPending`, `AppPending`, `AuthPending` e `MarketingPending` para os seus layouts, e `AdminUsersPending` e `AdminCourseSectionPending` um nível abaixo. Por isso, a rota de uma página é o único lugar que nomeia o seu esqueleto, seja qual for o layout que o mostre; `/admin/users`, que redireciona para `/admin/users/all`, define o esqueleto dessa página.
- Não existe um `defaultPendingComponent` para todo o router. `src/router.tsx` define `defaultPendingMs` como <RepositoryFact name="navigationPendingMs" unit="millisecond" /> e `defaultPendingMinMs` como <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, ambos de `src/data/navigation.constants.ts`: uma navegação que não terminou até lá mostra o esqueleto da rota, e o esqueleto some assim que a página fica pronta, sem ficar na tela nem um instante a mais. As rotas mantêm esses valores; veja [Desempenho](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) para as medições por trás deles.
- As páginas da documentação desenham os seus esqueletos dentro do layout da documentação: `DocsIndexPending` e `DocsPagePending` preenchem as áreas da grade do artigo e do sumário do Fumadocs, então uma navegação entre páginas da documentação mantém a barra lateral na tela. O componente da página renderiza o MDX no próprio `<Suspense key={path}>`, então a barra lateral funciona antes de o chunk MDX da página carregar, e uma navegação substitui o HTML do servidor da página anterior em vez de hidratá-lo com os dados da próxima.

## Links

- Os links do router recebem uma constante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, ou um padrão de rota com `params` para caminhos dinâmicos. O `LinkButton` e o `SidebarMenuLink` do shadcn recebem `to` da mesma forma, e o `AnchorButton` recebe um `href` para um endereço fora da árvore de rotas.
- Nunca adicione o prefixo de locale a um link do router; o rewrite do router o adiciona. Uma URL completa no locale atual, para um valor que sai do router como string, vem de `router.buildLocation({ ... }).publicHref`, como `use-auth-redirect.ts` monta os seus links de login. `localizePathname` é para URLs montadas fora de um contexto de router ou para outro locale: e-mails, destinos de redirecionamento do Better Auth, links dentro de MDX e o seletor de idioma.

## Caminhos e navegação [#paths-and-navigation]

Nenhum arquivo da aplicação lista todas as áreas. Cada área, como os cursos, os produtos ou as páginas legais, declara os próprios caminhos, itens de menu e seus rótulos, esqueletos de página e permissões, e um barrel os reúne, então uma área entra ou sai junto com os próprios arquivos. É assim que a CLI `saasyland` monta um projeto a partir de camadas de templates. Só `scripts/areas.ts`, que a aplicação nunca carrega, lista as áreas opcionais com os seus arquivos, para que `bun run check:areas` possa checar os tipos do site sem cada uma delas ([Testes](/docs/conventions/testing#tests-follow-the-areas)).

| O quê                            | Cada área declara                                                     | Barrel                           | Lido de                                                                                                                                                                                    |
| -------------------------------- | --------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Caminhos                         | `src/areas/<area>.shared.ts`: um `export const` por caminho           | `src/routes.ts`                  | `import * as ROUTES from "~/src/routes"`                                                                                                                                                   |
| Itens de menu                    | `src/data/<area>.navigation.ts`: uma lista `<AREA>_NAVIGATION`        | `src/data/navigation.entries.ts` | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` e `FOOTER_NAVIGATION` em `src/data/navigation.ts` |
| Estatísticas e painéis do painel | `src/data/<area>.dashboard.ts`: uma lista `<AREA>_DASHBOARD`          | `src/data/dashboard.entries.ts`  | `ADMIN_DASHBOARD_STATS` e `ADMIN_DASHBOARD_PANELS` em `src/data/dashboard.ts`                                                                                                              |
| Permissões                       | `src/areas/<area>.access.ts`: um objeto `<AREA>_ACCESS`               | `src/areas/access.entries.ts`    | `APP_STATEMENTS` e `grantsOf` em `src/integrations/better-auth/auth.access.ts`                                                                                                             |
| Caminhos não listados            | `src/areas/<area>.shared.ts`: `unlisted` em um objeto `<AREA>_SHARED` | `src/areas/shared.entries.ts`    | `UNLISTED_ROUTES` e `isUnlistedRoute` em `src/areas/shared.ts`                                                                                                                             |
| Namespaces de layout             | `src/data/<area>.namespaces.ts`: uma lista `<AREA>_NAMESPACES`        | `src/data/namespaces.entries.ts` | `layoutNamespaces(layout)` em `src/data/namespaces.ts`                                                                                                                                     |

Um barrel contém só linhas `export { … } from`, uma por arquivo de área, ordenadas por módulo, como `src/integrations/drizzle-orm/drizzle.schemas.ts`. Um barrel que só áreas opcionais preenchem, como os namespaces de layout, também recebe uma lista vazia da base (`CORE_NAMESPACES` em `src/data/core.namespaces.ts`), então um projeto sem essas áreas continua passando na verificação de tipos e no lint. O barrel dos caminhos é o próprio `src/routes.ts`, e cada arquivo o importa como um único namespace, `import * as ROUTES from "~/src/routes"`, então cada caminho mantém o seu tipo literal e `<Link to={ROUTES.COURSES}>` continua sendo verificado contra a árvore de rotas:

```ts title="src/routes.ts"
export { API, HOME } from "./areas/core.shared.ts"
export { ADMIN_COURSES, ADMIN_COURSES_CREATE, COURSES } from "./areas/courses.shared.ts"
```

Um item de menu indica onde aparece com `placement` (`NAVIGATION_PLACEMENT` em `src/data/navigation.constants.ts`): a barra lateral do admin, os botões acima do painel, as ações rápidas da paleta de comandos, a barra lateral do app do cliente e os seus recursos, o cabeçalho público ou o rodapé. O seu `order` o posiciona entre os itens das outras áreas, então nenhuma lista depende da ordem dos arquivos. Os itens do admin também indicam o seu grupo da barra lateral (`group`), e os links do rodapé a sua coluna (`column`); `ADMIN_NAVIGATION_GROUPS` e `FOOTER_COLUMNS` fixam a ordem de grupos e colunas, e os que nenhuma área preenche ficam de fora. O console de administração e o workspace do cliente só existem com login, então pertencem à área de autenticação: os seus caminhos, `/admin`, `/admin/settings`, `/app` e `/app/settings`, os seus itens de painel, visão geral, configurações e gerenciamento de usuários, e **Entrar** no cabeçalho e no rodapé:

Uma entrada do cabeçalho ou do rodapé pode indicar um rótulo `signedIn` que substitui o seu para um visitante logado, e o seu link passa a levar ao espaço de trabalho desse visitante: `/admin` para uma conta com acesso de administrador, `/app` para todas as outras. `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`) decide pelo papel da sessão, com `hasPermission` e a permissão `admin: ["access"]` que `requireAdmin` verifica. As páginas públicas são pré-renderizadas, então o HTML delas mostra **Entrar**; depois da hidratação, um navegador que tem o cookie do Better Auth com o último método de login pede a sua sessão, e o cabeçalho, o menu móvel e o rodapé mostram **Sua conta** no lugar, já com o link para o espaço certo. Um navegador que nunca fez login não pede nada. Até que uma parte da página tenha sido hidratada, `useVisitorWorkspace` não retorna nada, mesmo quando o navegador já tem a sessão, porque `useHydrated` responde com o valor do servidor enquanto o React hidrata: um rodapé que hidrata depois de a sessão chegar mostra o mesmo **Entrar** do HTML e muda depois, em vez de quebrar a hidratação.

Toda entrada do admin abre uma tela que funciona com dados reais, e a landing page conta todas elas. Uma tela cujos dados ainda não têm fonte não recebe entrada (veja [Painel administrativo](/docs/features/admin-dashboard#real-data-only)).

A área de licenças adiciona o seu item **Licença** à barra lateral do app do cliente, e a área de conteúdo adiciona **Documentação** aos seus recursos, acima do endereço de suporte. A área base declara apenas `/` e `/api`, e o item **Preços** do cabeçalho, o único com `hash`, que leva à seção de preços de `/`.

Uma estatística do painel tem um `prefetch`, que o loader de `/admin` executa, e um hook `useValue`, que `DashboardStats` chama para ler o número.

O arquivo de acesso de uma área define as declarações de permissão dos seus recursos e os papéis aos quais as concede. `auth.access.ts` monta o controle de acesso do Better Auth a partir de `APP_STATEMENTS` e cada papel a partir de `grantsOf(role)`, de modo que a integração de autenticação não cita nenhuma área, e `APP_STATEMENTS` falha quando duas áreas declaram o mesmo recurso (veja [Papéis e permissões](/docs/guides/roles-and-permissions)).

As listas de `src/data/navigation.ts` têm um tipo declarado, `NavigationEntry`, em vez dos tipos dos itens que as áreas declaram no momento, então uma posição que nenhuma área preenche, como as ações do painel em um projeto sem a área de pagamentos, é uma lista vazia que continua passando na verificação de tipos. `navigation.test.ts` verifica na compilação que o `to` de cada item que uma área declara é um caminho da árvore de rotas (`FileRouteTypes["to"]` de `src/routeTree.gen.ts`).

Um item indica a sua `area`, e a área o rotula no próprio arquivo de mensagens: `<placement>.<key>` em `messages/<locale>/navigation.<area>.json`, como `admin.courses` e `header.courses` em `navigation.courses.json`. Uma estatística do painel é rotulada pela sua `key` em `dashboard.<area>.json`, e uma seção do admin rotula as suas subpáginas para a trilha de navegação em `breadcrumbs.<segment>` no seu `navigation.<area>.json`, como `breadcrumbs.create`; uma aba da gestão de usuários é rotulada em `userTabs.<key>`, que dá nome à aba e à sua página na trilha de navegação, e um painel do dashboard guarda os seus textos sob a sua `key` em `dashboard.<area>.json`. Os dois tipos de arquivo são namespaces raiz, então qualquer menu pode rotular qualquer item, e `useNavigationLabel` em `src/hooks/use-navigation-label.ts` retorna o rótulo de um item. O que pertence ao próprio menu fica no namespace dele: `groups.<group>` em `pages.admin.sidebar`, `columns.<column>` em `components.custom.footer` e, do cabeçalho, a chamada para ação, o botão do menu e o link de pular para o conteúdo em `components.custom.navigation`. `enum-labels.test.ts` falha quando falta o rótulo de um item ou de uma estatística em algum locale.

Uma área cujas páginas são renderizadas no Worker a cada requisição, como `/admin`, `/auth` ou `/courses`, lista esses caminhos no campo `unlisted` do seu objeto `<AREA>_SHARED`, em `src/areas/<area>.shared.ts`. O plugin do TanStack Start em `src/data/tanstack.vite.ts` os deixa fora da pré-renderização com `isUnlistedRoute`, e `buildPageHead` lhes dá o card do site em vez de um card de página (veja [Busca e prévias em redes sociais](/docs/features/seo)). O Vite não resolve o alias `~` enquanto carrega a própria configuração, por isso cada arquivo de `src/areas` que ele carrega, `shared.ts`, `shared.entries.ts` e cada `<area>.shared.ts`, importa por caminho relativo. A entrada do Worker, o `vite.config.ts` e o projeto Remotion alcançam cada arquivo compartilhado por meio de `ROUTES`, então um arquivo compartilhado contém caminhos e nada que traga uma dependência. As verificações do site no ar são um tipo de arquivo próprio, `src/areas/<area>.live.ts`, porque só a verificação depois do deploy e a documentação as carregam.
