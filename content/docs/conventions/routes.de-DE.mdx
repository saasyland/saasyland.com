title: "Routendateien"
description: "Die eine Form einer Seitenroute und einer Layout-Route: NAMESPACE oder NAMESPACES, ein einziger Loader mit Promise.all, ein Skeleton, das die Seite spiegelt, Such-Schemas und Links."
---

Jede Datei in `src/routes` hat dieselbe Form, sodass ein Leser, der eine kennt, alle kennt. Eine Routendatei setzt zusammen: Sie deklariert, was die Seite braucht, und platziert Komponenten. Widgets, Formulare, Dialoge und Tabellenspalten liegen in `src/presentation/components/custom`.

## Seitenrouten

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        onReorder={({ offset, row }) => move.mutateAsync({ courseId: row.id, offset })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        search={t("table.search")}
        selectable
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Die Komponente** ist eine lokale `const` namens `<Name>Page` und wird zuerst definiert. Kleines Markup, das nur diese Seite verwendet, darf als lokale Komponente darüber stehen, wie `CourseProgress` und `StartLink` in `_site._marketing.courses.$course.index.tsx`; alles mit eigenen Daten, einer Mutation oder eigenem Zustand kommt in eine Komponentendatei.
- **Ein Namespace.** `const NAMESPACE = "pages.<feature>.<page>"` steht direkt über `export const Route` und wird in `loadPageMetadata`, `preloadNamespaces` und `staticData` verwendet. Alles andere, was die Seite braucht, deklariert ihr Layout.
- **Ein `Promise.all`.** Der Loader startet alle Arbeiten gleichzeitig: Seitenmetadaten, den Namespace und jede Query, die die Komponenten lesen. Er gibt `{ locale, metadata }` für `head` zurück. Warte nie auf eine davon, bevor du die nächste startest.
- **`head: pageHead(ROUTES.X)`** baut Titel, Beschreibung, kanonische URL und Sprachalternativen aus den Metadaten in der Namespace-Datei.
- **Pfade stammen aus `ROUTES`** in `src/routes.ts`, das die Pfade aller Bereiche zusammenführt (siehe [Pfade und Navigation](#paths-and-navigation)); schreibe nie ein Pfadliteral.

Eine Seite, deren Titel aus einem Datensatz stammt, wartet auf diesen Datensatz und baut ihren Head aus den Loader-Daten, wie `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Layout-Routen

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Ein Layout deklariert `const NAMESPACES = [...] as const` über `export const Route` und lädt sie vor. Hat es keine, lässt es die Option weg; ein `namespaces: []` gibt es nicht.
- Ein Layout nennt jeden Namespace, den seine Seiten und deren Komponenten brauchen, auch die anderer Features, als einfache Strings in seinen `NAMESPACES`. `/app` listet `pages.license`, `pages.withdrawal` und `withdrawal.validations` auf, weil seine Übersicht die Lizenzkarte und das Angebot und seine Lizenzseite die Widerrufskarte zeigt; `/admin/users` listet `pages.admin.customers`, `pages.admin.orders` und `pages.admin.users.license` auf; und `/_site/_marketing` und `/_site/docs` listen `auth.validations` auf, weil ihre Footer das Newsletter-Formular zeigen, das Marketing-Layout außerdem `withdrawal.validations`. Fällt ein Feature weg, werden seine Nachrichtendateien gelöscht, und die Bereinigungsregel löscht jeden String, der eine davon nennt ([Testen](/docs/conventions/testing#tests-follow-the-features)).
- Die Komponente, sofern das Layout eine rendert, heißt `<Name>Layout` und platziert ein `<Outlet />`.
- Ein Guard gehört in `beforeLoad` des Layouts, dem der Bereich gehört: `beforeLoad: requireAdmin` in `admin.tsx`, `requireSignedIn` in `app.tsx`, beides Layouts des Auth-Bereichs. Guards entscheiden nur über die Navigation; jede Server Function prüft trotzdem ihre eigene Berechtigung.

## Reihenfolge der Optionen

`sort-keys` ist in `src/routes` abgeschaltet, weil TanStack Router Typen in der Reihenfolge der Deklaration ableitet. Optionen sind alphabetisch sortiert, außer dass `validateSearch` als Erstes kommt, vor allen Optionen, die die Suchparameter lesen:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Schreibe nie ein Array oder Objekt mit Daten inline in `createFileRoute`; deklariere es darüber als Konstante.

## Suchparameter

`validateSearch` ist ein `zod.object`, gebaut aus den Helfern in `src/lib/search-params.ts`:

| Helfer                            | Wert, wenn der Parameter fehlt oder fehlerhaft ist | Verwendung                           |
| --------------------------------- | -------------------------------------------------- | ------------------------------------ |
| `searchText()`                    | `undefined`                                        | Tokens, E-Mail-Adressen, Fehlercodes |
| `searchFlag()`                    | `undefined`                                        | Booleans                             |
| `searchParam(schema)`             | `undefined`                                        | Jedes andere Schema, etwa ein Pfad   |
| `searchChoice(choices, fallback)` | `fallback`                                         | Ein Tab oder eine Ansicht            |

Fehlender Text bleibt `undefined`, sodass ein Standardwert nie in eine URL gelangt, die der Router baut. Ein `searchChoice`-Parameter wird mit `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }` kombiniert, das den Standardwert aus der URL entfernt. Eine Seite, auf die eine andere Website Besucher zurückschickt, deklariert außerdem `search: { middlewares: [onlyDeclaredSearch(schema)] }` mit ihrem eigenen Schema, so wie `/app` und `/app/license` für den Checkout von Polar: Der Router baut ihre Adresse dann nur mit den deklarierten Parametern, und der Server leitet eine Adresse mit einem anderen Parameter auf dieselbe Adresse ohne ihn weiter, bevor eine Prüfung oder die Seite ihn liest. Schreibe nie von Hand Prüfungen wie `typeof search["x"] === "string"`; ergänze einen Helfer, wenn eine neue Art von Feld nötig ist. Braucht eine Kindkomponente einen Parameter, dessen Vorhandensein die Seite validiert hat, grenzt die Seite ihn ein und reicht ihn weiter, so wie `auth.reset-password.tsx` `token` an `ResetPasswordForm` übergibt. Seiten, die dieselben Parameter lesen, teilen sich ein Schema in der `.zod.ts` des Moduls, das sie lesen, das auch ihre Skeletons parsen, so wie `/app/license` und der Teil der Übersicht, den der Lizenzbereich beiträgt, mit `licenseSearchSchema` (`src/modules/license/license.zod.ts`).

## Skeletons

Navigation muss sich sofort anfühlen, daher hat jede Route, die eine Seite rendert, eine `pendingComponent`, die sie spiegelt: dasselbe Layout, dieselben Karten und dieselbe Anzahl an Zeilen.

- Skeletons liegen in der Pending-Datei des Bereichs (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) und verwenden `Skeleton` von shadcn.
- Skeletons liegen im Einstiegsskript jeder Seite, daher importiert ein Skeleton `Skeleton`, die shadcn-Primitive, andere Skeletons und die Konstanten, die seine Längen bestimmen, nie ein Formular oder die Datei, die eines enthält; `pending-imports.test.ts` schlägt fehl, wenn eines `@tanstack/react-form` erreicht (siehe [Performance](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Ein Textplatzhalter erhält das echte Typografie-Token plus `h-lh scale-y-70`, sodass er die Höhe der Zeile hat, die er ersetzt: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- Listenlängen stammen aus den Konstanten, die die Seite verwendet: `DataGridPending` in `data-grid-pending.tsx` zeichnet standardmäßig `DEFAULT_PAGE_SIZE` Zeilen, die Seitengröße jeder Admin-Tabelle.
- Ein Layout-Skeleton rendert die `pendingComponent` der ersten Route unterhalb seines Layouts, die für den aktuellen Pfad eine hat; `usePagePending(layout)` in `src/hooks/use-page-pending.ts` liest sie aus dem Routenbaum. So arbeiten `AdminPending`, `AppPending`, `AuthPending` und `MarketingPending` für ihre Layouts und `AdminUsersPending` und `AdminCourseSectionPending` eine Ebene tiefer. Die Route einer Seite ist deshalb die einzige Stelle, die ihr Skeleton nennt, egal welches Layout es zeigt; `/admin/users`, das zu `/admin/users/all` weiterleitet, setzt das Skeleton dieser Seite.
- Es gibt keine routerweite `defaultPendingComponent`. `src/router.tsx` setzt `defaultPendingMs` auf <RepositoryFact name="navigationPendingMs" unit="millisecond" /> und `defaultPendingMinMs` auf <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, beide aus `src/data/navigation.constants.ts`: Eine Navigation, die bis dahin nicht abgeschlossen ist, zeigt das Skeleton der Route, und das Skeleton verschwindet, sobald die Seite bereit ist, ohne länger stehen zu bleiben. Routen behalten diese Werte bei; die Messungen dahinter stehen unter [Performance](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once).
- Die Docs-Seiten zeichnen ihre Skeletons innerhalb des Docs-Layouts: `DocsIndexPending` und `DocsPagePending` füllen die Grid-Bereiche des Artikels und des Inhaltsverzeichnisses von Fumadocs, sodass eine Navigation zwischen Docs-Seiten die Seitenleiste auf dem Bildschirm hält. Die Seitenkomponente rendert das MDX in einer eigenen `<Suspense key={path}>`, sodass die Seitenleiste funktioniert, bevor der MDX-Chunk der Seite geladen ist, und eine Navigation das Server-HTML der vorherigen Seite ersetzt, statt es mit den Daten der nächsten Seite zu hydrieren.

## Links

- Router-Links erhalten eine Konstante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>` oder ein Routenmuster mit `params` für dynamische Pfade. `LinkButton` und `SidebarMenuLink` von shadcn erhalten `to` auf dieselbe Weise, und `AnchorButton` erhält ein `href` für eine Adresse außerhalb des Routenbaums.
- Füge einem Router-Link nie das Locale-Präfix hinzu; das Rewrite des Routers ergänzt es. Eine vollständige URL in der aktuellen Locale, für einen Wert, der den Router als String verlässt, kommt aus `router.buildLocation({ ... }).publicHref`, so wie `use-auth-redirect.ts` seine Anmeldelinks baut. `localizePathname` ist für URLs gedacht, die außerhalb eines Router-Kontexts oder für eine andere Locale gebaut werden: E-Mails, Weiterleitungsziele von Better Auth, Links in MDX und der Sprachumschalter.

## Pfade und Navigation [#paths-and-navigation]

Jeder Pfad und jeder Menüeintrag steht genau einmal in einer Liste, und ein Feature, das wegfallen kann, etwa die Kurse, die Produkte oder die Rechtstexte, ist darin ein Element, das seinen eigenen Pfad nennt. Fällt das Feature weg, werden seine Dateien und seine Namen gelöscht und mit ihnen jedes Element, das einen davon nennt, sodass die Listen weder eine Datei pro Feature noch ein Barrel brauchen. So setzt die `saasyland`-CLI ein Projekt aus Template-Layern zusammen. Nur `scripts/features.ts`, das die Anwendung nie lädt, listet die optionalen Features mit ihren Dateien und den Pfaden auf, die ihnen gehören, damit `bun run check:features` die Website ohne jedes von ihnen prüfen kann ([Testen](/docs/conventions/testing#tests-follow-the-features)).

| Was                                             | Deklariert in                                                                                                                                                                                                                           | Gelesen aus                                                                                                     |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Pfade                                           | `src/routes.ts`: ein `export const` pro Pfad                                                                                                                                                                                            | `import * as ROUTES from "~/src/routes"`                                                                        |
| Bei jedem Request gerenderte Pfade              | `REQUEST_RENDERED_ROUTES` in `src/routes.ts`                                                                                                                                                                                            | `isRequestRenderedRoute` in `src/routes.ts`                                                                     |
| Menüeinträge                                    | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` und `FOOTER_NAVIGATION` in `src/data/navigation.ts`, in der Reihenfolge, in der sie erscheinen | Die Sidebars, der Header, der Footer, die Befehlspalette und das Dashboard                                      |
| Layout-Namespaces                               | `NAMESPACES` in der Layout-Route                                                                                                                                                                                                        | Loader und `staticData` des Layouts                                                                             |
| Listen der Admin-Konsole und des Kundenbereichs | `DASHBOARD_STATS`, `DASHBOARD_PANELS`, `COMMAND_SEARCHES`, `USER_TABS`, `USER_PROFILE_SECTIONS` und `ACCOUNT_DELETION_NOTICES`, jeweils in der Komponente, die sie rendert                                                              | Diese Komponente, ihr Skeleton und die Route, die ihre Daten lädt                                               |
| Live-Checks                                     | `LIVE_SITE_CHECKS` in `src/lib/deployment.ts`                                                                                                                                                                                           | `verifyDeployment` ([Plattform und Tests](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)) |

`src/routes.ts` deklariert jeden Pfad und importiert nichts, weil jede Laufzeit die Datei lädt: der Browser, der Worker bei jedem Kaltstart, Bun-Skripte, Playwright, `vite.config.ts` und das Remotion-Projekt. Jede Datei importiert sie als einen Namespace, `import * as ROUTES from "~/src/routes"`, sodass jeder Pfad seinen Literaltyp behält und `<Link to={ROUTES.COURSES}>` weiterhin gegen den Routenbaum geprüft wird. Ein Pfad, der aus einem anderen gebildet wird, etwa `BLOG_FEED` aus `BLOG`, steht hinter diesem.

Die Listen, zu denen ein Bereich noch in einer eigenen Datei beiträgt, die Worker-Handler und die Vite-Plugins, behalten vorerst ihre Barrels. Ein Barrel enthält nur Zeilen der Form `export { … } from`, eine pro Bereichsdatei und nach Modul sortiert, wie `src/integrations/drizzle-orm/drizzle.schemas.ts`.

`src/data/navigation.ts` enthält die sieben Menüs als ausgeschriebene Listen, jeden Eintrag mit seiner Seite in `to`, dem vollständigen Schlüssel seiner Nachricht in `label` und, in der Admin-Konsole und im Kundenbereich, seinem Icon aus `lucide-react`. Das Admin-Menü gruppiert seine Einträge unter einer Sidebar-Gruppe, `key` aus `ADMIN_NAVIGATION_GROUP`, und der Footer seine Links unter einer Spalte, `key` aus `FOOTER_COLUMN`. Die Datei importiert nur `lucide-react`, `~/src/routes` und `~/src/data/navigation.constants`, weil das Remotion-Projekt das Admin-Menü liest und sein CI-Job nur die eigenen Pakete von Remotion installiert; `src/__test__/source-layout.test.ts` schlägt fehl, wenn sie etwas anderes importiert. Die Admin-Konsole und der Kundenbereich existieren nur mit Anmeldung, deshalb nennen ihre Einträge die Pfade des Auth-Bereichs und fallen mit ihm weg, so wie **Anmelden** im Header und im Footer:

```ts title="src/data/navigation.ts"
export const HEADER_NAVIGATION: readonly SiteEntry[] = [
  { hash: MARKETING_SECTION_IDS.PRICING, label: "navigation.core.header.pricing", to: ROUTES.HOME },
  { label: "navigation.courses.header.courses", to: ROUTES.COURSES },
  { label: "navigation.content.header.blog", to: ROUTES.BLOG },
  { label: "navigation.content.header.docs", to: ROUTES.DOCS },
  { label: "navigation.auth.header.signIn", signedIn: { label: "navigation.auth.header.account" }, to: ROUTES.SIGN_IN },
]
```

Ein Projekt ohne die Kurse hat kein `ROUTES.COURSES`, deshalb löscht die Bereinigungsregel den Eintrag **Kurse** im Header, und eine Gruppe oder Spalte, die dadurch leer wird, fällt mit ihm weg, so wie die Rechtsspalte des Footers in einem Projekt ohne die Rechtstexte.

Ein Header- oder Footer-Eintrag kann eine `signedIn`-Beschriftung nennen, die seine eigene für einen angemeldeten Besucher ersetzt, und sein Link führt dann zu dessen Arbeitsbereich: `/admin` für ein Konto mit Admin-Zugriff, `/app` für alle anderen. `Navigation`, `MobileMenu` und `Footer` lesen beide Menüs aus `useSiteNavigation` (`src/hooks/use-site-navigation.ts`), das die `signedIn`-Einträge einsetzt, sobald es den Arbeitsbereich des Besuchers kennt, und die Listen sonst unverändert zurückgibt. Den Arbeitsbereich nimmt es vom einzigen Hook in seinen `WORKSPACE_HOOKS`, `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`), der anhand der Rolle in der Sitzung mit `hasPermission` und der Berechtigung `admin: ["access"]` entscheidet, die `requireAdmin` prüft; ein Projekt ohne Anmeldung hat keinen Hook, seine Menüs bleiben also unverändert. Die öffentlichen Seiten sind vorgerendert, ihr HTML zeigt daher **Anmelden**; nach der Hydration fragt ein Browser, der das Cookie von Better Auth mit der zuletzt verwendeten Anmeldemethode hat, nach seiner Sitzung, und Header, mobiles Menü und Footer zeigen an dieser Stelle **Dein Konto**, gleich mit dem Link zum richtigen Arbeitsbereich. Jedes Menü vergibt die Keys seiner Links nach ihrer Stelle in der Liste, sodass React denselben Link ändert, statt ihn zu ersetzen, und ein Druck, der auf **Anmelden** beginnt, während die Sitzung lädt, trotzdem den Arbeitsbereich öffnet. Ein Browser, der sich nie angemeldet hat, fragt nichts ab. Bis ein Teil der Seite hydriert ist, liefert `useVisitorWorkspace` nichts, auch wenn der Browser die Sitzung schon hat, weil `useHydrated` während der Hydrierung durch React den Wert des Servers liefert: Ein Footer, der erst nach dem Eintreffen der Sitzung hydriert, rendert dasselbe **Anmelden** wie das HTML und wechselt danach, statt die Hydrierung zu brechen.

Jeder Admin-Eintrag öffnet eine Ansicht, die mit echten Daten arbeitet, und die Landingpage zählt sie alle. Eine Ansicht, deren Daten noch keine Quelle haben, bekommt keinen Eintrag (siehe [Admin-Dashboard](/docs/features/admin-dashboard#real-data-only)).

Die Seitenleiste des Kundenbereichs enthält den Eintrag **Lizenz** des Lizenzbereichs und ihre Ressourcen über der Support-Adresse die **Dokumentation** des Inhaltsbereichs. Der Kern braucht nur `/` und `/api` sowie im Header **Preise**, den einzigen Eintrag mit `hash`, der zum Preisabschnitt von `/` führt.

Eine Dashboard-Statistik in `DASHBOARD_STATS` hat ein `prefetch`, das der Loader von `/admin` ausführt, und einen Hook `useValue`, den `DashboardStats` aufruft, um die Zahl zu lesen.

`APP_STATEMENTS` in `auth.access.ts` deklariert die Berechtigungs-Statements, eines pro Ressource, und `scripts/features.ts` nennt die Statements eines Features, das wegfallen kann, etwa `APP_STATEMENTS.course`, sodass sie mit ihm wegfallen (siehe [Rollen und Berechtigungen](/docs/guides/roles-and-permissions)).

Die Listen in `src/data/navigation.ts` haben einen deklarierten Typ aus `src/data/navigation.constants.ts`, etwa `IconEntry` oder `SiteEntry`. Eine Liste, deren Einträge ein Projekt weglässt, etwa die Dashboard-Aktionen ohne den Zahlungsbereich, ist deshalb eine leere Liste, die trotzdem die Typprüfung besteht. `navigation.test.ts` prüft, dass das `to` jedes Eintrags ein Pfad des Routenbaums ist und dass kein Menü eine Seite oder eine Beschriftung zweimal nennt.

Das `label` eines Eintrags ist der vollständige Schlüssel seiner Nachricht, etwa `navigation.courses.admin.courses`, und die Nachricht liegt in der Datei des Features, dem die Seite gehört, `messages/<locale>/navigation.<feature>.json`, sodass mit dem Feature auch seine Beschriftungen wegfallen. Eine Komponente rendert sie mit `t(entry.label)` aus `useTranslations()`. Ein Admin-Abschnitt beschriftet seine Unterseiten für die Breadcrumbs in den `breadcrumbs` seines Eintrags, vom Pfadsegment zum Schlüssel, etwa `create` zu `navigation.courses.breadcrumbs.create`. Ein Tab der Benutzerverwaltung, eine Suche der Befehlspalette und eine Dashboard-Statistik nennen ebenfalls den vollständigen Schlüssel ihrer Beschriftung, etwa `navigation.team.userTabs.invitations`, `navigation.auth.search.users` und `dashboard.courses.learners`, und ein Dashboard-Panel liest seine Texte unter seinem `key` in `dashboard.<feature>.json`. Beide Arten von Dateien sind Root-Namespaces, sodass jedes Menü jeden Eintrag beschriften kann. Was zum Menü selbst gehört, bleibt in dessen Namespace: `groups.<group>` in `pages.admin.sidebar`, `columns.<column>` in `components.custom.footer` und der Call-to-Action, der Menü-Button und der Skip-Link des Headers in `components.custom.navigation`. `navigation.test.ts` schlägt fehl, wenn einem Eintrag, seiner Variante für angemeldete Besucher, einem Breadcrumb, einem Tab der Benutzerverwaltung oder einer Suche der Befehlspalette in einer Locale die Nachricht fehlt, und `admin-dashboard.component.test.tsx`, wenn sie einer Statistik fehlt.

Seiten, die der Worker bei jedem Request rendert, etwa `/admin`, `/auth` oder `/courses`, stehen in `REQUEST_RENDERED_ROUTES` in `src/routes.ts`. Das TanStack-Start-Plugin in `vite.config.ts` nimmt sie mit `shouldPrerender` (`src/lib/prerender.ts`), das `isRequestRenderedRoute` aufruft, vom Prerendering aus, sodass sie auch nicht in der Sitemap der Seiten stehen, und `buildPageHead` gibt ihnen die Karte der Website, sofern die Route kein eigenes Bild übergibt. Dass eine Seite bei jedem Request gerendert wird, hält sie nicht aus den Suchergebnissen heraus: Die Kursseiten stehen in einer Sitemap, die der Worker aus D1 schreibt (siehe [Suche und Social-Media-Vorschauen](/docs/features/seo#course-sitemap)). Vite löst den Alias `~` nicht auf, während es seine eigene Konfiguration lädt, deshalb importiert `prerender.ts` die Datei `src/routes.ts` über einen relativen Pfad.
