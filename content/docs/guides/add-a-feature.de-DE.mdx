---
title: "Feature hinzufügen"
description: "Durchgängige Anleitung von der Datenbanktabelle bis zur getesteten Seite, mit Verweisen auf die ausführlichen Anleitungen."
---

Ein Feature berührt meist jede Schicht: ein Tabellenmodul, seine Use-Cases, eine Route, Präsentationskomponenten, Messages und Tests. Die Kurse zeigen den vollständigen Weg: `src/modules/course`, `src/routes/admin.courses.index.tsx` und `src/presentation/components/custom/admin/courses/course-columns.tsx`.

## 1. Daten modellieren

Wenn das Feature neue Daten speichert, ein Modul für seine Tabelle hinzufügen und die Migration generieren.

- [Modul hinzufügen](/docs/guides/add-a-module)
- [Datenbankmigrationen](/docs/guides/database-migrations)

## 2. Festlegen, wer was darf

Die neuen Aktionen zum Statement der Ressource in `APP_STATEMENTS` (`src/integrations/better-auth/auth.access.ts`) hinzufügen und sie in `ROLES` Rollen zuweisen; ein Feature, das wegfallen kann, nennt eine neue Ressource in seinen `names` in `scripts/features.ts`.

- [Rollen und Berechtigungen](/docs/guides/roles-and-permissions)

## 3. Operationen schreiben

Pro Operation einen Use-Case mit Middleware, Validator, Handler und Query- oder Mutation-Optionen hinzufügen.

- [Use-Case hinzufügen](/docs/guides/add-a-use-case)
- [Server-Funktionen](/docs/guides/server-functions)

## 4. Route hinzufügen

1. Den Pfad in `src/routes.ts` und die Menüeinträge in den Listen von `src/data/navigation.ts` deklarieren, jeden mit dem vollständigen Schlüssel seiner Beschriftung, und die Pfade eines optionalen Features in dessen `names` in `scripts/features.ts` nennen (siehe [Pfade und Navigation](/docs/conventions/routes#paths-and-navigation)).
2. Eine flache Route-Datei für den Bereich anlegen: `src/routes/admin.<feature>.tsx` unter dem Admin-Layout, `src/routes/app.<feature>.tsx` unter dem Layout für angemeldete Kunden oder `src/routes/_site._marketing.<page>.tsx` für eine öffentliche Seite.
3. Der Route-Konvention folgen: `const NAMESPACE`, `staticData: { namespaces: [NAMESPACE] }`, `head: pageHead(ROUTES.X)`, ein Loader, der in einem einzigen `Promise.all` auf Metadaten, Messages und die Daten des ersten Teils seiner Antwort wartet und den Rest in die Skeletons der Seite streamt, sowie das eigene Skeleton der Seite als `pendingComponent`, das das Layout-Skeleton auch zeigt, wenn jemand von woanders in das Layout wechselt (siehe [Lade-Skeletons](/docs/architecture/delivery-layer#lade-skeletons)).
4. Der `beforeLoad`-Guard des Layouts (`requireAdmin` für `/admin`, `requireSignedIn` für `/app`) schützt die Seite. Die Server-Funktionen autorisieren trotzdem jeden Aufruf selbst.

- [Admin-Seite hinzufügen](/docs/guides/add-an-admin-page)
- [URL-Zustand](/docs/guides/url-state)

## 5. UI bauen

Widgets, Dialoge, Formulare und Tabellenspalten im flachen Ordner des Bereichs ablegen, `src/presentation/components/custom/<area>/`, bei einem Feature des Adminbereichs in `src/presentation/components/custom/admin/<feature>/`, jeweils eine Komponente pro Datei. Jede Komponente liest ihre eigenen Übersetzungen und Daten; die Route setzt sie nur zusammen.

- [Datenraster hinzufügen](/docs/guides/add-a-data-table)
- [Formulare und Validierung](/docs/guides/forms-and-validation)

## 6. Messages hinzufügen

Den Seiten-Namespace und gegebenenfalls einen Validierungs-Namespace in jeder Locale anlegen. Seiten-Namespaces benötigen `metadata.title` und `metadata.description`.

- [Internationalisierung und Locales](/docs/guides/i18n-messages)
- [E-Mail-Vorlagen](/docs/guides/email-templates), wenn das Feature E-Mails versendet

## 7. Testen und prüfen

Die Use-Cases, Komponenten und die Route mit Tests abdecken und anschließend die Gates und die Specs des Features ausführen; die CI führt die gesamte Browser-Suite aus, bevor der Pull-Request gemergt wird:

```sh
bun run check
bun run test:coverage
bun run build:test
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

- [Tests schreiben](/docs/guides/writing-tests)
- [Sicherheits-Checkliste](/docs/guides/security-checklist)
