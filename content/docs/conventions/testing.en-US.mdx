Every change ships with the tests that prove it, in the same commit, and coverage stays at <RepositoryFact name="coverageThreshold" unit="percent" /> for lines, statements, functions and branches. A bug fix comes with a test that fails without the fix.

## Projects

`vite.config.ts` defines three Vitest projects, chosen by the file suffix. Tests import their API from `vite-plus/test` and live in `__test__/` beside the code they cover.

| Suffix                 | Project       | Use it for                                                                                                                                                         |
| ---------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `.test.ts`             | `node`        | Use cases, loaders, `head`, schemas, utilities: anything that runs on the server                                                                                   |
| `.integration.test.ts` | `integration` | Better Auth, payment and licence flows, the D1 adapter and message loading, with timeouts of <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Components and pages in jsdom                                                                                                                                      |

`src/platform/testing/mocks/cloudflare.ts` replaces `cloudflare:workers` in every project: D1 is an in-memory `node:sqlite` database built from every checked-in migration, KV and a bucket for each R2 binding of the `test` environment in `wrangler.jsonc` are in-memory stores. `resetTestBindings()` empties KV, the bucket and the rate-limit table before each test, and each suite's seed function resets the rows it depends on. No test talks to Cloudflare, Polar, Resend or an OAuth provider: `fetch` reaches the strict doubles in `mocks/resend.ts` and `mocks/polar.ts`, which validate every request against the SDKs' request models and fail the test on one the provider would refuse. Tests assert what the double received instead of mocking an SDK method, and auth suites drive the real `auth.server.ts` configuration through `auth.harness.ts`.

## Testing a server function

Call it through its exported options, so the test exercises the real middleware, validation and handler. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts`:

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` and `executeMutation(options, variables)` from `src/platform/testing/lib/query.ts` run the options in a fresh `QueryClient`.
- The session comes from `createAuthSessionFixture` in `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts`; every permission is tested from the side that must be refused as well (`it("is for staff only")`).
- Seed data lives in the module's `__test__/fixtures/`, with its IDs in named objects (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` deletes the rows it owns and inserts them again through Drizzle, so every test starts from the same state.
- In the `component` project a server function rejects, because jsdom stands for the browser. Component tests give a route its loader data or mock the `queryFn` and `mutationFn` of the options the component reads.

## Assertions use the code's names

- Expected statuses, kinds, roles and error codes are the constants the code uses: `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. A test never repeats a domain string literal, and neither does the e2e data or the test seed: `e2e/data/courses.ts` writes `kind: COURSE_KIND.COURSE`.
- Schema tests are the one place a stored value is written out: `license.schema.test.ts` pins `expect(LICENSE_STATUSES).toStrictEqual(["active", "revoked", "refunded"])`, so changing a value the database holds fails a test instead of needing a migration nobody wrote.
- The browser suite imports its constants from the application (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`), so it can import only files that load outside the Worker. Polar's values come from `polar.constants.ts`, which reads no environment: `e2e/fixtures/license.ts` and the sandbox journey take the order statuses from `POLAR_ORDER_STATUS`, and the order itself comes from `src/platform/testing/lib/polar.ts`. The tier product IDs are the exception: `POLAR_PRODUCT_IDS` reads `cloudflare:workers`, so the browser suite reads them from `.env.test`.
- Component tests read expected copy from the English message files, as `admin-course-routes.component.test.tsx` does with `import labels from "~/messages/en-US/pages.admin.courses.json"` and `labels.form.kinds.course`, and find elements by role and accessible name.
- A test that needs a type reads it from a typed source or checks it at runtime with `toHaveProperty`; it never casts.
- Test names describe behaviour as a sentence: "lists every course with its lesson count, drafts included".

## Coverage

`bun run test:coverage` fails below <RepositoryFact name="coverageThreshold" unit="percent" /> on any of the four metrics for `src/**/*.{ts,tsx}`. Tests, `__test__/`, declaration files, `src/routeTree.gen.ts`, the shadcn primitives and `src/platform/testing/` are excluded. The gate is kept meaningful:

- **Delete branches that can never run** instead of covering them with stubs. A `?? fallback` on data that is always present, or an optional chain on a value that cannot be `undefined`, is removed from the source, not reached by stubbing a global.
- **Cover real behaviour.** Pending states hold the request open with `Promise.withResolvers()`, assert the pending UI, resolve inside `act` and assert the idle UI, as `expectPending` and `expectIdle` do in `auth-forms.component.test.tsx`.
- **Keep assertions when a rule bites.** When a test passes `max-statements`, extract a named helper instead of dropping checks.
- **Load every message file.** `i18n.messages.test.ts` loads every namespace of every locale, which is what covers the `import.meta.glob` lines in `i18n.loaders.ts`. A new message file is covered by it automatically.

## Tests on a busy machine

Vitest's time limit and the one-second budget of `waitFor` and `findBy*` count wall-clock time, so a test that does work its behaviour does not need, or that waits on a timer, fails on a busy machine although nothing is broken. The default time limit stays as it is; a slow test is made to do less:

- **A check over many files runs one test per file.** `check-content.test.ts` runs `pageProblems` for each English page with `it.each(sourcePages())`, and a drift names its page.
- **What a component suspends on is loaded before it renders**, as `preloadNamespaces` does for translations. When the loading is what the test is about, the test resolves it inside `act`, as `translations-provider.component.test.tsx` does: content that resumes outside `act` appears only after React's reveal throttle, on a real timer, and the test has to poll for it.
- **A test replaces a module once instead of importing the component again.** `affiliate-referral.component.test.tsx` mocks `AFFILIATE_PROGRAM` once and sets it in each test. Importing a component after `vi.resetModules()` evaluates its whole import graph inside the test.
- **Fixtures that every test reads are built once per file**, such as the messages from `getTestMessages`.
- **A form is filled with `user.paste` unless its keystrokes are the behaviour under test.** `fill` in `admin-course-routes.component.test.tsx` clicks the field and pastes; `user.type` runs the form's validation and rendering once per character.
- **A long option list is cheap to re-render.** The time zone combobox in `preferences-card.tsx` passes its options to `ComboboxList` as memoized `items`, so React Aria reuses them when the form re-renders.

## Tests follow the features

The features whose files and paths `scripts/features.ts` names (see [Paths and navigation](/docs/conventions/routes#paths-and-navigation)) own their tests as well, so the `saasyland` CLI can leave a feature out of a generated project together with its tests while every remaining test still passes.

A test file covers one feature or one source file. A feature's admin pages are tested with their skeletons and breadcrumbs in `src/routes/__test__/admin-<feature>-routes.component.test.tsx` and their loaders in `admin-<feature>-loaders.test.ts`. A layout skeleton test renders the layout skeleton with `createTestRouter(path, routeTree)` from `src/platform/testing/lib/render.tsx`, a router on the real route tree, and the course skeletons are tested in `admin/__test__/courses-pending.component.test.tsx`, because `admin-course-routes` rebuilds the course routes for its own router; `admin-layout`, `admin-dashboard` and `admin-loaders` test the admin shell itself and name no feature. Unrelated files get one test file each, such as `background.component.test.tsx` and `wordmark.component.test.tsx`, and each API handler has its own: `src/routes/api/__test__/auth.test.ts` and `index.test.ts`. `cli.v1.test.ts` covers the route files of the CLI licence API, whose behaviour is tested in `src/modules/license/__test__/license.api.integration.test.ts`.

A list that spans the features has no barrel: each feature declares its part in a file of its own, and the one file that reads the list imports each part and writes them out in one literal list, so leaving a feature out deletes its file and, with the import, its element:

| List             | Each feature declares                                                                                                              | Listed by                                                        |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Admin query data | `seed<Feature>Queries` and its row factories in `src/presentation/components/custom/admin/__test__/<feature>.fixtures.ts`          | `adminQueryClient()` in `fixtures.tsx`                           |
| Enum labels      | `src/integrations/use-intl/__test__/<feature>.labels.ts`                                                                           | `ENUM_LABELS` in `enum-labels.test.ts`, the core.s labels inline |
| D1 rows          | `src/integrations/drizzle-orm/__test__/<feature>.rows.ts`                                                                          | `d1.integration.test.ts`                                         |
| Browser pages    | `e2e/data/<feature>.pages.ts`                                                                                                      | `ENTRIES` in `e2e/data/pages.ts`, with the home pages inline     |
| Test database    | `e2e/data/<feature>.seed.ts`                                                                                                       | `scripts/seed-test.ts`                                           |
| Flow inventory   | `e2e/data/<feature>.flows.ts`: the feature's flows, each with the test that proves it or the reason it is missing                  | `FLOWS` in `scripts/check-flows.ts`                              |
| Public queries   | a query with `public: true` in its own source file                                                                                 | `PUBLIC_QUERIES` in `auth.session.test.ts`, one property a query |
| Provider doubles | `src/platform/testing/mocks/<provider>.ts`: one `<PROVIDER>_PROVIDER_DOUBLES` list, each double an `origin`, `respond` and `reset` | `DOUBLES` in `mocks/providers.ts`                                |
| Polar catalogue  | `src/modules/<module>/__test__/fixtures/<feature>.polar-catalogue.ts`: the products and licence-key benefits the feature sells     | `CATALOGUES` in `mocks/polar.ts`                                 |
| Test Worker      | `e2e/data/<feature>.worker.ts`: set-ups and test endpoints                                                                         | `ENTRIES` in `src/platform/testing/worker.ts`                    |

No file declares an empty list for the core: an entry every project has is written in the list itself, as the home pages are in `e2e/data/pages.ts`, and `scripts/seed-test.ts` runs Wrangler only when a feature seeds rows. A feature's page object comes with a fixture of its own: `e2e/fixtures/auth.ts` extends the core `test` of `e2e/fixtures/test.ts` with `authPage`, and the specs that sign in import `test` from it. A feature's email helpers live in a fixture file of their own too, such as `e2e/fixtures/license-emails.ts` and `e2e/fixtures/invitation-emails.ts`, beside the shared `getSentEmails`, `latestEmail` and `linkTo` in `e2e/fixtures/emails.ts`, and a feature's browser double joins `BROWSER_DOUBLES` in `e2e/fixtures/test.ts`, as `servePolarCheckout` does.

Helpers that several features use are written once: `renderAdmin` and `renderAdminPage` in `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` in `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` and `busyMarkup` in `src/platform/testing/lib/skeleton.tsx`, and in the browser suite `AuthPage.signIn`, `BasePage.leaveWhileLoading` and the `pageWithoutJavaScript` fixture. The specs of public pages, such as `accessibility.spec.ts` and `theme.spec.ts`, sign in to no account; `workspaces.spec.ts` checks the signed-in pages, their accessibility and their theme.

A test of shared code that needs an entry the features contribute declares its own instead of reading one a feature declares. `dashboard-actions.component.test.tsx` replaces `ADMIN_DASHBOARD_ACTIONS` with a test-local action, so `DashboardActions` and the action placeholders of `AdminDashboardPending` stay covered in a project without the payments feature, which declares the dashboard actions today. `server.test.ts` serves each request handler's files and runs each document rewrite through the Worker in a test that names the feature's own module, so leaving the feature out deletes the test, `vite-config.test.ts` loads `VITE_PLUGINS` in their order, and a vendor's plugins are tested beside them, such as in `zod.vite.test.ts`. Shared code that only optional features render gets a test of its own: `pending-blocks.component.test.tsx` covers the field skeleton that the course admin skeletons use. `auth.access.test.ts` checks what each role is granted, each feature checks its own statements in `auth.access.<feature>.test.ts`, such as `auth.access.courses.test.ts`, and `auth.access.website.test.ts` pins every role's permissions on the website.

`auth.server.test.ts` lists the id of every Better Auth plugin in order, and `navigation.test.ts` checks the menus without expecting any one entry, so it passes whichever entries a project keeps. `translations-provider.component.test.tsx` samples core namespaces, and the auth tests sample the auth feature's own data and paths, such as the session list and `/app/settings`.

The licence route test replaces the courses' `CourseUnlocks` with a test-local section and its catalogue query with a mock, the licence skeleton test does the same with `CourseUnlocksPending`, and the course tests replace the course access grants of `lesson.access.ts` with `TEST_COURSE_ACCESS` through `withTestCourseAccess` (`src/modules/course/__test__/fixtures/course-access.ts`), so neither feature's tests read the other. `src/modules/lesson/__test__/lesson.access.license.test.ts` covers what joins them: the licence's grant, with a snapshot of who may watch which lesson for a guest, an account, staff and every licence tier and status.

A test that pins the whole website, such as `navigation.website.test.ts` with the order of every menu, belongs to the website only; the templates do not generate it.

`scripts/features.ts` lists the files of each optional feature as globs, the names the feature owns in files that stay, such as each feature's paths in `src/routes.ts`, and the features it requires, and `bun run check:features` checks that the site still works without them. One scenario leaves out only the features that only the website has; each of the others also leaves out the courses, the billing features, the content or the auth feature. For each scenario the script deletes the files of those features and of every feature that requires one of them, then prunes the files that stay with one rule, the one the `saasyland` CLI follows when it leaves a feature out:

1. It deletes the names the removed features own, each with its declaration or object property.
2. A removed reference is an identifier imported from a deleted file, a use of a removed name, such as `ROUTES.COURSES` once `src/routes.ts` no longer declares it, a function that calls `import()` on a deleted file, or a `vi.mock`, `vi.doMock`, `vi.unmock` or `vi.doUnmock` that names a deleted module. Every `import` and `export … from` of a deleted file goes, and so does every import of a module that only a deleted declaration file declares, such as `virtual:repository-facts`.
3. A removed reference in the callback of a test, that is an `it` or a `test` in any of its forms, such as `.each`, `.skip` or `.only`, or a Playwright `test.step`, takes the whole test with it. For any other removed reference it deletes the nearest of these units that can go; a function, class, `return` statement, condition or export never goes whole, so it reports a reference that only one of them encloses by file, line and column:
   - the nearest array element within its top-level statement, or else the nearest object property, spread, type member or JSX child, without crossing a statement;
   - the expression statement around it, at the top of a module, a `describe` or a hook such as `beforeEach`, and inside any other function only when everything it names from outside itself goes;
   - the variable declarator around it, when its value is neither a function nor a class and everything its initializer names goes; the names it binds are then removed names too, and the declarator goes only if every use of them goes by this same rule. A value that also draws on code that stays, such as the link `signedInDestination(entry, workspace)` builds from a menu entry, stays and is reported, because it is the design that has to change, not the pruning;
   - the hook or the `describe` around it.
4. When that empties an array that is a property of an array element, the element goes too, as a menu group with no entries left does. So do a test whose `.each` table it empties, a test, step, hook or `describe` whose callback it empties, a `describe` with no test left, and a loop or a callback with an empty body, the callback together with the unit around it. When it would empty the body of a function or a condition, the statements stay and it reports their references.
5. It deletes each string array element that names the namespace of a deleted message file.
6. It deletes the import specifiers, the declarations that are not exported, at any depth, and the array pattern elements that nothing references any more, leaving a hole before an element that stays, and repeats until nothing changes. It deletes a `*.test.*` or `*.spec.*` file left without a test.

`scripts/prune-references.ts` applies the rule to the syntax trees of the oxc parser, and `scripts/module-bindings.ts` resolves every name to the declaration it refers to, so a parameter or a local of the same name is never taken for an import. `scripts/test-cases.ts` finds the tests, groups, hooks and mocks among the calls of what a file imports as `it`, `test`, `describe`, a hook or `vi`, under any local name, `scripts/prune-units.ts` chooses the unit around each reference, and `scripts/prune-edits.ts` writes the deletions, keeping the wider of the two gaps around a deleted statement, so the blank line between groups of statements stays. Generated files, which `.gitattributes` marks `linguist-generated`, are copied as they are, and the check generates the route tree again. The script then copies the files that Git tracks or would add to a temporary directory, the pruned ones in place of the originals, formats the pruned files with `vp fmt`, generates the class-name tables, the content collections while the content feature stays and the route tree, with `scripts/generate-routes.ts`, runs `tsc --noEmit` over `src`, `e2e`, `scripts` and `vite.config.ts`, and runs `check:i18n` on the messages that are left. A scenario fails on a reference the rule cannot prune, on any type error and on any translation error, and `src/__test__/check-features.test.ts` fails when a glob matches no file or a name is not declared in its file. The fix for a reference the rule cannot prune is to put the code where the [layout](/docs/architecture/directory-structure) says, never an exception in the pruner. CI runs one job per scenario, and a failing scenario fails the run ([CI/CD](/docs/tooling/ci-cd#checks)).

## Browser tests

Playwright runs the built test Worker: `bun run build:test` compiles it with local D1 and KV under `.wrangler/test`, `bun run db:reset:test` recreates that database and seeds the accounts, video and course in `e2e/data`, and the test entry captures outgoing email at `/__test/emails` so a spec can follow a verification link.

- Specs are named after the flow (`course-admin.spec.ts`, `auth-redirect.spec.ts`) and drive the page through roles and accessible names, with page objects in `e2e/pages/`.
- Each spec creates the data it changes with unique values, such as a slug built from `crypto.randomUUID()`, and signs in from its own `CF-Connecting-IP` header, so specs can run in parallel and rerun without colliding with each other or with rate limits.
- A test that changes seeded data, such as the machines on a licence, gets seeded records of its own, one for each parallel worker, so no two running tests change the same record. `cli-licence-api.spec.ts` activates machines on the licence that `TEST_CLI_LICENSES` in `e2e/data/licenses.ts` seeds for each worker's `parallelIndex`, which Playwright never gives to two workers at once, and its `cliMachine` fixture releases the machine when the test ends, so a retry starts from the seeded licence. `TEST_LICENSE`, which `license.spec.ts` reads, keeps only its seeded machine.
- A spec acts on a page only after `waitForAppReady()` from `e2e/pages/base-page.ts` has returned, after client-side navigations too. It returns once TanStack Router has rendered the current URL, which the automatic `recordRenders` fixture records from the router's `onRendered` event, because a client-side navigation changes the URL before the next route renders. Route content can hydrate after that render, so a spec that depends on a component's own state, or presses a link outside the content before the content has hydrated, first calls `waitForHydration(element)`, which waits until React has hydrated the element and everything in it; `LandingPage.goto()` does this for the landing page's `main`. A spec may leave a page while it loads, as a visitor can, and one that collects page errors over several direct visits opens each visit in its own tab, as `auth-routing.spec.ts` does, or leaves each page only once its network is idle (`page.waitForLoadState("networkidle")`), as `workspaces.spec.ts` does, because a page starts some requests only after it has hydrated, such as a sidebar badge or a video's segments. A spec that collects page errors leaves a page only after its client-side navigation has rendered: WebKit reports a request that the page starts after the spec has begun to leave it as a page error, `Fetch API cannot load … due to access control checks.`, even though the app handles the failed request.
- A spec that must prove a text never appears, not only that it is gone at the end, calls `watchForText(text)` from `e2e/pages/base-page.ts` before the change and asserts afterwards that the text never showed: a `MutationObserver` in the page records it the moment it renders. The upgrade test in `checkout-funnel.spec.ts` does this for the thanks for the old tier, and the journey suite for the thanks for any tier but the one bought.
- Every spec fails when a page breaks its Content Security Policy: the automatic `cspViolations` fixture in `e2e/fixtures/test.ts` logs each `securitypolicyviolation` event and expects none when the test ends. A spec that causes one on purpose takes it with `cspViolations.splice(0)`, as `content-security-policy.spec.ts` does. The suite runs the production build of `build:test`, because the dev server sends no script policy.
- Pull requests and the merge queue run every spec in Chromium and in WebKit; locally `bun run test:e2e:pr` runs them in Chromium and `bun run test:e2e` in both. Pushes to `main` run WebKit again, and a weekly schedule runs both.
- A spec that reads the clipboard takes the `readClipboard` fixture from `e2e/fixtures/test.ts`, which grants the clipboard permissions the browser knows before the spec starts: Chromium `clipboard-read` and `clipboard-write`, WebKit only `clipboard-read`, because WebKit has no write permission and lets the click that copies write to the clipboard, as Safari does.
- A spec that performs a flow end to end and asserts its outcome is named by that flow in `e2e/data/<feature>.flows.ts`, by its spec file and full title. `bun run check` fails when a flow names a test that the suite does not have, so a renamed test takes its flow with it in the same commit, and a flow that no test proves says why. See [Test coverage](/docs/tooling/test-coverage).
- A route, flow or visual fix that unit tests cannot see gets a spec: the accessibility scans and the navigation regressions in `navigation.spec.ts` and in the specs of the features they concern, such as `content.spec.ts`, `legal.spec.ts` and `landing.spec.ts`, are examples. A spec that scrolls makes the page tall enough itself, as the scroll test in `navigation.spec.ts` does, rather than relying on the length of a page. A section that fills in after the page loads keeps its height, so a spec that scrolls never has to load one first: a section that changed height above the viewport moved what the visitor was reading, and WebKit stopped a smooth scroll when scroll anchoring made up for it. The course block's specs in `landing.spec.ts` hold its request, let it succeed or fail, and check that the block keeps its height and that no layout shift is reported.
