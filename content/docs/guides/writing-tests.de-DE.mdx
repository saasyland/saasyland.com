title: "Tests schreiben"
description: "Wo Tests liegen, wie die Vitest-Projekte und Test-Bindings funktionieren, das Coverage-Gate und Playwright."
---

Vite+ führt Vitest (`vp test`) in drei Projekten aus. Tests liegen in einem `__test__`-Ordner neben dem Code, den sie abdecken, und importieren ihre APIs aus `vite-plus/test`.

| Projekt       | Dateien                          | Umgebung |
| ------------- | -------------------------------- | -------- |
| `node`        | `__test__/*.test.ts(x)`          | Node     |
| `integration` | `__test__/*.integration.test.ts` | Node     |
| `component`   | `__test__/*.component.test.tsx`  | jsdom    |

Einen Test nach seiner Quelldatei benennen: `category.zod.ts` wird durch `__test__/category.zod.test.ts` abgedeckt.

## Befehle

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
```

`bun run test` verwenden, nicht `bun test`: Nur Vitest lädt die Projekte, Umgebungen und die Setup-Datei.

## Coverage-Gate

`bun run test:coverage` schlägt fehl, wenn Zeilen, Anweisungen, Funktionen oder Verzweigungen des Anwendungscodes unter `src` unter **<RepositoryFact name="coverageThreshold" unit="percent" />** liegen. Tests, `src/platform/testing`, die shadcn-Primitives und generierte Dateien sind ausgenommen. Echtes Verhalten abdecken und Verzweigungen, die nie ausgeführt werden können, löschen, statt Globals zu stubben, um sie zu erreichen. Berichte werden nach `coverage/` geschrieben.

## Test-Laufzeitumgebung

- `src/platform/testing/setup.ts` registriert die jest-dom-Matcher, setzt die Bindings vor jedem Test zurück und leitet jedes `createServerFn` durch `withTestRpc`, sodass Aufrufe die echte Middleware und den echten Validator durchlaufen. Das gilt in den Projekten `node` und `integration`. Im Projekt `component` schlägt eine Serverfunktion fehl, weil jsdom der Browser ist.
- `cloudflare:workers` wird zu `src/platform/testing/mocks/cloudflare.ts` aufgelöst. D1 ist eine In-Memory-SQLite-Datenbank, auf die alle eingecheckten Migrationen angewendet sind, KV und der R2-Bucket `MEDIA` sind In-Memory-Maps, und `flushWaitUntil()` wartet auf Hintergrundaufgaben. `createEdgeCache()` aus `mocks/cache.ts` ersetzt den Workers-Cache durch einen Stub.
- `.env.test` liefert Dummy-Zugangsdaten. `fetch` erreicht strikte Test-Doubles von Resend und Polar (`mocks/resend.ts`, `mocks/polar.ts`), und jeder andere Host schlägt fehl, als wäre der Rechner offline, sodass nichts ihn verlässt. Ein Request, den der Anbieter ablehnen würde, lässt den Test fehlschlagen.
- `renderWithRouter` in `src/platform/testing/lib/render.tsx` rendert Komponenten mit einem echten Router und `QueryClient`.

## Use Case testen

Gekürzt aus `src/modules/category/use-cases/__test__/create-category.test.ts`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"

import { executeMutation } from "~/src/platform/testing/lib/query"

import { createAuthSessionFixture } from "~/src/integrations/better-auth/__test__/fixtures/auth.session.fixture"
import { ROLE_CODES } from "~/src/integrations/better-auth/auth.access"
import type { auth } from "~/src/integrations/better-auth/auth.server"
import * as authServer from "~/src/integrations/better-auth/auth.server"

import { ERROR_CODES } from "~/src/modules/_core/constants/errors"
import { CATEGORY_KIND } from "~/src/modules/category/category.constants"
import { createCategoryMutation } from "~/src/modules/category/use-cases/create-category"

const getSessionMock = vi.hoisted(() => vi.fn<(typeof auth.api)["getSession"]>())

vi.mock(import("@tanstack/react-start/server-only"), () => ({}))

describe("create-category", () => {
  it("returns a domain error when the caller is not an admin", async () => {
    vi.spyOn(authServer.auth.api, "getSession").mockImplementation(getSessionMock)
    getSessionMock.mockResolvedValue(
      createAuthSessionFixture({ role: ROLE_CODES.CUSTOMER, userId: "01900000-0000-7000-8000-000000000001" }),
    )

    await expect(executeMutation(createCategoryMutation, { kind: CATEGORY_KIND.CATEGORY, name: "SaaS Plans" })).rejects.toThrow(
      ERROR_CODES.FORBIDDEN,
    )
  })
})
```

Jedes Ergebnis eines Use Case testen: Erfolg, jeden `AppError`-Code, fehlende Session und fehlende Berechtigung. Domänenwerte und Fehlercodes stammen aus ihren Konstanten (`CATEGORY_KIND`, `ERROR_CODES`), nie aus wiederholten Strings.

## Gegen Resend und Polar testen

Das SDK von Resend oder Polar nicht mocken. Den Code aufrufen, der den Request sendet, und prüfen, was das Double empfangen hat. `getSentEmails(recipient)` aus `mocks/resend.ts` gibt die zugestellten E-Mails mit ihrem gerenderten HTML und ihrem Idempotenzschlüssel zurück; `mocks/polar.ts` hält die Checkouts, Bestellungen und Lizenzschlüssel, und seine Funktionen bringen einen Kauf voran: `payPolarCheckout`, `grantPolarLicenseKey`, `refundPolarOrder`, `revokePolarLicenseKey` und `activatePolarLicenseKey`. Gekürzt aus `src/modules/license/__test__/license-purchase.integration.test.ts`:

```ts
const buyer = await signUpAndVerify()
const order = await paidOrder(buyer, LICENSE_TIER.COMPLETE)

expect(await deliver(LICENSE_WEBHOOK_EVENTS.onOrderPaid, order)).toBe(HTTP_STATUS.OK)
expect(await currentLicense(buyer)).toMatchObject({ status: LICENSE_STATUS.ACTIVE, tier: LICENSE_TIER.COMPLETE })
```

`paidOrder` startet den Checkout über das echte `startCheckout` und bezahlt ihn im Double. `deliver` signiert das Event mit `signedPolarWebhook` aus `lib/polar.ts`, sendet es per POST an den Polar-Endpunkt von Better Auth und gibt den Status der Antwort zurück, sodass die Signaturprüfung, das Plugin und die Handler in `license.webhooks.ts` alle laufen. Um zu testen, wie die Anwendung mit einem Fehler des Anbieters umgeht, einen einzelnen Request mit dem Fehler des Anbieters beantworten, wie es `resend.utils.test.ts` tut: `vi.spyOn(globalThis, "fetch").mockResolvedValueOnce(Response.json(error, { status }))`.

## Auth-Ablauf testen

Auth-Suites laufen gegen das echte `auth` aus `auth.server.ts`. `src/integrations/better-auth/__test__/fixtures/auth.harness.ts` legt Konten so an, wie es ein Besucher tut: `signUp`, `verifyEmail` (das dem Token in der zugestellten E-Mail folgt und die Session zurückgibt, die es öffnet), `signIn` und `signUpAndVerify`. `browserHeaders()` gibt jedem Request seine eigene `CF-Connecting-IP`, sodass die Rate-Limits von Better Auth wie in Produktion gelten, ohne dass ein Test das Kontingent eines anderen aufbraucht. Vor dem Lesen einer E-Mail, die Better Auth im Hintergrund sendet, auf `flushWaitUntil()` warten.

## Komponente testen

Komponententests rendern mit echten Messages aus `messages/en-US`, mocken das Use-Case-Modul, das die Mutation-Optionen bereitstellt, und steuern die UI mit Testing Library und `userEvent`. Für Ladezustände den gemockten Request mit `Promise.withResolvers()` offen halten, die Lade-UI prüfen, dann innerhalb von `act` auflösen und die UI im Ruhezustand prüfen. Eine Komponente, die sich nach einer Verzögerung ändert, wird mit Fake Timers getestet (`vi.useFakeTimers()`, dann `vi.advanceTimersByTimeAsync` innerhalb von `act`), nie durch Warten in Echtzeit, und der `QueryClient` eines Routentests hält die Daten, die sein Loader geladen hat, frisch (`staleTime: Infinity`), sodass die Rendergeschwindigkeit des Rechners nie beeinflusst, wie oft eine Query läuft. `userEvent.setup({ delay: null })` steuert die UI ohne echten Timer zwischen den Tastenanschlägen. `src/presentation/components/custom/__test__/newsletter-form.component.test.tsx` ist ein vollständiges Beispiel. Ein Routentest gibt der Route ihre Loader-Daten, und ein `node`-Test deckt den Loader über `getRouter()` ab: `src/routes/__test__/marketing-routes.component.test.tsx` und `marketing-loaders.test.ts` sind die beiden Hälften.

## Browser-Tests

Playwright-Specs liegen in `e2e/specs`, Page Objects in `e2e/pages` und Fixtures in `e2e/fixtures`. Sie laufen gegen die gebaute Testanwendung mit lokalem D1, KV und R2 in `.wrangler/test` und den vorbefüllten Konten aus `e2e/data/accounts.ts`. Lokal migriert, befüllt, baut und startet Playwright diese Anwendung selbst.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:ui
```

Der Test-Worker installiert dieselben Test-Doubles von Resend und Polar und zeichnet versendete E-Mails auf, sodass eine Spec den Verifizierungslink aus `/__test/emails?to=<address>` lesen kann. `deliverPaidOrder` in `e2e/fixtures/polar.ts` sendet ein vollständiges `order.paid`-Event, signiert wie die Events der Integrations-Suites.

## Vor dem Push

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`build:test` führt den vollständigen Cloudflare-Build aus, den die Unit-Tests nicht abdecken, und `test:e2e:pr` führt jede Spec in Chromium aus, wie es die CI bei Pull Requests tut.

Die CI führt Checks, Coverage und die Chromium-Browser-Suite bei jedem Pull Request und jedem Push auf `main` aus, WebKit wöchentlich und bei Pushes auf `main`.
