## Worker e bindings

`wrangler.jsonc` define `src/server.ts` como a entrada do Worker. O Worker recebe quatro bindings:

| Binding  | Tipo              | Usado para                                                            |
| -------- | ----------------- | --------------------------------------------------------------------- |
| `DB`     | Banco de dados D1 | Todas as tabelas, incluindo as sessões e os contadores de rate limit  |
| `CACHE`  | Namespace KV      | A contagem de estrelas do GitHub e os descontos regionais do checkout |
| `MEDIA`  | Bucket R2         | Arquivos de vídeo, servidos por `serveMedia` em `/media/`             |
| `ASSETS` | Assets estáticos  | As páginas pré-renderizadas e os arquivos de `public`                 |

Requisições para `/assets/*`, `/fonts/*`, `/robots.txt` e `/llms.txt` são servidas a partir dos assets estáticos sem executar o Worker. O código de servidor lê os bindings, os secrets e `waitUntil` de `cloudflare:workers`. `src/server.ts` adiciona os cabeçalhos de segurança a toda resposta que retorna; os arquivos servidos sem o Worker recebem o subconjunto de `public/_headers` ([Segurança e hardening](/docs/features/security)).

## Ambientes

`wrangler.jsonc` define quatro ambientes. `CLOUDFLARE_ENV` escolhe um deles para `vp dev` e `vp build`.

| Ambiente      | Bindings                               | Usado por                                       |
| ------------- | -------------------------------------- | ----------------------------------------------- |
| `development` | D1, KV e R2 de preview remotos         | `bun run dev`                                   |
| `preview`     | D1, KV e R2 de preview                 | `bun run build:preview`, `deploy:preview`       |
| `production`  | D1, KV e R2 de produção                | `bun run build:production`, `deploy:production` |
| `test`        | D1, KV e R2 locais em `.wrangler/test` | `bun run build:test`, Playwright                |

Cada ambiente lista os secrets obrigatórios em `secrets.required`. Os valores vêm do arquivo `.env.<environment>` correspondente; os scripts de deploy gravam as chaves declaradas em `.wrangler/secrets.<environment>.json` e repassam esse arquivo ao Wrangler com `--secrets-file`. O ambiente `test` usa `src/platform/testing/worker.ts` como entrada e os valores fictícios versionados em `.env.test`. `AFFONSO_PROGRAM_ID` é público, então é uma variável comum do Worker em `vars`, e não um secret; só `test` define um.

## Tipos

- `src/types/bindings.d.ts` declara `Cloudflare.Env`: os bindings, todos os secrets que o Worker lê e a variável opcional `AFFONSO_PROGRAM_ID`. Os três secrets `CLOUDFLARE_*` não são declarados, porque só o drizzle-kit os lê, de `process.env`.
- `src/types/worker-configuration.d.ts` é gerado por `bun run cf-typegen`.
- `src/types/router.d.ts` registra o tipo do router e a opção de rota `staticData.namespaces`.

## Configuração do runtime de testes

`src/platform/testing` contém apenas o que não pode pertencer a uma única funcionalidade:

- `setup.ts`: os matchers do jest-dom, um reset dos bindings antes de cada teste e o substituto de `createServerFn` que executa as server functions no próprio processo
- `mocks/cloudflare.ts`: um D1 em SQLite em memória que executa as migrações versionadas no repositório, um KV em memória, um bucket `MEDIA` em memória e um `waitUntil` que os testes podem esvaziar
- `mocks/cache.ts`: `createEdgeCache`, um stub do cache do Workers para os testes de entrega de mídia
- `mocks/resend.ts` e `mocks/polar.ts`: dublês estritos das APIs do Resend e do Polar, e `mocks/providers.ts`, que direciona o `fetch` para eles em todos os testes e no Worker de testes de navegador
- `mocks/wrksz-themes.ts`: um substituto para a biblioteca de temas
- `lib/`: a ponte RPC das server functions, helpers de renderização, helpers de URL de requisição, executores de queries e modelos do Polar com webhooks assinados
- `worker.ts`: a entrada do Worker para os testes de navegador, que instala os dublês dos provedores e expõe os e-mails entregues

Veja [Testes e CI](/docs/architecture/testing-architecture) para saber como as suítes usam esses recursos.
