title: "Pisanie testów"
description: "Gdzie znajdują się testy, jak działają projekty Vitest i testowe bindingi, wymagany próg pokrycia oraz Playwright."
---

Vite+ uruchamia Vitest (`vp test`) w trzech projektach. Testy znajdują się w folderze `__test__` obok kodu, który sprawdzają, i importują API z `vite-plus/test`.

| Projekt       | Pliki                            | Środowisko |
| ------------- | -------------------------------- | ---------- |
| `node`        | `__test__/*.test.ts(x)`          | Node       |
| `integration` | `__test__/*.integration.test.ts` | Node       |
| `component`   | `__test__/*.component.test.tsx`  | jsdom      |

Nazywaj test od pliku źródłowego: `category.zod.ts` testuje `__test__/category.zod.test.ts`.

## Polecenia

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
```

Używaj `bun run test`, a nie `bun test`: tylko Vitest wczytuje projekty, środowiska i plik konfiguracyjny testów.

## Wymagane pokrycie

`bun run test:coverage` kończy się błędem poniżej **<RepositoryFact name="coverageThreshold" unit="percent" />** linii, instrukcji, funkcji i gałęzi kodu aplikacji w `src`. Wyłączone są testy, `src/platform/testing`, prymitywy shadcn i pliki generowane. Testuj rzeczywiste zachowanie i usuwaj gałęzie, które nigdy się nie wykonają, zamiast podmieniać obiekty globalne, żeby do nich dotrzeć. Raporty trafiają do `coverage/`.

## Środowisko testów

- `src/platform/testing/setup.ts` rejestruje matchery jest-dom, resetuje bindingi przed każdym testem i przepuszcza każde `createServerFn` przez `withTestRpc`, więc wywołania uruchamiają prawdziwe middleware i walidator. Dotyczy to projektów `node` i `integration`. W projekcie `component` funkcja serwerowa kończy się błędem, ponieważ jsdom jest przeglądarką.
- `cloudflare:workers` wskazuje na `src/platform/testing/mocks/cloudflare.ts`. D1 to baza SQLite w pamięci z zastosowanymi wszystkimi zatwierdzonymi migracjami, KV i bucket R2 `MEDIA` to mapy w pamięci, a `flushWaitUntil()` czeka na zadania w tle. `createEdgeCache()` z `mocks/cache.ts` zastępuje cache Workers zaślepką.
- `.env.test` dostarcza fikcyjne dane dostępowe. `fetch` trafia do ścisłych dublerów Resend i Polar (`mocks/resend.ts`, `mocks/polar.ts`), a żądanie do każdego innego hosta kończy się błędem, jakby komputer był offline, więc nic go nie opuszcza. Żądanie, które dostawca by odrzucił, kończy test błędem.
- `renderWithRouter` z `src/platform/testing/lib/render.tsx` renderuje komponenty z prawdziwym routerem i `QueryClient`.

## Przetestuj przypadek użycia

Skrócona wersja `src/modules/category/use-cases/__test__/create-category.test.ts`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"

import { executeMutation } from "~/src/platform/testing/lib/query"

import { createAuthSessionFixture } from "~/src/integrations/better-auth/__test__/fixtures/auth.session.fixture"
import { ROLE_CODES } from "~/src/integrations/better-auth/auth.access"
import type { auth } from "~/src/integrations/better-auth/auth.server"
import * as authServer from "~/src/integrations/better-auth/auth.server"

import { ERROR_CODES } from "~/src/modules/_core/constants/errors"
import { CATEGORY_KIND } from "~/src/modules/category/category.constants"
import { createCategoryMutation } from "~/src/modules/category/use-cases/create-category"

const getSessionMock = vi.hoisted(() => vi.fn<(typeof auth.api)["getSession"]>())

vi.mock(import("@tanstack/react-start/server-only"), () => ({}))

describe("create-category", () => {
  it("returns a domain error when the caller is not an admin", async () => {
    vi.spyOn(authServer.auth.api, "getSession").mockImplementation(getSessionMock)
    getSessionMock.mockResolvedValue(
      createAuthSessionFixture({ role: ROLE_CODES.CUSTOMER, userId: "01900000-0000-7000-8000-000000000001" }),
    )

    await expect(executeMutation(createCategoryMutation, { kind: CATEGORY_KIND.CATEGORY, name: "SaaS Plans" })).rejects.toThrow(
      ERROR_CODES.FORBIDDEN,
    )
  })
})
```

Testuj każdy wynik przypadku użycia: sukces, każdy kod `AppError`, brak sesji i brak uprawnienia. Wartości domenowe i kody błędów pochodzą z ich stałych (`CATEGORY_KIND`, `ERROR_CODES`), nigdy z powtarzanych napisów.

## Przetestuj wywołania Resend i Polar

Nie mockuj SDK Resend ani Polar. Wywołaj kod, który wysyła żądanie, i sprawdź, co otrzymał dubler. `getSentEmails(recipient)` z `mocks/resend.ts` zwraca dostarczone e-maile wraz z wyrenderowanym HTML-em i kluczem idempotencji; `mocks/polar.ts` przechowuje sesje płatności, zamówienia i klucze licencyjne, a jego funkcje posuwają zakup naprzód: `payPolarCheckout`, `grantPolarLicenseKey`, `refundPolarOrder`, `revokePolarLicenseKey` i `activatePolarLicenseKey`. Skrócona wersja `src/modules/license/__test__/license-purchase.integration.test.ts`:

```ts
const buyer = await signUpAndVerify()
const order = await paidOrder(buyer, LICENSE_TIER.COMPLETE)

expect(await deliver(POLAR_WEBHOOK_EVENT.ORDER_PAID, order)).toBe(HTTP_STATUS.OK)
expect(await currentLicense(buyer)).toMatchObject({ status: LICENSE_STATUS.ACTIVE, tier: LICENSE_TIER.COMPLETE })
```

`paidOrder` tworzy sesję płatności przez prawdziwe `startCheckout` i opłaca ją w dublerze. `deliver` podpisuje zdarzenie przez `signedPolarWebhook` z `lib/polar.ts`, wysyła je do endpointu Polar w Better Auth i zwraca status odpowiedzi, więc wykonują się weryfikacja podpisu, wtyczka i handlery z `license.webhooks.ts`. Aby sprawdzić, jak aplikacja radzi sobie z awarią dostawcy, odpowiedz na pojedyncze żądanie błędem dostawcy, tak jak robi to `resend.utils.test.ts`: `vi.spyOn(globalThis, "fetch").mockResolvedValueOnce(Response.json(error, { status }))`.

## Przetestuj przepływ uwierzytelniania

Zestawy testów uwierzytelniania działają na prawdziwym `auth` z `auth.server.ts`. `src/integrations/better-auth/__test__/fixtures/auth.harness.ts` tworzy konta tak, jak robi to odwiedzający: `signUp`, `verifyEmail` (który używa tokenu z dostarczonego e-maila i zwraca otwartą przez niego sesję), `signIn` i `signUpAndVerify`. `browserHeaders()` nadaje każdemu żądaniu własny `CF-Connecting-IP`, więc limity żądań Better Auth działają jak na produkcji, a żaden test nie wyczerpuje limitu innego. Zanim odczytasz e-mail, który Better Auth wysyła w tle, zaczekaj na `flushWaitUntil()`.

## Przetestuj komponent

Testy komponentów renderują z prawdziwymi komunikatami z `messages/en-US`, mockują moduł przypadku użycia, który dostarcza opcje mutacji, i sterują interfejsem przez Testing Library oraz `userEvent`. W stanach oczekiwania wstrzymaj mockowane żądanie przez `Promise.withResolvers()`, sprawdź interfejs oczekiwania, a potem rozwiąż żądanie wewnątrz `act` i sprawdź interfejs spoczynkowy. Komponent, który zmienia się po upływie czasu, testuje się fałszywymi timerami (`vi.useFakeTimers()`, a potem `vi.advanceTimersByTimeAsync` wewnątrz `act`), nigdy czekaniem w czasie rzeczywistym, a `QueryClient` w teście trasy utrzymuje dane pobrane przez loader jako świeże (`staleTime: Infinity`), więc szybkość renderowania na danej maszynie nigdy nie wpływa na to, ile razy wykona się zapytanie. `userEvent.setup({ delay: null })` steruje interfejsem bez prawdziwego timera między naciśnięciami klawiszy. Kompletnym przykładem jest `src/presentation/components/custom/__test__/newsletter-form.component.test.tsx`. Test trasy przekazuje trasie dane loadera, a test `node` pokrywa loader przez `getRouter()`: `src/routes/__test__/marketing-routes.component.test.tsx` i `marketing-loaders.test.ts` to dwie połowy.

## Testy przeglądarkowe

Specyfikacje Playwright znajdują się w `e2e/specs`, obiekty stron w `e2e/pages`, a fixtures w `e2e/fixtures`. Działają na zbudowanej aplikacji testowej z lokalnymi D1, KV i R2 w `.wrangler/test` oraz z kontami z `e2e/data/accounts.ts`. Lokalnie Playwright sam wykonuje migracje, zasila bazę danymi, buduje i uruchamia tę aplikację.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:ui
```

Testowy Worker instaluje te same dublery Resend i Polar i zapisuje wysłane e-maile, więc specyfikacja może odczytać link weryfikacyjny z `/__test/emails?to=<address>`. `deliverPaidOrder` z `e2e/fixtures/polar.ts` wysyła kompletne zdarzenie `order.paid`, podpisane tak jak zdarzenia zestawów testów integracyjnych.

## Przed wypchnięciem zmian

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`build:test` wykonuje pełny build Cloudflare, którego testy jednostkowe nie sprawdzają, a `test:e2e:pr` uruchamia każdą specyfikację w Chromium, tak jak CI dla pull requestów.

CI uruchamia kontrole, pokrycie i testy przeglądarkowe w Chromium przy każdym pull requeście i wypchnięciu do `main`, a WebKit co tydzień oraz przy wypchnięciach do `main`.
