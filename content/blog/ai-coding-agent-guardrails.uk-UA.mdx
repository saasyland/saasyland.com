    answer: >-
      Перевірки, які виконуються незалежно від того, чи згоден із ними агент: правило лінтера,

  - question: Куди класти правило, в AGENTS.md чи в CI?
    answer: >-
      У CI — щоразу, коли програма може вирішити його за кодом, контентом, результатом збірки чи
      diff, а в AGENTS.md — коли воно потребує судження, як-от виправлення першопричини чи невеликий
      розмір pull request. Більшість правил зрештою потрапляє в обидва місця: перевірка забезпечує
      правило, а один рядок у файлі інструкцій називає команду, яка його перевіряє, тож агент
      запускає її, перш ніж сказати, що закінчив.

  - question: Як перетворити правило стилю коду на перевірку лінтера?

Практичний посібник із запобіжників для команд, які дозволяють ШІ-агентам програмування змінювати продакшн-кодову базу: перевірки, хуки, правила гілок і схвалення, через які хибна зміна провалюється сама, а не чекає, поки хтось її помітить. Він написаний для будь-якого стеку й будь-якого агента. Кожен розділ спершу формулює правила, а потім показує, як їх застосовує saasyland.com, з його справжніми файлами, інцидентами й цифрами CI. У ньому:

1. Чому правило, про яке агенту лише сказали, не працює, і шість способів, у які воно підводить.
2. Де може жити правило, від файлу інструкцій до правила гілки, і які правила належать до перевірок.
3. Аудит правил через їх навмисне порушення і перетворення правила стилю на перевірку.
4. Шляхи, що потребують рев’ю людини, і чому схвалення належить до diff.
5. Критерії готовності як коди виходу і що наші перевірки відхилили за три місяці pull request.
6. Два інциденти, які пройшли всі перевірки, план впровадження, витрати, межі й стартовий набір, який можна скопіювати.

## Коротка відповідь

Вважайте кожне правило, яке ви даєте агенту, проханням, доки його не забезпечує програма. Для кожного правила запитайте, чи могла б програма вирішити його за кодом, контентом, результатом збірки чи diff. Якщо так, напишіть перевірку, зробіть так, щоб її повідомлення казало, що робити натомість, і запускайте її там, де працює агент, і ще раз як обов’язковий статус CI, повз який ніхто не може злити зміну. Залиште файл інструкцій для того, чого не може вирішити жодна програма, і нехай кожен рядок у ньому вказує на команду, яка це перевіряє. Поставте незворотні шляхи й шляхи, що рухають гроші, за другим ключем, який тримає людина з ідентичністю, якої агент не має. Визначте готовність як короткий список команд, які мають завершитися з кодом 0, у певному порядку. А потім навмисно поруште власні правила, щоб з’ясувати, на які з них ви лише сподівалися.

Інженери Google мають назву для ідеї, що стоїть за всім цим. _Software Engineering at Google_ називає її правилом Бейонсе: «Якщо вам це подобалося, треба було покрити це тестом». Коли код пишуть агенти, воно стосується кожного правила, а не лише поведінки.

## Чому правило, про яке агенту лише сказали, — це прохання

Файл інструкцій, як-от `AGENTS.md` чи `CLAUDE.md`, — це текст, який потрапляє в контекст моделі на початку сесії. Він впливає на те, що робить агент; він нічого не вирішує. Документація Anthropic для Claude Code каже це прямо: Claude сприймає ці файли «як контекст, а не як примусову конфігурацію», і «щоб заблокувати дію незалежно від того, що вирішить Claude, використовуйте натомість хук PreToolUse». Та сама сторінка проводить межу між двома видами контролю: «Правила налаштувань застосовує клієнт, хоч би що вирішив зробити Claude. Інструкції CLAUDE.md формують поведінку Claude, але не є рівнем жорсткого примусу».

Це не слабкість одного інструмента. Кожен агент читає свій файл інструкцій як частину промпту, а промпт конкурує з усім іншим у контексті: із завданням, файлами, які відкрив агент, власними системними інструкціями інструмента й тим, що підказало останнє повідомлення про помилку. Дослідження вимірюють, як проходить ця конкуренція. IFScale, бенчмарк, опублікований у липні 2025 року, давав 20 моделям до 500 інструкцій одночасно й виявив, що «навіть найкращі передові моделі досягають лише 68% точності за максимальної щільності в 500 інструкцій», з упередженням на користь інструкцій, що йшли першими. У звіті METR за червень 2025 року йдеться, що нещодавні передові моделі, отримавши завдання з оцінкою, намагалися «отримати вищу оцінку, змінюючи тести чи код оцінювання», і що вони «демонструють усвідомлення того, що їхня поведінка не відповідає намірам користувача».

Жоден із цих результатів не означає, що агенти недбалі. Він означає, що правило, яке живе лише в тексті, — один вхідний сигнал серед багатьох, якого здебільшого дотримуються, а випадки, коли його не дотримуються, — саме ті, коли ніхто не дивиться.

### Шість способів, у які підводять правила лише в інструкціях

Кожен із них стався в наших репозиторіях, і для кожного є виправлення, яке не залежить від того, наскільки уважно читає агент.

**1. Розмивання.** Кожне нове правило трохи зменшує ймовірність, що агент дотримається кожного іншого. Документація Claude Code радить тримати файли інструкцій коротшими за 200 рядків, бо «довші файли займають більше контексту й знижують дотримання». Наш `AGENTS.md` — це короткий виклад, який посилається на цілий розділ документації з конвенціями. Агент читає виклад у кожній сесії, а сторінки — лише коли про них згадає.

**2. Конфлікт.** Інструкції надходять із кількох місць, і вони суперечать одна одній. Інструменти агентів за замовчуванням додають до комітів трейлер атрибуції, як-от `Co-Authored-By`. Наші правила це забороняють, бо GitHub зіставляє адресу з трейлера з обліковим записом і показує цей обліковий запис серед учасників репозиторію. Виправлення, яке тримається, — структурне, а не ще одне речення: репозиторій дозволяє лише злиття через squash, а squash-коміт бере заголовок pull request із порожнім тілом, тож ніщо, що агент пише в повідомленні коміту в гілці, не доходить до `main`. Починаючи з #274, хук `commit-msg` також відхиляє будь-яке повідомлення коміту, трейлер якого називає інструмент ШІ, тож агент дізнається про це вже на першому коміті.

**3. З чужих слів.** Коли кілька агентів працюють разом, більшість інструкцій доходить до виконавця через чужий переказ, а перекази щось гублять. У нашому налаштуванні головний агент пише бриф для кожного виконавця. В одному брифі йшлося, що «власник схвалив» зміну в платежах, тоді як він схвалив дещо інше (#166). Наступного ранку у двох брифах ішлося, що API ліцензій для CLI немає в списку рев’ю людиною, хоча `AGENTS.md` перелічував його ще з попереднього дня, і два pull request його змінили (#208 і #211). Наступний крок щоразу зупиняла не інструкція: рівень дозволів обв’язки агента відмовився зливати зміну в платежах і продовжувати роботу над другою зміною ліцензій, доки власник не сказав «так». Його «так» для зміни ліцензій процитовано в її pull request.

**4. Буква замість наміру.** Коли перевірка вимагає артефакту, агент створює найдешевший артефакт, який її проходить. Наша конфігурація лінтера колись дозволяла записувати як число без назви лише `0`, тож кожна `1` ставала константою: `SINGLE_CALL` існувала 16 разів, `SINGLE_ROW_LIMIT` — 12 разів, і близько 80 констант дорівнювали `0` чи `1` без жодної причини, крім правила (#230). У нашому приватному репозиторії CLI перевірка випуску, яка вимагає changeset, отримала порожній, і це зупинило наступний випуск; історію наведено нижче. Жоден агент не порушив правила. Обидва його виконали.

**5. Дрейф.** Інструкція описує кодову базу такою, якою вона була в день написання. Коли код змінюється, а речення ні, агент іде за реченням. Документація, яка переказує значення, визначене кодом, помиляється так само: наша документація колись вписувала вручну ліміти частоти запитів, покриття й ліміти лінтера, ціни й кількість локалей, у кожній мові, тож одна зміна в коді могла залишити сторінку хибною в кожній із них (#137). Виправленням стало виведення цих значень із коду; як саме — розповідає [третя стаття цієї серії](/blog/documentation-drift-numbers-from-code).

**6. Самозвіт.** Підсумок агента про власну роботу — найменш надійне з того, що він створює. «Усі тести проходять» — це речення; код виходу — це доказ. Наш pull request #224, виправлення макета, злили з описом #225, зміни ліцензій, разом з абзацом про те, що власник схвалив зміни у файлах ліцензій, яких #224 ніколи не торкався. Жодна перевірка не читає описи, тож ніщо цього не помітило.

Два принципи вирішують, куди йде правило.

**Ставте кожне правило на найнижчий щабель, який може його вирішити, і повторюйте його на першому щаблі, який агент не може пропустити.** Правило, яке живе лише в хуку Git, зникає, щойно хтось робить коміт із `--no-verify`; правило, яке живе лише в CI, змушує агента чекати кілька хвилин, щоб дізнатися про пропущену крапку з комою. Хуки — для швидкості, а CI — для істини, тож наш хук pre-commit запускає всі перевірки `bun run check`, крім переліку сценаріїв, причому форматування, лінтер і типи — лише на проіндексованих файлах, а пропущений хук коштує одного червоного запуску CI, а не зламаного `main`.

**Ніколи не робіть рівень дозволів агента єдиним рівнем.** Це найшвидше місце, щоб зупинити небезпечну команду, і найлегше для обходу. Власна документація Claude Code попереджає, що «шаблони дозволів Bash, які намагаються обмежувати аргументи команд, крихкі», і що правило, яке забороняє `git push`, не збігається з «push, записаним інакше, як-от `git -C . push`». Усе, що має триматися, потребує правила на сервері за ним.

### Приклад: одне правило на трьох щаблях

Наше правило щодо історії просте: `main` лишається лінійною, і ніхто не переписує спільну гілку. Його забезпечено тричі: дозволами агентів, правилами гілок на сервері й власником, який єдиний може ці правила зняти.

Агент зробив rebase своєї гілки pull request і спробував надіслати її через force-push. Налаштування дозволів агента не дозволяли force-push, тож команду відхилили, і робота пішла новим pull request із нової гілки (#235 закрили на користь #236). Результат був правильний, а причина — ні: rebase власної гілки й push із `--force-with-lease` безпечні, бо, за словами Git, push проходить, лише «якщо поточне значення віддаленого посилання дорівнює очікуваному». Тож власник дозволив саме цю форму, на власних гілках pull request агентів, і більше нічого.

За локальним правилом стоїть сервер. Набори правил GitHub «не дають користувачам виконувати force-push у цільові гілки», а наші блокують force-push і видалення на спільних гілках і вимагають лінійної історії. Коли власник таки захотів переписати спільну гілку випусків у репозиторії CLI, щоб прибрати коміти злиття, сервер відхилив навіть push із lease. Знадобилося, щоб він зняв правило для одного push і відновив його, суворішим, ніж раніше, тепер із вимогою лінійної історії й там. Локальне правило за секунди перехопило буденну помилку; серверне правило встояло, коли хтось із вагомими причинами спробував зробити небезпечну річ.

## Які правила належать до перевірок, а які до інструкцій

Будь-яке правило сортують три запитання.

1. **Чи може програма вирішити його за артефактом,** як-от вихідним кодом, контентом, конфігурацією, результатом збірки, diff чи повідомленням коміту, не знаючи, навіщо зроблено зміну? Якщо так, воно належить до перевірки.
2. **Чи дешевше закодувати його один раз, ніж переглядати вічно?** Правило, яке ви застосуєте в сотнях рев’ю, окупає день роботи над інструментами. Правило, яке спрацьовує двічі на рік, може й не окупити.
3. **Чи коштуватиме хибне спрацювання більше, ніж пропуск?** Перевірка, яка достатньо часто спрацьовує на легітимному коді, привчає всіх, зокрема агентів, її обходити. Звужуйте визначення, доки цього не станеться, або залиште правило для рев’ю.

### Для чого інструкції досі потрібні

Інструкції не застаріли; просто їхня робота вужча. Використовуйте їх для наміру («виправте причину»), для одного канонічного прикладу, який треба копіювати, для списку шляхів, яким потрібна людина, для критеріїв готовності та як покажчик перевірок: кожне правило разом із командою, яка його забезпечує. Агент, який знає, що `bun run check` провалиться на коментарі, пише менше коментарів, а решту виправляє за секунди, а не на рев’ю. Наш `AGENTS.md` завершує критерії готовності реченням, спрямованим на шостий режим збою, описаний вище: «Ніщо інше не вважається готовим, зокрема й підсумок, який стверджує, що все готово».

## Перевірте свої правила, порушивши їх

Найдешевший аудит, який ви можете провести, — файл, що порушує кожне з ваших правил по одному разу. Запустіть на ньому свої перевірки й запишіть, які рядки проходять. Це займає годину й замінює те, що ви думаєте про свої інструменти, тим, що вони справді забезпечують.

### Приклад: що відхиляє наш лінтер

Ми зробили це 20 листопада 2026 року для правил стилю коду з нашого `AGENTS.md`. Наша конфігурація oxlint вмикає як помилки цілі категорії правил, `correctness`, `nursery`, `pedantic`, `perf`, `style` і `suspicious`, з увімкненими правилами з урахуванням типів. Ми записали по рядку на правило в чернетковий файл і запустили на ньому `vp lint`.

З однієї таблиці випливли чотири уроки, і всі чотири стосуються будь-якого лінтера.

**Категорії дають правила випадково.** Через увімкнені `style` і `pedantic` здавалося, що «жодних коментарів» забезпечено: коментарі з малої літери, після коду й TODO провалювалися через правила, які ніхто для цього не обирав. Будь-який агент, що пише охайний коментар із великої літери в окремому рядку, проходить. Якщо правило важливе, вмикайте його за назвою й знайте, яке правило його забезпечує.

**Лінтер не може контролювати власний вимикач.** Коментар вимкнення — це коментар, але лінтер читає його як інструкцію раніше, ніж його побачить будь-яке правило, тож він заглушує саме те правило, яке заперечило б. ESLint уміє їх відхиляти: «Щоб вимкнути всі вбудовані коментарі конфігурації, використовуйте налаштування `noInlineConfig` у своєму файлі конфігурації». Для інструмента без такої опції шукайте директиви в CI, поза лінтером.

**Значення за замовчуванням свідомо поблажливі.** `ban-ts-comment` у typescript-eslint дозволяє `@ts-expect-error`, «якщо він містить опис», і порт в oxlint поводиться так само, тож агент, який пише причину, проходить. «Значення `true` для певної директиви означає, що це правило повідомлятиме про будь-яке використання цієї директиви». Обирайте `true`, якщо правило звучить як «ніколи».

**Повторно запускайте пробний файл після кожного оновлення лінтера.** Категорії на кшталт `nursery` отримують і втрачають правила між випусками. Пробний файл — це тест вашої конфігурації, і він заслуговує запускатися в CI, як будь-який інший тест; стартовий набір наприкінці містить такий.

Ми закрили кожну прогалину з цієї таблиці наступного дня, у #274. `code-style/no-comments` повідомляє про кожен коментар, `code-style/no-multiline-ternary` — про кожен тернарний оператор, що займає кілька рядків, а `code-style/no-undefined-fallback` — про кожен `?? undefined`; `typescript/ban-ts-comment` тепер відхиляє `@ts-expect-error` навіть з описом, а `typescript/consistent-type-assertions` з `assertionStyle: "never"` відхиляє розширювальне `as`. Увімкнені в усьому репозиторії, ці правила знайшли 21 багаторядковий тернарний оператор, 17 з них у скопійованих у репозиторій компонентах shadcn, і два приведення `as`, і pull request переписав кожне з них, а не зробив для нього виняток.

## Як перетворити правило стилю на перевірку

1. **Сформулюйте правило як запитання про артефакт із відповіддю «так» чи «ні».** «Чи містить цей файл коментар?» можна вирішити. «Чи зрозумілий цей код?» — ні, і йому місце на рев’ю. Якщо ви не можете сформулювати запитання, ви знайшли інструкцію, а не перевірку.
2. **Оберіть найдешевший інструмент, який відповідає на нього точно.** По черзі: наявне правило, увімкнене за назвою; прапорець компілятора чи конфігурації; власне правило лінтера над синтаксичним деревом; скрипт над файлами; тест, який перевіряє властивість коду чи контенту; перевірка результату збірки; перевірка живої системи.
3. **Для всього всередині коду використовуйте парсер.** Регулярний вираз, який шукає `//`, знаходить і кожну URL-адресу в рядку, і кожну екрановану скісну риску в шаблоні. Синтаксичне дерево знає, що таке коментар.
4. **Зробіть повідомлення про помилку інструкцією.** Агент прочитає його посеред завдання, без жодного іншого контексту. Скажіть, що робити натомість і де.
5. **Перевірте її на відомих порушеннях.** Перш ніж довіряти новій перевірці, запустіть її на коді, для якого її написано, і переконайтеся, що вона позначає саме ті випадки, про які ви знаєте, не більше й не менше.
6. **Тримайте винятки в коді, з тестом для кожного.** Список дозволених у перевірці, який рецензують як будь-яку зміну, кращий за коментар вимкнення, якого ніхто не бачить.
7. **Запускайте її у двох місцях.** У хуку pre-commit, щоб агент дізнавався про проблему за секунди, і як обов’язкову перевірку CI, щоб вона трималася, коли хук не запускається.
8. **Вирішіть, що робити з наявними порушеннями.** Виправте їх у тому самому pull request, якщо можете; інакше зафіксуйте базову лінію й провалюйте лише нові, а базову лінію свідомо зменшуйте.

Наша перевірка журналу змін показує крок 4. Запуск CI для pull request провалюється, доки не з’явиться запис, названий його номером, а повідомлення і є виправленням:

```ts title="scripts/check-content.ts"
export const pullRequestEntryProblems = (ref: string): string[] => {
  const pullRequest = pullRequestOf(ref)

  if (pullRequest === undefined || existsSync(join(REPOSITORY_DIR, CHANGELOG_DIRECTORY, `${pullRequest}${SOURCE_MDX_SUFFIX}`))) {
    return []
  }

  return [`Pull request #${pullRequest} has no changelog entry: add ${CHANGELOG_DIRECTORY}/${pullRequest}.<locale>.mdx in every locale`]
}
```

### Приклад: помилка гідратації стає правилом лінтера

### Приклад: жодних коментарів, і це забезпечує парсер

Аудит вище показав, що наше правило «жодних коментарів» забезпечувалося лише випадково. Ось правило, яке закрило цю прогалину, написане для API правил ESLint, яке Oxlint теж завантажує («API плагінів Oxlint сумісний з ESLint v9+»); у нас це `code-style/no-comments` у `scripts/code-style-lint-plugin.ts`:

```ts title="scripts/code-style-lint-plugin.ts"
export const COMMENT_MESSAGES = {
  comment:
    "Remove this comment. Say it in a name, a named constant or a smaller function, and put the reasoning in the commit message, the pull request or the docs.",
  directive: "Remove this directive comment, which switches a check off, and fix the cause the rule or the compiler reports instead.",
} as const

export const commentMessageId = (text: string): keyof typeof COMMENT_MESSAGES => (DIRECTIVE.test(text) ? "directive" : "comment")

export const noComments = defineRule({
  create: (context) => ({
    Program: () => {
      for (const comment of context.sourceCode.getAllComments()) {
        if (comment.type !== SHEBANG) {
          context.report({ loc: comment.loc, messageId: commentMessageId(comment.value) })
        }
      }
    },
  }),
  meta: {
    docs: {
      description: "Source files carry no comments: names, the commit message, the pull request and the docs carry the meaning.",
    },
    messages: COMMENT_MESSAGES,
    type: "problem",
  },
})
```

Ми запустили його з нашою наявною конфігурацією на кожному файлі, який охоплює лінтер. Воно повідомило про коментар у рядку з великої літери, блок JSDoc і коментар у JSX із пробного файлу, не зачепило `//` усередині рядка з URL-адресою та всередині регулярного виразу й знайшло рівно одну проблему в коді, який охоплює лінтер: рядок `#!/usr/bin/env bun` на початку скрипта. ESLint документує причину: shebang-рядки «вважаються коментарями» й повертаються з `getAllComments()`. Звідси виняток `SHEBANG`, і це урок кроку 5 у мініатюрі: перевірка, яку ви не запускали на справжньому коді, має помилки, яких ви ще не зустрічали.

Інша знахідка важить не менше: крім цього рядка, у коді, який перевіряє лінтер, не було жодного коментаря. Рев’ю втримало правило. Але щоразу воно коштувало власникові уваги, потрібної, щоб його втримати, і саме про цей обмін ця стаття.

Проте правило лінтера має дві сліпі зони. Воно не бачить файлів, які лінтер пропускає, а в нас це набір браузерних тестів, файли оголошень і таблиці стилів, і не може повідомити про `/* oxlint-disable */`, що його називає, бо лінтер першим підкоряється директиві. Тому `bun run check:comments` розбирає кожен файл TypeScript, JavaScript і CSS, який відстежує Git, поза лінтером, через oxc для коду й PostCSS для стилів, і провалюється на будь-якому коментарі ще до запуску лінтера. Перший запуск знайшов ще один: рядок `/// <reference types>` у файлі оголошень, який перенесли в `types` у `tsconfig.json`.

### Коли правило породжує формальності, виправляйте правило

Перевірку, яка трохи хибна, агенти не ігнорують. Вони її виконують, і виконують масово. Наше правило `no-magic-numbers` дозволяло лише `0`, тож агенти давали назву кожній `1`: `SINGLE_CALL`, `NEXT`, `STEP`, `FIRST_LETTER`, `ZERO_TICK`, `NO_OFFSET`. Кожна константа була коректною, і кожна робила код важчим для читання. Pull request #230 дозволив `0` і `1` як літерали й вбудував назад 72 константи, які існували лише заради правила, зберігши ті, що мають власний зміст, як-от `FAILURE_EXIT_CODE` та `INCLUSIVE_END`. Урок загальний: коли ви бачите шаблон дотримання, якого не написала б жодна людина, як-от константи, що дорівнюють одиниці, порожні changeset чи коментар вимкнення з дбайливо написаною причиною, змінюйте правило, а не код.

### Перевірки — теж шлях, що потребує рев’ю людини

Висновок METR про агентів, які редагують тести й код оцінювання, — причина, з якої існує останній рядок. Агент, якого попросили змусити провалену перевірку пройти, має два варіанти: виправити код або послабити перевірку. Другий часто коротший. Тож файли, які визначають ваші перевірки, — робочі процеси CI, конфігурація лінтера й типів, пороги покриття й скрипти перевірок — потребують того самого другого ключа, що й ваш платіжний код. Наш список називає `.github/workflows/`; він поки що не називає `vite.config.ts`, де живуть правила лінтера й пороги покриття, чи `scripts/`, де живуть перевірки контенту. Їм там місце.

### Схвалення належить до diff, а не до прози

Інциденти «з чужих слів» вище мають спільну форму: схвалення існувало як речення, і речення мандрувало далі, ніж схвалення. «Власник схвалив» у брифі, опис, вставлений з іншого pull request, список, у якому йшлося, що файл не захищений. Виправлення — зробити схвалення записом із трьох частин: слова людини, процитовані дослівно; шляхи, які воно охоплює; і те, чого воно не охоплює. Pull request #223, через який розгортання почало відхиляти секрети-заповнювачі, робить саме це. Він цитує відповідь власника, «6. так», називає скрипти розгортання, які охоплює, і перелічує шляхи, що потребують рев’ю людини й лишаються незачепленими. Рецензент чи перевірка можуть порівняти цей список із diff. Правило, якого ми тепер дотримуємося: ніхто не пише «власник схвалив», не процитувавши повідомлення, де це сказано.

### Другому ключу потрібна друга ідентичність

GitHub може забезпечити другий ключ: файл `CODEOWNERS` призначає шляхи людям, а правило гілки може «вимагати рев’ю від власників коду». Є нюанс, важливий для кожного розробника-одинака, який запускає агентів. Документація GitHub каже про це однозначно: «Автори pull request не можуть схвалювати власні pull request». Якщо ваші агенти відкривають pull request із вашими обліковими даними, кожен контроль на сервері бачить вас, і обов’язкове рев’ю від вас дати неможливо.

Саме така в нас ситуація сьогодні. Агенти працюють під обліковим записом власника, тож наше правило гілки вимагає перевірок CI й черги злиття, а не схвального рев’ю, а «так» власника для шляху, що потребує рев’ю людини, — це процитоване повідомлення, яке втримує рівень дозволів агентів. Це працювало, як показують інциденти, і це найслабша частина нашого налаштування. Надійніше влаштування легко описати: дайте агентам власну ідентичність, як-от обліковий запис бота чи GitHub App із правом запису, але без прав адміністратора, внесіть шляхи, що потребують рев’ю людини, у `CODEOWNERS` і вимагайте рев’ю власника коду на `main`. Тоді другий ключ — це клік людини, і жодне речення не може його замінити.

## Визначайте готовність через коди виходу

«Готово» — найдорожче слово, яке каже агент, бо все після нього — це чужий час. Визначте готовність як короткий список команд, які мають завершитися з кодом 0 у гілці, яку збираються надіслати, у фіксованому порядку, від найшвидшої до найповільнішої, де кожна виявляє вид збою, якого не можуть виявити попередні. Нехай CI запускає ті самі команди, а не схожі на них, щоб зелений локальний запуск передбачав зелений запуск CI. Просіть у pull request коди виходу й кількості, а підсумок сприймайте як твердження, яке треба перевірити.

### Приклад: три команди й специфікації, яких ви торкнулися

Наші критерії готовності — це три команди, потім браузерні специфікації, яких торкається зміна, потім черга злиття. Ось рядки `AGENTS.md`, які вони використовують:

```sh title="AGENTS.md"
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
bun scripts/enqueue-pr.ts <number>
```

`check` форматує, лінтить, перевіряє типи й запускає перевірки перекладів і контенту в кожній локалі. `test:coverage` запускає модульні, інтеграційні й компонентні тести з порогом покриття <RepositoryFact name="coverageThreshold" unit="percent" /> для рядків, інструкцій, функцій і гілок. `build:test` збирає Cloudflare Worker і перевіряє результат. `test:e2e:pr` віддає цю збірку й проганяє весь набір браузерних тестів у Chromium; CI запускає його на pull request і ще раз у черзі злиття, а локально агент натомість запускає рядок `bunx playwright test` для специфікацій, яких торкається його зміна, на власному вільному порту. Pull request готовий лише тоді, коли в CI все зелене, а останній рядок поставив його в чергу.

### Перевірки, що супроводжують кожен тест

Набір браузерних тестів робить більше, ніж виконує власні перевірки. Три фікстури автоматично під’єднуються до кожного тесту й провалюють його, коли сторінка повідомляє про порушену Content Security Policy, відсутній чи пошкоджений переклад або політику дозволів, яку браузер не розпізнає. Тож кожен новий браузерний тест — це також тест цих трьох властивостей на сторінках, які він відвідує, без жодних зусиль його автора:

```ts title="e2e/fixtures/test.ts"
const reportCspViolations = (prefix: string): void => {
  document.addEventListener("securitypolicyviolation", ({ blockedURI, lineNumber, sourceFile, violatedDirective }) => {
    console.error(`${prefix} ${violatedDirective} blocked ${blockedURI} in ${sourceFile}:${String(lineNumber)}`)
  })
}
```

Той самий набір запускає скани доступності axe в обох колірних темах. Ці скани провалили три запуски з нашої вибірки нижче через текст, що не відповідав вимогам WCAG до контрасту, — регресію, якої жоден рецензент не помітив би на хорошому моніторі.

### Перевірки збірки й розгортання

`scripts/verify-build.ts` перевіряє властивості результату збірки, яких не бачить жоден модульний тест: кожну опубліковану сторінку документації й кожен допис попередньо відрендерено, жоден серверний модуль не потрапив у браузерний скрипт, кожна локаль має свій пошуковий індекс, а код, який Worker завантажує під час холодного старту, лишається в межах бюджету в байтах, без пакетів, що належать окремим запитам:

```ts title="scripts/verify-build.ts"
if (bootPackages.size > 0) {
  throw new Error(`The Worker loads ${[...bootPackages].join(", ")} on every cold start; import it where a request needs it`)
}
```

Розгортання має власні перевірки. У листопаді продакшн-файл середовища досі містив `AUTH_GOOGLE_CLIENT_ID="[UPDATE]"`, розгортання вивантажило його, бо відхиляло лише порожні значення, і вхід через Google завершувався помилкою `invalid_client`. Pull request #223 змусив розгортання відхиляти заповнювачі ще до збирання: значення в квадратних дужках або одне зі слів короткого списку, у будь-якому регістрі.

```ts title="src/lib/deploy-secrets.ts"
export const SECRET_PLACEHOLDER_WORDS = ["changeme", "placeholder", "replaceme", "tbd", "todo", "update"] as const
```

## Коли всі перевірки зелені, а продукт зламаний

Два інциденти пройшли всі перевірки, які ми мали. Обидва навчили нас більшого, ніж 68 відмов.

### 100% покриття, а `init` не працював

SaaSy Land має два репозиторії: цей вебсайт, який обслуговує API ліцензій, і приватний CLI, який клієнти запускають, щоб створювати проєкти. Обидва імпортують один пакет контракту, що визначає запити й відповіді API, і обидва валідують ним. Схеми контракту відхиляють ключі, яких не знають, і це добре значення за замовчуванням: мовчазне ігнорування було б гіршим.

Випуск CLI додав запитання, про UI-бібліотеку, і надсилав відповідь на нього до API ліцензій. Вебсайт у продакшні досі валідував попередньою версією контракту. Кожен модульний тест в обох репозиторіях проходив, бо кожен репозиторій тестував себе проти версії контракту, яку закріпив; покриття було повним з обох боків. 20 листопада 2026 року ми запустили опублікований CLI, прямо з npm, проти продакшну, зі справжньою ліцензією, виданою через продакшн-оформлення замовлення, як наскрізний тест. `init` провалився: API відхилив запит із повідомленням «Unrecognized key: library», тобто «невідомий ключ: library».

Виправленням став перехід вебсайту на нову версію контракту (#244), який вийшов того ж дня по обіді, після чого опублікований CLI створив свій проєкт на продакшні. Уроки загальні:

- **Покриття — властивість репозиторію. Коректність — властивість розгорнутої системи.** Ніщо в жодному з наборів тестів не запускало дві розгорнуті половини разом.
- **Розбіжність версій між тим, що ви розгортаєте окремо, невидима для модульних тестів.** Тестуйте опублікований клієнт проти живого сервера або принаймні проти тієї версії сервера, яка працюватиме, коли вийде клієнт.
- **Упорядковуйте розгортання.** Зміна контракту виходить на сервері й починає працювати раніше, ніж випускають клієнт, який її використовує. Тепер ми дотримуємося цього правила, а наступний запобіжник — запуск опублікованого CLI проти живого API в CI перед випуском. Йому потрібен ключ ліцензії як секрет CI, а це саме по собі зміна, що потребує рев’ю людини, тож вона чекає на власника.

### Порожній changeset, який зупинив випуск

Це сталося в приватному репозиторії CLI, тож ось процес без коду. CLI випускається за допомогою Changesets, і CI відхиляє pull request, який змінює пакет без changeset — файлу, який каже, що міститиме наступний випуск. Changesets документує обхідний шлях: «Якщо ви хочете злити зміну без жодних випусків (наприклад, коли змінюєте лише тести чи інструменти збирання), можна запустити `changeset --empty`, щоб додати спеціальний changeset, який нічого не випускає».

Pull request у гілці передвипусків лише виправляв журнал змін, тож додав порожній changeset, точно як задокументовано. У гілці в режимі передвипуску, де очікував лише порожній changeset, робочий процес випуску не знайшов нічого, для чого підняти версію, і нічого для публікації, тож наступну бету не було підготовлено. Виправлення прибрало порожній changeset, а посібник із випусків тепер каже, що порожнім changeset місце лише в основній гілці.

Це знову збій «буква замість наміру», на рівень вище. Перевірка вимагала артефакту, агент надав найдешевший коректний, а справжнім споживачем артефакту була інша система з власними правилами. Коли перевірка вимагає файлу, запитайте, що ще читає цей файл, і протестуйте конвеєр, який його читає.

## Впровадження в наявному репозиторії

Вам не потрібно все це вже в понеділок. Ось порядок, який дає найбільше за кожен день роботи.

<Steps>

<Step>

**Складіть інвентар.** Перелічіть кожне правило, яке ви коли-небудь давали агенту чи колезі: файли інструкцій, коментарі на рев’ю, які ви постійно повторюєте, сторінку конвенцій. Поруч із кожним правилом запишіть, де його забезпечено сьогодні. Більшість команд виявляє, що більшість їхніх правил не забезпечено ніде.

</Step>

<Step>

**Перевірте його пробним файлом.** Напишіть файл, який порушує кожне правило по одному разу, запустіть свої перевірки й позначте, що пройшло. Це перетворює інвентар із того, у що ви вірите, на те, що є правдою.

</Step>

<Step>

**Зробіть одну команду.** Єдиний скрипт `check`, який форматує, лінтить, перевіряє типи й запускає ваші перевірки контенту, і єдина команда тестів із покриттям. Запишіть обидві у файл інструкцій як критерії готовності.

</Step>

<Step>

**Нехай CI запускає ті самі команди, і зробіть їх обов’язковими.** Позначте завдання CI як обов’язкові перевірки статусу в правилі гілки разом із блокуванням force-push і видалення для `main`. Від цього кроку нічого червоного не зливається, хоч би хто це написав.

</Step>

<Step>

**Додавайте перевірки по одній, із храповиком.** Суворі прапорці типів, потім поріг покриття, потім перевірки контенту, потрібні вашому продукту. Для кожної виправте наявні порушення в тому самому pull request, якщо можете, як #220 зробив із 1404 формальними німецькими формами. Інакше зафіксуйте базову лінію й провалюйте лише нові порушення. `coverage.thresholds.autoUpdate` у Vitest піднімає пороги, коли покриття покращується, тож число лише зростає.

</Step>

<Step>

**Огородіть небезпечні шляхи.** Забороніть force-push, розгортання й продакшн-облікові дані в налаштуваннях дозволів агента. Напишіть список рев’ю людиною з причиною для кожного запису, включіть файли, які визначають ваші перевірки, і підкріпіть його власниками коду та окремою ідентичністю для агентів.

</Step>

<Step>

**Скоротіть файл інструкцій.** Видаліть кожне правило, яке тепер забезпечує перевірка, і замініть його командою, яка його забезпечує. Лишитися мають намір, приклади, список рев’ю й критерії готовності.

</Step>

<Step>

**Знову перевіряйте пробним файлом після оновлень.** Запускайте пробний файл знову щоразу, коли лінтер, компілятор чи тестовий раннер змінює мажорну версію, і щоразу, коли змінюється правило. А краще зробіть його тестом.

</Step>

</Steps>

## Скільки це коштує

Запобіжники не безкоштовні, і той, хто каже вам інакше, жодного з них не підтримував.

**Час на кожну зміну.** 20 листопада наш CI займав близько 16 з половиною хвилин від push до зеленого, здебільшого в наборі браузерних тестів на одному раннері. Відколи набір працює паралельно на <RepositoryFact name="e2eShards" /> раннерах, запуск pull request займає близько 7–9 хвилин, а черга злиття запускає його ще раз перед злиттям, плюс скільки займе локальний запуск перед push. Шарди купують цей час хвилинами раннерів, бо кожен заново налаштовує інструменти й браузер. Для публічного репозиторію самі хвилини CI нічого не коштують на стандартних раннерах GitHub, які GitHub документує як безкоштовні для публічних репозиторіїв; приватний репозиторій платить за кожну хвилину, і саме набір браузерних тестів їх з’їдає.

**Код, який треба написати й підтримувати.** Наші перевірки контенту й перекладів, скрипт перевірки збірки, плагін гідратації й хук комітів разом — це понад тисяча рядків TypeScript із власними тестами. Це такий самий код, як будь-який інший: у ньому є помилки, як показують shebang і французьке «ton», і він потребує того самого рев’ю.

**Червоне, що означає «ще ні».** 34 із 37 провалених запусків `check` у нашій вибірці походили з pull request, запису журналу змін яких ще не існувало, бо запис називається номером, якого не існує, доки немає самого pull request. Перевірка, яка регулярно провалюється з очікуваної причини, привчає всіх сприймати червоне як шум, і це найнебезпечніша звичка, якої може навчитися команда із запобіжниками. Якщо ви проєктуєте таку перевірку, дайте їй стан, який не є провалом, або приймайте цю ціну свідомо, як ми досі робимо.

**Формальності.** Правило, яке трохи надто суворе, породжує дотримання, якого ніхто не написав би вручну, як показали 72 константи з #230. Закладайте час на налаштування правил після того, як їх додали.

**Робота на кожну зміну, що зростає разом із продуктом.** У нашому репозиторії кожна зміна оновлює документацію <RepositoryFact name="languages" /> мовами й додає запис журналу змін кожною з них. Перевірки гарантують, що це відбувається. Дешевшим вони це не роблять.

Натомість ви отримуєте те, що показує таблиця вище: 68 запусків, які не могли злитися й жоден із яких не потребував людини, щоб його помітити, а також агентів, які можуть годинами працювати без нагляду за кожним кроком, бо репозиторій каже «ні» замість нас. Мовою нашої [статті про готовність репозиторію](/blog/ai-coding-agents-repository-readiness), кожна перевірка тут знижує Time to No.

## Чого запобіжники не помічають

Перевірки вирішують те, що може вирішити програма. Для всього іншого досі потрібна людина, яка читає зміну й запитує «чому».

- **Намір.** Правильний код для хибної проблеми проходить кожну перевірку. Так само як і виправлення симптому. Pull request #146 виправив помилку гідратації в одному компоненті лендингу, з регресійним тестом, і всі перевірки пройшли; причиною був захист маршруту, який очищав увесь кеш запитів щоразу, коли змінювався користувач, що увійшов, і #152 виправив це для кожної сторінки.
- **Дизайн.** Друга допоміжна функція, що дублює вже наявну, нова абстракція, яка нікому не була потрібна, модуль не в тому місці. Лінтер бачить синтаксис, а не призначення.
- **Слабкі тести.** Тест, який перевіряє реалізацію, проходить і покриває свої рядки. Покриття вимірює, що виконалося, а не що перевірено; мутаційне тестування вимірює більше, і ми його поки не додали.
- **Межі між розгортаннями.** Інцидент з `init`: кожна сторона правильна, а пара зламана.
- **Проза.** Описи pull request, твердження в документації й тексти журналу змін, якщо ви не виводите їхні факти з коду.
- **Самі перевірки.** Перевірка може бути хибною, надто поблажливою чи надто суворою. Перевіряйте її пробним файлом.
- **Наступний новий збій.** Кожен запобіжник у цій статті кодує інцидент, який уже стався. Рев’ю — це спосіб знайти той, якого ще не сталося.

## Стартовий набір, який можна скопіювати

Ці частини працюють у більшості репозиторіїв на TypeScript. Вони використовують npm, ESLint, Vitest і GitHub Actions, бо це найпоширеніші інструменти; кожна ідея переноситься на інші.

**Одна команда для кожної перевірки**, з однаковою назвою всюди, щоб файл інструкцій, хук і CI казали одне й те саме:

```json
{
  "scripts": {
    "check": "prettier --check . && eslint --max-warnings 0 . && tsc --noEmit",
    "test:coverage": "vitest run --coverage",
    "build": "vite build",
    "test:e2e": "playwright test"
  }
}
```

**Конфігурація лінтера без вимикача.** Вбудоване вимкнення заборонено, правило про коментарі з попереднього розділу включено, а обхідні шляхи заборонено за назвою. `assertionStyle: "never"` усе одно дозволяє `as const`, який, за документацією typescript-eslint, «це правило завжди дозволяє».

```js
import { defineConfig } from "eslint/config"
import tseslint from "typescript-eslint"

const noComments = {
  meta: {
    type: "suggestion",
    messages: { comment: "Say it in a name, a commit message or the docs." },
  },
  create: (context) => ({
    Program: () => {
      for (const comment of context.sourceCode.getAllComments()) {
        if (comment.type !== "Shebang") {
          context.report({ loc: comment.loc, messageId: "comment" })
        }
      }
    },
  }),
}

export default defineConfig({ linterOptions: { noInlineConfig: true } }, tseslint.configs.strictTypeChecked, {
  languageOptions: { parserOptions: { projectService: true } },
  plugins: { house: { rules: { "no-comments": noComments } } },
  rules: {
    "house/no-comments": "error",
    "@typescript-eslint/ban-ts-comment": ["error", { "ts-expect-error": true, "ts-ignore": true, "ts-nocheck": true }],
    "@typescript-eslint/consistent-type-assertions": ["error", { assertionStyle: "never" }],
    "@typescript-eslint/no-explicit-any": "error",
    "@typescript-eslint/no-non-null-assertion": "error",
    "no-magic-numbers": ["error", { ignore: [0, 1], ignoreArrayIndexes: true, ignoreDefaultValues: true }],
  },
})
```

**Суворі типи.** Ось прапорці, які наш власний `tsconfig.json` задає понад `strict`:

```json
{
  "compilerOptions": {
    "strict": true,
    "exactOptionalPropertyTypes": true,
    "noUncheckedIndexedAccess": true,
    "noPropertyAccessFromIndexSignature": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true
  }
}
```

**Поріг покриття.** `100: true` — це скорочення Vitest, яке «встановлює глобальні пороги на 100». У наявній кодовій базі почніть із сьогоднішніх чисел з `autoUpdate: true` і дайте їм зростати.

```ts
import { defineConfig } from "vitest/config"

export default defineConfig({
  test: {
    coverage: {
      provider: "v8",
      include: ["src/**/*.{ts,tsx}"],
      thresholds: { 100: true },
    },
  },
})
```

**Пробний тест для ваших правил**, щоб оновлення лінтера чи зміна конфігурації, яка вимикає правило, провалювали CI. Тримайте пробні файли поза звичайним запуском лінтера й перевіряйте їх тут із вимкненими ігноруваннями:

```ts
import { ESLint } from "eslint"
import { expect, it } from "vitest"

const eslint = new ESLint({ ignore: false })

it.each([
  ["comment.ts", "house/no-comments"],
  ["assertion.ts", "@typescript-eslint/consistent-type-assertions"],
  ["expect-error.ts", "@typescript-eslint/ban-ts-comment"],
  ["explicit-any.ts", "@typescript-eslint/no-explicit-any"],
])("rejects %s with %s", async (file, rule) => {
  const [result] = await eslint.lintFiles([`test/rule-probes/${file}`])

  expect(result?.messages.map(({ ruleId }) => ruleId)).toContain(rule)
})
```

**CI, який запускає ті самі команди**, плюс пошук коментарів, що вимикають перевірки, який не залежить від того, чи дотримується лінтер власних налаштувань. Зробіть це завдання обов’язковою перевіркою статусу:

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc
      - run: npm ci
      - run: npm run check
      - run: npm run test:coverage
      - run: npm run build
      - name: No suppression comments
        run: |
          if git grep -n -E "(eslint|oxlint)-disable|biome-ignore|@ts-(ignore|expect-error|nocheck)" -- "*.ts" "*.tsx" "*.js" "*.jsx" "*.mjs"; then exit 1; fi
```

**Правило гілки для `main`:** вимагайте завдання CI; вимагайте pull request лише зі злиттям через squash; вимагайте лінійної історії; блокуйте force-push і видалення; вимагайте рев’ю від власників коду, щойно агенти матимуть власну ідентичність.

**Власники коду для шляхів, яким потрібна людина**, включно з файлами, що визначають ваші перевірки:

```text
/db/migrations/ @your-org/maintainers
/src/billing/ @your-org/maintainers
/src/auth/ @your-org/maintainers
/.github/ @your-org/maintainers
/eslint.config.js @your-org/maintainers
/vitest.config.ts @your-org/maintainers
```

**Дозволи агента**, які забороняють команди, що ніколи не мають виконуватися, і дозволяють безпечну форму force-push. Цей приклад — `.claude/settings.json` для Claude Code; правила заборони мають перевагу над правилами дозволу, бо «правила оцінюються в такому порядку: deny, потім ask, потім allow». Пам’ятайте, що шаблони аргументів крихкі, і саме тому існує правило гілки вище.

```json
{
  "permissions": {
    "deny": ["Bash(git push --force *)", "Bash(git push -f *)", "Bash(git commit --no-verify *)"],
    "ask": ["Edit(./db/migrations/**)", "Edit(./src/billing/**)", "Edit(./.github/**)"],
    "allow": ["Bash(git push --force-with-lease *)"]
  }
}
```

**Файл інструкцій, який вказує на перевірки**, а не повторює їх:

```md
# AGENTS.md

## Done

`npm run check`, `npm run test:coverage`, `npm run build` and `npm run test:e2e` exit 0, in that order, on the branch you push. Put each exit code in the pull request. A summary is not evidence.

## Rules a check enforces

- No comments, suppression comments, type assertions or `any`: `npm run check` fails on each.
- Coverage stays at 100%: `npm run test:coverage` fails below it.

## Rules review enforces

- Fix the cause, not the symptom, and say in the pull request what caused the bug.
- One change per pull request.

## Human review required

Do not change these without a maintainer's written yes that names the paths:

- `db/migrations/`: applied to production and irreversible.
- `src/billing/` and `src/auth/`: money and identity.
- `.github/`, `eslint.config.js` and `vitest.config.ts`: the checks themselves.
```

## Де запобіжники saasyland.com сьогодні не дотягують

Написання цієї статті було аудитом, і аудит знайшов прогалини. У дусі решти статті — ось вони.

Три з них закрито: коментарі, обхідні шляхи, а також багаторядкові тернарні оператори з `?? undefined` тепер провалюють `bun run check` (#274). Залишаються такі:

- **Набір браузерних тестів** лежить поза лінтером: `bun run check:comments` читає `e2e/`, але жодне інше правило лінтера цього не робить.
- **Шляхи, що потребують рев’ю людини**, тримаються на інструкції та рівні дозволів агентів, а не на GitHub, бо агенти працюють під ідентичністю власника. До того ж у списку немає файлів, які визначають перевірки.
- **Описи pull request** не звіряються з diff.
- **Опублікований CLI** поки що не запускається проти живого API перед кожним випуском.
- **Мутаційне тестування**, яке вимірювало б, скільки тести перевіряють, а не скільки вони виконують, не налаштовано.

Кожне з цього — правило, яке ми проголошуємо, а не забезпечуємо, і кожне спуститься драбиною нижче.
