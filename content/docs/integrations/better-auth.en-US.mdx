Better Auth stores users, accounts, sessions and verification tokens in D1 through the Drizzle adapter. It provides email and password sign-up that signs a new account in at once and saves what needs a confirmed address for later, GitHub and Google sign-in, password reset, email change, TOTP two-factor authentication, admin user management and Polar checkout. Its HTTP API is served by `src/routes/api/auth.$.ts`. `auth.server.ts` and `auth.client.ts` set Better Auth's `basePath` to `ROUTES.API_AUTH_BASE`, the path that file serves, so the server and the browser client take it from one constant.

| `auth.routes.ts`                                       | Route guards for `beforeLoad`                                                                                                                                                                         |
| `auth.middleware.ts`                                   | Server-function middleware: `withRequest`, `authorized`, `withRateLimit` and `RATE_LIMITS`                                                                                                            |

| `auth.constants.ts`                                    | `AUTH_PROVIDER`: the ids of the email and password provider (`credential`) and the OAuth providers; `LOGIN_METHOD` and `LAST_LOGIN_METHOD_COOKIE` for the **Last used** badge                         |

## Route guards

| Guard                | Used by                          | Behaviour                                                                                    |
| -------------------- | -------------------------------- | -------------------------------------------------------------------------------------------- |
| `requireSignedIn`    | `/app`                           | Redirects to sign-in without a session, with the page as `redirect`, and returns the session |
| `requireAdmin`       | `/admin`                         | Also requires the `admin: ["access"]` permission, otherwise redirects to `/app`              |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Sends a signed-in user to `redirect`, or to `/admin` or `/app` by role                       |
| `redirectAfterAuth`  | `/auth/callback`                 | Requires a session, then redirects to `redirect` or to the workspace for the role            |
| `redirectIfVerified` | `/auth/verify-email`             | Sends a session with a confirmed address to `redirect`, or to `/admin` or `/app` by role     |

The guards load the session through the query cache and, when the signed-in user changes, remove every cached query that is not public with `removeUserData` from `auth.session.ts`.

## Server functions

Page guards only protect navigation, so every protected server function checks the caller again with middleware from `auth.middleware.ts`:

- `authorized(permission?)` requires a session, optionally checks a permission, and adds the session to the context as `context.auth`. Operations on the caller's own data use `context.auth.user.id`, never a user ID from the input.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (<RepositoryFact name="sensitiveRateLimit" /> requests per <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) or `RATE_LIMITS.TOKEN` (<RepositoryFact name="tokenRateLimit" /> per <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) limits a public operation per client IP from `cf-connecting-ip`.
- `withRequest`, which both include, maps errors to `AppError` codes: Better Auth errors become `AUTH_API_ERROR` with their error key, Zod errors become `VALIDATION`, and unexpected errors are logged and returned as `INTERNAL_ERROR`.

## Roles and permissions

`auth.roles.ts` defines two roles: `admin` and `customer` (the default for new accounts). Each area declares the statements of its resources and grants them to roles in `src/areas/<area>.access.ts`: today the auth area declares `admin` and `settings`, the products area `category` and `product`, the courses area `course` and `video`, and the payments area `order`, and each grants them to admins. `auth.access.ts` builds the access control and the roles from them; the admin role also receives Better Auth's admin statements. `hasPermission({ permission, role })` is shared by guards, middleware and the UI. See [Roles and permissions](/docs/guides/roles-and-permissions).

## Email and rate limits

`auth.server.ts` names no other area. A list of the auth area's own joins the plugins the others add:

| List         | Each area declares                                                                                | Barrel                             | Used by                                                                                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth plugins | `src/data/<area>.auth-plugins.ts`: plugins, with the paths Better Auth exempts from rate limiting | `src/data/auth-plugins.entries.ts` | `plugins` and `rateLimit.customRules`; the auth area adds `haveIBeenPwned`, the licence area the `user.delete.before` hook that revokes a deleted account's licence, and the polar area the Polar plugin |

The areas' plugins follow `admin` and `twoFactor` and precede `tanstackStartCookies`, which must come last. Better Auth reads the user and session fields of its plugins from the plugin list in order up to the first spread list, so a plugin that adds such fields belongs in `auth.server.ts`. The email hooks call the senders of the verification, account and user modules directly, because auth needs email: `sendVerifyEmail`, `sendExistingAccountEmail`, `sendResetPasswordEmail`, `sendPasswordChangedEmail`, `sendDeleteAccountEmail` and `sendChangeEmailConfirmationEmail`. Better Auth's own rate limiter stores its counters in the D1 `rate_limit` table under an `auth:` prefix through `consumeRateLimit` from `src/lib/rate-limit.ts`, which uses atomic upserts and rejects requests when its storage is unavailable. `clientAddress` in `auth.middleware.ts` resolves a request's client the way that limiter does, from `cf-connecting-ip` with IPv6 addresses grouped by /64. The cookie prefix is `APP_SLUG` from the branding. `getRequestSession` bypasses the cookie cache, so authorization always reads the session from D1.
