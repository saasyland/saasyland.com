## 設定

`src/integrations/better-auth/auth.server.ts` が Better Auth のインスタンスを作成します。

- D1 上の Drizzle アダプター、UUID v7 の ID、Cookie プレフィックス `saasyland`、`development` と `test` 以外のモードでのセキュア Cookie、`appHostsForMode` によるモード別の許可ホスト。
- メール確認が必須のメールとパスワード認証、大文字と記号を含む <RepositoryFact name="passwordMinLength" />〜<RepositoryFact name="passwordMaxLength" /> 文字のパスワード（`auth.constraints.ts`）、パスワードリセット時のセッション失効と、リセット後の「パスワードが変更されました」というメール（`onPasswordReset`）。確認とリセットのリンクは `EMAIL_LINK_LIFETIME_HOURS`（`auth.constants.ts`）の間有効です。この値は `emailVerification.expiresIn` と `resetPasswordTokenExpiresIn` の両方を設定し、メールにも記載されます。
- `hooks.before` ミドルウェアの `enforceInputPolicy`（`auth.hooks.ts`）は、フォームのスキーマを Better Auth 自身のエンドポイントにも適用します。対象は登録、パスワードのリセットと変更、プロフィールとメールの変更、ユーザー作成やパスワード設定を行う管理エンドポイントです。`/api/auth` に直接送られたリクエストもルールを回避できず、`400 VALIDATION_ERROR` を返します。
- アカウント連携と暗号化された OAuth トークンを備えた GitHub と Google のソーシャルプロバイダー。
- プラグイン: `auth.access.ts` のアクセス制御とロールを使う `admin`、`twoFactor`、Polar（`checkout`、`portal`、`webhooks`）、`tanstackStartCookies`。
- D1 の `rate_limit` テーブルに保存されるレート制限。`/get-session`、`/sign-out`、Polar の Webhook は対象外です。
- 追加のユーザーフィールド `timezone` と、確認メール付きのメールアドレス変更。

`src/routes/api/auth.$.ts` は `/api/auth` 配下のすべての GET と POST を `auth.handler` に渡します。

## 画面

`/auth` レイアウトは `auth.*` 名前空間をプリロードし、すべての認証ページを同じグリッドに配置します。`lg` ブレークポイント以上では、共通のヘッダー行の下に 2 つの列が並び、左に見出しと約束事項を載せた案内パネル、右にフォームを置きます。ワードマークと見出しは左端がそろい、見出しとフォームは同じ高さから始まるため、認証ページ間を移動してもフォームの見出しの位置は変わりません。`lg` 未満では案内パネルを隠し、ワードマーク、**ホームへ戻る** リンク、フォームを、フォームと同じ幅の中央寄せの 1 列に並べます。`AuthPending` は読み込み中も同じグリッドを描画し、`e2e/specs/auth-layout.spec.ts` が 4 つのウィンドウサイズで配置を確認します。入力欄、プロバイダーのボタン、主要なボタンの高さは、サイトの CTA ボタンと同じです。

| ルート                                          | コンポーネント                            | 動作                                                                                                                                                                                                        |
| ----------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/auth/sign-in`                                 | `OAuthButtons`、`SignInForm`              | Better Auth の `signIn.email` でサインインします。未確認のメールには新しい確認リンクが送られ、`unverified` 付きで `/auth/verify-email` へ進みます。2FA が有効なアカウントは `/auth/two-factor` へ進みます。 |
| `/auth/sign-up`                                 | `OAuthButtons`、`SignUpForm`              | サーバー関数 `signUpWithPassword` を呼び出し、アドレスにかかわらず `/auth/verify-email` へ移動します。[既知のアドレスでのサインアップ](#signing-up-with-a-known-address)を参照。                            |
| `/auth/callback`                                | なし                                      | `redirectAfterAuth` が訪問者を `redirect` へ、それがなければ管理者を `/admin` へ、それ以外を `/app` へ送ります。                                                                                            |
| `/auth/verify-email`                            | `VerifyEmailForm`                         | [メール確認](/docs/features/email-verification)を参照。                                                                                                                                                     |
| `/auth/forgot-password`、`/auth/reset-password` | `ForgotPasswordForm`、`ResetPasswordForm` | [パスワードリセット](/docs/features/password-reset)を参照。                                                                                                                                                 |
| `/auth/two-factor`                              | `TwoFactorForm`                           | [二要素認証](/docs/features/two-factor)を参照。                                                                                                                                                             |

サインインに成功すると、`useAuthRedirect` の `finishSignIn` がクエリキャッシュから前のユーザーのデータを削除し、ルーターキャッシュをクリアして、`redirect` を保持したまま `/auth/callback` へ移動します。`/auth/sign-in` に `?error=` として返された Better Auth のエラーは、対応する `auth.errors` のメッセージで表示されます。

## 既知のアドレスでのサインアップ [#signing-up-with-a-known-address]

サインアップ画面は、アドレスにアカウントがあるかどうかを決して明かしません（アカウント列挙に対する OWASP の推奨）。Better Auth はすべてのサインアップに同じ応答、つまり `token: null` とセッションのないユーザーを返し、フォームは常に `/auth/verify-email` へ移動します。このページには「受信トレイをご確認ください。メールアドレスを確認するためのリンク、またはすでにアカウントをお持ちの場合はログイン用のリンクをお送りしました。」と表示されます。受信トレイに届くものはアドレスによって異なります。

| アドレス                   | 結果                                                                                                                                                                                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| アカウントがない           | Better Auth がユーザーを作成し、`sendVerifyEmail` が確認リンクを送ります。                                                                                                                                                                                         |
| 確認済みのアカウントのもの | 何も作成されません。`onExistingUserSignUp` が `sendExistingAccountEmail` を呼び出し、「SaaSy Landのアカウントはすでにお持ちです」というメールで、アカウントが持つサインイン方法、`redirect` を保持したサインインリンク、パスワードをリセットするリンクを送ります。 |
| 未確認のアカウントのもの   | 何も作成されません。`onExistingUserSignUp` が `sendVerifyEmail` で新しい確認リンクを送ります。                                                                                                                                                                     |

どちらの通知もサインアップページのロケールで送られ、1 つのアドレスにつき 1 時間あたり <RepositoryFact name="recipientEmailsPerHour" /> 通までに制限されます。Better Auth は既知のアドレスでも送信されたパスワードをハッシュ化し、`onExistingUserSignUp` を `waitUntil` でバックグラウンド実行します。そのため、サインイン方法の検索もメールも応答を遅らせることはなく、新しいアドレスへの応答との違いは、書き込む 2 行だけです。

未確認のアカウントへのサインインは `EMAIL_NOT_VERIFIED` を返し、`emailVerification.sendOnSignIn` が、リクエスト元のサインインページのロケールと `redirect` で新しいリンクを送ります。`SignInForm` は `/auth/verify-email?unverified=true` へ移動し、このページは新しいリンクを送信中であることを伝えて **確認メールを再送信** を表示します。パスワードが間違っている場合は通常どおり `INVALID_EMAIL_OR_PASSWORD` が返り、何も送信されません。

## ルートガード

`src/integrations/better-auth/auth.routes.ts` は `beforeLoad` で使うガードをエクスポートします。

- `requireSignedIn` は `/app` を保護し、ページを `redirect` として `/auth/sign-in` へリダイレクトします。
- `requireAdmin` は `/admin` を保護します。`admin: ["access"]` 権限のないサインイン済みユーザーは `/app` へ移動します。
- `redirectIfSignedIn` は、サインインと登録の画面を開いたサインイン済みユーザーを `redirect` または自分のワークスペースへ送ります。
- `redirectAfterAuth` は `/auth/callback` を処理します。

ガードは `getCurrentSessionQuery` でセッションを読み取り、サインイン中のユーザーが変わると、[公開クエリ](/docs/conventions/data-fetching#public-queries)は残したまま、前のユーザーのデータをクエリキャッシュから削除します。`redirect` がサインイン、登録、OAuth、二要素認証の確認の間でどのように引き継がれるかは、[認証フロー](/docs/guides/auth-flows#return-path) で説明しています。

## サーバー関数

サーバー関数は `auth.middleware.ts` のミドルウェアを使います。`authorized()` はセッションを要求し、`authorized({ user: ["list"] })` はさらに権限を確認し、`withRateLimit(kind, RATE_LIMITS.SENSITIVE)` はクライアント IP ごとに呼び出し回数を制限します。

```ts
export const signOutUser = createServerFn({ method: "POST" })
  .middleware([authorized()])
  .handler(({ context }) => auth.api.signOut({ headers: context.requestHeaders }))
```

ロールは `admin` と `customer`（新規ユーザーの既定）の 2 つです。
