O plugin `admin` do Better Auth oferece personificação, e `src/modules/user/use-cases` a encapsula:

```ts
export const impersonateUser = createServerFn({ method: "POST" })
  .middleware([authorized({ user: ["impersonate"] })])
  .validator((input: User["impersonateUser"]) => userZodSchemas.impersonateUser.parse(input))
  .handler(({ context, data }) => auth.api.impersonateUser({ body: data, headers: context.requestHeaders }))
```

`stopImpersonatingUser` exige apenas uma sessão logada. Os dois arquivos exportam opções de mutação (`impersonateUserMutation`, `stopImpersonatingUserMutation`).

## Início

**Entrar como este usuário** no menu de ações de um usuário ([Usuários (admin)](/docs/features/users-admin)), em `/admin/users/all` ou no perfil do usuário, chama `impersonateUser`. O Better Auth cria para o usuário uma sessão marcada com `impersonatedBy`, guarda o token de sessão do administrador em um cookie assinado `admin_session` e troca o cookie de sessão para a nova sessão; `tanstackStartCookies()` leva os dois cookies na resposta da função de servidor. Em seguida, o menu remove os dados do administrador do cache de consultas com `removeUserData`, limpa o cache do roteador e abre `/app`.

O item aparece apenas para um usuário que não é administrador nem está bloqueado. O Better Auth se recusa a personificar um usuário com papel de administrador, a menos que quem chama tenha `user: ["impersonate-admins"]`, que nenhum papel em `auth.access.ts` concede, e o hook de sessão dele nega a sessão a um usuário bloqueado. `auth.server.ts` não define `impersonationSessionDuration`, então a sessão dura o quanto o padrão do Better Auth permitir.

## Banner e encerramento

`ImpersonationBanner` (`src/presentation/components/custom/app/impersonation-banner.tsx`) fica acima do cabeçalho do layout de `/app`. Ele lê `getCurrentSessionQuery` e só é renderizado quando a sessão tem `impersonatedBy`: uma região rotulada a partir de `components.custom.impersonation-banner.json` que mostra o usuário personificado e o e-mail dele, e um botão **Encerrar personificação**. O botão chama `stopImpersonatingUser`, que exclui a sessão de personificação e restaura a sessão do administrador a partir do cookie `admin_session`; depois o banner remove os dados do usuário do cache e abre o perfil desse usuário em `/admin/users`.

As duas mutações primeiro aguardam `settleQueries` (`src/lib/settle-queries.ts`), que se resolve quando nenhuma consulta está carregando, e só então chamam o servidor. Uma leitura ainda em andamento leva o cookie da sessão que está sendo deixada. Se ela chegasse ao servidor depois que `stopImpersonatingUser` excluiu a sessão de personificação, o Better Auth responderia expirando o cookie de sessão, e uma resposta que chegasse depois da resposta da própria interrupção apagaria o cookie restaurado do administrador e o desconectaria. A verificação de confirmação do e-mail, que se repete enquanto o cliente personificado não confirmou o endereço, é uma dessas leituras.

## Sessões

- `getActiveSessions` deixa as sessões de personificação de fora da lista de sessões das configurações, e o próprio endpoint `list-sessions` do Better Auth faz o mesmo.
- O card de sessões no perfil de um usuário as lista, então um administrador pode revogar uma sessão de personificação que outro administrador deixou aberta.
- As guardas de rota removem os dados do usuário anterior do cache de consultas quando o usuário da sessão muda, então cada navegação depois de iniciar ou encerrar carrega os dados do usuário certo.

Não existe log de auditoria de personificações.
