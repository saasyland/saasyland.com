---
title: "File di route"
description: "L'unica forma di una route di pagina e di una route di layout: NAMESPACE o NAMESPACES, un loader con un solo Promise.all, uno scheletro che rispecchia la pagina, schemi di ricerca e link."
---

Ogni file in `src/routes` ha la stessa forma, quindi chi ne conosce uno li conosce tutti. Un file di route compone: dichiara ciò di cui la pagina ha bisogno e posiziona i componenti. Widget, form, finestre di dialogo e colonne delle tabelle si trovano in `src/presentation/components/custom`.

## Route di pagina

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        onReorder={({ position, row }) => move.mutateAsync({ courseId: row.id, position })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        search={t("table.search")}
        selectable
      />
    </div>

}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Il componente** è una `const` locale chiamata `<Name>Page`, definita per prima. Piccoli frammenti di markup usati solo da questa pagina possono stare sopra di essa come componenti locali, come fanno `CourseProgress` e `StartLink` in `_site._marketing.courses.$course.index.tsx`; tutto ciò che ha dati, mutation o stato propri va in un file di componente.
- **Un solo namespace.** `const NAMESPACE = "pages.<area>.<page>"` sta subito sopra `export const Route` ed è usato in `loadPageMetadata`, `preloadNamespaces` e `staticData`. Tutto il resto di cui la pagina ha bisogno lo dichiara il suo layout.
- **Un solo `Promise.all`.** Il loader avvia tutto il lavoro in una volta: i metadati della pagina, il namespace e ogni query che i componenti leggono. Restituisce `{ locale, metadata }` per `head`. Non attendere mai uno di questi prima di avviare il successivo.
- **`head: pageHead(ROUTES.X)`** costruisce titolo, descrizione, URL canonico e alternative a partire dai metadati del file del namespace.
- **I percorsi provengono da `ROUTES`** in `src/routes.ts`, che riunisce i percorsi di tutte le aree (vedi [Percorsi e navigazione](#paths-and-navigation)); non scrivere mai un percorso letterale.

Una pagina il cui titolo proviene da un record attende quel record e costruisce il proprio head dai dati del loader, come fa `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Route di layout

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Un layout dichiara `const NAMESPACES = [...] as const` sopra `export const Route` e lo precarica. Quando non ne ha, omette l'opzione; non esiste `namespaces: []`.
- Un namespace di cui un componente di un'altra area ha bisogno nel layout viene aggiunto da quell'area in `src/areas/<area>.ts`, che indica il layout con il suo route id, e il layout espande `...layoutNamespaces("/app")` nei suoi `NAMESPACES`. L'area della licenza aggiunge `pages.license`, `pages.withdrawal` e `withdrawal.validations` a `/app`, la cui panoramica mostra la scheda e l'offerta della licenza e la cui pagina della licenza mostra la scheda del recesso, `withdrawal.validations` a `/_site/_marketing` e `pages.admin.users.license` a `/admin/users`; l'area dei pagamenti aggiunge `pages.admin.customers` e `pages.admin.orders` a `/admin/users`; e l'area della newsletter aggiunge `auth.validations` a `/_site/_marketing` e `/_site/docs`, i cui footer mostrano il modulo della newsletter. `browser.test.tsx` controlla in compilazione che ogni layout nominato da un'area sia un route id.
- Il componente, quando il layout ne rende uno, si chiama `<Name>Layout` e posiziona un `<Outlet />`.
- Una guard va in `beforeLoad` sul layout che possiede l'area: `beforeLoad: requireAdmin` in `admin.tsx`, `requireSignedIn` in `app.tsx`, entrambi layout dell'area di autenticazione. Le guard decidono solo la navigazione; ogni server function controlla comunque il proprio permesso.

## Ordine delle opzioni

`sort-keys` è disattivata in `src/routes` perché TanStack Router inferisce i tipi nell'ordine di dichiarazione. Le opzioni sono in ordine alfabetico, tranne `validateSearch`, che viene per prima, prima di qualsiasi cosa legga la ricerca:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Non scrivere mai un array o un oggetto di dati direttamente dentro `createFileRoute`; dichiaralo come costante sopra.

## Parametri di ricerca

`validateSearch` è uno `zod.object` costruito con gli helper di `src/lib/search-params.ts`:

| Helper                            | Valore quando il parametro manca o è malformato | Uso                                      |
| --------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| `searchText()`                    | `undefined`                                     | Token, email, codici di errore           |
| `searchFlag()`                    | `undefined`                                     | Booleani                                 |
| `searchParam(schema)`             | `undefined`                                     | Qualsiasi altro schema, come un percorso |
| `searchChoice(choices, fallback)` | `fallback`                                      | Una scheda o una vista                   |

Il testo assente resta `undefined`, quindi un valore predefinito non finisce mai in un URL costruito dal router. Un parametro `searchChoice` è abbinato a `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, che rimuove il valore predefinito dall'URL. Una pagina a cui un altro sito rimanda i visitatori dichiara anche `search: { middlewares: [onlyDeclaredSearch(schema)] }` con il proprio schema, come fanno `/app` e `/app/license` per il checkout di Polar: il router costruisce allora il suo indirizzo con i soli parametri dichiarati, e il server reindirizza un indirizzo che porta un altro parametro allo stesso indirizzo senza di esso, prima che un controllo o la pagina lo leggano. Non scrivere mai a mano controlli come `typeof search["x"] === "string"`; aggiungi un helper quando serve un nuovo tipo di campo. Quando un componente figlio ha bisogno di un parametro che la pagina ha già verificato come presente, la pagina ne restringe il tipo e lo passa in basso, come `auth.reset-password.tsx` passa `token` a `ResetPasswordForm`. Le pagine che leggono gli stessi parametri condividono uno schema in `src/data`, che analizzano anche i loro scheletri, come fanno `/app/license` e la parte della panoramica aggiunta dall'area della licenza con `licenseSearchSchema` (`src/data/license.ts`).

## Scheletri

La navigazione deve sembrare istantanea, quindi ogni route che rende una pagina ha un `pendingComponent` che la rispecchia: lo stesso layout, le stesse card e lo stesso numero di righe.

- Gli scheletri si trovano nel file pending dell'area (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) e usano `Skeleton` di shadcn.
- Gli scheletri sono nello script di ingresso di ogni pagina, quindi uno scheletro importa `Skeleton`, le primitive shadcn, altri scheletri e le costanti che ne fissano le lunghezze, mai un form o il file che lo contiene; `pending-imports.test.ts` fallisce quando uno raggiunge `@tanstack/react-form` (vedi [Prestazioni](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Un segnaposto di testo riceve il vero token tipografico più `h-lh scale-y-70`, così ha l'altezza della riga che sostituisce: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- La lunghezza degli elenchi proviene dalle costanti che usa la pagina: `DataGridPending` in `data-grid-pending.tsx` disegna per impostazione predefinita `DEFAULT_PAGE_SIZE` righe, la dimensione di pagina di ogni tabella dell'amministrazione.
- Lo scheletro di un layout renderizza il `pendingComponent` della prima route sotto il layout che corrisponde al percorso corrente e ne definisce uno, che `usePagePending(layout)` in `src/hooks/use-page-pending.ts` legge dall'albero delle route: `AdminPending`, `AppPending`, `AuthPending` e `MarketingPending` per i loro layout, e `AdminUsersPending` e `AdminCourseSectionPending` un livello più in basso. La route di una pagina è quindi l'unico punto che nomina il suo scheletro, qualunque sia il layout che lo mostra; `/admin/users`, che reindirizza a `/admin/users/all`, imposta lo scheletro di quella pagina.
- Non esiste un `defaultPendingComponent` valido per tutto il router. `src/router.tsx` imposta `defaultPendingMs` a <RepositoryFact name="navigationPendingMs" unit="millisecond" /> e `defaultPendingMinMs` a <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, entrambi da `src/data/navigation.constants.ts`: una navigazione non ancora terminata dopo il primo mostra lo scheletro della route, e lo scheletro sparisce non appena la pagina è pronta, senza restare un istante di più. Le route mantengono questi valori; vedi [Prestazioni](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) per le misurazioni su cui si basano.
- Le pagine della documentazione disegnano i loro scheletri dentro il layout della documentazione: `DocsIndexPending` e `DocsPagePending` riempiono le aree della griglia dell'articolo e dell'indice dei contenuti di Fumadocs, così una navigazione tra pagine della documentazione mantiene la barra laterale sullo schermo. Il componente della pagina renderizza l'MDX in un proprio `<Suspense key={path}>`, così la barra laterale funziona prima che il chunk MDX della pagina sia caricato, e una navigazione sostituisce l'HTML del server della pagina precedente invece di idratarlo con i dati della successiva.

## Link

- I link del router ricevono una costante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, oppure un pattern di route con `params` per i percorsi dinamici. `LinkButton` e `SidebarMenuLink` di shadcn ricevono `to` allo stesso modo, e `AnchorButton` riceve un `href` per un indirizzo fuori dall’albero delle route.
- Non aggiungere mai il prefisso del locale a un link del router; lo aggiunge la riscrittura del router. Un URL completo nel locale corrente, per un valore che esce dal router come stringa, proviene da `router.buildLocation({ ... }).publicHref`, come fa `use-auth-redirect.ts` per costruire i suoi link di accesso. `localizePathname` serve per gli URL costruiti fuori dal contesto di un router o per un altro locale: email, destinazioni di reindirizzamento di Better Auth, link dentro l'MDX e il selettore della lingua.

## Percorsi e navigazione [#paths-and-navigation]

Nessun file dell'applicazione elenca tutte le aree. Ogni area, come i corsi, i prodotti o le pagine legali, dichiara i propri percorsi, le proprie voci di menu con le relative etichette, gli scheletri delle pagine e i permessi, e un barrel li riunisce: un'area si aggiunge o si esclude con i suoi file. È così che la CLI `saasyland` compone un progetto a partire da layer di template. Solo `scripts/areas.ts`, che l'applicazione non carica mai, elenca le aree opzionali con i loro file, così che `bun run check:areas` possa controllare i tipi del sito senza ciascuna di esse ([Test](/docs/conventions/testing#tests-follow-the-areas)).

| Cosa                                   | Ogni area dichiara                                                            | Barrel                            | Letto da                                                                                                                                                                                   |
| -------------------------------------- | ----------------------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Percorsi                               | `src/areas/<area>.shared.ts`: un `export const` per percorso                  | `src/routes.ts`                   | `import * as ROUTES from "~/src/routes"`                                                                                                                                                   |
| Voci di menu                           | `src/areas/<area>.navigation.ts`: `entries` in un oggetto `<AREA>_NAVIGATION` | `src/areas/navigation.entries.ts` | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` e `FOOTER_NAVIGATION` in `src/data/navigation.ts` |
| Statistiche e pannelli della dashboard | `src/data/<area>.dashboard.ts`: una lista `<AREA>_DASHBOARD`                  | `src/data/dashboard.entries.ts`   | `ADMIN_DASHBOARD_STATS` e `ADMIN_DASHBOARD_PANELS` in `src/data/dashboard.ts`                                                                                                              |
| Permessi                               | `src/areas/<area>.access.ts`: un oggetto `<AREA>_ACCESS`                      | `src/areas/access.entries.ts`     | `APP_STATEMENTS` e `grantsOf` in `src/integrations/better-auth/auth.access.ts`                                                                                                             |
| Percorsi non elencati                  | `src/areas/<area>.shared.ts`: `unlisted` in un oggetto `<AREA>_SHARED`        | `src/areas/shared.entries.ts`     | `UNLISTED_ROUTES` e `isUnlistedRoute` in `src/areas/shared.ts`                                                                                                                             |
| Namespace dei layout                   | `src/areas/<area>.ts`: `layoutNamespaces` in un oggetto `<AREA>_BROWSER`      | `src/areas/browser.entries.ts`    | `layoutNamespaces(layout)` in `src/areas/browser.ts`                                                                                                                                       |

Un barrel contiene solo righe `export { … } from`, una per file di area e ordinate per modulo, come `src/integrations/drizzle-orm/drizzle.schemas.ts`. Un barrel che solo aree opzionali riempiono riceve anche un file dalla base, come `src/areas/core.ts`, che contiene solo il nome della base, così un progetto senza quelle aree supera ancora il controllo dei tipi e il lint. Il barrel dei percorsi è `src/routes.ts` stesso, e ogni file lo importa come un unico namespace, `import * as ROUTES from "~/src/routes"`, così ogni percorso mantiene il suo tipo letterale e `<Link to={ROUTES.COURSES}>` resta verificato rispetto all'albero delle route:

```ts title="src/routes.ts"
export { API, HOME } from "./areas/core.shared.ts"
export { ADMIN_COURSES, ADMIN_COURSES_CREATE, COURSES } from "./areas/courses.shared.ts"
```

Una voce di menu indica dove compare con `placement` (`NAVIGATION_PLACEMENT` in `src/data/navigation.constants.ts`): la sidebar dell'admin, i pulsanti sopra la dashboard, le azioni rapide della palette dei comandi, la barra laterale dell'app clienti e le sue risorse, l'intestazione pubblica o il footer. Il suo `order` la colloca tra le voci delle altre aree, quindi nessuna lista dipende dall'ordine dei file. Le voci dell'admin indicano anche il loro gruppo della sidebar (`group`) e i link del footer la loro colonna (`column`); `ADMIN_NAVIGATION_GROUPS` e `FOOTER_COLUMNS` fissano l'ordine di gruppi e colonne, e quelli che nessuna area riempie vengono omessi. La console di amministrazione e l'app clienti esistono solo con l'accesso, quindi appartengono all'area di autenticazione: i loro percorsi, `/admin`, `/admin/settings`, `/app` e `/app/settings`, le loro voci di dashboard, panoramica, impostazioni e gestione utenti, e **Accedi** nell'intestazione e nel footer:

Una voce dell’intestazione o del piè di pagina può indicare un’etichetta `signedIn` che sostituisce la sua per un visitatore che ha effettuato l’accesso, e il suo link porta allora all’area di lavoro del visitatore: `/admin` per un account con accesso di amministrazione, `/app` per tutti gli altri. `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`) lo decide dal ruolo della sessione con `hasPermission` e il permesso `admin: ["access"]` che controlla `requireAdmin`. Le pagine pubbliche sono prerenderizzate, quindi il loro HTML mostra **Accedi**; dopo l’idratazione, un browser che ha il cookie di Better Auth con l’ultimo metodo di accesso usato chiede la sua sessione, e l’intestazione, il suo menu mobile e il piè di pagina mostrano **Il tuo account** al suo posto, già con il link all’area giusta. Un browser che non ha mai effettuato l’accesso non chiede nulla. Finché una parte della pagina non è idratata, `useVisitorWorkspace` non restituisce nulla, anche se il browser ha già la sessione, perché `useHydrated` risponde con il valore del server mentre React idrata: un footer che si idrata dopo l'arrivo della sessione mostra lo stesso **Accedi** dell'HTML e cambia dopo, invece di rompere l'idratazione.

Ogni voce dell’admin apre una schermata che funziona con dati reali, e la landing page le conta tutte. Una schermata i cui dati non hanno ancora una fonte non riceve alcuna voce (vedi [Dashboard di amministrazione](/docs/features/admin-dashboard#real-data-only)).

L'area della licenza aggiunge la sua voce **Licenza** alla barra laterale dell'app clienti, e l'area dei contenuti aggiunge **Documentazione** alle sue risorse, sopra l'indirizzo del supporto. L'area di base dichiara solo `/` e `/api`, e **Prezzi** nell'intestazione, l'unica voce con un `hash`, che porta alla sezione dei prezzi di `/`.

Una statistica della dashboard ha un `prefetch`, che il loader di `/admin` esegue, e un hook `useValue`, che `DashboardStats` chiama per leggere il numero.

Il file di accesso di un'area contiene le dichiarazioni di permesso delle sue risorse e i ruoli a cui le concede. `auth.access.ts` costruisce il controllo degli accessi di Better Auth da `APP_STATEMENTS` e ogni ruolo da `grantsOf(role)`, quindi l'integrazione di autenticazione non nomina alcuna area, e `APP_STATEMENTS` fallisce quando due aree dichiarano la stessa risorsa (vedi [Ruoli e permessi](/docs/guides/roles-and-permissions)).

Le liste di `src/data/navigation.ts` hanno un tipo dichiarato, `NavigationEntry`, invece dei tipi delle voci che le aree dichiarano in quel momento, quindi una posizione che nessuna area riempie, come le azioni della dashboard in un progetto senza l'area dei pagamenti, è una lista vuota che supera comunque il controllo dei tipi. `navigation.test.ts` controlla in compilazione che il `to` di ogni voce dichiarata da un'area sia un percorso dell'albero delle route (`FileRouteTypes["to"]` da `src/routeTree.gen.ts`).

Una voce riceve la sua `area` dal `name` dell'oggetto `<AREA>_NAVIGATION` della sua area, e l'area le assegna l'etichetta nel proprio file di messaggi: `<placement>.<key>` in `messages/<locale>/navigation.<area>.json`, come `admin.courses` e `header.courses` in `navigation.courses.json`. Una statistica della dashboard ha l'etichetta sotto la sua `key` in `dashboard.<area>.json`, e una sezione dell'admin definisce le etichette delle sue sottopagine per le breadcrumb sotto `breadcrumbs.<segment>` nel suo `navigation.<area>.json`, come `breadcrumbs.create`; una scheda della gestione utenti ha l'etichetta sotto `userTabs.<key>`, che dà il nome alla scheda e alla sua pagina nelle breadcrumb, e un pannello della dashboard tiene i suoi testi sotto la sua `key` in `dashboard.<area>.json`. Entrambi i tipi di file sono namespace radice, quindi ogni menu può mostrare l'etichetta di qualsiasi voce, e `useNavigationLabel` in `src/hooks/use-navigation-label.ts` restituisce l'etichetta di una voce. Ciò che appartiene al menu stesso resta nel suo namespace: `groups.<group>` in `pages.admin.sidebar`, `columns.<column>` in `components.custom.footer` e la call to action, il pulsante del menu e il link di salto dell'intestazione in `components.custom.navigation`. `enum-labels.test.ts` fallisce quando a una voce o a una statistica manca l'etichetta in un locale.

Un'area le cui pagine vengono renderizzate dal Worker a ogni richiesta, come `/admin`, `/auth` o `/courses`, elenca quei percorsi nel campo `unlisted` del suo oggetto `<AREA>_SHARED`, in `src/areas/<area>.shared.ts`. Il plugin di TanStack Start in `src/data/tanstack.vite.ts` li esclude dal prerendering con `isUnlistedRoute`, e `buildPageHead` assegna loro la card del sito invece di una card della pagina (vedi [Motori di ricerca e anteprime social](/docs/features/seo)). Vite non risolve l'alias `~` mentre carica la propria configurazione, quindi ogni file di `src/areas` che carica, `shared.ts`, `shared.entries.ts` e ogni `<area>.shared.ts`, importa con un percorso relativo. L'entry del Worker, `vite.config.ts` e il progetto Remotion raggiungono ogni file condiviso tramite `ROUTES`, quindi un file condiviso contiene percorsi e nulla che si porti dietro una dipendenza. I controlli del sito online sono un tipo di file a sé, `src/areas/<area>.live.ts`, perché li caricano solo la verifica dopo il deploy e la documentazione. Anche le voci di menu sono un tipo di file a sé e puro, `src/areas/<area>.navigation.ts`, che `src/areas/navigation.entries.ts` riunisce e `src/data/navigation.ts` legge, perché il progetto Remotion legge il menu dell'admin e il suo job di CI installa solo i pacchetti propri di Remotion, quindi non può caricare il file del browser di un'area, `src/areas/<area>.ts`, che importa codice del router, di TanStack Query e delle server function.
