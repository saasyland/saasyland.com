Workflow-файли розміщено в `.github/workflows/`. Workflow-файли застосунку (`ci.yml`, `e2e-reusable.yml` і `deploy-reusable.yml`) налаштовують інструментарій через складену дію `.github/actions/setup`: Bun 1.4.4, Vite+ з версією Node з `.nvmrc`, кеш Bun, `bun install --frozen-lockfile --ignore-scripts` і `bun run typegen`. Натомість `remotion.yml` налаштовує Node з `.nvmrc` і npm.

| Workflow              | Тригер                                                 | Завдання                                                                                  |
| --------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull request і push у `main`                           | Перевірки й покриття, E2E у Chromium, потім розгортання preview або production із релізом |
| `e2e-full.yml`        | Push у `main`, щотижня в понеділок о 03:15 UTC, вручну | WebKit при push; Chromium і WebKit за розкладом і при ручному запуску                     |
| `e2e-reusable.yml`    | Викликається наведеними вище workflow                  | Тестова база даних, тестова збірка та один проєкт Playwright                              |
| `deploy-reusable.yml` | Викликається з `ci.yml`                                | Збірка, міграції D1 і `wrangler deploy`                                                   |
| `remotion.yml`        | Зміни в `remotion/` або його спільних константах       | Перевіряє та пакує проєкт відео для лендингу за допомогою npm                             |

## Перевірки

Завдання `verify` у `ci.yml` запускає `bun run check` (таблиці імен класів, перевірки i18n і контенту, форматування, лінтинг і типи) та `bun run test:coverage`, а потім завантажує звіт про покриття. Завдання `e2e` запускає `db:reset:test` і `build:test`, встановлює браузер і запускає `bunx playwright test e2e/specs --project=chromium`. Невдалі запуски E2E завантажують звіт Playwright.

## Розгортання

Розгортання запускаються лише після успішних `verify` і `e2e`:

| Подія                                  | Ціль         | Середовище GitHub | URL                           |
| -------------------------------------- | ------------ | ----------------- | ----------------------------- |
| Pull request з гілки цього репозиторію | `preview`    | `Preview`         | https://preview.saasyland.com |
| Push у `main`                          | `production` | `Production`      | https://saasyland.com         |

Pull request із форків і від Dependabot перевіряються, але не розгортаються. Preview спільний: кожне розгортання замінює попереднє й використовує ту саму базу даних D1, простір імен KV і бакет R2 для preview.

`deploy-reusable.yml` перевіряє наявність секретів `CLOUDFLARE_API_TOKEN` і `CLOUDFLARE_ACCOUNT_ID`, запускає `scripts/verify-bindings.ts`, виконує збірку з фіктивними значеннями з `.env.test`, видаляє згенерований `dist/server/.dev.vars`, застосовує `db:migrate:<target>` і запускає `vp exec wrangler deploy --config dist/server/wrangler.json`. `scripts/verify-deployment.ts`, перевірка розгорнутого сайту зі скриптів `deploy:<target>`, тут не запускається, бо захист Cloudflare від ботів відповідає 403 на запити з раннерів CI. Файл секретів не завантажується: Worker зберігає секрети середовища виконання, уже задані в Cloudflare. Розгортання в ту саму ціль стають у чергу, а не скасовують одне одного.

Dependabot щотижня оновлює GitHub Actions.

## Релізи й теги [#releases-and-tags]

Сайт розгортається безперервно, тож його версії — це дати, а не семантичні версії. Коли розгортання production завершується успішно, завдання `release` у `ci.yml` позначає розгорнутий коміт тегом `vYYYY.MM.DD` з датою за UTC і публікує для нього GitHub Release. Друге розгортання production того самого дня отримує тег `vYYYY.MM.DD.2`, наступне — `.3` і так далі. Розгортання preview ніколи не отримують тегів. Завдання `release` — єдине з `contents: write`.

Нотатки до релізу — це розділ цього дня з [журналу змін](/docs/project/changelog), тож кожну зміну описано в одному місці; якщо в журналі змін немає розділу для цього дня, нотатки містять посилання на нього. `scripts/publish-release.ts` визначає тег і нотатки за допомогою `src/lib/release.ts` і запускає `gh release create`. Повторний запуск залишає тег, який коміт уже має, і пропускає реліз, що вже існує.

Щоб повернути production до релізу, скасуйте в pull request усе, що йде після його тегу:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Після злиття код із тегу розгортається після звичайних перевірок і позначається як новий реліз. Міграції D1 не скасовуються, тож старіший код працює з новішою схемою. Кожна зміна схеми має працювати із застосунком, розгорнутим перед нею, тому повернення до попереднього релізу безпечне; перш ніж повертатися далі, перегляньте міграції між ними.
