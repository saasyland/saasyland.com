title: "Modules"
description: "A module is one database table: its schema, constants, Zod schemas, types interface, use cases and the few concern files a table may need."
---

`src/modules/<table>/` exists only for a real database table. The folder mirrors the Drizzle schema, so creating one claims that a table exists. Code that serves a feature without a table of its own goes elsewhere: a server function that reads GitHub or the docs collection lives in `src/lib/<topic>.ts` or in the one route that uses it, and vendor setup lives in `src/integrations/<vendor>`.

The modules are `account`, `category`, `chapter`, `course`, `lesson`, `lesson-attachment`, `lesson-progress`, `license`, `newsletter-subscriber`, `order`, `product`, `rate-limit`, `session`, `subscription`, `two-factor`, `user`, `verification`, `video` and `withdrawal`. `license` owns two tables, `license` and `revoked_license_order`. `_core` is not a module: it holds the error codes, catalogues and Zod fields every module shares.

## Anatomy

`src/modules/course` is the reference. A module contains these files, all named after the table:

| File                         | Contains                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| `<table>.schema.ts`          | The Drizzle table, its indexes and relations                                         |
| `<table>.constants.ts`       | Domain value objects, their enum tuples, query keys, mutation keys and module limits |
| `<table>.zod.ts`             | One input schema per operation, exported as one `<table>ZodSchemas` object           |
| `<table>.types.ts`           | One interface named after the module                                                 |
| `<table>.utils.ts`           | Helpers for the table, pure and browser-safe unless they read the Worker environment |
| `<table>.<concern>.ts`       | One further concern of the table, such as `lesson.access.ts` or `video.delivery.ts`  |
| `use-cases/<verb>-<noun>.ts` | One operation, named after its server function                                       |
| `__test__/`                  | Tests and fixtures for the files above                                               |

## Schema

```ts
export const course = sqliteTable(
  "course",
  {
    icon: text("icon", { enum: COURSE_ICONS }).notNull().default(COURSE_ICON.BOOK_OPEN),
    id: text("id").primaryKey(),
    kind: text("kind", { enum: COURSE_KINDS }).notNull().default(COURSE_KIND.COURSE),
    level: text("level", { enum: COURSE_LEVELS }).notNull().default(COURSE_LEVEL.BEGINNER),
    outcomes: text("outcomes", { mode: "json" })
      .$type<LocalizedList>()
      .notNull()
      .default(sql`'{}'`),
    position: integer("position").notNull().default(0),
    prerequisites: text("prerequisites", { mode: "json" })
      .$type<LocalizedList>()
      .notNull()
      .default(sql`'{}'`),
    slug: text("slug", { length: SLUG_MAX_LENGTH }).notNull().unique(),
    status: text("status", { enum: COURSE_STATUSES }).notNull().default(COURSE_STATUS.DRAFT),
    summary: text("summary", { mode: "json" }).$type<LocalizedText>().notNull(),
    title: text("title", { mode: "json" }).$type<LocalizedText>().notNull(),
    ...timestamps(),
  },
  (table) => [index("course_status_position_idx").on(table.status, table.position)],
)
```

- Columns are camelCase in TypeScript and snake_case in SQL. Keys are sorted, as the linter requires, with `...timestamps()` as the last entry.
- `createdAt` and `updatedAt` come from `timestamps()` in `src/integrations/drizzle-orm/drizzle.columns.ts`: milliseconds, filled by SQLite on insert, with `updatedAt` refreshed on every update. Never write them by hand. `lesson_progress` needs only the second, so it takes `updatedAt: timestamps().updatedAt`. Two tables have no timestamps: `rate_limit` holds short-lived counters that carry their own `expiresAt` and change on every request, and `revoked_license_order` records each refunded Polar order once, by its ID.
- Primary keys are text. A use case that inserts a row fills the key with a UUID v7 (`v7()` from `uuid`); a [table that mirrors a provider](#tables-that-mirror-a-provider) takes the provider's ID instead.
- Enum columns take a tuple built from the module's constant object, never a list of literals. The tuple sits beside the object in `<table>.constants.ts`, because the Zod schemas and the browser read it too, and that file imports nothing from Drizzle.
- Text a visitor reads in several languages is a `LocalizedText` JSON column, validated by `localizedTextSchema` and read with `localize(text, locale)` from `src/modules/_core/utils/localized-text.ts`.
- A new table is re-exported from `src/integrations/drizzle-orm/drizzle.schemas.ts`, and its migration is generated with `bun run db:generate`. See [Database migrations](/docs/guides/database-migrations).

## Tables that mirror a provider

`order` and `subscription` hold copies of Polar's orders and subscriptions, written only from Polar's data and never edited by hand. A mirror table follows the provider where the rules above would not:

- Its primary key is the provider's ID, a text column of `POLAR_ID_MAX_LENGTH`, and its columns take the provider's field names, such as `customer_id`, `product_id` and `subscription_id`. A table of ours that points at the provider prefixes the name instead, as `license.polar_order_id` does.
- The provider's own times sit beside `...timestamps()`. `placedAt` is when Polar created the order, and `changedAt` is the version of Polar's record that the row holds: its `modified_at`, or its `created_at` while it has never changed. `createdAt` and `updatedAt` still record when D1 wrote the row.
- Enum columns take tuples of the provider's values: `ORDER_STATUSES` in `order.constants.ts` lists `POLAR_ORDER_STATUS` from `src/integrations/polar/polar.constants.ts`, and a type test fails when the SDK names a value that the tuple lacks.
- No column has a default apart from `createdAt` and `updatedAt`, because every value comes from the provider.
- `user_id` is `ON DELETE SET NULL`: deleting an account keeps its orders and subscriptions and only removes the link.

`order` is an SQL keyword. Drizzle quotes every identifier, so its queries need nothing; raw SQL names the table through the schema object, as `${order}` inside a `sql` template, never as a bare `order`.

## Constants

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const

export const COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const

export const COURSE_STALE_MS = 60_000

export const COURSE_SHOWCASE = {
  COURSES: 2,
} as const

export const COURSE_QUERY_KEYS = {
  ALL: ["course"],
  CATALOGUE: ["course", "catalogue"],
  DETAIL: ["course", "detail"],
  EDITOR: ["course", "getCourseEditor"],
  LIST: ["course", "getCourses"],
  SHOWCASE: ["course", "showcase"],
} as const

export const COURSE_MUTATION_KEYS = {
  CREATE: ["course", "createCourse"],
  DELETE: ["course", "deleteCourse"],
  MOVE: ["course", "moveCourse"],
  UPDATE: ["course", "updateCourse"],
} as const
```

- Every query key starts with the module's `ALL` prefix, so one `invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL })` refreshes everything the module serves. See [Data fetching and caching](/docs/conventions/data-fetching).
- Mutation keys are the module name and the server function name.
- Column and input lengths are named here and shared by the schema and the Zod schema, such as `PRODUCT_NAME_MAX_LENGTH` in `product.constants.ts`.
- `<MODULE>_VALIDATION_PARAMS` holds the numbers that validation messages interpolate, such as `{ slugTooLong: { max: SLUG_MAX_LENGTH } }`.
- `scripts/repository-facts.ts` reads some constants files, such as `license.constants.ts`, while Vite loads its configuration, when the `~` alias does not resolve yet. Such a file imports other source files by relative path, as `license.constants.ts` imports `POLAR_WEBHOOK_EVENT` from `../../integrations/polar/polar.constants.ts`; type-only imports are erased and may keep the alias.

## Zod schemas

```ts title="src/modules/chapter/chapter.zod.ts"
import zod from "zod/v4"

import { MOVE_DIRECTIONS } from "~/src/modules/_core/constants/ordering"
import { localizedTextSchema, optionalLocalizedTextSchema } from "~/src/modules/_core/utils/localized-text"
import { idField } from "~/src/modules/_core/utils/zod-fields"

const chapterIdInput = zod.object({
  chapterId: idField,
})

const chapterFields = zod.object({
  summary: optionalLocalizedTextSchema,
  title: localizedTextSchema,
})

const createChapter = chapterFields.extend({ courseId: idField })

const deleteChapter = chapterIdInput

const moveChapter = chapterIdInput.extend({ direction: zod.enum(MOVE_DIRECTIONS) })

const updateChapter = chapterFields.extend(chapterIdInput.shape)

export const chapterZodSchemas = {
  createChapter,
  deleteChapter,
  moveChapter,
  updateChapter,
}
```

- `<table>.zod.ts` imports `zod from "zod/v4"` and exports a single object whose keys are the operation names.
- Forms validate with the same schemas in the browser, so `<table>.zod.ts` imports nothing from Drizzle or from a `.schema.ts`. Enum tuples and lengths come from `<table>.constants.ts`, which the table imports too, so the column and the schema share one definition. The client build fails when `drizzle-orm` reaches the browser; see [Keep the ORM out of the browser](/docs/conventions/performance#keep-the-orm-out-of-the-browser).
- No Zod schema is derived from the table: nothing validates a whole row at runtime, and the row types in the module interface come from `$inferSelect` and `$inferInsert`.
- Fields come from `src/modules/_core/utils/zod-fields.ts` (`idField`, `localeField`, `slugField`) and from shared fragments in the same file, never re-declared per schema.
- Paginated lists reuse `paginationSchema`; single-record operations take an object such as `{ courseId }`, never a bare string.
- Error messages are translation keys (`{ message: "slugInvalid" }`), rendered from the module's `<table>.validations` namespace. See [Forms and tables](/docs/conventions/forms-and-tables).

## The module interface

`<table>.types.ts` exports exactly one interface, named after the module, whose keys mirror the Zod object:

```ts
export interface Lesson {
  select: typeof lesson.$inferSelect
  insert: typeof lesson.$inferInsert
  page: LessonPage
  detail: LessonPage["lesson"]
  attachment: LessonPage["lesson"]["attachments"][number]
  createLesson: zod.input<typeof lessonZodSchemas.createLesson>
  deleteLesson: zod.input<typeof lessonZodSchemas.deleteLesson>
  getLesson: zod.input<typeof lessonZodSchemas.getLesson>
  getLessonPlayback: zod.input<typeof lessonZodSchemas.getLessonPlayback>
  moveLesson: zod.input<typeof lessonZodSchemas.moveLesson>
  replaceLessonVideo: zod.input<typeof lessonZodSchemas.replaceLessonVideo>
  updateLesson: zod.input<typeof lessonZodSchemas.updateLesson>
}
```

Server functions, mutation options and forms type their input as `Lesson["createLesson"]`. When you add a schema to `<table>.zod.ts`, add its key here in the same change. Never derive an input type with `Parameters<typeof fn>[0]`, and never declare a local alias or a second `LessonInput` interface. When components need the shape a read returns, the interface names it too, derived from the server function: `Course["listRow"]` is `Awaited<ReturnType<typeof getCourses>>["rows"][number]`.

## Use cases

Each file in `use-cases/` holds one operation, named after its server function in kebab-case: `get-course-editor.ts` exports `getCourseEditor` and `courseEditorQuery`, `update-course.ts` exports `updateCourse` and `updateCourseMutation`. The pattern, its middleware and its errors are on [Server functions and errors](/docs/conventions/server-functions).

A use case that runs only on the server, called by a Better Auth hook or a Polar webhook rather than by the browser, is a plain `async` function in a file that starts with `import "@tanstack/react-start/server-only"`, such as `license/use-cases/grant-license.ts` and the email senders `send-verify-email.ts`, `send-reset-password-email.ts` and `send-change-email-confirmation-email.ts`.

## Concern files

When a table needs logic that is neither a use case nor a pure helper, it gets one file per concern, named `<table>.<concern>.ts`:

| File                                              | Concern                                                                    |
| ------------------------------------------------- | -------------------------------------------------------------------------- |
| `course/course.outline.ts`                        | A published course's outline for a viewer, for `getCourse` and `getLesson` |
| `lesson/lesson.access.ts`                         | Who may watch a lesson; pure, used on the server and in tests              |
| `lesson/lesson.playable.ts`                       | The join to a lesson's video that leaves placeholders out                  |
| `lesson-attachment/lesson-attachment.download.ts` | Signing download URLs of lesson materials                                  |
| `lesson-attachment/lesson-attachment.delivery.ts` | The Worker handler for signed `/media/downloads/` requests                 |
| `lesson/lesson.viewer.ts`                         | Resolves the signed-in viewer and their course access on the server        |
| `license/license.webhooks.ts`                     | Polar webhook handlers, called by `license.polar-events.ts`                |
| `license/license.api.ts`                          | The CLI licence API handlers, served by `src/routes/api/cli.v1.*.ts`       |
| `license/license.bundles.ts`                      | Signing the URLs of the CLI's template bundles; their object keys          |
| `license/license.delivery.ts`                     | The Worker handler for signed `/bundles/` requests                         |
| `license/license.ppp.ts`                          | The buyer's price for a tier at checkout, regional price included          |
| `license/license.pricing.ts`                      | Regional price bands and the opt-out cookie; pure                          |
| `license/license.upgrade-price.ts`                | The price of an upgrade, from the customer's licence orders in Polar       |
| `license/license.refunds.ts`                      | Whether a purchase can be refunded, from its records; pure                 |
| `withdrawal/withdrawal.contracts.ts`              | The active licence a withdrawal statement names, and its refund terms      |
| `video/video.delivery.ts`                         | The Worker handler for signed `/media/` requests                           |
| `video/video.playback.ts`, `video/video.files.ts` | Signing playback URLs; object keys and content types                       |

A file that must never reach the browser bundle starts with `import "@tanstack/react-start/server-only"`, as `course.outline.ts`, `lesson.viewer.ts`, `lesson-attachment.delivery.ts`, `lesson-attachment.objects.ts`, `license.webhooks.ts`, `license.api.ts`, `license.delivery.ts`, `video.delivery.ts` and `license.utils.ts` (which reads the Polar product IDs, `POLAR_PRODUCT_IDS`, from the Worker environment) do. Pure files such as `lesson.access.ts` and `course.utils.ts` import nothing server-side, so components and tests can use them.
