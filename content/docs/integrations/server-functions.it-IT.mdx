Le operazioni di business si trovano in `src/modules/<table>/use-cases/<operation>.ts`, un'operazione per file. Ogni file esporta una `createServerFn` nativa con il suo middleware, la validazione Zod e l'handler, oltre alle query o mutation options usate dai componenti. Una funzione server che non appartiene a nessuna tabella va in `src/lib` (ad esempio `getStarCount` in `src/lib/github.ts`), mentre una usata da una sola route può essere definita nel file di quella route (`getBlogPosts` in `src/routes/blog.index.tsx`).

```ts
export const createCategory = createServerFn({ method: "POST" })
  .middleware([authorized({ category: ["create"] })])
  .validator((input: zod.input<typeof categoryZodSchemas.createCategory>) => categoryZodSchemas.createCategory.parse(input))
  .handler(({ data }) =>
    db
      .insert(category)
      .values({
        description: data.description ?? "",
        icon: data.icon ?? "FolderOpen",
        id: v7(),
        kind: data.kind,
        name: data.name,
        visibility: data.visibility ?? "public",
      })
      .returning()
      .get(),
  )

export const createCategoryMutation = mutationOptions({
  mutationFn: (data: Parameters<typeof createCategory>[0]["data"]) => createCategory({ data }),
  mutationKey: CATEGORY_MUTATION_KEYS.CREATE,
})
```

## Regole

- Il middleware viene eseguito prima della validazione e dell'handler. Usa `authorized(permission?)` per le operazioni protette e `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` o `RATE_LIMITS.TOKEN` per quelle pubbliche sensibili; vedi [Better Auth](/docs/integrations/better-auth).
- Valida l'input con lo schema Zod del modulo (`<table>.zod.ts`).
- Restituisci direttamente i dati e lancia `AppError(ERROR_CODES.X)` da `src/modules/_core/constants/errors.ts` per gli errori previsti. Gli altri errori arrivano al client come `INTERNAL_ERROR`, così i dettagli del provider restano sul server.
- Le chiavi delle query e delle mutation sono tuple readonly nel file `<table>.constants.ts` del modulo, e le chiavi delle query includono ogni input che modifica il risultato.
- Mantieni le operazioni atomiche con una singola istruzione SQL o con `db.batch`; D1 non supporta transazioni interattive.

## Usare un caso d'uso

I componenti espandono le options esportate in `useQuery`, `useSuspenseQuery` o `useMutation`, traducono gli errori con `useErrorMessage()` da `src/hooks/use-error-message.ts` e invalidano le chiavi delle query del modulo dopo una mutation riuscita:

```tsx
const deleteUser = useMutation({
  ...deleteUserMutation,
  onError: (error) => {
    toast.error(errorMessage(error))
  },
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: USER_QUERY_KEYS.ALL })
    toast.success(t("feedback.deleteSuccess"))
  },
})
```

I loader precaricano le stesse query options nel loro `Promise.all`, così il rendering lato server e il client condividono un'unica voce di cache.
