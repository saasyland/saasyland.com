description: "La única forma de una ruta de página y de una ruta de layout: NAMESPACE o NAMESPACES, un loader con un solo Promise.all, un esqueleto que reproduce la página, esquemas de búsqueda y enlaces."

Todos los archivos de `src/routes` tienen la misma forma, así que quien conoce uno los conoce todos. Un archivo de ruta compone: declara lo que necesita la página y coloca componentes. Los widgets, formularios, diálogos y columnas de tabla viven en `src/presentation/components/custom`.

## Rutas de página

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const columns = useCourseColumns()

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        rowActionsSize={COURSE_COLUMN_SIZES.actions}
        search={t("table.search")}
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **El componente** es una `const` local llamada `<Name>Page`, definida en primer lugar. El marcado pequeño que solo usa esta página puede ir encima como componentes locales, como hacen `CourseProgress` y `StartLink` en `_site._marketing.courses.$course.index.tsx`; cualquier cosa con sus propios datos, mutación o estado va a un archivo de componente.
- **Un espacio de nombres.** `const NAMESPACE = "pages.<area>.<page>"` va justo encima de `export const Route` y se usa en `loadPageMetadata`, `preloadNamespaces` y `staticData`. Todo lo demás que necesite la página lo declara su layout.
- **Un solo `Promise.all`.** El loader inicia todo el trabajo a la vez: los metadatos de la página, el espacio de nombres y cada consulta que leen los componentes. Devuelve `{ locale, metadata }` para `head`. Nunca esperes a que termine una de estas tareas antes de iniciar la siguiente.
- **`head: pageHead(ROUTES.X)`** construye el título, la descripción, la URL canónica y las URL alternativas a partir de los metadatos del archivo del espacio de nombres.
- **Las rutas de URL salen de `ROUTES`**, en `src/routes.ts`, que reúne las rutas de todas las áreas (consulta [Rutas y navegación](#paths-and-navigation)); nunca escribas una ruta como literal.

Una página cuyo título sale de un registro espera ese registro y construye su head a partir de los datos del loader, como hace `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Rutas de layout

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Un layout declara `const NAMESPACES = [...] as const` encima de `export const Route` y lo precarga. Cuando no tiene ninguno, omite la opción; no existe `namespaces: []`.
- Un namespace que necesita en el layout un componente de otra área lo añade esa área en `src/areas/<area>.ts`, que nombra el layout por su id de ruta, y el layout expande `...layoutNamespaces("/app")` en sus `NAMESPACES`. El área de licencias añade `pages.license`, `pages.withdrawal` y `withdrawal.validations` a `/app`, cuyo resumen muestra la tarjeta de licencia y la oferta y cuya página de licencia muestra la tarjeta de desistimiento, `withdrawal.validations` a `/_site/_marketing` y `pages.admin.users.license` a `/admin/users`; el área de pagos añade `pages.admin.customers` y `pages.admin.orders` a `/admin/users`; y el área del boletín añade `auth.validations` a `/_site/_marketing` y `/_site/docs`, cuyos pies muestran el formulario del boletín. `browser.test.tsx` comprueba al compilar que cada layout que nombra un área es un id de ruta.
- El componente, cuando el layout renderiza uno, se llama `<Name>Layout` y coloca un `<Outlet />`.
- Una guarda va en el `beforeLoad` del layout que es dueño del área: `beforeLoad: requireAdmin` en `admin.tsx`, `requireSignedIn` en `app.tsx`, ambos layouts del área de autenticación. Las guardas solo deciden la navegación; cada función de servidor sigue comprobando su propio permiso.

## Orden de las opciones

`sort-keys` está desactivada en `src/routes` porque TanStack Router infiere los tipos en el orden de declaración. Las opciones van en orden alfabético, salvo `validateSearch`, que va primero, antes de todo lo que lee los parámetros de búsqueda:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Nunca escribas en línea un array o un objeto de datos dentro de `createFileRoute`; decláralo encima como una constante.

## Parámetros de búsqueda

`validateSearch` es un `zod.object` construido con los helpers de `src/lib/search-params.ts`:

| Helper                            | Valor cuando el parámetro falta o está mal formado | Uso                                            |
| --------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| `searchText()`                    | `undefined`                                        | Tokens, correos electrónicos, códigos de error |
| `searchFlag()`                    | `undefined`                                        | Booleanos                                      |
| `searchParam(schema)`             | `undefined`                                        | Cualquier otro esquema, como una ruta          |
| `searchChoice(choices, fallback)` | `fallback`                                         | Una pestaña o una vista                        |

Un texto ausente se queda en `undefined`, así que un valor por defecto nunca se cuela en una URL que construye el router. Un parámetro `searchChoice` va acompañado de `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, que elimina el valor por defecto de la URL. Una página a la que otro sitio devuelve a los visitantes declara además `search: { middlewares: [onlyDeclaredSearch(schema)] }` con su propio esquema, como hacen `/app` y `/app/license` para el pago de Polar: el router construye entonces su dirección solo con los parámetros declarados, y el servidor redirige una dirección que lleva cualquier otro parámetro a la misma dirección sin él, antes de que una comprobación o la página lo lean. Nunca escribas a mano comprobaciones `typeof search["x"] === "string"`; añade un helper cuando haga falta un nuevo tipo de campo. Cuando un hijo necesita un parámetro que la página ha validado como presente, la página estrecha su tipo y se lo pasa, como `auth.reset-password.tsx` pasa `token` a `ResetPasswordForm`. Las páginas que leen los mismos parámetros comparten un esquema en `src/data`, que también parsean sus esqueletos, como hacen `/app/license` y la parte del resumen que aporta el área de licencias con `licenseSearchSchema` (`src/data/license.ts`).

## Esqueletos

La navegación debe sentirse instantánea, así que cada ruta que renderiza una página tiene un `pendingComponent` que la reproduce: la misma disposición, las mismas tarjetas y el mismo número de filas.

- Los esqueletos viven en el archivo pending del área (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) y usan `Skeleton` de shadcn.
- Los esqueletos están en el script de entrada de cada página, así que un esqueleto importa `Skeleton`, las primitivas de shadcn, otros esqueletos y las constantes que fijan sus longitudes, nunca un formulario ni el archivo que lo contiene; `pending-imports.test.ts` falla cuando alguno llega a `@tanstack/react-form` (consulta [Rendimiento](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Un marcador de texto lleva el token tipográfico real más `h-lh scale-y-70`, para que tenga la altura de la línea que sustituye: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- La longitud de las listas sale de las constantes que usa la página: `DataGridPending` en `data-grid-pending.tsx` dibuja por defecto `DEFAULT_PAGE_SIZE` filas, el tamaño de página de todas las tablas de administración.
- El esqueleto de un layout renderiza el `pendingComponent` de la primera ruta coincidente por debajo del layout que define uno, que `usePagePending(layout)` de `src/hooks/use-page-pending.ts` lee del árbol de rutas: `AdminPending`, `AppPending`, `AuthPending` y `MarketingPending` en sus layouts, y `AdminUsersPending` y `AdminCourseSectionPending` un nivel más abajo. Por eso, la ruta de una página es el único lugar que nombra su esqueleto, sea cual sea el layout que lo muestre; `/admin/users`, que redirige a `/admin/users/all`, fija el esqueleto de esa página.
- No hay un `defaultPendingComponent` para todo el router. `src/router.tsx` fija `defaultPendingMs` en <RepositoryFact name="navigationPendingMs" unit="millisecond" /> y `defaultPendingMinMs` en <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, ambos de `src/data/navigation.constants.ts`: una navegación que no ha terminado pasado el primero muestra el esqueleto de la ruta, y el esqueleto desaparece en cuanto la página está lista, sin quedarse ni un momento más. Las rutas mantienen estos valores; consulta [Rendimiento](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) para ver las mediciones que los respaldan.
- Las páginas de la documentación dibujan sus esqueletos dentro del layout de la documentación: `DocsIndexPending` y `DocsPagePending` ocupan las áreas de la cuadrícula del artículo y de la tabla de contenidos de Fumadocs, así que una navegación entre páginas de la documentación mantiene la barra lateral en pantalla. El componente de la página renderiza el MDX en su propio `<Suspense key={path}>`, así que la barra lateral funciona antes de que cargue el chunk MDX de la página, y una navegación reemplaza el HTML del servidor de la página anterior en lugar de hidratarlo con los datos de la siguiente.

## Enlaces

- Los enlaces del router reciben una constante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, o un patrón de ruta con `params` para las rutas dinámicas. `LinkButton` y `SidebarMenuLink` de shadcn reciben `to` de la misma manera, y `AnchorButton` recibe un `href` para una dirección fuera del árbol de rutas.
- Nunca añadas el prefijo de idioma a un enlace del router; lo añade la reescritura del router. Una URL completa en el idioma actual, para un valor que sale del router como cadena, se obtiene de `router.buildLocation({ ... }).publicHref`, que es como `use-auth-redirect.ts` construye sus enlaces de inicio de sesión. `localizePathname` es para las URL que se construyen fuera de un contexto de router o para otro idioma: correos, destinos de redirección de Better Auth, enlaces dentro de MDX y el selector de idioma.

## Rutas y navegación [#paths-and-navigation]

Ningún archivo de la aplicación enumera todas las áreas. Cada área, como los cursos, los productos o las páginas legales, declara sus propias rutas, sus entradas de menú con sus etiquetas, sus esqueletos de página y sus permisos, y un barrel los reúne, así que un área se añade o se deja fuera con sus propios archivos. Así es como la CLI `saasyland` monta un proyecto a partir de capas de plantillas. Solo `scripts/areas.ts`, que la aplicación nunca carga, enumera las áreas opcionales con sus archivos, para que `bun run check:areas` pueda comprobar los tipos del sitio sin cada una de ellas ([Pruebas](/docs/conventions/testing#tests-follow-the-areas)).

| Qué                              | Cada área declara                                                            | Barrel                            | Se lee de                                                                                                                                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Rutas                            | `src/areas/<area>.shared.ts`: un `export const` por ruta                     | `src/routes.ts`                   | `import * as ROUTES from "~/src/routes"`                                                                                                                                                   |
| Entradas de menú                 | `src/areas/<area>.navigation.ts`: `entries` en un objeto `<AREA>_NAVIGATION` | `src/areas/navigation.entries.ts` | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` y `FOOTER_NAVIGATION` en `src/data/navigation.ts` |
| Estadísticas y paneles del panel | `src/areas/<area>.ts`: `dashboard` en un objeto `<AREA>_BROWSER`             | `src/areas/browser.entries.ts`    | `ADMIN_DASHBOARD_STATS` y `ADMIN_DASHBOARD_PANELS` en `src/data/dashboard.ts`                                                                                                              |
| Permisos                         | `src/areas/<area>.access.ts`: un objeto `<AREA>_ACCESS`                      | `src/areas/access.entries.ts`     | `APP_STATEMENTS` y `grantsOf` en `src/integrations/better-auth/auth.access.ts`                                                                                                             |
| Rutas no listadas                | `src/areas/<area>.shared.ts`: `unlisted` en un objeto `<AREA>_SHARED`        | `src/areas/shared.entries.ts`     | `UNLISTED_ROUTES` y `isUnlistedRoute` en `src/areas/shared.ts`                                                                                                                             |
| Namespaces de layout             | `src/areas/<area>.ts`: `layoutNamespaces` en un objeto `<AREA>_BROWSER`      | `src/areas/browser.entries.ts`    | `layoutNamespaces(layout)` en `src/areas/browser.ts`                                                                                                                                       |

Un barrel solo contiene líneas `export { … } from`, una por archivo de área y ordenadas por módulo, como `src/integrations/drizzle-orm/drizzle.schemas.ts`. Un barrel que solo llenan áreas opcionales recibe además un archivo de la base, como `src/areas/core.ts`, que solo contiene el nombre de la base, de modo que un proyecto sin esas áreas sigue pasando la comprobación de tipos y el lint. El barrel de las rutas es el propio `src/routes.ts`, y cada archivo lo importa como un único espacio de nombres, `import * as ROUTES from "~/src/routes"`, así que cada ruta conserva su tipo literal y `<Link to={ROUTES.COURSES}>` se sigue comprobando contra el árbol de rutas:

```ts title="src/routes.ts"
export { API, HOME } from "./areas/core.shared.ts"
export { ADMIN_COURSES, ADMIN_COURSES_CREATE, COURSES } from "./areas/courses.shared.ts"
```

Una entrada de menú indica dónde aparece con `placement` (`NAVIGATION_PLACEMENT` en `src/data/navigation.constants.ts`): la barra lateral de administración, los botones sobre el panel, las acciones rápidas de la paleta de comandos, la barra lateral de la app de clientes y sus recursos, la cabecera pública o el pie. Su `order` la ordena entre las entradas de las demás áreas, de modo que ninguna lista depende del orden de los archivos. Las entradas de administración indican además su grupo de la barra lateral (`group`), y los enlaces del pie su columna (`column`); `ADMIN_NAVIGATION_GROUPS` y `FOOTER_COLUMNS` fijan el orden de grupos y columnas, y el que ninguna área rellena se omite. La consola de administración y el espacio de trabajo de clientes solo existen con inicio de sesión, así que son del área de autenticación: sus rutas, `/admin`, `/admin/settings`, `/app` y `/app/settings`, sus entradas de panel, resumen, ajustes y gestión de usuarios, e **Iniciar sesión** en la cabecera y en el pie:

Una entrada de la cabecera o del pie de página puede nombrar una etiqueta `signedIn` que sustituye la suya para un visitante con sesión iniciada, y su enlace lleva entonces a su espacio de trabajo: `/admin` para una cuenta con acceso de administración, `/app` para todas las demás. `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`) lo decide a partir del rol de la sesión con `hasPermission` y el permiso `admin: ["access"]` que comprueba `requireAdmin`. Las páginas públicas están prerenderizadas, así que su HTML muestra **Iniciar sesión**; tras la hidratación, un navegador que tiene la cookie de Better Auth con el último método de inicio de sesión pide su sesión, y la cabecera, su menú móvil y el pie de página muestran **Tu cuenta** en su lugar, ya con el enlace al espacio de trabajo correcto. Un navegador que nunca ha iniciado sesión no pide nada. Hasta que una parte de la página se ha hidratado, `useVisitorWorkspace` no devuelve nada, aunque el navegador ya tenga la sesión, porque `useHydrated` responde con el valor del servidor mientras React hidrata: un pie de página que se hidrata después de que llegue la sesión muestra el mismo **Iniciar sesión** que el HTML y cambia después, en lugar de romper la hidratación.

Cada entrada del panel de administración abre una pantalla que funciona con datos reales, y la página de inicio las cuenta todas. Una pantalla cuyos datos aún no tienen origen no recibe ninguna entrada (consulta [Panel de administración](/docs/features/admin-dashboard#real-data-only)).

El área de licencias añade su entrada **Licencia** a la barra lateral de la app de clientes, y el área de contenido añade **Documentación** a sus recursos, encima de la dirección de soporte. El área base solo declara `/` y `/api`, y **Precios** en la cabecera, la única entrada con `hash`, que enlaza con la sección de precios de `/`.

Una estadística del panel tiene un `prefetch`, que ejecuta el loader de `/admin`, y un hook `useValue`, al que `DashboardStats` llama para leer el número.

El archivo de acceso de un área define las declaraciones de permisos de sus recursos y los roles a los que las concede. `auth.access.ts` construye el control de acceso de Better Auth a partir de `APP_STATEMENTS` y cada rol a partir de `grantsOf(role)`, así que la integración de autenticación no nombra ningún área, y `APP_STATEMENTS` falla cuando dos áreas declaran el mismo recurso (consulta [Roles y permisos](/docs/guides/roles-and-permissions)).

Las listas de `src/data/navigation.ts` tienen un tipo declarado, `NavigationEntry`, en lugar de los tipos de las entradas que declaren las áreas en cada momento, así que una ubicación que ningún área llena, como las acciones del panel en un proyecto sin el área de pagos, es una lista vacía que sigue pasando la comprobación de tipos. `navigation.test.ts` comprueba al compilar que el `to` de cada entrada que declara un área es una ruta del árbol de rutas (`FileRouteTypes["to"]` de `src/routeTree.gen.ts`).

Una entrada recibe su `area` del `name` del objeto `<AREA>_NAVIGATION` de su área, y el área la etiqueta en su propio archivo de mensajes: `<placement>.<key>` en `messages/<locale>/navigation.<area>.json`, como `admin.courses` y `header.courses` en `navigation.courses.json`. Una estadística del panel se etiqueta por su `key` en `dashboard.<area>.json`, y una sección de administración etiqueta sus subpáginas para las migas de pan bajo `breadcrumbs.<segment>` en su `navigation.<area>.json`, como `breadcrumbs.create`; una pestaña de la gestión de usuarios se etiqueta bajo `userTabs.<key>`, que nombra la pestaña y su página en las migas de pan, y un panel del dashboard guarda sus textos bajo su `key` en `dashboard.<area>.json`. Los dos tipos de archivo son espacios de nombres raíz, así que cualquier menú puede etiquetar cualquier entrada, y `useNavigationLabel` en `src/hooks/use-navigation-label.ts` devuelve la etiqueta de una entrada. Lo que pertenece al propio menú se queda en su espacio de nombres: `groups.<group>` en `pages.admin.sidebar`, `columns.<column>` en `components.custom.footer` y la llamada a la acción, el botón del menú y el enlace de salto de la cabecera en `components.custom.navigation`. `enum-labels.test.ts` falla cuando a una entrada o a una estadística le falta la etiqueta en algún locale.

Un área cuyas páginas se renderizan en el Worker en cada solicitud, como `/admin`, `/auth` o `/courses`, enumera esas rutas en el campo `unlisted` de su objeto `<AREA>_SHARED`, en `src/areas/<area>.shared.ts`. El plugin de TanStack Start en `src/data/tanstack.vite.ts` las excluye del prerenderizado con `isUnlistedRoute`, y `buildPageHead` les asigna la tarjeta del sitio en lugar de una tarjeta de página (consulta [Búsqueda y vistas previas en redes sociales](/docs/features/seo)). Vite no resuelve el alias `~` mientras carga su propia configuración, así que cada archivo de `src/areas` que carga, `shared.ts`, `shared.entries.ts` y cada `<area>.shared.ts`, importa por ruta relativa. La entrada del Worker, `vite.config.ts` y el proyecto de Remotion llegan a cada archivo compartido a través de `ROUTES`, así que un archivo compartido contiene rutas y nada que arrastre una dependencia. Las comprobaciones del sitio publicado son un tipo de archivo propio, `src/areas/<area>.live.ts`, porque solo las cargan la verificación tras el despliegue y la documentación. Las entradas de menú también son un tipo de archivo propio y puro, `src/areas/<area>.navigation.ts`, que `src/areas/navigation.entries.ts` reúne y `src/data/navigation.ts` lee, porque el proyecto de Remotion lee el menú de administración y su job de CI solo instala los paquetes propios de Remotion, así que no puede cargar el archivo de navegador de un área, `src/areas/<area>.ts`, que importa código del router, de TanStack Query y de funciones de servidor.
