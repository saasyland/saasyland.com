---
title: "Rollen und Berechtigungen"
description: "Die Berechtigungs-Statements und Rollenzuweisungen eines Bereichs in seiner Access-Datei deklarieren und in Route-Guards und Server-Funktionen prüfen."
---

Die Zugriffskontrolle nutzt das Admin-Plugin von Better Auth. Jeder Bereich deklariert die Berechtigungs-Statements seiner Ressourcen und die Rollen, denen er sie gewährt, in `src/data/<area>.access.ts`. `src/data/access.entries.ts` führt die Bereiche zusammen, und `src/integrations/better-auth/auth.access.ts` baut daraus die Zugriffskontrolle von Better Auth, die Rollen und die Berechtigungsprüfung auf, sodass die Auth-Integration keinen Bereich nennt. Die Rollencodes liegen in `src/integrations/better-auth/auth.roles.ts`.

## Statements und Rollen

```ts title="src/data/products.access.ts"
const STATEMENTS = {
  category: ["create", "read", "update", "delete"],
  product: ["create", "read", "update", "delete", "publish"],
} as const

export const PRODUCTS_ACCESS = {
  grants: { [ROLE_CODES.ADMIN]: STATEMENTS },
  statements: STATEMENTS,
} as const satisfies AreaAccess
```

```ts title="src/integrations/better-auth/auth.access.ts"
export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...grantsOf(ROLE_CODES.ADMIN), ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole(grantsOf(ROLE_CODES.CUSTOMER)),
}
```

- `APP_STATEMENTS` in `src/data/access.ts` führt die Statements aller Bereiche nach Ressource sortiert zusammen und schlägt beim Start fehl, wenn zwei Bereiche dieselbe Ressource deklarieren. `grantsOf(role)` führt zusammen, was jeder Bereich dieser Rolle gewährt.
- Der Kernbereich deklariert `admin` und `settings`, der Produktbereich `category` und `product`, der Kursbereich `course` und `video` und der Zahlungsbereich `order`.
- `defaultStatements` von Better Auth fügen die Ressourcen `user` und `session` hinzu (etwa `user: ["list", "set-role", "ban", "impersonate", "delete"]` und `session: ["list", "revoke"]`).
- Jeder Bereich gewährt alle seine Statements der Rolle `admin`, die außerdem die Admin-Statements von Better Auth erhält; der Rolle `customer`, der Standardrolle für neue Benutzer, wird keines gewährt.
- `ROLE_VALUES` typisiert die Spalte `user.role` und die Rollenschemas in `user.zod.ts`.
- `Permission`, der Typ, den `authorized` und `hasPermission` annehmen, wird aus den Statements gebildet, die die Bereiche deklarieren, sodass ein Statement oder eine Aktion, die kein Bereich deklariert, nicht kompiliert.

## Wo Berechtigungen geprüft werden

| Schicht         | Prüfung                                                                       |
| --------------- | ----------------------------------------------------------------------------- |
| Route-Guard     | `requireAdmin` verlangt `admin: ["access"]` für den gesamten `/admin`-Bereich |
| Server-Funktion | `authorized({ product: ["update"] })` auf jeder geschützten Operation         |
| Nur angemeldet  | `authorized()` für Operationen auf den eigenen Daten des Aufrufers            |
| Überall sonst   | `hasPermission({ permission, role })` gibt einen booleschen Wert zurück       |

Der Route-Guard entscheidet nur, welche Seiten gerendert werden. Server-Funktionen sind direkt per RPC aufrufbar, daher muss jede ihre eigene Berechtigung prüfen. Einen Button auszublenden ist Darstellung, keine Autorisierung.

## Berechtigung hinzufügen

1. Die Aktion zu den Statements des Bereichs hinzufügen, dem die Ressource gehört, zum Beispiel `report: ["read", "export"]` in `src/data/analytics.access.ts`. Ein neuer Bereich ergänzt seine Datei und eine Zeile in `src/data/access.entries.ts`.
2. Sie in den `grants` derselben Datei gewähren: Die Bereiche gewähren `ROLE_CODES.ADMIN` ihre gesamten `STATEMENTS`, und einer Rolle, die weniger erhalten soll, wird eine Teilmenge gewährt.
3. In der Server-Funktion verlangen: `.middleware([authorized({ report: ["export"] })])`.
4. Sowohl den erlaubten als auch den `FORBIDDEN`-Fall testen, in `src/data/__test__/<area>.access.test.ts` des Bereichs und in den Tests des Use Cases.

## Rolle hinzufügen

1. Den Code zu `ROLE_CODES` und `ROLE_VALUES` in `auth.roles.ts` hinzufügen.
2. Die Rolle zu `ROLES` in `auth.access.ts` hinzufügen und ihr in den `grants` der Bereiche, die sie nutzen darf, Statements gewähren.
3. Die Rollenbeschriftung zu `filters.role.options` in `messages/<locale>/pages.admin.users.json` für jede Locale hinzufügen.

Der Auth-Client (`auth.client.ts`) erhält `ac` und `ROLES`, sodass Admin-Aktionen im Browser dieselben Definitionen verwenden.

## Benutzer- und Session-Verwaltung

Die Module für Benutzer und Sessions kapseln die Admin-API von Better Auth in Use Cases, jeder mit eigener Berechtigung: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` und weitere. Operationen auf den eigenen Daten des Aufrufers, etwa `revokeSession`, verwenden `authorized()` und filtern nach `context.auth.user.id`.

Außerhalb der Testdatenbank gibt es keinen Admin-Seed. Um den ersten Admin anzulegen: registrieren, die E-Mail-Adresse verifizieren und die `role` dieses Benutzers in D1 auf `admin` setzen, zum Beispiel mit `bun run db:studio:development`.
