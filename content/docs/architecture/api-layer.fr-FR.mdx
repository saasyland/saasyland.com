---
title: "Handlers HTTP de TanStack Start"
description: "Les endpoints HTTP sous /api, et quand en ajouter un plutôt qu'une fonction serveur."
---

Les opérations propres à l'application sont des fonctions serveur. Les handlers HTTP n'existent que là où un élément extérieur au client RPC de l'application appelle une URL : le client navigateur de Better Auth, les fournisseurs OAuth, les webhooks Polar et le champ de recherche de la documentation.

| Fichier                    | Chemin        | Méthodes  | Traite                                                                                                                                         |
| -------------------------- | ------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/routes/api/index.ts`  | `/api`        | GET       | Une réponse d'état JSON `{ runtime: "cloudflare-workers" }`                                                                                    |
| `src/routes/api/auth.$.ts` | `/api/auth/*` | GET, POST | Tous les endpoints Better Auth, y compris les callbacks OAuth, la vérification d'e-mail, le portail client Polar et `/api/auth/polar/webhooks` |
| `src/routes/api/search.ts` | `/api/search` | GET       | La recherche Fumadocs dans la documentation                                                                                                    |

Un handler se déclare avec `server.handlers` dans `createFileRoute`. Il reçoit la `Request` Web et renvoie une `Response` :

```ts
import { createFileRoute } from "@tanstack/react-router"

import { auth } from "~/src/integrations/better-auth/auth.server"

export const Route = createFileRoute("/api/auth/$")({
  server: { handlers: { GET: ({ request }) => auth.handler(request), POST: ({ request }) => auth.handler(request) } },
})
```

## Règles

- N'ajoutez pas d'endpoint REST pour une opération que seule cette application appelle. Écrivez plutôt un cas d'usage avec `createServerFn` : il bénéficie d'une entrée typée, des middlewares et des options de query.
- Un handler valide lui-même son entrée et vérifie lui-même les permissions. Les middlewares des fonctions serveur (`authorized`, `withRateLimit`) ne s'exécutent pas pour les handlers.
- Laissez la vérification propre à un fournisseur dans son intégration. Les signatures des webhooks Polar sont vérifiées par le plugin Polar dans Better Auth, et non par un handler personnalisé.
- Les chemins `/api` ne sont jamais localisés ni prérendus, et le Worker ne leur applique pas sa gestion des locales.
