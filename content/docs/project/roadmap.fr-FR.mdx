## En cours

- La facturation avec Polar dans la CLI, la première des options ci-dessous. La facturation générique de l’application, sur laquelle elle s’appuie, est en ligne : le paiement de n’importe quel produit Polar, le catalogue Polar dans `/admin/products`, la page de facturation avec les commandes, les abonnements et les factures du compte et le portail client de Polar, et la licence construite dessus. Les modèles de la CLI sont d’abord mis à jour avec l’application ; ils reçoivent ensuite le paiement, les webhooks, les copies des commandes et des abonnements, le portail client, et les commandes et les clients dans la console d’administration générée.

## CLI : chaque option du configurateur

Le [configurateur](/#cli) affiche chaque option et chaque extra du paquet de stack de la CLI, et la CLI les générera tous. Deux autres sont prévus et rejoindront le configurateur avec une version de ce paquet : MongoDB, via Prisma, et l’extra Temps réel. Une option n’est activée dans le configurateur, et acceptée par `init`, que lorsqu’un projet généré avec elle s’installe, passe la vérification des types, réussit ses tests à <RepositoryFact name="coverageThreshold" /> % de couverture, se construit et démarre, en CI, à chaque modification susceptible de l’atteindre. D’ici là, le configurateur l’affiche désactivée et `init` la refuse avec le code de sortie <RepositoryFact name="cliExitNotAvailable" />, avant toute vérification de licence.

Certaines réponses dépendent d’autres. La question de l’API ne concerne que les architectures API séparée et microservices, et certains environnements d’exécution et fournisseurs ne tournent pas sur toutes les cibles de déploiement, comme l’environnement d’exécution Bun sur Cloudflare Workers. Le configurateur désactive toute combinaison que la cible ne peut pas exécuter.

Les options arrivent dans cet ordre :

1. La facturation avec Polar, avec les commandes et les clients dans la console d’administration générée (En cours).
2. L’extra Cours par abonnement, avec les cours dans la console d’administration générée. Il a besoin de la facturation.
3. La facturation avec Stripe, et l’e-mail avec Plunk.
4. Prisma, d’abord sur Cloudflare D1, puis sur chaque base de données à mesure qu’elle arrive ; ensuite MongoDB via Prisma, que Drizzle ne peut pas utiliser.
5. Votre propre serveur avec Docker : une image de production qui tourne avec un utilisateur non root, dispose d’un contrôle de santé et ne garde aucun secret dans ses couches, une configuration Compose avec la base de données et un proxy TLS, l’image construite et analysée en CI, et des guides pour les mises à niveau et les sauvegardes.
6. L’architecture API séparée : un monorepo avec l’application web, une API Hono et un contrat partagé, à partir duquel oRPC sert des appels typés à l’application web et une API REST avec sa description OpenAPI.
7. Le temps réel, en extra : le streaming du serveur vers le navigateur sur chaque environnement d’exécution, les WebSockets bidirectionnels, avec les Durable Objects sur Cloudflare Workers et les utilitaires WebSocket de Hono sur Node et Bun, et une démo en direct des deux dans la console d’administration générée.
8. Se passer de l’e-mail, et se passer du contenu. Sans e-mail, la connexion a besoin d’un parcours qui n’envoie aucun message ; sans contenu, les conventions de code vers lesquelles renvoient les instructions pour agents d’un projet généré doivent se trouver en dehors de la documentation.
9. Postgres avec Neon, Supabase ou votre propre serveur ; Turso ; un fichier SQLite local.
10. Le déploiement sur Vercel ; les environnements d’exécution Bun et Deno.
11. Une API Elysia, puis les microservices.
12. Next.js et React Router sur React.
13. Solid avec SolidStart et TanStack Start, Vue avec Nuxt, Svelte avec SvelteKit, et Angular avec Analog et Angular SSR.
14. L’option Multitenant, une fois que les organisations et les rôles seront dans l’application.
15. La boutique avec des produits d’exemple, le constructeur de pages visuel et l’éditeur visuel de publication, chacun après que l’application aura livré la fonctionnalité qu’il génère.

### Commandes et versions

- Des questions interactives dans un terminal. Aujourd’hui, une session de terminal répond par la valeur par défaut à chaque question que vous n’avez pas passée en flag, comme le fait `--yes`.
- `status`, qui affiche la version, les réponses et la licence d’un projet.
- `change`, qui relance la CLI sur un projet existant avec d’autres réponses : les modules d’abord, les changements de plateforme ensuite.
- `update`, qui fait passer un projet à une version plus récente en une seule commande, avec une fusion à trois voies qui conserve vos propres modifications. Des scénarios de mise à jour et de changement tournent chaque nuit sur les versions récentes.
- Une référence générée de chaque commande et de chaque flag dans le [guide de la CLI](/docs/cli), et des guides pour mettre à jour la CLI, renouveler une clé de licence, résoudre les problèmes, et mettre à jour ou modifier un projet. Chaque commande du guide s’exécute en CI contre la CLI testée.
- Une prochaine bêta qui corrige les README de la CLI elle-même et sa documentation de version.
- La version stable sur le tag par défaut de npm. D’ici là, lancez la CLI avec <RepositoryFact name="cliPackageSpec" />. La version stable sortira quand la facturation et l’extra de cours seront là, et quand la suite de parcours client nocturne générera un projet avec chaque gestionnaire de paquets, le construira, exécutera ses tests et vérifiera la licence de bout en bout. Le site passera alors ses commandes sur le tag par défaut et publiera les notes de version et un article de sortie.

## Application

1. Les prix du site lus depuis Polar, pour qu’un prix ne change qu’à un seul endroit.
2. Créer, modifier et supprimer des produits depuis l’administration, via Polar ; les modèles de tarification, ponctuels et récurrents ; les codes de réduction.
3. Émettre des remboursements depuis la page de la commande, qui affiche déjà les remboursements enregistrés dans Polar ; un e-mail à l’acheteur quand une licence est remboursée ou révoquée ; et les litiges de paiement sur la page de la commande, avec leur issue appliquée à la licence.
4. Passer à une offre inférieure depuis la page de la licence. Aujourd’hui, cela se fait par e-mail au support.
5. Des métriques de tableau de bord sur des données réelles ; une mesure de l’entonnoir d’inscription et de paiement respectueuse de la vie privée ; un écran d’analytique avec les pages vues, les visiteurs, la rétention et l’attrition.
6. L’activation ou la désactivation de la newsletter dans l’espace client.
7. Les permissions : un rôle de rédacteur, des menus filtrés selon les permissions et un éditeur de rôles.
8. Les organisations et les équipes, puis les places d’équipe d’Agency.
9. Un journal d’audit des bannissements, des suppressions et des emprunts d’identité.
10. La modification du blog depuis l’administration, dans un éditeur visuel qui commite dans Git via une pull request ; puis la modification de la documentation.
11. La page d’accueil construite à partir d’un registre de sections, puis le concepteur visuel de pages, une page de tarifs, une bibliothèque de sections et des pages de campagne.
12. L’ouverture du programme d’affiliation.
13. Apple Pay et Google Pay dans le checkout intégré, que Polar doit activer pour les checkouts intégrés.

## Qualité et ingénierie

- La suite de parcours client nocturne exécutée contre le site de preview et la sandbox de Polar, puis étendue pour générer un projet avec la CLI, le construire et exécuter ses tests avec chaque gestionnaire de paquets.
- Un test dans le navigateur pour chaque parcours listé plus bas comme manquant, et pour les parcours encore à construire à mesure que leurs fonctionnalités sont livrées.
- Des tests de mutation sur le code des licences, des paiements et des accès, et la couverture de code dans le navigateur de la suite Playwright.
- Des règles de lint pour les assertions non nulles et les blocs `catch` vides, et des garde-fous pour les agents de codage : un registre des règles avec leurs vérifications, des skills du dépôt générées à partir des conventions avec un contrôle de dérive, et des hooks versionnés dans le dépôt.
- Une règle de lint sur les frontières entre modules dans les projets générés, et des projets générés construits chaque nuit sur les dernières dépendances.
- Performance : les sections les plus lentes de la console d'administration, de la page des produits et de la page de facturation diffusées en continu dans leurs squelettes, les pages de cours mises en cache en périphérie pour les visiteurs non connectés, un test A/B de la suppression des indications modulepreload, Server-Timing sur le Worker, et les activations de licence diffusées en continu vers la page.
- Des dépendances maintenues sur leurs dernières versions, chaque patch étant retiré dès que son correctif sort en amont.
- Les anciennes issues de la précédente base de code Next.js fermées avec une note.
