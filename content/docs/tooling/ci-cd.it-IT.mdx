I workflow si trovano in `.github/workflows/`. I workflow dell'applicazione (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `updates.yml`, `e2e-reusable.yml` e `deploy-reusable.yml`) preparano la toolchain con l'azione composita `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ con la versione di Node in `.nvmrc` e la cache di installazione di Bun, che `setup-vp` ripristina una sola volta, `bun install --frozen-lockfile --ignore-scripts` e `bun run typegen`. `remotion.yml` invece prepara Node da `.nvmrc` e npm.

| Workflow              | Attivazione                                                                                 | Job                                                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull request, gruppi della coda di merge, e chiamate da `deploy.yml`                        | Controlli, test con copertura su shard paralleli, controllo dei tipi senza ogni funzionalità opzionale, E2E su Chromium e su WebKit e il caricamento del Worker di preview |
| `deploy.yml`          | Push su `main`                                                                              | I controlli di `ci.yml`, a meno che non li abbia eseguiti la coda di merge, poi preview, produzione e la release                                                           |
| `preview.yml`         | Manuale                                                                                     | Distribuisce sulla preview condivisa un branch i cui controlli sono passati                                                                                                |
| `e2e-full.yml`        | Push su `main`, la pianificazione <RepositoryFact name="e2eFullSchedule" /> in UTC, manuale | WebKit al push, come su ogni pull request; Chromium e WebKit nelle esecuzioni pianificate e manuali                                                                        |
| `journey.yml`         | La pianificazione <RepositoryFact name="journeySchedule" /> in UTC, manuale                 | La [suite del percorso cliente](#journey-suite) contro la preview condivisa, nella sandbox di Polar                                                                        |
| `updates.yml`         | La pianificazione <RepositoryFact name="updatesSchedule" /> in UTC, manuale                 | Apre, aggiorna o chiude la [issue degli aggiornamenti](#updates)                                                                                                           |
| `e2e-reusable.yml`    | Richiamato dai workflow precedenti                                                          | Una sola build di test, un progetto Playwright su shard paralleli e un solo controllo per entrambi                                                                         |
| `deploy-reusable.yml` | Richiamato da `ci.yml`, `deploy.yml` e `preview.yml`                                        | Build, poi migrazioni D1 e `wrangler deploy`, oppure `wrangler versions upload`                                                                                            |
| `remotion.yml`        | Modifiche a `remotion/` o ai file del sito che importa                                      | Controlla e crea il bundle del progetto video della landing page con npm                                                                                                   |

`remotion.yml` si attiva sugli stessi percorsi per le pull request e i push: `remotion/`, il workflow stesso e i file del sito che `remotion/src` importa, direttamente o tramite altri file del sito. `src/__test__/workflows.test.ts` segue queste importazioni e fallisce quando un file che raggiungono non corrisponde a nessuno dei percorsi, o un percorso non corrisponde a nessuno dei file.

I checkout di `e2e-reusable.yml`, la cui build genera il changelog e il cui `content.spec.ts` lo legge, di `deploy-reusable.yml`, che compila il sito, e del job `release` scaricano tutti i commit senza i loro alberi (`fetch-depth: 0` e `filter: tree:0`): il [changelog](/docs/project/changelog) data ogni voce in base al commit che l'ha portata su `main`. Rispetto a un clone superficiale si aggiungono solo i commit stessi; un clone superficiale farebbe fallire la build invece di datare male le voci. `src/__test__/workflows.test.ts` fallisce quando uno di questi checkout smette di scaricare la cronologia.

Ogni action di un altro repository, comprese quelle di `actions/*`, è bloccata sullo SHA completo del commit di una release, con il tag della release in un commento subito dopo: `uses: <owner>/<repo>@<commit> # <tag>`. Un workflow esegue quindi esattamente il codice di quella release, anche se in seguito il suo tag viene spostato. `src/__test__/workflows.test.ts` fallisce quando un `uses:` in `.github/workflows/` o `.github/actions/` indica un tag o un branch invece di un commit, non ha il tag della release dopo il commit o blocca due release dello stesso repository. `bun run deps:update` porta ogni action all'ultima release e riscrive insieme commit e tag ([Dipendenze](/docs/conventions/dependencies#upgrading)), così le action si aggiornano sullo stesso branch dei pacchetti.

## Controlli [#checks]

Dietro il controllo obbligatorio `Format, lint, types, i18n, tests`, che il job `verify` riporta, ci sono i job `check`, `test` e `features` di `ci.yml`:

| Job                                                   | Esegue                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                               | `bun run check`: tabelle dei nomi delle classi, controlli di i18n e dei contenuti, l'[inventario dei flussi](/docs/tooling/test-coverage#flow-coverage), le [skill per agenti](/docs/tooling/agent-skills#drift-checks), formattazione, lint e tipi                                      |
| `test`                                                | Un job per shard, <RepositoryFact name="vitestShards" /> in parallelo: `bun run test:coverage --shard=<n>/<total>` con il reporter blob di Vitest, poi carica il report blob dello shard con la sua copertura                                                                            |
| `verify`, chiamato `Format, lint, types, i18n, tests` | Quando ogni shard è passato, scarica i report blob ed esegue `bun run test:coverage --merge-reports`, che unisce la copertura e applica le soglie, poi carica il report di copertura; fallisce a meno che `check`, ogni shard, l'unione e ogni scenario del job `features` siano passati |

Uno shard non controlla alcuna soglia, perché misura solo il codice che raggiungono i suoi test; le soglie di `vite.config.ts` si applicano una volta, alla copertura unita di tutti gli shard, come in un `bun run test:coverage` locale. Di questi job, `verify` è l'unico controllo richiesto dalle regole del branch, quindi aggiungere o togliere uno shard o uno scenario non cambia il nome di alcun controllo obbligatorio.

Il job `features` esegue `bun run check:features <scenario>` una volta per ogni scenario di `scripts/features.ts`, in parallelo. Elimina le funzionalità dello scenario, pota ciò che i file rimasti ne nominano, formatta i file potati, controlla i tipi del resto e ne verifica le traduzioni ([Test](/docs/conventions/testing#tests-follow-the-features)). Uno scenario con un riferimento che non si può potare, un errore di tipo o un errore di traduzione fa fallire il suo job e, con esso, il controllo obbligatorio `Format, lint, types, i18n, tests`.

Il job `check` esegue poi `bun run deps:audit`, la [scansione delle dipendenze](/docs/conventions/dependencies#security-advisories): `scripts/audit-dependencies.ts` esegue `bun audit` sulle dipendenze di produzione e fallisce con un avviso di gravità <RepositoryFact name="auditBlockingSeverities" /> che nessuna eccezione valida copre. Una pull request quindi non può introdurre una dipendenza del genere, e un nuovo avviso contro una dipendenza già su `main` ferma la pull request successiva finché non viene corretta o coperta da un'eccezione. La scansione interroga il registry npm, quindi un'interruzione del registry fa fallire il job; rieseguilo.

Il job `sbom`, chiamato `Software bill of materials`, esegue `bun run deps:sbom` in ogni run e carica `sbom.cdx.json` come artefatto `sbom`: lo SBOM CycloneDX delle dipendenze di produzione, con la versione e il package URL di ciascun pacchetto e il grafo delle dipendenze. cdxgen lo scrive a partire da `bun.lock` e tralascia i pacchetti che servono solo alle devDependencies, e `scripts/verify-sbom.ts` fa fallire il job quando nello SBOM manca una dipendenza di `package.json`. Lo SBOM di un commit su `main` è l'artefatto del run del gruppo di merge che lo ha testato. cdxgen gira tramite `bunx` alla versione esatta dello script `deps:sbom` invece che come devDependency, perché i suoi binari di scansione opzionali aggiungerebbero centinaia di megabyte a ogni installazione; `readDependencies` in `scripts/dependencies.ts` legge quella versione dallo script, così la [issue degli aggiornamenti](#updates) elenca un cdxgen più recente come pacchetto fissato. Il job non è un controllo obbligatorio.

I job `e2e` ed `e2e-webkit` richiamano `e2e-reusable.yml`, il primo con `browser: chromium` e il secondo con `browser: webkit`. Ogni chiamata compila una sola volta ed esegue la suite nel suo browser su <RepositoryFact name="e2eShards" /> runner in parallelo:

| Job                                            | Esegue                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                        | `db:reset:test` e `build:test`, poi carica `dist`, il `.wrangler/deploy` che punta alla configurazione del suo Worker e il `.wrangler/test` popolato dal seed come un unico artefatto                                                                                                                      |
| `shard`                                        | Un job per shard, avviato insieme alla build: attende cloud-init e rimuove la sorgente di pacchetti Microsoft del runner, che nessun passaggio usa, installa il browser, attende il caricamento della build, la scarica ed esegue `bunx playwright test e2e/specs --project=<browser> --shard=<n>/<total>` |
| `report`, chiamato `Build and E2E (<browser>)` | Fallisce a meno che la build e ogni shard siano riusciti; quando uno shard è fallito, unisce i report blob degli shard in un unico report HTML e lo carica                                                                                                                                                 |

Gli shard non aspettano la fine dell'intero job `build` (`needs`): partono con lui e preparano la toolchain e il browser mentre compila. Poi `scripts/download-artifact.ts` interroga l'API di GitHub ogni pochi secondi sul job `build` dell'esecuzione, finché il suo step `Upload the test build` non è riuscito. Uno step riuscito non significa che GitHub elenchi già il suo artefatto, e un download in quell'intervallo fallisce con `Artifact not found`, quindi lo script interroga poi gli artefatti dell'esecuzione finché GitHub non elenca `test-worker-<browser>` caricato dopo l'avvio della build, e poi scarica da sé quell'artefatto e lo verifica con il digest SHA-256 che GitHub ha registrato. Un artefatto elencato può ancora rispondere `Not Found` per un momento, quindi lo script richiede finché GitHub non serve l'archivio intero, e nessun altro step lo chiede nel frattempo. Lo script invia l'ETag della risposta precedente, e GitHub non conta una risposta invariata nel limite di richieste del token. Uno step della build che fallisce, o una build che finisce senza il suo caricamento, fa fallire ogni shard in pochi secondi, con lo step fallito e un link alla build, e uno shard che aspetta oltre il limite dello script fallisce con un errore che dice se manca lo step, l'elenco o il download. Leggere i job e gli artefatti dell'esecuzione richiede `actions: read`, che solo il job `shard` chiede: `ci.yml`, `e2e-full.yml` e il job `checks` di `deploy.yml` lo concedono ai workflow che richiamano, e ogni altro job mantiene `contents: read`.

I retry e i worker di Playwright restano come li descrive [Playwright](/docs/tooling/playwright#configuration), su ogni shard. Il job `report` di ciascun browser è l'unico controllo di quel browser richiesto dalle regole del branch, quindi aggiungere o rimuovere uno shard non cambia il nome di nessun controllo richiesto. La build impacchetta anche l'elenco dei tag di release che ha letto, e ogni shard elimina ogni tag creato da allora: `content.spec.ts` legge i tag di release da Git, e una release taggata mentre gli shard aspettano gli farebbe attendere un changelog che la build non ha mai generato.

Il job `upload`, chiamato `Worker upload`, richiama `deploy-reusable.yml` con `upload: true`: compila il Worker di preview esattamente come fa un deploy ed esegue `wrangler versions upload`, che lo invia al Worker `saasyland-preview` come nuova versione senza distribuirla. Cloudflare controlla il caricamento come controlla un deploy, con il limite di dimensione, il tempo di avvio, i binding e i secret che `secrets.required` nomina, quindi il deploy di un Worker che supera questo controllo riesce, mentre `preview.saasyland.com` continua a servire la versione distribuita in precedenza. Il job non applica alcuna migrazione e non registra alcun deployment GitHub (`deployment: false`), e gira in parallelo ai caricamenti delle altre pull request. La versione di una pull request riceve l'alias `pr-<number>`, che dà il nome alla versione nella dashboard di Cloudflare; il riepilogo del job mostra l'ID e la dimensione della versione, e il suo URL quando le Version URLs sono attive per il Worker, cosa che oggi non vale per `saasyland-preview`. Le pull request provenienti da fork e da Dependabot non possono leggere le credenziali di Cloudflare e saltano il job; la coda di merge, che invece può leggerle, carica la loro build prima del merge.

In una pull request, `bun run check` fallisce anche finché la pull request non aggiunge la propria [voce del changelog](/docs/conventions/git-workflow#changelog-entries), e nella coda di merge finché manca la voce della pull request in coda. La build dei job `e2e` e `upload`, e quella dei job di deploy, fallisce finché il changelog mostrerebbe sotto **Non rilasciato** una voce che non è quella della pull request stessa, e nella coda di merge e su `main` finché ne mostrerebbe una qualsiasi.

## Coda di merge [#merge-queue]

Il ruleset che protegge `main` richiede `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)`, `Build and E2E / Build and E2E (webkit)` e `Worker upload / Upload preview`, e fa il merge delle pull request solo attraverso la coda di merge di GitHub, che fa lo squash di ciascuna. `bun scripts/enqueue-pr.ts <number>` mette una pull request in coda ([Git e pull request](/docs/conventions/git-workflow#merging)). Per ogni pull request in coda, GitHub scrive il commit squash su un branch chiamato `gh-readonly-queue/main/pr-<number>-<commit>`, sopra `main` e le pull request che la precedono, e vi esegue `ci.yml` per l'evento `merge_group`. Quando ogni pull request di un gruppo è passata, GitHub sposta `main` sull'ultimo commit del gruppo, proprio il commit che la coda ha testato, così un solo push porta su `main` ogni pull request del gruppo come un proprio commit squash. Una pull request che fallisce esce dalla coda, e quelle che la seguono vengono testate di nuovo senza di essa.

Il ruleset contiene anche `copilot_code_review` con `review_on_push: true`, ma al 22 novembre 2026 GitHub Copilot non ha revisionato alcuna pull request dalla #70, quindi le pull request non ricevono alcuna revisione automatica. Una revisione sarebbe solo consultiva: il ruleset non richiede alcuna approvazione né alcun thread di revisione risolto, quindi una pull request aspetta solo i quattro check qui sopra.

`ci.yml` annulla il run di una pull request quando un commit più recente lo sostituisce, ma mai un run della coda, i cui branch hanno ciascuno un proprio ref. Il controllo del changelog tratta il branch della coda come `main`: ogni pull request del gruppo è già un commit squash il cui oggetto termina con il suo numero, quindi nessuna voce può restare non rilasciata, e la voce della pull request in coda deve esistere.

## Deploy

`deploy.yml` distribuisce ogni push su `main`, prima sulla preview condivisa e poi in produzione, una volta che il commit ha superato tutti i controlli che `main` richiede. Il suo primo job, `tested`, esegue `scripts/tested-commit.ts`, che legge quei controlli dal ruleset tramite l'API di GitHub e cerca un'esecuzione riuscita di ciascuno sul commit pubblicato. Un commit arrivato attraverso la coda di merge li ha, perché la coda ha testato proprio quel commit, quindi `deploy.yml` lo distribuisce senza eseguire di nuovo i controlli; un commit arrivato su `main` in qualsiasi altro modo esegue prima i controlli di `ci.yml`.

| Evento                              | Destinazione                | Ambiente GitHub             | URL                                                  |
| ----------------------------------- | --------------------------- | --------------------------- | ---------------------------------------------------- |
| Push su `main`                      | `preview`, poi `production` | `Preview`, poi `Production` | https://preview.saasyland.com, https://saasyland.com |
| Esecuzione manuale di `preview.yml` | `preview`                   | `Preview`                   | https://preview.saasyland.com                        |

`deploy-reusable.yml` assegna a ogni ambiente GitHub il suo URL, e `src/__test__/workflows.test.ts` fallisce quando uno differisce dal suo host in `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). La preview è condivisa: ogni deploy sostituisce il precedente e usa lo stesso database D1, lo stesso namespace KV e gli stessi bucket R2 di preview. Esegue `main`, così la [suite del percorso cliente](/docs/tooling/playwright#journey-suite), i webhook della sandbox di Polar e l'accesso su `preview.saasyland.com`, l'unico host di preview di cui Better Auth si fida, incontrano tutti il codice che la produzione sta per eseguire, e ogni migrazione raggiunge il database di preview prima della produzione. Per provare un branch lì prima del merge, esegui `gh workflow run preview.yml --ref <branch>`: distribuisce il branch, migrazioni comprese, solo quando il suo commit ha superato i controlli che `main` richiede, e il push successivo su `main` rimette lì `main`.

`deploy-reusable.yml` verifica la presenza dei secret `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID`, esegue `scripts/verify-bindings.ts`, compila con i valori fittizi di `.env.test`, rimuove il file generato `dist/server/.dev.vars`, applica `db:migrate:<target>` ed esegue `vp exec wrangler deploy --config dist/server/wrangler.json`, oppure, con `upload: true`, esegue `vp exec wrangler versions upload` al posto degli ultimi due passaggi. Non esegue `scripts/verify-deployment.ts`, il controllo del sito online degli script `deploy:<target>`, perché la protezione dai bot di Cloudflare risponde 403 alle richieste dei runner di CI. Non esegue nemmeno `scripts/run-deploy-checks.ts`, quindi la CI non esegue nessuno dei controlli di deploy, cioè degli script `<name>:verify:<environment>` in `package.json`: nella CI non c'è alcun `.env.<target>` e gli ambienti GitHub contengono solo le credenziali di Cloudflare, oltre alle impostazioni della sandbox della [suite del percorso cliente](#journey-suite) in `Preview`. Oggi sono `auth:verify` della funzionalità di autenticazione e `polar:verify` della funzionalità Polar; esegui in locale `bun run auth:verify:<target>` dopo aver modificato un client OAuth e `bun run polar:verify:<target>` dopo ogni modifica in Polar ([Configurazione di Polar](/docs/getting-started/polar-setup)). Non viene caricato alcun file di secret: il Worker mantiene i secret di runtime già impostati in Cloudflare. I deploy verso la stessa destinazione si mettono in coda invece di annullarsi a vicenda, e i caricamenti girano in parallelo. Un nuovo commit su una pull request annulla il run di `ci.yml` del commit precedente, che nessuno unirà, mentre i run della coda di merge non si annullano mai a vicenda e quelli di `deploy.yml` ed `e2e-full.yml` su `main` si mettono in coda (`concurrency` con `queue: max`), così ogni push su `main` viene distribuito.

## Suite del percorso cliente [#journey-suite]

`journey.yml` esegue `bun run test:journey`, la [suite del percorso cliente](/docs/tooling/playwright#journey-suite), contro `https://preview.saasyland.com` secondo la pianificazione <RepositoryFact name="journeySchedule" /> in UTC e quando lo si avvia a mano:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` vale `all`, `core`, `complete`, `agency` o `upgrade`; ogni valore diverso da `all` esegue solo il test con quel tag. Il job legge questi secret dell'ambiente GitHub `Preview` senza registrare un deploy (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` e `RESEND_API_KEY`. Imposta `POLAR_SERVER` a `sandbox`, l'unico valore che la suite accetta, e la suite crea il suo client Polar per la sandbox, quindi il workflow non può raggiungere il Polar di produzione. Le esecuzioni si mettono in coda e non si annullano mai a vicenda, perché un'esecuzione annullata lascerebbe pagati i suoi ordini. Il job scrive il risultato e la durata di ogni test, e l'errore di ogni test fallito, nel riepilogo dell'esecuzione, e carica il report HTML, `playwright-report/journey.json` e le tracce, i video e le directory delle macchine dei test falliti come artefatto `journey-report`.

Il workflow non viene eseguito dopo ogni deploy di `main`. Ogni esecuzione registra un account per test sulla preview, paga e rimborsa i loro ordini nella sandbox di Polar e invia le loro email di verifica e conferme d'acquisto tramite l'account Resend che la preview condivide con la produzione. `main` viene distribuito molte volte in una giornata intensa, quindi un'esecuzione dopo ogni deploy moltiplicherebbe quelle email rispetto ai limiti di invio da cui dipendono le email della produzione, e non fermerebbe nulla: la produzione viene distribuita subito dopo la preview, qualunque cosa trovi il percorso. Ogni esecuzione copre l'intero acquisto: la registrazione con la verifica dell'email, un pagamento nella sandbox per ogni piano, la chiave emessa da Polar, la CLI pubblicata sui dispositivi del piano, il passaggio da Core a Complete e i rimborsi. Non è ancora verde: finora nessuna esecuzione è andata a buon fine, perché i suoi secret non sono impostati, quindi per ora non verifica alcun acquisto. Avviala a mano dopo una modifica a pagamenti, licenze o API delle licenze della CLI, e dopo `gh workflow run preview.yml --ref <branch>` per provare un branch prima del merge.

## Aggiornamenti [#updates]

`updates.yml` cerca aggiornamenti delle dipendenze e delle skill per agenti secondo la pianificazione <RepositoryFact name="updatesSchedule" /> in UTC e quando viene avviato a mano. Il primo passo, `bun scripts/report-updates.ts find`, chiede al registro npm l'ultima release di ogni dipendenza diretta ed esegue `bun run skills:update` nel checkout del runner, da cui non viene committato nulla, per vedere quali skill sono cambiate a monte. Il secondo passo, `bun scripts/report-updates.ts issue`, tiene una sola issue, <RepositoryFact name="updatesIssueTitle" />: la apre quando ci sono aggiornamenti, la riscrive nelle esecuzioni successive e la chiude quando tutto è aggiornato. La issue elenca ogni pacchetto non aggiornato, indicato come spostato da `bun run deps:update` o bloccato, e ogni skill con i commit tra cui si sposterebbe. Il primo passo legge anche, con `git ls-remote`, che non richiede token, i tag di release del repository di ogni action bloccata, e la issue elenca ogni action bloccata su una release più vecchia dell'ultima.

Dopo la issue, il job esegue `bun run deps:audit`, la stessa scansione del job `check`, così un nuovo avviso alto o critico fa fallire il run settimanale anche in una settimana senza pull request.

Il workflow può solo leggere il repository e scrivere issue, e solo il secondo passo riceve il token. Non apre pull request, perché GitHub non avvia alcun workflow per una pull request aperta dal token del workflow stesso, quindi i suoi controlli non verrebbero mai eseguiti; esegui invece `bun run deps:update` su un branch.

## Release e tag [#releases-and-tags]

Il sito viene distribuito in modo continuo, quindi le sue versioni sono date e non versioni semantiche. Quando un deploy di produzione va a buon fine, il job `release` di `deploy.yml` assegna al commit distribuito il tag `vYYYY.MM.DD` con la data UTC e pubblica una GitHub Release. Un secondo deploy di produzione nello stesso giorno riceve il tag `vYYYY.MM.DD.2`, il successivo `.3` e così via. I deploy di preview non ricevono mai un tag. Il job `release` è l'unico con `contents: write`.

Le note di rilascio sono le voci del [changelog](/docs/project/changelog) che la release ha rilasciato, quelle arrivate su `main` dal tag di release precedente, ciascuna chiusa da `(#<number>)`, che GitHub collega alla sua pull request, così ogni modifica è descritta in un solo posto; se una release non ne ha rilasciata nessuna, le sue note rimandano al changelog. `scripts/publish-release.ts` prende le note da `releaseNotes` in `src/lib/changelog.ts`, l'unico elemento di `RELEASE_NOTES`, ed esegue `gh release create` con il tag scelto dal deploy, quindi un progetto senza il changelog pubblica le sue release senza note. Una nuova esecuzione mantiene il tag che il commit ha già e salta una release che esiste già.

Il job del deploy in produzione sceglie quel tag prima della build: `scripts/choose-release-tag.ts` applica `releaseTag` di `src/lib/release.ts` ai tag del checkout, la build riceve il tag come `RELEASE_TAG` e il job lo passa al job `release` come output `release-tag`, così il deploy e la sua release condividono un solo tag. Con esso il [changelog](/docs/project/changelog) collega ogni voce alla release che l'ha rilasciata per prima: il tag di release più vecchio il cui commit contiene il commit squash della voce nella cronologia dei primi genitori di `main`, che la build legge insieme alle date con un solo `git log`, oppure il tag del deploy stesso per le voci che porta. Il job `release` legge il changelog allo stesso modo, con il tag che pubblica, quindi le note di una release sono esattamente le voci che la pagina collega a quella release. Le voci unite prima del primo tag di release non rimandano a nessuna release, e nelle build locali, di anteprima e delle pull request lo stesso vale per le voci che nessun deploy ha ancora rilasciato. Due deploy in produzione non possono scegliere lo stesso tag: `deploy.yml` esegue un solo run del workflow alla volta (`concurrency` con `queue: max`), quindi il job `release` del run precedente ha creato il suo tag prima che il deploy successivo faccia il checkout del repository.

Per riportare la produzione a una release, annulla in una pull request tutto ciò che viene dopo il suo tag:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Il merge distribuisce il codice del tag dopo i soliti controlli e gli assegna il tag di una nuova release. Le migrazioni D1 non vengono annullate, quindi il codice precedente gira sullo schema più recente. Ogni modifica dello schema deve funzionare con l'applicazione distribuita prima di essa, il che rende l'operazione sicura per la release precedente; leggi le migrazioni intermedie prima di tornare più indietro.
