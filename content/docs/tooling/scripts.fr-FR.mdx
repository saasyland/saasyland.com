Exécutez les scripts depuis la racine du dépôt avec `bun run <script>`. Les scripts qui appellent Wrangler, ainsi que `db:generate`, qui appelle drizzle-kit, les lancent via `vp exec`, qui prend le binaire dans `node_modules/.bin` : ils utilisent donc toujours les versions verrouillées dans `bun.lock`.

## Développement et build

| Script             | Exécute                                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dev`              | `generate:cn`, `content` et `vp dev` dans l'environnement `development` sur http://localhost:3000                                                                                      |
| `build`            | Identique à `build:preview`                                                                                                                                                            |
| `build:preview`    | Nettoyage de `dist`, `generate:cn`, `content`, `vp build` pour `preview`, `scripts/verify-build.ts preview`, `scripts/optimize-prerendered-html.ts` et `scripts/generate-seo-files.ts` |
| `build:production` | Les mêmes étapes pour `production`                                                                                                                                                     |
| `build:test`       | Les mêmes étapes pour l'environnement `test`                                                                                                                                           |
| `start`            | `vp preview` du dernier build sur http://127.0.0.1:3000                                                                                                                                |
| `start:test`       | `vp preview` du build de test                                                                                                                                                          |

`verify-build.ts` vérifie que `.wrangler/deploy/config.json` pointe vers `dist/server/wrangler.json` et que ce fichier déploie le Worker que `wrangler.jsonc` nomme pour l'environnement, puis la langue du document, les liens canoniques et alternatifs des pages d'accueil et des pages légales localisées, les polices, que les alias de langue et les pages situées sous les chemins non listés des zones n'ont pas été prérendus, que chaque page de la documentation et chaque article de blog publié a été prérendu, qu'aucun asset client n'importe `cloudflare:workers`, que les imports statiques du script d'entrée du navigateur ne contiennent le loader des messages d'aucun namespace de page, et que le code que le Worker charge à un démarrage à froid reste petit : les imports statiques de `dist/server/index.js` ne doivent pas atteindre `@polar-sh`, `drizzle-orm` ni `resend` et doivent totaliser au plus `BOOT_CLOSURE_MAX_BYTES` (voir [Performances](/docs/conventions/performance)). `optimize-prerendered-html.ts` retire des pages prérendues les indications `modulepreload` des dépendances et conserve l'indication du point d'entrée en basse priorité. `generate-seo-files.ts` écrit `sitemap.xml` et le flux du blog dans chaque langue, et génère une carte de partage pour chaque page prérendue ainsi que le logo de l'organisation, le tout à partir des métadonnées des pages elles-mêmes ; voir [Référencement et aperçus sociaux](/docs/features/seo).

## Déploiement

| Script              | Exécute                                                                                                                                                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `deploy:preview`    | `scripts/verify-bindings.ts preview`, `scripts/prepare-deploy-secrets.ts preview`, `scripts/run-deploy-checks.ts preview`, `build:preview`, `db:migrate:preview`, `wrangler deploy` de `dist/server/wrangler.json` et `scripts/verify-deployment.ts preview` |
| `deploy:production` | Les mêmes étapes pour `production`                                                                                                                                                                                                                           |

- `verify-bindings.ts` échoue lorsqu'il manque à l'environnement un binding que `development` déclare (ici `DB`, `CACHE`, `MEDIA` et `BUNDLES`) ou contient encore un identifiant D1 ou KV fictif, et lorsque la production partage sa base de données, son espace de noms ou son bucket avec la préversion.
- `prepare-deploy-secrets.ts` lit dans `.env.<environment>` les clés listées dans `secrets.required` de l'environnement, échoue lorsque l'une d'elles est absente, vide ou un espace réservé, et n'écrit que ces clés dans `.wrangler/secrets.<environment>.json`. Un espace réservé est une valeur entre crochets (<RepositoryFact name="secretPlaceholderBrackets" />), comme `[UPDATE]`, ou l'un des mots <RepositoryFact name="secretPlaceholderWords" />, en majuscules ou en minuscules, avec ou sans espaces, traits d'union ou tirets bas. L'erreur nomme les clés sans afficher leurs valeurs. Il lit les noms dans `wrangler.jsonc` et couvre ainsi les secrets de chaque zone sans en nommer aucune. Les autres variables du fichier ne sont pas téléversées.
- `run-deploy-checks.ts` exécute `bun run <check>:<environment>` pour chaque vérification de déploiement qu'une zone déclare dans `src/data/<area>.deploy.ts`, et arrête le déploiement avant le build lorsque l'une d'elles échoue. Aujourd'hui, ce sont `auth:verify`, de la zone d'authentification, qui échoue si <RepositoryFact name="oauthClientIdVariables" /> dans `.env.<environment>` ne contiennent pas chacune un identifiant client au format de son fournisseur (les formats que `verify-deployment.ts` applique après le déploiement), et `polar:verify`, de la zone Polar, qui échoue lorsque l'organisation Polar de `.env.<environment>` ne correspond pas au code.
- Les migrations s'exécutent après le build et avant le déploiement : un build en échec ne touche donc jamais la base de données, et le nouveau Worker ne démarre jamais sur un schéma plus ancien.
- Le déploiement exécute `env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.<environment>.json`. La configuration issue du build cible déjà un seul environnement ; un `CLOUDFLARE_ENV` resté défini dans le shell amènerait Wrangler à chercher une section d'environnement que ce fichier ne contient pas.
- `verify-deployment.ts` envoie une requête à <RepositoryFact name="liveSiteCheckPaths" /> sur le domaine de l'environnement et échoue si l'un d'eux ne répond pas `200` avec le type de contenu attendu. Sur <RepositoryFact name="socialSignInPath" />, il lance, comme le navigateur, la connexion avec chaque fournisseur de la page de connexion, <RepositoryFact name="oauthProviderIds" />, et échoue si l'URL d'autorisation qu'il reçoit n'est pas sur l'hôte du fournisseur ou ne porte pas un `client_id` au format de ce fournisseur et un `redirect_uri` égal à <RepositoryFact name="oauthCallbackPath" /> sur le même domaine. L'erreur nomme le fournisseur et le problème sans afficher la valeur. Il relance une vérification en échec jusqu'à <RepositoryFact name="liveSiteCheckRetries" /> fois, à <RepositoryFact name="liveSiteCheckRetrySeconds" unit="second" /> d'intervalle, et ne modifie rien d'autre que l'état OAuth et le compteur de tentatives de courte durée dans D1 que laisse aussi un clic sur un bouton de connexion. `bun scripts/verify-deployment.ts <preview|production>` vérifie séparément un site en ligne.

## Génération et maintenance

| Script           | Exécute                                                                                                                    |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `content`        | `fumadocs-mdx` : génère `.source/` à partir de `content/`                                                                  |
| `generate:cn`    | Construit les tables de fusion des classes dans `.source/cn-tables.ts` à partir de `src/lib/cn.config.ts`                  |
| `cf-typegen`     | `wrangler types` pour `development` : régénère `src/types/worker-configuration.d.ts`                                       |
| `typegen`        | `cf-typegen`, `generate:cn` et `content`                                                                                   |
| `skills:sync`    | `scripts/sync-skills.ts` : restaure les skills pour agents à partir de `skills-lock.json`                                  |
| `clean`          | Supprime `.source`, `.tanstack`, `.wrangler`, `dist`, `coverage`, la sortie de Playwright et `*.tsbuildinfo`               |
| `clean:deep`     | `clean` et `node_modules`                                                                                                  |
| `clean:hardcore` | `clean:deep`, `bun.lock` et `skills-lock.json`                                                                             |
| `prepare`        | S'exécute à l'installation : `vp config --no-agent` (hooks Git), `scripts/verify-git-hooks.ts`, `generate:cn` et `content` |

`clean` supprime `.wrangler`, y compris les bases de données locales de développement et de test et les fichiers de secrets écrits par les scripts de déploiement : exportez donc d'abord les données locales que vous souhaitez conserver.
