## Implemented

- **Sessions**: Better Auth sessions in D1, cookie prefix `saasyland`, secure cookies outside local modes, allowed hosts per mode, and `cf-connecting-ip` as the client address. The client session never contains the token.
- **Accounts**: required email verification, passwords checked against known data breaches with Better Auth's `haveIBeenPwned` plugin, sessions revoked on password reset, optional TOTP with backup codes, verification identifiers stored hashed and OAuth tokens encrypted.
- **Authorization**: `requireSignedIn` and `requireAdmin` on routes; `authorized(permission)` on server functions with the roles that `auth.access.ts` builds from the areas' access files.
- **Rate limits**: the Better Auth limiter and the `withRateLimit` middleware share the D1 `rate_limit` table. `RATE_LIMITS.SENSITIVE` allows <RepositoryFact name="sensitiveRateLimit" /> calls and `RATE_LIMITS.TOKEN` <RepositoryFact name="tokenRateLimit" /> calls per <RepositoryFact name="rateLimitWindowSeconds" unit="second" /> per client and action. Verification, password reset and newsletter confirmation emails are also limited to <RepositoryFact name="recipientEmailsPerHour" /> of each kind per address per hour (`withinRecipientRateLimit`, keyed on a SHA-256 hash of the address); over the limit the email is skipped silently. The [CLI licence API](/docs/features/cli-licence-api) counts its requests per address and per licence key in the same table.
- **Errors**: the request middleware turns failures into `AppError` codes (`src/modules/_core/constants/errors.ts`), so clients never receive raw server messages; components show them with `useErrorMessage`.
- **Webhooks and forms**: Polar webhooks are verified with `POLAR_WEBHOOK_SECRET`; a newsletter subscription (`subscribeToNewsletter`) is accepted only on the build mode's hosts from `appHostsForMode`, over HTTPS or, in development and test, HTTP (`newsletterRequestOrigin`).
- **Better Auth input**: `enforceInputPolicy` in `auth.hooks.ts` applies the form schemas to every Better Auth endpoint that accepts a password, name, email or image, so requests sent straight to `/api/auth` meet the same rules; a failing request gets `400` with `VALIDATION_ERROR`.
- **Media**: video files stay in a private R2 bucket. The Worker serves them only under `/media/` paths signed with an HMAC key derived from `AUTH_SECRET` and valid for at least <RepositoryFact name="signedMediaHours" unit="hour" />. `getVideoPlayback` issues them to callers with `video: ["read"]`; `getLessonPlayback` issues them for a published lesson once `hasLessonAccess` allows the viewer, so guests receive them for free previews, signed-in users for account lessons, Complete or Agency licence holders for paid lessons and admins for every lesson; a wrong or expired signature gets `403`. Lesson materials are served the same way under `/media/downloads/`, signed by `getLesson` for the same viewers, valid for at least <RepositoryFact name="signedDownloadHours" unit="hour" /> and downloaded as attachments.
- **CLI template bundles**: each release's bundle stays in the private `BUNDLES` bucket. The CLI licence API signs a `/bundles/` URL, valid for <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, only for an active licence and an activation of the calling machine, with an HMAC key that HKDF derives from `AUTH_SECRET` for bundles alone; a wrong or expired signature gets `403`. See [CLI licence API](/docs/features/cli-licence-api#template-bundles).
- **Headers**: every response from the Worker carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, a `Permissions-Policy` that turns off camera, microphone and geolocation, and a Content Security Policy that blocks framing, `<base>` changes and plugins (`base-uri 'none'`, `frame-ancestors 'none'`, `object-src 'none'`). The policy lists only features that browsers still recognize: Chromium is the only engine that reads the header, and it logs an error for every feature it does not know, as it does for `browsing-topics` since Chrome withdrew the Topics API. HTTPS responses add `Strict-Transport-Security`. They are defined once, as `SECURITY_HEADERS` and `HTTPS_SECURITY_HEADERS` in `src/modules/_core/constants/api.ts`, and `src/server.ts` sets them on every Worker response, replacing any value the response or a `public/_headers` rule already set. Files served without the Worker (`/assets/*`, `/fonts/*`, `/robots.txt`, `/llms.txt`) get the same headers from the `/*` rule in `public/_headers`, a static file the platform reads before any code runs; `src/__test__/server.test.ts` fails when that rule and the constants differ.
- **Scripts**: a page runs only the scripts it was served with. Every HTML response the Worker returns gets a nonce of its own and `documentPolicy(nonce)` from `src/lib/content-security-policy.ts` as its `Content-Security-Policy` header, which follows Google's strict CSP: `script-src` with the nonce, `'strict-dynamic'` so that those scripts can load the rest, such as route chunks and the Affonso pixel, `'unsafe-inline' https:` as fallbacks that browsers with nonce support ignore, and `object-src`, `base-uri` and `frame-ancestors` set to `'none'`. For a page TanStack Start renders, `src/server.ts` passes the nonce as the request context's `nonce`, and `getRouter` gives it to the router, so it is on every script the router, React and `ThemeScript` render. A prerendered page is a static file, so `src/server.ts` streams it from `ASSETS` through `withNonce`, an `HTMLRewriter` that puts the response's nonce on every executable script and module preload, replaces the nonce that prerendering left on any element, and writes it into the router's `csp-nonce` meta tag. Cloudflare reads the nonce from the header and gives it to the scripts it injects at the edge, such as Bot Fight Mode's JavaScript Detections, which it cannot do with a policy in a `<meta>` tag. Because every response has its own nonce, HTML responses are `private, no-cache` and carry no `ETag` or `Last-Modified`, so a browser never reuses a cached page with another response's nonce. The browser runs zod `jitless` (`src/integrations/zod/zod.config.ts`, kept in zod's own chunk), so zod never probes for `eval`. The dev server sends only the base policy, because Vite's inline scripts carry no nonce; the browser suite runs a production build and fails any spec in which a page reports a violation.

## Not implemented

- Content Security Policy directives for styles, images, media, fonts and connections, Trusted Types, and reports of violations: the policy restricts scripts, plugins, base URLs and framing.
- An audit log, including for bans, deletions and impersonation.
- Bot protection or CAPTCHA on public forms.
