`src/modules/_core` é a única pasta de módulo que não é dona de uma tabela. Ela reúne só a base sobre a qual se constroem os schemas, os schemas Zod e os casos de uso dos módulos, para que nenhum módulo tenha de redefini-la: os códigos de erro, as constantes HTTP e de ambiente, os catálogos de locales, fusos horários, países e moedas com a moeda da loja, os campos Zod e os textos localizados compartilhados, e as entradas de paginação, ordenação, busca e período.

## Constantes

| Arquivo                 | Conteúdo                                                                                                                                      |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `constants/errors.ts`   | `ERROR_CODES`, o tipo `ErrorCode` e a classe `AppError`                                                                                       |
| `constants/api.ts`      | `HTTP_STATUS`, os nomes dos headers `cf-ipcountry` e `cf-connecting-ip`, os headers de segurança e os hosts permitidos por modo de build      |
| `constants/locale.ts`   | O catálogo `LOCALES`, `LocaleCode`, `getLocaleName` e `getLocaleDirection`                                                                    |
| `constants/country.ts`  | O catálogo `COUNTRIES` e `CountryCode`                                                                                                        |
| `constants/currency.ts` | O catálogo `CURRENCIES`, `CurrencyCode`, e `toMinorUnits` e `fromMinorUnits`, que convertem um valor para a menor unidade da moeda e de volta |
| `constants/timezone.ts` | O catálogo `TIMEZONES` e `TimezoneCode`                                                                                                       |
| `constants/pricing.ts`  | A moeda da loja `DEFAULT_CURRENCY_CODE` e a formatação de moeda `CURRENCY_FORMAT`                                                             |
| `constants/ordering.ts` | `FIRST_POSITION`, o lugar do primeiro item em uma lista ordenada                                                                              |

Os catálogos ficam aqui porque a base é construída sobre eles: `countryCodeField` e `currencyCodeField`, os schemas de pedidos, produtos e assinaturas, as constantes do usuário e a moeda padrão de um produto. O catálogo de locales lista todos os locales conhecidos; os locales que a aplicação atende estão em `I18N.SUPPORTED_LOCALES`, no arquivo `src/integrations/use-intl/i18n.config.ts`. Os dados sobre os quais nenhum schema nem caso de uso é construído vão para `src/data`, que guarda só constantes e listas literais, e os helpers genéricos vão para `src/lib`. Um teste em `src/__test__/module-tables.test.ts` falha quando um arquivo de `_core` não está descrito nesta página, então cada arquivo novo é uma decisão consciente.

## Utilitários

- `utils/localized-text.ts`: `LocalizedText`, um texto por locale guardado como JSON, `localizedTextSchema`, que exige `en-US` e aceita no máximo <RepositoryFact name="localizedTextMaxLength" /> caracteres por texto, e `localize`, que recorre a `en-US`
- `utils/ordering.ts`: `nextPosition`, a maior `position` mais um, e `reorder`, que move um item para um lugar entre os irmãos, trata um lugar além de qualquer uma das pontas como essa ponta, numera a lista a partir de `FIRST_POSITION` e retorna só os itens cuja `position` muda; os casos de uso de curso, capítulo, aula e material mantêm `position` sem lacunas com elas
- `utils/pagination.ts`: `paginationSchema` (`pageIndex`, `pageSize`) e `DEFAULT_PAGE_SIZE`
- `utils/search.ts`: `searchSchema` e `localizedSearchSchema`, a entrada dos casos de uso de busca do painel administrativo, seus limites de tamanho e o `SearchHit` que retornam
- `utils/time-series.ts`: `TIME_RANGES` e `timeRangeSchema`, os períodos dos gráficos de receita e de cadastros do admin, `timeSeries`, as faixas diárias ou mensais de um período, e `pointsOf`, que dá zero a uma faixa sem valor
- `utils/zod-fields.ts`: campos Zod reutilizáveis, como `idField`, `localeField`, `positionField` (um número inteiro a partir de `FIRST_POSITION`) e `slugField`

## Erros

Existe uma única classe de erro e uma única lista de códigos:

```ts
export const ERROR_CODES = {
  AUTH_API_ERROR: "AUTH_API_ERROR",
  CONFLICT: "CONFLICT",
  FORBIDDEN: "FORBIDDEN",
  INTERNAL_ERROR: "INTERNAL_ERROR",
  NOT_FOUND: "NOT_FOUND",
  TOO_MANY_REQUESTS: "TOO_MANY_REQUESTS",
  UNAUTHORIZED: "UNAUTHORIZED",
  VALIDATION: "VALIDATION",
} as const

export type ErrorCode = (typeof ERROR_CODES)[keyof typeof ERROR_CODES]

export class AppError extends Error {
  readonly code: ErrorCode

  constructor(code: ErrorCode, message: string = code) {
    super(message)
    this.name = "AppError"
    this.code = code
  }
}
```

Server functions lançam `AppError`. O middleware `withRequest` normaliza todo o resto: erros da API do Better Auth viram `AUTH_API_ERROR`, com a chave de erro do Better Auth como mensagem; erros do Zod viram `VALIDATION`; e erros desconhecidos são registrados em log e viram `INTERNAL_ERROR`. No navegador, `useErrorMessage()`, de `src/hooks/use-error-message.ts`, mapeia a mensagem para as traduções `auth.errors.*` ou `errors.codes.*`.
