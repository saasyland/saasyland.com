このページのルールはどれも計測から生まれたもので、いくつかは、かえって状況を悪化させた直感的な修正を置き換えたものです。これらのルールの背後にあるコードを変更するのは、それを上回る新しい計測結果がある場合だけにしてください。

## 主張する前に計測する

- 同じページで以前のビルドと新しいビルドを比較します。それぞれ少なくとも 5 回ずつ交互に Lighthouse を実行し、中央値を比較します。1 回の実行では何も証明できません。マシンのノイズにより、およそ 5 回に 1 回は外れ値が出ます。
- PageSpeed Insights の 1 回の実行で変更を判断してはいけません。同じデプロイでも、テストを実行するマシンの速度によってスコアは大きく変わります。Lighthouse はその速度を `benchmarkIndex` として報告します。
- 本番ビルド（`bun run build:test` の後に `bun run start:test`）を、圧縮を有効にした HTTP/2 で配信して計測します。圧縮なしの素のローカル HTTP/1.1 では、Lighthouse のネットワークシミュレーションが、本番では決して起こらない接続と転送サイズを前提に計算してしまいます。
- Lighthouse の診断はスコアではありません。以下のセクションで示すように、「強制リフロー」や「適切なサイズの画像」のようなヒントが、そのページにとっては誤りである場合があります。対応する前に、スコアに反映される指標を確認してください。

## Worker の起動グラフを小さく保つ

`src/server.ts` はすべての HTML リクエストで実行され（`wrangler.jsonc` の `run_worker_first`）、静的にインポートしたものはすべて、コールドスタートのたびに評価されます。そのため、このファイルと各機能が追加する Worker ハンドラーは、定数と純粋なヘルパーだけをインポートし、それ以外はリクエストが必要としたときに読み込みます。

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

以前、Polar のクライアントもインポートしていたモジュールからヘッダー名を 1 つ静的にインポートしただけで、約 1.4 MB の SDK がすべてのコールドスタートに読み込まれ、ランディングページの最初の 1 バイトが届くまでに最大 1.4 秒かかったことがあります。`COUNTRY_HEADER` と `IP_ADDRESS_HEADER` が、重いものを何もインポートしない `src/modules/_core/constants/api.ts` にあるのはそのためです。`server.ts` やそれがインポートするモジュールに静的インポートを追加する前に、そのインポートの連鎖をたどってください。`polar`、`drizzle-orm`、`resend` に到達するものはすべて退行です。`scripts/verify-build.ts` はビルドのたびにこれを確認します。デプロイされる Worker のエントリーである `dist/server/index.js` の静的インポートをたどり、それらが `@polar-sh`、`drizzle-orm`、`resend` からバンドルされたコードに到達した場合や、合計が `BOOT_CLOSURE_MAX_BYTES` を超えた場合に失敗します。パスもこれらの静的インポートに含まれるため、`src/routes.ts` はパスを宣言するだけで何もインポートしません。

## ルートツリーを軽く保つ [#keep-the-route-tree-light]

Worker は、プリレンダリング済みのページでも静的ファイルでもないすべてのリクエストを TanStack Start に渡し、Start はほかの何よりも先にルートツリーを読み込みます。これはレンダリングするページの場合も、サーバー関数の呼び出しの場合も同じです。ルートツリーとは、`src/routeTree.gen.ts` と、ルートファイルが静的にインポートするすべてのモジュールのことで、`/api/auth/$` のようなサーバールートのハンドラーも含みます。Worker のアイソレートは、そのような最初のリクエストでこれを評価し、サーバー関数は最初の呼び出しで自分のチャンクを読み込みます。どちらも訪問者がクライアント側のナビゲーションを待っている間に起こるため、それらがインポートするものはすべて、新しいアイソレートでの待ち時間の一部になります。

以前は、ドキュメントとブログのコレクションを最初からすべて読み込んでいました。`.source/server.ts` は、すべてのロケールのすべてのドキュメントページとブログ記事のコンパイル済み MDX をインポートしていました。これは各ページの見出しと検索用テキストを含む 1,305 個のモジュールです。さらに Lucide アイコンプラグインが、ドキュメントの meta ファイルが名前を挙げる数個のアイコンのために、アイコンセット全体を追加していました。ドキュメントのレイアウト、ドキュメントのページ、ランディングページ、ブログはサーバー関数を通じてこのソースを読み、`/api/search` はこれを静的にインポートしていたため、ソースがルートツリーに入っていました。saasyland.com では、`/` から `/docs` へのクライアント側のナビゲーションが 2 つのサーバー関数を待つ時間は、新しいアイソレートで約 1.3 秒、ウォームなアイソレートで約 25 ms でした。ランディングページとブログも、最初のナビゲーションで同じだけの時間がかかっていました。

コレクションを `async` にしたことで、ソースは各ページのフロントマターを保持し、リクエストがページの見出しや検索用テキストを必要とするときにだけ、そのページのコンパイル済み MDX をインポートするようになりました。`/api/search` も、自分のインデックスをハンドラーの中でインポートするようになりました。その後、次のセクションの変更で、コンテンツは Worker から完全になくなりました。`fumadocs.icons.ts` は meta ファイルが名前を挙げるアイコンだけをインポートします。meta ファイルがインポートされていないアイコンを指定した場合や、どの meta ファイルも指定していないアイコンがインポートされている場合、`fumadocs.icons.test.ts` は失敗します。

サイズは、`bun run build:test` の Worker で各部分が静的にインポートするものの合計です。時間は、ノート PC で交互に 5 回ずつ実行した中央値です。

| 指標                                                                                              | 変更前                     | 変更後                   |
| ------------------------------------------------------------------------------------------------- | -------------------------- | ------------------------ |
| ルートツリー（すべてのサーバーリクエストが読み込む）                                              | 1,635 モジュール、21.7 MiB | 296 モジュール、4.9 MiB  |
| ドキュメントのページツリーと `getDocsPage`（それぞれのインポートを含む）                          | 1,402 モジュール、16.9 MiB | 41 モジュール、1.3 MiB   |
| `dist/server` 内の JavaScript                                                                     | 4,275 ファイル、28.0 MiB   | 2,953 ファイル、26.8 MiB |

| 新しい `vp preview` の Worker で、`/` から `/docs` の見出しが表示されるまでの最初のナビゲーション | 260 ms                     | 198 ms                   |

ルートツリーがまだ読み込むものの大部分、約 3 MiB は Better Auth とそれがインポートするモジュールで、`/api/auth/$`、認証ページの検索パラメーターのスキーマ、CLI のライセンス API がこれを静的にインポートしています。

## Worker はドキュメントやブログのコンテンツを保持しない [#the-worker-holds-no-docs-or-blog-content]

上の変更の後も、Worker はドキュメントとブログをバンドルしていました。1,305 ページ分のコンパイル済み MDX で、27.5 MiB のアップロードのうち約 14.6 MiB を占めていました。これは `/api/search` のため、そしてブログ記事の目次と読了時間のために残されており、ドキュメント、ブログ、ランディングページのサーバー関数が読むフロントマターと一緒に置かれていました。新しいアイソレートでのリクエストは、コードが実行され始めるまでに 1〜2 秒待たされ、saasyland.com でのドキュメント内のクライアント側のナビゲーションは、新しいアイソレートで 1.3〜2.0 秒、ウォームなアイソレートで約 270 ms かかり、ドキュメントの検索には 9〜18 秒かかっていました。

現在は、ビルドのたびにコンテンツを、アプリが静的ファイルとしてインポートするデータに変換します。Vite プラグインである `scripts/content-indexes.ts` が、Vite のモジュールランナーで `fumadocs.indexes.ts` を読み込みます。`fumadocs.indexes.ts` は、コレクションのスキーマと Fumadocs の `loader` を使って `content/docs` と `content/blog` を読み、ロケールごとに次のものを作ります。

- ドキュメントのインデックス: ページツリーと、スラッグごとのページ。各ページはタイトル、説明、セクション、MDX ファイルを持ちます。
- ブログのインデックス: 公開済みの記事を新しい順に並べたもの。各記事はフロントマター、目次、読了時間を持ちます。
- 検索インデックス: Fumadocs がドキュメントページから書き出す検索データベース。ビルドはこれを `/assets/search-index-<locale>-<hash>.json` に書き出します。

`virtual:content-indexes` の `loadDocsIndex` と `loadBlogIndex` は、ロケールのドキュメントまたはブログのインデックスをインポートします。各インデックスは `/assets/` 配下にある専用のチャンクです。ドキュメントのレイアウトとページ、ブログとその記事、ランディングページはローダーでこれを読みます。ローダーは、クライアント側のナビゲーションではブラウザーで、プリレンダリング中はサーバーで実行されます。ページのコンパイル済み MDX は、これまでどおりブラウザー用のチャンクから読み込まれます。`run_worker_first` は `/assets/*` を Cloudflare の静的アセットに任せるため、ドキュメントやブログの中でのクライアント側のナビゲーションは Worker に一切リクエストしません。ドキュメントの検索は、最初のクエリでそのロケールのインデックスをダウンロードし、ブラウザーで検索します（[ドキュメントサイト](/docs/features/docs-site#search) を参照）。`/api/search` はなくなりました。

デプロイされた Worker は、すべてのドキュメントページとブログ記事をプリレンダリング済みのものとして配信します。そのため、`scripts/deployed-worker.ts` はコンパイル済みページのインポートをすべて、例外を投げる 1 つのモジュールに解決し、ビルドはそれらを 1 つもコンパイルしません。`scripts/verify-build.ts` は、デプロイされた Worker のいずれかのファイルがドキュメントやブログのモジュールを含む場合、検索インデックスのないロケールがある場合、またはあるロケールのインデックスがそのロケールのドキュメントページをそのタイトルで過不足なく含んでいない場合に、ビルドを失敗させます。

サイズは `bun run build:test` の Worker から、時間はプレビューデプロイから取ったものです。時間はヘッドレス Chromium で計測し、各サンプルは新しいアイソレートで取得して、その `cf-ray` で Worker のログと照合しました。

| ------------------------------------------------------------------------------------------------------------ | --------------------------------- | --------------------------------- |
| Worker のアップロード、`wrangler deploy --dry-run`                                                           | 30,115 KiB、gzip 圧縮後 7,201 KiB | 13,465 KiB、gzip 圧縮後 3,148 KiB |
| `dist/server` 内のファイル                                                                                   | 3,021                             | 1,590                             |
| デプロイされる Worker 内のコンパイル済みのドキュメントとブログのページ                                       | 1,341                             | なし                              |

| `/` から `/docs`、さらにドキュメントページへのクライアント側のナビゲーションで発生する Worker へのリクエスト | 2 (0.9〜2.6 秒)                   | なし                              |

`e2e/specs/content.spec.ts` は、ドキュメントとブログの中でのクライアント側のナビゲーションが静的ファイル以外に何もリクエストしないこと、そしてドキュメントの検索が、誰かが検索したときに初めてページのロケールのインデックスをダウンロードすることを確認します。

## 遅いナビゲーションはすぐにスケルトンを表示する [#a-slow-navigation-shows-its-skeleton-at-once]

`src/router.tsx` は、`src/data/navigation.constants.ts` の値を使って、`defaultPendingMs` を <RepositoryFact name="navigationPendingMs" unit="millisecond" /> に、`defaultPendingMinMs` を <RepositoryFact name="navigationPendingMinMs" unit="millisecond" /> に設定します。TanStack Router のデフォルトである 1 秒と 0.5 秒のままでは、遅いナビゲーションは丸 1 秒間、新しいアドレス以外に何も表示しませんでした。新しいアイソレートで **ドキュメント** を最初にクリックすると約 1.6 秒かかり、ドキュメントのスケルトンは 1 秒後にようやく表示されるか、まったく表示されませんでした。また、ルートに `pendingMs: Number.POSITIVE_INFINITY` が設定されていたドキュメントページ間のクリックでは、待っている間ずっと前のページが表示されたままでした。

- 遅延時間内に完了するナビゲーションは、次のページの準備ができるまで前のページを表示し続け、スケルトンを表示することはありません。saasyland.com では、ルーターがホバー時にプリロードしたページや、すでに読み込んだページへのナビゲーションは、クリックから 40〜115 ms で完了しました。ウォーム状態の Worker でセクションを初めて訪れる場合は、リクエストごとに 40 ms のレイテンシを加え、リンクにホバーせずにローカルで測定すると 184〜314 ms でした。遅延時間はどちらよりも長いため、どちらのナビゲーションでもスケルトンは表示されません。
- 遅延時間を過ぎてもまだ読み込み中のナビゲーションは、読み込みが続いている間だけルートのスケルトンを表示します。`defaultPendingMinMs` は <RepositoryFact name="navigationPendingMinMs" unit="millisecond" /> なので、ルーターはスケルトンを画面に留めておくことはせず、ページの準備ができた時点で取り除きます。
- ドキュメントのページには独自のスケルトン `DocsIndexPending` と `DocsPagePending` があり、サイドバーの横の記事と目次を埋めます。そのため、ドキュメントページ間の遅いナビゲーションでは、前のページをそのまま残すのではなく、次のページの形が表示されます。

`e2e/specs/content.spec.ts` は、`/docs` へのナビゲーションではドキュメントのインデックスを、ドキュメントページ間のナビゲーションではコンパイル済み MDX を保留し、それらが届くまで、それぞれがスケルトンを表示し、2 つ目ではサイドバーも表示することを確認します。これらのテストは先にデータセーバーを有効にし、クリックの前にヘッダーがドキュメントを読み込まないようにします。

## リクエストごとにレンダリングするページは遅いセクションをストリーミングする [#request-rendered-pages-stream-their-slow-sections]

管理画面、ワークスペース、コースのページは、リクエストごとに Worker でレンダリングされます。以前はこれらのローダーがすべてのクエリを await していたため、最も遅いクエリが応答するまで Worker からは何も送られませんでした。`/admin` と `/admin/products` では、それが表示のたびに Polar の API を呼び出す Polar の商品カタログでした。現在、各ローダーはレスポンスの最初の送信に必要なものだけを await し、残りは await せずに開始します。遅いセクションはそれぞれ、同じレスポンスの中でスケルトンへストリーミングされます（[ストリーミングされるセクション](/docs/conventions/routes#streamed-sections)）。

- `/admin` は、`DataGrid` が `useQuery` で読み取る最新のアカウントを await します。統計とパネルはそれぞれ専用の境界の中でストリーミングされるので、Polar を待つのは商品数だけです。
- `/admin/products` はグリッドをストリーミングします。
- `/app/billing` は注文とサブスクリプション、そしてそれらに依存する Polar のカスタマーポータルへのボタンをストリーミングします。
- レッスンはプレーヤーをストリーミングします。レッスンが再生可能だとローダーがわかった時点で、ストリームの署名を await せずに開始するので、タイトル、本文、目次は署名済みのストリームができる前に Worker から送られ、プレーヤーはそのスケルトンを埋めます。

`bun run start:test` が配信する `bun run build:test` のビルドで、ブラウザーのユーザーエージェントを使い、Cookie でサインインした状態で、ページとビルドごとに 10 リクエストを 3 ラウンド交互に実行して計測しました。テストビルドは Polar への呼び出しにメモリ上のテストダブルで応答します。今回の計測では、Polar の API との往復の代わりとして、応答のたびに 300 ms 待たせました。テストビルドの D1 はローカルです。最初のバイトは、TanStack Start がページの最初の部分と一緒に送るレスポンスヘッダーが届くまでの時間です。各セルは 3 ラウンドの中央値の中央値です。

| ページ            | 最初のバイト（変更前） | 最初のバイト（変更後） | ページ全体（変更前） | ページ全体（変更後） |
| ----------------- | ---------------------- | ---------------------- | -------------------- | -------------------- |
| `/admin`          | 403 ms                 | 83 ms                  | 419 ms               | 327 ms               |
| `/admin/products` | 361 ms                 | 43 ms                  | 370 ms               | 367 ms               |
| `/app/billing`    | 30 ms                  | 28 ms                  | 36 ms                | 35 ms                |
| レッスン          | 38 ms                  | 35 ms                  | 45 ms                | 44 ms                |

`/app/billing` とレッスンが読み取るのは、ここではローカルにある D1 だけなので、今回の計測では差が出ていません。Cloudflare 上では、これらの最初のバイトは、現在ストリーミングされるクエリをもう待ちません。遅延なしでは、どのページも変更前と変更後で同じ時間がかかり、差は実行ごとのばらつきの範囲内でした。完全に読み込まれたページは、英語とドイツ語の幅 1440 ピクセルと 390 ピクセルでピクセル単位まで同一で、各スケルトンはそれを置き換えるセクションと同じサイズを占めます。

クローラーは最初のレスポンスで、すべてのセクションが所定の位置にあるページ全体を受け取ります。TanStack Start は、`isbot` がユーザーエージェントを認識したリクエストには、すべてのセクションを待ってから応答し、router-core のパッチによって、ルーターがそれより前に React のストリームを読むことはありません（[依存関係](/docs/conventions/dependencies)）。`isbot` は `curl` や Bun と Node の `fetch` もクローラーとみなすため、ストリーミングを計測するスクリプトはブラウザーのユーザーエージェントを送る必要があります。

`src/routes/__test__/admin-products-loaders.test.ts` は、Polar のカタログを読み込んでいる間も `/admin` と `/admin/products` がレンダリングされることを確認します。`app-billing-routes.component.test.tsx` と `lesson-routes.component.test.tsx` は、データがストリーミングされている間、請求履歴とプレーヤーがスケルトンを表示し続けることを確認します。

## ヘッダーのページはクリックの前に読み込む [#the-headers-pages-load-before-a-click]

`defaultPreload: "intent"` は、ポインターがリンクの上に `defaultPreloadDelay`（<RepositoryFact name="navigationPreloadDelayMs" unit="millisecond" />、`src/data/navigation.constants.ts` の `NAVIGATION_PRELOAD_DELAY_MS`）のあいだ留まって初めて、そのリンクのコードとデータを読み込みます。素早いクリック、スマートフォンでのタップ、キーボード操作では、その時間は決して得られません。ルートツリーを軽くした後、saasyland.com で `/` から `/docs` の見出しまでのクライアントナビゲーションは、温まった Worker の isolate では 255〜283 ms、新しい isolate では 1.3〜2.0 秒かかっていました。ドキュメントの 2 つのサーバー関数が、isolate の起動を 1.1〜2.0 秒待っていたためです。

そこで `Navigation` は、表示中のページがアイドルになると、`HEADER_NAVIGATION` の各項目のページを TanStack Router を通じてプリロードします。新しい isolate はクリックの前に起動し、クリック時にはページのコードとデータがルーターのキャッシュにあります。エフェクトの中で各項目について `router.preloadRoute` を呼び出し、その呼び出しを `preloadWhenIdle` でスケジュールします。

```ts title="src/lib/idle-preload.ts"
const schedule = (preload: () => void, signal: AbortSignal): void => {
  if (dataSaverSchema.safeParse(navigator).success) {
    return
  }
  if (document.readyState === "complete") {
    whenIdle(preload, signal)
    return
  }
  globalThis.addEventListener(
    "load",
    () => {
      whenIdle(preload, signal)
    },
    { once: true, signal },
  )
}
```

- `preloadWhenIdle`（`src/lib/idle-preload.ts`）は `load` イベントを待ち、次に `requestIdleCallback` を待つので、プリロードがページ自身のリクエスト、Largest Contentful Paint、ハイドレーションと競合することはありません。Safari には `requestIdleCallback` がないため、そこでは `load` の <RepositoryFact name="idleFallbackDelayMs" unit="millisecond" /> 後まで待ちます。待機を取り消す関数を返し、その前にヘッダーがアンマウントされたりページが変わったりすると、エフェクトがそれを呼び出します。
- データセーバー（`navigator.connection.saveData`）を有効にした訪問者には何もプリロードしません。
- エフェクトは `shownPath`、つまりルーターの `resolvedLocation` から得た表示中のページのパスに依存するので、次のページがアイドルになるとヘッダーはもう一度プリロードし、サイトを見て回るあいだ自分のページを新しいまま保ちます。データがまだ新しいページは読み込み直しません。訪問の最初のページはビルド時にレンダリングされたものなので、ルーターはそのデータを古いとみなし、ヘッダーが別のページから初めてそれをプリロードするときに読み込み直します。
- ヘッダーのリンクに TanStack Router の `preload="viewport"` を付けると、リンクがビューポートに入った時点で始まります。固定ヘッダーは常にビューポート内にあるので、ハイドレーションと競合してしまいます。またスマートフォンではリンクがメニューの中にあり、メニューは開いたときに初めてリンクをレンダリングします。
- この方法でプリロードするのはヘッダーのリンクだけです。ドキュメントのサイドバーにある何百ものリンクをはじめ、ほかのリンクはすべて `defaultPreload: "intent"` のままです。
- セッションによってアカウントリンクの行き先が訪問者のワークスペース（`/admin` または `/app`）になると、そのエントリーはコードだけを読み込みます。一致する各ルートに `router.loadRouteChunk` を使います。以前はページをプリロードすると、そのワークスペースのガードとローダーが実行されていました。管理者の場合は、表示するすべてのページで、Polar のカタログを含むダッシュボード全体が読み込まれていました。**ログイン** を含め、`HEADER_NAVIGATION` が宣言するページを開くエントリーは、引き続きデータも読み込みます。`bun run build:test` のビルドで計測すると、サインイン済みのページがアイドルになるまでに送ったサーバー関数のリクエストは、`/` で管理者の場合 12 から 2 に、顧客の場合 4 から 2 に減りました。

`src/router.tsx` は `defaultPreloadStaleTime` を TanStack Router の TanStack Query ガイドが示す値 <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" /> にし、`defaultStaleTime` はルーターの既定値のままにしています。そのため何が新しいかを決めるのは TanStack Query だけで、プリロード後のクリックはページの loader をもう一度実行し、loader はプリロードがクエリキャッシュに入れたものを読みます。以前はドキュメントとブログの loader が TanStack Query の外でサーバー関数を呼んでいたので、ルーターはプリロードしたページをクエリの stale time のあいだ保持していました。今はこれらの loader がビルド時のインデックスを読み込み、ブラウザーは一度読み込んだインデックスを保持するので、その必要はありません。`bun run build:test` のビルドでリンクにホバーしてからクリックしたところ、講座、ブログ、ドキュメント、管理コンソールのどのページでも、サーバー関数の呼び出しはどちらの設定でも同じでした。最初のホバーではページのクエリに応じて 1 回か 2 回、2 回目のホバー、クリック、戻る操作では 0 回です。

preview.saasyland.com で、実行ごとに新しいブラウザーを使って計測しました。各実行は `/` を読み込み、ネットワークが静かになってからさらに 2 秒待ち、**ドキュメント** をクリックします。Cloudflare は 1 つのブラウザーのリクエストを複数の isolate に振り分けるため、変更前はほとんどの実行が新しい isolate に当たりました。各セルは中央値と、括弧内に範囲を示します。

| 指標                                                                                              | 変更前                 | 変更後         |
| ------------------------------------------------------------------------------------------------- | ---------------------- | -------------- |
| クリックからドキュメントの見出しまで（ドキュメントのサーバー関数が新しい isolate に当たった場合） | 1,287 ms (1,116–2,137) | 87 ms (67–145) |
| クリックからドキュメントの見出しまで（どちらも温まった isolate に当たった場合）                   | 194 ms (177–208)       | 96 ms (91–101) |
| クリックが待つサーバー関数のリクエスト                                                            | 2                      | 0              |

ホームページは遅くなっていません。`bun run build:test` のビルドを圧縮付きの HTTP/2 プロキシの背後に置き、`/` で Lighthouse を実行した結果で、ビルドごとに 13 回、半分ずつ順序を入れ替えて実行した中央値です。

| 指標                                    | 変更前   | 変更後   |
| --------------------------------------- | -------- | -------- |
| モバイルの Largest Contentful Paint     | 1,546 ms | 1,538 ms |
| モバイルの Total Blocking Time          | 12 ms    | 12 ms    |
| デスクトップの Largest Contentful Paint | 729 ms   | 728 ms   |
| デスクトップの Total Blocking Time      | 137 ms   | 136 ms   |

`e2e/specs/navigation.spec.ts` は、`/` と `/docs` でヘッダーのプリロードが終わるのを待ってから、すべてのサーバー関数を保留し、デスクトップとスマートフォンのメニューでヘッダーの各リンクをクリックします。それでも各ページは開きます。また、データセーバーを有効にした訪問者にはクリック前に何も読み込まないことも確認します。

TanStack Router 自体のデフォルトの遅延は 50 ms です。40 ms の遅延を加えた `bun run build:test` のビルドで、押す前にポインターを管理画面のサイドバーのエントリーに 75 ms または 150 ms 置き、セルごとに 20 回押して計測すると、押してからページが表示されるまでの中央値は、50 ms では 37 ms、現在の遅延では 40〜46 ms で、実行ごとのばらつき（12〜122 ms）の範囲内でした。一方、押さずにエントリーあたり 75 ms でサイドバーを下へ移動するポインターは、50 ms では 8 回、現在の遅延では 2 回のサーバー関数のリクエストを発生させました。遅延は現在の値のままにします。

## ローダーはルートのチャンクに置く [#loaders-stay-in-their-routes-chunk]

`vite.config.ts` は、各ルートのローダーを、そのコンポーネント、エラーコンポーネント、not-found コンポーネントと一緒に専用のチャンクへ分割します。TanStack Router のデフォルトでは、ローダーはルートツリーに残ります。ルートツリーに残すと、何もプリロードされていないナビゲーション（タップや、リンクの上で止まらないクリック）が往復 1 回分速くなりますが、すべてのローダーとそれがインポートするものがエントリースクリプトに入ります。`bun run build:test` のビルドを使い、データセーバーを有効にして 1 リクエストあたり 150 ms の遅延を加えた Chromium で、ビルドごとに 4 クリックのラウンドを交互に実行し、セルごとに 8〜12 クリックで計測しました。サイズは各ページが読み込むすべてのスクリプトの gzip 圧縮後の合計です。

| 指標                                               | ローダーを分割 | ローダーをルートツリーに置く |
| -------------------------------------------------- | -------------- | ---------------------------- |
| `/` の JavaScript                                  | 530.5 KiB      | 644.5 KiB                    |
| `/admin` の JavaScript                             | 644.6 KiB      | 762.5 KiB                    |
| `/` から `/courses` へのクリック（プリロードなし） | 649 ms         | 508 ms                       |
| 管理画面のサイドバーでのクリック（プリロードなし） | 515 ms         | 355 ms                       |

ルートツリーに置くと、プリロードが間に合わないクリックで往復 1 回分を節約するために、どのページも約 115 KiB 多く読み込むことになります。ヘッダーのページはすでにプリロードされているので、ローダーは分割したままにします。

## ガードはキャッシュ済みのセッションを再利用する [#guards-reuse-the-cached-session]

TanStack Router は、レイアウトの `beforeLoad` をその配下へのナビゲーションのたびに実行し、それが終わってからローダーを開始します。`requireSignedIn` と `requireAdmin` はこれまで `getCurrentSessionQuery` を `staleTime: 0` で読んでいたため、`/app` と `/admin` でのクリックはすべて、すでに開いたページに戻るときでさえ、ページ自身のリクエストが始まる前にセッションのリクエストを待っていました。saasyland.com では、管理画面のサイドバーでの 190〜300 ms のクリックのうち 60〜70 ms がこのリクエストでした。

いまのガードは、セッション自身の stale time である `SESSION_STALE_TIME_MS`（<RepositoryFact name="sessionStaleTimeMinutes" unit="minute" />）でセッションを読みます。新しいセッションならリクエストなしでナビゲーションを通し、古いセッションはページの読み込み前に再取得します。ガードが決めるのは訪問者に何を見せるかだけで、各サーバー関数は引き続き自分のリクエストのセッションを確認します（[認証とセキュリティ](/docs/architecture/security-model) を参照）。終了したセッションにもすぐ気づけるよう、`getRouter` は `QueryCache` と `MutationCache` に共通の `onError` を渡し、この `onError` が失敗をすべて `QUERY_ERROR_HANDLERS` の各ハンドラーに渡します。ハンドラーは認証機能の `recheckRefusedSession` だけです。サーバー関数が `UNAUTHORIZED` または `FORBIDDEN` を返すと、`recheckRefusedSession` がセッションを専用のキャッシュエントリに取得し、ユーザーまたはロールが変わっていれば、キャッシュ済みのセッションを古いものとして印を付け、`router.invalidate()` でガードを再実行します。ガードは訪問者を、セッションが終了したことを伝えてサインインへ、元管理者なら `/app` へ送ります。セッションが変わっていなければページはそのままなので、拒否がループすることはありません。

`bun run start:test` で配信した `bun run build:test` のビルドで、Chromium でリクエストごとに 40 ms の遅延を加え、シードの管理者としてサインインし、ビルドごとに 5 回の実行を 2 ラウンド交互に行って計測しました。各実行は `/admin` を開き、サイドバーの各項目を 2 回ずつ開きました。押す前にポインターを項目上に 250 ms 置き、クリックは押してから、ルーターがページをレンダリングした後の最初のフレームまでを計りました。各セルはすべての項目の中央値と、括弧内に範囲を示します。

| 指標                               | 変更前                      | 変更後                     |
| ---------------------------------- | --------------------------- | -------------------------- |
| 押してからページまで（初回）       | 209 ms (83–1,206)           | 156 ms (41–647)            |
| 押してからページまで（再訪）       | 68 ms (49–406)              | 18 ms (11–56)              |
| クリックごとのセッションリクエスト | 1、**User Management** は 2 | セッションが新しい間はなし |
| 再訪が待つサーバー関数のリクエスト | 1–2                         | 0                          |

`e2e/specs/admin-navigation.spec.ts` は、コンソールの各ページが 2 回目はリクエストなしで開くこと、そして別の場所で終了したセッションが、それを拒否した最初のサーバー関数でサインインにつながることを確認します。

## ヘッダーはスクリプトより先にセッションを知る [#the-header-knows-the-session-before-its-scripts]

公開ページはすべてプリレンダリングされるため、その HTML は誰が読んでいるかを知ることができません。以前は、ページがスクリプトを読み込み、ハイドレートし、セッションを問い合わせた後になって初めて、ヘッダーの **ログイン** リンクが **マイアカウント** に変わり、幅の広いラベルが **料金**、**講座**、**ブログ**、**ドキュメント** を横に押し出していました。一度でもサインインしたことのあるブラウザは、ページを表示するたびにセッションを問い合わせていました。判定に使っていたのが、サインアウト後も残る Better Auth の前回使用したサインイン方法の Cookie だったためです。

現在は、HTML が Worker を出る前に Worker がラベルを決めます。`markSession` は、リクエストにセッション Cookie がある場合に `<html>` に `data-session` を設定します。見るのは Cookie があるかどうかだけで、データベースは読みません。リンクは両方のラベルを持ち、CSS が印に応じたほうだけを表示するため、リンクの幅は表示中のラベルと同じになり、隣のリンクとの間隔もヘッダーのほかのリンクと同じです。セッションのリクエストは印の付いたページでだけ実行され、セッションが終わった Cookie はその最初のリクエストで削除されるため、次のページには印が付きません（[パスとナビゲーション](/docs/conventions/routes#paths-and-navigation) と [キャッシュと SSR](/docs/architecture/caching-and-ssr#prerendering) を参照）。この変更を加えたプルリクエスト #405 で、Worker のコールドスタートは 702 バイト増えて 38,292 バイトになりました。

1 台のマシンで `vp preview` が配信する `bun run build:test` のビルドを使い、Chromium を 1440 × 900、データセーバー有効の状態で計測しました。こうすることで、サーバー関数に届くのはセッションのリクエストだけになります。2 つのビルドを、`/`、`/docs`、`/blog` のそれぞれで 2 回の実行を 2 ラウンド交互に行い、セルごとに 12 回のページ表示を計測しました。ラベルが正しいのは、正しいテキストでヘッダーを表示した最初のフレームからです。中央値を先に、範囲を括弧内に示します。

| 指標                                                             | 変更前                    | 変更後                           |
| ---------------------------------------------------------------- | ------------------------- | -------------------------------- |
| サインイン済み: ラベルが正しくなるまで、通常の CPU               | 684 ms (438–2,863)        | 69 ms (52–101)、最初のフレーム   |
| サインイン済み: ラベルが正しくなるまで、CPU を 4 倍低速化        | 1,206 ms (1,021–1,753)    | 162 ms (114–391)、最初のフレーム |
| サインイン済み: 動くヘッダーのリンク                             | どのページ表示でも 4      | なし                             |
| サインイン済み: レイアウトシフト                                 | どのページ表示でも 0.0004 | 0                                |
| ページ表示ごとのセッションリクエスト、サインイン後にサインアウト | 1                         | 0                                |
| ページ表示ごとのセッションリクエスト、サインイン済み             | 1                         | 1                                |
| ページ表示ごとのセッションリクエスト、別の場所でセッション終了   | どのページ表示でも 1      | 最初に 1、その後は 0             |

別の場所でセッションが終わったブラウザは、確認の応答が返るまで **マイアカウント** を表示し（通常の速度で 405 ms (292–611)）、その後 **ログイン** を表示します。ラベルは状態がわかった時点で実際の状態を示し、そのページ表示でだけ、前にあるリンクが 2 つのラベルの幅の差だけ一度動きます。Lighthouse 13 を `/` で、Brotli 付きの HTTP/2 プロキシの背後に置き、CPU を 7 倍低速化したデスクトッププリセットで実行しました。セルごとに 4 回実行した中央値で、負荷の急増があった 2 回は除いています。セッション Cookie がある場合、First Contentful Paint は変更前 453 ms、変更後 403 ms、Largest Contentful Paint は 871 ms と 867 ms、Total Blocking Time は 218 ms と 226 ms、Cumulative Layout Shift はどちらも 0 です。Cookie がない場合とモバイルプリセットでは、どの指標も実行ごとのばらつきの範囲内に収まりました。

`e2e/specs/header-session.spec.ts` は Chromium と WebKit で次のことを確認します。スクリプトが動く前にページが正しいラベルを表示すること。英語とポーランド語で、サインアウトしたページでもサインイン済みのページでも読み込み中にヘッダーのリンクが動かず、アカウントのリンクと隣のリンクの間隔がほかのリンク同士と同じであること。サインアウトしたブラウザがセッションを問い合わせないこと。終わったセッションではラベルが **ログイン** に戻ってサインアウトしたページと同じ配置になり、それ以上問い合わせないこと。**マイアカウント** の押下が、スクリプトの実行前でもセッションの読み込み中でもワークスペースに届くこと。

## React Aria のリンクもルーターのリンクと同じようにプリロードする [#react-aria-links-preload-like-router-links]

`defaultPreload: "intent"` は TanStack Router の `<Link>` の機能です。サイドバー、`LinkButton`、その他のリンクボタンは React Aria の `RouterProvider` 経由で遷移する React Aria の `Link` だったため、ポインターを置いても何も読み込まれず、クリックはページのコードとサーバー関数を待っていました。現在の `LinkButton` は `createLink(AnchorButton)`、`SidebarMenuLink` は `createLink(SidebarMenuButton)` で、TanStack Router が React Aria Components 向けに説明している方法です。`params` と `search` を伴う `to` を受け取り、`<Link>` と同じように意図、フォーカス、タッチでプリロードします。ルートツリーの外のアドレスには `AnchorButton` を使います。`/admin/users` のタブである `TabsLink` は、ポインターがタブの上に止まったときやタブにフォーカスが移ったときに `router.preloadRoute` を呼び、`AdminCommandPalette` の結果もポインターが上に止まったときに同じことをします。

上と同じ計測で、ビルドごとに 5 回の実行を 1 ラウンド行い、押す前にサイドバーの各項目にポインターを 250 ms 置きました。

| 指標                         | 変更前          | 変更後        |
| ---------------------------- | --------------- | ------------- |
| 押してからページまで（初回） | 128 ms (38–270) | 34 ms (16–91) |
| 押してからページまで（再訪） | 16 ms (14–34)   | 16 ms (9–33)  |

## ORM をブラウザーに入れない [#keep-the-orm-out-of-the-browser]

Drizzle は Worker の中だけで動きます。ブラウザーには、フォームのためにモジュールの Zod スキーマが、セレクトフィールドのために enum のタプルが必要です。そのため、どちらも Drizzle から何もインポートしないファイル、`<table>.zod.ts` と `<table>.constants.ts` に置きます（[モジュール](/docs/conventions/modules)を参照）。ブラウザー側のインポートが `<table>.schema.ts` に到達すると `sqliteTable(...)` が実行されます。バンドラーはこの呼び出しを取り除けないため、`drizzle-orm` も一緒に読み込まれます。

以前の `<table>.zod.ts` は、`drizzle-zod` を使ってテーブルから `insert`、`select`、`update` のスキーマも組み立てていましたが、実行時にそれらを読むものはありませんでした。`drizzle-zod` は zod の名前空間全体を保持するため、バンドラーは zod のすべてのロケール、JSON Schema への変換器、コンパイラーまで残していました。`/admin` と `/app` の読み込み中のスケルトンは `preferences-card.tsx` から `PreferencesCardPending` をインポートしていて、このファイルは `user.zod.ts` をインポートしていました。ペンディングコンポーネントはコード分割されないため、これらすべてがすべてのページで読み込まれていました。タプルを定数に移し、これらのスキーマを削除したことで、すべてのページで gzip 圧縮後の JavaScript が約 75 KiB 減りました。以下のサイズは、各ページが読み込むすべてのスクリプトを gzip で圧縮した合計で、`bun run build:test` の出力から取ったものです。

| ページ         | 変更前    | 変更後    |
| -------------- | --------- | --------- |
| `/`            | 526.2 KiB | 450.7 KiB |
| `/docs/<page>` | 612.1 KiB | 536.5 KiB |
| `/blog`        | 487.2 KiB | 411.7 KiB |
| `/app`         | 496.6 KiB | 421.0 KiB |
| `/admin`       | 515.0 KiB | 439.4 KiB |

`vite.config.ts` は、TanStack Start のインポート保護によって、クライアント環境での `drizzle-orm` のインポートを禁止しています。

```ts title="vite.config.ts"
const SERVER_ONLY_PACKAGES = [/^drizzle-orm(?:\/|$)/u]
```

そのインポートがツリーシェイキング後も残るビルドは失敗し、ルートから Drizzle に到達したファイルまでのインポートの連鎖を出力します。連鎖はその起点で断ち切ってください。タプルはモジュールの定数からインポートするか、コードをサーバー関数に移します。型のみのインポートは消去されるため、対象になりません。

## メッセージはページが必要とするときに読み込む [#load-messages-when-a-page-needs-them]

訪問者が最初に開くページは、ブラウザーでメッセージファイルを 1 つも読み込みません。root ルートとマッチしたルートがサーバー上で名前空間をクエリキャッシュにプリロードし、TanStack Start がそのキャッシュを HTML と一緒に送るからです。ブラウザーが名前空間を読み込むのは、後のナビゲーションでキャッシュにまだない名前空間が必要になったときだけです。

`import.meta.glob` はメッセージファイルごとに専用のチャンクを作りますが、各ファイルからチャンクへの対応表は、すべてのロケールのすべての名前空間を含み、glob を呼び出すモジュールに入ります。そのモジュールは root ルートがインポートする `i18n.messages.ts` で、メッセージ用とページメタデータ用に対応表を 2 つ持っていたため、どのページも約 240 KiB、gzip 圧縮後で 21 KiB のローダーを読み込んでいました。対応表は現在 `i18n.loaders.ts` に単独で置かれ、`loadNamespace` が最初に名前空間を読み込むときにインポートします。

```ts title="src/integrations/use-intl/i18n.messages.ts"
const { MESSAGE_LOADERS } = await import("~/src/integrations/use-intl/i18n.loaders")
```

`loadPageMetadata` は 2 つ目の対応表ではなくページの名前空間から `metadata` を読むため、ページの head とメッセージは同じチャンクから来ます。ブラウザーは `i18n.loaders.ts`（gzip 圧縮後で約 11 KiB）を、ナビゲーション時またはホバーによるプリロード時に、最初に読み込む名前空間と一緒に取得します。root 名前空間は引き続き `i18n.messages.ts` でファイル名から見つけられ、その glob のキーは gzip 圧縮後で約 2 KiB です。各ページが読み込むすべてのスクリプトの gzip 圧縮後のサイズ（`bun run build:test` の出力より）：

| ページ         | 変更前    | 変更後    |
| -------------- | --------- | --------- |
| `/`            | 462.9 KiB | 442.3 KiB |
| `/docs/<page>` | 553.5 KiB | 532.9 KiB |
| `/blog`        | 424.6 KiB | 404.0 KiB |
| `/app`         | 430.4 KiB | 409.7 KiB |
| `/admin`       | 452.8 KiB | 432.2 KiB |

メッセージは `loadNamespace` 経由でのみ読み込み、root ルートがインポートするモジュールに `messages/` を対象とする `import.meta.glob` を追加してはいけません。`scripts/verify-build.ts` はブラウザーのエントリースクリプトの静的インポートをたどり、ページ名前空間のローダーが含まれているとビルドを失敗させます。

## プリレンダリングされたページは CSS とフォントを先に読み込む

公開ページはプリレンダリングされており、最初の描画に JavaScript を必要としません。TanStack Start は、ページが必要としうるすべてのチャンクに対して `modulepreload` ヒントを出力し、ランディングページではその数が 100 を超えます。シミュレートされたモバイルネットワークでは、これらがスタイルシートやフォントと帯域を奪い合います。すべてのビルドスクリプトが実行する `scripts/optimize-prerendered-html.ts` は、依存関係のヒントをすべて削除し、ページ自身のエントリースクリプトのヒントだけを `fetchpriority="low"` で残します。

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

ヒントを削除したことで First Contentful Paint は約 3 分の 1 短くなり、エントリーのヒントを低い優先度で残したことで、モバイルの First Contentful Paint がさらに 375 ms 短くなりました。依存関係のものでもルートのチャンクのものでも、プリロードヒントを戻してはいけません。このスクリプトは、削除するヒントや残すヒントが見つからない場合にビルドを失敗させます。そのため、ビルド出力が変わっても、この最適化が気づかないうちに元に戻ることはなく、確実に検出されます。

TanStack Start は現在すべてのヒントを `fetchpriority="low"` で出力するため、2026 年 11 月にランディングページでこのルールを測り直しました。各バリアントで交互に 5 回ずつ実行しています。156 個のヒントをすべて残すと、ブラウザーはページのチャンクを 11 回ではなく 1 回の波で取得し、CLI コンフィギュレーターのハイドレーションはデスクトップで 250 ms、スロットリングしたスマートフォンで 315 ms 早まりましたが、First Contentful Paint はデスクトップで 68 ms、モバイルで 77 ms 遅くなりました。ヒントは引き続き削除します。

スクリプトのポリシーもこの順序を保ちます。Worker は、すべてのプリレンダリングされたページを `withNonce` に通してストリーミングします。この `HTMLRewriter` は、エントリーの `<script type="module">` とそのヒントにレスポンスの nonce を追加するだけで、ほかには何も変更しません。そのため、head にあるヒントは引き続き低い優先度でダウンロードを開始し、モジュールも引き続き、パーサーが body の終わりに達した時点で実行されます。書き換えはストリーミングで行われるので、バイトを溜め込むことはありません。ただし、HTML レスポンスには `ETag` が付かないため、ブラウザーはページを再検証せずに、もう一度ダウンロードします。

`robots.txt` と `llms.txt` は `public/` にある静的ファイルで、Worker を経由しません（`run_worker_first` の `"!/robots.txt", "!/llms.txt"`）。Lighthouse はどちらも 2 秒のタイムアウトで取得するため、Worker の応答が遅いと SEO とエージェント対応の監査で不合格になっていました。

## Early Hints にはデプロイ後も残るファイルだけを並べる

HTML レスポンスに付く Worker の `Link` ヘッダーには、ロケールのフォントだけを並べます。Cloudflare はこのヘッダーを URL ごとに保存し、その URL への次のリクエストに Worker が応答する前に `103 Early Hints` レスポンスとして送ります。保存されたコピーはデプロイ後も残ります。Vite はスタイルシートに内容から決まる名前を付けるので、CSS が少しでも変わるデプロイの後は、ヒントに載ったスタイルシートはもう存在しないファイルです。ブラウザーは 404 をダウンロードし、結局は HTML から新しいスタイルシートを見つけます。`public/fonts` のファイルは、デプロイをまたいでも同じ名前のままです。

saasyland.com で Chromium を使い、3 ページでバリアントごとに 15 回ずつ交互に実行し、エッジの実際の Early Hints のタイミングで測定しました。フォントをヒントに載せると、First Contentful Paint は 168–208 ms から 144–164 ms に下がりました。スタイルシートのヒントは、URL が最新のときはさらに 12–28 ms 短縮しましたが、デプロイで置き換わった後は何も短縮しませんでした。デプロイの 25 分後、Early Hints を受け取ったサイトマップの 91 ページのうち 67 ページが、まだ前のスタイルシートをヒントに載せていました。スタイルシートの `<link>` はどのページでも最初の 1 キロバイトにあるので、ブラウザーは HTML の最初のバイトでそれを見つけます。ヒントには、デプロイ後も URL が変わらないファイルだけを載せてください。

## プロバイダーはルートの outlet を包まない

TanStack Router はルートの outlet を Suspense 境界で包み、React はそれらの境界を後から小さな単位で少しずつハイドレーションします。その上にあるコンテキストプロバイダーの値がハイドレーション直後に変わると、React はその下にあるすべてを一度にハイドレーションせざるを得なくなります。

- アプリケーション全体を包む `ThemeProvider` によって、ランディングページのハイドレーションが、入力をブロックする 200 ms の 1 つのタスクになっていました。利用する 2 つのコンポーネント、`Toaster` とドキュメントの `ThemeSwitch` の周りにマウントしたところ、Total Blocking Time は約 150 ms から 10 ms 未満になりました。
- ルートの outlet の上にある `MotionProvider` は、アニメーション機能の読み込みが終わると新しいコンテキストを公開します。ブログ記事では、ページがまだコンテンツを読み込んでいる最中にその更新が届き、React がクライアントレンダリングにフォールバックして、レイアウトがずれました。

`__root.tsx` やレイアウトにプロバイダーを追加する前に、その値がハイドレーション後に変わりうるかを確認してください。変わりうる場合は、すべてのルートの `<Outlet />` より下で、それを読み取るコンポーネントのそばにマウントします。配置の一覧は[コンポーネントとスタイリング](/docs/conventions/components)にあります。

## ハイドレーションが重いウィジェットには専用の境界を与える [#a-widget-that-is-heavy-to-hydrate-gets-its-own-boundary]

ランディングページの CLI コンフィギュレーターは 40 個の React Aria ボタンを描画し、それぞれが押下、ホバー、フォーカスのフックを持ちます。ページの残りと一緒にハイドレーションすると、それらのエフェクトによってページのハイドレーションを締めくくるコミットが Lighthouse のデスクトップのスロットリングで 70〜100 ms のタスクになり、Total Blocking Time が 101 ms から 147 ms に上がりました。`CliSection` は `CliConfigurator` を、決してサスペンドしない `Suspense` 境界で包みます。React はこのような境界をページの残りの後に単独でハイドレーションし、別のコミットで確定するため、長いタスクはなくなり、Total Blocking Time は 100 ms になりました。First Contentful Paint と Largest Contentful Paint は変わりません。コンフィギュレーター自体のハイドレーションは約 50 ms 遅くなります。ほかのウィジェットに専用の境界を与えるのは、比較で同じ長いタスクが確認できたときだけにしてください。

## スケルトンはエントリースクリプトに残す [#skeletons-stay-in-the-entry-script]

TanStack Router はデフォルトでは `pendingComponent` を専用のチャンクに分割せず、`vite.config.ts` もこのデフォルトを保っています。そのため、すべてのスケルトンはエントリースクリプトに含まれ、ナビゲーションが `pendingMs` を超えた瞬間に表示されます。分割は計測したうえで採用しませんでした。

- 計測した時点では、レイアウトのスケルトン `AdminPending`、`AppPending`、`MarketingPending` は、すべての機能のスケルトンをインポートするリストからページのスケルトンを描画していました。ルーターはページのハイドレーション前に、マッチしたルートの読み込み中コンポーネントを読み込みます。`/`、`/app`、`/admin` は分割後も、専用のチャンクとしてすべてのスケルトンを読み込み、gzip 圧縮後で 3.5〜6.5 KiB 増えました。軽くなったのは、`/docs` や `/blog` のように、レイアウトが独自のスケルトンを持つページだけでした。
- 分割したスケルトンは、読み込まれるまで表示できません。ヘッドレス Chromium で 400 ms の遅延と 200 KiB/s を加えると、`/` から `/blog` へのクライアント側のナビゲーションでブログが表示されるまで 1,390 ms ではなく 2,290 ms かかり、その間、分割しないビルドでは一度も必要なかったスケルトンが表示されました。遅延が 150 ms の場合は 640 ms ではなく 800 ms でした。

すべてのページがすべてのスケルトンを読み込むため、スケルトンがインポートするのは `Skeleton`、shadcn のプリミティブ、他のスケルトン、長さを決める定数だけで、フォームは決してインポートしません。`PreferencesCardPending` は `preferences-card.tsx` からエクスポートされていたため、`/admin` と `/app` のスケルトンが、設定フォーム、TanStack Form、タイムゾーンの一覧、ユーザーのスキーマをすべてのページのエントリースクリプトに持ち込んでいました。現在は専用のファイル `preferences-card-pending.tsx` にあります。各ページが読み込むすべてのスクリプトの gzip 圧縮後のサイズ（`bun run build:test` の出力より）：

| ページ         | 変更前    | 変更後    |
| -------------- | --------- | --------- |
| `/`            | 463.0 KiB | 451.9 KiB |
| `/docs/<page>` | 553.6 KiB | 527.3 KiB |
| `/blog`        | 424.7 KiB | 413.6 KiB |
| `/app`         | 430.4 KiB | 404.1 KiB |
| `/admin`       | 452.9 KiB | 427.7 KiB |

`/` と `/blog` の削減量が小さいのは、レイアウトがニュースレターのフォームを描画しており、いずれにしても TanStack Form が必要だからです。`pending-imports.test.ts` はすべての `*-pending.tsx` のインポートをたどり、いずれかが `@tanstack/react-form`、`@tanstack/react-table`、`recharts` に到達するとテストを失敗させます。管理ダッシュボードのパネルは 1 つのリストでスケルトンとコンポーネントを組にしており、スケルトンはそのリストから描画されていたため、パネルのグラフと表はすべてのページで読み込まれていました。現在のリストは各パネルのスケルトンとクエリだけを指定し、パネルはダッシュボードと一緒に読み込まれます（[操作できるセクションはページと一緒に読み込む](#a-section-with-controls-loads-with-its-page)を参照）。エントリースクリプトがインポートするスクリプト（gzip 圧縮後、`bun run build:test` の出力から）:

| エントリースクリプトと静的インポート | 557.8 KiB | 410.9 KiB |
| ファイル数                           | 176       | 172       |

顧客向け概要のセクションは、そのリストで今もスケルトンとコンポーネントを組にしているため、それらのコンポーネントはスケルトンと一緒に読み込まれます。

## 操作できるセクションはページと一緒に読み込む [#a-section-with-controls-loads-with-its-page]

React がページをハイドレーションする前に、ルーターは一致したルートのチャンクを読み込みます。`@tanstack/router-core` の `hydrate` は、各ルートのコンポーネントとペンディングコンポーネントを待ちます。ページが React の `lazy` や `lazyRouteComponent` で指定したコンポーネントはこれに含まれないため、フルロードではハイドレーション中に React がそこへ到達して初めてチャンクが要求されます。そのチャンクが届くまで、React は最も近い `Suspense` 境界をサーバーの HTML のまま残し、その上の押下をすべて捨てます。境界がハイドレーションされた後に押下を再生することもありません。管理ダッシュボードのパネルはこの方法で読み込まれており、最も近い境界はルート自身のものだったため、パネルのチャンクが届くまで、コンソールのレイアウトより下のダッシュボード全体がクリックを無視していました。コースのプレーヤーも専用の境界の中でこの方法で読み込まれていたため、プレーヤーのチャンクが届くまで再生ボタンは何もしませんでした。

そのため、ボタン、リンク、入力欄、表を持つ部分は、それを描画するページがインポートし、押下を受けない部分だけを専用の `Suspense` 境界の中で遅延読み込みにします。`source-layout.test.ts` は、`src/presentation` または `src/routes` のファイルが `lazy` や `lazyRouteComponent` で読み込むすべてのモジュールをたどり、いずれかが React Aria、ルーター、TanStack Form、TanStack Table、動画プレーヤーに到達すると失敗します。スケルトンがリストから各部分を描画する場合、そのリストにはスケルトンとローダーが必要とするものだけを入れます。`panels-pending.tsx` の `DASHBOARD_PANELS` は各パネルの `key`、スケルトン、`prefetch` を指定し、`panels.tsx` はそれらのキーで型付けした `Record` で各キーにパネルを対応させます。そのため、項目のないパネルやパネルのない項目は型チェックで失敗します。コースページのスケルトンは、プレーヤーのスケルトンを `player-pending.tsx` から取ります。ダッシュボードのコンポーネントは `panels.tsx` を、レッスンのコンポーネントはプレーヤーをインポートするため、それらの操作部品はハイドレーションの前にページ自身のチャンクと一緒に届き、スケルトンは以前と同じく軽いままです。

遅延読み込みのまま残すのは、ダッシュボードのグラフの描画だけです。Recharts をダッシュボードのチャンクに含めると、ブラウザーはハイドレーションの前に、ダッシュボードのコードと同じ長いタスクの中でそれを評価し、`/admin` のフルロードは描画を専用のチャンクに分けた場合より 98 ms 長くメインスレッドをブロックしました（CPU を 6 倍に遅くした Chromium、交互に 6 回読み込んだ中央値）。現在の `TimeSeriesChart` は値の表をパネルと一緒に描画し、棒グラフ（`time-series-bars.tsx` の `TimeSeriesBars`）だけを専用の境界の中で `lazyRouteComponent` によって読み込み、ダッシュボードのローダーがデータと一緒にプリロードします。期間のボタンと通貨のタブは最初の瞬間から効き、まだ届いていない描画は、チャンクが届いた時点で押下に追いつきます。

`e2e/specs/admin-dashboard.spec.ts` のテスト「a press on a dashboard panel right after a full load hydrates the console takes effect, however late the scripts arrive」は、すべてのスクリプトを遅らせて `/admin` を読み込み、コンソールのサイドバーがハイドレーションされた瞬間に売上パネルの 12 か月を押し、パネルが切り替わることを確かめます。遅延読み込みのパネルでは失敗し、現在は成功します。以下は、`bun run build:test` の出力から求めたエントリースクリプトと静的インポート（gzip 圧縮後）、CPU を 7 倍に遅くした Lighthouse のデスクトップのプリセットで交互に 5 回ずつ実行した中央値、そして CPU を 6 倍に遅くした Chromium がフルロード中に記録した長いタスクがメインスレッドをブロックした時間（`/admin` は 12 回、レッスンは 7 回読み込んだ中央値）です。Lighthouse のシミュレーションは `/admin` の Total Blocking Time を高く見積もりますが、Chromium が記録する長いタスクがメインスレッドをブロックする時間は短くなっています。

## Tailwind のビルドは 1 つ

Tailwind を実行するのは `src/presentation/styles/globals.css` だけです。`docs.css` や `typeset.css` のようなルートのスタイルシートは素の CSS で、Fumadocs 自身のスタイルは `globals.css` を通して読み込みます。

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

以前、ルートのスタイルシートで 2 つ目の Tailwind ビルドを行った結果、独自の `.hidden`、`.rounded-md`、テーマ変数が出力されたことがあります。同じ名前のカスケードレイヤーはスタイルシートをまたいでマージされ、React は `precedence` 付きで挿入したスタイルシートを決して削除しません。そのため、ドキュメントを一度訪れると、ランディングページはリロードするまでレスポンシブなレイアウトとフォントを失いました。`e2e/specs/landing.spec.ts` の E2E テスト「landing keeps its responsive styles after visiting the docs」がこれを防いでいます。Tailwind が必要なものはすべて `globals.css` を通します。

## メディア

- **ランディングページのループ動画。** 各 `src/presentation/assets/motion/<name>.webm` には、動画とまったく同じ寸法のポスター `<name>.webp` があるため、ポスターから動画に切り替わるときに画像が目に見えて鮮明になることはありません。寸法は `src/data/landing-videos.ts` の `LANDING_VIDEO_SIZES` で、Remotion のコンポジションと `ConceptLoop` の両方がこれを読み取ります。より小さい幅は別ファイルの `<name>-<width>.webp` で、ポスターの `srcSet` を通して提供します。ポスターのサイズがそのコンポジションやファイル名の幅と異なると、`landing-videos.test.ts` が失敗します。フルサイズのポスターを縮小してはいけません。軽くしたい場合は、同じ寸法で再エンコードします。動画は `preload="none"` で読み込み、4 分の 1 が表示されている間だけ再生し、モーションを減らす設定の読者には決して再生しません。ヒーローのループはフェードインせずにせり上がります（`animate-rise` に `--rise-opacity: 1`）。デスクトップ画面ではそのポスターがファーストビューで最大の要素であり、透明からフェードインするポスターはフェードが始まって初めて描画されたと数えられるためです。
- **コースツアー**（`course-showcase.tsx`）はループ動画ではありません。`<video>` は訪問者が再生を押してから初めてレンダリングされるため、それまでページが読み込むのはポスターだけです。ポスターは、動画と同じ 1600 ピクセル幅と 800 ピクセル幅の AVIF と WebP のソースを持つ `<picture>` です。動画そのものは WebM で配信し、MP4 をフォールバックにしています。
- **コースの動画**は、事前にアダプティブ HLS にエンコードし、Workers のキャッシュを使って R2 から配信します。[動画](/docs/features/videos)を参照してください。
- **スクロールに連動する動画。** 現在のサイトにはありません。再生位置がスクロール位置に追従する動画は、オールイントラ（すべてのフレームをキーフレームにする、`keyint=1`）でエンコードしなければなりません。通常のエンコードではシークに約 200 ms かかりますが、オールイントラでは約 3 ms です。200 ms かかるシークは、JavaScript でどれだけ滑らかにしてもスクラブ再生にはなりません。

## スクロールで表示する

`Reveal`（`src/presentation/components/custom/landing-page/components/reveal.tsx`）は、ランディングページのセクションがビューポートに入るとフェードインさせます。すべてのインスタンスで 1 つの `IntersectionObserver` を共有し、オブザーバーの最初のコールバックで要素がファーストビューより下から始まるかを判断し、React の状態も再レンダリングも使わずに `data-reveal` 属性を直接書き込みます。表示状態を React の状態に保持していたバージョンでは、すべてのセクションが再レンダリングされてページのレイアウトが 2 回行われたため、Total Blocking Time が 2 倍になりました。状態に戻してはいけません。また、比較せずに置き換えてもいけません。

ほかに 2 つの最適化を計測し、不採用にしました。ランディングページのセクションに `content-visibility: auto` を指定する方法は、ページ下部のセクションへのページ内リンクを壊しました。ニュースレターのフォームを遅延読み込みする方法は、直接描画する場合と同じか、より悪いスコアでした。

## 後から届く内容は大きさを保つ

プリレンダリングされたページはスクリプトが動く前に描画されるため、後から中身が入るセクションは、与えられた場所に収まらなければなりません。ランディングページのコースブロックがその一つです。スクロールで近づくと公開済みのコースを読み込みますが、以前のプレースホルダーは 6 レッスンのコースが 2 つあると見込んでいたため、コースが届くとブロックが伸び縮みし、その下のすべてを 100 ピクセル以上動かしていました。現在は各列が決まった数の 1 行の項目を持ち、プレースホルダーは同じ行を描き、メッセージは列と同じ大きさの枠に表示されるため、どの状態でもどの画面幅でも高さが同じです（[コース](/docs/features/courses) を参照）。ランディングページのスター数も、数字と同じ高さのスケルトンで同じようにしています。コースをプリレンダリングされた HTML に書き込むことはできません。ビルドには本番のデータベースがなく、リクエストのたびに Worker でランディングページをレンダリングすれば、プリレンダリングで短縮した最初の 1 バイトまでの時間を失うためです。
