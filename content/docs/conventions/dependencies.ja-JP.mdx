このリポジトリは、すべての依存関係の最新リリースで動作しています。アップグレードで何かが壊れた場合は、元に戻すのではなく、コードかアップストリームで前に進む形で修正します。

## ツールチェーンのバージョン [#upgrading]

依存関係、エージェントスキル、GitHub Actions は、専用のブランチで 1 つのコマンドでまとめて更新します。

```sh
bun run deps:update
```

`scripts/update-dependencies.ts` は次の順に実行します。

1. Vite+ の最新リリースが `package.json` の `vite-plus` より新しい場合は、そのリリースの `vp migrate`。`vite-plus`、`vite` エイリアス、`vitest` をまとめて動かします。
2. `^` または `~` の範囲で宣言されたすべての依存関係に対する `bun update --latest`。新しいメジャーバージョンを含む最新リリースに移し、範囲の書き方は保ちます。
3. `bun run skills:update`。[エージェントスキル](/docs/tooling/agent-skills)を各ソースの最新コミットに移し、スキルが説明するパッケージのバージョンを記録します。
4. `scripts/github-actions.ts`。`.github/workflows/` と `.github/actions/` の各アクションのリポジトリのリリースタグを `git ls-remote` で読み、最新の安定版リリースを選び、注釈付きタグはコミットまでたどって、各 `uses:` をそのコミットとタグに書き換えます（[CI/CD](/docs/tooling/ci-cd)）。

完全一致で固定したバージョンは、どれもこのページに理由があるため変更せず、最後に新しいリリースがある固定パッケージをすべて表示します。スキルが説明するパッケージが前回の `skills:update` 以降に動いている間は `bun run check` が失敗するため、依存関係とスキルがずれることはありません。毎週、`updates.yml` ワークフローが利用できる更新を 1 つの GitHub Issue にまとめます。[CI/CD](/docs/tooling/ci-cd#updates) を参照してください。

そのうえで、動いた各パッケージについて次を行います。

- Bun はパッケージマネージャー兼スクリプトランナーです。そのバージョンを設定する場所は `package.json` の `packageManager`（Bun <RepositoryFact name="bunVersion" />）だけで、CI もそこから読み取ります。`bun.lock` はコミットします。
- Node のバージョンは `.nvmrc`（<RepositoryFact name="nodeVersion" />）で決まり、`engines.node` はそれ以上のバージョンを要求します。
- 唯一の例外は `remotion/` で、独自の npm ツールチェーンを持ち、ランディングページの動画を編集するときにだけインストールします。 その `typescript` は、Remotion の lint ルールを実行する `typescript-eslint` が peer 依存関係として受け入れる最新のリリースです。TypeScript 7 には `typescript-eslint` が読み込むコンパイラ API が含まれていないためです。サイトと共有するパッケージ（`@saasyland/stack`、`lucide-react`、`react`、`react-dom`）は、サイトの `package.json` が受け入れる最も低いバージョンに固定します。動画がそれらをインポートするサイトのファイルを描画するためで、両者が異なると `src/data/__test__/cli.test.ts` が失敗します。

## アップグレード

1. 新しいバージョンの変更履歴と移行ガイドを読みます。できれば `node_modules/<package>` に同梱されているものを読んでください。
2. 新しいバージョンのドキュメントに記載された使い方に合わせてコードを変更します。
3. 次の順序で検証します。最後のステップが成功するまでは、何も完了したと報告しないでください。

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` とテストは Cloudflare と TanStack Start のビルドを行わずに実行されるため、ビルドが壊れていても成功することがあります。実際、1 回のアップグレードでそれが 2 度起きました。新しい `@polar-sh/sdk` がバンドルできなかったことと、TanStack Start のリリースで、`optimize-prerendered-html.ts` が書き換える `modulepreload` のマークアップが変わったことです。どちらも `build:test` でしか表面化しませんでした。ビルドの後、`find dist/server -name '*.map'` は何も出力してはいけません。`wrangler.jsonc` に `upload_source_maps: false` があるのは、ソースマップを含めた Worker が、Cloudflare がアップロードで受け付けるサイズを超えてしまうためです（[Cloudflare Workers](/docs/integrations/cloudflare-workers) を参照）。

破壊的変更を避けるためにパッケージを古いリリースに固定してはいけません。また、ライブラリのバグを回避するコードをアプリケーションに追加してはいけません。

## バグがアップストリームにある場合

アプリケーションがすでにドキュメントどおりの使い方をしていて、新しいバージョンのほうが誤っている場合は、新しいバージョンのまま修正を保持します。

1. このリポジトリの外で、最小限の再現例を作ってバグを証明します。
2. アップストリームに提案する修正と同じ内容で、パッケージ内のバグを直す最小限の変更を書き、`bun patch` で保存します。パッチは `patches/<package>@<version>.patch` と `patchedDependencies` に記録され、パッチが適用され続けるよう、パッケージはその正確なバージョンに固定されます。
3. そのプロジェクトのコントリビューションのルールに従って、アップストリームにバグを報告し、修正を含むプルリクエストを作成します。
4. 修正を含むリリースが出たら、すぐにパッチを削除します。パッチを維持したりドキュメントに記載したりする前に、`npm view <package> version` でそのリリースがすでに出ていないかを確認してください。

現在のパッチは次のとおりです。

- `patches/@tanstack%2Frouter-core@1.171.39.patch` は、ハイドレーション後のルーターの最初のレンダリングがウィンドウを先頭までスクロールし直さないようにします。アップストリームには [TanStack/router#8933](https://github.com/TanStack/router/issues/8933) として報告しており、パッチは [TanStack/router#8934](https://github.com/TanStack/router/pull/8934) で提案している修正です。
- `patches/@tanstack%2Freact-router@1.170.46.patch` は、訪問者がページを離れるためにブラウザーがルートのチャンクを中止したとき、`lazyRouteComponent` がそのページを再読み込みしないようにします。これは [TanStack/router#8830](https://github.com/TanStack/router/pull/8830) で提案されている修正に、ページが `beforeunload` の後に読み込み始め、Safari がすぐに失敗させるチャンクへの対応を加えたものです。
- `patches/framer-motion@14.14.0.patch` は、読み込めなかった機能バンドルを `LazyMotion` が無視するようにし、拒否が未処理のまま残らないようにします。これに合わせて `motion` は 14.14.0 に固定されています。Motion は 14.14.0 のリリース後に [motiondivision/motion#4089](https://github.com/motiondivision/motion/issues/4089) の修正を取り込んだため、この修正を含む最初のリリースでパッチを削除します。
- `patches/better-auth@1.7.27.patch` は、統合テストの `(await auth.$context).password.hash()` のように Better Auth のエンドポイントの外でパスワードをハッシュするときにも `haveIBeenPwned` プラグインが動くようにします。そこで例外を投げる `getCurrentAuthEndpointContext` の代わりに、`tryGetCurrentAuthEndpointContext` でエンドポイントのコンテキストを読みます。これに合わせて `better-auth` は 1.7.27 に固定されています。[better-auth/better-auth#12873](https://github.com/better-auth/better-auth/pull/12873) で提案している修正です。
- `patches/playwright-core@1.65.1.patch` は、Polar のホスト型チェックアウトからワークスペースへ戻るときのように、`Cross-Origin-Opener-Policy` を送るページへのクロスサイトのナビゲーションを Playwright の WebKit ドライバーが追えるようにします。Playwright 1.65 の WebKit ビルドはプロセスの切り替えのために、1 つ目の仮ページを破棄する前に 2 つ目を作ります。ドライバーは `WKPage._onTargetCreated` のアサーションで失敗する代わりに、1 つ目を破棄するようになります。これに合わせて `@playwright/test` は 1.65.1 に固定しています。アップストリームには [microsoft/playwright#44254](https://github.com/microsoft/playwright/issues/44254) として報告しており、Playwright は完了としてクローズしました。1.65.1 より後の安定版で修正を含むものはまだないため、それが出るまでパッチを残します。

`src/lib/stale-build.ts` が `isModuleNotFoundError` をインポートするため、`@tanstack/router-core` は直接の依存関係であり、パッチが適用され続けるよう 1.171.39 に固定されています。`@tanstack/react-router` は 1.170.46 に、`@tanstack/react-start` は 1.169.7 に固定されています。どちらもパッチを当てた TanStack のバージョンにそのまま依存しているためです。`fumadocs-mdx` 15.6.0 へのパッチも同じ方法で保持し、15.6.1 でアップストリームの修正がリリースされた時点で削除しました。`@fumadocs/base-ui` と `fumadocs-core` 16.19.2 へのパッチも、16.19.3 でそれぞれの修正がリリースされた時点で削除しました。`@videojs/utils` 10.4.0 へのパッチは、10.5.0 で修正がリリースされた時点で削除しました。Fumadocs のドキュメントレイアウトに `skipToContent` スロットを加えるパッチは、Fumadocs がそのスロットを採用しなかったため削除しました。代わりに `globals.css` が Fumadocs のリンクを隠し、サイト自身のスキップリンクがドキュメントの記事へ移動します（[ドキュメントサイト](/docs/features/docs-site)を参照）。

パッチが変えるのはパッケージのファイルであり、Bun がそのパッケージにインストールするバージョンではありません。パッケージが自分の依存関係の 1 つを、アプリケーションが使うリリースより古いバージョンに固定していて、2 つのコピーの型が合わない場合は、代わりに `package.json` の `overrides` のエントリーでそのバージョンを引き上げます。現在は必要ありません。`@polar-sh/better-auth` が使う `@polar-sh/adapter-utils` 1.1.1 は `@polar-sh/sdk` を 1.3.1 に固定しているので、Bun はアプリケーションの 1.3.2 の横にそのコピーをインストールします。アダプターが SDK をインポートするのはプラグインの `webhooks({ onPayload })` を型付けするためだけで、1.3.2 のペイロードを受け取る `handlePolarEvent` は 1.3.1 のペイロードも受け入れます。1.3.2 はサブスクリプションのステータスへの `trial_ended` の追加のように、型を広げただけだからです。今後の SDK リリースがアダプターのコピーでは受け入れられない形でペイロードを変えたときは、`bun run check` が `handlePolarEvent` で失敗します。その場合は、`@polar-sh/adapter-utils` のリリースがその SDK に依存するようになるまで、`@polar-sh/sdk` の `overrides` エントリーでアダプターのコピーを引き上げます（`npm view @polar-sh/adapter-utils dependencies`）。

## セキュリティアドバイザリー

Dependabot のアラートは `remotion/package-lock.json` を対象にしますが、GitHub は `bun.lock` を読みません。そのため、アプリケーションは `bun audit` で、動画プロジェクトは `remotion/` 内の `npm audit` で確認します。アドバイザリーは、脆弱なパッケージを取り込んでいるパッケージの最新リリースで解消します。そのパッケージのバージョン範囲がすでに修正済みのリリースを許容している場合は、ロックファイルを更新するだけで十分です（`bun update`、または `remotion/` での `npm update`）。

親パッケージのどのリリースもまだ修正を許容していない場合は、`overrides` のエントリーで脆弱なパッケージのバージョンを引き上げ、親パッケージのリリースが対応した時点でそのエントリーを削除します。現在のエントリーは次のとおりです。

- `package.json`: `"minimatch": "^11.0.1"`。`shadcn` は `ts-morph` 26 と `@ts-morph/common` を経由して `minimatch` ^10 を使っており、GHSA-g3hv-75wg-m249 を修正するのは `minimatch` 11.0.1 だけです。[dsherret/ts-morph#1697](https://github.com/dsherret/ts-morph/pull/1697) を含む `ts-morph` のリリースに `shadcn` が依存するようになったら削除します。
- `remotion/package.json`: `@typescript-eslint/typescript-estree` 配下の `minimatch` ^11.0.1 で、同じアドバイザリーへの対応です。`@remotion/eslint-config-flat` は `typescript-eslint` を 8.71.2 に固定しており、そのパーサーが `minimatch` ^10 を要求します。[typescript-eslint/typescript-eslint#13145](https://github.com/typescript-eslint/typescript-eslint/pull/13145) を含む `typescript-eslint` のリリースに `@remotion/eslint-config-flat` が依存するようになったら削除します。

`bun audit` は、適用できる修正のないアドバイザリーを 1 件まだ報告します。

- `esbuild` 0.18.20（GHSA-67mh-4wv8-2f99、重大度は中）: `drizzle-kit` と `@esbuild-kit/esm-loader` 経由です。`drizzle-kit` 0.31.11 はこのローダーを依存関係として宣言していますが一度も import しておらず、アドバイザリーの対象は esbuild の開発サーバーで、このリポジトリでそれを起動するものはありません。[drizzle-team/drizzle-orm#5304](https://github.com/drizzle-team/drizzle-orm/issues/5304) で削除が追跡されており、`drizzle-kit` 1.0 のリリース候補はすでにこれに依存していません。

`shadcn` と `@shadcn/registry` が取り込んでいた `deepmerge` 4.3.1 のアドバイザリー（GHSA-gcqx-w48m-w2h4）は、[github/advisory-database#10910](https://github.com/github/advisory-database/issues/10910) を受けて GitHub が取り下げたため、`bun audit` はもう報告しません。

## package.json の Vite+ のエントリー

```json
"vite": "npm:@voidzero-dev/vite-plus-core@8.3.8000",
"vite-plus": "1.7.0",
"vitest": "5.1.0"
```

これらの行と、`overrides` 配下の同じ `vite` エイリアスと `vitest` のバージョンは、Vite+ 自身の移行ツールが書き出すものとまったく同じです。`vite-plus` は正確なバージョンに固定され、Bun はコアを直接の `vite` 依存関係として必要とし、`vitest` は `@vitest/coverage-v8` とテストの型が必要とするため記載されています。`vite-plus` 1.7.0 以降、コアは同梱する Vite のリリースのバージョンを名乗るので、8.3.8000 は Vite 8.3.8 です。対応は `vp toolchain` で表示できます。これらは `bun update` ではなく、`vp migrate` でまとめてアップグレードします。どれかを削除できるかどうかを知りたい場合は、プロジェクトをコピーし、コピーに対して `vp migrate` を実行して結果の差分を取ってください。推論で判断してはいけません。`overrides` 配下の `minimatch` エントリーは上で説明したセキュリティ対応で、`vp migrate` はそれを変更しません。

`src/integrations/polar/polar.vite.ts` が設定する `build.rolldownOptions.external` には、`@polar-sh/sdk` の省略可能なピア依存関係のうち、インストールされておらず Worker からツリーシェイキングで除かれるものを列挙しています。[Vite+](/docs/tooling/vite-plus) を参照してください。Polar がパッケージングを修正したら、このリストを削除します。

## 依存関係を追加する

1 つの関心事に使うライブラリを 1 つに保つため、まず `package.json` にすでにあるパッケージでその役割を果たせないかを確認します。ランタイムの依存関係は `bun add` で、ツールは `bun add --dev` で追加し、ベンダーのエージェントスキルが `skills-lock.json` にあればそれを使います（[エージェントスキル](/docs/tooling/agent-skills)を参照）。 ベンダーのスキルが新しいパッケージを説明している場合は、`SKILL_SOURCES`（`src/data/skills.ts`）のそのソースにパッケージを追加し、`bun run skills:update` を実行します。
