## Route

`src/routes/_site._marketing.index.tsx` composes its sections from `src/presentation/components/custom/landing-page/sections` inside `MotionProvider`: Hero, Proof, Stack, Manifesto, CLI, Line, Quality, Rally, Manifest, Studio, Record, Cases, Compare, Pricing, FAQ, Notes and Gate. Copy comes from the `pages.landing` namespace. The loader also picks the posts of the Notes section with `blogNotes`, the first post of `FEATURED_BLOG_POSTS` as a card with its cover and the newest other posts beside it (see [Blog](/docs/features/blog#source)), and warms `starCountQuery`, the GitHub star count cached in KV for the Proof section. It then formats the Core price from `TIER_PRICES` into the page description, whose `pages.landing` message takes it as `{price}`. The page also carries the organisation's structured data, `ORGANIZATION_STRUCTURED_DATA_HTML`; see [Search and social previews](/docs/features/seo#structured-data).

Every other count on the page is measured, not typed: the `virtual:repository-facts` Vite plugin in `scripts/repository-facts.ts` counts the test files, Playwright specs, the browser tests Playwright lists and UI components, takes the number of currencies, timezones and countries from `CURRENCY_CODES`, `TIMEZONES` and `COUNTRIES`, and reads the React and TanStack Table majors, when the site is built. `REPOSITORY_FACTS` in `src/lib/repository-facts.ts` adds the languages, the working admin sections and, from `STACK_MODULES` and `STACK_EXTRAS` in `@saasyland/stack`, the CLI modules (`cliModules`), modules an answer can leave out (`cliOptionalModules`) and extras (`cliExtras`), and the sections pass it to `pages.landing` messages as ICU arguments such as `{testFiles, number}`. The **Check every claim** list takes the files and commands it cites from the same facts, so no locale translates them: the coverage summary path from `vite.config.ts`, the specs directory from `playwright.config.ts`, the CI workflow, the messages directory, the auth integration, the [Test coverage](/docs/tooling/test-coverage) page, and the commands <RepositoryFact name="coverageCommand" />, <RepositoryFact name="flowCheckCommand" /> and <RepositoryFact name="i18nCheckCommand" />.

The head start in the manifesto and the closing section is `headStartHours`, derived from `HEAD_START_ROWS` in `src/data/head-start.ts`. Each row names a part of the default project that the CLI's templates generate, the template layer it ships in, and the low and high hours a senior engineer would spend writing it by hand; billing, organisations, tenancy and sample commerce have no row until a template generates them. The rows add up to <RepositoryFact name="headStartLowHours" /> to <RepositoryFact name="headStartHighHours" /> hours, and the claim takes the low total rounded down to `HEAD_START_ROUNDING_HOURS` and capped at `HEAD_START_CLAIM_MAX_HOURS`, so it reads <RepositoryFact name="headStartHours" /> and falls on its own if rows go. The blog prints the rows with `<HeadStartTable />`, labelled from `pages.blog.headStart`.

The coverage figure everywhere on the page is `coverageThreshold`, read from `vite.config.ts`, and the count of browser tests is `e2eTests`, the tests Playwright lists. The page prints no ratio of flows: the Quality section links to [Test coverage](/docs/tooling/test-coverage), which lists every flow with the test that proves it or what is missing. Two kinds of value are declared rather than measured, once each in `src/data/marketing.ts`: the facts about the two course platforms (`REACTPROJECTS_FACTS` and `ANGULARPROJECTS_FACTS`: each platform's host, taken from its URL, its number of builds and its access status) and the pricing ledger's illustrative hourly rate (`ILLUSTRATIVE_HOURLY_RATE`), from which `CORE_PRICE_IN_HOURS` (`src/data/license.ts`) computes the whole hours the Core price stays under; `license.test.ts` fails if it stops staying under them.

`adminSections` counts the entries of `ADMIN_NAVIGATION` in `src/data/navigation.ts`. Every admin entry opens a screen that works on real data, so every one counts: <RepositoryFact name="adminSections" /> today. The same entries name the sections beside the count, in the Proof grid and in the Manifest, through `useAdminSections`, which lists the menu labels in the reader's language. The Proof grid's **Languages** shows the supported locales, and its test counts say that they are counted in this site's own source, not in a generated project.

Every public page sits in the pathless `_site` layout (`src/routes/_site.tsx`), which renders the site header, `Navigation`, and `BackToTop` once for all of them. Inside it, the `_marketing` layout (`_site._marketing.tsx`) wraps `/`, the legal pages, the newsletter pages, the blog and the courses with `PageFrame`, the `main` landmark and `Footer`. It sets `dark: true` in its `staticData`, and `_site` switches the whole page, header included, to the dark theme whenever a matched route sets it, while the docs keep the visitor's theme. Section anchors are `MARKETING_SECTION_IDS` in `src/data/navigation.constants.ts` (`foundation`, `cli`, `quality`, `toolkit`, `pricing`, `faq`); links use `<Link to={ROUTES.HOME} hash={MARKETING_SECTION_IDS.PRICING}>`. `Footer` links the GitHub repository and the Instagram profile, `APP_GITHUB_URL` and `APP_INSTAGRAM_URL`, in a new tab next to `LocaleSwitcher`. `Footer` lays out its brand block and its two link groups as one wrapping flex row in which no item gets narrower than its longest word, so the groups sit side by side while their labels fit and stack when they do not, and no label runs into another in any language. On a phone the brand block takes the first row; from `md` up the three share one row 1.5 : 1.3 : 1.

## Not-found page

Every path no route matches reaches `_site._marketing.$.tsx`, whose loader throws `notFound()`, so the server answers with status 404 and the page sits in the `_marketing` layout like any other: under the one site header, above the footer, in the marketing theme. A blog post, course or lesson that does not exist throws `notFound()` from its own loader and shows the same `DefaultNotFound` (`src/presentation/components/custom/default-not-found.tsx`) in the same place, and a missing docs page shows it in the docs layout. When their match is not found, these routes take their head from `notFoundHead` (`src/lib/not-found.ts`): the localized title and description from `errors.not-found` and `noindex`, without a canonical link or social card. The page's one action is `BackHomeLink`, labelled from `common.backHome`, which the spent newsletter link offers too.

## Navigation and back to top

- The header links are `HEADER_NAVIGATION` in `src/data/navigation.ts`, in the order it lists them: **Pricing** (a link to the `pricing` section of `/` through its `hash`), **Courses**, **Blog**, **Docs** and **Sign in**, each labelled by the message its `label` names, such as `navigation.core.header.pricing` in `navigation.core.json`. The **Sign in** entry also names a `signedIn` label, so a signed-in visitor reads **Your account** there from the first paint ([Performance](/docs/conventions/performance#the-header-knows-the-session-before-its-scripts)). `Navigation` renders them, then the **Start building** call to action to the pricing section. Below the `lg` breakpoint the entries move into `MobileMenu` (`src/presentation/components/custom/mobile-menu.tsx`), a React Aria `Modal` with a `Dialog` that covers the window. Its top row repeats the logo and puts the close button where the menu button was; under it come the same entries in the same order and then **Start building**, which the header itself hides below `sm`. Focus moves to the close button and Tab stays in the menu, Escape and the close button return focus to the menu button, and the page behind is `inert` and does not scroll. `html` keeps the scrollbar's room ([Scrollbars](/docs/ui/theme#scrollbars)), so nothing moves when the menu opens or closes. An entry added to `HEADER_NAVIGATION` appears in the header and the menu of every public page.
- Once a page has loaded and the browser is idle, `Navigation` preloads the page of every header entry through the router, its code and its data, so a click, a tap in the phone menu or a key press opens it without waiting for the Worker. It loads nothing for a visitor who has turned on data saver, and it runs again after each navigation; see [Performance](/docs/conventions/performance#the-headers-pages-load-before-a-click).
- TanStack Router's `Link` marks the entry of the current section with `aria-current="page"`, and the header shows it brighter with a dot below: **Blog** on the blog index and every post, **Docs** on every docs page. An entry with a `hash` is marked only on its own address, `/#pricing`, so the rest of the home page marks no entry. The footer's links to the landing sections, **Foundation**, **Pricing** and **FAQ**, pass `activeOptions={{ includeHash: true }}` for the same reason. **Start building** is never marked, not even on `/#pricing`: it is an action, not a place, so `Navigation` and `MobileMenu` build it with `useLinkProps` and drop the `aria-current` that TanStack Router puts on every link to the current address.
- The header opens with a **Skip to content** link, hidden until it has keyboard focus, to the page's content: the `main` landmark of the `_marketing` layout, whose id is `SITE_CONTENT_ID`, or, on a docs page, the article, whose id is `DOCS_CONTENT_ID`, Fumadocs' `nd-page` (both in `src/data/navigation.constants.ts`; see [Docs site](/docs/features/docs-site)).
- The header is fixed and looks the same at every scroll position: a blurred background and a line along its bottom edge, over which a progress line grows as the page scrolls. Its height is the `--spacing-header` theme token in `globals.css` (`h-header`), and its content is as wide as the content of every public page, `--container-site` (`max-w-site`), so the logo and **Start building** keep their places from page to page. The `main` landmark of the `_marketing` layout starts every page below it with `pt-header`, except the landing page, whose `staticData` sets `underHeader: true` so its hero runs under the header; the docs layout sets Fumadocs' `--fd-banner-height` to it so the sidebar and the table of contents stick below it, and `html` reserves it with `scroll-padding-top`, so neither a heading reached through an anchor nor an element that takes keyboard focus ends up under the header.
- The logo in the header is `HomeLink` (`src/presentation/components/custom/home-link.tsx`). On `/` a click scrolls back to the top and removes a section hash such as `#pricing` from the address, replacing the history entry, instead of reloading the page the visitor is already on. On any other page it is an ordinary link home, and a click with a modifier key still opens a new tab or window. In the phone menu the logo also closes the menu.
- `BackToTop` (`src/presentation/components/custom/back-to-top.tsx`) is a React Aria button fixed to the bottom-right corner, labelled from the `components.custom.back-to-top` namespace. An `IntersectionObserver` sentinel shows it once the first screen has scrolled out of view and hides it again near the top, so no code runs on scroll events. Pressing it scrolls to the top and moves focus to the page's `h1`. The `_site` layout renders it once for every public page.
- Both call `scrollTo({ top: 0 })` and leave the motion to `globals.css`: `html` scrolls smoothly, and under `prefers-reduced-motion: reduce` it jumps straight to the top.

## Pricing and regional pricing

`PricingSection` renders `PricingTiers` from `src/presentation/components/custom/pricing.tsx`, the same tier cards the [customer app](/docs/features/customer-app) shows to accounts without a licence. Each card shows a tier from `LICENSE_TIERS` (`src/modules/license/license.constants.ts`) with its `TIER_PRICES` amount and copy from the `components.custom.pricing` namespace, and its button comes from the page: on the landing page a link to `/auth/sign-up?redirect=/app?tier=<tier>`, so the chosen tier survives sign-up. The grid switches to three columns when its own container is at least 42rem wide (`@container`), so it fits the narrower app column too. Regional pricing works without client JavaScript, so the page stays prerendered.

The featured tier, `FEATURED_TIER` (Complete), carries the **Recommended** label. In one column a card's button sits under its price, before the features, so a visitor on a phone reaches it without scrolling past the list; in three columns it moves to the bottom of the card (`order-last`), where the buttons line up. Under the cards, `PricingTrust` lists `PRICING_TRUST_ITEMS` from the `trust` messages: Polar as the Merchant of Record, with its receipt and VAT invoice and the VAT ID field for companies; prices in US dollars, VAT included in the EU and sales tax added in the US, Canada and India, which the [tax behaviour](/docs/getting-started/polar-setup#tax-behaviour) in Polar must match; the full refund within <RepositoryFact name="refundWithdrawalDays" unit="day" /> before a project is generated or a paid lesson opened, with a link to the Refund Policy; and the CLI beta, every release of which is included. The hero's `stack` sentence follows its description and names the stack the CLI writes today: `GeneratedStack` reads the framework, UI library and deployment options of `CLI_TEMPLATE_SUPPORT`, labels them from the `stack` namespace, joins each list with `format.list` as alternatives, and links the [roadmap](/docs/project/roadmap) for the others, so the sentence names a new framework or host in the release that generates it. The hero repeats the offer under its buttons in `hero.anchor`: the Core price through `PRICE_TAGS`, regional where it applies, lifetime updates and the refund period from `REFUND_TERMS.WITHDRAWAL_DAYS`.

A card's features come from `TIER_FEATURES` in `src/data/license.ts`. Each entry has an id, whose text is `tiers.<tier>.features.<id>`, and a `FEATURE_STATUS`, and the card lists the entries under **Available now** and **Arriving** (`status.available` and `status.arriving`), so the split between what works today and what is arriving is declared once and no translation names a status. The available group ends with the machines a key runs on at a time, `LICENSE_ACTIVATION_LIMITS[tier]` through the `machines` message, an ICU plural: <ActivationLimit tier="core" /> on Core, <ActivationLimit tier="complete" /> on Complete and <ActivationLimit tier="agency" /> on Agency. `LicenseOfferPending` draws the same groups from `TIER_FEATURES`.

Complete's free lifetime access to the two course platforms takes its status from `REACTPROJECTS_ACCESS` and `ANGULARPROJECTS_ACCESS` in the same file, `FEATURE_STATUS` values like `CLI_GENERATION`. Today reactprojects.com is <RepositoryFact name="reactprojectsAccess" /> and angularprojects.com <RepositoryFact name="angularprojectsAccess" />, because both take waitlist sign-ups and neither has opened. The FAQ's answer about Complete is an ICU `select` on `reactprojectsAccess` and on `angularprojectsAccess`, which the FAQ receives in `COURSE_PLATFORM_VALUES` with the platforms' hosts, so setting a platform's status to `FEATURE_STATUS.AVAILABLE` moves its feature under **Available now** and changes that sentence in every locale. `src/data/__test__/course-platform-access.test.ts` renders both variants in every locale. Agency's team seats on the course and both platforms take their status from `TEAM_SEATS_ACCESS`, <RepositoryFact name="teamSeatsAccess" /> today, and the FAQ's answer about subscriptions is an ICU `select` on `teamSeatsAccess`, whose two variants `feature-status-copy.test.ts` renders in every locale. The blog posts describe the access in prose that changes when a platform opens.

Regional prices reach the page like this:

1. `Price` renders the regular price as text. Each regional amount, one per multiplier in `PPP_KEYS`, rounded down to whole dollars by `regionalPrice`, the function checkout charges with, and the struck-through regular price beside it sit in a `data-text` attribute that CSS draws (`.ppp-text::before`), and so do the offer under the tiers and the saving under each price. A reader without CSS, such as a crawler, reads the regular price alone and none of the offer.
2. `rewritePppOffer` (`src/modules/license/license.pricing.ts`), which the Worker runs on every HTML page as an element of `DOCUMENT_REWRITES`, reads `cf-ipcountry`. For a country in `PPP_TIERS` it uses `HTMLRewriter` to set `data-ppp` and the `--ppp-region` and `--ppp-percent` variables on the `html` element. It sets no header: every HTML page the Worker serves is `private, no-cache` with `Vary: Cookie` (`setDocumentHeaders` in `src/server.ts`).
3. CSS in `globals.css` shows the matching price while the regional offer checkbox is checked.
4. Unchecking stores `regional_pricing=off` in a cookie; the Worker and `startCheckout` both respect it, so the price on the card is the price at checkout.

Below the tiers, `WaysIn` puts three cards side by side, each with its label, its promise, its price and one button: **Free**, the website's own source under the MIT licence for $0, whose button opens `APP_GITHUB_URL`; **Agencies**, the Agency tier's client projects, its architecture call and its key's `LICENSE_ACTIVATION_LIMITS` machines, at the Agency price through `Price`, regional where it applies, with the same sign-up link as the Agency card; and **Consulting**, at `CONSULTING_HOURLY_RATE` from `src/data/marketing.ts`, formatted with `CURRENCY_FORMAT`. The call is booked by email rather than sold through Polar, so it has no regional price, and its button says **Email to book a call**. The call lasts `TIER_SUPPORT.CALL_MINUTES` from `src/data/license.ts`, <RepositoryFact name="callMinutes" unit="minute" />, and Complete's priority support answers within `TIER_SUPPORT.RESPONSE_BUSINESS_DAYS`, <RepositoryFact name="supportResponseDays" /> business day; the tier cards, the consulting card, the FAQ and the blog posts print both from `TIER_SUPPORT_VALUES`.

## CLI configurator

`CliSection` hosts `CliConfigurator` (`landing-page/components/cli-configurator.tsx`). The questions and extras of `STACK_CHOICES` and `STACK_EXTRAS` from `@saasyland/stack` and the package managers in `src/data/cli.ts` build a <RepositoryFact name="scaffoldTarget" /> command with flags, which `CopyButton` copies. The labels of the questions, options and extras, and each question's `note`, are the `stack` namespace, which the route loads beside `pages.landing` and the docs layout loads for the [roadmap](/docs/project/roadmap)'s tables. Whether the CLI runs it yet is `CLI_GENERATION`, described below; the [CLI guide](/docs/cli) says what the CLI does today.

The configurator lets a visitor pick only what the CLI's templates generate. The source is `TEMPLATE_SUPPORT` from `@saasyland/stack/cli`, the list the CLI checks too, which `src/data/cli.ts` exports as `CLI_TEMPLATE_SUPPORT` and which lists for each question the options the templates write and under `extras` the extras they write. Every other option and extra keeps its place, disabled, with an hourglass after its label, and `aria-describedby` points it at the `coming` legend beside the package manager tabs, above the questions. The `generates` line under the configurator says that project generation writes every option a visitor can pick. Once the templates generate an option, the `@saasyland/stack` release that ships them lists it, and upgrading the package enables it; nothing else changes. The questions, their options and their rules come from the same package, so the website keeps no copy of them.

The configurator opens on the answers `init --yes` resolves from that list (`resolveCliAnswers` in `src/lib/cli.ts`, which calls the stack's `resolveAnswers`): for each question in turn, the CLI's default when the templates generate it and the earlier answers allow it, otherwise the first option that meets both. When a visitor changes an answer, the answers it rules out are resolved again the same way, and the others stay. The release post prints the same opening command with `<ScaffoldCommand />`, whose flags `stackArguments` from `@saasyland/stack` writes from those answers, so the post never shows a flag the templates do not generate. `cli.test.ts` checks that every option and extra of the stack has a label in the `stack` messages, so an option that a new `@saasyland/stack` release adds fails the tests until it is translated. No answer the configurator can reach, the opening one included, puts a flag in the command that the templates do not generate.

Each question is a radio group, the shadcn `ToggleGroup` with `selectionMode="single"`, named by its row's label, and the extras are one `ToggleGroup` with `selectionMode="multiple"`. The arrow keys move within a question, Space or Enter answers it, and Tab moves to the next question. Every option keeps its place. One that an earlier answer rules out through its `unavailableWhen` or `visibleWhen` rule in `@saasyland/stack` is disabled and struck through, and the question's `note`, printed under its options, says why; `aria-describedby` gives screen readers the same reason, after the `coming` legend when the option is coming as well. An extra that an answer rules out leaves the command. A selected option changes colour only, nothing scales when pressed, and the configurator fades in without rising, so a press never moves a control under the pointer. `e2e/specs/cli-configurator.spec.ts` presses every available option at its centre and at both edges and checks that no option moved, and presses options that are coming to check that the command stays the same.

The UI library is the first question, as in `@saasyland/stack`, so the command passes `--library` before `--framework`. The framework question lists every framework under the library it runs on, which the frameworks' `visibleWhen` rule in `@saasyland/stack` declares: TanStack Start, Next.js and React Router under React, Analog and Angular SSR under Angular, Nuxt under Vue, SvelteKit under Svelte, and SolidStart under Solid. TanStack Start runs on Solid as well, so it is listed once, under React, and the Solid group names it after SolidStart. Each library's frameworks form a `role="group"` named by the library inside the question's radio group, so the arrow keys still move across the whole question. A framework that does not run on the chosen library is disabled but not struck through, because its group already shows why, and `aria-describedby` points it at the question's `note`. `CLI_TEMPLATE_SUPPORT` lists React and TanStack Start, so every other library and framework carries the hourglass, and so does Deno, which the runtime question rules out on Cloudflare and on Vercel.

Whether project generation has shipped is `CLI_GENERATION` in `src/data/cli.ts`, a `FEATURE_STATUS`. Every message that depends on it is an ICU `select` on `generation` with an `available` variant and an arriving one (`other`), and the components pass `CLI_GENERATION_VALUES`: the status and the npm init command, <RepositoryFact name="cliInitCommand" />. The Core features that generation delivers, and Agency's client projects, take their status in `TIER_FEATURES` from the same constant, so changing it changes those sentences in every locale and moves the features under **Available now**. Billing on the Core card also waits for `CLI_TEMPLATE_SUPPORT` to list a billing provider, so it stays under **Arriving** until the templates generate billing, and the hero and the closing call to action name billing among what a project ships with only once `BILLING_GENERATION` is available. The Manifest's **Billing** item says that this site sells through Polar and, from `BILLING_GENERATION`, whether a generated project has billing yet. `src/data/__test__/cli-generation.test.ts` lists the messages, renders both variants in every locale and fails when the arriving wording appears outside the select. The blog posts, these docs and `public/llms.txt` say it in prose and change with the release that ships generation.

## Newsletter

`Footer` renders `NewsletterForm` (`src/presentation/components/custom/newsletter-form.tsx`):

1. `subscribeToNewsletter` (rate limited) stores a pending `newsletter_subscriber` row and sends `NewsletterConfirmationEmail`. An address that is already subscribed gets `alreadySubscribed` and nothing is written. After <RepositoryFact name="recipientEmailsPerHour" /> confirmation emails to one address within an hour, it returns `confirmationSent` without writing or sending anything.
2. `/newsletter/confirm?token=` asks the visitor to confirm. Pressing the button calls `confirmNewsletterSubscription`, which confirms the subscription and sends `NewsletterNotificationEmail` to `CONTACT_EMAIL`.
3. `/newsletter/unsubscribe?token=` asks the same way before `unsubscribeFromNewsletter` unsubscribes. Opening or prefetching either link changes nothing, so a mail scanner cannot subscribe or unsubscribe anyone. Every issue links to `/newsletter/unsubscribe`, and a mail client's own unsubscribe button posts to it and unsubscribes at once ([Newsletter](/docs/features/newsletter#unsubscribing)).

The admin writes and sends the issues ([Newsletter](/docs/features/newsletter)). `NEWSLETTER_SENDING` in `src/data/newsletter.ts` is <RepositoryFact name="newsletterSending" />, so the footer, the confirmation page and email and the empty course catalogue say that the build log arrives with its next issue; while it is `arriving`, they say that the first issue is arriving. The confirmation page and email print how long the link lasts, `CONFIRMATION_WINDOW_IN_HOURS` (<RepositoryFact name="newsletterConfirmationHours" unit="hour" />), from `newsletter-subscriber.constants.ts`.
