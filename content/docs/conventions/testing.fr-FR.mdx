Chaque modification est livrée avec les tests qui la prouvent, dans le même commit, et la couverture reste à <RepositoryFact name="coverageThreshold" unit="percent" /> pour les lignes, les instructions, les fonctions et les branches. Une correction de bug s'accompagne d'un test qui échoue sans la correction.

## Projets

`vite.config.ts` définit trois projets Vitest, choisis d'après le suffixe du fichier. Les tests importent leur API depuis `vite-plus/test` et se trouvent dans `__test__/`, à côté du code qu'ils couvrent.

| Suffixe                | Projet        | À utiliser pour                                                                                                                                                                                       |
| ---------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | Les cas d'usage, les loaders, `head`, les schémas, les utilitaires : tout ce qui s'exécute sur le serveur                                                                                             |
| `.integration.test.ts` | `integration` | Les flux Better Auth, de paiement et de licence, l'adaptateur D1 et le chargement des messages, avec des délais d'expiration de <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Les composants et les pages dans jsdom                                                                                                                                                                |

`src/platform/testing/mocks/cloudflare.ts` remplace `cloudflare:workers` dans chaque projet : D1 est une base de données `node:sqlite` en mémoire construite à partir de chaque migration versionnée, KV et un bucket pour chaque binding R2 de l'environnement `test` de `wrangler.jsonc` sont des stockages en mémoire. `resetTestBindings()` vide KV, le bucket et la table de limitation de débit avant chaque test, et la fonction d'amorçage de chaque suite réinitialise les lignes dont elle dépend. Aucun test ne communique avec Cloudflare, Polar, Resend ou un fournisseur OAuth : `fetch` atteint les doublures strictes de `mocks/resend.ts` et `mocks/polar.ts`, qui valident chaque requête d'après les modèles de requête des SDK et font échouer le test sur une requête que le fournisseur refuserait. Les tests vérifient ce que la doublure a reçu au lieu de simuler une méthode du SDK, et les suites d'authentification pilotent la vraie configuration de `auth.server.ts` via `auth.harness.ts`.

## Tester une fonction serveur

Appelez-la via ses options exportées, pour que le test exerce le vrai middleware, la vraie validation et le vrai handler. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts` :

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` et `executeMutation(options, variables)` de `src/platform/testing/lib/query.ts` exécutent les options dans un nouveau `QueryClient`.
- La session provient de `createAuthSessionFixture` dans `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts` ; chaque permission est aussi testée du côté qui doit être refusé (`it("is for staff only")`).
- Les données d'amorçage se trouvent dans le dossier `__test__/fixtures/` du module, avec leurs identifiants dans des objets nommés (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` supprime les lignes qui lui appartiennent et les insère de nouveau via Drizzle, si bien que chaque test part du même état.
- Dans le projet `component`, une fonction serveur échoue, car jsdom tient lieu de navigateur. Les tests de composants fournissent à une route ses données de loader ou simulent le `queryFn` et le `mutationFn` des options que lit le composant.

## Les assertions utilisent les noms du code

- Les statuts, types, rôles et codes d'erreur attendus sont les constantes qu'utilise le code : `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. Un test ne répète jamais un littéral de chaîne du domaine, pas plus que les données e2e ou le seed de test : `e2e/data/courses.ts` écrit `kind: COURSE_KIND.COURSE`.
- Les tests de schéma sont le seul endroit où une valeur stockée est écrite en clair : `product.schema.test.ts` fige `expect(PRODUCT_STATUSES).toStrictEqual(["draft", "published", "archived"])`, de sorte que modifier une valeur conservée en base fait échouer un test au lieu d'exiger une migration que personne n'a écrite.
- La suite du navigateur importe ses constantes depuis l'application (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`) et ne peut donc importer que des fichiers qui se chargent hors du Worker. Les valeurs de Polar proviennent de `polar.constants.ts`, qui ne lit aucun environnement : `e2e/fixtures/license.ts` et le parcours client dans la sandbox prennent les statuts de commande dans `POLAR_ORDER_STATUS`, et la commande elle-même provient de `src/platform/testing/lib/polar.ts`. Les identifiants des produits des offres font exception : `POLAR_PRODUCT_IDS` lit `cloudflare:workers`, donc la suite du navigateur les lit dans `.env.test`.
- Les tests de composants lisent les textes attendus dans les fichiers de messages anglais, comme le fait `admin-course-routes.component.test.tsx` avec `import labels from "~/messages/en-US/pages.admin.courses.json"` et `labels.form.kinds.course`, et trouvent les éléments par rôle et par nom accessible.
- Un test qui a besoin d'un type le lit depuis une source typée ou le vérifie à l'exécution avec `toHaveProperty` ; il ne fait jamais de conversion.
- Les noms de test décrivent un comportement sous forme de phrase : « lists every course with its lesson count, drafts included ».

## Couverture

`bun run test:coverage` échoue en dessous de <RepositoryFact name="coverageThreshold" unit="percent" /> sur l'une des quatre métriques pour `src/**/*.{ts,tsx}`. Les tests, `__test__/`, les fichiers de déclaration, `src/routeTree.gen.ts`, les primitives shadcn et `src/platform/testing/` sont exclus. Le seuil garde tout son sens :

- **Supprimez les branches qui ne peuvent jamais s'exécuter** au lieu de les couvrir avec des stubs. Un `?? fallback` sur une donnée toujours présente, ou un chaînage optionnel sur une valeur qui ne peut pas être `undefined`, est retiré du code source, et non atteint en remplaçant une globale.
- **Couvrez le comportement réel.** Pour les états en attente, les tests maintiennent la requête ouverte avec `Promise.withResolvers()`, vérifient l'interface en attente, résolvent la promesse dans `act` et vérifient l'interface au repos, comme le font `expectPending` et `expectIdle` dans `auth-forms.component.test.tsx`.
- **Conservez les assertions quand une règle se déclenche.** Lorsqu'un test dépasse `max-statements`, extrayez une fonction utilitaire nommée au lieu de supprimer des vérifications.
- **Chargez chaque fichier de messages.** `i18n.messages.test.ts` charge chaque espace de noms de chaque locale, ce qui couvre les lignes `import.meta.glob` de `i18n.loaders.ts`. Un nouveau fichier de messages est automatiquement couvert par ce test.

## Tests sur une machine chargée

Le délai de Vitest et la marge d'une seconde de `waitFor` et `findBy*` se comptent en temps réel : un test qui fait un travail dont son comportement n'a pas besoin, ou qui attend un minuteur, échoue sur une machine chargée alors que rien n'est cassé. Le délai par défaut reste tel quel ; un test lent est modifié pour en faire moins :

- **Une vérification sur de nombreux fichiers lance un test par fichier.** `check-content.test.ts` exécute `pageProblems` pour chaque page anglaise avec `it.each(sourcePages())`, et un écart nomme sa page.
- **Ce qu'un composant attend avec Suspense est chargé avant son rendu**, comme le fait `preloadNamespaces` pour les traductions. Quand le test porte sur le chargement lui-même, il le résout dans `act`, comme `translations-provider.component.test.tsx` : un contenu qui reprend en dehors de `act` n'apparaît qu'après le délai que React impose à son affichage, sur un vrai minuteur, et le test doit interroger le DOM jusqu'à le voir.
- **Un test remplace la liste d'une zone sans réimporter le composant.** `translations-provider.component.test.tsx` simule `TIME_ZONE_SOURCES` une fois et la remplit dans chaque test, et `time-zone.test.ts` vérifie comment les listes des zones sont réunies. Réimporter un composant après `vi.resetModules()` réévalue tout son graphe d'imports pendant le test.
- **Les fixtures que lit chaque test sont construites une fois par fichier**, comme les messages de `getTestMessages`.
- **Un formulaire se remplit avec `user.paste`, sauf si ses frappes sont le comportement testé.** `fill` dans `admin-course-routes.component.test.tsx` clique dans le champ et colle ; `user.type` exécute la validation et le rendu du formulaire pour chaque caractère.
- **Une longue liste d'options se ré-affiche à faible coût.** Le combobox des fuseaux horaires de `preferences-card.tsx` passe ses options à `ComboboxList` sous forme d'`items` mémoïsés, si bien que React Aria les réutilise quand le formulaire se ré-affiche.

## Les tests suivent les zones [#tests-follow-the-areas]

Les zones qui déclarent leurs propres chemins et entrées de menu (voir [Chemins et navigation](/docs/conventions/routes#paths-and-navigation)) possèdent aussi leurs tests : la CLI `saasyland` peut ainsi retirer une zone d'un projet généré avec ses tests, et tous les autres tests continuent de passer.

Un fichier de test couvre une zone ou un fichier source. Les pages d'administration d'une zone sont testées avec leurs squelettes et leur fil d'Ariane dans `src/routes/__test__/admin-<area>-routes.component.test.tsx`, et leurs loaders dans `admin-<area>-loaders.test.ts` ; `admin-layout`, `admin-dashboard` et `admin-loaders` testent l'interface d'administration elle-même et ne nomment aucune zone. Des fichiers sans lien entre eux ont chacun leur fichier de test, comme `background.component.test.tsx` et `wordmark.component.test.tsx`, et chaque gestionnaire d'API a le sien : `src/routes/api/__test__/auth.test.ts`, `search.test.ts` et `index.test.ts`. `cli.v1.test.ts` couvre les fichiers de route de l’API de licence de la CLI, dont le comportement est testé dans `src/modules/license/__test__/license.api.integration.test.ts`.

Une liste qui couvre plusieurs zones est déclarée par zone et réunie par un barrel :

| Liste                                   | Chaque zone déclare                                                                                                                                | Barrel                             | Lu par                                          |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------- |
| Données de requêtes de l'administration | `seed<Area>Queries` et ses fabriques de lignes dans `src/presentation/components/custom/admin/__test__/<area>.fixtures.ts`                         | `fixtures.entries.ts`              | `adminQueryClient()` dans `fixtures.tsx`        |
| Libellés d'énumérations                 | `src/integrations/use-intl/__test__/<area>.labels.ts`                                                                                              | `labels.entries.ts`                | `enum-labels.test.ts`                           |
| Lignes D1                               | `src/integrations/drizzle-orm/__test__/<area>.rows.ts`                                                                                             | `rows.entries.ts`                  | `d1.integration.test.ts`                        |
| Pages des tests dans le navigateur      | `e2e/data/<area>.pages.ts`                                                                                                                         | `e2e/data/pages.entries.ts`        | `accessibility.spec.ts` et `workspaces.spec.ts` |
| Base de test                            | `e2e/data/<area>.seed.ts`                                                                                                                          | `e2e/data/seed.entries.ts`         | `scripts/seed-test.ts`                          |
| Requêtes publiques                      | `src/integrations/better-auth/__test__/<area>.public-queries.ts`                                                                                   | `public-queries.entries.ts`        | `auth.session.test.ts`                          |
| Doublures des fournisseurs              | `src/platform/testing/mocks/<provider>.ts` : une liste `<PROVIDER>_PROVIDER_DOUBLES`, chaque doublure avec un `origin`, un `respond` et un `reset` | `mocks/providers.entries.ts`       | `mocks/providers.ts`                            |
| Catalogue Polar                         | `src/modules/<module>/__test__/fixtures/<area>.polar-catalogue.ts` : les produits, remises et avantages de clé de licence que la zone vend         | `mocks/polar-catalogue.entries.ts` | `mocks/polar.ts`                                |
| Worker de test                          | `e2e/data/<area>.worker.ts` : préparations et points d'accès de test                                                                               | `e2e/data/worker.entries.ts`       | `src/platform/testing/worker.ts`                |

La base ajoute une liste vide aux barrels que seules des zones facultatives remplissent, `e2e/data/core.seed.ts`, `e2e/data/core.worker.ts`, `mocks/core.providers.ts` et `src/integrations/drizzle-orm/__test__/core.rows.ts`, si bien qu'un projet sans ces zones passe toujours la vérification des types, et `scripts/seed-test.ts` ne lance Wrangler que lorsqu'une zone insère des lignes. Le page object d'une zone vient avec sa propre fixture : `e2e/fixtures/auth.ts` étend le `test` de la base de `e2e/fixtures/test.ts` avec `authPage`, et les specs qui se connectent importent `test` depuis ce fichier.

Les utilitaires que plusieurs zones utilisent n'existent qu'une fois : `renderAdmin` et `renderAdminPage` dans `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` dans `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` et `busyMarkup` dans `src/platform/testing/lib/skeleton.tsx` et, dans les tests dans le navigateur, `AuthPage.signIn`, `BasePage.leaveWhileLoading` et la fixture `pageWithoutJavaScript`. Les specs des pages publiques, comme `accessibility.spec.ts` et `theme.spec.ts`, ne se connectent à aucun compte ; `workspaces.spec.ts` vérifie les pages réservées aux utilisateurs connectés, leur accessibilité et leur thème.

Un test de code partagé qui a besoin d'une entrée fournie par les zones déclare la sienne au lieu de lire celle d'une zone. `dashboard-actions.component.test.tsx` remplace `ADMIN_DASHBOARD_ACTIONS` par une action propre au test, si bien que `DashboardActions` et les emplacements des actions de `AdminDashboardPending` restent couverts dans un projet sans la zone des produits, qui déclare aujourd'hui la seule action du tableau de bord. `server.test.ts`, `root.component.test.tsx` et `vite.test.ts` font de même avec des handlers du Worker, des composants racine et des plugins Vite propres au test, et chaque zone teste ses propres entrées dans `src/data/__test__/<area>.worker.test.ts` et `<area>.vite.test.ts`. Le code partagé que seules des zones optionnelles affichent a son propre test : `pending-blocks.component.test.tsx` couvre les squelettes des champs, des interrupteurs et de la zone de dépôt de fichiers qu'utilisent les squelettes des produits, des cours, des paiements et de l'éditeur d'articles. Un test du contrôle d'accès partagé ne vérifie que les déclarations de la zone d'authentification et celles de Better Auth ; chaque zone teste les permissions qu'elle accorde dans `src/data/__test__/<area>.access.test.ts`, et `access.website.test.ts` fige les permissions de chaque rôle du site.

`auth-plugins.test.ts` couvre la composition des plugins avec un plugin d'exemple, si bien qu'elle reste couverte sans le plugin Polar de la licence, et `navigation.test.ts` n'attend que les groupes d'administration et les colonnes du pied de page qui ont des entrées. `translations-provider.component.test.tsx` prend des namespaces de la base comme exemples, les tests d'authentification prennent les données et les chemins de la zone d'authentification elle-même, comme la liste des sessions et `/app/settings`, et `media-upload-zone.component.test.tsx` vérifie que la zone de dépôt de fichiers des produits et de l'éditeur d'articles dessine le cadre de son squelette.

Les tests des routes et des squelettes de la licence remplacent les sections de l'offre de licence par une section locale au test, et les tests des cours remplacent les octrois d'accès aux cours par `TEST_COURSE_ACCESS` (`src/modules/course/__test__/fixtures/course-access.ts`), si bien que les tests d'aucune des deux zones ne lisent l'autre. `license.course-access.test.ts` couvre ce qui les relie : l'octroi de la licence, avec un instantané de qui peut regarder quelle leçon pour un invité, un compte, l'équipe et chaque niveau et statut de licence.

Un test qui fige le site entier, comme `navigation.website.test.ts` avec l'ordre de chaque menu, n'appartient qu'au site ; les templates ne le génèrent pas.

## Tests dans le navigateur

Playwright exécute le Worker de test compilé : `bun run build:test` le compile avec D1 et KV en local sous `.wrangler/test`, `bun run db:reset:test` recrée cette base de données et y amorce les comptes, la vidéo et le cours de `e2e/data`, et l'entrée de test capture les e-mails sortants sur `/__test/emails` pour qu'une spec puisse suivre un lien de vérification.

- Les specs sont nommées d'après le parcours (`course-admin.spec.ts`, `auth-redirect.spec.ts`) et pilotent la page par rôles et noms accessibles, avec des page objects dans `e2e/pages/`.
- Chaque spec crée les données qu'elle modifie avec des valeurs uniques, comme un slug construit à partir de `crypto.randomUUID()`, et se connecte depuis son propre en-tête `CF-Connecting-IP` : les specs peuvent ainsi s'exécuter en parallèle et être relancées sans entrer en collision entre elles ni avec les limites de débit.
- Un test qui modifie des données créées par le seed, comme les machines d'une licence, reçoit ses propres enregistrements créés par le seed, un pour chaque worker parallèle, afin que deux tests en cours ne modifient jamais le même enregistrement. `cli-licence-api.spec.ts` active des machines sur la licence que `TEST_CLI_LICENSES` dans `e2e/data/licenses.ts` crée pour le `parallelIndex` de chaque worker, que Playwright n'attribue jamais à deux workers à la fois, et sa fixture `cliMachine` libère la machine à la fin du test, si bien qu'une relance repart de la licence créée par le seed. La licence `TEST_LICENSE`, que lit `license.spec.ts`, ne garde que sa machine créée par le seed.
- Une spec n'agit sur une page qu'une fois `waitForAppReady()` de `e2e/pages/base-page.ts` terminé, y compris après une navigation côté client. La méthode se termine lorsque TanStack Router a affiché l'URL courante, ce que la fixture automatique `recordRenders` enregistre à partir de l'événement `onRendered` du routeur, car une navigation côté client change l'URL avant que la route suivante ne s'affiche. Le contenu de la route peut s'hydrater après ce rendu : une spec qui dépend de l'état propre d'un composant, ou qui active un lien hors du contenu avant que celui-ci soit hydraté, appelle donc d'abord `waitForHydration(element)`, qui attend que React ait hydraté l'élément et tout ce qu'il contient ; `LandingPage.goto()` le fait pour le `main` de la page d'accueil. Une spec peut quitter une page pendant son chargement, comme peut le faire un visiteur, et une spec qui collecte les erreurs de page sur plusieurs visites directes ouvre chaque visite dans son propre onglet, comme le fait `auth-routing.spec.ts`. Une spec qui collecte les erreurs de page ne quitte une page qu'une fois sa navigation côté client rendue : WebKit signale comme erreur de page une requête que la page lance après que la spec a commencé à la quitter, `Fetch API cannot load … due to access control checks.`, même si l'application gère l'échec de la requête.
- Les pull requests exécutent chaque spec dans Chromium (`bun run test:e2e:pr`) ; les pushs sur `main` et une exécution hebdomadaire planifiée lancent aussi WebKit.
- Une route, un parcours ou une correction visuelle que les tests unitaires ne peuvent pas voir reçoit une spec : les analyses d'accessibilité et les régressions de navigation de `navigation.spec.ts` et des specs des zones qu'elles concernent, comme `content.spec.ts`, `legal.spec.ts` et `landing.spec.ts`, en sont des exemples. Une spec qui fait défiler la page la rend elle-même assez haute, comme le test de défilement de `navigation.spec.ts`, au lieu de compter sur la longueur d'une page. Une spec qui vérifie où s'arrête un défilement fluide charge d'abord les sections qui se remplissent en différé sur son trajet, comme le test du logo de `landing-controls.spec.ts` le fait avec le bloc des cours : WebKit arrête un défilement fluide quand l'ancrage du défilement compense une section située au-dessus du viewport dont la hauteur change pendant ce défilement.
