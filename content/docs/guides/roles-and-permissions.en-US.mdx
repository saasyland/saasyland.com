title: "Roles and permissions"
description: "Declare the permission statements and role grants in Better Auth's access file and check them in route guards and server functions."
---

Access control uses the Better Auth admin plugin. `src/integrations/better-auth/auth.access.ts` declares the permission statements of every resource in `APP_STATEMENTS`, grants them to the roles and builds Better Auth's access control and the permission check from them, in one file that a person reviews. The role codes live in `src/integrations/better-auth/auth.roles.ts`.

## Statements and roles

```ts title="src/integrations/better-auth/auth.access.ts"
export const APP_STATEMENTS = {
  admin: ["access"],
  category: ["create", "read", "update", "delete"],
  course: ["create", "read", "update", "delete"],
  order: ["read", "update", "refund"],
  product: ["create", "read", "update", "delete", "publish"],
  settings: ["manage"],
  video: ["read", "delete"],
} as const

export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...APP_STATEMENTS, ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole({}),
}
```

- `APP_STATEMENTS` lists one statement per resource, sorted by resource: `admin` and `settings` for the admin console and its settings, `product` for the products page, which lists the Polar catalogue, and for the product module, `category` for the category module's use cases, which no screen uses, `course` and `video` for the courses, and `order` for the orders.
- `defaultStatements` from Better Auth add the `user` and `session` resources (such as `user: ["list", "set-role", "ban", "impersonate", "delete"]` and `session: ["list", "revoke"]`).
- `admin` is granted every statement and Better Auth's admin statements; `customer`, the default role for new users, is granted none.
- A feature that a project leaves out takes its statements with it: `scripts/features.ts` names them, such as `APP_STATEMENTS.course`, and the pruning rule deletes them from the object ([Testing](/docs/conventions/testing#tests-follow-the-features)).
- `ROLE_VALUES` types the `user.role` column and the role schemas in `user.zod.ts`.
- `Permission`, the type `authorized` and `hasPermission` take, is built from `APP_STATEMENTS`, so a statement or action that it does not declare does not compile.

## Where permissions are checked

| Layer           | Check                                                                   |
| --------------- | ----------------------------------------------------------------------- |
| Route guard     | `requireAdmin` requires `admin: ["access"]` for the whole `/admin` area |
| Server function | `authorized({ product: ["update"] })` on every protected operation      |
| Signed-in only  | `authorized()` for operations on the caller's own data                  |
| Anywhere else   | `hasPermission({ permission, role })` returns a boolean                 |

The route guard only decides which pages render. Server functions are callable directly over RPC, so each one must check its own permission. Hiding a button is presentation, not authorization.

## Add a permission

1. Add the action to the resource's statement in `APP_STATEMENTS`, or add the resource in its sorted place, for example `report: ["read", "export"]`. A feature that can be left out names a new resource in its `names` in `scripts/features.ts`, such as `APP_STATEMENTS.report`.
2. Grant it in `ROLES`: `admin` receives the whole of `APP_STATEMENTS`, and a role that should get less is granted a subset.
3. Require it in the server function: `.middleware([authorized({ report: ["export"] })])`.
4. Test both the allowed and the `FORBIDDEN` case, in the owning feature's `src/integrations/better-auth/__test__/auth.access.<feature>.test.ts` and in the use case's tests.

## Add a role

1. Add the code to `ROLE_CODES` and `ROLE_VALUES` in `auth.roles.ts`.
2. Add it to `ROLES` in `auth.access.ts` with the statements it may use.
3. Add the role label to `filters.role.options` in `messages/<locale>/pages.admin.users.json` for every locale.

The auth client (`auth.client.ts`) receives `ac` and `ROLES`, so admin actions in the browser use the same definitions.

## User and session administration

The user and session modules wrap the Better Auth admin API in use cases, each with its own permission: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` and more. Operations on the caller's own data, such as `revokeSession`, use `authorized()` and filter by `context.auth.user.id`.

Locally, `bun run db:seed:local` creates an admin. On preview and production, the first admin is created by `bun run admin:grant:preview <email>` or `bun run admin:grant:production <email>`, which only someone with write access to that D1 database can run, for an account that has verified its email; later admins are made in **Administration → User Management** with **Change role**. See [The first admin](/docs/tooling/database#the-first-admin). An existing admin can also invite a new address with the `admin` role; see [Invitations](/docs/features/users-admin#invitations).
