## Couverture de code [#code-coverage]

`bun run test:coverage` exécute les projets Vitest <RepositoryFact name="vitestProjects" /> et échoue lorsque les lignes, les instructions, les fonctions ou les branches tombent sous <RepositoryFact name="coverageThreshold" unit="percent" /> de <RepositoryFact name="coverageInclude" />. Il exclut <RepositoryFact name="coverageExclude" />. La CI l'exécute sur chaque pull request et chaque push sur `main`.

La suite de tests du navigateur ne compte pas dans ce chiffre : Playwright pilote le Worker de test construit, et aucune couverture n'y est collectée. Une couverture de code complète signifie que chaque ligne mesurée s'est exécutée sous un test qui a vérifié quelque chose. Elle ne signifie pas que les éléments fonctionnent ensemble à travers le Worker, D1, le navigateur et les fournisseurs : la spec de bundle de l'API de licence de la CLI n'envoie que les réponses par défaut, si bien qu'une requête de bundle avec une autre réponse pourrait échouer en production alors que chaque ligne du handler est couverte. La couverture des parcours mesure cette seconde question.

## Couverture des parcours [#flow-coverage]

L'inventaire des parcours liste chaque parcours du site, de l'espace client et de la console d'administration. Chaque zone déclare ses parcours dans `e2e/data/<area>.flows.ts`, réunis par `e2e/data/flows.entries.ts`, avec les types et les constantes dans `e2e/data/flows.ts`, comme les zones déclarent leurs pages et leurs seeds. Un parcours a un identifiant, une zone, le résultat qu'un test doit vérifier et l'un de trois statuts :

- **couvert** : un test Playwright effectue le parcours de bout en bout et vérifie son résultat. Le parcours nomme la spec et le titre complet de chacun de ces tests.
- **manquant** : la fonctionnalité existe, mais aucun test dans le navigateur ne l'effectue de bout en bout. Le parcours dit ce qui manque, et nomme les tests qui en font une partie ainsi que, le cas échéant, l'étape de la suite de parcours client qui l'effectue.
- **à construire** : la fonctionnalité n'existe pas encore, comme les écrans d'administration des produits, des prix et des remises, qui affichent des données d'exemple. Le parcours dit ce qui se trouve à sa place.

`bun run check` exécute `bun run check:flows`, qui liste la suite de tests du navigateur avec `playwright test --list` dans Chromium, comme les pull requests l'exécutent, et échoue lorsque :

- un parcours nomme une spec ou un titre de test que la suite n'a pas, ce que produit le renommage ou la suppression du test ;
- un parcours nomme un test ignoré ;
- deux parcours partagent un identifiant ;
- un parcours manquant ou à construire ne dit pas pourquoi ;
- un parcours nomme une étape que la suite de parcours client n'a pas.

Un parcours couvert ne perd donc son test que lorsque la même pull request change son statut et écrit pourquoi.

Aujourd'hui, sur <RepositoryFact name="flows" /> parcours, <RepositoryFact name="flowsCovered" /> sont couverts, <RepositoryFact name="flowsMissing" /> manquent et <RepositoryFact name="flowsToBuild" /> restent à construire. La suite de tests du navigateur compte <RepositoryFact name="e2eTests" /> tests dans <RepositoryFact name="e2eSpecs" /> fichiers de spec.

De nombreux parcours manquants sont déjà testés en processus : les [suites d'intégration](/docs/architecture/testing-architecture#integration-suites) livrent des webhooks deux fois, dans le désordre et avec de mauvaises signatures, remboursent et révoquent des licences, et atteignent les limites de débit de l'API de licence de la CLI. Un parcours ne compte comme couvert que lorsqu'un test dans le navigateur l'effectue contre le Worker construit : ceux-là comptent donc comme manquants jusqu'à ce qu'un test le fasse.

## Suite de parcours client [#journey-suite]

La [suite de parcours client](/docs/tooling/playwright#journey-suite) achète chaque offre sur la preview dans la sandbox Polar avec la carte de test de Stripe, attend que les webhooks émettent la clé, utilise la CLI publiée sur autant de machines que l'offre le permet et rembourse la commande ; elle met aussi Core à niveau vers Complete moyennant la différence et rembourse la mise à niveau pour revenir à Core. Elle effectue <RepositoryFact name="flowsInJourney" /> des parcours manquants, que le tableau des parcours manquants nomme dans sa dernière colonne, mais aucun workflow de CI ne l'exécute : ces parcours comptent donc comme manquants. L'exécuter en CI demande trois étapes que seul le propriétaire peut accomplir :

1. **Secrets.** L'environnement GitHub `Preview` contient `POLAR_ACCESS_TOKEN`, un token de sandbox avec les scopes `orders:read`, `refunds:write`, `benefits:read` et `license_keys:read` ; `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE` et `POLAR_PRODUCT_ID_AGENCY`, les produits de la sandbox ; et `RESEND_API_KEY`, une clé à accès complet qui peut lire les e-mails qu'envoie la preview. `POLAR_SERVER` vaut `sandbox` et ne demande aucun secret.
2. **Sandbox.** L'organisation de la sandbox correspond au code, ce que vérifie `bun run polar:verify:preview`, et son webhook pointe vers la preview.
3. **Workflow.** Un job exécute `bun run test:journey` avec Chromium installé après le job **Deploy preview**, qui déploie la branche d'une pull request sur la preview. Dans ce dépôt, les workflows demandent la relecture d'une personne : le job est donc proposé plutôt qu'ajouté.

## Prévu [#planned]

- **Tests de mutation.** Un outil de mutation modifie le code testé, un opérateur ou une condition à la fois, et compte les modifications qu'aucun test ne remarque. Il mesure si les tests vérifient des résultats ou se contentent d'exécuter des lignes. Il commencerait par le code des licences, des paiements, des prix, de l'accès aux cours et de l'authentification. Rien n'est encore mis en place.
- **Couverture de code dans le navigateur.** Collecter la couverture V8 pendant que la suite de tests du navigateur exécute l'application construite montrerait quel code aucun test dans le navigateur n'atteint. Elle serait rapportée à côté du chiffre de Vitest, sans s'y ajouter, et sans contrôle bloquant. Rien n'est encore mis en place.
