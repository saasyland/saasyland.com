Vite+ (`vite-plus`, command `vp`) bundles Vite, Vitest, oxlint and oxfmt behind one CLI, and `vite.config.ts` configures all of them. `package.json` overrides `vite` with `@voidzero-dev/vite-plus-core` and pins `vitest` to 5.1.0. `vite-plus` is pinned to an exact version too; upgrade all three together with `vp migrate`, not `bun update`. The package scripts call `vp`; outside them use the global Vite+ CLI or `bunx vp`.

| Command           | Used by                                           |
| ----------------- | ------------------------------------------------- |
| `vp dev`          | `dev`                                             |
| `vp build --mode` | `build:preview`, `build:production`, `build:test` |
| `vp preview`      | `start`, `start:test`                             |
| `vp test`         | `test` and the `test:*` Vitest scripts            |
| `vp lint`         | `lint`                                            |
| `vp fmt`          | `format`, `format:check`                          |
| `vp check`        | `check`, `check:fix`                              |
| `vp staged`       | `check:pre-commit`                                |
| `vp config`       | `prepare`, which installs the Git hooks           |

## Configuration

`vite.config.ts` lists its plugins in `VITE_PLUGINS` and loads them lazily, each entry importing its package inside `load`; a vendor's plugins come from `src/integrations/<vendor>/<vendor>.vite.ts` (see [What the Worker and the build run](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)). Under Vitest only the entries marked `vitest` load, which are `contentIndexes()`, `repositoryFacts()` and `@vitejs/plugin-react`; otherwise the stack is:

- `@cloudflare/vite-plugin`: runs the Worker in the SSR environment and persists local state (in `.wrangler/test` for the `test` mode, `.wrangler/state` otherwise), with `remoteBindings: false`, so no environment's dev server or build connects to a remote binding.
- `fumadocs-mdx`: compiles the docs and blog collections.
- `saasyland:fumadocs-bundled`: keeps `fumadocs-core` and `@fumadocs/base-ui` in the server bundle (`resolve.noExternal`). It and `fumadocs-mdx` come from `fumadocsVitePlugins` (`src/integrations/fumadocs/fumadocs.vite.ts`).
- `contentIndexes` (`scripts/content-indexes.ts`): serves `virtual:content-indexes` and `virtual:docs-search`, the docs, blog and search indexes that `fumadocs.indexes.ts` builds from `content/docs` and `content/blog`; see [Fumadocs](/docs/integrations/fumadocs#content-indexes).
- `repositoryFacts` (`scripts/repository-facts.ts`): serves the `virtual:repository-facts` module, the counts, versions and tool settings that the landing page and the docs print, and the `virtual:repository-tables` module, the tables that only the docs print, both read from the repository at build time; see [Translations and content](/docs/conventions/translations) and [Performance](/docs/conventions/performance#repository-tables-load-with-the-docs).
- `unused-primitives` (`scripts/unused-primitives.ts`): before Tailwind, leaves out the classes of every shadcn primitive that no application source imports; see [Shadcn components](/docs/ui/shadcn-components).
- `@tailwindcss/vite`: Tailwind CSS 4.
- `tanstackStart`: routing, code splitting and prerendering of public pages, filtered by `shouldPrerender` (`src/lib/prerender.ts`).
- `@vitejs/plugin-react`.
- `saasyland:zod-config-chunk` (`src/integrations/zod/zod.vite.ts`): in the client build, puts `src/integrations/zod/zod.config.ts` into zod's own chunk, so zod runs `jitless` before any chunk builds a schema and never probes for `eval` under the content security policy; see [Security and hardening](/docs/features/security).
- `deployedWorker` (`scripts/deployed-worker.ts`): rebuilds the Worker after prerendering without the compiled docs and blog pages and without the landing and legal page translations; see [Cloudflare Workers](/docs/integrations/cloudflare-workers).
- `saasyland:polar-sdk-optional-peers`: marks the optional peer dependencies of `@polar-sh/sdk` that are not installed as external (`build.rolldownOptions.external`); see [Dependencies](/docs/conventions/dependencies).

The dev server listens on `localhost:3000` and fails if the port is taken. `resolve.tsconfigPaths` provides the `~/` import alias. The same file holds the `fmt`, `lint`, `staged` and `test` sections; see [Lint and format](/docs/tooling/lint-format) and [Testing](/docs/tooling/testing).

`vp preview`, which `start`, `start:test` and prerendering run, listens on `127.0.0.1:3000`, the `LOCAL_SERVER` address in `src/data/local-server.ts`, and Playwright opens that address; prerendering uses the same address with a free port. With `localhost`, the server would listen only on the first address Node resolves the name to, `::1`, and every client would try `::1` and then `127.0.0.1`, giving each a short time to answer: on a busy machine that time runs out before the client sees the connection, the client gives up on `::1`, finds nothing on `127.0.0.1`, and prerendering stops with `ETIMEDOUT ::1` and `ECONNREFUSED 127.0.0.1`.

`polarVitePlugins` in `src/integrations/polar/polar.vite.ts` returns a plugin whose `config` hook lists the optional peer dependencies of `@polar-sh/sdk` (OpenTelemetry and `ioredis`) in `build.rolldownOptions.external`. They are not installed, and the module that imports them is tree-shaken out of the Worker.

## Git hooks

`bun install` runs `prepare`, which calls `vp config --no-agent` to install the hook dispatcher for `.vite-hooks/` and then `scripts/verify-git-hooks.ts`, which fails the install when Git would not run that dispatcher. `pre-commit` runs `bun run check:pre-commit`, `prepare-commit-msg` runs `scripts/commit-msg.ts` and `commit-msg` runs `scripts/verify-commit-msg.ts` (see [Conventional commits](/docs/tooling/conventional-commits)), and `post-checkout` runs `vp hooks enable` in a checkout that has no dispatcher yet, such as a worktree that `git worktree add` has just created. `post-merge`, `post-checkout` and `post-rewrite` run `bun install --frozen-lockfile` when `bun.lock` changed, so a pull, a rebase or a branch switch never leaves `node_modules` out of date. `vp hooks status` shows whether the hooks are active in a clone, and [Git and pull requests](/docs/conventions/git-workflow#hooks-in-every-worktree) explains why every worktree needs its own dispatcher.

Prefer the package scripts; call `vp` directly for targeted runs, such as formatting or linting specific paths.
