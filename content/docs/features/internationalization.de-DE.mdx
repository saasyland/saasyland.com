## Locales

`I18N` in `src/integrations/use-intl/i18n.config.ts` definiert `en-US` (Standard), `de-DE`, `es-ES`, `fr-FR`, `it-IT`, `ja-JP`, `pl-PL`, `pt-BR` und `uk-UA`, das Cookie `saasyland.com_locale`, die Standardzeitzone `UTC` und die benannten Datumsformate `FORMATS`.

## URLs

Die Standard-Locale hat kein Präfix; jede andere Locale ist ein Pfadpräfix, zum Beispiel `/docs` und `/pl-PL/docs`. Bei Dokumentanfragen leitet der Worker (`resolveLocale` in `i18n.middleware.ts`) nicht kanonische Pfade mit einem 308 weiter: Aus `/en-US/docs` wird `/docs` und aus `/pl/docs` wird `/pl-PL/docs`. Pfade unter `/api` und `/_serverFn` tragen nie ein Präfix.

Das Router-`rewrite` in `src/router.tsx` entfernt das Präfix aus eingehenden URLs und fügt es ausgehenden hinzu, sodass Routen und Links einfache Pfade verwenden: `<Link to={ROUTES.SIGN_IN}>`. Rohe URLs in der aktuellen Locale, etwa `callbackURL` und `errorCallbackURL` von Better Auth, kommen aus `router.buildLocation(...).publicHref`; `localizePathname({ locale, pathname })` baut eine URL für eine bestimmte Locale, etwa die Links der Sprachauswahl und Links in E-Mails. `AriaProvider` lokalisiert das `href` von React-Aria-Komponenten.

## Locale-Cookie

Weicht die Locale in einer Dokument-URL vom Cookie ab, setzt der Worker das Cookie in der Antwort; kein Code wählt eine Locale anhand des Cookies. `getCurrentLocale()` funktioniert auf beiden Seiten und liest den URL-Pfad, mit `en-US` als Fallback. `/api`- und Serverfunktions-URLs haben kein Präfix, daher gibt die Funktion für sie auf dem Server `en-US` zurück. E-Mails erhalten ihre Locale stattdessen aus dem Ablauf: Auth-E-Mails aus dessen `callbackURL`, die Newsletter-Bestätigung aus der `locale`, die das Formular sendet.

## Meldungen

Meldungen liegen in `messages/<locale>/<namespace>.json`; der Dateiname ist der Namespace, zum Beispiel `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` oder `common`. Jeder Seiten-Namespace enthält `metadata.title` und `metadata.description`.

- Die Root-Namespaces (`common`, `components.*`, `errors*`) werden im Root-`beforeLoad` vorab geladen.
- Ein Layout deklariert `NAMESPACES`, eine Seite `NAMESPACE`. Beide landen in `staticData.namespaces` und werden vom Loader vorab geladen:

```ts
loader: async ({ context }) => {
  const locale = getCurrentLocale()
  const [metadata] = await Promise.all([
    loadPageMetadata({ locale, namespace: NAMESPACE }),
    preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
  ])
  return { locale, metadata }
},
```

- `TranslationsProvider` umschließt den Body des Dokuments und führt die Root-Namespaces mit den Namespaces der passenden Routen in einem `IntlProvider` zusammen, sodass auch Fehleransichten übersetzt sind.
- E-Mails laden ihren Namespace auf dem Server mit `loadNamespace`.

## Komponenten

Jede Komponente ruft `useTranslations` einmal auf und nennt den Übersetzer `t`. Eine Komponente, die zwei Namespaces benötigt, verwendet deren gemeinsamen übergeordneten Namespace oder `useTranslations()` mit vollständigen Schlüsseln.

## Datumsangaben, Zahlen und Zeitzonen

Datumsangaben und Zahlen werden mit `useFormatter` von use-intl formatiert (`format.dateTime`, `format.number`, `format.relativeTime`, `format.list`). Die Locale bestimmt die Konventionen: die Reihenfolge von Tag und Monat, die 12- oder 24-Stunden-Uhr und die Trennzeichen. Die Zeitzone ist die einzige Anzeigepräferenz, die ein Benutzer speichert.

`TranslationsProvider` übergibt `IntlProvider` zwei weitere Werte:

- `timeZone`: die `timezone` des angemeldeten Benutzers aus der aktuellen Session-Query oder ohne Session `I18N.DEFAULT_TIMEZONE` (`UTC`). Der Provider liest die Session, die die Route-Guards von `/app`, `/admin` und den Auth-Routen laden, und ruft sie nie selbst ab, sodass vorgerenderte öffentliche Seiten für jeden Besucher gleich sind und unverändert hydrieren. Ändert sich die Session-Query, etwa nachdem der Benutzer in den [Einstellungen](/docs/features/settings) eine neue Zeitzone gespeichert hat, wird jedes Datum neu gerendert.
- `formats`: `I18N.FORMATS`, die benannten Datumsformate. `src/types/use-intl.d.ts` registriert ihre Namen bei use-intl, sodass ein unbekannter Name die Typprüfung nicht besteht.

| Name            | Beispiel (Englisch)       | Verwendung                                                                                                                               |
| --------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `date`          | Nov 14, 2026              | Der Tag eines Zeitpunkts in der Zeitzone des Lesers, in Tabellen                                                                         |
| `dateTime`      | Nov 14, 2026, 3:04 PM UTC | Ein Zeitpunkt mit Uhrzeit und Zonenkürzel: Lizenzaktivierungen und Datumsangaben von Konten im Adminbereich                              |
| `calendarDate`  | Nov 14, 2026              | Ein Datum ohne Uhrzeit, etwa das Datum eines Blogbeitrags. Es wird in UTC formatiert und verschiebt sich daher nie auf einen anderen Tag |
| `calendarDay`   | November 14               | Tagesbeschriftungen des Analysediagramms im Adminbereich                                                                                 |
| `calendarMonth` | Nov                       | Monatsbeschriftungen des Diagramms im Admin-Dashboard                                                                                    |

Ein Aufruf kann eine Option eines benannten Formats überschreiben: `format.dateTime(new Date(post.date), "calendarDate", { month: "long" })`. Admin-Tabellen zeigen die Datumsangaben anderer Benutzer in der eigenen Zeitzone des Betrachters mit deren Kürzel, sodass eine Spalte in einer einzigen Zeitzone gelesen und sortiert wird; die Zeitzone des Benutzers hat eine eigene Spalte.

## Sprache wechseln

`locale-switcher.tsx` enthält zwei Sprachauswahlen. `LocaleSwitcher` im Marketing-Footer ist ein `<details>`-Menü mit einem einfachen Link pro Locale auf den aktuellen Pfad in dieser Locale und funktioniert daher schon vor der Hydration. `LocaleSelect` in den Seitenleisten der Dokumentation und der Kunden-App ist ein Auswahlfeld im Stil von `ThemeSwitch`, das dieselbe URL öffnet. In beiden Fällen lädt die Wahl einer Sprache ein neues Dokument, und Query-String und Hash werden nicht übernommen. Polnische und ukrainische Seiten laden zusätzlich die Schrift-Subsets Latin Extended und Cyrillic vorab ([Schriften und Branding](/docs/ui/fonts-and-branding)).

## Prüfungen

`bun run check:i18n` prüft die Schlüsselparität zwischen den Locales, löst statische Schlüssel in ihrem `useTranslations`-Scope auf, validiert die ICU-Syntax der Meldungen und prüft die Parität der Dokumentations- und Blog-Inhalte.
