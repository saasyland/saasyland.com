title: "Міграції бази даних"
description: "Змініть схему Drizzle, згенеруйте SQL-міграцію й застосуйте її до кожної бази D1."
---

Базою даних застосунку є Cloudflare D1 (SQLite). Схеми модулів використовують `drizzle-orm/sqlite-core`, `src/integrations/drizzle-orm/drizzle.schemas.ts` збирає їх, а drizzle-kit записує міграції в `src/integrations/drizzle-orm/migrations/` з префіксом часової позначки.

## Порядок роботи

1. Змініть `<table>.schema.ts`. Нову таблицю також експортуйте з `drizzle.schemas.ts`.
2. Згенеруйте SQL:

```sh
bun run db:generate
```

3. Перегляньте згенерований файл і закомітьте його разом зі зміною схеми.
4. Застосуйте його до бази, з якою працюєте, і до кожної віддаленої бази перед розгортанням коду, що від нього залежить.

## Команди

| Команда                          | База даних                                                                                                 |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `bun run db:migrate:test`        | Локальна тестова база в `.wrangler/test`, яку використовують Playwright та ізольований попередній перегляд |
| `bun run db:migrate:local`       | Локальна база для розробки; `bun run dev` і далі використовує віддалені прив'язки                          |
| `bun run db:migrate:development` | Віддалена база середовища розробки, типово спільна з попереднім переглядом                                 |
| `bun run db:migrate:preview`     | Віддалена база попереднього перегляду                                                                      |
| `bun run db:migrate:production`  | Віддалена продакшн-база                                                                                    |

`bun run db:studio:development`, `db:studio:preview` і `db:studio:production` відкривають Drizzle Studio, а скрипти `db:introspect:*` аналізують D1 через його HTTP API. Обидва потребують `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` і `CLOUDFLARE_ACCESS_TOKEN` у відповідному файлі середовища.

## Конвенції схеми

- Дати — це `integer(..., { mode: "timestamp_ms" })` з типовим значенням `(unixepoch() * 1000)`.
- Булеві значення — це `integer(..., { mode: "boolean" })`.
- Індекси, обмеження унікальності, зовнішні ключі й зв'язки лишаються у файлі схеми.
- D1 не має інтерактивних транзакцій. Зберігайте атомарність операції за допомогою однієї SQL-інструкції або `db.batch([...])`, як це роблять `getUsers` і обмежувач запитів.

## Тести

Тестова прив'язка D1 застосовує кожен SQL-файл із теки міграцій до бази SQLite в пам'яті, тож тести, що використовують D1, працюють зі схемою після міграцій. `src/integrations/drizzle-orm/__test__/` перевіряє, що схема, її індекси й зовнішні ключі створюються коректно. Див. [Написання тестів](/docs/guides/writing-tests).

## Наявні дані PostgreSQL

Ці міграції створюють лише схему SQLite. Перенесення даних із попередньої інсталяції PostgreSQL потребує окремих, перевірених експорту й імпорту.
