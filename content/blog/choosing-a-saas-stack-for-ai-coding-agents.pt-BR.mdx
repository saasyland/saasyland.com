O conselho que todos dão sobre escolher um stack para agentes de programação com IA é que o popular é melhor, porque os modelos já viram mais dele. Parece obviamente verdade. Era verdade. Em 2026, isso está em parte invertido, e a prova é um arquivo que o Next.js escreve sozinho no seu projeto.

Execute `next dev` no Next.js 16 e ele escreve isto no seu `AGENTS.md`, sem que ninguém peça:

```markdown
# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all
differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/`
before writing any code. Heed deprecation notices.
```

O framework React mais popular do mundo agora entrega aos agentes de programação um aviso de que o que eles lembram sobre ele está errado. Isso não é uma crítica ao Next.js. É uma resposta honesta a um problema real, e é a declaração mais clara do que a escolha de stack realmente significa em 2026.

Este artigo é sobre esse problema e sobre o que fazer com ele. Não é uma lista de compras. Listas ficam desatualizadas, e uma lista não consegue dizer o que fazer com a biblioteca que você já usa e que não está nela.

## O que um stack realmente faz por um agente de programação com IA?

Um stack não torna um agente correto. Ele muda **quantos programas errados podem ser expressos**. Cada escolha de biblioteca encolhe ou amplia o espaço de código que compila mas está errado. Esse é todo o mecanismo, e é por isso que “amigável para agentes” é uma propriedade que você pode testar, e não uma impressão.

Considere o mesmo erro em duas bases de código. Um agente interpreta uma coluna do banco de dados como string quando ela é um timestamp.

Em um query builder tipado, o erro não pode ser expresso. O código não compila, o agente vê o erro dentro da própria execução e corrige. Custo: cerca de dois segundos.

Em uma consulta bruta que retorna `any`, o erro compila, passa na revisão porque parece correto e produz uma data errada em um e-mail de cobrança seis semanas depois. Custo: um incidente.

Mesmo modelo. Mesmo prompt. Mesmo erro. O stack decidiu se seria um erro de compilação ou um incidente.

## A lacuna de atualidade, e por que o popular deixou de ser um indicador

Este é o argumento que todos usam: bibliotecas populares aparecem mais nos dados de treinamento, então os modelos as escrevem com mais precisão. A primeira metade é verdadeira. A segunda agora depende inteiramente de algo que o argumento ignora: **a velocidade com que a biblioteca muda**.

**A lacuna de atualidade é a distância entre a API de que um modelo se lembra e a API que você realmente entrega.** O volume de dados de treinamento diz com que confiança um modelo vai escrever uma biblioteca. A lacuna de atualidade diz se essa confiança se justifica. São grandezas diferentes e, para frameworks que mudam rápido, agora apontam em direções opostas.

As pesquisas sobre isso são inequívocas. Um estudo com oito bibliotecas amplamente usadas mediu **taxas de uso de APIs obsoletas de 25% a 38%** em código gerado por modelos, atribuindo-as a conhecimento paramétrico desatualizado e à ausência de qualquer visão ao vivo de como a API é hoje ([APILOT, arXiv](https://arxiv.org/pdf/2409.16526)). Trabalhos sobre APIs em evolução descrevem a mesma falha como um conflito de conhecimento: o modelo não está chutando, está lembrando com confiança uma versão que não existe mais ([When LLMs Lag Behind, arXiv](https://arxiv.org/html/2604.09515v1)).

Isso produz uma classificação contraintuitiva. Ordenada por quanto problema a memória do modelo causa:

| Perfil da biblioteca                                                   | Volume de treinamento | Mudanças na API | Efeito líquido no resultado do agente               |
| ---------------------------------------------------------------------- | --------------------- | --------------- | --------------------------------------------------- |
| Popular e estável (React, PostgreSQL, Tailwind)                        | Alto                  | Baixo           | **Melhor.** A memória é grande e ainda está correta |
| Pequena e estável (Zod, a maioria dos utilitários focados)             | Menor                 | Baixo           | **Bom.** Menos memória, mas o que existe está certo |
| Popular e em rápida mudança (um framework no meio de uma versão major) | Alto                  | Alto            | **Pior.** Confiante, fluente e errado               |
| Pequena e em rápida mudança                                            | Baixo                 | Alto            | Ruim, mas o agente hesita em vez de afirmar         |

A célula do canto inferior direito é a interessante. Quando um modelo sabe pouco sobre uma biblioteca, ele tende a hesitar, pesquisar ou ler o código-fonte. Quando sabe muito sobre a _versão anterior_ de uma biblioteca, ele afirma. **A confiança é calibrada pelo volume de treinamento, e não pela correção**, então o pior caso é volume alto somado a mudanças frequentes: um agente que escreve código obsoleto com fluência e nunca demonstra dúvida.

É exatamente o caso sobre o qual o Next.js alerta no bloco acima. É o framework React com mais dados de treinamento que existe, e mudou o suficiente para que o fornecedor decidisse que um aviso impresso para os agentes era necessário.

### O que fazer a respeito

Você não consegue corrigir a memória de um modelo, mas consegue tornar seus erros baratos:

- **Prefira estabilidade a popularidade quando elas entrarem em conflito.** Uma API estável há cinco anos da qual o modelo se lembra pela metade é melhor do que uma API reescrita da qual ele se lembra inteiramente errado.
- **Deixe o compilador pegar o desvio de versão.** Erros de APIs obsoletas só são caros em fronteiras sem tipos. Esse é o verdadeiro argumento a favor de tipos de ponta a ponta, e é mais forte do que o habitual.
- **Fixe e mantenha localmente a documentação que o agente lê.** O próprio Next.js recomenda ler o guia em `node_modules`, e não na web. A documentação local corresponde à versão instalada; um post de blog de 2024, não.
- **Trate dependências novas como não confiáveis.** Mais sobre isso abaixo, porque é um problema de segurança, e não só de correção.

## O Teste de Stack para Agentes

Quatro perguntas por dependência, com 0, 1 ou 2 pontos cada, num total de 8. Ele se aplica a bibliotecas que não existiam quando este texto foi escrito, e é justamente para isso que serve um teste, e não uma lista.

### 1. Restrição: o uso incorreto pode impedir a compilação?

- **0**: A biblioteca devolve `any`, ou a configuração usa chaves em string, ou os erros só aparecem em tempo de execução.
- **1**: Existem tipos, mas são apenas indicativos; uma chamada errada ainda compila com um cast.
- **2**: O uso incorreto é um erro de tipo. Programas errados não podem ser expressos.

### 2. Convergência: existe um jeito óbvio de fazer a tarefa?

Os agentes trabalham por imitação, então uma biblioteca com seis APIs equivalentes dá a você uma chance em seis de acertar aquela que sua base de código já usa.

- **0**: Muitas abordagens equivalentes, todas comuns por aí e todas nos dados de treinamento.
- **1**: Um jeito recomendado, além de alternativas legadas amplamente usadas.
- **2**: Um único jeito, e as alternativas foram removidas, e não apenas descontinuadas.

### 3. Verificabilidade: o agente consegue provar sozinho que funciona?

- **0**: A correção só pode ser observada por uma pessoa olhando o aplicativo em execução.
- **1**: É testável, mas a configuração é manual o bastante para que o agente não a faça.
- **2**: Um comando que o agente já executa cobre isso.

### 4. Atualidade: a memória do modelo sobre ela está atualizada?

- **0**: Mudanças de versão major no último ano, com APIs públicas renomeadas ou removidas.
- **1**: Mudanças menores recentes, ou a documentação com que o modelo aprendeu agora está errada em alguns pontos.
- **2**: A API pública está estável há tempo suficiente para que o código lembrado ainda funcione, ou a biblioteca inclui documentação legível por máquina junto da versão instalada.

**Como ler a pontuação.** De 7 a 8 é uma dependência que pode ser confiada a um agente sem supervisão. De 4 a 6 significa que ela funciona com uma fronteira de tipos ou um teste em volta. 3 ou menos significa embrulhá-la em uma interface que você controla ou aceitar que uma pessoa escreva cada ponto de chamada.

O teste trata deliberadamente do _formato_ de uma dependência, e não da sua qualidade. Bibliotecas excelentes pontuam mal aqui (uma ótima biblioteca no meio de uma reescrita marca 0 em atualidade), e bibliotecas comuns pontuam bem. Isto mede a adequação a agentes, não o mérito.

## Aplicando o teste, camada por camada

O que segue é o stack que entregamos, pontuado honestamente, inclusive onde ele custa alguma coisa. Suas respostas podem ser diferentes; o raciocínio é a parte transferível.

### Linguagem: TypeScript, rigoroso, sem escapatórias

**Pontuação: 8/8.** É a escolha da qual depende todo o resto da lista.

O modo strict é o piso, não o objetivo. As propriedades que importam para agentes são as que as pessoas costumam desativar: nada de `any` implícito, nada de acesso a índice sem verificação, nada de asserções de não nulo. Cada uma dessas flags converte uma classe de resultados confiantes mas errados do agente, de uma surpresa em tempo de execução, em um sublinhado vermelho que o agente vê antes de terminar sua vez.

A versão importa menos que as configurações. Um TypeScript recente configurado de forma frouxa é pior para o trabalho com agentes do que um mais antigo configurado com rigor.

### Runtime e framework: Cloudflare Workers, TanStack Start, React

**Pontuação: 6/8.** Restrição 2, convergência 1, verificabilidade 2, atualidade 1.

Este é o ponto fraco honesto, e é o mesmo sobre o qual o Next.js alerta. O núcleo do React está estável há tempo suficiente para que a memória dos modelos seja confiável. A camada de framework em volta dele não está, e o ponto de atualidade cobra o preço.

O aplicativo público atual usa React com TanStack Start no Cloudflare Workers. Bun e Vite+ fornecem o conjunto de ferramentas local. Os agentes devem ler a documentação do pacote instalado e as skills oficiais e fixadas do TanStack Start e da Cloudflare antes de mudar o código de framework ou de implantação.

A convergência perde um ponto porque route loaders, funções de servidor, cache de consultas e endpoints HTTP comuns têm responsabilidades diferentes. Este repositório demonstra onde cada um pertence: os arquivos de rota coordenam a navegação, os casos de uso das funcionalidades são donos das operações e as integrações de fornecedores são donas da configuração dos serviços.

### Camada de API: funções de servidor do TanStack Start, tipadas de ponta a ponta

**Pontuação: 7/8.**

A propriedade que importa não é o framework, e sim que os tipos de entrada e saída de um handler fiquem visíveis para quem o chama. Quando o formato de uma rota muda, cada ponto de chamada que passou a estar errado deixa de compilar.

Os conselhos dos concorrentes aqui costumam citar bibliotecas RPC específicas. Isso é uma implementação da propriedade, não a propriedade. Qualquer abordagem em que mudar um endpoint quebre o build nos pontos de chamada se qualifica. O que não se qualifica é um `fetch` simples para uma rota JSON tipada à mão no ponto de chamada, porque essa é uma fronteira em que a suposição errada de um agente compila sem erros, vai para produção e é descoberta por um cliente.

**Fronteiras de API sem tipos são onde os erros dos agentes vão para sobreviver.**

### Banco de dados: Drizzle sobre Cloudflare D1

**Pontuação: 8/8.**

O schema é TypeScript, então ele é ao mesmo tempo a fonte das migrações e a fonte dos tipos, e não há um segundo artefato para se desalinhar. Uma consulta que referencia uma coluna inexistente é um erro de compilação, e não um 500.

Duas propriedades importam além da tipagem. As consultas do Drizzle se parecem com SQL, então o conhecimento de SQL existente se transfere. O Cloudflare D1 usa a semântica do SQLite, então os agentes devem seguir o adaptador D1 e a documentação instalada em vez de copiar consultas específicas do Postgres. Migrações versionadas e bindings locais isolados tornam as mudanças revisáveis antes de qualquer operação remota.

### Validação: Zod na fronteira das requisições

**Pontuação: 8/8.** É a camada que a maioria dos stacks pula e a que se paga mais rápido.

Tipos descrevem o que você acredita. Schemas verificam. Todo lugar por onde dados entram no processo (corpos HTTP, variáveis de ambiente, payloads de webhooks, respostas de terceiros, colunas JSON do banco de dados) é um lugar em que o sistema de tipos confia em uma promessa que ninguém verificou.

Nesta aplicação, o Zod valida as entradas das funções de servidor, os parâmetros de busca das rotas e os valores de formulários, e o SDK do Polar verifica e valida os payloads de webhooks. Os bindings de ambiente são tipados pelo Wrangler, e não validados, por isso continuam sendo a fronteira em que se confia sem verificar.

No trabalho com agentes, isso importa mais do que no trabalho humano. Uma pessoa que escreve uma integração tende a desconfiar do payload porque já se queimou antes. Um agente escreve o caminho feliz com total confiança, porque é o caminho feliz que seus dados de treinamento mais contêm. Um schema na borda transforma esse otimismo em um erro capturado, com uma mensagem que nomeia o campo.

### Autenticação: Better Auth, no seu repositório

**Pontuação: 7/8.**

A propriedade relevante para agentes é que a implementação é código-fonte que pertence a você, e não uma chamada hospedada opaca. Um agente consegue ler como uma sessão é emitida, seguir o token até onde ele é verificado e estendê-lo de um jeito que você pode revisar em um diff.

A autenticação hospedada pontua pior aqui por um motivo estrutural, separado do argumento de preço: a metade importante da lógica fica atrás de uma fronteira de API que o agente não consegue ler, então qualquer pergunta sobre o comportamento termina em um palpite ou em uma consulta à documentação, e qualquer personalização vira uma integração em vez de uma mudança.

O ponto que ela perde é a atualidade. É uma biblioteca que muda rápido, em um ecossistema que ainda está se consolidando, então a memória dos modelos sobre sua API não é confiável. É um bom exemplo do teste cumprindo seu papel: uma biblioteca pode ser a escolha certa e ainda pontuar mal em um eixo, e saber qual é o eixo diz onde colocar a proteção.

### Estilos: Tailwind

**Pontuação: 7/8.**

O motivo normalmente citado é o volume de dados de treinamento. O motivo melhor é estrutural: os estilos ficam no próprio elemento que estilizam, então **não há um segundo arquivo que o agente precise lembrar de abrir**. Uma folha de estilos em outro diretório é uma obrigação de sincronização, e o modo de falha dos agentes não é estilizar mal, é atualizar só um dos dois lugares.

Isso vale para além dos estilos. O mesmo argumento favorece testes e tipos colocados junto ao código e vai contra qualquer padrão em que uma mudança precise ser espelhada em algum lugar para onde o agente não tem motivo para olhar.

### Internacionalização: use-intl com verificação de paridade

**Pontuação: 7/8**, e ela ganha seu lugar aqui por um motivo que não é exatamente sobre i18n.

Traduções são o arquétipo da falha silenciosa. Um agente adiciona um recurso, escreve as strings em inglês, e os outros idiomas agora estão com chaves faltando. Nada quebra. Os testes passam. O bug chega exatamente aos clientes que não conseguem relatá-lo com clareza.

A solução não é uma biblioteca melhor, e sim fazer `bun run check:i18n` derrubar a CI quando falta uma chave. Qualquer parte do seu sistema com esse formato (presente em um lugar, silenciosamente ausente em outro) precisa do mesmo tratamento e, até tê-lo, fica invisível para o seu agente e para você.

### Pagamentos e e-mail: Polar, Resend

**Pontuação: 6/8** e **7/8**.

As integrações de pagamento perdem pontos em convergência, e não em qualidade. Este aplicativo usa o checkout do Polar e webhooks verificados, com o tratamento de compras e de chaves de licença nos casos de uso das funcionalidades. Siga essa implementação e o comportamento de novas tentativas documentado pelo provedor. O Resend envia, a partir do Worker, os templates de e-mail localizados.

Os webhooks merecem um alerta próprio, e ele vem abaixo.

### Testes: Vitest e Playwright

**Pontuação: 8/8**, e é a camada que torna todas as outras pontuações utilizáveis.

O ponto não é a cobertura como número. É que `bun run check && bun run test:coverage` existe, termina com 0 ou 1, e um agente consegue executá-lo sem que ninguém explique como. Tudo acima desta linha trata de restringir o que um agente consegue expressar. Esta linha trata de pegar o que ainda passou.

## O número de dependências é superfície para o agente

Cada dependência é uma API que o modelo pode lembrar errado. Isso transforma o argumento habitual de “dependências demais”, que normalmente trata de tamanho do bundle e de cadeia de suprimentos, também em um argumento de correção.

As dependências de runtime estão listadas em `package.json`. O que importa não é a quantidade, e sim o formato: quase todas são tipadas de ponta a ponta ou ficam embrulhadas em uma fronteira que controlamos, então uma suposição errada sobre elas impede a compilação em vez de falhar em produção.

Agora existe um segundo motivo para cuidado, e ele é de segurança. Modelos de fronteira lançados entre outubro de 2025 e março de 2026 foram medidos alucinando nomes de pacotes em taxas entre **4,62% e 6,10%** ([arXiv](https://arxiv.org/pdf/2605.17062)). Atacantes registram esses nomes inventados em registros públicos e esperam, um ataque chamado **slopsquatting** ([Mend](https://www.mend.io/blog/the-hallucinated-package-attack-slopsquatting/)).

A regra prática: **uma dependência adicionada por um agente é uma pull request não revisada de um desconhecido.** Verifique se o pacote existe, se o nome é o que você esperava, e não um quase igual, e se você realmente precisava dele. Lockfiles e uma etapa de revisão para mudanças em `package.json` cobrem a maior parte da exposição com quase nenhum esforço.

## O que os agentes nunca deveriam controlar sozinhos

Algumas partes de um SaaS compartilham uma propriedade: **a versão errada parece certa, passa nos testes, se sai bem na demonstração e só falha em condições que sua suíte de testes não reproduz.** É essa propriedade, e não a dificuldade, que torna inseguro delegá-las.

| Superfície                         | Por que a versão errada passa na revisão                                        |
| ---------------------------------- | ------------------------------------------------------------------------------- |
| Tratamento de sessões e tokens     | Um login que funciona não prova nada sobre expiração, rotação ou revogação      |
| Webhooks de pagamento              | Um handler não idempotente está correto até a nova tentativa chegar             |
| Migrações de banco de dados        | Reversibilidade e perda de dados são invisíveis até o rollback                  |
| Isolamento de tenants              | A consulta está certa para o tenant de teste e errada para o segundo            |
| Qualquer coisa que leia um segredo | Registrar um token em log é uma mudança de uma linha que funciona perfeitamente |

O webhook é o caso mais claro. A Stripe faz novas tentativas quando não recebe um 2xx, então um handler que cobra corretamente na primeira entrega e cobra de novo na nova tentativa passa em todos os testes que um agente pensaria em escrever, porque escrever o teste exige já conhecer o modo de falha. Isso não é um limite da capacidade do modelo. É que a suíte de testes que um agente escreve reflete os modos de falha presentes nos seus dados de treinamento, e bugs de idempotência estão sub-representados ali em relação à frequência com que custam dinheiro de verdade.

Marque esses caminhos no `AGENTS.md` como exclusivos para revisão humana e reforce isso com revisores obrigatórios, para que a intenção seja aplicada, e não apenas confiada.

## O stack, e onde conferi-lo

**Para quem isto não é.** Se você quer algo gratuito para aprender, clone um template e aproveite. Este produto é para quem pretende continuar dono das próprias margens com cinquenta mil usuários.

## Perguntas frequentes

<Accordions>

<Accordion title={"Qual é o melhor stack para agentes de programação com IA em 2026?"}>

TypeScript de ponta a ponta, com uma camada de banco de dados tipada, validação por schema em cada fronteira externa, autenticação que vive no seu repositório e um único comando que verifica tipos, roda o lint e executa os testes. As bibliotecas específicas importam muito menos do que o fato de o uso incorreto delas impedir a compilação. Avalie qualquer candidata em restrição, convergência, verificabilidade e atualidade antes de adotá-la.

</Accordion>

<Accordion title={"Escolher um framework popular ajuda os agentes de programação com IA?"}>

Menos do que antes, e às vezes nada. A popularidade dá ao modelo mais dados de treinamento, mas apenas sobre a versão com a qual ele foi treinado. Um framework que lança mudanças incompatíveis mais rápido do que os modelos são retreinados produz código confiante, fluente e errado. Quando uma biblioteca muda rápido, a estabilidade importa mais do que o volume.

</Accordion>

<Accordion title={"Por que meu agente escreve código usando APIs que não existem mais?"}>

Porque ele está lembrando a versão com a qual foi treinado. Pesquisas mediram taxas de uso de APIs obsoletas de 25% a 38% em oito bibliotecas amplamente usadas, atribuídas a conhecimento paramétrico desatualizado e à falta de uma visão ao vivo de como a API é hoje. O verificador de tipos é a correção mais barata para isso, e é por isso que o problema sobrevive justamente nas fronteiras sem tipos.

</Accordion>

<Accordion title={"Devo deixar um agente de IA escolher minhas dependências?"}>

Não sem verificar se cada pacote existe. Modelos de fronteira lançados entre outubro de 2025 e março de 2026 alucinaram nomes de pacotes em taxas entre 4,62% e 6,10%, e atacantes agora registram esses nomes inventados em registros públicos, um ataque chamado slopsquatting. Trate qualquer dependência nova adicionada por um agente como uma pull request não revisada de um desconhecido.

</Accordion>

<Accordion title={"Um monorepo é melhor para agentes de programação com IA?"}>

Só se as fronteiras forem aplicadas por ferramentas, e não descritas em um README. Um monorepo cujas fronteiras entre pacotes fazem o build falhar quando são cruzadas ensina sua arquitetura a um agente em segundos. Um monorepo mantido por convenção dá ao agente mais lugares para colocar o código certo no pacote errado.

</Accordion>

<Accordion title={"Quais partes de um SaaS um agente nunca deveria escrever sozinho?"}>

Tudo em que um erro de aparência plausível é caro e silencioso: tratamento de sessões e tokens, webhooks de pagamento, migrações de banco de dados, isolamento de tenants e qualquer coisa que leia um segredo. Essas partes têm uma propriedade em comum: a versão errada passa nos testes e se sai bem na demonstração, e só falha em condições que sua suíte de testes não reproduz.

</Accordion>

<Accordion title={"Preciso de tRPC ou oRPC para ter uma API amigável para agentes?"}>

Você precisa de tipos que atravessem a fronteira da rede; a biblioteca específica é secundária. Qualquer abordagem em que um cliente que chama um endpoint alterado deixa de compilar serve. O que não funciona é um fetch simples para uma rota JSON sem tipos, porque essa é uma fronteira em que uma suposição errada compila sem erros e chega à produção.

</Accordion>

<Accordion title={"Quantas dependências são demais para uma base de código assistida por agentes?"}>

Conte superfícies, e não pacotes. Cada dependência é uma API que o modelo pode lembrar errado, então a questão é quantas delas são estruturais, pouco conhecidas e não verificadas. Uma dependência coberta por tipos rigorosos e por um teste custa pouco. Uma que devolve dados sem tipos para a sua lógica de negócio cobra o preço a cada mudança futura.

</Accordion>

<Accordion title={"O Tailwind realmente ajuda os agentes de programação com IA?"}>

Sim, por um motivo estrutural, e não estilístico. Os estilos ficam no próprio elemento que estilizam, então não há um segundo arquivo que o agente precise lembrar de abrir e atualizar. O mesmo argumento favorece testes e tipos colocados junto ao código e vai contra qualquer padrão em que uma mudança precise ser espelhada em um arquivo que o agente não tem motivo para abrir.

</Accordion>

<Accordion title={"Devo trocar de stack para meu agente funcionar melhor?"}>

Quase nunca. O custo da migração é certo e o ganho é limitado, enquanto adicionar tipos rigorosos, validação nas fronteiras e um único comando de verificação ao stack que você já tem é barato e vale imediatamente. Troque de stack quando você já fosse trocá-lo de qualquer forma, e deixe a adequação a agentes ser um critério de desempate, e não o motivo.

</Accordion>
