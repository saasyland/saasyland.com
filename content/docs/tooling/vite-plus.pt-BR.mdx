O Vite+ (`vite-plus`, comando `vp`) reúne Vite, Vitest, oxlint e oxfmt em uma única CLI, e `vite.config.ts` configura todos eles. O `package.json` substitui `vite` por `@voidzero-dev/vite-plus-core` e fixa `vitest` na versão 5.1.0. `vite-plus` também está fixado em uma versão exata; atualize os três juntos com `vp migrate`, e não com `bun update`. Os scripts do pacote chamam `vp`; fora deles, use a CLI global do Vite+ ou `bunx vp`.

| Comando           | Usado por                                         |
| ----------------- | ------------------------------------------------- |
| `vp dev`          | `dev`                                             |
| `vp build --mode` | `build:preview`, `build:production`, `build:test` |
| `vp preview`      | `start`, `start:test`                             |
| `vp test`         | `test` e os scripts `test:*` do Vitest            |
| `vp lint`         | `lint`                                            |
| `vp fmt`          | `format`, `format:check`                          |
| `vp check`        | `check`, `check:fix`                              |
| `vp staged`       | `check:pre-commit`                                |
| `vp config`       | `prepare`, que instala os hooks do Git            |

## Configuração

`vite.config.ts` não nomeia nenhum plugin: ele carrega sob demanda os plugins que cada área declara em `src/data/<area>.vite.ts`, que `src/data/vite.entries.ts` reúne e `vitePlugins` em `src/data/vite.ts` ordena pelo `order` de cada um (veja [O que as áreas adicionam](/docs/architecture/platform-layer#what-the-areas-add)). No Vitest, apenas as entradas marcadas com `vitest` são carregadas, ou seja, `repositoryFacts()`, `contentIndexes()` e `@vitejs/plugin-react`; nos demais casos, a stack é:

- `@cloudflare/vite-plugin`: executa o Worker no ambiente de SSR e persiste o estado local (em `.wrangler/test` no modo `test` e em `.wrangler/state` nos demais), com `remoteBindings: false`, então nenhum servidor de desenvolvimento ou build de nenhum ambiente se conecta a um binding remoto.
- `fumadocs-mdx`: compila as coleções da documentação e do blog.
- `contentIndexes` (`scripts/content-indexes.ts`): serve `virtual:content-indexes` e `virtual:docs-search`, os índices da documentação, do blog e de busca que `fumadocs.indexes.ts` monta a partir de `content/docs` e `content/blog`; veja [Fumadocs](/docs/integrations/fumadocs#content-indexes).
- `saasyland:fumadocs-bundled`: mantém `fumadocs-core` e `@fumadocs/base-ui` no bundle do servidor (`resolve.noExternal`).
- `repositoryFacts` (`scripts/repository-facts.ts`): serve o módulo `virtual:repository-facts`: as contagens, as versões e as configurações de ferramentas que a landing page e a documentação mostram, lidas do repositório durante o build; veja [Traduções e conteúdo](/docs/conventions/translations).
- `unused-primitives` (`scripts/unused-primitives.ts`): antes do Tailwind, deixa de fora as classes de cada primitiva do shadcn que nenhum código da aplicação importa; veja [Componentes do shadcn](/docs/ui/shadcn-components).
- `@tailwindcss/vite`: Tailwind CSS 4.
- `tanstackStart`: roteamento, code splitting e pré-renderização das páginas públicas.
- `@vitejs/plugin-react`.
- `deployedWorker` (`scripts/deployed-worker.ts`): depois da pré-renderização, recompila o Worker sem as páginas compiladas da documentação e do blog e sem as traduções da landing e das páginas legais; veja [Cloudflare Workers](/docs/integrations/cloudflare-workers).
- `saasyland:polar-sdk-optional-peers`: marca como externas as dependências peer opcionais de `@polar-sh/sdk` que não estão instaladas (`build.rolldownOptions.external`); veja [Dependências](/docs/conventions/dependencies).

O servidor de desenvolvimento escuta em `localhost:3000` e falha se a porta estiver ocupada. `resolve.tsconfigPaths` fornece o alias de import `~/`. O mesmo arquivo contém as seções `fmt`, `lint`, `staged` e `test`; veja [Lint e formatação](/docs/tooling/lint-format) e [Testes](/docs/tooling/testing).

`vp preview`, que `start`, `start:test` e a pré-renderização executam, escuta em `127.0.0.1:3000`, o endereço `LOCAL_SERVER` de `src/data/local-server.ts`, e o Playwright abre esse endereço; a pré-renderização usa o mesmo endereço com uma porta livre. Com `localhost`, o servidor escutaria apenas no primeiro endereço para o qual o Node resolve o nome, `::1`, e cada cliente tentaria `::1` e depois `127.0.0.1`, dando pouco tempo para cada um responder: em uma máquina sobrecarregada esse tempo se esgota antes de o cliente perceber a conexão, o cliente desiste de `::1`, não encontra nada em `127.0.0.1` e a pré-renderização para com `ETIMEDOUT ::1` e `ECONNREFUSED 127.0.0.1`.

`src/data/polar.vite.ts` adiciona um plugin cujo hook `config` lista em `build.rolldownOptions.external` as dependências peer opcionais de `@polar-sh/sdk` (OpenTelemetry e `ioredis`). Elas não estão instaladas, e o módulo que as importa é removido do Worker por tree-shaking.

## Hooks do Git

`bun install` executa `prepare`, que chama `vp config --no-agent` para instalar o dispatcher de hooks de `.vite-hooks/` e depois `scripts/verify-git-hooks.ts`, que faz a instalação falhar quando o Git não executaria esse dispatcher. `pre-commit` executa `bun run check:pre-commit`, `prepare-commit-msg` executa `scripts/commit-msg.ts` (veja [Conventional commits](/docs/tooling/conventional-commits)), e `post-checkout` executa `vp hooks enable` em um checkout que ainda não tem dispatcher, como uma worktree que `git worktree add` acabou de criar. `post-merge`, `post-checkout` e `post-rewrite` executam `bun install --frozen-lockfile` quando `bun.lock` mudou, então um pull, um rebase ou uma troca de branch nunca deixa `node_modules` desatualizado. `vp hooks status` mostra se os hooks estão ativos em um clone, e [Git e pull requests](/docs/conventions/git-workflow#hooks-in-every-worktree) explica por que cada worktree precisa do próprio dispatcher.

Prefira os scripts do pacote; chame `vp` diretamente para execuções pontuais, como formatar ou aplicar o lint em caminhos específicos.
