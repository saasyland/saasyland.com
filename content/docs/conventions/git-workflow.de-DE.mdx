Die Historie von `main` ist Teil des Produkts: Jeder per Squash-Merge zusammengeführte Pull Request ist eine Zeile, die sagt, was sich für die Menschen geändert hat, die den Code verwenden.

## Commits

Commit-Nachrichten folgen Conventional Commits und werden ohne Emoji geschrieben; der Hook `prepare-commit-msg` fügt das Emoji des Typs hinzu (die Tabelle steht unter [Conventional Commits](/docs/tooling/conventional-commits)):

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- Der Betreff ist kleingeschrieben, steht im Imperativ und sagt, was die Änderung für ihre Nutzer bewirkt: `feat(course): reorder the catalogue from the course list`, nicht `update course files`.
- Der Scope ist das Modul oder der Bereich: `course`, `auth`, `a11y`, `deps`, `readme`.
- Der Typ ist einer von `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 und `revert` 🗑️; der Hook lehnt jeden anderen ab. Tippe das Emoji nie selbst: Der Hook prüft keinen Betreff, der bereits mit einem Emoji beginnt.
- Teile einen Pull Request in logische Commits auf: die Funktion, ihre Dokumentation als `docs(<scope>)` und unterwegs gefundene Korrekturen.
- Committe nie mit `--no-verify`. Der Hook `pre-commit` führt `bun run check:pre-commit` aus; wenn er fehlschlägt, behebe die Ursache.
- Formatiere und linte nur die Dateien, die du geändert hast, mit `bunx vp fmt <files>` und `bunx vp lint --fix <files>`. Führe `bun run check:fix` oder `vp check --fix` nicht über das gesamte Repository aus: Sie schreiben Dateien um, die du nicht angefasst hast, einschließlich der gemeinsamen Editor-Einstellungen in `.vscode/settings.json`. Wenn `.vscode/` in `git status` erscheint, stelle es aus `HEAD` wieder her.

## Keine KI-Attribution

Commits und Beschreibungen von Pull Requests enthalten keinen `Co-Authored-By`-Trailer für ein KI-Werkzeug, keine Zeile "Generated with" und keine andere KI-Attribution, selbst wenn ein Werkzeug standardmäßig eine hinzufügt. GitHub ordnet die Adresse eines solchen Trailers einem fremden Konto zu, das dann als Mitwirkender des Repositorys erscheint. Dasselbe gilt für Korrekturen, die upstream beigetragen werden (siehe [Abhängigkeiten](/docs/conventions/dependencies)).

## Branches und Worktrees

- Erstelle Branches von `main`, ein Branch pro Pull Request.
- Gib jedem Branch einen eigenen Git-Worktree, statt den Branch eines Checkouts zu wechseln, damit ein Checkout, den ein Editor oder ein anderer Prozess geöffnet hat, nie unter ihm verändert wird:

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Bevor du einem Testlauf vertraust, prüfe `git branch --show-current` in dem Verzeichnis, in dem du getestet hast.
- Bringe einen Pull-Request-Branch auf den neuesten Stand, indem du `main` hineinmergst. Rebase keinen gepushten Branch und pushe ihn nicht per Force-Push: Pull Requests werden per Squash-Merge zusammengeführt, sodass die Historie des Branches nie `main` erreicht, und ein Force-Push zerstört nur die Review-Historie.

## Pull Requests

- **Klein und gezielt.** Eine Korrektur, eine Funktion oder ein Refactoring pro Pull Request. Eine große Funktion wird zu einem Stapel von Pull Requests, die jeweils für sich reviewbar sind, wie es bei Videos, Kursen und der Kursverwaltung im Admin der Fall war.
- **Der Titel ist der Squash-Commit.** Verwende das Commit-Format; der Titel wird zum Betreff auf `main`.
- **Die Beschreibung** hat eine `## Summary` dessen, was sich geändert hat und warum, einen `## Test plan` mit den Befehlen, die du ausgeführt hast, und ihren Ergebnissen, und eine `## Docs`-Liste der Seiten, README-Abschnitte und Texte, die du aktualisiert hast. Schreibe sie schlicht, ohne Marketingsprache.
- **Jeder Pull Request aktualisiert, was er ungenau macht:** die README, die Dokumentationsseiten in jeder Locale und alle Website-Texte oder Aussagen der Landingpage, die er berührt, und er fügt seinen [Changelog-Eintrag](#changelog-entries) hinzu. Ungenauigkeiten in Code, den du nicht geändert hast, bekommen einen eigenen Pull Request.

## Changelog-Einträge [#changelog-entries]

Jeder Pull Request fügt dem [Changelog](/docs/project/changelog) einen eigenen Eintrag hinzu, sodass gleichzeitig offene Pull Requests nie dieselbe Datei bearbeiten.

- **Nach dem Pull Request benennen.** Öffne den Pull Request und lege dann `content/changelog/<number>.<locale>.mdx` in jeder Locale an: eine Aufzählung ohne Frontmatter, was sich für die Nutzer des Codes ändert, mit Links auf die betroffenen Dokumentationsseiten.
- **Nie ein Datum schreiben.** Die Changelog-Seite und die Release Notes entnehmen den Tag jedes Eintrags der Git-Historie: den Tag (UTC) des Squash-Commits, dessen Betreff GitHub mit `(#<number>)` abschließt. Bis der Pull Request gemergt ist, steht sein Eintrag unter **Unveröffentlicht**.
- **CI prüft es.** In einem Pull Request schlägt `bun run check` fehl, solange `content/changelog/<number>.en-US.mdx` fehlt, und `check:i18n` vergleicht jede Übersetzung damit wie bei einer Dokumentationsseite. Eine Datei, die weder nach einer Pull-Request-Nummer noch nach einem vollständigen Commit-Hash benannt ist, schlägt ebenfalls fehl: Die wenigen Änderungen, die ohne Pull Request in `main` gelangt sind, tragen den Namen ihres Commits.

## Prüfungen

Die CI führt `bun run check` und `bun run test:coverage` aus, baut dann den Test-Worker und führt die Browser-Suite in Chromium aus; nur wenn beides erfolgreich ist, deployt sie eine Preview. Warte auch auf das Preview-Deployment: Es ist der einzige Schritt, der den Worker zu Cloudflare hochlädt, und die Upload-Limits von Cloudflare haben schon ein Deployment scheitern lassen, das jede andere Prüfung bestanden hatte. Siehe [CI/CD](/docs/tooling/ci-cd).
