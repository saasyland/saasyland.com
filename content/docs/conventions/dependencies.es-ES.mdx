El repositorio usa la última versión publicada de cada dependencia. Una actualización que rompe algo se arregla hacia delante, en el código o en el proyecto original, nunca volviendo atrás.

## Versiones de las herramientas [#upgrading]

Actualiza las dependencias, las skills para agentes y las GitHub Actions con un solo comando, en una rama propia:

```sh
bun run deps:update
```

`scripts/update-dependencies.ts` ejecuta, en este orden:

1. `vp migrate` de la versión más reciente de Vite+ cuando es más nueva que el `vite-plus` de `package.json`, lo que mueve juntos `vite-plus`, el alias `vite` y `vitest`;
2. `bun update --latest` para cada dependencia declarada con un rango `^` o `~`, lo que la lleva a su versión más reciente, incluida una nueva versión mayor, y conserva el rango;
3. `bun run skills:update`, que lleva las [skills para agentes](/docs/tooling/agent-skills) a los commits más recientes de sus orígenes y registra las versiones de los paquetes que documentan;
4. `scripts/github-actions.ts`, que lee con `git ls-remote` las etiquetas de versión del repositorio de cada action de `.github/workflows/` y `.github/actions/`, toma la versión estable más reciente, sigue una etiqueta anotada hasta su commit y reescribe cada `uses:` con ese commit y esa etiqueta ([CI/CD](/docs/tooling/ci-cd)).

Deja intactas las versiones fijadas exactas, porque cada una tiene un motivo en esta página, y termina nombrando cada paquete fijado que tiene una versión más reciente. `bun run check` falla mientras un paquete que documenta una skill se haya movido desde el último `skills:update`, de modo que las dependencias y las skills no pueden desviarse. Cada semana, el flujo de trabajo `updates.yml` enumera las actualizaciones disponibles en una issue de GitHub; consulta [CI/CD](/docs/tooling/ci-cd#updates).

Después, para cada paquete que se movió:

- Bun es el gestor de paquetes y el ejecutor de scripts. `packageManager` en `package.json` (Bun <RepositoryFact name="bunVersion" />) es el único lugar donde se fija su versión; CI la lee de ahí. `bun.lock` está incluido en el repositorio.
- Node se toma de `.nvmrc` (<RepositoryFact name="nodeVersion" />), y `engines.node` exige al menos esa versión.
- `remotion/` es la única excepción, con su propia cadena de herramientas de npm, que solo se instala al editar los vídeos de la página de inicio. Su `typescript` es la versión más reciente que `typescript-eslint`, que ejecuta las reglas de lint de Remotion, acepta como dependencia peer, porque TypeScript 7 no incluye la API del compilador que lee `typescript-eslint`. Los paquetes que comparte con el sitio web, `@saasyland/stack`, `lucide-react`, `react` y `react-dom`, están fijados a la versión más baja que acepta el `package.json` del sitio, porque los vídeos renderizan archivos del sitio que los importan, y `src/data/__test__/cli.test.ts` falla cuando las dos difieren.

## Actualizar

1. Lee el registro de cambios y la guía de migración de la nueva versión, preferiblemente la copia incluida en `node_modules/<package>`.
2. Cambia el código para que se ajuste al uso documentado de la nueva versión.
3. Verifica en este orden, y no des nada por terminado antes de que pase el último paso:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` y las pruebas se ejecutan sin el build de Cloudflare y TanStack Start, así que pueden pasar mientras el build está roto. Ocurrió dos veces en una misma actualización: un `@polar-sh/sdk` nuevo no se podía empaquetar, y una versión de TanStack Start cambió el marcado `modulepreload` que reescribe `optimize-prerendered-html.ts`. Ambos problemas solo aparecieron en `build:test`. Después de un build, `find dist/server -name '*.map'` no debe imprimir nada; `upload_source_maps: false` en `wrangler.jsonc` existe porque el Worker con sus source maps supera el tamaño que Cloudflare acepta en una subida (consulta [Cloudflare Workers](/docs/integrations/cloudflare-workers)).

Nunca fijes un paquete a una versión anterior para evitar un cambio incompatible, y nunca añadas a la aplicación código que sortee un bug de una biblioteca.

## Cuando el bug está en el paquete [#when-the-bug-is-upstream]

Cuando la aplicación ya sigue el uso documentado y es la nueva versión la que falla, conserva la nueva versión y aplica tú la corrección:

1. Demuestra el bug con una reproducción mínima fuera de este repositorio.
2. Escribe el cambio más pequeño que lo corrija en el paquete, igual que la corrección que vas a proponer en el proyecto original, y guárdalo con `bun patch`. El parche queda en `patches/<package>@<version>.patch` y en `patchedDependencies`, y el paquete se fija a esa versión exacta para que el parche se siga aplicando.
3. Informa del bug en el proyecto original y abre una pull request con la corrección, siguiendo las normas de contribución de ese proyecto.
4. Elimina el parche en cuanto una versión publicada contenga la corrección. Antes de conservar o documentar un parche, comprueba con `npm view <package> version` si esa versión ya ha salido.

Los parches actuales:

- `patches/@tanstack%2Frouter-core@1.171.39.patch` lleva dos correcciones. Evita que el primer renderizado del router tras la hidratación vuelva a desplazar la ventana hasta arriba, un fallo notificado upstream como [TanStack/router#8933](https://github.com/TanStack/router/issues/8933) y corregido como se propone en [TanStack/router#8934](https://github.com/TanStack/router/pull/8934). Además, da al stream que devuelve `transformReadableStreamWithRouter` un `highWaterMark` de 0, para que nada lea el stream de React antes de que `renderRouterToStream` haya esperado a `allReady` en la petición de un rastreador: con el valor por defecto de 1, el stream leía la salida de React de inmediato, React enviaba la página con sus secciones en streaming todavía pendientes y un rastreador recibía cada una como un segmento oculto que un script coloca en su sitio. `e2e/specs/course-seo.spec.ts` comprueba que un rastreador recibe una lección con su reproductor en su sitio.
- `patches/@tanstack%2Freact-router@1.170.46.patch` evita que `lazyRouteComponent` recargue una página cuyo chunk de ruta canceló el navegador porque el visitante se está yendo. Es la corrección propuesta en [TanStack/router#8830](https://github.com/TanStack/router/pull/8830), ampliada al chunk que la página empieza a cargar después de `beforeunload` y que Safari hace fallar al instante.
- `patches/framer-motion@14.14.0.patch` hace que `LazyMotion` ignore un bundle de funcionalidades que no se puede cargar en lugar de dejar el rechazo sin gestionar. `motion` está fijado a 14.14.0 junto con él. Motion integró la corrección de [motiondivision/motion#4089](https://github.com/motiondivision/motion/issues/4089) después de publicar 14.14.0, así que el parche se va con la primera versión que la incluya.
- `patches/better-auth@1.7.27.patch` permite que el plugin `haveIBeenPwned` haga el hash de una contraseña fuera de un endpoint de Better Auth, como hace `(await auth.$context).password.hash()` en los tests de integración: lee el contexto del endpoint con `tryGetCurrentAuthEndpointContext` en lugar de `getCurrentAuthEndpointContext`, que ahí lanza una excepción. `better-auth` está fijado a 1.7.27 junto con él. Es la corrección propuesta en [better-auth/better-auth#12873](https://github.com/better-auth/better-auth/pull/12873).
- `patches/playwright-core@1.65.1.patch` permite que el driver de WebKit de Playwright siga una navegación entre sitios hacia una página que envía `Cross-Origin-Opener-Policy`, como la vuelta desde el checkout alojado de Polar al espacio de trabajo: la compilación de WebKit de Playwright 1.65 crea una segunda página provisional para el cambio antes de destruir la primera, y el driver ahora descarta la primera en lugar de fallar una aserción en `WKPage._onTargetCreated`. Con él, `@playwright/test` queda fijado en 1.65.1. Está notificado upstream como [microsoft/playwright#44254](https://github.com/microsoft/playwright/issues/44254), que Playwright ha cerrado como completado; ninguna versión estable posterior a 1.65.1 incluye todavía la corrección, así que el parche se queda hasta que salga una.

`@tanstack/router-core` es una dependencia directa, porque `src/lib/stale-build.ts` importa de ella `isModuleNotFoundError`, y está fijada a 1.171.39 para que su parche siga aplicándose. `@tanstack/react-router` está fijado a 1.170.46 y `@tanstack/react-start` a 1.169.7, porque dependen exactamente de las versiones de TanStack parcheadas. Un parche para `fumadocs-mdx` 15.6.0 se mantuvo del mismo modo y se eliminó cuando 15.6.1 publicó la corrección del proyecto original, y lo mismo ocurrió con los parches para `@fumadocs/base-ui` y `fumadocs-core` 16.19.2 cuando 16.19.3 publicó las suyas. El parche para `@videojs/utils` 10.4.0 se quitó cuando 10.5.0 publicó su corrección. Un parche que daba al layout de la documentación de Fumadocs un slot `skipToContent` se eliminó cuando Fumadocs rechazó el slot; ahora `globals.css` oculta el enlace de Fumadocs y el enlace de salto propio del sitio lleva al artículo de la documentación (consulta [Sitio de documentación](/docs/features/docs-site)).

Los proyectos que escribe `saasyland init` llevan sus propias copias de los parches que necesita su stack, en su propia carpeta `patches/` y en `patchedDependencies`, con cada paquete parcheado fijado a la versión parcheada: las plantillas de TanStack Start añaden los parches de `@tanstack/router-core` y `@tanstack/react-router`, y todo proyecto recibe el de `framer-motion`. Los parches de `router-core` y `framer-motion` son los mismos archivos que aquí. El parche de `react-router` del proyecto es solo la corrección propuesta en TanStack/router#8830, sin la ampliación de este sitio para un chunk que empieza a cargarse después de `beforeunload`. Los parches de `better-auth` y `playwright-core` se quedan aquí: un proyecto generado no usa el plugin `haveIBeenPwned` ni la prueba en WebKit del checkout de Polar que tiene este sitio. Cuando una versión incluye una corrección, el proyecto borra el parche y su entrada de `patchedDependencies` y pasa a esa versión, igual que este sitio (consulta [SaaSy Land CLI](/docs/cli#create-a-project)).

Un parche cambia los archivos de un paquete, no las versiones que Bun instala para él. Cuando un paquete fija una de sus propias dependencias por debajo de la versión que usa la aplicación y los tipos de las dos copias no coinciden, una entrada de `overrides` en `package.json` la sube en su lugar. Hoy no hace falta ninguna. `@polar-sh/adapter-utils` 1.1.1, que usa `@polar-sh/better-auth`, fija `@polar-sh/sdk` 1.3.1, así que Bun instala esa copia junto a la 1.3.2 de la aplicación. El adaptador importa el SDK solo para tipar el `webhooks({ onPayload })` del plugin, y `handlePolarEvent`, que recibe el payload de la 1.3.2, acepta el de la 1.3.1, porque la 1.3.2 solo amplía tipos, como `trial_ended` entre los estados de suscripción. Cuando una versión posterior del SDK cambie un payload de forma que la copia del adaptador no lo acepte, `bun run check` fallará en `handlePolarEvent`; entonces una entrada de `overrides` para `@polar-sh/sdk` sube la copia del adaptador hasta que una versión de `@polar-sh/adapter-utils` dependa de ese SDK (`npm view @polar-sh/adapter-utils dependencies`).

## Avisos de seguridad [#security-advisories]

`bun run deps:audit` ejecuta `bun audit` sobre las dependencias de producción en el job `check` de cada pull request y de cada grupo de fusión, y de nuevo cada semana en `updates.yml` ([CI/CD](/docs/tooling/ci-cd#checks)). Falla ante un aviso de gravedad <RepositoryFact name="auditBlockingSeverities" /> que no cubra ninguna excepción vigente y muestra los de menor gravedad sin fallar.

Las alertas de Dependabot cubren `remotion/package-lock.json`, pero GitHub no lee `bun.lock`, así que revisa la aplicación con `bun audit` y el proyecto de vídeo con `npm audit` dentro de `remotion/`. Resuelve un aviso con la versión más reciente del paquete que trae el paquete vulnerable. Si el rango de versiones de ese paquete ya admite la versión corregida, basta con actualizar el lockfile: `bun update`, o `npm update` en `remotion/`.

Mientras ninguna versión del paquete padre admita la corrección, una entrada en `overrides` sube el paquete vulnerable, y se elimina en cuanto una versión del padre lo haga. Las entradas actuales:

- `package.json`: `"minimatch": "^11.0.1"`. `shadcn` llega a `minimatch` ^10 a través de `ts-morph` 26 y `@ts-morph/common`, y solo `minimatch` 11.0.1 corrige GHSA-g3hv-75wg-m249. Elimínala cuando `shadcn` dependa de una versión de `ts-morph` que incluya [dsherret/ts-morph#1697](https://github.com/dsherret/ts-morph/pull/1697).
- `remotion/package.json`: `minimatch` ^11.0.1 bajo `@typescript-eslint/typescript-estree`, por el mismo aviso. `@remotion/eslint-config-flat` fija `typescript-eslint` en 8.71.2, cuyo parser pide `minimatch` ^10. Elimínala cuando `@remotion/eslint-config-flat` dependa de una versión de `typescript-eslint` que incluya [typescript-eslint/typescript-eslint#13145](https://github.com/typescript-eslint/typescript-eslint/pull/13145).

`bun audit` sigue informando de un aviso que no tiene ninguna corrección que aplicar:

- `esbuild` 0.18.20 (GHSA-67mh-4wv8-2f99, moderada), a través de `drizzle-kit` y `@esbuild-kit/esm-loader`. `drizzle-kit` 0.31.11 declara el loader pero nunca lo importa, y el aviso afecta al servidor de desarrollo de esbuild, que aquí nada inicia. [drizzle-team/drizzle-orm#5304](https://github.com/drizzle-team/drizzle-orm/issues/5304) sigue su eliminación; las release candidates de `drizzle-kit` 1.0 ya no dependen de él.

GitHub retiró el aviso de `deepmerge` 4.3.1 (GHSA-gcqx-w48m-w2h4), que traían `shadcn` y `@shadcn/registry`, tras [github/advisory-database#10910](https://github.com/github/advisory-database/issues/10910), así que `bun audit` ya no lo muestra.

### Excepciones [#audit-exceptions]

Un aviso que aún no tiene corrección, normalmente en un paquete transitivo, recibe una excepción en `AUDIT_EXCEPTIONS` (`src/data/dependency-audit.ts`), la única lista de excepciones, añadida en un pull request propio y revisada como cualquier otro cambio. Cada entrada nombra el aviso de GitHub (`advisory`) y el paquete (`package`), explica por qué se acepta el aviso hasta que haya corrección (`reason`) e incluye la fecha de la revisión (`reviewedOn`), la fecha en que termina la excepción (`expiresOn`) y un enlace a la issue o el pull request del proyecto original que sigue la corrección (`tracking`). El análisis falla ante una excepción:

- que ha caducado: revísala de nuevo con fechas nuevas o elimínala;
- que dura más de <RepositoryFact name="auditExceptionMaxDays" unit="day" /> desde su revisión, o cuya fecha de revisión está en el futuro;
- que ya no coincide con ningún aviso alto o crítico notificado, para que ninguna sobreviva a su motivo.

Cada aviso que permite una excepción se muestra como advertencia en cada ejecución, así que ninguna excepción pasa desapercibida, y `dependency-audit.test.ts` comprueba los campos de cada entrada. El pull request que incorpora la corrección elimina la entrada.

## Las entradas de Vite+ en package.json

```json
"vite": "npm:@voidzero-dev/vite-plus-core@8.3.8000",
"vite-plus": "1.7.0",
"vitest": "5.1.0"
```

Estas líneas, junto con el mismo alias `vite` y la misma versión de `vitest` en `overrides`, son exactamente lo que escribe el propio migrador de Vite+: `vite-plus` está fijado a una versión exacta, Bun necesita el núcleo como dependencia directa `vite`, y `vitest` aparece porque lo necesitan `@vitest/coverage-v8` y los tipos de las pruebas. Desde `vite-plus` 1.7.0, el núcleo lleva la versión de la release de Vite que incluye, así que 8.3.8000 es Vite 8.3.8; `vp toolchain` muestra la correspondencia. Actualízalas juntas con `vp migrate`, nunca con `bun update`. Para saber si alguna de ellas puede eliminarse, copia el proyecto, ejecuta `vp migrate` sobre la copia y compara el resultado; no lo decidas razonando sobre ello. La entrada `minimatch` de `overrides` es la corrección de seguridad descrita arriba, y `vp migrate` la deja intacta.

`build.rolldownOptions.external`, que fija `src/integrations/polar/polar.vite.ts`, enumera dependencias peer opcionales de `@polar-sh/sdk` que no están instaladas y que el tree-shaking elimina del Worker; consulta [Vite+](/docs/tooling/vite-plus). Elimina la lista cuando Polar corrija su empaquetado.

## Añadir una dependencia

Comprueba primero si algún paquete que ya está en `package.json` hace el trabajo, para que cada responsabilidad siga teniendo una sola biblioteca. Añade una dependencia de ejecución con `bun add` y una herramienta con `bun add --dev`, y usa la skill para agentes del proveedor que figura en `skills-lock.json` cuando exista (consulta [Skills para agentes](/docs/tooling/agent-skills)). Cuando una skill de un proveedor documenta el nuevo paquete, añade el paquete a su origen en `SKILL_SOURCES` (`src/data/skills.ts`) y ejecuta `bun run skills:update`.
