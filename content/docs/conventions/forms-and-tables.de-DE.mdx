Formulare und Tabellen sind die beiden Stellen, an denen sich selbstgebaute Varianten am schnellsten vermehren. Für beide gibt es genau einen Weg, übernommen aus den eigenen Anleitungen der Anbieter statt hier erfunden.

## Formulare

Jedes Formular folgt der [TanStack-Form-Anleitung von shadcn](https://ui.shadcn.com/docs/forms/tanstack-form): `useForm` aus `@tanstack/react-form`, das Zod-Schema des Moduls als Validator und die shadcn-Komponenten `Field`, `FieldLabel`, `Input`, `Textarea` oder `Select`. `src/presentation/components/custom/admin/courses/course-form.tsx`:

```tsx
const form = useForm({
  defaultValues: course === undefined ? NEW_COURSE : toValues(course),
  listeners: { onBlur: validateOnBlur },
  onSubmit: ({ value }) => {
    if (course === undefined) {
      create.mutate(value)
      return
    }
    update.mutate({ ...value, courseId: course.id })
  },
  validators: { onChange: courseZodSchemas.createCourse },
})

return (
  <form
    noValidate
    onSubmit={(event) => {
      void submitForm(event, form)
    }}
  >
```

- **Das Schema ist das Schema des Servers.** Der Validator ist dasselbe `courseZodSchemas.createCourse`, mit dem die Server Function parst, oder ein `.pick(...)` davon, wie `chapter-dialog.tsx` mit `chapterZodSchemas.updateChapter.pick({ summary: true, title: true })`. Schreibe nie ein zweites Schema nur für das Formular.
- **Ein Validator, `onChange`.** TanStack Form führt ihn bei jeder Änderung und beim Absenden noch einmal aus. Füge keine `onSubmit`-Kopie hinzu: Ein Fehler des Absende-Validators verschwindet erst, wenn sich sein eigenes Feld ändert, daher blieb ein feldübergreifender Fehler wie `passwordsMustMatch` rot, nachdem das andere Feld korrigiert war.
- **Das Feld validieren, das der Besucher verlässt.** `listeners: { onBlur: validateOnBlur }` führt denselben Validator aus, wenn ein Feld den Fokus verliert, sodass ein Feld, das der Besucher nur durchquert hat, seinen Fehler genau in diesem Moment bekommt und nicht erst bei einem späteren Tastendruck in einem anderen Feld.
- **Über `submitForm` absenden.** `submitForm(event, form)` aus `src/integrations/tanstack-form/form.submit.ts` unterbindet das eigene Absenden des Browsers und ruft `form.handleSubmit()` auf. Ist das Formular ungültig, markiert es jedes Feld als verlassen, sodass alle Fehler auf einmal erscheinen, und setzt den Fokus auf das erste Steuerelement mit `aria-invalid="true"`.
- **`noValidate`.** Die eigene Validierung des Browsers ist abgeschaltet, sodass jede Meldung aus dem Schema stammt und übersetzt ist.
- **Standardwerte sind über das Modul-Interface typisiert**, etwa `NEW_COURSE: Course["createCourse"]`.
- **Mit der Mutation absenden.** `onSubmit` ruft `mutate` aus den Mutation-Optionen auf, und der Absende-Button zeigt den Ladezustand: `<Button isPending={create.isPending || update.isPending} type="submit">`.

### Wann Fehler erscheinen

Fehler folgen der Regel „früh belohnen, spät bestrafen“:

- Während der Besucher in einem Feld tippt, zeigt das Feld keinen Fehler und hat kein `aria-invalid`, auch wenn der Wert noch nicht gültig ist.
- Wenn der Besucher das Feld verlässt oder abzusenden versucht, zeigt das Feld seinen Fehler.
- Ab dann validiert das Feld bei jeder Änderung neu, sodass der Fehler mit dem Tastendruck verschwindet, der den Wert korrigiert.
- Rückmeldungen, die Fortschritt belohnen, etwa die Liste der Passwortanforderungen, aktualisieren sich ab dem ersten Tastendruck, denn sie sind kein Fehler.
- Serverfehler, etwa eine bereits registrierte E-Mail-Adresse, erscheinen als Toast.

`isFieldInvalid(field)` aus `src/integrations/tanstack-form/form.fields.ts` ist die eine Stelle, die das entscheidet: `field.state.meta.isBlurred && !field.state.meta.isValid`. Übernimm nicht die `isTouched`-Prüfung aus der Anleitung von shadcn: TanStack Form setzt `isTouched` beim ersten Tastendruck, wodurch ein halb getipptes Passwort rot wurde.

### Felder

Jedes Feld ist ein shadcn-`Field`, dessen ungültiger Zustand von `isFieldInvalid` kommt. Aus `course-fields.tsx`:

```tsx
<Field data-invalid={isFieldInvalid(field)}>
  <FieldLabel htmlFor={id}>{label}</FieldLabel>
  <Input
    aria-describedby={`${id}-error`}
    aria-invalid={isFieldInvalid(field)}
    className={cn({ "font-mono": isCode })}
    id={id}
    lang={lang}
    name={field.name}
    onBlur={field.handleBlur}
    onChange={(event) => {
      field.handleChange(event.target.value)
    }}
    value={field.state.value ?? ""}
  />
  <FieldMessage field={field} id={id} />
</Field>
```

- `data-invalid`, `aria-invalid` und das Fehlerelement lesen alle `isFieldInvalid(field)`, sodass ein Screenreader genau dann meldet, dass ein Feld ungültig ist, wenn der Fehler erscheint, und nie, während der Besucher noch tippt.
- Jedes Steuerelement ruft `field.handleBlur` in `onBlur` auf; eine Dateiauswahl ruft es auf, nachdem eine Datei gewählt wurde.
- Das Eingabefeld verweist mit `aria-describedby` immer auf die ID seines Fehlers. Das Fehlerelement wird nur gerendert, solange das Feld ungültig ist, und ein Verweis auf ein fehlendes Element beschreibt nichts.
- Fehler werden über `ValidationFieldError` aus `custom/validation-field-error.tsx` gerendert. Zod-Meldungen sind Übersetzungsschlüssel, daher schlägt die Komponente sie im Namespace `<table>.validations` des Moduls nach und interpoliert die Zahlen aus `<MODULE>_VALIDATION_PARAMS`:

```tsx
<ValidationFieldError
  id={`${id}-error`}
  message={fieldErrorMessage(field.state.meta.errors)}
  namespace="course.validations"
  params={COURSE_VALIDATION_PARAMS}
/>
```

- Keine handgeschriebenen `<input>`-, `<label>`- oder `<button>`-Elemente und keine Wrapper-Komponente um ein Feld für ein einzelnes Formular. Eine Feldkomponente, die mehrere Formulare eines Bereichs teilen, liegt in einer Datei, so wie `CourseTextField`, `CourseTextAreaField` und `CourseOptionField` für die Kurs-, Kapitel- und Lektionsformulare.
- Serverfehler werden mit `toast.error(errorMessage(error))` angezeigt, Erfolg mit einem übersetzten `toast.success`.

### Absende-Buttons bleiben aktiv

Der Absende-Button wird nie deaktiviert, weil das Formular unvollständig ist: kein `isDisabled`, kein `disabled` und kein `aria-disabled`, solange Werte fehlen oder ungültig sind. Ein gedimmter Button sagt nicht, was falsch ist, und GOV.UK, NN/g und Adrian Roselli raten davon ab. Ein Druck darauf trotz Fehlern ist ein gewöhnlicher Absendeversuch: `submitForm` zeigt jeden Fehler und setzt den Fokus auf das erste ungültige Feld. Nur `isPending` deaktiviert den Button, solange die Anfrage läuft.

Der shadcn-`Button` setzt `preventFocusOnPress` bei einem Button mit `type="submit"`, sodass der Fokus beim Drücken mit Maus oder Finger im gerade bearbeiteten Feld bleibt. Sonst würde der Fehler, der beim Verlassen dieses Felds erscheint, den Button verschieben, bevor das Drücken endet, und das Drücken würde nichts absenden.

### Serverfehler an einem Feld

Wenn der Server ein einzelnes Feld zurückweist, gehört der Fehler unter dieses Feld statt in einen Toast. Die Formulare für Registrierung, Passwort zurücksetzen und das Passwort in den Einstellungen tun das für ein Passwort, das in einem bekannten Datenleck vorkommt, und zwar im `onError` der Mutation in `onSubmit`. Aus `sign-up-form.tsx`:

```tsx
onError: (error) => {
  if (error.message === AUTH_ERRORS.PASSWORD_COMPROMISED) {
    showFieldError(formApi, { controlId: "sign-up-password", field: "password", message: error.message })
    return
  }
  toast.error(errorMessage(error))
},
```

- `showFieldError` aus `src/integrations/tanstack-form/form.submit.ts` speichert den Nachrichtenschlüssel als Absendefehler des Felds, markiert das Feld als verlassen, damit `isFieldInvalid` den Fehler anzeigt, und setzt den Fokus auf das Steuerelement.
- Der Schlüssel wird wie jede andere Validierungsmeldung nachgeschlagen und braucht daher einen Eintrag im Validierungs-Namespace des Felds, hier `auth.validations.passwordCompromised`.
- Der Fehler verschwindet bei der nächsten Änderung dieses Felds, und jeder andere Serverfehler bleibt ein Toast.

Das kleinste vollständige Beispiel ist `src/presentation/components/custom/newsletter-form.tsx`; die [Formular-Anleitung](/docs/guides/forms-and-validation) führt Schritt für Schritt durch den Bau eines Formulars.

## Tabellen

Jede Tabelle ist das `DataGrid` aus `src/presentation/components/custom/data-grid.tsx`, direkt auf der Seite verwendet:

```tsx
<DataGrid
  columns={columns}
  empty={t("empty")}
  id={ORDER_GRID_ID}
  label={t("title")}
  query={(request) => getOrdersPageQuery(orderZodSchemas.getOrders.parse(request))}
  search={t("filters.search")}
  selectable
/>
```

Seine Props sind die gesamte Schnittstelle:

| Prop          | Enthält                                                                                            |
| ------------- | -------------------------------------------------------------------------------------------------- |
| `columns`     | Den Spaltensatz aus dem Hook in `<entity>-columns.tsx`                                             |
| `id`          | Den Schlüssel des Layouts, das der Browser speichert, und den Anfang des CSV-Dateinamens           |
| `label`       | Den zugänglichen Namen der Tabelle                                                                 |
| `data`        | Zeilen, die bereits im Speicher sind, für ein Raster, das auf dem Client arbeitet                  |
| `query`       | Die Anfrage des Rasters zu Query-Optionen, für ein Raster, das auf dem Server arbeitet             |
| `search`      | Die Beschriftung des Suchfelds; ohne sie gibt es keine Suche                                       |
| `empty`       | Was das Raster sagt, bevor es irgendeine Zeile gibt                                                |
| `selectable`  | Zeilenauswahl mit der Auswahlleiste                                                                |
| `bulkActions` | Weitere Schaltflächen für die ausgewählten Zeilen                                                  |
| `rowActions`  | Die Komponente, die jede Zeile mit ihrem ⋯-Menü (`RowMenu`) abschließt                             |
| `onReorder`   | Griffe, die eine Zeile an eine neue Stelle ziehen oder sie mit den Pfeiltasten dorthin verschieben |

Die Suche, die Filter nach Spaltentyp, die Sortierung, Sichtbarkeit, Anheften, Reihenfolge und Breiten der Spalten, die Dichte, die Seitengröße, das gespeicherte Layout, die Auswahl, der CSV-Export, das Skeleton und die Leerzustände liegen alle darin ([Datenraster](/docs/ui/data-grid)). Schreibe keine eigene Tabellen-, Kopfzeilen-, Zeilen-, Werkzeugleisten- oder Paginierungskomponente pro Seite.

### Spalten

Ein Spaltensatz ist ein Hook in `custom/<area>/<entity>-columns.tsx`, gebaut mit `createColumnHelper<DataGridFeatures, Row>()`, wobei der Zeilentyp aus dem Modul-Interface stammt (`Order["listRow"]`). Er liest seine Übersetzungen und die Daten, die seine Filter anbieten, und gibt die Spalten memoisiert zurück:

```tsx
export const useOrderColumns = (): DataGridColumn<OrderRow>[] => {
  const t = useTranslations()

  const { countries, discounts, products } = useSuspenseQuery(orderFiltersQuery).data

  return useMemo(() => columnHelper.columns([...]), [countries, discountLabel, discounts, products, t])
}
```

- `header` ist die übersetzte Beschriftung als String; das Raster braucht sie als Text für seine Menüs, Chips, Ansagen und die CSV.
- `meta.filter` deklariert die Filterart und bei einer Auswahl ihre Optionen; `meta.hidden` und `meta.pinned` legen das Standardlayout fest; `meta.export` schreibt den CSV-Text.
- Jede Zelle ist eine kleine Komponente in derselben Datei, die ihre eigenen Übersetzungen liest (`StatusCell`, `CountryCell`) und bei Aktionen ihre eigenen Mutationen.
- Anfangsbreiten liegen in einer Konstante in `src/data` (`ORDER_COLUMN_SIZES`), die sowohl die Spalten als auch das Skeleton der Route lesen.
