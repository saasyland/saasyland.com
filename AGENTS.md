# AGENTS.md

SaaSy Land is the source of the saasyland.com website, customer workspace and admin console: one TanStack Start (React 19) application running as a Cloudflare Worker with D1 through Drizzle, KV and R2, Better Auth, Polar, Resend, use-intl and Fumadocs. Bun is the package manager and script runner; Vite+ (`vp`) runs the dev server, builds, Vitest, oxlint and oxfmt from `vite.config.ts`.

The coding standard is the Conventions section of the docs, [`content/docs/conventions/`](content/docs/conventions/index.en-US.mdx), published at <https://saasyland.com/docs/conventions>. Read the page for the kind of code you are about to write before you write it. This file is the summary.

## Commands

```sh
bun install --frozen-lockfile
bun run dev
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
bun scripts/enqueue-pr.ts <number>
bun run check:features
```

Run tests with `bun run test`, never `bun test`. `bun run db:reset:test` recreates and seeds the local test database that the browser suite uses. Other worktrees run browser suites on this machine too, so run yours on a free port from 3020 to 3029, the range the test build trusts: `lsof -nP -iTCP:3027 -sTCP:LISTEN` prints nothing for a free port, then `PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr`. Never stop or reuse a server you did not start; the run stops before the first test when the server on its port belongs to another worktree. Format and lint only the files you changed with `bunx vp fmt <files>` and `bunx vp lint --fix <files>`; never run `bun run check:fix` or `vp check --fix` over the repository. The formatter keeps `package.json` scripts sorted by name, and `vp check` fails when one is out of order.

## Definition of done

`bun run check`, `bun run test:coverage` and `bun run build:test`, in that order, exit 0 on the branch you are about to push, then so do the browser specs your change touches (`bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium`, with `PLAYWRIGHT_BASE_URL` on a free port of 3020 to 3029), and the pull request carries its changelog entry (rule 10). CI runs the full browser suite on the pull request and again in the merge queue, and the pull request is done only when it is green there and `bun scripts/enqueue-pr.ts <number>` has put it in the queue; never merge by hand. `bun run test:e2e:pr` runs the full suite locally. A documentation-only change may skip the browser specs, not the build. Nothing else counts as done, including a summary that says it is.

## Where code goes

- `src/modules/<table>/`: one folder per database table, and only for real tables: `<table>.schema.ts`, `.constants.ts` (with the `<MODULE>_EMAIL_PURPOSE` of the emails its use cases send), `.zod.ts`, `.types.ts` (one interface named after the module), `use-cases/<verb>-<noun>.ts` (a server function plus its query or mutation options). Tables end their columns with `...timestamps()` from `src/integrations/drizzle-orm/drizzle.columns.ts`, except the short-lived `rate_limit` counters and the insert-only `revoked_license_order`. Copy `src/modules/course`. `src/modules/_core/` is not a module: it holds only the foundation that schemas, Zod schemas and use cases are built from (error codes, HTTP and environment constants, the locale, time zone, country and currency catalogues with the store currency, shared Zod fields and localized text, the pagination, ordering, search and time-range inputs); constants that nothing is built from go to `src/data/`, generic helpers to `src/lib/`, and `src/__test__/module-tables.test.ts` fails a `_core` file that `content/docs/architecture/core` does not describe.
- `src/routes/`: route files that compose pages, with `NAMESPACE` or `NAMESPACES`, one `Promise.all` loader and a skeleton `pendingComponent`, which the layout skeletons also read from the route tree. Copy `src/routes/admin.courses.index.tsx`.
- `src/presentation/components/custom/`: a file per component, named after it, in flat folders, one per part of the site; it may also export the companions that only make sense beside it (a compound part, a page's skeletons, a field family). Components read their own translations and data; controls are shadcn primitives or React Aria components, not hand-written elements; corners take `rounded-lg` for surfaces, `rounded-md` for controls, `rounded-sm` for elements inside them and `rounded-full` for circles and pills, never another radius.
- `src/integrations/<vendor>/`: vendor configuration and the lists the vendor runs: the permission statements in `APP_STATEMENTS` (`better-auth/auth.access.ts`), the Better Auth plugins in `plugins` (`better-auth/auth.server.ts`), the code each Polar webhook event reaches in `POLAR_EVENT_HANDLERS` (`polar/polar.webhooks.ts`) and a vendor's Vite plugins in `<vendor>.vite.ts`. `src/lib/`: utilities and server functions that own no table, and the live site checks in `LIVE_SITE_CHECKS` (`src/lib/deployment.ts`). `src/routes.ts`: every path, `REQUEST_RENDERED_ROUTES` and `isRequestRenderedRoute`, and no import, because every runtime reads it (the browser, the Worker on each cold start, Bun, Playwright, `vite.config.ts` and the Remotion project); every file reads it as `import * as ROUTES from "~/src/routes"`. `src/data/navigation.ts`: the seven menus as literal lists in the order they are shown, each entry with its `to`, the full message key of its `label` and, in the console and the workspace, its icon; it imports only `lucide-react`, `~/src/routes` and `~/src/data/navigation.constants`, because the Remotion project reads the admin menu with only Remotion's own packages installed, and `src/__test__/source-layout.test.ts` fails when either file imports more. A list lives once, in the file that renders or runs it, and an optional feature joins it as one element that names its own identifier, such as its path, as the admin console's and the workspace's lists do in their components (`DASHBOARD_STATS`, `DASHBOARD_PANELS`, `COMMAND_SEARCHES`, `USER_TABS`, `USER_PROFILE_SECTIONS`, `ACCOUNT_DELETION_NOTICES`); a single contribution is referenced directly, as `__root.tsx` renders `<AffiliateReferral />`, the workspace's sidebar renders `CourseProgressBadge`, `translations-provider.tsx` lists `useSessionTimeZone` in `TIME_ZONE_HOOKS` and each layout names every namespace it loads in `NAMESPACES`. Course access is `COURSE_ACCESS_GRANTS` in `src/modules/lesson/lesson.access.ts`, beside `hasLessonAccess`, with the licence's grant written inline. There is no `src/areas`, and `src/__test__/source-layout.test.ts` fails when it comes back. `src/data/`: constants and literal lists several files share, with no function, schema or Zod import, which `src/__test__/source-layout.test.ts` checks; a search schema that several routes read goes to the module's `.zod.ts`. The Worker runs `REQUEST_HANDLERS` and `DOCUMENT_REWRITES` in `src/server.ts`, the build `VITE_PLUGINS` in `vite.config.ts`, which imports only by relative path, and a feature's deploy checks are `<name>:verify:<environment>` scripts in `package.json`; the admin console and the customer workspace belong to the auth feature. No application file lists every feature, and there is no `*.entries.ts` barrel, in the application or in its tests: a test list imports each element from the file that declares it, as `FLOWS` in `scripts/check-flows.ts` does. Leaving a feature out is the job of `scripts/features.ts`, which names each optional feature's files, the paths it owns in `src/routes.ts` and the permission statements it owns in `APP_STATEMENTS`, and of `bun run check:features`, which deletes them in each scenario, prunes every reference to them with one rule, and formats, type-checks and checks the translations of the site that is left; it fails on a reference the rule cannot prune, and the fix is to put the code where this section says, never to teach the pruner an exception.
- `messages/<locale>/<namespace>.json`, `content/docs/**/<page>.<locale>.mdx` and `content/changelog/<number>.<locale>.mdx`: every string, every docs page and every changelog entry in every locale; a feature labels its menu entries in its own `navigation.<feature>.json`, which each entry names by the message's full key, and its dashboard statistics in `dashboard.<feature>.json`; Polish copy follows the [Polish style guide](content/docs/conventions/polish-style.en-US.mdx) and takes every term from its glossary in `src/data/polish-glossary.ts`.

## Rules without exceptions

1. No comments anywhere: code, tests, scripts, configuration, CSS. Only generated files (`src/routeTree.gen.ts`, `src/types/worker-configuration.d.ts`) are exempt.
2. No `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, `as` casts or `any` to get past a rule. Fix the cause.
3. No multi-line ternaries; conditional classes use `cn("base", { "classes": condition })` from `~/src/lib/cn`.
4. No `?? undefined`; validate with Zod instead. Outside tests and `src/platform/testing`, `null` is written only where an API defines it: in a comparison with a value that can be `null`, and in a React DOM ref (`useRef<HTMLElement>(null)`).
5. Statuses, kinds, tiers, roles, environment names, HTTP statuses and other domain values are named constants (`COURSE_STATUS.DRAFT`, `ENVIRONMENT.PRODUCTION`, `HTTP_STATUS.NOT_FOUND`), never repeated string literals, in tests, e2e data and the seed too; schema tests are the one place a stored value is written out. Lengths are named constants in the module's `.constants.ts` as well.
6. Server functions validate their input with the module's Zod schema, type it as `Module["operation"]` and run the middleware of `auth.middleware.ts` that fits: `authorized(...)` for a signed-in user or a permission, `withRequest` for a public read, `withRateLimit(...)` for an operation that sends email, changes credentials or redeems a token. Route guards are not authorization.
7. Forms follow the shadcn TanStack Form pattern; tables use the one `DataGrid` with an `<entity>-columns.tsx` file.
8. Every user-facing string in every locale; numbers shown on the site are measured (`REPOSITORY_FACTS` in `src/lib/repository-facts.ts`) or declared once in `src/data` (`TIER_PRICES`), and the docs print values the code defines with `<RepositoryFact>` and `<RepositoryTable>`; nothing is typed.
9. Coverage stays at 100% for lines, statements, functions and branches; delete unreachable branches instead of stubbing them. Every user and admin flow is listed in `e2e/data/<feature>.flows.ts` with the Playwright test that performs it end to end and asserts its outcome, or the reason no test does yet; `bun run check:flows` fails when a flow names a test that is gone.
10. A change updates the README, the docs in every locale and the site copy it affects, and its pull request adds its changelog entry: once the pull request has its number, write `content/changelog/<number>.<locale>.mdx` in every locale, a bulleted list without a date. The changelog dates each entry by the squash commit that brings it to `main`, and `bun run check` fails a pull request's CI run while its entry is missing.
11. Commits are conventional (`fix(auth): keep the locale in verification links`), never `--no-verify` or `-c core.hooksPath`, and carry no `Co-Authored-By` trailer or any other AI attribution; the same goes for pull request descriptions. Do not type the emoji: the hook adds it from the type, and `scripts/enqueue-pr.ts` adds it to the pull request title, which becomes the squash commit (`feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎, `revert` 🗑️). History is linear: never create a merge commit, bring a branch up to date by rebasing it onto `main` (`gh pr update-branch --rebase`), and push a rewritten branch of your own with `git push --force-with-lease`, never `--force`.
12. Stay on the latest dependency versions: update with `bun run deps:update`, which moves the dependencies, the agent skills and the GitHub Actions, pinned to release commits, together, then adapt the code, or carry an upstream bug as a `bun patch` and report it upstream. Never pin back. `bun run check` fails when a package that a skill documents (`SKILL_SOURCES` in `src/data/skills.ts`) moved without `bun run skills:update`, or when the installed skills differ from `skills-lock.json`.

## Human review required

Do not change these without a person's explicit go-ahead in the task:

- `src/integrations/drizzle-orm/migrations/`: applied to production databases and irreversible.
- `src/modules/license/license.webhooks.ts`, `src/modules/license/use-cases/`, `src/integrations/polar/` and `src/integrations/affonso/`: payments, licences and affiliate referrals, and `polar.webhooks.ts`, which code each Polar webhook event reaches.
- `src/integrations/better-auth/`: sessions, tokens, permissions (`auth.access.ts`) and plugins (`auth.server.ts`).
- `src/modules/lesson/lesson.access.ts`: who may open paid lessons.
- `src/modules/license/license.api.ts` and `src/routes/api/cli.v1.*`: the CLI licence API, which activates, checks and releases licence keys.
- `wrangler.jsonc`, `.env*`, `.github/workflows/` and anything that reads a secret.

Never deploy, apply remote migrations or change secrets (`wrangler deploy`, `--remote`, `wrangler secret`); those are human steps.

## Current library documentation

The framework versions here are newer than most training data. Read the installed documentation before using an API:

- Vite+: `node_modules/vite-plus/docs`.
- TanStack Start, Router and Table ship agent skills inside their packages: `node_modules/@tanstack/react-start/skills`, `node_modules/@tanstack/react-router/skills`, `node_modules/@tanstack/react-table/skills`.
- Vendor skills for Better Auth, Cloudflare, Polar, Resend, TanStack and others are pinned in `skills-lock.json`; `bun run skills:sync` installs them into `.agents/skills` and links them into `.claude/skills`, and `bun run skills:update` moves every pin to the latest commit of its source and records the versions of the packages each source documents in `skills-packages.json`.
