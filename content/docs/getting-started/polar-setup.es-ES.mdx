Polar vende los tres niveles, emite sus claves de licencia y aplica los descuentos regionales. El código espera una configuración precisa en Polar, y Polar no avisa cuando ambos dejan de coincidir: un producto sin un beneficio de clave de licencia sigue aceptando el pago, pero no emite ninguna clave. `bun run polar:verify:<environment>` compara Polar con el código, y los scripts de despliegue lo ejecutan antes de cada despliegue manual.

## Producción y sandbox

Polar mantiene dos servicios independientes. Producción (`polar.sh`, API `api.polar.sh`) hace cargos en tarjetas reales; el sandbox (`sandbox.polar.sh`, API `sandbox-api.polar.sh`) solo acepta tarjetas de prueba. No comparten nada: una cuenta, una organización, un token, un producto, un descuento o un webhook existe en un solo servicio, así que regístrate por separado en `sandbox.polar.sh` y configura cada servicio por su cuenta.

| Archivo de entorno | `POLAR_SERVER` | Organización de Polar |
| ------------------ | -------------- | --------------------- |
| `.env.development` | `sandbox`      | Sandbox               |
| `.env.preview`     | `sandbox`      | Sandbox               |
| `.env.production`  | `production`   | Producción            |

Desarrollo y preview pueden compartir una organización del sandbox, ya que comparten una base de datos D1: su webhook envía los eventos al host de preview, y una compra de prueba hecha en desarrollo llega a través de él a la base de datos compartida.

No pongas nunca un token, un ID de organización o un ID de producto de producción en `.env.development` ni en `.env.preview`. La API del sandbox rechaza un token de producción, y con `POLAR_SERVER=production` un pago de prueba haría un cargo en una tarjeta real y concedería la licencia en la base de datos local o de preview. `polar:verify` rechaza `POLAR_SERVER=production` para desarrollo y preview, y `POLAR_SERVER=sandbox` para producción.

## Organización y token

En el sandbox y, después, en producción:

1. Crea una organización y copia su ID, que figura en los ajustes de la organización, en `POLAR_ORGANIZATION_ID`. Da a las dos organizaciones el slug de `POLAR_ORGANIZATION_SLUG` (`src/data/polar.ts`), o cambia la constante por su slug: el [aviso y la lista de administración de los pedidos que no corresponden a ninguna cuenta](/docs/features/licences#orders-that-match-no-account) enlazan cada pedido al panel de Polar con ese slug.
2. En los ajustes de la organización, crea un token de acceso de organización con estos ámbitos, y ningún otro, y cópialo en `POLAR_ACCESS_TOKEN`.

| Ámbito                    | Lo necesita                                                                                                                                                                 |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkouts:write`         | `startCheckout`, que crea el pago mediante el plugin de Polar para Better Auth                                                                                              |
| `customer_sessions:write` | El enlace al portal de cliente, `/api/auth/customer/portal`                                                                                                                 |
| `discounts:read`          | La búsqueda del descuento regional en el pago (`pppDiscountId`) y `polar:verify`                                                                                            |
| `license_keys:write`      | Leer una clave y sus activaciones, activar un dispositivo y eliminar una activación (`deactivateLicense` y la [API de licencias de la CLI](/docs/features/cli-licence-api)) |
| `orders:read`             | Los handlers de los webhooks, que leen el pedido que hay detrás de una licencia y el cliente actual de un pedido cuyo evento no corresponde a ninguna cuenta                |
| `products:read`           | `polar:verify`                                                                                                                                                              |
| `webhooks:read`           | `polar:verify`                                                                                                                                                              |

Un ámbito de escritura incluye la lectura, así que `license_keys:write` también cubre la lectura de claves. Un token de organización ya actúa en nombre de su propia organización. Aun así, `polar:verify` envía `POLAR_ORGANIZATION_ID` como parámetro de consulta `organization_id`, igual que la búsqueda de descuentos en el pago, así que un ID de otra organización se manifiesta como productos que faltan.

## Productos

Crea un producto por nivel: una compra única, no una suscripción, con un precio fijo en `DEFAULT_CURRENCY_CODE` (dólares estadounidenses) igual a `TIER_PRICES` de `src/data/marketing.ts`. Copia el ID de cada producto en su clave.

| Nivel    | Clave                       | Precio                        | Activaciones por clave              |
| -------- | --------------------------- | ----------------------------- | ----------------------------------- |
| Core     | `POLAR_PRODUCT_ID_CORE`     | <TierPrice tier="core" />     | <ActivationLimit tier="core" />     |
| Complete | `POLAR_PRODUCT_ID_COMPLETE` | <TierPrice tier="complete" /> | <ActivationLimit tier="complete" /> |
| Agency   | `POLAR_PRODUCT_ID_AGENCY`   | <TierPrice tier="agency" />   | <ActivationLimit tier="agency" />   |

Polar guarda los precios en la unidad menor de la moneda, centavos en el caso del dólar estadounidense, y `polar:verify` convierte `TIER_PRICES` de la misma forma antes de compararlos. Ignora los precios archivados.

## Claves de licencia

Crea un beneficio de tipo **License Keys** (claves de licencia) por nivel y vincúlalo solo al producto de ese nivel:

- **Activaciones**: limitadas al número de la tabla anterior, `LICENSE_ACTIVATION_LIMITS` en `src/modules/license/license.constants.ts`. Permitir que los clientes gestionen sus activaciones en Polar es opcional, porque `/app/license` ya las enumera y las elimina por su cuenta.
- **Caducidad**: ninguna. Las claves no caducan nunca, ya que la compra es un pago único.
- **Límite de uso**: ninguno.
- **Prefijo**: el que prefieras; `polar:verify` no lo comprueba.

Cada producto necesita exactamente un beneficio de clave de licencia; puede tener otros beneficios además de ese. Cuando Polar concede el beneficio, el webhook `benefit_grant.created` guarda la clave en la licencia del comprador.

## Casilla de consentimiento [#consent-checkbox]

El diálogo de pago del sitio pide al comprador el consentimiento al suministro inmediato (consulta [Licencias](/docs/features/licences#consent-to-immediate-supply)), y el pago de Polar lo registra en el pedido. Crea un campo personalizado en la organización y vincúlalo a los tres productos:

- **Tipo**: casilla de verificación.
- **Identificador (slug)**: <RepositoryFact name="licenseWithdrawalConsentField" />, `LICENSE_CHECKOUT_FIELD.WITHDRAWAL_CONSENT` en `src/modules/license/license.constants.ts`. El pedido guarda la casilla marcada con esta clave en `custom_field_data`.
- **Etiqueta**: exactamente `WITHDRAWAL_CONSENT_FIELD.label` de `src/lib/polar.ts`, la frase en inglés construida a partir de `REFUND_TERMS.WITHDRAWAL_DAYS` que termina con un enlace en Markdown a la Política de Reembolsos de producción.
- **Nombre**: el que prefieras; `WITHDRAWAL_CONSENT_FIELD.name` es el que sugiere el código, y `polar:verify` no lo comprueba.
- **Obligatorio** en cada uno de los tres productos. Los demás campos que pidan los productos pueden quedarse.

`startCheckout` envía como valor del campo el consentimiento que el comprador acaba de dar, así que Polar muestra la casilla ya marcada. Polar solo conserva los valores de los campos que pide el producto: antes de vincular el campo, el pago sigue funcionando, pero el pedido no registra ningún consentimiento, y la [confirmación de compra](/docs/features/licences#purchase-confirmation) indica en su lugar el derecho de desistimiento legal.

Crear el campo y vincularlo a un producto requiere los ámbitos `custom_fields:write` y `products:write`, que el token anterior no tiene. Créalo y vincúlalo en el panel de Polar, o mediante la API con otro token que sí los tenga. `polar:verify` lee los campos vinculados en el listado de productos, así que no necesita ningún otro ámbito.

## Descuentos regionales

El proceso de pago aplica un precio regional mediante un descuento automático de Polar (consulta [Licencias](/docs/features/licences)). Crea un descuento porcentual para cada tramo de `PPP_TIERS` (`src/modules/license/license.pricing.ts`): <RegionalDiscounts />. Cada descuento debe:

- descontar un porcentaje; Polar lo guarda en puntos básicos, es decir, en centésimas de punto porcentual;
- no tener código, para que el pago pueda aplicarlo sin que el comprador escriba ninguno;
- aplicarse a los tres productos o a ningún producto en concreto;
- poder canjearse ahora: sin fecha de inicio en el futuro, sin fecha de fin en el pasado y, si tiene un límite de canjes, con canjes disponibles.

`findRegionalDiscount`, en `src/integrations/polar/polar.discounts.ts`, decide qué descuento aplica el pago, y `polar:verify` consulta esa misma función.

## Webhook

Crea un endpoint de webhook para cada entorno desplegado, en la organización que usa ese entorno.

| Entorno      | Organización | URL                                                     |
| ------------ | ------------ | ------------------------------------------------------- |
| `preview`    | Sandbox      | `https://preview.saasyland.com/api/auth/polar/webhooks` |
| `production` | Producción   | `https://saasyland.com/api/auth/polar/webhooks`         |

El host sale de `DEPLOYED_HOSTS` y la ruta, de `ROUTES`. Elige el formato raw, mantén el endpoint activado y suscríbelo exactamente a los eventos de `POLAR_EVENTS` (`src/data/polar-events.ts`), que reúne los eventos que gestiona cada área (consulta [Pagos](/docs/features/payments#webhooks)). Hoy el área de licencias gestiona los eventos de `LICENSE_WEBHOOK_EVENTS` (`src/modules/license/license.constants.ts`), y el área de facturación, los de `src/data/billing.polar-events.ts`:

| Evento                  | Área de licencias                                                                  | Área de facturación                  |
| ----------------------- | ---------------------------------------------------------------------------------- | ------------------------------------ |
| `benefit_grant.created` | Guarda la clave de licencia                                                        |                                      |
| `benefit_grant.revoked` | Revoca la licencia                                                                 |                                      |
| `order.created`         |                                                                                    | Copia el pedido en D1                |
| `order.paid`            | Concede la licencia                                                                | Actualiza la copia del pedido        |
| `order.refunded`        | Marca la licencia como reembolsada cuando el pedido se ha reembolsado por completo | Actualiza la copia del pedido        |
| `order.updated`         |                                                                                    | Actualiza la copia del pedido        |
| `subscription.created`  |                                                                                    | Copia la suscripción en D1           |
| `subscription.updated`  |                                                                                    | Actualiza la copia de la suscripción |

Cuando un área empiece a gestionar un evento, añade el evento a cada endpoint antes de desplegar ese código. El código desplegado hasta entonces responde 200 a un evento que ninguna área gestiona y no hace nada con él, así que añadir el evento primero no causa ningún daño, y `polar:verify` hace fallar el despliegue mientras un endpoint no envíe todos los eventos de `POLAR_EVENTS`.

Copia el secreto de firma del endpoint en `POLAR_WEBHOOK_SECRET`, en el mismo archivo de entorno. Desarrollo no necesita ningún endpoint, porque Polar no puede acceder a `localhost`.

No añadas nunca un endpoint de preview a la organización de producción ni un endpoint de producción al sandbox: los pagos reales llegarían a preview, o las compras de prueba concederían licencias en producción.

## Comprobar la configuración

```sh
bun run polar:verify:development
bun run polar:verify:preview
bun run polar:verify:production
```

Cada script lee las claves de Polar de `.env.<environment>` y solo envía peticiones GET a la API que indica `POLAR_SERVER`: enumera los productos, los descuentos y los endpoints de webhook de la organización, y no modifica nada. Comprueba que:

- el archivo de entorno define todas las claves de Polar, con `POLAR_SERVER=sandbox` para desarrollo y preview y `POLAR_SERVER=production` para producción;
- cada `POLAR_PRODUCT_ID_*` corresponde a un producto de la organización que no está archivado ni es una suscripción, y cuyos precios son fijos, están en `DEFAULT_CURRENCY_CODE` y son iguales a `TIER_PRICES`;
- cada producto tiene exactamente un beneficio de clave de licencia con el límite del nivel según `LICENSE_ACTIVATION_LIMITS`, sin caducidad y sin límite de uso;
- cada producto exige el campo de casilla <RepositoryFact name="licenseWithdrawalConsentField" /> con la etiqueta de `WITHDRAWAL_CONSENT_FIELD`;
- para cada tramo de `PPP_TIERS`, hay un descuento porcentual automático que puede canjearse en el producto de cada nivel, según la regla que usa el pago;
- preview y producción tienen un endpoint raw activado en su URL de webhook, firmado con `POLAR_WEBHOOK_SECRET` y suscrito exactamente a `POLAR_EVENTS`;
- ningún endpoint envía eventos al host de un entorno que usa el otro servicio de Polar.

`polar:verify` es la comprobación de despliegue del área de Polar (`POLAR_DEPLOY_CHECKS` en `src/data/polar.deploy.ts`), así que `deploy:preview` y `deploy:production` lo ejecutan a través de `scripts/run-deploy-checks.ts`, después de `scripts/verify-bindings.ts` y `scripts/prepare-deploy-secrets.ts` y antes de la compilación. Los despliegues de la CI no ejecutan ninguna comprobación de despliegue, tampoco `polar:verify`: `deploy-reusable.yml` no tiene ningún paso para `scripts/run-deploy-checks.ts`, los entornos de GitHub no guardan ningún token de Polar, y el Worker conserva los secretos de Polar ya configurados en Cloudflare. Ejecuta tú mismo `polar:verify` después de cada cambio en Polar.

## Cuando falla

El script termina con un error que enumera todos los problemas que ha encontrado, uno por línea:

```text
Polar production does not match the code for production:
The core product (POLAR_PRODUCT_ID_CORE) has 0 licence-key benefits; it needs exactly one.
A webhook endpoint posts to https://preview.saasyland.com/api/auth/polar/webhooks, the preview host, from this Polar production organisation; remove it.
```

Un fallo detiene el despliegue antes de que se compile, se migre o se suba nada. El script nunca modifica Polar: corrige Polar y vuelve a ejecutarlo. Cada mensaje indica la clave, la constante o el ajuste que hay que corregir:

- **`Set … in .env.<environment>`**: falta una clave de Polar o está vacía, o `POLAR_SERVER` indica el servicio equivocado.
- **`rejects POLAR_ACCESS_TOKEN`**: el token no es válido, se ha revocado o es del otro servicio, como un token de producción en `.env.preview`.
- **`lacks the … scope`**: crea un token con los ámbitos indicados más arriba.
- **`names no product of the organisation`**: el ID de producto o `POLAR_ORGANIZATION_ID` es incorrecto, o pertenece al otro servicio.
- **Un precio, una clave de licencia o un descuento**: cámbialo en Polar para que coincida con el código. Cuando un valor de negocio cambie a propósito, cambia primero `TIER_PRICES`, `LICENSE_ACTIVATION_LIMITS` o `PPP_TIERS` y después Polar.
- **`does not ask for the … checkout field`, `without requiring it`, `instead of a checkbox` o `label differs`**: crea, vincula o corrige la [casilla de consentimiento](#consent-checkbox). Cuando la redacción cambie a propósito, cambia primero `WITHDRAWAL_CONSENT_FIELD.label` y después la etiqueta en Polar.
- **Un endpoint de webhook**: corrige el endpoint que indica el mensaje o elimina un endpoint que envíe eventos al host de otro entorno.
