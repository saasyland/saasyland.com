## コードカバレッジ [#code-coverage]

`bun run test:coverage` は Vitest のプロジェクト <RepositoryFact name="vitestProjects" /> を実行し、<RepositoryFact name="coverageInclude" /> の行、ステートメント、関数、分岐のいずれかが <RepositoryFact name="coverageThreshold" unit="percent" /> を下回ると失敗します。<RepositoryFact name="coverageExclude" /> は対象外です。CI は、すべてのプルリクエストと `main` へのすべてのプッシュでこれを <RepositoryFact name="vitestShards" /> 個の並列シャードに分けて実行し、しきい値をチェックする前にカバレッジを統合します（[CI/CD](/docs/tooling/ci-cd#checks)）。

ブラウザーのスイートはこの数値に含まれません。Playwright はビルドしたテスト用 Worker を操作し、そこではカバレッジを収集しないためです。コードカバレッジが完全であるとは、計測対象のすべての行が、何かをアサートするテストの中で実行されたという意味です。各部分が Worker、D1、ブラウザー、プロバイダーを通じて連携して動くという意味ではありません。CLI ライセンス API のバンドルのスペックはデフォルトの回答しか送らないため、ハンドラーのすべての行がカバーされていても、別の回答を含むバンドルのリクエストは本番環境で失敗する可能性があります。この 2 つ目の問いを計測するのがフローカバレッジです。

## フローカバレッジ [#flow-coverage]

フロー一覧には、サイト、顧客ワークスペース、管理コンソールのすべてのフローが載っています。各機能は、ページやシードを宣言するのと同じように `e2e/data/<feature>.flows.ts` で自身のフローを宣言し、`scripts/check-flows.ts` の `FLOWS` がそれらをインポートします。型と定数は `e2e/data/flows.ts` にあります。フローは ID、機能、テストがアサートすべき結果、そして次の 3 つのステータスのいずれかを持ちます。

- **カバー済み**: Playwright のテストがフローをエンドツーエンドで実行し、その結果をアサートします。フローには、そうしたテストそれぞれのスペックと完全なタイトルを記載します。
- **未カバー**: 機能は存在しますが、それをエンドツーエンドで実行するブラウザーテストがありません。フローには不足しているものを記載し、その一部を実行するテストや、それを実行するジャーニーのステップがあれば、それも挙げます。
- **未実装**: 商品の作成や価格と割引の変更のように、機能がまだ存在せず、画面もありません。フローには、その代わりに何があるかを記載します。

`bun run check` は `bun run check:flows` を実行します。これは Chromium で `playwright test --list` を使ってブラウザーのスイートを一覧にし、次の場合に失敗します。

- フローが、スイートにないスペックまたはテストのタイトルを挙げている場合。テストの名前を変えたり削除したりすると、こうなります。
- フローが、スキップされるテストを挙げている場合。
- 2 つのフローが同じ ID を持つ場合。
- 未カバーのフローまたは未実装のフローが、その理由を記載していない場合。
- フローが、ジャーニースイートにないステップを挙げている場合。

そのため、カバー済みのフローがテストを失うのは、同じプルリクエストでそのステータスを変更し、理由を書き残した場合だけです。

現在、<RepositoryFact name="flows" /> 件のフローのうち、<RepositoryFact name="flowsCovered" /> 件がカバー済み、<RepositoryFact name="flowsMissing" /> 件が未カバー、<RepositoryFact name="flowsToBuild" /> 件が未実装です。ブラウザーのスイートには、<RepositoryFact name="e2eSpecs" /> 個のスペックファイルに <RepositoryFact name="e2eTests" /> 件のテストがあります。

## ジャーニースイート [#journey-suite]

[ジャーニースイート](/docs/tooling/playwright#journey-suite)は、プレビュー上の Polar のサンドボックスで、Stripe のテストカードを使って各プランを購入し、Webhook がキーを発行するのを待ち、プランが許す台数の端末で公開済みの CLI を使い、注文を返金します。さらに Core を差額で Complete にアップグレードし、そのアップグレードを返金して Core に戻します。未カバーのフローのうち <RepositoryFact name="flowsInJourney" /> 件を実行し、未カバーの表の最後の列にそれが記載されています。`journey.yml` は毎晩これを実行するようスケジュールされており、手動でも起動できますが（[CI/CD](/docs/tooling/ci-cd#journey-suite)）、プルリクエストはその結果を待たないため、それらのフローは未カバーと数えられます。成功した実行はまだありません。このワークフローには、オーナーにしか用意できない次の 2 つが必要ですが、どちらもまだ整っていません。

1. **シークレット。** GitHub の環境 `Preview` には、スコープ `orders:read`、`refunds:write`、`benefits:read`、`license_keys:read` を持つサンドボックスのトークン `POLAR_ACCESS_TOKEN`、サンドボックスの商品 `POLAR_PRODUCT_ID_CORE`、`POLAR_PRODUCT_ID_COMPLETE`、`POLAR_PRODUCT_ID_AGENCY`、そしてプレビューが送信するメールを読み取れるフルアクセスのキー `RESEND_API_KEY` が必要です。`POLAR_SERVER` は `sandbox` で、シークレットは不要です。
2. **サンドボックス。** サンドボックスの組織はコードと一致している必要があり、`bun run polar:verify:preview` がそれを確認します。また、その Webhook はプレビューを指している必要があります。

## 予定 [#planned]

- **ミューテーションテスト。** ミューテーションツールは、テスト対象のコードを演算子や条件 1 つずつ変更し、どのテストにも気づかれなかった変更を数えます。これにより、テストが結果をアサートしているのか、行を実行しているだけなのかを計測します。まずはライセンス、決済、価格、コースへのアクセス、認証のコードから始める予定です。まだ何も設定されていません。
- **ブラウザーのコードカバレッジ。** ブラウザーのスイートがビルドしたアプリケーションを実行する間に V8 のカバレッジを収集すれば、どのブラウザーテストも到達しないコードがわかります。これは Vitest の数値に加算せず、その横に報告し、ゲートにはしません。まだ何も設定されていません。
