Der Rat, den alle zur Stack-Wahl für KI-Coding-Agenten geben, lautet: Beliebt ist besser, weil Modelle mehr davon gesehen haben. Das klingt offensichtlich richtig. Es war auch richtig. 2026 hat es sich teilweise ins Gegenteil verkehrt, und der Beweis ist eine Datei, die dieses Repository selbst erzeugt.

Führen Sie `next dev` unter Next.js 16 aus, und es schreibt ungefragt Folgendes in Ihre `AGENTS.md`:

```markdown
# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all
differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/`
before writing any code. Heed deprecation notices.
```

Das beliebteste React-Framework der Welt liefert Coding-Agenten inzwischen eine Warnung mit, dass das, woran sie sich erinnern, falsch ist. Das ist keine Kritik an Next.js. Es ist eine ehrliche Antwort auf ein echtes Problem und die klarste Aussage darüber, was die Wahl eines Stacks 2026 tatsächlich bedeutet.

## Was leistet ein Stack eigentlich für einen KI-Coding-Agenten?

Ein Stack macht einen Agenten nicht korrekt. Er verändert, **wie viele falsche Programme sich überhaupt ausdrücken lassen**. Jede Bibliothekswahl verkleinert oder vergrößert den Raum an Code, der kompiliert, aber falsch ist. Das ist der gesamte Mechanismus, und deshalb ist „agentenfreundlich“ eine Eigenschaft, die Sie testen können, und kein Bauchgefühl.

Betrachten Sie denselben Fehler in zwei Codebasen. Ein Agent liest eine Datenbankspalte als String, obwohl sie ein Zeitstempel ist.

In einem typisierten Query Builder lässt sich der Fehler nicht ausdrücken. Der Code kompiliert nicht, der Agent sieht den Fehler innerhalb seines eigenen Durchlaufs und korrigiert ihn. Kosten: etwa zwei Sekunden.

Bei einer rohen Abfrage, die `any` zurückgibt, kompiliert der Fehler, besteht das Review, weil er sich richtig liest, und erzeugt sechs Wochen später ein falsches Datum in einer Rechnungs-E-Mail. Kosten: ein Vorfall.

Dasselbe Modell. Derselbe Prompt. Derselbe Fehler. Der Stack hat entschieden, ob daraus ein Kompilierfehler oder ein Vorfall wurde.

## Die Aktualitätslücke, und warum Beliebtheit kein Indikator mehr ist

Das Argument, das alle vorbringen, lautet: Beliebte Bibliotheken kommen häufiger in Trainingsdaten vor, also schreiben Modelle sie genauer. Die erste Hälfte stimmt. Die zweite hängt inzwischen ganz von etwas ab, das das Argument ignoriert, nämlich **wie schnell sich die Bibliothek verändert**.

**Die Aktualitätslücke ist der Abstand zwischen der API, an die sich ein Modell erinnert, und der API, die Sie tatsächlich ausliefern.** Die Menge der Trainingsdaten sagt Ihnen, wie selbstsicher ein Modell eine Bibliothek schreibt. Die Aktualitätslücke sagt Ihnen, ob diese Selbstsicherheit berechtigt ist. Das sind unterschiedliche Größen, und bei schnelllebigen Frameworks zeigen sie inzwischen in entgegengesetzte Richtungen.

Die Forschung dazu ist eindeutig. Eine Studie zu acht weit verbreiteten Bibliotheken maß in modellgeneriertem Code **Nutzungsraten veralteter APIs von 25 % bis 38 %** und führte sie auf veraltetes parametrisches Wissen und das Fehlen jeder aktuellen Sicht auf die heutige API zurück ([APILOT, arXiv](https://arxiv.org/pdf/2409.16526)). Arbeiten zu sich weiterentwickelnden APIs beschreiben denselben Fehler als Wissenskonflikt: Das Modell rät nicht, es erinnert sich selbstsicher an eine Version, die es nicht mehr gibt ([When LLMs Lag Behind, arXiv](https://arxiv.org/html/2604.09515v1)).

Daraus ergibt sich eine kontraintuitive Rangfolge, sortiert danach, wie viel Ärger das Gedächtnis des Modells verursacht:

| Profil der Bibliothek                                                | Trainingsmenge | API-Änderungen | Nettowirkung auf die Agenten-Ergebnisse                      |
| -------------------------------------------------------------------- | -------------- | -------------- | ------------------------------------------------------------ |
| Beliebt und stabil (React, PostgreSQL, Tailwind)                     | Hoch           | Gering         | **Am besten.** Das Gedächtnis ist groß und noch korrekt      |
| Klein und stabil (Zod, die meisten fokussierten Utilities)           | Geringer       | Gering         | **Gut.** Weniger Gedächtnis, aber was da ist, stimmt         |
| Beliebt und schnelllebig (ein Framework mitten in der Major-Version) | Hoch           | Hoch           | **Am schlechtesten.** Selbstsicher, flüssig und falsch       |
| Klein und schnelllebig                                               | Gering         | Hoch           | Schlecht, aber der Agent sichert sich ab, statt zu behaupten |

Die Zelle unten rechts ist die interessante. Wenn ein Modell wenig über eine Bibliothek weiß, sichert es sich eher ab, sucht oder liest den Quellcode. Wenn es viel über die _vorherige Version_ einer Bibliothek weiß, behauptet es. **Die Selbstsicherheit richtet sich nach der Trainingsmenge, nicht nach der Korrektheit**, also ist der schlimmste Fall eine hohe Menge plus hohe Änderungsrate: ein Agent, der veralteten Code flüssig schreibt und nie Zweifel signalisiert.

Genau vor diesem Fall warnt Next.js im Block oben. Es ist das React-Framework mit den meisten Trainingsdaten überhaupt, und es hat so viel verändert, dass der Hersteller eine gedruckte Warnung an Agenten für nötig hielt.

### Was Sie dagegen tun können

Das Gedächtnis eines Modells können Sie nicht reparieren, aber Sie können seine Fehler billig machen:

- **Ziehen Sie Stabilität der Beliebtheit vor, wenn beide kollidieren.** Eine seit fünf Jahren stabile API, an die sich das Modell halb erinnert, schlägt eine umgeschriebene API, an die es sich vollständig falsch erinnert.
- **Lassen Sie den Compiler die Versionsabweichung abfangen.** Fehler durch veraltete APIs sind nur an untypisierten Grenzen teuer. Das ist das eigentliche Argument für durchgängige Typen, und es ist stärker als das übliche.
- **Pinnen Sie die Dokumentation, die der Agent liest, und legen Sie sie lokal ab.** Next.js rät selbst dazu, die Anleitung in `node_modules` zu lesen, nicht im Web. Lokale Dokumentation passt zu Ihrer installierten Version; ein Blogbeitrag von 2024 nicht.
- **Behandeln Sie neue Abhängigkeiten als nicht vertrauenswürdig.** Mehr dazu weiter unten, denn das ist ein Sicherheitsproblem und nicht nur eine Frage der Korrektheit.

## Der Agent Stack Test

Vier Fragen pro Abhängigkeit, jeweils mit 0, 1 oder 2 bewertet, für 8 Punkte. Er gilt auch für Bibliotheken, die es beim Schreiben dieses Artikels noch nicht gab, und genau darin liegt der Sinn eines Tests statt einer Liste.

### 1. Einschränkung: Kann falsche Verwendung schon beim Kompilieren scheitern?

- **0**: Die Bibliothek gibt `any` zurück, die Konfiguration basiert auf String-Schlüsseln, oder Fehler zeigen sich erst zur Laufzeit.
- **1**: Typen existieren, sind aber nur Empfehlungen; ein falscher Aufruf kompiliert mit einem Cast trotzdem.
- **2**: Falsche Verwendung ist ein Typfehler. Falsche Programme lassen sich nicht ausdrücken.

### 2. Konvergenz: Gibt es einen offensichtlichen Weg für die Aufgabe?

Agenten arbeiten durch Nachahmung, also gibt Ihnen eine Bibliothek mit sechs gleichwertigen APIs eine Chance von eins zu sechs auf diejenige, die Ihre Codebasis bereits verwendet.

- **0**: Viele gleichwertige Ansätze, alle in freier Wildbahn verbreitet und alle in den Trainingsdaten.
- **1**: Ein empfohlener Weg, dazu weit verbreitete Legacy-Alternativen.
- **2**: Ein Weg, und die Alternativen sind entfernt statt nur als veraltet markiert.

### 3. Überprüfbarkeit: Kann der Agent selbst beweisen, dass es funktioniert?

- **0**: Korrektheit ist nur sichtbar, wenn ein Mensch die laufende App ansieht.
- **1**: Testbar, aber die Einrichtung ist so manuell, dass der Agent sie nicht vornimmt.
- **2**: Ein Befehl, den der Agent ohnehin ausführt, deckt es ab.

### 4. Aktualität: Ist das Gedächtnis des Modells auf dem aktuellen Stand?

- **0**: Major-Versionswechsel innerhalb des letzten Jahres, mit umbenannten oder entfernten öffentlichen APIs.
- **1**: Kürzliche kleinere Änderungen, oder die Dokumentation, aus der das Modell gelernt hat, ist inzwischen stellenweise falsch.
- **2**: Die öffentliche API ist lange genug stabil, dass erinnerter Code noch läuft, oder die Bibliothek liefert maschinenlesbare Dokumentation zusammen mit der installierten Version aus.

**So lesen Sie die Punktzahl.** 7 bis 8 ist eine Abhängigkeit, der man einen Agenten unbeaufsichtigt anvertrauen kann. 4 bis 6 bedeutet, dass es mit einer Typgrenze oder einem Test drumherum funktioniert. 3 oder weniger bedeutet: Kapseln Sie sie hinter einer Schnittstelle, die Ihnen gehört, oder akzeptieren Sie, dass ein Mensch jede Aufrufstelle schreibt.

Der Test bewertet bewusst die _Form_ einer Abhängigkeit und nicht ihre Qualität. Hervorragende Bibliotheken schneiden hier schlecht ab (eine großartige Bibliothek mitten in einer Neuschreibung erhält bei der Aktualität 0), und unscheinbare schneiden gut ab. Gemessen wird die Eignung für Agenten, nicht der Wert.

## Den Test anwenden, Schicht für Schicht

Es folgt der Stack, den wir ausliefern, ehrlich bewertet, auch dort, wo er etwas kostet. Ihre Antworten können anders ausfallen; übertragbar ist die Begründung.

### Sprache: TypeScript, strikt, ohne Hintertüren

**Punktzahl: 8/8.** Von dieser Wahl hängt alles andere auf der Liste ab.

Der Strict Mode ist die Untergrenze, nicht das Ziel. Die Eigenschaften, die für Agenten zählen, sind genau die, die man üblicherweise abschaltet: kein implizites `any`, kein ungeprüfter Indexzugriff, keine Non-Null-Assertions. Jedes dieser Flags verwandelt eine Klasse selbstsicherer, aber falscher Agenten-Ergebnisse von einer Überraschung zur Laufzeit in eine rote Wellenlinie, die der Agent sieht, bevor er seinen Zug beendet.

Die Version ist weniger wichtig als die Einstellungen. Ein locker konfiguriertes aktuelles TypeScript ist für die Arbeit mit Agenten schlechter als ein strikt konfiguriertes älteres.

### Laufzeit und Framework: Cloudflare Workers, TanStack Start, React

**Punktzahl: 6/8.** Einschränkung 2, Konvergenz 1, Überprüfbarkeit 2, Aktualität 1.

Das ist die ehrliche Schwachstelle, und es ist dieselbe, vor der Next.js warnt. Der Kern von React ist lange genug stabil, dass das Gedächtnis der Modelle verlässlich ist. Die Framework-Schicht darum herum war es nicht, und das kostet den Punkt bei der Aktualität.

Die aktuelle öffentliche Anwendung nutzt React mit TanStack Start auf Cloudflare Workers. Bun und Vite+ stellen die lokale Toolchain bereit. Agenten sollten die Dokumentation der installierten Pakete und die gepinnten offiziellen Skills für TanStack Start und Cloudflare lesen, bevor sie Framework- oder Deployment-Code ändern.

Bei der Konvergenz geht ein Punkt verloren, weil Route Loader, Server Functions, Query-Caching und gewöhnliche HTTP-Endpunkte unterschiedliche Aufgaben haben. Dieses Repository zeigt, wohin was gehört: Routendateien koordinieren die Navigation, Feature-Use-Cases verantworten die Operationen, und Anbieter-Integrationen verantworten die Konfiguration der Dienste.

### API-Schicht: TanStack Start Server Functions, durchgängig typisiert

**Punktzahl: 7/8.**

Entscheidend ist nicht das Framework, sondern dass die Eingabe- und Ausgabetypen eines Handlers für den Aufrufer sichtbar sind. Wenn sich die Form einer Route ändert, kompiliert jede Aufrufstelle, die nun falsch ist, nicht mehr.

Die Ratschläge der Konkurrenz nennen hier meist konkrete RPC-Bibliotheken. Das ist eine Umsetzung der Eigenschaft, nicht die Eigenschaft selbst. Jeder Ansatz, bei dem die Änderung eines Endpunkts den Build an seinen Aufrufstellen bricht, erfüllt sie. Nicht erfüllt wird sie von einem einfachen `fetch` auf eine JSON-Route, die an der Aufrufstelle von Hand typisiert ist, denn das ist eine Grenze, an der eine falsche Annahme des Agenten sauber kompiliert, ausgeliefert und von einem Kunden entdeckt wird.

**An untypisierten API-Grenzen überleben die Fehler von Agenten.**

### Datenbank: Drizzle auf Cloudflare D1

**Punktzahl: 8/8.**

Das Schema ist TypeScript, also gleichzeitig Quelle der Migrationen und Quelle der Typen, und es gibt kein zweites Artefakt, das abweichen kann. Eine Abfrage auf eine Spalte, die nicht existiert, ist ein Kompilierfehler und kein 500er.

Über die Typisierung hinaus zählen zwei Eigenschaften. Drizzle-Abfragen ähneln SQL, also lässt sich vorhandenes SQL-Wissen übertragen. Cloudflare D1 verwendet SQLite-Semantik, also müssen Agenten dem D1-Adapter und der installierten Dokumentation folgen, statt Postgres-spezifische Abfragen zu kopieren. Versionierte Migrationen und isolierte lokale Bindings machen Änderungen prüfbar, bevor irgendeine Remote-Operation stattfindet.

### Validierung: Zod an jeder externen Grenze

**Punktzahl: 8/8.** Diese Schicht lassen die meisten Stacks weg, und sie zahlt sich am schnellsten aus.

Typen beschreiben, was Sie glauben. Schemas prüfen es. Jede Stelle, an der Daten in den Prozess gelangen (HTTP-Bodies, Umgebungsvariablen, Webhook-Payloads, Antworten von Drittanbietern, JSON-Spalten in der Datenbank), ist eine Stelle, an der das Typsystem einem Versprechen vertraut, das niemand geprüft hat.

Bei der Arbeit mit Agenten zählt das mehr als bei menschlicher Arbeit. Ein Mensch, der eine Integration schreibt, misstraut der Payload meist, weil er sich schon die Finger verbrannt hat. Ein Agent schreibt den Happy Path mit voller Zuversicht, weil seine Trainingsdaten überwiegend den Happy Path enthalten. Ein Schema an der Grenze verwandelt diesen Optimismus in einen abgefangenen Fehler mit einer Meldung, die das Feld benennt.

### Authentifizierung: Better Auth, in Ihrem Repository

**Punktzahl: 7/8.**

Die für Agenten relevante Eigenschaft ist, dass die Implementierung Quellcode ist, der Ihnen gehört, und kein undurchsichtiger gehosteter Aufruf. Ein Agent kann lesen, wie eine Session ausgestellt wird, dem Token bis zu seiner Prüfung folgen und sie so erweitern, dass Sie es in einem Diff prüfen können.

Gehostete Authentifizierung schneidet hier aus einem strukturellen Grund schlechter ab, unabhängig vom Preisargument: Die wichtige Hälfte der Logik liegt hinter einer API-Grenze, die der Agent nicht lesen kann, also endet jede Frage zum Verhalten in einer Vermutung oder einem Blick in die Dokumentation, und jede Anpassung wird zu einer Integration statt zu einer Änderung.

Den Punkt verliert sie bei der Aktualität. Es ist eine schnelllebige Bibliothek in einem Ökosystem, das sich noch konsolidiert, also ist das Gedächtnis der Modelle über ihre API unzuverlässig. Das ist ein gutes Beispiel dafür, dass der Test seine Arbeit tut: Eine Bibliothek kann die richtige Wahl sein und trotzdem auf einer Achse schlecht abschneiden, und zu wissen, auf welcher, sagt Ihnen, wo die Leitplanke hingehört.

### Styling: Tailwind

**Punktzahl: 7/8.**

Der übliche Grund ist die Menge an Trainingsdaten. Der bessere Grund ist strukturell: Die Styles stehen direkt am Element, das sie gestalten, also **gibt es keine zweite Datei, an deren Öffnen der Agent denken muss**. Ein Stylesheet in einem anderen Verzeichnis ist eine Synchronisationspflicht, und der typische Fehler von Agenten ist nicht, dass sie schlecht stylen, sondern dass sie nur eine der beiden Stellen aktualisieren.

Das gilt über das Styling hinaus. Dasselbe Argument spricht für Tests und Typen direkt neben dem Code und gegen jedes Muster, bei dem eine Änderung an einer Stelle gespiegelt werden muss, an der der Agent keinen Grund hat nachzusehen.

### Internationalisierung: use-intl mit einer Paritätsprüfung

**Punktzahl: 7/8**, und sie verdient ihren Platz hier aus einem Grund, der eigentlich nichts mit i18n zu tun hat.

Übersetzungen sind der Prototyp des stillen Fehlers. Ein Agent fügt ein Feature hinzu, schreibt englische Strings, und in den anderen Sprachen fehlen nun Schlüssel. Nichts stürzt ab. Die Tests laufen durch. Der Fehler erreicht genau die Kunden, die ihn nicht klar melden können.

Die Lösung ist keine bessere Bibliothek, sondern dass `bun run check:i18n` die CI bei einem fehlenden Schlüssel scheitern lässt. Jeder Teil Ihres Systems mit dieser Form (an einer Stelle vorhanden, an einer anderen still abwesend) braucht dieselbe Behandlung, und solange er keine hat, ist er für Ihren Agenten und für Sie unsichtbar.

### Zahlungen und E-Mail: Polar, Resend

**Punktzahl: 6/8** und **7/8**.

Zahlungsintegrationen verlieren Punkte bei der Konvergenz, nicht bei der Qualität. Diese Anwendung nutzt Polar Checkout und verifizierte Webhooks, wobei Käufe und Lizenzschlüssel in Feature-Use-Cases verarbeitet werden. Folgen Sie dieser Implementierung und dem dokumentierten Wiederholungsverhalten des Anbieters. Resend versendet die lokalisierten E-Mail-Vorlagen aus dem Worker.

Webhooks verdienen eine eigene Warnung, und die folgt weiter unten.

### Tests: Vitest und Playwright

**Punktzahl: 8/8**, und diese Schicht macht alle anderen Punktzahlen erst nutzbar.

Es geht nicht um die Testabdeckung als Zahl. Es geht darum, dass `bun run check && bun run test:coverage` existiert, mit 0 oder 1 endet und ein Agent es ausführen kann, ohne dass man ihm erklärt, wie. Alles oberhalb dieser Zeile dient dazu, einzugrenzen, was ein Agent ausdrücken kann. Diese Zeile dient dazu, abzufangen, was trotzdem durchgekommen ist.

## Jede Abhängigkeit ist Oberfläche für den Agenten

Jede Abhängigkeit ist eine API, an die sich das Modell falsch erinnern kann. Das macht aus dem üblichen Argument „zu viele Abhängigkeiten“, bei dem es normalerweise um Bundle-Größe und Lieferkette geht, zusätzlich ein Argument der Korrektheit.

Die Laufzeitabhängigkeiten stehen in `package.json`. Entscheidend ist nicht ihre Zahl, sondern ihre Form: Fast alle sind entweder durchgängig typisiert oder an einer Grenze gekapselt, die uns gehört, sodass eine falsche Annahme über sie beim Kompilieren scheitert und nicht erst in Produktion.

Inzwischen gibt es einen zweiten Grund zur Vorsicht, und das ist ein Sicherheitsgrund. Bei Frontier-Modellen, die zwischen Oktober 2025 und März 2026 erschienen sind, wurden Halluzinationsraten für Paketnamen zwischen **4,62 % und 6,10 %** gemessen ([arXiv](https://arxiv.org/pdf/2605.17062)). Angreifer registrieren diese erfundenen Namen in öffentlichen Registries und warten ab, ein Angriff namens **Slopsquatting** ([Mend](https://www.mend.io/blog/the-hallucinated-package-attack-slopsquatting/)).

Die praktische Regel: **Eine Abhängigkeit, die ein Agent hinzugefügt hat, ist ein ungeprüfter Pull Request von einem Fremden.** Prüfen Sie, ob das Paket existiert, ob sein Name genau der erwartete ist und nicht nur ähnlich klingt, und ob Sie es wirklich gebraucht haben. Lockfiles und ein Review-Schritt bei Änderungen an `package.json` decken den Großteil des Risikos mit nahezu null Aufwand ab.

## Was Agenten nie allein verantworten sollten

Manche Teile eines SaaS teilen eine Eigenschaft: **Die falsche Version sieht richtig aus, besteht die Tests, funktioniert in der Demo und scheitert erst unter Bedingungen, die Ihre Testsuite nicht nachstellt.** Diese Eigenschaft, nicht die Schwierigkeit, macht ihre Delegation unsicher.

| Bereich                     | Warum die falsche Version das Review besteht                                   |
| --------------------------- | ------------------------------------------------------------------------------ |
| Session- und Token-Handling | Ein funktionierender Login beweist nichts über Ablauf, Rotation oder Widerruf  |
| Zahlungs-Webhooks           | Ein nicht idempotenter Handler ist korrekt, bis die Wiederholung eintrifft     |
| Datenbankmigrationen        | Umkehrbarkeit und Datenverlust bleiben bis zum Rollback unsichtbar             |
| Mandantentrennung           | Die Abfrage stimmt für den Test-Mandanten und ist für den zweiten falsch       |
| Alles, was ein Secret liest | Ein Token zu loggen ist eine einzeilige Änderung, die einwandfrei funktioniert |

Der Webhook ist der deutlichste Fall. Stripe wiederholt die Zustellung bei Antworten außerhalb von 2xx, also besteht ein Handler, der bei der ersten Zustellung korrekt abbucht und bei der Wiederholung erneut abbucht, jeden Test, an den ein Agent denken würde, denn um den Test zu schreiben, muss man den Fehlerfall bereits kennen. Das ist keine Grenze der Modellfähigkeit. Die Testsuite, die ein Agent schreibt, spiegelt die Fehlerfälle in seinen Trainingsdaten wider, und Idempotenzfehler sind dort im Verhältnis dazu, wie oft sie echtes Geld kosten, unterrepräsentiert.

Kennzeichnen Sie diese Pfade in `AGENTS.md` als „nur mit menschlichem Review“ und sichern Sie das mit verpflichtenden Reviewern ab, damit die Absicht durchgesetzt wird, statt auf Vertrauen zu beruhen.

## Der Stack, und wo Sie ihn prüfen können

Jede Aussage unten verweist auf einen Befehl im öffentlichen Repository der Website und nicht auf ein Adjektiv auf einer Seite.

| Schicht           | Wahl                              | Punkte | Prüfung                                                                                                             |
| ----------------- | --------------------------------- | :----: | ------------------------------------------------------------------------------------------------------------------- |
| Sprache           | TypeScript, strikt, kein `any`    |   8    | `tsc --strict` blockiert den Merge                                                                                  |
| Laufzeit          | Cloudflare Workers                |   7    | `bun run check && bun run test:coverage`                                                                            |
| Framework         | TanStack Start, React             |   6    | Installierte Dokumentation, in `AGENTS.md` gepinnt                                                                  |
| API               | TanStack Start Server Functions   |   7    | Eine geänderte Route bricht die Aufrufstellen beim Build                                                            |
| Datenbank         | Drizzle, Cloudflare D1            |   8    | Das Schema ist Migration und Typen zugleich                                                                         |
| Validierung       | Zod an jeder Grenze               |   8    | HTTP, Umgebung, Webhooks und Zeilen werden alle geparst                                                             |
| Authentifizierung | Better Auth, im Repository        |   7    | Lesbarer Quellcode, `$0` pro Nutzer                                                                                 |
| Styling           | Tailwind, shadcn/ui im Repository |   7    | <RepositoryCount fact="uiComponents" /> Komponenten, die Sie bearbeiten können                                      |
| i18n              | use-intl, mit Paritätsprüfung     |   7    | `bun run check:i18n`                                                                                                |
| Tests             | Vitest, Playwright                |   8    | <RepositoryCount fact="testFiles" /> Testdateien, <RepositoryCount fact="e2eSpecs" /> Playwright-Suites, 100-%-Gate |

Das 100-%-Coverage-Gate ist der Teil, der den Rest sicher genug macht, um einen Agenten darauf anzusetzen. Der Agent kann so schnell schreiben, wie er will; nichts, was er kaputt macht, erreicht main, und Sie erfahren es im Pull Request statt von einem Kunden.

**Für wen das nichts ist.** Wenn Sie etwas Kostenloses zum Lernen suchen, klonen Sie ein Template und haben Sie Spaß damit. Wenn Ihnen lieber ist, dass ein gehosteter Anbieter Ihre Authentifizierung betreibt und Ihnen pro monatlich aktivem Nutzer Rechnungen stellt, kaufen Sie stattdessen das. Dies ist für Leute, die ihre Margen auch bei fünfzigtausend Nutzern noch selbst in der Hand haben wollen.

<Callout title="Prüfen Sie es, bevor Sie dafür bezahlen">

Die [Dokumentation](/docs) ist öffentlich, und der Coverage-Bericht wird vom Repository selbst erzeugt. Dann [sehen Sie sich an, was es kostet](/#pricing): eine Zahlung ab 249 $, lebenslange Core-Updates, keine Gebühren pro Nutzer.

</Callout>

## Häufig gestellte Fragen

<Accordions>

<Accordion title="Welcher Tech-Stack ist 2026 der beste für KI-Coding-Agenten?">

Durchgängiges TypeScript mit einer typisierten Datenbankschicht, Schema-Validierung an jeder externen Grenze, einer Authentifizierung, die in Ihrem Repository liegt, und einem einzigen Befehl, der Typen prüft, lintet und testet. Die konkreten Bibliotheken sind weit weniger wichtig als die Frage, ob ihre falsche Verwendung schon beim Kompilieren scheitert. Bewerten Sie jeden Kandidaten vor der Einführung nach Einschränkung, Konvergenz, Überprüfbarkeit und Aktualität.

</Accordion>

<Accordion title="Hilft ein beliebtes Framework KI-Coding-Agenten?">

Weniger als früher, und manchmal überhaupt nicht. Beliebtheit verschafft einem Modell mehr Trainingsdaten, aber nur über die Version, mit der es trainiert wurde. Ein Framework, das Breaking Changes schneller ausliefert, als Modelle neu trainiert werden, erzeugt selbstsicheren, flüssigen und falschen Code. Sobald sich eine Bibliothek schnell bewegt, zählt Stabilität mehr als Menge.

</Accordion>

<Accordion title="Warum schreibt mein Agent Code mit APIs, die es nicht mehr gibt?">

Weil er sich an die Version erinnert, mit der er trainiert wurde. Forschende haben in acht weit verbreiteten Bibliotheken Nutzungsraten veralteter APIs von 25 % bis 38 % gemessen und sie auf veraltetes parametrisches Wissen und das Fehlen jeder aktuellen Sicht auf die heutige API zurückgeführt. Ihr Typprüfer ist die günstigste Korrektur dafür, und deshalb überlebt das Problem genau an untypisierten Grenzen.

</Accordion>

<Accordion title="Sollte ich einen KI-Agenten meine Abhängigkeiten auswählen lassen?">

Nicht, ohne zu prüfen, ob jedes Paket existiert. Frontier-Modelle, die zwischen Oktober 2025 und März 2026 erschienen sind, haben Paketnamen mit Raten zwischen 4,62 % und 6,10 % halluziniert, und Angreifer registrieren diese erfundenen Namen inzwischen in öffentlichen Registries, ein Angriff namens Slopsquatting. Behandeln Sie jede neue Abhängigkeit, die ein Agent hinzufügt, wie einen ungeprüften Pull Request von einem Fremden.

</Accordion>

<Accordion title="Ist ein Monorepo besser für KI-Coding-Agenten?">

Nur wenn die Grenzen durch Werkzeuge durchgesetzt und nicht bloß in einer README beschrieben werden. Ein Monorepo, dessen Paketgrenzen beim Überschreiten den Build scheitern lassen, bringt einem Agenten Ihre Architektur in Sekunden bei. Ein Monorepo, das nur durch Konventionen zusammengehalten wird, gibt dem Agenten mehr Gelegenheiten, den richtigen Code ins falsche Paket zu legen.

</Accordion>

<Accordion title="Welche Teile eines SaaS sollte ein Agent nie allein schreiben?">

Alles, wo ein plausibel aussehender Fehler teuer ist und still bleibt: Session- und Token-Handling, Zahlungs-Webhooks, Datenbankmigrationen, Mandantentrennung und alles, was ein Secret liest. Diese Bereiche teilen eine Eigenschaft: Die falsche Version besteht Tests und Demos einwandfrei und scheitert erst unter Bedingungen, die Ihre Testsuite nicht nachstellt.

</Accordion>

<Accordion title="Brauche ich tRPC oder oRPC für eine agentenfreundliche API?">

Sie brauchen Typen, die die Netzwerkgrenze überqueren; die konkrete Bibliothek ist zweitrangig. Jeder Ansatz, bei dem ein Client, der einen geänderten Endpunkt aufruft, nicht mehr kompiliert, erfüllt den Zweck. Was nicht funktioniert, ist ein einfacher fetch auf eine untypisierte JSON-Route, denn das ist eine Grenze, an der eine falsche Annahme sauber kompiliert und in Produktion gelangt.

</Accordion>

<Accordion title="Wie viele Abhängigkeiten sind zu viele für eine agentengestützte Codebasis?">

Zählen Sie API-Oberflächen statt Pakete. Jede Abhängigkeit ist eine API, an die sich das Modell falsch erinnern kann, also lautet die Frage, wie viele davon tragend, unbekannt und ungeprüft sind. Eine Abhängigkeit, die durch strikte Typen und einen Test abgedeckt ist, kostet wenig. Eine, die untypisierte Daten in Ihre Geschäftslogik liefert, kostet bei jeder künftigen Änderung.

</Accordion>

<Accordion title="Hilft Tailwind KI-Coding-Agenten tatsächlich?">

Ja, aus einem strukturellen und nicht aus einem stilistischen Grund. Die Styles stehen direkt am Element, das sie gestalten, also gibt es keine zweite Datei, an deren Öffnen und Aktualisieren der Agent denken muss. Dasselbe Argument spricht für Tests und Typen direkt neben dem Code und gegen jedes Muster, bei dem eine Änderung in einer Datei gespiegelt werden muss, die der Agent ohne Grund nie öffnen würde.

</Accordion>

<Accordion title="Sollte ich den Stack wechseln, damit mein Agent besser arbeitet?">

Fast nie. Die Migrationskosten sind sicher und der Gewinn ist begrenzt, während strikte Typen, Validierung an den Grenzen und ein einziger Prüfbefehl in Ihrem bestehenden Stack günstig sind und sofort wirken. Wechseln Sie den Stack, wenn Sie ihn ohnehin wechseln wollten, und lassen Sie die Eignung für Agenten bei Gleichstand den Ausschlag geben, statt sie zum Grund zu machen.

</Accordion>

</Accordions>
