Playwright teste l'application construite dans de vrais navigateurs. La suite s'exécute sur l'environnement Wrangler `test` : D1, KV et R2 locaux dans `.wrangler/test`, identifiants factices issus de `.env.test` et point d'entrée de test `src/platform/testing/worker.ts`, qui intercepte les requêtes vers Resend et Polar.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:visual
bun run test:visual:update
bun run test:journey
```

| Script               | Exécute                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| `test:e2e:install`   | Installe Chromium et WebKit avec les dépendances système                                              |
| `test:e2e`           | Toutes les specs dans Chromium et WebKit                                                              |
| `test:e2e:smoke`     | `e2e/specs/smoke.spec.ts` dans Chromium                                                               |
| `test:e2e:pr`        | Toutes les specs dans Chromium, comme les exécute la vérification Chromium de la CI des pull requests |
| `test:e2e:headed`    | Toutes les specs dans des navigateurs visibles                                                        |
| `test:e2e:ui`        | Mode UI de Playwright                                                                                 |
| `test:visual`        | Les [tests visuels](#visual-tests) dans Chromium, depuis l'image Docker de Playwright                 |
| `test:visual:update` | Les tests visuels, en réécrivant les captures qui ne correspondent plus                               |
| `test:journey`       | La [suite de parcours client](#journey-suite) sur la preview                                          |

## Configuration [#configuration]

`playwright.config.ts` exécute les specs de `e2e/specs/`, définit les projets `chromium` (Desktop Chrome) et `webkit` (Desktop Safari) et utilise `PLAYWRIGHT_BASE_URL` ou `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` de `src/data/local-server.ts`). En local, la commande du serveur web exécute `db:reset:test`, `build:test` et `start:test`, et réutilise un serveur qui répond déjà à cette URL. En CI, un job prépare le build, chacun des <RepositoryFact name="e2eShards" /> shards qui se partagent la suite le décompresse, et Playwright se contente de démarrer le serveur ([CI/CD](/docs/tooling/ci-cd#checks)).

| Paramètre  | Local                                            | CI                                               |
| ---------- | ------------------------------------------------ | ------------------------------------------------ |
| Relances   | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" />    |
| Workers    | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" />    |
| Traces     | Conservées en cas d'échec                        | À la première relance                            |
| Vidéos     | Désactivées                                      | Conservées en cas d'échec                        |
| Rapporteur | Liste et HTML                                    | GitHub et blob, fusionnés en HTML en cas d'échec |

## Lancer la suite à côté d'autres worktrees [#running-beside-other-worktrees]

Le build de test n'accepte les requêtes que des hôtes auxquels il fait confiance en mode test, car Better Auth et les liens de la newsletter vérifient l'hôte de la requête : `127.0.0.1:3000` et `localhost:3000`, ainsi que `127.0.0.1` et `localhost` sur les ports <RepositoryFact name="testServerFirstPort" /> à <RepositoryFact name="testServerLastPort" />, fixés par `TEST_SERVER_PORTS` dans `src/data/local-server.ts`. Sur tout autre port, les pages de connexion et de cours échouent : `playwright.config.ts` s'arrête donc avant de construire quoi que ce soit quand `PLAYWRIGHT_BASE_URL` désigne un autre hôte.

`PLAYWRIGHT_BASE_URL` est le seul réglage qui choisit le port : Playwright ouvre cette URL et démarre `start:test` sur son port. Quand d'autres worktrees lancent leur suite en même temps, donnez à chaque worktree son propre port de la plage. Vérifiez que rien n'écoute sur ce port, puis lancez-y la suite :

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` n'affiche rien quand le port est libre. S'il affiche un processus, prenez un autre port et laissez ce serveur tranquille : n'arrêtez que les serveurs que vous avez démarrés.

En local, Playwright réutilise un serveur qui répond déjà à l'URL et saute alors la réinitialisation de la base de données et le build : la suite ne doit donc jamais atteindre le serveur d'un autre worktree. `e2e/global-setup.ts` y veille : avant le premier test, il cherche avec `lsof` les processus qui écoutent sur le port et arrête l'exécution quand l'un d'eux tourne dans un autre répertoire que ce worktree. Un serveur que vous avez démarré depuis ce worktree passe la vérification et est réutilisé tel quel : arrêtez-le quand la suite doit tester un build tout neuf.

## Organisation

- `e2e/specs/` : specs pour les vérifications de fumée, la page d'accueil et ses commandes, la navigation, les langues, le thème, le SEO, l'authentification avec ses redirections et son routage, les espaces de travail, l'administration des utilisateurs, la newsletter, le contenu, les pages légales, la tarification régionale, le tunnel de paiement, la page de licence, l'API de licence de la CLI, l'affiliation, les vidéos, les cours, l'accès aux cours, l'administration des cours, les couvertures, l'import et les supports des cours, le tableau de bord d'administration, les commandes, les produits et les machines des licences, l'index du blog et le partage des articles, la Content Security Policy, la rétractation, le pied de page, les anneaux de focus, les barres de défilement, les webhooks des licences, la CLI publiée et l'accessibilité (<RepositoryFact name="e2eSpecs" /> fichiers).
- `e2e/pages/` : objets de page.
- `e2e/fixtures/` : la fixture `test` étendue, des utilitaires pour les e-mails capturés, `deliverPaidOrder` dans `license.ts`, qui envoie un webhook `order.paid` signé pour accorder une licence, `buyLicense`, qui demande au Worker de test sur `/__test/polar/purchase` une commande avec sa clé de licence dans le double de test Polar et envoie leurs `order.paid` et `benefit_grant.created` signés, `startedCheckouts`, qui lit sur `/__test/polar/checkouts` les paiements créés par le double, `payCheckout`, qui paie via `/__test/polar/pay` du Worker de test un paiement que l'application a ouvert, avec le consentement coché, et envoie les `order.paid` et `benefit_grant.created` signés de sa commande, `accessibilityViolations` avec les `COLOR_SCHEMES` clair et sombre dans `accessibility.ts`, et la page de paiement de Polar dans `polar-checkout.ts`. Le double Polar donne à chaque paiement une URL sur l'origine du checkout de Polar, et `servePolarCheckout`, l'un des `BROWSER_DOUBLES` qu'installe la fixture automatique `browserDoubles`, répond à cette URL dans chaque contexte de navigateur avec une page du double, lue sur `/__test/polar/checkout` du Worker de test : elle indique à la fenêtre superposée qu'elle est chargée, et ses boutons **Pay** et **Close** envoient `confirmed` et `success`, ou `close`, à l'`embed_origin` du paiement, comme le fait la page de Polar. `payInCheckoutOverlay` et `closeCheckoutOverlay` appuient dessus, et `refusePolarCheckoutEmbedding` sert la page avec `frame-ancestors 'none'`, comme Polar le fait pour un hôte que son organisation ne liste pas. La suite de parcours client règle l'option `browserDoublesEnabled` sur `false` et paie sur la vraie sandbox. `orderLicense` n’envoie que le `order.paid` d’un tel achat et renvoie `issueKey`, qui envoie plus tard son `benefit_grant.created`. Ouvert comme la page de paiement de Polar elle-même, hors d’un cadre, le bouton **Pay** du double envoie le navigateur vers l’URL de succès du paiement avec un `customer_session_token`, comme le fait la page de Polar, et `payOnPolarCheckoutPage` le presse. `refundOrder`, `revokeLicenseKey`, `deliverGuestOrder` et `cutOffPolar` demandent au Worker de test sur `/__test/polar/refund`, `/__test/polar/revoke`, `/__test/polar/guest-purchase` et `/__test/polar/cut-off` un `order.refunded` signé d’une commande du double, un `benefit_grant.revoked` signé de sa clé, un `order.paid` signé d’un acheteur sans compte, ou une clé dont les requêtes à Polar échouent comme si Polar était injoignable. `signUpBuyer` dans `buyer.ts` inscrit un acheteur par l’API, `sendToApi` dans `cli-api.ts` appelle l’API de licence de la CLI depuis une adresse qui lui est propre, et `EVERY_STACK_ANSWER` dans `stack-answers.ts` réunit un jeu de réponses valide pour chaque option et chaque extra de la stack.
- `e2e/data/accounts.ts` : les comptes créés par le seed, un administrateur et un client, ainsi que leur mot de passe. `e2e/data/licenses.ts` contient le client avec une licence et cette licence, ainsi qu'une licence pour chaque worker parallèle, sur laquelle la spec de l'API de licence de la CLI active des machines.
- `e2e/data/videos.ts` et `e2e/data/courses.ts` : la vidéo de test créée par le seed, dont les fichiers sont dans `e2e/fixtures/video/`, et le cours créé par le seed : deux chapitres, le premier avec un aperçu gratuit, une leçon réservée aux comptes et une leçon payante, le second avec trois leçons payantes dont la vidéo est encore en cours d'enregistrement.
- `e2e/data/<feature>.pages.ts` et `e2e/data/<feature>.seed.ts` : les pages de chaque fonctionnalité, que visitent `accessibility.spec.ts` et `workspaces.spec.ts`, ainsi que ses lignes et ses médias dans la base de test, chaque liste importée par `ENTRIES` dans `e2e/data/pages.ts` et par `scripts/seed-test.ts`.
- `e2e/data/<feature>.flows.ts` : les parcours de chaque fonctionnalité, chacun avec le test qui le prouve de bout en bout ou la raison pour laquelle il manque, importés par `FLOWS` dans `scripts/check-flows.ts` ; voir [Couverture des tests](/docs/tooling/test-coverage).
- `e2e/global-setup.ts` : la configuration globale, qui arrête l'exécution quand le serveur du port de la suite tourne depuis un autre worktree.
- `e2e/journey/` : la [suite de parcours client](#journey-suite), avec sa propre configuration. `published-cli.spec.ts` exécute la CLI publiée avec `runCli` de `e2e/journey/cli.ts` contre le Worker de test : la suite navigateur a donc besoin du registre npm.

Le Worker de test exécute ce que les fonctionnalités déclarent dans `e2e/data/<feature>.worker.ts`, chaque liste importée par `ENTRIES` dans `src/platform/testing/worker.ts` : la fonctionnalité des licences enregistre les clés de licence de test dans le mock de Polar, Resend expose `/__test/emails` pour lire les e-mails capturés et la newsletter `/__test/newsletter` pour lire l'état d'un abonné.

## Accessibilité

`e2e/specs/accessibility.spec.ts` exécute [axe-core](https://github.com/dequelabs/axe-core) via `@axe-core/playwright` sur les pages publiques, les pages de cours, l'accueil de la documentation, chaque page de Conventions et une page de chacune des autres sections de la documentation, un article du blog et les espaces de travail administrateur et client, dans les thèmes clair et sombre. Les pages d'administration comprennent `/admin/courses`, `/admin/courses/create` et l'éditeur du cours de test, que `e2e/specs/workspaces.spec.ts` visite aussi. Il applique les règles A et AA des WCAG 2.0, 2.1 et 2.2 ainsi que les bonnes pratiques d'axe, échoue si une page ne se charge pas avec un statut de succès, fait défiler la page pour que les sections qui apparaissent au défilement soient aussi vérifiées, attend la fin des animations finies et échoue à la moindre violation en indiquant la règle, son impact et les sélecteurs concernés.

axe ne voit ni le parcours au clavier ni la mise en page, donc trois specs les vérifient pour l'en-tête et le pied de page du site : `e2e/specs/navigation.spec.ts`, que le menu du téléphone prend le focus, garde Tab à l'intérieur, rend la page derrière `inert` et rend le focus à son bouton ; `e2e/specs/footer.spec.ts`, qu'à <RepositoryFact name="footerPhoneWidths" /> px aucun lien du pied de page n'en touche un autre ni n'en sort, dans aucune langue, et qu'un lien vers une section de l'accueil n'est courant que sur sa propre section ; et `e2e/specs/focus-rings.spec.ts`, que le sélecteur de langue du pied de page et le déclencheur de la palette de commandes de l'administration dessinent leur anneau pour le clavier.

`e2e/specs/text-layout.spec.ts` vérifie le formulaire de cours et les tableaux de l’administration ainsi que le générateur de commandes de la page d’accueil à <RepositoryFact name="textLayoutWidths" /> px avec `textLayoutProblems` de `e2e/fixtures/text-layout.ts` : aucune ligne de texte ne chevauche une autre ligne ou une icône, aucune n’est coupée sans points de suspension, aucune n’est réduite à quelques lettres par des points de suspension, la page ne défile jamais horizontalement et chaque onglet de langue du formulaire de cours est visible. Le texte qui défile sous une colonne épinglée ou un en-tête fixe est masqué par eux ; la vérification ne compare donc le texte fixe qu’à d’autre texte fixe. Un autre test ouvre chaque tableau de l’administration en anglais et en ukrainien, la langue aux en-têtes les plus longs, et échoue dès qu’un en-tête est plus large que sa cellule.

## Barres de défilement [#scrollbars]

`e2e/specs/scrollbars.spec.ts` lance Chromium sans l'option `--hide-scrollbars` de Playwright, via `ignoreDefaultArgs` dans `launchOptions` : Chromium dessine alors des barres de défilement classiques qui prennent de la place, comme sous Windows, sous Linux et sur un Mac réglé pour toujours afficher les barres. La spec vérifie qu'une page légale, une page d'authentification et une page d'administration gardent leur titre en place quand la fenêtre grandit jusqu'à ce que la page ne défile plus (une page de la documentation défile toujours, car le pied de page du site suit sa mise en page de la hauteur de la fenêtre), qu'ouvrir la recherche de la documentation, le sélecteur de langue, une boîte de dialogue ou un menu ne déplace rien, que `/admin` remplit la fenêtre et que la fenêtre derrière une page sombre est sombre avec le thème clair. WebKit sur macOS ne dessine que des barres superposées, qui ne prennent pas de place, et aucune option de lancement n'y change rien : la vérification de la place réservée ne tourne donc que dans Chromium. Le menu du site, qui remplace les liens de l'en-tête sous `lg`, est vérifié à 768 px : l'ouvrir et le fermer ne déplace rien.

## Tests visuels [#visual-tests]

`e2e/specs/visual-*.spec.ts` comparent ce que voit un visiteur avec des captures d'écran approuvées, rangées dans `e2e/specs/__screenshots__/`. Une modification qui fait passer un titre sur une ligne de plus, ajoute une carte ou déplace une section fait donc échouer la pull request, même quand tous les autres tests passent. Les specs tournent dans leur propre projet Playwright, `visual`, que `playwright.config.ts` ne définit que lorsque `PLAYWRIGHT_VISUAL_BROWSER` désigne un serveur de navigateur ; les projets `chromium` et `webkit` les ignorent.

```sh
bun run test:visual
bun run test:visual:update
```

| Spec                                             | Captures                                                                                                                                                                        | Langues et largeurs                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `visual-landing.spec.ts`, `visual-facts.spec.ts` | L'en-tête, la section d'ouverture, la grille des chiffres, les tarifs avec les autres options, les cas, le manifeste, la section finale et le pied de page de la page d'accueil | Chaque langue à chaque largeur                         |
| `visual-content.spec.ts`                         | La carte de l'auteur et l'appel à l'action à la fin d'un article de blog                                                                                                        | Chaque langue sur téléphone, l'anglais sur ordinateur  |
| `visual-content.spec.ts`                         | Une page de la documentation                                                                                                                                                    | L'anglais aux deux largeurs, l'allemand sur ordinateur |
| `visual-auth.spec.ts`                            | L'en-tête d'un visiteur connecté, `/admin` et `/admin/settings`                                                                                                                 | L'anglais aux deux largeurs, l'allemand sur ordinateur |
| `visual-billing.spec.ts`                         | `/app/billing`                                                                                                                                                                  | L'anglais aux deux largeurs, l'allemand sur ordinateur |

Les langues sont <RepositoryFact name="visualLocales" />, les largeurs <RepositoryFact name="visualWidths" /> px, et la suite compte <RepositoryFact name="visualScreenshots" /> captures. Sur la page d'accueil, c'est surtout le texte qui change : ses sections sont donc capturées dans chaque langue aux deux largeurs. Les cartes sous un article de blog cassent là où les mots longs passent à la ligne, sur un téléphone : elles sont donc capturées à la largeur d'un téléphone dans chaque langue. Les pages de l'administration et de l'espace client tiennent leur mise en page de leurs composants plutôt que de leurs textes : l'anglais aux deux largeurs montre la mise en page, et l'allemand, la langue aux mots les plus longs, montre les libellés qui ne tiennent plus.

### Les mêmes pixels à chaque exécution [#same-pixels-on-every-run]

- Le contexte du navigateur fixe `reducedMotion: "reduce"` : l'entrée de la section d'ouverture, les sections qui apparaissent au défilement et les vidéos en boucle restent immobiles, et les vidéos affichent leur image d'aperçu. `toHaveScreenshot` arrête toutes les autres animations, comme le bandeau défilant de la stack, et masque le curseur de texte.
- Le thème est sombre et le fuseau horaire UTC.
- Avant la première capture, `openForScreenshots` de `e2e/fixtures/visual.ts` attend que la page soit rendue et hydratée, charge et décode chaque image, y compris celles chargées à la demande, et attend `document.fonts.ready`.
- `expectRegion` découpe une section dans la page entière, à l'endroit où elle se trouve, si bien que l'en-tête fixe ne la recouvre jamais.
- Des masques cachent ce qui change sans aucun changement de mise en page : les chiffres qui comptent des fichiers du dépôt et les étoiles GitHub, et les années de la mention de copyright dans le pied de page.
- Les données viennent de la base de test remplie de ses données initiales. `scripts/visual-tests.ts` s'arrête avant le premier test quand un serveur répond déjà à l'URL de la suite, si bien que Playwright réinitialise lui-même la base, construit et démarre le serveur ; en CI, le job décompresse sa propre copie du build et de ses données.

### Le même navigateur sur chaque machine [#the-same-browser-on-every-machine]

Les polices s'affichent différemment sous macOS et sous Linux, et même d'une image Linux à l'autre : les tests visuels n'utilisent donc jamais un navigateur de la machine qui les lance. `scripts/visual-tests.ts` démarre le serveur de navigateur de Playwright dans l'image Docker `<RepositoryFact name="visualBrowserImage" />` pour `linux/amd64`, que Docker Desktop émule sur les puces Apple, transmet son adresse dans `PLAYWRIGHT_VISUAL_BROWSER` et lance `playwright test --project=visual`. Les tests s'y connectent par `connectOptions`, dont `exposeNetwork: "<loopback>"` permet au navigateur d'atteindre le serveur de test sur l'adresse de bouclage de la machine. Le tag de l'image suit la version installée de `@playwright/test` : `bun run deps:update` fait donc avancer ensemble le navigateur et l'outil qui lance les tests. Un portable et la CI produisent les mêmes pixels, et les captures de référence prises en local passent donc en CI. `test:visual` a besoin de Docker en marche.

### Seuil [#threshold]

Une capture échoue lorsque plus de <RepositoryFact name="visualMaxDiffPercent" unit="percent" /> de ses pixels diffèrent, un pixel ne comptant comme différent que si sa couleur dépasse le seuil que Playwright applique à chaque pixel. Le navigateur et ses polices sont partout les mêmes : une page inchangée ne diffère d'aucun pixel, et la nuance ou deux dont un autre processeur peut arrondir l'anticrénelage reste sous ce seuil. Une capture dont la taille change, parce qu'un titre passe sur une ligne de plus ou qu'une carte s'ajoute, échoue quel que soit le seuil, et un seul mot ajouté au paragraphe de la section d'ouverture change déjà plus de pixels que le seuil n'en permet.

### Mettre à jour les captures de référence [#updating-the-baselines]

Quand une modification de la mise en page ou du texte est voulue, lancez `bun run test:visual:update`, ouvrez chaque PNG modifié de `e2e/specs/__screenshots__/` dans le diff de votre branche, regardez-le et committez-le avec la modification. `--update-snapshots=changed` ne réécrit que les captures qui ne correspondent plus. Quand le job `visual` échoue en CI, il envoie `test-results/` comme artefact `visual-differences`, avec l'image attendue, l'image obtenue et l'image des différences de chaque capture en échec.

### En CI [#in-ci]

Le job `visual` de `e2e-reusable.yml` ne tourne que pour Chromium, à côté des shards : il attend le build de test comme un shard, le décompresse et lance `bun run test:visual`, et la vérification `Build and E2E (chromium)` échoue s'il n'a pas réussi. Les captures de référence sont celles de Chromium, parce que WebKit dessine le texte et les sous-pixels autrement : il lui faudrait un second jeu de captures et une seconde relecture de la même mise en page, tandis que la vérification WebKit continue de tester le comportement de WebKit.

## Suite de parcours client [#journey-suite]

`bun run test:journey` achète une licence et utilise la CLI comme le fait un client, sur le déploiement de preview à `https://preview.saasyland.com`, qui encaisse les paiements dans la sandbox Polar. `e2e/journey/playwright.config.ts` est une configuration à part, avec son propre projet Chromium et sans serveur web, si bien que ni `test:e2e` ni les vérifications des pull requests ne l'exécutent ; `journey.yml` l'exécute chaque nuit et à la main ([CI/CD](/docs/tooling/ci-cd#journey-suite)). Chaque offre est un test à part entière, avec le tag `@core`, `@complete` ou `@agency`, les tests s'exécutent en parallèle, et chacun passe par ces étapes :

1. **Compte.** Le test s'inscrit avec une nouvelle adresse de la boîte de test de Resend, `delivered+journey-<run>-<tier>@resend.dev`, ou `upgrade` à la place de l'offre pour le test de mise à niveau, trouve l'e-mail de vérification via l'API Resend et ouvre son lien.
2. **Prix.** `/app/license` doit proposer l'offre au prix du pays où Cloudflare situe le runner, tel que `/cdn-cgi/trace` l'indique : le prix régional dans un pays de `PPP_TIERS`, le prix plein partout ailleurs.
3. **Paiement.** Le checkout de la sandbox Polar doit s'ouvrir par-dessus `/app/license`, dans un cadre de `sandbox.polar.sh` qui prend le focus, sans quitter la page, avec l'e-mail du compte déjà rempli et le consentement à la fourniture immédiate décoché ; le test le coche dans le cadre. Le test paie avec la [carte de test de Stripe](https://docs.stripe.com/testing) et une facturation en Pologne, où l'adresse de facturation se limite au pays. La page doit recevoir les messages `loaded`, `confirmed` et `success` de Polar dans cet ordre, fermer la fenêtre superposée et afficher la licence active sur `/app?checkoutId=<id>&tier=<tier>`. Polar n'affiche le checkout dans un cadre que tant que l'organisation sandbox liste `preview.saasyland.com` sous [Settings > Embedding](/docs/getting-started/polar-setup#embedding).
4. **Commande et clé.** Polar doit détenir une seule commande payée pour le produit de l'offre, au prix qu'a proposé `/app/license`, avec le consentement et la langue de l'acheteur, la confirmation d'achat doit arriver dans la boîte de réception, et `/app/license` doit afficher la clé émise par les webhooks, les commandes de la CLI et aucune machine utilisée.
5. **CLI.** La CLI publiée, lancée comme <RepositoryFact name="cliExec" /> à l'image des commandes de `/app/license`, s'adresse à la preview via `SAASYLAND_API_URL`. `activate` écrit le fichier d'identifiants avec le mode `0600`, une nouvelle activation garde le même emplacement, et `whoami` affiche la machine. Des machines de CI, distinguées par `SAASYLAND_CI_REPOSITORY`, occupent les emplacements restants, jusqu'à <ActivationLimit tier="core" /> machines pour Core, <ActivationLimit tier="complete" /> pour Complete et <ActivationLimit tier="agency" /> pour Agency, et la suivante est refusée avec `activationLimitReached`. Dès qu'un emplacement est libéré sur `/app/license`, la machine refusée l'obtient et celle qui a été libérée reçoit `activationNotFound`. `deactivate` libère la première machine et supprime ses identifiants.
6. **Remboursement.** Le test rembourse la commande via l'API de la sandbox Polar et attend que `/app/license` affiche la licence comme remboursée ; `whoami` doit alors répondre `licenseRefunded` et supprimer les identifiants.

Un quatrième test, avec le tag `@upgrade`, met une licence à niveau. Il achète Core de la même façon et occupe les <ActivationLimit tier="core" /> machines de Core, et la suivante est refusée. `/app/license?tier=complete` doit ensuite proposer Complete à son prix pour le pays du runner, moins ce qu'a coûté la commande Core, et le test paie cette différence de la même façon, dans le paiement de Polar par-dessus la page. Polar doit détenir la commande de mise à niveau au montant de la différence, avec la commande et l'offre Core dans `upgrade_from_order` et `upgrade_from_tier` ; la clé de la commande Core doit maintenant autoriser les <ActivationLimit tier="complete" /> machines de Complete, la clé que Polar a accordée pour la commande de mise à niveau doit être désactivée, et `/app/license` doit afficher Complete avec la même clé. La machine refusée et la suivante s'activent alors, et celle d'après est refusée. Le test rembourse la commande de mise à niveau via l'API de la sandbox Polar : la licence doit redevenir Core, avec la même clé et la limite de Core, les machines déjà activées continuent de fonctionner et une nouvelle est refusée. Un remboursement de la commande Core met ensuite fin à la licence.

Chaque machine de la CLI est un répertoire du dossier de sortie du test que la CLI utilise comme répertoire personnel, et la CLI s'exécute avec pour tout environnement `PATH`, ce répertoire, un cache npm et les variables `SAASYLAND_*`, de sorte qu'aucun identifiant de la suite ne l'atteint. Une commande qu'un test en échec laisse payée est remboursée à la fin du test. Les comptes restent sur la preview, chacun avec une licence remboursée.

La suite lit ces valeurs dans l'environnement, ou dans `.env.preview` quand le fichier existe, et s'arrête avant le premier test sans elles ; en CI, `journey.yml` les lit dans l'environnement GitHub `Preview` :

| Variable                                                                        | Utilisation                                                                                                                                                            |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | Lire et rembourser les commandes dans la sandbox et lire leurs clés de licence, avec les scopes `orders:read`, `refunds:write`, `benefits:read` et `license_keys:read` |
| `POLAR_SERVER`                                                                  | Doit valoir `sandbox`                                                                                                                                                  |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Les produits de la sandbox auxquels les commandes doivent correspondre                                                                                                 |
| `RESEND_API_KEY`                                                                | Lire les e-mails de vérification envoyés par la preview, ce qui demande une clé à accès complet                                                                        |

La preview doit exécuter un build qui contient l'[API de licence de la CLI](/docs/features/cli-licence-api). Elle exécute `main`, que `deploy.yml` y déploie avant la production ; pour tester une branche avant sa fusion, déployez-la avec `gh workflow run preview.yml --ref <branch>` une fois ses vérifications réussies. La sandbox doit correspondre au code, ce que vérifie `bun run polar:verify:preview`. Ensuite :

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

`bun run test:journey --grep @core` ne lance que le test qui porte ce tag. Le rapport HTML est écrit dans `playwright-report/journey/` et un rapport JSON dans `playwright-report/journey.json`, et les traces, vidéos et répertoires de machines des tests en échec dans `test-results/journey/`.
