Better Auth зберігає користувачів, облікові записи, сесії та токени верифікації в D1 через адаптер Drizzle. Він забезпечує реєстрацію за електронною поштою й паролем з обов'язковим підтвердженням пошти, вхід через GitHub і Google, скидання пароля, зміну електронної пошти, двофакторну автентифікацію TOTP, керування користувачами для адміністраторів і оформлення замовлення через Polar. Його HTTP API обслуговує `src/routes/api/auth.$.ts`.

## Файли

| Файл                                                   | Відповідальність                                                                                                                                                |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth.server.ts`                                       | Екземпляр `betterAuth`: провайдери, плагіни `admin`, `twoFactor`, Polar і `tanstackStartCookies`, дозволені хости, обмеження частоти запитів у D1 і хуки листів |
| `auth.client.ts`                                       | `authClient` та його методи (`signIn`, `signUp`, `signOut`, `useSession`, `twoFactor` та інші)                                                                  |
| `auth.routes.ts`                                       | Гарди маршрутів для `beforeLoad`                                                                                                                                |
| `auth.middleware.ts`                                   | Middleware серверних функцій: `withRequest`, `authorized`, `withRateLimit` і `RATE_LIMITS`                                                                      |
| `auth.access.ts`                                       | Ролі, оголошення дозволів і `hasPermission`                                                                                                                     |
| `auth.session.ts`                                      | `getRequestSession`, серверна функція `getCurrentSession` і `getCurrentSessionQuery`                                                                            |
| `auth.errors.ts`, `auth.zod.ts`, `auth.constraints.ts` | Ключі помилок, схеми форм і обмеження пароля                                                                                                                    |

## Гарди маршрутів

| Гард                 | Використовується в               | Поведінка                                                                       |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------------- |
| `requireSignedIn`    | `/app`                           | Без сесії перенаправляє на сторінку входу, інакше повертає сесію                |
| `requireAdmin`       | `/admin`                         | Додатково вимагає дозвіл `admin: ["access"]`, інакше перенаправляє на `/app`    |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Надсилає користувача, який уже ввійшов, на `/admin` або `/app` залежно від ролі |
| `redirectAfterAuth`  | `/auth/callback`                 | Вимагає сесію, а потім перенаправляє до робочого простору відповідно до ролі    |

Гарди завантажують сесію через кеш запитів і очищують кеш, коли змінюється користувач, що ввійшов.

## Серверні функції

Гарди сторінок захищають лише навігацію, тому кожна захищена серверна функція повторно перевіряє викликача за допомогою middleware з `auth.middleware.ts`:

- `authorized(permission?)` вимагає сесію, за потреби перевіряє дозвіл і додає сесію до контексту як `context.auth`. Операції з власними даними викликача використовують `context.auth.user.id`, а не ідентифікатор користувача із вхідних даних.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (3 запити за 60 секунд) або `RATE_LIMITS.TOKEN` (5 за 60 секунд) обмежує публічну операцію для кожної клієнтської IP-адреси з `cf-connecting-ip`.
- `withRequest`, який входить до обох, зіставляє помилки з кодами `AppError`: помилки Better Auth стають `AUTH_API_ERROR` зі своїм ключем помилки, помилки Zod — `VALIDATION`, а неочікувані помилки записуються в лог і повертаються як `INTERNAL_ERROR`.

## Ролі та дозволи

`auth.access.ts` визначає дві ролі: `admin` і `customer` (типова для нових облікових записів). Оголошення застосунку охоплюють `admin`, `category`, `order`, `product` і `settings`; роль адміністратора також отримує адміністративні оголошення Better Auth. `hasPermission({ permission, role })` спільно використовують гарди, middleware та UI.

## Листи та обмеження частоти

Хуки листів в `auth.server.ts` викликають сценарії використання: `sendVerifyEmail`, `sendResetPasswordEmail` і `sendChangeEmailConfirmationEmail`. Власний обмежувач частоти Better Auth зберігає лічильники в таблиці D1 `rate_limit` через `authRateLimitStorage` з `src/lib/rate-limit.ts`, який використовує атомарні upsert-операції й відхиляє запити, коли його сховище недоступне. `getRequestSession` оминає кеш cookie, тож авторизація завжди зчитує сесію з D1.
