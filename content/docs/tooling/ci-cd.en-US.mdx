Workflows live in `.github/workflows/`. The application workflows (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `e2e-reusable.yml` and `deploy-reusable.yml`) set up the toolchain with the composite action `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ with the Node version from `.nvmrc` and Bun's install cache, which `setup-vp` restores once, `bun install --frozen-lockfile --ignore-scripts` and `bun run typegen`. `remotion.yml` sets up Node from `.nvmrc` and npm instead.

| Workflow              | Trigger                                                                                 | Jobs                                                                                              |
| --------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests, merge groups, and calls from `deploy.yml`                                | Checks, tests with coverage on parallel shards, Chromium E2E and the upload of the preview Worker |
| `deploy.yml`          | Pushes to `main`                                                                        | The checks of `ci.yml` unless the merge queue ran them, then preview, production and the release  |
| `preview.yml`         | Manual                                                                                  | Deploys a branch whose checks passed to the shared preview                                        |
| `e2e-full.yml`        | Pushes to `main`, the schedule <RepositoryFact name="e2eFullSchedule" /> in UTC, manual | WebKit on push; Chromium and WebKit on schedule and manual runs                                   |
| `journey.yml`         | The schedule <RepositoryFact name="journeySchedule" /> in UTC, manual                   | The [journey suite](#journey-suite) against the shared preview, in the Polar sandbox              |
| `e2e-reusable.yml`    | Called by the workflows above                                                           | One test build, one Playwright project on parallel shards and one check for both                  |
| `deploy-reusable.yml` | Called by `ci.yml`, `deploy.yml` and `preview.yml`                                      | Build, then D1 migrations and `wrangler deploy`, or `wrangler versions upload`                    |
| `remotion.yml`        | Changes to `remotion/` or the website files it imports                                  | Checks and bundles the landing page video project with npm                                        |

`remotion.yml` runs on the same paths for pull requests and pushes: `remotion/`, the workflow itself and the website files that `remotion/src` imports, directly or through other website files. `src/__test__/workflows.test.ts` follows those imports and fails when a file they reach matches none of the paths, or a path matches none of the files.

The checkouts in `e2e-reusable.yml`, whose build renders the changelog and whose `content.spec.ts` reads it, in `deploy-reusable.yml`, which builds the site, and in the `release` job fetch every commit without its trees (`fetch-depth: 0` and `filter: tree:0`), because the [changelog](/docs/project/changelog) dates each entry by the commit that brought it to `main`. That adds only the commits themselves to what a shallow clone downloads, and a shallow clone fails the build instead of dating the entries wrongly. `src/__test__/workflows.test.ts` fails when one of these checkouts stops fetching the history.

## Checks

Three jobs in `ci.yml` stand behind the required check `Format, lint, types, i18n, tests`:

| Job                                                | Runs                                                                                                                                                                                                                                                  |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                            | `bun run check`: class-name tables, i18n and content checks, the [flow inventory](/docs/tooling/test-coverage#flow-coverage), formatting, lint and types                                                                                              |
| `test`                                             | One job per shard, <RepositoryFact name="vitestShards" /> in parallel: `bun run test:coverage --shard=<n>/<total>` with Vitest's blob reporter, then uploads the shard's blob report with its coverage                                                |
| `verify`, named `Format, lint, types, i18n, tests` | Once every shard passed, downloads the blob reports and runs `bun run test:coverage --merge-reports`, which merges the coverage and enforces the thresholds, then uploads the coverage report; fails unless `check`, every shard and the merge passed |

A shard checks no threshold, because it measures only the code its own tests reach; the thresholds of `vite.config.ts` apply once, to the merged coverage of every shard, as they do to a local `bun run test:coverage`. The `verify` job is the one check that the branch rules require, so adding or removing a shard changes no required check name.

The `e2e` job calls `e2e-reusable.yml`, which builds once and runs the suite on <RepositoryFact name="e2eShards" /> runners in parallel:

| Job                                        | Runs                                                                                                                                                                                           |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                    | `db:reset:test` and `build:test`, then uploads `dist`, the `.wrangler/deploy` pointer to its Worker configuration and the seeded `.wrangler/test` as one artifact                              |
| `shard`                                    | One job per shard, started beside the build: installs the browser, waits for the build's upload, downloads it and runs `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>` |
| `report`, named `Build and E2E (chromium)` | Fails unless the build and every shard passed; when a shard failed, merges the shards' blob reports into one HTML report and uploads it                                                        |

The shards do not wait for the whole `build` job (`needs`): they start with it and set up the toolchain and the browser while it builds. Then `scripts/wait-for-job.ts` asks GitHub's API every few seconds for the run's `build` job, until its step `Upload the test build` has succeeded, and the shard downloads the artifact. It sends the ETag of the previous answer, and GitHub does not count an unchanged answer against the token's rate limit. A failed step of the build, or a build that ends without its upload, fails every shard within seconds with the failed step and a link to the build, and a shard that waits past the script's limit fails with an error that says so. Reading the run's jobs takes `actions: read`, which only the `shard` job asks for: `ci.yml`, `e2e-full.yml` and the `checks` job of `deploy.yml` grant it to the workflows they call, and every other job keeps `contents: read`.

Playwright's own retries and workers stay as [Playwright](/docs/tooling/playwright#configuration) describes them, on every shard. The `report` job is the one check that the branch rules require, so adding or removing a shard changes no required check name. The build also packs the list of release tags it read, and each shard deletes any tag created since: `content.spec.ts` reads the release tags from Git, and a release tagged while the shards wait would make it expect a changelog the build never rendered.

The `upload` job, named `Worker upload`, calls `deploy-reusable.yml` with `upload: true`: it builds the preview Worker exactly as a deploy does and runs `wrangler versions upload`, which sends it to the `saasyland-preview` Worker as a new version without deploying it. Cloudflare checks the upload as it checks a deploy, the size limit, the start-up time, the bindings and the secrets that `secrets.required` names, so a Worker that this check passes deploys, while `preview.saasyland.com` keeps serving the version deployed before. The job applies no migration and records no GitHub deployment (`deployment: false`), and it runs side by side with the uploads of other pull requests. A pull request's version gets the alias `pr-<number>`, which names the version in Cloudflare's dashboard; the job summary prints the version's ID and size, and its URL when Version URLs are on for the Worker, which they are not for `saasyland-preview` today. Pull requests from forks and from Dependabot cannot read the Cloudflare credentials and skip the job; the merge queue, which can, uploads their build before they merge.

In a pull request, `bun run check` also fails until the pull request adds its [changelog entry](/docs/conventions/git-workflow#changelog-entries), and in the merge queue until the entry of the queued pull request is there. The build in the `e2e` and `upload` jobs, and in the deploy jobs, fails while the changelog would list an entry under **Unreleased** that is not the pull request's own, and in the merge queue and on `main` while it would list any.

## Merge queue [#merge-queue]

The ruleset that protects `main` requires `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)` and `Worker upload / Upload preview`, and merges pull requests only through GitHub's merge queue, which squashes each one. `bun scripts/enqueue-pr.ts <number>` puts a pull request in the queue ([Git and pull requests](/docs/conventions/git-workflow#merging)). For each pull request in the queue, GitHub writes the squash commit on a branch named `gh-readonly-queue/main/pr-<number>-<commit>`, on top of `main` and of the pull requests ahead of it, and runs `ci.yml` on it for the `merge_group` event. Once each pull request of a group has passed, GitHub moves `main` to the group's last commit, the very commit the queue tested, so one push brings every pull request of the group to `main` as its own squash commit. A pull request that fails leaves the queue, and the ones behind it are tested again without it.

`ci.yml` cancels a pull request's run when a newer commit replaces it, but never a run of the queue, whose branches each have a ref of their own. The changelog gate treats the queue's branch as `main`: each pull request of the group is already a squash commit whose subject ends with its number, so no entry may be unreleased, and the queued pull request's own entry must exist.

## Deployments

`deploy.yml` deploys every push to `main`, the shared preview first and production after it, once the commit has passed every check that `main` requires. Its first job, `tested`, runs `scripts/tested-commit.ts`, which reads those checks from the ruleset through GitHub's API and looks for a successful run of each on the pushed commit. A commit that came through the merge queue has them, because the queue tested that very commit, so `deploy.yml` deploys it without running the checks again; a commit that reached `main` any other way runs the checks of `ci.yml` first.

| Event                       | Target                       | GitHub environment           | URL                                                  |
| --------------------------- | ---------------------------- | ---------------------------- | ---------------------------------------------------- |
| Push to `main`              | `preview`, then `production` | `Preview`, then `Production` | https://preview.saasyland.com, https://saasyland.com |
| Manual run of `preview.yml` | `preview`                    | `Preview`                    | https://preview.saasyland.com                        |

`deploy-reusable.yml` gives each GitHub environment its URL, and `src/__test__/workflows.test.ts` fails when one differs from its host in `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). The preview is shared: each deployment replaces the previous one and uses the same preview D1 database, KV namespace and R2 buckets. It runs `main`, so the [journey suite](/docs/tooling/playwright#journey-suite), the Polar sandbox's webhooks and the sign-in on `preview.saasyland.com`, the only preview host Better Auth trusts, all meet the code that production is about to run, and every migration reaches the preview database before production. To try a branch there before it merges, run `gh workflow run preview.yml --ref <branch>`: it deploys the branch, migrations included, only when its commit has passed the checks that `main` requires, and the next push to `main` puts `main` back.

`deploy-reusable.yml` checks for the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets, runs `scripts/verify-bindings.ts`, builds with the dummy values from `.env.test`, removes the generated `dist/server/.dev.vars`, applies `db:migrate:<target>` and runs `vp exec wrangler deploy --config dist/server/wrangler.json`, or, with `upload: true`, runs `vp exec wrangler versions upload` in place of the last two steps. It does not run `scripts/verify-deployment.ts`, the live site check of the `deploy:<target>` scripts, because Cloudflare's bot protection answers 403 to requests from CI runners. Nor does it run `scripts/run-deploy-checks.ts`, so CI runs none of the deploy checks the areas declare in `DEPLOY_CHECKS`: CI has no `.env.<target>`, and the GitHub environments hold only the Cloudflare credentials, besides the [journey suite](#journey-suite)'s sandbox settings in `Preview`. Today these are the auth area's `auth:verify` and the Polar area's `polar:verify`; run `bun run auth:verify:<target>` locally after changing an OAuth client and `bun run polar:verify:<target>` after every change in Polar ([Polar setup](/docs/getting-started/polar-setup)). No secrets file is uploaded: the Worker keeps the runtime secrets already set in Cloudflare. Deployments to the same target queue instead of cancelling each other, and uploads run side by side. A new commit on a pull request cancels the run of `ci.yml` for the commit before it, which nobody will merge, while the runs of the merge queue never cancel one another and those of `deploy.yml` and `e2e-full.yml` on `main` queue (`concurrency` with `queue: max`), so every push to `main` is deployed.

Dependabot updates the GitHub Actions weekly.

## Journey suite [#journey-suite]

`journey.yml` runs `bun run test:journey`, the [journey suite](/docs/tooling/playwright#journey-suite), against `https://preview.saasyland.com` on the schedule <RepositoryFact name="journeySchedule" /> in UTC and when started by hand:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` is `all`, `core`, `complete`, `agency` or `upgrade`; any value but `all` runs only the test with that tag. The job reads these secrets of the GitHub environment `Preview`, without recording a deployment (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` and `RESEND_API_KEY`. It sets `POLAR_SERVER` to `sandbox`, the only value the suite accepts, and the suite builds its Polar client for the sandbox, so the workflow cannot reach production Polar. Runs queue and never cancel one another, because a cancelled run would leave its orders paid. The job writes each test's result and duration, and the error of each failed test, to the run's summary, and uploads the HTML report, `playwright-report/journey.json` and the traces, videos and machine directories of the failed tests as the `journey-report` artifact.

The workflow does not run after each deploy of `main`. Each run signs up an account per test on preview, pays and refunds their orders in the Polar sandbox and sends their verification emails and purchase confirmations through the Resend account that preview shares with production. `main` is deployed many times on a busy day, so a run after each deploy would multiply those emails against the sending limits that production's emails depend on, and it would stop nothing: production deploys right after preview, whatever the journey finds. The nightly run finds a broken purchase within a day. Start it by hand after a change to payments, licences or the CLI licence API, and after `gh workflow run preview.yml --ref <branch>` to test a branch before it merges.

## Releases and tags

The site is deployed continuously, so its versions are dates, not semantic versions. When a production deploy succeeds, the `release` job in `deploy.yml` tags the deployed commit `vYYYY.MM.DD` with the UTC date and publishes a GitHub Release for it. A second production deploy on the same day is tagged `vYYYY.MM.DD.2`, the next one `.3`, and so on. Preview deploys are never tagged. The `release` job is the only job with `contents: write`.

The release notes are the [changelog](/docs/project/changelog) entries that the release shipped, the ones that reached `main` since the previous release tag, each ending with `(#<number>)`, which GitHub links to its pull request, so every change is described in one place; when a release shipped none, its notes link to the changelog. `scripts/publish-release.ts` takes the notes from `src/lib/release.ts` and runs `gh release create` with the tag the deploy chose. A re-run keeps the tag the commit already has and skips a release that already exists.

The production deploy job chooses that tag before it builds: `scripts/choose-release-tag.ts` runs `releaseTag` from `src/lib/release.ts` on the tags of the checkout, the build gets the tag as `RELEASE_TAG`, and the job hands it to the `release` job as its `release-tag` output, so the deploy and its release share one tag. With it, the [changelog](/docs/project/changelog) links each entry to the first release that shipped it: the earliest release tag whose commit contains the entry's squash commit along the first-parent history of `main`, which the build reads together with the dates in one `git log`, or the deploy's own tag for the entries it brings. The `release` job reads the changelog the same way, with the tag it publishes, so a release's notes are exactly the entries the page links to that release. Entries merged before the first release tag link to no release, and so do entries that no deploy has shipped yet in local, preview and pull request builds. Two production deploys cannot choose the same tag: `deploy.yml` runs one workflow run at a time (`concurrency` with `queue: max`), so the `release` job of the previous run has created its tag before the next deploy checks out the repository.

To roll production back to a release, revert everything after its tag in a pull request:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Merging it deploys the tagged code after the usual checks and tags it as a new release. D1 migrations are not reverted, so the older code runs against the newer schema. Every schema change must work with the application deployed before it, which makes this safe for the previous release; read the migrations in between before going further back.
