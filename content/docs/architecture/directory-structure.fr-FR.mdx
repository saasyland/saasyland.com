## Règles de placement

- **Les fichiers et dossiers sont en kebab-case.** Les tests se trouvent dans un dossier `__test__` voisin.
- **Les routes ne font que composer.** Un fichier de route définit le composant de page ou de layout, `NAMESPACE` ou `NAMESPACES`, le loader et `head`. Il ne contient ni widgets, ni boîtes de dialogue, ni définitions de colonnes.
- **Les modules sont des tables de base de données.** Ne créez `src/modules/<name>` que pour une vraie table. Une fonction serveur qui ne travaille pas sur une table va dans `src/lib` (par exemple `src/lib/github.ts`) ou, si une seule route l'utilise, dans le fichier de cette route.
- **Les composants partagés sont à plat.** Un composant utilisé dans plusieurs zones est un fichier unique placé directement dans `presentation/components/custom`.
- **Dossiers de zone et de page.** Les composants utilisés par une seule zone se trouvent dans `admin/`, `app/`, `auth/`, `blog/`, `courses/`, `landing-page/` ou `settings/`, qui contient les cartes de compte que partagent `/app/settings` et `/admin/settings`. Les pages d'administration ont leur propre dossier, comme `admin/users/`. La landing page se divise en `sections/` (un fichier par section de la page) et `components/` (les éléments que les sections partagent).
- **Un widget, une boîte de dialogue, un formulaire ou un ensemble de colonnes par fichier.** Ne scindez pas un composant en un wrapper et un fichier `-content`.
- **Pas de dossiers utilitaires imbriqués.** Les dossiers de composants ne contiennent jamais de sous-dossiers `components/`, `constants/`, `hooks/`, `lib/` ou `types/`, et aucun fichier utilitaire `.ts` ne se trouve à côté d'un composant. Une constante utilisée par un seul composant reste dans le fichier de ce composant.
- **Les données partagées vont dans `src/data`.** Exemples : `MARKETING_SECTION_IDS` et les choix de la CLI. Les zones y déclarent aussi ce qu'elles apportent à la plateforme : handlers du Worker et plugins Vite (voir [Ce que les zones apportent](/docs/architecture/platform-layer#what-the-areas-add)).
- **Chaque chemin va dans `src/routes.ts`.** Tous les environnements d'exécution chargent ce fichier : le navigateur, le Worker, les scripts Bun, Playwright, `vite.config.ts` et le projet Remotion. Il déclare donc les chemins et n'importe rien (voir [Chemins et navigation](/docs/conventions/routes#paths-and-navigation)).
- **Chaque menu va dans `src/data/navigation.ts`.** Les sept menus y figurent sous forme de listes littérales, et le fichier n'importe que `lucide-react`, `~/src/routes` et `~/src/data/navigation.constants`, car le projet Remotion lit le menu d'administration alors que seuls les paquets propres à Remotion sont installés.
- **Les vérifications du site en ligne vont dans `src/lib/deployment.ts`**, sous le nom `LIVE_SITE_CHECKS`, à côté de `verifyDeployment`, qui les interroge.
- **Les déclarations de permissions vont dans `APP_STATEMENTS`, dans `src/integrations/better-auth/auth.access.ts`**, pour qu'une personne relise chacune de leurs modifications, comme elle relit qui peut ouvrir les leçons payantes dans `src/modules/lesson/lesson.access.ts` et quel code atteint chaque événement de webhook Polar dans `src/integrations/polar/polar.webhooks.ts`.
- **Les fichiers générés ne se modifient pas à la main.** Le plugin du routeur écrit `src/routeTree.gen.ts`, `bun run cf-typegen` écrit `src/types/worker-configuration.d.ts`, et `bun run content` et `bun run generate:cn` écrivent `.source/`.
