---
title: "Usurpation d’identité"
description: "Usurpation d’identité par l’administrateur avec Better Auth : les fonctions serveur existent, aucun écran ne les utilise encore."
---

Le plugin `admin` de Better Auth fournit l’usurpation d’identité, et `src/modules/user/use-cases` l’encapsule :

```ts
export const impersonateUser = createServerFn({ method: "POST" })
  .middleware([authorized({ user: ["impersonate"] })])
  .validator((input: zod.input<typeof userZodSchemas.impersonateUser>) => userZodSchemas.impersonateUser.parse(input))
  .handler(({ context, data }) => auth.api.impersonateUser({ body: data, headers: context.requestHeaders }))
```

`stopImpersonatingUser` exige seulement une session connectée. Les deux fichiers exportent des options de mutation (`impersonateUserMutation`, `stopImpersonatingUserMutation`).

## État actuel

- Aucun écran n’appelle ces fonctions : le menu d’actions des lignes d’utilisateurs n’a pas d’entrée d’usurpation et il n’existe pas de bandeau pour y mettre fin.
- Better Auth marque les sessions d’usurpation avec `impersonatedBy` ; `getActiveSessions` les exclut de la liste des sessions des paramètres.
- Les gardes de route vident le cache des requêtes lorsque l’utilisateur de la session change : la navigation suivante après l’usurpation charge donc les données de l’autre utilisateur.
- Il n’existe pas de journal d’audit des usurpations.

Pour l’ajouter, placez une entrée de menu dans `UserRowActions` (`src/presentation/components/custom/admin/users/row-actions.tsx`) et un moyen visible d’arrêter l’usurpation dans les layouts.
