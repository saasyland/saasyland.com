`src/modules/_core` é a única pasta de módulo que não é dona de uma tabela. Ela reúne só a base sobre a qual se constroem os schemas, os schemas Zod e os casos de uso dos módulos, para que nenhum módulo tenha de redefini-la: os códigos de erro, as constantes HTTP e de ambiente, os campos Zod e os textos localizados compartilhados, e as entradas de paginação, ordenação e busca.

## Constantes

| Arquivo                 | Conteúdo                                                                                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `constants/errors.ts`   | `ERROR_CODES`, o tipo `ErrorCode` e a classe `AppError`                                                                                  |
| `constants/api.ts`      | `HTTP_STATUS`, os nomes dos headers `cf-ipcountry` e `cf-connecting-ip`, os headers de segurança e os hosts permitidos por modo de build |
| `constants/ordering.ts` | `MOVE_DIRECTION` (`up`, `down`), `MOVE_DIRECTIONS` e o tipo `MoveDirection`                                                              |

Os dados e os helpers que os módulos usam, mas sobre os quais não se constroem, ficam fora de `_core`: os catálogos de países, moedas, locales e fusos horários em `src/data/countries.ts`, `src/data/currencies.ts`, `src/data/locales.ts` e `src/data/timezones.ts`, a moeda da loja e o formato dos preços em `src/data/pricing.ts`, e os períodos e os intervalos dos gráficos do painel administrativo em `src/lib/time-series.ts`. O catálogo de locales lista todos os locales conhecidos; os locales que a aplicação atende estão em `I18N.SUPPORTED_LOCALES`, no arquivo `src/integrations/use-intl/i18n.config.ts`. Um teste em `src/__test__/module-tables.test.ts` falha quando um arquivo de `_core` não está descrito nesta página, então cada arquivo novo é uma decisão consciente.

## Utilitários

- `utils/localized-text.ts`: `LocalizedText`, um texto por locale guardado como JSON, `localizedTextSchema`, que exige `en-US` e aceita no máximo <RepositoryFact name="localizedTextMaxLength" /> caracteres por texto, e `localize`, que recorre a `en-US`
- `utils/ordering.ts`: `nextPosition`, a maior `position` mais um, e `reorder`, que troca um item de lugar com o vizinho e numera a lista a partir de 1; os casos de uso de curso, capítulo e aula mantêm `position` sem lacunas com elas
- `utils/pagination.ts`: `paginationSchema` (`pageIndex`, `pageSize`) e `DEFAULT_PAGE_SIZE`
- `utils/search.ts`: `searchSchema` e `localizedSearchSchema`, a entrada dos casos de uso de busca do painel administrativo, seus limites de tamanho e o `SearchHit` que retornam
- `utils/zod-fields.ts`: campos Zod reutilizáveis, como `idField`, `localeField` e `slugField`

## Erros

Existe uma única classe de erro e uma única lista de códigos:

```ts
export const ERROR_CODES = {
  AUTH_API_ERROR: "AUTH_API_ERROR",
  CONFLICT: "CONFLICT",
  FORBIDDEN: "FORBIDDEN",
  INTERNAL_ERROR: "INTERNAL_ERROR",
  NOT_FOUND: "NOT_FOUND",
  TOO_MANY_REQUESTS: "TOO_MANY_REQUESTS",
  UNAUTHORIZED: "UNAUTHORIZED",
  VALIDATION: "VALIDATION",
} as const

export type ErrorCode = (typeof ERROR_CODES)[keyof typeof ERROR_CODES]

export class AppError extends Error {
  readonly code: ErrorCode

  constructor(code: ErrorCode, message: string = code) {
    super(message)
    this.name = "AppError"
    this.code = code
  }
}
```

Server functions lançam `AppError`. O middleware `withRequest` normaliza todo o resto: erros da API do Better Auth viram `AUTH_API_ERROR`, com a chave de erro do Better Auth como mensagem; erros do Zod viram `VALIDATION`; e erros desconhecidos são registrados em log e viram `INTERNAL_ERROR`. No navegador, `useErrorMessage()`, de `src/hooks/use-error-message.ts`, mapeia a mensagem para as traduções `auth.errors.*` ou `errors.codes.*`.
