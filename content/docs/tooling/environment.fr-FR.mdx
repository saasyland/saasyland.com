`wrangler.jsonc` définit quatre environnements. `CLOUDFLARE_ENV` en sélectionne un pour le serveur de développement et les builds, et chacun lit ses secrets dans son propre fichier d'environnement :

| Environnement | Sélectionné par                               | Bindings                              | Secrets issus de   |
| ------------- | --------------------------------------------- | ------------------------------------- | ------------------ |
| `development` | `bun run dev`                                 | D1 et KV de préversion distants       | `.env.development` |
| `preview`     | `build:preview`, `deploy:preview`             | D1 et KV de préversion                | `.env.preview`     |
| `production`  | `build:production`, `deploy:production`       | D1 et KV de production                | `.env.production`  |
| `test`        | `build:test`, `start:test`, `db:migrate:test` | D1 et KV locaux dans `.wrangler/test` | `.env.test`        |

`.env.development`, `.env.preview` et `.env.production` sont ignorés par Git ; `.env.example` liste leurs clés. `.env.test` est versionné et ne contient que des valeurs factices. Les scripts de déploiement téléversent le fichier correspondant avec `wrangler deploy --secrets-file`.

## Secrets

Chaque environnement liste ses secrets dans `secrets.required` : les clés Better Auth, OAuth, Resend et Polar, ainsi que `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` et `CLOUDFLARE_ACCESS_TOKEN` pour l'outillage Drizzle (l'environnement `test` omet ces trois-là). Voir [Variables d'environnement](/docs/getting-started/environment-variables) pour chaque clé.

Le code serveur lit les secrets avec `import { env } from "cloudflare:workers"`. Aucune variable `VITE_` n'est utilisée, et aucune ne doit contenir de secret, car Vite les expose au navigateur. `scripts/verify-build.ts` fait échouer le build lorsqu'un asset client importe `cloudflare:workers`. Le domaine canonique provient de `APP_DOMAIN` dans `src/presentation/branding/index.ts`, et non d'une variable d'environnement.

## Bindings

| Binding  | Type             | Utilisation                                                    |
| -------- | ---------------- | -------------------------------------------------------------- |
| `DB`     | D1               | Base de données de l'application, sessions et limites de débit |
| `CACHE`  | KV               | Nombre d'étoiles GitHub                                        |
| `ASSETS` | Assets statiques | Pages prérendues, polices et fichiers publics                  |

Le développement utilise les bindings distants de Cloudflare ; `bun run dev` lit et écrit donc dans la base de données de préversion. Exécutez `bun run cf-typegen` après avoir modifié les bindings pour régénérer `src/types/worker-configuration.d.ts`.

## Tests

Vitest charge `.env.test` via `test.env` et résout `cloudflare:workers` vers `src/platform/testing/mocks/cloudflare.ts`, qui fournit un D1 et un KV en mémoire. Playwright utilise l'environnement `test` et son point d'entrée `src/platform/testing/worker.ts`. Aucun des deux n'a besoin de vrais identifiants.
