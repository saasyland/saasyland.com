O Cloudflare D1 (SQLite) é o banco de dados da aplicação, vinculado como `DB`. `src/integrations/drizzle-orm/` o conecta ao Drizzle:

| Arquivo               | Finalidade                                                                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `drizzle.database.ts` | `db` exclusivo do servidor, criado com `drizzle(env.DB, { schema })`                                                             |
| `drizzle.schemas.ts`  | Reexporta o schema de cada tabela e suas relações                                                                                |
| `drizzle.config.ts`   | drizzle-kit: dialeto SQLite, driver `d1-http`, migrações com prefixo de timestamp em `migrations/`                               |
| `drizzle.errors.ts`   | `rethrowAsConflict`, que transforma um erro de restrição única em `AppError(ERROR_CODES.CONFLICT)` e relança qualquer outro erro |
| `drizzle.columns.ts`  | `timestamps()`, as colunas `createdAt` e `updatedAt` que toda tabela com timestamps inclui no seu esquema                        |

## Tabelas

Cada tabela pertence a um módulo em `src/modules/<table>/` com `<table>.schema.ts` (`drizzle-orm/sqlite-core`), mais `.zod.ts`, `.constants.ts`, `.types.ts` e `use-cases/` quando a tabela tem operações e `.utils.ts` quando precisa de helpers. O [catálogo de módulos](/docs/reference/modules) lista cada módulo com suas tabelas e casos de uso, lidos do código. Código que não é dono de uma tabela não ganha um módulo.

Os schemas seguem as mesmas convenções:

- IDs são strings UUID v7, exceto em `order` e `subscription`, que copiam os registros da Polar sob os IDs da Polar (veja [Módulos](/docs/conventions/modules#tables-that-mirror-a-provider)).
- Datas são colunas `integer` no modo `timestamp_ms`, com padrão `unixepoch() * 1000`. `...timestamps()` adiciona `createdAt` e `updatedAt` dessa forma, e `updatedAt` é renovado a cada atualização.
- Booleanos são colunas `integer` no modo `boolean`.
- Relações, índices, restrições de unicidade e chaves estrangeiras são declarados no schema.

## Escritas atômicas

O D1 não tem transações interativas. Mantenha uma operação atômica com uma única instrução, como um upsert com `onConflictDoUpdate`, ou agrupe instruções com `db.batch`. Os casos de uso de listas paginadas buscam uma página e o seu total em um único batch (`src/modules/category/use-cases/get-categories.ts`):

```ts
const filter = data.kind && eq(category.kind, data.kind)
const [rows, totals] = await db.batch([
  db
    .select()
    .from(category)
    .where(filter)
    .orderBy(desc(category.createdAt), desc(category.id))
    .limit(data.pageSize)
    .offset(data.pageIndex * data.pageSize),
  db.select({ total: count() }).from(category).where(filter),
])
return { rows, total: totals.reduce((sum, row) => sum + row.total, 0) }
```

O rate limiter em `src/lib/rate-limit.ts` lê os contadores que recusam uma requisição, remove uma quantidade limitada de contadores expirados e conta a requisição com um upsert atômico por limite, tudo em um único batch, para que as instâncias do Worker compartilhem os mesmos limites e uma requisição recusada não grave nada. `rateLimitBatch` devolve essas instruções para que quem o chama adicione a própria consulta ao mesmo batch; a API de licenças da CLI adiciona a consulta da licença.

## Migrações

As migrações são arquivos SQL em `src/integrations/drizzle-orm/migrations/`, geradas com `bun run db:generate` e aplicadas com o Wrangler. O Vitest as executa em um banco SQLite em memória. Veja [Banco de dados](/docs/tooling/database) para os comandos.
