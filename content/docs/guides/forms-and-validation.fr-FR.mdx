title: "Formulaires et validation"
description: "Créez des formulaires avec TanStack Form, les champs shadcn et le schéma Zod du module que le serveur applique aussi."
---

Les formulaires suivent le modèle shadcn pour TanStack Form : `useForm` avec le schéma Zod du module, des render props `form.Field`, les composants `Field` de shadcn et une mutation pour l'envoi. La fonction serveur valide à nouveau le même schéma ; la vérification côté client sert donc uniquement au retour visuel.

## Exemple

Version condensée de `src/presentation/components/custom/newsletter-form.tsx` (sans les styles) :

```tsx
const emailSchema = newsletterSubscriberZodSchemas.subscribeToNewsletter.pick({ email: true })

export const NewsletterForm = (): JSX.Element => {
  const t = useTranslations("components.custom.newsletter-form")
  const inputId = useId()
  const errorMessage = useErrorMessage()
  const queryClient = useQueryClient()

  const subscribe = useMutation({
    ...subscribeToNewsletterMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSuccess: ({ status }) => {
      toast.success(t(status))
      return queryClient.invalidateQueries({ queryKey: NEWSLETTER_SUBSCRIBER_QUERY_KEYS.ALL })
    },
  })

  const form = useForm({
    defaultValues: { email: "" },
    listeners: { onBlur: validateOnBlur },
    onSubmit: ({ value, formApi }) => {
      subscribe.mutate(
        { email: value.email, locale: getCurrentLocale() },
        {
          onSuccess: () => {
            formApi.reset()
          },
        },
      )
    },
    validators: { onChange: emailSchema },
  })

  return (
    <form
      noValidate
      onSubmit={(event) => {
        void submitForm(event, form)
      }}
    >
      <form.Field name="email">
        {(field) => {
          const isInvalid = isFieldInvalid(field)

          return (
            <Field data-invalid={isInvalid}>
              <FieldLabel htmlFor={inputId}>{t("label")}</FieldLabel>
              <Input
                aria-describedby={`${inputId}-error`}
                aria-invalid={isInvalid}
                autoComplete="email"
                id={inputId}
                name={field.name}
                onBlur={field.handleBlur}
                onChange={(event) => {
                  field.handleChange(event.target.value)
                }}
                placeholder={t("placeholder")}
                type="email"
                value={field.state.value}
              />
              <Button isPending={subscribe.isPending} type="submit">
                {subscribe.isPending ? t("submitting") : t("button")}
              </Button>
              <div id={`${inputId}-error`}>
                {isInvalid && (
                  <ValidationFieldError
                    message={fieldErrorMessage(field.state.meta.errors)}
                    namespace="auth.validations"
                    params={AUTH_VALIDATION_PARAMS}
                  />
                )}
              </div>
            </Field>
          )
        }}
      </form.Field>
    </form>
  )
}
```

## Schéma

- Utilisez le schéma de `<table>.zod.ts` du module, ou de `src/integrations/better-auth/auth.zod.ts` pour les formulaires d'authentification. `.pick(...)` sélectionne les champs affichés par le formulaire ; les valeurs que l'utilisateur ne saisit pas, comme la langue, sont ajoutées dans `onSubmit`.
- `validators: { onChange: emailSchema }` est le seul validateur. TanStack Form l'exécute à chaque modification, puis de nouveau à l'envoi ; une copie `onSubmit` séparée laisserait une erreur produite à l'envoi, comme `passwordsMustMatch`, en rouge jusqu'à ce que son propre champ change.
- `listeners: { onBlur: validateOnBlur }` exécute le même validateur quand un champ perd le focus : un champ que le visiteur a traversé avec la touche Tab affiche donc son erreur dès qu'il le quitte.
- `noValidate` désactive la validation du navigateur pour que les messages Zod soient les seules erreurs.

## Erreurs

- Un champ affiche son erreur dès que le visiteur l'a quitté ou a tenté d'envoyer le formulaire, jamais pendant qu'il tape encore : `isFieldInvalid(field)` de `src/integrations/tanstack-form/form.fields.ts`, qui vaut `field.state.meta.isBlurred && !field.state.meta.isValid`. Cette valeur définit `data-invalid` sur `Field`, `aria-invalid` sur le champ de saisie et l'affichage de l'erreur : les trois changent donc ensemble.
- Une fois l'erreur affichée, chaque modification revalide le champ, si bien que l'erreur disparaît à la frappe qui corrige la valeur. N'utilisez pas `isTouched` : TanStack Form le définit dès la première frappe.
- Les retours en direct qui récompensent la progression, comme `PasswordRequirements`, lisent directement les valeurs et se mettent à jour dès la première frappe.
- Le champ définit toujours `aria-describedby` sur l'id de son erreur, `<input id>-error`, et `ValidationFieldError` ne rend cet élément avec cet id que tant que le champ est invalide. Les navigateurs ignorent une référence à un élément absent, donc un champ valide n'a pas de description.
- Les messages Zod sont des clés de traduction, comme `emailInvalid`. `fieldErrorMessage` prend le premier, et `ValidationFieldError` affiche `<namespace>.<key>` avec l'entrée correspondante de `params`, par exemple `{ max: 254 }` pour `emailMaxLength`. Une clé inexistante se rabat sur `errors.codes.VALIDATION`.
- Les formulaires transmettent `auth.validations`, que les layouts `auth` et `admin` préchargent et que la zone de la newsletter ajoute au layout `_marketing` pour son formulaire, sauf les formulaires de cours de l'administration, qui transmettent `course.validations` depuis le layout `admin.courses.tsx`. La route doit charger l'espace de noms qu'utilise un formulaire. `messages/` contient aussi un espace de noms `<table>.validations` pour d'autres modules, comme `user.validations`, mais aucun formulaire ni aucune route ne les charge.
- Les erreurs serveur passent par `useErrorMessage()` dans le `onError` de la mutation.

## Envoi

- Le `onSubmit` du formulaire appelle `submitForm(event, form)` de `src/integrations/tanstack-form/form.submit.ts`. Cette fonction empêche l'envoi par le navigateur et appelle `form.handleSubmit()` ; quand le formulaire est invalide, elle marque chaque champ comme quitté, pour que toutes les erreurs s'affichent, et place le focus sur le premier contrôle portant `aria-invalid="true"`.
- Envoyez via les options de mutation du cas d'usage étalées dans `useMutation`. `SignInForm` fait exception : il appelle `signIn.email` du client Better Auth dans son propre `useMutation`, et le plugin de double authentification du client gère `twoFactorRedirect`.
- `<Button isPending={mutation.isPending} type="submit">` désactive le bouton et annonce l'état en attente pendant la requête.
- Le bouton d'envoi reste actif tant que le formulaire est incomplet ; seul `isPending` le désactive. L'activer malgré des erreurs affiche toutes les erreurs et place le focus sur le premier champ invalide.
- Une erreur serveur qui concerne un seul champ, comme `passwordCompromised` pour un mot de passe qui figure dans une fuite de données connue, s'affiche sous ce champ avec `showFieldError(formApi, { controlId, field, message })` de `form.submit.ts` au lieu d'un toast ; elle disparaît quand le champ change.
- Réinitialisez le formulaire ou naviguez dans le `onSuccess` de la mutation, et invalidez les queries du module que la mutation modifie.

Autres exemples : `sign-in-form.tsx`, `sign-up-form.tsx`, `reset-password-form.tsx` et `two-factor-form.tsx` dans `src/presentation/components/custom/auth/`.
