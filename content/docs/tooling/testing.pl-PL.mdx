Vite+ uruchamia Vitest z konfiguracją z `vite.config.ts`. Testy leżą w folderze `__test__` obok kodu, który sprawdzają, i importują API testowe z `vite-plus/test`.

| Projekt       | Pliki                                                            | Środowisko                                                                                |
| ------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `node`        | `*.test.ts` i `*.test.tsx` z wyjątkiem dwóch poniższych rodzajów | Node                                                                                      |
| `integration` | `*.integration.test.ts`                                          | Node, limity czasu: <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `component`   | `*.component.test.tsx`                                           | jsdom                                                                                     |

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
```

Używaj `bun run test`, a nie `bun test`: wbudowany w Buna runner testów pomija projekty, środowiska i plik inicjalizujący Vitest.

## Platforma testowa

`src/platform/testing/` zawiera wspólną infrastrukturę testów; wszystko inne leży obok kodu, do którego należy.

- `setup.ts` rejestruje matchery jest-dom i wspólne hooki.
- `mocks/cloudflare.ts` zastępuje `cloudflare:workers`: D1 to baza `node:sqlite` w pamięci, która stosuje każdą migrację z repozytorium, KV to mapa w pamięci, a każdy bucket R2, `MEDIA` i `BUNDLES`, to magazyn w pamięci, który obsługuje zakresy i listowanie ze stronicowaniem.
- `mocks/cache.ts` eksportuje `createEdgeCache`, który w testach serwowania mediów zastępuje cache Workers zaślepką.
- `lib/server-function.ts` wywołuje funkcje serwerowe przez prawdziwy potok middleware i walidacji TanStack. Tak jest w projektach `node` i `integration`. W projekcie `component` wywołanie funkcji serwerowej jest odrzucane, ponieważ jsdom pełni tam rolę przeglądarki.
- `lib/render.tsx` renderuje komponenty z prawdziwym QueryClientem i routerem.
- `mocks/resend.ts` i `mocks/polar.ts` to ścisłe atrapy API Resend i Polara; każda jest na liście atrap swojego obszaru, którą `mocks/providers.entries.ts` łączy z pustą listą rdzenia w `mocks/core.providers.ts`, a `mocks/providers.ts` kieruje do nich `fetch`. `setup.ts` instaluje je w każdym teście i oznacza jako nieudany test, który wysłał żądanie, jakiego dostawca by nie przyjął; instaluje je też testowy Worker dla Playwrighta (`worker.ts`).
- `lib/polar.ts` buduje modele Polara i podpisuje webhooki dla testów integracyjnych i testów w przeglądarce.

Wywołania zewnętrznych usług e-mail, OAuth i płatności nigdy nie wychodzą poza proces testów.

## Pokrycie

`bun run test:coverage` wymusza <RepositoryFact name="coverageThreshold" unit="percent" /> pokrycia linii, instrukcji, funkcji i gałęzi dla `src/**/*.{ts,tsx}`. Wykluczone są testy, foldery `__test__`, pliki deklaracji, `src/routeTree.gen.ts`, prymitywy shadcn i `src/platform/testing/`. Raporty trafiają do `coverage/` w formie tekstowej, HTML i `coverage-summary.json`. Testuj rzeczywiste zachowanie i usuwaj gałęzie, które nigdy nie mogą się wykonać, zamiast podmieniać obiekty globalne, żeby do nich dotrzeć. CI sprawdza próg pokrycia w każdym pull requeście.

Testy w przeglądarce nie wliczają się do tej liczby. [Pokrycie testami](/docs/tooling/test-coverage) podaje ich pokrycie osobno: jako przepływy użytkownika i administratora, które test w przeglądarce przechodzi od początku do końca.
