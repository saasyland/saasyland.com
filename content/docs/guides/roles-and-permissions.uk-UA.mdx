Контроль доступу використовує плагін admin Better Auth. Кожен розділ оголошує декларації дозволів своїх ресурсів і ролі, яким їх надає, у `src/data/<area>.access.ts`. `src/data/access.entries.ts` об’єднує розділи, а `src/integrations/better-auth/auth.access.ts` будує з них контроль доступу Better Auth, ролі й перевірку дозволів, тож інтеграція автентифікації не називає жодного розділу. Коди ролей розміщені в `src/integrations/better-auth/auth.roles.ts`.

## Дозволи та ролі

```ts title="src/data/core.access.ts"
const STATEMENTS = {
  admin: ["access"],
  settings: ["manage"],
} as const

export const CORE_ACCESS = {
  grants: { [ROLE_CODES.ADMIN]: STATEMENTS },
  statements: STATEMENTS,
} as const satisfies AreaAccess
```

```ts title="src/integrations/better-auth/auth.access.ts"
export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...grantsOf(ROLE_CODES.ADMIN), ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole(grantsOf(ROLE_CODES.CUSTOMER)),
}
```

- `APP_STATEMENTS` у `src/data/access.ts` об’єднує декларації всіх розділів, відсортовані за ресурсом, і падає під час запуску, коли два розділи оголошують той самий ресурс. `grantsOf(role)` об’єднує все, що кожен розділ надає цій ролі.
- Основний розділ оголошує `admin` і `settings`, розділ продуктів — `category` і `product`, розділ курсів — `course` і `video`, а розділ платежів — `order`.
- `defaultStatements` з Better Auth додають ресурси `user` і `session` (наприклад, `user: ["list", "set-role", "ban", "impersonate", "delete"]` і `session: ["list", "revoke"]`).
- Кожен розділ надає всі свої декларації ролі `admin`, яка також отримує адміністративні декларації Better Auth; ролі `customer`, типовій для нових користувачів, не надано жодної.
- `ROLE_VALUES` типізує колонку `user.role` і схеми ролей у `user.zod.ts`.
- `Permission`, тип, який приймають `authorized` і `hasPermission`, будується з декларацій, які оголошують розділи, тож декларація чи дія, якої не оголошує жоден розділ, не компілюється.

## Де перевіряються дозволи

| Шар                       | Перевірка                                                          |
| ------------------------- | ------------------------------------------------------------------ |
| Guard маршруту            | `requireAdmin` вимагає `admin: ["access"]` для всієї зони `/admin` |
| Серверна функція          | `authorized({ product: ["update"] })` у кожній захищеній операції  |
| Лише для тих, хто увійшов | `authorized()` для операцій із власними даними того, хто викликає  |
| Будь-де ще                | `hasPermission({ permission, role })` повертає булеве значення     |

Guard маршруту лише визначає, які сторінки рендеряться. Серверні функції можна викликати напряму через RPC, тож кожна має сама перевіряти свій дозвіл. Приховати кнопку — це питання представлення, а не авторизації.

## Додайте дозвіл

1. Додайте дію до декларацій розділу, якому належить ресурс, наприклад `report: ["read", "export"]` у `src/data/analytics.access.ts`. Новий розділ додає свій файл і один рядок до `src/data/access.entries.ts`.
2. Надайте її в `grants` того самого файлу: розділи надають усі свої `STATEMENTS` ролі `ROLE_CODES.ADMIN`, а ролі, яка має отримати менше, надають лише частину з них.
3. Вимагайте її в серверній функції: `.middleware([authorized({ report: ["export"] })])`.
4. Протестуйте і дозволений випадок, і випадок `FORBIDDEN` — у `src/data/__test__/<area>.access.test.ts` розділу та в тестах сценарію використання.

## Додайте роль

1. Додайте код до `ROLE_CODES` і `ROLE_VALUES` в `auth.roles.ts`.
2. Додайте її до `ROLES` в `auth.access.ts` і надайте їй декларації в `grants` тих розділів, якими вона може користуватися.
3. Додайте мітку ролі до `filters.role.options` у `messages/<locale>/pages.admin.users.json` для кожної мови.

Клієнт автентифікації (`auth.client.ts`) отримує `ac` і `ROLES`, тож адміністративні дії в браузері використовують ті самі визначення.

## Керування користувачами та сесіями

Модулі користувачів і сесій обгортають адміністративний API Better Auth у сценарії використання, кожен із власним дозволом: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` та інші. Операції з власними даними того, хто викликає, наприклад `revokeSession`, використовують `authorized()` і фільтрують за `context.auth.user.id`.

Поза тестовою базою немає жодного заздалегідь створеного адміністратора. Щоб створити першого адміністратора, зареєструйтеся, підтвердьте пошту й встановіть `role` цього користувача на `admin` у D1, наприклад через `bun run db:studio:development`.
