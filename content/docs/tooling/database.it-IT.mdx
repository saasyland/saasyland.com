Gli schemi si trovano nei moduli delle tabelle e vengono raccolti da `src/integrations/drizzle-orm/drizzle.schemas.ts`. Le migrazioni sono file SQL con prefisso di timestamp in `src/integrations/drizzle-orm/migrations/`, versionati insieme alla modifica dello schema.

## Tre database [#three-databases]

Ogni ambiente Wrangler ha il proprio database D1, e nessuno script o server raggiunge i dati di un altro ambiente:

| Ambiente      | Database                                      | Usato da                                         | I suoi dati                               |
| ------------- | --------------------------------------------- | ------------------------------------------------ | ----------------------------------------- |
| `development` | `saasyland_local` locale in `.wrangler/state` | `bun run dev` e gli script `:local`              | Tuoi; `db:seed:local` lo popola           |
| `preview`     | `saasyland_com_preview` remoto                | `preview.saasyland.com` e gli script `:preview`  | Acquisti di prova con la sandbox di Polar |
| `production`  | `saasyland_com_production` remoto             | `saasyland.com` e gli script `:production`       | Clienti                                   |
| `test`        | `saasyland_test` locale in `.wrangler/test`   | Playwright, la preview isolata e `db:reset:test` | `db:seed:test` lo popola                  |

`bun run dev` non legge né scrive mai un database remoto. Ogni binding dell'ambiente `development` in `wrangler.jsonc` ha `remote: false`, il plugin Vite di Cloudflare gira con `remoteBindings: false` (`src/data/cloudflare.vite.ts`), e `src/__test__/wrangler.test.ts` fallisce quando un binding di sviluppo diventa remoto o condivide un database, un namespace o un bucket con `preview` o `production`. Gli altri binding sono locali per lo stesso motivo:

- `CACHE` (KV) contiene solo cache che il Worker riempie di nuovo, il conteggio delle stelle GitHub e gli sconti regionali del checkout, quindi un namespace locale parte vuoto e funziona subito.
- `MEDIA` e `BUNDLES` (R2) sono i bucket locali `saasyland-local` e `saasyland-bundles-local`. Le righe che puntano ai loro file, cioè video, materiali delle lezioni e bundle di template, sono in D1, quindi un database locale con bucket remoti mostrerebbe i file della preview a righe che non esistono e lascerebbe file orfani nei bucket della preview.
- Better Auth tiene utenti, sessioni, token di verifica e rate limit in D1, quindi registrazione, accesso e amministrazione funzionano in locale. Le email partono comunque tramite Resend con la chiave in `.env.development`, e le chiamate a Polar vanno alla sandbox indicata da `POLAR_SERVER`.

## Migrazioni [#migrations]

1. Modifica `src/modules/<table>/<table>.schema.ts`.
2. Esegui `bun run db:generate` e rivedi l'SQL generato.
3. Applicala in locale con `bun run db:migrate:local` ed esegui i test; Vitest applica ogni migrazione al proprio database in memoria.
4. Esegui il deploy: gli script di deploy e la CI la applicano al database di preview o di produzione prima che il nuovo Worker vada online.

```sh
bun run db:generate
bun run db:migrate:local
bun run db:migrate:test
```

L'installazione delle dipendenze e la build non migrano mai un database.

SQLite non impone la lunghezza di un tipo di colonna come `text(<length>)`, e drizzle-kit la cambia ricostruendo la tabella: una tabella nuova, ogni riga copiata dentro, la vecchia eliminata. Per questo i limiti sono quelli che convalidano i moduli e le funzioni server, e una colonna mantiene la lunghezza con cui è stata creata. `user.email` e `newsletter_subscriber.email` restano `text(<RepositoryFact name="declaredEmailColumnLength" />)` e `user.name` `text(<RepositoryFact name="declaredNameColumnLength" />)` tramite `DECLARED_COLUMN_LENGTH` in `auth.constraints.ts`, mentre un indirizzo può avere <RepositoryFact name="emailMaxLength" /> caratteri (`EMAIL_MAX_LENGTH`, il limite di percorso della RFC 5321) e un nome <RepositoryFact name="nameMaxLength" /> (`NAME_MAX_LENGTH`). Una tabella creata in seguito, come `withdrawal`, dichiara `EMAIL_MAX_LENGTH` e `NAME_MAX_LENGTH` fin dall'inizio, quindi non c'è nulla da ricostruire. Una migrazione generata che contiene ``CREATE TABLE `__new_`` ricostruisce una tabella; rivedila prima di fare commit.

## Drizzle Studio

`bun run db:studio:local` esegue `scripts/studio-local.ts`. Miniflare tiene il database locale in un unico file SQLite in `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/`, il cui nome deriva da un hash dell'ID del database in `wrangler.jsonc`; lo script ricava il nome come fa Miniflare, fallisce con un suggerimento quando il file non esiste ancora e apre Drizzle Studio su di esso con `src/integrations/drizzle-orm/drizzle.local.config.ts`, che legge il file tramite `@libsql/client`. Studio e il server di sviluppo possono girare contemporaneamente.

`bun run db:studio:preview` e `bun run db:studio:production` usano l'API HTTP di D1 con `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` e `CLOUDFLARE_ACCESS_TOKEN` di `.env.preview` o `.env.production`, tramite `src/integrations/drizzle-orm/drizzle.config.ts`. Ogni modifica fatta lì è una modifica ai dati reali di quell'ambiente.

## Il seed locale [#the-local-seed]

```sh
bun run db:reset:local
bun run db:seed:local
bun run dev
```

Ferma il server di sviluppo prima di `db:reset:local`. `db:seed:local` (`scripts/seed-local.ts`) avvia i binding locali dell'ambiente `development` con `getPlatformProxy` di Wrangler, scrive quanto segue e può essere rieseguito in qualsiasi momento; modifica solo ciò che differisce:

- Un amministratore, <RepositoryFact name="localAdminEmail" />, con un indirizzo email verificato. La sua password è `LOCAL_ADMIN_PASSWORD` di `.env.development`, oppure <RepositoryFact name="localAdminPassword" /> quando non è impostata, e deve rispettare le regole della registrazione. Ogni esecuzione imposta di nuovo la password. Usa una password che esiste solo sulla tua macchina, mai una di produzione: il seed scrive solo il database locale.
- Il programma dei corsi di `content/courses/saasy-land-courses.json`, importato con `planCourseImport` e `applyCourseImport` di `src/modules/course/course.transfer.ts`, lo stesso codice di **Importa** nell'amministrazione. Le sue lezioni non hanno ancora un video, quindi risultano [in registrazione](/docs/features/courses#being-recorded).
- Le copertine di `content/courses/covers/`, con lo slug come nome, per i corsi che non ne hanno: ogni dimensione va nel bucket `MEDIA` locale e il corso riceve la sua chiave, così il catalogo locale appare come quello di produzione.
- Le licenze, l'ordine senza licenza e il bundle di template della CLI del seed di test (`e2e/data/license.seed.ts`), così il cruscotto di amministrazione e le pagine delle licenze hanno dati con una forma reale. I loro account cliente usano la password <RepositoryFact name="testPassword" />.

Accedi su http://localhost:3000/auth/sign-in con l'amministratore e apri `/admin/courses` per vedere i corsi.

## I dati dei corsi in ogni ambiente [#course-data-in-each-environment]

- Locale: `bun run db:seed:local` importa il programma dei corsi.
- Produzione: un amministratore importa `content/courses/saasy-land-courses.json` nell'amministrazione. Accedi come amministratore, apri **Admin → Corsi**, scegli **Importa**, seleziona il file, esegui **Controlla il file**, leggi il piano, poi **Importa**. Importare di nuovo lo stesso file non cambia nulla. Vedi [Importazione ed esportazione](/docs/features/courses#import-and-export).
- Preview: `bun run courses:sync:preview` copia i corsi pubblicati della produzione, così preview mostra lo stesso catalogo della produzione.

### Copiare i corsi su preview [#copying-the-courses-to-preview]

```sh
bunx wrangler login
bun run courses:sync:preview
```

`scripts/sync-courses.ts` raggiunge D1 come `admin:grant:*`, tramite `wrangler d1 execute --remote` e il modulo condiviso `scripts/d1-execute.ts`. Alla produzione invia solo istruzioni `SELECT`, e scrive su preview in un'unica esecuzione con `--file`. Copia, riga per riga e con i loro id e timestamp:

- ogni corso pubblicato, con i suoi capitoli, le sue lezioni e i loro allegati di tipo link; una riga che preview ha già viene aggiornata tramite il suo id, così una seconda esecuzione non cambia nulla che non sia cambiato in produzione;
- le righe di `video` che usano quelle lezioni, come segnaposto. I file di un video sono nel bucket `MEDIA` della produzione e non vengono copiati, quindi su preview le sue lezioni appaiono [in registrazione](/docs/features/courses#being-recorded) invece di non riuscire a partire. Una riga di `video` che preview ha già mantiene il suo flag di segnaposto.

Nei corsi che copia, elimina i capitoli, le lezioni e gli allegati di tipo link che la produzione non ha più, insieme ai progressi di preview su quelle lezioni, ed elimina un corso di preview che la produzione non pubblica più. Non copia allegati di tipo file, i cui file sono nel bucket della produzione, né nulla al di fuori di queste tabelle: né utenti, né sessioni, né licenze, né ordini, né abbonamenti, né progressi. Una lezione che punti a un altro video nell'editor delle lezioni di preview torna a puntare al video della produzione dopo l'esecuzione successiva.

Lascia `course.cover` fuori dalla copia: i file di una copertina sono nel bucket `MEDIA` di produzione, quindi un corso nuovo su preview non ha copertina, e un corso che preview ha già mantiene la copertina caricata lì.

Si ferma prima di scrivere se un corso di preview ha lo slug di un corso della produzione con un altro id, come uno importato dal file del programma; elimina quel corso nell'amministrazione di preview, poi eseguilo di nuovo. Stampa ciò che ha creato, aggiornato e rimosso in ogni tabella, poi conta le righe su preview e fallisce se sono diverse da quelle della produzione.

## Sconti e paesi di fatturazione degli ordini precedenti [#discounts-and-billing-countries-of-older-orders]

La migrazione `20261122143452_familiar_tusk.sql` ha aggiunto lo sconto e il paese di fatturazione alla copia `order` ([Pagamenti](/docs/features/payments#orders-and-subscriptions-in-d1)). I nuovi webhook li compilano, e un ordine copiato prima della migrazione ha `discount_amount` vuoto finché Polar non lo invia di nuovo. Per compilare tutti questi ordini in una volta:

```sh
bunx wrangler login
bun run orders:backfill:preview
bun run orders:backfill:production
```

`scripts/backfill-order-terms.ts` legge `POLAR_ACCESS_TOKEN` e `POLAR_SERVER` da `.env.<environment>`, elenca gli ordini con `discount_amount` vuoto con `wrangler d1 execute` (in remoto per preview e produzione, in locale per `orders:backfill:local`) e legge ciascuno da Polar con `polar.orders.get`, uno alla volta, aspettando quanto chiede Polar quando risponde 429. Scrive tutti gli ordini in un’unica esecuzione `--file`, ogni `UPDATE` limitato al suo ID e a un `discount_amount` vuoto, quindi non sovrascrive mai una copia che un webhook ha compilato nel frattempo e una seconda esecuzione non cambia nulla. Stampa quanti ordini ha copiato ed esce con un errore finché ne resta qualcuno, come un ordine che Polar non restituisce più. Applica prima la migrazione.

## Il primo amministratore [#the-first-admin]

L'applicazione non ha alcun endpoint, seed o variabile che assegni il ruolo `admin`. Su preview e in produzione, il primo amministratore viene creato con uno script, e questo è l'unico modo:

```sh
bunx wrangler login
bun run admin:grant:production you@example.com
```

1. Registrati sul sito con l'indirizzo e apri il link nell'email di verifica.
2. Accedi a Wrangler con un account Cloudflare che può scrivere nel database D1 dell'ambiente.
3. Esegui `bun run admin:grant:preview <email>` o `bun run admin:grant:production <email>`.

`scripts/grant-admin.ts` legge l'account con `wrangler d1 execute --remote`, lo stampa e rifiuta un indirizzo senza account, un account la cui email non è verificata e un account bloccato. Poi imposta `role` su `admin` in quell'unica riga, legge di nuovo l'account e lo stampa. Un account che è già amministratore resta com'è.

È sicuro per tre motivi:

- Solo chi può scrivere nel database D1 di quell'account Cloudflare può eseguirlo, con il proprio `wrangler login`. Una persona del genere potrebbe comunque modificare qualsiasi riga nella dashboard di Cloudflare; lo script non aggiunge nessuna nuova via d'accesso.
- Modifica una sola colonna di un solo account che ha dimostrato di possedere il proprio indirizzo email.
- L'applicazione applica i ruoli sul server: `requireAdmin` protegge `/admin`, e ogni funzione server di amministrazione verifica il proprio permesso con `authorized(...)` in `auth.middleware.ts`. Vedi [Ruoli e permessi](/docs/guides/roles-and-permissions).

Gli amministratori successivi li nomina un amministratore esistente in **Admin → Gestione degli utenti**: apri l'utente, poi **Cambia ruolo**. `bun run admin:grant:local <email>` fa lo stesso per un account con cui ti sei registrato in locale.
