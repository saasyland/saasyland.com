---
title: "Lint y formato"
description: "oxlint y oxfmt a través de Vite+, y los scripts de comprobación."
---

Vite+ ejecuta oxfmt para el formateo y oxlint para el linting, ambos configurados en las secciones `fmt` y `lint` de `vite.config.ts`. `bun run check` es el control que ejecuta CI:

```sh
bun run check
```

Ejecuta `generate:cn`, `check:comments`, `check:i18n`, `check:flows` y `vp check`, que comprueba el formato, aplica las reglas de lint y comprueba los tipos del proyecto. Usa `bun run lint`, `bun run format` y `bun run format:check` para ejecutar las herramientas de una en una.

## Formato

- Sin punto y coma, comillas dobles, comas finales, sangría de <RepositoryFact name="tabWidth" /> espacios, un ancho de línea de <RepositoryFact name="printWidth" /> y finales de línea LF.
- Las importaciones se ordenan en grupos fijos: solo servidor, `cloudflare:workers`, React, paquetes externos, después las áreas de `~/src` (platform, providers, integrations, modules, routes, hooks, datos y tema, types, lib, branding, componentes de shadcn, componentes personalizados, estilos) y, por último, las importaciones relativas.
- Las clases de Tailwind se ordenan en `className` y dentro de las llamadas a `cn`, `cva`, `clsx` y `tw`.

## Linting

- Las categorías `correctness`, `nursery`, `pedantic`, `perf`, `style` y `suspicious` son errores.
- Las reglas con información de tipos y la comprobación de tipos están activadas (`typeAware` y `typeCheck`).
- Límites destacados: <RepositoryFact name="maxLines" /> líneas por archivo, <RepositoryFact name="maxLinesPerFunction" /> líneas por función, <RepositoryFact name="maxStatements" /> sentencias por función, ningún número mágico aparte de `0` y `1`, ningún `any` explícito (`typescript/no-explicit-any`) e identificadores de al menos dos caracteres, salvo `_`, `m` y `t`.
- Las sobrescrituras relajan algunas reglas para las pruebas, el código de presentación y los hooks, los mocks de prueba y los archivos de ruta.
- `jsPlugins` carga los plugins de oxlint propios del repositorio: `scripts/code-style-lint-plugin.ts`, cuyas reglas `code-style/no-comments`, `code-style/no-multiline-ternary`, `code-style/no-undefined-branch`, `code-style/no-undefined-fallback` y `code-style/zod-namespace-import` hacen fallar cada comentario, cada ternario que ocupa varias líneas, cada ternario con una rama `undefined` o `null`, cada `return undefined` y cada `?? undefined`, así como cada importación de Zod distinta de `import * as zod from "zod"` (consulta [Estilo de código](/docs/conventions/code-style)), `scripts/hydration-lint-plugin.ts`, cuya regla `hydration/no-clock-or-locale-in-render` impide que el código de renderizado lea el reloj o el locale del entorno de ejecución (consulta [Estilo de código](/docs/conventions/code-style)), `scripts/admin-data-lint-plugin.ts`, cuya regla `admin-data/no-literal-data` mantiene los datos de demostración fuera del código de administración (consulta [Panel de administración](/docs/features/admin-dashboard#real-data-only)), y `scripts/radius-lint-plugin.ts`, cuya regla `radius/no-off-scale` mantiene cada esquina en la escala de radios (consulta [Tema](/docs/ui/theme#corner-radius)). `scripts/type-lint-plugin.ts` añade `type/no-off-scale` y `type/mono-for-code`, que mantienen cada tamaño de texto en la escala tipográfica y la fuente monoespaciada en el código (consulta [Tema](/docs/ui/theme#type-scale)).
- Las vías de escape están prohibidas por su nombre: `typescript/ban-ts-comment` rechaza `@ts-expect-error`, `@ts-ignore` y `@ts-nocheck` incluso con una descripción, `typescript/consistent-type-assertions` con `assertionStyle: "never"` rechaza cualquier aserción de tipo salvo `as const`, y `respectEslintDisableDirectives: false` hace que un comentario `eslint-disable` no desactive nada. `code-style/no-comments` sustituye a `capitalized-comments`, `no-inline-comments` y `no-warning-comments`, que las categorías activan y que solo veían algunos comentarios cada una, así que esas tres están desactivadas.

Ambas herramientas ignoran los archivos generados y externos: archivos de declaración, `src/routeTree.gen.ts`, migraciones, `.source`, `dist`, `coverage`, `e2e`, `remotion`, las carpetas de agentes y la salida de Playwright. `scripts/` se formatea y se analiza igual que `src/`. `bun run check:comments` también lee lo que el linter omite: `e2e`, `remotion`, los archivos de declaración y las hojas de estilo.

El formateador también ordena `package.json`, incluidos sus `scripts` alfabéticamente (`sortPackageJson: { sortScripts: true }`), así que `vp check` falla cuando un script está fuera de orden.

Corrige la causa de un error de lint. No añadas comentarios de desactivación, `@ts-expect-error` ni conversiones `as` para satisfacer una regla. Un comentario de desactivación es un comentario, y el linter lo obedece antes de que ninguna regla lo vea, así que `bun run check:comments`, que se ejecuta fuera del linter, lo hace fallar esté donde esté.

## Correcciones

El hook de pre-commit ejecuta `bun run check:pre-commit`; su paso `vp staged` ejecuta `vp check --fix` solo en los archivos preparados para el commit. `bun run check:fix` aplica correcciones en todo el repositorio y puede reescribir archivos que no has modificado, así que revisa tu diff antes de hacer commit. Para corregir solo tus propios cambios, pasa sus rutas a `vp` (la CLI global de Vite+ o `bunx vp`):

```sh
vp fmt src/routes/admin.users.all.tsx
vp lint --fix src/routes/admin.users.all.tsx
```
