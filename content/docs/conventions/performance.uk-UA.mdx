Кожне правило на цій сторінці з’явилося з вимірювання, і кілька з них замінили інтуїтивні виправлення, які робили лише гірше. Змінюйте код, що стоїть за будь-яким із них, лише маючи нове вимірювання, яке його перевершує.

## Вимірюйте, перш ніж стверджувати

- Порівнюйте попередню й нову збірки на тій самій сторінці, щонайменше по п’ять запусків Lighthouse для кожної, чергуючи їх, і порівнюйте медіани. Один запуск нічого не доводить: приблизно кожен п’ятий запуск — викид через шум машини.
- Не оцінюйте зміну за одним запуском PageSpeed Insights. Те саме розгортання отримує дуже різні оцінки залежно від швидкості машини, яка виконує тест, і Lighthouse повідомляє цю швидкість як `benchmarkIndex`.
- Вимірюйте продакшн-збірку (`bun run build:test`, потім `bun run start:test`), віддану через HTTP/2 зі стисненням. Через звичайний локальний HTTP/1.1 без стиснення мережева симуляція Lighthouse моделює з’єднання й розміри передавання, яких у продакшні ніколи не буває.
- Діагностика Lighthouse — це не оцінка. Підказка на кшталт «forced reflow» чи «properly size images» може бути хибною для сторінки, як показують розділи нижче; перш ніж діяти, перевірте метрики, що входять в оцінку.

## Тримайте граф завантаження Worker невеликим

`src/server.ts` виконується для кожного HTML-запиту (`run_worker_first` у `wrangler.jsonc`), і все, що він статично імпортує, обчислюється під час кожного холодного старту. Він і обробники Worker, які додають розділи, імпортують лише константи й чисті допоміжні функції, а решту завантажують, коли вона потрібна запиту:

```ts
const { default: handler } = await import("@tanstack/react-start/server-entry")
```

```ts
const { serveMedia } = await import("~/src/modules/video/video.delivery")
```

Один статичний імпорт назви HTTP-заголовка з модуля, який також імпортував клієнт Polar, колись затягував приблизно 1,4 МБ SDK у кожен холодний старт, і перший байт лендингу надходив аж за 1,4 секунди. Саме тому `COUNTRY_HEADER` і `IP_ADDRESS_HEADER` лежать у `src/modules/_core/constants/api.ts`, який не імпортує нічого важкого. Перш ніж додати статичний імпорт до `server.ts` або до `<area>.worker.ts`, простежте його ланцюжок імпортів: усе, що доходить до `polar`, `drizzle-orm` чи `resend`, — це регресія. `scripts/verify-build.ts` перевіряє це під час кожної збірки: він іде за статичними імпортами точки входу розгорнутого Worker, `dist/server/index.js`, і не проходить, коли вони доходять до коду, зібраного з `@polar-sh`, `drizzle-orm` чи `resend`, або разом перевищують `BOOT_CLOSURE_MAX_BYTES`.

## Тримайте ORM поза браузером [#keep-the-orm-out-of-the-browser]

Drizzle працює лише у Worker. Браузеру потрібні схеми Zod модуля для форм і його кортежі переліків для полів вибору, тож і ті, і ті лежать у файлах, які нічого не імпортують із Drizzle: `<table>.zod.ts` і `<table>.constants.ts` (див. [Модулі](/docs/conventions/modules)). Браузерний імпорт, що доходить до `<table>.schema.ts`, виконує `sqliteTable(...)` — виклик, який бандлер мусить зберегти, — і тягне за собою `drizzle-orm`.

Колись `<table>.zod.ts` ще й будував із таблиць схеми `insert`, `select` і `update` за допомогою `drizzle-zod`, і під час виконання їх ніщо не читало. `drizzle-zod` тримає весь простір імен zod, тому бандлер зберігав і всі локалі zod, і його конвертер у JSON Schema, і його компілятор. Скелетони завантаження `/admin` і `/app` імпортували `PreferencesCardPending` з `preferences-card.tsx`, який імпортував `user.zod.ts`, а компоненти очікування не проходять розділення коду, тож усе це завантажувалося на кожній сторінці. Перенесення кортежів у константи й видалення цих схем зменшило JavaScript кожної сторінки приблизно на 75 КіБ після gzip. Нижче наведено сумарний розмір усіх скриптів, які завантажує кожна сторінка, після gzip, за виводом `bun run build:test`:

| Сторінка       | До        | Після     |
| -------------- | --------- | --------- |
| `/`            | 526,2 КіБ | 450,7 КіБ |
| `/docs/<page>` | 612,1 КіБ | 536,5 КіБ |
| `/blog`        | 487,2 КіБ | 411,7 КіБ |
| `/app`         | 496,6 КіБ | 421,0 КіБ |
| `/admin`       | 515,0 КіБ | 439,4 КіБ |

`src/data/tanstack.vite.ts` забороняє `drizzle-orm` у клієнтському середовищі через захист імпортів TanStack Start:

```ts title="src/data/tanstack.vite.ts"
const SERVER_ONLY_PACKAGES = [/^drizzle-orm(?:\/|$)/u]
```

Збірка, у якій імпорт цього пакета переживає tree-shaking, завершується помилкою й виводить ланцюжок імпортів від маршруту до файлу, що дійшов до Drizzle. Розривайте ланцюжок там, де він починається: імпортуйте кортеж із констант модуля або перенесіть код у серверну функцію. Імпорти лише типів стираються й ніколи не враховуються.

## Попередньо відрендерені сторінки спершу завантажують CSS і шрифти

Публічні сторінки пререндерено, і для першого відображення їм не потрібен JavaScript. TanStack Start генерує підказку `modulepreload` для кожного чанка, який може знадобитися сторінці, — на лендингу їх понад сотню, — і в симульованій мобільній мережі вони конкурують із таблицею стилів і шрифтами. `scripts/optimize-prerendered-html.ts`, який запускає кожен скрипт збірки, прибирає всі підказки для залежностей і залишає лише підказку власного вхідного скрипту сторінки з `fetchpriority="low"`:

```ts
moduleEntries.has(hint) ? `<link rel="modulepreload" href="${hint}" fetchpriority="low"/>` : ""
```

Прибирання підказок скоротило First Contentful Paint приблизно на третину; збереження вхідної підказки з низьким пріоритетом скоротило мобільний First Contentful Paint ще на 375 мс. Ніколи не повертайте підказки попереднього завантаження ні для залежностей, ні для чанків маршрутів. Скрипт зупиняє збірку з помилкою, коли не знаходить жодної підказки, яку треба прибрати, або жодної, яку треба залишити, тож зміну у вихідних даних збірки буде виявлено, і вона не скасує цю оптимізацію непомітно.

`robots.txt` і `llms.txt` — статичні файли в `public/`, які обходять Worker (`"!/robots.txt", "!/llms.txt"` у `run_worker_first`). Lighthouse завантажує обидва з тайм-аутом у дві секунди, і повільна відповідь Worker провалювала його аудити SEO та готовності для агентів.

## Провайдери ніколи не обгортають outlet маршруту

TanStack Router обгортає outlet-и маршрутів межами Suspense, і React гідратує ці межі пізніше, невеликими частинами. Провайдер контексту над ними, значення якого змінюється одразу після гідратації, змушує React гідратувати все під ним за один раз:

- `ThemeProvider` навколо всього застосунку перетворював гідратацію лендингу на одне 200-мілісекундне завдання, яке блокувало введення. Коли його змонтували навколо двох споживачів, `Toaster` і `ThemeSwitch` документації, Total Blocking Time знизився приблизно зі 150 мс до менш ніж 10 мс.
- `MotionProvider` над outlet маршруту публікує новий контекст, коли завершується завантаження його можливостей анімації. На сторінці допису блогу це оновлення надходило, поки сторінка ще завантажувала свій вміст, React переходив до рендерингу на клієнті, і розкладка зсувалася.

Перш ніж додати провайдер до `__root.tsx` чи макета, перевірте, чи може його значення змінитися після гідратації. Якщо може, змонтуйте його поруч із компонентами, що його читають, нижче кожного `<Outlet />` маршруту. Місця розміщення перелічено на сторінці [Компоненти та стилізація](/docs/conventions/components).

## Скелетони лишаються у вхідному скрипті [#skeletons-stay-in-the-entry-script]

TanStack Router за замовчуванням не виносить `pendingComponent` в окремий чанк, і `src/data/tanstack.vite.ts` зберігає це налаштування, тож кожен скелетон міститься у вхідному скрипті й з'являється, щойно навігація перевищує `pendingMs`. Винесення виміряли й відхилили:

- Скелетони макетів `AdminPending`, `AppPending` і `MarketingPending` малюють скелетон сторінки з `PAGE_SKELETONS`, який імпортує скелетони всіх розділів, а маршрутизатор завантажує компоненти очікування зіставлених маршрутів до гідратації сторінки. `/`, `/app` і `/admin` і далі завантажували кожен скелетон, тепер в окремих чанках, і виросли на 3,5–6,5 КіБ після стиснення gzip; легшими стали лише сторінки, макет яких має власний скелетон, як-от `/docs` і `/blog`.
- Винесений скелетон має завантажитися, перш ніж з'явиться. У headless Chromium з додатковою затримкою 400 мс і швидкістю 200 КіБ/с клієнтська навігація з `/` на `/blog` показала блог через 2290 мс замість 1390 мс, за скелетоном, якого збірка без винесення ніколи не потребувала; із затримкою 150 мс вона тривала 800 мс замість 640 мс.

Оскільки кожна сторінка завантажує кожен скелетон, скелетон імпортує `Skeleton`, примітиви shadcn, інші скелетони й константи, що задають його довжини, але ніколи не форму. `PreferencesCardPending` експортувався з `preferences-card.tsx`, тож скелетони `/admin` і `/app` вносили у вхідний скрипт кожної сторінки форму налаштувань, TanStack Form, список часових поясів і схеми користувача; тепер він має власний файл, `preferences-card-pending.tsx`. Усі скрипти, які завантажує кожна сторінка, після стиснення gzip, за виводом `bun run build:test`:

| Сторінка       | До        | Після     |
| -------------- | --------- | --------- |
| `/`            | 463,0 КіБ | 451,9 КіБ |
| `/docs/<page>` | 553,6 КіБ | 527,3 КіБ |
| `/blog`        | 424,7 КіБ | 413,6 КіБ |
| `/app`         | 430,4 КіБ | 404,1 КіБ |
| `/admin`       | 452,9 КіБ | 427,7 КіБ |

`/` і `/blog` заощаджують менше, бо їхні макети рендерять форму розсилки, якій TanStack Form потрібен так чи інакше. `pending-imports.test.ts` іде імпортами кожного `*-pending.tsx` і падає, коли котрийсь доходить до `@tanstack/react-form`. Панелі адмінської панелі керування й розділи огляду для клієнта досі поєднують у списку розділу кожен скелетон з його компонентом, тож ці компоненти завантажуються разом зі скелетонами.

## Одна збірка Tailwind

Tailwind запускає лише `src/presentation/styles/globals.css`. Таблиці стилів маршрутів, як-от `docs.css` і `typeset.css`, — це звичайний CSS, а власні стилі Fumadocs підключаються через `globals.css`:

```css
@import "@fumadocs/base-ui/css/shadcn.css";
@import "@fumadocs/base-ui/css/preset.css";
```

Друга збірка Tailwind у таблиці стилів маршруту колись постачала власні `.hidden`, `.rounded-md` і змінні теми. Однойменні каскадні шари об’єднуються між таблицями стилів, а React ніколи не прибирає таблицю стилів, яку вставив із `precedence`, тож після одного відвідування документації лендинг втрачав адаптивну розкладку й шрифти до перезавантаження. Від цього захищає наскрізний тест «landing keeps its responsive styles after visiting the docs» в `e2e/specs/landing.spec.ts`. Усе, що потребує Tailwind, проходить через `globals.css`.

## Медіа

- **Цикли лендингу.** Кожен `src/presentation/assets/motion/<name>.webm` має постер `<name>.webp` точно з розмірами відео, тож перехід від постера до відео не стає помітно різкішим. Розміри задає `LANDING_VIDEO_SIZES` у `src/data/landing-videos.ts`, який читають і композиції Remotion, і `ConceptLoop`. Менші ширини — це окремі файли `<name>-<width>.webp`, які пропонує `srcSet` постера. `landing-videos.test.ts` завершується помилкою, коли розмір постера відрізняється від його композиції або від ширини в назві файлу. Ніколи не зменшуйте повнорозмірний постер; щоб полегшити його, перекодуйте його з тими самими розмірами. Відео завантажуються з `preload="none"`, відтворюються лише тоді, коли видно чверть відео, і ніколи не відтворюються для читачів, які віддають перевагу зменшеному руху.
- **Тур курсом** у `course-showcase.tsx` — не цикл. Його `<video>` рендериться лише після того, як відвідувач натисне відтворення, тож доти сторінка завантажує тільки постер: `<picture>` з джерелами AVIF і WebP завширшки як відео, 1600 пікселів, і завширшки 800. Саме відео віддається у WebM із запасним MP4.
- **Відео курсів** заздалегідь кодуються в адаптивний HLS і віддаються з R2 через кеш Workers. Див. [Відео](/docs/features/videos).
- **Відео, кероване прокручуванням.** Зараз на сайті такого немає. Відео, час якого слідує за позицією прокручування, має бути закодоване all-intra (кожен кадр — ключовий, `keyint=1`): звичайне кодування виконує перехід до позиції приблизно за 200 мс, all-intra — приблизно за 3 мс, і жодне згладжування в JavaScript не зробить плавним перемотування з переходом за 200 мс.

## Поява під час прокручування

`Reveal` (`src/presentation/components/custom/landing-page/components/reveal.tsx`) плавно показує розділи лендингу, коли вони потрапляють в область перегляду. Він використовує один `IntersectionObserver` для всіх екземплярів, за першим колбеком спостерігача вирішує, чи починається елемент нижче першого екрана, і записує атрибути `data-reveal` безпосередньо, без стану React і без повторного рендерингу. Версія, яка зберігала видимість у стані React, подвоїла Total Blocking Time, бо кожен розділ рендерився повторно, а сторінка двічі перераховувала розкладку. Не повертайте його до стану й не замінюйте без порівняння.

Дві інші оптимізації виміряли й відхилили: `content-visibility: auto` для розділів лендингу, що зламало посилання всередині сторінки на розділи нижче, і ліниве завантаження форми розсилки, що дало таку саму або гіршу оцінку, ніж її безпосередній рендеринг.
