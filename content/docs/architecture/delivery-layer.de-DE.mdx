## Routendateien

Routen sind flache Dateien in `src/routes`. Punkte werden zu Pfadsegmenten:

| Datei                             | URL                | Hinweise                                |
| --------------------------------- | ------------------ | --------------------------------------- |
| `__root.tsx`                      | alle Seiten        | Dokument-Shell und Root-Namespaces      |
| `_site.tsx`                       | keine              | Pfadloses Layout mit dem Website-Header |
| `_site._marketing.tsx`            | keine              | Pfadloses Layout für Marketingseiten    |
| `_site._marketing.terms.tsx`      | `/terms`           | Seite innerhalb des Marketing-Layouts   |
| `admin.tsx`                       | `/admin`           | Layout mit dem Guard `requireAdmin`     |
| `admin.users.all.tsx`             | `/admin/users/all` | Seite innerhalb des Admin-Layouts       |
| `_site._marketing.blog.index.tsx` | `/blog`            | Indexseite des `blog`-Layouts           |
| `_site.docs.$.tsx`                | `/docs/*`          | Splat-Route für Dokumentationsseiten    |
| `api/auth.$.ts`                   | `/api/auth/*`      | HTTP-Handler, keine Komponente          |

Die IDs in `createFileRoute("…")` sind String-Literale, die der Router-Generator pflegt; er schreibt auch `src/routeTree.gen.ts`. Dateien in `__test__`-Ordnern werden ignoriert. Jede URL hat eine Konstante in `ROUTES` (`src/routes.ts`), und Links verwenden `<Link to={ROUTES.X}>`.

## Seitenrouten

Eine Seitenroute definiert eine Komponente `<Name>Page`, eine Konstante `NAMESPACE` direkt über `export const Route` und einen Loader, der die Seitenmetadaten und den Namespace in einem einzigen `Promise.all` lädt:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Zusätzliche Daten kommen in dasselbe `Promise.all`, zum Beispiel `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` in `admin.users.all.tsx`. `pageHead` aus `src/lib/seo.ts` erzeugt aus den `metadata` des Loaders den Titel, die Beschreibung, den Canonical-Link sowie die Tags für `hreflang`, Open Graph und das Vorschaubild; siehe [Suche und Social-Media-Vorschauen](/docs/features/seo).

## Layout-Routen

Eine Layout-Route definiert eine Komponente `<Name>Layout`, ein Array `NAMESPACES` und für geschützte Bereiche einen Guard in `beforeLoad`. Ihre `NAMESPACES` enden mit den Namespaces, die andere Bereiche ihr hinzufügen, und ein Suchparameter wird von den Seiten validiert, die ihn lesen, so wie es die Lizenzseiten `/app` und `/app/license` mit `tier` tun:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "timezones", ...layoutNamespaces("/app")] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Die Guards `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn` und `redirectAfterAuth` stammen aus `src/integrations/better-auth/auth.routes.ts`.

## Lade-Skeletons

Die meisten Navigationen sind abgeschlossen, bevor überhaupt eine Pending-UI erscheint. Links laden ihre Route bei Hover und Touch vorab, öffentliche Seiten sind vorgerendert, und der Router wartet seinen Standardwert für `pendingMs` von einer Sekunde ab, bevor er etwas anzeigt. Ein Skeleton erscheint nur, wenn eine Navigation länger dauert, typischerweise beim ersten Besuch eines Bereichs über eine langsame Verbindung.

Es gibt keine Standardkomponente für Pending. Jede Layout- und Seitenroute legt ihre eigene `pendingComponent` fest, außer den Docs-Seiten: `_site.docs.index.tsx` und `_site.docs.$.tsx` setzen stattdessen `pendingMs: Number.POSITIVE_INFINITY`, zeigen also nie ein eigenes Skeleton, und `DocsPending` gehört zum `docs`-Layout. Jedes Skeleton bildet die Seite nach, die es vertritt:

- **Seiten-Skeletons** wie `SignInPending` und `LegalPending` liegen in der Pending-Datei des Bereichs und kennzeichnen ihr Wurzelelement mit `aria-busy="true"`. Die Dateien sind `custom/auth/auth-pending.tsx`, die Admin-Dateien in `custom/admin/` (`admin-pending.tsx` für das Layout, eine Datei `<area>-pending.tsx` pro Bereich, etwa `products-pending.tsx`, und gemeinsame Bausteine in `pending-blocks.tsx`), die Dateien der Kunden-App in `custom/app/` (`app-pending.tsx` für das Layout, `auth-pending.tsx` und `license-pending.tsx` sowie der gemeinsame Seitenkopf in `pending-blocks.tsx`), die Dateien des öffentlichen Layouts direkt in `custom/` (`marketing-pending.tsx` für das Layout, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` und `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` und `custom/docs-pending.tsx`.
- **Layout-Skeletons** wie `AuthPending` und `MarketingPending` rendern den Rahmen des Layouts und wählen das Seiten-Skeleton für den aktuellen Pfad aus einer Map mit `ROUTES` als Schlüsseln. Das Admin-Layout, die Kunden-App und das öffentliche Layout teilen sich eine Map, `PAGE_SKELETONS` in `src/data/skeletons.ts`, die die Listen zusammenführt, die jeder Bereich in `src/data/<area>.skeletons.ts` deklariert. Wer von woanders in einen Bereich wechselt, sieht deshalb gleich die richtige Seite. Rahmenelemente, die keine Daten benötigen, etwa `Wordmark` und `PageFrame`, werden echt gerendert, und der Website-Header bleibt sichtbar, weil das Layout `_site`, das ihn rendert, keinen Loader hat, auf den es warten müsste.
- **Textplatzhalter** sind `Skeleton`-Balken mit dem Schrift-Token des echten Elements plus `h-lh scale-y-70`, sodass jeder Balken genau eine Zeilenbox füllt. Boxen verwenden die echten Höhen und Radien. Listen beziehen ihre Länge aus denselben Konstanten wie die UI, etwa `OAUTH_PROVIDERS` und `PASSWORD_RULES` in `src/data/auth.ts`.

Wenn du eine Seite hinzufügst, ergänze ihr Skeleton in der Pending-Datei des Bereichs, registriere es in der Map des Layout-Skeletons (bei einer Seite des Admins, der Kunden-App oder des öffentlichen Layouts in `src/data/<area>.skeletons.ts` ihres Bereichs) und setze es als `pendingComponent` der Route.

## Weitere Aspekte von Routen

- **Suchparameter** werden in der Route mit `validateSearch` geparst, zum Beispiel der Parameter `tab` von `/admin/products` oder der Parameter `view` von `/admin/blog`. Das Schema ist ein `zod.object` aus den Hilfsfunktionen in `src/lib/search-params.ts`: `searchText()` und `searchFlag()` liefern `undefined` für einen fehlenden, leeren oder fehlerhaften Wert, und `searchChoice(choices, fallback)` liefert den Fallback. `searchParam(schema)` liefert `undefined`, sofern der Wert nicht zu einem anderen zod-Schema passt, etwa zum Newsletter-Token.
- **Server Functions für eine einzelne Route** dürfen mit `createServerFn` in der Routendatei definiert werden, so wie `getBlogPosts` in `_site._marketing.blog.index.tsx`.
- **HTTP-Endpunkte** liegen in `src/routes/api`. Siehe [HTTP-Handler in TanStack Start](/docs/architecture/api-layer).

## Router

`src/router.tsx` exportiert `getRouter`, das für jeden Request einen neuen `QueryClient` und einen neuen Router erstellt. Dabei wird Folgendes festgelegt:

- Standardkomponenten für Fehler und Not Found aus `presentation/components/custom`, aber keine Standardkomponente für Pending (siehe [Lade-Skeletons](#lade-skeletons))
- Preloading bei Intent und eine Standard-Stale-Time von <RepositoryFact name="routerStaleTimeMinutes" unit="minute" />
- ein `rewrite`, das das Locale-Präfix aus eingehenden URLs entfernt und es in generierten Links wieder hinzufügt
- die SSR-Query-Integration über `setupRouterSsrQueryIntegration`
