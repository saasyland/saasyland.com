title: "Provedores OAuth"
description: "Login com GitHub e Google pelos provedores sociais do Better Auth."
---

`auth.server.ts` registra dois provedores com credenciais do ambiente do Worker, indexados pelos ids de provedor em `AUTH_PROVIDER` (`auth.constants.ts`):

```ts
socialProviders: {
  [AUTH_PROVIDER.GITHUB]: { clientId: env.AUTH_GITHUB_CLIENT_ID, clientSecret: env.AUTH_GITHUB_CLIENT_SECRET },
  [AUTH_PROVIDER.GOOGLE]: { clientId: env.AUTH_GOOGLE_CLIENT_ID, clientSecret: env.AUTH_GOOGLE_CLIENT_SECRET },
},
```

## Fluxo

`OAuthButtons` (`src/presentation/components/custom/auth/oauth-buttons.tsx`) mostra um botão por provedor no login e no cadastro, GitHub primeiro, com os rótulos **Continuar com GitHub** e **Continuar com Google** (`auth.oauth.continueWith`) nas duas páginas. O plugin `lastLoginMethod` do Better Auth guarda a última forma de login usada no navegador, `email`, `github` ou `google`, no cookie `saasyland.last_used_login_method` (`LAST_LOGIN_METHOD_COOKIE`), e o botão correspondente, ou o campo de e-mail na página de login, recebe o selo **Usado por último** depois da hidratação. A página de login também oferece os dois provedores junto a uma senha errada. Ele chama `signIn.social` do Better Auth com um `callbackURL` localizado (`/auth/callback`) e um `errorCallbackURL` (`/auth/sign-in`). Quando o provedor retorna, `/auth/callback` redireciona administradores para `/admin` e clientes para `/app`. Uma tentativa malsucedida volta para a página de login com `?error=`, que mostra a mensagem traduzida de `auth.errors`.

`accountLinking` está ativado, então um login social é vinculado a um usuário existente com o mesmo e-mail. Os tokens do provedor ficam criptografados na tabela `account`.

## Configuração do provedor

Registre as URLs de callback <RepositoryFact name="oauthCallbackPaths" /> para cada host que você usa: `localhost:3000` localmente, `preview.saasyland.com` e `saasyland.com` (veja `DEPLOYED_HOSTS` em `src/modules/_core/constants/api.ts`). Coloque os IDs e segredos de cliente nas variáveis de ambiente acima.

Antes do build, `bun run deploy:<environment>` recusa um client ID que o provedor rejeitaria: `scripts/prepare-deploy-secrets.ts` falha diante de um placeholder como `[UPDATE]` em qualquer secret, e a verificação de deploy da área de autenticação, `auth:verify`, falha a menos que <RepositoryFact name="oauthClientIdVariables" /> em `.env.<environment>` tragam cada um um client ID no formato do seu provedor. Depois de um deploy, `scripts/verify-deployment.ts` inicia o login com cada provedor no domínio do deploy e falha quando a URL de autorização do provedor não está no host dele, traz um `client_id` que não está no formato desse provedor ou um `redirect_uri` que não volta ao mesmo domínio ([Scripts do projeto](/docs/tooling/scripts)). [Solução de problemas](/docs/reference/troubleshooting) explica como corrigir o `Error 401: invalid_client` do Google.

As credenciais do GitHub também autenticam a consulta do número de estrelas do repositório em `src/lib/github.ts`.
