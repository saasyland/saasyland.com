---
title: "Route files"
description: "The one shape of a page route and a layout route: NAMESPACE or NAMESPACES, a single Promise.all loader, a skeleton that mirrors the page, search schemas and links."
---

Every file in `src/routes` has the same shape, so a reader who knows one knows all of them. A route file composes: it declares what the page needs and places components. Widgets, forms, dialogs and table columns live in `src/presentation/components/custom`.

## Page routes

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        onReorder={({ offset, row }) => move.mutateAsync({ courseId: row.id, offset })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        search={t("table.search")}
        selectable
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **The component** is a local `const` named `<Name>Page`, defined first. Small markup used only by this page may sit above it as local components, as `CourseProgress` and `StartLink` do in `_site._marketing.courses.$course.index.tsx`; anything with its own data, mutation or state goes to a component file.
- **One namespace.** `const NAMESPACE = "pages.<area>.<page>"` sits directly above `export const Route` and is used in `loadPageMetadata`, `preloadNamespaces` and `staticData`. Anything else the page needs is declared by its layout.
- **One `Promise.all`.** The loader starts every piece of work at once: page metadata, the namespace and every query the components read. It returns `{ locale, metadata }` for `head`. Never await one of them before starting the next.
- **`head: pageHead(ROUTES.X)`** builds the title, description, canonical URL and alternates from the metadata in the namespace file.
- **Paths come from `ROUTES`** in `src/routes.ts`, which joins the paths of every area (see [Paths and navigation](#paths-and-navigation)); never write a path literal.

A page whose title comes from a record awaits that record and builds its head from the loader data, as `admin.courses.$courseId.tsx` does:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Layout routes

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- A layout declares `const NAMESPACES = [...] as const` above `export const Route` and preloads it. When it has none, it omits the option; there is no `namespaces: []`.
- A layout names every namespace its pages and their components need, those of other features included, as plain strings in its `NAMESPACES`. `/app` lists `pages.license`, `pages.withdrawal` and `withdrawal.validations`, because its overview shows the licence card and offer and its licence page shows the withdrawal card; `/admin/users` lists `pages.admin.customers`, `pages.admin.orders` and `pages.admin.users.license`; and `/_site/_marketing` and `/_site/docs` list `auth.validations`, because their footers show the newsletter form, and the marketing layout also `withdrawal.validations`. Leaving a feature out deletes its message files, and the pruning rule deletes each string that names one of them ([Testing](/docs/conventions/testing#tests-follow-the-areas)).
- The component, when the layout renders one, is named `<Name>Layout` and places an `<Outlet />`.
- A guard goes in `beforeLoad` on the layout that owns the area: `beforeLoad: requireAdmin` in `admin.tsx`, `requireSignedIn` in `app.tsx`, both layouts of the auth area. Guards decide navigation only; every server function still checks its own permission.

## Option order

`sort-keys` is off in `src/routes` because TanStack Router infers types in declaration order. Options are alphabetical, except that `validateSearch` comes first, before anything that reads the search:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Never inline an array or object of data inside `createFileRoute`; declare it as a constant above.

## Search params

`validateSearch` is a `zod.object` built from the helpers in `src/lib/search-params.ts`:

| Helper                            | Value when the param is missing or malformed | Use                              |
| --------------------------------- | -------------------------------------------- | -------------------------------- |
| `searchText()`                    | `undefined`                                  | Tokens, emails, error codes      |
| `searchFlag()`                    | `undefined`                                  | Booleans                         |
| `searchParam(schema)`             | `undefined`                                  | Any other schema, such as a path |
| `searchChoice(choices, fallback)` | `fallback`                                   | A tab or a view                  |

Absent text stays `undefined`, so a default never leaks into a URL the router builds. A `searchChoice` param is paired with `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, which removes the default from the URL. A page another site sends visitors back to also declares `search: { middlewares: [onlyDeclaredSearch(schema)] }` with its own schema, as `/app` and `/app/license` do for Polar's checkout: the router then builds its address with only the declared params, and the server redirects an address that carries any other param to the same address without it, before a guard or the page reads it. Never hand-write `typeof search["x"] === "string"` checks; add a helper when a new kind of field is needed. When a child needs a param that the page has validated as present, the page narrows it and passes it down, as `auth.reset-password.tsx` passes `token` to `ResetPasswordForm`. Pages that read the same params share one schema in `src/data`, which their skeletons parse as well, as `/app/license` and the licence area's part of the overview do with `licenseSearchSchema` (`src/data/license.ts`).

## Skeletons

Navigation must feel instant, so every route that renders a page has a `pendingComponent` that mirrors it: the same layout, the same cards and the same number of rows.

- Skeletons live in the area's pending file (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) and use `Skeleton` from shadcn.
- Skeletons are in every page's entry script, so a skeleton imports `Skeleton`, the shadcn primitives, other skeletons and the constants that give it its lengths, never a form or the file that holds one; `pending-imports.test.ts` fails when one reaches `@tanstack/react-form` (see [Performance](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- A text placeholder takes the real type token plus `h-lh scale-y-70`, so it has the height of the line it replaces: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- List lengths come from the constants the page uses: `DataGridPending` in `data-grid-pending.tsx` draws `DEFAULT_PAGE_SIZE` rows by default, the page size of every admin table.
- A layout skeleton renders the `pendingComponent` of the first route below it that has one for the current path, which `usePagePending(layout)` in `src/hooks/use-page-pending.ts` reads from the route tree: `AdminPending`, `AppPending`, `AuthPending` and `MarketingPending` for their layouts, and `AdminUsersPending` and `AdminCourseSectionPending` one level down. A page's route is therefore the only place that names its skeleton, whichever layout shows it; `/admin/users`, which redirects to `/admin/users/all`, sets the skeleton of that page.
- There is no router-wide `defaultPendingComponent`. `src/router.tsx` sets `defaultPendingMs` to <RepositoryFact name="navigationPendingMs" unit="millisecond" /> and `defaultPendingMinMs` to <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, both from `src/data/navigation.constants.ts`: a navigation that has not finished by then shows the route's skeleton, and the skeleton goes the moment the page is ready, never held on screen any longer. Routes keep these values; see [Performance](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) for the measurements behind them.
- The docs pages draw their skeletons inside the docs layout: `DocsIndexPending` and `DocsPagePending` fill the grid areas of Fumadocs' article and table of contents, so a navigation between docs pages keeps the sidebar on screen. The page component renders the MDX in its own `<Suspense key={path}>`, so the sidebar works before the page's MDX chunk has loaded, and a navigation replaces the previous page's server HTML instead of hydrating it with the next page's data.

## Links

- Router links take a constant: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, or a route pattern with `params` for dynamic paths. shadcn `LinkButton` and `SidebarMenuLink` take `to` the same way, and `AnchorButton` takes an `href` for an address outside the route tree.
- Never add the locale prefix to a router link; the router's rewrite adds it. A full URL in the current locale, for a value that leaves the router as a string, comes from `router.buildLocation({ ... }).publicHref`, as `use-auth-redirect.ts` builds its sign-in links. `localizePathname` is for URLs built outside a router context or for another locale: emails, Better Auth redirect targets, links inside MDX and the language switcher.

## Paths and navigation

Each path and each menu entry is written once, in one list, and a feature that can be left out, such as the courses, the products or the legal pages, joins that list as one element that names its own path. Leaving the feature out deletes its files and its names, and with them every element that names one, so the lists need no file per feature and no barrel. This is how the `saasyland` CLI builds a project from template layers. Only `scripts/areas.ts`, which the application never loads, lists the optional areas with their files and the paths they own, so that `bun run check:areas` can type-check the site without each of them ([Testing](/docs/conventions/testing#tests-follow-the-areas)).

| What                      | Declared in                                                                                                                                                                                                               | Read from                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Paths                     | `src/routes.ts`: one `export const` per path                                                                                                                                                                              | `import * as ROUTES from "~/src/routes"`                                                                         |
| Unlisted paths            | `UNLISTED_ROUTES` in `src/routes.ts`                                                                                                                                                                                      | `isUnlistedRoute` in `src/routes.ts`                                                                             |
| Menu entries              | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` and `FOOTER_NAVIGATION` in `src/data/navigation.ts`, in the order they are shown | The sidebars, the header, the footer, the command palette and the dashboard                                      |
| Layout namespaces         | `NAMESPACES` in the layout route                                                                                                                                                                                          | The layout's loader and `staticData`                                                                             |
| Admin and workspace lists | `DASHBOARD_STATS`, `DASHBOARD_PANELS`, `COMMAND_SEARCHES`, `USER_TABS`, `USER_PROFILE_SECTIONS` and `ACCOUNT_DELETION_NOTICES`, each in the component that renders it                                                     | That component, its skeleton and the route that loads its data                                                   |
| Live site checks          | `LIVE_SITE_CHECKS` in `src/lib/deployment.ts`                                                                                                                                                                             | `verifyDeployment` ([Platform and testing](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)) |

`src/routes.ts` declares every path and imports nothing, because every runtime loads it: the browser, the Worker on each cold start, Bun scripts, Playwright, `vite.config.ts` and the Remotion project. Every file imports it as one namespace, `import * as ROUTES from "~/src/routes"`, so each path keeps its literal type and `<Link to={ROUTES.COURSES}>` is still checked against the route tree. A path built from another, such as `BLOG_FEED` from `BLOG`, follows the one it is built from.

The lists that an area still adds to in a file of its own, the Worker handlers and the Vite plugins, keep their barrels for now. A barrel holds only `export { … } from` lines, one per area file, sorted by module, like `src/integrations/drizzle-orm/drizzle.schemas.ts`.

`src/data/navigation.ts` holds the seven menus as literal lists, each entry with its page in `to`, the full key of its message in `label` and, in the admin console and the workspace, its `lucide-react` icon. The admin menu groups its entries under a sidebar group, `key` from `ADMIN_NAVIGATION_GROUP`, and the footer its links under a column, `key` from `FOOTER_COLUMN`. The file imports only `lucide-react`, `~/src/routes` and `~/src/data/navigation.constants`, because the Remotion project reads the admin menu and its CI job installs only Remotion's own packages; `src/__test__/source-layout.test.ts` fails when it imports anything else. The admin console and the customer workspace exist only with sign-in, so their entries name the auth area's paths and leave with it, as **Sign in** in the header and the footer does:

```ts title="src/data/navigation.ts"
export const HEADER_NAVIGATION: readonly SiteEntry[] = [
  { hash: MARKETING_SECTION_IDS.PRICING, label: "navigation.core.header.pricing", to: ROUTES.HOME },
  { label: "navigation.courses.header.courses", to: ROUTES.COURSES },
  { label: "navigation.content.header.blog", to: ROUTES.BLOG },
  { label: "navigation.content.header.docs", to: ROUTES.DOCS },
  { label: "navigation.auth.header.signIn", signedIn: { label: "navigation.auth.header.account" }, to: ROUTES.SIGN_IN },
]
```

A project without the courses has no `ROUTES.COURSES`, so the pruning rule deletes the **Courses** entry of the header, and a group or column it empties goes with it, as the footer's legal column does in a project without the legal pages.

A header or footer entry may name a `signedIn` label that replaces its own for a signed-in visitor, and its link then leads to the visitor's workspace: `/admin` for an account with admin access, `/app` for everyone else. `Navigation`, `MobileMenu` and `Footer` read both menus from `useSiteNavigation` (`src/hooks/use-site-navigation.ts`), which puts the `signedIn` entries in place once it knows the visitor's workspace and otherwise returns the lists unchanged. It takes the workspace from the one hook in its `WORKSPACE_HOOKS`, `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`), which decides from the role in the session with `hasPermission` and the `admin: ["access"]` permission that `requireAdmin` checks; a project without sign-in has no hook, so its menus stay unchanged. The public pages are prerendered, so their HTML shows **Sign in**; after hydration, a browser that holds Better Auth's last-used sign-in method cookie asks for its session, and the header, its mobile menu and the footer show **Your account** in its place, already linking to the right workspace. A browser that never signed in asks for nothing. Until a part of the page has hydrated, `useVisitorWorkspace` returns nothing, even when the browser already holds the session, because `useHydrated` answers with the server's value while React hydrates: a footer that hydrates after the session has arrived renders the same **Sign in** as the HTML and switches after it, instead of breaking hydration.

Every admin entry opens a screen that works on real data, and the landing page counts them all. A screen whose data has no source yet gets no entry (see [Admin dashboard](/docs/features/admin-dashboard#real-data-only)).

The customer sidebar holds the licence's **Licence** entry, and its resources the content's **Documentation**, above the support address. The core needs only `/` and `/api`, and the header's **Pricing**, the one entry with a `hash`, which links to the pricing section of `/`.

A dashboard statistic in `DASHBOARD_STATS` has a `prefetch`, which the `/admin` loader runs, and a `useValue` hook, which `DashboardStats` calls to read the number.

`APP_STATEMENTS` in `auth.access.ts` declares the permission statements, one per resource, and `scripts/areas.ts` names the statements of a feature that can be left out, such as `APP_STATEMENTS.course`, so that leaving it out deletes them (see [Roles and permissions](/docs/guides/roles-and-permissions)).

The lists in `src/data/navigation.ts` have a declared type from `src/data/navigation.constants.ts`, such as `IconEntry` or `SiteEntry`, so a list whose entries a project leaves out, such as the dashboard actions without the payments area, is an empty list that still type-checks. `navigation.test.ts` checks that the `to` of every entry is a path of the route tree and that no menu names a page or a label twice.

An entry's `label` is the full key of its message, such as `navigation.courses.admin.courses`, and the message lives in the file of the feature that owns the page, `messages/<locale>/navigation.<area>.json`, so leaving the feature out deletes its labels with it. A component renders it with `t(entry.label)` from `useTranslations()`. An admin section labels its sub-pages for the breadcrumbs in its entry's `breadcrumbs`, from the path segment to the key, such as `create` to `navigation.courses.breadcrumbs.create`. A user management tab, a command palette search and a dashboard statistic name the full key of their label too, such as `navigation.team.userTabs.invitations`, `navigation.auth.search.users` and `dashboard.courses.learners`, and a dashboard panel reads its copy under its `key` in `dashboard.<area>.json`. Both kinds of file are root namespaces, so every menu can label every entry. What belongs to a menu itself stays in its namespace: `groups.<group>` in `pages.admin.sidebar`, `columns.<column>` in `components.custom.footer` and the header's call to action, menu button and skip link in `components.custom.navigation`. `navigation.test.ts` fails when an entry, a signed-in variant, a breadcrumb, a user management tab or a command palette search has no message in a locale, and `admin-dashboard.component.test.tsx` when a statistic has none.

Pages that render on the Worker for each request, such as `/admin`, `/auth` or `/courses`, are listed in `UNLISTED_ROUTES` in `src/routes.ts`. The TanStack Start plugin in `vite.config.ts` keeps them out of prerendering with `shouldPrerender` (`src/lib/prerender.ts`), which calls `isUnlistedRoute`, and `buildPageHead` gives them the site card instead of a page card (see [Search and social previews](/docs/features/seo)). Vite does not resolve the `~` alias while it loads its own configuration, so `prerender.ts` imports `src/routes.ts` by relative path.
