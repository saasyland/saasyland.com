description: "Dónde viven los tests, cómo funcionan los proyectos de Vitest y los bindings de prueba, el umbral de cobertura y Playwright."
---

Vite+ ejecuta Vitest (`vp test`) en tres proyectos. Los tests viven en una carpeta `__test__` junto al código que cubren e importan sus API de `vite-plus/test`.

| Proyecto      | Archivos                         | Entorno |
| ------------- | -------------------------------- | ------- |
| `node`        | `__test__/*.test.ts(x)`          | Node    |
| `integration` | `__test__/*.integration.test.ts` | Node    |
| `component`   | `__test__/*.component.test.tsx`  | jsdom   |

Nombra cada test según su archivo fuente: `__test__/category.zod.test.ts` cubre `category.zod.ts`.

## Comandos

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
```

Usa `bun run test`, no `bun test`: solo Vitest carga los proyectos, los entornos y el archivo de configuración.

## Umbral de cobertura

`bun run test:coverage` falla por debajo del **<RepositoryFact name="coverageThreshold" unit="percent" />** de líneas, sentencias, funciones y ramas del código de la aplicación en `src`. Quedan excluidos los tests, `src/platform/testing`, las primitivas de shadcn y los archivos generados. Cubre el comportamiento real y elimina las ramas que nunca se pueden ejecutar en lugar de sustituir globales para alcanzarlas. Los informes se escriben en `coverage/`.

## Entorno de pruebas

- `src/platform/testing/setup.ts` registra los matchers de jest-dom, reinicia los bindings antes de cada test y hace pasar cada `createServerFn` por `withTestRpc`, de modo que las llamadas ejecutan el middleware y el validador reales. Esto se aplica a los proyectos `node` e `integration`. En el proyecto `component` una función de servidor falla, porque jsdom es el navegador.
- `cloudflare:workers` se resuelve a `src/platform/testing/mocks/cloudflare.ts`. D1 es una base de datos SQLite en memoria con todas las migraciones del repositorio aplicadas, KV y el bucket de R2 `MEDIA` son mapas en memoria y `flushWaitUntil()` espera a las tareas en segundo plano. `createEdgeCache()` de `mocks/cache.ts` simula la caché de Workers.
- `.env.test` aporta credenciales ficticias. `fetch` llega a dobles de prueba estrictos de Resend y Polar (`mocks/resend.ts`, `mocks/polar.ts`), y cualquier otro host falla como si la máquina no tuviera conexión, así que nada sale de ella. Una petición que el proveedor rechazaría hace fallar el test.
- `renderWithRouter` de `src/platform/testing/lib/render.tsx` renderiza componentes con un router y un `QueryClient` reales.

## Prueba un caso de uso

Versión resumida de `src/modules/category/use-cases/__test__/create-category.test.ts`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"

import { executeMutation } from "~/src/platform/testing/lib/query"

import { createAuthSessionFixture } from "~/src/integrations/better-auth/__test__/fixtures/auth.session.fixture"
import { ROLE_CODES } from "~/src/integrations/better-auth/auth.access"
import type { auth } from "~/src/integrations/better-auth/auth.server"
import * as authServer from "~/src/integrations/better-auth/auth.server"

import { ERROR_CODES } from "~/src/modules/_core/constants/errors"
import { CATEGORY_KIND } from "~/src/modules/category/category.constants"
import { createCategoryMutation } from "~/src/modules/category/use-cases/create-category"

const getSessionMock = vi.hoisted(() => vi.fn<(typeof auth.api)["getSession"]>())

vi.mock(import("@tanstack/react-start/server-only"), () => ({}))

describe("create-category", () => {
  it("returns a domain error when the caller is not an admin", async () => {
    vi.spyOn(authServer.auth.api, "getSession").mockImplementation(getSessionMock)
    getSessionMock.mockResolvedValue(
      createAuthSessionFixture({ role: ROLE_CODES.CUSTOMER, userId: "01900000-0000-7000-8000-000000000001" }),
    )

    await expect(executeMutation(createCategoryMutation, { kind: CATEGORY_KIND.CATEGORY, name: "SaaS Plans" })).rejects.toThrow(
      ERROR_CODES.FORBIDDEN,
    )
  })
})
```

Prueba cada resultado de un caso de uso: éxito, cada código de `AppError`, sesión ausente y permiso ausente. Los valores de dominio y los códigos de error salen de sus constantes (`CATEGORY_KIND`, `ERROR_CODES`), nunca de cadenas repetidas.

## Prueba contra Resend y Polar

No simules el SDK de Resend ni el de Polar. Llama al código que envía la petición y comprueba lo que recibió el doble. `getSentEmails(recipient)` de `mocks/resend.ts` devuelve los correos entregados con su HTML renderizado y su clave de idempotencia; `mocks/polar.ts` guarda los pagos, los pedidos y las claves de licencia, y sus funciones hacen avanzar una compra: `payPolarCheckout`, `grantPolarLicenseKey`, `refundPolarOrder`, `revokePolarLicenseKey` y `activatePolarLicenseKey`. Versión resumida de `src/modules/license/__test__/license-purchase.integration.test.ts`:

```ts
const buyer = await signUpAndVerify()
const order = await paidOrder(buyer, LICENSE_TIER.COMPLETE)

expect(await deliver(POLAR_WEBHOOK_EVENT.ORDER_PAID, order)).toBe(HTTP_STATUS.OK)
expect(await currentLicense(buyer)).toMatchObject({ status: LICENSE_STATUS.ACTIVE, tier: LICENSE_TIER.COMPLETE })
```

`paidOrder` inicia el pago mediante el `startCheckout` real y lo paga en el doble. `deliver` firma el evento con `signedPolarWebhook` de `lib/polar.ts`, lo envía por POST al endpoint de Polar de Better Auth y devuelve el estado de la respuesta, de modo que se ejecutan la comprobación de la firma, el plugin y los manejadores de `license.webhooks.ts`. Para probar cómo gestiona la aplicación un fallo del proveedor, responde a una sola petición con el error del proveedor, como hace `resend.utils.test.ts`: `vi.spyOn(globalThis, "fetch").mockResolvedValueOnce(Response.json(error, { status }))`.

## Prueba un flujo de autenticación

Las suites de autenticación se ejecutan contra el `auth` real de `auth.server.ts`. `src/integrations/better-auth/__test__/fixtures/auth.harness.ts` crea cuentas como lo hace un visitante: `signUp`, `verifyEmail` (que sigue el token del correo entregado y devuelve la sesión que abre), `signIn` y `signUpAndVerify`. `browserHeaders()` da a cada petición su propio `CF-Connecting-IP`, de modo que los límites de peticiones de Better Auth se aplican como en producción sin que un test agote el cupo de otro. Espera a `flushWaitUntil()` antes de leer un correo que Better Auth envía en segundo plano.

## Prueba un componente

Los tests de componentes renderizan con mensajes reales de `messages/en-US`, simulan el módulo del caso de uso que aporta las opciones de mutation y manejan la interfaz con Testing Library y `userEvent`. Para los estados pendientes, mantén abierta la petición simulada con `Promise.withResolvers()`, comprueba la interfaz pendiente y después resuélvela dentro de `act` y comprueba la interfaz en reposo. Un componente que cambia tras un retardo se prueba con temporizadores falsos (`vi.useFakeTimers()` y después `vi.advanceTimersByTimeAsync` dentro de `act`), nunca esperando tiempo real, y el `QueryClient` de un test de ruta mantiene frescos los datos que obtuvo su loader (`staleTime: Infinity`), de modo que la velocidad a la que renderiza la máquina nunca cambia cuántas veces se ejecuta una consulta. `userEvent.setup({ delay: null })` maneja la interfaz sin un temporizador real entre pulsaciones de teclas. `src/presentation/components/custom/__test__/newsletter-form.component.test.tsx` es un ejemplo completo. Un test de ruta entrega a la ruta sus datos de loader, y un test `node` cubre el loader mediante `getRouter()`: `src/routes/__test__/marketing-routes.component.test.tsx` y `marketing-loaders.test.ts` son las dos mitades.

## Tests de navegador

Las specs de Playwright viven en `e2e/specs`, con page objects en `e2e/pages` y fixtures en `e2e/fixtures`. Se ejecutan contra la aplicación de pruebas compilada con D1, KV y R2 locales en `.wrangler/test` y las cuentas sembradas de `e2e/data/accounts.ts`. En local, Playwright migra, siembra, compila e inicia esa aplicación por sí mismo.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:ui
```

El Worker de pruebas instala los mismos dobles de Resend y Polar y guarda los correos enviados, así que una spec puede leer el enlace de verificación desde `/__test/emails?to=<address>`. `deliverPaidOrder` de `e2e/fixtures/polar.ts` envía un evento `order.paid` completo, firmado como los eventos de las suites de integración.

## Antes de hacer push

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`build:test` ejecuta el build completo de Cloudflare, que los tests unitarios no ejercitan, y `test:e2e:pr` ejecuta todas las specs en Chromium, como hace la CI de las pull requests.

La CI ejecuta las comprobaciones, la cobertura y la suite de navegador en Chromium en cada pull request y en cada push a `main`, y WebKit cada semana y en los push a `main`.
