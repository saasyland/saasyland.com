Кожен файл у `src/routes` має однакову форму, тож читач, який знає один, знає всі. Файл маршруту компонує: він оголошує, що потрібно сторінці, і розміщує компоненти. Віджети, форми, діалоги та стовпці таблиць лежать у `src/presentation/components/custom`.

## Маршрути сторінок

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const columns = useCourseColumns()

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        columns={columns}
        empty={t("table.empty")}
        id={COURSE_GRID_ID}
        label={t("title")}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        rowActionsSize={COURSE_COLUMN_SIZES.actions}
        search={t("table.search")}
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Компонент** — це локальна `const` з назвою `<Name>Page`, визначена першою. Невелика розмітка, яку використовує лише ця сторінка, може стояти над ним як локальні компоненти, як `CourseProgress` і `StartLink` у `_site._marketing.courses.$course.index.tsx`; усе, що має власні дані, мутацію чи стан, переходить у файл компонента.
- **Один простір імен.** `const NAMESPACE = "pages.<area>.<page>"` стоїть безпосередньо над `export const Route` і використовується в `loadPageMetadata`, `preloadNamespaces` і `staticData`. Усе інше, що потрібно сторінці, оголошує її макет.
- **Один `Promise.all`.** Loader запускає всю роботу одночасно: метадані сторінки, простір імен і кожен запит, який читають компоненти. Він повертає `{ locale, metadata }` для `head`. Ніколи не чекайте на одне з них, перш ніж запустити наступне.
- **`head: pageHead(ROUTES.X)`** будує заголовок, опис, канонічну URL-адресу й альтернативні версії з метаданих у файлі простору імен.
- **Шляхи беруться з `ROUTES`** у `src/routes.ts`, який об’єднує шляхи всіх розділів (див. [Шляхи та навігація](#paths-and-navigation)); ніколи не пишіть літерал шляху.

Сторінка, заголовок якої береться із запису, чекає на цей запис і будує свій head з даних loader, як це робить `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Маршрути макетів

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Макет оголошує `const NAMESPACES = [...] as const` над `export const Route` і завантажує їх наперед. Якщо просторів імен немає, опцію пропускають; `namespaces: []` не буває.
- Простір імен, потрібний компоненту іншого розділу в макеті, додає цей розділ у `src/data/<area>.namespaces.ts`, який називає макет за ідентифікатором маршруту, а макет розгортає `...layoutNamespaces("/app")` у свої `NAMESPACES`. Розділ ліцензій додає `pages.license`, `pages.withdrawal` і `withdrawal.validations` до `/app`, огляд якого показує картку ліцензії та пропозицію, а сторінка ліцензії — картку відмови від договору, `withdrawal.validations` — до `/_site/_marketing`, а `pages.admin.users.license` — до `/admin/users`; розділ платежів додає `pages.admin.customers` і `pages.admin.orders` до `/admin/users`; а розділ розсилки додає `auth.validations` до `/_site/_marketing` і `/_site/docs`, футери яких показують форму підписки на розсилку. `namespaces.test.ts` під час компіляції перевіряє, що кожен макет, який називає розділ, є ідентифікатором маршруту.
- Компонент, якщо макет його рендерить, називається `<Name>Layout` і розміщує `<Outlet />`.
- Guard розміщується в `beforeLoad` макета, якому належить розділ: `beforeLoad: requireAdmin` в `admin.tsx`, `requireSignedIn` в `app.tsx`, обидва — макети розділу автентифікації. Guard-и вирішують лише навігацію; кожна серверна функція все одно перевіряє власний дозвіл.

## Порядок опцій

`sort-keys` вимкнено в `src/routes`, бо TanStack Router виводить типи в порядку оголошення. Опції йдуть за алфавітом, але `validateSearch` стоїть першим, перед усім, що читає параметри пошуку:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Ніколи не вбудовуйте масив чи об’єкт даних усередину `createFileRoute`; оголосіть його константою вище.

## Параметри пошуку

`validateSearch` — це `zod.object`, побудований із допоміжних функцій з `src/lib/search-params.ts`:

| Допоміжна функція                 | Значення, коли параметр відсутній або некоректний | Використання                       |
| --------------------------------- | ------------------------------------------------- | ---------------------------------- |
| `searchText()`                    | `undefined`                                       | Токени, адреси пошти, коди помилок |
| `searchFlag()`                    | `undefined`                                       | Булеві значення                    |
| `searchParam(schema)`             | `undefined`                                       | Будь-яка інша схема, як-от шлях    |
| `searchChoice(choices, fallback)` | `fallback`                                        | Вкладка або вигляд                 |

Відсутній текст залишається `undefined`, тож значення за замовчуванням ніколи не потрапляє в URL-адресу, яку будує роутер. Параметр `searchChoice` поєднується з `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, що прибирає значення за замовчуванням з URL-адреси. Сторінка, на яку інший сайт повертає відвідувачів, також оголошує `search: { middlewares: [onlyDeclaredSearch(schema)] }` зі своєю схемою, як це роблять `/app` і `/app/license` для оплати Polar: тоді роутер будує її адресу лише з оголошених параметрів, а сервер переспрямовує адресу з будь-яким іншим параметром на ту саму адресу без нього, ще до того, як його прочитає перевірка чи сторінка. Ніколи не пишіть вручну перевірки `typeof search["x"] === "string"`; додайте допоміжну функцію, коли потрібен новий вид поля. Коли дочірньому компоненту потрібен параметр, наявність якого сторінка вже перевірила, сторінка звужує його тип і передає вниз, як `auth.reset-password.tsx` передає `token` до `ResetPasswordForm`. Сторінки, які читають ті самі параметри, спільно використовують одну схему в `src/data`, яку розбирають і їхні скелетони, як це роблять `/app/license` і частина огляду, яку додає розділ ліцензії, з `licenseSearchSchema` (`src/data/license.ts`).

## Скелетони

Навігація має відчуватися миттєвою, тож кожен маршрут, що рендерить сторінку, має `pendingComponent`, який її віддзеркалює: та сама розкладка, ті самі картки й та сама кількість рядків.

- Скелетони лежать у pending-файлі розділу (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) і використовують `Skeleton` із shadcn.
- Скелетони містяться у вхідному скрипті кожної сторінки, тож скелетон імпортує `Skeleton`, примітиви shadcn, інші скелетони й константи, що задають його довжини, але ніколи не форму чи файл, який її містить; `pending-imports.test.ts` падає, коли котрийсь доходить до `@tanstack/react-form` (див. [Продуктивність](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Текстовий заповнювач отримує справжній типографічний токен плюс `h-lh scale-y-70`, тож має висоту рядка, який замінює: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- Довжини списків беруться з констант, які використовує сторінка: `DataGridPending` у `data-grid-pending.tsx` типово малює `DEFAULT_PAGE_SIZE` рядків — розмір сторінки кожної таблиці адмінки.
- Скелетон макета вибирає скелетон сторінки для поточного шляху з мапи, як це роблять `AdminPending`, `AppPending` і `MarketingPending` з `PAGE_SKELETONS` та `AdminCourseSectionPending` з `COURSE_PAGES` в `admin/courses-pending.tsx`. Кожен розділ додає свої сторінки до `PAGE_SKELETONS` у `src/data/<area>.skeletons.ts` (див. [Шляхи та навігація](#paths-and-navigation)); сторінку макета, що належить одному розділу, як-от секції курсів в адмін-панелі, додають до власної мапи цього макета.
- Немає загального для роутера `defaultPendingComponent`. `src/router.tsx` задає `defaultPendingMs` значення <RepositoryFact name="navigationPendingMs" unit="millisecond" />, а `defaultPendingMinMs` — значення <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, обидва з `src/data/navigation.constants.ts`: перехід, який не завершився за перший із цих інтервалів, показує скелетон маршруту, і той зникає, щойно сторінка готова, не лишаючись на екрані ні миті довше. Маршрути зберігають ці значення; вимірювання, на яких вони ґрунтуються, див. у розділі [Продуктивність](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once).
- Сторінки документації малюють свої скелетони всередині макета документації: `DocsIndexPending` і `DocsPagePending` заповнюють області сітки статті та змісту Fumadocs, тож під час переходу між сторінками документації бічна панель лишається на екрані. Компонент сторінки рендерить MDX у власному `<Suspense key={path}>`, тож бічна панель працює ще до завантаження MDX-чанка сторінки, а навігація замінює серверний HTML попередньої сторінки, а не гідратує його даними наступної.

## Посилання

- Посилання роутера приймають константу: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>` або шаблон маршруту з `params` для динамічних шляхів. `LinkButton` і `SidebarMenuLink` із shadcn приймають `to` так само, а `AnchorButton` приймає `href` для адреси поза деревом маршрутів.
- Ніколи не додавайте префікс локалі до посилання роутера; його додає rewrite роутера. Повна URL-адреса в поточній локалі для значення, яке залишає роутер у вигляді рядка, береться з `router.buildLocation({ ... }).publicHref`, як `use-auth-redirect.ts` будує свої посилання для входу. `localizePathname` призначено для URL-адрес, побудованих поза контекстом роутера або для іншої локалі: листів, цілей перенаправлення Better Auth, посилань усередині MDX і перемикача мови.

## Шляхи та навігація [#paths-and-navigation]

Жоден файл застосунку не перелічує всі розділи. Кожен розділ, як-от курси, продукти чи юридичні сторінки, оголошує власні шляхи, пункти меню та їхні підписи, скелетони сторінок і дозволи, а barrel-файл їх об’єднує, тож розділ додається або вилучається разом із власними файлами. Саме так CLI `saasyland` збирає проєкт із шарів шаблонів. Лише `scripts/areas.ts`, якого застосунок ніколи не завантажує, перелічує необов’язкові розділи з їхніми файлами, щоб `bun run check:areas` міг перевірити типи сайту без кожного з них ([Тестування](/docs/conventions/testing#tests-follow-the-areas)).

| Що                                   | Кожен розділ оголошує                                             | Barrel-файл                      | Звідки читається                                                                                                                                                                          |
| ------------------------------------ | ----------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Шляхи                                | `src/data/<area>.routes.ts`: один `export const` на шлях          | `src/data/routes.entries.ts`     | `ROUTES` у `src/routes.ts`                                                                                                                                                                |
| Пункти меню                          | `src/data/<area>.navigation.ts`: один список `<AREA>_NAVIGATION`  | `src/data/navigation.entries.ts` | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` і `FOOTER_NAVIGATION` у `src/data/navigation.ts` |
| Статистика й панелі панелі керування | `src/data/<area>.dashboard.ts`: один список `<AREA>_DASHBOARD`    | `src/data/dashboard.entries.ts`  | `ADMIN_DASHBOARD_STATS` і `ADMIN_DASHBOARD_PANELS` у `src/data/dashboard.ts`                                                                                                              |
| Скелетони сторінок                   | `src/data/<area>.skeletons.ts`: один список `<AREA>_SKELETONS`    | `src/data/skeletons.entries.ts`  | `PAGE_SKELETONS` у `src/data/skeletons.ts`                                                                                                                                                |
| Дозволи                              | `src/data/<area>.access.ts`: один об’єкт `<AREA>_ACCESS`          | `src/data/access.entries.ts`     | `APP_STATEMENTS` і `grantsOf` у `src/data/access.ts`                                                                                                                                      |
| Неперелічені шляхи                   | `src/data/<area>.routes.ts`: один список `<AREA>_UNLISTED_ROUTES` | `src/data/unlisted.entries.ts`   | `UNLISTED_ROUTES` і `isUnlistedRoute` у `src/data/unlisted.ts`                                                                                                                            |
| Простори імен макетів                | `src/data/<area>.namespaces.ts`: один список `<AREA>_NAMESPACES`  | `src/data/namespaces.entries.ts` | `layoutNamespaces(layout)` у `src/data/namespaces.ts`                                                                                                                                     |

Barrel-файл містить лише рядки `export { … } from`, по одному на файл розділу, відсортовані за модулем, як `src/integrations/drizzle-orm/drizzle.schemas.ts`. Barrel-файл, який заповнюють лише необов'язкові розділи, як-от простори імен макетів, також отримує порожній список від основного розділу (`CORE_NAMESPACES` у `src/data/core.namespaces.ts`), тож проєкт без цих розділів і далі проходить перевірку типів і lint. `src/routes.ts` повторно експортує шляхи як один простір імен, тож кожен шлях зберігає свій літеральний тип, а `<Link to={ROUTES.COURSES}>` і далі перевіряється за деревом маршрутів:

```ts title="src/routes.ts"
export * as ROUTES from "~/src/data/routes.entries"
```

Пункт меню вказує полем `placement` (`NAVIGATION_PLACEMENT` у `src/data/navigation.constants.ts`), де він з’являється: у бічній панелі адмін-панелі, у кнопках над панеллю, у швидких діях палітри команд, у бічній панелі застосунку клієнта та її ресурсах, у публічному заголовку чи у футері. Його `order` ставить його серед пунктів інших розділів, тож жоден список не залежить від порядку файлів. Пункти адмін-панелі також називають свою групу бічної панелі (`group`), а посилання футера — свою колонку (`column`); `ADMIN_NAVIGATION_GROUPS` і `FOOTER_COLUMNS` задають порядок груп і колонок, а ті, які не заповнює жоден розділ, пропускаються. Адмін-панель і робочий простір клієнта існують лише разом із входом, тож ними володіє розділ автентифікації: їхні шляхи `/admin`, `/admin/settings`, `/app` і `/app/settings`, їхні пункти панелі, огляду, налаштувань і керування користувачами, а також **Увійти** в заголовку й футері:

```ts title="src/data/auth.navigation.ts"
  },
  {
    area: AREA,
    key: "signIn",
    order: 50,
    placement: NAVIGATION_PLACEMENT.HEADER,
    signedIn: { key: "account" },
    to: ROUTES.SIGN_IN,
  },
] as const satisfies readonly NavigationEntry[]
```

Пункт заголовка або футера може вказати мітку `signedIn`, яка замінює його власну для відвідувача, що ввійшов, і його посилання тоді веде до робочого простору цього відвідувача: `/admin` для облікового запису з доступом адміністратора, `/app` для всіх інших. `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`) вирішує це за роллю із сесії через `hasPermission` і дозвіл `admin: ["access"]`, який перевіряє `requireAdmin`. Публічні сторінки попередньо відрендерені, тож їхній HTML показує **Увійти**; після гідратації браузер, у якому є cookie Better Auth з останнім способом входу, запитує свою сесію, і заголовок, його мобільне меню та футер показують на цьому місці **Ваш обліковий запис** одразу з посиланням на правильний простір. Браузер, у якому ніколи не входили, нічого не запитує. Доки частина сторінки не гідратована, `useVisitorWorkspace` нічого не повертає, навіть коли браузер уже має сесію, бо під час гідратації React `useHydrated` відповідає значенням сервера: футер, що гідратується після надходження сесії, показує те саме **Увійти**, що й HTML, і перемикається потім, замість того щоб зламати гідратацію.

Кожен пункт адмін-панелі відкриває екран, що працює з реальними даними, і головна сторінка рахує їх усі. Екран, дані якого ще не мають джерела, не отримує пункту (див. [Панель адміністратора](/docs/features/admin-dashboard#real-data-only)).

Розділ ліцензій додає до бічної панелі застосунку клієнта свій пункт **Ліцензія**, а розділ контенту додає до її ресурсів, над адресою підтримки, пункт **Документація**. Основний розділ оголошує лише `/` і `/api`, а також **Ціни** в заголовку — єдиний пункт із `hash`, який веде до розділу з цінами на `/`.

Статистика панелі має `prefetch`, який виконує loader `/admin`, і хук `useValue`, який `DashboardStats` викликає, щоб прочитати число.

Скелетон сторінки пов’язує `to` сторінки з її `pendingComponent`, тим самим скелетоном, який задає маршрут сторінки. Скелетони макетів `AdminPending`, `AppPending` і `MarketingPending` малюють скелетон поточного шляху, коли хтось заходить у їхній макет з іншого місця. Розділ оголошує скелетони всіх своїх сторінок, хоч би який макет їх показував: розділ ліцензії оголошує `/app/license` і `/withdrawal`, а юридичний розділ — свої п’ять публічних сторінок.

Файл доступу розділу оголошує декларації дозволів його ресурсів і ролі, яким він їх надає. `auth.access.ts` будує контроль доступу Better Auth з `APP_STATEMENTS`, а кожну роль — з `grantsOf(role)`, тож інтеграція автентифікації не називає жодного розділу, а `APP_STATEMENTS` падає, коли два розділи оголошують той самий ресурс (див. [Ролі та дозволи](/docs/guides/roles-and-permissions)).

Списки в `src/data/navigation.ts` і `PAGE_SKELETONS` мають оголошені типи, `NavigationEntry` і `PageSkeleton`, а не типи пунктів, які розділи оголошують зараз, тож розміщення, яке не заповнює жоден розділ, як-от дії панелі в проєкті без розділу платежів, є порожнім списком, що все одно проходить перевірку типів. `navigation.test.ts` і `skeletons.test.ts` під час компіляції перевіряють, що `to` кожного пункту й кожного скелетона, які оголошує розділ, є шляхом дерева маршрутів (`FileRouteTypes["to"]` із `src/routeTree.gen.ts`).

Пункт вказує свій розділ у полі `area`, а розділ підписує його у власному файлі повідомлень: `<placement>.<key>` у `messages/<locale>/navigation.<area>.json`, як-от `admin.courses` і `header.courses` у `navigation.courses.json`. Статистику панелі підписано за її `key` у `dashboard.<area>.json`, а секція адмін-панелі підписує свої підсторінки для хлібних крихт під `breadcrumbs.<segment>` у своєму `navigation.<area>.json`, як-от `breadcrumbs.create`; вкладку керування користувачами підписано під `userTabs.<key>`, що називає вкладку та її сторінку в хлібних крихтах, а панель панелі керування тримає свої тексти під своїм `key` у `dashboard.<area>.json`. Обидва види файлів є кореневими просторами імен, тож кожне меню може підписати кожен пункт, а `useNavigationLabel` у `src/hooks/use-navigation-label.ts` повертає підпис пункту. Те, що належить самому меню, лишається в його просторі імен: `groups.<group>` у `pages.admin.sidebar`, `columns.<column>` у `components.custom.footer` і заклик до дії, кнопка меню та посилання для переходу до вмісту із заголовка в `components.custom.navigation`. `enum-labels.test.ts` падає, коли пункту чи статистиці бракує підпису в якійсь локалі.

Розділ, сторінки якого рендеряться у Worker для кожного запиту, як-от `/admin`, `/auth` чи `/courses`, перелічує ці шляхи в `<AREA>_UNLISTED_ROUTES`. Плагін TanStack Start у `src/data/tanstack.vite.ts` виключає їх із пререндерингу за допомогою `isUnlistedRoute`, а `buildPageHead` дає їм картку сайту замість картки сторінки (див. [Пошук і попередній перегляд у соцмережах](/docs/features/seo)). Vite не розпізнає аліас `~`, поки завантажує власну конфігурацію, тому `unlisted.entries.ts` і `unlisted.ts` імпортують файли розділів за відносним шляхом.
