Te strony to standard kodu w tym repozytorium. Opisują, jak piszemy tu kod, a nie jak można by go pisać, a każda reguła wskazuje pliki, które jej przestrzegają. Większości reguł pilnuje polecenie: `bun run check` (formatowanie, lint, typy, tłumaczenia i struktura dokumentacji), `bun run test:coverage` (próg pokrycia <RepositoryFact name="coverageThreshold" unit="percent" />) lub zestaw testów end-to-end. Pozostałych pilnuje przegląd kodu, a każda strona mówi, których.

Gdy nie wiesz, jak coś napisać, znajdź najbliższy istniejący przykład tego samego rodzaju, przeczytaj go i powtórz jego budowę. Spójność jest cenniejsza niż pomysł, który jest lepszy tylko w jednym miejscu: drugi sposób na to samo zmusza każdego kolejnego czytelnika, człowieka czy agenta, do poznania obu.

## Implementacja wzorcowa

Funkcja kursów to wzór do naśladowania. Obejmuje moduł tabeli, trasy publiczne i administracyjne, formularze, okna dialogowe, tabelę danych, szkielety i testy.

| Rodzaj                        | Wzoruj się na                                                          |
| ----------------------------- | ---------------------------------------------------------------------- |
| Moduł tabeli                  | `src/modules/course/`, a obok niego `chapter`, `lesson` i `video`      |
| Odczyt z opcjami zapytania    | `src/modules/course/use-cases/get-course-editor.ts`                    |
| Lista stronicowana dla tabeli | `src/modules/course/use-cases/get-courses.ts`                          |
| Mutacja z opcjami mutacji     | `src/modules/course/use-cases/update-course.ts`                        |
| Trasa layoutu                 | `src/routes/admin.courses.tsx`                                         |
| Trasa strony z tabelą danych  | `src/routes/admin.courses.index.tsx`                                   |
| Trasa strony z parametrem     | `src/routes/admin.courses.$courseId.tsx`                               |
| Formularz                     | `src/presentation/components/custom/admin/courses/course-form.tsx`     |
| Okno dialogowe z formularzem  | `src/presentation/components/custom/admin/courses/chapter-dialog.tsx`  |

## Reguły bez wyjątków

Złamanie którejkolwiek z nich oznacza odrzucenie zmiany, niezależnie od jej pozostałych zalet.

1. Żadnych komentarzy, chyba że komentarz jest naprawdę potrzebny, a wtedy tylko jednowierszowy link do miejsca z uzasadnieniem: strony dokumentacji, README, roadmapy lub zgłoszenia w projekcie zależności. Zobacz [Styl kodu](/docs/conventions/code-style#comments).
2. Żadnych `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, rzutowań `as` ani `any` w celu obejścia reguły. Usuń przyczynę.
3. Żadnych wielowierszowych operatorów trójargumentowych ani `?? undefined`. Poza testami i `src/platform/testing` wartość `null` pojawia się tylko tam, gdzie wymaga go API: w porównaniu z wartością, która może być `null`, i w referencji React do elementu DOM (`useRef<HTMLElement>(null)`). Zobacz [Styl kodu](/docs/conventions/code-style).
4. Statusy, rodzaje, pakiety, role i inne wartości domenowe są nazwanymi stałymi, nigdy powtarzanymi literałami tekstowymi, także w testach. Testy schematów to jedyne miejsce, w którym zapisaną w bazie wartość podaje się wprost. Zobacz [Testy](/docs/conventions/testing).
5. Folder w `src/modules` istnieje tylko dla tabeli bazy danych. Zobacz [Moduły](/docs/conventions/modules).
6. Każdy tekst widoczny dla użytkownika istnieje w każdym języku, podobnie jak każda strona dokumentacji. Liczby pokazywane w serwisie są mierzone albo deklarowane raz w `src/data`, nigdy wpisywane ręcznie. Zobacz [Tłumaczenia i treści](/docs/conventions/translations).
7. Pokrycie linii, instrukcji, funkcji i gałęzi pozostaje na poziomie <RepositoryFact name="coverageThreshold" unit="percent" />. Zobacz [Testy](/docs/conventions/testing).
8. Zmiana aktualizuje w tym samym pull requeście README, dokumentację i teksty serwisu, które stają się przez nią nieaktualne.
9. Commity i pull requesty nie zawierają żadnej wzmianki o udziale AI ani trailera `Co-Authored-By`. Zobacz [Git i pull requesty](/docs/conventions/git-workflow).

## Definicja ukończenia [#definition-of-done]

Zmiana jest ukończona, gdy na gałęzi, którą zamierzasz wypchnąć, przechodzą te polecenia, w tej kolejności, a po nich specyfikacje przeglądarkowe, które obejmują zmieniony kod:

```sh
bun run check
bun run test:coverage
bun run build:test
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`check` i testy nie sprawdzają buildu Cloudflare: aktualizacja zależności przeszła kiedyś jedno i drugie, choć build produkcyjny był zepsuty. Uruchamiaj `build:test` przy każdej zmianie, a jeśli zmiana wykracza poza dokumentację, także specyfikacje stron i przepływów, których dotyka, na własnym porcie, jak opisuje strona [Playwright](/docs/tooling/playwright#running-beside-other-worktrees). CI uruchamia cały zestaw testów przeglądarkowych przy każdym pull requeście i ponownie w kolejce scalania, a pull request trafia do `main` tylko wtedy, gdy ten przebieg jest zielony: umieść go w kolejce, jak opisuje strona [Git i pull requesty](/docs/conventions/git-workflow#merging), i nigdy nie scalaj go ręcznie. Nic innego nie oznacza ukończenia, także podsumowanie, które twierdzi, że zmiana jest gotowa. Przed commitem przejrzyj własny diff i poszukaj w nim komentarzy, literałów tekstowych, które powinny być stałymi, oraz tekstów i dokumentacji, które przez zmianę przestały być prawdziwe.
