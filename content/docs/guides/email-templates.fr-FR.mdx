Un e-mail comporte trois parties : un modèle dans `src/presentation/emails/`, un espace de noms de messages dans `messages/<locale>/emails.<name>.json` et le cas d'usage qui charge les messages, affiche le modèle et l'envoie. La page [Resend](/docs/integrations/resend) liste chaque modèle avec le cas d'usage qui l'envoie.

## Modèle

Un modèle ne contient que du balisage et exporte son espace de noms. Il traduit avec `createTranslator` de `use-intl`, car il s'affiche hors du contexte React. `src/presentation/emails/verify-email.tsx` :

```tsx title="src/presentation/emails/verify-email.tsx"
import type { JSX } from "react"

import { Body, Button, Container, Head, Heading, Html, Preview, Section, Tailwind, Text, pixelBasedPreset } from "react-email"
import { createTranslator } from "use-intl"

import { EMAIL_LINK_LIFETIME_HOURS } from "~/src/integrations/better-auth/auth.constants"
import type { SupportedLocale } from "~/src/integrations/use-intl/i18n.config"

import type emailMessages from "~/messages/en-US/emails.verify-email.json"
import { APP_NAME } from "~/src/presentation/branding"
import { EmailBrandHeader } from "~/src/presentation/emails/email-brand-header"
import { EmailFallbackLink } from "~/src/presentation/emails/email-fallback-link"

export const VERIFY_EMAIL_NAMESPACE = "emails.verify-email"

const TAILWIND_CONFIG = { presets: [pixelBasedPreset] }

interface VerifyEmailProps {
  readonly locale: SupportedLocale
  readonly messages: typeof emailMessages
  readonly name: string
  readonly verifyUrl: string
}

export const VerifyEmail = ({ messages, locale, name, verifyUrl }: Readonly<VerifyEmailProps>): JSX.Element => {
  const t = createTranslator({ locale, messages: { emails: { "verify-email": messages } }, namespace: "emails.verify-email" })

  return (
    <Html lang={locale}>
      <Tailwind config={TAILWIND_CONFIG}>
        <Head />
        <Body className="font-sans">
          <Preview>{t("preview", { appName: APP_NAME })}</Preview>
          <Container className="mx-auto px-5 py-10">
            <EmailBrandHeader />
            <Section>
              <Heading className="m-0 mb-4 text-2xl font-bold">{t("heading")}</Heading>
              <Text className="m-0 mb-6 text-base text-neutral-600">{t("body", { name })}</Text>
              <Button
                href={verifyUrl}
                className="box-border rounded-md bg-neutral-900 px-5 py-3 text-center text-base text-white no-underline"
              >
                {t("button")}
              </Button>
              <Text className="mt-6 mb-0 text-base text-neutral-600">{t("expiry", { hours: EMAIL_LINK_LIFETIME_HOURS })}</Text>
              <EmailFallbackLink label={t("fallback")} url={verifyUrl} />
              <Text className="mt-6 text-sm text-neutral-500">{t("footer")}</Text>
            </Section>
          </Container>
        </Body>
      </Tailwind>
    </Html>
  )
}
```

## Messages

Créez `messages/<locale>/emails.<name>.json` dans toutes les langues. Incluez une clé `subject` ; le cas d'usage la traduit séparément du corps.

```json title="messages/en-US/emails.verify-email.json"
{
  "subject": "Verify your email address",
  "preview": "Verify your email for {appName}",
  "heading": "Verify your email",
  "body": "Hi {name}, thanks for signing up. Confirm your email address to finish setting up your account.",
  "button": "Verify email",
  "expiry": "The link works for {hours, plural, one {# hour} other {# hours}}.",
  "fallback": "If the button does not work, copy this link into your browser:",
  "footer": "If you did not create an account, you can safely ignore this email."
}
```

Les routes ne préchargent jamais les espaces de noms d'e-mails ; le cas d'usage qui envoie le message les charge sur le serveur.

## Envoi

Le cas d'usage tire la langue de l'URL de callback qu'il reçoit, vérifie la limite par destinataire, charge les messages, construit des liens absolus avec `localizePathname` et appelle `sendEmail`. `src/modules/verification/use-cases/send-verify-email.ts` :

```ts title="src/modules/verification/use-cases/send-verify-email.ts"
export const sendVerifyEmail = async ({
  callbackURL,
  token,
  user,
}: {
  callbackURL: string
  token: string
  user: { email: string; name: string }
}): Promise<void> => {
  if (!(await withinRecipientRateLimit({ kind: EMAIL_PURPOSE.VERIFY_EMAIL, recipient: user.email }))) {
    console.warn("[email] verification email not sent: the recipient reached the hourly limit")
    return
  }

  const callback = new URL(callbackURL, getRequest().url)
  const locale = extractLocaleFromPath(callback.pathname) ?? I18N.DEFAULT_LOCALE
  const verifyUrl = new URL(localizePathname({ locale, pathname: ROUTES.VERIFY_EMAIL }), getRequest().url)
  verifyUrl.search = callback.search
  verifyUrl.searchParams.set("token", token)

  const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })

  await sendEmail({
    idempotency: { purpose: EMAIL_PURPOSE.VERIFY_EMAIL, token: crypto.randomUUID() },
    react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
    subject: createTranslator({ locale, messages })("subject"),
    to: user.email,
  })
}
```

`sendEmail` (`src/integrations/resend/resend.utils.ts`) envoie via Resend depuis `RESEND_EMAIL_FROM` sauf si `from` est fourni, transmet la clé d'idempotence pour qu'une nouvelle tentative n'envoie jamais deux fois, et lève une erreur lorsque Resend en renvoie une.

L’e-mail de vérification prend une clé neuve à chaque envoi, `crypto.randomUUID()`, comme les e-mails de compte existant et de mot de passe modifié : Better Auth signe ses jetons de vérification avec des horodatages à la seconde, donc une inscription et une connexion dans la même seconde portent le même jeton, et Resend traiterait le second e-mail comme une nouvelle tentative du premier.

## Qui envoie quoi

- Les hooks Better Auth de `src/integrations/better-auth/auth.server.ts` appellent les cas d'usage via `RESEND_AUTH_EMAILS` (`src/data/resend.auth-emails.ts`) : `sendVerifyEmail` pour `emailVerification.sendVerificationEmail` et les inscriptions répétées de comptes non vérifiés, `sendExistingAccountEmail` pour les inscriptions répétées de comptes vérifiés, `sendResetPasswordEmail` pour `emailAndPassword.sendResetPassword`, `sendPasswordChangedEmail` pour `emailAndPassword.onPasswordReset`, `sendChangeEmailConfirmationEmail` pour `user.changeEmail` et `sendDeleteAccountEmail` pour `user.deleteUser.sendDeleteAccountVerification`.
- Les requêtes Better Auth arrivent sur `/api/auth` sans préfixe de langue : les hooks déterminent donc la langue de l'e-mail à partir du `callbackURL` du parcours, un chemin de page localisé, avec `extractLocaleFromCallbackURL` ou `extractLocaleFromPath` de `src/integrations/use-intl/i18n.paths.ts`. L'anglais sert de langue de repli.
- Les cas d'usage de la newsletter envoient eux-mêmes les e-mails de confirmation et de notification, par exemple `subscribeToNewsletter`.
- Le handler de webhook `onOrderPaid` de la zone des licences appelle `sendPurchaseConfirmationEmail` après avoir accordé la licence. L'e-mail tire sa langue du `metadata.locale` de la commande, ses liens de l'hôte qui a reçu le webhook et son jeton d'idempotence de l'identifiant de la commande Polar, et un envoi en échec fait échouer le handler afin que Polar réessaie.
- Lorsqu'une commande de licence payée ne correspond à aucun compte, `onOrderPaid` n'accorde rien et appelle `sendUnmatchedOrderAlert`, qui prévient le propriétaire du site en anglais.
- `recordWithdrawal`, qu'appelle `submitWithdrawal`, envoie l'accusé de réception d'une déclaration de rétractation dans la langue de la page d'où elle a été envoyée, et la notification de rétractation au propriétaire du site en anglais. Un envoi en échec est journalisé et ne fait pas échouer la déclaration.
- `sendVerifyEmail`, `sendResetPasswordEmail`, `sendExistingAccountEmail` et `subscribeToNewsletter` appellent `withinRecipientRateLimit` (`src/lib/rate-limit.ts`) avant l'envoi : au plus <RepositoryFact name="recipientEmailsPerHour" /> e-mails d'un même type par adresse et par heure, avec pour clé un hachage SHA-256 de l'adresse. Au-delà de la limite, ils journalisent un avertissement et n'envoient rien. Ajoutez la même vérification à tout e-mail qu'un visiteur peut déclencher sans compte.

## Ajouter un e-mail

1. Ajoutez le modèle dans `src/presentation/emails/<name>.tsx` avec son `<NAME>_NAMESPACE` exporté.
2. Ajoutez `messages/<locale>/emails.<name>.json` dans toutes les langues.
3. Nommez son objet dans le `src/data/<area>.email-purposes.ts` de la zone, que `src/data/email-purposes.entries.ts` réunit dans `EMAIL_PURPOSE`, et envoyez-le depuis le cas d'usage propriétaire de l'action, en passant `idempotency: { purpose, token }` avec le jeton ou l'identifiant de l'enregistrement déclencheur.
4. Testez le modèle dans `src/presentation/emails/__test__/` et le cas d'usage avec `sendEmail` simulé.

Identifiants Resend : `RESEND_API_KEY` et `RESEND_EMAIL_FROM`. Les tests ne contactent jamais Resend.
