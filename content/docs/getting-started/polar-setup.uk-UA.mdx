Polar продає три плани, видає для них ліцензійні ключі й застосовує регіональні знижки. Код розраховує на точно визначене налаштування Polar, а Polar не попереджає, коли його налаштування розходиться з кодом: продукт без бенефіту ліцензійного ключа все одно приймає оплату, але не видає ключа. `bun run polar:verify:<environment>` порівнює Polar із кодом, а скрипти розгортання запускають цю перевірку перед кожним ручним розгортанням.

## Продакшн і пісочниця

Polar має два окремі сервіси. Продакшн (`polar.sh`, API `api.polar.sh`) списує кошти з реальних карток; пісочниця, або sandbox (`sandbox.polar.sh`, API `sandbox-api.polar.sh`), приймає лише тестові картки. Спільного в них немає нічого: обліковий запис, організація, токен, продукт, знижка чи вебхук існують лише в одному сервісі, тож зареєструйтеся на `sandbox.polar.sh` окремо й налаштуйте кожен сервіс незалежно від іншого.

| Файл середовища    | `POLAR_SERVER` | Організація Polar |
| ------------------ | -------------- | ----------------- |
| `.env.development` | `sandbox`      | Пісочниця         |
| `.env.preview`     | `sandbox`      | Пісочниця         |
| `.env.production`  | `production`   | Продакшн          |

Розробка й preview можуть спільно використовувати одну організацію в пісочниці, бо в них спільна база даних D1: вебхук цієї організації надсилає події на хост preview, і через нього тестова покупка, зроблена під час розробки, потрапляє до спільної бази даних.

Ніколи не вписуйте продакшн-токен, ID продакшн-організації чи ID продакшн-продукту в `.env.development` або `.env.preview`. API пісочниці відхиляє продакшн-токен, а з `POLAR_SERVER=production` тестова оплата списала б кошти з реальної картки й видала б ліцензію в базі даних preview. `polar:verify` відхиляє `POLAR_SERVER=production` для розробки та preview і `POLAR_SERVER=sandbox` для продакшну.

## Організація й токен

Спершу в пісочниці, потім у продакшні:

1. Створіть організацію й скопіюйте її ID з налаштувань організації в `POLAR_ORGANIZATION_ID`.
2. У налаштуваннях організації створіть токен доступу організації з наведеними нижче областями доступу (scopes) і лише з ними та скопіюйте його в `POLAR_ACCESS_TOKEN`.

| Область доступу           | Кому потрібна                                                                 |
| ------------------------- | ----------------------------------------------------------------------------- |
| `checkouts:write`         | `startCheckout`, який створює сеанс оплати через плагін Polar для Better Auth |
| `customer_sessions:write` | Посилання на портал клієнта, `/api/auth/customer/portal`                      |
| `discounts:read`          | Пошук регіональної знижки під час оплати (`pppDiscountId`) і `polar:verify`   |
| `license_keys:write`      | Читання ключа та його активацій і видалення активації (`deactivateLicense`)   |
| `orders:read`             | Обробники вебхуків, які читають замовлення, з якого походить ліцензія         |
| `products:read`           | `polar:verify`                                                                |
| `webhooks:read`           | `polar:verify`                                                                |

Область доступу на запис охоплює й читання, тож `license_keys:write` дозволяє також читати ключі. Токен організації і так діє від імені своєї організації. Проте `polar:verify`, як і пошук знижки під час оплати, надсилає `POLAR_ORGANIZATION_ID` як параметр запиту `organization_id`, тож з ID іншої організації продукти виглядатимуть відсутніми.

## Продукти

Створіть по одному продукту для кожного плану: одноразову покупку, а не підписку, з фіксованою ціною в `DEFAULT_CURRENCY_CODE` (доларах США), що дорівнює `TIER_PRICES` у `src/data/marketing.ts`. Скопіюйте ID кожного продукту в його ключ.

| План     | Ключ                        | Ціна                          | Активацій на ключ                   |
| -------- | --------------------------- | ----------------------------- | ----------------------------------- |
| Core     | `POLAR_PRODUCT_ID_CORE`     | <TierPrice tier="core" />     | <ActivationLimit tier="core" />     |
| Complete | `POLAR_PRODUCT_ID_COMPLETE` | <TierPrice tier="complete" /> | <ActivationLimit tier="complete" /> |
| Agency   | `POLAR_PRODUCT_ID_AGENCY`   | <TierPrice tier="agency" />   | <ActivationLimit tier="agency" />   |

Polar зберігає ціну в дрібних одиницях валюти, для доларів США це центи, і `polar:verify` так само перераховує `TIER_PRICES`, перш ніж їх порівнювати. Архівовані ціни він ігнорує.

## Ліцензійні ключі

Створіть по одному бенефіту типу **License Keys** (ліцензійні ключі) для кожного плану й прикріпіть його лише до продукту цього плану:

- **Активації**: обмежені числом із таблиці вище, `LICENSE_ACTIVATION_LIMITS` у `src/modules/license/license.constants.ts`. Дозволяти клієнтам керувати своїми активаціями в Polar необов'язково, бо `/app/license` сам показує й видаляє їх.
- **Термін дії**: немає. Ключі ніколи не втрачають чинності, бо покупка — це одноразовий платіж.
- **Ліміт використань**: немає.
- **Префікс**: на ваш вибір; `polar:verify` його не перевіряє.

Кожен продукт повинен мати рівно один бенефіт ліцензійного ключа; інші бенефіти поруч із ним допустимі. Коли Polar надає бенефіт, вебхук `benefit_grant.created` зберігає ключ у ліцензії покупця.

## Регіональні знижки

Під час оплати регіональна ціна застосовується через автоматичну знижку в Polar (див. [Платежі та ліцензії](/docs/features/payments)). Створіть по одній відсотковій знижці для кожного рівня в `PPP_TIERS` (`src/modules/_core/constants/pricing.ts`): <RegionalDiscounts />. Кожна знижка повинна:

- знімати відсоток від ціни; Polar зберігає його в базисних пунктах, тобто в сотих частках відсотка;
- не мати коду, щоб оплата могла застосувати її, не вимагаючи від покупця вводити код;
- діяти на всі три продукти або не бути прив'язаною до жодного конкретного продукту;
- бути доступною для використання вже зараз: без дати початку в майбутньому, без дати завершення в минулому і, якщо вона має ліміт використань, із залишком використань.

`findRegionalDiscount` у `src/integrations/polar/polar.discounts.ts` визначає, яку знижку застосує оплата, і `polar:verify` звертається до цієї самої функції.

## Вебхук

Створіть по одній кінцевій точці вебхука для кожного розгорнутого середовища в організації, яку це середовище використовує.

| Середовище   | Організація | URL                                                     |
| ------------ | ----------- | ------------------------------------------------------- |
| `preview`    | Пісочниця   | `https://preview.saasyland.com/api/auth/polar/webhooks` |
| `production` | Продакшн    | `https://saasyland.com/api/auth/polar/webhooks`         |

Хост береться з `DEPLOYED_HOSTS`, а шлях — з `ROUTES`. Виберіть формат Raw, залиште кінцеву точку ввімкненою й підпишіть її саме на ті події, які обробляє `licenseWebhookHandlers`, перелічені в `LICENSE_WEBHOOK_EVENTS` (`src/modules/license/license.constants.ts`):

- `order.paid` видає ліцензію;
- `order.refunded` відкликає її, щойно за замовлення повернуто всю суму;
- `benefit_grant.created` зберігає ліцензійний ключ;
- `benefit_grant.revoked` відкликає ліцензію.

Скопіюйте секрет підпису кінцевої точки в `POLAR_WEBHOOK_SECRET` у файлі того самого середовища. Для розробки кінцева точка не потрібна, бо Polar не може звернутися до `localhost`.

Ніколи не додавайте кінцеву точку preview до продакшн-організації, а продакшн-кінцеву точку — до пісочниці: справжні платежі потрапляли б у preview, а тестові покупки видавали б ліцензії в продакшні.

## Перевірка налаштування

```sh
bun run polar:verify:development
bun run polar:verify:preview
bun run polar:verify:production
```

Кожен скрипт зчитує ключі Polar з `.env.<environment>` і надсилає лише GET-запити до API, яке вказує `POLAR_SERVER`: він отримує списки продуктів, знижок і кінцевих точок вебхуків організації й нічого не змінює. Він перевіряє, що:

- файл середовища задає кожен ключ Polar, з `POLAR_SERVER=sandbox` для розробки та preview і `POLAR_SERVER=production` для продакшну;
- кожен `POLAR_PRODUCT_ID_*` указує на продукт організації, який не архівовано й не є підпискою, а його ціни фіксовані, у `DEFAULT_CURRENCY_CODE` і дорівнюють `TIER_PRICES`;
- кожен продукт має рівно один бенефіт ліцензійного ключа з лімітом плану з `LICENSE_ACTIVATION_LIMITS`, без терміну дії й без ліміту використань;
- для кожного рівня в `PPP_TIERS` автоматичну відсоткову знижку можна застосувати до продукту кожного плану за тим самим правилом, яке використовує оплата;
- preview і продакшн мають за своєю URL-адресою вебхука ввімкнену кінцеву точку у форматі Raw із секретом підпису `POLAR_WEBHOOK_SECRET`, підписану саме на ті події, що обробляються;
- жодна кінцева точка не надсилає події на хост середовища, яке використовує інший сервіс Polar.

`deploy:preview` і `deploy:production` запускають його одразу після `scripts/verify-bindings.ts`, перед збіркою. Розгортання з CI його не запускають: середовища GitHub не містять токена Polar, а Worker зберігає секрети Polar, уже задані в Cloudflare. Після кожної зміни в Polar запускайте `polar:verify` самостійно.

## Коли перевірка не проходить

Скрипт завершується помилкою, яка перелічує всі знайдені проблеми, по одній на рядок:

```text
Polar production does not match the code for production:
The core product (POLAR_PRODUCT_ID_CORE) has 0 licence-key benefits; it needs exactly one.
A webhook endpoint posts to https://preview.saasyland.com/api/auth/polar/webhooks, the preview host, from this Polar production organisation; remove it.
```

Невдала перевірка зупиняє розгортання до того, як щось буде зібрано, мігровано чи завантажено. Скрипт ніколи не змінює Polar: виправте Polar, а потім запустіть його знову. Кожне повідомлення називає ключ, константу чи налаштування, яке треба виправити:

- **`Set … in .env.<environment>`**: ключ Polar відсутній чи порожній або `POLAR_SERVER` вказує не на той сервіс.
- **`rejects POLAR_ACCESS_TOKEN`**: токен недійсний, відкликаний або належить іншому сервісу, як-от продакшн-токен у `.env.preview`.
- **`lacks the … scope`**: створіть токен з наведеними вище областями доступу.
- **`names no product of the organisation`**: ID продукту чи `POLAR_ORGANIZATION_ID` хибний або належить іншому сервісу.
- **Ціна, ліцензійний ключ або знижка**: змініть їх у Polar відповідно до коду. Коли бізнес-значення змінюється навмисно, спершу змініть `TIER_PRICES`, `LICENSE_ACTIVATION_LIMITS` або `PPP_TIERS`, а потім Polar.
- **Кінцева точка вебхука**: виправте кінцеву точку, яку називає повідомлення, або видаліть кінцеву точку, що надсилає події на хост іншого середовища.
