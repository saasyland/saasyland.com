Форми дотримуються шаблону shadcn для TanStack Form: `useForm` зі схемою Zod модуля, render props `form.Field`, компоненти `Field` із shadcn і мутація для надсилання. Серверна функція ще раз валідує ту саму схему, тож перевірка на клієнті потрібна лише для зворотного зв'язку.

## Приклад

Скорочена версія `src/presentation/components/custom/newsletter-form.tsx` (без стилів):

```tsx
const emailSchema = newsletterSubscriberZodSchemas.subscribeToNewsletter.pick({ email: true })

export const NewsletterForm = (): JSX.Element => {
  const t = useTranslations("components.custom.newsletter-form")
  const inputId = useId()
  const errorMessage = useErrorMessage()
  const queryClient = useQueryClient()

  const subscribe = useMutation({
    ...subscribeToNewsletterMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSuccess: ({ status }) => {
      toast.success(t(status))
      return queryClient.invalidateQueries({ queryKey: NEWSLETTER_SUBSCRIBER_QUERY_KEYS.ALL })
    },
  })

  const form = useForm({
    defaultValues: { email: "" },
    onSubmit: ({ value, formApi }) => {
      subscribe.mutate(
        { email: value.email, locale: getCurrentLocale() },
        {
          onSuccess: () => {
            formApi.reset()
          },
        },
      )
    },
    validators: { onChange: emailSchema, onSubmit: emailSchema },
  })

  return (
    <form
      noValidate
      onSubmit={(event) => {
        event.preventDefault()
        void form.handleSubmit()
      }}
    >
      <form.Field name="email">
        {(field) => {
          const isInvalid = field.state.meta.isTouched && !field.state.meta.isValid

          return (
            <Field data-invalid={isInvalid}>
              <FieldLabel htmlFor={inputId}>{t("label")}</FieldLabel>
              <Input
                aria-describedby={`${inputId}-error`}
                aria-invalid={isInvalid}
                autoComplete="email"
                id={inputId}
                name={field.name}
                onBlur={field.handleBlur}
                onChange={(event) => {
                  field.handleChange(event.target.value)
                }}
                placeholder={t("placeholder")}
                type="email"
                value={field.state.value}
              />
              <Button isPending={subscribe.isPending} type="submit">
                {subscribe.isPending ? t("submitting") : t("button")}
              </Button>
              <div id={`${inputId}-error`}>
                {isInvalid && (
                  <ValidationFieldError
                    message={fieldErrorMessage(field.state.meta.errors)}
                    namespace="auth.validations"
                    params={AUTH_VALIDATION_PARAMS}
                  />
                )}
              </div>
            </Field>
          )
        }}
      </form.Field>
    </form>
  )
}
```

## Схема

- Використовуйте схему з `<table>.zod.ts` модуля, а для форм автентифікації — з `src/integrations/better-auth/auth.zod.ts`. `.pick(...)` вибирає поля, які показує форма; значення, яких користувач не вводить, наприклад мова, додаються в `onSubmit`.
- `onChange` валідує під час введення, а `onSubmit` валідує всі поля під час надсилання форми.
- `noValidate` вимикає валідацію браузера, тож єдиними помилками лишаються повідомлення Zod.

## Помилки

- Поле показує помилки лише після того, як його торкнулися: `field.state.meta.isTouched && !field.state.meta.isValid`. Це значення встановлює `data-invalid` на `Field` і `aria-invalid` на полі введення.
- Поле завжди вказує в `aria-describedby` id своєї помилки, `<input id>-error`, а `ValidationFieldError` рендерить елемент із цим id лише поки поле некоректне. Браузери ігнорують посилання на відсутній елемент, тож коректне поле не має опису.
- Повідомлення Zod — це ключі перекладу, наприклад `emailInvalid`. `fieldErrorMessage` бере перше з них, а `ValidationFieldError` рендерить `<namespace>.<key>` з відповідним записом із `params`, наприклад `{ max: 64 }` для `emailMaxLength`. Для неіснуючого ключа використовується `errors.codes.VALIDATION`.
- Форми передають `auth.validations`, який заздалегідь завантажують layout `_landing`, `blog`, `auth` і `admin`, крім форм курсів в адмінпанелі, які передають `course.validations` з layout `admin.courses.tsx`. Маршрут має завантажити простір імен, який використовує форма. У `messages/` також є простір імен `<table>.validations` для інших модулів, наприклад `user.validations`, але жодна форма чи маршрут їх не завантажує.
- Помилки сервера проходять через `useErrorMessage()` в `onError` мутації.

## Надсилання

- Надсилайте форму через параметри мутації сценарію використання, розгорнуті в `useMutation`. Виняток — `SignInForm`: вона викликає `signIn.email` клієнта Better Auth у власному `useMutation`, а двофакторний плагін клієнта обробляє `twoFactorRedirect`.
- `<Button isPending={mutation.isPending} type="submit">` блокує кнопку й повідомляє про стан очікування, поки триває запит.
- Скидайте форму або переходьте на іншу сторінку в `onSuccess` мутації та інвалідуйте запити модуля, які змінює мутація.

Більше прикладів: `sign-in-form.tsx`, `sign-up-form.tsx`, `reset-password-form.tsx` і `two-factor-form.tsx` у `src/presentation/components/custom/auth/`.
