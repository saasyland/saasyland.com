Історія `main` — частина продукту: кожен pull request, злитий через squash, — це один рядок, який каже, що змінилося для людей, які користуються кодом.

## Коміти

Повідомлення комітів відповідають Conventional Commits і пишуться без емодзі; хук `prepare-commit-msg` додає емодзі відповідного типу (таблицю наведено на сторінці [Conventional commits](/docs/tooling/conventional-commits)):

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- Тема пишеться з малої літери, в наказовому способі, і каже, що зміна робить для своїх користувачів: `feat(course): reorder the catalogue from the course list`, а не `update course files`.
- Область (scope) — це модуль або розділ: `course`, `auth`, `a11y`, `deps`, `readme`.
- Тип — один із `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 і `revert` 🗑️; хук відхиляє будь-який інший. Ніколи не вводьте емодзі самостійно: хук не перевіряє тему, яка вже починається з емодзі.
- Розбивайте pull request на логічні коміти: функціональність, її документацію як `docs(<scope>)` і виправлення, знайдені дорогою.
- Ніколи не робіть коміт із `--no-verify`. Хук `pre-commit` запускає `bun run check:pre-commit`; коли він не проходить, виправляйте причину.
- Форматуйте й лінтьте лише змінені вами файли через `bunx vp fmt <files>` і `bunx vp lint --fix <files>`. Не запускайте `bun run check:fix` чи `vp check --fix` для всього репозиторію: вони переписують файли, яких ви не торкалися, зокрема спільні налаштування редактора в `.vscode/settings.json`. Якщо `.vscode/` з’являється в `git status`, відновіть його з `HEAD`.

## Жодної атрибуції ШІ

Коміти й описи pull request не містять трейлера `Co-Authored-By` для інструмента ШІ, рядка «Generated with» чи будь-якої іншої атрибуції ШІ, навіть якщо інструмент додає її за замовчуванням. GitHub зіставляє адресу з такого трейлера зі стороннім обліковим записом, який потім з’являється серед учасників репозиторію. Те саме стосується виправлень, які ви надсилаєте в upstream (див. [Залежності](/docs/conventions/dependencies)).

## Гілки та робочі дерева

- Створюйте гілку від `main`, одну гілку на pull request.
- Давайте кожній гілці власне робоче дерево Git (worktree) замість перемикання гілки в наявному checkout, щоб checkout, відкритий у редакторі чи іншому процесі, ніколи не змінювався без його відома:

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Перш ніж довіряти результатам тестів, перевірте `git branch --show-current` у каталозі, де ви тестували.

### Хуки в кожному робочому дереві [#hooks-in-every-worktree]

Git читає `core.hooksPath` зі спільної конфігурації всіх робочих дерев репозиторію, а Vite+ записує туди відносний шлях `.vite-hooks/_`, тож Git запускає диспетчер хуків того робочого дерева, у якому ви робите коміт. Диспетчер генерується й ніколи не потрапляє в коміт, тому кожному робочому дереву потрібен власний, а там, де його немає, Git без попередження пропускає хуки. Його встановлюють два кроки:

- `git worktree add` запускає хук `post-checkout` того checkout, з якого ви викликаєте команду, а `.vite-hooks/post-checkout` встановлює диспетчер нового робочого дерева командою `vp hooks enable`. Тоді коміт, зроблений до `bun install`, завершується помилкою в хуку `pre-commit`, а не пропускає його.
- `bun install` запускає `prepare`, який оновлює диспетчер командою `vp config --no-agent`, а потім запускає `scripts/verify-git-hooks.ts`. Встановлення завершується помилкою, коли `core.hooksPath` не дорівнює `.vite-hooks/_` або коли в диспетчері бракує хука з `.vite-hooks/`, а повідомлення про помилку показує команду, яка це виправляє.

Ніколи не задавайте `core.hooksPath` інше значення й ніколи не передавайте Git `-c core.hooksPath`. Поки там був абсолютний шлях до диспетчера основного checkout, `vp config` не встановлював диспетчер в інших робочих деревах, а коли наступний `bun install` в основному checkout повернув відносний шлях, коміти в цих робочих деревах створювалися без хуків. `vp hooks status` показує, чи активні хуки в робочому дереві.

## Лінійна історія [#linear-history]

Ruleset, що захищає `main` на GitHub, вимагає лінійної історії, приймає лише злиття через squash і відхиляє force-push, тож кожен pull request потрапляє в `main` одним комітом. Гілки pull request теж лишаються лінійними:

- Ніколи не створюйте коміт злиття ні в `main`, ні в гілці pull request: не зливайте `main` у гілку й не розв’язуйте конфлікти в коміті злиття.
- Оновлюйте гілку, роблячи rebase на `main`, командою `gh pr update-branch --rebase` або командами `git fetch origin` і `git rebase origin/main`.
- Коли GitHub не може зробити rebase pull request із кількома комітами, внесіть його знову одним комітом поверх `main`: зведіть гілку в один коміт на її merge base, а потім зробіть rebase цього коміту, щоб розв’язати кожен конфлікт лише раз:

```sh
git fetch origin
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -m "feat(course): reorder the catalogue from the course list"
git rebase origin/main
git push --force-with-lease
```

- Надсилайте переписану гілку командою `git push --force-with-lease` і лише власну гілку pull request. Ніколи не робіть force-push у `main` чи в чужу гілку й ніколи не використовуйте простий `--force`, який перезаписує коміти, надіслані після вашого останнього fetch.

## Pull request

- **Невеликі й цільові.** Одне виправлення, одна функціональність або один рефакторинг на pull request. Велика функціональність стає стеком pull request, кожен з яких можна переглянути окремо, як це було з відео, курсами й адмінкою курсів.
- **Заголовок — це squash-коміт.** Використовуйте формат коміту; він стає темою в `main`.
- **Опис** містить `## Summary` з тим, що змінилося і чому, `## Test plan` з командами, які ви запускали, та їхніми результатами, і `## Docs` зі списком сторінок, розділів README і текстів, які ви оновили. Пишіть просто, без маркетингової мови.
- **Кожен pull request оновлює те, що він робить неточним:** README, сторінки документації в усіх локалях і будь-які тексти сайту чи твердження лендингу, яких він стосується, а також додає власний [запис журналу змін](#changelog-entries). Неточність, знайдена в коді, який ви не змінювали, отримує окремий pull request.

## Записи журналу змін [#changelog-entries]

Кожен pull request додає власний запис до [журналу змін](/docs/project/changelog), тож pull request, відкриті паралельно, ніколи не редагують той самий файл.

- **Назвіть його номером pull request.** Відкрийте pull request, а потім додайте `content/changelog/<number>.<locale>.mdx` в усіх локалях: маркований список без frontmatter про те, що змінилося для тих, хто користується кодом, з посиланнями на сторінки документації, яких він стосується.
- **Ніколи не пишіть ні дату, ні номер pull request.** Сторінка журналу змін бере день кожного запису, а нотатки до релізу — його реліз, з історії Git: день (UTC) squash-коміту, тему якого GitHub завершує `(#<number>)`. Доки pull request не злито, його запис показано в розділі **Ще не випущено**. Номер вони беруть із назви файлу: сторінка завершує кожен запис посиланням на його pull request, а запис, названий за комітом, — посиланням на цей коміт, тоді як нотатки до релізу завершують його `(#<number>)`, що GitHub перетворює на посилання. Після розгортання сторінка також посилається з кожного запису на [реліз](/docs/tooling/ci-cd#releases-and-tags), який першим його доставив.
- **CI це перевіряє.** У pull request `bun run check` завершується помилкою, доки бракує `content/changelog/<number>.en-US.mdx`, а `check:i18n` порівнює з ним кожен переклад так само, як сторінку документації. Помилкою завершується й файл, названий ні номером pull request, ні повним хешем коміту: нечисленні зміни, що потрапили в `main` без pull request, мають назву свого коміту.
- **Невипущеним може бути лише ваш власний запис.** У CI збірка сайту завершується помилкою, доки журнал змін показував би в розділі **Ще не випущено** запис, якого там не має бути: у pull request до `main` — будь-який запис, крім запису самого pull request, а в `main` — будь-який запис. Локальна збірка, яка не має `GITHUB_REF`, показує всі незлиті записи. Так виявляється запис, що пережив свій pull request: `content/changelog/219.<locale>.mdx` залишився після того, як #219 закрили без злиття, повторював запис #220 і показувався в production у розділі **Ще не випущено**, доки #254 його не видалив.

## Перевірки

CI запускає `bun run check` і `bun run test:coverage`, потім збирає тестовий Worker і запускає набір браузерних тестів у Chromium; лише коли обидва етапи проходять, він розгортає preview. Дочекайтеся й розгортання preview: це єдиний крок, який завантажує Worker у Cloudflare, і обмеження Cloudflare на завантаження вже провалювали розгортання, яке пройшло всі інші перевірки. Див. [CI/CD](/docs/tooling/ci-cd).
