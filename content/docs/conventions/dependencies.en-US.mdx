The repository runs on the latest release of every dependency. An upgrade that breaks something is fixed forward, in the code or upstream, never by going back.

## Toolchain versions [#upgrading]

Update the dependencies, the agent skills and the GitHub Actions with one command, on a branch of its own:

```sh
bun run deps:update
```

`scripts/update-dependencies.ts` runs, in this order:

1. `vp migrate` from the newest Vite+ release when it is newer than the `vite-plus` in `package.json`, which moves `vite-plus`, the `vite` alias and `vitest` together;
2. `bun update --latest` for every dependency declared with a `^` or `~` range, which moves it to its newest release, a new major included, and keeps the range;
3. `bun run skills:update`, which moves the [agent skills](/docs/tooling/agent-skills) to the newest commits of their sources and records the versions of the packages they document;
4. `scripts/github-actions.ts`, which reads the release tags of every action's repository in `.github/workflows/` and `.github/actions/` with `git ls-remote`, takes the newest stable release, follows an annotated tag to its commit and rewrites each `uses:` to that commit and tag ([CI/CD](/docs/tooling/ci-cd)).

It leaves the exact pins alone, because each one has a reason on this page, and ends by naming every pinned package that has a newer release. `bun run check` fails while a package that a skill documents has moved since the last `skills:update`, so the dependencies and the skills cannot drift apart. Every week the `updates.yml` workflow lists the available updates in one GitHub issue; see [CI/CD](/docs/tooling/ci-cd#updates).

Then, for every package that moved:

- Bun is the package manager and script runner. `packageManager` in `package.json` (Bun <RepositoryFact name="bunVersion" />) is the one place its version is set; CI reads it from there. `bun.lock` is committed.
- Node comes from `.nvmrc` (<RepositoryFact name="nodeVersion" />), and `engines.node` requires at least that version.
- `remotion/` is the one exception, with its own npm toolchain, installed only when editing the landing videos. Its `typescript` is the newest release that `typescript-eslint`, which runs Remotion's lint rules, accepts as a peer dependency, because TypeScript 7 does not ship the compiler API that `typescript-eslint` reads. The packages it shares with the website, `@saasyland/stack`, `lucide-react`, `react` and `react-dom`, are pinned to the lowest version the website's `package.json` accepts, because the videos render website files that import them, and `src/data/__test__/cli.test.ts` fails when the two differ.

## Upgrading

1. Read the changelog and the migration guide of the new version, preferably the copy shipped in `node_modules/<package>`.
2. Change the code to match the documented usage of the new version.
3. Verify in this order, and report nothing as done before the last step passes:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` and the tests run without the Cloudflare and TanStack Start build, so they can pass while the build is broken. That happened twice in one upgrade: a new `@polar-sh/sdk` could not be bundled, and a TanStack Start release changed the `modulepreload` markup that `optimize-prerendered-html.ts` rewrites. Both surfaced only in `build:test`. After a build, `find dist/server -name '*.map'` must print nothing; `upload_source_maps: false` in `wrangler.jsonc` exists because the Worker with its source maps is larger than Cloudflare accepts for an upload (see [Cloudflare Workers](/docs/integrations/cloudflare-workers)).

Never pin a package back to an older release to avoid a breaking change, and never add code to the application that works around a library bug.

## When the bug is upstream

When the application already follows the documented usage and the new version is wrong, keep the new version and carry the fix:

1. Prove the bug with a minimal reproduction outside this repository.
2. Write the smallest change that fixes it in the package, mirroring the fix you will propose upstream, and save it with `bun patch`. The patch lands in `patches/<package>@<version>.patch` and in `patchedDependencies`, and the package is pinned to that exact version so the patch keeps applying.
3. Report the bug upstream and open a pull request with the fix, following that project's contribution rules.
4. Delete the patch as soon as a release contains the fix. Before keeping or documenting a patch, check with `npm view <package> version` whether that release is already out.

The current patches:

- `patches/@tanstack%2Frouter-core@1.171.39.patch` stops the router's first render after hydration from scrolling the window back to the top. It is reported upstream as [TanStack/router#8933](https://github.com/TanStack/router/issues/8933), and the patch is the fix proposed in [TanStack/router#8934](https://github.com/TanStack/router/pull/8934).
- `patches/@tanstack%2Freact-router@1.170.46.patch` stops `lazyRouteComponent` from reloading a page whose route chunk the browser cancelled because the visitor is leaving. It is the fix proposed in [TanStack/router#8830](https://github.com/TanStack/router/pull/8830), extended to a chunk that the page starts to load after `beforeunload`, which Safari fails at once.
- `patches/framer-motion@14.14.0.patch` makes `LazyMotion` ignore a feature bundle that fails to load instead of leaving the rejection unhandled. `motion` is pinned to 14.14.0 with it. Motion merged the fix for [motiondivision/motion#4089](https://github.com/motiondivision/motion/issues/4089) after releasing 14.14.0, so the patch goes with the first release that contains it.
- `patches/better-auth@1.7.27.patch` lets the `haveIBeenPwned` plugin hash a password outside a Better Auth endpoint, as `(await auth.$context).password.hash()` does in the integration tests, by reading the endpoint context with `tryGetCurrentAuthEndpointContext` instead of `getCurrentAuthEndpointContext`, which throws there. `better-auth` is pinned to 1.7.27 with it. It is the fix proposed in [better-auth/better-auth#12873](https://github.com/better-auth/better-auth/pull/12873).
- `patches/playwright-core@1.65.1.patch` lets Playwright's WebKit driver follow a cross-site navigation to a page that sends `Cross-Origin-Opener-Policy`, such as the return from Polar's hosted checkout to the workspace: the WebKit build of Playwright 1.65 creates a second provisional page for the swap before it destroys the first, and the driver now discards the first instead of failing an assertion in `WKPage._onTargetCreated`. `@playwright/test` is pinned to 1.65.1 with it. It is reported upstream as [microsoft/playwright#44254](https://github.com/microsoft/playwright/issues/44254), which Playwright has closed as completed; no stable release after 1.65.1 contains the fix yet, so the patch stays until one does.

`@tanstack/router-core` is a direct dependency, because `src/lib/stale-build.ts` imports `isModuleNotFoundError` from it, and is pinned to 1.171.39 so its patch keeps applying. `@tanstack/react-router` is pinned to 1.170.46 and `@tanstack/react-start` to 1.169.7, because they depend on exactly the patched TanStack versions. A patch to `fumadocs-mdx` 15.6.0 was carried the same way and removed when 15.6.1 shipped the upstream fix, and so were the patches to `@fumadocs/base-ui` and `fumadocs-core` 16.19.2 when 16.19.3 shipped theirs. The patch to `@videojs/utils` 10.4.0 went when 10.5.0 shipped its fix. A patch that gave the Fumadocs docs layout a `skipToContent` slot was removed when Fumadocs declined the slot; `globals.css` now hides Fumadocs' link, and the site's own skip link leads to the docs article (see [Docs site](/docs/features/docs-site)).

A patch changes a package's files, not the versions Bun installs for it. When a package pins one of its own dependencies below the release the application uses and the two copies' types disagree, an `overrides` entry in `package.json` lifts it instead. None is needed today. `@polar-sh/adapter-utils` 1.1.1, which `@polar-sh/better-auth` uses, pins `@polar-sh/sdk` 1.3.1, so Bun installs that copy beside the application's 1.3.2. The adapter imports the SDK only to type the plugin's `webhooks({ onPayload })`, and `handlePolarEvent`, which takes the 1.3.2 payload, accepts the 1.3.1 one, because 1.3.2 only widens types, such as `trial_ended` among the subscription statuses. When a later SDK release changes a payload in a way the adapter's copy does not accept, `bun run check` fails at `handlePolarEvent`; an `overrides` entry for `@polar-sh/sdk` then lifts the adapter's copy until an `@polar-sh/adapter-utils` release depends on that SDK (`npm view @polar-sh/adapter-utils dependencies`).

## Security advisories

Dependabot alerts cover `remotion/package-lock.json`, but GitHub does not read `bun.lock`, so check the application with `bun audit` and the video project with `npm audit` inside `remotion/`. Clear an advisory with the newest release of the package that pulls in the vulnerable one. When that package's version range already allows the fixed release, refreshing the lockfile is enough: `bun update`, or `npm update` in `remotion/`.

When no release of the parent allows the fix yet, an `overrides` entry lifts the vulnerable package, and it is deleted as soon as a parent release does. The current entries:

- `package.json`: `"minimatch": "^11.0.1"`. `shadcn` reaches `minimatch` ^10 through `ts-morph` 26 and `@ts-morph/common`, and only `minimatch` 11.0.1 fixes GHSA-g3hv-75wg-m249. Delete it when `shadcn` depends on a `ts-morph` release that contains [dsherret/ts-morph#1697](https://github.com/dsherret/ts-morph/pull/1697).
- `remotion/package.json`: `minimatch` ^11.0.1 under `@typescript-eslint/typescript-estree`, for the same advisory. `@remotion/eslint-config-flat` pins `typescript-eslint` 8.71.2, whose parser asks for `minimatch` ^10. Delete it when `@remotion/eslint-config-flat` depends on a `typescript-eslint` release that contains [typescript-eslint/typescript-eslint#13145](https://github.com/typescript-eslint/typescript-eslint/pull/13145).

`bun audit` still reports one advisory that has no fix to take:

- `esbuild` 0.18.20 (GHSA-67mh-4wv8-2f99, moderate), through `drizzle-kit` and `@esbuild-kit/esm-loader`. `drizzle-kit` 0.31.11 declares the loader but never imports it, and the advisory concerns esbuild's development server, which nothing here starts. [drizzle-team/drizzle-orm#5304](https://github.com/drizzle-team/drizzle-orm/issues/5304) tracks removing it; the `drizzle-kit` 1.0 release candidates no longer depend on it.

GitHub withdrew the `deepmerge` 4.3.1 advisory (GHSA-gcqx-w48m-w2h4), which `shadcn` and `@shadcn/registry` pulled in, after [github/advisory-database#10910](https://github.com/github/advisory-database/issues/10910), so `bun audit` no longer reports it.

## The Vite+ entries in package.json

```json
"vite": "npm:@voidzero-dev/vite-plus-core@8.3.8000",
"vite-plus": "1.7.0",
"vitest": "5.1.0"
```

These lines, and the same `vite` alias and `vitest` version under `overrides`, are exactly what Vite+'s own migrator writes: `vite-plus` is pinned to an exact version, Bun needs the core as a direct `vite` dependency, and `vitest` is listed because `@vitest/coverage-v8` and the test types need it. Since `vite-plus` 1.7.0 the core carries the version of the Vite release it bundles, so 8.3.8000 is Vite 8.3.8; `vp toolchain` prints the pairing. Upgrade them together with `vp migrate`, never with `bun update`. To find out whether one of them can go, copy the project, run `vp migrate` on the copy and diff the result; do not decide by reasoning about it. The `minimatch` entry under `overrides` is the security override described above, and `vp migrate` leaves it unchanged.

`build.rolldownOptions.external`, which `src/integrations/polar/polar.vite.ts` sets, lists optional peer dependencies of `@polar-sh/sdk` that are not installed and are tree-shaken out of the Worker; see [Vite+](/docs/tooling/vite-plus). Remove the list when Polar fixes its packaging.

## Adding a dependency

Check first whether a package already in `package.json` does the job, so each concern keeps one library. Add a runtime dependency with `bun add`, a tool with `bun add --dev`, and use the vendor's agent skill from `skills-lock.json` when there is one (see [Agent skills](/docs/tooling/agent-skills)). When a vendor skill documents the new package, add the package to its source in `SKILL_SOURCES` (`src/data/skills.ts`) and run `bun run skills:update`.
