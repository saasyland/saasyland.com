---
title: "File di route"
description: "L'unica forma di una route di pagina e di una route di layout: NAMESPACE o NAMESPACES, un loader con un solo Promise.all, uno scheletro che rispecchia la pagina, schemi di ricerca e link."
---

Ogni file in `src/routes` ha la stessa forma, quindi chi ne conosce uno li conosce tutti. Un file di route compone: dichiara ciò di cui la pagina ha bisogno e posiziona i componenti. Widget, form, finestre di dialogo e colonne delle tabelle si trovano in `src/presentation/components/custom`.

## Route di pagina

`src/routes/admin.courses.index.tsx`:

```tsx
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <div className="flex flex-col gap-4 sm:flex-row sm:items-end sm:justify-between">
        <div>
          <h1 className="text-statement font-semibold text-foreground">{t("title")}</h1>
          <p className="text-sm text-muted-foreground">{t("description")}</p>
        </div>
        <LinkButton className="h-9 gap-2" href={ROUTES.ADMIN_COURSES_CREATE} size="sm">
          <PlusCircle aria-hidden className="size-4" />
          {t("actions.create")}
        </LinkButton>
      </div>

      <DataTable columns={courseColumns} options={{ query: ({ pageIndex, pageSize }) => getCoursesPageQuery({ pageIndex, pageSize }) }} />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  head: pageHead(ROUTES.ADMIN_COURSES),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Il componente** è una `const` locale chiamata `<Name>Page`, definita per prima. Piccoli frammenti di markup usati solo da questa pagina possono stare sopra di essa come componenti locali, come fanno `CourseProgress` e `StartLink` in `courses.$course.index.tsx`; tutto ciò che ha dati, mutation o stato propri va in un file di componente.
- **Un solo namespace.** `const NAMESPACE = "pages.<area>.<page>"` sta subito sopra `export const Route` ed è usato in `loadPageMetadata`, `preloadNamespaces` e `staticData`. Tutto il resto di cui la pagina ha bisogno lo dichiara il suo layout.
- **Un solo `Promise.all`.** Il loader avvia tutto il lavoro in una volta: i metadati della pagina, il namespace e ogni query che i componenti leggono. Restituisce `{ locale, metadata }` per `head`. Non attendere mai uno di questi prima di avviare il successivo.
- **`head: pageHead(ROUTES.X)`** costruisce titolo, descrizione, URL canonico e alternative a partire dai metadati del file del namespace.
- **I percorsi provengono da `ROUTES`** in `src/routes.ts`, che riunisce i percorsi di tutte le aree (vedi [Percorsi e navigazione](#paths-and-navigation)); non scrivere mai un percorso letterale.

Una pagina il cui titolo proviene da un record attende quel record e costruisce il proprio head dai dati del loader, come fa `admin.courses.$courseId.tsx`:

```tsx
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  head: ({ loaderData }: { loaderData?: { locale: SupportedLocale; pathname: string; title: string } | undefined }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  pendingComponent: AdminCourseEditorPending,
})
```

## Route di layout

`src/routes/admin.courses.tsx`:

```tsx
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Un layout dichiara `const NAMESPACES = [...] as const` sopra `export const Route` e lo precarica. Quando non ne ha, omette l'opzione; non esiste `namespaces: []`.
- Il componente, quando il layout ne rende uno, si chiama `<Name>Layout` e posiziona un `<Outlet />`.
- Una guard va in `beforeLoad` sul layout che possiede l'area: `beforeLoad: requireAdmin` in `admin.tsx`, `requireSignedIn` in `app.tsx`. Le guard decidono solo la navigazione; ogni server function controlla comunque il proprio permesso.

## Ordine delle opzioni

`sort-keys` è disattivata in `src/routes` perché TanStack Router inferisce i tipi nell'ordine di dichiarazione. Le opzioni sono in ordine alfabetico, tranne `validateSearch`, che viene per prima, prima di qualsiasi cosa legga la ricerca:

```tsx
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: zod.object({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Non scrivere mai un array o un oggetto di dati direttamente dentro `createFileRoute`; dichiaralo come costante sopra.

## Parametri di ricerca

`validateSearch` è uno `zod.object` costruito con gli helper di `src/lib/search-params.ts`:

| Helper                            | Valore quando il parametro manca o è malformato | Uso                                      |
| --------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| `searchText()`                    | `undefined`                                     | Token, email, codici di errore           |
| `searchFlag()`                    | `undefined`                                     | Booleani                                 |
| `searchParam(schema)`             | `undefined`                                     | Qualsiasi altro schema, come un percorso |
| `searchChoice(choices, fallback)` | `fallback`                                      | Una scheda o una vista                   |

Il testo assente resta `undefined`, quindi un valore predefinito non finisce mai in un URL costruito dal router. Un parametro `searchChoice` è abbinato a `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, che rimuove il valore predefinito dall'URL. Non scrivere mai a mano controlli come `typeof search["x"] === "string"`; aggiungi un helper quando serve un nuovo tipo di campo. Quando un componente figlio ha bisogno di un parametro che la pagina ha già verificato come presente, la pagina ne restringe il tipo e lo passa in basso, come `auth.reset-password.tsx` passa `token` a `ResetPasswordForm`. Un layout valida i parametri letti da tutta la sua area, come fa `app.tsx` con `validateSearch: appSearchSchema`; lo schema si trova in `src/data/app.ts` perché lo scheletro del layout analizza gli stessi parametri.

## Scheletri

La navigazione deve sembrare istantanea, quindi ogni route che rende una pagina ha un `pendingComponent` che la rispecchia: lo stesso layout, le stesse card e lo stesso numero di righe.

- Gli scheletri si trovano nel file pending dell'area (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) e usano `Skeleton` di shadcn.
- Un segnaposto di testo riceve il vero token tipografico più `h-lh scale-y-70`, così ha l'altezza della riga che sostituisce: `<Skeleton className="h-lh w-28 scale-y-70 font-mono text-label" />`.
- La lunghezza degli elenchi proviene dalle costanti che usa la pagina: `PAGE_ROWS` in `admin/pending-blocks.tsx` ha `DEFAULT_PAGE_SIZE` righe, la dimensione di pagina di ogni tabella dell'amministrazione.
- Lo scheletro di un layout sceglie lo scheletro di pagina per il percorso corrente da una mappa, come fanno `AdminPending`, `AppPending` e `MarketingPending` con `PAGE_SKELETONS` e `AdminCourseSectionPending` con `COURSE_PAGES` in `admin/courses-pending.tsx`. Ogni area aggiunge le sue pagine a `PAGE_SKELETONS` in `src/data/<area>.skeletons.ts` (vedi [Percorsi e navigazione](#paths-and-navigation)); una pagina di un layout che appartiene a una sola area, come una sezione di un corso, viene aggiunta alla mappa propria di quel layout.
- Non esiste un `defaultPendingComponent` valido per tutto il router, e `pendingMs` mantiene il valore predefinito di TanStack. Le route della documentazione sono l'unica eccezione: `pendingMs: Number.POSITIVE_INFINITY` e `wrapInSuspense: false`. Il componente della pagina si idrata con il layout della documentazione e renderizza l'MDX in un proprio `<Suspense key={path}>`, così la barra laterale funziona prima che il chunk MDX della pagina sia caricato, e una navigazione sostituisce l'HTML del server della pagina precedente invece di idratarlo con i dati della successiva.

## Link

- I link del router ricevono una costante: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, oppure un pattern di route con `params` per i percorsi dinamici. `LinkButton` di shadcn riceve un `href`.
- Non aggiungere mai il prefisso del locale a un link del router; lo aggiunge la riscrittura del router. Un URL completo nel locale corrente, per un valore che esce dal router come stringa, proviene da `router.buildLocation({ ... }).publicHref`, come fa `use-auth-redirect.ts` per costruire i suoi link di accesso. `localizePathname` serve per gli URL costruiti fuori dal contesto di un router o per un altro locale: email, destinazioni di reindirizzamento di Better Auth, link dentro l'MDX e il selettore della lingua.

## Percorsi e navigazione [#paths-and-navigation]

Nessun file elenca tutte le aree dell'applicazione. Ogni area, come i corsi, i prodotti o le pagine legali, dichiara i propri percorsi, le proprie voci di menu con le relative etichette, gli scheletri delle pagine e i permessi, e un barrel li riunisce: un'area si aggiunge o si esclude con i suoi file. È così che la CLI `saasyland` compone un progetto a partire da layer di template.

| Cosa                        | Ogni area dichiara                                              | Barrel                           | Letto da                                                                                                                              |
| --------------------------- | --------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Percorsi                    | `src/data/<area>.routes.ts`: un `export const` per percorso     | `src/data/routes.entries.ts`     | `ROUTES` in `src/routes.ts`                                                                                                           |
| Voci di menu                | `src/data/<area>.navigation.ts`: una lista `<AREA>_NAVIGATION`  | `src/data/navigation.entries.ts` | `ADMIN_NAVIGATION`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `NAVIGATION_PAGES` e `FOOTER_NAVIGATION` in `src/data/navigation.ts` |
| Statistiche della dashboard | `src/data/<area>.dashboard.ts`: una lista `<AREA>_DASHBOARD`    | `src/data/dashboard.entries.ts`  | `ADMIN_DASHBOARD_STATS` in `src/data/dashboard.ts`                                                                                    |
| Scheletri delle pagine      | `src/data/<area>.skeletons.ts`: una lista `<AREA>_SKELETONS`    | `src/data/skeletons.entries.ts`  | `PAGE_SKELETONS` in `src/data/skeletons.ts`                                                                                           |
| Permessi                    | `src/data/<area>.access.ts`: un oggetto `<AREA>_ACCESS`         | `src/data/access.entries.ts`     | `APP_STATEMENTS` e `grantsOf` in `src/data/access.ts`                                                                                 |
| Percorsi non elencati       | `src/data/<area>.routes.ts`: una lista `<AREA>_UNLISTED_ROUTES` | `src/data/unlisted.entries.ts`   | `UNLISTED_ROUTES` e `isUnlistedRoute` in `src/data/unlisted.ts`                                                                       |

Un barrel contiene solo righe `export { … } from`, una per file di area e ordinate per modulo, come `src/integrations/drizzle-orm/drizzle.schemas.ts`. `src/routes.ts` riesporta i percorsi come un unico namespace, così ogni percorso mantiene il suo tipo letterale e `<Link to={ROUTES.COURSES}>` resta verificato rispetto all'albero delle route:

```ts title="src/routes.ts"
export * as ROUTES from "~/src/data/routes.entries"
```

Una voce di menu indica dove compare con `placement` (`NAVIGATION_PLACEMENT` in `src/data/navigation.constants.ts`): la sidebar dell'admin, i pulsanti sopra la dashboard, la barra laterale dell'app clienti, l'intestazione pubblica o il footer. Il suo `order` la colloca tra le voci delle altre aree, quindi nessuna lista dipende dall'ordine dei file. Le voci dell'admin indicano anche il loro gruppo della sidebar (`group`) e i link del footer la loro colonna (`column`); `ADMIN_NAVIGATION_GROUPS` e `FOOTER_COLUMNS` fissano l'ordine di gruppi e colonne, e quelli che nessuna area riempie vengono omessi. L'area di base, presente in ogni progetto, aggiunge due voci dell'admin e due voci alla barra laterale dell'app clienti:

```ts title="src/data/core.navigation.ts"
const AREA = "core"

export const CORE_NAVIGATION = [
  {
    area: AREA,
    group: ADMIN_NAVIGATION_GROUP.OVERVIEW,
    icon: Home,
    key: "dashboard",
    order: 10,
    placement: NAVIGATION_PLACEMENT.ADMIN,
    to: ROUTES.ADMIN,
  },
  {
    area: AREA,
    group: ADMIN_NAVIGATION_GROUP.ADMINISTRATION,
    icon: Settings,
    key: "settings",
    order: 30,
    placement: NAVIGATION_PLACEMENT.ADMIN,
    to: ROUTES.ADMIN_SETTINGS,
  },
  { area: AREA, icon: Home, key: "overview", order: 10, placement: NAVIGATION_PLACEMENT.APP, to: ROUTES.APP },
  { area: AREA, icon: Settings, key: "settings", order: 30, placement: NAVIGATION_PLACEMENT.APP, to: ROUTES.APP_SETTINGS },
] as const satisfies readonly NavigationEntry[]
```

Una statistica della dashboard ha un `prefetch`, che il loader di `/admin` esegue, e un hook `useValue`, che `DashboardStats` chiama per leggere il numero.

Uno scheletro di pagina associa il `to` della pagina al suo `pendingComponent`, lo stesso scheletro che imposta la route della pagina. Gli scheletri di layout `AdminPending`, `AppPending` e `MarketingPending` disegnano quello del percorso corrente quando qualcuno entra nel loro layout da un'altra parte. Un'area dichiara gli scheletri di tutte le sue pagine, qualunque sia il layout che le mostra: l'area della licenza dichiara `/app`, `/app/license` e `/premium`, e l'area legale le sue cinque pagine pubbliche.

Il file di accesso di un'area contiene le dichiarazioni di permesso delle sue risorse e i ruoli a cui le concede. `auth.access.ts` costruisce il controllo degli accessi di Better Auth da `APP_STATEMENTS` e ogni ruolo da `grantsOf(role)`, quindi l'integrazione di autenticazione non nomina alcuna area, e `APP_STATEMENTS` fallisce quando due aree dichiarano la stessa risorsa (vedi [Ruoli e permessi](/docs/guides/roles-and-permissions)).

Le liste di `src/data/navigation.ts` e `PAGE_SKELETONS` hanno tipi dichiarati, `NavigationEntry` e `PageSkeleton`, invece dei tipi delle voci che le aree dichiarano in quel momento, quindi una posizione che nessuna area riempie, come le azioni della dashboard in un progetto senza l'area dei prodotti, è una lista vuota che supera comunque il controllo dei tipi. `navigation.test.ts` e `skeletons.test.ts` controllano in compilazione che il `to` di ogni voce e di ogni scheletro dichiarato da un'area sia un percorso dell'albero delle route (`FileRouteTypes["to"]` da `src/routeTree.gen.ts`).

Una voce indica la sua `area`, e l'area le assegna l'etichetta nel proprio file di messaggi: `<placement>.<key>` in `messages/<locale>/navigation.<area>.json`, come `admin.courses` e `header.courses` in `navigation.courses.json`. Una statistica della dashboard ha l'etichetta sotto la sua `key` in `dashboard.<area>.json`, e una sezione dell'admin definisce le etichette delle sue sottopagine per le breadcrumb sotto `breadcrumbs.<segment>` nel suo `navigation.<area>.json`, come `breadcrumbs.create`. Entrambi i tipi di file sono namespace radice, quindi ogni menu può mostrare l'etichetta di qualsiasi voce, e `useNavigationLabel` in `src/hooks/use-navigation-label.ts` restituisce l'etichetta di una voce. Ciò che appartiene al menu stesso resta nel suo namespace: `groups.<group>` in `pages.admin.sidebar`, `columns.<column>` in `components.custom.footer` e le sezioni della landing page in `components.custom.navigation`. `enum-labels.test.ts` fallisce quando a una voce o a una statistica manca l'etichetta in un locale.

Un'area le cui pagine vengono renderizzate dal Worker a ogni richiesta, come `/admin`, `/auth` o `/courses`, elenca quei percorsi in `<AREA>_UNLISTED_ROUTES`. `vite.config.ts` li esclude dal prerendering con `isUnlistedRoute`, e `buildPageHead` assegna loro la card del sito invece di una card della pagina (vedi [Motori di ricerca e anteprime social](/docs/features/seo)). Vite non risolve l'alias `~` mentre carica la propria configurazione, quindi `unlisted.entries.ts` e `unlisted.ts` importano i file di area con un percorso relativo.
