`bun run check` запускає `bun run generate:cn`, `bun run check:comments`, `bun run check:i18n` і `bun run check:flows`, а потім `vp check`, який за один прохід форматує код через oxfmt, лінтить через oxlint і перевіряє типи через TypeScript з конфігурацією з `vite.config.ts` і `tsconfig.json`. CI запускає ту саму команду. Ніщо тут не є справою смаку: якщо інструменти пропускають код, що порушує правило з цієї сторінки, його відхиляють на рев’ю.

## Що забезпечують інструменти

oxlint запускає категорії `correctness`, `nursery`, `pedantic`, `perf`, `style` і `suspicious` як помилки, з увімкненими правилами з урахуванням типів і перевіркою типів. Обмеження, які найбільше впливають на форму коду:

| Правило                                 | Налаштування                                                                  | Наслідок                                                                |
| --------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `max-lines`                             | <RepositoryFact name="maxLines" />                                            | Розділіть файл за відповідальностями, перш ніж він розростеться         |
| `max-lines-per-function`                | <RepositoryFact name="maxLinesPerFunction" />                                 | Компоненти й обробники залишаються невеликими                           |
| `max-statements`                        | <RepositoryFact name="maxStatements" />                                       | Виносьте іменовані допоміжні функції замість довгих тіл                 |
| `no-magic-numbers`                      | дозволено лише `0` і `1`, а також індекси масивів і значення за замовчуванням | Кожне інше число — іменована константа                                  |
| `id-length`                             | щонайменше два символи, крім `_`, `m` і `t`                                   | Ідентифікатори — це слова; `t` — функція перекладу                      |
| `one-var`                               | `never`                                                                       | Одне оголошення на інструкцію                                           |
| `unicorn/no-null`                       | увімкнено поза тестами й `src/platform/testing`                               | Відсутні значення — це `undefined`                                      |
| `typescript/no-explicit-any`            | `error`                                                                       | Жодне значення не має типу `any`                                        |
| `typescript/ban-ts-comment`             | `true` для `@ts-expect-error`, `@ts-ignore` і `@ts-nocheck`                   | Жодну помилку компілятора не приглушують, ні з поясненням, ні без нього |
| `typescript/consistent-type-assertions` | `assertionStyle: "never"`                                                     | Жодного приведення `as`; `as const` і `satisfies` залишаються           |
| `code-style/no-comments`                | `error`                                                                       | Жодного коментаря, зокрема коментарів-директив                          |
| `code-style/no-multiline-ternary`       | `error`                                                                       | Тернарний оператор вміщується в один рядок                              |
| `code-style/no-undefined-fallback`      | `error`                                                                       | Жодного `?? undefined`                                                  |
| `radius/no-off-scale`                   | `error`                                                                       | Кожен кут бере радіус зі шкали                                          |
| `type/no-off-scale`                     | `error`                                                                       | Кожен розмір тексту — крок типографічної шкали                          |
| `type/mono-for-code`                    | `error`                                                                       | Моноширинний шрифт лише для коду                                        |

Перевизначення вузькі й обмежені файлами: тести та спільні тестові допоміжні модулі в `src/platform/testing` послаблюють `no-magic-numbers`, `no-await-in-loop`, `unicorn/no-null`, `hydration/no-clock-or-locale-in-render` і `admin-data/no-literal-data`; `src/presentation` і `src/hooks` послаблюють `typescript/consistent-return`; тестові моки послаблюють `require-await`; `src/routes` вимикає `sort-keys`, бо опції маршруту мають власний порядок (див. [Файли маршрутів](/docs/conventions/routes)); а маршрути, компоненти й файли даних адмін-панелі вмикають `admin-data/no-literal-data` (див. [Панель адміністратора](/docs/features/admin-dashboard#real-data-only)). Увесь `src` вмикає `radius/no-off-scale`, `type/no-off-scale` і `type/mono-for-code`, які тести та `src/platform/testing` знову вимикають, а `src/presentation/social-card.tsx` вимикає `type/no-off-scale`, бо Takumi рендерить соціальну картку як зображення фіксованого розміру, розміри тексту якого задано в inline-стилях, а не на типографічній шкалі сторінки (див. [Тема](/docs/ui/theme#type-scale)).

`tsconfig.json` додає суворі прапорці, що змінюють спосіб написання коду: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` і `noUnusedParameters`. Читання за індексом може повернути `undefined`, необов’язковій властивості не можна явно присвоїти `undefined`, а сигнатуру індексу читають як `record["key"]`.

Форматер виводить код без крапок з комою, з подвійними лапками, завершальними комами й шириною рядка <RepositoryFact name="printWidth" />. Він також сортує імпорти у фіксовані групи, класи Tailwind — у `className` і викликах `cn`, а скрипти `package.json` — за назвою (`sortPackageJson: { sortScripts: true }`), тож ніколи не впорядковуйте нічого з цього вручну: `vp check` завершується помилкою, коли щось із цього стоїть не в тому порядку. Команди описано на сторінці [Лінтинг і форматування](/docs/tooling/lint-format).

## Рендерити те, що відрендерив сервер

Сторінка рендериться двічі: на сервері й ще раз у браузері, коли React гідратує HTML. Обидва рендери мають вивести однаковий текст, інакше React повідомляє про невідповідність гідратації (помилка #418) і рендерить сторінку заново. Тому код рендерингу ніколи не читає годинник чи локаль середовища виконання, які відрізняються між ними: жодного `new Date()` без аргументу, жодного `Date.now` і жодних `toLocaleString`, `toLocaleDateString` чи `toLocaleTimeString`. Використовуйте значення, спільне для обох сторін:

- відносний час відлічується від `dataUpdatedAt` запиту, який прочитав його дані, як показано в [Інтернаціоналізація та мови](/docs/features/internationalization);
- рік, який виводить сайт, походить зі збірки: футер закінчує копірайт на `REPOSITORY_FACTS.buildYear`, році за UTC, коли зібрали сайт;
- числа й дати проходять через `useFormatter` з use-intl, мовою сторінки та в часовому поясі користувача;
- очікування в браузері, як-от тайм-аут активації в `CheckoutActivation`, — це таймер, запущений у `useEffect`, тож перший рендер збігається із серверним.

`hydration/no-clock-or-locale-in-render`, правило власного oxlint-плагіна репозиторію в `scripts/hydration-lint-plugin.ts`, забезпечує це в `src/hooks`, `src/presentation`, `src/providers` і `src/routes/*.tsx`. Усе там вважається кодом рендерингу, крім функції, яка виконується пізніше: обробника подій `on…` як JSX-пропа, властивості об’єкта чи змінної; `queryFn` або `mutationFn`; і колбека, переданого в `useEffect`, `useLayoutEffect`, `useCallback`, `setTimeout`, `setInterval`, `requestAnimationFrame` або `addEventListener`. Ці списки в плагіні й є списком дозволених: новий вид відкладеного колбека додають туди з випадком у `src/__test__/hydration-lint-plugin.test.ts`, а не коментарем, що вимикає правило.

## Жодних коментарів

Не пишіть коментарів: ні в TypeScript, TSX, тестах, скриптах, конфігурації чи CSS, ні навіть для пояснення неочевидного обмеження. Сенс натомість передає назва, а міркування потрапляють у повідомлення коміту, pull request або цю документацію.

```ts
const INCLUSIVE_END = 1
const FIRST_SEQUENCE = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

Перші дві взято з `video.delivery.ts` і `release.ts`, третю — з `src/data/polar.vite.ts`: інакше кожна з них потребувала б коментаря.

Правило забезпечують дві перевірки, і обидві називають файл, рядок і спосіб виправлення:

- `code-style/no-comments`, правило власного oxlint-плагіна репозиторію в `scripts/code-style-lint-plugin.ts`, повідомляє про кожен коментар у файлах, які читає лінтер, у редакторі та у `vp check`.
- `bun run check:comments` запускає `scripts/check-comments.ts` перед лінтером, у `bun run check` і в pre-commit-хуку. Він розбирає кожен файл TypeScript, JavaScript і CSS, який Git відстежує або додав би, через oxc для коду й PostCSS для стилів, тож `//` в URL чи регулярному виразі та `/*` у CSS-glob не є коментарями. Він читає те, чого не може лінтер: `e2e`, `remotion`, файли оголошень, таблиці стилів і коментар `/* oxlint-disable */`, якому лінтер підкоряється раніше, ніж його побачить будь-яке правило.

Винятками є файли, які `.gitattributes` позначає як `linguist-generated`, з яких кодом є `src/routeTree.gen.ts` і `src/types/worker-configuration.d.ts`, а також рядок `#!` скрипта, який граматика JavaScript не вважає коментарем. Тип, потрібний компілятору всюди, додають у `types` у `tsconfig.json`, як глобальні змінні Vitest, і ніколи не в коментар `/// <reference>`.

## Жодних обхідних шляхів

Ніколи не пишіть `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, приведення `as` чи `any`, щоб правило пройшло. Правило, яке спрацьовує, вказує на проблему в дизайні; змініть дизайн. Перевірки відхиляють кожен із них: `typescript/ban-ts-comment` — три директиви компілятора навіть із поясненням, `typescript/consistent-type-assertions` — кожне твердження типу, крім `as const`, `typescript/no-explicit-any` — `any`, а `code-style/no-comments` і `bun run check:comments` — кожен коментар, що вимикає правило. Коментар `eslint-disable` і так нічого не вимикає (`respectEslintDisableDirectives: false`).

- **Валідуйте замість тверджень.** Дані зі сховища, мережі чи запиту розбираються через Zod: `src/lib/github.ts` читає кешовану кількість зірок як `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, що є числом або `undefined`, а не здогадкою.
- **Звужуйте тип через type guard.** `isRole` в `src/integrations/better-auth/auth.roles.ts` і `isErrorCode` в `src/hooks/use-error-message.ts` перетворюють `string` на union-тип за допомогою справжньої перевірки.
- **Анотуйте, а не стверджуйте.** Надавайте значенню потрібний тип там, де його оголошено: сайдбар shadcn оголошує `SIDEBAR_MOBILE_STYLE: StyleWithCssVars`, тобто властивості CSS разом із власною властивістю сайдбара `--sidebar-width`, замість приведення об’єктного літерала.
- **Перевіряйте, а не перетворюйте.** `as const` і `satisfies` дозволені, бо ніколи не змінюють тип: `POLAR_ORDER_STATUS` закінчується на `as const satisfies Record<string, models.OrderStatus>`, тож статус Polar з помилкою в написанні не скомпілюється.
- **Змінюйте структуру, коли контракт бібліотеки заважає.** Обгорніть значення в об’єкт, розділіть функцію або читайте з типізованого джерела замість приведення.

## Null і undefined

Поза тестами й `src/platform/testing` відсутнє значення — це `undefined`, а `null` ніколи не записують як значення. Лінтер дозволяє його там, де його вимагає API: у порівнянні зі значенням, яке може бути `null`, наприклад зі стовпцем, що допускає NULL (`entry.completedAt !== null` у `course.outline.ts`), і в ref React для DOM-елемента, який починається з `useRef<HTMLElement>(null)`, бо React типізує `ref` як `RefObject<T | null>` і повертає його до `null` під час демонтування (`course-showcase.tsx`). Ніколи не перетворюйте результат API, що повертає `null`, через `?? undefined`; `code-style/no-undefined-fallback` відхиляє такий код. Спершу валідуйте вхідні дані, щоб виклик не міг завершитися невдачею, або використайте парсер, який уже повертає `undefined`. Найчастіший випадок — параметри пошуку, і `searchParam(schema)` з `src/lib/search-params.ts` повертає `undefined` для відсутнього або некоректного значення:

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Тернарні оператори та ранні повернення

Тернарний оператор має вміщуватися в один рядок, як-от `{t(course === undefined ? "create" : "save")}` у `course-form.tsx`. Усе довше, а також кожен вибір між двома фрагментами JSX, стає раннім поверненням, парою умов `&&` або невеликим компонентом; умовний клас стає `cn("base", { "classes": condition })`. `code-style/no-multiline-ternary` відхиляє кожен тернарний оператор, що займає кілька рядків, зокрема той, який розбив форматер, бо той переріс ширину рядка. `src/routes/auth.reset-password.tsx` рендерить два свої стани двома умовами:

```tsx
{hasValidToken && <ResetPasswordForm token={token} />}
{!hasValidToken && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

Функції виходять раніше в особливих випадках і залишають основний шлях без додаткового відступу, як це робить `hasLessonAccess` у `src/modules/lesson/lesson.access.ts`:

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.entitled
}
```

## Іменовані константи

Числа, крім `0` і `1`, мають назви (`COURSE_STALE_MS = 60_000`, `SAVE_INTERVAL_MS = 15_000`). `0` і `1` пишуть як літерали, як-от `.limit(1)`, `index + 1` і `toHaveBeenCalledTimes(1)`, якщо вони не мають власного значення: код виходу процесу — це `FAILURE_EXIT_CODE`, а включний кінець діапазону байтів HTTP — `INCLUSIVE_END`. Значення, що належать до домену, як-от статуси, види, рівні доступу, тарифи, ролі та значення подій постачальників, оголошуються один раз як об’єкт `as const` і всюди використовуються за назвою, зокрема в тестах і фікстурах:

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

Кортеж, потрібний стовпцю чи enum-схемі, будується з об’єкта, а не набирається заново, і лежить поруч із ним у константах модуля, що нічого не імпортують із Drizzle: `course.constants.ts` оголошує `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, який використовують і `text("status", { enum: COURSE_STATUSES })` у `course.schema.ts`, і `zod.enum(COURSE_STATUSES)` у `course.zod.ts`. Код браузера теж читає кортежі звідти: таблиця цін перебирає `LICENSE_TIERS` з `license.constants.ts`.

- Константи модуля лежать у його `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`); значення постачальника — у `*.constants.ts` інтеграції (`POLAR_ORDER_STATUS` у `polar.constants.ts`, `AUTH_PROVIDER` в `auth.constants.ts`).
- Довжини стовпців і вхідних даних отримують назву один раз, у константах модуля, і їх читають і схема Drizzle, і схема Zod: `PRODUCT_NAME_MAX_LENGTH` у `product.constants.ts`.
- Одне поняття має одну мапу в одному регістрі: `ERROR_CODES` для серверних помилок, `AUTH_ERRORS` для ключів помилок Better Auth, `ROLE_CODES` для ролей.
- Назви середовищ і коди статусу HTTP оголошують один раз, у `src/modules/_core/constants/api.ts`: `ENVIRONMENT.PRODUCTION` у `__root.tsx` і в скриптах розгортання, `HTTP_STATUS.PARTIAL_CONTENT` в обробнику медіа у Worker. Жоден файл не оголошує власної мапи ні для того, ні для іншого. Єдиний виняток — файли плагінів Vite, як-от `src/data/cloudflare.vite.ts`, які порівнюють `mode` з простими назвами: Vite завантажує їх до того, як розв’язує псевдонім `~`, тож вони не можуть імпортувати `api.ts`.
- Константа, яку використовує один файл, залишається в ньому, під імпортами. Константа, яку використовують кілька файлів, переходить до свого модуля, до `src/data` (див. [Файли та іменування](/docs/conventions/files-and-naming)) або до `src/modules/_core/constants`. Ніколи не виділяйте одній константі окремий файл.
- Типізовані назви полів API, як-от `license_key_id`, — це властивості, а не значення, і до них звертаються як до властивостей.

## Хуки в компонентах

Спершу йдуть виклики хуків, що повертають одне значення, потім порожній рядок, потім кожен деструктурований результат хука, тож значення, які компонент розбирає на частини, читаються як окрема група. `src/presentation/components/custom/auth/sign-in-form.tsx`:

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Компонент викликає `useTranslations` один раз і називає результат `t`; чому саме так, пояснено на сторінці [Переклади та контент](/docs/conventions/translations).

## Назви та імпорти

- Файли й папки — у kebab-case; компоненти — у PascalCase; константи — у SCREAMING_SNAKE_CASE; функції починаються з дієслова (`resolveViewer`, `rethrowAsConflict`); булеві значення читаються як запитання (`isPending`, `hasLessonAccess`).
- Імпорти використовують псевдонім `~/src/...` і беруться з файлу, який визначає символ. Немає barrel-файлів, що реекспортують папку; єдиний файл реекспорту — `src/integrations/drizzle-orm/drizzle.schemas.ts`, бо Drizzle потребує всіх таблиць в одному об’єкті схеми.
- Зсув індексу на одиницю пишуть літералом: `lessons[index + 1]` у `course.utils.ts`. Будь-який інший зсув, зокрема `-1`, отримує назву: `groups.at(LAST_GROUP_INDEX)` у `robots.ts`, а не `slice(index, -5)`.
