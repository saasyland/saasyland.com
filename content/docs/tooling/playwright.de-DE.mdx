Playwright testet die gebaute Anwendung in echten Browsern. Die Suite läuft gegen die Wrangler-Umgebung `test`: lokale D1, KV und R2 in `.wrangler/test`, Platzhalter-Zugangsdaten aus `.env.test` und der Test-Einstiegspunkt `src/platform/testing/worker.ts`, der Anfragen an Resend und Polar abfängt.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:journey
```

| Skript             | Führt aus                                                |
| ------------------ | -------------------------------------------------------- |
| `test:e2e:install` | Installiert Chromium und WebKit mit Systemabhängigkeiten |
| `test:e2e`         | Alle Specs in Chromium und WebKit                        |
| `test:e2e:smoke`   | `e2e/specs/smoke.spec.ts` in Chromium                    |
| `test:e2e:pr`      | Alle Specs in Chromium, wie in der CI für Pull Requests  |
| `test:e2e:headed`  | Alle Specs in sichtbaren Browsern                        |
| `test:e2e:ui`      | UI-Modus von Playwright                                  |
| `test:journey`     | Die [Journey-Suite](#journey-suite) gegen Preview        |

## Konfiguration

`playwright.config.ts` führt die Specs in `e2e/specs/` aus, definiert die Projekte `chromium` (Desktop Chrome) und `webkit` (Desktop Safari) und verwendet `PLAYWRIGHT_BASE_URL` oder `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` aus `src/data/local-server.ts`). Lokal führt der Webserver-Befehl `db:reset:test`, `build:test` und `start:test` aus und verwendet einen Server wieder, der unter dieser URL bereits antwortet. In der CI bereitet der Workflow den Build vor, und Playwright startet nur den Server.

## Neben anderen Worktrees ausführen [#running-beside-other-worktrees]

Der Test-Build nimmt Requests nur von den Hosts an, denen er im Testmodus vertraut, weil Better Auth und die Newsletter-Links den Host der Anfrage prüfen: `127.0.0.1:3000` und `localhost:3000` sowie `127.0.0.1` und `localhost` auf den Ports <RepositoryFact name="testServerFirstPort" /> bis <RepositoryFact name="testServerLastPort" />, festgelegt durch `TEST_SERVER_PORTS` in `src/data/local-server.ts`. Auf jedem anderen Port schlagen die Anmelde- und Kursseiten fehl, deshalb bricht `playwright.config.ts` ab, bevor etwas gebaut wird, wenn `PLAYWRIGHT_BASE_URL` einen anderen Host nennt.

`PLAYWRIGHT_BASE_URL` ist die einzige Einstellung, die den Port wählt: Playwright öffnet diese URL und startet `start:test` auf ihrem Port. Wenn andere Worktrees gleichzeitig ihre Suites ausführen, bekommt jeder Worktree einen eigenen Port aus dem Bereich. Prüfe, dass nichts auf ihm lauscht, und führe die Suite dann dort aus:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` gibt nichts aus, wenn der Port frei ist. Gibt es einen Prozess aus, nimm einen anderen Port und lass diesen Server in Ruhe: Beende nur Server, die du selbst gestartet hast.

Lokal verwendet Playwright einen Server wieder, der unter der URL bereits antwortet, und überspringt dann das Zurücksetzen der Datenbank und den Build; die Suite darf also nie den Server eines anderen Worktrees erreichen. `e2e/global-setup.ts` stellt das sicher: Vor dem ersten Test ermittelt es mit `lsof` die Prozesse, die auf dem Port lauschen, und bricht den Lauf ab, wenn einer davon in einem anderen Verzeichnis als diesem Worktree läuft. Ein Server, den du aus diesem Worktree gestartet hast, besteht die Prüfung und wird so wiederverwendet, wie er ist; beende ihn also, wenn die Suite einen frischen Build testen soll.

## Aufbau

- `e2e/specs/`: Specs für Smoke-Checks, die Landingpage und ihre Steuerelemente, Navigation, Sprachen, Theme, SEO, Authentifizierung mit ihren Weiterleitungen und ihrem Routing, Arbeitsbereiche, Benutzerverwaltung, Newsletter, Inhalte, rechtliche Seiten, regionale Preise, Checkout-Funnel, Lizenzseite, CLI-Lizenz-API, Partnerprogramm, Videos, Kurse, Kurszugriff, Kursverwaltung, Footer, Fokusringe, Scrollleisten und Barrierefreiheit (<RepositoryFact name="e2eSpecs" /> Dateien).
- `e2e/pages/`: Page Objects.
- `e2e/fixtures/`: die erweiterte `test`-Fixture, Hilfsfunktionen für abgefangene E-Mails, `deliverPaidOrder` in `license.ts`, das einen signierten `order.paid`-Webhook sendet, um eine Lizenz zu vergeben, `buyLicense`, das beim Test-Worker unter `/__test/polar/purchase` eine Bestellung mit Lizenzschlüssel im Polar-Testdouble anfordert und deren signierte `order.paid` und `benefit_grant.created` sendet, `startedCheckouts`, das die Checkouts, die das Double angelegt hat, aus `/__test/polar/checkouts` liest, `payCheckout`, das einen Checkout, den die App geöffnet hat, über `/__test/polar/pay` des Test-Workers mit angekreuzter Zustimmung bezahlt und die signierten `order.paid` und `benefit_grant.created` seiner Bestellung sendet, und `accessibilityViolations` mit den Farbschemata hell und dunkel in `COLOR_SCHEMES` in `accessibility.ts`.
- `e2e/data/accounts.ts`: die per Seed angelegten Konten, ein Admin und ein Kunde, und ihr Passwort. `e2e/data/licenses.ts` enthält den Kunden mit Lizenz und diese Lizenz sowie für jeden parallelen Worker eine Lizenz, auf der die Spec der CLI-Lizenz-API Geräte aktiviert.
- `e2e/data/videos.ts` und `e2e/data/courses.ts`: das per Seed angelegte Testvideo, dessen Dateien in `e2e/fixtures/video/` liegen, und der per Seed angelegte Kurs: ein Kapitel mit einer kostenlosen Vorschau, einer Kontolektion und zwei bezahlten Lektionen, eine davon ohne Video.
- `e2e/data/<area>.pages.ts` und `e2e/data/<area>.seed.ts`: die Seiten jedes Bereichs, die `accessibility.spec.ts` und `workspaces.spec.ts` besuchen, und seine Zeilen und Medien in der Testdatenbank, zusammengeführt von `pages.entries.ts` und `seed.entries.ts`.
- `e2e/data/<area>.flows.ts`: die Abläufe jedes Bereichs, jeder mit dem Test, der ihn End-to-End beweist, oder dem Grund, warum er fehlt, zusammengeführt von `flows.entries.ts`; siehe [Testabdeckung](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: das globale Setup, das den Lauf abbricht, wenn der Server auf dem Port der Suite aus einem anderen Worktree läuft.
- `e2e/journey/`: die [Journey-Suite](#journey-suite) mit eigener Konfiguration.

Der Test-Worker führt aus, was die Bereiche in `e2e/data/<area>.worker.ts` deklarieren, zusammengeführt von `worker.entries.ts`: Der Lizenzbereich legt die Testlizenzschlüssel im Polar-Double an, Resend stellt `/__test/emails` bereit, um die abgefangenen E-Mails zu lesen, und der Newsletter-Bereich `/__test/newsletter`, um den Status eines Abonnenten abzufragen.

## Barrierefreiheit

`e2e/specs/accessibility.spec.ts` führt [axe-core](https://github.com/dequelabs/axe-core) über `@axe-core/playwright` auf den öffentlichen Seiten, den Kursseiten, der Startseite der Dokumentation, jeder Seite des Abschnitts Konventionen und je einer Seite aus jedem anderen Abschnitt der Dokumentation, einem Blogartikel sowie dem Admin- und dem Kundenbereich im hellen und dunklen Theme aus. Zu den Admin-Seiten gehören `/admin/courses`, `/admin/courses/create` und der Editor des geseedeten Kurses, die auch `e2e/specs/workspaces.spec.ts` besucht. Die Spec prüft die Regeln der Stufen A und AA aus WCAG 2.0, 2.1 und 2.2 sowie die Best Practices von axe, schlägt fehl, wenn eine Seite nicht mit einem Erfolgsstatus lädt, scrollt durch die Seite, damit auch beim Scrollen eingeblendete Abschnitte geprüft werden, wartet, bis endliche Animationen abgeschlossen sind, und schlägt bei jedem Verstoß fehl, mit Regel, Schweregrad und betroffenen Selektoren.

axe sieht weder den Tastaturablauf noch das Layout, deshalb prüfen drei Specs beides für Header und Footer der Website: `e2e/specs/navigation.spec.ts`, dass das Menü auf dem Smartphone den Fokus zu sich holt, Tab darin hält, die Seite dahinter `inert` macht und den Fokus an seine Schaltfläche zurückgibt; `e2e/specs/footer.spec.ts`, dass sich bei 320, 390 und 430 px in keiner Locale zwei Footer-Links berühren oder den Footer verlassen und dass ein Link zu einem Abschnitt der Startseite nur auf seinem eigenen Abschnitt aktuell ist; und `e2e/specs/focus-rings.spec.ts`, dass der Sprachumschalter im Footer und der Trigger der Admin-Befehlspalette ihren Ring für die Tastatur zeichnen.

## Scrollleisten [#scrollbars]

`e2e/specs/scrollbars.spec.ts` startet Chromium ohne Playwrights Schalter `--hide-scrollbars`, über `ignoreDefaultArgs` in `launchOptions`. So zeichnet Chromium klassische Scrollleisten, die Platz einnehmen, wie unter Windows, unter Linux und auf einem Mac, der Scrollleisten immer anzeigt. Die Spec prüft, dass eine rechtliche Seite, eine Auth-Seite und eine Admin-Seite ihre Überschrift an Ort und Stelle halten, wenn das Fenster wächst, bis die Seite nicht mehr scrollt (eine Seite der Dokumentation scrollt immer, weil der Footer der Website auf ihr bildschirmhohes Layout folgt), dass das Öffnen der Suche der Dokumentation, der Sprachauswahl, eines Dialogs oder eines Menüs nichts verschiebt, dass `/admin` das Fenster ausfüllt und dass das Fenster hinter einer dunklen Seite im hellen Theme dunkel ist. WebKit auf macOS zeichnet nur überlagernde Scrollleisten, die keinen Platz einnehmen, und keine Startoption ändert das; die Prüfung des freigehaltenen Platzes läuft deshalb nur in Chromium. Das Website-Menü, das unterhalb von `lg` die Header-Links ersetzt, wird bei 768 px geprüft: Öffnen und Schließen verschieben nichts.

## Journey-Suite [#journey-suite]

`bun run test:journey` kauft eine Lizenz und nutzt die CLI so wie ein Kunde, auf dem Preview-Deployment unter `https://preview.saasyland.com`, das Zahlungen in der Polar-Sandbox abwickelt. `e2e/journey/playwright.config.ts` ist eine eigene Konfiguration mit einem eigenen Chromium-Projekt und ohne Webserver, deshalb führen `test:e2e` und die Prüfungen von Pull Requests sie nie aus, und bisher führt auch kein Workflow sie aus: [Testabdeckung](/docs/tooling/test-coverage#journey-suite) listet auf, was nötig ist, um sie in der CI auszuführen. Jede Stufe ist ein eigener Test, die Tests laufen parallel, und jeder durchläuft diese Schritte:

1. **Konto.** Der Test registriert sich mit einer neuen Adresse des Test-Postfachs von Resend, `delivered+journey-<run>-<tier>@resend.dev`, beim Upgrade-Test mit `upgrade` statt der Stufe, findet die Verifizierungs-E-Mail über die Resend-API und öffnet ihren Link.
2. **Preis.** `/app/license` muss die Stufe zu dem Preis anbieten, der für das Land gilt, in dem Cloudflare den Runner verortet, wie es `/cdn-cgi/trace` meldet: zum regionalen Preis in einem Land aus `PPP_TIERS`, sonst zum vollen Preis.
3. **Checkout.** Der Checkout der Polar-Sandbox muss mit der E-Mail-Adresse des Kontos und nicht angekreuzter Zustimmung zur sofortigen Bereitstellung öffnen; der Test kreuzt sie auf der Seite von Polar an. Der Test bezahlt mit der [Testkarte von Stripe](https://docs.stripe.com/testing) und einer Rechnungsadresse in Polen, wo die Rechnungsadresse nur aus dem Land besteht.
4. **Bestellung und Schlüssel.** Polar muss genau eine bezahlte Bestellung für das Produkt der Stufe führen, zu dem Preis, den `/app/license` angeboten hat, mit der Zustimmung und der Sprache des Käufers, die Kaufbestätigung muss im Posteingang ankommen, und `/app/license` muss den Schlüssel zeigen, den die Webhooks ausgestellt haben, dazu die CLI-Befehle und kein belegtes Gerät.
5. **CLI.** Die veröffentlichte CLI, aufgerufen als <RepositoryFact name="cliExec" /> wie die Befehle auf `/app/license`, spricht über `SAASYLAND_API_URL` mit Preview. `activate` schreibt die Datei mit den Zugangsdaten mit dem Modus `0600`, eine erneute Aktivierung behält denselben Aktivierungsplatz, und `whoami` zeigt das Gerät. CI-Geräte, die `SAASYLAND_CI_REPOSITORY` unterscheidet, belegen die übrigen Plätze, bis zu <ActivationLimit tier="core" /> Geräte bei Core, <ActivationLimit tier="complete" /> bei Complete und <ActivationLimit tier="agency" /> bei Agency, und das nächste wird mit `activationLimitReached` abgewiesen. Sobald auf `/app/license` ein Platz freigegeben ist, bekommt ihn das abgewiesene Gerät, und das freigegebene erhält `activationNotFound`. `deactivate` gibt das erste Gerät frei und entfernt seine Zugangsdaten.
6. **Erstattung.** Der Test erstattet die Bestellung über die API der Polar-Sandbox und wartet, bis `/app/license` die Lizenz als erstattet zeigt; danach muss `whoami` mit `licenseRefunded` antworten und die Zugangsdaten entfernen.

Ein vierter Test stuft eine Lizenz hoch. Er kauft Core auf dieselbe Weise und belegt die <ActivationLimit tier="core" /> Geräte von Core, und das nächste wird abgelehnt. Danach muss `/app/license?tier=complete` Complete zu seinem Preis für das Land des Runners anbieten, abzüglich dessen, was die Core-Bestellung gekostet hat, und der Test bezahlt diese Differenz im Checkout von Polar. Polar muss die Upgrade-Bestellung zur Differenz führen, mit der Core-Bestellung und der Stufe in `upgrade_from_order` und `upgrade_from_tier`; der Schlüssel der Core-Bestellung muss nun die <ActivationLimit tier="complete" /> Geräte von Complete zulassen, der Schlüssel, den Polar für die Upgrade-Bestellung vergeben hat, muss deaktiviert sein, und `/app/license` muss Complete mit demselben Schlüssel zeigen. Danach werden das abgelehnte Gerät und das nächste aktiviert, und das übernächste wird abgelehnt. Der Test erstattet die Upgrade-Bestellung über die API der Polar-Sandbox: Die Lizenz muss wieder Core sein, mit demselben Schlüssel und dem Limit von Core, die bereits aktivierten Geräte arbeiten weiter, und ein neues wird abgelehnt. Eine Erstattung der Core-Bestellung beendet danach die Lizenz.

Jedes CLI-Gerät ist ein Verzeichnis im Ausgabeordner des Tests, das die CLI als Home-Verzeichnis nutzt, und die CLI läuft mit nichts in ihrer Umgebung außer `PATH`, diesem Home-Verzeichnis, einem npm-Cache und den Variablen `SAASYLAND_*`, sodass keine Zugangsdaten der Suite sie erreichen. Eine Bestellung, die ein fehlgeschlagener Test bezahlt hinterlässt, wird am Ende des Tests erstattet. Die Konten bleiben auf Preview, jedes mit einer erstatteten Lizenz.

Die Suite liest diese Werte aus der Umgebung oder aus `.env.preview`, wenn die Datei existiert, und bricht ohne sie vor dem ersten Test ab:

| Variable                                                                        | Wofür                                                                                                                                                                       |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | Lesen und Erstatten der Bestellungen in der Sandbox und Lesen ihrer Lizenzschlüssel, mit den Scopes `orders:read`, `refunds:write`, `benefits:read` und `license_keys:read` |
| `POLAR_SERVER`                                                                  | Muss `sandbox` sein                                                                                                                                                         |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Die Sandbox-Produkte, für die die Bestellungen sein müssen                                                                                                                  |
| `RESEND_API_KEY`                                                                | Lesen der Verifizierungs-E-Mails, die Preview gesendet hat; dafür braucht es einen Schlüssel mit vollem Zugriff                                                             |

Auf Preview muss ein Build mit der [CLI-Lizenz-API](/docs/features/cli-licence-api) laufen: Ein Pull Request deployt seinen Branch im Job **Deploy preview** dorthin. Die Sandbox muss zum Code passen, was `bun run polar:verify:preview` prüft. Dann:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

Der Bericht landet in `playwright-report/journey/`, die Traces, Videos und Geräteverzeichnisse fehlgeschlagener Tests in `test-results/journey/`.
