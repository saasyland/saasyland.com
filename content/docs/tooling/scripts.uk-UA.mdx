---
title: "Скрипти проєкту"
description: "Усі скрипти package.json і те, що вони запускають."
---

Запускайте скрипти з кореня репозиторію командою `bun run <script>`. Скрипти, які викликають Wrangler, а також `db:generate`, що викликає drizzle-kit, запускають їх через `vp exec`, який бере виконуваний файл із `node_modules/.bin`, тож вони завжди використовують версії, зафіксовані в `bun.lock`.

## Розробка та збірка

| Скрипт             | Що запускає                                                                                                                                                                      |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dev`              | `generate:cn`, `content` і `vp dev` у середовищі `development` за адресою http://localhost:3000                                                                                  |
| `build`            | Те саме, що `build:preview`                                                                                                                                                      |
| `build:preview`    | Очищення `dist`, `generate:cn`, `content`, `vp build` для `preview`, `scripts/verify-build.ts preview`, `scripts/optimize-prerendered-html.ts` і `scripts/generate-seo-files.ts` |
| `build:production` | Ті самі кроки для `production`                                                                                                                                                   |
| `build:test`       | Ті самі кроки для середовища `test`                                                                                                                                              |
| `start`            | `vp preview` останньої збірки за адресою http://127.0.0.1:3000                                                                                                                   |
| `start:test`       | `vp preview` тестової збірки                                                                                                                                                     |

`verify-build.ts` перевіряє, що `.wrangler/deploy/config.json` вказує на `dist/server/wrangler.json` і що цей файл розгортає Worker, який `wrangler.jsonc` називає для цього середовища, а потім мову документа, канонічні та альтернативні посилання локалізованих головної і юридичних сторінок, шрифти, те, що псевдоніми локалей і сторінки під непереліченими шляхами розділів не були попередньо відрендерені, те, що кожну сторінку документації та кожен опублікований допис блогу попередньо відрендерено, те, що жоден клієнтський ресурс не імпортує `cloudflare:workers`, те, що статичні імпорти вхідного скрипту браузера не містять loader-функції повідомлень жодного простору імен сторінки, те, що вбудована оплата Polar лежить в одному клієнтському ресурсі, який завантажує лише `import()`, коли покупець починає оплату, а також те, що код, який Worker завантажує під час холодного старту, лишається малим: статичні імпорти `dist/server/index.js` не мають доходити до `@polar-sh`, `drizzle-orm` чи `resend`, а їхній загальний розмір не має перевищувати `BOOT_CLOSURE_MAX_BYTES` (див. [Продуктивність](/docs/conventions/performance)). `optimize-prerendered-html.ts` видаляє підказки `modulepreload` для залежностей з попередньо відрендерених сторінок і залишає підказку для точки входу з низьким пріоритетом. `generate-seo-files.ts` записує `sitemap.xml` і стрічку блогу кожною мовою та рендерить картку для соцмереж для кожної попередньо відрендереної сторінки й логотип організації, усе на основі метаданих самих сторінок; див. [Пошук і попередній перегляд у соцмережах](/docs/features/seo).

## Розгортання

| Скрипт              | Що запускає                                                                                                                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `deploy:preview`    | `scripts/verify-bindings.ts preview`, `scripts/prepare-deploy-secrets.ts preview`, `scripts/run-deploy-checks.ts preview`, `build:preview`, `db:migrate:preview`, `wrangler deploy` для `dist/server/wrangler.json` і `scripts/verify-deployment.ts preview` |
| `deploy:production` | Ті самі кроки для `production`                                                                                                                                                                                                                               |

- `verify-bindings.ts` завершується помилкою, коли середовищу бракує прив'язки, яку оголошує `development` (тут `DB`, `CACHE`, `MEDIA` і `BUNDLES`) чи досі має ідентифікатор-заглушку D1 або KV, а також коли production використовує ту саму базу даних, простір імен або бакет, що й preview.
- `prepare-deploy-secrets.ts` зчитує з `.env.<environment>` ключі, перелічені в `secrets.required` середовища, завершується помилкою, коли якийсь із них відсутній, порожній або є заповнювачем, і записує лише ці ключі в `.wrangler/secrets.<environment>.json`. Заповнювач — це значення в дужках (<RepositoryFact name="secretPlaceholderBrackets" />), як-от `[UPDATE]`, або одне зі слів <RepositoryFact name="secretPlaceholderWords" /> у будь-якому регістрі, з пробілами, дефісами чи підкресленнями або без них. Помилка називає ключі, не виводячи їхніх значень. Назви ключів скрипт бере з `wrangler.jsonc`, тож охоплює секрети всіх розділів, не називаючи жодного з них. Інші змінні з файлу не завантажуються.
- `run-deploy-checks.ts` запускає `bun run <check>:<environment>` для кожної перевірки перед розгортанням, яку розділ оголошує в `src/data/<area>.deploy.ts`, і зупиняє розгортання перед збіркою, якщо якась не проходить. Зараз це `auth:verify` із розділу автентифікації, яка не проходить, якщо <RepositoryFact name="oauthClientIdVariables" /> у `.env.<environment>` не містять ідентифікатора клієнта у форматі свого провайдера (тих самих форматів, які `verify-deployment.ts` застосовує після розгортання), і `polar:verify` із розділу Polar, яка не проходить, коли організація Polar з `.env.<environment>` не відповідає коду.
- Міграції виконуються після збірки й перед розгортанням, тож невдала збірка ніколи не зачіпає базу даних, а новий Worker ніколи не запускається на старішій схемі.
- Розгортання запускає `env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.<environment>.json`. Зібрана конфігурація вже націлена на одне середовище; `CLOUDFLARE_ENV`, що залишився в оболонці, змусив би Wrangler шукати розділ середовища, якого в цьому файлі немає.
- `verify-deployment.ts` надсилає запити до <RepositoryFact name="liveSiteCheckPaths" /> на домені середовища й завершується помилкою, якщо котрийсь із них не відповідає `200` з очікуваним типом вмісту. На <RepositoryFact name="socialSignInPath" /> він, як і браузер, починає вхід через кожного провайдера сторінки входу, <RepositoryFact name="oauthProviderIds" />, і завершується помилкою, якщо отримана URL-адреса авторизації не розташована на хості самого провайдера або не містить `client_id` у форматі цього провайдера й `redirect_uri`, що дорівнює <RepositoryFact name="oauthCallbackPath" /> на тому самому домені. Помилка називає провайдера й проблему, не виводячи значення. Перевірку, що не пройшла, він повторює до <RepositoryFact name="liveSiteCheckRetries" /> разів з інтервалом <RepositoryFact name="liveSiteCheckRetrySeconds" unit="second" /> і не змінює нічого, крім короткочасних стану OAuth і лічильника спроб у D1, які залишає й звичайний клік на кнопці входу. `bun scripts/verify-deployment.ts <preview|production>` окремо перевіряє розгорнутий сайт.

## Генерування та обслуговування

| Скрипт           | Що запускає                                                                                                                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `content`        | `fumadocs-mdx`: генерує `.source/` з `content/`                                                                                                                                                                                                                     |
| `generate:cn`    | Будує таблиці злиття класів у `.source/cn-tables.ts` з `src/lib/cn.config.ts`                                                                                                                                                                                       |
| `cf-typegen`     | `wrangler types` для `development`: перегенеровує `src/types/worker-configuration.d.ts`                                                                                                                                                                             |
| `typegen`        | `cf-typegen`, `generate:cn` і `content`                                                                                                                                                                                                                             |
| `deps:update`    | `scripts/update-dependencies.ts`: `vp migrate` для новішого Vite+, `bun update --latest` для кожної залежності з діапазоном, потім `skills:update`; називає зафіксовані пакети, що мають новіший реліз; див. [Залежності](/docs/conventions/dependencies#upgrading) |
| `skills:sync`    | `scripts/sync-skills.ts`: відновлює навички агентів з `skills-lock.json`                                                                                                                                                                                            |
| `skills:update`  | `scripts/sync-skills.ts update`: переводить кожну навичку агентів із `skills-lock.json` на найновіший коміт джерела, і записує в `skills-packages.json` версії пакетів, які описують навички                                                                        |
| `clean`          | Видаляє `.source`, `.tanstack`, `.wrangler`, `dist`, `coverage`, результати Playwright і `*.tsbuildinfo`                                                                                                                                                            |
| `clean:deep`     | `clean` і `node_modules`                                                                                                                                                                                                                                            |
| `clean:hardcore` | `clean:deep`, `bun.lock` і `skills-lock.json`                                                                                                                                                                                                                       |
| `prepare`        | Запускається під час встановлення: `vp config --no-agent` (Git-хуки), `scripts/verify-git-hooks.ts`, `generate:cn` і `content`                                                                                                                                      |

`clean` видаляє `.wrangler`, зокрема локальні бази даних для розробки й тестів і файли секретів, записані скриптами розгортання, тож спершу експортуйте локальні дані, які хочете зберегти.
