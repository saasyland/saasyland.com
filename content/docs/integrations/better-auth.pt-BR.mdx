O Better Auth armazena usuários, contas, sessões e tokens de verificação no D1 por meio do adaptador do Drizzle. Ele oferece cadastro com e-mail e senha que faz o login de uma conta nova na hora e deixa para depois o que precisa de um endereço confirmado, login com GitHub e Google, redefinição de senha, troca de e-mail, autenticação de dois fatores com TOTP, gerenciamento de usuários pelo administrador e, por meio do plugin da Polar, o portal do cliente e os webhooks da Polar. Os checkouts não fazem parte do Better Auth: quem os cria é `createCheckout` (`src/modules/order/order.checkout.ts`). Sua API HTTP é servida por `src/routes/api/auth.$.ts`. `auth.server.ts` e `auth.client.ts` definem o `basePath` do Better Auth como `ROUTES.API.AUTH.BASE`, o caminho que esse arquivo atende, de modo que o servidor e o cliente do navegador o obtêm de uma única constante.

## Guards de rota

| Guard                | Usado por                        | Comportamento                                                                                          |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `requireSignedIn`    | `/app`                           | Redireciona para o login quando não há sessão, com a página como `redirect`, e retorna a sessão        |
| `requireAdmin`       | `/admin`                         | Também exige a permissão `admin: ["access"]`; caso contrário, redireciona para `/app`                  |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Envia um usuário logado para `redirect` ou, conforme o papel, para `/admin` ou `/app`                  |
| `redirectAfterAuth`  | `/auth/callback`                 | Exige uma sessão e redireciona para `redirect` ou para o workspace correspondente ao papel             |
| `redirectIfVerified` | `/auth/verify-email`             | Envia uma sessão com endereço confirmado para `redirect` ou, conforme o papel, para `/admin` ou `/app` |

Os guards carregam a sessão pelo cache de queries e, quando o usuário logado muda, removem com `removeUserData` de `auth.session.ts` toda query em cache que não seja pública. [Sessões](/docs/features/sessions#cached-data-and-the-signed-in-account) explica como eles sabem de quem são os dados do cache.

## Funções de servidor

Os guards de página protegem apenas a navegação, por isso toda função de servidor protegida verifica o chamador novamente com o middleware de `auth.middleware.ts`:

- `authorized(permission?)` exige uma sessão, verifica opcionalmente uma permissão e adiciona a sessão ao contexto como `context.auth`. Operações sobre os próprios dados do chamador usam `context.auth.user.id`, nunca um ID de usuário vindo do input.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (<RepositoryFact name="sensitiveRateLimit" /> requisições a cada <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) ou `RATE_LIMITS.TOKEN` (<RepositoryFact name="tokenRateLimit" /> a cada <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) limita uma operação pública por IP do cliente, obtido de `cf-connecting-ip`.
- `withRequest`, incluído por ambos, mapeia erros para códigos de `AppError`: erros do Better Auth viram `AUTH_API_ERROR` com sua chave de erro, erros do Zod viram `VALIDATION`, e erros inesperados são registrados em log e retornados como `INTERNAL_ERROR`.

## Papéis e permissões

`auth.roles.ts` define dois papéis: `admin` e `customer` (o padrão para novas contas). `auth.access.ts` define as declarações de cada recurso em `APP_STATEMENTS`: `admin` e `settings` para o console de administração e as suas configurações, `product` para a página de produtos, que lista o catálogo da Polar, e para o módulo de produtos, `category` para os casos de uso do módulo de categorias, que nenhuma tela usa, `course` e `video` para os cursos, e `order` para os pedidos. Ele concede todas aos administradores, que também recebem as declarações de administração do Better Auth, e monta a partir delas o controle de acesso e os papéis. `hasPermission({ permission, role })` é compartilhado por guards, middleware e UI. Veja [Papéis e permissões](/docs/guides/roles-and-permissions).

## Plugins

`plugins`, em `auth.server.ts`, lista todos os plugins do Better Auth, na ordem em que o Better Auth os aplica:

| Plugin                    | O que adiciona                                                                                                                                 |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `admin`                   | A administração de usuários e sessões com `ac` e `ROLES` de `auth.access.ts`                                                                   |
| `twoFactor`               | A autenticação em dois fatores                                                                                                                 |
| `lastLoginMethod`         | O cookie que lembra a última forma de login                                                                                                    |
| `invitationPlugin`        | Os convites (`src/modules/invitation/invitation.plugin.ts`)                                                                                    |
| `haveIBeenPwned`          | A verificação de vazamentos de toda senha nova (`NEW_PASSWORD_PATHS`)                                                                          |
| `password-change-notice`  | `notifyPasswordChange` depois de uma troca de senha                                                                                            |
| `license-retention`       | O hook `user.delete.before` que revoga a licença de uma conta excluída                                                                         |
| `polar`                   | O plugin da Polar com o portal do cliente e os webhooks, que repassam cada evento a `handlePolarEvent` ([Pagamentos](/docs/features/payments)) |
| `polar-verified-customer` | `requireVerifiedEmail` antes de cada endpoint em `/customer/`                                                                                  |
| `tanstackStartCookies`    | Define os cookies do Better Auth nas respostas do TanStack Start, e precisa vir por último                                                     |

Cada plugin está escrito por extenso na lista, então os tipos do Better Auth incluem os campos de usuário e de sessão que cada um adiciona. Um elemento que nomeia um arquivo de uma funcionalidade, como `revokeAccountLicense` ou `polarCore`, sai junto com essa funcionalidade, assim como `[ROUTES.API.AUTH.POLAR.WEBHOOKS]: false` em `rateLimit.customRules`, que mantém as entregas da Polar fora do rate limiter do Better Auth.

## E-mail e rate limits

Os hooks de e-mail chamam diretamente os remetentes dos módulos de verificação, de conta e de usuário, porque a autenticação precisa de e-mail: `sendVerifyEmail`, `sendExistingAccountEmail`, `sendResetPasswordEmail`, `sendPasswordChangedEmail`, `sendDeleteAccountEmail` e `sendChangeEmailConfirmationEmail`. O rate limiter próprio do Better Auth guarda seus contadores na tabela `rate_limit` do D1 sob um prefixo `auth:` por meio de `consumeRateLimit`, de `src/lib/rate-limit.ts`, que usa upserts atômicos e rejeita requisições quando seu armazenamento não está disponível. `clientAddress` em `auth.middleware.ts` resolve o cliente de uma requisição do mesmo jeito que esse rate limiter, a partir de `cf-connecting-ip`, com os endereços IPv6 agrupados por /64. O prefixo dos cookies é `APP_SLUG`, da identidade visual. `getRequestSession` ignora o cache de cookies, então a autorização sempre lê a sessão do D1.
