---
title: "Liste de contrôle de sécurité"
description: "Ce qu'il faut vérifier avant de fusionner un changement qui touche aux routes, aux fonctions serveur, aux données ou aux secrets."
---

Parcourez la liste pour chaque changement qui ajoute une page, une opération, un endpoint ou un secret.

## Accès

- [ ] Les pages privées se trouvent sous un layout protégé : `requireAdmin` (`/admin`) ou `requireSignedIn` (`/app`) dans `beforeLoad`.
- [ ] Chaque fonction serveur protégée a `authorized(permission)` ou `authorized()`. Le garde de route ne protège pas l'appel RPC.
- [ ] Les opérations sur les données de l'appelant prennent l'utilisateur dans `context.auth.user.id`, jamais dans l'entrée.
- [ ] Les nouvelles permissions figurent dans `APP_STATEMENTS` et ne sont attribuées qu'aux rôles qui en ont besoin.
- [ ] Les tests couvrent `UNAUTHORIZED` et `FORBIDDEN`.

## Entrées

- [ ] Chaque fonction serveur a un `.validator` qui analyse le schéma Zod du module.
- [ ] Les handlers d'API valident leur query et leur corps avant de les utiliser.
- [ ] Les cibles de redirection sont des chemins internes construits avec `localizePathname` ; `callbackPathSchema` dans `auth.zod.ts` n'accepte que des chemins commençant par un seul `/`, et l'inscription comme le changement d'e-mail l'utilisent pour `callbackURL`.
- [ ] Les règles des formulaires s’appliquent aussi aux endpoints de Better Auth : ajoutez un schéma à `INPUT_POLICY` dans `auth.hooks.ts` pour chaque endpoint qui accepte un mot de passe, un nom, un e-mail ou une image.

## Abus

- [ ] Les opérations publiques qui envoient un e-mail, vérifient un code ou consomment un jeton utilisent `withRateLimit` avec `RATE_LIMITS.SENSITIVE` ou `RATE_LIMITS.TOKEN`.
- [ ] Les e-mails qu’un visiteur peut déclencher sans compte (vérification, réinitialisation du mot de passe, confirmation de la newsletter) vérifient `withinRecipientRateLimit` avant l’envoi : au plus trois par type, par adresse et par heure, comptés sous un hash de l’adresse. Au-delà, la requête reçoit sa réponse habituelle et rien n’est envoyé.
- [ ] Le limiteur stocke les compteurs dans D1 par opération et par IP cliente (`cf-connecting-ip`) et rejette la requête lorsque son stockage est indisponible. Les endpoints propres à Better Auth utilisent le même stockage.
- [ ] Les e-mails sont envoyés avec une clé d'idempotence.

## Erreurs

- [ ] Les échecs attendus lèvent un `AppError` avec un code de `ERROR_CODES`.
- [ ] Rien d'autre n'atteint le client : `withRequest` journalise les erreurs inconnues et les remplace par `INTERNAL_ERROR`.
- [ ] Les composants affichent les erreurs via `useErrorMessage`, jamais via le `error.message` brut.

## Secrets et code réservé au serveur

- [ ] Les secrets sont lus depuis `env` dans `cloudflare:workers` uniquement par du code serveur : modules exclusivement serveur, handlers de fonctions serveur et utilitaires importés uniquement par eux. `scripts/verify-build.ts` fait échouer le build lorsqu'une ressource client importe `cloudflare:workers`.
- [ ] Aucune valeur privée n'a de préfixe `VITE_`, qui l'exposerait au navigateur.
- [ ] Les données de session envoyées au client proviennent de `getCurrentSession`, qui retire le jeton de session.

## Sessions et cookies

Ces réglages se trouvent dans `auth.server.ts` ; conservez-les lorsque vous modifiez la configuration :

- [ ] `requireEmailVerification: true` et `revokeSessionsOnPasswordReset: true`.
- [ ] `useSecureCookies` hors des modes locaux et `baseURL.allowedHosts` limité aux hôtes de l'environnement.
- [ ] `encryptOAuthTokens: true` et `verification.storeIdentifier: "hashed"`.
- [ ] La connexion et la déconnexion vident le cache des queries, et les gardes le vident lorsque l'utilisateur change.

## Webhooks et sortie

- [ ] Les webhooks vérifient leur signature avant de traiter le contenu ; Polar utilise `POLAR_WEBHOOK_SECRET`.
- [ ] Les pages privées et celles qui consomment des jetons restent hors du prérendu : `/admin`, `/app`, `/auth`, `/newsletter` et `/api` sont exclus.
- [ ] Les liens à jeton n’agissent qu’après une action explicite, jamais dans un loader : les pages de confirmation et de désinscription de la newsletter demandent avant d’agir.
- [ ] Les réponses conservent les en-têtes de sécurité : `src/server.ts` ajoute `SECURITY_HEADERS`, et `Strict-Transport-Security` en HTTPS, sauf si la réponse définit les siens, et `public/_headers` couvre les fichiers servis sans le Worker. Une route qui définit elle-même l'un de ces en-têtes ne doit pas l'affaiblir.
