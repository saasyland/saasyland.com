---
title: "Współtworzenie"
description: "Jak proponować zmiany w SaaSy Land."
---

1. Większe zmiany najpierw omów w zgłoszeniu otwartym z formularza błędu lub propozycji funkcji.
2. Utwórz gałąź od `main`.
3. Trzymaj się [konwencji](/docs/conventions) i [architektury](/docs/architecture), a przed zmianą integracji z dostawcą przeczytaj odpowiednią [umiejętność agenta](/docs/tooling/agent-skills). Agenci AI piszący kod zaczynają od `AGENTS.md` w katalogu głównym repozytorium.
4. Trzymaj testy obok kodu, który testują, i nie schodź poniżej progu pokrycia <RepositoryFact name="coverageThreshold" unit="percent" />.
5. Uruchom poniższe kontrole.
6. Utwórz commit z komunikatem w formacie [konwencjonalnego commita](/docs/tooling/conventional-commits), otwórz pull request z tytułem w tym samym formacie i wypełnij jego szablon.
7. Zrób rebase gałęzi na `main`, gdy jest z nim w konflikcie, i nigdy nie scalaj do niej `main`, jak opisuje strona [Git i pull requesty](/docs/conventions/git-workflow#linear-history). Opiekun projektu umieszcza zielony pull request w [kolejce scalania](/docs/conventions/git-workflow#merging), która testuje go ponownie na aktualnym `main` i scala.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`build:test` uruchamia pełny build Cloudflare, którego nie sprawdzają ani `check`, ani testy jednostkowe. Ostatnie polecenie buduje i uruchamia testowego Workera, jeśli żaden serwer nie działa, a następnie wykonuje w Chromium wskazane specyfikacje: uruchom te, które obejmują zmieniony kod. CI uruchamia wszystkie specyfikacje w Chromium i w WebKit na pull requeście i ponownie w kolejce scalania, a pull request zostaje scalony tylko wtedy, gdy obie przeglądarki przejdą; `bun run test:e2e:pr` uruchamia lokalnie cały zestaw w Chromium. Przy zmianach, które mogą działać inaczej w WebKit, uruchom go także w nim (`bun run test:e2e`). Gdy zmieniasz konfigurację prawdziwych integracji z dostawcami, sprawdź je osobno.

Gdy zmienia się zachowanie aplikacji, zaktualizuj `content/docs` w każdym języku; `bun run check:content` odrzuca brakujące tłumaczenia oraz różnice w blokach kodu i nawigacji. Szablon pull requesta zawiera podsumowanie, plan testów z powyższymi kontrolami i listę zaktualizowanej dokumentacji; opisz w nim wynikowe zachowanie, sposób weryfikacji oraz wszelkie przepływy, które zmiana pozostawia niedokończone. Ekran panelu administracyjnego trafia do projektu tylko z prawdziwym źródłem swoich danych (zobacz [Panel administracyjny](/docs/features/admin-dashboard#real-data-only)).

`CONTRIBUTING.md` w katalogu głównym repozytorium to skrócona wersja tej strony, a `SUPPORT.md` wskazuje, gdzie szukać pomocy. Wszyscy uczestnicy przestrzegają `CODE_OF_CONDUCT.md`, czyli Contributor Covenant 2.1. Luki w zabezpieczeniach zgłaszaj poufnie, tak jak opisuje to `SECURITY.md`, nigdy w publicznym zgłoszeniu.
