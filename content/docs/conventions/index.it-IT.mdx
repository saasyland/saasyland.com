Queste pagine sono lo standard di codifica di questo repository. Descrivono come si scrive il codice qui, non come si potrebbe scrivere, e ogni regola indica i file che la seguono. La maggior parte delle regole è imposta da un comando: `bun run check` (formattazione, lint, tipi, traduzioni e struttura della documentazione), `bun run test:coverage` (la soglia del 100%) o la suite end-to-end. Le altre vengono fatte rispettare in revisione, e ogni pagina indica quali.

Quando non sai bene come scrivere qualcosa, trova l'esempio esistente più vicino dello stesso tipo, leggilo e riprendine la forma. La coerenza vale più di un'idea migliore solo in un punto: un secondo modo di fare la stessa cosa costringe ogni lettore successivo, umano o agente, a impararli entrambi.

## Implementazione di riferimento

La funzionalità dei corsi è il codice più recente del repository e la forma da copiare. Comprende un modulo di tabella, route pubbliche e di amministrazione, form, finestre di dialogo, una tabella dati, scheletri di caricamento e test.

| Tipo                                 | Da copiare da                                                          |
| ------------------------------------ | ---------------------------------------------------------------------- |
| Modulo di tabella                    | `src/modules/course/`, con `chapter`, `lesson` e `video` accanto       |
| Lettura con opzioni di query         | `src/modules/course/use-cases/get-course-editor.ts`                    |
| Elenco paginato per una tabella      | `src/modules/course/use-cases/get-courses.ts`                          |
| Mutation con opzioni di mutation     | `src/modules/course/use-cases/update-course.ts`                        |
| Route di layout                      | `src/routes/admin.courses.tsx`                                         |
| Route di pagina con una tabella dati | `src/routes/admin.courses.index.tsx`                                   |
| Route di pagina con un parametro     | `src/routes/admin.courses.$courseId.tsx`                               |
| Form                                 | `src/presentation/components/custom/admin/courses/course-form.tsx`     |
| Finestra di dialogo con un form      | `src/presentation/components/custom/admin/courses/chapter-dialog.tsx`  |
| Colonne della tabella                | `src/presentation/components/custom/admin/courses/course-columns.tsx`  |
| Scheletri delle route                | `src/presentation/components/custom/admin/content-pending.tsx`         |
| Test delle server function           | `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts` |
| Test nel browser                     | `e2e/specs/course-admin.spec.ts`                                       |

## Regole senza eccezioni

Violarne una basta a far rifiutare una modifica, qualunque altra cosa faccia bene.

1. Nessun commento nel codice, nei test, negli script, nella configurazione o nel CSS. Vedi [Stile del codice](/docs/conventions/code-style).
2. Nessun `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, cast con `as` o `any` per aggirare una regola. Correggi la causa.
3. Nessun ternario su più righe e nessun `?? undefined`. Fuori dai test e da `src/platform/testing`, `null` compare solo dove lo impone un'API: nel confronto con un valore che può essere `null` e in un ref DOM di React (`useRef<HTMLElement>(null)`). Vedi [Stile del codice](/docs/conventions/code-style).
4. Stati, tipologie, piani, ruoli e gli altri valori di dominio sono costanti con un nome, mai letterali stringa ripetuti, anche nei test. I test dello schema sono l'unico posto in cui un valore memorizzato si scrive per esteso. Vedi [Test](/docs/conventions/testing).
5. Una cartella in `src/modules` esiste solo per una tabella del database. Vedi [Moduli](/docs/conventions/modules).
6. Ogni stringa visibile all'utente esiste in tutti e nove i locale, e lo stesso vale per ogni pagina della documentazione. I numeri mostrati sul sito sono misurati o dichiarati una sola volta in `src/data`, mai scritti a mano. Vedi [Traduzioni e contenuti](/docs/conventions/translations).
7. La copertura resta al 100% per righe, istruzioni, funzioni e branch. Vedi [Test](/docs/conventions/testing).
8. Una modifica aggiorna, nella stessa pull request, il README, la documentazione e i testi del sito che rende inesatti.
9. Commit e pull request non riportano alcuna attribuzione all'IA né il trailer `Co-Authored-By`. Vedi [Git e pull request](/docs/conventions/git-workflow).

## Criteri di completamento

Una modifica è completa quando questi comandi passano, in quest'ordine, sul branch che stai per pubblicare con push:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` e i test non mettono alla prova la build di Cloudflare: una volta un aggiornamento di una dipendenza li ha superati entrambi mentre la build di produzione era rotta. Esegui `build:test` per ogni modifica, e la suite nel browser per tutto ciò che non è documentazione. Prima del commit, rileggi il tuo diff cercando commenti, letterali stringa che dovrebbero essere costanti, e testi o documentazione che la modifica ha reso sbagliati.
