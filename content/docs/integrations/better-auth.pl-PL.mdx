Better Auth przechowuje użytkowników, konta, sesje i tokeny weryfikacyjne w D1 za pośrednictwem adaptera Drizzle. Zapewnia rejestrację e-mailem i hasłem z obowiązkową weryfikacją adresu e-mail, logowanie przez GitHub i Google, reset hasła, zmianę adresu e-mail, uwierzytelnianie dwuskładnikowe TOTP, zarządzanie użytkownikami przez administratora oraz płatności Polar. Jego API HTTP obsługuje `src/routes/api/auth.$.ts`.

## Pliki

| Plik                                                   | Odpowiedzialność                                                                                                                                          |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth.server.ts`                                       | Instancja `betterAuth`: dostawcy, pluginy `admin`, `twoFactor`, Polar i `tanstackStartCookies`, dozwolone hosty, limitowanie żądań w D1 i hooki e-mailowe |
| `auth.client.ts`                                       | `authClient` i jego metody (`signIn`, `signUp`, `signOut`, `useSession`, `twoFactor` i inne)                                                              |
| `auth.routes.ts`                                       | Strażnicy tras dla `beforeLoad`                                                                                                                           |
| `auth.middleware.ts`                                   | Middleware funkcji serwerowych: `withRequest`, `authorized`, `withRateLimit` i `RATE_LIMITS`                                                              |
| `auth.access.ts`                                       | Role, deklaracje uprawnień i `hasPermission`                                                                                                              |
| `auth.session.ts`                                      | `getRequestSession`, funkcja serwerowa `getCurrentSession` i `getCurrentSessionQuery`                                                                     |
| `auth.errors.ts`, `auth.zod.ts`, `auth.constraints.ts` | Klucze błędów, schematy formularzy i ograniczenia haseł                                                                                                   |

## Strażnicy tras

| Strażnik             | Używany przez                    | Działanie                                                                                    |
| -------------------- | -------------------------------- | -------------------------------------------------------------------------------------------- |
| `requireSignedIn`    | `/app`                           | Bez sesji przekierowuje do logowania, a w przeciwnym razie zwraca sesję                      |
| `requireAdmin`       | `/admin`                         | Dodatkowo wymaga uprawnienia `admin: ["access"]`, w przeciwnym razie przekierowuje do `/app` |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Kieruje zalogowanego użytkownika do `/admin` lub `/app` w zależności od roli                 |
| `redirectAfterAuth`  | `/auth/callback`                 | Wymaga sesji, a następnie przekierowuje do obszaru roboczego odpowiedniego dla roli          |

Strażnicy ładują sesję przez cache zapytań i czyszczą ten cache, gdy zmienia się zalogowany użytkownik.

## Funkcje serwerowe

Strażnicy stron chronią wyłącznie nawigację, dlatego każda chroniona funkcja serwerowa ponownie sprawdza wywołującego za pomocą middleware z `auth.middleware.ts`:

- `authorized(permission?)` wymaga sesji, opcjonalnie sprawdza uprawnienie i dodaje sesję do kontekstu jako `context.auth`. Operacje na własnych danych wywołującego używają `context.auth.user.id`, nigdy identyfikatora użytkownika z danych wejściowych.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (3 żądania na 60 sekund) lub `RATE_LIMITS.TOKEN` (5 na 60 sekund) ogranicza operację publiczną dla każdego adresu IP klienta pobranego z `cf-connecting-ip`.
- `withRequest`, zawarte w obu powyższych, mapuje błędy na kody `AppError`: błędy Better Auth stają się `AUTH_API_ERROR` z własnym kluczem błędu, błędy Zod stają się `VALIDATION`, a nieoczekiwane błędy są logowane i zwracane jako `INTERNAL_ERROR`.

## Role i uprawnienia

`auth.access.ts` definiuje dwie role: `admin` i `customer` (domyślna dla nowych kont). Deklaracje uprawnień aplikacji obejmują `admin`, `category`, `order`, `product` i `settings`; rola administratora otrzymuje dodatkowo administracyjne deklaracje Better Auth. Z `hasPermission({ permission, role })` korzystają wspólnie strażnicy, middleware i interfejs użytkownika.

## E-mail i limity żądań

Hooki e-mailowe w `auth.server.ts` wywołują przypadki użycia: `sendVerifyEmail`, `sendResetPasswordEmail` i `sendChangeEmailConfirmationEmail`. Wbudowany limiter Better Auth przechowuje liczniki w tabeli D1 `rate_limit` za pośrednictwem `authRateLimitStorage` z `src/lib/rate-limit.ts`, który korzysta z atomowych upsertów i odrzuca żądania, gdy magazyn jest niedostępny. `getRequestSession` pomija cache ciasteczka, więc autoryzacja zawsze odczytuje sesję z D1.
