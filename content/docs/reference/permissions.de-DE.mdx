Jeder Bereich deklariert seine Berechtigungs-Statements und die Rollen, denen er sie gewährt, in `src/data/<area>.access.ts`, und `src/integrations/better-auth/auth.access.ts` baut daraus die Zugriffskontrolle von Better Auth und die Rollen auf (siehe [Rollen und Berechtigungen](/docs/guides/roles-and-permissions)). Dieselben Definitionen nutzen sowohl der Server (`authorized`, Route-Guards) als auch der Better-Auth-Client.

## Rollen

| Rolle | Code       | Berechtigungen                                                                                                                                           |
| ----- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin | `admin`    | Alle unten aufgeführten Anwendungs-Statements, die jeder Bereich den Admins gewährt, sowie die Admin-Statements von Better Auth für `user` und `session` |
| Kunde | `customer` | Keine. Kunden können Server Functions aufrufen, die nur eine Session verlangen.                                                                          |

Neue Nutzer erhalten `customer` (`DEFAULT_ROLE_CODE` in `auth.roles.ts`).

## Eine Berechtigung prüfen

Server Functions verwenden die Middleware, zum Beispiel `authorized({ category: ["read"] })`. Anderer Code ruft `hasPermission` auf, so wie die Route-Guards:

```ts
const isAdmin = (role: string | null | undefined): boolean => hasPermission({ permission: { admin: ["access"] }, role })

export const requireAdmin = async (context: ProtectedRouteContext) => {
  const result = await requireSignedIn(context)
  if (!isAdmin(result.session.user.role)) {
    throw redirect({ replace: true, to: ROUTES.APP })
  }
  return result
}
```
