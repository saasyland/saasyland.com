`src/integrations/resend/resend.config.ts` tworzy klienta Resend z `RESEND_API_KEY`. `resend.utils.ts` eksportuje `sendEmail`, jedyną funkcję wysyłającą e-maile. `from` domyślnie przyjmuje wartość `RESEND_EMAIL_FROM`, wymagana opcja `idempotency` podaje cel wiadomości i token, który ją wywołał, a `sendEmail` tworzy z nich klucz `<purpose>/<SHA-256 tokenu>`, który chroni przed dwukrotnym wysłaniem ponowionego żądania przez Resend i mieści się w limicie 256 znaków, a błąd Resend jest rzucany dalej. Oba pliki działają wyłącznie na serwerze. `resend.constants.ts` nazywa każdy cel w `EMAIL_PURPOSE`, a przypadki użycia przekazują tę samą nazwę jako `kind` limitu na odbiorcę.

## Szablony i przypadki użycia

Szablony w `src/presentation/emails/` to komponenty React Email zawierające wyłącznie znaczniki. Każdy eksportuje stałą `*_NAMESPACE`, otrzymuje `locale` i `messages` jako propsy i tłumaczy za pomocą `createTranslator` z use-intl. Przypadek użycia, który wysyła e-mail, otrzymuje język od wywołującego (e-mail weryfikacyjny odczytuje go z adresu zwrotnego), ładuje komunikaty, renderuje szablon i wywołuje `sendEmail`:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await sendEmail({
  idempotency: { purpose: EMAIL_PURPOSE.VERIFY_EMAIL, token },
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

| Szablon                               | Przestrzeń nazw                          | Wysyłany przez                                                               |
| ------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------- |
| `verify-email.tsx`                    | `emails.verify-email`                    | `modules/verification/use-cases/send-verify-email.ts`                        |
| `reset-password-email.tsx`            | `emails.reset-password-email`            | `modules/verification/use-cases/send-reset-password-email.ts`                |
| `change-email-confirmation-email.tsx` | `emails.change-email-confirmation-email` | `modules/account/use-cases/send-change-email-confirmation-email.ts`          |
| `newsletter-confirmation-email.tsx`   | `emails.newsletter-confirmation-email`   | `modules/newsletter-subscriber/use-cases/subscribe-to-newsletter.ts`         |
| `newsletter-notification-email.tsx`   | `emails.newsletter-notification-email`   | `modules/newsletter-subscriber/use-cases/confirm-newsletter-subscription.ts` |

Better Auth wywołuje pierwsze trzy przypadki użycia ze swoich hooków w `auth.server.ts`. Po potwierdzeniu subskrypcji powiadomienie o newsletterze trafia do właściciela serwisu w języku angielskim. Linki w e-mailach są budowane za pomocą `localizePathname`, więc otwierają się w języku e-maila.

Przypadki użycia weryfikacji, resetu hasła i potwierdzenia newslettera najpierw wywołują `withinRecipientRateLimit` z `src/lib/rate-limit.ts`: limit e-maili każdego rodzaju na adres na godzinę wynosi <RepositoryFact name="recipientEmailsPerHour" />, z kluczem w postaci skrótu SHA-256 adresu. Powyżej limitu pomijają e-mail bez zgłaszania błędu.

## Testy

Vitest mockuje wywołania dostawców. W testowym Workerze Playwright żądania do API Resend są przechwytywane zamiast wysyłane, a `/__test/emails?to=<address>` zwraca przechwycone e-maile.
