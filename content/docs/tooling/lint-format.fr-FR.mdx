---
title: "Lint et formatage"
description: "oxlint et oxfmt via Vite+, et les scripts de vérification."
---

Vite+ exécute oxfmt pour le formatage et oxlint pour le lint, tous deux configurés dans les sections `fmt` et `lint` de `vite.config.ts`. `bun run check` est le contrôle exécuté par la CI :

```sh
bun run check
```

Il exécute `generate:cn`, `check:comments`, `check:i18n`, `check:flows` et `vp check`, qui vérifie le formatage, applique les règles de lint et vérifie les types du projet. Utilisez `bun run lint`, `bun run format` et `bun run format:check` pour un seul outil à la fois.

## Formatage

- Pas de points-virgules, guillemets doubles, virgules finales, indentation de <RepositoryFact name="tabWidth" /> espaces, largeur de ligne de <RepositoryFact name="printWidth" /> et fins de ligne LF.
- Les imports sont triés en groupes fixes : server-only, `cloudflare:workers`, React, paquets externes, puis les zones de `~/src` (platform, providers, integrations, modules, routes, hooks, données et thème, types, lib, branding, composants shadcn, composants custom, styles), puis les imports relatifs.
- Les classes Tailwind sont triées dans `className` et dans les appels à `cn`, `cva`, `clsx` et `tw`.

## Lint

- Les catégories `correctness`, `nursery`, `pedantic`, `perf`, `style` et `suspicious` sont des erreurs.
- Les règles tenant compte des types et la vérification des types sont activées (`typeAware` et `typeCheck`).
- Limites notables : <RepositoryFact name="maxLines" /> lignes par fichier, <RepositoryFact name="maxLinesPerFunction" /> lignes par fonction, <RepositoryFact name="maxStatements" /> instructions par fonction, aucun nombre magique autre que `0` et `1`, aucun `any` explicite (`typescript/no-explicit-any`), et des identifiants d'au moins deux caractères, sauf `_`, `m` et `t`.
- Des surcharges assouplissent quelques règles pour les tests, le code de présentation et les hooks, les mocks de test et les fichiers de route.
- `jsPlugins` charge les plugins oxlint propres au dépôt : `scripts/code-style-lint-plugin.ts`, dont les règles `code-style/no-comments`, `code-style/no-multiline-ternary`, `code-style/no-undefined-branch`, `code-style/no-undefined-fallback` et `code-style/zod-namespace-import` font échouer chaque commentaire, chaque ternaire réparti sur plusieurs lignes, chaque ternaire dont une branche vaut `undefined` ou `null`, chaque `return undefined` et chaque `?? undefined`, ainsi que chaque import de Zod autre que `import * as zod from "zod"` (voir [Style de code](/docs/conventions/code-style)), `scripts/hydration-lint-plugin.ts`, dont la règle `hydration/no-clock-or-locale-in-render` empêche le code de rendu de lire l’horloge ou la locale de l’environnement d’exécution (voir [Style de code](/docs/conventions/code-style)), `scripts/admin-data-lint-plugin.ts`, dont la règle `admin-data/no-literal-data` tient les données de démonstration hors du code de l’administration (voir [Tableau de bord d’administration](/docs/features/admin-dashboard#real-data-only)), et `scripts/radius-lint-plugin.ts`, dont la règle `radius/no-off-scale` garde chaque coin sur l’échelle des rayons (voir [Thème](/docs/ui/theme#corner-radius)). `scripts/type-lint-plugin.ts` ajoute `type/no-off-scale` et `type/mono-for-code`, qui gardent chaque taille de texte sur l’échelle typographique et la police à chasse fixe pour le code (voir [Thème](/docs/ui/theme#type-scale)).
- Les échappatoires sont interdites nommément : `typescript/ban-ts-comment` rejette `@ts-expect-error`, `@ts-ignore` et `@ts-nocheck` même accompagnés d’une description, `typescript/consistent-type-assertions` avec `assertionStyle: "never"` rejette toute assertion de type sauf `as const`, et `respectEslintDisableDirectives: false` fait qu’un commentaire `eslint-disable` ne désactive rien. `code-style/no-comments` remplace `capitalized-comments`, `no-inline-comments` et `no-warning-comments`, que les catégories activent et dont chacune ne voyait qu’une partie des commentaires ; ces trois règles sont donc désactivées.

Les deux outils ignorent les fichiers générés et externes : fichiers de déclaration, `src/routeTree.gen.ts`, migrations, `.source`, `dist`, `coverage`, `e2e`, `remotion`, les dossiers des agents et la sortie de Playwright. `scripts/` est formaté et linté comme `src/`. `bun run check:comments` lit aussi ce que le linter ignore : `e2e`, `remotion`, les fichiers de déclaration et les feuilles de style.

Le formateur trie aussi `package.json`, y compris ses `scripts` par ordre alphabétique (`sortPackageJson: { sortScripts: true }`), donc `vp check` échoue quand un script n'est pas à sa place.

Corrigez la cause d'une erreur de lint. N'ajoutez pas de commentaires de désactivation, de `@ts-expect-error` ni de conversions `as` pour satisfaire une règle. Un commentaire de désactivation est un commentaire, et le linter lui obéit avant qu'aucune règle ne le voie ; c'est pourquoi `bun run check:comments`, qui s'exécute en dehors du linter, le fait échouer où qu'il se trouve.

## Corrections

Le hook de pre-commit exécute `bun run check:pre-commit` ; son étape `vp staged` exécute `vp check --fix` uniquement sur les fichiers indexés. `bun run check:fix` applique les corrections à tout le dépôt et peut réécrire des fichiers que vous n'avez pas touchés : relisez donc son diff avant de committer. Pour ne corriger que vos propres modifications, passez leurs chemins à `vp` (la CLI Vite+ globale, ou `bunx vp`) :

```sh
vp fmt src/routes/admin.users.all.tsx
vp lint --fix src/routes/admin.users.all.tsx
```
