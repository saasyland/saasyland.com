## En bref

Traitez la publication comme la seule étape qui n’est pas une fusion. Tout ce qui précède le registre peut être automatisé et relancé : le versionnage à partir des changesets, la construction, l’empaquetage unique, l’exécution du programme construit sur chaque plateforme que vous prenez en charge, le téléversement de tout ce que la CLI téléchargera. L’étape irréversible, l’apparition d’une version sur npm, reçoit une seconde clé qu’aucun workflow ne détient. Mettez la version en attente depuis la CI avec le trusted publishing de npm, qui utilise un jeton OIDC à courte durée de vie au lieu d’un jeton stocké, et faites approuver la version en attente par un mainteneur avec l’authentification à deux facteurs. Épinglez par son contenu tout ce que la CLI récupère à l’exécution, et vérifiez-le auprès de deux sources. Ne créez les tags Git et les GitHub Releases qu’une fois que npm sert la version, car une version en attente peut ne jamais être publiée. Et méfiez-vous des moments où un outil de publication décide, selon ses propres règles, qu’il n’y a rien à faire : un changeset vide a un jour empêché l’une de nos bêtas d’être mise en attente, alors que tous les jobs étaient au vert.

## Pourquoi une publication n’est pas une fusion

Une fusion peut être annulée par une autre fusion. Une publication, non, pour trois raisons.

**Le numéro de version est consommé.** La politique de dépublication de npm est sans détour : « Une fois que `package@version` a été utilisé, vous ne pouvez plus jamais l’utiliser. » Elle ajoute : « C’est vrai même si ce paquet a été dépublié. » La dépublication elle-même n’est permise pendant les 72 premières heures que si aucun autre paquet du registre ne dépend du vôtre, et ensuite seulement à des conditions plus strictes ; pour tout le reste, npm recommande la dépréciation. On corrige une mauvaise version en publiant la suivante, et la mauvaise reste dans le registre pour tous ceux qui l’ont épinglée.

**Les clients écrivent des scripts qui en dépendent.** L’interface publique d’une CLI est plus étendue que les exports d’une bibliothèque : ses commandes, ses options et leurs valeurs par défaut, ses codes de sortie, sa sortie lisible par une machine, les fichiers qu’elle écrit et les runtimes sur lesquels elle démarre. Une valeur par défaut modifiée ou un nouveau code de sortie casse un job de CI que vous ne verrez jamais.

**Une CLI payante a plusieurs rouages.** La nôtre vérifie la licence auprès de saasyland.com chaque fois qu’elle crée un projet, et télécharge les modèles à partir desquels elle génère, un bundle par version, par l’API de licence du site. Une publication, c’est un paquet sur npm, plus un bundle de modèles dans un stockage, plus un contrat avec un serveur. Les trois doivent concorder dès la première minute où un client peut installer la version.

Les agents IA déplacent le risque. Ils sont rapides et minutieux sur les parties réversibles : écrire les changesets, tenir à jour une pull request de version, modifier les workflows, rédiger les notes de version en <RepositoryFact name="languages" /> langues, vérifier le registre après coup. Sur la partie irréversible, ils sont exactement aussi sûrs d’eux que sur tout le reste. Le principe de conception de cet article est donc simple : laissez les agents tout faire jusqu’au registre, faites en sorte que chaque étape qui le précède puisse tourner deux fois sans danger, et confiez à un humain la clé de la seule étape qui n’est ni réversible ni répétable.

Un mot sur notre organisation, pour que vous puissiez la transposer à la vôtre. La CLI SaaSy Land se compose de trois paquets npm, `saasyland`, `create-saasyland` et `@saasyland/stack`, publiés depuis un dépôt GitHub privé avec Changesets 3 et GitHub Actions. Au 25 novembre 2026, les préversions sortent sur le tag <RepositoryFact name="cliReleaseChannel" /> de npm, la dernière étant 0.1.0-beta.5 du 20 novembre, et les clients lancent <RepositoryFact name="cliPackageSpec" /> ; `latest` contient toujours la version provisoire `0.0.0` qui a réservé les noms. Les agents sont des sessions Claude Code, un agent principal et les exécutants dont il rédige les briefs, et ils prennent la CLI en charge de bout en bout. Quand le propriétaire la leur a confiée, il a demandé « le versionnage, le journal des modifications et tout le reste, aussi professionnels que possible », publiés « par lots vraiment cohérents ». Il approuve chaque publication.

## Le pipeline en un coup d’œil

Chaque ligne est une étape de la publication, avec ce qu’elle peut écrire et ce qui l’arrête. La suite de l’article reprend les lignes dans l’ordre où elles peuvent échouer.

| ---------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Pull request                 | La CI sous Linux et une vérification des changesets                                    | Rien en dehors de la pull request                 | N’importe quelle vérification, ou un paquet publié modifié sans changeset                                    |
| Pull request de version      | `changeset version`, puis l’épinglage des modèles                                      | Sa propre branche et sa pull request              | Une personne qui relit et trouve une mauvaise montée de version ou une note qu’un client ne comprendrait pas |

## Un versionnage sur lequel un client peut compter

### Définissez ce qu’est un changement incompatible pour une CLI

Le versionnage sémantique n’aide que si vous avez écrit noir sur blanc ce qu’est votre interface publique. Notre politique de publication liste ce qui compte comme un changement incompatible pour la CLI :

- une commande, une option ou une valeur d’option supprimée ou renommée, ou une valeur par défaut modifiée ;
- un code de sortie différent pour la même situation ;
- un champ de la sortie `--json` supprimé, renommé ou dont le type change, alors qu’un nouveau champ n’est pas un changement incompatible ;
- une modification du manifeste du projet qu’une CLI plus ancienne ne sait pas lire ;
- une version minimale de Node plus élevée ;
- un export du paquet partagé supprimé ou modifié ;
- une modification que les propres règles de l’API de licence qualifient d’incompatible.

Avant la 1.0, une version mineure apporte de nouvelles fonctionnalités ou un changement incompatible, et un patch n’apporte que des corrections. L’API de licence applique la même discipline de son côté. Dans `v1`, le site peut ajouter un champ de réponse, un endpoint ou un code d’erreur, et la CLI ignore les champs qu’elle ne connaît pas ; tout le reste exige une `v2` servie à côté de `v1` aussi longtemps qu’une CLI prise en charge l’appelle. [Le premier article de cette série](/blog/ai-coding-agent-guardrails) raconte comment une CLI publiée envoyait un champ que le site en production n’acceptait pas encore, et pourquoi une modification de contrat est désormais livrée d’abord sur le serveur.

### Un changeset est une note de version destinée aux clients

Chaque pull request qui modifie un paquet publié ajoute un changeset, et la CI refuse celle qui ne le fait pas : `changeset status --since=origin/<base>` échoue lorsqu’un paquet a changé sans changeset. La règle qui compte le plus porte sur le contenu. Un changeset, c’est la note de version que lit le client : une ou deux phrases simples sur ce qui change pour lui et ce qu’il doit faire, avec les commandes et les options écrites telles qu’il les tape. « Correction d’un bug dans l’analyseur d’options » n’apprend rien à un client. Voici la note de la 0.1.0-beta.5, telle que l’affichent les [notes de version](/docs/cli/releases) publiques :

> **Changement incompatible :** `--billing lemonsqueezy` disparaît, car Lemon Squeezy ferme : il n’accepte plus de nouvelles inscriptions depuis le 16 novembre 2026 et fermera le 31 mars 2027. `--billing polar` et `--billing stripe` restent des valeurs que `--billing` connaît, et `init` refuse toujours l’une comme l’autre avec le code <RepositoryFact name="cliExitNotAvailable" />, car les projets générés n’ont pas encore de facturation. `init --billing lemonsqueezy` se termine désormais avec le code <RepositoryFact name="cliExitUsage" />, comme toute autre valeur que `--billing` ne connaît pas.

La façon dont la règle est écrite décide de ce que produisent les agents. Si on lui dit seulement d’« ajouter un changeset », un agent a tendance à écrire « Refactorisation de l’analyseur d’options ». Si on lui dit que le changeset est ce qu’un client lit dans le journal des modifications, il écrit la note ci-dessus. Une modification que les clients ne peuvent pas remarquer, comme une refactorisation ou un nouveau test, reçoit un changeset vide. Cette échappatoire est à l’origine du second incident de cet article.

### Une seule version pour des paquets livrés ensemble

Les trois paquets forment un groupe fixe de Changesets, dans lequel « tous les paquets du groupe changeront de version et seront publiés ensemble, même s’ils n’ont aucune modification ». Ainsi, `saasyland@0.1.0-beta.5` sort toujours avec `@saasyland/stack@0.1.0-beta.5`, et un client, un rapport de bug et une réponse du support n’ont besoin que d’un seul numéro. Le coût se voit dans le journal des modifications : un paquet qui n’a rien à dire de son côté reçoit quand même une version, et les notes de version de notre site affichent pour lui « Aucun changement dans cette version. » plutôt que de laisser un vide qui ressemblerait à un oubli.

### Publier par lots, et retenir la pull request de version

Changesets garde ouverte une pull request « Version Packages » et la reconstruit à mesure que des changesets sont fusionnés. Cette pull request est le point de contrôle de la publication : la fusionner, c’est décider de publier. Nous publions par lots cohérents, jamais une version par pull request. Sur `main`, la pull request « Version Packages » de 0.1.0 est ouverte depuis le 14 novembre et contenait 24 changesets le 25 novembre ; elle sera fusionnée quand le lot stable sera complet et documenté.

Les préversions sortent d’une branche `beta`, dans le mode préversion (pre mode) de Changesets. Sa documentation prévient que « les préversions sont très compliquées ! » et que « des erreurs peuvent conduire à des états du dépôt et de la publication très difficiles à réparer ». Les deux phrases se sont vérifiées chez nous, comme vous allez le voir. Si vous utilisez le mode préversion, gardez-le sur une branche à part, gardez l’historique de cette branche linéaire pour que les tags de version pointent dans un historique lisible, et faites entrer les modifications de `main` d’une manière que vous pouvez relire. Nous appliquons les commits de `main` par cherry-pick sur une branche créée à partir de `beta`, puis nous la fusionnons par squash, si bien que `beta` ne reçoit jamais de commit de fusion.

### Le README sur npm fait partie de la publication

Jusqu’à la première version stable, `latest` est la version provisoire : un README qui indique `npx saasyland init` lance donc la version provisoire, où aucune commande ne fonctionne. Dans la 0.1.0-beta.1, les README empaquetés faisaient exactement cela, et les commandes `create` sans tag se résolvaient elles aussi vers `latest`. Un smoke test lit désormais le README de chaque tarball empaqueté et échoue quand une commande nomme l’un des paquets sans le dist-tag, ou avec un autre. Le dist-tag qu’attendent les tests est déclaré une seule fois, et le changer fait partie des étapes de la première version stable. Le [guide de la CLI](/docs/cli) du site affiche ses commandes à partir d’une seule constante, <RepositoryFact name="cliPackageSpec" />, pour la même raison.

## Le staged publishing : c’est au registre qu’un humain tient la clé

### Ce qu’est la mise en attente

Le staged publishing de npm « ajoute une étape d’approbation avant que les paquets ne soient mis en ligne sur le registre npm ». La CI lance `npm stage publish`, qui « ne nécessite pas de 2FA », et la version attend dans une zone d’attente jusqu’à ce qu’un mainteneur l’approuve : « La vérification 2FA vous sera demandée, que vous approuviez le paquet dans la CLI ou sur npmjs.com. » Rejeter une version en attente exige aussi le second facteur. Le dist-tag est fixé au moment de la mise en attente : « Le tag est une propriété immuable du paquet en attente. » La mise en attente nécessite npm 11.15.0 ou une version ultérieure ; notre job de mise en attente utilise le npm fourni avec Node 26.13.1, c’est-à-dire npm 11.20.0, et affiche dans son résumé la version de npm qu’il a utilisée pour la mise en attente.

npm pousse tout le monde dans cette direction. Son journal des modifications de septembre 2026 indique que « npm vise janvier 2027 pour supprimer la publication directe au moyen de jetons qui contournent la 2FA », et propose des jetons limités à la mise en attente comme voie de migration pour l’automatisation qui ne peut pas encore passer au trusted publishing. Nos exécutions de mise en attente consignent l’avertissement de npm : « Les jetons npm qui contournent la 2FA sont restreints pour les modifications de compte et la publication directe. »

### Pourquoi le point de contrôle est chez npm et non dans la CI

GitHub peut faire attendre un job jusqu’à l’accord d’une personne grâce aux environnements, et le guide de Changesets suggère de « créer un environnement avec des relecteurs obligatoires pour approuver l’exécution du job de publication ». Nous avons préféré placer la clé chez npm, pour deux raisons. Elle protège l’irréversible lui-même : quoi que fasse un workflow, et quoi que fusionne un agent, rien n’est public tant qu’un mainteneur n’a pas approuvé la version exacte qui est en attente. Et elle repose sur le second facteur npm du mainteneur, qu’aucun workflow, aucun agent ni aucun jeton GitHub ne peut détenir. Une approbation dans la CI protège un job, et une fois qu’elle est donnée, ce job peut publier tout ce qu’il a construit. GitHub ne propose d’ailleurs les relecteurs obligatoires sur les dépôts privés que dans ses offres Enterprise : pour beaucoup d’équipes, le registre est donc le seul endroit où un tel point de contrôle est disponible.

### Changesets ne sait pas encore mettre en attente : mettez en attente à partir de son plan

Le guide de Changesets est explicite : « Pour le moment, le staged publishing ne fonctionne pas avec Changesets : utilisez plutôt le trusted publishing pour l’instant. » L’annonce de sa v3 indique que la mise en attente arrivera avec « la prochaine mise à jour fonctionnelle ». D’ici là, son action de publication lance `npm publish`, que npm refuse à un trusted publisher autorisé uniquement à mettre en attente. Notre job de mise en attente fait donc ce que ferait l’action, avec une seule commande changée. Il lit le plan de publication que `changeset pack` écrit à côté des tarballs et met chaque paquet en attente avec l’accès et le dist-tag qu’a choisis Changesets : `beta` en mode préversion, `latest` sinon.

Pour chaque paquet de ce plan, le job demande d’abord à npm, au moyen d’un `npm view` public qui n’a besoin d’aucun identifiant, si cette version exacte est déjà servie. Si ce n’est pas le cas, il lance `npm stage publish` sur le tarball empaqueté avec l’accès et le dist-tag du plan et l’option `--json`, puis lit l’identifiant de mise en attente dans la réponse de npm. Chaque paquet aboutit à une seule des trois issues ci-dessous, ce qui permet de relancer le job sans danger. Et c’est important, car un job de publication est justement celui qu’on veut le plus relancer quand un runner tombe en panne :

- **Déjà sur npm :** ignoré. Un push sur `main` après une publication, ou une relance, ne tente pas de publier deux fois.
- **Mis en attente par une exécution précédente :** npm répond par une erreur 409, et le job le signale puis continue. Un jeton de trusted publishing peut mettre en attente et publier, mais npm précise que « les jetons à courte durée de vie ne peuvent pas exécuter les sous-commandes de `npm stage` » : le job ne peut donc pas lister les versions en attente pour retrouver l’identifiant précédent, et son résumé indique à la personne qui approuve où chercher.
- **Tout autre cas :** le job s’arrête avant le paquet suivant.

Le résumé du job est la liste de travail de la personne qui approuve : une ligne par paquet, avec sa version, son dist-tag, son identifiant de mise en attente et la commande exacte qui l’approuve. Les trois paquets forment une seule version : ils sont donc approuvés tous les trois ensemble. Le kit de publication à la fin de cet article contient une version générique de ce job, écrite d’après la documentation de npm, pour un dépôt sans Changesets.

### Ce que le registre enregistre

Pour la 0.1.0-beta.5, les métadonnées de npm désignent GitHub Actions comme éditeur, par l’intermédiaire d’un trusted publisher, et nomment le mainteneur qui l’a approuvée. Elle a été mise en attente à 11:25 UTC le 20 novembre et est devenue publique à 11:44. Cet enregistrement constitue la piste d’audit : quel workflow a produit les octets, et quelle personne les a laissés sortir.

## Le trusted publishing : aucun jeton à laisser fuiter

### Des identifiants à courte durée de vie, sur un seul job

Le trusted publishing permet à la CI de publier « au moyen de jetons à courte durée de vie, signés cryptographiquement », obtenus par l’OIDC du fournisseur de CI au lieu d’un jeton npm stocké. Il nécessite npm 11.5.1 et Node 22.14.0 ou des versions ultérieures, et sur GitHub, « l’exigence essentielle est la permission id-token: write ». Côté npm, un trusted publisher nomme l’organisation ou l’utilisateur GitHub, le dépôt, le fichier de workflow et, facultativement, un environnement. Deux réglages supplémentaires ferment les portes restantes :

- **Le trusted publisher peut mettre en attente, et rien d’autre.** Avec la CLI de npm, c’est `npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish`, sans `--allow-publish`. Pour un trusted publisher, indique la documentation de npm, « `npm stage publish` est toujours autorisé », alors que la publication directe et les modifications de dist-tags sont des options distinctes, désactivées tant qu’un mainteneur ne les active pas.
- **L’accès en publication exige l’authentification à deux facteurs et refuse les jetons.** npm note que ce réglage « ne concerne que l’authentification traditionnelle par jeton » : le trusted publisher continue donc de fonctionner, alors qu’aucun jeton, où qu’il soit stocké, ne peut publier.

Un trusted publisher se configure dans les réglages d’un paquet sur npmjs.com : un nouveau nom de paquet coûte donc une étape manuelle. Le propriétaire publie à la main une version provisoire `0.0.0`, avec l’authentification à deux facteurs, puis ajoute le trusted publisher et le réglage d’accès. C’est pourquoi `latest` contient aujourd’hui `0.0.0`.

Côté GitHub, le workflow commence par `permissions: {}`, et chaque job demande ce dont il a besoin. Le guide de Changesets le dit sans détour : « assurez-vous que `id-token: write` n’est défini que sur le job qui doit publier ».

| Job                                          | Permissions                                                     | Pourquoi                                                             |
| -------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------- |
| Sélection du mode de publication             | `contents: read`                                                | Lit les changesets en attente                                        |
| Ouverture de la pull request de version      | `contents`, `pull-requests` et `actions` en écriture            | Pousse la branche de publication, ouvre la pull request, lance sa CI |
| Construction, vérification et empaquetage    | `contents: read`                                                | Construit, teste et empaquette                                       |
| Exécution des binaires construits, neuf jobs | `contents: read`                                                | Construit et lance les binaires                                      |
| Mise en attente sur npm                      | `contents: read` et `id-token: write`, un environnement protégé | Échange un jeton OIDC avec npm et téléverse le bundle de modèles     |
| Création des tags et des Releases            | `contents: write`                                               | Crée les tags et les Releases                                        |

Le job de mise en attente est le seul autorisé à demander un jeton OIDC, et le seul à utiliser l’environnement protégé. Cet environnement contient les identifiants du stockage des modèles, et seules les branches de publication peuvent y déployer. GitHub rend les secrets d’environnement « disponibles uniquement pour les jobs de workflow qui utilisent l’environnement » : aucun autre job, et aucune exécution de workflow lancée depuis une autre branche, ne peut donc les lire.

### Le jeton du checkout est aussi une permission

`actions/checkout` conserve le jeton du job dans la configuration Git locale « pour exécuter des commandes git authentifiées », sauf si vous définissez `persist-credentials: false`. Nous l’avions mis à false dans chaque job, et la première pull request « Version Packages » ne s’est jamais ouverte : quand Changesets a poussé la branche de publication, Git a répondu « could not read Username for 'https://github.com' ». Le correctif a rendu le jeton à ce seul job, le seul qui pousse. Le moindre privilège est une propriété de chaque job, pas un réglage recopié d’un bout à l’autre d’un fichier.

### L’échec que npm ne savait pas expliquer

La première bêta a atteint npm douze heures après la fusion de sa pull request de version. Le 14 novembre à 06:18 UTC, le job de mise en attente a échoué avec l’erreur propre à npm :

```text
npm error code ENEEDAUTH
npm error need auth This command requires you to be logged in to https://registry.npmjs.org/
```

Le message vous dit de vous connecter. La vraie raison était l’échec de l’échange du jeton OIDC, et npm écrit cette raison au niveau verbose, dans un journal de débogage sur le runner qui est supprimé avec le job. Nous avons fait téléverser `~/.npm/_logs/` comme artefact par le job de mise en attente chaque fois qu’il échoue, et le journal de l’échec suivant a nommé la cause : npm n’avait trouvé aucun trusted publisher correspondant au dépôt, au workflow et à l’environnement de l’exécution. La documentation de npm met précisément en garde contre ce cas : « npm ne vérifie pas la configuration de votre trusted publisher lorsque vous l’enregistrez », et « tous les champs sont sensibles à la casse et doivent être exacts ». Une fois les réglages de npmjs.com alignés sur le workflow, une relance du job en échec a mis la 0.1.0-beta.0 en attente à 18:24, et le propriétaire l’a approuvée quatre minutes plus tard.

La leçon dépasse npm. Quand une couche d’authentification échoue, son message d’erreur décrit généralement la solution de repli qu’elle a tentée en dernier, pas l’étape qui a échoué en premier. Conservez le journal de débogage de l’outil pour chaque job de publication en échec, avec une courte durée de rétention, et lisez-le avant de changer quoi que ce soit.

### La provenance exige un dépôt public

Sur un dépôt public, le trusted publishing vous donne la provenance gratuitement : npm « génère et publie automatiquement des attestations de provenance », mais seulement si deux conditions sont réunies, « publier depuis un dépôt public » et « publier un paquet public », et « la génération de la provenance n’est pas prise en charge pour les dépôts privés ». Notre CLI est commerciale et son dépôt est privé : ses paquets ne portent donc aucune attestation de provenance. Ce qu’ils portent, c’est la signature du registre npm, que chacun peut vérifier : dans un répertoire propre où `saasyland@0.1.0-beta.5` est installé, `npm audit signatures` affiche « 1 package has a verified registry signature ». Si votre code source est public, activez la provenance et expliquez à vos utilisateurs comment la vérifier. S’il est privé, dites-le, plutôt que de laisser « trusted publishing » suggérer une garantie que vous n’avez pas.

## Épinglez tout ce que la CLI télécharge

### Les modèles font partie de la version, mais pas du paquet

`saasyland init` génère un projet à partir de modèles qu’il n’embarque pas. Après la vérification de la licence, il télécharge le bundle de modèles de sa propre version par l’API de licence du site. Cela garde les modèles payants hors d’un tarball npm public, et cela donne à chaque version un second artefact dont npm ne sait rien. Deux règles en découlent : le bundle qu’obtient un client doit être exactement celui avec lequel la version a été testée, et il doit exister avant que quiconque puisse installer la version.

### L’empreinte du contenu, pas de la compression

Le bundle est construit de façon déterministe : les couches triées par identifiant, les fichiers par chemin, les clés dans un ordre fixe, et rien n’est repris du système de fichiers hormis le contenu de chaque fichier et son bit d’exécution. Son empreinte est le SHA-256 du JSON contenu dans l’archive, et non des octets gzip, car Node et Bun compressent le même JSON en octets différents. Quand nous l’avons mesuré, les empreintes des archives différaient, celles du contenu non. Une empreinte du fichier compressé identifie un compresseur ; elle casserait la première fois qu’un runtime mettrait à jour son zlib, et on dirait à un client que son téléchargement est corrompu.

### Épingler au versionnage, vérifier avant le téléversement, téléverser avant la mise en attente

L’empreinte est épinglée dans la pull request « Version Packages ». Le script de version lance `changeset version`, puis construit le bundle de la nouvelle version et ajoute son empreinte à un fichier d’empreintes épinglées dans la CLI : la personne qui relit voit ainsi la montée de version et l’empreinte côte à côte, et la version porte l’empreinte dans son propre code. L’épinglage refuse de modifier une empreinte déjà épinglée. Chaque CLI porte aussi les empreintes de toutes les versions précédentes, car `update`, quand cette commande arrivera, régénérera la version à partir de laquelle un projet a été créé pour s’en servir comme base de sa fusion.

Au moment de la publication, le job de mise en attente reconstruit le bundle et échoue si son empreinte n’est pas celle qui est épinglée. Il téléverse ensuite l’archive, avec l’empreinte dans les métadonnées de l’objet, vers le stockage que lit l’API de licence, et relit chaque objet : sa taille, son type de contenu, ses métadonnées et l’empreinte de son contenu. Ce n’est qu’ensuite qu’il met quoi que ce soit en attente sur npm, car une CLI publiée ne doit jamais demander un bundle qui n’existe pas. Le téléversement refuse toute archive qui n’est pas le bundle épinglé : une relance ne peut donc jamais changer ce que sert une version.

### Vérifier deux fois, auprès de deux sources

Le site répond à une requête de bundle avec une URL signée à courte durée de vie, valable <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, ainsi qu’avec la taille et l’empreinte du bundle, qu’il lit dans l’en-tête de l’objet stocké sans ouvrir l’archive :

```ts title="src/modules/license/license.api.ts"
const storedBundle = async (version: string): Promise<StoredBundle> => {
  const key = bundleObjectKey(version)
  const object = await env.BUNDLES.head(key)

  if (object === null) {
    return { error: { code: API_ERROR.VERSION_NOT_FOUND, version }, success: false }
  }

  const metadata = bundleMetadataSchema.safeParse(object.customMetadata)

  if (!metadata.success) {
    throw new Error(`${key} has no ${BUNDLE_METADATA.SHA256} digest in its custom metadata`, { cause: metadata.error })
  }

  return { bundle: { sha256: metadata.data[BUNDLE_METADATA.SHA256], size: object.size }, success: true }
}
```

Un objet sans empreinte n’est pas servi : l’API répond `serviceUnavailable`, et le journal nomme l’objet. La CLI télécharge ensuite l’archive, ne lit pas plus que la taille annoncée, et la refuse si sa taille et son empreinte ne correspondent pas à la réponse de l’API, ou si l’empreinte diffère de celle qui est compilée dans la version. En cas de différence, la CLI se termine avec le code <RepositoryFact name="cliExitProtocol" /> sans rien écrire ; même un téléchargement valide est écrit d’un seul coup dans le répertoire du projet, si bien qu’une exécution interrompue ne laisse rien derrière elle.

Pourquoi les deux vérifications ? L’empreinte de l’API protège le téléchargement. L’empreinte épinglée protège la version contre son propre serveur : quoi qu’il y ait dans le stockage sous la clé d’une version, une CLI publiée n’exécute que les modèles avec lesquels sa version a été testée. Chaque source vérifie l’autre, et aucune ne fait foi à elle seule. La documentation du site décrit en détail l’endpoint et les règles de publication des bundles, dans [API de licence de la CLI](/docs/features/cli-licence-api#publishing-bundles).

### La règle générale

Tout ce que votre CLI récupère à l’exécution, qu’il s’agisse de modèles, de schémas, de binaires ou d’une liste de plugins, fait partie de la version. Versionnez-le avec la publication, épinglez-le par son contenu dans le code que vous publiez, téléversez-le avant que le paquet puisse être installé, et conservez chacune de ses versions qu’une version encore prise en charge peut demander.

## Construire une fois, puis tester ce que vous livrez

### Empaqueter une fois, mettre en attente ces octets-là

Le job d’empaquetage lance les vérifications de formatage, de lint et de types, les tests à couverture complète et les smoke tests, puis `changeset pack` écrit les tarballs et le plan de publication dans un artefact. Le job de mise en attente télécharge cet artefact ; il ne construit jamais rien. Les octets que npm met en attente sont ceux qu’a produits ce job.

### Un outil d’empaquetage qui laissait fuiter la syntaxe du workspace

La 0.1.0-beta.1 est parue sur npm avec des spécificateurs `catalog:` dans les `devDependencies` des trois paquets, six entrées en tout, comme le registre le montre encore. Un workspace Bun écrit les versions partagées sous la forme `catalog:`. Changesets 3 n’empaquette qu’avec npm, pnpm ou Yarn, et dans un workspace Bun il se rabattait sur `npm pack`, qui recopie ces spécificateurs tels quels, non résolus, dans le `package.json` empaqueté. Rien n’a échoué, car personne n’installe les dépendances de développement d’une CLI. La même fuite dans `dependencies` aurait cassé chaque installation de la version.

La correction à la racine embarque un correctif de Changesets appliqué avec `bun patch`, qui empaquette avec `bun pm pack` ; celui-ci écrit la version vers laquelle se résout chaque spécificateur et refuse d’empaqueter un spécificateur qu’il ne sait pas résoudre. Ce correctif est la moitié consacrée à l’empaquetage d’une pull request amont encore ouverte qui ajoute Bun à Changesets, [changesets/changesets#2334](https://github.com/changesets/changesets/pull/2334), et il disparaîtra quand une version inclura cette modification. Ce qui garantit que le problème reste corrigé, c’est un test : les smoke tests empaquettent chaque paquet publié avec la commande qu’utilise la publication et échouent sur tout `catalog:` ou `workspace:` resté dans un champ de dépendances. Testez le tarball, pas le workspace. Les fonctionnalités de workspace de votre gestionnaire de paquets sont invisibles pour un test qui s’exécute depuis les sources.

### Conditionner la mise en attente à la réussite sur chaque plateforme

Les clients lancent la CLI sous Node et Bun, sur Linux, macOS et Windows. Les pull requests n’exécutent le programme construit que sous Linux, pour économiser des minutes ; l’exécution de publication vérifie chaque plateforme, sur le commit exact qu’elle s’apprête à mettre en attente. Neuf jobs construisent les paquets et lancent les binaires sous Node 22.12.0, 24 et 26 sur chaque système, et sous Bun sur chaque runner.

Les neuf jobs forment une seule matrice, trois systèmes croisés avec trois versions de Node, à partir de la plus ancienne version de Node que la CLI prend en charge. Deux réglages font de cette matrice un point de contrôle. Le job de mise en attente liste à la fois le job d’empaquetage et la matrice sous `needs` et n’a pas de `if:` propre : GitHub l’ignore donc si l’un d’eux n’a pas réussi, et une condition comme `if: always()` sur le job de mise en attente annulerait discrètement cette garantie. Et la matrice définit `fail-fast: false` : l’échec d’un job de la matrice n’annule pas les autres, et l’exécution montre chaque plateforme en échec, au lieu de la seule première.

Un point de contrôle que vous n’avez jamais vu échouer est un espoir, pas un point de contrôle. Avant de faire confiance à celui-ci, nous avons lancé le vrai workflow de publication sur une branche temporaire, depuis un commit équivalent à une pull request « Version Packages » fusionnée, avec un job de la matrice volontairement mis en échec : Windows sous Node 26. Tous les autres jobs ont réussi, et le job de mise en attente a été ignoré dès que le dernier job de la matrice s’est terminé. La sonde n’aurait pas pu publier même si le point de contrôle avait été défaillant, car l’environnement dont a besoin le job de mise en attente ne se déploie que depuis les branches de publication ; ensuite, npm listait les mêmes versions qu’avant, et aucun tag ni aucune Release n’était apparu.

Déplacer les exécutions macOS et Windows de chaque fusion vers la publication elle-même a réduit d’un tiers à la moitié les minutes facturables d’une fusion dans `main`, selon la mesure que nous avons faite lors du changement, pour un coût payé une fois par publication. Ce que ce point de contrôle ne fait pas figure vers la fin de cet article : il exécute `--version` et `--help`, pas une génération complète de projet, et il construit sur chaque runner au lieu d’installer le tarball mis en attente.

## N’enregistrer une version qu’une fois qu’elle existe

### 0.1.0-beta.3, jamais publiée

Notre premier workflow de publication créait les tags Git et les GitHub Releases juste après la mise en attente. La raison en était que npm n’offre à un workflow aucun événement sur lequel se déclencher quand un mainteneur approuve une version en attente. Les tags apparaissaient donc quand une version était mise en attente, et non quand elle était publiée. L’historique des publications montre ce que cela signifiait, en UTC :

| Version      | Pull request de version fusionnée | GitHub Releases créées | Servie par npm     |
| ------------ | --------------------------------- | ---------------------- | ------------------ |
| 0.1.0-beta.0 | 14 novembre, 06:17                | 14 novembre, 18:24     | 14 novembre, 18:28 |
| 0.1.0-beta.1 | 14 novembre, 18:38                | 14 novembre, 18:40     | 14 novembre, 23:08 |
| 0.1.0-beta.2 | 15 novembre, 22:52                | 15 novembre, 22:55     | 15 novembre, 23:32 |
| 0.1.0-beta.3 | 17 novembre, 14:23                | 17 novembre, 14:26     | Jamais             |
| 0.1.0-beta.4 | 20 novembre, 09:49                | 20 novembre, 09:51     | 20 novembre, 10:11 |
| 0.1.0-beta.5 | 20 novembre, 11:18                | 20 novembre, 11:45     | 20 novembre, 11:44 |

La 0.1.0-beta.3 a été mise en attente le 17 novembre et attendait toujours son approbation trois jours plus tard, quand la bêta suivante, qui reprenait toutes ses modifications plus une, a été créée et mise en attente. Le propriétaire a approuvé la 0.1.0-beta.4. La 0.1.0-beta.3 n’a jamais atteint npm, et `npm view saasyland versions` liste 0.1.0-beta.2 puis 0.1.0-beta.4. Le dépôt, lui, avait trois tags et trois GitHub Releases pour cette version, qui décrivaient des paquets que personne ne pouvait installer. Même pour les quatre bêtas qui ont atteint npm de cette façon, les Releases sont arrivées en premier, avec une avance de quatre minutes à quatre heures et demie. Le workflow avait raison sur tout, sauf sur la seule chose qu’il ne pouvait pas savoir : si une personne approuverait, et quand.

### Interroger npm, puis créer les tags

Nous avons déplacé les tags et les Releases dans un job distinct qui interroge d’abord le registre. Pour chaque paquet publié, il vérifie trois choses : que le `CHANGELOG.md` du paquet contient une section pour la version extraite, ce que seule une pull request « Version Packages » écrit ; que npm sert exactement cette version, au moyen d’un `npm view` public qui n’a besoin d’aucun jeton ; et si le tag existe déjà. C’est seulement quand chaque paquet passe les deux premières vérifications et qu’un tag manque qu’il lance `changeset git-tag` par l’action Changesets, qui pousse les tags et crée une Release à partir de chaque entrée du journal des modifications. Sinon, il n’écrit rien, et son résumé dit pourquoi.

Les deux vérifications sont volontairement simples. Une version ne compte comme servie que si `npm view` affiche exactement cette version : une version absente, une erreur réseau et une réponse inattendue comptent donc toutes comme non servies, et aucun tag n’est créé. Un tag ne compte comme présent que si Git résout sa référence complète : une branche du même nom ne peut donc pas passer pour lui. Le kit de publication à la fin de cet article contient une version générique de cette vérification pour un seul paquet.

Le job s’exécute de trois manières : juste après la mise en attente, où il trouve généralement la version encore en attente ; à la main, ce que fait l’agent principal dès que le propriétaire a approuvé ; et une fois par jour, en filet de sécurité. Ses exécutions sur une même branche partagent un groupe de concurrence et font la queue au lieu de se chevaucher, si bien que deux exécutions ne créent jamais de tags en même temps, et il récupère d’abord tous les tags : il ne crée donc que ce qui manque et peut tourner autant de fois que nécessaire.

La 0.1.0-beta.5 a été la première version à passer par lui. Dans son exécution de publication, le job des tags et des Releases a tourné à 11:25 UTC et a constaté que la version n’était pas encore servie. npm l’a servie à 11:44:37 ; l’agent principal a lancé le workflow des tags et des Releases à 11:45:27, et les trois Releases sont apparues à 11:45:51.

### Une planification est un filet de sécurité, pas une étape

Le filet de sécurité quotidien nous a appris deux choses sur l’événement `schedule` de GitHub. D’abord, « les workflows planifiés s’exécutent sur le dernier commit de la branche par défaut », alors que les tags d’une bêta doivent pointer vers un commit de `beta`. Le job planifié ne crée donc lui-même aucun tag : il lit les branches dans le déclencheur du workflow de publication et lance sur chacune le workflow des tags et des Releases avec `workflow_dispatch`, pour que chaque exécution crée les tags de sa propre branche. Ensuite, la planification est approximative. GitHub indique que l’événement « peut être retardé pendant les périodes de forte charge » et que « certains jobs en file d’attente peuvent être abandonnés ». Le nôtre est réglé tôt le matin, heure UTC, et du 21 au 24 novembre, il a démarré avec environ huit à onze heures de retard. Un job planifié peut rattraper ce qu’une personne a oublié. Il ne doit jamais être l’étape qu’attend une publication.

### Signalez ce qui n’a jamais été livré

Les tags et les Releases de la 0.1.0-beta.3 restent où ils sont : les supprimer effacerait la trace de ce qui a été construit et mis en attente. À la place, le journal des modifications de chaque paquet indique désormais, sous son titre 0.1.0-beta.3 : « Non publiée sur npm : 0.1.0-beta.4 a remplacé cette version avant son approbation, et toutes les modifications ci-dessous sont livrées dans 0.1.0-beta.4. » Les trois GitHub Releases portent la mention « (not published) », c’est-à-dire « non publiée », dans leur titre, et les [notes de version](/docs/cli/releases) du site disent la même chose. La politique s’est aussi enrichie d’une règle : approuver ou rejeter une version en attente avant que la pull request « Version Packages » suivante soit fusionnée.

## Le changeset vide qui a bloqué une publication

[Le premier article de cette série](/blog/ai-coding-agent-guardrails) raconte brièvement cet épisode, comme l’exemple d’un agent qui respecte une vérification à la lettre. Voici la séquence complète, parce qu’elle montre une catégorie d’échecs facile à manquer : un outil de publication qui décide, à juste titre selon ses propres règles, qu’il n’y a rien à faire.

### Trois fusions en 81 secondes

Tout s’est passé sur `beta` le 20 novembre, en UTC :

1. **11:17:12.** Une pull request a apporté deux commits de `main`. Son exécution de publication a ouvert la pull request « Version Packages » de la 0.1.0-beta.5.
2. **11:18:06.** Une pull request qui ajoutait la mention « Non publiée sur npm » aux trois journaux des modifications a été fusionnée. Une modification du journal des modifications compte comme une modification du paquet : la vérification des changesets a donc exigé un changeset, et la pull request en a ajouté un vide, exactement comme la politique de publication le prescrivait pour une modification que les clients ne peuvent pas remarquer.
3. **11:18:33.** La pull request de version a été fusionnée, 27 secondes plus tard. Elle avait été construite avant la fusion de la correction du journal des modifications : elle n’avait donc pas consommé le changeset vide.
4. **11:19.** L’exécution de publication sur ce commit de fusion a sélectionné son mode et ignoré tous les autres jobs. La 0.1.0-beta.5 était versionnée sur `beta` sans être mise en attente, et tous les jobs étaient au vert.

Entre-temps, l’exécution de publication du commit de fusion de la correction du journal des modifications, en file d’attente derrière les autres, a ouvert une seconde pull request « Version Packages » à partir d’un commit déjà dépassé ; elle a été fermée sans être fusionnée.

### Pourquoi le mode était « none »

`changesets/action/select-mode` renvoie l’un de trois modes : version, publish ou none. Voici la décision dans son code source public en v2.1.2, avec la mise en forme de ce site :

```ts
if (changesets.length > 0) {
  const hasNonEmptyChangesets = changesets.some((changeset) => changeset.releases.length > 0)
  if (hasNonEmptyChangesets) {
    return { mode: "version" }
  }
  return { mode: "none" }
}
```

Si un changeset est en attente et que tous sont vides, le mode est `none`, et le plan de publication, qui aurait constaté que la 0.1.0-beta.5 manquait sur npm, n’est jamais calculé. De son propre point de vue, c’est raisonnable : un changeset vide signifie « ne rien publier ». Combiné à une pull request de version fusionnée avant d’avoir été reconstruite, cela a donné une version créée et jamais livrée.

### Le correctif et les règles

Une pull request de suivi a supprimé le changeset vide cinq minutes plus tard. L’exécution suivante a sélectionné `publish` et mis la 0.1.0-beta.5 en attente à 11:25, et le propriétaire l’a approuvée à 11:44. Notre politique dit désormais que les changesets vides n’ont leur place que sur `main`, et qu’une modification faite directement sur `beta` que les clients ne peuvent pas remarquer, comme une correction du journal des modifications, ne porte aucun changeset, l’échec de sa vérification des changesets étant le seul échec autorisé.

Deux règles valent pour toute équipe :

- **Ne fusionnez une pull request de version que si elle a été construite à partir de la tête actuelle de la branche.** Si quoi que ce soit a été fusionné après sa dernière mise à jour, attendez que le workflow de publication la reconstruise.
- **Traitez « rien à faire » comme un résultat à vérifier.** Une exécution de publication qui ne sélectionne aucun travail alors que la version de la branche manque au registre a échoué, même si tous les jobs sont au vert.

Nous avons la première règle par écrit, et pas encore la seconde sous forme de vérification. Et notre règle écrite sur les changesets vides couvre la branche où c’est arrivé, alors que le mécanisme ne dépend pas du mode préversion : la même situation de concurrence sur `main` laisserait le même changeset vide en attente.

## La CI de la pull request à partir de laquelle vous publiez

### GitHub ne lance pas de workflows pour les pushes de son propre jeton

Le job de version pousse la branche « Version Packages » avec le `GITHUB_TOKEN` du workflow, et la documentation de GitHub indique que « les événements déclenchés par le `GITHUB_TOKEN` ne créent pas de nouvelle exécution de workflow », avec une exception qui compte ici : « les événements `workflow_dispatch` et `repository_dispatch` créent toujours des exécutions de workflow ». La pull request que nous nous apprêtions à publier n’affichait donc aucune vérification ; pour obtenir une exécution sur l’une d’elles, un agent l’a fermée puis rouverte à la main. Le correctif garde le jeton par défaut et lance lui-même la CI. Juste après que Changesets a ouvert ou mis à jour la pull request de version, le même job recherche la branche de la pull request et y déclenche le workflow de CI avec `gh workflow run`, ce qui fonctionne parce que le workflow de CI accepte `workflow_dispatch` en plus de `pull_request`.

Le job obtient `actions: write` pour ce seul appel, et les exécutions de vérification s’attachent au commit de tête de la branche : elles s’affichent donc sur la pull request. Un jeton de GitHub App déclencherait aussi la CI, mais il faut pour cela une app et un secret de plus ; cette solution n’a besoin ni de l’une ni de l’autre.

### Mettre en file les exécutions de publication, sans jamais les remplacer

Les groupes de concurrence de GitHub Actions ne gardaient autrefois qu’une seule exécution en attente : « Si une autre exécution entrait dans le groupe, l’exécution en attente était annulée et remplacée. » Pour un workflow de publication, c’est un défaut, car trois pushes rapprochés sur `beta` feraient disparaître celui du milieu. Depuis mai 2026, `queue: max` permet à un groupe de « mettre en file plusieurs exécutions en attente et de les traiter l’une après l’autre », jusqu’à 100, lorsque `cancel-in-progress` vaut false.

Un exemple générique, d’après la documentation de GitHub sur la concurrence, pour un workflow de publication qui ne doit jamais abandonner une exécution :

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false
  queue: max
```

Notre workflow de publication fonctionne ainsi : chaque push sur une branche de publication obtient sa propre exécution complète, dans l’ordre. La séquence du changeset vide montre l’autre face de cette garantie : une exécution en file décide à partir de son propre commit, même quand ce commit est déjà dépassé au moment où elle s’exécute. La file d’attente conserve chaque exécution ; elle ne rend pas actuelle la décision d’une exécution ancienne.

## Qui détient quelle clé

Les agents mènent la publication ; le propriétaire détient ce qui ne peut pas être défait.

| Tâche                                               | Agents                                                                                 | Propriétaire                                                                                                      |
| --------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Les changesets et la pull request de version        | Les écrivent, relisent les notes et fusionnent quand le lot est complet                | Rien                                                                                                              |
| Les workflows de publication                        | Écrivent la modification et la prouvent, par exemple avec une exécution de sonde       | Approuve chaque modification des fichiers qui décident de ce qui atteint npm, par un oui écrit, cité mot pour mot |
| Construire, tester, empaqueter et mettre en attente | Rien : la CI s’en charge sur le commit de fusion                                       | Rien                                                                                                              |
| Approuver ou rejeter une version en attente         | Transmettent les identifiants de mise en attente exacts                                | Approuve ou rejette avec l’authentification à deux facteurs                                                       |
| Les tags et les GitHub Releases                     | Lancent le workflow des tags et des Releases juste après l’approbation                 | Rien                                                                                                              |
| Un nouveau nom de paquet                            | Le préparent sur `main` et rédigent les étapes exactes                                 | Publie la version provisoire et configure son trusted publisher                                                   |
| Une mauvaise version                                | Rédigent le message de dépréciation et le correctif                                    | Lance `npm deprecate` avec l’authentification à deux facteurs                                                     |
| Les notes de version et la vérification             | Installent depuis npm dans un répertoire propre, rédigent les notes dans chaque langue | Relit                                                                                                             |

Le workflow de publication, la configuration de Changesets et les champs des paquets qui décident de ce qui atteint npm figurent sur la liste de revue humaine du dépôt de la CLI : chaque pull request qui les modifie, comme celle qui a changé la façon dont les publications sont enregistrées, cite donc l’accord écrit du propriétaire. Le même fichier d’instructions interdit aux agents de publier ou de lancer `npm trust`. Et aucun agent ne détient d’identifiant npm, car il n’en existe aucun : chaque paquet refuse la publication par jeton, et la seule identité automatisée capable de mettre en attente est le workflow de publication lui-même.

La vérification ne s’arrête pas à la publication. La suite de parcours du site s’exécute selon la planification <RepositoryFact name="journeySchedule" /> en UTC : elle achète chaque forfait dans le bac à sable de Polar sur le déploiement de preview, puis pilote la CLI publiée, directement depuis npm, à travers l’activation, les limites de machines, la désactivation et le remboursement qui met fin à la licence :

```ts title="e2e/journey/cli.ts"
const child = spawn("env", ["-i", ...variables, PACKAGE_MANAGER.NPM.exec, "--yes", CLI_PACKAGE_SPEC, ...inputs, "--json"], { cwd: home })
```

Le principe est celui par lequel cet article a commencé. Les agents peuvent faire tout ce qui est réversible, ou ce qu’une étape ultérieure rattrapera. Une personne détient les étapes qui ne sont ni l’un ni l’autre, grâce à un facteur que les agents ne peuvent pas détenir.

## Quand une version est mauvaise

Une version publiée sur npm est définitive : revenir en arrière signifie aller de l’avant.

- **Déprécier, puis livrer un patch.** `npm deprecate` avec un message qui nomme le correctif, par exemple « Casse init sous Windows. Utilisez 1.4.1 ou une version ultérieure. », lancé par le propriétaire avec l’authentification à deux facteurs. Le correctif passe par le même pipeline que n’importe quelle publication. Un correctif de sécurité ou une correction de perte de données est publié immédiatement, sans attendre son lot.
- **Ne jamais dépublier.** Cela casse chaque projet et chaque script qui a épinglé la version, et le numéro de version ne peut plus jamais être réutilisé.
- **Rejeter ce qui n’est qu’en attente.** `npm stage reject <stage id>` supprime une version en attente sans la publier, là encore avec l’authentification à deux facteurs.
- **Penser à la version rejetée.** Une version rejetée reste la version du dépôt, et elle manque toujours sur npm : le prochain push sans changeset en attente la remet donc en attente. Fusionnez le correctif, avec son changeset, avant toute autre chose.

## Ce qui nous manque encore

Dans l’esprit du reste de la série, voici les points faibles de notre propre processus de publication.

- **Pas de provenance.** Le dépôt est privé : les paquets portent donc la signature du registre npm, sans attestation de provenance.
- **Pas encore de canal stable.** `latest` est toujours la version provisoire, et chaque commande que nous publions nomme le tag <RepositoryFact name="cliReleaseChannel" />. La première version stable devra basculer ensemble les README, les tests qui les vérifient et les commandes du site.
- **Un point de contrôle multiplateforme superficiel.** Sous macOS et Windows, la publication vérifie `--version` et `--help` avec chaque runtime, pas un `init` complet, et elle construit sur chaque runner au lieu d’installer le tarball qui sera mis en attente.
- **L’approbation se fonde sur le résumé.** `npm stage download` de npm récupère un tarball en attente « pour une inspection locale » sans second facteur : la personne qui approuve pourrait donc installer et exécuter exactement ces octets avant d’approuver. Nous ne le faisons pas encore.
- **Aucune alerte pour « rien à faire ».** Une exécution de publication qui ne sélectionne aucun travail alors que la version de la branche manque sur npm ne fait rien échouer.
- **Un filet de sécurité tardif.** L’exécution planifiée des tags et des Releases démarre des heures après son horaire : l’agent principal la lance donc à la main après chaque approbation.
- **Une seule personne pour approuver.** La 0.1.0-beta.3 a attendu son approbation trois jours, puis a été remplacée. Une publication qui dépend du second facteur d’une seule personne avance au rythme de cette personne.
- **Aucune exécution contre l’API en production avant une publication.** [Le premier article](/blog/ai-coding-agent-guardrails) décrit le garde-fou que nous voulons : la CLI publiée, exécutée contre la production dans la CI avant chaque publication. Il lui faut une clé de licence comme secret de CI, une modification soumise à la revue humaine qui attend le propriétaire.

## Un kit de publication à copier

**Une checklist de publication**, dans l’ordre :

1. Le lot est fusionné, et la dernière exécution de CI sur la branche de publication est au vert.
2. Chaque changeset se lit comme une note destinée à un client, et la montée de version est la bonne.
3. La pull request de version a été reconstruite après la dernière fusion, et ses vérifications sont au vert.
4. La documentation dont la version a besoin est en ligne, et toute modification d’un contrat que lit le serveur est déployée sur le serveur.
5. Aucune version en attente n’attend encore son approbation.
6. Fusionnez la pull request de version.
7. Empaquetez une seule fois ; exécutez le programme construit sur chaque système et chaque runtime que vous prenez en charge ; ne mettez en attente que si tout a réussi.
8. Téléversez et relisez tout ce que la CLI téléchargera, et vérifiez-le par rapport à l’empreinte épinglée, avant la mise en attente.
9. Approuvez chaque paquet de la version avec l’authentification à deux facteurs, ou rejetez-la.
10. Créez les tags et les Releases une fois que le registre sert chaque paquet de la version.
11. Installez depuis le registre dans un répertoire propre et lancez la CLI.
12. Publiez les notes de version, et signalez tout ce qui a été mis en attente sans jamais être publié.

**Un job de mise en attente**, un exemple générique écrit d’après la documentation de npm pour un dépôt sans Changesets, et non le workflow de la CLI. Il n’a besoin d’aucun jeton et peut être relancé sans danger. Il suppose un job `pack` qui téléverse les tarballs comme artefact nommé `tarballs`, un environnement nommé `release`, et un trusted publisher sur npmjs.com qui nomme ce fichier de workflow, cet environnement et la permission limitée à la mise en attente. Chaque action y est épinglée sur le commit d’une version publiée, suivi de son tag, car un tag peut être déplacé, et un job de publication est le dernier endroit où exécuter du code que vous n’avez pas relu :

```yaml
stage:
  needs: pack
  runs-on: ubuntu-latest
  environment: release
  permissions:
    contents: read
    id-token: write
  steps:
    - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
      with:
        node-version: 26
    - uses: actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2
      with:
        name: tarballs
    - name: Stage every tarball npm does not serve yet
      shell: bash
      run: |
        for tarball in *.tgz; do
          manifest=$(tar -xOzf "$tarball" package/package.json)
          name=$(jq -r .name <<< "$manifest")
          version=$(jq -r .version <<< "$manifest")
          if [ "$(npm view "$name@$version" version 2> /dev/null)" = "$version" ]; then
            echo "$name@$version is already on npm" >> "$GITHUB_STEP_SUMMARY"
          elif staged=$(npm stage publish "$tarball" --access public --tag latest --json); then
            echo "$name@$version staged as $(jq -r --arg name "$name" '.[$name].stageId' <<< "$staged")" >> "$GITHUB_STEP_SUMMARY"
          elif [ "$(jq -r '.error.code' <<< "$staged")" = E409 ]; then
            echo "$name@$version was staged by an earlier run" >> "$GITHUB_STEP_SUMMARY"
          else
            exit 1
          fi
        done
    - name: Keep npm's logs when staging fails
      if: failure()
      uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
      with:
        name: npm-logs
        path: ~/.npm/_logs/
        retention-days: 7
```

**Un trusted publisher qui ne peut que mettre en attente**, configuré une fois par paquet par un mainteneur avec l’authentification à deux facteurs :

```sh
npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish
```

**Des tags uniquement pour ce que npm sert**, un exemple générique pour un seul paquet, à relancer sans danger autant de fois que nécessaire, par exemple après chaque approbation :

```sh
name=$(jq -r .name package.json)
version=$(jq -r .version package.json)
if [ "$(npm view "$name@$version" version 2> /dev/null)" != "$version" ]; then
  echo "npm does not serve $name@$version yet, so nothing is tagged"
  exit 0
fi
if git rev-parse -q --verify "refs/tags/v$version" > /dev/null; then
  exit 0
fi
git tag "v$version"
git push origin "v$version"
gh release create "v$version" --verify-tag --notes-file release-notes.md
```

**Un téléchargement vérifié auprès du serveur et de l’empreinte épinglée** avant que quoi que ce soit ne le lise, un exemple générique en TypeScript pour Node :

```ts
import { createHash } from "node:crypto"
import { gunzipSync } from "node:zlib"

const MAX_CONTENT_BYTES = 256 * 1024 * 1024

interface BundleAnswer {
  readonly sha256: string
  readonly size: number
}

export const verifiedContent = (archive: Buffer, answer: BundleAnswer, pinned: string): Buffer => {
  if (archive.length !== answer.size) {
    throw new Error(`Expected ${answer.size} bytes and received ${archive.length}`)
  }

  const content = gunzipSync(archive, { maxOutputLength: MAX_CONTENT_BYTES })
  const digest = createHash("sha256").update(content).digest("hex")

  if (digest !== answer.sha256 || digest !== pinned) {
    throw new Error("The download is not the bundle this release was tested with")
  }

  return content
}
```

**Des règles de publication pour votre fichier d’instructions**, pour que les agents préparent ce que le propriétaire approuvera :

```md
## Releases

- Never run npm publish, npm unpublish, npm stage approve or npm stage reject. CI stages releases, and a maintainer approves them with 2FA.
- Every change to a published package adds a changeset written for customers: what changes for them and what they have to do.
- Merge a version pull request only when it was built from the branch's current head, and never while a staged release awaits approval.
- After an approval, start the records workflow, install the release from npm in a clean directory and run it before announcing anything.
- Label a version that was staged and never published in its changelog and its GitHub Release. Never delete its tag.
```
