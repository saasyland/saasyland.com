Chaque chemin a une constante dans `ROUTES`, déclarée dans `src/routes.ts`, qui n'importe rien (voir [Chemins et navigation](/docs/conventions/routes#paths-and-navigation)). Les liens utilisent la constante, par exemple `<Link to={ROUTES.SIGN_IN}>`, et le routeur ajoute le préfixe de locale. Chaque page ci-dessous est aussi servie sous le préfixe de chaque locale autre que la locale par défaut, par exemple `/pl-PL/terms`.

## Pages publiques

Ces pages se trouvent dans le layout `_site`, qui affiche l'en-tête du site. Toutes, sauf la documentation, se trouvent aussi dans le layout `_marketing` (cadre de page et pied de page), le layout de la documentation affiche lui-même ce même pied de page, et le blog et la documentation y ont chacun leur propre layout. Elles sont toutes prérendues, sauf les pages de newsletter.

| ----------------------------- | ------------------------ | -------------------------------------------------------------- |
| `/`                           | `HOME`                   | `_site._marketing.index.tsx`                                   |
| `/licence`                    | `LICENCE`                | `_site._marketing.licence.tsx`                                 |
| `/privacy`                    | `PRIVACY`                | `_site._marketing.privacy.tsx`                                 |
| `/terms`                      | `TERMS`                  | `_site._marketing.terms.tsx`                                   |
| `/refunds`                    | `REFUNDS`                | `_site._marketing.refunds.tsx`                                 |
| `/withdrawal`                 | `WITHDRAWAL`             | `_site._marketing.withdrawal.tsx`                              |
| `/affiliates`                 | `AFFILIATES`             | `_site._marketing.affiliates.tsx`                              |
| `/newsletter/confirm`         | `NEWSLETTER_CONFIRM`     | `_site._marketing.newsletter.confirm.tsx`                      |
| `/newsletter/unsubscribe`     | `NEWSLETTER_UNSUBSCRIBE` | `_site._marketing.newsletter.unsubscribe.tsx`                  |
| `/blog`                       | `BLOG`                   | `_site._marketing.blog.tsx`, `_site._marketing.blog.index.tsx` |
| `/blog/rss.xml`               | `BLOG_FEED`              | aucun                                                          |
| `/blog/page/*`                | aucune                   | `_site._marketing.blog.page.$page.tsx`                         |

`/*` désigne toute adresse qu’aucune autre route ne reconnaît : `_site._marketing.$.tsx` lève `notFound()`, si bien que le serveur répond 404 avec la page introuvable, rendue à chaque requête (voir [Page introuvable](/docs/features/landing-page#not-found-page)).

`/blog/rss.xml` n'a pas de fichier de route : `scripts/generate-seo-files.ts` écrit le flux de chaque langue après le build (voir [Flux RSS](/docs/features/blog#feed)).

## Cours

Le layout `/courses` (`_site._marketing.courses.tsx`) se trouve, comme le blog, dans les layouts `_site` et `_marketing` et n'a pas de guard : le serveur vérifie le niveau d'accès de chaque leçon (voir [Cours](/docs/features/courses)). Ces pages lisent D1 à chaque requête et ne sont pas prérendues. `/sitemap-courses.xml` n'a pas de fichier de route : un handler de requêtes de `src/server.ts` y répond à partir de D1 (voir [Sitemap des cours](/docs/features/seo#course-sitemap)).

| Chemin                       | Constante         | Fichier de route                                                     |
| ---------------------------- | ----------------- | -------------------------------------------------------------------- |
| `/courses`                   | `COURSES`         | `_site._marketing.courses.tsx`, `_site._marketing.courses.index.tsx` |
| `/courses/<course>`          | aucune            | `_site._marketing.courses.$course.index.tsx`                         |
| `/courses/<course>/<lesson>` | aucune            | `_site._marketing.courses.$course.$lesson.tsx`                       |
| `/sitemap-courses.xml`       | `COURSES_SITEMAP` | aucun                                                                |

## API

Les chemins d'API ne sont jamais localisés.

| Chemin                                       | Constante       | Fichier de route                                                                                                                                   |
| -------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api`                                       | `API`           | `api/index.ts`                                                                                                                                     |
| `/api/auth/*`                                | `API_AUTH_BASE` | `api/auth.$.ts`                                                                                                                                    |
| <RepositoryFact name="cliApiBasePath" />`/*` | aucune          | `api/cli.v1.license.ts`, `api/cli.v1.activations.ts`, `api/cli.v1.activations.$activationId.ts`, `api/cli.v1.activations.$activationId.bundles.ts` |

Les chemins de l'API de licence de la CLI viennent de son contrat, `API_BASE_PATH` et `API_ROUTE` dans `@saasyland/stack/api`, et `src/routes/api/__test__/cli.v1.test.ts` vérifie que le routeur envoie chacun d'eux à son fichier de route (voir [API de licence de la CLI](/docs/features/cli-licence-api)).

`ROUTES.API_AUTH` liste les chemins des endpoints propres à Better Auth et de ceux de ses plugins d'administration et d'authentification à deux facteurs, relatifs à `/api/auth` ; `auth.server.ts` s'en sert pour exempter certains endpoints de la limitation de débit, et `INPUT_POLICY` dans `auth.hooks.ts` pour valider les endpoints qui acceptent un mot de passe, un nom, un e-mail ou une image. `ROUTES.API_AUTH_POLAR` liste les webhooks du plugin Polar, que `auth.server.ts` exempte de la limitation de débit, et disparaît avec la zone Polar, tout comme `API_AUTH_CUSTOMER_PORTAL`. `API_AUTH_CUSTOMER_PORTAL` et `API_AUTH_VERIFY_EMAIL` sont des chemins complets vers des endpoints Better Auth, construits à partir de `API_AUTH_BASE`. `AUTH` et `NEWSLETTER` n'ont pas de page propre ; avec `ADMIN`, `APP`, `API` et `COURSES`, ils délimitent les zones qui ne sont jamais prérendues (`REQUEST_RENDERED_ROUTES` dans `src/routes.ts`, que lit `isRequestRenderedRoute`), et `verify-build.ts` fait échouer un build qui a prérendu une page sous l'un d'eux.

## Médias

`/media/<expiry>.<signature>/<videoId>/<file>` sert les fichiers vidéo signés. Ce chemin n'a ni constante `ROUTES` ni fichier de route : `src/server.ts` l'envoie à `serveMedia` avant le middleware de langue, il n'est donc jamais localisé. Voir [Cloudflare R2](/docs/integrations/cloudflare-r2).

`/media/covers/<courseId>/<file>` sert les couvertures publiques des cours via `serveCover`, et `/media/downloads/<expiry>.<signature>/<attachmentId>/<fileName>` les ressources signées des leçons via `serveAttachment`. Le handler `/media/` de la zone des cours les y envoie, si bien qu’ils ne sont jamais localisés non plus. Voir [Couvertures des cours](/docs/features/courses#course-covers).

<RepositoryFact name="cliBundleUrlPath" /> sert de la même manière les bundles de modèles signés de la CLI, via `serveBundle`, et tire son
préfixe de `BUNDLE_PATH_PREFIX` dans `license.constants.ts`. Voir [API de licence de la
CLI](/docs/features/cli-licence-api#template-bundles).
