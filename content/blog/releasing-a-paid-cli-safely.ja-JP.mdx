  - question: npm のステージング公開とは何ですか？
    answer: >-
      CI と公開レジストリのあいだに置かれる承認のステップです。CI は 2 つ目の要素を必要としない npm stage publish を実行し、バージョンはステージしたときの dist-tag を付けたまま、ステージング領域で待ちます。公開されるのは、メンテナーが npmjs.com か npm stage approve で承認したときだけで、どちらの方法でも npm は二要素認証を求めます。却下されたバージョンは、公開されないまま削除されます。
  - question: CI からの公開には、Trusted Publishing と npm トークンのどちらを使うべきですか？
    answer: >-
      Trusted Publishing です。CI は GitHub Actions や GitLab の短命な OIDC トークンを公開用の認証情報と交換するので、保管し、ローテーションし、漏洩に備えなければならない長期のトークンがありません。id-token の write 権限は公開するジョブにだけ与え、承認も必要なら Trusted Publisher にはステージだけを許可し、パッケージには二要素認証を必須にしてトークンを禁止する設定をしてください。
  - question: Trusted Publishing を使えば、パッケージに来歴証明が付きますか？
    answer: >-
      公開リポジトリからの場合だけです。npm は、ソースのリポジトリとパッケージの両方が公開されているとき、Trusted Publishing による公開に来歴証明を自動で生成しますが、非公開のリポジトリでは生成しません。非公開のリポジトリからビルドしたパッケージにも、npm audit signatures で検証できる npm のレジストリ署名は付きますが、来歴証明は付きません。
  - question: リリースのワークフローは、Git のタグと GitHub Releases をいつ作成すべきですか？
    answer: >-
      CI がバージョンをステージしたときや公開したときではなく、レジストリがそのバージョンを配信するようになってからです。ステージしたバージョンは、却下されることも、後のバージョンに置き換えられることも、単に承認されないままになることもあり、そうなるとタグとリリースは、誰もインストールできないパッケージを説明することになります。まずレジストリでそのバージョンそのものを確認し、ジョブを何度実行しても安全なものにし、承認のたびに実行し直してください。
  - question: CLI がリリース時とまったく同じファイルをダウンロードしていることは、どう確かめればよいですか？
    answer: >-
      圧縮したファイルではなく内容のダイジェストを、公開するコードの中に固定し、その固定値はバージョンを切るときに書き込みます。パッケージをインストールできるようになる前にファイルをアップロードし、サーバーには保存しているサイズとダイジェストを返させ、サイズかダイジェストがサーバーの応答または固定値と異なるダウンロードは、中身を読む前に拒否してください。
  - question: 空の changeset がリリースを止めることはありますか？
    answer: >-
      あります。保留中の changeset がすべて空だと、ブランチに npm にまだないバージョンがあっても、Changesets のアクションは何の作業も選びません。私たちの場合は、バージョンのプルリクエストがビルドされた後に空の changeset が入り、そのプルリクエストが作り直されないままマージされたときに起きました。バージョンのプルリクエストは、ブランチの現在のヘッドからビルドされたときだけマージしてください。
  - question: 公開した npm のバージョンが壊れていたら、どうすればよいですか？

  - question: AI エージェントにパッケージの公開を任せてよいですか？
    answer: >-
      レジストリの手前までなら、すべて任せられます。changeset、バージョンのプルリクエスト、レビューを経たワークフローの変更、リリースノート、検証、リリース後の記録です。取り消せないステップには、ステージされたバージョンをメンテナーが二要素認証で承認するといった、どのエージェントも持たない要素を必須にし、エージェントが使える公開トークンはどこにも置かないようにしてください。

## 結論から

リリースを、マージではない唯一のステップとして扱ってください。レジストリより前のことは、すべて自動化でき、やり直せます。changeset からのバージョン付け、ビルド、1 回だけのパッケージング、サポートするすべてのプラットフォームでのビルドしたプログラムの実行、CLI がダウンロードするもののアップロードです。取り消せないステップ、つまり npm にバージョンが現れることには、どのワークフローも持っていない 2 本目の鍵を付けます。リリースは、npm の Trusted Publishing を使って CI からステージします。保存したトークンの代わりに短命な OIDC トークンを使う仕組みです。そしてステージされたバージョンを、メンテナーが二要素認証で承認します。CLI が実行時に取得するものは、すべて内容で固定し、2 つの情報源に照らして確認します。Git のタグと GitHub Releases は、npm がそのバージョンを配信するようになってから作成します。ステージされたバージョンは、公開されないこともあるからです。そして、リリースツールが自分のルールに従って「やることは何もない」と判断する瞬間に注意してください。かつて空の changeset のせいで、私たちのベータ版の 1 つは、すべてのジョブが緑のまま、まったくステージされませんでした。

## リリースがマージとは違う理由

マージは別のマージで元に戻せます。リリースは戻せません。理由は 3 つあります。

**バージョン番号は使い切り。** npm の unpublish のポリシーは率直です。「`package@version` は、一度使われると二度と使えない」。さらに「これは、そのパッケージの公開が取り消された場合でも変わらない」と続きます。公開の取り消し自体は、レジストリのほかのパッケージが自分のパッケージに依存していなければ最初の 72 時間に限って認められ、それ以降はより厳しい条件の下でだけ認められます。それ以外のすべての場合について、npm は非推奨にすることを勧めています。悪いリリースは新しいバージョンで前に進んで直し、悪いバージョンは、それを固定した人のためにレジストリに残り続けます。

**顧客はそれを前提にスクリプトを書く。** CLI の公開インターフェースは、ライブラリのエクスポートより広いものです。コマンド、フラグ、デフォルト値、終了コード、機械が読むための出力、書き出すファイル、起動するランタイムまでが含まれます。デフォルト値が 1 つ変わったり、新しい終了コードが 1 つ増えたりするだけで、自分では決して目にしない CI のジョブが壊れます。

**有料 CLI には動く部品が複数ある。** 私たちの CLI は、プロジェクトを作成するたびに saasyland.com でライセンスを確認し、生成に使うテンプレートを、リリースごとに 1 つのバンドルとして、ウェブサイトのライセンス API からダウンロードします。リリースとは、npm のパッケージと、ストレージにあるテンプレートバンドルと、サーバーとの契約を合わせたものです。この 3 つは、顧客がそのバージョンをインストールできるようになった最初の 1 分から、一致していなければなりません。

AI エージェントによって、リスクのある場所が変わります。エージェントは、元に戻せる部分では速く、抜かりがありません。changeset を書き、バージョンのプルリクエストを最新に保ち、ワークフローを編集し、<RepositoryFact name="languages" /> つの言語でリリースノートを書き、その後でレジストリを確認します。そして、取り消せない部分についても、ほかのすべてとまったく同じくらい自信を持っています。だからこの記事の設計原則は単純です。レジストリの手前まではすべてエージェントに任せ、その前のステップはどれも 2 回実行しても安全にし、元に戻すことも繰り返すこともできない唯一のステップには人の鍵を置きます。

構成についても少し説明しておきます。自分の環境に当てはめやすくするためです。SaaSy Land CLI は `saasyland`、`create-saasyland`、`@saasyland/stack` の 3 つの npm パッケージで、Changesets 3 と GitHub Actions を使って、非公開の GitHub リポジトリからリリースしています。2026年11月25日の時点で、プレビュー版は npm の <RepositoryFact name="cliReleaseChannel" /> タグで公開しており、最新は 11月20日の 0.1.0-beta.5 です。顧客は <RepositoryFact name="cliPackageSpec" /> を実行します。`latest` には、名前を確保した `0.0.0` のプレースホルダーがまだ入っています。エージェントは Claude Code のセッションで、リードエージェントと、リードエージェントが指示書を書くワーカーからなり、CLI を端から端まで担当しています。オーナーは CLI を任せるとき、「バージョニング、変更履歴、そのほかすべてをできるかぎりプロフェッショナルに」すること、そして「本当に意味のあるまとまりで」リリースすることを求めました。すべての公開を承認するのはオーナーです。

## 顧客が頼りにできるバージョニング

### CLI にとっての「破壊的」を書き出す

セマンティックバージョニングが役に立つのは、自分の公開インターフェースが何かを書き出してあるときだけです。私たちのリリースポリシーは、CLI にとって何が破壊的変更にあたるかを挙げています。

- コマンド、フラグ、フラグの値の削除や名前の変更、またはデフォルト値の変更
- 同じ状況での異なる終了コード
- `--json` の出力のフィールドの削除、名前の変更、型の変更（新しいフィールドの追加は破壊的変更に含めない）
- 古い CLI が読めなくなる、プロジェクトのマニフェストの変更
- Node の最低バージョンの引き上げ
- 共有パッケージのエクスポートの削除や変更
- ライセンス API 自身のルールが破壊的とする変更

  1.0 より前は、マイナーバージョンに新機能か破壊的変更を入れ、パッチには修正だけを入れます。ライセンス API も、自身の境界で同じ規律を守っています。`v1` の中では、ウェブサイトはレスポンスのフィールド、エンドポイント、エラーコードを追加でき、CLI は知らないフィールドを無視します。それ以外の変更には、サポート対象の CLI が呼び出しているかぎり `v1` と並べて配信する `v2` が必要です。[このシリーズの最初の記事](/blog/ai-coding-agent-guardrails)では、公開済みの CLI が、本番のウェブサイトがまだ受け付けていなかったフィールドを送っていた経緯と、契約の変更を今はまずサーバーでリリースしている理由を説明しています。

### changeset は顧客のためのリリースノート

公開パッケージを変更するプルリクエストはすべて changeset を追加し、追加しないものは CI が拒否します。`changeset status --since=origin/<base>` は、changeset なしでパッケージが変更されると失敗します。もっと大事なルールは、中身に関するものです。changeset は顧客のリリースノートです。顧客にとって何が変わり、何をしなければならないかを平易な 1〜2 文で書き、コマンドとフラグは顧客が入力するとおりに書きます。「フラグのパーサーのバグを修正」では、顧客には何も伝わりません。公開している[リリースノート](/docs/cli/releases)に載っている 0.1.0-beta.5 のノートは、次のとおりです。

> **破壊的変更：** Lemon Squeezy がサービスを終了するため、`--billing lemonsqueezy` を削除しました。Lemon Squeezy は 2026年11月16日から新規登録を受け付けておらず、2027年3月31日に終了します。`--billing polar` と `--billing stripe` は `--billing` が認識する値として残りますが、生成されるプロジェクトにはまだ課金がないため、`init` は引き続きどちらもコード <RepositoryFact name="cliExitNotAvailable" /> で拒否します。`init --billing lemonsqueezy` は、`--billing` にないほかの値と同じく、コード <RepositoryFact name="cliExitUsage" /> で終了するようになりました。

ルールの書き方が、エージェントの出力を決めます。「changeset を追加して」とだけ言われたエージェントは、「フラグのパーサーをリファクタリング」と書きがちです。changeset は顧客が変更履歴で読むものだと伝えられていれば、上のようなノートを書きます。リファクタリングや新しいテストのように顧客が気づけない変更には、空の changeset を付けます。この逃げ道が、この記事の 2 つ目のインシデントの原因です。

### 一緒にリリースするパッケージには 1 つのバージョン

3 つのパッケージは、Changesets の fixed グループを構成しています。このグループでは「変更がない場合でも、グループ内のすべてのパッケージのバージョンが上げられ、一緒に公開される」のです。そのため `saasyland@0.1.0-beta.5` は必ず `@saasyland/stack@0.1.0-beta.5` と一緒に出て、顧客も、バグ報告も、サポートの返信も、1 つの番号で話が通じます。その代償は変更履歴に表れます。自分に固有の変更が何もないパッケージにもリリースが出るので、私たちのウェブサイトのリリースノートは、漏れに見える空白を残す代わりに、そのパッケージについて「このリリースでの変更はありません。」と表示します。

### リリースはまとまりで切り、バージョンのプルリクエストは寝かせておく

Changesets は Version Packages のプルリクエストを開いたままにし、changeset がマージされるたびに作り直します。このプルリクエストがリリースの関門で、これをマージすることがリリースするという決定になります。私たちはリリースを、プルリクエストごとではなく、筋の通ったまとまりで切っています。`main` では、0.1.0 の Version Packages のプルリクエストが 11月14日から開いていて、11月25日の時点で 24 個の changeset を含んでいました。安定版のまとまりがそろい、ドキュメントが整ったときにマージします。

プレビュー版は、Changesets のプレリリースモードで `beta` ブランチから出します。そのドキュメントは「プレリリースはとても複雑！」と警告し、「間違えると、リポジトリと公開の状態が、直すのがとても難しいものになりうる」とも書いています。後で見るとおり、どちらの文も私たちのところで現実になりました。プレリリースモードを使うなら、専用のブランチに置き、リリースのタグが読める履歴を指すようにそのブランチの履歴を線形に保ち、`main` からの変更はレビューできる方法で取り込んでください。私たちは `main` のコミットを `beta` から切ったブランチにチェリーピックし、それをスカッシュマージしているので、`beta` にマージコミットができることはありません。

### npm の README はリリースの一部

最初の安定版リリースまで `latest` はプレースホルダーなので、`npx saasyland init` と書いた README は、どのコマンドも動かないプレースホルダーを実行させてしまいます。0.1.0-beta.1 では、パッケージに含めた README がまさにそうなっていて、タグのない `create` のコマンドも `latest` を解決していました。現在は、スモークテストがパッケージングした各 tarball の中の README を読み、どれかのパッケージを dist-tag なしで、または別の dist-tag で指定しているコマンドがあれば失敗します。テストが期待する dist-tag は 1 か所で宣言されていて、それを切り替えることが、最初の安定版リリースの手順の 1 つです。同じ理由から、ウェブサイトの [CLI ガイド](/docs/cli)は、コマンドを 1 つの定数 <RepositoryFact name="cliPackageSpec" /> から出力しています。

## ステージング公開：人の鍵はレジストリに置く

### ステージングとは

npm のステージング公開（staged publishing）は、「パッケージが npm レジストリで公開される前に、承認のステップを加える」ものです。CI は「2FA を必要としない」`npm stage publish` を実行し、バージョンはメンテナーが承認するまでステージング領域で待ちます。「CLI で承認する場合も npmjs.com で承認する場合も、2FA による確認を求められる」のです。ステージされたバージョンの却下にも、2 つ目の要素が必要です。dist-tag はステージした時点で決まります。「タグは、ステージされたパッケージの変更できない属性である」。ステージングには npm 11.15.0 以降が必要です。私たちのステージのジョブは Node 26.13.1 に同梱の npm、つまり npm 11.20.0 を使い、ステージに使った npm のバージョンをサマリーに出力します。

npm は、すべての利用者をこの方向に移そうとしています。2026年9月の変更履歴には、「npm は、2FA を回避するトークンによる直接の公開を 2027年1月に廃止することを目指している」とあり、まだ Trusted Publishing に移行できない自動化のための移行先として、ステージ専用のトークンを用意しています。私たちのステージの実行は、npm の次の通知をログに残しています。「npm tokens that bypass 2FA are being restricted for account changes and direct publishing.」

### ゲートを CI ではなく npm に置く理由

GitHub では環境を使ってジョブをレビュアーの承認待ちにでき、Changesets のガイドは「公開ジョブの実行を承認する必須のレビュアーを設定した環境を作ること」を提案しています。私たちは代わりに npm に鍵を置きました。理由は 2 つあります。1 つは、取り消せないものそのものを守れることです。ワークフローが何をしようと、エージェントが何をマージしようと、メンテナーがステージされたそのバージョンを承認するまで、何も公開されません。もう 1 つは、どのワークフローも、エージェントも、GitHub のトークンも持てない、メンテナーの npm の 2 つ目の要素に基づいていることです。CI での承認が守るのはジョブであり、いったん承認されれば、そのジョブはビルドしたものを何でも公開できます。さらに GitHub は、非公開リポジトリでの必須のレビュアーを Enterprise プランでしか提供していないので、多くのチームにとって、こうしたゲートを置ける場所はレジストリしかありません。

### Changesets はまだステージしないので、その計画に従ってステージする

Changesets のガイドははっきり書いています。「現時点では、Staged Publishing は Changesets と一緒には動かないので、当面は代わりに Trusted Publishing を使うべき」。v3 の告知では、ステージングは「次の機能アップデート」で入るとしています。それまでは、そのパブリッシュアクションは `npm publish` を実行し、ステージだけを許可された Trusted Publisher はそれを拒否します。そこで私たちのステージのジョブは、アクションが行うことを、コマンドを 1 つだけ変えて行います。`changeset pack` が tarball の隣に書き出す公開計画を読み、Changesets が選んだアクセス権と dist-tag で各パッケージをステージします。プレリリースモードなら `beta`、それ以外なら `latest` です。

公開計画にある各パッケージについて、ジョブはまず、認証情報の要らない公開の `npm view` で、そのバージョンがすでに配信されているかを npm に問い合わせます。配信されていなければ、パッケージングした tarball に対して、計画のアクセス権と dist-tag、そして `--json` フラグを付けて `npm stage publish` を実行し、npm の応答からステージ ID を読み取ります。どのパッケージも、次の 3 つの結果のうちちょうど 1 つに行き着きます。これによって、このジョブは何度実行しても安全になります。ランナーが落ちた後にいちばん再実行したくなるのがリリースのジョブなので、これは重要です。

- **すでに npm にある：** スキップします。リリース後の `main` へのプッシュや再実行で、二重に公開しようとすることはありません。
- **以前の実行でステージ済み：** npm は 409 を返し、ジョブはそれを報告して次に進みます。Trusted Publishing のトークンはステージも公開もできますが、npm によれば「短命なトークンは `npm stage` のサブコマンドを実行できない」ので、ジョブはステージの一覧から以前の ID を探せません。そのため、どこを見ればよいかをサマリーで承認者に伝えます。
- **それ以外：** ジョブは、次のパッケージに進む前に止まります。

ジョブのサマリーは、承認者の作業リストです。パッケージごとに 1 行で、バージョン、dist-tag、ステージ ID、そしてそれを承認する正確なコマンドを示します。3 つのパッケージで 1 つのリリースなので、3 つをまとめて承認します。この記事の最後にあるリリースキットには、Changesets を使わないリポジトリ向けに、npm のドキュメントをもとに書いたこのジョブの汎用的な版を載せています。

### レジストリが記録するもの

0.1.0-beta.5 について、npm のメタデータは、公開元として Trusted Publisher 経由の GitHub Actions を挙げ、承認したメンテナーも記録しています。ステージされたのは 11月20日の 11:25 UTC で、公開されたのは 11:44 でした。この記録が監査証跡になります。どのワークフローがそのバイト列を作り、誰がそれを外に出したのか、です。

## Trusted Publishing：漏れるトークンがない

### 短命な認証情報を、1 つのジョブだけに

Trusted Publishing は、保存した npm のトークンではなく、CI プロバイダーの OIDC を通じて得た「短命で、暗号学的に署名されたトークンを使って」、CI から公開できるようにする npm の仕組みです。npm 11.5.1 以降と Node 22.14.0 以降が必要で、GitHub では「重要な要件は id-token: write の権限」です。npm 側では、Trusted Publisher に GitHub の組織またはユーザー、リポジトリ、ワークフローファイル、そして必要なら環境を指定します。さらに 2 つの設定で、残りの扉を閉じます。

- **Trusted Publisher にはステージしか許可しない。** npm の CLI では `npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish` で、`--allow-publish` は付けません。npm のドキュメントによれば、Trusted Publisher には「`npm stage publish` は常に許可されている」一方で、直接の公開と dist-tag の変更は別のオプションで、メンテナーが有効にしないかぎりオフです。
- **公開のアクセス権に二要素認証を必須にし、トークンを禁止する。** npm は、この設定が「従来のトークン認証にだけ影響する」と述べているので、Trusted Publisher は動き続け、どこに保存されたトークンでも公開はできなくなります。

Trusted Publisher は npmjs.com のパッケージの設定で構成するので、新しいパッケージ名には手作業のステップが 1 つ必要です。オーナーが二要素認証を使って `0.0.0` のプレースホルダーを手で公開し、その後で Trusted Publisher とアクセスの設定を追加します。`latest` に今 `0.0.0` が入っているのは、そのためです。

GitHub 側では、ワークフローは `permissions: {}` から始まり、各ジョブが必要なものだけを求めます。Changesets のガイドは、これをはっきりこう書いています。「`id-token: write` は、公開する必要のあるジョブにだけ設定すること」。

| ジョブ                                | 権限                                                  | 理由                                                                   |
| ------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------- |
| リリースモードの選択                  | `contents: read`                                      | 保留中の changeset を読む                                              |
| バージョンのプルリクエストを開く      | `contents`、`pull-requests`、`actions` の write       | リリースブランチをプッシュし、プルリクエストを開き、その CI を開始する |
| ビルド、検証、パッケージング          | `contents: read`                                      | ビルド、テスト、パッケージングを行う                                   |
| ビルドした bin の実行（9 つのジョブ） | `contents: read`                                      | bin をビルドして実行する                                               |
| npm へのステージ                      | `contents: read` と `id-token: write`、保護された環境 | npm と OIDC トークンを交換し、テンプレートバンドルをアップロードする   |
| タグとリリースの作成                  | `contents: write`                                     | タグとリリースを作成する                                               |

OIDC トークンを要求できるのはステージのジョブだけで、保護された環境を使うのもこのジョブだけです。この環境はテンプレートのストレージの認証情報を保持し、そこへデプロイできるのはリリースブランチだけです。GitHub では、環境のシークレットは「その環境を使うワークフローのジョブだけが利用できる」ので、ほかのジョブも、ほかのブランチからのワークフローの実行も、それを読めません。

### チェックアウトのトークンも権限の 1 つ

`actions/checkout` は、`persist-credentials: false` を設定しないかぎり、「認証付きの git コマンドを実行するために」ジョブのトークンをローカルの Git の設定に残します。すべてのジョブでこれを false にしたところ、最初の Version Packages のプルリクエストが開かれませんでした。Changesets がリリースブランチをプッシュしたとき、Git が「could not read Username for 'https://github.com'」と報告したのです。修正では、プッシュする唯一のジョブであるそのジョブにだけ、トークンを戻しました。最小権限は、ファイル全体にコピーした 1 つの設定ではなく、ジョブごとの性質です。

### npm が説明できなかった失敗

最初のベータ版が npm に届いたのは、そのバージョンのプルリクエストがマージされてから 12 時間後でした。11月14日の 06:18 UTC、ステージのジョブは、npm 自身が出した次のエラーで失敗しました。

```text
npm error code ENEEDAUTH
npm error need auth This command requires you to be logged in to https://registry.npmjs.org/
```

メッセージはログインするように言っています。本当の理由は OIDC トークンの交換が失敗したことで、npm はその理由を verbose レベルで、ジョブとともに削除されるランナー上のデバッグログに書き込みます。そこで、ステージのジョブが失敗したときには必ず `~/.npm/_logs/` をアーティファクトとしてアップロードするようにしたところ、次の失敗のログが原因を示しました。実行のリポジトリ、ワークフロー、環境に一致する Trusted Publisher を、npm が見つけられなかったのです。npm のドキュメントは、まさにこれを警告しています。「npm は、Trusted Publisher の設定を保存するときにそれを検証しない」、そして「すべてのフィールドは大文字と小文字を区別し、正確でなければならない」。npmjs.com の設定がワークフローと一致した後、失敗したジョブを再実行すると 18:24 に 0.1.0-beta.0 がステージされ、オーナーは 4 分後にそれを承認しました。

この教訓は npm に限りません。認証のレイヤーが失敗すると、そのエラーメッセージはたいてい、最初に失敗したステップではなく、最後に試したフォールバックを説明します。失敗したすべてのリリースジョブから、ツールのデバッグログを短い保持期間で残し、何かを変える前にそれを読んでください。

### 来歴証明には公開リポジトリが必要

公開リポジトリなら、Trusted Publishing で来歴証明（provenance）が追加の手間なしに手に入ります。npm は「来歴証明を自動的に生成して公開する」のですが、それは「公開リポジトリから公開している」かつ「公開パッケージを公開している」場合に限られ、「非公開リポジトリでは、来歴の生成はサポートされていない」のです。私たちの CLI は商用で、リポジトリは非公開なので、パッケージに来歴証明は付いていません。付いているのは npm のレジストリ署名で、これは誰でも確認できます。`saasyland@0.1.0-beta.5` をインストールしたクリーンなディレクトリで、`npm audit signatures` は「1 package has a verified registry signature」と報告します。ソースが公開されているなら来歴証明を有効にし、ユーザーにその検証方法を伝えてください。非公開なら、「Trusted Publishing」という名前に実際にはない保証を連想させたままにせず、そのことをはっきり書いてください。

## CLI がダウンロードするものはすべて固定する

### テンプレートは、パッケージには入らないリリースの一部

`saasyland init` は、同梱していないテンプレートからプロジェクトを生成します。ライセンスを確認した後、自分のリリースのテンプレートバンドルを、ウェブサイトのライセンス API からダウンロードします。これによって有料のテンプレートを公開の npm の tarball に入れずに済みますが、同時に、リリースごとに npm が何も知らない 2 つ目の成果物ができます。ここから 2 つのルールが導かれます。顧客が受け取るバンドルは、そのリリースのテストに使ったものとまったく同じでなければならず、誰かがリリースをインストールできるようになる前に存在していなければなりません。

### 圧縮ではなく内容のダイジェストを取る

バンドルは決定的にビルドされます。レイヤーは ID 順、ファイルはパス順、キーは決まった順に並び、ファイルシステムから記録するのは、各ファイルの内容と実行ビットだけです。そのダイジェストは、gzip のバイト列ではなく、アーカイブの中の JSON の SHA-256 です。Node と Bun は、同じ JSON を異なるバイト列に圧縮するからです。実際に計測したところ、アーカイブのダイジェストは異なり、内容のダイジェストは一致しました。圧縮したファイルのダイジェストが識別するのは圧縮器です。ランタイムが zlib を更新した最初の時点で一致しなくなり、顧客はダウンロードが壊れていると告げられることになります。

### バージョン付けのときに固定し、アップロードの前に検証し、ステージの前にアップロードする

固定値は、Version Packages のプルリクエストで書き込まれます。バージョンのスクリプトは `changeset version` を実行し、続いて新しいバージョンのバンドルをビルドし、そのダイジェストを CLI の中にある固定値のファイルに追加します。そのため、レビュアーはバージョンの変更と固定値を並べて見ることができ、リリースは自分のコードの中にダイジェストを持つことになります。固定の処理は、すでに固定されたダイジェストの変更を拒否します。どの CLI も、それより前のすべてのリリースの固定値を持っています。`update` が提供されると、プロジェクトの作成元になったリリースを、マージのベースとして再生成するからです。

リリースの時点で、ステージのジョブはバンドルをビルドし直し、そのダイジェストが固定値と一致しなければ失敗します。次に、ダイジェストをオブジェクトのメタデータに入れてアーカイブを、ライセンス API が読むストレージにアップロードし、すべてのオブジェクトを読み戻します。サイズ、コンテンツタイプ、メタデータ、そして内容のダイジェストです。npm に何かをステージするのは、その後だけです。公開済みの CLI が、存在しないバンドルを要求することがあってはならないからです。アップロードの処理は、固定されたバンドル以外のアーカイブをすべて拒否するので、再実行によってリリースが配信するものが変わることはありません。

### 2 つの情報源に照らして 2 回確認する

ウェブサイトはバンドルのリクエストに対して、有効期間が <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />の短命な署名付き URL と、バンドルのサイズとダイジェストを返します。サイズとダイジェストは、アーカイブを開かずに、保存されたオブジェクトのヘッドから読み取ります。

```ts title="src/modules/license/license.api.ts"
const storedBundle = async (version: string): Promise<StoredBundle> => {
  const key = bundleObjectKey(version)
  const object = await env.BUNDLES.head(key)

  if (object === null) {
    return { error: { code: API_ERROR.VERSION_NOT_FOUND, version }, success: false }
  }

  const metadata = bundleMetadataSchema.safeParse(object.customMetadata)

  if (!metadata.success) {
    throw new Error(`${key} has no ${BUNDLE_METADATA.SHA256} digest in its custom metadata`, { cause: metadata.error })
  }

  return { bundle: { sha256: metadata.data[BUNDLE_METADATA.SHA256], size: object.size }, success: true }
}
```

ダイジェストのないオブジェクトは配信されません。API は `serviceUnavailable` を返し、ログにはそのオブジェクトが記録されます。続いて CLI はアーカイブをダウンロードし、通知されたサイズまでしか読まず、サイズとダイジェストが API の応答と一致し、さらにダイジェストがリリースに組み込まれた固定値とも一致しないかぎり、それを拒否します。不一致があればコード <RepositoryFact name="cliExitProtocol" /> で終了し、何も書き込みません。正しくダウンロードできた場合でも、プロジェクトのディレクトリには一度にまとめて書き込むので、中断された実行は何も残しません。

なぜ両方を確認するのでしょうか。API のダイジェストは、ダウンロードを守ります。固定値は、リリースをそれ自身のサーバーから守ります。あるバージョンのキーの下にストレージで何が置かれていても、公開済みの CLI が実行するのは、そのリリースのテストに使ったテンプレートだけです。それぞれの情報源がもう一方を確認し、どちらも単独では信頼しません。ウェブサイトのドキュメントでは、このエンドポイントとバンドルを公開するためのルールを、[CLI ライセンス API](/docs/features/cli-licence-api#publishing-bundles) で詳しく説明しています。

### 一般的なルール

テンプレート、スキーマ、バイナリ、プラグインの一覧など、CLI が実行時に取得するものは、すべてリリースの一部です。リリースとともにバージョンを付け、公開するコードの中で内容によって固定し、パッケージをインストールできるようになる前にアップロードし、サポートしているリリースがまだ要求しうるバージョンはすべて残しておいてください。

## 1 回ビルドし、出荷するものをテストする

### 1 回パッケージングし、そのバイト列をステージする

パッケージングのジョブは、フォーマット、リント、型のチェック、完全なカバレッジでのテスト、スモークテストを実行し、続いて `changeset pack` が tarball と公開計画をアーティファクトに書き出します。ステージのジョブはそのアーティファクトをダウンロードするだけで、ビルドは一切しません。npm がステージするバイト列は、そのジョブが作ったバイト列そのものです。

### ワークスペースの構文を漏らしたパッケージャー

0.1.0-beta.1 は、3 つのパッケージすべての `devDependencies` に `catalog:` の指定子を含んだまま npm に公開されました。全部で 6 つのエントリーで、レジストリには今もそのまま残っています。Bun のワークスペースは、共有するバージョンを `catalog:` と書きます。Changesets 3 がパッケージングに使えるのは npm、pnpm、Yarn だけで、Bun のワークスペースでは `npm pack` にフォールバックしていました。`npm pack` は、そうした指定子を解決しないまま、パッケージングした `package.json` にコピーします。何も失敗しませんでした。CLI の開発用の依存関係をインストールする人はいないからです。同じ漏れが `dependencies` で起きていれば、そのリリースのインストールはすべて壊れていたはずです。

根本原因の修正では、`bun pm pack` でパッケージングするように Changesets を変える `bun patch` を当てています。`bun pm pack` は各指定子が解決されるバージョンを書き込み、解決できない指定子があればパッケージングを拒否します。このパッチは、Changesets に Bun を追加するアップストリームのオープンなプルリクエスト [changesets/changesets#2334](https://github.com/changesets/changesets/pull/2334) のうちパッケージングの部分で、その変更を含むリリースが出たら削除します。修正を保っているのはテストです。スモークテストは、公開するすべてのパッケージをリリースと同じコマンドでパッケージングし、どの依存関係のフィールドにでも `catalog:` や `workspace:` が残っていれば失敗します。ワークスペースではなく、tarball をテストしてください。パッケージマネージャーのワークスペースの機能は、ソースから実行するテストには見えません。

### すべてのプラットフォームを通ってからステージする

顧客は CLI を Node と Bun で、Linux、macOS、Windows の上で実行します。プルリクエストでは、時間を節約するために、ビルドしたプログラムを Linux でしか実行しません。リリースの実行は、まさにこれからステージするコミットで、すべてのプラットフォームを確認します。9 つのジョブがパッケージをビルドし、各 OS で Node 22.12.0、24、26 を使って、さらに各ランナーで Bun を使って bin を実行します。

9 つのジョブは 1 つのマトリクスで、3 つの OS と 3 つの Node のバージョンを掛け合わせ、CLI がサポートするいちばん古い Node から始まります。このマトリクスをゲートにしているのは 2 つの設定です。ステージのジョブは、パッケージングのジョブとマトリクスの両方を `needs` に挙げ、独自の `if:` を持たないので、そのすべてが成功しないかぎり GitHub はこのジョブをスキップします。ステージのジョブに `if: always()` のような条件を付けると、この仕組みは気づかないうちに無効になります。そしてマトリクスは `fail-fast: false` を設定しているので、1 つの組み合わせが失敗してもほかの組み合わせはキャンセルされず、実行結果には、最初の 1 つだけでなく、壊れたすべてのプラットフォームが表示されます。

一度も失敗するところを見たことのないゲートは、ゲートではなく願望です。このゲートを信頼する前に、マージされた Version Packages のプルリクエストと同等のコミットから、一時的なブランチで実際のリリースワークフローを実行し、1 つの組み合わせ、Node 26 の Windows をわざと失敗させました。ほかのジョブはすべて成功し、最後の組み合わせが終わった時点でステージのジョブはスキップされました。ステージのジョブが必要とする環境にはリリースブランチからしかデプロイできないので、この検証用の実行は、たとえゲートが間違っていても何も公開できませんでした。終わった後も npm が挙げるバージョンは以前と同じで、タグもリリースも作られていませんでした。

macOS と Windows での実行を、マージのたびではなくリリースのときだけにしたことで、`main` へのマージ 1 回あたりの課金対象の時間は、この変更を入れたときの私たちの計測で 3 分の 1 から半分減りました。その分のコストは、リリースごとに 1 回払うだけです。このゲートがしないことは、この記事の終わり近くに挙げています。実行するのはプロジェクトの生成全体ではなく `--version` と `--help` で、ステージされる tarball をインストールするのではなく、各ランナーでビルドしています。

## リリースは存在してから記録する

### 公開されなかった 0.1.0-beta.3

最初のリリースワークフローは、ステージの直後に Git のタグと GitHub Releases を作成していました。その理由は、メンテナーがステージされたバージョンを承認しても、npm はワークフローのきっかけになるイベントを何も発生させないことでした。そのためタグは、バージョンが公開されたときではなく、ステージされたときに現れていました。それが何を意味したかは、リリースの履歴を見ればわかります（UTC）。

| 0.1.0-beta.0 | 11月14日 06:17                     | 11月14日 18:24         | 11月14日 18:28 |
| 0.1.0-beta.1 | 11月14日 18:38                     | 11月14日 18:40         | 11月14日 23:08 |

0.1.0-beta.3 は 11月17日にステージされ、3 日後もまだ承認を待っていました。そのとき、そのすべての変更ともう 1 つの変更を含む次のベータ版が切られ、ステージされました。オーナーが承認したのは 0.1.0-beta.4 です。0.1.0-beta.3 が npm に届くことはなく、`npm view saasyland versions` には 0.1.0-beta.2 の次に 0.1.0-beta.4 が並んでいます。それでもリポジトリには、そのための 3 つのタグと 3 つの GitHub Releases があり、誰もインストールできないパッケージを説明していました。公開されたベータ版でも、リリースのほうが 4 分から 4 時間半早く作られていました。このワークフローは、知りようのなかった 1 つのことを除いて、すべて正しく動いていました。人が承認するかどうか、そしていつ承認するかです。

### まず npm に問い合わせ、それからタグを付ける

私たちは、タグとリリースを、まずレジストリに問い合わせる別のジョブに移しました。このジョブは、公開する各パッケージについて 3 つのことを確認します。パッケージの `CHANGELOG.md` に、チェックアウトしたバージョンのセクションがあること（このセクションを書くのは Version Packages のプルリクエストだけです）、トークンの要らない公開の `npm view` で、npm がまさにそのバージョンを配信していること、そしてタグがすでに存在するかどうかです。すべてのパッケージが最初の 2 つの確認を通り、かつどこかのタグが欠けているときにだけ、Changesets のアクションを通じて `changeset git-tag` を実行します。このアクションはタグをプッシュし、変更履歴の各エントリーからリリースを作成します。それ以外の場合は何も書き込まず、その理由をサマリーに示します。

どちらの確認も、意図的に単純にしています。バージョンが配信されているとみなすのは、`npm view` がまさにそのバージョンを出力したときだけです。そのため、バージョンがない場合も、ネットワークエラーも、予期しない応答も、すべて配信されていないとみなされ、タグは付けられません。タグが存在するとみなすのは、Git がその完全な参照を解決できたときだけなので、同じ名前のブランチをタグと取り違えることはありません。この記事の最後にあるリリースキットには、1 つのパッケージ向けにこの確認を汎用化したものを載せています。

このジョブは 3 つの方法で実行されます。ステージの直後に実行されたときは、たいていバージョンがまだ承認を待っているのを見つけます。手動での実行は、オーナーが承認するとすぐにリードエージェントが行います。そして、保険として 1 日に 1 回実行されます。1 つのブランチでの実行は同じ同時実行グループを共有し、重ならずに順番を待つので、2 つの実行が同時にタグを付けることはありません。また、最初にすべてのタグを取得するので、欠けているものだけを作成し、何度実行しても問題ありません。

0.1.0-beta.5 は、このジョブを通った最初のリリースでした。そのリリースの実行での記録のジョブは 11:25 UTC に実行され、バージョンがまだ配信されていないことを確認しました。npm は 11:44:37 にそれを配信し、リードエージェントが 11:45:27 に記録のワークフローを開始すると、11:45:51 に 3 つのリリースが現れました。

### スケジュールはステップではなく安全網

毎日の保険の実行から、GitHub の `schedule` イベントについて 2 つのことを学びました。1 つ目に、「スケジュールされたワークフローは、デフォルトブランチの最新のコミットで実行される」のですが、ベータ版のタグは `beta` のコミットを指していなければなりません。そこでスケジュールされたジョブは、自分では何もタグ付けせず、リリースワークフロー自身のトリガーからブランチを読み取り、そのそれぞれで `workflow_dispatch` によって記録のワークフローを開始します。こうすると、各実行が自分のブランチにタグを付けます。2 つ目に、スケジュールはおおよそのものです。GitHub は、このイベントが「高負荷の時間帯には遅れることがある」こと、そして「キューに入ったジョブの一部が破棄されることがある」ことを述べています。私たちのスケジュールは UTC の早朝に設定していますが、11月21日から 24日にかけては、およそ 8〜11 時間遅れて始まりました。スケジュールされたジョブは、人が忘れたことを拾えます。しかし、リリースが待つステップにしてはいけません。

### 出荷されなかったものにはラベルを付ける

0.1.0-beta.3 のタグとリリースは、そのまま残しています。削除すると、何がビルドされ、何がステージされたかの記録が消えてしまうからです。その代わりに、各パッケージの変更履歴の 0.1.0-beta.3 の見出しの下に、今は「npm には公開されていません。承認される前に 0.1.0-beta.4 がこのバージョンに取って代わり、以下の変更はすべて 0.1.0-beta.4 で提供されました。」と書かれています。3 つの GitHub Releases のタイトルには「(not published)」（未公開）が付き、ウェブサイトの[リリースノート](/docs/cli/releases)も同じことを伝えています。ポリシーにもルールが 1 つ加わりました。次の Version Packages のプルリクエストをマージする前に、ステージされたリリースを承認するか却下すること、です。

## リリースを止めた空の changeset

[このシリーズの最初の記事](/blog/ai-coding-agent-guardrails)では、チェックを文言どおりに満たしたエージェントの例として、この件を短く紹介しました。ここでは経緯の全体を示します。見落としやすい種類の失敗、つまり、リリースツールが自分のルールに照らして正しく「やることは何もない」と判断するという失敗を示しているからです。

### 81 秒間に 3 回のマージ

すべて 11月20日に `beta` で起きました（UTC）。

1. **11:17:12。** あるプルリクエストが `main` から 2 つのコミットを取り込みました。そのリリースの実行が、0.1.0-beta.5 の Version Packages のプルリクエストを開きました。
2. **11:18:06。** 3 つの変更履歴に「npm には公開されていません」の注記を加えるプルリクエストがマージされました。変更履歴の編集はパッケージの変更として扱われるので、changeset のチェックが changeset を求め、そのプルリクエストは、顧客が気づけない変更についてリリースポリシーが定めていたとおりに、空の changeset を追加しました。
3. **11:18:33。** その 27 秒後に、バージョンのプルリクエストがマージされました。これは変更履歴の修正のマージ前にビルドされていたので、空の changeset を取り込んでいませんでした。
4. **11:19。** そのマージコミットでのリリースの実行はモードを選び、ほかのジョブをすべてスキップしました。0.1.0-beta.5 は `beta` でバージョンが付けられたもののステージされず、すべてのジョブは緑でした。

その間に、変更履歴の修正をマージしたコミットでのリリースの実行が、ほかの実行の後ろでキューに入った末に、すでに古くなっていたコミットから 2 つ目の Version Packages のプルリクエストを開きました。これはマージされずに閉じられました。

### モードが「none」になった理由

`changesets/action/select-mode` は、version、publish、none の 3 つのモードのいずれかを返します。v2.1.2 の公開されているソースにある判定は、次のとおりです（このサイトのフォーマットで表示しています）。

```ts
if (changesets.length > 0) {
  const hasNonEmptyChangesets = changesets.some((changeset) => changeset.releases.length > 0)
  if (hasNonEmptyChangesets) {
    return { mode: "version" }
  }
  return { mode: "none" }
}
```

保留中の changeset が 1 つでもあり、そのすべてが空なら、モードは `none` になり、0.1.0-beta.5 が npm にないことを見つけたはずの公開計画は、計算すらされません。アクション自身の考え方としては筋が通っています。空の changeset は「何もリリースしない」という意味だからです。しかし、作り直す前にマージされたバージョンのプルリクエストと組み合わさると、切られたのに出荷されないリリースが生まれました。

### 修正とルール

5 分後に、続くプルリクエストが空の changeset を削除しました。次の実行は `publish` を選び、11:25 に 0.1.0-beta.5 をステージし、オーナーが 11:44 に承認しました。現在のポリシーでは、空の changeset は `main` にだけ置くものとし、`beta` に直接加える、顧客が気づけない変更、たとえば変更履歴の訂正には changeset を付けず、その changeset のチェックの失敗を、唯一許される失敗としています。

どのチームにも当てはまるルールが 2 つあります。

- **バージョンのプルリクエストは、ブランチの現在のヘッドからビルドされたときだけマージする。** 最後の更新の後に何かがマージされていたら、リリースワークフローがそれを作り直すまで待ってください。
- **「やることは何もない」を、確認すべき結果として扱う。** ブランチにあるバージョンがレジストリにないのに何の作業も選ばなかったリリースの実行は、たとえすべてのジョブが緑でも失敗しています。

1 つ目のルールは文書にしてありますが、2 つ目はまだチェックにしていません。また、空の changeset についての私たちの文書化されたルールは、それが起きたブランチを対象にしていますが、この仕組みはプレリリースモードには依存しません。`main` で同じ競合が起きれば、同じように空の changeset が保留中のまま残ります。

## リリース元のプルリクエストのための CI

### GitHub は自分のトークンによるプッシュではワークフローを実行しない

バージョンのジョブは、ワークフローの `GITHUB_TOKEN` で Version Packages のブランチをプッシュします。GitHub のドキュメントには「`GITHUB_TOKEN` によってトリガーされたイベントは、新しいワークフローの実行を作成しない」とあり、ここで重要な例外が 1 つあります。「`workflow_dispatch` と `repository_dispatch` のイベントは、常にワークフローの実行を作成する」。そのため、これからリリースしようとしているプルリクエストには、チェックが 1 つも表示されませんでした。そうしたプルリクエストの 1 つで実行を得るために、エージェントが手作業でそれを閉じて開き直したこともあります。修正では、デフォルトのトークンはそのままにして、CI を自分で開始します。Changesets がバージョンのプルリクエストを開くか更新した直後に、同じジョブがそのプルリクエストのブランチを調べ、`gh workflow run` でそのブランチに CI のワークフローをディスパッチします。CI のワークフローが `pull_request` に加えて `workflow_dispatch` も受け付けるので、これが機能します。

このジョブは、この 1 回の呼び出しのために `actions: write` を得ます。チェックの実行はブランチのヘッドコミットに紐づくので、プルリクエストに表示されます。GitHub App のトークンでも CI はトリガーされますが、アプリと別のシークレットが必要になります。この方法なら、どちらも要りません。

### リリースの実行はキューに入れ、置き換えない

GitHub Actions の同時実行グループは、以前は保留中の実行を 1 つしか保持しませんでした。「別の実行がグループに入ると、保留中の実行はキャンセルされて置き換えられた」のです。リリースのワークフローにとって、これは誤りです。`beta` への素早いプッシュが 3 回続くと、真ん中の 1 回が失われるからです。2026年5月からは、`cancel-in-progress` が false のとき、`queue: max` によってグループは「複数の保留中の実行をキューに入れて、順番に処理する」ことができ、最大 100 件まで並べられます。

決して実行を取りこぼしてはいけないリリースのワークフロー向けに、GitHub の同時実行のドキュメントに沿った汎用的な例を示します。

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false
  queue: max
```

私たちのリリースのワークフローはこのように動くので、リリースブランチへのすべてのプッシュが自分の完全な実行を、順番に得ます。空の changeset の一件は、この保証のもう一つの面を示しています。キューに入った実行は、実行される時点でそのコミットがすでに古くなっていても、自分のコミットに基づいて判断します。キューはすべての実行を残しますが、古い実行の判断を最新のものにするわけではありません。

## どの鍵を誰が持つか

エージェントがリリースを動かし、取り消せないものはオーナーが持ちます。

| 作業                                     | エージェント                                                                | オーナー                                                                       |
| ---------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| changeset とバージョンのプルリクエスト   | 書き、ノートをレビューし、まとまりがそろったらマージする                    | なし                                                                           |
| リリースのワークフロー                   | 変更を書き、たとえば検証用の実行でそれを証明する                            | npm に届くものを決めるファイルへのすべての変更を、引用された「はい」で承認する |
| ビルド、テスト、パッケージング、ステージ | なし。マージコミットで CI が行う                                            | なし                                                                           |
| ステージされたバージョンの承認または却下 | 正確なステージ ID を渡す                                                    | 二要素認証で承認または却下する                                                 |
| タグと GitHub Releases                   | 承認の直後に記録のワークフローを開始する                                    | なし                                                                           |
| 新しいパッケージ名                       | `main` で準備し、正確な手順を書く                                           | プレースホルダーを公開し、Trusted Publisher を設定する                         |
| 問題のあるバージョン                     | 非推奨のメッセージと修正を書く                                              | 二要素認証で `npm deprecate` を実行する                                        |
| リリースノートと検証                     | クリーンなディレクトリに npm からインストールし、すべての言語でノートを書く | レビューする                                                                   |

リリースのワークフロー、Changesets の設定、そして npm に届くものを決めるパッケージのフィールドは、CLI のリポジトリの、人間によるレビューが必要なリストに入っています。そのため、それらを変更するプルリクエストは、リリースの記録方法を変えたものも含めてすべて、オーナーの書面による承認を引用しています。同じ指示ファイルは、公開も `npm trust` の実行も決してしないよう、エージェントに指示しています。そして、どのエージェントも npm の認証情報を持っていません。そもそも存在しないからです。すべてのパッケージはトークンによる公開を禁止しており、ステージできる唯一の自動化されたアイデンティティは、リリースワークフローそのものです。

検証は、リリースで終わりません。ウェブサイトのジャーニースイートは、UTC のスケジュール <RepositoryFact name="journeySchedule" /> で実行されます。プレビューのデプロイ上で Polar のサンドボックスを使って各プランを購入し、それから npm から直接取得した公開済みの CLI を使って、有効化、マシン数の上限、無効化、そしてライセンスを終わらせる返金までを通します。

```ts title="e2e/journey/cli.ts"
const child = spawn("env", ["-i", ...variables, PACKAGE_MANAGER.NPM.exec, "--yes", CLI_PACKAGE_SPEC, ...inputs, "--json"], { cwd: home })
```

これは、この記事の出発点にした原則と同じです。エージェントは、元に戻せること、または後のステップが捉えられることなら、何をしてもかまいません。そのどちらでもないステップは、エージェントが持てない要素を通じて、人が持ちます。

## リリースに問題があったとき

npm のバージョンは取り消せないので、ロールバックとは前に進むことです。

- **非推奨にしてから、パッチを出す。** 修正を示すメッセージ、たとえば「Windows で init が壊れます。1.4.1 以降を使ってください。」を付けた `npm deprecate` を、オーナーが二要素認証で実行します。修正は、ほかのリリースと同じパイプラインを通ります。セキュリティの修正やデータ損失の修正は、まとまりを待たずにすぐリリースします。
- **公開を取り消さない。** そのバージョンを固定していたすべてのプロジェクトとスクリプトが壊れ、そのバージョン番号は二度と使えません。
- **ステージされただけのものは却下する。** `npm stage reject <stage id>` は、ステージされたバージョンを公開せずに削除します。これにも二要素認証が必要です。
- **却下したバージョンに注意する。** 却下したバージョンは、リポジトリではまだそのバージョンのままで、npm にはまだないので、保留中の changeset がない次のプッシュで再びステージされます。ほかの何よりも先に、changeset を付けた修正を入れてください。

## まだ足りないもの

シリーズのほかの記事と同じく、私たち自身のリリースプロセスの弱いところを示します。

- **来歴証明がない。** リポジトリが非公開なので、パッケージには npm のレジストリ署名はあっても、来歴証明はありません。
- **安定版のチャンネルがまだない。** `latest` はまだプレースホルダーで、私たちが公開するコマンドはすべて <RepositoryFact name="cliReleaseChannel" /> タグを指定しています。最初の安定版リリースでは、README、それを確認するテスト、ウェブサイトのコマンドを一緒に切り替える必要があります。
- **浅いクロスプラットフォームのゲート。** macOS と Windows では、リリースは各ランタイムで `init` 全体ではなく `--version` と `--help` を確認し、ステージされる tarball をインストールするのではなく、各ランナーでビルドしています。
- **承認はサマリーを読むだけ。** npm の `npm stage download` は、2 つ目の要素なしで、ステージされた tarball を「ローカルで確認するために」取得できるので、承認者は承認の前に、まさにそのバイト列をインストールして実行できます。私たちは、まだそれをしていません。
- **「やることは何もない」への警報がない。** ブランチのバージョンが npm にないのに何の作業も選ばなかったリリースの実行は、何も失敗させません。
- **遅れて届く安全網。** スケジュールされた記録の実行は、予定より何時間も遅れて始まるので、リードエージェントが承認のたびに手動で開始しています。
- **承認者が 1 人。** 0.1.0-beta.3 は 3 日間承認を待ち、置き換えられました。1 人の 2 つ目の要素に頼るリリースは、その人のペースでしか進みません。
- **リリース前に本番の API に対して実行していない。** [最初の記事](/blog/ai-coding-agent-guardrails)では、私たちが望むガードレールを説明しています。各リリースの前に、公開済みの CLI を CI で本番環境に対して実行することです。それには CI のシークレットとしてライセンスキーが必要で、それは人間によるレビューが必要な変更なので、オーナーを待っています。

## コピーして使えるリリースキット

**リリースのチェックリスト**です。順番に進めます。

1. まとまりがマージされ、リリースブランチでの最後の CI の実行が緑であること。
2. どの changeset も顧客へのノートとして読め、バージョンの上げ方が正しいこと。
3. バージョンのプルリクエストが最後のマージの後に作り直され、そのチェックが緑であること。
4. リリースに必要なドキュメントが公開済みで、サーバーが読む契約に変更があれば、それがサーバーにデプロイ済みであること。
5. 承認を待っているステージ済みのリリースが残っていないこと。
6. バージョンのプルリクエストをマージする。
7. 1 回だけパッケージングし、サポートするすべてのシステムとランタイムでビルドしたプログラムを実行し、すべて成功したときだけステージする。
8. CLI がダウンロードするものをすべてアップロードして読み戻し、ステージの前に固定値と照らし合わせる。
9. リリースのすべてのパッケージを二要素認証で承認するか、却下する。
10. レジストリがリリースのすべてのパッケージを配信するようになったら、タグとリリースを作成する。
11. クリーンなディレクトリにレジストリからインストールし、CLI を実行する。
12. リリースノートを公開し、ステージされたまま公開されなかったものにはラベルを付ける。

**Changesets を使わないリポジトリ向けのステージのジョブ**です。npm のドキュメントをもとに書いた汎用的な例で、CLI 自身のワークフローではありません。トークンは不要で、何度実行しても安全です。`tarballs` という名前のアーティファクトとして tarball をアップロードする `pack` ジョブ、`release` という名前の環境、そしてこのワークフローファイル、その環境、ステージ専用の権限を指定した npmjs.com の Trusted Publisher があることを前提にしています。

```yaml
stage:
  needs: pack
  runs-on: ubuntu-latest
  environment: release
  permissions:
    contents: read
    id-token: write
  steps:
    - uses: actions/setup-node@v7
      with:
        node-version: 26
    - uses: actions/download-artifact@v8
      with:
        name: tarballs
    - name: Stage every tarball npm does not serve yet
      shell: bash
      run: |
        for tarball in *.tgz; do
          manifest=$(tar -xOzf "$tarball" package/package.json)
          name=$(jq -r .name <<< "$manifest")
          version=$(jq -r .version <<< "$manifest")
          if [ "$(npm view "$name@$version" version 2> /dev/null)" = "$version" ]; then
            echo "$name@$version is already on npm" >> "$GITHUB_STEP_SUMMARY"
          elif staged=$(npm stage publish "$tarball" --access public --tag latest --json); then
            echo "$name@$version staged as $(jq -r --arg name "$name" '.[$name].stageId' <<< "$staged")" >> "$GITHUB_STEP_SUMMARY"
          elif [ "$(jq -r '.error.code' <<< "$staged")" = E409 ]; then
            echo "$name@$version was staged by an earlier run" >> "$GITHUB_STEP_SUMMARY"
          else
            exit 1
          fi
        done
    - name: Keep npm's logs when staging fails
      if: failure()
      uses: actions/upload-artifact@v7
      with:
        name: npm-logs
        path: ~/.npm/_logs/
        retention-days: 7
```

**ステージだけを許可された Trusted Publisher**です。メンテナーが二要素認証を使って、パッケージごとに 1 回設定します。

```sh
npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish
```

**npm が配信しているものだけにタグを付けるスクリプト**です。1 つのパッケージ向けの汎用的な例で、何度実行しても安全なので、たとえば承認のたびに実行できます。

```sh
name=$(jq -r .name package.json)
version=$(jq -r .version package.json)
if [ "$(npm view "$name@$version" version 2> /dev/null)" != "$version" ]; then
  echo "npm does not serve $name@$version yet, so nothing is tagged"
  exit 0
fi
if git rev-parse -q --verify "refs/tags/v$version" > /dev/null; then
  exit 0
fi
git tag "v$version"
git push origin "v$version"
gh release create "v$version" --verify-tag --notes-file release-notes.md
```

**読む前にサーバーと固定値に照らして確認するダウンロード**です。Node 向けの TypeScript で書いた汎用的な例です。

```ts
import { createHash } from "node:crypto"
import { gunzipSync } from "node:zlib"

const MAX_CONTENT_BYTES = 256 * 1024 * 1024

interface BundleAnswer {
  readonly sha256: string
  readonly size: number
}

export const verifiedContent = (archive: Buffer, answer: BundleAnswer, pinned: string): Buffer => {
  if (archive.length !== answer.size) {
    throw new Error(`Expected ${answer.size} bytes and received ${archive.length}`)
  }

  const content = gunzipSync(archive, { maxOutputLength: MAX_CONTENT_BYTES })
  const digest = createHash("sha256").update(content).digest("hex")

  if (digest !== answer.sha256 || digest !== pinned) {
    throw new Error("The download is not the bundle this release was tested with")
  }

  return content
}
```

**指示ファイルに加えるリリースのルール**です。オーナーが承認するものを、エージェントがあらかじめ用意するようにします。

```md
## Releases

- Never run npm publish, npm unpublish, npm stage approve or npm stage reject. CI stages releases, and a maintainer approves them with 2FA.
- Every change to a published package adds a changeset written for customers: what changes for them and what they have to do.
- Merge a version pull request only when it was built from the branch's current head, and never while a staged release awaits approval.
- After an approval, start the records workflow, install the release from npm in a clean directory and run it before announcing anything.
- Label a version that was staged and never published in its changelog and its GitHub Release. Never delete its tag.
```
