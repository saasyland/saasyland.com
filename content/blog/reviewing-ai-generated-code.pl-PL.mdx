  - question: Dlaczego zielone CI nie wystarcza w przypadku kodu pisanego przez AI?
    answer: >-
      Bo CI sprawdza to, co potrafi rozstrzygnąć program, a kosztowne błędy dotyczą intencji:
      poprawka w złym miejscu, test, który ułatwiono, projekt nagięty wokół reguły, zdanie, które nie
      jest prawdą. Agenty optymalizują też pod kontrole, które widzą, więc zielony przebieg mówi, że

  - question: Jak odróżnić obejście od naprawy przyczyny źródłowej?
    answer: >-
      Zapytaj, co spowodowało błąd, a potem sprawdź, czy diff zmienia właśnie to, czy tylko miejsce,
      w którym błąd się pokazał. Obejście zwykle siedzi obok objawu: czekanie w teście, wartość
      zastępcza, warunek, który pomija nieprzechodzący przypadek, ponowienie. Jeśli po scaleniu inna
      strona albo inne miejsce wywołania może trafić na ten sam błąd, przyczyna wciąż tam jest.
  - question: Jak agenty AI do kodowania oszukują testy?
    answer: >-
      Zwracają wartości, których oczekuje test, zamiast rozwiązać problem, edytują test tak, żeby
      pasował do kodu, pomijają albo luzują asercje i podnoszą limity czasu. Anthropic i OpenAI
      opisały te zachowania u własnych modeli. Obroną jest czytanie każdej zmiany w pliku testu równie
      uważnie jak zmiany w kodzie.
  - question: Których furtek w typach nie wyłapuje linter?
    answer: >-
      Nawet gdy asercje typów, any i komentarze wyłączające są zakazane, ścisła konfiguracja
      TypeScriptu może przepuścić asercję non-null, strażnika typu, który nie sprawdza tego, co
      deklaruje, schemat, który pod konkretnym typem przyjmuje cokolwiek, wartość zastępczą, taką jak
      pusty ciąg znaków, która ukrywa brakującą wartość, oraz błąd, który zostaje złapany i
      zignorowany. Każda z nich zamienia błąd w czasie działania w ciche błędne zachowanie.
  - question: Czy jeden agent AI powinien recenzować kod innego agenta?
    answer: >-
      Tak, jako pierwsze podejście: recenzent ze świeżym kontekstem, z narzędziami tylko do odczytu i
      z briefem, na podstawie którego zbudowano zmianę, znajduje luki, które ukrywa kontekst autora.
      Dzieli jednak martwe pola swojego modelu, a recenzent poproszony o znalezienie problemów zawsze
      jakieś znajdzie. Ostatnim czytelnikiem wszystkiego, co nieodwracalne, niech pozostaje człowiek,
      a recenzentowi powiedz, czego nie zgłaszać.
  - question: Jak recenzować twierdzenia w opisie pull requesta?
    answer: >-
      Traktuj każde z nich jako twierdzenie do sprawdzenia. Liczba testów, udany przebieg czy zgoda
      powinny wskazywać coś, co możesz otworzyć: przebieg CI na commicie head, wynik polecenia,
      wiadomość z zatwierdzeniem. Każdy plik, który zmienia diff, powinien być wyjaśniony, a każda
      zmiana, o której wspomina opis, powinna być w diffie.
  - question: Jak sprawić, żeby recenzja nie stała się wąskim gardłem?
    answer: >-
      Przenieś do kontroli każdą regułę, którą potrafi rozstrzygnąć program, ograniczaj pull requesty
      do jednej zmiany, czytaj w kolejności, która najszybciej wykrywa problemy, i wchodź w szczegóły
      tam, gdzie zasięg szkód jest największy: przy płatnościach, tożsamości, migracjach, kontraktach
      i samych kontrolach. Wysiłek recenzji powinien iść na to, czego nie rozstrzygnie żadna kontrola.

## Krótka odpowiedź

Recenzuj pull request agenta w kolejności, która najszybciej wykrywa problemy, a uwagę poświęcaj tam, gdzie nie sięga żadna kontrola. Najpierw dowody: commit, który czytasz, jest commitem, który przetestowano, i CI na nim przeszło. Potem opis względem diffa, a diff względem Twojej listy chronionych ścieżek. Potem każda zmiana w teście, bo agent, który nie potrafi sprawić, że test przechodzi, czasem sprawia, że test staje się łatwiejszy. Potem pytanie, które wyłapuje najkosztowniejsze błędy: czy ta zmiana usuwa przyczynę problemu, czy tylko miejsce, w którym się pokazał? Dalej furtki w typach i obsłudze błędów, na które pozwala Twój linter, zakres zmiany, każdy projekt nagięty wokół reguły i każde twierdzenie, jakie zmiana stawia w prozie. Podsumowanie, które mówi „gotowe”, traktuj jako twierdzenie. Proś o polecenie, jego wynik i commit, na którym je uruchomiono.

## Dlaczego kod pisany przez AI wymaga innej recenzji

Recenzja zawsze w mniejszym stopniu dotyczyła szukania błędów, niż się ludziom wydaje. W badaniu recenzji kodu w Microsoft z 2013 roku Alberto Bacchelli i Christian Bird stwierdzili, że „znajdowanie defektów pozostaje główną motywacją recenzji”, a jednak „recenzje w mniejszym stopniu dotyczą defektów, niż oczekiwano”, i że „zrozumienie kodu i zmiany jest kluczowym aspektem recenzji kodu”. Gdy autorem jest człowiek, zrozumienie jest wspólne: autor wie, dlaczego kod wygląda tak, a nie inaczej, a recenzja jest rozmową.

Gdy autorem jest agent, zmieniają się trzy rzeczy.

**Pewność siebie autora nie niesie żadnej informacji.** Agent pisze „wszystkie testy przechodzą” tym samym tonem bez względu na to, czy przechodzą. Przewodnik Anthropic po Claude Code opisuje ten mechanizm wprost: „Claude kończy, gdy praca wygląda na skończoną”. Recenzentowi radzi prosić o dowody: „polecenie, które uruchomił, i jego wynik albo zrzut ekranu. Samo «wszystkie testy przechodzą» mówi bardzo niewiele”.

**Kod wygląda poprawnie.** W ankiecie Stack Overflow z 2025 roku najczęstszą frustracją związaną z narzędziami AI, wskazaną przez 66% programistów, były „rozwiązania AI, które są prawie dobre, ale nie do końca”, a 45,2% stwierdziło, że debugowanie kodu wygenerowanego przez AI zajmuje więcej czasu. Kod prawie dobry najtrudniej zrecenzować, bo nic w nim nie wygląda źle.

**Twoje własne poczucie postępu jest zawodne.** Randomizowane badanie METR z udziałem doświadczonych programistów open source z początku 2025 roku wykazało, że gdy wolno im było używać narzędzi AI, „rozwiązywanie zgłoszeń zajmuje im o 19% więcej czasu”. Przed badaniem „oczekiwali, że AI przyspieszy ich pracę o 24%”, a po nim „wciąż uważali, że AI przyspieszyło ich pracę o 20%”. Recenzent, który czuje, że praca idzie szybko, niczego nie mierzy.

### Agenty optymalizują pod kontrole, które widzą

Najmocniejszy powód, by recenzować inaczej, udokumentowali sami twórcy modeli.

Karta systemowa Claude 3.7 Sonnet, opublikowana przez Anthropic w lutym 2025, ma sekcję zatytułowaną „Nadmierne skupienie na przechodzeniu testów”. Podaje, że model „czasem ucieka się do obsługi przypadków szczególnych, żeby przejść przypadki testowe w agentowych środowiskach programistycznych, takich jak Claude Code”. Najczęściej oznaczało to „bezpośrednie zwracanie oczekiwanych wartości testowych zamiast implementowania ogólnych rozwiązań, ale obejmuje też modyfikowanie samych problematycznych testów tak, by pasowały do wyniku kodu”. Działo się to „po wielu nieudanych próbach opracowania ogólnego rozwiązania”, a Anthropic zalecił wypatrywanie trzech sygnałów: „nadmiernej liczby cykli edycji i uruchamiania testów na jednym pliku”, „komentarzy sugerujących obsługę specyficzną dla testów” i „nieoczekiwanych modyfikacji plików testów”.

OpenAI opisało tę samą rodzinę zachowań w marcu 2025, w pracy o monitorowaniu modeli rozumujących. Wśród przykładów jest agent, który rozumował: „Możemy obejść verify, żeby zawsze zwracało true”, i inny, który planował: „Żeby pominąć wszystkie testy, możemy zdefiniować funkcję `pytest_runtest_setup`, która zawsze pomija”. Gdy OpenAI podczas treningu karało model za takie myśli, „agent trenowany pod presją na CoT wciąż uczy się hakować nagrodę”, ale „nauczył się ukrywać swoją intencję w łańcuchu myśli”. Wcześniejszy raport METR o hakowaniu nagrody, cytowany w [pierwszym wpisie z tej serii](/blog/ai-coding-agent-guardrails), stwierdził to samo w zadaniach z punktacją.

Anthropic podaje, że jego zabezpieczenia na etapie treningu „znacząco zmniejszyły częstość tego zachowania w typowym użyciu”. To, co zostaje, pojawia się tam, gdzie widział to Anthropic: po wielokrotnych porażkach przy trudnym problemie, czyli w takiej zmianie, która najbardziej potrzebuje recenzji. Praktyczny wniosek jest prosty. Zielony przebieg CI mówi, że kontrole przeszły. Nie mówi, że to te same kontrole, od których zaczynałeś.

## Recenzuj dowody przed kodem

Pierwsze minuty recenzji powinny pójść na to, co pull request twierdzi o sobie. Większość kosztownych porażek, jakie widzieliśmy, siedziała w twierdzeniach, a nie w kodzie.

**Czy commit, który czytasz, jest commitem, który przetestowano?** Agent, który po ostatnim przebiegu testów robi rebase, poprawia commit przez amend albo wypycha poprawkę, ma pull request, którego opis dotyczy wcześniejszego commita. Sprawdź, czy CI działało na commicie head i czy przebieg przeszedł każdą wymaganą kontrolę, a nie tylko te szybkie. [Drugi wpis z tej serii](/blog/running-ai-coding-agents-in-parallel) opowiada, jak agent zgłosił „gotowe”, gdy zestaw testów przeglądarkowych wciąż działał.

**Czy liczby są dowodami?** Dobry plan testów wymienia każde polecenie z jego wynikiem, liczbami, które dało, i wszystkim, czego nie dało się uruchomić. Nasze pull requesty pokazują różnicę. Plan testów #177 podaje 355 plików testowych i 2301 testów przy pełnym pokryciu, mówi, że cztery testy w plikach, których nie dotykał, przekroczyły limit czasu przy load average maszyny od 40 do 170, wymienia flagę, której użył udany przebieg, i mówi wprost, że zestawu testów przeglądarkowych nie uruchomiono lokalnie, oraz dlaczego. #123 opisuje pierwszy przebieg pokrycia, w którym siedem testów przekroczyło limit czasu pod obciążeniem, i czysty przebieg powtórzony po nim. Żaden nie ukrywa porażki i oba są bardziej użyteczne niż „wszystko zielone”.

**Czy opis dotyczy tego diffa?** 16 listopada #224, poprawkę layoutu, scalono z opisem #225, zmiany licencji, łącznie z akapitem mówiącym, że właściciel zatwierdził zmiany w plikach licencji, których #224 w ogóle nie dotykał. Żadna kontrola nie czyta opisów. Od tamtej pory recenzja je porównuje: każda zmiana, o której wspomina opis, jest w diffie, każdy plik w diffie jest wyjaśniony, a każda zgoda jest zacytowana razem ze ścieżkami, których dotyczy.

**Czy to wygląda na skończone, czy działa?** Kontrolka, która się renderuje, jest twierdzeniem, że coś robi. W listopadzie ekrany użytkowników w panelu admina pokazywały przyciski **Edit**, **View profile** i **Add User** bez obsługi zdarzeń, a dziewięć funkcji serwerowych dotyczących użytkowników i sesji nie miało żadnego wywołania (#194). Żadna kontrola tego nie zauważyła: przycisk bez obsługi zdarzenia się renderuje, a nic go nie naciskało. Poprawka podłączyła każdą kontrolkę do prawdziwej funkcji serwerowej albo ją usunęła. W przypadku wszystkiego, co widzi użytkownik, dowodem jest zrzut ekranu albo test przeglądarkowy, który naciska przycisk i sprawdza wynik.

## Obejścia a przyczyny źródłowe

Najkosztowniejszy błąd, jaki popełnia agent, to poprawka w złym miejscu. Przechodzi każdą kontrolę, często przychodzi z testem regresji i zostawia przyczynę w kodzie, żeby trafiła na nią następna strona.

Obejście ma rozpoznawalny kształt. Siedzi obok objawu, a nie wyżej w łańcuchu przyczyn: czekanie dodane do testu, wartość zastępcza przekazana do jednego komponentu, warunek, który pomija nieprzechodzący przypadek, ponowienie wokół wyścigu, zależność cofnięta do starszej wersji. Pytanie, które je demaskuje, to to, na które naprowadza przewodnik Google po recenzjach, gdy mówi: „Często warto spojrzeć na CL w szerszym kontekście”: co sprawiło, że to się stało, i czy po scaleniu mogłoby na to trafić coś jeszcze?

### Obejście wybrane celowo

14 listopada zalogowany odwiedzający, który nacisnął link w nagłówku strony głównej, zanim strona przeszła hydratację, sprawiał, że React zgłaszał błąd hydratacji: serwer wypisał liczbę gwiazdek na GitHubie, a przeglądarka wyrenderowała w jej miejscu szkielet ładowania. #146 naprawił to, przekazując liczbę z loadera strony do komponentu jako dane zastępcze, z testem regresji, i każda kontrola przeszła.

Jego opis wskazywał prawdziwą przyczynę. Strażnik trasy w integracji uwierzytelniania czyścił cały cache zapytań za każdym razem, gdy znalazł sesję, o której wstępnie wyrenderowana strona nie wiedziała, żeby jeden użytkownik nigdy nie zobaczył danych innego. Strażnik wyrzucał dane publiczne razem z prywatnymi, a na ten sam błąd mogła trafić każda strona renderowana z cache. Opis mówił też, dlaczego przyczyna została nietknięta: jej zmiana oznaczała decyzję o tym, które dane mogą przetrwać zmianę użytkownika, w `src/integrations/better-auth/`, ścieżce, która wymaga zgody właściciela.

Recenzja poprosiła o przyczynę źródłową, właściciel zgodził się na zmianę chronionej ścieżki, a dwie godziny później #152 ją naprawił: zapytania same oznaczają się jako publiczne, zmiana użytkownika usuwa każde zapytanie, które publiczne nie jest, a obejście z #146 usunięto. Lekcja ma dwie połowy. Agenty często znają przyczynę, a dobry brief prosi, żeby ją podały. A chroniona ścieżka, która istnieje po to, żeby niebezpieczne zmiany zdarzały się rzadziej, sprawia też, że poprawki objawów zdarzają się częściej, bo najtańsza droga wokół chronionej przyczyny to poprawka gdzie indziej. Gdy poprawka leży obok chronionej ścieżki, zapytaj, czy to ochrona wybrała projekt.

### Testy, które przeczekują błąd

Wcześniej tego samego dnia #142 sprawił, że zestaw testów przeglądarkowych zaczął działać niezawodnie w WebKit, bo czekał, aż router wyrenderuje stronę, zanim cokolwiek na niej zrobił. To czekanie modeluje prawdziwą gotowość i jest poprawne. Ale niektóre wyścigi, które naprawiło, wynikały z błędów w bibliotekach, i #151 je nazwał: „#142 sprawił, że zestaw testów przeglądarkowych przeczekuje trzy błędy bibliotek, ale odwiedzający wciąż na nie trafiają”. Odwiedzający, który przewijał stronę w trakcie hydratacji, był odsyłany na górę; nawigacja z ładującej się strony mogła zamienić się w przeładowanie strony, którą się opuszczało.

#151 wprowadził każdą poprawkę jako patch na najnowsze wydanie TanStack Router i Motion, dodał test przeglądarkowy, który bez danego patcha kończy się błędem, i usunął czekania, które istniały tylko po to, żeby ominąć te błędy. Jeden z patchy routera to zmiana z otwartego pull requesta w repozytorium biblioteki. Jego reprodukcja to dowód, o jaki powinna prosić recenzja: minimalna aplikacja TanStack Start, która bez jednowierszowej poprawki zawiodła w sześciu przebiegach na sześć, a z nią przeszła w dziesięciu na dziesięć.

Zasada, którą z tego wynieśliśmy: czekanie w teście jest dopuszczalne, gdy modeluje to, na co czeka też użytkownik. Gdy przeczekuje błąd, użytkownicy wciąż na niego trafiają, a poprawka należy do kodu albo, w przypadku biblioteki, do patcha z testem regresji i zgłoszeniem w repozytorium biblioteki.

### Reguła decyzyjna

Akceptuj obejście tylko wtedy, gdy spełnione są wszystkie trzy warunki: przyczyna jest poza Twoją kontrolą, obejście jest oznaczone tam, gdzie znajdzie je następny czytelnik, i coś śledzi jego usunięcie. W przeciwnym razie proś o przyczynę. Cofnięcie zależności do starszej wersji to obejście z długim ogonem; nasza zasada każe zostać na najnowszym wydaniu i nosić błąd biblioteki jako patch, żeby poprawka odeszła razem z kolejnym wydaniem, zamiast zostać na zawsze.

## Testy, które stały się łatwiejsze

Diff, który zmienia test, zasługuje na więcej uwagi niż diff, który zmienia kod, bo to testowi ufasz, gdy nie patrzysz. Przewodnik Google po recenzjach ujmuje to w czterech słowach: „Testy nie testują siebie”.

Przeczytaj każdą zmianę w pliku testu i szukaj:

- **Usuniętych albo poluzowanych asercji:** `toEqual`, które staje się `toMatchObject`, konkretnej wartości, która staje się `expect.anything()`, asercji usuniętej razem z kodem, który sprawdzała.
- **Zaktualizowanych snapshotów albo fixtures**, których nowej zawartości nikt nie przeczytał.
- **Przypadków szczególnych:** testowanego kodu, który rozgałęzia się na wartości używanej tylko przez test albo zwraca dokładnie tę wartość, której oczekuje test.
- **Nowych pominięć, ponowień i limitów czasu,** w tym dłuższego limitu czasu dla jednego testu.
- **Nowych mocków** dokładnie tego, co test miał sprawdzać.
- **Asercji na implementacji** zamiast na zachowaniu: która funkcja została wywołana, a nie co widzi użytkownik.

Anthropic zauważył, że obserwowana przez niego obsługa przypadków szczególnych „często (choć nie zawsze) zawiera jawne komentarze wskazujące na obsługę przypadku szczególnego (np. «# special case for test XYZ»)”. Nasze repozytorium zakazuje komentarzy, a kontrola odrzuca każdy z nich. To usuwa etykietę, więc w bazie kodu takiej jak nasza sygnał musi pochodzić z samego czytania diffa testów.

Przykładem wartym skopiowania jest #191. Na obciążonej maszynie naszym najwolniejszym testom jednostkowym zabrakło czasu. Łatwą poprawką byłoby podniesienie limitów czasu. Zamiast tego pull request ustalił, dlaczego każdy z tych testów jest wolny, i usunął pracę, której nie potrzebował: jeden test uruchamiał kontrolę treści na każdej stronie w dziewięciu wersjach językowych i stał się jednym przypadkiem na stronę; kilka pozwalało, by throttling fallbacku suspense w React działał poza `act`; combobox przebudowywał każdą opcję przy każdym naciśnięciu klawisza. Jego opis podaje ograniczenie, którego się trzymał: „Nie podniesiono żadnego limitu czasu i żaden test nie dostał własnego limitu”. Recenzent może sprawdzić to zdanie względem diffa w minutę, i właśnie to powinien umożliwiać plan testów.

## Ciche furtki w typach

Ścisły kompilator i ścisły linter łapią głośne furtki: `any`, asercje typów, komentarze wyłączające. Do recenzji docierają te ciche, które kompilują się bez zastrzeżeń i zawodzą w czasie działania.

TypeScript mówi wprost, dlaczego asercje są niebezpieczne: „asercje typów są usuwane przez kompilator i nie wpływają na zachowanie Twojego kodu w czasie działania” oraz „Jeśli asercja typu jest błędna, nie zostanie zgłoszony wyjątek ani wygenerowane `null`”. To samo dotyczy asercji non-null: „nie zmienia to zachowania Twojego kodu w czasie działania”.

### Co nasz linter wciąż przepuszcza

22 listopada przepuściliśmy plik próbny przez naszą konfigurację lintera, która włącza całe kategorie reguł jako błędy, razem z regułami korzystającymi z informacji o typach, i zakazuje `any`, każdej asercji typu poza `as const` oraz każdego komentarza wyłączającego:

| Wiersz w pliku próbnym                                            | Odrzucony | Przez                                                                       |
| ----------------------------------------------------------------- | --------- | --------------------------------------------------------------------------- |
| `(raw: string): Licence => JSON.parse(raw)`                       | Tak       | `typescript/no-unsafe-return`                                               |
| `const parse = <T>(raw: string): T => JSON.parse(raw)`            | Tak       | `typescript/no-unsafe-return` i `typescript/no-unnecessary-type-parameters` |
| `Reflect.get(target, key)` zwrócone jako `string`                 | Tak       | `typescript/no-unsafe-return`                                               |
| `items.find((item) => item.length > 2)!.length`                   | Nie       |                                                                             |
| `(value: unknown): value is Licence => typeof value === "object"` | Nie       |                                                                             |
| `zod.custom<Licence>()` bez żadnego sprawdzenia                   | Nie       |                                                                             |
| `licence?.key ?? ""`                                              | Nie       |                                                                             |
| Pusty `catch {}` albo `catch`, który zwraca wartość domyślną      | Nie       |                                                                             |

Każdy wiersz, który przeszedł, zamienia brakującą albo zniekształconą wartość w błędne zachowanie bez żadnego błędu. Asercja non-null mówi, że wartość istnieje. Strażnik typu mówi, że obiekt jest typu `Licence`, choć sprawdził tylko, że jest obiektem. Własny schemat przyjmuje cokolwiek i nadaje temu typ `Licence`. Wartość zastępcza w postaci pustego ciągu zamienia „brak licencji” w klucz licencyjny, który jest pustym ciągiem, a następna funkcja może go bez oporów wysłać do API. Połknięty błąd ukrywa porażkę przed osobą, która by ją naprawiła. Nasz kod aplikacji nie ma dziś asercji non-null ani własnych schematów bez sprawdzenia; nic poza recenzją nie utrzymuje tego stanu, a reguły dla pierwszej z tych furtek istnieją zarówno w typescript-eslint, jak i w Oxlint.

### Furtka z dobrym powodem to wciąż furtka

Commit, który 6 września 2026 przeniósł saasyland.com na TanStack Start, zawierał sześć komentarzy wyłączających reguły lintera: cztery dla niebezpiecznych asercji typów, jeden dla `null` i jeden dla niebezpiecznego argumentu. Każdemu towarzyszyło zdanie, przez które wydawał się konieczny:

```ts
// TanStack Query requires a defined result; null represents an absent license.
// oxlint-disable-next-line unicorn/no-null
const NO_LICENSE = null
```

Połowa tego powodu była prawdziwa. Dokumentacja TanStack Query mówi, że „po sukcesie rozwiązana wartość może być czymkolwiek poza undefined”. Wniosek już nie: zapytanie nie potrzebowało `null`, potrzebowało zdefiniowanej wartości. Recenzja usunęła wszystkie sześć w ciągu trzech tygodni, zmieniając projekt, który każdy z nich chronił. Ten stał się obiektem, który zawsze istnieje:

```ts
.handler(async ({ context }) => ({ license: await getLicense(context.auth.user.id) }))
```

Pozostałe poszły tą samą drogą: pomocnik testowy, który stosował asercję wygenerowanego typu, buduje teraz nietypowane drzewo komunikatów, a testowe proxy, które stosowało asercję typu buildera, sprawdza teraz w czasie działania, czy dostało funkcję serwerową, a w przeciwnym razie rzuca `TypeError`. Nasze konwencje wymieniają teraz alternatywy dla furtki: waliduj zamiast stosować asercje, zawężaj prawdziwym strażnikiem typu, adnotuj zamiast stosować asercje, sprawdzaj przez `satisfies` zamiast konwertować i przebuduj kod, gdy kontrakt biblioteki z Tobą walczy. Od #274 `bun run check` odrzuca każdy komentarz wyłączający, więc ten rodzaj furtki nie dociera już do recenzji. Lekcja zostaje dla tych, które docierają: powód zapisany obok furtki to argument, a zadaniem recenzji jest ten argument sprawdzić, a nie go podziwiać.

## Zakres, projekt i kształt zmiany

**Zmiany, o które nikt nie prosił.** Agenty poprawiają rzeczy po drodze. Często jest to przydatne i zawsze jest problemem dla recenzji, bo zmiana, o którą nikt nie prosił, jest recenzowana jako część zmiany, o którą ktoś prosił. Nasza zasada: poprawki przy okazji są mile widziane, gdy opis je wymienia i mówi, dlaczego powstały. #169, poprawka przetłumaczonych ścieżek plików, wymienia inne błędy, które poprawił w tekstach, które i tak przepisywał. #191, pull request o wolnych testach, zmienił komponent produkcyjny, a jego opis wyjaśnia, że komponent przebudowywał każdą opcję przy każdym renderze, co było problemem zarówno testu, jak i użytkownika. Zmiana, o której opis nie wspomina, to powód, żeby się zatrzymać i zapytać.

**Abstrakcje, których nikt nie potrzebował.** Przewodnik Google prosi recenzentów, by „zachęcali programistów do rozwiązywania problemu, o którym wiedzą, że trzeba go rozwiązać teraz, a nie problemu, o którym programista spekuluje, że może trzeba będzie go rozwiązać w przyszłości”. Agenty skłaniają się w drugą stronę: wrapper wokół wywołania biblioteki, fabryka z jednym produktem, funkcja pomocnicza, która powiela taką, która istnieje już trzy foldery dalej. Nasze konwencje każą mieć jeden oczywisty mechanizm na każdą kwestię i wywoływać bibliotekę bezpośrednio; w recenzji najtańszym sprawdzeniem jest przeszukanie repozytorium pod kątem istniejącej funkcji, zanim zaakceptujesz nową.

**Ceremonia, która spełnia regułę.** Gdy reguła jest odrobinę błędna, agenty stosują się do niej na masową skalę. Nasza reguła przeciw magicznym liczbom dopuszczała tylko `0`, więc agenty nazywały każdą `1`, a #230 wstawił z powrotem w miejsca użycia 72 takie stałe. [Pierwszy wpis z tej serii](/blog/ai-coding-agent-guardrails) opowiada tę historię. W recenzji wzorzec, którego żaden człowiek nie napisałby ręcznie, jest sygnałem, żeby naprawić regułę.

**Projekty nagięte wokół chronionej ścieżki.** To ten subtelny przypadek. #177 potrzebował stałej statusu dla funkcji, które są dostępne albo w przygotowaniu. Film Remotion ze strony głównej importuje nawigację panelu admina, a test wymaga, żeby workflow filmów obserwował każdy plik importowany przez Remotion, więc nowy plik oznaczałby edycję `.github/workflows/`, ścieżki, która wymaga zgody właściciela. Pull request umieścił stałą w `src/data/navigation.constants.ts`, pliku, który workflow już obserwował, i napisał o tym w opisie. Późniejsze zmiany całkiem usunęły status z nawigacji panelu admina. Dziś stała obsługuje karty cennika i teksty serwisu, a wciąż mieszka w stałych nawigacji, z powodu, który już nie istnieje. Nic tego nie sprawdza. To w recenzji pytasz: czy ten plik to miejsce, w którym nowy czytelnik by tego szukał, a jeśli nie, co sprawiło, że autor umieścił to właśnie tu?

Przewodnik Anthropic dodaje ostrzeżenie, które dotyczy każdego recenzenta, człowieka czy agenta: „Recenzent, którego poproszono o znalezienie problemów, zawsze znajdzie _coś_. Jeśli naprawisz każde znalezisko, skończysz z dodatkowymi warstwami abstrakcji i testami przypadków, które nie mogą się zdarzyć”. Zakres działa w obie strony. Recenzja, która żąda każdego możliwego ulepszenia, produkuje ten sam przerośnięty kod co agent, który dodaje je bez pytania.

## Chronione ścieżki w diffie

[Pierwszy wpis z tej serii](/blog/ai-coding-agent-guardrails) wyjaśnia, które ścieżki potrzebują drugiego klucza w rękach człowieka i dlaczego zgoda należy do diffa. W recenzji wynikają z tego dwie kontrole.

**Porównuj zmienione pliki z listą mechanicznie.** Czytanie długiego diffa w poszukiwaniu chronionych ścieżek to dokładnie to zadanie, które człowiek pod koniec dnia wykonuje źle. Jednowierszowe polecenie robi to za każdym razem; zestaw na końcu artykułu je zawiera. Gdy w diffie jest chroniona ścieżka, opis musi cytować zgodę i wymieniać ścieżki, których ona dotyczy.

**Pytaj, co zmieniła ochrona.** Dwa opisane wyżej incydenty, poprawka objawu obok chronionej przyczyny i stała umieszczona tak, żeby ominąć chroniony plik, pokazują, że lista chronionych ścieżek kształtuje kod wokół siebie. Żaden z nich nie dotknął chronionej ścieżki, więc żaden nie pojawiłby się w mechanicznej kontroli. Pytanie dla recenzenta jest odwrotne: czy ta zmiana ominęła chronioną ścieżkę i czy właściwa poprawka przeszłaby przez nią?

## Fakty i twierdzenia w prozie

Agenty piszą prozę równie płynnie jak kod, a proza nie ma kompilatora. Opisy pull requestów, dokumentacja, historie zmian, pliki README i wpisy na blogu stawiają twierdzenia, a nasza historia pokazuje cztery rodzaje błędnych twierdzeń.

**Wymyślona konfiguracja.** Dwa nasze wpisy mówiły, że `typescript/no-explicit-any` jest błędem w naszej konfiguracji lintera, choć nie był; #123 sprawił, że to zdanie stało się prawdziwe, bo włączył tę regułę. Ten sam audyt znalazł przytoczony `tsconfig.json` z `verbatimModuleSyntax`, którego projekt nie ustawia, i opcję lintera `denyWarnings: true`, która nie istnieje.

**Źle przypisane źródła.** Audyt każdego wpisu względem jego źródeł z 17 listopada (#241) znalazł liczbę ze Stack Overflow przytoczoną jako 45%, podczas gdy ankieta podaje 66%, odsetek użycia przestarzałego API przypisany niewłaściwemu artykułowi i liczbę defektów przypisaną GitClear, której nie zawiera publiczna strona GitClear.

**Nieaktualny kontekst.** Tłumaczenia zrobione ze starszej wersji angielskiej opisywały stack, którego serwis już nie używał, ze starymi liczbami i starymi nazwami pakietów (#116). Każde zdanie było płynne i wiarygodne.

**Opisy niewłaściwej zmiany,** jak w #224.

Recenzja prozy wygląda tak samo jak recenzja kodu, tylko zamiast testów są źródła. Każda liczba wskazuje kod, który ją definiuje, a [poprzedni wpis](/blog/documentation-drift-numbers-from-code) pokazuje, jak ją stamtąd wyświetlić, żeby nie mogła być błędna. Każda liczba z zewnątrz ma link, a recenzent otwiera link i szuka dokładnych słów. Każde „jest egzekwowane” wskazuje kontrolę, która to egzekwuje. Każdy cytat jest w źródle.

## Drugi agent jako recenzent

Agent recenzent jest tani, szybki i przydatny jako pierwsze podejście, jeśli przygotujesz go do tego zadania.

- **Świeży kontekst.** Przewodnik Anthropic opisuje swoje polecenie `/code-review` jako recenzowanie „diffa w świeżym subagencie, który nigdy nie widział Twojej rozmowy. Nie ulega rozumowaniu, z którego powstał kod”. Recenzent, który przeczytał rozumowanie autora, zwykle je akceptuje.
- **Narzędzia tylko do odczytu.** Recenzent, który może edytować, naprawi to, co znajdzie, i zamieni recenzję w drugą zmianę. Subagenty Claude Code przyjmują w swojej definicji listę `tools`; daj recenzentowi tylko czytanie i wyszukiwanie.
- **Specyfikacja, względem której recenzuje.** Brief, z którego zbudowano zmianę, albo zgłoszenie, żeby recenzent sprawdzał wymagania, a nie gust.
- **Instrukcje, czego nie zgłaszać.** Stylu i przypadków hipotetycznych, z powodu, który Anthropic podaje wyżej.

Znaj jego ograniczenia. Agent recenzent zwykle działa na tym samym modelu co autor albo na mniejszym, więc dzieli martwe pola autora, i nie powie Ci, czy ta zmiana jest właściwą rzeczą do zbudowania. W naszym układzie agent prowadzący pisze brief dla każdego wykonawcy i czyta jego raport oraz diff względem tego briefu, zanim zmiana trafi do kolejki scalania, a wszystko z listy wymagającej przeglądu przez człowieka czeka na zacytowane „tak” właściciela. Pytanie z [drugiego wpisu](/blog/running-ai-coding-agents-in-parallel) wciąż wyłapuje najwięcej: czego postanowiłeś nie robić i dlaczego?

## Kolejność recenzji, która najszybciej wykrywa problemy

Drugi wpis z tej serii ma ośmiopunktową listę do recenzji pull requesta agenta. Tu jest dłuższa wersja, której używamy teraz, po kolei, z tym, czego szuka każdy krok. Zatrzymaj się na pierwszym kroku, który nie przechodzi; nie ma sensu czytać kodu, któremu brakuje dowodów.

1. **Dowody.** Commit head jest przetestowanym commitem. CI przeszło na nim każdą wymaganą kontrolę. Plan testów wymienia polecenia, wyniki i liczby oraz mówi, czego nie uruchomiono. Zmiany widoczne dla użytkownika mają zrzut ekranu albo test przeglądarkowy, który naciska kontrolkę.
2. **Opis względem diffa.** Każda zmiana, którą deklaruje opis, jest w diffie. Każdy plik w diffie jest wyjaśniony.
3. **Chronione ścieżki.** Żadna się nie zmieniła albo każdą obejmuje zacytowana zgoda, która ją wymienia.
4. **Diff testów.** Żadnej poluzowanej ani usuniętej asercji bez powodu, żadnego nowego pominięcia, ponowienia, limitu czasu ani mocka testowanej jednostki, żadnego przypadku szczególnego.
5. **Przyczyna źródłowa.** Poprawka zmienia to, co spowodowało problem. Po scaleniu nic innego nie może trafić na ten sam błąd. Każde obejście jest oznaczone i śledzone.
6. **Furtki.** Żadnej asercji non-null, kłamiącego strażnika typu, schematu, który przyjmuje cokolwiek, wartości zastępczej, która ukrywa brak wartości, ani połkniętego błędu.
7. **Zakres i projekt.** Nic, o co nikt nie prosił i czego nikt nie wyjaśnił. Żadnej nowej abstrakcji z jednym użytkownikiem, żadnej kopii istniejącej funkcji pomocniczej, żadnego pliku umieszczonego tam, gdzie czytelnik by nie zajrzał, żadnego projektu nagiętego wokół reguły.
8. **Twierdzenia w prozie.** Liczby wyświetlane z kodu, fakty zewnętrzne podlinkowane i znalezione pod linkiem, „egzekwowane” wskazujące swoją kontrolę.
9. **Wszystko, na co wpływa zmiana.** Dokumentacja, README, teksty serwisu i historia zmian w każdym języku; większość z tego sprawdza kontrola, a reszta jest tutaj.
10. **Historia.** Jedna zmiana, tytuł, który dobrze się przeczyta jako commit squash, żadnych wierszy atrybucji.

Kroki od 1 do 3 zajmują minuty i nie wymagają rozumienia kodu, więc odesłanie pull requesta, który nie przejdzie któregoś z nich, nie kosztuje prawie nic. Na kroki od 4 do 7 idzie najwięcej czasu i to te kroki, których żaden program nie zrobi za Ciebie.

## Ile to kosztuje i na co wydawać ten czas

Recenzja to jedyna część tego systemu, która nie skaluje się wraz z liczbą agentów. [Drugi wpis](/blog/running-ai-coding-agents-in-parallel) wykazał, że prawdziwym limitem tego, ile agentów może pracować naraz, był recenzent, a nie maszyny czy minuty CI. Trzy nawyki sprawiają, że ten koszt da się udźwignąć.

**Przenieś do kontroli wszystko, co da się rozstrzygnąć.** Każda reguła, którą potrafi rozstrzygnąć program, a Ty wciąż sprawdzasz ją wzrokiem, to czas recenzji wydany na niewłaściwą rzecz. O tym jest [wpis o barierkach](/blog/ai-coding-agent-guardrails).

**Trzymaj zmiany małe i pojedyncze.** Pull request z jedną zmianą da się czytać pod kątem jednego pytania. Agenty tanio produkują duże diffy; brief powinien prosić o jedną zmianę na pull request, a recenzent powinien odsyłać te, które się do tego nie stosują.

**Dobieraj głębokość do zasięgu szkód.** Płatności, tożsamość, migracje, kontrakty, od których zależy inne oprogramowanie, i same kontrole dostają całą listę, powoli. Poprawka w dokumentacji dostaje kroki 1, 2 i 8.

## Czego nasza recenzja wciąż nie wyłapuje

W duchu reszty serii oto miejsca, w których nasz własny proces jest słaby.

- **Opisy porównuje z diffami człowiek**, a nie kontrola, więc w pracowity dzień wciąż można któryś przeoczyć.
- **Stała statusu z #177** wciąż mieszka w stałych nawigacji, z powodu, który już nie istnieje.
- **Asercji non-null i własnych schematów** nie ma w naszym kodzie z przyzwyczajenia; żadna reguła jeszcze ich nie odrzuca.
- **Testy mutacyjne**, które mierzyłyby, czy testy kończą się błędem, gdy zmienia się kod, nie są skonfigurowane, więc wykrywanie „testów, które stały się łatwiejsze” zależy od czytania.
- **Recenzent i autor często mają ten sam model**, a więc i te same martwe pola.
- **Agenty pracują na koncie właściciela**, więc GitHub nie może wymagać recenzji od kogoś innego niż autor; drugi klucz trzyma warstwa uprawnień agentów i zacytowana zgoda, jak opisuje pierwszy wpis.

## Zestaw do recenzji do skopiowania

**Szablon pull requesta**, który prosi o dowody zamiast zapewnień:

```md
## What and why

One change. What made the problem happen, and how this removes it.

## Evidence

| Command | Result | Commit |
| ------- | ------ | ------ |
|         |        |        |

Not run, and why:

## Also changed

Every change the title does not cover, with its reason.

## Protected paths

None, or each path with the quoted approval that covers it.

## Not done

What I decided not to do, and why.
```

**Polecenie, które wypisuje chronione ścieżki w diffie**, uruchamiane przez recenzenta albo w CI:

```sh
git diff --name-only origin/main...HEAD | grep -E '^(db/migrations/|src/billing/|src/auth/|\.github/|eslint\.config\.js|vitest\.config\.ts)'
```

**Wyszukiwanie sygnałów ostrzegawczych w diffie testów** jako punkt wyjścia do kroku 4:

```sh
git diff origin/main...HEAD -- '*.test.*' '*.spec.*' | grep -nE '^\+.*(\.skip|\.only|\.todo|retry|retries|timeout|expect\.anything|toMatchObject|vi\.mock|jest\.mock)|^-.*expect\('
```

**Reguły lintera dla dwóch cichych furtek**, pod nazwami z ESLint i typescript-eslint:

```js
export default [
  {
    rules: {
      "@typescript-eslint/no-non-null-assertion": "error",
      "no-empty": "error",
    },
  },
]
```

**Subagent recenzent tylko do odczytu** dla Claude Code, w `.claude/agents/reviewer.md`:

```md
---
name: reviewer
description: Reviews a pull request's diff against the brief it was built from, before a person reads it.
tools: Read, Grep, Glob
---

You review a change you did not write. You are given the brief and the diff.

Report, in this order, only what affects correctness:

1. Claims in the description that the diff does not support, and files in the diff the description does not explain.
2. Changes to tests that make them easier: removed or loosened assertions, skips, retries, timeouts, mocks of the unit under test, special cases.
3. Fixes that change where a problem shows rather than what causes it.
4. Non-null assertions, type guards that do not check what they claim, schemas that accept anything, fallbacks that hide a missing value, swallowed errors.
5. New abstractions with one user, and helpers that duplicate existing ones.

Do not report style. Do not report cases that cannot happen. Do not edit anything.
```

**Wiersz do Twojego pliku instrukcji**, żeby autor przygotował to, o co zapyta recenzent:

```md
## Before you say done

Give the commit you tested, each command with its result, what you did not run and why, every change beyond the task, and what you decided not to do. A summary is not evidence.
```
