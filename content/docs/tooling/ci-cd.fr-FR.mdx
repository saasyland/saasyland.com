Les workflows se trouvent dans `.github/workflows/`. Les workflows de l'application (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `updates.yml`, `e2e-reusable.yml` et `deploy-reusable.yml`) mettent en place la chaîne d'outils avec l'action composite `.github/actions/setup` : Bun <RepositoryFact name="bunVersion" />, Vite+ avec la version de Node de `.nvmrc` et le cache d'installation de Bun, que `setup-vp` restaure une seule fois, `bun install --frozen-lockfile --ignore-scripts` et `bun run typegen`. `remotion.yml` met plutôt en place Node depuis `.nvmrc` et npm.

| Workflow              | Déclencheur                                                                                       | Jobs                                                                                                                                                                                           |
| --------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests, groupes de la file de fusion, et appels depuis `deploy.yml`                        | Vérifications, tests avec couverture sur des shards parallèles, vérification des types sans chaque zone optionnelle, E2E dans Chromium et dans WebKit et téléversement du Worker de préversion |
| `deploy.yml`          | Pushs sur `main`                                                                                  | Les vérifications de `ci.yml`, sauf si la file de fusion les a exécutées, puis la préversion, la production et la publication de la version                                                    |
| `preview.yml`         | Manuel                                                                                            | Déploie sur la préversion partagée une branche dont les vérifications ont réussi                                                                                                               |
| `e2e-full.yml`        | Pushs sur `main`, selon la planification <RepositoryFact name="e2eFullSchedule" /> en UTC, manuel | WebKit lors d'un push, comme sur chaque pull request ; Chromium et WebKit lors des exécutions planifiées et manuelles                                                                          |
| `journey.yml`         | Selon la planification <RepositoryFact name="journeySchedule" /> en UTC, manuel                   | La [suite de parcours client](#journey-suite) sur la préversion partagée, dans le bac à sable Polar                                                                                            |
| `updates.yml`         | Selon la planification <RepositoryFact name="updatesSchedule" /> en UTC, manuel                   | Ouvre, met à jour ou ferme l'[issue des mises à jour](#updates)                                                                                                                                |
| `e2e-reusable.yml`    | Appelé par les workflows ci-dessus                                                                | Un seul build de test, un projet Playwright sur des shards en parallèle et une seule vérification pour les deux                                                                                |
| `deploy-reusable.yml` | Appelé par `ci.yml`, `deploy.yml` et `preview.yml`                                                | Build, puis migrations D1 et `wrangler deploy`, ou `wrangler versions upload`                                                                                                                  |
| `remotion.yml`        | Modifications de `remotion/` ou des fichiers du site qu'il importe                                | Vérifie et empaquette avec npm le projet vidéo de la page d'accueil                                                                                                                            |

`remotion.yml` se déclenche sur les mêmes chemins pour les pull requests et les pushs : `remotion/`, le workflow lui-même et les fichiers du site que `remotion/src` importe, directement ou via d'autres fichiers du site. `src/__test__/workflows.test.ts` suit ces imports et échoue lorsqu'un fichier qu'ils atteignent ne correspond à aucun des chemins, ou qu'un chemin ne correspond à aucun des fichiers.

Les checkouts de `e2e-reusable.yml`, dont le build génère le journal des modifications et dont `content.spec.ts` le lit, de `deploy-reusable.yml`, qui construit le site, et du job `release` récupèrent tous les commits sans leurs arbres (`fetch-depth: 0` et `filter: tree:0`) : le [journal des modifications](/docs/project/changelog) date chaque entrée d'après le commit qui l'a amenée sur `main`. Par rapport à un clone superficiel, seuls les commits eux-mêmes s'ajoutent ; un clone superficiel ferait échouer la construction plutôt que de mal dater les entrées. `src/__test__/workflows.test.ts` échoue lorsqu'un de ces checkouts ne récupère plus l'historique.

Chaque action d'un autre dépôt, `actions/*` compris, est épinglée au SHA complet du commit d'une version, avec le tag de la version dans un commentaire à la suite : `uses: <owner>/<repo>@<commit> # <tag>`. Un workflow exécute donc exactement le code de cette version, même si son tag est déplacé plus tard. `src/__test__/workflows.test.ts` échoue quand un `uses:` de `.github/workflows/` ou `.github/actions/` nomme un tag ou une branche au lieu d'un commit, n'a pas de tag de version après le commit ou épingle deux versions d'un même dépôt. `bun run deps:update` amène chaque action à sa dernière version et réécrit ensemble le commit et le tag ([Dépendances](/docs/conventions/dependencies#upgrading)), si bien que les actions avancent sur la même branche que les paquets.

## Vérifications [#checks]

Les jobs `check`, `test` et `features` de `ci.yml` se trouvent derrière la vérification obligatoire `Format, lint, types, i18n, tests`, que rapporte le job `verify` :

| Job                                                | Exécute                                                                                                                                                                                                                                                                                                     |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                            | `bun run check` : tables des noms de classes, vérifications i18n et de contenu, l'[inventaire des parcours](/docs/tooling/test-coverage#flow-coverage), les [skills pour agents](/docs/tooling/agent-skills#drift-checks), formatage, lint et types                                                         |
| `test`                                             | Un job par shard, <RepositoryFact name="vitestShards" /> en parallèle : `bun run test:coverage --shard=<n>/<total>` avec le reporter blob de Vitest, puis téléverse le rapport blob du shard avec sa couverture                                                                                             |
| `verify`, nommé `Format, lint, types, i18n, tests` | Une fois chaque shard réussi, télécharge les rapports blob et exécute `bun run test:coverage --merge-reports`, qui fusionne la couverture et applique les seuils, puis téléverse le rapport de couverture ; échoue sauf si `check`, chaque shard, la fusion et chaque scénario du job `features` ont réussi |

Un shard ne vérifie aucun seuil, car il ne mesure que le code que ses propres tests atteignent ; les seuils de `vite.config.ts` s'appliquent une seule fois, à la couverture fusionnée de tous les shards, comme pour un `bun run test:coverage` local. De ces jobs, `verify` est la seule vérification qu'exigent les règles de la branche, donc ajouter ou retirer un shard ou un scénario ne change le nom d'aucune vérification obligatoire.

Le job `features` lance `bun run check:features <scenario>` une fois pour chaque scénario de `scripts/features.ts`, en parallèle. Il supprime les fonctionnalités du scénario, élague ce que les fichiers restants en nomment, formate les fichiers élagués, vérifie les types du reste et contrôle ses traductions ([Tests](/docs/conventions/testing#tests-follow-the-features)). Un scénario qui laisse une référence impossible à élaguer, une erreur de type ou une erreur de traduction fait échouer son job, et avec lui la vérification obligatoire `Format, lint, types, i18n, tests`.

Le job `check` lance ensuite `bun run deps:audit`, l'[analyse des dépendances](/docs/conventions/dependencies#security-advisories) : `scripts/audit-dependencies.ts` lance `bun audit` sur les dépendances de production et échoue sur un avis de gravité <RepositoryFact name="auditBlockingSeverities" /> qu'aucune exception en cours ne couvre. Une pull request ne peut donc pas introduire une telle dépendance, et un nouvel avis contre une dépendance déjà sur `main` bloque la pull request suivante jusqu'à ce qu'elle soit corrigée ou couverte par une exception. L'analyse interroge le registre npm, donc une panne du registre fait échouer le job ; relancez-le.

Le job `sbom`, nommé `Software bill of materials`, lance `bun run deps:sbom` à chaque exécution et téléverse `sbom.cdx.json` comme artefact `sbom` : le SBOM CycloneDX des dépendances de production, avec la version et l'URL de paquet de chacune et le graphe des dépendances. cdxgen l'écrit à partir de `bun.lock` et laisse de côté les paquets dont seules les devDependencies ont besoin, et `scripts/verify-sbom.ts` fait échouer le job quand le SBOM omet une dépendance de `package.json`. Le SBOM d'un commit de `main` est l'artefact de l'exécution du groupe de fusion qui l'a testé. cdxgen s'exécute via `bunx` à la version exacte du script `deps:sbom` plutôt que comme devDependency, car ses binaires d'analyse optionnels ajouteraient des centaines de mégaoctets à chaque installation ; `readDependencies` dans `scripts/dependencies.ts` lit cette version dans le script, si bien que l'[issue des mises à jour](#updates) signale un cdxgen plus récent comme paquet épinglé. Le job n'est pas une vérification requise.

Les jobs `e2e` et `e2e-webkit` appellent `e2e-reusable.yml`, le premier avec `browser: chromium`, le second avec `browser: webkit`. Chaque appel construit une seule fois et exécute la suite dans son navigateur sur <RepositoryFact name="e2eShards" /> runners en parallèle :

| Job                                         | Exécute                                                                                                                                                                                                                                 |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                     | `db:reset:test` et `build:test`, puis téléverse `dist`, le `.wrangler/deploy` qui pointe vers la configuration de son Worker et le `.wrangler/test` rempli par le seed en un seul artefact                                              |
| `shard`                                     | Un job par shard, lancé en même temps que le build : installe le navigateur, attend le téléversement du build, le télécharge et lance `bunx playwright test e2e/specs --project=<browser> --shard=<n>/<total>`                          |
| `visual`                                    | Chromium seulement, à côté des shards : attend le build comme un shard, puis lance `bun run test:visual`, les [tests visuels](/docs/tooling/playwright#visual-tests), et téléverse les différences quand une capture ne correspond plus |
| `report`, nommé `Build and E2E (<browser>)` | Échoue sauf si le build, chaque shard et, dans Chromium, les tests visuels ont réussi ; si un shard a échoué, fusionne les rapports blob des shards en un seul rapport HTML et le téléverse                                             |

Les shards n'attendent pas la fin du job `build` entier (`needs`) : ils démarrent avec lui et installent la chaîne d'outils et le navigateur pendant qu'il construit. Ensuite, `scripts/download-artifact.ts` interroge l'API de GitHub toutes les quelques secondes sur le job `build` de l'exécution, jusqu'à ce que son étape `Upload the test build` ait réussi. Une étape réussie ne veut pas dire que GitHub liste déjà son artefact, et un téléchargement dans cet intervalle échoue avec `Artifact not found` : le script interroge donc ensuite les artefacts de l'exécution jusqu'à ce que GitHub liste `test-worker-<browser>` téléversé depuis le début du build, puis télécharge lui-même cet artefact et le vérifie avec le digest SHA-256 que GitHub a enregistré. Un artefact listé peut encore répondre `Not Found` pendant un instant : le script redemande donc jusqu'à ce que GitHub serve l'archive entière, et aucune autre étape ne la demande entre-temps. Le script envoie l'ETag de la réponse précédente, et GitHub ne décompte pas une réponse inchangée de la limite de requêtes du jeton. Une étape du build qui échoue, ou un build qui se termine sans son téléversement, fait échouer chaque shard en quelques secondes, avec l'étape en échec et un lien vers le build, et un shard qui attend au-delà de la limite du script échoue avec une erreur qui dit si c'est l'étape, la liste ou le téléchargement qui manque. Lire les jobs et les artefacts de l'exécution demande `actions: read`, que seuls les jobs `shard` et `visual` réclament : `ci.yml`, `e2e-full.yml` et le job `checks` de `deploy.yml` l'accordent aux workflows qu'ils appellent, et tous les autres jobs gardent `contents: read`.

Les relances et les workers de Playwright restent tels que [Playwright](/docs/tooling/playwright#configuration) les décrit, sur chaque shard. Le job `report` de chaque navigateur est la seule vérification de ce navigateur qu'exigent les règles de la branche : ajouter ou retirer un shard ne change donc le nom d'aucune vérification requise. Le build emballe aussi la liste des tags de release qu'il a lus, et chaque shard supprime tout tag créé depuis : `content.spec.ts` lit les tags de release dans Git, et une release taguée pendant que les shards attendent lui ferait attendre un changelog que le build n'a jamais rendu.

Le job `upload`, nommé `Worker upload`, appelle `deploy-reusable.yml` avec `upload: true` : il construit le Worker de préversion exactement comme le fait un déploiement et lance `wrangler versions upload`, qui l'envoie au Worker `saasyland-preview` sous forme d'une nouvelle version sans la déployer. Cloudflare vérifie ce téléversement comme il vérifie un déploiement, avec la limite de taille, le temps de démarrage, les bindings et les secrets que nomme `secrets.required` : un Worker qui passe cette vérification se déploie donc, tandis que `preview.saasyland.com` continue de servir la version déployée auparavant. Le job n'applique aucune migration et n'enregistre aucun déploiement GitHub (`deployment: false`), et il s'exécute en parallèle des téléversements des autres pull requests. La version d'une pull request reçoit l'alias `pr-<number>`, qui nomme la version dans le tableau de bord de Cloudflare ; le résumé du job affiche l'identifiant et la taille de la version, ainsi que son URL lorsque les Version URLs sont activées pour le Worker, ce qui n'est pas le cas aujourd'hui pour `saasyland-preview`. Les pull requests provenant de forks et de Dependabot ne peuvent pas lire les identifiants Cloudflare et sautent ce job ; la file de fusion, qui le peut, téléverse leur build avant leur fusion.

Dans une pull request, `bun run check` échoue aussi tant que la pull request n'ajoute pas son [entrée au journal des modifications](/docs/conventions/git-workflow#changelog-entries), et dans la file de fusion tant que l'entrée de la pull request en file n'est pas là. La construction des jobs `e2e` et `upload`, et celle des jobs de déploiement, échoue tant que le journal afficherait sous **Non publié** une entrée qui n'est pas celle de la pull request elle-même, et dans la file de fusion et sur `main` tant qu'il en afficherait une.

## File de fusion [#merge-queue]

Le ruleset qui protège `main` exige `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)`, `Build and E2E / Build and E2E (webkit)` et `Worker upload / Upload preview`, et ne fusionne les pull requests que par la file de fusion de GitHub, qui squashe chacune d'elles. `bun scripts/enqueue-pr.ts <number>` place une pull request dans la file ([Git et pull requests](/docs/conventions/git-workflow#merging)). Pour chaque pull request de la file, GitHub écrit le commit squash sur une branche nommée `gh-readonly-queue/main/pr-<number>-<commit>`, au-dessus de `main` et des pull requests qui la précèdent, et y exécute `ci.yml` pour l'événement `merge_group`. Une fois que chaque pull request d'un groupe a réussi, GitHub avance `main` jusqu'au dernier commit du groupe, celui-là même que la file a testé : un seul push amène ainsi chaque pull request du groupe sur `main` sous la forme de son propre commit squash. Une pull request qui échoue quitte la file, et celles qui la suivent sont testées de nouveau sans elle.

Le ruleset contient aussi `copilot_code_review` avec `review_on_push: true`, mais au 22 novembre 2026, GitHub Copilot n'a relu aucune pull request depuis #70 : les pull requests ne reçoivent donc aucune revue automatique. Une revue ne serait que consultative : le ruleset n'exige aucune approbation ni aucun fil de revue résolu, si bien qu'une pull request n'attend que les quatre checks ci-dessus.

`ci.yml` annule le run d'une pull request lorsqu'un commit plus récent le remplace, mais jamais un run de la file, dont chaque branche a sa propre ref. Le contrôle du journal des modifications traite la branche de la file comme `main` : chaque pull request du groupe est déjà un commit squash dont le sujet se termine par son numéro, si bien qu'aucune entrée ne peut rester non publiée, et l'entrée de la pull request en file doit exister.

## Déploiements

`deploy.yml` déploie chaque push sur `main`, d'abord sur la préversion partagée, puis en production, une fois que le commit a passé toutes les vérifications qu'exige `main`. Son premier job, `tested`, exécute `scripts/tested-commit.ts`, qui lit ces vérifications dans le ruleset via l'API de GitHub et cherche une exécution réussie de chacune sur le commit poussé. Un commit arrivé par la file de fusion les a, car la file a testé ce commit précis : `deploy.yml` le déploie donc sans relancer les vérifications ; un commit arrivé sur `main` par tout autre chemin exécute d'abord les vérifications de `ci.yml`.

| Événement                           | Cible                        | Environnement GitHub         | URL                                                  |
| ----------------------------------- | ---------------------------- | ---------------------------- | ---------------------------------------------------- |
| Push sur `main`                     | `preview`, puis `production` | `Preview`, puis `Production` | https://preview.saasyland.com, https://saasyland.com |
| Exécution manuelle de `preview.yml` | `preview`                    | `Preview`                    | https://preview.saasyland.com                        |

`deploy-reusable.yml` donne à chaque environnement GitHub son URL, et `src/__test__/workflows.test.ts` échoue lorsque l'une d'elles diffère de son hôte dans `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). La préversion est partagée : chaque déploiement remplace le précédent et utilise la même base de données D1, le même espace de noms KV et les mêmes buckets R2 de préversion. Elle exécute `main` : la [suite de parcours client](/docs/tooling/playwright#journey-suite), les webhooks de la sandbox Polar et la connexion sur `preview.saasyland.com`, le seul hôte de préversion auquel Better Auth fait confiance, rencontrent ainsi tous le code que la production s'apprête à exécuter, et chaque migration atteint la base de données de préversion avant la production. Pour essayer une branche sur la préversion avant sa fusion, lancez `gh workflow run preview.yml --ref <branch>` : le workflow ne déploie la branche, migrations comprises, que si son commit a passé les vérifications qu'exige `main`, et le push suivant sur `main` y remet `main`.

`deploy-reusable.yml` vérifie la présence des secrets `CLOUDFLARE_API_TOKEN` et `CLOUDFLARE_ACCOUNT_ID`, exécute `scripts/verify-bindings.ts`, construit avec les valeurs factices de `.env.test`, supprime le fichier généré `dist/server/.dev.vars`, applique `db:migrate:<target>` et lance `vp exec wrangler deploy --config dist/server/wrangler.json`, ou, avec `upload: true`, lance `vp exec wrangler versions upload` à la place de ces deux dernières étapes. Il ne lance pas `scripts/verify-deployment.ts`, la vérification du site en ligne des scripts `deploy:<target>`, car la protection anti-bots de Cloudflare répond 403 aux requêtes des runners de CI. Il ne lance pas non plus `scripts/run-deploy-checks.ts` : la CI n'exécute donc aucune des vérifications de déploiement, c'est-à-dire des scripts `<name>:verify:<environment>` de `package.json`, car elle n'a pas de `.env.<target>` et les environnements GitHub ne contiennent que les identifiants Cloudflare, plus les réglages du bac à sable de la [suite de parcours client](#journey-suite) dans `Preview`. Aujourd'hui, ce sont `auth:verify`, de la zone d'authentification, et `polar:verify`, de la zone Polar ; lancez en local `bun run auth:verify:<target>` après avoir modifié un client OAuth et `bun run polar:verify:<target>` après chaque modification dans Polar ([Configurer Polar](/docs/getting-started/polar-setup)). Aucun fichier de secrets n'est téléversé : le Worker conserve les secrets d'exécution déjà définis dans Cloudflare. Les déploiements vers une même cible sont mis en file d'attente au lieu de s'annuler mutuellement, et les téléversements s'exécutent en parallèle. Un nouveau commit sur une pull request annule le run de `ci.yml` du commit précédent, que personne ne fusionnera, tandis que les runs de la file de fusion ne s'annulent jamais les uns les autres et que ceux de `deploy.yml` et de `e2e-full.yml` sur `main` se mettent en file d'attente (`concurrency` avec `queue: max`) : chaque push sur `main` est ainsi déployé.

## Suite de parcours client [#journey-suite]

`journey.yml` lance `bun run test:journey`, la [suite de parcours client](/docs/tooling/playwright#journey-suite), sur `https://preview.saasyland.com` selon la planification <RepositoryFact name="journeySchedule" /> en UTC et quand on le démarre à la main :

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` vaut `all`, `core`, `complete`, `agency` ou `upgrade` ; toute valeur autre que `all` ne lance que le test qui porte ce tag. Le job lit ces secrets de l'environnement GitHub `Preview` sans enregistrer de déploiement (`deployment: false`) : `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` et `RESEND_API_KEY`. Il fixe `POLAR_SERVER` à `sandbox`, la seule valeur que la suite accepte, et la suite crée son client Polar pour le bac à sable : le workflow ne peut donc pas atteindre le Polar de production. Les exécutions se mettent en file d'attente et ne s'annulent jamais entre elles, car une exécution annulée laisserait ses commandes payées. Le job écrit le résultat et la durée de chaque test, et l'erreur de chaque test en échec, dans le résumé de l'exécution, et téléverse le rapport HTML, `playwright-report/journey.json` ainsi que les traces, les vidéos et les répertoires de machine des tests en échec sous forme de l'artefact `journey-report`.

Le workflow ne s'exécute pas après chaque déploiement de `main`. Chaque exécution inscrit un compte par test sur la préversion, paie et rembourse leurs commandes dans le bac à sable Polar et envoie leurs e-mails de vérification et leurs confirmations d'achat par le compte Resend que la préversion partage avec la production. `main` est déployé de nombreuses fois lors d'une journée chargée : une exécution après chaque déploiement multiplierait ces e-mails face aux limites d'envoi dont dépendent les e-mails de la production, et elle n'arrêterait rien, puisque la production est déployée juste après la préversion, quoi que trouve le parcours. Chaque exécution couvre l'achat de bout en bout : l'inscription avec la vérification de l'e-mail, un paiement dans la sandbox pour chaque offre, la clé qu'émet Polar, la CLI publiée sur les appareils de l'offre, le passage de Core à Complete et les remboursements. Elle n'est pas encore au vert : aucune exécution n'a réussi, car les secrets du workflow ne sont pas définis, donc elle ne vérifie encore aucun achat. Lancez-la à la main après une modification des paiements, des licences ou de l'API de licence de la CLI, et après `gh workflow run preview.yml --ref <branch>` pour tester une branche avant sa fusion.

## Mises à jour [#updates]

`updates.yml` cherche les mises à jour des dépendances et des skills pour agents selon la planification <RepositoryFact name="updatesSchedule" /> en UTC et lorsqu'on le lance à la main. Sa première étape, `bun scripts/report-updates.ts find`, demande au registre npm la dernière version de chaque dépendance directe et exécute `bun run skills:update` dans le checkout du runner, dont rien n'est commité, pour voir quelles skills ont changé en amont. Sa seconde étape, `bun scripts/report-updates.ts issue`, tient une seule issue, <RepositoryFact name="updatesIssueTitle" /> : elle l'ouvre quand il y a des mises à jour, la réécrit aux exécutions suivantes et la ferme dès que tout est à jour. L'issue liste chaque paquet obsolète, marqué comme déplacé par `bun run deps:update` ou épinglé, et chaque skill avec les commits entre lesquels elle passerait. La première étape lit aussi, avec `git ls-remote`, qui n'a besoin d'aucun token, les tags de version du dépôt de chaque action épinglée, et l'issue liste chaque action épinglée à une version plus ancienne que sa dernière.

Après l'issue, le job lance `bun run deps:audit`, la même analyse que le job `check`, pour qu'un nouvel avis élevé ou critique fasse échouer l'exécution hebdomadaire même une semaine sans pull request.

Le workflow ne peut que lire le dépôt et écrire des issues, et seule la seconde étape reçoit le jeton. Il n'ouvre aucune pull request, car GitHub ne démarre aucun workflow pour une pull request ouverte par le jeton du workflow lui-même, si bien que ses vérifications ne s'exécuteraient jamais ; exécutez plutôt `bun run deps:update` sur une branche.

## Versions et tags [#releases-and-tags]

Le site est déployé en continu : ses versions sont donc des dates et non des versions sémantiques. Quand un déploiement en production réussit, le job `release` de `deploy.yml` pose le tag `vYYYY.MM.DD` à la date UTC sur le commit déployé et publie une GitHub Release correspondante. Un deuxième déploiement en production le même jour reçoit le tag `vYYYY.MM.DD.2`, le suivant `.3`, et ainsi de suite. Les déploiements en préversion ne reçoivent jamais de tag. Le job `release` est le seul à disposer de `contents: write`.

Les notes de version sont les entrées du [journal des modifications](/docs/project/changelog) que la version a livrées, celles arrivées sur `main` depuis le tag de version précédent, chacune terminée par `(#<number>)`, dont GitHub fait un lien vers sa pull request, si bien que chaque changement n'est décrit qu'à un seul endroit ; si une version n'en a livré aucune, ses notes renvoient vers le journal. `scripts/publish-release.ts` prend les notes dans `releaseNotes`, dans `src/lib/changelog.ts`, l'unique élément de son `RELEASE_NOTES`, et lance `gh release create` avec le tag que le déploiement a choisi, si bien qu'un projet sans le journal publie ses versions sans notes. Une nouvelle exécution conserve le tag que le commit possède déjà et ignore une GitHub Release qui existe déjà.

Le job du déploiement en production choisit ce tag avant de construire : `scripts/choose-release-tag.ts` applique `releaseTag` de `src/lib/release.ts` aux tags du checkout, la construction reçoit le tag dans `RELEASE_TAG`, et le job le transmet au job `release` par sa sortie `release-tag`, si bien que le déploiement et sa version partagent un seul tag. Grâce à lui, le [journal des modifications](/docs/project/changelog) relie chaque entrée à la version qui l'a livrée en premier : le plus ancien tag de version dont le commit contient le commit squash de l'entrée dans l'historique des premiers parents de `main`, que la construction lit avec les dates en un seul `git log`, ou le tag du déploiement lui-même pour les entrées qu'il apporte. Le job `release` lit le journal de la même façon, avec le tag qu'il publie, si bien que les notes d'une version sont exactement les entrées que la page relie à cette version. Les entrées fusionnées avant le premier tag de version ne renvoient vers aucune version, pas plus que, dans les constructions locales, de prévisualisation et de pull requests, les entrées qu'aucun déploiement n'a encore livrées. Deux déploiements en production ne peuvent pas choisir le même tag : `deploy.yml` n'exécute qu'un seul run du workflow à la fois (`concurrency` avec `queue: max`), si bien que le job `release` du run précédent a créé son tag avant que le déploiement suivant ne fasse le checkout du dépôt.

Pour ramener la production à une version, annulez dans une pull request tout ce qui suit son tag :

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Sa fusion déploie le code du tag après les vérifications habituelles et lui pose le tag d'une nouvelle version. Les migrations D1 ne sont pas annulées : l'ancien code s'exécute donc sur le schéma plus récent. Chaque modification du schéma doit fonctionner avec l'application déployée avant elle, ce qui rend l'opération sûre pour la version précédente ; lisez les migrations intermédiaires avant de remonter plus loin.
