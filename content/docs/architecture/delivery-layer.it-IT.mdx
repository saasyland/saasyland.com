## File di route

Le route sono file piatti in `src/routes`. I punti diventano segmenti del percorso:

| File                              | URL                | Note                                              |
| --------------------------------- | ------------------ | ------------------------------------------------- |
| `__root.tsx`                      | tutte le pagine    | Shell del documento e namespace radice            |
| `_site.tsx`                       | nessuno            | Layout senza percorso con l'intestazione del sito |
| `_site._marketing.tsx`            | nessuno            | Layout senza percorso per le pagine di marketing  |
| `_site._marketing.terms.tsx`      | `/terms`           | Pagina all'interno del layout marketing           |
| `admin.tsx`                       | `/admin`           | Layout con la guard `requireAdmin`                |
| `admin.users.all.tsx`             | `/admin/users/all` | Pagina all'interno del layout admin               |
| `_site._marketing.blog.index.tsx` | `/blog`            | Pagina indice del layout `blog`                   |
| `_site.docs.$.tsx`                | `/docs/*`          | Route splat per le pagine della documentazione    |
| `api/auth.$.ts`                   | `/api/auth/*`      | Handler HTTP, senza componente                    |

Gli ID di `createFileRoute("…")` sono stringhe letterali gestite dal generatore del router, che scrive anche `src/routeTree.gen.ts`. I file nelle cartelle `__test__` vengono ignorati. Ogni URL ha una costante in `ROUTES` (`src/routes.ts`) e i link usano `<Link to={ROUTES.X}>`.

## Route di pagina

Una route di pagina definisce un componente `<Name>Page`, una costante `NAMESPACE` subito sopra `export const Route` e un loader che carica i metadati della pagina e il namespace in un unico `Promise.all`:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

I dati aggiuntivi vanno nello stesso `Promise.all`, ad esempio `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` in `admin.users.all.tsx`. `pageHead` di `src/lib/seo.ts` costruisce i tag title, description, canonical, `hreflang`, Open Graph e dell'immagine social a partire dai `metadata` del loader; vedi [Motori di ricerca e anteprime social](/docs/features/seo).

## Route di layout

Una route di layout definisce un componente `<Name>Layout`, un array `NAMESPACES` e, per le aree protette, una guard in `beforeLoad`. I suoi `NAMESPACES` nominano ogni namespace di cui hanno bisogno le sue pagine, compresi quelli di altre funzionalità, e un parametro di ricerca viene validato dalle pagine che lo leggono, come fanno le pagine della licenza `/app` e `/app/license` con `tier`:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "pages.license", "timezones"] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Le guard `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn`, `redirectIfVerified` e `redirectAfterAuth` provengono da `src/integrations/better-auth/auth.routes.ts`.

## Scheletri di caricamento

La maggior parte delle navigazioni termina prima che compaia qualsiasi UI di attesa: i link precaricano la loro route al passaggio del mouse e al tocco, e le pagine pubbliche sono prerenderizzate. Quando una navigazione non è terminata dopo `defaultPendingMs`, <RepositoryFact name="navigationPendingMs" unit="millisecond" />, il router mostra lo scheletro della route e, poiché `defaultPendingMinMs` è <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, lo toglie non appena la pagina è pronta. Succede con una connessione lenta o alla prima richiesta a un nuovo isolate del Worker (vedi [Prestazioni](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

Non esiste un componente pending predefinito. Ogni route di layout e di pagina imposta il proprio `pendingComponent`. Le pagine della documentazione vengono disegnate dentro il layout della documentazione: `_site.docs.index.tsx` e `_site.docs.$.tsx` mostrano `DocsIndexPending` e `DocsPagePending`, l'articolo e il suo indice dei contenuti accanto alla barra laterale, e il layout `docs` mostra `DocsPending` quando qualcuno entra nella documentazione da un'altra parte del sito. Ogni scheletro riproduce la pagina che sostituisce:

- **Gli scheletri di pagina**, come `SignInPending` e `LegalPending`, si trovano nel file pending della funzionalità e marcano il proprio elemento radice con `aria-busy="true"`. I file sono `custom/auth/auth-pending.tsx`, i file di amministrazione in `custom/admin/` (`admin-pending.tsx` per il layout, un file `<feature>-pending.tsx` per ogni funzionalità, come `products-pending.tsx`, e blocchi condivisi in `pending-blocks.tsx`), i file dell'app clienti in `custom/app/` (`app-pending.tsx` per il layout, `auth-pending.tsx` e `license-pending.tsx`, e l'intestazione di pagina che condividono in `pending-blocks.tsx`), i file del layout pubblico al primo livello di `custom/` (`marketing-pending.tsx` per il layout, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` e `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` e `custom/docs-pending.tsx`.
- **Gli scheletri di layout**, come `AuthPending` e `MarketingPending`, renderizzano la cornice del layout e, al suo interno, il `pendingComponent` della prima route sotto il layout che corrisponde al percorso corrente e ne definisce uno, che `usePagePending` in `src/hooks/use-page-pending.ts` legge dall'albero delle route. Entrando in un'area da un'altra parte del sito si vede quindi la pagina giusta, e uno scheletro di layout un livello più in basso, come `AdminUsersPending`, fa lo stesso per le proprie pagine. Gli elementi della cornice che non richiedono dati, come `Wordmark` e `PageFrame`, vengono renderizzati davvero, e l'intestazione del sito resta sullo schermo, perché il layout `_site` che la renderizza non ha alcun loader da attendere.
- **I segnaposto di testo** sono barre `Skeleton` con il token tipografico dell'elemento reale più `h-lh scale-y-70`, così ogni barra riempie esattamente una line box. I riquadri usano le altezze e i raggi reali. Gli elenchi prendono la loro lunghezza dalle stesse costanti della UI, come `OAUTH_PROVIDERS` e `AUTH_ASSURANCES` in `src/data/auth.ts`.

Quando aggiungi una pagina, aggiungi il suo scheletro al file pending della funzionalità e impostalo come `pendingComponent` della route; gli scheletri di layout lo trovano lì.

## Altri aspetti delle route

- **I parametri di ricerca** vengono analizzati da `validateSearch` nella route, ad esempio il parametro `tab` di `/app/settings`. Lo schema è uno `zod.object` costruito con gli helper di `src/lib/search-params.ts`: `searchText()` e `searchFlag()` restituiscono `undefined` per un valore mancante, vuoto o malformato, e `searchChoice(choices, fallback)` restituisce il valore di riserva. `searchParam(schema)` restituisce `undefined` a meno che il valore rispetti un altro schema zod, come il token della newsletter.
- **Le server function di una sola route** possono essere definite nel file della route con `createServerFn`.
- **I contenuti generati dalla build**: i loader della documentazione, del blog e della landing leggono gli indici dei contenuti da `virtual:content-indexes`, file sotto `/assets/`, quindi non hanno bisogno di server function e vengono eseguiti nel browser durante una navigazione lato client (vedi [Fumadocs](/docs/integrations/fumadocs#content-indexes)).
- **Gli endpoint HTTP** si trovano in `src/routes/api`. Vedi [Handler HTTP di TanStack Start](/docs/architecture/api-layer).

## Router

`src/router.tsx` esporta `getRouter`, che crea un nuovo `QueryClient` e un nuovo router per ogni richiesta. Imposta:

- i componenti predefiniti di errore e not-found da `presentation/components/custom`, e nessun componente pending predefinito (vedi [Scheletri di caricamento](#scheletri-di-caricamento))
- il precaricamento su intent e uno stale time predefinito di <RepositoryFact name="routerStaleTimeMinutes" unit="minute" /> sia per le pagine caricate sia per quelle precaricate, così una pagina che `Navigation` precarica per l'intestazione appena una pagina è inattiva è ancora fresca al momento del clic (vedi [Prestazioni](/docs/conventions/performance#the-headers-pages-load-before-a-click))
- un `rewrite` che rimuove il prefisso del locale dagli URL in entrata e lo aggiunge di nuovo ai link generati
- l'integrazione SSR delle query tramite `setupRouterSsrQueryIntegration`

## Dopo un deploy [#after-a-deploy]

Ogni deploy sostituisce gli asset statici del Worker, e Vite dà a ogni file un nome basato sul suo contenuto, quindi una scheda aperta prima di un deploy richiede chunk di route che non esistono più. TanStack Start mette il componente e il loader di ogni route in chunk separati. TanStack Router ricarica la pagina quando il chunk di un componente non si carica (`lazyRouteComponent`), ma router-core carica il chunk di un loader con `lazyFn`, che passa l'import fallito alla route come errore del suo loader. Un clic su **Blog** in una scheda del genere falliva sul chunk del loader del layout del blog e mostrava la pagina di errore.

`DefaultError`, il componente di errore predefinito del router, ora rimedia. `isStaleBuildError` in `src/lib/stale-build.ts` riconosce un errore che significa che la pagina esegue codice rimosso da un deploy più recente:

- un import dinamico fallito, che `isModuleNotFoundError` di router-core riconosce in Chromium, Firefox e Safari;
- un file che Vite non è riuscito a precaricare per un chunk, come il suo foglio di stile, che Vite segnala con un evento `vite:preloadError`. La route radice ascolta l'evento finché l'applicazione è aperta (`listenForStaleBuilds`).

Per un errore del genere, `DefaultError` carica come nuova pagina l'indirizzo verso cui il visitatore ha navigato, con `router.navigate({ href, reloadDocument: true, replace: true })`, così il visitatore arriva sulla pagina che ha cliccato, servita dal nuovo deploy; finché il browser non lascia la pagina, il componente mostra un `main` vuoto e segnato come occupato al posto del messaggio di errore. `claimReload` consente un solo ricaricamento del genere per destinazione e build. Salva la destinazione in `sessionStorage` insieme all'URL dello script di ingresso della pagina, che cambia con ogni deploy che modifica un file caricato dal browser, perché ogni chunk si raggiunge dall'ingresso tramite il suo nome basato sul contenuto. Un secondo errore per la stessa destinazione nella stessa build mostra la pagina di errore, così un file che manca davvero non può far ricaricare la pagina all'infinito, e il deploy successivo ha un ricaricamento tutto suo. Se il browser rifiuta il session storage, non si ricarica nulla.

Safari annulla i file che una pagina sta ancora caricando non appena il visitatore inizia a lasciarla, quindi un chunk o un foglio di stile in arrivo fallisce come se un deploy lo avesse rimosso. Per questo `listenForStaleBuilds` registra anche quando la pagina riceve `beforeunload`, e `DefaultError` attende con `whenPageStays` che un `pageshow`, `pointerdown` o `keydown` mostri che il visitatore è rimasto prima di ricaricare la pagina. Un visitatore che se ne va raggiunge la pagina che ha chiesto invece di essere rimandato a quella che lasciava, e chi torna sulla pagina o vi resta riceve allora il ricaricamento. `stale-build.spec.ts` trattiene il codice della route di una lezione, passa all'informativa sulla privacy, annulla il codice e verifica che l'informativa sulla privacy si apra e che la lezione non venga richiesta di nuovo.

Un precaricamento fallito non consuma nulla. Passare il puntatore su un link ne precarica la route, come fa l'intestazione per i propri link appena una pagina è inattiva; se il precaricamento fallisce, non compare alcun componente di errore, e il router richiede di nuovo il chunk al clic. `e2e/specs/stale-build.spec.ts` attiva il risparmio dati, così l'intestazione non carica prima il blog, toglie i chunk del blog a una pagina aperta e verifica che un clic, anche dopo un precaricamento fallito al passaggio del puntatore, arrivi sul blog dopo un ricaricamento, e che una pagina i cui chunk continuano a mancare mostri la pagina di errore dopo due ricaricamenti, uno di `DefaultError` e uno di `lazyRouteComponent`.
