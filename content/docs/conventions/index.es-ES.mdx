Estas páginas son el estándar de código de este repositorio. Describen cómo se escribe el código aquí, no cómo podría escribirse, y cada regla nombra los archivos que la siguen. La mayoría de las reglas las hace cumplir un comando: `bun run check` (formato, lint, tipos, traducciones y estructura de la documentación), `bun run test:coverage` (el umbral del <RepositoryFact name="coverageThreshold" unit="percent" />) o la suite end-to-end. El resto se vigila en la revisión, y cada página indica cuáles.

Cuando no tengas claro cómo escribir algo, busca el ejemplo existente más parecido del mismo tipo, léelo y copia su forma. La coherencia vale más que una idea mejor a nivel local: una segunda manera de hacer lo mismo obliga a cada lector posterior, humano o agente, a aprender las dos.

## Implementación de referencia

La funcionalidad de cursos es la forma de referencia que hay que copiar. Abarca un módulo de tabla, rutas públicas y de administración, formularios, diálogos, una tabla de datos, esqueletos de carga y pruebas.

| Tipo                                  | Copiar de                                                              |
| ------------------------------------- | ---------------------------------------------------------------------- |
| Módulo de tabla                       | `src/modules/course/`, con `chapter`, `lesson` y `video` a su lado     |
| Lectura con opciones de consulta      | `src/modules/course/use-cases/get-course-editor.ts`                    |
| Lista paginada para una tabla         | `src/modules/course/use-cases/get-courses.ts`                          |
| Mutación con opciones de mutación     | `src/modules/course/use-cases/update-course.ts`                        |
| Ruta de layout                        | `src/routes/admin.courses.tsx`                                         |
| Ruta de página con una tabla de datos | `src/routes/admin.courses.index.tsx`                                   |
| Ruta de página con un parámetro       | `src/routes/admin.courses.$courseId.tsx`                               |
| Formulario                            | `src/presentation/components/custom/admin/courses/course-form.tsx`     |
| Diálogo con un formulario             | `src/presentation/components/custom/admin/courses/chapter-dialog.tsx`  |

## Reglas sin excepciones

Incumplir una de ellas hace que se rechace un cambio, por bien que haga todo lo demás.

1. Ningún comentario salvo que sea de verdad necesario, y en ese caso solo un enlace de una línea al lugar donde está el motivo: una página de la documentación, el README, la hoja de ruta o una incidencia de un proyecto externo. Consulta [Estilo de código](/docs/conventions/code-style#comments).
2. Sin `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, casts con `as` ni `any` para saltarse una regla. Corrige la causa.
3. Sin ternarios de varias líneas y sin `?? undefined`. Fuera de las pruebas y de `src/platform/testing`, `null` solo se escribe donde lo impone una API: al comparar con un valor que puede ser `null` y en una ref del DOM de React (`useRef<HTMLElement>(null)`). Consulta [Estilo de código](/docs/conventions/code-style).
4. Los estados, tipos, niveles, roles y demás valores del dominio son constantes con nombre, nunca literales de cadena repetidos, también en las pruebas. Las pruebas de esquema son el único lugar donde se escribe un valor almacenado. Consulta [Pruebas](/docs/conventions/testing).
5. Una carpeta en `src/modules` existe solo para una tabla de la base de datos. Consulta [Módulos](/docs/conventions/modules).
6. Cada texto visible para el usuario existe en todos los idiomas, y lo mismo cada página de la documentación. Las cifras que muestra el sitio se miden o se declaran una sola vez en `src/data`, nunca se escriben a mano. Consulta [Traducciones y contenido](/docs/conventions/translations).
7. La cobertura se mantiene al <RepositoryFact name="coverageThreshold" unit="percent" /> en líneas, sentencias, funciones y ramas. Consulta [Pruebas](/docs/conventions/testing).
8. Un cambio actualiza el README, la documentación y los textos del sitio que deja inexactos, en la misma pull request.
9. Los commits y las pull requests no llevan atribución a una IA ni el trailer `Co-Authored-By`. Consulta [Git y pull requests](/docs/conventions/git-workflow).

## Definición de terminado [#definition-of-done]

Un cambio está terminado cuando estos comandos pasan, en este orden, en la rama que vas a subir, seguidos de las specs del navegador que cubren lo que has cambiado:

```sh
bun run check
bun run test:coverage
bun run build:test
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`check` y las pruebas no ejercitan el build de Cloudflare: una actualización de dependencias pasó una vez ambos mientras el build de producción estaba roto. Ejecuta `build:test` en cada cambio y, en todo lo que no sea documentación, las specs de las páginas y los flujos que has tocado, en un puerto propio, como describe [Playwright](/docs/tooling/playwright#running-beside-other-worktrees). La CI ejecuta la suite completa del navegador en cada pull request y de nuevo en la cola de fusión, y una pull request solo llega a `main` cuando esa ejecución está en verde: ponla en la cola como describe [Git y pull requests](/docs/conventions/git-workflow#merging), no la fusiones nunca a mano. La pull request añade además su [entrada del registro de cambios](/docs/conventions/git-workflow#changelog-entries), y en una pull request `bun run check` falla mientras falte esa entrada. Nada más cuenta como terminado, tampoco un resumen que diga que lo está. Antes de hacer commit, lee tu propio diff en busca de comentarios, literales de cadena que deberían ser constantes y textos o documentación que el cambio haya vuelto incorrectos.
