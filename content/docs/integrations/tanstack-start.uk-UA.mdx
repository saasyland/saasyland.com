Застосунок побудовано на TanStack Start. `src/router.tsx` створює роутер з окремим QueryClient для кожного запиту, SSR-інтеграцією запитів, типовими компонентами помилки та «не знайдено», попереднім завантаженням за наміром, часом застарівання попередньо завантажених даних, що дорівнює його часу застарівання, і `rewrite` локалі. Типового компонента очікування немає: кожен маршрут задає власний скелетон (див. [Скелетони завантаження](/docs/architecture/delivery-layer#loading-skeletons)). `src/routes.ts` експортує `ROUTES` — константи шляхів, які використовують посилання, гарди та теги head.

Репозиторій містить патчі Bun для `@tanstack/router-core` 1.171.39 і `@tanstack/react-router` 1.170.46 і фіксує `@tanstack/router-core`, `@tanstack/react-router` та `@tanstack/react-start`, щоб пропатчені версії залишалися встановленими. Перший рендеринг роутера після гідратації скидав позицію прокручування вікна, яку браузер і вбудований скрипт відновлення роутера вже встановили, тож відвідувач, який прокручував сторінку під час гідратації, повертався на початок; з патчем гідратація не змінює позицію прокручування. `lazyRouteComponent` перезавантажує сторінку, коли чанк маршруту не вдається завантажити, щоб підхопити нове розгортання, а Safari і Firefox так само обривають чанки сторінки, яку відвідувач залишає, тож перезавантаження підміняло навігацію відвідувача сторінкою, яку він залишав; з патчем чанк, що не завантажився після `beforeunload`, чекає й завантажується знову, якщо відвідувач залишається. Для чанка loader маршруту такого перезавантаження немає; після розгортання сторінку знову завантажує типовий компонент помилки роутера (див. [Маршрути та доставка](/docs/architecture/delivery-layer#after-a-deploy)). Див. [Залежності](/docs/conventions/dependencies).

## Маршрути

`src/routes/` містить пласкі файлові маршрути: `admin.users.all.tsx` обслуговує `/admin/users/all`, `_site.tsx` — це макет без шляху, а `_site.docs.$.tsx` — splat-маршрут. Ідентифікатор у `createFileRoute("…")` — це рядковий літерал, який підтримує генератор роутера в `src/routeTree.gen.ts`; папки `__test__` не вважаються маршрутами.

Файл маршруту лише компонує свою сторінку. Він визначає компонент `<Name>Page` або `<Name>Layout`, `NAMESPACE` або `NAMESPACES`, завантажувач, що виконує завантаження метаданих, повідомлень і даних в одному `Promise.all`, `head: pageHead(ROUTES.X)` і, для захищених зон, гард у `beforeLoad`. Віджети, діалоги, форми та стовпці таблиць розміщено в `src/presentation/components/custom/`, і вони самі зчитують свої переклади та дані. Про завантажувач див. [use-intl](/docs/integrations/use-intl), а про гарди — [Better Auth](/docs/integrations/better-auth).

## Серверні функції

Операції — це нативні функції `createServerFn`, експортовані зі сценаріїв використання модулів, тож застосунок не відкриває для них REST-ендпоінтів. Див. [Серверні функції та сценарії використання](/docs/integrations/server-functions).

## HTTP-обробники

Ці маршрути в `src/routes/api/` оголошують `server.handlers`:

| Маршрут                                      | Обробник                                                                                  |
| -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `/api`                                       | Повертає середовище виконання у форматі JSON                                              |
| `/api/auth/$`                                | Better Auth, зокрема OAuth-колбеки та вебхуки Polar за адресою `/api/auth/polar/webhooks` |
| <RepositoryFact name="cliApiBasePath" />`/*` | API ліцензій для CLI, `licenseApiHandlers` у `src/modules/license/license.api.ts`         |

```ts
import { createFileRoute } from "@tanstack/react-router"

import { auth } from "~/src/integrations/better-auth/auth.server"

export const Route = createFileRoute("/api/auth/$")({
  server: { handlers: { GET: ({ request }) => auth.handler(request), POST: ({ request }) => auth.handler(request) } },
})
```

## Попередній рендеринг

Плагін TanStack Start у `vite.config.ts` вмикає попередній рендеринг з обходом посилань, а `shouldPrerender` (`src/lib/prerender.ts`) фільтрує пройдені шляхи. `build:preview`, `build:production` і `build:test` попередньо рендерять публічні сторінки (лендинг, юридичні сторінки, блог і документацію) у кожній локалі. Фільтр пропускає `/admin`, `/api`, `/app`, `/auth`, `/courses` і `/newsletter` з префіксом локалі чи без нього, а також посилання, що містять `?` або `#`. Пропущені сторінки рендеряться у Worker для кожного запиту.
