## 結論から

ページ上のすべての事実は、ちょうど 1 つの情報源を持ち、ページはそこからそれを出力すべきです。サイトが述べていることを種類ごとに分けてください。コードについての件数は、ビルドが計測します。価格や上限のようにビジネスが決める値は、コードで一度だけ宣言してインポートします。そこから導出する数値は計算し、しかも控えめに計算します。機能が動くかどうかはコードの中のステータスであり、それに依存するすべての文はステータスごとのバージョンを持ちます。振る舞いについての約束は、それを証明するテストとともに列挙します。外部の世界についての事実には、日付とリンクを付けます。コードの抜粋やリファレンスの表のように手入力のまま残さなければならないものは、CI を失敗させるチェックがコードと比較します。そうすれば、人やエージェントが間違えうるのは値の周りの文章だけになり、それこそがレビューの役割です。

## ドキュメントのドリフトとは何か、そしてエージェントがそれを悪化させる理由

ドキュメントのドリフトとは、言葉が述べていることとコードがしていることの間のずれです。誰かが間違いを犯す必要はありません。「12 個のインテグレーション」と書いたページは、書かれた日には正しかったのです。コードには 13 個目が加わり、ページには加わらず、今ではそれが誤りになっています。原因は不注意ではなく重複です。同じ事実が 2 か所にあり、そのうち 1 か所しか、それを変えるものによって保守されていないのです。

Dave Thomas と Andy Hunt は、_The Pragmatic Programmer_ でこの原則に名前を付けました。「すべての知識は、システムの中で、単一で、曖昧さのない、権威ある表現を持たなければならない」。彼らは、ドキュメントもその対象だと明言しています。違反を見分けるための彼らのテストはこうです。「コードのある 1 つの側面を変えなければならないとき、その変更を複数の場所で、複数の異なる形式で行っていないだろうか。コードとドキュメントを変更しなければならないだろうか……。もしそうなら、そのコードは DRY ではない」。

Google のドキュメントのガイドは、これを運用の言葉で示しています。「ドキュメントは、コードの変更と同じ CL で変更する」。このルールは、コードを変更する人が、そのコードに触れているすべてのページを知っている場合には機能します。規模が大きくなると機能しなくなり、AI コーディングエージェントはまさにその規模をもたらします。

### エージェントがコピーを増やす 3 つの仕方

**速度。** エージェントはドキュメントのページを数分で書き、目にした数値をそのまま書きます。別のページに 176 個のテストファイルとあれば、新しいページにも 176 と書きます。エージェントがほかのページをもとに書くページは、どれもそれらの誤りを受け継ぎ、コピーを 1 つ増やします。

**言語。** saasyland.com は <RepositoryFact name="languages" /> 言語で公開されています。手入力した数値は言語の数だけ存在し、翻訳エージェントは、渡された英語のテキストがどれであれ、それをもとに作業します。2026年11月12日、私たちは、翻訳されたブログ記事が古い英語のバージョンから作られていたことに気づきました。それらは、サイトがもう使っていない Next.js、Bun、Elysia、Neon のスタック、54 言語、141 個のテストファイル、472 件のテストを説明していました（#116）。どの翻訳もそれ自体としては一貫していて、流暢で、そして誤っていました。

**並行するセッション。** 同時に作業する複数のエージェントは、それぞれ自分のセッションが始まったときに正しかったバージョンの事実をコピーします。どちらもある件数に触れている 2 つのプルリクエストは、どちらの順にでもマージされえて、後からマージされたほうが、その数値が新しいかどうかに関係なく勝ちます。

エージェントは、翻訳してはいけないものも翻訳します。翻訳者にとって、文の中の数値やパスはテキストに見えるからです。11月15日の整合性の監査では、ランディングページの根拠の一覧が、日本語では `bun run テスト`、フランス語では `src/intégrations/` と表示していることがわかりました（#169）。管理画面のデモ用の価格画面では、各言語のメッセージに価格が手入力されていて、翻訳者がそれを換算していました。ポーランド語のページは 129 zł、ブラジルのページは 58 レアル、ドイツ語のページは 58 € と表示し、その隣には $290 というドルの価格がありました（#169）。2 つのロケールは、連絡先のメールアドレスそのものまで翻訳していました（#132）。どれも値を含む文であり、その値が文の一部として扱われたのです。

### 私たち自身のドリフトはどう見えたか

saasyland.com のランディングページは、かつて、そこにあるすべての数値がこの公開リポジトリから生成されていると述べていました。11月12日の時点で、そうだったのは 2 つだけでした。GitHub のスター数と React のメジャーバージョンです。残りはメッセージファイルに手入力されていて、ずれていました（#115）。

| ページ上の主張                            | リポジトリにあったもの |
| ----------------------------------------- | ---------------------- |
| 176 個のテストファイル                    | 221                    |
| 8 個の Playwright のスイート              | 12                     |
| 13 個の管理セクション、別の箇所では「十」 | 9                      |
| 「十二」の CLI の質問                     | 13                     |

どれも、手入力された時点では嘘ではありませんでした。どれもコードがすでに追い越したスナップショットだったのです。そこが要点です。注意深くなることでドリフトを直すことはできません。コピーは誤りになるその日まで正しく、それがどの日なのかを教えてくれるものは何もないからです。

## 6 種類の記述と、それぞれの真実がある場所

何かを作る前に、サイトが述べていることを分類してください。種類ごとに信頼できる情報源が異なり、必要な仕組みも異なります。

| 種類       | 例                                 | 信頼できる情報源                | 仕組み                                     | ずれたときに失敗するもの                                     |
| ---------- | ---------------------------------- | ------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| 計測       | テスト、ページ、言語の数           | リポジトリ                      | ビルドが数える                             | ずれようがない：ビルドが今日の件数を出力する                 |
| 宣言       | 価格、プランの上限、返金期間       | コード内の 1 つの定数           | インポートし、ロケールごとに書式を整える   | 外部のシステムを定数と比較するテスト                         |
| 導出       | 節約できる時間、時間に換算した価格 | 宣言された値に対する式          | コードで計算し、控えめに丸める             | 主張がまだ成り立つことを確かめるテスト                       |
| ステータス | 機能が提供中か提供予定か           | 機能ごとに 1 つのステータス定数 | ステータスごとのバージョンを持つメッセージ | 両方のバージョンを描画するテスト                             |
| 振る舞い   | 「返金するとライセンスが終了する」 | コードの振る舞い                | 主張の隣に名前を記したテスト               | 証明済みのすべての主張にまだテストがあるかを確かめるチェック |
| 外部       | アンケートの結果、競合の価格       | 他者のページ                    | 日付付きの引用と、その再確認               | 自動で失敗するものはない：見直しの日付                       |

表から 2 つのルールが導かれます。第一に、最後の種類を除くすべての種類は、ずれたときにチェックを失敗させるようにできるので、レビューで注意を向けるべきなのは最後の種類です。第二に、仕組みは記述の種類によって決まり、それが現れる場所によっては決まりません。同じ価格が、プランのカード、ブログ記事、FAQ の回答、ページのメタディスクリプションに現れ、そのどれもが同じ情報源を必要とします。

## ビルド時に計測する

リポジトリについての件数は、ページを公開するビルドが、その件数の対象となるのと同じファイルから計算すべきです。たいていのバンドラーには、そのための場所があります。Vite のプラグイン API はそれを仮想モジュールと呼んでいます。「仮想モジュールを使うと、通常の ESM の import 構文で、ビルド時の情報をソースファイルに渡せる」。プラグインはビルドの開始時に値を計算し、どのページも通常のモジュールのようにそれをインポートします。

私たちのプラグインは `scripts/repository-facts.ts` で、`virtual:repository-facts` を提供します。テストファイル、Playwright のスペック、UI コンポーネントを glob で数え、Playwright に問い合わせてブラウザーテストを一覧にし、ツールの設定ファイルそのものから設定を読み取ります。`vite.config.ts` からはカバレッジのしきい値、リントの上限、フォーマッターの幅を、`.nvmrc` からは Node のバージョンを、`package.json` からは Bun のバージョンを、ワークフローのファイルからは CI のシャードの数を読みます。数行を見るだけでも、計測がいかに直接的かがわかります。

```ts title="scripts/repository-facts.ts"
    e2eShards: readShards(E2E_WORKFLOW),
    e2eSpecs: countFiles(`${e2eSpecsPath}/*.spec.ts`),
    e2eSpecsPath,
    e2eTests: browserTests.length,
```

プラグイン自体は 30 行ほどです。Vite の `config` フックで 2 つのモジュール、つまりファクトと、ドキュメントだけが表示する表のソースを組み立て、Vite のプラグインガイドが仮想モジュールについて示しているとおり、`\0` で始まる解決済みの ID でそれぞれを提供します。

```ts title="scripts/repository-facts.ts"
    enforce: "pre",
    load: { filter: { id: RESOLVED_MODULE_IDS }, handler: (id) => sources.get(id) },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: MODULE_IDS }, handler: (id) => `${RESOLVED}${id}` },
```

これを信頼できるものにしているのは、3 つの設計上の選択です。

**主張の対象そのものを計測し、代わりのものを計測しない。** 最初のバージョンは、管理セクションをサイドバーのラベルから数えていました。サイドバーそのものを数えると、gzip 圧縮で 3.7 KB の管理画面のコードがランディングページに入り込むからです（#115）。ラベルがサイドバーと一致し続けることは、テストが確かめていました。その後、件数の意味が変わりました。ランディングページは動作する管理セクションの数を主張していたのに、11 個のうち 5 個はデモデータを表示していたのです。そこで管理メニューの各項目にステータスを与え、ファクトは動作するものだけを数えるようにし、数値は 11 から 6 に下がりました（#177）。その後、デモ画面はすべて削除されました（#259）。このファクトは現在 <RepositoryFact name="adminSections" /> を示しており、すべての項目が動作する画面なので、すべての項目を数えています。

**ドキュメントが説明できない設定を拒否する。** 「カバレッジは 100% に保たれている」と述べるページは、しきい値が 1 つであることを前提にしています。誰かが branches を 95 に、lines を 100 に設定すれば、その文は曖昧になります。私たちのプラグインは読み取った設定をスキーマで検証し、そのスキーマは 4 つの異なるしきい値を拒否します。

```ts title="scripts/repository-facts.ts"
const thresholdsSchema = zod
  .object({ branches: zod.number(), functions: zod.number(), lines: zod.number(), statements: zod.number() })
  .refine(
    ({ branches, functions, lines, statements }) => [branches, functions, statements].every((threshold) => threshold === lines),
    "The docs state one coverage threshold for all four metrics",
  )
```

ビルドはそのメッセージとともに失敗し、しきい値を変えた人またはエージェントは、ドキュメントに何と書くべきかを決めなければなりません。これは事実の値だけでなく、事実の形に対するチェックです。

**パスとコマンドも事実の一部。** 読者に `coverage/coverage-summary.json` を開くように、あるいは `bun run test:coverage` を実行するように伝える文には、コードが所有する値が 2 つ含まれています。#169 以降、ランディングページはそれらを同じモジュールから取得しています。サマリーのパスは Vite の設定の `reportsDirectory` から、スペックのディレクトリは Playwright の `testDir` から、コマンドは `package.json` からです。引用されたすべてのパスが存在し、すべてのコマンドがスクリプトであることを、テストが確かめます。翻訳にそれらが含まれることはないので、どの翻訳者も、それをもう一度 `bun run テスト` に変えることはできません。

## 値は文字列ではなくコンポーネントで出力する

値がコードの中に存在するようになったら、それを 1 つのコンポーネントで出力し、その結果を決して手入力しないでください。私たちのドキュメントとブログでは、そのコンポーネントが `<RepositoryFact>` です。MDX では、`<RepositoryFact name="testFiles" />` は <RepositoryFact name="testFiles" /> と、`<RepositoryFact name="e2eTests" />` は <RepositoryFact name="e2eTests" /> と、`<RepositoryFact name="coverageThreshold" unit="percent" />` は <RepositoryFact name="coverageThreshold" unit="percent" /> と表示され、いずれも今読んでいるページの言語に合わせて書式が整えられます。書式のルールは、全体でも十数行に収まります。

```tsx title="src/presentation/components/custom/repository-fact.tsx"
const FactValue = ({ unit, value }: { readonly unit?: keyof typeof UNIT_FORMATS | undefined; readonly value: Value }): JSX.Element => {
  const format = useFormatter()

  if (typeof value === "number") {
    return <>{format.number(value, unit && UNIT_FORMATS[unit])}</>
  }

  if (typeof value === "string") {
    return <code>{value}</code>
  }

  return <>{format.list(value.map((item) => <code key={item}>{item}</code>))}</>
}
```

数値は、ロケールの区切り文字で書式が整えられ、`unit` を指定すると、秒、時間、日、パーセントを表すそのロケールの語が、正しい複数形で付きます。文字列はコードとして出力されます。文字列のファクトはどれも、すべての言語で同じに見えなければならないパス、コマンド、識別子だからです。リストは、そのロケールでのコードのリストになります。英語では「a, b and c」、フランス語では「a, b et c」です。

表も同じように扱います。`<RepositoryTable>` は、コードが組み立てた行を、ページが翻訳した列名の下に出力します。各ロールの権限ステートメント、コミットのタイプとその絵文字、地域別価格の倍率とその国、各言語が使ってはいけない呼びかけの形などです。<RepositoryFact name="languages" /> 言語に手入力した表は、1 つのデータ構造の <RepositoryFact name="languages" /> 個のコピーです。その構造から出力した表は 1 つです。

コンポーネントを描画できない場所が 3 つあり、それぞれに別の答えが必要です。

- **メッセージファイル。** インターフェースの文言は、MDX ではなく JSON のメッセージにあります。値は `{testFiles, number} test files` のように ICU の引数としてメッセージに入り、メッセージを描画するコンポーネントがファクトのモジュールを渡します。こうしたメッセージにはすべて ICU の指針が当てはまります。「サブメッセージの中には完全な文を書く」。断片をつなぎ合わせた文は、翻訳者が語順を入れ替えられないからです。
- **フロントマター。** 記事のタイトル、説明、FAQ は YAML で、ページの head、フィード、構造化データに使われます。私たちの記事のタイトルと FAQ の回答は、`formatPostText` がファクトを使って書式を整える ICU メッセージなので、FAQ の回答に言語の数を含めることができます。メタディスクリプションはそうできないので、数値を使わずに書きます。
- **コードブロック。** コードブロックはバイト単位でそのままコピーされます。これには次の仕組みが必要です。

その成果は、私たちの履歴に表れています。#137 がドキュメントの手入力された値をすべて置き換えたとき、ブログだけでも、このコンポーネントの以前のバージョンの使用箇所が 81 か所あり、その名前を変える必要がありました。ドキュメントには、レート制限、カバレッジ、リントの上限、タイムアウト、動画のエンコード設定、署名付き URL の有効期間、ポーリングの間隔、ページサイズ、価格、バージョン、リトライ、スケジュールの値が出力されるようになりました。どれもそれまで 9 つの言語で手入力されていたものです。

## 値を手入力のまま残すなら、チェックする

テキストそのものに値を含めなければならない場合もあります。コードの抜粋、ルートの表、環境変数の一覧です。そうしたものについてのルールは、失敗するチェックでページとコードを比較することです。

**例を実行するか、ソースと比較する。** Rust はこれをドキュメントのツールに組み込んでいます。「rustdoc は、ドキュメントの例をテストとして実行することをサポートしている。これにより、ドキュメント内の例が最新で、動作することが確かめられる」。TypeScript のサイトでは、すべてのスニペットを実行するのは難しいので、代わりに比較します。リポジトリのパスをタイトルに付けたコードブロックは、そのファイルの正確な抜粋でなければなりません。

```ts title="scripts/check-content.ts"
const quotedSourceProblems = ({ label, target }: Translation): string[] =>
  [...target.matchAll(QUOTED_SOURCE_PATTERN)].flatMap(({ groups }) => {
    const path = groups?.["path"] ?? ""
    const file = join(REPOSITORY_DIR, path)

    if (existsSync(file) && readFileSync(file, "utf8").includes(groups?.["code"] ?? "")) {
      return []
    }

    return [`A code block in ${label} is not an excerpt of ${path}`]
  })
```

この記事のタイトル付きのコードブロックはすべて、<RepositoryFact name="languages" /> 言語のすべてで、すべてのプルリクエストに対して、このようにチェックされます。上で引用したファイルのどれかを誰かが変更すると、`bun run check` はこの記事の名前を挙げ、抜粋が更新されるまで失敗します。

**リファレンスの表は生成するか、比較する。** ルートのリファレンス、スクリプトのページ、環境変数の表は、コードがすでに持っているリストです。私たちのコンテンツチェックは、ルートのページがルートの定数に誤ったパスを与えたとき、スクリプトのページが `package.json` のスクリプトを載せていないか、存在しないスクリプトを載せているとき、環境変数の表が `wrangler.jsonc` で宣言されたシークレットを載せていないときに失敗します。ドキュメントのページが、どのビルドモードでも許可されないローカルホストやサブドメインに言及したときにも失敗します。

**翻訳を英語のページの構造に従わせる。** 翻訳は、英語のページと同じインラインコード、同じ props を持つ同じコンポーネント、同じリンク、同じ数の表の行を持たなければなりません。翻訳されたコマンドとパスを完全になくしたのは、このチェックです。翻訳者は、人間であれエージェントであれ、すべての文を言い換えることはできますが、バッククォートの中の文字は 1 文字も変えられません。

**デプロイの前に、外部のシステムをコードと照合する。** 価格は `TIER_PRICES` で宣言されています。決済プロバイダーは自分の商品カタログに独自のコピーを持っていて、そこに食い違いがあれば、ページがある価格を表示している一方で、別の価格を請求することになります。私たちのデプロイスクリプト `bun run deploy:<environment>` はビルドの前に `polar:verify` を実行し、Polar の商品の価格が定数と異なるとき、あるいはそのライセンスキーが `LICENSE_ACTIVATION_LIMITS` と異なる台数の端末を許可するときに失敗します。`main` へのプッシュのたびに CI が実行するデプロイはこれを実行しません。CI には読み込める `.env.<environment>` がないからです。そのため、Polar で何かを変更するたびに手でも実行しています。エラーメッセージは定数の名前を挙げるので、それを読んだ人は、どちらが情報源なのかがわかります。

## 時制ではなくステータス

正しく保つのが最も難しいのは、未来についての主張です。「課金を生成する」は、出荷されるまでは偽で、出荷された後は真であり、それを述べるすべての文が同じ日に変わらなければなりません。文章はこれをうまく扱えません。未来のこととして書いた文は、機能が出荷された後も未来のことのまま残り、現在のこととして書いた文は、そのほうが聞こえがよいという理由で、早すぎる時期に書かれます。

解決策は、提供状況をコードの中の値にすることです。各機能がステータスを持ち、それに依存するすべての文は、ステータスごとに 1 つのバージョンを持つメッセージになります。

私たちのステータスは `FEATURE_STATUS.AVAILABLE` と `FEATURE_STATUS.ARRIVING` の 2 つです。各プランの機能は、そのステータスとともに `TIER_FEATURES` に列挙されていて、プランのカードはそれらを **提供中** と **提供予定** の下にまとめるので、どの言語もステータスを手入力しません。CLI がまだプロジェクトを生成できなかったころ、その事実は文章の中にありました。9 つの言語で 11 個のメッセージです。#189 はそれを 1 つの定数 `CLI_GENERATION` に移し、それらのメッセージのそれぞれを ICU の select に変えました。

```json title="messages/en-US/components.custom.pricing.json"
      "tagline": "{generation, select, available {The CLI and the generated source with its tests.} other {The CLI now, the generated source and tests as they arrive.}}",
```

ICU はこの仕組みを、「固定されたキーワードの集合によってサブメッセージを選ぶ『select』引数」を使うものと説明しています。各バージョンは完全な文なので、それぞれの言語が自分なりの書き方をできます。あるテストは、そうした文をすべて、すべての言語で両方のステータスで描画するので、今日は誰も目にしないバージョンも正しくなければなりません。別のテストは、ある言語が select の外、つまりステータスが届かない場所で「提供予定」と言っているときに失敗します。

11月20日に CLI がプロジェクトの生成を出荷し、#251 が定数を「提供中」に切り替えました。すべての select が、すべての言語で、ひとりでに切り替わりました。ヒーロー、コンフィギュレーター、FAQ、プランのキャッチコピー、顧客ワークスペースです。それでも同じプルリクエストで、10 本のブログ記事、ドキュメント、README の文章は手作業で更新しなければなりませんでした。それらの文は、select が届かない形で生成について説明していたからです。教訓は、まだ出荷していない機能についてのすべての文を、書いたその日からステータスを通すことです。長い形式のコンテンツの文も含めてです。

### できるところではステータスを導出する

手で設定するステータスは、それでも早すぎる時期に設定されることがあります。機能が動くかどうかをコード自身が知っているなら、ステータスをその知識から導出してください。私たちの CLI は、テンプレートがどの回答をサポートしているかを公開していて、ウェブサイトは課金のステータスをそこから導出します。

```ts title="src/data/marketing.ts"
const TEMPLATES_GENERATE_BILLING = CLI_TEMPLATE_SUPPORT.choices.billing.some((option) => option !== NONE)

export const BILLING_GENERATION: FeatureStatus = TEMPLATES_GENERATE_BILLING ? CLI_GENERATION : FEATURE_STATUS.ARRIVING
```

`CLI_GENERATION` が切り替わったとき、課金は **提供予定** のまま残りました。課金を生成するテンプレートがまだなかったからです（#233）。課金が例外であることを誰も覚えておく必要はありませんでした。課金を生成するテンプレートがリリースされれば、そのリリースが課金を移動させます。

### 情報源を指す文を書く

主張の中には、増えていくリストもあります。「TanStack Start、Cloudflare、D1、Drizzle、Better Auth、Resend を生成する」は、あるリリースでは正しく、次のリリースでは不完全です。#233 は、そうした文を、内容を言い直す代わりに情報源を名指しするように書き直しました。生成が書き出すのは「コンフィギュレーターで選択できるオプション」であり、コンフィギュレーターはテンプレートがサポートするオプションだけを有効にします。リストが増えても文は正しいままで、リストは 1 か所にあります。

## 導出した数値：切り捨て、上限を設け、行を見せる

マーケティングの数値は、しばしば導出したものです。節約できる時間、節約できるお金、最初のデプロイまでの時間などです。こうした数値は最も水増ししやすく、最も確かめにくいので、3 つのルールを適用します。

1. **項目ごとの入力からコードで計算し**、すべての入力を読んで異議を唱えられるようにします。
2. **読者に不利な方向に丸め**、見出しの数値には上限を設けて、行が追加されたときに主張がひとりでに大きくならないようにします。
3. **行を公開します。** 見出しの数値が長い形式で現れるところでは、必ずそうします。

私たちの「先行時間」の主張、つまり生成されたプロジェクトが節約するシニアの作業時間は、#184 以降この 3 つすべてに従っています。`src/data/head-start.ts` の `HEAD_START_ROWS` は、テンプレートが生成するデフォルトのプロジェクトの各部分、それが含まれるテンプレートのレイヤー、そして手作業で作った場合にかかる時間の低い見積もりと高い見積もりを列挙しています。課金、組織、テナンシー、サンプルのコマースには行がありません。それらを生成するテンプレートがまだないからです。行を合計すると、現在は <RepositoryFact name="headStartLowHours" />〜<RepositoryFact name="headStartHighHours" /> 時間になり、見出しの数値は低いほうを取ります。

```ts title="src/data/head-start.ts"
export const HEAD_START_HOURS = Math.min(
  HEAD_START_CLAIM_MAX_HOURS,
  Math.floor(HEAD_START_LOW_HOURS / HEAD_START_ROUNDING_HOURS) * HEAD_START_ROUNDING_HOURS,
)
```

見出しには <RepositoryFact name="headStartHours" /> と表示されます。上限は、行ができる前にサイトがすでに主張していた数値なので、項目に分けることは、主張を裏付けるか、引き下げるかのどちらかにしかなりえませんでした。行が削除されれば、誰もページを編集しなくても数値は下がります。この数値を論じる記事はすべての行をその見積もりとともに出力するので、ある見積もりに同意しない読者は、それがどの見積もりで、どれだけ違うのかを見ることができます。

価格から導出するどんな数値にも、同じことが当てはまります。Core の価格はシニアエンジニアの <RepositoryFact name="corePriceInHours" unit="hour" /> 分の時間より安い、という主張は `CORE_PRICE_IN_HOURS` であり、価格と、その隣で宣言されている例示用の時給から計算されます。価格がその時間を下回らなくなれば、テストが失敗します。#132 は、2 つのプランの差額のような、価格から導出して文章に手入力していた合計をすべて削除しました。手入力した差額は、どちらかの価格が変わったその日に誤りになるからです。

## 2 つのリポジトリの間の 1 つのコントラクト

2 つのリポジトリの間のドリフトは、同じ問題をもっと離れた距離で見たものです。_The Pragmatic Programmer_ はこれを表現の重複と呼んでいます。「コードは、外部のものにも存在する知識を持たなければならない……。一方の端で変えれば、もう一方の端が壊れる」。

SaaSy Land には 2 つのリポジトリがあります。ライセンスを販売し、ライセンス API を提供するこのウェブサイトと、顧客が実行する非公開の CLI です。どちらも、同じプラン、API のルート、エラーコード、上限、終了コード、スタックのオプションの一覧を必要とします。その知識は 1 つのパッケージ `@saasyland/stack` にあり、MIT ライセンスで npm に公開されています。CLI がそれをビルドし、ウェブサイトがそれをインポートします。

どれだけインポートするかはトレードオフで、私たちの場合は計測がそれを決めました。パッケージのプランの定数を実行時に再エクスポートすると、12,072 バイト、gzip 圧縮で 4,493 バイトのチャンクがランディングページの JavaScript に入るところでした。パッケージが副作用を宣言しておらず、何もツリーシェイキングできなかったからです（#160）。ウェブサイトは自分のプラン名を持ち、それを型のレベルでコントラクトに結び付けています。これには実行時のコストがかかりません。

```ts title="src/modules/license/license.constants.ts"
export const LICENSE_TIER = {
  AGENCY: "agency",
  COMPLETE: "complete",
  CORE: "core",
} as const satisfies Record<string, Api["tier"]>
```

どちらかの側でプランを追加または削除すると、ウェブサイトのコンパイルが失敗し、テストが値を比較します。#244 以降、ランディングページのコンフィギュレーターも、スタックの質問、オプション、ルールをパッケージから読み取るので、ウェブサイトはマトリクスのコピーを持っていません。

共有のコントラクトは、重複した知識を取り除きます。デプロイ同士のバージョンのずれは取り除きません。11月20日、公開された CLI が送ったフィールドを、まだ 1 つ前のコントラクトのバージョンで動いていた本番のウェブサイトが拒否しました。どちらのリポジトリも、自分が固定したバージョンに対してはすべてのテストに合格していました。[このシリーズの最初の記事](/blog/ai-coding-agent-guardrails)がその経緯を伝えています。そこから生まれたルールは、コントラクトの変更は、それを使うクライアントがリリースされる前にサーバーで有効になっていなければならない、というものです。

### この記事を書きながら見つけたドリフト

パッケージ自身の README もほかと同じページの 1 つであり、同じようにずれていきます。`@saasyland/stack` 0.1.0-beta.5 とともに公開された README には、今も「saasyland.com のコンフィギュレーターは、マトリクスの独自のコピーを持っている」と書かれています。これは、11月20日にマージされてそのコピーを削除した #244 までは正しいことでした。npm はこの種のドリフトを残りやすくします。「パッケージのページの `README.md` ファイルが更新されるのは、パッケージの新しいバージョンを公開したときだけ」だからです。別のリポジトリについて説明する README は、そのリポジトリが所有する事実のコピーであり、解決策は、パッケージ自身がすることだけを述べることです。

## テストで証明できることのための主張の台帳

振る舞いについての主張もあります。「返金されたライセンスは動かなくなる」「CLI は選んだオプションだけを書き出す」「すべての文字列が翻訳されている」といったものです。コードはそれらを出力できません。テストはそれらを証明でき、台帳は各主張をそのテストに結び付けられます。

CLI のリポジトリは、そうした台帳を 1 つ持っています。1 つの文書が、saasyland.com、そのドキュメント、法的ページ、記事、そして CLI 自身の README が、CLI とそれが生成するプロジェクトについてしているすべての約束を列挙しています。各行には、変わることのない ID、主張の正確な文言、その主張をしているすべての場所、それを証明するテストのレイヤー、そして次の 3 つの状態のいずれかにある証明のセルがあります。

- **証明済み：** 1 つ以上のテスト。それぞれをファイルとタイトルで示します。
- **予定：** 証明を追加することになるプルリクエスト。
- **未解決：** その主張は現時点では偽であるか証明できず、行には、何を変えなければならないか、つまりプロダクトか文言かが書かれています。

このリポジトリのチェックは、証明済みの主張が存在しないテストファイルやテストのタイトルを挙げているとき、予定の主張が予定のプルリクエストを挙げていないとき、2 つの主張が同じ ID を共有しているときに失敗します。ウェブサイトのリポジトリのテストで証明される主張は、下で説明するゴールデン差分を実行するのと同じ CI のジョブが、固定したコミットのウェブサイトに対してチェックします。予定の主張にテストを追加するプルリクエストは、同じコミットで予定のセルをそのテストに置き換えます。CLI の動作を変えるプルリクエストは、それを説明する行を確認します。

最も役に立つのは未解決の行です。文言が述べているのにプロダクトがまだしていないことを、すべてのプルリクエストから見える場所に記録し、機能を作るか文言を言い換えるかという決定で終わらなければなりません。

ウェブサイトには、ある種類の主張のための独自の台帳があります。ユーザーと管理者のすべてのフローは、それをエンドツーエンドで実行するブラウザーテスト、またはまだどのテストも実行していない理由とともに `e2e/data/<feature>.flows.ts` に列挙されていて、なくなったテストをフローが挙げていると `bun run check` が失敗します（#253）。[テストカバレッジ](/docs/tooling/test-coverage)のドキュメントのページがその一覧を出力しています。現在、<RepositoryFact name="flows" /> 件のフローのうち <RepositoryFact name="flowsCovered" /> 件がカバーされ、<RepositoryFact name="flowsMissing" /> 件にはブラウザーテストがなく、<RepositoryFact name="flowsToBuild" /> 件はまだ作る必要のある機能です。同じプルリクエストは、カバレッジについての主張を正確にしました。「テストカバレッジ 100%」は「コードカバレッジ 100%」になりました。その数値が計測しているのは、ユニットテスト、統合テスト、コンポーネントテストが実行した行であって、ブラウザーで証明されたフローではないからです。FAQ の質問が 1 つだけ漏れていて、11月22日に変更されました。

### 台帳が見つけられないもの

台帳がチェックするのは証明であって、主張ではありません。証明のセルだけを読むチェックは、行の文言を引用先のページと比較しません。そのため、文言が言い換えられたり取り下げられたりした後も、行が古い文を引用し続けることがあります。台帳を持つなら、引用したテストだけでなく、引用した場所もチェックに読ませ、主張がサイトから消えたら行を削除してください。

## ゴールデン差分：生成された出力と実際のプロダクトの比較

コードを生成するプロダクトには、守るべき主張がもう 1 つあります。生成されたプロジェクトが、マーケティングで見せているものと同じだということです。CLI のリポジトリは、この 2 つを直接比較します。そこにある 1 つのスクリプトは、`init` と同じようにテンプレートから参照用のスタックを生成し、固定したコミットのウェブサイトを取得して、2 つのツリーをファイルごとに比較します。結果は、同一、意図的なカスタマイズ、相違、欠落のいずれかです。コミットされた一覧が、意図された相違をすべて理由とともに挙げています。たとえば法的ページは、顧客自身の約束なので生成されません。このレポートはすべてのプルリクエストで実行されます。まだマージを止めはしませんが、予定されている変更でゲートになり、ドリフトの夜間レポートも加わります。

生成されたプロジェクト自身のドキュメントも、同じ基準で扱います。テストは、インストールせずにスタックを生成し、その README、`AGENTS.md`、CI のワークフローを読みます。それらのドキュメントは、生成された `package.json` にないスクリプト、プロジェクトが定義していない環境変数、プロジェクトが含んでも作成してもいないパスに言及してはならず、バージョンにも言及してはなりません。バージョンは、バージョンを固定するファイルに任せます。そのため、テンプレートのドキュメントが述べられるのは、それを含むスタックについて正しいことだけです。

## 外部の事実：日付を付け、出典を示し、再確認する

外部の世界についての事実はコードから出力できず、しかも何よりも速くずれていきます。価格、アンケートの結果、競合の機能、次のリリースの後のツールの振る舞いなどです。それらを正直に保つルールが 3 つあります。

1. **一次情報源を引用する。** リンクを付け、数値を言い換えるのではなく引用します。
2. **すべての確認に日付を付ける。** 私たちの記事は「最終確認日」の行で始まり、出典をいつ読んだかについての注記で終わります。
3. **予定を決めて再確認する。** 事実が変わったら、記事の `updated` の日付を更新します。

再確認すると、思った以上のものが見つかります。11月17日、私たちはすべての記事をその出典と照らし合わせて監査しました（#241）。Stack Overflow の統計は、アンケートでは 66% とあるのに 45% と引用されていました。45% は同じリストの 2 番目の項目でした。非推奨の API を使う割合の 25〜38% という数値は、誤った論文のものとされていました。GitClear のものとされていた欠陥の数値は、GitClear の公開ページにはまったく載っていませんでした。競合の価格や件数も変わっていました。それらの文はエージェントが自信を持って書いたもので、私たちが持っていたすべてのチェックを通過していました。アンケートを読むチェックはないからです。

気にかけるべき商業上の理由は、信頼性にとどまりません。米国では、FTC の広告主向けのガイダンスが「広告主は、主張を裏付ける証拠を持っていなければならない」と述べ、「法律は、広告が出る前に広告主が証拠を持っていることを求めている」としています。主張をコードから出力し、振る舞いについての主張をテストとともに列挙するプロダクトのページは、その仕組み上、証拠を手元に持っています。

## かかるコスト

どれも無料ではありません。始める前に、そのコストを知っておく価値があります。

**保守すべきビルドステップとコンポーネント。** ファクトのプラグイン、コンポーネント、書式のルール、そしてそれらのテストは、ほかと同じコードです。レビューが必要で、手入力したテキストにはない形で失敗します。ビルドが見つけられないファイルを読むファクトは、ビルドを止めます。

**不注意なら、バンドルサイズ。** 値をインポートすると、そのモジュール全体がインポートされることがあります。値を共有する自然な方法が、ランディングページに不要なコードを引き込むところだったことが 2 回ありました。管理セクションを数えるための 3.7 KB の管理画面のコード（#115）と、3 つのプラン名を共有するための 12 KB のスタックのマトリクスとコントラクトのスキーマ（#160）です。公開ページに値をインポートするときはバンドルを計測し、型のレベルでの結び付けや範囲の狭いモジュールを選んでください。

**変化に耐える文章。** 数値を出力する文は、どんな数値でも正しく読めなければなりません。英語なら「1 test file」と「221 test files」のどちらでも、そして英語より多くの複数形を持つポーランド語でもです。私たちはそうした文を ICU の複数形で書くか、数値が単独で立つように言い換えます。文法が抵抗することもあります。ドイツ語やポーランド語では、出力された数値が文に必要な格を常に取れるとは限らないので、文をその数値の周りで書き直します。

**数値のないフロントマター。** メタディスクリプションと抜粋はコードを実行できないので、数える代わりに説明します。検索結果のスニペットでは少し損をします。

**一度きりの大きな変更。** 手入力された値の置き換えは、#137 で 643 個のファイルに及びました。どの値も 9 つの言語に存在していたからです。早くやるほうが、遅くやるよりはるかに安く済みます。

その見返りとして、私たちのドキュメントと記事が saasyland.com について述べる現在の件数、価格、上限、バージョン、言語の数は、すべての言語でコードから出力され、引用した抜粋やリファレンスの表を誤りにするようなコードの変更は、そのページの名前とともに CI を失敗させます。コールドスタートのような過去のビルドの計測値は、次のセクションで説明するとおり、そのプルリクエストを添えて手入力します。

## まだずれるもの

上の仕組みが届かないものもあり、誤りが今も現れるのはそこです。

- **値を含まない文章。** どのブラウザーがプルリクエストで実行され、どのブラウザーが `main` でだけ実行されるかは、数値を含まない CI のワークフローについての事実で、ランディングページは #115 まで、すべての言語でそれを誤っていました。そうした文を見つけられるのは、レビューか、ワークフローを読むテストだけです。
- **過去の数値。** この記事は、176、221、643 のような数値を意図的に手入力しています。それらはある日のリポジトリの姿を説明していて、それぞれがプルリクエストに結び付いています。過去についての主張なので、ずれることはありません。現在の数値は出力しています。
- **引数を取らないメッセージの中の値。** メッセージのチェックは翻訳の引数を英語と比較しますが、引数のないメッセージの中の数値は探しません。この記事を書いている間に、私たちはそうしたものを 1 つ見つけました。サインインフォームの横のキャッチコピーが、カバレッジの数値をすべての言語で手入力していたのです。
- **ビルドの外にあるドキュメント。** npm に公開されたパッケージの README などで、誰かが公開したときにしか変わりません。
- **外部の事実。** 再確認と再確認の間にずれます。

## コピーして使えるスターターキット

これらの部品は、Vite で作ったたいていの TypeScript のサイトに合います。上で説明したものの最小限のバージョンなので、名前は適宜変えてください。

**ファクトのプラグイン**です。ビルド時に計測し、仮想モジュールを提供します。

```ts
import { globSync, readFileSync } from "node:fs"
import type { Plugin } from "vite"
import { exactRegex } from "vite/rolldown/pluginutils"

const MODULE_ID = "virtual:facts"
const RESOLVED_ID = `\0${MODULE_ID}`

const collectFacts = () => ({
  testFiles: globSync("src/**/*.test.{ts,tsx}").length,
  nodeVersion: readFileSync(".nvmrc", "utf8").trim(),
})

export const facts = (): Plugin => ({
  name: "facts",
  resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_ID },
  load: { filter: { id: exactRegex(RESOLVED_ID) }, handler: () => `export default ${JSON.stringify(collectFacts())}` },
})
```

**コンポーネント**です。ページのロケールに合わせてファクトを出力し、コードはコードとして出力します。

```tsx
import facts from "virtual:facts"

export const Fact = ({ name, locale }: { name: keyof typeof facts; locale: string }) => {
  const value = facts[name]

  return typeof value === "number" ? <>{new Intl.NumberFormat(locale).format(value)}</> : <code>{value}</code>
}
```

**ステータスと、両方のバージョンを持つメッセージ**です。これに、両方を描画するテストを加えます。

```ts
export const FEATURE_STATUS = { ARRIVING: "arriving", AVAILABLE: "available" } as const

export const BILLING = FEATURE_STATUS.ARRIVING
```

```json
{
  "billing": "{billing, select, available {Billing is wired in.} other {Billing is arriving in a later release.}}"
}
```

**抜粋のチェック**です。パスをタイトルに付けたコードブロックを対象に、CI で実行します。

````ts
import { readFileSync } from "node:fs"

const TITLED_BLOCK = /^```\w*\s+title="(?<path>[^"]+)"\n(?<code>[\s\S]*?)^```$/gmu

export const excerptProblems = (page: string, source: string): string[] =>
  [...source.matchAll(TITLED_BLOCK)].flatMap(({ groups }) =>
    readFileSync(groups?.path ?? "", "utf8").includes(groups?.code ?? "") ? [] : [`${page}: not an excerpt of ${groups?.path}`],
  )
````

**主張の台帳**です。リポジトリの中に表として置き、証明済みのすべての行のテストが存在することを確かめるチェックを付けます。

```md
| ID        | Claim                            | Where                | Proof                                                   |
| --------- | -------------------------------- | -------------------- | ------------------------------------------------------- |
| CLAIM-001 | "Refunded licences stop working" | pricing page, FAQ q4 | `test/licence.test.ts` › "a refund revokes the licence" |
| CLAIM-002 | "Exports to CSV"                 | features page        | Planned: the export pull request                        |
| CLAIM-003 | "Works offline"                  | landing page hero    | Open: no offline mode exists; reword or build it        |
```

**レビューのルール**です。それ以外のすべてについて、指示ファイルに書きます。

```md
## Numbers and claims

- Never type a count, price, limit, version, path or command into docs, copy or messages: print it from code.
- Every sentence about a feature that has not shipped goes through its status.
- Every external fact has a link to its primary source and the date it was checked.
```
