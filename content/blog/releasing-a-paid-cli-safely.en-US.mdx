## The short answer

Treat the release as the one step that is not a merge. Everything before the registry can be automated and retried: versioning from changesets, building, packing once, running the built program on every platform you support, uploading whatever the CLI will download. The step that cannot be undone, a version appearing on npm, gets a second key that no workflow holds. Stage the release from CI with npm’s trusted publishing, which uses a short-lived OIDC token instead of a stored one, and have a maintainer approve the staged version with two-factor authentication. Pin by content everything the CLI fetches at run time, and check it against two sources. Create Git tags and GitHub Releases only after npm serves the version, because a staged version may never be published. And watch for the moments when a release tool decides, by its own rules, that there is nothing to do: an empty changeset once kept one of our betas from being staged at all, with every job green.

## Why a release is not a merge

A merge can be reverted with another merge. A release cannot, for three reasons.

**The version number is spent.** npm’s unpublish policy is blunt: "Once `package@version` has been used, you can never use it again." It adds: "This is true even if that package is unpublished." Unpublishing itself is allowed in the first 72 hours only if no other package in the registry depends on yours, and later only under stricter conditions; for everything else, npm recommends deprecation. A bad release is fixed forward with a new version, and the bad one stays in the registry for everyone who pinned it.

**Customers script against it.** A CLI’s public interface is wider than a library’s exports: its commands, flags and defaults, its exit codes, its machine-readable output, the files it writes and the runtimes it starts on. A changed default or a new exit code breaks a CI job you will never see.

**A paid CLI has more than one moving part.** Ours checks the licence with saasyland.com every time it creates a project, and downloads the templates it generates from, one bundle per release, through the website’s licence API. A release is a package on npm, plus a template bundle in storage, plus a contract with a server. The three have to agree from the first minute a customer can install the version.

AI agents change where the risk sits. They are fast and thorough at the reversible parts: writing changesets, keeping a version pull request current, editing workflows, writing release notes in <RepositoryFact name="languages" /> languages, checking the registry afterwards. They are exactly as confident about the irreversible part as about everything else. So the design principle of this post is simple: let the agents do everything up to the registry, make every step before it safe to run twice, and put a human key on the one step that is neither reversible nor repeatable.

A word on the setup, so you can map it to yours. The SaaSy Land CLI is three npm packages, `saasyland`, `create-saasyland` and `@saasyland/stack`, released from a private GitHub repository with Changesets 3 and GitHub Actions. As of 25 November 2026, previews go out on npm’s <RepositoryFact name="cliReleaseChannel" /> tag, the latest being 0.1.0-beta.5 of 20 November, and customers run <RepositoryFact name="cliPackageSpec" />; `latest` still holds the `0.0.0` placeholder that reserved the names. The agents are Claude Code sessions, a lead and the workers it briefs, and they own the CLI end to end. When the owner handed it over, he asked for "versioning, changelog and everything as professional as possible", released "in batches that make real sense". He approves every publication.

## Versioning a customer can rely on

### Write down what "breaking" means for a CLI

Semantic versioning only helps if you have written down what your public interface is. Our release policy lists what counts as breaking for the CLI:

- a command, flag or flag value removed or renamed, or a default changed;
- a different exit code for the same situation;
- a field of the `--json` output removed, renamed or given another type, while a new field is not breaking;
- a change to the project manifest that an older CLI cannot read;
- a higher minimum Node version;
- a removed or changed export of the shared package;
- a change that the licence API’s own rules call breaking.

Before 1.0 a minor version carries new features or a break, and a patch carries fixes only. The licence API has the same discipline at its own boundary. Within `v1` the website may add a response field, an endpoint or an error code, and the CLI ignores fields it does not know; anything else needs a `v2` served beside `v1` for as long as a supported CLI calls it. [The first post in this series](/blog/ai-coding-agent-guardrails) tells how a published CLI still sent a field the live website did not accept yet, and why a contract change now ships on the server first.

### A changeset is a release note for customers

Every pull request that changes a published package adds a changeset, and CI refuses one that does not: `changeset status --since=origin/<base>` fails when a package changed without one. The rule that matters more is about the content. A changeset is the customer’s release note: one or two plain sentences on what changes for them and what they have to do, with commands and flags written as they type them. "Fix bug in the flag parser" tells a customer nothing. This is the note of 0.1.0-beta.5, as the public [release notes](/docs/cli/releases) print it:

> **Breaking:** `--billing lemonsqueezy` is gone, because Lemon Squeezy is closing: it has taken no new sign-ups since 16 November 2026 and shuts down on 31 March 2027. `--billing polar` and `--billing stripe` remain values that `--billing` knows, and `init` still refuses both with code <RepositoryFact name="cliExitNotAvailable" />, because generated projects have no billing yet. `init --billing lemonsqueezy` now exits with code <RepositoryFact name="cliExitUsage" />, like any other value `--billing` does not have.

The way the rule is written decides what the agents produce. Told only to "add a changeset", an agent tends to write "Refactor the flag parser". Told that the changeset is what a customer reads in the changelog, it writes the note above. A change that customers cannot notice, such as a refactor or a new test, takes an empty changeset. That escape hatch is the source of the second incident in this post.

### One version for packages that ship together

The three packages form a Changesets fixed group, in which "all packages in the group will be version-bumped and published together even when there are no changes". So `saasyland@0.1.0-beta.5` always ships with `@saasyland/stack@0.1.0-beta.5`, and a customer, a bug report and a support reply all need one number. The cost is visible in the changelog: a package with nothing of its own to say still gets a release, and our website’s release notes print "No changes in this release." for it rather than leave a gap that looks like an omission.

### Cut releases in batches, and hold the version pull request

Changesets keeps a Version Packages pull request open and rebuilds it as changesets merge. That pull request is the release gate: merging it is the decision to release. We cut releases as coherent batches, never one per pull request. On `main`, the Version Packages pull request for 0.1.0 has been open since 14 November and held 24 changesets on 25 November; it merges when the stable batch is complete and documented.

Previews go out from a `beta` branch in Changesets’ pre mode. Its documentation warns that "Prereleases are very complicated!" and that "Mistakes can lead to repository and publish states that are very hard to fix." Both sentences came true for us, as you will see. If you use pre mode, keep it on a branch of its own, keep that branch’s history linear so the release tags point into a history you can read, and bring changes from `main` in a way you can review. We cherry-pick `main`’s commits onto a branch from `beta` and squash-merge it, so `beta` never gets a merge commit.

### The README on npm is part of the release

Until the first stable release, `latest` is the placeholder, so a README that says `npx saasyland init` runs the placeholder, where no command works. In 0.1.0-beta.1 the packed READMEs did exactly that, and untagged `create` commands resolved `latest` too. A smoke test now reads the README inside each packed tarball and fails when a command names one of the packages without the dist-tag, or with another one. The dist-tag the tests expect is declared once, and switching it is a step of the first stable release. The website’s own [CLI guide](/docs/cli) prints its commands from one constant, <RepositoryFact name="cliPackageSpec" />, for the same reason.

## Staged publishing: the human key sits at the registry

### What staging is

npm’s staged publishing "adds an approval step before packages go live on the npm registry". CI runs `npm stage publish`, which "does not require 2FA", and the version waits in a staging area until a maintainer approves it: "You will be prompted for 2FA verification whether you approve the package in the CLI or on npmjs.com." Rejecting a staged version needs the second factor too. The dist-tag is fixed when the version is staged: "The tag is an immutable property of the staged package." Staging needs npm 11.15.0 or later; our stage job uses the npm bundled with Node 26.13.1, which is npm 11.20.0, and prints the version it staged with in its summary.

npm is moving everyone this way. Its September 2026 changelog says that "npm is targeting January 2027 to remove direct publishing through bypass-2FA tokens", and offers stage-only tokens as the migration path for automation that cannot move to trusted publishing yet. Our stage runs log npm’s notice: "npm tokens that bypass 2FA are being restricted for account changes and direct publishing."

### Why the gate is at npm and not in CI

GitHub can make a job wait for a reviewer through environments, and the Changesets guide suggests "creating an environment with required reviewers to approve the publish job run". We put the key at npm instead, for two reasons. It guards the irreversible thing itself: whatever a workflow does, and whatever an agent merges, nothing is public until a maintainer approves the exact staged version. And it rests on the maintainer’s npm second factor, which no workflow, agent or GitHub token can hold. An approval in CI guards a job, and once it is given, that job can publish whatever it built. GitHub also offers required reviewers on private repositories only on its Enterprise plans, so for many teams the registry is the only place such a gate is available.

### Changesets does not stage yet, so stage from its plan

The Changesets guide is explicit: "At the moment, Staged Publishing does not work with Changesets, so you should use Trusted Publishing instead for now." Its v3 announcement says staging is coming in "the next feature update". Until then, its publish action runs `npm publish`, which a trusted publisher allowed only to stage rejects. So our stage job does what the action would do, with one command changed. It reads the publish plan that `changeset pack` writes beside the tarballs and stages each package with the access and the dist-tag that Changesets chose: `beta` in pre mode, `latest` otherwise.

For each package in that plan, the job first asks npm, with a public `npm view` that needs no credentials, whether the exact version is already served. If it is not, it runs `npm stage publish` on the packed tarball with the plan’s access and dist-tag and the `--json` flag, and reads the stage id from npm’s answer. Every package ends in exactly one of three outcomes, and that is what makes the job safe to run again, which matters because a release job is the one you most want to re-run after a runner fails:

- **Already on npm:** skipped. A push to `main` after a release, or a re-run, does not try to publish twice.
- **Staged by an earlier run:** npm answers with a 409, and the job reports it and moves on. A trusted publishing token can stage and publish, but npm says that "Shortlived tokens cannot run `npm stage` subcommands", so the job cannot list the stages to find the earlier id; its summary tells the approver where to look.
- **Anything else:** the job stops before the next package.

The job summary is the approver’s worklist: one row per package, with its version, its dist-tag, its stage id and the exact command that approves it. The three packages are one release, so all three are approved together. The release kit at the end of this post has a generic version of this job, written from npm’s documentation, for a repository without Changesets.

### What the registry records

For 0.1.0-beta.5, npm’s metadata names GitHub Actions as the publisher, through a trusted publisher, and names the maintainer who approved it. It was staged at 11:25 UTC on 20 November and became public at 11:44. That record is the audit trail: which workflow produced the bytes, and which person let them out.

## Trusted publishing: no token to leak

### Short-lived credentials, on one job only

Trusted publishing lets CI publish "using short-lived, cryptographically-signed tokens", obtained through the CI provider’s OIDC instead of a stored npm token. It needs npm 11.5.1 and Node 22.14.0 or later, and on GitHub, "The critical requirement is the id-token: write permission". On npm’s side, a trusted publisher names the GitHub organization or user, the repository, the workflow file and, optionally, an environment. Two more settings close the remaining doors:

- **The trusted publisher may stage and nothing else.** With npm’s CLI that is `npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish`, leaving `--allow-publish` off. For a trusted publisher, npm’s docs say, "`npm stage publish` is always allowed", while direct publishing and dist-tag changes are separate options, off unless a maintainer turns them on.
- **Publishing access requires two-factor authentication and disallows tokens.** npm notes that this "only affects traditional token authentication", so the trusted publisher keeps working while no token, stored anywhere, can publish.

A trusted publisher is configured in a package’s settings on npmjs.com, so a new package name costs one manual step: the owner publishes a `0.0.0` placeholder by hand, with two-factor authentication, then adds the trusted publisher and the access setting. That is why `latest` holds `0.0.0` today.

On GitHub’s side, the workflow starts with `permissions: {}`, and each job asks for what it needs. The Changesets guide puts it plainly: "make sure the `id-token: write` is only set on the job that needs to publish."

| Job                               | Permissions                                                     | Why                                                              |
| --------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| Choosing the release mode         | `contents: read`                                                | Reads the pending changesets                                     |
| Opening the version pull request  | `contents`, `pull-requests` and `actions` write                 | Pushes the release branch, opens the pull request, starts its CI |
| Building, verifying and packing   | `contents: read`                                                | Builds, tests and packs                                          |
| Running the built bins, nine jobs | `contents: read`                                                | Builds and runs the bins                                         |
| Staging on npm                    | `contents: read` and `id-token: write`, a protected environment | Exchanges an OIDC token with npm and uploads the template bundle |
| Creating tags and Releases        | `contents: write`                                               | Creates tags and Releases                                        |

The staging job is the only one that may request an OIDC token, and the only one that uses the protected environment. That environment holds the credentials for the template storage, and only the release branches may deploy to it. GitHub makes environment secrets "only available to workflow jobs that use the environment", so no other job, and no workflow run from any other branch, can read them.

### The token on the checkout is a permission too

`actions/checkout` keeps the job’s token in the local Git configuration "to run authenticated git commands", unless you set `persist-credentials: false`. We set it to false in every job, and the first Version Packages pull request never opened: when Changesets pushed the release branch, Git "could not read Username for 'https://github.com'". The fix gave the token back to that one job, the only one that pushes. Least privilege is a property of each job, not one setting copied through a file.

### The failure npm could not explain

The first beta reached npm twelve hours after its version pull request merged. On 14 November at 06:18 UTC, the stage job failed with npm’s own error:

```text
npm error code ENEEDAUTH
npm error need auth This command requires you to be logged in to https://registry.npmjs.org/
```

The message tells you to log in. The real reason was that the OIDC token exchange had failed, and npm writes that reason at verbose level, into a debug log on the runner that is deleted with the job. We made the stage job upload `~/.npm/_logs/` as an artifact whenever it fails, and the log of the next failure named the cause: npm found no trusted publisher that matched the run’s repository, workflow and environment. npm’s docs warn about exactly this: "npm does not verify your trusted publisher configuration when you save it", and "All fields are case-sensitive and must be exact." Once the settings on npmjs.com matched the workflow, a re-run of the failed job staged 0.1.0-beta.0 at 18:24, and the owner approved it four minutes later.

The lesson reaches beyond npm. When an authentication layer fails, its error message usually describes the fallback it tried last, not the step that failed first. Keep the tool’s debug log from every failed release job, with a short retention, and read it before you change anything.

### Provenance needs a public repository

On a public repository, trusted publishing gives you provenance for free: npm "automatically generates and publishes provenance attestations", but only when you are "Publishing from a public repository" and "Publishing a public package", and "Provenance generation is not supported for private repositories". Our CLI is commercial and its repository is private, so its packages carry no provenance attestation. What they carry is npm’s registry signature, which anyone can check: in a clean directory with `saasyland@0.1.0-beta.5` installed, `npm audit signatures` reports "1 package has a verified registry signature". If your source is public, turn provenance on and tell your users how to verify it. If it is private, say so, rather than let "trusted publishing" imply a guarantee you do not have.

## Pin everything the CLI downloads

### The templates are part of the release, but not of the package

`saasyland init` generates a project from templates it does not ship. After the licence check, it downloads the template bundle of its own release through the website’s licence API. That keeps paid templates out of a public npm tarball, and it gives each release a second artifact that npm knows nothing about. Two rules follow: the bundle a customer gets must be exactly the one the release was tested with, and it must exist before anyone can install the release.

### Digest the content, not the compression

The bundle is built deterministically: layers sorted by id, files by path, keys in a fixed order, and nothing recorded from the file system except each file’s content and its executable bit. Its digest is the SHA-256 of the JSON inside the archive, not of the gzip bytes, because Node and Bun compress the same JSON to different bytes. When we measured it, the archives’ digests differed and the content’s did not. A digest of the compressed file identifies a compressor; it would break the first time a runtime upgraded its zlib, and a customer would be told that their download was corrupt.

### Pin at version time, verify before upload, upload before staging

The pin is written in the Version Packages pull request. The version script runs `changeset version`, then builds the new version’s bundle and adds its digest to a file of pins inside the CLI, so the reviewer sees the version bump and the pin side by side, and the release carries the digest in its own code. Pinning refuses to change a digest that is already pinned. Every CLI carries the pins of every earlier release too, because `update`, when it arrives, will regenerate the release a project was made from as the base of its merge.

At release time, the stage job rebuilds the bundle and fails unless its digest is the pinned one. Then it uploads the archive, with the digest as the object’s metadata, to the storage that the licence API reads, and reads every object back: its size, its content type, its metadata and the digest of its content. Only then does it stage anything on npm, because a published CLI must never ask for a bundle that is not there. The upload refuses any archive that is not the pinned bundle, so a re-run can never change what a release serves.

### Check twice, against two sources

The website answers a bundle request with a short-lived signed URL, valid for <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />, and with the bundle’s size and digest, which it reads from the stored object’s head without opening the archive:

```ts title="src/modules/license/license.api.ts"
const storedBundle = async (version: string): Promise<StoredBundle> => {
  const key = bundleObjectKey(version)
  const object = await env.BUNDLES.head(key)

  if (object === null) {
    return { error: { code: API_ERROR.VERSION_NOT_FOUND, version }, success: false }
  }

  const metadata = bundleMetadataSchema.safeParse(object.customMetadata)

  if (!metadata.success) {
    throw new Error(`${key} has no ${BUNDLE_METADATA.SHA256} digest in its custom metadata`, { cause: metadata.error })
  }

  return { bundle: { sha256: metadata.data[BUNDLE_METADATA.SHA256], size: object.size }, success: true }
}
```

An object without its digest is not served: the API answers `serviceUnavailable`, and the log names the object. The CLI then downloads the archive, reads no more than the announced size, and refuses it unless its size and digest match the API’s answer and the digest also matches the pin compiled into the release. A mismatch exits with code <RepositoryFact name="cliExitProtocol" /> and writes nothing; even a good download is written into the project directory all at once, so an interrupted run leaves nothing behind.

Why both checks? The API’s digest protects the download. The pin protects the release from its own server: whatever sits in storage under a version’s key, a published CLI runs only the templates its release was tested with. Each source checks the other, and neither is trusted alone. The website’s docs describe the endpoint and the rules for publishing bundles in full, in [CLI licence API](/docs/features/cli-licence-api#publishing-bundles).

### The general rule

Anything your CLI fetches at run time, whether templates, schemas, binaries or a list of plugins, is part of the release. Version it with the release, pin it by content in the code you publish, upload it before the package can be installed, and keep every version that a supported release can still ask for.

## Build once, then test what you ship

### Pack once, stage those bytes

The pack job runs the format, lint and type checks, the tests at full coverage and the smoke tests, and then `changeset pack` writes the tarballs and the publish plan into an artifact. The stage job downloads that artifact; it never builds. The bytes that npm stages are the bytes that job produced.

### A packer that leaked workspace syntax

0.1.0-beta.1 went to npm with `catalog:` specifiers in the `devDependencies` of all three packages, six entries in all, as the registry still shows. A Bun workspace writes shared versions as `catalog:`. Changesets 3 packs only with npm, pnpm or Yarn, and in a Bun workspace it fell back to `npm pack`, which copies those specifiers into the packed `package.json` unresolved. Nothing failed, because nobody installs a CLI’s dev dependencies. The same leak in `dependencies` would have broken every install of the release.

The root-cause fix carries a `bun patch` of Changesets that packs with `bun pm pack`, which writes the version each specifier resolves to and refuses to pack one it cannot resolve. The patch is the packing half of an open upstream pull request that adds Bun to Changesets, [changesets/changesets#2334](https://github.com/changesets/changesets/pull/2334), and it goes when a release includes that change. What keeps it fixed is a test: the smoke tests pack every published package with the release’s own command and fail on any `catalog:` or `workspace:` left in any dependency field. Test the tarball, not the workspace. Your package manager’s workspace features are invisible to a test that runs from source.

### Gate staging on every platform

Customers run the CLI under Node and Bun, on Linux, macOS and Windows. Pull requests run the built program on Linux only, to save minutes; the release run checks every platform, on the exact commit it is about to stage. Nine jobs build the packages and run the bins under Node 22.12.0, 24 and 26 on each system, and under Bun on each runner.

The nine jobs are one matrix, three systems by three Node versions, starting at the oldest Node the CLI supports. Two settings turn that matrix into a gate. The staging job lists both the pack job and the matrix under `needs` and has no `if:` of its own, so GitHub skips it unless every one of them succeeded; a condition such as `if: always()` on the staging job would quietly undo that. And the matrix sets `fail-fast: false`, so a failure on one leg does not cancel the others, and the run shows every platform that broke instead of only the first.

A gate you have never seen fail is a hope, not a gate. Before trusting this one, we ran the real release workflow on a temporary branch, from a commit equivalent to a merged Version Packages pull request, with one leg made to fail on purpose: Windows under Node 26. Every other job passed, and the staging job was skipped as soon as the last leg finished. The probe could not have published even if the gate had been wrong, because the environment the stage job needs deploys only from the release branches; afterwards, npm listed the same versions as before, and no tag or Release had appeared.

Moving the macOS and Windows runs from every merge to the release itself cut the billable minutes of a merge to `main` by a third to a half, as we measured it when we made the change, for a cost paid once per release. What the gate does not do is listed near the end of this post: it runs `--version` and `--help`, not a full project generation, and it builds on each runner instead of installing the staged tarball.

## Record a release only after it exists

### The unpublished 0.1.0-beta.3

Our first release workflow created the Git tags and GitHub Releases right after staging. The reason was that npm gives a workflow no event to trigger on when a maintainer approves a staged version. So the tags appeared when a version was staged, not when it was published. The release history shows what that meant, in UTC:

| Version      | Version pull request merged | GitHub Releases created | Served by npm      |
| ------------ | --------------------------- | ----------------------- | ------------------ |
| 0.1.0-beta.0 | 14 November, 06:17          | 14 November, 18:24      | 14 November, 18:28 |
| 0.1.0-beta.1 | 14 November, 18:38          | 14 November, 18:40      | 14 November, 23:08 |
| 0.1.0-beta.2 | 15 November, 22:52          | 15 November, 22:55      | 15 November, 23:32 |
| 0.1.0-beta.3 | 17 November, 14:23          | 17 November, 14:26      | Never              |
| 0.1.0-beta.4 | 20 November, 09:49          | 20 November, 09:51      | 20 November, 10:11 |
| 0.1.0-beta.5 | 20 November, 11:18          | 20 November, 11:45      | 20 November, 11:44 |

0.1.0-beta.3 was staged on 17 November and was still waiting for approval three days later, when the next beta, carrying all of its changes and one more, was cut and staged. The owner approved 0.1.0-beta.4. 0.1.0-beta.3 never reached npm, and `npm view saasyland versions` lists 0.1.0-beta.2 and then 0.1.0-beta.4. The repository, though, had three tags and three GitHub Releases for it, describing packages nobody could install. Even for the published betas, the Releases came first, by four minutes to four and a half hours. The workflow was right about everything except the one thing it could not know: whether, and when, a person would approve.

### Ask npm, then tag

We moved tags and Releases into a separate job that asks the registry first. For each published package, it checks three things: that the package’s `CHANGELOG.md` has a section for the checked-out version, which only a Version Packages pull request writes; that npm serves exactly that version, through a public `npm view` that needs no token; and whether the tag already exists. Only when every package passes the first two checks and a tag is missing does it run `changeset git-tag` through the Changesets action, which pushes the tags and creates a Release from each changelog entry. Otherwise it writes nothing, and its summary says why.

Both checks are deliberately plain. A version counts as served only when `npm view` prints exactly that version, so a missing version, a network error and an unexpected answer all count as not served, and nothing is tagged. A tag counts as present only when Git resolves its full ref, so a branch with the same name cannot pass for it. The release kit at the end of this post has a generic version of the check for a single package.

The job runs three ways: right after staging, where it usually finds the version still waiting; by hand, which the lead agent does as soon as the owner approves; and once a day as a fallback. Its runs on one branch share a concurrency group and queue instead of overlapping, so two runs never tag at once, and it fetches every tag first, so it creates only what is missing and can run any number of times.

0.1.0-beta.5 was the first release through it. Its release run’s records job ran at 11:25 UTC and found the version not yet served. npm served it at 11:44:37; the lead agent started the records workflow at 11:45:27, and the three Releases appeared at 11:45:51.

### A schedule is a safety net, not a step

The daily fallback taught us two things about GitHub’s `schedule` event. First, "Scheduled workflows run on the latest commit on the default branch", and a beta’s tags must point at a commit on `beta`. So the scheduled job tags nothing itself: it reads the branches from the release workflow’s own trigger and starts the records workflow on each of them with `workflow_dispatch`, so that each run tags its own branch. Second, the schedule is approximate. GitHub says the event "can be delayed during periods of high loads" and that "some queued jobs may be dropped". Ours is set for the early morning in UTC, and from 21 to 24 November it started roughly eight to eleven hours late. A scheduled job can catch what a person forgot. It should never be the step a release waits for.

### Label what never shipped

The tags and Releases of 0.1.0-beta.3 stay where they are: deleting them would erase the record of what was built and staged. Instead, each package’s changelog now says under its 0.1.0-beta.3 heading: "Not published to npm: this version was superseded by 0.1.0-beta.4 before it was approved, and every change below shipped in 0.1.0-beta.4." The three GitHub Releases carry "(not published)" in their titles, and the website’s [release notes](/docs/cli/releases) say the same. The policy also gained a rule: approve or reject a staged release before the next Version Packages pull request is merged.

## The empty changeset that blocked a release

[The first post in this series](/blog/ai-coding-agent-guardrails) tells this one briefly, as an agent satisfying a check by its letter. Here is the full sequence, because it shows a class of failure that is easy to miss: a release tool that decides, correctly by its own rules, that there is nothing to do.

### Three merges in 81 seconds

All of it happened on `beta` on 20 November, in UTC:

1. **11:17:12.** A pull request brought two commits from `main`. Its release run opened the Version Packages pull request for 0.1.0-beta.5.
2. **11:18:06.** A pull request that added the "Not published to npm" note to the three changelogs merged. A changelog edit counts as a change to the package, so the changeset check asked for a changeset, and the pull request added an empty one, exactly as the release policy prescribed for a change customers cannot notice.
3. **11:18:33.** The version pull request merged, 27 seconds later. It had been built before the changelog fix merged, so it had not consumed the empty changeset.
4. **11:19.** The release run on that merge commit selected its mode and skipped every other job. 0.1.0-beta.5 was versioned on `beta` and not staged, and every job was green.

Meanwhile, the release run of the changelog fix’s merge commit, queued behind the others, opened a second Version Packages pull request from a commit that was already history; it was closed unmerged.

### Why the mode was "none"

`changesets/action/select-mode` returns one of three modes: version, publish or none. This is the decision in its public source at v2.1.2, in this site’s formatting:

```ts
if (changesets.length > 0) {
  const hasNonEmptyChangesets = changesets.some((changeset) => changeset.releases.length > 0)
  if (hasNonEmptyChangesets) {
    return { mode: "version" }
  }
  return { mode: "none" }
}
```

If any changeset is pending and all of them are empty, the mode is `none`, and the publish plan, which would have found that 0.1.0-beta.5 was missing from npm, is never computed. On its own terms that is reasonable: an empty changeset means "release nothing". Combined with a version pull request merged before it was rebuilt, it meant a release that was cut and never shipped.

### The fix and the rules

A follow-up pull request removed the empty changeset five minutes later. The next run selected `publish`, staged 0.1.0-beta.5 at 11:25, and the owner approved it at 11:44. Our policy now says that empty changesets belong on `main` only, and that a change made directly on `beta` that customers cannot notice, such as a changelog correction, carries no changeset, with its failing changeset check as the one failure allowed.

Two rules carry over to any team:

- **Merge a version pull request only when it was built from the branch’s current head.** If anything merged after its last update, wait for the release workflow to rebuild it.
- **Treat "nothing to do" as a result to check.** A release run that selects no work while the version on the branch is missing from the registry has failed, even when every job is green.

We have the first rule in writing and not yet the second as a check. And our written rule about empty changesets covers the branch where it happened, while the mechanism does not depend on pre mode: the same race on `main` would leave the same empty changeset pending.

## CI for the pull request you release from

### GitHub does not run workflows for its own token’s pushes

The version job pushes the Version Packages branch with the workflow’s `GITHUB_TOKEN`, and GitHub’s docs say that "events triggered by the `GITHUB_TOKEN` will not create a new workflow run", with one exception that matters here: "`workflow_dispatch` and `repository_dispatch` events always create workflow runs." So the pull request we were about to release showed no checks at all; to get a run on one of them, an agent closed and reopened it by hand. The fix keeps the default token and starts CI itself. Right after Changesets opens or updates the version pull request, the same job looks up the pull request’s branch and dispatches the CI workflow on it with `gh workflow run`, which works because the CI workflow accepts `workflow_dispatch` as well as `pull_request`.

The job gains `actions: write` for that one call, and the check runs attach to the branch’s head commit, so they show on the pull request. A GitHub App token would also trigger CI, but it needs an app and another secret; this needs neither.

### Queue release runs, never replace them

GitHub Actions concurrency groups used to keep one pending run: "If another run entered the group, the pending run was canceled and replaced." For a release workflow that is wrong, because three quick pushes to `beta` would drop the middle one. Since May 2026, `queue: max` lets a group "queue multiple pending runs and process them sequentially", up to 100 of them, when `cancel-in-progress` is false.

A generic example, after GitHub’s concurrency documentation, for a release workflow that must never drop a run:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false
  queue: max
```

Our release workflow works this way, so every push to a release branch gets its own complete run, in order. The empty-changeset sequence shows the other side of that guarantee: a queued run decides from its own commit, even when that commit is already history by the time it runs. Queuing keeps every run; it does not make an old run’s decision current.

## Who holds which key

The agents run the release; the owner holds what cannot be undone.

| Task                                    | Agents                                                                   | Owner                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Changesets and the version pull request | Write them, review the notes and merge when the batch is complete        | Nothing                                                                            |
| Release workflows                       | Write the change and prove it, for example with a probe run              | Approves every change to the files that decide what reaches npm, with a quoted yes |
| Build, test, pack and stage             | Nothing: CI does it on the merge commit                                  | Nothing                                                                            |
| Approve or reject a staged version      | Hand over the exact stage ids                                            | Approves or rejects with two-factor authentication                                 |
| Tags and GitHub Releases                | Start the records workflow right after the approval                      | Nothing                                                                            |
| A new package name                      | Prepare it on `main` and write the exact steps                           | Publishes the placeholder and sets up its trusted publisher                        |
| A bad version                           | Write the deprecation message and the fix                                | Runs `npm deprecate` with two-factor authentication                                |
| Release notes and verification          | Install from npm in a clean directory, write the notes in every language | Reviews                                                                            |

The release workflow, the Changesets configuration and the package fields that decide what reaches npm are on the CLI repository’s human-review list, so every pull request that changes them, such as the one that changed how releases are recorded, quotes the owner’s written go-ahead. The same instruction file tells agents never to publish or run `npm trust`. And no agent holds an npm credential, because none exists: every package disallows publishing with tokens, and the only automated identity that can stage is the release workflow itself.

Verification does not end at the release. The website’s journey suite runs on the schedule <RepositoryFact name="journeySchedule" /> in UTC: it buys each tier in Polar’s sandbox on the preview deployment, then drives the published CLI, straight from npm, through activation, the machine limits, deactivation and the refund that ends the licence:

```ts title="e2e/journey/cli.ts"
const child = spawn("env", ["-i", ...variables, PACKAGE_MANAGER.NPM.exec, "--yes", CLI_PACKAGE_SPEC, ...inputs, "--json"], { cwd: home })
```

The principle is the one this post started from. Agents may do anything that is reversible, or that a later step will catch. A person holds the steps that are neither, through a factor the agents cannot hold.

## When a release is bad

A version on npm is permanent, so rollback means moving forward.

- **Deprecate, then ship a patch.** `npm deprecate` with a message that names the fix, for example "Breaks init on Windows. Use 1.4.1 or later.", run by the owner with two-factor authentication. The fix goes through the same pipeline as any release. A security fix or a fix for data loss is released at once, without waiting for its batch.
- **Never unpublish.** It breaks every project and script that pinned the version, and the version number can never be used again.
- **Reject what is only staged.** `npm stage reject <stage id>` removes a staged version without publishing it, again with two-factor authentication.
- **Mind the version you rejected.** A rejected version is still the version in the repository, and still missing from npm, so the next push without a pending changeset stages it again. Land the fix, with its changeset, before anything else.

## What we still do not have

In the spirit of the rest of the series, here is where our own release process is weak.

- **No provenance.** The repository is private, so the packages carry npm’s registry signature and no provenance attestation.
- **No stable channel yet.** `latest` is still the placeholder, and every command we publish names the <RepositoryFact name="cliReleaseChannel" /> tag. The first stable release has to switch the READMEs, the tests that check them and the website’s commands together.
- **A shallow cross-platform gate.** On macOS and Windows the release checks `--version` and `--help` under each runtime, not a full `init`, and it builds on each runner instead of installing the tarball that will be staged.
- **Approval reads the summary.** npm’s `npm stage download` fetches a staged tarball "for local inspection" without a second factor, so an approver could install and run the exact bytes before approving. We do not do that yet.
- **No alarm for "nothing to do".** A release run that selects no work while the branch’s version is missing from npm fails nothing.
- **A late safety net.** The scheduled records run starts hours after its time, so the lead agent starts it by hand after each approval.
- **One approver.** 0.1.0-beta.3 waited three days for approval and was superseded. A release that depends on one person’s second factor moves at that person’s pace.
- **No run against the live API before a release.** [The first post](/blog/ai-coding-agent-guardrails) describes the guardrail we want: the published CLI run against production in CI before each release. It needs a licence key as a CI secret, a human-review change that waits for the owner.

## A release kit you can copy

**A release checklist**, in order:

1. The batch is merged, and the last CI run on the release branch is green.
2. Every changeset reads as a note to a customer, and the bump is right.
3. The version pull request was rebuilt after the last merge, and its checks are green.
4. The docs the release needs are live, and any change to a contract the server reads is deployed on the server.
5. No staged release still waits for approval.
6. Merge the version pull request.
7. Pack once; run the built program on every system and runtime you support; stage only if all of it passed.
8. Upload and read back everything the CLI will download, and verify it against the pin, before staging.
9. Approve every package of the release with two-factor authentication, or reject it.
10. Create tags and Releases once the registry serves every package of the release.
11. Install from the registry in a clean directory and run the CLI.
12. Publish the release notes, and label anything that was staged and never published.

**A staging job**, a generic example written from npm’s documentation for a repository without Changesets, not the CLI’s own workflow. It needs no token and is safe to run again. It assumes a `pack` job that uploads the tarballs as an artifact named `tarballs`, an environment named `release`, and a trusted publisher on npmjs.com that names this workflow file, that environment and the stage-only permission. Every action in it is pinned to the commit of a release, with the tag after it, because a tag can move and a release job is the last place to run code you did not review:

```yaml
stage:
  needs: pack
  runs-on: ubuntu-latest
  environment: release
  permissions:
    contents: read
    id-token: write
  steps:
    - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
      with:
        node-version: 26
    - uses: actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2
      with:
        name: tarballs
    - name: Stage every tarball npm does not serve yet
      shell: bash
      run: |
        for tarball in *.tgz; do
          manifest=$(tar -xOzf "$tarball" package/package.json)
          name=$(jq -r .name <<< "$manifest")
          version=$(jq -r .version <<< "$manifest")
          if [ "$(npm view "$name@$version" version 2> /dev/null)" = "$version" ]; then
            echo "$name@$version is already on npm" >> "$GITHUB_STEP_SUMMARY"
          elif staged=$(npm stage publish "$tarball" --access public --tag latest --json); then
            echo "$name@$version staged as $(jq -r --arg name "$name" '.[$name].stageId' <<< "$staged")" >> "$GITHUB_STEP_SUMMARY"
          elif [ "$(jq -r '.error.code' <<< "$staged")" = E409 ]; then
            echo "$name@$version was staged by an earlier run" >> "$GITHUB_STEP_SUMMARY"
          else
            exit 1
          fi
        done
    - name: Keep npm's logs when staging fails
      if: failure()
      uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
      with:
        name: npm-logs
        path: ~/.npm/_logs/
        retention-days: 7
```

**A trusted publisher that may only stage**, set up once per package by a maintainer with two-factor authentication:

```sh
npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-stage-publish
```

**Tags only for what npm serves**, a generic example for a single package, safe to run any number of times, for example after each approval:

```sh
name=$(jq -r .name package.json)
version=$(jq -r .version package.json)
if [ "$(npm view "$name@$version" version 2> /dev/null)" != "$version" ]; then
  echo "npm does not serve $name@$version yet, so nothing is tagged"
  exit 0
fi
if git rev-parse -q --verify "refs/tags/v$version" > /dev/null; then
  exit 0
fi
git tag "v$version"
git push origin "v$version"
gh release create "v$version" --verify-tag --notes-file release-notes.md
```

**A download that is checked against the server and the pin** before anything reads it, a generic example in TypeScript for Node:

```ts
import { createHash } from "node:crypto"
import { gunzipSync } from "node:zlib"

const MAX_CONTENT_BYTES = 256 * 1024 * 1024

interface BundleAnswer {
  readonly sha256: string
  readonly size: number
}

export const verifiedContent = (archive: Buffer, answer: BundleAnswer, pinned: string): Buffer => {
  if (archive.length !== answer.size) {
    throw new Error(`Expected ${answer.size} bytes and received ${archive.length}`)
  }

  const content = gunzipSync(archive, { maxOutputLength: MAX_CONTENT_BYTES })
  const digest = createHash("sha256").update(content).digest("hex")

  if (digest !== answer.sha256 || digest !== pinned) {
    throw new Error("The download is not the bundle this release was tested with")
  }

  return content
}
```

**Release rules for your instruction file**, so agents prepare what the owner will approve:

```md
## Releases

- Never run npm publish, npm unpublish, npm stage approve or npm stage reject. CI stages releases, and a maintainer approves them with 2FA.
- Every change to a published package adds a changeset written for customers: what changes for them and what they have to do.
- Merge a version pull request only when it was built from the branch's current head, and never while a staged release awaits approval.
- After an approval, start the records workflow, install the release from npm in a clean directory and run it before announcing anything.
- Label a version that was staged and never published in its changelog and its GitHub Release. Never delete its tag.
```
