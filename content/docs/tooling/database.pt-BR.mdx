Os schemas ficam nos módulos das tabelas e são reunidos por `src/integrations/drizzle-orm/drizzle.schemas.ts`. As migrações são arquivos SQL com prefixo de timestamp em `src/integrations/drizzle-orm/migrations/`, versionados junto com a alteração do schema.

## Três bancos de dados [#three-databases]

Cada ambiente do Wrangler tem o próprio banco de dados D1, e nenhum script ou servidor alcança os dados de outro ambiente:

| Ambiente      | Banco de dados                               | Usado por                                       | Os dados dele                           |
| ------------- | -------------------------------------------- | ----------------------------------------------- | --------------------------------------- |
| `development` | `saasyland_local` local em `.wrangler/state` | `bun run dev` e os scripts `:local`             | Seus; `db:seed:local` o preenche        |
| `preview`     | `saasyland_com_preview` remoto               | `preview.saasyland.com` e os scripts `:preview` | Compras de teste com o sandbox da Polar |
| `production`  | `saasyland_com_production` remoto            | `saasyland.com` e os scripts `:production`      | Clientes                                |
| `test`        | `saasyland_test` local em `.wrangler/test`   | Playwright, o preview isolado e `db:reset:test` | `db:seed:test` o preenche               |

`bun run dev` nunca lê nem grava em um banco de dados remoto. Todo binding do ambiente `development` em `wrangler.jsonc` tem `remote: false`, o plugin Vite da Cloudflare roda com `remoteBindings: false` (`src/data/cloudflare.vite.ts`), e `src/__test__/wrangler.test.ts` falha quando um binding de desenvolvimento passa a ser remoto ou compartilha um banco de dados, um namespace ou um bucket com `preview` ou `production`. Os outros bindings são locais pelo mesmo motivo:

- `CACHE` (KV) guarda apenas caches que o Worker preenche de novo, a contagem de estrelas do GitHub e os descontos regionais do checkout, então um namespace local começa vazio e funciona de imediato.
- `MEDIA` e `BUNDLES` (R2) são os buckets locais `saasyland-local` e `saasyland-bundles-local`. As linhas que apontam para os arquivos deles, vídeos, materiais das aulas e pacotes de templates, ficam no D1, então um banco de dados local com buckets remotos mostraria os arquivos do preview para linhas que não existem e deixaria arquivos órfãos nos buckets do preview.
- O Better Auth guarda os usuários, as sessões, os tokens de verificação e os rate limits no D1, então o cadastro, o login e a administração funcionam localmente. Os e-mails continuam saindo pelo Resend com a chave de `.env.development`, e as chamadas à Polar vão para o sandbox indicado por `POLAR_SERVER`.

## Migrações [#migrations]

1. Altere `src/modules/<table>/<table>.schema.ts`.
2. Execute `bun run db:generate` e revise o SQL gerado.
3. Aplique a migração localmente com `bun run db:migrate:local` e execute os testes; o Vitest aplica todas as migrações ao seu banco de dados em memória.
4. Faça o deploy: os scripts de deploy e a CI a aplicam ao banco de dados de preview ou de produção antes que o novo Worker entre no ar.

```sh
bun run db:generate
bun run db:migrate:local
bun run db:migrate:test
```

Instalar dependências e fazer o build nunca migram um banco de dados.

O SQLite não impõe o tamanho de um tipo de coluna como `text(<length>)`, e o drizzle-kit o altera reconstruindo a tabela: uma tabela nova, cada linha copiada para ela e a antiga excluída. Por isso os limites são os que os formulários e as funções de servidor validam, e uma coluna mantém o tamanho com que foi criada. `user.email` e `newsletter_subscriber.email` continuam `text(<RepositoryFact name="declaredEmailColumnLength" />)` e `user.name` `text(<RepositoryFact name="declaredNameColumnLength" />)` por meio de `DECLARED_COLUMN_LENGTH` em `auth.constraints.ts`, enquanto um endereço pode ter <RepositoryFact name="emailMaxLength" /> caracteres (`EMAIL_MAX_LENGTH`, o limite de caminho da RFC 5321) e um nome <RepositoryFact name="nameMaxLength" /> (`NAME_MAX_LENGTH`). Uma tabela criada depois, como `withdrawal`, declara `EMAIL_MAX_LENGTH` e `NAME_MAX_LENGTH` desde o início, então nada precisa ser reconstruído. Uma migração gerada que contém ``CREATE TABLE `__new_`` reconstrói uma tabela; revise-a antes do commit.

| `bun run db:migrate:local`                                          | `development` local              | Aplica as migrações                                                                                             |
| `bun run db:migrations:local`                                       | `development` local              | Lista as migrações ainda não aplicadas; não altera nada                                                         |
| `bun run db:reset:local`                                            | `development` local              | Apaga `.wrangler/state/v3/d1` e depois aplica todas as migrações: um banco de dados vazio                       |
| `bun run db:seed:local`                                             | `development` local              | O administrador local, o conteúdo programático, licenças e um pedido; veja [O seed local](#the-local-seed)      |
| `bun run db:studio:local`                                           | `development` local              | Drizzle Studio no arquivo SQLite local                                                                          |
| `bun run admin:grant:local`                                         | `development` local              | Dá a uma conta verificada o papel de administrador; veja [O primeiro administrador](#the-first-admin)           |
| `bun run db:migrate:test`                                           | `test` local em `.wrangler/test` | Aplica as migrações                                                                                             |
| `bun run db:seed:test`                                              | `test` local                     | Contas de teste, uma licença, um vídeo, um curso com seus capítulos e aulas e um pacote de templates da CLI     |
| `bun run db:reset:test`                                             | `test` local                     | Apaga `.wrangler/test` e depois executa `db:migrate:test` e `db:seed:test`                                      |
| `bun run db:migrate:preview`, `bun run db:migrate:production`       | Remoto                           | Aplica as migrações                                                                                             |
| `bun run db:migrations:preview`, `bun run db:migrations:production` | Remoto                           | Lista as migrações ainda não aplicadas; não altera nada                                                         |
| `bun run db:studio:preview`, `bun run db:studio:production`         | Remoto                           | Drizzle Studio pela API HTTP do D1                                                                              |
| `bun run db:introspect:preview`, `bun run db:introspect:production` | Remoto                           | Introspecção do drizzle-kit pela API HTTP do D1                                                                 |

`deploy:preview`, `deploy:production` e o deploy na CI executam `db:migrate:preview` ou `db:migrate:production` antes de `wrangler deploy`. Nenhum deploy preenche um banco de dados remoto com seed.

## Drizzle Studio

`bun run db:studio:local` executa `scripts/studio-local.ts`. O Miniflare guarda o banco de dados local como um único arquivo SQLite em `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/`, com um nome derivado de um hash do ID do banco de dados em `wrangler.jsonc`; o script calcula esse nome do mesmo jeito que o Miniflare, falha com uma dica quando o arquivo ainda não existe e abre o Drizzle Studio nele com `src/integrations/drizzle-orm/drizzle.local.config.ts`, que lê o arquivo por meio de `@libsql/client`. O Studio e o servidor de desenvolvimento podem rodar ao mesmo tempo.

`bun run db:studio:preview` e `bun run db:studio:production` usam a API HTTP do D1 com `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` e `CLOUDFLARE_ACCESS_TOKEN` de `.env.preview` ou `.env.production`, por meio de `src/integrations/drizzle-orm/drizzle.config.ts`. Toda edição feita ali é uma edição nos dados reais desse ambiente.

## O seed local [#the-local-seed]

```sh
bun run db:reset:local
bun run db:seed:local
bun run dev
```

Pare o servidor de desenvolvimento antes de `db:reset:local`. `db:seed:local` (`scripts/seed-local.ts`) inicia os bindings locais do ambiente `development` com o `getPlatformProxy` do Wrangler, grava o que vem a seguir e pode ser executado de novo a qualquer momento; ele altera apenas o que for diferente:

- Um administrador, <RepositoryFact name="localAdminEmail" />, com o endereço de e-mail verificado. A senha dele é `LOCAL_ADMIN_PASSWORD` de `.env.development`, ou <RepositoryFact name="localAdminPassword" /> quando ela não está definida, e precisa seguir as regras do cadastro. Cada execução define a senha de novo. Use uma senha que só exista na sua máquina, nunca uma de produção: o seed grava apenas o banco de dados local.
- O conteúdo programático de `content/courses/saasy-land-courses.json`, importado com `planCourseImport` e `applyCourseImport` de `src/modules/course/course.transfer.ts`, o mesmo código de **Importar** na administração. As aulas dele ainda não têm vídeo, então aparecem como [em gravação](/docs/features/courses#being-recorded).
- As capas de `content/courses/covers/`, com o slug como nome, para os cursos que não têm nenhuma: cada tamanho vai para o bucket `MEDIA` local e o curso recebe sua chave, então o catálogo local fica igual ao de produção.
- As licenças, o pedido sem licença e o pacote de templates da CLI do seed de testes (`e2e/data/license.seed.ts`), para que o painel da administração e as páginas de licenças tenham dados com formato real. As contas de cliente deles usam a senha <RepositoryFact name="testPassword" />.

Faça login em http://localhost:3000/auth/sign-in com o administrador e abra `/admin/courses` para ver os cursos.

## Dados dos cursos em cada ambiente [#course-data-in-each-environment]

- Local: `bun run db:seed:local` importa o conteúdo programático.
- Produção: um administrador importa `content/courses/saasy-land-courses.json` na administração. Faça login como administrador, abra **Conteúdo → Cursos**, escolha **Importar**, selecione o arquivo, execute **Verificar arquivo**, leia o plano e depois clique em **Importar**. Importar o mesmo arquivo de novo não altera nada. Veja [Importar e exportar](/docs/features/courses#import-and-export).
- Preview: `bun run courses:sync:preview` copia os cursos publicados da produção, então o preview mostra o mesmo catálogo que a produção.

### Copiar os cursos para o preview [#copying-the-courses-to-preview]

```sh
bunx wrangler login
bun run courses:sync:preview
```

`scripts/sync-courses.ts` acessa o D1 como `admin:grant:*`, por `wrangler d1 execute --remote` e pelo módulo compartilhado `scripts/d1-execute.ts`. Para a produção ele envia só instruções `SELECT`, e grava no preview em uma única execução com `--file`. Ele copia, linha por linha, com os ids e os timestamps:

- cada curso publicado, com seus capítulos, suas aulas e os anexos de link delas; uma linha que o preview já tem é atualizada pelo id, então uma segunda execução não muda nada que não tenha mudado na produção;
- as linhas de `video` que essas aulas usam, como placeholders. Os arquivos de um vídeo ficam no bucket `MEDIA` da produção e não são copiados, então no preview as aulas dele aparecem [em gravação](/docs/features/courses#being-recorded) em vez de falhar ao reproduzir. Uma linha de `video` que o preview já tem mantém sua flag de placeholder.

Nos cursos que copia, ele exclui os capítulos, as aulas e os anexos de link que a produção não tem mais, junto com o progresso do preview nessas aulas, e exclui um curso do preview que a produção não publica mais. Ele não copia anexos de arquivo, cujos arquivos ficam no bucket da produção, nem nada fora dessas tabelas: nenhum usuário, sessão, licença, pedido, assinatura ou progresso. Uma aula que você apontar para outro vídeo no editor de aulas do preview volta a apontar para o vídeo da produção depois da próxima execução.

Ele deixa `course.cover` fora da cópia: os arquivos de uma capa estão no bucket `MEDIA` de produção, então um curso novo no preview não tem capa, e um curso que o preview já tem mantém a capa enviada lá.

Ele para antes de gravar quando um curso do preview tem o slug de um curso da produção com outro id, como um importado do arquivo do conteúdo programático; exclua esse curso no admin do preview e execute de novo. Ele mostra o que criou, atualizou e removeu em cada tabela, depois conta as linhas no preview e falha se forem diferentes das da produção.

## Descontos e países de cobrança de pedidos antigos [#discounts-and-billing-countries-of-older-orders]

A migração `20261122143452_familiar_tusk.sql` adicionou o desconto e o país de cobrança à cópia `order` ([Pagamentos](/docs/features/payments#orders-and-subscriptions-in-d1)). Os novos webhooks os preenchem, e um pedido copiado antes da migração tem `discount_amount` vazio até a Polar enviá-lo de novo. Para preencher todos esses pedidos de uma vez:

```sh
bunx wrangler login
bun run orders:backfill:preview
bun run orders:backfill:production
```

`scripts/backfill-order-terms.ts` lê `POLAR_ACCESS_TOKEN` e `POLAR_SERVER` de `.env.<environment>`, lista com `wrangler d1 execute` os pedidos cujo `discount_amount` está vazio (remoto para preview e produção, local para `orders:backfill:local`) e lê cada um da Polar com `polar.orders.get`, um de cada vez, esperando o tempo que a Polar pedir quando ela responde 429. Ele grava todos os pedidos em uma única execução com `--file`, cada `UPDATE` limitado ao seu ID e a um `discount_amount` vazio, então nunca sobrescreve uma cópia que um webhook preencheu nesse meio-tempo e uma segunda execução não muda nada. Ele mostra quantos pedidos copiou e termina com erro enquanto restar algum, como um pedido que a Polar não retorna mais. Aplique a migração primeiro.

## O primeiro administrador [#the-first-admin]

A aplicação não tem nenhum endpoint, seed ou variável que conceda o papel `admin`. No preview e na produção, o primeiro administrador é criado com um script, e essa é a única forma:

```sh
bunx wrangler login
bun run admin:grant:production you@example.com
```

1. Cadastre-se no site com o endereço e abra o link do e-mail de verificação.
2. Faça login no Wrangler com uma conta da Cloudflare que possa gravar no banco de dados D1 do ambiente.
3. Execute `bun run admin:grant:preview <email>` ou `bun run admin:grant:production <email>`.

`scripts/grant-admin.ts` lê a conta com `wrangler d1 execute --remote`, a exibe e recusa um endereço sem conta, uma conta cujo e-mail não foi verificado e uma conta bloqueada. Em seguida, define `role` como `admin` nessa única linha, lê a conta de novo e a exibe. Uma conta que já é administradora fica como está.

Isso é seguro por três motivos:

- Só quem pode gravar no banco de dados D1 dessa conta da Cloudflare consegue executá-lo, com o próprio `wrangler login`. Essa pessoa já poderia alterar qualquer linha no painel da Cloudflare; o script não abre nenhum acesso novo.
- Ele altera uma coluna de uma conta que provou ser dona do próprio endereço de e-mail.
- A aplicação aplica os papéis no servidor: `requireAdmin` protege `/admin`, e toda função de servidor da administração verifica a sua permissão com `authorized(...)` em `auth.middleware.ts`. Veja [Papéis e permissões](/docs/guides/roles-and-permissions).

Os administradores seguintes são criados por um administrador existente em **Administração → Gerenciamento de usuários**: abra o usuário e escolha **Alterar função**. `bun run admin:grant:local <email>` faz o mesmo para uma conta com que você se cadastrou localmente.
