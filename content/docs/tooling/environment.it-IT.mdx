`wrangler.jsonc` definisce quattro ambienti. `CLOUDFLARE_ENV` ne seleziona uno per il server di sviluppo e per le build, e ciascuno legge i secret dal proprio file di ambiente:

| Ambiente      | Selezionato da                              | Binding                                 | Secret da          |
| ------------- | ------------------------------------------- | --------------------------------------- | ------------------ |
| `development` | `bun run dev`                               | D1, KV e R2 locali in `.wrangler/state` | `.env.development` |
| `preview`     | `build:preview`, `deploy:preview`           | D1, KV e R2 di preview                  | `.env.preview`     |
| `production`  | `build:production`, `deploy:production`     | D1, KV e R2 di produzione               | `.env.production`  |
| `test`        | `build:test`, `start:test`, `db:reset:test` | D1, KV e R2 locali in `.wrangler/test`  | `.env.test`        |

`.env.development`, `.env.preview` e `.env.production` sono ignorati da Git; `.env.example` ne elenca le chiavi. `.env.test` è versionato e contiene solo valori fittizi. Gli script di deploy caricano solo le chiavi elencate in `secrets.required` dell'ambiente, lette dal file corrispondente.

## Secret

Ogni ambiente elenca i propri secret in `secrets.required`: le chiavi di Better Auth, OAuth, Resend e Polar, più `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` e `CLOUDFLARE_ACCESS_TOKEN` per gli strumenti di Drizzle (l'ambiente `test` omette queste tre). Vedi [Variabili d'ambiente](/docs/getting-started/environment-variables) per ogni chiave.

`AFFONSO_PROGRAM_ID`, l'ID pubblico del programma Affonso che serve al tracciamento dei referral degli affiliati, è una variabile del Worker sotto `vars`, non un secret, quindi non compare in `.env.example` né in `secrets.required`. Impostalo solo per l'ambiente che riceve pagamenti reali; `production` imposta l'ID di programma di SaaSy Land e `test` un ID fittizio per i test nel browser. Il tracciamento funziona solo quando il Worker ha l'ID e il programma è aperto: oggi `AFFILIATE_PROGRAM` vale <RepositoryFact name="affiliateProgram" /> ([Aprire il programma](/docs/features/affiliates#opening-the-programme)).

Il codice server legge i secret con `import { env } from "cloudflare:workers"`. Nulla usa una variabile `VITE_`, e nessuna di esse può contenere un secret, perché Vite le espone al browser. `scripts/verify-build.ts` fa fallire la build quando un asset client importa `cloudflare:workers`. Il dominio canonico proviene da `APP_DOMAIN` in `src/presentation/branding/index.ts`, non da una variabile d'ambiente.

## Binding

| Binding   | Tipo          | Utilizzo                                                  |
| --------- | ------------- | --------------------------------------------------------- |
| `DB`      | D1            | Database dell'applicazione, sessioni e rate limit         |
| `CACHE`   | KV            | Conteggio delle stelle GitHub                             |
| `MEDIA`   | R2            | File video, serviti tramite `/media/`                     |
| `BUNDLES` | R2            | Bundle di template della CLI, serviti tramite `/bundles/` |
| `ASSETS`  | Asset statici | Pagine prerenderizzate, font e file pubblici              |

Lo sviluppo usa solo binding locali, quindi `bun run dev` non tocca mai i dati di preview o di produzione; [Database](/docs/tooling/database#three-databases) spiega perché ogni binding è locale. Esegui `bun run cf-typegen` dopo aver modificato i binding per rigenerare `src/types/worker-configuration.d.ts`.

## Test

Vitest carica `.env.test` tramite `test.env` e risolve `cloudflare:workers` in `src/platform/testing/mocks/cloudflare.ts`, che fornisce D1, KV e un bucket per ogni binding R2, tutti in memoria; `src/platform/testing/mocks/cache.ts` fa da stub della cache di Workers. Playwright usa l'ambiente `test` e il suo entry point `src/platform/testing/worker.ts`. Nessuno dei due ha bisogno di credenziali reali.
