Los flujos de trabajo se encuentran en `.github/workflows/`. Los flujos de trabajo de la aplicación (`ci.yml`, `deploy.yml`, `preview.yml`, `journey.yml`, `updates.yml`, `e2e-reusable.yml` y `deploy-reusable.yml`) configuran la cadena de herramientas con la acción compuesta `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ con la versión de Node de `.nvmrc` y la caché de instalación de Bun, que `setup-vp` restaura una sola vez, `bun install --frozen-lockfile --ignore-scripts` y `bun run typegen`. `remotion.yml`, en cambio, configura Node desde `.nvmrc` y npm.

| Flujo de trabajo      | Disparador                                                                                | Jobs                                                                                                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests, grupos de la cola de fusión y llamadas desde `deploy.yml`                  | Comprobaciones, tests con cobertura en shards paralelos, comprobación de tipos sin cada funcionalidad opcional, E2E en Chromium y en WebKit y la subida del Worker de preview |
| `deploy.yml`          | Pushes a `main`                                                                           | Las comprobaciones de `ci.yml`, salvo que ya las haya ejecutado la cola de fusión, y después preview, producción y la publicación de la versión                               |
| `preview.yml`         | Manual                                                                                    | Despliega en la preview compartida una rama cuyas comprobaciones se han superado                                                                                              |
| `e2e-full.yml`        | Pushes a `main`, la programación <RepositoryFact name="e2eFullSchedule" /> en UTC, manual | WebKit en cada push, como en cada pull request; Chromium y WebKit en las ejecuciones programadas y manuales                                                                   |
| `journey.yml`         | La programación <RepositoryFact name="journeySchedule" /> en UTC, manual                  | La [suite del recorrido del cliente](#journey-suite) contra la preview compartida, en el sandbox de Polar                                                                     |
| `updates.yml`         | La programación <RepositoryFact name="updatesSchedule" /> en UTC, manual                  | Abre, actualiza o cierra la [issue de actualizaciones](#updates)                                                                                                              |
| `e2e-reusable.yml`    | Invocado por los flujos de trabajo anteriores                                             | Una sola compilación de pruebas, un proyecto de Playwright en shards paralelos y una sola comprobación para ambos                                                             |
| `deploy-reusable.yml` | Invocado por `ci.yml`, `deploy.yml` y `preview.yml`                                       | Compilación y después migraciones de D1 y `wrangler deploy`, o `wrangler versions upload`                                                                                     |
| `remotion.yml`        | Cambios en `remotion/` o en los archivos del sitio web que importa                        | Comprueba y empaqueta con npm el proyecto de vídeo de la página de inicio                                                                                                     |

`remotion.yml` se ejecuta con las mismas rutas en las pull requests y en los pushes: `remotion/`, el propio flujo de trabajo y los archivos del sitio web que importa `remotion/src`, directamente o a través de otros archivos del sitio web. `src/__test__/workflows.test.ts` sigue esas importaciones y falla cuando un archivo al que llegan no coincide con ninguna de las rutas, o una ruta no coincide con ninguno de los archivos.

Los checkouts de `e2e-reusable.yml`, cuya compilación renderiza el registro de cambios y cuyo `content.spec.ts` lo lee, de `deploy-reusable.yml`, que compila el sitio, y del job `release` descargan todos los commits sin sus árboles (`fetch-depth: 0` y `filter: tree:0`): el [registro de cambios](/docs/project/changelog) fecha cada entrada por el commit que la llevó a `main`. Frente a un clon superficial solo se añaden los propios commits; con un clon superficial la compilación fallaría en lugar de fechar mal las entradas. `src/__test__/workflows.test.ts` falla cuando uno de esos checkouts deja de descargar el historial.

Cada action de otro repositorio, incluidas las de `actions/*`, está fijada al SHA completo del commit de una versión, con la etiqueta de la versión en un comentario detrás: `uses: <owner>/<repo>@<commit> # <tag>`. Así, un flujo de trabajo ejecuta exactamente el código de esa versión aunque su etiqueta se mueva después. `src/__test__/workflows.test.ts` falla cuando un `uses:` de `.github/workflows/` o `.github/actions/` nombra una etiqueta o una rama en lugar de un commit, no lleva la etiqueta de la versión detrás del commit o fija dos versiones de un mismo repositorio. `bun run deps:update` lleva cada action a su versión más reciente y reescribe juntos el commit y la etiqueta ([Dependencias](/docs/conventions/dependencies#upgrading)), de modo que las actions se actualizan en la misma rama que los paquetes.

## Comprobaciones [#checks]

Los jobs `check`, `test` y `features` de `ci.yml` sostienen la comprobación obligatoria `Format, lint, types, i18n, tests`, que informa el job `verify`:

| Job                                                  | Ejecuta                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                              | `bun run check`: tablas de nombres de clase, comprobaciones de i18n y de contenido, el [inventario de flujos](/docs/tooling/test-coverage#flow-coverage), las [skills para agentes](/docs/tooling/agent-skills#drift-checks), formato, lint y tipos                                                       |
| `test`                                               | Un job por shard, <RepositoryFact name="vitestShards" /> en paralelo: `bun run test:coverage --shard=<n>/<total>` con el reporter blob de Vitest, y después sube el informe blob del shard con su cobertura                                                                                               |
| `verify`, llamado `Format, lint, types, i18n, tests` | Cuando todos los shards han pasado, descarga los informes blob y ejecuta `bun run test:coverage --merge-reports`, que fusiona la cobertura y aplica los umbrales, y después sube el informe de cobertura; falla salvo que `check`, cada shard, la fusión y cada escenario del job `features` hayan pasado |

Un shard no comprueba ningún umbral, porque solo mide el código que alcanzan sus propios tests; los umbrales de `vite.config.ts` se aplican una vez, a la cobertura fusionada de todos los shards, igual que en un `bun run test:coverage` local. De estos jobs, `verify` es la única comprobación que exigen las reglas de la rama, así que añadir o quitar un shard o un escenario no cambia el nombre de ninguna comprobación obligatoria.

El job `features` ejecuta `bun run check:features <scenario>` una vez por cada escenario de `scripts/features.ts`, en paralelo. Borra las funcionalidades del escenario, poda lo que los archivos que se quedan nombran de ellas, formatea los archivos podados, comprueba los tipos del resto y revisa sus traducciones ([Pruebas](/docs/conventions/testing#tests-follow-the-features)). Un escenario con una referencia que no se puede podar, un error de tipos o un error de traducción hace fallar su job y, con él, la comprobación obligatoria `Format, lint, types, i18n, tests`.

Después, el job `check` ejecuta `bun run deps:audit`, el [análisis de dependencias](/docs/conventions/dependencies#security-advisories): `scripts/audit-dependencies.ts` ejecuta `bun audit` sobre las dependencias de producción y falla ante un aviso de gravedad <RepositoryFact name="auditBlockingSeverities" /> que no cubra ninguna excepción vigente. Así, un pull request no puede introducir una dependencia así, y un aviso nuevo contra una que ya está en `main` detiene el siguiente pull request hasta que se corrija o se registre una excepción. El análisis consulta el registro de npm, así que una caída del registro hace fallar el job; vuelve a ejecutarlo.

El job `sbom`, llamado `Software bill of materials`, ejecuta `bun run deps:sbom` en cada ejecución y sube `sbom.cdx.json` como el artefacto `sbom`: el SBOM CycloneDX de las dependencias de producción, con la versión y la URL de paquete de cada una y el grafo de dependencias. cdxgen lo escribe a partir de `bun.lock` y omite los paquetes que solo necesitan las devDependencies, y `scripts/verify-sbom.ts` hace fallar el job cuando al SBOM le falta una dependencia de `package.json`. El SBOM de un commit de `main` es el artefacto de la ejecución del grupo de fusión que lo probó. cdxgen se ejecuta con `bunx` en la versión exacta del script `deps:sbom` en lugar de como devDependency, porque sus binarios opcionales de análisis añadirían cientos de megabytes a cada instalación; `readDependencies` de `scripts/dependencies.ts` lee esa versión del script, de modo que la [issue de actualizaciones](#updates) muestra un cdxgen más reciente como paquete fijado. El job no es una comprobación obligatoria.

Los jobs `e2e` y `e2e-webkit` invocan `e2e-reusable.yml`, el primero con `browser: chromium` y el segundo con `browser: webkit`. Cada llamada compila una sola vez y ejecuta la suite en su navegador en <RepositoryFact name="e2eShards" /> runners en paralelo:

| Job                                           | Ejecuta                                                                                                                                                                                                                                                                                   |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                       | `db:reset:test` y `build:test`, y después sube `dist`, el `.wrangler/deploy` que apunta a la configuración de su Worker y el `.wrangler/test` sembrado como un solo artefacto                                                                                                             |
| `shard`                                       | Un job por shard, que arranca junto a la compilación: quita el origen de paquetes de Microsoft del runner, que ningún paso usa, instala el navegador, espera a que se suba la compilación, la descarga y ejecuta `bunx playwright test e2e/specs --project=<browser> --shard=<n>/<total>` |
| `report`, llamado `Build and E2E (<browser>)` | Falla salvo que la compilación y todos los shards se hayan superado; cuando un shard ha fallado, combina los informes blob de los shards en un solo informe HTML y lo sube                                                                                                                |

Los shards no esperan a que termine todo el job `build` (`needs`): arrancan con él y preparan la cadena de herramientas y el navegador mientras compila. Después, `scripts/download-artifact.ts` pregunta a la API de GitHub cada pocos segundos por el job `build` de la ejecución, hasta que su paso `Upload the test build` ha terminado bien. Que el paso haya terminado bien no significa que GitHub ya liste su artefacto, y una descarga en ese intervalo falla con `Artifact not found`, así que el script pregunta después por los artefactos de la ejecución hasta que GitHub lista `test-worker-<browser>` subido desde que empezó la compilación, y después descarga él mismo ese artefacto y lo comprueba con el digest SHA-256 que GitHub registró. Un artefacto listado todavía puede responder `Not Found` durante un momento, así que el script vuelve a preguntar hasta que GitHub sirve el archivo entero, y ningún otro paso lo pide entretanto. Envía el ETag de la respuesta anterior, y GitHub no descuenta una respuesta sin cambios del límite de peticiones del token. Un paso de la compilación que falla, o una compilación que termina sin subir nada, hace fallar todos los shards en pocos segundos, con el paso que falló y un enlace a la compilación, y un shard que espera más allá del límite del script falla con un error que dice si falta el paso, el listado o la descarga. Leer los jobs y los artefactos de la ejecución requiere `actions: read`, que solo pide el job `shard`: `ci.yml`, `e2e-full.yml` y el job `checks` de `deploy.yml` se lo conceden a los flujos de trabajo que invocan, y todos los demás jobs se quedan con `contents: read`.

Los reintentos y los workers propios de Playwright se mantienen como los describe [Playwright](/docs/tooling/playwright#configuration), en cada shard. El job `report` de cada navegador es la única comprobación de ese navegador que exigen las reglas de la rama, así que añadir o quitar un shard no cambia el nombre de ninguna comprobación obligatoria. La compilación también empaqueta la lista de etiquetas de release que leyó, y cada shard borra cualquier etiqueta creada desde entonces: `content.spec.ts` lee las etiquetas de release de Git, y una release etiquetada mientras los shards esperan le haría esperar un changelog que la compilación nunca generó.

El job `upload`, llamado `Worker upload`, invoca `deploy-reusable.yml` con `upload: true`: compila el Worker de preview exactamente como lo hace un despliegue y ejecuta `wrangler versions upload`, que lo envía al Worker `saasyland-preview` como una nueva versión sin desplegarla. Cloudflare comprueba la subida igual que comprueba un despliegue (el límite de tamaño, el tiempo de arranque, los bindings y los secretos que nombra `secrets.required`), así que un Worker que supera esta comprobación se puede desplegar, mientras `preview.saasyland.com` sigue sirviendo la versión desplegada antes. El job no aplica ninguna migración ni registra ningún despliegue de GitHub (`deployment: false`), y se ejecuta en paralelo con las subidas de otras pull requests. La versión de una pull request recibe el alias `pr-<number>`, que da nombre a la versión en el panel de Cloudflare; el resumen del job muestra el ID y el tamaño de la versión, y su URL cuando las Version URLs están activadas para el Worker, que hoy no lo están para `saasyland-preview`. Las pull requests desde forks y de Dependabot no pueden leer las credenciales de Cloudflare y se saltan el job; la cola de fusión, que sí puede, sube su compilación antes de que se fusionen.

En una pull request, `bun run check` también falla hasta que la pull request añade su [entrada del registro de cambios](/docs/conventions/git-workflow#changelog-entries), y en la cola de fusión hasta que está la entrada de la pull request en cola. La compilación de los jobs `e2e` y `upload`, y la de los jobs de despliegue, falla mientras el registro de cambios fuera a mostrar en **Sin publicar** una entrada que no sea la de la propia pull request, y en la cola de fusión y en `main` mientras fuera a mostrar cualquiera.

## Cola de fusión [#merge-queue]

El ruleset que protege `main` exige `Format, lint, types, i18n, tests`, `Build and E2E / Build and E2E (chromium)`, `Build and E2E / Build and E2E (webkit)` y `Worker upload / Upload preview`, y solo fusiona pull requests a través de la cola de fusión de GitHub, que aplica squash a cada una. `bun scripts/enqueue-pr.ts <number>` pone una pull request en la cola ([Git y pull requests](/docs/conventions/git-workflow#merging)). Para cada pull request de la cola, GitHub escribe el commit squash en una rama llamada `gh-readonly-queue/main/pr-<number>-<commit>`, sobre `main` y sobre las pull requests que van por delante, y ejecuta en ella `ci.yml` para el evento `merge_group`. Cuando cada pull request de un grupo ha pasado, GitHub mueve `main` al último commit del grupo, el mismo commit que probó la cola, de modo que un solo push lleva a `main` cada pull request del grupo como su propio commit squash. Una pull request que falla sale de la cola, y las que van detrás se vuelven a probar sin ella.

El ruleset también incluye `copilot_code_review` con `review_on_push: true`, pero, a 22 de noviembre de 2026, GitHub Copilot no ha revisado ningún pull request desde #70, así que los pull requests no reciben ninguna revisión automática. Una revisión sería solo orientativa: el ruleset no exige ninguna revisión aprobatoria ni que se resuelva ningún hilo de revisión, así que un pull request solo espera a los cuatro checks de arriba.

`ci.yml` cancela la ejecución de una pull request cuando un commit más reciente la sustituye, pero nunca una ejecución de la cola, cuyas ramas tienen cada una su propia ref. El control del registro de cambios trata la rama de la cola como `main`: cada pull request del grupo ya es un commit squash cuyo asunto termina con su número, así que ninguna entrada puede quedar sin publicar, y la entrada de la propia pull request en cola tiene que existir.

## Despliegues

`deploy.yml` despliega cada push a `main`, primero en la preview compartida y después en producción, una vez que el commit ha superado todas las comprobaciones que exige `main`. Su primer job, `tested`, ejecuta `scripts/tested-commit.ts`, que lee esas comprobaciones del ruleset a través de la API de GitHub y busca una ejecución correcta de cada una en el commit recibido. Un commit que ha llegado a través de la cola de fusión las tiene, porque la cola probó ese mismo commit, así que `deploy.yml` lo despliega sin volver a ejecutar las comprobaciones; un commit que ha llegado a `main` de cualquier otra forma ejecuta primero las comprobaciones de `ci.yml`.

| Evento                            | Destino                          | Entorno de GitHub                | URL                                                  |
| --------------------------------- | -------------------------------- | -------------------------------- | ---------------------------------------------------- |
| Push a `main`                     | `preview` y después `production` | `Preview` y después `Production` | https://preview.saasyland.com, https://saasyland.com |
| Ejecución manual de `preview.yml` | `preview`                        | `Preview`                        | https://preview.saasyland.com                        |

`deploy-reusable.yml` asigna a cada entorno de GitHub su URL, y `src/__test__/workflows.test.ts` falla cuando una no coincide con su host en `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). La preview es compartida: cada despliegue sustituye al anterior y usa la misma base de datos D1, el mismo espacio de nombres de KV y los mismos buckets de R2 de preview. En ella se ejecuta `main`, de modo que la [suite del recorrido del cliente](/docs/tooling/playwright#journey-suite), los webhooks del sandbox de Polar y el inicio de sesión en `preview.saasyland.com`, el único host de preview en el que confía Better Auth, se encuentran con el código que producción está a punto de ejecutar, y cada migración llega a la base de datos de preview antes que a producción. Para probar allí una rama antes de que se fusione, ejecuta `gh workflow run preview.yml --ref <branch>`: despliega la rama, migraciones incluidas, solo cuando su commit ha superado las comprobaciones que exige `main`, y el siguiente push a `main` vuelve a dejar `main` en ella.

`deploy-reusable.yml` comprueba que existan los secretos `CLOUDFLARE_API_TOKEN` y `CLOUDFLARE_ACCOUNT_ID`, ejecuta `scripts/verify-bindings.ts`, compila con los valores ficticios de `.env.test`, elimina el `dist/server/.dev.vars` generado, aplica `db:migrate:<target>` y ejecuta `vp exec wrangler deploy --config dist/server/wrangler.json` o, con `upload: true`, ejecuta `vp exec wrangler versions upload` en lugar de los dos últimos pasos. No ejecuta `scripts/verify-deployment.ts`, la comprobación del sitio desplegado de los scripts `deploy:<target>`, porque la protección contra bots de Cloudflare responde con 403 a las peticiones de los runners de CI. Tampoco ejecuta `scripts/run-deploy-checks.ts`, así que la CI no ejecuta ninguna de las comprobaciones de despliegue, es decir, de los scripts `<name>:verify:<environment>` de `package.json`: en la CI no hay ningún `.env.<target>` y los entornos de GitHub solo guardan las credenciales de Cloudflare, además de los ajustes del sandbox de la [suite del recorrido del cliente](#journey-suite) en `Preview`. Hoy son `auth:verify`, de la funcionalidad de autenticación, y `polar:verify`, de la funcionalidad de Polar; ejecuta en local `bun run auth:verify:<target>` después de cambiar un cliente OAuth y `bun run polar:verify:<target>` después de cada cambio en Polar ([Configuración de Polar](/docs/getting-started/polar-setup)). No se sube ningún archivo de secretos: el Worker conserva los secretos de ejecución ya configurados en Cloudflare. Los despliegues al mismo destino se ponen en cola en lugar de cancelarse entre sí, y las subidas se ejecutan en paralelo. Un nuevo commit en una pull request cancela la ejecución de `ci.yml` del commit anterior, que nadie va a fusionar, mientras que las ejecuciones de la cola de fusión nunca se cancelan entre sí y las de `deploy.yml` y `e2e-full.yml` en `main` se ponen en cola (`concurrency` con `queue: max`), así que cada push a `main` se despliega.

## Suite del recorrido del cliente [#journey-suite]

`journey.yml` ejecuta `bun run test:journey`, la [suite del recorrido del cliente](/docs/tooling/playwright#journey-suite), contra `https://preview.saasyland.com` según la programación <RepositoryFact name="journeySchedule" /> en UTC y cuando alguien lo lanza a mano:

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` vale `all`, `core`, `complete`, `agency` o `upgrade`; cualquier valor distinto de `all` ejecuta solo la prueba con esa etiqueta. El job lee estos secretos del entorno `Preview` de GitHub sin registrar un despliegue (`deployment: false`): `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` y `RESEND_API_KEY`. Fija `POLAR_SERVER` en `sandbox`, el único valor que acepta la suite, y la suite crea su cliente de Polar para el sandbox, así que el flujo de trabajo no puede llegar al Polar de producción. Las ejecuciones se ponen en cola y nunca se cancelan entre sí, porque una ejecución cancelada dejaría sus pedidos pagados. El job escribe el resultado y la duración de cada prueba, y el error de cada prueba fallida, en el resumen de la ejecución, y sube el informe HTML, `playwright-report/journey.json` y las trazas, los vídeos y los directorios de máquina de las pruebas fallidas como el artefacto `journey-report`.

El flujo de trabajo no se ejecuta después de cada despliegue de `main`. Cada ejecución registra una cuenta por prueba en preview, paga y reembolsa sus pedidos en el sandbox de Polar y envía sus correos de verificación y sus confirmaciones de compra a través de la cuenta de Resend que preview comparte con producción. `main` se despliega muchas veces en un día con mucha actividad, así que una ejecución tras cada despliegue multiplicaría esos correos frente a los límites de envío de los que dependen los correos de producción, y no frenaría nada: producción se despliega justo después de preview, encuentre lo que encuentre el recorrido. Cada ejecución cubre la compra completa: el registro con la verificación del correo, un pago en el sandbox por cada nivel, la clave que emite Polar, la CLI publicada en los dispositivos del nivel, la mejora de Core a Complete y los reembolsos. Todavía no está en verde: ninguna ejecución ha salido bien, porque sus secretos no están configurados, así que de momento no comprueba ninguna compra. Lánzala a mano después de un cambio en los pagos, las licencias o la API de licencias de la CLI, y después de `gh workflow run preview.yml --ref <branch>` para probar una rama antes de fusionarla.

## Actualizaciones [#updates]

`updates.yml` busca actualizaciones de dependencias y de skills para agentes según la programación <RepositoryFact name="updatesSchedule" /> en UTC y cuando se inicia a mano. Su primer paso, `bun scripts/report-updates.ts find`, pide al registro de npm la versión más reciente de cada dependencia directa y ejecuta `bun run skills:update` en el checkout del runner, del que no se hace ningún commit, para ver qué skills cambiaron en el origen. Su segundo paso, `bun scripts/report-updates.ts issue`, mantiene una sola issue, <RepositoryFact name="updatesIssueTitle" />: la abre cuando hay actualizaciones, la reescribe en las ejecuciones siguientes y la cierra cuando todo está al día. La issue enumera cada paquete desactualizado, marcado como movido por `bun run deps:update` o como fijado, y cada skill con los commits entre los que se movería. El primer paso también lee con `git ls-remote`, que no necesita token, las etiquetas de versión del repositorio de cada action fijada, y la issue enumera cada action fijada a una versión anterior a la más reciente.

Después de la issue, el job ejecuta `bun run deps:audit`, el mismo análisis que el job `check`, para que un aviso alto o crítico nuevo haga fallar la ejecución semanal incluso en una semana sin pull requests.

El flujo de trabajo solo puede leer el repositorio y escribir issues, y solo el segundo paso recibe el token. No abre ninguna pull request, porque GitHub no inicia ningún flujo de trabajo para una pull request que abre el propio token del flujo, así que sus comprobaciones nunca se ejecutarían; ejecuta `bun run deps:update` en una rama en su lugar.

## Versiones y etiquetas [#releases-and-tags]

El sitio se despliega de forma continua, así que sus versiones son fechas, no versiones semánticas. Cuando un despliegue a producción termina con éxito, el job `release` de `deploy.yml` etiqueta el commit desplegado como `vYYYY.MM.DD` con la fecha UTC y publica una GitHub Release para él. Un segundo despliegue a producción el mismo día recibe la etiqueta `vYYYY.MM.DD.2`, el siguiente `.3`, y así sucesivamente. Los despliegues a preview nunca se etiquetan. El job `release` es el único con `contents: write`.

Las notas de la versión son las entradas del [registro de cambios](/docs/project/changelog) que publicó la versión, las que llegaron a `main` desde la etiqueta de versión anterior, cada una terminada en `(#<number>)`, que GitHub enlaza a su pull request, de modo que cada cambio se describe en un solo lugar; si una versión no publicó ninguna, sus notas enlazan al registro de cambios. `scripts/publish-release.ts` toma las notas de `releaseNotes`, en `src/lib/changelog.ts`, el único elemento de su `RELEASE_NOTES`, y ejecuta `gh release create` con la etiqueta que eligió el despliegue, así que un proyecto sin el registro de cambios publica sus versiones sin notas. Una nueva ejecución conserva la etiqueta que ya tiene el commit y omite la GitHub Release si ya existe.

El job del despliegue a producción elige esa etiqueta antes de compilar: `scripts/choose-release-tag.ts` aplica `releaseTag` de `src/lib/release.ts` a las etiquetas del checkout, la compilación recibe la etiqueta como `RELEASE_TAG` y el job se la pasa al job `release` como su salida `release-tag`, de modo que el despliegue y su versión comparten una etiqueta. Con ella, el [registro de cambios](/docs/project/changelog) enlaza cada entrada a la versión que la publicó por primera vez: la etiqueta de versión más antigua cuyo commit contiene el commit squash de la entrada en el historial de primeros padres de `main`, que la compilación lee junto con las fechas en un solo `git log`, o la propia etiqueta del despliegue para las entradas que trae. El job `release` lee el registro de cambios de la misma manera, con la etiqueta que publica, así que las notas de una versión son exactamente las entradas que la página enlaza a esa versión. Las entradas fusionadas antes de la primera etiqueta de versión no enlazan a ninguna versión, y en las compilaciones locales, de vista previa y de pull requests tampoco las entradas que ningún despliegue ha publicado aún. Dos despliegues a producción no pueden elegir la misma etiqueta: `deploy.yml` ejecuta una sola ejecución del workflow a la vez (`concurrency` con `queue: max`), así que el job `release` de la ejecución anterior ya ha creado su etiqueta cuando el siguiente despliegue hace checkout del repositorio.

Para devolver producción a una versión, revierte en una pull request todo lo posterior a su etiqueta:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Al fusionarla, el código etiquetado se despliega tras las comprobaciones habituales y se etiqueta como una nueva versión. Las migraciones de D1 no se revierten, así que el código anterior se ejecuta sobre el esquema más reciente. Cada cambio de esquema debe funcionar con la aplicación desplegada antes que él, lo que hace que esto sea seguro para la versión anterior; lee las migraciones intermedias antes de retroceder más.
