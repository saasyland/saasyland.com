---

Roles and permissions are defined in `src/integrations/better-auth/auth.access.ts` with Better Auth's access control. The same definitions are used by the server (`authorized`, route guards) and by the Better Auth client.

## Roles

| Role     | Code       | Permissions                                                                                     |
| -------- | ---------- | ----------------------------------------------------------------------------------------------- |
| Admin    | `admin`    | Every application statement below, plus Better Auth's admin statements for `user` and `session` |
| Customer | `customer` | None. Customers can call server functions that only require a session.                          |

New users get `customer` (`DEFAULT_ROLE_CODE`).

## Statements

Application statements (`APP_STATEMENTS`):

| Resource   | Actions                                         |
| ---------- | ----------------------------------------------- |
| `admin`    | `access`                                        |
| `category` | `create`, `read`, `update`, `delete`            |
| `order`    | `read`, `update`, `refund`                      |
| `product`  | `create`, `read`, `update`, `delete`, `publish` |
| `settings` | `manage`                                        |

Better Auth statements granted to admins:

| Resource  | Actions                                                                                                    |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| `user`    | `create`, `list`, `set-role`, `ban`, `impersonate`, `delete`, `set-password`, `set-email`, `get`, `update` |
| `session` | `list`, `revoke`, `delete`                                                                                 |

## Where permissions are checked

| Permission               | Checked by                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `admin: ["access"]`      | `requireAdmin` on the `/admin` layout and the redirect after sign-in                                         |
| `category` actions       | The category use cases: `read`, `create`, `update`, `delete`                                                 |
| `product` actions        | The product use cases: `read`, `create`, `update`, `delete`                                                  |
| `user` actions           | The user use cases, one action each; `ban` covers both `ban-user` and `unban-user`                           |
| `session` actions        | `list-user-sessions` (`list`), `revoke-user-session` and `revoke-user-sessions` (`revoke`)                   |
| A session, no permission | Account, license, two-factor, newsletter preference and own-session use cases, and `stop-impersonating-user` |

`order`, `product: ["publish"]` and `settings` are declared but not yet checked by any server function.

## Checking a permission

Server functions use the middleware, for example `authorized({ category: ["read"] })`. Other code calls `hasPermission`, as the admin guard does:

```ts
export const requireAdmin = async (context: AuthRouteContext) => {
  const result = await requireSignedIn(context)
  if (!hasPermission({ permission: { admin: ["access"] }, role: result.session.user.role })) {
    throw redirect({ replace: true, to: ROUTES.APP })
  }
  return result
}
```
