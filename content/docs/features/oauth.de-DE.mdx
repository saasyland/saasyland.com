title: "OAuth-Anbieter"
description: "Anmeldung mit GitHub und Google über die Social-Provider von Better Auth."
---

`auth.server.ts` registriert zwei Anbieter mit Zugangsdaten aus der Worker-Umgebung, mit den Anbieter-IDs aus `AUTH_PROVIDER` (`auth.constants.ts`) als Schlüsseln:

```ts
socialProviders: {
  [AUTH_PROVIDER.GITHUB]: { clientId: env.AUTH_GITHUB_CLIENT_ID, clientSecret: env.AUTH_GITHUB_CLIENT_SECRET },
  [AUTH_PROVIDER.GOOGLE]: { clientId: env.AUTH_GOOGLE_CLIENT_ID, clientSecret: env.AUTH_GOOGLE_CLIENT_SECRET },
},
```

## Ablauf

`OAuthButtons` (`src/presentation/components/custom/auth/oauth-buttons.tsx`) rendert bei Anmeldung und Registrierung eine Schaltfläche pro Anbieter, GitHub zuerst, auf beiden Seiten beschriftet mit **Mit GitHub fortfahren** und **Mit Google fortfahren** (`auth.oauth.continueWith`). Das Plugin `lastLoginMethod` von Better Auth speichert, wie sich der Browser zuletzt angemeldet hat, `email`, `github` oder `google`, im Cookie `saasyland.last_used_login_method` (`LAST_LOGIN_METHOD_COOKIE`), und die passende Schaltfläche, auf der Anmeldeseite auch das E-Mail-Feld, trägt nach der Hydration das Badge **Zuletzt verwendet**. Bei einem falschen Passwort bietet die Anmeldeseite außerdem beide Anbieter an. Die Komponente ruft Better Auth `signIn.social` mit einer lokalisierten `callbackURL` (`/auth/callback`) und `errorCallbackURL` (`/auth/sign-in`) auf. Nach der Rückkehr vom Anbieter leitet `/auth/callback` Admins zu `/admin` und Kunden zu `/app` weiter. Ein fehlgeschlagener Versuch kehrt mit `?error=` zur Anmeldeseite zurück, die die übersetzte Meldung aus `auth.errors` anzeigt.

`accountLinking` ist aktiviert, sodass eine Social-Anmeldung mit einem bestehenden Benutzer mit derselben E-Mail-Adresse verknüpft wird. Anbieter-Tokens werden verschlüsselt in der Tabelle `account` gespeichert.

## Einrichtung der Anbieter

Registriere die Callback-URLs <RepositoryFact name="oauthCallbackPaths" /> für jeden Host, den du betreibst: lokal `localhost:3000`, `preview.saasyland.com` und `saasyland.com` (siehe `DEPLOYED_HOSTS` in `src/modules/_core/constants/api.ts`). Trage die Client-IDs und Secrets in die oben genannten Umgebungsvariablen ein.

Vor dem Build lehnt `bun run deploy:<environment>` eine Client-ID ab, die der Anbieter zurückweisen würde: `scripts/prepare-deploy-secrets.ts` schlägt bei einem Platzhalter wie `[UPDATE]` in einem beliebigen Secret fehl, und der Deploy-Check des Auth-Bereichs, `auth:verify`, schlägt fehl, es sei denn, <RepositoryFact name="oauthClientIdVariables" /> in `.env.<environment>` enthalten jeweils eine Client-ID im Format ihres Anbieters. Nach einem Deployment startet `scripts/verify-deployment.ts` die Anmeldung bei jedem Anbieter auf der deployten Domain und schlägt fehl, wenn die Autorisierungs-URL des Anbieters nicht auf dessen Host liegt, eine `client_id` enthält, die nicht im Format dieses Anbieters ist, oder eine `redirect_uri`, die nicht zur selben Domain zurückführt ([Projektskripte](/docs/tooling/scripts)). Wie du Googles `Error 401: invalid_client` behebst, erklärt die [Fehlerbehebung](/docs/reference/troubleshooting).

Die GitHub-Zugangsdaten authentifizieren außerdem die Abfrage der Repository-Sterne in `src/lib/github.ts`.
