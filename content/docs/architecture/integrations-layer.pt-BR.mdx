Cada biblioteca ou serviço de terceiros que precisa de configuração tem uma pasta própria em `src/integrations`. Os arquivos seguem o padrão `<prefix>.<concern>.ts`, em que o prefixo é o nome curto do fornecedor.

| Pasta            | Arquivos                                                                                                                                                                                   | Responsabilidade                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `affonso`        | `affonso.constants`, `affonso.program`, `affonso.referral`                                                                                                                                 | Os parâmetros de indicação, a URL do pixel, o ID do programa e a indicação repassada à Polar como metadados do checkout                                |
| `better-auth`    | `auth.server`, `auth.client`, `auth.access`, `auth.roles`, `auth.middleware`, `auth.routes`, `auth.session`, `auth.errors`, `auth.hooks`, `auth.zod`, `auth.constraints`, `auth.constants` | Configuração da autenticação, papéis, middleware das server functions, guards de rota, query de sessão, IDs dos provedores                             |
| `drizzle-orm`    | `drizzle.config`, `drizzle.database`, `drizzle.schemas`, `drizzle.errors`, `drizzle.columns`, `migrations/`                                                                                | O cliente D1, o registro de schemas, as migrações SQL, `rethrowAsConflict` para erros de restrição única e as colunas compartilhadas de `timestamps()` |
| `fumadocs`       | `fumadocs.config`, `fumadocs.schema`, `fumadocs.indexes`, `fumadocs.docs`, `fumadocs.blog`, `fumadocs.i18n`                                                                                | As coleções MDX da documentação e do blog, os índices da documentação, do blog e de busca gerados no build, e o carregamento das páginas               |

| `resend`         | `resend.config`, `resend.utils`, `resend.constants`                                                                                                                                        | O cliente do Resend, `sendEmail` e os nomes de `EMAIL_PURPOSE`                                                                                         |

## O que não é uma integração

- A contagem de estrelas do GitHub é uma server function em `src/lib/github.ts`, com cache no KV.
- O rate limiting fica em `src/lib/rate-limit.ts`, apoiado na tabela `rate_limit`.
- Os bindings do Cloudflare não precisam de adaptador. O código de servidor os lê de `env` em `cloudflare:workers`.

## A lógica de negócio fica nos módulos

Uma integração configura um fornecedor. As decisões sobre os dados da aplicação pertencem ao módulo dono da tabela:

- O plugin da Polar, que a área da Polar adiciona ao Better Auth em `src/data/polar.auth-plugins.ts`, verifica as assinaturas dos webhooks com `POLAR_WEBHOOK_SECRET` e repassa cada evento para `handlePolarEvent`, em `src/data/polar-events.ts`. Essa função o repassa a cada área que lista o evento no seu `<area>.polar-events.ts`; o `src/data/license.polar-events.ts` da área de licenças chama `licenseWebhookHandlers`, em `src/modules/license/license.webhooks.ts`, que chamam os casos de uso de licença. Os IDs dos produtos dos planos de licença, `POLAR_PRODUCT_IDS`, também pertencem à área de licenças, em `src/modules/license/license.utils.ts`.
- Os hooks de e-mail do Better Auth chamam `sendVerifyEmail`, `sendResetPasswordEmail` e `sendChangeEmailConfirmationEmail`, dos módulos de verificação e de conta, que o Resend adiciona em `src/data/resend.auth-emails.ts`.
- Um caso de uso envia um e-mail no locale que o chamador repassa (o e-mail de verificação o lê da URL de callback): ele carrega o namespace do template, renderiza o template e chama `sendEmail`:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await sendEmail({
  idempotency: { purpose: EMAIL_PURPOSE.VERIFY_EMAIL, token: crypto.randomUUID() },
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verifyUrl: verifyUrl.toString() }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```
