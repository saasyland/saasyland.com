Workflows live in `.github/workflows/`. The application workflows (`ci.yml`, `deploy.yml`, `e2e-reusable.yml` and `deploy-reusable.yml`) set up the toolchain with the composite action `.github/actions/setup`: Bun <RepositoryFact name="bunVersion" />, Vite+ with the Node version from `.nvmrc` and Bun's install cache, which `setup-vp` restores once, `bun install --frozen-lockfile --ignore-scripts` and `bun run typegen`. `remotion.yml` sets up Node from `.nvmrc` and npm instead.

| Workflow              | Trigger                                                                                 | Jobs                                                                             |
| --------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests, and calls from `deploy.yml`                                              | Checks and coverage, Chromium E2E, then the preview deploy of a pull request     |
| `deploy.yml`          | Pushes to `main`                                                                        | The checks of `ci.yml`, then the production deploy and its release               |
| `e2e-full.yml`        | Pushes to `main`, the schedule <RepositoryFact name="e2eFullSchedule" /> in UTC, manual | WebKit on push; Chromium and WebKit on schedule and manual runs                  |
| `e2e-reusable.yml`    | Called by the workflows above                                                           | One test build, one Playwright project on parallel shards and one check for both |
| `deploy-reusable.yml` | Called by `ci.yml` and `deploy.yml`                                                     | Build, D1 migrations and `wrangler deploy`                                       |
| `remotion.yml`        | Changes to `remotion/` or the website files it imports                                  | Checks and bundles the landing page video project with npm                       |

`remotion.yml` runs on the same paths for pull requests and pushes: `remotion/`, the workflow itself and the website files that `remotion/src` imports, directly or through other website files. `src/__test__/workflows.test.ts` follows those imports and fails when a file they reach matches none of the paths, or a path matches none of the files.

The checkouts in `e2e-reusable.yml`, whose build renders the changelog and whose `content.spec.ts` reads it, in `deploy-reusable.yml`, which builds the site, and in the `release` job fetch every commit without its trees (`fetch-depth: 0` and `filter: tree:0`), because the [changelog](/docs/project/changelog) dates each entry by the commit that brought it to `main`. That adds only the commits themselves to what a shallow clone downloads, and a shallow clone fails the build instead of dating the entries wrongly. `src/__test__/workflows.test.ts` fails when one of these checkouts stops fetching the history.

## Checks

The `verify` job in `ci.yml` runs `bun run check` (class-name tables, i18n and content checks, the [flow inventory](/docs/tooling/test-coverage#flow-coverage), formatting, lint and types) and `bun run test:coverage`, then uploads the coverage report. The `e2e` job calls `e2e-reusable.yml`, which builds once and runs the suite on <RepositoryFact name="e2eShards" /> runners in parallel:

| Job                                        | Runs                                                                                                                                           |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                    | `db:reset:test` and `build:test`, then uploads `dist` and the seeded `.wrangler/test` as one artifact                                          |
| `shard`                                    | One job per shard: downloads that build, installs the browser and runs `bunx playwright test e2e/specs --project=chromium --shard=<n>/<total>` |
| `report`, named `Build and E2E (chromium)` | Fails unless the build and every shard passed; when a shard failed, merges the shards' blob reports into one HTML report and uploads it        |

Playwright's own retries and workers stay as [Playwright](/docs/tooling/playwright#configuration) describes them, on every shard. The `report` job is the one check that the branch rules require, so adding or removing a shard changes no required check name.

In a pull request, `bun run check` also fails until the pull request adds its [changelog entry](/docs/conventions/git-workflow#changelog-entries). The build in the `e2e` job, and in the deploy jobs, fails while the changelog would list an entry under **Unreleased** that is not the pull request's own, and on `main` while it would list any.

## Deployments

Deployments run only after `verify` and `e2e` pass, in the run of `ci.yml` for a pull request and in the run of `deploy.yml`, which calls `ci.yml`, for a push to `main`:

| Event                                         | Target       | GitHub environment | URL                           |
| --------------------------------------------- | ------------ | ------------------ | ----------------------------- |
| Pull request from a branch in this repository | `preview`    | `Preview`          | https://preview.saasyland.com |
| Push to `main`                                | `production` | `Production`       | https://saasyland.com         |

`deploy-reusable.yml` gives each GitHub environment its URL, and `src/__test__/workflows.test.ts` fails when one differs from its host in `DEPLOYED_HOSTS` (`src/modules/_core/constants/api.ts`). Pull requests from forks and Dependabot are validated but not deployed. The preview is shared: each deployment replaces the previous one and uses the same preview D1 database, KV namespace and R2 buckets.

`deploy-reusable.yml` checks for the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets, runs `scripts/verify-bindings.ts`, builds with the dummy values from `.env.test`, removes the generated `dist/server/.dev.vars`, applies `db:migrate:<target>` and runs `vp exec wrangler deploy --config dist/server/wrangler.json`. It does not run `scripts/verify-deployment.ts`, the live site check of the `deploy:<target>` scripts, because Cloudflare's bot protection answers 403 to requests from CI runners. Nor does it run `scripts/run-deploy-checks.ts`, so CI runs none of the deploy checks the areas declare in `DEPLOY_CHECKS`: CI has no `.env.<target>`, and the GitHub environments hold only the Cloudflare credentials. Today these are the auth area's `auth:verify` and the Polar area's `polar:verify`; run `bun run auth:verify:<target>` locally after changing an OAuth client and `bun run polar:verify:<target>` after every change in Polar ([Polar setup](/docs/getting-started/polar-setup)). No secrets file is uploaded: the Worker keeps the runtime secrets already set in Cloudflare. Deployments to the same target queue instead of cancelling each other. A new commit on a pull request cancels the run of `ci.yml` for the commit before it, which nobody will merge, while the runs of `deploy.yml` and `e2e-full.yml` on `main` queue and never cancel one another (`concurrency` with `queue: max`), so every push to `main` is tested and deployed.

Dependabot updates the GitHub Actions weekly.

## Releases and tags

The site is deployed continuously, so its versions are dates, not semantic versions. When a production deploy succeeds, the `release` job in `deploy.yml` tags the deployed commit `vYYYY.MM.DD` with the UTC date and publishes a GitHub Release for it. A second production deploy on the same day is tagged `vYYYY.MM.DD.2`, the next one `.3`, and so on. Preview deploys are never tagged. The `release` job is the only job with `contents: write`.

The release notes are the [changelog](/docs/project/changelog) entries that the release shipped, the ones that reached `main` since the previous release tag, each ending with `(#<number>)`, which GitHub links to its pull request, so every change is described in one place; when a release shipped none, its notes link to the changelog. `scripts/publish-release.ts` takes the notes from `src/lib/release.ts` and runs `gh release create` with the tag the deploy chose. A re-run keeps the tag the commit already has and skips a release that already exists.

The production deploy job chooses that tag before it builds: `scripts/choose-release-tag.ts` runs `releaseTag` from `src/lib/release.ts` on the tags of the checkout, the build gets the tag as `RELEASE_TAG`, and the job hands it to the `release` job as its `release-tag` output, so the deploy and its release share one tag. With it, the [changelog](/docs/project/changelog) links each entry to the first release that shipped it: the earliest release tag whose commit contains the entry's squash commit along the first-parent history of `main`, which the build reads together with the dates in one `git log`, or the deploy's own tag for the entries it brings. The `release` job reads the changelog the same way, with the tag it publishes, so a release's notes are exactly the entries the page links to that release. Entries merged before the first release tag link to no release, and so do entries that no deploy has shipped yet in local, preview and pull request builds. Two production deploys cannot choose the same tag: `deploy.yml` runs one workflow run at a time (`concurrency` with `queue: max`), so the `release` job of the previous run has created its tag before the next deploy checks out the repository.

To roll production back to a release, revert everything after its tag in a pull request:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Merging it deploys the tagged code after the usual checks and tags it as a new release. D1 migrations are not reverted, so the older code runs against the newer schema. Every schema change must work with the application deployed before it, which makes this safe for the previous release; read the migrations in between before going further back.
