## ShipFast が公開している数字と、公開していない数字

ShipFast は、ほとんどのボイラープレートが避けていることをしています。自らの計算を示しているのです。ホームページでは、省ける作業を項目ごとに挙げ、その合計を出しています。メール、3 時間。ランディングページ、6 時間。Stripe の Webhook、4 時間。SEO タグ、2 時間。Google OAuth、1 時間。DNS、3 時間。保護された API ルート、2 時間。**「22 時間以上の頭痛の種」**。

この数字は正直であり、市場もそれを認めています。**8,393 人のメイカー** がこの製品にお金を払っています。ページ上のある推薦文では、個人の実感として「15 時間以上」という数字が挙げられています。私はこのどれにも異論はありません。月曜日までにランディングページ、ログイン、動作するチェックアウトを公開することが目標なら、ShipFast を買うのが正解であり、本記事がそれを思いとどまらせることはありません。

2 つ目の数字は、どのスターターキットも公開していないものです。項目化するのが難しく、はるかに大きいからです。

**ローンチから 2 番目の有料顧客コホートまでに、何時間かかるでしょうか？**

空のフォルダからデプロイまでではありません。デプロイから事業になるまでです。その間に、最初のチームがシートを求め、最初の顧客の経理部門が自社名入りの請求書を求め、「アカウント削除」が 9 つのテーブルにカスケードしなければならないことに気づき、誰かがこのアプリをドイツ語で使えるかと尋ねてきます。

22 時間目はボイラープレートの問題です。**300 時間目はアーキテクチャの問題**であり、この 2 つにはほとんど何の関係もありません。

## ShipFast が無条件で優れている点

3 つあり、どれも小さなことではありません。

**オファーが際立って正直です。** ほとんどのボイラープレートは成果を売ります。ShipFast は期間を売り、その期間を明示し、その期間が価格に見合うかどうかを確かめさせてくれます。これはこのカテゴリーのほぼどの製品よりも優れたポジショニングであり、この数字が頻繁に引用されるのもそのためです。

**コンポーネントライブラリが本当に役立ちます。** ヘッダー、ヒーロー、推薦文、料金ブロック、FAQ セクション、モーダル。料金表の見た目を整えるために土曜日を丸ごと費やしたことがあれば、マーケティング面は、創業者が一貫して過小評価する本物の作業だとわかるはずです。

**スコープが規律立っています。** ShipFast はエンタープライズ向けプラットフォームのふりをしていません。アイデアを素早く検証したい人を対象としており、作者自身がそう明言していて、製品もその狙いと一貫しています。自分が何でないかを分かっているツールは、本来あるべき以上に珍しいものです。

有料ニュースレター、単一ユーザー向けの AI ラッパー、ディレクトリサイト、あるいは顧客が 1 枚のクレジットカードを持つ 1 人の個人であるようなものをローンチするなら、ここで読むのをやめてください。ShipFast を買いましょう。そのほうが早く公開でき、本記事はあなた向けではありません。

## 4 つの判断と、それぞれが 300 時間目に生むコスト

ここから先は、もう一方の読者のためのものです。つまり、企業がお金を払う、複数のシートを持つものを作っていて、顧客が付いた後も保守し続けるつもりの人です。

### 1. リレーショナルなプロダクトの下にあるドキュメントストア

ShipFast の技術スタックは、ホームページで **「Mongo + Mailgun + Stripe + NextJS + Tailwind + NextAuth = ShipFast」** と記載されており、代替として Supabase も利用できます。

SaaS が課金の対象とするオブジェクトはリレーショナルであり、それは偶然ではありません。ユーザーは組織に属します。組織はサブスクリプションを持ちます。サブスクリプションは請求書を生み出します。請求書には明細行があり、明細行は価格を参照し、価格は商品を参照します。この一連の文に出てくる矢印は、すべて外部キーです。

Postgres では、これらの矢印は制約です。データベースは、請求書が孤立することを拒否します。アカウント削除時のカスケードは、誰かが覚えていてくれることを願うコードパスではなく、スキーマの性質です。サブスクリプション、組織、シートを結合するレポートは、1 つのクエリで済みます。

ドキュメントストアでは、これらの矢印の一つひとつがアプリケーションコードになります。結合は 2 回目のラウンドトリップです。整合性の保証は規約にすぎません。ドキュメントが 4 つでユーザーが 1 人しかいない 22 時間目には、どれも問題になりません。これは 300 時間目に静かにやってくる種類の問題です。解約した組織にまだ課金されているというサポートチケットが届き、原因を突き止めるのに 2 日かかる、といった形で。

この 10 年に特有の事情もあります。コーディングエージェントは、ドキュメント向けのコードよりもリレーショナルなコードをはるかに上手に書きます。スキーマが型になるからです。宣言された Postgres スキーマの上に型付きのクエリビルダーがあれば、間違ったカラムはコンパイルエラーになります。この仕組みについては [AI コーディングエージェントのための SaaS スタックの選び方](/blog/choosing-a-saas-stack-for-ai-coding-agents) で書きましたが、ここでもそれが強く当てはまります。ドキュメントストアでは、間違った形のデータでもコンパイルが通り、デプロイでき、デモも正しく動いてしまいます。

### 2. NextAuth と、3 人目のシートで起きること

NextAuth は「Google でログインできるようにする」ことを解決し、しかもうまく解決しています。ビジネス向けプロダクトに必要な機能は、そのすぐ先にあるものです。招待機能付きの組織、特定の操作を制限するロール、選択肢として提供するのではなくポリシーで強制する二要素認証、サポートのためのなりすまし、誰かが退職したときのセッション失効、そしてそのすべての監査証跡です。

どれも珍しいものではありません。どれもが、最初のビジネス顧客から届く最初のセキュリティ質問票に載っています。そして、後から追加すると、どれもセッションモデルに手を入れることになり、つまりセッションを読むあらゆる箇所に手を入れることになります。

代わりの選択肢は、別のライブラリというより、別の出発点となる前提です。認証コードはリポジトリの中に読めるソースとして存在し、ロール、二要素認証、なりすまし、失効可能なセッションがすでにスキーマにある、という前提です。上の表の「リポジトリ内の Better Auth」が意味するのはこのことです。2 年目のコストモデルに、月間アクティブユーザーごとの費用項目がない理由でもあります。

### 3. 2 つのリポジトリと、好みの問題としての型システム

ShipFast は JavaScript 版と TypeScript 版を提供しています。これは筋の通った製品判断です。同時に構造的な表明でもあり、その表明とは、**型システムは制約ではなく、配布形態の選択肢である**ということです。

厳格さが任意ではない場合にどう見えるかと比べてみてください。このコードベースの TypeScript 設定は、「strict: true」だけで終わりではありません。次のとおりです。

```jsonc
{
  "strict": true,
  "exactOptionalPropertyTypes": true,
  "noUncheckedIndexedAccess": true,
  "noPropertyAccessFromIndexSignature": true,
  "noImplicitReturns": true,
  "noFallthroughCasesInSwitch": true,
  "noUnusedLocals": true,
  "noUnusedParameters": true,
}
```

`noUncheckedIndexedAccess` だけでも、コードベースの性格は変わります。`array[0]` は `T | undefined` になるので、「明らかにそこにある」というバグは、午前 3 時の呼び出しではなくコンパイルエラーになります。`exactOptionalPropertyTypes` は、明示的な `undefined` がキーの欠落と同じではないことを意味します。これはまさに、更新ハンドラーで気づかないうちにデータが失われる原因となる区別です。

さらに、`typescript/no-explicit-any` は警告ではなくエラーであり、プロジェクトが有効にしているリントのカテゴリはすべてエラーに設定されています。`any` という逃げ道はなく、無視することに慣れてしまう警告もありません。指摘が 1 つでもあれば、マージを判定するチェックが失敗するからです。

要点は、ShipFast のユーザーが悪いコードを書くということではありません。厳格さがプロジェクトごとの選択であるコードベースには、十分な時間と十分な数のコントリビューターを経るうちに、どこかに弱いほうの選択が入り込むということです。そして、それがどこなのかは、問題になるまでわかりません。

### 4. ドキュメントにないセクション

これはどんなスターターキットを評価するときにもできる最も有益なことで、4 分しかかかりません。ホームページではなく、ドキュメントの目次を開いて読むことです。

ShipFast の目次は Tutorials、Features、Components、Security、Deployment、Extras です。Features の下には SEO、データベース、メール、決済、OAuth、マジックリンク、サポート、エラー処理、アナリティクス。Security の下にはレート制限、送信制限、セキュリティヘッダー、スキーマ検証。その製品にふさわしい、よく整理されたドキュメントです。

そこにないもの：テスト、マルチテナンシー、組織、ロールと権限、管理画面、国際化。

ドキュメントのページがないことは、機能が存在しない証拠にはなりません。しかし、その機能が製品としてサポートされている部分なのか、自分で作ることが期待されているものなのかを判断する、信頼できる目安にはなります。そして、この 6 つはそれぞれ 1 週間分の作業であり、最悪のタイミングでやってきます。つまり、これから作り直そうとしている部分に顧客が依存するようになった後です。

## 300 時間目：項目別の残作業

1 つ目の計算と同じ考え方で、2 つ目の計算を示します。これは、有能な開発者が、有料の企業顧客に出せると思える水準で各項目を作る場合の控えめな見積もりであり、どう実装するかを決める時間は含みません。

| まだ自分で作るもの                       | 午後だけでは終わらない理由                                                                         | 正直な見積もり    |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------- | ----------------- |
| 組織と招待                               | スキーマ、招待トークン、有効期限、シート数のカウント、所有権の移転、メンバー退出時の処理           | 25〜40 時間       |
| ロールと権限                             | すべてのクエリとルートが参照しなければならないポリシー層と、それを反映する UI                      | 20〜30 時間       |
| テナントの分離                           | ビュー層ではなくクエリ層で強制し、2 つ目のテナントでテストする                                     | 15〜25 時間       |
| 管理画面                                 | 誰も見ないが、なければ運営できない 10 のセクション：ユーザー、組織、サブスクリプション、返金、ログ | 40〜60 時間       |
| 最初のチェックアウト以降の課金           | 日割り計算、アップグレード、ダウングレード、督促、冪等な Webhook 処理、請求履歴                    | 25〜40 時間       |
| スパム扱いされないトランザクションメール | テンプレート、プレビュー、ロケールごとの文面、到達率、配信停止とコンプライアンス                   | 15〜25 時間       |
| 国際化                                   | 翻訳ではありません。ルーティング、フォーマッター、複数形ルール、キーの一致チェック                 | 20〜35 時間       |
| デプロイを止めるテストスイート           | テスト、フィクスチャ、CI の設定、そして赤のままマージしない規律                                    | 60〜100 時間      |
| **合計**                                 |                                                                                                    | **220〜355 時間** |

時給 $150 で計算すると、この範囲の下限は **$33,000** です。上限は $53,000 を超えます。それに比べれば、$199 のボイラープレートと <TierPrice tier="core" /> のボイラープレートの差は、1 秒以上考える価値のある数字ではありません。

しかも、時間は安いほうの部分です。高くつくのは、8 項目のうち 4 つ、つまりテナントの分離、権限、Webhook の冪等性、セッションの失効が、共通の性質を持っていることです。**間違った実装でもレビューを通過し、デモでは正しく動きます。** 後になって、本番環境で、他人のデータの上で、静かに失敗します。これは時間をかければ直せる種類のバグではありません。あなたが来る前に正しく作られた基盤によって避けるべき種類のバグです。

## 機能ではない違い

機能比較表は最も弱い比較の形です。誰でも行を追加できるからです。ここで示すのは、競合が来週、表に追加することのできない違いです。それは、コードがどのようにまとまっているかという性質だからです。

**このコードベースでは、所有範囲が明示されています。** ルート、機能の操作、ベンダーの設定、プレゼンテーションには、それぞれ別の置き場所があり、型付きのチェックと振る舞いのテストがその構造を支えています。

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

`src/routes` はリクエストとナビゲーションを調整します。`src/modules` は機能のユースケースとバリデーションを、`src/integrations` はベンダーのセットアップを、`src/presentation` はコンポーネントとその周辺の部品を受け持ちます。`src/platform` ディレクトリには、ローカルでのテストを支える仕組みが入っています。これらの責務は文書化されており、コードと一緒にレビューされます。

この区別は重要です。型チェックとサーバー専用の境界は強制されますが、機能の所有範囲には引き続きレビューが必要です。コントリビューターやコーディングエージェントは、同じ機能にある既存の操作に倣い、別のレイヤーを発明することなくその振る舞いをテストできます。

フォルダ構成図は出発点にすぎません。関連する操作とコンポーネントをまとめておくこと、型付きの境界を使うこと、追加されたものを既存のパターンと照らしてレビューすること。それらが、時間が経ってもこの構造を保ちます。

アイデアを検証している段階で、コードが使われる期間の正直な見込みが 6 か月未満なら、ShipFast を買いましょう。顧客が企業ではなく個人なら、買いましょう。このスタックで以前にもリリースした経験があり、どの部分を置き換えるか正確に分かっているなら、買いましょう。今月重要な指標がチェックアウトを公開するまでのスピードだけなら、買いましょう。その指標において ShipFast は優秀であり、8,393 人がそれに同意しています。

1 つのものを作っていて、2 年後もそれを作り続けるつもりなら、こちらを買ってください。顧客が企業である場合、つまりシート、請求書、ロール、セキュリティ質問票が必要になる場合。認証をアクティブユーザー単位で借りるより、自分で所有したい場合。テストのないコードベースを引き継いだ経験があり、そのときの気持ちを覚えている場合。サーバー専用の境界でビルドが失敗し、それ以外のアーキテクチャはレビュアーが確認できる場所に書き残されていることを望む場合。

## よくある質問

<Accordions>

<Accordion title="2026 年における最良の ShipFast の代替は何ですか？">

何を作るかによります。今週末にアイデアを検証して次へ進みたいなら、ShipFast がすでに最適なツールであり、最初のデプロイまでの時間で ShipFast に勝る代替はありません。チームに課金する、シートを追加する、セキュリティレビューを通過する、あるいは 2 年後もコードベースを保守しているつもりなら、リレーショナルなデータモデル、厳格な型、テストゲートを備えた基盤が必要です。本記事で検討するのは、このトレードオフです。

</Accordion>

<Accordion title="ShipFast は TypeScript で書かれていますか？">

両方あります。ShipFast は JavaScript のリポジトリと TypeScript のリポジトリを別々の選択肢として提供しており、ドキュメントは両方を扱っています。これは、厳格な TypeScript しか存在しないコードベースとの実質的な違いです。型システムが配布形態の選択肢である場合、それは将来のコードが満たさなければならない制約ではなく、後から加わったコントリビューターが型のない道を選ぶことを妨げるものは何もありません。

</Accordion>

<Accordion title="ShipFast には自動テストが含まれていますか？">

公開ドキュメントにはテストのページがありません。セクションは Tutorials、Features、Components、Security、Deployment、Extras です。これは、長期的な保守ではなく最初のデプロイまでのスピードという、製品が掲げる目的と一貫しています。ただし、リグレッションを防ぐセーフティネットは、2 番目の機能を作る前に自分で構築するものだということになります。

</Accordion>

<Accordion title="ShipFast はマルチテナンシーや組織に対応していますか？">

ドキュメントには、マルチテナンシー、組織、チーム、ロールベースのアクセス制御のページがありません。1 人で運営するプロダクトならそれで問題ありません。企業に販売するものであれば、これは残作業の中で最大の項目です。テナントの分離は、顧客が付いてから UI 層に追加するのではなく、クエリ層で強制しなければならないからです。

</Accordion>

<Accordion title="SaaS のボイラープレートで MongoDB を使うことがなぜ問題になるのですか？">

SaaS が課金の対象とするオブジェクトはリレーショナルだからです。ユーザーは組織に属し、組織はサブスクリプションを持ち、サブスクリプションは請求書を生み出し、請求書は明細行を参照します。ドキュメントストアはこれをアプリケーションレベルの結合で表現し、外部キーはありません。そのため参照整合性は、データベースが保証する性質ではなく、自分で書いて正しく保ち続けなければならないコードになります。

</Accordion>

<Accordion title="ShipFast が $199 なのに、SaaSy Land を買う価値はありますか？">

価格の差は判断材料ではありません。どちらの価格も、作業量と比べれば誤差にすぎません。判断すべきは、どちらの問題群を自分で抱えたいかです。$199 なら、テナンシー、ロール、管理画面、テストスイート、データモデルの書き直しを自分で引き受けることになります。<TierPrice tier="core" /> の SaaSy Land なら、それらは実装済みで、テストでカバーされた状態で届きます。差を自分の作業時間で見積もれば、比較は価格の問題ではなくなります。

</Accordion>

<Accordion title="既存の ShipFast プロジェクトを移行できますか？">

はい。ただし、正直に言えば、その道筋は移行ではありません。新しいプロジェクトを生成し、ビジネスロジックをモジュール境界に移植し、データは 1 回限りのスクリプトで移します。残す価値があるのは、ドメインのコードと文言です。置き換える部分、つまり認証の配線、課金の仕組み、データモデルは、そもそもスターターキットが提供するはずだった部分です。

</Accordion>

<Accordion title="ShipFast の顧客数はどれくらいですか？">

執筆時点で、ホームページには 8,393 人のメイカーと記載されており、最初の 8,400 人の顧客までカウントダウンする割引も表示されています。これはオファーに対する本物の評価であり、真剣に受け止めるべきものです。ただしこれが測っているのは、素早いスタートを望んだ人の数であり、それらのプロジェクトのうちどれだけが 1 年後もまだ保守されていたかとは別の問題です。

</Accordion>

<Accordion title="アーキテクチャのどの部分をビルドが強制しますか？">

公開リファレンスアプリは、ルート、機能のユースケース、ベンダー連携、プレゼンテーションを分離しています。Vite+ は型情報を使ったリントチェックを実行し、テストが振る舞いを保証し、サーバー専用の境界が Worker のコードをブラウザから締め出します。機能の所有範囲は、レビュアーが確認すべき文書化された規約のままであり、ビルドがすべてのフォルダ間の関係を強制するわけではありません。

</Accordion>

<Accordion title="そもそもボイラープレートを買うべきですか？それとも create-next-app から始めるべきですか？">

学びたいのが配管部分そのものである場合や、スターターの前提とぶつかるほどプロダクトが特殊な場合は、ゼロから始めてください。空のフォルダから、本当に新しい最初の 1 行にたどり着くまでの作業が、以前にもやったことがあり、二度とやりたくない作業であるなら、買ってください。自分の認証実装に対してお金を払ってもらえた人は、これまでほとんどいません。

</Accordion>

</Accordions>
