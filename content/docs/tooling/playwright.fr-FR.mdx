Playwright teste l'application construite dans de vrais navigateurs. La suite s'exécute sur l'environnement Wrangler `test` : D1, KV et R2 locaux dans `.wrangler/test`, identifiants factices issus de `.env.test` et point d'entrée de test `src/platform/testing/worker.ts`, qui intercepte les requêtes vers Resend et Polar.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:journey
```

| Script             | Exécute                                                            |
| ------------------ | ------------------------------------------------------------------ |
| `test:e2e:install` | Installe Chromium et WebKit avec les dépendances système           |
| `test:e2e`         | Toutes les specs dans Chromium et WebKit                           |
| `test:e2e:smoke`   | `e2e/specs/smoke.spec.ts` dans Chromium                            |
| `test:e2e:pr`      | Toutes les specs dans Chromium, comme dans la CI des pull requests |
| `test:e2e:headed`  | Toutes les specs dans des navigateurs visibles                     |
| `test:e2e:ui`      | Mode UI de Playwright                                              |
| `test:journey`     | La [suite de parcours client](#journey-suite) sur la preview       |

## Configuration [#configuration]

`playwright.config.ts` exécute les specs de `e2e/specs/`, définit les projets `chromium` (Desktop Chrome) et `webkit` (Desktop Safari) et utilise `PLAYWRIGHT_BASE_URL` ou `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` de `src/data/local-server.ts`). En local, la commande du serveur web exécute `db:reset:test`, `build:test` et `start:test`, et réutilise un serveur qui répond déjà à cette URL. En CI, un job prépare le build, chacun des <RepositoryFact name="e2eShards" /> shards qui se partagent la suite le décompresse, et Playwright se contente de démarrer le serveur ([CI/CD](/docs/tooling/ci-cd#checks)).

| Paramètre  | Local                                            | CI                                               |
| ---------- | ------------------------------------------------ | ------------------------------------------------ |
| Relances   | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" />    |
| Workers    | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" />    |
| Traces     | Conservées en cas d'échec                        | À la première relance                            |
| Vidéos     | Désactivées                                      | Conservées en cas d'échec                        |
| Rapporteur | Liste et HTML                                    | GitHub et blob, fusionnés en HTML en cas d'échec |

## Lancer la suite à côté d'autres worktrees [#running-beside-other-worktrees]

Le build de test n'accepte les requêtes que des hôtes auxquels il fait confiance en mode test, car Better Auth et les liens de la newsletter vérifient l'hôte de la requête : `127.0.0.1:3000` et `localhost:3000`, ainsi que `127.0.0.1` et `localhost` sur les ports <RepositoryFact name="testServerFirstPort" /> à <RepositoryFact name="testServerLastPort" />, fixés par `TEST_SERVER_PORTS` dans `src/data/local-server.ts`. Sur tout autre port, les pages de connexion et de cours échouent : `playwright.config.ts` s'arrête donc avant de construire quoi que ce soit quand `PLAYWRIGHT_BASE_URL` désigne un autre hôte.

`PLAYWRIGHT_BASE_URL` est le seul réglage qui choisit le port : Playwright ouvre cette URL et démarre `start:test` sur son port. Quand d'autres worktrees lancent leur suite en même temps, donnez à chaque worktree son propre port de la plage. Vérifiez que rien n'écoute sur ce port, puis lancez-y la suite :

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` n'affiche rien quand le port est libre. S'il affiche un processus, prenez un autre port et laissez ce serveur tranquille : n'arrêtez que les serveurs que vous avez démarrés.

En local, Playwright réutilise un serveur qui répond déjà à l'URL et saute alors la réinitialisation de la base de données et le build : la suite ne doit donc jamais atteindre le serveur d'un autre worktree. `e2e/global-setup.ts` y veille : avant le premier test, il cherche avec `lsof` les processus qui écoutent sur le port et arrête l'exécution quand l'un d'eux tourne dans un autre répertoire que ce worktree. Un serveur que vous avez démarré depuis ce worktree passe la vérification et est réutilisé tel quel : arrêtez-le quand la suite doit tester un build tout neuf.

## Organisation

- `e2e/specs/` : specs pour les vérifications de fumée, la page d'accueil et ses commandes, la navigation, les langues, le thème, le SEO, l'authentification avec ses redirections et son routage, les espaces de travail, l'administration des utilisateurs, la newsletter, le contenu, les pages légales, la tarification régionale, le tunnel de paiement, la page de licence, l'API de licence de la CLI, l'affiliation, les vidéos, les cours, l'accès aux cours, l'administration des cours, le pied de page, les anneaux de focus, les barres de défilement et l'accessibilité (<RepositoryFact name="e2eSpecs" /> fichiers).
- `e2e/pages/` : objets de page.
- `e2e/fixtures/` : la fixture `test` étendue, des utilitaires pour les e-mails capturés, `deliverPaidOrder` dans `license.ts`, qui envoie un webhook `order.paid` signé pour accorder une licence, `buyLicense`, qui demande au Worker de test sur `/__test/polar/purchase` une commande avec sa clé de licence dans le double de test Polar et envoie leurs `order.paid` et `benefit_grant.created` signés, `startedCheckouts`, qui lit sur `/__test/polar/checkouts` les paiements créés par le double, et `accessibilityViolations` avec les `COLOR_SCHEMES` clair et sombre dans `accessibility.ts`.
- `e2e/data/accounts.ts` : les comptes créés par le seed, un administrateur et un client, ainsi que leur mot de passe. `e2e/data/licenses.ts` contient le client avec une licence et cette licence, ainsi qu'une licence pour chaque worker parallèle, sur laquelle la spec de l'API de licence de la CLI active des machines.
- `e2e/data/videos.ts` et `e2e/data/courses.ts` : la vidéo de test créée par le seed, dont les fichiers sont dans `e2e/fixtures/video/`, et le cours créé par le seed : un chapitre avec un aperçu gratuit, une leçon réservée aux comptes et deux leçons payantes, dont une sans vidéo.
- `e2e/data/<area>.pages.ts` et `e2e/data/<area>.seed.ts` : les pages de chaque zone, que visitent `accessibility.spec.ts` et `workspaces.spec.ts`, ainsi que ses lignes et ses médias dans la base de test, réunis par `pages.entries.ts` et `seed.entries.ts`.
- `e2e/data/<area>.flows.ts` : les parcours de chaque zone, chacun avec le test qui le prouve de bout en bout ou la raison pour laquelle il manque, réunis par `flows.entries.ts` ; voir [Couverture des tests](/docs/tooling/test-coverage).
- `e2e/global-setup.ts` : la configuration globale, qui arrête l'exécution quand le serveur du port de la suite tourne depuis un autre worktree.
- `e2e/journey/` : la [suite de parcours client](#journey-suite), avec sa propre configuration.

Le Worker de test exécute ce que les zones déclarent dans `e2e/data/<area>.worker.ts`, des fichiers réunis par `worker.entries.ts` : la zone des licences enregistre les clés de licence de test dans le mock de Polar, Resend expose `/__test/emails` pour lire les e-mails capturés et la zone de la newsletter `/__test/newsletter` pour lire l'état d'un abonné.

## Accessibilité

`e2e/specs/accessibility.spec.ts` exécute [axe-core](https://github.com/dequelabs/axe-core) via `@axe-core/playwright` sur les pages publiques, les pages de cours, l'accueil de la documentation, chaque page de Conventions et une page de chacune des autres sections de la documentation, un article du blog et les espaces de travail administrateur et client, dans les thèmes clair et sombre. Les pages d'administration comprennent `/admin/courses`, `/admin/courses/create` et l'éditeur du cours de test, que `e2e/specs/workspaces.spec.ts` visite aussi. Il applique les règles A et AA des WCAG 2.0, 2.1 et 2.2 ainsi que les bonnes pratiques d'axe, échoue si une page ne se charge pas avec un statut de succès, fait défiler la page pour que les sections qui apparaissent au défilement soient aussi vérifiées, attend la fin des animations finies et échoue à la moindre violation en indiquant la règle, son impact et les sélecteurs concernés.

axe ne voit ni le parcours au clavier ni la mise en page, donc trois specs les vérifient pour l'en-tête et le pied de page du site : `e2e/specs/navigation.spec.ts`, que le menu du téléphone prend le focus, garde Tab à l'intérieur, rend la page derrière `inert` et rend le focus à son bouton ; `e2e/specs/footer.spec.ts`, qu'à 320, 390 et 430 px aucun lien du pied de page n'en touche un autre ni n'en sort, dans aucune langue, et qu'un lien vers une section de l'accueil n'est courant que sur sa propre section ; et `e2e/specs/focus-rings.spec.ts`, que le sélecteur de langue du pied de page et le déclencheur de la palette de commandes de l'administration dessinent leur anneau pour le clavier.

## Barres de défilement [#scrollbars]

`e2e/specs/scrollbars.spec.ts` lance Chromium sans l'option `--hide-scrollbars` de Playwright, via `ignoreDefaultArgs` dans `launchOptions` : Chromium dessine alors des barres de défilement classiques qui prennent de la place, comme sous Windows, sous Linux et sur un Mac réglé pour toujours afficher les barres. La spec vérifie qu'une page légale, une page d'authentification et une page d'administration gardent leur titre en place quand la fenêtre grandit jusqu'à ce que la page ne défile plus (une page de la documentation défile toujours, car le pied de page du site suit sa mise en page de la hauteur de la fenêtre), qu'ouvrir la recherche de la documentation, le sélecteur de langue, une boîte de dialogue ou un menu ne déplace rien, que `/admin` remplit la fenêtre et que la fenêtre derrière une page sombre est sombre avec le thème clair. WebKit sur macOS ne dessine que des barres superposées, qui ne prennent pas de place, et aucune option de lancement n'y change rien : la vérification de la place réservée ne tourne donc que dans Chromium. Le menu du site, qui remplace les liens de l'en-tête sous `lg`, est vérifié à 768 px : l'ouvrir et le fermer ne déplace rien.

## Suite de parcours client [#journey-suite]

`bun run test:journey` achète une licence et utilise la CLI comme le fait un client, sur le déploiement de preview à `https://preview.saasyland.com`, qui encaisse les paiements dans la sandbox Polar. `e2e/journey/playwright.config.ts` est une configuration à part, avec son propre projet Chromium et sans serveur web, si bien que ni `test:e2e` ni les vérifications des pull requests ne l'exécutent, et aucun workflow ne l'exécute encore : [Couverture des tests](/docs/tooling/test-coverage#journey-suite) liste ce qu'il faut pour l'exécuter en CI. Chaque offre est un test à part entière, et les tests s'exécutent en parallèle :

1. **Compte.** Le test s'inscrit avec une nouvelle adresse de la boîte de test de Resend, `delivered+journey-<run>-<tier>@resend.dev`, trouve l'e-mail de vérification via l'API Resend et ouvre son lien.
2. **Prix.** `/app/license` doit proposer l'offre au prix du pays où Cloudflare situe le runner, tel que `/cdn-cgi/trace` l'indique : le prix régional dans un pays de `PPP_TIERS`, le prix plein partout ailleurs.
3. **Paiement.** Le checkout de la sandbox Polar doit s'ouvrir avec l'e-mail du compte déjà rempli et le consentement à la fourniture immédiate décoché ; le test le coche sur la page de Polar. Le test paie avec la [carte de test de Stripe](https://docs.stripe.com/testing) et une facturation en Pologne, où l'adresse de facturation se limite au pays.
4. **Commande et clé.** Polar doit détenir une seule commande payée pour le produit de l'offre, au prix plein moins la remise régionale, avec le consentement et la langue de l'acheteur, la confirmation d'achat doit arriver dans la boîte de réception, et `/app/license` doit afficher la clé émise par les webhooks, les commandes de la CLI et aucune machine utilisée.
5. **CLI.** La CLI publiée, lancée comme <RepositoryFact name="cliExec" /> à l'image des commandes de `/app/license`, s'adresse à la preview via `SAASYLAND_API_URL`. `activate` écrit le fichier d'identifiants avec le mode `0600`, une nouvelle activation garde le même emplacement, et `whoami` affiche la machine. Des machines de CI, distinguées par `SAASYLAND_CI_REPOSITORY`, occupent les emplacements restants, jusqu'à <ActivationLimit tier="core" /> machines pour Core, <ActivationLimit tier="complete" /> pour Complete et <ActivationLimit tier="agency" /> pour Agency, et la suivante est refusée avec `activationLimitReached`. Dès qu'un emplacement est libéré sur `/app/license`, la machine refusée l'obtient et celle qui a été libérée reçoit `activationNotFound`. `deactivate` libère la première machine et supprime ses identifiants.
6. **Remboursement.** Le test rembourse la commande via l'API de la sandbox Polar et attend que `/app/license` affiche la licence comme remboursée ; `whoami` doit alors répondre `licenseRefunded` et supprimer les identifiants.

Chaque machine de la CLI est un répertoire du dossier de sortie du test que la CLI utilise comme répertoire personnel, et la CLI s'exécute avec pour tout environnement `PATH`, ce répertoire, un cache npm et les variables `SAASYLAND_*`, de sorte qu'aucun identifiant de la suite ne l'atteint. Une commande qu'un test en échec laisse payée est remboursée à la fin du test. Les comptes restent sur la preview, chacun avec une licence remboursée.

La suite lit ces valeurs dans l'environnement, ou dans `.env.preview` quand le fichier existe, et s'arrête avant le premier test sans elles :

| Variable                                                                        | Utilisation                                                                                        |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | Lire et rembourser les commandes dans la sandbox, avec les scopes `orders:read` et `refunds:write` |
| `POLAR_SERVER`                                                                  | Doit valoir `sandbox`                                                                              |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Les produits de la sandbox auxquels les commandes doivent correspondre                             |
| `RESEND_API_KEY`                                                                | Lire les e-mails de vérification envoyés par la preview, ce qui demande une clé à accès complet    |

La preview doit exécuter un build qui contient l'[API de licence de la CLI](/docs/features/cli-licence-api) : une pull request y déploie sa branche dans le job **Deploy preview**. La sandbox doit correspondre au code, ce que vérifie `bun run polar:verify:preview`. Ensuite :

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

Le rapport est écrit dans `playwright-report/journey/`, et les traces, vidéos et répertoires de machines des tests en échec dans `test-results/journey/`.
