---
title: "Contributing"
description: "How to propose changes to SaaSy Land."
---

1. Discuss large changes in an issue first, opened from the bug report or feature request form.
2. Branch from `main`.
3. Follow the [conventions](/docs/conventions) and the [architecture](/docs/architecture), and read the matching [agent skill](/docs/tooling/agent-skills) before changing a vendor integration. Coding agents start from `AGENTS.md` at the repository root.
4. Keep tests beside their owner and hold the <RepositoryFact name="coverageThreshold" unit="percent" /> coverage gate.
5. Run the checks below.
6. Commit with a [conventional commit](/docs/tooling/conventional-commits) message and open a pull request with a conventional title, then fill in its template.
7. Rebase the branch onto `main` when it conflicts, never merge `main` into it, as [Git and pull requests](/docs/conventions/git-workflow#linear-history) describes. A maintainer puts the green pull request in the [merge queue](/docs/conventions/git-workflow#merging), which tests it again on top of `main` and merges it.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`build:test` runs the full Cloudflare build, which `check` and the unit tests do not exercise. The last command builds and serves the test Worker when no server is running and runs the specs you name in Chromium: run those that cover what you changed. CI runs every spec on the pull request and again in the merge queue, and the pull request merges only when that run is green; `bun run test:e2e:pr` runs the whole suite locally the same way. Run the full browser suite in WebKit too (`bun run test:e2e`) for changes that may behave differently there. Validate real provider integrations separately when you change their configuration.

When behaviour changes, update `content/docs` in every locale; `bun run check:content` rejects missing translations, differing code blocks and navigation. The pull request template has a summary, a test plan with the checks above and a docs list; describe in it the resulting behaviour, how you verified it and any workflow the change leaves unfinished. An admin screen ships only with a real source for its data (see [Admin dashboard](/docs/features/admin-dashboard#real-data-only)).

`CONTRIBUTING.md` at the repository root is the short version of this page, and `SUPPORT.md` says where to get help. Everyone who takes part follows `CODE_OF_CONDUCT.md`, the Contributor Covenant 2.1. Report security vulnerabilities privately, as `SECURITY.md` describes, never in a public issue.
