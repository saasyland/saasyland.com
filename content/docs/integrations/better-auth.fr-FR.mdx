Better Auth stocke les utilisateurs, les comptes, les sessions et les jetons de vérification dans D1 via l'adaptateur Drizzle. Il fournit l'inscription par e-mail et mot de passe, qui connecte aussitôt un nouveau compte et réserve pour plus tard ce qui demande une adresse confirmée, la connexion avec GitHub et Google, la réinitialisation du mot de passe, le changement d'e-mail, l'authentification à deux facteurs TOTP, la gestion des utilisateurs par l'administrateur et, grâce à son plugin Polar, le portail client et les webhooks de Polar. Les paiements ne passent pas par Better Auth : c'est `createCheckout` (`src/modules/order/order.checkout.ts`) qui crée les sessions de paiement. Son API HTTP est servie par `src/routes/api/auth.$.ts`. `auth.server.ts` et `auth.client.ts` fixent le `basePath` de Better Auth à `ROUTES.API_AUTH_BASE`, le chemin que sert ce fichier, si bien que le serveur et le client du navigateur le tirent d'une seule constante.

## Gardes de route

| Garde                | Utilisée par                     | Comportement                                                                                               |
| -------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `requireSignedIn`    | `/app`                           | Redirige vers la connexion en l'absence de session, avec la page comme `redirect`, et renvoie la session   |
| `requireAdmin`       | `/admin`                         | Exige en plus la permission `admin: ["access"]`, sinon redirige vers `/app`                                |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Envoie un utilisateur connecté vers `redirect`, ou vers `/admin` ou `/app` selon son rôle                  |
| `redirectAfterAuth`  | `/auth/callback`                 | Exige une session, puis redirige vers `redirect` ou vers l'espace de travail correspondant au rôle         |
| `redirectIfVerified` | `/auth/verify-email`             | Envoie une session dont l'adresse est confirmée vers `redirect`, ou vers `/admin` ou `/app` selon son rôle |

Les gardes chargent la session via le cache de requêtes et, lorsque l'utilisateur connecté change, suppriment avec `removeUserData` de `auth.session.ts` chaque requête en cache qui n'est pas publique. [Sessions](/docs/features/sessions#cached-data-and-the-signed-in-account) explique comment elles savent à qui appartiennent les données du cache.

## Fonctions serveur

Les gardes de page ne protègent que la navigation ; chaque fonction serveur protégée vérifie donc à nouveau l'appelant avec le middleware de `auth.middleware.ts` :

- `authorized(permission?)` exige une session, vérifie éventuellement une permission et ajoute la session au contexte sous la forme `context.auth`. Les opérations sur les propres données de l'appelant utilisent `context.auth.user.id`, jamais un identifiant d'utilisateur provenant de l'entrée.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (<RepositoryFact name="sensitiveRateLimit" /> requêtes par <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) ou `RATE_LIMITS.TOKEN` (<RepositoryFact name="tokenRateLimit" /> par <RepositoryFact name="rateLimitWindowSeconds" unit="second" />) limite une opération publique par adresse IP cliente, lue dans `cf-connecting-ip`.
- `withRequest`, que les deux incluent, convertit les erreurs en codes `AppError` : les erreurs Better Auth deviennent `AUTH_API_ERROR` avec leur clé d'erreur, les erreurs Zod deviennent `VALIDATION`, et les erreurs inattendues sont journalisées puis renvoyées sous la forme `INTERNAL_ERROR`.

## Rôles et permissions

`auth.roles.ts` définit deux rôles : `admin` et `customer` (le rôle par défaut des nouveaux comptes). `auth.access.ts` définit les déclarations de chaque ressource dans `APP_STATEMENTS` : `admin` et `settings` pour la console d'administration et ses paramètres, `product` pour la page des produits, qui liste le catalogue Polar, et pour le module des produits, `category` pour les cas d'usage du module des catégories, qu'aucun écran n'utilise, `course` et `video` pour les cours, et `order` pour les commandes. Il les accorde toutes aux administrateurs, qui reçoivent aussi les déclarations d'administration de Better Auth, et construit à partir d'elles le contrôle d'accès et les rôles. `hasPermission({ permission, role })` est partagée par les gardes, le middleware et l'interface. Voir [Rôles et permissions](/docs/guides/roles-and-permissions).

## Plugins

`plugins`, dans `auth.server.ts`, liste chaque plugin Better Auth, dans l'ordre où Better Auth les applique :

| Plugin                    | Ce qu'il ajoute                                                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `admin`                   | L'administration des utilisateurs et des sessions, avec `ac` et `ROLES` de `auth.access.ts`                                                            |
| `twoFactor`               | L'authentification à deux facteurs                                                                                                                     |
| `lastLoginMethod`         | Le cookie qui retient la dernière méthode de connexion                                                                                                 |
| `invitationPlugin`        | Les invitations (`src/modules/invitation/invitation.plugin.ts`)                                                                                        |
| `haveIBeenPwned`          | La vérification des fuites de données pour chaque nouveau mot de passe (`NEW_PASSWORD_PATHS`)                                                          |
| `password-change-notice`  | `notifyPasswordChange` après un changement de mot de passe                                                                                             |
| `license-retention`       | Le hook `user.delete.before` qui révoque la licence d'un compte supprimé                                                                               |
| `polar`                   | Le plugin Polar, avec le portail client et les webhooks, qui transmettent chaque événement à `handlePolarEvent` ([Paiements](/docs/features/payments)) |
| `polar-verified-customer` | `requireVerifiedEmail` avant chaque endpoint sous `/customer/`                                                                                         |
| `tanstackStartCookies`    | Pose les cookies de Better Auth sur les réponses de TanStack Start, et doit venir en dernier                                                           |

Chaque plugin est écrit en toutes lettres dans la liste, si bien que les types de Better Auth incluent les champs d'utilisateur et de session que chacun ajoute. Un élément qui nomme un fichier d'une fonctionnalité, comme `revokeAccountLicense` ou `polarCore`, disparaît avec cette fonctionnalité, tout comme `[ROUTES.API_AUTH_POLAR.WEBHOOKS]: false` dans `rateLimit.customRules`, qui tient les livraisons de Polar à l'écart du limiteur de débit de Better Auth.

## E-mails et limitation de débit

Les hooks d'e-mail appellent directement les expéditeurs des modules verification, account et user, car l'authentification a besoin de l'e-mail : `sendVerifyEmail`, `sendExistingAccountEmail`, `sendResetPasswordEmail`, `sendPasswordChangedEmail`, `sendDeleteAccountEmail` et `sendChangeEmailConfirmationEmail`. Le limiteur de débit propre à Better Auth stocke ses compteurs dans la table D1 `rate_limit` sous un préfixe `auth:` via `consumeRateLimit` de `src/lib/rate-limit.ts`, qui utilise des upserts atomiques et rejette les requêtes lorsque son stockage est indisponible. `clientAddress` dans `auth.middleware.ts` détermine le client d'une requête comme le fait ce limiteur, à partir de `cf-connecting-ip`, en regroupant les adresses IPv6 par /64. Le préfixe des cookies est `APP_SLUG`, issu de l'identité visuelle. `getRequestSession` contourne le cache du cookie, de sorte que l'autorisation lit toujours la session dans D1.
