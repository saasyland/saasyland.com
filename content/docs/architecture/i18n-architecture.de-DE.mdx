## Locales und URLs

SaaSy Land liefert neun Locales aus: en-US (Standard), de-DE, es-ES, fr-FR, it-IT, ja-JP, pl-PL, pt-BR und uk-UA. Die Standard-Locale hat kein Präfix (`/docs`); jede andere Locale verwendet ihr vollständiges Tag (`/pl-PL/docs`). Der Worker leitet reine Sprachpräfixe und Präfixe der Standard-Locale wie `/pl/docs` oder `/en-US/docs` auf die kanonische URL um.

`getCurrentLocale()` ist isomorph. Auf dem Server liest die Funktion die URL, bei `/api`- und Server-Function-Requests dagegen das Locale-Cookie. Im Browser liest sie die URL. Der Worker hält das Cookie mit der URL der Seite synchron. Server Functions, die lokalisierte Inhalte zurückgeben, erhalten die Locale als Eingabe, statt sich auf das Cookie zu verlassen.

## Nachrichten

Übersetzungen liegen in `messages/<locale>/<namespace>.json`. Der Dateiname ist der Namespace, zum Beispiel `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` oder `common`. Namespaces mit Punkten werden zu einem gemeinsamen Nachrichtenbaum zusammengeführt, sodass `useTranslations("pages.admin.users")` die Datei `pages.admin.users.json` liest. Jeder Seiten-Namespace enthält `metadata.title` und `metadata.description` für die Head-Tags. Nachrichten sind einfaches JSON ohne generierte Typen.

## Laden

- **Root-Namespaces** (`common`, `components.*`, `errors*`) werden im Root-`beforeLoad` vorgeladen.
- **Seitenrouten** deklarieren `const NAMESPACE = "pages.x"`, laden den Namespace im Loader vor und führen ihn in `staticData.namespaces` auf.
- **Layout-Routen** deklarieren `const NAMESPACES = [...] as const` und gehen genauso vor.
- **`TranslationsProvider`** umschließt den Body des Dokuments in der Root-Shell. Er kombiniert die Root-Namespaces mit den `staticData.namespaces` der passenden Routen und übergibt das Ergebnis an `IntlProvider`, sodass jeder Bildschirm übersetzt ist, auch Fehlerbildschirme.
- **E-Mails** laden ihren Namespace auf dem Server mit `loadNamespace`, und zwar in dem Use Case, der sie versendet.

## Links

Router-Links brauchen keine Locale-Behandlung: `<Link to={ROUTES.SIGN_IN}>` erhält das Präfix über das `rewrite` des Routers. `localizePathname` ist nur für rohe URLs gedacht, die den Router umgehen, etwa `callbackURL`-Werte für Better Auth, Links in E-Mails und von Hand gebaute `<a href>`-Elemente:

```ts
const callbackURL = localizePathname({ locale: getCurrentLocale(), pathname: `${ROUTES.VERIFY_EMAIL}?verified=true` })
```

Der Locale-Switcher rendert einen einfachen Link auf denselben Pfad in jeder Locale, sodass ein Sprachwechsel ein neues Dokument lädt.

## Übersetzungen in Komponenten

Eine Komponente ruft `useTranslations` genau einmal auf und nennt die Übersetzungsfunktion `t`. i18n-ally ordnet jeden `t()`-Aufruf nach einem späteren `useTranslations`-Aufruf einem neuen Scope zu, und `bun run check:i18n` schlägt bei Keys fehl, die sich in ihrem Scope nicht auflösen lassen. Eine Komponente, die zwei voneinander unabhängige Namespaces braucht, verwendet deren gemeinsamen übergeordneten Namespace oder `useTranslations()` mit vollständigen Keys.

`bun run check:i18n` führt drei Skripte aus: `check-i18n.ts` (Key-Parität zwischen den Locales und Auflösung der Keys im jeweiligen Scope), `check-message-formats.ts` (ICU-Nachrichtensyntax) und `check-content.ts` (Parität von Dokumentation und Blog zwischen den Locales).
