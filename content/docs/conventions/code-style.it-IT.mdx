`bun run check` esegue `vp check`, che in un unico passaggio formatta con oxfmt, analizza con oxlint e controlla i tipi con TypeScript, con la configurazione in `vite.config.ts` e `tsconfig.json`. La CI esegue lo stesso comando. Niente qui è una questione di gusti: se gli strumenti accettano codice che viola una regola di questa pagina, la revisione lo rifiuta.

## Cosa impongono gli strumenti

oxlint tratta come errori le categorie `correctness`, `nursery`, `pedantic`, `perf`, `style` e `suspicious`, con le regole basate sui tipi e il controllo dei tipi attivati. I limiti che più influenzano il codice:

| Regola                       | Impostazione                                                            | Effetto                                                   |
| ---------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| `max-lines`                  | 800                                                                     | Dividi un file per responsabilità prima che cresca        |
| `max-lines-per-function`     | 150                                                                     | Componenti e handler restano piccoli                      |
| `max-statements`             | 20                                                                      | Estrai helper con un nome invece di scrivere corpi lunghi |
| `no-magic-numbers`           | ammesso solo `0`, oltre agli indici degli array e ai valori predefiniti | Ogni altro numero è una costante con un nome              |
| `id-length`                  | almeno due caratteri, tranne `_`, `m` e `t`                             | Gli identificatori sono parole; `t` è il traduttore       |
| `one-var`                    | `never`                                                                 | Una dichiarazione per istruzione                          |
| `unicorn/no-null`            | attiva fuori dai test e da `src/platform/testing`                       | I valori assenti sono `undefined`                         |
| `typescript/no-explicit-any` | `error`                                                                 | Nessun valore è tipizzato `any`                           |

Gli override sono mirati e limitati a determinati file: i test e gli helper di test condivisi in `src/platform/testing` rilassano `no-magic-numbers`, `no-await-in-loop` e `unicorn/no-null`; `src/presentation` e `src/hooks` rilassano `typescript/consistent-return`; i mock dei test rilassano `require-await`; `src/routes` disattiva `sort-keys`, perché le opzioni delle route seguono un proprio ordine (vedi [File di route](/docs/conventions/routes)).

`tsconfig.json` aggiunge i flag rigorosi che cambiano il modo di scrivere il codice: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` e `noUnusedParameters`. Una lettura tramite indice può essere `undefined`, una proprietà opzionale non può essere impostata esplicitamente a `undefined` e una firma di indice si legge come `record["key"]`.

Il formatter scrive senza punti e virgola, con virgolette doppie, virgole finali e una larghezza di 140 caratteri. Ordina anche gli import in gruppi fissi, le classi Tailwind in `className` e nelle chiamate a `cn`, e gli script di `package.json` per nome (`sortPackageJson: { sortScripts: true }`), quindi non ordinare mai nessuno di questi a mano: `vp check` fallisce quando uno è fuori ordine. Vedi [Lint e formattazione](/docs/tooling/lint-format) per i comandi.

## Niente commenti

Non scrivere commenti: né in TypeScript, TSX, test, script, configurazione o CSS, e nemmeno per spiegare un vincolo non ovvio. Il significato lo porta invece un nome, e il ragionamento va nel messaggio di commit, nella pull request o in questa documentazione.

```ts
const SINGLE_ROW_LIMIT = 1
const LAST_INDEX_OFFSET = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

Le prime due vengono da `get-course-editor.ts` e `course-columns.tsx`, la terza da `vite.config.ts`: ognuna avrebbe altrimenti bisogno di un commento. I file generati (`src/routeTree.gen.ts`, `src/types/worker-configuration.d.ts`) sono esenti. Prima del commit, cerca nel tuo diff `//`, `/*` e `{/*`.

## Niente scappatoie

Non scrivere mai `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, un cast con `as` o `any` per far passare una regola. Una regola che scatta indica un problema di design; cambia il design.

- **Valida invece di asserire.** I dati provenienti dallo storage, dalla rete o da una richiesta vengono analizzati con Zod: `src/lib/github.ts` legge il numero di stelle in cache con `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, che è un numero o `undefined`, mai un'ipotesi.
- **Restringi con un type guard.** `isRole` in `src/integrations/better-auth/auth.access.ts` e `isErrorCode` in `src/hooks/use-error-message.ts` trasformano una `string` in una union con un controllo reale.
- **Verifica, non convertire.** `as const` e `satisfies` sono ammessi perché non cambiano mai un tipo: `POLAR_ORDER_STATUS` termina con `as const satisfies Record<string, models.OrderStatus>`, quindi uno stato di Polar scritto male non compila.
- **Ristruttura quando il contratto di una libreria ti ostacola.** Avvolgi un valore in un oggetto, dividi una funzione o leggi da una sorgente tipizzata invece di fare un cast.

## Null e undefined

Fuori dai test e da `src/platform/testing`, un valore assente è `undefined` e `null` non viene mai scritto come valore. Il linter lo consente dove lo impone un'API: nel confronto con un valore che può essere `null`, come una colonna nullable (`entry.completedAt !== null` in `get-course.ts`), e in un ref DOM di React, che parte da `useRef<HTMLElement>(null)` perché React tipizza `ref` come `RefObject<T | null>` e lo riporta a `null` allo smontaggio (`course-showcase.tsx`). Non fare mai da ponte con `?? undefined` verso un'API che restituisce `null`. Valida prima l'input, così la chiamata non può fallire, oppure usa un parser che restituisce già `undefined`. I parametri di ricerca sono il caso più comune, e `searchParam(schema)` in `src/lib/search-params.ts` restituisce `undefined` per un valore mancante o malformato:

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Ternari e return anticipati

Un ternario sta su una riga, come `{t(course === undefined ? "create" : "save")}` in `course-form.tsx`. Qualsiasi cosa più lunga, e ogni scelta tra due blocchi di JSX, diventa un return anticipato, una coppia di condizioni `&&` o un piccolo componente. `src/routes/auth.reset-password.tsx` rende i suoi due stati con due condizioni:

```tsx
{resetToken !== undefined && <ResetPasswordForm token={resetToken} />}
{resetToken === undefined && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

Le funzioni escono subito per i casi speciali e mantengono il percorso principale senza rientro, come fa `hasLessonAccess` in `src/modules/lesson/lesson.access.ts`:

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.licensed
}
```

## Costanti con un nome

I numeri diversi da `0` hanno un nome (`COURSE_STALE_MS = 60_000`, `SAVE_INTERVAL_MS = 15_000`). I valori che appartengono al dominio, come stati, tipologie, livelli di accesso, piani, ruoli e valori degli eventi dei provider, vengono dichiarati una sola volta come oggetto `as const` e richiamati per nome ovunque, compresi test e fixture:

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

La tupla di cui ha bisogno una colonna o uno schema enum si costruisce dall'oggetto, senza riscriverla: `course.schema.ts` dichiara `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, che alimenta sia `text("status", { enum: COURSE_STATUSES })` sia `zod.enum(COURSE_STATUSES)`. Una tupla che legge anche il codice del browser si dichiara invece nelle costanti del modulo, che non importano nulla da Drizzle: la tabella dei prezzi itera `LICENSE_TIERS` da `license.constants.ts`.

- Le costanti di un modulo si trovano nel suo `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`); i valori di un provider si trovano nel `*.constants.ts` dell'integrazione (`POLAR_ORDER_STATUS` in `polar.constants.ts`, `AUTH_PROVIDER` in `auth.constants.ts`, `EMAIL_PURPOSE` in `resend.constants.ts`).
- Le lunghezze delle colonne e degli input ricevono un nome una sola volta, nelle costanti del modulo, e le leggono sia lo schema Drizzle sia lo schema Zod: `PRODUCT_NAME_MAX_LENGTH` in `product.constants.ts`.
- Un concetto ha una sola mappa con un solo stile di maiuscole: `ERROR_CODES` per gli errori del server, `AUTH_ERRORS` per le chiavi di errore di Better Auth, `ROLE_CODES` per i ruoli.
- I nomi degli ambienti e i codici di stato HTTP si dichiarano una sola volta, in `src/modules/_core/constants/api.ts`: `ENVIRONMENT.PRODUCTION` in `__root.tsx` e negli script di deploy, `HTTP_STATUS.PARTIAL_CONTENT` nel gestore dei media del Worker. Nessun file dichiara una propria mappa per nessuno dei due. L'unica eccezione è `vite.config.ts`, che confronta `mode` con i nomi semplici: Vite carica la configurazione prima di risolvere l'alias `~`, quindi non può importare `api.ts`.
- Una costante usata da un solo file resta in quel file, sotto gli import. Una costante usata da più file va nel suo modulo, in `src/data` (vedi [File e nomi](/docs/conventions/files-and-naming)) o in `src/modules/_core/constants`. Non dare mai a una costante un file tutto suo.
- I nomi dei campi tipizzati di un'API, come `license_key_id`, sono proprietà, non valori, e restano accessi a proprietà.

## Hook nei componenti

Le chiamate a hook che restituiscono un singolo valore vengono prima, poi una riga vuota, poi ogni risultato di hook destrutturato, così i valori che un componente scompone si leggono come un gruppo a sé. `src/presentation/components/custom/auth/sign-in-form.tsx`:

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Un componente chiama `useTranslations` una sola volta e chiama il risultato `t`; vedi [Traduzioni e contenuti](/docs/conventions/translations) per il motivo.

## Nomi e import

- File e cartelle sono in kebab-case; i componenti sono in PascalCase; le costanti in SCREAMING_SNAKE_CASE; le funzioni iniziano con un verbo (`resolveViewer`, `rethrowAsConflict`); i booleani si leggono come domande (`isPending`, `hasLessonAccess`).
- Gli import usano l'alias `~/src/...` e provengono dal file che definisce il simbolo. Non esistono barrel file che riesportano una cartella; l'unico file di riesportazione è `src/integrations/drizzle-orm/drizzle.schemas.ts`, perché Drizzle ha bisogno di tutte le tabelle in un unico oggetto schema.
- Anche l'aritmetica sugli indici ha un nome: `index + NEXT` in `course.utils.ts`, mai `slice(i + 1, -5)`.
