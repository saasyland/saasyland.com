Дані потрапляють на екран через TanStack Query. Сценарій використання експортує свої опції поруч із серверною функцією, а loader маршруту, компонент і тест використовують ті самі опції, тож за побудовою мають спільний запис у кеші.

## Опції запиту

```ts
export const courseEditorQuery = (input: Course["getCourseEditor"]) =>
  queryOptions({
    queryFn: () => getCourseEditor({ data: input }),
    queryKey: [...COURSE_QUERY_KEYS.EDITOR, input.courseId],
    staleTime: COURSE_STALE_MS,
  })
```

| Вид читання                          | Що експортується                                                     | Приклад                                          |
| ------------------------------------ | -------------------------------------------------------------------- | ------------------------------------------------ |
| Приймає вхідні дані                  | Функція, що повертає опції, з назвою `<noun>Query`                   | `courseEditorQuery(input)`, `courseQuery(input)` |
| Не приймає вхідних даних             | Константа з назвою `<noun>Query`                                     | `currentLicenseQuery`                            |
| Посторінковий список для `DataTable` | `get<Things>PageQuery(input)` і перша сторінка як `get<Things>Query` | `getCoursesPageQuery`, `getCoursesQuery`         |

## Ключі запитів

Ключ починається з префікса модуля з `<table>.constants.ts`, далі йде операція, а потім усі вхідні дані, що змінюють результат:

```ts
queryKey: [...COURSE_QUERY_KEYS.CATALOGUE, input.locale]
queryKey: [...COURSE_QUERY_KEYS.DETAIL, input.locale, input.slug]
queryKey: [...COURSE_QUERY_KEYS.LIST, courseZodSchemas.getCourses.parse(input)]
```

Ключ списку зберігає розібрані вхідні дані, тож `getCoursesPageQuery()` і `getCoursesPageQuery({ pageIndex: 0, pageSize: 10 })` вказують на той самий запис. Локаль належить до ключа щоразу, коли сервер локалізує результат. Ніколи не пишіть ключ безпосередньо в компоненті: беріть його з опцій або, для інвалідації, з об’єкта `<MODULE>_QUERY_KEYS`.

## Актуальність

`getRouter()` у `src/router.tsx` створює один `QueryClient` на запит із такими налаштуваннями за замовчуванням, а роутер використовує ту саму хвилину:

```ts
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      gcTime: FIVE_MINS_IN_MS,
      staleTime: ONE_MIN_IN_MS,
    },
  },
})
```

Запит, якому потрібна інша актуальність, задає `staleTime` іменованою константою, що пояснює причину: `PLAYBACK_STALE_MS` (година, у межах терміну дії підписаної URL-адреси відтворення), `REFRESH_AFTER_MS` для кількості зірок GitHub, `Infinity` для повідомлень перекладу, які змінюються лише з розгортанням. Ніколи не створюйте `QueryClient` на рівні модуля: на сервері він передав би дані одного користувача наступному запиту.

## Loader-и завантажують наперед, компоненти читають

Loader сторінки заздалегідь завантажує запити, які читають її компоненти, усередині єдиного `Promise.all`, описаного на сторінці [Файли маршрутів](/docs/conventions/routes). З `src/routes/app.license.tsx`:

```ts
context.queryClient.query({ ...currentLicenseQuery, staleTime: "static" })
```

`staleTime: "static"` змушує loader повертати будь-які кешовані дані замість повторного завантаження. Потім компонент читає ті самі опції й застосовує власний `staleTime` запиту:

```tsx
const { license } = useSuspenseQuery(currentLicenseQuery).data
```

Тож сторінка, дані якої вже є в кеші, після переходу рендериться одразу, а застарілі дані оновлюються у фоні, не затримуючи навігацію.

Читання `"static"` також ігнорує інвалідацію: воно повертає кешовані дані навіть після того, як мутація їх інвалідувала, а свіжі дані надходять лише тоді, коли компонент завантажить їх повторно. Тому loader натомість чекає на запит із власним `staleTime` запиту, коли сторінка ніколи не повинна показувати дані, старіші за щойно виконану відвідувачем дію, або коли самому loader потрібні дані — для заголовка чи щоб відповісти 404. Так роблять сторінки курсів і редактор курсу в адмінці, бо після завершення уроку чи збереження в редакторі наступний екран має показати оновлену програму:

```ts
context.queryClient.query(courseQuery({ locale, slug: params.course })).catch(rethrowAsNotFound)
```

- Використовуйте `useSuspenseQuery` для даних, які loader завантажив наперед, а `useQuery` — лише для даних, які можуть надійти пізніше, не блокуючи сторінку, як-от кількість зірок у `proof-section.tsx`.
- Не завантажуйте дані в `useEffect` і не передавайте результати запитів униз через властивості: кожен компонент сам викликає потрібні йому опції.
- `DataTable` отримує функцію, яка перетворює стан сторінки на опції, `options={{ query: ({ pageIndex, pageSize }) => getCoursesPageQuery({ pageIndex, pageSize }) }}`, і сам виконує запит.

## Мутації та інвалідація

Компонент розгортає опції мутації в `useMutation` і додає лише власні колбеки. Після успішного запису він інвалідує префікс модуля, а потім показує відгук:

```tsx
const update = useMutation({
  ...updateCourseMutation,
  onError,
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL })
    toast.success(t("saved"))
  },
})
```

- Інвалідуйте найвужчий префікс, що охоплює всі екрани, які показують змінені дані. Мутації розділів і уроків інвалідують `COURSE_QUERY_KEYS.ALL`, бо їх показують редактор курсу й публічні сторінки курсів. `useLessonProgress` інвалідує лише `COURSE_QUERY_KEYS.DETAIL` і лише тоді, коли урок завершено.
- Дочекайтеся інвалідації, перш ніж переходити на іншу сторінку чи закривати діалог, щоб наступний екран рендерив свіжі дані.
- Помилки проходять через `useErrorMessage()`; див. [Серверні функції та помилки](/docs/conventions/server-functions).
- Ніколи не оновлюйте кеш вручну, щоб підробити результат. Єдиний виняток — сесія: `loadRouteSession` в `auth.routes.ts` очищає весь кеш, коли змінюється користувач, який увійшов, тож жодні приватні дані не переживають вихід чи зміну облікового запису.
