Vite+ (`vite-plus`, comando `vp`) reúne Vite, Vitest, oxlint y oxfmt en una sola CLI, y `vite.config.ts` los configura todos. `package.json` sobrescribe `vite` con `@voidzero-dev/vite-plus-core` y fija `vitest` en la versión 5.1.0. `vite-plus` también está fijado a una versión exacta; actualiza los tres a la vez con `vp migrate`, no con `bun update`. Los scripts del paquete llaman a `vp`; fuera de ellos, usa la CLI global de Vite+ o `bunx vp`.

| Comando           | Usado por                                         |
| ----------------- | ------------------------------------------------- |
| `vp dev`          | `dev`                                             |
| `vp build --mode` | `build:preview`, `build:production`, `build:test` |
| `vp preview`      | `start`, `start:test`                             |
| `vp test`         | `test` y los scripts de Vitest `test:*`           |
| `vp lint`         | `lint`                                            |
| `vp fmt`          | `format`, `format:check`                          |
| `vp check`        | `check`, `check:fix`                              |
| `vp staged`       | `check:pre-commit`                                |
| `vp config`       | `prepare`, que instala los hooks de Git           |

## Configuración

`vite.config.ts` enumera sus plugins en `VITE_PLUGINS` y los carga de forma diferida, y cada entrada importa su paquete dentro de `load`; los plugins de un proveedor vienen de `src/integrations/<vendor>/<vendor>.vite.ts` (consulta [Lo que ejecutan el Worker y el build](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)). Con Vitest solo se cargan las entradas marcadas con `vitest`, es decir, `contentIndexes()`, `repositoryFacts()` y `@vitejs/plugin-react`; en los demás casos, la pila es:

- `@cloudflare/vite-plugin`: ejecuta el Worker en el entorno de SSR y conserva el estado local (en `.wrangler/test` para el modo `test`, en `.wrangler/state` en los demás), con `remoteBindings: false`, así que ni el servidor de desarrollo ni la compilación de ningún entorno se conectan a un binding remoto.
- `fumadocs-mdx`: compila las colecciones de documentación y de blog.
- `saasyland:fumadocs-bundled`: mantiene `fumadocs-core` y `@fumadocs/base-ui` dentro del bundle del servidor (`resolve.noExternal`). Viene, junto con `fumadocs-mdx`, de `fumadocsVitePlugins` (`src/integrations/fumadocs/fumadocs.vite.ts`).
- `contentIndexes` (`scripts/content-indexes.ts`): sirve `virtual:content-indexes` y `virtual:docs-search`, los índices de la documentación, del blog y de búsqueda que `fumadocs.indexes.ts` construye a partir de `content/docs` y `content/blog`; consulta [Fumadocs](/docs/integrations/fumadocs#content-indexes).
- `repositoryFacts` (`scripts/repository-facts.ts`): sirve el módulo `virtual:repository-facts`, con las cifras, las versiones y los ajustes de herramientas que muestran la página de inicio y la documentación, y el módulo `virtual:repository-tables`, con las tablas que solo muestra la documentación, ambos leídos del repositorio durante el build; consulta [Traducciones y contenido](/docs/conventions/translations) y [Rendimiento](/docs/conventions/performance#repository-tables-load-with-the-docs).
- `unused-primitives` (`scripts/unused-primitives.ts`): antes de Tailwind, deja fuera las clases de cada primitiva de shadcn que no importa ningún código de la aplicación; consulta [Componentes de shadcn](/docs/ui/shadcn-components).
- `@tailwindcss/vite`: Tailwind CSS 4.
- `tanstackStart`: enrutamiento, división de código y prerenderizado de las páginas públicas, filtrado por `shouldPrerender` (`src/lib/prerender.ts`).
- `@vitejs/plugin-react`.
- `saasyland:zod-config-chunk` (`src/integrations/zod/zod.vite.ts`): en el build del cliente, coloca `src/integrations/zod/zod.config.ts` en el chunk propio de zod, para que zod se ejecute en modo `jitless` antes de que cualquier chunk construya un esquema y nunca compruebe si `eval` está disponible bajo la Content Security Policy; consulta [Seguridad y endurecimiento](/docs/features/security).
- `deployedWorker` (`scripts/deployed-worker.ts`): vuelve a compilar el Worker después del prerenderizado sin las páginas compiladas de la documentación y del blog y sin las traducciones de la landing y de las páginas legales; consulta [Cloudflare Workers](/docs/integrations/cloudflare-workers).
- `saasyland:polar-sdk-optional-peers`: marca como externas las dependencias peer opcionales de `@polar-sh/sdk` que no están instaladas (`build.rolldownOptions.external`); consulta [Dependencias](/docs/conventions/dependencies).

El servidor de desarrollo escucha en `localhost:3000` y falla si el puerto está ocupado. `resolve.tsconfigPaths` proporciona el alias de importación `~/`. El mismo archivo contiene las secciones `fmt`, `lint`, `staged` y `test`; consulta [Lint y formato](/docs/tooling/lint-format) y [Pruebas](/docs/tooling/testing).

`vp preview`, que ejecutan `start`, `start:test` y el prerenderizado, escucha en `127.0.0.1:3000`, la dirección `LOCAL_SERVER` de `src/data/local-server.ts`, y Playwright abre esa dirección; el prerenderizado usa la misma dirección con un puerto libre. Con `localhost`, el servidor solo escucharía en la primera dirección a la que Node resuelve el nombre, `::1`, y cada cliente probaría `::1` y luego `127.0.0.1`, con poco tiempo para que cada una responda: en una máquina ocupada ese tiempo se agota antes de que el cliente vea la conexión, el cliente abandona `::1`, no encuentra nada en `127.0.0.1` y el prerenderizado se detiene con `ETIMEDOUT ::1` y `ECONNREFUSED 127.0.0.1`.

`polarVitePlugins`, en `src/integrations/polar/polar.vite.ts`, devuelve un plugin cuyo hook `config` enumera en `build.rolldownOptions.external` las dependencias peer opcionales de `@polar-sh/sdk` (OpenTelemetry e `ioredis`). No están instaladas, y el módulo que las importa se elimina del Worker mediante tree-shaking.

## Hooks de Git

`bun install` ejecuta `prepare`, que llama a `vp config --no-agent` para instalar el despachador de hooks de `.vite-hooks/` y después a `scripts/verify-git-hooks.ts`, que hace fallar la instalación cuando Git no ejecutaría ese despachador. `pre-commit` ejecuta `bun run check:pre-commit`, `prepare-commit-msg` ejecuta `scripts/commit-msg.ts` y `commit-msg` ejecuta `scripts/verify-commit-msg.ts` (consulta [Commits convencionales](/docs/tooling/conventional-commits)), y `post-checkout` ejecuta `vp hooks enable` en un checkout que aún no tiene despachador, como un worktree que `git worktree add` acaba de crear. `post-merge`, `post-checkout` y `post-rewrite` ejecutan `bun install --frozen-lockfile` cuando `bun.lock` ha cambiado, así que un pull, un rebase o un cambio de rama nunca dejan `node_modules` desactualizado. `vp hooks status` muestra si los hooks están activos en un clon, y [Git y pull requests](/docs/conventions/git-workflow#hooks-in-every-worktree) explica por qué cada worktree necesita su propio despachador.

Dé preferencia a los scripts del paquete; llame a `vp` directamente para ejecuciones concretas, como formatear o analizar rutas específicas.
