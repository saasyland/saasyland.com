Role i uprawnienia są zdefiniowane w `src/integrations/better-auth/auth.access.ts` za pomocą mechanizmu kontroli dostępu Better Auth. Z tych samych definicji korzysta serwer (`authorized`, guardy tras) i klient Better Auth.

## Role

| Rola          | Kod        | Uprawnienia                                                                                                |
| ------------- | ---------- | ---------------------------------------------------------------------------------------------------------- |
| Administrator | `admin`    | Wszystkie poniższe deklaracje aplikacji oraz administracyjne deklaracje Better Auth dla `user` i `session` |
| Klient        | `customer` | Brak. Klienci mogą wywoływać funkcje serwerowe, które wymagają jedynie sesji.                              |

Nowi użytkownicy otrzymują rolę `customer` (`DEFAULT_ROLE_CODE`).

## Gdzie sprawdzane są uprawnienia

| Uprawnienie            | Sprawdzane przez                                                                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `admin: ["access"]`    | `requireAdmin` w layoucie `/admin` oraz przekierowanie po zalogowaniu                                                                                                                                                |
| Akcje `category`       | Przypadki użycia kategorii: `read`, `create`, `update`, `delete`                                                                                                                                                     |
| `course: ["read"]`     | `get-courses` i `get-course-editor`; poza tym `resolveViewer` (`lesson.viewer.ts`): posiadacze widzą każdą lekcję w `get-course`, `get-lesson-playback` i `save-lesson-progress`, niezależnie od jej poziomu dostępu |
| `course: ["create"]`   | `create-course`                                                                                                                                                                                                      |
| `course: ["update"]`   | `update-course`, `move-course` oraz zapisy rozdziałów i lekcji: `create-chapter`, `update-chapter`, `delete-chapter`, `move-chapter`, `create-lesson`, `update-lesson`, `delete-lesson`, `move-lesson`               |
| `course: ["delete"]`   | `delete-course`                                                                                                                                                                                                      |
| Akcje `product`        | Przypadki użycia produktów: `read`, `create`, `update`, `delete`                                                                                                                                                     |
| Akcje `video`          | `get-videos` i `get-video-playback` (`read`), `delete-video` (`delete`)                                                                                                                                              |
| Akcje `user`           | Przypadki użycia użytkowników, każdy z jedną akcją; `ban` obejmuje zarówno `ban-user`, jak i `unban-user`                                                                                                            |
| Akcje `session`        | `list-user-sessions` (`list`), `revoke-user-session` i `revoke-user-sessions` (`revoke`)                                                                                                                             |
| Sesja, bez uprawnienia | Przypadki użycia konta, licencji, uwierzytelniania dwuskładnikowego, preferencji newslettera i własnych sesji, `stop-impersonating-user` oraz `save-lesson-progress`                                                 |

`order`, `product: ["publish"]` i `settings` są zadeklarowane, ale nie sprawdza ich jeszcze żadna funkcja serwerowa.

## Sprawdzanie uprawnienia

Funkcje serwerowe korzystają z middleware, na przykład `authorized({ category: ["read"] })`. Pozostały kod wywołuje `hasPermission`, tak jak guardy tras:

```ts
const isAdmin = (role: string | null | undefined): boolean => hasPermission({ permission: { admin: ["access"] }, role })

export const requireAdmin = async (context: ProtectedRouteContext) => {
  const result = await requireSignedIn(context)
  if (!isAdmin(result.session.user.role)) {
    throw redirect({ replace: true, to: ROUTES.APP })
  }
  return result
}
```
