## 結論から

**Vercel を選ぶ**のは、Next.js で開発していてその機能を何も設定せずに使いたい場合、コミットごとのプレビューデプロイとそのレビューツールがチームにとって重要な場合、コードに完全な Node.js ランタイムが必要な場合、あるいはアプリの大半が CPU をあまり使わないページでトラフィックもほどほどの場合です。最後の場合、$20 のシートは、本来ならインフラに費やすはずの時間を買ってくれます。

**Cloudflare を選ぶ**のは、成長したときのコストが重要な場合、動画やダウンロードのような大きなファイルを配信する場合、リクエストが時間の大半をデータベースや AI モデルの応答待ちに費やす場合、あるいはコンピューティング、SQL データベース、キャッシュ、オブジェクトストレージを 1 つのアカウントと 1 つの請求書にまとめたい場合です。その代わりに、Node.js ではないランタイム、上限に合わせて設計しなければならない SQLite データベース、Cloudflare にしか存在しない API を受け入れることになります。

その判断の大部分は、次の 5 つの事実から来ています。

- **どちらも待ち時間ではなく CPU に課金します。** Vercel の Active CPU も Cloudflare の CPU 時間も、コードが I/O を待っている間はカウントを止めます。違いはその周辺のすべてです。Vercel は、リクエストが処理中である間ずっとプロビジョニングされたメモリにも課金し、さらに呼び出しと CDN トラフィックにも課金します。Cloudflare が課金するのはリクエストと CPU で、実時間（ウォールタイム）、メモリ、帯域幅には何も課金しません。
- **静的ファイルは Cloudflare では無料で、Vercel では計量されます。** Vercel の CDN が配信するファイルはすべて CDN リクエストになり、そのバイト数はデータ転送に数えられます。Workers では「静的アセットへのリクエストは無料で無制限」です。
- **Vercel はデフォルトで関数を 1 つのリージョンで実行し、Cloudflare は Worker をリクエストが届いた場所で実行します。** どちらが自動的に速いということはありません。重要なのは、コードがデータからどれだけ離れているかです。
- **どちらにも今では支出のハードリミットがありますが、遅れを伴います。** Vercel の一時停止の確認は数分ごとに行われ、Cloudflare の上限は 2026年11月13日にベータ版として提供が始まったもので、対象は Workers と Durable Objects だけです。
- **Vercel のデータベースは他社のものです。** Postgres と Redis は、Neon、Upstash、Supabase といった Marketplace のプロバイダーから提供されます。Cloudflare の D1、KV、R2、Queues、Durable Objects は Cloudflare 自身のもので、接続文字列ではなくバインディングを通じて使います。

## 2 つのマシン：それぞれのプラットフォームがコードをどう実行するか

料金も、上限も、意外な点のほとんども、アーキテクチャ上の 1 つの違いから生じています。そのため、数字を見る前に理解しておく価値があります。

### Vercel：Fluid compute 上の関数

Vercel Function は自分で選んだリージョンで動き、変更しなければワシントン D.C. の `iad1` です。その前には Vercel の CDN があり、[リージョンのページ](https://vercel.com/docs/regions)はこれを、プライベートネットワークを通じてコンピューティングに対応した 19 のリージョンへルーティングする、126 を超える PoP（拠点）と説明しています。Hobby は関数を 1 つのリージョンで、Pro は最大 3 つのリージョンで実行するので、シドニーの訪問者は、より近いリージョンを追加しない限りバージニアの関数にアクセスすることになります。Vercel 自身も「関数はデータベースと同じリージョンで実行すべき」と助言しています。

2025年4月23日以降、新しいプロジェクトは [Fluid compute](https://vercel.com/docs/fluid-compute) を使います。Fluid compute は、重要な 3 つの点でモデルを変えました。

- Node.js と Python のランタイムでは、**1 つのインスタンスが複数のリクエストを同時に処理します。** Vercel はこれを最適化された並行処理（optimized concurrency）と呼んでいます。あるリクエストのためにデータベースを待っているインスタンスが、別のリクエストを処理できるということです。
- **コールドスタートは減りましたが、なくなってはいません。** Vercel はコンパイル済みのバイトコードをキャッシュし、関数を事前にウォームアップしますが、どちらも本番のデプロイだけが対象で、プレビューデプロイにはどちらも適用されません。
- **各インスタンスは本物の Node.js プロセスです。** Vercel の上限のページには、「Node.js の完全なカバレッジ」、デフォルトで 1 vCPU と 2 GB のメモリ、Pro では最大 2 vCPU と 4 GB、そして非圧縮で最大 250 MB のバンドルが記載されています。

### Cloudflare：あらゆるロケーションにあるアイソレート

Worker は V8 アイソレートの中で動きます。Cloudflare のドキュメントによれば、アイソレートは「コンテナや仮想マシン上の Node プロセスよりも約 100 倍速く起動でき」、起動時に使うメモリは「1 桁少ない」ものです。選ぶべきリージョンはありません。「デフォルトでは、Workers と Pages Functions はリクエストを受けた場所に最も近いデータセンターで動く」とされ、Cloudflare はそのネットワークを数百のロケーションからなるものと説明しています。

その代償はランタイムにあります。アイソレートのメモリは 128 MB で、Worker のグローバルスコープは 1 秒以内に起動を終える必要があり、Node.js の API は Cloudflare が互換性フラグを通じて提供する一部だけです。また、アイソレートがどれだけ存続するかを決めることもできません。アイソレートは「必ずしも長く存続するわけではない」ので、モジュールレベルの状態は、ときどきしか機能しないキャッシュです。

### 2026年における「エッジ」の意味

Vercel には独自のアイソレートのランタイムである Edge ランタイムがありますが、そのドキュメントは今では「パフォーマンスと信頼性を高めるため、edge から Node.js への移行を推奨します」という一文で始まり、Next.js 16.3 からは「`runtime = 'edge'` の設定はサポートされなくなった」とされています。現在の Vercel で「エッジ」が指すのは、コードが動く場所ではなく、リージョンの関数の前にある CDN です。

Cloudflare では、コードはエッジで動きます。それが Cloudflare の強みと制約の両方の源です。「Vercel Edge Functions と Cloudflare Workers」を比較している記事は時代遅れで、2026年における公平な比較は、Node.js 上の Fluid compute と Workers の比較です。

## Vercel vs Cloudflare の料金：それぞれの課金の仕組み

### Vercel：プラットフォーム料金、シート、メーター

Vercel には 3 つのプランがあります。**Hobby** は無料で、毎月、関数の呼び出し 100 万回、Active CPU 4 時間、プロビジョニングされたメモリ 360 GB・時間、CDN リクエスト 100 万回、Fast Data Transfer 100 GB が含まれます。Vercel の規約には「Hobby プランのサービスは、個人的または非商用の利用にのみ使用するものとする」とあります。Hobby の上限を超えると Vercel はチームを一時停止し、訪問者には `503 DEPLOYMENT_PAUSED` が表示され、「ほとんどの場合」30 日待つことになります。**Enterprise** の料金は契約で決まります。

**Pro** はビジネスで使うプランです。その[プランのページ](https://vercel.com/docs/plans/pro-plan)には「月額 $20 の Pro プラットフォーム料金」が記載されており、デプロイできるシート 1 つと「月額 $20 の利用クレジット」が含まれます。デプロイできるシートを追加するごとに月額 $20 がかかり、閲覧者のシートは無料で、クレジットは「使わなければ月末に失効」します。Pro にはコンピューティングの無料枠がありません。クレジットが尽きるまではクレジットで支払われ、その後は従量課金になります。

[コンピューティングのメーター](https://vercel.com/docs/functions/usage-and-pricing)は、ワシントン D.C. の料金で次のとおりです。

- **Active CPU**：1 CPU・時間あたり $0.128 で、「実際にコードを実行している間だけ課金され、I/O 操作の間は課金されない」ものです。100 ms 計算してデータベースを 400 ms 待つリクエストは、100 ms 分が課金されます。
- **プロビジョニングされたメモリ**：1 GB・時間あたり $0.0106 で、いずれかのリクエストが処理中である間、「I/O 操作の間も含め」、「インスタンスの存続期間全体に対して課金」されます。同じリクエストでは、500 ms すべてについてメモリが課金されます。
- **呼び出し**：100 万回あたり $0.60 で、「リクエストの成否にかかわらず」カウントされます。

料金はリージョンによって異なります。フランクフルトは 1 CPU・時間あたり $0.184、1 GB・時間あたり $0.0152、サンパウロは $0.221 と $0.0183 です。

### Flat Rate CDN：帯域幅の請求に対する Vercel の答え

Vercel の請求のもう半分は配信です。これは 3 つのリソースからなります。静的ファイルを含め CDN が処理するすべてのリクエストである **CDN リクエスト**（「静的アセットと関数はすべて CDN Requests を発生させる」）、CDN と訪問者の間のバイト数である **Fast Data Transfer**、そして CDN と関数の間のバイト数である **Fast Origin Transfer** です。ワシントン D.C. の従量課金では、それぞれ 100 万リクエストあたり $2.00、1 GB あたり $0.15、1 GB あたり $0.06 です。

2026年9月8日、Vercel は [Flat Rate CDN](https://vercel.com/docs/pricing/flat-rate-cdn) の一般提供を開始し、新しい Pro チームではデフォルトで有効になっています。リクエストと転送に単位ごとの料金を払う代わりに、容量のティアに対して支払います。

| ティア         | 月あたりの CDN リクエスト | 月あたりのデータ転送 |
| -------------- | ------------------------- | -------------------- |
| Pro に含まれる | 100 万                    | 1 TB                 |
| 月額 $20       | 1,000 万                  | 50 TB                |
| 月額 $100      | 5,000 万                  | 50 TB                |
| 月額 $300      | 1 億 5,000 万             | 50 TB                |

急増によってティアを超えたトラフィックは、[発表](https://vercel.com/changelog/flat-rate-cdn-is-now-ga-for-pro-teams)の言葉では「通常どおり、パフォーマンスを落とさずに配信され、課金されない」ものです。超過が続く場合は、次の請求サイクルの開始時に次のティアに移ります。これには 2 つの注意点を添えておくべきです。Fast Origin Transfer は対象外なので、関数が返すバイト数は引き続き 1 GB 単位で課金されます。また、ティアは「メディアやファイルの大規模な配信で、その配信が帯域幅の使用量の大半を占めるもの」を対象としていないため、動画コースは定額料金の対象になりません。

知っておくべき食い違いが 1 つあります。2026年11月21日の時点で、Vercel の料金ページには Pro に 1,000 万 CDN リクエストが含まれると記載されていましたが、ドキュメントと 9 月の変更履歴には 100 万と記載されています。以下ではドキュメントの数字を使います。最終的な判断の基準は、自分のチームの請求ページです。

### Cloudflare：5 ドルと 2 つのメーター

[Workers Paid](https://developers.cloudflare.com/workers/platform/pricing/) には、シート単位ではなく「アカウントあたり月額 5 米ドルの最低料金」があります。毎月 1,000 万リクエストと 3,000 万 CPU ミリ秒が含まれ、それを超えると 100 万リクエストあたり $0.30、100 万 CPU ミリ秒あたり $0.02 が課金されます。料金ページは、実行時間（duration）について「料金も上限もなし」とし、「データ転送（エグレス）やスループット（帯域幅）に追加料金はかからない」と述べています。静的アセットへのリクエストは「無料で無制限」で、「上限と請求に数えられるのは Worker に到達したリクエストだけ」です。

ほかのプロダクトにも、同じ $5 の中にそれぞれの無料枠があります。

| --------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| D1              | 読み取り 250 億行、書き込み 5,000 万行、ストレージ 5 GB    | 読み取り 100 万行あたり $0.001、書き込み 100 万行あたり $1.00、1 GB・月あたり $0.75 |

キャッシュを追加する人が見落としやすい細かな点が 1 つあります。「Cloudflare Workers は Cloudflare のキャッシュより前に実行されるため、リクエストをキャッシュしてもコストは発生する」のです。Worker の中でのキャッシュヒットも課金されるリクエストであり、節約できるのは CPU だけです。

### サイドプロジェクト向けの無料プラン

どちらの無料プランも、販売しないものには十分な内容ですが、規模が大きくなって上限を超えたときの止まり方が異なります。

- **Vercel Hobby** には上記の無料枠が含まれ、「個人的または非商用の利用」のためのものです。チームが上限を超えるとデプロイが一時停止し、「一時停止した Hobby チームは自動的には再開しない」とされています。
- **Workers Free** では、UTC の午前 0 時にリセットされる 1 日 10 万リクエストと、リクエストあたり 10 ms の CPU が使えます。D1 は 1 日に読み取り 500 万行と書き込み 10 万行、合計 5 GB まで、KV は 1 日に読み取り 10 万回と書き込み 1,000 回までです。リクエストの上限を超えると「Cloudflare は Error 1027 を返す」か、ルートがフェイルオープンなら、Worker がないかのようにリクエストが素通りします。

注意すべきは 10 ms という CPU の上限です。1 行を読む API には十分ですが、リクエストのたびに React のページをサーバーサイドレンダリングするには厳しい値です。

### CPU 時間と実時間：最も重要な違い

どちらのプラットフォームも経過時間ではなく CPU に課金し、CPU 1 ミリ秒あたりの料金の差は 3 倍以内に収まります。1 CPU・時間あたり $0.128 は、ワシントン D.C. では 100 万 CPU ミリ秒あたり $0.0356、フランクフルトでは $0.0511 にあたり、Cloudflare は $0.02 です。

本当の違いは、コードが待っている間にそれぞれが何に課金するかです。Vercel では、プロビジョニングされたメモリのメーターが動き続けます。デフォルトの 2 GB では、その間ほかのリクエストがインスタンスを共有しない限り、リクエストが処理中である 1 秒ごとに約 $0.0000059、つまり 100 万リクエスト・秒あたり $5.89 がかかります。Cloudflare では、データベース、決済 API、言語モデルを待っている Worker は、待ち時間に対して何も支払いません。

そのため、表に出ている単価よりも、リクエストの形のほうが請求額を大きく左右します。

- **短く、CPU をあまり使わないリクエスト**（ページのレンダリング、インデックスを使うクエリの上の JSON API）は、どちらでもほとんどコストがかからず、Vercel でのリクエストごとのオーバーヘッドは主に呼び出しと配信です。
- **長い待ち時間**（AI の応答のストリーミング、遅いサードパーティの API、ほかのサービスを呼び出す Webhook）は、Vercel ではメモリの時間としてコストがかかり、Cloudflare では追加のコストはかかりません。Fluid compute では 1 つのインスタンス上の同時リクエストがそのメモリを共有するので影響は和らぎますが、メーターは動き続けます。
- **重い CPU 処理**（画像処理、PDF の生成、大きな JSON の変換）はどちらでも CPU のコストがかかり、それを 2 GB や 4 GB のメモリと完全な Node.js で実行できるのは Vercel だけです。

### CPU ミリ秒を見積もる方法

必要なのはリクエストの種類ごとに 1 つの数字で、何かを移行する前に手に入れられます。

1. **Cloudflare では、読み取ります。** ダッシュボードの Worker のメトリクスには、実行ごとの CPU 時間と実時間が分位数で表示されます。中央値が計画に使う数字で、高い分位数がリスクを表します。
2. **Vercel では、Observability でルートごとの Active CPU を読み取り**、同じルートの呼び出し回数で割ります。
3. **ノートパソコンでは、近似値を求めます。** ハンドラーの前後で `process.cpuUsage()` を呼んで囲み、ローカルのデータベースに対して数百回実行し、ユーザー時間とシステム時間の合計の中央値を取ります。ノートパソコン上の Node.js はエッジのアイソレートではないので、結果は見積もりとして扱い、プラットフォームの数字が手に入ったらそれに置き換えてください。
4. **待ち時間と処理時間を分けます。** 実時間から CPU 時間を引いたものが I/O の待ち時間で、Cloudflare では無料、Vercel ではメモリの時間として課金されます。

Cloudflare 自身の料金の例はリクエストあたり 7 ms の CPU を想定しており、短い API 呼び出しの最初の見積もりとしては妥当です。サーバーサイドレンダリングは通常それより多くかかり、大きなコンポーネントツリーや重いライブラリがあると何倍にもなりうるので、平均値を信じる前に自分のものを計測してください。

## 計算例：月 10 万、100 万、1,000 万リクエスト

同じ SaaS の 1 か月分の請求を 3 つの規模で示し、上記の料金でそれぞれのプラットフォームの金額を計算します。モデルはあえて単純にしてあるので、どの行でも変更できます。

### 前提

- **サーバーリクエスト：** コードを実行するリクエスト（ページのレンダリングと API 呼び出し）が月 10 万、100 万、または 1,000 万回。
- **CPU：** サーバーリクエストあたり 10 ms。**実時間：** 150 ms で、その大半はデータベースの待ち時間。
- **静的ファイル：** ブラウザーのキャッシュを経たうえで、サーバーリクエスト 1 回につき 4 つ、平均 50 KB ずつ。Cloudflare では Worker を経由せず、Vercel では CDN リクエストになります。
- **レスポンス：** サーバーリクエストあたり 30 KB。
- **データベース：** サーバーリクエストあたり読み取り 20 行、書き込み 0.2 行（5 リクエストに 1 回の書き込み）。
- **Vercel：** シート 1 つの Pro、ワシントン D.C. の料金、Flat Rate CDN は有効、関数はデフォルトの 2 GB で、インスタンスを共有するリクエストはないものとします。これはメモリのコストの上限にあたります。$20 のクレジットは従量課金分の支払いに充てられ、CDN のティアはそれとは別に課金されると仮定します。
- **Cloudflare：** Workers Paid、データベースは D1。

### Cloudflare の内訳

- **サーバーリクエスト 10 万回：** 10 万リクエストと 100 万 CPU ms は、含まれる 1,000 万と 3,000 万の範囲内です。D1 は 200 万行を読み取り、2 万行を書き込みます。**合計：$5.00。**
- **100 万回：** 100 万リクエストと 1,000 万 CPU ms で、どちらも無料枠の範囲内です。D1 は 2,000 万行を読み取り、20 万行を書き込みます。**合計：$5.00。**
- **1,000 万回：** 1,000 万リクエストで、ちょうど無料枠の量です。CPU は 1 億 ms で、超過分は 7,000 万 ms なので、70 × $0.02 = $1.40 です。D1 は 2 億行を読み取り、200 万行を書き込み、どちらも範囲内です。**合計：$6.40。**

### Vercel の内訳

サーバーリクエスト 100 万回あたり：呼び出し $0.60、Active CPU 1,000 万 ms = 2.78 時間 × $0.128 = $0.36、メモリ 2 GB × 0.15 秒 × 100 万 = 83.3 GB・時間 × $0.0106 = $0.88、Fast Origin Transfer 30 GB × $0.06 = $1.80。合わせて、サーバーリクエスト 100 万回あたり $3.64 の従量課金です。

- **10 万回：** 従量課金分は $0.36 で、$20 のクレジットの範囲内です。CDN：50 万リクエストと 23 GB で、含まれるティアの範囲内です。**合計：$20.00。**
- **100 万回：** 従量課金分は $3.64 で、クレジットの範囲内です。CDN：500 万リクエストと 230 GB で、含まれる 100 万リクエストを超えるので、安定したトラフィックによってチームは $20 のティアに移ります。**合計：$40.00。**
- **1,000 万回：** 従量課金分は $36.39 で、そのうち $20 をクレジットで支払います。CDN：5,000 万リクエストと 2.3 TB で、$100 のティアに収まります。**合計：$20 + $100 + $16.39 = $136.39。**

### 比較

| 月あたりのサーバーリクエスト | Cloudflare Workers Paid | Vercel Pro、シート 1 つ |
| ---------------------------- | ----------------------- | ----------------------- |
| 10 万                        | $5.00                   | $20.00                  |
| 100 万                       | $5.00                   | $40.00                  |
| 1,000 万                     | $6.40                   | $136.39                 |

この表に表れていないことが 3 つあります。

- **データベース。** Cloudflare の列には D1 が含まれています。Vercel の列にはデータベースが含まれていません。Marketplace のプロバイダーの Postgres は、そのプロバイダーが独自の料金で請求します。
- **シート。** Vercel でデプロイする開発者が 1 人増えるごとに月額 $20 が加わります。Workers Paid の料金はアカウント単位です。
- **その先。** サーバーリクエストが 1 億回になると、同じモデルで Cloudflare は $51.40 です。Vercel では 5 億 CDN リクエストが最大の定額ティアを超えるので、配信は従量課金になり、請求額の大半はコンピューティングではなく CDN リクエストと転送が占めるようになります。

アプリが月 10 万リクエストで開発者 1 人の、CPU をあまり使わない Next.js のサイトなら、$15 の差額で Next.js との統合、コミットごとのプレビュー、完全な Node.js ランタイムが手に入り、それは良い取引になりえます。この差が移行の理由になるのは、トラフィック、シート、大きなファイルが増えたときです。

### 自分の数字で計算し直す

```text
cloudflare = 5
  + max(0, requests - 10000000) * 0.30 / 1000000
  + max(0, requests * cpu_ms - 30000000) * 0.02 / 1000000
  + max(0, rows_written - 50000000) * 1.00 / 1000000

vercel_metered = requests * 0.60 / 1000000
  + requests * cpu_ms / 3600000 * cpu_hour_price
  + requests * memory_gb * wall_seconds / 3600 * gb_hour_price
  + response_gb * 0.06

vercel = 20 * seats + cdn_tier + max(0, vercel_metered - 20)
```

`cpu_hour_price` と `gb_hour_price` は Vercel の表の自分のリージョンの行から取り、`cdn_tier` はサーバーと静的ファイルを合わせた CDN リクエストの合計から決めます。メモリの行は上限値です。1 つのインスタンス上で重なったリクエストはそのメモリを共有するので、実際の数字はこれより小さくなります。

### 平均では見えないケース：動画と大きなファイル

受講者が月に 2 TB 分視聴する、100 GB の動画を持つコースサイトを考えます。

- **Cloudflare R2 では**、ストレージは無料の 10 GB を 90 GB 超え、1 GB あたり $0.015 で月 $1.35 です。これに、最初の 1,000 万回を超える Class B の読み取りが 100 万回あたり $0.36 加わります。エグレスは無料なので、視聴が 2 TB でも 20 TB でもコストは同じです。
- **Vercel Blob では**、ストレージは 1 GB あたり $0.023 で 100 GB なら $2.30、Blob Data Transfer はワシントン D.C. で 1 GB あたり $0.05 なので、2 TB の視聴には月約 $100 かかります。これにはキャッシュミス時の CDN リクエストと Fast Origin Transfer が含まれていません。Flat Rate CDN はアプリケーションのトラフィックについては Blob Data Transfer もカバーしますが、その適用条件は、メディアが帯域幅の大半を占めるサイトを除外しています。

saasyland.com はまさにこのケースです。コースの動画は <RepositoryFact name="videoSegmentSeconds" unit="second" />のセグメントに分割された HLS ストリームで、非公開の R2 バケットに保存され、署名済み URL の奥で Worker を通じて配信されます。そのため、視聴によって請求に加わるのは Worker のリクエストと R2 の読み取りで、帯域幅が加わることはありません。

## オートスケーリング：それぞれにおける「ゼロまでスケール」と「スケールアップ」の意味

どちらのプラットフォームも、課金の意味ではゼロまでスケールします。トラフィックがなければ、コンピューティングの料金はかかりません。スケールアップの仕方は異なり、最初に突き当たる限界がコンピューティングであることはめったにありません。

**Vercel** はインスタンスの数でスケールします。Fluid compute は「スケールアップする前に既存のリソースを自動的に最適化」します。つまり、新しいリクエストは、余裕があればすでに動いているインスタンスに送られ、余裕がなければ新しいインスタンスが起動します。並行性は「需要に応じて自動的にスケール」します。それとともに増えるのがデータベースの接続数です。新しいインスタンスが起動するたびに、Postgres への接続を開く Node.js プロセスが 1 つ増えます。そのため、Vercel の上限のページはコネクションプーリングを勧め、リージョンのページは関数をデータベースと同じリージョンに置くよう勧めています。

**Cloudflare** はあらゆるロケーションのアイソレートでスケールします。サイズを決めるインスタンスも、追加するリージョンもありません。東京でトラフィックが急増すれば、東京でアイソレートが起動します。忙しい Worker ではコールドスタートはまれです。Cloudflare は 2025年9月に、ウォームなアイソレートへのリクエストのルーティング方法を変えた結果、「エンタープライズのトラフィックでは、ウォームなリクエストの割合が 99.9% から 99.99% に上がった」と報告しました。ただし、トラフィックがほどほどのサイトでは、多くのリクエストが今でも新しいアイソレートに当たります。次のセクションで示すように、saasyland.com はそのコストを計測しました。

**天井はデータです。** Cloudflare では、コンピューティングは何も設定せずにスケールアウトしますが、D1 はそうではありません。「個々の D1 データベースは本質的にシングルスレッドで、クエリを一度に 1 つずつ処理する」からです。1 ms で終わるクエリなら 1 秒間に約 1,000 回の余裕がありますが、テーブルを 200 ms かけてスキャンするクエリは、その 200 ms の間ほかのすべてのリクエストを止めます。Vercel では、同じ役割を Postgres サーバーの CPU と接続数の上限が担います。どちらのプラットフォームでも、データ層の限界に合わせて設計し、リリース前に負荷をかけてテストしてください。

**もう 1 つの天井は距離です。** ヨーロッパにある D1 のプライマリに 5 つのクエリを順に送るシドニーの Worker は、大陸間のラウンドトリップを 5 回払うことになります。D1 は、データベースを作成する「リクエストを発行した場所に近いロケーション」にプライマリを作成し、リードレプリカが応答するのは Sessions API を通したクエリだけです。残りを解決するのが [Smart Placement](https://developers.cloudflare.com/workers/configuration/placement/) です。Worker のトラフィックを計測し、そのほうが速い場合は Worker をユーザーの近くではなくバックエンドの近くで実行します。Cloudflare はこれを、まさにこのケース、つまりシドニーのユーザーとフランクフルトのデータベースで説明しています。判断には複数のロケーションからの継続的なトラフィックが必要で、分析には最大 15 分かかることがあります。

### 計測したコールドスタート

Vercel では、コールドスタートとは新しい Node.js プロセスがバンドルを読み込むことで、本番のデプロイではバイトコードのキャッシュと事前のウォームアップがそれを短くします。Cloudflare では、新しいアイソレートのコストは小さいものの、応答する前に Worker 全体を読み込む必要があります。saasyland.com は、それがどれほど重要かを 2 度思い知りました。

- Polar のクライアントもインポートしていたモジュールからヘッダー名を**1 つ静的にインポートしただけ**で、約 1.4 MB の SDK がすべてのコールドスタートに読み込まれ、ランディングページの最初の 1 バイトが届くまでに最大 1.4 秒かかりました。[パフォーマンスの規約](/docs/conventions/performance)に記録しているとおり、現在はビルドが Worker のエントリーの静的インポートをたどり、それが Polar SDK、Drizzle、Resend に到達すると失敗します。
- **Worker の中のコンテンツ。** [#239](https://github.com/saasyland/saasyland.com/pull/239) より前は、Worker がコンパイル済みのドキュメントとブログをバンドルしていました。それらを静的ファイルに移したことで、アップロードは 30,115 KiB から 13,465 KiB になり、プレビューデプロイの新しいアイソレートでハンドラーが実行されるまでの待ち時間は、中央値で 934 ms から 561 ms になりました。

この教訓はどちらのプラットフォームにも当てはまります。コールドスタートで読み込まれるもののサイズはそのままレイテンシーになり、CI でチェックする価値があります。その方法は [Workers で動く SaaS のガイド](/blog/saas-on-cloudflare-workers-d1-kv-r2)で説明しています。

## 想定外の高額請求と Denial of Wallet

Denial of Wallet 攻撃はサイトを停止させるのではなく、サイトの運用費を高くします。従量課金のプラットフォームはどれもこの攻撃にさらされており、そのリスクはメーターに沿って生じます。

### Vercel の請求額を押し上げうるもの

- **攻撃と認識されない関数へのトラフィック。** Vercel の [DDoS のページ](https://vercel.com/docs/vercel-firewall/ddos-mitigation)には、「ブロックされたトラフィックについて顧客に課金しない」とある一方で、「イベントを自動的に緩和する前に正常に処理されたリクエスト」と「DDoS イベントとして認識されないリクエスト（ボットやクローラーのトラフィックを含む場合がある）」については利用料が発生するとも書かれています。
- **遅いアップストリーム。** メモリはリクエストが待っている間も課金されるので、100 ms から 5 秒に遅くなった API は、インスタンスが多くのリクエストを同時に処理しない限り、それを呼び出すすべてのリクエストのメモリのコストを何倍にもします。
- **メディアとダウンロード。** 定額料金の外のデータ転送、Blob の転送、Fast Origin Transfer は、1 バイトごとに増えていきます。
- **Image Optimization。** 変換は、ワシントン D.C. の Pro で 1,000 回あたり $0.05 で、これにキャッシュの読み取りと書き込みが加わります。そのため、多くの画像を多くのサイズでリクエストするページは、それらを何倍にも増やします。

Flat Rate CDN は、それを利用するチームにとって、Vercel の典型的な想定外の高額請求、つまりバズったローンチがギガバイト単位で課金される問題に対処します。Vercel 自身の例では、従量課金なら請求額が「数万ドルに達していたはず」のチームが、$20 のままで済みました。関数は引き続き計量されます。

### Cloudflare の請求額を押し上げうるもの

- **Worker に到達するリクエスト。** CPU 1 ms のリクエストが 1 億回押し寄せた場合、無料枠を超えた分として、リクエストで約 $30、CPU で約 $2 かかります。リクエストは安く、リスクは Worker がそれぞれのリクエストで何をするかにあります。
- **書き込み。** D1 は書き込み 100 万行あたり $1.00、KV は書き込み 100 万回あたり $5.00 を請求するので、書き込みを引き起こすループや攻撃者は、高額な請求への最短経路です。リクエストごとに 1 行を書き込むレートリミッターにも、同じように注意を払う必要があります。
- **CPU を大量に使うエンドポイント。** 呼び出しごとに 500 ms の CPU を使うエンドポイントは、10 ms のものの 50 倍のコストがかかり、Workers Paid のデフォルトの CPU の上限はリクエストあたり 30 秒です。
- **ログ。** 2026年12月1日から、ログとトレースは [Cloudflare Observability の料金体系](https://developers.cloudflare.com/observability/pricing/)に移行します。有料プランでは請求サイクルごとに取り込み 50 GB とストレージ 10 GB・月が含まれ、それを超えると取り込み 1 GB あたり $0.25、保存 1 GB・月あたり $0.10 です。

Cloudflare の DDoS 対策はすべてのプランで「従量課金なし」で、WAF は不正なトラフィックをコードに届く前に止められます。Free プランにも、IP ごとに 10 秒間で数えるレート制限ルールが 1 つ含まれています。リクエストをブロックするルールはそこでリクエストを終わらせ、「リクエストは停止し、後のフェーズには到達しない」とされています。インシデントの際は、Worker のリクエストのメトリクスを確認して、何が到達したかを確かめてください。

### 支出の管理機能の比較

| 管理機能               | Vercel Pro                                                                                      | Cloudflare                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| デフォルトのアラート   | 請求サイクルごとのオンデマンドの支出が $200 に達すると通知                                      | 予算アラートのない従量課金制のアカウントに、アカウント全体で $10 の予算アラート           |
| 自分で設定するアラート | チーム、プロジェクト、プロダクトごとの予算。50%、75%、100% でメールと Web、100% で SMS。Webhook | アカウント全体の支出に対する予算アラート。支出上限の 80% と 100% でメール                 |
| 強制停止               | チームまたはプロジェクトの予算で本番のデプロイを一時停止                                        | Workers または Durable Objects の支出上限で、次の期間まで新しい呼び出しを拒否（ベータ版） |
| 遅れ                   | 「数分ごと」に確認                                                                              | 「ブロックは即時ではない」。支出データは 10 分以内に届く                                  |
| 停止後も動き続けるもの | ストレージの料金。AI Gateway と v0 の利用                                                       | 静的アセットは配信を続ける。KV、R2、D1 などのプロダクトは Workers の上限の対象外          |
| リクエストごとのガード | 関数ごとの `maxDuration`                                                                        | Worker ごとの `limits.cpu_ms`                                                             |

### Vercel で支出に上限を設ける方法

1. **Settings** > **Billing** > **Spend Management**、または CLI から**チームの予算を作成し**、**Pause production deployments** を有効にします。支出が予算に達した後も「プロジェクトは数分間トラフィックを処理し続け、利用料が発生し続ける可能性がある」ので、支払ってもよい最大額より低く設定してください。
2. 社内ツールなど、先に一時停止したいプロジェクトには**プロジェクトの予算を追加します**。
3. サイトを静的なフォールバックに切り替えるなど、一時停止ほど極端ではない処理を行う **Webhook を追加します**。
4. **すべての関数に `maxDuration` を設定し**、正当なリクエストが必要とする最長の時間にします。
5. 攻撃を受けているときは **Attack Mode を有効にします**。すべてのプランで無料で、すべてのトラフィックにチャレンジを課します。

```sh
vercel billing budgets set --amount 200 --pause
vercel billing budgets set --project my-app --amount 100
```

一時停止したプロジェクトは一時停止したままです。「予算額を増やしても、プロジェクトの一時停止は自動的には解除されない」ので、誰かがそれぞれを再開する必要があります。

### Cloudflare で支出に上限を設ける方法

1. **デフォルトの予算アラートを残すか**、**Billable Usage** で独自のものを設定し、受信者を追加します。ダッシュボードで作成した支出上限には、デフォルトではメールの受信者が設定されていません。
2. 上限を引き上げるまでのダウンタイムのほうが、際限のない請求より安くつくなら、**Workers の支出上限を設定します**。これはベータ版で、$5 のサブスクリプションとほかのプロダクトは対象外であり、Cloudflare は「上限は請求額の最大値を保証するものではない」と明言しています。
3. 異常なリクエスト 1 つが 30 秒間動き続けることがないよう、**呼び出しごとの CPU の上限を設定します**。

```jsonc
{
  "limits": {
    "cpu_ms": 50,
  },
}
```

4. D1 や KV に書き込む、メールを送る、有料の API を呼び出すエンドポイントには、**レート制限ルールを追加します**。
5. **書き込みは認証の後ろに置くか**、低コストのチェックの後ろに置き、匿名のトラフィックが発生させるコストを読み取りだけにします。

## データ：コードの隣に何があるか

ここが、両プラットフォームの違いが最も大きく、選択を最も取り消しにくい部分です。

**Vercel はファイルと設定を保存し、データベースはパートナーに任せています。** その[ストレージの概要](https://vercel.com/docs/storage)には、ファイル用の Vercel Blob、10 ms 未満で読み取れる設定用の Global Config、リージョン単位のキャッシュ用の Runtime Cache、そしてリレーショナルやキーバリューのデータすべてに使う「Marketplace のストレージ」が挙げられており、後者は「Neon、Upstash、Supabase などのプロバイダー」から提供されます。`vercel install neon` はデータベースをプロビジョニングし、その認証情報を環境変数として注入します。その後、アプリはドライバーを使ってネットワーク越しに Postgres とやり取りし、トランザクション、拡張機能、大きなエコシステム、数十年分のツールといった、Postgres がもたらすすべてを得られます。

**Cloudflare は自社のデータプロダクトを運用し、それをバインディングとして Worker に渡します。** バインディングは `env` 上のオブジェクトで、D1 なら `env.DB`、R2 のバケットなら `env.MEDIA` のように、Wrangler の設定で宣言します。漏洩しうる接続文字列も、サイズを決めるべきプールも、インスタンスごとにプロビジョニングするものもありません。プロダクトを簡単に紹介します。

- **D1**：Cloudflare のストレージとレプリケーションを備えた SQLite。データベースあたり 10 GB、データベースごとに一度に 1 つのクエリ、ステートメントは自動コミットモードで、バッチはトランザクションとして実行されます。
- **KV**：1 分遅れで読んでも構わないデータのための、結果整合性のキーバリューストア。
- **R2**：エグレス料金のない S3 互換のオブジェクトストレージ。
- **Queues** と **Durable Objects**：バックグラウンド処理と、一貫した 1 つの所有者が必要な協調処理のためのもの。
- **Hyperdrive**：すでに運用している Postgres や MySQL のデータベースのためのコネクションプーリングとクエリキャッシュで、Workers のプランに含まれています。

最後のものは、移行を検討している人にとって重要です。Workers で動かすために D1 を採用する必要はありません。Neon を使う Vercel 上の Next.js アプリは、コンピューティングを Cloudflare に移し、データベースはそのまま残して、その前に Hyperdrive を置けます。

Vercel 自身の[移行ガイド](https://vercel.com/kb/guide/migrate-to-vercel-from-cloudflare)は逆方向にプロダクトを対応付けており、それぞれのプラットフォームが何を自社製にしているかを見るのに便利な表です。

| Cloudflare      | Vercel（Vercel のガイドによる）            |
| --------------- | ------------------------------------------ |
| Workers KV      | Marketplace の Redis、または Global Config |
| R2              | Vercel Blob                                |
| D1              | Marketplace の Postgres                    |
| Durable Objects | 直接の相当物なし                           |
| Queues          | Vercel Queues（ベータ版）                  |
| Cron Triggers   | Cron Jobs                                  |

## 開発者体験

### プレビューデプロイ

**プレビューデプロイは Vercel が最も強い分野です。** デフォルトで、本番以外のブランチへのすべてのプッシュとすべてのプルリクエストにプレビューデプロイが作られ、ブランチを追いかける「ブランチ固有の URL」と、コミットごとの「コミット固有の URL」が付きます。新しいプロジェクトではプレビューが Vercel Authentication で保護され、プレビューは `noindex` 付きで配信され、各環境は専用の変数を持ち、Pro ではステージングなどのカスタム環境を追加できます。何も設定せずに動き、Vercel を選ぶ最も良い理由の 1 つです。

**Cloudflare は 2 段階で追いつきました。** Worker のアップロードされた各バージョンには、以前はプレビュー URL と呼ばれていた **Version URL** を付けられますが、これは「アップロードされた 1 つのバージョンを本番のリソースに対して実行する」ものなので、テストできるのはデータではなくコードです。2026年9月22日、Cloudflare は [Worker Previews](https://developers.cloudflare.com/workers/previews/) を追加しました。ブランチごとに 1 つの Preview があり、それぞれが「専用の変数、シークレット、バインディング、URL、オブザーバビリティ」を持ち、`wrangler preview` で、またはプルリクエストに対して Workers Builds によって作成されます。Vercel と異なる点が 2 つあります。Cloudflare Access を前に置くまでは「Preview の URL はデフォルトで公開」されており、KV、D1、R2 が分離されるのは各 Preview を別のリソースにバインドした場合だけです。一方、Durable Objects には自動的に専用の名前空間が割り当てられます。

**saasyland.com のやり方。** saasyland.com は Worker Previews より前から存在し、`preview.saasyland.com` にある共有の `preview` 環境を 1 つ使っています。この環境は専用の D1 データベース、KV 名前空間、R2 バケットを持っています。チェックとブラウザーテストのスイートに合格すると GitHub Actions がデプロイし、フォークからのプルリクエストは検証されますがデプロイはされず、プレビューのデプロイはそのたびに前のものを置き換えます。プッシュが二重にデプロイしたり CI のゲートを飛ばしたりしないよう、Workers Builds の自動デプロイは無効にしています。その設定は [CI/CD のページ](/docs/tooling/ci-cd)と[プレビューをデプロイする](/docs/getting-started/deploy-preview)のページで説明しています。

### ローカル開発

Wrangler は Worker をローカルの `workerd` プロセスで実行し、「Wrangler の設定で Worker にバインドされているすべてのリソースはローカルでシミュレートされる」ので、D1、KV、R2、Queues、Durable Objects も含まれます。saasyland.com がしているように、クラウドのアカウントなしで開発し、ブラウザーテストのスイートを実行できます。

saasyland.com はこれに依存しており、これがないと何が起きるかを経験しました。[#258](https://github.com/saasyland/saasyland.com/pull/258) までは、`development` 環境がプレビューの D1 データベースをリモートでバインドしていたため、ローカル開発がプレビューのデータに書き込み、開発用のデータベーススクリプトもすべてプレビューのデータベースに届いていました。現在は `development` と `test` が `.wrangler/` 配下のローカルの D1、KV、R2 をバインドし、`bun run dev` に Cloudflare へのログインは不要で、開発用のバインディングがリモートになったり、プレビューや本番とリソースを共有したりするとテストが失敗します。本番、プレビュー、開発、テストはそれぞれ専用のデータベースを持っており、[データベースのガイド](/docs/tooling/database)にその一覧があります。

Vercel では、ローカル開発はフレームワークの開発サーバーを Node.js で実行するので本番環境とよく一致し、`vercel env pull` で環境の変数を取得できます。データベースはプロバイダーから提供されるので、ローカル開発には専用の開発用データベースかローカルの Postgres が必要です。

### ビルド、CI、ロールバック

Vercel は自社のマシンでビルドし、有料プランでは 1 CPU・分あたり $0.0035 から課金され、Pro では 1 日に最大 6,000 回デプロイできます。Workers Builds は有料プランで月 6,000 分のビルド時間を含み、それを超えると 1 分あたり $0.005 で、タイムアウトは 20 分です。あるいは、saasyland.com のように自分の CI でビルドして `wrangler deploy` を実行することもできます。

ロールバックについて。Vercel の Instant Rollback を使うと、Pro のチームは本番を配信したことのある任意のデプロイに、再ビルドなしで戻れます。Cloudflare は `wrangler rollback` のために直近の 100 バージョンを保持しており、「ロールバックの間、Worker に接続されたリソースは変更されない」としています。どちらでも、ロールバックされるのはコードであってデータではありません。だからこそ、スキーマの変更はどれも、その前のリリースで動作するようにすべきです。

### ログとデバッグ

Vercel はランタイムログを Hobby で 1 時間、Pro で 1 日保持し、それ以上は Observability Plus として 100 万イベントあたり $1.20 で販売しています。Cloudflare は Workers Logs を Free で 3 日間、Paid で 7 日間保持し、ライブログには `wrangler tail` があり、ダッシュボードでは呼び出しごとの CPU 時間と実時間を確認でき、2026年12月1日からは新しい料金体系になります。

### Next.js、v0、エコシステム

Vercel は [Next.js](https://github.com/vercel/next.js) を保守しており、Vercel では ISR、画像最適化、Server Actions、Cache Components、そして middleware の後継である `proxy.ts` といった機能にアダプターは不要です。Vercel の AI アプリビルダーである [v0](https://v0.app/docs/introduction) は、Vercel に「ワンクリックで」デプロイします。テンプレートギャラリー、インテグレーション、そして真っ先に Vercel 向けに書かれたガイドの多さは、特に小さなチームにとって実際の利点です。

Cloudflare では、Next.js はアダプターを通じて動きます。Cloudflare は「Cloudflare Workers で Next.js アプリケーションを動かすデフォルトの方法として vinext を推奨」しつつ、「vinext はベータ版」としています。vinext 自身の README は、本番環境で使うべきかという問いに「使えますが、注意が必要です」と答えています。[OpenNext のアダプター](https://opennext.js.org/cloudflare)は「Next.js 16 のすべてのマイナーバージョンとパッチバージョン、および Next.js 15 の最新のマイナーバージョン」に対応しており、vinext の README はこちらをより成熟した選択肢と呼んでいます。Vite で作られたフレームワークは、Cloudflare 自身の Vite プラグインを通じて Workers にデプロイします。saasyland.com が使う TanStack Start は Cloudflare を公式ホスティングパートナーとして挙げており、Next.js との比較は [SaaS のための TanStack Start と Next.js の比較](/blog/tanstack-start-vs-nextjs-for-saas)で行いました。

## パフォーマンス：ベンチマークが示すこと

2025年10月、Theo Browne が両プラットフォームでのサーバーサイドレンダリングのベンチマークを公開しました。Vercel の[記事](https://vercel.com/blog/fluid-compute-benchmark-results)は、計算量の多いタスクで「Fluid compute は Cloudflare Workers より 1.2〜5 倍速かった」と報告し、両者が異なる構成で動いていたことにも触れています。Workers は「共有 CPU、128MB RAM」、Fluid compute は「2 vCPU、4GB RAM」です。Cloudflare は[これに応えて](https://blog.cloudflare.com/unpacking-cloudflare-workers-cpu-performance-benchmarks)、差の多くは、1 つのクライアントからの CPU 負荷の高いバーストをスケジューラーがキューに入れていたこと、2017年からのガベージコレクターの設定、OpenNext の非効率によるものだと説明し、修正を出荷したうえで、「Cloudflare は現在、Next.js に基づくものを除くすべてのベンチマークケースで Vercel と同等の性能を発揮している」と報告しました。さらに、アイソレートを待つ時間は CPU 時間ではないので、スケジューリングの問題は「請求額には影響しなかったはず」だと付け加えています。

両方の記事を読んでも揺るがない結論が 3 つあります。CPU がボトルネックになる処理では、Vercel ではより大きなマシンを買えますが、Cloudflare では買えません。Next.js に限れば、Vercel が基準となるプラットフォームです。そして、他人のコードのベンチマークは自分のコードについてほとんど何も教えてくれません。代表的なルートを両方にデプロイし、ユーザーがいる場所から最初の 1 バイトまでの時間を計測してください。

## Cloudflare の率直な欠点

### Workers は Node.js とは別物

Workers が実装しているのは「Node.js API の一部」です。2026年8月4日の互換性日付でデフォルトで有効になる `nodejs_compat` を使えば、`buffer`、`crypto`、`stream`、`http`、`fs` などのモジュールが使えますが、`child_process` は何もしないスタブで、Node.js のネイティブアドオンは読み込まれず、長時間動き続けるプロセスや永続的なディスクを前提とするコードには別の居場所が必要です。SaaS が使う npm パッケージのほとんどは動きますが、動かないもの（ヘッドレスブラウザ、ネイティブバインディングを持つ画像ライブラリ、ネイティブコードを必要とするドライバーなど）は、えてして簡単には置き換えられないものです。採用を決める前に、サーバーの依存関係をすべて確認してください。

### D1 は SQLite で、データベースごとにスレッドは 1 つ

D1 は Workers Paid で、データベースを 10 GB、クエリを 30 秒とバインドパラメーター 100 個、呼び出しを 1,000 クエリに制限しています。トランザクションを開いて読み取り、JavaScript で判断してあとでコミットする、ということはできず、アトミックな変更は 1 つのステートメントか 1 回の `batch()` になります。テナントごとのデータなら、各テナントが専用のデータベースを持てるのでうまくスケールします。書き込みの多い大きな共有データセット 1 つなら、Hyperdrive 経由の Postgres のほうが良い選択で、そのデータベースは自分で運用するか、プロバイダーにお金を払って運用してもらいます。

### 128 MB と、コールドスタートのたびに読み込まれるバンドル

アイソレートのメモリは 128 MB で、Worker は 1 秒以内に起動しなければなりません。2026年9月4日以降、Worker のサイズはすべてのプランで非圧縮 64 MiB までになりました。以前は Free で圧縮後 3 MB、Paid で 10 MB でした。しかし「バンドルが大きく、グローバルスコープの初期化コードが重いほど、起動時間は長くなる」ので、実際に突き当たる限界は、サイズの上限よりもずっと前にレイテンシーです。

### 本番環境のデバッグ

バンドルされたコードのスタックトレースはソースマップなしでは読みにくく、ソースマップはアップロードを大きくします。saasyland.com は、Cloudflare の Vite プラグインがデフォルトでソースマップをアップロードするようになった後、これを無効にしました。[コミット 704bbef](https://github.com/saasyland/saasyland.com/commit/704bbef94) に記録されているとおり、約 3,300 のモジュールがあるため、ソースマップでアップロードが 2 倍になり、Cloudflare の API がそれを「multipart: message too large」として拒否したからです。この設定は今も無効のままです。

```jsonc title="wrangler.jsonc"
  "compatibility_flags": ["nodejs_compat"],
  "keep_vars": true,
  "upload_source_maps": false,
  "observability": {
    "enabled": true,
  },
```

ログは Paid で 7 日間保持され、Version URL は tail できず、`workerd` でのローカル実行は、エッジでアイソレートがどのように作成され、共有され、破棄されるかを再現しません。

### ロックイン

バインディングは便利さであると同時にロックインでもあります。`env.DB.batch()` を呼び出す、`env.CACHE` を読む、R2 の URL に署名する、Durable Object に状態を保持する、といったコードは Cloudflare でしか動きません。その範囲を限定することはできます。各バインディングを自分のモジュールの後ろに置き、SQL の移植性を保つために D1 の上で Drizzle などのクエリビルダーを使い、可能なところでは R2 を S3 互換の API で使います。しかし、Vercel 自身のガイドにもあるとおり、Durable Objects にはほかに相当するものがなく、D1 のデータベースを移すことは、SQLite から新しいプラットフォームが提供するものへ移ることを意味します。

### 本番環境で遭遇した落とし穴

どれも saasyland.com の時間を奪ったもので、入門ガイドには 1 つも載っていません。

- **モジュールスコープの状態はリクエストに属します。** このサイトはかつて、Polar の地域割引をモジュールレベルの Promise としてキャッシュしていました。Workers では、その Promise はそれを作成したリクエストに属します。そのリクエストがキャンセルされると Promise は決して解決されず、そのアイソレートでのその後のチェックアウトはすべて、アイソレートが作り直されるまでそれを待ち続けました。[#103](https://github.com/saasyland/saasyland.com/pull/103) の修正では、キャッシュを取得時刻付きで KV に移し、<RepositoryFact name="regionalDiscountsRefreshMinutes" unit="minute" />が過ぎると更新するようにしました。
- **Early Hints はデプロイ後も残ります。** Cloudflare はページの最後の `Link` ヘッダーをデプロイ後も `103 Early Hints` として再送するので、内容に基づいた名前を持つヒント対象のスタイルシートが、削除済みのファイルを指していました。現在、Worker がヒントを出すのは、名前が決して変わらないフォントだけです（[#214](https://github.com/saasyland/saasyland.com/pull/214)）。
- **Speed Brain は Worker のページを拒否します。** このゾーン設定は Chromium にリンクのプリフェッチを求めますが、Cloudflare は Worker を実行する URL のプリフェッチを拒否して `503` で応答するので、無効にしています。それで何も失わない理由は [Cloudflare Workers のページ](/docs/integrations/cloudflare-workers)で説明しています。
- **自分のボット対策が自分の CI をブロックします。** Cloudflare は CI ランナーからのリクエストに `403` で応答するので、デプロイ後の稼働中のサイトのチェックは開発者のマシンからしか実行しません。

## Vercel の率直な欠点

- **シート。** デプロイする開発者 1 人あたり月額 $20 は、チームでは積み重なり、Cloudflare にはないコストです。
- **待っている間もメモリに課金されます。** 長いリクエストは、Vercel では CPU から想像されるよりも高くつきます。差が最も大きくなるのは、ストリーミング、AI、遅い API のワークロードです。
- **デフォルトでは 1 つのリージョン。** リージョンを追加しない限り、`iad1` から遠い訪問者はラウンドトリップを待つことになり、Pro で使えるのは最大 3 つです。どのみちデータベースが 1 つのリージョンにあるなら、それで問題ありません。
- **静的ファイルとバイト数が計量されます。** Flat Rate CDN によってアプリケーションのトラフィックについては予測しやすくなりましたが、メディアの多いサイトは対象外で、Fast Origin Transfer はいずれにしても課金されます。
- **ベンダーが増えます。** データベース、キャッシュ、そして多くの場合キューも別々の会社から提供され、アカウント、認証情報、請求書、ステータスページもそれぞれ別です。
- **リクエストボディ。** 関数が受け付けるのはデフォルトで 4.5 MB、ベータ版で 20 MiB なので、アップロードは Blob などのストアに直接送ります。
- **Hobby はビジネス向けではありません。** 無料プランでは販売するプロダクトをホストできず、上限を超えると一時停止し、ほとんどの場合それが 30 日間続きます。

## Vercel のほうが良い選択になる場合

- **Next.js で開発しており**、アダプターなしですべての機能を使いたい。
- **コードに Node.js が必要：** ネイティブモジュール、ヘッドレスブラウザ、子プロセス、大きなメモリ、CPU を長時間使う処理。
- **チームがプレビューで作業をレビューしており**、保護されたコミットごとのプレビュー URL、コメント、プロモーションに、シートの価格以上の価値を見いだしている。
- **トラフィックがほどほどで CPU をあまり使わない**ので、請求額がプラットフォーム料金の近くにとどまり、利便性が安く手に入る。
- **どのみち Postgres が必要**で、その運用を Neon や Supabase に任せて構わない。

## Cloudflare のほうが良い選択になる場合

- **成長するにつれてコストが重要になる：** リクエスト、シート、帯域幅のいずれでも。
- 動画、ダウンロード、バックアップ、ビルド成果物など、R2 の無料のエグレスで経済性が変わる**大きなファイルを配信する**。
- **リクエストのほとんどが待ち時間：** データベース、サードパーティの API、言語モデルを待つ時間で、その実時間は無料。
- **ユーザーが世界中にいて**、データがユーザーごと、テナントごと、またはキャッシュ可能なので、ユーザーの近くのコードはデータの近くにもある。
- **1 つのプラットフォームにまとめたい：** コンピューティング、SQL、キャッシュ、ストレージ、キュー、静的ファイルを、1 つのアカウント、1 つの設定ファイル、1 つの請求書で。
- **フレームワークが Vite で作られている**か、TanStack Start、Astro、React Router、Hono のように Workers を直接ターゲットにしている。

## saasyland.com が Cloudflare で動いている理由

2026年9月まで、saasyland.com は Vercel 上の Next.js 16 アプリで、Postgres は Neon、Redis は Upstash にあり、`vercel deploy` でデプロイしていました。2026年9月6日、D1、KV、R2 を使う Cloudflare Workers 上の TanStack Start に[移行しました](https://github.com/saasyland/saasyland.com/commit/0b9a1b986)。私たちが Cloudflare を選んだ理由は 5 つあり、どれも現在のリポジトリで確認できます。

1. **3 つではなく 1 つのプラットフォーム。** サイトのサーバーコード、データベース、キャッシュ、非公開のファイルストレージ、静的ファイルは 1 つの `wrangler.jsonc` に書かれたバインディングで、アカウントも、請求書も、デプロイの認証情報も 1 つずつです。移行前は、同じサイトに Vercel、Neon、Upstash のアカウントが必要で、それぞれがすべての環境で独自の認証情報を持っていました。
2. **世界中の小さな顧客層に販売するプロダクトにコストモデルが合っています。** このサイトは、<RepositoryFact name="languages" /> 言語のマーケティングページ、ドキュメント、ブログ、顧客ワークスペース、管理コンソール、ライセンス API、決済の Webhook を提供しています。静的ファイルの配信にはお金がかからず、リクエストは短く、デプロイする人がいてもシートの料金はかかりません。
3. **バインディング。** ユーザー、セッション、ライセンス、コースは D1 の行で、2 つのキャッシュ済みの応答は KV にあり、コースの動画と CLI のバンドルは R2 のオブジェクトです。どれも接続文字列、プール、ドライバーなしで `env` を通じて使え、開発とテストのためにすべてローカルでシミュレートされます。
4. **エグレス料金がありません。** コースの動画と CLI のテンプレートバンドルは R2 から Worker を通じて配信されるので、顧客が視聴したりダウンロードしたりする量に応じて請求額が増えることはありません。
5. **デフォルトでグローバル。** プリレンダリング済みのページはすべての訪問者の近くにある静的アセットから届き、各ページにセキュリティヘッダーと地域別の価格を加える Worker は、リージョンを選ばなくても、リクエストが届いた場所で動きます。

移行にはコストもあり、リポジトリはそれも記録しています。計測して削らなければならなかったコールドパス、それに合わせて設計している SQLite データベース、諦めたソースマップ、そして上で挙げた本番環境での落とし穴です。このようなプロダクトにとっては、それだけの価値がある取引です。初日からすべての機能が必要な、コンテンツの多い Next.js のサイトを作るチームには、Vercel のほうが合っています。

## 両者の間での移行

### Vercel から Cloudflare へ

1. Node.js の互換性リストと照らし合わせて、**サーバーの依存関係を棚卸しします**。プロセスを起動するものやネイティブコードを必要とするものは、最初に解決すべき問題です。
2. Next.js を使っているなら、**Next.js をどう動かすかを選びます**。現時点で最も幅広い機能に対応しているのは OpenNext で、ビルドの速さのためにベータ版を受け入れるなら vinext です。フレームワークが Vite で作られているなら、Cloudflare の Vite プラグインを使います。
3. **最初はデータベースをそのまま残します。** 既存の Postgres の前に Hyperdrive を置き、コンピューティングを移し、D1 についてはアプリが動いてから判断します。
4. 使っている**プラットフォームの機能を対応付けます**。`next/image` は Cloudflare Images に、Blob は R2 に、Vercel Cron Jobs は Cron Triggers に、Global Config は KV に、`@vercel/functions` の `waitUntil` は Worker 自身の `waitUntil` に、Vercel の IP と位置情報のヘッダーは Cloudflare の `cf-connecting-ip` と `cf-ipcountry` にします。
5. 初日から**環境ごとに別々のリソースを作成し**、テストとローカル開発には専用のローカルのバインディングを用意します。
6. ローカルではなく**実際のデプロイでコールドスタートを計測し**、Worker のエントリーのサイズのチェックを CI に追加します。
7. **DNS は最後に移します。** ドメインがすでに Cloudflare にあるなら、切り替えは Worker の設定の中のルート 1 つで済みます。

### Cloudflare Workers へのフルスタックアプリのデプロイ

移行する場合も一から始める場合も、Workers 上のフルスタックアプリに必要な手順は同じで、数もわずかです。saasyland.com の[プレビューをデプロイする](/docs/getting-started/deploy-preview)ガイドでは、実際の名前を使ってそれらを実行しています。

1. 環境ごとに**リソースを作成します**。D1 データベース、KV 名前空間、必要な R2 バケットです。
2. 環境ごとに、データベースのマイグレーションのディレクトリとともに、`wrangler.jsonc` で**それらをバインディングとして宣言します**。
3. それを必要とするコードが公開される前に、`wrangler d1 migrations apply` で対象のデータベースに**マイグレーションを適用します**。
4. 自分の CI から、または Workers Builds で、`wrangler deploy` を使って**デプロイします**。

```sh
bunx wrangler login
bunx wrangler d1 create saasyland_com_preview
bunx wrangler kv namespace create CACHE --env preview
bunx wrangler r2 bucket create saasyland-preview
```

その後のこと、つまりどのデータをどこに置くか、ダウンタイムのないマイグレーション、各デプロイの前後に実行するチェックについては、[Workers で動く SaaS のガイド](/blog/saas-on-cloudflare-workers-d1-kv-r2)で説明しています。

### Cloudflare から Vercel へ

1. **バインディングをクライアントに置き換えます。** Vercel のガイドにもあるとおり、`env.DB` は Postgres のクライアントに、`env.CACHE` は Redis のクライアントに、`env.MEDIA` は Blob SDK になり、シークレットは `env.SECRET` から `process.env.SECRET` に移ります。
2. **データを移行します。** D1 は SQLite で、Vercel のデータベースの多くは Postgres なので、スキーマの変換とエクスポートを計画してください。Vercel のガイドは、Cloudflare KV には「直接のエクスポートツールがない」と指摘しています。
3. **Durable Objects を使っていた部分を設計し直します。** 直接の相当物がないので、Redis やキューを中心にします。
4. 新しいデータベースの隣に**リージョンを選び**、2 つ以上必要かどうかを判断します。
5. トラフィックを受ける前に、**一時停止付きの支出予算を設定します**。
6. **ヘッダーとリダイレクトを作り直します。** `_headers` と `_redirects` の内容を `vercel.json` かフレームワークの設定に移します。TanStack Start のアプリは Nitro を通じて Vercel にデプロイします。

## 選ぶ前のチェックリスト

- リクエストの種類ごとに、リクエストあたりの CPU ミリ秒と実時間の中央値を把握している
- 静的ファイルへのリクエスト、バイト数、シート、データベースを含め、想定されるトラフィックの料金を両方のプラットフォームで計算した
- サーバーの依存関係をすべて Workers の Node.js 互換性リストと照らし合わせたか、完全な Node.js が必要だと判断した
- データがどこにあるかを把握しており、コードはその隣で動くか、ラウンドトリップが少ない
- 支出のハードリミットか一時停止の仕組みがあり、それぞれが作動するまでにかかる時間を把握している
- すべての環境が専用のデータベース、キャッシュ、ストレージを持っている
- 実際のデプロイでコールドスタートを計測した
- 乗り換えるときに書き直さなければならないものを把握しており、それを自分のモジュールの後ろに隔離している
