## Route

`src/routes/_site._marketing.index.tsx` compose dix-sept sections de `src/presentation/components/custom/landing-page/sections` dans `MotionProvider` : Hero, Proof, Stack, Manifesto, CLI, Line, Quality, Rally, Manifest, Studio, Record, Cases, Compare, Pricing, FAQ, Notes et Gate. Les textes viennent de l’espace de noms `pages.landing`. Le loader récupère aussi les trois derniers articles du blog (les articles mis en avant d’abord) pour la section Notes et préchauffe `starCountQuery`, le nombre d’étoiles GitHub mis en cache dans KV pour la section Proof. Il formate ensuite le prix de Core tiré de `TIER_PRICES` dans la description de la page, dont le message `pages.landing` le reçoit comme `{price}`. La page contient aussi les données structurées de l’organisation, `ORGANIZATION_STRUCTURED_DATA_HTML` ; voir [Référencement et aperçus sociaux](/docs/features/seo#structured-data).

Tous les autres chiffres de la page sont mesurés, pas saisis : le plugin Vite `virtual:repository-facts` de `scripts/repository-facts.ts` compte, au build, les fichiers de test, les specs Playwright et les composants d’UI, tire le nombre de devises, de fuseaux horaires et de pays de `CURRENCY_CODES`, `TIMEZONES` et `COUNTRIES`, et lit les versions majeures de React et de TanStack Table. `REPOSITORY_FACTS` dans `src/data/repository-facts.ts` ajoute les langues, les sections de l’admin qui fonctionnent et, depuis `src/data/cli.ts`, les modules (`cliModules`), les modules qu’une réponse peut écarter (`cliOptionalModules`) et les extras (`cliExtras`) de la CLI, et les sections le passent aux messages `pages.landing` comme arguments ICU, par exemple `{testFiles, number}`. La liste **Vérifiez chaque affirmation** tire des mêmes faits les fichiers et les commandes qu’elle cite, si bien qu’aucune langue ne les traduit : le chemin du résumé de couverture depuis `vite.config.ts`, le répertoire des specs depuis `playwright.config.ts`, le workflow de CI, le répertoire des messages, l’intégration d’authentification et les commandes <RepositoryFact name="coverageCommand" /> et <RepositoryFact name="i18nCheckCommand" />.

L’avance affichée dans les sections Hero, Manifesto et Gate est `headStartHours`, dérivée de `HEAD_START_ROWS` dans `src/data/head-start.ts`. Chaque ligne nomme une partie du projet par défaut que génèrent les templates de la CLI, la couche de template qui la livre, et l’estimation basse et haute des heures qu’un ingénieur senior passerait à l’écrire à la main ; la facturation, les organisations, le multi-tenant et le commerce d’exemple n’ont pas de ligne tant qu’aucun template ne les génère. Les lignes totalisent de <RepositoryFact name="headStartLowHours" /> à <RepositoryFact name="headStartHighHours" /> heures, et le titre reprend le total bas arrondi à l’inférieur à `HEAD_START_ROUNDING_HOURS` et plafonné à `HEAD_START_CLAIM_MAX_HOURS` : il indique donc <RepositoryFact name="headStartHours" /> et baisse de lui-même si des lignes disparaissent. Le blog affiche les lignes avec `<HeadStartTable />`, libellées depuis `pages.blog.headStart`.

Le chiffre de couverture partout sur la page est `coverageThreshold`, lu dans `vite.config.ts`. Deux sortes de valeurs sont déclarées plutôt que mesurées, une seule fois chacune dans `src/data/marketing.ts` : les chiffres de reactprojects.com (`REACTPROJECTS_FACTS`) et le taux horaire indicatif du calcul de prix (`ILLUSTRATIVE_HOURLY_RATE`), à partir duquel `CORE_PRICE_IN_HOURS` calcule le nombre d’heures entières sous lequel reste le prix de Core ; `marketing.test.ts` échoue s’il cesse d’y rester.

`adminSections` ne compte que les entrées de `ADMIN_NAVIGATION` dont le `status` est `FEATURE_STATUS.AVAILABLE` (`src/data/navigation.constants.ts`), que chaque zone déclare à côté de l’entrée dans `src/data/<area>.navigation.ts` : les écrans d’administration qui affichent des données de démonstration ne sont donc pas comptés, soit <RepositoryFact name="adminSections" /> aujourd’hui. La case **Langues** de la grille Proof affiche les locales prises en charge, et ses chiffres de tests précisent qu’ils sont comptés dans le code source de ce site, pas dans un projet généré.

Toutes les pages publiques se trouvent dans le layout sans chemin `_site` (`src/routes/_site.tsx`), qui affiche, une seule fois pour toutes ces pages, l’en-tête du site (`Navigation`) et `BackToTop`. À l’intérieur, le layout `_marketing` (`_site._marketing.tsx`) enveloppe `/`, les pages légales, les pages de newsletter, le blog et les cours avec `PageFrame`, le point de repère `main` et `Footer`. Il définit `dark: true` dans ses `staticData`, et `_site` fait passer toute la page, en-tête compris, au thème sombre dès qu’une route correspondante le définit, tandis que la documentation garde le thème du visiteur. Les ancres de section sont `MARKETING_SECTION_IDS` dans `src/data/navigation.constants.ts` (`foundation`, `cli`, `quality`, `toolkit`, `pricing`, `faq`) ; les liens utilisent `<Link to={ROUTES.HOME} hash={MARKETING_SECTION_IDS.PRICING}>`. `Footer` renvoie vers le dépôt GitHub et le profil Instagram, `APP_GITHUB_URL` et `APP_INSTAGRAM_URL`, dans un nouvel onglet, à côté de `LocaleSwitcher`. `Footer` dispose son bloc de marque et ses deux groupes de liens dans une seule rangée flex qui passe à la ligne, où aucun élément ne devient plus étroit que son mot le plus long : les groupes restent côte à côte tant que leurs libellés tiennent et s’empilent sinon, si bien qu’aucun libellé n’empiète sur un autre, dans aucune langue. Sur un téléphone, le bloc de marque occupe la première rangée ; à partir de `md`, les trois se partagent une rangée dans les proportions 1,5 : 1,3 : 1.

## Page introuvable [#not-found-page]

Toute adresse qu’aucune route ne reconnaît aboutit à `_site._marketing.$.tsx`, dont le loader lève `notFound()` : le serveur répond avec le statut 404 et la page se trouve dans le layout `_marketing` comme les autres, sous l’unique en-tête du site, au-dessus du pied de page, dans le thème marketing. Un article de blog, un cours ou une leçon qui n’existe pas lève `notFound()` depuis son propre loader et affiche le même `DefaultNotFound` (`src/presentation/components/custom/default-not-found.tsx`) au même endroit ; une page de documentation manquante l’affiche dans le layout de la documentation. Quand leur correspondance est introuvable, ces routes prennent leur head de `notFoundHead` (`src/lib/not-found.ts`) : le titre et la description traduits de `errors.not-found` et `noindex`, sans lien canonique ni carte sociale. La seule action de la page est `BackHomeLink`, libellé par `common.backHome`, que propose aussi le lien de newsletter expiré.

## Navigation et retour en haut [#navigation-and-back-to-top]

- Les liens de l’en-tête sont `HEADER_NAVIGATION` dans `src/data/navigation.ts`, les entrées d’en-tête que déclarent les zones, triées par leur `order` : **Tarifs** de la zone de base (`src/data/core.navigation.ts`, un lien vers la section `pricing` de `/` grâce à son `hash`), **Cours** de la zone des cours, **Blog** et **Documentation** de la zone de contenu et **Se connecter** de la zone d’authentification, chacune avec le libellé du `navigation.<area>.json` de sa zone. `Navigation` les affiche, puis l’appel à l’action **Commencer à créer** vers la section des tarifs. Sous le breakpoint `lg`, les entrées passent dans `MobileMenu` (`src/presentation/components/custom/mobile-menu.tsx`), un `Modal` React Aria contenant un `Dialog` qui couvre la fenêtre. Sa rangée du haut reprend le logo et place le bouton de fermeture là où se trouvait le bouton du menu ; viennent ensuite les mêmes entrées dans le même ordre, puis **Commencer à créer**, que l’en-tête lui-même masque sous `sm`. Le focus passe au bouton de fermeture et Tab reste dans le menu, Échap et le bouton de fermeture rendent le focus au bouton du menu, et la page derrière est `inert` et ne défile pas. `html` garde la place de la barre de défilement ([Barres de défilement](/docs/ui/theme#scrollbars)), si bien que rien ne bouge à l’ouverture ni à la fermeture du menu. Une entrée qu’ajoute une zone apparaît dans l’en-tête et dans le menu de chaque page publique.
- Le `Link` de TanStack Router marque l’entrée de la section courante avec `aria-current="page"`, et l’en-tête l’affiche plus lumineuse, avec un point en dessous : **Blog** sur l’index du blog et sur chaque article, **Documentation** sur chaque page de la documentation. Une entrée avec un `hash` n’est marquée que sur sa propre adresse, `/#pricing`, si bien que le reste de la page d’accueil ne marque aucune entrée. Les liens du pied de page vers les sections de l’accueil, **Fondations**, **Tarifs** et **FAQ**, passent `activeOptions={{ includeHash: true }}` pour la même raison. **Commencer à créer** n’est jamais marqué, pas même sur `/#pricing` : c’est une action, pas un lieu, donc `Navigation` et `MobileMenu` le construisent avec `useLinkProps` et retirent le `aria-current` que TanStack Router met sur tout lien vers l’adresse courante.
- L’en-tête commence par un lien **Aller au contenu**, masqué tant qu’il n’a pas le focus clavier, vers l’élément dont l’id est `SITE_CONTENT_ID` (`src/data/navigation.constants.ts`) : le point de repère `main` du layout `_marketing` et l’article d’une page de la documentation.
- L’en-tête est fixe et reste identique à toute position de défilement : un fond flouté et une ligne le long de son bord inférieur, sur laquelle une ligne de progression s’étend à mesure que la page défile. Sa hauteur est le token de thème `--spacing-header` dans `globals.css` (`h-header`), et son contenu est aussi large que celui de chaque page publique, `--container-site` (`max-w-site`), si bien que le logo et **Commencer à créer** gardent leur place d’une page à l’autre. Le point de repère `main` du layout `_marketing` fait commencer chaque page sous l’en-tête avec `pt-header`, sauf la page d’accueil, dont le `staticData` fixe `underHeader: true` pour que son hero passe sous l’en-tête ; le layout de la documentation règle la variable `--fd-banner-height` de Fumadocs sur cette hauteur pour que la barre latérale et la table des matières restent collées sous l’en-tête, et `html` la réserve avec `scroll-padding-top`, si bien que ni un titre atteint par une ancre ni un élément qui reçoit le focus clavier ne se retrouve sous l’en-tête.
- Le logo de l’en-tête est `HomeLink` (`src/presentation/components/custom/home-link.tsx`). Sur `/`, un clic fait remonter en haut de la page et retire de l’adresse une ancre de section comme `#pricing`, en remplaçant l’entrée de l’historique, au lieu de recharger la page sur laquelle se trouve déjà le visiteur. Sur toute autre page, c’est un lien ordinaire vers l’accueil, et un clic avec une touche de modification ouvre toujours un nouvel onglet ou une nouvelle fenêtre. Dans le menu du téléphone, le logo ferme aussi le menu.
- `BackToTop` (`src/presentation/components/custom/back-to-top.tsx`) est un bouton React Aria fixé dans le coin inférieur droit, dont le libellé vient de l’espace de noms `components.custom.back-to-top`. Une sentinelle observée par un `IntersectionObserver` l’affiche dès que le premier écran est sorti de la vue et le masque de nouveau près du haut de la page : aucun code ne s’exécute sur les événements de défilement. Un appui fait remonter en haut de la page et place le focus sur le `h1` de la page. Le layout `_site` l’affiche une seule fois pour toutes les pages publiques.
- Les deux appellent `scrollTo({ top: 0 })` et laissent le mouvement à `globals.css` : `html` défile en douceur et, avec `prefers-reduced-motion: reduce`, saute directement en haut.

## Tarifs et tarifs régionaux

`PricingSection` affiche `PricingTiers` de `src/presentation/components/custom/pricing.tsx`, les mêmes cartes d’offres que l’[application client](/docs/features/customer-app) montre aux comptes sans licence. Chaque carte présente une offre de `LICENSE_TIERS` (`src/modules/license/license.constants.ts`) avec son montant `TIER_PRICES` et des textes de l’espace de noms `components.custom.pricing`, et son bouton est fourni par la page : sur la page d’accueil, un lien vers `/auth/sign-up?redirect=/app?tier=<tier>`, si bien que l’offre choisie est conservée pendant l’inscription. La grille passe à trois colonnes quand son propre conteneur mesure au moins 42rem de large (`@container`), et tient ainsi aussi dans la colonne plus étroite de l’application. Les tarifs régionaux fonctionnent sans JavaScript côté client, la page reste donc prérendue.

Les fonctionnalités d’une carte viennent de `TIER_FEATURES` dans `src/data/marketing.ts`. Chaque entrée a un identifiant, dont le texte est `tiers.<tier>.features.<id>`, et un `FEATURE_STATUS`, et la carte range les entrées sous **Disponible maintenant** et **À venir** (`status.available` et `status.arriving`) : le partage entre ce qui fonctionne aujourd’hui et ce qui est à venir est déclaré une seule fois, et aucune traduction ne nomme un statut. Le groupe disponible se termine par le nombre d’appareils sur lesquels une clé fonctionne à la fois, `LICENSE_ACTIVATION_LIMITS[tier]` via le message `machines`, un pluriel ICU : <ActivationLimit tier="core" /> avec Core, <ActivationLimit tier="complete" /> avec Complete et <ActivationLimit tier="agency" /> avec Agency. `LicenseOfferPending` dessine les mêmes groupes à partir de `TIER_FEATURES`.

Les tarifs régionaux arrivent jusqu’à la page ainsi :

1. `Price` affiche le montant une fois par multiplicateur régional (`PPP_KEYS`), plus le prix normal barré.
2. Le handler de documents de la zone des licences (`src/data/license.worker.ts`), que le Worker applique à chaque page HTML, lit `cf-ipcountry`. Pour un pays présent dans `PPP_TIERS`, il utilise `HTMLRewriter` pour poser `data-ppp` et les variables `--ppp-region` et `--ppp-percent` sur l’élément `html`, et marque la réponse `private, no-cache`.
3. Le CSS de `globals.css` affiche le prix correspondant tant que la case de l’offre régionale est cochée.
4. Décocher la case enregistre `regional_pricing=off` dans un cookie ; le Worker et `startCheckout` le respectent tous deux.

Sous les offres, la carte de conseil affiche `CONSULTING_HOURLY_RATE` de `src/data/marketing.ts`, formaté avec `CURRENCY_FORMAT`. L’appel se réserve par e-mail et ne se vend pas via Polar ; il n’a donc pas de prix régional.

## Configurateur de CLI [#cli-configurator]

`CliSection` héberge `CliConfigurator` (`landing-page/components/cli-configurator.tsx`). Les choix, les extras et les gestionnaires de paquets de `src/data/cli.ts` construisent une commande <RepositoryFact name="scaffoldTarget" /> avec ses options, que `CopyButton` copie. C’est `CLI_GENERATION`, décrit plus bas, qui indique si la CLI l’exécute déjà ; le [guide de la CLI](/docs/cli) décrit ce qu’elle fait aujourd’hui.

Le configurateur s’ouvre sur la stack par défaut, la première option de chaque choix que les réponses précédentes autorisent (`DEFAULT_STACK`). Il signale par un point chaque option que liste `CLI_TEMPLATE_SUPPORT` dans `src/data/cli.ts`, aujourd’hui la stack par défaut et `--no-auth`, et les relie à la légende `defaultStack` avec `aria-describedby`. `CLI_TEMPLATE_SUPPORT` reprend la forme de `TEMPLATE_SUPPORT` de la CLI, que `@saasyland/stack` n’exporte pas encore.

Chaque question est un groupe de boutons radio, le `ToggleGroup` de shadcn avec `selectionMode="single"`, nommé par le libellé de sa ligne, et les extras forment un seul `ToggleGroup` avec `selectionMode="multiple"`. Les flèches se déplacent dans une question, Espace ou Entrée y répond, et Tab passe à la question suivante. Chaque option garde sa place. Celle qu’une réponse précédente exclut par son `unavailableWhen` dans `src/data/cli.ts` est désactivée, et la `note` de la question, affichée sous ses options, en donne la raison ; `aria-describedby` transmet la même raison aux lecteurs d’écran. Un extra qu’une réponse exclut quitte la commande. Une option sélectionnée ne change que de couleur, rien ne rétrécit à l’appui et le configurateur apparaît en fondu sans monter, si bien qu’un appui ne déplace jamais un contrôle sous le pointeur. `e2e/specs/cli-configurator.spec.ts` appuie sur chaque option disponible en son centre et sur ses deux bords et vérifie qu’aucune option n’a bougé.

C’est `CLI_GENERATION` dans `src/data/cli.ts`, un `FEATURE_STATUS`, qui indique si la génération de projets est livrée. Chaque message qui en dépend est un `select` ICU sur `generation`, avec une variante `available` et une autre pour « à venir » (`other`), et les composants transmettent `CLI_GENERATION_VALUES` : le statut et la commande npm qui crée un projet, <RepositoryFact name="cliInitCommand" />. Les fonctionnalités de Core qu’apporte la génération prennent leur statut dans `TIER_FEATURES` à la même constante : la modifier change donc ces phrases dans toutes les langues et fait passer ces fonctionnalités sous **Disponible maintenant**. `src/data/__test__/cli-generation.test.ts` liste les messages, affiche les deux variantes dans toutes les langues et échoue si la formule « à venir » apparaît hors de la sélection. Les articles du blog, cette documentation et `public/llms.txt` le disent en prose et changent avec la version qui livre la génération.

## Newsletter

`Footer` affiche `NewsletterForm` (`src/presentation/components/custom/newsletter-form.tsx`) :

1. `subscribeToNewsletter` (limitée) enregistre une ligne `newsletter_subscriber` en attente et envoie `NewsletterConfirmationEmail`. Une adresse déjà abonnée reçoit `alreadySubscribed` et rien n’est écrit. Après <RepositoryFact name="recipientEmailsPerHour" /> e-mails de confirmation à une même adresse en une heure, elle renvoie `confirmationSent` sans rien écrire ni envoyer.
2. `/newsletter/confirm?token=` demande au visiteur de confirmer. Le bouton appelle `confirmNewsletterSubscription`, qui confirme l’abonnement et envoie `NewsletterNotificationEmail` à `CONTACT_EMAIL`.
3. `/newsletter/unsubscribe?token=` demande de la même façon avant que `unsubscribeFromNewsletter` désabonne. Ouvrir ou précharger l’un des liens ne change rien, donc un scanner de courriels ne peut abonner ni désabonner personne. Aucun e-mail ne renvoie vers `/newsletter/unsubscribe` : `unsubscribeUrl` dans `newsletter-subscriber.utils.ts` construit le lien, mais rien ne l’appelle.

## Écran d’administration (démo)

`/admin/landing-page` est une maquette statique d’éditeur : une liste de sections, un canevas et un panneau de propriétés construits à partir de constantes. Il ne modifie pas la page d’accueil.
