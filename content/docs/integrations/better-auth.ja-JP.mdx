Better Auth は、ユーザー、アカウント、セッション、検証トークンを Drizzle アダプター経由で D1 に保存します。メールアドレスとパスワードによるサインアップ（新しいアカウントはすぐにサインインし、確認済みのアドレスが必要なものは後回しにします）、GitHub と Google によるサインイン、パスワードリセット、メールアドレスの変更、TOTP による二要素認証、管理者によるユーザー管理、Polar のチェックアウトを提供します。HTTP API は `src/routes/api/auth.$.ts` から提供されます。`auth.server.ts` と `auth.client.ts` は、Better Auth の `basePath` をこのファイルが提供するパス `ROUTES.API_AUTH_BASE` に設定します。そのため、サーバーとブラウザのクライアントは 1 つの定数からパスを取得します。

## ファイル

| ファイル                                               | 役割                                                                                                                                                                                                               |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auth.server.ts`                                       | `betterAuth` インスタンス。プロバイダー、`admin`・`twoFactor`・`lastLoginMethod`・`tanstackStartCookies` の各プラグインとエリアが追加するプラグイン、許可するホスト、D1 によるレート制限、メールフックを設定します |
| `auth.client.ts`                                       | `authClient` とそのメソッド（`signIn`、`signUp`、`signOut`、`useSession`、`twoFactor` など）                                                                                                                       |
| `auth.routes.ts`                                       | `beforeLoad` 用のルートガード                                                                                                                                                                                      |
| `auth.middleware.ts`                                   | サーバー関数のミドルウェア: `withRequest`、`authorized`、`withRateLimit`、`RATE_LIMITS`                                                                                                                            |
| `auth.access.ts`                                       | エリアが宣言する権限ステートメントと付与から組み立てる `ac`、`ROLES`、`hasPermission`                                                                                                                              |
| `auth.roles.ts`                                        | `ROLE_CODES`、`ROLE_VALUES`、`DEFAULT_ROLE_CODE`、`isRole`                                                                                                                                                         |
| `auth.constants.ts`                                    | `AUTH_PROVIDER`：メールとパスワードのプロバイダー（`credential`）と OAuth プロバイダーの ID。**前回使用** バッジ用の `LOGIN_METHOD` と `LAST_LOGIN_METHOD_COOKIE`                                                  |
| `auth.session.ts`                                      | `getRequestSession`、`getCurrentSession` サーバー関数、`getCurrentSessionQuery`                                                                                                                                    |
| `auth.errors.ts`, `auth.zod.ts`, `auth.constraints.ts` | エラーキー、フォームのスキーマ、パスワードの制限                                                                                                                                                                   |
| `auth.hooks.ts`                                        | `enforceInputPolicy`：フォームのスキーマを Better Auth のエンドポイントに適用。`signInNewAccount`：新しいアカウントのセッション。`requireVerifiedEmail`：確認済みのアドレスが必要なものへのゲート                  |

## ルートガード

| ガード               | 使用箇所                         | 動作                                                                                             |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------ |
| `requireSignedIn`    | `/app`                           | セッションがなければ、ページを `redirect` としてサインインへリダイレクトし、セッションを返します |
| `requireAdmin`       | `/admin`                         | さらに `admin: ["access"]` 権限を要求し、持っていなければ `/app` へリダイレクトします            |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | サインイン済みのユーザーを `redirect`、またはロールに応じて `/admin` か `/app` へ送ります        |
| `redirectAfterAuth`  | `/auth/callback`                 | セッションを要求し、`redirect` またはロールに対応するワークスペースへリダイレクトします          |
| `redirectIfVerified` | `/auth/verify-email`             | アドレスが確認済みのセッションを `redirect`、またはロールに応じて `/admin` か `/app` へ送ります  |

ガードはクエリキャッシュを通じてセッションを読み込み、サインイン中のユーザーが変わると、`auth.session.ts` の `removeUserData` で、公開クエリ以外のキャッシュ済みのクエリをすべて削除します。

## サーバー関数

ページのガードが保護するのはナビゲーションだけです。そのため、保護されたサーバー関数はすべて `auth.middleware.ts` のミドルウェアで呼び出し元を改めてチェックします。

- `authorized(permission?)` はセッションを要求し、必要に応じて権限をチェックし、セッションを `context.auth` としてコンテキストに追加します。呼び出し元自身のデータに対する操作では、入力に含まれるユーザー ID ではなく、必ず `context.auth.user.id` を使います。
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)`（上限 <RepositoryFact name="sensitiveRateLimit" /> リクエスト、<RepositoryFact name="rateLimitWindowSeconds" unit="second" />ごと）または `RATE_LIMITS.TOKEN`（上限 <RepositoryFact name="tokenRateLimit" /> リクエスト、<RepositoryFact name="rateLimitWindowSeconds" unit="second" />ごと）は、`cf-connecting-ip` から取得したクライアント IP ごとに公開操作を制限します。
- 上記の両方に含まれる `withRequest` は、エラーを `AppError` のコードに変換します。Better Auth のエラーはエラーキー付きの `AUTH_API_ERROR` に、Zod のエラーは `VALIDATION` になり、予期しないエラーはログに記録されたうえで `INTERNAL_ERROR` として返されます。

## ロールと権限

`auth.roles.ts` は 2 つのロールを定義します。`admin` と `customer`（新規アカウントのデフォルト）です。各エリアは、自分のリソースのステートメントを `src/data/<area>.access.ts` で宣言し、ロールに付与します。現在は、認証エリアが `admin` と `settings`、商品エリアが `category` と `product`、コースエリアが `course` と `video`、決済エリアが `order` を宣言し、いずれも管理者に付与しています。`auth.access.ts` はそれらからアクセス制御とロールを組み立て、admin ロールには Better Auth の管理者用ステートメントも付与されます。`hasPermission({ permission, role })` はガード、ミドルウェア、UI で共有されます。[ロールと権限](/docs/guides/roles-and-permissions)を参照してください。

## メールとレート制限

`auth.server.ts` はほかのエリアを名指ししません。ほかのエリアが追加するプラグインは、認証エリア自身のリストがまとめます。

| リスト         | 各エリアが宣言するもの                                                                      | バレル                             | 使う側                                                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 認証プラグイン | `src/data/<area>.auth-plugins.ts`：プラグインと、Better Auth がレート制限の対象外にするパス | `src/data/auth-plugins.entries.ts` | `plugins` と `rateLimit.customRules`。認証のエリアが `haveIBeenPwned` を、ライセンスのエリアが削除されたアカウントのライセンスを取り消す `user.delete.before` フックを、Polar のエリアが Polar プラグインを追加します |

エリアのプラグインは `admin` と `twoFactor` の後、最後に置かなければならない `tanstackStartCookies` の前に入ります。Better Auth は、プラグインのユーザーとセッションのフィールドを、プラグインのリストから最初に展開されたリストの手前まで順に読み取るため、そうしたフィールドを追加するプラグインは `auth.server.ts` に置きます。認証にはメールが欠かせないため、メールフックは verification、account、user の各モジュールの送信関数を直接呼び出します。`sendVerifyEmail`、`sendExistingAccountEmail`、`sendResetPasswordEmail`、`sendPasswordChangedEmail`、`sendDeleteAccountEmail`、`sendChangeEmailConfirmationEmail` です。Better Auth 自身のレートリミッターは、`src/lib/rate-limit.ts` の `consumeRateLimit` を通じて、D1 の `rate_limit` テーブルに `auth:` プレフィックス付きでカウンターを保存します。この関数はアトミックなアップサートを使い、ストレージが利用できない場合はリクエストを拒否します。`auth.middleware.ts` の `clientAddress` は、このリミッターと同じ方法でリクエストのクライアントを特定します。`cf-connecting-ip` を使い、IPv6 アドレスは /64 単位でまとめます。Cookie のプレフィックスはブランディングの `APP_SLUG` です。`getRequestSession` は Cookie キャッシュを経由しないため、認可では常に D1 からセッションを読み込みます。
