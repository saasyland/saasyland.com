## Pliki tras

Trasy to płaskie pliki w `src/routes`. Kropki stają się segmentami ścieżki:

| Plik                              | URL                | Uwagi                                       |
| --------------------------------- | ------------------ | ------------------------------------------- |
| `__root.tsx`                      | wszystkie strony   | Shell dokumentu i główne przestrzenie nazw  |
| `_site.tsx`                       | brak               | Layout bez ścieżki z nagłówkiem witryny     |
| `_site._marketing.tsx`            | brak               | Layout bez ścieżki dla stron marketingowych |
| `_site._marketing.terms.tsx`      | `/terms`           | Strona w layoucie marketingowym             |
| `admin.tsx`                       | `/admin`           | Layout z guardem `requireAdmin`             |
| `admin.users.all.tsx`             | `/admin/users/all` | Strona w layoucie panelu administracyjnego  |
| `_site._marketing.blog.index.tsx` | `/blog`            | Strona indeksowa layoutu `blog`             |
| `_site.docs.$.tsx`                | `/docs/*`          | Trasa splat dla stron dokumentacji          |
| `api/auth.$.ts`                   | `/api/auth/*`      | Handler HTTP bez komponentu                 |

Identyfikatory w `createFileRoute("…")` to literały tekstowe utrzymywane przez generator routera, który zapisuje też `src/routeTree.gen.ts`. Pliki w folderach `__test__` są ignorowane. Każdy URL ma stałą w `ROUTES` (`src/routes.ts`), a linki używają `<Link to={ROUTES.X}>`.

## Trasy stron

Trasa strony definiuje komponent `<Name>Page`, stałą `NAMESPACE` bezpośrednio nad `export const Route` oraz loader, który ładuje metadane strony i przestrzeń nazw w jednym `Promise.all`:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Dodatkowe dane trafiają do tego samego `Promise.all`, na przykład `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` w `admin.users.all.tsx`. `pageHead` z `src/lib/seo.ts` buduje na podstawie `metadata` z loadera tagi tytułu, opisu, adresu kanonicznego, `hreflang`, Open Graph i obrazu podglądu; zobacz [Podglądy w wyszukiwarkach i mediach społecznościowych](/docs/features/seo).

## Trasy layoutów

Trasa layoutu definiuje komponent `<Name>Layout`, tablicę `NAMESPACES`, a w przypadku obszarów chronionych także guard w `beforeLoad`. Jej `NAMESPACES` kończą się przestrzeniami nazw, które dodają do niej inne obszary, a parametr wyszukiwania walidują strony, które go odczytują, tak jak strony licencji `/app` i `/app/license` robią to z `tier`:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "timezones", ...layoutNamespaces("/app")] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Guardy `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn` i `redirectAfterAuth` pochodzą z `src/integrations/better-auth/auth.routes.ts`.

## Szkielety ładowania [#loading-skeletons]

Większość nawigacji kończy się, zanim pojawi się jakikolwiek interfejs oczekiwania. Linki wstępnie ładują swoją trasę po najechaniu kursorem i dotknięciu, strony publiczne są prerenderowane, a router odczekuje domyślny czas `pendingMs` wynoszący jedną sekundę, zanim cokolwiek pokaże. Szkielet pojawia się tylko wtedy, gdy nawigacja trwa dłużej, zwykle przy pierwszej wizycie w danym obszarze przy wolnym połączeniu.

Nie ma domyślnego komponentu stanu oczekiwania. Każda trasa layoutu i strony ustawia własny `pendingComponent`, z wyjątkiem stron dokumentacji: `_site.docs.index.tsx` i `_site.docs.$.tsx` ustawiają zamiast tego `pendingMs: Number.POSITIVE_INFINITY`, więc nigdy nie pokazują własnego szkieletu, a `DocsPending` należy do layoutu `docs`. Każdy szkielet odwzorowuje stronę, którą zastępuje:

- **Szkielety stron**, takie jak `SignInPending` i `LegalPending`, znajdują się w pliku szkieletów danego obszaru i oznaczają swój element główny atrybutem `aria-busy="true"`. Są to pliki `custom/auth/auth-pending.tsx`, pliki panelu administracyjnego w `custom/admin/` (`admin-pending.tsx` dla layoutu, po jednym pliku `<area>-pending.tsx` na każdy obszar, np. `products-pending.tsx`, i wspólne bloki w `pending-blocks.tsx`), pliki aplikacji klienta w `custom/app/` (`app-pending.tsx` dla layoutu, `auth-pending.tsx` i `license-pending.tsx` oraz wspólny dla nich nagłówek strony w `pending-blocks.tsx`), pliki layoutu publicznego bezpośrednio w `custom/` (`marketing-pending.tsx` dla layoutu, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` i `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` i `custom/docs-pending.tsx`.
- **Szkielety layoutów**, takie jak `AuthPending` i `MarketingPending`, renderują ramę layoutu i wybierają szkielet strony dla bieżącej ścieżki z mapy, której kluczami są stałe z `ROUTES`. Layout panelu administracyjnego, aplikacja klienta i layout publiczny współdzielą jedną mapę, `PAGE_SKELETONS` w `src/data/skeletons.ts`, która łączy listy deklarowane przez każdy obszar w `src/data/<area>.skeletons.ts`. Dzięki temu po wejściu do obszaru z innego miejsca widać właściwą stronę. Elementy ramy, które nie potrzebują danych, takie jak `Wordmark` i `PageFrame`, renderują się naprawdę, a nagłówek witryny zostaje na ekranie, bo renderujący go layout `_site` nie ma loadera, na który musiałby czekać.
- **Placeholdery tekstu** to paski `Skeleton` z tokenem typograficznym prawdziwego elementu oraz `h-lh scale-y-70`, dzięki czemu każdy pasek wypełnia dokładnie jedną linię tekstu (line box). Bloki mają prawdziwe wysokości i promienie zaokrągleń. Listy biorą swoją długość z tych samych stałych co UI, np. `OAUTH_PROVIDERS` i `PASSWORD_RULES` w `src/data/auth.ts`.

Gdy dodajesz stronę, dodaj jej szkielet do pliku szkieletów obszaru, zarejestruj go w mapie szkieletu layoutu (w przypadku strony panelu administracyjnego, aplikacji klienta lub layoutu publicznego w `src/data/<area>.skeletons.ts` jej obszaru) i ustaw jako `pendingComponent` trasy.

## Inne aspekty tras

- **Parametry wyszukiwania** są parsowane przez `validateSearch` w trasie, na przykład parametr `tab` w `/admin/products` lub parametr `view` w `/admin/blog`. Schemat to `zod.object` zbudowany z helperów z `src/lib/search-params.ts`: `searchText()` i `searchFlag()` zwracają `undefined` dla brakującej, pustej lub nieprawidłowej wartości, a `searchChoice(choices, fallback)` zwraca wartość zapasową. `searchParam(schema)` zwraca `undefined`, chyba że wartość pasuje do innego schematu zod, np. tokenu newslettera.
- **Funkcje serwerowe używane przez jedną trasę** można zdefiniować w pliku trasy za pomocą `createServerFn`, tak jak `getBlogPosts` w `_site._marketing.blog.index.tsx`.
- **Endpointy HTTP** znajdują się w `src/routes/api`. Zobacz [Handlery HTTP w TanStack Start](/docs/architecture/api-layer).

## Router

`src/router.tsx` eksportuje `getRouter`, który dla każdego żądania tworzy nowy `QueryClient` i router. Konfiguruje:

- domyślne komponenty błędu i nieznalezionej strony z `presentation/components/custom`, bez domyślnego komponentu stanu oczekiwania (zobacz [Szkielety ładowania](#loading-skeletons))
- wstępne ładowanie przy intencji i domyślny czas świeżości danych (<RepositoryFact name="routerStaleTimeMinutes" unit="minute" />)
- `rewrite`, który usuwa prefiks locale z przychodzących URL-i i dodaje go z powrotem do generowanych linków
- integrację zapytań z SSR przez `setupRouterSsrQueryIntegration`
