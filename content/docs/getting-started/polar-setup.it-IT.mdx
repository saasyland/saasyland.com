Polar vende i tre piani ai prezzi che invia il checkout, emette le loro chiavi di licenza e addebita le imposte. Il codice si aspetta in Polar una configurazione precisa, e Polar non ti avvisa quando le due divergono: un prodotto senza un benefit di chiave di licenza incassa comunque il pagamento ma non emette alcuna chiave. `bun run polar:verify:<environment>` confronta Polar con il codice, e gli script di deploy lo eseguono prima di ogni deploy manuale.

## Produzione e sandbox

Polar gestisce due servizi separati. La produzione (`polar.sh`, API `api.polar.sh`) addebita carte reali; la sandbox (`sandbox.polar.sh`, API `sandbox-api.polar.sh`) accetta solo carte di test. Non condividono nulla: un account, un'organizzazione, un token, un prodotto, uno sconto o un webhook esiste in un solo servizio, quindi registrati separatamente su `sandbox.polar.sh` e configura ciascun servizio per conto suo.

| File di ambiente   | `POLAR_SERVER` | Organizzazione Polar |
| ------------------ | -------------- | -------------------- |
| `.env.development` | `sandbox`      | Sandbox              |
| `.env.preview`     | `sandbox`      | Sandbox              |
| `.env.production`  | `production`   | Produzione           |

Sviluppo e preview possono condividere un'unica organizzazione sandbox, ma il suo webhook raggiunge solo la preview: invia gli eventi all'host di preview, che scrive nel database D1 della preview, mentre `bun run dev` usa un proprio database locale. Un acquisto di prova fatto in sviluppo quindi non concede alcuna licenza in locale; prova gli acquisti dall'inizio alla fine sulla preview.

Non mettere mai un token, un ID di organizzazione o un ID di prodotto di produzione in `.env.development` o `.env.preview`. L'API della sandbox rifiuta un token di produzione, e con `POLAR_SERVER=production` un checkout di prova addebiterebbe una carta reale e assegnerebbe la licenza nel database locale o di preview. `polar:verify` rifiuta `POLAR_SERVER=production` per sviluppo e preview, e `POLAR_SERVER=sandbox` per la produzione.

## Organizzazione e token

Nella sandbox, poi in produzione:

1. Crea un'organizzazione e copia il suo ID dalle impostazioni dell'organizzazione in `POLAR_ORGANIZATION_ID`. Assegna a entrambe le organizzazioni lo slug indicato in `POLAR_ORGANIZATION_SLUG` (`src/integrations/polar/polar.constants.ts`), oppure sostituisci il valore della costante con il loro slug: l'[avviso e l'elenco di amministrazione degli ordini che non corrispondono a nessun account](/docs/features/licences#orders-that-match-no-account) collegano ogni ordine alla dashboard di Polar con quello slug.
2. Nelle impostazioni dell'organizzazione, crea un token di accesso dell'organizzazione con questi scope, e nessun altro, e copialo in `POLAR_ACCESS_TOKEN`.

| Scope                     | Necessario per                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkouts:write`         | `startCheckout`, che crea il checkout con l'SDK di Polar (`polar.checkouts.create`)                                                                                                                                                                                                                                                                                                               |
| `customer_sessions:write` | Il link al portale clienti, `/api/auth/customer/portal`                                                                                                                                                                                                                                                                                                                                           |
| `license_keys:write`      | La lettura di una chiave e delle sue attivazioni, l'attivazione di un dispositivo e la rimozione di un'attivazione (`deactivateLicense` e l'[API delle licenze della CLI](/docs/features/cli-licence-api)) e, per un upgrade, l'aumento del limite di attivazioni della chiave e la disattivazione della chiave che Polar emette per l'ordine di upgrade                                          |
| `orders:read`             | Gli handler dei webhook, che leggono l'ordine alla base di una licenza e il cliente attuale di un ordine il cui evento non corrisponde a nessun account, il prezzo dell'upgrade, che somma quanto il cliente ha pagato per le licenze, la pagina di un ordine nell'admin, che legge l'ordine e la sua fattura, e `orders:backfill`, che copia lo sconto e il paese di fatturazione di ogni ordine |
| `organizations:read`      | `polar:verify`, che legge se la localizzazione del checkout è attiva, il comportamento fiscale predefinito e gli host che possono incorporare il checkout                                                                                                                                                                                                                                         |
| `products:read`           | `polar:verify`                                                                                                                                                                                                                                                                                                                                                                                    |
| `webhooks:read`           | `polar:verify`                                                                                                                                                                                                                                                                                                                                                                                    |

Uno scope di scrittura include la lettura, quindi `license_keys:write` copre anche la lettura delle chiavi. Un token dell'organizzazione agisce già per la propria organizzazione. `polar:verify` invia comunque `POLAR_ORGANIZATION_ID` come parametro di query `organization_id`, come fa l'elenco degli ordini per un upgrade, quindi l'ID di un'altra organizzazione si traduce in prodotti mancanti.

## Prodotti

Crea un prodotto per ogni piano: un acquisto una tantum, non un abbonamento, con un prezzo fisso in `DEFAULT_CURRENCY_CODE` (dollari statunitensi) pari a `TIER_PRICES` in `src/data/license.ts`. Copia l'ID di ogni prodotto nella sua chiave.

| Piano    | Chiave                      | Prezzo                        | Attivazioni per chiave              |
| -------- | --------------------------- | ----------------------------- | ----------------------------------- |
| Core     | `POLAR_PRODUCT_ID_CORE`     | <TierPrice tier="core" />     | <ActivationLimit tier="core" />     |
| Complete | `POLAR_PRODUCT_ID_COMPLETE` | <TierPrice tier="complete" /> | <ActivationLimit tier="complete" /> |
| Agency   | `POLAR_PRODUCT_ID_AGENCY`   | <TierPrice tier="agency" />   | <ActivationLimit tier="agency" />   |

Polar memorizza un prezzo nell'unità minore della valuta, i centesimi per i dollari statunitensi, e `polar:verify` converte `TIER_PRICES` allo stesso modo prima di confrontarli. Ignora i prezzi archiviati.

## Chiavi di licenza

Crea per ogni piano un benefit di tipo **License Keys** e collegalo solo al prodotto di quel piano:

- **Attivazioni**: limitate al numero indicato nella tabella qui sopra, `LICENSE_ACTIVATION_LIMITS` in `src/modules/license/license.constants.ts`. Permettere ai clienti di gestire le proprie attivazioni in Polar è facoltativo, perché `/app/license` le elenca e le rimuove da sé.
- **Scadenza**: nessuna. Le chiavi non scadono mai, dato che l'acquisto è un pagamento una tantum.
- **Limite di utilizzo**: nessuno.
- **Prefisso**: a tua scelta; `polar:verify` non lo controlla.

Ogni prodotto deve avere esattamente un benefit di chiave di licenza; altri benefit accanto a esso vanno bene. Quando Polar assegna il benefit, il webhook `benefit_grant.created` salva la chiave sulla licenza dell'acquirente.

## Casella del consenso [#consent-checkbox]

L'acquirente dà il consenso alla fornitura immediata nel checkout di Polar, e questo campo è l'unico punto in cui viene chiesto (vedi [Licenze](/docs/features/licences#consent-to-immediate-supply)); Polar lo registra sull'ordine. Crea un campo personalizzato nell'organizzazione e collegalo ai tre prodotti:

- **Tipo**: casella di controllo.
- **Slug**: <RepositoryFact name="licenseWithdrawalConsentField" />, `LICENSE_CHECKOUT_FIELD.WITHDRAWAL_CONSENT` in `src/modules/license/license.constants.ts`. L'ordine salva la casella spuntata sotto questa chiave in `custom_field_data`.
- **Etichetta**: esattamente `WITHDRAWAL_CONSENT_FIELD.label` di `src/lib/polar.ts`, la frase in inglese costruita a partire da `REFUND_TERMS.WITHDRAWAL_DAYS` che termina con un link Markdown alla Politica sui rimborsi di produzione.
- **Nome**: a tua scelta; `WITHDRAWAL_CONSENT_FIELD.name` è quello che suggerisce il codice, e `polar:verify` non lo controlla.
- **Obbligatorio** su ciascuno dei tre prodotti. Gli altri campi che i prodotti richiedono possono restare.

`startCheckout` non invia alcun valore per il campo, quindi la casella parte vuota e la spunta l'acquirente; Polar non accetta il pagamento finché una casella obbligatoria è vuota. Polar conserva solo i valori dei campi che il prodotto richiede: prima che il campo sia collegato un checkout funziona comunque, ma l'ordine non registra alcun consenso e la [conferma dell'acquisto](/docs/features/licences#purchase-confirmation) indica invece il diritto di recesso previsto dalla legge.

Creare il campo e collegarlo a un prodotto richiede gli scope `custom_fields:write` e `products:write`, che il token descritto sopra non ha. Crealo e collegalo nella dashboard di Polar, oppure tramite l'API con un token separato che li abbia. `polar:verify` legge i campi collegati dall'elenco dei prodotti, quindi non gli serve nessun altro scope.

## Lingua del checkout [#checkout-language]

Polar mostra il suo checkout nella lingua richiesta da `startCheckout` solo finché la localizzazione del checkout è attiva per l'organizzazione; altrimenti ogni checkout si apre in inglese. Attivala nelle impostazioni dell'organizzazione. La [guida alla localizzazione del checkout](https://polar.sh/docs/features/checkout/localization) di Polar la chiama feature flag, e l'API la restituisce come `feature_settings.checkout_localization_enabled` sull'organizzazione. `POLAR_CHECKOUT_LANGUAGES` in `src/integrations/polar/polar.constants.ts` elenca le lingue che il codice richiede, e `polar:verify` fallisce finché la localizzazione è disattivata.

## Comportamento fiscale [#tax-behaviour]

Le schede dei prezzi dicono che i prezzi sono in dollari statunitensi, che nell'UE l'IVA è inclusa e che negli Stati Uniti, in Canada e in India l'imposta sulle vendite si aggiunge al checkout. Polar applica le imposte in questo modo quando il comportamento fiscale predefinito dell'organizzazione è basato sulla località, quindi impostalo così nelle impostazioni dell'organizzazione. L'API lo restituisce come `default_tax_behavior` sull'organizzazione, e `polar:verify` fallisce finché non è `location` (`POLAR_TAX_BEHAVIOR.LOCATION` in `src/lib/polar.ts`).

## Incorporamento [#embedding]

I pulsanti di acquisto aprono il checkout di Polar sopra il sito in un iframe ([Licenze](/docs/features/licences#the-checkout-over-the-page)), e Polar permette di incorporare il suo checkout in un frame solo agli host elencati dalla sua organizzazione. In **Settings > Embedding**, elenca gli host che `appHostsForMode` serve in ciascun ambiente, senza schema e con la porta quando c'è:

| Ambiente      | Organizzazione | Host                               |
| ------------- | -------------- | ---------------------------------- |
| `development` | Sandbox        | `localhost:3000`, `127.0.0.1:3000` |
| `preview`     | Sandbox        | `preview.saasyland.com`            |
| `production`  | Produzione     | `saasyland.com`                    |

Una voce `*.saasyland.com` copre `preview.saasyland.com` ma non `saasyland.com`. Polar aggiunge da sé all'elenco i domini verificati dell'organizzazione. L'API restituisce l'elenco come `embed_hosts` sull'organizzazione, e `polar:verify` fallisce finché manca un host dell'ambiente. Finché non è elencato, il frame di Polar resta vuoto su quell'host e, dopo <RepositoryFact name="checkoutOverlayGraceSeconds" unit="second" />, il pulsante manda invece l'acquirente alla pagina di checkout di Polar, così gli acquirenti possono comunque pagare, solo un po' più tardi.

## Prezzi regionali [#regional-prices]

I prezzi regionali non richiedono nulla in Polar. Per un acquirente in un paese di `PPP_TIERS` (`src/modules/license/license.pricing.ts`), le cui fasce tolgono <RegionalDiscounts />, `startCheckout` invia il prezzo stesso: `regionalPrice` arrotonda per difetto il prezzo del piano ai dollari interi, l'importo che mostrano le schede dei piani, e il checkout lo porta in `prices` come prezzo fisso per il prodotto del piano valido solo per quel checkout, così il prodotto mantiene il suo prezzo di `TIER_PRICES`. Un [upgrade](/docs/features/licences#upgrades) invia il suo prezzo allo stesso modo. Gli sconti creati da una configurazione precedente non vengono più usati e puoi eliminarli.

## Webhook

Crea un endpoint del webhook per ogni ambiente distribuito, nell'organizzazione che quell'ambiente usa.

| Ambiente     | Organizzazione | URL                                                     |
| ------------ | -------------- | ------------------------------------------------------- |
| `preview`    | Sandbox        | `https://preview.saasyland.com/api/auth/polar/webhooks` |
| `production` | Produzione     | `https://saasyland.com/api/auth/polar/webhooks`         |

L'host viene da `DEPLOYED_HOSTS` e il percorso da `ROUTES`. Scegli il formato raw, mantieni l'endpoint abilitato e iscrivilo esattamente agli eventi di `POLAR_EVENTS` (`src/integrations/polar/polar.webhooks.ts`), che riunisce gli eventi di tutti gli handler di `POLAR_EVENT_HANDLERS` (vedi [Pagamenti](/docs/features/payments#webhooks)). Oggi la licenza gestisce gli eventi di `LICENSE_WEBHOOK_EVENTS` (`src/modules/license/license.constants.ts`) e le copie degli ordini e degli abbonamenti quelli di `ORDER_WEBHOOK_EVENTS` e `SUBSCRIPTION_WEBHOOK_EVENTS`:

| Evento                  | Area delle licenze                                                       | Area di fatturazione               |
| ----------------------- | ------------------------------------------------------------------------ | ---------------------------------- |
| `benefit_grant.created` | Salva la chiave di licenza                                               |                                    |
| `benefit_grant.revoked` | Revoca la licenza                                                        |                                    |
| `order.created`         |                                                                          | Copia l'ordine in D1               |
| `order.paid`            | Assegna la licenza                                                       | Aggiorna la copia dell'ordine      |
| `order.refunded`        | Segna la licenza come rimborsata quando l'ordine è rimborsato per intero | Aggiorna la copia dell'ordine      |
| `order.updated`         |                                                                          | Aggiorna la copia dell'ordine      |
| `subscription.created`  |                                                                          | Copia l'abbonamento in D1          |
| `subscription.updated`  |                                                                          | Aggiorna la copia dell'abbonamento |

Quando un'area inizia a gestire un evento, aggiungi l'evento a ogni endpoint prima di distribuire quel codice. Il codice distribuito fino ad allora risponde 200 a un evento che nessuna area gestisce e non ne fa nulla, quindi aggiungere prima l'evento non fa danni, e `polar:verify` fa fallire il deploy finché un endpoint non invia tutti gli eventi di `POLAR_EVENTS`.

Copia il secret di firma dell'endpoint in `POLAR_WEBHOOK_SECRET` nello stesso file di ambiente. Lo sviluppo non ha bisogno di un endpoint, perché Polar non può raggiungere `localhost`.

Non aggiungere mai un endpoint di preview all'organizzazione di produzione, né un endpoint di produzione alla sandbox: i pagamenti reali arriverebbero alla preview, oppure gli acquisti di prova assegnerebbero licenze in produzione.

## Controllare la configurazione

```sh
bun run polar:verify:development
bun run polar:verify:preview
bun run polar:verify:production
```

Ogni script legge le chiavi Polar da `.env.<environment>` e invia solo richieste GET all'API indicata da `POLAR_SERVER`: legge l'organizzazione ed elenca i suoi prodotti e gli endpoint dei webhook, e non modifica nulla. Controlla che:

- il file di ambiente imposti ogni chiave Polar, con `POLAR_SERVER=sandbox` per sviluppo e preview e `POLAR_SERVER=production` per la produzione;
- la localizzazione del checkout sia attiva per l'organizzazione, il suo comportamento fiscale predefinito sia basato sulla località e l'organizzazione permetta a ogni host dell'ambiente di incorporare il suo checkout;
- ogni `POLAR_PRODUCT_ID_*` indichi un prodotto dell'organizzazione che non sia né archiviato né un abbonamento, i cui prezzi siano fissi, in `DEFAULT_CURRENCY_CODE` e pari a `TIER_PRICES`;
- ogni prodotto abbia esattamente un benefit di chiave di licenza con il limite del piano preso da `LICENSE_ACTIVATION_LIMITS`, senza scadenza e senza limite di utilizzo;
- ogni prodotto richieda il campo casella di controllo <RepositoryFact name="licenseWithdrawalConsentField" /> con l'etichetta di `WITHDRAWAL_CONSENT_FIELD`;
- preview e produzione abbiano un endpoint raw abilitato al loro URL del webhook, firmato con `POLAR_WEBHOOK_SECRET` e iscritto esattamente a `POLAR_EVENTS`;
- nessun endpoint invii eventi all'host di un ambiente che usa l'altro servizio Polar.

`polar:verify` è il controllo di deploy dell'area Polar, perché i suoi script si chiamano `polar:verify:<environment>`. Per questo `deploy:preview` e `deploy:production` lo eseguono tramite `scripts/run-deploy-checks.ts`, dopo `scripts/verify-bindings.ts` e `scripts/prepare-deploy-secrets.ts` e prima della build. I deploy della CI non eseguono nessun controllo di deploy, `polar:verify` compreso: `deploy-reusable.yml` non ha alcun passaggio per `scripts/run-deploy-checks.ts`, gli ambienti GitHub non contengono alcun token Polar, e il Worker mantiene i secret Polar già impostati in Cloudflare. Esegui tu stesso `polar:verify` dopo ogni modifica in Polar.

## Quando fallisce

Lo script termina con un errore che elenca ogni problema trovato, uno per riga:

```text
Polar production does not match the code for production:
The core product (POLAR_PRODUCT_ID_CORE) has 0 licence-key benefits; it needs exactly one.
A webhook endpoint posts to https://preview.saasyland.com/api/auth/polar/webhooks, the preview host, from this Polar production organisation; remove it.
```

Un errore interrompe il deploy prima di qualsiasi build, migrazione o caricamento. Lo script non modifica mai Polar: correggi Polar, poi eseguilo di nuovo. Ogni messaggio indica la chiave, la costante o l'impostazione da correggere:

- **`Set … in .env.<environment>`**: una chiave Polar manca o è vuota, oppure `POLAR_SERVER` indica il servizio sbagliato.
- **`rejects POLAR_ACCESS_TOKEN`**: il token non è valido, è stato revocato o appartiene all'altro servizio, come un token di produzione in `.env.preview`.
- **`lacks the … scope`**: crea un token con gli scope indicati sopra.
- **`names no product of the organisation`**: l'ID del prodotto o `POLAR_ORGANIZATION_ID` è sbagliato, oppure appartiene all'altro servizio.
- **Un prezzo o una chiave di licenza**: modificalo in Polar perché corrisponda al codice. Quando un valore commerciale cambia di proposito, modifica prima `TIER_PRICES` o `LICENSE_ACTIVATION_LIMITS`, poi Polar.
- **`does not ask for the … checkout field`, `without requiring it`, `instead of a checkbox` o `label differs`**: crea, collega o correggi la [casella del consenso](#consent-checkbox). Quando il testo cambia di proposito, modifica prima `WITHDRAWAL_CONSENT_FIELD.label`, poi l'etichetta in Polar.
- **`Checkout localization is off`**: attiva la [localizzazione del checkout](#checkout-language) per l'organizzazione.
- **`default tax behaviour is not location`**: imposta il [comportamento fiscale](#tax-behaviour) dell'organizzazione in modo che sia basato sulla località.
- **`does not let … embed its checkout`**: aggiungi l'host indicato dal messaggio in [Settings > Embedding](#embedding).
- **Un endpoint del webhook**: correggi l'endpoint indicato dal messaggio, oppure rimuovi un endpoint che invia eventi all'host di un altro ambiente.
