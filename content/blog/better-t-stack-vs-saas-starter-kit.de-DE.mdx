## Vorweg: Es ist sehr gut, und Sie sollten es wahrscheinlich nutzen

[Better-T-Stack](https://better-t-stack.dev/) ist eine CLI, die durchgängig typsichere TypeScript-Projekte erzeugt. Es steht unter der MIT-Lizenz, sein README verspricht „kostenlos und Open Source: für immer“, es hat **5.636 GitHub-Sterne** und wird rund **2.476-mal pro Woche** von npm geladen.

Die Optionsmatrix ist die beste im ganzen Ökosystem, und das mit großem Abstand:

| Schicht         | Was es bietet                                                                                                                    |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Frontend        | React mit TanStack Router, React Router oder TanStack Start, Next.js, Nuxt, Svelte, Solid, Astro, React Native oder keins        |
| Backend         | Hono, Express, Fastify, Elysia, selbst gehostetes Fullstack, Convex oder keins                                                   |
| API             | tRPC, oRPC oder keine                                                                                                            |
| Runtime         | Bun, Node.js, Cloudflare Workers                                                                                                 |
| Datenbank       | SQLite, PostgreSQL, MySQL, MongoDB oder keine                                                                                    |
| ORM             | Drizzle, Prisma, Mongoose oder keins                                                                                             |
| Auth            | Better Auth oder Clerk, optional                                                                                                 |
| Datenbank-Setup | Turso, Neon, Supabase, Prisma Postgres, MongoDB Atlas, Cloudflare D1, Docker                                                     |
| Add-ons         | Turborepo, Nx, PWA, Tauri, Electrobun, Biome, Lefthook, Husky, Starlight, Fumadocs, Ultracite, Oxlint, MCP, OpenTUI, WXT, Skills |
| Beispiele       | Todo, AI                                                                                                                         |

So viele Kombinationen dazu zu bringen, ein Projekt zu erzeugen, das tatsächlich die Typprüfung besteht und läuft, ist echte, anspruchsvolle Ingenieursarbeit. Es gibt das Werkzeug außerdem als Claude-Code-Plugin mit einem MCP-Server, sodass ein Agent einen gültigen Stack planen und erzeugen kann, statt Boilerplate von Hand zu schreiben. Das ist sorgfältig durchdacht.

**Wenn Sie einen Prototyp, ein internes Tool, ein Portfolio-Projekt, eine App, die kein SaaS ist, oder irgendetwas bauen, bei dem Sie den Unterbau lernen wollen, hören Sie hier auf zu lesen und führen Sie `bun create better-t-stack@latest` aus.** Es ist kostenlos, es ist hervorragend, und nichts im Folgenden spricht dagegen.

Der Rest richtet sich an einen bestimmten Leser: an die Person, die entscheiden will, ob die kostenlose CLI für ein SaaS ausreicht, für das sie Geld verlangen möchte.

## Ein Stack ist kein Produkt

Das README von Better-T-Stack fasst seine Philosophie in vier Zeilen zusammen, und die zweite ist der ganze Vergleich:

> Stellen Sie Ihren eigenen Stack zusammen: Sie wählen nur die Teile, die Sie brauchen, nichts darüber hinaus.
> **Minimale Vorlagen: schlanke Grundgerüste ohne jeden Ballast.**
> Aktuelle Abhängigkeiten: standardmäßig immer aktuelle, stabile Versionen.
> Kostenlos und Open Source: für immer.

Das ist keine versteckte Einschränkung. Es ist das Design, offen ausgesprochen, und das Projekt liefert genau, was es verspricht. Der Beleg steht in der letzten Zeile der Tabelle oben: Die mitgelieferten Beispiele sind **Todo** und **AI**. Eine Todo-Liste und ein Chat. Das sind die kanonischen Demonstrationen dafür, dass die Verdrahtung funktioniert, und es sind die richtigen Beispiele für ein Werkzeug, dessen Aufgabe die Verdrahtung ist.

Die ehrliche Einordnung lautet also nicht „einem kostenlosen Werkzeug fehlen Features“. Sie lautet:

**Better-T-Stack erzeugt einen Stack. Ein SaaS-Starter-Kit erzeugt ein Produkt.**

Beide sind Scaffolder. Sie hören an unterschiedlichen Linien auf. Better-T-Stack hört auf, wenn das Frontend das Backend aufrufen kann und das Backend die Datenbank erreicht, typsicher, mit Ihrer Wahl aus neun Frontends und sechs Backends. Das ist ein vertretbarer Punkt, um aufzuhören, und dort sollten die meisten Scaffolder aufhören.

Ein SaaS-Starter-Kit hört woanders auf: wenn sich eine Person registrieren, einer Organisation beitreten, eine Rolle zugewiesen bekommen, monatlich belastet werden, eine E-Mail darüber erhalten und von Ihnen im Admin-Panel angesehen werden kann, wenn sie sich verwirrt meldet. Alles zwischen diesen beiden Linien ist die Rechnung.

## Die aufgeschlüsselte Rechnung

Das liegt zwischen `bun create better-t-stack@latest` und einem Produkt, für das Sie Geld verlangen können. Die Schätzungen gehen von einem kompetenten Entwickler aus, der jeden Posten auf einem Niveau baut, das er einem zahlenden Unternehmen vorlegen würde. Nicht enthalten ist die Zeit für die Entscheidung, wie man es umsetzt, und die ist bei mehreren Zeilen größer als die Implementierung.

| Posten                         | Better-T-Stack | Was „fertig“ tatsächlich bedeutet                                                                                                  | Stunden         |
| ------------------------------ | :------------: | ---------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| Typsichere Stack-Verdrahtung   |       Ja       | Frontend, API, Runtime, Datenbank und ORM stimmen auf Typebene überein                                                             | 0               |
| Konfigurierte Auth-Bibliothek  |    Optional    | Better Auth oder Clerk eingerichtet: Anmelden, Abmelden, Sessions                                                                  | 0               |
| Organisationen und Einladungen |      Nein      | Schema, Einladungstokens, Ablauf, Platzzählung, Eigentümerwechsel, der Fall eines austretenden Mitglieds                           | 25 bis 40       |
| Rollen und Berechtigungen      |      Nein      | Eine Policy-Schicht, die jede Abfrage und Route konsultiert, plus die UI, die sie widerspiegelt                                    | 20 bis 30       |
| Mandantenisolation             |      Nein      | Auf der Abfrageebene statt auf der View-Ebene durchgesetzt und gegen einen zweiten Mandanten getestet                              | 15 bis 25       |
| Abrechnung                     |      Nein      | Nicht der Checkout. Anteilige Verrechnung, Upgrades, Downgrades, Mahnwesen, Rechnungen, idempotente Webhooks, Abgleich             | 25 bis 40       |
| Transaktions-E-Mails           |      Nein      | Vorlagen, Vorschauen, Texte pro Sprache, Zustellbarkeit, Abmeldung, Compliance                                                     | 15 bis 25       |
| Admin-Panel                    |      Nein      | Zehn Bereiche, die niemand sieht, ohne die Sie aber nicht arbeiten können: Nutzer, Organisationen, Abos, Erstattungen, Logs, Flags | 40 bis 60       |
| Komponentenbibliothek          |      Nein      | Barrierefrei, mit Theming, getestet und von Ihnen bearbeitbar statt in einem Paket eingeschlossen                                  | 30 bis 50       |
| Internationalisierung          |      Nein      | Nicht Übersetzung. Routing, Formatierer, Pluralregeln und eine Prüfung der Schlüsselparität, die den Build fehlschlagen lässt      | 20 bis 35       |

Bei 150 $ pro Stunde sind das **42.000 $ bis 69.750 $**. Setzen Sie Ihren eigenen Stundensatz ein, und die Zahl verschiebt sich, das Fazit aber nicht. Gegenüber einem Einmalpreis von 249 $ ist der Vergleich für jeden eindeutig, dessen Zeit einen Preis hat.

Aber die Stunden sind das langweilige Argument, und ich bringe lieber das interessante.

## Der Teil, der sich nicht in Stunden messen lässt

Sehen Sie sich vier Zeilen dieser Tabelle an: **Mandantenisolation, Rollen und Berechtigungen, Webhook-Idempotenz und das Widerrufen von Sessions.**

Sie teilen eine Eigenschaft, die keine der anderen Zeilen hat. **Die falsche Implementierung besteht das Review, funktioniert in der Entwicklung und lässt sich korrekt vorführen.**

Ein Mandantenfilter, der in der View-Schicht statt in der Abfrageschicht angewendet wird, funktioniert mit einem Mandanten perfekt. Er funktioniert in Ihren Tests perfekt, weil Ihre Fixtures nur einen Mandanten haben. Er versagt an dem Tag, an dem die Daten Ihres zweiten Kunden im Dashboard Ihres ersten Kunden auftauchen, und das ist dann kein Bug-Report, sondern ein Anruf.

Ein Webhook-Handler ohne Idempotenzschlüssel funktioniert bei jedem Test, weil Sie nie dasselbe Event zweimal senden. Stripe tut das bei einem Retry, und dann wurde jemand doppelt belastet oder hat einen Plan doppelt erhalten.

Eine Berechtigungsprüfung, die die Rolle aus der Session liest, statt sie erneut aus der Datenbank zu lesen, funktioniert so lange, bis jemand herabgestuft wird und seine alte Session behält.

Das sind keine schwierigen Probleme. Es sind Probleme, bei denen **ein Fehler unsichtbar bleibt, bis er teuer wird**, und das ist ein völlig anderes Risikoprofil als „das dauert 40 Stunden“. Mit mehr Stunden kaufen Sie sich da nicht heraus, weil Sie nicht wissen, dass Sie die Stunden brauchen. Sie vermeiden diese Probleme, indem Sie auf einem Fundament beginnen, auf dem jemand den Fehler bereits gemacht und behoben hat und auf dem es jetzt einen Test gibt, der fehlschlägt, wenn der Fehler zurückkehrt.

Dafür ist ein kostenpflichtiges Starter-Kit eigentlich da, nicht für die Stundenzahl.

## Wie die kostenpflichtige Seite konkret aussieht

Um konkret statt abstrakt zu bleiben: Das bedeutet „bereits gelöst“ in dieser Codebasis, mit Zahlen, die aus dem Testlauf ausgelesen und nicht in eine Marketing-Datei getippt wurden.

**Ein Coverage-Gate statt eines Coverage-Badges.** <RepositoryCount fact="testFiles" /> Testdateien und vier Schwellen in der Konfiguration:

```ts
coverage: {
  thresholds: { branches: 100, functions: 100, lines: 100, statements: 100 },
}
```

Ein Branch-Coverage-Gate bei 100 zwingt Sie, genau die Fehlerzweige aus dem vorigen Abschnitt zu testen. Das ist der Mechanismus, nicht die Zahl.

**Klare Zuständigkeiten und typisierte Prüfungen.** Die öffentliche Referenz-App gruppiert Operationen nach Feature und konfiguriert Vite+ so, dass es sowohl Lint-Regeln als auch Typen prüft:

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

Routendateien koordinieren die Navigation; Feature-Use-Cases liegen in `src/modules`; die Einrichtung von Drittanbietern liegt in `src/integrations`; die UI liegt in `src/presentation`. Server-only-Module halten Worker-Bindings vom Client fern. Die Zuständigkeit innerhalb dieser Ordner ist eine Konvention, die im Review geprüft wird, keine Importbeschränkung, die dieser Ausschnitt durchsetzt.

**Strenge ohne Hintertür.** `strict`, dazu `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` und `noImplicitReturns`. `typescript/no-explicit-any` ist ein Fehler, und die Lint-Kategorien sind als Fehler konfiguriert, sodass die Prüfung mit einem Fehler-Exit-Code endet.

**Optionale Features statt einer starren Vorlage.** Der [Konfigurator](/#cli) stellt <RepositoryCount fact="cliQuestions" /> Fragen und bietet vier Extras: einen Shop mit Beispielprodukten, einen Abo-Kurs, einen visuellen Page Builder und einen visuellen Beitragseditor. Wer eines davon aktiviert, erhält ein zusätzliches Modul. Bleibt es deaktiviert, existiert dieser Code in Ihrem Repository nicht.

Nichts davon ist Kritik an Better-T-Stack. Es beschreibt, wo die beiden Produkte aufhören.

## Wann Better-T-Stack die richtige Antwort ist

Ordentlich formuliert, denn ein Vergleich, der immer die kostenpflichtige Option empfiehlt, ist Werbung und kein Vergleich.

**Nutzen Sie Better-T-Stack, wenn:**

- Sie einen Prototyp bauen und das Ding in einem Monat vielleicht nicht mehr existiert.
- Sie lernen und der Unterbau genau der Punkt ist. Einmal selbst Authentifizierung zu bauen ist eine wirklich wertvolle Lektion, und niemand sollte sie Ihnen ausreden.
- Ihr Produkt kein SaaS ist. Keine Organisationen, keine Abos, kein Adminbereich. Ein Tool, ein Spiel, ein internes Dashboard, eine Kunden-Website.
- Sie bereits eine interne Bibliothek für die langweiligen drei Viertel haben, wie viele Agenturen und erfahrene Teams.
- Ihr Stack außerhalb dessen liegt, was ein kostenpflichtiges Kit bietet. Nuxt, Svelte, Solid, Astro, React Native, Convex, tRPC. Better-T-Stack deckt all das ab, und kein kostenpflichtiges Starter-Kit deckt das meiste davon ab.
- Ihr Budget wirklich bei null liegt. Das ist eine legitime Einschränkung, und dafür muss sich niemand schämen. Better-T-Stack ist eine bessere kostenlose Option als die kostenlose Stufe jedes kostenpflichtigen Produkts.

**Ziehen Sie in Betracht zu bezahlen, wenn:**

- Sie ein einziges Produkt bauen, für das Sie Unternehmen zur Kasse bitten wollen, mit Nutzerplätzen, Rollen, Rechnungen und einem Sicherheitsfragebogen in Ihrer Zukunft.
- Sie Organisationen und Abrechnung schon einmal gebaut haben und noch genau wissen, wie lange die langweiligen Teile gedauert haben.
- Sie ein Test-Gate wollen, das Sie nicht selbst schreiben mussten, denn eine Coverage-Suite von null zu schreiben ist der Punkt, zu dem nie jemand kommt.
- Sie die Architekturgrenzen durchgesetzt statt nur beabsichtigt haben wollen.
- Ihre Zeit einen Preis hat und 280 bis 465 Stunden davon mehr kosten als ein paar hundert Dollar.

## Sie sind eigentlich keine Konkurrenten

Das Nützlichste, was ich Ihnen sagen kann: Das hier ist kein Zweikampf.

Better-T-Stack ist ein Scaffolder für _jedes_ TypeScript-Projekt, über neun Frontends und sechs Backends hinweg. Ein SaaS-Starter-Kit ist ein Fundament für _eine Art_ von Geschäft. Die Überschneidung sind die zehn Minuten am Anfang, in denen beide ein Projekt schreiben. Danach erledigen sie unterschiedliche Aufgaben.

Der Fehler, den Sie vermeiden sollten, ist nicht, „das kostenlose zu wählen“. Es ist, eines von beiden zu wählen, ohne zu wissen, welche der beiden Aufgaben Sie erledigt haben wollten. Ein Gründer, der einen schönen typsicheren Stack erzeugt und dann sechs Monate damit verbringt, Organisationen und Abrechnung zu bauen, hat kein Geld gespart. Er hat die Rechnung in der Währung bezahlt, die auf keiner Rechnung auftaucht.

Die Abrechnung dauert 25 bis 40 Stunden, denn der Checkout ist das leichte Zehntel: Der Rest sind anteilige Verrechnung, Upgrades, Downgrades, Mahnwesen, Rechnungshistorie, idempotente Webhook-Verarbeitung und der Abgleichsjob, der den Webhook auffängt, den Sie nie erhalten haben. Die erste Zahlung zu bekommen ist nicht dasselbe, wie zuverlässig abrechnen zu können.

</Accordion>

<Accordion title="Kann ich Better-T-Stack und ein kostenpflichtiges Starter-Kit zusammen verwenden?">

Nicht sinnvoll im selben Projekt, denn beide erzeugen das Fundament, und Sie haben nur ein Fundament. Sie passen zu verschiedenen Projekten. Viele Entwickler nutzen einen kostenlosen Scaffolder für Prototypen und interne Tools und ein kostenpflichtiges Fundament für das Produkt, das Geld verdienen muss. Das ist eine sinnvolle Aufteilung und kein Widerspruch.

</Accordion>

<Accordion title="Enthält Better-T-Stack Authentifizierung?">

Optional, als Verdrahtungsschritt: Es kann Better Auth oder Clerk einrichten. Damit haben Sie korrekt konfiguriertes An- und Abmelden. Was Sie damit nicht bekommen, sind Organisationen, Einladungen, Platzzählung, rollenbasierte Aktionen, erzwungene Zwei-Faktor-Authentifizierung, Impersonation für den Support oder das Widerrufen von Sessions. All das sind eigene Features auf Basis der Bibliothek.

</Accordion>

<Accordion title="Was ist besser für KI-Coding-Agenten?">

Beides sind gute Ausgangspunkte, aus unterschiedlichen Gründen. Ein minimales Grundgerüst gibt einem Agenten einen kleinen Kontext und nichts, was ihn verwirren könnte. Ein größeres Fundament mit durchgesetzten Grenzen gibt ihm funktionierende Beispiele und einen Build, der fehlschlägt, wenn er abdriftet. Die schlechteste Option ist die, die keines von beiden bietet: eine große Codebasis, deren Regeln nur in einer README stehen.

</Accordion>

<Accordion title="Wie viele Stunden spart ein kostenpflichtiges Starter-Kit tatsächlich?">

Für ein mandantenfähiges SaaS mit Abrechnung, Rollen und Adminbereich liegt die aufgeschlüsselte Spanne in diesem Artikel bei 280 bis 465 Stunden kompetenter Arbeit. Für ein Einzelnutzer-Tool mit einem einzigen Stripe-Checkout sind es eher 20. Die ehrliche Zahl hängt ganz davon ab, was Sie bauen, und deshalb ist die Tabelle aufgeschlüsselt statt für Sie aufsummiert.

</Accordion>

<Accordion title="Sollte ich es einfach selbst bauen?">

Bauen Sie es selbst, wenn Sie genau den Unterbau lernen wollen, wenn Ihr Produkt so ungewöhnlich ist, dass die Annahmen eines Starter-Kits gegen Sie arbeiten würden, oder wenn Ihre Zeit wirklich keine Opportunitätskosten hat. Kaufen Sie, wenn Sie es schon einmal gebaut haben und noch genau wissen, wie lange die langweiligen drei Viertel gedauert haben.

</Accordion>

</Accordions>
