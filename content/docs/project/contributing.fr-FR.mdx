---
title: "Contribuer"
description: "Comment proposer des modifications à SaaSy Land."
---

1. Discutez d'abord des modifications importantes dans une issue, ouverte depuis le formulaire de rapport de bug ou de demande de fonctionnalité.
2. Créez une branche à partir de `main`.
3. Respectez les [conventions](/docs/conventions) et l'[architecture](/docs/architecture), et lisez la [skill pour agents](/docs/tooling/agent-skills) correspondante avant de modifier l'intégration d'un fournisseur. Les agents de code partent de `AGENTS.md` à la racine du dépôt.
4. Placez les tests à côté de leur propriétaire et maintenez le seuil de couverture à <RepositoryFact name="coverageThreshold" unit="percent" />.
5. Exécutez les vérifications ci-dessous.
6. Committez avec un message de [commit conventionnel](/docs/tooling/conventional-commits), ouvrez une pull request avec un titre conventionnel et remplissez son modèle.
7. Rebasez la branche sur `main` lorsqu'elle entre en conflit, sans jamais y fusionner `main`, comme l'explique [Git et pull requests](/docs/conventions/git-workflow#linear-history). Une personne chargée de la maintenance place la pull request au vert dans la [file de fusion](/docs/conventions/git-workflow#merging), qui la teste de nouveau au-dessus de `main` et la fusionne.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`build:test` exécute le build Cloudflare complet, que `check` et les tests unitaires ne sollicitent pas. La dernière commande construit et sert le Worker de test lorsqu'aucun serveur ne tourne, puis exécute dans Chromium les specs que vous nommez : lancez celles qui couvrent ce que vous avez modifié. La CI exécute chaque spec sur la pull request, puis de nouveau dans la file de fusion, et la pull request n'est fusionnée que lorsque cette exécution est au vert ; `bun run test:e2e:pr` exécute toute la suite en local de la même façon. Exécutez aussi la suite complète de tests dans le navigateur sous WebKit (`bun run test:e2e`) pour les modifications qui peuvent s'y comporter différemment. Validez séparément les intégrations réelles avec les fournisseurs lorsque vous modifiez leur configuration.

Lorsque le comportement change, mettez à jour `content/docs` dans toutes les langues ; `bun run check:content` rejette les traductions manquantes, ainsi que les blocs de code et la navigation qui diffèrent. Le modèle de pull request comprend un résumé, un plan de test avec les vérifications ci-dessus et la liste de la documentation mise à jour ; décrivez-y le comportement obtenu, la façon dont vous l'avez vérifié et tout flux que la modification laisse inachevé. Un écran d'administration n'est livré qu'avec une véritable source pour ses données (voir [Tableau de bord d’administration](/docs/features/admin-dashboard#real-data-only)).

`CONTRIBUTING.md`, à la racine du dépôt, est la version courte de cette page, et `SUPPORT.md` indique où obtenir de l'aide. Toutes les personnes qui participent respectent `CODE_OF_CONDUCT.md`, le Contributor Covenant 2.1. Signalez les vulnérabilités de sécurité en privé, comme le décrit `SECURITY.md`, jamais dans une issue publique.
