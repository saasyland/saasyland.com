Better Auth stores users, accounts, sessions and verification tokens in D1 through the Drizzle adapter. It provides email and password sign-up with required email verification, GitHub and Google sign-in, password reset, email change, TOTP two-factor authentication, admin user management and Polar checkout. Its HTTP API is served by `src/routes/api/auth.$.ts`.

## Files

| File                                                   | Responsibility                                                                                                                                        |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth.server.ts`                                       | The `betterAuth` instance: providers, `admin`, `twoFactor`, Polar and `tanstackStartCookies` plugins, allowed hosts, D1 rate limiting and email hooks |
| `auth.client.ts`                                       | `authClient` and its methods (`signIn`, `signUp`, `signOut`, `useSession`, `twoFactor` and others)                                                    |
| `auth.routes.ts`                                       | Route guards for `beforeLoad`                                                                                                                         |
| `auth.middleware.ts`                                   | Server-function middleware: `withRequest`, `authorized`, `withRateLimit` and `RATE_LIMITS`                                                            |
| `auth.access.ts`                                       | Roles, permission statements and `hasPermission`                                                                                                      |
| `auth.session.ts`                                      | `getRequestSession`, the `getCurrentSession` server function and `getCurrentSessionQuery`                                                             |
| `auth.errors.ts`, `auth.zod.ts`, `auth.constraints.ts` | Error keys, form schemas and password limits                                                                                                          |

## Route guards

| Guard                | Used by                          | Behaviour                                                                       |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------------- |
| `requireSignedIn`    | `/app`                           | Redirects to sign-in without a session and returns the session                  |
| `requireAdmin`       | `/admin`                         | Also requires the `admin: ["access"]` permission, otherwise redirects to `/app` |
| `redirectIfSignedIn` | `/auth/sign-in`, `/auth/sign-up` | Sends a signed-in user to `/admin` or `/app`, depending on the role             |
| `redirectAfterAuth`  | `/auth/callback`                 | Requires a session, then redirects to the workspace for the role                |

The guards load the session through the query cache and clear the cache when the signed-in user changes.

## Server functions

Page guards only protect navigation, so every protected server function checks the caller again with middleware from `auth.middleware.ts`:

- `authorized(permission?)` requires a session, optionally checks a permission, and adds the session to the context as `context.auth`. Operations on the caller's own data use `context.auth.user.id`, never a user ID from the input.
- `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` (3 requests per 60 seconds) or `RATE_LIMITS.TOKEN` (5 per 60 seconds) limits a public operation per client IP from `cf-connecting-ip`.
- `withRequest`, which both include, maps errors to `AppError` codes: Better Auth errors become `AUTH_API_ERROR` with their error key, Zod errors become `VALIDATION`, and unexpected errors are logged and returned as `INTERNAL_ERROR`.

## Roles and permissions

`auth.access.ts` defines two roles: `admin` and `customer` (the default for new accounts). Application statements cover `admin`, `category`, `order`, `product` and `settings`; the admin role also receives Better Auth's admin statements. `hasPermission({ permission, role })` is shared by guards, middleware and the UI.

## Email and rate limits

The email hooks in `auth.server.ts` call use cases: `sendVerifyEmail`, `sendResetPasswordEmail` and `sendChangeEmailConfirmationEmail`. Better Auth's own rate limiter stores its counters in the D1 `rate_limit` table through `authRateLimitStorage` from `src/lib/rate-limit.ts`, which uses atomic upserts and rejects requests when its storage is unavailable. `getRequestSession` bypasses the cookie cache, so authorization always reads the session from D1.
