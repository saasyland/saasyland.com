The history of `main` is part of the product: every squash-merged pull request is one line that says what changed for the people using the code.

## Commits

Commit messages follow Conventional Commits, written without an emoji; the `prepare-commit-msg` hook adds the emoji of the type (see [Conventional commits](/docs/tooling/conventional-commits) for the table):

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- The subject is lowercase, in the imperative, and says what the change does for its users: `feat(course): reorder the catalogue from the course list`, not `update course files`.
- The scope is the module or area: `course`, `auth`, `a11y`, `deps`, `readme`.
- The type is one of `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 and `revert` 🗑️; the hook rejects any other. Never type the emoji yourself: the hook does not check a subject that already starts with one.
- Split a pull request into logical commits: the feature, its documentation as `docs(<scope>)`, and fixes found on the way.
- Never commit with `--no-verify`. The `pre-commit` hook runs `bun run check:pre-commit`; when it fails, fix the cause.
- Format and lint only the files you changed, with `bunx vp fmt <files>` and `bunx vp lint --fix <files>`. Do not run `bun run check:fix` or `vp check --fix` over the whole repository: they rewrite files you did not touch, including the shared editor settings in `.vscode/settings.json`. If `.vscode/` appears in `git status`, restore it from `HEAD`.

## No AI attribution

Commits and pull request descriptions carry no `Co-Authored-By` trailer for an AI tool, no "Generated with" line and no other AI attribution, even when a tool adds one by default. GitHub resolves such a trailer's address to an unrelated account, which then shows up as a contributor to the repository. The same applies to fixes contributed upstream (see [Dependencies](/docs/conventions/dependencies)).

## Branches and worktrees

- Branch from `main`, one branch per pull request.
- Give each branch its own Git worktree instead of switching the branch of a checkout, so a checkout that an editor or another process has open is never changed underneath it:

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Before trusting a test run, check `git branch --show-current` in the directory you tested.

### Hooks in every worktree

Git reads `core.hooksPath` from the configuration that every worktree of a repository shares, and Vite+ sets it to the relative path `.vite-hooks/_`, so Git runs the hook dispatcher of the worktree you commit in. The dispatcher is generated and never committed, so each worktree needs its own, and where it is missing Git skips the hooks without a warning. Two steps install it:

- `git worktree add` runs the `post-checkout` hook of the checkout you run it from, and `.vite-hooks/post-checkout` installs the dispatcher of the new worktree with `vp hooks enable`. A commit made before `bun install` then fails in the `pre-commit` hook instead of skipping it.
- `bun install` runs `prepare`, which refreshes the dispatcher with `vp config --no-agent` and then runs `scripts/verify-git-hooks.ts`. The install fails when `core.hooksPath` is not `.vite-hooks/_` or when the dispatcher lacks a hook from `.vite-hooks/`, and the error prints the command that repairs it.

Never set `core.hooksPath` to another value and never pass `-c core.hooksPath` to Git. While it held the absolute path of the main checkout's dispatcher, `vp config` installed no dispatcher in the other worktrees, and once the next `bun install` in the main checkout set the relative path back, commits in those worktrees ran no hooks. `vp hooks status` shows whether the hooks are active in a worktree.

## Linear history

The ruleset that protects `main` on GitHub requires a linear history, accepts only squash merges and rejects force-pushes, so each pull request reaches `main` as one commit. Pull request branches stay linear too:

- Never create a merge commit, on `main` or on a pull request branch: do not merge `main` into a branch, and do not resolve conflicts in a merge commit.
- Bring a branch up to date by rebasing it onto `main`, with `gh pr update-branch --rebase` or with `git fetch origin` and `git rebase origin/main`.
- When GitHub cannot rebase a pull request with several commits, land it again as one commit on top of `main`: squash the branch into one commit at its merge base, then rebase that commit, so you resolve each conflict once:

```sh
git fetch origin
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -m "feat(course): reorder the catalogue from the course list"
git rebase origin/main
git push --force-with-lease
```

- Push a rewritten branch with `git push --force-with-lease`, and only your own pull request branch. Never force-push `main` or anyone else's branch, and never use a plain `--force`, which overwrites commits pushed since your last fetch.

## Pull requests

- **Small and targeted.** One fix, one feature or one refactor per pull request. A large feature becomes a stack of pull requests, each reviewable on its own, as videos, courses and the course admin were.
- **The title is the squash commit.** Use the commit format; it becomes the subject on `main`.
- **The description** has a `## Summary` of what changed and why, a `## Test plan` with the commands you ran and their results, and a `## Docs` list of the pages, README sections and copy you updated. Write it plainly, without marketing language.
- **Every pull request updates what it makes inaccurate:** the README, the docs pages in every locale and any site copy or landing page claim it touches, and it adds its [changelog entry](#changelog-entries). Inaccuracy found in code you did not change gets its own pull request.

## Changelog entries

Every pull request adds its own entry to the [changelog](/docs/project/changelog), so pull requests open side by side never edit the same file.

- **Name it after the pull request.** Open the pull request, then add `content/changelog/<number>.<locale>.mdx` in every locale: a bulleted list, without frontmatter, of what changed for the people using the code, linking the docs pages it affects.
- **Never write a date or the pull request's number.** The changelog page and the release notes take each entry's day from the Git history: the day, in UTC, of the squash commit whose subject GitHub ends with `(#<number>)`. Until the pull request is merged, its entry is listed under **Unreleased**. They take the number from the file name: the page ends each entry with a link to its pull request, or to its commit for an entry named after one, and the release notes end it with `(#<number>)`, which GitHub links.
- **CI checks it.** In a pull request, `bun run check` fails while `content/changelog/<number>.en-US.mdx` is missing, and `check:i18n` compares each translation with it as it does a docs page. A file named after neither a pull request number nor a full commit hash fails too: the few changes that reached `main` without a pull request are named after their commit.
- **Only your own entry may be unreleased.** In CI, the build of the site fails while the changelog would list an entry under **Unreleased** that should not be there: in a pull request into `main`, any entry but the pull request's own, and on `main`, any entry at all. A local build, which has no `GITHUB_REF`, lists every unmerged entry. This catches an entry that outlives its pull request: `content/changelog/219.<locale>.mdx` stayed behind when #219 was closed without merging, repeated #220's entry and showed as **Unreleased** on production until #254 removed it.

## Checks

CI runs `bun run check` and `bun run test:coverage`, then builds the test Worker and runs the browser suite in Chromium; only when both pass does it deploy a preview. Wait for the preview deployment as well: it is the only step that uploads the Worker to Cloudflare, and Cloudflare's upload limits have failed a deployment that every other check passed. See [CI/CD](/docs/tooling/ci-cd).
