---
title: "プレビューをデプロイする"
description: "Cloudflare のリソースを用意し、プレビュー用 Worker をデプロイします。"
---

`preview` 環境は、Worker `saasyland-preview` を `preview.saasyland.com` にデプロイします。`preview` は専用の D1 データベース、KV 名前空間、2 つの R2 バケットを持ちます。`development` はローカルのものを使い、`preview` とは何も共有しません。

## リソースを用意する

```sh
bunx wrangler login
bunx wrangler d1 create saasyland_com_preview
bunx wrangler kv namespace create CACHE --env preview
bunx wrangler r2 bucket create saasyland-preview
bunx wrangler r2 bucket create saasyland-bundles-preview
```

`wrangler.jsonc` で、`preview` にある `database_id`、`database_name`、KV の `id`、`MEDIA` と `BUNDLES` の `bucket_name` を置き換えます。`development` のブロックはローカルのリソースを指定しているため、変更は不要です。バインディング名の `DB`、`CACHE`、`MEDIA`、`BUNDLES`、および `migrations_dir` はそのままにし、Worker 名とカスタムドメインのルートを自分のアカウントに合わせて更新します。本番用には `saasyland` バケットと `saasyland-bundles` バケットを含む別のリソースを作成し、`production` ブロックを更新してください。`BUNDLES` には CLI の各リリースのテンプレートバンドルが入り、CLI のリポジトリのリリースがプレビューと本番のバケットにアップロードします。[バンドルの公開](/docs/features/cli-licence-api#publishing-bundles)を参照してください。`src/presentation/branding/index.ts` で `APP_DOMAIN` を設定します。`src/modules/_core/constants/api.ts` の `DEPLOYED_HOSTS` は、この値からデプロイ先のホスト（本番では `APP_DOMAIN`、プレビューでは `preview.<APP_DOMAIN>`）を導き出します。コードの中でこれらのホストを指定しているのはここだけです。`appHostsForMode` は Better Auth とニュースレターのリンクが受け付けるホストとしてこれを読み取り、`scripts/verify-deployment.ts` はデプロイ後にこれらのホストへリクエストを送ります。ローカルでは、`appHostsForMode` は開発で `localhost:3000` または `127.0.0.1:3000` を、テストではそれらに加えて、ポート <RepositoryFact name="testServerFirstPort" /> から <RepositoryFact name="testServerLastPort" /> までの `localhost` と `127.0.0.1` を受け付けます。`DEPLOYED_HOSTS` を編集するのは、プレビューのホスト名が異なる場合だけです。`wrangler.jsonc` のカスタムドメインの `routes` と `.github/workflows/deploy-reusable.yml` の環境 URL も同じホストを指定しているため、これらも合わせて更新してください。

## デプロイする

`.env.preview` に値を記入し、[Polar の設定](/docs/getting-started/polar-setup)の説明に従って Polar のサンドボックスを設定してから、デプロイします。

```sh
bun run deploy:preview
```

`deploy:preview` は、まずバインディングの欠落とプレースホルダーの ID を拒否する `scripts/verify-bindings.ts preview` を実行し、次に `scripts/prepare-deploy-secrets.ts preview` を実行します。これは `wrangler.jsonc` が `preview` 向けに宣言しているシークレットを `.env.preview` から `.wrangler/secrets.preview.json` に書き出し、いずれかが空であるか `[UPDATE]` のようなプレースホルダーであれば失敗します。続いて `scripts/run-deploy-checks.ts preview` が各エリアのデプロイ前チェックを実行します。現在は、`.env.preview` の OAuth クライアント ID がそれぞれのプロバイダーの形式であることを確認する `auth:verify:preview` と、`.env.preview` の Polar の組織をコードと比較する `polar:verify:preview` です。その後、`build:preview` が公開ページをプリレンダリングして出力を検証します。`wrangler deploy` がそれらのシークレットとともに `dist/server/wrangler.json` をアップロードする前に `db:migrate:preview` が新しいマイグレーションを適用し、最後に `scripts/verify-deployment.ts preview` が、`DEPLOYED_HOSTS` のプレビューのホスト（`https://preview.saasyland.com`）が応答すること、そして各 OAuth プロバイダーのサインインが、そのプロバイダーの形式のクライアント ID でプロバイダーに届き、プレビューのホストに戻ってくることを確認します。R2 バケットは名前でバインドされるため、`verify-bindings.ts` はバケットが存在するかどうかをチェックしません。両方のバケットが存在するまで、デプロイは失敗します。`bun run db:migrations:preview` は、プレビューのデータベースにまだ適用されていないマイグレーションを一覧表示します。

[環境変数](/docs/getting-started/environment-variables)に記載されているとおり、プレビューのホスト用に OAuth のコールバックを登録します。

## 自動デプロイ

CI は `main` へのすべてのプッシュを、チェックとブラウザーテストがマージキューまたはその実行の中で成功した時点で、まず共有プレビューに、続いて本番にデプロイします。`Preview` ワークフローは、ブランチを手動で共有プレビューにデプロイします。必要な GitHub のシークレットについては [CI/CD](/docs/tooling/ci-cd) を参照してください。
