Ces pages constituent la norme de code de ce dépôt. Elles décrivent la façon dont le code est écrit ici, et non la façon dont il pourrait l'être, et chaque règle cite les fichiers qui l'appliquent. La plupart des règles sont imposées par une commande : `bun run check` (formatage, lint, types, traductions et structure de la documentation), `bun run test:coverage` (le seuil de 100 %) ou la suite de bout en bout. Les autres sont contrôlées en revue, et chaque page précise lesquelles.

Quand vous ne savez pas comment écrire quelque chose, trouvez l'exemple existant le plus proche du même genre, lisez-le et reprenez sa forme. La cohérence vaut plus qu'une idée localement meilleure : une deuxième façon de faire la même chose oblige chaque lecteur suivant, humain ou agent, à apprendre les deux.

## Implémentation de référence

La fonctionnalité des cours est le code le plus récent du dépôt et la forme à reprendre. Elle couvre un module de table, des routes publiques et d'administration, des formulaires, des boîtes de dialogue, un tableau de données, des squelettes et des tests.

| Genre                                    | À reprendre de                                                         |
| ---------------------------------------- | ---------------------------------------------------------------------- |
| Module de table                          | `src/modules/course/`, avec `chapter`, `lesson` et `video` à côté      |
| Lecture avec des options de query        | `src/modules/course/use-cases/get-course-editor.ts`                    |
| Liste paginée pour un tableau            | `src/modules/course/use-cases/get-courses.ts`                          |
| Mutation avec des options de mutation    | `src/modules/course/use-cases/update-course.ts`                        |
| Route de layout                          | `src/routes/admin.courses.tsx`                                         |
| Route de page avec un tableau de données | `src/routes/admin.courses.index.tsx`                                   |
| Route de page avec un paramètre          | `src/routes/admin.courses.$courseId.tsx`                               |
| Formulaire                               | `src/presentation/components/custom/admin/courses/course-form.tsx`     |
| Boîte de dialogue avec un formulaire     | `src/presentation/components/custom/admin/courses/chapter-dialog.tsx`  |
| Colonnes de tableau                      | `src/presentation/components/custom/admin/courses/course-columns.tsx`  |
| Squelettes de route                      | `src/presentation/components/custom/admin/content-pending.tsx`         |

## Règles sans exception

Enfreindre l'une de ces règles fait rejeter une modification, quelles que soient ses autres qualités.

1. Pas de commentaires dans le code, les tests, les scripts, la configuration ou le CSS. Voir [Style de code](/docs/conventions/code-style).
2. Pas de `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, conversions `as` ou `any` pour contourner une règle. Corrigez la cause.
3. Pas de ternaires sur plusieurs lignes et pas de `?? undefined`. Hors des tests et de `src/platform/testing`, `null` n'apparaît que là où une API l'impose : dans une comparaison avec une valeur qui peut être `null`, et dans une ref DOM de React (`useRef<HTMLElement>(null)`). Voir [Style de code](/docs/conventions/code-style).
4. Les statuts, les types, les offres, les rôles et les autres valeurs du domaine sont des constantes nommées, jamais des littéraux de chaîne répétés, y compris dans les tests. Les tests de schéma sont le seul endroit où une valeur stockée est écrite en clair. Voir [Tests](/docs/conventions/testing).
5. Un dossier de `src/modules` n'existe que pour une table de la base de données. Voir [Modules](/docs/conventions/modules).
6. Chaque chaîne visible par l'utilisateur existe dans les neuf langues, et chaque page de documentation aussi. Les nombres affichés sur le site sont mesurés ou déclarés une seule fois dans `src/data`, jamais saisis à la main. Voir [Traductions et contenu](/docs/conventions/translations).
7. La couverture reste à 100 % pour les lignes, les instructions, les fonctions et les branches. Voir [Tests](/docs/conventions/testing).
8. Une modification met à jour le README, la documentation et les textes du site qu'elle rend inexacts, dans la même pull request.
9. Les commits et les pull requests ne portent aucune attribution à une IA ni de trailer `Co-Authored-By`. Voir [Git et pull requests](/docs/conventions/git-workflow).

## Définition de « terminé »

Une modification est terminée lorsque ces commandes réussissent, dans cet ordre, sur la branche que vous vous apprêtez à pousser :

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` et les tests ne sollicitent pas le build Cloudflare : une mise à jour de dépendance a déjà passé les deux alors que le build de production était cassé. Exécutez `build:test` pour chaque modification, et la suite dans le navigateur pour tout ce qui n'est pas de la documentation. Avant de committer, relisez votre propre diff à la recherche de commentaires, de littéraux de chaîne qui devraient être des constantes, et de textes ou de documentation que la modification a rendus faux.
