O repositório roda com a versão mais recente de todas as dependências. Uma atualização que quebra algo é corrigida para a frente, no código ou upstream, nunca voltando atrás.

## Versões do toolchain [#upgrading]

Atualize as dependências, as skills para agentes e as GitHub Actions com um único comando, em uma branch própria:

```sh
bun run deps:update
```

`scripts/update-dependencies.ts` executa, nesta ordem:

1. `vp migrate` da versão mais recente do Vite+ quando ela é mais nova que o `vite-plus` de `package.json`, o que move juntos `vite-plus`, o alias `vite` e `vitest`;
2. `bun update --latest` para cada dependência declarada com um intervalo `^` ou `~`, o que a leva à versão mais recente, inclusive uma nova versão major, e mantém o intervalo;
3. `bun run skills:update`, que leva as [skills para agentes](/docs/tooling/agent-skills) aos commits mais recentes das suas origens e registra as versões dos pacotes que elas documentam;
4. `scripts/github-actions.ts`, que lê com `git ls-remote` as tags de versão do repositório de cada action em `.github/workflows/` e `.github/actions/`, pega a versão estável mais recente, segue uma tag anotada até o seu commit e reescreve cada `uses:` com esse commit e essa tag ([CI/CD](/docs/tooling/ci-cd)).

Ele não mexe nas versões fixadas exatas, porque cada uma tem um motivo nesta página, e termina listando cada pacote fixado que tem uma versão mais nova. `bun run check` falha enquanto um pacote documentado por uma skill tiver mudado desde o último `skills:update`, então as dependências e as skills não podem se desencontrar. Toda semana, o workflow `updates.yml` lista as atualizações disponíveis em uma única issue do GitHub; veja [CI/CD](/docs/tooling/ci-cd#updates).

Depois, para cada pacote que mudou:

- O Bun é o gerenciador de pacotes e o executor de scripts. `packageManager` em `package.json` (Bun <RepositoryFact name="bunVersion" />) é o único lugar onde a sua versão é definida; a CI a lê de lá. `bun.lock` é versionado.
- O Node vem de `.nvmrc` (<RepositoryFact name="nodeVersion" />), e `engines.node` exige pelo menos essa versão.
- `remotion/` é a única exceção, com o seu próprio toolchain npm, instalado apenas para editar os vídeos da landing page. O `typescript` dele é a versão mais recente que o `typescript-eslint`, que executa as regras de lint do Remotion, aceita como dependência peer, porque o TypeScript 7 não inclui a API do compilador que o `typescript-eslint` lê. Os pacotes que ele compartilha com o site, `@saasyland/stack`, `lucide-react`, `react` e `react-dom`, ficam fixados na menor versão que o `package.json` do site aceita, porque os vídeos renderizam arquivos do site que os importam, e o `src/data/__test__/cli.test.ts` falha quando as duas versões diferem.

## Atualizar

1. Leia o changelog e o guia de migração da nova versão, de preferência a cópia distribuída em `node_modules/<package>`.
2. Altere o código para seguir o uso documentado da nova versão.
3. Verifique nesta ordem, e não dê nada como pronto antes que a última etapa passe:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` e os testes rodam sem o build do Cloudflare e do TanStack Start, então podem passar enquanto o build está quebrado. Isso aconteceu duas vezes em uma única atualização: um novo `@polar-sh/sdk` não podia ser empacotado, e uma versão do TanStack Start mudou a marcação de `modulepreload` que `optimize-prerendered-html.ts` reescreve. Os dois problemas só apareceram em `build:test`. Depois de um build, `find dist/server -name '*.map'` não pode imprimir nada; `upload_source_maps: false` em `wrangler.jsonc` existe porque o Worker com os seus source maps fica maior do que o Cloudflare aceita em um upload (veja [Cloudflare Workers](/docs/integrations/cloudflare-workers)).

Nunca fixe um pacote em uma versão mais antiga para evitar uma breaking change, e nunca adicione à aplicação código que contorna um bug de biblioteca.

## Quando o bug é upstream

Quando a aplicação já segue o uso documentado e a nova versão está errada, mantenha a nova versão e carregue a correção:

1. Comprove o bug com uma reprodução mínima fora deste repositório.
2. Escreva a menor alteração que o corrige no pacote, espelhando a correção que você vai propor upstream, e salve-a com `bun patch`. O patch vai para `patches/<package>@<version>.patch` e para `patchedDependencies`, e o pacote é fixado nessa versão exata para que o patch continue sendo aplicado.
3. Relate o bug upstream e abra um pull request com a correção, seguindo as regras de contribuição daquele projeto.
4. Exclua o patch assim que uma versão trouxer a correção. Antes de manter ou documentar um patch, verifique com `npm view <package> version` se essa versão já saiu.

Os patches atuais:

- `patches/@tanstack%2Frouter-core@1.171.39.patch` impede que a primeira renderização do router após a hidratação role a janela de volta ao topo. O bug está relatado upstream em [TanStack/router#8933](https://github.com/TanStack/router/issues/8933), e o patch é a correção proposta em [TanStack/router#8934](https://github.com/TanStack/router/pull/8934).
- `patches/@tanstack%2Freact-router@1.170.46.patch` impede que `lazyRouteComponent` recarregue uma página cujo chunk de rota o navegador cancelou porque o visitante está saindo dela. É a correção proposta em [TanStack/router#8830](https://github.com/TanStack/router/pull/8830), estendida ao chunk que a página começa a carregar depois de `beforeunload` e que o Safari faz falhar na hora.
- `patches/framer-motion@14.14.0.patch` faz o `LazyMotion` ignorar um bundle de recursos que não carrega, em vez de deixar a rejeição sem tratamento. `motion` está fixado na 14.14.0 junto com ele. O Motion incorporou a correção de [motiondivision/motion#4089](https://github.com/motiondivision/motion/issues/4089) depois de lançar a 14.14.0, então o patch sai com a primeira versão que a contiver.
- `patches/better-auth@1.7.27.patch` permite que o plugin `haveIBeenPwned` gere o hash de uma senha fora de um endpoint do Better Auth, como faz `(await auth.$context).password.hash()` nos testes de integração: ele lê o contexto do endpoint com `tryGetCurrentAuthEndpointContext` em vez de `getCurrentAuthEndpointContext`, que lança uma exceção nesse ponto. `better-auth` está fixado na 1.7.27 junto com ele. É a correção proposta em [better-auth/better-auth#12873](https://github.com/better-auth/better-auth/pull/12873).
- `patches/playwright-core@1.65.1.patch` permite que o driver WebKit do Playwright acompanhe uma navegação entre sites para uma página que envia `Cross-Origin-Opener-Policy`, como a volta do checkout hospedado da Polar para o espaço de trabalho: o build do WebKit do Playwright 1.65 cria uma segunda página provisória para a troca antes de destruir a primeira, e o driver agora descarta a primeira em vez de falhar uma asserção em `WKPage._onTargetCreated`. Com ele, `@playwright/test` fica fixado em 1.65.1. O bug está relatado upstream em [microsoft/playwright#44254](https://github.com/microsoft/playwright/issues/44254), que o Playwright fechou como concluído; nenhuma versão estável depois da 1.65.1 traz a correção ainda, então o patch fica até que uma traga.

`@tanstack/router-core` é uma dependência direta, porque `src/lib/stale-build.ts` importa dele `isModuleNotFoundError`, e está fixado na 1.171.39 para que o patch dele continue se aplicando. `@tanstack/react-router` está fixado na 1.170.46 e `@tanstack/react-start` na 1.169.7, porque dependem exatamente das versões do TanStack com patch. Um patch para o `fumadocs-mdx` 15.6.0 foi carregado da mesma forma e removido quando a 15.6.1 trouxe a correção upstream, assim como os patches para `@fumadocs/base-ui` e `fumadocs-core` 16.19.2 quando a 16.19.3 trouxe as suas. O patch para o `@videojs/utils` 10.4.0 saiu quando a 10.5.0 trouxe a sua correção. Um patch que dava ao layout da documentação do Fumadocs um slot `skipToContent` foi removido quando o Fumadocs recusou o slot; agora `globals.css` oculta o link do Fumadocs, e o link de pular do próprio site leva ao artigo da documentação (veja [Site de documentação](/docs/features/docs-site)).

Um patch altera os arquivos de um pacote, não as versões que o Bun instala para ele. Quando um pacote fixa uma das próprias dependências abaixo da versão que a aplicação usa e os tipos das duas cópias não batem, uma entrada em `overrides` no `package.json` a eleva em vez disso. Hoje nenhuma é necessária. O `@polar-sh/adapter-utils` 1.1.1, que o `@polar-sh/better-auth` usa, fixa o `@polar-sh/sdk` 1.3.1, então o Bun instala essa cópia ao lado da 1.3.2 da aplicação. O adaptador importa o SDK só para tipar o `webhooks({ onPayload })` do plugin, e `handlePolarEvent`, que recebe o payload da 1.3.2, aceita o da 1.3.1, porque a 1.3.2 só amplia tipos, como `trial_ended` entre os status de assinatura. Quando uma versão posterior do SDK mudar um payload de um jeito que a cópia do adaptador não aceite, `bun run check` falha em `handlePolarEvent`; aí uma entrada em `overrides` para o `@polar-sh/sdk` eleva a cópia do adaptador até que uma versão do `@polar-sh/adapter-utils` dependa desse SDK (`npm view @polar-sh/adapter-utils dependencies`).

## Avisos de segurança

Os alertas do Dependabot cobrem `remotion/package-lock.json`, mas o GitHub não lê `bun.lock`, então verifique a aplicação com `bun audit` e o projeto de vídeo com `npm audit` dentro de `remotion/`. Resolva um aviso com a versão mais recente do pacote que traz o pacote vulnerável. Quando a faixa de versões desse pacote já permite a versão corrigida, basta atualizar o lockfile: `bun update`, ou `npm update` em `remotion/`.

Enquanto nenhuma versão do pacote pai permitir a correção, uma entrada em `overrides` eleva o pacote vulnerável, e ela é removida assim que uma versão do pai fizer isso. As entradas atuais:

- `package.json`: `"minimatch": "^11.0.1"`. O `shadcn` chega ao `minimatch` ^10 por meio do `ts-morph` 26 e do `@ts-morph/common`, e só o `minimatch` 11.0.1 corrige o GHSA-g3hv-75wg-m249. Remova-a quando o `shadcn` depender de uma versão do `ts-morph` que contenha [dsherret/ts-morph#1697](https://github.com/dsherret/ts-morph/pull/1697).
- `remotion/package.json`: `minimatch` ^11.0.1 sob `@typescript-eslint/typescript-estree`, pelo mesmo aviso. O `@remotion/eslint-config-flat` fixa o `typescript-eslint` em 8.71.2, cujo parser pede `minimatch` ^10. Remova-a quando o `@remotion/eslint-config-flat` depender de uma versão do `typescript-eslint` que contenha [typescript-eslint/typescript-eslint#13145](https://github.com/typescript-eslint/typescript-eslint/pull/13145).

O `bun audit` ainda relata um aviso que não tem correção a adotar:

- `esbuild` 0.18.20 (GHSA-67mh-4wv8-2f99, moderada), por meio do `drizzle-kit` e do `@esbuild-kit/esm-loader`. O `drizzle-kit` 0.31.11 declara o loader, mas nunca o importa, e o aviso diz respeito ao servidor de desenvolvimento do esbuild, que nada aqui inicia. [drizzle-team/drizzle-orm#5304](https://github.com/drizzle-team/drizzle-orm/issues/5304) acompanha a remoção; as release candidates do `drizzle-kit` 1.0 já não dependem dele.

O GitHub retirou o aviso de `deepmerge` 4.3.1 (GHSA-gcqx-w48m-w2h4), que vinha por `shadcn` e `@shadcn/registry`, depois de [github/advisory-database#10910](https://github.com/github/advisory-database/issues/10910), então o `bun audit` não o relata mais.

## As entradas do Vite+ no package.json

```json
"vite": "npm:@voidzero-dev/vite-plus-core@8.3.8000",
"vite-plus": "1.7.0",
"vitest": "5.1.0"
```

Estas linhas, e o mesmo alias `vite` e a mesma versão de `vitest` em `overrides`, são exatamente o que o próprio migrador do Vite+ escreve: `vite-plus` é fixado em uma versão exata, o Bun precisa do core como dependência direta `vite`, e `vitest` é listado porque `@vitest/coverage-v8` e os tipos de teste precisam dele. Desde o `vite-plus` 1.7.0, o core leva a versão da release do Vite que inclui, então 8.3.8000 é o Vite 8.3.8; o `vp toolchain` mostra a correspondência. Atualize-os juntos com `vp migrate`, nunca com `bun update`. Para descobrir se um deles pode sair, copie o projeto, execute `vp migrate` na cópia e compare o resultado; não decida apenas raciocinando sobre isso. A entrada `minimatch` em `overrides` é a correção de segurança descrita acima, e o `vp migrate` a mantém inalterada.

`build.rolldownOptions.external`, que `src/integrations/polar/polar.vite.ts` define, lista dependências peer opcionais de `@polar-sh/sdk` que não estão instaladas e são removidas do Worker pelo tree-shaking; veja [Vite+](/docs/tooling/vite-plus). Remova a lista quando a Polar corrigir o seu empacotamento.

## Adicionar uma dependência

Verifique primeiro se um pacote que já está em `package.json` resolve o problema, para que cada aspecto continue com uma única biblioteca. Adicione uma dependência de runtime com `bun add`, uma ferramenta com `bun add --dev`, e use a skill para agentes do fornecedor listada em `skills-lock.json` quando houver uma (veja [Skills para agentes](/docs/tooling/agent-skills)). Quando uma skill de um fornecedor documenta o novo pacote, adicione o pacote à origem dela em `SKILL_SOURCES` (`src/data/skills.ts`) e execute `bun run skills:update`.
