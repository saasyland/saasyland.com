      Donnez à chaque fonctionnalité un statut dans le code, disponible ou à venir, et écrivez chaque

## La réponse courte

Chaque fait d’une page devrait avoir exactement une source, et la page devrait l’afficher à partir de là. Classez ce que dit votre site par types. Les décomptes qui portent sur votre code sont mesurés par le build. Les valeurs que fixe l’entreprise, comme les prix et les limites, sont déclarées une seule fois dans le code et importées. Les nombres qui en découlent sont calculés, et calculés avec prudence. Le fait qu’une fonctionnalité marche ou non est un statut dans le code, et chaque phrase qui en dépend a une version pour chaque statut. Les promesses sur le comportement sont listées avec le test qui les prouve. Les faits sur le monde extérieur portent une date et un lien. Tout ce qui doit rester saisi, comme un extrait de code ou un tableau de référence, est comparé au code par une vérification qui fait échouer la CI. La seule chose sur laquelle une personne ou un agent puisse alors encore se tromper, c’est la prose autour des valeurs, et c’est à cela que sert la revue.

## Ce qu’est la dérive de la documentation, et pourquoi les agents l’aggravent

La dérive de la documentation, c’est l’écart entre ce que disent vos mots et ce que fait votre code. Elle n’a besoin de l’erreur de personne. Une page qui dit « 12 intégrations » était vraie le jour où elle a été écrite ; le code en a gagné une treizième, la page non, et la voilà fausse. La cause n’est pas la négligence mais la duplication : le même fait vit à deux endroits, et un seul des deux est tenu à jour par ce qui le fait changer.

Dave Thomas et Andy Hunt ont nommé le principe dans _The Pragmatic Programmer_ : « Chaque élément de connaissance doit avoir une représentation unique, non ambiguë et faisant autorité au sein d’un système. » Ils précisent explicitement que la documentation est concernée. Leur test pour repérer une violation : « quand une seule facette du code doit changer, vous retrouvez-vous à faire ce changement à plusieurs endroits, et dans plusieurs formats différents ? Devez-vous changer le code et la documentation […] ? Si c’est le cas, votre code n’est pas DRY. »

Le guide de documentation de Google en donne la version opérationnelle : « Modifiez votre documentation dans la même CL que la modification du code. » Cette règle fonctionne quand la personne qui modifie le code connaît chaque page qui le mentionne. Elle cesse de fonctionner à grande échelle, et les agents de codage IA apportent l’échelle.

### Trois façons dont les agents multiplient les copies

**La vitesse.** Un agent écrit une page de documentation en quelques minutes, et il écrit les nombres qu’il voit. Si une autre page dit 176 fichiers de test, la nouvelle page dit 176 elle aussi. Chaque page qu’un agent écrit à partir d’autres pages hérite de leurs erreurs et ajoute une copie.

**Les langues.** saasyland.com est publié en <RepositoryFact name="languages" /> langues. Un nombre saisi à la main existe une fois par langue, et les agents traducteurs travaillent à partir du texte anglais qu’on leur a donné, quel qu’il soit. Le 12 novembre 2026, nous avons découvert que les articles de blog traduits avaient été faits à partir d’une ancienne version anglaise : ils décrivaient une stack Next.js, Bun, Elysia et Neon que le site n’utilisait plus, 54 langues, 141 fichiers de test et 472 tests (#116). Chaque traduction était cohérente en elle-même, fluide, et fausse.

**Les sessions parallèles.** Plusieurs agents qui travaillent en même temps recopient chacun la version d’un fait qui était vraie au début de leur session. Deux pull requests qui mentionnent toutes deux un décompte peuvent être fusionnées dans n’importe quel ordre, et la seconde l’emporte, que son nombre soit le plus récent ou non.

Les agents traduisent aussi ce qui ne doit pas l’être, car pour un traducteur, un nombre ou un chemin au milieu d’une phrase ressemble à du texte. Notre audit de cohérence du 15 novembre a trouvé la liste de preuves de la page d’accueil affichant `bun run テスト` en japonais et `src/intégrations/` en français (#169). L’écran de tarification de démonstration de l’administration avait des prix saisis dans les messages de chaque langue, et les traducteurs les avaient convertis : la page polonaise affichait 129 zł, la brésilienne 58 reais et l’allemande 58 €, à côté d’un prix en dollars de 290 $ (#169). Deux locales avaient traduit l’adresse e-mail de contact elle-même (#132). Chacun de ces cas était une phrase qui contenait une valeur, et la valeur avait été traitée comme une partie de la phrase.

### À quoi ressemblait notre propre dérive

La page d’accueil de saasyland.com affirmait autrefois que chacun de ses nombres était généré à partir de ce dépôt public. Le 12 novembre, seuls deux l’étaient : le nombre d’étoiles GitHub et la version majeure de React. Les autres avaient été saisis dans les fichiers de messages et avaient dérivé (#115) :

| Affirmation sur la page                           | Ce que contenait le dépôt |
| ------------------------------------------------- | ------------------------- |
| 176 fichiers de test                              | 221                       |
| 8 suites Playwright                               | 12                        |
| 13 sections d’administration, et « dix » ailleurs | 9                         |
| « Douze » questions de la CLI                     | 13                        |

Aucun de ces nombres n’était un mensonge au moment où il a été saisi. Chacun était un instantané que le code avait dépassé. C’est tout le problème : vous ne pouvez pas corriger la dérive en étant plus attentif, car la copie est correcte jusqu’au jour où elle ne l’est plus, et rien ne vous dit quel jour c’est.

## Six types d’énoncés, et où se trouve la vérité de chacun

Avant de construire quoi que ce soit, classez ce que dit votre site. Chaque type a une source de vérité différente et demande un mécanisme différent.

| Type           | Exemple                                                   | Source de vérité                           | Mécanisme                                   | Ce qui échoue quand il dérive                                       |
| -------------- | --------------------------------------------------------- | ------------------------------------------ | ------------------------------------------- | ------------------------------------------------------------------- |
| Mesuré         | Un décompte de tests, de pages ou de langues              | Le dépôt                                   | Compté par le build                         | Rien ne peut dériver : le build affiche le décompte du jour         |
| Déclaré        | Un prix, une limite de formule, un délai de remboursement | Une seule constante dans le code           | Importé, formaté pour chaque locale         | Un test qui compare les systèmes externes à la constante            |
| Dérivé         | Les heures gagnées, un prix exprimé en heures             | Une formule sur des valeurs déclarées      | Calculé dans le code, arrondi avec prudence | Un test qui vérifie que l’affirmation tient toujours                |
| Statut         | Si une fonctionnalité est disponible ou à venir           | Une constante de statut par fonctionnalité | Des messages avec une version par statut    | Un test qui rend les deux versions                                  |
| Comportemental | « Un remboursement met fin à la licence »                 | Le comportement du code                    | Un test nommé à côté de l’affirmation       | Une vérification que chaque affirmation prouvée a toujours son test |
| Externe        | Un résultat d’enquête, le prix d’un concurrent            | La page de quelqu’un d’autre               | Une citation datée, revérifiée              | Rien d’automatique ; une date de revue                              |

Deux règles découlent du tableau. D’abord, chaque type sauf le dernier peut faire échouer une vérification quand il dérive : c’est donc au dernier que revient votre attention en revue. Ensuite, le mécanisme dépend du type, pas de l’endroit où apparaît l’énoncé : le même prix figure sur une carte de formule, dans un article de blog, dans une réponse de FAQ et dans la meta description d’une page, et chacun a besoin de la même source.

## Mesurer au moment du build

Un décompte qui porte sur votre dépôt devrait être calculé par le build qui publie la page, à partir des fichiers mêmes dont il parle. La plupart des bundlers ont un endroit prévu pour cela. L’API des plugins de Vite l’appelle un module virtuel : « Les modules virtuels permettent de transmettre des informations du moment du build aux fichiers source avec la syntaxe d’import ESM habituelle. » Un plugin calcule les valeurs au démarrage du build, et n’importe quelle page les importe comme un module normal.

Le nôtre est `scripts/repository-facts.ts`, qui sert `virtual:repository-facts`. Il compte les fichiers de test, les specs Playwright et les composants d’interface avec des globs, liste les tests du navigateur en interrogeant Playwright, et lit des réglages dans les fichiers des outils eux-mêmes : le seuil de couverture, les limites de lint et les largeurs du formateur dans `vite.config.ts`, la version de Node dans `.nvmrc`, la version de Bun dans `package.json`, le nombre de shards de CI dans les fichiers de workflow. Quelques-unes de ses lignes montrent à quel point les mesures sont directes :

```ts title="scripts/repository-facts.ts"
    e2eShards: readShards(E2E_WORKFLOW),
    e2eSpecs: countFiles(`${e2eSpecsPath}/*.spec.ts`),
    e2eSpecsPath,
    e2eTests: browserTests.length,
```

Le plugin lui-même fait une vingtaine de lignes : il construit le code source du module dans le hook `config` de Vite et le sert sous un identifiant résolu qui commence par `\0`, comme le montre le guide des plugins de Vite pour les modules virtuels.

```ts title="scripts/repository-facts.ts"
    enforce: "pre",
    load: (id) => (id === RESOLVED_MODULE_ID ? moduleSource : undefined),
    name: "saasyland:repository-facts",
    resolveId: (id) => (id === MODULE_ID ? RESOLVED_MODULE_ID : undefined),
```

Trois choix de conception le rendent digne de confiance.

**Mesurez ce dont parle l’affirmation, pas un substitut.** Notre première version comptait les sections d’administration à partir des libellés de la barre latérale, car compter la barre latérale elle-même aurait fait entrer dans la page d’accueil 3,7 Ko de code d’administration compressé avec gzip (#115). Un test maintenait les libellés égaux à la barre latérale. Plus tard, le décompte a changé de sens : la page d’accueil affirmait des sections d’administration qui fonctionnent, et cinq des onze affichaient des données de démonstration. Chaque entrée du menu d’administration a donc reçu un statut, le fait n’a plus compté que celles qui fonctionnaient, et le nombre est passé de 11 à 6 (#177). Puis les écrans de démonstration ont été entièrement supprimés (#259). Le fait affiche désormais <RepositoryFact name="adminSections" />, et il compte chaque entrée, car chaque entrée est un écran qui fonctionne.

**Refusez une configuration que la documentation ne peut pas décrire.** Une page qui dit « la couverture est maintenue à 100 % » suppose un seul seuil. Si quelqu’un fixe les branches à 95 et les lignes à 100, la phrase devient ambiguë. Notre plugin valide la configuration qu’il lit avec un schéma, et le schéma refuse quatre seuils différents :

```ts title="scripts/repository-facts.ts"
const thresholdsSchema = zod
  .object({ branches: zod.number(), functions: zod.number(), lines: zod.number(), statements: zod.number() })
  .refine(
    ({ branches, functions, lines, statements }) => [branches, functions, statements].every((threshold) => threshold === lines),
    "The docs state one coverage threshold for all four metrics",
  )
```

Le build échoue avec ce message, et la personne ou l’agent qui a modifié le seuil doit décider de ce que la documentation doit dire. C’est une vérification de la forme d’un fait, pas seulement de sa valeur.

**Les chemins et les commandes sont aussi des faits.** Une phrase qui dit aux lecteurs d’ouvrir `coverage/coverage-summary.json` ou de lancer `bun run test:coverage` contient deux valeurs qui appartiennent au code. Depuis #169, la page d’accueil les prend dans le même module : le chemin du résumé à partir de `reportsDirectory` dans la configuration de Vite, le répertoire des specs à partir du `testDir` de Playwright, les commandes à partir de `package.json`. Un test vérifie que chaque chemin cité existe et que chaque commande est un script. Aucun traducteur ne peut plus les transformer en `bun run テスト`, car la traduction ne les contient jamais.

## Afficher les valeurs au moyen de composants, pas de chaînes

Une fois qu’une valeur existe dans le code, affichez-la au moyen d’un seul composant, et n’en saisissez jamais le résultat. Dans notre documentation et notre blog, ce composant est `<RepositoryFact>`. En MDX, `<RepositoryFact name="testFiles" />` affiche <RepositoryFact name="testFiles" />, `<RepositoryFact name="e2eTests" />` affiche <RepositoryFact name="e2eTests" />, et `<RepositoryFact name="coverageThreshold" unit="percent" />` affiche <RepositoryFact name="coverageThreshold" unit="percent" />, formaté pour la langue de la page que vous lisez. Toute la règle de formatage tient en une douzaine de lignes :

```tsx title="src/presentation/components/custom/repository-fact.tsx"
const FactValue = ({ unit, value }: { readonly unit?: keyof typeof UNIT_FORMATS | undefined; readonly value: Value }): JSX.Element => {
  const format = useFormatter()

  if (typeof value === "number") {
    return <>{format.number(value, unit === undefined ? undefined : UNIT_FORMATS[unit])}</>
  }

  if (typeof value === "string") {
    return <code>{value}</code>
  }

  return <>{format.list(value.map((item) => <code key={item}>{item}</code>))}</>
}
```

Un nombre est formaté avec les séparateurs de la locale et, avec une `unit`, avec le mot de la locale pour les secondes, les heures, les jours ou le pourcentage, au bon pluriel. Une chaîne est affichée comme du code, car chaque fait de type chaîne est un chemin, une commande ou un identifiant qui doit être identique dans toutes les langues. Une liste devient la liste de code de la locale : « a, b and c » en anglais, « a, b et c » en français.

Les tableaux reçoivent le même traitement. `<RepositoryTable>` affiche des lignes que le code construit, sous des noms de colonnes que la page traduit : les déclarations de permissions de chaque rôle, les types de commit et leurs émojis, les multiplicateurs de prix régionaux avec leurs pays, les formes d’adresse que chaque langue ne doit pas employer. Un tableau saisi dans <RepositoryFact name="languages" /> langues, ce sont <RepositoryFact name="languages" /> copies d’une structure de données ; un tableau affiché à partir de la structure n’en est qu’une.

Trois endroits ne peuvent pas rendre un composant, et chacun demande sa propre réponse :

- **Les fichiers de messages.** Les textes de l’interface vivent dans des messages JSON, pas en MDX. Les valeurs y entrent comme arguments ICU, comme dans `{testFiles, number} test files`, et le composant qui rend le message lui transmet le module des faits. La recommandation d’ICU s’applique à chacun de ces messages : « écrivez des phrases complètes dans leurs sous-messages », car un traducteur ne peut pas réordonner une phrase assemblée à partir de fragments.
- **Le frontmatter.** Le titre, la description et la FAQ d’un article sont en YAML, qui alimente l’en-tête de la page, le flux et les données structurées. Les titres et les réponses de FAQ de nos articles sont des messages ICU que `formatPostText` formate avec les faits : une réponse de FAQ peut donc contenir le nombre de langues. La meta description ne le peut pas : elle est donc écrite sans nombres.
- **Les blocs de code.** Un bloc de code est copié octet pour octet. Il a besoin du mécanisme suivant.

Le résultat est visible dans notre historique. Quand #137 a remplacé chaque valeur saisie dans la documentation, le blog comptait déjà à lui seul 81 usages d’une version antérieure du composant à renommer, et la documentation a gagné des valeurs affichées pour les limites de débit, la couverture, les limites de lint, les délais d’expiration, les réglages d’encodage vidéo, les durées de vie des URL signées, les intervalles d’interrogation, les tailles de page, les prix, les versions, les nouvelles tentatives et les plannings, chacune jusque-là saisie dans neuf langues.

## Quand une valeur doit rester saisie, vérifiez-la

Certains textes doivent contenir la valeur elle-même : un extrait de code, un tableau de routes, une liste de variables d’environnement. Pour ceux-là, la règle est de comparer la page au code dans une vérification qui échoue.

**Exécutez les exemples, ou comparez-les à la source.** Rust l’intègre à son outil de documentation : « rustdoc permet d’exécuter les exemples de votre documentation comme des tests. Cela garantit que les exemples de votre documentation sont à jour et fonctionnent. » Pour un site TypeScript, exécuter chaque extrait est plus difficile : nous comparons donc à la place. Un bloc de code dont le titre est un chemin du dépôt doit être un extrait exact de ce fichier :

```ts title="scripts/check-content.ts"
const quotedSourceProblems = ({ label, target }: Translation): string[] =>
  [...target.matchAll(QUOTED_SOURCE_PATTERN)].flatMap(({ groups }) => {
    const path = groups?.["path"] ?? ""
    const file = join(REPOSITORY_DIR, path)

    if (existsSync(file) && readFileSync(file, "utf8").includes(groups?.["code"] ?? "")) {
      return []
    }

    return [`A code block in ${label} is not an excerpt of ${path}`]
  })
```

Chaque bloc de code titré de cet article est vérifié ainsi, dans les <RepositoryFact name="languages" /> langues, sur chaque pull request. Si quelqu’un modifie l’un des fichiers cités plus haut, `bun run check` nomme cet article et échoue tant que l’extrait n’est pas mis à jour.

**Générez les tableaux de référence, ou comparez-les.** Une référence des routes, une page des scripts et un tableau des variables d’environnement sont des listes que le code contient déjà. Notre vérification du contenu échoue quand la page des routes donne un mauvais chemin à une constante de route, quand la page des scripts omet un script de `package.json` ou en liste un qui n’existe pas, et quand les tableaux d’environnement omettent un secret déclaré dans `wrangler.jsonc`. Elle échoue aussi quand une page de documentation nomme un hôte local ou un sous-domaine qu’aucun mode de build n’autorise.

**Imposez aux traductions la structure de la page anglaise.** Une traduction doit avoir les mêmes extraits de code en ligne, les mêmes composants avec les mêmes props, les mêmes liens et le même nombre de lignes de tableau que la page anglaise. C’est la vérification qui a mis fin pour de bon aux commandes et aux chemins traduits : un traducteur, humain ou agent, peut reformuler chaque phrase, mais ne peut pas changer un seul caractère entre accents graves.

**Vérifiez les systèmes externes par rapport au code avant un déploiement.** Les prix sont déclarés dans `TIER_PRICES` ; le prestataire de paiement en garde sa propre copie dans son catalogue de produits, et un écart à cet endroit facturerait un prix pendant que la page en affiche un autre. Notre déploiement lance `polar:verify` avant le build, et il échoue quand le prix d’un produit Polar diffère de la constante ou que ses clés de licence autorisent un autre nombre d’appareils que `LICENSE_ACTIVATION_LIMITS`. Le message d’erreur nomme la constante : quiconque le lit sait donc quel côté fait foi.

## Des statuts, pas des temps verbaux

Les affirmations les plus difficiles à garder vraies sont celles qui portent sur l’avenir. « Génère votre facturation » est faux jusqu’à la livraison, vrai ensuite, et chaque phrase qui le dit doit changer le même jour. La prose s’en sort mal : les phrases au futur restent au futur après la livraison de la fonctionnalité, et les phrases au présent sont écrites trop tôt parce qu’elles sonnent mieux.

La solution consiste à faire de la disponibilité une valeur dans le code. Chaque fonctionnalité reçoit un statut, et chaque phrase qui en dépend est un message avec une version par statut.

Nous avons deux statuts, `FEATURE_STATUS.AVAILABLE` et `FEATURE_STATUS.ARRIVING`. Les fonctionnalités de chaque formule sont listées dans `TIER_FEATURES` avec leur statut, et les cartes des formules les regroupent sous **Disponible maintenant** et **À venir** : aucune langue ne saisit donc de statut. Quand la CLI ne pouvait pas encore générer de projets, ce fait vivait dans la prose : onze messages, dans neuf langues. #189 l’a déplacé dans une seule constante, `CLI_GENERATION`, et a transformé chacun de ces messages en select ICU :

```json title="messages/en-US/components.custom.pricing.json"
      "tagline": "{generation, select, available {The CLI and the generated source with its tests.} other {The CLI now, the generated source and tests as they arrive.}}",
```

ICU décrit le mécanisme comme l’usage d’« un argument “select” pour choisir des sous-messages au moyen d’un ensemble fixe de mots-clés ». Chaque version est une phrase complète : chaque langue peut donc l’écrire à sa façon. Un test rend chacune de ces phrases avec les deux statuts dans chaque langue, si bien que la version que personne ne voit aujourd’hui doit tout de même être correcte, et un autre échoue quand une langue dit « à venir » en dehors du select, là où le statut ne peut pas l’atteindre.

Le 20 novembre, la CLI a livré la génération de projets, et #251 a fait passer la constante à disponible. Chaque select a basculé de lui-même, dans chaque langue : le hero, le configurateur, la FAQ, les slogans des formules, l’espace client. La même pull request a pourtant dû mettre à jour la prose à la main dans dix articles de blog, dans la documentation et dans le README, car ces phrases décrivaient la génération d’une façon que le select n’atteignait pas. La leçon : faites passer par le statut chaque phrase sur une fonctionnalité non livrée dès le jour où vous l’écrivez, y compris celles des contenus longs.

### Dérivez le statut quand vous le pouvez

Un statut fixé à la main peut encore être fixé trop tôt. Là où le code lui-même sait si une fonctionnalité marche, dérivez le statut de ce savoir. Notre CLI publie les réponses que prennent en charge ses templates, et le site web en dérive le statut de la facturation :

```ts title="src/data/marketing.ts"
const TEMPLATES_GENERATE_BILLING = CLI_TEMPLATE_SUPPORT.choices.billing.some((option) => option !== NONE)

export const BILLING_GENERATION: FeatureStatus = TEMPLATES_GENERATE_BILLING ? CLI_GENERATION : FEATURE_STATUS.ARRIVING
```

Quand `CLI_GENERATION` a basculé, la facturation est restée sous **À venir**, car aucun template ne générait encore la facturation (#233). Personne n’a eu à se souvenir que la facturation était une exception ; c’est une version des templates qui génère la facturation qui la fera basculer.

### Écrivez des phrases qui renvoient à la source

Certaines affirmations sont des listes qui vont s’allonger. « Génère TanStack Start, Cloudflare, D1, Drizzle, Better Auth et Resend » est vrai pour une version et incomplet pour la suivante. #233 a réécrit ces phrases pour nommer la source au lieu de la reformuler : la génération écrit « les options que vous pouvez choisir dans le configurateur », et le configurateur active exactement les options que les templates prennent en charge. La phrase reste vraie à mesure que la liste s’allonge, et la liste vit à un seul endroit.

## Les nombres dérivés : arrondir vers le bas, plafonner et montrer les lignes

Les nombres marketing sont souvent dérivés : les heures gagnées, l’argent économisé, le délai avant le premier déploiement. Ce sont les plus faciles à gonfler et les plus difficiles à vérifier : trois règles s’appliquent donc.

1. **Calculez-les dans le code à partir d’entrées détaillées**, pour que chaque entrée puisse être lue et contestée.
2. **Arrondissez au détriment du lecteur**, et plafonnez le chiffre phare pour que l’affirmation ne puisse pas grossir d’elle-même quand une ligne est ajoutée.
3. **Publiez les lignes** partout où le chiffre phare apparaît sous une forme longue.

Notre affirmation d’« avance », les heures de travail senior qu’économise un projet généré, suit ces trois règles depuis #184. `HEAD_START_ROWS` dans `src/data/head-start.ts` liste chaque partie du projet par défaut que génèrent les templates, la couche de template dans laquelle elle est livrée, et une estimation basse et une estimation haute des heures qu’elle demanderait à la main. La facturation, les organisations, le multi-tenant et le commerce d’exemple n’ont pas de ligne, car aucun template ne les génère encore. Les lignes totalisent aujourd’hui de <RepositoryFact name="headStartLowHours" /> à <RepositoryFact name="headStartHighHours" /> heures, et le chiffre phare retient le bas de la fourchette :

```ts title="src/data/head-start.ts"
export const HEAD_START_HOURS = Math.min(
  HEAD_START_CLAIM_MAX_HOURS,
  Math.floor(HEAD_START_LOW_HOURS / HEAD_START_ROUNDING_HOURS) * HEAD_START_ROUNDING_HOURS,
)
```

Le chiffre phare affiche <RepositoryFact name="headStartHours" />. Le plafond est le nombre que le site affirmait déjà avant que les lignes n’existent : le détail ne pouvait donc que confirmer l’affirmation ou la revoir à la baisse. Si une ligne est supprimée, le chiffre baisse sans que personne ne modifie une page. Les articles qui en parlent affichent chaque ligne avec son estimation : un lecteur en désaccord avec une estimation peut voir laquelle, et de combien.

La même règle vaut pour tout chiffre dérivé d’un prix. L’affirmation selon laquelle Core coûte moins de <RepositoryFact name="corePriceInHours" unit="hour" /> du temps d’un ingénieur senior est `CORE_PRICE_IN_HOURS`, calculé à partir du prix et d’un taux horaire indicatif déclaré à côté, et un test échoue si le prix cesse un jour de rester sous ce nombre d’heures. #132 a supprimé chaque somme dérivée de prix qui était saisie dans la prose, comme la différence entre deux formules, car une différence saisie est fausse le jour où l’un des deux prix change.

## Un seul contrat entre deux dépôts

La dérive entre deux dépôts est le même problème à plus grande distance. _The Pragmatic Programmer_ l’appelle la duplication de représentation : « votre code doit posséder une connaissance qui est aussi présente dans l’élément externe […] Changez-la à un bout, et l’autre bout casse. »

SaaSy Land a deux dépôts : ce site web, qui vend des licences et sert une API de licence, et une CLI privée que les clients exécutent. Les deux ont besoin des mêmes formules, des mêmes routes d’API, des mêmes codes d’erreur, des mêmes limites, des mêmes codes de sortie et de la même liste d’options de la stack. Cette connaissance vit dans un seul paquet, `@saasyland/stack`, publié sur npm sous licence MIT. La CLI le construit ; le site web l’importe.

Combien importer est un compromis, et c’est la mesure qui a tranché pour nous. Réexporter à l’exécution les constantes de formules du paquet aurait ajouté au JavaScript de la page d’accueil un chunk de 12 072 octets, 4 493 octets compressés avec gzip, car le paquet ne déclarait rien sur ses effets de bord et rien ne pouvait être éliminé par tree-shaking (#160). Le site web garde ses propres noms de formules et les relie au contrat au niveau des types, ce qui ne coûte rien à l’exécution :

```ts title="src/modules/license/license.constants.ts"
export const LICENSE_TIER = {
  AGENCY: "agency",
  COMPLETE: "complete",
  CORE: "core",
} as const satisfies Record<string, Api["tier"]>
```

Une formule ajoutée ou supprimée d’un côté ou de l’autre empêche le site web de compiler, et un test compare les valeurs. Depuis #244, le configurateur de la page d’accueil lit lui aussi dans le paquet les questions, les options et les règles de la stack : le site web ne garde donc aucune copie de la matrice.

Un contrat partagé supprime la connaissance dupliquée. Il ne supprime pas le décalage de versions entre les déploiements. Le 20 novembre, la CLI publiée a envoyé un champ que le site web de production, encore sur la version précédente du contrat, a refusé. Les deux dépôts passaient chaque test contre la version qu’ils avaient figée. [Le premier article de cette série](/blog/ai-coding-agent-guardrails) raconte cette histoire ; la règle qui en est sortie est qu’une modification de contrat est en ligne sur le serveur avant que ne soit publié le client qui l’utilise.

### La dérive que nous avons trouvée en écrivant cet article

Le README du paquet lui-même est une page comme une autre, et il dérive comme une autre. Le README publié avec `@saasyland/stack` 0.1.0-beta.5 dit toujours que « le configurateur de saasyland.com garde sa propre copie de la matrice ». C’était vrai jusqu’à #244, fusionnée le 20 novembre, qui a supprimé la copie. npm rend ce genre de dérive tenace : « Le fichier `README.md` ne sera mis à jour sur la page du paquet que lorsque vous publierez une nouvelle version de votre paquet. » Un README qui décrit un autre dépôt est une copie d’un fait qui appartient à ce dépôt, et la solution consiste à n’énoncer que ce que fait le paquet lui-même.

## Un registre des affirmations pour ce qu’un test peut prouver

Certaines affirmations portent sur un comportement : « les licences remboursées cessent de fonctionner », « la CLI n’écrit que les options que vous avez choisies », « chaque chaîne est traduite ». Le code ne peut pas les afficher. Un test peut les prouver, et un registre peut relier chaque affirmation à son test.

Le dépôt de la CLI en tient un. Son `docs/acceptance.md` liste chaque promesse que saasyland.com, sa documentation, ses pages juridiques, ses articles et les README de la CLI elle-même font à propos de la CLI et des projets qu’elle génère. Chaque ligne a un identifiant stable, les mots exacts de l’affirmation, chaque endroit qui la fait, la couche de tests qui la prouve, et une cellule de preuve dans l’un de trois états :

- **Prouvée :** un ou plusieurs tests, chacun désigné par son fichier et son titre.
- **Prévue :** la pull request qui ajoutera la preuve.
- **Ouverte :** l’affirmation est fausse ou impossible à prouver aujourd’hui, et la ligne dit ce qui devrait changer : le produit ou le texte.

`bun run check` échoue quand une affirmation prouvée nomme un fichier de test ou un titre de test qui n’existe pas, quand une affirmation prévue ne nomme aucune pull request prévue, ou quand deux affirmations partagent un identifiant. Une affirmation prouvée par un test du dépôt du site web est vérifiée contre le site web à un commit figé, par le même job de CI qui exécute le golden diff décrit plus bas. Une pull request qui ajoute le test d’une affirmation prévue remplace la cellule prévue par ce test dans le même commit, et une pull request qui change ce que fait la CLI vérifie les lignes qui le décrivent.

Une ligne ouverte est la plus utile. Elle consigne une phrase que disent les textes et que le produit ne fait pas encore, là où chaque pull request peut la voir, et elle doit aboutir à une décision : construire la fonctionnalité ou reformuler le texte.

Le site web a son propre registre pour un type d’affirmation. Chaque parcours utilisateur et administrateur est listé dans `e2e/data/<area>.flows.ts` avec le test dans le navigateur qui l’effectue de bout en bout, ou la raison pour laquelle aucun test ne le fait encore, et `bun run check` échoue quand un parcours nomme un test qui n’existe plus (#253). La page de documentation sur la [couverture des tests](/docs/tooling/test-coverage) affiche l’inventaire : aujourd’hui, <RepositoryFact name="flowsCovered" /> parcours sur <RepositoryFact name="flows" /> sont couverts, <RepositoryFact name="flowsMissing" /> n’ont pas encore de test dans le navigateur et <RepositoryFact name="flowsToBuild" /> sont des fonctionnalités encore à construire. La même pull request a rendu exactes les affirmations sur la couverture : « 100 % de couverture de tests » est devenu « 100 % de couverture de code », car le nombre mesure les lignes exécutées par les tests unitaires, d’intégration et de composants, pas les parcours prouvés dans un navigateur. Une question d’une FAQ lui avait échappé ; elle a été corrigée le 22 novembre.

### Ce qu’un registre ne détecte pas

Un registre vérifie des preuves, pas des affirmations. Une vérification qui ne lit que les cellules de preuve ne compare jamais les mots d’une ligne avec la page qu’elle cite : une ligne peut donc continuer à citer une phrase après que le texte a été reformulé ou retiré. Si vous tenez un registre, faites lire à la vérification les endroits cités autant que les tests cités, et supprimez une ligne dès que son affirmation quitte le site.

## Le golden diff : la sortie générée face au vrai produit

Un produit qui génère du code a une affirmation de plus à tenir : que le projet généré est bien ce que montre le marketing. Le dépôt de la CLI compare directement les deux. Son script `golden` génère la stack de référence à partir des templates exactement comme le ferait `init`, récupère le site web à un commit figé, et compare les deux arborescences fichier par fichier : identique, personnalisé volontairement, différent ou manquant. Une liste commitée nomme chaque différence voulue, avec sa raison, comme les pages juridiques, qui sont l’engagement propre du client et ne sont pas générées. Le rapport est produit sur chaque pull request. Il ne bloque pas encore les fusions ; une modification prévue en fera un contrôle bloquant, avec un rapport nocturne de la dérive.

Les documents du projet généré lui-même sont soumis à la même exigence. Des tests génèrent les stacks sans les installer et lisent leur README, leur `AGENTS.md` et leur workflow de CI : ces documents ne peuvent nommer aucun script absent du `package.json` généré, aucune variable d’environnement que le projet ne définit pas, aucun chemin qu’il ne contient ni ne crée, et aucune version, qu’ils laissent aux fichiers qui figent les versions. La documentation d’un template ne peut donc dire que ce qui est vrai de la stack qui l’inclut.

## Les faits externes : les dater, les citer, les revérifier

Les faits sur le monde extérieur ne peuvent pas être affichés à partir de votre code, et ce sont eux qui dérivent le plus vite : les prix, les résultats d’enquêtes, les fonctionnalités des concurrents, le comportement d’un outil après sa prochaine version. Trois règles les gardent honnêtes.

1. **Citez la source primaire**, avec un lien, et citez-la textuellement plutôt que de paraphraser un nombre.
2. **Datez chaque vérification.** Nos articles s’ouvrent sur une ligne « Dernière vérification » et se terminent par une note indiquant quand les sources ont été lues.
3. **Revérifiez selon un calendrier**, et mettez à jour la date `updated` de l’article quand un fait change.

Revérifier révèle plus de choses que vous ne le pensez. Le 17 novembre, nous avons confronté chaque article à ses sources (#241). Une statistique de Stack Overflow avait été citée à 45 % alors que l’enquête dit 66 % ; 45 % était le deuxième élément de la même liste. Un taux de 25 à 38 % d’usage d’API dépréciées avait été attribué au mauvais article de recherche. Un chiffre de défauts attribué à GitClear ne figurait pas du tout sur la page publique de GitClear. Les prix et les décomptes des concurrents avaient bougé. Des agents avaient écrit ces phrases avec assurance, et elles avaient passé chacune de nos vérifications, car aucune vérification ne lit une enquête.

La raison commerciale de s’en soucier va au-delà de la crédibilité. Aux États-Unis, les recommandations de la FTC aux annonceurs disent que « les annonceurs doivent disposer de preuves pour étayer leurs affirmations », et que « la loi exige que les annonceurs disposent de preuves avant la diffusion de la publicité ». Une page produit qui affiche ses affirmations à partir du code, et qui liste ses affirmations comportementales avec leurs tests, a ces preuves dans ses dossiers par construction.

## Ce que cela coûte

Rien de tout cela n’est gratuit, et les coûts méritent d’être connus avant de commencer.

**Une étape de build et des composants à maintenir.** Le plugin des faits, les composants, les règles de formatage et leurs tests sont du code comme un autre. Ils demandent une revue, et ils échouent d’une façon dont un texte saisi n’échoue pas : un fait qui lit un fichier que le build ne trouve pas arrête le build.

**La taille du bundle, si vous n’y prenez pas garde.** Importer une valeur peut importer tout son module. Par deux fois, la façon évidente de partager une valeur aurait fait entrer dans la page d’accueil du code dont elle n’avait pas besoin : 3,7 Ko de code d’administration pour compter les sections d’administration (#115), et 12 Ko de la matrice de la stack et des schémas du contrat pour partager trois noms de formules (#160). Mesurez le bundle quand vous importez une valeur dans une page publique, et préférez les liens au niveau des types ou les modules étroits.

**Une prose qui tolère le changement.** Une phrase qui affiche un nombre doit se lire correctement pour n’importe quel nombre : « 1 fichier de test » et « 221 fichiers de test », et en polonais, dont les pluriels ont plus de formes que ceux du français. Nous écrivons ces phrases avec des pluriels ICU ou nous les reformulons pour que le nombre soit isolé, et certaines grammaires résistent : un nombre affiché ne peut pas toujours prendre le cas dont une phrase a besoin en allemand ou en polonais, si bien que la phrase est réécrite autour de lui.

**Un frontmatter sans nombres.** Les meta descriptions et les extraits ne peuvent pas exécuter de code : ils décrivent donc au lieu de compter. Cela coûte un peu dans les extraits des résultats de recherche.

**De grosses modifications, une fois.** Remplacer les valeurs saisies a touché 643 fichiers dans #137, car chaque valeur existait dans neuf langues. Le faire tôt coûte beaucoup moins cher que le faire tard.

Ce que cela apporte : les décomptes, les prix, les limites, les versions et les nombres de langues que notre documentation et nos articles indiquent à propos de saasyland.com sont affichés à partir du code dans chaque langue, et une modification du code qui rendrait faux un extrait cité ou un tableau de référence fait échouer la CI avec le nom de la page.

## Ce qui dérive encore

Certaines choses échappent aux mécanismes ci-dessus, et c’est là que les erreurs apparaissent encore.

- **La prose sans valeur.** Quels navigateurs tournent sur les pull requests et lesquels uniquement sur `main` : c’est un fait du workflow de CI qui ne contient aucun nombre, et la page d’accueil se trompait à ce sujet dans chaque langue jusqu’à #115. Seule la revue détecte une telle phrase, ou un test qui lit le workflow.
- **Les nombres historiques.** Cet article saisit volontairement des nombres comme 176, 221 et 643 : ils décrivent ce à quoi ressemblait le dépôt un jour donné, et chacun est rattaché à une pull request. Ils ne dérivent pas, car ce sont des affirmations sur le passé. Les nombres au présent sont affichés.
- **Les valeurs dans des messages qui ne prennent aucun argument.** La vérification des messages compare les arguments d’une traduction à ceux de l’anglais, mais elle ne cherche pas de nombres dans un message qui n’en a aucun. En écrivant cet article, nous en avons trouvé un : le slogan à côté du formulaire de connexion saisissait son chiffre de couverture dans chaque langue.
- **Les documents hors du build,** comme un README de paquet publié sur npm, qui ne changent que lorsque quelqu’un publie.
- **Les faits externes** entre deux revérifications.

## Un kit de démarrage à copier

Ces éléments conviennent à la plupart des sites TypeScript construits avec Vite. Ce sont des versions minimales de ce qui est décrit plus haut ; adaptez les noms.

**Un plugin de faits** qui mesure au moment du build et sert un module virtuel :

```ts
import { globSync, readFileSync } from "node:fs"
import type { Plugin } from "vite"

const MODULE_ID = "virtual:facts"
const RESOLVED_ID = `\0${MODULE_ID}`

const collectFacts = () => ({
  testFiles: globSync("src/**/*.test.{ts,tsx}").length,
  nodeVersion: readFileSync(".nvmrc", "utf8").trim(),
})

export const facts = (): Plugin => ({
  name: "facts",
  resolveId: (id) => (id === MODULE_ID ? RESOLVED_ID : undefined),
  load: (id) => (id === RESOLVED_ID ? `export default ${JSON.stringify(collectFacts())}` : undefined),
})
```

**Un composant** qui affiche un fait pour la locale de la page, et le code comme du code :

```tsx
import facts from "virtual:facts"

export const Fact = ({ name, locale }: { name: keyof typeof facts; locale: string }) => {
  const value = facts[name]

  return typeof value === "number" ? <>{new Intl.NumberFormat(locale).format(value)}</> : <code>{value}</code>
}
```

**Un statut et un message avec les deux versions**, plus un test qui rend les deux :

```ts
export const FEATURE_STATUS = { ARRIVING: "arriving", AVAILABLE: "available" } as const

export const BILLING = FEATURE_STATUS.ARRIVING
```

```json
{
  "billing": "{billing, select, available {Billing is wired in.} other {Billing is arriving in a later release.}}"
}
```

**Une vérification des extraits** pour les blocs de code titrés par un chemin, à exécuter dans la CI :

````ts
import { readFileSync } from "node:fs"

const TITLED_BLOCK = /^```\w*\s+title="(?<path>[^"]+)"\n(?<code>[\s\S]*?)^```$/gmu

export const excerptProblems = (page: string, source: string): string[] =>
  [...source.matchAll(TITLED_BLOCK)].flatMap(({ groups }) =>
    readFileSync(groups?.path ?? "", "utf8").includes(groups?.code ?? "") ? [] : [`${page}: not an excerpt of ${groups?.path}`],
  )
````

**Un registre des affirmations**, sous la forme d’un tableau dans votre dépôt, avec une vérification que le test de chaque ligne prouvée existe :

```md
| ID        | Claim                            | Where                | Proof                                                   |
| --------- | -------------------------------- | -------------------- | ------------------------------------------------------- |
| CLAIM-001 | "Refunded licences stop working" | pricing page, FAQ q4 | `test/licence.test.ts` › "a refund revokes the licence" |
| CLAIM-002 | "Exports to CSV"                 | features page        | Planned: the export pull request                        |
| CLAIM-003 | "Works offline"                  | landing page hero    | Open: no offline mode exists; reword or build it        |
```

**Une règle de revue** pour tout le reste, dans votre fichier d’instructions :

```md
## Numbers and claims

- Never type a count, price, limit, version, path or command into docs, copy or messages: print it from code.
- Every sentence about a feature that has not shipped goes through its status.
- Every external fact has a link to its primary source and the date it was checked.
```
