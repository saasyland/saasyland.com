## Comienza aquí: es excelente, y probablemente deberías utilizarlo.

[Better-T-Stack](https://better-t-stack.dev/) Es una CLI para la creación de plantillas de proyectos TypeScript de tipo seguro para pruebas de extremo a extremo. Está licenciado bajo MIT, su README promete "libre y de código abierto: para siempre", y cuenta con… **5.636 estrellas en GitHub** y se extrae aproximadamente **2,476 veces por semana** de npm.

La opción de matriz es la mejor del ecosistema, y no se acerca.

Lograr tantas combinaciones para producir un proyecto que pase las comprobaciones de tipo y se ejecute, es un desafío de ingeniería realmente complejo. Además, se entrega como un complemento de Claude Code con un servidor MCP, para que un agente pueda planificar y generar un stack válido, en lugar de tener que crear manualmente plantillas, lo cual es un trabajo bien pensado.

**Si estás desarrollando un prototipo, una herramienta interna, un proyecto de portafolio, una aplicación no SaaS, o cualquier cosa donde quieras entender el funcionamiento interno, deja de leer y ejecuta: `bun create better-t-stack@latest`.** Es gratuito, es excelente, y nada más lo demuestra.

## Una pila no es un producto.

El README de Better-T-Stack describe su filosofía en cuatro líneas, y la segunda línea es la comparación completa:

> Construye tu propia solución: elige solo las funcionalidades que necesitas, sin nada adicional.
> **Plantillas mínimas: estructuras básicas con cero "bloat".**
> Las últimas dependencias: siempre utilizar las versiones más recientes y estables de forma predeterminada.
> Código abierto y gratuito: forever.

No se trata de una limitación oculta. Es el diseño, expresado de manera clara, y el proyecto entrega exactamente lo que promete. La evidencia se encuentra en la última fila de la tabla anterior: los ejemplos entregados son… **Todo** y **IA**Una lista de tareas y un chat. Estos son las demostraciones canónicas que muestran que la conexión funciona, y son los ejemplos perfectos para una herramienta cuyo objetivo es conectar.

La descripción honesta no es "herramienta gratuita con funcionalidades limitadas". Es:

**Better-T-Stack crea un stack. Un kit de inicio para SaaS crea un producto.**

Ambos son scaffolders. Se detienen en diferentes puntos. Better-T-Stack se detiene cuando la interfaz de usuario puede llamar al backend y el backend puede acceder a la base de datos, de forma segura, con una de tus nueve interfaces de usuario y seis backends. Es un punto sólido donde la mayoría de los scaffolders deberían detenerse.

Una solución SaaS se detiene en otro punto: cuando una persona puede registrarse, unirse a una organización, recibir una función, ser facturada mensualmente, recibir un correo electrónico al respecto, y ser revisada por ti en un panel de administración cuando escriben de forma confusa. Todo lo que haya entre esas dos líneas es la factura.

## La parte que no corresponde a horas.

Observe las cuatro filas en esa tabla: **aislamiento multi-inquilino, roles y permisos, idempotencia de webhooks, y revocación de sesiones.**

Comparten una propiedad que ninguna de las otras filas posee. **La implementación incorrecta pasa la revisión, funciona en el entorno de desarrollo y se demuestra correctamente.**

Un filtro de tenant aplicado en la capa de visualización funciona perfectamente con un único tenant. Funciona a la perfección en tus pruebas, ya que tus fixtures utilizan un único tenant. Sin embargo, falla cuando los datos de tu segundo cliente empiezan a aparecer en el panel de control de tu primer cliente, y esto no es un reporte de error, sino una llamada telefónica.

Un manejador de webhook sin una clave de idempotencia funciona cada vez que lo pruebas, ya que nunca se envía el mismo evento dos veces. Stripe, en caso de reintento, provoca que alguien sea facturado o se le asigne un plan dos veces.

Una comprobación de permisos que lee el rol de la sesión en lugar de volver a leerlo desde la base de datos funciona hasta que alguien es degradado y mantiene su sesión anterior.

Estas no son problemas complejos. Son problemas donde… **Ser incorrecto es invisible hasta que tiene un costo.**, lo cual presenta un perfil de riesgo completamente diferente a "esto lleva 40 horas". No se puede "comprar" una solución con más horas, ya que no sabes que las necesitas. Se evitan mediante un punto de partida donde alguien ya cometió el error y lo solucionó, y donde ahora existe una prueba que falla si vuelve a ocurrir.

Lo que realmente está destinado a un \*starter kit\* de pago, no es la cantidad de horas, sino aquello.

## ¿Cómo se ve la funcionalidad de pago concretamente?

Para ser más específico en lugar de ser abstracto, esto es lo que significa "ya resuelto" en este código, mostrando los números leídos durante la ejecución de las pruebas, en lugar de introducirlos en un archivo de marketing.

**Una puerta de cobertura en lugar de una insignia de cobertura.** 141 archivos de prueba, 472 pruebas y cuatro umbrales en la configuración:

```ts
coverage: {
  thresholds: { branches: 100, functions: 100, lines: 100, statements: 100 },
}
```

Los errores que se identificaron en la sección anterior son precisamente lo que obliga una puerta de cobertura de ramas al 100 a que se pruebe. Ese es el mecanismo, no el número.

**La arquitectura es compatible con el compilador.** Tres reglas de lint aseguran que los límites del módulo sean ejecutables:

```ts
// vite.config.ts, abridged
lint: {
  options: { typeAware: true, typeCheck: true },
}
```

No se puede incluir una consulta a la base de datos en un componente de React. La compilación falla y te indica la razón.

**Rigidez sin salida.** `strict`, más `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` y `verbatimModuleSyntax`. `typescript/no-explicit-any` Este es un error, y el linter se ejecuta con `denyWarnings: true`, por lo que no hay ninguna advertencia que no puedas aprender a ignorar.

**Características opcionales, no un modelo predefinido.** El [configurator
Configurador](/#cli) plantea doce preguntas y ofrece cuatro extras: una tienda con productos de ejemplo, un curso de suscripción, un constructor de páginas visual y un editor de publicaciones visual. Activar uno añade un módulo. Desactivarlo significa que el código no existe en tu repositorio.

Ninguna de esto es una crítica dirigida contra Better-T-Stack. Es una descripción de dónde dejan de coincidir los dos productos.

## Cuando Better-T-Stack es la solución adecuada.

Expresado correctamente, ya que una comparación que siempre recomienda la opción de pago es una publicidad, no una comparación.

**Utiliza Better-T-Stack si:**

- Estás en fase de prototipado, y es posible que esta funcionalidad no esté lista en un mes.
- Estás aprendiendo, y el objetivo es asegurar la autenticación una sola vez. Lograr una autenticación completa es una inversión educativa realmente valiosa, y nadie debería ser persuadido de no hacerlo.
- Su producto no es un SaaS. No hay organizaciones, ni suscripciones, ni administración. Es una herramienta, un juego, un panel interno, un sitio de cliente.
- Ya dispones de una biblioteca interna para los tres trimestres "aburridos", algo que muchas agencias y equipos experimentados ya utilizan.
- Tu pila va más allá de lo que ofrecen cualquier paquete de pago. Nuxt, Svelte, Solid, Astro, React Native, Convex, tRPC. “Better-T-Stack” abarca todo eso, y ningún paquete de inicio de pago cubre la mayoría de estas tecnologías.
- Su presupuesto es realmente cero. Esto es una restricción legítima y no hay que avergonzarse por ello. Better-T-Stack es una opción gratuita que supera a cualquier producto de pago en su nivel gratuito.

**Considere pagar si:**

- Estás desarrollando un producto que planeas ofrecer a empresas, con funcionalidades como asientos, roles, facturas y un cuestionario de seguridad para el futuro.
- Ya has creado organizaciones y facturación una vez, y recuerdas exactamente cuánto tiempo duraron las partes aburridas.
- Quieren una puerta de pruebas que no tengan que crear, porque escribir un conjunto de pruebas de cobertura desde cero es la tarea que nadie llega a realizar.
- Quieren que se hagan cumplir los límites arquitectónicos, en lugar de los que se pretenden.
- Tu tiempo tiene un coste, y 280 a 465 horas equivalen a más de varios cientos de dólares.

## No son realmente competidores.

La cosa más útil que puedo decirte es que no se trata de una competencia entre dos opciones.

Better-T-Stack es un generador de proyectos. _cualquier_ Proyecto de TypeScript, que abarca nueve frontends y seis backends. Un kit de inicio para SaaS es una base para… _Uno._ En el ámbito de los negocios. La superposición son esos diez minutos al inicio, donde ambos crean un proyecto. Después de eso, realizan tareas diferentes.

El error de evitar no es "elegir al libre". Es elegir uno sin saber cuál de los dos trabajos que necesitó hacer. Un fundador que recorre una hermosa pila de seguridad de tipo y luego pasa seis meses construyendo organizaciones y facturación no ha ahorrado dinero. Han pagado la factura en la moneda que no aparece en una factura.

Conseguir el primer pago no es lo mismo que poder facturar de manera fiable.

</Accordion>

<Accordion title={"¿Puedo utilizar Better-T-Stack y un paquete de inicio de pago juntos?"}>

No es útil dentro del mismo proyecto, ya que ambos generan la base y solo obtienes una base. Son para proyectos diferentes. Muchos desarrolladores utilizan un scaffolder gratuito para prototipos y herramientas internas, y una “foundation” de pago para el producto que debe generar ingresos, lo cual es una asignación sensata en lugar de un conflicto.

</Accordion>

<Accordion title={"¿Incluye Better-T-Stack la autenticación?"}>

Opcionalmente, como paso de configuración: puede configurar Better Auth o Clerk. Esto le permite configurar correctamente el inicio de sesión y el cierre de sesión. Sin embargo, no le proporciona las funcionalidades de organizaciones, invitaciones, conteo de usuarios, acciones con control de roles, autenticación de dos factores obligatoria, o la posibilidad de imitación para soporte o revocación de sesiones, todas ellas funciones separadas que se añaden a la librería.

</Accordion>

<Accordion title={"¿Cuál es mejor para los agentes de codificación de IA?"}>

Ambos son buenos puntos de partida, por diferentes razones. Un scaffold mínimo proporciona al agente un contexto reducido y nada que le confunda. Un fundamento más grande con límites definidos ofrece ejemplos de funcionamiento y un build que falla cuando se desvía. La peor opción es la que ninguna ofrece: un gran codebase cuyas reglas solo existen en un README.

</Accordion>

<Accordion title={"¿Cuántas horas de tiempo ahorra realmente un paquete de inicio de pago?"}>

Para un SaaS multi-inquilino con facturación, roles y un administrador, el rango especificado en este artículo es de 280 a 465 horas de trabajo competente. Para una herramienta de usuario único con un único procesamiento de Stripe, se acerca más a 20. El número real depende completamente de lo que estés construyendo, por eso la tabla se presenta en detalle en lugar de sumada.

</Accordion>

<Accordion title={"¿Debería hacerlo yo mismo?"}>

Construylo tú mismo cuando quieras aprender sobre lo que necesitas, cuando tu producto es lo suficientemente peculiar que las suposiciones de un principiante te dificulten, o cuando realmente no tienes margen de tiempo. Compra cuando ya lo has construido una vez y recuerda exactamente cuánto tiempo le costaron los tres primeros trimestres.

</Accordion>

</Accordions>
