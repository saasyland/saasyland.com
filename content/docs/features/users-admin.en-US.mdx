## Routes

`src/routes/admin.users.tsx` is a layout whose link tabs are `USER_TABS` in `src/data/user-tabs.ts`, which joins each area's `src/data/<area>.user-tabs.ts` by `order`. A tab names its path and its page skeleton, and its label in the area's `navigation.<area>.json` also names the page in the breadcrumbs. The auth area adds **All users** and the payments area **Customers** (see [Orders and customers](/docs/features/orders#customers)). `/admin/users` redirects to `/admin/users/all`. Every tab takes its page title from `pages.admin.users`.

| Route                    | Content                                                                          |
| ------------------------ | -------------------------------------------------------------------------------- |
| `/admin/users/all`       | Live users table                                                                 |
| `/admin/users/customers` | Every Polar customer with their account, orders and what they paid after refunds |
| `/admin/users/$userId`   | A user's profile: account details, sessions and the cards other areas add        |

## All users

```tsx
<DataTable columns={userColumns} options={{ query: getUsersPageQuery, selectable: true }} />
```

- `getUsersPageQuery` calls the `getUsers` server function (`src/modules/user/use-cases/get-users.ts`, permission `user: ["list"]`). Pagination and sorting run on the server over name, role, status, email verification, 2FA, time zone and the created and updated dates.
- Status is not a column. `getUserStatus` (`user.utils.ts`) derives `banned`, `pending` or `active` from `banned` and `emailVerified`, and the server sorts by the same SQL `case` expression. `UserStatusBadge` (`user-status-badge.tsx`) draws it in the table and on the profile.
- `userColumns` lives in `src/presentation/components/custom/admin/users/user-columns.tsx`; each name links to the user's profile. The created and updated dates use the `common.dateTime` message, in the viewer's own time zone with its abbreviation, so both columns read and sort in one zone. Each user's zone has its own column.

**Add user** opens `CreateUserDialog` (`create-user-dialog.tsx`), a TanStack Form validated by `userZodSchemas.createUser`: name, email, a starting password and a role. It calls `createUser` (`user: ["create"]`, and Better Auth also checks `user: ["set-role"]` for the role), then opens the new user's profile. Better Auth creates the account with its email unverified, so the first sign-in leads to `/auth/verify-email`, which sends the verification link.

## Profile

`src/routes/admin.users.$userId.tsx` loads the user, their sessions and the data of the other areas' cards at once and titles the page after the user; a user that does not exist is a not found page.

- `getUserQuery` reads the user's row (`get-user.ts`, `user: ["get"]`). `UserDetails` (`user-details.tsx`) lists the role, status, email verification, two-factor authentication, time zone and the created and updated dates, in the order of `ADMIN_USER_DETAILS` (`src/data/admin.ts`), which `AdminUserProfilePending` follows too.
- `listUserSessionsQuery` lists the user's live sessions, newest first, without their tokens (`list-user-sessions.ts`, `session: ["list"]`). `UserSessions` (`user-sessions.tsx`) shows each device and its activity, revokes one session with `revokeUserSession` and, after a confirmation, every session with `revokeUserSessions` (both `session: ["revoke"]`). `revokeUserSession` takes the session's ID and looks its token up on the server, as `revokeSession` does for the admin's own sessions.
- Other areas add cards below the account details in `src/data/<area>.user-profile.ts`, which `src/data/user-profile.entries.ts` joins into `USER_PROFILE_SECTIONS` (`src/data/user-profile.ts`). A section names its card, its skeleton, which `AdminUserProfilePending` draws as well, and the data the page loads for the user. The auth area adds none. The licence area adds `UserLicense` (`user-license.tsx`), which reads `userLicenseQuery` (`get-user-license.ts`, `user: ["get"]`): the tier, the status, the purchase time, the consent to immediate delivery, the first activation, the first template download, the first paid lesson opened and, for an active licence, whether it can be refunded, which the server works out at the time of the request (see [Licences](/docs/features/licences#records-and-refunds)). Below it, `UserWithdrawals` (`user-withdrawals.tsx`) reads `userWithdrawalsQuery` (`get-user-withdrawals.ts`, `user: ["get"]`) and lists the account's withdrawal statements, newest first, with the name, email and order number given, how the buyer was identified, the refund terms when the statement arrived and whether the acknowledgement was emailed (see [Licences](/docs/features/licences#withdrawal-function)). Their copy is in `pages.admin.users.license`, which the licence area adds to the layout in `src/data/license.namespaces.ts`.
- The licence card shows the tier's machine limit from `LICENSE_ACTIVATION_LIMITS` and, under **Machines in use**, the machines the key has activated in Polar: how many against Polar's limit, and each machine's label, system and activation time. `userActivationsQuery` (`get-user-activations.ts`, `user: ["get"]`) reads them with `polar.licenseKeys.get` for up to <RepositoryFact name="defaultPageSize" /> accounts at a time, each request with a timeout of <RepositoryFact name="licenseActivationsTimeoutSeconds" unit="second" />, and keeps the answer for <RepositoryFact name="licenseActivationsStaleMinutes" unit="minute" />. A licence without a key says that Polar has not issued one yet, and a key that Polar does not answer for keeps the rest of the card and says that Polar could not be reached.
- The first paid lesson opened shows the lesson and its course under its time. The licence area defines that list in `src/data/opened-lesson.ts`, and the courses area adds the title in `src/data/courses.opened-lesson.ts`, read with `lessonTitleQuery` (`get-lesson-title.ts`, `course: ["read"]`), so the licence module reads no course table. Without the courses area, or for a lesson since deleted, the row shows the time alone.
- The payments area adds `UserOrders`, the account's orders and what it paid after refunds per currency (see [Orders and customers](/docs/features/orders#customers)).

The header shows the user's name and email and the same actions menu as the table row.

## Actions

`UserActions` (`row-actions.tsx`) is the menu of a user, in the last column of the table (`UserRowActions`) and on the profile:

| Item               | Opens                    | Server function                                  |
| ------------------ | ------------------------ | ------------------------------------------------ |
| **Edit user**      | `EditUserDialog`         | `updateUser` (`user: ["update"]`), the name only |
| **Change role**    | A submenu of the roles   | `setUserRole` (`user: ["set-role"]`)             |
| **Reset password** | `ResetPasswordDialog`    | `setUserPassword` (`user: ["set-password"]`)     |
| **Impersonate**    | Nothing, signs in        | `impersonateUser` (`user: ["impersonate"]`)      |
| **Ban user**       | `BanUserDialog`, confirm | `banUser` (`user: ["ban"]`)                      |
| **Unban user**     | Nothing                  | `unbanUser` (`user: ["ban"]`)                    |
| **Delete user**    | `DeleteUserDialog`       | `deleteUser` (`user: ["delete"]`)                |

- The signed-in admin's own row has no **Change role**, **Ban user** or **Delete user**, so an admin cannot lock themselves out; Better Auth refuses to ban or delete the caller anyway.
- **Impersonate** appears only for a user who is neither an admin nor banned: Better Auth refuses to impersonate an admin without `user: ["impersonate-admins"]`, which no role holds, and refuses a session to a banned user. See [Impersonation](/docs/features/impersonation).
- Deleting the user whose profile is open returns to `/admin/users/all`.
- Every success invalidates `USER_QUERY_KEYS.ALL`, or `SESSION_QUERY_KEYS.USER` for sessions, and shows a toast; errors, a missing permission among them, go through `useErrorMessage`. The menu button is disabled while one of its actions runs.

Each server function checks its own permission with `authorized(...)` from `auth.middleware.ts`. The `user` and `session` statements are Better Auth's `defaultStatements`, and the `admin` role holds Better Auth's `adminAc`, so `src/data/auth.access.ts` declares only `admin` and `settings`. The `/admin` guard admits only roles that hold `admin: ["access"]`.

## Invitations and roles

There is no invitation table, and the roles are `admin` and `customer` in `auth.roles.ts`, set per user with **Change role**. The admin has no invitations or role editor until a table and a use case back them.
