Każdy plik w `src/routes` ma tę samą budowę, więc czytelnik, który zna jeden, zna wszystkie. Plik trasy tylko składa stronę z części: deklaruje, czego potrzebuje strona, i rozmieszcza komponenty. Widżety, formularze, okna dialogowe i kolumny tabel znajdują się w `src/presentation/components/custom`.

## Trasy stron

`src/routes/admin.courses.index.tsx`:

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN_COURSES_CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}

        label={t("title")}
        onReorder={({ offset, row }) => move.mutateAsync({ courseId: row.id, offset })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.ADMIN_COURSES),
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Komponent** to lokalna stała `const` nazwana `<Name>Page`, zdefiniowana na początku. Drobne fragmenty znaczników używane tylko przez tę stronę mogą znajdować się nad nią jako komponenty lokalne, tak jak `CourseProgress` i `StartLink` w `_site._marketing.courses.$course.index.tsx`; wszystko, co ma własne dane, mutację lub stan, trafia do pliku komponentu.
- **Jedna przestrzeń nazw.** `const NAMESPACE = "pages.<feature>.<page>"` stoi bezpośrednio nad `export const Route` i jest używana w `loadPageMetadata`, `preloadNamespaces` i `staticData`. Wszystko inne, czego potrzebuje strona, deklaruje jej layout.
- **Jedno `Promise.all`.** Loader rozpoczyna całą pracę naraz: metadane strony, przestrzeń nazw i każde zapytanie, które odczytują komponenty. Zwraca `{ locale, metadata }` dla `head`. Nigdy nie czekaj na jedno z nich przed rozpoczęciem następnego.
- **`head: pageHead(ROUTES.X)`** buduje tytuł, opis, kanoniczny URL i wersje alternatywne z metadanych w pliku przestrzeni nazw.
- **Ścieżki pochodzą z `ROUTES`** w `src/routes.ts`, który łączy ścieżki wszystkich obszarów (zobacz [Ścieżki i nawigacja](#paths-and-navigation)); nigdy nie wpisuj literału ścieżki.

Strona, której tytuł pochodzi z rekordu, czeka na ten rekord i buduje swój head z danych loadera, tak jak `admin.courses.$courseId.tsx`:

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN_COURSES}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  head: ({ loaderData }) =>
    buildPageHead({ locale: loaderData?.locale, pathname: loaderData?.pathname ?? ROUTES.ADMIN_COURSES, title: loaderData?.title }),
  pendingComponent: AdminCourseEditorPending,
})
```

## Trasy layoutów

`src/routes/admin.courses.tsx`:

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Layout deklaruje `const NAMESPACES = [...] as const` nad `export const Route` i wczytuje je z wyprzedzeniem. Gdy nie ma żadnych, pomija tę opcję; nie ma `namespaces: []`.
- Layout wymienia w swoich `NAMESPACES`, jako zwykłe napisy, każdą przestrzeń nazw, której potrzebują jego strony i ich komponenty, także przestrzenie nazw innych funkcji. `/app` wymienia `pages.license`, `pages.withdrawal` i `withdrawal.validations`, bo jego przegląd pokazuje kartę licencji i ofertę, a strona licencji – kartę odstąpienia od umowy; `/admin/users` wymienia `pages.admin.customers`, `pages.admin.orders` i `pages.admin.users.license`, a `/_site/_marketing` i `/_site/docs` wymieniają `auth.validations`, bo ich stopki pokazują formularz newslettera, przy czym layout marketingowy wymienia też `withdrawal.validations`. Pominięcie funkcji usuwa jej pliki komunikatów, a reguła czyszczenia usuwa każdy napis, który wskazuje jeden z nich ([Testy](/docs/conventions/testing#tests-follow-the-features)).
- Komponent, jeśli layout go renderuje, nazywa się `<Name>Layout` i umieszcza `<Outlet />`.
- Guard trafia do `beforeLoad` w layoucie, który obejmuje obszar: `beforeLoad: requireAdmin` w `admin.tsx`, `requireSignedIn` w `app.tsx`, czyli w obu layoutach obszaru uwierzytelniania. Guardy decydują tylko o nawigacji; każda funkcja serwerowa i tak sprawdza własne uprawnienie.

## Kolejność opcji

Reguła `sort-keys` jest wyłączona w `src/routes`, ponieważ TanStack Router wnioskuje typy w kolejności deklaracji: typy opcji pochodzą z opcji nad nią. Opcje są ułożone alfabetycznie, z wyjątkiem tych, przez które router wnioskuje typy. Te stoją w kolejności z jego przewodnika po ładowaniu danych: `validateSearch` na pierwszym miejscu, przed wszystkim, co odczytuje parametry wyszukiwania, potem `loaderDeps`, `context`, `beforeLoad` i `loader`, a `head`, `headers` i `scripts` po `loader`, bo odczytują jego dane. Dzięki temu `head` dostaje typ zwracany przez loader bez zmian, bez typu pisanego ręcznie, a `code-style/route-option-order` odrzuca trasę, która deklaruje te opcje w innej kolejności:

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

Nigdy nie wpisuj tablicy ani obiektu z danymi bezpośrednio w `createFileRoute`; zadeklaruj je jako stałą powyżej.

## Parametry wyszukiwania

`validateSearch` to `zod.object` zbudowany z funkcji pomocniczych z `src/lib/search-params.ts`:

| Funkcja                           | Wartość, gdy parametru brak lub jest błędny | Zastosowanie                       |
| --------------------------------- | ------------------------------------------- | ---------------------------------- |
| `searchText()`                    | `undefined`                                 | Tokeny, adresy e-mail, kody błędów |
| `searchFlag()`                    | `undefined`                                 | Wartości logiczne                  |
| `searchParam(schema)`             | `undefined`                                 | Każdy inny schemat, np. ścieżka    |
| `searchChoice(choices, fallback)` | `fallback`                                  | Zakładka lub widok                 |

Brakujący tekst pozostaje `undefined`, więc wartość domyślna nigdy nie przecieka do URL-a budowanego przez router. Parametr `searchChoice` idzie w parze z `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, które usuwa wartość domyślną z URL-a. Strona, na którą inny serwis odsyła odwiedzających, deklaruje też `search: { middlewares: [onlyDeclaredSearch(schema)] }` z własnym schematem, jak robią to `/app` i `/app/license` dla strony płatności Polara: router buduje wtedy jej adres tylko z zadeklarowanych parametrów, a serwer przekierowuje adres z jakimkolwiek innym parametrem na ten sam adres bez niego, zanim odczyta go guard albo strona. Nigdy nie pisz ręcznie sprawdzeń `typeof search["x"] === "string"`; dodaj funkcję pomocniczą, gdy potrzebny jest nowy rodzaj pola. Gdy komponent podrzędny potrzebuje parametru, którego obecność strona już zwalidowała, strona go zawęża i przekazuje w dół, tak jak `auth.reset-password.tsx` przekazuje `token` do `ResetPasswordForm`. Strony, które czytają te same parametry, współdzielą jeden schemat w pliku `.zod.ts` modułu, z którego czytają dane, który parsują też ich szkielety, tak jak `/app/license` i część przeglądu dodawana przez obszar licencji robią to z `licenseSearchSchema` (`src/modules/license/license.zod.ts`).

## Szkielety

Nawigacja musi sprawiać wrażenie natychmiastowej, więc każda trasa, która renderuje stronę, ma `pendingComponent` odzwierciedlający tę stronę: ten sam układ, te same karty i tę samą liczbę wierszy.

- Szkielety znajdują się w pliku szkieletów danego obszaru (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) i używają `Skeleton` z shadcn.
- Szkielety są w skrypcie wejściowym każdej strony, więc szkielet importuje `Skeleton`, prymitywy shadcn, inne szkielety i stałe wyznaczające jego długości, nigdy formularz ani plik, który go zawiera; `pending-imports.test.ts` kończy się błędem, gdy któryś dociera do `@tanstack/react-form` (zobacz [Wydajność](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Zastępnik tekstu otrzymuje prawdziwy token typografii oraz `h-lh scale-y-70`, dzięki czemu ma wysokość wiersza, który zastępuje: `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- Długości list pochodzą ze stałych, których używa strona: `DataGridPending` w `data-grid-pending.tsx` domyślnie rysuje `DEFAULT_PAGE_SIZE` wierszy, czyli rozmiar strony każdej tabeli w panelu administracyjnym.
- Szkielet layoutu renderuje `pendingComponent` pierwszej trasy poniżej layoutu, która pasuje do bieżącej ścieżki i go ustawia; `usePagePending(layout)` w `src/hooks/use-page-pending.ts` odczytuje go z drzewa tras. Tak działają `AdminPending`, `AppPending`, `AuthPending` i `MarketingPending` w swoich layoutach oraz `AdminUsersPending` i `AdminCourseSectionPending` o poziom niżej. Dlatego trasa strony jest jedynym miejscem, które wskazuje jej szkielet, niezależnie od tego, który layout go pokazuje; trasa `/admin/users`, która przekierowuje do `/admin/users/all`, ustawia szkielet tamtej strony.
- Nie ma `defaultPendingComponent` dla całego routera. `src/router.tsx` ustawia `defaultPendingMs` na <RepositoryFact name="navigationPendingMs" unit="millisecond" />, a `defaultPendingMinMs` na <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, obie wartości z `src/data/navigation.constants.ts`: nawigacja, która do tego czasu się nie skończy, pokazuje szkielet trasy, a szkielet znika w chwili, gdy strona jest gotowa, i nie zostaje na ekranie ani chwili dłużej. Trasy zachowują te wartości; pomiary, na których się opierają, opisuje strona [Wydajność](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once).
- Strony dokumentacji rysują swoje szkielety wewnątrz layoutu dokumentacji: `DocsIndexPending` i `DocsPagePending` wypełniają obszary siatki artykułu i spisu treści Fumadocs, więc przy nawigacji między stronami dokumentacji pasek boczny zostaje na ekranie. Komponent strony renderuje MDX we własnym `<Suspense key={path}>`, więc pasek boczny działa, zanim załaduje się chunk MDX strony, a nawigacja zastępuje serwerowy HTML poprzedniej strony, zamiast hydratować go danymi następnej.

## Linki

- Linki routera przyjmują stałą: `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>` albo wzorzec trasy z `params` dla ścieżek dynamicznych. `LinkButton` i `SidebarMenuLink` z shadcn przyjmują `to` w ten sam sposób, a `AnchorButton` przyjmuje `href` dla adresu spoza drzewa tras.
- Nigdy nie dodawaj prefiksu języka do linku routera; dodaje go przepisywanie adresów w routerze. Pełny URL w bieżącym języku, dla wartości, która opuszcza router jako string, pochodzi z `router.buildLocation({ ... }).publicHref`, tak jak `use-auth-redirect.ts` buduje swoje linki logowania. `localizePathname` służy do URL-i budowanych poza kontekstem routera lub dla innego języka: e-maili, celów przekierowań Better Auth, linków w MDX i przełącznika języka.

## Ścieżki i nawigacja [#paths-and-navigation]

Każdą ścieżkę i każdą pozycję menu zapisuje się raz, na jednej liście, a funkcja, którą można pominąć, na przykład kursy, produkty czy strony prawne, trafia na tę listę jako jeden element wskazujący jej własną ścieżkę. Pominięcie funkcji usuwa jej pliki i nazwy, a wraz z nimi każdy element, który którąś z nich wskazuje, więc listy nie potrzebują osobnego pliku dla każdej funkcji ani zbiorczego eksportu. W ten sposób CLI `saasyland` składa projekt z warstw szablonów. Tylko `scripts/features.ts`, którego aplikacja nigdy nie ładuje, wylicza opcjonalne funkcje z ich plikami i należącymi do nich ścieżkami, żeby `bun run check:features` mogło sprawdzić witrynę bez każdej z nich ([Testy](/docs/conventions/testing#tests-follow-the-features)).

| Co                                              | Deklaracja                                                                                                                                                                                                           | Odczyt z                                                                                                      |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Ścieżki                                         | `src/routes.ts`: jedno `export const` na ścieżkę                                                                                                                                                                     | `import * as ROUTES from "~/src/routes"`                                                                      |
| Ścieżki renderowane przy żądaniu                | `REQUEST_RENDERED_ROUTES` w `src/routes.ts`                                                                                                                                                                          | `isRequestRenderedRoute` w `src/routes.ts`                                                                    |
| Pozycje menu                                    | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` i `FOOTER_NAVIGATION` w `src/data/navigation.ts`, w kolejności wyświetlania | Paski boczne, nagłówek, stopka, paleta poleceń i pulpit                                                       |
| Przestrzenie nazw layoutów                      | `NAMESPACES` w trasie layoutu                                                                                                                                                                                        | Loader layoutu i `staticData`                                                                                 |
| Listy panelu administracyjnego i panelu klienta | `DASHBOARD_STATS`, `DASHBOARD_PANELS`, `COMMAND_SEARCHES`, `USER_TABS`, `USER_PROFILE_SECTIONS` i `ACCOUNT_DELETION_NOTICES`, każda w komponencie, który ją renderuje                                                | Ten komponent, jego szkielet i trasa, która wczytuje jego dane                                                |
| Sprawdzenia działającej witryny                 | `LIVE_SITE_CHECKS` w `src/lib/deployment.ts`                                                                                                                                                                         | `verifyDeployment` ([Platforma i testy](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)) |

`src/routes.ts` deklaruje każdą ścieżkę i niczego nie importuje, bo wczytuje go każde środowisko uruchomieniowe: przeglądarka, Worker przy każdym zimnym starcie, skrypty Bun, Playwright, `vite.config.ts` i projekt Remotion. Każdy plik importuje go jako jedną przestrzeń nazw, `import * as ROUTES from "~/src/routes"`, więc każda ścieżka zachowuje swój typ literałowy, a `<Link to={ROUTES.COURSES}>` nadal jest sprawdzany względem drzewa tras. Ścieżka zbudowana z innej, na przykład `BLOG_FEED` z `BLOG`, stoi zaraz po tej, z której ją zbudowano.

Listy, do których obszar nadal dodaje wpisy we własnym pliku, czyli handlery Workera i wtyczki Vite, na razie zachowują swoje zbiorcze eksporty. Zbiorczy eksport zawiera wyłącznie wiersze `export { … } from`, po jednym na plik obszaru, posortowane według modułu, tak jak `src/integrations/drizzle-orm/drizzle.schemas.ts`.

`src/data/navigation.ts` zawiera siedem menu zapisanych wprost jako listy: każda pozycja ma swoją stronę w `to`, pełny klucz swojego komunikatu w `label`, a w panelu administracyjnym i panelu klienta także ikonę z `lucide-react`. Menu panelu administracyjnego grupuje pozycje w grupach paska bocznego, których `key` pochodzi z `ADMIN_NAVIGATION_GROUP`, a stopka – linki w kolumnach, których `key` pochodzi z `FOOTER_COLUMN`. Plik importuje tylko `lucide-react`, `~/src/routes` i `~/src/data/navigation.constants`, bo projekt Remotion czyta menu panelu administracyjnego, a jego zadanie w CI instaluje tylko własne pakiety Remotion; `src/__test__/source-layout.test.ts` kończy się błędem, gdy plik importuje cokolwiek innego. Panel administracyjny i panel klienta istnieją tylko z logowaniem, więc ich pozycje wskazują ścieżki obszaru uwierzytelniania i znikają razem z nim, tak jak **Zaloguj się** w nagłówku i w stopce:

```ts title="src/data/navigation.ts"
export const HEADER_NAVIGATION: readonly SiteEntry[] = [
  { hash: MARKETING_SECTION_IDS.PRICING, label: "navigation.core.header.pricing", to: ROUTES.HOME },
  { label: "navigation.courses.header.courses", to: ROUTES.COURSES },
  { label: "navigation.content.header.blog", to: ROUTES.BLOG },
  { label: "navigation.content.header.docs", to: ROUTES.DOCS },
  { label: "navigation.auth.header.signIn", signedIn: { label: "navigation.auth.header.account" }, to: ROUTES.SIGN_IN },
]
```

Projekt bez kursów nie ma `ROUTES.COURSES`, więc reguła czyszczenia usuwa z nagłówka pozycję **Kursy**, a grupa lub kolumna, która przez to zostaje pusta, znika razem z nią, tak jak kolumna informacji prawnych w stopce projektu bez stron prawnych.

Pozycja nagłówka lub stopki może wskazać etykietę `signedIn`, która zastępuje jej własną dla zalogowanego odwiedzającego, a jej link prowadzi wtedy do jego panelu: `/admin` dla konta z dostępem administratora, `/app` dla wszystkich pozostałych. `Navigation`, `MobileMenu` i `Footer` czytają oba menu z `useSiteNavigation` (`src/hooks/use-site-navigation.ts`), który kieruje pozycje `signedIn` do panelu, gdy tylko go zna, a w przeciwnym razie zwraca listy bez zmian. Panel bierze z jedynego hooka ze swojej listy `WORKSPACE_HOOKS`, czyli z `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`), który rozstrzyga to na podstawie roli z sesji za pomocą `hasPermission` i uprawnienia `admin: ["access"]`, które sprawdza `requireAdmin`; projekt bez logowania nie ma żadnego hooka, więc jego menu zostają bez zmian.

Etykieta jest wybierana, zanim uruchomi się jakikolwiek skrypt. `SiteEntryLabel` (`src/presentation/components/custom/site-entry-label.tsx`) renderuje obie etykiety takiej pozycji w jednej komórce siatki, więc link w każdym języku ma szerokość dłuższej z nich, a wariant `signed-in` z `globals.css` pokazuje **Twoje konto** zamiast **Zaloguj się**, gdy tylko `<html>` ma atrybut `data-session`. Worker ustawia ten atrybut na każdej stronie HTML, którą zwraca na żądanie z plikiem cookie sesji Better Auth (`markSession`, zobacz [Cache i SSR](/docs/architecture/caching-and-ssr#prerendering)), więc prerenderowana strona przychodzi już z właściwą etykietą i żaden link nie przesuwa się podczas ładowania strony. Dopóki sesja nie jest znana, link prowadzi na stronę `/auth/sign-in`, która zalogowanego odwiedzającego przekierowuje do jego panelu, a każdemu innemu pokazuje formularz. Po hydratacji `useVisitorWorkspace` pyta o sesję tylko na stronie oznaczonej przez Workera, kieruje link do panelu i utrzymuje oznaczenie w zgodzie z sesją: usuwa je, gdy sesja stojąca za plikiem cookie się zakończyła, i ustawia, gdy odwiedzający zaloguje się bez przeładowania strony. Przeglądarka po wylogowaniu o nic nie pyta, choć zachowuje plik cookie Better Auth z ostatnio użytą metodą logowania, który przetrwa wylogowanie, aby strona logowania mogła oznaczyć tę metodę jako **Ostatnio używane**. Każde menu nadaje swoim linkom klucze według ich miejsca na liście, więc React zmienia ten sam link, zamiast go zastępować, a naciśnięcie, które zaczyna się, gdy sesja się wczytuje, i tak trafia w ten link. Dopóki część strony nie zostanie zhydratowana, `useVisitorWorkspace` nie zwraca nic, bo `useHydrated` podczas hydratacji Reacta odpowiada wartością serwera: stopka hydratowana po nadejściu sesji renderuje ten sam HTML co serwer i zmienia się dopiero potem, zamiast psuć hydratację.

Każda pozycja panelu administracyjnego otwiera ekran działający na prawdziwych danych, a strona główna liczy je wszystkie. Ekran, którego dane nie mają jeszcze źródła, nie dostaje pozycji (zobacz [Panel administracyjny](/docs/features/admin-dashboard#real-data-only)).

Pasek boczny panelu klienta zawiera pozycję **Licencja** z obszaru licencji i pozycję **Płatności** z obszaru płatności, a jego materiały, nad adresem wsparcia, pozycję **Dokumentacja** z obszaru treści. Obszar podstawowy potrzebuje tylko `/` i `/api` oraz pozycji **Cennik** w nagłówku, jedynej z `hash`, która prowadzi do sekcji cennika strony `/`.

Statystyka pulpitu w `DASHBOARD_STATS` ma `prefetch`, który uruchamia loader `/admin`, i hook `useValue`, który `DashboardStats` wywołuje, aby odczytać liczbę.

`APP_STATEMENTS` w `auth.access.ts` zawiera deklaracje uprawnień, po jednej na zasób, a `scripts/features.ts` wskazuje deklaracje funkcji aplikacji, którą można pominąć, na przykład `APP_STATEMENTS.course`, aby jej pominięcie usuwało też te deklaracje (zobacz [Role i uprawnienia](/docs/guides/roles-and-permissions)).

Listy w `src/data/navigation.ts` mają zadeklarowany typ z `src/data/navigation.constants.ts`, na przykład `IconEntry` lub `SiteEntry`, więc lista, której pozycje projekt pomija, np. akcje pulpitu bez obszaru płatności, jest pustą listą, która nadal przechodzi sprawdzanie typów. `navigation.test.ts` sprawdza, czy `to` każdej pozycji jest ścieżką drzewa tras i czy żadne menu nie wskazuje dwa razy tej samej strony ani etykiety.

`label` pozycji to pełny klucz jej komunikatu, na przykład `navigation.courses.admin.courses`, a komunikat znajduje się w pliku funkcji, do której należy strona, `messages/<locale>/navigation.<feature>.json`, więc pominięcie funkcji usuwa razem z nią jej etykiety. Komponent renderuje etykietę przez `t(entry.label)` z `useTranslations()`. Sekcja panelu administracyjnego nadaje etykiety swoim podstronom w ścieżce nawigacyjnej w polu `breadcrumbs` swojej pozycji, które mapuje segment ścieżki na klucz, np. `create` na `navigation.courses.breadcrumbs.create`. Zakładka zarządzania użytkownikami, wyszukiwanie w palecie poleceń i statystyka pulpitu też podają pełny klucz swojej etykiety, na przykład `navigation.team.userTabs.invitations`, `navigation.auth.search.users` i `dashboard.courses.learners`, a panel pulpitu bierze swoje teksty spod swojego `key` w `dashboard.<feature>.json`. Oba rodzaje plików są głównymi przestrzeniami nazw, więc każde menu może podpisać każdą pozycję. To, co należy do samego menu, zostaje w jego przestrzeni nazw: `groups.<group>` w `pages.admin.sidebar`, `columns.<column>` w `components.custom.footer` oraz wezwanie do działania, przycisk menu i link przejścia do treści z nagłówka w `components.custom.navigation`. `navigation.test.ts` kończy się błędem, gdy pozycji, jej wariantowi dla zalogowanych, elementowi ścieżki nawigacyjnej, zakładce zarządzania użytkownikami albo wyszukiwaniu w palecie poleceń brakuje komunikatu w którymś języku, a `admin-dashboard.component.test.tsx` – gdy brakuje go statystyce.

Strony renderowane przez Workera przy każdym żądaniu, na przykład `/admin`, `/auth` czy `/courses`, są wymienione w `REQUEST_RENDERED_ROUTES` w `src/routes.ts`. Wtyczka TanStack Start w `vite.config.ts` wyłącza je z prerenderingu za pomocą funkcji `shouldPrerender` (`src/lib/prerender.ts`), która wywołuje `isRequestRenderedRoute`, więc nie ma ich też w mapie witryny stron, a `buildPageHead` przypisuje im kartę witryny, chyba że trasa przekaże własny obraz. Renderowanie przy każdym żądaniu nie wyklucza strony z wyników wyszukiwania: strony kursów są wymienione w mapie witryny, którą Worker generuje z D1 (zobacz [Podglądy w wyszukiwarkach i mediach społecznościowych](/docs/features/seo#course-sitemap)). Vite nie rozwiązuje aliasu `~` podczas wczytywania własnej konfiguracji, więc `prerender.ts` importuje `src/routes.ts` po ścieżce względnej.
