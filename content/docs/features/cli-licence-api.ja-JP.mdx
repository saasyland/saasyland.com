有料の `saasyland` CLI は、ライセンスキーを saasyland.com で確認します。Worker は <RepositoryFact name="cliApiBasePath" /> 配下で応答し、キーを D1 の `license` テーブルと照合し、端末を Polar 上のキーのアクティベーションとして管理し、各リリースのテンプレートバンドルを R2 から配信します。そのため、CLI が Polar を直接呼び出すことはありません。

両者の間のコントラクトは、`@saasyland/stack` パッケージの `./api` エントリーです。このパッケージは MIT ライセンスで、CLI のリポジトリから公開されています。コントラクトは、ルート、ヘッダー、リクエストとレスポンスのスキーマ、エラーコード、レート制限を定義します。CLI はこれを使ってすべてのリクエストを組み立て、すべてのレスポンスを読み取ります。サイトはこれを使ってすべてのリクエストを読み取り、すべてのレスポンスを書き出します（`readApiRequest`、`apiResponse`、`apiErrorResponse`）。そのため、どちらの側も相手からずれることはありません。このページの値と表は、コントラクトから出力しています。

## 端末

- ライセンスキーは、プランが許す数の端末で有効にできます。Core は <ActivationLimit tier="core" />、Complete は <ActivationLimit tier="complete" />、Agency は <ActivationLimit tier="agency" /> です。これは `LICENSE_ACTIVATION_LIMITS` で、Polar が強制する上限です。ランディングページと `/app/license` のプランのカード（`PricingTiers`）もこの値を表示するため、購入者は支払いの前に各上限を確認できます。
- CLI は、その端末上で導出する端末 ID で端末を識別します。これは、オペレーティングシステムのマシン ID、または CI では CI プロバイダーとリポジトリの ID を、固定の鍵で HMAC-SHA256 にかけたものです。オペレーティングシステムの生の ID が端末の外に出ることはありません。
- 同じ端末からもう一度アクティベートすると、別の枠を使わずに、その端末のアクティベーションを変更せずに返します。そのため、端末は枠と名前をそのまま保持します。端末の名前を変更するには、端末を解放してから `--label` を付けてもう一度アクティベートします。CI では、1 つのリポジトリ内のすべての実行が同じ端末として扱われます。
- 顧客は、`/app/license` の **端末** から、または CLI で枠を解放します。

## リクエスト

すべてのリクエストは、ライセンスキーを `authorization: Bearer <key>` として、端末 ID を <RepositoryFact name="cliApiMachineHeader" /> ヘッダーで送信します。レスポンスはすべて JSON です。

<RepositoryTable columns={["リクエスト", "成功時のステータス", "エラーコード"]} name="cliApiEndpoints" />

- **ライセンスの読み取り**: プラン、その端末数の上限、使用中の端末の数、そしてすべての端末とそのラベルおよび作成日時を返します。CLI がアクティベートした端末には、種類（端末または CI）、プラットフォーム、CLI のバージョンも表示されます。呼び出し元の端末には `current` の印が付きます。
- **アクティベート**: CLI のバージョン、種類、プラットフォーム、最大 <RepositoryFact name="cliApiLabelMaxLength" /> 文字のラベルを受け取ります。新しいアクティベーションには表の 1 つ目のステータスで、呼び出し元の端末の既存のアクティベーションには 2 つ目のステータスで応答します。
- **アクティベーションの確認**: アクティベーションがそのキーと呼び出し元の端末のものであることを確認します。
- **リリースのテンプレートのダウンロード**: リリース（`version`）とスタックの回答を受け取り、リリースのテンプレートバンドルへの署名済み URL、バンドルのダイジェストとサイズ、URL の有効期限を返します。[テンプレートバンドル](#template-bundles)を参照してください。
- **アクティベーションの解放**: キーの任意の端末を削除し、その枠を解放します。

## テンプレートバンドル [#template-bundles]

CLI のテンプレートは、リリースごとに 1 つのバンドルとして提供されます。これは CLI のリポジトリのリリースがビルドするアーカイブで、JSON にしたバンドルを gzip で圧縮したものです。各リリースのアーカイブは、<RepositoryFact name="cliBundleBinding" /> R2 バケットの <RepositoryFact name="cliBundleKey" /> というキーのオブジェクトです。バンドルのリクエストは次のことを行います。

1. **アクティベーションの確認** と同じように、パスのアクティベーションがそのキーと呼び出し元の端末のものであることを確認し、そうでなければ `activationNotFound` を返します。
2. リリースのオブジェクトのヘッド、つまり内容を除いたサイズとメタデータを読み取り、オブジェクトがなければ、要求された `version` を付けて `versionNotFound` を返します。
3. `url`、`sha256`、`size`、`expiresAt` を返します。

`sha256` は、アーカイブの内容、つまり gzip を展開して得られる JSON の SHA-256 を小文字の 16 進数で表したものです。これは、CLI が `bundle-digests.json` でリリースごとに固定し、ダウンロードしたものを展開するときに `unpackBundle` から返されるダイジェストです。圧縮後のバイト列はランタイムの zlib によって変わりますが、JSON は変わらないためです。`size` は URL が配信するバイト数、つまり圧縮されたアーカイブのサイズです。Worker はアーカイブを読まずに、どちらもオブジェクトのヘッドから読み取ります。`size` はオブジェクトのサイズ、`sha256` はリリースがアーカイブと一緒に書き込むオブジェクトのカスタムメタデータ <RepositoryFact name="cliBundleDigestMetadata" /> です。そのため、バンドルがどれだけ大きくなっても、バンドルのリクエストにかかるコストは変わりません。

URL は、コントラクトが求めるとおり HTTPS で、リクエストに応答したホスト上の <RepositoryFact name="cliBundleUrlPath" /> というパスです。

- `expiry` は 36 進数の Unix 時刻で、URL を発行した秒から <RepositoryFact name="cliApiBundleUrlTtlSeconds" unit="second" />後です（`API_LIMIT.BUNDLE_URL_TTL_SECONDS`）。`expiresAt` は同じ時刻を ISO 8601 で表したものです。
- `signature` は、HKDF が `AUTH_SECRET` からバンドルの URL 専用に導出した鍵による `<version>.<expiry>` の HMAC-SHA-256 です（`src/lib/hmac.ts` の `signHmac`）。URL には S3 の認証情報も独自のシークレットも必要なく、署名済みの動画のパスでバンドルが開くことはありません。

`src/server.ts` の `REQUEST_HANDLERS` にあるライセンスのエントリーは、`/bundles/` 配下のすべてのパスを、ロケールミドルウェアと TanStack Start より前に `serveBundle`（`src/modules/license/license.delivery.ts`）へ渡します。`serveBundle` は `GET` と `HEAD` だけを受け付け（それ以外は `405`）、署名済みのバンドルのパスではないパスやアーカイブのないリリースには `404` を、期限切れまたは不正な署名には `403` を返し、それ以外の場合はオブジェクトを <RepositoryFact name="cliBundleContentType" /> として、その `Content-Length`、`ETag`、`Cache-Control: private, no-store` とともにストリーミングします。署名済み URL は、期限が切れるまでベアラーリンクとして機能します。誰がダウンロードできるかのチェックは、URL を発行する時点で行われます。

コントラクトはスタック自身のスキーマで回答を検証するため、ルールが禁止するスタックのリクエストには、何も読み取る前に `invalidRequest` を返します。どのスタックにもそのリリースの同じバンドルが返され、サイトは回答もリリースも保存しません。読み取れないバケットや、メタデータ <RepositoryFact name="cliBundleDigestMetadata" /> に SHA-256 がないオブジェクトには `serviceUnavailable` を返し、ログにそのオブジェクトを記録します。

## バンドルの公開 [#publishing-bundles]

サイトが <RepositoryFact name="cliBundleBinding" /> バケットに書き込むことはありません。CLI のリポジトリのリリースワークフローが、各リリースのアーカイブを変更せずに、`wrangler.jsonc` がバインドする次のバケットにアップロードします。

<RepositoryTable columns={["環境", "バケット"]} name="cliBundleBuckets" />

- すべてのリリースは、デプロイされた両方のバケットにアップロードされます。プレビューのバケットはプレビューのデプロイ上のジャーニースイートに、本番のバケットは顧客に配信します。`development` と `test` のバケットはローカルで、`bun run db:seed:local` と `bun run db:reset:test` が Wrangler の `getPlatformProxy` で `e2e/fixtures/bundle` のアーカイブとそのダイジェストを投入します。
- オブジェクトのキーは <RepositoryFact name="cliBundleKey" /> で、バージョンは CLI が `version` で送るとおりのものです。
- コンテンツタイプは <RepositoryFact name="cliBundleContentType" /> で、コンテンツエンコーディングは指定しません。アーカイブそのものがオブジェクトであり、`Content-Encoding` があると、CLI が確認する前に HTTP クライアントがアーカイブを展開してしまうためです。
- オブジェクトは `serializeBundle` が書き出したアーカイブです。その内容の SHA-256 はリリースが固定するダイジェストなので、その固定値を持つ CLI はほかのバイト列を拒否し、公開したアーカイブが変わることはありません。
- オブジェクトは、その SHA-256 を小文字の 16 進数でカスタムメタデータ <RepositoryFact name="cliBundleDigestMetadata" /> として持ちます。Workers API では `customMetadata`、R2 の S3 API では `x-amz-meta-<name>` ヘッダーです。Worker はこの値をそのまま返し、計算のためにアーカイブを読むことはないため、この値がないオブジェクトは配信されません。
- CLI リポジトリの `bun run bundle:upload <version>` が、両方のバケットへの書き込みを許可された API トークンで、R2 の S3 API を通じてアーカイブ、コンテンツタイプ、ダイジェストを書き込み、読み戻して確認します。`wrangler r2 object put` はカスタムメタデータを設定しないため、バンドルの公開には使えません。

## エラー

エラーは、`code` でそのエラーを示す JSON オブジェクトで応答します。

<RepositoryTable columns={["コード", "HTTP ステータス"]} name="cliApiErrors" />

- `invalidLicenseKey`: キーがない、形式が正しくない、または存在しません。レスポンスには `www-authenticate: Bearer` が付きます。
- `licenseRefunded`: Polar が注文を全額返金しました。
- `licenseRevoked`: 返金なしでライセンスが取り消されました。たとえば、Polar がキーを取り消した場合です。
- `activationLimitReached`: すべての枠が使用中です。レスポンスにはライセンスとその端末が含まれるため、CLI はそれらを一覧表示し、`/app/license` で枠を解放するよう顧客を案内できます。
- `activationNotFound`: キーにそのアクティベーションがないか、アクティベーションが別の端末のものです。
- `versionNotFound`: リリースにテンプレートバンドルがありません。レスポンスには `version` が含まれます。
- `invalidRequest`: 問題を 1 つずつ、`body.label` のようなパスとメッセージとともに `issues` に列挙します。
- `rateLimited` と `serviceUnavailable`: `retryAfterSeconds` と、同じ数値を入れた `retry-after` ヘッダーを返します。`rateLimited` は、そのアドレスまたはキーが期間内のリクエストを使い切ったことを意味します。`serviceUnavailable` は、サイトが応答できなかったことを意味します。D1 がリクエストをカウントできなかった、ライセンスを読み取れなかった、またはその最初の使用を記録できなかった、Polar に到達できなかった、Polar が失敗した、サイトのリクエストを制限した、またはリクエストを拒否した、バンドルのバケットを読み取れなかった、リリースのオブジェクトのメタデータにダイジェストがなかった、あるいは Worker がそれ以外の理由で失敗した場合です。CLI は <RepositoryFact name="cliApiRetryAfterSeconds" unit="second" />後（`LICENSE_API_RETRY_AFTER_SECONDS`）に再試行してください。

どのエンドポイントも、サイトの失敗には HTTP 500 ではなく `serviceUnavailable` を返します。HTTP 500 は、コントラクトの `readApiResponse` が `unexpectedResponse` に変換し、CLI が自身の更新を促す案内に変えてしまうためです。ハンドラーは `license.api.ts` の `serve` という 1 つの境界を共有します。`serve` はコントラクトのどの回答にも当てはまらないエラーをすべて捕捉し、エラーとその原因、スタックとともに `[license] <method> <path> failed` をログに記録して、`serviceUnavailable` を返します。ログでは呼び出し元のライセンスキーが `[licence key]` に置き換わります。Drizzle のクエリエラーにはクエリにバインドされた値が含まれ、Polar の検証エラーにはリクエストの内容が含まれることがあるためです。

## レート制限 [#rate-limits]

<RepositoryFact name="cliApiRateLimitSeconds" unit="second" />
あたり、IP アドレスごとに <RepositoryFact name="cliApiRequestsPerAddress" /> 件、ライセンスキーごとに
<RepositoryFact name="cliApiRequestsPerLicenseKey" />
件のリクエストを送信できます。最初に判定するのはアドレスの上限で、そこで拒否されたリクエストはキーにはカウントされないため、1
つのアドレスからキーを推測しようとしても、アドレスの上限で止まります。コントラクトが読み取れるキーのないリクエストは、そのアドレスにだけカウントされます。カウンターは
`rate_limit` テーブルに保持され、アドレスと、ライセンスキーの SHA-256
ハッシュで識別されます。ライセンスキーそのものを使うことはありません。バンドルのリクエストはほかのリクエストと同じようにカウントされますが、署名済み
URL からのダウンロードはカウントされません。

リクエストが D1 に届くのは、Worker が Polar に問い合わせる前の 1 回だけです。`rateLimitBatch`（`src/lib/rate-limit.ts`）は、リクエストをアドレスとキーにカウントするステートメントを返し、`license.api.ts` の `admit` がそれをライセンスの検索と一緒に 1 つのバッチとして D1 に送ります。D1 はバッチを 1 つのトランザクションとして実行します。キーは `authorization` ヘッダーから取り出すため、`readApiRequest` が本文、端末ヘッダー、ルートパラメーターを読み取るのは両方の上限が許可したリクエストだけで、どちらかの上限を超えたリクエストは本文を読み取る前に拒否されます。バッチはカウンターに書き込む前に、リクエストを拒否するカウンターを読み取るため、拒否されたリクエストは何も書き込みません。キーはアドレスがリクエストを許可したときだけカウントし、期限切れのカウンターはリクエストごとに 1 回、上限のある件数だけ削除します。D1 がバッチを実行できないときは、リクエストは拒否されずに失敗するため、API は `rateLimited` ではなく `serviceUnavailable` を返します。

## 返金済みと取り消し済みのライセンス

判断するのは、キーが属する `license` 行です。Polar の Webhook がこの行を最新の状態に保ちます（[ライセンス](/docs/features/licences)を参照）。全額返金でステータスは `refunded` になり、特典の取り消しで `revoked` になります。Polar は返金された注文の特典も取り消し、2 つのイベントはどちらの順序でも届く可能性があるため、取り消しが `refunded` を置き換えることはありません。Polar がすでにキーを取り消すか無効にしていて、その Webhook がまだ届いていない場合も、API は `licenseRevoked` を返します。

## 使用の記録 [#records-of-use]

API は、[ライセンス](/docs/features/licences#records-and-refunds)の返金ルールのために、レッスンのページが記録する最初の有料レッスンと並べて、現在の購入での CLI の最初の使用をその `license` 行に記録します。

- `activated_at`: キーがいずれかの端末で最初にアクティベートされた日時です。新しい Polar のアクティベーションによるものも、すでにアクティベーションを持つ端末によるものも含みます。この列が追加される前にアクティベートされた端末は、次にアクティベートしたときに記録されます。
- `delivered_at`: バンドルのリクエストが最初にテンプレートを渡した日時です。Worker はバンドルのダイジェストとサイズを読み取って URL に署名した後、応答する前にこれを書き込むため、記録されていない署名済み URL を CLI が受け取ることはありません。

リクエストを数えるバッチ内のライセンス検索で両方の記録も読み取るため、Worker は受け付けたライセンスの記録がまだ空の場合にだけ書き込み、後のアクティベーションやダウンロードで D1 への往復が増えることはありません。各書き込みは、`update … where key = ? and delivered_at is null` のように、列が空の間だけその列を設定します。そのため、2 つのリクエストが競合しても、後のアクティベーションやダウンロードが最初の記録を動かすことはありません。書き込みが失敗すると、サイトのほかの失敗と同じく `serviceUnavailable` を返します。Polar がすでに保持しているアクティベーションを CLI が再試行した場合、その端末はアクティベート済みとして扱われ、再試行の際に記録されます。`activationLimitReached`、`activationNotFound`、`versionNotFound` のように拒否されたリクエストは、何も記録しません。
