Schemas live in the table modules and are collected by `src/integrations/drizzle-orm/drizzle.schemas.ts`. Migrations are timestamp-prefixed SQL files in `src/integrations/drizzle-orm/migrations/`, committed together with the schema change.

## Three databases

Each Wrangler environment has its own D1 database, and no script or server reaches another environment's data:

| Environment   | Database                                     | Used by                                              | Its data                            |
| ------------- | -------------------------------------------- | ---------------------------------------------------- | ----------------------------------- |
| `development` | Local `saasyland_local` in `.wrangler/state` | `bun run dev` and the `:local` scripts               | Yours; `db:seed:local` fills it     |
| `preview`     | Remote `saasyland_com_preview`               | `preview.saasyland.com` and the `:preview` scripts   | Test purchases with Polar's sandbox |
| `production`  | Remote `saasyland_com_production`            | `saasyland.com` and the `:production` scripts        | Customers                           |
| `test`        | Local `saasyland_test` in `.wrangler/test`   | Playwright, the isolated preview and `db:reset:test` | `db:seed:test` fills it             |

`bun run dev` never reads or writes a remote database. Every binding of the `development` environment in `wrangler.jsonc` has `remote: false`, the Cloudflare Vite plugin runs with `remoteBindings: false` (`vite.config.ts`), and `src/__test__/wrangler.test.ts` fails when a development binding becomes remote or shares a database, namespace or bucket with `preview` or `production`. The other bindings are local for the same reason:

- `CACHE` (KV) holds only caches that the Worker fills again, the GitHub star count and the regional checkout discounts, so a local namespace starts empty and works at once.
- `MEDIA` and `BUNDLES` (R2) are the local buckets `saasyland-local` and `saasyland-bundles-local`. The rows that point at their files, videos, lesson materials and template bundles, are in D1, so a local database with remote buckets would show preview's files to rows that do not exist and leave orphaned files in preview's buckets.
- Better Auth keeps its users, sessions, verification tokens and rate limits in D1, so sign-up, sign-in and the admin work locally. Emails still go out through Resend with the key in `.env.development`, and Polar calls go to the sandbox named by `POLAR_SERVER`.

## Migrations

1. Change `src/modules/<table>/<table>.schema.ts`.
2. Run `bun run db:generate` and review the generated SQL.
3. Apply it locally with `bun run db:migrate:local` and run the tests; Vitest applies every migration to its in-memory database.
4. Deploy: the deploy scripts and CI apply it to the preview or production database before the new Worker goes live.

```sh
bun run db:generate
bun run db:migrate:local
bun run db:migrate:test
```

Installing dependencies and building never migrate a database.

SQLite does not enforce the length in a column type such as `text(<length>)`, and drizzle-kit changes one by rebuilding the table: a new table, every row copied into it, the old one dropped. So the limits are the ones the forms and the server functions validate, and a column keeps the length it was created with. `user.email` and `newsletter_subscriber.email` stay `text(<RepositoryFact name="declaredEmailColumnLength" />)` and `user.name` `text(<RepositoryFact name="declaredNameColumnLength" />)` through `DECLARED_COLUMN_LENGTH` in `auth.constraints.ts`, while an address may have <RepositoryFact name="emailMaxLength" /> characters (`EMAIL_MAX_LENGTH`, the path limit of RFC 5321) and a name <RepositoryFact name="nameMaxLength" /> (`NAME_MAX_LENGTH`). A table created later, such as `withdrawal`, declares `EMAIL_MAX_LENGTH` and `NAME_MAX_LENGTH` from the start, so nothing has to be rebuilt. A generated migration that contains ``CREATE TABLE `__new_`` rebuilds a table; review it before you commit it.

## Drizzle Studio

`bun run db:studio:local` runs `scripts/studio-local.ts`. Miniflare keeps the local database as one SQLite file in `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/`, named after a hash of the database ID in `wrangler.jsonc`; the script works the name out the way Miniflare does, fails with a hint when the file does not exist yet, and opens Drizzle Studio on it with `src/integrations/drizzle-orm/drizzle.local.config.ts`, which reads the file through `@libsql/client`. Studio and the dev server can run at the same time.

`bun run db:studio:preview` and `bun run db:studio:production` use the D1 HTTP API with `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` and `CLOUDFLARE_ACCESS_TOKEN` from `.env.preview` or `.env.production`, through `src/integrations/drizzle-orm/drizzle.config.ts`. Every edit there is an edit to that environment's live data.

## The local seed

```sh
bun run db:reset:local
bun run db:seed:local
bun run dev
```

Stop the dev server before `db:reset:local`. `db:seed:local` (`scripts/seed-local.ts`) starts the local bindings of the `development` environment with Wrangler's `getPlatformProxy`, writes the following and can run again at any time; it changes only what differs:

- An admin, <RepositoryFact name="localAdminEmail" />, with a verified email address. Its password is `LOCAL_ADMIN_PASSWORD` from `.env.development`, or <RepositoryFact name="localAdminPassword" /> when that is not set, and it must meet the sign-up rules. Each run sets the password again. Use a password that exists only on your machine, never a production one: the seed writes only the local database.
- The curriculum from `content/courses/saasy-land-courses.json`, imported with `planCourseImport` and `applyCourseImport` from `src/modules/course/course.transfer.ts`, the same code as **Import** in the admin. Its lessons have no video yet, so they show as [being recorded](/docs/features/courses#being-recorded).
- The covers in `content/courses/covers/`, named by slug, for the courses that have none: each size goes to the local `MEDIA` bucket and the course gets its key, so the local catalogue looks like production's.
- The licences, the order without a licence and the CLI template bundle of the test seed (`e2e/data/license.seed.ts`), so the admin dashboard and the licence pages have real-shaped data. Their customer accounts use the password <RepositoryFact name="testPassword" />.

Each of these is one element of `LOCAL_SEEDS` in `scripts/seed-local.ts`, written in its area's own file: the admin in `scripts/seed-local-admin.ts`, the curriculum and the covers in `scripts/seed-local-courses.ts`, and the licences in `e2e/data/license.seed.ts`. A project without an area has no element for it and seeds the rest.

Sign in at http://localhost:3000/auth/sign-in with the admin and open `/admin/courses` to see the courses.

## Course data in each environment

- Local: `bun run db:seed:local` imports the curriculum.
- Production: an admin imports `content/courses/saasy-land-courses.json` in the admin. Sign in as an admin, open **Content → Courses**, choose **Import**, pick the file, run **Check file**, read the plan, then **Import**. Importing the same file again changes nothing. See [Import and export](/docs/features/courses#import-and-export).
- Preview: `bun run courses:sync:preview` copies the published courses of production, so preview shows the catalogue that production shows.

### Copying the courses to preview

```sh
bunx wrangler login
bun run courses:sync:preview
```

`scripts/sync-courses.ts` reaches D1 the way `admin:grant:*` does, through `wrangler d1 execute --remote` and the shared `scripts/d1-execute.ts`. It sends production `SELECT` statements only, and writes preview in one `--file` run. It copies, row for row with their ids and timestamps:

- every published course, with its chapters, its lessons and their link attachments; a row preview already has is updated by its id, so a second run changes nothing that production has not changed.

It copies no `video` rows and leaves each lesson's `video_id` out of the copy: a video's files are in production's `MEDIA` bucket, so a lesson new to preview starts without a video and shows as [being recorded](/docs/features/courses#being-recorded) instead of failing to play, and a lesson preview already has keeps the video uploaded in preview's lesson editor.

Within the courses it copies, it deletes the chapters, lessons and link attachments that production no longer has, with preview's progress on those lessons, and it deletes a preview course that production no longer publishes. It copies no file attachments, whose files are in production's bucket, and nothing outside these tables: no users, sessions, licences, orders, subscriptions, uploads or progress.

It leaves `course.cover` out of the copy: a cover's files are in production's `MEDIA` bucket, so a course new to preview has no cover, and a course preview already has keeps the cover uploaded there.

It stops before writing when a preview course has the slug of a production course with another id, such as one imported from the curriculum file; delete that course in preview's admin, then run it again. It prints what it created, updated and removed in each table, then counts the rows in preview and fails if they differ from production's.

## Discounts and billing countries of older orders

The migration `20261122143452_familiar_tusk.sql` added the discount and the billing country to the `order` copy ([Payments](/docs/features/payments#orders-and-subscriptions-in-d1)). New webhooks fill them, and an order copied before the migration has an empty `discount_amount` until Polar sends it again. To fill every such order at once:

```sh
bunx wrangler login
bun run orders:backfill:preview
bun run orders:backfill:production
```

`scripts/backfill-order-terms.ts` reads `POLAR_ACCESS_TOKEN` and `POLAR_SERVER` from `.env.<environment>`, lists the orders whose `discount_amount` is empty with `wrangler d1 execute` (remote for preview and production, local for `orders:backfill:local`), and reads each from Polar with `polar.orders.get`, one at a time, waiting as long as Polar asks when it answers 429. It writes every order in one `--file` run, each `UPDATE` limited to its ID and to an empty `discount_amount`, so it never overwrites a copy that a webhook filled meanwhile and a second run changes nothing. It prints how many orders it copied and exits with an error while any is left, such as an order Polar no longer returns. Apply the migration first.

## The first admin

The application has no endpoint, seed or variable that grants the `admin` role. On preview and production, the first admin is created with a script, and this is the only way:

```sh
bunx wrangler login
bun run admin:grant:production you@example.com
```

1. Sign up on the site with the address and open the link in the verification email.
2. Sign in to Wrangler with a Cloudflare account that can write to the environment's D1 database.
3. Run `bun run admin:grant:preview <email>` or `bun run admin:grant:production <email>`.

`scripts/grant-admin.ts` reads the account with `wrangler d1 execute --remote`, prints it, and refuses an address with no account, an account whose email is not verified and a banned account. It then sets `role` to `admin` on that one row, reads the account again and prints it. An account that is already an admin is left as it is.

This is safe for three reasons:

- Only someone who can write to the D1 database of that Cloudflare account can run it, with their own `wrangler login`. Such a person could change any row in Cloudflare's dashboard anyway; the script adds no new way in.
- It changes one column of one account that has proved it owns its email address.
- The application enforces roles on the server: `requireAdmin` guards `/admin`, and every admin server function checks its permission with `authorized(...)` in `auth.middleware.ts`. See [Roles and permissions](/docs/guides/roles-and-permissions).

Later admins are made by an existing admin in **Administration → User Management**: open the user, then **Change role**. `bun run admin:grant:local <email>` does the same for an account you signed up with locally. An existing admin can also invite a new address with the `admin` role; see [Invitations](/docs/features/users-admin#invitations).
