## Locales and URLs

SaaSy Land serves <RepositoryFact name="languages" /> locales, <RepositoryFact name="supportedLocales" />, with `en-US` as the default. The default locale has no prefix (`/docs`); every other locale uses its full tag (`/pl-PL/docs`). The Worker redirects language-only and default-locale prefixes such as `/pl/docs` or `/en-US/docs` to the canonical URL.

`getCurrentLocale()` is isomorphic and reads the locale from the URL path on both sides, falling back to `en-US` when the path has no locale prefix. `/api` and server function URLs never have one, so on the server it returns `en-US` for those requests. The Worker keeps the locale cookie in sync with the page URL, but no code chooses a locale from the cookie. Server functions that return localized content take the locale as input, and auth emails read it from the flow's `callbackURL`.

## Messages

Translations live in `messages/<locale>/<namespace>.json`. The file name is the namespace, for example `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` or `common`. Dotted namespaces are merged into one message tree, so `useTranslations("pages.admin.users")` reads `pages.admin.users.json`. Every page namespace has `metadata.title` and `metadata.description` for the head tags. Messages are plain JSON without generated types.

## Loading

- **Root namespaces** (`common`, `components.*`, `errors*`) are preloaded in the root `beforeLoad`.
- **Page routes** declare `const NAMESPACE = "pages.x"`, preload it in the loader and list it in `staticData.namespaces`.
- **Layout routes** declare `const NAMESPACES = [...] as const` and do the same.
- **`TranslationsProvider`** wraps the document body in the root shell. It combines the root namespaces with the matched routes' `staticData.namespaces` and passes the result to `IntlProvider`, so every screen, including error screens, is translated.
- **Emails** load their namespace on the server with `loadNamespace` in the use case that sends them.

## Links

Router links need no locale handling: `<Link to={ROUTES.SIGN_IN}>` gets the prefix from the router's `rewrite`. A raw URL in the current locale, such as a Better Auth `callbackURL`, comes from the router too, which applies the same rewrite and serializes the search params (`useAuthRedirect` in `src/hooks/use-auth-redirect.ts`):

```ts
const { publicHref: callbackURL } = router.buildLocation({ search: { redirect }, to: ROUTES.AUTH_CALLBACK })
```

`localizePathname({ locale, pathname })` builds a URL for a given locale: the locale switcher's links and the links in emails, which the server builds without a router.

The locale switcher renders a plain link to the same path in each locale, so changing language loads a new document.

## Translations in components

A component calls `useTranslations` exactly once and names the translator `t`. i18n-ally re-scopes every `t()` call after a later `useTranslations` call, and `bun run check:i18n` fails on keys that do not resolve in their scope. A component that needs two unrelated namespaces uses their common parent or `useTranslations()` with full keys.

`bun run check:i18n` runs three scripts: `check-i18n.ts` (key parity across locales, scoped key resolution and keys that no source file renders), `check-message-formats.ts` (ICU message syntax) and `check-content.ts` (documentation and blog parity across locales).
