## Locales et URL

SaaSy Land sert <RepositoryFact name="languages" /> locales : <RepositoryFact name="supportedLocales" />, avec `en-US` par défaut. La locale par défaut n'a pas de préfixe (`/docs`) ; toutes les autres utilisent leur code complet (`/pl-PL/docs`). Le Worker redirige vers l'URL canonique les préfixes limités à la langue et ceux de la locale par défaut, comme `/pl/docs` ou `/en-US/docs`.

`getCurrentLocale()` est isomorphe et lit la locale dans le chemin de l'URL des deux côtés, avec `en-US` comme repli lorsque le chemin n'a pas de préfixe de locale. Les URL de `/api` et des fonctions serveur n'en ont jamais, donc côté serveur elle renvoie `en-US` pour ces requêtes. Le Worker maintient le cookie de locale synchronisé avec l'URL de la page, mais aucun code ne choisit une locale à partir du cookie. Les fonctions serveur qui renvoient du contenu localisé reçoivent la locale en entrée, et les e-mails d'authentification la lisent dans le `callbackURL` du parcours.

## Messages

Les traductions se trouvent dans `messages/<locale>/<namespace>.json`. Le nom du fichier est le namespace, par exemple `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` ou `common`. Les namespaces à points sont fusionnés en un seul arbre de messages, si bien que `useTranslations("pages.admin.users")` lit `pages.admin.users.json`. Chaque namespace de page contient `metadata.title` et `metadata.description` pour les balises head. Les messages sont du JSON simple, sans types générés.

## Chargement

- **Les namespaces racine** (`common`, `components.*`, `errors*`) sont préchargés dans le `beforeLoad` racine.
- **Les routes de page** déclarent `const NAMESPACE = "pages.x"`, le préchargent dans le loader et l'inscrivent dans `staticData.namespaces`.
- **Les routes de layout** déclarent `const NAMESPACES = [...] as const` et procèdent de la même façon.
- **`TranslationsProvider`** enveloppe le body du document dans le shell racine. Il combine les namespaces racine avec les `staticData.namespaces` des routes correspondantes et transmet le résultat à `IntlProvider`, de sorte que chaque écran, y compris les écrans d'erreur, est traduit.
- **Les e-mails** chargent leur namespace côté serveur avec `loadNamespace`, dans le cas d'usage qui les envoie.

## Liens

Les liens du routeur n'ont pas à gérer la locale : `<Link to={ROUTES.SIGN_IN}>` reçoit le préfixe grâce au `rewrite` du routeur. Une URL brute dans la locale courante, comme un `callbackURL` de Better Auth, vient elle aussi du routeur, qui applique le même rewrite et sérialise les paramètres de recherche (`useAuthRedirect` dans `src/hooks/use-auth-redirect.ts`) :

```ts
const { publicHref: callbackURL } = router.buildLocation({ search: { redirect }, to: ROUTES.AUTH_CALLBACK })
```

`localizePathname({ locale, pathname })` construit une URL pour une locale donnée : les liens du sélecteur de langue et les liens dans les e-mails, que le serveur construit sans routeur.

Le sélecteur de langue affiche un simple lien vers le même chemin dans chaque locale : changer de langue charge donc un nouveau document.

## Traductions dans les composants

Un composant appelle `useTranslations` exactement une fois et nomme le traducteur `t`. i18n-ally réattribue la portée de chaque appel `t()` après un appel ultérieur à `useTranslations`, et `bun run check:i18n` échoue sur les clés qui ne se résolvent pas dans leur portée. Un composant qui a besoin de deux namespaces sans rapport entre eux utilise leur parent commun ou `useTranslations()` avec des clés complètes.

`bun run check:i18n` exécute trois scripts : `check-i18n.ts` (parité des clés entre les locales, résolution des clés dans leur portée et clés qu'aucun fichier source n'affiche), `check-message-formats.ts` (syntaxe des messages ICU) et `check-content.ts` (parité de la documentation et du blog entre les locales).
