`bun run check` esegue `bun run generate:cn`, `bun run check:comments`, `bun run check:i18n` e `bun run check:flows`, e poi `vp check`, che in un unico passaggio formatta con oxfmt, analizza con oxlint e controlla i tipi con TypeScript, con la configurazione in `vite.config.ts` e `tsconfig.json`. La CI esegue lo stesso comando. Niente qui è una questione di gusti: se gli strumenti accettano codice che viola una regola di questa pagina, la revisione lo rifiuta.

## Cosa impongono gli strumenti

oxlint tratta come errori le categorie `correctness`, `nursery`, `pedantic`, `perf`, `style` e `suspicious`, con le regole basate sui tipi e il controllo dei tipi attivati. I limiti che più influenzano il codice:

| Regola                                  | Impostazione                                                                  | Effetto                                                                     |
| --------------------------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `max-lines`                             | <RepositoryFact name="maxLines" />                                            | Dividi un file per responsabilità prima che cresca                          |
| `max-lines-per-function`                | <RepositoryFact name="maxLinesPerFunction" />                                 | Componenti e handler restano piccoli                                        |
| `max-statements`                        | <RepositoryFact name="maxStatements" />                                       | Estrai helper con un nome invece di scrivere corpi lunghi                   |
| `no-magic-numbers`                      | ammessi solo `0` e `1`, oltre agli indici degli array e ai valori predefiniti | Ogni altro numero è una costante con un nome                                |
| `id-length`                             | almeno due caratteri, tranne `_`, `m` e `t`                                   | Gli identificatori sono parole; `t` è il traduttore                         |
| `one-var`                               | `never`                                                                       | Una dichiarazione per istruzione                                            |
| `unicorn/no-null`                       | attiva fuori dai test e da `src/platform/testing`                             | I valori assenti sono `undefined`                                           |
| `typescript/no-explicit-any`            | `error`                                                                       | Nessun valore è tipizzato `any`                                             |
| `typescript/ban-ts-comment`             | `true` per `@ts-expect-error`, `@ts-ignore` e `@ts-nocheck`                   | Nessun errore del compilatore viene soppresso, con o senza un motivo        |
| `typescript/consistent-type-assertions` | `assertionStyle: "never"`                                                     | Nessun cast con `as`; `as const` e `satisfies` restano ammessi              |
| `code-style/no-comments`                | `error`                                                                       | Nessun commento, compresi i commenti di direttiva                           |
| `code-style/no-multiline-ternary`       | `error`                                                                       | Un ternario sta su una riga                                                 |
| `code-style/no-undefined-branch`        | `error`                                                                       | Nessun ternario con un ramo `undefined` o `null`, nessun `return undefined` |
| `code-style/no-undefined-fallback`      | `error`                                                                       | Nessun `?? undefined`                                                       |
| `code-style/zod-namespace-import`       | `error`                                                                       | Zod si importa come `* as zod` da `zod`                                     |
| `radius/no-off-scale`                   | `error`                                                                       | Ogni angolo prende un raggio dalla scala                                    |
| `type/no-off-scale`                     | `error`                                                                       | Ogni dimensione del testo è un gradino della scala tipografica              |
| `type/mono-for-code`                    | `error`                                                                       | Il carattere monospaziato è solo per il codice                              |

Gli override sono mirati e limitati a determinati file: i test e gli helper di test condivisi in `src/platform/testing` rilassano `no-magic-numbers`, `no-await-in-loop`, `unicorn/no-null`, `hydration/no-clock-or-locale-in-render` e `admin-data/no-literal-data`; `src/presentation` e `src/hooks` rilassano `typescript/consistent-return`; i mock dei test rilassano `require-await`; `src/routes` disattiva `sort-keys`, perché le opzioni delle route seguono un proprio ordine (vedi [File di route](/docs/conventions/routes)); e le route, i componenti e i file di dati dell’amministrazione attivano `admin-data/no-literal-data` (vedi [Dashboard di amministrazione](/docs/features/admin-dashboard#real-data-only)). Tutto `src` attiva `radius/no-off-scale`, `type/no-off-scale` e `type/mono-for-code`, che i test e `src/platform/testing` disattivano di nuovo, e `src/presentation/social-card.tsx` disattiva `type/no-off-scale`, perché Takumi esegue il rendering della social card come immagine di dimensioni fisse, con le dimensioni del testo impostate negli stili inline anziché sulla scala tipografica della pagina (vedi [Tema](/docs/ui/theme#type-scale)).

`tsconfig.json` aggiunge i flag rigorosi che cambiano il modo di scrivere il codice: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` e `noUnusedParameters`. Una lettura tramite indice può essere `undefined`, una proprietà opzionale non può essere impostata esplicitamente a `undefined` e una firma di indice si legge come `record["key"]`.

Il formatter scrive senza punti e virgola, con virgolette doppie, virgole finali e una larghezza di <RepositoryFact name="printWidth" /> caratteri. Ordina anche gli import in gruppi fissi, le classi Tailwind in `className` e nelle chiamate a `cn`, e gli script di `package.json` per nome (`sortPackageJson: { sortScripts: true }`), quindi non ordinare mai nessuno di questi a mano: `vp check` fallisce quando uno è fuori ordine. Vedi [Lint e formattazione](/docs/tooling/lint-format) per i comandi.

## Renderizzare ciò che ha renderizzato il server

Una pagina viene renderizzata due volte: sul server e di nuovo nel browser, quando React idrata l’HTML. I due rendering devono stampare lo stesso testo, altrimenti React segnala un errore di idratazione (errore #418) e renderizza di nuovo la pagina. Per questo il codice di rendering non legge mai l’orologio né il locale dell’ambiente di esecuzione, che differiscono tra i due: niente `new Date()` senza argomenti, niente `Date.now` e niente `toLocaleString`, `toLocaleDateString` o `toLocaleTimeString`. Usa un valore che entrambi i lati condividono:

- un tempo relativo si conta dal `dataUpdatedAt` della query che ha letto i suoi dati, come mostra [Internazionalizzazione e lingue](/docs/features/internationalization);
- un anno stampato dal sito viene dalla build: il footer chiude il copyright con `REPOSITORY_FACTS.buildYear`, l’anno UTC in cui il sito è stato costruito;
- numeri e date passano da `useFormatter` di use-intl, nella lingua della pagina e nel fuso orario dell’utente;
- un’attesa nel browser, come il timeout di attivazione di `CheckoutActivation`, è un timer avviato in `useEffect`, così il primo rendering è quello del server.

`hydration/no-clock-or-locale-in-render`, la regola del plugin oxlint proprio del repository in `scripts/hydration-lint-plugin.ts`, lo impone in `src/hooks`, `src/presentation`, `src/providers` e `src/routes/*.tsx`. Lì tutto conta come codice di rendering tranne una funzione che viene eseguita dopo: un gestore di eventi `on…`, come prop JSX, proprietà di un oggetto o variabile; una `queryFn` o una `mutationFn`; e una callback passata a `useEffect`, `useLayoutEffect`, `useCallback`, `setTimeout`, `setInterval`, `requestAnimationFrame` o `addEventListener`. Queste liste nel plugin sono la allowlist: un altro tipo di callback differita si aggiunge lì, con un caso in `src/__test__/hydration-lint-plugin.test.ts`, mai con un commento di disattivazione.

## Niente commenti

Non scrivere commenti: né in TypeScript, TSX, test, script, configurazione o CSS, e nemmeno per spiegare un vincolo non ovvio. Il significato lo porta invece un nome, e il ragionamento va nel messaggio di commit, nella pull request o in questa documentazione.

```ts
const INCLUSIVE_END = 1
const FIRST_SEQUENCE = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

Le prime due vengono da `video.delivery.ts` e `release.ts`, la terza da `src/integrations/polar/polar.vite.ts`: ognuna avrebbe altrimenti bisogno di un commento.

Due controlli impongono la regola, ed entrambi indicano il file, la riga e la correzione:

- `code-style/no-comments`, una regola del plugin oxlint del repository in `scripts/code-style-lint-plugin.ts`, segnala ogni commento nei file che il linter legge, nell'editor e in `vp check`.
- `bun run check:comments` esegue `scripts/check-comments.ts` prima del linter, in `bun run check` e nell'hook di pre-commit. Esegue il parsing di ogni file TypeScript, JavaScript e CSS che Git traccia o aggiungerebbe, con oxc per il codice e PostCSS per gli stili, quindi un `//` in un URL o in un'espressione regolare e un `/*` in un glob CSS non sono commenti. Legge ciò che il linter non può leggere: `e2e`, `remotion`, i file di dichiarazione, i fogli di stile e un commento `/* oxlint-disable */`, a cui il linter obbedisce prima che una qualsiasi regola lo veda.

Le esenzioni sono i file che `.gitattributes` contrassegna come `linguist-generated`, di cui `src/routeTree.gen.ts` e `src/types/worker-configuration.d.ts` sono codice, e la riga `#!` di uno script, che la grammatica di JavaScript non considera un commento. Un tipo di cui il compilatore ha bisogno ovunque va in `types` in `tsconfig.json`, come i globali di Vitest, mai in un commento `/// <reference>`.

## Niente scappatoie

Non scrivere mai `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, un cast con `as` o `any` per far passare una regola. Una regola che scatta indica un problema di design; cambia il design. I controlli li rifiutano tutti: `typescript/ban-ts-comment` le tre direttive del compilatore anche con una descrizione, `typescript/consistent-type-assertions` ogni asserzione tranne `as const`, `typescript/no-explicit-any` l'`any`, e `code-style/no-comments` e `bun run check:comments` ogni commento di disattivazione. Un commento `eslint-disable` non disattiva niente fin dall'inizio (`respectEslintDisableDirectives: false`).

- **Valida invece di asserire.** I dati provenienti dallo storage, dalla rete o da una richiesta vengono analizzati con Zod: `src/lib/github.ts` legge il numero di stelle in cache con `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, che è un numero o `undefined`, mai un'ipotesi.
- **Restringi con un type guard.** `isRole` in `src/integrations/better-auth/auth.roles.ts` e `isErrorCode` in `src/hooks/use-error-message.ts` trasformano una `string` in una union con un controllo reale.
- **Annota, non asserire.** Dai a un valore il tipo di cui ha bisogno dove viene dichiarato: la sidebar di shadcn dichiara `SIDEBAR_MOBILE_STYLE: StyleWithCssVars`, le proprietà CSS più la sua proprietà personalizzata `--sidebar-width`, invece di fare un cast dell'oggetto letterale.
- **Verifica, non convertire.** `as const` e `satisfies` sono ammessi perché non cambiano mai un tipo: `POLAR_ORDER_STATUS` termina con `as const satisfies Record<string, models.OrderStatus>`, quindi uno stato di Polar scritto male non compila.
- **Ristruttura quando il contratto di una libreria ti ostacola.** Avvolgi un valore in un oggetto, dividi una funzione o leggi da una sorgente tipizzata invece di fare un cast.

## Null e undefined

Fuori dai test e da `src/platform/testing`, un valore assente è `undefined` e `null` non viene mai scritto come valore. Il linter lo consente dove lo impone un'API: nel confronto con un valore che può essere `null`, come una colonna nullable (`entry.completedAt !== null` in `course.outline.ts`), e in un ref DOM di React, che parte da `useRef<HTMLElement>(null)` perché React tipizza `ref` come `RefObject<T | null>` e lo riporta a `null` allo smontaggio (`course-showcase.tsx`). Non fare mai da ponte con `?? undefined` verso un'API che restituisce `null`; `code-style/no-undefined-fallback` lo fa fallire. Valida prima l'input, così la chiamata non può fallire, oppure usa un parser che restituisce già `undefined`. I parametri di ricerca sono il caso più comune, e `searchParam(schema)` in `src/lib/search-params.ts` restituisce `undefined` per un valore mancante o malformato:

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Ternari e return anticipati

Un ternario sta su una riga, come `{t(course === undefined ? "create" : "save")}` in `course-form.tsx`. Qualsiasi cosa più lunga, e ogni scelta tra due blocchi di JSX, diventa un return anticipato, una coppia di condizioni `&&` o un piccolo componente; una classe condizionale diventa `cn("base", { "classes": condition })`. `code-style/no-multiline-ternary` fa fallire ogni ternario che occupa più righe, compreso uno che il formatter ha spezzato perché superava la larghezza di riga. `src/routes/auth.reset-password.tsx` rende i suoi due stati con due condizioni:

```tsx
{hasValidToken && <ResetPasswordForm token={token} />}
{!hasValidToken && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

Le funzioni escono subito per i casi speciali e mantengono il percorso principale senza rientro, come fa `hasLessonAccess` in `src/modules/lesson/lesson.access.ts`:

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.entitled
}
```

Nemmeno un ramo scrive per esteso il valore assente: `code-style/no-undefined-branch` fa fallire un ternario con un ramo `undefined` o `null` e ogni `return undefined`. Scrivi invece che cosa fa il codice: esci subito con una guard clause, leggi un valore che può mancare con `?.` o con `??` e un vero valore predefinito, restituisci ciò che trova una tabella di lookup o `find`, mostra il JSX con `&&` e dai all'hook di un plugin Vite un filtro che nomina gli id che gestisce, così Rolldown non lo chiama per nessun altro id. È così che `scripts/repository-facts.ts` serve il suo modulo virtuale:

```ts title="scripts/repository-facts.ts"
    load: { filter: { id: exactRegex(RESOLVED_MODULE_ID) }, handler: () => moduleSource },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_MODULE_ID },
```

## Costanti con un nome

I numeri diversi da `0` e `1` hanno un nome (`COURSE_STALE_MS = 60_000`, `SAVE_INTERVAL_MS = 15_000`). `0` e `1` si scrivono come letterali, come in `.limit(1)`, `index + 1` e `toHaveBeenCalledTimes(1)`, a meno che non abbiano un significato proprio: il codice di uscita di un processo è `FAILURE_EXIT_CODE`, e la fine inclusiva di un intervallo di byte HTTP è `INCLUSIVE_END`. I valori che appartengono al dominio, come stati, tipologie, livelli di accesso, piani, ruoli e valori degli eventi dei provider, vengono dichiarati una sola volta come oggetto `as const` e richiamati per nome ovunque, compresi test e fixture:

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

La tupla di cui ha bisogno una colonna o uno schema enum si costruisce dall'oggetto, senza riscriverla, e sta accanto a esso nelle costanti del modulo, che non importano nulla da Drizzle: `course.constants.ts` dichiara `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, che alimenta sia `text("status", { enum: COURSE_STATUSES })` in `course.schema.ts` sia `zod.enum(COURSE_STATUSES)` in `course.zod.ts`. Anche il codice del browser legge le tuple da lì: la tabella dei prezzi itera `LICENSE_TIERS` da `license.constants.ts`.

- Le costanti di un modulo si trovano nel suo `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`); i valori di un provider si trovano nel `*.constants.ts` dell'integrazione (`POLAR_ORDER_STATUS` in `polar.constants.ts`, `AUTH_PROVIDER` in `auth.constants.ts`).
- Le lunghezze delle colonne e degli input ricevono un nome una sola volta, nelle costanti del modulo, e le leggono sia lo schema Drizzle sia lo schema Zod: `PRODUCT_NAME_MAX_LENGTH` in `product.constants.ts`.
- Un concetto ha una sola mappa con un solo stile di maiuscole: `ERROR_CODES` per gli errori del server, `AUTH_ERRORS` per le chiavi di errore di Better Auth, `ROLE_CODES` per i ruoli.
- I nomi degli ambienti e i codici di stato HTTP si dichiarano una sola volta, in `src/modules/_core/constants/api.ts`: `ENVIRONMENT.PRODUCTION` in `__root.tsx` e negli script di deploy, `HTTP_STATUS.PARTIAL_CONTENT` nel gestore dei media del Worker. Nessun file dichiara una propria mappa per nessuno dei due. L'unica eccezione sono i file dei plugin di Vite come `src/data/cloudflare.vite.ts`, che confrontano `mode` con i nomi semplici: Vite li carica prima di risolvere l'alias `~`, quindi non possono importare `api.ts`.
- Una costante usata da un solo file resta in quel file, sotto gli import. Una costante usata da più file va nel suo modulo, in `src/data` (vedi [File e nomi](/docs/conventions/files-and-naming)) o in `src/modules/_core/constants`. Non dare mai a una costante un file tutto suo.
- I nomi dei campi tipizzati di un'API, come `license_key_id`, sono proprietà, non valori, e restano accessi a proprietà.

## Hook nei componenti

Le chiamate a hook che restituiscono un singolo valore vengono prima, poi una riga vuota, poi ogni risultato di hook destrutturato, così i valori che un componente scompone si leggono come un gruppo a sé. `src/presentation/components/custom/auth/sign-in-form.tsx`:

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Un componente chiama `useTranslations` una sola volta e chiama il risultato `t`; vedi [Traduzioni e contenuti](/docs/conventions/translations) per il motivo.

## Nomi e import

- File e cartelle sono in kebab-case; i componenti sono in PascalCase; le costanti in SCREAMING_SNAKE_CASE; le funzioni iniziano con un verbo (`resolveViewer`, `rethrowAsConflict`); i booleani si leggono come domande (`isPending`, `hasLessonAccess`).
- Gli import usano l'alias `~/src/...` e provengono dal file che definisce il simbolo; l'unica eccezione sono i percorsi, che ogni file importa come un unico namespace, `import * as ROUTES from "~/src/routes"`. Non esistono barrel file che riesportano una cartella. I file di riesportazione sono i punti di raccordo, con una riga `export { … } from` per area, come `src/routes.ts` e i barrel `*.entries.ts` (vedi [Percorsi e navigazione](/docs/conventions/routes#paths-and-navigation)), e `src/integrations/drizzle-orm/drizzle.schemas.ts`, perché Drizzle ha bisogno di tutte le tabelle in un unico oggetto schema.
- Zod si importa in un solo modo, `import * as zod from "zod"` (o `import type * as zod from "zod"` per i soli tipi), la forma mostrata dalla documentazione di Zod 4; `code-style/zod-namespace-import` fa fallire un import predefinito, un import con nome e un sottopercorso come `zod/v4`.
- Far avanzare un indice di uno usa il letterale: `lessons[index + 1]` in `course.utils.ts`. Ogni altro scostamento, `-1` compreso, ha un nome: `groups.at(LAST_GROUP_INDEX)` in `robots.ts`, mai `slice(index, -5)`.
