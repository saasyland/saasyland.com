## Archivos de ruta

Las rutas son archivos planos en `src/routes`. Los puntos se convierten en segmentos de la ruta:

| Archivo                           | URL                | Notas                                                     |
| --------------------------------- | ------------------ | --------------------------------------------------------- |
| `__root.tsx`                      | todas las páginas  | Shell del documento y namespaces raíz                     |
| `_site.tsx`                       | ninguna            | Layout sin segmento de ruta con la cabecera del sitio     |
| `_site._marketing.tsx`            | ninguna            | Layout sin segmento de ruta para las páginas de marketing |
| `_site._marketing.terms.tsx`      | `/terms`           | Página dentro del layout de marketing                     |
| `admin.tsx`                       | `/admin`           | Layout con el guard `requireAdmin`                        |
| `admin.users.all.tsx`             | `/admin/users/all` | Página dentro del layout de administración                |
| `_site._marketing.blog.index.tsx` | `/blog`            | Página índice del layout `blog`                           |
| `_site.docs.$.tsx`                | `/docs/*`          | Ruta comodín para las páginas de documentación            |
| `api/auth.$.ts`                   | `/api/auth/*`      | Handler HTTP, sin componente                              |

Los IDs de `createFileRoute("…")` son literales de cadena que mantiene el generador del router, que también escribe `src/routeTree.gen.ts`. Los archivos de las carpetas `__test__` se ignoran. Cada URL tiene una constante en `ROUTES` (`src/routes.ts`) y los enlaces usan `<Link to={ROUTES.X}>`.

## Rutas de página

Una ruta de página define un componente `<Name>Page`, una constante `NAMESPACE` justo encima de `export const Route` y un loader que carga los metadatos de la página y el namespace en un único `Promise.all`:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Los datos adicionales van en el mismo `Promise.all`, por ejemplo `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` en `admin.users.all.tsx`. `pageHead`, de `src/lib/seo.ts`, construye las etiquetas de título, descripción, URL canónica, `hreflang`, Open Graph e imagen social a partir de los `metadata` del loader; consulta [Búsqueda y vistas previas en redes sociales](/docs/features/seo).

## Rutas de layout

Una ruta de layout define un componente `<Name>Layout`, un array `NAMESPACES` y, en las áreas protegidas, un guard en `beforeLoad`. Sus `NAMESPACES` nombran todos los namespaces que necesitan sus páginas, incluidos los de otras funcionalidades, y un parámetro de búsqueda lo validan las páginas que lo leen, como hacen con `tier` las páginas de licencia `/app` y `/app/license`:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "pages.license", "timezones"] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

Los guards `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn`, `redirectIfVerified` y `redirectAfterAuth` vienen de `src/integrations/better-auth/auth.routes.ts`.

## Esqueletos de carga

La mayoría de las navegaciones terminan antes de que aparezca cualquier interfaz de carga: los enlaces precargan su ruta al pasar el cursor y al tocarlos, y las páginas públicas están prerenderizadas. Cuando una navegación no ha terminado pasado `defaultPendingMs`, <RepositoryFact name="navigationPendingMs" unit="millisecond" />, el router muestra el esqueleto de la ruta y, como `defaultPendingMinMs` es <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, lo quita en cuanto la página está lista. Eso ocurre con una conexión lenta o en la primera petición a un isolate nuevo del Worker (consulta [Rendimiento](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

No hay ningún componente de carga por defecto. Cada ruta de layout y de página define su propio `pendingComponent`. Las páginas de la documentación se dibujan dentro del layout de la documentación: `_site.docs.index.tsx` y `_site.docs.$.tsx` muestran `DocsIndexPending` y `DocsPagePending`, el artículo y su tabla de contenidos junto a la barra lateral, y el layout `docs` muestra `DocsPending` cuando alguien entra en la documentación desde otra parte. Cada esqueleto reproduce la página a la que sustituye:

- **Los esqueletos de página**, como `SignInPending` y `LegalPending`, están en el archivo de esqueletos del área y marcan su elemento raíz con `aria-busy="true"`. Los archivos son `custom/auth/auth-pending.tsx`, los archivos de administración en `custom/admin/` (`admin-pending.tsx` para el layout, un archivo `<area>-pending.tsx` por área, como `products-pending.tsx`, y bloques compartidos en `pending-blocks.tsx`), los archivos de la app de clientes en `custom/app/` (`app-pending.tsx` para el layout, `auth-pending.tsx` y `license-pending.tsx`, y la cabecera de página que comparten en `pending-blocks.tsx`), los archivos del layout público en la raíz de `custom/` (`marketing-pending.tsx` para el layout, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` y `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` y `custom/docs-pending.tsx`.
- **Los esqueletos de layout**, como `AuthPending` y `MarketingPending`, renderizan el marco del layout y, dentro de él, el `pendingComponent` de la primera ruta coincidente por debajo del layout que define uno, que `usePagePending` de `src/hooks/use-page-pending.ts` lee del árbol de rutas. Por eso, al entrar en un área desde otra parte se muestra la página correcta, y un esqueleto de layout un nivel más abajo, como `AdminUsersPending`, hace lo mismo con sus propias páginas. Los elementos del marco que no necesitan datos, como `Wordmark` y `PageFrame`, se renderizan de verdad, y la cabecera del sitio permanece en pantalla, porque el layout `_site` que la renderiza no tiene ningún loader al que esperar.
- **Los marcadores de posición de texto** son barras `Skeleton` con el token tipográfico del elemento real más `h-lh scale-y-70`, de modo que cada barra ocupa exactamente una caja de línea. Las cajas usan las alturas y los radios reales. Las listas toman su longitud de las mismas constantes que la interfaz, como `OAUTH_PROVIDERS` y `AUTH_ASSURANCES` en `src/data/auth.ts`.

Cuando añadas una página, añade su esqueleto al archivo de esqueletos del área y asígnalo como `pendingComponent` de la ruta; los esqueletos de layout lo encuentran ahí.

## Otros aspectos de las rutas

- **Los parámetros de búsqueda** se parsean con `validateSearch` en la propia ruta, por ejemplo el parámetro `tab` de `/app/settings`. El esquema es un `zod.object` construido con las funciones auxiliares de `src/lib/search-params.ts`: `searchText()` y `searchFlag()` devuelven `undefined` para un valor ausente, vacío o mal formado, y `searchChoice(choices, fallback)` devuelve el valor de respaldo. `searchParam(schema)` devuelve `undefined` salvo que el valor cumpla otro esquema de zod, como el token del boletín.
- **Las funciones de servidor de una sola ruta** pueden definirse en el archivo de ruta con `createServerFn`.
- **Contenido generado en el build**: los loaders de la documentación, del blog y de la landing leen los índices de contenido de `virtual:content-indexes`, archivos bajo `/assets/`, así que no necesitan ninguna función de servidor y se ejecutan en el navegador en una navegación en el cliente (consulta [Fumadocs](/docs/integrations/fumadocs#content-indexes)).
- **Los endpoints HTTP** viven en `src/routes/api`. Consulta [Handlers HTTP de TanStack Start](/docs/architecture/api-layer).

## Router

`src/router.tsx` exporta `getRouter`, que crea un `QueryClient` y un router nuevos en cada petición. Configura:

- los componentes por defecto de error y página no encontrada, desde `presentation/components/custom`, y ningún componente de carga por defecto (consulta [Esqueletos de carga](#esqueletos-de-carga))
- la precarga por intención y un tiempo de validez (stale time) por defecto de <RepositoryFact name="routerStaleTimeMinutes" unit="minute" /> tanto para las páginas cargadas como para las precargadas, de modo que una página que `Navigation` precarga para la cabecera en cuanto una página queda inactiva sigue vigente cuando se hace clic en ella (consulta [Rendimiento](/docs/conventions/performance#the-headers-pages-load-before-a-click))
- un `rewrite` que quita el prefijo de locale de las URL entrantes y lo vuelve a añadir a los enlaces generados
- la integración de las consultas con SSR mediante `setupRouterSsrQueryIntegration`

## Después de un despliegue [#after-a-deploy]

Cada despliegue sustituye los assets estáticos del Worker, y Vite nombra cada archivo según su contenido, así que una pestaña abierta antes de un despliegue pide chunks de ruta que ya no existen. TanStack Start pone el componente y el loader de cada ruta en chunks propios. TanStack Router recarga la página cuando no se puede cargar el chunk de un componente (`lazyRouteComponent`), pero router-core carga el chunk de un loader con `lazyFn`, que entrega a la ruta la importación fallida como error de su loader. Un clic en **Blog** en una pestaña así fallaba en el chunk del loader del layout del blog y mostraba la página de error.

`DefaultError`, el componente de error por defecto del router, ahora se recupera de eso. `isStaleBuildError` en `src/lib/stale-build.ts` reconoce un error que indica que la página ejecuta código que un despliegue más reciente eliminó:

- una importación dinámica fallida, que `isModuleNotFoundError` de router-core reconoce en Chromium, Firefox y Safari;
- un archivo que Vite no pudo precargar para un chunk, como su hoja de estilos, que Vite notifica con un evento `vite:preloadError`. La ruta raíz escucha ese evento mientras la aplicación está abierta (`listenForStaleBuilds`).

Ante un error así, `DefaultError` carga como página nueva la dirección a la que navegó el visitante, con `router.navigate({ href, reloadDocument: true, replace: true })`, de modo que el visitante llega a la página en la que hizo clic, servida ya por el nuevo despliegue; hasta que el navegador sale de la página, muestra un `main` vacío y marcado como ocupado en lugar del mensaje de error. `claimReload` permite una sola recarga así por destino y build. Guarda el destino en `sessionStorage` junto con la URL del script de entrada de la página, que cambia con cada despliegue que modifica un archivo que carga el navegador, porque a cada chunk se llega desde la entrada por su nombre basado en el contenido. Un segundo fallo para el mismo destino en el mismo build muestra la página de error, así que un archivo que falta de verdad no puede hacer que la página se recargue sin fin, y el siguiente despliegue tiene su propia recarga. Si el navegador rechaza el almacenamiento de sesión, no se recarga nada.

Safari cancela los archivos que una página aún está cargando en cuanto el visitante empieza a salir de ella, así que un chunk o una hoja de estilos que venía de camino falla como si un despliegue lo hubiera eliminado. Por eso `listenForStaleBuilds` también anota cuándo la página recibe `beforeunload`, y `DefaultError` espera con `whenPageStays` a que un `pageshow`, `pointerdown` o `keydown` muestre que el visitante se quedó antes de volver a cargar la página. Un visitante que se va llega a la página que pidió en lugar de volver a la que dejaba, y quien vuelve a la página o se queda en ella recibe entonces la recarga. `stale-build.spec.ts` retiene el código de la ruta de una lección, sale hacia la política de privacidad, cancela el código y comprueba que se abre la política de privacidad y que la lección no se vuelve a pedir.

Una precarga fallida no consume nada. Al pasar el puntero sobre un enlace, el router precarga su ruta, como hace la cabecera con sus propios enlaces en cuanto una página queda inactiva; si eso falla, no se muestra ningún componente de error, y el router vuelve a pedir el chunk cuando el visitante hace clic. `e2e/specs/stale-build.spec.ts` activa el ahorro de datos, para que la cabecera no cargue antes el blog, quita los chunks del blog a una página abierta y comprueba que un clic, también tras una precarga fallida al pasar el puntero, llega al blog tras una recarga, y que una página cuyos chunks siguen faltando muestra la página de error tras dos recargas, una de `DefaultError` y otra de `lazyRouteComponent`.
