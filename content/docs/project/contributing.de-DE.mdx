---
title: "Mitwirken"
description: "Wie du Änderungen an SaaSy Land vorschlägst."
---

1. Besprich größere Änderungen zuerst in einem Issue, das du über das Formular für Fehlerberichte oder Feature-Wünsche eröffnest.
2. Erstelle einen Branch von `main`.
3. Halte dich an die [Konventionen](/docs/conventions) und die [Architektur](/docs/architecture), und lies den passenden [Agent-Skill](/docs/tooling/agent-skills), bevor du eine Anbieter-Integration änderst. Coding-Agenten beginnen mit `AGENTS.md` im Stammverzeichnis des Repositorys.
4. Lege Tests neben ihren Besitzer und halte die Testabdeckung bei <RepositoryFact name="coverageThreshold" unit="percent" />.
5. Führe die folgenden Prüfungen aus.
6. Committe mit einer Nachricht im Format der [Conventional Commits](/docs/tooling/conventional-commits), öffne einen Pull-Request mit einem konventionellen Titel und fülle dessen Vorlage aus.
7. Rebase den Branch auf `main`, wenn er mit `main` in Konflikt steht, und merge `main` nie hinein, wie [Git und Pull-Requests](/docs/conventions/git-workflow#linear-history) beschreibt. Ein Maintainer stellt den grünen Pull-Request in die [Merge-Queue](/docs/conventions/git-workflow#merging), die ihn noch einmal auf `main` testet und mergt.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bunx playwright test e2e/specs/<spec>.spec.ts --project=chromium
```

`build:test` führt den vollständigen Cloudflare-Build aus, den `check` und die Unit-Tests nicht abdecken. Der letzte Befehl baut und startet den Test-Worker, wenn kein Server läuft, und führt die Specs, die du angibst, in Chromium aus: Führe die aus, die abdecken, was du geändert hast. Die CI führt jede Spec in Chromium und in WebKit im Pull-Request und noch einmal in der Merge-Queue aus, und der Pull-Request wird nur gemergt, wenn beide Browser grün sind; `bun run test:e2e:pr` führt die gesamte Suite lokal in Chromium aus. Führe sie auch in WebKit aus (`bun run test:e2e`), wenn sich eine Änderung dort anders verhalten könnte. Prüfe echte Anbieter-Integrationen separat, wenn du deren Konfiguration änderst.

Wenn sich Verhalten ändert, aktualisiere `content/docs` in jeder Sprache; `bun run check:content` weist fehlende Übersetzungen, abweichende Codeblöcke und abweichende Navigation zurück. Die Pull-Request-Vorlage enthält eine Zusammenfassung, einen Testplan mit den obigen Prüfungen und eine Liste der aktualisierten Dokumentation; beschreibe darin das resultierende Verhalten, wie du es geprüft hast und welche Abläufe die Änderung unfertig zurücklässt. Eine Admin-Ansicht wird nur mit einer echten Quelle für ihre Daten ausgeliefert (siehe [Admin-Dashboard](/docs/features/admin-dashboard#real-data-only)).

`CONTRIBUTING.md` im Stammverzeichnis des Repositorys ist die Kurzfassung dieser Seite, und `SUPPORT.md` nennt die Wege zu Hilfe. Alle Beteiligten halten sich an `CODE_OF_CONDUCT.md`, den Contributor Covenant 2.1. Melde Sicherheitslücken vertraulich, wie in `SECURITY.md` beschrieben, und niemals in einem öffentlichen Issue.
