L'historique de `main` fait partie du produit : chaque pull request fusionnée par squash y forme une ligne qui dit ce qui a changé pour les personnes qui utilisent le code.

## Commits

Les messages de commit suivent Conventional Commits et s'écrivent sans émoji ; le hook `prepare-commit-msg` ajoute l'émoji du type (voir [Commits conventionnels](/docs/tooling/conventional-commits) pour le tableau) :

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- Le sujet est en minuscules, à l'impératif, et dit ce que la modification apporte à ses utilisateurs : `feat(course): reorder the catalogue from the course list`, et non `update course files`.
- La portée est le module ou la zone : `course`, `auth`, `a11y`, `deps`, `readme`.
- Le type est l'un de `feat` ✨, `fix` 🐛, `docs` 📚, `refactor` 📦, `chore` ♻️, `test` 🚨, `perf` 🚀, `build` 🛠️, `ci` ⚙️, `style` 💎 et `revert` 🗑️ ; le hook rejette tout autre type. Ne tapez jamais l'émoji vous-même : le hook ne vérifie pas un sujet qui commence déjà par un émoji.
- Découpez une pull request en commits logiques : la fonctionnalité, sa documentation sous la forme `docs(<scope>)`, et les corrections trouvées en chemin.
- Ne committez jamais avec `--no-verify`. Le hook `pre-commit` exécute `bun run check:pre-commit` ; lorsqu'il échoue, corrigez la cause.
- Formatez et lintez uniquement les fichiers que vous avez modifiés, avec `bunx vp fmt <files>` et `bunx vp lint --fix <files>`. N'exécutez pas `bun run check:fix` ni `vp check --fix` sur tout le dépôt : ils réécrivent des fichiers que vous n'avez pas touchés, y compris les réglages partagés de l'éditeur dans `.vscode/settings.json`. Si `.vscode/` apparaît dans `git status`, restaurez-le depuis `HEAD`.

## Aucune attribution à une IA

Les commits et les descriptions de pull request ne portent aucun trailer `Co-Authored-By` pour un outil d'IA, aucune ligne « Generated with » ni aucune autre attribution à une IA, même lorsqu'un outil en ajoute une par défaut. GitHub associe l'adresse d'un tel trailer à un compte sans rapport, qui apparaît alors comme contributeur du dépôt. Le hook `commit-msg` rejette un message de commit qui en porte un et nomme la ligne à retirer (voir [Commits conventionnels](/docs/tooling/conventional-commits)). Il en va de même pour les correctifs proposés en amont (voir [Dépendances](/docs/conventions/dependencies)).

## Branches et worktrees

- Créez une branche à partir de `main`, une branche par pull request.
- Donnez à chaque branche son propre worktree Git au lieu de changer la branche d'un checkout, pour qu'un checkout ouvert par un éditeur ou un autre processus ne soit jamais modifié à son insu :

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- Avant de vous fier à une exécution des tests, vérifiez `git branch --show-current` dans le répertoire que vous avez testé.

### Les hooks dans chaque worktree [#hooks-in-every-worktree]

Git lit `core.hooksPath` dans la configuration que partagent tous les worktrees d'un dépôt, et Vite+ lui donne le chemin relatif `.vite-hooks/_` : Git exécute donc le répartiteur de hooks du worktree dans lequel vous committez. Le répartiteur est généré et n'est jamais committé, si bien que chaque worktree a besoin du sien, et là où il manque, Git saute les hooks sans prévenir. Deux étapes l'installent :

- `git worktree add` exécute le hook `post-checkout` du checkout depuis lequel vous lancez la commande, et `.vite-hooks/post-checkout` installe le répartiteur du nouveau worktree avec `vp hooks enable`. Un commit fait avant `bun install` échoue alors dans le hook `pre-commit` au lieu de le sauter.
- `bun install` exécute `prepare`, qui renouvelle le répartiteur avec `vp config --no-agent` puis exécute `scripts/verify-git-hooks.ts`. L'installation échoue quand `core.hooksPath` ne vaut pas `.vite-hooks/_` ou quand il manque au répartiteur un hook de `.vite-hooks/`, et l'erreur affiche la commande qui le répare.

Ne donnez jamais une autre valeur à `core.hooksPath` et ne passez jamais `-c core.hooksPath` à Git. Tant que ce réglage contenait le chemin absolu du répartiteur du checkout principal, `vp config` n'a installé aucun répartiteur dans les autres worktrees, et quand le `bun install` suivant dans le checkout principal a rétabli le chemin relatif, les commits de ces worktrees se sont faits sans hooks. `vp hooks status` indique si les hooks sont actifs dans un worktree.

## Historique linéaire [#linear-history]

Le ruleset qui protège `main` sur GitHub exige un historique linéaire, n'accepte les pull requests que par la file de fusion, qui squashe chacune d'elles, et refuse les force-push : chaque pull request arrive donc sur `main` en un seul commit. Les branches des pull requests restent elles aussi linéaires :

- Ne créez jamais de commit de merge, ni sur `main` ni sur une branche de pull request : ne fusionnez pas `main` dans une branche et ne résolvez pas de conflits dans un commit de merge.
- Mettez une branche à jour en la rebasant sur `main`, avec `gh pr update-branch --rebase` ou avec `git fetch origin` et `git rebase origin/main`, quand elle entre en conflit avec `main`. Une pull request sans conflit n'a besoin d'aucun rebase pour être fusionnée : la file de fusion la teste au-dessus de la dernière version de `main`.
- Quand GitHub ne peut pas rebaser une pull request de plusieurs commits, intégrez-la de nouveau en un seul commit au-dessus de `main` : regroupez la branche en un commit sur sa base de merge, puis rebasez ce commit, pour ne résoudre chaque conflit qu'une fois :

```sh
git fetch origin
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -m "feat(course): reorder the catalogue from the course list"
git rebase origin/main
git push --force-with-lease
```

- Poussez une branche réécrite avec `git push --force-with-lease`, et seulement votre propre branche de pull request. Ne faites jamais de force-push sur `main` ou sur la branche de quelqu'un d'autre, et n'utilisez jamais un simple `--force`, qui écrase les commits poussés depuis votre dernier fetch.

## Pull requests

- **Petites et ciblées.** Une correction, une fonctionnalité ou un refactoring par pull request. Une grosse fonctionnalité devient une pile de pull requests, chacune pouvant être relue séparément, comme l'ont été les vidéos, les cours et l'administration des cours.
- **Le titre est le commit de squash.** Utilisez le format des commits, sans l'émoji ; il devient le sujet sur `main`, que GitHub termine par `(#<number>)`. `scripts/enqueue-pr.ts` ajoute l'émoji qu'ajouterait le hook de commit quand il place la pull request dans la file de fusion.
- **La description** comporte une section `## Summary` sur ce qui a changé et pourquoi, une section `## Test plan` avec les commandes exécutées et leurs résultats, et une liste `## Docs` des pages, des sections du README et des textes que vous avez mis à jour. Rédigez-la simplement, sans langage marketing.
- **Aucune revue automatique.** Le ruleset de `main` contient la règle `copilot_code_review` avec `review_on_push: true`, mais au 22 novembre 2026, GitHub Copilot n'a relu aucune pull request depuis #70 : les pull requests ne reçoivent donc aucune revue automatique. Même une revue ne serait que consultative : elle n'approuverait rien et ne bloquerait rien, car le ruleset n'exige aucune approbation.
- **Chaque pull request met à jour ce qu'elle rend inexact :** le README, les pages de documentation dans toutes les langues et tout texte du site ou toute affirmation de la page d'accueil qu'elle touche, et elle ajoute son [entrée au journal des modifications](#changelog-entries). Une inexactitude repérée dans du code que vous n'avez pas modifié fait l'objet de sa propre pull request. Le README ne peut pas afficher de valeurs issues du code, c'est donc `src/__test__/readme.test.ts` qui le lit : chaque version, port, nombre et seuil qu'il indique doit être égal à la valeur que contiennent le code ou `REPOSITORY_FACTS`, tout autre nombre échoue sauf s'il s'agit d'une date ou de l'un des faits externes que le test énumère, chaque commande `bun run` doit nommer un script de `package.json`, et chaque fichier, route et règle de lint qu'il nomme doit exister.

## Fusion [#merging]

Une pull request n'arrive sur `main` que par la file de fusion de GitHub. Une fois ses vérifications au vert et son entrée du journal des modifications ajoutée, placez-la dans la file avec son numéro :

```sh
bun scripts/enqueue-pr.ts 280
```

Le script échoue sur un titre qui ne suit pas le format des commits, remplace le titre par le sujet qu'écrirait le hook de commit, émoji compris, et lance `gh pr merge --auto --squash`, qui ajoute la pull request à la file dès que ses vérifications réussissent. La file teste chaque pull request au-dessus de `main` et des pull requests qui la précèdent, avec les vérifications que la pull request a exécutées, en construit plusieurs à la fois et intègre un groupe de pull requests d'un seul coup une fois que chacune d'elles a réussi : personne n'a donc à rebaser une pull request prête pour la fusionner. Une pull request qui échoue dans la file en sort ; corrigez-la et remettez-la dans la file. Ne fusionnez jamais une pull request à la main ni en contournant la file : c'est l'exécution de la file qui a testé le commit qui arrive sur `main`, et `deploy.yml` relance toutes les vérifications pour un commit qui ne l'a pas suivie.

## Entrées du journal des modifications [#changelog-entries]

Chaque pull request ajoute sa propre entrée au [journal des modifications](/docs/project/changelog), si bien que des pull requests ouvertes en parallèle ne modifient jamais le même fichier.

- **Nommez-la d'après la pull request.** Ouvrez la pull request, puis ajoutez `content/changelog/<number>.<locale>.mdx` dans chaque langue : une liste à puces, sans frontmatter, de ce qui change pour les personnes qui utilisent le code, avec des liens vers les pages de documentation concernées.
- **N'écrivez jamais de date ni le numéro de la pull request.** La page du journal tire le jour de chaque entrée, et les notes de version sa version, de l'historique Git : le jour, en UTC, du commit squash dont GitHub termine l'objet par `(#<number>)`. Tant que la pull request n'est pas fusionnée, son entrée figure sous **Non publié**. Elles tirent le numéro du nom du fichier : la page termine chaque puce d'une entrée par un lien vers sa pull request, ou vers son commit pour une entrée nommée d'après un commit, et les notes de version terminent chaque puce par `(#<number>)`, dont GitHub fait un lien. Une fois déployée, la page relie aussi chaque entrée à la [version](/docs/tooling/ci-cd#releases-and-tags) qui l'a livrée en premier.
- **La CI le vérifie.** Dans une pull request, `bun run check` échoue tant que `content/changelog/<number>.en-US.mdx` manque, et `check:content` compare chaque traduction à ce fichier comme pour une page de documentation. Un fichier nommé ni d'après un numéro de pull request ni d'après un hash de commit complet échoue aussi : les rares changements arrivés sur `main` sans pull request portent le nom de leur commit.
- **Seule votre propre entrée peut rester non publiée.** En CI, la construction du site échoue tant que le journal afficherait sous **Non publié** une entrée qui n'a rien à y faire : dans une pull request vers `main`, toute entrée autre que celle de la pull request elle-même, et dans la file de fusion et sur `main`, toute entrée. Une branche de la file de fusion contient déjà le commit squash de chaque pull request de son groupe, si bien que chacune de leurs entrées a son jour. Une construction locale, qui n'a pas de `GITHUB_REF`, affiche toutes les entrées non fusionnées. Cela repère une entrée qui survit à sa pull request : `content/changelog/219.<locale>.mdx` est resté en place quand #219 a été fermée sans fusion, répétait l'entrée de #220 et figurait sous **Non publié** en production jusqu'à ce que #254 le supprime.

## Vérifications

La CI exécute `bun run check` et `bun run test:coverage`, construit le Worker de test et exécute la suite de tests du navigateur dans Chromium et dans WebKit, et envoie le Worker de préversion sur Cloudflare sous forme d'une version qui ne reçoit aucun trafic. Cet envoi est la vérification que Cloudflare accepte le Worker : ses limites d'envoi ont déjà fait échouer un déploiement qui avait passé toutes les autres vérifications. La file de fusion exécute de nouveau les mêmes vérifications sur la pull request réunie avec `main` et les pull requests qui la précèdent. Voir [CI/CD](/docs/tooling/ci-cd).
