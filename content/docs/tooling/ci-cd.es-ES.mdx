Los flujos de trabajo se encuentran en `.github/workflows/`. Los flujos de trabajo de la aplicación (`ci.yml`, `e2e-reusable.yml` y `deploy-reusable.yml`) configuran la cadena de herramientas con la acción compuesta `.github/actions/setup`: Bun 1.4.4, Vite+ con la versión de Node de `.nvmrc`, una caché de Bun, `bun install --frozen-lockfile --ignore-scripts` y `bun run typegen`. `remotion.yml`, en cambio, configura Node desde `.nvmrc` y npm.

| Flujo de trabajo      | Disparador                                                      | Jobs                                                                                                                  |
| --------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`              | Pull requests y pushes a `main`                                 | Comprobaciones y cobertura, E2E en Chromium y después despliegue a preview, o a producción con publicación de versión |
| `e2e-full.yml`        | Pushes a `main`, semanalmente los lunes a las 03:15 UTC, manual | WebKit en cada push; Chromium y WebKit en las ejecuciones programadas y manuales                                      |
| `e2e-reusable.yml`    | Invocado por los flujos de trabajo anteriores                   | Base de datos de pruebas, compilación de pruebas y un proyecto de Playwright                                          |
| `deploy-reusable.yml` | Invocado por `ci.yml`                                           | Compilación, migraciones de D1 y `wrangler deploy`                                                                    |
| `remotion.yml`        | Cambios en `remotion/` o en sus constantes compartidas          | Comprueba y empaqueta con npm el proyecto de vídeo de la página de inicio                                             |

## Comprobaciones

El job `verify` de `ci.yml` ejecuta `bun run check` (tablas de nombres de clase, comprobaciones de i18n y de contenido, formato, lint y tipos) y `bun run test:coverage`, y después sube el informe de cobertura. El job `e2e` ejecuta `db:reset:test` y `build:test`, instala el navegador y ejecuta `bunx playwright test e2e/specs --project=chromium`. Las ejecuciones E2E fallidas suben el informe de Playwright.

## Despliegues

Los despliegues solo se ejecutan después de que `verify` y `e2e` se superen:

| Evento                                          | Destino      | Entorno de GitHub | URL                           |
| ----------------------------------------------- | ------------ | ----------------- | ----------------------------- |
| Pull request desde una rama de este repositorio | `preview`    | `Preview`         | https://preview.saasyland.com |
| Push a `main`                                   | `production` | `Production`      | https://saasyland.com         |

Las pull requests desde forks y de Dependabot se validan, pero no se despliegan. La preview es compartida: cada despliegue sustituye al anterior y usa la misma base de datos D1, el mismo espacio de nombres de KV y el mismo bucket de R2 de preview.

`deploy-reusable.yml` comprueba que existan los secretos `CLOUDFLARE_API_TOKEN` y `CLOUDFLARE_ACCOUNT_ID`, ejecuta `scripts/verify-bindings.ts`, compila con los valores ficticios de `.env.test`, elimina el `dist/server/.dev.vars` generado, aplica `db:migrate:<target>` y ejecuta `vp exec wrangler deploy --config dist/server/wrangler.json`. No ejecuta `scripts/verify-deployment.ts`, la comprobación del sitio desplegado de los scripts `deploy:<target>`, porque la protección contra bots de Cloudflare responde con 403 a las peticiones de los runners de CI. Tampoco ejecuta `polar:verify:<target>`, porque los entornos de GitHub no guardan ningún token de Polar; ejecútelo en local después de cada cambio en Polar ([Configuración de Polar](/docs/getting-started/polar-setup)). No se sube ningún archivo de secretos: el Worker conserva los secretos de ejecución ya configurados en Cloudflare. Los despliegues al mismo destino se ponen en cola en lugar de cancelarse entre sí.

Dependabot actualiza las GitHub Actions semanalmente.

## Versiones y etiquetas [#releases-and-tags]

El sitio se despliega de forma continua, así que sus versiones son fechas, no versiones semánticas. Cuando un despliegue a producción termina con éxito, el job `release` de `ci.yml` etiqueta el commit desplegado como `vYYYY.MM.DD` con la fecha UTC y publica una GitHub Release para él. Un segundo despliegue a producción el mismo día recibe la etiqueta `vYYYY.MM.DD.2`, el siguiente `.3`, y así sucesivamente. Los despliegues a preview nunca se etiquetan. El job `release` es el único con `contents: write`.

Las notas de la versión son la sección de ese día del [registro de cambios](/docs/project/changelog), de modo que cada cambio se describe en un solo lugar; si el registro de cambios no tiene sección para ese día, las notas enlazan a él. `scripts/publish-release.ts` elige la etiqueta y las notas con `src/lib/release.ts` y ejecuta `gh release create`. Una nueva ejecución conserva la etiqueta que ya tiene el commit y omite la GitHub Release si ya existe.

Para devolver producción a una versión, revierta en una pull request todo lo posterior a su etiqueta:

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

Al fusionarla, el código etiquetado se despliega tras las comprobaciones habituales y se etiqueta como una nueva versión. Las migraciones de D1 no se revierten, así que el código anterior se ejecuta sobre el esquema más reciente. Cada cambio de esquema debe funcionar con la aplicación desplegada antes que él, lo que hace que esto sea seguro para la versión anterior; lea las migraciones intermedias antes de retroceder más.
