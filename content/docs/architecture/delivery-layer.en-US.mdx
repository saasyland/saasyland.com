## Route files

Routes are flat files in `src/routes`. Dots become path segments:

| File                              | URL                | Notes                                |
| --------------------------------- | ------------------ | ------------------------------------ |
| `__root.tsx`                      | all pages          | Document shell and root namespaces   |
| `_site.tsx`                       | none               | Pathless layout with the site header |
| `_site._marketing.tsx`            | none               | Pathless layout for marketing pages  |
| `_site._marketing.terms.tsx`      | `/terms`           | Page inside the marketing layout     |
| `admin.tsx`                       | `/admin`           | Layout with the `requireAdmin` guard |
| `admin.users.all.tsx`             | `/admin/users/all` | Page inside the admin layout         |
| `_site._marketing.blog.index.tsx` | `/blog`            | Index page of the `blog` layout      |
| `_site.docs.$.tsx`                | `/docs/*`          | Splat route for documentation pages  |
| `api/auth.$.ts`                   | `/api/auth/*`      | HTTP handler, no component           |

The `createFileRoute("…")` IDs are string literals maintained by the router generator, which also writes `src/routeTree.gen.ts`. Files in `__test__` folders are ignored. Every URL has a constant in `ROUTES` (`src/routes.ts`), and links use `<Link to={ROUTES.X}>`.

## Page routes

A page route defines a `<Name>Page` component, a `NAMESPACE` constant directly above `export const Route`, and a loader that loads the page metadata and namespace in one `Promise.all`:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Extra data goes into the same `Promise.all`, for example `context.queryClient.query({ ...getUsersQuery, staleTime: "static" })` in `admin.users.all.tsx`. `pageHead` from `src/lib/seo.ts` builds the title, description, canonical, `hreflang`, Open Graph and social image tags from the loader's `metadata`; see [Search and social previews](/docs/features/seo).

## Layout routes

A layout route defines a `<Name>Layout` component, a `NAMESPACES` array and, for protected areas, a guard in `beforeLoad`. Its `NAMESPACES` end with the namespaces other areas add to it, and a search parameter is validated by the pages that read it, as the licence pages `/app` and `/app/license` do with `tier`:

```tsx
const NAMESPACES = ["auth.errors", "pages.app.sidebar", "timezones", ...layoutNamespaces("/app")] as const

export const Route = createFileRoute("/app")({
  beforeLoad: requireSignedIn,
  component: AppLayout,
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AppPending,
  staticData: { namespaces: NAMESPACES },
})
```

The guards `requireSignedIn`, `requireAdmin`, `redirectIfSignedIn` and `redirectAfterAuth` come from `src/integrations/better-auth/auth.routes.ts`.

## Loading skeletons

Most navigations finish before any pending UI appears: links preload their route on hover and touch, and public pages are prerendered. When a navigation has not finished after `defaultPendingMs`, <RepositoryFact name="navigationPendingMs" unit="millisecond" />, the router shows the route's skeleton, and since `defaultPendingMinMs` is <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, it removes the skeleton the moment the page is ready. That happens on a slow connection or on the first request to a new Worker isolate (see [Performance](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once)).

There is no default pending component. Every layout and page route sets its own `pendingComponent`. The docs pages are drawn inside the docs layout: `_site.docs.index.tsx` and `_site.docs.$.tsx` show `DocsIndexPending` and `DocsPagePending`, the article and its table of contents beside the sidebar, and the `docs` layout shows `DocsPending` when someone enters the docs from elsewhere. Every skeleton mirrors the page it stands in for:

- **Page skeletons** such as `SignInPending` and `LegalPending` live in the area's pending file and mark their root with `aria-busy="true"`. The files are `custom/auth/auth-pending.tsx`, the admin files in `custom/admin/` (`admin-pending.tsx` for the layout, one `<area>-pending.tsx` per area, such as `products-pending.tsx`, and shared blocks in `pending-blocks.tsx`), the customer app files in `custom/app/` (`app-pending.tsx` for the layout, `auth-pending.tsx` and `license-pending.tsx`, and the page header they share in `pending-blocks.tsx`), the public layout files at the top of `custom/` (`marketing-pending.tsx` for the layout, `core-pending.tsx`, `legal-pending.tsx`, `license-pending.tsx` and `newsletter-pending.tsx`), `custom/blog/blog-pending.tsx`, `custom/courses/courses-pending.tsx` and `custom/docs-pending.tsx`.
- **Layout skeletons** such as `AuthPending` and `MarketingPending` render the layout's chrome and choose the page skeleton for the current path from a map keyed by `ROUTES`. The admin, customer app and public layouts share one map, `PAGE_SKELETONS` in `src/data/skeletons.ts`, which joins the lists each area declares in `src/data/<area>.skeletons.ts`. Entering an area from elsewhere therefore shows the right page. Chrome that needs no data, such as `Wordmark` and `PageFrame`, renders for real, and the site header stays on screen, because the `_site` layout that renders it has no loader to wait for.
- **Text placeholders** are `Skeleton` bars with the real element's type token plus `h-lh scale-y-70`, so each bar fills exactly one line box. Boxes use the real heights and radii. Lists take their length from the same constants as the UI, such as `OAUTH_PROVIDERS` and `PASSWORD_RULES` in `src/data/auth.ts`.

When you add a page, add its skeleton to the area's pending file, register it in the layout skeleton's map (for an admin, customer app or public page, in its area's `src/data/<area>.skeletons.ts`) and set it as the route's `pendingComponent`.

## Other route concerns

- **Search params** are parsed by `validateSearch` in the route, for example the `tab` parameter of `/admin/products` or the `view` parameter of `/admin/blog`. The schema is a `zod.object` built from the helpers in `src/lib/search-params.ts`: `searchText()` and `searchFlag()` give `undefined` for a missing, empty or malformed value, and `searchChoice(choices, fallback)` gives the fallback. `searchParam(schema)` gives `undefined` unless the value matches any other zod schema, such as the newsletter token.
- **Single-route server functions** may be defined in the route file with `createServerFn`, as `getBlogPosts` is in `_site._marketing.blog.index.tsx`.
- **HTTP endpoints** live in `src/routes/api`. See [TanStack Start HTTP handlers](/docs/architecture/api-layer).

## Router

`src/router.tsx` exports `getRouter`, which creates a new `QueryClient` and router for every request. It sets:

- default error and not-found components from `presentation/components/custom`, and no default pending component (see [Loading skeletons](#loading-skeletons))
- preloading on intent and a default stale time of <RepositoryFact name="routerStaleTimeMinutes" unit="minute" />
- a `rewrite` that removes the locale prefix from incoming URLs and adds it back to generated links
- SSR query integration through `setupRouterSsrQueryIntegration`
