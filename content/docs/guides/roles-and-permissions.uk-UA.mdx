Контроль доступу використовує плагін admin Better Auth. `src/integrations/better-auth/auth.access.ts` оголошує декларації дозволів кожного ресурсу в `APP_STATEMENTS`, надає їх ролям і будує з них контроль доступу Better Auth та перевірку дозволів — в одному файлі, який переглядає людина. Коди ролей розміщені в `src/integrations/better-auth/auth.roles.ts`.

## Дозволи та ролі

```ts title="src/integrations/better-auth/auth.access.ts"
export const APP_STATEMENTS = {
  admin: ["access"],
  category: ["create", "read", "update", "delete"],
  course: ["create", "read", "update", "delete"],
  order: ["read", "update", "refund"],
  product: ["create", "read", "update", "delete", "publish"],
  settings: ["manage"],
  video: ["read", "delete"],
} as const

export const ac = createAccessControl({ ...defaultStatements, ...APP_STATEMENTS })

export const ROLES = {
  [ROLE_CODES.ADMIN]: ac.newRole({ ...APP_STATEMENTS, ...adminAc.statements }),
  [ROLE_CODES.CUSTOMER]: ac.newRole({}),
}
```

- `APP_STATEMENTS` перелічує по одній декларації на ресурс, відсортовані за ресурсом: `admin` і `settings` для адмінпанелі та її налаштувань, `category` і `product` для продуктів, `course` і `video` для курсів, а `order` — для замовлень.
- `defaultStatements` з Better Auth додають ресурси `user` і `session` (наприклад, `user: ["list", "set-role", "ban", "impersonate", "delete"]` і `session: ["list", "revoke"]`).
- Роль `admin` отримує всі декларації та адміністративні декларації Better Auth; ролі `customer`, типовій для нових користувачів, не надано жодної.
- Можливість, яку проєкт пропускає, забирає свої декларації з собою: `scripts/features.ts` їх називає, як-от `APP_STATEMENTS.course`, а правило очищення видаляє їх з об’єкта ([Тестування](/docs/conventions/testing#tests-follow-the-features)).
- `ROLE_VALUES` типізує колонку `user.role` і схеми ролей у `user.zod.ts`.
- `Permission`, тип, який приймають `authorized` і `hasPermission`, будується з `APP_STATEMENTS`, тож декларація чи дія, якої там не оголошено, не компілюється.

## Де перевіряються дозволи

| Шар                       | Перевірка                                                          |
| ------------------------- | ------------------------------------------------------------------ |
| Guard маршруту            | `requireAdmin` вимагає `admin: ["access"]` для всієї зони `/admin` |
| Серверна функція          | `authorized({ product: ["update"] })` у кожній захищеній операції  |
| Лише для тих, хто увійшов | `authorized()` для операцій із власними даними того, хто викликає  |
| Будь-де ще                | `hasPermission({ permission, role })` повертає булеве значення     |

Guard маршруту лише визначає, які сторінки рендеряться. Серверні функції можна викликати напряму через RPC, тож кожна має сама перевіряти свій дозвіл. Приховати кнопку — це питання представлення, а не авторизації.

## Додайте дозвіл

1. Додайте дію до декларації ресурсу в `APP_STATEMENTS` або додайте ресурс на його місце в порядку сортування, наприклад `report: ["read", "export"]`. Можливість, яку можна пропустити, називає новий ресурс у своїх `names` у `scripts/features.ts`, як-от `APP_STATEMENTS.report`.
2. Надайте її в `ROLES`: `admin` отримує весь `APP_STATEMENTS`, а ролі, яка має отримати менше, надають лише частину декларацій.
3. Вимагайте її в серверній функції: `.middleware([authorized({ report: ["export"] })])`.
4. Протестуйте і дозволений випадок, і випадок `FORBIDDEN` — у `src/integrations/better-auth/__test__/auth.access.<feature>.test.ts` та в тестах сценарію використання.

## Додайте роль

1. Додайте код до `ROLE_CODES` і `ROLE_VALUES` в `auth.roles.ts`.
2. Додайте її до `ROLES` в `auth.access.ts` разом із деклараціями, якими вона може користуватися.
3. Додайте мітку ролі до `filters.role.options` у `messages/<locale>/pages.admin.users.json` для кожної мови.

Клієнт автентифікації (`auth.client.ts`) отримує `ac` і `ROLES`, тож адміністративні дії в браузері використовують ті самі визначення.

## Керування користувачами та сесіями

Модулі користувачів і сесій обгортають адміністративний API Better Auth у сценарії використання, кожен із власним дозволом: `setUserRole`, `banUser`, `unbanUser`, `impersonateUser`, `deleteUser`, `setUserPassword`, `revokeUserSession` та інші. Операції з власними даними того, хто викликає, наприклад `revokeSession`, використовують `authorized()` і фільтрують за `context.auth.user.id`.

Локально `bun run db:seed:local` створює адміністратора. На preview і в продакшні першого адміністратора створює `bun run admin:grant:preview <email>` або `bun run admin:grant:production <email>` для облікового запису з підтвердженою поштою, і запустити їх може лише той, хто має право запису в цю базу D1; наступних адміністраторів призначають у **Адміністрація → Керування користувачами** дією **Змінити роль**. Див. [Перший адміністратор](/docs/tooling/database#the-first-admin). Наявний адміністратор також може запросити нову адресу з роллю `admin`; див. [Запрошення](/docs/features/users-admin#invitations).
