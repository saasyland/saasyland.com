Повідомлення використовують `use-intl` із синтаксисом ICU. Кожен простір імен — це один JSON-файл на мову в `messages/<locale>/<namespace>.json` для дев'яти мов: `en-US` (типова), `de-DE`, `es-ES`, `fr-FR`, `it-IT`, `ja-JP`, `pl-PL`, `pt-BR` і `uk-UA`. Назва файлу і є простором імен: `messages/en-US/pages.admin.users.json` — це `pages.admin.users`.

## Типи просторів імен

| Простір імен                                  | Хто завантажує                                                    |
| --------------------------------------------- | ----------------------------------------------------------------- |
| `common`, `components.*`, `errors*`           | `beforeLoad` кореневого маршруту, на кожній сторінці              |
| `pages.*`                                     | Маршрут сторінки, який його оголошує                              |
| Простори layout, наприклад `auth.validations` | Маршрут layout (`src/routes/auth.tsx`, `admin.tsx`, `app.tsx`, …) |
| `emails.*`                                    | Сценарій використання, що надсилає лист, лише на сервері          |

`TranslationsProvider` обгортає тіло документа й поєднує кореневі простори імен із просторами всіх відповідних маршрутів, тож кожен екран, зокрема екрани помилок, перекладено.

## Додайте ключ

Додайте ключ до того самого файлу для всіх дев'яти мов з однаковою структурою. `bun run check:i18n` завершується помилкою, якщо в якійсь мові бракує ключа або є зайвий.

## Додайте простір імен сторінки

1. Створіть `messages/<locale>/pages.<area>.<page>.json` для всіх дев'яти мов. Кожен простір імен сторінки має `metadata.title` і `metadata.description`; `loadPageMetadata` читає їх для заголовка документа.
2. Оголосіть і завантажте його в маршруті:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_landing/terms")({
  component: TermsPage,
  head: pageHead(ROUTES.TERMS),
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  pendingComponent: LegalPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

Маршрути layout оголошують `const NAMESPACES = [...] as const`, заздалегідь завантажують їх у loader і перелічують у `staticData`. Оголошений простір імен без файлу кидає помилку `No messages/<locale>/<namespace>.json`.

## Використовуйте повідомлення в компонентах

- Викликайте `useTranslations` рівно один раз на компонент і називайте перекладач `t`. i18n-ally і `check:i18n` розв'язують кожен `t("key")` відносно найближчої попередньої області `useTranslations`.
- Якщо компоненту потрібні ключі з двох непов'язаних просторів імен, обмежте `t` їхнім спільним батьківським простором або викличте `useTranslations()` і використовуйте повні ключі, як це робить `sign-in-form.tsx`.
- Компоненти самі читають свої повідомлення; батьківські компоненти ніколи не передають мітки через props.
- Форматований текст використовує `t.rich("key", TAGS)` з мапою тегів, оголошеною як константа на рівні модуля, наприклад `LEGAL_TAGS` у `src/routes/auth.sign-up.tsx`.
- `getCurrentLocale()` повертає мову і на сервері, і в браузері. `useDateFormatter` і `useCurrencyFormatter` форматують дати й суми для цієї мови.

## Перевірте

```sh
bun run check:i18n
```

Команда перевіряє відповідність ключів між мовами, статичні ключі щодо їхньої області `useTranslations`, формати повідомлень ICU та відповідність вмісту документації між мовами. Її також запускає `bun run check`.

## Мови в URL

Англійські сторінки не мають префікса (`/docs`), інші мови його мають (`/pl-PL/docs`). Worker перенаправляє короткі префікси, як-от `/pl`, на `/pl-PL` і синхронізує мовне cookie з URL сторінки. URL серверних функцій і `/api` не містять мови, тож серверні функції, що повертають локалізований вміст, отримують мову як вхідні дані.
