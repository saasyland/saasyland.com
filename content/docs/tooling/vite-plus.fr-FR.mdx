Vite+ (`vite-plus`, commande `vp`) regroupe Vite, Vitest, oxlint et oxfmt derrière une seule CLI, et `vite.config.ts` les configure tous. `package.json` remplace `vite` par `@voidzero-dev/vite-plus-core` et fixe `vitest` à la version 5.1.0. `vite-plus` est lui aussi épinglé à une version exacte ; mettez les trois à jour ensemble avec `vp migrate`, et non avec `bun update`. Les scripts du paquet appellent `vp` ; en dehors de ceux-ci, utilisez la CLI Vite+ globale ou `bunx vp`.

| Commande          | Utilisée par                                      |
| ----------------- | ------------------------------------------------- |
| `vp dev`          | `dev`                                             |
| `vp build --mode` | `build:preview`, `build:production`, `build:test` |
| `vp preview`      | `start`, `start:test`                             |
| `vp test`         | `test` et les scripts Vitest `test:*`             |
| `vp lint`         | `lint`                                            |
| `vp fmt`          | `format`, `format:check`                          |
| `vp check`        | `check`, `check:fix`                              |
| `vp staged`       | `check:pre-commit`                                |
| `vp config`       | `prepare`, qui installe les hooks Git             |

## Configuration

`vite.config.ts` liste ses plugins dans `VITE_PLUGINS` et les charge à la demande, chaque entrée important son paquet dans `load` ; les plugins d'un fournisseur viennent de `src/integrations/<vendor>/<vendor>.vite.ts` (voir [Ce que le Worker et le build exécutent](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)). Sous Vitest, seules les entrées marquées `vitest` sont chargées, c'est-à-dire `contentIndexes()`, `repositoryFacts()` et `@vitejs/plugin-react` ; sinon, la pile est la suivante :

- `@cloudflare/vite-plugin` : exécute le Worker dans l'environnement SSR, conserve l'état local (dans `.wrangler/test` pour le mode `test`, dans `.wrangler/state` sinon), avec `remoteBindings: false` : ni le serveur de développement ni le build d'aucun environnement ne se connecte à un binding distant.
- `fumadocs-mdx` : compile les collections de la documentation et du blog.
- `saasyland:fumadocs-bundled` : garde `fumadocs-core` et `@fumadocs/base-ui` dans le bundle serveur (`resolve.noExternal`). Il et `fumadocs-mdx` viennent de `fumadocsVitePlugins` (`src/integrations/fumadocs/fumadocs.vite.ts`).
- `contentIndexes` (`scripts/content-indexes.ts`) : sert `virtual:content-indexes` et `virtual:docs-search`, les index de la documentation, du blog et de la recherche que `fumadocs.indexes.ts` construit à partir de `content/docs` et `content/blog` ; voir [Fumadocs](/docs/integrations/fumadocs#content-indexes).
- `repositoryFacts` (`scripts/repository-facts.ts`) : sert le module `virtual:repository-facts`, les nombres, les versions et les réglages d'outils que la page d'accueil et la documentation affichent, et le module `virtual:repository-tables`, les tableaux que seule la documentation affiche, tous deux lus dans le dépôt au moment du build ; voir [Traductions et contenu](/docs/conventions/translations) et [Performances](/docs/conventions/performance#repository-tables-load-with-the-docs).
- `unused-primitives` (`scripts/unused-primitives.ts`) : avant Tailwind, écarte les classes de chaque primitive shadcn qu'aucune source de l'application n'importe ; voir [Composants shadcn](/docs/ui/shadcn-components).
- `@tailwindcss/vite` : Tailwind CSS 4.
- `tanstackStart` : routage, découpage du code et prérendu des pages publiques, filtré par `shouldPrerender` (`src/lib/prerender.ts`).
- `@vitejs/plugin-react`.
- `saasyland:zod-config-chunk` (`src/integrations/zod/zod.vite.ts`) : dans le build client, place `src/integrations/zod/zod.config.ts` dans le chunk propre à zod, pour que zod s'exécute en mode `jitless` avant qu'un chunk ne construise un schéma et ne teste jamais la disponibilité d'`eval` sous la Content Security Policy ; voir [Sécurité et durcissement](/docs/features/security).
- `deployedWorker` (`scripts/deployed-worker.ts`) : recompile le Worker après le prérendu sans les pages compilées de la documentation et du blog ni les traductions de la landing page et des pages légales ; voir [Cloudflare Workers](/docs/integrations/cloudflare-workers).
- `saasyland:polar-sdk-optional-peers` : marque comme externes les dépendances pairs optionnelles de `@polar-sh/sdk` qui ne sont pas installées (`build.rolldownOptions.external`) ; voir [Dépendances](/docs/conventions/dependencies).

Le serveur de développement écoute sur `localhost:3000` et échoue si le port est occupé. `resolve.tsconfigPaths` fournit l'alias d'import `~/`. Le même fichier contient les sections `fmt`, `lint`, `staged` et `test` ; voir [Lint et formatage](/docs/tooling/lint-format) et [Tests](/docs/tooling/testing).

`vp preview`, que lancent `start`, `start:test` et le prérendu, écoute sur `127.0.0.1:3000`, l'adresse `LOCAL_SERVER` de `src/data/local-server.ts`, et Playwright ouvre cette adresse ; le prérendu utilise la même adresse avec un port libre. Avec `localhost`, le serveur n'écouterait que sur la première adresse que Node obtient pour ce nom, `::1`, et chaque client essaierait `::1` puis `127.0.0.1` en laissant peu de temps à chacune pour répondre : sur une machine chargée, ce délai expire avant que le client voie la connexion, il abandonne `::1`, ne trouve rien sur `127.0.0.1` et le prérendu s'arrête sur `ETIMEDOUT ::1` et `ECONNREFUSED 127.0.0.1`.

`polarVitePlugins`, dans `src/integrations/polar/polar.vite.ts`, renvoie un plugin dont le hook `config` liste dans `build.rolldownOptions.external` les dépendances peer optionnelles de `@polar-sh/sdk` (OpenTelemetry et `ioredis`). Elles ne sont pas installées, et le module qui les importe est éliminé du Worker par tree-shaking.

## Hooks Git

`bun install` exécute `prepare`, qui appelle `vp config --no-agent` pour installer le répartiteur de hooks de `.vite-hooks/`, puis `scripts/verify-git-hooks.ts`, qui fait échouer l'installation quand Git n'exécuterait pas ce répartiteur. `pre-commit` exécute `bun run check:pre-commit`, `prepare-commit-msg` exécute `scripts/commit-msg.ts` et `commit-msg` exécute `scripts/verify-commit-msg.ts` (voir [Commits conventionnels](/docs/tooling/conventional-commits)), et `post-checkout` exécute `vp hooks enable` dans un checkout qui n'a pas encore de répartiteur, comme un worktree que `git worktree add` vient de créer. `post-merge`, `post-checkout` et `post-rewrite` exécutent `bun install --frozen-lockfile` lorsque `bun.lock` a changé : un pull, un rebase ou un changement de branche ne laisse donc jamais `node_modules` obsolète. `vp hooks status` indique si les hooks sont actifs dans un clone, et [Git et pull requests](/docs/conventions/git-workflow#hooks-in-every-worktree) explique pourquoi chaque worktree a besoin de son propre répartiteur.

Privilégiez les scripts du paquet ; appelez `vp` directement pour des exécutions ciblées, comme le formatage ou le lint de chemins précis.
