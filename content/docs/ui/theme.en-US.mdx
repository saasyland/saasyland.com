## Theme selection

`THEME` in `src/presentation/theme/index.ts` defines the themes `light`, `dark` and `system` (the default) and the cookie `saasyland.com_theme`. The app uses `@wrksz/themes`:

- `ThemeScript` in the `head` of the root document (`src/routes/__root.tsx`) reads the cookie and sets the theme class before the first paint, so there is no flash.
- `ThemeProvider` (`src/providers/theme-provider.tsx`) starts from the cookie (`getStoredTheme`), stores changes in the cookie and keeps every `ThemeProvider` in the same document in sync (`enableSameDocumentSync`). It does not sync other tabs.
- `ThemeProvider` wraps only the widgets that read or change the theme: the root `Toaster` and the `ThemeSwitch` in the docs sidebar. It never wraps a route `Outlet`, because a provider that updates after hydration would re-render the whole page.

```tsx
const RootComponent = () => (
  <AriaProvider>
    <OfflineBanner />
    <AffiliateReferral />
    <Outlet />
    <ThemeProvider>
      <Toaster />
    </ThemeProvider>
  </AriaProvider>
)
```

`/admin`, `/app` and `/docs` follow the stored theme; the only theme switch is in the docs sidebar. The `_site` layout adds the `dark` class to its wrapper while a matched route sets `dark: true` in its `staticData`, as the `_marketing` layout of the landing, legal, blog and course pages does, and the auth layout adds it to its own wrapper; these pages always render dark. `globals.css` also gives `html` the dark tokens while one of these wrappers is a direct child of `body` (`:root:has(> body > .dark)`), so the window around the page, behind the scrollbar included, is dark in the light theme too.

## Tokens

`src/presentation/styles/globals.css` defines the shadcn tokens as OKLCH variables in `:root` (light) and `.dark`: `background`, `foreground`, `card`, `popover`, `primary`, `secondary`, `muted`, `accent`, `destructive`, `border`, `input`, `ring`, `chart-1` to `chart-5`, the `sidebar-*` set and `radius`. The brand accent is `ring`: it colours focus rings, active states and highlights, and matches `chart-1`. `dark:` utilities follow the class:

```css
@custom-variant dark (&:is(.dark *));
```

`@theme inline` maps the variables to Tailwind colours, sets the font families and defines the type scale. `globals.css` also imports the Fumadocs UI styles, so the docs use the same tokens.

`@theme` adds the layout tokens: `--spacing-header`, the height of the site header (`h-header`); `--container-site`, the width of the public pages (`max-w-site`); and `--container-docs-sidebar` and `--container-docs-toc`, the widths of the docs sidebar and table of contents (`w-docs-sidebar`, `w-docs-toc`). `Navigation`, `MobileMenu`, `Footer`, `PageFrame`, the landing page sections, `ContentPage`, blog posts, the course pages and the docs layout all use `max-w-site` and, from `md` up, the same side padding, so the header keeps its width and place from page to page, also while a client navigation swaps the page, and the content lines up under it. Fumadocs' `--fd-layout-width`, the width its docs grow to at most, is set to the same token, and two rules at the end of `globals.css` set Fumadocs' `--fd-sidebar-width` to the sidebar token from `md` up and `--fd-toc-width` to the table of contents token from `xl` up; the docs loading skeleton uses the same tokens.

## Scrollbars

The window keeps room for its scrollbar on every page, so the content stays in place when a page is too short to scroll, when it grows and when a dialog, popover or menu stops the page from scrolling. `globals.css` sets `scrollbar-gutter: stable` on `html`, next to the thin page scrollbar: browsers style the window's scrollbar from the `scrollbar-color` and `scrollbar-width` of `html`, never of `body`.

```css
html {
  scroll-behavior: smooth;
  scroll-padding-top: var(--spacing-header);
  scrollbar-color: color-mix(in oklab, var(--foreground) 20%, transparent) transparent;
  scrollbar-gutter: stable;
  scrollbar-width: thin;
}
html:has([data-page-scroller]) {
  scrollbar-gutter: auto;
}
[data-page-scroller] {
  scrollbar-gutter: stable;
}
```

`/app` and `/admin` fill the window and scroll their content area instead, so that element carries `data-page-scroller`, in the layouts and in their loading skeletons alike: the room moves there, and the workspace takes the full width of the window. React Aria's `usePreventScroll` and Base UI, which runs the docs search, also keep the page still with `scrollbar-gutter: stable` rather than with padding, so nothing makes up for the room twice. Fixed layers such as the header, the page frame and the back-to-top button are placed in the window without that room and line up with the content, and the scrollbar's track is transparent, so the room shows the page's own background.

## Type scale

Use the named text utilities instead of raw sizes: `text-display-hero`, `text-display-gate`, `text-display-blast`, `text-headline-peak`, `text-headline-support`, `text-price`, `text-title-lg`, `text-title`, `text-statement`, `text-lead`, `text-body`, `text-body-sm`, `text-spec`, `text-label` and `text-code`. Each sets size, line height, letter spacing and, for headings, weight. `src/lib/cn.config.ts` registers them so `cn` keeps them when merging classes; `bun run generate:cn` rebuilds the lookup tables.

The small end of the scale has a floor: nothing a reader must read is set smaller than `text-label`.

| Class          | Size                                                        | Use                                                                                                    |
| -------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `text-body-sm` | <RepositoryFact name="textBodySmallPixels" /> px            | Secondary copy, menu, sidebar and list items, help under a field                                       |
| `text-spec`    | <RepositoryFact name="textSpecPixels" /> px                 | Metadata: dates, counts, durations, billing periods, table cells, tooltips, captions and notes         |
| `text-label`   | <RepositoryFact name="textLabelPixels" /> px, medium weight | Short labels: uppercase eyebrows and section labels, table headers, badges, keys and menu group titles |
| `text-code`    | A step below the text around it                             | Inline code inside a sentence                                                                          |

- Geist sets the text. Geist Mono is kept for code, commands, keys and identifiers, such as a command, a slug, an ID, a file name or a locale code. Labels, dates, counts and prices are set in Geist, with `tabular-nums` where figures line up in a column or change in place.
- Muted text uses `text-muted-foreground` at full strength, which passes WCAG AA (4.5:1) on every surface in both themes. Only decorative marks hidden with `aria-hidden`, such as a prompt's `$` or a separator, are lighter.
- Text keeps the platform's font smoothing, which on macOS keeps small light text on a dark surface full-bodied. Page titles, the display, headline and price sizes and article headings keep grayscale antialiasing (`-webkit-font-smoothing: antialiased`) for crisper edges; the rule is in the base layer of `globals.css`.
- `text-xs` stays defined only because Fumadocs' own components use it, at the size of `text-spec`.

The lint rules in `scripts/type-lint-plugin.ts` fail `bun run check` when code under `src/` sets type off the scale. `type/no-off-scale` rejects `text-xs`, an arbitrary size such as `text-[11px]`, a `[font-size:…]` property and `fontSize` in a style object; the social card, which Takumi draws from inline styles, is exempt. `type/mono-for-code` rejects `font-mono` in the same class string as `uppercase`, `tabular-nums` or `text-label`, which mark a label or a figure rather than code. `src/presentation/styles/__test__/type-scale.test.ts` holds the small sizes, keeps every token at or above the floor and checks the smoothing rule.

## Corner radius

Every corner takes its radius from one scale. `--radius` in `:root` is the base, and `@theme static` in `globals.css` derives the three steps from it, so changing that one value rescales the whole site. Each kind of element has one step:

| Class          | Radius                                      | Use                                                                                                                                                           |
| -------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rounded-lg`   | <RepositoryFact name="radiusLgPixels" /> px | Surfaces: cards, panels, dialogs, sheets, popovers, menus, toasts, callouts, tables, code blocks, video and image frames, and the course and pricing cards    |
| `rounded-md`   | <RepositoryFact name="radiusMdPixels" /> px | Controls: buttons, calls to action, inputs, selects, tab lists, toggles, badges, chips, tooltips, icon tiles, menu rows of the sidebars and one-line commands |
| `rounded-sm`   | <RepositoryFact name="radiusSmPixels" /> px | Elements inside a padded surface or control: menu, select and command items, tab triggers, `kbd`, inline code, checkboxes, and the focus ring of a text link  |
| `rounded-full` | Circle or pill                              | Avatars, status and marker dots, switches, sliders, radio buttons, progress bars, step numbers, play buttons and round icon badges                            |
| `rounded-none` | 0                                           | An element that must stay square inside a rounded parent, such as the field of an input group                                                                 |

An element inside a padded, rounded container never has a larger radius than the container: the items of a menu are `rounded-sm` inside its `rounded-lg` panel, and a button in a card is `rounded-md`. `rounded-[inherit]`, which repeats the parent's radius exactly, is the one arbitrary value allowed.

`globals.css` clears Tailwind's own radius steps with `--radius-*: initial`, so `rounded-xs`, `rounded-3xl`, `rounded-4xl` and a bare `rounded` produce no CSS. `rounded-xl` and `rounded-2xl` stay defined only because Fumadocs' components use them, and they resolve to `--radius-lg`, so the docs search dialog, cards, callouts, tabs and code blocks match the rest of the site. Fumadocs rounds its own controls with `rounded-lg`, so the docs sidebar in `_site.docs.tsx` gives its rows and search button `rounded-md` and its `kbd` keys `rounded-sm`, `docs-search-dialog.tsx` gives the search results `rounded-sm`, and `globals.css` gives the inline code of Fumadocs' prose `--radius-sm`. The prose styles in `typeset.css` read the same variables: inline code, `kbd` and highlighted text take `--radius-sm`, code blocks, images and videos `--radius-lg`. The emails use React Email's Tailwind, whose default `rounded-sm`, `rounded-md` and `rounded-lg` have the same values.

The lint rule `radius/no-off-scale` in `scripts/radius-lint-plugin.ts` fails `bun run check` when code under `src/` uses any other radius: a retired step, a bare `rounded` or a side without a step such as `rounded-l`, an arbitrary value such as `rounded-[4px]` or `rounded-(--cell-radius)`, a `border-radius` property in brackets, a component's radius variable set to anything but `var(--radius)`, `var(--radius-sm)`, `var(--radius-md)` or `var(--radius-lg)`, or `borderRadius` in a style object. `src/presentation/styles/__test__/radius.test.ts` holds the scale in `globals.css` and checks that every `border-radius` in the stylesheets reads it.

## Badges

A status, an access level or a kind of course is the shadcn `Badge` (`src/presentation/components/shadcn/badge.tsx`), and every badge has the same shape: `h-5.5`, `px-2.5`, `text-label`, `tracking-normal`, `rounded-md` and a hairline border. `[text-box:trim-both_cap_alphabetic]` trims the label's line to its capitals and `content-center` centres them in the box, so the capitals sit in the middle whatever the font's ascent and descent. Each of the four tones is a light fill with a border of the same hue, so badges differ only in colour, never in kind:

| Variant       | Use                                                                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `neutral`     | The default, for a plain fact: an access level that needs an account or Complete, a role, a locale, a product type, the last sign-in method         |
| `accent`      | What is open or live: **Free preview**, a course's kind, a published course or lesson, a paid order, an active user or licence, the current session |
| `warning`     | What waits on someone: a pending order or licence, a user who has not confirmed the address, a lesson being recorded                                |
| `destructive` | What was withdrawn: a refunded order, a banned user, an archived product, a revoked licence                                                         |

Screens pass a `variant` and no classes that change the badge's size, padding, radius or colour. The tone of each value lives next to the values: `LESSON_ACCESS_BADGES`, `COURSE_STATUS_BADGES` and `LESSON_STATUS_BADGES` in `src/data/course-badges.ts`, `USER_STATUS_BADGES` in `src/data/admin.ts`, and `ORDER_STATUS_BADGES` and `SUBSCRIPTION_STATUS_BADGES` in `src/data/billing.ts`. Under a lesson title, `LessonMeta` (`lesson-meta.tsx`) sets the badge, then the length or the hourglass and **Coming soon**, on one centre line, `mt-2` below the title in the curriculum and in the landing page's course block. On a course card's cover the kind and level sit on a frosted tray (`bg-background/85` with `backdrop-blur-sm`), so their tones read as they do on the page.

Three small shapes are not badges: the blog's active filters are buttons that remove a filter, so they are `rounded-full` chips with a close icon; the number on the blog's **Filters** button is a round counter; and **Recommended** names the featured tier in its card's header strip, like the other section labels. `e2e/fixtures/badge-layout.ts` measures the badges: `e2e/specs/course-pages.spec.ts` and `e2e/specs/landing.spec.ts` check at phone, tablet and desktop widths, and on the course page zoomed in, that each label's capitals are centred in the box, that the badge, the length and the hourglass share one centre line, and that every lesson's meta row sits the same gap below its title.

## Page titles and calls to action

The content pages, which are the blog index, the course catalogue, the newsletter pages, the legal pages and the not-found page, open with `ContentPage` (`src/presentation/components/custom/content-page.tsx`): the `h1` in `text-headline-peak` and the lead in `text-lead`, at the same distance below the site header on every page, and `ContentPagePending` draws the same block in their skeletons. Blog posts keep the larger `text-display-gate` for the article title. Calls to action on the public pages use `CTA_CLASSES.PRIMARY` or `CTA_CLASSES.SECONDARY` from `src/data/cta.ts`, so every one has the same height (`h-11`), padding and type; `BackHomeLink` is the primary one back to `/`, labelled from `common.backHome`, on the not-found page and the newsletter pages.

## Route stylesheets

`docs.css` holds the `typeset` prose styles for docs and blog articles. It is plain CSS, loaded by the `/docs` and `/blog` layouts as a `?url` stylesheet link. Route stylesheets must not run a second Tailwind build.
