ワークフローは `.github/workflows/` にあります。アプリケーションのワークフロー（`ci.yml`、`deploy.yml`、`preview.yml`、`journey.yml`、`updates.yml`、`e2e-reusable.yml`、`deploy-reusable.yml`）は、コンポジットアクション `.github/actions/setup` でツールチェーンをセットアップします。内容は Bun <RepositoryFact name="bunVersion" />、`.nvmrc` の Node バージョンと、`setup-vp` が 1 回だけ復元する Bun のインストールキャッシュを使う Vite+、`bun install --frozen-lockfile --ignore-scripts`、`bun run typegen` です。`remotion.yml` は代わりに `.nvmrc` の Node と npm をセットアップします。

| ワークフロー          | トリガー                                                                                    | ジョブ                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ci.yml`              | プルリクエスト、マージキューのグループ、および `deploy.yml` からの呼び出し                  | チェック、並列シャードでのカバレッジ付きテスト、オプションのエリアを 1 つずつ外した型チェック、Chromium と WebKit の E2E、プレビュー用 Worker のアップロード |
| `deploy.yml`          | `main` へのプッシュ                                                                         | マージキューが実行していなければ `ci.yml` のチェック、その後プレビュー、本番、リリース                                                                       |
| `preview.yml`         | 手動実行                                                                                    | チェックが成功したブランチを共有プレビューにデプロイ                                                                                                         |
| `e2e-full.yml`        | `main` へのプッシュ、UTC のスケジュール <RepositoryFact name="e2eFullSchedule" />、手動実行 | プッシュ時は WebKit（プルリクエストと同じ）、スケジュール実行と手動実行では Chromium と WebKit                                                               |
| `journey.yml`         | UTC のスケジュール <RepositoryFact name="journeySchedule" />、手動実行                      | 共有プレビューに対する Polar サンドボックスでの[ジャーニースイート](#journey-suite)                                                                          |
| `updates.yml`         | UTC のスケジュール <RepositoryFact name="updatesSchedule" />、手動実行                      | [更新の Issue](#updates) を作成、更新、またはクローズ                                                                                                        |
| `e2e-reusable.yml`    | 上記のワークフローから呼び出し                                                              | 1 回のテスト用ビルド、並列のシャードで実行する 1 つの Playwright プロジェクト、その両方をまとめる 1 つのチェック                                             |
| `deploy-reusable.yml` | `ci.yml`、`deploy.yml`、`preview.yml` から呼び出し                                          | ビルド、その後 D1 マイグレーションと `wrangler deploy`、または `wrangler versions upload`                                                                    |
| `remotion.yml`        | `remotion/` またはそれがインポートするサイトのファイルの変更                                | ランディングページの動画プロジェクトを npm でチェックしてバンドル                                                                                            |

`remotion.yml` は、プルリクエストでもプッシュでも同じパスで実行されます。対象は `remotion/`、ワークフロー自体、そして `remotion/src` が直接または他のサイトのファイルを通じてインポートするサイトのファイルです。`src/__test__/workflows.test.ts` はそのインポートをたどり、たどり着いたファイルがどのパスにも一致しない場合や、どのファイルにも一致しないパスがある場合に失敗します。

ビルドが変更履歴を生成し、`content.spec.ts` がそれを読み込む `e2e-reusable.yml` のチェックアウト、サイトをビルドする `deploy-reusable.yml` のチェックアウト、そして `release` ジョブのチェックアウトは、すべてのコミットをツリーなしで取得します（`fetch-depth: 0` と `filter: tree:0`）。[変更履歴](/docs/project/changelog)が、各エントリの日付をそれを `main` に入れたコミットから決めるためです。シャロークローンと比べて増えるのはコミットそのものだけです。シャロークローンでは、エントリの日付を誤る代わりにビルドが失敗します。これらのチェックアウトが履歴を取得しなくなると、`src/__test__/workflows.test.ts` が失敗します。

`actions/*` を含め、ほかのリポジトリのアクションはすべてリリースのコミット SHA 全体に固定し、その後ろのコメントにリリースタグを書きます: `uses: <owner>/<repo>@<commit> # <tag>`。そのため、タグが後で動かされても、ワークフローはそのリリースのコードをそのまま実行します。`.github/workflows/` または `.github/actions/` の `uses:` がコミットではなくタグやブランチを指している場合、コミットの後ろにリリースタグがない場合、または 1 つのリポジトリの 2 つのリリースを固定している場合、`src/__test__/workflows.test.ts` は失敗します。`bun run deps:update` は各アクションを最新リリースに移し、コミットとタグを一緒に書き換えます（[依存関係](/docs/conventions/dependencies#upgrading)）。そのため、アクションはパッケージと同じブランチで更新されます。

## チェック [#checks]

`verify` ジョブが報告する必須チェック `Format, lint, types, i18n, tests` は、`ci.yml` の `check`、`test`、`features` の各ジョブで構成されます。

| ジョブ                                                | 実行内容                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                                               | `bun run check`：クラス名テーブル、i18n とコンテンツのチェック、[フロー一覧](/docs/tooling/test-coverage#flow-coverage)、[エージェントスキル](/docs/tooling/agent-skills#drift-checks)、フォーマット、リント、型チェック                                                                        |
| `test`                                                | シャードごとに 1 ジョブ、<RepositoryFact name="vitestShards" /> 個を並列に実行：Vitest の blob レポーター付きで `bun run test:coverage --shard=<n>/<total>` を実行し、そのシャードのカバレッジを含む blob レポートをアップロード                                                                |
| `verify`（名前は `Format, lint, types, i18n, tests`） | すべてのシャードが成功すると blob レポートをダウンロードし、カバレッジを統合してしきい値を適用する `bun run test:coverage --merge-reports` を実行してから、カバレッジレポートをアップロード。`check`、すべてのシャード、統合、`features` ジョブのすべてのシナリオのいずれかが成功しなければ失敗 |

各シャードは自分のテストが到達するコードしか計測しないため、しきい値をチェックしません。`vite.config.ts` のしきい値は、ローカルの `bun run test:coverage` と同じく、全シャードを統合したカバレッジに 1 回だけ適用されます。これらのジョブのうちブランチのルールが要求するチェックは `verify` ジョブだけなので、シャードやシナリオを増減しても必須チェックの名前は変わりません。

`features` ジョブは `scripts/features.ts` の各シナリオについて `bun run check:features <scenario>` を並列に 1 回ずつ実行します。シナリオの機能を削除し、残るファイルがそれを指している箇所を刈り込み、刈り込んだファイルを整形してから、残りの型と翻訳をチェックします（[テスト](/docs/conventions/testing#tests-follow-the-features)）。刈り込めない参照、型エラー、翻訳エラーのどれかが残るシナリオはジョブを失敗させ、必須チェック `Format, lint, types, i18n, tests` も失敗させます。

`e2e` ジョブは `browser: chromium`、`e2e-webkit` ジョブは `browser: webkit` で `e2e-reusable.yml` を呼び出します。どちらの呼び出しも 1 回だけビルドし、<RepositoryFact name="e2eShards" /> 台のランナーでスイートをそのブラウザーで並列に実行します。

| ジョブ                                         | 実行内容                                                                                                                                                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`                                        | `db:reset:test` と `build:test` を実行し、`dist`、Worker 設定を指す `.wrangler/deploy`、シード済みの `.wrangler/test` を 1 つのアーティファクトとしてアップロード                                                   |
| `shard`                                        | シャードごとに 1 つのジョブ。ビルドと並行して開始し、ブラウザーをインストールしてビルドのアップロードを待ち、それをダウンロードして `bunx playwright test e2e/specs --project=<browser> --shard=<n>/<total>` を実行 |
| `report`（名前は `Build and E2E (<browser>)`） | ビルドとすべてのシャードが成功しない限り失敗。失敗したシャードがあれば、各シャードの blob レポートを 1 つの HTML レポートにマージしてアップロード                                                                   |

シャードは `build` ジョブ全体の完了（`needs`）を待たず、`build` と同時に開始して、ビルド中にツールチェーンとブラウザーを準備します。その後 `scripts/download-artifact.ts` が数秒ごとに GitHub の API で同じ実行の `build` ジョブを問い合わせ、そのステップ `Upload the test build` が成功するまで待ちます。ステップが成功しても GitHub がその成果物をまだ一覧に出しているとは限らず、その間にダウンロードすると `Artifact not found` で失敗します。そのためスクリプトは続けて実行の成果物を問い合わせ、ビルド開始以降にアップロードされた `test-worker-<browser>` が一覧に現れるまで待ち、その成果物を自らダウンロードして、GitHub が記録した SHA-256 ダイジェストと照合します。一覧に出た成果物でも少しの間 `Not Found` を返すことがあるため、スクリプトは GitHub がアーカイブ全体を返すまで問い合わせを繰り返し、その間にほかのステップが成果物を求めることはありません。スクリプトは前回の応答の ETag を送り、GitHub は変化のない応答をトークンのレート制限に数えません。ビルドのステップが失敗するか、ビルドがアップロードせずに終わると、失敗したステップとビルドへのリンクを示して、すべてのシャードが数秒で失敗します。スクリプトの上限を超えて待ったシャードも、ステップ、一覧、ダウンロードのどれが欠けているかを伝えるエラーで失敗します。実行のジョブと成果物を読むには `actions: read` が必要で、これを求めるのは `shard` ジョブだけです。`ci.yml`、`e2e-full.yml`、`deploy.yml` の `checks` ジョブが呼び出すワークフローにこれを許可し、ほかのジョブはすべて `contents: read` のままです。

Playwright 自体のリトライとワーカーは、どのシャードでも [Playwright](/docs/tooling/playwright#configuration) の説明どおりです。ブランチのルールが各ブラウザーで必須とするチェックはそのブラウザーの `report` ジョブだけなので、シャードを追加または削除しても、必須チェックの名前は変わりません。 ビルドは読み込んだリリースタグの一覧もまとめ、各シャードはそれ以降に作られたタグを削除します。`content.spec.ts` は Git からリリースタグを読むため、シャードが待っている間にリリースのタグが付くと、ビルドが一度も描画していない changelog を期待してしまうからです。

`upload` ジョブ（名前は `Worker upload`）は、`upload: true` を付けて `deploy-reusable.yml` を呼び出します。デプロイとまったく同じようにプレビュー用 Worker をビルドし、`wrangler versions upload` を実行して、デプロイせずに新しいバージョンとして `saasyland-preview` Worker に送ります。Cloudflare は、サイズの上限、起動時間、バインディング、`secrets.required` が挙げるシークレットを、デプロイと同じようにアップロードでも検査します。そのため、このチェックに通った Worker はデプロイでき、その間も `preview.saasyland.com` は以前にデプロイされたバージョンを配信し続けます。このジョブはマイグレーションを適用せず、GitHub のデプロイも記録せず（`deployment: false`）、ほかのプルリクエストのアップロードと並行して実行されます。プルリクエストのバージョンには `pr-<number>` というエイリアスが付き、Cloudflare のダッシュボードでそのバージョンを示します。ジョブのサマリーにはバージョンの ID とサイズが表示され、Worker で Version URLs が有効な場合はその URL も表示されます。現在、`saasyland-preview` では有効になっていません。フォークと Dependabot からのプルリクエストは Cloudflare の認証情報を読めないため、このジョブをスキップします。認証情報を読めるマージキューが、マージ前にそれらのビルドをアップロードします。

プルリクエストでは、自分の[変更履歴のエントリ](/docs/conventions/git-workflow#changelog-entries)を追加するまで `bun run check` も失敗し、マージキューでは、キューに入ったプルリクエストのエントリがない間は失敗します。`e2e` ジョブと `upload` ジョブ、そしてデプロイジョブのビルドは、変更履歴がそのプルリクエスト自身のもの以外のエントリを**未リリース**の下に載せることになる間は失敗し、マージキューと `main` では未リリースのエントリが 1 つでもあれば失敗します。

## マージキュー [#merge-queue]

`main` を保護するルールセットは、`Format, lint, types, i18n, tests`、`Build and E2E / Build and E2E (chromium)`、`Build and E2E / Build and E2E (webkit)`、`Worker upload / Upload preview` を必須とし、プルリクエストを GitHub のマージキュー経由でのみマージします。マージキューは各プルリクエストをスカッシュします。`bun scripts/enqueue-pr.ts <number>` でプルリクエストをキューに入れます（[Git とプルリクエスト](/docs/conventions/git-workflow#merging)）。GitHub はキュー内の各プルリクエストについて、`main` とその前に並んでいるプルリクエストの上に、`gh-readonly-queue/main/pr-<number>-<commit>` という名前のブランチでスカッシュコミットを作成し、そのブランチで `merge_group` イベントとして `ci.yml` を実行します。グループ内の各プルリクエストが成功すると、GitHub は `main` をグループの最後のコミット、つまりキューがテストしたまさにそのコミットに移動します。そのため、1 回のプッシュでグループのすべてのプルリクエストが、それぞれ独自のスカッシュコミットとして `main` に入ります。失敗したプルリクエストはキューから外れ、その後ろのプルリクエストはそれを除いてもう一度テストされます。

ルールセットには `review_on_push: true` の `copilot_code_review` もありますが、2026 年 11 月 22 日時点で、GitHub Copilot は #70 以降どのプルリクエストもレビューしていないため、プルリクエストに自動レビューは付きません。レビューされても助言にとどまります。ルールセットは承認レビューもレビュースレッドの解決も求めないため、プルリクエストが待つのは上の 4 つのチェックだけです。

`ci.yml` は、新しいコミットに置き換えられたプルリクエストの実行をキャンセルしますが、キューの実行はキャンセルしません。キューのブランチはそれぞれ独自の ref を持つためです。変更履歴のゲートは、キューのブランチを `main` として扱います。グループの各プルリクエストはすでに、件名が自身の番号で終わるスカッシュコミットになっているため、未リリースのエントリは 1 つも許されず、キューに入ったプルリクエスト自身のエントリが存在する必要があります。

## デプロイ

`deploy.yml` は、`main` へのすべてのプッシュを、そのコミットが `main` が必須とするすべてのチェックに成功した時点で、まず共有プレビューに、続いて本番にデプロイします。最初のジョブ `tested` は `scripts/tested-commit.ts` を実行します。このスクリプトは GitHub の API を通じてルールセットからそれらのチェックを読み取り、プッシュされたコミットでそれぞれが成功した実行を探します。マージキューを経由したコミットには、キューがまさにそのコミットをテストしたため、それらの実行があります。そのため `deploy.yml` はチェックを再実行せずにデプロイします。それ以外の方法で `main` に入ったコミットでは、まず `ci.yml` のチェックを実行します。

| イベント                 | デプロイ先                     | GitHub の環境                  | URL                                                  |
| ------------------------ | ------------------------------ | ------------------------------ | ---------------------------------------------------- |
| `main` へのプッシュ      | `preview`、その後 `production` | `Preview`、その後 `Production` | https://preview.saasyland.com, https://saasyland.com |
| `preview.yml` の手動実行 | `preview`                      | `Preview`                      | https://preview.saasyland.com                        |

`deploy-reusable.yml` は GitHub の各環境に URL を設定します。`src/__test__/workflows.test.ts` は、そのいずれかが `DEPLOYED_HOSTS`（`src/modules/_core/constants/api.ts`）にあるその環境のホストと異なる場合に失敗します。プレビューは共有されており、各デプロイは前回のデプロイを置き換え、同じプレビュー用の D1 データベース、KV 名前空間、R2 の各バケットを使います。プレビューでは `main` が動いています。そのため、[ジャーニースイート](/docs/tooling/playwright#journey-suite)、Polar サンドボックスの Webhook、そして Better Auth が信頼する唯一のプレビューのホストである `preview.saasyland.com` でのサインインは、いずれも本番がまもなく実行するコードに対して行われ、すべてのマイグレーションは本番より先にプレビューのデータベースに適用されます。マージ前にブランチをそこで試すには、`gh workflow run preview.yml --ref <branch>` を実行します。ブランチのコミットが `main` の必須チェックに成功している場合にのみ、マイグレーションも含めてそのブランチをデプロイします。次に `main` へのプッシュがあると、プレビューは `main` に戻ります。

`deploy-reusable.yml` は `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` のシークレットがあることを確認し、`scripts/verify-bindings.ts` を実行し、`.env.test` のダミー値でビルドし、生成された `dist/server/.dev.vars` を削除し、`db:migrate:<target>` を適用し、`vp exec wrangler deploy --config dist/server/wrangler.json` を実行します。`upload: true` の場合は、最後の 2 つのステップの代わりに `vp exec wrangler versions upload` を実行します。`deploy:<target>` スクリプトが行う稼働中のサイトの確認 `scripts/verify-deployment.ts` は実行しません。Cloudflare のボット対策が CI ランナーからのリクエストに 403 を返すためです。`scripts/run-deploy-checks.ts` も実行しません。そのため、デプロイ前チェック、つまり `package.json` の `<name>:verify:<environment>` スクリプトは、CI ではいずれも実行されません。CI には `.env.<target>` がなく、GitHub の環境には Cloudflare の認証情報と、`Preview` にある[ジャーニースイート](#journey-suite)のサンドボックス設定しかないからです。現在のチェックは認証エリアの `auth:verify` と Polar エリアの `polar:verify` です。OAuth クライアントを変更したらローカルで `bun run auth:verify:<target>` を、Polar を変更するたびに `bun run polar:verify:<target>` を実行してください（[Polar の設定](/docs/getting-started/polar-setup)）。シークレットファイルはアップロードしません。Worker は Cloudflare にすでに設定されているランタイムのシークレットをそのまま使います。同じデプロイ先へのデプロイは、互いにキャンセルするのではなくキューに入り、アップロードは並行して実行されます。プルリクエストに新しいコミットが追加されると、誰もマージすることのない 1 つ前のコミットに対する `ci.yml` の実行はキャンセルされます。一方、マージキューの実行は互いにキャンセルすることがなく、`main` での `deploy.yml` と `e2e-full.yml` の実行はキューに入ります（`concurrency` と `queue: max`）。そのため、`main` へのプッシュはすべてデプロイされます。

## ジャーニースイート [#journey-suite]

`journey.yml` は、[ジャーニースイート](/docs/tooling/playwright#journey-suite)である `bun run test:journey` を `https://preview.saasyland.com` に対して、UTC のスケジュール <RepositoryFact name="journeySchedule" /> と手動での起動時に実行します。

```sh
gh workflow run journey.yml --ref <branch> -f journey=all
```

`journey` は `all`、`core`、`complete`、`agency`、`upgrade` のいずれかで、`all` 以外の値はそのタグを持つテストだけを実行します。ジョブはデプロイを記録せずに（`deployment: false`）、GitHub の環境 `Preview` から次のシークレットを読みます: `POLAR_ACCESS_TOKEN`、`POLAR_PRODUCT_ID_CORE`、`POLAR_PRODUCT_ID_COMPLETE`、`POLAR_PRODUCT_ID_AGENCY`、`RESEND_API_KEY`。`POLAR_SERVER` にはスイートが受け付ける唯一の値 `sandbox` を設定し、スイートは Polar クライアントをサンドボックス向けに作るので、このワークフローが本番の Polar に届くことはありません。実行はキューに並び、互いにキャンセルしません。キャンセルされた実行は注文を支払い済みのまま残してしまうからです。ジョブは各テストの結果と所要時間、失敗した各テストのエラーを実行のサマリーに書き、HTML レポート、`playwright-report/journey.json`、失敗したテストのトレース、動画、マシンディレクトリを成果物 `journey-report` としてアップロードします。

このワークフローは `main` のデプロイのたびには実行しません。各実行はテストごとにプレビューでアカウントを登録し、Polar サンドボックスで注文を支払って返金し、確認メールと購入確認メールを、プレビューが本番と共有している Resend アカウントから送ります。`main` は忙しい日には何度もデプロイされるため、デプロイごとに実行すると、本番のメールが頼る送信上限に対してこれらのメールが何倍にも増えます。しかも何も止められません。ジャーニーが何を見つけても、本番はプレビューの直後にデプロイされるからです。各実行は購入の流れ全体を扱います。メール確認付きの登録、各プランのサンドボックスでの支払い、Polar が発行するキー、プランの台数分の端末での公開済み CLI、Core から Complete へのアップグレード、返金です。ただし、まだグリーンではありません。シークレットが設定されていないため成功した実行はなく、今のところ購入は何も確認していません。決済、ライセンス、CLI ライセンス API を変更した後や、マージ前のブランチを `gh workflow run preview.yml --ref <branch>` でテストした後は、手動で起動してください。

## 更新 [#updates]

`updates.yml` は、UTC のスケジュール <RepositoryFact name="updatesSchedule" /> と手動実行で、依存関係とエージェントスキルの更新を探します。最初のステップ `bun scripts/report-updates.ts find` は、npm レジストリにすべての直接依存関係の最新リリースを問い合わせ、ランナーのチェックアウトで `bun run skills:update` を実行して、上流で変わったスキルを確認します。このチェックアウトからは何もコミットしません。2 つ目のステップ `bun scripts/report-updates.ts issue` は 1 つの Issue <RepositoryFact name="updatesIssueTitle" /> を管理します。更新があれば Issue を作成し、以降の実行で書き直し、すべてが最新になったらクローズします。Issue には、古くなった各パッケージを `bun run deps:update` で動くものか固定のものかを示して並べ、各スキルを移動前後のコミットとともに並べます。最初のステップは、トークンが不要な `git ls-remote` で、固定した各アクションのリポジトリのリリースタグも読み取ります。Issue には、固定したリリースが最新リリースより古いアクションも並べます。

このワークフローに許されているのはリポジトリの読み取りと Issue の書き込みだけで、トークンを受け取るのは 2 つ目のステップだけです。プルリクエストは作成しません。ワークフロー自身のトークンで作成したプルリクエストに対して GitHub はワークフローを起動しないため、そのチェックが実行されないからです。代わりにブランチで `bun run deps:update` を実行してください。

## リリースとタグ [#releases-and-tags]

サイトは継続的にデプロイされるため、バージョンはセマンティックバージョンではなく日付です。本番へのデプロイが成功すると、`deploy.yml` の `release` ジョブがデプロイしたコミットに UTC の日付で `vYYYY.MM.DD` のタグを付け、GitHub Release を公開します。同じ日の 2 回目の本番デプロイには `vYYYY.MM.DD.2`、その次には `.3` というようにタグが付きます。プレビューへのデプロイにはタグを付けません。`contents: write` を持つジョブは `release` ジョブだけです。

リリースノートは、そのリリースが出荷した、つまり前のリリースタグ以降に `main` に入った[変更履歴](/docs/project/changelog)のエントリで、各エントリの末尾には GitHub がプルリクエストへのリンクにする `(#<number>)` が付きます。これにより、変更の説明は 1 か所にまとまります。出荷したエントリがないリリースでは、リリースノートは変更履歴へのリンクになります。 `scripts/publish-release.ts` は、自身の `RELEASE_NOTES` の唯一の要素である `src/lib/changelog.ts` の `releaseNotes` からリリースノートを取り、デプロイが選んだタグで `gh release create` を実行します。そのため、変更履歴のないプロジェクトはリリースノートなしでリリースを公開します。再実行すると、コミットにすでに付いているタグをそのまま使い、既存のリリースは作り直しません。

本番デプロイのジョブは、ビルドの前にそのタグを選びます。`scripts/choose-release-tag.ts` がチェックアウトのタグに `src/lib/release.ts` の `releaseTag` を適用し、ビルドはそのタグを `RELEASE_TAG` として受け取り、ジョブは出力 `release-tag` として `release` ジョブに渡します。これで、デプロイとそのリリースは同じタグを共有します。このタグを使って、[変更履歴](/docs/project/changelog)は各エントリを、それを最初に出荷したリリースにリンクします。リンク先は、`main` の第一親の履歴をたどってエントリのスカッシュコミットを含むコミットに付いた、最も古いリリースタグです。ビルドはこれを日付と一緒に 1 回の `git log` で読みます。デプロイ自身が持ち込むエントリには、そのデプロイのタグを使います。`release` ジョブも公開するタグを使って同じ方法で変更履歴を読むため、リリースのリリースノートは、ページがそのリリースにリンクするエントリとちょうど一致します。最初のリリースタグより前にマージされたエントリはどのリリースにもリンクせず、ローカル、プレビュー、プルリクエストのビルドでは、まだどのデプロイも出荷していないエントリもリンクしません。2 つの本番デプロイが同じタグを選ぶことはありません。`deploy.yml` は一度に 1 つのワークフロー実行しか走らせない（`concurrency` と `queue: max`）ため、前の実行の `release` ジョブがタグを作成してから、次のデプロイがリポジトリをチェックアウトします。

本番をあるリリースに戻すには、そのタグより後の変更をすべてプルリクエストで取り消します。

```sh
git fetch --tags origin
git switch --create rollback/v2026.11.13 origin/main
git revert --no-commit v2026.11.13..HEAD
git commit --message "revert: roll back to v2026.11.13"
```

マージすると、通常のチェックを経てタグのコードがデプロイされ、新しいリリースとしてタグが付きます。D1 のマイグレーションは元に戻らないため、古いコードが新しいスキーマ上で動きます。スキーマの変更はすべて、その前にデプロイされていたアプリケーションで動作しなければならないので、1 つ前のリリースに戻すのは安全です。それより前に戻す場合は、間のマイグレーションを確認してください。
