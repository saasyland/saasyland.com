## Cache delle query

`getRouter` crea un nuovo `QueryClient` per ogni richiesta, così sul server nessun dato passa da un utente all'altro. Valori predefiniti:

| Impostazione                         | Valore                                                                                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `staleTime` delle query              | <RepositoryFact name="queryStaleTimeMinutes" unit="minute" />                                                                                |
| `gcTime` delle query                 | <RepositoryFact name="queryGcTimeMinutes" unit="minute" />                                                                                   |
| `defaultStaleTime` del router        | <RepositoryFact name="routerStaleTimeMinutes" unit="minute" />                                                                               |
| `defaultPreloadStaleTime` del router | <RepositoryFact name="routerStaleTimeMinutes" unit="minute" />                                                                               |
| Precaricamento                       | Su intent, e le [pagine dell'intestazione](/docs/conventions/performance#the-headers-pages-load-before-a-click) appena una pagina è inattiva |

I loader riempiono la cache con `queryClient.query({ ...options, staleTime: "static" })` e i componenti leggono le stesse chiavi con `useSuspenseQuery`. Fanno eccezione le pagine dei corsi e l'editor dei corsi dell'amministrazione: le loro query mantengono `staleTime: COURSE_STALE_MS` (un minuto), perché `invalidateQueries` non ricarica mai una query `static`, e completare una lezione o salvare una modifica nell'editor deve aggiornare il programma. `setupRouterSsrQueryIntegration` serializza la cache del server nell'HTML e la idrata nel browser.

- **I messaggi di traduzione** vengono messi in cache per locale e namespace con `staleTime` e `gcTime` infiniti.
- **La query della sessione** (`getCurrentSessionQuery`) ha uno `staleTime` di <RepositoryFact name="sessionStaleTimeMinutes" unit="minute" />. Le guard delle route lasciano passare una navigazione con la sessione in cache finché è fresca e la ricaricano quando diventa obsoleta. Una funzione server che risponde `UNAUTHORIZED` o `FORBIDDEN` fa ricontrollare la sessione a `recheckRefusedSession` in `auth.routes.ts`, e le guard vengono eseguite di nuovo se è cambiata. Quando cambia l'utente autenticato, le guard rimuovono ogni query non contrassegnata con `meta: { public: true }`. Le query pubbliche, come le traduzioni e il numero di stelle con cui è stata renderizzata una pagina prerenderizzata, restano in cache. Vedi [Query pubbliche](/docs/conventions/data-fetching#public-queries).
- **Le mutazioni** invalidano le chiavi di query del proprio modulo, ad esempio `USER_QUERY_KEYS.ALL`, quando vanno a buon fine.

## Prerendering

`bun run build` prerenderizza le pagine pubbliche seguendo i link: landing, pagine legali, blog e documentazione in tutti i locale. Sono esclusi i percorsi sotto `/admin`, `/app`, `/auth`, `/courses`, `/newsletter` e `/api` (con o senza prefisso del locale) e i link con query string o hash. Le pagine dei corsi sono escluse perché mostrano i blocchi e i progressi di ogni spettatore. Il browser completa il blocco dei corsi della landing page con `getCourseShowcase` quando si avvicina all’area visibile, quindi la landing page prerenderizzata resta uguale per tutti (vedi [Corsi](/docs/features/courses)).

Il Worker serve l'HTML prerenderizzato dal binding `ASSETS` prima di caricare l'applicazione. Una pagina prerenderizzata non contiene dati utente, quindi può essere servita a tutti in sicurezza. Quando un visitatore ha diritto ai prezzi regionali, il Worker riscrive l'HTML e contrassegna la risposta con `Cache-Control: private, no-cache`.

Il prerendering viene eseguito su una build del Worker che contiene tutte le pagine. Il Worker destinato al deploy viene poi ricompilato senza le pagine compilate della documentazione e del blog e senza le traduzioni usate solo dalla landing e dalle pagine legali. Non gli servono né le une né le altre: la documentazione, il blog e la landing page leggono i loro contenuti da indici che la build scrive in `/assets/`, nel browser durante una navigazione lato client, e la ricerca della documentazione cerca in un indice statico nel browser, quindi le navigazioni lato client e la ricerca non raggiungono mai il Worker (vedi [Prestazioni](/docs/conventions/performance#the-worker-holds-no-docs-or-blog-content)). Vedi [Cloudflare Workers](/docs/integrations/cloudflare-workers).

## KV e D1

- **KV (`CACHE`)** memorizza il numero di stelle GitHub per `src/lib/github.ts`. Un numero di stelle più vecchio di un'ora viene restituito subito e aggiornato in background con `waitUntil`.
- **D1 (`DB`)** memorizza le sessioni e i contatori del rate limit. I controlli di sessione delle server function aggirano la cache dei cookie di Better Auth e vengono memoizzati per il resto della richiesta.
- **La cache di Workers** conserva i file video che `serveMedia` legge da R2 sotto `/media/_/<videoId>/<file>`, senza la firma, così gli spettatori di una stessa località edge condividono un'unica copia in cache. Vedi [Cloudflare R2](/docs/integrations/cloudflare-r2).
- Le server function non prendono mai decisioni sui permessi a partire da dati in cache.
