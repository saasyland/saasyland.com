As sessões ficam na tabela `session` do D1 (`src/modules/session/session.schema.ts`). `auth.session.ts` as lê com `getRequestSession`, memorizada por requisição, e expõe `getCurrentSessionQuery` para rotas e componentes. A cópia do cliente nunca inclui o token de sessão.

Cada sessão também armazena `country`, um campo adicional do Better Auth que o hook de banco de dados `session.create.before` em `auth.server.ts` preenche a partir do cabeçalho `cf-ipcountry` que a Cloudflare adiciona a toda requisição (`COUNTRY_HEADER`). Só um código do catálogo `COUNTRIES` é mantido, então endereços do Tor (`T1`) e desconhecidos (`XX`) deixam o campo vazio. O navegador e o sistema operacional vêm do user agent: `sessionDevice` em `src/modules/session/session.utils.ts` reconhece pelo nome os navegadores e sistemas comuns e distingue celulares de tablets.

## Casos de uso

| Caso de uso                               | Middleware                          | Usado por      |
| ----------------------------------------- | ----------------------------------- | -------------- |
| `getActiveSessions`                       | logado                              | `SessionsCard` |
| `revokeSession`                           | logado; somente as próprias sessões | `SessionRow`   |
| `revokeOtherSessions`                     | logado                              | `SessionsCard` |
| `listUserSessions`                        | `session: ["list"]`                 | `UserSessions` |
| `revokeUserSession`, `revokeUserSessions` | `session: ["revoke"]`               | `UserSessions` |

`getActiveSessions` retorna as sessões não expiradas do usuário atual, das mais recentes para as mais antigas, e deixa de fora as sessões de personificação. `listUserSessions` retorna as sessões não expiradas de outro usuário a partir do `listUserSessions` do Better Auth, das mais recentes para as mais antigas e sem os tokens, incluindo as de personificação. `revokeUserSession` recebe um ID de sessão e procura o token dela no servidor, então nenhum token chega ao navegador.

## Interface

A aba **Segurança** de `/app/settings` e `/admin/settings` mostra `SessionsCard` (`src/presentation/components/custom/settings/sessions-card.tsx`), com este navegador primeiro. Cada `SessionRow` nomeia o navegador e o sistema, como "Firefox no Windows", marca **Este dispositivo** e mostra o país, o endereço IP, quando a sessão teve atividade pela última vez e quando ela foi iniciada. Todas as outras linhas têm **Encerrar sessão**, cujo nome acessível nomeia o dispositivo, e o card termina com **Encerrar sessão nos outros dispositivos** enquanto houver algum. Alterar ou definir a senha também encerra todas as outras sessões e atualiza a lista.

O perfil de um usuário em `/admin/users` mostra `UserSessions` (`src/presentation/components/custom/admin/users/user-sessions.tsx`): o dispositivo de cada sessão, do mesmo `useSessionDeviceName`, e quando ela começou e teve atividade pela última vez, um botão que a revoga e, após uma confirmação, um botão que desconecta o usuário em todos os lugares. Veja [Usuários (admin)](/docs/features/users-admin).

## Dados em cache e a conta autenticada [#cached-data-and-the-signed-in-account]

Toda query que não está marcada como pública pertence à conta que estava autenticada quando ela carregou ([Queries públicas](/docs/conventions/data-fetching#public-queries)). `auth.routes.ts` registra essa conta para cada cache de queries. `getRouter()` repassa cada mudança do cache a `recordUserDataOwner`, que pega a conta da primeira sessão que o cache recebe, seja porque o servidor a renderizou na página, seja porque um guard de rota a carregou ou o cabeçalho a pediu. Cada guard de rota compara a sessão que carrega com esse registro. Quando são diferentes, o guard remove com `removeUserData` as queries e mutations da conta anterior, guarda a nova sessão e registra a nova conta. Um visitante não autenticado conta como uma conta própria, então entrar, sair e trocar de conta esvaziam o cache, enquanto uma verificação que encontra a mesma conta mantém tudo o que a página carregou, como uma aula que o aluno acabou de marcar como concluída.

O registro fica ao lado do cache, e não na query da sessão, então continua apontando para a conta anterior quando um componente busca a sessão de novo e encontra outra conta, ou quando a query da sessão sai do cache. O guard seguinte remove então os dados da conta anterior.
