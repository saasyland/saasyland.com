SaaSy Land obsługuje następujące języki (łącznie <RepositoryFact name="languages" />): <RepositoryFact name="supportedLocales" />; domyślny to `en-US`. Angielski używa ścieżek bez prefiksu (`/docs`), a pozostałe języki – pełnego prefiksu (`/pl-PL/docs`). Aliasy języków, takie jak `/pl/docs`, przekierowują na stałe do ścieżki kanonicznej.

## Pliki

Cała logika języków znajduje się w `src/integrations/use-intl/`:

| Plik                 | Odpowiedzialność                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `i18n.config.ts`     | `I18N` z `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, `COOKIE_NAME`, `DEFAULT_TIMEZONE` i nazwanymi formatami dat `FORMATS`                                   |
| `i18n.loaders.ts`    | `MESSAGE_LOADERS`, które `loadNamespace` importuje, gdy pierwszy raz ładuje przestrzeń nazw                                                             |
| `i18n.messages.ts`   | `loadNamespace`, `loadPageMetadata`, `messagesQueryOptions`, `preloadNamespaces` i `ROOT_NAMESPACES`                                                    |
| `i18n.middleware.ts` | `resolveLocale` i `parseLocaleCookie`: przekierowania kanoniczne i synchronizacja ciasteczka języka dla żądań dokumentów, używane przez `src/server.ts` |
| `i18n.paths.ts`      | `localizePathname`, `deLocalizePathname`, `canonicalizePathname`, `localeLinks` i powiązane funkcje pomocnicze ścieżek                                  |
| `i18n.utils.ts`      | `getCurrentLocale`, `localizeUrl` i `deLocalizeUrl`                                                                                                     |

## Przestrzenie nazw

Komunikaty znajdują się w `messages/<locale>/<namespace>.json`, a nazwa pliku jest nazwą przestrzeni nazw: `pages.admin.users`, `components.custom.footer`, `emails.verify-email`, `auth.validations` lub `common`. Komunikaty to zwykły JSON bez generowanych typów. Każda przestrzeń nazw strony zawiera `metadata.title` i `metadata.description` dla sekcji head strony.

Trasa główna wstępnie ładuje główne przestrzenie nazw (`common`, `components.*` i `errors*`) w `beforeLoad`. Trasa strony deklaruje jedną `NAMESPACE`, a trasa layoutu deklaruje `NAMESPACES` dla swojego poddrzewa; obie wymieniają je w `staticData.namespaces` i wstępnie ładują w loaderze:

```tsx
const NAMESPACE = "pages.legal.terms"

export const Route = createFileRoute("/_site/_marketing/terms")({
  component: TermsPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.TERMS),
  staticData: { namespaces: [NAMESPACE] },
})
```

`TranslationsProvider` opakowuje body dokumentu i łączy główne przestrzenie nazw z przestrzeniami nazw każdej dopasowanej trasy w jeden `IntlProvider`, dzięki czemu ekrany błędu i „nie znaleziono” również są przetłumaczone. Przestrzenie nazw e-maili ładuje wyłącznie serwerowy przypadek użycia, który wysyła dany e-mail.

## Język i linki

`getCurrentLocale()` działa izomorficznie i po obu stronach odczytuje język ze ścieżki adresu, z `en-US` jako wartością zapasową. Adresy `/api` i funkcji serwerowych nie mają prefiksu języka, więc na serwerze zwraca dla nich `en-US`. Worker utrzymuje ciasteczko języka zgodne z adresem strony, ale żaden kod nie wybiera na jego podstawie języka.

`rewrite` routera usuwa prefiks języka z przychodzących adresów URL i dodaje go do wychodzących, więc `<Link to={ROUTES.X}>` zawsze pozostaje w bieżącym języku. Surowe adresy URL w bieżącym języku, takie jak adresy zwrotne Better Auth, pochodzą z `router.buildLocation(...).publicHref`. `localizePathname({ locale, pathname })` buduje adres URL w wybranym języku, na przykład linki w e-mailach i linki przełącznika języka, więc wybór języka ładuje tę samą stronę w nowym dokumencie.

## Komponenty

Komponent wywołuje `useTranslations` dokładnie raz i nazywa funkcję tłumaczącą `t`. i18n-ally zmienia zakres każdego późniejszego `t()` po kolejnym wywołaniu `useTranslations`, a `bun run check:i18n` zgłasza błąd dla kluczy, których nie da się rozwiązać w ich zakresie. Komponent, który potrzebuje dwóch niepowiązanych przestrzeni nazw, używa ich wspólnej przestrzeni nadrzędnej albo `useTranslations()` z pełnymi kluczami.

## Kontrole

`bun run check:i18n` uruchamia pierwsze dwa z tych skryptów, a `bun run check:content` trzeci; `bun run check` uruchamia oba:

- `scripts/check-i18n.ts`: kompletność kluczy względem `en-US` i rozwiązywanie statycznych kluczy w ich zakresie.
- `scripts/check-message-formats.ts`: każdy komunikat daje się sparsować jako ICU i zachowuje swoje argumenty, znaczniki formatowania, ścieżki plików i polecenia, bez grawisów Markdown i bez [formy zwracania się](/docs/conventions/translations#one-form-of-address), której jego język nie używa.
- `scripts/check-content.ts`: pliki dokumentacji i bloga, nawigacja, przykłady kodu, kod w linii, komponenty, linki i tabele są zgodne we wszystkich językach, a ich tekst zwraca się do czytelnika w formie przyjętej dla języka.
