## Worker y bindings

`wrangler.jsonc` define `src/server.ts` como punto de entrada del Worker. El Worker recibe cuatro bindings:

| Binding  | Tipo               | Uso                                                                               |
| -------- | ------------------ | --------------------------------------------------------------------------------- |
| `DB`     | Base de datos D1   | Todas las tablas, incluidas las sesiones y los contadores de límite de peticiones |
| `CACHE`  | Namespace de KV    | El número de estrellas de GitHub y los descuentos regionales del checkout         |
| `MEDIA`  | Bucket de R2       | Archivos de vídeo, servidos por `serveMedia` bajo `/media/`                       |
| `ASSETS` | Recursos estáticos | Páginas prerenderizadas y archivos de `public`                                    |

Las peticiones a `/assets/*`, `/fonts/*`, `/robots.txt` y `/llms.txt` se sirven desde los recursos estáticos sin ejecutar el Worker. El código de servidor lee los bindings, los secretos y `waitUntil` de `cloudflare:workers`. `src/server.ts` añade las cabeceras de seguridad a cada respuesta que devuelve; los archivos que se sirven sin el Worker reciben el subconjunto de `public/_headers` ([Seguridad y endurecimiento](/docs/features/security)).

## Entornos

`wrangler.jsonc` define cuatro entornos. `CLOUDFLARE_ENV` selecciona uno para `vp dev` y `vp build`.

| Entorno       | Bindings                                | Lo usa                                          |
| ------------- | --------------------------------------- | ----------------------------------------------- |
| `development` | D1, KV y R2 de preview remotos          | `bun run dev`                                   |
| `preview`     | D1, KV y R2 de preview                  | `bun run build:preview`, `deploy:preview`       |
| `production`  | D1, KV y R2 de producción               | `bun run build:production`, `deploy:production` |
| `test`        | D1, KV y R2 locales en `.wrangler/test` | `bun run build:test`, Playwright                |

Cada entorno enumera sus secretos obligatorios en `secrets.required`. Los valores salen del archivo `.env.<environment>` correspondiente; los scripts de despliegue escriben las claves declaradas en `.wrangler/secrets.<environment>.json` y pasan ese archivo a Wrangler con `--secrets-file`. El entorno `test` usa `src/platform/testing/worker.ts` como punto de entrada y los valores ficticios versionados en `.env.test`. `AFFONSO_PROGRAM_ID` es público, así que es una variable de Worker normal en `vars` y no un secreto; solo `test` lo define.

## Tipos

- `src/types/bindings.d.ts` declara `Cloudflare.Env`: los bindings, todos los secretos que lee el Worker y la variable opcional `AFFONSO_PROGRAM_ID`. Los tres secretos `CLOUDFLARE_*` no se declaran, porque solo los lee drizzle-kit, desde `process.env`.
- `src/types/worker-configuration.d.ts` lo genera `bun run cf-typegen`.
- `src/types/router.d.ts` registra el tipo del router y la opción de ruta `staticData.namespaces`.

## Infraestructura del runtime de pruebas

`src/platform/testing` contiene solo lo que no puede pertenecer a una única funcionalidad:

- `setup.ts`: los matchers de jest-dom, el reinicio de los bindings antes de cada prueba y el sustituto de `createServerFn` que ejecuta las funciones de servidor en el mismo proceso
- `mocks/cloudflare.ts`: un D1 en memoria sobre SQLite que ejecuta las migraciones del repositorio, un KV en memoria, un bucket `MEDIA` en memoria y un `waitUntil` que las pruebas pueden vaciar
- `mocks/cache.ts`: `createEdgeCache`, un sustituto de la caché de Workers para las pruebas de entrega de medios
- `mocks/resend.ts` y `mocks/polar.ts`: dobles de prueba estrictos de las API de Resend y Polar, y `mocks/providers.ts`, que dirige `fetch` hacia ellos en cada prueba y en el Worker de las pruebas de navegador
- `mocks/wrksz-themes.ts`: un sustituto de la librería de temas
- `lib/`: el puente RPC de las funciones de servidor, utilidades de renderizado, utilidades para las URL de las peticiones, ejecutores de consultas y modelos de Polar con webhooks firmados
- `worker.ts`: el punto de entrada del Worker para las pruebas de navegador, que instala los dobles de los proveedores y expone el correo entregado

Consulta [Pruebas y CI](/docs/architecture/testing-architecture) para ver cómo los usan las suites.
