O Playwright testa a aplicação compilada em navegadores reais. A suíte é executada contra o ambiente `test` do Wrangler: D1, KV e R2 locais em `.wrangler/test`, credenciais fictícias de `.env.test` e a entrada de testes `src/platform/testing/worker.ts`, que intercepta as requisições ao Resend e à Polar.

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:journey
```

| Script             | Executa                                                          |
| ------------------ | ---------------------------------------------------------------- |
| `test:e2e:install` | Instala o Chromium e o WebKit com as dependências do sistema     |
| `test:e2e`         | Todas as specs no Chromium e no WebKit                           |
| `test:e2e:smoke`   | `e2e/specs/smoke.spec.ts` no Chromium                            |
| `test:e2e:pr`      | Todas as specs no Chromium, como na CI de pull requests          |
| `test:e2e:headed`  | Todas as specs em navegadores visíveis                           |
| `test:e2e:ui`      | Modo UI do Playwright                                            |
| `test:journey`     | A [suíte da jornada do cliente](#journey-suite) contra o preview |

## Configuração [#configuration]

`playwright.config.ts` roda as specs de `e2e/specs/`, define os projetos `chromium` (Desktop Chrome) e `webkit` (Desktop Safari) e usa `PLAYWRIGHT_BASE_URL` ou `http://127.0.0.1:3000` (`LOCAL_SERVER_ORIGIN` de `src/data/local-server.ts`). Localmente, o comando do servidor web executa `db:reset:test`, `build:test` e `start:test`, e reutiliza um servidor que já responda nessa URL. Na CI, um job prepara o build, cada um dos <RepositoryFact name="e2eShards" /> shards que dividem a suíte o descompacta e o Playwright apenas inicia o servidor ([CI/CD](/docs/tooling/ci-cd#checks)).

| Configuração     | Local                                            | CI                                            |
| ---------------- | ------------------------------------------------ | --------------------------------------------- |
| Novas tentativas | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" /> |
| Workers          | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" /> |
| Traces           | Mantidos em falhas                               | Na primeira nova tentativa                    |
| Vídeos           | Desativados                                      | Mantidos em falhas                            |
| Relatórios       | List e HTML                                      | GitHub e blob, mesclados em HTML em falhas    |

## Rodar ao lado de outros worktrees [#running-beside-other-worktrees]

O build de teste só aceita requisições dos hosts em que confia no modo de teste, porque o Better Auth e os links da newsletter verificam o host da requisição: `127.0.0.1:3000` e `localhost:3000`, e `127.0.0.1` e `localhost` nas portas <RepositoryFact name="testServerFirstPort" /> a <RepositoryFact name="testServerLastPort" />, definidas por `TEST_SERVER_PORTS` em `src/data/local-server.ts`. Em qualquer outra porta, as páginas de login e de cursos falham, por isso `playwright.config.ts` para antes de construir qualquer coisa quando `PLAYWRIGHT_BASE_URL` indica outro host.

`PLAYWRIGHT_BASE_URL` é a única configuração que escolhe a porta: o Playwright abre essa URL e inicia `start:test` na porta dela. Quando outros worktrees rodam suas suítes ao mesmo tempo, dê a cada worktree uma porta própria do intervalo. Verifique que nada escuta nela e rode a suíte ali:

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

`lsof` não imprime nada quando a porta está livre. Se imprimir um processo, use outra porta e deixe esse servidor em paz: encerre apenas os servidores que você iniciou.

Localmente, o Playwright reutiliza um servidor que já responde na URL e então pula o reset do banco de dados e o build, por isso a suíte nunca pode chegar ao servidor de outro worktree. `e2e/global-setup.ts` garante isso: antes do primeiro teste, ele procura com `lsof` os processos que escutam na porta e interrompe a execução quando algum deles roda em outro diretório que não este worktree. Um servidor que você iniciou a partir deste worktree passa na verificação e é reutilizado como está, então encerre-o quando a suíte precisar testar um build novo.

## Estrutura

- `e2e/specs/`: specs para smoke checks, a landing page e seus controles, navegação, locales, tema, SEO, autenticação com seus redirecionamentos e seu roteamento, workspaces, administração de usuários, newsletter, conteúdo, páginas legais, preços regionais, o funil de checkout, a página de licença, a API de licenças da CLI, afiliados, vídeos, cursos, acesso aos cursos, administração de cursos, rodapé, anéis de foco, barras de rolagem e acessibilidade (<RepositoryFact name="e2eSpecs" /> arquivos).
- `e2e/pages/`: page objects.
- `e2e/fixtures/`: a fixture `test` estendida, helpers para os e-mails capturados, `deliverPaidOrder` em `license.ts`, que envia um webhook `order.paid` assinado para conceder uma licença, `buyLicense`, que pede ao Worker de teste em `/__test/polar/purchase` um pedido com sua chave de licença no dublê de teste da Polar e envia os `order.paid` e `benefit_grant.created` assinados, `startedCheckouts`, que lê de `/__test/polar/checkouts` os checkouts que o dublê criou, `payCheckout`, que paga um checkout aberto pelo app por meio de `/__test/polar/pay` do Worker de teste, com o consentimento marcado, e envia os `order.paid` e `benefit_grant.created` assinados do pedido dele, e `accessibilityViolations` com os `COLOR_SCHEMES` claro e escuro em `accessibility.ts`.
- `e2e/data/accounts.ts`: as contas criadas pelo seed, um administrador e um cliente, e sua senha. `e2e/data/licenses.ts` contém o cliente com licença e essa licença, além de uma licença para cada worker paralelo, na qual a spec da API de licenças da CLI ativa dispositivos.
- `e2e/data/videos.ts` e `e2e/data/courses.ts`: o vídeo de teste criado pelo seed, cujos arquivos ficam em `e2e/fixtures/video/`, e o curso criado pelo seed: um capítulo com uma prévia gratuita, uma aula para contas e duas aulas pagas, uma delas sem vídeo.
- `e2e/data/<area>.pages.ts` e `e2e/data/<area>.seed.ts`: as páginas de cada área, que `accessibility.spec.ts` e `workspaces.spec.ts` visitam, e as linhas e mídias dela no banco de dados de teste, reunidas por `pages.entries.ts` e `seed.entries.ts`.
- `e2e/data/<area>.flows.ts`: os fluxos de cada área, cada um com o teste que o prova de ponta a ponta ou o motivo pelo qual ele falta, reunidos por `flows.entries.ts`; veja [Cobertura de testes](/docs/tooling/test-coverage).
- `e2e/global-setup.ts`: o setup global, que interrompe a execução quando o servidor na porta da suíte roda a partir de outro worktree.
- `e2e/journey/`: a [suíte da jornada do cliente](#journey-suite), com configuração própria.

O Worker de testes executa o que as áreas declaram em `e2e/data/<area>.worker.ts`, reunido por `worker.entries.ts`: a área de licenças semeia as chaves de licença de teste no dublê da Polar, o Resend expõe `/__test/emails` para ler os e-mails capturados e a área da newsletter, `/__test/newsletter` para ler o estado de um inscrito.

## Acessibilidade

`e2e/specs/accessibility.spec.ts` executa o [axe-core](https://github.com/dequelabs/axe-core) por meio do `@axe-core/playwright` nas páginas públicas, nas páginas de cursos, na página inicial da documentação, em todas as páginas de Convenções e em uma página de cada uma das outras seções da documentação, em um post do blog e nos workspaces de administrador e de cliente, nos temas claro e escuro. As páginas de administração incluem `/admin/courses`, `/admin/courses/create` e o editor do curso semeado, que `e2e/specs/workspaces.spec.ts` também visita. Aplica as regras A e AA das WCAG 2.0, 2.1 e 2.2 e as boas práticas do axe, falha quando uma página não carrega com um status de sucesso, rola a página para que as seções que aparecem com a rolagem também sejam verificadas, espera as animações finitas terminarem e falha em qualquer violação, informando a regra, o impacto e os seletores afetados.

O axe não vê o percurso do teclado nem o layout, então três specs os verificam no cabeçalho e no rodapé do site: `e2e/specs/navigation.spec.ts`, que o menu do celular leva o foco para si, mantém o Tab dentro, deixa a página por trás `inert` e devolve o foco ao seu botão; `e2e/specs/footer.spec.ts`, que a 320, 390 e 430 px nenhum link do rodapé encosta em outro nem sai do rodapé, em nenhum idioma, e que um link para uma seção da página inicial só é o atual na própria seção; e `e2e/specs/focus-rings.spec.ts`, que o seletor de idioma do rodapé e o gatilho da paleta de comandos do admin desenham o seu anel para o teclado.

## Barras de rolagem [#scrollbars]

`e2e/specs/scrollbars.spec.ts` inicia o Chromium sem a opção `--hide-scrollbars` do Playwright, por meio de `ignoreDefaultArgs` em `launchOptions`, então o Chromium desenha barras de rolagem clássicas que ocupam espaço, como no Windows, no Linux e em um Mac configurado para mostrá-las sempre. A spec verifica que uma página legal, uma de autenticação e uma do painel de administração mantêm o título no lugar quando a janela cresce até a página deixar de rolar (uma página da documentação sempre rola, porque o rodapé do site vem depois do layout dela, da altura da janela), que abrir a busca da documentação, o seletor de idioma, um diálogo ou um menu não move nada, que `/admin` ocupa a janela e que a janela atrás de uma página escura é escura no tema claro. O WebKit no macOS só desenha barras sobrepostas, que não ocupam espaço, e nenhuma opção de inicialização muda isso, então a verificação do espaço reservado roda só no Chromium. O menu do site, que substitui os links do cabeçalho abaixo de `lg`, é verificado a 768 px: abri-lo e fechá-lo não move nada.

## Suíte da jornada do cliente [#journey-suite]

`bun run test:journey` compra uma licença e usa a CLI como um cliente, no deploy de preview em `https://preview.saasyland.com`, que recebe os pagamentos no sandbox da Polar. `e2e/journey/playwright.config.ts` é uma configuração própria, com um projeto Chromium só dela e sem servidor web, então nem `test:e2e` nem as verificações dos pull requests a executam, e nenhum workflow a executa ainda: [Cobertura de testes](/docs/tooling/test-coverage#journey-suite) lista o que é preciso para executá-la na CI. Cada plano é um teste próprio, os testes rodam em paralelo, e cada um segue estes passos:

1. **Conta.** O teste se cadastra com um endereço novo da caixa de testes do Resend, `delivered+journey-<run>-<tier>@resend.dev`, ou `upgrade` no lugar do plano no teste de upgrade, encontra o e-mail de verificação pela API do Resend e abre o link dele.
2. **Preço.** `/app/license` precisa oferecer o plano pelo preço do país em que a Cloudflare situa o runner, conforme `/cdn-cgi/trace` informa: o preço regional em um país de `PPP_TIERS`, o preço cheio em qualquer outro.
3. **Checkout.** O checkout do sandbox da Polar precisa abrir com o e-mail da conta já preenchido e o consentimento ao fornecimento imediato desmarcado; o teste o marca na página da Polar. O teste paga com o [cartão de teste da Stripe](https://docs.stripe.com/testing) e cobrança na Polônia, onde o endereço de cobrança é só o país.
4. **Pedido e chave.** A Polar precisa ter um único pedido pago do produto do plano, pelo preço que `/app/license` ofereceu, com o consentimento e o idioma do comprador, a confirmação da compra precisa chegar à caixa de entrada, e `/app/license` precisa mostrar a chave que os webhooks emitiram, os comandos da CLI e nenhum dispositivo em uso.
5. **CLI.** A CLI publicada, executada como <RepositoryFact name="cliExec" /> assim como os comandos de `/app/license`, fala com o preview por meio de `SAASYLAND_API_URL`. `activate` grava o arquivo de credenciais com o modo `0600`, ativar de novo mantém a mesma ativação, e `whoami` mostra o dispositivo. Dispositivos de CI, diferenciados por `SAASYLAND_CI_REPOSITORY`, ocupam as ativações restantes, até <ActivationLimit tier="core" /> dispositivos no Core, <ActivationLimit tier="complete" /> no Complete e <ActivationLimit tier="agency" /> no Agency, e o seguinte é recusado com `activationLimitReached`. Assim que uma ativação é liberada em `/app/license`, o dispositivo recusado fica com ela e o liberado recebe `activationNotFound`. `deactivate` libera o primeiro dispositivo e remove as credenciais dele.
6. **Reembolso.** O teste reembolsa o pedido pela API do sandbox da Polar e espera até `/app/license` mostrar a licença como reembolsada; então `whoami` precisa responder `licenseRefunded` e remover as credenciais.

Um quarto teste faz o upgrade de uma licença. Ele compra o Core do mesmo jeito e ocupa os <ActivationLimit tier="core" /> dispositivos do Core, e o seguinte é recusado. Depois, `/app/license?tier=complete` precisa oferecer o Complete pelo preço dele para o país do runner, menos o que custou o pedido do Core, e o teste paga essa diferença no checkout da Polar. A Polar precisa ter o pedido de upgrade pela diferença, com o pedido e o plano do Core em `upgrade_from_order` e `upgrade_from_tier`; a chave do pedido do Core precisa permitir agora os <ActivationLimit tier="complete" /> dispositivos do Complete, a chave que a Polar concedeu pelo pedido de upgrade precisa estar desativada, e `/app/license` precisa mostrar o Complete com a mesma chave. Depois, o dispositivo recusado e o seguinte são ativados, e o próximo é recusado. O teste reembolsa o pedido de upgrade pela API do sandbox da Polar: a licença precisa voltar a ser Core, com a mesma chave e o limite do Core, os dispositivos já ativados continuam funcionando e um novo é recusado. Um reembolso do pedido do Core encerra a licença em seguida.

Cada dispositivo da CLI é um diretório na pasta de saída do teste que a CLI usa como home, e a CLI roda sem nada no ambiente além de `PATH`, essa home, um cache do npm e as variáveis `SAASYLAND_*`, então nenhuma credencial da suíte chega até ela. Um pedido que um teste com falha deixa pago é reembolsado quando o teste termina. As contas ficam no preview, cada uma com uma licença reembolsada.

A suíte lê estes valores do ambiente, ou de `.env.preview` quando o arquivo existe, e para antes do primeiro teste sem eles:

| Variável                                                                        | Para quê                                                                                                                                                      |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | Ler e reembolsar os pedidos no sandbox e ler as chaves de licença deles, com os escopos `orders:read`, `refunds:write`, `benefits:read` e `license_keys:read` |
| `POLAR_SERVER`                                                                  | Precisa ser `sandbox`                                                                                                                                         |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | Os produtos do sandbox a que os pedidos precisam corresponder                                                                                                 |
| `RESEND_API_KEY`                                                                | Ler os e-mails de verificação que o preview enviou, o que exige uma chave com acesso total                                                                    |

O preview precisa rodar um build com a [API de licenças da CLI](/docs/features/cli-licence-api). Ele roda a `main`, que o `deploy.yml` coloca lá antes da produção; para testar uma branch antes de ela ser mesclada, faça o deploy dela com `gh workflow run preview.yml --ref <branch>` depois que as verificações dela passarem. O sandbox precisa corresponder ao código, o que `bun run polar:verify:preview` verifica. Depois:

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

O relatório é gravado em `playwright-report/journey/`, e os traces, vídeos e diretórios de dispositivos dos testes com falha em `test-results/journey/`.
