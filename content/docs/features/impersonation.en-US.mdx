---

The Better Auth `admin` plugin provides impersonation, and `src/modules/user/use-cases` wraps it:

```ts
export const impersonateUser = createServerFn({ method: "POST" })
  .middleware([authorized({ user: ["impersonate"] })])
  .validator((input: User["impersonateUser"]) => userZodSchemas.impersonateUser.parse(input))
  .handler(({ context, data }) => auth.api.impersonateUser({ body: data, headers: context.requestHeaders }))
```

`stopImpersonatingUser` needs only a signed-in session. Both files export mutation options (`impersonateUserMutation`, `stopImpersonatingUserMutation`).

## Start

**Impersonate** in the actions menu of a user ([Users (admin)](/docs/features/users-admin)), on `/admin/users/all` or on the user's profile, calls `impersonateUser`. Better Auth creates a session for the user marked with `impersonatedBy`, keeps the admin's session token in a signed `admin_session` cookie and switches the session cookie to the new session; `tanstackStartCookies()` carries both cookies on the server function's response. The menu then removes the admin's data from the query cache with `removeUserData`, clears the router cache and opens `/app`.

The item appears only for a user who is neither an admin nor banned. Better Auth refuses to impersonate a user with an admin role unless the caller holds `user: ["impersonate-admins"]`, which no role in `auth.access.ts` grants, and its session hook refuses a session to a banned user. `auth.server.ts` sets no `impersonationSessionDuration`, so the session lasts as long as Better Auth's default allows.

## Banner and stop

`ImpersonationBanner` (`src/presentation/components/custom/app/impersonation-banner.tsx`) sits above the header of the `/app` layout. It reads `getCurrentSessionQuery` and renders only when the session has `impersonatedBy`: a region labelled from `components.custom.impersonation-banner.json` that names the impersonated user and their email, and a **Stop impersonating** button. The button calls `stopImpersonatingUser`, which deletes the impersonation session and restores the admin's session from the `admin_session` cookie; the banner then removes the user's data from the cache and opens that user's profile in `/admin/users`.

## Sessions

- `getActiveSessions` leaves impersonation sessions out of the settings session list, and Better Auth's own `list-sessions` endpoint does the same.
- The sessions card on a user's profile lists them, so an admin can revoke an impersonation session that another admin left open.
- The route guards remove the previous user's data from the query cache when the session user changes, so every navigation after starting or stopping loads the right user's data.

There is no audit log of impersonation.
