  - question: エージェントを活用するコードベースでは、依存関係はいくつから多すぎますか？

    answer: ほとんどの場合、その必要はありません。移行コストは確実にかかり、得られる効果には限りがあります。一方で、既存のスタックに厳密な型、境界での検証、検証用の 1 つのコマンドを追加するのは安価で、すぐに効果が出ます。スタックはどのみち変更する予定があるときに変更し、エージェントとの相性は変更の理由ではなく、決め手に迷ったときの判断材料にしてください。

## AI コーディングエージェントにとって、スタックは実際に何をするのか？

スタックはエージェントを正しくするわけではありません。スタックが変えるのは、**表現できる誤ったプログラムの数** です。ライブラリの選択はどれも、「コンパイルは通るが間違っている」コードの範囲を狭めるか、広げるかのどちらかです。仕組みはこれがすべてです。だからこそ「エージェントに適している」かどうかは、雰囲気ではなく、テストできる性質なのです。

2 つのコードベースで同じ誤りが起きた場合を考えてみましょう。エージェントが、タイムスタンプであるデータベースのカラムを文字列だと読み違えたとします。

型付きのクエリビルダーでは、この誤りは表現できません。コードはコンパイルされず、エージェントは自分の実行の中でエラーを目にして修正します。かかるコストは約 2 秒です。

`any` を返す生のクエリでは、この誤りはコンパイルを通り、読んだ限りでは正しく見えるのでレビューも通過し、6 週間後に請求メールの日付を誤って表示します。かかるコストは、1 件のインシデントです。

同じモデル、同じプロンプト、同じ誤り。それがコンパイルエラーで済むか、インシデントになるかを決めたのはスタックでした。

## 鮮度ギャップと、人気が指標でなくなった理由

誰もが持ち出す論拠はこうです。人気のあるライブラリは学習データに多く登場するので、モデルはより正確に書ける。前半は正しいのですが、後半はいまや、この論拠が無視している要素に完全に左右されます。それは **ライブラリがどれだけ速く変化するか** です。

**鮮度ギャップとは、モデルが記憶している API と、実際にリリースしているコードの API との距離のことです。** 学習データの量からわかるのは、モデルがそのライブラリをどれだけ自信を持って書くかです。鮮度ギャップからわかるのは、その自信に根拠があるかどうかです。この 2 つは別の量であり、変化の速いフレームワークでは、いまや正反対の方向を指しています。

この点に関する研究の結論は明確です。広く使われている 8 つのライブラリを対象にした研究では、モデルが生成したコードにおける **非推奨 API の使用率が 25% から 38%** と測定され、その原因は古くなったパラメトリック知識と、現在の API を参照する手段がまったくないことにあるとされました（[APILOT, arXiv](https://arxiv.org/pdf/2409.16526)）。進化する API に関する研究は、同じ失敗を知識の衝突として捉えています。モデルは推測しているのではなく、もう存在しないバージョンを自信を持って思い出しているのです（[When LLMs Lag Behind, arXiv](https://arxiv.org/html/2604.09515v1)）。

ここから、直感に反する順位が生まれます。モデルの記憶が引き起こす問題の大きさで並べると、次のようになります。

| ライブラリの特徴                                                         | 学習データ量 | API の変更頻度 | エージェントの出力への最終的な影響          |
| ------------------------------------------------------------------------ | ------------ | -------------- | ------------------------------------------- |
| 人気があり安定している（React、PostgreSQL、Tailwind）                    | 多い         | 低い           | **最良。** 記憶が多く、しかも今でも正しい   |
| 小規模で安定している（Zod、用途を絞ったユーティリティの大半）            | やや少ない   | 低い           | **良好。** 記憶は少ないが、ある記憶は正しい |
| 人気があり変化が速い（メジャーバージョンの移行途中にあるフレームワーク） | 多い         | 高い           | **最悪。** 自信に満ち、流暢で、間違っている |
| 小規模で変化が速い                                                       | 少ない       | 高い           | 悪いが、エージェントは断定せずに慎重になる  |

興味深いのは右下のセルです。モデルがあるライブラリについてほとんど知らない場合、断定を避けたり、検索したり、ソースを読んだりする傾向があります。ところが、ライブラリの _以前のバージョン_ についてよく知っている場合、モデルは断定します。**自信は正しさではなく学習データの量に合わせて調整されている** ため、最悪のケースは、データ量が多く変化も激しい場合です。エージェントは古くなったコードを流暢に書き、疑いの兆しを一切見せません。

これこそが、上のブロックで Next.js が警告しているケースです。Next.js は学習データに最も多く含まれている React フレームワークであり、ベンダーがエージェント向けに警告を出力すべきだと判断するほど、多くの変更をリリースしてきました。

### どう対処するか

モデルの記憶を直すことはできませんが、その誤りのコストを安くすることはできます。

- **両者が対立するときは、人気よりも安定性を優先する。** モデルがうろ覚えでも 5 年間安定している API のほうが、モデルが完全に記憶違いをしている書き直された API よりも優れています。
- **バージョンのずれはコンパイラーに捕まえさせる。** 非推奨 API のエラーが高くつくのは、型のない境界においてだけです。これがエンドツーエンドの型を採用する本当の理由であり、よく挙げられる理由よりも強力です。
- **エージェントが読むドキュメントのバージョンを固定し、手元に置く。** Next 自身の推奨は、Web ではなく `node_modules` 内のガイドを読むことです。ローカルのドキュメントはインストール済みのバージョンと一致しますが、2024 年のブログ記事は一致しません。
- **新しい依存関係は信頼しない。** これは正しさだけでなくセキュリティの問題でもあるため、後で詳しく説明します。

## エージェントスタックテスト

依存関係ごとに 4 つの問いを 0、1、2 で採点し、合計 8 点満点とします。この記事の執筆時点で存在しなかったライブラリにも適用できます。それこそが、リストではなくテストにする意味です。

### 1. 制約：誤った使い方をコンパイルエラーにできるか？

- **0**：ライブラリが `any` を返す、設定が文字列キーで書かれている、またはエラーが実行時にしか表面化しない。
- **1**：型はあるが参考程度で、キャストすれば誤った呼び出しもコンパイルを通る。
- **2**：誤った使い方は型エラーになる。誤ったプログラムは表現できない。

### 2. 収束：その作業をこなす明白な方法が 1 つだけあるか？

エージェントは模倣によって動くため、同等の API が 6 つあるライブラリでは、コードベースがすでに使っている方法をエージェントが選ぶ確率は 6 分の 1 になります。

- **0**：同等の方法が多数あり、どれも実際によく使われていて、どれも学習データに含まれている。
- **1**：推奨される方法があるが、広く使われている旧来の代替手段も残っている。
- **2**：方法は 1 つだけで、代替手段は非推奨にとどまらず削除されている。

### 3. 検証可能性：エージェントが動作することを自分で証明できるか？

- **0**：正しさは、人間が実行中のアプリを見ることでしか確認できない。
- **1**：テストは可能だが、準備に手作業が多く、エージェントは実行しない。
- **2**：エージェントがすでに実行しているコマンドで確認できる。

### 4. 鮮度：モデルの記憶は最新か？

- **0**：この 1 年以内にメジャーバージョンの大きな変更があり、公開 API の名前変更や削除が行われている。
- **1**：最近マイナーな変更があった、またはモデルが学習したドキュメントが部分的に誤りになっている。
- **2**：公開 API が十分長く安定していて、記憶から書いたコードがそのまま動く。またはライブラリが、インストール済みのバージョンと一緒に機械可読のドキュメントを提供している。

**スコアの読み方。** 7〜8 点なら、エージェントに監督なしで任せられる依存関係です。4〜6 点なら、型の境界やテストで囲めば機能します。3 点以下なら、自分で管理するインターフェースでラップするか、すべての呼び出し箇所を人間が書くことを受け入れるかのどちらかです。

このテストは、依存関係の品質ではなく、意図的にその _形_ を評価しています。優れたライブラリでもここでは低い点になることがあり（書き直しの途中にある優れたライブラリは鮮度で 0 点です）、平凡なライブラリが高い点を取ることもあります。測っているのはエージェントとの相性であり、価値ではありません。

## レイヤーごとにテストを適用する

ここからは、私たちが提供しているスタックを、コストがかかる部分も含めて率直に採点します。あなたの答えは違うかもしれませんが、応用できるのは考え方のほうです。

### 言語：TypeScript、strict、抜け道なし

**スコア：8/8。** この一覧のほかのすべてが、この選択に依存しています。

strict モードは目標ではなく最低ラインです。エージェントにとって重要な設定は、多くの人が無効にしているものです。暗黙の `any` を許さないこと、未検査のインデックスアクセスを許さないこと、非 null アサーションを許さないこと。これらのフラグはそれぞれ、自信満々だが誤ったエージェントの出力の一群を、実行時の想定外の動作から、エージェントがターンを終える前に目にする赤い波線へと変えます。

バージョンよりも設定のほうが重要です。設定のゆるい最新の TypeScript は、厳格に設定された古い TypeScript よりもエージェントの作業に向きません。

### ランタイムとフレームワーク：Cloudflare Workers、TanStack Start、React

**スコア：6/8。** 制約 2、収束 1、検証可能性 2、鮮度 1。

ここは正直に言って弱点であり、Next.js が警告しているのと同じ弱点です。React のコアは十分長く安定しているため、モデルの記憶は信頼できます。しかし、その周りのフレームワーク層はそうではなく、鮮度で 1 点を失っています。

現在の公開アプリケーションは、Cloudflare Workers 上で React と TanStack Start を使用しています。ローカルのツールチェーンは Bun と Vite+ が提供します。エージェントは、フレームワークやデプロイのコードを変更する前に、インストール済みパッケージのドキュメントと、固定された公式の TanStack Start および Cloudflare のスキルを読む必要があります。

収束で 1 点を失うのは、ルートローダー、サーバー関数、クエリキャッシュ、通常の HTTP エンドポイントがそれぞれ異なる責務を持つためです。このリポジトリは、それぞれをどこに置くべきかを示しています。ルートファイルはナビゲーションを調整し、機能のユースケースが処理を担い、ベンダー連携がサービスの設定を担います。

### API 層：TanStack Start のサーバー関数、エンドツーエンドで型付け

**スコア：7/8。**

重要なのはフレームワークではなく、ハンドラーの入力と出力の型が呼び出し側から見えることです。ルートの形が変わると、誤りとなったすべての呼び出し箇所がコンパイルに失敗します。

ここで競合他社が示す助言では、特定の RPC ライブラリの名前が挙がるのが普通です。しかしそれは、この性質を実現する方法の 1 つにすぎず、性質そのものではありません。エンドポイントを変更すると呼び出し箇所でビルドが壊れる方法であれば、どれでも条件を満たします。満たさないのは、呼び出し箇所で手作業で型を付けた JSON ルートへの素の `fetch` です。エージェントの誤った前提がそのままコンパイルを通り、リリースされ、顧客によって発見される境界だからです。

**型のない API 境界は、エージェントの誤りが生き延びる場所です。**

### データベース：Cloudflare D1 上の Drizzle

**スコア：8/8。**

スキーマは TypeScript で書かれているので、マイグレーションの元にも型の元にもなり、ずれが生じうる 2 つ目の成果物が存在しません。存在しないカラムを参照するクエリは、500 エラーではなくコンパイルエラーになります。

型付け以外にも重要な性質が 2 つあります。Drizzle のクエリは SQL に似ているため、既存の SQL の知識がそのまま活かせます。Cloudflare D1 は SQLite のセマンティクスを使うため、エージェントは Postgres 固有のクエリをコピーするのではなく、D1 アダプターとインストール済みのドキュメントに従う必要があります。バージョン管理されたマイグレーションと分離されたローカルバインディングにより、リモート操作を行う前に変更をレビューできます。

### 検証：すべての外部境界に Zod

**スコア：8/8。** 多くのスタックが省略する層であり、最も早く元が取れる層です。

型は、あなたが信じていることを記述します。スキーマはそれを確認します。データがプロセスに入ってくるすべての場所（HTTP のボディ、環境変数、Webhook のペイロード、サードパーティのレスポンス、データベースの JSON カラム）は、誰も検証していない約束を型システムが信用している場所です。

エージェントの作業では、これは人間の作業以上に重要です。連携を実装する人間は、過去に痛い目を見ているので、ペイロードを疑ってかかる傾向があります。エージェントは正常系を完全な自信を持って書きます。学習データに含まれているのは、主に正常系だからです。境界にスキーマを置けば、その楽観は、フィールド名を示すメッセージ付きの、捕捉されたエラーに変わります。

### 認証：リポジトリ内の Better Auth

**スコア：7/8。**

エージェントにとって重要な性質は、実装が不透明なホスト型サービスの呼び出しではなく、あなたが所有するソースコードであることです。エージェントは、セッションがどのように発行されるかを読み、トークンが検証される場所までたどり、差分でレビューできる形で拡張できます。

ホスト型の認証は、料金の議論とは別の構造的な理由で、ここでは点数が下がります。ロジックの重要な半分が、エージェントが読めない API 境界の向こう側にあるため、動作に関する疑問は推測かドキュメントの確認で終わり、カスタマイズはすべて変更ではなく連携の作業になります。

失う 1 点は鮮度です。これはまだ統合が進んでいる途中のエコシステムにある変化の速いライブラリなので、その API に関するモデルの記憶は信頼できません。これはテストがきちんと役目を果たしている好例です。ライブラリは正しい選択でありながら、1 つの軸では低い点になることがあります。どの軸かがわかれば、どこにガードレールを置くべきかがわかります。

### スタイリング：Tailwind

**スコア：7/8。**

よく挙げられる理由は学習データの量です。より良い理由は構造上のものです。スタイルは対象の要素そのものに書かれるので、**エージェントが開くことを覚えておかなければならない 2 つ目のファイルがありません**。別のディレクトリにあるスタイルシートは同期の義務を生みます。エージェントの失敗のしかたは、スタイリングが下手なことではなく、2 か所のうち 1 か所だけを更新してしまうことです。

これはスタイリングに限らず一般化できます。同じ理由から、テストや型を同じ場所に置く構成が有利になり、1 つの変更を、エージェントが見る理由のない場所にも反映しなければならないパターンは不利になります。

### 国際化：パリティチェック付きの use-intl

**スコア：7/8**。この項目がここにあるのは、実は i18n とはあまり関係のない理由からです。

翻訳は、表に出ない失敗の典型です。エージェントが機能を追加して英語の文字列を書くと、ほかのロケールではキーが欠けた状態になります。何もクラッシュせず、テストも通ります。そしてそのバグは、それを明確に報告できない顧客にだけ届きます。

解決策はより良いライブラリではなく、キーが 1 つでも欠けていれば `bun run check:i18n` が CI を失敗させることです。システムの中で同じ形をした部分（ある場所には存在するのに、別の場所では黙って欠けている部分）には、すべて同じ対策が必要です。対策がない限り、それはエージェントにもあなたにも見えません。

### 決済とメール：Polar、Resend

**スコア：6/8** と **7/8**。

決済の連携が点を失うのは、品質ではなく収束の面です。このアプリケーションは Polar のチェックアウトと検証済みの Webhook を使い、購入とライセンスキーの処理は機能のユースケースで扱っています。その実装と、プロバイダーが文書化している再試行の動作に従ってください。Resend は、ローカライズされたメールテンプレートを Worker から配信します。

Webhook には個別の警告が必要なので、後述します。

### テスト：Vitest と Playwright

**スコア：8/8**。ほかのすべてのスコアを活かせるようにするのがこの層です。

重要なのは、数値としてのカバレッジではありません。`bun run check && bun run test:coverage` が存在し、0 か 1 で終了し、エージェントが方法を教わらなくても実行できることです。ここより上の項目はすべて、エージェントが表現できるものを狭めるためのものでした。この項目は、それでもすり抜けたものを捕まえるためのものです。

## 依存関係の数は、エージェントにとっての表面積

どの依存関係も、モデルが誤って記憶しているかもしれない API です。そう考えると、通常はバンドルサイズやサプライチェーンの観点から語られる「依存関係が多すぎる」という議論が、正しさの議論にもなります。

ランタイムの依存関係は `package.json` に記載されています。重要なのは数ではなく形です。ほぼすべてが、エンドツーエンドで型付けされているか、私たちが所有する境界でラップされています。そのため、それらに関する誤った前提は、本番環境で失敗するのではなく、コンパイルに失敗します。

いまでは、注意すべき 2 つ目の理由があります。それはセキュリティです。2025 年 10 月から 2026 年 3 月にリリースされたフロンティアモデルは、**4.62% から 6.10%** の割合でパッケージ名のハルシネーションを起こすと測定されています（[arXiv](https://arxiv.org/pdf/2605.17062)）。攻撃者は、そうした架空の名前を公開レジストリに登録して待ち構えています。これは **スロップスクワッティング** と呼ばれる攻撃です（[Mend](https://www.mend.io/blog/the-hallucinated-package-attack-slopsquatting/)）。

実践的なルールはこうです。**エージェントが追加した依存関係は、見知らぬ人からの未レビューのプルリクエストです。** パッケージが実在すること、名前が似て非なるものではなく期待どおりであること、そして本当に必要だったことを確認してください。ロックファイルと、`package.json` の変更に対するレビュー手順があれば、ほとんど手間をかけずにリスクの大部分をカバーできます。

## エージェントに単独で任せてはいけないもの

SaaS の一部には、共通する性質があります。**誤ったバージョンでも正しく見え、テストに通り、デモでも正しく動き、テストスイートが再現しない条件下でのみ失敗する** という性質です。委任するのが危険なのは、難しさではなく、この性質のためです。

| 対象                               | 誤ったバージョンがレビューを通過する理由                                     |
| ---------------------------------- | ---------------------------------------------------------------------------- |
| セッションとトークンの処理         | ログインが動いても、有効期限、ローテーション、失効については何も証明されない |
| 決済の Webhook                     | 冪等でないハンドラーは、再試行が届くまでは正しく動く                         |
| データベースのマイグレーション     | 元に戻せるかどうかやデータの損失は、ロールバックするまで見えない             |
| テナントの分離                     | クエリはテスト用のテナントでは正しく、2 つ目のテナントでは間違っている       |
| シークレットを読み取るあらゆる処理 | トークンをログに出力する変更は 1 行で済み、完璧に動作する                    |

最もわかりやすいのは Webhook です。Stripe は 2xx 以外のレスポンスに対して再試行するため、最初の配信では正しく課金し、再試行で再び課金するハンドラーでも、エージェントが思いつくようなテストにはすべて通ります。そのテストを書くには、失敗のパターンをあらかじめ知っている必要があるからです。これはモデルの能力の限界ではありません。エージェントが書くテストスイートは学習データに含まれる失敗パターンを反映しており、冪等性のバグは、実際に損失を生む頻度に比べて学習データの中で過小に表れているということです。

これらのパスは `AGENTS.md` で人間によるレビュー専用として明記し、必須レビュアーの設定で裏付けてください。そうすれば、意図は信頼に頼るのではなく強制されます。

## よくある質問

<Accordions>

<Accordion title="2026 年の AI コーディングエージェントに最適な技術スタックは何ですか？">

エンドツーエンドの TypeScript に、型付きのデータベース層、すべての外部境界でのスキーマ検証、リポジトリ内に置かれた認証、そして型チェック、lint、テストを 1 つで実行するコマンドを組み合わせたものです。個々のライブラリよりも、誤った使い方がコンパイルエラーになるかどうかのほうがはるかに重要です。採用する前に、どの候補も制約、収束、検証可能性、鮮度の観点で採点してください。

</Accordion>

<Accordion title="人気のフレームワークを選ぶと AI コーディングエージェントの役に立ちますか？">

以前ほどではなく、まったく役に立たないこともあります。人気があればモデルの学習データは増えますが、それは学習時点のバージョンについてだけです。モデルの再学習よりも速く破壊的変更をリリースするフレームワークからは、自信に満ちて流暢な、しかし誤ったコードが生まれます。ライブラリの変化が速くなると、データ量よりも安定性のほうが重要になります。

</Accordion>

<Accordion title="エージェントがもう存在しない API を使ったコードを書くのはなぜですか？">

学習したバージョンを思い出して書いているからです。広く使われている 8 つのライブラリを対象にした研究では、非推奨 API の使用率が 25% から 38% と測定され、その原因は古くなったパラメトリック知識と、現在の API を参照する手段がないことにあるとされています。これを最も安く修正できるのは型チェッカーです。だからこそ、この問題は型のない境界で生き残ります。

</Accordion>

<Accordion title="依存関係の選定を AI エージェントに任せてもよいですか？">

各パッケージが実在することを確認せずに任せてはいけません。2025 年 10 月から 2026 年 3 月にリリースされたフロンティアモデルは、4.62% から 6.10% の割合でパッケージ名のハルシネーションを起こしており、攻撃者はいまや、そうした架空の名前を公開レジストリに登録しています。これはスロップスクワッティングと呼ばれる攻撃です。エージェントが追加した新しい依存関係はすべて、見知らぬ人からの未レビューのプルリクエストとして扱ってください。

</Accordion>

<Accordion title="AI コーディングエージェントにはモノレポのほうが適していますか？">

README に書かれているだけでなく、ツールによって境界が強制されている場合に限ります。パッケージ境界をまたぐとビルドが失敗するモノレポは、エージェントにアーキテクチャを数秒で教えます。慣習だけでまとまっているモノレポでは、正しいコードを間違ったパッケージに置ける場所がエージェントにとって増えるだけです。

</Accordion>

<Accordion title="SaaS のうち、エージェントに単独で書かせてはいけない部分はどこですか？">

もっともらしく見える誤りが高くつき、しかも表に出ない部分すべてです。セッションとトークンの処理、決済の Webhook、データベースのマイグレーション、テナントの分離、そしてシークレットを読み取るあらゆる処理がこれに当たります。これらには共通の性質があります。誤ったバージョンでもテストに通り、デモでも正しく動き、テストスイートが再現しない条件下でのみ失敗するという点です。

</Accordion>

<Accordion title="エージェントに適した API には tRPC や oRPC が必要ですか？">

必要なのはネットワーク境界を越えて伝わる型であり、具体的なライブラリは二の次です。変更されたエンドポイントを呼び出すクライアントがコンパイルに失敗する方法であれば、どれでも構いません。うまくいかないのは、型のない JSON ルートへの素の fetch です。誤った前提がそのままコンパイルを通り、本番環境に届いてしまう境界だからです。

</Accordion>

<Accordion title="エージェントを活用するコードベースでは、依存関係はいくつから多すぎますか？">

パッケージの数ではなく、表面の数を数えてください。どの依存関係も、モデルが誤って記憶している可能性のある API です。したがって問題は、そのうちいくつが重要な役割を担い、なじみがなく、検証されていないかです。厳密な型とテストで守られた依存関係のコストはわずかです。型のないデータをビジネスロジックに返す依存関係は、今後の変更のたびにコストを生みます。

</Accordion>

<Accordion title="Tailwind は本当に AI コーディングエージェントの役に立ちますか？">

はい。ただし理由はスタイル上のものではなく構造上のものです。スタイルは対象の要素そのものに書かれるので、エージェントが開いて更新することを覚えておかなければならない 2 つ目のファイルがありません。同じ理由から、テストや型を同じ場所に置く構成が有利になり、1 つの変更を、エージェントが開く理由のないファイルにも反映しなければならないパターンは不利になります。

</Accordion>

<Accordion title="エージェントがうまく働くようにスタックを切り替えるべきですか？">

ほとんどの場合、その必要はありません。移行コストは確実にかかり、得られる効果には限りがあります。一方で、既存のスタックに厳密な型、境界での検証、検証用の 1 つのコマンドを追加するのは安価で、すぐに効果が出ます。スタックはどのみち変更する予定があるときに変更し、エージェントとの相性は変更の理由ではなく、決め手に迷ったときの判断材料にしてください。

</Accordion>

</Accordions>
