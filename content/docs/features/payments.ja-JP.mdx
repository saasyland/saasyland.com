決済は `@polar-sh/better-auth` プラグインを通じて Polar で処理されます。このプラグインは、`src/integrations/better-auth/auth.server.ts` の `plugins` に、直後に続く専用のプラグインと一緒に並んでいます。

```ts title="src/integrations/better-auth/auth.server.ts"
    polar({
      client: polarCore,
      use: [portal(), webhooks({ onPayload: handlePolarEvent, secret: env.POLAR_WEBHOOK_SECRET })],
    }),
    {
      hooks: {
        before: [
          {
            handler: requireVerifiedEmail,
            matcher: ({ path }) => path?.startsWith(ROUTES.API_AUTH_POLAR.CUSTOMER) === true,
          },
        ],
      },
      id: "polar-verified-customer",
    },
```

プラグインはカスタマーポータルと Webhook を追加し、Webhook は `rateLimit.customRules` の `[ROUTES.API_AUTH_POLAR.WEBHOOKS]: false` によって Better Auth のレート制限の対象外になります。購入セッションはプラグインでは作成しません。プラグインの `checkout()` はアカウントの ID だけで購入セッションを作成するため、Polar がサインイン済みの購入者にメールアドレスをもう一度尋ねることになるからです。Better Auth は HTTP に対してパスを閉じないため、`src/integrations/better-auth/__test__/auth.server.polar.integration.test.ts` がプラグインのチェックアウトのパスが 404 を返すことを確認し、プラグインに `checkout()` を追加すると失敗します。購入セッションは、代わりに注文モジュールで Polar SDK を使って作成します（[チェックアウト](#checkout)を参照）。

2 つ目の要素 `polar-verified-customer` は独立したプラグインで、`/customer/` 以下のすべてのエンドポイントの前に `requireVerifiedEmail`（`auth.hooks.ts`）を実行します。そのため、アカウントのアドレスが確認されるまで、カスタマーポータルは `403 EMAIL_NOT_VERIFIED` を返します（[メール確認](/docs/features/email-verification)）。

`src/integrations/polar/polar.config.ts` は、`POLAR_ACCESS_TOKEN` と `POLAR_SERVER` からプラグインが使う `polarCore` を作成し、その上に購入セッション、ライセンスキー、注文、商品のサービスをまとめた `polar` を構築します。`POLAR_ORGANIZATION_ID` は、組織を指定する Polar の呼び出しすべての対象を組織に絞り込みます。その一覧は[環境とバインディング](/docs/reference/environment)にあります。`src/integrations/polar/polar.constants.ts` は Polar 固有の値を保持します。`POLAR_ORDER_STATUS`、`POLAR_SUBSCRIPTION_STATUS`、`POLAR_RECURRING_INTERVAL`、`POLAR_LICENSE_KEY_STATUS`、`POLAR_WEBHOOK_EVENT` はそれぞれ SDK の型と照合されており、ほかに `POLAR_CHECKOUT_ID_PLACEHOLDER`、`POLAR_CUSTOMER_SESSION_TOKEN_PARAM` と、Polar の ID を保持するすべての列の長さである `POLAR_ID_MAX_LENGTH` があります。このファイルは環境を読み取らないため、ブラウザーとブラウザーテストのスイートもこれをインポートします。Polar のパスである `API_AUTH_POLAR` と `API_AUTH_CUSTOMER_PORTAL` は `src/routes.ts` にあります。[Polar の設定](/docs/getting-started/polar-setup)では、このコードが Polar に求める商品、ライセンスキー、同意のチェックボックス、税の扱い、Webhook、トークンを説明しており、`bun run polar:verify:<environment>` がそれらを確認します。

## チェックアウト [#checkout]

`src/modules/order/order.checkout.ts` の `createCheckout` は、サイトが開始するすべてのチェックアウトを `polar.checkouts.create` で作成します。サーバー関数のコンテキストからサインイン中のアカウントを、引数から `{ locale, productId, returnPath, successPath }` を受け取り、次の処理を行います。

1. リクエストのオリジンを `trustedRequestOrigin`（`src/lib/request-origin.ts`）で読み取ります。この関数は、ビルドモードについて `appHostsForMode` が挙げていないホストや、開発とテスト以外での平文の HTTP を `FORBIDDEN` で拒否します。読み取ったオリジンは、チェックアウトをフレームに表示してそのメッセージを受け取れる唯一のページとして `embed_origin` に指定します。これにより、`openCheckoutOverlay`（`src/lib/checkout-overlay.ts`）がチェックアウトをページに重ねて表示できます（[ページに重ねて開くチェックアウト](/docs/features/licences#the-checkout-over-the-page)）。
2. チェックアウトをアカウントに紐付け（`external_customer_id`）、そのメールアドレスと名前（`customer_email`、`customer_name`）を入力済みにするため、チェックアウトのフォームはそれらが入った状態で開きます。`cf-connecting-ip` から得た購入者の IP アドレス（`customer_ip_address`。Better Auth の `getIP` で読み取り）も渡します。
3. `polarCheckoutLanguage` が `locale` に対して返す言語で Polar のページを開き、`locale` そのものは `metadata` の `ORDER_CHECKOUT_METADATA.LOCALE`（`order.constants.ts`）に書き込みます。訪問者がアフィリエイトリンクから来た場合は、アフィリエイトの紹介情報もその隣に入ります（[アフィリエイトプログラム](/docs/features/affiliates)）。Polar はメタデータを注文にコピーします。
4. `returnPath` を `return_url` として渡し、Polar がそのページへの戻るボタンを表示するようにします。また、購入者の言語にした（`localizePathname`）`successPath` を成功 URL として渡し、パス自身の検索パラメーターの前に `checkoutId={CHECKOUT_ID}` を付けます。Polar は `{CHECKOUT_ID}`（`POLAR_CHECKOUT_ID_PLACEHOLDER`）をチェックアウト ID に置き換えます。
5. 呼び出し側が独自の条件（`allow_discount_codes`、`metadata`、`prices`）を渡さない限り、購入者は Polar の割引コードを入力でき、Polar で設定した商品の価格が請求されます。最後に `{ checkoutId, url }` を返します。

`src/modules/order/use-cases/start-checkout.ts` の `startCheckout` は、任意の Polar 商品のチェックアウトを開始するサーバー関数です。その入力である `orderZodSchemas.startCheckout`（`Order["startCheckout"]`）は、商品の Polar ID を UUID として受け取り、2 つのパスはサイト内にとどまるよう `callbackPathSchema` で検証します。`authorized()` を実行するため、購入できるのはサインイン済みのアカウントだけです。また、機能が独自のチェックアウトで販売する商品は、Polar に問い合わせることなく `FORBIDDEN` で拒否します。その判定を行う `hasOwnCheckout` は `PRODUCTS_WITH_OWN_CHECKOUT` を読み取り、その唯一の要素はライセンスの `POLAR_PRODUCT_IDS` です。ライセンス独自の `startCheckout` は、アカウントのライセンスを確認し、プランの価格を決めてから、独自の条件で `createCheckout` を呼び出します（[ライセンス](/docs/features/licences#starting-the-checkout)）。このサイトには、ほかの商品を提供するページはまだありません。

どちらのサーバー関数も `authorized()` の前に `withRateLimit(CHECKOUT_RATE_LIMIT_KIND, CHECKOUT_RATE_LIMIT)` を実行し、どちらが開始したかにかかわらず、クライアントごとに 1 分あたり <RepositoryFact name="checkoutsPerMinute" /> 件までのチェックアウトを許可します。チェックアウトはそれぞれ組織のトークンを使った Polar API へのリクエストであり、そのトークンのレート制限はすべての購入者で共有されるためです。

## Webhook [#webhooks]

Polar は `/api/auth/polar/webhooks` にイベントを送信します。プラグインは `POLAR_WEBHOOK_SECRET` で署名を検証し、各イベントを `src/integrations/polar/polar.webhooks.ts` の `handlePolarEvent` に渡します。同じファイルの `POLAR_EVENT_HANDLERS` は各イベントが届くコードを列挙し、各要素は、処理するイベントと、それを処理する関数を指定します。

```ts title="src/integrations/polar/polar.webhooks.ts"
export interface PolarEventHandler {
  readonly events: readonly models.WebhookEventType[]
  readonly handle: (event: webhooks.WebhookPayload) => Promise<void>
}
```

- `handlePolarEvent` は、そのイベントの種類を列挙しているすべての要素の `handle` を同時に実行し、すべての完了を待ちます。
- いずれかが失敗しても、`handlePolarEvent` は他のハンドラーの完了を待ち、どのハンドラーも書き込みの途中で止まらないようにしてから、すべての失敗をまとめた `AggregateError` で reject します。プラグインは 500 を返し、Polar は後でイベントを再送します。そのため、各ハンドラーは同じイベントで 2 回実行されても安全でなければなりません。Polar は失敗し続けるエンドポイントを無効にし、`polar:verify` は無効になったエンドポイントを報告します。
- どの要素にも列挙されていないイベントは受領され、どこにも渡されません。
- `POLAR_EVENTS` は、すべての要素のイベントを重複なく並べ替えてまとめたものです。Polar の Webhook エンドポイントはこれらのイベントだけを過不足なく送信する必要があり、`polar:verify` が両者を比較します。
- 最初の 2 つの要素は、`ORDER_WEBHOOK_EVENTS`（`order.constants.ts`）と `SUBSCRIPTION_WEBHOOK_EVENTS`（`subscription.constants.ts`）のイベントで注文とサブスクリプションを D1 にコピーし（[コピーの書き込み](#writing-the-copies)を参照）、3 つ目は `LICENSE_WEBHOOK_EVENTS` のイベントでライセンスを付与し、取り消します（[ライセンス](/docs/features/licences#webhooks-and-licences)を参照）。ライセンスや注文のコピーがないプロジェクトでは、それらのファイルを指す要素が外れます。

`polar:verify` は Worker の外の Bun で実行され、`POLAR_EVENTS` を読み取ります。そのため、`polar.webhooks.ts` は定数だけをインポートします。ハンドラーは、イベントが届いたときに自分のコードを読み込みます。

```ts title="src/integrations/polar/polar.webhooks.ts"
const { licenseWebhookHandlers } = await import("~/src/modules/license/license.webhooks")
```

`src/integrations/polar/__test__/polar.webhooks.test.ts` は Bun で `polar.webhooks.ts` をインポートし、そのインポートが Worker のランタイムに到達すると失敗します。

## D1 の注文とサブスクリプション [#orders-and-subscriptions-in-d1]

Polar のエリアは、Polar の注文とサブスクリプションのコピーを D1 の 2 つのテーブル、`order`（`src/modules/order/`）と `subscription`（`src/modules/subscription/`）に保持します。これにより、一覧、検索、アクセスチェックが SQL で読み取れ、Polar の応答が遅いときも動き続けます。情報源はあくまで Polar です。各行は Polar の ID で保存された Polar のレコードであり、Polar の Webhook からのみ書き込まれ、手作業で編集することはありません。こうしたミラーテーブルが従うルールは[モジュール](/docs/conventions/modules#tables-that-mirror-a-provider)にあります。

| テーブル       | 列                                                                                                                                                                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `order`        | `id`、`user_id`、`customer_id`、`product_id`、`subscription_id`、`status`（`ORDER_STATUSES`）、`currency`、`total_amount`、`refunded_amount`、`invoice_number`、`discount_id`、`discount_code`、`discount_name`、`discount_amount`、`billing_country`、`description`、`placed_at`、`changed_at`       |
| `subscription` | `id`、`user_id`、`customer_id`、`product_id`、`product_name`、`status`（`SUBSCRIPTION_STATUSES`）、`amount`、`currency`、`recurring_interval`（`SUBSCRIPTION_RECURRING_INTERVALS`）、`recurring_interval_count`、`current_period_end`、`cancel_at_period_end`、`started_at`、`ended_at`、`changed_at` |

- `id`、`customer_id`、`product_id`、`subscription_id` は Polar の ID で、Polar からコピーする列はすべて Polar のフィールド名を使います。Polar のイベントは順不同で届くことがあるため、`subscription_id` には外部キーがありません。
- `user_id` はアカウントを紐付け、アカウントを持たない顧客では空のままです。アカウントを削除しても、その注文とサブスクリプションは残り、`user_id` が空になります（`ON DELETE SET NULL`）。
- 金額は、Polar が送るとおり通貨の最小単位で表します。`description` は Polar が請求書に記載した注文の購入内容、`product_name` は Polar が最後に伝えたサブスクリプションの商品名です。
- `discount_id`、`discount_code`、`discount_name` は Polar が適用した割引で、注文の `discount_id` とその `discount` から取ります。`discount_amount` はその割引が小計から差し引いた額です。`billing_country` は注文の請求先住所の国で、ISO 3166-1 alpha-2 のコードです。割引や請求先住所のない注文では空になり、`discount_amount` が空になるのは、これらの列ができる前にコピーされた注文だけです（[注文と顧客](/docs/features/orders#discounts-and-billing-countries-of-older-orders)を参照）。
- `placed_at` は Polar が注文を作成した時刻です。`changed_at` は行が保持している Polar のレコードのバージョンで、Polar の `modified_at`、一度も変更されていないレコードでは Polar の `created_at` です。行自身の `created_at` と `updated_at` は、D1 が行を書き込んだ時刻を記録します。
- インデックスは、これらのコピーの用途である一覧を支えます。`order_user_placed_at_idx` はアカウントの注文を、`order_status_placed_at_idx` はあるステータスの注文を、いずれも注文された日時の順に、`subscription_user_status_idx` はアカウントのサブスクリプションをステータス別に、`subscription_status_current_period_end_idx` はあるステータスのサブスクリプションを期間の終了日時の順に引きます。
- `status` には Polar の値をそのまま保存します。トライアルが支払いなしで終わったときに Polar が設定する `trial_ended` も含みます。サブスクリプションのステータスでアクセスを与える処理はまだありません。そうする処理は `trialing` と `active` だけを継続中のサブスクリプションとして数えるので、`trial_ended`、`past_due` などのステータスが継続中とみなされることはありません。

### コピーの書き込み [#writing-the-copies]

`POLAR_EVENT_HANDLERS` の最初の 2 つの要素（[Webhook](#webhooks)を参照）は、それぞれイベントが届いたときに自分のユースケースを読み込みます。

| イベント                                                         | ユースケース                                                                        |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `order.created`, `order.updated`, `order.paid`, `order.refunded` | `src/modules/order/use-cases/record-order.ts` の `recordOrder`                      |
| `subscription.created`, `subscription.updated`                   | `src/modules/subscription/use-cases/record-subscription.ts` の `recordSubscription` |

- 各ユースケースは Polar のレコード（`models.Order` または `models.Subscription`）を受け取り、1 つの文で書き込みます。Polar の ID で行を挿入し、行がすでにある場合は、保存されている `changed_at` がレコードのものより後でないときだけ更新します。新しいバージョンは反映され、遅れて届いた古いバージョンは何も変えず、2 回届いた同じバージョンは同じ値で書き直されます。同じ `modified_at` を持つ 2 つの異なる状態では、最後に書き込まれたほうが、Polar がレコードを再び変更するまで残ります。
- `recordOrder` は割引と請求先の国を `polarOrderTerms`（`src/modules/order/order.polar.ts`）から取得し、`scripts/backfill-order-terms.ts` も同じものを使います。請求先住所のない後のバージョンは、すでにコピーされた国を保ちます。
- 同じ文が、`src/integrations/polar/polar.customers.ts` の `polarCustomerAccount` で `user_id` を埋めます。これは ID が顧客の `external_id` と一致するアカウントで、`external_id` は `createCheckout` がすべてのチェックアウトに設定します（[チェックアウト](#checkout)）。顧客に `external_id` がない場合や、その ID のアカウントがない場合（アカウントが削除された場合など）は空のままです。
- ライセンスも `order.paid` と `order.refunded` を処理します。コピーもこれらを受け取るため、Polar がそれらについて `order.updated` も送るかどうかに関係なく、支払いと返金を保持します。`handlePolarEvent` は両方のハンドラーを同時に実行します。コピーが失敗すると配信は 500 を返し、Polar の再試行は両方の書き込みを繰り返しますが、どちらかがすでに書き込んだ内容は変わりません。
- 管理ダッシュボードは注文のコピーを読み取り、ライセンスのない支払い済みのライセンス注文を一覧表示し（[ライセンス](/docs/features/licences#orders-that-match-no-account)を参照）、売上を集計します（[ダッシュボードの売上](#revenue-on-the-dashboard)を参照）。サブスクリプションのコピーを読み取るページはまだありません。

## カスタマーポータル

`ROUTES.API_AUTH_CUSTOMER_PORTAL`（`/api/auth/customer/portal`）は、サインイン中のアカウントの Polar カスタマーポータルを開きます。`/app/license` のライセンスカードがここにリンクしています。

## ダッシュボードの売上 [#revenue-on-the-dashboard]

`order` の権限ステートメント（`read`、`update`、`refund`）は `APP_STATEMENTS`（`src/integrations/better-auth/auth.access.ts`）にあり、決済のエリアは `DASHBOARD_PANELS`（`custom/admin/dashboard/panels.tsx`）の項目としてダッシュボードに **売上** パネルを追加します。そのクエリである `src/modules/order/use-cases/get-revenue.ts` の `getRevenue` は `order: ["read"]` をチェックし、期間内の支払い済みの注文のコピーを、返金を差し引いて通貨ごとに集計します。何を数えるかは[管理ダッシュボード](/docs/features/admin-dashboard#revenue)で説明しています。ライセンスのエリアの `get-unlicensed-orders` も `order: ["read"]` をチェックします。コピーを読む管理画面は[注文と顧客](/docs/features/orders)で説明しています。注文を更新したり返金したりするユースケースはまだなく、返金と出金は Polar で行います。
