Każdy obszar deklaruje swoje uprawnienia i role, którym je przyznaje, w `src/areas/<area>.access.ts`, a `src/integrations/better-auth/auth.access.ts` buduje z nich mechanizm kontroli dostępu Better Auth i role (zobacz [Role i uprawnienia](/docs/guides/roles-and-permissions)). Z tych samych definicji korzysta serwer (`authorized`, guardy tras) i klient Better Auth.

## Role

| Rola          | Kod        | Uprawnienia                                                                                                                                               |
| ------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Administrator | `admin`    | Wszystkie poniższe deklaracje aplikacji, które każdy obszar przyznaje administratorom, oraz administracyjne deklaracje Better Auth dla `user` i `session` |
| Klient        | `customer` | Brak. Klienci mogą wywoływać funkcje serwerowe, które wymagają jedynie sesji.                                                                             |

Nowi użytkownicy otrzymują rolę `customer` (`DEFAULT_ROLE_CODE` w `auth.roles.ts`).

## Gdzie sprawdzane są uprawnienia

Każdy przypadek użycia z `src/modules/*/use-cases/`, pogrupowany według wywołania `authorized`, które uruchamia; `authorized()` wymaga sesji, ale żadnego uprawnienia:

<RepositoryTable name="permissionChecks" columns={["Middleware", "Przypadki użycia"]} />

Funkcje serwerowe bez `authorized` uruchamiają `withRequest` lub `withRateLimit` i nie wymagają sesji: <RepositoryFact name="publicUseCases" />. Poza przypadkami użycia `requireAdmin` w layoucie `/admin` i przekierowanie po zalogowaniu sprawdzają `admin: ["access"]` przez `hasPermission`, a `resolveViewer` (`lesson.viewer.ts`) pozwala użytkownikom z `course: ["read"]` oglądać każdą lekcję i pobierać jej materiały niezależnie od poziomu dostępu lekcji.

<RepositoryFact name="uncheckedStatements" /> są zadeklarowane, ale nie sprawdza ich jeszcze żadna funkcja serwerowa.

## Sprawdzanie uprawnienia

Funkcje serwerowe korzystają z middleware, na przykład `authorized({ category: ["read"] })`. Pozostały kod wywołuje `hasPermission`, tak jak guardy tras:

```ts
const isAdmin = (role: string | null | undefined): boolean => hasPermission({ permission: { admin: ["access"] }, role })

export const requireAdmin = async (context: ProtectedRouteContext) => {
  const result = await requireSignedIn(context)
  if (!isAdmin(result.session.user.role)) {
    throw redirect({ replace: true, to: ROUTES.APP })
  }
  return result
}
```
