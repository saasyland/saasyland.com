Los formularios y las tablas son los dos lugares donde más rápido se multiplican las variantes hechas a mano. Hay una sola forma de construir cada uno, tomada de las guías de los propios proveedores en lugar de inventada aquí.

## Formularios

Todos los formularios siguen la [guía de TanStack Form de shadcn](https://ui.shadcn.com/docs/forms/tanstack-form): `useForm` de `@tanstack/react-form`, el esquema Zod del módulo como validador y `Field`, `FieldLabel`, `Input`, `Textarea` o `Select` de shadcn. `src/presentation/components/custom/admin/courses/course-form.tsx`:

```tsx
const form = useForm({
  defaultValues: course === undefined ? NEW_COURSE : toValues(course),
  listeners: { onBlur: validateOnBlur },
  onSubmit: ({ value }) => {
    if (course === undefined) {
      create.mutate(value)
      return
    }
    update.mutate({ ...value, courseId: course.id })
  },
  validators: { onChange: courseZodSchemas.createCourse },
})

return (
  <form
    noValidate
    onSubmit={(event) => {
      void submitForm(event, form)
    }}
  >
```

- **El esquema es el del servidor.** El validador es el mismo `courseZodSchemas.createCourse` con el que parsea la función de servidor, o un `.pick(...)` suyo, como hace `chapter-dialog.tsx` con `chapterZodSchemas.updateChapter.pick({ title: true })`. Nunca escribas un segundo esquema solo para el formulario.
- **Un solo validador, `onChange`.** TanStack Form lo ejecuta en cada cambio y otra vez al enviar. No añadas una copia en `onSubmit`: un error del validador de envío solo se borra cuando cambia su propio campo, así que un error entre campos como `passwordsMustMatch` seguía en rojo después de corregir el otro campo.
- **Valida el campo que el visitante abandona.** `listeners: { onBlur: validateOnBlur }` ejecuta el mismo validador cuando un campo pierde el foco, así que un campo por el que el visitante solo ha pasado recibe su error en ese momento y no con una pulsación posterior en otro campo.
- **Envía mediante `submitForm`.** `submitForm(event, form)` de `src/integrations/tanstack-form/form.submit.ts` detiene el envío propio del navegador y llama a `form.handleSubmit()`. Cuando el formulario no es válido, marca todos los campos como abandonados, de modo que todos los errores aparecen a la vez, y mueve el foco al primer control con `aria-invalid="true"`.
- **`noValidate`.** La validación propia del navegador está desactivada, así que cada mensaje viene del esquema y está traducido.
- **Los valores por defecto se tipan a través de la interfaz del módulo**, como `NEW_COURSE: Course["createCourse"]`.
- **Envía con la mutación.** `onSubmit` llama a `mutate` de las opciones de mutación, y el botón de envío muestra el estado pendiente: `<Button isPending={create.isPending || update.isPending} type="submit">`.

### Cuándo se muestran los errores

Los errores siguen la regla de premiar pronto y penalizar tarde:

- Mientras el visitante escribe en un campo, el campo no muestra ningún error ni tiene `aria-invalid`, aunque el valor todavía no sea válido.
- Cuando el visitante abandona el campo, o intenta enviar el formulario, el campo muestra su error.
- A partir de ese momento el campo se vuelve a validar en cada cambio, así que el error desaparece con la pulsación que corrige el valor.
- La información que premia el progreso, como la lista de requisitos de la contraseña, se actualiza desde la primera pulsación: no es un error.
- Los errores del servidor, como un correo que ya está registrado, se muestran como una notificación.

`isFieldInvalid(field)` de `src/integrations/tanstack-form/form.fields.ts` es el único lugar que lo decide: `field.state.meta.isBlurred && !field.state.meta.isValid`. No copies la comprobación de `isTouched` de la guía de shadcn: TanStack Form establece `isTouched` con la primera pulsación, lo que ponía en rojo una contraseña a medio escribir.

### Campos

Cada campo es un `Field` de shadcn cuyo estado no válido viene de `isFieldInvalid`. De `course-fields.tsx`:

```tsx
<Field data-invalid={isFieldInvalid(field)}>
  <FieldLabel htmlFor={id}>{label}</FieldLabel>
  <Input
    aria-describedby={`${id}-error`}
    aria-invalid={isFieldInvalid(field)}
    className={cn({ "font-mono": isCode })}
    id={id}
    lang={lang}
    name={field.name}
    onBlur={field.handleBlur}
    onChange={(event) => {
      field.handleChange(event.target.value)
    }}
    value={field.state.value ?? ""}
  />
  <FieldMessage field={field} id={id} />
</Field>
```

- `data-invalid`, `aria-invalid` y el elemento de error leen todos `isFieldInvalid(field)`, así que un lector de pantalla oye que un campo no es válido justo cuando aparece el error, nunca mientras el visitante sigue escribiendo.
- Cada control llama a `field.handleBlur` en `onBlur`; un selector de archivos lo llama después de elegir un archivo.
- El input siempre apunta `aria-describedby` al ID de su error. El elemento de error solo se renderiza mientras el campo no es válido, y una referencia a un elemento inexistente no describe nada.
- Los errores se renderizan con `ValidationFieldError` de `custom/validation-field-error.tsx`. Los mensajes de Zod son claves de traducción, así que las busca en el espacio de nombres `<table>.validations` del módulo e interpola los números de `<MODULE>_VALIDATION_PARAMS`:

```tsx
<ValidationFieldError
  id={`${id}-error`}
  message={fieldErrorMessage(field.state.meta.errors)}
  namespace="course.validations"
  params={COURSE_VALIDATION_PARAMS}
/>
```

- Nada de elementos `<input>`, `<label>` o `<button>` escritos a mano, ni de componentes envoltorio alrededor de un campo para un solo formulario. Un componente de campo que comparten varios formularios de una misma área vive en un único archivo, como `CourseTextField`, `CourseTextAreaField` y `CourseOptionField` para los formularios de curso, capítulo y lección.
- Los errores del servidor se muestran con `toast.error(errorMessage(error))`, y el éxito, con un `toast.success` traducido.

### Los botones de envío siguen activos

El botón de envío nunca se desactiva porque el formulario esté incompleto: ni `isDisabled`, ni `disabled`, ni `aria-disabled` mientras falten valores o no sean válidos. Un botón atenuado no dice qué está mal, y GOV.UK, NN/g y Adrian Roselli lo desaconsejan. Pulsarlo con errores es un intento de envío normal: `submitForm` muestra todos los errores y mueve el foco al primer campo no válido. Solo `isPending` desactiva el botón, mientras se ejecuta la petición.

El `Button` de shadcn activa `preventFocusOnPress` en un botón con `type="submit"`, así que al pulsarlo con el ratón o el dedo el foco se queda en el campo que se está editando. Si no, el error que aparece al salir de ese campo movería el botón antes de que terminara la pulsación, y la pulsación no enviaría nada.

### Errores del servidor en un campo

Cuando el servidor rechaza un campo, el error va bajo ese campo y no en un toast. Los formularios de registro, de restablecimiento de contraseña y de contraseña de los ajustes lo hacen con una contraseña que aparece en una filtración de datos conocida, desde el `onError` de la mutación en `onSubmit`. De `sign-up-form.tsx`:

```tsx
onError: (error) => {
  if (error.message === AUTH_ERRORS.PASSWORD_COMPROMISED) {
    showFieldError(formApi, { controlId: "sign-up-password", field: "password", message: error.message })
    return
  }
  toast.error(errorMessage(error))
},
```

- `showFieldError` de `src/integrations/tanstack-form/form.submit.ts` guarda la clave del mensaje como error de envío del campo, marca el campo como abandonado para que `isFieldInvalid` lo muestre y mueve el foco al control.
- La clave se busca como cualquier otro mensaje de validación, así que necesita una entrada en el espacio de nombres de validación del campo, aquí `auth.validations.passwordCompromised`.
- El error desaparece con el siguiente cambio de ese campo, y todos los demás errores del servidor siguen siendo un toast.

El ejemplo completo más pequeño es `src/presentation/components/custom/newsletter-form.tsx`; la [guía de formularios](/docs/guides/forms-and-validation) explica paso a paso cómo construir uno.

## Tablas

Todas las tablas son el `DataTable` genérico de `src/presentation/components/custom/data-table.tsx`, usado directamente en la página:

```tsx
<DataTable columns={courseColumns} options={{ query: ({ pageIndex, pageSize }) => getCoursesPageQuery({ pageIndex, pageSize }) }} />
```

Sus props son toda su interfaz:

| Prop      | Contiene                                                                                                                |
| --------- | ----------------------------------------------------------------------------------------------------------------------- |
| `columns` | El conjunto de columnas de `<entity>-columns.tsx`                                                                       |
| `data`    | Filas que ya están en memoria, para una tabla que pagina en el cliente                                                  |
| `options` | `query` (del estado de la página a las opciones de consulta, para paginar en el servidor), `selectable`, `initialState` |
| `filters` | Controles de búsqueda y de selección vinculados a los ID de columna                                                     |

`DataTable` sigue el modelo de la [tabla de datos de React Aria de shadcn](https://ui.shadcn.com/docs/components/aria/data-table): `tableFeatures` y `useTable` de TanStack Table v9, renderizados con las primitivas de tabla de shadcn. La paginación, la ordenación, el filtrado, la selección, las filas de carga y la barra de paginación viven dentro de él. No escribas un componente de tabla, cabecera, fila o paginación para cada página, ni añadas una opción que todavía no use ninguna página.

### Columnas

Un conjunto de columnas vive en `custom/<area>/<entity>-columns.tsx` y se construye con `createColumnHelper<DataTableFeatures, Row>()`, donde el tipo de fila viene de la interfaz del módulo (`Course["listRow"]`):

```tsx
export const courseColumns = columnHelper.columns([
  columnHelper.accessor("title", { cell: TitleCell, enableSorting: false, header: () => <CourseHeader id="course" /> }),
  columnHelper.accessor("kind", { cell: KindCell, enableSorting: false, header: () => <CourseHeader id="kind" /> }),
  columnHelper.accessor("status", { cell: StatusCell, enableSorting: false, header: () => <CourseHeader id="status" /> }),
  columnHelper.accessor("lessons", { cell: LessonsCell, enableSorting: false, header: () => <CourseHeader id="lessons" /> }),
  columnHelper.accessor("updatedAt", { cell: UpdatedCell, enableSorting: false, header: () => <CourseHeader id="updated" /> }),
  columnHelper.display({ cell: ActionsCell, header: DataTableActionsHeader, id: "actions" }),
])
```

- Cada celda es un pequeño componente del mismo archivo que lee sus propias traducciones (`KindCell`, `StatusCell`) y, en el caso de las acciones, sus propias mutaciones (`ActionsCell`).
- Las etiquetas de las cabeceras vienen de un componente de cabecera que lee el espacio de nombres de la página, nunca de cadenas en la definición de la columna.
- La columna de acciones usa `DataTableActionsHeader`, que da a los lectores de pantalla un nombre de columna.
- Las acciones que solo tienen un icono llevan un `aria-label` que nombra la fila: `t("actions.edit", { title })`.
