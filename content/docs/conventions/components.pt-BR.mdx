Os componentes são onde o código mais facilmente ganha camadas que ninguém pediu. As regras abaixo mantêm cada tela legível a partir de um único arquivo: você abre o componente e vê os dados que ele lê, o texto que ele mostra e as classes que ele aplica.

## Abstrações mínimas

- **Um mecanismo óbvio por aspecto.** Chame a biblioteca diretamente: `toast.error(...)` de `sonner`, `hasPermission(...)` de `auth.access.ts`, o `Button` do shadcn. Não adicione uma fachada, uma factory, um provider ou um componente wrapper que apenas repassa props ou as renomeia.
- **Abstraia no terceiro uso, não no primeiro.** Um helper conquista o seu lugar quando pelo menos três pontos de chamada compartilham uma lógica que não é trivial, e ele fica no único arquivo que é dono do aspecto. `course-fields.tsx` existe porque o formulário de curso, o diálogo de capítulo e o diálogo de aula renderizam o mesmo campo de texto localizado com a mesma exibição de validação.
- **Exclua antes de estender.** Quando um mecanismo não compensa mais, remova-o em vez de adicionar opções a ele. Opções, props e parâmetros especulativos “para depois” não são adicionados.
- **Nada de maquinário cosmético.** Constantes ou helpers cuja única função é parecer organizados, como um builder para um único emoji ou uma prop `className` para um único ponto de chamada, não são adicionados.

## Os componentes leem os próprios dados

Um componente obtém sozinho o seu texto e os seus dados:

- traduções com `useTranslations`, restritas ao seu próprio namespace (veja [Traduções e conteúdo](/docs/conventions/translations));
- dados de query com `useSuspenseQuery(options)`, que o loader da rota pré-carregou;
- dados da rota com `Route.useParams()` no arquivo de rota, ou `getRouteApi("/blog/$")` em um arquivo de componente, como faz `post-meta.tsx`.

As props carregam apenas o que só o pai sabe: o registro que um diálogo edita (`chapter`), o ID a que um formulário pertence (`courseId`), um elemento de gatilho, `isOpen` e `onOpenChange`. Um componente que consegue ler sozinho um rótulo, uma lista ou o resultado de uma query não o recebe como prop, e um valor nunca atravessa um componente que não o usa. Os mapas de tags de texto rico para `t.rich` são constantes no nível do módulo, ao lado do componente que os usa, nunca objetos criados durante a renderização.

## Forma de um arquivo de componente

`src/presentation/components/custom/admin/courses/chapter-dialog.tsx` é um arquivo típico:

```tsx
interface ChapterDialogProps {
  readonly chapter?: { readonly id: string; readonly title: LocalizedText }
  readonly courseId: string
  readonly trigger: ReactNode
}

export const ChapterDialog = ({ chapter, courseId, trigger }: ChapterDialogProps): JSX.Element => {
  const t = useTranslations("pages.admin.courses.chapter")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const [isOpen, setOpen] = useState(false)
```

- Um arquivo tem o nome do componente que exporta, declarado como `export const Name = (...): JSX.Element =>`. Um componente que pode não renderizar nada retorna `JSX.Element | undefined`. O arquivo também exporta os acompanhantes que só fazem sentido ao lado dele, e nada mais: as partes de um componente composto (`HighlightGroup` e `HighlightItem`, `DataTable` e `DataTableActionsHeader`), os campos que os formulários de uma área compartilham (`course-fields.tsx`), os skeletons de uma área (`content-pending.tsx`) ou uma peça que outra tela da mesma funcionalidade renderiza (`UnlockLink` em `locked-lesson.tsx`, `PlayerPending` em `lesson-player.tsx`, `Price` em `pricing.tsx`).
- As props são `readonly`, em uma interface `<Name>Props` acima do componente, ou inline quando há uma única prop.
- Os hooks vêm primeiro, na ordem e com o espaçamento descritos em [Estilo de código](/docs/conventions/code-style), depois os callbacks locais e, por fim, o JSX.
- Escolhas entre dois trechos de JSX usam pares de `&&` ou um retorno antecipado, nunca um ternário de várias linhas.

## Nomes de classe

A estilização é feita com utilitários do Tailwind em `className`. As classes condicionais passam por `cn` de `~/src/lib/cn` com a sintaxe de objeto, nunca com um ternário dentro da chamada:

```tsx
className={cn("flex items-center gap-4 border-b transition-colors duration-200 ease-exp", {
  "border-border focus-within:border-foreground": !isInvalid,
  "border-destructive": isInvalid,
})}
```

Uma escolha entre duas opções vira duas entradas, a segunda negada, como em `newsletter-form.tsx` acima. As chaves podem ser calculadas: `curriculum.tsx` escreve `[COMPACT_COLUMNS]: compact`. Uma string de classes longa usada mais de uma vez em um arquivo vira uma constante nesse arquivo, como `CTA_CLASSNAME` em `src/presentation/components/custom/courses/locked-lesson.tsx`. Strings de classes compartilhadas por vários arquivos ficam em `src/data`, como as classes das chamadas para ação, `CTA_CLASSES` em `src/data/cta.ts`.

`~/src/lib/cn` é obrigatório, não uma preferência. Ele é `createCn`, montado a partir de `src/lib/cn.config.ts` e das tabelas que `bun run generate:cn` grava em `.source/cn-tables.ts`. A configuração registra os tokens tipográficos do projeto (`text-body`, `text-body-sm`, `text-label`, `text-spec`, `text-code`, `text-lead`, `text-title`, `text-statement`, `text-price` e os tamanhos `text-headline-*` e `text-display-*`) como tamanhos de fonte. Um `cn` comum os leria como cores e descartaria uma de duas classes que ele considera conflitantes: `cn("text-body-sm text-muted-foreground", { "text-foreground": true })` perderia o tamanho da fonte. Use esses tokens para a tipografia em vez de tamanhos brutos, e as cores do tema (`text-foreground`, `text-muted-foreground`, `bg-card`) em vez de cores fixas.

Os cantos tiram o raio da escala conforme o tipo de elemento: `rounded-lg` para superfícies como cards, diálogos e popovers, `rounded-md` para controles como botões, campos e badges, `rounded-sm` para elementos dentro de uma superfície ou de um controle com padding, como os itens de um menu e os gatilhos de abas, e `rounded-full` para círculos e pílulas. Um elemento interno nunca tem um raio maior que o do seu contêiner. A regra de lint `radius/no-off-scale` faz `bun run check` falhar com qualquer outro degrau ou com um raio arbitrário; veja [Tema](/docs/ui/theme#corner-radius).

O texto tira o tamanho de uma escala do mesmo tipo: `text-spec` para metadados, `text-label` para rótulos curtos e badges, nunca `text-xs` nem um tamanho arbitrário, e `font-mono` só para código, comandos, teclas e identificadores. Caso contrário, as regras de lint `type/no-off-scale` e `type/mono-for-code` fazem `bun run check` falhar; veja [Tema](/docs/ui/theme#type-scale).

Um status, um nível de acesso ou o tipo de um curso é o `Badge` do shadcn com uma `variant`: `neutral`, `accent`, `warning` ou `destructive`. Uma tela nunca desenha um badge com um `span` estilizado nem muda o tamanho, o espaçamento, o raio ou a cor de um badge; veja [Tema](/docs/ui/theme#badges).

## Primitivos do shadcn

`src/presentation/components/shadcn/` contém os primitivos do shadcn/ui do estilo `aria-lyra` indicado em `components.json`, construídos sobre o React Aria Components. As telas os importam diretamente; não há camada de wrappers. Adicione um primitivo com a CLI do shadcn, e altere o arquivo de um primitivo apenas para corrigir o próprio primitivo, como o seu comportamento de foco ou de acessibilidade, nunca para a aparência de uma única tela. As props do React Aria diferem dos hábitos do DOM: `onPress`, `isDisabled`, `isOpen` com `onOpenChange`, `isSelected`. Veja [Componentes do shadcn](/docs/ui/shadcn-components) para a tabela completa e para como os primitivos não usados ficam fora do CSS.

Quando nenhuma primitiva tem a forma de que um controle precisa, a tela usa o próprio componente do React Aria, nunca um elemento escrito à mão: o botão de reprodução do tour do curso e `back-to-top.tsx` usam `Button` de `react-aria-components`, e a oferta de preços regionais em `pricing.tsx` usa `CheckboxField` e `CheckboxButton`. A oferta estiliza sua caixa pelo estado nativo `:checked` (`group-has-checked:`), e não por `data-selected`, porque o Worker a desmarca no HTML pré-renderizado para quem a recusou, antes de a página hidratar. Um `<button>` nativo fica só em `copy-button.tsx`, onde o Motion anima a largura do próprio botão quando o rótulo muda.

## Anéis de foco

Os componentes do React Aria estilizam o seu anel de foco com variantes `data-focus-visible:`, como fazem `select.tsx`, `checkbox.tsx`, `switch.tsx` e `radio-group.tsx`. O React Aria define `data-focus-visible` apenas para o foco pelo teclado. Já o `:focus-visible` do Chrome também se aplica quando um popover se fecha depois de um clique fora e o React Aria devolve o foco ao seu gatilho, então `focus-visible:` em um gatilho pinta um anel depois de uma interação feita só com o mouse. Links comuns e elementos que não são componentes do React Aria mantêm `focus-visible:`, porque nunca recebem `data-focus-visible`; é por isso que `button-variants.ts`, que também estiliza links, usa `focus-visible:`. O `outline-none` do Tailwind define o estilo do contorno como `none`, que `data-focus-visible:outline-2` mantém; por isso, um gatilho do React Aria que esconde o anel do próprio navegador acrescenta `data-focus-visible:outline-solid`, como faz o gatilho da paleta de comandos do admin. `outline-hidden` define o mesmo estilo `none`. Um elemento comum não esconde o anel de jeito nenhum: a camada base de `globals.css` desenha um contorno `--ring` de 2px em volta de todo link, `summary` e elemento com `tabindex` que recebe o foco pelo teclado, e os seus utilitários `focus-visible:` só ajustam esse anel, como faz o seletor de idioma do rodapé. `e2e/specs/focus-rings.spec.ts` verifica um controle de cada tipo.

## Providers

Um provider cujo valor muda depois da hidratação nunca envolve um `<Outlet />` de rota. Ele é montado ao lado dos componentes que o consomem:

- `AriaProvider` envolve o outlet raiz em `__root.tsx` e `TranslationsProvider` envolve o corpo do documento, porque todas as telas precisam deles e os seus valores estão prontos na hidratação.
- `ThemeProvider` envolve apenas o `Toaster` em `__root.tsx` e o `ThemeSwitch` em `_site.docs.tsx`.
- `MotionProvider` envolve as seções da landing page em `_site._marketing.index.tsx`, a lista de posts em `_site._marketing.blog.index.tsx` e os cards dos planos em `license-offer.tsx`.

O motivo, medido, está em [Desempenho](/docs/conventions/performance).
