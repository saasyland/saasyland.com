## Cache delle query

`getRouter` crea un nuovo `QueryClient` per ogni richiesta, così sul server nessun dato passa da un utente all'altro. Valori predefiniti:

| Impostazione                  | Valore    |
| ----------------------------- | --------- |
| `staleTime` delle query       | 1 minuto  |
| `gcTime` delle query          | 5 minuti  |
| `defaultStaleTime` del router | 1 minuto  |
| Precaricamento                | Su intent |

I loader riempiono la cache con `queryClient.query({ ...options, staleTime: "static" })` e i componenti leggono le stesse chiavi con `useSuspenseQuery`. `setupRouterSsrQueryIntegration` serializza la cache del server nell'HTML e la idrata nel browser.

- **I messaggi di traduzione** vengono messi in cache per locale e namespace con `staleTime` e `gcTime` infiniti.
- **La query della sessione** (`getCurrentSessionQuery`) ha uno `staleTime` di un minuto. Le guard delle route la ricaricano durante le navigazioni reali e svuotano l'intera cache quando cambia l'utente autenticato.
- **Le mutazioni** invalidano le chiavi di query del proprio modulo, ad esempio `USER_QUERY_KEYS.ALL`, quando vanno a buon fine.

## Prerendering

`bun run build` prerenderizza le pagine pubbliche seguendo i link: landing, pagine legali, blog e documentazione in tutti e nove i locale. Sono esclusi i percorsi sotto `/admin`, `/app`, `/auth`, `/newsletter` e `/api` (con o senza prefisso del locale) e i link con query string o hash.

Il Worker serve l'HTML prerenderizzato dal binding `ASSETS` prima di caricare l'applicazione. Una pagina prerenderizzata non contiene dati utente, quindi può essere servita a tutti in sicurezza. Quando un visitatore ha diritto ai prezzi regionali, il Worker riscrive l'HTML e contrassegna la risposta con `Cache-Control: private, no-cache`.

## KV e D1

- **KV (`CACHE`)** memorizza solo il numero di stelle GitHub per `src/lib/github.ts`. Un valore in cache più vecchio di un'ora viene restituito subito e aggiornato in background con `waitUntil`.
- **D1 (`DB`)** memorizza le sessioni e i contatori del rate limit. I controlli di sessione delle server function aggirano la cache dei cookie di Better Auth e vengono memoizzati per il resto della richiesta.
- Le server function non prendono mai decisioni sui permessi a partire da dati in cache.
