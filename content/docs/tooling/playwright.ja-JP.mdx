Playwright は、ビルドしたアプリケーションを実際のブラウザーでテストします。スイートは Wrangler の `test` 環境に対して実行されます。この環境では、`.wrangler/test` 内のローカル D1、KV、R2、`.env.test` のダミー認証情報、そして Resend と Polar へのリクエストを横取りするテスト用エントリー `src/platform/testing/worker.ts` を使います。

```sh
bun run test:e2e:install
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
bun run test:e2e:headed
bun run test:e2e:ui
bun run test:visual
bun run test:visual:update
bun run test:journey
```

| スクリプト           | 実行内容                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `test:e2e:install`   | Chromium と WebKit をシステムの依存関係とともにインストールします                          |
| `test:e2e`           | すべてのスペックを Chromium と WebKit で実行します                                         |
| `test:e2e:smoke`     | `e2e/specs/smoke.spec.ts` を Chromium で実行します                                         |
| `test:e2e:pr`        | プルリクエストの CI の Chromium チェックと同じく、すべてのスペックを Chromium で実行します |
| `test:e2e:headed`    | すべてのスペックを表示されるブラウザーで実行します                                         |
| `test:e2e:ui`        | Playwright の UI モード                                                                    |
| `test:visual`        | Playwright の Docker イメージの Chromium で[ビジュアルテスト](#visual-tests)を実行します   |
| `test:visual:update` | ビジュアルテストを実行し、一致しなくなったスクリーンショットを書き直します                 |
| `test:journey`       | プレビューに対する[ジャーニースイート](#journey-suite)                                     |

## 設定 [#configuration]

`playwright.config.ts` は `e2e/specs/` のスペックを実行し、`chromium`（Desktop Chrome）と `webkit`（Desktop Safari）のプロジェクトを定義し、`PLAYWRIGHT_BASE_URL` または `http://127.0.0.1:3000`（`src/data/local-server.ts` の `LOCAL_SERVER_ORIGIN`） を使います。ローカルでは、Web サーバーのコマンドが `db:reset:test`、`build:test`、`start:test` を実行し、その URL ですでに応答しているサーバーがあれば再利用します。CI では 1 つのジョブがビルドを準備し、スイートを分担する <RepositoryFact name="e2eShards" /> 個のシャードがそれぞれそのビルドを展開し、Playwright はサーバーを起動するだけです（[CI/CD](/docs/tooling/ci-cd#checks)）。

| 設定       | ローカル                                         | CI                                            |
| ---------- | ------------------------------------------------ | --------------------------------------------- |
| リトライ   | <RepositoryFact name="playwrightLocalRetries" /> | <RepositoryFact name="playwrightCiRetries" /> |
| ワーカー   | <RepositoryFact name="playwrightLocalWorkers" /> | <RepositoryFact name="playwrightCiWorkers" /> |
| トレース   | 失敗時に保持                                     | 最初のリトライ時                              |
| ビデオ     | オフ                                             | 失敗時に保持                                  |
| レポーター | List と HTML                                     | GitHub と blob、失敗時に HTML にマージ        |

## 他のワークツリーと並行して実行する [#running-beside-other-worktrees]

Better Auth とニュースレターのリンクがリクエストのホストを確認するため、テストビルドはテストモードで信頼するホストからのリクエストだけを受け付けます。対象は `127.0.0.1:3000` と `localhost:3000`、およびポート <RepositoryFact name="testServerFirstPort" /> から <RepositoryFact name="testServerLastPort" /> までの `127.0.0.1` と `localhost` で、この範囲は `src/data/local-server.ts` の `TEST_SERVER_PORTS` が決めます。それ以外のポートではサインインとコースのページが失敗するため、`PLAYWRIGHT_BASE_URL` が別のホストを指していると、`playwright.config.ts` は何かをビルドする前に停止します。

ポートを選ぶ設定は `PLAYWRIGHT_BASE_URL` だけです。Playwright はその URL を開き、そのポートで `start:test` を起動します。他のワークツリーが同時にスイートを実行するときは、ワークツリーごとに範囲内の専用ポートを割り当てます。そのポートで何も待ち受けていないことを確認してから、そこでスイートを実行します。

```sh
lsof -nP -iTCP:3027 -sTCP:LISTEN
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3027 bun run test:e2e:pr
```

ポートが空いていれば、`lsof` は何も出力しません。プロセスが表示されたら別のポートを使い、そのサーバーには手を触れないでください。停止してよいのは、自分で起動したサーバーだけです。

ローカルの Playwright は、URL ですでに応答しているサーバーを再利用し、その場合はデータベースのリセットとビルドを省略します。そのため、スイートが別のワークツリーのサーバーに接続することがあってはなりません。`e2e/global-setup.ts` がこれを保証します。最初のテストの前に、ポートで待ち受けているプロセスを `lsof` で調べ、そのいずれかがこのワークツリー以外のディレクトリで動いていれば実行を停止します。このワークツリーから自分で起動したサーバーは確認を通り、そのまま再利用されます。新しいビルドをテストしたいときは、そのサーバーを停止してください。

## 構成

- `e2e/specs/`: スモークチェック、ランディングページとその操作、ナビゲーション、ロケール、テーマ、SEO、認証とそのリダイレクトおよびルーティング、ワークスペース、ユーザー管理、ニュースレター、コンテンツ、法務ページ、地域別価格、購入ファネル、ライセンスページ、CLI ライセンス API、アフィリエイト、動画、コース、コースへのアクセス、コース管理、コースのカバー画像・インポート・教材、管理ダッシュボード、注文、商品、ライセンスのマシン、ブログの一覧と共有、Content Security Policy、契約の撤回、フッター、フォーカスリング、スクロールバー、ライセンスの Webhook、公開済みの CLI、アクセシビリティのスペック（<RepositoryFact name="e2eSpecs" /> ファイル）。
- `e2e/pages/`: ページオブジェクト。
- `e2e/fixtures/`: 拡張した `test` フィクスチャ、キャプチャしたメール用のヘルパー、署名付きの `order.paid` Webhook を送信してライセンスを付与する `license.ts` の `deliverPaidOrder`、テスト用 Worker の `/__test/polar/purchase` に Polar のテストダブルでの注文とライセンスキーを求め、署名付きの `order.paid` と `benefit_grant.created` を送る `buyLicense`、ダブルが作成したチェックアウトを `/__test/polar/checkouts` から読み取る `startedCheckouts`、アプリが開いたチェックアウトをテスト用 Worker の `/__test/polar/pay` を通じて同意にチェックを入れた状態で支払い、その注文の署名付きの `order.paid` と `benefit_grant.created` を送る `payCheckout`、`accessibility.ts` の `accessibilityViolations` とライトとダークの `COLOR_SCHEMES`、`polar-checkout.ts` の Polar のチェックアウトページ。Polar のダブルは各チェックアウトに Polar のチェックアウトのオリジン上の URL を与え、自動フィクスチャ `browserDoubles` がインストールする `BROWSER_DOUBLES` の 1 つ、`servePolarCheckout` は、すべてのブラウザーコンテキストでその URL に、テスト用 Worker の `/__test/polar/checkout` から読み取ったダブルのページで応答します。このページはオーバーレイに読み込みが終わったことを伝え、その **Pay** ボタンと **Close** ボタンは、Polar のページと同じように、チェックアウトの `embed_origin` に `confirmed` と `success`、または `close` を送ります。`payInCheckoutOverlay` と `closeCheckoutOverlay` はこれらのボタンを押し、`refusePolarCheckoutEmbedding` は、組織が登録していないホストに対して Polar が行うのと同じように、`frame-ancestors 'none'` を付けてページを配信します。ジャーニースイートは `browserDoublesEnabled` オプションを `false` にして、実際のサンドボックスで支払います。`orderLicense` はそうした購入の `order.paid` だけを送信し、後でその `benefit_grant.created` を送信する `issueKey` を返します。フレームの外で Polar 自身のチェックアウトページとして開いた場合、ダブルの **Pay** は Polar のページと同じように、`customer_session_token` を付けたチェックアウトの成功 URL へブラウザーを送り、`payOnPolarCheckoutPage` がそれを押します。 `refundOrder`、`revokeLicenseKey`、`deliverGuestOrder`、`cutOffPolar` は、テスト用 Worker の `/__test/polar/refund`、`/__test/polar/revoke`、`/__test/polar/guest-purchase`、`/__test/polar/cut-off` に、ダブル内の注文の署名付き `order.refunded`、そのキーの署名付き `benefit_grant.revoked`、アカウントを持たない購入者の署名付き `order.paid`、または Polar に届かないかのように Polar へのリクエストが失敗するキーを求めます。`buyer.ts` の `signUpBuyer` は API で購入者を登録し、`cli-api.ts` の `sendToApi` は専用のアドレスから CLI ライセンス API を呼び出し、`stack-answers.ts` の `EVERY_STACK_ANSWER` はスタックのすべての選択肢とエクストラについて有効な回答の組を持ちます。
- `e2e/data/accounts.ts`: シードされるアカウント（管理者と顧客）とそのパスワード。ライセンスを持つ顧客とそのライセンス、および CLI ライセンス API のスペックが端末をアクティベートする、並列ワーカーごとのライセンスは `e2e/data/licenses.ts` にあります。
- `e2e/data/videos.ts` と `e2e/data/courses.ts`: シードされるテスト動画（ファイルは `e2e/fixtures/video/`）と、シードされるコース。コースは 2 つのチャプターを持ち、1 つ目には無料プレビュー、アカウント用レッスン、有料レッスン 1 つが、2 つ目には動画を収録中の有料レッスン 3 つがあります。
- `e2e/data/<feature>.pages.ts` と `e2e/data/<feature>.seed.ts`: 各機能のページ（`accessibility.spec.ts` と `workspaces.spec.ts` が訪れます）と、テスト用データベースに入るその機能の行とメディア。各リストは `e2e/data/pages.ts` の `ENTRIES` と `scripts/seed-test.ts` がインポートします。
- `e2e/data/<feature>.flows.ts`: 各機能のフロー。それぞれに、そのフローをエンドツーエンドで証明するテスト、またはテストがない理由を記載し、`scripts/check-flows.ts` の `FLOWS` がインポートします。[テストカバレッジ](/docs/tooling/test-coverage)を参照してください。
- `e2e/global-setup.ts`: スイートのポートで動いているサーバーが別のワークツリーのものであれば実行を止める、グローバルセットアップ。
- `e2e/journey/`: 独自の設定を持つ[ジャーニースイート](#journey-suite)。`published-cli.spec.ts` は `e2e/journey/cli.ts` の `runCli` で公開済みの CLI をテスト用 Worker に対して実行するため、ブラウザースイートには npm レジストリが必要です。

テスト用 Worker は、各機能が `e2e/data/<feature>.worker.ts` で宣言し、`src/platform/testing/worker.ts` の `ENTRIES` がインポートしたものを実行します。ライセンス機能は Polar のモックにテスト用のライセンスキーを登録し、Resend はキャプチャしたメールを読み取る `/__test/emails` を、ニュースレター機能は購読者の状態を読み取る `/__test/newsletter` を公開します。

## アクセシビリティ

`e2e/specs/accessibility.spec.ts` は `@axe-core/playwright` を通じて [axe-core](https://github.com/dequelabs/axe-core) を実行し、公開ページ、コースのページ、ドキュメントのトップページ、規約のすべてのページと、それ以外の各ドキュメントセクションから 1 ページずつ、ブログ記事、管理者とカスタマーのワークスペースをライトテーマとダークテーマで検査します。管理画面のページには `/admin/courses`、`/admin/courses/create`、シード済みのコースのエディターが含まれ、これらは `e2e/specs/workspaces.spec.ts` でも巡回します。WCAG 2.0、2.1、2.2 の A と AA のルールに加えて axe のベストプラクティスを適用し、ページが成功ステータスで読み込まれなければ失敗とし、スクロールで表示されるセクションも検査できるようページ全体をスクロールし、有限のアニメーションが終わるのを待ってから検査します。違反が 1 件でもあれば、ルール、影響度、該当するセレクターを示して失敗します。

axe はキーボードの操作の流れもレイアウトも確認できないため、サイトのヘッダーとフッターについては 3 つのスペックがそれを確認します。`e2e/specs/navigation.spec.ts` はスマートフォンのメニューがフォーカスを自身に移し、Tab を中にとどめ、背後のページを `inert` にし、フォーカスをボタンに戻すことを、`e2e/specs/footer.spec.ts` はどのロケールでも <RepositoryFact name="footerPhoneWidths" /> px でフッターのリンク同士が接したりフッターからはみ出したりしないこと、およびホームページのセクションへのリンクが自身のセクションでだけ現在のリンクになることを、`e2e/specs/focus-rings.spec.ts` はフッターの言語切り替えと管理画面のコマンドパレットのトリガーがキーボードに対してリングを描くことを確認します。

`e2e/specs/text-layout.spec.ts` は、管理画面のコースフォームと表、ランディングページのコマンドビルダーを <RepositoryFact name="textLayoutWidths" /> px で `e2e/fixtures/text-layout.ts` の `textLayoutProblems` を使って確かめます。文字の行がほかの行やアイコンと重ならないこと、省略記号なしで切れないこと、省略記号で数文字まで縮まないこと、ページが横にスクロールしないこと、コースフォームのすべてのロケールタブが見えることを確認します。 固定した列や固定ヘッダーの下にスクロールしたテキストはそれに覆われるため、固定されたテキストは固定されたテキスト同士でのみ比較します。 別のテストは、管理画面のすべての表を英語と、列見出しが最も長いウクライナ語で開き、見出しがセルより広い場合に失敗します。

## スクロールバー [#scrollbars]

`e2e/specs/scrollbars.spec.ts` は、`launchOptions` の `ignoreDefaultArgs` で Playwright の `--hide-scrollbars` スイッチを外して Chromium を起動します。そのため Chromium は、Windows や Linux、スクロールバーを常に表示する設定の Mac と同じく、場所を取るクラシックなスクロールバーを描画します。このスペックは、法的情報のページ、認証ページ、管理画面のページが、ページがスクロールしなくなるまでウィンドウを広げても見出しの位置を保つこと（ドキュメントのページは、画面の高さいっぱいのレイアウトの後にサイトのフッターが続くため、常にスクロールします）、ドキュメントの検索、言語の選択、ダイアログ、メニューを開いても何も動かないこと、`/admin` がウィンドウいっぱいに広がること、ライトテーマでもダークなページの背後のウィンドウがダークであることを確認します。macOS の WebKit は場所を取らないオーバーレイのスクロールバーしか描画せず、起動オプションでは変えられないため、確保した場所の確認は Chromium でのみ実行します。ヘッダーのリンクを `lg` 未満で置き換えるサイトのメニューは 768 px で確認し、開閉しても何も動かないことを確かめます。

## ビジュアルテスト [#visual-tests]

`e2e/specs/visual-*.spec.ts` は、訪問者が見る画面を `e2e/specs/__screenshots__/` にある承認済みのスクリーンショットと比べます。見出しが 1 行増えて折り返す、カードが増える、セクションがずれるといった変更は、ほかのテストがすべて通ってもプルリクエストを失敗させます。これらのスペックは専用の Playwright プロジェクト `visual` で動きます。`playwright.config.ts` は `PLAYWRIGHT_VISUAL_BROWSER` がブラウザーサーバーを指すときだけこのプロジェクトを定義し、`chromium` と `webkit` のプロジェクトはこれらのスペックを実行しません。

```sh
bun run test:visual
bun run test:visual:update
```

| スペック                                         | スクリーンショット                                                                                                             | ロケールと幅                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| `visual-landing.spec.ts`, `visual-facts.spec.ts` | ランディングページのヘッダー、ヒーロー、数字のグリッド、ほかの選択肢を含む料金、事例、マニフェスト、締めのセクション、フッター | すべてのロケールをすべての幅で                               |
| `visual-content.spec.ts`                         | ブログ記事の末尾にある著者カードと行動喚起                                                                                     | すべてのロケールをスマートフォン幅で、英語をデスクトップ幅で |
| `visual-content.spec.ts`                         | ドキュメントのページ                                                                                                           | 英語を両方の幅で、ドイツ語をデスクトップ幅で                 |
| `visual-auth.spec.ts`                            | サインインした訪問者のヘッダー、`/admin`、`/admin/settings`                                                                    | 英語を両方の幅で、ドイツ語をデスクトップ幅で                 |
| `visual-billing.spec.ts`                         | `/app/billing`                                                                                                                 | 英語を両方の幅で、ドイツ語をデスクトップ幅で                 |

ロケールは <RepositoryFact name="visualLocales" />、幅は <RepositoryFact name="visualWidths" /> px で、スクリーンショットは全部で <RepositoryFact name="visualScreenshots" /> 枚です。ランディングページで変わるのは主に文章なので、各セクションはすべてのロケールで両方の幅を撮ります。ブログ記事の下のカードは長い単語が折り返すスマートフォンで崩れるので、すべてのロケールでスマートフォン幅を撮ります。管理画面と顧客向け画面のレイアウトは文章ではなくコンポーネントで決まります。英語の両方の幅でレイアウトを確かめ、単語がいちばん長いドイツ語で収まらなくなったラベルを確かめます。

### 毎回同じピクセル [#same-pixels-on-every-run]

- ブラウザーのコンテキストは `reducedMotion: "reduce"` を設定します。そのためヒーローの登場アニメーション、スクロールで現れるセクション、ループ動画は止まったままで、動画はポスター画像を表示します。`toHaveScreenshot` はスタックのマーキーなどほかのアニメーションをすべて止め、テキストカーソルを隠します。
- テーマはダーク、タイムゾーンは UTC です。
- 最初のスクリーンショットの前に、`e2e/fixtures/visual.ts` の `openForScreenshots` がページの描画とハイドレーションを待ち、遅延読み込みの画像も含めてすべての画像を読み込んでデコードし、`document.fonts.ready` を待ちます。
- `expectRegion` はページ全体からセクションをその位置のまま切り出すので、固定ヘッダーがセクションに重なることはありません。
- レイアウトが変わらなくても変わる値はマスクで隠します。リポジトリのファイル数と GitHub のスター数を数える数字、そしてフッターの著作権表示の年です。
- データは初期データを投入したテスト用データベースから来ます。スイートの URL ですでにサーバーが応答していると `scripts/visual-tests.ts` は最初のテストの前に止まるので、Playwright 自身がデータベースをリセットし、ビルドしてサーバーを起動します。CI ではジョブが初期データ付きのビルドを自分用に展開します。

### どのマシンでも同じブラウザー [#the-same-browser-on-every-machine]

フォントの描画は macOS と Linux で違い、Linux のイメージ同士でも違うため、ビジュアルテストは実行するマシンのブラウザーを使いません。`scripts/visual-tests.ts` は Playwright のブラウザーサーバーを `linux/amd64` 向けの Docker イメージ `<RepositoryFact name="visualBrowserImage" />` で起動し（Apple シリコンの Docker Desktop はこれをエミュレートします）、そのアドレスを `PLAYWRIGHT_VISUAL_BROWSER` で渡して `playwright test --project=visual` を実行します。テストは `connectOptions` で接続し、その `exposeNetwork: "<loopback>"` によってブラウザーはマシンのループバック上のテストサーバーに届きます。イメージのタグはインストール済みの `@playwright/test` に合わせるので、`bun run deps:update` はブラウザーとテストランナーを一緒に更新します。ノートパソコンと CI は同じピクセルを描くので、ローカルで撮った基準画像は CI でも通ります。`test:visual` には起動中の Docker が必要です。

### しきい値 [#threshold]

スクリーンショットは、ピクセルの <RepositoryFact name="visualMaxDiffPercent" unit="percent" /> を超えて違うと失敗します。ピクセルが違うと数えるのは、その色が Playwright のピクセルごとのしきい値を超えたときだけです。ブラウザーとフォントはどこでも同じなので、変更のないページは 1 ピクセルも違いません。別の CPU がアンチエイリアスを 1、2 段階違えて丸めても、このしきい値の内に収まります。見出しが 1 行増えて折り返したりカードが増えたりしてスクリーンショットの大きさが変わると、しきい値に関係なく失敗します。ヒーローの段落に単語を 1 つ足すだけでも、しきい値が許すより多くのピクセルが変わります。

### 基準画像を更新する [#updating-the-baselines]

レイアウトや文章の変更が意図したものなら、`bun run test:visual:update` を実行し、`e2e/specs/__screenshots__/` で変わった PNG をブランチの差分で 1 枚ずつ開いて確かめ、変更と一緒にコミットします。`--update-snapshots=changed` は一致しなくなったスクリーンショットだけを書き直します。CI で `visual` ジョブが失敗すると、`test-results/` を `visual-differences` アーティファクトとしてアップロードし、失敗したスクリーンショットごとに期待画像、実際の画像、差分画像を残します。

### CI では [#in-ci]

`e2e-reusable.yml` の `visual` ジョブは Chromium でだけ、シャードと並んで動きます。シャードと同じようにテストビルドを待って展開し、`bun run test:visual` を実行します。このジョブが通らなければ `Build and E2E (chromium)` チェックは失敗します。基準画像が Chromium のものなのは、WebKit が文字とサブピクセルを違う方法で描くためです。WebKit にはもう 1 組の基準画像と同じレイアウトのもう 1 回のレビューが必要になりますが、WebKit の動作は WebKit のチェックが引き続き確かめます。

## ジャーニースイート [#journey-suite]

`bun run test:journey` は、顧客と同じ手順でライセンスを購入し、CLI を使います。対象は `https://preview.saasyland.com` のプレビューデプロイで、支払いは Polar のサンドボックスで処理されます。`e2e/journey/playwright.config.ts` は専用の Chromium プロジェクトを持ち、Web サーバーを起動しない独立した設定なので、`test:e2e` やプルリクエストのチェックでは実行されません。`journey.yml` が毎晩と手動で実行します（[CI/CD](/docs/tooling/ci-cd#journey-suite)）。プランごとに `@core`、`@complete`、`@agency` のタグを付けた独立したテストがあり、テストは並行して実行され、それぞれ次の手順を進みます。

1. **アカウント。** Resend のテスト用受信箱の新しいアドレス `delivered+journey-<run>-<tier>@resend.dev`（アップグレードのテストではプランの代わりに `upgrade`）で登録し、Resend API で認証メールを見つけて、そのリンクを開きます。
2. **価格。** `/app/license` は、`/cdn-cgi/trace` が示す、Cloudflare がランナーの所在地とみなす国の価格でプランを提示しなければなりません。`PPP_TIERS` に含まれる国では地域価格、それ以外の国では通常価格です。
3. **チェックアウト。** Polar サンドボックスのチェックアウトは、ページを離れずに `/app/license` の上に、フォーカスを受け取る `sandbox.polar.sh` のフレームで開き、アカウントのメールアドレスが入力済みで、即時提供への同意にチェックが入っていない状態でなければなりません。テストはフレームの中でその同意にチェックを入れます。テストは [Stripe のテストカード](https://docs.stripe.com/testing)を使って支払います。請求先はポーランドで、請求先住所は国だけで済みます。ページは Polar の `loaded`、`confirmed`、`success` のメッセージをこの順に受け取り、オーバーレイを閉じて、`/app?checkoutId=<id>&tier=<tier>` で有効なライセンスを表示しなければなりません。Polar がチェックアウトをフレームに表示するのは、サンドボックスの組織が [Settings > Embedding](/docs/getting-started/polar-setup#embedding) に `preview.saasyland.com` を登録している間だけです。
4. **注文とキー。** Polar には、プランの商品に対する支払い済みの注文が 1 件だけあり、その金額は `/app/license` が提示した価格でなければなりません。注文には同意と購入者の言語も含まれていなければなりません。また、購入確認メールが受信箱に届き、`/app/license` には、Webhook が発行したキー、CLI コマンド、使用中の端末がないことが表示されなければなりません。
5. **CLI。** 公開済みの CLI は、`/app/license` のコマンドと同じく <RepositoryFact name="cliExec" /> として実行され、`SAASYLAND_API_URL` を通じてプレビューと通信します。`activate` は認証情報ファイルをモード `0600` で書き込み、もう一度アクティベートしても同じ枠のままで、`whoami` は端末を表示します。`SAASYLAND_CI_REPOSITORY` で区別される CI 端末が残りの枠（Core は最大 <ActivationLimit tier="core" /> 台、Complete は <ActivationLimit tier="complete" /> 台、Agency は <ActivationLimit tier="agency" /> 台）を埋め、次の端末は `activationLimitReached` で拒否されます。`/app/license` で枠を解放すると、拒否された端末がその枠を得て、解放された端末には `activationNotFound` が返ります。`deactivate` は最初の端末を解放し、その認証情報を削除します。
6. **返金。** Polar サンドボックスの API で注文を返金し、`/app/license` にライセンスが返金済みと表示されるまで待ちます。その後、`whoami` は `licenseRefunded` を返し、認証情報を削除しなければなりません。

`@upgrade` のタグを付けた 4 つ目のテストはライセンスをアップグレードします。同じ手順で Core を購入して Core の <ActivationLimit tier="core" /> 台を埋め、次の端末は拒否されます。続いて `/app/license?tier=complete` が、ランナーの国での Complete の価格から Core の注文の額を引いた額で Complete を提示しなければならず、テストはその差額を、同じ方法でページに重ねて開いた Polar のチェックアウトで支払います。Polar には差額でのアップグレードの注文があり、`upgrade_from_order` と `upgrade_from_tier` に Core の注文とプランが入っていなければなりません。Core の注文のキーは Complete の <ActivationLimit tier="complete" /> 台まで認め、Polar がアップグレードの注文に付与したキーは無効になり、`/app/license` は同じキーで Complete を表示しなければなりません。そのあと拒否された端末と次の端末が有効化され、その次の端末は拒否されます。テストは Polar のサンドボックス API でアップグレードの注文を返金し、ライセンスは同じキーと Core の上限で Core に戻り、有効化済みの端末はそのまま動き、新しい端末は拒否されなければなりません。最後に Core の注文の返金でライセンスが終了します。

CLI の各端末はテストの出力フォルダー内のディレクトリで、CLI はそれをホームディレクトリとして使います。CLI の環境には `PATH`、そのホームディレクトリ、npm のキャッシュ、`SAASYLAND_*` 変数しかないため、スイートの認証情報が CLI に渡ることはありません。失敗したテストが支払い済みのまま残した注文は、テストの終了時に返金されます。アカウントはそれぞれ返金済みのライセンスとともにプレビューに残ります。

スイートはこれらの値を環境変数から、またはファイルがあれば `.env.preview` から読み込み、値がなければ最初のテストの前に停止します。CI では `journey.yml` が GitHub の環境 `Preview` から読み込みます。

| 変数                                                                            | 用途                                                                                                                                                                 |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POLAR_ACCESS_TOKEN`                                                            | サンドボックスでの注文の読み取りと返金、およびそのライセンスキーの読み取り。スコープ `orders:read`、`refunds:write`、`benefits:read`、`license_keys:read` が必要です |
| `POLAR_SERVER`                                                                  | `sandbox` でなければなりません                                                                                                                                       |
| `POLAR_PRODUCT_ID_CORE`, `POLAR_PRODUCT_ID_COMPLETE`, `POLAR_PRODUCT_ID_AGENCY` | 注文の対象となるべきサンドボックスの商品                                                                                                                             |
| `RESEND_API_KEY`                                                                | プレビューが送信した認証メールの読み取り。フルアクセスのキーが必要です                                                                                               |

プレビューでは [CLI ライセンス API](/docs/features/cli-licence-api) を含むビルドが動いている必要があります。プレビューでは `main` が動いており、`deploy.yml` が本番より先にそこへデプロイします。マージ前にブランチをテストするには、チェックが成功した後に `gh workflow run preview.yml --ref <branch>` でそのブランチをデプロイしてください。サンドボックスはコードと一致している必要があり、`bun run polar:verify:preview` がそれを確認します。そのうえで次を実行します。

```sh
bun run test:e2e:install
bun run polar:verify:preview
bun run test:journey
```

`bun run test:journey --grep @core` は、そのタグを持つテストだけを実行します。HTML レポートは `playwright-report/journey/` に、JSON レポートは `playwright-report/journey.json` に、失敗したテストのトレース、動画、端末ディレクトリは `test-results/journey/` に書き出されます。
