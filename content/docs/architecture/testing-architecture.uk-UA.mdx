## Проєкти Vitest

`vp test` запускає Vitest через Vite+ із трьома проєктами, визначеними у `vite.config.ts`. Тести лежать у папці `__test__` поруч із кодом, який вони покривають, та імпортують тестові API з `vite-plus/test`.

| Проєкт        | Середовище | Шаблон файлів           |
| ------------- | ---------- | ----------------------- |
| `node`        | Node       | `*.test.ts`             |
| `integration` | Node       | `*.integration.test.ts` |
| `component`   | jsdom      | `*.component.test.tsx`  |

Жоден тест не звертається до справжнього облікового запису Cloudflare чи провайдера:

- D1 — це база даних SQLite у пам'яті, яка застосовує збережені в репозиторії міграції, а KV і бакет R2 `MEDIA` — мапи в пам'яті. KV, бакет і лічильники обмеження частоти запитів скидаються перед кожним тестом, а `createEdgeCache` підміняє кеш Workers.
- `createServerFn` підмінено, тож серверна функція виконується в тому самому процесі через свої справжні middleware та валідатор. Це стосується проєктів `node` та `integration`. У проєкті `component` серверна функція завершується помилкою, бо jsdom є браузером.
- Компонентні тести рендеряться зі справжніми `QueryClient` і роутером.
- `fetch` потрапляє до строгих дублерів Resend і Polar замість мережі, а запит до будь-якого іншого хоста завершується помилкою, наче машина офлайн.

## Дублери провайдерів

`src/platform/testing/setup.ts` підміняє `fetch` перед кожним тестом, тож клієнти SDK Resend і Polar, якими користується сам застосунок, надсилають свої справжні запити до `src/platform/testing/mocks/resend.ts` і `src/platform/testing/mocks/polar.ts`.

- Вони перевіряють те саме, що перевіряє провайдер: ключ API або токен доступу, кінцеву точку й метод, а також тіло або параметри запиту, за допомогою строгих схем Zod, типізованих за власними моделями запитів SDK (`EmailApiOptions`, `models.CheckoutCreate`, `models.LicenseKeyDeactivate`). Дублер Polar також відхиляє продукт або знижку, яких немає в організації.
- Вони відповідають так, як відповідає провайдер: Resend на повторний `Idempotency-Key` повертає попередню відповідь замість повторного надсилання й відповідає 409, коли ключ надходить з іншим листом; Polar повертає повні об'єкти `models.Checkout`, `models.Order` і `models.LicenseKeyWithActivations` і 404 для замовлення чи ключа, яких у нього немає.
- Каталог Polar береться з коду: ID продуктів з `POLAR_PRODUCT_IDS`, ціни з `TIER_PRICES` і одна автоматична відсоткова знижка на кожен рівень регіональних цін.
- Запит, який провайдер відхилив би, або звернення до кінцевої точки, яку застосунок не викликає, записується, а спільний `afterEach` провалює тест, навіть якщо застосунок перехопив помилку.

## Інтеграційні набори

Файли `*.integration.test.ts` перевіряють цілі серверні сценарії на D1 у пам'яті та дублерах провайдерів:

- Набори Better Auth працюють зі справжнім `auth` з `auth.server.ts`, включно з його плагінами, хуками, обмеженнями частоти запитів і функціями надсилання листів. `__test__/fixtures/auth.harness.ts` реєструє користувача, підтверджує пошту й виконує вхід із заголовками, які надсилає браузер, і читає кожен токен з листа, який доставив дублер Resend.
- `license-purchase.integration.test.ts` покриває платежі й ліцензії: створення сеансу оплати (план, регіональна знижка за країною, метадані партнерської рекомендації, відмова за активної ліцензії), потім підписані вебхуки `order.paid`, `benefit_grant.created`, `order.refunded` (часткове й повне повернення) і `benefit_grant.revoked` через кінцеву точку Polar у Better Auth, доставлені не по порядку, двічі та з недійсними підписами, а також перелік активацій ліцензії та їх деактивацію.

## Покриття

`bun run test:coverage` вимагає 100% покриття рядків, інструкцій, функцій і гілок у всьому `src`. Примітиви shadcn, `src/platform/testing`, згенеровані файли й оголошення типів виключено. Покривайте реальну поведінку, а гілки, які ніколи не можуть виконатися, видаляйте, замість того щоб підміняти глобальні об'єкти, аби до них дістатися.

## Браузерні тести

Специфікації Playwright лежать у `e2e/specs`, page objects — у `e2e/pages`, фікстури — у `e2e/fixtures`. Вони запускаються на збірці, наближеній до production, яка використовує середовище Wrangler `test`: локальні D1, KV і R2 у `.wrangler/test`, фіктивні секрети з `.env.test` і тестовий Worker, який встановлює ті самі дублери Resend і Polar та відкриває доступ до доставлених листів, щоб специфікація могла перейти за справжнім посиланням підтвердження. `e2e/fixtures/polar.ts` доставляє оплачене замовлення, підписане точно так, як інтеграційні набори підписують свої. Локально Playwright сам застосовує міграції, наповнює базу, збирає й запускає застосунок. Набір виконується в Chromium і WebKit.

## Скрипти

```sh
bun run test
bun run test:unit
bun run test:integration
bun run test:component
bun run test:watch
bun run test:changed
bun run test:coverage
bun run test:e2e
bun run test:e2e:smoke
bun run test:e2e:pr
```

## CI

`.github/workflows/ci.yml` запускається для pull request і для пушів у `main`:

1. `bun run check`: форматування, лінтинг, перевірка типів і `check:i18n`
2. `bun run test:coverage`
3. Тестова збірка та набір Playwright у Chromium
4. Розгортання preview для pull request або розгортання production для `main`
