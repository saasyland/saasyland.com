Cloudflare D1 (SQLite) è il database dell'applicazione, collegato come `DB`. `src/integrations/drizzle-orm/` lo collega a Drizzle:

| File                  | Scopo                                                                                                                                    |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `drizzle.database.ts` | `db` solo lato server, creato con `drizzle(env.DB, { schema })`                                                                          |
| `drizzle.schemas.ts`  | Riesporta lo schema di ogni tabella e le sue relazioni                                                                                   |
| `drizzle.config.ts`   | drizzle-kit: dialetto SQLite, driver `d1-http`, migrazioni con prefisso di timestamp in `migrations/`                                    |
| `drizzle.errors.ts`   | `rethrowAsConflict`, che trasforma un errore di vincolo di unicità in `AppError(ERROR_CODES.CONFLICT)` e rilancia qualsiasi altro errore |

## Tabelle

Ogni tabella appartiene a un modulo in `src/modules/<table>/` con `<table>.schema.ts` (`drizzle-orm/sqlite-core`), più `.zod.ts`, `.constants.ts`, `.types.ts` e `use-cases/` quando la tabella ha delle operazioni e `.utils.ts` quando servono funzioni di supporto. I moduli sono `account`, `category`, `chapter`, `course`, `lesson`, `lesson-progress`, `license`, `newsletter-subscriber`, `product`, `rate-limit`, `session`, `two-factor`, `user`, `verification` e `video`. `rate-limit` contiene solo il proprio schema, e `license` possiede anche `revoked_license_order`. Il codice che non possiede una tabella non ha un modulo.

Gli schemi seguono le stesse convenzioni:

- Gli ID sono stringhe UUID v7.
- Le date sono colonne `integer` in modalità `timestamp_ms`, con valore predefinito `unixepoch() * 1000`.
- I booleani sono colonne `integer` in modalità `boolean`.
- Relazioni, indici, vincoli di unicità e chiavi esterne vengono dichiarati nello schema.

## Scritture atomiche

D1 non supporta transazioni interattive. Mantieni un'operazione atomica con una singola istruzione, come un upsert con `onConflictDoUpdate`, oppure raggruppa le istruzioni con `db.batch`. I casi d'uso delle liste paginate recuperano una pagina e il suo totale in un unico batch (`src/modules/category/use-cases/get-categories.ts`):

```ts
const filter = data.kind && eq(category.kind, data.kind)
const [rows, totals] = await db.batch([
  db
    .select()
    .from(category)
    .where(filter)
    .orderBy(desc(category.createdAt), desc(category.id))
    .limit(data.pageSize)
    .offset(data.pageIndex * data.pageSize),
  db.select({ total: count() }).from(category).where(filter),
])
return { rows, total: totals.reduce((sum, row) => sum + row.total, 0) }
```

Il rate limiter in `src/lib/rate-limit.ts` combina pulizia, un upsert atomico e una lettura in un unico batch, così le istanze del Worker condividono gli stessi limiti.

## Migrazioni

Le migrazioni sono file SQL in `src/integrations/drizzle-orm/migrations/`, generati con `bun run db:generate` e applicati con Wrangler. Vitest le esegue su un database SQLite in memoria. Vedi [Migrazioni del database](/docs/tooling/database) per i comandi.
