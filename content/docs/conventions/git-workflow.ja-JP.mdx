`main` の履歴はプロダクトの一部です。スカッシュマージされたプルリクエストはそれぞれ 1 行になり、コードを使う人にとって何が変わったのかを伝えます。

## コミット

コミットメッセージは Conventional Commits に従い、絵文字なしで書きます。タイプに対応する絵文字は `prepare-commit-msg` フックが付けます（対応表は [Conventional Commits](/docs/tooling/conventional-commits) を参照）。

```sh
git commit -m "fix(auth): keep the locale in verification links"
```

- 件名は小文字の命令形で書き、その変更がユーザーにとって何をするのかを述べます。`update course files` ではなく、`feat(course): reorder the catalogue from the course list` のように書きます。
- スコープはモジュールまたはエリアです（`course`、`auth`、`a11y`、`deps`、`readme`）。
- タイプは `feat` ✨、`fix` 🐛、`docs` 📚、`refactor` 📦、`chore` ♻️、`test` 🚨、`perf` 🚀、`build` 🛠️、`ci` ⚙️、`style` 💎、`revert` 🗑️ のいずれかで、それ以外はフックが拒否します。絵文字を自分で入力してはいけません。すでに絵文字で始まる件名は、フックがチェックしないためです。
- プルリクエストは論理的なコミットに分割します。機能そのもの、`docs(<scope>)` としてのそのドキュメント、そして途中で見つけた修正です。
- `--no-verify` を付けてコミットしてはいけません。`pre-commit` フックは `bun run check:pre-commit` を実行します。失敗した場合は原因を修正してください。
- フォーマットとリントは、`bunx vp fmt <files>` と `bunx vp lint --fix <files>` で、変更したファイルだけに行います。リポジトリ全体に対して `bun run check:fix` や `vp check --fix` を実行してはいけません。触っていないファイルまで書き換えてしまい、`.vscode/settings.json` の共有エディター設定もその対象になります。`git status` に `.vscode/` が表示された場合は、`HEAD` から復元してください。

## AI の帰属表示をしない

コミットとプルリクエストの説明には、AI ツールの `Co-Authored-By` トレーラーも、「Generated with」の行も、その他の AI の帰属表示も含めません。ツールがデフォルトで追加する場合も同様です。GitHub はそのようなトレーラーのアドレスを無関係なアカウントに結び付け、そのアカウントがリポジトリのコントリビューターとして表示されてしまいます。`commit-msg` フックは、そうした表示を含むコミットメッセージを拒否し、削除すべき行を示します（[Conventional Commits](/docs/tooling/conventional-commits)を参照）。アップストリームに提供する修正にも同じことが当てはまります（[依存関係](/docs/conventions/dependencies)を参照）。

## ブランチとワークツリー

- `main` からブランチを作成し、プルリクエストごとに 1 つのブランチを使います。
- チェックアウトのブランチを切り替えるのではなく、ブランチごとに専用の Git ワークツリーを用意します。そうすれば、エディターや別のプロセスが開いているチェックアウトが、知らないうちに変更されることはありません。

```sh
git worktree add ../saasyland-fix-locale -b fix/locale-links main
cd ../saasyland-fix-locale
bun install --frozen-lockfile
```

- テストの実行結果を信用する前に、テストしたディレクトリで `git branch --show-current` を確認します。

### すべてのワークツリーのフック [#hooks-in-every-worktree]

Git は `core.hooksPath` を、リポジトリのすべてのワークツリーが共有する設定から読み取ります。Vite+ はこの値を相対パス `.vite-hooks/_` に設定するため、Git はコミットしたワークツリーのフックディスパッチャーを実行します。ディスパッチャーは生成されるファイルでコミットされないため、ワークツリーごとに専用のものが必要で、存在しないワークツリーでは Git が警告なしにフックを飛ばします。次の 2 つの仕組みでインストールします。

- `git worktree add` は、コマンドを実行したチェックアウトの `post-checkout` フックを実行し、`.vite-hooks/post-checkout` が `vp hooks enable` で新しいワークツリーのディスパッチャーをインストールします。そのため、`bun install` の前にコミットすると、フックが飛ばされるのではなく `pre-commit` フックで失敗します。
- `bun install` は `prepare` を実行し、`prepare` は `vp config --no-agent` でディスパッチャーを更新してから `scripts/verify-git-hooks.ts` を実行します。`core.hooksPath` が `.vite-hooks/_` でない場合や、`.vite-hooks/` のフックがディスパッチャーに欠けている場合はインストールが失敗し、エラーに修復するコマンドが表示されます。

`core.hooksPath` をほかの値に設定したり、Git に `-c core.hooksPath` を渡したりしてはいけません。この値がメインのチェックアウトのディスパッチャーを指す絶対パスだった間、`vp config` はほかのワークツリーにディスパッチャーをインストールせず、メインのチェックアウトで次に実行した `bun install` が相対パスに戻したとき、それらのワークツリーのコミットはフックなしで作成されました。ワークツリーでフックが有効かどうかは `vp hooks status` で確認できます。

## 線形の履歴 [#linear-history]

GitHub で `main` を保護するルールセットは線形の履歴を必須とし、プルリクエストをマージキュー経由でのみ受け付け（マージキューが各プルリクエストをスカッシュします）、force-push を拒否します。そのため、各プルリクエストは 1 つのコミットとして `main` に入ります。プルリクエストのブランチも線形に保ちます。

- `main` でもプルリクエストのブランチでも、マージコミットは作成しません。ブランチに `main` をマージせず、コンフリクトをマージコミットで解決しないでください。
- ブランチが `main` とコンフリクトしている場合は、`gh pr update-branch --rebase`、または `git fetch origin` と `git rebase origin/main` で `main` にリベースしてブランチを最新にします。コンフリクトのないプルリクエストは、マージするためにリベースする必要はありません。マージキューが最新の `main` の上でテストします。
- 複数のコミットを持つプルリクエストを GitHub がリベースできない場合は、`main` の上に 1 つのコミットとして入れ直します。ブランチをマージベースで 1 つのコミットにまとめてからそのコミットをリベースすると、各コンフリクトを一度解決するだけで済みます。

```sh
git fetch origin
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -m "feat(course): reorder the catalogue from the course list"
git rebase origin/main
git push --force-with-lease
```

- 書き換えたブランチは `git push --force-with-lease` でプッシュし、対象は自分のプルリクエストのブランチだけにします。`main` やほかの人のブランチに force-push してはいけません。また、最後の fetch 以降にプッシュされたコミットを上書きする単なる `--force` は使用しないでください。

## プルリクエスト

- **小さく、目的を絞る。** 1 つのプルリクエストには、1 つの修正、1 つの機能、または 1 つのリファクタリングだけを含めます。大きな機能は、動画、コース、コースの管理画面がそうだったように、それぞれ単独でレビューできるプルリクエストの積み重ねにします。
- **タイトルがスカッシュコミットになる。** 絵文字を付けずにコミットの形式を使ってください。タイトルが `main` での件名になり、GitHub がその末尾に `(#<number>)` を付けます。`scripts/enqueue-pr.ts` は、プルリクエストをマージキューに入れるときに、コミットフックが付けるはずの絵文字を追加します。
- **説明**には、何をなぜ変更したかを書く `## Summary`、実行したコマンドとその結果を書く `## Test plan`、更新したページ、README のセクション、文言を列挙する `## Docs` を含めます。マーケティング的な表現を使わず、平易に書いてください。
- **すべてのプルリクエストは、自分が不正確にしたものを更新する。** README、すべてのロケールのドキュメントページ、そして影響するサイトの文言やランディングページの主張です。さらに、自分の[変更履歴のエントリ](#changelog-entries)を追加します。変更していないコードで見つけた不正確な点は、別のプルリクエストで扱います。 README はコードの値を表示できないため、代わりに `src/__test__/readme.test.ts` が README を読み取ります。記載されたバージョン、ポート、件数、しきい値はすべてコードまたは `REPOSITORY_FACTS` の値と一致しなければならず、それ以外の数値は日付かテストが列挙する外部の事実でない限り失敗します。また、すべての `bun run` コマンドは `package.json` のスクリプトを指し、記載されたファイル、ルート、lint ルールはすべて存在しなければなりません。

## マージ [#merging]

プルリクエストが `main` に入る経路は、GitHub のマージキューだけです。チェックが成功し、変更履歴のエントリが揃ったら、番号を指定してキューに入れます。

```sh
bun scripts/enqueue-pr.ts 280
```

このスクリプトは、タイトルがコミットの形式に従っていなければ失敗し、タイトルをコミットフックが書くはずの件名に絵文字も含めて設定してから、`gh pr merge --auto --squash` を実行します。これにより、チェックが成功した時点でプルリクエストがキューに追加されます。キューは各プルリクエストを、`main` とその前に並んでいるプルリクエストの上で、そのプルリクエストが実行したのと同じチェックでテストし、一度に複数をビルドして、グループ内の各プルリクエストが成功したらそのグループをまとめて取り込みます。そのため、準備のできたプルリクエストをマージするために誰かがリベースする必要はありません。キューで失敗したプルリクエストはキューから外れます。修正して、もう一度キューに入れてください。プルリクエストを手動で、またはキューを迂回してマージしてはいけません。`main` に入るコミットをテストしたのはキューの実行であり、キューを経なかったコミットについては `deploy.yml` がすべてのチェックを再実行します。

## 変更履歴のエントリ [#changelog-entries]

すべてのプルリクエストは[変更履歴](/docs/project/changelog)に専用のエントリを追加します。そのため、同時に開いているプルリクエストが同じファイルを編集することはありません。

- **プルリクエストの番号で名前を付ける。** プルリクエストを開いてから、すべてのロケールに `content/changelog/<number>.<locale>.mdx` を追加します。中身はフロントマターのない箇条書きで、コードを使う人にとって何が変わったかを書き、影響するドキュメントページにリンクします。
- **日付もプルリクエストの番号も書かない。** 変更履歴のページは各エントリの日付を、リリースノートは各エントリのリリースを Git の履歴から取ります。GitHub が件名の末尾に `(#<number>)` を付けたスカッシュコミットの日付（UTC）です。プルリクエストがマージされるまで、そのエントリは**未リリース**の下に表示されます。番号はファイル名から取ります。ページはエントリの各項目の末尾にそのプルリクエストへのリンクを付け（コミット名のエントリにはそのコミットへのリンクを付けます）、リリースノートは各項目の末尾に `(#<number>)` を付けます。GitHub がこれをリンクにします。デプロイ後は、ページが各エントリを、そのエントリを最初に出荷した[リリース](/docs/tooling/ci-cd#releases-and-tags)にもリンクします。
- **CI が確認する。** プルリクエストでは、`content/changelog/<number>.en-US.mdx` がない間 `bun run check` が失敗し、`check:i18n` はドキュメントページと同じように各翻訳をこのファイルと比較します。プルリクエスト番号でも完全なコミットハッシュでもない名前のファイルも失敗します。プルリクエストを経ずに `main` に入った少数の変更は、そのコミットの名前を使います。
- **未リリースにしてよいのは自分のエントリだけ。** CI では、変更履歴が**未リリース**の下に載せるべきでないエントリを載せることになる間、サイトのビルドが失敗します。`main` へのプルリクエストではそのプルリクエスト自身のもの以外のすべてのエントリ、マージキューと `main` ではすべてのエントリが対象です。マージキューのブランチには、そのグループのすべてのプルリクエストのスカッシュコミットがすでに含まれているため、それらのエントリにはそれぞれ日付があります。`GITHUB_REF` のないローカルビルドは、マージされていないエントリをすべて表示します。これで、プルリクエストより長く残ったエントリが見つかります。`content/changelog/219.<locale>.mdx` は #219 がマージされずにクローズされたあとも残り、#220 のエントリを繰り返し、#254 で削除されるまで本番環境で**未リリース**として表示されていました。

## チェック

CI は `bun run check` と `bun run test:coverage` を実行し、テスト用 Worker をビルドして Chromium でブラウザーのスイートを実行し、プレビュー用 Worker をトラフィックを処理しないバージョンとして Cloudflare にアップロードします。このアップロードが、Cloudflare が Worker を受け入れることを確かめるチェックです。ほかのチェックがすべて成功したのに、Cloudflare のアップロードの制限によってデプロイが失敗したことがあります。マージキューは、プルリクエストを `main` およびその前に並んでいるプルリクエストと組み合わせて、同じチェックをもう一度実行します。[CI/CD](/docs/tooling/ci-cd) を参照してください。
