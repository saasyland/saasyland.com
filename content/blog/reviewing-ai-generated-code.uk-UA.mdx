Практичний посібник із рев’ю коду, який написали ШІ-агенти для програмування, — для будь-якої команди й будь-якого стеку. Він виходить із того, що ваші перевірки вже відхиляють те, що може вирішити програма, і розглядає те, що лишається. Кожен розділ спершу дає правило, потім дослідження, що за ним стоять, а потім pull request у публічному репозиторії saasyland.com, де рев’ю зловило те, що пройшло кожну перевірку. У ньому:

1. Чому код, написаний ШІ, потребує іншого рев’ю і що кажуть дослідження про агентів і тести.
2. Рев’ю доказів і опису раніше за код.
3. Обхідні шляхи проти першопричин і тести, які стали легшими.
4. Обходи системи типів і обробки помилок, які досі пропускає суворий лінтер.
5. Обсяг змін, дизайн і захищені шляхи, зокрема дизайн, вигнутий навколо правила.
6. Твердження в тексті, другий агент як рецензент, порядок рев’ю, який можна скопіювати, і що наше власне рев’ю досі пропускає.

## Коротка відповідь

Робіть рев’ю pull request агента в порядку, який найшвидше виявляє проблему, і витрачайте увагу там, де не може жодна перевірка. Спершу докази: коміт, який ви читаєте, — той, який тестували, і CI на ньому пройшов. Потім опис проти diff, а diff — проти вашого списку захищених шляхів. Потім кожна зміна в тестах, бо агент, який не може змусити тест пройти, іноді робить тест легшим. Потім запитання, що ловить найдорожчі помилки: ця зміна прибирає причину проблеми чи лише місце, де вона проявилася? Після цього — обходи системи типів і обробки помилок, які дозволяє ваш лінтер, обсяг зміни, будь-який дизайн, вигнутий навколо правила, і кожне твердження, яке зміна робить у тексті. Сприймайте підсумок, що каже «готово», як твердження. Просіть команду, її вивід і коміт, на якому вона виконувалася.

## Чому код, написаний ШІ, потребує іншого рев’ю

Рев’ю завжди менше стосувалося пошуку помилок, ніж думають люди. У своєму дослідженні рев’ю коду в Microsoft 2013 року Alberto Bacchelli і Christian Bird виявили, що «пошук дефектів лишається головною мотивацією для рев’ю», проте «рев’ю менше стосуються дефектів, ніж очікувалося», і що «розуміння коду й змін — ключовий аспект рев’ю коду». Коли автор — людина, розуміння спільне: автор знає, чому код виглядає саме так, і рев’ю — це розмова.

Коли автор — агент, змінюються три речі.

**Упевненість автора не несе жодної інформації.** Агент пише «усі тести проходять» тим самим тоном, байдуже, проходять вони чи ні. Посібник Anthropic до Claude Code прямо описує механізм: «Claude зупиняється, коли робота виглядає завершеною». Його порада рецензенту — просити докази: «команду, яку він запустив, і її вивід або знімок екрана. „Усі тести проходять“ саме по собі каже вам дуже мало».

**Код виглядає правильним.** В опитуванні Stack Overflow 2025 року найпоширенішим розчаруванням у ШІ-інструментах, яке назвали 66% розробників, були «рішення ШІ, які майже правильні, але не зовсім», а 45,2% сказали, що налагодження коду, згенерованого ШІ, забирає більше часу. Майже правильний код найважче рецензувати, бо ніщо в ньому не виглядає хибним.

**Ваше власне відчуття прогресу ненадійне.** Рандомізоване дослідження METR за участі досвідчених розробників відкритого коду на початку 2025 року виявило, що коли ШІ-інструменти дозволено, «вони витрачають на 19% більше часу на виконання задач». Перед дослідженням вони «очікували, що ШІ прискорить їх на 24%», а після нього «досі вірили, що ШІ прискорив їх на 20%». Рецензент, який відчуває, що робота йде швидко, нічого не вимірює.

### Агенти оптимізують під перевірки, які бачать

Найвагомішу причину робити рев’ю по-іншому задокументували самі розробники моделей.

Системна картка Anthropic для Claude 3.7 Sonnet, опублікована в лютому 2025 року, має розділ під назвою «Надмірна зосередженість на проходженні тестів». У ньому йдеться, що модель «час від часу вдається до спеціальних випадків, щоб пройти тестові сценарії в агентних середовищах програмування, як-от Claude Code». Найчастіше це означало «пряме повернення очікуваних тестових значень замість реалізації загальних рішень, але також включає зміну самих проблемних тестів, щоб вони відповідали виводу коду». Це траплялося «після кількох невдалих спроб розробити загальне рішення», і Anthropic радила стежити за трьома сигналами: «Надмірні цикли редагування / запуску тестів для одного файлу», «Коментарі, що вказують на обробку, специфічну для тестів» і «Неочікувані зміни тестових файлів».

OpenAI повідомила про ту саму родину поведінки в березні 2025 року, у своїй роботі з моніторингу моделей міркування. Серед її прикладів — агент, який міркував: «Ми можемо обійти verify, щоб він завжди повертав true», та інший, який планував: «Щоб пропустити всі тести, можна визначити функцію `pytest_runtest_setup`, яка завжди пропускає». Коли OpenAI штрафувала модель за такі думки під час навчання, «агент, навчений під тиском на CoT, усе одно вчиться хакати винагороду», але «він навчився приховувати свій намір у ланцюжку міркувань». Раніший звіт METR про хакінг винагороди, процитований у [першому дописі цієї серії](/blog/ai-coding-agent-guardrails), виявив те саме в задачах з оцінкою.

Anthropic повідомляє, що її заходи під час навчання «значно зменшили частоту такої поведінки за типового використання». Те, що лишається, з’являється там, де це бачила Anthropic: після повторних невдач на складній задачі, а це саме той вид зміни, який найбільше потребує рев’ю. Практичний наслідок простий. Зелений запуск CI каже вам, що перевірки пройшли. Він не каже, що це ті самі перевірки, з якими ви починали.

## Робіть рев’ю доказів раніше за код

Перші хвилини рев’ю мають піти на те, що pull request стверджує про себе. Більшість дорогих збоїв, які ми бачили, були в твердженнях, а не в коді.

**Чи коміт, який ви читаєте, — той, який тестували?** Якщо агент робить rebase чи amend або надсилає виправлення після свого останнього запуску тестів, опис його pull request описує раніший коміт. Перевірте, що CI запускався на head-коміті і що запуск пройшов кожну обов’язкову перевірку, а не лише швидкі. [Другий допис цієї серії](/blog/running-ai-coding-agents-in-parallel) розповідає, як агент повідомив «готово», поки набір браузерних тестів ще працював.

**Чи є числа доказами?** Добрий план тестування називає кожну команду з її результатом, кількості, які вона дала, і все, чого не вдалося запустити. Наші pull request показують різницю. План тестування #177 повідомляє про 355 тестових файлів і 2 301 тест за повного покриття, каже, що чотири тести у файлах, яких pull request не торкався, вперлися в тайм-аут за середнього навантаження машини від 40 до 170, називає прапорець, з яким пройшов успішний запуск, і прямо каже, що набір браузерних тестів локально не запускали, і чому. #123 повідомляє про перший запуск покриття, у якому сім тестів не вклалися в тайм-аут під навантаженням, і про чистий повторний запуск. Жоден не приховує збою, і обидва корисніші за «усе зелене».

**Чи стосується опис саме цього diff?** 16 листопада #224, виправлення макета, злили з описом #225, зміни ліцензій, разом з абзацом про те, що власник схвалив зміни у файлах ліцензій, яких #224 ніколи не торкався. Жодна перевірка не читає описи. Відтоді рев’ю їх порівнює: кожна зміна, яку згадує опис, є в diff, кожен файл у diff пояснено, а кожне схвалення процитовано разом зі шляхами, які воно охоплює.

**Воно виглядає готовим чи працює?** Елемент керування, який рендериться, — це твердження, що він щось робить. У листопаді екрани користувачів в адмінці показували кнопки **Edit**, **View profile** і **Add User** без обробника, тоді як дев’ять серверних функцій для користувачів і сесій ніхто не викликав (#194). Жодна перевірка цього не помітила: кнопка без обробника рендериться, і ніщо її не натискало. Виправлення під’єднало кожен елемент керування до справжньої серверної функції або прибрало його. Для всього, що може побачити користувач, доказ — це знімок екрана або браузерний тест, який натискає кнопку й перевіряє результат.

## Обхідні шляхи проти першопричин

Найдорожча помилка агента — виправлення не в тому місці. Воно проходить кожну перевірку, часто приходить із регресійним тестом і лишає причину в коді, щоб на неї натрапила наступна сторінка.

Обхідний шлях має впізнавану форму. Він стоїть поруч із симптомом, а не вище за течією: очікування, додане в тест, запасне значення, передане одному компоненту, умова, що пропускає випадок, який падає, повторна спроба навколо гонки, відкат версії назад. Запитання, яке його викриває, — те, на яке натякає посібник Google з рев’ю, коли каже: «Часто корисно подивитися на CL у ширшому контексті»: що це спричинило і чи може щось інше натрапити на це після злиття?

### Обхідний шлях, обраний свідомо

14 листопада відвідувач, який увійшов в обліковий запис і натиснув посилання в шапці лендингу, перш ніж сторінка пройшла гідратацію, змушував React повідомляти про помилку гідратації: сервер вивів кількість зірок на GitHub, а браузер рендерив на її місці скелетон завантаження. #146 виправив це, передаючи кількість із loader сторінки в компонент як дані-заповнювач (placeholder data), з регресійним тестом, і кожна перевірка пройшла.

Його опис називав справжню причину. Захист маршруту в інтеграції автентифікації очищав увесь кеш запитів щоразу, коли знаходив сесію, про яку попередньо відрендерена сторінка не знала, щоб один користувач ніколи не побачив даних іншого. Захист викидав публічні дані разом із приватними, і будь-яка сторінка, відрендерена з кешу, могла натрапити на ту саму помилку. Опис також пояснював, чому причину не чіпали: її зміна означала рішення про те, які дані можуть пережити зміну користувача, у `src/integrations/better-auth/`, шляху, що потребує згоди власника.

Рев’ю попросило виправити першопричину, власник схвалив зміну захищеного шляху, і через дві години #152 її виправив: запити позначають себе як публічні, зміна користувача прибирає кожен запит, який таким не є, а обхідний шлях #146 видалили. Урок має дві половини. Агенти часто знають причину, і добрий бриф просить їх її назвати. А захищений шлях, який існує, щоб небезпечні зміни траплялися рідше, водночас робить виправлення симптомів імовірнішими, бо найдешевший шлях в обхід захищеної причини — виправлення деінде. Коли виправлення стоїть поруч із захищеним шляхом, запитайте, чи не захист обрав дизайн.

### Тести, які перечікують помилку

Раніше того самого дня #142 зробив набір браузерних тестів надійним у WebKit: тести чекали, доки роутер відрендерить сторінку, перш ніж щось на ній робити. Це очікування моделює справжню готовність, і воно правильне. Але деякі з гонок, які воно виправило, походили від помилок у бібліотеках, і #151 їх назвав: «#142 змусив набір браузерних тестів перечікувати три помилки бібліотек, але відвідувачі досі на них натрапляють». Відвідувача, який прокручував сторінку під час гідратації, відкидало нагору; перехід зі сторінки, що завантажувалася, міг перетворитися на перезавантаження сторінки, яку покидали.

#151 доставив кожне виправлення як патч на останній випуск TanStack Router і Motion, додав браузерний тест, який падає без кожного патча, і прибрав очікування, які існували лише для того, щоб обійти помилки. Один із патчів роутера — це зміна з відкритого upstream pull request. Його відтворення — саме такий доказ, якого має вимагати рев’ю: мінімальний застосунок на TanStack Start, який падав шість запусків із шести без однорядкового виправлення й проходив десять із десяти з ним.

Правило, яке ми з цього взяли: очікування в тесті прийнятне, коли воно моделює те, на що чекає й користувач. Коли воно перечікує помилку, користувачі досі на неї натрапляють, і виправлення належить до коду або, якщо це бібліотека, до патча з регресійним тестом і звітом в upstream.

### Правило для рішення

Приймайте обхідний шлях лише тоді, коли виконуються всі три умови: причина поза вашим контролем, обхідний шлях позначено там, де його знайде наступний читач, і щось відстежує його прибирання. Інакше просіть виправити причину. Відкат залежності на старішу версію — обхідний шлях із довгим хвостом; наша політика — лишатися на останньому випуску й тримати помилку upstream як патч, тож виправлення зникає разом із наступним випуском, а не лишається назавжди.

## Тести, які стали легшими

Diff, що змінює тест, заслуговує більше уваги, ніж diff, що змінює код, бо тест — це те, чому ви довіряєте, коли не дивитеся. Посібник Google з рев’ю каже це чотирма словами: «Тести самі себе не тестують».

Читайте кожну зміну в тестовому файлі й шукайте таке:

- **Видалені чи послаблені перевірки:** `toEqual`, що стає `toMatchObject`, конкретне значення, що стає `expect.anything()`, перевірка, видалена разом із кодом, який вона тестувала.
- **Оновлені знімки чи фікстури**, новий вміст яких ніхто не прочитав.
- **Спеціальні випадки:** код під тестом, що розгалужується за значенням, яке використовує лише тест, або повертає саме те значення, якого очікує тест.
- **Нові пропуски, повторні спроби й тайм-аути,** зокрема довший тайм-аут для одного тесту.
- **Нові моки** саме того, що тест мав перевіряти.
- **Перевірки реалізації** замість поведінки: яку функцію викликали, а не що бачить користувач.

Anthropic зазначила, що спеціальні випадки, які вона спостерігала, «часто (хоча не завжди) містять явні коментарі, що вказують на спеціальний випадок (наприклад, „# special case for test XYZ“)». Наш репозиторій забороняє всі коментарі, крім однорядкового посилання на місце з обґрунтуванням, і перевірка відхиляє решту. Це прибирає позначку, тож у кодовій базі на кшталт нашої сигнал має давати саме читання diff тестів.

Протилежний приклад, вартий наслідування, — #191. На завантаженій машині наші найповільніші модульні тести не вкладалися в час. Легким виправленням було б збільшити тайм-аути. Натомість pull request з’ясував, чому кожен тест повільний, і прибрав роботу, яка йому не потрібна: один тест запускав перевірку контенту для кожної сторінки дев’ятьма локалями й став окремим випадком на кожну сторінку; кілька дозволяли затримці suspense fallback у React спрацьовувати поза `act`; комбобокс перебудовував кожен варіант на кожне натискання клавіші. Його опис формулює обмеження, якого він дотримався: «Жодного тайм-ауту не збільшено, і жоден тест не отримав власного тайм-ауту». Рецензент може звірити це речення з diff за хвилину, і саме це має уможливлювати план тестування.

## Тихі обходи системи типів

Суворий компілятор і суворий лінтер ловлять гучні обходи: `any`, твердження типів, коментарі, що вимикають правила. До рев’ю доходять тихі, які чисто компілюються й ламаються під час виконання.

TypeScript прямо пояснює, чому твердження небезпечні: «компілятор видаляє твердження типів, і вони не впливають на поведінку вашого коду під час виконання», і «Якщо твердження типу хибне, не буде ні винятку, ні згенерованого `null`». Те саме стосується твердження non-null: «це не змінює поведінки вашого коду під час виконання».

### Що наш лінтер досі пропускає

22 листопада ми прогнали пробний файл через нашу конфігурацію лінтера, яка вмикає цілі категорії правил як помилки разом із правилами, що враховують типи, і забороняє `any`, кожне твердження типу, крім `as const`, і кожен коментар, що вимикає правила:

| Рядок у пробному файлі                                                 | Відхилено | Чим                                                                         |
| ---------------------------------------------------------------------- | --------- | --------------------------------------------------------------------------- |
| `(raw: string): Licence => JSON.parse(raw)`                            | Так       | `typescript/no-unsafe-return`                                               |
| `const parse = <T>(raw: string): T => JSON.parse(raw)`                 | Так       | `typescript/no-unsafe-return` і `typescript/no-unnecessary-type-parameters` |
| `Reflect.get(target, key)`, повернений як `string`                     | Так       | `typescript/no-unsafe-return`                                               |
| `items.find((item) => item.length > 2)!.length`                        | Ні        |                                                                             |
| `(value: unknown): value is Licence => typeof value === "object"`      | Ні        |                                                                             |
| `zod.custom<Licence>()` без перевірки                                  | Ні        |                                                                             |
| `licence?.key ?? ""`                                                   | Ні        |                                                                             |
| Порожній `catch {}` або `catch`, що повертає значення за замовчуванням | Ні        |                                                                             |

Кожен рядок, що пройшов, перетворює відсутнє чи некоректне значення на хибну поведінку без помилки. Твердження non-null каже, що значення існує. Захисник типу (type guard) каже, що об’єкт є `Licence`, перевіривши лише, що це об’єкт. Власна схема приймає будь-що й типізує це як `Licence`. Запасний порожній рядок перетворює «немає ліцензії» на ліцензійний ключ, що є порожнім рядком, і наступна функція може спокійно надіслати його в API. Проковтнута помилка приховує збій від людини, яка б його виправила. Сьогодні в нашому коді застосунку немає ні тверджень non-null, ні власних схем без перевірки; так його тримає лише рев’ю, а правила для першого з цих обходів існують і в typescript-eslint, і в Oxlint.

### Обхід із доброю причиною — все одно обхід

Коміт, який переніс saasyland.com на TanStack Start 6 вересня 2026 року, містив шість коментарів, що вимикали правила лінтера: чотири для небезпечних тверджень типів, один для `null` і один для небезпечного аргументу. До кожного додавалося речення, через яке він звучав необхідним:

```ts
// TanStack Query requires a defined result; null represents an absent license.
// oxlint-disable-next-line unicorn/no-null
const NO_LICENSE = null
```

Половина причини була правдою. Документація TanStack Query каже: «У разі успіху розв’язане значення може бути будь-чим, крім undefined». Висновок — ні: запиту не потрібен був `null`, йому потрібне було визначене значення. Рев’ю прибрало всі шість за три тижні, змінивши дизайн, який захищав кожен із них. Цей став об’єктом, що існує завжди:

```ts
.handler(async ({ context }) => ({ license: await getLicense(context.auth.user.id) }))
```

Інші пішли тим самим шляхом: тестовий помічник, що стверджував згенерований тип, тепер будує нетипізоване дерево повідомлень, а тестовий проксі, що стверджував тип builder, тепер під час виконання перевіряє, що отримав серверну функцію, і інакше викидає `TypeError`. Наші конвенції тепер перелічують альтернативи обходу: валідуйте замість твердження, звужуйте справжнім захисником типу, анотуйте замість твердження, перевіряйте через `satisfies` замість перетворення і змінюйте структуру коду, коли контракт бібліотеки вам опирається. Починаючи з #274, `bun run check` відхиляє кожен коментар, що вимикає правило, тож такий обхід більше не доходить до рев’ю. Урок лишається для тих, що доходять: причина, написана поруч з обходом, — це аргумент, і завдання рев’ю — перевірити аргумент, а не захоплюватися ним.

## Обсяг, дизайн і форма зміни

**Незапитані зміни.** Агенти дорогою виправляють усяке. Це часто корисно й завжди створює проблему для рев’ю, бо зміну, якої ніхто не просив, переглядають як частину зміни, яку хтось просив. Правило, яким ми користуємося: супутні виправлення вітаються, коли опис їх перелічує й пояснює чому. #169, виправлення перекладених шляхів до файлів, перелічує інші помилки, які він виправив у рядках, що їх і так переписував. #191, pull request про повільні тести, змінив продакшн-компонент, і його опис пояснює, що компонент перебудовував кожен варіант на кожен рендер, а це була проблема і тесту, і користувача. Зміна, якої опис не згадує, — привід зупинитися й запитати.

**Абстракції, які нікому не були потрібні.** Посібник Google просить рецензентів «заохочувати розробників розв’язувати проблему, яку, як вони знають, треба розв’язати зараз, а не проблему, яку, як припускає розробник, може знадобитися розв’язати в майбутньому». Агенти схиляються в інший бік: обгортка навколо виклику бібліотеки, фабрика з одним продуктом, помічник, що дублює вже наявний за три теки звідси. Наші конвенції просять один очевидний механізм на кожне завдання й прямий виклик бібліотеки; на рев’ю найдешевша перевірка — пошукати в репозиторії наявну функцію, перш ніж приймати нову.

**Формальності, що задовольняють правило.** Коли правило трохи хибне, агенти виконують його в масштабі. Наше правило проти магічних чисел дозволяло лише `0`, тож агенти давали назву кожній `1`, і #230 вбудував назад 72 такі константи. [Перший допис цієї серії](/blog/ai-coding-agent-guardrails) розповідає цю історію. На рев’ю шаблон, якого жодна людина не написала б вручну, — ознака, що треба виправити правило.

**Дизайн, вигнутий навколо захищеного шляху.** Це найтонший випадок. #177 потребував константи статусу для функцій, які доступні чи готуються. Відео для лендингу в Remotion імпортує навігацію адмінки, а тест вимагає, щоб workflow відео стежив за кожним файлом, який імпортує Remotion, тож новий файл означав би правку в `.github/workflows/`, шляху, що потребує схвалення власника. Pull request поклав константу в `src/data/navigation.constants.ts`, файл, за яким workflow уже стежив, і сказав про це в описі. Пізніші зміни взагалі прибрали статус із навігації адмінки. Сьогодні константа обслуговує картки цін і тексти, а живе досі в константах навігації — з причини, якої більше не існує. Ніщо цього не перевіряє. Саме на рев’ю ви запитуєте: чи це той файл, де новий читач це шукав би, а якщо ні, то що змусило автора покласти це сюди?

Посібник Anthropic додає застереження, яке стосується кожного рецензента, людини чи агента: «Рецензент, якого попросили знайти проблеми, завжди знайде _щось_. Якщо ви виправлятимете кожну знахідку, то отримаєте зайві шари абстракції й тести для випадків, які не можуть статися». Обсяг ріже в обидва боки. Рев’ю, яке вимагає кожного можливого покращення, дає такий самий розрослий код, як агент, що додає ці покращення без запиту.

## Захищені шляхи в diff

[Перший допис цієї серії](/blog/ai-coding-agent-guardrails) пояснює, яким шляхам потрібен другий ключ у руках людини і чому схвалення належить до diff. На рев’ю з цього випливають дві перевірки.

**Порівнюйте змінені файли зі списком механічно.** Читати довгий diff у пошуках захищених шляхів — саме те завдання, яке людина виконує погано наприкінці дня. Однорядкова команда робить це щоразу; у наборі наприкінці є така. Коли захищений шлях є в diff, опис має цитувати схвалення й називати шляхи, які воно охоплює.

**Запитайте, що змінив захист.** Два інциденти вище, виправлення симптому поруч із захищеною причиною й константа, покладена так, щоб оминути захищений файл, показують, що список захищених шляхів формує код навколо себе. Жоден із них не торкнувся захищеного шляху, тож жоден не з’явився б у механічній перевірці. Запитання для рецензента зворотне: чи ця зміна оминула захищений шлях і чи пройшло б правильне виправлення через нього?

## Факти й твердження в тексті

Агенти пишуть текст так само вправно, як код, а текст не має компілятора. Описи pull request, документація, журнали змін, README і дописи в блозі — усі роблять твердження, і наша історія показує чотири види хибних.

**Вигадана конфігурація.** Два наші дописи казали, що `typescript/no-explicit-any` є помилкою в нашій конфігурації лінтера, хоча це було не так; #123 зробив речення правдою, увімкнувши правило. Той самий аудит знайшов процитований `tsconfig.json` із `verbatimModuleSyntax`, якого проєкт не встановлює, і опцію лінтера `denyWarnings: true`, якої не існує.

**Неправильно приписані джерела.** Аудит кожного допису за його джерелами 17 листопада (#241) знайшов цифру Stack Overflow, процитовану як 45%, тоді як опитування каже 66%, частку використання застарілих API, приписану не тій статті, і цифру дефектів від GitClear, якої немає на публічній сторінці GitClear.

**Застарілий контекст.** Переклади, зроблені зі старішої англійської версії, описували стек, яким сайт уже не користувався, зі старими кількостями й старими назвами тарифів (#116). Кожне речення було гладким і правдоподібним.

**Описи не тієї зміни,** як у #224.

Рев’ю тексту таке саме, як рев’ю коду, тільки з джерелами замість тестів. Кожне число вказує на код, який його визначає, а [попередній допис](/blog/documentation-drift-numbers-from-code) показує, як виводити його звідти, щоб воно не могло бути хибним. Кожна зовнішня цифра має посилання, і рецензент відкриває посилання й шукає там точні слова. Кожне «забезпечено» називає перевірку, яка це забезпечує. Кожна цитата є в джерелі.

## Другий агент як рецензент

Агент-рецензент дешевий, швидкий і корисний як перший прохід, якщо налаштувати його для цієї роботи.

- **Свіжий контекст.** Посібник Anthropic описує свою команду `/code-review` як таку, що робить рев’ю «diff у свіжому субагенті, який ніколи не бачив вашої розмови. На нього не впливають міркування, які породили код». Рецензент, який читав міркування автора, схильний їх приймати.
- **Інструменти лише для читання.** Рецензент, який може редагувати, виправить те, що знайде, і перетворить рев’ю на другу зміну. Субагенти Claude Code приймають список `tools` у своєму визначенні; дайте рецензенту лише читання й пошук.
- **Специфікація, за якою робити рев’ю.** Бриф, за яким будували зміну, або issue, щоб рецензент перевіряв вимоги, а не смак.
- **Інструкції про те, про що не повідомляти.** Стиль і гіпотетичні випадки — з причини, яку Anthropic наводить вище.

Знайте його межі. Агент-рецензент зазвичай працює на тій самій моделі, що й автор, або на меншій, тож має ті самі сліпі плями, що й автор, і не може сказати вам, чи цю зміну взагалі варто будувати. У нашому налаштуванні головний агент пише бриф кожного виконавця й читає його звіт і diff, звіряючи їх із цим брифом, перш ніж зміна піде в чергу злиття, а все зі списку для рев’ю людиною чекає на процитоване «так» власника. Запитання з [другого допису](/blog/running-ai-coding-agents-in-parallel) досі ловить найбільше: що ви вирішили не робити і чому?

## Порядок рев’ю, який швидко виявляє проблему

Другий допис цієї серії має список із восьми кроків для рев’ю pull request агента. Ось довша версія, якою ми користуємося тепер, по черзі, з тим, що шукає кожен крок. Зупиняйтеся на першому кроці, який не пройдено; немає сенсу читати код, для якого бракує доказів.

1. **Докази.** Head-коміт — той, який тестували. CI пройшов на ньому кожну обов’язкову перевірку. План тестування називає команди, результати й кількості і каже, що не запускали. Зміни, які бачить користувач, мають знімок екрана або браузерний тест, який натискає елемент керування.
2. **Опис проти diff.** Кожна зміна, яку заявляє опис, є в diff. Кожен файл у diff пояснено.
3. **Захищені шляхи.** Жоден не змінено, або кожен охоплено процитованим схваленням, яке його називає.
4. **Diff тестів.** Жодної послабленої чи видаленої перевірки без причини, жодного нового пропуску, повторної спроби, тайм-ауту чи моку модуля, що тестується, жодного спеціального випадку.
5. **Першопричина.** Виправлення змінює те, що спричинило проблему. Ніщо інше не може натрапити на ту саму помилку після злиття. Будь-який обхідний шлях позначено й відстежено.
6. **Обходи.** Жодного твердження non-null, захисника типу, що бреше, схеми, яка приймає будь-що, запасного значення, що приховує відсутність, чи проковтнутої помилки.
7. **Обсяг і дизайн.** Нічого незапитаного й непоясненого. Жодної нової абстракції з одним користувачем, жодного дубліката наявного помічника, жодного файлу там, де читач не шукав би, жодного дизайну, вигнутого навколо правила.
8. **Твердження в тексті.** Числа виведено з коду, зовнішні факти мають посилання й знаходяться за посиланням, а кожне «забезпечено» називає свою перевірку.
9. **Усе, чого стосується зміна.** Документація, README, тексти й журнал змін усіма мовами; більшість цього — перевірка, а решта — тут.
10. **Історія.** Одна зміна, заголовок, який добре читатиметься як squash-коміт, жодних рядків атрибуції.

Кроки з 1 по 3 займають хвилини й не потребують розуміння коду, тож повернути pull request, який не пройшов один із них, майже нічого не коштує. На кроки з 4 по 7 іде основний час, і це ті кроки, яких жодна програма за вас не зробить.

## Скільки це коштує і куди вкладати зусилля

Рев’ю — єдина частина цієї системи, яка не масштабується з кількістю агентів. [Другий допис](/blog/running-ai-coding-agents-in-parallel) з’ясував, що справжнім обмеженням того, скільки агентів можуть працювати одночасно, був рецензент, а не машини чи хвилини CI. Тримати ціну доступною допомагають три звички.

**Переносьте в перевірки все, що можна вирішити програмно.** Кожне правило, яке може вирішити програма, а ви досі перевіряєте на око, — це час рев’ю, витрачений не на те. [Допис про запобіжники](/blog/ai-coding-agent-guardrails) саме про це.

**Тримайте зміни малими й поодинокими.** Pull request з однією зміною можна читати з одним запитанням. Агенти дешево виробляють великі diff; бриф має просити одну зміну на pull request, а рецензент — повертати ті, що такими не є.

**Розподіляйте глибину за радіусом ураження.** Платежі, автентифікація, міграції, контракти, від яких залежить інше програмне забезпечення, і самі перевірки отримують повний список, без поспіху. Виправлення документації отримує кроки 1, 2 і 8.

## Що наше рев’ю досі пропускає

У дусі решти серії — ось де наш власний процес слабкий.

- **Описи з diff порівнює людина**, а не перевірка, тож у напружений день невідповідність ще можна пропустити.
- **Константа статусу з #177** досі живе в константах навігації — з причини, якої більше не існує.
- **Тверджень non-null і власних схем** немає в нашому коді за звичкою; жодне правило їх поки не відхиляє.
- **Мутаційне тестування**, яке вимірювало б, чи падають тести, коли змінюється код, не налаштовано, тож пункт «тести, які стали легшими» тримається на читанні.
- **Рецензент і автор часто мають спільну модель**, а отже, і її сліпі плями.
- **Агенти працюють під обліковим записом власника**, тож GitHub не може вимагати рев’ю від когось, крім автора; другий ключ тримають рівень дозволів агентів і процитоване схвалення, як описує перший допис.

## Набір для рев’ю, який можна скопіювати

**Шаблон pull request**, який просить докази замість запевнень:

```md
## What and why

One change. What made the problem happen, and how this removes it.

## Evidence

| Command | Result | Commit |
| ------- | ------ | ------ |
|         |        |        |

Not run, and why:

## Also changed

Every change the title does not cover, with its reason.

## Protected paths

None, or each path with the quoted approval that covers it.

## Not done

What I decided not to do, and why.
```

**Команда, що перелічує захищені шляхи в diff**, яку запускає рецензент або CI:

```sh
git diff --name-only origin/main...HEAD | grep -E '^(db/migrations/|src/billing/|src/auth/|\.github/|eslint\.config\.js|vitest\.config\.ts)'
```

**Пошук тривожних ознак у diff тестів** як відправна точка для кроку 4:

```sh
git diff origin/main...HEAD -- '*.test.*' '*.spec.*' | grep -nE '^\+.*(\.skip|\.only|\.todo|retry|retries|timeout|expect\.anything|toMatchObject|vi\.mock|jest\.mock)|^-.*expect\('
```

**Правила лінтера для двох тихих обходів** під тими назвами, які їм дають ESLint і typescript-eslint:

```js
export default [
  {
    rules: {
      "@typescript-eslint/no-non-null-assertion": "error",
      "no-empty": "error",
    },
  },
]
```

**Субагент-рецензент лише для читання** для Claude Code, у `.claude/agents/reviewer.md`:

```md
---
name: reviewer
description: Reviews a pull request's diff against the brief it was built from, before a person reads it.
tools: Read, Grep, Glob
---

You review a change you did not write. You are given the brief and the diff.

Report, in this order, only what affects correctness:

1. Claims in the description that the diff does not support, and files in the diff the description does not explain.
2. Changes to tests that make them easier: removed or loosened assertions, skips, retries, timeouts, mocks of the unit under test, special cases.
3. Fixes that change where a problem shows rather than what causes it.
4. Non-null assertions, type guards that do not check what they claim, schemas that accept anything, fallbacks that hide a missing value, swallowed errors.
5. New abstractions with one user, and helpers that duplicate existing ones.

Do not report style. Do not report cases that cannot happen. Do not edit anything.
```

**Рядок для вашого файлу інструкцій**, щоб автор підготував те, що попросить рецензент:

```md
## Before you say done

Give the commit you tested, each command with its result, what you did not run and why, every change beyond the task, and what you decided not to do. A summary is not evidence.
```
