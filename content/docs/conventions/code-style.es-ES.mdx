`bun run check` ejecuta `bun run generate:cn`, `bun run check:comments`, `bun run check:i18n` y `bun run check:flows`, y después `vp check`, que formatea con oxfmt, analiza con oxlint y comprueba los tipos con TypeScript en una sola pasada, con la configuración de `vite.config.ts` y `tsconfig.json`. CI ejecuta el mismo comando. Nada de esto es cuestión de gustos: si las herramientas aceptan código que incumple una regla de esta página, la revisión lo rechaza.

## Lo que imponen las herramientas

oxlint trata como errores las categorías `correctness`, `nursery`, `pedantic`, `perf`, `style` y `suspicious`, con las reglas con información de tipos y la comprobación de tipos activadas. Los límites que más condicionan el código:

| Regla                                   | Valor                                                                        | Efecto                                                                       |
| --------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `max-lines`                             | <RepositoryFact name="maxLines" />                                           | Divide un archivo por responsabilidades antes de que crezca                  |
| `max-lines-per-function`                | <RepositoryFact name="maxLinesPerFunction" />                                | Los componentes y los handlers se mantienen pequeños                         |
| `max-statements`                        | <RepositoryFact name="maxStatements" />                                      | Extrae helpers con nombre en lugar de escribir cuerpos largos                |
| `no-magic-numbers`                      | solo se permiten `0` y `1`, además de índices de array y valores por defecto | Cualquier otro número es una constante con nombre                            |
| `id-length`                             | al menos dos caracteres, salvo `_`, `m` y `t`                                | Los identificadores son palabras; `t` es el traductor                        |
| `one-var`                               | `never`                                                                      | Una declaración por sentencia                                                |
| `unicorn/no-null`                       | activada fuera de las pruebas y de `src/platform/testing`                    | Los valores ausentes son `undefined`                                         |
| `typescript/no-explicit-any`            | `error`                                                                      | Ningún valor tiene el tipo `any`                                             |
| `typescript/ban-ts-comment`             | `true` para `@ts-expect-error`, `@ts-ignore` y `@ts-nocheck`                 | No se suprime ningún error del compilador, con o sin motivo                  |
| `typescript/consistent-type-assertions` | `assertionStyle: "never"`                                                    | Ningún cast con `as`; `as const` y `satisfies` siguen permitidos             |
| `code-style/no-comments`                | `error`                                                                      | Ningún comentario, incluidos los comentarios de directiva                    |
| `code-style/no-multiline-ternary`       | `error`                                                                      | Un ternario cabe en una línea                                                |
| `code-style/no-undefined-branch`        | `error`                                                                      | Ningún ternario con una rama `undefined` o `null`, ningún `return undefined` |
| `code-style/no-undefined-fallback`      | `error`                                                                      | Ningún `?? undefined`                                                        |
| `code-style/zod-namespace-import`       | `error`                                                                      | Zod se importa como `* as zod` desde `zod`                                   |
| `radius/no-off-scale`                   | `error`                                                                      | Cada esquina toma un radio de la escala                                      |
| `type/no-off-scale`                     | `error`                                                                      | Cada tamaño de texto es un paso de la escala tipográfica                     |
| `type/mono-for-code`                    | `error`                                                                      | La fuente monoespaciada es solo para código                                  |

Las sobrescrituras son acotadas y se limitan a ciertos archivos: las pruebas y los helpers de prueba compartidos de `src/platform/testing` relajan `no-magic-numbers`, `no-await-in-loop`, `unicorn/no-null`, `hydration/no-clock-or-locale-in-render` y `admin-data/no-literal-data`; `src/presentation` y `src/hooks` relajan `typescript/consistent-return`; los mocks de prueba relajan `require-await`; `src/routes` desactiva `sort-keys`, porque las opciones de ruta siguen su propio orden (consulta [Archivos de ruta](/docs/conventions/routes)); y las rutas, los componentes y los archivos de datos de la administración activan `admin-data/no-literal-data` (consulta [Panel de administración](/docs/features/admin-dashboard#real-data-only)). Todo `src` activa `radius/no-off-scale`, `type/no-off-scale` y `type/mono-for-code`, que las pruebas y `src/platform/testing` vuelven a desactivar, y `src/presentation/social-card.tsx` desactiva `type/no-off-scale`, porque Takumi renderiza la tarjeta social como una imagen de tamaño fijo cuyos tamaños de texto se fijan en estilos en línea y no en la escala tipográfica de la página (consulta [Tema](/docs/ui/theme#type-scale)).

`tsconfig.json` añade los flags estrictos que cambian la forma de escribir el código: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` y `noUnusedParameters`. Una lectura por índice puede ser `undefined`, a una propiedad opcional no se le puede asignar `undefined` de forma explícita y una firma de índice se lee como `record["key"]`.

El formateador escribe sin punto y coma, con comillas dobles, comas finales y un ancho de <RepositoryFact name="printWidth" />. También ordena las importaciones en grupos fijos, las clases de Tailwind en `className` y en las llamadas a `cn`, y los scripts de `package.json` por nombre (`sortPackageJson: { sortScripts: true }`), así que nunca ordenes ninguno de ellos a mano: `vp check` falla cuando alguno está desordenado. Consulta [Lint y formato](/docs/tooling/lint-format) para ver los comandos.

## Renderizar lo mismo que el servidor

Una página se renderiza dos veces: en el servidor y de nuevo en el navegador, cuando React hidrata el HTML. Ambos renderizados deben mostrar el mismo texto; si no, React informa de un error de hidratación (error #418) y vuelve a renderizar la página. Por eso el código de renderizado nunca lee el reloj ni el locale del entorno de ejecución, que difieren entre ambos: nada de `new Date()` sin argumentos, ni `Date.now`, ni `toLocaleString`, `toLocaleDateString` o `toLocaleTimeString`. Usa un valor que ambos lados compartan:

- un tiempo relativo cuenta desde el `dataUpdatedAt` de la consulta que leyó sus datos, como muestra [Internacionalización e idiomas](/docs/features/internationalization);
- un año que muestra el sitio viene de la build: el pie de página termina su copyright en `REPOSITORY_FACTS.buildYear`, el año UTC en que se construyó el sitio;
- los números y las fechas pasan por `useFormatter` de use-intl, en el idioma de la página y la zona horaria del usuario;
- una espera en el navegador, como el tiempo límite de activación de `CheckoutActivation`, es un temporizador que se inicia en `useEffect`, así que el primer renderizado es el del servidor.

`hydration/no-clock-or-locale-in-render`, la regla del plugin de oxlint propio del repositorio en `scripts/hydration-lint-plugin.ts`, lo impone en `src/hooks`, `src/presentation`, `src/providers` y `src/routes/*.tsx`. Allí todo cuenta como código de renderizado salvo una función que se ejecuta después: un manejador de eventos `on…`, como prop de JSX, propiedad de objeto o variable; una `queryFn` o una `mutationFn`; y un callback pasado a `useEffect`, `useLayoutEffect`, `useCallback`, `setTimeout`, `setInterval`, `requestAnimationFrame` o `addEventListener`. Esas listas del plugin son la lista de permitidos: otro tipo de callback diferido se añade ahí, con un caso en `src/__test__/hydration-lint-plugin.test.ts`, nunca con un comentario que desactive la regla.

## Sin comentarios

No escribas comentarios: ni en TypeScript, TSX, pruebas, scripts, configuración o CSS, ni siquiera para explicar una restricción que no es evidente. Es el nombre el que transmite el significado, y el razonamiento va en el mensaje de commit, en la pull request o en esta documentación.

```ts
const INCLUSIVE_END = 1
const FIRST_SEQUENCE = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

Las dos primeras vienen de `video.delivery.ts` y `release.ts`, y la tercera de `src/data/polar.vite.ts`: de lo contrario, cada una necesitaría un comentario.

Dos comprobaciones imponen la regla, y ambas indican el archivo, la línea y la corrección:

- `code-style/no-comments`, una regla del plugin de oxlint del repositorio en `scripts/code-style-lint-plugin.ts`, informa de cada comentario en los archivos que lee el linter, en el editor y en `vp check`.
- `bun run check:comments` ejecuta `scripts/check-comments.ts` antes del linter, en `bun run check` y en el hook de pre-commit. Parsea cada archivo TypeScript, JavaScript y CSS que Git rastrea o añadiría, con oxc para el código y PostCSS para los estilos, así que un `//` en una URL o en una expresión regular y un `/*` en un glob de CSS no son comentarios. Lee lo que el linter no puede leer: `e2e`, `remotion`, los archivos de declaración, las hojas de estilo y un comentario `/* oxlint-disable */`, que el linter obedece antes de que ninguna regla lo vea.

Las exenciones son los archivos que `.gitattributes` marca como `linguist-generated`, de los cuales `src/routeTree.gen.ts` y `src/types/worker-configuration.d.ts` son código, y la línea `#!` de un script, que la gramática de JavaScript no cuenta como comentario. Un tipo que el compilador necesita en todas partes va en `types` de `tsconfig.json`, como los globales de Vitest, nunca en un comentario `/// <reference>`.

## Sin vías de escape

Nunca escribas `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, un cast con `as` ni `any` para que pase una regla. Una regla que salta señala un problema de diseño; cambia el diseño. Las comprobaciones rechazan cada uno de ellos: `typescript/ban-ts-comment`, las tres directivas del compilador incluso con una descripción; `typescript/consistent-type-assertions`, toda aserción salvo `as const`; `typescript/no-explicit-any`, el `any`; y `code-style/no-comments` y `bun run check:comments`, todo comentario de desactivación. Un comentario `eslint-disable` no desactiva nada de entrada (`respectEslintDisableDirectives: false`).

- **Valida en lugar de hacer aserciones.** Los datos que vienen del almacenamiento, de la red o de una petición se parsean con Zod: `src/lib/github.ts` lee el número de estrellas en caché con `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, que es un número o `undefined`, nunca una suposición.
- **Estrecha el tipo con una guarda de tipo.** `isRole` en `src/integrations/better-auth/auth.roles.ts` e `isSupportedLocale` en `src/integrations/use-intl/i18n.paths.ts` convierten un `string` en una unión mediante una comprobación real.
- **Anota, no hagas aserciones.** Dale a un valor el tipo que necesita donde se declara: el sidebar de shadcn declara `SIDEBAR_MOBILE_STYLE: StyleWithCssVars`, las propiedades CSS más su propiedad personalizada `--sidebar-width`, en lugar de hacer un cast del literal de objeto.
- **Comprueba, no conviertas.** `as const` y `satisfies` están permitidos porque nunca cambian un tipo: `POLAR_ORDER_STATUS` termina en `as const satisfies Record<string, models.OrderStatus>`, así que un estado de Polar mal escrito no compila.
- **Reestructura cuando el contrato de una biblioteca te lo ponga difícil.** Envuelve un valor en un objeto, divide una función o lee de una fuente tipada en lugar de hacer un cast.

## Null y undefined

Fuera de las pruebas y de `src/platform/testing`, un valor ausente es `undefined` y `null` nunca se escribe como valor. El linter lo permite donde lo impone una API: al comparar con un valor que puede ser `null`, como una columna anulable (`entry.completedAt !== null` en `course.outline.ts`), y en una ref del DOM de React, que empieza como `useRef<HTMLElement>(null)` porque React tipa `ref` como `RefObject<T | null>` y la vuelve a poner a `null` al desmontar (`course-showcase.tsx`). Nunca adaptes una API que devuelve `null` con `?? undefined`; `code-style/no-undefined-fallback` lo hace fallar. Valida antes la entrada, para que la llamada no pueda fallar, o usa un parser que ya devuelva `undefined`. Los parámetros de búsqueda son el caso habitual, y `searchParam(schema)` de `src/lib/search-params.ts` devuelve `undefined` para un valor ausente o mal formado:

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Ternarios y retornos anticipados

Un ternario cabe en una línea, como `{t(course === undefined ? "create" : "save")}` en `course-form.tsx`. Cualquier cosa más larga, y toda elección entre dos fragmentos de JSX, se convierte en un retorno anticipado, un par de condiciones `&&` o un componente pequeño; una clase condicional se convierte en `cn("base", { "classes": condition })`. `code-style/no-multiline-ternary` hace fallar todo ternario que ocupe varias líneas, incluido uno que el formateador partió porque superaba el ancho de línea. `src/routes/auth.reset-password.tsx` renderiza sus dos estados con dos condiciones:

```tsx
{hasValidToken && <ResetPasswordForm token={token} />}
{!hasValidToken && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

Las funciones retornan pronto en los casos especiales y mantienen el camino principal sin sangría, como hace `hasLessonAccess` en `src/modules/lesson/lesson.access.ts`:

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.entitled
}
```

Tampoco una rama escribe el valor ausente: `code-style/no-undefined-branch` hace fallar un ternario con una rama `undefined` o `null` y cada `return undefined`. Escribe en su lugar lo que hace el código: retorna pronto desde una cláusula de guarda, lee un valor que puede faltar con `?.` o con `??` y un valor por defecto real, devuelve lo que encuentra una tabla de búsqueda o `find`, renderiza el JSX con `&&` y da al hook de un plugin de Vite un filtro que nombre los ids que maneja, para que Rolldown no lo llame con ningún otro id. Así sirve `scripts/repository-facts.ts` su módulo virtual:

```ts title="scripts/repository-facts.ts"
    load: { filter: { id: exactRegex(RESOLVED_MODULE_ID) }, handler: () => moduleSource },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_MODULE_ID },
```

## Constantes con nombre

Los números distintos de `0` y `1` llevan nombre (`COURSE_STALE_MS = 60_000`, `SAVE_INTERVAL_MS = 15_000`). `0` y `1` se escriben como literales, como en `.limit(1)`, `index + 1` y `toHaveBeenCalledTimes(1)`, salvo que tengan un significado propio: el código de salida de un proceso es `FAILURE_EXIT_CODE`, y el final inclusivo de un rango de bytes HTTP es `INCLUSIVE_END`. Los valores que pertenecen al dominio, como estados, tipos, niveles de acceso, niveles de licencia, roles y valores de eventos de proveedores, se declaran una sola vez como un objeto `as const` y se referencian por su nombre en todas partes, incluidas las pruebas y las fixtures:

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

La tupla que necesita una columna o un esquema enum se construye a partir del objeto, no se vuelve a escribir, y está junto a él en las constantes del módulo, que no importan nada de Drizzle: `course.constants.ts` declara `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, que alimenta tanto `text("status", { enum: COURSE_STATUSES })` en `course.schema.ts` como `zod.enum(COURSE_STATUSES)` en `course.zod.ts`. El código del navegador también lee las tuplas de ahí: la tabla de precios recorre `LICENSE_TIERS` de `license.constants.ts`.

- Las constantes de un módulo viven en su `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`); los valores de un proveedor viven en el `*.constants.ts` de la integración (`POLAR_ORDER_STATUS` en `polar.constants.ts`, `AUTH_PROVIDER` en `auth.constants.ts`).
- Las longitudes de las columnas y de las entradas se nombran una sola vez, en las constantes del módulo, y las leen tanto el esquema de Drizzle como el esquema Zod: `PRODUCT_NAME_MAX_LENGTH` en `product.constants.ts`.
- Cada concepto tiene un único mapa, con una sola convención de mayúsculas: `ERROR_CODES` para los errores del servidor, `AUTH_ERRORS` para las claves de error de Better Auth, `ROLE_CODES` para los roles.
- Los nombres de entorno y los códigos de estado HTTP se declaran una sola vez, en `src/modules/_core/constants/api.ts`: `ENVIRONMENT.PRODUCTION` en `__root.tsx` y en los scripts de despliegue, `HTTP_STATUS.PARTIAL_CONTENT` en el manejador de medios del Worker. Ningún archivo declara su propio mapa de ninguno de los dos. La única excepción son los archivos de plugins de Vite, como `src/data/cloudflare.vite.ts`, que comparan `mode` con los nombres tal cual: Vite los carga antes de resolver el alias `~`, así que no pueden importar `api.ts`.
- Una constante que usa un solo archivo se queda en ese archivo, debajo de las importaciones. Una constante que usan varios archivos va a su módulo, a `src/data` (consulta [Archivos y nomenclatura](/docs/conventions/files-and-naming)) o a `src/modules/_core/constants`. Nunca des a una constante un archivo propio.
- Los nombres de campo de una API tipada, como `license_key_id`, son propiedades, no valores, y se siguen leyendo como acceso a propiedades.

## Hooks en los componentes

Primero van las llamadas a hooks que devuelven un solo valor, después una línea en blanco y luego cada resultado de hook desestructurado, de modo que los valores que un componente desestructura se lean como un grupo propio. `src/presentation/components/custom/auth/sign-in-form.tsx`:

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Un componente llama a `useTranslations` una sola vez y llama `t` al resultado; consulta [Traducciones y contenido](/docs/conventions/translations) para saber por qué.

## Nombres e importaciones

- Los archivos y las carpetas van en kebab-case; los componentes, en PascalCase; las constantes, en SCREAMING_SNAKE_CASE; las funciones empiezan por un verbo (`resolveViewer`, `rethrowAsConflict`); los booleanos se leen como preguntas (`isPending`, `hasLessonAccess`).
- Las importaciones usan el alias `~/src/...` y vienen del archivo que define el símbolo; la única excepción son las rutas, que cada archivo importa como un único espacio de nombres, `import * as ROUTES from "~/src/routes"`. No hay archivos barrel que reexporten una carpeta. Los archivos de reexportación son los puntos de unión, con una línea `export { … } from` por área, como `src/routes.ts` y los barrels `*.entries.ts` (consulta [Rutas y navegación](/docs/conventions/routes#paths-and-navigation)), y `src/integrations/drizzle-orm/drizzle.schemas.ts`, porque Drizzle necesita todas las tablas en un único objeto de esquema.
- Zod se importa de una sola forma, `import * as zod from "zod"` (o `import type * as zod from "zod"` solo para tipos), la que muestra la documentación de Zod 4; `code-style/zod-namespace-import` hace fallar una importación por defecto, una importación con nombre y una subruta como `zod/v4`.
- Avanzar un índice en uno usa el literal: `lessons[index + 1]` en `course.utils.ts`. Cualquier otro desplazamiento, `-1` incluido, lleva nombre: `groups.at(LAST_GROUP_INDEX)` en `robots.ts`, nunca `slice(index, -5)`.
