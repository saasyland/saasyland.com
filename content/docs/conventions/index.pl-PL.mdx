Te strony to standard kodowania tego repozytorium. Opisują, jak kod jest tu pisany, a nie jak można by go pisać, a każda reguła wskazuje pliki, które jej przestrzegają. Większość reguł egzekwuje polecenie: `bun run check` (formatowanie, lint, typy, tłumaczenia i struktura dokumentacji), `bun run test:coverage` (wymóg 100% pokrycia) lub zestaw testów end-to-end. Pozostałych pilnuje przegląd kodu, a każda strona podaje, których.

Gdy nie wiesz, jak coś napisać, znajdź najbliższy istniejący przykład tego samego rodzaju, przeczytaj go i odtwórz jego kształt. Spójność jest cenniejsza niż lokalnie lepszy pomysł: drugi sposób na zrobienie tego samego zmusza każdego kolejnego czytelnika, człowieka czy agenta, do poznania obu.

## Implementacja wzorcowa

Funkcja kursów to najnowszy kod w repozytorium i wzór do naśladowania. Obejmuje moduł tabeli, trasy publiczne i administracyjne, formularze, okna dialogowe, tabelę danych, szkielety i testy.

| Rodzaj                        | Wzoruj się na                                                          |
| ----------------------------- | ---------------------------------------------------------------------- |
| Moduł tabeli                  | `src/modules/course/`, a obok niego `chapter`, `lesson` i `video`      |
| Odczyt z opcjami zapytania    | `src/modules/course/use-cases/get-course-editor.ts`                    |
| Lista stronicowana dla tabeli | `src/modules/course/use-cases/get-courses.ts`                          |
| Mutacja z opcjami mutacji     | `src/modules/course/use-cases/update-course.ts`                        |
| Trasa layoutu                 | `src/routes/admin.courses.tsx`                                         |
| Trasa strony z tabelą danych  | `src/routes/admin.courses.index.tsx`                                   |
| Trasa strony z parametrem     | `src/routes/admin.courses.$courseId.tsx`                               |
| Formularz                     | `src/presentation/components/custom/admin/courses/course-form.tsx`     |
| Okno dialogowe z formularzem  | `src/presentation/components/custom/admin/courses/chapter-dialog.tsx`  |
| Kolumny tabeli                | `src/presentation/components/custom/admin/courses/course-columns.tsx`  |
| Szkielety tras                | `src/presentation/components/custom/admin/content-pending.tsx`         |

## Reguły bez wyjątków

Złamanie którejkolwiek z nich oznacza odrzucenie zmiany, niezależnie od jej pozostałych zalet.

1. Żadnych komentarzy w kodzie, testach, skryptach, konfiguracji ani CSS. Zobacz [Styl kodu](/docs/conventions/code-style).
2. Żadnych `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, rzutowań `as` ani `any` w celu obejścia reguły. Usuń przyczynę.
3. Żadnych wielowierszowych operatorów trójargumentowych, `?? undefined` ani literałów `null`.
4. Statusy, rodzaje, poziomy licencji, role i inne wartości domenowe są nazwanymi stałymi, nigdy powtarzanymi literałami tekstowymi, także w testach.
5. Folder w `src/modules` istnieje tylko dla tabeli bazy danych. Zobacz [Moduły](/docs/conventions/modules).
6. Każdy tekst widoczny dla użytkownika istnieje we wszystkich dziewięciu językach, podobnie jak każda strona dokumentacji. Liczby pokazywane w serwisie są mierzone albo deklarowane raz w `src/data`, nigdy wpisywane ręcznie. Zobacz [Tłumaczenia i treści](/docs/conventions/translations).
7. Pokrycie linii, instrukcji, funkcji i gałęzi pozostaje na poziomie 100%. Zobacz [Testy](/docs/conventions/testing).
8. Zmiana aktualizuje w tym samym pull requeście README, dokumentację i teksty serwisu, które stają się przez nią nieaktualne.
9. Commity i pull requesty nie zawierają atrybucji AI ani trailera `Co-Authored-By`. Zobacz [Git i pull requesty](/docs/conventions/git-workflow).

## Definicja ukończenia

Zmiana jest ukończona, gdy te polecenia przechodzą, w tej kolejności, na gałęzi, którą zamierzasz wypchnąć:

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:pr
```

`check` i testy nie sprawdzają buildu Cloudflare: aktualizacja zależności przeszła kiedyś jedno i drugie, choć build produkcyjny był zepsuty. Uruchamiaj `build:test` przy każdej zmianie, a zestaw testów przeglądarkowych przy wszystkim, co nie jest dokumentacją. Przed commitem przejrzyj własny diff pod kątem komentarzy, literałów tekstowych, które powinny być stałymi, oraz tekstów i dokumentacji, które zmiana uczyniła nieprawdziwymi.
