`wrangler.jsonc` définit quatre environnements. `CLOUDFLARE_ENV` en sélectionne un pour le serveur de développement et les builds, et chacun lit ses secrets dans son propre fichier d'environnement :

| Environnement | Sélectionné par                             | Bindings                                   | Secrets issus de   |
| ------------- | ------------------------------------------- | ------------------------------------------ | ------------------ |
| `development` | `bun run dev`                               | D1, KV et R2 locaux dans `.wrangler/state` | `.env.development` |
| `preview`     | `build:preview`, `deploy:preview`           | D1, KV et R2 de préversion                 | `.env.preview`     |
| `production`  | `build:production`, `deploy:production`     | D1, KV et R2 de production                 | `.env.production`  |
| `test`        | `build:test`, `start:test`, `db:reset:test` | D1, KV et R2 locaux dans `.wrangler/test`  | `.env.test`        |

`.env.development`, `.env.preview` et `.env.production` sont ignorés par Git ; `.env.example` liste leurs clés. `.env.test` est versionné et ne contient que des valeurs factices. Les scripts de déploiement ne téléversent que les clés listées dans `secrets.required` de l'environnement, lues depuis le fichier correspondant.

## Secrets

Chaque environnement liste ses secrets dans `secrets.required` : les clés Better Auth, OAuth, Resend et Polar, ainsi que `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` et `CLOUDFLARE_ACCESS_TOKEN` pour l'outillage Drizzle (l'environnement `test` omet ces trois-là). Voir [Variables d'environnement](/docs/getting-started/environment-variables) pour chaque clé.

`AFFONSO_PROGRAM_ID`, l'identifiant public du programme Affonso dont a besoin le suivi des recommandations d'affiliation, est une variable de Worker sous `vars` et non un secret : il ne figure donc ni dans `.env.example` ni dans `secrets.required`. Ne le définissez que pour l'environnement qui reçoit de vrais paiements ; `production` définit l'identifiant de programme de SaaSy Land et `test` un identifiant factice pour les tests dans le navigateur. Le suivi ne fonctionne que si le Worker a cet identifiant et que le programme est ouvert : `AFFILIATE_PROGRAM` vaut aujourd'hui <RepositoryFact name="affiliateProgram" /> ([Ouvrir le programme](/docs/features/affiliates#opening-the-programme)).

Le code serveur lit les secrets avec `import { env } from "cloudflare:workers"`. Aucune variable `VITE_` n'est utilisée, et aucune ne doit contenir de secret, car Vite les expose au navigateur. `scripts/verify-build.ts` fait échouer le build lorsqu'un asset client importe `cloudflare:workers`. Le domaine canonique provient de `APP_DOMAIN` dans `src/presentation/branding/index.ts`, et non d'une variable d'environnement.

## Bindings

| Binding   | Type             | Utilisation                                                    |
| --------- | ---------------- | -------------------------------------------------------------- |
| `DB`      | D1               | Base de données de l'application, sessions et limites de débit |
| `CACHE`   | KV               | Nombre d'étoiles GitHub et remises régionales du paiement      |
| `MEDIA`   | R2               | Fichiers vidéo, servis via `/media/`                           |
| `BUNDLES` | R2               | Bundles de modèles de la CLI, servis via `/bundles/`           |
| `ASSETS`  | Assets statiques | Pages prérendues, polices et fichiers publics                  |

Le développement n'utilise que des bindings locaux : `bun run dev` ne touche donc jamais les données de préversion ou de production, et [Base de données](/docs/tooling/database#three-databases) explique pourquoi chaque binding est local. Exécutez `bun run cf-typegen` après avoir modifié les bindings pour régénérer `src/types/worker-configuration.d.ts`.

## Tests

Vitest charge `.env.test` via `test.env` et résout `cloudflare:workers` vers `src/platform/testing/mocks/cloudflare.ts`, qui fournit en mémoire un D1, un KV et un bucket pour chaque binding R2 ; `src/platform/testing/mocks/cache.ts` simule le cache des Workers. Playwright utilise l'environnement `test` et son point d'entrée `src/platform/testing/worker.ts`. Aucun des deux n'a besoin de vrais identifiants.
