---
title: "Sessions"
description: "Better Auth sessions in D1 with the country they signed in from, self-service revocation in settings and revocation of any user's sessions from their admin profile."
---

Sessions live in the D1 `session` table (`src/modules/session/session.schema.ts`). `auth.session.ts` reads them with `getRequestSession`, memoized per request, and exposes `getCurrentSessionQuery` to routes and components. The client copy never includes the session token.

Each session also stores `country`, a Better Auth additional field that the `session.create.before` database hook in `auth.server.ts` fills from the `cf-ipcountry` header Cloudflare adds to every request (`COUNTRY_HEADER`). Only a code from the `COUNTRIES` catalogue is kept, so Tor (`T1`) and unknown (`XX`) addresses leave it empty. The browser and the operating system come from the user agent: `sessionDevice` in `src/modules/session/session.utils.ts` recognizes the common browsers and systems by name and tells phones and tablets apart.

## Use cases

| Use case                                  | Middleware                   | Used by        |
| ----------------------------------------- | ---------------------------- | -------------- |
| `getActiveSessions`                       | signed in                    | `SessionsCard` |
| `revokeSession`                           | signed in; own sessions only | `SessionRow`   |
| `revokeOtherSessions`                     | signed in                    | `SessionsCard` |
| `listUserSessions`                        | `session: ["list"]`          | `UserSessions` |
| `revokeUserSession`, `revokeUserSessions` | `session: ["revoke"]`        | `UserSessions` |

`getActiveSessions` returns the current user's unexpired sessions, newest first, and leaves out impersonation sessions. `listUserSessions` returns another user's unexpired sessions from Better Auth's `listUserSessions`, newest first and without their tokens, impersonation sessions included. `revokeUserSession` takes a session ID and looks its token up on the server, so no token reaches the browser.

## UI

The **Security** tab of `/app/settings` and `/admin/settings` renders `SessionsCard` (`src/presentation/components/custom/settings/sessions-card.tsx`), with this browser first. Each `SessionRow` names the browser and the system, such as "Firefox on Windows", marks **This device**, and shows the country, the IP address, when the session was last active and when it signed in. Every other row has **Sign out**, whose accessible name names the device, and the card ends with **Sign out other devices** while there is one. Changing or setting the password signs out every other session as well and refreshes the list.

A user's profile in `/admin/users` renders `UserSessions` (`src/presentation/components/custom/admin/users/user-sessions.tsx`): each session's device, from the same `useSessionDeviceName`, and when it signed in and was last active, a button that revokes it and, after a confirmation, a button that signs the user out everywhere. See [Users (admin)](/docs/features/users-admin).

## Cached data and the signed-in account

Every query not marked public belongs to the account that was signed in when it loaded ([Public queries](/docs/conventions/data-fetching#public-queries)). `auth.routes.ts` records that account for each query cache. `getRouter()` passes every change of the cache to `recordUserDataOwner`, which takes the account from the first session the cache holds, whether the server rendered it into the page, a route guard loaded it or the header asked for it. Each route guard compares the session it loads with that record. When they differ, the guard removes the earlier account's queries and mutations with `removeUserData`, stores the new session and records the new account. A visitor who is not signed in counts as an account of its own, so signing in, signing out and switching accounts each clear the cache, while a check that finds the same account keeps everything the page has loaded, such as a lesson the learner has just marked complete.

The record sits beside the cache rather than in the session query, so it still names the earlier account when a component fetches the session again and finds another one, or when the session query leaves the cache. The next guard then removes the earlier account's data.
