Ogni modifica viene rilasciata con i test che la dimostrano, nello stesso commit, e la copertura resta pari a <RepositoryFact name="coverageThreshold" unit="percent" /> per righe, istruzioni, funzioni e branch. La correzione di un bug arriva con un test che fallisce senza la correzione.

## Progetti

`vite.config.ts` definisce tre progetti Vitest, scelti in base al suffisso del file. I test importano la propria API da `vite-plus/test` e si trovano in `__test__/` accanto al codice che coprono.

| Suffisso               | Progetto      | Da usare per                                                                                                                                                                       |
| ---------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.test.ts`             | `node`        | Casi d'uso, loader, `head`, schemi, utility: tutto ciò che viene eseguito sul server                                                                                               |
| `.integration.test.ts` | `integration` | Flussi di Better Auth, di pagamento e di licenza, l'adapter D1 e il caricamento dei messaggi, con timeout di <RepositoryFact name="integrationTestTimeoutSeconds" unit="second" /> |
| `.component.test.tsx`  | `component`   | Componenti e pagine in jsdom                                                                                                                                                       |

`src/platform/testing/mocks/cloudflare.ts` sostituisce `cloudflare:workers` in ogni progetto: D1 è un database `node:sqlite` in memoria costruito da ogni migrazione versionata, KV e un bucket per ogni binding R2 dell'ambiente `test` in `wrangler.jsonc` sono store in memoria. `resetTestBindings()` svuota KV, il bucket e la tabella dei limiti di richieste prima di ogni test, e la funzione di seed di ogni suite reimposta le righe da cui dipende. Nessun test comunica con Cloudflare, Polar, Resend o un provider OAuth: `fetch` raggiunge i test double rigorosi in `mocks/resend.ts` e `mocks/polar.ts`, che validano ogni richiesta rispetto ai modelli di richiesta degli SDK e fanno fallire il test per una richiesta che il provider rifiuterebbe. I test verificano ciò che il test double ha ricevuto invece di fare il mock di un metodo dell'SDK, e le suite di autenticazione pilotano la vera configurazione di `auth.server.ts` tramite `auth.harness.ts`.

## Testare una server function

Chiamala tramite le sue opzioni esportate, così il test mette alla prova il vero middleware, la validazione e l'handler. `src/modules/course/use-cases/__test__/course-admin-use-cases.test.ts`:

```ts
const signInAs = (role: string): void => {
  vi.spyOn(auth.api, "getSession").mockResolvedValue(createAuthSessionFixture({ role, userId: USERS.VISITOR }))
}

beforeEach(async () => {
  await seedCatalogue()
})

afterEach(() => {
  vi.restoreAllMocks()
})

describe("getCourses", () => {
  it("lists every course with its lesson count, drafts included", async () => {
    signInAs(ROLE_CODES.ADMIN)

    const page = await executeQuery(getCoursesPageQuery())

    expect(page.total).toBe(3)
    expect(page.rows.map(({ id, lessons, status }) => [id, lessons, status])).toStrictEqual([
      [IDS.DRAFT_COURSE, 0, COURSE_STATUS.DRAFT],
      [IDS.COURSE, 5, COURSE_STATUS.PUBLISHED],
      [IDS.TUTORIAL, 0, COURSE_STATUS.PUBLISHED],
    ])
  })
```

- `executeQuery(options)` ed `executeMutation(options, variables)` da `src/platform/testing/lib/query.ts` eseguono le opzioni in un `QueryClient` nuovo.
- La sessione proviene da `createAuthSessionFixture` in `src/integrations/better-auth/__test__/fixtures/auth.session.fixture.ts`; ogni permesso viene testato anche dal lato che deve essere rifiutato (`it("is for staff only")`).
- I dati di seed si trovano nella cartella `__test__/fixtures/` del modulo, con i loro ID in oggetti con un nome (`IDS`, `LESSON_IDS`, `USERS`). `seedCatalogue()` elimina le righe che possiede e le inserisce di nuovo tramite Drizzle, così ogni test parte dallo stesso stato.
- Nel progetto `component` una server function fallisce, perché jsdom fa le veci del browser. I test dei componenti forniscono a una route i dati del suo loader oppure fanno il mock di `queryFn` e `mutationFn` nelle opzioni che il componente legge.

## Le asserzioni usano i nomi del codice

- Gli stati, le tipologie, i ruoli e i codici di errore attesi sono le costanti che usa il codice: `COURSE_STATUS.DRAFT`, `ROLE_CODES.ADMIN`, `rejects.toThrow(ERROR_CODES.FORBIDDEN)`. Un test non ripete mai un letterale stringa di dominio, e non lo fanno nemmeno i dati e2e o il seed di test: `e2e/data/courses.ts` scrive `kind: COURSE_KIND.COURSE`.
- I test dello schema sono l'unico posto in cui un valore memorizzato si scrive per esteso: `license.schema.test.ts` fissa `expect(LICENSE_STATUSES).toStrictEqual(["active", "revoked", "refunded"])`, così modificare un valore salvato nel database fa fallire un test invece di richiedere una migrazione che nessuno ha scritto.
- La suite del browser importa le sue costanti dall'applicazione (`LICENSE_TIER`, `ROLE_CODES`, `I18N.SUPPORTED_LOCALES`), quindi può importare solo file che si caricano fuori dal Worker. I valori di Polar vengono da `polar.constants.ts`, che non legge l'ambiente: `e2e/fixtures/license.ts` e la suite del percorso cliente nella sandbox prendono gli stati degli ordini da `POLAR_ORDER_STATUS`, e l'ordine stesso viene da `src/platform/testing/lib/polar.ts`. Gli ID dei prodotti dei piani sono l'eccezione: `POLAR_PRODUCT_IDS` legge `cloudflare:workers`, quindi la suite del browser li legge da `.env.test`.
- I test dei componenti leggono i testi attesi dai file di messaggi inglesi, come fa `admin-course-routes.component.test.tsx` con `import labels from "~/messages/en-US/pages.admin.courses.json"` e `labels.form.kinds.course`, e trovano gli elementi per ruolo e nome accessibile.
- Un test che ha bisogno di un tipo lo legge da una sorgente tipizzata o lo verifica a runtime con `toHaveProperty`; non fa mai cast.
- I nomi dei test descrivono il comportamento con una frase: "lists every course with its lesson count, drafts included".

## Copertura

`bun run test:coverage` fallisce quando una qualsiasi delle quattro metriche per `src/**/*.{ts,tsx}` è inferiore a <RepositoryFact name="coverageThreshold" unit="percent" />. Sono esclusi i test, `__test__/`, i file di dichiarazione, `src/routeTree.gen.ts`, le primitive shadcn e `src/platform/testing/`. La soglia viene mantenuta significativa:

- **Elimina i branch che non possono mai essere eseguiti** invece di coprirli con degli stub. Un `?? fallback` su dati sempre presenti, o un optional chaining su un valore che non può essere `undefined`, viene rimosso dal sorgente, non raggiunto facendo lo stub di una variabile globale.
- **Copri il comportamento reale.** Gli stati di attesa tengono aperta la richiesta con `Promise.withResolvers()`, verificano la UI di attesa, risolvono dentro `act` e verificano la UI inattiva, come fanno `expectPending` ed `expectIdle` in `auth-forms.component.test.tsx`.
- **Mantieni le asserzioni quando una regola si fa sentire.** Quando un test supera `max-statements`, estrai un helper con un nome invece di eliminare dei controlli.
- **Carica ogni file di messaggi.** `i18n.messages.test.ts` carica ogni namespace di ogni locale, ed è questo che copre le righe `import.meta.glob` in `i18n.loaders.ts`. Un nuovo file di messaggi viene coperto automaticamente.

## Test su una macchina carica

Il limite di tempo di Vitest e il margine di un secondo di `waitFor` e `findBy*` contano il tempo reale, quindi un test che fa lavoro di cui il suo comportamento non ha bisogno, o che aspetta un timer, fallisce su una macchina carica anche se niente è rotto. Il limite predefinito resta com'è; un test lento viene cambiato perché faccia meno:

- **Un controllo su molti file esegue un test per file.** `check-content.test.ts` esegue `pageProblems` per ogni pagina inglese con `it.each(sourcePages())`, e una discrepanza indica la sua pagina.
- **Ciò che un componente attende con Suspense viene caricato prima del rendering**, come fanno `preloadNamespaces` per le traduzioni e `TimeSeriesBars.preload()` per il grafico caricato su richiesta in `revenue-chart.component.test.tsx`. Quando il test riguarda il caricamento stesso, lo risolve dentro `act`, come fa `translations-provider.component.test.tsx`: il contenuto che riprende fuori da `act` compare solo dopo il ritardo con cui React lo mostra, su un timer reale, e il test deve interrogare il DOM finché non lo vede.
- **Un test sostituisce un modulo una sola volta invece di importare di nuovo il componente.** `affiliate-referral.component.test.tsx` simula `AFFILIATE_PROGRAM` una volta e lo imposta in ogni test. Importare un componente dopo `vi.resetModules()` rivaluta tutto il suo grafo di import dentro il test.
- **Le fixture che ogni test legge si costruiscono una volta per file**, come i messaggi di `getTestMessages`.
- **Un modulo si compila con `user.paste`, a meno che le sue battute non siano il comportamento sotto test.** `fill` di `src/platform/testing/lib/fill.ts` fa clic sul campo e incolla; `user.type` esegue la validazione e il rendering del modulo per ogni carattere.
- **Un test che attende un debounce o un polling fa avanzare l'orologio invece di aspettare.** `controlTimers()` di `src/platform/testing/lib/clock.ts` simula i timer per quel solo test, che continuano ad avanzare con il tempo reale, e `passTime(ms)` fa avanzare l'orologio dentro `act` della costante del componente stesso, come fanno la ricerca del `DataGrid` con `DATA_GRID_TYPING_DELAY_MS` e la pagina della licenza con `LICENSE_POLL_MS.KEY`. Un test che aspetta il ritardo reale passa quel tempo inattivo, e una macchina carica lo allunga ancora.
- **Un lungo elenco di opzioni si ri-renderizza a basso costo.** Il combobox dei fusi orari di `preferences-card.tsx` passa le sue opzioni a `ComboboxList` come `items` memoizzati, così React Aria le riusa quando il modulo si ri-renderizza.

## I test seguono le funzionalità [#tests-follow-the-features]

Le funzionalità di cui `scripts/features.ts` nomina file e percorsi (vedi [Percorsi e navigazione](/docs/conventions/routes#paths-and-navigation)) possiedono anche i propri test, così la CLI `saasyland` può escludere una funzionalità da un progetto generato insieme ai suoi test, mentre tutti gli altri test continuano a passare.

Un file di test copre una funzionalità o un file sorgente. Le pagine di amministrazione di una funzionalità si testano con i loro scheletri e breadcrumb in `src/routes/__test__/admin-<feature>-routes.component.test.tsx` e i loro loader in `admin-<feature>-loaders.test.ts`. Il test di uno scheletro di layout lo renderizza con `createTestRouter(path, routeTree)` di `src/platform/testing/lib/render.tsx`, un router costruito sul vero albero delle route, e gli scheletri dei corsi si testano in `admin/__test__/courses-pending.component.test.tsx`, perché `admin-course-routes` ricostruisce le route dei corsi per il proprio router; `admin-layout`, `admin-dashboard` e `admin-loaders` testano l'interfaccia di amministrazione stessa e non nominano alcuna funzionalità. File non correlati hanno ciascuno il proprio file di test, come `background.component.test.tsx` e `wordmark.component.test.tsx`, e ogni handler dell'API ha il suo: `src/routes/api/__test__/auth.test.ts` e `index.test.ts`. `cli.v1.test.ts` copre i file di route dell’API delle licenze della CLI, il cui comportamento è testato in `src/modules/license/__test__/license.api.integration.test.ts`.

Una lista che copre più funzionalità non ha barrel: ogni funzionalità dichiara la sua parte in un file proprio, e l'unico file che legge la lista importa ogni parte e le scrive in una lista letterale, così escludere una funzionalità ne elimina il file e, con l'import, l'elemento:

| Elenco                                | Ogni funzionalità dichiara                                                                                                                   | Elencato da                                                                |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Dati delle query dell'amministrazione | `seed<Feature>Queries` e le sue factory di righe in `src/presentation/components/custom/admin/__test__/<feature>.fixtures.ts`                | `adminQueryClient()` in `fixtures.tsx`                                     |
| Etichette delle enumerazioni          | `src/integrations/use-intl/__test__/<feature>.labels.ts`                                                                                     | `ENUM_LABELS` in `enum-labels.test.ts`, che scrive lì le etichette di base |
| Righe di D1                           | `src/integrations/drizzle-orm/__test__/<feature>.rows.ts`                                                                                    | `d1.integration.test.ts`                                                   |
| Pagine dei test nel browser           | `e2e/data/<feature>.pages.ts`                                                                                                                | `ENTRIES` in `e2e/data/pages.ts`, che scrive lì le home page               |
| Database di test                      | `e2e/data/<feature>.seed.ts`                                                                                                                 | `scripts/seed-test.ts`                                                     |
| Inventario dei flussi                 | `e2e/data/<feature>.flows.ts`: i flussi della funzionalità, ognuno con il test che lo dimostra o il motivo per cui manca                     | `FLOWS` in `scripts/check-flows.ts`                                        |
| Query pubbliche                       | una query con `public: true` nel proprio file sorgente                                                                                       | `PUBLIC_QUERIES` in `auth.session.test.ts`, una proprietà per query        |
| Test double dei provider              | `src/platform/testing/mocks/<provider>.ts`: una lista `<PROVIDER>_PROVIDER_DOUBLES`, ogni double con un `origin`, un `respond` e un `reset`  | `DOUBLES` in `mocks/providers.ts`                                          |
| Catalogo Polar                        | `src/modules/<module>/__test__/fixtures/<feature>.polar-catalogue.ts`: i prodotti e i benefit di chiave di licenza che la funzionalità vende | `CATALOGUES` in `mocks/polar.ts`                                           |
| Worker di test                        | `e2e/data/<feature>.worker.ts`: preparazioni ed endpoint di test                                                                             | `ENTRIES` in `src/platform/testing/worker.ts`                              |

Nessun file dichiara una lista vuota per la base: una voce che ogni progetto ha si scrive nella lista stessa, come le home page in `e2e/data/pages.ts`, e `scripts/seed-test.ts` esegue Wrangler solo quando una funzionalità carica righe. Il page object di una funzionalità ha una fixture propria: `e2e/fixtures/auth.ts` estende il `test` di base di `e2e/fixtures/test.ts` con `authPage`, e le spec che fanno l'accesso importano `test` da lì. Anche gli helper email di una funzionalità stanno in un file di fixture proprio, come `e2e/fixtures/license-emails.ts` ed `e2e/fixtures/invitation-emails.ts`, accanto ai condivisi `getSentEmails`, `latestEmail` e `linkTo` di `e2e/fixtures/emails.ts`, e il double del browser di una funzionalità si aggiunge a `BROWSER_DOUBLES` in `e2e/fixtures/test.ts`, come fa `servePolarCheckout`.

Gli helper usati da più funzionalità esistono una sola volta: `renderAdmin` e `renderAdminPage` in `src/presentation/components/custom/admin/__test__/fixtures.tsx`, `loadAsAdmin` in `src/routes/__test__/fixtures/admin-router.ts`, `markupOf` e `busyMarkup` in `src/platform/testing/lib/skeleton.tsx` e, nei test nel browser, `AuthPage.signIn`, `BasePage.leaveWhileLoading` e la fixture `pageWithoutJavaScript`. Le spec delle pagine pubbliche, come `accessibility.spec.ts` e `theme.spec.ts`, non accedono con alcun account; `workspaces.spec.ts` controlla le pagine per gli utenti autenticati, la loro accessibilità e il loro tema.

Un test di codice condiviso che ha bisogno di una voce fornita dalle funzionalità ne dichiara una propria invece di leggere quella di una funzionalità. `dashboard-actions.component.test.tsx` sostituisce `ADMIN_DASHBOARD_ACTIONS` con un'azione locale al test, così `DashboardActions` e i segnaposto delle azioni di `AdminDashboardPending` restano coperti in un progetto senza la funzionalità dei pagamenti, che oggi dichiara le azioni della dashboard. `server.test.ts` serve i file di ogni handler di richieste e fa passare ogni riscrittura di documento attraverso il Worker in un test che nomina il modulo proprio della funzionalità, così lasciare fuori la funzionalità elimina il test, `vite-config.test.ts` carica `VITE_PLUGINS` nel loro ordine, e i plugin di un fornitore si testano accanto a essi, come in `zod.vite.test.ts`. Il codice condiviso che solo funzionalità opzionali renderizzano ha un test tutto suo: `pending-blocks.component.test.tsx` copre lo scheletro del campo che usano gli scheletri dell'amministrazione dei corsi. `auth.access.test.ts` verifica ciò che viene concesso a ogni ruolo, ogni funzionalità verifica le proprie dichiarazioni in `auth.access.<feature>.test.ts`, come `auth.access.courses.test.ts`, e `auth.access.website.test.ts` fissa i permessi di ogni ruolo del sito.

`auth.server.test.ts` elenca in ordine l'id di ogni plugin di Better Auth, e `navigation.test.ts` controlla i menu senza aspettarsi alcuna voce in particolare, così passa qualunque siano le voci che un progetto conserva. `translations-provider.component.test.tsx` usa come esempi namespace della base e i test di autenticazione usano i dati e i percorsi della funzionalità di autenticazione stessa, come l'elenco delle sessioni e `/app/settings`.

Il test della rotta della licenza sostituisce il `CourseUnlocks` dei corsi con una sezione locale al test e la sua query del catalogo con un mock, il test dello skeleton della licenza fa lo stesso con `CourseUnlocksPending`, e i test dei corsi sostituiscono le concessioni dell'accesso ai corsi di `lesson.access.ts` con `TEST_COURSE_ACCESS` tramite `withTestCourseAccess` (`src/modules/course/__test__/fixtures/course-access.ts`), così i test di nessuna delle due funzionalità leggono l'altra. `src/modules/lesson/__test__/lesson.access.license.test.ts` copre ciò che le unisce: la concessione della licenza, con uno snapshot di chi può guardare quale lezione per un ospite, un account, lo staff e ogni livello e stato di licenza.

Un test che fissa l'intero sito, come `navigation.website.test.ts` con l'ordine di ogni menu, appartiene solo al sito; i template non lo generano.

`scripts/features.ts` elenca come glob i file di ogni funzionalità opzionale, i nomi che la funzionalità possiede nei file che restano, come i suoi percorsi in `src/routes.ts`, e le funzionalità che richiede, e `bun run check:features` verifica che il sito funzioni ancora senza di esse. Uno scenario esclude soltanto le funzionalità che ha solo il sito; ciascuno degli altri esclude anche i corsi, le funzionalità di fatturazione, i contenuti o l'autenticazione. Per ogni scenario lo script elimina i file di quelle funzionalità e di ogni funzionalità che ne richiede una, poi pota i file che restano con un'unica regola, la stessa che segue la CLI `saasyland` quando esclude una funzionalità:

1. Elimina i nomi che possiedono le funzionalità rimosse, ciascuno con la sua dichiarazione o proprietà di oggetto.
2. Un riferimento rimosso è un identificatore importato da un file eliminato, l'uso di un nome rimosso, come `ROUTES.COURSES` non appena `src/routes.ts` smette di dichiararlo, una funzione che chiama `import()` su un file eliminato, oppure un `vi.mock`, `vi.doMock`, `vi.unmock` o `vi.doUnmock` che nomina un modulo eliminato. Ogni `import` ed `export … from` di un file eliminato sparisce, e così ogni import di un modulo che solo un file di dichiarazioni eliminato dichiara, come `virtual:repository-facts`.
3. Un riferimento rimosso nel callback di un test, cioè un `it` o un `test` in qualunque forma, come `.each`, `.skip` o `.only`, oppure un `test.step` di Playwright, porta via l'intero test. Per ogni altro riferimento rimosso elimina la più vicina di queste unità che può sparire; una funzione, una classe, un'istruzione `return`, una condizione o un export non spariscono mai per intero, quindi segnala con file, riga e colonna un riferimento racchiuso solo da uno di essi:
   - l'elemento di array più vicino all'interno della sua istruzione di primo livello oppure, se non c'è, la proprietà di oggetto, lo spread, il membro di tipo o il figlio JSX più vicino, senza attraversare un'istruzione;
   - l'istruzione di espressione che lo contiene, al primo livello di un modulo, di un `describe` o di un hook come `beforeEach`, e dentro qualunque altra funzione solo quando sparisce tutto ciò che nomina da fuori di sé;
   - il dichiaratore di variabile che lo contiene, quando il suo valore non è una funzione né una classe e sparisce tutto ciò che nomina il suo inizializzatore; i nomi che lega diventano allora anch'essi nomi rimossi, e il dichiaratore sparisce solo se ogni loro uso sparisce secondo questa stessa regola. Un valore che attinge anche a codice che resta, come il link che `signedInDestination(entry, workspace)` costruisce da una voce di menu, resta e viene segnalato, perché a dover cambiare è il progetto, non la potatura;
   - l'hook o il `describe` che lo contiene.
4. Quando questo svuota un array che è una proprietà di un elemento di array, sparisce anche l'elemento, come un gruppo di menu rimasto senza voci. Allo stesso modo spariscono un test di cui svuota la tabella `.each`, un test, uno step, un hook o un `describe` di cui svuota il callback, un `describe` rimasto senza test e un ciclo o un callback con il corpo vuoto, il callback insieme all'unità che lo contiene. Se svuotasse il corpo di una funzione o di una condizione, le istruzioni restano e ne segnala i riferimenti.
5. Elimina ogni stringa di un array che nomina il namespace di un file di messaggi eliminato.
6. Elimina gli specificatori di import, le dichiarazioni non esportate, a qualunque livello, e gli elementi di un pattern di destrutturazione di array a cui niente fa più riferimento, lasciando un buco davanti a un elemento che resta, e ripete finché non cambia più nulla. Elimina per intero un file `*.test.*` o `*.spec.*` rimasto senza test.
7. In ogni `package.json` elimina ogni passo di uno script, cioè ogni comando tra due `&&`, che nomina un file eliminato o avvia con `bun run` uno script che se ne va, elimina lo script rimasto senza passi e ripete finché non cambia più nulla: così un sito senza i contenuti non tiene `check:content` e non avvia `content` in `dev` né in `build:*`. Un passo che condivide il proprio comando con un altro tramite `||`, `;`, `|` o `&` non può andarsene da solo, quindi lo segnala.

`scripts/prune-references.ts` applica la regola agli alberi sintattici del parser oxc, e `scripts/module-bindings.ts` risolve ogni nome nella dichiarazione a cui si riferisce, così un parametro o una variabile locale con lo stesso nome non viene mai scambiato per un import. `scripts/test-cases.ts` riconosce test, gruppi, hook e mock dalle chiamate a ciò che un file importa come `it`, `test`, `describe`, un hook o `vi`, con qualunque nome locale, `scripts/prune-units.ts` sceglie l'unità attorno a ogni riferimento, e `scripts/prune-edits.ts` scrive le eliminazioni conservando il più ampio dei due spazi attorno a un'istruzione eliminata, così la riga vuota tra gruppi di istruzioni resta. `scripts/prune-scripts.ts` applica il settimo passo agli script di ogni `package.json`. I file generati, che `.gitattributes` marca come `linguist-generated`, vengono copiati così come sono, e il controllo rigenera l'albero delle route. Poi lo script copia in una directory temporanea i file che Git traccia o aggiungerebbe, quelli potati al posto degli originali, formatta i file potati con `vp fmt`, genera le tabelle dei nomi delle classi, le collezioni dei contenuti finché resta la funzionalità dei contenuti e l'albero delle route, con `scripts/generate-routes.ts`, esegue `tsc --noEmit` su `src`, `e2e`, `scripts` e `vite.config.ts` e infine `check:i18n` sui messaggi rimasti. Uno scenario fallisce per un riferimento che la regola non riesce a potare, per uno script del `package.json` rimasto che nomina un file eliminato o avvia con `bun run` qualcosa che non è né uno dei suoi script né un binario installato, per qualsiasi errore di tipo e per qualsiasi errore di traduzione, e `src/__test__/check-features.test.ts` fallisce quando un glob non corrisponde a nessun file o un nome non è dichiarato nel suo file. Un riferimento che la regola non riesce a potare si corregge mettendo il codice dove dice la [struttura delle cartelle](/docs/architecture/directory-structure), mai con un'eccezione nella potatura. La CI esegue un job per scenario, e uno scenario che fallisce fa fallire l'esecuzione ([CI/CD](/docs/tooling/ci-cd#checks)).

## Test nel browser

Playwright esegue il Worker di test compilato: `bun run build:test` lo compila con D1 e KV locali in `.wrangler/test`, `bun run db:reset:test` ricrea quel database e popola gli account, il video e il corso in `e2e/data`, e l'entry di test intercetta le email in uscita su `/__test/emails`, così una spec può seguire un link di verifica.

- Le spec prendono il nome dal flusso (`course-admin.spec.ts`, `auth-redirect.spec.ts`) e guidano la pagina tramite ruoli e nomi accessibili, con i page object in `e2e/pages/`.
- Ogni spec crea i dati che modifica con valori univoci, come uno slug costruito da `crypto.randomUUID()`, ed effettua l'accesso con un proprio header `CF-Connecting-IP`, così le spec possono essere eseguite in parallelo e ripetute senza scontrarsi tra loro o con i limiti di richieste.
- Un test che modifica dati creati dal seed, come i dispositivi di una licenza, riceve record creati dal seed tutti suoi, uno per ogni worker parallelo, così due test in esecuzione non modificano mai lo stesso record. `cli-licence-api.spec.ts` attiva i dispositivi sulla licenza che `TEST_CLI_LICENSES` in `e2e/data/licenses.ts` crea per il `parallelIndex` di ogni worker, che Playwright non assegna mai a due worker contemporaneamente, e la sua fixture `cliMachine` rilascia il dispositivo quando il test finisce, così un retry riparte dalla licenza creata dal seed. La licenza `TEST_LICENSE`, che `license.spec.ts` legge, mantiene solo il dispositivo creato dal seed.
- Una spec agisce su una pagina solo dopo che `waitForAppReady()` di `e2e/pages/base-page.ts` è terminato, anche dopo una navigazione lato client. Il metodo termina quando TanStack Router ha renderizzato l'URL corrente, che la fixture automatica `recordRenders` registra dall'evento `onRendered` del router, perché una navigazione lato client cambia l'URL prima che la route successiva venga renderizzata. Il contenuto della route può idratarsi dopo quel render, quindi una spec che dipende dallo stato proprio di un componente, o che preme un link fuori dal contenuto prima che questo sia idratato, chiama prima `waitForHydration(element)`, che attende che React abbia idratato l'elemento e tutto ciò che contiene; `LandingPage.goto()` lo fa per il `main` della landing page. Una spec può lasciare una pagina mentre è in caricamento, come può fare un visitatore, e una spec che raccoglie gli errori di pagina su più visite dirette apre ogni visita in una scheda propria, come fa `auth-routing.spec.ts`, oppure lascia ogni pagina solo quando la sua rete è inattiva (`page.waitForLoadState("networkidle")`), come fa `workspaces.spec.ts`, perché una pagina avvia alcune richieste solo dopo l'idratazione, come un badge della barra laterale o i segmenti di un video. Una spec che raccoglie gli errori di pagina lascia una pagina solo dopo che la sua navigazione lato client è stata renderizzata: WebKit segnala come errore di pagina una richiesta che la pagina avvia dopo che la spec ha iniziato a lasciarla, `Fetch API cannot load … due to access control checks.`, anche se l'app gestisce la richiesta fallita.
- Una spec che deve dimostrare che un testo non compare mai, non solo che alla fine è sparito, chiama `watchForText(text)` di `e2e/pages/base-page.ts` prima della modifica e verifica poi che il testo non sia mai apparso: un `MutationObserver` nella pagina lo registra appena viene renderizzato. Il test dell’upgrade in `checkout-funnel.spec.ts` lo fa per il ringraziamento del vecchio piano, e la suite del percorso per il ringraziamento di qualsiasi piano diverso da quello acquistato.
- Ogni spec fallisce quando una pagina viola la sua Content Security Policy: la fixture automatica `cspViolations` in `e2e/fixtures/test.ts` registra ogni evento `securitypolicyviolation` e si aspetta che non ce ne sia nessuno alla fine del test. Una spec che provoca di proposito una violazione la rimuove con `cspViolations.splice(0)`, come fa `content-security-policy.spec.ts`. La suite esegue la build di produzione di `build:test`, perché il server di sviluppo non invia alcuna policy degli script.
- Le pull request e la coda di merge eseguono ogni spec in Chromium e in WebKit; in locale `bun run test:e2e:pr` le esegue in Chromium e `bun run test:e2e` in entrambi. I push su `main` eseguono di nuovo WebKit, e un'esecuzione settimanale pianificata li esegue entrambi.
- Una spec che legge gli appunti usa la fixture `readClipboard` di `e2e/fixtures/test.ts`, che prima dell'avvio della spec concede i permessi degli appunti che il browser conosce: in Chromium `clipboard-read` e `clipboard-write`, in WebKit solo `clipboard-read`, perché WebKit non ha un permesso di scrittura e lascia che il clic che copia scriva negli appunti, come Safari.
- Un endpoint di test che ha bisogno di una firma la calcola nel Worker di test con i secret fittizi di `.env.test`, che la build `test` legge, così nessuna spec contiene un secret. `/__test/media/signed-paths` in `e2e/data/courses.worker.ts` firma uno stream video e un download di una lezione una volta per adesso e una volta per una scadenza già passata, e `/__test/polar/billing-purchase` in `e2e/data/billing.worker.ts` firma gli eventi di ordini e abbonamenti di Polar, tra cui un `subscription.updated` successivo, con il secret di test del webhook.
- Una spec che dipende dall'ordine delle richieste le trattiene o le scarta con `page.route`. `header-session.spec.ts` trattiene il controllo della sessione dell'header mentre il visitatore preme **Your account**, e il test della lezione completata in `course-progress.spec.ts` lo scarta, così il primo controllo della sessione che riesce è il preload del guard delle route, fatto quando la lezione è già nella pagina.
- Una spec che esegue un flusso end-to-end e ne verifica l'esito è nominata da quel flusso in `e2e/data/<feature>.flows.ts`, con il suo file di spec e il titolo completo. `bun run check` fallisce quando un flusso nomina un test che la suite non ha, quindi un test rinominato porta con sé il suo flusso nello stesso commit, e un flusso che nessun test dimostra dice perché. Vedi [Copertura dei test](/docs/tooling/test-coverage).
- Una correzione di route, di flusso o visiva che i test unitari non possono vedere riceve una spec: le scansioni di accessibilità e le regressioni di navigazione in `navigation.spec.ts` e nelle spec delle funzionalità che riguardano, come `content.spec.ts`, `legal.spec.ts` e `landing.spec.ts`, ne sono esempi. Una spec che scorre rende la pagina abbastanza alta da sé, come fa il test di scorrimento in `navigation.spec.ts`, invece di contare sulla lunghezza di una pagina. Una sezione che si riempie dopo il caricamento della pagina mantiene la sua altezza, quindi una spec che scorre non deve mai caricarla prima: una sezione che cambiava altezza sopra il viewport spostava ciò che il visitatore stava leggendo, e WebKit interrompeva uno scorrimento fluido quando l'ancoraggio dello scorrimento lo compensava. Le spec del blocco dei corsi in `landing.spec.ts` trattengono la sua richiesta, la lasciano riuscire o fallire e verificano che il blocco mantenga la sua altezza e che non venga segnalato alcuno spostamento del layout.
