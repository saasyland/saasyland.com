title: "Moduły"
description: "Moduł to jedna tabela bazy danych: jej schemat, stałe, schematy Zod, interfejs typów, przypadki użycia i kilka plików zagadnień, których tabela może potrzebować."
---

`src/modules/<table>/` istnieje tylko dla rzeczywistej tabeli bazy danych. Folder odzwierciedla schemat Drizzle, więc jego utworzenie to deklaracja, że tabela istnieje. Kod, który obsługuje funkcję bez własnej tabeli, trafia gdzie indziej: funkcja serwerowa, która czyta dane z GitHuba lub kolekcję dokumentacji, znajduje się w `src/lib/<topic>.ts` lub w jedynej trasie, która jej używa, a konfiguracja dostawcy w `src/integrations/<vendor>`.

Moduły to <RepositoryFact name="modules" />. Do `license` należą dwie tabele: `license` i `revoked_license_order`. `_core` nie jest modułem: zawiera kody błędów, katalogi i pola Zod współdzielone przez wszystkie moduły.

## Budowa

Wzorcem jest `src/modules/course`. Moduł zawiera następujące pliki, wszystkie nazwane od tabeli:

| Plik                         | Zawartość                                                                                            |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| `<table>.schema.ts`          | Tabelę Drizzle, jej indeksy i relacje                                                                |
| `<table>.constants.ts`       | Obiekty wartości domenowych, ich krotki enumów, klucze zapytań, klucze mutacji i limity modułu       |
| `<table>.zod.ts`             | Po jednym schemacie wejścia na operację, wszystkie w jednym obiekcie `<table>ZodSchemas`             |
| `<table>.types.ts`           | Jeden interfejs nazwany jak moduł                                                                    |
| `<table>.utils.ts`           | Funkcje pomocnicze tabeli, czyste i bezpieczne w przeglądarce, chyba że odczytują środowisko Workera |
| `<table>.<concern>.ts`       | Jedno dodatkowe zagadnienie tabeli, np. `lesson.access.ts` lub `video.delivery.ts`                   |
| `use-cases/<verb>-<noun>.ts` | Jedną operację, nazwaną od jej funkcji serwerowej                                                    |
| `__test__/`                  | Testy i fixtury dla powyższych plików                                                                |

## Schemat

```ts title="src/modules/course/course.schema.ts"
export const course = sqliteTable(
  "course",
  {
    cover: text("cover"),
    icon: text("icon", { enum: COURSE_ICONS }).notNull().default(COURSE_ICON.BOOK_OPEN),
    id: text("id").primaryKey(),
    kind: text("kind", { enum: COURSE_KINDS }).notNull().default(COURSE_KIND.COURSE),
    level: text("level", { enum: COURSE_LEVELS }).notNull().default(COURSE_LEVEL.BEGINNER),
    outcomes: text("outcomes", { mode: "json" })
      .$type<LocalizedList>()
      .notNull()
      .default(sql`'{}'`),
    position: integer("position").notNull().default(0),
    prerequisites: text("prerequisites", { mode: "json" })
      .$type<LocalizedList>()
      .notNull()
      .default(sql`'{}'`),
    slug: text("slug", { length: SLUG_MAX_LENGTH }).notNull().unique(),
    status: text("status", { enum: COURSE_STATUSES }).notNull().default(COURSE_STATUS.DRAFT),
    summary: text("summary", { mode: "json" }).$type<LocalizedText>().notNull(),
    title: text("title", { mode: "json" }).$type<LocalizedText>().notNull(),
    ...timestamps(),
  },
  (table) => [index("course_status_position_idx").on(table.status, table.position)],
)
```

- Kolumny są w camelCase w TypeScript i w snake_case w SQL. Klucze są posortowane, jak wymaga linter, a `...timestamps()` jest ostatnim wpisem.
- `createdAt` i `updatedAt` pochodzą z `timestamps()` w `src/integrations/drizzle-orm/drizzle.columns.ts`: są w milisekundach, wypełnia je SQLite przy wstawianiu wiersza, a `updatedAt` odświeża się przy każdej aktualizacji. Nigdy nie pisz ich ręcznie. `lesson_progress` potrzebuje tylko drugiej z nich, więc przyjmuje `updatedAt: timestamps().updatedAt`. Dwie tabele nie mają znaczników czasu: `rate_limit` przechowuje krótkotrwałe liczniki, które mają własne `expiresAt` i zmieniają się przy każdym żądaniu, a `revoked_license_order` zapisuje raz każde zwrócone zamówienie z Polara, po jego ID.
- Klucze główne są tekstowe. Przypadek użycia, który wstawia wiersz, wypełnia klucz identyfikatorem UUID v7 (`v7()` z `uuid`); [tabela odzwierciedlająca dostawcę](#tables-that-mirror-a-provider) przyjmuje zamiast tego identyfikator dostawcy.
- Kolumny enum przyjmują krotkę zbudowaną z obiektu stałych modułu, nigdy listę literałów. Krotka znajduje się obok obiektu w `<table>.constants.ts`, bo czytają ją też schematy Zod i przeglądarka, a ten plik nie importuje niczego z Drizzle.
- Tekst, który odwiedzający czyta w kilku językach, jest kolumną JSON `LocalizedText`, walidowaną przez `localizedTextSchema` i odczytywaną za pomocą `localize(text, locale)` z `src/modules/_core/utils/localized-text.ts`.
- Nowa tabela jest reeksportowana z `src/integrations/drizzle-orm/drizzle.schemas.ts`, a jej migrację generuje się poleceniem `bun run db:generate`. Zobacz [Migracje bazy danych](/docs/guides/database-migrations).

## Tabele odzwierciedlające dostawcę [#tables-that-mirror-a-provider]

`order` i `subscription` przechowują kopie zamówień i subskrypcji z Polara, zapisywane wyłącznie na podstawie danych z Polara i nigdy nieedytowane ręcznie. Tabela-lustro trzyma się dostawcy tam, gdzie powyższe zasady mówią co innego:

- Jej kluczem głównym jest identyfikator dostawcy, kolumna tekstowa o długości `POLAR_ID_MAX_LENGTH`, a kolumny noszą nazwy pól dostawcy, takie jak `customer_id`, `product_id` i `subscription_id`. Nasza własna tabela, która wskazuje na dane dostawcy, dodaje natomiast prefiks do nazwy kolumny, tak jak `license.polar_order_id`.
- Własne znaczniki czasu dostawcy leżą obok `...timestamps()`. `placedAt` to moment, w którym Polar utworzył zamówienie, a `changedAt` to wersja rekordu z Polara przechowywana w wierszu: jego `modified_at` albo, dopóki rekord nigdy się nie zmienił, jego `created_at`. `createdAt` i `updatedAt` nadal zapisują, kiedy wiersz trafił do D1.
- Kolumny enum przyjmują krotki wartości dostawcy: `ORDER_STATUSES` w `order.constants.ts` wymienia `POLAR_ORDER_STATUS` z `src/integrations/polar/polar.constants.ts`, a test typów kończy się błędem, gdy SDK wymienia wartość, której brakuje w krotce.
- Żadna kolumna poza `createdAt` i `updatedAt` nie ma wartości domyślnej, bo każda wartość pochodzi od dostawcy.
- `user_id` ma `ON DELETE SET NULL`: usunięcie konta zachowuje jego zamówienia i subskrypcje, a usuwa jedynie powiązanie.

`order` jest słowem kluczowym SQL. Drizzle ujmuje w cudzysłów każdy identyfikator, więc jego zapytania nie wymagają niczego więcej; surowy SQL odwołuje się do tabeli przez obiekt schematu, jako `${order}` w szablonie `sql`, nigdy przez samo `order`.

## Stałe

```ts title="src/modules/course/course.constants.ts"
export const COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const

export const COURSE_STALE_MS = 60_000

export const COURSE_SHOWCASE = {
  COURSES: 5,
  LESSONS: 5,
} as const

export const COURSE_QUERY_KEYS = {
  ALL: ["course"],
  CATALOGUE: ["course", "catalogue"],
  DETAIL: ["course", "detail"],
  EDITOR: ["course", "getCourseEditor"],
  LIST: ["course", "getCourses"],
  SEARCH: ["course", "searchCourses"],
  SHOWCASE: ["course", "showcase"],
} as const

export const COURSE_MUTATION_KEYS = {
  CREATE: ["course", "createCourse"],
  DELETE: ["course", "deleteCourse"],
  EXPORT: ["course", "exportCourses"],
  IMPORT: ["course", "importCourses"],
  MOVE: ["course", "moveCourse"],
  REMOVE_COVER: ["course", "removeCourseCover"],
  REORDER_CURRICULUM: ["course", "reorderCurriculum"],
  UPDATE: ["course", "updateCourse"],
  UPLOAD_COVER: ["course", "uploadCourseCover"],
} as const
```

- Każdy klucz zapytania zaczyna się od prefiksu `ALL` modułu, więc jedno `invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL })` odświeża wszystko, co moduł udostępnia. Zobacz [Pobieranie danych i cache](/docs/conventions/data-fetching).
- Klucze mutacji składają się z nazwy modułu i nazwy funkcji serwerowej.
- Długości kolumn i danych wejściowych są nazywane tutaj i współdzielone przez schemat oraz schemat Zod, np. `PRODUCT_NAME_MAX_LENGTH` w `product.constants.ts`.
- `<MODULE>_VALIDATION_PARAMS` przechowuje liczby, które interpolują komunikaty walidacji, np. `{ slugTooLong: { max: SLUG_MAX_LENGTH } }`.
- `scripts/repository-facts.ts` odczytuje niektóre pliki stałych, np. `license.constants.ts`, gdy Vite wczytuje swoją konfigurację, a alias `~` nie jest jeszcze rozwiązany. Taki plik importuje inne pliki źródłowe po ścieżce względnej, tak jak `license.constants.ts` importuje `POLAR_WEBHOOK_EVENT` z `../../integrations/polar/polar.constants.ts`; importy samych typów są usuwane, więc mogą zachować alias.

## Schematy Zod

```ts title="src/modules/chapter/chapter.zod.ts"
import * as zod from "zod"

import { localizedTextSchema, optionalLocalizedTextSchema } from "~/src/modules/_core/utils/localized-text"
import { idField } from "~/src/modules/_core/utils/zod-fields"

const chapterIdInput = zod.object({
  chapterId: idField,
})

const chapterFields = zod.object({
  summary: optionalLocalizedTextSchema,
  title: localizedTextSchema,
})

const createChapter = chapterFields.extend({ courseId: idField })

const deleteChapter = chapterIdInput

const updateChapter = chapterFields.extend(chapterIdInput.shape)

export const chapterZodSchemas = {
  createChapter,
  deleteChapter,
  updateChapter,
}
```

- `<table>.zod.ts` importuje `* as zod from "zod"` i eksportuje jeden obiekt, którego klucze są nazwami operacji.
- Formularze walidują dane tymi samymi schematami w przeglądarce, więc `<table>.zod.ts` nie importuje niczego z Drizzle ani z pliku `.schema.ts`. Krotki enumów i długości pochodzą z `<table>.constants.ts`, który importuje też tabela, więc kolumna i schemat mają jedną wspólną definicję. Build klienta kończy się błędem, gdy `drizzle-orm` trafia do przeglądarki; zobacz [ORM poza przeglądarką](/docs/conventions/performance#keep-the-orm-out-of-the-browser).
- Żaden schemat Zod nie jest wyprowadzany z tabeli: w czasie działania nic nie waliduje całego wiersza, a typy wierszy w interfejsie modułu pochodzą z `$inferSelect` i `$inferInsert`.
- Pola pochodzą z `src/modules/_core/utils/zod-fields.ts` (`idField`, `localeField`, `slugField`) i ze wspólnych fragmentów w tym samym pliku; nigdy nie są deklarowane od nowa dla każdego schematu.
- Listy stronicowane używają `paginationSchema`; operacje na pojedynczym rekordzie przyjmują obiekt, np. `{ courseId }`, nigdy samego stringa.
- Komunikaty błędów są kluczami tłumaczeń (`{ message: "slugInvalid" }`), renderowanymi z przestrzeni nazw `<table>.validations` modułu. Zobacz [Formularze i tabele](/docs/conventions/forms-and-tables).

## Interfejs modułu

`<table>.types.ts` eksportuje dokładnie jeden interfejs, nazwany jak moduł, którego klucze odzwierciedlają obiekt Zod:

```ts title="src/modules/lesson/lesson.types.ts"
export interface Lesson {
  select: typeof lesson.$inferSelect
  insert: typeof lesson.$inferInsert
  page: LessonPage
  detail: LessonPage["lesson"]
  attachment: LessonPage["lesson"]["attachments"][number]
  createLesson: zod.input<typeof lessonZodSchemas.createLesson>
  deleteLesson: zod.input<typeof lessonZodSchemas.deleteLesson>
  getLesson: zod.input<typeof lessonZodSchemas.getLesson>
  getLessonPlayback: zod.input<typeof lessonZodSchemas.getLessonPlayback>
  getLessonTitle: zod.input<typeof lessonZodSchemas.getLessonTitle>
  removeLessonVideo: zod.input<typeof lessonZodSchemas.removeLessonVideo>
  replaceLessonVideo: zod.input<typeof lessonZodSchemas.replaceLessonVideo>
  searchLessons: zod.input<typeof lessonZodSchemas.searchLessons>
  setLessonFormat: zod.input<typeof lessonZodSchemas.setLessonFormat>
  updateLesson: zod.input<typeof lessonZodSchemas.updateLesson>
}
```

Funkcje serwerowe, opcje mutacji i formularze typują swoje wejście jako `Lesson["createLesson"]`. Gdy dodajesz schemat do `<table>.zod.ts`, dodaj w tej samej zmianie jego klucz tutaj. Nigdy nie wyprowadzaj typu wejścia przez `Parameters<typeof fn>[0]` i nigdy nie deklaruj lokalnego aliasu ani drugiego interfejsu `LessonInput`. Gdy komponenty potrzebują kształtu danych zwracanych przez odczyt, interfejs także go nazywa, wyprowadzając go z funkcji serwerowej: `Course["listRow"]` to `Awaited<ReturnType<typeof getCourses>>["rows"][number]`.

## Przypadki użycia

Każdy plik w `use-cases/` zawiera jedną operację, nazwaną od jej funkcji serwerowej w kebab-case: `get-course-editor.ts` eksportuje `getCourseEditor` i `courseEditorQuery`, a `update-course.ts` eksportuje `updateCourse` i `updateCourseMutation`. Wzorzec, jego middleware i błędy opisuje strona [Funkcje serwerowe i błędy](/docs/conventions/server-functions). [Katalog modułów](/docs/reference/modules) i [macierz uprawnień](/docs/reference/permissions) wyświetlają tabele każdego modułu, jego przypadki użycia i wywołanie `authorized` każdego z nich, które `collectModuleTables` w `scripts/repository-facts.ts` odczytuje z kodu podczas budowania, więc nowy przypadek użycia pojawia się tam bez ręcznej edycji, a `src/__test__/module-tables.test.ts` kończy się błędem, gdy katalog pomija plik modułu spoza standardowego zestawu.

Przypadek użycia, który działa tylko na serwerze i jest wywoływany przez hook Better Auth lub webhook Polara, a nie przez przeglądarkę, to zwykła funkcja `async` w pliku zaczynającym się od `import "@tanstack/react-start/server-only"`, np. `license/use-cases/grant-license.ts` oraz pliki wysyłające e-maile `send-verify-email.ts`, `send-reset-password-email.ts` i `send-change-email-confirmation-email.ts`.

## Pliki zagadnień

Gdy tabela potrzebuje logiki, która nie jest ani przypadkiem użycia, ani czystą funkcją pomocniczą, dostaje jeden plik na zagadnienie, nazwany `<table>.<concern>.ts`:

| Plik                                              | Zagadnienie                                                                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `course/course.outline.ts`                        | Konspekt opublikowanego kursu dla widza, dla `getCourse` i `getLesson`                                             |
| `course/course.cover.ts`                          | Rozmiary, szerokości, dozwolone typy plików i klucze obiektów okładki kursu; czysta logika                         |
| `course/course.delivery.ts`                       | Handler Workera `serveCover`, który serwuje okładki kursów                                                         |
| `course/course.objects.ts`                        | Usuwanie obiektów okładki kursu z R2                                                                               |
| `course/course.transfer.ts`                       | Eksport i import kursów jako jednego dokumentu JSON                                                                |
| `lesson/lesson.access.ts`                         | Kto może oglądać lekcję; czysta logika, używana na serwerze i w testach                                            |
| `lesson/lesson.playable.ts`                       | Złączenie z wideo lekcji, które pomija filmy zastępcze                                                             |
| `lesson-attachment/lesson-attachment.download.ts` | Podpisywanie adresów URL do pobierania materiałów lekcji                                                           |
