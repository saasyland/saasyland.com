---
title: "Współtworzenie"
description: "Jak proponować zmiany w SaaSy Land."
---

1. Większe zmiany najpierw omów w zgłoszeniu (issue).
2. Utwórz gałąź od `main`.
3. Stosuj się do [konwencji](/docs/conventions) i [architektury](/docs/architecture), a przed zmianą integracji z dostawcą przeczytaj odpowiednią [umiejętność agenta](/docs/tooling/agent-skills). Agenci kodujący zaczynają od `AGENTS.md` w katalogu głównym repozytorium.
4. Trzymaj testy obok testowanego kodu i utrzymuj wymóg 100% pokrycia.
5. Uruchom poniższe kontrole.
6. Utwórz commit z komunikatem w formacie [konwencjonalnego commita](/docs/tooling/conventional-commits) i otwórz pull request z tytułem w tym samym formacie.

```sh
bun run check
bun run test:coverage
bun run build:test
bun run test:e2e:install
bun run test:e2e:pr
```

`build:test` uruchamia pełny build Cloudflare, którego nie sprawdzają ani `check`, ani testy jednostkowe. `test:e2e:pr` buduje i uruchamia testowego Workera, jeśli żaden serwer nie działa, a następnie wykonuje wszystkie specyfikacje w Chromium, tak jak CI dla pull requestów. Przy zmianach, które mogą działać inaczej w WebKit, uruchom dodatkowo pełny zestaw testów przeglądarkowych (`bun run test:e2e`). Gdy zmieniasz konfigurację prawdziwych integracji z dostawcami, zweryfikuj je osobno.

Gdy zmienia się zachowanie aplikacji, zaktualizuj `content/docs` we wszystkich dziewięciu językach; `bun run check:i18n` odrzuca brakujące tłumaczenia oraz różnice w blokach kodu i nawigacji. W pull requeście opisz wynikowe zachowanie, sposób weryfikacji oraz wszelkie pozostawione dane demonstracyjne lub niedokończone przepływy.
