Cloudflare D1 (SQLite) ist die Datenbank der Anwendung und als `DB` gebunden. `src/integrations/drizzle-orm/` verbindet sie mit Drizzle:

| Datei                 | Zweck                                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `drizzle.database.ts` | Serverseitiges `db`, erstellt mit `drizzle(env.DB, { schema })`                                                                            |
| `drizzle.schemas.ts`  | Exportiert jedes Tabellenschema und seine Relationen erneut                                                                                |
| `drizzle.config.ts`   | drizzle-kit: SQLite-Dialekt, `d1-http`-Treiber, Migrationen mit Zeitstempel-Präfix in `migrations/`                                        |
| `drizzle.errors.ts`   | `rethrowAsConflict`, das einen Unique-Constraint-Fehler in `AppError(ERROR_CODES.CONFLICT)` umwandelt und jeden anderen Fehler weiterwirft |
| `drizzle.columns.ts`  | `timestamps()`, die Spalten `createdAt` und `updatedAt`, die jede Tabelle mit Zeitstempeln in ihr Schema einfügt                           |

## Tabellen

Jede Tabelle gehört zu einem Modul in `src/modules/<table>/` mit `<table>.schema.ts` (`drizzle-orm/sqlite-core`), dazu `.zod.ts`, `.constants.ts`, `.types.ts` und `use-cases/`, wenn die Tabelle Operationen hat, und `.utils.ts`, wenn sie Hilfsfunktionen braucht. Der [Modulkatalog](/docs/reference/modules) listet jedes Modul mit seinen Tabellen und Use Cases auf, aus dem Code gelesen. Code, dem keine Tabelle gehört, erhält kein Modul.

Die Schemas folgen denselben Konventionen:

- IDs sind UUID-v7-Strings, außer in `order` und `subscription`, die die Datensätze von Polar unter den IDs von Polar kopieren (siehe [Module](/docs/conventions/modules#tables-that-mirror-a-provider)).
- Datumswerte sind `integer`-Spalten im Modus `timestamp_ms` mit dem Standardwert `unixepoch() * 1000`. `...timestamps()` fügt `createdAt` und `updatedAt` in dieser Form hinzu; `updatedAt` wird bei jedem Update neu gesetzt.
- Boolesche Werte sind `integer`-Spalten im Modus `boolean`.
- Relationen, Indizes, Unique-Constraints und Fremdschlüssel werden im Schema deklariert.

## Atomare Schreibvorgänge

D1 hat keine interaktiven Transaktionen. Halte eine Operation mit einer einzelnen Anweisung atomar, etwa einem Upsert mit `onConflictDoUpdate`, oder fasse Anweisungen mit `db.batch` zusammen. Die Anwendungsfälle für paginierte Listen laden eine Seite und die Gesamtzahl in einem Batch (`src/modules/category/use-cases/get-categories.ts`):

```ts
const filter = data.kind && eq(category.kind, data.kind)
const [rows, totals] = await db.batch([
  db
    .select()
    .from(category)
    .where(filter)
    .orderBy(desc(category.createdAt), desc(category.id))
    .limit(data.pageSize)
    .offset(data.pageIndex * data.pageSize),
  db.select({ total: count() }).from(category).where(filter),
])
return { rows, total: totals.reduce((sum, row) => sum + row.total, 0) }
```

Die Ratenbegrenzung in `src/lib/rate-limit.ts` liest die Zähler, die einen Request ablehnen, entfernt eine begrenzte Zahl abgelaufener Zähler und zählt den Request mit einem atomaren Upsert pro Limit, alles in einem Batch, sodass alle Worker-Instanzen dieselben Limits teilen und ein abgelehnter Request nichts schreibt. `rateLimitBatch` gibt diese Anweisungen zurück, damit ein Aufrufer seine eigene Abfrage in denselben Batch legen kann; die CLI-Lizenz-API fügt ihre Abfrage der Lizenz hinzu.

## Migrationen

Migrationen sind SQL-Dateien in `src/integrations/drizzle-orm/migrations/`, die mit `bun run db:generate` erzeugt und mit Wrangler angewendet werden. Vitest führt sie gegen eine In-Memory-SQLite-Datenbank aus. Die Befehle findest du unter [Datenbank](/docs/tooling/database).
