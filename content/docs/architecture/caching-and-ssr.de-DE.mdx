## Query-Cache

`getRouter` erstellt für jeden Request einen neuen `QueryClient`, sodass auf dem Server keine Daten zwischen Nutzern durchsickern. Standardwerte:

| Einstellung                      | Wert                                                                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Query `staleTime`                | <RepositoryFact name="queryStaleTimeMinutes" unit="minute" />                                                                                    |
| Query `gcTime`                   | <RepositoryFact name="queryGcTimeMinutes" unit="minute" />                                                                                       |
| Router `defaultPreloadStaleTime` | <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />                                                                            |
| Preloading                       | Bei Intent, und die [Seiten des Headers](/docs/conventions/performance#the-headers-pages-load-before-a-click), sobald eine Seite im Leerlauf ist |

Allein TanStack Query entscheidet, was frisch ist. `defaultPreloadStaleTime` beträgt <RepositoryFact name="routerPreloadStaleTimeMs" unit="millisecond" />, wie es der Leitfaden von TanStack Router für die Nutzung mit TanStack Query verlangt, und `defaultStaleTime` behält den Standardwert des Routers. Der Router führt die Loader einer Route also bei jedem Preload und jeder Navigation aus, und die Loader lesen den Query-Cache, der nur lädt, was fehlt oder veraltet ist.

Loader füllen den Cache mit `queryClient.query({ ...options, staleTime: "static" })`, und Komponenten lesen dieselben Keys mit `useSuspenseQuery`. Ausnahme sind die Kursseiten und der Kurseditor im Admin: Ihre Queries behalten `staleTime: COURSE_STALE_MS` (<RepositoryFact name="courseStaleMinutes" unit="minute" />), weil `invalidateQueries` eine `static`-Query nie neu lädt und der Lehrplan nach einer abgeschlossenen Lektion oder einer im Editor gespeicherten Änderung aktualisiert werden muss. `setupRouterSsrQueryIntegration` serialisiert den Server-Cache ins HTML und hydratisiert ihn im Browser.

- **Übersetzungsnachrichten** werden pro Locale und Namespace mit unendlicher `staleTime` und `gcTime` gecacht.
- **Die Session-Query** (`getCurrentSessionQuery`) hat eine `staleTime` von <RepositoryFact name="sessionStaleTimeMinutes" unit="minute" />. Route-Guards lassen eine Navigation mit der zwischengespeicherten Session durch, solange sie frisch ist, und laden sie neu, sobald sie veraltet ist. Antwortet eine Server-Funktion mit `UNAUTHORIZED` oder `FORBIDDEN`, prüft `recheckRefusedSession` in `auth.routes.ts` die Session erneut, und die Guards laufen noch einmal, wenn sie sich geändert hat. Ändert sich der angemeldete Nutzer, entfernen die Guards jede Query, die nicht mit `meta: { public: true }` markiert ist. Öffentliche Queries, etwa die Übersetzungen und die Anzahl der Sterne, mit der eine vorgerenderte Seite gerendert wurde, bleiben im Cache. Siehe [Öffentliche Queries](/docs/conventions/data-fetching#public-queries).
- **Mutationen** invalidieren nach erfolgreichem Abschluss die Query-Keys ihres Moduls, zum Beispiel `USER_QUERY_KEYS.ALL`.

## Prerendering

`bun run build` rendert die öffentlichen Seiten vor, indem es Links folgt: Landing-, Rechts-, Blog- und Doku-Seiten in jeder Locale. Ausgenommen sind Pfade unter `/admin`, `/app`, `/auth`, `/courses`, `/newsletter` und `/api` (mit oder ohne Locale-Präfix) sowie Links mit Query-String oder Hash. Die Kursseiten sind ausgenommen, weil sie für jeden Betrachter Sperren und Fortschritt zeigen. Den Kursblock der Landingpage füllt der Browser aus `getCourseShowcase`, sobald er in die Nähe des sichtbaren Bereichs kommt; die vorgerenderte Landingpage bleibt daher für alle gleich (siehe [Kurse](/docs/features/courses)).

Der Worker liefert vorgerendertes HTML aus dem `ASSETS`-Binding aus, bevor er die Anwendung lädt. Eine vorgerenderte Seite enthält keine Nutzerdaten und kann daher gefahrlos an alle ausgeliefert werden. Vor dem Ausliefern schreibt der Worker sie mit den Einträgen von `DOCUMENT_REWRITES` um: regionale Preise für einen Besucher, der sich dafür qualifiziert, und `data-session` auf `<html>`, wenn der Request das Sitzungs-Cookie von Better Auth mitbringt, wodurch im Header die Beschriftung **Dein Konto** gewählt wird, bevor ein Skript läuft (siehe [Pfade und Navigation](/docs/conventions/routes#paths-and-navigation)). Die Markierung prüft nur, ob das Cookie vorhanden ist, nie die Datenbank; ein Cookie, dessen Sitzung beendet ist, löscht die erste Seite, die es prüft, etwa die Anmeldeseite oder die Sitzungsprüfung des Headers. Jede HTML-Antwort wird deshalb mit `Cache-Control: private, no-cache` und `Vary: Cookie` gesendet, sodass kein gemeinsamer Cache die Seite eines Besuchers für einen anderen speichert. Ein Cache vor dem Worker, etwa Workers Cache oder eine Cache-Regel für HTML, würde allen dieselbe Variante ausliefern; Dokumente dürfen nur dort gecacht werden, wo diese Rewrites nach dem Cache noch laufen.

Das Prerendering läuft auf einem Worker-Build, der alle Seiten enthält. Der deployte Worker wird danach ohne die kompilierten Seiten von Doku und Blog und ohne die Übersetzungen neu gebaut, die nur die Landing- und Rechtsseiten nutzen. Er braucht beides nicht: Doku, Blog und Landingpage lesen ihre Inhalte bei einer clientseitigen Navigation im Browser aus Indizes, die der Build nach `/assets/` schreibt, und die Suche der Doku durchsucht einen statischen Index im Browser, daher erreichen clientseitige Navigationen und die Suche nie den Worker (siehe [Performance](/docs/conventions/performance#the-worker-holds-no-docs-or-blog-content)). Siehe [Cloudflare Workers](/docs/integrations/cloudflare-workers).

## KV und D1

- **KV (`CACHE`)** speichert die Anzahl der GitHub-Sterne für `src/lib/github.ts`. Eine Sternezahl, die älter als <RepositoryFact name="starCountRefreshHours" unit="hour" /> ist, wird sofort zurückgegeben und im Hintergrund mit `waitUntil` aktualisiert.
- **D1 (`DB`)** speichert Sessions und Rate-Limit-Zähler. Session-Prüfungen für Serverfunktionen umgehen den Cookie-Cache von Better Auth und werden für den Rest des Requests memoisiert.
- **Der Workers-Cache** hält die Videodateien, die `serveMedia` aus R2 liest, unter `/media/_/<videoId>/<file>` ohne die Signatur vor, sodass sich die Zuschauer an einem Edge-Standort eine einzige gecachte Kopie teilen. Siehe [Cloudflare R2](/docs/integrations/cloudflare-r2). `serveCover` hält die Titelbilder der Kurse in einem eigenen Workers-Cache, `covers`, unter ihrem öffentlichen Pfad und sendet sie mit `public, max-age=31536000, immutable`, weil jedes neue Titelbild eine neue ID bekommt.
- Serverfunktionen treffen nie eine Berechtigungsentscheidung auf Basis gecachter Daten.
