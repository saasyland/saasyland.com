Chaque fichier de `src/routes` a la même forme : qui en connaît un les connaît tous. Un fichier de route compose : il déclare ce dont la page a besoin et place des composants. Les widgets, les formulaires, les boîtes de dialogue et les colonnes de tableau se trouvent dans `src/presentation/components/custom`.

## Routes de page

`src/routes/admin.courses.index.tsx` :

```tsx title="src/routes/admin.courses.index.tsx"
const CoursesPage = (): JSX.Element => {
  const t = useTranslations("pages.admin.courses")
  const queryClient = useQueryClient()
  const errorMessage = useErrorMessage()
  const columns = useCourseColumns()

  const move = useMutation({
    ...moveCourseMutation,
    onError: (error) => {
      toast.error(errorMessage(error))
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: COURSE_QUERY_KEYS.ALL }),
    scope: COURSE_ORDER_SCOPE,
  })

  return (
    <div className="flex w-full animate-in flex-col space-y-8 duration-500 fade-in-50">
      <AdminPageHeader
        actions={
          <>
            <ImportCoursesDialog />
            <ExportCoursesButton />
            <LinkButton className="h-9 gap-2" to={ROUTES.ADMIN.COURSES.CREATE} size="sm">
              <PlusCircle aria-hidden className="size-4" />
              {t("actions.create")}
            </LinkButton>
          </>
        }
        description={t("description")}
        title={t("title")}
      />

      <DataGrid
        bulkActions={(rows) => <DeleteCoursesButton courses={rows} />}
        columns={columns}
        empty={t("table.empty")}
        emptyDescription={t("table.emptyDescription")}
        id={COURSE_GRID_ID}
        label={t("title")}
        onReorder={({ offset, row }) => move.mutateAsync({ courseId: row.id, offset })}
        query={(request) => getCoursesPageQuery(courseZodSchemas.getCourses.parse(request))}
        rowActions={CourseActions}
        search={t("table.search")}
        selectable
      />
    </div>
  )
}

const NAMESPACE = "pages.admin.courses"

export const Route = createFileRoute("/admin/courses/")({
  component: CoursesPage,
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getCoursesQuery, staleTime: "static" }),
    ])
    return { locale, metadata }
  },
  head: pageHead(ROUTES.ADMIN.COURSES.INDEX),
  pendingComponent: AdminCoursesPending,
  staticData: { namespaces: [NAMESPACE] },
})
```

- **Le composant** est une `const` locale nommée `<Name>Page`, définie en premier. Un petit balisage utilisé uniquement par cette page peut se placer au-dessus sous forme de composants locaux, comme `CourseProgress` et `StartLink` dans `_site._marketing.courses.$course.index.tsx` ; tout ce qui a ses propres données, sa propre mutation ou son propre état va dans un fichier de composant.
- **Un seul espace de noms.** `const NAMESPACE = "pages.<feature>.<page>"` se trouve juste au-dessus de `export const Route` et sert dans `loadPageMetadata`, `preloadNamespaces` et `staticData`. Tout ce dont la page a besoin en plus est déclaré par son layout.
- **Un seul `Promise.all` pour la première partie de la réponse.** Le loader lance tout le travail en même temps. Il attend, dans un seul `Promise.all`, ce dont le serveur a besoin avant d'envoyer le premier octet : les métadonnées de la page, l'espace de noms, les données que le loader lit lui-même et celles qu'un composant lit avec `useQuery`, comme la première page d'un `DataGrid`. Toute autre query démarre sans être attendue et arrive en streaming dans le squelette de sa section (voir [Sections en streaming](#streamed-sections)). Le loader renvoie `{ locale, metadata }` pour `head`. N'attendez jamais un travail avant de lancer le suivant.
- **`head: pageHead(ROUTES.X)`** construit le titre, la description, l'URL canonique et les alternatives à partir des métadonnées du fichier d'espace de noms.
- **Les chemins proviennent de `ROUTES`** dans `src/routes.ts`, qui réunit les chemins de toutes les zones (voir [Chemins et navigation](#paths-and-navigation)) ; n'écrivez jamais de chemin littéral.

Une page dont le titre provient d'un enregistrement attend cet enregistrement et construit son head à partir des données du loader, comme le fait `admin.courses.$courseId.tsx` :

```tsx title="src/routes/admin.courses.$courseId.tsx"
export const Route = createFileRoute("/admin/courses/$courseId")({
  component: CourseEditorPage,
  loader: async ({ context, params }) => {
    const locale = getCurrentLocale()
    const data = await context.queryClient.query(courseEditorQuery({ courseId: params.courseId })).catch(rethrowAsNotFound)
    return { locale, pathname: `${ROUTES.ADMIN.COURSES.INDEX}/${data.course.id}`, title: localize(data.course.title, locale) }
  },
  head: recordHead(ROUTES.ADMIN.COURSES.INDEX),
  pendingComponent: AdminCourseEditorPending,
})
```

`recordHead` (`src/lib/not-found.ts`) construit ce head à partir des données du loader et reprend le chemin de la liste tant que l'enregistrement se charge. Quand le loader lève `notFound`, parce que `rethrowAsNotFound` a rencontré un enregistrement absent, il renvoie à la place le titre et la description de la page introuvable avec `noindex` : un utilisateur, une commande, un cours ou une leçon absents ne portent pas le nom du site comme titre.

## Sections en streaming [#streamed-sections]

Une page dont les sections secondaires attendent des données plus lentes, comme le catalogue de Polar ou les compteurs du tableau de bord, envoie ses premiers octets sans elles. `src/routes/admin.index.tsx` attend les métadonnées, l'espace de noms et les comptes les plus récents, que son `DataGrid` lit avec `useQuery`, et lance les queries des statistiques et des panneaux sans les attendre :

```tsx title="src/routes/admin.index.tsx"
  loader: async ({ context }) => {
    const locale = getCurrentLocale()
    for (const { prefetch } of [...DASHBOARD_STATS, ...DASHBOARD_PANELS]) {
      void prefetch(context.queryClient).catch(noop)
    }
    const [metadata] = await Promise.all([
      loadPageMetadata({ locale, namespace: NAMESPACE }),
      preloadNamespaces({ locale, namespaces: [NAMESPACE], queryClient: context.queryClient }),
      context.queryClient.query({ ...getUsersPageQuery({ pageSize: ADMIN_DASHBOARD_PREVIEW_PAGINATION.pageSize }), staleTime: "static" }),
      TimeSeriesBars.preload?.(),
    ])
    return { locale, metadata }
  },
```

- Une query en streaming démarre avant le `Promise.all`, avec `void` et `.catch(noop)` de TanStack Query, comme le fait le guide de TanStack Router consacré à TanStack Query, pour qu'un échec ne devienne jamais un rejet non géré. L'échec atteint quand même le composant qui lit la query, puis, de là, le composant d'erreur de la route.
- Le composant la lit avec `useSuspenseQuery` dans une frontière `Suspense` dont le fallback est le squelette de la section, celui que dessine le `pendingComponent` de la route : la section occupe ainsi la même place avant et après l'arrivée de ses données. `DashboardStats` enveloppe chaque statistique dans `<Suspense fallback={<DashboardStatPending />}>` et `DashboardPanels` chaque panneau dans son `Pending` ; `/admin/products` enveloppe sa grille dans `PolarProductGridPending` et `/app/billing` ses commandes dans `BillingHistoryPending`, dans le fichier de route.
- Ne diffusez jamais en streaming des données qu'un composant lit avec `useQuery`, comme une page d'un `DataGrid` : le serveur rend le composant sans les données, le navigateur l'hydrate avec elles et React jette le HTML du serveur. Attendez-les plutôt.
- `head` s'exécute une fois que le loader a renvoyé son résultat : il ne lit donc que des données attendues.

Lors d'une requête, TanStack Start envoie aussitôt la page jusqu'à ses frontières non résolues, puis chaque section dès que sa query se résout, dans la même réponse, et `@tanstack/react-router-ssr-query` y joint les données de chaque query, si bien que le navigateur ne les récupère pas une seconde fois. Un robot d'indexation, reconnu par `isbot`, reçoit la page entière d'un coup. Lors d'une navigation côté client, la page apparaît dès que le travail qu'elle attend est terminé, et chaque section remplit son squelette. [Performances](/docs/conventions/performance#request-rendered-pages-stream-their-slow-sections) donne les mesures.

## Routes de layout

`src/routes/admin.courses.tsx` :

```tsx title="src/routes/admin.courses.tsx"
const NAMESPACES = ["course.validations", "pages.admin.courses"] as const

export const Route = createFileRoute("/admin/courses")({
  loader: ({ context }) => preloadNamespaces({ locale: getCurrentLocale(), namespaces: NAMESPACES, queryClient: context.queryClient }),
  pendingComponent: AdminCourseSectionPending,
  staticData: { namespaces: NAMESPACES },
})
```

- Un layout déclare `const NAMESPACES = [...] as const` au-dessus de `export const Route` et les précharge. Lorsqu'il n'en a aucun, il omet l'option ; il n'y a pas de `namespaces: []`.
- Un layout nomme chaque namespace dont ses pages et leurs composants ont besoin, y compris ceux d'autres fonctionnalités, sous forme de simples chaînes dans ses `NAMESPACES`. `/app` liste `pages.license`, `pages.withdrawal` et `withdrawal.validations`, car sa vue d'ensemble affiche la carte et l'offre de licence et sa page de licence la carte de rétractation ; `/admin/users` liste `pages.admin.customers`, `pages.admin.orders` et `pages.admin.users.license` ; et `/_site/_marketing` et `/_site/docs` listent `auth.validations`, car leurs pieds de page affichent le formulaire de la newsletter, et le layout marketing aussi `withdrawal.validations`. Retirer une fonctionnalité supprime ses fichiers de messages, et la règle d'élagage supprime chaque chaîne qui nomme l'un d'eux ([Tests](/docs/conventions/testing#tests-follow-the-features)).
- Le composant, lorsque le layout en affiche un, est nommé `<Name>Layout` et place un `<Outlet />`.
- Un guard va dans le `beforeLoad` du layout qui possède la zone : `beforeLoad: requireAdmin` dans `admin.tsx`, `requireSignedIn` dans `app.tsx`, les deux layouts de la zone d'authentification. Les guards ne décident que de la navigation ; chaque fonction serveur vérifie toujours sa propre permission.

## Ordre des options

`sort-keys` est désactivé dans `src/routes`, car TanStack Router infère les types dans l'ordre de déclaration : les types d'une option viennent des options placées au-dessus. Les options sont classées par ordre alphabétique, sauf celles par lesquelles le routeur infère des types, qui suivent l'ordre de son guide sur le chargement des données : `validateSearch` en premier, avant tout ce qui lit la recherche, puis `loaderDeps`, `context`, `beforeLoad` et `loader`, et `head`, `headers` et `scripts` après `loader`, car ils lisent ses données. `head` reçoit alors tel quel le type que renvoie le loader, sans type écrit à la main, et `code-style/route-option-order` fait échouer une route qui déclare ces options dans un autre ordre :

```tsx title="src/routes/auth.reset-password.tsx"
export const Route = createFileRoute("/auth/reset-password")({
  validateSearch: authSearchSchema.extend({
    error: searchText(),
    token: searchText(),
  }),
  component: ResetPasswordPage,
```

N'écrivez jamais un tableau ou un objet de données directement dans `createFileRoute` ; déclarez-le comme constante au-dessus.

## Paramètres de recherche

`validateSearch` est un `zod.object` construit à partir des utilitaires de `src/lib/search-params.ts` :

| Utilitaire                        | Valeur quand le paramètre est absent ou mal formé | Usage                              |
| --------------------------------- | ------------------------------------------------- | ---------------------------------- |
| `searchText()`                    | `undefined`                                       | Jetons, e-mails, codes d'erreur    |
| `searchFlag()`                    | `undefined`                                       | Booléens                           |
| `searchParam(schema)`             | `undefined`                                       | Tout autre schéma, comme un chemin |
| `searchChoice(choices, fallback)` | `fallback`                                        | Un onglet ou une vue               |

Un texte absent reste `undefined`, si bien qu'une valeur par défaut ne fuit jamais dans une URL que construit le routeur. Un paramètre `searchChoice` est associé à `search: { middlewares: [stripSearchParams({ tab: DEFAULT_TAB })] }`, qui retire la valeur par défaut de l'URL. Une page vers laquelle un autre site renvoie les visiteurs déclare aussi `search: { middlewares: [onlyDeclaredSearch(schema)] }` avec son propre schéma, comme le font `/app` et `/app/license` pour le paiement de Polar : le routeur construit alors son adresse avec les seuls paramètres déclarés, et le serveur redirige une adresse qui porte un autre paramètre vers la même adresse sans lui, avant qu'une vérification ou la page ne le lise. N'écrivez jamais à la main des vérifications `typeof search["x"] === "string"` ; ajoutez un utilitaire lorsqu'un nouveau type de champ est nécessaire. Lorsqu'un enfant a besoin d'un paramètre dont la page a validé la présence, la page l'affine et le lui transmet, comme `auth.reset-password.tsx` transmet `token` à `ResetPasswordForm`. Les pages qui lisent les mêmes paramètres partagent un schéma dans le `.zod.ts` du module qu'elles lisent, que leurs squelettes analysent aussi, comme le font `/app/license` et la partie de la vue d'ensemble qu'ajoute la zone de la licence avec `licenseSearchSchema` (`src/modules/license/license.zod.ts`).

## Squelettes

La navigation doit sembler instantanée : chaque route qui affiche une page a donc un `pendingComponent` qui la reproduit, avec la même mise en page, les mêmes cartes et le même nombre de lignes.

- Les squelettes se trouvent dans le fichier de squelettes de la zone (`admin/products-pending.tsx`, `courses/courses-pending.tsx`) et utilisent `Skeleton` de shadcn.
- Les squelettes sont dans le script d'entrée de chaque page, donc un squelette importe `Skeleton`, les primitives shadcn, d'autres squelettes et les constantes qui fixent ses longueurs, jamais un formulaire ni le fichier qui en contient un ; `pending-imports.test.ts` échoue lorsque l'un d'eux atteint `@tanstack/react-form` (voir [Performances](/docs/conventions/performance#skeletons-stay-in-the-entry-script)).
- Un emplacement de texte reçoit le vrai jeton typographique plus `h-lh scale-y-70`, pour avoir la hauteur de la ligne qu'il remplace : `<Skeleton className="h-lh w-28 scale-y-70 text-label" />`.
- Les longueurs des listes proviennent des constantes qu'utilise la page : `DataGridPending` dans `data-grid-pending.tsx` dessine par défaut `DEFAULT_PAGE_SIZE` lignes, la taille de page de tous les tableaux de l'administration.
- Un squelette de layout affiche le `pendingComponent` de la première route sous son layout qui correspond au chemin courant et en définit un, que `usePagePending(layout)` de `src/hooks/use-page-pending.ts` lit dans l'arbre des routes : `AdminPending`, `AppPending`, `AuthPending` et `MarketingPending` pour leurs layouts, et `AdminUsersPending` et `AdminCourseSectionPending` un niveau plus bas. La route d'une page est donc le seul endroit qui nomme son squelette, quel que soit le layout qui l'affiche ; `/admin/users`, qui redirige vers `/admin/users/all`, définit le squelette de cette page.
- Il n'y a pas de `defaultPendingComponent` pour tout le routeur. `src/router.tsx` règle `defaultPendingMs` sur <RepositoryFact name="navigationPendingMs" unit="millisecond" /> et `defaultPendingMinMs` sur <RepositoryFact name="navigationPendingMinMs" unit="millisecond" />, deux valeurs issues de `src/data/navigation.constants.ts` : une navigation qui n'est pas terminée à ce moment-là affiche le squelette de la route, et le squelette disparaît dès que la page est prête, sans rester affiché plus longtemps. Les routes conservent ces valeurs ; voir [Performances](/docs/conventions/performance#a-slow-navigation-shows-its-skeleton-at-once) pour les mesures qui les justifient.
- Les pages de la documentation dessinent leurs squelettes dans la mise en page de la documentation : `DocsIndexPending` et `DocsPagePending` remplissent les zones de grille de l'article et de la table des matières de Fumadocs, si bien qu'une navigation entre pages de la documentation garde la barre latérale à l'écran. Le composant de page rend le MDX dans son propre `<Suspense key={path}>`, si bien que la barre latérale fonctionne avant le chargement du chunk MDX de la page, et qu'une navigation remplace le HTML serveur de la page précédente au lieu de l'hydrater avec les données de la suivante.

## Liens

- Les liens du routeur prennent une constante : `<Link to={ROUTES.COURSES}>`, `<Link hash={MARKETING_SECTION_IDS.PRICING} to={ROUTES.HOME}>`, ou un modèle de route avec `params` pour les chemins dynamiques. Les `LinkButton` et `SidebarMenuLink` de shadcn prennent `to` de la même façon, et `AnchorButton` prend un `href` pour une adresse hors de l’arbre des routes.
- N'ajoutez jamais le préfixe de locale à un lien du routeur ; la réécriture du routeur l'ajoute. Une URL complète dans la locale courante, pour une valeur qui quitte le routeur sous forme de chaîne, provient de `router.buildLocation({ ... }).publicHref`, comme `use-auth-redirect.ts` construit ses liens de connexion. `localizePathname` sert aux URL construites hors d'un contexte de routeur ou pour une autre locale : e-mails, cibles de redirection de Better Auth, liens dans le MDX et sélecteur de langue.

## Chemins et navigation [#paths-and-navigation]

Chaque chemin et chaque entrée de menu s'écrit une seule fois, dans une seule liste, et une fonctionnalité qui peut être retirée, comme les cours, les produits ou les pages légales, y figure comme un élément qui nomme son propre chemin. Retirer la fonctionnalité supprime ses fichiers et ses noms, et avec eux chaque élément qui en nomme un : les listes n'ont donc besoin ni d'un fichier par fonctionnalité ni d'un barrel. C'est ainsi que la CLI `saasyland` assemble un projet à partir de couches de templates. Seul `scripts/features.ts`, que l'application ne charge jamais, liste les fonctionnalités optionnelles avec leurs fichiers et les chemins qui leur appartiennent, pour que `bun run check:features` puisse vérifier le site sans chacune d'elles ([Tests](/docs/conventions/testing#tests-follow-the-features)).

| Quoi                                             | Déclaré dans                                                                                                                                                                                                                     | Lu depuis                                                                                                       |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Chemins                                          | `src/routes.ts` : un objet `ROUTES` dont les clés suivent l'URL                                                                                                                                                                  | `import { ROUTES } from "~/src/routes"`                                                                         |
| Chemins rendus à chaque requête                  | `REQUEST_RENDERED_ROUTES` dans `src/routes.ts`                                                                                                                                                                                   | `isRequestRenderedRoute` dans `src/routes.ts`                                                                   |
| Entrées de menu                                  | `ADMIN_NAVIGATION`, `ADMIN_COMMAND_ACTIONS`, `ADMIN_DASHBOARD_ACTIONS`, `APP_NAVIGATION`, `APP_RESOURCE_NAVIGATION`, `HEADER_NAVIGATION` et `FOOTER_NAVIGATION` dans `src/data/navigation.ts`, dans l'ordre où elles s'affichent | Les barres latérales, l'en-tête, le pied de page, la palette de commandes et le tableau de bord                 |
| Namespaces des layouts                           | `NAMESPACES` dans la route de layout                                                                                                                                                                                             | Le loader et les `staticData` du layout                                                                         |
| Listes de l'administration et de l'espace client | `DASHBOARD_STATS`, `DASHBOARD_PANELS`, `COMMAND_SEARCHES`, `USER_TABS`, `USER_PROFILE_SECTIONS` et `ACCOUNT_DELETION_NOTICES`, chacune dans le composant qui l'affiche                                                           | Ce composant, son squelette et la route qui charge ses données                                                  |
| Vérifications du site en ligne                   | `LIVE_SITE_CHECKS` dans `src/lib/deployment.ts`                                                                                                                                                                                  | `verifyDeployment` ([Plateforme et tests](/docs/architecture/platform-layer#what-the-worker-and-the-build-run)) |

`src/routes.ts` déclare chaque chemin dans un seul objet, `ROUTES`, et n'importe rien, car tous les environnements d'exécution le chargent : le navigateur, le Worker à chaque démarrage à froid, les scripts Bun, Playwright, `vite.config.ts` et le projet Remotion. Ses clés suivent l'URL : `ROUTES.ADMIN.USERS.ALL` est `/admin/users/all` ; `INDEX` désigne un chemin qui est à la fois une page et le parent d'autres chemins, comme `ROUTES.BLOG.INDEX`, et `BASE` un parent qui n'est pas une page, comme `ROUTES.AUTH.BASE`. Chaque fichier l'importe avec `import { ROUTES } from "~/src/routes"`, et l'objet est déclaré `as const` : chaque chemin garde ainsi son type littéral et `<Link to={ROUTES.COURSES}>` reste vérifié par rapport à l'arbre des routes. Un segment que partagent plusieurs chemins, comme `const BLOG = "/blog"`, est une constante du fichier qui n'est pas exportée, si bien que chaque segment n'est écrit qu'une fois.

Le Worker et le build tiennent leurs listes de la même façon : `REQUEST_HANDLERS` et `DOCUMENT_REWRITES` dans `src/server.ts` et `VITE_PLUGINS` dans `vite.config.ts` sont eux aussi des listes littérales, où une fonctionnalité optionnelle figure comme un élément.

`src/data/navigation.ts` contient les sept menus sous forme de listes littérales, chaque entrée avec sa page dans `to`, la clé complète de son message dans `label` et, dans la console d'administration et l'espace client, son icône `lucide-react`. Le menu d'administration regroupe ses entrées sous un groupe de barre latérale, `key` tiré de `ADMIN_NAVIGATION_GROUP`, et le pied de page ses liens sous une colonne, `key` tiré de `FOOTER_COLUMN`. Le fichier n'importe que `lucide-react`, `~/src/routes` et `~/src/data/navigation.constants`, car le projet Remotion lit le menu d'administration et son job de CI n'installe que les paquets propres à Remotion ; `src/__test__/source-layout.test.ts` échoue quand il importe autre chose. La console d'administration et l'espace client n'existent qu'avec la connexion : leurs entrées nomment donc les chemins de la zone d'authentification et disparaissent avec elle, comme **Se connecter** dans l'en-tête et le pied de page :

```ts title="src/data/navigation.ts"
export const HEADER_NAVIGATION: readonly SiteEntry[] = [
  { hash: MARKETING_SECTION_IDS.PRICING, label: "navigation.core.header.pricing", to: ROUTES.HOME },
  { label: "navigation.courses.header.courses", to: ROUTES.COURSES },
  { label: "navigation.content.header.blog", to: ROUTES.BLOG.INDEX },
  { label: "navigation.content.header.docs", to: ROUTES.DOCS.INDEX },
  { label: "navigation.auth.header.signIn", signedIn: { label: "navigation.auth.header.account" }, to: ROUTES.AUTH.SIGN_IN },
]
```

Un site construit sans la fonctionnalité des cours n'a pas de `ROUTES.COURSES` : la règle d'élagage supprime donc l'entrée **Cours** de l'en-tête, et un groupe ou une colonne qu'elle vide disparaît avec elle, comme la colonne légale du pied de page dans un site sans les pages légales.

Une entrée de l’en-tête ou du pied de page peut nommer un libellé `signedIn` qui remplace le sien pour un visiteur connecté, et son lien mène alors à l’espace de ce visiteur : `/admin` pour un compte qui a l’accès administrateur, `/app` pour tous les autres. `Navigation`, `MobileMenu` et `Footer` lisent les deux menus dans `useSiteNavigation` (`src/hooks/use-site-navigation.ts`), qui fait pointer les entrées `signedIn` vers l’espace dès qu’il le connaît et, sinon, renvoie les listes telles quelles. Il tient l’espace du seul hook de ses `WORKSPACE_HOOKS`, `useVisitorWorkspace` (`src/hooks/use-visitor-workspace.ts`), qui le décide d’après le rôle de la session, avec `hasPermission` et la permission `admin: ["access"]` que vérifie `requireAdmin` ; un projet sans connexion n’a aucun hook, et ses menus restent tels quels.

Le libellé est choisi avant l’exécution de tout script. `SiteEntryLabel` (`src/presentation/components/custom/site-entry-label.tsx`) rend les deux libellés d’une telle entrée, et la variante `signed-in` de `globals.css` affiche **Votre compte** au lieu de **Se connecter** dès que `<html>` porte `data-session`. Seul le libellé affiché occupe de la place : le lien a donc la largeur de son propre texte dans toutes les langues et le même espacement que les autres liens de l’en-tête. Le Worker pose cet attribut sur chaque page HTML qu’il renvoie à une requête qui porte le cookie de session de Better Auth (`markSession`, voir [Cache et SSR](/docs/architecture/caching-and-ssr#prerendering)) : une page prérendue arrive donc avec le bon libellé et aucun lien ne bouge pendant le chargement de la page. Tant que la session n’est pas connue, le lien mène à `/auth/sign-in`, qui renvoie un visiteur connecté vers son espace et affiche le formulaire à tous les autres. Après l’hydratation, `useVisitorWorkspace` ne demande la session que sur une page que le Worker a marquée, fait pointer le lien vers l’espace et garde la marque en phase avec la session : il retire la marque quand la session derrière le cookie a pris fin et la pose quand le visiteur se connecte sans recharger la page. Un navigateur déconnecté ne demande rien, même s’il garde le cookie de Better Auth indiquant la dernière méthode de connexion, qui survit à la déconnexion pour que la page de connexion puisse signaler la méthode par **Dernière utilisation**. Chaque menu donne à ses liens leur position dans la liste comme clé : React modifie donc le même lien au lieu de le remplacer, et un appui commencé pendant le chargement de la session atteint quand même ce lien. Tant qu’une partie de la page n’est pas hydratée, `useVisitorWorkspace` ne renvoie rien, car `useHydrated` répond avec la valeur du serveur pendant que React hydrate : un pied de page qui s’hydrate après l’arrivée de la session affiche le même HTML que le serveur et change ensuite, au lieu de casser l’hydratation.

Chaque entrée d’administration ouvre un écran qui fonctionne sur des données réelles, et la page d’accueil les compte toutes. Un écran dont les données n’ont pas encore de source n’a pas d’entrée (voir [Tableau de bord d’administration](/docs/features/admin-dashboard#real-data-only)).

La barre latérale de l'espace client contient l'entrée **Licence** de la zone de la licence et l'entrée **Facturation** de la zone de facturation, et ses ressources l'entrée **Documentation** de la zone de contenu, au-dessus de l'adresse du support. La base n'a besoin que de `/` et `/api`, ainsi que de l'entrée **Tarifs** de l'en-tête, la seule entrée avec un `hash`, qui renvoie vers la section des tarifs de `/`.

Une statistique du tableau de bord dans `DASHBOARD_STATS` a un `prefetch`, que le loader de `/admin` lance sans l'attendre, et un hook `useValue`, que `DashboardStats` appelle pour lire le nombre dans la frontière `Suspense` propre à la statistique.

`APP_STATEMENTS`, dans `auth.access.ts`, contient les déclarations de permissions, une par ressource, et `scripts/features.ts` nomme les déclarations d'une fonctionnalité qui peut être omise, comme `APP_STATEMENTS.course`, si bien que l'omettre les supprime (voir [Rôles et permissions](/docs/guides/roles-and-permissions)).

Les listes de `src/data/navigation.ts` ont un type déclaré dans `src/data/navigation.constants.ts`, comme `IconEntry` ou `SiteEntry` : une liste dont un projet retire les entrées, comme les actions du tableau de bord sans la zone des paiements, est donc une liste vide qui passe toujours la vérification des types. `navigation.test.ts` vérifie que le `to` de chaque entrée est un chemin de l'arbre des routes et qu'aucun menu ne nomme deux fois une page ou un libellé.

Le `label` d'une entrée est la clé complète de son message, comme `navigation.courses.admin.courses`, et le message se trouve dans le fichier de la fonctionnalité à laquelle appartient la page, `messages/<locale>/navigation.<feature>.json` : retirer la fonctionnalité supprime donc aussi ses libellés. Un composant l'affiche avec `t(entry.label)`, tiré de `useTranslations()`. Une section d'administration définit les libellés de ses sous-pages dans le fil d'Ariane dans les `breadcrumbs` de son entrée, du segment de chemin à la clé, comme `create` vers `navigation.courses.breadcrumbs.create`. Un onglet de la gestion des utilisateurs, une recherche de la palette de commandes et une statistique du tableau de bord nomment eux aussi la clé complète de leur libellé, comme `navigation.team.userTabs.invitations`, `navigation.auth.search.users` et `dashboard.courses.learners`, et un panneau du tableau de bord lit ses textes sous sa `key` dans `dashboard.<feature>.json`. Ces deux sortes de fichiers sont des namespaces racine : chaque menu peut donc afficher le libellé de n'importe quelle entrée. Ce qui appartient au menu lui-même reste dans son namespace : `groups.<group>` dans `pages.admin.sidebar`, `columns.<column>` dans `components.custom.footer` et l'appel à l'action, le bouton du menu et le lien d'évitement de l'en-tête dans `components.custom.navigation`. `navigation.test.ts` échoue quand une entrée, sa variante pour un visiteur connecté, un élément du fil d'Ariane, un onglet de la gestion des utilisateurs ou une recherche de la palette de commandes n'a pas de message dans une locale, et `admin-dashboard.component.test.tsx` quand une statistique n'en a pas.

Les pages rendues par le Worker à chaque requête, comme `/admin`, `/auth` ou `/courses`, sont listées dans `REQUEST_RENDERED_ROUTES`, dans `src/routes.ts`. Le plugin TanStack Start de `vite.config.ts` les exclut du prérendu avec `shouldPrerender` (`src/lib/prerender.ts`), qui appelle `isRequestRenderedRoute`, si bien qu'elles ne figurent pas non plus dans le sitemap des pages, et `buildPageHead` leur attribue la carte du site, sauf si la route passe sa propre image. Être rendue à chaque requête ne retire pas une page des résultats de recherche : les pages de cours sont listées dans un sitemap que le Worker écrit à partir de D1 (voir [Référencement et aperçus sociaux](/docs/features/seo#course-sitemap)). Vite ne résout pas l'alias `~` pendant qu'il charge sa propre configuration : `prerender.ts` importe donc `src/routes.ts` par chemin relatif.
