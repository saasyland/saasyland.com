`bun run check` uruchamia `bun run generate:cn`, `bun run check:comments`, `bun run check:i18n`, `bun run check:content` i `bun run check:flows`, a następnie `vp check`, który w jednym przebiegu formatuje kod przez oxfmt, lintuje go przez oxlint i sprawdza typy przez TypeScript, z konfiguracją w `vite.config.ts` i `tsconfig.json`. CI uruchamia to samo polecenie. Nic tutaj nie jest kwestią gustu: jeśli narzędzia przepuszczą kod łamiący regułę z tej strony, odrzuci go przegląd kodu.

## Czego pilnują narzędzia

oxlint traktuje kategorie `correctness`, `nursery`, `pedantic`, `perf`, `style` i `suspicious` jako błędy, z włączonymi regułami uwzględniającymi typy i sprawdzaniem typów. Limity, które najmocniej wpływają na kształt kodu:

Nadpisania są wąskie i dotyczą konkretnych plików: testy i wspólne pomocnicze moduły testowe w `src/platform/testing` łagodzą `no-magic-numbers`, `no-await-in-loop`, `unicorn/no-null`, `hydration/no-clock-or-locale-in-render` i `admin-data/no-literal-data`; `src/presentation` i `src/hooks` łagodzą `typescript/consistent-return`; mocki testowe łagodzą `require-await`; `src/routes` wyłącza `sort-keys`, ponieważ opcje tras mają własną kolejność (zobacz [Pliki tras](/docs/conventions/routes)); a trasy, komponenty i pliki danych panelu administracyjnego włączają `admin-data/no-literal-data` (zobacz [Panel administracyjny](/docs/features/admin-dashboard#real-data-only)). Cały `src` włącza `radius/no-off-scale`, `type/no-off-scale` i `type/mono-for-code`, a testy i `src/platform/testing` je wyłączają; `src/presentation/social-card.tsx` wyłącza `type/no-off-scale`, ponieważ Takumi renderuje kartę społecznościową jako obraz o stałym rozmiarze, którego rozmiary tekstu są ustawione w stylach inline, a nie na skali typograficznej strony (zobacz [Motyw](/docs/ui/theme#type-scale)).

`tsconfig.json` dodaje rygorystyczne flagi, które zmieniają sposób pisania kodu: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals` i `noUnusedParameters`. Odczyt po indeksie może zwrócić `undefined`, właściwości opcjonalnej nie można jawnie ustawić na `undefined`, a sygnaturę indeksu odczytuje się jako `record["key"]`.

Formatter zapisuje kod bez średników, z podwójnymi cudzysłowami, przecinkami końcowymi i szerokością wiersza <RepositoryFact name="printWidth" />. Sortuje też importy w stałe grupy, klasy Tailwind w `className` i wywołaniach `cn` oraz skrypty w `package.json` według nazwy (`sortPackageJson: { sortScripts: true }`), więc nigdy nie porządkuj żadnego z nich ręcznie: `vp check` kończy się błędem, gdy któryś z nich jest w złej kolejności. Polecenia opisuje strona [Lint i formatowanie](/docs/tooling/lint-format).

## Renderuj to, co wyrenderował serwer

Strona renderuje się dwa razy: na serwerze i ponownie w przeglądarce, gdy React hydratuje HTML. Oba renderowania muszą wypisać ten sam tekst, inaczej React zgłasza niezgodność hydratacji (błąd #418) i renderuje stronę od nowa. Dlatego kod renderujący nigdy nie odczytuje zegara ani języka środowiska uruchomieniowego, bo po obu stronach są one różne: żadnego `new Date()` bez argumentu, żadnego `Date.now` ani `toLocaleString`, `toLocaleDateString` czy `toLocaleTimeString`. Użyj wartości wspólnej dla obu stron:

- czas względny liczy się od `dataUpdatedAt` zapytania, które odczytało jego dane, jak pokazuje [Internacjonalizacja i języki](/docs/features/internationalization);
- rok wypisywany przez stronę pochodzi z builda: stopka kończy informację o prawach autorskich na `REPOSITORY_FACTS.buildYear`, roku UTC, w którym zbudowano stronę;
- liczby i daty przechodzą przez `useFormatter` z use-intl, w języku strony i strefie czasowej użytkownika;
- oczekiwanie w przeglądarce, takie jak limit czasu aktywacji w `CheckoutActivation`, to licznik czasu uruchamiany w `useEffect`, więc pierwsze renderowanie jest takie jak na serwerze.

`hydration/no-clock-or-locale-in-render`, reguła wtyczki oxlint napisanej w tym repozytorium (`scripts/hydration-lint-plugin.ts`), pilnuje tego w `src/hooks`, `src/presentation`, `src/providers` i `src/routes/*.tsx`. Wszystko tam jest kodem renderującym z wyjątkiem funkcji, które wykonują się później: funkcji obsługi zdarzenia `on…`, podanej jako prop JSX, właściwość obiektu lub zmienna; `queryFn` lub `mutationFn`; oraz callbacku przekazanego do `useEffect`, `useLayoutEffect`, `useCallback`, `setTimeout`, `setInterval`, `requestAnimationFrame` lub `addEventListener`. Te listy we wtyczce to lista dozwolonych wyjątków: nowy rodzaj odroczonego callbacku dopisuje się właśnie tam, razem z przypadkiem testowym w `src/__test__/hydration-lint-plugin.test.ts`, nigdy komentarzem wyłączającym regułę.

## Komentarze [#comments]

Domyślnie nie pisz komentarzy: ani w TypeScript, TSX, testach, skryptach, konfiguracji, CSS, ani w workflowach. Znaczenie niesie zamiast tego nazwa, a uzasadnienie trafia do komunikatu commita, do pull requesta lub do tej dokumentacji.

```ts
const INCLUSIVE_END = 1
const FIRST_SEQUENCE = 1
const UNINSTALLED_POLAR_SDK_OPTIONAL_PEERS = [/^@opentelemetry\//u, "ioredis"]
```

Pierwsze dwie pochodzą z `video.delivery.ts` i `release.ts`, trzecia z `src/integrations/polar/polar.vite.ts`: bez takiej nazwy każda z nich wymagałaby komentarza.

Komentarz ma sens tylko wtedy, gdy czytelnik kodu naprawdę musi wiedzieć, gdzie zapisano uzasadnienie, i wtedy wskazuje to miejsce zamiast cokolwiek tłumaczyć. Kontrole przepuszczają dwie postaci i nic więcej:

- Komentarz z linkiem: jeden wiersz, którego treścią jest link do miejsca z uzasadnieniem, poprzedzony co najwyżej <RepositoryFact name="linkCommentWords" /> słowami. Linkiem jest adres `https://`, na przykład strona dokumentacji, README lub roadmapa na GitHubie albo zgłoszenie czy pull request w projekcie zależności, albo ścieżka dokumentacji tej strony zaczynająca się od `/docs/`: `// https://github.com/TanStack/router/issues/8933` lub `// See /docs/conventions/code-style#comments`. Komentarz blokowy i komentarz w JSX mają tę samą jednowierszową postać, a w wierszu nad nim i pod nim nie może być innego komentarza.
- Tag wersji w workflowie: wiersz YAML `uses:`, który przypina akcję do 40-znakowego SHA commita, kończy się tagiem, pod którym ten commit wydano, `# v4` lub `# v7.0.0`. Plik YAML nie przyjmuje żadnego innego komentarza.

Wszystko inne nie przechodzi: wyjaśnienie, baner, `TODO`, zakomentowany kod, drugi wiersz, tekst po linku i komentarz-dyrektywa, nawet jeśli kończy się linkiem.

Tej reguły pilnują dwie kontrole, a obie podają plik, wiersz i sposób poprawki:

- `code-style/no-comments`, reguła wtyczki oxlint z repozytorium (`scripts/code-style-lint-plugin.ts`), zgłasza każdy komentarz poza komentarzem z linkiem w plikach, które czyta linter, w edytorze i w `vp check`.
- `bun run check:comments` uruchamia `scripts/check-comments.ts` przed linterem, w `bun run check` i w hooku pre-commit. Parsuje każdy plik TypeScript, JavaScript, CSS i YAML, który Git śledzi lub by dodał, za pomocą oxc dla kodu, PostCSS dla stylów i pakietu `yaml` dla YAML, więc `//` w adresie URL lub wyrażeniu regularnym, `/*` w globie CSS i `#` w ciągu znaków YAML nie są komentarzami. Sprawdza to, czego linter nie czyta: `e2e`, `remotion`, pliki deklaracji, arkusze stylów, workflowy oraz komentarz `/* oxlint-disable */`, który linter wykonuje, zanim zadziała jakakolwiek reguła.

Zwolnione są pliki, które `.gitattributes` oznacza jako `linguist-generated`, spośród których kodem są `src/routeTree.gen.ts` i `src/types/worker-configuration.d.ts`, oraz wiersz `#!` skryptu, którego gramatyka JavaScriptu nie uznaje za komentarz. Typ, którego kompilator potrzebuje wszędzie, trafia do `types` w `tsconfig.json`, tak jak typy globalne Vitest, a nigdy do komentarza `/// <reference>`.

## Bez furtek

Nigdy nie pisz `oxlint-disable`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, rzutowania `as` ani `any`, żeby reguła przestała zgłaszać błąd. Reguła, która zgłasza błąd, wskazuje problem w budowie kodu; zmień budowę. Kontrole odrzucają każdą z tych furtek: `typescript/ban-ts-comment` trzy dyrektywy kompilatora nawet z opisem, `typescript/consistent-type-assertions` każdą asercję poza `as const`, `typescript/no-explicit-any` typ `any`, a `code-style/no-comments` i `bun run check:comments` każdy komentarz wyłączający. Komentarz `eslint-disable` i tak niczego nie wyłącza (`respectEslintDisableDirectives: false`).

- **Waliduj zamiast stosować asercje typów.** Dane z magazynu danych, z sieci lub z żądania parsuje Zod: `src/lib/github.ts` odczytuje zapisaną w cache liczbę gwiazdek przez `cachedStarCountSchema.safeParse(await env.CACHE.get(CACHE_KEY, "json")).data`, co daje liczbę albo `undefined`, nigdy domysł.
- **Zawężaj strażnikiem typu.** `isRole` w `src/integrations/better-auth/auth.roles.ts` i `isSupportedLocale` w `src/integrations/use-intl/i18n.paths.ts` zawężają `string` do unii prawdziwym sprawdzeniem.
- **Podaj typ, zamiast go wymuszać.** Nadaj wartości potrzebny jej typ tam, gdzie jest deklarowana: pasek boczny shadcn deklaruje `SIDEBAR_MOBILE_STYLE: StyleWithCssVars`, czyli właściwości CSS wraz z jego niestandardową właściwością `--sidebar-width`, zamiast rzutować literał obiektu.
- **Sprawdzaj, nie konwertuj.** `as const` i `satisfies` są dozwolone, ponieważ nigdy nie zmieniają typu: `POLAR_ORDER_STATUS` kończy się na `as const satisfies Record<string, models.OrderStatus>`, więc literówka w statusie Polara nie przejdzie kompilacji.
- **Przebuduj kod, gdy kontrakt biblioteki stawia opór.** Opakuj wartość w obiekt, podziel funkcję lub odczytaj dane z typowanego źródła zamiast rzutować.

## Null i undefined

Poza testami i `src/platform/testing` brakująca wartość to `undefined`, a `null` nigdy nie jest zapisywany jako wartość. Linter dopuszcza go tam, gdzie wymaga tego API: w porównaniu z wartością, która może być `null`, na przykład z kolumną dopuszczającą NULL (`entry.completedAt !== null` w `course.outline.ts`), oraz w referencji React do elementu DOM, która zaczyna się od `useRef<HTMLElement>(null)`, bo React typuje `ref` jako `RefObject<T | null>` i przy odmontowaniu ustawia go z powrotem na `null` (`course-showcase.tsx`). Nigdy nie zamieniaj `null` zwracanego przez API na brak wartości za pomocą `?? undefined`; `code-style/no-undefined-fallback` odrzuca taki kod. Najpierw zwaliduj dane wejściowe, żeby wywołanie nie mogło się nie powieść, albo użyj parsera, który już zwraca `undefined`. Najczęstszym przypadkiem są parametry wyszukiwania, a `searchParam(schema)` w `src/lib/search-params.ts` zwraca `undefined` dla brakującej lub błędnej wartości:

```ts
export const authSearchSchema = zod.object({
  redirect: searchParam(callbackPathSchema),
})
```

## Operatory trójargumentowe i wczesne powroty

Operator trójargumentowy mieści się w jednym wierszu, np. `{t(course === undefined ? "create" : "save")}` w `course-form.tsx`. Wszystko, co dłuższe, oraz każdy wybór między dwoma fragmentami JSX staje się wczesnym powrotem, parą warunków `&&` lub małym komponentem; klasa warunkowa staje się wywołaniem `cn("base", { "classes": condition })`. `code-style/no-multiline-ternary` odrzuca każdy operator trójargumentowy rozciągający się na kilka wierszy, także taki, który formatter złamał, bo przekroczył szerokość wiersza. `src/routes/auth.reset-password.tsx` renderuje swoje dwa stany dwoma warunkami:

```tsx
{hasValidToken && <ResetPasswordForm token={token} />}
{!hasValidToken && (
  <>
    <p className="text-body text-pretty text-destructive">{t("form.invalidToken")}</p>
```

Funkcje kończą się wcześnie w przypadkach szczególnych, a główna ścieżka zostaje bez wcięcia, tak jak `hasLessonAccess` w `src/modules/lesson/lesson.access.ts`:

```ts
export const hasLessonAccess = (access: Lesson["select"]["access"], viewer: Viewer): boolean => {
  if (access === LESSON_ACCESS.PREVIEW || viewer.isStaff) {
    return true
  }

  if (access === LESSON_ACCESS.ACCOUNT) {
    return viewer.userId !== undefined
  }

  return viewer.entitled
}
```

Żadna gałąź nie wypisuje też brakującej wartości: `code-style/no-undefined-branch` odrzuca operator trójargumentowy z gałęzią `undefined` lub `null` i każde `return undefined`. Zamiast tego napisz, co kod robi: zakończ funkcję wcześniej warunkiem na jej początku, odczytaj wartość, której może brakować, przez `?.` albo przez `??` z prawdziwą wartością domyślną, zwróć to, co znajdzie mapa albo `find`, renderuj JSX przez `&&`, a hookowi wtyczki Vite daj filtr z identyfikatorami, które obsługuje, żeby Rolldown nie wywoływał go dla żadnego innego. Tak `scripts/repository-facts.ts` udostępnia swój moduł wirtualny:

```ts title="scripts/repository-facts.ts"
    load: { filter: { id: exactRegex(RESOLVED_MODULE_ID) }, handler: () => moduleSource },
    name: "saasyland:repository-facts",
    resolveId: { filter: { id: exactRegex(MODULE_ID) }, handler: () => RESOLVED_MODULE_ID },
```

## Nazwane stałe

Liczby inne niż `0` i `1` mają nazwy (`COURSE_STALE_MS = 60_000`, `LESSON_PROGRESS_SAVE_INTERVAL_MS = 15_000`). `0` i `1` zapisuje się jako literały, jak w `.limit(1)`, `index + 1` i `toHaveBeenCalledTimes(1)`, chyba że niosą własne znaczenie: kod wyjścia procesu to `FAILURE_EXIT_CODE`, a liczony włącznie koniec zakresu bajtów HTTP to `INCLUSIVE_END`. Wartości należące do domeny, takie jak statusy, rodzaje, poziomy dostępu, pakiety, role i wartości zdarzeń dostawców, deklaruje się raz jako obiekt `as const` i wszędzie przywołuje po nazwie, także w testach i danych testowych:

```ts
export const COURSE_STATUS = {
  DRAFT: "draft",
  PUBLISHED: "published",
} as const
```

Krotka potrzebna kolumnie lub schematowi enum jest budowana z obiektu, a nie przepisywana, i znajduje się obok niego w stałych modułu, które nie importują niczego z Drizzle: `course.constants.ts` deklaruje `COURSE_STATUSES = [COURSE_STATUS.DRAFT, COURSE_STATUS.PUBLISHED] as const`, z której korzystają zarówno `text("status", { enum: COURSE_STATUSES })` w `course.schema.ts`, jak i `zod.enum(COURSE_STATUSES)` w `course.zod.ts`. Kod przeglądarki też czyta krotki właśnie stamtąd: tabela cen iteruje po `LICENSE_TIERS` z `license.constants.ts`.

- Stałe modułu znajdują się w jego `<module>.constants.ts` (`LESSON_ACCESS`, `LICENSE_TIER`); wartości dostawcy znajdują się w pliku `*.constants.ts` integracji (`POLAR_ORDER_STATUS` w `polar.constants.ts`, `AUTH_PROVIDER` w `auth.constants.ts`).
- Długości kolumn i danych wejściowych są nazywane raz, w stałych modułu, i odczytywane zarówno przez schemat Drizzle, jak i schemat Zod: `VIDEO_TITLE_MAX_LENGTH` w `video.constants.ts`.
- Jedno pojęcie ma jedną mapę w jednej konwencji wielkości liter: `ERROR_CODES` dla błędów serwera, `AUTH_ERRORS` dla kluczy błędów Better Auth, `ROLE_CODES` dla ról.
- Nazwy środowisk i kody statusu HTTP deklaruje się raz, w `src/modules/_core/constants/api.ts`: `ENVIRONMENT.PRODUCTION` w `__root.tsx` i w skryptach wdrożeniowych, `HTTP_STATUS.PARTIAL_CONTENT` w obsłudze mediów w Workerze. Żaden plik nie deklaruje własnej mapy żadnego z nich. Jedynym wyjątkiem jest `vite.config.ts`, który porównuje `mode` z samą nazwą: Vite ładuje go, zanim rozwiąże alias `~`, więc nie może importować `api.ts`.
- Stała używana w jednym pliku zostaje w tym pliku, pod importami. Stała używana w kilku plikach trafia do swojego modułu, do `src/data` (zobacz [Pliki i nazewnictwo](/docs/conventions/files-and-naming)) lub do `src/modules/_core/constants`. Nigdy nie dawaj jednej stałej osobnego pliku.
- Typowane nazwy pól API, takie jak `license_key_id`, są właściwościami, a nie wartościami, więc odczytuje się je jako właściwości.

## Hooki w komponentach

Najpierw idą wywołania hooków zwracające pojedynczą wartość, potem pusty wiersz, a potem każdy destrukturyzowany wynik hooka, dzięki czemu wartości, które komponent rozbiera na części, czyta się jako osobną grupę. `src/presentation/components/custom/auth/sign-in-form.tsx`:

```tsx
const t = useTranslations()
const router = useRouter()

const { finishSignIn, redirect } = useAuthRedirect()
```

Komponent wywołuje `useTranslations` raz i nazywa wynik `t`; dlaczego, wyjaśnia strona [Tłumaczenia i treści](/docs/conventions/translations).

## Nazwy i importy

- Pliki i foldery używają kebab-case; komponenty PascalCase; stałe SCREAMING_SNAKE_CASE; funkcje zaczynają się od czasownika (`resolveViewer`, `rethrowAsConflict`); wartości logiczne brzmią jak pytania (`isPending`, `hasLessonAccess`).
- Importy używają aliasu `~/src/...` i pochodzą z pliku, który definiuje dany symbol; jedynym wyjątkiem są ścieżki, które każdy plik importuje jako jedną przestrzeń nazw, `import * as ROUTES from "~/src/routes"`. Nie ma plików barrel: żaden plik nie reeksportuje folderu ani nie łączy list z kilku plików, a `src/routes.ts` sam deklaruje ścieżki. Poza prymitywami shadcn w `src/presentation/components/shadcn/`, z których część reeksportuje opakowywane przez siebie elementy, reeksportują tylko te pliki: `src/integrations/drizzle-orm/drizzle.schemas.ts`, ponieważ Drizzle potrzebuje wszystkich tabel w jednym obiekcie schematu; `src/modules/license/license.utils.ts`, który reeksportuje `orderCurrencySchema` i `polarOrderUrl` dla kodu licencji; oraz `src/integrations/motion/motion.features.ts`, który reeksportuje `domMax` jako pakiet funkcji wczytywany przez `LazyMotion`.
- Zod importujemy w jeden sposób, `import * as zod from "zod"` (albo `import type * as zod from "zod"`, gdy potrzebne są tylko typy), tak jak pokazuje dokumentacja Zod 4; `code-style/zod-namespace-import` odrzuca import domyślny, import nazwany i podścieżkę taką jak `zod/v4`.
- Przesunięcie indeksu o jeden zapisuje się literałem: `lessons[index + 1]` w `course.utils.ts`. Każde inne przesunięcie, także `-1`, dostaje nazwę: `groups.at(LAST_GROUP_INDEX)` w `robots.ts`, nigdy `slice(index, -5)`.
