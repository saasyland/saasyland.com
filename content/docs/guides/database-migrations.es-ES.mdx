---
title: "Migraciones de base de datos"
description: "Cambia un esquema de Drizzle, genera la migración SQL y aplícala a cada base de datos D1."
---

Cloudflare D1 (SQLite) es la base de datos de la aplicación. Los esquemas de los módulos usan `drizzle-orm/sqlite-core`, `src/integrations/drizzle-orm/drizzle.schemas.ts` los reúne y drizzle-kit escribe las migraciones en `src/integrations/drizzle-orm/migrations/` con un prefijo de marca de tiempo.

## Flujo de trabajo

1. Cambia `<table>.schema.ts`. Si es una tabla nueva, expórtala también desde `drizzle.schemas.ts`.
2. Genera el SQL:

```sh
bun run db:generate
```

3. Revisa el archivo generado y haz commit junto con el cambio de esquema.
4. Aplícalo a la base de datos con la que trabajas y a todas las bases de datos remotas antes de desplegar código que dependa de él.

## Comandos

| Comando                          | Base de datos                                                                                      |
| -------------------------------- | -------------------------------------------------------------------------------------------------- |
| `bun run db:migrate:test`        | Base de datos local de pruebas en `.wrangler/test`, usada por Playwright y la vista previa aislada |
| `bun run db:migrate:local`       | Base de datos local de desarrollo; `bun run dev` sigue usando los bindings remotos                 |
| `bun run db:migrate:development` | Base de datos remota del entorno de desarrollo, compartida por defecto con la vista previa         |
| `bun run db:migrate:preview`     | Base de datos remota de la vista previa                                                            |
| `bun run db:migrate:production`  | Base de datos remota de producción                                                                 |

`bun run db:studio:development`, `db:studio:preview` y `db:studio:production` abren Drizzle Studio, y los scripts `db:introspect:*` inspeccionan D1 a través de su API HTTP. Ambos necesitan `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` y `CLOUDFLARE_ACCESS_TOKEN` en el archivo de entorno correspondiente.

## Convenciones del esquema

- Las fechas son `integer(..., { mode: "timestamp_ms" })` con el valor por defecto `(unixepoch() * 1000)`.
- Los booleanos son `integer(..., { mode: "boolean" })`.
- Los índices, las restricciones de unicidad, las claves foráneas y las relaciones se quedan en el archivo del esquema.
- D1 no tiene transacciones interactivas. Mantén una operación atómica con una sola sentencia SQL o con `db.batch([...])`, como hacen `getUsers` y el limitador de peticiones.

## Tests

El binding D1 de pruebas aplica cada archivo SQL de la carpeta de migraciones a una base de datos SQLite en memoria, así que los tests que usan D1 se ejecutan contra el esquema migrado. `src/integrations/drizzle-orm/__test__/` comprueba que el esquema, sus índices y sus claves foráneas se materializan. Consulta [Escribir tests](/docs/guides/writing-tests).

## Datos existentes de PostgreSQL

Estas migraciones solo crean el esquema de SQLite. Mover datos desde una instalación anterior de PostgreSQL requiere una exportación e importación aparte y revisadas.
