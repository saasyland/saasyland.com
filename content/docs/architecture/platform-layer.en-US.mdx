## Worker and bindings

`wrangler.jsonc` sets `src/server.ts` as the Worker entry. The Worker receives these bindings:

| Binding   | Type          | Used for                                                                                                               |
| --------- | ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `DB`      | D1 database   | All tables, including sessions and rate-limit counters                                                                 |
| `CACHE`   | KV namespace  | The GitHub star count                                                                                                  |
| `MEDIA`   | R2 bucket     | Videos, lesson materials and course covers, served under `/media/` by `serveMedia`, `serveAttachment` and `serveCover` |
| `BUNDLES` | R2 bucket     | The CLI's template bundles, served by `serveBundle` under `/bundles/`                                                  |
| `ASSETS`  | Static assets | Prerendered pages and files from `public`                                                                              |

Requests for `/assets/*`, `/fonts/*`, `/robots.txt` and `/llms.txt` are served from static assets without running the Worker. Server code reads bindings, secrets and `waitUntil` from `cloudflare:workers`. `src/server.ts` adds the security headers to every response it returns; files served without the Worker get the subset in `public/_headers` ([Security and hardening](/docs/features/security)).

## What the areas add

No platform file names an area. Each area, such as the courses or the licence sales, adds what it needs to the Worker and the Vite build in files of its own, and a barrel joins them. The root route, the time zone and the live site checks name what they use directly, as the paths and menus do (see [Paths and navigation](/docs/conventions/routes#paths-and-navigation)):

| What            | Each area declares                                             | Barrel                       | Used by                                                                                        |
| --------------- | -------------------------------------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------- |
| Worker handlers | `src/data/<area>.worker.ts`: one `<AREA>_WORKER_HANDLERS` list | `src/data/worker.entries.ts` | `DOCUMENT_HANDLERS` and `REQUEST_HANDLERS` in `src/data/worker.ts`, which `src/server.ts` runs |
| Vite plugins    | `src/data/<area>.vite.ts`: one `<AREA>_VITE_PLUGINS` list      | `src/data/vite.entries.ts`   | `vitePlugins` in `src/data/vite.ts`, which `vite.config.ts` loads                              |

A request handler claims a `pathPrefix` and answers every request under it before the locale middleware, the static assets and TanStack Start, as the courses area's handler does for `/media/` and the licence area's for `/bundles/`. A document handler receives every HTML page the Worker returns, with its locale and the request, and returns the page to send, as the licence area's regional pricing does. `src/server.ts` imports the handlers statically, so they are evaluated on every cold start: a handler file imports only constants and pure helpers and loads anything larger with a dynamic `import()` (see [Performance](/docs/conventions/performance)).

A Vite plugin entry has an `order`, which places its plugins among those of the other areas, and `vitest`, which says whether they also load under Vitest. Vite loads its configuration before the `~` alias resolves, so `vite.ts`, `vite.entries.ts` and every `<area>.vite.ts` import by relative path with the `.ts` extension, and an entry imports its plugin package inside its `plugins` function, so that `vp lint` and `vp fmt` never load it.

`src/routes/__root.tsx` renders `AffiliateReferral` beside the outlet, which loads Affonso's script only while the affiliate programme is open and the visit carries a referral parameter ([Affiliate programme](/docs/features/affiliates)). `TranslationsProvider` formats dates in the zone of the first hook in its `TIME_ZONE_HOOKS`, `useSessionTimeZone` (`src/hooks/use-session-time-zone.ts`), which returns the signed-in user's zone from the session that the route guards loaded, or `UTC`; a project without sign-in has no hook, and the provider uses `UTC` as well. `useSiteNavigation` takes the visitor's workspace for the header and the footer from the one hook in its `WORKSPACE_HOOKS`, `useVisitorWorkspace`; `getRouter` passes every failed query and mutation to each handler in `QUERY_ERROR_HANDLERS`, the auth area's `recheckRefusedSession`; and `useErrorMessage` finds the namespace that translates an error's message in `ERROR_NAMESPACES`, which spreads the auth area's `AUTH_ERRORS` in beside the core's `ERROR_CODES`. Without sign-in, the menus stay as listed, a failed request rechecks nothing and a message is looked up among `ERROR_CODES` alone. The footer's copyright runs from `APP_FOUNDED_YEAR` to `REPOSITORY_FACTS.buildYear` and names a year they share once, so a project without `REPOSITORY_FACTS` prints the founding year alone. Each is one element or one JSX element that names the feature's own file, so leaving the feature out deletes it with the file.

A deploy check is a package script named `<name>:verify:<environment>`, which an area adds to `package.json` with its own scripts. `bun scripts/run-deploy-checks.ts preview` runs every script that ends in `:verify:preview`, today the auth area's `auth:verify:preview` and the Polar area's `polar:verify:preview`, so a project without one of those areas has neither its script nor its check. No area declares a check for an empty or placeholder secret: `scripts/prepare-deploy-secrets.ts` runs before the deploy checks and refuses one among all the secrets that `wrangler.jsonc` declares.

A live site check names a path and the content type it must answer with after a deploy, always with status `200`. `LIVE_SITE_CHECKS` in `src/lib/deployment.ts` lists them, and `scripts/verify-deployment.ts` requests them after a deploy: the home page, `robots.txt`, the sitemap, the site card, the organisation logo and `/api`, the session endpoint, the sign-in with every provider, the blog feed and `/courses`, which renders from D1 on every request. A check with a `post` sends its JSON body from the site's own origin instead and hands the JSON answer to `findProblems`: `signInPost` in `src/lib/auth.ts` starts the sign-in with every provider in `OAUTH_PROVIDERS` this way and refuses an authorize URL that is not on the provider's host, carries a `client_id` in another format or has a `redirect_uri` that does not return to the deployed domain ([OAuth providers](/docs/features/oauth)). A check names its feature's path or helper, so a project without the feature has no check for it.

An area can also define a list of its own that other areas add to in the same way. The courses area defines course access in `src/data/course-access.ts`, and the licence area grants it in `src/data/license.course-access.ts` ([Courses](/docs/features/courses)). The auth area defines the plugins and emails that other areas add to Better Auth ([Better Auth](/docs/integrations/better-auth)): the auth area itself adds the `haveIBeenPwned` breach check, the polar area the Polar plugin and Resend the auth emails. The polar area defines the Polar webhook events in `src/data/polar-events.ts`, and the licence area and the billing area add the events they handle in `src/data/license.polar-events.ts` and `src/data/billing.polar-events.ts` ([Payments](/docs/features/payments)). A project without one of the areas leaves out the list that area defines together with what the others add to it, so no area imports another that does not depend on it. The licence area exists only on the website and always ships with the courses, so it imports the courses' parts of its pages directly instead of defining a list for them: the locked courses at the end of its offer ([Customer app](/docs/features/customer-app)), the title of the first paid lesson a licence opened ([Users (admin)](/docs/features/users-admin#profile)) and the link to the courses in its purchase confirmation ([Licences](/docs/features/licences#purchase-confirmation)).

The lists of the admin console and the customer workspace live in the component that renders them, and another area joins one as an element that names its own identifier: the user management tabs in `USER_TABS` and the cards of a user's profile in `USER_PROFILE_SECTIONS` ([Users (admin)](/docs/features/users-admin)), the dashboard's statistics and panels in `DASHBOARD_STATS` and `DASHBOARD_PANELS` and the command palette's searches in `COMMAND_SEARCHES` ([Admin dashboard](/docs/features/admin-dashboard)), and the notices of the account deletion in `ACCOUNT_DELETION_NOTICES` ([Settings](/docs/features/settings#delete-account)). What only one area adds is rendered directly, with no list: the course progress next to the workspace's **Courses** entry ([Customer app](/docs/features/customer-app)), the licence's section of the overview, the consent line under the sign-up form ([Legal pages](/docs/features/legal-pages)) and the **Machines** column of the customers table ([Orders and customers](/docs/features/orders#customers)). The sign-up page keeps a list of intros with one entry, the licence's order summary, because it chooses between an intro and its own description ([Licences](/docs/features/licences)). Leaving an area out deletes every list element, property and JSX element that names its files.

The core adds a file to each barrel that only optional areas fill, `src/data/core.worker.ts` with an empty list, so a project without those areas still type-checks and lints, the auth area adds an empty `AUTH_AUTH_PLUGINS` to its plugin list, and the polar area an empty `POLAR_POLAR_EVENTS` to its webhook events. Each module that sends email names the purposes of its emails in its `<module>.constants.ts`, such as `VERIFICATION_EMAIL_PURPOSE` ([Resend](/docs/integrations/resend)).

## Environments

`wrangler.jsonc` defines four environments. `CLOUDFLARE_ENV` selects one for `vp dev` and `vp build`.

| Environment   | Bindings                                 | Used by                                         |
| ------------- | ---------------------------------------- | ----------------------------------------------- |
| `development` | Local D1, KV and R2 in `.wrangler/state` | `bun run dev`                                   |
| `preview`     | Preview D1, KV and R2                    | `bun run build:preview`, `deploy:preview`       |
| `production`  | Production D1, KV and R2                 | `bun run build:production`, `deploy:production` |
| `test`        | Local D1, KV and R2 in `.wrangler/test`  | `bun run build:test`, Playwright                |

Each environment lists its required secrets under `secrets.required`. Values come from the matching `.env.<environment>` file; the deploy scripts refuse an empty or placeholder value and write the declared keys to `.wrangler/secrets.<environment>.json` and pass that file to Wrangler with `--secrets-file`. The `test` environment uses `src/platform/testing/worker.ts` as its entry and the committed dummy values in `.env.test`. `AFFONSO_PROGRAM_ID` is public, so it is a plain Worker variable under `vars` rather than a secret; `production` sets SaaSy Land's own programme ID and `test` a dummy one. The secrets of one module stay together, in the order of `.env.example`, and of `.env.test` for `test`, so an area contributes its secrets as one group; `src/__test__/wrangler.test.ts` compares the names in order and fails when they differ. A blank line between two groups is only for reading, since a formatter may remove it, so the test ignores it.

An area's bindings form a block of their own as well. The R2 buckets belong to areas, `MEDIA` to the courses and `BUNDLES` to the licence sales, so `r2_buckets` comes last in each environment, with one entry per area, and a project without an area leaves its entry out. `wrangler.test.ts` also fails when an environment binds other D1 databases, KV namespaces or R2 buckets than `development`, when a `development` binding is remote, and when `development` shares a resource with `preview` or `production`, and `scripts/verify-bindings.ts` checks every binding the target environment declares without naming any.

## Types

- `src/types/worker-configuration.d.ts` is generated by `bun run cf-typegen` from the `development` environment of `wrangler.jsonc` and declares `Cloudflare.Env`: the `DB`, `CACHE`, `MEDIA` and `BUNDLES` bindings and every secret in `secrets.required`. `src/types/bindings.d.ts` adds `ASSETS`, which Wrangler leaves out.
- An area declares in `src/types/<area>.d.ts` only what Wrangler cannot derive: `affiliates.d.ts` the optional `AFFONSO_PROGRAM_ID` variable, which only `production` and `test` set, `polar.d.ts` the two values of `POLAR_SERVER`, `repository-facts.d.ts` the `virtual:repository-facts` module and `content-indexes.d.ts` the `virtual:content-indexes` module. `use-intl.d.ts` registers the message and format types of use-intl.
- `src/types/router.d.ts` registers the router type and the `staticData.namespaces` route option.

## Test runtime wiring

`src/platform/testing` holds only what cannot belong to one feature:

- `setup.ts`: jest-dom matchers, a binding reset before each test, and the `createServerFn` replacement that runs server functions in-process
- `mocks/cloudflare.ts`: an in-memory SQLite D1 that runs the checked-in migrations, an in-memory KV, an in-memory bucket for each R2 binding of the `test` environment in `wrangler.jsonc` and a `waitUntil` that tests can flush
- `mocks/cache.ts`: `createEdgeCache`, a stub of the Workers cache for the media delivery tests
- `mocks/resend.ts`, `mocks/polar.ts` and `mocks/auth.providers.ts`: strict doubles of the Resend and Polar APIs and of the Have I Been Pwned range API, each in a list of its area's doubles (`RESEND_PROVIDER_DOUBLES`, `POLAR_PROVIDER_DOUBLES`, `AUTH_PROVIDER_DOUBLES`) that `mocks/providers.entries.ts` joins with the core's empty `CORE_PROVIDER_DOUBLES`, and `mocks/providers.ts`, which routes `fetch` to them and resets them in every test and in the browser test Worker
- `mocks/wrksz-themes.ts`: a replacement for the theme library
- `lib/`: the server-function RPC bridge, render helpers, request URL helpers, query runners, and Polar models with signed webhooks
- `worker.ts`: the Worker entry for browser tests, which installs the provider doubles and runs the set-up and test endpoints the areas declare in `e2e/data/<area>.worker.ts` (`worker.entries.ts`): the licence area seeds the test licence key in the Polar double, Resend exposes the delivered email and the newsletter a subscriber's state

See [Testing and CI](/docs/architecture/testing-architecture) for how the suites use them.
